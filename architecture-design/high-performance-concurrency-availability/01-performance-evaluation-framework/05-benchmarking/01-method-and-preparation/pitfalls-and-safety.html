压测注意事项：保护系统，也保护结论

一次压测若影响共享服务，或只测出了压测机上限，哪怕数字很大也没有参考价值。

范围、止损与清理

  • 只测自有或明确授权的隔离目标；确认域名/IP、允许时段、负责人、监控值守及共享依赖。第三方 API 的文档配额不代表压测许可。
  • 事先设定成功率、P99、持续积压、CPU/内存/网络与下游错误等阈值；达到停止条件就停止升档、撤销负载并确认系统恢复，不以打崩为目标。
  • 写请求必须有专用账户和可清理数据；隔离消息、邮件、付款、告警等有副作用的路径。准备恢复/回滚步骤与测试后的数据核对。

最常见的测量陷阱

  1. 测错对象：把非 2xx 响应、重定向到登录页、缓存命中结果当成功；抽样检查状态码和响应体/业务字段。
  2. 生成器先饱和：压测机 CPU、带宽、端口或文件描述符先满，增加客户端并发只增加本地等待；两端都要监控。
  3. 闭环掩盖拥塞：服务变慢后客户端等结果再发，实际到达率下降；若目标是固定到达速率，要换模型并记录被丢弃/积压的请求。
  4. 预热与窗口混杂：冷启动、JIT、缓存升温及恢复期间混入正式统计；显式分段，既保留冷启动结果又独立报告稳态。
  5. 只看平均与成功样本：超时/失败被过滤会让 P99 看上去变好；对比工具的延迟分布、超时和业务日志。
  6. 测试条件漂移：请求体变小、数据库变空、缓存由冷转热、依赖被替身替换或自动扩缩容发生时，不能把两次结果直接作版本比较。

工具边界与报告约束

ab 的 -c 是客户端并发请求数；wrk 的 -c 是连接数。两者都不能直接读作服务端业务并行数。常规固定并发/连接压测也不等于恒定到达率；客户端测得的 Requests/sec 未必是业务成功吞吐。

保留命令、工具版本、服务器配置、请求与响应样本、失败分类、完整时序和监控截图/导出数据。一个结果只对当时版本、环境、数据与负载模型成立；生产容量还需故障切换与流量突刺余量。

压测最大的风险是「测了假的」和「把生产搞挂」

压测有两重风险：一是结果不可信（测了压测机瓶颈、缓存热点、没预热），二是影响真实业务（写脏数据、打垮依赖、触发限流或账单）。这一页把两类问题都列清楚，压测前逐条对照。

安全压测的十条 checklist

① 压测前

  • 明确目标与终止条件（达到 X QPS 或 P99 超 Y 即停）。
  • 通知相关方（DBA、SRE、依赖方、客服）。
  • 准备一键停止与回滚方案。
  • 关闭或豁免相关告警与限流。
  • 确认外部依赖已挡板化。

② 压测中

  • 阶梯加压，每级观察几分钟。
  • 实时监控：服务端与压测机资源都要看。
  • 出现异常立即停止，不要「再看看」。
  • 记录每个阶梯的 QPS、P50/P99、错误率、资源使用率。
  • 有人值守，保持沟通通道畅通。

③ 压测后

  • 清理压测数据（独立库最省事）。
  • 恢复限流、告警、白名单配置。
  • 输出报告：目标、方法、结果、拐点、瓶颈、结论。
  • 把结论沉淀为容量模型，供后续规划。
  • 复盘压测过程本身的问题。

④ 常态化

  • 把压测纳入发布流程（重大变更前后各一次）。
  • 建立基线：每次压测与历史对比，发现性能退化。
  • 用影子流量做常态化验证，比定期全链路压测成本低。
  • 容量模型随业务变化定期校准。

深入自检

为什么压测一定要挡板外部依赖？

因为短信、支付、推送这类调用会产生真实费用与真实副作用（用户收到短信、产生订单）。压测的流量是放大的，可能瞬间产生巨额费用或大量投诉。正确做法是用挡板（mock）拦截，只测自己系统的处理能力，外部依赖用固定延迟模拟。

影子流量和构造流量哪个更好？

影子流量更真实（分布、参数、分支覆盖都贴合），但要求高：需要流量复制设施、写操作隔离、依赖挡板；构造流量更可控（能精确控制 QPS 与场景），适合做极限容量测试。理想组合：日常用影子流量验证，大促前用构造流量做极限压测。

压测时应该测到什么程度就停？

通常测到「拐点」即可——即延迟开始明显恶化、或错误率超过阈值。继续加压到崩溃的价值在于验证限流与降级是否生效（这可以单独做一次「破坏性测试」）。不要在日常压测里反复把系统打死。

全链路压测怎样不影响真实用户？

关键技术是「流量染色」：压测请求带特殊标记，沿链路传递；中间件（MQ、缓存）据此路由到影子 topic/影子库；写操作落到影子表；外部调用被挡板拦截；监控也按标记区分统计。这样压测流量与真实流量共用基础设施但互不干扰。

压测结果比生产差很多，可能哪里错了？

常见：① 压测机与服务端跨地域，网络 RTT 占比过高；② 压测客户端语言/框架效率低（如 Python 单进程）；③ 连接数设置过小；④ 压测数据分布更「重」（大字段、冷数据）；⑤ 压测环境少了 CDN 或本地缓存。要逐项对比生产链路，找出差异。

如何避免压测触发安全风控？

提前与安全/风控团队沟通：把压测源 IP 加入白名单、为压测账号打标记、临时放宽频率限制或关闭某些规则、压测结束后恢复。对于登录、支付等敏感接口，优先用挡板而不是真实调用，避免触发反欺诈模型导致真实账号被误封。
