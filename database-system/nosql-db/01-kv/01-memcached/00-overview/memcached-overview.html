🧱 Memcached：最简主义的内存缓存

纯内存的键值缓存，多线程、无持久化、无数据结构——用极致的简单换取极高的吞吐。

🧱

纯 KV

只存字符串，值 ≤ 1MB

🧵

多线程

充分利用多核

🚫

无持久化

重启数据全丢

📊

Slab 分配

按大小分块，减少碎片

先建立直觉：一个超大号的共享便签墙

Memcached 就像一面便签墙：每张便签有一个编号（key）和一段内容（value）。它只有这一种用法——你不能给便签加结构、不能排序、不能遍历，只能「按编号取」和「按编号贴」。

但正因为简单，它极快且极易扩展：多个线程可以同时贴取，加机器就能扩容。

核心特性

特性说明
数据模型纯 String → String，值最大 1MB（默认）
线程模型多线程，可充分利用多核
持久化无，进程重启数据全部丢失
集群无原生集群，由客户端做一致性哈希分片
淘汰策略主要是 LRU（按 Slab 类分别做）
协议简单的文本协议（也支持二进制）
过期惰性删除：访问时才检查是否过期
最重要的一点：Memcached 是「缓存」而不是「存储」。它不保证数据一定在——内存满了会淘汰，进程重启会清空。所以业务必须假设「随时可能取不到」，取不到就回源。任何把 Memcached 当持久存储用的设计都是错的。

Slab 分配机制

Memcached 把内存切成若干种固定大小的块（slab class），每种大小负责一个范围的 value。写入时按 value 大小选最合适的 slab。

Slab 的两个后果：
① 内存浪费：value 大小若正好卡在两个 chunk 尺寸之间，会浪费一部分空间。
② 局部淘汰：LRU 是按 slab class 分别做的。如果某个尺寸的 slab 满了，即使其他尺寸的 slab 还有大量空闲，也会淘汰该 class 内的数据。因此要避免大量相同尺寸的 value 集中写入。

分布式：客户端分片

Memcached 没有集群概念——服务端各实例互不相识。分片逻辑在客户端：用一致性哈希根据 key 决定发往哪个实例。

  • ✅ 优点：服务端极简单，扩容只需加机器；
  • ❌ 缺点：扩缩容会导致部分 key 重新映射（一致性哈希能把影响降到约 1/N，但仍会miss）；客户端要实现路由逻辑。

🎯 面试问答

Q：Memcached 的数据会丢吗？
A：会，而且丢是设计的一部分：① 进程重启——无持久化，内存数据全部丢失；② 内存满——LRU 淘汰旧数据；③ key 过期——惰性删除。所以业务代码必须假设随时可能取不到，取不到就回源数据库。任何把 Memcached 当作持久存储、或认为「写进去就一定在」的设计都是错误的。

Q：为什么 Memcached 只支持字符串？
A：这是它的设计取舍：只支持 String 让服务端实现极简单（无需解析复杂结构、无需类型相关的命令），从而换取极高的吞吐和极低的操作延迟。代价是灵活性转移到客户端——要存对象就得自己序列化，要修改某个字段就得「整个取出 → 改 → 整个写回」。这也是 Redis 流行的主要原因：它把常用的数据结构直接放到服务端，避免了这些往返。

Q：Slab 机制会导致什么问题？
A：两个：① 内存浪费——value 大小落在两个 chunk 尺寸之间时，会占用更大的 chunk，差额被浪费（可通过调整 growth factor 缓解）。② 局部淘汰——LRU 是按 slab class 分别做的，某个尺寸的 slab 满了就会淘汰该 class 内的数据，即使其他 class 还有大量空闲内存。所以要避免大量相同尺寸的 value 集中写入把某个 class 打满。

Q：Memcached 怎么扩容？
A：它没有服务端集群，分片在客户端：用一致性哈希把 key 映射到实例。扩容就是加机器并更新客户端的实例列表。代价：一致性哈希只能把影响降到约 1/N（N 为节点数）——仍有约 1/N 的 key 会重新映射到新节点，导致这些 key 瞬间 miss，需要回源（这就是扩容时的缓存抖动）。实践中常在低峰期分批扩容，并提前预热。

选择判据很清晰：如果只需要简单的 get/set、value 较大、且希望把多核性能压满 → Memcached；如果需要任何数据结构操作、持久化、发布订阅、Lua 脚本 → Redis。现在的趋势是 Redis 占绝对主导，Memcached 主要留在大规模纯 KV 缓存场景（如 Facebook 级别的缓存层）。

Slab 分配机制与内存浪费

Memcached 把内存切成固定大小的 slab class，每个 class 内的 chunk 大小固定，避免内存碎片但可能产生浪费。

参数默认值含义
-m64 MB最大内存
-f（增长因子）1.25相邻 slab class 的大小倍率
-n48 字节最小 chunk 的 item 结构开销
-I1 MB单 item 最大尺寸（即 value 上限）
-c1024最大连接数

Slab 与命中率

# 启动并查看 slab 分布
memcached -m 2048 -f 1.25 -I 1m -c 4096 -u nobody -d

# 查看各 slab class 的使用情况
echo "stats slabs" | nc localhost 11211
# 关注：chunk_size、chunks_per_page、used_chunks、free_chunks
# 若某个 class 的 used 很高但 free_chunks 也很多 → 可能存在内存浪费

# 查看命中率
echo "stats" | nc localhost 11211 | grep -E 'get_hits|get_misses'
# 命中率 = get_hits / (get_hits + get_misses)，低于 80% 需要排查

增长因子越大，内存浪费越多但 slab class 越少。value 尺寸集中在少数几档时，调大 -f（如 2.0）能减少 class 数量、提高内存利用率；尺寸分散时用小的 -f（1.1~1.25）更合适。

客户端分片与一致性哈希

Memcached 没有服务端集群，分片完全由客户端决定——这既带来简单性，也带来扩容痛点。

一致性哈希实现

# 客户端一致性哈希（伪代码）
import hashlib

class MemcachedRouter:
    def __init__(self, servers, vnodes=150):
        self.ring = {}
        for s in servers:
            for i in range(vnodes):                # 虚拟节点，均衡分布
                k = self._hash(f"{s}:{i}")
                self.ring[k] = s
        self.sorted_keys = sorted(self.ring)

    def _hash(self, s):
        return int(hashlib.md5(s.encode()).hexdigest()[:8], 16)

    def get_server(self, key):
        h = self._hash(key)
        for k in self.sorted_keys:                  # 顺时针找第一个
            if k >= h:
                return self.ring[k]
        return self.ring[self.sorted_keys[0]]       # 环形回绕

# 虚拟节点数 150 是经验值：
#   太少 → 分布不均（热点倾斜）；太多 → 内存与查找开销上升
方案扩容影响说明
取模 hash % N全部失效（N 变了映射全变）绝不可用
一致性哈希仅 1/N 的 key 受影响标准方案
带虚拟节点同上且分布更均匀推荐，vnodes 取 100~200

自检 Q&A

Q：为什么 Memcached 限制 value 为 1 MB？

A：设计取舍，不是技术限制。Slab 分配器需要预先确定 chunk 尺寸，允许超大 value 会让 slab class 数量失控、内存利用率骤降；同时大 value 的网络传输会长时间占用连接（Memcached 单连接串行），拖慢其他请求。可以通过 -I 调到最大 128 MB，但官方不推荐——真有大对象需求应改用对象存储。

Q：Memcached 重启后数据全丢，怎么办？

A：接受它——Memcached 的定位就是“可丢失的缓存”。正确的应对是让应用能承受缓存冷启动：① 预热（启动时批量回填热点 key）；② 限流保护（冷启动时限制打到数据库的并发，防止雪崩）；③ 分层（本地缓存挡一层，即使 Memcached 全空也不至于全打到库）。如果需要持久化的缓存，那就该用 Redis。

Q：多线程为什么没有让 Memcached 明显快于 Redis？

A：因为两者的瓶颈常常不在命令执行。Memcached 多线程避免了单核瓶颈，但 Memcached 功能简单、单命令开销本就极小；Redis 单线程在纯内存操作 + IO 多路复用下已经能到十万级 QPS。差距主要体现在大 value 场景（Memcached 多线程并行传输优势明显）与超高并发（单核打满）时。另外 Redis 6.0 起 IO 多线程已经补上了这块短板。

Q：命中率突然下降怎么排查？

A：按三个方向查——① 内存是否满了：stats 看 bytes 与 limit_maxbytes，满了会大量 LRU 淘汰（evictions 快速增长）；② key 模式是否变了：比如上线了新逻辑带了随机参数，或 TTL 被改短；③ 是否刚扩容/重启：缓存重建期命中率天然低。最直接的诊断是看 evictions 与 get_misses 的增长速率。
