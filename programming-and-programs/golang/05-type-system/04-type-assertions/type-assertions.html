类型断言 x.(T)

成功返回具体类型，失败 panic

断言把接口值转回具体类型；若实际类型不符且未用 comma-ok，会直接 panic。

var i interface{} = "hello"
s := i.(string)     // "hello"
// n := i.(int)     // panic: interface is string, not int
comma-ok 安全断言

永远推荐的形式

用 v, ok := x.(T) 避免 panic；ok 为 false 时 v 是 T 的零值，可优雅降级。

v, ok := i.(int)
if !ok {
    // 不是 int，走默认逻辑
    return defaultVal
}
// 安全使用 v
识别具体错误类型

断言 + errors.As 互补

除了 errors.As，也可直接断言错误的具体类型来读取其字段（如错误码）。

if e, ok := err.(*MyErr); ok {
    fmt.Println("code:", e.Code)  // 读具体字段
} else if errors.Is(err, os.ErrNotExist) {
    // 或按根因判断
}
查询接口能力

断言成「更小的接口」

不关心具体类型，只想知道「它能不能做某件事」，就断言成某个小接口；成功即代表具备该能力。

// 想知道 w 是否支持清空
if c, ok := w.(interface{ Close() error }); ok {
    c.Close()
}
// 更常见的：if rw, ok := w.(io.ReadWriter)
类型分支 type switch

按实际类型分发

type switch 比一连串断言更清晰，特别适合处理异构的 interface{}（如 XML/JSON 解码器按标签选择）。

switch v := i.(type) {
case int:
    fmt.Println("int", v)
case string:
    fmt.Println("string", v)
case nil:
    fmt.Println("nil")
default:
    fmt.Printf("other %T\n", v)
}

接口的内部结构：两个字段

接口变量内部存的是动态类型 + 动态值。理解这一点，类型断言与 nil 判断的所有怪现象都能解释。

接口 = 类型 + 值，两者都空才是 nil
动态类型接口当前持有的具体类型。
动态值该类型的值。
二者都空接口才等于 nil。
类型化 nil赋给接口后接口不为 nil。

两种断言写法

var x any = "hello" // ① 单返回值：失败直接 panic s := x.(string) // 成功 // n := x.(int) // panic: interface conversion // ② 带 ok：失败返回零值与 false（推荐） if s, ok := x.(string); ok { fmt.Println("string:", s) } // 对接口类型断言：判断是否实现了某接口 if w, ok := x.(io.Writer); ok { w.Write([]byte("data")) } // 类型开关：一次判断多种类型 switch v := x.(type) { case string: fmt.Println("str", v) // v 是 string case int: fmt.Println("int", v) // v 是 int case nil: fmt.Println("nil") default: fmt.Printf("other %T\n", v) }
写法失败行为何时用
x.(T)panic你非常确定类型一定是 T
v, ok := x.(T)返回零值与 false绝大多数场景
switch x.(type)走 default 或 nil 分支需要分支处理多种类型
x.(interface)判断是否实现某接口能力探测（如是否支持 Writer）

经验法则：除非你能在同一处证明类型必然成立（比如刚构造出来的值），否则一律用带 ok 的形式。生产代码里裸断言造成的 panic 很难排查。

典型用法与陷阱

错误类型判断

用 errors.As 代替类型断言，能处理包装过的错误。

var pathErr *os.PathError if errors.As(err, &pathErr) { fmt.Println(pathErr.Path) } // 对比：直接断言只能匹配最外层 // pe, ok := err.(*os.PathError) // 包装后就失效

同理，判断哨兵错误用 errors.Is。

从 map[string]any 取值

解析外部 JSON 后的常见操作。

m := map[string]any{"count": 1, "name": "go"} // ❌ 直接断言数字（JSON 数字会变成 float64） // n := m["count"].(int) // panic // ✅ 先按 float64 取再转换 if f, ok := m["count"].(float64); ok { n := int(f) } // 更稳的做法：直接反序列化到结构体

nil 接口的坑

函数返回接口时最容易中招。

func get() error { var err *MyError = nil // 类型化的 nil if badCondition { err = &MyError{} } return err // ❌ 永远不是 nil！ } // ✅ 正确写法 func get() error { var err error = nil // 直接用接口类型 if badCondition { err = &MyError{} } return err }

深入自检

为什么类型化 nil 赋给接口后不等于 nil？

接口内部有两个字段：动态类型与动态值。赋入一个 nil 指针后，类型字段被填上了具体类型（如 *MyError），因此接口本身不再是「空」。这与 C 里 void* 为 NULL 的直觉不同，是最经典的 Go 陷阱。

怎么避免这个陷阱？

两条：一是函数返回错误时直接用 error 类型变量，不要用具体错误类型的变量再返回；二是判断时不要只判 err != nil，必要时用反射或让库保证不返回类型化 nil（这也是 Go 官方建议的写法）。

errors.As 和类型断言有什么区别？

errors.As 会沿着错误链（Unwrap）逐层查找，能匹配被 fmt.Errorf %w 包装过的错误；直接断言只看最外层。现代代码应统一用 errors.As / errors.Is。

类型开关的 default 分支必要吗？

如果输入来源可控且已穷举，可以不写；但处理外部数据（JSON、插件、第三方库）时一定要写 default，否则新类型进来会静默走空逻辑，比 panic 更难发现。

频繁类型断言说明什么？

通常说明抽象设计有问题：本该用接口表达的能力，被塞进了 any 里到处断言。可以考虑定义更合适的接口、用泛型参数化，或者在入口处一次性解析成结构体。

断言、类型分支与反射的取舍

三种方式都能「从接口里取出具体类型」，但性能差一个量级，安全性也不同。选错要么 panic，要么拖慢热路径。

方式写法失败行为性能量级适用
安全断言v, ok := x.(T)返回 ok=false~1~2 ns首选，绝大多数场景
不安全断言v := x.(T)panic~1 ns只在 100% 确定类型时用
类型分支switch v := x.(type)走 default1~3 ns（多分支线性匹配）3 个以上分支
反射reflect.TypeOf/ValueOf需自己判50~500 ns类型在编译期未知（序列化、ORM）

四种写法

// 1) 安全断言（带 ok）—— 默认就用这个
if s, ok := x.(string); ok {
    fmt.Println("string:", s)
}

// 2) 类型分支
func describe(x any) string {
    switch v := x.(type) {
    case nil:      return "nil"            // 注意：nil 分支要写在这里
    case int:      return fmt.Sprintf("int %d", v)
    case string:   return v
    case error:    return v.Error()        // 接口也可以作为 case
    case []byte:   return string(v)
    default:       return fmt.Sprintf("%T", v)
    }
}

// 3) errors.As：断言 error 链里的具体类型（Go 1.13+）
var pe *os.PathError
if errors.As(err, &pe) {           // 会沿 Unwrap 链一直找
    fmt.Println(pe.Path)
}
if errors.Is(err, os.ErrNotExist) { // 判等值
}

// 4) 反射（只在框架里用）
rv := reflect.ValueOf(x)
switch rv.Kind() {                 // 注意是 Kind 不是 Type
case reflect.Slice, reflect.Array:
    for i := 0; i < rv.Len(); i++ { _ = rv.Index(i).Interface() }
}

性能实测参考（Go 1.22，64 位）：安全断言约 1.5 ns，3 分支 type switch 约 3 ns，reflect.TypeOf 约 60 ns，reflect.ValueOf(x).Interface() 约 100 ns。所以在序列化、ORM 这类框架之外的业务代码里，不该出现 reflect——出现就意味着设计可以再简化。

JSON 与 error 处理

# JSON 数字的经典坑（encoding/json 解码到 any 时）
var m map[string]any
json.Unmarshal([]byte(`{"a":1}`), &m)
m["a"].(int)        # panic! 实际是 float64(1)
m["a"].(float64)    # 正确

# 想保留整数精度：用 json.Number
dec := json.NewDecoder(r); dec.UseNumber()
var m map[string]any; dec.Decode(&m)
m["a"].(json.Number).Int64()      # 拿到 int64

# 断言错误的推荐方式（不要用类型断言比较 error 字符串）
if errors.Is(err, sql.ErrNoRows) { ... }        # 等值
var e *mysql.MySQLError
if errors.As(err, &e) && e.Number == 1062 {     # 唯一键冲突
    // 1062 = ER_DUP_ENTRY
}
为什么 v, ok := x.(T) 里 v 在 else 分支不能用？

因为 Go 的作用域规则：ok=false 时 v 是零值，使用它毫无意义且容易掩盖 bug。编译器通过作用域限制直接禁止了这种误用。这也是 Go 的设计哲学之一——让错误用法无法通过编译。

type switch 的分支顺序有影响吗？

有影响。case 是从上到下依次匹配，所以更具体的类型要写在前面。例：如果某个类型同时实现了 error 和另一个接口，把 error 写在前面就会先命中。另外 case nil 只匹配「接口本身为 nil」，不匹配「typed nil」。

反射能替代类型断言吗？

能但没必要。反射是给「编译期不知道类型」的场景准备的（序列化、ORM、依赖注入框架）。业务代码里用反射的代价：① 性能差 1~2 个量级；② 失去编译期类型检查，重构时不会报错；③ 代码可读性大幅下降。判断标准：如果你能在代码里写出类型名，就不该用反射。
