1从"能调用"到"生产可用"

教程里的 function calling 是单轮、单函数、理想 JSON。生产环境面对的是：一次要并行调多个工具、工具之间要嵌套（工具的结果触发下一个工具）、模型吐出的参数不合法、下游超时或报错。把 demo 变成可靠服务，核心是校验、并发控制与失败兜底三件套。

重点：本文聚焦 LLM API 本身的工程加固，不展开通用 agent 工具编排框架。

2并行与嵌套调用模式

模式触发方式注意点
并行调用模型一次返回多个 tool_call并发上限、幂等、聚合顺序
嵌套调用工具 A 的结果作为工具 B 入参深度限制、循环防护
强制单步禁用并行，逐次执行延迟高但易调试

3schema 校验与失败兜底代码

import jsonschema, tenacity

def validate_args(schema, args):
    try:
        jsonschema.validate(instance=args, schema=schema)
        return True, None
    except jsonschema.ValidationError as e:
        return False, e.message

@tenacity.retry(stop=tenacity.stop_after_attempt(3),
                wait=tenacity.wait_exponential(multiplier=0.5))
def call_tool(name, args):
    # 真实工具调用；失败抛异常触发重试
    return dispatch(name, args)

def handle_tool_calls(resp, schemas):
    results = []
    for tc in resp.tool_calls:               # 并行：逐个提交到线程池
        ok, err = validate_args(schemas[tc.name], tc.args)
        if not ok:
            results.append({"id": tc.id, "error": f"schema: {err}"})
            continue
        try:
            results.append({"id": tc.id, "out": call_tool(tc.name, tc.args)})
        except Exception as e:
            results.append({"id": tc.id, "error": f"exec: {e}"})
    return results

务必把"参数非法"和"执行失败"区分开：前者应让模型看到错误并修正，后者走重试或降级。

4调用闭环

图：带校验、重试与错误回灌的生产化闭环

第一层 · 概念与判定

判定是否需生产加固：只要出现"多工具、不可信参数、下游可能失败"任一，就必须上校验与兜底；纯单工具只读 demo 可简化。

  • 工具是否幂等（重试前提）；
  • 参数是否来自模型自由生成（必须校验）；
  • 是否有人工可接受的降级输出。

第二层 · 参数·命令·量化

关键参数与做法：

项建议值
并行上限按下游 QPS 设并发池，避免打爆
重试次数2–3 次指数退避；仅对可重试错误
嵌套深度硬上限（如 5）防循环
超时每个工具独立 timeout，整体 budget

第三层 · 排障与边界

排障与边界：

  • JSON 解析失败：模型偶发多余文本，用宽松解析+重试；
  • 参数幻觉：枚举/范围用 schema 约束，越界即拒；
  • 工具超时雪崩：设熔断，失败率超阈值切降级；
  • 循环调用：嵌套深度计数 + 去重已调用签名。
何时该降级而非重试

下游 5xx/超时且重试仍失败、或整体延迟预算耗尽时，返回"部分结果 + 提示"，而不是无限重试拖垮链路。

第四层 · 原理与取舍

原理取舍：

  • 并行提升吞吐但增加结果聚合复杂度与成本峰值；
  • 严格 schema 提升可靠性却牺牲模型灵活性（把"会干"变"只能按契约干"）；
  • 重试提升可用性但放大成本与延迟，需配合幂等；
  • 结论：把 function calling 当作"带契约的 RPC"，校验与兜底不是可选项。
