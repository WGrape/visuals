①为什么向量数据库会有“一致性”问题

因为 Milvus 的写入是异步的：数据先写 WAL（消息队列），QueryNode 消费后才能被检索；Segment 封口后还要异步建索引。这意味着“写入成功”和“能被搜到”之间存在一个时间窗口。一致性级别就是让你显式声明：我愿意等多久、能容忍多少滞后。

②四个一致性级别

级别语义延迟适用
Strong读到请求发起时刻之前全部已提交的写入最高（要等待时间戳推进）金融/权限类强一致校验、写完立刻要查
Bounded
（Bounded Staleness）		容忍固定时长的滞后（如若干秒），超时则等待中大多数在线检索：既不太慢也不至于读到太久之前
Session
（默认）		保证同一个客户端会话能读到自己刚写入的数据低默认选择：写入方与查询方是同一个进程时的直觉行为
Eventually不保证顺序，读到什么算什么最低离线分析、可以容忍短暂陈旧的推荐/统计
一致性是Collection 级默认 + 请求级覆盖：建表时设 consistency_level，每次 search/query 也可以单独传参覆盖。

③底层机制：时间戳怎么决定“能不能看见”

Milvus 用混合逻辑时钟（TSO）给每次写入打时间戳。查询请求会带上一个 Guarantee Timestamp：QueryNode 必须等到自己消费到该时间戳之后才执行检索——这就是一致性的实现方式。
  • Strong：GuaranteeTs = 当前最新时间戳 → 必须等所有在途数据都可见，最慢但最新。
  • Bounded：GuaranteeTs = 当前时间戳 − 容忍窗口 → 最多等一个窗口，超时就直接查（可能略陈旧）。
  • Session：客户端记住自己最后一次写入的时间戳，下次查询以它为 GuaranteeTs → 只保证“读己之写”。
  • Eventually：GuaranteeTs 设成一个极小值 → 不等待，立刻查当前已可见的数据。

④读路径：growing 段与 sealed 段的可见性差异

Growing Segment（内存中）

持有最新的增量数据，用暴力扫描检索。它是“刚写入就能查到”的原因——只要 QueryNode 消费到该条 WAL，就能立刻命中，不必等 flush 和索引。

Sealed Segment（对象存储）

已持久化的数据，走 ANN 索引检索，快但滞后于 WAL 的最新进度。刚 flush 完、索引还没建好的段会短暂退回暴力扫描。

一次查询 = growing 段暴力扫描 + 各 sealed 段 ANN 检索，结果在 Proxy 归并。所以：

  • growing 段占比高 → 数据最新但查询变慢（暴力计算量大）。
  • 加大写入批次、及时 flush，可以把 growing 段维持在健康比例。
  • 多副本之间消费 WAL 的进度不同，同一条查询打到不同副本可能得到不同结果——这也是强一致 + 多副本代价更高的原因。

⑤怎么选：按业务语义而不是“越高越好”

场景推荐理由
RAG / 语义搜索（读写分离进程）Bounded检索对秒级陈旧不敏感，换来更低延迟
写完立刻查（如入库即校验）Session 或 StrongSession 保证读己之写，Strong 保证全局最新
离线批量导入后统一建索引再上线Eventually没有并发写入，无需等待
删除后必须立刻不可见（合规）Strong只有强一致能确认删除已对所有查询生效
多副本 + 高 QPSBounded / SessionStrong 要等所有副本追平，代价被放大
误区：把 Strong 当默认值更“安全”。实际上它会让查询阻塞在时间戳等待上，写入频繁时 P99 会急剧恶化；同时多副本下要等所有副本追平，成本更高。

⑥用现象反推一致性问题

现象最可能的原因处理
刚插入的数据搜不到级别过低，或 QueryNode 消费 WAL 有堆积提到 Session/Strong；检查消息队列积压
删除了还能查到删除是软删除，副本未追平确认副本消费进度；必要时提高一致性级别
查询结果时好时坏（同一请求两次不同）多副本消费进度不一致 + 低一致性级别提高级别或接受最终一致
查询延迟突然升高Strong + 写入高峰，时间戳等待被拉长降级到 Bounded；写入与查询错峰

一致性是 Milvus 里最容易被忽略、却最能解释“玄学现象”的一节：写入返回 ≠ 可被检索。记住四个级别对应的是“查询在时间轴上的站位”，绝大多数在线检索用 Bounded 就够，只有“读己之写”和“合规删除立刻生效”才需要往上加。
