秒杀系统全链路设计

从「瞬时百万 QPS」到「不超卖、不宕机」：用分层削峰、异步解耦与库存防超卖，把一场风暴变成可承受的细流。

秒杀的本质：一场「读多写少、突发极陡」的压力测试

秒杀的核心矛盾是：瞬时流量远大于系统常态处理能力，但真正能成交的只有极少部分。如果让所有请求都穿透到数据库，库存行被几百万次并发更新，数据库瞬间锁死，正常业务全部受影响。设计目标不是「扛住所有请求」，而是尽快拦截无效请求、把有效请求有序处理。

🔥 流量极陡

开抢瞬间 QPS 可从数百飙到数十万，持续仅几秒到几分钟。

📦 读多写少

绝大部分是「查库存/查详情」的读，真正「下单扣减」比例极低。

🎯 绝对不能超卖

库存 100 件就卖 100 件，多卖 1 件都是资损与客诉。

⏱️ 体验要好

用户要看到「排队中 / 抢光了」，而不是一直转圈或 500。

全链路分层削峰 Layered Load Shedding

把「洪水」从外到内一层层削减：能拦在边缘的绝不进内核，能异步的绝不同步，能缓存的绝不查库。每一层都把流量缩小一个数量级。

图：流量从 100 万 QPS 经四层拦截 + 队列削峰，最终落到数据库的写请求只剩几千。
⚠️ 避坑：不要把「校验库存」和「扣减库存」都放数据库。数据库只应在最后一步做最终确认，前面的所有判断都应在 Redis 完成。

防超卖：库存扣减的三种正确姿势

超卖的根源是「查」和「改」不是原子的。下面三种方案按可靠性递增，实战中常组合使用。

方案做法优点注意
Redis 原子扣减
DECR / Lua		用 DECR stock:key，返回值 ≥ 0 才算抢到；或用 Lua 脚本保证「判断+扣减」原子。性能极高，单机可达十万级 QPS，是秒杀第一道防线。扣减后只是「资格」，最终下单仍需落库确认。
数据库乐观锁
version / CAS		UPDATE stock SET cnt=cnt-1 WHERE id=? AND cnt>0，影响行数为 0 即失败。无需分布式锁，靠 WHERE 条件天然防超卖。高并发下大量 UPDATE 竞争行锁，需配合前置拦截。
Redis + 库存分片把 100 库存拆成 10 个 key 各 10 件，用户随机/按号段落到一个分片，分散热点。破解「大 Key + 单点热点」，避免一个 key 被打满。分片分配与回补逻辑要设计好。
-- Lua 脚本：判断+扣减原子化，避免「超卖」 local stock = tonumber(redis.call('GET', KEYS[1])) if stock <= 0 then return 0 end -- 已售罄 redis.call('DECR', KEYS[1]) return 1 -- 抢到资格
💡 类比：把秒杀想象成 100 张电影票。Redis 是「售票员手里那叠票」，先快速撕票（原子扣减）确认你有资格；真正「选座、出票」的琐事（生成订单）再慢慢异步处理。售票员不会让两个人同时抢到同一张票。

异步化：用消息队列把「下单」和「支付」解耦

抢到资格的用户，前端立即返回「排队中 / 抢购成功」，后端把创建订单的任务丢进 MQ，由订单服务按自身节奏匀速消费。这样即使瞬间 10 万人抢到，数据库也只看到平稳的写入流。

  • 前端：抢到即提示「已锁定，15 分钟内支付」，提升体感。
  • MQ：Kafka / RocketMQ 做削峰缓冲，消费者按 DB 承受能力限速。
  • 订单服务：消费消息 → 落库 → 扣减数据库库存 → 发支付链接。
  • 超时回补：未支付订单到期释放库存（用延时消息或定时任务），避免「占着茅坑不拉屎」。

兜底与降级

🚦 限流兜底

网关层令牌桶，超过阈值的请求直接返回「活动太火爆，请稍后再试」，保护后端。

🔴 熔断降级

库存服务异常时，短暂返回「已抢光」或排队页，避免雪崩拖垮全站。

📢 防刷防黄牛

答题、设备指纹、滑块验证，把机器脚本挡在门外，让真实用户更容易抢到。

🧯 库存售罄标记

Redis 置售罄标志后，后续请求在网关层直接拦截，不再触达任何后端。

🎯 面试问答

Q：为什么不直接用数据库事务扣库存？
A：数据库行锁在极高并发下会成为瓶颈，且事务持有锁期间其他请求阻塞，吞吐量极低。正确顺序是「Redis 快速原子扣减（拦截 99% 无效请求）→ 异步落库做最终一致确认」，数据库只处理真正抢到资格的那一小撮。
Q：Redis 扣减成功但数据库落库失败怎么办？
A：这是「少卖」而非「超卖」，影响较小。可用「库存回滚（INCR 回去）」或「对账补偿任务」定期核对 Redis 与 DB 差额并修正；也可以把下单做成幂等操作，失败重试。
Q：如何防止超卖的终极手段？
A：数据库层 WHERE cnt>0 的乐观锁是最后一道不可绕过的防线，即便前面所有缓存逻辑都出错，它也能保证不超卖。缓存层负责「性能」，数据库层负责「正确」。

秒杀系统的分层拦截与量化

层次拦截手段拦截比例（典型）

CDN/静态化页面静态化，动态数据走接口挡掉绝大部分页面请求

秒杀的核心矛盾：瞬时流量是平时的几百~几千倍，但真实成交只有库存那么多（几百到几千件）。所以设计的本质不是「提升系统容量」，而是层层拦截——让 99.9% 的请求在到达 DB 之前就被挡掉。

核心代码

# 1) Redis 原子预扣库存（核心）
def seckill(user_id, item_id):
    # a) 资格校验（是否重复购买）—— 用 SET 记录已购买用户
    if not redis.sadd(f"buyers:{item_id}", user_id):
        return "already bought"          # sadd 返回 0 = 已存在

    # b) 原子扣减库存
    stock_key = f"stock:{item_id}"
    remain = redis.decr(stock_key)
    if remain < 0:
        redis.incr(stock_key)            # 回滚，别让库存变负
        redis.srem(f"buyers:{item_id}", user_id)
        return "sold out"

    # c) 生成订单号，投递到 MQ（异步落库）
    order_id = gen_id()
    mq.send("seckill_orders", {"order_id": order_id, "user_id": user_id,
                               "item_id": item_id})
    return {"order_id": order_id, "status": "processing"}

# 库存分片：把热点 key 打散
# stock:{item_id}:0 ~ stock:{item_id}:9，每个 100 件
# 随机或按 user_id 哈希选一个分片扣，失败再试下一个
# 效果：单 key QPS 从 10 万提升到 100 万
-- 2) 数据库最终扣减（乐观锁防超卖）
UPDATE items
SET stock = stock - 1
WHERE item_id = ? AND stock > 0;
-- 返回受影响行数：1 = 成功，0 = 已售罄
-- 靠 DB 的行锁保证并发安全，不需要额外的锁

-- 或带版本号的乐观锁
UPDATE items SET stock = stock - 1, version = version + 1
WHERE item_id = ? AND version = ? AND stock > 0;

-- 3) 幂等：防止重复下单
INSERT INTO orders (order_id, user_id, item_id)
VALUES (?, ?, ?)
ON DUPLICATE KEY UPDATE order_id = order_id;   -- MySQL
-- 或用唯一索引 (user_id, item_id) 保证一人一件

-- 4) 超时未支付释放库存
-- 方案 a：延迟消息（推荐，精确）
-- 方案 b：定时扫描（每分钟扫一次 pending 订单）
SELECT order_id FROM orders
WHERE status = 'pending' AND created_at < NOW() - INTERVAL 15 MINUTE
LIMIT 1000;
-- 扫到后：改状态为 cancelled + Redis 归还库存 incr

排障清单

症状原因处理
超卖了预扣与最终扣减不一致；或没用原子操作DB 层必须乐观锁兜底；Redis 用 DECR 不用 get+set
Redis 单 key 打爆所有请求打同一个 key库存分片；或本地缓存 + 异步同步
重复下单没做幂等唯一索引（user_id + item_id）；MQ 消费端幂等
下单成功但支付时没货预扣与真实库存脱节支付时再校验一次；或缩短支付超时
MQ 堆积消费端慢扩容消费者；批量落库；必要时降级（部分订单延迟确认）
用户看到已抢完但还有货预扣后未支付没释放超时释放；释放要归还 Redis 库存
压测很好但线上崩了压测没模拟真实热点分布用真实商品和用户分布压测；单商品热点是主要风险

不超卖的三道保险：① Redis 原子 DECR 预扣（挡住绝大部分）；② 唯一索引保证一人一件；③ DB 乐观锁 WHERE stock > 0 最终兜底。第③ 条是唯一不可省略的——前面任何环节出错，它都能保证不超卖。
