🔎 MongoDB 查询与聚合

MQL 操作符、聚合管道各阶段、$lookup 与性能注意事项

两层查询能力

MongoDB 提供两套东西：MQL 查询（find + 过滤/投影/排序，相当于 SELECT）和聚合管道（Aggregation Pipeline，一串阶段依次处理文档流，相当于 GROUP BY / JOIN / 复杂变换）。

find过滤 + 投影 + 排序 + 分页，走索引
aggregate多阶段流水线：$match → $group → $sort …
$lookup跨集合左外连接（类似 LEFT JOIN）
管道优化$match/$sort 尽量前置，让后续阶段数据更少

查询操作符速查

类别操作符例子
比较$eq $ne $gt $gte $lt $lte $in $nin{age: {$gte: 18, $lt: 65}}
逻辑$and $or $not $nor{$or: [{vip:true},{score:{$gt:90}}]}
元素$exists $type{email: {$exists: true}}
数组$all $elemMatch $size{tags: {$all: ["a","b"]}}
求值$regex $mod $text $expr{name: {$regex: "^A"}}
投影$slice $elemMatch（投影用）{comments: {$slice: -5}}

$elemMatch：数组查询的关键区别

// 文档：{ _id:1, scores: [ {s: 80, t: "math"}, {s: 95, t: "en"} ] }

// ❌ 错：只要数组里「有 80」且「有 en」就命中（可以来自不同元素）
db.c.find({ "scores.s": 80, "scores.t": "en" });   // 命中！

// ✅ 对：要求同一个元素同时满足 s=80 且 t=en
db.c.find({ scores: { $elemMatch: { s: 80, t: "en" } } });  // 不命中
💡 记住：点号多条件 = 跨元素「或」语义；$elemMatch = 同元素「且」语义。这是 MongoDB 数组查询最常见的坑。

聚合管道全景

常用聚合阶段

阶段作用要点
$match过滤尽量放最前，能走索引，还能减少后续数据量
$project选字段 / 计算新字段提前裁掉大字段能显著降低内存
$group分组_id 为分组键；配合 $sum/$avg/$max/$min/$push/$addToSet
$unwind数组展开数组长 N → 变 N 条文档；前面先 $match 很重要
$sort排序内存上限 100MB，超了要 allowDiskUse:true
$lookup左外连接被连接集合不能是分片集合（4.2 前）
$facet一次输入多路输出一个管道同时算「总数 + 分页 + 分桶统计」，省多次往返
$bucket按区间分桶直方图场景
$out / $merge结果写入集合做预计算/物化视图

实战聚合例子

// 例1：统计每个城市的用户数与平均年龄（先过滤再分组）
db.users.aggregate([
  { $match: { status: "active" } },                    // 走索引，先缩小数据集
  { $group: { _id: "$city", cnt: { $sum: 1 }, avgAge: { $avg: "$age" } } },
  { $sort: { cnt: -1 } },
  { $limit: 20 }
]);

// 例2：展开数组后统计标签热度
db.posts.aggregate([
  { $unwind: "$tags" },
  { $group: { _id: "$tags", posts: { $sum: 1 } } },
  { $sort: { posts: -1 } }
]);

// 例3：$lookup 关联订单与用户
db.orders.aggregate([
  { $match: { status: "paid" } },
  { $lookup: {
      from: "users",              // 被关联集合
      localField: "userId",       // 本集合字段
      foreignField: "_id",        // 目标集合字段
      as: "userInfo"              // 输出数组字段名
  } },
  { $unwind: "$userInfo" },       // 左外连接 → 通常只有一条
  { $project: { total: 1, "userInfo.name": 1 } }
]);

// 例4：$facet 一次拿「总数 + 当页 + 分布」
db.items.aggregate([
  { $match: { cat: "book" } },
  { $facet: {
      total:   [ { $count: "n" } ],
      page:    [ { $sort: { price: 1 } }, { $skip: 20 }, { $limit: 10 } ],
      byPrice: [ { $bucket: { groupBy: "$price", boundaries: [0,50,100,200], default: "200+" } } ]
  } }
]);

分页：skip 的陷阱

// ❌ 深分页：skip 越大越慢（要真的走过前 100000 条）
db.items.find().sort({_id:1}).skip(100000).limit(10);

// ✅ 游标分页（keyset pagination）：记住上一页最后一个排序值
db.items.find({ _id: { $gt: lastSeenId } }).sort({ _id: 1 }).limit(10);

skip(n) 的代价是 O(n)——MongoDB 必须先扫描并丢弃前 n 条。翻到第 1000 页时基本不可用。游标分页用「上一页最后一条的排序键」做起点，代价恒定 O(log N)。

性能红线

  • 100MB 内存排序上限：$sort 无索引支撑时内存排序，超 100MB 报错，需 {allowDiskUse:true}（但会变慢）。
  • 16MB 单文档返回上限：聚合结果单条不能超 16MB，需要 $out 落集合。
  • $group 后索引失效：分组输出是全新文档，后续 $match 只能全量过滤。
  • $unwind 会放大：数组平均长 100 → 文档数 ×100，内存也 ×100。
  • $lookup 是逐批匹配：不是 SQL 优化器那种 hash join，被查侧要有 foreignField 索引。

🎯 常见问法与答题要点

Q：$match 和 find 的过滤条件一样吗？聚合里放前面还是后面？

A：语法完全一样。位置必须尽量靠前：①开头的 $match 能走索引（后面的不能）；②越早过滤，后续阶段要处理的文档越少；③MongoDB 优化器虽然会自动下推 $match，但不会把它推进 $group 之后。所以自己写在最前最保险。

Q：$elemMatch 和点号查询到底差在哪？

A：点号多条件是对整个数组做「存在性」匹配——只要数组里某个元素满足 A、某个元素满足 B（可以是不同元素）就命中。$elemMatch 要求同一个元素同时满足所有条件。涉及数组内多条件且要「且」语义时，必须用 $elemMatch。

Q：深分页为什么慢？怎么优化？

A：skip(n) 需要真正遍历并丢弃前 n 条文档，代价 O(n)，翻到 1000 页就要扫几十万条。优化方案：①游标分页用上一页最后的排序值做 $gt 起点（代价恒定，缺点是不能跳页）；②把排序字段建索引，让 skip 至少走索引不回表；③限制最大翻页深度（很多产品只给前 100 页）。

Q：聚合报 "Sort exceeded memory limit of 104857600 bytes" 怎么办？

A：排序超了 100MB 内存上限。三条路：①给排序字段建索引，让 $sort 走索引（最优）；②在 $sort 前加 $match / $project 减少数据量；③加 {allowDiskUse: true} 允许写临时文件（能跑但明显变慢，属兜底）。

Q：$lookup 能替代 SQL 的 JOIN 吗？

A：能实现左外连接，但不建议当 SQL JOIN 用。差异：①它是「对主表每批文档去目标集合查一次」，不是优化器选出的 hash/merge join；②被 lookup 的字段必须有索引，否则目标集合全表扫；③历史版本限制被关联集合不能是分片集合（4.2 后放宽）。高频 join 场景说明应该改用嵌入建模。

Q：$unwind 后面为什么数据变多了？

A：$unwind 把一个含 N 元数组的文档拆成 N 条文档（每条带一个元素）。所以文档数会按数组长度放大，内存占用同步放大。正确做法是先 $match 过滤、再 $project 裁字段、最后才 $unwind，把放大基数压到最小。

Q：$facet 有什么用？

A：一次输入、多路并行输出。典型场景是列表页需要「总数 + 当前页数据 + 筛选分布」，用 $facet 一个管道全搞定，省掉 3 次往返。注意：$facet 每个子管道独立处理同一份输入，输入文档多时开销不小，所以前面的 $match 很关键。
