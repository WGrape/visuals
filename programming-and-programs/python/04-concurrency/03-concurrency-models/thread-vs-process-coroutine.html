线程、进程、协程：怎么选

三者解决的是不同的问题：进程为「真并行」、线程为「轻量共享」、协程为「高并发不阻塞」。在 GIL 的约束下，选错模型要么跑不满 CPU、要么并发上不去。这一篇给你一张决策表。

三者本质

进程、线程、协程是三个层级

进程是 OS 资源分配最小单位，各自独立内存；线程是进程内的执行流，共享内存；协程是用户态的「轻线程」，在单线程内手动切换，不靠 OS 调度。

📦
进程 Process
独立内存、自带 GIL、开销大、真正并行
🧵
线程 Thread
共享内存、受 GIL、轻量、需加锁
🍃
协程 Coroutine
单线程内切换、万级并发、靠 await

GIL 只在单进程内生效。所以多线程无法多核并行，但多进程可以（每个进程一把 GIL）。协程更极端——它根本不在意 GIL，因为它压根不并行，只是「不阻塞地快速切换」。

GIL 下真相

看懂 GIL 才能选对

GIL 让「同一进程的多线程」无法在多核上同时跑 Python 字节码。结论：CPU 密集用多进程，I/O 密集用多线程或协程，高并发网络用协程。

import time, threading, multiprocessing as mp

def cpu_task(n):
    while n > 0: n -= 1

# CPU 密集：多线程被 GIL 卡住，不如单线程
t0 = time.time()
ts = [threading.Thread(target=cpu_task, args=(10**7,)) for _ in range(4)]
[t.start() for t in ts]; [t.join() for t in ts]
print("thread:", time.time()-t0)

# CPU 密集：多进程真并行，明显更快
t0 = time.time()
with mp.Pool(4) as p: p.map(cpu_task, [10**7]*4)
print("process:", time.time()-t0)
GIL 的完整机制（为什么存在、何时释放、3.13 no-GIL）见GIL 完全解析；I/O 时为何释放 GIL 见GIL 与 I/O 细节。
决策表

先判场景，再选模型

一句话口诀：算得多 → 多进程；等得多（网络/磁盘）→ 多线程或协程；连接多/高并发 → 协程。

场景首选为什么
图像/数值计算、加密多进程绕过 GIL，真多核并行
爬虫、调用外部 API多线程 / 协程I/O 等待时释放 GIL
Web 服务器万级连接协程 asyncio单线程扛海量并发，开销极小
混合（既算又等）进程+线程/协程计算交给进程，I/O 交给线程
⚠️ 别用多线程跑 CPU 密集任务——在 CPython 下它可能比单线程还慢（GIL 争抢开销）。也别用多进程跑海量 I/O——进程内存开销大、上下文切换贵，协程更合适。
统一接口

concurrent.futures 一把梭

无论选线程还是进程，推荐用 concurrent.futures 的统一 API：把「执行器」抽象掉，业务代码几乎不变，将来切换模型只换一个类名。

from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

# I/O 密集：线程池
with ThreadPoolExecutor(max_workers=20) as ex:
    r = list(ex.map(fetch_url, urls))

# CPU 密集：进程池（只改这一行）
with ProcessPoolExecutor(max_workers=4) as ex:
    r = list(ex.map(cpu_task, data))

协程不属于这个执行器家族，但它有自己的「并发原语」（asyncio.gather / TaskGroup），详见asyncio 任务与并发。线程共享内存带来的「竞态」问题，见锁与同步原语。

GIL 实测代码

# 实测：CPU 密集任务，多线程 vs 多进程
import time, threading, multiprocessing, os

def cpu_work(n):
    s = 0
    for i in range(n): s += i * i
    return s

N = 30_000_000

# ① 单线程
t=time.time(); [cpu_work(N) for _ in range(4)]; print("单线程  ", round(time.time()-t,2), "s")

# ② 4 线程（受 GIL 制约，反而更慢）
t=time.time()
ts=[threading.Thread(target=cpu_work, args=(N,)) for _ in range(4)]
[t.start() for t_ in ts]; [t_.join() for t_ in ts]
print("4 线程  ", round(time.time()-t,2), "s")     # 通常比单线程慢 10-30%

# ③ 4 进程（真正并行，接近 4 倍速）
t=time.time()
ps=[multiprocessing.Process(target=cpu_work, args=(N,)) for _ in range(4)]
[p.start() for p in ps]; [p.join() for p in ps]
print("4 进程  ", round(time.time()-t,2), "s")     # 通常快 3-4 倍

# IO 密集场景则完全相反：线程/协程远胜进程
# 因为 IO 期间会释放 GIL，切换成本远低于进程

Python 3.13 起有实验性的 free-threading（--disable-gil 编译选项，PEP 703），但短期内生态（C 扩展）还没跟上，生产仍按“有 GIL”来设计。

四种并发模型代码

# ① 进程池：CPU 密集（注意：必须在 __main__ 里，Windows/macOS spawn 模式要求）
from concurrent.futures import ProcessPoolExecutor
if __name__ == "__main__":
    with ProcessPoolExecutor(max_workers=os.cpu_count()) as ex:
        results = list(ex.map(cpu_work, [N]*8))
# max_workers 默认 = os.cpu_count()；CPU 密集就设成核数，不要多

# ② 线程池：IO 密集（线程数可以远大于核数）
from concurrent.futures import ThreadPoolExecutor
# 经验公式：线程数 = 核数 * (1 + 等待时间/计算时间)
# 纯 IO（等待时间 >> 计算时间）可设 核数 * 10 ~ 50，如 8 核设 50-200
with ThreadPoolExecutor(max_workers=50) as ex:
    results = list(ex.map(fetch_url, urls))

# ③ 协程：超高并发 IO
import asyncio, aiohttp
async def fetch(session, url):
    async with session.get(url, timeout=aiohttp.ClientTimeout(total=10)) as r:
        return await r.text()
async def main(urls):
    sem = asyncio.Semaphore(200)          # 关键：限流，别把对方打挂
    async with aiohttp.ClientSession() as s:
        async def g(u):
            async with sem:
                return await fetch(s, u)
        return await asyncio.gather(*[g(u) for u in urls])
asyncio.run(main(urls))

# ④ 混合：协程里调阻塞库
loop = asyncio.get_running_loop()
result = await loop.run_in_executor(None, blocking_call, args)

协程为什么快：把开销拆开看

开销来源线程协程倍数
创建需 clone() 系统调用 + 分配 8 MB 栈只是分配一个对象（几百字节）100×
切换陷入内核、保存寄存器、TLB 可能失效纯用户态，改几个寄存器10 – 100×
调度抢占式（内核随时打断，要加锁保护临界区）协作式（只在 await 处让出）无锁竞争
内存8 MB × 1000 = 8 GB（需调小栈）10 KB × 100000 = 1 GB800×

协作式调度最大的好处是“不用加锁”：因为协程只在 await 处让出，两个 await 之间的代码不可能被打断，天然是原子的。这就是为什么 asyncio 代码里很少看到锁——不是不需要，而是大部分场景不需要。

但反过来，协作式也意味着一个协程不让出就会卡死整个循环。所以协程里绝对不能出现 time.sleep()、requests.get()、密集 CPU 计算——要用 asyncio.sleep()、aiohttp、run_in_executor。

深入自检

有了 asyncio，线程池是不是就没用了？

完全不是。三个场景线程池更合适：① 调用的库不支持 async（requests、boto3、多数数据库驱动）——只能用 run_in_executor 包一层，本质上还是线程池；② 并发量不大（< 100）时线程池代码更简单，心智负担低；③ 遗留同步代码改造——改成 async 会传染（async 函数只能被 async 函数调用），成本极高。判断标准：并发量是否到了线程池撑不住的程度（数千以上）。

协程数量有没有上限？

理论上限很高（10 万级），但实际瓶颈往往在别处：① 文件描述符——默认 ulimit -n 常是 1024，必须调大到 10 万；② 对方服务承受力——几万并发会把下游打挂，所以要 Semaphore 限流；③ 内存——每个连接的缓冲区。所以正确做法是用信号量控制真实并发数，而不是无脑创建海量协程。

多进程的 IPC 开销有多大？

不小。multiprocessing.Queue 传递数据要pickle 序列化 + 管道拷贝，传 1 MB 数据约 1 – 5 ms。所以原则：传少量结果，别传大量中间数据。需要共享大块数据时用 multiprocessing.shared_memory（3.8+）或 mmap，进程启动时就加载好（fork 模式的 copy-on-write 也能省一份）。

怎么快速判断该用哪种？

一句话：看瓶颈是 CPU 还是 IO。跑一下 top——CPU 打满 → 进程；CPU 很闲但吞吐上不去 → IO 密集 → 协程/线程池。再看并发量：低 → 线程池（简单）；高 → 协程。最后看生态：主力库不支持 async 就别硬改，用线程池 + 调大 worker 数通常够用。
