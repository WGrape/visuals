🗄️ 数据库分区 vs 分库分表

一文看清两种"拆数据"策略的本质区别、架构形态与适用场景

本文以单实例 MySQL 表分区和跨实例分片为例；分布式数据库也可能同时使用分区与多节点存储。

需要从系统设计角度选分片键、估算跨片代价时，可接着看数据分片架构选型。

① 核心概念
🔵 数据库分区 Partition

在本文的单实例示例中，应用仍访问同一张逻辑表， 数据库按分区规则组织数据并决定读写目标分区。

一般查询仍可使用同一表名，但分区键、唯一键约束、DDL 和查询是否能裁剪分区，都可能要求应用与表结构配合。

  • 本图示单实例表分区
  • 逻辑上仍是一张表
  • 数据库内核自动路由
  • 需验证 SQL 与约束的兼容性
🟠 分库分表 Sharding

将数据分散到多台数据库实例（分库）或多张真实表（分表）中， 应用通过中间件（Sharding-JDBC / MyCat 等） 或自己计算路由，把请求打到正确的库和表。

跨实例部署可以分摊容量和负载，但热点、跨片操作与迁移成本仍需治理。

  • 本图示多实例横向扩展
  • 物理上是多张独立的表
  • 应用/中间件负责路由
  • 需要改造应用或接入中间件

常见路由策略
• 取模：user_id % N（均匀，但扩容难）
• 范围：按 ID 区间分（冷热不均）
• 一致性哈希：扩容时通常比直接取模迁移更少数据
• 目录表：用元数据表查路由（最灵活）
⚠️ 分库分表的新挑战
• 跨库 JOIN 依赖中间件或应用能力，通常代价较高
• 全局唯一 ID 需要专门生成（雪花算法等）
• 分布式事务一致性难保障
• 扩容/缩容时数据迁移复杂
⑦ 何时用哪个？
🔵 用「数据库分区」的场景
📦单实例容量与吞吐仍足够，主要问题是查询裁剪或历史数据维护
🕐数据有明显的时间序列特征（日志表、订单历史），按时间分区后可快速归档旧分区
🔍查询条件经常带分区键（如按月/年查），能充分利用分区裁剪
💰团队规模小，不想引入中间件复杂度，改造成本敏感
🗑️需要快速清理历史数据（DROP PARTITION 远比 DELETE 快）
🟠 用「分库分表」的场景
🚀已证实单实例容量或处理能力不足，且无法靠索引、归档和升配解决
⚡写并发极高，单台 MySQL 的写吞吐成为瓶颈（如电商大促）
📈业务持续增长，并能承担分片键设计、迁移与跨片访问治理
🌏需要多地域部署，数据按地区分片到不同数据中心
🏢大型互联网公司，已有中间件团队或成熟的 Sharding 框架可用

⑨ 一句话总结

🎯 本质区别

本例的单实例表分区 让应用访问一张逻辑表，由数据库按规则管理分区；它可帮助查询裁剪与历史数据维护，但分区键、约束和 DDL 仍需设计，单靠它也不能增加实例的计算资源。

本例的跨实例分片 把数据和负载分到多个实例，可增加总容量与吞吐；它同时引入路由、热点、数据迁移、跨片查询与事务协调等成本。

💡 类比理解：分区像把一个大文件柜里的文件按年份分隔归档（还是同一个柜子）；分库分表像把文件拆到不同城市的多个仓库（完全不同的物理位置）。

分区与分片的本质区别

维度分区（Partition）分片（Sharding）
分布位置单实例内，同一 MySQL 进程跨实例/跨机器
是否透明完全透明，SQL 无需改需路由，应用层或中间件感知
解决什么单表太大导致的索引与维护问题单机容量/写入吞吐上限
跨片操作无此问题跨片 JOIN / 事务 / 排序都很痛
扩容方式加分区（秒级）数据迁移，成本高
典型规模单表千万~亿级单表 亿级以上或写入打满单机

选型判据：先看瓶颈是容量还是吞吐。单表数据量大但读写压力单机扛得住 → 分区足够（改造成本极低）；单机 CPU/IO/连接数打满 → 必须分片。很多项目过早分片，付出了跨片复杂度却没解决真正的瓶颈。

分区的类型与限制

类型依据典型用法限制
RANGE连续区间按日期（最常用）需预建分区，否则插入失败
LIST离散枚举值按地区/状态新增枚举需改分区定义
HASH哈希取模均匀分布无法按范围裁剪
KEYMySQL 内部哈希类似 HASH，支持非整型同上

分区定义

-- 按日期 RANGE 分区（最常用）
CREATE TABLE orders (
  id BIGINT NOT NULL,
  created_at DATETIME NOT NULL,
  amount DECIMAL(10,2),
  PRIMARY KEY (id, created_at)          -- 分区键<strong>必须包含在主键内</strong>
) PARTITION BY RANGE COLUMNS(created_at) (
  PARTITION p202610 VALUES LESS THAN ('2026-11-01'),
  PARTITION p202611 VALUES LESS THAN ('2026-12-01'),
  PARTITION pmax   VALUES LESS THAN (MAXVALUE)      -- 兜底分区，必须有
);

-- 关键限制（MySQL）：
--   1) 分区键必须是主键/唯一键的一部分 → 无法只对 id 建主键
--   2) 最多 8192 个分区（含子分区）
--   3) 外键与分区不兼容
--   4) 分区裁剪依赖 WHERE 命中分区键，否则全分区扫描

-- 确认是否命中裁剪
EXPLAIN PARTITIONS SELECT * FROM orders WHERE created_at >= '2026-10-15';
-- 输出 partitions 列只列出相关分区即命中

兜底分区 pmax 必须建：否则超出范围的插入会直接报错（Table has no partition for value）。运维上要定期把 pmax 拆分并预建新分区。

分片键选择与扩容代价

分片键优点缺点适用
用户 ID同用户数据集中，单用户查询快大客户数据倾斜最常见，C 端业务
订单 ID分布均匀按用户查要跨片按 ID 点查为主
时间便于归档与冷热分离热点集中在新片日志、流水
地域/租户天然隔离租户大小差异大SaaS 多租户

扩容的数据迁移量：从 N 片扩到 2N 片，取模分片需要迁移 约 50% 的数据；一致性哈希只需迁移 1/N。这是选择分片算法的核心考量。

方案扩容迁移量实现复杂度
取模 id % N约 50%最简单
一致性哈希1/N中等（需虚拟节点）
预分片（如 1024 逻辑片）0（只迁移逻辑片到新机）推荐，前期规划

预分片是最优解：一开始就分 1024 个逻辑分片，物理上只放在 4 台机器。扩容时只搬逻辑分片，路由规则完全不变，无需数据重分布。

自检 Q&A

Q：什么时候该分表？

A：看三个量化信号——① 单表数据量超过 2000 万~5000 万行（B+ 树层数增加，查询变慢）；② 单表物理大小超过 几十 GB（备份、DDL、索引维护困难）；③ 写入 TPS 接近单机上限。只满足一条可以先不拆，优先做索引优化与归档。注意分区能解决 ①②，但解决不了 ③——吞吐问题必须分片。

Q：分片后跨片查询怎么办？

A：三种策略。避免：把查询设计成都能带分片键（最有效）；聚合：在中间件层并行查各片再归并（排序、分组、分页都要在中间件做，代价高）；冗余：建全局索引表或异构索引（如按订单号查就单独维护一张 订单号→用户ID 的映射表）。跨片 JOIN 应尽量消灭在业务设计阶段。

Q：分片后自增 ID 冲突怎么解决？

A：不能再用数据库自增。四种方案——① 雪花算法（64 位：符号位+41 位时间戳+10 位机器 ID+12 位序列，单机每毫秒 4096 个）；② 号段模式（数据库批量分配区间，如一次取 1000 个，性能好但有空洞）；③ Redis INCR（简单但引入依赖）；④ UUID（无序，作主键会严重损害索引性能，不推荐）。生产最常用雪花与号段。

Q：分区表的 DDL 会锁表吗？

A：MySQL 5.6+ 的多数分区操作（ADD/REORGANIZE）是在线的，但仍会短暂拿元数据锁（MDL）。真正的痛点是大表的 ALTER TABLE——即使不锁表，重建索引也要很久。生产建议用 pt-online-schema-change 或 gh-ost（通过触发器或 binlog 同步到影子表再切换），把变更拆成可中断、可限速的步骤。
