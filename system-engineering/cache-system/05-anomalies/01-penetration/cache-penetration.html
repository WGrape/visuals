🕳️ 缓存穿透

查询一个根本不存在的 key，缓存永远不命中，请求每次都直插数据库。

🕳️

定义

查不存在的 key，缓存形同虚设

🥤

空值缓存

查库返回空也写入缓存

🌸

布隆过滤器

用极小内存拦截不可能存在的 key

🛡️

参数校验

在接口层挡住非法请求

先建立直觉：缓存是「漏斗」，漏洞在底下

把缓存想成挡在数据库前面的漏斗：绝大多数请求被漏斗接住直接返回，只有漏下去的才打到数据库。正常业务里，热点数据都被缓存住了，漏下去的量很小，数据库扛得住。

但穿透是这个漏斗底部破了一个洞：有人不断查询根本不存在的数据。这类 key 永远不会进缓存（因为查库也是空，没东西可缓存），于是每一次请求都必然穿过缓存直插数据库。缓存命中率是 0，保护完全失效。

关键特征：穿透的 key 是数据库中不存在的。它不是「缓存还没加载」，也不是「缓存过期了」，而是这个数据本身就没有。所以你无论怎么预热、怎么加大缓存容量都解决不了——因为根本没东西可缓存。

它长什么样：从请求到数据库的完整路径

三种对策，从外到内层层设防

① 参数校验与限流（最外层，成本最低）

很多穿透根本不是攻击，而是业务 bug 或爬虫：比如前端传了 id=-1、id=0、负数、超长字符串。在接口层做基础校验就能挡掉一大半：id 必须为正整数、必须在合理区间、分页大小有上限。

对明显异常的请求（如同一 IP 短时间大量不同 id）做限流与封禁。这一层是「不要把所有防线都压在缓存上」。

② 缓存空值（最常用，改动最小）

思路非常朴素：数据库返回空，也把这个「空」写进缓存。下次同样的 key 再来，缓存命中，直接返回空，不再查库。

// 伪代码：缓存空值
String val = redis.get(key);
if (val != null) {
    return "NULL".equals(val) ? null : val;   // 命中占位值 → 视为空
}
Object db = mysql.query(key);
if (db == null) {
    redis.setex(key, 60, "NULL");   // 关键：空结果也缓存，TTL 要短
    return null;
}
redis.setex(key, 300, db);
return db;
两个必须注意的点：
1. TTL 要短（通常 1~5 分钟）。如果 TTL 太长，会出现「这个数据后来真的被创建了，但缓存里一直是空」的诡异问题。
2. 会占用内存。攻击者若用海量不同随机 key，你会缓存海量空值，反而把内存打满（这叫缓存污染）。所以空值缓存通常要配合第 ① 层限流，或改用布隆过滤器。

③ 布隆过滤器（最彻底，挡在缓存之前）

在系统启动时，把所有真实存在的 key 灌进一个布隆过滤器。请求进来先问它：「这个 key 可能存在吗？」

  • 回答「不存在」→ 一定不存在，直接返回，连缓存和数据库都不用碰。这是决定性的拦截。
  • 回答「存在」→ 可能存在（有极小误判率），继续走正常流程。

布隆过滤器的代价极小：判断一个元素是否属于集合，只需 几个 bit，不像 HashSet 要存完整 key。1 亿个 key 大约只需一百多 MB。

它为什么能省内存？传统集合要完整保存 key（比如 32 字节的字符串）；布隆过滤器只保存 key 经过多个哈希函数映射后的几个 bit 位。它不存数据本身，只存「指纹痕迹」。
布隆过滤器的短板：
• 有误判：可能把不存在的说成存在（漏过），但绝不会把存在的说成不存在。
• 不支持删除：标准布隆过滤器删除会影响其他元素。需要删除请用 Counting Bloom Filter（计数变体）或 Cuckoo Filter。
• 需要预热与同步：数据库新增了数据，要同步加进过滤器；否则新数据会被误判为不存在而永远查不到。

三种方案怎么选

方案拦截位置能挡住代价 / 风险
参数校验 + 限流接口层非法参数、明显爬虫挡不住「合法格式但不存在」的随机 id
缓存空值缓存层重复的同一个不存在 key占内存；TTL 过长会屏蔽后建的新数据
布隆过滤器缓存之前任意不存在的 key，一次命中有误判；不支持删除；需与 DB 同步
工程上的典型组合：参数校验（挡非法）+ 布隆过滤器（挡不存在）+ 缓存空值（兜底残余）+ 限流（防量级攻击）。四层叠加，穿透基本绝迹。

穿透 vs 击穿 vs 雪崩：一张表分清

问题key 是否存在触发条件核心对策
穿透不存在持续查询不存在的数据布隆过滤器 / 空值缓存
击穿存在但刚过期单个热点 key 过期瞬间高并发互斥重建 / 逻辑过期 / 永不过期

🎯 面试问答

Q：穿透和击穿到底怎么区分？
A：看 key 在数据库里是否存在。穿透查的是根本不存在的数据，所以缓存里永远没有，每次都查库；击穿查的是存在的数据，只是缓存刚过期那一瞬间，成千上万的请求同时发现没缓存、同时去查库重建。一个是「永远打不到」，一个是「恰好这一刻打不到」。

Q：布隆过滤器说「存在」，就一定存在吗？
A：不一定，这叫误判（false positive）：它可能把不存在的 key 说成存在。但反过来绝不会发生——它不会把存在的说成不存在。所以「不存在」的回答是可信的、决定性的，这正是它能用来拦截穿透的原因。误判率可以通过增大位数组、增加哈希函数数量压到很低（如 1%）。漏过的少数请求，靠后面的空值缓存兜底。

Q：缓存空值的 TTL 设多久合适？
A：一般 1~5 分钟，不宜过长。太短起不到保护作用，太长会出现「数据后来真的创建了，但缓存里还是空」——用户新增了一条记录却查不到。如果你的业务新增很频繁，就要把这个 TTL 调短，或者改用布隆过滤器并在新增时同步写入。

Q：攻击者用一亿个不同的随机 key，布隆过滤器还有效吗？
A：有效，而且这正是它最擅长的场景。布隆过滤器不是靠「缓存过谁」来工作，而是靠全量合法 key 的指纹集合——随机 key 不在集合里，第一个 bit 检查就被否掉了，与请求量无关。反倒是缓存空值这个方案在这种情况下会失效：一亿个空值会把 Redis 内存撑爆。所以面对海量随机 key，布隆过滤器是正解。

三种缓存异常的区别（先分清）

现象定义根因核心对策
穿透查一个根本不存在的 key，缓存永远不命中，请求直达 DB恶意攻击 / 业务逻辑漏洞空值缓存 + 布隆过滤器 + 参数校验
击穿某个热点 key 过期的瞬间，大量请求同时回源热点 key + 同时过期互斥重建（锁/singleflight） + 逻辑过期
雪崩大批 key 同时过期或缓存集群挂掉TTL 设置集中 / 集群故障TTL 加随机抖动 + 多级缓存 + 限流降级

穿透的本质：缓存里没有这个值，DB 里也没有，所以每次都必然打到 DB。它的危险在于成本不对称——攻击者用极低成本的随机 key，就能逼你付出每次一次 DB 查询。

三道防线与参数

三道防线

// 防线 1：空值缓存（最简单有效）
v, err := cache.Get(key)
if err == redis.Nil {
    row, err := db.Query(id)
    if errors.Is(err, sql.ErrNoRows) {
        cache.Set(key, "", 60*time.Second)   // 空值也缓存，TTL 短一些（30~120s）
        return nil, nil
    }
    if err == nil {
        cache.Set(key, row, 5*time.Minute)
    }
}
// 坑：空值缓存会占内存，随机 key 攻击下会塞满缓存
//   -> 必须配合较短 TTL + 布隆过滤器

// 防线 2：布隆过滤器（先判存在，不存在直接返回）
if !bloom.MightContain(id) {
    return nil, ErrNotFound        // 直接挡掉，不查缓存也不查 DB
}
// 参数换算（这是最该记住的一组数字）：
//   误判率 p 与 位数组大小 m、元素数 n、哈希函数数 k 的关系：
//     m = -n·ln p / (ln2)^2        k = (m/n)·ln2
//   例：n = 1 亿，要求 p = 1%
//     m ≈ 9.58 亿 bit ≈ 114 MB
//     k ≈ 6~7 个哈希函数
//   对照：直接存 1 亿个 8 字节 ID 需要约 800 MB —— 布隆省了约 7 倍

// 防线 3：互斥重建（针对击穿，顺带缓解穿透带来的回源风暴）
v, err, _ := singleflight.Do(key, func() (any, error) {
    return loadFromDB(key)         // 同一个 key 只有一个请求真正回源
})
参数建议值理由
空值 TTL30~120 s太短挡不住，太长占内存且影响「真的插入了」的可见性
布隆误判率1%~3%误判只会多查一次 DB，不会返回错误结果；但要保证不漏
布隆容量按上限的 1.5~2 倍规划布隆过滤器不支持删除（要删用 Counting Bloom 或 Cuckoo Filter）
随机 key 校验ID 必须是正整数、在合理范围、符合业务规则最便宜的一道防线，能挡掉大部分低级攻击
  • 布隆过滤器的特性：说没有就一定没有，说有不一定真有（可能误判）。所以它只适合做「前置拦截」，不能作为唯一依据。
  • 布隆不支持删除：元素无法移除，容量规划要按上限算；需要删除用 Cuckoo Filter 或定期重建。
  • 业务层的兜底：对同一 IP / 用户的请求做频率限制，异常 key 模式（如连续不存在的 ID）触发告警。
  • 不要忘了监控：缓存命中率骤降 + DB QPS 骤升是穿透发生的典型信号，要能自动告警。
只靠空值缓存够吗？

对随机 key 攻击不够：每个新 key 都会写一条空值，缓存会被打满并触发大量淘汰，反而影响正常数据。所以空值缓存 + 布隆过滤器要一起用。

布隆过滤器误判了会怎样？

只是多查一次 DB（不会返回错误结果），影响可控。真正要避免的是漏判——布隆保证不会漏，这是它能用于拦截的前提。

数据真的插入后，布隆过滤器怎么办？

必须同步插入。常见做法是写 DB 后发一条消息更新布隆，或接受短暂不一致（靠空值缓存的短 TTL 兜底）。
