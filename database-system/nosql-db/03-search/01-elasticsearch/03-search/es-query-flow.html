核心速览

Scatter-Gather协调节点把查询广播到所有相关分片，再汇总——ES 分布式的核心模型
Query Then Fetch先各分片打分取 Top-K，再回主取文档；两阶段而非一次做完
近实时写入后默认 1 秒（refresh_interval）才可被搜到
深翻页上限from+size 受 max_result_window（默认 10000）限制

为什么要分两个阶段

假设直接让每个分片各自返回完整文档：一个命中 10 万条、只要前 10 条的查询，就要把 10 万份完整文档从各分片传到协调节点，网络与内存都扛不住。所以 ES 拆成两步：

Phase 1 · Query Phase

每个分片在本地倒排索引上执行查询并打分，只返回 (doc_id, score) 的 Top-K（K = from + size）。不返回文档内容，所以传输量极小。

Phase 2 · Fetch Phase

协调节点把各分片的 Top-K 全局归并排序，确定真正的 Top-N，然后只对这 N 个 doc_id 发 Multi-GET 去对应分片取 _source。

💡 关键点：每个分片返回的数量是 from+size，不是 size。查 from=990, size=10 时每个分片要算 Top-1000，协调节点要归并 分片数 × 1000 条——这就是深翻页昂贵的根源。

相关性是怎么算出来的

ES 默认用 BM25（ES 5.0 起取代 TF-IDF）。直观理解三个因子：

因子含义直觉
词频 TF该词在这篇文档里出现多少次出现越多越相关——但有饱和，出现 20 次不会是 10 次的两倍相关
逆文档频率 IDF该词在所有文档里有多罕见"的""了"几乎每篇都有 → IDF 极低、几乎不贡献分；生僻词权重高
字段长度归一文档/字段越短，命中越"精准"同样的词出现在 100 字短文本比在 1 万字长文里更说明问题
⚠️ 打分是每个分片本地算的。分片各自统计 IDF，如果数据分布不均（某分片恰好缺含该词的文档），各分片的 IDF 会不一致，导致跨分片排序轻微失真。?search_type=dfs_query_then_fetch 会先全局统计再算分（更准但更慢）。小数据量或要求精确排序时才用。

Query DSL 骨架

GET /my_index/_search
{
  "query": {
    "bool": {
      "must":     [ { "match": { "title": "分布式系统" } } ],   // 参与打分
      "filter":   [ { "term":  { "status": "published" } },     // 不打分，可缓存
                    { "range": { "publish_at": { "gte": "2026-01-01" } } } ],
      "should":   [ { "match": { "tags": "架构" } } ],           // 加分项
      "must_not": [ { "term":  { "deleted": true } } ]
    }
  },
  "sort":  [ { "publish_at": "desc" }, { "_score": "desc" } ],
  "_source": ["title", "author", "publish_at"],   // 只取需要的字段
  "from": 0, "size": 20,
  "aggs": {
    "by_author": { "terms": { "field": "author.keyword", "size": 10 } }
  },
  "highlight": { "fields": { "title": {} } }
}
💡 filter vs must：filter 不打分、结果进 节点查询缓存（bitset），明显更快。凡是「是/否」型条件（状态、时间范围、类目）都应放 filter，只有「相关度」条件才放 must。

深翻页的三种方案

方案做法适用限制
from + size"from":990,"size":10前几页，人机交互翻页上限 max_result_window（10000）；越深越慢越吃内存
search_after用上一页最后一条的排序值继续实时深翻页首选不能跳页；排序组合必须唯一（通常加 _id 兜底）
Scroll创建快照游标逐批取全量导出、离线处理不是实时的；占用服务端资源，需及时 clear
// search_after：用上一页最后一条的 sort 值作为起点
GET /my_index/_search
{
  "size": 20,
  "sort": [ { "publish_at": "desc" }, { "_id": "asc" } ],
  "search_after": [ "2026-01-15T10:00:00Z", "doc_id_12345" ]
}

慢查询怎么排查

  • 开慢日志：PUT /my_index/_settings {"index.search.slowlog.threshold.query.warn":"1s"}
  • 用 GET /my_index/_search?profile=true 看各阶段耗时（Query / Fetch / 各子查询）
  • 看是否走了 filter（可缓存）还是全 match（要打分）
  • 避免 *abc* 通配前缀查询、大范围 range、无索引的 script 排序
  • 聚合很慢时检查 size、考虑 eager_global_ordinals 或预计算
  • 分片数过多会让每次查询都广播到所有分片——控制单索引分片规模

🎯 常见问法与答题要点

Q：ES 的查询为什么叫 Query Then Fetch？

A：因为分两阶段。Query 阶段各分片只在本地倒排索引上匹配并打分，返回 Top-K 的 (doc_id, score)，不返回文档内容；协调节点归并排序选出全局 Top-N；Fetch 阶段只对这 N 个 id 发 Multi-GET 取 _source。好处是把网络传输从「10 万份完整文档」压到「几千个 id + N 份文档」。

Q：为什么深翻页慢且不能超过 10000？

A：因为每个分片都要算 from+size 条并全部传给协调节点。from=9900、size=100 时，若有 5 个分片，协调节点要归并 5×10000 = 5 万条，内存与排序开销巨大。所以 ES 用 max_result_window（默认 10000）硬性设限。真正的深翻页用 search_after（游标，代价恒定），离线导出用 Scroll。

Q：filter 和 must 有什么区别？什么时候用哪个？

A：must 参与打分（贡献 _score），filter 不打分且结果会被缓存成 bitset 供后续复用。凡是「是/否」型条件（status、时间范围、类目、地域）都应该用 filter，性能明显更好；只有需要影响相关度排序的文本匹配才放 must。这是 ES 查询优化的第一条。

Q：写入后为什么搜不到？

A：ES 是近实时：文档写入后先进入内存 buffer，要等 refresh（默认每 1 秒）生成新的 segment 后才可被检索。要立刻可见可以：①查询端用 ?refresh=true（强制刷新，代价高，别在高频写入时用）；②写入 API 带 ?refresh=wait_for；③接受 1 秒延迟（推荐）。

Q：协调节点是什么？需要单独部署吗？

A：协调节点不是一种特殊角色，任意节点都可以充当——收到客户端请求的那个节点就是本次查询的协调节点。它负责解析 DSL、广播到相关分片、归并结果。大集群建议部署若干专用协调节点（node.roles 里只留 coordinating），让数据节点专心做存储与搜索，避免协调开销影响数据节点。

Q：副本分片会被查询到吗？

A：会。Query 阶段协调节点会在「主分片或其任一副本」中选一个拷贝发请求，默认轮询分摊读压力——这正是副本提供读扩展的方式。可以通过 preference 参数控制（如 ?preference=_primary 强制读主分片，用于要求强一致读取的场景）。

Q：ES 的聚合是在哪一步算的？

A：在 Query Phase 各分片本地独立计算，协调节点再做合并（reduce）。所以聚合结果在某些场景下是近似的：terms 聚合每个分片只返回自己估算的 Top-N，合并时可能漏掉小分片的低频项。用 shard_size 调大每分片返回量可提高精度（代价是更多内存与网络），或用 show_term_doc_count_error 看误差上界。
