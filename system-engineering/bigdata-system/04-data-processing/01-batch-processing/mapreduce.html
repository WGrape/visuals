MapReduce 计算模型

分而治之：Map、Shuffle 与 Reduce 的完整旅程

分而治之的思想

MapReduce 的精髓是「分而治之」：把一个大到单机放不下的问题，拆成许多小任务，分发到集群各节点并行处理，再把局部结果汇总成最终答案。它把并行化、容错、数据分发、负载均衡这些脏活全包了，你只需写两个函数：map() 和 reduce()。

最经典的例子是 WordCount（词频统计）：给定一堆文本，统计每个单词出现多少次。用 MapReduce 来表达，代码极简——

// map: 读入一行文本，切成单词，每个词输出 (词, 1)
map(String key, String value):
    for word in value.split(" "):
        emit(word, 1)

// reduce: 收到同一个词的所有 (词,1)，累加得到总数
reduce(String key, Iterator<Int> values):
    sum = 0
    for v in values: sum += v
    emit(key, sum)
类比：map 像流水线工人把每箱苹果贴上「苹果:1」标签；reduce 像收银员把所有人手里的「苹果:1」加起来，得到「苹果:100」。框架负责把同一类标签（同一单词）汇集到同一个收银员那里。

完整执行流程

一次 MapReduce 作业的数据旅程如下图。输入被切成 InputSplit 喂给 Map 任务，Map 输出先分区（partition）并排序，溢写到磁盘（spill），再合并（merge）；随后进入 Shuffle 阶段被拉取到对应 Reduce 端，最后 Reduce 汇总输出回 HDFS。

Shuffle：性能的咽喉

Shuffle 指「Map 端输出被重新分发、按 key 聚集到 Reduce 端」的过程，是 MapReduce 最慢也最关键的环节。它慢在三点：

  • 落盘：Map 输出先 spill（溢写）到本地磁盘而非内存，产生大量磁盘 I/O；merge 阶段还要再次读写磁盘。
  • 排序：Map 端和 Reduce 端都要对 key 做排序，排序本身有计算与内存开销。
  • 网络传输：Reduce 要从各个 Map 节点把属于自己的那部分数据「拉」过来，跨网络传输数据量巨大。
经验法则：Shuffle 的数据量越小，作业越快。所以一切优化（combiner、压缩、合理分区数）几乎都围绕「减少 Shuffle 传输量」展开。

Combiner（局部规约）是 Map 端的「小 Reduce」：在 spill 之前先把本节点同一个 key 的 (k,1) 聚合成 (k,本地计数)，从而大幅减少写入磁盘和跨网络传输的数据量。它不是必须的，但能显著提速；前提是聚合操作必须满足结合律（如 sum、max 可以，avg 不行，否则结果会错）。

MapReduce vs Spark

维度MapReduceSpark
中间结果落磁盘（HDFS/本地盘），I/O 重尽量内存（RDD/DAG），可缓存复用
延迟高，适合离线批处理低，支持批/流/交互式
代码量多，需手写 map/reduce 与样板少，高阶 API（DataFrame/SQL）表达力强
执行模型Map→Reduce 两阶段，难以表达复杂流水线DAG 多阶段，算子丰富
适用场景超大规模离线批处理、低成本存储计算迭代计算、机器学习、交互查询、流处理
二者并不互斥：Spark 常跑在 YARN 上、读 HDFS 数据，只是把「中间结果落盘」换成了「内存迭代」。MapReduce 的退场是计算引擎层面的，存储与调度底座仍在。

面试问答

Q：Shuffle 为什么是性能瓶颈？
A：因为它同时触发三类昂贵操作：Map 端把输出 spill 溢写到磁盘并排序（大量磁盘 I/O）；Reduce 端跨网络把各 Map 的数据拉取到本地（网络带宽瓶颈）；两端都要排序与合并。数据在磁盘和网络间反复搬运，且 Shuffle 发生在所有 Map 完成之后，是作业的关键路径，因此慢。优化核心就是减 Shuffle 量（combiner、压缩、调分区数）。
Q：Combiner 一定安全吗？
A：不一定。Combiner 本质是 Map 端的局部 reduce，它只能安全用于满足结合律的聚合操作：sum、count、max、min 都没问题；但求平均值（avg）不行——把 (1,2,3) 的 avg 当 2、再和别的合并会算错。此外 Combiner 执行次数不保证（可能 0 次或多次），所以必须保证多次执行结果一致。不满足时就不该用 Combiner。
Q：MapReduce 现在还被使用吗？
A：作为主计算引擎基本被 Spark/Flink 取代，但并未完全消失：老版本 Hive 仍可将 SQL 翻译为 MapReduce 任务执行；超大规模纯离线 ETL 中仍有遗留作业。更重要的是，其「分而治之 + Map/Shuffle/Reduce」的思想长存，是理解 Spark RDD、Flink 算子乃至分布式计算范式的地基，学习价值依旧很高。

MapReduce 的阶段与代价

阶段做什么是否落盘 / 代价
Split把输入切成 split（默认 128MB）通常等于 HDFS block 大小
Map每个 split 一个 map task输出先写环形缓冲区（默认 100MB）
Spill（溢写）缓冲达 80% 时溢写到磁盘产生多个 spill 文件

为什么 shuffle 是最贵的：map 的输出要写本地磁盘 → 通过网络传给 reduce → reduce 再读磁盘并归并。数据要经历「磁盘 → 网络 → 磁盘」三次 IO。这就是为什么 Spark 要用内存缓存代替落盘——同样的逻辑，Spark 通常比 MapReduce 快 10~100 倍（迭代计算尤其明显）。

代码与调优

// WordCount：MapReduce 的 Hello World
public class WordCount {
    // Mapper: 输入 (行偏移, 文本) -> 输出 (单词, 1)
    public static class TokenizerMapper extends Mapper<LongWritable, Text, Text, IntWritable> {
        private final static IntWritable one = new IntWritable(1);
        private Text word = new Text();
        public void map(LongWritable key, Text value, Context context)
                throws IOException, InterruptedException {
            for (String w : value.toString().split("\\s+")) {
                word.set(w);
                context.write(word, one);          // 每个单词发一次
            }
        }
    }
    // Combiner：在 map 端先做一次本地聚合（关键优化！）
    // job.setCombinerClass(IntSumReducer.class);
    // 效果：map 输出从 N 条降到去重后的 M 条，网络传输减少几十倍

    // Reducer: (单词, [1,1,1...]) -> (单词, 总数)
    public static class IntSumReducer extends Reducer<Text, IntWritable, Text, IntWritable> {
        public void reduce(Text key, Iterable<IntWritable> values, Context context) {
            int sum = 0;
            for (IntWritable v : values) sum += v.get();
            context.write(key, new IntWritable(sum));
        }
    }
}

数据倾斜的通用解法：加盐。把热点 key 变成 key_0 ~ key_9（加随机前缀），先在 map 端按加盐 key 聚合，再在下一轮去掉前缀二次聚合。这样热点被分到 10 个 reduce 上，单 reduce 的压力降到 1/10。
