① 物理流复制：主备如何同步

PostgreSQL 的流复制（Streaming Replication）是物理复制：把 WAL 记录原样（字节级）发送给备库，备库持续重放 WAL，从而保持与主库一致的数据块。

# 主库 postgresql.conf
wal_level = replica
max_wal_senders = 10
max_replication_slots = 10
synchronous_standby_names = 'standby1'    # 同步备库名（留空则全异步）
synchronous_commit = on                    # 或 remote_apply 更强

# 主库 pg_hba.conf 允许复制连接
host replication rep 10.0.0.2/32 scram-sha-256

# 备库初始化（PG 12+ 直接用 -R 写出配置）
pg_basebackup -h primary -D /var/lib/pgsql/data -U rep -R -X stream -P
# 备库自动生成 standby.signal + primary_conninfo

② 同步 vs 异步：RPO 与性能的权衡

模式synchronous_commit主库提交等待到RPO性能
异步on（无同步备）本地 WAL fsync秒级（可能丢）最高
同步·接收on + 同步备备库收到 WAL 并写盘0（主库不丢）中
同步·应用remote_apply备库应用完（查询可见）0 且备库零延迟较低
本地写local本地写入（不 fsync）掉电可能丢高
同步复制的陷阱：若唯一的同步备库宕机，主库的写事务会一直挂起（等不到确认），造成业务整体不可用。对策：① 配置两个及以上同步备（synchronous_standby_names = 'ANY 1 (s1, s2)'，PG 12+）；② 或用 FIRST 1 (s1, s2) 指定优先级；③ 监控复制状态并及时摘除故障备库。

③ 复制槽与延迟监控

-- 主库查看复制状态与延迟
SELECT client_addr, state, sync_state,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS replay_lag_bytes,
       pg_wal_lsn_diff(pg_current_wal_lsn(), flush_lsn)   AS flush_lag_bytes
FROM pg_stat_replication;

-- 备库查看延迟
SELECT now() - pg_last_xact_replay_timestamp() AS replay_delay;
SELECT pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn();

-- 复制槽保留量（非 active 的槽是磁盘杀手）
SELECT slot_name, active, restart_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots;
监控要点：① 用字节差（pg_wal_lsn_diff）而非单纯的时间差，更敏感；② 同时监控 pg_stat_replication.state（应为 streaming）；③ 非 active 的复制槽必须告警——它会导致 WAL 无限堆积。

④ 逻辑复制：按表订阅

物理复制是「整实例克隆」，逻辑复制则是「按表订阅行级变更」：可跨大版本、可选表、可过滤、可双向拓扑。

-- 发布端（源库）
CREATE PUBLICATION pub_orders FOR TABLE orders, order_items;
-- 或订阅所有表：CREATE PUBLICATION pub_all FOR ALL TABLES;

-- 订阅端（目标库）
CREATE SUBSCRIPTION sub_orders
  CONNECTION 'host=10.0.0.1 port=5432 dbname=prod user=rep password=xxx'
  PUBLICATION pub_orders;

-- 状态
SELECT * FROM pg_stat_subscription;
SELECT * FROM pg_replication_origin_status;
维度物理流复制逻辑复制
单位整个实例（字节级）表（行级变更）
版本必须一致可跨大版本
DDL自动同步不同步，需手工
序列 SEQUENCE同步不同步（常见坑）
目标库可写备库只读可写（可做双向/汇聚）
典型用途高可用、读扩展升级迁移、数据分发、数仓接入
逻辑复制的常见坑：① 表必须有主键或唯一标识（否则 UPDATE/DELETE 无法定位行）；② DDL 不同步，加列要两端都做；③ 大事务会造成明显延迟；④ 序列值不同步，切换后需手动重置。

⑤ 故障切换（Failover）

PG 自带的流复制不提供自动故障切换——需要 Patroni / repmgr / Stolon 等工具，或云厂商的托管服务。

方式操作风险
计划内切换（switchover）先停主库 → 备库 promote → 原主库以新备库身份重新接入（pg_rewind）低，有短暂中断
紧急提升（failover）备库执行 pg_ctl promote 或 SELECT pg_promote();可能丢数据（异步复制下）
pg_rewind把「时间线分叉」的旧主库快速回退并作为备库重新接入，不用全量重做需开启 wal_log_hints 或 checksums
脑裂防护用 奇数节点 + 共识（etcd/ZooKeeper） 或 fencing（STONITH）确保只有一个主自动化的核心难点
# 紧急提升备库
pg_ctl promote -D /var/lib/pgsql/data
# 或 SQL：SELECT pg_promote(true, 60);

# 旧主库回退后重新作为备库
pg_rewind --target-pgdata=/var/lib/pgsql/data           --source-server='host=new_primary user=postgres'

⑥ 常见问法

Q：物理复制和逻辑复制怎么选？

A：物理流复制：整实例字节级同步，备库只读，版本必须一致——用于高可用与读扩展；逻辑复制：按表订阅行级变更，可跨版本、可选表、目标库可写——用于大版本升级、数据分发、异构汇聚、数仓同步。局限对照：逻辑复制不同步 DDL 与序列、表必须有主键、大事务延迟高。常见组合：物理复制做 HA，逻辑复制做数据分发。

Q：同步备库挂了会怎样？怎么避免主库不可用？

A：如果 synchronous_standby_names 只配了一个备库且它宕机，主库上的写事务会一直等待确认而挂起，直到备库恢复或超时（取决于配置），造成业务写不可用。对策：① 配置至少两个候选同步备，用 ANY 1 (s1, s2)（PG 12+ 支持法定数语义）——任意一个确认即可；② 或用 FIRST 1 (s1, s2) 指定优先级；③ 监控复制状态并及时把故障备库从同步列表中摘除；④ 关键业务应权衡「丢几秒数据」与「整体不可用」哪个更不可接受。

Q：怎么衡量复制延迟？字节差还是时间差？

A：两者都看，字节差更灵敏。① pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) 给出未重放的 WAL 字节数，在主库上可查，对突发写入很敏感；② 备库上 now() - pg_last_xact_replay_timestamp() 给出时间滞后，但在无写入时会虚高（因为最后一个事务是很久之前的），需结合写入活动判断。实践：告警用字节差为主 + 时间差为辅，并排除「空闲期」的误报。

Q：复制槽有什么用？有什么风险？

A：作用：主库为每个槽保留备库尚未消费的 WAL，使备库短暂掉线后不必重建——这是它的核心价值。风险：如果备库永久下线而槽未删除，主库会无上限地保留 WAL，pg_wal 目录持续膨胀直到磁盘写满、数据库宕机。最佳实践：① 监控 pg_replication_slots 中 active = false 的槽并告警；② 给 WAL 目录单独分区并设置容量告警；③ 备库下线时务必 pg_drop_replication_slot()；④ 可配合 max_slot_wal_keep_size（PG 13+）限制单槽保留量。

Q：主备切换后，旧主库怎么重新加入？

A：用 pg_rewind：它对比两台机器的时间线分叉点，把旧主库回退到分叉点并拉取之后的 WAL，从而无需全量 pg_basebackup，速度极快。前提：① 需开启 wal_log_hints = on 或初始化时启用 data checksums；② 旧主库干净关闭（不能是崩溃状态）；③ 需要能连接到新主库并有复制权限。流程：确认新主 → 停旧主 → pg_rewind → 配置 standby.signal + primary_conninfo → 启动。

Q：延迟备库有什么用？

A：通过 recovery_min_apply_delay = '1h' 让备库故意延后应用 WAL。它的价值是救回人为误操作：主库上误删数据后，物理备库会同步删除，但延迟备库还没应用，可以立即在其上查询/导出被删数据，甚至把备库 promote 到误操作前的时间点。代价：占用一台机器、延迟窗口内的切换会丢数据。最佳实践：延迟备库是「误操作保险」，与实时备库（HA）、PITR 备份（灾难恢复）共同构成三层防护。

复制模式的对比与参数

模式同步性数据丢失窗口性能影响
异步（默认）主库不等从库确认可能丢已提交事务最小
半同步（synchronous_commit=on）等 WAL 落从库磁盘几乎为零增加 1 次 RTT

复制配置

# postgresql.conf 关键参数（主库）
wal_level = replica              # minimal < replica < logical
max_wal_senders = 10             # 最大 walsender 进程数
wal_keep_size = 1GB              # 保留的 WAL 量（防止从库落后被清理）
max_replication_slots = 10       # 复制槽数量

# 同步复制配置
synchronous_commit = on          # off/local/remote_write/on/remote_apply
synchronous_standby_names = 'ANY 1 (standby1, standby2)'   # 任意一个确认即可
#   或 'FIRST 1 (standby1, standby2)'  → 第一个优先
#   或 'ANY 2 (...)' → quorum 模式，等 2 个确认

# 从库（standby.signal + primary_conninfo）
primary_conninfo = 'host=primary port=5432 user=repl password=xxx'
hot_standby = on                 # 允许从库只读查询

# 必用复制槽（否则从库断开后 WAL 可能被清理，需重建）
SELECT pg_create_physical_replication_slot('standby1_slot');
# 在 primary_slot_name 里指定

复制槽的双刃剑：它保证 WAL 不会被清理（从库一定能追上），但如果从库永久下线而槽未删除，WAL 会无限堆积撑爆磁盘。所以必须用 max_slot_wal_keep_size（PG 13+）限制，并监控复制延迟与槽的活跃状态。

延迟监控与故障切换

指标查询方式告警阈值
字节延迟pg_wal_lsn_diff(sent, replay)> 100 MB
时间延迟now() - pg_last_xact_replay_timestamp()> 30 秒
复制状态pg_stat_replication.state非 streaming 即异常

延迟监控

-- 主库查看所有从库状态
SELECT client_addr, state, sync_state,
       pg_wal_lsn_diff(sent_lsn, replay_lsn) AS lag_bytes
FROM pg_stat_replication;
--   state: streaming(正常) / catchup / backup / stopped
--   sync_state: sync(同步) / potential / async

-- 从库查看延迟（最实用）
SELECT
  pg_last_wal_receive_lsn() AS receive,
  pg_last_wal_replay_lsn()  AS replay,
  pg_last_xact_replay_timestamp() AS last_replay,
  now() - pg_last_xact_replay_timestamp() AS lag_time;
-- 注意：<strong>无写入时 last_replay 不更新</strong>，
#   lag_time 会虚高，需结合 lag_bytes 判断

故障切换的两种触发：

  • 计划内切换（switchover）：先停主库、确保从库追平、再从库 pg_ctl promote、最后老主库降级为新从库。有序、无数据丢失。
  • 故障切换（failover）：主库已挂，只能 promote 从库。此时异步复制下必然丢数据（丢失量 = 复制延迟窗口内的事务）。

脑裂风险：老主库若只是网络隔离而非真正宕机，它可能仍在接受写入。promote 新主后，两个「主库」同时写入 → 数据分叉，几乎无法自动合并。防护手段是 fencing（隔离老主库的网络或存储），或至少用奇数节点的 quorum 与看门狗。这也是为什么生产要用 Patroni 等成熟工具而不是手工 promote。

逻辑复制与物理复制的选择

维度物理复制（流复制）逻辑复制
复制内容WAL 字节流（整库）表级的行变更
版本要求主从必须同大版本可跨版本
选择性整实例，不能挑表可按表订阅
从库可写不可写（只读）可写（可做双向/汇聚）
DDL自动同步不复制 DDL

逻辑复制

-- 逻辑复制：发布端
CREATE PUBLICATION my_pub FOR TABLE orders, users;
-- 或 FOR ALL TABLES

-- 订阅端
CREATE SUBSCRIPTION my_sub
  CONNECTION 'host=primary dbname=mydb user=repl password=xxx'
  PUBLICATION my_pub;

-- 关键限制（务必知道）：
--   1) <strong>不复制 DDL</strong>：加字段要手动在两端执行
--   2) <strong>不复制序列</strong>：序列值需单独同步
--   3) 表必须有<strong>主键或唯一键</strong>（否则 UPDATE/DELETE 无法定位行）
--   4) 大表初始同步很慢，建议先做基础备份
--   5) 双向复制<strong>不解决冲突</strong>，需业务侧规避

-- 监控

自检 Q&A

Q：从库延迟越来越高怎么办？

A：先判断是「产生慢」还是「应用慢」。主库写入量突增（大批量导入、大事务）→ 从库追不上，属正常，等峰值过去会追上；从库自身瓶颈（单线程 apply 打满、磁盘慢、长查询阻塞 apply）→ 需要优化。PG 的 apply 在 15 版前基本是单线程，这是常见的结构性瓶颈。缓解办法：① 拆分大事务；② 从库用更快的磁盘；③ 调大 maintenance_work_mem；④ 避免从库上的长查询阻塞 apply（可用 hot_standby_feedback 权衡）。

Q：同步复制会不会让主库不可用？

A：会，这是它的代价。配成 synchronous_commit=on 且指定了同步从库时，所有从库都挂掉会导致主库写入阻塞（一直等待确认）。所以配置要点：① 用 synchronous_standby_names 列出至少 2 个候选（ANY 1 (s1, s2)），容忍单台故障；② 或只等关键事务用同步（会话级设置），普通事务走异步。千万不要只配一个同步从库还指望高可用。

Q：热备（hot_standby）上的长查询有什么影响？

A：可能阻塞 WAL apply，导致复制延迟。因为查询结果需要与正在应用的 WAL 保持一致，若查询引用的行正被修改，apply 必须等待查询结束（或取消查询）。两个参数控制：max_standby_streaming_delay（默认 30 秒，超时后取消冲突的查询）与 hot_standby_feedback（从库反馈活跃事务给主库，让主库延迟 vacuum，减少冲突但增加主库膨胀）。典型选择：报表类从库开 feedback，高可用备库不开。

Q：级联复制什么时候用？

A：从库数量多或跨地域时。所有从库都直连主库会耗尽 max_wal_senders 并占用主库带宽；级联让部分从库从另一台从库复制，减轻主库压力。代价是链路更长、延迟累积、故障切换更复杂。典型场景：同城两台直连主库（用于高可用），异地从库从其中一台级联（用于灾备）。注意级联链路上的每个节点都需要复制槽来保证 WAL 不丢。
