01选型的四个决定性问题

别从产品特性开始比，先从这四个问题开始——它们直接决定了候选范围，比任何参数表都有效。
  1. 数据是谁产生的？运维监控指标 → Prometheus 生态；设备/传感器遥测 → InfluxDB / TDengine；业务侧自埋点 → 看写入方式与 SDK 生态。
  2. 基数有多大？几千条时间线 → 随便选；几十万 → 关注内存模型；千万级 → 必须专门评估，很多方案会直接淘汰。
  3. 要存多久、查询多频繁？近期热数据 → 本地存储；长期留存 → 必须配套降采样与远端存储方案。
  4. 谁来消费？Grafana + PromQL → Prometheus 生态；SQL 分析师 → TDengine / TimescaleDB；自研程序 → 看协议与客户端成熟度。

03常见组合模式

模式一：纯 Prometheus

规模不大、只关心近期监控。零组件、最快上手。缺点是容量与长期留存受限。

模式二：Prometheus + 远端存储

最常见的生产形态。Prometheus 负责抓取与告警，remote_write 写入 VictoriaMetrics / Mimir / Thanos 做长期留存与全局查询。

模式三：专用时序库直写

设备遥测、业务埋点这类「推送为主」的数据直接写 InfluxDB / TDengine，不经过 Prometheus。

模式四：混合

运维监控走 Prometheus 生态，设备数据走 TDengine/InfluxDB，需要时用 Grafana 的多数据源或统一的查询层拼起来。

不要试图用一个库解决所有问题。「运维指标」和「设备遥测」在数据模型、基数、查询模式上差异巨大，硬塞进同一个库通常两边都不舒服。模式四看起来复杂，实际长期维护成本更低。

04POC 要测什么

  1. 真实基数：用生产的 label 组合规模，不要造 100 条时间线就说「测过了」。基数错一个量级，结论完全变样。
  2. 真实写入速率：包括峰值。很多方案在平均速率下表现良好，峰值时队列堆积。
  3. 真实查询：把你最重的那几个仪表盘查询原样跑一遍。不要只测「查一条线最近一小时」。
  4. 资源占用：稳态运行至少几天后的内存与磁盘，别看刚启动的数字。
  5. 故障行为：杀进程、断网、写满磁盘，看它怎么表现、数据丢不丢、恢复要多久。这一项最容易被跳过，也最容易在生产上出事。
  6. 运维成本：升级麻不麻烦、备份怎么做、出问题有没有人能排查。这一项决定长期总成本。
本文不给出具体性能数字。时序数据库的性能高度依赖数据分布与版本，任何脱离实测的数字都不可靠。请在你自己的环境上验证。

05五个选型误区

误区为什么错正确做法
「选性能最强的那个」性能依赖场景，通用榜单意义有限用真实数据 POC，看查询与故障行为
「先上分布式架构」单机能撑的规模常被低估从单机起步，监控水位，撑不住再扩
「高基数问题换库能解决」换库只是让同样的基数更便宜先治理 label 设计，再谈扩容
「兼容性看文档就行」PromQL 兼容度、协议细节差异很大把现有仪表盘与告警规则原样迁移测一遍
「只要数据库，不管生态」采集端、可视化、告警链路才是大头把整条链路的组件一起评估

一个反直觉的建议：不要为了“时序场景”就一定要上专门的时序库。如果数据量不大（< 10 万 series）、且已经有 ClickHouse 或 Elasticsearch，直接复用现有系统往往比引入新组件更划算——运维成本常常超过存储收益。

PromQL 兼容性的重要性

考虑点说明影响
PromQL 生态Grafana 面板、告警规则、Exporter 全部基于 PromQL换不兼容的产品 = 重建所有看板
VictoriaMetrics100% 兼容 PromQL + 扩展 MetricsQL可无缝替换 Prometheus
Thanos / Mimir / Cortex兼容 PromQL，加长期存储平滑扩展，无需改查询
InfluxDB / TDengine不兼容 PromQL需重写查询与告警（成本很高）

PromQL 模板

# PromQL 常用查询模板（换产品时需要重写的就是这些）
# ① 速率（counter 类型必须用 rate）
rate(http_requests_total[5m])

# ② 分位数（必须先用 histogram_quantile，不要 avg）
histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))

# ③ 聚合（by 按标签分组）
sum by (job) (rate(http_requests_total[5m]))

# ④ 增量（gauge 用 delta / idelta）
idelta(temperature[5m])

# ⑤ 预测（基于线性回归预测 4 小时后磁盘满）
predict_linear(node_filesystem_free_bytes[6h], 4*3600) < 0

# ⑥ 告警规则写法
groups:
- name: node
  rules:
  - alert: DiskWillFillIn4Hours
    expr: predict_linear(node_filesystem_free_bytes[6h], 4*3600) < 0
    for: 5m              # 持续 5 分钟才告警（防抖动）
    labels: {severity: critical}
    annotations:
      summary: "磁盘将在 4 小时内写满"

# 关键：[5m] 的区间至少要 > 2 × 采集间隔，否则数据点太少

最常见的 PromQL 错误：对 gauge 用 rate（应该用 delta/idelta），或对 counter 忘了加 rate（直接用原始值，只增不减毫无意义）。另一个坑：[5m] 区间要至少 2 倍采集间隔，否则结果不准。

深入自检

Prometheus 单机能撑多大规模？

官方经验值：单实例可处理 每秒约 100 万样本、约 1000 万活跃 series，前提是内存充足（每 100 万 series 约需 4 – 8 GB）且磁盘够快。实践中更常见的瓶颈是内存而非磁盘——因为 head block（最近 2 小时的数据）全部常驻内存。超过这个规模就用 VictoriaMetrics（内存效率高 5 – 10 倍）或 Thanos/Mimir（分片 + 对象存储）。

VictoriaMetrics 为什么比 Prometheus 省资源？

几个关键设计：① 索引结构更紧凑——用更省内存的倒排索引；② 无 head block 全内存要求——它的 LSM 结构让近期数据不必全在内存；③ 压缩算法优化——约 0.7 B/点 vs Prometheus 的 1.7 B/点；④ 单机架构简单——没有 Thanos 那套复杂组件。实测在同样数据量下，内存约 1/5 – 1/10，磁盘约 1/3。这也是它近年流行的主要原因。

什么时候该从 Prometheus 迁走？

三个信号：① 内存频繁 OOM 且已经加了内存还涨（series 太多）；② 查询越来越慢（> 几秒），且大部分查询是看长周期趋势（应该降采样了）；③ 需要长期存储但不想维护 Thanos 全家桶。最平滑的路径是迁到 VictoriaMetrics（PromQL 兼容，看板和告警不用改），或用 remote_write 把数据双写过去，验证无误后再切读。

时序数据和日志能放一起吗？

技术上可以（ClickHouse / ES 都能存两者），但要看访问模式：时序数据是结构化、聚合查询、极高频写入；日志是半结构化、全文检索、偶尔查询。混存的问题是：索引策略冲突（时序不需要全文索引，日志需要）和保留期不同。务实做法：指标用时序库（看趋势、告警），日志用 ES/Loki（查详情），靠 trace_id / 时间范围关联。规模小的时候放一起也行。
