类型参数与函数

方括号声明类型参数

函数名后加 [T any] 声明类型参数；调用时可省略（编译器推断）。

func Max[T int | float64](a, b T) T {
    if a > b { return a }
    return b
}

m := Max(3, 5)            // T 推断为 int
m2 := Max[float64](1.2, 2.3)
约束（constraint）

约束是对类型的「接口」

约束用 interface 描述「T 必须满足哪些方法/结构」。标准库 constraints 包提供常见数值约束。

type Number interface {
    ~int | ~int64 | ~float64   // 类型集
}
func Sum[T Number](xs []T) T {
    var s T
    for _, x := range xs { s += x }
    return s
}
类型集（type set）

~T 表示「底层类型」

约束里的 `~int` 表示「底层类型是 int 的任意类型」（含 type MyInt int）。没有 ~ 则只匹配 exactly int。这是泛型约束的精髓。

空接口 any 是最宽约束（任意类型）；comparable 是编译器特殊支持、要求可用 == 的约束。
常用内置约束

comparable 与 any

comparable 用于 map 键、去重等需要相等比较的场景；any 等价于 interface{}。

// 要求 K 可比较
func Keys[K comparable, V any](m map[K]V) []K {
    ks := make([]K, 0, len(m))
    for k := range m { ks = append(ks, k) }
    return ks
}
实战建议

泛型 vs 接口

容器、算法（排序/映射/过滤）、需要类型安全的工具函数适合泛型；若行为靠方法多态，接口更合适。

⚠️ 不要为了泛型而泛型：单类型的函数没必要参数化；约束过宽会丧失可读性。

泛型解决什么问题

Go 1.18 引入泛型，主要解决三类重复：容器（任意类型的栈、队列、集合）、通用算法（Map/Filter/Reduce、排序）、以及需要类型安全的工具函数。在此之前，这些只能靠 interface{} + 反射，或复制粘贴多份。

// 泛型前：要么用 interface{} 丢掉类型安全 func MaxAny(a, b any) any { ... } // 调用方要断言 // 泛型后：编译期检查，无运行时开销（对值类型） func Max[T int | float64](a, b T) T { if a > b { return a } return b } Max(1, 2) // T 推断为 int Max(1.5, 2.5) // T 推断为 float64 Max[int](1, 2) // 也可显式指定 // 用官方约束更简洁 func Sum[T constraints.Ordered](xs []T) T { ... }
类型参数方括号里的 [T any] 就是类型参数。
约束限制 T 可以是哪些类型。
类型推断多数情况不用显式写类型。
编译期检查错误在编译期暴露，不是运行时。

约束怎么写

约束写法含义适用
any任意类型（等价于 interface{}）容器、不需要操作的场景
comparable支持 == 与 !=map 的 key、查找、去重
constraints.Ordered支持 < > <= >=排序、求最值
接口约束要求实现某些方法需要调用方法时
联合类型 int | string只能是列举的几种限定具体类型集合
~int底层类型是 int 的所有类型包含自定义类型
// ① 联合类型 type Number interface { int | int64 | float64 } // ② 底层类型约束（~ 很重要） type MyInt int type IntLike interface{ ~int } // 接受 int 和 MyInt type OnlyInt interface{ int } // 只接受 int // ③ 方法约束 type Stringer interface { String() string } func Join[T Stringer](xs []T) string { ... } // ④ 组合约束 type Ordered interface { ~int | ~int64 | ~float64 | ~string } // ⑤ 泛型类型 type Stack[T any] struct { items []T } func (s *Stack[T]) Push(v T) { s.items = append(s.items, v) } func (s *Stack[T]) Pop() (T, bool) { if len(s.items) == 0 { var zero T return zero, false } v := s.items[len(s.items)-1] s.items = s.items[:len(s.items)-1] return v, true }

~ 的作用：~int 表示「底层类型是 int 的所有类型」，包含 type MyInt int；而 int 只匹配 int 本身。写通用库时通常要用 ~。

什么时候该用，什么时候不该用

适合用泛型

  • 容器类型：栈、队列、集合、可选值
  • 通用算法：Map、Filter、查找、排序辅助
  • 需要类型安全的工具函数
  • 多个类型需要完全相同的逻辑
// 典型：一次编写，多类型复用 func Contains[T comparable](xs []T, v T) bool { for _, x := range xs { if x == v { return true } } return false } func Keys[K comparable, V any](m map[K]V) []K { ks := make([]K, 0, len(m)) for k := range m { ks = append(ks, k) } return ks }

不适合用泛型

  • 只有一种类型会用到 —— 直接写具体类型
  • 逻辑其实不同，硬套泛型会写出一堆类型分支
  • 接口已经能优雅解决 —— 优先用接口
  • 为了让代码「看起来高级」

已知限制

  • 不支持方法上的类型参数（只能定义在类型上）
  • 不支持可变数量的类型参数
  • 类型参数不能直接做类型断言
  • 编译产物可能变大（单态化有取舍）
  • 错误信息有时较难读

泛型与接口怎么选

// 接口：运行时多态，适合「行为不同、调用方统一」 type Writer interface{ Write([]byte) (int, error) } func Save(w Writer, data []byte) error { return w.Write(data) } // 可以传 *os.File、*bytes.Buffer、网络连接…… // 泛型：编译期参数化，适合「逻辑相同、类型不同」 func Map[T, R any](in []T, f func(T) R) []R { ... } // 对 []int、[]string 都是同一套逻辑 // 判断口诀： // 关注的是「能做什么」→ 接口 // 关注的是「装的是什么」→ 泛型
先接口后泛型多数场景接口已足够
泛型不是银弹不能替代良好的抽象设计
标准库已提供slices/maps 包覆盖常见需求
注意编译体积大量实例化会让二进制变大
错误信息约束不满足时报错可能很长
保持简单能用具体类型就别泛型化

深入自检

泛型会影响性能吗？

多数情况下不会变差。Go 对值类型做单态化（为每种类型生成一份代码），因此没有接口调用的动态派发开销；对指针类型则共享一份实现。代价是二进制体积可能增大，以及编译时间变长。

any 和 interface{} 有什么区别？

完全等价，any 是 Go 1.18 引入的别名，写起来更短。官方建议在泛型与非泛型代码中都优先用 any，语义相同。

为什么我的自定义类型不满足 int 约束？

因为约束写成了 int（只匹配 int 本身）。若要接受所有底层为 int 的类型，应写成 ~int。这是写通用库时最常见的约束错误。

泛型能完全替代反射吗？

不能。泛型要求类型在编译期已知（或至少满足约束），而反射处理的是「运行时才知道结构」的情况，比如 JSON 编解码。两者有重叠，但适用场景不同。

什么时候用官方的 slices/maps 包而不是自己写？

大多数时候。Go 1.21 起标准库提供了 slices（排序、查找、删除、去重）与 maps（遍历、删除）的泛型工具，覆盖了日常绝大多数需求，自己写的版本通常既不更快也不更清晰。
