Tokenizer 的边界坑：OOV、多语言、代码与 emoji 分词

分词器不是透明管道，理解 OOV、多语言、代码与 emoji 的边界坑。

1分词器不是透明的

开发者常把"文本"等同"token 数"，但 tokenizer 是模型的第一道关卡，它决定了模型"看到"的单元。同一段文字在不同 tokenizer（GPT 系列、Llama、Qwen、Claude）下 token 数可能相差 2–3 倍，直接传导到成本与上下文上限。理解边界坑，是做多语言、代码和 emoji 场景的前提。

关键事实：token 是分词的产物，不是字符；分词表（vocab）是有限且训练时固定的，遇到训练分布外的字符就会退化。

2四类典型边界坑

坑表现后果
OOV / 未登录字符生僻字、新 emoji、私有区字符被拆成字节或 <unk>语义丢失、补全变乱码
多语言不平衡中文/阿拉伯文 token 数远多于英文非英文成本高、易超窗口
代码分词缩进、符号、驼峰被切得过碎代码补全贵且易错
emoji / 组合字符一个 emoji 由多 code point 拼成，占多个 token计数失真、截断错位

3用 tiktoken 实测 token 数

import tiktoken
enc = tiktoken.get_encoding("cl100k_base")  # GPT-3.5/4 常用
texts = ["Hello world", "你好世界", "def foo(): return 1", "🚀🔥"]
for t in texts:
    ids = enc.encode(t)
    print(f"{t!r:>20}  ->  {len(ids)} tokens  {ids[:6]}")

# 多语言成本对比：同样含义的句子
print(len(enc.encode("请将这段话翻译成英文")))
print(len(enc.encode("Please translate this paragraph into English")))

运行后会发现中文/代码往往 token 更密，这正是计费与截断要重点关注的地方。

第一层 · 概念与判定

判定某场景是否有分词坑的快速检查：

  • 文本是否含训练语料稀有的字符集（古文字、新 emoji、私有符号）；
  • 是否多语言混排，且非拉丁语占比高；
  • 是否大量代码/日志/正则（符号密集）；
  • 是否对"字符数≈token 数"有假设（如按长度计费展示）。

第二层 · 参数·命令·量化

常用命令与量化：

# 在线统计（Python）
len(enc.encode(text))            # token 数
enc.decode(ids)                  # 还原
# 成本换算
cost = tokens/1000 * price_per_1k
场景经验倍数
英文 vs 同义中文中文常多 1.5–2.5× tokens
源码 vs 散文代码常更碎、更贵
emoji 组合每个 ZWJ 序列可占 2–4 token

第三层 · 排障与边界

排障：

  • 截断错位：按字符截断再编码会切坏多字节字符，应"按 token 截断"或用支持 truncation 的接口；
  • 计数失真：前端用 len(str) 估算成本，实际差很多，应服务端统计；
  • 跨模型漂移：换模型 tokenizer 变了，缓存 key 与成本都要重算；
  • 填空洞：用 Tiktoken izer 侧未知字符落到 <unk> 时，考虑预处理做 NFKC 归一化。

第四层 · 原理与取舍

原理取舍：

  • 词表越大覆盖越好但 embedding 表越重；子词（BPE/Unigram）用"可组合"换取小词表，代价是稀有序列被切碎；
  • 多语言公平性与成本冲突：为低资源语言加词表会稀释公共 token；
  • 结论：把 tokenizer 当作"计费单元 + 上下文容量"的硬约束来设计，而非透明管道。
