ClickHouse ReplacingMergeTree 去重：为什么刚写完还能查到两版

用同一订单的两条版本记录，解释排序键、后台合并、FINAL 与查询正确性的取舍。

先看同一订单的两次状态

订单 42 初始状态为“待支付”，版本号 1；一分钟后状态变为“已支付”，版本号 2。分析库把两条变化都写入 ReplacingMergeTree。此引擎在合并数据 Part 时，可依据 ORDER BY 定义的排序键识别相同逻辑行，并保留选定版本。若 ORDER BY 包含会变化的状态或时间戳，两条记录的排序键就不同，合并也无法把它们认成同一行。通常应把稳定的业务标识放在去重键语义中，并仔细设计 ORDER BY 与查询过滤。

ReplacingMergeTree 的后台合并是异步发生的。刚插入两条版本后，直接 SELECT count() 可能仍看到 2；“插入成功”并不代表旧版立即消失。即使后来合并，分区边界、Part 分布和查询方式也会影响读到的记录。必须先确定报表需要的是事件历史、当前状态，还是可容忍延迟的近似当前状态。

手推一次查询差异

假设两条数据的稳定排序键都是 order_id=42，version 分别为 1、2，金额都为 100，但状态不同。尚未合并的普通查询会返回两行；`count()` 得 2，`sum(amount)` 得 200。如果业务只想统计当前订单金额，显然不能把这两行直接求和。使用 `FINAL` 可在查询时应用相应去重语义，得到最新状态的一行；但查询时处理更多数据，可能显著增加 CPU 与延迟。具体行为要按表定义、版本列、分区和当前版本验证。

不写版本列时保留哪条记录可能受合并顺序影响，不能把“最后插入的一条”当作可靠业务版本。用单调业务版本号或更新序号表达新旧，并处理重复投递与乱序到达。若两个版本号相同但内容不同，需要定义冲突规则，不然合并结果无法稳定代表业务真相。

分区与删除的边界

同一逻辑订单的不同版本若被写入不同分区，常规后台合并通常只在分区内部工作，旧版可能不会按预期自动消失。常见错误是按可变的更新时间分区，导致同一订单跨月；即使查询加 FINAL，也要理解跨分区处理的实际设置与成本。分区设计应与生命周期、查询裁剪和去重范围一起决定。

删除也可用版本化墓碑表达，但最终是否返回已删除记录、何时物理清理，取决于引擎参数与查询写法。不能把逻辑删除立刻等同于释放磁盘。若要审计完整变更历史，保留所有事件的明细表与当前状态表可能比一张表兼任两种语义更清晰。

操作可能结果适用条件
普通 SELECT/SUM合并前可见多版接受暂时重复或查事件
FINAL 查询按引擎语义查询时去重需测扫描和并发成本
后台合并逐步减少旧版不能承诺实时完成
按版本构建当前层查询目标清晰维护版本与冲突规则

什么时候用查询时去重

报表必须读到当前准确状态时，可在查询中使用 FINAL，或构建按订单 ID 选最大版本的查询/物化状态。后者需注意聚合状态的正确合并与重复事件处理。大表全量 FINAL 有成本，先评估分区过滤、查询范围与并发。若是每日离线报表，可能接受等待合并后再计算，但等待并不是严格的正确性保证；后台合并何时完成受负载影响。

若指标本身是事件数，例如“支付状态变更次数”，就不该把旧版删除后再统计。建模时先给每个指标标明“事件”还是“实体当前快照”。把两种粒度混在一起，SQL 再复杂也补不回丢失的语义。

写入与查询验收步骤

建一张 ORDER BY order_id、带 version 的示意表，插入同一 order_id 的两条不同状态。立即查普通 SELECT、带 FINAL 的 SELECT，以及按 version 求最新的查询，对比行数与金额。再插入一次重复的 version=2 事件，检查重复投递是否产生多计。把更新时间跨分区的例子单独测试，确认实际分区策略不会让旧记录永久残留。

生产观测包含活跃 Part 数、后台合并队列、查询扫描行数、FINAL 查询延迟与磁盘占用。过多小 Part 会拖慢合并与查询；盲目执行昂贵的强制合并来追求“立刻去重”，可能影响整个集群。应按业务准确性需求选择查询时去重或独立当前状态层。

三句必须说清的边界

ReplacingMergeTree 的“Replacing”描述合并时的替换行为，不是事务式 UPDATE；ORDER BY 键定义哪些行会被视为同一逻辑行，不等于普通数据库的唯一约束；版本列帮助挑出新旧，不会自动修复错误分区或相同版本冲突。把这三句写到设计评审里，比只说“它支持去重”更能防止线上错账。
