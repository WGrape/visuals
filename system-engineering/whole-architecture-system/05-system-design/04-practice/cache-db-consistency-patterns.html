缓存与数据库一致性模式

「先更新缓存还是先更新数据库？」这题没有银弹，只有权衡。本文把四种经典读写模式讲清楚，并给出「双写一致性」的可落地方案。

先认清一个事实：缓存和数据库是两个数据源

只要数据存在两处，就必然存在「某一瞬间两边不一致」的窗口。我们的目标是把不一致窗口缩到最短、把不一致概率降到业务可接受，而不是追求绝对实时一致（那会牺牲性能，得不偿失）。先记住两条铁律：

  • 缓存是「副本」，数据库才是「真相」。任何读，最终以数据库为准（或强一致读直接查库）。
  • 写操作后必须让旧缓存失效。缓存里永远不要写「可能过期的值」，而是删掉它，下次读再回源重建。

四种经典读写模式

模式读路径写路径一致性适用
Cache-Aside
(旁路缓存)		先查缓存，未命中查库并回填缓存。先更新 DB，再删除缓存。最终一致最常用，通用读写场景。
Read-Through应用只查缓存，由缓存层负责「未命中回源填库」。—最终一致希望应用不感知回源逻辑。
Write-Through同 Read-Through。写同时更新缓存与 DB（同步）。较强读多写少、要求缓存常新。
Write-Behind
(写回)		—只写缓存，由缓存异步批量刷盘。弱（丢数据风险）写极高、可容忍丢少量数据。

Cache-Aside 的「先删缓存还是先更新库」

这是最高频的面试题。两种顺序都有并发漏洞，但「先更新数据库，再删除缓存」的不一致窗口更小，是主流选择。

图：Cache-Aside 推荐顺序「先更新库 → 再删缓存」，不一致窗口极小。
⚠️ 为什么「先删缓存再更新库」更糟？因为删缓存后、更新库完成前，若有读请求进来，会回源把旧值重新填回缓存，导致缓存长期持有脏数据，直到下次失效。

双写一致性：当业务要求「尽量不读到脏数据」

仅「删缓存」还不够稳（删失败、或并发读回填旧值）。生产常用两招加固：

🔁 延迟双删

写库前删一次缓存，更新库后延迟几百毫秒再删一次，清掉期间可能回填的旧值。实现简单，覆盖大多数场景。

📡 订阅 binlog

通过 Canal 监听数据库 binlog，异步删除/更新缓存。业务代码零侵入，且与主流程解耦，是大型系统的首选。

🔒 读写加锁/串行

对强一致要求的 key，用分布式锁让「读-改-写」串行，彻底消除并发窗口（牺牲并发度）。

⏱️ 兜底 TTL

给缓存设较短过期时间，即使出现脏数据也会在 TTL 后自动消失，作为最后防线。

-- 延迟双删伪代码 delCache(key); // 第一次删 updateDB(data); // 更新数据库 sleep(500ms); // 等并发读回填的旧值沉淀 delCache(key); // 第二次删，清掉脏值
💡 类比：缓存像白板上的便利贴，数据库是账本。你改账本时，先把白板便利贴撕掉（删缓存）；有人此时看白板发现空的，就去翻账本抄最新数贴回去（回源）。你改完再确认撕一次，确保没人贴着旧数。

选型速查

你的诉求推荐方案
通用缓存，能接受秒级最终一致Cache-Aside + 删除缓存 + TTL 兜底
对脏数据敏感、系统规模大Cache-Aside + 订阅 binlog 异步删缓存
读极多写极少，缓存要常新Write-Through（写同步更缓存）
资金/库存等强一致要求绕过缓存直接读库，或用锁串行化

🎯 面试问答

Q：Cache-Aside 下，更新数据库成功了但删缓存失败，怎么办？
A：缓存仍是旧值，出现不一致。解法：删除操作加重试（重试队列/定时补偿）；更稳妥的是「订阅 binlog 删缓存」——只要库更新了，binlog 就一定触发删，与业务删缓存是否成功无关。
Q：为什么不直接「更新数据库 + 更新缓存」？
A：两个写操作没有原子性，并发下极易产生「后更新的缓存被先更新的缓存覆盖」的乱序；且频繁写场景下每次都写缓存性价比低。「删」比「写」更安全简单——把重建交给读路径。
Q：缓存和数据库能强一致吗？
A：严格强一致需要分布式事务（如 2PC / TCC）或串行化访问，代价是吞吐骤降。绝大多数业务用「最终一致 + 短 TTL 兜底」即可，只有资金、库存扣减等才值得为强一致付出性能成本。

四种一致性模式对照

模式流程一致性适用
Cache Aside读：命中返回，未命中读库回填；写：更新库后删缓存最终一致通用默认，读多写少
Read/Write Through应用只与缓存交互，缓存负责落库较强缓存层支持写穿透时
Write Behind只写缓存，异步批量落库弱（可能丢）写入量大、可容忍丢失（如计数）
双删写前删一次 + 写库 + 延迟再删一次较强对脏读极敏感的场景

为什么是“删除缓存”而不是“更新缓存”：两个原因——① 更新缓存意味着每次写都要算一遍缓存值，若该值很少被读就是纯浪费；② 并发写时，两个线程更新缓存的顺序可能与更新库的顺序不一致，留下长期脏数据。删除则让下次读自然回填，天然避免了这个问题。

并发脏读的成因与处理

经典时序：线程 A 读缓存未命中 → 读库得旧值 v1；此时线程 B 更新库为 v2 并删除缓存；A 才把 v1 回填进缓存。此后读到的一直是 v1，直到缓存过期。

场景概率处理方案
上述“读-删除”交错窗口极低（需读慢于写且跨越删除点）延迟双删 / 设置较短 TTL 兜底
删除缓存失败低但后果持久重试 + 消息队列，保证删除最终成功
主从延迟导致回填旧值中（读写分离架构常见）回填时强制读主库，或延迟回填
缓存过期瞬间的高并发穿透高（热点 key）互斥锁重建或逻辑过期

延迟双删与失败补偿

# 延迟双删（把并发脏读窗口再压缩一次）
def update_data(key, new_value):
    cache.delete(key)              # 1) 写前删
    db.update(new_value)           # 2) 更新库
    submit_delayed_task(           # 3) 延迟再删（延迟 > 一次读的耗时）
        lambda: cache.delete(key), delay_ms=500)

# 删除失败必须补偿：进 MQ 重试，否则脏数据会存活到 TTL 结束
def delete_with_retry(key, max_retry=3):
    for i in range(max_retry):
        try:
            cache.delete(key); return True
        except Exception:
            time.sleep(0.05 * (2 ** i))     # 指数退避
    mq.send("cache_delete_failed", {"key": key})   # 兜底
    return False

TTL 与穿透/击穿/雪崩

问题现象方案
穿透查不存在的 key，每次都打到库布隆过滤器 / 缓存空值（短 TTL，如 60 s）
击穿热点 key 过期瞬间大量请求打库互斥锁单线程重建 / 逻辑过期不删
雪崩大批 key 同时过期TTL 加随机抖动（基础值 ± 20%）

TTL 抖动与单飞

import random, time

def set_with_jitter(key, val, base_ttl=3600, jitter=0.2):
    # 关键：给 TTL 加随机量，避免同一批 key 同时到期
    ttl = int(base_ttl * (1 + random.uniform(-jitter, jitter)))
    cache.setex(key, ttl, val)

# 击穿防护：单飞（singleflight）重建
def get_or_rebuild(key, loader, ttl=3600):
    v = cache.get(key)
    if v is not None:
        return v
    lock = cache.setnx(f"lock:{key}", 1, ex=5)   # 抢锁
    if lock:
        try:
            v = loader()                          # 只有一个线程查库
            cache.setex(key, ttl, v)
            return v
        finally:
            cache.delete(f"lock:{key}")
    time.sleep(0.05); return get_or_rebuild(key, loader, ttl)  # 等待后重试

自检 Q&A

Q：Cache Aside 能保证强一致吗？

A：不能，它的定位就是最终一致。存在两个窗口——① 删缓存后、下次读回填前，读到的是旧值（其实这时缓存已空，会读库得新值，所以反而安全）；② 前面说的“读慢于写”交错窗口会回填旧值。要强一致必须引入分布式锁或版本号校验，代价是吞吐下降明显，多数业务接受最终一致 + 短 TTL 即可。

Q：为什么推荐先更新数据库再删缓存，反过来行不行？

A：反过来（先删缓存再更新库）风险更大：删完缓存、库还没更新完时，一个读请求会把旧值回填进缓存，之后库更新完成，缓存里就长期是旧值了。而“先更新库再删缓存”只在极端时序下出问题，且能通过延迟双删进一步压缩。所以标准做法是先库后缓存。

Q：缓存空值会不会撑爆内存？

A：会，如果攻击者批量构造不存在的 key。所以空值缓存必须配短 TTL（60~300 秒）并且限制总量。更彻底的方案是布隆过滤器：把存在的 key 预先存进过滤器，查询前先过一遍，不存在直接返回，根本不碰缓存和库。注意布隆过滤器有误判率（约 1%，可调）且不天然支持删除，删除场景要用 Counting Bloom Filter。

Q：主从延迟导致的脏回填怎么根治？

A：三种力度递增的办法——① 回填时强制读主库（最简单，给主库增加读压力）；② 记录数据版本号，回填时只允许更新的版本写入（需要缓存里存版本）；③ 用 Canal 订阅 binlog，由数据变更事件驱动缓存删除，而不是应用自己删——这样删除动作由数据库的真实变更触发，天然与主库进度对齐。
