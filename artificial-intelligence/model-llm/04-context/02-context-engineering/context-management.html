📚 上下文窗口管理（Context Management）

大模型为什么"记不住"长对话？Token 怎么算？超窗口了怎么办？

🧠 一句话理解：上下文窗口就像你桌面上那张便签纸——能写下的字有限。写满了，要么把旧内容划掉（截断），要么先总结一遍再写（压缩）。模型没有"长期记忆"，它每轮只能看到这张便签上的内容。

一、窗口限制：Token 是什么，怎么算

模型不是按"字"记账，而是按 Token。Token 是模型分词（BPE/WordPiece）后的最小单位。

文本如何变成 Token

一段中文"我爱自然语言处理"会被切成一串子词 Token（如 我 爱 自然 语言 处理），英文 "learning" 可能切为 learn + ing。不同模型的分词器不同，Token 数也不同。

图：中文 9 个字 → 5 个 Token（取决于分词器）

经验估算（用于快速判断成本）

语言粗略换算举例
中文约 1.5~2 字 = 1 Token"今天天气真好" ≈ 4 Token
英文约 4 字符 = 1 Token"Hello world" ≈ 2 Token
代码约 1 Token / 3~4 字符一行 Python ≈ 8~15 Token
💡 多数平台提供 tiktoken（OpenAI）或各自 tokenizer 工具，能精确计数。估算成本前先量一次真实文本最稳妥。

窗口是输入 + 输出合计的上限。例如 128K 窗口，若已输入 120K，模型最多只能再输出 8K。

二、为什么需要"管理"：窗口会溢出

多轮对话里，历史消息不断累积，最终越过窗口红线，旧信息被"挤出去"。

图：对话越久，历史越多，旧内容从窗口底部被"挤掉"

⚠️ 溢出不是报错，而是静默丢失：模型不会告诉你它"忘了"开头说了什么。表现往往是：前面约定的规则失效、人物设定漂移、引用了不存在的内容。

三、四种压缩 / 管理策略

当内容要超窗口时，常见思路是"少装点"或"先总结"。

① 摘要压缩（Summarization）

把较早的对话交给模型生成一段摘要，用摘要替换原始多轮记录。例：把前 20 轮压成"用户目标：搭建博客；已确认技术栈：Next.js + Postgres"。

② 滑动窗口（Sliding Window）

只保留最近 N 条消息，更早的直接丢弃。实现最简单，但会丢掉长期背景。

③ 重要性筛选（Selection / KV-Cache 裁剪）

根据注意力分数或规则，保留关键消息（如系统设定、工具调用结果），丢弃闲聊。进阶做法是检索时只把"相关历史"塞回窗口。

④ RAG 增强（检索替代长上下文）

把长文档、历史记录存到外部（向量库/数据库），用时再检索最相关的片段注入窗口，而不是一次性全塞进去。

策略实现成本保留长期信息适用场景
摘要压缩中（需额外调用）★★★☆☆长对话助手、客服
滑动窗口低★☆☆☆☆短时任务、一次性问答
重要性筛选中~高★★★★☆Agent、带工具的多轮

图：无论哪种策略，目标都是"在窗口红线内塞进最该被看见的信息"

四、持久化：把记忆搬出窗口

窗口之外，用外部存储兜底长期状态。四种常见落点：

🗄️

关系型 / 文档数据库

存结构化会话、用户配置、业务状态。适合需要查询与事务一致性的数据。

⚡

Redis 缓存

存热点会话、短期状态、限流计数。低延迟，适合"当前正在进行的对话"。

🔍

向量数据库

存长文档与历史 embeddings，按需检索最相关片段注入窗口（RAG 核心）。

💬

会话管理

把每轮 (user, assistant) 落盘，支持"换设备续聊""按会话回放"。

💡 实践里常组合使用：Redis 扛在线会话、向量库扛知识检索、数据库扛持久业务数据。

五、实践避坑清单

⚠️ 常见错误
  • 把几十轮原始对话全量塞回下一轮请求 → Token 爆表且贵。
  • 只在 System Prompt 写规则，却在第 30 轮被挤出窗口 → 规则"失忆"。
  • 用超长上下文替代检索 → 成本极高，且长文档里关键信息易被"平均稀释"。
✅ 推荐做法
  • 关键信息前置：把角色、约束、目标放进 System Prompt，且尽量精简。
  • 先估算后发送：正式接入前用 tokenizer 量一次真实长度。
  • 用 RAG 替代堆长文本：文档放外部，按需检索注入。
  • 多级缓存：在线会话用 Redis，长期知识用向量库。

延伸阅读：压缩与检索的工程实现，是上下文工程的两个核心方向——前者在"窗口内"用摘要/筛选省空间，后者把知识"搬到窗口外"用检索按需注入。组合使用效果最佳。
