StatefulSet 与 PVC：Pod 重建后名字没变，数据就一定安全吗

沿 db-0 故障重建，区分稳定身份、卷声明、物理存储与数据库复制。

无状态副本和有状态副本的差别

普通 Web 服务的三个 Pod 可以互换，请求发给任何一个都能处理；数据库节点常有成员 ID、日志位置和本地数据，不能随意当成相同副本。StatefulSet 给每个副本稳定序号和名字，例如 db-0、db-1、db-2；结合无头 Service 可获得可预测的网络身份。它还可通过 volumeClaimTemplates 为每个序号创建独立 PVC，使 db-0 重建后仍引用自己的持久卷声明。

“稳定”指控制器努力维持标识和存储关联，不表示 Pod 永远不重启、IP 永不变，也不表示数据库数据自动复制到别的节点。网络身份通常依靠名字与 DNS，具体记录可用性受 Pod Ready 状态与 Service 配置影响；客户端仍应处理连接失败与重试。

db-0 故障的时间线

起初 db-0 挂载自己的 PVC，写入一批日志。节点故障后，旧 Pod 不再正常提供服务，控制器尝试在合适节点重建 db-0。新 Pod 使用同一序号、同一 PVC 声明和稳定名字；能否成功挂载取决于底层 PV、存储访问模式、拓扑位置、卷附着和旧节点是否完成安全卸载。若卷只允许单节点读写，在旧节点状态未知时，新节点可能需要等待卷分离，避免同时写同一块存储。

一旦新 Pod 能挂卷，文件是否完整仍取决于数据库的刷盘、日志恢复与存储可靠性。StatefulSet 不验证数据页校验和，也不会自动修复业务层复制协议。若底层 PV 本身损坏，固定名字也救不回数据；应有备份、复制和恢复演练。

PVC、PV 与存储类各负责什么

PVC 是工作负载提出的容量、访问模式等存储需求；PV 是满足它的实际存储资源抽象；StorageClass 通常定义动态供应方式与参数。绑定后，PVC 为 Pod 提供相对稳定的存储引用。删除 Pod 通常不会自动删除对应 PVC，但删除 StatefulSet、缩容以及设置了 PVC 保留策略后的具体行为需要按版本与配置核对。不能以为“缩容后旧卷一定永远保留”，也不能未经确认就手工删除卷。

存储访问模式如 ReadWriteOnce 描述底层访问约束，不等于数据库可以多进程安全写入；即使存储允许多节点共享，数据库文件格式未必允许并发写。网络文件系统的持久化与锁语义也会影响数据库正确性。选择卷时要同时考虑延迟、吞吐、可用区拓扑和恢复时间。

层次提供什么不保证什么
StatefulSet稳定 Pod 序号数据库复制
Headless Service可预测的成员 DNS固定 IP 或固定主节点
PVC/PV存储声明与实际卷内容绝不损坏
数据库日志恢复与选主底层卷必定可用

顺序创建与滚动更新

StatefulSet 默认通常按序创建和删除 Pod，配合 Ready 状态推进，有利于有序启动；也有并行 Pod 管理策略可选。滚动更新时如何逐个替换，仍要确认数据库自己的主从关系、仲裁和升级兼容性。控制器保证 Kubernetes 资源趋近目标状态，不了解数据库当前领导者是否可安全下线。

三副本数据库如果升级时同时失去两份有效副本，可能失去多数派。即便控制器逐个更新，也要检查每一步成员是否追平、剩余仲裁是否足够、客户端是否正确切换。数据库 Operator 能编码部分领域规则，但也须审查它的故障与升级流程。

服务发现和读写路由

Headless Service 可让客户端发现每个有身份的 Pod，但“知道 db-0 地址”不代表 db-0 永远是主节点。领导者可能切换到 db-1，应用需要通过数据库协议、代理或 Operator 提供的服务路由找到正确写入口。把 StatefulSet 序号硬编码成主从角色，会在故障切换后写错位置。

Pod IP 会变化，DNS 记录也有缓存和生效时间；长连接在重建后需要重连。若使用固定域名做成员互联，要验证启动与就绪探针、DNS 解析、网络策略和证书里的名字一致。稳定身份减少发现成本，不能消除网络故障。

一套最小演练

部署三副本测试库，记录 db-0 的 Pod 名称、IP、PVC、PV 与数据库日志位置。删除 db-0 Pod，观察新 Pod 名字保留、IP 可能变化、PVC 是否仍绑定同一卷；再模拟节点不可用，观察卷分离与重新挂载耗时。最后验证数据库集群成员关系、已提交数据和主节点路由。演练完成后测试备份恢复，而不是只测试 Pod 自动重建。

StatefulSet 的四项稳定保证

保证具体表现依赖
稳定名称Pod 名为 <sts>-0、-1…，重建后不变StatefulSet 控制器
稳定网络标识每个 Pod 有独立 DNS：pod-0.svc.ns.svc.cluster.localHeadless Service（clusterIP: None）
稳定存储按 volumeClaimTemplates 为每个实例建 PVC，重建后仍挂载同一卷PVC + PV
有序操作默认按序号顺序创建/扩缩/更新，前一个 Ready 才继续OrderedReady 策略

前提：必须配套 Headless Service，否则 Pod 没有稳定的 DNS 记录，稳定网络标识无从谈起。

关键参数对照

参数取值含义
podManagementPolicyOrderedReady（默认）/ Parallel是否严格按序；Parallel 可并行创建，加快扩容但失去顺序保证
updateStrategy.typeRollingUpdate / OnDelete有状态服务常用 OnDelete 人工控制升级节奏
rollingUpdate.partition如 2序号 ≥ partition 的 Pod 才更新，用于灰度（金丝雀）
persistentVolumeClaimRetentionPolicywhenDeleted / whenScaled（1.27+ 稳定）控制删除/缩容时是否保留 PVC
serviceNameHeadless Service 名决定 DNS 域名后缀
replicas缩容时按序号从大到小删缩容前需先迁移数据

运维命令

命令

# 扩缩容（缩容按序号从大到小，务必先迁移/备份数据）
kubectl scale sts mysql --replicas=5
kubectl patch sts mysql -p '{"spec":{"replicas":3}}'

# 灰度更新：只更新序号 >= 3 的 Pod（先让 3、4 跑新版本）
kubectl patch sts mysql -p '{"spec":{"updateStrategy":{"rollingUpdate":{"partition":3}}}}'
kubectl set image sts/mysql mysql=mysql:8.0.36

# 验证稳定 DNS（在集群内解析）
kubectl run -it --rm dnsutils --image=busybox:1.36 --restart=Never -- \
  nslookup mysql-0.mysql.default.svc.cluster.local

# 查看 PVC 与绑定（重建后仍绑定同一个 PV）
kubectl get pvc -l app=mysql -o wide

# 删除 StatefulSet 但保留 PVC（默认就是保留，删除 PVC 才会真丢数据）
kubectl delete sts mysql --cascade=orphan
kubectl delete pvc mysql-data-mysql-0      # 谨慎：这一步才真正丢数据

定义

# 最小可用定义（Headless Service + volumeClaimTemplates）
apiVersion: v1
kind: Service
metadata:
  name: mysql
spec:
  clusterIP: None                 # Headless：不做负载均衡，暴露每个 Pod 的 DNS
  selector:
    app: mysql
  ports:
  - port: 3306
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
spec:
  serviceName: mysql
  replicas: 3
  podManagementPolicy: OrderedReady
  updateStrategy:
    type: OnDelete                # 有状态服务：人工确认后再升级
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels: {app: mysql}
    spec:
      containers:
      - name: mysql
        image: mysql:8.0
        volumeMounts:
        - name: data
          mountPath: /var/lib/mysql
  volumeClaimTemplates:            # 每个实例一份 PVC
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: fast-ssd
      resources:
        requests:
          storage: 100Gi

深入自检

StatefulSet 稳定的到底是什么？

三件事：名称（name-序号重建后不变）、网络标识（配合 Headless Service 得到固定 DNS）、存储（每个实例一份 PVC，重建后挂载同一个卷）。Deployment 的 Pod 名随机、重建换 IP、共享存储语义，都不具备这些保证。

为什么必须配 Headless Service？

因为 StatefulSet 的稳定网络标识依赖 Headless Service 给每个 Pod 生成独立的 DNS A 记录（pod-0.svc.ns.svc...）。普通 Service 只提供一个 ClusterIP 做负载均衡，没有 per-Pod 记录，所以稳定身份无从建立。

partition 有什么用？

它指定「序号小于 partition 的 Pod 不更新」，因此可以实现灰度：先让高序号实例（如 replica 3、4）跑新版本验证，确认无误后再把 partition 调小逐步推进，最后置 0 全量。这是有状态服务控制升级风险的关键手段。

缩容会丢数据吗？

取决于 PVC 保留策略。默认删除 StatefulSet 不会删 PVC，但缩容（scale down）在旧版本会删除对应 PVC（1.27+ 可用 persistentVolumeClaimRetentionPolicy.whenScaled: Retain 保留）。无论如何，缩容前都应先把该实例的数据迁移或确认已备份。

OrderedReady 和 Parallel 怎么选？

需要严格启动顺序（如选主、初始化依赖前序节点）用默认 OrderedReady，代价是扩容串行、任一卡住全队阻塞；实例之间无启动依赖、追求扩容速度时用 Parallel，代价是失去顺序保证，应用必须自己处理并发初始化与选主。

自检

新 Pod 仍叫 db-0 并挂上原 PVC，能否据此断言数据一定完整且它仍是主节点？

不能。存储完整性与数据库主从选举由各自机制保证，StatefulSet 只管理身份和资源关联。

第三层 · 排障与边界：StatefulSet 运维高频问题

现象原因怎么查 / 怎么办
Pod 卡在 PendingPVC 没有可用 PV（StorageClass 没配 / 配额满）kubectl describe pvc 看 Events；kubectl get sc 确认 provisioner
Pod 删不掉 / 一直 Terminating前一个 Pod 未完全终止（有序性约束）kubectl delete pod xxx --grace-period=0 --force（谨慎）
滚动更新卡在某个序号该 Pod 的 readiness probe 一直失败kubectl describe pod 看就绪探针；kubectl logs
节点故障后 Pod 不重建默认需人工确认（节点 NotReady 超过阈值才驱逐）等 kube-controller-manager 判定；或手动 delete node
缩容后 PVC 还在PVC 不会随 Pod 删除（这是设计，保数据）确认无疑后手动 kubectl delete pvc
扩不了容，报 volume node affinityPV 绑在特定节点的本地盘本地存储场景需调度回原节点；换用网络存储
  • 排查顺序：get pod → describe pod 看 Events → describe pvc 看绑定 → get pv 看供给。
  • 边界一：StatefulSet 的 Pod 是逐个创建/删除的（序号 0 → n-1），前一个 Ready 才会动下一个——所以 n 个副本的滚动更新耗时是单体的 n 倍。
  • 边界二：删除 StatefulSet 不会删除 PVC，也不会删除 PV；删 PVC 是否删 PV 取决于 StorageClass 的 reclaimPolicy（Retain / Delete）。
  • 边界三：spec.replicas 缩容时，PVC 保留但 Pod 消失；再次扩容会重新挂上原来的卷——这是「稳定身份」的价值所在。

排障命令

# 一眼看清 Pod / PVC / PV 的绑定关系
kubectl get pod,pvc,pv -o wide | grep -i <name>

# 看 PVC 为什么没绑上
kubectl describe pvc <pvc-name>      # 重点看 Events 段

# 看 StatefulSet 的更新进度
kubectl rollout status statefulset/<name>

# 手动确认无数据风险后再删 PVC（危险操作）
kubectl delete pvc <pvc-name>

量化参考：StatefulSet 滚动更新默认 partition=0 全量更新；设 partition=N 可实现「只更新序号 ≥ N 的 Pod」，常用于金丝雀发布。
