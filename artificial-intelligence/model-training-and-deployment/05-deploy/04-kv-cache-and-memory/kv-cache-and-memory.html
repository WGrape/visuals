KV Cache 与推理显存

把显存账算清楚：KV Cache 的精确估算公式、MHA/GQA/MQA 的差异、前缀共享与分页管理如何消灭碎片，以及容量不够时按收益排序的三个杠杆。

KV Cache 到底占多少显存

Decode 阶段每生成一个 token，都要把历史上所有 token 的 Key / Value 重新参与注意力计算。 缓存下来就不用重算，代价是显存随 batch × 序列长度 × 层数 × KV 头数 × head_dim 线性增长。

# 每个 token 的 KV 显存（bytes）
per_token = 2(K 和 V) × n_layers × n_kv_heads × head_dim × dtype_size

# 例：32 层、GQA 8 个 KV 头、head_dim=128、fp16(2 bytes)
per_token = 2 × 32 × 8 × 128 × 2 = 131072 bytes ≈ 128 KB / token

# 一条 8K 上下文的请求：8192 × 128KB ≈ 1 GB
# 并发 32 条：≈ 32 GB —— 已经超过一张 A100 80G 的一半
这是大模型服务显存墙的根源：并发数和上下文长度不能同时要。 很多"OOM"事故不是模型太大，而是KV Cache 吃掉了剩下的显存。
MHA
每个 Q 头配一个 K 头一个 V 头，KV 最大
GQA
一组 Q 头共享一个 KV 头，压缩 4~8 倍，质量几乎不掉
MQA
所有 Q 头共享 1 个 KV 头，压缩最大，长文质量略降

四条压缩路线

前缀共享（Prefix Caching / Automatic Prefix Cache）在两类场景收益最大： ① 所有请求共享一段很长的 system prompt；② 多轮对话的历史部分不变，只追加新一轮。 命中时该段 prefill 直接跳过，TTFT 明显下降。
量级感受：同一段上下文，首次请求约 840 ms，第二次命中缓存可降到 190 ms 上下 ——不是模型变快了，而是有 4 倍的工作根本不用做。
注意代价：前缀缓存要多占显存（存的是 KV，不是省掉 KV），所以它换来的是「延迟」而不是「并发」； 显存本来就紧的配置上盲目开启，反而可能压低并发上限。

碎片：为什么"还剩 30% 显存"却分配失败

朴素做法是为每条请求预留一块最大长度的连续显存（比如 max_seq_len=8192 全预留）。 实际用多少不确定，于是产生两类浪费：

内部碎片
请求只用了 800 token，却占着 8192 的坑，剩下的谁也用不了
外部碎片
不同请求反复申请释放后，空闲显存被切成小块，凑不出一整段连续的

容量估算：一问就能算出要几张卡

显存总需求 ≈ 模型权重 + KV Cache + 激活值 + 框架开销

1) 权重：    参数量 × dtype 字节
             7B × fp16(2B) = 14 GB
             7B × int4(0.5B) ≈ 3.5 GB

2) KV Cache：并发数 × 平均上下文 × per_token
             32 × 4096 × 128KB ≈ 16 GB

3) 激活与框架：经验值 1~3 GB（与 batch、实现相关）

7B + fp16 + 32 并发 4K 上下文 ≈ 14 + 16 + 2 ≈ 32 GB  → 单卡 A100 40G 够，L4 24G 不够
调容量时的三个杠杆（按收益排序）： ① 降 KV 单 token 成本——开 fp8 KV、用 GQA 模型； ② 降并发或上下文——限流、截断历史、开启前缀共享； ③ 降权重——量化（见本学科「模型量化」章节）。 先量出来到底是哪一项占大头，再动对应的杠杆。
上面的公式是量级估算，不是精确值。不同框架的实现（是否用 PagedAttention、 是否共享前缀、激活是否重算）会差出 20%~40%。上线前用真实流量压测，以实测为准。

KV Cache 显存计算

模型层数 / 头数 / 维度每 token KV 占用
LLaMA-2-7B32 层 / 32 头 / 128 维0.5 MB/token（FP16）
LLaMA-2-13B40 层 / 40 头 / 128 维0.8 MB/token
LLaMA-2-70B80 层 / 64 头 / 128 维（GQA 8）0.32 MB/token（GQA 大幅降低）
GPT-3-175B96 层 / 96 头 / 128 维1.2 MB/token

计算公式：每 token 字节数 = 2(K和V) × 层数 × 头数 × 每头维度 × 精度字节数 × batch。以 LLaMA-2-7B 为例：2 × 32 × 32 × 128 × 2(FP16) = 524288 B ≈ 0.5 MB。所以 2048 token 上下文、batch=8 时：0.5 MB × 2048 × 8 = 8 GB——比模型权重（14GB的一半）还大。这就是为什么长上下文服务显存吃紧的根本原因。

优化手段效果代价
GQA（分组查询注意力）KV 显存降 4~8 倍质量轻微下降；LLaMA-2-70B/Qwen 都用
MLA（DeepSeek）降 5~10 倍实现复杂
PagedAttention（vLLM）显存利用率 60%→90%+解决碎片与预留浪费
KV Cache 量化（INT8/FP8）显存减半轻微掉点
prefix caching相同前缀复用，省 30~90%需要命中前缀
滑动窗口/截断限制长度丢失远距离信息

代码与配置

# 精确计算 KV cache 显存
def kv_cache_bytes(n_layers, n_heads, head_dim, n_kv_heads=None,
                   ctx_len=2048, batch=1, dtype_bytes=2):
    """n_kv_heads != n_heads 表示用了 GQA/MQA"""
    n_kv = n_kv_heads or n_heads
    per_token = 2 * n_layers * n_kv * head_dim * dtype_bytes   # K 和 V 各一份
    return per_token * ctx_len * batch, per_token

total, per_token = kv_cache_bytes(32, 32, 128, ctx_len=2048, batch=8)
print(f"每 token {per_token/1024:.0f} KB, 总计 {total/1024**3:.2f} GB")
# LLaMA-2-7B: 每 token 512 KB, 总计 8.00 GB

# GQA 的收益（LLaMA-2-70B: 64 头 query, 8 头 kv）
_, p_mha = kv_cache_bytes(80, 64, 128, n_kv_heads=64)
_, p_gqa = kv_cache_bytes(80, 64, 128, n_kv_heads=8)
print(f"MHA {p_mha/1024:.0f}KB -> GQA {p_gqa/1024:.0f}KB, 省 {p_mha/p_gqa:.0f}x")
# vLLM 配置（PagedAttention + prefix caching）
python -m vllm.entrypoints.openai.api_server \
  --model meta-llama/Llama-2-7b-hf \
  --dtype bfloat16 \
  --max-model-len 4096 \
  --gpu-memory-utilization 0.90 \      # 留给 KV cache 的显存比例
  --enable-prefix-caching \            # system prompt 相同的请求复用 KV
  --kv-cache-dtype fp8                  # KV cache 用 FP8，显存减半
  --max-num-seqs 256                    # 最大并发序列数

# 关键参数关系：
# 可用 KV 显存 = 总显存 × gpu_memory_utilization - 模型权重 - 激活
# 能支持的并发数 = 可用KV显存 / (每token字节 × 平均上下文长度)
# 所以：降低 ctx_len 或量化 KV -> 并发数线性提升

# 监控（vLLM 暴露的指标）
# vllm:gpu_cache_usage_perc        <- 接近 1 说明 KV cache 满了，新请求会排队
# vllm:num_requests_waiting        <- 排队请求数
# vllm:avg_generation_throughput   <- 生成吞吐

排障清单

症状原因处理
并发上不去，请求排队KV cache 显存不够降 max-model-len；量化 KV；开 prefix caching；加卡
长上下文直接 OOMKV 显存随 ctx_len 线性增长限制长度；用 GQA/MLA 模型；PagedAttention
显存利用率只有 50%静态分配造成碎片与预留浪费用 vLLM 的 PagedAttention；不用 HuggingFace 的默认 generate
预填充（prefill）很慢prompt 太长，prefill 是计算密集用 prefix caching；拆短 prompt
解码速度慢decode 是访存密集（每步要读全部 KV）量化 KV 减少读取字节数；增大 batch 提高带宽利用
相同 system prompt 反复计算没开 prefix caching--enable-prefix-caching；把固定内容放开头
batch 大了反而慢KV cache 挤爆，触发 swapping降 max-num-seqs；或开 CPU offload（会慢）

核心公式要记住：KV 显存 = 每 token 字节 × 上下文长度 × 并发数。三个因子任意一个翻倍，显存就翻倍。这是 LLM 服务容量规划的基石。
