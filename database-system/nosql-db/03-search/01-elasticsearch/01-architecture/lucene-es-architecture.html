先分清 Lucene 和 Elasticsearch

这两个名字经常一起出现，但它们根本不是一回事：

Lucene

一个单机检索库。负责真正的倒排索引、分词、打分、查询执行。它是 Elasticsearch 的心脏。

Lucene 自己不关心网络、分片、副本、集群 —— 这些都是上层的事。

Elasticsearch

一个分布式服务。它在 Lucene 外面包了一层，提供：

  • 把数据切成多个分片分散到多台机器
  • 副本与故障转移
  • 把请求路由到正确的分屑片、汇总结果
  • HTTP API、映射（mapping）、聚合 DSL

一句话：每个 Elasticsearch 分片，本质上就是一个独立的 Lucene 索引。理解了 Lucene 在单机上怎么工作，ES 的很多行为就能解释。

倒排索引：从「文档找词」到「词找文档」

正向索引是「这篇文档里有哪些词」，倒排索引反过来：这个词出现在哪些文档里。

倒排索引把「文档→词」翻成「词→文档」
组成部分存什么用在哪
词项词典 Term Dictionary所有出现过的词（排序后）快速定位一个词是否存在
倒排表 Posting List包含该词的文档 id 列表 + 词频/位置召回候选文档
Doc Values按文档组织的列式值排序、聚合（与倒排方向相反）
Stored Fields原始文档的字段内容取回结果展示
Norms归一化因子（长度等）打分时消除长度偏好

写入到底发生了什么：refresh / flush / merge

Elasticsearch 被叫做「近实时」而不是「实时」，原因全在这条写入链路上：

文档写入 ↓ 内存 buffer + 写 translog（保证不丢） ↓ refresh（默认 1 秒一次） 生成一个新的不可变 segment，并让它变得可被搜索 ← 到这里就能被查到了 ↓ flush（translog 攒够 / 定时 / 手动） 把内存里的数据真正 fsync 到磁盘，清空 translog ↓ merge（后台持续进行） 把多个小 segment 合并成大 segment 并<b>真正删除被标记删除的文档</b>
不可变 segment：追加写 + 后台合并的基石

这三个动作最容易混淆，记住触发条件：

refresh多久能被搜到 —— 默认约 1 秒。代价是生成很多小段。
flush数据是否落到磁盘 —— 保证宕机不丢。
merge段是否被合并、磁盘是否被回收 —— 后台长期任务。

查询是怎么在各个分片上跑的

一个搜索请求打到 ES 之后，是一次典型的分散-收集（scatter-gather）：

  1. 任意一个节点作为协调节点接住请求。
  2. 根据索引的分片数算出要查哪些分片，把请求转发给持有这些分片的节点。
  3. 每个分片各自执行查询，算好自己的 top-N 结果（注意：此时打分只基于本分片的统计信息）。
  4. 协调节点收集所有分片的候选，重新排序，取全局 top-N。
  5. 如果需要完整文档，还要向相关分片再发一次 fetch 请求取回字段。

这里藏着一个著名的坑：默认情况下每个分片的 TF-IDF/BM25 统计是本地的。一个词在分片 A 很稀有、在分片 B 很常见，本地打分就会失真，跨分片的比较天然不公平。缓解办法：数据分布均匀（更多文档、合理分片数），或者使用 dfs_query_then_fetch 先全局统计一次词频再打分 —— 代价是多一轮网络往返。

深入自检

为什么 refresh_interval 太长会让「刚写入的数据查不到」？

因为新写入的文档必须先被 refresh 成一个可被搜索的 segment，才会进入倒排索引参与查询。refresh 之前，数据只在内存 buffer 与 translog 里 —— 查不到，但也不会丢（translog 保证持久化）。写多读少的场景适当调大 refresh_interval（如 30s）能显著减少小段数量、降低 merge 压力。

为什么删了很多文档，磁盘占用没降？

因为删除只是在 .del 文件里记一笔「这个文档已作废」，数据本身还在 segment 里，只有等到包含它的 segment 参与 merge、被重写成新段时才会真正释放。另外 update 在 Lucene 里就是「删旧 + 写新」，会产生同样的效果。大量删除后想立刻回收，可以触发 merge —— 但要清楚这是一次 IO 密集操作。

为什么 Elasticsearch 不建议用 _id 之外的方式自行指定路由分数？

路由公式默认是 hash(_id) % 主分片数。如果换用自定义路由字段，好处是同一业务键的文档会落在同一分片（可以做分片内 join 与更好的聚合性能），代价是数据可能倾斜 —— 某个路由值过热会把压力堆到一个分片上。所以要挑区分度高且分布均匀的字段，并接受 hot shard 的风险。

Lucene 的段合并为什么会拖慢写入？

merge 需要把多个 segment 读出来、合并排序、重新写出一个新段，是 IO 与 CPU 双密集的操作。写入压力大时会产生大量小段，触发频繁 merge，形成「越写越慢」。常见缓解：调大 refresh_interval、控制单分片大小、给 merge 限速（合并节流）、以及避免一次性批量导入超大文档。
