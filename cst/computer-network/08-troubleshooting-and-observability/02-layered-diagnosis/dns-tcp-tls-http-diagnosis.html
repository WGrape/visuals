DNS → TCP → TLS → HTTP：一次访问失败怎样分层定位

用“网页打不开”把域名解析、建连、证书、HTTP 状态和应用响应逐段验证。

先记录故障的精确形态

“网页打不开”可能指域名解析失败、连接超时、证书告警、HTTP 5xx 或页面资源加载失败。排查第一步记录 URL、时间、客户端网络、错误提示、是否仅某地域或某用户发生，以及最近变更。不要在没有证据时直接清缓存或重启服务；这会抹掉可用于定位的状态。一次请求应尽量关联客户端时间、边缘节点、负载均衡和源站日志。

先验证问题是否可复现：同一域名从不同网络访问、同一网络直接访问目标 IP、强制 IPv4 或 IPv6。差异可将故障限定在 DNS、某条网络路径或某个协议栈。测试时注意直接用 IP 访问 HTTPS 可能因 Host/SNI 不匹配而失败，不能把这个新错误当成源站不可用。

路径图：网页访问的分层检查

箭头表示本例中的处理次序；每个环节的状态都要分别验证，不能由前一环节成功推断后一环节成功。

DNS 阶段

查询 A 与 AAAA，记录响应码、TTL、CNAME 链和实际返回地址。NXDOMAIN 表示名称不存在，SERVFAIL 更像解析链路或权威响应失败；拿到 IP 只是第一关。把权威服务器与客户端使用的递归解析器结果对比，可发现缓存或配置传播问题。若只有 IPv6 访问失败而普通浏览器缓慢回退，重点查 AAAA、IPv6 路由和监听。

有时解析器返回正确地址，但应用进程沿用旧连接或自己的 DNS 缓存。对比连接的真实远端 IP 和 `dig` 的答案。如果不一致，查连接池、运行时解析策略和代理。不要把命令行单次 DNS 结果当作浏览器真实使用的结果。

逐步推演

查名称

核对 DNS 响应、TTL、A/AAAA 与实际使用地址。

查连接

观察 TCP SYN/ACK 或 QUIC 握手与回退。

查 TLS

按 SNI、SAN、证书链和版本定位。

查 HTTP

关联状态码、请求 ID、上游与浏览器资源。

TCP 或 QUIC 建连阶段

对 TCP 连接看 SYN 是否发出、SYN-ACK 是否返回、是否收到 RST，以及三次握手耗时。SYN 重传而无回应可能是路由、ACL、目标未监听或回程问题；立即 RST 通常表示目标栈明确拒绝连接，但还需确认 RST 来自哪台设备。能 ping 通只说明某种 ICMP 路径可用，不保证目标端口可达。

HTTP/3 使用 QUIC over UDP 时，不能期待看到 TCP SYN。检查 UDP 通路、QUIC 握手与是否回退到 HTTP/2。若只在企业网络失败，可能是中间设备限制 UDP；若 TCP 回退成功，应用层可能无故障。记录传输协议和最终连接的远端地址，避免把两个不同路径混在一个结论里。

TLS 阶段

TCP 连上之后仍可能在 TLS 握手失败。核对 SNI、证书 SAN、有效期、证书链、协议版本和双方支持的密码套件。负载均衡或 CDN 终止 TLS 时，客户端看到的是入口证书，而后端到源站可能还有另一段 TLS。若前端成功、后端握手失败，浏览器可能只看到网关返回的 502。

调试时使用准确的域名进行 TLS 验证，避免 `curl` 直接访问 IP 时缺失 SNI。不得通过跳过证书验证来宣布故障修复；那会隐藏身份不匹配或中间人问题。若只有一批客户端报错，比较其信任库与 TLS 版本支持。

HTTP 和应用阶段

握手成功后记录请求方法、Host、路径、状态码、响应头、首字节时间和响应体。404 可能是路径或路由错误，401/403 可能是认证授权问题，429 是限流线索，502/503/504 需要区分网关到后端的失败、无可用实例或上游超时。状态码只是入口给的结果，真实原因仍需请求 ID 对齐后端日志。

若 HTTP 返回 200 但页面空白，继续检查资源请求、CSP、脚本错误和浏览器渲染。若首字节很慢，比较网关排队、后端处理与数据库时间；若正文传输慢，看窗口、丢包、队列与客户端读取速度。把“连接建立成功”误当成“页面可用”，会漏掉一半故障链。

一张简化的决策树

无 DNS 答案，查权威、递归与缓存；有答案但端口连不上，查去程、回程、监听和策略；端口通但 TLS 不通过，查名称与链；TLS 通但 HTTP 报错，按状态和请求 ID 查网关与应用；HTTP 正常但用户仍失败，查浏览器资源和渲染。每步都保留一个可复现命令或抓包证据，下一步才不会建立在猜测上。

诊断应记录“哪一层已被证实正常、证据来自哪里、尚未验证什么”。例如本机 SYN 发出只证明客户端发包，不证明服务器收到；服务器返回 200 只证明入口回包，不证明浏览器执行 JS 成功。对每一层区分观察点，才能避免错误归因。

复盘和长期监控

建立分阶段指标：DNS 错误率、连接建立成功率和耗时、TLS 失败原因、HTTP 状态分布、首字节与总耗时、前端资源错误。用请求 ID 或 trace 串起网关与后端，并按地区、运营商、IPv4/IPv6、HTTP 版本切片。平均成功率可能掩盖某一地区全部故障，应观察关键切片的尾部。

复盘时把故障开始时间与 DNS 变更、证书轮换、路由发布、网关配置和应用部署对齐。提出修复时明确验证指标与回滚条件，避免“重启后好了”成为唯一结论。

自检

浏览器收到了 HTTP 200，就能证明用户一定看到了完整页面吗？

不能。后续资源请求、脚本执行和渲染仍可能失败；还需前端错误与资源加载证据。
