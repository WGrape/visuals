🧩 组合优于继承

判断信号当两个功能维度会独立变化、子类名称开始拼接多个形容词时，先考虑组合。

01 · 原则从问题里长出来

直接写会有什么代价？

通知有普通/加急两种规则，发送渠道有邮件/短信两种。继承容易做成四个子类；以后再加推送渠道与定时发送，组合数继续增长。

先看问题写法

class UrgentEmailNotice ...
class UrgentSmsNotice ...
class NormalEmailNotice ...
class NormalSmsNotice ...
// 新增渠道 × 新增规则，子类数不断相乘

关键转折

把消息规则和发送渠道分成两种职责；Notice 持有 Channel 接口。运行时选择搭配即可。

04 · 把原则写进代码

最小伪代码

interface Channel { send(text) }
interface Rule { format(text) }
class Notice {
  constructor(rule: Rule, channel: Channel) {
    this.rule = rule; this.channel = channel
  }
  send(text) { this.channel.send(this.rule.format(text)) }
}
notice = Notice(UrgentRule(), SmsChannel())

从代码中带走三件事

  1. 找出独立变化轴，而不是看到继承就一律重写。
  2. 抽象只表达稳定契约，不把 Email 的专有参数塞进 Channel。
  3. 在组装处选择实现；业务流程只依赖接口。
05 · 原则不是教条

对应哪些模式？什么时候收手？

  • 桥接：两个独立维度由组合连接
  • 策略：注入可替换算法
  • 装饰器：组合叠加可选职责

继承不是错误：稳定的 is-a 关系、共享不变量和模板流程仍可用继承。问题是用继承表示“可以自由拼装的能力”。

加急通知和短信渠道都可能增加新类型，为什么不要建立 UrgentSmsNotice？

两个维度的组合会成倍扩张；让 UrgentNotice 持有 Channel，可分别新增消息规则或渠道。
