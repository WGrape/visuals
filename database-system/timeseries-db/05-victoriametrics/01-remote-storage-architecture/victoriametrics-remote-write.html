VictoriaMetrics 远端写入与存储架构

沿 Prometheus remote_write、写入、存储和查询的角色关系理解架构。

VictoriaMetrics

01它解决 Prometheus 的什么问题

VictoriaMetrics 最常见的用法是作为 Prometheus 的远端存储：Prometheus 继续负责抓取和告警判定，把样本通过 remote_write 转发给它长期保存。它可以在单机上吃下比 Prometheus 本地存储大得多的数据量，同时保持不错的查询性能。

两种形态
  • 单机版：一个二进制，同时做写入、存储、查询。中小规模优先选它——运维简单，单机能撑的规模往往已经够用
  • 集群版：拆成 vminsert / vmselect / vmstorage 三类组件，写入与查询各自横向扩展
兼容什么
  • 写入：Prometheus remote_write、InfluxDB line protocol、OpenTSDB、Graphite、CSV 等
  • 查询：PromQL 兼容，Grafana 基本可以直接换数据源
  • 扩展：MetricsQL 在 PromQL 之上增加了一批函数与语法糖
关于「省资源 N 倍」这类宣传：厂商与社区给出的对比数字（内存、磁盘占用）依赖具体的数据集、基数分布和版本，不同测试口径结论差异很大。把它当作「值得实测的候选」而不是「既定事实」，在你自己的数据上压一遍再下结论。

02集群版架构

写入与查询分离，各自无状态可横向扩展；vmstorage 负责持久化和副本。
为什么要把写入和查询拆开？因为两者的压力来源完全不同：写入压力取决于采集规模和抓取频率，查询压力取决于仪表盘数量和查询复杂度。拆开后可以只扩你缺的那一侧，而不是整体扩容。
