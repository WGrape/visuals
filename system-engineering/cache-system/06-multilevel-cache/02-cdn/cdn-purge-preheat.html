先建立直觉：两个方向的动作

  • 刷新（Purge）：内容已经错了，你要把错的赶紧撤下来——通知所有门店「这批货下架，下次有人要再从仓库调新的」。
  • 预热（Preheat）：还没人来买，但你提前把货铺到门店——这样第一个顾客来时店里就有货，不用等调货。

一个是事后补救（被动），一个是事前准备（主动）。

刷新（Purge / 缓存清除）

它做了什么

向 CDN 提交要刷新的 URL（或目录），CDN 让边缘节点把对应缓存标记为失效。下一个请求到达时会回源拉取最新内容。

注意：刷新只是标记失效，不是主动去拉新内容。所以刷新后的第一个用户请求仍然会慢（要走一次回源）。如果你不希望第一个用户承担这个延迟，就要再叠加预热。

三种粒度

方式粒度适用场景
URL 刷新单个精确 URL改了某一张图、某一个 JS
目录刷新某个路径前缀整批资源更新
全站刷新整个域名慎用，会引发全量回源
全站刷新的风险：它等于让所有边缘缓存瞬间全部失效，接下来所有请求都会回源——这在 CDN 领域就是一次雪崩。如果源站扛不住全量流量，会直接被打挂。除非万不得已，不要全站刷新；必须做时，要提前扩容源站并分批进行。

预热（Preheat / 缓存预热）

它做了什么

主动让 CDN 去源站拉取指定资源并缓存到边缘节点。这样真实用户第一次访问时就已经命中，不会有回源延迟。

典型场景：① 大促/活动开始前，把活动页的所有静态资源预热；② 发布新版本后预热新的 JS/CSS；③ 热点视频/安装包上线前预热，避免首访用户集体回源。

预热 vs 刷新的配合

更好的方案：用版本号代替刷新

如果你把文件名做成内容相关（如 app.3f2a1b.js），那么内容一变，文件名就变，HTML 里引用的自然是新 URL：

  • ✅ 不需要刷新：新 URL 从未被缓存过，天然回源拉最新；
  • ✅ 不会有不一致：旧文件还在（旧 HTML 仍可正常访问），新 HTML 引用新文件；
  • ✅ 可以设超长 TTL：因为内容永不变，命中率极高。
这是前端静态资源的最佳实践：HTML 用 no-cache（每次校验），JS/CSS/图片用内容 hash 命名 + 一年 TTL。发版时几乎不需要手动刷新，只需预热新文件。

注意事项

事项说明
刷新有生效延迟全网节点生效通常需要几十秒到几分钟，不是瞬时的
刷新有配额限制厂商通常限制每日刷新条数，大量刷新要走 API 分批或提额
预热不保证全部成功节点众多，可能部分失败；重要资源要验证
预热要给源站余量大量预热等于主动发起大量回源，源站要能承受
预热的隐藏风险：如果你一次性预热几万个资源，相当于主动对源站发起几万次请求。源站如果正在处理线上流量，可能被你自己压垮。做法：预热要限速分批，且避开业务高峰期。

🎯 面试问答

Q：刷新和预热能合并成一个操作吗？
A：不能，它们是方向相反的两个动作：刷新是删除（让边缘丢弃旧内容），预热是填充（让边缘提前拉取新内容）。实际使用中需要按顺序组合：先刷新清掉旧的，再预热填入新的。有些厂商提供「刷新并预热」的组合接口，但底层仍是这两步。

Q：为什么我刷新了，用户还是看到旧内容？
A：几个常见原因：① 生效延迟——全网节点需要几十秒到几分钟；② 用户本地缓存——浏览器自己也缓存了，CDN 刷新管不到用户浏览器；③ 中间层缓存——公司/运营商的代理服务器也缓存了一份；④ URL 不匹配——刷新的 URL 和实际的 URL 不一致（多了参数、协议不同）。排查：用 curl -I 看响应头里的 X-Cache 和 Age 字段确认边缘状态。

Q：大促前应该怎么预热？
A：步骤：① 提前把活动页所有静态资源（图片、JS、CSS）列成清单；② 限速分批提交预热（避免打垮源站）；③ 预热完成后抽样验证（从不同地区 curl 检查是否命中、内容是否正确）；④ 活动开始前再补一轮增量资源；⑤ 全程监控回源带宽，发现异常随时补预热。注意：预热通常只覆盖主要运营商和地区的边缘节点，不可能覆盖全部。

Q：用 hash 文件名后还需要刷新吗？
A：基本不需要。因为内容变化时文件名也变了，浏览器和 CDN 会把它当作一个全新的资源去请求，天然拿到新内容。旧文件可以留着不管（旧 HTML 可能还在引用它，留着反而更安全）。这也是为什么「内容 hash + 长 TTL」被认为是优于手动刷新的方案——它把「缓存失效」从运维操作变成了发布流程的自然结果，零失误。

刷新 vs 预热：什么时候用哪个

操作做什么产生回源吗生效时间配额
刷新 Purge删除边缘节点的缓存副本会（下次访问触发回源）通常 1~5 分钟有（按 URL/目录条数）
预热 Prefetch主动把内容推到边缘节点会（由 CDN 主动发起，可控速）数分钟~数十分钟有（且更严格）
覆盖写（部分厂商）直接替换缓存内容不会快有

厂商 API 与配额

# 阿里云 CDN 刷新（API 签名较复杂，这里给概念示意）
#   接口：RefreshObjects
#   参数：ObjectPath（支持 URL 或目录，目录以 / 结尾）
#        ObjectType: File | Directory
#   配额（常见值）：
#      URL 刷新   2000 条/天（可提额）
#      目录刷新   500 条/天
#      预热       1000 条/天（按不同套餐）

# 腾讯云 CDN
#   接口：PurgeUrlsCache / PurgePathCache（刷新）
#        PushUrlsCache（预热）
#   配额：URL 刷新 10000 条/天，目录刷新 500 条/天，预热 1000 条/天

# 通用做法：用官方 SDK，别手搓签名
pip install alibabacloud_cdn20180510
# 或
aliyun cdn RefreshObjects --ObjectPath "https://cdn.x.com/a.jpg" --ObjectType File

配额是硬约束，大版本发布前务必确认：一次全站发布可能需要刷新上万个 URL，直接超配额。应对策略：① 优先用目录刷新（1 条 = 整个目录）；② 最根本的是文件名带内容哈希，发布即新 URL，完全不需要刷新。

正确姿势与排障

  • 顺序很重要：先刷新，再预热。只预热不刷新会预热到旧内容；只刷新不预热会让首批用户承担回源延迟。
  • 预热要限速：一次性预热 10 万个文件会把源站带宽打满。分批次 + 控制并发，或只对热点 Top N（如首页、主推商品）预热。
  • 预热 URL 要和实际访问的 URL 完全一致：协议（http/https）、域名、大小写、查询参数任一不同都不会命中。
  • 刷新后验证：用 curl -I 看 Age 是否归零、X-Cache 是否变 MISS 再变 HIT。
  • 大促前预热是标准动作：提前 1~2 小时把活动页、商品图、静态资源预热到边缘，把首屏回源消除掉。
  • 别用短 TTL 代替刷新：TTL 设 60 秒看似「准实时」，实际让回源率暴涨几十倍，源站必崩。

验证命令

# 验证刷新/预热是否生效
# 1) 看 Age 是否归零（刷新成功）
curl -sI https://cdn.example.com/a.jpg | grep -iE '^(age|x-cache|cf-cache-status)'
#   刷新前：Age: 3600   X-Cache: HIT
#   刷新后：Age: 0      X-Cache: MISS   （再刷一次变 HIT，Age 从 0 开始涨）

# 2) 多节点验证（预热是否覆盖到位）
for ip in $(dig +short cdn.example.com | head -5); do
  echo "== $ip"
  curl -sI --resolve cdn.example.com:443:$ip https://cdn.example.com/a.jpg \
    | grep -iE '^(age|x-cache)'
done

# 3) 用 CDN 厂商提供的「刷新进度查询」接口看完成率
#    大批量刷新是异步的，几万条可能要十几分钟才全部生效
刷新和改文件名（加版本号）哪个更好？

改文件名完胜：app.a1b2c3.js 每次构建哈希都变，等于天然的新 URL，不需要刷新、不会有缓存不一致、配额永远够用，而且可以设 1 年 TTL + immutable 让命中率接近 100%。刷新只在「URL 必须固定」的场景（如首页 /、固定 API 路径）才用。这是现代前端发布的标准做法。

预热的配额不够怎么办？

三个层次：① 只预热热点——用访问日志统计 Top 1000 的 URL，覆盖 80%+ 流量；② 用目录预热（部分厂商支持）——1 条覆盖整个目录；③ 降低预热必要性——延长 TTL 让缓存自然命中，或预热时只预热首屏关键资源（HTML + 首屏图片），其余依赖 TTL。另外配额通常可以提工单申请提升，大促前提早申请。

刷新了但用户还是看到旧内容？

逐层排查：① 用户侧——浏览器本地缓存，刷新 CDN 不影响它（所以要靠版本号）；② 中间代理——企业/运营商代理有自己的缓存；③ CDN 多层节点——刷新是异步的，边缘节点多，全量生效要几分钟；④ URL 不匹配——带参数的 URL 要按带参数的完整 URL 刷新，或开启「忽略参数缓存」；⑤ 源站返回了旧内容——源站自己有缓存（如 Nginx proxy_cache、应用级缓存）。
