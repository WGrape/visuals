从整数集合到哈希表的去重魔法

Redis 2.0

Set 诞生 + intset 初代

2010 年，Redis Set 类型诞生。底层使用 intset（整数集合）实现， 专为纯整数小集合设计，内存极其紧凑。

// intset 结构

纯整数存储 内存极致 二分查找 O(log n) 查询
Redis 2.2

dict 应对复杂数据

当 Set 包含非整数元素或元素数量超过 intset 阈值时， 自动转换为 dict（字典）实现。

// dictEntry (Set 场景)
void *key 成员
dictEntry *next 哈希冲突链
注意: Set 的 dict value 为 NULL
O(1) 单点操作 任意类型成员 无数量上限
Redis 2.4

编码转换阈值确立

确立 intset → dict 的转换阈值。当集合元素不超过 set-max-intset-entries 且全为整数时使用 intset，否则转为 dict。

// intset 限制条件
1. 元素数量 ≤ 512
2. 所有元素必须是 整数

任意一条不满足 → dict
自动编码转换 512 元素阈值
Redis 3.2

底层结构稳定

Set 的 intset/dict 双编码机制稳定成熟。 dict 作为 O(1) 查询的核心，支持 SISMEMBER 高效判断成员存在性。

// Set 核心操作
SADD: 添加成员 → O(1)
SISMEMBER: 判断存在 → O(1)
SREM: 删除成员 → O(1)
SUNION: 交集运算 → O(n)
O(1) 增删查 集合运算
Redis 6.2

阈值参数调整

将 set-max-intset-entries 默认值从 512 调整为 512（保持）， 但优化了 intset 升级到 dict 的转换性能。

// Redis 6.2 配置
set-max-intset-entries 512
性能优化 参数保持
Redis 7.0+

set-max-intset-entries 扩大

Redis 7.0 将 set-max-intset-entries 扩大到 512（部分版本支持更大）。 intset 内部编码仍支持 int16_t/int32_t/int64_t 自动升级。

演进总结

Redis Set 的演进是一个"量体裁衣"的过程：

intset（纯整数小集合）⟷ dict（通用场景）

核心设计思想：
整数场景 → 用紧凑数组省内存（二分查找）
通用场景 → 用哈希表保性能（O(1) 查询）
自动切换 → 根据数据特征选择最优编码

这就是为什么 Set 既能存储"点赞用户 ID"（整数），也能存储"标签集合"（字符串）， 而且都能保持高性能和低内存占用。

intset 为什么省内存

① 紧凑数组没有哈希表的桶数组、指针与 dictEntry 结构开销，纯数据。
② 按需编码元素都很小时用 int16 存，变大才升级到 int32/int64，按最大元素决定编码。
③ 有序存放从小到大排列，查找用二分，不需要额外索引结构。
④ 升级不可逆一旦因为某个大数升级到 int64，即使删掉它也不会降级。

使用建议

场景建议原因
大量小整数集合（如标签 ID）保持数量在阈值内可显著省内存
元素数会持续增长别指望 intset 一直生效迟早会转 hashtable
存字符串（UUID、订单号）直接是 hashtable无 intset 红利
元素值忽大忽小（有超大整数）注意编码升级单个大数会让整个 intset 用 int64
超大规模集合考虑拆分或用 BitmapSet 的内存开销随规模线性放大

深入自检

为什么 intset 转 hashtable 后不回退？

因为回退需要实时判断且收益有限，而判断本身有开销。Redis 的设计取向是简单可靠：转换是一次性的，避免反复震荡。

调大 set-max-intset-entries 一定好吗？

不一定。数量越大，intset 的 O(logN) 查找与插入时的元素搬移越慢。阈值是个权衡：太小失去省内存收益，太大影响单次操作延迟。

为什么插入一个字符串会导致整个 Set 变编码？

因为一个 Set 只能有一种底层编码。这也是实践中常见的「内存突然涨一截」的原因 —— 可能只是加了一个非整数元素。

Set 和 Bitmap 什么时候互换？

元素是密集整数 ID（如活跃用户 ID）且范围可预估时，Bitmap 极省内存；ID 稀疏、范围巨大时 Bitmap 反而浪费。Set 更通用，Bitmap 更极端。

如何估算一个 Set 占多少内存？

intset 约等于「元素数 × 单元素编码长度」加少量头开销；hashtable 要算 dictEntry + 键对象 + 桶数组，通常是元素大小的数倍。精确值用 MEMORY USAGE 看。

Set 的编码演进与阈值

编码条件特点版本
intset元素是整数且数量 ≤ set-max-intset-entries（默认 512）紧凑数组、有序、二分查找，省内存全部
hashtable不满足上述条件dict 实现，O(1) 查找但内存开销大全部
listpack元素是字符串且数量少、元素短（Redis 7.2 引入 set 的 listpack 编码）紧凑连续内存，比 hashtable 省得多7.2+

验证命令

# 查看编码（排障与验证的第一步）
OBJECT ENCODING myset        # intset / hashtable / listpack
DEBUG OBJECT myset           # 更详细（含序列化长度）
MEMORY USAGE myset           # 实际占用字节

# 相关配置项
CONFIG GET set-max-intset-entries      # 默认 512
CONFIG GET set-max-listpack-entries    # 7.2+，默认 128
CONFIG GET set-max-listpack-value      # 7.2+，默认 64（字节）

# 转换是<b>单向</b>的：intset -> hashtable 后不会自动转回来
#   即使删到只剩几个元素也仍是 hashtable
#   -> 长期运行的 set 可能「内存虚胖」，需要重建

# 实验：观察阈值
SADD s 1 2 3;              OBJECT ENCODING s    # intset
CONFIG SET set-max-intset-entries 2
SADD s2 1 2 3;             OBJECT ENCODING s2   # hashtable（超过 2）
  • intset 只存整数：一旦插入一个非整数（如 SADD s abc），整个 set 会立刻转成 hashtable 且不会转回。
  • 升级是不可逆的：这是所有紧凑编码的共同特性，所以「先小后大」的集合会长期占用更高的内存。
  • 内存差距很可观：同样 500 个小整数，intset 通常只有 hashtable 的 1/5 ~ 1/10。
  • 判断依据看 OBJECT ENCODING：不要凭数据量猜，实际编码受配置项和元素类型共同影响。
  • 调大阈值要谨慎：更省内存，但 intset/listpack 是 O(n) 查找，元素多了会让 SISMEMBER 变慢。

为什么我的 set 内存比预期大很多？

八成是编码已经升级成 hashtable（元素含非整数或超过阈值），且删除元素后不会降级。用 OBJECT ENCODING 确认，必要时重建集合。

intset 的 512 阈值能调吗？

能（set-max-intset-entries），但调大意味着 O(n) 查找的集合变大，要在内存和查询延迟之间权衡。

大 set 的并集操作会阻塞吗？

会。SUNION/SINTER 在主线程执行，复杂度与输入规模相关。百万级集合建议用 ...STORE 放到从库或离线处理。
