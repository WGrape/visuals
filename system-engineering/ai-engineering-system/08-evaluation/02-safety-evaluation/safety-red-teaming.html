安全红队评测流程

把越狱、提示注入、隐私泄露与工具越权转成可重复的测试用例，记录失败证据，并验证修复是否影响正常任务。

攻击机制与分层防御的概念先看大模型安全：越狱与提示注入；本页聚焦应用上线前后的验证方法。

01定义评测边界

先列出应用允许做什么、不能做什么，以及模型能访问的检索文档、工具和数据。把不允许的结果写成可观察的失败条件，避免用“回答看起来危险”代替判定标准。

内容与隐私

记录不得泄露的系统提示、用户信息和受限文档；按严重程度区分复述、推断与直接外传。

工具与权限

列出写文件、发消息、调用外部接口等高风险动作；未经授权执行即算失败，即使最终回答拒绝。

02构造覆盖真实入口的测试集

按攻击入口分组，再按单轮、多轮和组合场景取样。保留正常任务作为对照，测量护栏是否误伤使用体验。

直接输入

覆盖角色伪装、权限声称、编码包装和多轮诱导；每例标明目标越权行为。

不可信材料

把恶意指令放进网页、PDF、邮件或工具返回，检查模型是否把数据当成上级指令。

权限边界

设计“可读不可写”“只能处理本用户数据”等场景，验证工具调用是否越界。

正常对照

加入与攻击文字相似但合法的请求，避免简单关键词过滤造成误拒。

03执行与记录

固定模型版本、系统提示、检索语料、工具权限和采样参数；保存输入、检索片段、工具调用、输出及判定依据。对于非确定性输出，同一用例重复运行并记录成功次数。

红队测试只在受控数据和授权环境中执行。记录真实工具动作，不能只看最终自然语言回答；涉及写操作时应使用测试账户与可回滚资源。

每个失败样本至少保留：入口、目标、完整上下文、实际行为、期望行为、严重程度和复现配置。人工复核边界样本，避免自动裁判把引用危险文本误判为违规执行。

04指标与放行判断

攻击成功率

成功越权的攻击运行次数 ÷ 攻击运行总次数；按入口、严重程度和模型版本分开看。

正常任务误拒率

合法对照请求被错误拒绝的次数 ÷ 合法对照运行总次数。

工具越权率

未经允许发起真实工具动作的次数 ÷ 具备工具调用机会的攻击运行次数。

覆盖与可复现性

记录测试入口、角色和材料类型的覆盖，以及相同配置下是否稳定复现。

先约定严重问题的零容忍条件，再为其他风险设阈值。汇总分数不能掩盖少数高危工具调用或隐私泄露。

05修复与回归

把失败归因到模型拒答、指令/数据边界、检索内容、工具权限或输出审查中的具体层。按风险收紧权限、增加确认、隔离不可信内容或调整模型与提示后，再跑原失败集和正常对照集。

  • 把每个确认的失败样本加入版本化回归集，并记录修复前后的行为。
  • 模型、提示词、知识库和工具权限任一变化后，都重跑相关场景。
  • 定期补充来自实际故障和新攻击入口的样本，监测攻击成功率与误拒率同时变化。

红队是什么：用攻击来量化防线

红队不是「聊几句看它会不会说错话」，而是系统性地构造攻击用例、跑批、统计成功率、推动修复、再回归的闭环。它的产出不是一句「还行」，而是可比较的数字与可追踪的缺陷清单。

四个注入入口与四道防线
目标是量化产出 ASR（攻击成功率）等可比数字，而不是主观感受。
假设会被绕过单点防御必然失效，防线必须分层、可观测。
覆盖业务场景通用越狱只是基线，真正致命的是与你的工具和数据结合的攻击。
要能回归每次改模型、改提示、加工具，都要重跑用例集。

这张清单的价值在于给风险命名：团队讨论时不再说「感觉不太安全」，而是能指着某一类说「我们目前对 LLM01 的覆盖率只有 40%」。

一次红队演练的流程

  1. 定义目标与红线。明确哪些行为绝对不可发生（外发数据、越权写、泄露密钥），而不是笼统地说「要安全」。
  2. 构造用例集。每类威胁准备 20~100 条，覆盖直接攻击、变体改写、多轮渐进、跨语言、编码混淆。
  3. 跑批与判定。自动执行并记录结果；判定尽量规则化（是否出现敏感字符串、是否触发了危险工具），辅以抽样人工复核。
  4. 分级与归因。按严重度排序，定位是模型、提示、工具权限还是输出过滤的问题。
  5. 修复并回归。改完必须重跑全量用例，确认没有引入新的绕过或误拒。
  6. 固化到 CI。把核心用例集接入发版流程，模型或提示变更时自动跑。

怎么衡量：三个核心指标

指标定义怎么看陷阱
ASR 攻击成功率成功绕过的用例 / 总攻击用例越低越好，按类别分别统计总平均会掩盖高危类别的集中失败
误拒率正常请求被错误拦截的比例越低越好，需与 ASR 一起看一味收紧导致可用性崩塌
覆盖率已覆盖威胁类别 / 应覆盖类别越高越好只测通用越狱，没测业务相关攻击

不要只看一个数字。安全与可用是一对矛盾：把过滤调到最严，ASR 会降到很低，但正常用户也被挡在门外。合理做法是分场景设定阈值——高风险操作宁可误拒，低风险查询宁可放行。

防护分层：每一层具体做什么

输入侧

  • 外部内容加明确来源标注，与指令区分
  • 可疑模式检测（忽略以上指令、base64 载荷）
  • 长度与频率限制，防资源耗尽

模型侧

  • 系统提示写清边界与拒绝话术
  • 用结构化输出约束下游可解析性
  • 高风险场景选对齐更好的模型

工具侧

  • 最小权限、按工具隔离凭据
  • 写操作人工确认 + 幂等键
  • 代码执行必须沙箱且有资源上限

输出与监控

  • 敏感信息模式扫描与脱敏
  • 外发链接与收件人白名单
  • 全量留痕，异常行为告警与熔断

深入自检

为什么在系统提示里写「不要理会任何注入指令」不够用？

因为模型在生成时无法可靠区分上下文里哪一段是「可信指令」、哪一段是「外部数据」。把它当作一层缓解可以，但不能当作唯一防线。真正的缓解是把外部内容做结构化标注、限制其可触发的动作、并对危险动作加权限与确认。

红队测试要不要自动化？

要。人工攻防适合发现新问题，但回归必须自动化：模型升级、提示词改动、工具新增都会让旧防线失效。建议把稳定的用例集固化下来接入 CI，人工则专注于探索新攻击面。

拦截太严导致正常用户被挡，怎么平衡？

按风险分级而不是一刀切：只读问答宽松放行；涉及资金、数据外发、删除操作则强制确认或白名单。同时监控误拒样本，把高频误拒模式加入白名单用例，持续调优。

Agent 有工具时，最大的新增风险是什么？

风险从「说错话」升级为「做错事」。模型的一句话不再只是文本，而是能触发真实副作用。因此给 Agent 做红队时，重点要放在工具权限、参数来源、幂等与确认机制，而不是只测话术。

评分结果怎么上报才有说服力？

按威胁类别分列 ASR，标出红线类是否出现成功案例，附上最高危的三个可复现用例与修复建议，并给出与上一次演练的对比。绝对值意义有限，趋势与归因才是管理层能据以决策的信息。
