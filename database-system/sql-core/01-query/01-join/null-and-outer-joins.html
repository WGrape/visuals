LEFT JOIN 中 ON、WHERE 与 NULL 的边界

把右表条件放在 ON 或 WHERE，结果可能完全不同。

核心机制

LEFT JOIN 保留左表的每一行。找不到匹配时，右表列被填成 NULL。ON 决定哪些右表行能够匹配；WHERE 在连接结果形成后继续筛选整行。

SQL 的比较有 TRUE、FALSE、UNKNOWN 三种结果。NULL = 1 得到 UNKNOWN；WHERE 只保留 TRUE，所以在 WHERE 中筛右表字段常会删除未匹配的左表行。

用一个例子看过程

SELECT u.id, o.id FROM users u
LEFT JOIN orders o ON o.user_id=u.id AND o.status='paid';
-- 所有用户仍在；没付费订单的用户其 o.id 为 NULL。

形成匹配

ON o.user_id=u.id AND o.status=paid 只选择付费订单参与匹配。

补齐左行

无匹配订单的用户仍输出一行，右表字段为 NULL。

再执行 WHERE

若加 WHERE o.status=paid，上一步补齐的行因 UNKNOWN 被过滤。

观察、原因与处理

观察原因或含义处理与验证
要保留所有用户付费条件写在 ON未匹配者显示 NULL
只要付费用户条件写在 WHERE 或用 INNER JOIN检查多订单造成的重复

把两种写法落到具体数据

假设 users 有 Alice、Bob、Carol 三人；orders 只有 Alice 的 paid 订单和 Bob 的 pending 订单。若把 o.status = 'paid' 写在 ON 中，连接时 Bob 的 pending 订单不算匹配，但 Bob 和 Carol 的左表行仍保留，右表列补 NULL。若把相同条件写在 WHERE 中，Bob 和 Carol 的结果行都会被筛掉，只剩 Alice。语句看起来只是移动了一个条件，结果却从“所有用户及其付费订单”变成“有付费订单的用户”。

当未匹配行的 o.status 为 NULL 时，o.status = 'paid' 的结果是 UNKNOWN，而 WHERE 只保留 TRUE。NULL = NULL 同样不会得到 TRUE；检查缺失值应使用 IS NULL。优化器可以改变物理执行顺序，但不能改变这个语义结果。

反连接和重复行

要找“没有付费订单的用户”，先在 ON 中限定 paid，再用 WHERE o.id IS NULL 查补齐行，其中 o.id 应为右表非空主键。若误用允许 NULL 的列判断，真实匹配行可能被错当成未匹配。另一种写法是 NOT EXISTS 相关子查询，它直接表达“某种订单不存在”。是否更快取决于索引、基数与优化器计划，不能只凭 SQL 形式猜测。

如果 Alice 有两笔 paid 订单，LEFT JOIN 会输出两行 Alice。做用户级报表时要先确认连接基数，再使用聚合、去重或预聚合。把重复误认为优化器故障，会掩盖真实的一对多关系。

练习：把需求分别改写成“展示所有用户”“只展示付费用户”“查找从未付费的用户”，为每条 SQL 选择 ON、WHERE 或 NOT EXISTS，并用上表手算返回行数。

边界与误区

优化器可重排物理执行，但必须保持 SQL 语义。对 NULL 值做等号比较应使用 IS NULL / IS NOT NULL；部分方言还有专用的 NULL 安全比较。

检查真实查询时的顺序

先用极小的手工数据覆盖“有匹配”“只有不满足条件的右表行”“完全无右表行”三种情况，并写出期望结果；再看实际 SQL。之后才使用 EXPLAIN 检查索引和连接算法。性能计划不能替代语义验证：即便优化器把 LEFT JOIN 在特定条件下化简为 INNER JOIN，也必须与原 SQL 在该条件下的结果一致。若报表还需要聚合，先确认右表一对多会生成多少行，再聚合，以免把每个用户的金额重复计数。

COUNT 的另一处陷阱

LEFT JOIN 补出的行在右表列上是 NULL。按用户分组后，COUNT(*) 会把这条补齐行计为 1，而 COUNT(o.id) 只统计非空的右表主键；因此“无订单用户的订单数”应根据需要选后者。若右表真实匹配多行，COUNT(o.id) 会给出多行数量，COUNT(DISTINCT o.id) 才去重。把 ON/WHERE 的条件位置与 COUNT 的对象同时检查，才能防止报表既漏用户又错计数量。

自检

LEFT JOIN 后写 WHERE o.status = paid，为何无订单用户消失？

其 o.status 为 NULL，比较结果 UNKNOWN；WHERE 不保留 UNKNOWN。
