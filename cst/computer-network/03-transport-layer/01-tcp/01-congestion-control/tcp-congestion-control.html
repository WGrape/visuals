📚 TCP拥塞控制算法详解

1️⃣ 慢启动 (Slow Start)

目标：快速探测可用带宽，从无到有指数级增长发送速率。

原理：

  • 初始 cwnd = 1 MSS（最大报文段）
  • 每收到一个 ACK，cwnd 增加 1 MSS
  • 每个 RTT（往返时间），cwnd 翻倍（指数增长）
  • 当 cwnd >= ssthresh 时，进入拥塞避免阶段
  • 遇到丢包（超时），ssthresh = cwnd/2，cwnd = 1，重新慢启动

增长公式：cwnd = cwnd * 2（每个RTT）

2️⃣ 拥塞避免 (Congestion Avoidance)

目标：当接近网络容量时，谨慎地线性增加发送速率。

原理：

  • 当 cwnd >= ssthresh 时进入此阶段
  • 每个 RTT，cwnd 增加 1 MSS（线性增长）
  • 增长速率远慢于慢启动，避免过度拥塞
  • 收到 3 个重复 ACK：ssthresh = cwnd/2，cwnd = ssthresh + 3，进入快速恢复
  • 超时丢包：ssthresh = cwnd/2，cwnd = 1，回到慢启动

增长公式：cwnd = cwnd + 1（每个RTT）

3️⃣ 快速重传 (Fast Retransmit)

目标：在超时之前快速重传丢失的数据包，减少等待时间。

原理：

  • 发送方收到 3 个重复 ACK（表明接收方收到了后续数据包）
  • 立即重传丢失的数据包，无需等待超时定时器
  • 避免不必要的等待，提高传输效率

触发条件：收到 3 个重复 ACK（dupACK = 3）

4️⃣ 快速恢复 (Fast Recovery)

目标：在快速重传后，避免过度降低发送速率，快速恢复传输。

原理：

  • 快速重传后不直接回到慢启动（cwnd = 1）
  • 而是设置 cwnd = ssthresh + 3 MSS（Tahoe版本直接回慢启动）
  • 每个重复 ACK，cwnd 增加 1 MSS（膨胀窗口）
  • 收到新 ACK 后，cwnd = ssthresh，进入拥塞避免
  • Reno 版本：快速恢复后进入拥塞避免
  • Cubic 版本：Linux 现代实现，更复杂的增长曲线

关键：避免"每个丢包都从 cwnd=1 重新开始"的性能损失

📋 事件日志

两个窗口：一个问接收方，一个问网络

TCP 的流量控制与拥塞控制常被混淆。它们是两个独立的约束：流量控制用接收窗口 rwnd，回答「对方缓冲还装得下吗」；拥塞控制用拥塞窗口 cwnd，回答「网络还扛得住吗」。实际发送上限 = min(rwnd, cwnd)。

为什么「丢包」不再是好信号：现代网络设备缓冲区很大，拥塞往往先表现为延迟上升而非丢包，等到丢包时已经排了大量队。BBR 正是要绕开这个滞后信号。

工程实践与调优

① 常见现象与定位

  • 吞吐低于带宽：检查 cwnd 是否上不去（丢包、RTT 大、rwnd 小）。
  • 延迟突然飙升：可能是缓冲膨胀（bufferbloat），队列排满。
  • 长肥管道（高带宽 × 高 RTT）：需要更大的窗口，检查窗口缩放选项。
  • 工具：ss -i 看 cwnd/rtt；Wireshark 看重传与重复 ACK。

② 关键内核参数

  • net.ipv4.tcp_congestion_control：切换算法（cubic / bbr）。
  • tcp_window_scaling：开启窗口缩放（高带宽必需）。
  • tcp_slow_start_after_idle：空闲后是否重回慢启动，长连接可关闭。
  • 初始 cwnd（initcwnd）：影响短连接的首屏速度，可适当调大。

③ 短连接为什么慢

  • 慢启动阶段传输量小，短连接在还没加速完就结束了。
  • 对策：复用连接（Keep-Alive/连接池）、开启 TLS 会话复用、CDN 就近接入。
  • 提高 initcwnd（如 10）能明显改善小文件首字节时间。
  • 减少 RTT 是关键：任何握手与重定向都在增加慢启动的时间成本。

④ QUIC 的做法

  • 拥塞控制逻辑移到用户态，可快速迭代（默认也用 CUBIC/BBR）。
  • 连接迁移：换网络（WiFi→4G）时连接不中断。
  • 0-RTT 握手减少往返，配合拥塞控制更快进入高速阶段。
  • 丢包恢复更精细，避免 TCP 重传歧义问题。

深入自检

流量控制和拥塞控制有什么区别？

流量控制解决「发送方别把接收方冲垮」，通过接收窗口 rwnd 由接收方通告；拥塞控制解决「别把网络冲垮」，通过拥塞窗口 cwnd 由发送方根据网络反馈调整。两者独立生效，实际可发送量取二者较小值。一个典型的混淆是把零窗口（rwnd=0）当成拥塞。

为什么收到 3 个重复 ACK 就重传，而不是等到超时？

因为重复 ACK 说明「接收方收到了后面的包，只是缺了中间这个」——网络仍在正常传输，只是个别包丢失。等到 RTO 超时再重传会造成长时间空窗，吞吐断崖式下降。3 这个数字是权衡：单个重复 ACK 可能是乱序，连续 3 个基本可以判定丢失。

慢启动为什么是指数增长？

因为每收到一个 ACK 就把 cwnd 加 1 个 MSS，而一个 RTT 内会收到约 cwnd 个 ACK，所以每个 RTT cwnd 翻倍。指数增长能快速探明可用带宽，代价是末期可能一下超出网络容量造成丢包，所以要用 ssthresh 及时切换到线性增长。

BBR 一定比 CUBIC 好吗？

不一定。BBR 在高带宽高延迟、有浅缓冲区、有随机丢包的链路上通常更好（吞吐高、延迟低）。但在某些场景（如与 CUBIC 流竞争、低带宽、对公平性敏感的环境）表现可能不稳定。正确做法是实测：在自己的业务流量与网络条件下对比吞吐、P99 延迟与重传率。

什么是缓冲膨胀（bufferbloat）？

网络设备缓冲区过大时，拥塞不会立刻表现为丢包，而是数据包在队列里长时间排队，延迟显著上升。基于丢包的拥塞算法会误以为网络还很好、继续加窗，加剧排队。解决方案包括：主动队列管理（CoDel/PIE）、改用基于延迟的算法（BBR）、以及合理设置设备缓冲。

如何判断线上是不是被拥塞控制拖慢了？

几个信号：① ss -i 显示 cwnd 远小于「带宽×RTT」的理论值；② 存在大量重传或 dup ACK；③ RTT 明显高于基线（排队）；④ 大文件传输初期很慢（慢启动）。进一步可用 iperf 测纯网络吞吐，与业务实测对比，区分是网络问题还是应用层问题。
