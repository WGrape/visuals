理论页讲了 PG 的表锁/行锁/advisory lock 分类。本页给排查工具链：怎么看谁锁了谁、怎么抓死锁、以及 advisory lock 的实战用法。

01观测：pg_locks 联查 pg_stat_activity

pg_locks 只给锁，要结合 pg_stat_activity 才知道是哪个会话、哪条 SQL 在持锁/等锁。

-- 谁在等锁、被谁阻塞（最常用的一句）
SELECT a.pid, a.usename, a.query, a.state,
       l.locktype, l.mode, l.granted,
       b.pid AS blocked_by
FROM pg_locks l
JOIN pg_stat_activity a ON l.pid = a.pid
LEFT JOIN pg_locks bl ON bl.locktype=l.locktype
   AND bl.database IS NOT DISTINCT FROM l.database
   AND bl.relation IS NOT DISTINCT FROM l.relation
   AND bl.page IS NOT DISTINCT FROM l.page
   AND bl.tuple IS NOT DISTINCT FROM l.tuple
   AND bl.virtualxid IS NOT DISTINCT FROM l.virtualxid
   AND bl.transactionid IS NOT DISTINCT FROM l.transactionid
   AND bl.classid IS NOT DISTINCT FROM l.classid
   AND bl.objid IS NOT DISTINCT FROM l.objid
   AND bl.objsubid IS NOT DISTINCT FROM l.objsubid
   AND bl.pid <> l.pid
WHERE bl.granted AND NOT l.granted;
要点：pg_locks 一行是一个锁请求，granted=false 表示在等；上面的自连接专门找出持锁者(granted) 阻塞了 等锁者(not granted) 的关系。

02死锁：log_lock_waits 与 deadlock_timeout

PG 会自动检测死锁并回滚其中一个事务，但最好在日志里留痕，便于事后复盘。

参数默认值建议
deadlock_timeout1s复杂事务可调到 200ms~500ms 更快暴露
log_lock_waitsoff务必设 on，锁等待超过 deadlock_timeout 即记录
lock_timeout0(无限)应用侧设 1s~5s，避免单条语句无限等锁
-- 会话级临时设置（不污染全局）
SET lock_timeout = '3s';
SET deadlock_timeout = '500ms';
-- 全局（postgresql.conf）
log_lock_waits = on
deadlock_timeout = 500ms
# 改完 reload： SELECT pg_reload_conf();
要点：lock_timeout 只作用于锁等待，不作用于语句执行本身；设太小会把正常的短锁等待也报错，应用要有重试。

03advisory lock 实战：跨会话分布式锁

advisory lock 是应用自己定义锁 ID 的轻量锁，PG 不赋予语义，完全由你约定，适合做定时任务单飞、幂等控制。

-- 拿一把会话级咨询锁（ID=12345），拿不到就阻塞
SELECT pg_advisory_lock(12345);
-- 非阻塞版本：拿不到立即返回 false，不阻塞
SELECT pg_try_advisory_lock(12345);
-- 事务级咨询锁：事务提交/回滚时自动释放
SELECT pg_advisory_xact_lock(12345);
-- 释放
SELECT pg_advisory_unlock(12345);
  • 定时任务单飞：任务开始时 pg_try_advisory_lock(job_id)，成功才跑，结束 unlock；多实例部署也不会重复执行
  • 避免用 bigint 的同一段 ID 空间做不同用途，冲突会互相阻塞
  • 会话锁忘了解，会话断开才释放；事务锁随事务结束释放更安全
要点：advisory lock 不写入 WAL、不随备库回放，主备切换后锁信息丢失；需要跨主备的锁请用外部协调（etcd/Redis）。

04排查清单

  • 应用卡住先查 pg_stat_activity 看 state='idle in transaction' 的长事务——它们持锁不放
  • 用上面的阻塞查询定位阻塞链，必要时 pg_terminate_backend(pid) 杀掉持锁会话
  • DDL（ALTER TABLE）拿 ACCESS EXCLUSIVE，会和一切冲突，大表 DDL 用 CONCURRENTLY 或低峰期
  • 热点行更新用 SELECT ... FOR UPDATE SKIP LOCKED 避免互相等待
问：idle in transaction 为什么危险？

它占着事务和锁，却不在干活。连接池泄漏、忘了 commit 都会产生它，是 PG 锁等待的头号来源。
