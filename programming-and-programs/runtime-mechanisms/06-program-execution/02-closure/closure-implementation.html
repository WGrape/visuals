闭包实现：捕获变量、环境对象与生命周期

闭包之所以「记得」外层变量，是因为编译器／运行时把那些变量从调用栈挪到了一个独立的环境对象里。理解这一点，很多诡异行为都能解释。

闭包到底是什么

闭包是函数 + 它引用的外部变量。关键在「引用的外部变量」这部分：普通函数只用参数和自己的局部变量，闭包还用到了定义它的作用域里的变量——这些变量在语法上属于外层函数，按常规规则外层返回后就该销毁。

为了让闭包在外层返回后仍能工作，运行时必须延长这些变量的生命周期。实现方式通常是：把所有被捕获的变量打包成一个环境对象（environment / closure record），分配在堆上，闭包持有对它的引用。

为什么必须挪到堆上

外层返回即销毁

outer 函数有一个局部计数器 count，它返回的函数读取并修改 count。如果 count 严格待在栈帧里，outer 一返回，栈帧被回收，闭包再访问就是未定义行为。

把被捕获的变量装箱

编译器识别出「count 被内层函数捕获」，于是不把它放进栈帧，而是分配一个堆上的小对象存放 count，闭包持有指向该对象的引用。

交给 GC 或引用计数

环境对象的生命周期不再由作用域决定，而是由可达性决定——只要闭包还活着（或还能被调用），它引用的环境就不能回收。

闭包会延长对象寿命

这正是「闭包导致内存泄漏」的机制：闭包持有一个大对象，闭包自己被某个长期存活的结构引用，于是大对象也跟着活下来。

按值捕获还是按引用捕获

不同语言的规定不同，这是闭包最容易被误解的地方：

语言/机制捕获方式后果
C++（显式指定）[=] 值捕获 / [&] 引用捕获必须自己决定。[&] 下返回闭包引用局部变量会悬垂
Java（局部变量）要求 effectively final，按值捕获一份不能修改被捕获的局部变量，规避了悬垂问题
Go按引用捕获变量本身多个闭包共享同一个变量，循环里容易出错
Python按引用捕获（cell 对象）nonlocal 才能写入；循环里的闭包会看到最终值
JavaScriptvar 函数作用域 / let 每次迭代新绑定var 的经典陷阱，let 已修复

核心区别：按值捕获时每个闭包拿到一份快照，互不影响；按引用捕获时所有闭包共享同一个存储单元，一个改了另一个能看到。

循环里创建闭包：最经典的坑

funcs = []
for i in range(3):
    funcs.append(lambda: i)   # 捕获的是 i 这个变量本身

print([f() for f in funcs])   # 输出 [2, 2, 2]，不是 [0, 1, 2]

三个 lambda 捕获的是同一个 i（不是三次迭代的三个副本）。循环结束时 i 停在 2，所以三个闭包都返回 2。

语言现象常见修正
Python全部看到最终值用默认参数绑定：lambda i=i: i；或 functools.partial
Go（旧版本）全部看到最终值在循环体内创建局部变量副本，或把变量作为参数传入
JS（var）全部看到最终值改用 let，它在每次迭代创建新绑定
JS（let）各自看到自己的值无需修正，语言已保证

这个坑的本质不是「闭包难」，而是捕获的是变量还是值没搞清楚。判断方法很简单：问一句「这个标识符指向的存储单元有几个？」

闭包与逃逸分析

上面说的「被捕获就放堆上」是一般规律，但现代编译器会做逃逸分析做优化：如果闭包没有逃出当前函数（不返回、不存到外部结构、不传给其他协程），编译器可以证明环境对象的生命周期不超过栈帧，就能把它留在栈上甚至完全消除。

所以「闭包一定在堆上分配」并不绝对。但这属于编译器优化，语义上仍然等价于堆分配——你可以按堆分配来理解行为，实际性能由编译器决定。

闭包带来的三类问题

问题机制排查与规避
意外的长生命周期（内存泄漏）闭包持有环境对象，环境对象里可能有大对象检查闭包是否被全局变量、缓存、未取消的定时器引用
循环变量共享按引用捕获同一个存储单元显式绑定副本，或用每次迭代新建绑定的语法
悬垂引用（不安全语言）按引用捕获了生命周期更短的栈变量C++ 用 [=] 或 shared_ptr；不要在返回后仍使用 [&] 捕获的局部变量

边界与误区

闭包不是「函数指针」。C 语言的函数指针不携带环境，所以 C 里要模拟闭包必须手动传一个 void* ctx 参数。闭包的价值恰恰在于环境是自动携带的——这也是回调风格（callback hell）在支持闭包的语言里明显更可读的原因。

闭包的实现：捕获的是变量还是值？

闭包的核心问题是捕获的到底是变量本身还是当时的值。不同语言答案不同，这也解释了 Go 循环里开 goroutine、Python 循环里定义 lambda 的经典坑。

语言捕获语义经典坑规避
Go捕获变量（同一个引用）for i:=0;i<3;i++ { go func(){print(i)}() } 全打印 3把变量作为参数传进去，或在循环内重新声明
Python捕获变量（延迟绑定）[lambda: i for i in range(3)] 全返回 2lambda i=i: i（默认参数早绑定）
JavaScript (let)每次迭代新建绑定var 有坑，let 没有用 let 而非 var
Rust显式 move 才转移所有权借用闭包生命周期不匹配需要跨线程时用 move
C++[=] 按值、[&] 按引用，显式[&] 捕获局部变量后跨线程 → 悬垂引用明确列出要捕获的变量
Java只能捕获 effectively final 的局部变量想改外面的变量改不了用数组或 AtomicInteger 包一层
实现机制做法代表代价
环境对象（堆分配）把被捕获的变量装进一个堆上的结构体Go、Python、JS被捕获的变量逃逸到堆，有分配开销
值拷贝闭包创建时把值复制一份C++ [=]无法修改外部变量（要 mutable）
引用捕获 + 生命周期检查借用检查器保证引用有效Rust写起来最啰嗦但最安全
扁平闭包（Flat Closure）直接把捕获的变量塞进闭包对象C#、部分编译器快，但嵌套闭包会变大

各语言写法

# ---------- Python 经典坑：延迟绑定 ----------
funcs = [lambda: i for i in range(3)]
[f() for f in funcs]        # [2, 2, 2]  不是 [0,1,2]！
# 原因：lambda 捕获的是变量 i 本身，循环结束时 i=2

# 修复 1：默认参数（早绑定，最常用）
funcs = [lambda i=i: i for i in range(3)]
[f() for f in funcs]        # [0, 1, 2]

# 修复 2：functools.partial
from functools import partial
funcs = [partial(lambda x: x, i) for i in range(3)]

# 修改外部变量：nonlocal（Python 3）
def counter():
    n = 0
    def inc():
        nonlocal n        # 声明：n 是外层函数的变量，不是新建局部
        n += 1
        return n
    return inc

# ---------- Go 经典坑：循环变量捕获 ----------
for i := 0; i < 3; i++ {
    go func() { fmt.Println(i) }()    // Go 1.22 前：全打印 3
}
// 修复 1：作为参数传入（最清晰）
for i := 0; i < 3; i++ {
    go func(i int) { fmt.Println(i) }(i)
}
// 修复 2：循环内重新声明
for i := 0; i < 3; i++ {
    i := i
    go func() { fmt.Println(i) }()
}
// Go 1.22+ 已修复：每次迭代的循环变量是新的变量

# ---------- Rust：move 闭包 ----------
let v = vec![1, 2, 3];
std::thread::spawn(move || {        // move：转移所有权到闭包
    println!("{:?}", v);            // 否则借用的 v 活不过线程
});
  • 被捕获的变量会逃逸到堆：这是闭包的隐含成本。Go 里原本在栈上的局部变量一旦被闭包捕获，编译器会把它分配到堆上（逃逸分析），增加 GC 压力。
  • 循环里创建闭包是高发坑区：Go、Python、JS(var) 都有这个陷阱。规则很简单——闭包捕获的是变量，不是值，除非语言明确做了每次迭代新建绑定（JS let、Go 1.22+）。
  • Python 的 nonlocal vs global：nonlocal 改外层函数变量，global 改模块级变量。不加声明直接赋值会被当成新建局部变量，读的时候还会报 UnboundLocalError。
  • 闭包会让对象生命周期变长：捕获了大对象的闭包如果长期存活（如注册为回调），那个大对象就不会被回收——这是内存泄漏的常见来源。
  • Rust 的 move 是最明确的：跨线程必须用 move 转移所有权，否则借用检查器会拒绝（因为闭包可能比被借用的变量活得久）。
  • 闭包 ≠ 匿名函数：匿名函数只是没有名字的函数；闭包是函数 + 捕获的环境。C 语言里没有闭包（函数指针不带环境），所以回调都要额外传一个 void* userdata——那其实就是手动实现的「环境对象」。
为什么 Go 循环里开 goroutine 会打印同一个值？

因为 Go 1.22 之前，循环变量在整个循环中是同一个变量，闭包捕获的是这个变量的引用而不是每次迭代的值。所以三个 goroutine 都指向同一个 i，等到它们真正被调度执行时，主协程的循环早就跑完了，i 已经是 3，于是三个都打印 3。这个坑非常普遍，以至于 Go 1.22 专门改了语义——每次迭代创建新的循环变量，从语言层面修掉了这个陷阱。在 1.22 之前的标准解法有三个：① 把 i 作为参数传给闭包（go func(i int){...}(i)）——最清晰，推荐；② 循环内重新声明（i := i）——创建一个新变量；③ 用函数包装。注意这个坑在 Go 1.22 之后依然存在的情况：如果你显式在循环外声明变量然后在循环里改它，捕获的仍是同一个变量。

闭包的性能开销有多大？

分两块：① 捕获导致的堆分配——被捕获的变量必须从栈逃逸到堆（Go 的逃逸分析会做这件事），一次堆分配 + 后续 GC 压力。如果闭包在热路径（如循环里）被频繁创建，这个开销会累积。优化方法：把不变的值作为参数传入而不是捕获，或者把闭包提到循环外只创建一次；② 间接调用开销——通过闭包调用通常无法内联（编译器不知道闭包里是哪个函数），这会让每次调用多一次间接跳转，还可能阻碍其他优化。在极热的路径上（如排序的比较函数每元素调用一次）这会很明显。实践建议：绝大多数场景不用在意（一次堆分配几十纳秒），只有在 benchmark 显示闭包分配进入 top 分配源时才优化。Go 里可以用 go build -gcflags=-m 看逃逸分析，用 pprof 的 alloc_space 看闭包分配。

Python 里闭包改不了外部变量怎么办？

用 nonlocal 声明。Python 的规则是：在函数内对一个变量赋值，就会把它当成该函数的新局部变量——所以如果你在闭包里写 n += 1 而没有声明，Python 会认为 n 是闭包自己的局部变量，然后在读取时发现它还没赋值，抛出 UnboundLocalError（注意：如果只是读不写，不需要声明，闭包能直接读到外层的变量）。nonlocal n 的作用就是告诉解释器「这个 n 是外层函数作用域的那个，别新建」。三个要区分的关键字：global（模块级变量）、nonlocal（外层函数变量）、都不加（自己的局部变量）。如果不想用 nonlocal，常见的替代方案是用一个可变容器——比如 counter = [0]，然后在闭包里改 counter[0] += 1（因为你没有给 counter 赋值，只是修改了它指向的对象，所以不需要声明）。这个技巧在 Python 2 时代（没有 nonlocal）非常普遍。

自检

为什么 Java 要求被捕获的局部变量是 final 或 effectively final？

Java 对局部变量采用按值捕获，闭包拿到的是副本。如果允许修改，就会出现「改了副本但外层看不见」这种极易混淆的语义。禁止修改让「捕获」这件事在语义上保持简单一致。
