1CDN 是什么，解决什么问题

CDN（Content Delivery Network，内容分发网络）= 把内容缓存在离用户更近的边缘节点上，让用户就近获取，而不是每次都跨地域打到源站。

🌍 降低延迟

用户从「本地边缘节点」拿数据，省去跨城/跨国长途，RTT 从几百 ms 降到十几 ms。

🛡️ 减轻源站压力

大部分请求被边缘节点命中，源站只需服务「未命中回源」的少量流量，扛得住突发峰值。

📈 提升可用与扩展

节点多、天然冗余；单点故障可被调度层绕开，整体可用性远高于单源站。

本质一句话：把「计算/存储离数据近」反转为「把数据副本放到离用户近」——用空间（多副本）换时间（延迟）和抗压能力。

2核心原理：调度 + 缓存 + 回源

CDN 三大支柱：调度（把用户导向最近的节点）、缓存（节点存内容）、回源（没有就找源站要）。

2.1 调度：怎么让用户「就近」？

DNS 调度（最常用）

用户访问 cdn.example.com，该域名 CNAME 到 CDN 厂商的调度域名；CDN 的权威 DNS 根据用户本地 DNS 的 IP 归属（地域/运营商）返回最近边缘节点的 IP。配置简单，但精度受「本地 DNS」位置影响。

HTTPDNS / 302 调度

APP 内置 HTTPDNS SDK 直接拿「用户真实 IP」向调度服务请求节点 IP，避免本地 DNS 偏差；或用 302 重定向把请求导到具体节点。精度高，需客户端配合。

Anycast（BGP 任播）

多个节点用同一个 IP 公告，由骨干网路由把用户包送到「网络最近」的节点。无需 DNS 解析差异，就近性极佳，但需自有 AS 与 BGP 能力（大厂/自建常用）。

IP 调度 / 边缘计算

在更靠近用户的 PoP 做 L7 路由与改写，结合实时负载做节点间二次分发，适合动态加速。

2.2 缓存与回源

命中 vs 回源：缓存命中率 = 命中数 / 总请求数。命中率越高，源站压力越小、成本越低。缓存未命中时，边缘节点才向上（父层或直接源站）回源取数据并缓存，供后续请求复用。

4必须掌握的关键概念

边缘节点 / PoP

部署在运营商骨干、离用户近的缓存服务器，是真正对外服务的节点。

源站 Origin

内容的「真相源」（你的对象存储 / 服务器）。CDN 只缓存副本。

缓存 TTL

资源在边缘的存活时间。到期或主动刷新后失效，下次回源。静态资源可设长（天级），动态资源短或不过期。

缓存命中率

核心 KPI。命中走边缘，回源走源站；命中率每升 1% 都直接省钱省压。

缓存刷新 / 预热

刷新：主动让边缘旧内容失效（URL/目录刷新）；预热：提前把内容推到边缘，避免首波用户回源「冷启动」。

回源 / 回源比

未命中请求打到源站的比例。回源比过高说明缓存策略有问题，源站会被打爆。

5方式一：接入云厂商 CDN（最省事）

适合绝大多数业务：不用运维节点，几步配置即可。以阿里云/腾讯云/CDN 通用流程为例。

配置要点

  • 源站：填你的服务器 IP、域名或对象存储（OSS/COS/S3）。建议源站仅对 CDN 回源 IP 开放（隐藏源站，见安全篇）。
  • 缓存规则：按文件后缀设 TTL——.jpg/.css/.js 长缓存（30d），.html 短缓存或不过期，带版本号 hash 的资源可永久缓存。
  • CNAME：把加速域名 CNAME 到厂商给的调度域名，DNS 解析即生效。
  • HTTPS：上传证书或在厂商申请免费证书，开启全链路 HTTPS（用户→CDN、CDN→源站可分别配置）。
  • 刷新/预热：发版后刷新对应 URL 或目录；大促前预热热点资源。

6方式二：自建 CDN（原理级实现）

当你有多地域服务器、想完全掌控或做特殊加速时，可用 Nginx 做边缘缓存 + 智能调度（DNS/Anycast） 拼出一个轻量 CDN。

6.1 边缘节点：Nginx 反向代理 + 缓存

每个边缘节点就是一个开了 proxy_cache 的 Nginx，把回源结果缓存下来，后续请求直接命中本地。

# nginx.conf —— 边缘节点缓存配置
proxy_cache_path /data/cdn_cache levels=1:2 keys_zone=edge_cache:200m
                 max_size=20g inactive=7d use_temp_path=off;

server {
    listen 80;
    server_name cdn.example.com;

    location / {
        proxy_pass http://origin_backend;   # 回源地址
        proxy_cache edge_cache;
        proxy_cache_key $scheme$host$request_uri;  # 缓存键
        proxy_cache_valid 200 302 7d;        # 200/302 缓存7天
        proxy_cache_valid 404 1m;
        proxy_cache_lock on;                # 回源合并，防雪崩
        proxy_cache_use_stale error timeout updating; # 源站挂时用旧内容

        add_header X-Cache-Status $upstream_cache_status; # HIT/MISS 便于观测
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

upstream origin_backend {
    server origin.example.com:80;   # 源站
    keepalive 32;
}
$upstream_cache_status：HIT 命中、MISS 回源、BYPASS 跳过、EXPIRED 过期、UPDATING 更新中、STALE 用旧值。拿它算命中率是标配。

6.2 调度层：让用户就近落到节点

方案 A：智能 DNS（geoip）

用 bind + geoip 或云解析，按用户本地 DNS 的 IP 地域返回不同边缘节点 IP。配置简单、零客户端改动，但精度受本地 DNS 位置影响。

# 伪配置：华北回北京节点，华南回广州节点
view "north" {
  match-clients { geoip:cn-north; };
  zone "cdn.example.com" {
    A 1.2.3.4;   # 北京节点
  };
}

方案 B：Anycast（BGP 任播）

各地节点用相同 IP 向运营商公告路由，骨干网自动把用户流量送到网络最近节点。就近最准，但需要自有 AS、IP 段与 BGP 运维能力——通常是大厂/专业 CDN 的选择。

6.3 节点间内容同步（可选）

简单架构下节点各自独立回源即可（命中率略低但实现简单）。若想「一处回源、多节点共享」可做父层/中间层：边缘 → 区域父节点 → 源站，父层缓存被多边缘复用，进一步降回源。也可用 rsync / 对象存储主动分发静态资源到各节点。

自建的代价：你要自己运维节点、监控、证书、调度、容量与故障切换，且单节点带宽/覆盖远不及商业 CDN。除非有多地域闲置服务器或强管控需求，否则首选云 CDN；自建更适合做「原理学习」或「特定链路加速」。

7自建 vs 云 CDN：怎么选

维度云厂商 CDN自建 CDN
接入成本低（控制台/API）高（搭节点+调度）
节点覆盖全球几百~上千 PoP仅你有的地域
运维负担厂商负责全部自己扛
可控性中（受限于产品）完全可控
成本模型按流量/带宽付费服务器+带宽固定投入
适用绝大多数业务、出海、突发峰值原理学习、特殊加速、强管控
一句话：生产业务直接上云 CDN（省心、覆盖广）；想深入理解 CDN 或做定制化加速，用 Nginx + 智能 DNS 自建一套做实验——原理完全一致。
