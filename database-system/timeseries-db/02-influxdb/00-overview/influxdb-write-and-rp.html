InfluxDB 写入与保留策略实战

Line Protocol 格式、批量写入、保留策略与连续查询的取舍

InfluxDB时序数据库TSDBLine Protocol
Line Protocol 批量写入 保留策略 连续查询
时序数据靠 Line Protocol 写入，保留策略(RP)自动清理过期数据，连续查询(CQ)做降采样。高基数 tag 是 InfluxDB 性能第一杀手。

01Line Protocol 格式

# measurement,tag=值 field=值 时间戳(可选，不写用服务端时间)
cpu,host=web01,region=cn usage=0.82 1700000000
mem,host=web01 used=1234567890i
要点：tag 会被索引（用于过滤/分组），field 不索引（用于聚合）。把高基数字段（如 user_id）放 field，否则索引爆炸。

02批量写入

# 1.x：多行拼接一次 POST，建议每批数千点
curl -i -XPOST 'http://localhost:8086/write?db=mydb&precision=s' \
  --data-binary 'cpu,host=web01 usage=0.1 100
cpu,host=web02 usage=0.2 101'
# 2.x：org + bucket 模型
curl -i -XPOST 'http://localhost:8086/api/v2/write?org=myorg&bucket=mybucket&precision=s' \
  -H 'Authorization: Token xxx' --data-binary 'cpu,host=web01 usage=0.1 100'
要点：时间戳精度参数 precision=s/m/h/ms/u/n；批太小有协议开销，批太大易超时，数千点/批是常见甜点。

03保留策略(RP)

# 1.x：建一个 30 天自动过期的 RP 并设为默认
CREATE RETENTION POLICY "rp_30d" ON "mydb" DURATION 30d REPLICATION 1 DEFAULT
# 2.x：在 bucket 创建时指定 retention（控制台或 API），无 RP 概念
要点：RP 到点自动删数据，不用手写定时任务。1.x 若不显式建 RP，默认是永久保留。

04连续查询(CQ)降采样

CREATE CONTINUOUS QUERY "cq_cpu_1m" ON "mydb"
BEGIN
  SELECT mean("usage") INTO "cpu_1m" FROM "cpu" GROUP BY time(1m),*
END
要点：CQ 把原始高频点聚合成低频点，查询历史时读聚合表更快、更省。高基数 group by 会让 CQ 本身变重，慎用。

05常见疑问

问：1.x 和 2.x 最大区别？

2.x 引入 org/bucket 与新的写 API、认证模型；1.x 用 db + RP。迁移需改写入端与权限。

问：写入报 500 但数据偶发丢失？

检查批大小、时间戳精度与是否有高基数 tag；高基数会让内存与索引压力陡增。

第一层 · 概念与判定

InfluxDB 写入基于 Line Protocol（measurement,tag,field timestamp）；保留策略 RP 决定数据存活时长与分片（shard group）粒度。

  • RP 三要素：DURATION（保留多久）、REPLICATION（副本，集群才有意义）、SHARD DURATION（分片时间跨度）。
  • 无 RP 时默认永久保留，数据无限膨胀。
  • 判定：写入慢/数据不删 → 先看 RP 与 batch 设置。

第二层 · 参数·命令·量化

创建 RP 与写入：

示例

-- 建保留策略：保留 30 天，按 7 天分片
CREATE RETENTION POLICY "rp_30d" ON "mydb"
DURATION 30d REPLICATION 1 SHARD DURATION 7d DEFAULT;

-- 带 RP 的批量写入（HTTP）
curl -i -XPOST 'http://localhost:8086/write?db=mydb&rp=rp_30d' \
  --data-binary 'cpu,host=a usage=23.1 1700000000'

写入建议：批量（每批数千点）、并发受 max-series-per-database 与 max-values-per-tag 约束。

第三层 · 排障与边界

  • 写入超时/积压：单批过大或 cardinality 过高；减小 batch、避免高基 tag（如把时间戳当 tag）。
  • RP 误删数据：DURATION 设太短，旧数据被后台 compaction 清掉；确认业务留存需求。
  • shard 过多：SHARD DURATION 太小导致海量 shard，元数据与查询变慢；通常 1d~7d。
  • cardinality 爆炸：tag 组合爆炸拖垮写入与内存；用 SHOW CARDINALITY 监控。

第四层 · 原理与取舍

RP 用 shard group 把时间相邻的数据聚到同一分片，过期时整 shard 直接丢弃（而非行级删除），删除成本极低。DURATION 与 SHARD DURATION 的解耦让「保留久但分片小」成为可能。

为什么不能靠 DELETE 删旧数据？

时序数据量极大，行级删除代价高；RP 以分片为单位整体过期，近乎零成本。

SHARD DURATION 怎么选？

查询热窗口通常几天，分片取 1d~7d 能在过期效率与分片数量间平衡，别设成 1h。
