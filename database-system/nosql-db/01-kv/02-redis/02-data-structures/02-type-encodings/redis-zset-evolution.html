Redis Zset 数据结构演进史

跳表 + 字典的完美组合

Redis 2.0

Zset 诞生 + ziplist

2010 年，Zset（有序集合）诞生。底层使用 ziplist 实现， member 和 score 成对存储，按 score 有序排列。

// ziplist 存储结构
|...|score1|member1|score2|member2|...|

• 按 score 升序排列
• member + score 连续存储
• 二分查找定位
紧凑内存 O(log n) 范围查询 小数据友好
Redis 2.4

阈值机制确立

确立 ziplist 的使用条件。当元素数量不超过 zset-max-ziplist-entries 且每个元素长度不超过 zset-max-ziplist-value 时使用 ziplist。

// ziplist 限制条件
✓ 元素数 ≤ 128
✓ member 长度 ≤ 64 bytes

任意一条不满足 → 转换为 skiplist + dict
自动编码转换 128 元素阈值
Redis 2.8

ZRANGEBYSCORE 优化

优化 ZRANGEBYSCORE 等范围查询命令的性能。 ziplist 的二分查找机制确保 O(log n) 的范围定位。

// 范围查询复杂度
ziplist:
  定位: O(log n)
  返回连续元素: O(m) [m=返回数量]

skiplist:
  定位: O(log n)
  返回连续元素: O(log n + m)
范围查询优化 ZSET 命令完善
Redis 3.0 ⭐ 核心变革

skiplist + dict 组合

革命性突破！引入 skiplist（跳表）和 dict（字典）组合作为 Zset 的高性能底层实现。 skiplist 保证有序，dict 保证 O(1) 单点查询。

skiplist 跳表

• 节点按 score 有序
• 多层链表加速查找
• O(log n) 范围查询
• O(log n) 插入/删除

dict 字典

• member → score 映射
• O(1) ZSCORE 查询
• O(1) ZREM 删除
• 哈希表实现
// zset 结构 (Redis 3.0+)
dict *dict member→score
skiplist *zsl score→member
关键: 指向同一个 zskiplistNode
双索引结构 O(1) 单点查询 O(log n) 范围
Redis 4.0

参数调整与优化

调整 zset-max-ziplist-entries 从 128 → 128（保持）， 优化跳表的随机层数生成算法，保持结构稳定。

// Redis 4.0 配置
zset-max-ziplist-entries 128
zset-max-ziplist-value 64 bytes
跳表优化 渐进式 rehash
Redis 6.2

阈值大幅提升

将 zset-max-ziplist-entries 从 128 → 128， 但优化了内部实现，提升 ZRANK/ZREVRANK 等排名查询的性能。

// ZRANK vs ZSCORE
ZRANK:
  跳表中定位 → O(log n)
  返回成员排名

ZSCORE:
  字典中查找 → O(1)！
  返回分数
O(log n) 排名查询 O(1) 分值查询
Redis 7.0+ ⭐ 底层升级

listpack 替换 ziplist

Redis 7.0 将 Zset 的 ziplist 替换为 listpack。 skiplist + dict 组合保持不变，只是 ziplist 部分升级为 listpack。

// Redis 7.0 Zset 编码
小数据: listpack
  • 无级联更新
  • 内存更紧凑

大数据: skiplist + dict
  • O(log n) 范围查询
  • O(1) 单点查询
listpack 编码 无级联更新 向后兼容

演进总结

Redis Zset 的演进是"鱼与熊掌兼得"的典范：

按序存储（范围查询）+ O(1) 查询（单点定位）= skiplist + dict

核心设计哲学：
空间换时间 — 两份索引，但都是指针
自动切换 — 小数据用 listpack 省内存
各司其职 — skiplist 管有序，dict 管去重+快速查询

这就是为什么 Zset 能同时支持"排行榜"（ZRANGE）和"实时分数"（ZSCORE）两种高频场景。

ZSet 的两种编码与阈值

编码底层触发条件复杂度特点
listpack紧凑连续内存（member 与 score 相邻存放，按 score 排序）元素数 ≤ zset-max-listpack-entries（128）且 member 长度 ≤ zset-max-listpack-value（64 字节）插入 O(n)极省内存，小集合首选
skiplist + dict跳表（按 score 有序）+ 哈希表（member → score，O(1) 查分）任一条件超出插入/删除/按分查 O(log n)；按 member 查 O(1)功能完整，内存开销大

为什么要同时用跳表和哈希表：跳表负责“按 score 范围/排名查询”（ZRANGEBYSCORE、ZRANK O(log n)）；哈希表负责“按 member 查分数”（ZSCORE O(1)）。两者指向同一份 member/score 数据（共享指针），所以内存只多了一份索引结构，不是两份数据。

跳表参数值含义
最大层数32（ZSKIPLIST_MAXLEVEL）最多 32 层索引
晋升概率 p0.25（1/4）每层节点数是下层的 1/4，比 1/2 更省内存
平均层数约 1.33p=0.25 时每个节点平均只有 1.33 层
百万元素查找约 20 次比较log₄(10⁶) ≈ 10，加上每层少量比较

ZSet 编码与命令

# 阈值配置
CONFIG GET zset-max-listpack-entries     # 128
CONFIG GET zset-max-listpack-value       # 64

# 观察编码转换
ZADD z1 1 a 2 b
OBJECT ENCODING z1          # "listpack"
# 加到 129 个元素
redis-cli EVAL "for i=1,129 do redis.call('ZADD', KEYS[1], i, 'm'..i) end return 1" 1 z1
OBJECT ENCODING z1          # "skiplist"
# 关键：转换不可逆，删回少量元素也不变回 listpack

# 常见命令复杂度
# ZADD / ZREM / ZSCORE / ZRANK     : O(log n)（ZSCORE 走 dict 是 O(1)）
# ZRANGE / ZREVRANGE               : O(log n + m)，m 为返回元素数
# ZRANGEBYSCORE                     : O(log n + m)
# ZRANGEBYLEX                       : O(log n + m)
# ZCARD                             : O(1)
# ZCOUNT / ZLEXCOUNT                : O(log n)

# 排行榜典型用法
ZADD leaderboard 100 "player1"
ZINCRBY leaderboard 50 "player1"
ZREVRANGE leaderboard 0 9 WITHSCORES        # Top 10
ZREVRANK leaderboard "player1"              # 我的排名（从 0 开始）
ZSCORE leaderboard "player1"

典型场景与坑

场景做法说明
排行榜ZADD + ZREVRANGE + ZREVRANK同分按 member 字典序排
延迟队列score = 执行时间戳，ZRANGEBYSCORE 0 now 捞到期任务比 List 灵活（可任意时间点）
优先级队列score = 优先级配合 ZPOPMIN（Redis 5+）
时间线/滑动窗口统计score = 时间戳，ZREMRANGEBYSCORE 清理旧数据如“最近 1 小时的访问记录”
分页 + 排序ZRANGE ... WITHSCORES注意大 offset 的开销 O(log n + m)
  • 编码转换不可逆：同 Hash。一旦超过 128 个元素或 member 超过 64 字节就永久变 skiplist。做延迟队列时元素数必然超阈值，所以编码必然是 skiplist——不要指望 listpack 省内存。
  • ZRANGEBYSCORE 的 LIMIT offset 陷阱：大 offset（如跳过 10 万条）需要先遍历 10 万个节点，虽是 O(log n + m) 但 m 很大时依然慢。深分页要用游标（记上次的 score）而不是 offset。
  • score 是双精度浮点数：只有 53 位精度。超过 2^53（约 9×10^15）的整数会丢失精度，时间戳用毫秒没问题（1.7×10^12），但微秒/纳秒要注意。同分时按 member 的字典序排。
  • 大 ZSet 的删除：几百万成员的 ZSet 用 DEL 会阻塞。用 UNLINK 或 ZREMRANGEBYRANK 分批删。
  • 内存优化：member 尽量短（短 member 才能用 listpack）；不需要精确排名时可用 Hash 代替；超大排行榜要拆分（如按时间段分片）。
  • 排障：OBJECT ENCODING → ZCARD 看元素数 → MEMORY USAGE → 慢查询日志看是否有大 offset 的 ZRANGE。
为什么 ZSet 不用红黑树而用跳表？

跳表实现简单（不用处理复杂的再平衡）、支持高效的范围查询（找到起点后沿底层链表顺序扫即可，红黑树要中序遍历）、且可以通过调 p 在内存与性能间权衡。Redis 作者明确说明跳表“更简单且性能足够”。

ZSet 和 Set 该怎么选？

需要排序、按分数范围查、取 TopN → ZSet；只需要去重与存在性判断 → Set（更省内存，Set 也有 intset/listpack 编码的紧凑优化）。
