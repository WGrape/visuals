TiDB Region：分裂、热点与 PD 调度

沿一次热点写入理解 TiKV Region、Raft Leader 与 PD 放置策略分别负责什么。

Region 是什么边界

TiKV 把有序键空间划分为多个 Region，每个 Region 覆盖一段 key range，并由一组副本通过 Raft 维护一致性。TiDB SQL 层将表行和索引编码成键，查询或写入最终落到相应 Region。PD 保存并调度 Region 的分布信息，帮助节点找到路由和负载均衡方向。Region 不是一张表，也不是一个固定数据库分片；同一张表可能分布在许多 Region，Region 的边界还会随数据增长而变化。

分裂解决“一个 Region 过大或需要细分调度单元”的问题。分裂后会出现两个 key range，路由信息与副本状态需要更新。PD 可以据资源和放置约束安排副本或 Leader 的位置。分裂本身不等于负载马上均匀：如果所有新写入都持续落在最新的键尾部，热点仍可能跟着移动。

逐步推演

编码与路由

表行和索引写入编码键，TiDB 定位目标 Region。

Raft 写入

目标 Region 的 Leader 协调副本复制与持久化。

分裂与调度

Region 增长或负载变化时细分范围，并由 PD 考虑放置与均衡。

验证热点

关联 key range、Leader 负载和业务键分布，选择对应改动。

一个递增主键热点案例

订单表使用严格递增的键，新订单不断写入键空间末尾。同一时刻，大量请求容易打到少数尾部 Region 的 Leader，表现为写入排队、延迟上升和少数 TiKV 节点 CPU/网络偏高。Region 分裂后，旧数据分散了，但新订单仍向新的末尾 Region 聚集。单纯“增加节点”未必立即消除这个有序写入热点。

现象先看什么可能的处理
少数 Leader 很忙热点 Region 与写键分布调整键设计或写入散布
副本分布不均PD 调度状态和放置规则检查调度约束与节点容量
事务冲突高相同业务键竞争优化事务粒度或业务模型
全体节点都忙总吞吐、磁盘和网络容量规划而非只搬 Leader

分裂、迁移和副本不是一回事

分裂改变 key range 的粒度；副本调度改变一个 Region 的副本放在哪些 TiKV 节点；Leader 调度改变哪个副本处理主要读写协调。它们可能连续发生，却对应不同目标。若热点来自一个高频更新的单个键，即便把 Region 拆得更小，也不能把同一键的一次写拆给多个 Leader 同时处理。应先确定负载集中在连续范围、单个键、索引还是某种事务冲突上，再选策略。

为了散布写入，可以考虑更合适的键编码或业务分桶，但随机化也可能降低范围扫描局部性并增加查询复杂度。对 HTAP 负载还要区分 TiKV 的行存事务查询和 TiFlash 的分析副本，不能用分析查询的节点 CPU 推断订单写热点。任何键设计改动都应与实际查询、索引和事务路径一起评估。

排查顺序与演练

  1. 观察写入延迟分位数、热点 Region、Leader 分布、Region split/merge 与 PD 调度事件。
  2. 把热点 key range 映射回表或索引，确认是递增键、集中更新还是索引尾部写。
  3. 检查副本约束、机房位置和节点资源，避免为了均衡打破容灾规则。
  4. 在代表性流量上验证键设计或调度改动，并观察范围查询和事务冲突是否退化。

练习：新增三台 TiKV 节点后，写入 P99 仍高，监控显示只有一个尾部 Region Leader 忙。说明为什么容量增加未直接解决问题，并列出一项数据模型实验与一项运行时证据。

热点定位要同时看写键和读计划

Region Leader 高负载可能来自递增写入，也可能是少数热门行反复更新、某个二级索引集中写入或范围扫描压在同一数据段。把 SQL 慢日志、热点 Region 的 key range 和表索引映射起来，才能知道该改主键、索引还是查询。若只是把 Leader 迁移到新节点，而写键分布仍集中，热点会跟着迁移。若一个业务键本身争用严重，增加 Region 数量也无效。

分裂和副本搬迁期间还可能短暂增加调度与网络成本。不要把 PD 正在收敛时的几分钟指标当成稳态性能，也不要在容量不足时同时触发大量迁移。验证方案应在代表性写入量下持续观察 Region 分布、热点持续时间和事务冲突率，并检查范围查询是否因键散布而变慢。

Region 数不是越多越好：Region 过多会让心跳与 PD 内存压力上升，经验上单 TiKV 实例承载的 Region 数维持在数万量级，超过后调度开销会明显变大。

定位热点与查看分布的命令

诊断

-- 1) 看某张表的 Region 分布与读写流量
SHOW TABLE t REGIONS;
SELECT * FROM information_schema.TIKV_REGION_STATUS
 WHERE table_name='t' ORDER BY written_bytes DESC LIMIT 10;

-- 2) 把 Region 的 start/end key 解码成可读的表/行信息
SELECT tidb_decode_key('<start_key_hex>');

-- 3) 看 PD 视角的热点（读/写分开看）
tiup ctl:<ver> pd -u http://pd:2379 region
tiup ctl:<ver> pd -u http://pd:2379 hot write
tiup ctl:<ver> pd -u http://pd:2379 hot read
tiup ctl:<ver> pd -u http://pd:2379 operator show

-- 4) 看调度器配置与限流
tiup ctl:<ver> pd -u http://pd:2379 scheduler show
tiup ctl:<ver> pd -u http://pd:2379 config show scheduler

进一步定位

# 5) 单节点维度：Region 数量、大小、副本健康
tiup ctl:<ver> pd -u http://pd:2379 store
tiup ctl:<ver> pd -u http://pd:2379 region --jq='.regions | length'

# 6) 集群健康与慢查询（判断是否读热点来自执行计划）
SELECT * FROM information_schema.CLUSTER_SLOW_QUERY
 WHERE time > NOW() - INTERVAL 10 MINUTE ORDER BY duration DESC LIMIT 10;

打散热点的三种手段与取舍

手段写法生效时机代价 / 限制
预分裂 RegionSPLIT TABLE t BETWEEN (0) AND (100000) REGIONS 16;立即只分散初始分布，写仍在尾部时热点会跟着走
打散行 IDSHARD_ROW_ID_BITS=4（→16 分片）建表/改表时分片过多会放大 Range 扫描代价；常用 4~5
随机主键AUTO_RANDOM(5) 代替 AUTO_INCREMENT建表时主键不再单调，范围扫描与业务排序受影响
索引打散对热点二级索引同样考虑前缀打散建表时索引键的单调性决定索引 Region 是否热点

建表示例

-- 建表时就规避自增主键写热点
CREATE TABLE orders (
  id BIGINT PRIMARY KEY /*T![auto_rand] AUTO_RANDOM(5) */,
  user_id BIGINT NOT NULL,
  created_at DATETIME NOT NULL,
  KEY idx_user (user_id)
) SHARD_ROW_ID_BITS = 4 PRE_SPLIT_REGIONS = 4;
  • 写热点（尾部追加）：优先 AUTO_RANDOM / SHARD_ROW_ID_BITS，调度只能迁移，不能消除。
  • 读热点（小表高频）：靠 leader-schedule-limit 迁移 Leader + 加 Follower Read（tidb_replica_read='follower'）。
  • 分裂不等于均衡：分裂只是把键区间切开，若写入键持续单调，新 Region 会继续成为热点。

深入自检

Region 分裂后写热点一定会消失吗？

不一定。分裂只改变键区间边界。若写入键持续单调增长（自增主键、时间前缀），热点会随着“最新的那个 Region”移动，症状从“一个 Region 热”变成“热 Region 在漂移”。根治要打散键本身。

分裂、迁移、副本补充三者有什么区别？

分裂是键区间切分（一个 Region 变两个）；迁移是 PD 把 Region 的副本或 Leader 挪到别的 TiKV（负载均衡）；副本补充是副本数不足时按 placement 规则新增副本。三者由不同调度器负责，限流参数也不同。

什么情况下该调大 Region 目标大小？

Region 数量已成为 PD 与心跳瓶颈（单实例数万 Region）、或批量导入频繁触发分裂抖动时，可把 96 MiB 调到 128~256 MiB。代价是单个 Region 变大，迁移与分裂的粒度变粗，负载均衡的精细度下降。

SHARD_ROW_ID_BITS 设多大合适？

常用 4（16 个分片）到 5（32 个分片）。它把 _tidb_rowid 的高位打散，使写入分布到多个 Region。值越大写越分散，但按主键范围的扫描会跨更多 Region，需要按读写比例权衡。

如何区分是写热点还是读热点？

看 PD 的 hot write 与 hot read：写热点集中在少数 Region 的 written_bytes；读热点表现为 read_bytes/read_keys 高且常伴随慢查询里的固定小表或固定索引。前者改键设计，后者改执行计划或加 Follower Read。

自检

Region 分裂能否自动解决单个热点键的写竞争？

不能。同一键仍属于一个 Region，业务上的竞争与 Leader 路径仍存在。

PD 调度副本和 SQL 优化器选择计划是同一件事吗？

不是。前者处理 Region 分布与集群资源，后者决定查询的物理执行方式。
