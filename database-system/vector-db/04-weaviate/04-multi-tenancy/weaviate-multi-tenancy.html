①三种隔离方案对比

Weaviate 的多租户实现是三个产品里最「彻底」的：一个 tenant 就是一个独立 shard，物理上住在各自的段里，不存在「过滤条件写漏就串数据」的风险。

方案隔离级别开销适用
tenant（原生多租户）物理隔离（独立 shard）每 tenant 有固定开销，适合中大规模租户B2B SaaS 首选
单租户 + payload 过滤逻辑隔离最低租户数极大（10 万+）、单租户数据极少
每租户一个 Class物理隔离（独立 collection 级）最高极少的大客户、需独立配置

②tenant 状态机与内存释放

Tenant 有明确的状态机，理解状态才知道内存什么时候被释放：

状态含义内存怎么进入
ACTIVE正常服务已加载创建或激活
INACTIVE保留数据但不接受查询释放API 置为 inactive
OFFLOADED数据在冷存储，需先加载未加载长时间不活跃自动降级（可配）
# 创建租户
POST /v1/schema/Doc/tenants
[{ "name": "tenant_a" }, { "name": "tenant_b" }]

# 查询时指定租户（必须）
GET /v1/objects?class=Doc&tenant=tenant_a

# GraphQL 里也要带
{ Get { Doc(tenant: "tenant_a", limit: 5) { content } } }

# 停用（释放内存）
PUT /v1/schema/Doc/tenants
[{ "name": "tenant_a", "activityStatus": "INACTIVE" }]
忘记带 tenant 参数会直接报错（这其实是好事 —— 报错好过静默跨租户）。对比 Qdrant 的 payload 过滤方案，忘记写条件不会报错，只会越权。这是 Weaviate 多租户的核心优势。

③激活代价与冷热分层的正确姿势

OFFLOADED / INACTIVE 是省内存的利器，但激活是有延迟的重操作 —— 这正是「冷租户」方案在体验上的代价。

操作耗时量级对用户的影响
ACTIVE → INACTIVE秒级查询立刻失败（应提前从路由摘除）
OFFLOADED → ACTIVE取决于数据量，可能数十秒到分钟级首个请求超时；需预热
新建 tenant毫秒级无
冷热分层的前提是能预判谁要热起来。登录即触发异步激活 + 前端 loading 兜底，或者按租户活跃度定时预热 —— 直接把冷租户丢给用户第一请求，必然超时。

④按租户数与数据量选型

按租户数与单租户数据量两个维度选型，比按「哪个高级」选更靠谱：

租户数单租户数据推荐理由
< 100大（十万级以上）每租户一个 Class 或 tenant，配独立资源隔离彻底，成本可控
100 – 1 万中tenantWeaviate 的设计甜点区
1 万 – 10 万小tenant + 冷热分层大量租户需卸载冷数据
> 10 万极小（数百条）单 Class + payload 过滤shard 数量过多会让元数据管理爆炸
每个 tenant 一个 shard 不是没有代价：shard 数量过多会显著拖慢集群元数据操作和启动时间。十万级 tenant 的场景不要硬套原生多租户。

⑤速记卡

实现方式

tenant = 独立 shard，物理隔离。

核心优势

查询必带 tenant，漏写会报错而不是越权。

三种状态

ACTIVE / INACTIVE / OFFLOADED，后两者释放内存。

激活代价

OFFLOADED → ACTIVE 可能数十秒，需预热或异步。

甜点区

100 – 1 万租户、单租户中等数据量。

上限警告

10 万+ tenant 会让元数据与启动变慢，改用过滤。

vs Qdrant

Qdrant 靠 payload 过滤，需 SDK 层强制注入条件。

冷热分层

必须能预判热租户，不能靠第一请求硬扛。

多租户选型的本质是在「隔离强度」和「shard 数量」之间找平衡。租户越多越不能靠物理隔离，越要注意越权。
