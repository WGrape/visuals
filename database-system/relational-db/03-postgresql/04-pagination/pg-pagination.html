深分页与游标分页

LIMIT/OFFSET 的陷阱，以及 keyset（游标）分页为什么更快更稳。

① OFFSET 分页为什么会慢② Keyset（游标）分页：正确的深翻页姿势③ COUNT(*) 慢怎么办④ 其他实用技巧⑤ 常见问法

① OFFSET 分页为什么会慢

最常见的写法 LIMIT n OFFSET m 有个致命问题：数据库必须先扫描并丢弃前 m 行。页码越深，丢弃越多，代价线性增长。

EXPLAIN ANALYZE
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 100000;
-- Limit (cost=...) (actual time=...) 
--   ->  Index Scan ... (actual rows=100020)   ← 读了 10 万行只返回 20 行
另一个问题：OFFSET 分页会「漂移」。翻页期间若有新数据插入（或删除），用户会看到重复行或漏行。这在「按时间倒序」的列表里尤其常见。

② Keyset（游标）分页：正确的深翻页姿势

思路：记住上一页最后一行的排序键，下一页用 WHERE 直接从它之后开始取——让索引直接定位。

-- 第一页
SELECT * FROM orders ORDER BY created_at DESC, id DESC LIMIT 20;
-- 记下最后一行的 (created_at, id) = ('2026-10-01 09:00:00', 12345)

-- 后续页（关键：用元组比较，且带上唯一键 id 保证确定性）
SELECT * FROM orders
WHERE (created_at, id) < ('2026-10-01 09:00:00', 12345)
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- 对应的索引（列顺序与 ORDER BY 一致！）
CREATE INDEX idx_orders_created_id ON orders (created_at DESC, id DESC);

优点

代价与页码无关（始终 O(limit)）；不受插入/删除影响，不会漂移

代价

只能「下一页/上一页」，不能跳到第 N 页；需要客户端保存游标

必须带唯一键

排序键可能重复（同时间创建多行），加 id 作为 tie-breaker 才能严格单调

元组比较

PG 支持 (a, b) < (x, y)，配合复合索引可高效走索引

排序方向要统一：若索引是 (created_at DESC, id DESC)，查询也要 ORDER BY created_at DESC, id DESC。方向混用（一个 DESC 一个 ASC）会导致无法使用该索引做有序扫描，退化成排序。

③ COUNT(*) 慢怎么办

分页组件总要显示「共 N 条」，但 SELECT count(*) FROM t WHERE ... 在某些条件下需要全表扫描（没有索引能覆盖时），大表上可能几秒甚至几十秒。

方案做法适用
精确计数直接 count(*) + 合适索引数据量小或条件可走索引
估算值SELECT reltuples FROM pg_class WHERE relname='orders';「约 12 万条」够用的场景
EXPLAIN 估算EXPLAIN SELECT ... 读 rows带条件的近似估算
计数表用触发器/异步任务维护计数高频读取、容忍短暂不准
不显示总数改为「加载更多」/ 无限滚动信息流、时间线类产品
index-only scan建覆盖索引 + 保证 VM 已 VACUUM条件简单时可大幅提速
-- 让 count(*) 走 index-only scan
CREATE INDEX idx_orders_status ON orders (status);
VACUUM ANALYZE orders;              -- 更新可见性映射，避免回表
EXPLAIN SELECT count(*) FROM orders WHERE status = 'paid';
-- Aggregate -> Index Only Scan using idx_orders_status

④ 其他实用技巧

覆盖索引

CREATE INDEX ... INCLUDE (col) 让查询只走索引，避免回表（PG 11+）

部分索引

WHERE status='pending' 的索引更小、更快；适合「只查未处理」的场景

表达式索引

CREATE INDEX ON t (lower(email)) 让 WHERE lower(email)=? 走索引

游标 CURSOR

服务端游标适合大批量顺序导出，不适合交互式分页（占连接、有状态）

keyset + 反向

「上一页」用 > 比较 + ORDER BY ... ASC 后再反转结果

稳定排序

ORDER BY 必须包含唯一键，否则同值行的顺序不确定，会导致重复/漏行

-- 覆盖索引（INCLUDE）：避免回表
CREATE INDEX idx_orders_list ON orders (created_at DESC, id DESC)
  INCLUDE (status, amount);

-- 部分索引：只索引热点子集
CREATE INDEX idx_pending ON orders (created_at) WHERE status = 'pending';

-- 表达式索引：大小写不敏感查询
CREATE INDEX idx_users_email_lower ON users (lower(email));

⑤ 常见问法

Q：为什么深分页（OFFSET 很大）会变慢？

A：因为 OFFSET m 的语义是「先产生前 m 行结果，再丢弃它们」。数据库必须真正扫描（或索引扫描）这 m 行才能知道该从哪开始返回，因此代价是 O(offset + limit)，页码越深越慢。此外 OFFSET 分页会漂移：翻页期间有新数据插入/删除时，用户可能看到重复行或漏行。解法：改用 keyset（游标）分页。

Q：keyset 分页怎么写？有什么限制？

A：把上一页最后一行的排序键作为锚点：WHERE (created_at, id) < (last_created, last_id) ORDER BY created_at DESC, id DESC LIMIT 20，并建与 ORDER BY 顺序一致的复合索引。关键：① 排序键必须唯一，所以要补上 id 作为 tie-breaker；② 用 元组比较 (a,b) < (x,y) 才能正确走复合索引；③ 索引列顺序与排序方向要匹配。限制：不能跳页（无法直接到第 500 页），因此适合「加载更多」与时间线，不适合传统页码导航（后者可限制最大页数 + 缓存）。

Q：分页一定要显示总数吗？怎么优化 COUNT？

A：不一定。精确 COUNT 在大数据量下代价高，可选方案：① 估算：SELECT reltuples FROM pg_class 或用 EXPLAIN 的 rows 估计；② 维护计数表（触发器或异步任务更新）；③ 产品上改为「加载更多」而不显示总数；④ 让 COUNT 走 index-only scan（建覆盖索引 + 及时 VACUUM 更新可见性映射）。实践建议：如果「约 12 万条」就够用，绝不要为了精确而付出全表扫描的代价。

Q：ORDER BY 里为什么建议带上唯一键？

A：因为若排序键有重复值（如同一秒创建的多个订单），数据库不保证这些行的相对顺序稳定——两次查询之间顺序可能变化，导致同一行出现在两页，或某些行被跳过。加上 id 作为次级排序键后，排序键变成严格唯一的「全序」，分页结果才确定。这条对 OFFSET 与 keyset 分页都适用。

Q：覆盖索引（INCLUDE）对分页有什么帮助？

A：分页查询通常需要先按索引顺序定位，再回表取完整行。若索引里已包含列表页所需的列（用 INCLUDE (col1, col2) 或建成复合索引），就可以走 index-only scan，完全不回表，随机 IO 大幅减少。前提：① 可见性映射（VM）已设置，否则仍需回表检查可见性——所以要及时 VACUUM；② 索引不能太大，否则得不偿失；③ INCLUDE 列不参与索引排序，只作为「附带数据」（PG 11+）。

Q：服务端游标（CURSOR）适合做分页吗？

A：不适合交互式分页，适合大批量导出。游标是有状态的：占用连接、持有事务快照、阻止 VACUUM 回收，在 Web 应用中（请求之间连接会被复用/释放）难以管理。正确用法：离线导出、ETL、批处理中声明游标并 FETCH 分批读取，读完后关闭。Web 分页请用 keyset（无状态）——它把「位置」编码在查询条件里，天然适合无状态的 HTTP 请求。

第一层 · 概念与判定

分页有两种本质不同的做法：

  • OFFSET 分页（LIMIT offset, size）：按固定顺序跳过前 N 行，适合随机跳页、后台遍历，但深度翻页代价高。
  • 游标/Keyset 分页（WHERE key > last_key ORDER BY key LIMIT size）：基于上一页最后一条的排序键向后取，适合「上一页/下一页」无限滚动，深度无关。
  • 判定信号：需要跳到第 100 页 → OFFSET；只需要连续翻 → Keyset。

第二层 · 参数·命令·量化

OFFSET 翻页延迟随偏移线性增长，因为数据库要先扫描并丢弃前 offset 行：

两种写法对比

-- 深度翻页：越深越慢
SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 200000;

-- Keyset 游标分页：稳定且快（id 为索引唯一键）
SELECT * FROM orders WHERE id > 200000 ORDER BY id LIMIT 20;

Keyset 要求 ORDER BY 的列必须唯一且带索引，否则会出现重复或漏数据。复合排序键时条件要写成「上一页最后一个 (a,b) 之后的下一个」：

SELECT * FROM t WHERE (a, b) > (10, 50) ORDER BY a, b LIMIT 20;
-- 等价于 a>10 OR (a=10 AND b>50)，需配合行值比较或展开条件

第三层 · 排障与边界

  • 深度翻页慢：OFFSET 500000 时 EXPLAIN 看到 Seq Scan/Index Scan 但仍丢弃大量行；改 Keyset 或延迟物化（先取 id 再 join）。
  • 翻页重复/漏数据：ORDER BY 无唯一键，并发插入导致游标错位；务必把主键纳入排序。
  • COUNT(*) 全量计数慢：精确总数在大表上昂贵；前端改用「估算值」或去掉总数、只做无限滚动。
  • ORDER BY 与索引不一致：用了 Keyset 但排序方向反了，条件要同向（都 ASC 或都 DESC）。

第四层 · 原理与取舍

OFFSET 越深越慢的根因是它无法利用索引跳过，必须从结果集起点顺序扫描并丢弃。Keyset 则把「下一页从哪开始」编码为索引范围条件，走 Index Range Scan，扫描量恒等于一页大小。

为什么不直接用 LIMIT size OFFSET？

OFFSET 翻页复杂度 O(offset+size)，而 Keyset 是 O(size)；百万元级数据翻到末页，前者可能慢几十到上百倍。

复合排序键怎么写 Keyset？

用行值比较 (a,b) > (last_a,last_b)，或展开为 a>last_a OR (a=last_a AND b>last_b)，并保证 (a,b) 有联合索引。
