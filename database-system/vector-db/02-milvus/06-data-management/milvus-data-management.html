①写入链路与批次建议

写入路径：SDK → Proxy → WAL（消息队列）→ DataNode 落盘对象存储 / QueryNode 内存消费。写入是追加式的，没有“原地更新”这一说——这决定了后面 upsert、delete、compaction 的所有行为。
  • 批量优先：单条循环写入会把 RPC 开销放大几十倍。经验上每批控制在 MB 量级（如 1–10 MB），条数按向量维度换算。
  • 超大批量走 Bulk Import：一次性几十 GB 的历史数据导入，用 SDK 逐批写会很慢且容易触发限流，用 bulk import 直写对象存储再让服务端挂载。
  • 维度与条数决定批次大小：768 维 float32 一条约 3 KB，1 MB 约 300 条；批次大小要按这个换算，而不是拍脑袋写 1000。

②insert / upsert / delete 的真实语义

操作行为注意
insert追加写入。主键已存在时，会多出一条同主键记录（查询可能命中旧的）不确定是否已存在就用 upsert，不要 insert
upsert存在则覆盖、不存在则插入，幂等代价高于 insert（要先查/标记），但换来了重跑安全
delete按主键或表达式软删除：写入删除标记，查询时过滤掉空间不会立刻释放，要等 compaction 真正清理
最常见的线上事故：用 insert 做更新。库里会堆积同一个 doc_id 的多版本，检索时随机命中旧内容，而且删不掉——因为删除只能按主键，按主键删会把新旧一起删掉。正确做法是一开始就用 upsert。
# 幂等写入：文档更新后重新灌入，不会留下旧版本
client.upsert(collection_name="docs", data=rows)

# 删除：按主键，或按表达式批量删
client.delete(collection_name="docs", ids=[1001, 1002])
client.delete(collection_name="docs", filter='tenant == "acme"')

③flush 与 compaction

flush()

把 growing 段强制封口并持久化到对象存储。批量导入结束后调用一次，可确保数据不留在内存里。代价：会产生较多小段，紧接着往往需要 compaction。

Compaction

后台把多个小段合并成大段，并真正清除被删除的数据。它同时改善两件事：减少段数量（降低查询固定开销）、释放删除占用的空间。

典型节奏：

  1. 批量写入 → flush()（数据落盘、不再依赖内存）
  2. 等待/触发 compaction（小段合并、删除清理）
  3. 确认索引构建完成（若对延迟有要求，用 wait_for_index_building_complete 之类的方式等待就绪）
compaction 是资源密集型后台任务，会吃 CPU 与 IO。写入高峰期间触发大量 compaction，可能反过来拖慢在线查询——大批量导入尽量安排在业务低峰。

④TTL：让数据自动过期

对时效性数据（会话记录、临时缓存、新闻流），可以给 Collection 设置 TTL（秒）：数据超过指定时长后，由后台任务自动清理，不必自己写定时删除脚本。

client.alter_collection_properties(collection_name="session_logs",
                                   properties={"collection.ttl.seconds": 604800})  # 7 天
TTL 到期后同样依赖后台清理任务落盘生效，不是“到点瞬间消失”。需要立刻生效的场景仍然要显式 delete + compaction。

⑤批量导入：BulkWriter 与 Bulk Import

离线灌数据的标准姿势不是“循环 insert”，而是：

  1. 用 BulkWriter 把数据在本地切成 Parquet / JSON / Numpy 文件（按批次大小自动分片）；
  2. 把文件上传到与 Milvus 共享的对象存储（MinIO / S3）；
  3. 调用 bulk_import，服务端直接挂载这些文件为 Segment，跳过逐条解析与 WAL 回放。
from pymilvus import bulk_import, BulkFileType, get_import_progress

resp = bulk_import(url="http://localhost:19530", collection_name="docs",
                   files=[["part-1.parquet", "part-2.parquet"]])
task_id = resp["data"]["taskId"]
print(get_import_progress(url="http://localhost:19530", task_id=task_id))
bulk import 最适合首次建库和大版本重建；日常增量还是走 insert/upsert。它的吞吐通常比逐条写高一个数量级，因为省掉了 WAL 与逐条解析。

⑥备份与恢复

milvus-backup

官方备份工具，把 Collection 的元数据与数据导出到对象存储，支持全库/单集合备份与恢复，以及跨集群迁移。

备份什么

元数据（etcd）+ 对象存储数据两部分都要有，缺一个都不完整。索引可以不备份——恢复后重建即可（耗时更长）。

恢复演练

备份的价值只在“恢复成功过”之后才成立。至少在预发环境完整演练一次，记录耗时与校验方式。

替代方案

如果原始数据（文档 + Embedding 生成脚本）可重放，重建往往比恢复更快更干净——向量库在很多系统里是“可重建的派生数据”。

⑦常见坑清单

坑为什么怎么避
用 insert 做更新同主键多版本堆积，删不干净一律 upsert
删除后磁盘没降软删除 + 未 compaction删除后触发 compaction，别只看逻辑条数
小批量高频写入产生海量小段，查询变慢客户端攒批，或走 bulk import
写完不 flush 就下线growing 段仍在内存导入结束显式 flush
以为 upsert 很便宜upsert 需要先定位旧数据，写放大明显首次建库用 insert/bulk，增量更新才用 upsert
没有备份策略向量库被当成唯一数据源保留可重放的原始数据，或定期 milvus-backup
本页涉及的默认值与语法支持范围随版本演进，落地前请用你部署版本的官方文档核对。
Milvus 的数据管理围绕一条主线：写入是追加、删除是标记、清理靠 compaction。理解这三条，就能解释“为什么更新要用 upsert”“为什么删了空间没降”“为什么小段多了查询变慢”。
