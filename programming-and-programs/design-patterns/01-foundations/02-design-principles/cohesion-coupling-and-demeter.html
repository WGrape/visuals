04 · 把原则写进代码

最小伪代码

class ShippingPolicy {
  quote(customer, order) {
    region = customer.shippingRegion()
    return rateTable.lookup(region, order.weight)
  }
}
class Checkout {
  total(customer, order) {
    return order.subtotal + shippingPolicy.quote(customer, order)
  }
}

从代码中带走三件事

  1. 高内聚：同一变化原因的规则集中在合适模块。
  2. 低耦合：调用方只依赖必要的公开契约。
  3. 迪米特法则不是禁止所有点号；DTO 与不可变值对象的读取可能合理。
05 · 原则不是教条

对应哪些模式？什么时候收手？

  • 外观：用高层入口缩小客户端知识范围
  • 中介者：减少对象间网状依赖
  • 组合：对树形结构提供统一操作

别把所有逻辑都搬进一个巨型 Customer 类；规则属于哪个业务概念，就放在那里。封装应减少变化扩散，不是藏起所有数据。

customer.address.city.name 这样的访问一定违反迪米特法则吗？

不一定。若只是读取稳定的不可变 DTO，没有暴露行为耦合，未必需要包装；重点看内部变化是否迫使调用方修改。

怎么度量：内聚与耦合的分级

内聚与耦合不是形容词，是有分级标准的。判断一个模块好不好，先给它定级。

内聚等级（由低到高）含义例子评价
偶然内聚元素之间毫无关系一个 Util 类里塞了所有杂项最差
逻辑内聚做同一类事但由参数决定handle(type) 里 switch 做不同事差
时间内聚在同一时刻执行初始化函数里做一堆无关初始化差
过程内聚按同一流程串起来依次读文件、解析、写库（但各自独立）中
通信内聚操作同一份数据对同一订单做校验、计算、落库较好
顺序内聚上一步的输出是下一步的输入解析 → 校验 → 转换好
功能内聚共同完成一件且仅一件事一个只负责计算价格的模块最好
耦合等级（由低到高）含义例子评价
无直接耦合互不依赖通过主程序组装最好
数据耦合只传简单数据参数calc(price, count)好
标记耦合传整个数据结构但只用一部分calc(order) 只用两个字段中
控制耦合传参数控制对方行为parse(str, isStrict)中
外部耦合共享全局变量/全局配置两个模块都读写同一个全局配置差
公共耦合共享同一块全局数据区多个模块读写同一张全局表差
内容耦合直接访问对方内部实现直接改另一个模块的内部字段最差

迪米特法则：反例与正解

// 反例：迪米特法则违例（火车残骸 train wreck）
BigDecimal price = order.getCustomer().getWallet().getBalance().getAmount();
//  调用方知道了 Order、Customer、Wallet、Balance 四层的内部结构
//  任何一层改动，这一行都会编译失败

// 正解 1：让 Order 提供有意义的查询方法（委托）
class Order {
    public BigDecimal availableBalance() {
        return customer.availableBalance();     // 内部层层委托，外部只知一层
    }
}
BigDecimal price = order.availableBalance();

// 正解 2：需要展示时，让对象自己「填」给调用方
order.renderTo(view);                            // Tell, Don't Ask

// 正解 3：拆分，把需要的数据作为参数明确传入
BigDecimal price = pricing.calc(order.totalAmount(), discountPolicy);

耦合的改法

// 反例：公共耦合（全局可变状态）
object Config { var timeoutMs = 3000 }        // 任何地方都能改
class A { fun run() = use(Config.timeoutMs) }
class B { fun init() { Config.timeoutMs = 5000 } }   // B 悄悄影响了 A

// 正解：显式依赖注入，依赖关系可见
class A(private val timeoutMs: Int) { fun run() = use(timeoutMs) }
val a = A(timeoutMs = 3000)

// 反例：标记耦合（传整个对象只用一点）
fun calcTax(order: Order) = order.amount * 0.13
// 正解：只传需要的（数据耦合）
fun calcTax(amount: BigDecimal) = amount * 0.13

迪米特法则的实用判断标准（「只有一个点」原则）：一行代码里点号（.）不超过一个。a.b().c() 已经越界，a.getB().getC().doX() 是典型违例。唯一的例外是流畅接口（builder / stream），因为它们返回的是同一个抽象层级。

评审与重构逐条核对：

  • 先定级再说好坏：用内聚/耦合的分级表给模块定级，避免「我觉得不好」式争论。
  • 目标顺序：高内聚优先于低耦合——职责清楚了，依赖自然变简单。
  • 一行的点号不超过一个（迪米特法则的可操作判据）。
  • 全局可变状态是公共耦合，比参数传递危险得多，优先改成注入。
  • 传整个对象但只用一两个字段是标记耦合，改成只传需要的。
  • 用参数控制行为的函数（isStrict 类）是控制耦合，考虑拆成两个明确方法。
  • 循环依赖必须打破：抽公共模块或用依赖倒置。
  • 接口要窄：接口越宽，实现方与调用方的耦合越高。
  • 用架构约束测试固化规则（如 ArchUnit），否则规范会随人员流动退化。
  • 重构要有测试保护：没有测试的高内聚重构风险极高。

高内聚低耦合：一句口号背后的两件事

内聚描述模块内部元素的相关程度，耦合描述模块之间的依赖强度。目标很直白：内部紧密相关，外部尽量少依赖。

维度好坏表现
内聚功能内聚：一起完成一件事巧合内聚： unrelated 代码堆在一起util 包什么都往里塞
内聚修改一个需求只改一处一个需求要改五六个文件改个字段要动 handler/service/dao/model
耦合依赖抽象（接口）依赖具体实现直接 new 具体类型，无法替换
耦合依赖少而明确依赖多且隐蔽全局变量、隐式初始化顺序
内聚看内部一个模块是否只做一件事。
耦合看外部模块之间依赖是否必要且最小。
改一处高内聚的最终检验标准。
依赖抽象低耦合的主要手段。

耦合的六个层级（从坏到好）

内容耦合一个模块直接修改另一个的内部数据（最坏）
公共耦合多个模块共享全局数据
外部耦合都依赖同一个外部格式或协议
控制耦合通过标志参数控制对方内部流程
标记耦合传递整个数据结构但只用一部分
数据耦合只传递必要的数据（最好）
// ❌ 标记耦合：为了一个字段传整个大对象 func SendEmail(user User) error { return send(user.Email, tpl) // 只用了 Email } // ✅ 数据耦合：只传需要的 func SendEmail(to string, body string) error // ❌ 控制耦合：用标志控制对方行为 func Save(u *User, isAdmin bool) error // 内部按 isAdmin 分支 // ✅ 拆成两个明确语义的函数 func SaveUser(u *User) error func SaveAdmin(u *User) error

不必追求零耦合：完全没有依赖就无法协作。目标是让依赖必要、明确、单向——尤其是避免循环依赖与隐式依赖。

迪米特法则：只和直接的朋友说话

也叫最少知识原则：一个对象应当尽量少地了解其它对象的内部结构。通俗说法是「不要和陌生人说话」。

// ❌ 违反迪米特：一路点下去，暴露了整条链 city := order.GetUser().GetProfile().GetAddress().GetCity() // 调用方知道了 User、Profile、Address 三层的内部结构 // ✅ 让对象自己提供它该提供的 city := order.ShippingCity() // 或者至少只跨一层 city := order.User().City()

能调用谁

  • 自身的方法
  • 传入参数对象的方法
  • 自己创建的对象的方法
  • 自己的字段（含集合元素）的方法
  • 不要调用「方法返回值的方法」再往下点

好处

  • 内部重构不会波及调用方
  • 调用链短，出错点少
  • 测试只需 mock 直接依赖
  • 代码读起来不用来回跳转

别走极端

  • 为每个层级都加转发方法会产生大量样板
  • 数据流经的 DTO 链式访问是可以接受的
  • 核心是「别让调用方依赖它不该知道的结构」

怎么落地：三个可操作的检查

  1. 改一个需求要动几个文件？如果总是横跨多个目录，说明内聚不足或分层不合理。
  2. 画一下依赖方向。依赖应当是单向的（上层依赖下层、领域不依赖基础设施），出现环就要通过接口倒置或下沉公共部分来解。
  3. 看 import 列表。一个包 import 了十几个内部包，通常说明它承担了过多职责；一个包被几十个包依赖，说明它是基础设施，要特别保持稳定。
领域不依赖基础设施用接口倒置依赖方向
公共部分下沉被多方依赖的代码放到底层包
循环依赖Go 编译期就会报错，必须解
按业务分包让高内聚在目录上可见
稳定依赖原则不稳定的包不要被过度依赖
别怕重复一点点过早抽取公共库会造成耦合

深入自检

高内聚和低耦合矛盾吗？

不矛盾，反而是互补的。内聚高意味着模块内部紧密、对外暴露少；对外暴露少自然降低耦合。真正的矛盾通常出现在「复用」上——为了复用几行代码而抽取公共包，往往同时损害两者。

迪米特法则会不会导致大量转发方法？

有可能。判断标准是「这个转发是否属于该对象的职责」。如果调用方确实需要这个语义（如 ShippingCity），加上去是合理的；如果只是为了避免点号链，那不如让调用方拿到合适的对象。

怎么判断一个包是否内聚？

看它的包注释能否用一句话说清职责，以及包内的类型是否总是一起被使用。如果包里一半的类型只在某个场景下用，另一半在另一个场景用，就该拆分。

依赖倒置和降低耦合是什么关系？

依赖倒置是降低耦合最有效的手段之一：把「上层依赖下层实现」变成「双方都依赖抽象」，于是下层的改动不会波及上层。它是实现低耦合的具体方法，而不是与之并列的概念。

为什么不建议过早抽取公共代码？

因为抽取会创建依赖。两个模块恰好有相似代码，但它们的演进方向可能完全不同，过早共享会让一方的变化牵制另一方。通常建议等到第三次出现同样需求再抽取（Rule of Three）。
