Transactional Outbox：跨数据库与消息的可靠发布

让业务写入和待发事件进入同一数据库事务，再用可重试发布处理消息系统故障。

双写为什么容易留下半成品

订单服务既要写数据库订单，又要向消息队列发布“订单已创建”。若先提交数据库、再发消息，发消息前进程崩溃会留下订单但没有事件；若先发消息、再提交数据库，数据库提交失败会留下没有订单的事件。把两次调用放进一个普通 try 块也不能形成跨系统原子性。Transactional Outbox 把订单行和待发布的 outbox 行放在同一个数据库事务里提交，让“有订单就有待发事件”成为本地事务保证。

Outbox 不直接保证消息只送一次。后台发布器扫描或订阅 outbox，成功发送后标记已发布；若发送成功却在标记前崩溃，重启后会再次发送。通常应接受至少一次投递，并让消费者用事件 ID 做幂等处理。若消费者更新自己的数据库，幂等记录与业务写入最好也在同一个本地事务中。

逐步推演

本地提交

一个事务写业务记录和 outbox 事件，确保二者共同存在或共同回滚。

异步发布

发布器扫描或订阅待发事件，发送给消息系统。

幂等消费

消费者按稳定 event_id 去重，并与本地业务更新一起提交。

监控恢复

观察积压、最老事件年龄、重复投递和按业务键的顺序。

订单创建的完整时间线

一次请求生成稳定 order_id 与 event_id。在数据库事务里插入订单和 outbox 事件，提交后立刻向用户返回订单创建成功。发布器随后读取未发布事件，按指定主题发送；消息系统确认后，再记录发送状态。用户请求无需等待消息系统在线，但下游看到事件会有可监测的延迟。若业务要求“下游同步完成才算成功”，Outbox 并不满足该需求，需要另选协调或同步协议。

故障点留下的状态恢复方式
本地事务提交前订单与 outbox 都没有客户端按幂等键重试
提交后、发送前订单和待发事件都存在发布器稍后继续发送
发送后、标记前事件可能被重复发送消费者按 event_id 幂等
消费中途失败消息重新投递消费事务与去重记录一起提交

顺序、积压与清理仍要设计

同一个订单先“创建”后“取消”，若由多个发布器并发处理，消息可能乱序到达。可按 aggregate_id 分区、记录单调版本号，消费者拒绝旧版本，或按业务键顺序发布。全局顺序通常代价很高，也未必必要；应明确需要的是“同一订单内有序”还是“所有订单全局有序”。

发布器可以轮询 outbox，也可以利用数据库变更日志 CDC。轮询实现直接，却要控制扫描索引、批量大小与锁争用；CDC 降低轮询压力，但增加日志订阅与重放运维。两种方式都要监控待发条数、最老事件年龄、重复投递率和失败重试。删除旧 outbox 行前，先确认已被可靠发布并满足审计保留要求。

验收清单与适用边界

  1. 业务行和 outbox 行在同一数据库事务中写入，事件包含稳定 ID、业务键、类型、版本与时间。
  2. 消费者允许重复投递，幂等窗口覆盖消息重试和故障恢复周期。
  3. 发布积压达到门槛时报警，记录从业务提交到下游生效的端到端延迟。
  4. 演练发送成功但标记失败、发布器重启、消费者事务失败与消息乱序。

练习：订单事件发出后发布器崩溃，重启又发送同一个 event_id。消费者怎样保证库存只扣一次？如果两个事件属于同一订单，如何识别旧版本并避免状态倒退？

表结构与消费者去重的最小设计

Outbox 表至少应能表示 event_id、aggregate_id、aggregate_version、event_type、payload、created_at 和发布状态；发布状态可用于重试，但不能当作消费者已经生效的证明。消费者可以建立以 event_id 为唯一键的 inbox 或处理记录，在同一个本地事务中先尝试插入去重键、再更新业务状态。重复消息碰到唯一约束后直接确认处理完成，避免再次扣库存。

事件 payload 应包含足够的业务标识与版本，但不宜无节制复制敏感数据。Schema 演进时，旧消费者可能还在运行；新增字段尽量保持向后兼容，删除字段要等待消费者升级。订单创建和取消的顺序可由 aggregate_version 检查：如果取消版本 2 先到，消费者可以暂缓、重试或依业务策略处理，不能盲目用较旧的创建事件覆盖较新状态。

Outbox 适合最终一致的跨服务传播，并不保证下游在用户响应前已经完成。若业务必须在同一请求里确认多个系统全部成功，需要明确同步协调、超时和补偿策略。把 Outbox 的“可靠发布”误称为“全链路实时原子提交”，会导致接口契约与真实行为不符。

为什么需要 Outbox：先发消息还是先写库？

顺序失败场景后果
先发消息 → 再写库消息发出去了，本地事务回滚下游收到了不存在的订单（幽灵消息）
先写库 → 再发消息库写成功，发消息崩了下游永远不知道（丢消息）
Outbox消息与业务同一个本地事务落库原子性由 DB 保证，之后异步投递

Outbox 的核心洞察：不要试图把“数据库”和“消息中间件”放进一个分布式事务（2PC 又慢又脆），而是把消息当成一行数据写进业务库，借用本地事务的 ACID。之后用一个独立的投递组件把这张表“搬运”到 MQ。

表结构设计与投递流程

Outbox 表结构与投递 SQL

CREATE TABLE outbox (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  aggregate_id  VARCHAR(64)  NOT NULL COMMENT '业务聚合ID，如订单号',
  event_type    VARCHAR(128) NOT NULL COMMENT 'OrderCreated / OrderPaid',
  payload       JSON         NOT NULL,
  -- 投递状态：0=待投递 1=已投递 2=投递失败(待重试)
  status        TINYINT      NOT NULL DEFAULT 0,
  retry_count   INT          NOT NULL DEFAULT 0,
  next_retry_at DATETIME(3)  NULL,
  created_at    DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  KEY idx_polling (status, next_retry_at, id)   -- 轮询的核心索引
) ENGINE=InnoDB;

-- 业务代码：一个事务搞定，失败整体回滚
START TRANSACTION;
  INSERT INTO orders (...) VALUES (...);
  INSERT INTO outbox (aggregate_id, event_type, payload)
       VALUES ('ORD123', 'OrderCreated', '{"id":"ORD123","amt":9900}');
COMMIT;   -- 两者要么都在，要么都不在

-- 投递侧：原子地"认领"一批消息（关键：用 UPDATE 抢占，避免多实例重复发）
UPDATE outbox SET status = 1
 WHERE status = 0 AND (next_retry_at IS NULL OR next_retry_at <= NOW(3))
 ORDER BY id LIMIT 500;          -- 批量 500 条，一次 RTT
-- 然后 SELECT 出这 500 条（用应用层记录 id，或先 SELECT FOR UPDATE SKIP LOCKED）
SELECT id, event_type, payload FROM outbox WHERE status = 1 AND ... ;

MySQL 8.0 推荐用 SELECT ... FOR UPDATE SKIP LOCKED 做多实例并发认领，比“先 UPDATE 再 SELECT”更清晰；MySQL 5.7 只能用 UPDATE 抢占法。

三种投递方式：轮询 vs CDC vs 双写

方式延迟侵入性推荐度
定时轮询表50 – 500 ms（轮询间隔决定）低，实现最简单中小规模首选
CDC（Debezium/Flink CDC）10 – 100 ms零侵入，读 binlog大规模首选
事务提交后同步发（afterCommit）<10 ms中，且进程崩了会丢不推荐单独使用

轮询参数怎么定：间隔 100 ms + 批量 500 条，单实例可支撑约 5000 msg/s；间隔压到 50 ms、批量 1000 可到约 2 万 msg/s。再高就该上 CDC 了。

投递失败怎么重试：退避策略的具体数字

重试次数间隔累计延迟说明
11 s1 s网络抖动，绝大多数在这里恢复
25 s6 s下游短暂重启
330 s36 s下游较长时间不可用
45 min≈5.5 min疑似故障，告警介入
530 min≈35 min进入人工处理队列

公式：delay = min(base × 2^n, max_delay) × (1 + random(0, 0.1))。必须加随机抖动（jitter 10%），否则大批消息同时重试会形成重试风暴，把刚恢复的下游再次打垮——这是最常见的雪崩成因。

退避实现与监控

# 指数退避 + 抖动（Go）
func nextDelay(retry int) time.Duration {
    base := 1 * time.Second
    d := base * time.Duration(1<<uint(retry))      // 1s, 2s, 4s, 8s...
    if d > 30*time.Minute { d = 30 * time.Minute } // 上限
    jitter := time.Duration(rand.Int63n(int64(d) / 10))
    return d + jitter                              // +0~10% 抖动
}

# 死信：超过最大重试后转移，不要无限重试
UPDATE outbox SET status = 2, next_retry_at = NULL
 WHERE id = ? AND retry_count >= 5;

# 监控必须有的三个指标
#   1) outbox 表最大滞留时间（created_at 最老的一条）-> 超过 60s 告警
#   2) status=0 的行数（积压量）-> 超过 10000 告警
#   3) status=2 的行数（死信）-> 大于 0 立刻告警

消费端幂等：at-least-once + 幂等 = exactly-once

Outbox 保证消息至少发一次（不丢），但重复不可避免（投递成功但 ACK 丢失时会重发）。所以消费端必须幂等，两者合起来才是“有效一次”。

幂等方案做法适用
去重表 + 唯一键INSERT INTO consumed(msg_id) ... 利用唯一索引拦截最通用、最可靠
业务天然幂等用 SET status='paid' 而非 status=status+1状态机类，首选
乐观锁版本号WHERE version=? 更新并 +1需要并发控制
Redis SETNXSET msg_id 1 NX EX 86400高吞吐但可能丢，只做辅助

幂等消费实现

-- 去重表方案：和业务更新放在同一个事务里
CREATE TABLE consumed_msg (
  msg_id    VARCHAR(128) NOT NULL,
  topic     VARCHAR(128) NOT NULL,
  consumed_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (msg_id)                    -- 唯一键就是幂等的全部实现
) ENGINE=InnoDB;

START TRANSACTION;
  INSERT INTO consumed_msg (msg_id, topic) VALUES ('m-12345', 'order');  -- 重复则报 1062
  UPDATE orders SET status = 'PAID' WHERE id = 'ORD123';
COMMIT;
-- 若报 Duplicate entry 'm-12345' -> 说明已消费过，直接 ACK 返回即可

-- 定期清理（保留 7 天足够覆盖重发窗口）
DELETE FROM consumed_msg WHERE consumed_at < NOW() - INTERVAL 7 DAY;

深入自检

Outbox 表会无限膨胀吗？怎么处理？

会。每条消息都落表，百万 QPS 下一天就是几亿行。三个手段：① 投递成功后异步物理删除（或定期 DELETE WHERE status=1 AND created_at < NOW()-1天）；② 用 TRUNCATE 或分区表按天 DROP PARTITION（比 DELETE 快几个数量级，不产生 undo）；③ 高吞吐场景改用 CDC 直接读 binlog，连 outbox 表都不落（但要求 DB 开 binlog）。

CDC 读 binlog 和轮询 outbox 表，哪个更好？

中小规模用轮询（实现 100 行代码，可控可观测）；大规模用 CDC（延迟低、不扫表、不给 DB 加轮询压力）。判断点：如果轮询的 SELECT 已经让 DB 有可观测的压力，或延迟要求 < 100 ms，就上 CDC。注意 CDC 依赖 binlog，且 Debezium 需要额外的 Kafka Connect 集群运维。

Outbox 能保证“发出的消息顺序”吗？

能保证单个聚合（如同一个订单）内的顺序：给 outbox 表按 aggregate_id 分区投递，MQ 侧用同一个分区键（Kafka 的 key = aggregate_id）。但跨聚合的全局顺序无法保证也不该保证——那是把系统串行化了。

为什么不用 2PC / XA 直接跨 DB 和 MQ？

三个现实问题：① 性能——XA 的 prepare/commit 两轮日志，吞吐掉一个数量级；② 可用性——协调者宕机会导致资源被长时间锁定（悬挂事务）；③ 支持度——很多 MQ（早期 Kafka）根本不支持 XA。Outbox 用“本地事务 + 异步投递”绕开了全部三点，代价只是多一张表。

自检

Outbox 是否实现了跨数据库和消息队列的严格一次提交？

没有。它把业务写入和待发记录做成本地原子事务，发布阶段仍可能至少一次投递。

为什么发布器发送成功后仍可能再次发送？

发送确认与本地“已发送”标记之间可能崩溃，恢复后会重试未标记事件。
