深入理解 MySQL 支持的存储引擎及其特性对比

MySQL 主要存储引擎

InnoDB 默认引擎

MySQL 默认的存储引擎，支持事务、行级锁和外键，是大多数应用场景的首选。

  • 支持 ACID 事务
  • 支持行级锁
  • 支持外键约束
  • 支持崩溃恢复
  • 支持 MVCC
MyISAM legacy

MySQL 5.5 之前的默认引擎，不支持事务，但查询速度快，适合读密集型应用。

  • 支持全文索引
  • 支持空间索引
  • 表级锁
  • 不支持事务
  • 不支持外键
MEMORY 内存引擎

将数据存储在内存中，速度极快，但重启后数据丢失，适合临时数据。

  • 极高的读写速度
  • 支持哈希索引
  • 数据易失性
  • 表级锁
  • 适合临时表
CSV 文本存储

将数据存储为 CSV 格式文本文件，方便数据交换，但不支持索引。

  • CSV 格式存储
  • 方便数据导入导出
  • 不支持索引
  • 不支持分区
Archive 归档引擎

高度压缩的存储引擎，适合存储大量历史归档数据，只支持 INSERT 和 SELECT。

  • 高压缩比
  • 只支持 INSERT/SELECT
  • 支持行级锁
  • 不支持索引（除自增）
NDB Cluster 集群引擎

MySQL Cluster 的存储引擎，支持高可用性和分布式存储。

  • 分布式存储
  • 高可用性
  • 支持事务
  • 内存存储为主

存储引擎 = 表怎么被存放与管理

MySQL 的一个独特之处：存储引擎是插件式的，按「表」粒度选择。同一个库里，A 表可以用 InnoDB，B 表可以用 Memory —— 它们的事务、锁、索引实现完全不同。

这带来灵活性，也带来困惑。今天这个选择几乎已经收敛：默认 InnoDB，其它引擎只在特定场景使用。

引擎事务锁粒度崩溃恢复典型用途
InnoDB支持行级锁 + MVCC有（redo/undo）默认之选：OLTP、几乎所有业务表
MyISAM不支持表级锁弱，损坏需修复历史遗留；只读/只读汇总场景偶尔还有
Memory不支持表级锁重启数据全丢临时缓存、中间结果、会话表
Archive不支持行级插入锁一般高压缩的归档日志，只插入不更新
CSV不支持表级锁无以 CSV 文件形式交换数据
第三方（RocksDB 等）视实现视实现视实现特殊写入模式、超大压缩比需求

InnoDB 为什么赢：从 5.5 版本开始成为默认，因为它把当时 MyISAM 缺的东西补齐了 —— 事务、行级锁、崩溃安全、外键。在此之前换引擎常常是为了换个 lock 的行为；现在换引擎的理由通常非常具体且狭窄。

InnoDB 内部的关键差别

① 聚簇索引的数据组织

InnoDB 的主键 B+ 树叶子就是行数据本身（索引组织表）；二级索引的叶子存的是主键值。

这带来两个重要后果：主键的选择影响巨大（最好是单调递增，避免页分裂与碎片），以及二级索引查询需要一次「回表」。

② Buffer Pool 缓存数据本身

InnoDB 自己维护一个大缓存，缓存数据页与索引页。命中缓存时完全没有磁盘 IO。

对比之下，MyISAM 只缓存索引，数据每次都依赖操作系统的页缓存 —— 这条差别在高并发下非常明显。

③ redo log 保证崩溃安全

写操作先记 redo log（顺序写，很快），数据页的落盘可以异步进行。崩溃后用 redo 把未落盘的改动重做一遍。

这就是著名的 WAL（Write-Ahead Logging）思路，也是「数据不丢」与「写入够快」能同时成立的关键。

④ 行级锁 + MVCC

写只锁涉及的行，读走快照不阻塞。这让 InnoDB 能承受高并发混合读写。

MyISAM 的表级锁意味着一个写操作会阻塞整张表的所有访问 —— 在并发稍高时就成为瓶颈。

其它引擎还剩哪些用武之地

引擎仍然合适的场景必须小心的点
Memory会话表、一次性中间结果、极小且可重建的查找表重启即丢、表级锁、内存占用受上限约束、不支持某些数据类型
Archive写入一次、之后只偶尔全量读取的审计/流水归档不支持更新删除（或很差）、无普通索引
CSV与其它系统交换文件的中转表无索引、无事务，是格式而不是真正的存储引擎
MyISAM几乎不再推荐；偶尔用于只读的统计快照表表级锁、无事务、崩溃后可能损坏

一条务实的判断：如果你说不出「为什么非用它不可」，那就用 InnoDB。换引擎往往是过早优化，绝大多数性能问题在索引、SQL 与容量规划上，而不是引擎本身。

实操：查看与修改

-- 查看某表的引擎 SHOW TABLE STATUS LIKE 'orders'\G -- 或 SELECT engine FROM information_schema.tables WHERE table_schema='db' AND table_name='orders'; -- 建表时指定 CREATE TABLE t (id INT PRIMARY KEY) ENGINE=InnoDB; -- 修改已有表的引擎（会重建表） ALTER TABLE t ENGINE = InnoDB; 注意：ALTER 会重建整张表并复制数据， 大表执行要在低峰期，并确认磁盘空间足够。

顺带一提：MySQL 内部临时表会在特定条件下使用 Memory 引擎；当结果太大或含有不支持的类型时会自动转成磁盘临时表 —— 这条切换规则是很多「某个查询突然慢了」的幕后原因，观察 Created_tmp_disk_tables 状态值能发现端倪。

深入自检

为什么大家都从 MyISAM 迁走了？

核心是三点：① 表级锁让并发写几乎不可用；② 不支持事务，业务一致性只能靠应用层；③ 崩溃后可能丢数据或表损坏，需要人工修复。相比之下 InnoDB 提供了事务、行锁与崩溃恢复，代价只是体积稍大、 COUNT(*) 需要扫描 —— 后者可以用其它手段解决。

InnoDB 的 COUNT(*) 为什么慢？

因为它要兼顾 MVCC：不同的事务看到的行数可能不一样，所以不能简单地维护一个全局计数。它必须真的去数一遍（通常会选最小的可用索引来扫）。如果需要频繁获取近似行数，可以用统计信息里的估算值或自己维护一张汇总表。

临时用 Memory 表有什么坑？

三个：① 服务重启数据就没了；② 表级锁导致并发受限；③ 内存是共享资源，表变大可能影响整个实例。所以只适合「丢了能自动重建」的中间结果，绝不要用它存任何唯一一份的数据。

换引擎能解决我的性能问题吗？

极少。引擎是底层决策，而绝大多数瓶颈在索引是否合理、SQL 是否写了函数导致失效、返回行数是否过多、磁盘与内存是否够用。正确的排查顺序永远是：看执行计划 → 看索引 → 看数据量与返回行数 → 最后才考虑架构层面的改动。
