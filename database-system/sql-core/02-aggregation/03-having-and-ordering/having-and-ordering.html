①WHERE 与 HAVING 的分界线

两者的分界是聚合发生的位置：WHERE 在分组聚合之前过滤行， HAVING 在之后过滤分组。这决定了两点性能与一点语义。

能提到 WHERE 的条件尽量提前——聚合的输入越小，排序/哈希的开销越小
-- ❌ 100 万行全部分组，再丢掉 99% 的组
SELECT dept, COUNT(*) c FROM emp
GROUP BY dept
HAVING dept IN ('R&D', 'Sales');

-- ✓ 先过滤到 2 万行再分组
SELECT dept, COUNT(*) c FROM emp
WHERE dept IN ('R&D', 'Sales')
GROUP BY dept;

-- 只能放 HAVING 的情况：条件依赖聚合结果
SELECT dept, COUNT(*) c FROM emp
GROUP BY dept
HAVING COUNT(*) > 50;
HAVING 里能引用 SELECT 别名吗？MySQL 允许（HAVING c > 50）， 这是它对标准的扩展；PostgreSQL、SQL Server 不允许在 HAVING 里引用 SELECT 列表别名，必须重写聚合表达式。 写跨库 SQL 时一律写完整表达式最安全。

②ORDER BY 的三个细节

1. 排序的是「结果集」，不是表

表在关系模型里是无序集合。没有 ORDER BY 就不存在任何顺序保证—— 「看起来是按主键返回」只是某种执行计划的副产品，换索引、换版本、加并发就可能变。

2. NULL 排在哪里由实现决定

数据库ASC 时 NULLDESC 时 NULL显式控制
MySQL / SQL Server最前最后用 ORDER BY (col IS NULL), col
PostgreSQL / Oracle最后最前NULLS FIRST / NULLS LAST
当一个库要迁到另一个库，或同一份 SQL 跑在不同库上时，NULL 顺序差异常常导致分页结果「看起来错乱」。 永远显式指定。

3. 排序稳定性与分页

排序键不唯一时，相同键的行之间顺序不确定。LIMIT 10 OFFSET 10 这种分页在键不唯一时 会出现「同一行出现在两页」或「某行永远不出现」。解法是在 ORDER BY 末尾追加唯一键：

SELECT * FROM orders
WHERE status = 'paid'
ORDER BY created_at DESC, id DESC    -- id 保证全序
LIMIT 20 OFFSET 40;

③LIMIT / OFFSET 与窗口函数配合

每组 TopN

先 ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) rn， 外层 WHERE rn <= 3。不能在 WHERE 里直接用窗口函数——它计算于 WHERE 之后。

深翻页

OFFSET 100000 要先生成并丢弃 10 万行。改用键集分页： WHERE (created_at, id) < (?, ?) ORDER BY created_at DESC, id DESC LIMIT 20。

LIMIT 与 DML

标准 SQL 的 UPDATE/DELETE 不支持 LIMIT（MySQL 扩展支持）。 大批量删除务必分批 + 限制条数，否则长事务会锁住大片行并撑爆 undo / WAL。

排序内存

排序超过 sort_buffer_size / work_mem 会落盘，性能断崖。 大结果集排序要尽量让索引提供顺序（ORDER BY 字段与索引一致），避免额外排序。

④高频问题

Q：ORDER BY 的字段上有索引，为什么还有 Using filesort？
A：三种常见原因：① 混合了升幂降幂（a ASC, b DESC）而索引方向不一致； ② 排序字段跨表；③ 过滤后的数据仍需回表取其他列，优化器判断「回表随机 IO」比「直接排序」更贵。 覆盖索引（把 SELECT 的列都放进索引）往往能解决第三类。
Q：GROUP BY 的结果为什么过去是有序的、现在乱了？
A：MySQL 5.7 及之前 GROUP BY 会隐式按分组列排序，8.0 移除了这一行为（符合标准）。 依赖隐式排序的老 SQL 升级后会「乱序」，显式加 ORDER BY 即可。
Q：SELECT DISTINCT a ORDER BY b 报错怎么办？
A：因为去重后一个 a 可能对应多个 b，排序依据不明确。要么把 b 加进 DISTINCT， 要么改成 GROUP BY a 配 MAX(b) 之类的聚合来定序。
Q：HAVING 里能用别名以外的优化吗？
A：把不依赖聚合的条件全部挪到 WHERE，这是最有效的。 另外 HAVING COUNT(*) > N 这类「分组后按数量过滤」无法提前， 若数据量大且模式固定，考虑预聚合到汇总表。

执行顺序与 HAVING vs WHERE

逻辑执行顺序

书写顺序：   SELECT ... FROM ... WHERE ... GROUP BY ... HAVING ... ORDER BY ... LIMIT
实际执行：   FROM -> WHERE -> GROUP BY -> HAVING -> SELECT -> DISTINCT -> ORDER BY -> LIMIT

注意 SELECT 在 HAVING 之后才执行——这解释了下面两个现象：
  1) MySQL 允许 HAVING 引用 SELECT 里的别名
  2) WHERE 不能引用聚合函数（MySQL 报 ERROR 1111: Invalid use of group function）
对比项WHEREHAVING
作用对象行（分组前过滤）组（分组后过滤）
能否用聚合函数不能能（如 HAVING COUNT(*) > 5）
能否用 SELECT 别名MySQL 不允许MySQL 允许（因为 SELECT 先于 HAVING 求值）
能否走索引可以，优先用它过滤通常不行（分组后才过滤）
性能影响先过滤再分组，数据量小分组完再过滤，尽量把条件前推到 WHERE

ONLY_FULL_GROUP_BY：MySQL 5.7 起默认开启，SELECT 里出现非聚合列就必须出现在 GROUP BY 中，否则报 ERROR 1055。别用「关掉 sql_mode」来解决，正确做法是显式加进 GROUP BY 或加聚合函数（如 ANY_VALUE(col)）。

排序稳定性与分页（线上最常见的两坑）

场景问题解法
ORDER BY 非唯一列并列行的顺序不确定，翻页时可能重复或漏行末尾追加唯一列：ORDER BY score DESC, id ASC
LIMIT n OFFSET m 深翻页OFFSET 100000 要先扫并丢弃 100000 行改键集分页：WHERE (score, id) < (?, ?)
排序内存不足sort_buffer_size 默认 256KB，超出落盘，EXPLAIN 显示 Using filesort减少参与排序的列宽（只取需要的列），或调大 sort_buffer_size
NULL 的排序位置MySQL 认为 NULL 最小（ASC 排最前）；PostgreSQL 认为 NULL 最大（ASC 排最后）PG 用 NULLS LAST 显式指定；MySQL 用 ORDER BY col IS NULL, col
中文排序排序规则决定结果，utf8mb4_general_ci 与 unicode_ci 结果可能不同统一 collation；PG 注意 collation 的来源（ICU vs libc）
GROUP BY 的隐式排序MySQL 5.7 及以前 GROUP BY 会顺带排序，8.0 已移除要排序就显式写 ORDER BY，别依赖老行为

SQL 对照

-- ❌ 深翻页：OFFSET 越大越慢（要扫过 100000 行再丢掉）
SELECT id, score FROM t ORDER BY score DESC, id DESC LIMIT 20 OFFSET 100000;

-- ✅ 键集分页（游标分页）：直接定位，与页码无关，恒定快
SELECT id, score FROM t
WHERE (score, id) < (9821, 13579)        -- 上一页最后一行的 (score, id)
ORDER BY score DESC, id DESC
LIMIT 20;
-- 前提：必须有联合索引 (score, id)，否则照样慢

-- 排序稳定性：并列时必须加唯一列兜底
SELECT id, name, score FROM t ORDER BY score DESC, id ASC;   -- ✅ 稳定

-- 看排序是否落盘
EXPLAIN SELECT * FROM t ORDER BY big_col;      -- Extra: Using filesort
SHOW VARIABLES LIKE 'sort_buffer_size';        -- 默认 262144 (256KB)
SET SESSION sort_buffer_size = 4 * 1024 * 1024;

-- HAVING 能用但应前推的例子
SELECT dept, COUNT(*) c FROM emp GROUP BY dept HAVING dept <> 'test';  -- ❌
SELECT dept, COUNT(*) c FROM emp WHERE dept <> 'test' GROUP BY dept;   -- ✅ 先过滤

键集分页的代价：不能「跳到第 N 页」，只能「下一页」。产品上用「无限滚动 / 加载更多」替代页码是最省事的解法。

自检

为什么 COUNT(*) 加 LIMIT 还是慢？

LIMIT 是在结果集产出后才截断的，COUNT 必须先把所有行扫完才能知道总数。要快就得用近似值（如 EXPLAIN 的 rows 估算、Redis 计数器）或单独的汇总表。

HAVING 能用索引吗？

基本不能。HAVING 作用在分组之后，索引已经用不上。任何能提到 WHERE 的条件都应该提前——这是 GROUP BY 查询最简单有效的优化。

ORDER BY 的列不在索引里一定慢吗？

不绝对。小结果集在内存里排很快；慢的是「大结果集 + 宽行 + 排序内存不足落盘」。先看 EXPLAIN 的 rows 估算和 Extra，再决定是否加索引。

GROUP BY 和 DISTINCT 能互换吗？

只去重不聚合时语义等价，很多优化器会生成相同计划。但要聚合时只能用 GROUP BY。

第一层 · 概念与判定：HAVING 与 WHERE 的分工

一句话：WHERE 过滤「行」（聚合前），HAVING 过滤「组」（聚合后）。

维度WHEREHAVING
执行时机聚合前聚合后
过滤对象单条记录分组结果
能否用聚合函数❌ 不能✅ 可以
能否用列的别名❌ 不能⚠️ MySQL 允许，PG 不允许
性能影响先过滤能大幅减少参与分组的行过滤发生在分组之后

WHERE 与 HAVING 的正确分工

-- 正确分工：能放 WHERE 的绝不放到 HAVING
-- 慢：先对全表分组，再过滤
SELECT dept, COUNT(*) c FROM emp GROUP BY dept HAVING dept <> 'HR';
-- 快：先过滤行，再分组
SELECT dept, COUNT(*) c FROM emp WHERE dept <> 'HR' GROUP BY dept;

-- 必须用 HAVING 的场景：条件依赖聚合结果
SELECT dept, COUNT(*) c FROM emp GROUP BY dept HAVING COUNT(*) > 10;

-- 两者配合
SELECT dept, AVG(salary) avg_sal
FROM emp
WHERE hire_date >= '2020-01-01'      -- 先过滤行
GROUP BY dept
HAVING AVG(salary) > 10000           -- 再过滤组
ORDER BY avg_sal DESC;               -- 可用 SELECT 别名
  • 信号一：过滤条件不依赖 COUNT/SUM/AVG → 放 WHERE（性能更好）。
  • 信号二：条件里有聚合函数 → 必须 HAVING。
  • 信号三：想按聚合值排序 → ORDER BY COUNT(*) DESC 或引用 SELECT 别名。

性能原则：WHERE 越早过滤越好。把 100 万行先过滤到 1 万行再分组，比分组 100 万行再过滤快得多。

ORDER BY 与分页优化

-- 显式控制 NULL 位置（PostgreSQL / Oracle）
SELECT * FROM t ORDER BY score DESC NULLS LAST;
-- MySQL 的等价写法
SELECT * FROM t ORDER BY score IS NULL, score DESC;

-- LIMIT + ORDER BY 的经典慢查询：大偏移量
SELECT * FROM orders ORDER BY id LIMIT 1000000, 20;   -- 慢：要先扫 100 万行
-- 改写成游标分页（keyset）
SELECT * FROM orders WHERE id > :last_id ORDER BY id LIMIT 20;   -- 快：O(1) 定位

-- 让 ORDER BY 走索引（避免 filesort）
CREATE INDEX idx_orders_created ON orders(created_at);
EXPLAIN SELECT * FROM orders ORDER BY created_at;     -- Extra 不应出现 Using filesort
参数作用说明
sort_buffer_size排序缓冲区默认 256KB～2MB，不够则落磁盘
max_length_for_sort_data决定全字段排序还是 rowid 排序MySQL 专用
max_sort_length参与排序的字节数上限超长字符串会被截断比较

量化参考：LIMIT 1000000, 20 需要扫描并丢弃 100 万行；改成 WHERE id > last_id LIMIT 20 是直接定位，从秒级降到毫秒级——这是分页优化收益最大的一处。

第四层 · 原理与取舍：为什么 ORDER BY 会慢

排序的代价来自两点：① 比较次数 O(n log n)；② 内存不够时落磁盘做归并排序（filesort）。避免它的唯一办法是让数据已经有序——即 ORDER BY 的列上有索引。

为什么有时候 ORDER BY 主键还是很慢？

因为 InnoDB 的二级索引叶子存的是主键值，用二级索引过滤后再按主键排序，仍需回表并排序。要让 ORDER BY 免排序，需要 WHERE 条件与 ORDER BY 列组成复合索引，且顺序、方向都匹配。

ORDER BY 能用索引的严格条件是什么？

① 索引的列顺序与 ORDER BY 一致；② 排序方向一致（都 ASC 或都 DESC，MySQL 8.0 支持降序索引）；③ WHERE 中的等值条件列在索引中位于 ORDER BY 列之前。任一不满足就会出现 filesort。

大偏移量分页除了游标还有什么办法？

① 延迟关联：先用覆盖索引找出 id，再 JOIN 回原表取数据（减少回表量）；② 业务上禁止跳到很深的页（只允许「上一页/下一页」）；③ 用搜索引擎（ES）的 scroll / search_after。
