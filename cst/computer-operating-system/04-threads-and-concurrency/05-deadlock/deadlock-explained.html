01四个必要条件

第一层

概念与判定

死锁 = 一组进程互相等待对方持有的资源，且都不释放自己已持有的。四个必要条件必须同时成立：

条件含义破坏方法
互斥资源一次只能一个进程用共享化 / 只读
占有并等待持有资源又去申请新的一次性申请全部 / 申请前释放
不可抢占资源不能被强行夺走允许抢占 / 超时回滚
循环等待存在环形等待链锁排序（最实用）
图：P1 持 A 等 B，P2 持 B 等 A，形成循环等待。
活锁：进程不阻塞但一直重试、无法推进（如两个线程都退让再重试）。饥饿：某进程长期得不到资源（如低优先级被高优先级一直抢先）。三者不同。

03排障与边界

第三层

排障与边界

  • 锁顺序不一致：线程 1 lock(A); lock(B)，线程 2 lock(B); lock(A)，最经典的死锁。修复靠全局锁序约定。
  • 锁 + 回调：持锁时调用外部回调，回调里又拿同一把锁 → 自死锁（非递归锁）。
  • 数据库死锁：SHOW ENGINE INNODB STATUS 看 LATEST DETECTED DEADLOCK；按主键顺序更新可减少。
  • Java 死锁：jstack 会直接打印 Found one Java-level deadlock 与线程栈。
  • Go 死锁：运行时检测到「所有 goroutine 都阻塞」会 panic all goroutines are asleep - deadlock!。
  • 内核死锁：开 lockdep（CONFIG_PROVE_LOCKING）能提前报告锁序违规。

04原理与取舍

第四层

原理与取舍

死锁无法被「彻底消灭」，只能被工程化地规避。通用 OS 选择「忽略 + 检测（超时）」，因为预防的代价（资源利用率）太高；而数据库、实时系统会更严格。

场景现实策略
通用 OS忽略，靠重启/超时
数据库检测等待图，回滚代价小的事务
实时系统优先级天花板协议，静态分析
微服务超时 + 重试 + 幂等，把死锁转成超时

深入 Q&A

Q：为什么「锁排序」最实用？
A：它只破坏「循环等待」一个条件，不需要预知资源需求、不降低并发，只需团队约定 + 代码评审。代价最小。

Q：trylock 超时会不会掩盖真 bug？
A：会。超时是兜底，不是修复。应在监控里对 trylock 失败打点，定位真正的锁序问题。

互斥 / 占有并等待 / 不可抢占 / 循环等待。

最实用解法

全局锁排序，破坏循环等待。

银行家算法

分配前判安全性，需预知最大需求。

活锁 ≠ 死锁
