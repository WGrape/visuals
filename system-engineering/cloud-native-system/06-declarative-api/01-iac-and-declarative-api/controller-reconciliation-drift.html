声明式控制器：调谐、幂等与状态漂移

用副本控制器的循环说明期望状态如何收敛，以及冲突与外部副作用如何处理。

声明只是目标，控制器负责行动 用户写下“副本数为三”，API Server 保存期望状态；控制器观察当前集群，发现只有两个符合选择器的实例，于是创建一个。稍后若有实例故障，它再次比较并补齐。这个过程不是一次 apply 命令的魔法，而是持续的观察、计算差异、执行动作和复查。控制器通常只负责自己声明的资源边界，不能因为看见一个相似对象就随意接管。

调谐函数的输入可能是缓存中的观察结果，事件只是“值得重新检查”的提示；事件可能重复、合并或乱序。正确性应来自读取当前期望与实际状态，而非假设每个事件恰好处理一次。状态更新和外部动作之间也没有天然原子事务，需要让重复调谐安全。

一次控制循环的时间线 第 1 轮看到 desired=3、actual=2，控制器创建新实例。创建 API 超时，客户端不知道服务端是否成功；第 2 轮重新列表，若已经有 3 个，就不再创建。若控制器仅凭上次“超时”再盲目创建一个，可能升到 4 个。给子资源设置稳定名字或 owner reference，配合按身份查找，可以降低重复动作风险。

第 3 轮可能遇到节点容量不足，新实例 Pending。此时 actual“对象数量”虽然是 3，可用副本只有 2。控制器应在 status 中区分已创建与可用，并设置条件和原因，供运维判断是容量、镜像拉取还是健康检查失败。只写 spec 不保证环境一定能达到目标。

逐步推演

读取状态

从权威 API 获取期望与实际对象。

计算差异

区分对象数、可用性和自己拥有的字段。

幂等执行

按稳定身份创建或更新，冲突后重新读取。

反馈状态

写入条件、原因和重试线索，持续检查收敛。

幂等与重试边界 幂等意味着同样的观察结果重复调谐后，不会产生无上限的额外对象或副作用。常用做法是按稳定资源键 upsert、比较版本再更新，并把成功结果写入状态。对外部支付、发邮件之类不可逆动作，需要独立的幂等标识和明确授权；普通控制器的“重试”并不能自动让这些副作用安全。

API 更新常使用资源版本做乐观并发控制。若两个控制器同时改同一对象，一个可能收到冲突，应该重新读取并只修改自己拥有的字段。盲目全量覆盖会抹掉其他控制器或用户的更新。退避和速率限制可防止故障资源形成热循环，但不能掩盖长期不能收敛的错误配置。

状态漂移与所有权 手工修改运行中的资源会造成实际状态与 Git 或声明文件不一致。控制器可能把它改回，也可能因为字段不属于自己而保留修改。团队应先明确“谁拥有哪个字段”和“哪一份声明是权威来源”。例如 HPA 管理 replicas 时，交付流水线再持续强制写 replicas，会形成拉扯；需要调整字段所有权或停止重复声明该字段。

漂移检测要区分有意的默认值、服务端填充字段和真正的未授权变更。只做纯文本 YAML diff，可能把字段顺序、默认化和运行时 status 当成漂移。应对标准化后的期望与实际 spec 比较，并记录改动人、控制器和时间。生产修复先判断变更为何发生，再决定回滚、采纳还是更新声明。

失败恢复和最终化 创建容易，删除常涉及外部资源清理。Finalizer 可以在对象删除前阻止最终移除，让控制器删除云负载均衡或存储卷等附属资源，然后移除 finalizer。若清理逻辑永久失败，对象会卡在 Terminating；必须暴露清楚的条件、重试策略和人工修复步骤，而不是无条件忽略错误。

控制器重启后不能依赖进程内记录继续工作。它要从 API 中恢复期望与实际关系，处理孤儿对象和重复对象。对长时间 Pending、持续冲突、调谐队列积压分别设告警，并用事件与 status 提供用户可理解的诊断信息。

设计和测试 实现前写下不变量：最多允许多少子资源、每个子资源属于谁、什么状态算 Ready、删除时何时可释放。测试包括重复事件、乱序更新、API 超时、冲突、控制器重启、节点容量不足、删除中断。每个场景都应检查最终状态和中间副作用，不能只断言调谐函数返回 nil。

上线后观察收敛耗时分位数、失败重试次数、队列深度、对象状态条件和不期望漂移次数。若用户改了 spec 但长时间不收敛，要能从状态说明原因。这才是声明式接口可信的基础。

Reconcile 循环的关键参数

参数/概念默认值说明
sync-period（resync）10 小时（controller-manager 默认，含随机抖动）即使无事件也强制全量重新对账
抖动范围周期的 ±10%避免所有 controller 同时醒
RequeueAfter按业务（秒–小时）主动要求一段时间后再次对账
指数退避5 ms 起，上限 1000 s（controller-runtime 默认）失败后的重试间隔
MaxConcurrentReconciles1同一 controller 的并发 worker 数
幂等性必须同一输入重复执行结果相同

声明式 API 的核心模型：用户声明期望状态（spec），controller 不断把实际状态（status）朝期望状态收敛。这个循环叫 reconcile，它必须是幂等的——因为同一个对象会被反复 reconcile（事件触发、resync、重启后全量）。

漂移检测命令

# 观察漂移与期望状态
kubectl get deployment nginx -o yaml          # 看 spec（期望）与 status（实际）
kubectl diff -f manifest.yaml                 # 本地声明 vs 集群实际的差异（server-side dry-run）
kubectl get deployment nginx -o jsonpath='{.status}'  # 只看实际状态

# 查看 controller 的行为
kubectl logs -n kube-system deployment/kube-controller-manager | grep -i reconcile
kubectl get events --sort-by=.lastTimestamp   # 看 controller 产生的事件

# Terraform 的漂移检测
terraform plan          # 对比 state 与真实基础设施的漂移
terraform refresh       # 把真实状态同步回 state
terraform plan -refresh-only
terraform apply -auto-approve

# 强制触发 reconcile（annotate 改动会触发更新事件）
kubectl annotate deployment nginx kubectl.kubernetes.io/restartedAt="$(date +%s)" --overwrite

漂移的成因与处理

漂移来源例子检测处理
人工直接修改有人 kubectl edit 或手工改云控制台kubectl diff / terraform plan重新 apply 覆盖回去；或限制直接写权限
其它 controller 争抢两个 controller 改同一个字段看 managedFields / metadata明确 ownership，用 server-side apply 的 field manager
外部系统变更云厂商自动升级、节点故障resync（定期全量对账）controller 重新拉回期望状态
代码/模板升级GitOps 仓库内容变了ArgoCD 的 OutOfSync 状态自动或手动 sync
状态滞后status 没及时更新对比 spec 与 status检查 controller 是否正常（看日志/重启）
  • resync 是漂移的兜底：事件（watch）可能丢失（网络抖动、controller 重启），所以 controller 必须周期性全量对账。10 小时的默认 resync 意味着最长 10 小时才能发现一次“静默漂移”——对关键资源应缩短或用 RequeueAfter。
  • 漂移是声明式的必然副产品：只要存在“绕过声明层的修改入口”，漂移就无法杜绝。治理靠权限收敛（禁止直接写生产集群）+ GitOps（一切变更走 Git）+ 自动对账/自动修复。
  • Auto-reconcile vs 人工确认：ArgoCD/K8s 默认会自动把实际状态拉回期望；Terraform 默认只报告不自动修（要你 review plan 再 apply）。关键基础设施建议保留人工确认环节。
  • 幂等是硬要求：reconcile 会被调用无数次。如果逻辑不幂等（如每次 append 而不是 set、每次计数 +1），状态会失控。永远用 set 而非 append，用绝对值而非增量。
  • 并发与去重：controller-runtime 默认对同一对象的 reconcile 是串行的（workqueue 去重）。要并发需调 MaxConcurrentReconciles，但同一 key 仍不会并发——这保证了安全性。
  • 排障顺序：① kubectl get -o yaml 对比 spec/status；② 看 controller 日志（是否报错、是否在循环）；③ 看 events（有没有 Warning）；④ 看是否达到退避上限（1000 s，表现为长时间不动）；⑤ 确认 RBAC 是否有权限。
为什么我改了 spec 但很久没生效？

三种可能：① controller 没在跑或卡在退避（最长 1000 s）；② 有最终器（finalizer）阻止；③ 变更被 webhook 拒绝（看 events 里的 Warning）。先看 kubectl get events 和 controller 日志。

声明式和命令式的本质区别是什么？

命令式描述怎么做（执行一系列动作，中断了就不知道做到哪一步）；声明式描述要什么（目标状态，由 controller 反复收敛）。声明式的优势是幂等、自愈、可版本化、可审计——代价是需要一个持续运行的控制循环。

自检

控制器收到两次相同事件，会创建两个新副本吗？

正确实现应重新读取当前对象并按稳定身份调谐；事件可重复，不能把事件次数当成所需动作次数。

练习：选一个真实业务样本，写出输入、预期结果、一次失败时的证据，以及可以复现实验的验收标准。
