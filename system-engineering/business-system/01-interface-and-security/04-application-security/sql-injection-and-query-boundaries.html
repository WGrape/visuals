SQL 注入防线：绑定参数与动态查询边界

沿“按订单状态筛选并排序”的接口，区分值、标识符与数据库权限三道防线。

问题不在用户输入特殊，而在它被当成 SQL 语法

订单列表接口接受 status、sort 和分页参数。若程序把这些字符串拼进 SQL 文本，数据库无法区分“用户提供的值”与“查询结构”，可能改变筛选条件或执行意图。修复不是删除某几个字符，而是建立边界：值使用驱动提供的参数绑定；列名和排序方向不能用普通占位符时，在服务端固定映射表中选择；数据库账号只拥有该接口真正需要的权限。

查询构造层、ORM 与数据库驱动的接口各不相同，但共同原则是让数据值与 SQL 结构分别交给正确的机制。输出中的脱敏、错误处理和监控属于后续纵深防线，不能代替参数绑定。

图解：三类输入，三种处理

这些措施相互补充而非二选一：参数绑定挡住值变语法，标识符映射限制查询结构，最小权限限制意外查询的破坏面。

逐步推演：从查询参数到数据库

输入先按业务契约解析

接口接受 status=PAID、sort=created、limit=20。枚举 status、限定 limit 的范围，避免异常资源开销；输入校验用于业务正确性，不承担代替参数绑定的防注入职责。

结构由代码决定

服务端把 created 映射为固定的 created_at 列，把方向映射为 ASC 或 DESC。未知字段拒绝，不把客户端原串粘贴在 ORDER BY 后。

数据值由驱动绑定

订单状态和可信租户标识作为绑定参数交给驱动，不通过字符串转义拼接。某些驱动对 IN 列表需要生成与元素数相同的占位符，列表元素仍逐一绑定。

失败不暴露内部查询

数据库只授予本服务必需的表与操作；客户端只看到稳定错误码，内部日志记录查询模板/错误类别而不输出完整凭证或敏感值。异常排序字段增加可观测事件，但不能靠告警完成拦截。

第一层 · 三类防线各管什么

输入类型正确处理常见误区
订单 ID、状态、关键词等值参数占位符 + 驱动绑定自己替换引号或手工转义后拼接
表名、列名、排序方向从可信服务端映射表选择有限项把占位符误用于标识符，或直接拼原字符串
查询权限专用最小权限账号与敏感数据隔离应用进程持有可改所有表结构的管理员账号
错误输出响应统一、日志脱敏且有定位标识直接把原 SQL 和连接详情回传给用户

第二层 · 安全构造示例

// 示意伪代码：允许字段由服务器定义；值交给驱动绑定
allowedSort = {"created": "created_at", "amount": "amount"}
column = allowedSort.get(request.sort)
if column is None: rejectBadRequest()
direction = "DESC" if request.descending is True else "ASC"
query = "SELECT id, amount FROM orders WHERE tenant_id = ? AND status = ? "
query += "ORDER BY " + column + " " + direction + " LIMIT ?"
rows = database.execute(query, [trustedTenantId, request.status, boundedLimit])

column 和 direction 只来自常量映射；只有值走占位符。不同驱动的 ?、编号占位符等写法可能不同，不能把该伪代码直接照搬到生产。订单列表还要按可信租户与业务归属过滤；“不会 SQL 注入”并不等于“不会越权”。

第三层 · 容易漏掉的查询边界

  • ORM 不是永久免疫：ORM 的普通绑定 API 通常安全，但 raw SQL、手工 where 字符串、动态 order/group 仍需按规则处理；注意批量更新和迁移工具。
  • 动态 IN 列表：占位符数量可随列表长度生成，元素逐个绑定；同时限制列表长度，避免极端请求拖垮查询。
  • 存储过程：内部拼接动态 SQL 也会重建注入风险；不要只因入口调用是存储过程就跳过检查。
  • 最小权限：读接口与写接口可使用不同数据库角色；定期审视账号可访问的 schema/表和历史遗留权限。

第四层 · 原理与取舍

过滤掉单引号就够了吗？

不够。数据库语法、编码、上下文与驱动行为各不相同；字符黑名单容易漏情形，也会误伤合法数据。让驱动绑定值才是主要边界。

为什么 ORDER BY 的列名不能简单绑定为一个值？

参数占位符代表表达式中的数据值，不代表 SQL 的表名、列名等语法元素。排序项需从服务端固定映射表选择，不能期待数据库替客户端提供的字符串“自动变成安全列名”。

用了 WAF 还需要修改查询构造吗？

需要。WAF 无法理解所有业务上下文且可能绕过或误判；参数绑定与最小权限应在应用和数据库边界直接实施。

自检

status 用占位符了，sort 仍直接拼请求字符串，接口是否安全？

不安全。值的绑定不保护动态排序标识符；sort 必须映射到服务端列名允许列表。

练习：为“按多个订单状态过滤并按金额排序”划分哪部分是 SQL 结构、哪部分是需绑定的值，并说明这个查询还需要哪些租户约束。
