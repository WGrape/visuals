查询优化器

基于成本的 CBO、统计信息、选择性估计，以及慢查询排查。

① 优化器在做什么② 统计信息：优化器的眼睛③ 代价常数：让优化器认识你的硬件④ 常见的计划失误与对策⑤ 常见问法

① 优化器在做什么

PG 的优化器采用基于代价的优化（CBO） + 动态规划（DP）：枚举候选路径，用代价模型估算每条路径的代价，选最低者。

当 JOIN 表数超过 join_collapse_limit（默认 8）或 from_collapse_limit，PG 会退化为遗传算法（GEQO）启发式搜索，不再保证最优——这也是多表 JOIN 计划变差的常见原因。

② 统计信息：优化器的眼睛

-- 查看某列的统计信息
SELECT attname, null_frac, avg_width, n_distinct, most_common_vals, histogram_bounds
FROM pg_stats WHERE tablename = 'orders' AND attname = 'status';

-- 调整统计精度（默认 100，可到 10000）
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 500;
ANALYZE orders;
-- 或全局：default_statistics_target = 200

-- 多列相关时用扩展统计
CREATE STATISTICS st_city_zip (dependencies, ndistinct) ON city, zip FROM users;
ANALYZE users;
字段含义
null_fracNULL 值比例
avg_width平均字节宽度（影响内存/临时文件估算）
n_distinct不同值个数（-1 表示唯一，正数表示估算值）
most_common_vals最常见值（MCV）及其频率
histogram_bounds值分布直方图（用于范围选择性与排序）
correlation物理顺序与逻辑顺序的相关性（-1~1，影响索引扫描代价）
统计信息过期是「计划突然变差」的头号原因。大批量导入/删除后必须 ANALYZE；autovacuum 会触发 autoanalyze，但阈值（默认 10% 变化）对大表可能太迟钝。对大表建议设置更低的表级 autoanalyze 阈值。

③ 代价常数：让优化器认识你的硬件

参数默认含义建议
seq_page_cost1.0顺序读一页的相对成本（基准）保持 1.0
random_page_cost4.0随机读一页的相对成本SSD 上改 1.1~1.5（最关键！）
cpu_tuple_cost0.01处理一行的 CPU 成本一般不动
cpu_index_tuple_cost0.005处理一条索引项的 CPU 成本一般不动
cpu_operator_cost0.0025执行一次操作符/函数的成本一般不动
effective_cache_size4GBOS 缓存估计（不分配内存）设为内存的 50%~75%
parallel_tuple_cost0.1并行传递一行的成本—
最常见的调优动作：把 random_page_cost 从 4.0 调到 1.1~1.5。默认值是按机械硬盘设定的，在 SSD/NVMe 上会高估索引扫描的代价，导致优化器错误地选择全表扫描。这是很多「有索引却不走」问题的根因。

④ 常见的计划失误与对策

现象原因对策
rows 估计与实际差 10 倍以上统计信息过期 / 多列相关 / 函数包裹ANALYZE；扩展统计；改成可索引的表达式
有索引却全表扫描返回比例大；random_page_cost 偏高；索引失效调 random_page_cost；补/改索引；减少返回列
JOIN 顺序不优表数过多触发 GEQO；统计不准调 join_collapse_limit；拆查询；用 CTE 引导
Hash Join 落盘（Batches>1）work_mem 不足会话级调大 work_mem；减少列
嵌套循环内表被反复扫描内表缺索引给连接键建索引
参数化查询计划差generic plan 与具体值不匹配PG 12+ 有 plan_cache_mode；或强制 custom plan
-- 诊断利器：检查估计 vs 实际
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
-- 若 rows 估计 1000 而实际 5，说明选择性估算严重失误

-- 临时验证：关掉某些路径看计划变化（仅用于诊断，别长期关）
SET enable_seqscan = off;      -- 强制倾向索引（测试用）
SET enable_hashjoin = off;     -- 禁用 hash join
SET join_collapse_limit = 12;  -- 允许更多表的 DP 搜索
SET geqo_threshold = 20;
不要长期关闭 enable_* 参数。它们是诊断工具（用来验证「换个计划是否更快」），长期关闭会在数据分布变化后造成新的问题。确认有效后，应通过索引、统计信息、改写 SQL来引导优化器。

⑤ 常见问法

Q：优化器是怎么选计划的？

A：PG 采用基于代价的优化（CBO）：① 路径枚举——为每张表生成候选访问路径（Seq/Index/Bitmap 等），为 JOIN 枚举顺序与算法（Nested/Hash/Merge）；② 代价估算——用统计信息估算各节点返回行数，再乘以代价常数（seq_page_cost、random_page_cost、cpu_*）得到 IO + CPU 代价；③ 选最低代价。JOIN 表数在 join_collapse_limit（默认 8）以内用动态规划穷举，超过则退化为遗传算法 GEQO启发式搜索。因此：统计信息准确 + 代价常数贴合硬件 = 好计划。

Q：统计信息什么时候会不准？怎么修？

A：不准的典型情形：① 过期——大批量导入/删除/UPDATE 后没 ANALYZE（autovacuum 的 autoanalyze 阈值对大表可能太迟钝）；② 多列相关——优化器假设列独立，city 与 zip 这类强相关列会严重错估；③ 函数包裹——WHERE lower(name)=? 这类表达式的选择性只能靠粗略猜测；④ 数据倾斜——n_distinct 与 MCV 采样不足。修法：ANALYZE；提高 default_statistics_target（100 → 200~500）；用 扩展统计（dependencies/ndistinct）；对表达式建表达式索引并同步统计。

Q：为什么有索引却走了全表扫描？

A：三种原因：① 返回比例大——索引扫描要随机回表，返回超过 5%~10% 时顺序扫描确实更快（这是正确判断）；② 代价常数失配——random_page_cost=4.0 是机械盘时代默认值，SSD 上必须调到 1.1~1.5，否则会系统性高估索引代价；③ 索引不可用——列被函数包裹、类型不匹配、LIKE '%x%'。此外 effective_cache_size 过小也会让优化器低估缓存命中。排查：EXPLAIN 看 rows 估计与实际是否吻合，再逐项排除。

Q：join_collapse_limit 和 GEQO 是什么关系？

A：join_collapse_limit（默认 8）控制优化器是否重排显式 JOIN 的顺序；当 JOIN 的表数超过 geqo_threshold（默认 12）时，PG 会改用遗传算法 GEQO做启发式搜索，不再保证最优计划。这意味着十几张表的大 JOIN 很可能拿到次优计划。对策：① 拆分复杂查询（用 CTE 或临时表分段）；② 适当提高两个阈值（但会显著增加规划时间）；③ 用 CTE 的 MATERIALIZED（PG 12+）作为优化屏障，强制分段执行；④ 保证统计信息准确，让即便启发式也能选得不错。

Q：能用 hint 强制走某个计划吗？

A：PG 官方不支持 hint（这是有意的设计决定，社区倾向于「修根因」而非「打补丁」）。可选手段：① pg_hint_plan 扩展——提供 /*+ IndexScan(t idx) */ 这类注释式提示，生产可用但属于外部扩展；② 临时关闭 enable_* 参数做诊断；③ 用 CTE MATERIALIZED 作为优化屏障；④ 根本手段是建对索引、更新统计信息、改写 SQL、调代价常数。建议：把 hint 当最后手段，因为它会在数据分布变化后失效甚至变差。

Q：计划突然变差，排查思路是什么？

A：五步：① EXPLAIN (ANALYZE, BUFFERS) 比较 rows 估计 vs 实际，差 10 倍以上 → 先 ANALYZE；② 若估计准确但计划仍差 → 检查 random_page_cost、effective_cache_size 是否符合硬件；③ 看是否有 Batches>1 / external merge Disk（work_mem 不足）；④ 看 JOIN 是否被反复扫描（内表缺索引）或 JOIN 顺序不优（表数多触发 GEQO）；⑤ 检查是否数据分布发生突变（如某状态值占比从 1% 涨到 50%）或索引失效/缺失。预防：监控 pg_stat_statements 中 mean_exec_time 的突变，比事后救火有效得多。

优化器关键参数与成本估算

PostgreSQL 是基于代价的优化器（CBO）：它枚举候选路径，用一套成本常数算出最便宜的。想干预它，要么改统计信息，要么改这些常数。

参数默认值含义什么时候调
random_page_cost4.0随机读一页的相对成本（基准 seq_page_cost=1.0）SSD 上应调到 1.1~1.5，否则优化器不敢用索引
seq_page_cost1.0顺序读一页的成本一般不动
cpu_tuple_cost0.01处理一行的 CPU 成本很少调
cpu_index_tuple_cost0.005处理一条索引项的成本很少调
effective_cache_size4GB告诉优化器「大概有多少缓存可用」应设为系统内存的 50%~75%，影响索引扫描倾向
work_mem4MB排序/哈希每个操作可用的内存大排序调大；注意是每操作不是每连接
default_statistics_target100统计信息采样精度（1~10000）基数估计不准时提到 500~1000
enable_seqscan 等on强制开关某类扫描只用于调试，别在生产常开

诊断与修统计

-- 1) 看执行计划（必须看 ANALYZE 版本才准）
EXPLAIN (ANALYZE, BUFFERS, VERBOSE) SELECT * FROM orders WHERE user_id = 42;
--   BUFFERS 能看到实际读了多少块（shared hit vs read），判断缓存命中

-- 2) 关键：看估计行数 vs 实际行数
--   Seq Scan on orders (cost=0.00..18334.00 rows=<b>5000</b> width=36)
--                      (actual time=0.020..120.400 rows=<b>3</b> loops=1)
--   rows 5000 而 actual 3  =>  <b>基数估计错误，这是慢查询第一大原因</b>

-- 3) 修统计信息
ANALYZE orders;                                  -- 重新采样
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 500;   -- 提高该列精度
ANALYZE orders;
SELECT * FROM pg_stats WHERE tablename='orders' AND attname='status';

-- 4) 看扩展统计（多列相关性，PG 10+）
CREATE STATISTICS st_orders ON user_id, status FROM orders;
ANALYZE orders;
--   两列有相关性时（如「某用户只买某类商品」），普通单列统计会严重低估

最重要的一条实践：对比 rows（估计）和 actual rows（实际）。相差 10 倍以上几乎必然导致错误的 JOIN 顺序或扫描方式。修的优先级：先 ANALYZE → 再提高 statistics target → 再用扩展统计 → 最后才考虑 hint 或重写 SQL。

执行计划节点与常见慢因

节点什么时候出现优化方向
Seq Scan没索引 / 选择性差（返回 >5~10% 的行）加索引或提高选择性；小表 Seq Scan 反而更快
Index Scan高选择性，回表读行回表多时考虑 Index Only Scan（加 VACUUM 更新可见性图）
Index Only Scan查询列全在索引里且可见性图是最新的最快；要定期 VACUUM 才有
Bitmap Heap Scan中 selectivity，先扫索引建位图再批量读通常合理；work_mem 不够会退化成 lossy
Hash Join大表连大表，无索引大表连接的主力；work_mem 不够会分批写盘（看 Batches）
Nested Loop小表驱动 + 内表有索引外层行数估计错会变成灾难（实际 10 万 × 每次索引扫描）
Sort / GroupAggregate排序/分组work_mem 不够会 external merge Disk，慢 10 倍
Materialize缓存子查询结果通常是 Nested Loop 的配套，正常

慢查询与索引体检

-- 慢查询定位（pg_stat_statements 必须装）
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
-- postgresql.conf: shared_preload_libraries = 'pg_stat_statements'

SELECT substring(query, 1, 80) AS q,
       calls, round(total_exec_time::numeric, 1) AS total_ms,
       round(mean_exec_time::numeric, 2) AS avg_ms,
       rows, 100.0 * shared_blks_hit / nullif(shared_blks_hit+shared_blks_read,0) AS hit_pct
FROM pg_stat_statements
ORDER BY total_exec_time DESC LIMIT 10;
--   看 total（总耗时）而不是 mean：总耗时高的才是优化重点

-- 找没用的索引（占空间还拖慢写入）
SELECT schemaname, relname, indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes
WHERE idx_scan < 50 ORDER BY pg_relation_size(indexrelid) DESC;

-- 找缺失索引（顺序扫描多的大表）
SELECT relname, seq_scan, seq_tup_read, idx_scan, n_live_tup
FROM pg_stat_user_tables
WHERE seq_scan > 1000 AND n_live_tup > 100000 ORDER BY seq_tup_read DESC;

-- 膨胀检查（bloat）
SELECT relname, n_dead_tup, last_autovacuum FROM pg_stat_user_tables
WHERE n_dead_tup > 10000 ORDER BY n_dead_tup DESC;
为什么有索引却走全表扫描？

三个原因：① 选择性不够——要返回超过 5%~10% 的行时，索引回表的随机 IO 比顺序全表更贵（这就是 random_page_cost 的作用）；② 统计信息过期——优化器以为表很小；③ 类型不匹配——WHERE varchar_col = 123 会隐式转换导致索引失效（PG 里尤其常见，必须类型一致）。

random_page_cost 到底该设多少？

看存储介质：机械盘 4.0（默认，合理）；SSD / 云盘 1.1~1.5（随机读和顺序读差距很小）；内存数据库或全缓存场景 1.0。这个值是 PG 在 SSD 上「明明有索引却全表扫」的头号原因——很多团队升了 SSD 但忘了改这个参数，导致整个库的执行计划都是按机械盘算的。

work_mem 设多大？

别用「总内存 / 连接数」来算，那是错的。work_mem 是每个排序/哈希操作（不是每个连接）可用的内存，一个复杂查询可能有 5 个排序操作，就是 5 倍。经验：先按 总内存 × 0.25 / 平均并发 设（如 64GB 内存、50 并发 → 约 320MB，保守取 32~64MB），然后用 EXPLAIN ANALYZE 看有没有 external merge Disk，有就针对那个查询单独调（SET work_mem = '256MB'）。
