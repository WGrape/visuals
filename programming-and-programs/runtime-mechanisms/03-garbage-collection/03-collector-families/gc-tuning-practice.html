01Go：GOGC 与停顿观测

优化方向：减少短命大对象分配（用 sync.Pool 复用）、降低 GOGC 控内存、或把大对象搬离热路径。

# 默认 GOGC=100：堆涨到上次存活的 2 倍触发 GC
GOGC=50 ./app     # 更频繁、更省内存、CPU 更高
GOGC=off ./app    # 关闭 GC（只适合短命批处理）

# 看每次 GC 的停顿与触发原因
GODEBUG=gctrace=1 ./app
# 输出示例: gc 1 @0.12s 2%: 0.1+0.4+0.05 ms clock

# pprof 看分配热点
go tool pprof http://localhost:6060/debug/pprof/allocs

02JVM：选回收器

回收器特点适用
G1平衡吞吐与停顿，默认多数服务端
ZGC亚毫秒级停顿，堆大时优势大堆、低延迟
Shenandoah并发压缩，低停顿低延迟、堆中偏大
Parallel吞吐优先、停顿大批处理
# 选 ZGC 并看停顿
java -XX:+UseZGC -Xmx16g -Xlog:gc*:gc.log App
# 关键：调 -Xmx 同时给足，回收器只解决「怎么收」，收多少由堆大小决定

03Python：引用计数 + 循环 GC

Python 主靠引用计数即时回收；只有循环引用才等 gc 模块。优化：打破循环（弱引用/显式置 None）、用 `__slots__` 省内存、大对象自己管生命周期。

import gc, tracemalloc
tracemalloc.start()            # 看内存分配来源
gc.set_threshold(700, 10, 10) # 调代际阈值
gc.collect()                  # 手动触发循环 GC
# 循环引用会被 gc 收，但带 __del__ 的对象可能进 gc.garbage 卡住

  • 停顿尖刺：先看 GC 频率（GOGC/阈值太高会攒一大波），再降分配。
  • 内存不降：多半是被全局容器/缓存长期引用，GC 无能为力，要查引用链。
  • 大对象/大数组：优先池化或复用，避免反复触发大块回收。
问：为什么不能把 GOGC 调很小来换低延迟？

GC 更频繁意味着每次回收的活对象少、停顿短，但 CPU 花在回收上的比例上升，总吞吐下降。低延迟和高吞吐是天平两端，要根据业务（API 要低延迟、批处理要高吞吐）取舍。

第一层 · 概念与判定：先定调优目标

GC 调优只有两个对立目标：低延迟（STW 短、毛刺少）或高吞吐（总 GC 时间占比低）。先问业务是「怕卡」还是「怕慢」，再动手，否则互相矛盾。

业务画像目标手段倾向
在线交易/网关低延迟减小单次回收量
离线批处理高吞吐减小 GC 频率
大堆长驻两者兼顾分代/调比例
内存敏感容器控峰值降 GOGC/上限

Go/Java GC 关键参数

# Go：默认 GOGC=100（堆翻倍才 GC）；调小更频繁但每次更轻
GOGC=50 ./app              # 增 50% 即回收，延迟更稳、吞吐略降
GOMEMLIMIT=4GiB ./app      # 软上限，避免 OOMKill

# Java：吞吐与停顿的平衡
java -Xms4g -Xmx4g -XX:+UseG1GC      -XX:MaxGCPauseMillis=200 -jar app.jar

# 看 GC 真实开销
java -Xlog:gc*:file=gc.log:time,level,tags -jar app.jar

数量级：GOGC 从 100 降到 50，GC 频率约翻倍、单次 STW 约减半；Go 默认 STW 已压到亚毫秒级，调优重点是「堆增长带来的长尾」而非总耗时。

第三层 · 排障与边界：四个坑

  • 只盯吞吐忽略毛刺：平均 GC 时间漂亮，但偶发一次 200ms 停顿拖垮 p99——在线服务要看分布不是平均
  • GOGC 盲目调小：GC 太频繁反而吃光 CPU，吞吐反降——先量再调，别拍脑袋
  • 大对象/大切片没释放：底层数组被一个小引用挂着，GC 清不掉，表现为内存只涨不跌
  • 容器内存上限与 GOGC 脱节：没设 GOMEMLIMIT，堆按宿主内存增长，被 cgroup 限额 OOMKill

第四层 · 原理与取舍

GOGC 到底控制什么，怎么权衡？

GOGC 是触发 GC 的堆增长百分比：100 表示「相比上次回收后存活量再涨 100% 就回收」。调小 → 更频繁、单次回收少、停顿短但 CPU 开销大（吞吐降）；调大 → 反之。本质是内存换 CPU、延迟换吞吐的旋钮，配合 GOMEMLIMIT 在容器里兜住峰值更稳。

为什么分代 GC（Java）能兼顾吞吐与延迟？

因为大多数对象朝生夕死：分代把新对象放年轻代，用复制算法快速回收（暂停短），只有存活久的才晋升老年代（少发生、可并发）。这样高频的轻量回收覆盖绝大多数垃圾，低频的重量级回收只处理长命对象，整体吞吐高、毛刺少。Go 目前不分代，靠并发三色标记 + 调 GOGC 来平衡。

GOMEMLIMIT 相比 GOGC 解决了什么？

GOGC 是「相对增长」触发，不知道绝对内存上限，在容器 cgroup 限额下容易超界被 OOMKill。GOMEMLIMIT 直接给一个软上限，GC 会主动把堆压到限制内，宁可多 GC 也不越界。两者配合：GOGC 控节奏、GOMEMLIMIT 控生死，是容器部署的推荐组合。
