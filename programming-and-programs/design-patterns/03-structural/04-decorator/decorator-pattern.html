01 · 从问题出发

为什么会需要这个模式？

数据流按需压缩、加密、记录日志；为每种组合建子类会迅速膨胀。

文件流有加密、压缩、日志三种可选能力。若为每种组合都建子类，会出现 EncryptedLoggedStream 等命名不断膨胀；若在 FileStream 内放多个布尔开关，类又要知道所有扩展。

😵 直接写会怎样

class FileStream:
  write(data, logEnabled, encryptEnabled, compressEnabled):
    if logEnabled: ...
    if encryptEnabled: ...
    if compressEnabled: ...

💡 关键转折

每个装饰器实现同一接口并包住下一个对象，调用沿包装链传递。

让每层包装都遵守 Stream.write。客户端只见一个 Stream，但内部可以像套娃一样按顺序叠加职责。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

interface Stream { write(bytes) }
class EncryptStream implements Stream {
  constructor(inner: Stream) { this.inner = inner }
  write(bytes) { this.inner.write(encrypt(bytes)) }
}
class LogStream implements Stream {
  constructor(inner: Stream) { this.inner = inner }
  write(bytes) { log("write"); this.inner.write(bytes) }
}
stream = new LogStream(new EncryptStream(new FileStream()))

读代码时抓住三件事

  1. 每个装饰器都实现 Stream.write，因此外部类型不变。
  2. 装饰器持有另一个 Stream，形成递归包装链。
  3. 职责顺序由构造链决定，调用方向由外向内。

换个业务场景，还能认出来吗？

HTTP 客户端可以包装重试、指标和鉴权层；但重试写请求时必须考虑幂等，指标也要明确记录每次尝试还是整个逻辑调用。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

保留接口且需要按需叠加可组合职责

三个具体场景

  • 流对象按需压缩、加密、记录日志
  • HTTP 客户端叠加指标与重试
  • 咖啡对象逐层加奶与糖并计算价格

不适合或要小心

包装顺序可能改变结果。装饰器侧重叠加行为；适配器侧重翻译不兼容接口。

包装顺序会改变结果；层数太多会使调试困难

最容易混淆的相邻模式

模式真正的区别
代理也保持接口，但重点是控制访问，例如鉴权或延迟加载；装饰器重点是添加可组合行为。
适配器把不兼容接口转换成目标接口；装饰器的内外接口相同。

区分时问自己：重点是增加职责、控制访问，还是翻译接口？

落地前检查

  • 写清包装顺序，必要时固定组合方式。
  • 测试每层独立行为以及组合后的结果。
  • 避免装饰器暗改返回值或吞掉内层错误。
06 · 自己说一遍

两道检验理解的小题

客户端为何无需知道包了几层？

每一层都实现 Stream.write；外部看仍是一个 Stream。

为何“先压缩再加密”与“先加密再压缩”可能不同？

加密会破坏原始数据的重复模式，密文一般难再压缩；包装层顺序影响最终结果。

第一层 · 本质与识别信号

一句话本质：在不改原对象的前提下，一层层地包上新功能。它是继承的替代品——用组合代替继承，且可以运行时动态叠加。

识别信号说明
需要给对象加功能，但不想/不能改它第三方库、稳定模块、开了闭原则
功能可以任意组合（压缩+加密+缓存+限流）用继承会是 2ⁿ 个子类爆炸
功能需要运行时动态增删继承是编译期决定的，做不到
已经出现 XxxWrapper、XxxWithYyy 这种类名你其实已经在用了
  • 关键结构：装饰器实现与被装饰对象相同的接口，同时持有一个同接口的引用。这样它可以被继续装饰——这就是「层层包裹」能成立的原因。
  • 与继承的对比：继承是编译期静态扩展（类写死），装饰器是运行期动态扩展（可任意顺序组合）。
  • 与代理的区别：装饰器增强功能（加东西），代理控制访问（权限、懒加载、远程）。结构上几乎一样，区别在意图。

第二层 · 骨架代码与真实案例

Go 实现

// —— 经典形态：io.Reader 的层层包裹（Go 标准库的最佳示范）——
type Reader interface{ Read(p []byte) (n int, err error) }

// 装饰器：实现同一接口 + 持有同接口引用
type CountingReader struct {
    r     io.Reader
    count int64
}
func (c *CountingReader) Read(p []byte) (int, error) {
    n, err := c.r.Read(p)
    c.count += int64(n)      // 增强：统计
    return n, err            // 其余原样转发
}

// 使用：任意顺序组合，每层只加一件事
var r io.Reader = file
r = bufio.NewReader(r)              // 加缓冲
r = &CountingReader{r: r}           // 加统计
r = io.LimitReader(r, 1<<20)        // 加限流
r = &loggingReader{r: r}            // 加日志
// 这就是装饰器：不需要 BufferedCountingLimitedLoggingReader 这种类

// —— HTTP 中间件就是装饰器（最广泛的实际应用）——
type Middleware func(http.Handler) http.Handler

func Logging(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        next.ServeHTTP(w, r)                        // 调用被装饰者
        log.Printf("%s %s %v", r.Method, r.URL, time.Since(start))
    })
}

func Auth(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if r.Header.Get("Authorization") == "" {
            http.Error(w, "unauthorized", 401); return   // 可以【提前短路】
        }
        next.ServeHTTP(w, r)
    })
}

// 组合（注意顺序：从外到内依次是 Logging -> Auth -> handler）
h := Logging(Auth(myHandler))
标准库 / 框架里的装饰器装饰了什么
bufio.Reader缓冲（把多次小读合并成大读）
io.LimitReader限制读取总量
gzip.Reader / flate解压
context.WithValue/WithCancel附加值 / 取消能力
HTTP middleware（Gin/echo/net-http）日志、鉴权、限流、恢复 panic
gRPC interceptor同中间件模式，分 unary 与 stream
tls.Conn 包 net.Conn加密（典型：网络层装饰器）
Python @decorator语法糖层面的装饰器

Go 里装饰器最常见的形态是 middleware / interceptor：func(Handler) Handler。学会这一个签名，就等于掌握了 HTTP、gRPC、消息队列中间件的所有写法。

第三层 · 常见误用与排查清单

  • 装饰链太长导致调试地狱：10 层装饰后，报错栈里全是 wrapper，找不到真正的实现。解法：控制层数（≤5）、每层加明确的日志标识、用结构化日志带上链信息。
  • 顺序敏感却没文档：Logging(Auth(h)) 和 Auth(Logging(h)) 行为不同（前者会记录未授权请求，后者不会）。必须明确记录中间件顺序约定，通常「越通用的越靠外」（日志/恢复在外，鉴权在内）。
  • 装饰器改变了语义：如缓冲装饰器让数据「提前被读走」，导致底层 reader 的位置不符合预期；或 LimitReader 悄悄截断了数据。装饰器应该只增强、不改变契约。
  • 忘记转发所有方法：如果接口有 5 个方法，装饰器只实现了 1 个增强的、其余转发，很容易漏写某个方法导致行为不一致。用嵌入（embedding）转发能自动解决。
  • 资源泄漏：装饰器持有底层对象，如果装饰器被 GC 而底层连接没关，连接会泄漏。要确保 Close 能穿透整条链（每层都实现 Close 并向下传递）。
  • 装饰器里吞掉错误：next() 返回的错误必须向上传递或明确处理，静默吞掉会让上层以为成功。
  • 性能被层层叠加吃掉：每层装饰器都有一次函数调用 + 可能的分配。高频路径上 5 层中间件可能带来 10~30% 的开销。要把最热的路径减少层数或合并。

第四层 · 原理与取舍

装饰器解决的是继承的组合爆炸问题：n 个可选功能用继承要 2ⁿ 个子类，用装饰器只要 n 个类。这是它存在的根本原因。

  • 代价一：类型被擦平。装饰后你拿到的是接口，不知道具体是哪几层。IDE 跳转、静态分析都会失效。这也是「调试地狱」的根源。
  • 代价二：调用链变长。每层一次函数调用，且因为是通过接口调用，编译器通常无法内联（虚调用）。高频路径上这是实打实的开销。
  • 代价三：顺序耦合。装饰器的正确性可能依赖顺序，而这个约束编译器无法检查，只能靠文档和约定。
  • 取舍原则：低频/高价值路径（HTTP 请求、RPC 调用）放心用装饰器，可读性和扩展性收益远大于开销；极高频的内层循环（每字节处理、每帧渲染）要谨慎，可能得用编译期组合（泛型、代码生成）替代。
装饰器和代理模式结构几乎一样，怎么区分？

看意图，不是看结构。装饰器是「我要给它加功能」——调用方通常知道目标对象存在，装饰是增强（如加缓存、加日志）。代理是「我要控制对它的访问」——调用方常常不知道自己在跟代理打交道，代理负责权限、懒加载、远程调用、引用计数。一个实用的判断：如果把这层去掉，功能是否受损？受损 → 装饰器（它真的加了东西）；只是少了控制（如不再鉴权）→ 代理。另外装饰器通常支持层层叠加，代理一般只有一层。实际代码中两者经常混用（如一个 HTTP 中间件既是装饰器又是代理），没必要强行区分——重要的是你清楚这一层在做什么。

装饰器能完全替代继承吗？

不能，两者解决不同问题。装饰器适合可选的、可组合的、运行时的增强；继承适合本质的、固定的「是什么」关系（Dog is an Animal）。用装饰器去表达「是一种」会很别扭（你得转发所有方法），用继承去表达「可插拔功能」会导致组合爆炸。现代设计的共识是「组合优于继承」，但这句话的准确含义是：对于「行为扩展」优先用组合，对于「类型分类」仍然用继承/接口。Go 干脆去掉了继承，只保留接口（表达是什么）和嵌入 + 组合（表达有什么行为）——这倒逼出了更清晰的设计。

中间件链的性能开销到底多大？

量化一下：每层中间件是一次通过接口的间接调用（无法内联）+ 一次闭包调用 + 可能的堆分配（闭包捕获变量）。单次开销约 10~50ns。所以：5 层中间件 ≈ 50~250ns。对比一次 HTTP 请求的实际处理时间（通常 1~10ms），中间件开销占比 <1%——完全可以忽略。但如果你在每秒千万次的内层循环里套 5 层装饰器，那 250ns × 千万 = 2.5 秒/秒，直接把 CPU 吃满。结论很清晰：请求级/连接级用装饰器毫无问题，指令级/每字节级要避免。这也是为什么 Go 的 io.Reader 装饰链在文件 IO 上很常见，但在极致性能的序列化库里会被刻意压平。
