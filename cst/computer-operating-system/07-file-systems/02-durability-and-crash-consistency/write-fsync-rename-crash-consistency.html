写文件、fsync 与 rename：断电后怎样避免半份配置

沿临时文件写入到目录替换的时间线，区分页缓存、原子可见性与持久化。

write 成功还不等于落盘

应用调用 write 后，数据可能只是进入操作系统页缓存；返回成功表示内核接受了这次写入，通常不等于存储设备已经在断电后可恢复。close 会释放句柄并可能触发写回或报告错误，但不能把 close 当成通用的持久化保证。若新配置覆盖旧文件时断电，可能留下零长度、半份或新旧元数据不一致的结果，具体取决于文件系统、挂载参数与硬件缓存。

要区分三件事：进程现在能读到新数据、其他进程通过某个路径原子地看见新版本、断电重启后新版本仍存在。write 主要影响可见内容；rename 可提供同一文件系统内路径切换的原子命名语义；fsync 等同步操作用于请求持久化。三者不能互相替代。

图解：发布一份配置文件的四个阶段

沿箭头逐步核对输入、变换和输出；下面的推演可以逐步切换。

一个安全更新的基本流程

先在目标文件同一目录创建唯一临时文件，完整写入新配置并校验长度与格式；然后对临时文件执行 fsync，让文件内容和必要元数据持久化；接着用 rename 把临时路径替换为目标路径，最后对父目录执行 fsync，持久化目录项的变化。若步骤失败，应停止发布并保留旧目标，按错误路径清理临时文件。临时文件放同目录有助于保证 rename 发生在同一文件系统内。

这个流程是常见的崩溃一致性模式，但具体保证依赖操作系统、文件系统、存储设备是否正确履行 flush，以及目标文件原有状态。数据库或关键账务文件还需要校验和、版本号与恢复日志。不要用“调用过 fsync 就绝对万无一失”取代故障测试。

逐步推演

写临时文件

新配置完整写入，不触碰旧目标。

fsync 临时文件

请求持久化文件内容和必要元数据。

rename 替换

同一文件系统内原子切换目标名字。

fsync 父目录

请求持久化新的目录项映射。

为什么还要同步父目录

对临时文件 fsync 主要保证文件数据与相应文件元数据；rename 改变的是目录中的名字映射。若只同步文件，不同步父目录，断电后目录项变更未必持久，重启后可能仍看到旧名字映射或需要文件系统恢复规则处理。对父目录 fsync 旨在明确请求持久化这次命名变化。不同平台是否支持对目录打开并同步、以及错误处理方式有差异，代码需按目标系统实现。

rename 的“原子”通常是指并发读者通过目标路径查找时不会看到只有半个文件名切换的状态；它不表示切换自动耐久。已打开旧文件的进程可继续读旧内容，新打开目标路径的进程读新内容；这也解释了为什么配置热加载需要重新打开路径。跨文件系统的“移动”往往退化为复制加删除，不能直接套用同一文件系统 rename 的原子性。

故障时点正式路径的预期额外痕迹
写临时文件中旧版可能残留临时文件
文件 fsync 后、rename 前旧版完整临时文件可能存在
rename 后、目录 fsync 前运行时新版断电后的目录变化未获明确持久保证
目录 fsync 成功后新版持久化证据更强仍受硬件与文件系统契约约束

崩溃时间线逐点看

临时文件写入一半时崩溃：旧目标应仍在，可能留下临时垃圾。文件 fsync 完成、rename 前崩溃：旧目标仍应作为正式路径，新临时文件可能留存。rename 已返回、目录尚未 fsync 时崩溃：运行中的读者已经能见新版本，但重启后的命名持久性不能仅由 rename 返回保证。目录 fsync 成功后，才有更明确的“新路径映射已请求持久化”证据。

异常路径也要认真处理：磁盘满可能在 write、fsync 或 close 才暴露；`write` 还可能短写，需要循环直至所有字节写完。文件权限、所有者、ACL 与扩展属性是否应继承旧文件，要在替换前明确设置；否则内容正确但权限变了，也是一种发布失败。

日志与数据库为何更复杂

仅替换整个小配置文件时，临时文件加原子替换相对直接。数据库同时更新多个页、索引和元数据，无法用一次 rename 原子替换整个数据目录；通常需要写前日志、校验和、提交记录与恢复流程。文件系统日志主要保护自身元数据或某些数据模式，不自动保证应用的多文件业务事务。应用应根据自己的不变量设计持久化协议。

对于追加日志，还需明确刷盘批次与“成功响应”的关系：若服务先回复成功、后异步 fsync，断电可能丢失已确认记录；若每条都 fsync，延迟和吞吐会受到影响。组提交能摊薄刷盘成本，但需要告知调用方保证边界。

怎么验证

用测试进程循环生成有版本号和校验和的配置，反复在不同步骤模拟进程崩溃，并在可控环境里做断电级故障注入。每次重启后只接受“完整旧版或完整新版”，拒绝半份内容。记录 write、fsync、rename 和目录 fsync 的错误码，确保调用链没有吞错。普通 kill 测试主要覆盖进程崩溃，不能完全模拟电源故障。

练习：临时文件已 fsync 且 rename 已成功返回，但父目录尚未 fsync。当前进程从目标路径读到新配置，是否足以证明断电后一定还是新版？请指出可见性与耐久性的不同。

系统调用语义与持久化边界

调用保证什么不保证什么典型延迟量级
write()数据进入页缓存，后续读可见不保证落盘，断电即丢亚微秒（仅内存拷贝）
fsync(fd)数据 + 元数据（大小、mtime）落盘不保证父目录项落盘NVMe 数十~数百 μs；机械盘 数 ms
fdatasync(fd)数据 + 影响读取的元数据落盘可能跳过 mtime/ctime 等通常比 fsync 略快
rename(a,b)同一文件系统内原子替换不保证替换结果已持久化本身只是元数据操作
fsync(dirfd)把目录项（新建/改名）落盘与文件数据无关同 fsync 量级
O_DIRECT绕过页缓存直写设备不等于持久化，仍需同步延迟更低但对齐要求 512B/4K

核心事实：write() 返回成功不代表数据能扛断电。只有 fsync 类调用返回后，数据才在持久介质上。

原子替换文件的标准配方

标准写法

// 正确顺序：写临时文件 -> 同步数据 -> 原子改名 -> 同步目录
int fd = open("data.json.tmp", O_WRONLY | O_CREAT | O_TRUNC, 0644);
write(fd, buf, len);
fsync(fd);                    // 1) 数据落盘（缺了它可能出现 0 长度或半截内容）
close(fd);
rename("data.json.tmp", "data.json");   // 2) 原子替换，读者只会看到旧版或新版
int dfd = open(".", O_RDONLY | O_DIRECTORY);
fsync(dfd);                   // 3) 把"改名"这件事本身持久化（缺了它可能回到旧文件）
close(dfd);
省略的步骤断电后可能出现的现象发生条件
不 fsync(fd)新文件存在但内容为 0 或半截页缓存未回写即断电
不 fsync(dirfd)回到旧文件（改名丢失）目录项元数据未落盘
直接覆盖写（无 tmp）读到新旧混合的内容写入过程中崩溃，无原子性保护
用 O_TRUNC 后写旧内容已清空、新内容未写入截断与写入之间崩溃
  • 顺序不能反：先 fsync 文件数据，再 rename，最后 fsync 目录；反过来无法保证。
  • ext4 的 auto_da_alloc 会在截断/覆盖场景替你补一次分配落盘，但它只覆盖部分情况，不能替代显式 fsync。
  • 日志模式影响：data=ordered（默认）保证数据先于元数据提交；data=writeback 更快但崩溃后可能出现旧数据块。

实测与排查命令

命令

# 看一个程序到底有没有真的 fsync（最常见的排查手段）
strace -f -e trace=fsync,fdatasync,sync,write,rename -p $PID
strace -f -e trace=fsync -o fsync.log ./your_program
grep -c fsync fsync.log

# 量化 fsync 延迟：单线程同步写，看第 99 百分位
fio --name=fsync --ioengine=sync --rw=write --bs=4k --size=8m \
    --fsync=1 --fdatasync=1 --runtime=30 --time_based --group_reporting

# 看文件系统挂载参数（是否 nobarrier / data=writeback）
mount | grep -E "ext4|xfs" ; tune2fs -l /dev/sdXN | grep -i "filesystem features"

# 断电演练（在虚拟机里）：写一半后强制关机，再挂载检查文件完整性
fsck -f /dev/sdXN
观测指标含义经验阈值
fsync p99 延迟单次同步写的最坏耗时NVMe 应 < 1 ms；机械盘 5~15 ms 属正常

%util设备忙碌比例接近 100% 且 await 高 = 真瓶颈

深入自检

write() 返回成功，数据就安全了吗？

不安全。write 只保证数据进入内核页缓存并对后续读可见，回写时机由内核决定（通常几十秒内）。断电或内核崩溃都会丢失。必须 fsync 后才算持久化。

为什么 rename 后还要 fsync 目录？

rename 修改的是父目录的目录项。文件数据落盘不代表“目录里已经指向新文件”这件事落盘。若目录项未持久化，重启后可能仍然指向旧文件——表现为更新“丢了”。

fdatasync 能完全替代 fsync 吗？

多数场景可以更快：它只保证数据以及读取所必需的元数据（如文件大小）落盘，可能不回写 mtime/ctime。但如果你依赖时间戳或某些元数据语义，仍要用 fsync。

数据库为什么普遍用 group commit？

因为每次 fsync 的成本固定（NVMe 数十 μs、机械盘数 ms），若每条事务都 fsync，吞吐会被 fsync 次数锁死。把多个事务合并为一次 fsync，能把每秒事务数提升一个数量级，代价是单事务延迟略增。

O_DIRECT 是不是就等于持久化？

不是。O_DIRECT 绕过页缓存直接提交 IO，但 IO 完成不等于写入持久介质（设备自身还有缓存），仍需要 fsync 或 O_DSYNC 之类手段确认落盘。

自检

rename 已返回且当前能读到新版，是否就保证断电重启后仍是新版？

不能。可见性与持久化不同；还需要按平台语义同步父目录并检查错误。
