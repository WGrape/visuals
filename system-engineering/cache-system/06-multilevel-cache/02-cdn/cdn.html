先建立直觉：连锁便利店的仓库体系

如果所有商品都存在唯一一个中心仓库（源站），全国各地的人下单都要等长途运输，慢且中心仓压力大。

连锁便利店的做法是：在每个城市开很多小店（CDN 边缘节点），热门商品预先铺货到各店。你楼下的店有货，下楼就拿；只有店里没有的，才从中心仓调货（回源）。

CDN 就是这个「前置铺货」体系，只不过铺的是图片、视频、JS/CSS、下载包这类静态内容。

一次 CDN 请求的完整流程

三个核心机制

① 调度：怎么知道哪个节点离我最近

用户访问 img.example.com 时，DNS 解析会被导向 CDN 的调度系统。调度系统根据用户 IP判断其地理位置与运营商，返回最合适的边缘节点 IP。

关键点：CDN 调度发生在 DNS 解析阶段，不是 HTTP 请求阶段。所以 CDN 加速的是「同一个域名」，用户无感知——他的浏览器只是解析到了一个不同的 IP。

② 缓存：边缘节点存什么、存多久

主要由 HTTP 缓存头控制：

响应头含义
Cache-Control: max-age=3600边缘节点缓存 3600 秒
Cache-Control: no-cache每次都要回源校验
Cache-Control: no-store完全不缓存
Expires过期时间点（HTTP/1.0 遗留）
ETag / Last-Modified用于回源时的条件请求校验
Vary按某个请求头（如 Accept-Encoding）分别缓存
最常见的配置错误：把动态页面（HTML、个性化接口）也设了长 max-age，导致用户看到别人或过期的个性化内容。原则：静态资源（带 hash 的 JS/CSS/图片）可长缓存；HTML 与个性化接口通常 no-cache 或很短。

③ 回源：边缘没有怎么办

边缘节点向源站拉取内容，缓存在本地后再返回给用户。回源的代价是这一次请求很慢（等于源站延迟 + 额外的转发），所以要尽量提高命中率。

CDN 能带来什么

收益说明
降低延迟用户从同城节点取数据，跨运营商、跨地域的往返被消除
降低源站压力绝大部分请求被边缘吸收，源站带宽大幅下降
提高可用性源站短暂故障时，边缘仍有缓存内容可返回
抗流量突发热点事件带来的流量尖峰被分散到全网节点
节省带宽成本边缘带宽通常比源站带宽便宜

它不适合什么

  • 动态、个性化内容：每人不同的页面无法在边缘缓存（可用「动态加速」优化链路，但原理不同）。
  • 强实时数据：股价、库存等要求秒级新鲜的内容。
  • 私有/敏感数据：需谨慎评估缓存到公网节点的风险。
一句话：CDN 的本质是用空间（大量边缘节点）换时间（低延迟）和带宽（低回源），适合访问量大、内容相对静态、对延迟敏感的资源。

🎯 面试问答

Q：CDN 和 Redis 这类缓存有什么区别？
A：两者都是「缓存」，但位置与目的完全不同：CDN 缓存在用户附近的边缘节点，存的是HTTP 响应（图片、JS、视频），目的是降低网络延迟、减少跨地域传输；Redis 缓存在服务端，存的是业务数据（对象、查询结果），目的是减少数据库压力。一个优化「网络距离」，一个优化「计算与存储压力」，通常同时使用。

Q：为什么改了源站图片，用户看到的还是旧的？
A：因为边缘节点还缓存着旧版本，在 TTL 到期前不会回源。解决办法有三种：① 主动刷新（CDN 控制台或 API 触发 purge，强制边缘失效）；② 文件名加 hash/版本号（如 logo.a1b2c3.png），内容变了文件名就变，天然绕过旧缓存——这是最推荐的做法；③ 缩短 TTL（牺牲命中率）。

Q：命中率多少算健康？
A：静态资源类业务通常要求90% 以上，理想能到 95%~99%。命中率低说明缓存策略有问题：可能是 TTL 太短、URL 带了随机参数（如 ?t=123）导致每次都是新 key、或者资源太分散（长尾内容多）。排查顺序：先看有没有随机参数，再看 TTL 配置，最后看内容分布。

Q：HTTPS 时代 CDN 还能缓存吗？
A：能，但需要把证书私钥交给 CDN 厂商（或在边缘做 TLS 终结）。因为 HTTPS 内容是加密的，CDN 必须能解密才能缓存和分发——这就是「CDN 托管证书」。这也意味着你需要信任 CDN 厂商，敏感业务要评估这一风险，或采用「不缓存 + 仅做链路加速」的模式。
