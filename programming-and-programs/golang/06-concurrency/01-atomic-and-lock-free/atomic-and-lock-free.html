基础原子读写

Add/Load/Store

对 int32/64、uintptr、指针等提供原子增减与读写；保证不会被并发打断或看到半写状态。

import "sync/atomic"
var cnt int64
atomic.AddInt64(&cnt, 1)     // 原子 +1
n := atomic.LoadInt64(&cnt)  // 原子读
atomic.StoreInt64(&cnt, 0)   // 原子写
CompareAndSwap（CAS）

乐观并发的基础

CAS 比较旧值，若相符则换新值并返回 true，否则返回 false。无锁算法（如无锁队列）的核心。

for {
    old := atomic.LoadInt64(&cnt)
    if atomic.CompareAndSwapInt64(&cnt, old, old+1) {
        break  // 成功更新
    }
    // 失败说明被别的 goroutine 改了，重试
}
atomic.Value

任意类型的原子容器

atomic.Value 可原子地存/取任意类型（一次确定类型后不可变类型），常用于配置热更新。

var cfg atomic.Value
cfg.Store(Config{Timeout: 30})
v := cfg.Load().(Config)   // 类型断言取回
原子 vs 互斥锁

各自适用

单个计数器/标志用原子更轻；涉及多个变量一致性的复合操作必须用锁。别用原子硬凑复杂逻辑。

场景推荐

count++ 看似一步，实际是「读—改—写」三步。没有保护时两个 goroutine 会互相覆盖。互斥锁能解决，但原子操作更轻：它由单条 CPU 指令完成，不涉及 goroutine 挂起。

sync/atomic 怎么用

import "sync/atomic" // Go 1.19+ 推荐的类型化写法 var count atomic.Int64 count.Add(1) count.Store(10) v := count.Load() old := count.Swap(20) ok := count.CompareAndSwap(20, 30) // CAS：期待 20 才改成 30 // 布尔标志 var closed atomic.Bool closed.CompareAndSwap(false, true) // 指针与任意值 var cfg atomic.Pointer[Config] cfg.Store(newConfig) // 发布新配置 c := cfg.Load() // 无锁读取 // 老式函数写法（仍然可用） var n int64 atomic.AddInt64(&n, 1) atomic.LoadInt64(&n)
类型用途说明
atomic.Int64/Int32计数器、序号生成Add/Load/Store/Swap/CAS
atomic.Uint64/Uint32无符号计数同左
atomic.Bool状态开关、只执行一次CAS 保证只翻转一次
atomic.Pointer[T]无锁发布配置或数据结构读无锁，写用整块替换
atomic.Value泛型前的任意值容器类型必须一致，不可变对象
atomic.Int64 对齐结构体中放第一个字段保证 32 位平台上 8 字节对齐

对齐坑：在 32 位平台上做 64 位原子操作要求地址 8 字节对齐。把 64 位原子字段放在结构体第一个字段，或使用标准库类型，可避免这个问题。

CAS、ABA 与「无锁」的真实含义

CAS 循环

无锁算法的标准写法：读—算—尝试提交，失败重试。

func Inc(v *atomic.Int64) { for { old := v.Load() if v.CompareAndSwap(old, old+1) { return } // 被别人抢先了，重新读再试 } } // 关键：重试时重新 Load，不能用上一次的旧值

ABA 问题

值从 A 变成 B 又变回 A，CAS 会误以为没变过。

  • 简单计数器场景无所谓
  • 涉及指针复用与内存回收时要警惕
  • Go 有 GC，对象不会在被引用时释放，风险较低
  • 需要严格保证时加版本号（把计数与值打包）

无锁不等于更快

  • 高竞争下 CAS 会反复重试，反而更慢
  • 只保护一两个变量时原子更快
  • 临界区复杂时锁更简单也更可靠
  • 先写正确的锁版本，测出瓶颈再换

原子 vs 锁 vs channel 怎么选

场景选择理由
单个计数器 / 标志位atomic最轻，无挂起开销
保护一组字段的一致性mutex原子无法保证多字段同时更新
临界区含 I/O 或复杂逻辑mutexCAS 重试会浪费大量 CPU
传递所有权或协调流程channel语义清晰，天然可取消
配置热更新（读多写少）atomic.Pointer读无锁，写时整块替换
需要等待某个条件channel 或 Cond原子只能自旋，浪费 CPU
别用原子炫技可读性差且容易写错
先锁后优化锁是正确性的基线
atomic 不保护临界区它只保证单次读写的原子性
读写锁要分场景读远多于写时 RWMutex 才划算
注意伪共享高频写的相邻字段会互相拖慢
用 -race 验证原子与锁混用最容易出错

深入自检

原子操作为什么比锁快？

它通常由一条 CPU 指令完成，不需要进入内核、不涉及 goroutine 挂起与唤醒。锁在竞争时要让出 P、排队、再被唤醒，开销高一个数量级。但低竞争下现代互斥锁也很快，差距没那么夸张。

有了原子操作还需要锁吗？

需要。原子只保证「单个值的单次读改写」不可分割，无法保护「多个字段必须一起更新」的不变式，也无法保护一段包含 I/O 的临界区。这类场景只能靠锁。

Go 的原子操作是什么内存序？

Go 的文档保证 sync/atomic 的操作是顺序一致的（sequentially consistent），不提供 Relaxed/Acquire/Release 这类细粒度内存序选项。这降低了出错概率，也牺牲了一部分极致性能。

atomic.Value 有什么坑？

它要求前后存入的值类型必须完全一致，否则 panic；并且应当存入不可变对象——存进去后又修改其字段，会产生数据竞争。典型的正确用法是整块替换（copy-on-write）。

什么时候该放弃无锁改用锁？

当你要保护的状态变复杂（多个字段、有中间状态、需要等待条件），或者压测显示 CAS 重试率很高时。无锁的优势在简单状态与中低竞争，复杂场景下锁的正确性成本更低。
