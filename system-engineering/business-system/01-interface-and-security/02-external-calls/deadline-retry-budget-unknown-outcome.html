外部 API 超时与重试预算：请求没回复，操作到底成功了吗

沿一次订单提交拆分总截止时间、各跳超时、退避抖动、幂等键和未知结果查询。

超时只说明没有按时看到结果

客户端调用第三方“创建订单”接口，等待 800 毫秒后超时。可能请求根本没离开本机，也可能服务端已经提交订单、响应在回程丢失；调用方无法仅凭超时判断“未执行”。如果立刻换一个订单号再重试，就可能创建两笔。HTTP 连接中断、网关 504、读超时等错误应保留观察点和阶段：连接前失败与请求已发出后的结果不确定性不同，但都需要业务层明确恢复策略。

为可重复操作传稳定的幂等键，服务端把键、请求参数摘要和最终结果持久化；同一键相同参数重放时返回原结果，同一键换了金额等关键参数应拒绝。幂等键不能只存在短时本地缓存里，否则服务重启或跨实例重试会失效。具体保留时长要覆盖客户端最长重试和结果查询窗口。

图解：订单创建超时后的判断

沿箭头逐步核对输入、变换和输出；下面的推演可以逐步切换。

从总截止时间倒推每一跳

设用户接口最多允许 2 秒。入口验证和路由预留 100 毫秒，数据库本地处理预留 250 毫秒，响应网络与收尾预留 150 毫秒，留给第三方尝试与等待的总预算最多 1.5 秒。若单次外部调用就设 2 秒，再叠加三次重试，用户请求可能拖到 6 秒以上，违背总约定。应把同一个绝对截止时间或剩余预算向下游传播，并在每次重试前检查还剩多少。

连接超时、TLS 握手、等待响应和读取正文可设不同阶段限制，但不能简单把每项上限相加成无限长的整体等待。代理、SDK 和应用可能各自重试，若三层都重试 3 次，最坏情况下会放大到 27 次下游请求。设计时标明哪一层拥有重试权，其他层只传播错误和截止时间。

逐步推演

设置总期限

用户接口最多 2 秒，向下游传剩余预算。

稳定幂等键

同一订单同一键，同一参数才能重放。

超时标未知

响应没回来时查询权威状态，不直接判失败。

受控恢复

退避加抖动，限次数并监测积压。

退避和随机抖动为什么要一起用

故障发生后，一万客户端同时在 1、2、4 秒整重试，即使用指数退避，仍会形成同步尖峰。给等待加入随机抖动，可以把请求散开；同时设置最大尝试次数和总重试预算，避免持续占满线程、连接池与下游配额。若收到明确的限流响应及 Retry-After 等提示，应按接口契约处理，不要比服务端要求更早重试。

重试只适合暂时性错误且操作具备可重复语义。400 类参数错误通常需要修正输入；认证失败应刷新或修复凭据；目标明确拒绝且不可恢复时不应自动重试。即使是 500，写操作也可能已经生效，仍要用幂等键或查询接口兜底。

观察到的情况能确认什么下一步
连接前被拒本次可能未送达目标按错误类型和剩余预算处理
请求后读超时结果未知用同一幂等键查询或受控重试
明确终态响应目标报告成功或失败持久化结果并向用户展示
重复回调可能是投递重试按事件 ID 与业务单号去重

状态机处理未知结果

本地订单可有 INIT、SUBMITTING、UNKNOWN、SUCCESS、FAILED 等状态。发出第三方请求后若超时，先记录 UNKNOWN，并用原幂等键查询或重试同一操作；拿到权威终态才转 SUCCESS 或 FAILED。不要把“超时”直接标成 FAILED，因为下游可能已成功；也不要在 UNKNOWN 状态再次生成新的业务单号。异步回调、主动查询和对账可能同时到达，需要按版本或事务约束只允许合法状态转移。

结果查询接口如果也超时，可以稍后异步补偿，给用户展示“处理中”。前端应允许刷新后看到同一订单的最新状态，而不是重新提交。对于不可幂等的第三方接口，调用方要与供应商约定去重标识或人工核查流程，不能凭网络层重试“保证一次”。

故障放大算例

假设下游正常每秒处理 1000 次请求，入口每秒来 800 次。故障时 20% 请求超时，若每个超时都立即重试两次，粗略新增 320 次/秒，合计可能超过容量；下游更慢又触发更多超时，形成正反馈。真实概率与重试到达分布更复杂，但这个算例说明容量应覆盖故障路径。限流、熔断和排队上限可保护系统，但不能替代调用方处理未知结果。

服务恢复时若所有客户端一起放出积压，还会出现第二波冲击。恢复策略要观察下游成功率、在途请求数、等待队列和重试比例，逐步释放流量。

怎样验收

在调用前、写入后回包前、回包途中分别注入故障，观察是否只生成一个业务订单。记录统一 trace ID、幂等键、总截止时间、每次尝试序号、下游请求 ID 和最终状态。检查客户端取消后下游是否仍执行，若已执行如何把结果交付给用户。再测供应商返回 429、500、慢响应和半开连接时，整体耗时是否仍守住 2 秒用户预算。

最终指标应区分用户可见成功率、下游单次尝试成功率、平均重试次数、UNKNOWN 积压年龄和重复操作阻断次数。单次调用成功率下降不等于用户业务失败，反之“SDK 自动重试后成功”也可能藏着重复副作用。

自检

第三方写接口在回包途中超时，调用方能否直接认定操作失败并换新单号重试？

不能。操作可能已提交，应保留原业务标识和幂等键，查询或重试同一操作直到得到权威结果。
