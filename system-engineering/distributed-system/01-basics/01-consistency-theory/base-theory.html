BASE 理论

BASE 是 CAP 中放弃强一致（C）、换取可用（A）时的设计哲学。它告诉工程师：别追求每时每刻都一致，只要"最终一致"就行。大型互联网系统的标配思想。

BASE vs ACID/CAP 三要素 最终一致 柔性事务 实战示例 面试要点

⚖️BASE 与 ACID / CAP 的关系

ACID 追求强一致（银行转账），BASE 接受弱一致（社交动态）。CAP 说分区时只能选 C 或 A——BASE 就是"选 A 后如何把一致性补回来"的方法论。

理论立场典型场景
ACID强一致、事务严格银行核心、账目
CAP分区下 C 与 A 二选一（P 必选）理论框架
BASE舍强一致换可用，最终一致电商、社交、缓存
🧭
记忆：BASE 不是"不要一致性"，而是"不要求实时一致，但保证最终会一致"。它是分布式的"务实主义"。

🧩BASE 三要素

① BA — Basically Available（基本可用）
系统出现故障时，允许降级而非全挂。例如：响应变慢（限流）、返回兜底数据（缓存页）、部分功能不可用（只展示核心链路）。可用性优先于完美。
② S — Soft State（软状态）
允许系统中间状态存在且不立即一致。比如"订单处理中""余额同步中"——这些数据暂时不一致是被允许的，只要最终对齐。
③ E — Eventually Consistent（最终一致）
经过一小段时间（秒级/分钟级）后，所有副本数据会达到一致。这是 BASE 的落脚点，也是"柔性"能成立的底气。
✅
一句话：基本可用（不崩）+ 软状态（允许中间不一致）+ 最终一致（迟早对齐）。三者合起来，就是"柔性事务"的骨架。

🔄最终一致性（五档强度）

"最终一致"不是一刀切，按"用户何时看到一致"分强弱。

类型说明例子
因果一致有因果关系的操作顺序被保留评论→回复，回复不会早于评论显示
读己之写自己改完立刻能读到自己的新值改完昵称刷新能看到
会话一致同一会话内读己之写一次登录会话里保持一致
单调读不会读到比之前更旧的数据翻页不会看到"倒退"的旧内容
单调写同一客户端的写按序执行写操作不乱序
🎚️
选型：不是所有业务都要"读己之写"。像"朋友圈点赞数"用最弱的最终一致即可；"账户余额"则要有更强保证（甚至走强一致/对账）。

💡柔性事务：BASE 的工程实现

分布式事务很难做 2PC（阻塞、单点），工业界多用"柔性事务"替代强一致事务。

常用模式：
TCC（Try-Confirm-Cancel）：预留资源→确认/补偿，业务侵入大但可控。
消息队列最终一致：本地事务写业务+发消息，下游消费补偿，最常用。
Saga：长事务拆成一系列本地事务，失败则反向补偿。
最大努力通知：尽最大努力把结果通知对方，允许重试直到成功。
🧩
与事务章节呼应：严格的 2PC/3PC 见 transaction/ 目录；BASE 下的柔性事务是"放弃强一致、换可用与性能"的务实选择。

🛒实战示例：电商下单

✅
这就是 BASE：用户下单基本可用（立即返回成功）；系统处于软状态（库存/积分短暂未更新）；通过 MQ 异步处理实现最终一致（几秒内全部对齐）。

🎯面试要点速记

定位：BASE 是 CAP 中"选可用(A)"后的设计理论，放弃强一致、追求最终一致。
三要素：BA 基本可用 + S 软状态 + E 最终一致。
最终一致分级：因果/读己之写/会话/单调读/单调写，按需选强度。
柔性事务：TCC / 消息最终一致 / Saga / 最大努力通知。
对比 ACID：ACID 强一致难扩展，BASE 弱一致易扩展，按需取舍。
适用：电商、社交、缓存等"不怕短暂不一致"的场景。
🔥
必考题："BASE 和 ACID 怎么选？"——核心链路（钱、账）用 ACID/强一致；非核心/高并发（点赞、动态、积分）用 BASE/最终一致。几乎所有大厂都是"混合架构"。

ACID 与 BASE 逐项对照（记住这张表）

维度ACID（强一致）BASE（最终一致）

BASE 三个词拆开看：BA Basically Available（基本可用——允许降级，比如大促时关闭评论）；S Soft state（软状态——副本间允许中间态存在，不要求时刻同步）；E Eventual consistency（最终一致——停止写入后，所有副本终会收敛到同一值）。

最终一致到底“最终”是多久？——可量化的收敛窗口

“最终”不是玄学，工程上必须给出数字并写进 SLA。下面是一线系统的真实量级：

场景典型收敛时间决定因素
同机房 MySQL 主从（ROW binlog）10 – 100 msbinlog 落盘 + 网络 RTT
跨地域主从（如北京↻上海）0.5 – 3 s专线 RTT（约 25 – 40 ms）+ 复制线程
数据库 → 缓存（Canal 订阅 binlog）50 – 500 msCanal 轮询间隔 + 消费端批量
Kafka 消费者追平积压取决于 laglag / 消费速率，可能几分钟到几小时
DNS 记录变更TTL（常见 300 s）递归服务器缓存 TTL
CDN 边缘缓存刷新几分钟边缘节点数量 + 刷新 API 排队

实测收敛窗口

# 用 Canal 做 DB→缓存同步时，直接量出收敛延迟
# ① 写一条带时间戳的探针记录
mysql -e "UPDATE probe SET ts=NOW(6) WHERE id=1;"

# ② 立刻在缓存侧轮询，直到读到新值（单位 ms）
for i in $(seq 1 100); do
  v=$(redis-cli --raw GET probe:1:ts)
  [ -n "$v" ] && echo "第 ${i} 次轮询命中: $v" && break
  sleep 0.01
done

# ③ MySQL 侧看复制延迟（Seconds_Behind_Master 是最常用的指标）
mysql -e "SHOW SLAVE STATUS\G" | grep -E "Seconds_Behind_Master|SQL_Delay"

# 注意：Seconds_Behind_Master=0 不代表真的没延迟
# 大事务执行中它会一直是 0，直到事务提交才跳变
# 更可靠的是对比主从的 GTID 或 binlog 位点

经验值：同机房 <100 ms、跨地域 <3 s。超过这个数就该告警，而不是等用户来报 bug。

收敛冲突怎么解？（最终一致绕不开的问题）

策略做法代价 / 坑
LWW 最后写入胜出比较时间戳，大的赢时钟漂移会“吃掉”有效写入；需 NTP 校时
向量时钟每个节点维护版本向量能检出真并发冲突，但向量随节点数膨胀
CRDT数据结构本身保证可交换/可结合无冲突自动合并，但只能表达有限类型（计数器、集合）
业务侧对账定时任务比对 + 人工/自动补偿最笨但最可靠，金融场景必备
版本号 + 乐观锁WHERE version = ?冲突时报错重试，简单直观

工程上最常见的是 LWW + 定时对账兜底：LWW 解决 99.9% 的情况，剩下 0.1% 靠对账脚本在 T+1 修。

Dynamo 的 N / R / W 旋钮（BASE 的可调一致性）

Amazon Dynamo 论文给出的经典配置：N=3, W=2, R=2。含义是 3 副本、写成功 2 份才算成功、读要读 2 份取新值。

  • R + W > N → 读写集合必然相交，能读到最新值（强一致读）
  • R + W ≤ N → 可能读到旧副本（最终一致读，延迟更低）
  • N=3, W=1, R=1：写入最快、可用性最高，但可能读到旧值
  • N=3, W=3, R=1：写慢但读一定新，适合写少读多
  • N=3, W=1, R=3：写入即返回，读时修复，适合写多读少

会话一致性保证（Doug Terry 1994 提出的四种，做产品时非常实用）：读己之写（我改完一定能看到自己改的）、单调读（不会看到数据往回跳）、单调写（我的写入按序生效）、写跟随读（我读到的版本之后的写才生效）。做到前两条，用户基本感知不到“最终一致”的存在。

深入自检

BASE 是不是就是“放弃一致性”？

不是。BASE 放弃的是任意时刻的强一致，换来的是可用性与分区容错。它仍然保证“停止写入后必然收敛”，并且通常要配会话保证（读己之写）来消除用户可感知的异常。真正“放弃一致性”的系统是不做收敛的，那叫 bug 不叫 BASE。

为什么金融场景不能用 BASE？

因为 BASE 的不一致窗口内，可能出现超额扣款（两次消费都读到旧余额）。但也没有那么绝对：银行核心用 ACID，而对账、清分、报表这些链路大量使用 BASE——因为它们允许 T+1 收敛。判断标准是：不一致会不会造成不可逆的资金损失。

最终一致下，“删除”为什么特别难？

因为删除会和并发的写入打架：你删了 A，另一个副本还在写入 A 的新版本，收敛时 LWW 可能让被删的数据复活。标准解法是墓碑（tombstone）：删除不真删，写一个带删除标记的版本，墓碑保留期（常见 3 – 10 天，Cassandra 默认 gc_grace_seconds = 864000 秒 = 10 天）后才真正回收。

软状态（Soft state）和缓存有什么区别？

缓存是性能优化，丢了可以从源头重建；软状态是系统模型的一部分，它的值在没有新输入时也可能变化（因为异步复制在推进）。判断方法：把这份数据清空，系统还能不能正确工作？能 → 是缓存；不能 → 是软状态。
