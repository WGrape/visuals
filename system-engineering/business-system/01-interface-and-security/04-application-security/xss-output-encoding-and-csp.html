XSS 防线：上下文编码、富文本净化与 CSP

一条用户评论从数据库到页面，什么时候是文本、什么时候会被浏览器解释成代码？

XSS 的核心是数据进入了可执行上下文

用户评论可以存入数据库，也能从接口读回；危险发生在模板或前端把它放进 HTML、属性、URL 或脚本位置时，没有按目标上下文正确处理。存储型、反射型和 DOM 型 XSS 的入口不同，共同点都是不可信数据跨过“文本 → 浏览器可解释代码”的边界。后端输入校验有助于业务格式，但不能靠“所有地方统一过滤尖括号”解决各种输出上下文。

系统应尽量用模板的自动转义和 DOM 的安全文本 API；需要渲染富文本时，使用可信、明确允许元素/属性的净化器，并避免不可信 HTML 直接进入可执行位置。CSP 是减轻漏网情形的纵深防护，不能替代安全输出。

图解：同一条评论的不同出口

CSP 能限制脚本执行来源，却不能修复业务页面显示错误、授权漏洞或被不可信脚本滥用的合法权限。先把数据安全地放进页面，再增加防御纵深。

逐步推演：评论显示与富文本

服务端保存业务上允许的内容

限制长度与字段类型可保护业务，但不要在入库时做一次“通用 HTML 转义”就宣称所有未来页面安全：同一数据将来可能出现在属性、URL 或 JSON 中。

文本位置交给模板/DOM 安全 API

服务端模板使用默认自动转义，前端用 textContent 设置纯文本，不用拼接 innerHTML。输出编码发生在最了解目标上下文的一端。

富文本只有明确允许的 HTML 子集

若业务允许加粗/链接，先经可信净化器处理允许元素与属性，校验链接方案；净化后尽量不再次拼接未净化片段。新语法、新浏览器行为意味着需要持续维护净化规则。

限制脚本执行能力

部署非宽松 CSP（如对受信任脚本使用每响应 nonce 或哈希），观察报告模式结果再收紧；避免轻易加入 unsafe-inline。CSP 配置应与页面真实资源和第三方依赖匹配。

第一层 · 输出上下文不能共用一种“转义”

数据出现位置推荐方法不能照搬的做法
HTML 文本节点模板自动 HTML 编码或 DOM textContent把文本拼进 innerHTML
HTML 属性模板属性上下文编码，属性始终加引号把仅做 HTML 文本编码的值直接拼成属性
链接 URL允许列表限定协议/目的地，再做 URL 与属性处理认为“URL 编码过”就能接受任意方案
JavaScript / JSON优先放独立 JSON 响应或安全数据节点，使用正确序列化把用户串直接插入内联脚本
允许 HTML 的富文本维护可信净化器的元素/属性允许列表正则替换标签或允许任意事件属性

第二层 · 安全 API 与策略示意

// 纯文本评论：不把它解释成 HTML
commentElement.textContent = response.commentText;

// 如果业务必须支持富文本：采用持续维护的可信净化器
// cleanedHtml = trustedSanitizer.sanitize(response.richText, allowedPolicy)
// 输出到明确支持受控 HTML 的组件，并对 URL 属性再做方案校验

CSP 可先用报告模式观察被拦资源，再逐步限制脚本来源、移除不必要的内联脚本；每次响应 nonce 应不可预测且只适用于该响应。若使用 Trusted Types，可帮助限制危险 DOM sink，但它不是自动净化所有输入的替代品。

第三层 · 常见混淆与排障

  • HttpOnly 并不能消灭 XSS：脚本可能读不到 Cookie，但仍能在用户浏览器里发起带凭证的同源操作；必须处理内容注入根因。
  • CSRF 不等于 XSS：CSRF 利用浏览器自动带凭证的跨站请求，防护依赖 SameSite、令牌、Origin 等组合；XSS 是不可信代码进入受信任页面。详情见已有的 Cookie/CSRF 课程。
  • CORS 不等于授权：CORS 控制浏览器能否读取跨源响应，不会替服务端验证用户或订单归属；详情见 CORS 课程。
  • CSP 报告有噪声：先区分真正业务脚本、扩展注入和意外内联依赖，不能因为出现告警就给所有来源开通配。

第四层 · 原理与取舍

为什么不能“入库时统一转义一次”？

输出可能是 HTML 文本、属性、URL 或 JSON，各自编码规则不同；入库一次性转义会误伤合法内容，也可能在其他上下文失效。原始数据的业务校验与输出时的上下文编码是不同职责。

CSP 配好了，是否可以继续使用任意 innerHTML？

不能。CSP 是纵深防护，配置也可能随需求放宽或出现兼容问题。危险 DOM sink 的风险应在数据进入前由安全 API/净化器处理。

前端 React/Vue 自动转义，后端是不是不用管了？

框架默认文本插值通常有保护，但原始 HTML 渲染、模板例外、脚本拼接、富文本、邮件/导出页面仍需按实际输出上下文处理；后端也应确保业务输入与敏感字段的边界。

自检

评论用 textContent 显示安全，但同一字段拼进 href 属性，还能复用之前的结论吗？

不能。URL 除上下文编码还要校验允许的协议/目的地；不同输出位置需要重新做边界判断。

练习：指出评论正文、用户头像 URL、富文本内容三种出口各自需要的处理方式，以及 CSP 应站在哪一层。
