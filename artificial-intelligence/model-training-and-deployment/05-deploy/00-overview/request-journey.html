一次请求的完整旅程

你在对话框里敲下一句话、按下回车。几百毫秒后，字一个一个地冒出来。中间发生的事，远不止「把文字发给一个大模型」——你的请求会经历 路由 → 集群排队 → 批处理调度 → 逐 token 推理 → 结果缓存 五个环节。这一页把五步串成一条线，每一步再指向专门讲透它的那一篇。

01一台巨大的计算机？

先看几个很容易被忽略的事实：

  • 同一时刻，可能有数百万用户在跟同一个模型对话。
  • 智能体（Agent）是异步、长时运行的：你睡觉的时候，它还在反复调工具、读结果、继续推理。
  • 模型的权重是静态的一份，但每个用户请求要走的路不同、上下文不同、长度不同。

于是问题变成：一份固定的权重，怎么同时服务几百万个互不相同的请求？

答案不是「一台更快的机器」，而是一整套系统：把请求分派到合适的地方、把零散的请求攒成批、把重复的计算复用起来。这不是模型本身的算法问题，而是系统工程问题。这也是为什么同一份开源权重，在不同团队手里能差出 5~10 倍的成本。

为什么这一章放在「部署」而不是「模型」？因为从按下回车到看到第一个字，绝大部分时间既不在 attention 里、也不在采样里，而在排队、调度、数据搬运和重复计算上。理解这条链路，才知道优化该从哪里下手。

03第 01 步 · 请求路由：决定去哪

请求先进边缘节点 / API 网关，在这里完成鉴权、配额、协议转换（把 HTTP 请求变成流式 SSE），然后交给负载均衡器挑一个后端节点。

普通 Web 服务里，这一步简单到可以「轮询」。但 LLM 服务不行，原因只有一个：后端副本之间并不等价。

  • 显存占用不同：有的副本已经跑了 20 个长请求，KV Cache 快满了，再接就 OOM。
  • 缓存命中不同：同一个 system prompt 的请求打到上次那个副本，前缀 KV 能直接复用；打到别的副本就要从头 prefill。
  • 模型版本不同：灰度期间新旧版本共存，路由要按比例切流。

所以这里真正要看的是「队列深度 + KV 占用 + 前缀亲和」，而不是 CPU 利用率或简单轮询。细节全部在 请求入口与路由。

常见误区：以为「加个 Nginx 就完事了」。事实上 LLM 网关最难的从来不是转发性能，而是路由决策——选错副本会让 TTFT 从 300ms 变成 3s，也可能让本该命中的缓存全部失效。

04第 02 步 · GPU 集群：算力从哪来

路由选中的是一个服务副本，而每个副本可能占一张或多张 GPU。把规模拉起来，就是图中的「1024 个加速器」——它不是一个模型摊在 1024 张卡上（那是训练的思路），而是几十上百个副本，每个副本独立服务一批请求。

这里有个绕不开的现实：请求到达是不均匀的。图上那串时间戳很典型——

请求 #8,214   +0 ms
请求 #8,215   +12 ms
请求 #8,216   +31 ms
请求 #8,217   +47 ms
请求 #8,218   +63 ms
... 后面还有成千上万个

毫秒级连发意味着什么？意味着同一瞬间有大批请求同时要算力，而 30 秒后可能一个都没有。这种突发（burst）+ 潮汐（白天高、深夜低）+ 长尾（少数超长请求）的组合，正是 GPU 集群必须解决的调度问题。

一个反直觉的数字：扩容看起来是「加机器」，实际难点是冷启动——加载 70B 模型要几分钟（140GB 权重从存储搬到显存），再加编译与预热、健康检查，一个自动扩容从触发到真正能扛流量可能要 5~15 分钟。而流量洪峰往往只持续 2 分钟。所以「提前预留水位」比「事后扩容」重要得多。

05第 03 步 · 调度与批处理：决定什么时候算

请求进来后先进请求队列，调度器再从队列里取出若干请求，攒成一个批次一起送进 GPU。这一步是整条链路里性价比最高的优化点。

原因是 GPU 的天性：它擅长「一次对很多数据做同样的运算」。如果一个请求一个请求地算，GPU 的大部分单元都在空转。

批处理不是没有代价：攒批会让先到的请求多等一会儿，也就是 TTFT 变长。所以「批多大」本质上是在吞吐和延迟之间调平衡，而不是越大越好。这条取舍曲线的量化方法见 推理指标与成本，机制细节见 模型服务与部署。

06第 04 步 · 模型推理：真正产出 token

进入模型后有两个阶段，性格完全不同：

阶段做什么瓶颈受什么影响
prefill把整段 prompt 一次性算完，得到 KV Cache算力密集prompt 长度、上下文总长
decode每步只生成 1 个 token，再把它喂回去访存密集（要把全部权重读一遍）模型大小、显存带宽、batch 大小

这解释了两件常被问到的事：

  • 为什么输出比输入慢得多？输入是并行的（一次算完），输出是串行的（一个一个来）。200 个 token 的输出意味着 200 次完整的前向。
  • 为什么长 prompt 只是「慢一点」而长输出是「慢很多」？因为 prefill 可并行，decode 不可。

于是优化方向也就分岔了：prefill 优化看前缀缓存 + chunked prefill，decode 优化看量化 + 投机解码 + 增大 batch。深入：推理加速、投机解码。

07第 05 步 · 缓存：不要重复做已做过的工作

这是最容易被低估、收益又最直接的一步。真实流量里重复度高得惊人：同一段 system prompt、同一套 few-shot 示例、同一个用户的多轮对话——这些前缀每次都要重新 prefill 一遍，纯属浪费。

工程上有四层缓存，越往下越省算力、也越难做对：

L1结果缓存

请求完全相同（或标点归一后相同），直接返回上次的回答。最简单，命中率也最低。

L2语义缓存

用向量检索判断「问的是不是同一件事」，复用答案。收益高但风险也高——差一点点的问法可能答案完全不同。

L3前缀缓存

相同前缀的 KV 直接复用，跳过这段 prefill。性价比最高的一层，vLLM 的 --enable-prefix-caching 就是它。

L4KV Cache 本身

不是「缓存优化」，而是 decode 能跑起来的前提。显存不够时它才是第一瓶颈。

那个「840ms → 190ms」就是这么来的：同一段上下文第二次来时，不是模型变快了，而是有 4 倍的工作根本不用做了。

别混淆：「缓存」在 LLM 语境里至少指四种东西（结果、语义、前缀 KV、KV Cache 本体）。混着说会导致完全错误的容量规划——比如以为开了 prefix caching 就能省显存，实际它要占更多显存（存的是 KV，不是省掉 KV）。详见 KV Cache 与推理显存。

08放大来看：8,412 个请求同时在跑

把镜头拉远，你看到的不是一条流水线，而是成千上万条流水线并行运转：有人问天气，有人让写代码，有人上传了 3 万字文档要总结。每个请求的输入输出都不同，但都能被同一批 GPU 消化掉。

这背后有个关键设计：服务进程必须是无状态的。请求可以被路由到任何副本，中途失败可以被重试——

  • 「状态」被外置成了 KV Cache（临时、可丢弃）、会话历史（存在外部存储）、结果缓存（独立服务）。
  • 代价也很真实：KV Cache 让「无状态」变成了「半有状态」，于是路由要考虑亲和性、扩容要迁移缓存、缩容要等在飞请求跑完。这是 LLM 服务比普通 Web 服务复杂得多的根因。

09一次请求的时间账

把五步折算成时间，你会发现优化优先级和直觉不同：

总延迟 ≈ 网络往返        （20~80 ms）
       + 排队等待        （0 ~ 数秒，取决于负载与批策略）  ← 最不可控
       + prefill        （prompt_len 决定，长 prompt 可到秒级）
       + decode × N     （每 token 20~50 ms × 输出长度）   ← 通常是大头
       + 后处理/流式传输  （几 ms 到几十 ms）

例：TTFT 300ms + TPOT 40ms × 200 token ≈ 8.3 s
为什么"感觉快"？因为流式输出：第一个字 300ms 就出现了，
后面每个字 40ms，用户读到第 10 个字时你还在生成第 15 个。

三个立刻可用的结论：

  1. TTFT 由「排队 + prefill」主导，所以改善首字体验优先做前缀缓存、减少 prompt、控制队列。
  2. 总时长由 decode 主导，所以改善完整体验优先做量化、投机解码、限制输出长度。
  3. 排队是最不可控的一项，因为它由别人（同时段的流量）决定——这就是为什么要有弹性和调度。

回到开头那个问题。让几百万个请求同时得到回答的，不是某个神奇的算法，而是五个环节协同工作：

把这一页当成地图：遇到「首字慢」先看路由与排队，遇到「算力不够」先看集群与弹性，遇到「成本高」先看缓存与批处理。顺着链路找瓶颈，而不是一上来就换更大的模型。
