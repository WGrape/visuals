①LIKE：唯一标准化的匹配方式

LIKE 是 SQL 标准里唯一的字符串模式匹配。两个通配符：% 匹配任意长度（含零）， _ 匹配恰好一个字符。

模式含义能走 B+Tree 索引？
'abc%'以 abc 开头✓ 可转范围扫描
'%abc'以 abc 结尾✗
'%abc%'包含 abc✗
'a_c'a 开头 c 结尾共 3 字符△ 前缀部分可用
B+Tree 只能按「有序前缀」定位，前导通配符破坏了有序性
转义问题：要匹配字面量的 % 或 _ 必须用 ESCAPE 子句，如 LIKE '100\%%' ESCAPE '\'。 更根本的建议是：用户输入直接拼进 LIKE 就是注入风险，参数化查询是底线。

②大小写敏感与排序规则

LIKE 是否区分大小写，不取决于 LIKE，而取决于列的排序规则（collation）。 以 _ci 结尾（case insensitive）的不区分，_bin / _cs 区分。

数据库默认行为显式控制
MySQL（utf8mb4_general_ci / 0900_ai_ci）不区分用 _bin 排序规则或 LIKE BINARY
PostgreSQL区分（LIKE）ILIKE 不区分；citext 扩展
SQL Server取决于排序规则列定义或 COLLATE 子句
Oracle区分UPPER(col) LIKE UPPER(?)（会失索引，需函数索引）
大小写不敏感查询 + 索引：用 UPPER(col) = ? 会让索引失效， 正确做法是建函数索引 / 表达式索引（CREATE INDEX ON t (UPPER(col))）， 或干脆把列设成不区分大小写的排序规则。

③正则表达式

各库都提供正则匹配，但函数名与语法不统一，且都不走普通索引。

数据库语法说明
MySQL 8col REGEXP 'pattern' / REGEXP_LIKE(col, pat)ICU 正则，8.0 起支持
PostgreSQLcol ~ 'pat'（区分）/ ~*（不区分）POSIX 正则
OracleREGEXP_LIKE(col, 'pat')还有 REGEXP_SUBSTR/REPLACE
SQLite需加载扩展默认无内置
正则在数据库里是性能杀手：逐行回溯匹配、无法用索引、无法估算选择率。 数据量超过万行且需要在线响应时，应把这类匹配放到应用侧或搜索引擎。 数据库里的正则更适合数据清洗、一次性校验、小表过滤。

④什么时候该上全文检索

需求LIKE全文索引外部搜索引擎
前缀匹配 abc%✓ 最佳可以但没必要过重
任意位置子串✓（全表扫）△ 取决于分词器✓ n-gram 可支持
中文分词搜索✗ 语义不对△ MySQL 需 ngram 解析器✓ ES 最成熟
相关性打分排序✗△ 基础 BM25/TF-IDF✓ 可调
高亮、同义词、拼音、纠错✗✗✓ 唯一选择
选型口径：能收敛成前缀匹配就留在 LIKE； 需要「按词搜索 + 排序」用数据库全文索引（MySQL FULLTEXT、PG tsvector）； 需要中文分词、高亮、同义词、拼音、纠错、多字段权重 → 直接上 Elasticsearch / OpenSearch， 用 binlog 或双写保持同步。不要让数据库承担搜索引擎的职责。
Q：中文用 MySQL FULLTEXT 为什么搜不出？
A：默认解析器按空格/标点切词，中文整段会被当成一个词。需要配置 ngram 解析器并设置 token 大小（通常 2）， 且建索引时就要指定——改解析器必须重建索引。中文搜索体验要求高时仍建议改用 ES。
Q：LIKE '%x%' 一定要全表扫吗？
A：B+Tree 下必然如此。替代方案：① 反转列 + 前缀索引处理后缀查询；② 数据量大就用倒排索引； ③ 若只是固定的几个关键词，可以加一个生成列（generated column）标记录后再索引。
