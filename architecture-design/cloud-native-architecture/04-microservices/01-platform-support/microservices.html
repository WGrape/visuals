微服务运行支撑

按业务能力拆分服务后，服务发现、流量治理、可观测性、编排与交付共同支撑独立运行。

微服务拓扑 Topology

网关统一入口，服务间通过服务发现直连或经消息

每个服务独立进程、独立数据库、独立 CI/CD。服务间通过同步（REST/gRPC）或异步（消息队列）通信。团队按服务划分，『谁构建谁运维』。

关键支撑设施 Must-haves

缺任何一项，微服务都会很难受

通信模式 Sync vs Async

读多写少、强一致用同步；事件驱动、削峰用异步

面试高频问答

Q：微服务为什么需要『数据库按服务拆分』？
A：若共用一个库，服务间仍通过数据库耦合，等于假微服务。每服务自管数据才能做到独立部署与故障隔离；跨服务查询靠 CQRS / 聚合层。
Q：服务间调用如何避免雪崩？
A：引入超时、重试(带退避)、断路器(熔断)、舱壁隔离、限流；配合舱壁线程池避免一个慢依赖拖垮整个服务。

微服务在云原生平台上的落地形态

微服务是架构思想，云原生是落地平台。把微服务放到 K8s 上，原本需要自己实现的服务发现、负载均衡、弹性伸缩、滚动发布、健康检查，平台都提供了标准能力。

能力不在平台上时怎么做云原生平台提供什么
服务发现引入 Eureka / Nacos / Consul，客户端或服务端集成K8s Service + DNS + EndpointSlice，应用无感知
负载均衡Ribbon / 自研 LB / Nginx 配置Service 的 iptables/IPVS/eBPF 转发，或 Ingress
配置管理自研配置中心或散落的配置文件ConfigMap / Secret / 外部配置中心，支持热更新
弹性伸缩写脚本调用云 API 扩容HPA（按 CPU/内存/自定义指标）、VPA、CronHPA
发布策略手工替换或自研发布系统Deployment 滚动更新、蓝绿、金丝雀（Argo Rollouts）
自愈监控告警 + 人工重启liveness/readiness 探针 + 自动重启 + 自动漂移
限流熔断Sentinel / Hystrix 集成到应用Service Mesh（Istio）在基础设施层实现，业务零改动
可观测各服务自己埋点上报统一采集：Prometheus + Fluent Bit + Jaeger

关键变化：「服务治理」从应用代码下沉到了平台。业务开发只需要关心业务逻辑，这大幅降低了微服务的接入成本。

K8s 上的微服务最小单元

apiVersion: apps/v1 kind: Deployment metadata: name: order-service spec: replicas: 3 # ← 多实例 = 集群，天然高可用 selector: matchLabels: { app: order } template: metadata: labels: { app: order } spec: containers: - name: order image: registry/order:v1.2.3 # ← 不可变镜像 ports: - containerPort: 8080 resources: # ← 必须设，否则会 OOMKill 或被驱逐 requests: { cpu: 250m, memory: 512Mi } limits: { cpu: 500m, memory: 1Gi } readinessProbe: # ← 决定能否接流量 httpGet: { path: /actuator/health/readiness, port: 8080 } periodSeconds: 5 livenessProbe: # ← 决定是否重启 httpGet: { path: /actuator/health/liveness, port: 8080 } periodSeconds: 15 lifecycle: preStop: # ← 优雅关闭：先从 LB 摘除 exec: { command: ["sh", "-c", "sleep 15"] } --- apiVersion: v1 kind: Service metadata: { name: order-service } spec: selector: { app: order } ports: [{ port: 80, targetPort: 8080 }] # ← 稳定入口 + 负载均衡

平台化带来的新关注点

① 资源配额（requests / limits）

不设 limits，一个服务内存泄漏会拖垮同节点的所有服务；不设 requests，调度器无法合理放置，节点可能过载。

  • CPU 超限会被限流（变慢，不杀）
  • 内存超限会被 OOMKill（直接杀）——所以内存 limit 要留足余量
  • 建议：requests 按常态用量，limits 按峰值 × 1.5

② 探针设计（决定可用性）

readiness 决定「能不能接流量」，liveness 决定「要不要重启」。

  • liveness 失败会重启，所以要宽松——不应依赖外部服务，否则下游抖动会引发无谓重启
  • readiness 要真实——依赖不可用时应摘除，避免把错误返回给用户
  • 慢启动应用要设 startupProbe，避免启动未完成就被 liveness 杀掉

③ 优雅关闭（决定发布是否无损）

K8s 删除 Pod 时会同时发 SIGTERM 和从 Endpoint 摘除，但这两件事有传播延迟。

  • preStop sleep 几秒，等摘除生效后再真正关闭
  • terminationGracePeriodSeconds 要大于「最长请求处理时间」
  • 应用要处理 SIGTERM：停止接新请求 → 处理完存量 → 释放资源 → 退出

④ 服务间调用的可靠性

平台解决了发现与负载均衡，但熔断、重试、超时仍需治理。

  • 应用内：Resilience4j / Sentinel
  • 基础设施层：Service Mesh（Istio）统一配置
  • 重试要谨慎：平台层自动重试 + 应用层重试会叠加放大流量

常见落坑

  • 把 K8s 当虚拟机用。在 Pod 里跑多个进程、SSH 进去改配置、把数据写容器层——这些都违背了不可变与无状态原则，会导致自愈与扩容失效。
  • 忽略优雅关闭。Pod 被直接杀掉，正在处理的请求失败、分布式锁没释放、消息没提交 offset。这是「发布期间报错率上升」最常见的原因。
  • 探针写得太重。liveness 探针里查数据库，数据库抖动就导致所有 Pod 重启，引发雪崩。探针应该极轻量。
  • 不设资源限制。一个服务吃满节点内存，导致同节点其他服务被 OOMKill，故障面被放大。
  • 服务拆分过细。一次请求跨 15 个服务，每多一跳就多一份延迟与失败概率，可观测性与排障成本急剧上升。
  • 日志与指标不规范。没有统一的日志格式与 traceId，几十个服务的日志无法串联，出了问题只能靠猜。

深入自检

有了 Service Mesh 还需要 Spring Cloud 吗？

看团队与技术栈。两者功能高度重叠：服务发现、负载均衡、熔断、限流、重试、链路追踪。区别在实现位置：Spring Cloud 是应用内的 SDK（侵入代码、语言绑定 Java、升级要发版）；Service Mesh 是基础设施层的 Sidecar 代理（业务零感知、语言无关、配置动态生效）。如果技术栈统一是 Java/Spring，用 Spring Cloud Alibaba 这类全家桶上手更快、排障更直观；如果是多语言混合、或希望治理能力统一管控与动态生效，Mesh 更合适。也有团队走渐进路线：先 Spring Cloud，容器化后逐步把治理能力下沉到 Mesh。注意不要两层同时开启相同能力（如两边都做重试），会造成放大效应。

微服务一定要用 Kubernetes 吗？

不是必须，但 K8s 已成为事实标准，因为它把「调度、自愈、伸缩、发布、服务发现、配置」这些公共能力标准化了，避免每个团队重复造轮子。替代方案：云厂商的 PaaS（如各类容器服务、Serverless 平台）底层往往也是 K8s 或同类编排；小规模也可以用 Docker Compose + 简单脚本。但一旦服务数量超过十几个、需要自动伸缩与滚动发布，没有编排系统会迅速失控。结论：不是必须，但除非规模很小，否则引入托管 K8s 的收益远大于成本。

readiness 和 liveness 探针到底该怎么配？

核心区别：liveness 失败 → 重启容器（重手段，要谨慎）；readiness 失败 → 从 Service 摘除（轻手段，可恢复）。因此：① liveness 只检查进程自身是否死锁，绝不能依赖外部服务——否则数据库抖动一次会导致全部实例重启，故障被放大；② readiness 检查是否真的能服务，可以包含关键依赖（数据库、缓存）的轻量探测，失败就摘除，等依赖恢复后自动回到服务列表；③ 慢启动应用加 startupProbe，让它在启动完成前不受 liveness 管辖；④ 参数上：探测间隔不要太密（5~15s），failureThreshold 设 3 次以上避免偶发抖动误判。

发布期间总有少量报错，怎么排查？

按时间线排查四个点：① Pod 被杀时请求未完成——检查 preStop 是否配置、SIGTERM 处理是否优雅、terminationGracePeriodSeconds 是否够长；② Endpoint 摘除有延迟——Pod 已开始关闭但 LB 还在转发，preStop 里 sleep 几秒可覆盖这个窗口；③ 新 Pod 未就绪就接流量——readiness 探针是否真实，有没有「端口通就算就绪」的假探针；④ 客户端长连接未重连——连接池缓存了已销毁的 Pod IP，需要合理设置连接的 maxLifetime 与空闲检测。用「发布期间的 5xx 数量」作为指标持续观测，目标应该是零。
