02 · 输入表示

Token 嵌入：12 万行表格里查出来的第一层语义

模型看到的第一个张量不是 token id，而是 embedding 表里查出来的向量。这张表有多大、和输出头共不共享、能不能量化，直接决定模型装不装得进端侧内存。

一句话定位：一个 V×d 的查找表

Embedding 就是一个矩阵 E ∈ R^(V×d)，token id 是行号。前向时做的是 h = E[id]——纯查表，没有乘法，所以它的瓶颈是显存容量和随机读带宽，不是算力。

形状V × d（128256 × 4096，bf16 约 1.05GB）
初始化常见 std=0.02 或 1/√d，太大起步不稳
与输出头关系常共享（tied）；共享时输出 logits 会偏大，需缩放
位置编码embedding 之后单独加/旋，不在表里
查表得到向量，RoPE 与残差堆叠都在此之后发生

共享与不共享：一份参数还是两份

方案参数量训练稳定性代表模型取舍
Tied（共享）V×d需按 √d 缩放 logitsGPT-2 / LLaMA / Gemma省参数，输入输出语义一致
Untied（不共享）2×V×d更自由Qwen2.5 大杯 / 部分商用模型多 500M 参数，小模型不划算
部分共享（适配层）V×d + 小投影中等少数研究工程复杂，收益不明显
共享时别忘缩放

共享 embedding 让输入分布和输出 logits 用同一套尺度，隐藏层范数增长后会放大 logits。Gemma 的做法是先乘 √d 再进 lm_head，否则训练早期容易炸。

词表大小怎么影响模型

词表从 32K 涨到 128K，好处是同样文本用更少 token（中文尤其明显，压缩率可提升 30%~50%），代价是 embedding 与输出头参数涨 4 倍。

模型规模V=32K 时占比V=128K 时占比结论
0.5B≈ 13%≈ 30%小模型必须压词表，否则一半内存给了查表
1.5B≈ 5%≈ 15%折中区，看目标语言
7~8B≈ 2%≈ 7%主流选择 128K，中文收益明显
70B< 1%< 1%词表大小基本可以忽略

这也是为什么手机端模型常用 32K~64K 词表：每省 1 万词表项，就省下 1万 × 4096 × 2B ≈ 80MB 权重，对 4GB 内存预算来说是实打实的。

工程：初始化、扩展、切分

# 初始化新 token（扩展词表后必须做，否则是 0 或 nan） model.resize_token_embeddings(new_vocab_size) with torch.no_grad(): new_rows = model.get_input_embeddings().weight[-n:] new_rows.normal_(mean=0.0, std=0.02) # 或与旧行均值/方差对齐 # 词表 padding：张量并行要求 V 能按 TP 度整除（通常 pad 到 128 的倍数） # pad 出来的行必须冻结，且输出头要把 pad 位置的 logits 屏蔽为 -inf
  1. 对齐旧行统计：新增 token 的向量均值/方差最好与旧表一致，否则这些 token 的梯度会异常大。
  2. pad 行冻住：为 TP 整除而补的行不参与训练，也不该出现在采样候选里。
  3. 量化单独处理：embedding 与输出头通常保留更高比特（如 Q6 而不是 Q4），因为它们直接决定词的选择。

排障：五个和 embedding 有关的故障

现象根因排查
新增 token 输出乱码resize 后新行未初始化（全 0 或 nan）打印新行范数，应为 0.02 量级
换词表后 perplexity 崩tokenizer 与权重不匹配（同 id 不同词）对比 tokenizer.json 与 config 的 vocab_size、特殊 token id
生成出现 <pad>pad token 未被 mask，且采样时未排除检查 generation_config 的 suppressed tokens
多卡训练 loss 抖动词表未 pad，TP 切分后某些卡拿到空行V % TP != 0 时补行
4bit 量化后首 token 偏差大embedding 被一起量化把 embed/output 提到 6~8bit 重测

原理与取舍：为什么 embedding 能承载语义

训练时，出现在相似上下文的 token 会被推向相似方向，因为要产生相似的下一 token 分布。这让 embedding 空间天然具备「分布式语义」的结构——这也是 embedding 能单独拿去做检索（RAG 里的向量模型）的原因：它本来就是被这个目标训练出来的。

embedding 层需要 dropout 吗？

现代 LLM 预训练不用（0）；小数据微调时某些实现会加很小的 embedding dropout，但收益不稳定。

为什么 embedding 不参与权重衰减？

衰减会把向量整体拉向 0，破坏语义结构；实践中 embedding、norm、bias 通常被列入 no-decay 组。

端侧能不能只加载部分词表？

可以。按目标语言裁剪词表并重映射 id，是端侧压缩的常见手段；代价是遇到未登录字符只能走 byte fallback，中文场景要谨慎。
