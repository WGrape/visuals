杠杆一

分支预测：猜对了就快，猜错要还债

现代 CPU 是深度流水线的。遇到 if 分支时，CPU 不会等条件算完，而是猜测一个方向继续取指执行。猜对了零成本；猜错要清空流水线、回滚重来，代价可能是十几个甚至几十个周期。

经典例子

排序后的数组求和为什么更快

// 对大于 128 的元素累加
for (i = 0; i < n; i++) {
    if (data[i] >= 128) sum += data[i];
}

// 数据随机：分支走向随机 → 预测频繁失败 → 慢
// 数据有序：前半 false、后半 true，规律明显 → 预测几乎全中 → 快
如何消除分支：可用无分支写法改写，例如用位运算/查表/条件传送（cmov）代替 if。编译器在能证明安全时也会自动做「if 转换（if-conversion）」。
// 无分支版本（示意）：把条件变成算术
sum += (data[i] >= 128) ? data[i] : 0;   // 可能被编译为 cmov
杠杆二

缓存：访存才是真正的瓶颈

CPU 每秒能执行几十亿条指令，但访问一次主存要上百个周期——内存是「新的磁盘」。

层级典型容量典型延迟说明
寄存器几百字节~1 周期最快，直接参与运算
L1 Cache32–64 KB~4 周期分指令/数据缓存，每核独有
L2 Cache256 KB–1 MB~12 周期每核独有
L3 Cache几 MB–几十 MB~40 周期多核共享
主存GB 级~100+ 周期慢两个数量级
结论：在现代 CPU 上，减少缓存未命中往往比减少指令数更能提升性能。算法「理论上更快」但访存跳跃，可能输给「理论慢」但顺序访问的实现。
原则

局部性：缓存友好的本质

⏰
时间局部性
刚访问过的数据很可能很快再被访问 → 缓存保留它
📍
空间局部性
访问了某地址，附近地址很可能也被访问 → 按缓存行整块预取
📊
顺序 > 随机
数组（连续内存）远优于链表（指针跳跃），即使链表理论复杂度相同
🔀
紧凑布局
把经常一起访问的字段放在一起（结构体数组 vs 数组结构体 AoS/SoA 取舍）
实践

可以落地的优化建议

  1. 优先连续内存结构：数组/切片优于链表；批量场景考虑 SoA（结构体数组 → 数组结构体）布局。
  2. 减少随机跳转：哈希表虽 O(1) 但访存随机；元素少时线性扫描数组可能更快。
  3. 让分支可预测：把高频路径放在 if 前；或改写为无分支代码。
  4. 按块处理：循环分块（tiling / blocking）让工作集装进缓存，典型于矩阵运算。
  5. 先测量再优化：用 perf / VTune / pprof 看 cache-miss 与 branch-miss，别凭直觉。
最重要的一条：这些优化只在热点路径上值得做。先用性能剖析找到真正的瓶颈，再针对性优化——否则可读性的损失换不来任何收益。
面试问答

高频问题

Q1：为什么排序后的数组遍历更快？
因为分支预测。排序后条件走向呈现明显规律，预测器几乎全部命中；随机数据下分支走向不可预测，频繁预测失败导致流水线被清空，耗时显著增加。
Q2：什么是分支预测失败的代价？
CPU 猜测分支方向并提前执行；猜错时要丢弃已执行的推测结果、清空流水线并重新取指，损失可能达十几到几十个周期。分支越随机，代价越大。
Q3：什么是时间局部性与空间局部性？
时间局部性指刚访问过的数据很快会再被访问；空间局部性指访问某地址后其邻近地址也会被访问。缓存正是利用这两点，按缓存行整块加载并保留最近使用的数据。
Q4：为什么连续内存比链表快？
数组元素连续存放，访问具有极好的空间局部性，一次缓存行加载可覆盖多个后续元素；链表节点分散在堆中，每次访问都可能是缓存未命中，还需额外指针跳转。
Q5：什么是伪共享，怎么避免？
两个被不同核频繁写入的变量落在同一缓存行，导致缓存行在核间反复失效。解决办法是按缓存行填充把变量隔开，或让各核写独立副本后汇总。
Q6：性能优化的第一步应该做什么？
测量。用 perf/pprof 等工具定位真正的瓶颈（CPU 占用、cache-miss、分支预测失败、分配次数），再针对性优化。凭直觉优化往往改错了地方。

分支预测：代价到底多大

现代 CPU 流水线深达十几级，分支预测失败要把已取指执行的指令全部作废。

场景代价说明
预测成功0~1 周期几乎免费
预测失败15~20 周期约等于几十条简单指令
间接跳转失败更高虚函数调用、函数指针

规律分支几乎免费：循环里的 i < n 只有最后一次失败，命中率接近 100%。真正昂贵的是数据依赖的随机分支——比如 if (data[i] > 0) 且数据随机。

分支消除

# 经典实验：同样的数据，排序后快 3~5 倍
#   未排序：分支预测命中率约 50%，每次失败 15~20 周期
#   排序后：前段全 False、后段全 True，命中率 > 95%

# 消除分支的写法（branchless）
# 原始：if (x > 0) sum += x;
# 无分支：sum += x > 0 ? x : 0;   → 编译器可能生成 cmov
# 或：   sum += x & -(x > 0);     位运算技巧

# 查表替代分支：把小范围映射预计算成数组
# 原始：if (c >= 'A' && c <= 'Z') return c - 'A' + 'a';
# 查表：return table[c];   256 字节表，无条件判断

最该记住的一组数字：L1 约 1 ns、内存约 100 ns、SSD 约 100 μs、网络 RTT（同机房）约 0.5 ms。每一级差 3 个数量级——这就是“能用缓存就别落盘、能本地就别走网络”的量化依据。

缓存行与伪共享

CPU 以缓存行（通常 64 字节）为单位搬运内存，不是按字节。这带来两个关键影响。

概念含义后果
缓存行最小传输单位，64 B访问 1 字节也会载入 64 字节
空间局部性相邻数据会被一起载入连续数组远快于链表
伪共享两线程改同一行的不同变量缓存行反复失效，慢数倍
对齐按 64 字节对齐填充消除伪共享的标准手段

伪共享消除

// 伪共享：两个计数器在同一缓存行，多线程下互相拖慢
struct Bad  { long a; long b; };            // 同 64B 行

// 填充到 64 字节对齐，各自独占一行
struct Good { long a; char pad1[56];
              long b; char pad2[56]; };

// C++17 起可用标准写法
struct alignas(64) Counter { long value; };

// 实测：2 线程各增 1 亿次，填充后通常快 2~4 倍

判据：被不同线程频繁写入的变量，绝不能放在相邻 64 字节内。只读变量无所谓——伪共享只在至少一方写时才产生。

自检 Q&A

Q：链表为什么比数组慢？

A：不光是指针跳转，核心是缓存局部性。数组连续存储，一次载入 64 字节缓存行能覆盖 8 个 int（或 16 个），后续访问全部命中 L1；链表节点分散在堆里，每次访问都是一次可能的 cache miss（约 100 ns）。在遍历百万元素时，差距可达 5~10 倍——即使数组需要移动元素，往往仍比链表快。

Q：likely/unlikely 宏真的有用吗？

A：在分支已高度可预测时几乎无收益——硬件预测器已经做得很好。它的价值在两处：① 帮助编译器决定代码布局（把冷路径移出热区，减少指令缓存压力）；② 在分支无明显规律时给编译器提示，让它生成 cmov 而非跳转。乱加反而可能干扰编译器的已有判断。

Q：怎么判断程序是 CPU 密集还是内存密集？

A：看 IPC（每周期指令数）与 cache miss 率。用 perf stat：IPC > 1.5 且 miss 率低 → 计算受限，优化方向是减少指令与用好 SIMD；IPC < 0.5 且 cache-misses 高 → 内存受限，优化方向是改善数据布局（结构体拆分 AoS→SoA、提高局部性、减小数据体积），而不是改算法。

Q：循环展开有用吗？

A：现代编译器通常已经自动展开，手写展开常常无用甚至有害（增加指令缓存压力、寄存器溢出）。真正有效的是减少循环内的数据依赖：把 sum += a[i] 拆成 4 个独立累加器，让 CPU 能并行执行（打破串行依赖链），这在浮点累加场景常能提升 2~4 倍。
