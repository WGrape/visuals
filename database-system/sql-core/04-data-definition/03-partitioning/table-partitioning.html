①表内分区是什么，和分库分表有何不同

表内分区（PARTITION BY）是把一张逻辑表在存储层按某个键切成多个物理片段，对应用来说仍是同一张表，SQL 不变。它解决的是"单表太大导致维护与扫描慢"，而不是"单机容量/并发上限"——后者要靠分库分表（sharding）。

一句话区分：分区是单机内的物理切分，分库分表是跨实例的逻辑切分。很多业务先用分区解决 80% 的大表问题，再谈分片。

③分区裁剪：查询变快的真正原因

当 WHERE 带了分区键且是等值/范围条件时，优化器能做分区裁剪（partition pruning）：只打开命中的分区文件，跳过其余。一张 10 亿行的表按天分 365 个区，查"昨天"只扫描 1 个区，IO 直接降两个数量级。

-- 命中分区键：只扫 p20261027
EXPLAIN PARTITIONS
SELECT * FROM events WHERE ts >= '2026-10-27' AND ts < '2026-10-28';

-- 没带分区键：ALL partitions，裁剪失效
SELECT * FROM events WHERE user_id = 123;   -- 要扫全部分区
裁剪失效的常见原因：① 查询没带分区键；② 对分区键套了函数（WHERE DATE(ts)=... 而非范围）；③ 用了跨分区的 ORDER BY ... LIMIT 需要归并所有分区。

④分区维护：增删与重组

分区的价值很大程度来自"按时间滚动"——旧数据整区丢弃，而不是 DELETE 后慢慢回收。

-- MySQL：加新分区 / 丢弃最旧分区（秒级，不重写数据）
ALTER TABLE events ADD PARTITION (PARTITION p20261101 VALUES LESS THAN ('2026-11-02'));
ALTER TABLE events DROP PARTITION p20260101;        -- 直接删文件，比 DELETE 快得多

-- PostgreSQL：声明式分区
ALTER TABLE events ATTACH PARTITION events_20261027
  FOR VALUES FROM ('2026-10-27') TO ('2026-10-28');
分区与索引：每个分区有自己独立的索引；主键必须包含分区键（否则无法保证全局唯一），这是分区表最常踩的建表约束。

⑤反模式与坑

  1. 分区键选错：用一个低基数字段分区，结果所有数据落一个区，等于没分。
  2. 分太多区：几千个分区会让优化器的元数据开销和反序列化变慢，反而拖慢简单查询。
  3. NULL 落入哪个区：MySQL 中 NULL 会被当作最小值，落入第一个 RANGE 分区，容易污染“最早”的分区。
  4. 以为分区能替代索引：分区裁剪只减少扫描的分区数，分区内仍要靠索引定位行。

排障：裁剪失效与 NULL

裁剪失效三连：① 查询不带分区键；② 对分区键套函数（如 YEAR(ts)）让优化器无法反推范围；③ 跨分区排序 LIMIT 需归并所有分区。

NULL 归属：MySQL RANGE 中 NULL 视为最小，落入第一个分区，容易污染“最早”的分区。设计时在边界或默认值上预留，避免脏数据堆在最早分区。

主键必须含分区键否则建表报错——先想清楚唯一性约束是全局还是分区内。

自检 Q&A

分区表能让写入更快吗？

一般不会。写入仍要落到某个分区并维护其索引，和单表无本质差异。分区的性能收益集中在查询裁剪和整区删除，不是写入。

一张表分多少区合适？

经验上几百到一两千个分区是舒适区。几千个以上会让每个查询的分区元数据解析变慢，简单查询反而退步。按天分区保留 1~2 年通常没问题。

分区能解决单库容量上限吗？

不能。分区仍在同一个实例/同一个文件系统内。容量或并发到顶了要上分库分表（sharding）或分布式数据库（如 TiDB/OceanBase）。
