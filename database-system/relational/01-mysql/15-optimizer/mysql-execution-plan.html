①执行计划是什么

执行计划（Execution Plan）是 MySQL 优化器做完决策后、交给执行器的一份「作战方案书」。它把一条声明式的 SQL，翻译成一串确定、可执行的操作步骤，告诉执行器：

  • 每张表怎么访问：全表扫描？走哪个索引？索引范围扫描还是等值 REF 查找？（这叫访问路径 Access Path）
  • 多张表怎么连接：先扫哪张、再连哪张（连接顺序）？用嵌套循环、哈希连接还是块嵌套循环（连接算法）？
  • 怎么处理排序 / 分组 / 去重 / LIMIT：要不要 filesort？要不要建临时表？在哪一步截断行数？
一句话
执行计划 = 优化器的产出物，是一棵描述「用什么方法、什么顺序、取哪些数据」的树。你敲 EXPLAIN 看到的，就是这棵树的「打印版」（详见《EXPLAIN 详解》）。
②它在 SQL 执行链路里的位置

一条 SQL 从发出来到拿到结果，中间要经过一串组件。执行计划正好卡在「优化器产出」与「执行器消费」的交界处——它是优化器劳动的成果，也是执行器开工的依据。

注意：执行计划本身不是优化器（那是上一个系列讲的角色），也不是执行器。它只是两者之间的「交接物」。优化器负责想，执行器负责干，计划就是想出来的方案。

③为什么需要执行计划

你可能会问：SQL 不是「声明式」吗？我只要说「我要什么」，数据库直接给我不就行了，为什么中间非得多一份「计划」？原因有四点：

1. SQL 是「要什么」，而取数必须「怎么做」

SQL 只描述结果（SELECT ... FROM ... WHERE ...），但从磁盘把数据捞出来的每一步——扫哪张表、走不走索引、先连谁——都需要一个确定的线性步骤。这份步骤就是执行计划。没有它，执行器根本不知道先干哪步。

2. 解耦「决策」与「执行」

把「选最优方案」（优化器，重脑力、读统计信息、算代价）和「机械取数」（执行器，调存储引擎、读页、取行）拆开，两个组件各自演进、互不干扰。现代 MySQL 能独立把执行器重构成「迭代器模型」，正是因为有执行计划这层稳定中间表示当「契约」。

3. 让「优化」可被观测、可被验证

正因为计划是一棵结构化、可被序列化的树，才有了 EXPLAIN（看方案）、EXPLAIN ANALYZE（看实测）、optimizer_trace（看决策过程）这些工具。你才能知道「它到底打算怎么跑」「为什么选了全表扫描」。

4. 统一表示「一切查询都是 JOIN」

MySQL 内部把所有查询（哪怕单表查询）都当作 JOIN 来处理。执行计划用同一套树结构表达「单表扫描」「多表连接」「子查询物化」等所有情形，避免为每种 SQL 硬编码一套执行逻辑——没有这层统一表示，优化器根本没法通用地选路。

反例
如果不要计划、让执行器直接按 SQL 字面意思硬跑，会出现两个灾难：① 没法选路，永远只能一种固定跑法（永远全表扫描）；② 优化器想做的「谓词下推 / 连接重排 / 子查询扁平化」全部无从落地。计划，是 MySQL 能「智能选路」的前提。
④执行计划的数据结构：从 QEP_TAB 到 AccessPath

执行计划得有具体的数据结构来承载。MySQL 的表示方式经历过一次重要演进（已核实，勿改）：

版本核心结构形态说明
8.0.22 之前JOIN + QEP_TAB
（Query Execution Plan Table）		一个数组（左深树）每个 QEP_TAB 描述一张表怎么访问、上一个表用什么 join 方式连它。数组天然只能表示左深树。
8.0.22 及之后AccessPath 树一棵真正的树每个节点代表一种访问路径（扫描 / 连接 / 排序 / 聚合…）。树能表达更灵活的稠密树（bushy tree），也直接对应 EXPLAIN FORMAT=TREE 的输出。

规划好后，执行器再调用 CreateIteratorFromAccessPath()，把 AccessPath 树的每个节点翻译成对应的 RowIterator 对象，形成一棵「迭代器树」真正去跑。所以链路是：AccessPath 树 → RowIterator 树。

⑤火山模型：执行计划怎么被「跑」起来

AccessPath 树生成后，执行器会把它变成一棵 RowIterator 树，然后按火山模型（Volcano / Iterator Model）运行。这是数据库执行最经典、最广泛使用的模型（PostgreSQL、SQL Server、Presto 等都用）。

每个迭代器三个方法

Init()
Read()
Cleanup()

Init()（初始化）：从根迭代器往下递归调用，打开表、分配 buffer、建立连接状态。这一步把所有准备工作一次做完，真正的取数推迟到 Read。

Read()（取一行）：根迭代器反复调用 Read()，返回 0 表示「拿到一行」，返回 -1 表示「没了」。每次 Read 内部会递归向下拉取子迭代器的行、做本节点的处理（过滤 / 投影 / 连接 / 排序…）。这就是拉取模型（Pull-based）：数据自底向上被拉取、自顶向下调用。

Cleanup()（收尾）：迭代器析构、关闭表、释放临时表与内存。一次查询的生命周期到此结束。

为什么叫「火山」
迭代器像火山口，调用 Read() 像在火山口喊「下一行」，数据像岩浆一样从最底层的表扫描节点，一层层向上喷涌、被各层处理，最终到达顶部交给客户端。这正是火山模型名字的由来。
⑥执行计划怎么产生的（产生过程）

执行计划不是凭空出现的。它的产生，就是优化器工作过程的产物（详见《优化器工作过程》）。串起来看一条 SQL 的完整诞生路径：

  1. 解析：词法 + 语法分析，得到 AST。
  2. 预处理 / 名称解析：绑定表、列、类型，展开视图。
  3. 逻辑优化：子查询扁平化、外连接转内连接、谓词下推、等值推导、常量折叠——在不改变结果的前提下重写查询。
  4. 物理优化（核心）：基于代价模型，给每张表选访问路径（全表扫描 vs 索引）、选连接顺序与连接算法（NLJ / Hash Join / BNL），并估算代价。
  5. 生成 AccessPath 树：把上面选出的方案，结构化成那棵执行计划树（④ 里的形态）。
  6. CreateIteratorFromAccessPath：把树翻译成 RowIterator 树，交给执行器的火山模型去跑。
入口函数
在源码里，这一切的起点是 JOIN::optimize()——它把每个 Query_block 最终优化成 AccessPath。所以「执行计划的产生」=「优化器物理优化的收尾动作」。

一句话记忆：解析出语义 → 逻辑重写 → 物理选路 → 树化计划 → 迭代器化执行。执行计划，正是中间「树化计划」这一步的结晶。

⑦执行计划长什么样：EXPLAIN 三种格式

既然计划是一棵树，MySQL 提供了三种「打印」方式（详见《EXPLAIN 详解》），对应不同的可读性层级：

格式形态直观度用途
FORMAT=TRADITIONAL
（默认）		一张二维表：一行一个表、id/select_type/type/key/rows/Extra…中最常用，看每步走了什么访问类型、用了哪个索引。
FORMAT=JSON嵌套 JSON 对象，原样反映树的层级与代价。高需要看完整树结构、成本分解、优化器决策细节时用。
FORMAT=TREE缩进的树状文本，每个 -> 是一个迭代器节点。高最贴近 AccessPath / 迭代器树的真实形态，读起来就是「执行顺序」。
TREE 的阅读法则
缩进最深的节点先跑（最底层先取数），向上每一层消费其子节点的行。从下往上读，就是真正的执行顺序。这正是火山模型「数据自底向上拉取」在 EXPLAIN 输出上的体现。

所以「执行计划长什么样」这个问题，答案就是：三种格式本质上都是同一棵 AccessPath / 迭代器树的序列化——只是表格、JSON、缩进树三种不同的呈现。

⑧速查清单
  • 是什么：优化器产出、交给执行器的「作战方案书」；描述访问路径 + 连接顺序/算法 + 排序/分组/LIMIT 怎么处理；本质是一棵树。
  • 在哪：卡在「优化器产出」与「执行器消费」的交界，是两者的中间产物（不是优化器本身）。
  • 为什么需要：SQL 是声明式必须转成确定性步骤；解耦决策与执行；可观测（EXPLAIN / trace）；统一表示「一切查询都是 JOIN」。
  • 数据结构：8.0.22 前是 JOIN + QEP_TAB 数组（只能左深树）；8.0.22 后是 AccessPath 树（可 bushy）；再由 CreateIteratorFromAccessPath 转成 RowIterator 树。
  • 怎么跑：火山模型 / 迭代器模型，每个迭代器 Init() / Read() / Cleanup()，Read 返回 0=行、-1=结束，拉取式自底向上取数。
  • 怎么产生：解析 → 逻辑优化 → 物理优化（选路）→ 树化 AccessPath → 迭代器化执行，起点是 JOIN::optimize()。
  • 长什么样：TRADITIONAL 表 / JSON / TREE 三种格式，都是同一棵树的序列化；TREE 从下往上读即执行顺序。
