max_tokens 与停止序列：给生成装上刹车

输出预算怎么算、为什么会被截断、finish_reason 在说什么。

输出上限

max_tokens 限制的是"新生成"的 token

max_tokens 规定本次响应最多生成多少个新 token，不含输入。它不影响模型"想"多久，只限制输出长度——达到上限就停，哪怕话没说完。

命名演化：OpenAI 新接口已改名 max_completion_tokens，强调"补全部分"；Anthropic 叫 max_tokens 且必填；很多本地框架另有独立参数控制上下文总长。跨平台迁移时最容易踩这个坑。
预算

和上下文窗口一起算账

约束公式说明
窗口约束输入 + 输出 ≤ 上下文窗口部分 API 还要求 max_tokens 显式小于剩余空间
常见事故输入 7k + max_tokens 4k > 8k 窗口报错，或被 API 静默压缩
推理模型思维链也计入输出o1/R1 类模型的"思考 token"同样占 max_tokens，答非所问往往是预算被思考吃光
截断的两种姿势：话没说完被掐断时，流式输出会戛然而止、JSON 可能只剩半截。结构化输出场景要么留足预算，要么在代码里检测 finish_reason 并续写或重试。
停止序列

stop：遇到就停的"暗号"

stop（stop_sequences）是一组字符串，生成过程中一旦产出该序列即停止，且停止序列本身不会出现在输出里。经典用法：

对话轮次分隔
stop=["\nUser:"] 防止模型自导自演下一轮提问
截断追问
补全场景用 stop=["\n\n"] 只取第一段
工具调用边界
以特殊 token 作为函数调用的结束标记
信号

finish_reason：为什么停下来的三张字条

值含义处理
stop自然结束或命中 stop 序列正常，无需处理
length撞到 max_tokens 上限被截断：调大预算或做续写
content_filter触发安全策略按业务决定重试或拒绝
面试问答

高频问题

Q1：max_tokens 会影响回答质量吗？
不影响"质量"本身，模型仍是逐 token 生成；但设太小会导致截断（finish_reason=length），长答案变半截，等效于"质量问题"。思维链模型还需预留思考预算。
Q2：输入 token 算不算 max_tokens？
不算。max_tokens 只限新生成部分；但输入 + 输出合计不能超过上下文窗口，所以留输出预算时要先扣掉输入长度。
Q3：stop 序列会被计入输出吗？
不会。命中 stop 后序列本身被剥离；但生成这些 token 的开销已经发生，也不返回。它控制的是"从哪停"，不是"省 token"。
Q4：JSON 输出被截断怎么兜底？
检测 finish_reason=length；策略包括：调大 max_tokens、让模型输出更紧凑的 JSON、流式中途检测并用代码补全括号，或携带已生成部分做续写重试。
Q5：为什么推理模型的输出"答案很短"？
很可能 max_tokens 预算被思维链 token 耗尽，思考完没额度输出最终答案。给推理模型要显著调大输出预算。

两个参数，管的是「什么时候停下来」

如果把生成比作一场马拉松，temperature / top_p 决定运动员怎么跑，而 max_tokens 和 stop 决定跑道终点在哪。它们都是只看输出侧的限制 —— 不控制输入有多长。

max_tokens输出 token 数的硬上限。到点即停，不管句子有没有写完。
stop停止词数组。输出过程中一旦匹配到其中任意一个字符串，立刻在此处截断（该字符串本身通常不返回）。
finish_reason返回体里的结束原因：stop / length / content_filter / tool_calls，是判断「正常结束还是被砍断」的唯一依据。
预留预算输出上限受上下文窗口挤压：可用输出 = 模型窗口 − 输入 token − 系统/工具/该轮历史占用。
上下文预算被输入吃掉后，输出空间随之缩小

max_tokens 的四条实战规则

  • 它不等于「字数」。中文大约 1 个汉字 ≈ 1~2 token（取决于分词），英文约 1 个单词 ≈ 1.3 token。要求「300 字以内」不能写成 max_tokens=300。
  • 留余量，尤其是结构化输出。要模型返回 JSON，一个字段啰嗦几句就可能翻倍；通常按预估长度的 1.5~2 倍设置。
  • 记得看 finish_reason。看到 length 就说明被截断了，此时解析必然失败，应该重试（加大预算或精简输入），而不是让下游硬着头皮解析。
  • 思考型模型的预算是两份。带推理过程的模型会先消耗「思考 token」再产出答案，这部分同样计入 max_tokens；预算给小了会出现「想了很久却没吐出答案」的情况。
伪代码：带截断重试的安全调用 budget = 1024 for attempt in range(3): max_tokens = budget resp = call(messages, max_tokens=max_tokens) if resp.finish_reason != 'length': break budget = int(budget * 1.6) # 加大输出预算 messages = compress(messages) # 或反过来精简输入 else: raise RuntimeError('仍被截断，检查是否循环输出')

stop：比 max_tokens 更精细的刹车

stop 匹配的是字面字符串，不是 token，也不支持正则。它的价值在于「模型写完一件该停的事，就别再往下编了」。

工具调用链路协议自带停止序列模型吐完一个调用就该交还控制权

注意三点：① stop 字符串通常不会出现在返回内容里（不同实现细节有别，需实测）；② 如果答案本身可能包含该字符串（例如让模型写包含 \n\n 的 Markdown），用 stop 会误伤，此时应改用结构化输出或后处理；③ stop 与 max_tokens 是或的关系 —— 谁先满足就因谁而停，finish_reason 会告诉你答案。

深入自检

为什么我设了 max_tokens=4096，返回却很短？

正常。max_tokens 是上限不是目标长度。模型一旦采样到结束符（EOS）就会自然停下，finish_reason 为 stop。想控制长度应该改 prompt（明确字句数要求）或给示例，而不是指望 max_tokens 托底。

max_tokens 超过模型窗口会怎样？

多数服务端会直接返回参数校验错误，而不是自动裁剪。所以调用前应该做预算计算：预估输入 token 数（可用服务端计数接口或近似估算），用模型窗口减掉它，再分配给 max_tokens，并给 mini-batch、工具回包留 buffer。

被 length 截断时，能不能「接着上一次」继续生成？

可以，但不是一个干净的方案：把已产出的内容拼回来继续请求，语义衔接（尤其是 JSON、代码块、标点）容易出错。更好的做法是根因处理——精简上下文、缩短要求、把长输出拆成多次子任务分别调用。

为什么流式输出时我没拿到 finish_reason？

流式协议里 finish_reason 通常在最后一个 chunk 上携带（多数实现给它赋 null 直到最后一帧）。务必在循环里读最后一个数据帧并做判断，否则无法区分「正常结束」和「被 max_tokens 砍断」。
