多维映射表

把 HBase 的表想象成一个超大的、按行键排序的「三维坐标 → 值」字典。三维分别是 行(rowkey)、列(列族:限定符)、版本(timestamp)。任意组合唯一确定一个 cell。

核心概念

概念说明要点
表 Table多个列族的集合建表时就要声明列族，列族很少（2~3 个）
行键 RowKey每行的唯一主键字典序全局有序；是查询与分布的唯一索引
列族 ColumnFamily列的命名空间物理存储单位，不同列族存成不同文件
列限定符 Qualifier列族下的具体列可动态、任意多，无需建表声明
单元 Cell(rowkey, cf:q, ts) 对应的值没有类型，全是字节数组
版本 Version同 cell 的时间戳副本默认保留最近 VERSION 个版本（默认 1）
命名空间 Namespace表的逻辑分组类似 RDBMS 的库；默认 default、hbase 系统空间

逻辑视图 vs 物理视图

逻辑上是一张「宽表」，但稀疏：某个 rowkey 只在它实际有值的列上有 cell，其余格子根本不存在（不占空间）。物理上，同一列族的所有列存在一起（列族聚簇），不同列族分文件存储。

逻辑视图                              物理存储（按列族分开）
rowkey | info:name | info:age | stat:pv     HFile(info) : u001/info:name/Alice
u001   | Alice     | 30       | 128                      u001/info:age/30
u002   | Bob       | (无)     | (无)                     u002/info:name/Bob
u003   | (无)      | 25       | 7                        u003/info:age/25
                                            HFile(stat) : u001/stat:pv/128
                                                          u003/stat:pv/7
💡 关键推论：scan 时指定列族能大幅减少 IO，因为另一列族的文件根本不用读。这也是「列族要按访问模式划分」的物理依据。

版本（Version）机制

  • 每个 cell 可以保留多个时间戳版本，默认 VERSIONS => 1（只留最新）。
  • 时间戳可由客户端指定，也可由服务端写入时自动生成（毫秒）。
  • 查询时默认返回最新版本；{ VERSIONS => 3 } 可取最近 3 个。
  • 旧版本在 major compaction 时才被真正清理（连同墓碑标记一起）。
  • 还有 TTL（秒）：超过 TTL 的 cell 自动过期，也在 compaction 时清理。
create 't', { NAME => 'cf', VERSIONS => 5, TTL => 86400,
              BLOCKCACHE => true, COMPRESSION => 'SNAPPY' }
get 't', 'r1', { COLUMN => 'cf:q', VERSIONS => 3 }
scan 't', { TIMERANGE => [1700000000000, 1700086400000] }

列族的物理意义

隔离

一个列族对应一组 HFile 与独立的 MemStore 区域。flush 是按 Region 内单个 Store（= 列族） 触发的。

代价

列族过多 → MemStore 分散、文件数膨胀、flush 与 compaction 次数放大。一般控制在 2~3 个以内。

划分依据

把「访问模式不同、大小与增长速率不同」的列分到不同列族。例如基本信息小而常读、日志体大且只偶发读。

属性单位

VERSIONS、TTL、压缩算法、BloomFilter、块大小等都是列族级属性，不是列级。

没有的东西（很重要）

❌ 无数据类型全是 byte[]，类型解释交给应用
❌ 无二级索引原生只能按 rowkey 查，二级索引要靠 Phoenix
❌ 无 JOIN只能在应用层拼，或走 Phoenix/Spark
❌ 无 NULL不存在 = 该 cell 没有，与空串不同
❌ 无跨行事务只有行内原子 + 行级 CAS
❌ 无自增 IDrowkey 必须自己设计生成

🎯 常见问法与答题要点

Q：rowkey、列族、列限定符、版本，到底哪个决定了查询能力？

A：只有rowkey 是索引。HBase 原生只有一种访问路径：精确 rowkey 点查，或 rowkey 范围 scan。列族和限定符只能在 rowkey 定位之后做「过滤」——它们不参与定位。所以「我的查询能不能走索引」等价于「能不能把查询条件编码进 rowkey」，这就是 RowKey 设计篇是 HBase 最重要一篇的原因。

Q：为什么列族不能超过 2~3 个？

A：因为列族是物理隔离的单位：每个列族有独立的 MemStore 和独立的 HFile 集合。列族多了会带来：①MemStore 被摊薄，每个都很小却各自触发 flush，产生大量小文件；②一次 flush 是 Region 级别触发所有 Store，列族越多文件越多；③compaction 压力成倍增加。官方建议 2~3 个。

Q：稀疏表真的不占空间吗？

A：是的。HBase 只存储实际存在的 cell，没有「空列占位」。这与关系库不同（关系库即使某列是 NULL 也占行结构）。所以一张有一百万列的「宽表」，只要每行只写了几十个 cell，实际存储就只有那几十个 cell。但注意：空 cell 也没有默认值语义，读到就是不存在。

Q：VERSIONS 设大一点有什么代价？

A：每个版本都是一个完整的 cell（含 rowkey、列、时间戳、值），所以保留 N 个版本 ≈ 存储放大 N 倍，compaction 与 scan 的开销也同步放大。常见做法：默认 VERSIONS=1；确实需要历史版本的场景（如审计、时序）设 3~5，并配合 TTL 限制总量。

Q：timestamp 能自己指定吗？有什么坑？

A：能，put 时可以传时间戳。坑在于：如果客户端时间不准（机器时钟漂移），可能写入一个很旧的时间戳，导致该 cell 被「更新的版本」永久屏蔽（因为读默认取最新）——看起来就像写入丢失了。生产上一般不指定时间戳，让服务端生成。

Q：delete 之后为什么 scan 还能看到旧数据？

A：不会。delete 写的是墓碑标记（tombstone），读取路径上墓碑会屏蔽掉所有 ≤ 该时间戳的旧版本，所以 scan 立刻看不到。但物理删除（连同原数据和墓碑一起消失）要等 major compaction。这也是「删了数据磁盘没变小」的原因。
