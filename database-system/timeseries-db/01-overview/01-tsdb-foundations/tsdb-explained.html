时序数据库 TSDB 原理

为什么监控数据不能用 MySQL 存——时序数据的特点、压缩与降采样

① 时序数据特点 ② 数据模型 ③ 压缩算法 ④ 降采样与保留 ⑤ 产品对比 ⑥ 常见疑问
一句话总结：时序数据的特征是「写入量巨大、几乎不更新、不删单条、查询总带时间范围、旧数据价值递减」。 通用数据库为「随机读写 + 事务」优化，正好与这些特征错位。 TSDB 围绕这些特征重新设计，压缩比可达 10～20 倍，聚合查询快一个数量级。

02数据模型：时间线 Series

TSDB 的核心抽象是 时间线（Time Series）： 由指标名 + 一组标签（tags/labels）唯一确定，对应一串「时间戳 → 值」的点。

图 2：Series 是 TSDB 的基本存储单元
高基数（High Cardinality）是 TSDB 的头号杀手。 假设有 3 个标签，取值分别是 1000、50、20 种，理论时间线就有 100 万条。 把 user_id、request_id 这类无限取值字段当 tag， 会瞬间打爆内存索引。规则：tag 只能放有限枚举的维度，连续值放 field。

数值压缩：XOR

相邻浮点值通常只有低位比特不同。Gorilla 的做法是 与前一个值做异或（XOR），大部分 bit 变成 0，然后只存「前导零个数 + 有效位长度 + 有效位」。

prev = 42.0        → 0x4045000000000000
cur  = 42.5        → 0x4045400000000000
XOR  =             → 0x0000400000000000   ← 只有中间少数几位非零

存储：leading_zeros=30, meaningful_bits=4, value=0x4
→ 从 8 字节压到 ~10 bit

📉 实际压缩比

Prometheus 官方数据：每个采样点平均约 1.7 字节（时间戳 ~1 bit + 值 ~13 bit）。 相比原始 16 字节（8 字节时间 + 8 字节值），压缩比接近 10 倍。

🔢 整数型值

计数器（counter）类指标可用 Delta + 变长编码（ZigZag/Varint）， 单调递增的小增量效果极佳。

⚠️ 压缩前提

压缩依赖「同一 Series 的点相邻存放 + 值变化平滑」。 随机乱序写入、值剧烈抖动会大幅降低压缩比。

04降采样与数据保留

这是 TSDB 与通用数据库最不同的运维特性：数据会随时间自动"降级"和"消失"。

图 4：分层降采样——用精度换时间跨度

连续查询 Continuous Query

降采样通常由后台任务自动、增量完成，而不是事后批量重算：

-- InfluxDB 风格的连续查询示例
CREATE CONTINUOUS QUERY cq_1m ON monitor
BEGIN
  SELECT mean(value) AS value
  INTO monitor_downsampled.cpu_1m
  FROM cpu
  GROUP BY time(1m), host
END

Prometheus 的做法是 Recording Rules：预计算常用聚合表达式，存成新的时间序列， 查询时直接命中预计算结果。

05主流产品对比

产品定位数据模型特点
Prometheus监控告警事实标准metric + labels 拉模式（pull）、PromQL 强大、单机为主；长存储需接 Thanos/VictoriaMetrics
InfluxDB通用时序数据库measurement + tags + fields 推模式、Flux/InfluxQL、开源版集群能力受限（商业版才有）
TDengine国产，IoT/工业场景超级表（STable）+ 子表 一个设备一张表的设计，压缩比极高，写入性能强；国产化替代常见选择
VictoriaMetricsPrometheus 的长期存储兼容 Prometheus 内存占用低、性能高，Prometheus 生态的增强替代
TimescaleDB基于 PostgreSQL 的时序扩展关系表 + hypertable 完整 SQL、可 JOIN 业务表；适合不想引入新技术的团队
ClickHouse通用 OLAP（也能存时序）宽表 数据量极大时的选择；但缺少时序专属语义（如降采样、TTL 策略）
选型直觉：
· 云原生监控告警 → Prometheus（+ VictoriaMetrics 做长期存储）
· IoT / 设备上报 / 国产化 → TDengine
· 想用 SQL 且数据量中等 → TimescaleDB
· 已有 ClickHouse 且量大 → 直接用，配合物化视图做降采样

06常见疑问

Q：监控数据为什么不能直接用 MySQL 存？
A：三个硬伤：① 写不动——每秒几十万点，B+ 树随机写扛不住，索引维护成瓶颈； ② 存不起——每点 16 字节 × 几十万点 × 86400 秒，一天就几十 GB，MySQL 无时序压缩； ③ 删不掉——过期数据要按时间批量删，MySQL 的 DELETE 会产生大量 undo 与碎片。 而 TSDB 的追加写 + 高压缩 + 按时间块整体删除，正好对症。
Q：什么是"时间线爆炸"，怎么避免？
A：把 高基数字段当 tag（如 user_id、trace_id、URL 全路径）会导致 时间线数量 = 各 tag 取值数的笛卡尔积，内存索引瞬间撑爆。
规避：① tag 只放低基数枚举维度；② 高基数维度放进 field 或日志系统； ③ 用 relabel_config 丢弃不必要的 label；④ 监控 time series 数量并设置告警。
Q：Prometheus 为什么是"拉模式"？有什么优劣？
A：Pull 的好处是服务端无状态、目标发现简单、便于本地调试（直接 curl 目标 /metrics）。 代价是需要服务发现、不適合短生命周期任务（用 Pushgateway 补）、跨网络边界受限。 这是 Prometheus 与 InfluxDB（推模式）最核心的设计哲学差异。
