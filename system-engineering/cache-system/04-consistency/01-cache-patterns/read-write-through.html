什么时候适用？

判断信号：希望应用只面对缓存接口；缓存代理有能力可靠地访问权威数据库。

  • 多服务访问同一商品数据：Read-Through 代理统一处理未命中加载。
  • 库存写入需要同步确认权威数据：Write-Through 等数据库提交后才返回成功。
  • 日志聚合写入量大、允许秒级延后：Write-Behind 先可靠入队，再批量刷库。

和相近模式怎么区分？

相近方案选择边界
Read-Through 与 Cache-Aside读未命中时，前者由缓存代理查询数据库；后者由业务应用查询并回填。
Write-Through 与 Write-Behind前者成功通常意味着同步写库已完成；后者成功只代表写入可靠待刷记录，数据库可能仍是旧值。

核心伪代码

function readThrough(key):
  return cache.getOrLoad(key, loader=db.get)

function writeThrough(key, value):
  db.update(key, value)
  cache.set(key, value)
  return ACK

function writeBehind(key, value):
  durableQueue.append(key, value)
  cache.set(key, value)
  return ACK  // 后台重试刷库，需顺序和去重

Read-Through 可与不同写策略组合；Write-Behind 必须设计队列持久化、顺序、重试、回放与故障恢复。

统一代理

Read-Through

应用只和缓存交互；缓存未命中时由缓存层自己加载数据并回填，对应用透明。

Write-Through

写请求交给缓存代理，由代理同步写数据库并维护缓存；只有按其契约两步都成功才确认。写延迟包含数据库耗时，两步之间失败仍需要恢复策略。

Write-Behind

写请求先进入缓存层的待刷队列，后台再批量落库。响应可以更快，但数据库在一段时间内仍是旧值；若待刷记录未持久化，进程崩溃可能丢写入。

对比

模式负责的路径确认语义与风险
Read-Through读未命中回源不决定写库时机
Write-Through同步写库数据库写成功后确认；要处理部分失败
Write-Behind异步刷库先确认、后落库；要持久化待刷记录

🎯 面试问答

Q：Read-Through 与 Cache-Aside 区别？
A：未命中时由缓存层回源，应用只调用缓存层；Cache-Aside 则由应用回源并回填。
Q：Write-Behind 风险？
A：未刷库的记录若丢失会丢数据，还要处理顺序、重试和故障恢复。
Q：何时用 Write-Through？
A：需要同步确认数据库写入，且能接受相应延迟与部分失败处理成本。
