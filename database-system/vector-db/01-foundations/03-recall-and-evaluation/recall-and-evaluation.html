①为什么必须有可复现的召回数字

向量检索的结果「看起来都挺相关」，这种主观判断无法用于调参。把 ef 从 64 调到 128 到底换来多少召回、付出多少延迟，必须有一个可复现的数字。这个数字就是 recall@K，而它的前提是一份可信的标准答案（ground truth）。

recall@K = 近似检索返回的 K 条结果中，有多少条出现在真实前 K 名里 ÷ K。没有 ground truth 就没有 recall，没有 recall 就没有调参依据 —— 很多人调 ef 全靠「感觉快了/感觉准了」，本质是在盲调。

②ground truth 怎么建（必须用暴力检索）

ground truth 必须用暴力检索生成，不能用 ANN 生成 —— 用 ANN 生成的标准答案去评测 ANN，相当于自己给自己判卷。

  1. 冻结数据快照：把要评测的这批向量导出，或者建一个 FLAT 索引的副本（数据必须与线上完全一致）。
  2. 准备 query 集：从真实日志里抽 500–1000 条 query 向量；不要只用手写的几条「典型 query」，那会严重高估召回。
  3. 暴力检索：FLAT / brute-force，取 top-100（比目标 K 大一个量级，方便复用同一份 ground truth 评测 recall@1/10/100）。
  4. 落盘：存成 {query_id: [doc_id, ...]} 的映射，连同数据版本号一起存档。
# 用 Milvus 的 FLAT 索引造 ground truth
collection.create_index("embedding", {
    "index_type": "FLAT", "metric_type": "COSINE", "params": {}
})
collection.load()

truth = {}
for qid, qv in queries.items():
    hits = collection.search([qv], "embedding", {"metric_type": "COSINE"},
                             limit=100)[0]
    truth[qid] = [h.id for h in hits]

json.dump(truth, open("ground_truth_v1.json", "w"))
ground truth 必须带版本。数据增量写入、embedding 模型升级、向量归一化策略变化，任何一项变了旧 ground truth 就作废，否则你会在「召回突然从 0.96 掉到 0.72」时查错方向。

③recall@10 / @100 / MRR / nDCG 各看什么

不同 K 反映不同环节的健康度，别只盯一个：

指标反映什么典型目标掉下来先查
recall@10最终给用户的结果质量≥ 0.95（通用 RAG）索引参数 ef/nprobe、过滤选择率
recall@100粗筛层有没有把对的捞进来≥ 0.98量化精度、oversampling 是否够
MRR@10第一条正确结果排多前≥ 0.85重排（rerank）是否生效
nDCG@10多级相关性的排序质量视业务打分方向（cosine vs IP）搞反了没
recall@100 高但 recall@10 低 = 粗筛没问题，是排序/重排环节没做好；两个都低 = 索引或量化本身有问题，或者过滤把正确答案排除了。这两个信号的区分能直接省掉一半排查时间。

④建索引参数 vs 查询参数与拐点选择

这是最核心的一节：检索参数分「建索引时」和「查询时」两类，只有查询时的参数能在线调。

体系建索引参数（需重建）查询参数（可在线调）调大的效果
HNSWM、efConstructionef / ef_search召回↑ 延迟↑
IVFnlistnprobe召回↑ 延迟↑
PQ / 量化m、nbits、码本oversampling召回↑ 延迟↑
过滤检索过滤字段索引过滤选择率 / 迭代扫描视实现，可能反而更慢

正确的调参姿势是先定召回目标，再找最小代价点，而不是「ef 调到最大肯定最准」。做法是把 ef 从小到大扫一遍，画 recall-延迟曲线，取拐点：

ef（HNSW）recall@10p99 延迟判断
160.823 ms召回不够
320.914 ms偏紧
640.9556 ms拐点附近，推荐
1280.97211 ms多花 83% 延迟换 1.7 个点，不值
2560.97821 ms边际收益趋零
上表是典型的 HNSW 拐点形状：召回在 ef 走过某个值后迅速饱和，延迟却是线性上涨。真正该选的不是召回最高的那行，而是「再多加延迟换不来召回」的前一行。

⑤过滤场景：为什么越严格召回越差

带过滤条件的检索是召回塌方的高发区，而且现象很反直觉：过滤越严格，召回往往越差。

原因是 pre-filter 模式下，候选集被过滤得只剩很少的点，HNSW 的邻居图在这些点上不连通，遍历早早断头；post-filter 模式下则是「先取 top-K 再筛」，一旦筛选比例低，返回结果直接不够 K 条。

过滤选择率典型现象对策
> 50%基本无影响无需处理
10% – 50%召回轻微下降适度提高 ef 或 oversampling
1% – 10%召回明显下降，结果数可能不足 K改用支持迭代扫描的实现；用 partition/tenant 物理隔离
< 1%HNSW 几乎失效换过滤专用索引（payload index + 倒排优先），或干脆不用向量索引
评测带过滤场景时，ground truth 也必须带同样的过滤条件。拿无过滤的 ground truth 去评带过滤的结果，召回数字会毫无意义（必然很低）。

⑥离线之外：人工标注、A/B 与 badcase 归因

离线 recall 是必要条件，不是充分条件。用户感知的「检索好不好用」还包括排序质量和多样性。

人工标注集

抽 200 条 query，人工标「哪些结果算相关」，算 precision@10。这是唯一能发现「recall 很高但结果同质化」的手段。

线上 A/B

同一流量分桶，A 用旧参数、B 用新参数，比较点击率、追问率、「没用/重答」率。注意向量检索的效果常被 LLM 掩盖，要看二级指标。

badcase 归因

对「答案明显错」的会话回溯：是没召回（recall 问题）、召回了没排上来（rank 问题）、还是排上来了但 LLM 没用（prompt 问题）。三者修法完全不同。

回归测试集

把历史 badcase 固化成固定 query 集，每次改索引/换模型/调参都跑一遍，防止「修好一个坏掉三个」。

⑦七个让数字失真的错误

这些错误会让 recall 数字看起来很好或很差，但都不是真实的：

错误为什么错正确做法
用 ANN 结果当 ground truth自己给自己判卷，recall 恒为 1必须 FLAT / 暴力检索
K 不一致ground truth 存 top-10 却算 recall@100ground truth 的 K ≥ 评测的 K
query 集太小或太典型手写 20 条 query 无法代表线上分布从真实日志抽 500+ 条
数据已变但 ground truth 没重建新增/删除向量后标准答案失效ground truth 绑定数据版本
只测无过滤场景线上几乎都带过滤ground truth 带同样的过滤条件
忽略更新延迟刚写入的向量还没 flush，自然召不回评测前等待可见（或显式 flush）
在 CPU 空闲时测延迟延迟数字漂亮但线上不可复现按目标并发压测，看 p99 而非均值

⑧速记卡

recall 是什么

近似的 top-K 命中真实 top-K 的比例。没有它调参就是盲调。

ground truth

必须 FLAT 暴力检索生成，且绑定数据版本。

recall@100 vs @10

前者看粗筛、后者看排序。两个都低才是索引问题。

建索引 vs 查询参数

M / nlist / m 要重建；ef / nprobe / oversampling 可在线调。

调参目标

找拐点而不是最大值：再加延迟换不来召回的前一行。

过滤会塌召回

选择率 < 10% 时 HNSW 明显退化，考虑物理隔离。

离线≠线上

还要人工标注集、A/B、badcase 归因、回归集。

七个常见错

最致命的是「用 ANN 造 ground truth」和「K 不一致」。

评测的价值在于把「感觉更准了」换成「recall@10 从 0.91 到 0.955，p99 从 4ms 到 6ms」。没有这行数字，所有调参都是在赌。
