投机解码（Speculative Decoding）

为什么 decode 是带宽瓶颈、draft-verify-accept 的完整流程与接受准则、决定收益的三个变量、以及高 batch 与创意写作等不适用场景。

要解决的问题：decode 是带宽瓶颈

Decode 每步只生成一个 token，却要把整个模型权重从 HBM 读一遍。 这意味着：batch=1 时，算一次矩阵乘只服务 1 个 token，权重的搬运成本被严重摊薄。

加大 batch
一次权重加载服务 N 个请求 → 吞吐上去，但单请求延迟也上去，且受显存限制
投机解码
一次权重加载验证 K 个候选 token → 在不加大 batch 的前提下提吞吐
投机解码不改变输出分布（在正确的接受准则下），这是它相对"换个更小的模型"最大的优势—— 你加速的还是原来那个模型的采样结果。

流程：小模型起草，大模型验证

为什么能加速：Draft 模型小、每 token 便宜； Target 模型虽然每步要算 γ+1 个位置，但权重只加载一次，而 decode 的成本几乎全在权重加载上。 于是"γ 次串行前向"变成"1 次并行前向 + γ 次便宜的 draft"。

收益由三个数决定

变量含义影响
接受率 α候选 token 被接受的比例最关键。α 高 → 每轮产出多
草稿长度 γ每轮生成几个候选γ 太大会让拒绝位置靠前、白算增多；通常 3~8，需实测
成本比 cdraft 单步耗时 / target 单步耗时draft 越便宜越好，但要和 α 权衡——太小的模型 α 会掉
加速比不是线性的。α 从 0.5 提到 0.7 带来的收益，远大于 γ 从 5 加到 10。 所以工程重点在提高接受率：让 draft 模型的分布尽量贴近 target， 以及让 draft 更容易"猜中"——比如利用任务的高可预测性（代码补全、格式化输出、模板化回答的 α 天然更高）。
独立小模型
同系列小号（如 7B 给 70B 起草）。零训练成本，α 取决于分布相似度
自起草（EAGLE / Medusa）
用 target 自身的隐藏层/额外头预测候选，α 明显更高，但需训练适配层
检索式草稿
从历史输出或 n-gram 表取候选，对模板化、重复性内容有效

什么时候不该用

  • 高 batch 场景：decode 已经是算力瓶颈而非带宽瓶颈时，加大 batch 的收益更高，投机解码反而增加复杂度。
  • 草稿模型也要占显存：显存吃紧时放不下第二个模型，可用自起草方案缓解。
  • 输出高度随机时：温度高、创意写作类任务接受率低，收益有限甚至变慢。
  • prefill 主导的长输入短输出：瓶颈在 prefill，投机解码只优化 decode，帮不上忙。
部署提示：主流推理框架（vLLM、TensorRT-LLM、SGLang 等）已内置投机解码实现， 但各版本支持的 draft 方案、是否支持批量场景下的投机、与 prefix caching / chunked prefill 能否叠加都不相同。 启用前请查阅你所用版本的官方文档，并用真实请求压测确认收益——这是最容易"开了反而变慢"的优化项。

先搞清楚瓶颈在哪：为什么生成是一个字一个字蹦

Transformer 的推理分两段：prefill（一次性把整个输入算完，算力密集）和 decode（每次只算一个新 token，访存密集）。

问题出在 decode：为了产出 1 个 token，必须把全部模型权重从显存读一遍。你并没有算多少东西，时间全花在「搬运」上。GPU 的算力利用率常常只有个位数百分比，这是单条请求生成慢的根本原因。

一次 decode 步骤的实际账本 算力： ~2·N FLOPs（N = 参数量），推算 ~1 毫秒级 访存： 把 N 个权重读一遍 —— 这是真实瓶颈 结果： 算术单元大部分时间在「等数据」 所以：只看 utilization 会看到 GPU 很闲，但用户就是等得久

直觉上的解法是「一次多算几个 token」。但自回归的性质决定了：第 2 个 token 依赖第 1 个 token 的结果，没法直接并行。投机解码要解决的就是这个矛盾。

核心思路：让小模型先猜，大模型一次验收

流程只有四步：

投机解码四步：草稿 → 并行验证 → 拒绝采样 → 分布一致

加速比完全由接受率决定：草稿猜 4 个平均被接受 2.5 个，则近似把 3.5 个 token 塞进一次前向；猜得太贪心（γ 很大）会在验证上浪费算力，猜得太保守收益有限。工程上常根据历史接受率动态调整 γ。

几种常见变体

变体草稿从哪来优点局限
经典 Draft Model一个同源的小模型（如同系列的小尺寸版本）结构简单，效果稳定要额外维护一个模型、词表必须一致
自投机 Self-speculative用目标模型自己：跳层或用浅层部分的中间输出不需要额外模型，显存省实现复杂，收益依赖具体结构
多头方案（如 Medusa 类）在同一模型上加若干轻量预测头无需第二个模型，验证成本低需要额外训练这些头
检索式草稿从输入或历史里用 n-gram 匹配取候选零额外参数，对复读/模板化文本特别有效只在能匹配到重复模式时有效
块级/并行解码把若干位置当作独立块并行生成后修正适合结构化输出通用文本收益有限

和量化的关系：两者常常一起用 —— 草稿模型用激进量化版本（甚至同一权重的低比特副本），进一步降低那份额外显存，让「买一份小模型换 2~3 倍速度」这笔账更划算。

什么时候用得上，什么时候别折腾

收益明显的场景

  • 单条或小 batch 请求：GPU 本来就在等访存，并行验证几乎白捡算力。
  • 长文生成：decode 步数多，收益被放大。
  • 草稿与目标同词表、同风格：接受率才有保障。
  • 已有成熟小模型：同一系列的小尺寸版本是天然草稿模型。

收益有限甚至负优化

  • 大 batch 已经打满：算力已饱和，再并行也挤不出空档。
  • prefill 才是瓶颈：例如超长 prompt、短回答，此时该优化的是 prefill 与缓存复用。
  • 草稿质量太差：接受率下降，每个 token 都要重跑，反而多花一次验证的钱。
  • 纯 CPU 部署：CPU 侧瓶颈不同，优化方向往往不是这个。

深入自检

投机解码会改变输出质量吗？

规范的做法不会。关键在于被拒绝时的拒绝采样步骤：它经过构造，使得最终接受的 token 严格服从目标模型的原始分布（在数学上是无损的）。真正会改变输出的是工程细节——比如为了省事把贪婪验证写成「接受所有草稿」，那就抛弃了分布保证。

为什么有时开了投机解码反而更慢？

三 个常见原因：① 草稿模型本身较慢（尤其草稿模型没有被量化、或者批次形状不友好）；② γ 设得太大，验证阶段多算的位置大多被拒，白忙一场；③ batch 已经够大、算力饱和，此时多出来的验证 work 是净亏损。建议先离线量出「平均接受 token 数」，再决定是否开启，并对不同 batch 区间分别开关。

接受率多少才值得开？

粗略地看：若一轮平均能接受 2 个以上 token（也就是约 60%+ 的单 token 接受率，且 γ 配置合理），通常就有明显收益；若长期低于 1.5 个，应当先去找草质量的原因，而不是加大 γ。把接受率做成监控指标，是最实用的做法。

它和「多 token 预测」是一回事吗？

不完全一样。多 token 预测更多出现在训练阶段或特定的并行解码设计里，目标是让模型本身具备「同时预测未来若干位置」的能力；投机解码则是推理期的工程技巧，核心是保证「猜得快但验证得准」。两者可以结合：训练时具备多 token 预测能力的模型，天然适合充当自己的草稿源。
