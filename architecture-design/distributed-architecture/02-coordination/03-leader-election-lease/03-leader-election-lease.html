选主与租约：Leader Election 模式与 Lease 防脑裂

用选主 + 租约 + fencing 模式实现高可用协调、防脑裂。

1选主与租约解决什么

分布式里常需要唯一协调者（主节点）来避免重复工作与脑裂。纯粹"谁先到谁当"不可靠（原主其实还活着，只是网络抖）。Leader Election + Lease（租约）是更稳的模式：选举产生主，主持有带过期时间的租约，过期前续约，过期则重新选举，从而防止"两个主同时干活"的脑裂。

聚焦"模式"本身，不重讲 Raft 算法细节（可作例子）。

2选主与租约要素

要素作用失败后果
选举从候选中选出唯一主无主 / 多主
租约 TTL主权利的时效过长→故障切换慢
续约健康主延长租约未续约→被误剥夺
fencing隔离旧主（令牌）脑裂写脏

3基于租约的主循环

import time, uuid

LEASE_TTL = 5.0     # 秒
my_token = uuid.uuid4().hex

def try_become_leader(store):
    # 原子 CAS：仅当无主或租约已过期才写入自己+过期时间
    return store.cas("leader", None,
                     {"node": ME, "token": my_token,
                      "expire": time.time()+LEASE_TTL})

def maintain(store):
    while True:
        cur = store.get("leader")
        if cur and cur["token"] == my_token and cur["expire"] > time.time():
            store.set("leader", {**cur, "expire": time.time()+LEASE_TTL})  # 续约
        else:
            if try_become_leader(store):
                print("I am leader now")
        time.sleep(LEASE_TTL/3)   # 早于过期续约

真正防脑裂还要 fencing token：存储侧拒绝"令牌号小于当前"的写，旧主即便复活也写不进。

第一层 · 概念与判定

判定是否需要选主+租约：

  • 存在"全局唯一协调者"需求（调度、分片路由）；
  • 不能接受两个主同时写（脑裂）；
  • 允许秒级故障切换延迟；
  • 若要求强一致且零脑裂，还需 fencing 与共识提交。

第二层 · 参数·命令·量化

参数权衡：

项经验
TTL取网络抖动上界的若干倍，如 5–15s
续约周期TTL 的 1/3，留重试余量
quorum选举/租约写入需多数派
# etcd 租约示例
lease = client.lease(ttl=10)
client.put("leader", ME, lease=lease)  # 自动续约由库处理

第三层 · 排障与边界

排障与边界：

  • GC 停顿致失主：租约太短，停顿超 TTL 被踢，应留余量；
  • 时钟漂移：依赖墙上时钟的租约会误判，用单调时钟/共识；
  • 脑裂写脏：仅有主标识不够，必须 fencing token；
  • 羊群效应：主掉线全体抢主，用退避/jitter 缓解。

第四层 · 原理与取舍

原理取舍：

  • 租约用"时效"换故障可检测，代价是切换延迟；
  • 短 TTL 切换快但误踢风险高，长 TTL 反之；
  • 纯租约仍可能脑裂，需配合 fencing 或共识；
  • 结论：选主+租约+ fencing 是"高可用协调"的实用模式，Raft/ZK/etcd 都是其工程化。
