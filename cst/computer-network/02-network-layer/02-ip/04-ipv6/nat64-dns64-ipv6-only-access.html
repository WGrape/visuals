NAT64 与 DNS64：只有 IPv6 的手机怎样访问 IPv4 网站

用 IPv6 单栈客户端到 IPv4 单栈服务的路径解释合成 AAAA、协议转换和 IPv4 字面量难题。

两种地址族不能直接互读

IPv6 单栈客户端没有可直接使用的 IPv4 源地址，而某老网站只发布 A 记录和 IPv4 服务。客户端不能把 198.51.100.20 当作普通 IPv6 目的地址直接路由过去。DNS64 与 NAT64 常组合解决这类过渡：DNS64 在合适条件下把目标 A 地址嵌入特定 IPv6 前缀，提供合成 AAAA；客户端像访问 IPv6 地址一样连接；NAT64 网关识别该前缀并把流量转换到 IPv4 站点。

这里的“合成 AAAA”只是帮助客户端找到翻译入口，不代表网站本身真的支持 IPv6。链路上的 NAT64 设备维护必要映射和状态，可能成为容量与故障点。运营网络中还可能结合 464XLAT 等机制支持只会使用 IPv4 地址字面量的旧应用，具体方案依终端与网络部署。

一个查询与连接算例

应用查 `legacy.example.test` 的 AAAA，权威区没有原生 AAAA，但有 A=198.51.100.20。DNS64 解析器可在其配置的 NAT64 前缀下合成一个 IPv6 目的地址，客户端向该 IPv6 地址发包；NAT64 网关将目的取回为 198.51.100.20，并使用自己的 IPv4 出口地址与端口建立映射。IPv4 网站的回复回到 NAT64，再转换给客户端。

如果网站已有可用的原生 AAAA，通常优先走真正的 IPv6 路径，而不是无故翻译。若客户端绕过运营商 DNS64、改用不做合成的外部 DoH 解析器，可能只得到 A 记录而应用又没有 IPv4 通路，表现为“换浏览器就打不开”。排查要记录客户端使用的实际解析器。

逐步推演

查询名称

DNS64 从 A 记录合成带 NAT64 前缀的 AAAA。

IPv6 发包

单栈客户端连接合成目的地址。

网关转换

NAT64 映射到 IPv4 站点及返回流。

验证应用

保留原域名做 Host/SNI 与证书校验。

字面量和内嵌地址问题

一些老应用不查 DNS，直接连接字符串 `198.51.100.20`，DNS64 没有机会合成 AAAA；只靠 DNS64/NAT64 可能无法支持。另一些协议把 IPv4 地址写进应用负载，网络层翻译也不会自动理解正文。464XLAT 中的 CLAT 可在客户端侧把 IPv4 调用转换成可走 IPv6 的形式，再由运营商 NAT64 侧处理，但并不是所有系统或应用都支持。

因此过渡测试不能只用域名打开一个网页，还要测 IPv4 字面量、应用内嵌地址、UDP、长连接和错误报文。最彻底的长期方案仍是服务提供原生 IPv6，而翻译用于兼容期。

TLS 与证书并未改变

客户端通过合成 IPv6 连接时，HTTP Host 和 TLS SNI 仍应使用原域名 `legacy.example.test`；服务器证书也应匹配该域名。NAT64 只翻译网络层地址及相关传输信息，不替用户伪造新的证书。若应用把合成 IPv6 当成 HTTPS 主机名去验证，可能产生名称不匹配。

端到端日志会出现两套地址视图：客户端看到合成 IPv6 目的，IPv4 网站看到 NAT64 出口的 IPv4 来源。排查与风控要把时间、端口映射和请求 ID 对齐；不能用服务器端看到的单一 NAT64 IPv4 地址识别真实用户。

DNSSEC 与合成回答

DNS64 合成的 AAAA 并非原权威区直接签发的 AAAA。若验证解析器和客户端 DNSSEC 验证策略配合不当，可能出现“有 A 记录但合成 AAAA 被拒”的问题。部署应按相关协议处理验证与合成的边界，不能通过全局关闭 DNSSEC 来掩盖配置错误。对业务侧，仍需验证最终 HTTPS 证书和服务响应。

缓存也会影响迁移：网站新增原生 AAAA 后，某些客户端或递归解析器仍短暂持有旧合成结果。观测应按解析器、终端和地区切片，别把一处成功当作全球路径已切换。

性能与故障边界

NAT64 网关的 CPU、映射表、IPv4 出口端口和带宽都可能成为瓶颈；网关故障时多个 IPv4-only 站点会同时不可达。路径多一跳也可能增加时延，尤其跨地域部署。按实际应用测 DNS 时间、TCP/QUIC 建连、丢包和大包传输，确认 ICMP 错误与路径 MTU 反馈能够跨翻译边界正确工作。

运营时区分三类目标：原生 IPv6、经 NAT64 的 IPv4 域名、无法 DNS64 合成的字面量。它们失败时的根因和修复动作不同。

排查顺序

先查终端是否确为 IPv6 单栈，再查目标 A/AAAA、使用的 DNS64 解析器及合成前缀；随后查前缀路由是否到 NAT64、网关映射和 IPv4 侧回程。最后检查 SNI、Host 与应用行为。对直接写 IPv4 地址的旧应用，确认是否有 CLAT 或其他兼容机制。每一步记录两侧地址视图，避免把“IPv6 客户端打不开 IPv4 服务”简单归咎于网站 DNS。

自检

IPv6-only 应用直接连接 IPv4 字面量时，DNS64 一定有用吗？

不一定。没有 DNS 查询就没有合成机会，可能需要 CLAT/464XLAT 或应用自身支持。
