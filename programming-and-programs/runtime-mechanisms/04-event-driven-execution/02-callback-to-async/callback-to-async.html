第一代

回调：简单直接，但会失控

// 回调地狱：层层嵌套，错误处理重复，逻辑难以阅读
readFile("a.txt", (err, data) => {
    if (err) return handle(err);
    writeFile("b.txt", data, (err) => {
        if (err) return handle(err);
        readFile("b.txt", (err, out) => {
            if (err) return handle(err);
            done(out);
        });
    });
});
回调的三个痛点：① 嵌套过深（回调地狱），可读性崩溃；② 错误处理重复，每层都要判 err；③ 控制流难以复用——想串行/并行/竞速都得手写。
第二代

Promise：把「未来的值」变成对象

Promise 表示一个尚未完成但最终会有结果的操作。它有 pending → fulfilled / rejected 三种状态，并可用 .then() 链式串联，从而把嵌套拉平成链条。

// 链式调用：扁平、可组合、错误统一捕获
readFile("a.txt")
    .then(data => writeFile("b.txt", data))
    .then(() => readFile("b.txt"))
    .then(out => done(out))
    .catch(err => handle(err));   // 一处捕获全链路错误

// 组合能力
Promise.all([p1, p2, p3])        // 全部完成
Promise.race([p1, p2])           // 取最快
Promise.allSettled([p1, p2])     // 无论成败都等齐
第三代

async/await：用同步写法表达异步

// 语法糖：本质是 Promise + 生成器，但写法跟同步代码一样
async function run() {
    try {
        const data = await readFile("a.txt");
        await writeFile("b.txt", data);
        const out = await readFile("b.txt");
        done(out);
    } catch (err) {
        handle(err);          // try/catch 直接捕获异步错误
    }
}

await 会「暂停」什么？它暂停的是当前 async 函数的执行，而不是整个线程。await 让出控制权后，事件循环继续处理其它任务；等 Promise 完成后再恢复该函数。所以单线程下依然能并发处理大量 I/O。

常见误区

🐌
顺序 await 拖慢速度
多个互不依赖的异步任务被逐个 await，总耗时是串行之和。应改用 Promise.all 并发
🔒
同步代码阻塞事件循环
在异步函数里跑 CPU 密集的同步代码，会卡住整个循环。应拆分为小任务或交给工作线程
💥
忘记 await
拿到的是 Promise 而非结果，且异常不会被 catch 捕获，变成未处理的 rejection
♾️
并发 vs 并行混淆
单线程 async 是并发（交替处理），不是并行（同时执行）。CPU 密集任务需要多进程/多线程
面试问答

高频问题

Q1：Promise 解决了回调的什么问题？
把嵌套回调拉平成链式调用；提供统一的错误捕获（catch）；并提供 all/race/allSettled 等组合能力，使串行、并行、竞速等控制流可以简洁表达。
Q2：async/await 和 Promise 是什么关系？
async/await 是建立在 Promise 之上的语法糖。async 函数返回 Promise，await 等待一个 Promise。它不改变异步本质，只是让代码写法更接近同步。
Q3：await 会阻塞线程吗？
不会。await 只暂停当前 async 函数的执行并让出控制权，事件循环继续处理其它任务；Promise 完成后再恢复该函数。因此单线程下仍能高并发处理 I/O。
Q4：多个互不依赖的异步任务怎么写最快？
用 Promise.all 并发发起，再统一 await 结果。逐个 await 会串行化，总耗时等于各任务耗时之和。
Q5：并发和并行有什么区别？
并发是「交替处理多个任务」，宏观上同时进行、微观上切换；并行是「真正同时执行」，需要多核或多机。单线程 async 提供的是并发，不是并行。
Q6：为什么 async 函数里跑 CPU 密集代码会卡住？
因为事件循环是单线程执行的，同步的 CPU 密集代码会一直占用主线程，使其它任务和回调无法被处理。应拆分任务或交给工作线程/子进程。

三代异步写法

# ① 回调地狱（callback hell）—— 早期 Node.js 的典型
readFile("a.txt", (err, a) => {
    if (err) return handle(err);
    readFile("b.txt", (err, b) => {
        if (err) return handle(err);
        writeFile("c.txt", a + b, (err) => {
            if (err) return handle(err);
            console.log("done");
        });
    });
});
# 问题：① 缩进越来越深 ② 错误处理重复 ③ 无法用 for/try 等同步控制流

# ② Promise 链式
readFile("a.txt")
  .then(a => readFile("b.txt").then(b => [a, b]))
  .then(([a, b]) => writeFile("c.txt", a + b))
  .then(() => console.log("done"))
  .catch(handle);                       # 一个 catch 兜住所有错误
# 改善：扁平化 + 统一错误处理

# ③ async/await（最终形态）
async function main() {
    try {
        const a = await readFile("a.txt");
        const b = await readFile("b.txt");
        await writeFile("c.txt", a + b);
        console.log("done");
    } catch (err) {                     # 同步风格的 try/catch！
        handle(err);
    }
}
# 关键：代码长得像同步，但执行是非阻塞的

# ⚠️ 常见错误：串行 await（忘了并发）
const a = await fetchA();               # 等 100ms
const b = await fetchB();               # 又等 100ms -> 共 200ms
# ✅ 并发
const [a, b] = await Promise.all([fetchA(), fetchB()]);   # 共 100ms

async/await 的本质：语法糖 + 状态机

async/await 并没有发明新机制，它是基于 Promise 的语法糖——编译器（或解释器）把它转换成状态机 + 回调。理解这一点能帮你搞懂为什么 await 之后“代码的局部变量还在”。

async/await 展开

# Python 的等价展开（理解 await 的本质）
# 你写的代码：
async def fetch_all():
    a = await fetch("a")      # ① 暂停点
    b = await fetch("b")      # ② 暂停点
    return a + b

# 运行时大致等价（概念上）：
class FetchAllCoroutine:
    def __init__(self): self.state = 0; self.a = None
    def send(self, value):
        if self.state == 0:
            fut = fetch("a")
            fut.add_done_callback(self.resume)   # 完成后回调我
            self.state = 1
            return fut                            # 让出控制权给事件循环
        if self.state == 1:
            self.a = value                        # 接收 fetch("a") 的结果
            fut = fetch("b")
            fut.add_done_callback(self.resume)
            self.state = 2
            return fut
        if self.state == 2:
            return StopIteration(self.a + value)

# 关键理解：
#   ① await = "注册回调 + 让出控制权"，不是"阻塞等待"
#   ② 局部变量 a、b 存在<b>协程对象</b>里（不是栈上），所以恢复后还在
#   ③ 事件循环负责：IO 完成 -> 找到对应协程 -> send(result) 恢复执行

# C# 的 async/await 是编译器生成状态机（IL 层面）
# JavaScript 的 async 函数返回 Promise，由引擎实现
# Python 的 async 函数返回 coroutine，由事件循环驱动

最关键的一句话：await 让出的是当前协程的执行权，而不是整个线程。线程会立刻去跑其他协程——这就是异步能并发的根本原因。

事件循环：异步的发动机

阶段（以 Node.js 为例）做什么典型耗时
① timers执行 setTimeout/setInterval—
② pending callbacks上一轮遗留的系统回调—
③ poll等待 IO 事件（可能阻塞）主要耗时在这里
④ check执行 setImmediate—
⑤ close callbacks关闭事件的回调—
微任务（每阶段之间）Promise.then、process.nextTick必须清空才进下一阶段

事件循环顺序

# Node.js 事件循环顺序验证（经典面试题）
console.log("1");                       # 同步
setTimeout(() => console.log("2"), 0);  # 宏任务（timers）
Promise.resolve().then(() => console.log("3"));   # 微任务
process.nextTick(() => console.log("4"));         # 微任务（优先级最高）
console.log("5");                       # 同步
# 输出：1 5 4 3 2
# 规则：同步 -> nextTick -> Promise微任务 -> 宏任务

# ⚠️ 微任务饿死事件循环（真实的生产事故）
function starve() {
    Promise.resolve().then(starve);     # 无限递归创建微任务
}
starve();
setTimeout(() => console.log("永远不执行"), 0);
# 因为每轮都要<b>清空微任务队列</b>才能进入下一阶段
# -> 微任务永远清不完 -> timers 阶段永远到不了

# Python asyncio 的等价问题
async def bad():
    while True:
        await asyncio.sleep(0)          # 让出但立刻要回来 -> 其他任务饥饿
# 正确：用 await asyncio.sleep(0.001) 或让出给真正的 IO

# 观测事件循环延迟（Node.js）
const {monitorEventLoopDelay} = require('perf_hooks');
const h = monitorEventLoopDelay(); h.enable();
setInterval(() => console.log(`延迟 p99: ${h.percentile(99)/1e6}ms`), 5000);
# 健康值：p99 < 10ms；大于 50ms 说明有阻塞操作

深入自检

async/await 真的比回调快吗？

不是，甚至略慢——async/await 有状态机创建和协程调度的开销，纯性能上回调最快。但它带来的价值是可维护性：错误处理从“每个回调写一遍 if(err)”变成“一个 try/catch 兜住”，控制流从嵌套变成线性的。实测：Node.js 中 async 函数比等价的回调慢约 10 – 30%，但在绝大多数应用中这点开销完全被 IO 等待时间淹没。结论：除非在极端热路径（每秒百万次调用），否则一律用 async/await。

Promise.all 和 Promise.allSettled 怎么选？

Promise.all：任一失败就整体 reject——适合“所有都必须成功”的场景（如加载页面必需的多个配置）；allSettled：等所有都结束，返回每个的成功/失败状态，适合“部分失败可接受”的场景（如批量发送通知，失败几个没关系）。另外 Promise.race（第一个结束的就返回，无论成败）常用于超时控制；Promise.any（第一个成功的）——适合多源冗余取最快。Python 的 asyncio 对应：gather(return_exceptions=True) ≈ allSettled；wait(FIRST_COMPLETED) ≈ race。

异步代码里怎么做好错误处理？

四个层次：① 局部 try/catch——包裹可能失败的 await；② 并发时区分处理——allSettled 或 gather(return_exceptions=True) 收集所有错误；③ 超时——每个外部调用都要有 timeout（否则一个慢调用拖垮整个流程）；④ 全局兜底——进程级 unhandledRejection/uncaughtException 监听器，记录日志并优雅退出（不要继续跑，状态可能已不一致）。最常见的疏漏：忘记给 await 加超时，以及Promise 创建后没有 catch（错误被静默吞掉）。

回调里的 this 丢失是怎么回事？

JavaScript 的经典问题：this 由调用方式决定，把方法当回调传出去后，this 会变成调用者（通常是 undefined 或全局对象）。三种解法：① 箭头函数——() => this.method()，箭头函数不绑定自己的 this，继承外层（最常用）；② bind——this.method.bind(this)；③ 保存引用——const self = this（老写法）。Python 里没有这个问题（方法的 self 是显式参数），但要注意闭包捕获循环变量的等价陷阱。
