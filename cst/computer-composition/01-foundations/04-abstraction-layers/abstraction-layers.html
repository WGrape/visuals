七层抽象：从晶体管到应用，每一层的契约是什么

计算机不是一层层「叠加」出来的，而是一层层「隐藏」出来的。理解每一层向上承诺了什么、向下依赖什么，才知道为什么同一段代码在不同 CPU 上快慢差 10 倍，也才知道性能问题该在哪一层修。

一句话定位：分层就是「用契约换复杂度」

每一层都只向上暴露少数接口，把下层的复杂度藏起来。ISA 承诺「执行 add 就把两个数相加」，但不承诺用几个周期、走哪条数据通路——这正是同一份 x86 二进制能在 Intel 与 AMD 上运行、性能却不同的原因。

ISA 是契约指令语义、寄存器、地址空间、内存模型由 ISA 定义
微架构是实现流水线深度、乱序窗口、缓存大小由厂商自由决定
向上泄漏性能、原子性、内存序是「藏不住」的三件事
典型数量级5nm 门延迟约 10ps；3GHz 一个周期 333ps ≈ 33 个门延迟
七层抽象：只有 ISA 这一层同时被软件和硬件当作「合同」

每层在隐藏什么、泄漏什么

层向上提供的抽象隐藏了什么泄漏出来的证据
应用 / 算法函数、SQL、API数据放在哪、怎么调度同一算法不同实现差 10×
OS / ABI进程、虚拟地址、系统调用物理页、缺页、调度缺页抖动、NUMA 远端访问慢 2×
ISA指令语义、寄存器、内存序模型周期数、并行度、微架构细节同 ISA 不同 CPU 的 IPC 差 1.5×
微架构「指令按序执行」的假象乱序、预测、缓存、重命名Spectre 侧信道、伪共享
RTL / 门布尔逻辑、时序约束晶体管尺寸、布线电容频率上不去、功耗墙
晶体管开关行为量子效应、漏电5nm 以下漏电占比上升
性能与正确性都活在「泄漏」里

「分层」在功能上很干净，但在性能上从不成立：如果代码真的只依赖 ISA 语义，就不会有缓存友好、分支友好这些说法。优化的本质，就是故意向下看一层。

一条 a + b 要穿过几层

  1. 编译器把它变成 add eax, ebx（或 add w0, w1, w2），这是 ISA 层。
  2. 前端把指令取进流水线，译码成微操作（x86 的 add 通常 1 个 μop）。
  3. 调度器把它发射到整数执行单元，等两个操作数就绪（乱序执行）。
  4. ALU 内部是加法器：如进位选择或前缀结构，延迟 1~4 个周期。
  5. 结果写回寄存器堆，并更新标志位（CF/OF/ZF/SF）。
  6. 如果操作数在内存里，前面还要插一次 load，命中 L1 是 4 个周期，落空到 DRAM 是 200~300 个周期。
# 同一行 C 代码，四种命运
a + b;                    # 操作数在寄存器：~1 cycle
a + arr[i];              # L1 命中：~5 cycles
                          # L3 命中：~40 cycles
                          # DRAM：~250 cycles
                          # 缺页到磁盘：~10^7 cycles

现象被打破的抽象真实原因怎么修

为什么必须在两层之间做取舍

抽象的每一层都在用「通用性」换「效率」：ISA 越通用，越难为某个场景特化；微架构越激进（深流水、大乱序窗口），单核频率与能效越难兼顾。工程上的每一次重大性能跃迁，几乎都是「把某一层的抽象做得更贴合上层」——CISC 到 RISC、单核到多核、同构到异构，都是这个模式。

既然 ISA 是契约，为什么 ARM 程序不能在 x86 上直接跑？

ISA 不同就是契约不同：指令编码、寄存器数量、内存序模型都不一样。翻译层（如 Rosetta 2）本质上是在软件里重建一份契约，代价是翻译开销与语义差异（尤其内存序与浮点）。

微架构可以随便改吗？

功能上可以（只要 ISA 语义不变），工程上不行：操作系统、编译器、性能调优都隐式假设了一些微架构特征（缓存行 64B、页 4KB、TLB 层级）。这些「事实标准」改起来要动整个生态。

学组成原理为什么要背延迟数字？

因为分层的效率差异是数量级的，不是百分比的。知道 L1 与 DRAM 差 60 倍，才会本能地去想「这个循环的数据是不是能放进缓存」，而不是去抠一条指令的写法。
