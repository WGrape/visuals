Beam Search：保留多条最优路径的确定性解码

翻译和摘要的老王者，为什么到了对话和写作反而被弃用？

定位

不做随机采样，而是"多路并进找最优"

贪心解码每步只走概率最高的一个词，容易走进局部最优；Beam Search 每步保留概率最高的 B 条完整序列（束宽 beam width），最后输出整体概率最大的那条。它是确定性解码：同样输入永远同样输出。

过程

B=3 时的一步发生了什么

打分用累计 log 概率：逐词概率连乘会下溢，实践中用 log 概率求和；长序列天然吃亏（乘的负数多），所以常配长度惩罚（length penalty）防止系统偏向短输出。
反思

为什么 ChatGPT 们不用 Beam Search

输出千篇一律
永远选"最安全"的话，多样性归零——对话场景显得机械、没人味
高概率 = 高质量？
开放生成里人类偏好不等于模型概率最大；研究表明 beam 过宽反而产生重复、空洞的文本
计算贵
每步要算 B 份前向，显存与延迟按倍数涨；KV cache 也更难复用
随机性有价值
采样（温度/top-p）能带来自然表达与可控多样性，一个 seed 就能重 roll

什么时候仍然用它

面试问答

高频问题

Q1：Beam Search 和贪心解码的关系？
贪心是束宽 B=1 的特例：每步只保留一条路径。B 增大则搜索更充分、结果更好，但计算与显存开销线性增加，且输出永远确定。
Q2：为什么需要长度惩罚？
累计 log 概率是负数连加，序列越长分数越低，Beam 会系统性偏爱短输出。长度惩罚（除以长度的 α 次幂）校正这种偏置。
Q3：为什么对话模型不用 Beam Search？
开放对话没有唯一正确答案，概率最大 ≠ 人类偏好；Beam 输出保守重复、缺乏多样性，且计算开销大。采样类解码（温度 + top-p）更自然可控。
Q4：Beam width 越大效果一定越好吗？
不。研究表明束宽过大后翻译 BLEU 等指标反而下降，且开放生成中出现更多重复退化。存在一个适度区间（常见 4~10）。
Q5：Beam Search 和 Best-of-N 的区别？
Beam 是每步剪枝的确定性搜索，全程只维护 B 条路径；Best-of-N 是独立采样 N 个完整答案再挑最好的（可配验证器打分），天然并行、多样性更好，是推理模型时代的主流。

它优化的是「整句概率最大」，不是「说得最好」

Beam Search 的目标函数非常明确：找到使 P(整句) 最大的序列。这和人类认为的「好回答」不是一回事——人类偏好有信息量、有变化、不啰嗦的文本，而最大概率序列往往是安全、通用、重复的。这就是为什么对话模型几乎不用 beam search。

Beam Search 与采样方法对比

方法是否确定性多样性适合任务主要问题
贪心 (B=1)是无结构化输出、代码、抽取容易陷入重复，错过全局更优解
Beam Search是（给定 B）低（B 条之间相似）翻译、ASR、摘要、Caption文本呆板、重复、过长/过短偏置明显
Top-K/Top-P 采样否高对话、创作、头脑风暴可能不连贯、事实性差

Diverse Beam Search是中需要 n-best 且有差异的场景实现复杂，收益依赖调参
约束解码（CFG/JSON mode）是受约束限制必须满足格式/语法的输出需要语法定义，可能抑制合理表达

选型一句话：有明确「最优答案」且可用指标衡量 → Beam Search；要多样与自然 → 采样；有可自动验证的答案 → Best-of-N + 验证器（这也是推理模型的主流做法）。

工程要点与常见坑

① 长度偏置必须处理

  • 对数概率是负数累加，句子越长总分越低，天然偏向短句。
  • 用 length_penalty：score = sum_logp / (len^α)，α 越大越鼓励长句。
  • 也可用 avg_logp，但会过度鼓励长句，需实测权衡。

② 重复问题

  • Beam Search 极易产出「车轱辘话」，因为重复是高概率路径。
  • 缓解：no_repeat_ngram_size（禁重复 n-gram）、重复惩罚、或改用采样。
  • 对话场景基本属于「用了就后悔」，除非有强验证器。

③ 计算与显存

  • B 条路径可批处理并行，显存约为 B 倍但可共享 KV 前缀。
  • 前缀共享能显著省算力：B 条路径前几步通常相同。
  • 早停（early stopping）：所有路径都生成 EOS 后停止，避免无谓计算。

④ 与 KV Cache / 批处理

  • Beam Search 每步路径集合会变化，KV Cache 管理比单条生成复杂。
  • 实现时要正确重组 batch（哪些路径存活、哪些被剪）。
  • 很多推理框架的 beam search 实现效率低于采样，压测时要单独测。

深入自检

Beam Search 能保证找到最优解吗？

不能。它每步只保留当前累计分数最高的 B 条，是「逐步贪心」的近似搜索。若真正最优序列的前缀在某个中间步骤分数偏低，就会被永久剪掉，之后再也无法找回。这是剪枝搜索的固有局限。

为什么对话模型基本不用 Beam Search？

因为最大概率序列往往对应最平庸、最安全的回复，容易出现套话与重复，人类评分反而低于采样结果。再加上对话没有单一正确答案，追求「最大概率」本身就是错的目标函数。

Beam Search 在哪些场景仍然值得用？

机器翻译、语音识别、图像描述这类有较明确参考解、且可用 BLEU/WER/CIDEr 衡量优劣的任务；以及需要 n-best 候选供下游重排的场景。此外在需要确定性可复现输出的内部流程里也有价值。

B 越大越好吗？

不是。B 增大初期质量提升明显，但很快饱和；B 过大时（如 >16）文本会更冗长、更呆板，且计算线性增长。经验区间是翻译 4-8、ASR 8-16，需要实测确定。

num_return_sequences 返回的 n-best 有用吗？

有用但要注意：beam 的 n-best 之间往往只差几个词，多样性很低。如果需要真正有差异的候选，应该用采样生成 N 个，或用 diverse beam search。

为什么我用了 beam search 输出反而变差了？

最常见三个原因：① 没开长度惩罚，输出过短；② 没有禁用重复 n-gram，输出复读；③ 把本该用采样的开放生成任务硬套了 beam search。先确认任务性质，再决定解码策略。
