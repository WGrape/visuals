理解为什么哈希表需要扩容、常见的扩容策略及如何实现

🤔 为什么 Hash 需要扩容？

🔑 装载因子 (Load Factor)

装载因子 = 元素数 / 桶数。当装载因子过高时，碰撞概率急剧上升，查找效率从 O(1) 退化到 O(n)。Java HashMap 默认在 0.75 时触发扩容。

⚡ 保持性能

哈希表的核心优势是 O(1) 平均查找。扩容通过增加桶的数量，将元素重新分布，降低碰撞概率，保持性能稳定。

📊 时间换空间

扩容的 rehash 操作是一次性开销，但换来了长期稳定的查询性能。这是一种典型的"空间换时间"策略。

📐 常见的 Hash 扩容方案对比

🔢 倍增扩容 最常用

每次扩容为原来的 2 倍（newSize = oldSize × 2）。

Java HashMap、Go map、Python dict 等均采用此方案。优点是实现简单、扩容次数少、index = hash & (n-1) 位运算高效。

🔒 质数扩容 Redis 使用

每次扩容到下一个质数（8 → 17 → 37 → 79...）。

Redis dict 默认使用。质数模运算使哈希分布更均匀，减少聚集效应，但需要维护质数表。

📈 递增扩容 渐进式

每次扩容增加固定数量（如 +8、+16），或者不一次性完成，而是分批迁移旧数据。

优点是避免单次扩容的停顿时间，Redis 和 Go 的 map 都采用渐进式 rehash。

🛠️ 扩容是如何实现的？

1

检测是否触发扩容

每次插入时检查 装载因子 = count / buckets >= 阈值（通常 0.75），超过阈值则触发扩容。

2

分配新桶数组

根据所选策略确定新大小（2x、下一个质数、+N），创建新的空桶数组。

3

遍历旧桶，逐元素 Rehash

遍历每个旧桶中的每个元素，用新的桶数重新计算 newIndex = hash(key) % newSize，插入到对应的新桶中。

4

替换 & 释放旧数组

将桶数组指针指向新数组，释放旧数组内存。如果是渐进式 rehash，则逐步完成迁移。

扩容是哈希表的「成长烦恼」

哈希表用「数组 + 哈希函数」把 key 映射到下标。数组大小固定，元素多了冲突就多、查找就慢。所以必须在元素变多时扩容：换一个更大的数组，把所有元素重新安置。难点在于：这次搬迁是 O(n) 的，而在线服务不允许长时间停顿——于是有了各种渐进方案。

核心思想都一样：把一次不可接受的 O(n) 停顿，拆成许多次可接受的 O(1) 开销。这是系统设计里非常常见的一种「摊还」思维。

冲突处理与工程细节

① 两种冲突处理

  • 链地址法：冲突元素挂在同一个桶的链表/树上；实现简单，容忍高负载。
  • 开放寻址法：冲突就往后找空位；缓存友好、无指针开销，但删除麻烦（要墓碑标记）、负载必须低。
  • Java 8+ 的 HashMap：链表超过 8 且桶数 ≥64 时转红黑树，防止哈希攻击退化成 O(n)。
  • Python dict 用开放寻址，负载因子 2/3 扩容。

② 为什么容量取 2 的幂

  • 可以用位运算 hash & (cap-1) 代替取模，快得多。
  • 代价：对低位规律性强的 key 容易产生冲突，所以要先把 hash 值「扰动」（如 Java 的高 16 位异或低 16 位）。
  • 扩容时元素只会去「原位置」或「原位置 + 旧容量」两处，搬迁判断极快（Go 的 evacuate 就利用这点）。

③ 扩容时机的坑

  • 阈值设太高：冲突多，查找退化。
  • 阈值设太低：内存浪费、扩容频繁。
  • 缩容要有滞后（hysteresis）：扩容阈值与缩容阈值分开，否则在临界点反复抖动。
  • 批量插入前可预留容量（reserve），避免多次扩容。

④ 并发环境下的扩容

  • 扩容期间读写要同时能看到新旧两张表。
  • JDK 8 的做法：写线程协助迁移，迁移完成前读操作按桶状态决定查哪张表。
  • 要避免死锁与重复迁移（用标记与原子操作保护）。
  • 旧实现（JDK 7）曾因并发扩容时链表成环导致 CPU 100%，是经典事故。

深入自检

为什么不能等表满了再扩容？

因为冲突会随负载因子急剧上升。开放寻址法下，负载因子接近 1 时查找需要探测的次数趋于无穷；链地址法下链表会很长。所以在负载因子还不高（如 0.75）时就扩容，是用空间换时间，保证均摊 O(1)。

扩容一定要翻倍吗？

不一定，但翻倍最常见：一是 2 的幂便于位运算取模；二是扩容的摊还成本最优（每次扩容成本翻倍但频率减半，总摊还是 O(1)）。有些实现用 1.5 倍或素数容量（素数能减少某些哈希函数的规律性冲突）。

为什么开放寻址法删除元素要「墓碑」？

因为探测链是连续的：如果直接把槽位清空，后面因冲突被放到更远位置的元素就「断链」了，查找会提前终止而找不到它们。所以删除时标记为墓碑（已删除但继续探测），查找时跳过、插入时可复用。墓碑多了要及时重建，否则性能下降。

渐进式扩容期间查找怎么做？

两条路都查：先查新表，未命中再查旧表（或按迁移进度判断该查哪张）。插入只写新表，保证旧表只减不增、迁移必然收敛。Redis 的 dict 正是这套逻辑，用 rehashidx 记录进度。

预分配容量真的有用吗？

有用，尤其是批量插入场景。每次扩容都要重新分配更大数组并搬移全部元素，成本很高。预先 reserve 到接近最终规模，可以把 n 次扩容降为 0-1 次。对性能敏感的路径（如启动加载、批量导入）效果明显。

哈希攻击是什么，怎么防？

攻击者构造大量哈希值相同的 key，使哈希表退化成链表，单次操作从 O(1) 变成 O(n)，大量请求即可耗尽 CPU（DoS）。防护手段：使用带随机种子的哈希函数（如 SipHash）、链表过长时转为树（Java 8+）、限制单次请求的参数数量。
