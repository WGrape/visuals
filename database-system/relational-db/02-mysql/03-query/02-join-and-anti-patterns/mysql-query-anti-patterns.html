🚫 MySQL查询性能陷阱

动态可视化 - 深入理解索引失效的原理

1

LIKE '%keyword%' - 前置百分号陷阱

索引失效

📝 代码示例

-- ❌ 错误：前置百分号，索引失效
SELECT * FROM users WHERE name LIKE '%明%';

-- 原因：B+树无法定位起始位置

-- ✅ 正确：后置百分号，可以使用索引
SELECT * FROM users WHERE name LIKE '张%';

🎯 B+树索引查找原理

💡 原理解释

  • B+树索引是有序存储的，支持前缀匹配
  • LIKE '张%'：可以从"张"开始定位，然后顺序扫描
  • LIKE '%明%'：无法知道起始位置，只能全表扫描
  • 解决方案：使用全文索引、搜索引擎（Elasticsearch）
🐌
LIKE '%明%'
全表扫描
100万行 → 扫描100万次
⚡
LIKE '张%'
索引查找
100万行 → 扫描50次
2

NOT IN - 子查询陷阱

性能+NULL陷阱

📝 代码示例

-- ❌ 错误：NOT IN 有NULL陷阱
SELECT * FROM orders WHERE user_id NOT IN (SELECT user_id FROM blacklist);

-- 如果blacklist中有NULL，整个查询返回空！
-- SELECT 1 NOT IN (2, NULL) → 返回NULL，不是TRUE

-- ✅ 正确：使用 NOT EXISTS
SELECT * FROM orders o WHERE NOT EXISTS (
  SELECT 1 FROM blacklist b WHERE b.user_id = o.user_id
);

🎯 NOT IN vs NOT EXISTS 执行过程

💡 原理解释

  • NULL值陷阱：NOT IN (1, 2, NULL) 永远返回FALSE
  • 性能问题：子查询可能执行多次，无法优化
  • NOT EXISTS优势：遇到NULL正确处理，可以使用关联索引
  • 解决方案：用NOT EXISTS、LEFT JOIN + IS NULL替代
3

索引列上计算 - 函数陷阱

索引失效

📝 代码示例

-- ❌ 错误：在索引列上使用函数
SELECT * FROM users WHERE YEAR(create_time) = 2024;
SELECT * FROM users WHERE age + 1 > 20;

-- 原因：索引存储的是原始值，不是计算结果

-- ✅ 正确：将计算放在等号右边
SELECT * FROM users WHERE create_time >= '2024-01-01' AND create_time < '2025-01-01';
SELECT * FROM users WHERE age > 19;

🎯 索引存储 vs 计算后的结果

💡 原理解释

  • 索引存储：B+树中存储的是列的原始值（如：2024-05-01）
  • 函数计算：YEAR(create_time)需要对每一行进行计算
  • 无法使用索引：索引树按原始值排序，不是按函数结果排序
  • 解决方案：将计算放在等号右边，使用范围查询
🚫
YEAR(create_time)
全表扫描
每行都要计算函数
✅

索引范围扫描
直接定位索引范围

OR 条件 - 索引合并陷阱

可能索引失效

📝 代码示例

-- ❌ 危险：OR 可能导致全表扫描
SELECT * FROM users WHERE name = '张三' OR age = 20;

-- 如果name有索引，age没有索引 → 全表扫描

-- ✅ 正确：使用 UNION 替代 OR
SELECT * FROM users WHERE name = '张三'
UNION
SELECT * FROM users WHERE age = 20;

🎯 OR vs UNION 执行计划对比

💡 原理解释

  • OR的问题：需要同时满足两个条件的索引才能使用索引合并
  • 索引合并：MySQL可能使用index_merge，但效率低
  • UNION优势：每个子查询可以使用自己的索引
  • 最佳实践：确保OR的每个条件都有索引，或用UNION重写

📊 性能对比总结

场景 错误写法 正确写法 性能提升
LIKE查询 '%keyword%' 'keyword%' 100x ⬆️
NOT IN NOT IN (子查询) NOT EXISTS 10x ⬆️
索引列计算 YEAR(column) column >= 'value' 50x ⬆️
OR条件 WHERE a=x OR b=y UNION 5x ⬆️

怎么判定：从执行计划读出反模式

反模式不是靠背清单，而是靠执行计划里的三个数：type（访问类型）、rows（预估扫描行数）、Extra（额外动作）。看到 ALL + 大 rows + Using filesort 就是问题信号。

type 值含义相对代价出现时意味着什么
system / const单行命中主键或唯一键1最好情况
eq_refjoin 时命中主键/唯一键1~2join 的理想状态
ref非唯一索引等值匹配几~几十可接受
range索引范围扫描几十~几百还行，但要看 rows
index全索引扫描几百~几千没走过滤，等于扫整个索引
ALL全表扫描最差索引失效，rows 通常巨大

诊断命令

-- 标准诊断动作：先看实际执行计划，再看真实扫描行数
EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND status = 1;
EXPLAIN FORMAT=JSON SELECT ...;                 -- JSON 版信息更全（含 cost 估计）

-- MySQL 8.0.18+：EXPLAIN ANALYZE 给出真实耗时与实际返回行数（最准）
EXPLAIN ANALYZE SELECT * FROM orders WHERE created_at >= '2026-10-01';

-- 对比预估与实际的偏差（偏差大说明统计信息过期）
ANALYZE TABLE orders;                            -- 重新采样统计信息
SHOW INDEX FROM orders;                          -- 看 Cardinality（区分度）

-- 开启慢查询日志：默认 long_query_time = 10s，线上通常改 1s 甚至 0.5s
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;
SET GLOBAL log_queries_not_using_indexes = ON;   -- 记录没走索引的查询
SHOW VARIABLES LIKE 'slow_query_log_file';

最容易被忽略的一条：隐式类型转换。当列是 VARCHAR 而条件写成数字时（WHERE phone = 13800138000），MySQL 会对列做 CAST，索引直接失效；反过来（INT 列传字符串）则不会失效——因为转换发生在常量侧。

改写模板与检查清单

五种改写模板

-- 1) 深分页改写：从 OFFSET 改成游标（keyset pagination）
-- 慢：跳过 10 万行再取 20 行
SELECT * FROM orders ORDER BY id LIMIT 100000, 20;
-- 快：以上一页最大 id 为起点
SELECT * FROM orders WHERE id > 100000 ORDER BY id LIMIT 20;

-- 2) 函数改写到常量侧
-- 慢：对索引列做运算
SELECT * FROM orders WHERE DATE(created_at) = '2026-10-01';
-- 快：改成范围
SELECT * FROM orders WHERE created_at >= '2026-10-01' AND created_at < '2026-10-02';

-- 3) OR 改 UNION ALL（各分支都能走索引）
-- 慢
SELECT * FROM orders WHERE user_id = 1 OR status = 9;
-- 快
SELECT * FROM orders WHERE user_id = 1
UNION ALL
SELECT * FROM orders WHERE status = 9 AND user_id <> 1;

-- 4) NOT IN 改 NOT EXISTS
-- 慢
SELECT * FROM users WHERE id NOT IN (SELECT user_id FROM banned);
-- 快（且不受 NULL 语义影响）
SELECT u.* FROM users u WHERE NOT EXISTS (SELECT 1 FROM banned b WHERE b.user_id = u.id);

-- 5) 覆盖索引：Extra 出现 Using index 即无需回表
CREATE INDEX idx_user_status_time ON orders(user_id, status, created_at);
SELECT user_id, status FROM orders WHERE user_id = 100;   -- 只查索引就能返回

上线前逐条核对：

  • 每条核心 SQL 都要 EXPLAIN：看 type 是不是 ALL、rows 是不是远大于返回行数。
  • 用 EXPLAIN ANALYZE 看真实数据（8.0.18+），预估与实际的偏差往往很大。
  • 统计信息要定期 ANALYZE：数据分布变化大时，优化器会选错索引。
  • 索引列不要套函数，把运算挪到常量侧。
  • 比较两侧类型必须一致，字符串列别传数字。
  • join 的两列字符集与排序规则要一致，否则索引失效。
  • 禁止 SELECT *：多取一列就可能失去覆盖索引的机会。
  • 深分页改游标分页，不要用 OFFSET 跳几万行。
  • 联合索引遵循最左前缀，并把等值条件列放前面、范围列放后面。
  • 改完要对比 rows 与耗时，不能只看「看起来走了索引」。
