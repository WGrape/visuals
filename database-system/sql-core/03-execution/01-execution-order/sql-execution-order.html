① 核心结论 ② 完整流水线 ③ 别名可见性 ④ 为什么这样设计 ⑤ 常见疑问
一句话总结：你按 SELECT ... FROM ... WHERE ... 的顺序写， 数据库却按 FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT 的顺序执行。 这个错位解释了大量"看起来应该能跑却报错"的现象——最典型的就是 WHERE 里用不了 SELECT 的别名。

CTE（WITH 子句）的位置

CTE 在整个查询开始前先执行，生成一个临时的命名结果集， 然后被主查询当作普通表引用：

WITH dept_avg AS (                    -- ① CTE 先算好
    SELECT dept, AVG(salary) avg_sal
    FROM employees GROUP BY dept
)
SELECT e.name, e.salary, d.avg_sal     -- ② 主查询再引用
FROM employees e
JOIN dept_avg d ON e.dept = d.dept
WHERE e.salary > d.avg_sal;            -- 高于部门平均的人

-- MySQL 8.0+ 才支持 CTE；也支持递归 CTE（WITH RECURSIVE）

03别名可见性：一张表说清

子句能引用 SELECT 里定义的别名吗原因
WHERE❌ 不能（标准 SQL）WHERE 在 SELECT 之前执行，别名还不存在
GROUP BY✅ 可以（MySQL 扩展）MySQL 允许，但这是非标准扩展；PG 也支持，Oracle 不支持
HAVING✅ 可以（MySQL）MySQL 扩展。但标准写法是重复聚合表达式
ORDER BY✅ 可以（标准）ORDER BY 在 SELECT 之后执行，别名已存在
LIMIT—LIMIT 不引用列
-- ❌ 报错：WHERE 里用 SELECT 定义的别名
SELECT salary * 12 AS annual FROM employees WHERE annual > 500000;

-- ✅ 方案 1：重复表达式
SELECT salary * 12 AS annual FROM employees WHERE salary * 12 > 500000;

-- ✅ 方案 2：包一层子查询
SELECT * FROM (
  SELECT salary * 12 AS annual FROM employees
) t WHERE annual > 500000;

-- ✅ 方案 3：用 HAVING（MySQL 支持引用别名，但需配合 GROUP BY 语义）
-- 最通用清晰的是方案 2

-- ✅ ORDER BY 可以直接用别名（标准行为）
SELECT salary * 12 AS annual FROM employees ORDER BY annual DESC;
跨数据库差异：MySQL 允许在 GROUP BY / HAVING 里用别名， 但这是它自己的扩展，SQL 标准和 Oracle 都不允许。 写可移植的 SQL 时，只在 ORDER BY 里用别名，其它地方重复表达式或包子查询。

04为什么设计成这个顺序？

🎯 性能：尽早过滤

WHERE 排在最前面，是为了尽可能早地减少数据量。 先过滤掉 90% 的行，后面的分组、排序、连接代价都会小一个数量级。 这是最重要的优化原则——谓词下推。

🧮 语义：分层计算

必须先有"行"（FROM/WHERE），才能"分组"（GROUP BY）； 必须先"分组"，才能算"组内聚合"并过滤（HAVING）； 最后才能"挑选输出列"（SELECT）。 顺序由数据依赖关系决定，不能颠倒。

🔤 别名：先定义后使用

别名在 SELECT 阶段才"诞生"， 所以只有 SELECT 之后的 ORDER BY 能用它。 这与大多数编程语言"先声明后使用"的规则一致。

📉 LIMIT 最后

只有全部计算、排序完成后才能安全地截断。 如果 LIMIT 提前，排序结果就不对了—— 这也是为什么"先 LIMIT 再 ORDER BY"是错的。

05常见疑问

Q：为什么 WHERE 里不能用 COUNT(*)，而 HAVING 里可以？
A：因为执行到 WHERE 时还没有分组，聚合值无从谈起。 HAVING 在分组之后执行，此时每组的聚合结果已经算出来了，自然可以过滤。 记住口诀：过滤原始行用 WHERE，过滤聚合结果用 HAVING。
Q：SELECT 里写的表达式会被计算几次？
A：逻辑上，WHERE 里重复写的表达式会被计算一次用于过滤， SELECT 里的同名表达式再算一次。 优化器通常能识别重复子表达式并复用，但不能保证。 对复杂/昂贵表达式，用 CTE 或子查询物化一次更稳妥。
Q：ORDER BY 和 GROUP BY 一起用会怎样？
A：MySQL 5.7 之前，GROUP BY 会隐式按分组列排序， 再加 ORDER BY 等于排两次（多余的排序）。 可用 ORDER BY NULL 显式禁止隐式排序。
MySQL 8.0 起不再隐式排序（除非你显式写 ORDER BY）， 且 ORDER BY NULL 被废弃——需要排序就明确写出来。
Q：LIMIT 和 ORDER BY 谁先执行？
A：ORDER BY 先，LIMIT 后。 先排好序，再取前 N 条。所以 SELECT ... ORDER BY id LIMIT 10 得到的是"最小的 10 个 id"， 而不是"先随便取 10 条再排序"。 深分页（LIMIT 100000, 10）慢正是因为要先排/扫完前 10 万行。

书写顺序 vs 执行顺序

SQL 是声明式语言：SELECT 写在最前面，却是倒数第三个执行的。理解这个顺序，就能解释绝大多数「为什么这个别名用不了」的问题。

步骤子句关键动作能不能用 SELECT 别名
1FROM确定数据源，做 JOIN 生成笛卡尔积并过滤不能
2ONJOIN 的连接条件不能
3JOIN补上 OUTER JOIN 未匹配的行不能
4WHERE行级过滤（在分组之前）不能（最常见错误）
5GROUP BY分组可以（MySQL 允许，标准 SQL 不允许）
6HAVING组级过滤（在分组之后）可以
7SELECT计算投影、生成别名—（这里才产生别名）
8DISTINCT去重可以
9ORDER BY排序可以（最早能用的地方之一）
10LIMIT / OFFSET截断结果可以

别名与 WHERE/HAVING

-- 经典错误：WHERE 里用 SELECT 的别名
SELECT amount * 2 AS amt2 FROM orders WHERE amt2 > 100;
--   MySQL: ERROR 1054 (42S22): Unknown column 'amt2' in 'where clause'
--   原因：WHERE 在 SELECT 之前执行，别名还不存在

-- 三种正确写法
SELECT amount * 2 AS amt2 FROM orders WHERE amount * 2 > 100;   -- ① 重写表达式
SELECT amount * 2 AS amt2 FROM orders HAVING amt2 > 100;        -- ② 用 HAVING（可用别名，但无 GROUP BY 时会全表过滤，慎用）
SELECT * FROM (SELECT amount*2 AS amt2 FROM orders) t WHERE amt2 > 100;  -- ③ 子查询

-- WHERE 与 HAVING 的区别（核心）
--   统计订单数 > 5 的用户：
SELECT user_id, COUNT(*) AS cnt
FROM orders
WHERE status = 'paid'          -- 先过滤行（分组前，能用索引，快）
GROUP BY user_id
HAVING COUNT(*) > 5;           -- 再过滤组（分组后，对聚合结果筛选）
--   经验：能在 WHERE 做的过滤<b>绝不要</b>放到 HAVING（HAVING 是对已分组结果再筛，行数没减少）

记忆口诀：「先从哪张表取（FROM/JOIN），再筛掉哪些行（WHERE），然后怎么分组（GROUP BY），组里再筛（HAVING），最后要什么字段（SELECT），怎么排（ORDER BY），取几条（LIMIT）」。别名在 SELECT 之后才存在，所以 ORDER BY 能用、WHERE 不能用。

四个高频陷阱

-- 陷阱 1：ORDER BY 与 DISTINCT 同时用
SELECT DISTINCT city FROM users ORDER BY create_time;
--   PostgreSQL: ERROR: for SELECT DISTINCT, ORDER BY expressions must appear in select list
--   因为 DISTINCT 在 ORDER BY 之前，去重后 create_time 可能已不存在
--   解法：SELECT DISTINCT city, create_time ... 或 用 GROUP BY city ORDER BY MIN(create_time)

-- 陷阱 2：LIMIT 在 ORDER BY 之后，所以必须排序稳定
SELECT * FROM orders ORDER BY create_time LIMIT 10;
--   create_time 有重复 -> 结果不确定（可能漏行/重复行）
--   解法：加唯一兜底列 ORDER BY create_time, id

-- 陷阱 3：深分页
SELECT * FROM orders ORDER BY id LIMIT 10 OFFSET 100000;
--   数据库要<b>先算 100010 行再丢掉前 100000 行</b>，越往后越慢
--   解法：键集分页（keyset pagination）
SELECT * FROM orders WHERE id > :last_id ORDER BY id LIMIT 10;   -- 走索引，O(1)

-- 陷阱 4：COUNT(*) 与 LEFT JOIN 的扇出
SELECT COUNT(*) FROM users u LEFT JOIN orders o ON o.user_id = u.id;
--   LEFT JOIN 会产生行数放大（一个用户 N 个订单 -> N 行），COUNT(*) 被放大
--   解法：COUNT(DISTINCT u.id) 或先聚合再 JOIN
为什么标准 SQL 不允许 WHERE 用别名，但 MySQL 的 GROUP BY/HAVING 却可以？

这是各数据库的实现扩展，不是标准行为。标准 SQL 严格按执行顺序：别名在 SELECT 阶段产生，之前一律不可用。MySQL 做了宽松处理（把别名提前解析），好处是写起来方便，坏处是跨库迁移时会突然报错。所以写 SQL 的稳妥原则是：WHERE/GROUP BY 里都写原始表达式，只有 ORDER BY 用别名——这样在 MySQL/PG/SQL Server 上都能跑。

HAVING 能替代 WHERE 吗？

语法上能（无 GROUP BY 时 HAVING 相当于对全表一行组过滤），但性能上绝不能：WHERE 在分组前过滤，能大幅减少参与分组的行数，还能用索引；HAVING 是在分组聚合之后再筛，所有行都已经参与了分组计算。实测差距常常是几十倍。判据：过滤条件不涉及聚合函数，就一定放 WHERE。

SQL 执行顺序和数据库实际执行计划一致吗？

不完全一致。上面讲的是逻辑执行顺序（标准定义的语义），优化器会在语义等价的前提下重排物理执行：比如把 WHERE 条件下推到 JOIN 之前（谓词下推）、把 LIMIT 提前（top-N 优化）、用索引避免排序等。所以「逻辑顺序」用来理解语义和别名可见性，「执行计划」（EXPLAIN）用来理解真实性能和优化——两者是不同层面的东西。

第一层 · 概念与判定：书写顺序 vs 执行顺序

SQL 的书写顺序是给人读的，执行顺序是数据库内部真正干活的次序——两者不同，这是绝大多数 SQL 报错和性能问题的根源。

步骤子句书写顺序执行顺序作用
1FROM / JOIN11确定数据源与连接
2ON22连接条件
3WHERE33过滤行（聚合前）
4GROUP BY44分组
5HAVING55过滤组（聚合后）
6SELECT66计算输出列与聚合值
7DISTINCT77去重
8ORDER BY88排序（可用 SELECT 别名）
9LIMIT99限制返回行数
  • 信号一：WHERE 里写 COUNT(*)>5 报错 → 因为 WHERE 执行时还没分组。
  • 信号二：WHERE 里用 SELECT 的别名报错 → 因为 SELECT 在 WHERE 之后执行。
  • 信号三：ORDER BY 能用别名 → 因为 ORDER BY 在 SELECT 之后。

一句话记忆：WHERE 早于 SELECT，SELECT 早于 ORDER BY。所以「别名在 ORDER BY 能用、在 WHERE 不能用」。

第四层 · 原理与取舍：为什么要设计成「书写顺序 ≠ 执行顺序」

因为 SQL 是声明式语言：你描述「要什么」，数据库决定「怎么拿」。书写顺序按人类思维（从哪张表 → 要什么条件 → 要哪些列 → 怎么排序）排列，执行顺序则按数据流动的必要性排列——必须先有数据才能过滤，必须先过滤才能分组。

常见困惑原因解决办法
WHERE 里用不了聚合函数WHERE 在 GROUP BY 之前执行改用 HAVING
WHERE 里用不了 SELECT 别名WHERE 在 SELECT 之前执行写完整表达式，或包一层子查询
ORDER BY 能用别名ORDER BY 在 SELECT 之后—
LIMIT 不影响聚合结果LIMIT 最后执行要在聚合前限制就写进 WHERE

优化器会改变执行顺序吗？

会，但只在不改变结果的前提下。比如谓词下推：优化器会把外层 WHERE 条件下推到子查询或视图内部提前过滤，实际执行顺序与逻辑顺序不同，但结果一致。EXPLAIN 看到的才是真正执行的计划。

为什么不能按书写顺序执行？

因为语义上做不到。比如 SELECT COUNT(*) 写在 WHERE 之前，但 WHERE 要过滤的行还没确定，COUNT 无从计算。执行顺序由数据依赖关系决定，不是随便定的。

记住这个顺序有什么实际用处？

三个：① 解释报错（为什么 WHERE 不能用别名/聚合）；② 指导优化（能放 WHERE 就别放 HAVING，越早过滤越好）；③ 理解窗口函数的位置（在 GROUP BY 之后、ORDER BY 之前，所以能看到分组后的结果）。
