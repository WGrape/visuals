视频编码与封装：帧如何变成可播放文件

分清编码器、关键帧、时间戳与 MP4 等容器的职责。

学完能解释什么

  • 区分编码格式与容器格式
  • 解释帧间预测、GOP 和关键帧对随机访问的影响
  • 知道解码顺序与展示顺序何时不同

逐步看机制

视频首先是带时间戳的采样

分辨率、像素格式和帧率决定原始数据量；音轨也是独立时间序列，不与视频帧天然一一对应。

MP4 不是一种压缩算法

容器回答“轨道和元数据怎么打包”，codec 回答“每帧的像素怎么压缩和还原”。同为 .mp4，视频轨可能用 H.264、H.265 或 AV1，设备兼容性并不相同；同一 codec 也可放进不同容器。采集、训练和线上服务应明确实际轨道编码、像素格式、色彩空间及时间基准。

为什么 seek 常要回到关键帧

帧间预测利用相邻画面的相似性：I 帧提供可独立解码的入口，P 帧参考过去，B 帧可能同时参考前后。GOP 定义一组相互依赖的帧，关键帧间隔越长通常越省码率，但随机定位、容错和编辑响应可能更差。播放器跳到某个时间点时，往往从邻近可独立解码的帧开始，解码到目标时间。

时间戳决定同步

PTS 指示展示时刻，DTS 指示解码时刻；有帧重排时两者不能混用。音视频同步必须将不同轨道时间基准换算到同一时间轴。可变帧率视频不能只凭“第 120 帧 / 30 FPS”假定一定是第 4 秒；数据集采样和实时推理要优先使用实际时间戳。

若模型输入发生横向拉伸、色彩范围转换或丢帧，性能下降可能来自解码管道，而非视觉模型本身。

自检

文件名是 .mp4，能断定它的视频轨一定是 H.264 吗？

不能。MP4 是容器，视频轨实际 codec 要从轨道元数据读取。

核心概念区分

编码格式 Codec怎么压缩像素：H.264/AVC、H.265/HEVC、AV1、VP9
容器格式 Container怎么打包：MP4、MKV、WebM、TS、MOV
关键区别容器是「盒子」，编码是「内容」；同一个 MP4 里可以是 H.264 也可以是 H.265
码流 Bitstream压缩后的二进制数据（裸流如 .h264/.hevc）
常见误解「MP4 格式」通常指容器，具体清晰度取决于里面的编码与码率

主流编码格式对比

编码年代压缩效率兼容性适用场景
H.264 / AVC2003基准（1×）最好，几乎所有设备通用首选，直播、点播、兼容性要求高的场景
H.265 / HEVC2013比 H.264 省 ~40%较好（部分旧设备不支持）4K/高码率、存储敏感
VP92013接近 HEVC浏览器好（Google 推动）YouTube、Web 端
AV12018比 HEVC 再省 ~20%新设备/浏览器渐支持未来方向，编码慢但免专利费

常见操作

查看信息

ffprobe -v error -show_streams -show_format in.mp4。看 codec_name、分辨率、帧率、码率、时长——处理视频前的第一步永远是探针。

转码（换编码）

ffmpeg -i in.mov -c:v libx264 -crf 23 -c:a aac out.mp4。-crf 控制质量（18~28，越小越好越大）。

只换容器（不重编码）

ffmpeg -i in.mp4 -c copy out.mkv。-c copy 直接搬运码流，秒级完成且无损——能用就别重编码。

提取音频/视频轨

ffmpeg -i in.mp4 -vn -c:a copy out.aac（只音频）；-an 去掉音频。抽帧时用 -an 能省一点 IO。

编码器参数速查

CRF恒定质量模式，18~28；23 是常用默认，每减 6 码率约翻倍
preset编码速度/压缩率权衡：ultrafast → veryslow，越慢压缩越好
GOP / keyint关键帧间隔；越小 seek 越快但码率越高
profile / level兼容性档位；baseline 兼容最好，high 压缩最好
pix_fmt像素格式，yuv420p 兼容性最好

深入自检

编码格式和容器格式到底有什么区别？

用一个比喻：容器是箱子，编码是箱子里的东西用什么方式压缩。MP4、MKV、WebM 是容器（定义了怎么把视频轨、音频轨、字幕、元数据打包在一起）；H.264、H.265、AV1 是编码（定义了怎么把像素压成码流）。同一个 MP4 文件里的视频轨可能是 H.264 也可能是 H.265。所以「这个视频是什么格式」要分两问：容器是什么？编码是什么？实践意义：换容器（如 MP4→MKV）可以无损秒完成（-c copy），而换编码必须重新解码再编码，既慢又有质量损失。

H.264 和 H.265 该怎么选？

默认H.264，除非有明确理由。H.265/HEVC 能在相同画质下省约 40% 码率（对 4K、高码率场景价值很大），但代价是：兼容性稍差（旧设备、部分浏览器不支持）、编码更慢、专利授权更复杂。AV1 压缩效率更高且免专利费，是未来方向，但编码极慢、硬件支持还在普及中。实践建议：面向大众的 Web/移动端用 H.264；内部存储或已知客户端支持时用 H.265；追求长期成本且能接受编码耗时才上 AV1。

CRF 和码率（bitrate）有什么区别？该用哪个？

CRF（恒定质量）：你指定一个质量目标（如 23），编码器根据画面复杂度自动分配码率——复杂场景多给码率，简单场景少给。这是推荐做法，因为它在同等体积下质量更稳定。固定码率（CBR）：你指定码率（如 2Mbps），质量随场景复杂度波动——静态画面浪费码率，复杂画面不够用。所以：归档与点播用 CRF（质量优先）；直播用 CBR 或 ABR（带宽必须可预测）。还有两遍编码（2-pass）用于需要精确控制文件大小的场景。

为什么转码后画质变差了？

因为有损编码的代际损失：每一次解码-再编码都会引入新的量化误差，即使设置很高的质量也会累积。所以：①能用 -c copy 就别重编码（换容器、剪切、合并轨道在很多情况下可以直接 copy）；②若必须重编码，尽量从原始素材而不是从已压缩的版本转；③CRF 值调小（如 18~20）可以减少损失但文件变大；④多次处理的中间文件用无损或接近无损的格式（如 FFV1、ProRes）。

视频播放卡顿/不同步，可能是哪些原因？

常见原因：①码率超过带宽或解码能力——高码率 4K 在弱网/低端机上会卡，需要多码率自适应（HLS/DASH）；②音画不同步——时间戳（PTS）错误，常发生在剪切、合并、VFR 转 CFR 时没处理好；③GOP 太长——seek 慢、起播慢；④编码 profile 不兼容——用了 high profile 但设备只支持 baseline；⑤容器封装问题——moov atom 在文件尾部导致必须下载完才能播（用 -movflags +faststart 修复）。

编码与封装的分工

一句话区分：编码（codec）决定像素怎么压缩，封装（container）决定怎么把音视频+字幕打包成一个文件。两者可以自由组合。

概念作用常见格式
视频编码压缩画面（去空间/时间冗余）H.264/AVC、H.265/HEVC、AV1、VP9、H.266/VVC
音频编码压缩声音AAC、MP3、Opus、FLAC
封装格式打包 + 时间戳 + 轨道信息MP4、MKV、WebM、TS、FLV、MOV
传输协议怎么把数据传出去HLS、DASH、RTMP、WebRTC

查看与诊断

# 用 ffprobe 看一个文件到底装了什么
ffprobe -v error -show_format -show_streams input.mp4
#   format_name=mov,mp4,m4a,3gp,3g2,mj2      <- 封装
#   Stream #0:0: Video: h264 (avc1), yuv420p, 1920x1080, 2500 kb/s   <- 视频编码
#   Stream #0:1: Audio: aac (mp4a), 44100 Hz, stereo, 128 kb/s       <- 音频编码

# 只看关键信息
ffprobe -v error -select_streams v:0 \
  -show_entries stream=codec_name,width,height,r_frame_rate,bit_rate \
  -of default=noprint_wrappers=1 input.mp4

# 常见「能播但没声音 / 有画面没声音」的原因：
#   封装里有音轨，但编码格式播放器不支持（如 MP4 里装了 Opus）
#   解决：转音频编码
ffmpeg -i input.mkv -c:v copy -c:a aac output.mp4    # 只转音频，视频不变(-c:v copy)
编码压缩率（相对 H.264）硬件支持专利适用
H.264 / AVC1.0x（基准）全面（几乎所有设备）有（MPEG LA）兼容性首选
H.265 / HEVC省 40~50% 码率较新设备支持授权复杂4K、存储敏感
VP9省 30~40%浏览器普遍（Google）免费YouTube、Web
AV1省 50%+2020 后新设备免费（AOMedia）未来主流，Netflix/YouTube 已用
H.266 / VVC省 50%+极少授权复杂尚未普及

选型结论：要兼容性用 H.264；要省带宽且设备较新用 H.265；Web 端新项目优先 AV1（无专利费）；直播/实时场景注意 H.265 和 AV1 的编码耗时远高于 H.264（AV1 实时编码直到近两年才可行）。

码率、GOP 与实操参数

码率与编码参数

# 码率估算（决定文件大小和清晰度）
#   文件大小 ≈ 码率 x 时长 / 8
#   例：5 Mbps 的 10 分钟视频 = 5 x 600 / 8 = 375 MB
#
# 各分辨率的推荐码率（H.264，30fps，普通运动量）
#   480p  (854x480)    1.0 ~ 1.5 Mbps
#   720p  (1280x720)   2.5 ~ 4.0 Mbps
#   1080p (1920x1080)  4.5 ~ 8.0 Mbps
#   2K                 8 ~ 16 Mbps
#   4K    (3840x2160)  35 ~ 60 Mbps   （H.265 约 15~25 Mbps）

# CRF 恒定质量模式（推荐，比指定码率更省心）
ffmpeg -i input.mp4 -c:v libx264 -crf 23 -preset medium -c:a aac -b:a 128k out.mp4
#   CRF 范围 0~51，<b>默认 23</b>；每减 6 码率约翻倍
#   18 = 视觉无损，23 = 默认，28 = 明显压缩
#   preset: ultrafast/superfast/veryfast/faster/fast/medium/slow/slower/veryslow
#          越慢压缩率越好、耗时越长（medium 是性价比平衡点）

# 关键帧与 GOP
ffmpeg -i in.mp4 -c:v libx264 -g 60 -keyint_min 60 -sc_threshold 0 out.mp4
#   -g 60 = 每 60 帧一个关键帧（2 秒 @30fps）
#   GOP 大 -> 压缩率高，但 seek 慢、直播首帧慢
#   GOP 小 -> seek 快，但码率高
#   直播常用 GOP = 2 秒；点播可用 4~10 秒

# HLS 切片（直播/点播分发）
ffmpeg -i in.mp4 -c:v libx264 -c:a aac -f hls \
  -hls_time 6 -hls_list_size 0 -hls_segment_filename 'seg_%03d.ts' out.m3u8
#   -hls_time 6 = 每片 6 秒；片太短请求多，太长起播慢
问题原因解法
转码后画质差CRF 太大或码率太低CRF 降到 18~20；或用 2-pass 编码
转码极慢preset 太慢 / 分辨率太高-preset veryfast；开硬件编码 h264_nvenc/videotoolbox
音画不同步时间戳错误 / 帧率不匹配加 -vsync cfr -async 1；或用 -fflags +genpts
体积太大码率高 / 分辨率高降分辨率（-vf scale=1280:-2）或换 H.265/AV1
直播延迟高GOP 长 + 切片长 + 播放器缓冲GOP 缩到 1~2 秒、HLS 片缩到 2~4 秒、或用 LL-HLS / WebRTC

为什么改封装不用重编码？

因为封装只是容器——它只是把已经编好的码流（H.264 的 NALU、AAC 的帧）加上时间戳、轨道描述和索引打包起来。换容器（如 MKV→MP4）就像把同样的文件换个压缩包格式，内容不变。所以 ffmpeg -i in.mkv -c copy out.mp4 只需几秒且不损画质；而换编码（H.264→H.265）必须完整解码再编码，慢几十倍且有画质损失。

CRF 和指定码率（CBR/VBR）怎么选？

存档/点播用 CRF——它保证「每一段画面质量一致」，简单场景自动省码率，复杂场景自动加码率，总体积最小。直播/带宽受限用固定码率——需要可预测的网络占用，避免码率尖峰导致卡顿。折中是 CRF + maxrate 上限：-crf 23 -maxrate 5M -bufsize 10M（受限 CRF）。

HLS 和 MP4 直接播放有什么区别？

MP4 点播：一个完整文件，靠 HTTP Range 请求 seek，实现简单，适合短视频。HLS：把视频切成 .ts 分片 + .m3u8 索引，播放器按序拉取，天然支持自适应码率（根据网速切不同清晰度的流）和直播，是长视频和直播的事实标准。代价是有切片延迟（通常 6~30 秒，LL-HLS 可降到 2~5 秒）。
