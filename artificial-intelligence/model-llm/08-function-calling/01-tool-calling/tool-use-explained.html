函数调用与工具使用（Tool Use）

让 LLM 从「只会聊天」变成「能干活」的关键能力。面试常问：Function Calling 和普通补全有什么区别？参数怎么保证合法？和 MCP、Agent 是什么关系？

01是什么：从文本到动作

普通对话模型只输出文本；函数调用（Function Calling / Tool Use）让模型输出结构化的调用指令（调哪个函数、参数是什么），由外部程序真正执行并把结果回填，模型再据此继续生成。这是 LLM 连接真实世界的入口。

关键转变：模型不再「假装知道答案」，而是学会「在不知道时去查 / 去做」，把不确定交给工具。这是 Agent 的能力基石。

02完整流程（循环）

这是一个 ReAct 式的「思考—行动—观察」循环：模型输出调用 → 系统执行 → 结果回注上下文 → 模型再决定下一步，直到给出最终答案。

03Tool Schema：怎么描述工具

工具用 JSON Schema 声明：名字、描述、参数类型。模型据此生成符合 schema 的 arguments。

{
  "name": "get_weather",
  "description": "查询某城市天气",
  "parameters": {
    "type": "object",
    "properties": {
      "city": {"type": "string", "description": "城市名"},
      "unit": {"type": "string", "enum": ["celsius","fahrenheit"]}
    },
    "required": ["city"]
  }
}

04并行调用与多轮

并行调用

一次返回多个独立工具调用（如同时查天气+汇率），由运行时并发执行，省往返延迟。

多轮编排

复杂任务拆成多步：先检索再计算再总结，由 Agent 循环控制（见 agent 目录）。

05与 MCP / Agent 的关系

Function Calling

模型「生成调用指令」的能力，是协议层能力。

MCP

工具的「标准化接入协议」——定义工具如何被发现、调用、返回，解耦模型与工具实现（见 mcp 目录）。

Agent

把「调用工具」编排进自主循环，加规划、记忆、反思（见 agent 目录）。

一句话：Function Calling 是「能力」，MCP 是「接口标准」，Agent 是「使用方式」。三者是不同层次，常被一起考。

06常见坑

参数非法

模型可能生成 schema 外的字段/类型，必须做服务端校验再执行。

幻觉调用

不存在的工具/参数被编造，需约束可调用集合。

流式处理

流式下要能增量解析出完整 JSON 再执行，解析失败要重试。

副作用安全

写操作(发邮件/删数据)需权限、确认或沙箱，防提示注入滥用。

07面试速记卡

本质

模型输出结构化调用指令，外部执行并回填，形成循环。

Schema

用 JSON Schema 声明工具，模型生成合法 arguments。

三者关系

能力(FC) / 标准(MCP) / 编排(Agent) 不同层次。

必做

参数校验、防幻觉、副作用管控、流式解析。

为什么一定要「工具」这一步

模型内部的知识是训练时冻结下来的：它不知道你公司数据库里的最新订单，也不擅长十位数乘法。光靠生成，它只能给出「看起来合理」的东西。工具的出现就是为了解决这三类问题：

拿不到的数据实时信息、私有数据、用户上下文 —— 只能查不能猜。
不该由它算的事精确算术、字符串处理、日期推断 —— 代码执行比概率采样可靠得多。
会改变世界的动作下单、发邮件、改数据库 —— 模型负责决定「做什么」，真正的执行必须有明确的边界与鉴权。
可验证的结果执行结果会回填给模型，形成一个可观测的闭环，而不是黑箱胡诌。

所以工具调用的本质不是「让模型变强」，而是把确定的事交给确定的系统，让模型只负责它擅长的一环：理解意图、选择动作、组织结果。

一次完整的工具调用循环

工具调用五步；执行权始终在宿主程序手里

注意第 ⑤ 步：是否继续循环、最多调用几轮、组合哪些工具，通常是上层程序控制策略。这构成了一个简单的 Agent 雏形 —— 但它和完整的 Agent 区别在于，标准的一次函数调用往往是「一次猜准即结束」。

工具描述（schema）怎么写得让模型用对

模型只能通过你给的那段 JSON Schema 来了解工具。写得好不好，直接决定调用准确率。核心原则：把工具描述当成写给新同事的接口文档。

{ "name": "get_weather", // 动词开头，语义唯一 "description": "查询指定城市当日天气。当用户询问天气、出行是否需要带伞时调用；不要用于查询空气质量（用 get_aqi）。", "parameters": { "type": "object", "properties": { "city": { "type": "string", "description": "城市名，如「苏州」；不带「市」后缀" }, "unit": { "type": "string", "enum": ["celsius", "fahrenheit"], "default": "celsius" } }, "required": ["city"] } }
要做的不要做的原因
name 用动词短语，唯一无歧义起 get_data / handle 这种泛名模型靠名字猜用途
description 里同时写「何时用」和「何时不用」只写一句话边界样例比定义更能约束行为
参数尽量基础类型 + enum + default用复杂嵌套对象嵌套越深，生成错误的概率越高
必填项精简把一堆参数都设为必填必填越多，越容易编造参数
一次给 3~10 个工具一次性挂 50 个工具候选爆炸会显著拉低选择准确率

工具不是越多越好。经验做法是按业务意图动态注册：先判断用户意图属于哪一类，只把相关的几个工具放进本次请求的 tools 数组里。

工程上的六个必踩点

  • 一定要校验参数。模型可能把日期写成「下周三」、把城市写成拼音。schema 层面做校验，失败时把结构化的错误信息回传给模型（例如「unit 只能是 celsius/fahrenheit」），它通常能自我纠正一轮。
  • 权限最小化。给模型的 token 只应有它真正需要的那点权限；写操作最好走「二次确认」或人工审批。永远不要相信模型自己声明的身份。
  • 幂等是关键设计。网络超时后模型可能重试同一个调用，写接口必须支持幂等键，否则会出现重复下单。
  • 超时与步数上限。为单个调用设超时，为整轮对话设最大步数；触限时返回明确状态，让模型知道「这条路走不通」而不是无限重试。
  • 幻觉调用。模型可能调用没定义的工具、或参数填错 tool_call_id。宿主侧必须以「白名单 + 校验」的方式兜底，而不是照单执行。
  • 成本透明。每轮把工具结果塞回上下文会让 token 数快速增长。回传前做裁剪（只留必要字段、截断超长返回值），并记录每次调用的耗时与大小。

深入自检

模型会「真的执行」工具吗？

不会。模型只负责任地输出一段符合约定格式的调用意图（通常是 JSON），真正的执行权在宿主程序手里。这个分离非常重要：它意味着即使模型被诱导说「删除所有用户」，只要宿主不对它暴露这样的接口，就什么都不会发生。

为什么有时模型直接把 JSON 输出成文本，不走结构化的调用通道？

常见于:① 请求里没有 declaration 工具 schema，模型只是在模仿示例；② 提示或上下文让它倾向于「回答」而不是「调用」；③ 模型本身对这个 corner case 学得不够稳。稳妥做法是在宿主侧同时准备结构解析的兜底（从文本里抽取 JSON 并按同样方式执行），并校正温度、明确要求「你有工具可用」。

多个工具可以一次并行调用吗？

可以，多数现代推理服务支持在一轮里返回多个调用请求。前提是它们互不依赖（比如同时查北京和上海的天气）。对有依赖关系的子任务（先查订单、再按订单查物流），必须串行，否则模型拿不到上一步结果。宿主侧要区分这两类并据此执行。

怎么判断「该不该给它工具」？

问三个问题：① 答案是随时间/用户变化的吗（是→需要查）？② 出错代价能承受吗（不能→让确定性系统来做）？③ 用 prompt 能不能稳定逼出正确行为（能且代价低→也许不必做工具）？工具会增加延迟、成本与失败面，能用简单方案解决的就别加。
