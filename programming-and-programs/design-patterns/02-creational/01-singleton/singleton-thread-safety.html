单例要保证『全局唯一』且『并发安全』。Go 首选 sync.Once，Python 用模块级对象或改写 __new__。

1Go 双重检查锁（不推荐但常见）

type singleton struct{}
var (
    instance *singleton
    mu       sync.Mutex
)
func Get() *singleton {
    if instance == nil {        // 第一次检查
        mu.Lock()
        defer mu.Unlock()
        if instance == nil {    // 锁内第二次检查
            instance = &singleton{}
        }
    }
    return instance
}

2Go sync.Once（推荐）

type singleton struct{}
var (
    instance *singleton
    once     sync.Once
)
func Get() *singleton {
    once.Do(func() { instance = &singleton{} })
    return instance
}
要点：sync.Once 内部已处理内存可见性与只执行一次，比手写双重检查更安全。

3Python 实现

class Singleton:
    _instance = None
    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

# 更 Pythonic：模块级对象天然单例
# db.py
db = Database()  # import 多次也只执行一次

5何时不要用单例

  • 其实是『配置容器』→ 用依赖注入，便于测试与替换。
  • 需要多个实例或不同环境的实例 → 单例会锁死可测试性。
  • 隐藏的全局状态会让并发测试和推理变难。

第一层 · 概念与判定：什么时候真的需要单例

单例保证一个进程内只有一个实例，常用于配置中心、连接池、日志器。但多数情况是过度设计——能用依赖注入 / 模块级变量替代就不要用单例。

信号该用单例不该用
全局唯一且昂贵（连接池/客户端）✓单纯的「工具类」也用单例
需要跨模块共享同一状态✓只是想少传参数
测试需要可替换实现✗（单例难 mock）—

Go 单例：sync.Once vs 裸双重检查

// Go：sync.Once 是最省心的写法
var once sync.Once
var instance *Client
func Get() *Client {
    once.Do(func() { instance = newClient() })
    return instance
}

// 反例：裸双重检查在 Go 里没必要，且手写易漏
func GetBad() *Client {
    if instance == nil {          // 读没加锁，可能重复建
        mu.Lock()
        if instance == nil { instance = newClient() }
        mu.Unlock()
    }
    return instance
}

数量级：sync.Once 首次约 10–20ns，之后每次只做一次原子读（≈1ns）；裸锁每次读都进临界区，高并发下差距可达几十倍。

第三层 · 排障与边界：双重检查为什么容易写错

  • 指令重排导致拿到半初始化对象：Java/C++ 里未用 volatile 的 DCL，构造可能被重排，线程 B 读到非 null 但字段还没赋值
  • Go 里 DCL 完全没必要：once.Do 已封装内存屏障，手写锁既丑又慢还易错
  • 延迟初始化的隐藏成本：第一次请求突然变慢（建连接/读配置），压测要覆盖冷启动
  • 单例 + 可变状态：多个 goroutine 改同一个实例字段，需要实例内部自己加锁，单例只保证唯一不保证内部安全
  • 测试污染：单例跨测试共享状态，一个测试改了配置另一个测试炸——需要 reset 钩子

第四层 · 原理与取舍

为什么 Java 的双重检查必须加 volatile？

因为 JVM 允许指令重排序：new 对象分「分配内存→初始化→赋值引用」三步，未同步时可能先赋值引用再初始化（把步骤 2、3 重排）。线程 A 正在构造，线程 B 看到 instance != null 就直接返回，拿到一个字段全 0 的半成品。volatile 在此处有双重作用：保证可见性，并通过内存屏障禁止构造与赋值的重排序。

Go 为什么不需要 volatile 版 DCL？

Go 的内存模型没有 Java 那种「构造重排」陷阱，且 sync.Once 内部用了正确的原子操作与屏障，保证 once.Do 里的函数完全执行完后才对其他 goroutine 可见。所以直接 once.Do(new) 即可，手写 DCL 既不更快也不更安全，纯属多余。

单例和全局变量有什么区别，谁更糟？

单例至少把「唯一性」和「获取方式」封装起来，可替换、可懒加载；裸全局变量则完全暴露、无处不在可改，还难测试。但两者本质都是隐式共享状态，都会增加耦合。更优解是显式注入：调用方持有实例，测试时传一个假实现——代价只是多一个参数，换来可测与清晰。
