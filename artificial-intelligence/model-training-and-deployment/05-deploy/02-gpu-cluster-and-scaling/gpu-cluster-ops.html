01看卡与估显存

OOM 先看是谁占着：nvidia-smi 里显存占用不等于「模型权重」，框架碎片 + 临时张量常是元凶。

nvidia-smi                                   # 显存/利用率/温度速览
nvidia-smi -q -d MEMORY,UTIL,POWER       # 详细
nvidia-smi dmon -s u -d 1               # 每秒采样利用率
# 显存粗估（7B fp16）:
#   参数 7B*2B = 14GB；KV cache 随 seq*batch 涨；余量给激活 ~20GB+

02K8s 调度 GPU

要点：默认 device plugin 只能整卡分配。要分卡（MIG / 时间片）需对应插件或 vGPU 方案；否则小推理任务独占一整张卡很浪费。
# 节点需装 NVIDIA device plugin，Pod 这样要卡
resources:
  limits:
    nvidia.com/gpu: 1      # 整卡请求（默认不可分）
# 看节点 GPU 资源与标签
kubectl get nodes -o json | grep -i 'nvidia.com/gpu'
kubectl describe node <n> | grep -A3 'nvidia.com/gpu'

03弹性伸缩怎么落

  • 推理服务：用 HPA 但「GPU 利用率」不是好指标（显存常驻高但算得少），多用 QPS/排队长度或自定义指标（KEDA）。
  • 训练任务：用 Job/CronJob + 队列（如 Kueue/Volcano）排队拿卡，而不是无脑 HPA。
  • 节点级：用 cluster-autoscaler 按「Pending Pod 要 GPU」扩节点，缩容等任务结束释放。

04多卡通信与排障

  • 卡在 NCCL init：多半是节点间网络不通 / 防火墙挡了 NCCL 端口 / 多网卡选错接口（设 NCCL_SOCKET_IFNAME）。
  • 利用率低：检查数据加载是否成瓶颈（Disk/CPU 跟不上 GPU）。
  • 显存碎片：用 torch.cuda.empty_cache() 或重启；分布式下碎片会拖慢首步。
问：为什么多卡训练显存没按卡数线性降？

因为每张卡还要存优化器状态、梯度、以及数据并行下的冗余副本；模型并行虽然能把参数拆开，但激活和通信缓冲仍占显存。所以 8 卡不是 1/8 显存，常是 1/3~1/5 量级。

# 指定可见卡
CUDA_VISIBLE_DEVICES=0,1 python train.py
# 看 NCCL 拓扑与通信细节
NCCL_DEBUG=INFO python train.py
# 拓扑：NVLink（快）vs PCIe vs 跨节点 IB（慢）

数量级：一块 A100 80GB 训 7B 模型约吃 15–20GB（fp16），13B 约 30GB；利用率长期低于 20% 基本是数据加载没跟上（没用 prefetch / num_workers 太小）。

第三层 · 排障与边界：五个高频故障

  • OOM：batch 太大或梯度没释放——降 batch、开梯度检查点（重算换显存）、用 ZeRO/FSDP 切分
  • 利用率低：DataLoader 单进程读不动——设 num_workers=4×核数、pin_memory=True、开 prefetch
  • 多卡卡死：NCCL 某张卡没起来——NCCL_DEBUG=INFO 看哪张卡挂了，常是拓扑/NVLink 或 IB 配置错
  • 显存碎片：反复申请释放导致大块申请失败——用 cudaMallocAsync 或重启任务，训练前预热
  • 抢占/漂移：弹性训练被回收节点后状态丢——用 checkpoint 每 N 步落盘，支持 resume

第四层 · 原理与取舍

NVLink 和 InfiniBand 分别解决什么？

NVLink 是单机内卡间直连，带宽 300–900 GB/s，远高于 PCIe（≈64 GB/s），解决单机 8 卡通信瓶颈；InfiniBand 是跨机网络，几百 GB/s，解决多机间梯度同步。两者不是替代关系：单机内靠 NVLink，跨机靠 IB，缺一个多卡扩展就卡在慢的那段。没有 IB 时多机走 TCP 网络，带宽掉一个数量级，大模型训练基本不可行。

为什么显存不够不能直接堆 batch？

因为显存里除了激活还有优化器状态与梯度：AdamW 对每参数额外存 2 份（m、v），7B 模型 fp16 权重 14GB，但优化器状态能再吃 28GB。所以单纯加 batch 会先撞优化器显存。正解是 ZeRO/FSDP：把优化器状态和梯度分片到各卡，显存随卡数近线性下降。

弹性伸缩对训练友好吗？

对无状态推理极其友好：多副本 HPA 直接加减；对有状态训练则麻烦，节点被回收要能 resume：周期性 checkpoint + 容错 launcher（如 TorchElastic）。所以训练集群通常保活固定规模，推理集群才做弹性——别把两者调度策略混用。
