一句话总结：调度器决定"哪个任务此刻用 CPU"。线程与内核线程的映射方式（1:1 / N:1 / M:N）决定了能否真并行、切换贵不贵、会不会被一个阻塞调用拖垮。

01为什么需要调度

任务数远多于 CPU 核数，必须有人决定"下一刻谁上 CPU"。调度器做两件事：公平（不让某个任务饿死）和高效（切换成本可控、尽量保持缓存热度）。

02三种线程映射

模型含义优点缺点
1:1每个用户线程对应一个内核线程真并行；阻塞 syscall 只挡本线程上下文切换贵（进出内核）；线程数受内核限制
N:1多个用户协程跑在一个内核线程切换极便宜（用户态）；数量可极大一个阻塞 syscall 拖垮整组；不能吃多核
M:N多个协程映射到多个内核线程兼顾轻量与真并行调度器复杂（要处理绑定与偷取）
映射方式决定并行能力与切换成本

03抢占式 vs 协作式

  • 抢占式：内核按时间片强制切换，公平、不会饿死，但切换有成本。
  • 协作式：任务主动让出（await / yield），切换极快、延迟低，但一个任务不让出就会独占 CPU（饿死别人）。

现代 runtime 多混合：用户态协程用协作式（快），但 runtime 会插入异步抢占点防止某个协程长期霸占 P。

04goroutine 调度（G-M-P）

Go 的 M:N 调度核心是 G（goroutine）- M（内核线程）- P（处理器/上下文）：

  • 每个 P 持有一个本地运行队列，M 绑定 P 执行上面的 G。
  • 工作窃取：某 P 空闲时从别的 P 偷一半 G 来跑，保持负载均衡。
  • 网络轮询器：把网络 IO 注册到 netpoller，G 阻塞在网络上时 M 不被占住，可去跑别的 G。
  • 异步抢占：运行过久的 G 会被异步抢占，交还 P，避免饿死。

05运维注意

🌀 协程泄漏

goroutine 阻塞在无接收的 channel 会永远挂着，数量只增不减，需监控 goroutine 数。

🧮 数量级

协程轻量但非免费；百万级协程会有调度与栈（增长后）内存成本。

🔒 锁粒度

同一 P 上的 G 串行，跨 P 才真并行；共享状态仍要锁或 channel，锁竞争会抵消并发收益。

06常见疑问

协程能替代多线程做并行吗？
协程解决的是"并发"（交错推进、少切换），不是"并行"（同时跑在多核）。只有 M:N 且映射到多个内核线程时，协程才能真吃到多核；单内核线程上的 N:1 协程再多也只能用一个核。
为什么协程阻塞 syscall 很危险？
在 N:1 / 单个 M 上，一个协程做阻塞 syscall 会占住那个内核线程，同组其他协程全被卡住。所以 runtime 要把阻塞操作接管/调度开，或在独立线程上执行，避免阻塞传染。
工作窃取有什么用？
防止某些 P 满载、另一些空闲。空闲 P 从忙碌 P 偷一半 G，保持所有核都有活干，是 M:N 调度维持高吞吐的关键机制。

选型与排障

需求倾向
简单、吃多核1:1 线程（或语言原生线程）
海量并发连接M:N / 协程（Go / Erlang / Kotlin）
超低延迟切换协作式 + 异步抢占
确定性调度实时内核 / 固定优先级
为什么 Go 用 M:N 而不是直接 1:1？

1:1 下创建十万线程会被内核调度和资源压垮；M:N 让海量 goroutine 映射到少量内核线程，切换在用户态、几乎免费，又能通过多个 M 吃到多核。代价是调度器要处理 G 在 P 间迁移、syscall 时 M 的解绑与 P 的递补（hand-off），实现更复杂。

深度补充：调度器与线程模型参数

第一层 · 概念与判定 线程模型决定“多少个内核线程跑多少个执行流、谁负责切换”。判定：高并发服务看是 1:1（OS 线程）、N:1（用户协程）、还是 M:N（Go GMP）。

模型映射切换成本代表
1:1协程=OS线程高（内核态）pthread / Java
N:1多协程1线程低（用户态）早期 goroutine
M:N多协程多线程低且能并行Go GMP
事件循环单线程协作极低Node / Redis

第三层 · 排障与边界

  • Go 设 GOMAXPROCS 过小浪费多核、过大增加调度与缓存争用。
  • 阻塞系统调用会占用 P，Go 用 syscall 栈把它从 P 摘下，别用 cgo 长期阻塞。
  • 线程模型选错（CPU 密集用单线程事件循环）会撑满单核。
  • 锁粒度与调度耦合：持有锁时阻塞会让同 P 其他协程饿死。
第四层 · 原理与取舍

M:N 用“用户态调度器在少量 OS 线程上多路复用大量协程”兼顾并行与低切换成本，代价是调度器本身复杂、需处理系统调用与抢占（Go 用 sysmon 异步抢占）。权衡是“并行能力（多核）vs 切换开销（用户态）”。事件循环把切换降到极低但放弃并行，适合 IO 密集且逻辑单一的场景。

实例与速查：调度器旋钮

// Go：限制并行执行的内核线程数（默认 = 逻辑核数）
runtime.GOMAXPROCS(4)

// 主动让出 P，给其他协程机会（避免长循环饿死同 P 协程）
for i := 0; i < n; i++ {
    if i%100 == 0 { runtime.Gosched() }
}

# 查看 Go 调度统计
GODEBUG=schedtrace=1000 ./app
  • GOMAXPROCS 过小浪费多核，过大增加调度与缓存争用，通常等于核数。
  • 纯计算长循环要让出 P，否则同 P 上的其他协程饿死。
  • 避免 cgo 里长期阻塞系统调用，会占用 P 影响同 P 协程。
FAQ：协程切换会进内核吗？

正常情况下不进。Go 的 GMP 调度在用户态完成协程切换；只有协程发起阻塞系统调用时，运行时才把它从 P 摘下、用独立内核线程承接，P 可去跑别的协程。所以 GOMAXPROCS 控制的是并行执行的内核线程（M）上限，而非协程数。

常见误区与延伸

  • 误区一：协程越多并发越高。协程是并发单位，真正并行由 GOMAXPROCS（内核线程）决定，盲目起百万协程只增调度与内存。
  • 误区二：用多线程解决一切。CPU 密集用多线程/多进程才能吃满多核，单线程事件循环会压满单核。
  • 延伸：Go 的 sysmon 监控线程负责抢占、网络轮询、GC 辅助，是“用户态调度 + 内核态兜底”的关键。
  • 延伸：Netty/Redis 的线程模型是“少量 IO 线程 + 事件循环”，与 Go M:N 思路相通，都是减少内核切换。

一句话总结：选模型先看负载画像——IO 密集偏事件循环或协程，CPU 密集偏多线程/多进程，核心是减少等待与切换。

决策速记

  • 看负载：IO 密集偏协程/事件循环，CPU 密集偏多线程/进程。
  • 设并行：Go 的 GOMAXPROCS 通常等于核数，过大反噬调度。
  • 让出 P：长计算循环主动 Gosched，避免同 P 协程饿死。
  • 别阻塞 P：cgo 长期阻塞系统调用会占 P，影响同 P 协程。

一句话：模型选型先看负载画像，核心是减少等待与切换开销。

横向对比与追问

  • 与 Node/Redis 比：它们用单线程事件循环，协程/线程模型换并行；Go 用 M:N 兼顾并行与低切换。
  • 与 Java 比：Java 是 1:1 线程，上下文切换进内核，协程靠虚拟线程（Project Loom）补位。
  • 追问：为什么事件循环适合 IO 密集？因为等待 IO 时不占 CPU，单线程也能高并发。
  • 追问：Go 的 sysmon 做什么？负责抢占、网络轮询与 GC 辅助，是用户态调度的内核兜底。

小结：模型之争本质是“并行能力、切换成本、编程心智”的三角权衡。

速记口诀

口诀：IO 密集用协程，CPU 密集用多线程，GOMAXPROCS 等于核数。

  • M:N 兼顾并行与低切换，事件循环放弃并行。
  • 长循环主动让出 P，避免同 P 饿死。

先记三件事

  • 第一件：模型选型先看负载，IO 密集偏协程/事件循环，CPU 密集偏多线程。
  • 第二件：Go 的 GOMAXPROCS 通常等于核数，过大反而增加调度争用。
  • 第三件：长计算循环要主动让出 P，避免同 P 协程饿死。

线程模型选型速记

  • 1:1 线程：每请求映射一个 OS 线程，编程直观但上下文切换与内存（栈 1 到 8 MB）成本高，适合 CPU 密集型。
  • M:N 协程：用户态调度，海量并发低开销，但遇阻塞系统调用需与网络异步或 worker 池配合。
  • 事件循环：单线程跑回调，无锁无切换，适合 I/O 密集型高并发；长任务会阻塞循环，必须拆片或 Offload。
