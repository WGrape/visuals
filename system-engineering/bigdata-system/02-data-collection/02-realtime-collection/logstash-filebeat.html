别过度使用

简单场景可直接送 ES

先建立直觉：快递员与分拣中心

  • Filebeat 像快递员：跑在每台服务器上，只负责「把包裹从你家取走送到分拣中心」，轻装上阵、跑得快，不做任何加工。
  • Logstash 像分拣中心：集中处理——拆包、检查、贴标签、按目的地分类，功能强但更重。

你会发现这个分工和 Kafka 的「采集端 / 处理端」思路一致：轻的放在数据源旁边，重的集中部署。

为什么需要两级

核心理由：① Filebeat 极轻（约 10MB 内存），可以在成百上千台应用机上无感部署；② 解析规则集中在一处维护，改格式不用改每台机器；③ Logstash 能做缓冲削峰，保护下游 Elasticsearch。

两者对比

维度FilebeatLogstash
资源占用极低（~10MB 内存，Go 编写）较高（JVM，数百 MB 起）
部署位置每台数据源机器上集中部署（若干台）
处理能力简单（多行合并、加字段）强大（grok/date/mutate/ruby 等丰富插件）
缓冲有（内存队列 + 磁盘 spool）有（可配持久化队列）
典型角色采集搬运解析转换

Logstash 的三段式配置

input {
  beats { port => 5044 }          # 接收 Filebeat
}

filter {
  grok {                           # 解析非结构化日志
    match => { "message" => "%{TIMESTAMP_ISO8601:ts} %{LOGLEVEL:level} %{GREEDYDATA:msg}" }
  }
  date {                           # 用日志时间覆盖 @timestamp
    match => ["ts", "ISO8601"]
    target => "@timestamp"
  }
  mutate {                         # 字段处理
    convert => { "duration" => "float" }
    remove_field => ["agent", "ecs"]   # 删掉无用字段省空间
  }
}

output {
  elasticsearch {
    hosts => ["http://es:9200"]
    index => "app-%{+YYYY.MM.dd}"
  }
}
grok 是性能杀手。它靠正则匹配解析日志，复杂 pattern 的 CPU 开销很大。优化建议：① 优先让应用直接输出 JSON 格式日志，用 json filter 解析（快得多）；② grok 的 pattern 尽量锚定开头（加 ^），失败时快速退出；③ 无法匹配的日志要单独处理，避免反复尝试。

可靠性保障

机制说明
注册表（registry）Filebeat 记录每个文件的读取偏移量，重启后从断点继续，不重复不丢失
至少一次语义未收到确认会重发，可能重复——需要下游幂等（如用文档 ID 去重）
背压感知下游（Logstash/ES）处理慢时，Filebeat 自动降低发送速度，不会压垮下游
持久化队列Logstash 可开启 persistent queue，宕机后不丢数据
日志轮转的坑：日志切割（logrotate）时如果配置不当，Filebeat 可能丢日志或重复读。要点：① 用 copytruncate 需谨慎（可能丢行）；② 确保 Filebeat 的 close_inactive、clean_removed 等参数与轮转策略匹配；③ 监控是否有大量 harvester 未关闭。

什么时候可以省掉 Logstash

  • ✅ 日志本身就是 JSON，Filebeat 直接解析即可；
  • ✅ 不需要复杂转换，直接写入 ES（Filebeat 有 ES output 和内置模块）；
  • ✅ 量不大、机器不多，想简化运维。
现代趋势：让应用直接输出结构化 JSON 日志，Filebeat 采集后直接送 Kafka（由下游消费者处理），可以省掉 Logstash 这一层，架构更轻。Logstash 主要保留在「需要兼容多种历史日志格式」的场景。

🎯 面试问答

Q：Filebeat 和 Logstash 必须用在一起吗？
A：不是。Filebeat 可以独立工作——它自带 elasticsearch / kafka / logstash 等多种 output，如果日志已经是 JSON、无需复杂解析，完全可以 Filebeat → Elasticsearch 直连，省掉 Logstash。需要 Logstash 的典型场景：日志是非结构化的纯文本需要 grok 解析、要做字段富化（如 IP 转地理位置）、需要一条数据路由到多个下游、或需要更强的缓冲削峰能力。

Q：Filebeat 会丢日志吗？
A：设计上是「至少一次」语义，正常情况不丢：它用注册表（registry）记录每个文件的读取偏移量，只有收到下游确认后才更新偏移，重启后从断点继续。但要注意两类风险：① 日志轮转配置不当（尤其 copytruncate）可能在切割瞬间丢行；② 文件被删除而还没读完（用 clean_removed 控制）。另外它保证的是「不丢」而非「不重」——未确认时会重发，下游需要幂等处理。

Q：grok 太慢怎么办？
A：三个方向：① 改源头——让应用直接输出 JSON 日志，用 json filter 解析，比 grok 快一个数量级，这是最根本的解决方案；② 优化 pattern——加上 ^ 锚定开头，把最可能匹配的部分放前面，失败时快速退出；③ 降低解析量——在采集端先做一次粗过滤，不该解析的日志直接丢弃。另外可以横向扩容 Logstash 实例分散压力。

Q：日志量很大时怎么设计采集链路？
A：典型做法：Filebeat → Kafka → 消费者 → ES/数仓。用 Kafka 作为缓冲层解耦采集与处理，好处是：① 削峰，下游抖动不影响采集；② 多个消费者可以各自处理（一份进 ES 做检索，一份进数仓做分析）；③ 便于重放。关键点：Filebeat 端开启背压与磁盘 spool，Kafka 端分区数按吞吐估算，消费者端做好批量写入（批量比单条写快得多）。
