数据倾斜怎么解
为什么作业总卡在最后 1 个 Task 上

"1000 个 Task，999 个 10 秒就跑完了，剩下 1 个跑了 40 分钟还没完" —— 这是数据倾斜最典型的现场。它的本质是并行计算里最朴素的一条规律：整个 Stage 的耗时由最慢的那个 Task 决定。本文讲清倾斜从哪来、怎么一眼看出来，以及六种解法各自的适用边界。

1数据倾斜是什么

数据倾斜（Data Skew）= 数据在分区之间分布严重不均，导致少数 Task 承担了绝大部分工作量。

数据分布不均 → 少数 Task 拖垮整个 Stage

2为什么会倾斜：根源是 hash 分区

Shuffle 的分发规则是 partition = hash(key) % R。这个规则有两个直接后果：

  1. 相同 key 一定进同一个分区——这是聚合/join 正确性的前提，也是倾斜的根源。
  2. 某个 key 有多少条数据，那个分区就有多少条——如果一个 key 占了全表 60% 的行，那一个 Task 就要处理 60% 的数据。
并行度再高也救不了把分区数从 200 提到 2000，只是把"空桶"变多了。那个热点 key 无论怎么 hash 都只会落到一个桶里，那个桶依然巨大。增加分区数不解决倾斜，这是最常见的误操作。

三种倾斜场景

场景触发点现象
聚合倾斜groupBy / reduceByKey / distinct某个 key 的分组极大，Reduce 端单 Task 数据量爆炸，常伴 OOM
Join 倾斜join / SortMergeJoin大表里某几个 key 特别多，join 后这几路数据翻倍膨胀，单个 Reduce 撑爆
读取倾斜
（非 shuffle）		读不可切分的大文件（如单个巨大 Gzip）、或分区本身大小悬殊还没 shuffle 就已经不均：某个 Task 要读一个 10GB 的不可分割文件

3怎么发现倾斜

📊 看 Task 耗时分布

Spark UI → Stage 详情 → Tasks 表，按 Duration 排序。若中位数 8s、最大 45min，就是典型倾斜。

📦 看 Shuffle Read 量

同一个 Stage 里，Shuffle Read Size / Records 列。若中位数 20MB、最大 30GB，直接定位到倾斜分区。

🐢 看进度条

Stage 进度卡在 99% 长时间不动 —— 剩下 1% 就是那个大 Task。

💥 看 OOM 报错

OutOfMemoryError: Java heap space 或 Container killed by YARN for exceeding memory limits，且只发生在个别 Task 上。

先在 SQL 里量化在做任何优化前，先跑一句把分布摸清楚，别猜：
SELECT key, count(*) c FROM t GROUP BY key ORDER BY c DESC LIMIT 20;
看到 top-1 的 count 是第二名的几十倍以上，就是它了。

4六种解法与适用边界

解法 ①：加盐两阶段聚合（解决聚合倾斜，最通用）

思路：给 key 加随机前缀（盐），先打散到多个 Task 做局部聚合，再把盐去掉做最终聚合。

// 第一阶段：key 加随机盐 → 打散
val salted = rdd.map { case (key, value) =>
  val salt = Random.nextInt(20)          // 盐的数量按倾斜程度定
  (s"${salt}_${key}", value)
}.reduceByKey(_ + _)                      // 局部聚合：热点 key 被拆到 20 个 Task

// 第二阶段：去掉盐 → 最终聚合
val result = salted.map { case (saltedKey, agg) =>
  val key = saltedKey.substring(saltedKey.indexOf('_') + 1)
  (key, agg)
}.reduceByKey(_ + _)                      // 此时每个 key 最多剩 20 条，轻松

// 效果：原来 1 个 Task 处理 1 亿条 → 现在 20 个 Task 各处理 500 万条
为什么有效热点 key 原本只能落进一个桶。加了盐之后，"热点key+盐0"、"热点key+盐1"… 变成了 20 个不同的 key，自然落进 20 个桶，压力被分摊。代价是多一轮 Shuffle。

解法 ②：广播 Join（解决 Join 倾斜，收益最大）

如果倾斜发生在 大表 join 小表，直接把小表广播出去，完全取消 Shuffle，倾斜根本无从谈起。

// Spark SQL 自动广播（小表 < 阈值）
SET spark.sql.autoBroadcastJoinThreshold = 64MB;   // 默认 10MB，可适当调大

SELECT /*+ BROADCAST(dim) */ *
FROM big_fact f JOIN small_dim d ON f.sku_id = d.sku_id;

// 注意：广播的是"小表"，且要能被 Executor 内存装下

解法 ③：倾斜 key 单独拆出来处理（分流法）

思路：把数据分成"热点 key"和"非热点 key"两拨，分别处理再 UNION。非热点走普通 join（很快），热点走广播或加盐。

// 1. 先找出热点 key（样本统计或历史已知）
val hotKeys = Set("unknown", "", "-1")

// 2. 拆分
val hotPart  = bigRDD.filter { case (k, _) => hotKeys.contains(k) }
val normPart = bigRDD.filter { case (k, _) => !hotKeys.contains(k) }

// 3. 非热点：正常 join
val normResult = normPart.join(smallRDD)

// 4. 热点：小表也只取对应 key，直接广播 join（热点 key 虽多，但小表里就几条）
val hotResult = hotPart.join(broadcast(smallRDD.filter(...)))

// 5. 合并
val finalResult = normResult.union(hotResult)

解法 ④：提高 Shuffle 分区数（只对"轻度不均"有效）

只适用于没有极端热点 key，只是分区粒度太粗导致的不均（比如 200 个分区装 500GB）。对真正的热点 key 无效。

SET spark.sql.shuffle.partitions = 1000;   // 目标：单 Task 处理 128~256MB

解法 ⑤：开启 AQE 自动倾斜处理（Spark 3.0+，最省事）

spark.sql.adaptive.enabled=true
spark.sql.adaptive.skewJoin.enabled=true
spark.sql.adaptive.skewJoin.skewedPartitionFactor=5       // 超过中位数 5 倍视为倾斜
spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes=256MB
spark.sql.adaptive.advisoryPartitionSizeInBytes=128MB
原理AQE 在运行时看到真实的分区大小（而不是编译时猜），发现某个分区过大就自动把它切成多个小分区分别 join，再合并结果——相当于引擎替你做了"加盐拆分的等价操作"。现代 Spark 强烈建议默认开启。

解法 ⑥：处理读取倾斜

  • 避免不可切分的大 Gzip 文件：改用 Parquet / ORC / 可切分的 LZO / BZip2。一个 10GB 的 Gzip 只能由 1 个 Task 读。
  • 上游写数据时控制文件大小：让每个文件落在 128~512MB，避免单文件过大或海量小文件。
  • 跑 compaction：湖仓表里先用 OPTIMIZE / rewrite_data_files 把小文件合并均匀。

5怎么选解法

症状首选方案备选代价
聚合倾斜（groupBy / count distinct）① 加盐两阶段聚合⑤ AQE多一轮 Shuffle
大表 join 小表倾斜② 广播 join③ 分流小表要能装进内存
大表 join 大表倾斜③ 拆分热点单独处理⑤ AQE需要预先知道热点 key
轻度不均、无极端热点④ 调大分区数⑤ AQE几乎无
不想改代码 / SQL⑤ 开 AQE—需 Spark 3.0+
读阶段就不均⑥ 换可切分格式 + compaction—需要改上游写入
NULL / 空值导致的倾斜先过滤或赋随机值① 加盐需确认业务是否允许丢弃
NULL 陷阱特别值得单独提未登录用户的 user_id 常常是 NULL 或空串。这些记录可能有几亿条，全部 hash 到同一个分区。最简单的处理：WHERE user_id IS NOT NULL（业务允许就丢），或用 COALESCE(user_id, concat('rand_', rand())) 把它们打散。

6常见误区

"倾斜了就加大并行度 / 分区数"
最常见的无效操作。热点 key 无论分区数多少，只会落进一个桶。加大分区数只是让空桶更多，那个大桶一点没变小。只有在"没有极端热点、只是粒度粗"时才有效。
"加盐会影响结果正确性"
不会，只要第二阶段去掉盐后重新聚合。加盐只是把一次聚合拆成"局部聚合 + 全局聚合"两步，对满足结合律的操作（sum、count、max、min）完全等价。但要注意：avg 不能直接拆（要拆成 sum/count 两个），distinct count 也要特殊处理。
"开了 AQE 就再也不用管倾斜了"
AQE 很强但不是万能。它能自动处理 join 倾斜的分区拆分，但对聚合类倾斜、读取阶段倾斜、以及数据源本身不均帮助有限。而且它依赖运行时统计，某些复杂 SQL 下判断会失效。严重时仍需手工加盐或分流。
"广播 join 一定要用，越大越好"
广播表必须能装进每个 Executor 的内存，否则直接 OOM，且会挤占 Shuffle 可用内存。默认阈值 10MB 是保守值，调到 64MB / 100MB 常见，但不要广播几百 MB 的表。另外广播是"每个 Executor 一份"，Executor 数量多时总内存占用 = 表大小 × Executor 数。
