🆚 HBase vs Cassandra：两种宽列存储的路线之争

两者都是宽列存储、都能横向扩展，但一致性模型与架构哲学截然不同——选错会带来长期痛苦。

先建立直觉：两种组织方式

HBase 像一个有总部的连锁企业：有明确的中心（HMaster）负责协调，各门店（RegionServer）严格执行总部的安排。好处是规矩统一、账目准确；代价是总部出问题会影响全局。

Cassandra 像一个去中心化的合作社：没有总部，所有成员地位平等，互相之间直接沟通。好处是任何成员倒下都不影响整体运转；代价是「账目」需要一段时间才能在所有成员间对齐。

CAP 取舍：最本质的区别

不可写 Cassandra：选 AP 继续提供服务，稍后自行收敛一致 任何节点都能接收写入，分区期间 各自记账，恢复后按时间戳合并
这个差异带来的实际后果：
• HBase：你写入后立刻能读到，且读到的就是刚才写的值。适合「写完马上要读」「不能容忍读到旧值」的场景（如余额、订单状态）。
• Cassandra：写入后可能短暂读到旧值（取决于一致性级别配置）。适合「写入要快、要永远可写、能容忍短暂不一致」的场景（如消息、时序、日志）。

Cassandra 的可调一致性

Cassandra 允许每次读写指定一致性级别，这是它最大的灵活性：

-- 写：只要 W 个副本确认即返回
-- 读：从 R 个副本读取，取时间戳最新的

-- 强一致读：W + R > N（N 为副本数）
-- 例：N=3, QUORUM(2) + QUORUM(2) = 4 > 3  → 强一致

CONSISTENCY QUORUM;    -- 常用：多数派，兼顾性能与一致性
CONSISTENCY ALL;       -- 最强：等所有副本，最慢
CONSISTENCY ONE;       -- 最弱：一个副本即可，最快
CONSISTENCY LOCAL_QUORUM;  -- 多数据中心时，只等本地机房多数派
这就是 Cassandra 的精髓：它不是「只能最终一致」，而是把选择权交给你——按 W + R > N 的公式，你可以针对每次操作权衡性能与一致性。多数生产场景用 QUORUM。

🎯 面试问答

Q：HBase 和 Cassandra 最本质的区别是什么？
A：架构哲学与 CAP 取舍。HBase 是主从架构 + 强一致（CP），依赖 HDFS 和 ZooKeeper，网络分区时宁可拒绝服务也不返回不一致数据；Cassandra 是去中心化 + 最终一致（AP 倾向），无单点，任何节点都能写入。由此衍生出：HBase 写完立刻能读到最新值，Cassandra 可能短暂读到旧值（但可通过 QUORUM 级别调强）。

Q：Cassandra 能做到强一致吗？
A：能，通过可调一致性级别。核心公式：W + R > N（W=写确认副本数，R=读副本数，N=总副本数）。若 N=3 且读写都用 QUORUM（2），则 2+2=4 > 3，读写副本集必然有交集，从而保证读到最新值。代价：等待多个副本响应会增加延迟、降低可用性。实践：多数场景用 QUORUM 即可平衡；对一致性要求极高的操作可用 ALL，但会显著变慢。

Q：为什么都说 RowKey 设计最重要？
A：因为两者都按 key 决定数据分布在哪个节点，且key 是有序存储的。这带来两个后果：① 热点——如果 key 有单调递增前缀（如时间戳），所有新写入都会集中到同一个节点，集群其他节点闲置，写入能力等于单机；② 查询能力——只有按 key（或 key 前缀）查询才高效，非 key 条件的查询需要全表扫描或建二级索引。而且这个决策几乎不可逆转——改 key 设计意味着全量数据重写。所以必须在设计前彻㐎底梳理访问模式。

Q：已经有 Hadoop 集群，该选哪个？
A：优先考虑 HBase。理由：① 它与 HDFS原生集成，不需要额外存储系统；② Spark、Hive、Flink 都能直接读写 HBase，分析和在线访问可以共用一份数据；③ 团队已有的 Hadoop 运维经验可以复用。但如果有以下需求，仍应选 Cassandra：需要多数据中心部署、要求写入永不中断（AP）、或无法接受 HDFS 的运维复杂度。

选型判据：需要强一致、范围扫描（如按时间扫一段时间窗口）、已在 Hadoop 生态 → 选 HBase；需要多活多写、跨地域部署、无单点、写入吞吐极高 → 选 Cassandra。

关键配置与命令

# HBase：rowkey 设计是性能的生死线
# ❌ 时间戳打头：所有写入集中到一个 Region -> 热点，写不进去
rowkey = timestamp + user_id
# ✅ 加盐打散（salt 取 hash 的前 N 位）
salt = hash(user_id) % 20                       # 20 个前缀 = 20 个 Region 分摊
rowkey = f"{salt:02d}_{timestamp}_{user_id}"
# ✅ 或反转时间戳（适合「最新数据优先」的查询）
rowkey = user_id + "_" + (Long.MAX_VALUE - timestamp)

# Region 大小与分裂
# hbase.hregion.max.filesize 默认 10GB（0.94 前）/ 推荐 10~20GB
# 预分区：建表时就分好，避免早期全在一个 Region
create 't', 'cf', {NUMREGIONS => 20, SPLITALGO => 'HexStringSplit'}
-- Cassandra：分区键与聚簇键的设计
CREATE TABLE events (
    bucket     INT,          -- 分桶（如按天）：防止分区无限增长
    user_id    UUID,
    ts         TIMESTAMP,
    payload    TEXT,
    PRIMARY KEY ((bucket, user_id), ts)   -- ((分区键), 聚簇键)
) WITH CLUSTERING ORDER BY (ts DESC);
-- 分区键决定数据落在哪个节点（哈希）；聚簇键决定分区内的物理顺序
-- 分区大小建议 < 100MB、< 10 万行，否则查询会慢且压缩失效

-- 一致性级别：读写级别相加 > 副本数 才是强一致
-- RF=3 时：WRITE=QUORUM(2) + READ=QUORUM(2) -> 2+2 > 3 ✓ 强一致
--          WRITE=ONE(1) + READ=ONE(1)       -> 最快但可能读到旧值
CONSISTENCY QUORUM;
SELECT * FROM events WHERE bucket=20261022 AND user_id=? LIMIT 100;
