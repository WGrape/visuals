01建模第一原则：按查询设计分区键

Cassandra 不是关系库，不能先建表再随便查。分区键决定了数据落在哪个节点，必须按最高频的查询来设计。

CREATE TABLE orders_by_user (
  user_id   bigint,
  order_id  timeuuid,
  amount    decimal,
  PRIMARY KEY ((user_id), order_id)
) WITH CLUSTERING ORDER BY (order_id DESC);
-- 按 user_id 分区，order_id 聚簇排序，查某用户订单很快
  • 避免热分区：单一超级分区（如 user_id=0）会压垮一个节点 → 加桶 (user_id, bucket) 打散。
  • 分区键基数要够大，否则大量数据挤进少数分区。
  • 别用分区键做范围扫描，那是聚簇列的事。

02一致性级别调优

级别延迟一致性适用
ONE最低可能读旧对一致性不敏感的高吞吐读
QUORUM中多数派，强默认推荐，读写都 QUORUM
ALL最高全副本要求强但易超时，少用
LOCAL_QUORUM低（不跨 DC）多数派本地多数据中心首选

读写可以分别设不同级别（写 QUORUM、读 ONE 提高读吞吐），但要清楚代价。

03常用运维命令

nodetool status            # 看集群节点/状态/负载
nodetool cfstats ks.table  # 表级统计
nodetool repair -pr ks      # 反熵修复（定期跑，否则副本漂移）
nodetool compact ks table   # 手动 compaction
nodetool flush              # 内存表刷盘
要点：REPAIR 不跑的后果：节点失效后副本数据不一致且无法自动收敛。这是 Cassandra 运维的头号责任。

04常见反模式

  • 宽行无限增长（一个分区塞几百万行）→ 读写都慢、易超分区大小限制。
  • 滥用 Secondary Index：本质是隐藏的全集群扫描，热点明显。
  • 把 Cassandra 当关系库用（大量 join、聚合）→ 性能崩溃，应在写入时反范式化。
问：什么时候不该用 Cassandra？

需要复杂事务、跨行 ACID、或强一致读的场景；以及团队没有运维分布式存储经验时，先用托管方案更稳。
