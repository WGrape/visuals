①时序库真正擅长的负载

时序库为追加为主、几乎不变、按时间范围扫描、按标签聚合的负载设计：监控指标、IoT 采样、行情快照都属于这一类。它的压缩、降采样、TTL 都是围绕"时间戳 + 标签 + 数值"这个固定模式优化的。

判断口诀：如果数据主要是"某个对象在某个时刻的某个值"，时序库是首选；一旦偏离这个模式，就要警惕。

②三类不该直接进时序库的数据

  1. 事务型 / 需要强一致更新的数据：订单状态、账户余额——它们要 UPDATE、要事务、要回滚，时序库没有这些语义（或很弱），硬塞进去会丢失一致性保证。
  2. 需要多表关联的关系数据：用户档案、商品目录——它们靠 JOIN 和规范化组织，时序库通常不支持或极弱地支持关联查询。
  3. 需要频繁回改 / 删除的历史明细：审计流水、聊天记录——时序库的追加与 TTL 模型不适合"随时改一条旧记录"。

这些不是"不能存"，而是存进去后用不好：要么一致性没保障，要么查询要绕大弯。

③与关系库 / 数仓的边界

数据类型用时序库？更合适的归宿
监控指标 / IoT 采样是时序库（本职）
订单 / 账户余额否关系库（事务）
用户 / 商品档案否关系库（规范化）
行为事件流 / 日志看用法消息队列 + 数仓
需要回改的历史明细否关系库 / 对象存储

经验原则：热路径上"每时刻的值"进时序库；与之关联的"实体属性"（谁、什么类型、配置）留在关系库，通过标签/外键关联。两者配合，而不是用一个库扛所有。

④误用时序库的真实案例

把用户行为事件流全灌进时序库：事件本应进消息队列 + 数仓做漏斗分析，硬塞进 TSDB 后既做不了漏斗（没有会话关联），又因高基数（每个 user_id 一条线）把内存打爆。

把订单写进时序库：下单后状态变更只能用"再插入一条新样本"模拟，查询"当前未完成订单"要扫最近所有样本再聚合，远不如关系库一条 UPDATE + 索引。

⑤选型决策清单

在决定用时序库前问自己：① 数据主要是"时刻-值"吗？② 需要事务 / 回滚吗？③ 需要多实体 JOIN 吗？④ 单对象的历史会被原地修改吗？⑤ 基数可控吗？ 若 ②③④ 有任一是"是"，优先考虑关系库或数仓，时序库只承载其中的指标采样部分。

边界量化与代价

时序库把每个唯一标签组合当成一条独立时间线维护索引与内存；而关系库按行存、按主键查。当你的数据其实要“按主键更新一行”时，时序库的追加模型会让这个操作变成“插新样本 + 全量聚合”，查询成本随历史线性增长。所以改多于追加的数据，关系库更划算。

排障：已经误用了怎么办

① 分清冷热：把"时刻-值"部分留在时序库，把"实体属性/事务"迁回关系库；② 用标签对齐：时序库的标签值（如 order_id）只作展示/弱关联，真正的关联键放关系库；③ 高基数止血：若因 user_id 做标签导致内存暴涨，先 drop 高基数标签维度，改由关系库做用户级聚合后再回流指标；④ 双写过渡：迁移期间双写，验证新链路无误后再停旧写。

自检 Q&A

时序库能不能做事务？

多数时序库不支持跨序列的 ACID 事务。InfluxDB/TDengine 等提供单点写入的原子性，但没有“扣余额同时写流水”这种跨实体事务。需要事务请回关系库。

日志 / 行为事件该不该进时序库？

纯“看趋势”的聚合指标可以；但要漏斗、会话、明细下钻的事件流更适合消息队列 + 数仓。把事件当指标塞进 TSDB，既做不了关联分析，又容易因高基数拖垮集群。

能不能一个库搞定所有？

可以但不划算。能用时序库存指标、关系库存实体的“双库配合”是主流做法；强行单库，要么在时序库里模拟事务（慢且易错），要么在关系库里存海量时序（存储与查询都贵）。
