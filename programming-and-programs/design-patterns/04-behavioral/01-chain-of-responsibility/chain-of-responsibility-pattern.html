🔗 责任链

让请求沿着一条处理链传递，直到有人处理或链走完。

一句话记住报销单先到组长，金额太大再交经理。
问题从哪来图解协作动手试一试伪代码选型与边界
01 · 从问题出发

为什么会需要这个模式？

请求要经过鉴权、限流、业务校验；把所有步骤硬写在一个巨型函数里，增删步骤都难。

请求必须先鉴权、再限流、再处理业务。若一个函数承包所有规则，加一步风控就会修改巨型函数；若每个业务入口都复制检查链，顺序又可能不一致。

😵 直接写会怎样

function handle(req):
  if not authenticated(req): return 401
  if overLimit(req): return 429
  if risky(req): return 403
  return business(req)

💡 关键转折

每个处理器只做自己的事，并决定继续传给下一位或就此结束。

把检查拆为处理器，每个处理器只负责一个判断；通过后才显式调用 next，失败时短路返回。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

function auth(req, next) {
  if (!req.user) return Unauthorized
  return next(req)
}
function limit(req, next) {
  if (quota.exceeded(req.user)) return TooManyRequests
  return next(req)
}
handle = chain(auth, limit, business)
result = handle(request)

读代码时抓住三件事

  1. 处理器通过 next(req) 显式交给下一位。
  2. 每一环可以提前返回，所以顺序影响结果。
  3. 链尾必须有确定行为，不能让请求悄悄消失。

换个业务场景，还能认出来吗？

Web 中间件常把请求日志、鉴权、限流、路由处理串成一条链。日志如果要记录最终响应，可在 next 前后各执行一段逻辑，像洋葱一样包住后续处理。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

请求需经过可组合的多道检查，且可能中途结束

三个具体场景

  • HTTP 中间件串联鉴权与限流
  • 报销按金额逐级审批
  • 日志消息按级别进入不同处理器

不适合或要小心

明确链尾行为；顺序会影响语义，比如鉴权应先于耗资源操作。不要让处理器悄悄吞掉请求。

顺序和链尾行为必须明确；处理器不能默默吞请求

最容易混淆的相邻模式

模式真正的区别
装饰器也可形成包装链，但重点是叠加同一对象职责；责任链重点是沿链传递请求并允许某环处理或终止。
命令把操作封装成可传递的对象；责任链决定谁接收并处理请求。

区分时问自己：请求是在链上找处理者，还是给同一对象叠加职责？

落地前检查

  • 明确处理器顺序及链尾默认结果。
  • 测试每个短路分支都不会执行后续节点。
  • 注意异步 next 只能按约定调用一次，避免重复处理。

模式速览：让请求沿着链走，直到有人接手

责任链解决的是「请求可能有多个处理者，但事先不知道该由谁处理」的问题。做法是把处理者串成一条链，每个处理者决定：自己处理，还是交给下一个。

意图让多个对象都有机会处理请求，解耦发送者与接收者
角色处理者接口、具体处理者、链的组装方
何时用处理者不固定、顺序可配置、需要动态增减步骤
代价可能无人处理；链太长难调试；顺序敏感
责任链的流转：每个环节自己决定处理还是下传

四种相近写法怎么区分

写法各环节的权力是否会终止典型用途
责任链可处理也可下传处理后通常终止审批流、事件分发、校验
装饰器每个都要执行不终止，层层包裹给对象叠加能力
过滤器链都要执行，且分前置后置不终止请求与响应的拦截处理
策略列表只选一个执行选中即终止按条件选择算法

责任链与装饰器的区别

责任链是选择型的：通常只有一个环节真正处理，处理完就结束；装饰器是叠加型的：每个环节都要执行，共同完成一件事。判断方法很简单：如果拿掉一个环节，功能就不完整，那是装饰器。

终止还是继续

这是设计责任链时必须明确的约定。纯责任链处理完就停止；但很多现实场景需要「处理完继续传递」，比如中间件既要记录日志又要把请求交给下一环。这时它其实混合了过滤器链的语义，要在接口里说清楚。

Go 里的实现：中间件链

type Handler func(ctx *Context) error // 把多个处理者串成一条链 func Chain(handlers ...Handler) Handler { return func(ctx *Context) error { for _, h := range handlers { if err := h(ctx); err != nil { return err // 出错即终止，不再传递 } if ctx.Done { return nil // 已有人处理完，提前结束 } } return nil } } // 具体处理者：满足条件就处理并标记完成 func Auth(ctx *Context) error { if !ctx.HasToken { return errors.New("未认证") // 直接终止 } return nil // 放行给下一个 } func RateLimit(ctx *Context) error { if ctx.QPS > limit { return errors.New("被限流") } return nil } func Cache(ctx *Context) error { if v, ok := cache.Get(ctx.Key); ok { ctx.Result = v ctx.Done = true // 命中缓存，提前结束 } return nil } // 组装：顺序在这里决定，调用方完全解耦 h := Chain(Auth, RateLimit, Cache, Business) err := h(ctx) // 关键点： // 1) 顺序即策略，认证与限流必须在业务之前 // 2) 用返回值表达终止，用标记表达提前完成 // 3) 增删环节只改组装处，不改任何处理者

深入自检：责任链的五个问题

没人处理怎么办？

这是责任链的固有风险，必须显式约定：要么在链尾放一个兜底处理者，要么返回明确的失败，绝不能静默忽略。很多线上问题就出在「请求走完了整条链但谁都没处理」，看起来成功、实际上什么也没做。

链太长有什么问题？

调试困难：要理解一次请求的完整行为，得把所有环节都读一遍；性能也有累积开销。应对办法是给每个环节打日志或埋点，让请求经过的路径可观测。

顺序敏感怎么处理？

顺序往往是业务规则的一部分，比如认证必须在限流前、缓存必须在业务前。建议把顺序集中写在组装处并加注释，而不是散落在各处。必要时用显式的顺序声明而不是数组顺序。

处理者之间能共享状态吗？

可以通过上下文对象传递，但要明确约定谁写谁读，否则会退化成隐式的全局状态。更好的做法是让上下文只承载请求级数据，并且每个环节只写自己负责的字段。

什么时候不该用？

当处理者固定、只有一两个步骤时。直接 if-else 或 switch 更清楚，引入链反而把简单逻辑复杂化。责任链的价值在于处理者可变、顺序可配、需要动态扩展。

核心动作把处理者串成链，逐个尝试
两种约定处理即终止，或处理完继续传
必须有兜底否则可能无人处理
顺序即策略集中写在组装处
可观测记录请求经过的环节
上下文只在其中传递请求级数据
与装饰器区别一个选择执行，一个全部执行
典型场景中间件、审批流、校验链
