①Sargability：谓词能不能用上索引

Sargable = Search ArgumentABLE，指一个谓词能否被优化器转成「索引范围扫描」而不是全表扫描。 这是 SQL 性能里投入产出比最高的一个概念：改一个写法，可能从 8 秒降到 8 毫秒。

核心原则：让裸列单独出现在比较运算符的一侧，把计算放到常量那一侧
写法Sargable？改写
WHERE YEAR(d)=2026✗d >= '2026-01-01' AND d < '2027-01-01'
WHERE amount+0 > 100✗amount > 100
WHERE name LIKE '%abc'✗前缀通配符无法走 B+Tree，改用全文索引/倒排
WHERE name LIKE 'abc%'✓后缀通配可以走范围扫描
WHERE id = '123'（id 是整型）视实现隐式转换可能让索引失效，写成 id = 123
WHERE a=1 OR b=2各列独立有时失效拆成 UNION ALL 两个分支各自走索引
WHERE col IS NULL✓（多数实现）B+Tree 也会存 NULL，通常可用
WHERE col != 1△选择性差时优化器主动放弃索引

②三值逻辑与 NULL 过滤

SQL 的布尔逻辑是三值的：TRUE / FALSE / UNKNOWN。任何与 NULL 的比较结果都是 UNKNOWN， 而 WHERE 只保留 TRUE 的行——UNKNOWN 和 FALSE 一样被丢弃。这是「我明明写了条件怎么查不出来」的头号原因。

表达式结果说明
NULL = NULLUNKNOWN必须用 IS NULL 判断
NULL <> 1UNKNOWN不会返回「所有不等于 1 的行」
NULL AND TRUEUNKNOWNAND 遇 FALSE 才 FALSE
NULL OR TRUETRUEOR 遇 TRUE 即 TRUE——唯一能「救回」NULL 的地方
NOT UNKNOWNUNKNOWNNOT IN 踩坑根源
-- 想查「状态不是已完成」的所有单，但 status 可能为 NULL
SELECT * FROM orders WHERE status <> 'done';        -- ✗ 漏掉 status IS NULL 的行
SELECT * FROM orders WHERE status <> 'done' OR status IS NULL;  -- ✓

-- 更稳的写法（各库支持度不同）：空值安全等值比较
SELECT * FROM orders WHERE NOT (status <=> 'done');   -- MySQL 的 NULL 安全等于
SELECT * FROM orders WHERE status IS DISTINCT FROM 'done';  -- PostgreSQL / SQL 标准
聚合函数普遍忽略 NULL（COUNT(col) 不数 NULL，SUM/AVG 跳过）， 但 COUNT(*) 数的是行、不看列值。所以 COUNT(*) 与 COUNT(col) 不相等， 恰恰可以用来探测 NULL 数量：COUNT(*) - COUNT(col)。

③隐式类型转换

比较的两边类型不同时，数据库要做隐式转换。转换方向决定索引生死：如果被转换的是列， 等价于给列套了一层函数，索引失效；如果被转换的是常量，索引照常可用。

场景谁被转换索引
整型列 vs 字符串常量 id = '123'多数库把字符串转成数字（转常量）通常可用
字符串列 vs 数字常量 phone = 13800138000列被转数字失效
字符集/排序规则不一致的两列 JOIN列被转换失效
VARCHAR 列存日期再与 DATE 比较列被转换失效
最隐蔽的一条：JOIN 两列字符集不同。看起来两列都有索引、类型都是 varchar， 但一个 utf8mb4_general_ci 一个 utf8mb4_0900_ai_ci，或一个是 utf8 一个是 utf8mb4， 就会导致被驱动表那侧无法走索引，退化成全表扫描。建库时统一字符集与排序规则是最省事的预防。

④谓词下推与条件位置

标准 SQL 的执行顺序里 WHERE 在 JOIN 之后、聚合之前，但优化器会做 谓词下推：把能提前的过滤条件挪到更早的算子，减少后续处理的数据量。理解它能解释很多「写法不同但计划相同」。

ON 里加条件 vs WHERE 里加条件

INNER JOIN 两者等价（优化器会重排）；OUTER JOIN 不等价—— ON 里的条件在生成 NULL 行之前生效，WHERE 里的条件在之后生效。 把 LEFT JOIN 的右表条件写进 WHERE，效果等同 INNER JOIN。

WHERE vs HAVING

WHERE 在聚合前过滤行（减少聚合输入，更高效）； HAVING 在聚合后过滤分组。能放 WHERE 就不要放 HAVING。

能下推不代表一定下推

含 OR、子查询、不确定性函数、LIMIT 的视图，优化器可能无法下推。 看执行计划里过滤算子出现在哪一层，而不是凭 SQL 结构猜。

-- ❌ 常见错误：想把「已取消的订单排除」，却写成了 INNER JOIN
SELECT * FROM orders o
LEFT JOIN payments p ON p.order_id = o.id
WHERE p.status = 'paid';          -- 未支付的行 p.status 是 NULL，被 WHERE 干掉了

-- ✓ 条件放进 ON，保留所有订单
SELECT * FROM orders o
LEFT JOIN payments p ON p.order_id = o.id AND p.status = 'paid';

⑤过滤条件的自检清单

  1. 比较运算符的一侧是不是裸列？列上有没有包函数、算术、隐式转换？
  2. 条件涉及 NULL 吗？用 IS NULL / IS DISTINCT FROM 而不是 = NULL 或 <>。
  3. 字符串常量有没有写错类型（给数字列传了带引号的值、给字符串列传了数字）？
  4. 是 OR 吗？拆成 UNION ALL 会不会各自都能走索引？
  5. 外连接的右表条件是不是误写进了 WHERE？
  6. 能在 WHERE 过滤的，有没有跑到 HAVING 里去？
  7. 执行计划里这个过滤算子出现在第几层？实际扫描行数与预估差多少倍？
Q：WHERE 1=1 会影响性能吗？
A：不会，常量折叠在优化阶段就消掉了。它是动态拼 SQL 时为了方便加 AND 的写法，可以放心用。
Q：为什么我加了索引还是全表扫描？
A：三种常见原因：① 谓词不可 Sargable（本节 ①）；② 选择率太高——优化器估算要回表 30% 以上行数时， 随机 IO 比顺序扫更贵，会主动放弃索引；③ 统计信息过期，估算失真。先确认是哪种，再决定改写法还是更新统计信息。
