01容器与 VM 的区别

第一层

概念与判定

容器不是虚拟化硬件，而是隔离进程：它复用宿主机内核，用 namespace 做视图隔离、用 cgroup 做资源限制。所以容器比 VM 轻得多（秒级启动、近乎零开销），但隔离性弱于 VM（共享内核，一个内核漏洞全破）。

图：容器共享内核；VM 各有内核。
隔离维度Linux 原语
PIDpid namespace：容器内 1 号进程是自己的
Mountmount namespace：独立挂载树（overlayfs）
Networknet namespace：独立网卡/端口/路由
UTS/IPC/User主机名 / System V IPC / 用户映射
资源cgroup v2：CPU/内存/IO 限额
OCI 标准：容器镜像与运行时由 OCI 规范定义。runc 是参考实现，Docker/containerd/CRI-O 都调用它启动容器。overlayfs 用「下层镜像 + 上层可写层」叠加出容器的文件系统，省空间。

02运行时与配额

第二层

参数·命令·量化

运行时与配额

# 看当前命名空间（每个进程一个链接）
ls -l /proc/$$/ns/

# 进入/创建命名空间测试（unshare）
unshare --pid --fork --mount-proc bash     # 新 pid 命名空间

# cgroup v2 限额
echo 500000 > cpu.max               # 500ms/1s = 0.5 核
 echo 200M > memory.max              # 内存硬限

# 镜像层（overlayfs）
docker image inspect  | grep -A20 GraphDriver
 # LowerDir(只读镜像层) + UpperDir(可写层) + WorkDir

# runc 直接跑（OCI bundle）
runc run mybox
命令用途
unshare新建 namespace 跑程序（理解隔离）
nsenter进入已有容器的 namespace 调试
runcOCI 运行时，真正 create/start 容器
ctr / crictlcontainerd / k8s 的 CLI
User namespace 没开 = 容器内 root 近似宿主机 root：很多镜像以 root 跑且未映射 user ns，一旦逃逸影响宿主机。生产应开 userns 或非 root 运行。

03排障与边界

第三层

排障与边界

  • seccomp 过滤：默认容器已挡掉一批危险 syscall（如 reboot、swapon）。自定义 profile 可进一步收敛攻击面，但漏放会报 operation not permitted。
  • 特权容器（--privileged）：几乎等于拿到宿主机，能挂设备、改网络。应尽量避免；需要设备用 --device 精确授权。
  • fork 炸弹 / No Limit：忘设 cgroup 限额，容器内狂起进程拖垮宿主机（嘈杂邻居）。务必设 CPU/内存限。
  • overlayfs 写满：UpperDir 在宿主机某分区，容器日志/临时文件写爆会让同盘其他容器受影响。
  • 拷贝-on-write 镜像是只读层：运行时不提交（commit）的改动，容器删除即丢。持久化要走 volume（bind mount）。

04原理与取舍

第四层

原理与取舍

容器 = namespace(看不同) + cgroup(用受限) + overlayfs(文件独立)。它把「进程」包装成「应用单元」，代价是隔离依赖内核安全（没有独立内核这道墙）。

维度容器VM
启动秒级分钟级
开销近乎零Guest OS + 虚拟化
隔离共享内核（弱）独立内核（强）
密度高低
内核版本锁死宿主机可不同

深入 Q&A

Q：为什么容器里看到自己的 PID 1？
A：pid namespace 让容器内的进程树从 1 重新编号，容器里的 init 进程 PID=1（收到 SIGTERM 才能优雅退出）。宿主机的真实 PID 是另一个数。

Q：Kata / gVisor 是什么？
A：为补容器隔离短板——Kata 给每个容器跑一个轻量 VM（强隔离），gVisor 用用户态内核拦截 syscall（中等隔离、轻量）。介于纯容器和 VM 之间。

Namespace 与 cgroup 的实测命令

容器不是虚拟机，它是一组 namespace（看得见什么）+ 一组 cgroup（能用多少）+ 一个 rootfs（能读什么文件）。下面这组命令可以把这三层分别拆开来看。

拆解容器的三件事

# 1) 手动造一个最小容器：只用 unshare，不用 docker
unshare --mount --uts --ipc --pid --net --fork --mount-proc bash
# 进去后：ps 只有两个进程、hostname 独立、ip a 只有 lo

# 2) 从宿主机进入某个容器/进程的 namespace（排障神器）
nsenter --target $PID --mount --uts --ipc --net --pid -- bash
docker inspect <cid> --format '{{.State.Pid}}'      # 先拿到容器 PID 1 在宿主机的 PID

# 3) 看容器用了哪些 namespace
ls -l /proc/$PID/ns/
readlink /proc/$PID/ns/pid /proc/$PID/ns/net

# 4) 看 cgroup 限制（cgroup v2 路径）
cat /sys/fs/cgroup/system.slice/docker-<cid>.scope/memory.max
cat /sys/fs/cgroup/system.slice/docker-<cid>.scope/cpu.max      # 格式：quota period
cat /sys/fs/cgroup/system.slice/docker-<cid>.scope/pids.max

限额与限流观测

# 资源限制（Docker CLI 直接对应 cgroup 文件）
docker run --memory=512m --memory-swap=1g \   # memory.max / memory.swap.max
           --cpus=1.5 \                        # 等价于 cpu.max = 150000 100000
           --pids-limit=200 \                  # pids.max，防 fork 炸弹
           --blkio-weight=500 \
           nginx

# 运行时看实际用量与限流次数（被限流说明配额打满）
docker stats <cid>
cat /sys/fs/cgroup/.../memory.current
cat /sys/fs/cgroup/.../cpu.stat        # nr_throttled / throttled_time 是关键
cat /sys/fs/cgroup/.../memory.events   # oom_kill 计数大于 0 说明发生过 OOM
对比项cgroup v1cgroup v2实际影响
层级每个控制器一棵树，混乱单一统一层级v2 更容易做整体限额
内存 OOM整组杀进程可先回收再杀，报告更细v2 上 OOM 行为更可预期
CPU 限额cpu.cfs_quota_us / cpu.cfs_period_uscpu.max（quota period）换算关系一致：quota/period = 核数
IO 控制blkio 控制器（不完善）io 控制器，支持权重与上限v2 才能真正限 IO
Docker 支持默认（旧版本）Docker 20.10+ 支持，K8s 1.25+ 推荐新集群基本都走 v2

判断 CPU 是否被限流只看一个文件：cpu.stat 里的 nr_throttled 与 throttled_time。它不是「用了多少 CPU」，而是因为配额用完被强行暂停了多少次，这个值持续增长就说明 --cpus 给小了。

边界、排障与清单

容器共享宿主内核，这是它轻量（启动毫秒级、无 Guest OS）的原因，也是所有边界问题的根源。

边界项是否隔离后果规避方式
内核与内核模块不隔离容器里加载模块会影响整机禁止 privileged / SYS_MODULE
系统时间基本不隔离改时间影响宿主（需 CAP_SYS_TIME）不给该 capability
/proc、/sys 的只读内核信息部分不隔离free 看到的是宿主内存用 cgroup 文件取真实限额
设备与 /dev默认受限需要显式 --device只挂必需设备
root 用户默认容器 root = 宿主 root（未做映射）逃逸风险用 rootless 或 userns-remap
网络端口取决于网络模式host 模式直接占用宿主端口优先 bridge + 显式端口映射

容器内排障

# 排障：确认自己到底在不在容器里
cat /proc/1/cgroup | head -3          # 含 docker/kubepods 即为容器
ls -l /proc/1/ns/pid                  # 与宿主 PID 1 比较 inode
cat /proc/self/mountinfo | grep -c docker   # overlay 挂载点

# 常见故障一：容器内 ps/free 看到宿主数据
#   解法：以 cgroup 文件为准
cat /sys/fs/cgroup/memory.max /sys/fs/cgroup/memory.current

# 常见故障二：Java/Go runtime 按宿主核数开线程
#   解法：显式设置
docker run --cpus=2 -e GOMAXPROCS=2 ...
java -XX:ActiveProcessorCount=2 ...     # 或 -XX:+UseContainerSupport（JDK 8u191+ 默认开启）

# 常见故障三：OOM 被杀但日志里看不到
dmesg | grep -i 'killed process'
kubectl describe pod <pod> | grep -A3 'Last State'

上线与排障逐条核对：

  • 不要给 privileged：它等于把宿主所有 capability 与设备都交出去，逃逸风险极高。
  • 必须设内存与 PID 上限：只有 CPU 限额时，内存打满会拖垮同机所有容器。
  • 用 cgroup 文件而不是 free/top 判断资源：容器内看到的往往是宿主数据。
  • JVM/Go 要显式声明可用核数，否则按宿主核数开线程，容易被 throttle。
  • rootless 或 userns-remap：让容器内 root 映射到宿主普通用户。
  • 共享宿主的 /proc、/sys 只读挂载，避免容器修改宿主状态。
  • CPU 被限流看 cpu.stat 的 nr_throttled，不要只看 CPU 使用率。
  • 镜像要基于 scratch/distroless 或 alpine：体积越小，攻击面与启动时间越小。
  • 时区、证书、nsswitch 是容器内三大常见坑，镜像里要明确处理。
  • 健康检查用 exec 探针而不是简单端口探测：端口在不代表应用可用。
