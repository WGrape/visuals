第 04 章 · 数组与链表

连续存储与链式连接

同样是线性序列，数组擅长定位，链表擅长在已知位置改变连接关系。

核心速览

数组连续内存 + 按下标 O(1) + 缓存友好
动态数组容量不足时扩容（翻倍），均摊 O(1) 追加
单向链表每个节点存 next，只有后继
双向链表存 prev + next，可双向遍历

本质差别只有一句：内存是否连续

数组和链表存的是同样的线性序列，但内存布局完全不同。这一个差别派生出了后面所有的性能差异。

页脚那句话是关键：「比较复杂度前，先写清位置是否已知」。链表的插入是 O(1)——但前提是已经拿到了那个位置的指针；找到那个位置本身往往要 O(n)。脱离前提谈复杂度就会得出错误结论。

复杂度对照

操作数组链表说明
按下标访问 a[i]O(1)O(n)数组直接算地址；链表要逐个跳转
查找某值O(n)（有序则 O(log n)）O(n)都要遍历
在头部插入O(n)O(1)数组要全体后移
在尾部插入O(1)（动态数组均摊）O(1)（有尾指针）数组容量不足时扩容 O(n)，均摊 O(1)
在已知位置插入/删除O(n)（要搬移）O(1)（改指针）这是链表唯一的优势
内存开销紧凑（只有数据）每节点多 1~2 个指针双向链表还要 prev
缓存局部性极好（连续，可预取）差（跳跃访问）实际性能的重要差距

一个常被忽略的实际差距：缓存。数组元素连续存放，CPU 会预取相邻数据到缓存行，顺序遍历几乎全是缓存命中；链表节点分散在堆里，每次跳转都可能是缓存未命中（代价约 100 个 CPU 周期）。所以即使理论复杂度相同，数组的实际速度也经常快几倍——这也是为什么很多高性能场景宁愿用数组。

动态数组：为什么追加是均摊 O(1)

数组长度固定，但「动态数组」（C++ vector、Java ArrayList、Python list）能自动扩容。

  1. 容量不足时，申请一块 2 倍（或 1.5 倍）大的新内存。
  2. 把旧元素全部拷贝过去，释放旧空间。
  3. 后续 n 次追加都不需要再扩容。
均摊分析：单次扩容 O(n)，但它「保护」了接下来约 n 次 O(1) 的追加。把 O(n) 摊到 n 次操作上，每次只多摊 O(1)（等比数列求和收敛），所以追加的均摊复杂度是 O(1)。这跟哈希表扩容是同一个道理。经验：如果能预估大小，提前 reserve(n) 可以完全避免扩容抖动。

链表的几个经典技巧

1. 哑节点（dummy head）

在头节点前加一个不存数据的节点，消除「删除的是头节点」这一特殊情况，所有节点都能用同一套逻辑处理。

2. 快慢指针

用法做法原理
找中点slow 走 1 步、fast 走 2 步fast 到尾时 slow 正好在中点
判环同上，看二者是否相遇有环则 fast 必然追上 slow
找环入口相遇后，一个从头、一个从相遇点，同速前进再次相遇处即环入口
删除倒数第 k 个fast 先走 k 步，然后同速走fast 到尾时 slow 正好在待删节点前

3. 反转链表

def reverse(head):
    prev, cur = None, head
    while cur:
        nxt = cur.next      # 先存住下一个，否则改指针后就丢了
        cur.next = prev     # 反转指向
        prev, cur = cur, nxt
    return prev             # 循环结束时 prev 是新的头
反转链表的三个指针（prev / cur / nxt）是所有链表操作的基础功。关键是先存 nxt 再改指针，否则会丢失后续节点。理解了它，回文链表、K 个一组反转、重排链表等题目都是它的变体。

怎么选

场景选择原因
频繁按下标随机访问数组O(1) 且缓存友好
频繁在中间插入删除（且已有位置指针）链表改指针 O(1)
大小已知且固定数组无扩容开销
大小频繁变化、无法预估动态数组 / 链表看主要操作是访问还是增删
需要双向遍历双向链表有 prev 指针
追求实际运行速度通常数组缓存局部性带来巨大优势
要频繁按位置访问 + 有序查找数组 + 二分O(log n) 查找
工程经验：默认选数组（动态数组）。因为缓存局部性带来的实际收益往往超过理论复杂度的差异——哪怕链表在某个操作上复杂度更低，n 不大时数组通常更快。只有在「确实需要在已知位置频繁插入删除、且 n 很大」时才考虑链表。另外：需要有序查找时，数组的二分查找（O(log n)）是链表完全做不到的。

🎯 面试问答

Q：数组和链表最本质的区别是什么？

A：内存是否连续。数组在内存中连续存放，因此能按下标 O(1) 直接算出地址（基址 + i × 元素大小），且缓存局部性极好；但中间插入删除要搬移后续元素 O(n)。链表节点分散在内存中、靠指针串联，在已知位置插入删除只需改指针 O(1)，但按位置访问要逐个跳转 O(n)，且每节点有额外指针开销、缓存不友好。谈复杂度时必须写清「位置是否已知」这个前提。

Q：为什么链表插入是 O(1)，但很多人说链表插入慢？

A：因为 O(1) 的前提是「已经拿到了该位置的节点指针」，而在单链表中找到第 k 个位置本身就要 O(n)（只能从头逐个 next）。所以完整的「在第 k 个位置插入」是 O(n) 查找 + O(1) 修改 = O(n)，与数组同级甚至更慢（数组至少还能一次算出地址）。链表真正占优的场景是：已经持有节点指针（如遍历过程中、或 LRU 缓存里用哈希表记着指针），此时插入删除确实只有 O(1)。

Q：动态数组追加元素为什么是均摊 O(1)？

A：因为扩容不常发生。容量不足时申请一块约 2 倍大的新内存、把 n 个元素拷过去（O(n)），但这次扩容「保护」了接下来约 n 次 O(1) 的追加。把 O(n) 摊到这 n 次操作上，每次只多摊 O(1)（等比数列求和收敛为常数），所以追加的均摊复杂度是 O(1)。这和哈希表扩容是同一个道理。实践建议：如果能预估大小，提前 reserve(n) 可以完全避免扩容抖动。

Q：快慢指针能解决哪些链表问题？

A：四类经典问题：① 找中点——slow 走 1 步、fast 走 2 步，fast 到尾时 slow 正好在中点；② 判环——二者若相遇则有环（fast 必然追上 slow）；③ 找环入口——相遇后，一个指针从头、一个从相遇点同速前进，再次相遇处即入口；④ 删除倒数第 k 个——fast 先走 k 步，然后二者同速，fast 到尾时 slow 正好在待删节点的前一个。共同点是只用 O(1) 额外空间，通过「速度差」编码位置关系。

Q：反转链表怎么写？关键点是什么？

A：维护 prev / cur / nxt 三个指针：循环中先存 nxt = cur.next，再把 cur.next = prev 反转指向，然后 prev, cur = cur, nxt 整体前移；循环结束时 prev 就是新头节点。最关键的一点是「先存 nxt 再改指针」——否则改了 cur.next 后就再也找不到后续节点了。掌握了它，回文链表、K 个一组反转、重排链表等都是它的变体。

Q：实际工程中应该优先选数组还是链表？

A：默认选数组（动态数组）。理由：缓存局部性带来的实际收益常常超过理论复杂度差异——数组连续存放、CPU 能预取相邻数据，顺序遍历几乎全是缓存命中；链表每次跳转都可能是缓存未命中（代价约 100 个 CPU 周期）。所以即使链表在某个操作上复杂度更低，n 不大时数组通常更快。链表适合的场景：确实需要在已知位置频繁插入删除、n 很大、或需要稳定地址（元素地址不因扩容而失效）。此外需要有序查找时，数组的二分 O(log n) 是链表完全做不到的。
