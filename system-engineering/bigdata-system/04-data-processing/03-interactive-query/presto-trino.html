传统方案（如 Hive）像把所有货物运到同一个仓库再清点——慢，但稳。

Presto/Trino 像开一场视频会议，让各地仓库各自清点后直接报数——不用搬货，快得多。它能直接查询 Hive、MySQL、Kafka、Redis、Elasticsearch 等多种数据源，甚至在一条 SQL 里把它们 JOIN 起来。

Trino 不做容错，这是它换速度付出的代价。MapReduce/Spark 会把中间结果落盘，某个 task 失败可以单独重试；Trino 全在内存里跑，任何一个环节失败，整个查询就失败重来。所以它不适合跑几小时的巨型 ETL，那是 Spark 的活。

Presto 与 Trino 的关系

两者本是同一个项目。2019 年因治理分歧分叉：原班核心团队出走创立 Trino（原 PrestoSQL），而 Facebook 保留 PrestoDB。目前 Trino 社区更活跃，新项目建议选 Trino。

使用要点与常见坑

① 易 OOM。全内存执行意味着大查询可能撑爆 Worker。需要：配置合理的内存限制、避免超大 JOIN、开启溢出到磁盘（Trino 的 spill to disk 可缓解但会降速）。
② 大表 JOIN 要小心。默认 broadcast join 会把小表广播到所有 Worker，小表其实不小就会 OOM。解法：确认统计信息准确，或改用 distributed join（hash 分发）。
③ 谓词下推很关键。Connector 支持的话，过滤条件会下推到数据源（如 MySQL 里先 WHERE 再返回），能极大减少传输量。检查执行计划确认下推是否生效。
④ 最佳实践：把 Trino 用于交互式分析、即席查询、跨源联邦查询；把重 ETL 交给 Spark。两者互补，不是替代关系。

🎯 面试问答

Q：Presto 和 Trino 该选哪个？
A：新项目选 Trino。两者同源（Trino 原名 PrestoSQL），2019 年因社区治理分歧分叉，核心开发者多数加入了 Trino。目前 Trino 的社区更活跃、版本迭代更快、新特性更多（如更好的容错执行 FTE、Iceberg 支持）。PrestoDB 由 Facebook 维护，仍在发展但生态相对小。

Q：为什么 Trino 不做容错？
A：这是为速度做出的取舍。落盘（像 MapReduce 那样）可以带来 task 级重试的容错能力，但每次落盘的 IO 开销会让延迟从秒级升到分钟级。Trino 的定位是交互式查询——查询通常几秒到几分钟就结束，失败了重跑代价可接受；而几小时的巨型 ETL 才真正需要强容错，那是 Spark 的场景。不过 Trino 近年也引入了「容错执行」模式（FTE），在需要时可开启。

Q：Trino 查询老是 OOM 怎么办？
A：常见原因与对策：① 大表 JOIN 用了 broadcast——小表其实不小，广播到所有 Worker 撑爆内存；改用 distributed join 或确保统计信息准确让优化器正确判断。② 单查询数据量太大——加更严格的分区过滤，或拆分成多次查询。③ 并发过高——限制并发查询数。④ 内存配置不足——调大 query.max-memory，或启用 spill to disk（溢出到磁盘，会降速但能避免直接失败）。

Q：能直接查 MySQL 吗？会影响线上库吗？
A：能，通过 MySQL Connector。但必须谨慎：即席查询很容易产生大范围扫描，直接把线上库拖垮。安全做法：① 只连从库；② 限制查询的并发与时间；③ 确保谓词下推生效（避免全表拉取到 Trino 再过滤）；④ 对核心业务库设置只读账号和查询限流。生产上更推荐先把数据同步到数仓再查询，Trino 直连线上库仅用于轻量探查。

典型的内存三连错：Query exceeded per-node memory limit（调大 per-node 或 spill）、Query exceeded local memory limit（倾斜）、Query killed because the cluster is overloaded（并发过高）。

Hive / MapReduce离线批处理分钟~小时历史遗留、超大吞吐

Trino 的核心价值：不移动数据就能跨源查询（联邦查询），并且是纯内存流水线执行，没有 MapReduce 的落盘与容错开销——代价是单个查询失败需要整体重试。

常用命令与诊断

诊断

# 启动 CLI
trino --server http://coordinator:8080 --catalog hive --schema default

-- 看执行计划（含每个算子的估算行数与代价）
EXPLAIN SELECT ...;
EXPLAIN (TYPE DISTRIBUTED) SELECT ...;      -- 看分片与 exchange

-- 看正在跑的查询（最重要的一张系统表）
SELECT query_id, state, user, elapsed_time_ms,
       peak_user_memory_bytes / 1024 / 1024 AS peak_mem_mb
  FROM system.runtime.queries
 WHERE state = 'RUNNING'
 ORDER BY elapsed_time_ms DESC;

-- 杀掉问题查询
CALL system.runtime.kill_query('20260311_101500_00001_abcde');

优化

-- 找大表扫描与分区裁剪是否生效
EXPLAIN SELECT count(*) FROM events WHERE dt = DATE '2026-03-11';
--   看 TableScan 的 partitions / 估算行数；若扫了全表说明分区裁剪失败

-- 倾斜检测：看各 worker 处理的数据量差异
SELECT node_id, sum(processed_rows) AS rows
  FROM system.runtime.tasks WHERE query_id = '<qid>'
 GROUP BY node_id ORDER BY rows DESC;

-- 小文件问题诊断（Hive 端）
--   文件数 >> split 数会拖慢调度；目标文件大小通常 >= 128 MB

深入自检

Trino 和 Spark SQL 该怎么选？

看场景：交互式即席查询、跨源联邦查询、要求秒到分钟级响应时选 Trino；大规模 ETL、需要细粒度容错（stage 级重试）、重计算任务选 Spark。Trino 是纯内存流水线，没有中间落盘与容错，单查询失败要整体重跑，这也是它不适合超长任务的原因。

内存报错时该调哪个参数？

先看报错类型：per-node memory limit 调 query.max-memory-per-node 或开启 spill；local memory limit 多半是倾斜，要改查询（加盐、两阶段聚合）而不是加内存；cluster overloaded 是并发过高，用资源组限流而不是调内存。

为什么分区裁剪没生效？

常见三个原因：① 过滤条件没直接用分区列（用了函数或表达式，导致无法下推）；② 分区列类型不匹配（字符串 vs 日期，发生隐式转换）；③ 元数据未刷新（新分区未同步）。用 EXPLAIN 看 TableScan 的分区数与估算行数即可确认。

小文件为什么拖慢查询？

因为每个文件至少产生一个 split，文件过多会让 split 数远超并行度，调度与打开文件的开销占比急剧上升，同时元数据（如 Hive metastore）压力也变大。治理办法是写入侧合并（目标文件大小 ≥ 128 MB）或定期做 compaction。

跨源联邦查询的性能瓶颈在哪？

瓶颈在远端数据源的读取：Trino 只能把过滤与列裁剪下推到数据源，若数据源不支持（如某些 NoSQL 或 REST 接口），就会被全量拉取到 Trino 侧再过滤。优化手段是确保下推生效（用 EXPLAIN 检查）、只取需要的列、必要时把热数据物化到本地列存。
