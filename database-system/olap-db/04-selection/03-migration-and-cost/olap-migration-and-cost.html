01四条最常见的迁移来源

从哪来迁移动机主要难点
MySQL / PostgreSQL分析查询拖垮线上库 schema 需要重新建模；增量同步的延迟与一致性
Elasticsearch聚合能力弱、存储成本高查询语义不同（DSL → SQL）；嵌套结构扁平化
Hive / Spark 离线查询太慢，想要交互式分区与文件格式要重做；UDF 需要替换
自建 ClickHouse / Doris换引擎或上云托管SQL 方言差异；物化视图与索引要重建
先想清楚"为什么迁"：如果是为了降本，重点在存储与压缩；如果是为了提速，重点在数据模型与索引；如果是为了实时，重点在导入链路。三个目标的最优解不同。

02迁移路径：双写、灰度与回滚

① 全量回溯 + 增量追平。先把历史数据灌进去，再启动增量同步追平，最后在一个时间点切流。
② 双写双跑。新旧两套同时写入，查询也同时发两边，比对结果。这是唯一能在切换前发现语义差异的方法。
③ 灰度切读。先切 1% 的只读流量，观察延迟与错误率，逐步放大。永远保留快速切回的能力。
④ 观察一个完整周期。至少覆盖一次月结/大促/周报高峰，因为长尾问题常在负载峰值才暴露。
⑤ 下线旧链路。确认无流量后再停双写，避免"旧库还在写但没人知道"。
不要做"一次性大切换"。分析系统的错误往往不报错、只是结果不对，等到业务发现时已经影响决策很久了。双跑比对是必须的，不是可选的。

03数据模型改造：迁移中最容易低估的部分

从行存/文档型迁到列存分析引擎，最痛苦的不是搬数据，而是重新建模。三处最常出问题：

问题为什么怎么做
宽表 vs 星型行存里习惯范式化，分析引擎偏好宽表或星型按查询频率决定冗余程度，高频维度下沉到事实表
分区键选择选错会导致全表扫描或分区数爆炸按最常用的时间过滤字段分区，按高频 JOIN/过滤字段分桶
高基数字段用户 ID 这类字段做维度会导致聚合极慢考虑预聚合，或用近似去重（HLL）替代精确 COUNT DISTINCT
不要把 OLTP 的表结构原样搬过来。原样迁移是最省事的做法，也几乎必然导致性能不达标。建模改造才是迁移收益的主要来源。

04怎么验证迁移后结果一致

① 行数与汇总值比对。先比对总量、求和、去重计数，这一步能抓住 80% 的导入问题。
② 分维度下钻比对。按日期、按主要维度分组比对，暴露分区与编码问题。
③ 抽样明细比对。随机抽若干主键，逐字段比对，暴露类型转换与时区问题。
④ 慢查询比对。把旧系统的 Top 慢查询拿过来跑，确认延迟真的改善了。
特别关注四类差异：时区（UTC vs 本地）、浮点精度、NULL 与空串、去重语义。这四项不报错，但会让数字悄悄对不上。

05成本怎么估：存储、计算与人力

成本项怎么估容易漏掉的
存储原始量 × 压缩比（列存常见 3–10 倍，视数据与编码而定）副本倍数、索引与物化视图的额外占用、临时空间
计算按峰值并发 × 单查询资源占用估算导入与 compaction 也吃资源，常与查询争抢
数据同步全量回溯 + 常驻增量链路的资源同步任务的失败重试与监控成本
人力建模改造 + 查询改写 + 双跑验证这一项常被完全忽略，实际往往超过硬件成本
压缩比的具体倍数取决于数据特征与编码方式，差异很大——请用你自己的数据实际导入一次来测，不要按经验值做预算。
Q：迁移一定能降本吗？
A：不一定。如果查询形态没变、建模没改，只是换个引擎，降本幅度通常有限。真正的降本来自：压缩更优、预聚合减少扫描、冷热分层、以及下线旧系统。

06上线前风险清单

Q：最该担心什么？
A：结果不一致但不报错。这是分析系统独有的风险，必须靠双跑比对来防。
Q：实时导入需要特别准备什么？
A：导入的幂等与乱序处理。上游重发、延迟到达都会造成重复或丢数，需要主键去重与时间窗口兜底。
Q：权限怎么做？
A：迁移期两套系统并存，权限容易漏配。提前梳理角色与行级/列级权限需求，不要上线后补。
Q：要不要保留旧系统？
A：至少保留一个可回滚窗口（通常 2–4 周）。分析系统的正确性验证需要时间，过早下线会失去退路。
Q：什么时候该放弃迁移？
A：如果查询形态高度固定且量小，现有系统已经够用，迁移的收益可能覆盖不了建模改造与双跑验证的成本。不是所有分析场景都需要列存引擎。
一句话收尾：迁移的成败不在引擎选型，在建模改造与结果验证。这两项做扎实，换哪个引擎都不会太差。
