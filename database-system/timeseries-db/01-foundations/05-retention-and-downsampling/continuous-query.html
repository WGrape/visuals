时序数据连续查询（CQ）：把降采样结果自动"存档"

连续查询周期性自动跑聚合，把原始样本物化成更粗粒度的新时间线。它和"查询时降采样"互补：一个省算力但占存储，一个灵活但每次重算。

核心机制

连续查询（Continuous Query, CQ）是数据库按调度周期执行的预聚合任务：对原始时间线按 GROUP BY time(1h) 聚合 → 写入一条新的、更粗粒度的时间线（例如 cpu_1h）。

和一次性查询不同，CQ 持续运行、只处理新到达的数据、结果自动落库。它把"每次看板查询都重算"变成"后台提前算好"，代价是额外占一点存储空间。

连续查询 vs 查询时降采样

维度连续查询 CQ查询时降采样
触发方式自动周期执行每次查询临时算
存储额外占空间（物化结果）不占额外空间
算力平摊到后台查询时集中消耗
古老数据已物化，查得快原始过期则无法算
适用长期看板 / 告警临时探索分析

InfluxDB 示例

CREATE CONTINUOUS QUERY "cq_cpu_1h" ON "metrics"
BEGIN
  SELECT mean("usage") INTO "cpu_1h"
  FROM "cpu" GROUP BY time(1h), *
END

结果写入 cpu_1h，原 cpu 短期保留后过期，长期趋势仍留在 cpu_1h。看板直接查 cpu_1h，又快又省。

Prometheus 的等价物：Recording Rule

Prometheus 没有"CQ"这个名词，但有功能等价的 Recording Rule：周期性预计算并存储结果序列。

groups:
- name: cpu_rules
  rules:
  - record: job:cpu:rate5m
    expr: rate(node_cpu_seconds_total[5m])

它比 CQ 更轻量（贴近 TSDB 内部），服务于 Grafana 面板和告警，避免每次打开看板都重算 rate。

"太晚降采样"问题

若只保留 7 天原始点，到第 8 天想看"上月每小时均值"——原始已删、没有 CQ 物化过，历史趋势永久丢失。

必须提前用 CQ 把长期聚合物化下来，并且保证在原始点过期前 CQ 已经完成写入。CQ 只处理执行之后到达的新数据，不回填历史；历史补算要靠 backfill 脚本（批量重放原始数据或重算）。

类比：CQ 像"每天自动把当天的照片洗出来归档"，而查询时降采样像"现场拿底片现冲"。等你想起要归档旧照片，底片已经丢了——所以归档必须提前、持续地做。

现象原因处理

为什么 CQ 结果和临时聚合可能不一致？

CQ 在写入时按事件时间窗聚合，迟到/补传数据若晚于窗口已固化则不会被计入；临时查询若重扫原始样本则可包含这些点。要保证一致，需定义可重算窗口与补写流程。

连续查询与降采样：预聚合的设计要点

降采样（downsampling）是时序库控成本的核心手段：用低精度的大粒度数据换长期存储。连续查询（CQ）就是让这件事自动跑起来。

概念含义典型配置
降采样把高频原始数据聚合成低频汇总（如 1s → 1m → 1h）保留：原始数据 7 天 / 1m 汇总 90 天 / 1h 汇总 1 年
连续查询 CQ数据库内部定时自动执行的聚合查询每 1m 跑一次，把上一分钟聚合写入新表
保留策略 RP数据过期自动删除RETENTION POLICY 90d
降采样比例存储节省倍数1s→1m 约省 60 倍（只存聚合值）
系统机制写法要点
InfluxDB 1.xCREATE CONTINUOUS QUERY + RP原生支持，最成熟
InfluxDB 2.x / 3.xTask（Flux / SQL 定时）用 option task 定义

配置示例

-- InfluxDB 1.x 连续查询 + 保留策略
CREATE RETENTION POLICY "rp_90d" ON "mydb" DURATION 90d REPLICATION 1 DEFAULT;

CREATE CONTINUOUS QUERY "cq_1m" ON "mydb" BEGIN
  SELECT mean(value) AS value INTO "rp_90d"."cpu_1m"
  FROM "rp_7d"."cpu" GROUP BY time(1m), host
END;
--   INTO 指定写入目标（measurement）
--   GROUP BY time(1m) 定义聚合窗口
--   保留 tag（host）才能在降采样后仍可分组查询

-- 查看
SHOW CONTINUOUS QUERIES;
DROP CONTINUOUS QUERY "cq_1m" ON "mydb";

-- ---------- TimescaleDB 连续聚合 ----------
CREATE MATERIALIZED VIEW cpu_1m
WITH (timescaledb.continuous) AS
SELECT time_bucket('1 minute', ts) AS bucket,
       host, avg(value) AS value
FROM cpu GROUP BY bucket, host;

-- 设置自动刷新策略（关键，否则不会自动更新）
SELECT add_continuous_aggregate_policy('cpu_1m',
    start_offset => INTERVAL '3 hours',   -- 只刷新最近 3 小时（容忍迟到数据）
    end_offset   => INTERVAL '1 minute',
    schedule_interval => INTERVAL '1 minute');

-- 设置保留：原始数据只留 7 天
SELECT add_retention_policy('cpu', INTERVAL '7 days');
-- 注意：有了 CAGG 之后删原始数据，聚合结果仍在（TimescaleDB 的特性）
  • 降采样必须保留 tag（维度）：只聚合 value 而丢掉 host/region 等 tag，之后就无法按维度下钻查询了。GROUP BY time(1m), host 里的 host 不能少。
  • 聚合函数要选对：mean 会平滑掉峰值，监控告警场景通常还要额外存 max、min、count。如果只存 mean，尖峰就被永久抹掉了。
  • 处理迟到数据：网络抖动、客户端缓冲会让数据晚到。CQ 窗口要有 延迟容忍（如 TimescaleDB 的 start_offset 设 3 小时），否则迟到数据会被漏掉。
  • 降采样不可逆：原始数据删了就回不来了。保留策略要先确认业务能接受粒度损失。
  • 别过度降采样：1s→1m 省 60 倍很爽，但如果你的排障需要看秒级细节，原始数据至少要保留几天。
  • 计数类指标要用 sum 而不是 mean：QPS、错误数这类是累计量，降采样时 sum 或 rate 才对，用 mean 会得到完全错误的结果。
降采样后查出来的值和原始数据对不上，为什么？

四个常见原因：① 聚合函数选错——最典型的是把 counter（累计计数器）当成 gauge 处理。QPS 这类指标要先算 rate（每秒速率）再聚合，直接对原始累计值取 mean 毫无意义；② 窗口边界不一致——CQ 的 time(1m) 窗口和你手动查询的窗口起点不同，聚合结果自然不同；③ 迟到数据被漏掉——CQ 已经跑过的窗口不会重算，晚到的数据丢了；④ 部分窗口数据不全——比如刚启动、或采集中断，那一分钟只有 10 个点的 mean 和 60 个点的 mean 当然不同。排查顺序：先确认指标类型（counter/gauge），再确认窗口对齐，最后看迟到数据策略。

该保留原始数据多久？

按用途分档：① 排障需要的高精度数据：3~7 天——绝大多数线上问题是「最近发生了什么」，秒级/分钟级细节足够，超过一周的细节很少被翻出来；② 趋势分析/容量规划：3~12 个月，用 1h 或 1d 粒度；③ 合规/审计：1~3 年，通常是日级或月级汇总。成本对比很悬殊：假设 10 万时间序列、1 秒采样，原始数据约 每天几十 GB，而 1 小时粒度的汇总只有几十 MB，差 1000 倍。所以标准做法是「短期精度换长期跨度」：7 天原始 + 90 天 1m + 1 年 1h。具体数字按你的预算和排障需求调。

连续查询和物化视图是一回事吗？

思想相同（预计算、空间换时间），但实现和保障不同。数据库的物化视图通常有强一致性保证——查询时能自动合并「已物化部分 + 新增的增量」，结果和直接查基表一致（TimescaleDB 的 Continuous Aggregate 在实时模式下就是这样）。而时序库的 连续查询更像是定时 ETL——它按固定窗口把结果写进另一张表，查询时要你自己决定查哪张表，且通常是最终一致（有延迟）。选择上：如果你希望「查询时不用关心有没有降采样」，选物化视图类方案；如果你希望「简单、可控、能跨不同保留策略存储」，选 CQ。另外 CQ 写出的结果和普通数据一样可被再次聚合（多级降采样），这是它的灵活性优势。

它解决的是「原始数据太贵」

监控系统每秒采一次指标，一台机器一天就是八万多个点。要把它原样保存一年？存储成本与查询代价都会失控。可如果只保留七天，又没法回答「三个月前那次故障的曲线长什么样」。

连续查询（Continuous Query, CQ）就是解决这个矛盾的：提前注册一条聚合规则，系统周期性地自动执行，把高频原始数据聚合成低频的汇总，写进另一张表长期保存。

分层降采样：每一层由一条连续查询生成

它和物化视图、定时任务是什么关系

机制触发方式是否增量适合
普通查询用户发起时执行否即席分析
物化视图通常在写入时或事务提交时刷新可增量需要强一致的汇总
连续查询按固定时间周期自动执行是（只处理新到达的窗口）时序数据的滚动聚合
外部定时任务由调度系统触发自己实现已有调度体系、逻辑复杂时

一句话区分：连续查询是时序数据库内建的、周期性增量的降采样机制。它比外部脚本更省心（由数据库负责调度、重试与写入），代价是表达能力有限。

写法长什么样

-- 典型语法（类 InfluxQL 风格，具体以所用产品为准） CREATE CONTINUOUS QUERY cq_cpu_1m ON monitor BEGIN SELECT mean(usage), max(usage), min(usage) INTO monitor_rp_90d.cpu_1m -- 结果写入哪个保留策略下的表 FROM monitor_rp_7d.cpu -- 从原始表读 GROUP BY time(1m), host -- 按 1 分钟窗口 + 按 host 分组 END -- 再叠一层 CREATE CONTINUOUS QUERY cq_cpu_1h ON monitor BEGIN SELECT mean(mean), max(max), min(min) INTO monitor_rp_1y.cpu_1h FROM monitor_rp_90d.cpu_1m GROUP BY time(1h), host END 注意第二层：字段名已经是第一层聚合后的结果， 所以这里写的是 mean(mean) —— 对均值再取均值。

三个必须注意的细节：

  1. CQ 一般只处理「新到达」的数据，不会回头补算历史。注册 CQ 之前的历史数据需要手动回填（backfill），否则历史曲线会有断层。
  2. 时间窗口要对⻬。窗口边界不一致会让「分钟表」与「小时表」对不上，排查时非常难发现。
  3. 要跟保留策略配合。CQ 生成的新表要放在一个保留期更长的策略下，否则降采样完又被很快删掉，等于白做。

常见坑与工程建议

坑表现对策
CQ 静默失败汇总表长时间不更新，却没人发现监控汇总表的最新数据时间，落后太久就告警
窗口对不齐上下两层聚合结果对不上统一窗口与边界规则，跨层用同一套对齐方式
回填缺失CQ 创建前那段历史没有汇总数据用一次性查询补算历史并把结果写入目标表
聚合函数选错用均值掩盖了尖刺（如瞬时冲高）同时存 mean / max / p95 等多个维度
标签基数爆炸按过多维度分组导致序列数量暴涨只保留必要的分组维度，控制基数
写放大CQ 本身也要写入，占用 IO错开执行时间、控制 CQ 数量与频率

一条很实用的经验：聚合时不要只存均值。监控与容量分析最关心的往往是峰值与分位数，而均值会把这些尖刺完全抹平。常见做法是同时保存 mean、max、min、count、p95 —— 多存几个字段的成本，远低于事后发现「当时明明冲高了但图上什么都没有」。

深入自检

降采样会丢失信息，这能接受吗？

要分用途。看长期趋势时，分钟级甚至小时级聚合完全够用；做故障复盘时，往往需要秒级原始精度。所以正确的做法不是「二选一」，而是分层保留：高精度留短时间、低精度留长时间，并且确保关键指标的高精度数据保留期覆盖你的复盘周期。

为什么不干脆把原始数据全留着？

成本是三重的：存储成本、写入成本、以及查询成本 —— 扫一年每秒一个点的曲线，即使有索引也要处理几千万个数据点，交互体验会很差。降采样把「常用查询」的代价降低了几个数量级，这是它不可替代的价值。

CQ 和流处理引擎（如 Flink）怎么选？

看需求复杂度。CQ 是数据库内建的轻量方案，适合标准的滚动窗口聚合，运维成本极低；流处理引擎能做窗口、关联、乱序处理与复杂事件逻辑，但要自己维护一套集群。能用 CQ 解决的就不要上流处理，这是很实在的成本判断。

保留策略（Retention Policy）怎么定？

从业务问题倒推：问自己「我最长需要回溯多久的什么精度的曲线」。常见组合：原始精度 7~30 天（覆盖故障复盘）、分钟级 3~6 个月（覆盖容量与趋势分析）、小时级 1~3 年（覆盖同比与年报）。同时要估算每一层的实际占用，避免「策略定了但磁盘先满了」。
