DNS 走 UDP、TCP、DoT 还是 DoH：查询为什么会换通道

从普通解析、应答截断到加密解析，区分传输可靠性、隐私和 DNSSEC。

DNS 查询不只走 UDP 53

传统 DNS 查询常使用 UDP 53，数据报开销小、一次请求通常可一次应答；DNS 也使用 TCP 53，特别是在应答需要更可靠传输、区域传送或 UDP 应答截断后的重试中。不能把“DNS=UDP”当成绝对规则。现代解析还可能通过 TLS 上的 DoT 或 HTTPS 上的 DoH 与递归解析器通信，它们改变的是客户端到解析器这一段的传输保护方式，不改变 A、AAAA、MX 等记录的基本语义。

解析链仍有多个参与者：应用或操作系统、递归解析器、权威服务器。客户端启用 DoH 后，浏览器到 DoH 解析器的查询被 HTTPS 保护，但递归解析器仍能看到用户查询，解析器到权威的上游路径也取决于其实现。加密某一跳不等于“全世界都看不到访问的域名”。

UDP 应答变大时

一个 DNS 应答若包含大量记录或 DNSSEC 相关数据，可能超过客户端和路径可接受的 UDP 大小。解析器可在响应中设置 TC 截断标志，客户端据此改用 TCP 重试。EDNS(0) 允许协商更大的 UDP 载荷，但包越大，越可能遇到 IP 分片、路径 MTU 或中间设备丢弃；不能把 UDP 缓冲数字无限调大来避免 TCP。

若网络只放行 UDP 53 而封锁 TCP 53，普通小查询正常，大应答却可能失败。排查“某些域名可解析、某些不行”时要看响应大小、TC 标志和 TCP 回退是否成功。权威服务器和递归解析器都应支持符合业务需要的 UDP 与 TCP 通路。

DoT 与 DoH 的差别

DoT 通常在专用端口上把 DNS 消息放进 TLS 连接；DoH 把 DNS 查询放进 HTTPS 请求中，通常复用 HTTPS 传输生态。两者都可保护客户端到递归解析器的查询内容免受路径旁观者直接读取和篡改，前提是客户端正确验证解析器身份。DoH 与普通网页同走 HTTPS 可能便于穿越某些网络，也会让企业原有 DNS 观测与策略难以按端口识别。

是否选择 DoH/DoT 是网络管理和隐私的取舍。企业内部分区域可能只有指定内部解析器知道，浏览器私自改用外部 DoH 后可能解析不到内部域名。故障时要查应用实际使用的解析器与传输，而不是只运行系统 `dig` 就认定浏览器也走同一路。

DNSSEC 解决的是另一问题

DNSSEC 通过签名链让验证解析器检查 DNS 数据是否来自可信委派且未被篡改，它不加密查询名称。DoH/DoT 加密到递归解析器的通道，却不自动证明递归解析器返回的权威数据具备 DNSSEC 验证。可以同时使用二者，也可以只使用其中一者；不能把 DNSSEC 误叫成“DNS over HTTPS 的证书”。

DNSSEC 配置错误可能导致验证解析器返回 SERVFAIL，而未验证的路径看似正常。诊断要比较支持验证与不验证的解析器、DS/DNSKEY 链和权威响应，不能仅把 SERVFAIL 当作“域名不存在”。

一次问题时间线

用户访问某带 DNSSEC 大应答的域名：客户端先发 UDP 查询；递归回复带 TC 标志；客户端转 TCP 53，却被办公室出口防火墙拦截，于是域名访问失败。另一个客户端通过 DoH 向外部解析器查询可成功，表面上像“换浏览器就好了”。真正根因是内部 DNS 的 TCP 回退被挡，而不是该网站 HTTP 服务坏了。

若通过 DoH 成功但内部域名失败，则可能是解析器分流问题。两个现象方向相反，必须先查实际解析器和查询通道。排障抓包还要注意 DoH 内容经 TLS 加密，普通网络抓包只看得到 HTTPS 连接，需用浏览器或解析器日志观察查询结果。

设计与验收

为普通小记录、大 TXT/DNSSEC 记录、内部域名和不存在域名各准备样例，分别测 UDP、TCP 与加密解析路径。记录响应码、TC 标志、时延、最终地址和所用递归解析器。防火墙规则应允许必要的 DNS TCP 回退；加密解析策略要明确内部域名如何路由、谁维护解析器证书、日志如何保护隐私。

性能比较应区分冷连接和连接复用：DoH 首次连接要建 TLS，后续可复用；UDP 查询也可能命中本地缓存。只用一次冷启动延迟宣布某协议永远更快，会忽略缓存和并发。

自检

DoH 打开后，DNSSEC 就自动完成验证了吗？

不会。DoH 保护到递归解析器的传输；DNSSEC 是另一个机制，用签名链验证 DNS 数据。
