函数声明

参数可合并类型，返回值可命名

相邻同类型参数可省略重复类型；返回值可命名，命名返回在 defer 中可被修改。

func add(a, b int) int { return a + b }

// 命名返回值
func divmod(a, b int) (q, r int) {
    q = a / b
    r = a % b
    return   // 裸 return，返回 q, r
}
多返回值与 error

Go 的错误契约

函数要报告失败，就返回 (结果, error)；调用方必须检查 err。这是 Go 最鲜明的风格。

func find(id int) (*User, error) {
    if id <= 0 {
        return nil, errors.New("bad id")
    }
    return &User{ID: id}, nil
}

u, err := find(1)
if err != nil {
    return err   // 立刻处理错误
}
可变参数

...T 把实参收成切片

可变参数必须放最后；可传多个值，也可直接传一个同类型切片（加 ... 展开）。

func sum(nums ...int) int {
    s := 0
    for _, n := range nums { s += n }
    return s
}

sum(1, 2, 3)
slice := []int{1, 2, 3}
sum(slice...)   // 展开传入
递归

注意终止与栈深度

递归写法和其它语言一致；但要注意 Go 没有尾递归优化，深递归可能栈溢出，必要时改迭代或用显式栈。

func fact(n int) int {
    if n <= 1 { return 1 }   // 终止条件
    return n * fact(n-1)
}
函数类型

把函数当值传递

函数签名可定义成类型，从而作为变量、参数、返回值，实现回调与策略模式。

type Op func(int, int) int
func apply(a, b int, f Op) int { return f(a, b) }
apply(3, 4, func(x, y int) int { return x + y })

Go 函数的独特之处

Go 的函数语法看起来普通，但有几个设计直接影响写法：多返回值、只有值传递、defer、错误即值。

多返回值天然返回「结果 + 错误」，不用异常或输出参数。
全是值传递传指针才能改外部；但引用类型共享底层数据。
defer后进先出，参数在声明时求值。
错误是值用返回值表达失败，调用方显式处理。
// ① 多返回值 func div(a, b int) (int, error) { if b == 0 { return 0, errors.New("divide by zero") } return a / b, nil } // ② 命名返回值（配合裸 return，函数体长时慎用） func parse(s string) (n int, err error) { n, err = strconv.Atoi(s) if err != nil { return // 裸返回，返回 n 与 err } return } // ③ 变参 func sum(nums ...int) int { t := 0 for _, n := range nums { t += n } return t } sum(1, 2, 3) sum(slice...) // 展开切片传入 // ④ 函数作为值与类型 type Handler func(int) int var f Handler = func(x int) int { return x * 2 }

参数传递：值传递到底意味着什么

Go 里所有参数都是值传递——传进去的是副本。但「副本」的内容可能包含指针，于是产生了容易混淆的现象。

类型传参时函数内能改什么
int / struct拷贝整个值只能改副本，不影响外部
指针 *T拷贝指针值（地址）能改指针指向的对象
slice拷贝头部（指针+长度+容量）能改元素；改长度需返回新 slice
map / chan拷贝头部（含指针）能改内容；重新 make 不影响外部
数组 [N]T拷贝整个数组开销大，通常用切片或指针
// 想在函数里修改外部变量 → 传指针 func inc(n *int) { *n++ } x := 1 inc(&x) // x == 2 // slice 的坑：append 可能指向新数组 func add(s []int, v int) []int { return append(s, v) // 必须返回 } s = add(s, 4) // 只改元素不需要返回 func set(s []int, i, v int) { s[i] = v }

defer、panic 与 recover

defer 的三条规则

  • 多个 defer 后进先出
  • 参数在 defer 声明时求值
  • defer 在 return 之后、函数真正返回前执行
func f() (r int) { defer func() { r++ }() // 能修改命名返回值 return 1 // 实际返回 2 } // 参数在声明时求值 i := 0 defer fmt.Println(i) // 打印 0，不是后来的值 i++

panic 与 recover

panic 用于「程序无法继续」的情况，不是普通错误处理。

func safeRun() { defer func() { if r := recover(); r != nil { log.Printf("recovered: %v", r) } }() risky() } // 要点： // recover 必须在 defer 里直接调用才有效 // 恢复后从 panic 点之后继续执行是不可能的，只能从函数返回 // 每个 goroutine 要各自 recover，主 goroutine 无法救子 goroutine

错误处理惯例

  • 错误作为最后一个返回值
  • 用 fmt.Errorf 的 %w 包装保留上下文
  • 用 errors.Is / errors.As 判断类型
  • 预定义哨兵错误：var ErrNotFound = errors.New(...)
  • 不要忽略错误，忽略要写注释说明
var ErrNotFound = errors.New("not found") func find(id int) (*User, error) { u, err := db.Get(id) if err != nil { return nil, fmt.Errorf("find user %d: %w", id, err) } return u, nil } if errors.Is(err, ErrNotFound) { ... }

深入自检

Go 为什么没有异常机制？

设计取舍：Go 认为错误是预期内的值，应当显式处理，让失败路径在代码里可见。异常会让控制流跳跃、调用方容易忽略。代价是错误处理写起来啰嗦——这也是 Go 后来一直在优化的方面。

命名返回值该用吗？

短函数里能提升可读性（尤其配合文档说明含义）；长函数里的裸 return 会降低可读性，容易看不出返回了什么。一般建议：短函数可用，长函数显式 return。

defer 有什么性能代价？

现代 Go 中 defer 使用开放编码（open-coded defer），开销已经很小（几十纳秒级别）。但在极热的循环里，仍然建议把 defer 提到循环外或改用显式调用。

panic 应该用在什么地方？

用在「程序真的无法继续」的情况：初始化失败、不可能到达的分支、严重的内部不一致。可预期的业务失败（参数错、资源不存在）应当返回 error。库代码尤其不要向外 panic。

为什么 recover 救不了子 goroutine？

panic 只会沿着当前 goroutine 的调用栈展开，recover 也只能在该 goroutine 的 defer 中生效。子 goroutine 里未恢复的 panic 会导致整个进程崩溃，因此每个 goroutine 入口都应有自己的 recover 兜底。
