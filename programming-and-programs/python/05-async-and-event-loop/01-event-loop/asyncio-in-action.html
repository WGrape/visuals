Python asyncio 实战：并发 / 队列 / 锁 / 超时

run、Queue、Lock、Semaphore、wait_for 与 run_in_executor 骨架

asyncio协程并发Python
运行 队列 锁 超时 线程 坑
asyncio 的核心是事件循环：协程遇到 await 把控制权交还循环，等 IO 完成再恢复。下面给可直接跑的并发骨架。

1运行与并发多个协程

import asyncio

async def fetch(i):
    await asyncio.sleep(0.1)   # 模拟 IO
    return "task-" + str(i)

async def main():
    results = await asyncio.gather(fetch(1), fetch(2), fetch(3))
    print(results)

asyncio.run(main())
要点：不要自己写事件循环；99% 场景用 asyncio.run() 就够了。

2队列 + 工作者

async def worker(q, wid):
    while True:
        item = await q.get()
        try:
            await do_work(item)
        finally:
            q.task_done()

async def main():
    q = asyncio.Queue(maxsize=100)
    for w in range(5):
        asyncio.create_task(worker(q, w))
    for i in range(50):
        await q.put(i)
    await q.join()  # 等所有任务处理完

3锁与信号量

lock = asyncio.Lock()
sem = asyncio.Semaphore(10)  # 最多 10 个并发

async def safe_inc():
    async with lock:
        shared += 1

async def limited(i):
    async with sem:
        await do_io(i)
要点：这里的 Lock 是『单线程事件循环内』的协程锁，不是跨线程锁；跨线程请用 threading.Lock。

4超时与取消

try:
    await asyncio.wait_for(fetch(1), timeout=2.0)
except asyncio.TimeoutError:
    print("超时")

task = asyncio.create_task(fetch(99))
await asyncio.sleep(0.05)
task.cancel()                  # 请求取消
try:
    await task
except asyncio.CancelledError:
    print("已取消")

5把阻塞调用丢到线程

loop = asyncio.get_running_loop()
# CPU/阻塞型调用放到线程池，别阻塞事件循环
res = await loop.run_in_executor(None, blocking_io, arg)
  • 事件循环是单线程；任何『真阻塞』（文件 IO、CPU 密集）都会卡住所有协程。
  • 用 run_in_executor 或 asyncio.to_thread（3.9+）隔离阻塞。

6常见坑

  • 忘了 await：协程对象不执行，常见静默 bug。
  • 在协程里调用阻塞库（requests、time.sleep）→ 用 aiohttp / asyncio.sleep 替代。
  • 混用同步与异步：同一函数栈里要么全 async，要么明确切线程。

第一层 · 概念与判定：asyncio 适合什么

asyncio 是单线程事件循环 + 协程，专为IO 密集型、高并发连接设计（网络/磁盘异步）。CPU 密集任务用它反而慢——它不绕开 GIL。

场景用 asyncio别用
万级并发 HTTP 调用✓多线程开不起
爬虫/网关/WS 推送✓—
本地重计算✗（用多进程）GIL 占满
调用阻塞 SDK需 run_in_executor直接 await 卡循环

第二层 · 参数·命令·量化：核心 API 与超时

API用途注意
asyncio.run(main)入口启动循环一次性
await coro挂起等结果忘了 await 不执行
asyncio.gather(*ts)并发多任务异常需处理
wait_for(coro, 5)超时包裹避免永久挂起

asyncio 并发与超时示例

import asyncio, time

async def fetch(i):
    await asyncio.sleep(0.1)          # 模拟 IO 等待
    return i

async def main():
    # 并发 100 个，总耗时约 0.1s 而非 10s
    res = await asyncio.gather(*[fetch(i) for i in range(100)])
    # 超时保护：超 5s 抛 TimeoutError
    try:
        await asyncio.wait_for(fetch(999), timeout=5)
    except asyncio.TimeoutError:
        ...

# 阻塞函数丢到线程池，别直接 await
await asyncio.get_running_loop().run_in_executor(None, blocking_io)

asyncio.run(main())

数量级：单事件循环可承载数万并发协程；并发 100 个 0.1s 的 IO 任务总耗时约 0.1s（串行则要 10s），提速近 100×。

第三层 · 排障与边界：五个坑

  • 阻塞事件循环：在 async 函数里写了 time.sleep 或重同步 IO，整个循环卡死，所有协程等它——用 await asyncio.sleep 或 run_in_executor
  • 忘记 await：写成 do() 而非 await do()，协程对象不执行，静默无结果
  • 混用同步库：import 一个阻塞 SDK 直接调，等于卡循环——必须包进 executor 或换异步版
  • loop 已关还提交：asyncio.run 退出后循环关闭，再 schedule 任务直接报错
  • cancel 不处理 CancelledError：超时取消后没捕获，堆栈噪声且资源可能没清理

第四层 · 原理与取舍

asyncio 和多线程到底差在哪，为什么 IO 密集更合适？

多线程靠内核调度、每个线程独立栈，开几千就内存/切换爆炸；asyncio 在单线程里用事件循环手动切换协程，切换零内核开销、内存极小，且没有锁竞争（单线程）。代价是任一协程写同步重活就卡全循环。IO 密集时大部分时间在等，切换极廉价，所以碾压多线程。

为什么 asyncio 救不了 CPU 密集任务？

因为 Python 有GIL，同一时刻只有一个线程在跑字节码。asyncio 仍是单线程，CPU 密集计算照样占满 GIL，协程再怎么切也抢不到并行。CPU 密集要绕开 GIL：用 multiprocessing 多进程，或把热点丢 C 扩展/Numba。asyncio 的舞台就是「等 IO」，不是「算」。

gather 和 wait 有什么区别，异常怎么处理？

gather 一次性等所有任务，任一抛异常整体即报错（可用 return_exceptions=True 改收异常对象）；wait 更灵活，能设 FIRST_COMPLETED/timeout 提前返回。生产中建议 gather(return_exceptions=True) 或给每个任务单独 try，避免一个失败把整批拖垮、且错误被吞。
