🔌 模型 API 调用集成流程

以“把故障记录总结给值班同事”为例，走完一次调用的准备、发送、验收与失败处理

1. 准备输入与调用边界

先规定任务：“把一条故障记录总结成现象、影响、措施、待确认四项”。调用方只传本次记录，检查是否含不应发送的敏感字段，并给请求分配内部追踪 ID。密钥从服务端配置或密钥管理服务读取，不能由浏览器提交或写进日志。

同时确定总超时、输出长度上限、并发上限和每次调用的费用预算。采样参数属于模型行为配置；各厂商字段名与默认值不同，应由适配层转换，而不是在业务代码里到处拼请求体。

2. 发送并接收

业务层把任务说明和故障记录交给厂商适配层；适配层负责认证、消息格式、输出上限字段与响应解析。下面是流程伪代码，不是某家厂商的真实 SDK 接口：

trace_id = new_trace_id()
input = redact_and_limit(record)
request = adapter.build(task="故障交接摘要", input=input, output_limit=300)
response = adapter.call(request, timeout=20, cancel=request_context)
summary = adapter.extract_text(response)

非流式调用在完整响应后解析；流式调用则逐块拼接内容，并在连接中断时区分“本地已经收到多少”和“服务端是否仍在生成”。浏览器关闭页面时，向上游传播取消信号，避免无用的后台调用。

3. 验收结果并记录成本

  • 检查 HTTP 状态、响应中的结束原因与输出是否为空；若因长度上限截断，不把半截摘要当成功。
  • 校验四项摘要是否齐全，并把“待确认”与事实区分开。模型文本可能编造根因，仍需与输入记录核对。
  • 记录追踪 ID、模型版本、耗时、输入/输出用量和错误类型；日志保留必要元数据，不记录密钥或原始敏感内容。

4. 失败时怎么分流

401/403 先检查认证和权限，不靠重试解决；429 按服务端提示及本地限额做有界退避；5xx 或网络超时 可在调用预算内有限重试，但超时不等于上游完全没处理。若调用触发外部工具或写操作，还要单独设计幂等键和副作用保护。

连续失败时向用户说明服务暂不可用，并保留可追踪的错误类型。重试次数、总时长和并发闸门要一起限制，避免把短暂故障放大成重试风暴。

一次模型调用到底发生了什么

调用大模型 API 看似只是发一个 HTTP 请求，但要把它用稳，需要理解七个环节：拼消息、选模型、配参数、鉴权、发请求、接收（流式或一次性）、处理错误。

一次请求的七个环节，以及 TTFT / TPOT 分别出现在哪一段
messages 是核心模型只看对话数组，system 只是数组里第一条，不是独立的安全沙箱。
参数服务于可控性temperature、top_p、max_tokens 不是调味料，而是可控性与成本的开关。
流式改变体验流式基本不改变总耗时，但把等待从「最后一次性给」变成「边算边给」。
错误必须分类429 限速、5xx 服务端、超时、长度超限，四类错误的应对完全不同。

messages：四种角色怎么配合

对话数组里每条消息都有 role。理解四个角色的分工，是把调用写对的第一步。

角色作用典型内容注意
system设定全局行为、身份、输出格式、边界你是严谨的技术审校，只输出 JSON不是安全沙箱，用户内容仍可能覆盖它
user用户的请求与输入把这段日志总结成三条结论外部内容要标注来源并做注入防护
assistant模型历史回复，也用于 few-shot 示范上一轮回答，或人工写好的示例预填 assistant 可以强制输出风格与开头
tool把工具执行结果回填给模型tool_call_id + 返回内容必须带对 tool_call_id，否则模型接不上

多轮对话的本质：服务端不保存状态，每次请求都要把完整历史重新发一遍。所以对话越长，输入 token 越多、越贵、越慢。这就是为什么长对话要做摘要压缩或滑动窗口。

关键参数怎么配

参数干什么常用值配错的后果
temperature拉平或锐化概率分布确定性任务 0~0.2；创作 0.7~1.0该稳定的任务乱飘；该有创意的任务千篇一律
top_p只在累积概率前 p 的候选里采样0.8~0.95与 temperature 同时乱调会互相放大，难以复现
max_tokens限制本次生成的最大输出长度按任务上限留 20% 余量太小被截断；太大遇到长尾请求会拖垮超时
stop遇到指定字符串立即停止如 \n\n---没配时模型容易自己续写多余段落
n一次返回多个候选1（默认）费用乘以 n，容易不知不觉超预算
seed尽力复现同一次生成压测与回归时固定只能提高可复现性，不保证逐字一致
response_format约束输出为 JSON 等结构json_object / json_schema只保证语法合法，不保证语义正确

经验法则：temperature 与 top_p 只动一个。分类、抽取、格式化、代码生成这类任务先锁 temperature=0，把随机性降到最低，再评估效果是否够用。

流式输出：SSE 是怎么传的

开启 stream=true 后，服务端用 Server-Sent Events 把增量一块块推过来，每个 chunk 是一个 data: {...}，以 data: [DONE] 结束。

data: {"choices":[{"delta":{"content":"你"}}]} data: {"choices":[{"delta":{"content":"好"}}]} data: {"choices":[{"delta":{"content":"！"}}]} data: [DONE] 客户端: buf += delta.content // 逐块拼 渲染 buf // 用户看到打字机效果 收到 [DONE] 后再取 usage // 部分实现在最后一个 chunk 才给用量
首字更快用户几百毫秒内见到内容，心理等待大幅降低
长输出必须流式HTTP 网关普遍有 60s 超时，长文本不流式会被中间层掐断
省不了钱总 token 一样，费用基本不变；省的是体验与超时风险
要处理断连网络中断时已产出部分照样计费，需设计重试与提示

错误与重试：四类不同的应对

错误常见码本质正确做法
限速429并发或配额打满尊重 Retry-After，指数退避 + 抖动，降级到备用模型
服务端故障500/502/503上游抖动有限次重试（2~3 次），仍失败就快速失败
超时客户端 timeout长尾请求分读超时与连接超时；流式场景用「首字超时 + 空闲超时」
长度超限400 context_length_exceeded输入 + 预留输出超窗口请求前先估算 token，超了就压缩历史或换大窗口模型
# 指数退避 + 抖动，避免重试风暴 for i in range(3): try: return call(messages) except RateLimit as e: sleep(min(2 ** i, 8) + random() * 0.5) # 0.5~1 / 1~2 / 2~4 秒 continue except ServerError: sleep(0.5 * (i + 1)); continue raise # 仍然失败就交给上层降级，不要无限重试

只对幂等或可重放的请求重试。写操作类（下单、发消息）盲目重试会造成重复，必须先做幂等键或先查后写。

成本与容量：算清楚再上线

输入 tokenprompt 全部内容，含 system 与历史
输出 token模型生成的内容，单价通常高于输入
缓存命中前缀相同的部分可打折，把稳定的 system 放前面
批处理离线任务走批处理通道，可显著降价换取延迟
并发配额RPM / TPM 双限，突发会被 429 挡住
上下文成本多轮对话输入线性增长，是最常见的成本失控点

一个估算习惯：上线前用「日均请求数 × 单次输入 token × 单价 + 日均请求数 × 单次输出 token × 单价」先算出日成本，再乘 30。多数成本事故不是单价贵，而是请求量或多轮历史失控。

深入自检

temperature 和 top_p 到底调哪个？

两者都在改采样分布，同时调会互相放大且难以复现。实践上固定一个、只动另一个：想要「稳」就降 temperature 到 0~0.2，想要「多样性」就升 temperature 或放宽 top_p，二者取其一。

为什么流式了总时间没变短？

流式只改变「内容到达的节奏」，不改变「生成完最后一 token 的时刻」。它解决的是首字体验与网关超时，不是吞吐。真正的总耗时由输出 token 数与 decode 速度决定。

max_tokens 设很大会不会更贵？

不会直接更贵，只对实际生成的 token 计费。但设太大会让长尾请求拖长、占住连接、触发超时，间接抬高失败率与重试成本。正确做法是给每个任务设一个贴合的上限。

JSON 模式能保证结果合法且正确吗？

JSON 模式只保证语法合法，不保证字段语义正确、不保证不漏字段。要真正稳，用结构化输出的 schema 约束，并在拿到结果后做一次校验与失败重问。

密钥该怎么放才安全？

永远只在服务端调用，不要把 Key 下发到前端或客户端；按环境分 Key、按业务分 Key，便于限额与吊销；通过网关或代理转发，避免密钥散落在多个服务里。
