🧩 Redis 特殊数据结构

Bitmap / HyperLogLog / GEO / Stream 的原理、命令、场景与坑

Redis 除了 String/Hash/List/Set/ZSet 五大基础结构，还提供四种「特殊数据结构」。它们不是凭空造的新类型，而是用基础结构 + 专门命令包装出来的能力，用来极省内存或极简地解决一类具体问题。一句话定位：

🔲

Bitmap

用 1 个 bit 记一个布尔状态（签到/在线）

📐

HyperLogLog

12KB 估算「去重个数」，误差 0.81%

📍

GEO

基于 ZSet 的经纬度索引（附近的人）

🌊

Stream

带消费组的追加日志（轻量 MQ）

🔲 Bitmap：一个 bit 一个状态

本质 = String 的「位视图」：把字符串的每个字节当成 8 个 bit，用 offset 寻址到某一位。

💡 类比：一张签到表。表上有 10 万个格子，每个格子对应一个用户，打勾=1、空白=0。你不用为每个人存一条记录，只用一个超长表格的「格」就记下了所有人的状态，空间被压缩到 1/8。

核心命令

命令作用例子
SETBIT key offset 1把第 offset 位设为 1SETBIT sign:2026-10-20 10001 1（用户 10001 今日签到）
GETBIT key offset读某一位GETBIT sign:2026-10-20 10001
BITCOUNT key统计有多少位是 1BITCOUNT sign:2026-10-20 → 今日签到人数
BITOP AND/OR dest k1 k2多天位运算连续 7 天签到 = 7 个 key 做 AND
典型场景：用户每日签到、在线/离线状态、布尔特征标记、布隆过滤器底层。100 万用户的每日签到只占 1M/8 ≈ 125KB，而存 100 万条记录要几十 MB。
⚠️ 坑：offset 是「位」不是「字节」；offset 过大会瞬间撑大 key（Redis 会补零填充）；适合稀疏度可控的场景，否则空间优势消失。

📐 HyperLogLog：12KB 估出「去重人数」

概率基数估计算法，用固定 ~12KB（Redis 默认 16384 个寄存器）估出一个集合的「去重元素个数」。

💡 类比：数广场上有多少人，但不用逐个数。你只观察「最长的一片连续空地有多长」，就能反推出大约来了多少人——数得越精细（看越长），估得越准，但永远只看「空地长度」这一个统计量，不记录任何人脸。

核心命令

命令作用
PFADD key elem [elem...]把元素加进 HyperLogLog
PFCOUNT key [key...]估算去重基数（多个 key 会先合并再算）
PFMERGE dest key [key...]合并多个 HLL（如合并 7 天 UV 得周 UV）
典型场景：页面 UV、独立访客、搜索关键词去重计数。误差约 0.81%——1 亿 UV 最多差 800 万级别，但对监控/大盘完全够用，而内存只用 12KB。
⚠️ 坑：只能估「有多少个」，取不出具体是哪些元素；不精确但省几个数量级内存；PFCOUNT 作用在多个 key 上会触发合并，比单 key 稍贵。

📍 GEO：经纬度索引（附近的人）

底层就是 ZSet——把经纬度用 Geohash 编码成一个 52-bit 整数当作 score 存进去，于是「按距离排序/范围查找」退化成 ZSet 的区间查询。

核心命令

命令作用
GEOADD key lng lat member添加位置（经度在前！）
GEODIST key a b km两地距离
GEOSEARCH key FROMLONLAT ... RADIUS 5 km以某点为中心查 5km 内成员
GEOHASH key member看该点的 geohash 编码（便于调试）
典型场景：附近的人、门店推荐、配送范围。因为底层是 ZSet，你仍可以用 ZRANGE 看到所有成员、用 ZREM 删除。
⚠️ 坑：Geohash 在边界附近有精度/跳变问题；适合中小规模，超大规模或复杂空间查询请用专门引擎（如 PostGIS / Elasticsearch）。

🌊 Stream：带消费组的追加日志

为「消息流 / 事件流」设计的追加式（append-only）结构，支持多消费组、消息确认、回溯重放——是 Redis 做轻量消息队列的官方答案。

💡 类比：一个微信群聊记录。消息按时间顺序追加（你改不了历史）；新加入的客服可以从头补看（回溯）；多个客服分成一组轮流接客（消费组），每条消息只被一个人处理，处理完要「已读回执」（XACK 确认），没回执的会进入待处理列表。

核心命令

命令作用
XADD mystream * field val追加一条消息，* = 自动生成 id（毫秒时间-序号）
XGROUP CREATE mystream g1 $建消费组，$=只消费新消息，0=从头回溯
XREADGROUP GROUP g1 c1 COUNT 10 STREAMS mystream >消费者 c1 拉取未消费消息，>=新消息
XACK mystream g1 msgid确认已处理（否则留待 XPENDING）
XTRIM mystream MAXLEN 10000限制长度，防止无限增长
典型场景：轻量消息队列、事件溯源、IoT 设备上报、CQRS 事件总线。比用 List 做队列强得多——List 没有消费组、没有确认、没有回溯。
⚠️ 别拿它当 Kafka 用：没有分区、吞吐与持久化模型不同、运维工具生态弱。XDEL 不会真正释放空间，要靠 XTRIM 限长；id 天然有序，便于「断点续传」。

🎯 怎么选？一张表说清

问题选哪个理由
100 万用户每日签到，统计当天签了几人？Bitmap125KB 搞定，BITCOUNT 秒出
页面每天 UV 多少，不用知道是谁？HyperLogLog12KB 估算，误差可忽略
App 里「附近 1km 的门店」？GEO一行 GEOSEARCH 出半径结果
订单事件流，多个 worker 分组消费、不丢消息？Stream消费组 + 确认 + 回溯

🎯 面试问答

Q：HyperLogLog 能取出具体用户吗？
A：不能，它只估基数，不存元素本身——这是它省内存的根本原因。
Q：Bitmap 适合存「用户资料」吗？
A：不适合。Bitmap 只记布尔（0/1）。用户资料是结构化多字段，该用 Hash。
Q：Stream 和 List 做队列有什么区别？
A：Stream 支持消费组、消息确认（ACK）、Pending 列表、回溯；List 只能 LPUSH/RPOP，没有这些，容易丢消息。
Q：GEO 底层是什么？
A：ZSet。经纬度被编成 geohash 当作 score，范围查询其实是 ZSet 的分数区间扫描。
Q：Bitmap 的 offset 为什么不能乱设很大？
A：offset 直接决定 key 占用的字节数（offset/8+1），设到 1 亿会让这个 key 瞬间变大，浪费内存。
