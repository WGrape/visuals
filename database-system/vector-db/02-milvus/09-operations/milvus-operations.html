①监控体系：指标从哪来

Milvus 各组件暴露 Prometheus 格式的指标，官方提供 Grafana 看板。监控要覆盖四层：接入层（请求）、执行层（节点资源）、数据层（段与索引）、依赖层（etcd / WAL / 对象存储）。

②关键指标与告警阈值

指标关注点告警建议
QueryNode 内存使用率最硬的约束，逼近上限即 OOM 风险> 80% 预警，> 90% 紧急（立即扩容或减副本）
search P99 延迟用户体验的直接指标相对基线上升 50% 即告警，别只看绝对值
search / insert QPS 与错误率是否被限流、是否有失败重试风暴错误率 > 1% 告警
Growing Segment 大小 / 占比占比高 = 大量暴力扫描，查询变慢持续增长不回落即关注（flush 或消费出问题）
WAL 消费延迟（lag）数据可见性的根因指标lag 持续上升 = 消费能力不足，需要扩容
Segment 数量与平均大小小段过多会拖垮查询数量暴涨或平均大小持续偏小即关注
索引构建任务堆积堆积 = 新数据长时间走暴力长时间不下降即关注（IndexNode 不足 / 资源受限）
对象存储 IO / 延迟flush、compaction、回表都依赖它延迟突增即关注，常是底层存储问题
etcd 健康与延迟元数据不可用 = 集群不可用任何异常都应立即告警
告警阈值建议相对基线而非绝对数值：不同业务的 top_k、过滤、数据分布差异巨大，绝对值阈值要么误报要么漏报。

③故障模式排查表

现象优先排查处理方向
QueryNode OOM / 频繁重启HNSW 内存估算是否漏了标量与缓存；副本数是否过多；是否加载了不该加载的 Collection换量化索引（HNSW_PQ / IVF_PQ）、减副本、用资源组拆分、扩容内存
查询突然变慢growing 段占比、Segment 数量、是否在建索引/compaction、一致性级别flush + 等索引就绪、触发 compaction、降级一致性、检查后台任务
写入后查不到 / 延迟可见WAL 消费 lag、DataNode / QueryNode 数量、一致性级别见一致性；扩容消费节点
带过滤的查询特别慢过滤字段有没有 INVERTED 索引、过滤选择率补标量索引；高选择率场景改 Partition / Partition Key
召回率下降索引参数是否被改、metric 是否一致、Embedding 模型是否更换、数据分布是否漂移重跑 FLAT 基线对比；建立召回回归测试
删除后磁盘不降compaction 是否执行触发 compaction，见数据管理
写入被限流 / 报错单批是否过大、写入速率是否超配额、磁盘/对象存储是否满减小批次并加大间隔、走 bulk import、扩容存储
整个集群不可用etcd 是否健康、Coordinator 是否正常、依赖组件网络先恢复 etcd，再逐层拉起

④调优清单（按收益排序）

  1. 给所有过滤字段建 INVERTED 索引——投入最小、收益最大的一项。
  2. 查询改成批量（data 传多条），减少 RPC 与段扫描固定开销。
  3. 克制 output_fields，不要把正文/向量拉回来。
  4. 调 ef / nprobe 到召回拐点，别拍脑袋，见索引参数调优。
  5. 攒批写入，避免高频小批产生海量小段；必要时 compaction。
  6. 一致性降级到 Bounded/Session，除非确需强一致。
  7. 加副本提升 QPS（内存换吞吐，最贵的一步）。
  8. 换索引 / 上量化，用召回换内存（通常是最不得已的一步）。
调优必须有基线、有回归：每次改动前记录 P50/P99 与 recall@K，改动后对比。凭感觉调参等于赌博。

⑤变更与升级

索引变更

换索引类型 = 重建索引（耗时、吃资源）。先在影子 Collection 上验证召回与延迟，再切换流量。

维度变更

维度建表即固定，换 Embedding 模型就要重建 Collection 并全量重灌。提前设计好版本化的 Collection 名（如 docs_v2）。

版本升级

关注索引文件格式的兼容性说明，先在预发完整演练；滚动升级依赖多副本。

容量变更

QueryNode 扩容后需要重新加载/均衡 Segment；提前在压测环境验证扩容后的表现。

把 Collection 当不可变基础设施：通过 docs_v1 → docs_v2 双写 + 灰度切流来演进，而不是原地改结构。

⑥上线自检清单

项检查
索引向量索引已建且状态就绪；所有过滤字段都有标量索引
召回有 FLAT 基线，recall@K 达标，且有回归脚本
延迟P99 有基线，且压测用的是真实 nq / top_k / 过滤条件
内存QueryNode 内存按 1.5 倍估算留有余量；副本数 × 内存 = 总需求
一致性级别与业务语义匹配，多副本下表现已验证
写入用 upsert 而非 insert；有 flush 与 compaction 节奏
监控四层指标已接，关键项有告警且演练过
恢复有备份或可重放的原始数据，恢复流程演练过
本页的规模建议与数值均为经验量级，组件构成随版本演进（如较新版本引入 Woodpecker 以简化 WAL 依赖），请以你部署版本的官方文档为准。
运维 Milvus 的核心是把问题分层定位：请求慢先看接入层与执行层，查不到先看 WAL 消费与一致性，变慢先看段与索引，整体不可用先看 etcd。分层之后，「Milvus 很玄学」就变成了可枚举的排查路径。
