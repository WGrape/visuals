把「打开网页」拆成十步

从敲下回车到看见画面，中间发生的事比想象中多得多。理解这条链路，是所有 Web 性能优化的前提 —— 你没法优化一串你看不见的步骤。

缓存 → 减少往返 → 减少字节数 → 提前解析 → CDN → 压缩
完整链路十步，以及缓存命中能省掉大半

前三步：在字节离开机器之前

① URL 解析

浏览器先要把这串字符拆成结构：协议 scheme、主机名 host、端口 port、路径 path、查询串 query、片段 fragment。

还会顺手做非法字符转义与非 ASCII 字符的百分号编码。

② 缓存与 HSTS

先查强缓存：Cache-Control / Expires 未过期就直接复用本地副本，连请求都不发。

再查 HSTS 列表：如果域名在列表里，直接按 HTTPS 访问，省掉一次 80 端口跳转。

③ DNS：一层层问下去

浏览器缓存 → 操作系统缓存 → hosts 文件 → 本地 DNS 服务器。本地服务器不得不递归时，会从根服务器问到顶级域服务器再到权威服务器。

这一串往返在跨境、DNS 被污染或服务器响应慢时极其昂贵，因此有了 DNS 预解析（dns-prefetch）与 HTTPDNS 这些手段。

④ 建连接

TCP 三次握手之后如果是 HTTPS 还要 TLS 握手。两者都是纯往返，没有任何业务数据，距离越远越吃亏。

优化途经：preconnect 提前建连接、会话复用减少 TLS 往返、QUIC 把两者合并。

后七步：字节回来了不等于页面出来了

拿到 HTML 只是开始。浏览器要做的事情是一条流水线：

HTML 字节流 ↓ 词法/语法分析 DOM 树 ↓ 遇到 CSS CSSOM 树 ↓ DOM + CSSOM 合并 Render Tree（只包含可见节点） ↓ 计算每个节点的位置与尺寸 Layout（布局 / 重排） ↓ 生成绘制指令 Paint（绘制） ↓ 分层交给 GPU Composite（合成）→ 屏幕上的像素
环节常见的卡点对策
HTML 解析同步 <script> 阻塞解析用 defer / async，或把脚本放最后
CSSOM 构建CSS 是渲染阻塞资源首屏关键 CSS 内联，其余异步加载
资源加载图片、字体、脚本各自再次往返preload / preconnect、HTTP/2 多路复用、合理缓存
Layout读写布局属性交替触发多次重排批量读写、用 transform 代替改位置
Paint大面积重绘、复杂阴影与滤镜减少重绘区域、提升为独立图层
Composite图层过多消耗显存只给真正需要动画的元素加 layer

为什么 <script> 默认会阻塞：因为它可能调用 document.write 改变后续文档结构，浏览器只能停下来先执行。defer（HTML 解析完再执行、按顺序）和 async（下载完立刻执行、不保证顺序）就是用来解除这个阻塞的。

每一步大概花多久（数量级直觉）

本地缓存命中接近 0ms，完全没有网络参与。
DNS 查询命中缓存 ~0ms；递归查询几十到几百毫秒。
TCP + TLS 握手同地域几毫秒到几十毫秒；跨洲可达 200ms 以上。
服务端处理视业务而定，良好实践常在几十毫秒内。
下载与解析渲染取决于资源体积与设备性能，往往是最大的一块。

用这个数量级做预算：如果目标是 1 秒内首屏，把上面几项列出来加总，就能立刻知道该先从哪一项下手。离优化最近的一步永远是「先量一遍」，而不是凭直觉改代码。

深入自检

为什么第一次访问慢、第二次快那么多？

因为 DNS 记录、TCP/TLS 会话参数与静态资源全都有了本地缓存。第二次访问常常能跳过 DNS 与握手，资源直接命中本地磁盘/内存缓存。这也是为什么性能优化要区分「首次访问」和「回访」两个指标，只测其中一个是会误判的。

HTTPDNS 是什么，为什么要用它？

传统 DNS 走 UDP 53 端口，容易被劫持、污染，且解析结果未必最优。HTTPDNS 用一个 HTTP 接口直接向服务商查询域名对应的 IP，绕过运营商的 Local DNS。好处是防劫持、可以按用户来源返回更合适的 IP，代价是客户端需要自己接管连接与容灾。

CDN 到底加速了哪一步？

主要是减少物理距离带来的往返：把资源放到离用户更近的节点，DNS 与 TLS 握手、首字节等待都变短；同时对静态资源它还承担了缓存与压缩。CDN 不能减少你服务端处理业务逻辑的时间，也不会帮你缩小一个 5MB 的包 —— 那个还是得靠自己减。

为什么有时候能收到响应但页面还是白屏？

常见原因：① HTML 里的关键资源（CSS、同步脚本）加载失败或被阻塞；② 前端框架需要执行 JS 才能渲染，而 JS 还没下载完；③ 出现了渲染依赖的资源互相等待（比如字体阻塞）。这类问题要用浏览器的 Performance / Network 面板看时间线，而不是只看某一个环节的耗时。

耗时分解

# 一条命令看全流程耗时分解（最实用的一段）
curl -o /dev/null -s -w "
DNS 解析  : %{time_namelookup} s
TCP 连接  : %{time_connect} s
TLS 握手  : %{time_appconnect} s
首字节TTFB: %{time_starttransfer} s
总耗时    : %{time_total} s
下载大小  : %{size_download} B
平均速度  : %{speed_download} B/s
" https://example.com

# 分解读法：
#   time_connect - time_namelookup   = TCP 建连耗时
#   time_appconnect - time_connect   = TLS 握手耗时
#   time_starttransfer - time_appconnect = 服务器处理 + 首个响应（TTFB 主体）
#   time_total - time_starttransfer  = 内容传输耗时

# DNS 专项
dig +trace example.com
dig example.com +short

# 看连接复用与状态分布
ss -s
ss -tan state established | wc -l

关键比值：一次跨城 RTT（约 30 ms）已经远超大多数后端处理时间。所以在没有连接复用时，握手开销往往就是首屏的大头——这也是 HTTP/2 多路复用、TLS 会话复用、CDN 就近接入能带来数量级改善的原因。

优化清单与自检

  • 优先级排序：先消灭多余的 RTT（复用连接、升级 HTTP/2、CDN 就近），再压缩体积，最后才是后端优化。
  • DNS：减少域名分片（HTTP/2 下不需要多域名），启用 dns-prefetch / preconnect。
  • TLS：开 TLS 1.3 与会话复用；0-RTT 有重放风险，只用于幂等请求。
  • 关键渲染路径：CSS 放 head、JS 用 defer/async，避免同步脚本阻塞解析。
  • 缓存：静态资源用长 Cache-Control + 内容哈希文件名；HTML 用 no-cache + ETag。
  • 压缩：文本资源用 Brotli（通常比 gzip 再小 15%~20%），图片用 WebP/AVIF。
指标含义体感阈值
TTFB首字节时间< 200 ms 快；> 800 ms 明显卡
FCP首次内容绘制< 1.8 s 良好
LCP最大内容绘制< 2.5 s 良好
INP交互到下次绘制< 200 ms 良好
CLS累积布局偏移< 0.1 良好
为什么后端很快但页面还是慢？

八成耗在 RTT 和前端渲染上。先用 curl -w 把时间分解开，确认慢在 DNS/连接/TLS 还是下载/渲染，再对症处理——凭感觉优化最容易做无用功。

HTTP/2 一定更快吗？

在高丢包、高延迟链路上，HTTP/2 的单连接 TCP 队头阻塞可能反而不如 HTTP/1.1 多连接。HTTP/3（基于 QUIC）就是为了解决这一点。

preconnect 和 dns-prefetch 有什么区别？

dns-prefetch 只做 DNS 解析；preconnect 做完 DNS + TCP + TLS。后者省得更多，但开销也更大，只对确定会用到的少数源使用。
