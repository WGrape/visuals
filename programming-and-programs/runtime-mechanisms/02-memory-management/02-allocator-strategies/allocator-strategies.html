目标

分配器的两难

分配器要同时做到：分配快、碎片少、能并发。这三者互相制约——减少碎片通常需要更精细的管理，而精细管理意味着更高开销。

⚡
速度
分配/释放要快，最好多数走无锁快路径
🧩
碎片
内部碎片（分配多了）与外部碎片（空闲块太散）
🔒
并发
多线程同时分配不能成为瓶颈（锁竞争）
两种碎片：
• 内部碎片：分配单元比请求大，多余部分浪费（如按 16 字节对齐，请求 1 字节也占 16）。
• 外部碎片：空闲内存总量够，但被切成零散小块，无法满足一次大请求。
策略一

空闲链表（Free List）

把空闲块串成链表，分配时找一块合适的摘下来。

查找策略做法特点
首次适配 First Fit从头找第一个够大的块快，但容易在链表前部留下小碎片
最佳适配 Best Fit找最接近请求大小的块碎片少，但要遍历全部，慢
下次适配 Next Fit从上次位置继续找折中，碎片分布更均匀
释放时需要合并相邻空闲块（coalescing），否则外部碎片会迅速恶化。通常靠块头记录大小与空闲标志来实现。
策略二

伙伴系统（Buddy System）

按 2 的幂次分块，合并时只与「伙伴」合并，规则简单、速度快。

伙伴系统的取舍：优点是对齐规整、分配与合并都是 O(log n) 且实现简单，适合物理页框管理（Linux 内核用它管页）；缺点是内部碎片明显，不适合小对象分配。
策略三

分级分配与 Slab

📏
Size Class 分级
把请求按大小归入固定档位（8/16/32/64...字节），每档一个空闲链表。分配 O(1)，且同档复用避免外部碎片
🗄️
Slab / 对象池
为同一类型对象预分配整块内存并切成等长槽位，复用时不重新初始化。内核与 Go 的 mcache 都用它
🔁
复用优先
释放的对象先回到本档空闲链表，下次分配直接复用；减少向操作系统申请的次数
🧵
每线程缓存
每个线程/处理器持有小对象缓存（thread cache），无锁分配，大幅降低锁竞争
实践

面试问答

高频问题

Q1：内部碎片和外部碎片有什么区别？
内部碎片是分配单元大于实际请求造成的浪费（如按 16 字节对齐、伙伴系统向上取整到 2 的幂）；外部碎片是空闲内存总量够但分布零散，无法满足一次连续的大请求。
Q2：什么是伙伴系统？优缺点？
按 2 的幂次划分与合并内存块，只与大小相同、地址相邻的「伙伴」合并。优点是分配/合并快、实现简单，适合页框管理；缺点是向上取整带来明显内部碎片。
Q3：First Fit / Best Fit 的区别？
First Fit 取第一个够大的空闲块，快但易在链表前部留下碎片；Best Fit 取最接近请求大小的块，碎片更少但需要遍历全部，速度慢。
Q4：现代分配器如何让多线程分配变快？
采用每线程（或每处理器）小对象缓存，使大多数分配走无锁快路径；只有缓存不足时才访问全局 central cache 并加锁。TCMalloc、jemalloc、Go 分配器都是这一思路。
Q5：什么是 size class？
把请求大小归入若干固定档位（如 8/16/32/64 字节），每档维护独立空闲链表。分配时直接取对应档位，O(1) 完成，且同档复用可避免外部碎片。

第一层 · 三种策略解决什么问题

分配器的根本难题是 外部碎片：反复分配释放后，空闲内存被切成很多小块，虽然总量够但无法满足一次大请求。三种策略是三种不同的应对思路。

策略怎么工作外部碎片内部碎片分配速度代表
空闲链表（First/Best Fit）维护空闲块链表，按策略找合适的严重无O(n) 查找早期 malloc、ptmalloc
伙伴系统（Buddy）按 2 的幂分块，分裂/合并中最多浪费 50%O(log n)Linux 内核页分配
分级分配（Size Class）按大小分级，每级一个空闲链表小按级取整（通常 <25%）O(1)TCMalloc / jemalloc / Go
  • 内部碎片：分配给你的比你要的多（如要 100 字节给了 128）。外部碎片：空闲内存总量够但被切碎了凑不出连续块。
  • 伙伴系统的核心：只按 2 的幂分配（16/32/64/128...）。要 100 字节 → 给 128（内部碎片 28 字节）。释放时如果相邻的「伙伴」也空闲就合并成更大的块。合并简单是它的最大优势。
  • 分级分配的核心：把大小分成几十个档位（如 Go 有约 67 个 size class），每个档位一个空闲链表。分配时按大小直接定位到档位，O(1) 拿到。这是现代分配器的主流。

go build -gcflags='-m' main.go        # 看逃逸分析（哪些分配在堆上）
#   ./main.go:10:6: moved to heap: x     <- 逃逸了，会在堆上分配

go test -bench=. -benchmem ./...      # 【关键】看 allocs/op 与 B/op
#   BenchmarkX-8  1000000  1200 ns/op  512 B/op  4 allocs/op
#                                        ^字节   ^次数（越少越好）

GODEBUG=gctrace=1 ./app               # 打印每次 GC 的详情
#   gc 1 @0.012s 4%: 0.024+1.5+0.011 ms clock,
#     0.19+0.31/1.4/0.13+0.092 ms cpu, 4->5->3 MB, 5 MB goal, 8 P
#                                    ^GC 前后堆大小

# —— Linux：观察伙伴系统 ——
cat /proc/buddyinfo                   # 每个 order 有多少个空闲块
#   Node 0, zone  DMA    1  0  1  0  2  1  1  0  1  1  3
#                        ^order0 ^order1 ...（数字=该 order 的空闲块数）
#   若高阶全为 0 -> 已无大块连续内存，大页/大块分配会失败

cat /proc/meminfo | grep -E 'MemFree|MemAvailable|Slab|PageTables'
#   注意：MemFree 小不代表内存不够（还有 PageCache 可回收）

# —— 内存碎片量化 ——
#   内部碎片率 = (分配到的 - 请求的) / 请求
#     伙伴系统最坏：(2^n - (2^(n-1)+1)) / (2^(n-1)+1) ≈ 50%
#     分级分配（比例 1.125）：最坏 ≈ 12.5%
#   外部碎片率 = 1 - (最大连续空闲块 / 总空闲内存)

Go 程序的优化优先级：先看 allocs/op 再看 ns/op。因为每次分配最终都要 GC 回收，而 GC 是尾延迟的主要来源。把 4 allocs 降到 0，收益往往超过把 1200ns 降到 1000ns。

第三层 · 排障清单

  • Go 程序内存持续上涨 → 先区分是「真的泄漏」还是「还没 GC」。用 GODEBUG=gctrace=1 看 GC 后的堆大小是否持续上升；用 pprof heap 看是哪些对象。注意 Go 的 GC 目标不是把内存降到最低——它会留一些余量减少 GC 频率。
  • 分配次数太多导致 GC 频繁 → -benchmem 看 allocs/op。常见来源：在循环里创建临时对象、字符串拼接（用 strings.Builder）、[]byte 与 string 反复转换（每次都拷贝）、小对象装箱成接口。用 sync.Pool 复用是最直接的手段。
  • 大对象（>32KB）直接走堆 → 这类分配不经过 size class，代价高且容易造成碎片。大 buffer 要池化复用。
  • 逃逸分析没通过，本该栈上的对象上了堆 → -gcflags='-m' 查看。常见原因：返回局部变量指针、把局部变量存进接口、闭包捕获、slice 扩容不确定。栈上分配是零成本的（函数返回自动回收），堆上分配要 GC。
  • Linux 分配大块连续内存失败（order > 0 全为 0） → /proc/buddyinfo 查看。长期运行的系统会有碎片。解法：大页（HugePage）预留、echo 1 > /proc/sys/vm/compact_memory 手动整理、或重启。
  • slab 占用过高 → /proc/meminfo 的 Slab 项。内核对象缓存（dentry、inode）占用大。可用 slabtop 看细节，drop_caches 能回收部分。
  • 多线程分配时的锁竞争 → 这是 TCMalloc/jemalloc 存在的核心理由：每线程独立缓存，小对象分配无锁。Go 的 mcache 同理（每个 P 一个）。如果发现分配是瓶颈，检查是否有大量跨线程释放（会导致缓存不平衡）。
  • 内存占用远超实际需求（RSS > 堆大小很多） → Go 的堆是虚拟地址预留，RSS 才是实际物理内存。另外 GC 回收的内存不一定立刻还给 OS（Go 会保留一段时间，默认 5 分钟后逐步归还）。

第四层 · 原理与取舍

三种策略的本质取舍是：碎片、速度、实现复杂度 三者不可兼得。现代分配器（TCMalloc/jemalloc/Go）的分级 + 线程缓存方案，是当前的最优解。

  • 为什么伙伴系统适合内核而不适合应用：内核按页（4KB）分配，粒度粗，内部碎片 50% 的代价可以接受（反正页是最小的）；而且内核需要能合并来提供大块连续物理内存（DMA 需要物理连续），伙伴系统的合并逻辑（找 buddy）非常简洁高效。应用层按字节分配，50% 的内部碎片完全不能接受——所以应用层用分级分配。
  • 为什么分级分配这么快：两个关键设计：① 按大小分档，分配时 O(1) 定位（不需要搜索链表）；② 每线程（或每 P）缓存，小对象分配完全无锁。这两点让 TCMalloc 在高并发下比 ptmalloc 快数倍。代价是内存不能跨线程移动，某个线程缓存了很多而另一个没有时会浪费（现代实现有定期 rebalance）。
  • Go 的三级结构：mcache（每 P 一个，无锁）→ mcentral（按 size class 组织，需要锁）→ mheap（全局，大对象直接从这里拿）。绝大多数分配在 mcache 就完成了（无锁，几纳秒）。这个设计和 TCMalloc 几乎一样。
  • 内部碎片的量化：如果相邻 size class 的比例是 r，那么最坏情况下的内部碎片率是 r - 1。Go 用约 1.125~1.2 的比例，把内部碎片控制在 12.5%~20% 以内；代价是档位数变多（67 个）导致管理开销略增。这是典型的空间 vs 管理成本取舍——比例越接近 1，碎片越少但档位越多。
  • 为什么不做「完美」的紧凑整理（像 JVM 的某些 GC）：因为整理需要移动对象，而移动对象意味着要更新所有指针，且在 Go 这种可以直接拿到对象地址的语言里非常复杂（还有与 cgo 的交互）。Go 选择不整理，用分级分配 + 精细的 size class 来控制碎片——这是「用分配策略解决碎片」而非「用 GC 整理解决碎片」的路线。代价是长期运行可能有碎片，收益是 GC 停顿极短。
方案分配速度内部碎片外部碎片并发适用
空闲链表慢（O(n)）无严重需加锁简单场景
伙伴系统快（O(log n)）≤50%中（可合并）需加锁内核页分配
分级 + 线程缓存最快（O(1) 无锁）12~20%小无锁应用/运行时
对象池最快（复用）无无需同步高频同构对象
为什么 Go 不做内存整理（compaction）？

核心原因是成本与收益不匹配。做整理要解决一个难题：移动对象后，所有指向它的指针都要更新。在 Java 里这可行（JVM 完全掌控对象引用，且没有裸指针）；但在 Go 里：① 有unsafe.Pointer 和 cgo——用户可能拿着一个对象的真实地址，移动它会导致崩溃；② Go 把内部指针（指向对象中间的指针）暴露给了用户（如指向结构体字段的指针），这让「找到所有指向这个对象的指针」变得复杂；③ Go 的设计目标之一是极低的 GC 停顿（<1ms），而整理内存是耗时的（要拷贝大量数据并更新指针），与这个目标冲突。所以 Go 选择另一条路：用精细的分配策略（67 个 size class）控制碎片，而不是事后整理。实践效果很好——大多数 Go 服务的内存碎片率在可接受范围。代价是：如果你的程序有大量长生命周期的大对象混着小对象，长期运行后碎片会比较明显（RSS 持续高于实际用量），这时要靠对象池化、减少大对象分配来缓解，或者设置 GOGC 更激进地回收。

sync.Pool 什么时候该用？

用在高频创建且生命周期极短的同构对象上。三个判断条件：① 分配频率高（每秒几千次以上）——否则收益不抵管理开销；② 对象大小中等（几百字节到几十 KB）——太小的对象分配本身很便宜，太大的对象池化会占内存；③ 可以安全复用（复用前要重置状态，不能有残留数据）。典型场景：HTTP 的 buffer、序列化用的临时 buffer、RPC 的请求/响应对象（go-zero、gin 都大量使用）。四个注意事项：① Pool 里的对象随时可能被 GC 清掉（Go 1.13 后每次 GC 会清空部分），所以不能依赖 Pool 做缓存，只能在 miss 时重新创建；② 取出后必须重置——这是最常见的 bug 来源（脏数据）；③ 大对象放 Pool 会占用内存不释放，要权衡；④ 用 defer pool.Put(x) 归还，但要确保归还时对象没有被其他 goroutine 引用。反例：不要池化数据库连接、goroutine——这些有更合适的机制（连接池、worker pool）。

伙伴系统的 50% 内部碎片听着很糟，为什么还在用？

因为它的碎片是「可预测且有界的」，而且换来的是合并能力。具体说：① 内部碎片最坏 50%，但平均约 25%（请求大小随机分布时），而且内核分配的是页——本来就是粗粒度，浪费一页的一半在很多场景可以接受；② 它换来的是极简且可靠的合并：一个块释放时，只需检查它的「伙伴」（地址异或块大小）是否也空闲，是就合并，递归向上。这个性质对内核至关重要——内核经常需要物理连续的大块内存（DMA、大页），必须有可靠的合并能力；③ 分配/释放都是 O(log n)，且有界（最多 11 层），性能非常稳定，没有最坏情况的抖动。对比之下，空闲链表虽然无内部碎片，但外部碎片不可控（长期运行后可能完全无法分配），且查找是 O(n)。所以内核选伙伴系统是「用可预测的 25% 浪费换取可靠的连续内存供应」。另外现代内核还有 slab 分配器叠在伙伴系统之上——内核里的小对象（如 inode、task_struct）由 slab 按类型缓存，避免了伙伴系统的内部碎片。这是分层设计：伙伴系统管大块物理页，slab 管小对象。
