Channels 与 select 多路复用

Go 的口头禅：「不要通过共享内存来通信，而要通过通信来共享内存」。channel 是 goroutine 间传递数据的管道，select 用于在多个通信操作间多路复用。

channel 是类型化管道

channel 让你安全地在 goroutine 之间传递值，避免手动加锁。一端发、一端收，天然同步。

创建与类型

make 指定缓冲

无缓冲 channel 收发必须同时就绪；带缓冲的则缓冲未满/未空时不必等待。

ch := make(chan int)        // 无缓冲
buf := make(chan int, 3)   // 缓冲 3

// 方向限定（函数参数更清晰）
func worker(out chan<- int, in <-chan int) {}
发送与接收

<- 方向即语义

ch <- v 发送；v := <-ch 接收；<-ch 丢弃值。无缓冲下，发送会阻塞直到有接收者。

go func() { ch <- 1 }()
v := <-ch            // 阻塞直到收到 1

// 多返回值：是否成功接收（未关闭时恒 true）
v, ok := <-ch       // ok=false 表示 channel 已关闭且无数据
缓冲的作用

解耦生产消费速度

缓冲 channel 像队列，生产者可连续放入直到满；满后再发则阻塞。适合削峰填谷。

缓冲大小是设计决策：太小仍易阻塞，太大占用内存且可能掩盖背压问题。无缓冲则提供最强同步保证（ rendezvous ）。
关闭 channel

发送方关闭，接收方判停

只有发送方应关闭 channel；关闭后不能再发送（panic）。接收方用 comma-ok 或 for range 感知结束。

close(ch)
for v := range ch {   // 自动在关闭且无数据时退出
    fmt.Println(v)
}
// 或
v, ok := <-ch; if !ok { break }
select：多路复用

哪个就绪就走哪个

select 像 switch，但每个 case 是一个通信操作；随机挑一个就绪的分支执行；可加 default 实现非阻塞。

select {
case v := <-ch1:
    fmt.Println("from ch1", v)
case ch2 <- 10:
    fmt.Println("sent to ch2")
default:
    fmt.Println("non-blocking: 都没就绪")
}
常见坑

关闭/泄漏/死锁

三个高频问题

⚠️ 重复关闭、向已关闭 channel 发送都会 panic；goroutine 因无人接收而永久阻塞会泄漏；select 无 default 且所有 case 阻塞会死锁。务必规划好关闭责任方。

select：多路复用与三个惯用法

// ① 超时控制 select { case v := <-ch: handle(v) case <-time.After(3 * time.Second): return ErrTimeout } // ② 非阻塞尝试（default 分支） select { case ch <- v: // 发出去了 default: // 缓冲满了，丢弃或降级 } // ③ 配合 context 退出 for { select { case v := <-ch: handle(v) case <-ctx.Done(): return ctx.Err() // 收到取消就退出 } } // 注意：多个 case 同时就绪时，select 随机选一个 // 这是有意的，避免某个分支被长期饿死
随机选择多分支同时就绪时随机，不要依赖顺序
空 select{}永久阻塞，会触发死锁检测
default 慎用会变成忙等，烧 CPU
nil 分支禁用把 channel 置 nil 可屏蔽该分支
超时用 Timer循环里用 Ticker 而不是 time.After
select 里别做重活会阻塞其它分支的响应

有缓冲还是无缓冲

无缓冲（同步）

发送方必须等到接收方就绪，天然同步。

  • 保证「对方已收到」这一语义
  • 适合传递信号与交接所有权
  • 代价是双方都被对方的节奏拖住

有缓冲（异步）

缓冲未满时发送立即返回，解耦双方节奏。

ch := make(chan int, 10) // 缓冲大小怎么定？ // 0 严格同步 // 1 允许一次「提前生产」 // N 吸收突发，N 约等于每秒峰值 × 可容忍的处理延迟 // 注意：缓冲不是越大越好 // 它只会把背压推迟，不会让消费变快

缓冲满了之后发送方照样会阻塞，背压只是被延迟而非消失。

常见模式

  • 信号量：缓冲大小为 N 的 channel 控制并发数
  • 扇出：多个 worker 从同一个 channel 取任务
  • 扇入：多个结果汇总到一个 channel
  • 完成信号：done channel 通知退出
  • 用 ctx 代替 done：现代写法统一用 context

深入自检

channel 关闭了还能收到数据吗？

能。已关闭但缓冲中还有值时会继续取出，取完后才返回零值与 ok=false。这是 range 能够优雅退出的原因：它一直取到 channel 关闭且缓冲为空。

为什么不要由接收方关闭 channel？

因为可能有多个发送方。接收方关闭后，其他发送方再发送就会 panic。规则是「谁负责生产、谁负责关闭」，并且只在唯一的生产者退出时关闭一次。

缓冲越大越好吗？

不是。缓冲只是把背压推迟，消费能力没变的话队列终究会满，而且更大的缓冲意味着更高的内存占用与更长的处理延迟（数据排队时间变久）。缓冲大小应基于突发量与可接受延迟估算。

select 的 default 分支有什么风险？

它会让 select 永不阻塞，若放在循环里就变成忙等，持续占用一个 CPU 核。只有在明确需要「尝试一下，不行就算了」且不会高频循环时才用。

nil channel 有什么实际用途？

对 nil channel 的收发会永久阻塞，因此可以把某个 case 的 channel 置为 nil 来「禁用」这个分支。这在「某一路数据已处理完、不再关心」的合并场景中很实用。
