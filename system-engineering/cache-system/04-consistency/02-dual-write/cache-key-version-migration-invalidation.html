缓存键版本迁移：改了数据结构，怎样避免新旧应用互相读错

用商品卡片从 v1 到 v2 的上线过程讲命名空间、双读、回填、失效和回滚。

先分开两种“版本”

商品缓存原来存 `product:v1:42`，值只有价格和标题；新版要增加库存展示与币种。若新旧应用都读写同一个 key，旧版可能把新版字段丢掉，新版也可能把旧值误当完整数据。给缓存 key 加 schema 命名空间如 `product:v2:42`，可以隔离不同序列化格式；但这只解决“结构兼容”，不自动解决商品 42 的数据新鲜度。商品价格从 100 改为 90 时，v1 和 v2 都可能同时过期或陈旧，仍需按更新流程失效。

另一种数据修订号如数据库 row_version=18，用于识别同一商品哪一版内容更新。把 schema 版本和数据修订号混成一个字段，会让迁移和日常更新的职责不清。先写清值格式、键格式、修订来源和可容忍陈旧时间。

图解：商品缓存 v1→v2 迁移

沿箭头逐步核对输入、变换和输出；下面的推演可以逐步切换。

一次从 v1 到 v2 的上线

旧实例只读写 v1；先发布可读 v1 和 v2、但只写 v1 的兼容版，验证新解析器；再逐步让新版实例读写 v2。v2 首次未命中时从数据库构造新格式，而不是盲目把 v1 字节复制过去。观察 v2 命中率、数据库回源量和字段完整性后，扩大新版本比例。等所有旧实例退出且回滚窗口结束，再停止维护 v1，随后按 TTL 或受控清理让旧键消失。

具体顺序取决于应用是否允许双读和双写。若 v2 缺失就回退读 v1，应明确旧值能否安全转换；若不能，不应为了命中率返回结构不完整数据。发布时还要核对所有消费者，包括定时任务、后台管理和异步消息处理器，避免隐藏的旧代码继续写 v1。

逐步推演

隔离格式

v1 与 v2 使用不同命名空间。

灰度新读

v2 miss 从权威数据库构建，不盲拷 v1 字节。

双重失效

更新商品时覆盖仍活跃的两套读路径。

退出旧版

过回滚窗口后渐进清理旧键与监控。

更新和失效仍要覆盖两套键

后台把商品 42 的价格改为 90，数据库事务成功后需要使 v1、v2 中相关缓存不再被错误使用。迁移期间可同时失效两套键，或让旧实例停写并逐步退出；若只删 v2，旧实例仍从 v1 返回 100。缓存旁路模式中的并发读写竞态仍存在：读线程从数据库读到旧值、更新线程删键后，读线程又把旧值写回。版本检查、延迟再删或短 TTL 等策略可降低风险，最终选择要看一致性要求。

若用 `product:42:rev18` 这类数据版本键，读取者必须先知道当前修订号；版本指针本身又需要可靠更新。不能因为键名含 `rev18` 就宣称强一致。每个旧修订键也要设置 TTL 或有清理计划，否则频繁更新会让缓存占用无限增长。

对象版本解决什么没有解决什么
schema 命名空间 v1/v2新旧序列化格式隔离商品内容是否最新
数据修订号 rev18识别内容修订先后当前修订号的可靠发现
TTL为旧键设置最终回收界限更新后立即一致
灰度比例控制新键冷启动回源并发读写竞态

缓存雪崩与回源预算

上线时几百万个 v2 键都是冷的，如果所有流量瞬间切换，新版每次都打数据库，可能把后端压垮。可以灰度新读路径、按热点集合预热、限制每秒回源并为热点 miss 合并并发构建。预热也需基于数据库当前版本，并设置随机化 TTL，避免所有预热键同时到期。观测除命中率外还要看回源 QPS、数据库 P99、缓存写入量和旧键内存占用。

不要为追求 100% 命中率把过期旧值无限续命。若商品价格用于支付，结算环节应再次从权威数据确认价格与库存；展示层可容忍短暂陈旧，交易正确性不能完全委托给缓存。

回滚时的选择

新版上线后若发现 v2 格式有 bug，旧代码回滚可能仍可读取 v1；但若迁移过程中已经停写 v1，回滚后 v1 可能陈旧。回滚方案可选择“旧版从数据库重新构建 v1”或“在迁移窗口双重失效、必要时双写”，并明确数据库查询容量。不能只看应用镜像可回滚，忽略缓存状态与消息消费者版本。

回滚演练应在 v2 已经运行一段时间、v1 键已有部分过期的状态下做，检查价格更新是否准确、回源是否可承受以及旧解析器是否遇到新格式。安全清理旧键时优先使用有范围的扫描和渐进删除，避免一次性阻塞或误删相似前缀。

验收一条完整时间线

建立商品 42，v1 价格 100；发布兼容版和 v2 版，确认两格式独立；把数据库价格改为 90，检查两种应用都不会长期读出 100；让 v2 首次冷启动，观察回源峰值；再回滚一部分实例，检查旧路径仍能正确构建。最后按清理策略统计旧键数量与占用，不把临时迁移负担变成永久内存泄漏。

监控最好按 schema 版本分别记录命中、反序列化失败、值缺字段、回源和写入；若只看总命中率，新旧版本问题会互相掩盖。版本迁移的成功标准是结构兼容、数据新鲜度与容量三者都在约定范围。

Key 设计的规范与陷阱

原则好例子坏例子原因
业务前缀order:detail:123123不同类型 key 冲突
含版本v2:user:profile:88user:88结构变更时无法平滑迁移
长度可控< 100 字节把整个 SQL 当 key内存与网络开销
不含易变值product:1001product:1001:ts:1699...每次都是新 key，命中率为 0
用冒号分层app:entity:id:fieldapp_entity_id_field可读性 + 便于批量扫描

最隐蔽的坑：key 里带了时间戳、随机数、用户 IP 等易变值。结果是每次请求都是新 key，缓存永不命中，而且旧 key 还会堆积占满内存直到 LRU 淘汰。排查方法：看 INFO keyspace 的 key 总数是否持续增长且不回落。

版本化迁移：无缝切换结构

当缓存值的结构要变（如 JSON 加字段、序列化方式从 JSON 换 Protobuf），不能简单地全量删除——那会造成缓存击穿。

版本化迁移

# 版本化 key 的平滑迁移流程
# v1: order:detail:123        （旧结构）
# v2: v2:order:detail:123     （新结构）

def get_order(oid):
    # 1) 先读新版本
    v = redis.get(f"v2:order:detail:{oid}")
    if v is not None:
        return deserialize_v2(v)
    # 2) 新版本没有，尝试读旧版本并转换
    old = redis.get(f"order:detail:{oid}")
    if old is not None:
        obj = deserialize_v1(old)
        redis.setex(f"v2:order:detail:{oid}", ttl, serialize_v2(obj))
        return obj
    # 3) 都没有，查库并写新版本
    obj = db.query(oid)
    redis.setex(f"v2:order:detail:{oid}", ttl, serialize_v2(obj))
    return obj

# 迁移期结束后，一次性清理 v1（用 SCAN 而非 KEYS！）
#   redis-cli --scan --pattern 'order:detail:*' | xargs -L 1000 redis-cli DEL
步骤动作风险
1. 双写新代码同时写 v1 与 v2写入开销翻倍（短暂）
2. 双读先读 v2，miss 则读 v1 并回填逻辑复杂度上升
3. 观察确认 v2 命中率达标（> 90%）命中率低说明有问题
4. 停写 v1去掉 v1 的写入回滚需重新双写
5. 清理 v1用 SCAN 分批删，限速直接 KEYS 会阻塞

绝对不要用 KEYS 命令：它是 O(N) 且阻塞单线程，百万 key 时会卡住整个 Redis 数秒。批量删除一律用 SCAN + 分批（每批 1000 个），并控制速率。

批量失效的三种方案

方案做法优点缺点
按前缀扫描SCAN 匹配后逐批删无需额外结构慢，百万级要分钟级
标签集每个标签维护一个 Set 存所有 key秒级批量失效Set 本身占内存，需维护
版本号前缀key 里嵌版本号，换版本即全失效零成本瞬间失效只能整体失效，无法精细

标签集实现

# 方案 2：标签集实现（适合按维度批量失效，如“某商家所有商品”）
def set_with_tag(key, val, tags, ttl=3600):
    pipe = redis.pipeline()
    pipe.setex(key, ttl, val)
    for t in tags:
        pipe.sadd(f"tag:{t}", key)          # 记录该标签下的所有 key
        pipe.expire(f"tag:{t}", ttl + 86400)  # 标签集比数据多活一天
    pipe.execute()

def invalidate_tag(tag):
    keys = redis.smembers(f"tag:{tag}")
    if keys:
        for i in range(0, len(keys), 1000):    # 分批删，避免大命令阻塞
            redis.delete(*list(keys)[i:i+1000])
    redis.delete(f"tag:{tag}")

# 权衡：标签集让失效从 O(N 全库扫描) 降到 O(该标签下的 key 数)
# 代价是每个 key 要维护额外的 Set 成员，内存约增加 10~20%

自检 Q&A

Q：缓存命中率低，怎么定位是哪些 key 造成的？

A：三步——① 开命中率监控（INFO stats 的 keyspace_hits/misses）；② 用 redis-cli --hotkeys（需开启 maxmemory-policy=allkeys-lfu）或 MONITOR 采样看访问模式；③ 重点查是否 key 里嵌了易变值（时间戳、随机数）。这类问题占命中率低成因的大半，而且从代码看很难发现，必须看实际 key 内容。

Q：大 key 删除会阻塞吗？

A：会。DEL 一个百万元素的集合需要释放大量内存，耗时可达数十毫秒到秒级，期间整个 Redis 阻塞。Redis 4.0+ 用 UNLINK（异步删除，后台线程回收内存）替代；4.0 以下只能分批删（如 HSCAN 每次删 100 个）。另外要注意过期删除也可能产生尖刺——大量 key 同时过期时，Redis 的主动过期扫描会占用 CPU。

Q：缓存版本迁移时，新旧代码同时在跑怎么办？

A：这就是必须双写双读的原因。灰度期间新旧实例并存，新实例写 v2 也能读 v1，旧实例只认 v1——只要保证新实例写数据时两套都写，就不会出现一半数据在新一半在旧、互相读不到的情况。迁移完成后先停旧实例的写入，观察 v2 命中率稳定后再清理 v1。回滚也很简单：把读顺序换回先 v1 即可。

Q：key 太多导致内存满了，优先删哪些？

A：先看淘汰策略。noeviction（默认）会直接报错，生产应设为 allkeys-lru（对所有 key 做 LRU）或 volatile-lru（只对设了 TTL 的）。然后用 redis-cli --bigkeys 找大 key，用 INFO keyspace 找 key 数最多的库。另外检查是否有该设 TTL 却没设的 key——永久 key 累积是最常见的内存泄漏来源，应当建立规范：缓存 key 一律带 TTL。

自检

把 key 从 product:v1:42 改成 product:v2:42，能自动保证新价格不会读到旧值吗？

不能。schema 命名空间只隔离格式；价格更新仍需覆盖所有活跃读路径的失效和回填策略。
