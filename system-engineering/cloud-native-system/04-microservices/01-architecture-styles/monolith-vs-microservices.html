单体架构 vs 微服务

一张决策图说清两种主流架构的边界、取舍与适用场景。

核心区别 Monolith vs Microservices

单体关注『一个应用内怎么分模块』，微服务关注『多个应用间怎么协作』

微服务不是『把单体拆小』这么简单——它把『模块边界』升级成了『进程边界 + 网络边界 + 团队边界』，代价是引入了分布式系统的所有复杂度（网络、一致性、可观测性）。

微服务的隐性成本 Hidden cost

  • 网络开销：一次本地函数调用变成一次 RPC，延迟与失败率上升。
  • 分布式事务：跨服务一致性要靠 Saga、TCC、消息最终一致。
  • 运维复杂度：服务发现、配置中心、链路追踪、灰度发布缺一不可。
  • 数据孤岛：每个服务自管数据库，跨服务查询需 CQRS / 聚合层。

面试高频问答

Q：如何向面试官解释『为什么不用微服务』？
A：先说业务规模与团队规模：在域模型简单、团队小、迭代快的早期，单体的强一致和零分布式复杂度是优势；微服务带来的网络、一致性与运维成本在小规模下是净负担。强调『架构服务于当前阶段，而非追潮流』。
Q：服务拆多细合适？
A：以『领域边界 + 团队边界』为准，一个服务对应一个可独立部署、可独立演进的限界上下文；拆太细会陷入分布式调用地狱，一般一个团队维护 2~5 个服务较合理。
Q：单体就一定会变成『大泥球』吗？
A：不会。单体内部用清晰的模块边界（如 DDD 分层、包依赖约束）也能长期保持健康；『大泥球』源于缺乏边界意识，而非单体本身。
