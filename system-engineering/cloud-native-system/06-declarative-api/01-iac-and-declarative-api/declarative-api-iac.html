声明式 API 与基础设施即代码

只说"要什么"，不说"怎么做"——云原生自愈能力的根本来源

声明式 APIIaC控制循环TerraformOperator
① 命令式 vs 声明式 ② 控制循环 ③ K8s 中的体现 ④ 基础设施即代码 ⑤ 工具选型 ⑥ 常见疑问
一句话总结：命令式 API 告诉系统"怎么做"（开三台、装 Nginx、改配置）； 声明式 API 只描述"要什么"（我要 3 个 Nginx 副本、镜像是 x）。 系统通过控制循环持续比对"期望状态"与"实际状态"，自动把实际向期望调谐—— 这正是 Kubernetes 自愈、弹性伸缩等能力的根本来源。

01命令式 vs 声明式

维度命令式（Imperative）声明式（Declarative）
表达内容步骤与动作期望的终态
典型语句kubectl run nginx、kubectl scale --replicas=3spec.replicas: 3 写进 YAML 后 apply
谁负责收敛人：每步都要正确执行系统：持续调谐
故障后行为需人工介入重新执行自动重建/恢复
重复执行可能重复生效或报错（非幂等）幂等，结果一致
可审计性只有操作历史，难知当前状态如何形成清单即文档，状态一目了然
适合场景临时调试、一次性操作生产环境的标准方式

02控制循环：声明式的执行引擎

K8s 中每个控制器（Controller）都遵循同一个模式：

幂等地反复执行，直到实际状态收敛到期望状态
图 2：Observe → Diff → Act 的调谐循环
为什么必须幂等？因为控制循环会被反复执行（且可能并发、可能中断重启）。 每次执行的动作必须"重复做多次结果一样"，否则系统会在循环里震荡或产生重复副作用。 这也是声明式 API 要求"描述终态"而非"描述增量"的原因。

03在 Kubernetes 中的体现

# 声明式：只描述"我要 3 个副本跑 nginx:1.25"
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
spec:
  replicas: 3                      # ← 期望状态（desired state）
  selector:
    matchLabels: { app: nginx }
  template:
    metadata:
      labels: { app: nginx }
    spec:
      containers:
        - name: nginx
          image: nginx:1.25
          resources:
            limits: { cpu: "500m", memory: "512Mi" }
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler         # 声明式自动伸缩
metadata:
  name: nginx
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: nginx }
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } }

写好后 kubectl apply -f deploy.yaml： Deployment 控制器负责维持 3 个 Pod，HPA 控制器根据 CPU 调整 replicas， 人只改声明，其余全部自动。

Operator：声明式范式的延伸

Operator = 自定义资源（CRD）+ 自定义控制器。 它把"运维某个复杂软件的经验"编码成控制器，让用户用声明式方式管理有状态服务：

# 声明"我要一个 3 节点的 PostgreSQL 集群"，Operator 负责其余一切
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: pg-cluster
spec:
  instances: 3
  storage: { size: 100Gi }
  # 控制器自动处理：主从选举、备份、故障切换、版本升级

常见 Operator：Prometheus Operator、cert-manager、CloudNativePG、Strimzi（Kafka）、Elastic Cloud on Kubernetes。

04基础设施即代码 IaC

把"声明式"思想从应用部署推广到基础设施本身： 网络、虚拟机、数据库、负载均衡都用代码声明，版本化管理。

✅ 可复现

同一份代码随时重建整套环境， 灾备和多区域部署不再是体力活。

📝 可评审

基础设施变更走 PR 评审，与代码同流程， 避免"某人悄悄改了安全组"。

🔍 可审计

Git 历史完整记录谁在何时改了什么， 满足合规与溯源要求。

🔄 可回滚

配置出错时 revert commit 即可， 比手工找差异快且可靠。

  cidr_block = "10.0.0.0/16"
  tags = { Name = "prod-vpc" }

  vpc_config {

  }
}

# 工作流：terraform plan（预览变更）→ review → terraform apply（执行）
# state 文件记录实际状态，是 plan 能算出差异的关键
Terraform 的"声明式"与 K8s 的差别： Terraform 是执行式声明——apply 时计算差异并执行，执行完就结束， 之后若有人手工改了云资源，Terraform 不会自动纠正（除非再次 apply）。
K8s 是持续调谐式声明——控制器常驻运行，持续检测并自动纠偏。
理解这个差异，就明白为什么 GitOps 在 K8s 层用 ArgoCD（持续调谐）， 而基础设施层用 Terraform（执行式）是常见组合。

06常见疑问

Q：为什么 K8s 推荐 apply 而不是 create/run？
A：create 是命令式且不幂等（重复执行会报错"已存在"）； apply 是声明式且幂等（重复执行结果一致）， 并且能表达"这份清单是期望状态"，支持后续持续调谐与 GitOps。 生产环境应统一用 apply（或由 GitOps 工具代为 apply）。
Q：声明式 API 有什么代价？
A：① 抽象有学习成本——要理解资源模型与控制循环，不如敲命令直观； ② 调试更绕——出问题时得查"期望 vs 实际"的差异在哪一环没收敛； ③ 状态存储是关键依赖——etcd 挂了整个集群的期望状态就丢了，因此 etcd 的高可用至关重要。
Q：声明式和命令式哪个更好？
A：不是优劣关系，是适用场景不同。 临时调试、救急时用命令式（快）； 所有需要长期维持的状态、需要自愈与审计的生产环境，一律用声明式。 这也是云原生的核心主张之一。
