🔗 多级缓存的难题：本地缓存怎么失效

本地缓存快但无法中心化失效，各节点可能持有不同版本的数据——这是多级缓存的核心难点。

先建立直觉：各人手里的小抄

Redis 是墙上那块公共白板（中心化，改了大家都看到）。本地缓存是每个人手里的小抄（进程内，快，但各自一份）。

问题来了：白板上的内容改了，你没法瞬间把所有人的小抄都改掉。于是有人手里的还是旧的。这就是本地缓存的根本困境——快，是因为它在本地；不一致，也是因为它在本地。

本质矛盾：中心化缓存（Redis）可以主动失效，但每次访问要跨网络；本地缓存零网络开销，但无法被中心化地主动失效。多级缓存的全部设计，都是在「速度」和「一致性」之间找平衡。

多级缓存的结构

四种失效策略

① 短 TTL（最简单，最常用）

给本地缓存设一个很短的过期时间（如 1~10 秒）。不一致窗口最多就是 TTL 的长度。

为什么这招够用？因为大多数业务能容忍秒级的陈旧。1 秒的 TTL 意味着最坏情况「某个节点看到 1 秒前的数据」，这通常无伤大雅，而换来的是零网络开销的热点读取。

② 消息广播失效（一致性更好）

数据变更时，通过消息队列（Redis Pub/Sub、Kafka、RocketMQ）广播一条「key 失效」通知，所有应用实例收到后删除自己本地缓存里的对应 key。

// 写服务：更新数据库 + 删除 Redis + 广播失效
db.update(data);
redis.del(key);
mq.publish("cache-invalidate", key);

// 各应用实例：订阅并清理本地缓存
mq.subscribe("cache-invalidate", key -> localCache.invalidate(key));
风险：① 消息丢失或延迟 → 不一致仍然存在（只是窗口变小）；② 广播风暴（高频变更会产生大量消息）；③ 需要所有实例都正确订阅，新上线实例要能补数据。所以广播通常要和短 TTL 一起用——TTL 作为兜底。

③ 版本号 / 定时拉取（弱化实时性要求）

本地缓存存数据时带上版本号，另有一个全局版本号。读取时比对（可异步、批量）。适合配置类数据——变更极少，但要求所有节点最终一致。

④ 只缓存「低敏感度」数据

从业务侧规避：只把能容忍陈旧的数据放本地缓存。比如商品描述、文章正文、配置项；而库存、余额、订单状态不放本地缓存，直接读 Redis 或数据库。

策略对比

策略一致性复杂度适用
短 TTL秒级窗口极低绝大多数场景
消息广播毫秒~秒级中（要引入 MQ）一致性要求较高
版本号拉取最终一致中配置类、变更少
只放低敏数据取决于数据低配合以上任一
推荐组合：本地缓存短 TTL（1~10s）兜底 + 消息广播加速收敛 + 只缓存低敏感数据降低风险。三层叠加，既快又稳。

🎯 面试问答

Q：本地缓存和 Redis 缓存怎么配合才对？
A：典型读路径：L1 本地 → L2 Redis → L3 数据库，逐层回源并逐层回填（从数据库查到后写回 Redis，再写回本地）。写路径：更新数据库 → 删除 Redis → 广播通知各实例删除本地缓存。关键原则：删除要从上到下（先中心后本地），回填要从下到上（先本地后中心）。另外本地缓存容量要严格控制，只放最热的数据。

Q：消息广播失效可靠吗？
A：不保证 100% 可靠，只能显著缩小不一致窗口。消息可能丢失（网络问题、实例重启）、可能延迟（消费积压）。所以它不能替代 TTL，必须两者配合：广播负责「尽快收敛」，TTL 负责「兜底保证」。把广播当作唯一手段是危险的——一旦消息链路出问题，会出现长时间不一致且难以察觉。

Q：本地缓存设多长 TTL 合适？
A：取决于业务能容忍多久的陈旧，常见取值 1~30 秒。判断方法：问自己「某个用户看到 N 秒前的数据，会不会造成困惑或损失？」商品描述、文章内容可以放宽到 30 秒甚至几分钟；库存、价格、状态类要压到 1~5 秒；余额、订单这类干脆不要放本地缓存。

Q：多级缓存会不会让问题更难排查？
A：会，这是它真实的成本。同一个 key 可能有三份副本（本地/Redis/DB），出现「数据不对」时要逐层确认是哪一层没更新。缓解：① 在响应里加调试头（如 X-Cache-Level: L1）标明数据来源；② 提供强制穿透的调试参数（?nocache=1）；③ 监控各层命中率与不一致告警。没有这些可观测手段，多级缓存会成为运维噩梦。

四种失效方案的取舍（带数字）

方案失效延迟一致性实现复杂度适用
短 TTL（5~60s）最长 = TTL（秒级）最终一致；窗口内必然读到旧值最低能容忍短暂旧值的一切场景（默认打底方案）
写时广播删除毫秒级好（若消息不丢）中节点数 < 100、有可靠广播通道
Redis Pub/Sub毫秒级取决于通道可靠性低注意：Pub/Sub 不保证送达，订阅者掉线就漏
Redis Stream / Kafka毫秒~百毫秒好（可重放、可回溯）中要求不漏失效消息时的正解
binlog / CDC秒级（含解析延迟）好高已有 CDC 基建；不想侵入业务代码
版本号 / 租约校验多一次读的 RT强中强一致要求；可接受每次多一跳

关键结论：无论上哪种主动失效，短 TTL 都必须保留作为兜底。主动失效负责「快」，TTL 负责「消息丢了也不会一直错」。只靠 TTL 会把不一致窗口硬扛在头上；只靠广播则一旦消息丢失就是永久脏数据。

广播风暴估算：QPS(写) × 节点数 = 每秒失效消息数。1000 写 QPS × 200 节点 = 20 万条/秒，远超业务流量本身——所以大规模场景要么走 CDC 中心化下发，要么用版本号懒失效。

参考实现：可靠失效 + 幂等 + 防击穿

关键代码片段

// 1) 本地缓存 + 版本号幂等失效（Go + Caffeine 同理）
type Entry struct {
    Value   any
    Version int64   // 数据版本号，来自 DB 的 update_time 或 binlog
}

// 收到失效消息时：只有消息里的版本 >= 本地版本才失效，避免乱序消息把新值删掉
func (c *LocalCache) OnInvalidate(key string, version int64) {
    c.mu.Lock(); defer c.mu.Unlock()
    if e, ok := c.m[key]; ok && version >= e.Version {
        delete(c.m, key)
    }
}

// 2) 防击穿：同一 key 只有一个协程回源（singleflight）
//    Go:    golang.org/x/sync/singleflight
//    Java:  Caffeine 的 refreshAfterWrite / 或 Guava 的 LoadingCache 自动做
v, err, _ := g.Do(key, func() (any, error) {
    return loadFromDB(key)     // 只有一个请求打到 DB
})

// 3) 空值也要缓存（防穿透），且 TTL 要短
if errors.Is(err, sql.ErrNoRows) {
    c.Set(key, Entry{Value: nil, Version: ver}, 30*time.Second)   // 空值 TTL 30~60s
    return nil, nil
}

// 4) 兜底 TTL 永远保留：即使失效消息全丢，也不会脏超过 TTL
c.Set(key, Entry{Value: v, Version: ver}, 5*time.Minute)
  • 节点重启 / 冷启动：本地缓存是空的，会瞬间把流量全打到下游。要么预热，要么在启动后短时间内走「限流回源」。
  • 时钟回拨：用时间戳做版本号时，NTP 回拨会导致「新版本 < 旧版本」而被丢弃。用 DB 里的自增版本或 update_time 更安全。
  • 失效 vs 更新：广播「删除」比广播「新值」安全——新值可能因为顺序问题覆盖更新的值。
  • 可观测：必须有三个指标——本地命中率、失效消息处理延迟、以及「本地与 Redis 值不一致」的抽样比对告警。
为什么不能只靠 TTL？

TTL 把不一致窗口固定成了 TTL 长度，调小则缓存命中率崩、回源压力涨；调大则业务不能接受。主动失效是为了「平时几乎一致，最坏情况退化为 TTL」。

广播风暴怎么压？

三种：合并（把 100ms 内的失效 key 攒批下发）、只广播 key 前缀/租户维度做粗粒度失效、改成中心化的版本号（本地每次读时比对一次中心版本，而不是每次写都广播）。

本地缓存和 Redis 不一致怎么定位？

加一条「抽样比对」：按 1/1000 的概率读一次 Redis，与本地值比对，不一致就打日志上报。这条链路能在用户投诉前发现问题。
