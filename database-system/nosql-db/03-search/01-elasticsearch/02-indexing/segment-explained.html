4Segment 的文件结构

一个 Segment 包含以下文件 (都在磁盘上)：

index/ [_0] ← Segment _0 是一个目录 _0.tim ← Term Dictionary (词典/倒排表) _0.tip ← Term Index (词典索引，快速定位) _0.doc ← Doc IDs (正排表) _0.fnm ← Field Names (字段定义) _0.nvd ← Norms (字段权重/评分因子) _0.nvm ← Norms Metadata [_1] ← Segment _1 [_2] ← Segment _2
.tim
倒排表 - 词 → [DocId1, DocId2, ...] 的映射
查询时根据词找到所有包含该词的文档
.tip
词典索引 - FST 数据结构，快速定位 Term
不用遍历整个 .tim，用 FST 跳转
.doc
正排表 - DocId → 原始字段值
查询时根据 DocId 拉取原始文档内容

5总结

🎯 理解要点

Segment 不是一种数据格式，而是一个索引"包"

• Memory Buffer = 原始数据，还没建索引
• Segment (内存) = Buffer 数据经过分词+建索引，在 JVM 里
• Segment (磁盘) = 刷到磁盘的 Segment，持久化
• Merge = 把多个小 Segment 合并成大 Segment

为什么内存和磁盘都有?
因为它们是同一套数据结构的不同生命周期阶段：
内存中先建索引 → 可搜索 → 刷到磁盘持久化

内存
磁盘
索引已建立

segment 是什么：Lucene 的最小检索单元

一个 Lucene 索引（也就是 ES 的一个分片）并不是一个大文件，而是由若干个 segment 组成的集合。查询时，请求会依次查遍所有 segment，再把各自的结果汇总。

段数量直接影响查询成本，merge 是唯一的收敛手段
写只在最尾部追加新文档进 buffer，refresh 后成为新段，从不修改旧段。
删除是标记在 .del 里记一笔，查询时跳过这些文档。
更新 = 删 + 增本质是写入一个新的版本文档。
唯一anian段的回收方式参与 merge，被重写时不包含已删除文档。

一个 segment 里到底有哪些文件

Lucene 把不同类型的数据拆成不同类型的文件，各司其职。记住这几类就够了：

类别作用典型后缀什么时候用
词项索引在词典里快速定位词项的跳表前缀.tip查找某个词是否存在
词项词典所有词项及其在倒排表中的位置.tim取得该词的 posting list
倒排表文档 id、词频、位置信息.doc / .pos搜索的核心路径
Doc Values按文档组织的列式存储.dvd / .dvm排序、聚合、脚本取字段
Stored Fields原始文档内容.fdt / .fdx返回结果时取正文
Norms字段长度等归一化因子.nvd / .nvm算分
删除标记哪些文档已被删除.del / .liv查询时过滤

理解「倒排 vs Doc Values」的方向差别很重要：倒排是词 → 文档，用于搜索；Doc Values 是文档 → 值，用于排序与聚合。Elasticsearch 之所以能高效地做 terms aggregation，正是因为它在写索引时就额外准备好了一份列式的 Doc Values。

refresh、flush、merge 三件事对照

动作触发条件做了什么对性能的影响
refresh默认每 1 秒；或 buffer 满了把内存 buffer 变成一个新的可搜索 segment让数据「变得可搜索」；太频繁会产生大量小段
flushtranslog 达到阈值 / 定时 / 手动把数据 fsync 到磁盘并清空 translog保证持久化；不直接产生新段
merge后台策略自动挑段合并把多个小段重写成更少的大段释放磁盘、降低查询开销；IO 密集

translog 为什么必须存在：refresh 之后数据虽然能被搜到，但它还在操作系统的文件系统缓存里，断电就丢。translog 是一份追加写的日志，用来在崩溃后重放那些还没进盘的写入。

translog 的持久化策略 request（默认推荐）：每次写请求都要等 translog fsync 成功才返回 → 最安全，代价是每个写请求多一次磁盘同步 async：按固定间隔 fsync → 更快，但宕机时可能丢失最后几秒的写入 选择建议：数据重要就 request； 日志类可重建数据可以适当放松换取吞吐。

段管理的四条工程经验

  1. 别让单索引的段数量失控。频繁 refresh + 大量小文档会堆出几千个段，每次查询都要遍历全部 —— 这是「明明数据量不大却很慢」的常见原因。
  2. 写多的时候放宽 refresh_interval。日志、指标类索引把它调到 30s 甚至更长，能立刻降低 merge 压力。
  3. 批量删除后若急需回收空间，主动触发一次合并。但要挑业务低峰，因为它是 IO 密集操作，且过程中峰值磁盘占用会临时升高。
  4. 单个分片不宜过大也不宜过多。经验上把单分片控制在20~50GB 量级；过大让恢复与 move 变慢，过少则丧失并行度 —— 段只是其中的原因之一。

一个诊断技巧：查看每个分片的 segments 统计，如果看到段数量成百上千、其中大量是几 KB 的小段，几乎可以确定瓶颈就在段管理上 —— 调整 refresh 与合并策略，比扩容节点有效得多。

深入自检

为什么 Lucene 不直接修改已有文档，非要写成新版本？

因为随机写会让缓存失效、并发读需要加锁、还要处理写失败的部分状态。写成新版本保持了「追加写 + 不可变」的模型：不需要锁，可以被操作系统缓存友好地顺序读，写失败只影响尚未生效的新段。这套设计让 Lucene 的读取路径极其干净，代价是删除/更新需要靠后台合并来回收空间。

merge 的时候查询会受影响吗？

会受影响但不会中断。合并期间新旧段同时存在，查询仍可以访问旧段；合并完成后新段接管，旧段被释放。代价是磁盘 IO 与 CPU 被合并占用，查询延迟可能上升，并且磁盘空间在合并过程中会出现临时峰值。生产环境通常会限制合并的吞吐（节流）来保护查询延迟。

.del 文件会不会一直变大？

不会。.del 是与具体 segment 绑定的：当这个 segment 参与合并、被重写成新段时，标记为删除的文档不再被写入，旧的 .del 也随旧段一起删除。所以频繁删除的索引只要能正常触发 merge，标记文件就不会无限增长 —— 反过来，长期不合并会让被删数据一直占着磁盘。

Doc Values 会不会让索引变得很大？

会增大磁盘占用，但换来的是聚合与排序不必再依赖原始 fielddata 内存缓存（那种做法极易 OOM）。多数情况下这份空间代价是值得的：Doc Values 存在磁盘上、由操作系统缓存，内存压力小得多。对确定不需要排序/聚合的字段，可以显式关闭以节省空间。
