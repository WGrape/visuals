Python asyncio Event Loop 核心运行流程

Single-Threaded Asynchronous I/O — 事件循环每一次迭代的工作步骤

本页只展示 Python asyncio 的迭代流程；跨 Python、JavaScript 与 Redis 的事件模型比较见事件循环跨运行时比较。

事件循环在做什么

事件循环就是一个不断重复的过程：取一个就绪事件 → 执行它对应的回调 → 再取下一个。所有并发都发生在「等待」的时间里，而不是同时执行。

事件循环：就绪队列 + I/O 多路复用
单线程没有锁竞争，也没有线程切换开销。
await 让出协程在 await 处主动交还控制权。
靠 I/O 多路复用等待由操作系统通知，不空转。
阻塞是禁忌一处阻塞，整条循环停摆。

协程、任务与 future 的关系

import asyncio async def fetch(url): print('start', url) await asyncio.sleep(1) # 让出控制权，循环去干别的 print('done', url) return url async def main(): # ① 直接 await：串行，总共约 3 秒 await fetch('a'); await fetch('b'); await fetch('c') # ② 包装成 Task：并发，总共约 1 秒 tasks = [asyncio.create_task(fetch(u)) for u in ['a','b','c']] results = await asyncio.gather(*tasks) # ③ 带超时与逐个完成 try: await asyncio.wait_for(fetch('d'), timeout=2) except asyncio.TimeoutError: print('timeout') for coro in asyncio.as_completed(tasks): r = await coro asyncio.run(main()) # 入口：创建并运行事件循环
概念是什么要点
协程 coroutineasync def 定义的函数调用它只是创建对象，不会执行
await等待并让出控制权只有 await 处才会切换
Task被调度执行的协程create_task 后才会真正并发跑
Future代表「将来的结果」Task 是 Future 的子类
gather并发运行并收集结果顺序与传入一致
as_completed谁先完成先拿到谁顺序不定

最常见的误解：写了 async def 不等于并发。只有把协程包装成 Task（或用 gather）并 await，才会真正并发执行。

常见坑与正确做法

阻塞调用混入

这是 asyncio 最致命的坑。

# ❌ 在协程里用同步的 requests / time.sleep async def bad(): time.sleep(1) # 卡住整个事件循环！ r = requests.get(url) # 同样阻塞 # ✅ 方案一：用 async 库 async def good(): await asyncio.sleep(1) async with aiohttp.ClientSession() as s: async with s.get(url) as r: return await r.text() # ✅ 方案二：丢到线程池 async def ok(): loop = asyncio.get_running_loop() return await loop.run_in_executor(None, requests.get, url)

忘记 await

写了协程却没 await，等于什么都没做。

# ❌ 没有 await，也不会报错 async def main(): fetch('a') # 只是创建了协程对象 asyncio.create_task(fetch('b')) # 没等它完成 # ✅ async def main(): await fetch('a') t = asyncio.create_task(fetch('b')) await t

开启调试模式或严格检查未等待的协程。

并发控制

  • 用 Semaphore 限制并发数，避免打爆下游
  • 给每个请求设超时（wait_for）
  • 用 TaskGroup（3.11+）统一管理子任务
  • 取消要能被感知，别吞掉 CancelledError
sem = asyncio.Semaphore(20) async def limited(u): async with sem: return await fetch(u) # Python 3.11+ 的 TaskGroup async with asyncio.TaskGroup() as tg: for u in urls: tg.create_task(limited(u))

深入自检

asyncio 比多线程快吗？

在高并发 I/O 场景下通常更好：协程切换成本远低于线程，内存占用也小得多。但如果并发量不大，两者差别不明显；而 CPU 密集任务两者都不能利用多核，需要用多进程。

为什么一个阻塞调用会拖垮整个服务？

事件循环是单线程的，它按顺序执行就绪回调。任何一处同步阻塞（time.sleep、同步网络库、重计算）都会让循环停在那里，其余所有协程都得不到执行。因此异步代码必须全链路使用 async 库，或把阻塞调用丢到线程池。

create_task 和直接 await 有什么区别？

直接 await 会立即等待该协程完成，期间不会执行其它协程，效果是串行；create_task 把协程注册为独立的任务加入循环，之后 await 它时其它任务也能继续推进，从而实现并发。

什么时候不该用 asyncio？

任务以 CPU 计算为主时（应用多进程）；依赖的库没有 async 版本且不便改造时；并发量很小、同步写法更清晰时。异步会侵入整条调用链，收益不足时反而增加复杂度。

asyncio 里还需要锁吗？

需要的情况少很多，因为单线程内不存在「执行到一半被切换」的问题——只有在 await 处才会让出。但如果一段逻辑跨越了 await 且涉及共享状态的一致性，仍需要 asyncio.Lock 来保护。

为什么一个阻塞调用会毁掉整个 asyncio 程序：事件循环是单线程的，所有协程在同一个线程里被调度。任何一处执行了 time.sleep(1) 或同步 requests.get，整个循环就停 1 秒——不只是这个协程慢，所有协程都停。这是 asyncio 最常见的线上事故。

asyncio 排障清单

症状原因处理
整个程序周期性卡顿某处同步阻塞（sleep、requests、pymysql、CPU 密集计算）PYTHONASYNCIODEBUG=1 定位；改用 async 库或 run_in_executor
RuntimeError: no running event loop在同步上下文里调了 asyncio.run 之外的 API入口统一用 asyncio.run(main())
Task was destroyed but it is pending任务没被 await，程序结束时被丢弃保存 task 引用并 await；或用 asyncio.TaskGroup（3.11+）自动等待
并发上去后大量超时下游被打爆 / 连接池不够加 Semaphore 限速；aiohttp 的 TCPConnector(limit=100)
CPU 密集任务没加速GIL + 单线程，协程不解决 CPU 并行用 ProcessPoolExecutor 或多进程
协程泄漏，内存涨task 创建后无人等待也无引用用 TaskGroup；监控 asyncio.all_tasks() 数量
await 后代码没执行协程对象没被调度（只写了 coro() 没 await）会有 coroutine was never awaited 警告，别忽略
  • 协程 vs 线程怎么选：IO 密集且连接数上万 → 协程；需要利用多核 → 多进程；要调用大量同步库且改造成本高 → 线程池。
  • asyncio 的并发上限：理论可开上万协程，但实际受限于文件描述符（ulimit -n，常 1024）和下游服务的承受能力，所以一定要限速。
