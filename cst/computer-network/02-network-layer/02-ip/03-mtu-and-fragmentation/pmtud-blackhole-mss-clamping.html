PMTU 黑洞与 MSS 调整：小包能通，大请求为何卡住

用 VPN 隧道后的大报文故障解释 DF、ICMP Packet Too Big、TCP MSS 和 UDP 的区别。

路径上最窄的链路决定上限

主机网卡 MTU 为 1500 字节，并不表示去任何目的的 IP 包都能放下 1500 字节。经过 VPN 或其他隧道时，外层头部会占用空间；如果隧道实际可用 IP 包大小为 1420，超过它的报文需要源端缩小、由允许的设备分片，或被丢弃并返回差错。PMTU 是整条路径的有效上限，不等于本地接口 MTU。新旧路径可能不同，不能拿一次探测值永久套用。

IPv4 包设置 DF 时，中途路由器不能分片，若下一跳 MTU 不够，应丢弃并返回 ICMP Fragmentation Needed；IPv6 路由器不在中途分片，会向源端返回 ICMPv6 Packet Too Big。源端收到合适反馈后减小发送尺寸。若防火墙把这类 ICMP 全部挡掉，源端可能反复发送过大的包，于是形成 PMTU 黑洞。

为什么小请求正常、大请求挂住

TCP 三次握手的 SYN、SYN-ACK 通常很小，可以顺利通过；一个短 GET 和小响应也可能成功。等应用发送较大响应或上传数据，端点按错误估计发出大 IP 包，隧道设备无法通过，反馈又被挡住。用户看到的是“网站首页可打开，下载或登录提交卡住”，也可能表现为 TLS 握手阶段证书消息较大时超时。单凭 ping 小包成功不能排除 MTU 问题。

抓包时在隧道入口看到大包发出、出口看不到，且没有可用的 ICMP Packet Too Big 回到源端，是重要线索。不过网卡分段卸载可能让本机抓包显示比线上 MTU 大得多的“巨包”，要在合适抓包点或关闭相关卸载做受控验证，不能把本机虚拟大包直接当成真实线上违规帧。

逐步推演

小包通过

握手和短请求低于路径 MTU，表面正常。

大包受阻

隧道额外开销使 1500 字节包超过有效上限。

反馈丢失

必要 ICMP 被挡，源端不知道应减小。

修复验证

放行 PTB、核对 MTU，必要时调整 TCP MSS。

用数字算 TCP MSS

假设隧道后的有效 IP MTU 是 1420。若走 IPv4 且基本 IP 头 20 字节、TCP 头 20 字节，不计选项时 TCP MSS 上限约 1380 字节；若走 IPv6，基本头 40 字节、TCP 头 20 字节，则约 1360 字节。TCP MSS 指 TCP 数据部分，不是 IP 包或以太网帧总长；实际选项、扩展头、隧道嵌套可能进一步减少可用空间。

MSS 协商发生在 TCP SYN 阶段，告诉对端愿意接收的最大 TCP 段数据。中间设备可以在受控环境中做 MSS clamping，把经过隧道的 SYN 宣告值调小，缓解端点不知道额外封装开销的问题。但只改 TCP MSS 不会自动修复 UDP、QUIC 或 ICMP 大包，也不应替代正确放行 PMTU 所需的 ICMP。

探测与反馈的限制

传统 PMTUD依赖网络返回差错，反馈被过滤就会卡住；Packetization Layer PMTUD 等方法可通过端到端不同包大小试探路径，但具体支持依协议实现。QUIC 等运行于 UDP 的协议也必须处理数据报大小与路径变化，不能因为没有 TCP MSS 就忽略 MTU。对路径中不同链路，探测包是否带 DF、载荷大小、IPv4/IPv6 和所走路由都要一致。

ping 工具的 `-s` 等参数常表示 ICMP 载荷长度，还要加 IP 和 ICMP 头才是实际 IP 包大小。算题前先看工具定义；把“ping 发送 1400 字节”直接等同于 MTU=1400 是常见误差。

修复顺序

先确认隧道与物理接口的实际 MTU、封装开销和故障路径；再核对 ICMPv4 Fragmentation Needed 或 ICMPv6 Packet Too Big 是否被正确发送、转发和接收。若业务紧急且主要是 TCP，可在隧道入口谨慎设置 MSS clamping，同时留证据验证大流量恢复。长期仍应修复差错报文过滤或路径 MTU 配置错误。

修复后分别测试短请求、大响应、文件上传、IPv4、IPv6 和 UDP/QUIC。只用浏览器刷一个小页面无法证明全部协议都恢复。监控可关注大包丢弃、ICMP PTB、重传和应用超时分布。

一次复盘

记录正常路径和故障路径的逐跳 MTU、隧道类型、DF/Packet Too Big 报文以及客户端协商 MSS。若防火墙变更导致反馈丢失，复盘应把“允许哪些必要 ICMP 类型”写成规则，而不是笼统放开所有 ICMP 或继续全禁。若只靠调小 MSS 止损，要标出 UDP 仍可能失败的剩余风险与后续修复安排。

教科书里分片似乎能解决一切，但分片会带来额外开销与丢失放大，IPv6 中途更不允许路由器代分。优先让源端了解可用包大小，通常比依赖中途分片更稳健。

自检

把 TCP MSS 调小后，UDP/QUIC 大包问题一定消失吗？

不会。MSS 只约束 TCP 数据段，UDP/QUIC 仍需各自的包大小控制与路径 MTU 处理。
