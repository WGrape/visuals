定义 proto、生成、配置与 etcd 注册、鉴权拦截器、grpc status 错误处理。

go-zero 的 RPC 基于 gRPC + protobuf，从 proto 一键生成代码。这里走完『定义→生成→配置→中间件→错误处理』的完整链路。

01定义 proto 并生成

用 goctl 从 .proto 生成 pb.go 与 rpc 服务骨架，业务只填方法体。

# 定义 user.proto
syntax = "proto3";
package user;
option go_package = "./user";
service User {
  rpc GetUser(GetUserReq) returns (GetUserResp);
}
message GetUserReq { int64 id = 1; }
message GetUserResp { int64 id = 1; string name = 2; }

# 生成代码（需 goctl）
goctl rpc protoc user.proto --go_out=. --go-grpc_out=. --zrpc_out=.
# 生成后填 internal/logic/getuserlogic.go 的 GetUser 方法体

02RPC 配置与启动

etc/user.yaml 里配置监听、etcd 自动注册、超时与限流。zrpc 默认把服务注册到 etcd，调用方靠名字发现。

# etc/user.yaml
Name: user.rpc
ListenOn: 0.0.0.0:8080
Etcd:
  Hosts:
    - 127.0.0.1:2379
  Key: user.rpc
Log:
  Mode: console
# 超时/限流可在代码侧 interceptor 里做
# 启动：go run user.go  或  make run

03拦截器：鉴权/日志/recover

用 grpc.UnaryServerInterceptor 统一处理，避免在每个方法里重复写。recover 拦截器防止单个 panic 拖垮整个进程。

func AuthInterceptor() grpc.UnaryServerInterceptor {
    return func(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo,
        handler grpc.UnaryHandler) (interface{}, error) {
        md, _ := metadata.FromIncomingContext(ctx)
        if len(md.Get("authorization")) == 0 {
            return nil, status.Error(codes.Unauthenticated, "missing token")
        }
        return handler(ctx, req)
    }
}
// 注册：在 srv := zrpc.MustNewServer(c, func(s *grpc.Server){...}) 后
// s.Use(AuthInterceptor(), recovery.Interceptor)

04错误处理与客户端调用

业务错误用 grpc status 表达，客户端按 codes 分支；不要用普通 error 字符串掩盖语义。客户端用 zrpc.MustNewClient 起，直接调生成的方法。

// 服务端返回业务错误
if user == nil {
    return nil, status.Error(codes.NotFound, "user not found")
}

// 客户端
conn := zrpc.MustNewClient(c)               // c 为配置里的 Etcd/Target
client := user.NewUserClient(conn.Conn())
resp, err := client.GetUser(ctx, &user.GetUserReq{Id: 1})
if status.Code(err) == codes.NotFound {
    // 处理未找到
}

05常见坑

  • proto 改了必须重新生成，且 client/server 版本要一致，否则字段对不上。
  • ctx 必须带超时（context.WithTimeout），否则默认无限等待。
  • etcd 没起或 Key 冲突，服务发现会失败，先确认 etcd 连通。
  • 大 payload 注意 gRPC 默认 4MB 单消息上限，需调 MaxRecvMsgSize。
要点：go-zero RPC 把『协议定义→代码生成→服务发现→拦截器』都标准化了，业务只填 logic；出问题先查 etcd 注册与 proto 版本一致性。

第一层 · 概念与判定：go-zero zrpc 适合什么

go-zero 的 zrpc 是内置服务治理的 gRPC 封装（自带超时、限流、熔断、负载均衡、链路追踪）。适合内部微服务间高频 RPC，不想自己拼治理组件时用。

你的场景建议
内部服务互调✓ zrpc 开箱治理
对外暴露 API用 go-zero api 网关
要极致定制传输裸 gRPC 更灵活
一次性小工具✗ 略重

go-zero zrpc 生成与配置

# 从 proto 生成 zrpc 代码
goctl rpc gen -src greet.proto -dir .

# zrpc 服务端配置（etc/greet.yaml）
Name: greet.rpc
ListenOn: 0.0.0.0:8080
Timeout: 3000            # 毫秒
# 限流：单实例最大并发
MaxConns: 10000
MaxCalls: 1000
# 内置熔断默认开启，错误率阈值约 50%

数量级：zrpc 默认超时 3000ms，限流用令牌桶（默认单实例约 1000 并发）；服务发现走内建或 etcd，调用方自动负载均衡。

第三层 · 排障与边界：五个坑

  • 改了 proto 没重新 gen：手改生成目录外的代码被覆盖，或忘了 regen 导致字段对不上——以 proto 为准、改完必须 goctl gen
  • 超时没往下游传：收到 ctx 却自己 new 了一个没超时的 context，治理失效
  • 限流阈值按机器峰值拍脑袋：没结合压测，正常高峰就被拦——用 MaxConns/MaxCalls 按实例容量设
  • 错误码全当失败触发熔断：业务「已处理」的 error 也计入错误率，误熔断——区分可控 error 与系统失败
  • 忘配 tracing/日志采样：出问题没法定位链路，治理有了但可观测没跟上

第四层 · 原理与取舍

go-zero zrpc 和裸 gRPC 怎么选？

裸 gRPC 只给传输（编解码、流控），超时/限流/熔断/ tracing 全要自己接（或引第三方）；zrpc 把这些内建进框架，配置即用、与 goctl 生成流程一体。取舍：要快速落地、团队统一治理 → zrpc；要跨语言/极致定制传输 → 裸 gRPC 更合适。

为什么超时一定要靠 context 一路透传？

因为 go-zero 的超时是挂在 context 上的 Deadline，下游调用读取这个 Deadline 才知道何时该放弃。如果你在 handler 里 new 一个空 context，原请求的超时/取消信号就断了，上游超时了下游还在跑，资源白白耗、还可能雪崩。所以收到 ctx 必须透传给每个下游调用。

MaxConns 和 MaxCalls 分别卡住什么？

MaxConns 限制同时处理的连接/请求总并发（防被打爆），MaxCalls 限制单位时间通过的调用数（令牌桶限流）。前者护资源、后者护容量；两者配合才能既不被连接数拖垮、又不让过量请求穿透到业务逻辑。
