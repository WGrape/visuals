🔑 行键设计

原则、加盐/哈希/反转与反模式

为什么 rowkey 最重要

rowkey 是 HBase 中唯一的索引，它同时决定了：数据如何分布到 Region（避免热点）、如何被高效查询（范围扫描）、以及版本排序。一个糟糕的 rowkey 足以毁掉整个集群的性能和扩展性。

设计原则

原则理由
高基数取值空间大、分散，才能均匀分布到 Region，避免热点
长度适中建议 10~100 字节；过长浪费内存/索引，过短信息不足
把高频查询维度放前面便于按前缀做范围扫描（HBase 只擅长前缀/范围检索）
避免单调递增前缀时间戳/自增 ID 做前缀 → 写入永远落在最后 Region → 热点
必要时打散对单调递增键加盐/哈希/反转，把写压力摊到所有 Region

常用技巧

🧂

Salting 加盐

在 rowkey 前加随机前缀（如 0~9），把连续 key 强制分散到不同 Region；代价是失去全局有序，范围扫描需扫所有 salt 桶。

#️⃣

Hashing 哈希

对部分字段取 hash 前缀，兼顾分散与可按 hash 精确点查（如 userId 取 md5 前 N 位）。

🔁

Reversal 反转

反转字符串/数字（如手机号、时间戳倒序），把变化大的低位放到前面，打散单调前缀。

🧬

组合键

用「高基数维度+时间」拼接：userId + (Long.MAX-timestamp)，既能按用户扫、又把时间打散。

反模式

  • ❌ 用自增 ID / 当前时间戳直接做 rowkey 前缀（经典热点）。
  • ❌ rowkey 过长（如整条 JSON），浪费 Storage/内存与索引。
  • ❌ 用会被频繁更新的字段做 rowkey（rowkey 不可改，改 = 删旧写新）。
  • ❌ 用毫无随机性的单一枚举值（如固定 status）做前缀。

案例

场景糟糕 rowkey推荐 rowkey
时序/监控20260101...（时间戳前缀）(deviceId Hash 前缀) + 时间戳反转
订单orderId（自增）(userId Hash) + (Long.MAX - createTime) + orderId
用户画像userId（可，但注意量级）userId（高基数，已是良好选择）
✅ 口诀：「先想清楚怎么查，再设计 rowkey」——把最常用的查询条件（且是高基数）放到 rowkey 的前缀；如果前缀会单调，就加盐/哈希/反转把它打散。
