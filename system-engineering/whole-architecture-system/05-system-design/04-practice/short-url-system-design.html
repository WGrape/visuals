短链系统设计与实现

把 https://example.com/activity?ref=xxx&id=1234567890 变成 t.cn/Ab3d9F —— 一个看似简单、实则考验「高并发发号 + 低延迟跳转」的经典系统设计。

为什么需要短链 Why Short URLs

短链解决三类问题：节省字数（微博 140 字限制、短信按条计费）、美观易传播（二维码更密、手敲不易错）、统一跳转与统计（可统计点击、做 A/B、随时更换落地页）。其核心就是一个「短码 → 长 URL」的映射表。

图：短链跳转本质是一次「查表 + 重定向」，核心延迟在查表这一跳。

短码怎么来：发号器方案对比

短码本质是「一串碱基（62 进制：0-9a-zA-Z）」。关键诉求：不重复、够短、能高并发生成。下面三种方案各有取舍。

方案思路优点缺点
自增 ID + 进制转换数据库/发号器自增得到 1,2,3…，再转成 62 进制短码（如 1000 → 「g8」）。绝对不重复；短码单调递增、长度可控。自增 ID 易暴露业务量；需解决发号器单点（用号段 / 雪花 ID）。
哈希长 URL
(Murmur/MD5 截断)		对长 URL 哈希后取前 6~8 位作为短码。相同 URL 永远得到相同短码（天然去重）。有哈希冲突，需「冲突则加盐重试」；长尾冲突难处理。
预生成随机池提前批量生成百万个随机短码放入队列，用时 pop 一个。生成与写入解耦；随机无规律、不泄量。要维护码池与「已用/回收」状态。
-- 62 进制转换：十进制 ID → 短码 String chars = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"; StringBuilder sb = new StringBuilder(); while (id > 0) { sb.append(chars.charAt((int)(id % 62))); id /= 62; } return sb.reverse().toString(); // 1_000_000 → "4c92"
💡 类比：短码就像图书馆的「索书号」。书（长 URL）本身很长，但书架只认那一小段编号；读者报编号，管理员（短链服务）立刻找到对应那本书并递给你。

高并发下的存储与缓存

⚡ Redis 扛读

短链读远大于写。code→url 映射全量/热点放 Redis，命中率极高，单跳延迟 < 5ms。

🗄️ DB 落地

MySQL 存全量映射与统计字段（创建时间、过期时间、点击数），Redis 作为缓存层。

📊 异步统计

点击上报走 MQ 异步累加，不阻塞重定向主链路，避免统计拖慢跳转。

⏰ 过期清理

支持 expireAt 字段，过期短码返回 404 或跳默认页；定时任务清理释放空间。

⚠️ 避坑：重定向务必用 302（临时）还是 301（永久）？301 会被浏览器/CDN 强缓存，后续点击不再回源，统计失效且无法更换落地页；需要统计与可换链时用 302。

分布式发号器：避免单点瓶颈

自增 ID 方案要保证「全局唯一且高可用」，常见做法两种：

  • 号段模式（Leaf-segment）：DB 一次性分配一段区间（如 1~1000），服务内存自增发放，用完再申请下一段；DB 压力极小。
  • 雪花算法（Snowflake）：时间戳 + 机器号 + 序列号拼出 64 位 ID，无中心节点、天然分布式；转 62 进制后约 11 位，可通过「时间回拨处理」保证不重复。
-- Leaf 号段：一次取一段，内存发放 UPDATE id_segment SET max_id = max_id + 1000 WHERE biz = 'short_url'; -- 拿到 [old_max+1, old_max+1000] 这段，本地自增即可

🎯 面试问答

Q：短码冲突了怎么办？
A：自增/发号器方案不会冲突（ID 天然唯一）。哈希方案可能冲突——写入时若 code 已存在且对应 URL 不同，则加盐（追加随机字符）重新哈希再试，直到拿到空闲 code。
Q：短链被滥用发钓鱼链接怎么办？
A：加一层「安全检测」——对长 URL 做暗链/黑名单扫描与用户举报机制；高风险链接跳转前加风险提示页；对批量生成行为限流。
Q：如何让短码尽量短？
A：码长 L 与容量关系为 62^L。6 位约 568 亿，足够绝大多数业务；用自增 ID 时，ID 越小码越短，所以高位尽量留给「小 ID」，并优先用更紧凑的发号区间。

容量估算：先算清楚这几个数

问题估算结论
短码多长够用？62 进制：62^6 ≈ 568 亿、62^7 ≈ 3.5 万亿6 位足够（568 亿条）
每天新增多少？假设 1 亿条/天568 亿 / 1 亿 = 可用 1550 年
存储多大？每条记录约 500 B（短码+长链+元数据）1 亿 × 500 B = 50 GB/天，一年 18 TB
读写比例？100:1（典型读多写少）读 QPS 约 10 万，写约 1000
QPS10 万读 → 峰值 30 万（3 倍冗余）需缓存 + 多副本

为什么是 62 进制：0-9 + a-z + A-Z = 62 个字符，在 URL 中无需转义。如果只用数字（10 进制），6 位才 100 万，远远不够。注意别用 + /（Base64 里的）——URL 里要转义，这就是为什么要用“Base62”而不是标准 Base64。

Base62 编码实现

# Base62 编码 / 解码
ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
BASE = len(ALPHABET)          # 62

def encode(num):
    if num == 0: return ALPHABET[0]
    s = []
    while num:
        s.append(ALPHABET[num % BASE])
        num //= BASE
    return "".join(reversed(s))

def decode(s):
    num = 0
    for c in s:
        num = num * BASE + ALPHABET.index(c)
    return num

print(encode(123456789))      # 8M0kX
print(decode("8M0kX"))        # 123456789
print(62 ** 6)                # 56800235584  (568 亿)
print(62 ** 7)                # 3521614606208 (3.5 万亿)

# 发号器方案：自增 ID -> Base62
#   ID=1 -> "1", ID=62 -> "10", ID=568亿 -> "zzzzzz"(6位满)
# 优点：无冲突、长度递增（前期短码更短）
# 缺点：可预测 -> 可被遍历（加盐混淆或随机化解决）

三种短码生成方案对比

方案做法优点缺点
① 发号器 + Base62全局自增 ID → Base62无冲突、长度可控、最简单可预测（可被遍历）
② 哈希（MD5/SHA）长链哈希取前 6 位同一长链得到同一短码有冲突，需处理
③ 随机 + 查重随机 6 位，冲突则重试不可预测高并发下重试多

工业界的标准答案是 ①：发号器（Snowflake / 号段 / Redis INCR）+ Base62，再对可预测性做处理（加固定盐、或把 ID 打散）。方案 ② 的冲突处理很麻烦（要加盐重算，且冲突率随数据量上升——生日悖论：568 亿空间里存 10 亿条时，冲突概率已接近 100%）。

发号器实现

# 发号器的三种实现
# ① Redis INCR（最简单，10 万/s 足够）
def next_id():
    return redis.incr("shorturl:seq")       # 原子自增

# ② 号段模式（减少对 Redis 的依赖，性能高 10 倍）
#   应用每次从 DB 取一个号段（如 1000 个），本地发放完再取
class SegmentAllocator:
    def __init__(self):
        self.cur, self.max = 0, 0
    def next(self):
        if self.cur >= self.max:
            # 用 SELECT ... FOR UPDATE 原子地取一段
            self.cur, self.max = fetch_segment(size=1000)
        self.cur += 1
        return self.cur
# 好处：1000 次分配只需 1 次 DB 访问 -> QPS 提升 1000 倍

# ③ Snowflake（分布式，无中心依赖）
#   64 bit = 1符号位 + 41时间戳(ms) + 10机器ID + 12序列号
#   -> 单机每毫秒可生成 4096 个 ID，支持 1024 台机器
#   -> 可用 69 年（2^41 ms ≈ 69 年）

# 可预测性处理：给 ID 加混淆（简单的可逆混淆）
def obfuscate(num, salt=0x5DEECE66D):
    # 用乘法逆元做可逆混淆，让别人猜不出下一个 ID
    return (num * 0x27d4eb2d) ^ salt        # 简化示例
# 或者：把 ID 和一个随机生成的 32 位 salt 拼在一起再编码

301 还是 302：决定你能不能统计

状态码语义浏览器行为影响
301 Moved Permanently永久重定向缓存重定向结果后续不再经过你的服务器 → 无法统计点击
302 Found临时重定向每次都请求短链服务可统计每次点击（但多一次 RTT）

结论：如果需要统计点击、做风控、支持修改目标地址，必须用 302。301 虽然快（浏览器缓存后直接跳），但会永久失去对流量的控制——短链服务的核心价值（数据统计、反作弊、可撤回）就没了。这也是真实产品（如 bit.ly）用 302 的原因。

func redirect(w http.ResponseWriter, r *http.Request) {
    code := r.URL.Path[1:]
    long, err := cache.Get(code)              // 先查缓存
    if err != nil {
        long, err = db.Query(code)            // 缓存未命中查 DB
        if err != nil {
            http.NotFound(w, r); return

    // 异步记录点击（不阻塞响应！）
    go recordClick(code, r)

}

深入自检

短链服务的最核心挑战是什么？

不是生成算法，而是热点短链的高并发读。一个爆款链接可能有几十万 QPS打在同一个 key 上，这会打爆单个 Redis 分片（热 key 问题）。三层解法：① 本地缓存（每个实例缓存热点短码，10 – 60 s TTL），N 个实例就把压力降为 1/N；② 热 key 多副本（code:1 ~ code:10 随机读）；③ CDN 边缘缓存（302 也可以被 CDN 缓存，但会损失统计能力）。另外要防缓存穿透——不存在的短码要缓存空值（60 s TTL），否则会被打穿。

过期和清理怎么处理？

三种策略：① 惰性删除——访问时发现过期就返回 404 并异步删除（最简单）；② 定时扫描——每天扫一次过期表（注意别全表扫，用索引按过期时间查）；③ TTL 索引——MongoDB / Redis 原生支持，自动过期。关键提醒：短码不要立即回收复用——用户可能保存了旧链接，复用会导致“跳转到完全不同的内容”，这是严重的产品事故。建议过期后保留至少 6 – 12 个月再回收。

怎么防滥用（黄赌毒、钓鱼）？

四道防线：① 接入风控——新建短链时对目标 URL 做安全检测（黑名单库 + 内容扫描）；② 限速——单 IP / 单账号的新建频率限制（如 10 条/分钟）；③ 举报与下架——提供举报入口，确认违规后让短链失效（这是必须用 302 的又一个理由，301 缓存后就管不了了）；④ 审计日志——保留创建记录，配合合规要求。另外，自定义短码要单独风控——它是抢注和仿冒的重灾区。

数据量到千亿级别怎么办？

两个方向：① 存储分区——按短码哈希分库分表（如 1024 个分片），单表控制在千万级；② 冷热分离——热数据（近 3 个月）放 Redis + SSD，冷数据放对象存储或归档库。另外，短码长度可以从 6 位扩到 7 位（3.5 万亿空间），但要考虑兼容性——老短码仍是 6 位，解析时要兼容两种长度。现实中千亿级别很少见（bit.ly 十年也就几百亿），大多数团队高估了自己的增长。
