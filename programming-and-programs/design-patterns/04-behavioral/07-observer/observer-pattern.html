📣 观察者

一个对象变化，已订阅的对象自动得到通知。

一句话记住订阅天气播报的人，在天气变化后各自收到更新。
问题从哪来图解协作动手试一试伪代码选型与边界
01 · 从问题出发

为什么会需要这个模式？

订单支付后，页面、审计和通知都要响应；订单若直接调用每个模块，会与所有下游耦合。

订单状态变成已支付时，页面要刷新、审计要记录、通知模块要发消息。如果订单对象直接持有这三个具体模块，每增加一个响应者都要改订单代码。反过来，永久保存回调也可能导致重复执行和内存引用。

😵 直接写会怎样

function markPaid(order):
  order.status = PAID
  page.refresh(order)
  audit.record(order)
  sms.send(order.user)
  // 又加一个订阅者，就要修改这里

💡 关键转折

主题对象维护订阅集合，状态变化后通知订阅者；订阅者可独立加入或退出。

发布者只维护订阅集合并发出“已发生的变化”；观察者自己订阅、处理和在生命周期结束时取消。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

class Subject {
  listeners = Set()
  subscribe(fn) {
    listeners.add(fn)
    return () => listeners.delete(fn)
  }
  emit(event) {
    for fn in copy(listeners): fn(event)
  }
}
stop = orderEvents.subscribe(onOrderPaid)
orderEvents.emit(OrderPaid(orderId))
stop()

读代码时抓住三件事

  1. subscribe 返回取消订阅函数，方便明确释放。
  2. emit 遍历快照，可避免通知期间修改集合破坏当前迭代。
  3. 同步回调的耗时和异常传播是发布者必须考虑的语义。

换个业务场景，还能认出来吗？

浏览器的事件监听、GUI 数据绑定都常见观察者。跨服务订单事件若要求持久化、重试和至少一次投递，则需要消息系统、outbox 和消费者幂等，不能只靠内存回调。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

一个对象变化后，多个订阅者需要各自响应

三个具体场景

  • 订单支付后刷新页面并记审计
  • GUI 模型变化通知视图
  • 浏览器 DOM 事件通知多个监听器

不适合或要小心

同步回调会影响发布者的耗时和错误传播；跨服务可靠投递要用持久化消息与幂等消费。

同步回调会拖慢发布者；跨进程可靠交付需要消息队列等机制

最容易混淆的相邻模式

模式真正的区别
中介者集中决定多个对象如何协作；观察者是发布状态变化，让订阅者各自响应。
消息队列提供跨进程传输、持久化和重试等能力；进程内观察者不自动提供这些保证。

区分时问自己：发布者只广播事实，还是由中心协调者决定下一步？

落地前检查

  • 明确回调同步还是异步、失败后是否继续。
  • 测试重复订阅和取消订阅。
  • 业务事务未提交前不要发布“已完成”事件。
06 · 自己说一遍

两道检验理解的小题

为什么订阅函数最好返回取消订阅句柄？

组件卸载或任务结束时可移除回调，避免重复处理和长期持有对象。

如果观察者处理很慢，会影响发布者吗？

同步回调会占用同一调用链并拖慢发布者；需异步化时要重新定义投递和失败语义。
