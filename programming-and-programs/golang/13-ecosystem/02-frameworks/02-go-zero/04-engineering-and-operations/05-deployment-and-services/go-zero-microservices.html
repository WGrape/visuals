go-zero 微服务实战

从单体到微服务：怎么拆、怎么生成、服务之间怎么发现与调用、网关怎么收口。一张架构图先建立全局观。

微服务架构 服务拆分 goctl 生成 服务发现 API 网关 部署编排
全局观

go-zero 微服务长什么样

典型形态：一个对外 API 网关 + 多个对内 RPC 服务，全部通过 etcd 自动注册发现。客户端只认网关，网关再调度内部 RPC。

实线 = 调用链路；绿色虚线 = 服务启动时向 etcd 注册、调用方从 etcd 拉取节点。

第 1 步

怎么拆服务

拆分的依据不是「技术层」，而是「业务域」。一个域一个 RPC 服务，对外再包一层 API 网关。

✅ 按业务域拆
用户、订单、支付各自独立 RPC 服务，边界清晰、可独立扩容与发布。
❌ 按技术层拆
不要搞「common-rpc」「util-rpc」，会变成分布式大泥球，跨服务调用爆炸。
网关做收口
所有外部流量先进 user-api 这类 rest 网关，统一鉴权、限流、参数校验。
内部只用 RPC
服务之间永远走 zrpc，不互相直连数据库，避免数据耦合。
第 2 步

用 goctl 一键生成微服务

go-zero 的精髓：先写契约（.api / .proto / SQL），再让工具产出全部样板。

1

生成 API 网关

写好 user.api 后：goctl api go -api user.api -dir user-api

2

生成 RPC 服务

写好 user.proto 后：goctl rpc protoc user.proto --go_out=. --go-grpc_out=. --zrpc_out=. -m

3

生成数据模型

goctl model mysql ddl -src user.sql -dir ./internal/model -c 产出带缓存的 CRUD。

4

把 RPC 配进网关

网关的 config 里加 UserRpc zrpc.RpcClientConf，svc 里建 client，logic 里直接调用。

网关 logic 调用下游 RPC

func (l *LoginLogic) Login(req *types.LoginReq) (*types.LoginResp, error) {
    // 通过注入的 svcCtx 拿到 RPC 客户端
    resp, err := l.svcCtx.UserRpc.Login(l.ctx, &user.LoginRequest{
        Username: req.Username,
        Password: req.Password,
    })
    if err != nil {
        return nil, err
    }
    return &types.LoginResp{Token: resp.Token}, nil
}
第 3 步

服务注册与发现（etcd）

RPC 服务启动时自动注册到 etcd，调用方自动发现并负载均衡。你只需要在 yaml 里写 etcd 地址。

RPC 服务端配置（注册）

Name: user.rpc            # 服务名，调用方靠它找你
ListenOn: 0.0.0.0:8080
Etcd:
  Hosts:
    - 127.0.0.1:2379
  Key: user.rpc           # 注册到 etcd 的 key

调用方配置（发现）

UserRpc:
  Etcd:
    Hosts:
      - 127.0.0.1:2379
    Key: user.rpc         # 按 key 找到 user-rpc 的所有节点
调用方无需写死 IP:Port，节点扩缩容、故障切换对代码透明，框架自动从 etcd 拉列表并做负载均衡。
第 4 步

API 网关要做的事

网关是内外边界，把横切关注点集中处理，下游 RPC 保持纯粹。

统一鉴权
在中间件里校验 JWT，合法才放行到下游。
参数校验
.api 定义的类型自动做 json 绑定基础校验。
限流防刷
网关层 periodlimit，拦掉恶意流量。
聚合编排
一个接口需要多个 RPC 时，在 logic 里编排聚合。
第 5 步

容器化与编排

每个服务独立打镜像、独立部署，互不影响发布节奏。

生成 Dockerfile

goctl docker -go user-api.go

产出多阶段构建的 Dockerfile，体积小、启动快。

生成 K8s 部署

goctl kube deploy \
  -name user-api \
  -namespace default \
  -image user-api:v1 \
  -port 8888 \
  -o user-api.yaml

直接产出 Deployment + Service，改改镜像就能上集群。

微服务不是免费的：服务越多，运维（链路追踪、统一日志、配置中心）成本越高。go-zero 已经内置了大部分能力，但 etcd、Prometheus 这些基础设施要提前规划好。
一句话回顾：业务域拆成多个 RPC 服务，对外用 rest 网关收口，etcd 自动注册发现，goctl 一条命令把样板全生成，最后 docker + kube 各自部署。你专注写 logic 就行。

优雅退出与滚动更新

优雅退出的关键：收到 SIGTERM 后先摘流量、再等存量请求处理完、最后退出，否则滚动更新会产生 502。

优雅退出

// go-zero 已内置优雅退出，但需配合 K8s 配置
// 1) 服务需处理 SIGTERM（go-zero 的 MustNewServer 已处理）
// 2) K8s 侧必须给足退出时间

// main.go 里确保阻塞等待
func main() {
    flag.Parse()
    var c config.Config
    conf.MustLoad(*configFile, &c)
    ctx := svc.NewServiceContext(c)
    server := rest.MustNewServer(c.RestConf)
    defer server.Stop()          // 确保退出时清理
    handler.RegisterHandlers(server, ctx)
    fmt.Printf("Starting server at %s:%d...\n", c.Host, c.Port)
    server.Start()
}

K8s 配置

# K8s Deployment 必须配合的配置
apiVersion: apps/v1
kind: Deployment
spec:
  minReadySeconds: 10            # 就绪后观察 10 秒再认为可用
  strategy:
    rollingUpdate:
      maxSurge: 1                # 最多多起 1 个
      maxUnavailable: 0          # <strong>不允许不可用</strong>，保证无缝
  template:
    spec:
      terminationGracePeriodSeconds: 60   # 退出宽限期，必须 > 最长请求耗时
      containers:
      - name: order-api
        lifecycle:
          preStop:                        # 先 sleep 让注册中心摘流量
            exec:
              command: ["sh", "-c", "sleep 15"]
        readinessProbe:                   # 就绪探针决定是否被加到负载均衡
          httpGet: { path: /health, port: 8888 }
          initialDelaySeconds: 5
          periodSeconds: 5
        livenessProbe:                    # 存活探针决定是否重启
          httpGet: { path: /health, port: 8888 }
          initialDelaySeconds: 15
          periodSeconds: 10

preStop sleep 是必需的：K8s 发送 SIGTERM 与从 endpoints 摘除是并行的，服务可能已经退出但负载均衡还在转发。sleep 15 秒让摘流量先完成，能彻底消除滚动更新时的 502。

服务注册与健康检查

机制作用关键参数
就绪探针决定是否接收流量initialDelaySeconds、failureThreshold
存活探针决定是否重启容器失败 3 次触发重启
启动探针慢启动保护（1.16+）failureThreshold × periodSeconds 是最长启动时间
服务注册etcd/K8s DNSTTL 心跳，go-zero 默认自动

探针的三条铁律：

  • 就绪探针不要依赖下游：如果 DB 挂了导致就绪探针失败，所有实例被摘流量 → 雪崩。就绪探针只检查自身是否可服务。
  • 存活探针要保守：过于敏感会导致频繁重启，重启期间不可用。设好 failureThreshold: 3 与足够的 periodSeconds。
  • 三个探针用不同端点或不同语义：至少存活探针要比就绪探针宽松，避免“有点慢就被重启”的连锁反应。

自检 Q&A

Q：滚动更新时出现 502 怎么解决？

A：三个必配项——① preStop sleep（让注册中心先摘流量，通常 10~15 秒）；② terminationGracePeriodSeconds 要大于最长请求耗时（默认 30 秒，慢接口要调大）；③ maxUnavailable: 0 保证始终有可用实例。三者缺一都可能产生 502。另外要确认应用正确处理 SIGTERM——若进程收到信号立即退出，再长的宽限期也没用。

Q：服务上线后 CPU 突然打满，怎么定位？

A：Go 的利器是 pprof。三步——① 开启 net/http/pprof（import _ "net/http/pprof"）；② 抓 CPU profile：go tool pprof http://host:port/debug/pprof/profile?seconds=30；③ 用 top 与 web 命令看热点函数。注意要在问题发生时抓，事后抓不到。另配 go tool pprof -http 生成火焰图最直观。go-zero 可直接在配置里开启 pprof 端口。

Q：日志把磁盘打满了怎么办？

A：三层防护——① 日志轮转：go-zero 的 KeepDays + Compress（压缩后体积约降 90%）；② 容器层面限制：用 emptyDir 或日志采集到集中存储，不落本地盘；③ 降级日志级别：生产用 info，排查时才临时开 debug。最重要的一条是不要在热路径打日志——高频循环里的一条 log 可能每秒产生几 MB。

Q：多个服务的配置怎么统一管理？

A：三种递进方案——① ConfigMap：最简单，但改配置要重启（或重新挂载）；② 配置中心（Nacos/Apollo/etcd）：支持热更新，go-zero 可通过自定义 conf.MustLoad 接入；③ 环境变量 + 模板：K8s 里最常见，镜像不变、靠环境变量区分环境。判据是是否需要热更新——只有频繁调整的开关类配置才值得上配置中心，数据库连接等稳定配置用 ConfigMap 足够。
