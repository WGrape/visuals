Redis 数据持久化：快照 vs 写日志

RDB 快照与 AOF 追加的两条持久化路径

Redis 为何能作为"保险箱"？它有两种截然不同的数据持久化策略——RDB 定时快照和 AOF 持续记录。两者如何工作？各有何优劣？接下来用动态流程图和动画为你讲清楚。

RDB

Redis Database Backup

通过 fork 子进程，在指定时间点生成数据库的完整快照，dump 为 .rdb 文件。数据以二进制格式紧凑存储，是 Redis 最早的持久化方案。

定期快照 fork子进程 二进制压缩 全量备份
AOF

Append Only File

将每一个写操作命令追加记录到 .aof 文件，类似数据库的 WAL（预写日志）。服务重启时重放日志恢复数据，实现更精细的数据保护。

写命令追加 重放恢复 可配置策略 增量备份

always
每个命令都同步

每个写命令执行后立即调用 fsync 刷盘。最多丢失正在执行的那一条命令。

✓ 最高安全性
⚠ 性能开销最大，每次写都同步磁盘
everysec
每秒同步（默认）

每秒调用一次 fsync，最多丢失 1 秒内的操作。性能与安全性的最佳平衡。

✓ 推荐策略
Redis 默认配置，适合大多数场景
no
由系统决定

不主动同步，由操作系统决定何时刷盘。性能最好，但最多可能丢失未知时间窗口的数据。

⚠ 最大风险
依赖操作系统 buffer 策略

🔴 RDB — 定时快照

  • fork 子进程生成二进制快照
  • 文件小、恢复快
  • 可能丢失快照周期内的数据
  • fork 时有 2 倍内存峰值风险
  • 适合做冷备份和快速恢复

🔵 AOF — 写日志

  • 追加记录每个写命令
  • 数据安全性更高（可配置）
  • 文件较大，需定期重写压缩
  • 重放恢复速度慢于 RDB
  • everysec 是性能与安全的最佳平衡
💡 一句话总结
RDB 像"定时拍照"——简单高效，但两次快门之间发生的事情全丢了。
AOF 像"实时录像"——记录每一帧，数据更完整，但需要定期"剪辑"（重写）防止文件过大。
生产环境推荐 两者同时启用，取长补短。

第一层 · 三种持久化怎么选

先把结论钉死：生产环境几乎总是「RDB + AOF 混合」。RDB 负责快速恢复和冷备，AOF 负责把丢失窗口压到 1 秒内。只开 RDB 会丢最后一次快照之后的所有写；只开 AOF 恢复慢、文件大、历史版本管理麻烦。

方案丢失窗口恢复速度文件体积适用场景
只开 RDB最后一次快照之后全部（分钟级）最快（直接 mmap 加载）最小（二进制压缩）缓存、可重建数据、从库
只开 AOFappendfsync 决定（≤1s）慢（重放所有写命令）最大（文本命令）几乎不单独用
RDB + AOF（推荐）≤1 秒快（AOF 头部是 RDB 格式）中有持久化要求的生产环境
全关全部丢失—0纯缓存，且能容忍冷启动
  • 判定口诀：数据能不能重建。能重建（缓存、会话、排行榜）→ RDB 就够，甚至全关换性能；不能重建（订单、余额、配额）→ 必须 AOF 且 appendfsync everysec。
  • 混合持久化的关键开关是 aof-use-rdb-preamble yes（Redis 4.0+，默认开）。开启后 BGREWRITEAOF 生成的文件前半段是 RDB 二进制、后半段是增量 AOF 命令，兼顾体积和恢复速度。
  • 不要指望 Redis 持久化替代数据库。它解决的是「进程重启不丢」，不解决「误删、逻辑错误、机房故障」——后者靠从库 + 异地备份。

第三层 · 排障清单

  • 写请求突然全部报错 MISCONF Redis is configured to save RDB snapshots... → 快照失败后 stop-writes-on-bgsave-error yes 触发写保护。先 config set stop-writes-on-bgsave-error no 恢复服务，再去查真实原因（磁盘满 / 权限 / fork 失败）。
  • fork 耗时高、延迟尖刺 → latest_fork_usec 大于 100ms 就要处理。常见原因：开了 Transparent Huge Pages（THP，会把 fork 成本放大数倍，必须关）、实例内存过大（单实例建议 ≤10GB 以便快速 fork）、虚拟机内存超售。
  • BGSAVE 期间内存突然翻倍 → 这是 copy-on-write 的正常代价：写越密集，父子进程共享的页被复制得越多。峰值最坏可达 2 倍。所以 Redis 内存上限要按 maxmemory ≤ 物理内存的一半 来设，留出 fork 余量。
  • 磁盘被 AOF 撑满 → 先看是不是 rewrite 没触发（auto-aof-rewrite-min-size 设太大，或 appendfsync 压力导致 rewrite 排队）。紧急处理：手动 bgrewriteaof + 清理，长期要加磁盘告警（≥80%）。
  • 重启后数据比预期少 → 检查是否开着 AOF 却用 RDB 文件恢复：只要 appendonly yes，Redis 启动时只认 AOF，会忽略 dump.rdb。反过来同理。这是最常见的「数据变少」原因。
  • AOF 文件损坏无法启动 → 用 redis-check-aof --fix 截断修复，最多丢最后一条命令。修复前务必备份。
  • 从库全量同步（RDB 传输）把主库拖垮 → 加大 repl-backlog-size（默认 1MB 太小，生产建议 128MB+），避免短暂断开就触发全量同步。

第四层 · 原理与取舍

两句话讲清底层：RDB 是某一时刻的内存快照（fork + COW，子进程写新文件）；AOF 是写命令的追加日志（先执行命令再记日志，重启时重放）。两者对性能的影响点完全不同。

维度RDBAOF
代价发生在哪周期性：fork（阻塞主线程，与内存大小成正比）+ 子进程写盘持续：每次写的 write(2) + 每秒一次 fsync
对延迟的影响偶发尖刺（fork 期间）持续小开销；always 时吞吐可掉 50%
代价随什么增长随内存大小增长随写 QPS 增长
文件增长恒定（就是内存大小）持续增长，靠 rewrite 压缩
最坏丢失最后一次 save 之后全部everysec 时 ≤1 秒
为什么 appendfsync everysec 是最优解？

因为它把「安全」和「性能」的冲突点放在了最合适的位置。always 每次写都 fsync，把 Redis 的吞吐压到接近磁盘 IOPS（通常掉 50% 以上）；no 完全交给 OS，页缓存回刷周期可能 30 秒，断电就丢 30 秒数据。everysec 是后台线程每秒一次 fsync：最多丢 1 秒，而 fsync 的开销被摊到后台线程，主线程几乎无感。所以它是几乎所有生产配置的默认值。注意「最多丢 1 秒」的前提是 Redis 进程崩溃而不是fsync 本身失败——后者 Redis 会主动报错。

AOF 为什么需要 rewrite？不 rewrite 会怎样？

因为 AOF 是追加的，对同一个 key 写 100 次就记 100 条命令，但恢复时只需要最后一条。文件会无限膨胀（一个计数器 key 可以让 AOF 涨到几十 GB 而实际数据只有几 KB），恢复时要重放所有命令，可能要几十分钟。rewrite 的做法是读取当前内存中的值，用最少的命令重建一份等价的 AOF（同一 key 只写一条），文件立刻缩小一个数量级。rewrite 由子进程完成，不阻塞主进程。触发条件是「当前体积比上次 rewrite 后增长了 auto-aof-rewrite-percentage%」且「体积超过 auto-aof-rewrite-min-size」。

fork 到底阻塞多久？为什么 THP 是坑？

fork 本身要复制页表，耗时与内存大小成正比（不是与数据量）：经验值约 每 GB 内存 10~20ms（物理机），所以 10GB 实例 fork 一次约 100~200ms——这段时间 Redis 完全不响应。开启 Transparent Huge Pages（THP，Linux 默认 often 开启）后，页变大但页表项和 COW 粒度变粗，fork 耗时和 COW 复制量都会显著上升，实测可放大 2~5 倍。所以 Redis 官方明确要求 echo never > /sys/kernel/mm/transparent_hugepage/enabled。另外 Xen 等虚拟化平台 fork 更慢，这也是建议单实例内存控制在 10GB 以内的原因。

既然有持久化，为什么还要从库和备份？

因为持久化只解决「进程重启」，不解决另外三类问题：① 误操作——FLUSHALL 会被 AOF 忠实记录并重放，恢复后依然是空的；② 逻辑错误——代码 bug 写坏了数据，AOF 里也是坏数据；③ 主机/机房故障——本地磁盘一起没。正确做法是「持久化（防重启）+ 从库（防单机故障，最好是跨机架）+ 定期 RDB 冷备到对象存储并保留 7~30 天（防误删和逻辑错误，可回滚到历史时点）」三层。只做一层都不能称为「数据安全」。
