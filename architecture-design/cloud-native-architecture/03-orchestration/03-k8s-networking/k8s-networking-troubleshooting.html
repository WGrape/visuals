K8s 网络排障实战：从 Service 查到 Pod

Service→Endpoint 链路、iptables/ipvs 模式、跨节点与 DNS 排查清单

排查链路 模式 跨节点/DNS 清单
原理页讲了 Service 怎么用 iptables/ipvs 把请求转到 Endpoint、Pod 网络怎么互通。这一页给排障链路：从 Service 一路查到 Pod，以及跨节点不通、DNS 失败的定位。

01Service → Endpoint 排查链路

# 1) Service 是否存在、ClusterIP 对不对
kubectl get svc <name> -o wide
# 2) Endpoint/EndpointSlice 是否真的有就绪 Pod
kubectl get endpoints <name>      # 空的说明 selector 没匹配到 Pod
kubectl describe svc <name>       # 看 Selector 与端口映射
# 3) 进 Pod 内直接打 Pod IP 验证后端本身活着
kubectl exec -it <pod> -- curl -s <pod-ip>:<port>

02iptables vs ipvs 模式

kube-proxy 转发规则存在两种实现，排障时先确认当前模式。

要点：ipvs 在大量 Service 下性能更稳；但如果节点没加载 ip_vs 内核模块，kube-proxy 会静默回退到 iptables，现象是「规则看着像 ipvs 实际走 iptables」。
# 看 kube-proxy 模式
kubectl -n kube-system get cm kube-proxy -o yaml | grep mode
# ipvs 模式下看真实转发规则
ipvsadm -Ln | grep -A3 <service-ip>
# iptables 模式看链
iptables -t nat -L KUBE-SERVICES -n | grep <service-ip>

03跨节点不通与 DNS 失败

  • 跨节点不通：先查 CNI 插件状态（kubectl get pods -n kube-system | grep ）、节点安全组/防火墙是否放行 Pod 网段、MTU 是否匹配（VXLAN 会吃 50 字节，MTU 不一致会丢大包）。
  • DNS 失败：CoreDNS Pod 是否 Ready、kube-dns 服务 IP 是否可达、`/etc/resolv.conf` 的 nameserver 是否正确。
  • NetworkPolicy 误伤：确认没把该放的入站/出站流量 deny 掉。
# 从某 Pod 内解析服务名
kubectl exec -it <pod> -- nslookup <svc>.<ns>.svc.cluster.local
# 看 CoreDNS 日志
kubectl -n kube-system logs -l k8s-app=kube-dns --tail=50

04排障清单

  1. Service 有 ClusterIP 吗？
  2. Endpoint 有就绪 Pod 吗（selector 对不对）？
  3. Pod IP 直连通吗（后端本身活着吗）？
  4. kube-proxy 模式对吗、规则存在吗？
  5. 跨节点/防火墙/MTU 有问题吗？
  6. DNS/CoreDNS 正常吗？
  7. NetworkPolicy 没误杀吧？
问：为什么 Service IP 直连不通但 Pod IP 能通？

Service IP 是虚拟 IP，靠 kube-proxy 的 iptables/ipvs 规则做 DNAT 到 Pod IP；直连 Pod IP 绕过了这层。Service 不通说明规则没生成（常因 Endpoint 为空或 kube-proxy 没同步），而不是后端挂了。

第一层 · 概念与判定：先定位断在哪一層

K8s 网络有清晰分层：Pod IP → Service（ClusterIP） → DNS 解析 → Ingress/出口。排查第一原则是分层二分，而不是上来就到处改。

现象优先怀疑层
Pod 间直接 IP 不通CNI / 网络策略
Service 名连不上Endpoints / kube-proxy
svc 名字解析失败CoreDNS
外部进不来Ingress / LB / 端口

第二层 · 参数·命令·量化：排查命令与关键参数

K8s 网络分层排查命令

# 一条链快速定位
kubectl get pods -o wide                 # 看 Pod IP
kubectl get svc,endpoints my-svc         # 看有无就绪后端
kubectl exec -it $POD -- sh -c 'curl -s my-svc:8080/health; echo'
kubectl exec -it $POD -- nslookup my-svc # 解析是否 OK
# 网络策略是否拦了
kubectl get networkpolicy -n $NS
# CNI 层面（以 cilium 为例）
cilium endpoint list | grep -i $POD

数量级：Pod 间同节点 RT 通常 <0.2ms，跨节点走 overlay 约 0.3–1ms；CoreDNS 默认副本少时高并发解析会超时，是常见隐性瓶颈。

第三层 · 排障与边界：五个高频坑

  • NetworkPolicy 悄悄拦了：默认拒绝或忘了放行，Pod 能起但互相不通——先看 policy 再怀疑 CNI
  • Service 0 endpoints：selector 写错或 Pod 没就绪（readiness 失败），流量无处可去
  • CoreDNS 解析超时：副本过少/资源被挤，svc 名解析慢或失败，表现为「间歇连不上」
  • MTU 不匹配：overlay（vxlan/ipip）会吃掉约 50 字节 MTU，未调小会导致大包被丢、握手卡住
  • kube-proxy 模式差异：iptables 规则膨胀后更新慢、ipvs 需要 ip_vs 模块，模式选错排查完全不同

第四层 · 原理与取舍

iptables 模式和 ipvs 模式该怎么选？

iptables 是默认，规则线性匹配，Service 上千后规则膨胀、更新延迟明显；ipvs 用哈希表做负载均衡，规模大时更稳定、转发更快，但依赖内核 ip_vs 模块且某些旧版特性支持弱。经验：小规模无所谓，Service 数量大（数百+）或追求稳定转发选 ipvs。

为什么 overlay 网络要特意调小 MTU？

VXLAN/IPIP 等隧道会在原包外再封一层头（约 50 字节），若 Pod MTU 仍是 1500，封装后超过物理网卡的 1500 就会被分片或丢弃，表现为大文件/大响应传输卡顿、TLS 握手偶发失败。把 Pod 侧 MTU 调成 1450 之类留足封装余量即可。

CoreDNS 为什么经常成为隐性瓶颈？

因为几乎所有 Service 名访问都先走 DNS，而 CoreDNS 默认副本少、且和别的 Pod 抢资源。一旦它抖动，表现不是「解析完全失败」而是「偶发超时重试」，极难联想到 DNS。做法：给它独立资源请求 + 适当副本数 + 必要时 nodeLocalDNS 缓存。
