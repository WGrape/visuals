CPU 性能剖析

先量化再优化——用 top、perf 与火焰图把 CPU 热点看清楚。

为什么要先量再调

量化为先

没有基线的优化都是盲调。先用 top、vmstat、pidstat 拿到 CPU 使用率、用户态/内核态占比与上下文切换次数，建立「优化前」的数字，才能判断改动是否有效。

性能优化遵循「测量 → 定位 → 假设 → 验证」的循环，第一步永远是拿到可复现的负载和明确指标。

CPU 时间分为 用户态（user） 与 内核态（sys）。user 高通常是算法或逻辑自身消耗；sys 高往往是频繁系统调用、锁竞争或上下文切换。

火焰图怎么读

火焰图读法

横轴是采样数量（非时间顺序），纵轴是调用栈深度；越宽的方块占用 CPU 越多。找最宽且靠近顶层的方块，就是最值得优化的热点函数。

用 perf record -F 99 -g 采样，再用 FlameGraph 脚本生成 SVG，即可在浏览器里层层下钻。

问题 1
CPU 使用率 100% 一定有问题吗？

不一定。单进程跑满一个核可能是正常的高负载计算；但要警惕 多核整体 100% 且吞吐没上去——那往往是死循环、锁竞争或频繁 GC。

问题 2
user 高和 sys 高怎么区分对待？

user 高优先看算法与热点函数（perf 火焰图）；sys 高优先看系统调用次数与上下文切换（vmstat 1 的 cs 列）以及锁竞争（perf lock）。

问题 3
火焰图为什么顶层方块不代表瓶颈？

顶层是采样时正在执行的函数，但瓶颈常在被它反复调用的「宽」函数上。应沿最宽路径从下往上看，找到占比最高且可优化的那一帧。

问题 4
Go / Python 的栈能被 perf 抓到吗？

Go 自带 pprof 直接采样 CPU 火焰图；CPython 因 GIL 与解释执行，需 py-spy 或 perf 配合调试符号才能看到 Python 层栈。

Profile 是性能优化的第一步

凭直觉找性能瓶颈，正确率很低。正确做法是采样剖析（profiling）：周期性记录「此刻 CPU 在执行哪个调用栈」，统计后就能得到各函数占用 CPU 的比例。火焰图是这种数据最直观的呈现。

怎么做一次有效的 profiling

① 采样前

  • 明确要回答的问题（为什么慢？哪段耗时？）。
  • 构造能复现问题的负载（真实流量或压测）。
  • 确保符号可用（编译带 -g、不要 strip、保留映射文件）。
  • 记录环境信息（版本、参数、机器规格）。

② 采样中

  • 采样时长足够（几十秒到几分钟），覆盖典型负载。
  • 避免采样启动/预热阶段。
  • 同时采集多个维度（CPU、锁、分配）。
  • 关注对业务的影响（perf 开销通常可接受）。

③ 分析

  • 先看最宽的平顶。
  • 注意意外的热点（序列化、正则、日志、反射）。
  • 区分自身耗时与被调用耗时。
  • 结合业务语义判断「该不该这么慢」。

④ 优化后

  • 再采样对比，确认热点消失或下降。
  • 验证端到端指标（QPS、P99）。
  • 注意「热点转移」：优化 A 后 B 成为新瓶颈。
  • 固化基线，做回归检测。

深入自检

火焰图的横轴是时间吗？

不是。横轴是「采样出现的频次」，通常按字母序排列调用栈以便合并，并不表示时间先后。所以不能从火焰图读出「什么时候慢」，只能读出「哪些代码路径占了多少 CPU」。要看时间维度的变化，需要对比不同时间段的火焰图，或用时序指标。

为什么 perf 采样看到的栈是地址而不是函数名？

因为缺少符号信息：二进制被 strip、没有调试符号、或者 JIT 语言（Java、Go、Python）的代码是运行时生成的，perf 默认认不出来。解决办法：保留符号表、安装 debuginfo、JIT 语言要生成 perf map（Java 用 perf-map-agent，Go 通常自带符号，Node 需 --perf-basic-prof）。

采样会不会影响线上性能？

通常影响很小。perf 采样 99Hz 的开销一般在 1-5%，async-profiler、JFR 设计目标就是生产可用（<1%）。但要注意：高频率采样、采集硬件事件（如 cache-miss）、或 strace 这类逐事件工具开销很大，只适合短时使用。生产建议用低开销工具并控制采样时长。

CPU 不高但请求慢，该 profile 什么？

这种情况要采 off-CPU（等待）而不是 on-CPU：线程可能阻塞在锁、IO、数据库调用、下游 RPC、或者线程池排队。工具上可用 off-CPU 火焰图、Go 的 block/mutex profile、Java 的锁分析，或直接看全链路 Trace 的各段耗时。

为什么优化了一个热点，整体没变快？

常见原因：① 该热点只在部分请求路径上；② 瓶颈其实在别处（如数据库），CPU 只是表象；③ 优化后热点转移，新的瓶颈抵消了收益；④ 优化本身引入了其他开销。所以要端到端测量（QPS/P99），并用阿姆达尔定律估算：优化占比 20% 的部分，即使快一倍，整体也只快 10%。

如何把 profiling 变成常态化能力？

三个做法：① 持续剖析（continuous profiling）——低开销常驻采集，随时可回溯任意时刻的火焰图；② 性能基线纳入 CI，每次发布跑基准测试对比；③ 与监控告警联动：CPU 异常时自动触发采样并保存现场。这样能把「事后难复现」变成「随时可查」。
