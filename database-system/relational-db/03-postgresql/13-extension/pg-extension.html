① 扩展机制：PG 的杀手锏

PG 的扩展（Extension）机制允许在不改内核的前提下加入新类型、函数、索引访问方法、外部数据源。这是它能在 GIS、时序、向量检索等领域持续领先的根本原因。

-- 查看可用扩展
SELECT name, default_version, comment FROM pg_available_extensions ORDER BY name;

-- 查看已安装
SELECT extname, extversion FROM pg_extension ORDER BY extname;

-- 安装 / 升级 / 卸载
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
ALTER EXTENSION pg_stat_statements UPDATE;
DROP EXTENSION pg_stat_statements;

安装位置

扩展文件在 SHAREDIR/extension（.control + .sql），数据对象落在指定 schema

版本管理

ALTER EXTENSION ... UPDATE 执行升级脚本；支持多版本共存

依赖与迁移

pg_dump 会记录 CREATE EXTENSION；升级 PG 大版本时扩展需对应版本

权限

多数扩展需要 superuser 或对应权限安装

-- pg_stat_statements 配置（需重启）
# postgresql.conf
shared_preload_libraries = 'pg_stat_statements'
pg_stat_statements.track = all
pg_stat_statements.max = 10000

-- 查最耗时的 SQL
SELECT substring(query, 1, 60) AS q, calls,
       round(total_exec_time::numeric, 1) AS total_ms,
       round(mean_exec_time::numeric, 2) AS avg_ms,
       rows, shared_blks_read
FROM pg_stat_statements
ORDER BY total_exec_time DESC LIMIT 10;

③ 重量级扩展：把 PG 变成专用数据库

PostGIS

地理空间：几何类型、空间索引（GiST）、距离/相交/缓冲区计算——事实标准

TimescaleDB

时序数据：自动分区（hypertable）、压缩、连续聚合，兼容 SQL

pgvector

向量检索：vector 类型 + IVFFlat/HNSW 索引，支撑 RAG 与相似搜索

Citus

分布式：分片 + 并行查询，把 PG 变成分布式集群

pgaudit

审计日志：记录 DDL/DML，满足合规要求

pglogical / wal2json

逻辑解码：把 WAL 变成 JSON 变更流，接入 Kafka/数仓（CDC）

-- pgvector 示例（RAG 常用）
CREATE EXTENSION vector;
CREATE TABLE docs (id bigserial PRIMARY KEY, content text, embedding vector(1536));
CREATE INDEX ON docs USING hnsw (embedding vector_cosine_ops);
SELECT id, content FROM docs ORDER BY embedding <=> '[0.1,0.2,...]' LIMIT 5;

-- PostGIS 示例
CREATE EXTENSION postgis;
SELECT name FROM shops
WHERE ST_DWithin(geom, ST_MakePoint(116.4, 39.9)::geography, 1000);  -- 1km 内

-- pg_trgm 让模糊搜索走索引
CREATE EXTENSION pg_trgm;
CREATE INDEX idx_name_trgm ON users USING gin (name gin_trgm_ops);
SELECT * FROM users WHERE name LIKE '%zhang%';   -- 可用索引了

④ 自定义扩展与索引访问方法

PG 的开放接口让第三方可以实现全新的索引类型：

索引类型适用典型场景
B-tree默认，等值/范围/排序绝大多数场景
Hash等值（PG 10+ 支持 WAL，可用）长字符串等值
GiST「包含/相交」类谓词PostGIS 几何、范围类型、全文
SP-GiST空间分区结构（四叉树/k-d 树）非平衡数据结构
GIN多值列（数组、jsonb、全文）@> 包含查询、pg_trgm
BRIN超大时序表的块级摘要按时间范围的超大表扫描，索引极小
-- jsonb 用 GIN
CREATE INDEX idx_payload ON events USING gin (payload jsonb_path_ops);
SELECT * FROM events WHERE payload @> '{"status":"paid"}';

-- 数组用 GIN
CREATE INDEX idx_tags ON posts USING gin (tags);
SELECT * FROM posts WHERE tags @> ARRAY['postgres'];

-- 时序大表用 BRIN（索引只有几 MB！）
CREATE INDEX idx_ts ON metrics USING brin (created_at) WITH (pages_per_range = 128);
SELECT * FROM metrics WHERE created_at BETWEEN '2026-10-01' AND '2026-10-02';
BRIN 的价值：对按时间有序写入的超大表（TB 级），BRIN 只记录每个物理区间的 min/max，索引大小只有几十 KB 到几 MB，而 B-tree 可能几十 GB。代价是查询需要扫描候选区间再过滤，适合范围扫描且选择性较好的时序场景。

⑤ 常见问法

Q：pg_stat_statements 为什么必须装？

A：它按归一化后的 SQL 模板聚合执行统计（调用次数、总耗时、平均耗时、返回行数、共享块读/命中、临时文件、JIT 等），是定位性能瓶颈的第一工具——能直接回答「哪条 SQL 最耗时/调用最频繁/IO 最多」。代价很小（通常 < 5%），只需 shared_preload_libraries 预加载并重启一次。实践：所有生产库都应开启，并定期按 total_exec_time 与 mean_exec_time 两个维度排序排查（前者看总量、后者看单条质量）。

Q：pg_repack 和 VACUUM FULL 有什么区别？

A：VACUUM FULL 重写整表并真正收缩文件，但持有 ACCESS EXCLUSIVE 锁（全程阻塞读写）且需要约一倍额外空间；pg_repack 通过触发器捕获增量变更 + 在线重建，只在切换时刻短暂持锁（秒级），大幅降低业务影响。生产环境收缩膨胀应首选 pg_repack（需额外安装扩展）。注意：pg_repack 同样需要额外磁盘空间，且对有长事务的表可能等待较久。

Q：jsonb 该用什么索引？

A：用 GIN：CREATE INDEX ON t USING gin (payload); 支持 @>（包含）、?（键存在）、?& 等操作；若只需精确的路径-值包含，可用更小的 jsonb_path_ops 变体（USING gin (payload jsonb_path_ops)），它索引体积更小、查询更快，但不支持键存在查询（?）。对比：普通 B-tree 只能索引某个表达式（如 (payload->>'status')），适合固定路径的等值查询，体积最小但灵活性差。

Q：BRIN 索引适合什么场景？

A：适合超大、且物理顺序与查询条件强相关的表，典型是时序数据（按时间追加写入，按时间范围查询）。BRIN 只为每个连续物理区间记录 min/max，索引极小（TB 表也能只有几 MB），维护成本几乎为零。查询时先排除不满足的区间，再扫描候选区间。不适合：数据物理顺序与查询列无关（如随机 UUID 或频繁 UPDATE 导致顺序混乱的表）——这时 BRIN 几乎失效。

Q：PostGIS / TimescaleDB / pgvector 这类扩展为什么重要？

A：它们让 PG 在保持 SQL 与事务语义的同时，具备专用数据库的能力：PostGIS 是地理信息的事实标准（几何类型 + 空间索引 + 空间函数）；TimescaleDB 提供自动分区（hypertable）、时序压缩与连续聚合，可替代部分专用时序库；pgvector 提供向量类型与 HNSW/IVFFlat 索引，让 PG 直接支撑 RAG 与相似检索。工程价值：少维护一套系统、少一次数据同步、复用既有事务与备份体系——这是 PG 生态的核心竞争力。

Q：升级 PG 大版本时，扩展要注意什么？

A：三点：① 扩展本身要升级到兼容新 PG 的版本（很多扩展是按 PG 大版本编译的），升级前先在测试环境验证；② 使用 pg_upgrade 时，扩展的共享库文件（.so）必须在新版本目录中可用，否则 pg_upgrade --check 会报错；③ 部分扩展（如需要 shared_preload_libraries 的）在新实例上要先配置好再启动。实践流程：先在测试库跑 pg_upgrade --check 并逐个确认扩展兼容性，再安排维护窗口执行；逻辑复制也是跨版本迁移的常用替代方案。

扩展分两类：① 纯 SQL 扩展（CREATE EXTENSION 即可，如 pg_trgm、hstore）；② 需要预加载的（shared_preload_libraries，如 pg_stat_statements、pg_cron、citus），改了要重启数据库。这是最常见装不上的原因。

安装与使用命令

-- 1) 查看可用/已装扩展
SELECT * FROM pg_available_extensions ORDER BY name;
SELECT * FROM pg_extension;

-- 2) 纯 SQL 类：直接创建
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE EXTENSION IF NOT EXISTS pgcrypto;

-- 3) 需要预加载的（pg_stat_statements）
-- postgresql.conf:
--   shared_preload_libraries = 'pg_stat_statements'
--   pg_stat_statements.max = 10000          # 记录多少条不同 SQL
--   pg_stat_statements.track = all          # all/top/none；all 包含嵌套语句
-- 然后重启，再：
CREATE EXTENSION pg_stat_statements;

-- 查看最慢的 SQL（PG 的必备工具）
SELECT substring(query, 1, 80) AS q,
       calls, round(total_exec_time::numeric, 1) AS total_ms,
       round(mean_exec_time::numeric, 2) AS avg_ms,
       rows, shared_blks_read
FROM pg_stat_statements
ORDER BY total_exec_time DESC LIMIT 10;

-- 重置统计
SELECT pg_stat_statements_reset();
-- 4) pgvector（AI 场景）
CREATE EXTENSION vector;
CREATE TABLE items (id BIGSERIAL PRIMARY KEY, embedding vector(1536));

-- HNSW 索引（查询快、构建慢、内存大）
CREATE INDEX ON items USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);
-- IVFFlat（构建快、内存小，召回略低）
CREATE INDEX ON items USING ivfflat (embedding vector_cosine_ops)
  WITH (lists = 100);        -- lists ≈ 行数/1000，或 sqrt(行数)

-- 查询（注意排序方向与距离算子的匹配）
SELECT id, embedding <=> '[0.1,0.2,...]' AS distance
FROM items ORDER BY distance LIMIT 10;
-- 算子： <-> L2距离   <=> 余弦距离   <#> 内积
-- ⚠️ 用余弦距离必须建 vector_cosine_ops 索引且用 <=> 排序，否则索引不生效

-- 5) pg_repack：在线消除膨胀（不锁表）
pg_repack --no-order --table public.big_table dbname
-- 比 VACUUM FULL 好：VACUUM FULL 需要排他锁，会阻断业务

症状原因处理
CREATE EXTENSION 报文件不存在没装 contrib 包装 postgresql-contrib；或对应扩展的包
报 must be loaded via shared_preload_libraries需要预加载改 postgresql.conf 并重启
pg_stat_statements 没数据track 设置或没重启检查 pg_stat_statements.track；确认已重启
扩展版本不兼容PG 升级后扩展没升级ALTER EXTENSION xxx UPDATE;

扩展装了但函数找不到没设 search_pathCREATE EXTENSION ... SCHEMA public；或设 search_path

pg_stat_statements 是 PG 调优的第一工具，没有它你只能靠猜。它记录每条 SQL 的调用次数、总耗时、平均耗时、扫描行数，开销很小（通常 < 5%），建议生产常开。
