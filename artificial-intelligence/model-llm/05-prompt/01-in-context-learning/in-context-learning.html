LLM 能力与机制

上下文学习 ICL：不训练就能学会新任务

ICL（In-Context Learning）指不更新任何权重，仅靠 prompt 里给的示例/指令，模型就学会新任务。它是 Few-shot prompting 的底层能力，也是 LLM 区别于传统微调模型的关键。

一句话回答

ICL 是 免训练的学习：把任务说明 + 几个示例塞进 prompt，模型在不改动权重的情况下，对新输入给出符合示例模式的输出。它是 GPT-3 起大模型最核心的"用法"，也是 Few-shot / CoT 的底座。

三种设置

Zero-shot
只给指令/问题，不给示例。"把下面翻译成中文：…"
One-shot
给 1 个示例 + 新输入。
Few-shot
给 k 个示例（常 3~8），再给新输入。效果通常最好。
注意："few-shot" 在这里不意味额外训练——示例都在同一个 forward pass 的上下文里，权重纹丝不动。

为什么有效（几种解释）

  • 隐式贝叶斯推断：把示例看作从某个任务分布采的样本，模型据此推断"当前属于哪类任务"并照做。
  • 隐式微调 / 学习算法：有研究认为 Transformer 在上下文里"执行"了一个隐式的梯度下降式算法，把示例当成"训练数据"在注意力中完成适配（"模型会学习如何去学习"）。
  • 任务分布的元学习：预训练见过海量(task, demonstration)对，ICL 能力是在预训练阶段"元学习"出来的。
共识：ICL 能力主要来自大规模预训练，不是推理时才涌现的魔法；小模型基本没有可靠的 ICL。

与微调（Fine-tuning）的边界

维度ICL（Few-shot）微调
是否改权重否是
成本/速度即时、零训练需算力、数据、时间
适用任务多变、少样本、临时切换任务固定、追求极致/私有知识
上限受上下文长度+示例质量限制可更深、更稳

影响效果的因素

  • 示例数量：一般越多越好，但有边际递减，且受上下文窗口限制。
  • 示例顺序：有"近因偏差"——放最后的示例影响更大（所以常把最相关/最难放最后）。
  • 格式与标签空间：示例的输入输出格式要和目标一致；标签分布要合理。
  • 示例相关性：与待解样本越相近，引导越好。

局限

  • 近因/锚定偏差：示例顺序、格式会悄悄带偏输出。
  • 容量上限：示例塞不下、长任务撑爆上下文就失效。
  • 复杂任务不如微调：需要稳定记忆私有知识、强泛化的场景，ICL 不够。
  • 敏感且不稳定：换几个示例、调下顺序，结果可能波动。

总结

  • ICL = 免训练、靠 prompt 示例学会新任务，是 LLM 的标志性能力。
  • 来源是大规模预训练的元学习，不是推理魔法。
  • 和微调互补：ICL 即时灵活，微调稳而深；按任务频率与难度选。
  • 效果受数量/顺序/格式/相关性影响，注意偏差与窗口限制。

它不训练模型，只是「当场演示」

In-Context Learning（ICL）的本质：把示例放进上下文，模型当场从示例中推断出任务，权重一个字节都没改。这是它和微调最根本的区别，也决定了它的优点（零训练成本、即时切换任务）与代价（每次推理都要重复带上示例、上下文占用）。

Zero-shot只给指令不给示例，靠预训练中的任务理解
One-shot一个示例，主要用来锚定输出格式与风格
Few-shot多个示例，共同定义任务边界，通常更稳
不更新权重纯推理时行为，无梯度、无训练成本
上下文成本示例 token 每次推理都要重新付费
典型收益格式一致性、领域风格、少样本分类明显提升
三种设置：示例从 0 到多，稳定性递增、成本也递增

决策顺序：先试 zero-shot → 不够就 few-shot → 还不行且是知识问题就上 RAG → 仍然不够且任务稳定、量大、效果要求高，才做微调。反过来做会浪费大量成本。

示例工程的七条实操规则

① 示例要有代表性

  • 覆盖任务的典型情况与边界情况，而不是随机抽几条。
  • 分类任务要保证每个类别都有示例，且数量大致均衡。
  • 示例本身的正确答案必须准确，错例会被忠实模仿。

② 顺序与位置很敏感

  • 模型对末尾示例更敏感（近因效应），最后一条影响最大。
  • 类别顺序会导致预测偏置，应打乱或更换顺序测试稳定性。
  • 把最关键、最想被模仿的示例放在最后。

③ 格式统一到极致

  • 分隔符、大小写、标点必须完全一致，模型会模仿不一致。
  • 用清晰的结构化分隔（如 「输入：/输出：」 或 XML 标签）。
  • 输出示例就是我们想要的确切格式，包括是否有句号、是否带引号。

④ 数量：够用就停

  • 常见 2-8 条收益最大，之后边际递减。
  • 每加一条都要付 token 成本与延迟成本。
  • 做消融：逐条加示例看指标曲线，拐点就是最佳数量。

⑤ 与指令配合

  • 好的 prompt = 明确指令 + 少量示例 + 明确输出格式要求。
  • 指令说清「做什么」，示例说清「长什么样」。
  • 两者冲突时模型常听示例的，所以指令与示例必须一致。

⑥ 校准概率偏置

  • 分类任务中，示例的类别分布会偏置预测（多数类被偏好）。
  • 可用平衡示例、或在推理时做概率校准。
  • 评测集要和真实分布一致，否则指标虚高。

⑦ 何时不该用 ICL

  • 需要大量领域知识注入 → 用 RAG 或微调。
  • 每次调用量极大且示例很长 → 成本过高，微调更划算。
  • 任务要求极低延迟 → 长 prompt 直接拖慢 TTFT。
  • 示例很多且经常变 → 考虑「示例库 + 动态检索相似示例」。

深入自检

ICL 真的「学会」了任务吗？

严格说不是学习（没有权重更新），更像「条件化」：示例作为条件把模型的行为引导到某个任务模式上。研究上有两种解释——一是模型在预训练中已具备任务能力，示例只是「任务识别」的线索；二是前向传播中确实发生了类似梯度下降的隐式学习。两者都在不同实验中有支持。

为什么示例顺序会显著影响结果？

因为 Transformer 的位置编码与注意力存在近因偏置，靠后的 token 对最终预测影响更大；同时先出现的类别会在激活中形成先验。实务做法：固定一个测试过的顺序（别让它随机变化），并做顺序扰动测试评估稳定性。

few-shot 示例越多越好吗？

不是。通常 2-8 条提升最明显，之后收益递减，甚至因为上下文变长、注意力稀释而下降。同时每条示例都要付费并增加延迟。正确做法是做条数消融曲线找拐点。

示例和指令冲突时听谁的？

多数情况下示例的影响更强，模型倾向模仿它看到的模式。所以千万不要在示例里留下你不希望被模仿的格式；如果输出格式很重要，示例本身就是最强的格式约束。

分类任务用 ICL 有哪些坑？

三个典型坑：① 示例类别分布偏置预测；② 标签词选择影响巨大（用 「正面/负面」 还是 「1/0」 结果不同）；③ 校准问题——需要保证候选标签在示例中的出现频次均衡，或做概率校准。

ICL 和 RAG 可以一起用吗？

可以而且常见：RAG 负责提供「相关知识片段」，few-shot 示例负责「输出格式与风格」。注意两者都占上下文，需要控制总长度；也可以用「动态示例」——从示例库里检索与当前输入最相似的几条，比固定示例效果更好。
