05 · 推理

从概率到 token：解码流程与四种截断策略

拿到概率分布之后，怎么挑下一个 token 决定了输出是「稳定可复现」还是「有创意」。这一篇只看机制与顺序：logits 经过哪些处理、top-k / top-p / min-p 各自截掉什么。

一句话定位：一条固定的流水线

logits → 重复惩罚 → 温度缩放 → 截断（top-k / top-p / min-p）→ 归一化 → 采样。每一步的输入都是上一步的输出，顺序错了行为就变了。参数含义与调参经验在「生成参数」章节，这里讲实现。

贪心argmax，无随机性（理论上）
beam search保留 k 条候选路径，适合翻译/摘要等封闭任务
top-k只留概率最高的 k 个，候选数固定
top-p留累计概率 ≥ p 的最小集合，候选数随分布形状自适应
解码流水线：顺序比参数值更容易出错

四种截断的差别（同一分布下的行为）

策略保留规则优点缺点适合
贪心 / argmax只取最大确定、快重复、呆板结构化抽取、代码补全
Beam search保留 k 条总分最高的序列整体概率高开放生成偏平淡、显存 ×k翻译、摘要
top-k概率前 k 个简单、可预测开销k 固定，分布尖锐时留太多垃圾通用
top-p（nucleus）累计概率达到 p 的最小集合自适应候选数p 接近 1 时几乎不截断通用默认
min-p保留 p ≥ max_p × min_p 的 token随置信度自适应，长尾更干净新参数、经验值尚不统一创意写作、小模型
typical sampling保留「信息量接近期望」的 token减少无意义长尾实现复杂、参数难调研究/特定任务
# 典型实现（伪代码） logits = logits / temperature # 温度先做 if top_k: logits[logits < topk(logits, top_k)[-1]] = -inf probs = softmax(logits) if top_p < 1: sorted_idx = argsort(probs, descending=True) cum = cumsum(probs[sorted_idx]) cut = cum > top_p # 累计超过 p 的位置 cut[..., 1:] = cut[..., :-1].clone() # 保留第一个超出的（shift） cut[..., 0] = False probs[sorted_idx[cut]] = 0 probs = probs / probs.sum() next_token = multinomial(probs, 1)

确定性：为什么 temperature=0 还会变

来源说明能否消除
浮点归约顺序不同 batch 大小/不同 kernel 的加法顺序不同固定 batch + 确定性 kernel
MoE 路由top-k 边界打平时的 tie-break 可能不稳定固定路由实现
并行归约 / all-reduce多卡下归约顺序随拓扑变化单卡或固定拓扑
采样随机源未固定 seedtorch.manual_seed
vLLM 等引擎的调度不同请求混合改变数值路径单独跑同一请求对比
不要用「两次结果不同」来判断有没有 bug

生产环境的 batch 组成每时每刻在变，temperature=0 也不可能逐字复现。要定位问题，先在单请求、固定 batch=1、固定 seed 下对比。

排障：五种典型的生成异常

  1. 输出跑偏成乱码长尾：top_p=1 且温度偏高，长尾 token 被采到。降到 0.9 或加 min_p。
  2. 一直重复同一句：重复惩罚过小或没开；也可能是 prompt 结尾让模型进入了「复读」状态。
  3. 语法突然崩坏：重复惩罚过大（>1.3）会压制必要的功能词（的、是、逗号），中文尤其明显。
  4. beam search 结果比贪心还差：开放生成用 beam 会偏向高概率的通用表达，长度惩罚也有影响。
  5. 函数调用/JSON 解析失败：应该在解码层做约束（grammar / JSON schema 约束解码），而不是靠调温度。

原理与取舍：为什么默认是 top-p + 中等温度

语言模型的分布是长尾的：正确 token 通常占 30%~60%，剩下几千个 token 分掉长尾。top-k 用固定数量截断，遇到「很确定」的分布会留下垃圾；top-p 用累计概率截断，天然「确定时少留、不确定时多留」，所以成为默认。温度则调节整体的锐度，与截断解耦后更好调。

top-p 和 top-k 一起用会怎样？

先 top-k 再 top-p，等于取两者交集。实践中通常只用其中一个，同时开容易把候选压得过少导致重复。

温度应该在 softmax 之前还是之后？

作用在 logits 上（softmax 之前），等价于把分布锐化/平滑：softmax(z/T)。如果在概率上做幂运算，数学上等价但数值更差。

约束解码会改变模型能力吗？

只改变搜索空间、不改变分布本身。JSON/grammar 约束在结构化输出场景几乎是必需项，比调温度可靠得多。

第一层 · 概念与判定：五种解码策略怎么选

策略做法特点适用
Greedy每步取概率最大的 token确定性、最快，但容易重复、呆板需要可复现结果
Beam Search保留 top-B 条候选路径质量高但慢 B 倍，仍偏呆板翻译、摘要等有明确最优的任务
Temperature缩放 logits 再 softmaxT<1 更尖锐，T>1 更发散控制随机程度
Top-k只在概率前 k 个里采样截断长尾，但 k 固定不灵活早期常用
Top-p（核采样）在累积概率达 p 的最小集合里采样自适应候选集对话/创作首选
  • 信号一：要「稳定、可复现」→ greedy 或 T=0。
  • 信号二：要「有创意但不跑偏」→ top-p 0.9 + temperature 0.7。
  • 信号三：输出开始车轱辘话 → 加 repetition penalty 或降低 top-p。

关键认知：temperature 和 top-p 是两回事——temperature 改变分布的尖锐程度，top-p 改变候选集大小。通常先定 top-p，再微调 temperature。

第二层 · 参数·命令·量化：常用取值与组合

参数常见取值效果
temperature0.7~1.0（对话）/ 0.1~0.3（代码、抽取）越低越确定，越高越随机；0 即 greedy
top_p0.9~0.95越低候选集越小、越保守
top_k50（常与 top_p 二选一）固定候选个数
repetition_penalty1.05~1.2大于 1 惩罚已出现的 token
num_beams4~5beam search 的束宽；开销 ×B
max_new_tokens按需防止无限生成

解码参数配置

# HuggingFace 的标准用法
out = model.generate(
    **inputs,
    max_new_tokens=512,
    do_sample=True,          # False 则是 greedy / beam
    temperature=0.7,         # 采样时才生效
    top_p=0.9,               # 核采样
    top_k=0,                 # 设 0 表示不用 top_k（与 top_p 二选一）
    repetition_penalty=1.1,
)

# 确定性输出（可复现）
out = model.generate(**inputs, do_sample=False)          # greedy，等价于 temperature=0

# Beam search（注意与 sampling 互斥）
out = model.generate(**inputs, num_beams=4, early_stopping=True)

# OpenAI API 的对应参数
# temperature=0.7, top_p=0.9, presence_penalty / frequency_penalty

# 采样流程（原理）：先按 temperature 缩放，再截断，再采样
logits = logits / temperature
probs  = softmax(logits)
# top_p: 按概率降序累积，保留累积 <= p 的最小集合，其余置 0 后重新归一化

量化参考：推理速度上，greedy 最快；num_beams=B 会让解码耗时约 B 倍（要同时维护 B 条路径），所以在长文本生成里很少用 beam search。

第三层 · 排障与边界：生成质量问题的定位

现象原因怎么调
输出车轱辘话、重复采样太窄或惩罚不够加 repetition_penalty=1.1；提高 temperature
输出离题、胡编temperature 太高 / top_p 太大降 temperature 到 0.3~0.7；top_p 降到 0.85
输出呆板、千篇一律greedy 或 temperature 太低开采样；temperature 提到 0.8~1.0
每次结果都不一样do_sample=True 且没设种子设 torch.manual_seed() 或改 greedy
生成停不下来没设 max_new_tokens 或 eos 处理不当设上限；检查 eos_token_id
长文本后段质量下降上下文/注意力衰减属于模型能力边界，非解码参数能解决
  • 排查顺序：先确认 do_sample 是否开启 → 再看 temperature → 再调 top_p → 最后加 repetition penalty。
  • 边界一：temperature=0 与 do_sample=False 等价，都退化为 greedy。
  • 边界二：top_k 和 top_p 通常二选一。同时设会先应用 top_k 再 top_p，效果叠加、更难预测。
  • 边界三：repetition_penalty 过大（>1.5）会损伤正常表达，甚至出现用词怪异。

第四层 · 原理与取舍：为什么 top-p 比 top-k 更好用

top-k 的候选集大小固定，但这不合理：当模型很确定时（某个 token 占 99%），采 50 个候选纯属引入噪声；当模型很不确定时（概率均匀分布），50 个候选又可能不够。top-p 按累积概率自适应地决定候选集大小，正好解决这个问题。

维度top-ktop-p
候选集固定 k 个自适应（累积到 p 为止）
模型很确定时仍取 k 个，引入噪声候选集自动变小
模型不确定时可能截断不足候选集自动变大
调参难度需要按任务调 k0.9 基本通用
temperature 是怎么起作用的？

它在 softmax 之前缩放 logits：p_i ∝ exp(logit_i / T)。T→0 时最大 logit 会压倒一切（变 greedy）；T→∞ 时所有 token 概率趋于相等（完全随机）。所以 T 控制的是「分布的尖锐程度」。

为什么 beam search 在对话里很少用？

两个原因：① 开销是束宽的倍数，长生成太慢；② beam search 倾向于生成「高概率但平庸」的句子，对话场景反而显得呆板。现代聊天模型普遍用 top-p + temperature 采样。

怎么让输出完全可复现？

三种：① do_sample=False（greedy）；② 固定随机种子 torch.manual_seed()；③ API 侧传 seed 参数（若支持）。注意即便如此，不同 batch / 不同硬件上仍可能有细微数值差异。
