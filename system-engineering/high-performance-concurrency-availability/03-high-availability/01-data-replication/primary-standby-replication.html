主备同步与故障切换

主库承担写入，备库持续追赶。当主库失效时，让一台数据足够新的备库安全接管，并把流量切过去。

工作全景复制模式故障切换RPO / RTO关键防线速记

🔁主备不是“复制一份数据”

它是一条由写入确认、日志传输、备库回放、健康探测、主从角色切换共同组成的恢复链路。点选场景，观察确认点和流量路径的变化。

正常写入：主库提交事务，日志流向备库；备库持续接收并回放，始终保留可提升的副本。

⚖️复制模式：确认点决定取舍

确认越早，延迟越低、可用性越好；确认越晚，故障时丢失的数据越少。没有脱离业务目标的“最佳模式”。

异步复制 Async

主库本地提交后立即向客户端确认，备库稍后接收。吞吐和延迟表现好，但主库突然损坏时，尚未发送或回放的事务可能丢失。

半同步 Semi-sync

至少一个备库收到日志后再确认（常见实现不等于已落盘或已回放）。它在延迟与数据保护间折中；备库失联时应明确是阻塞还是降级。

同步复制 Sync

等待副本按约定完成持久化或应用后再确认。RPO 可以趋近于 0，但跨机房网络抖动会直接进入写路径，影响写可用性和尾延迟。

🚨自动故障切换：先保证只有一个主

“检测到主不可达”不等于“主已经停止写入”。网络分区、探测误判都会造成旧主仍在运行；因此切换的关键步骤是围栏。

多维健康确认：结合进程、端口、应用、复制状态和多数派，避免一次探测超时就切换。
围栏旧主（Fencing）：切断旧主写入资格，例如撤销租约、断开存储、隔离网络或 STONITH。未围栏，不提升。
选择最新可用备库：比较日志位置、延迟、校验状态和故障域，提升数据最完整、健康的候选者。
提升与切流：备库成为新主，更新服务发现、VIP、代理或 DNS；客户端应具备重试和幂等能力。
重建旧主：旧主恢复后不能直接接流量，应以新主为准重新同步、校验并作为新备库加入。

🎯用 RPO / RTO 说清承诺

高可用不是“永不出错”，而是明确故障后可接受的数据损失和恢复时长，并用演练检验这些数字。

RPO · 恢复点目标

最多能丢多久的数据。异步复制的 RPO 取决于复制延迟与未传输日志；同步复制可让 RPO 接近 0，但要付出确认等待的成本。

RTO · 恢复时间目标

从故障开始到服务恢复的最长时间。它包括故障确认、仲裁、围栏、提升、路由收敛、应用重连和验证，而不只是“切换命令”的耗时。

例：“异步复制 + 30 秒最大复制延迟 + 2 分钟自动切换”应被表述为：在极端主故障时，RPO 最多约 30 秒，RTO 目标约 2 分钟；两项都需要通过故障演练测量，而非只写在设计文档里。

🛡️两类常被忽略的防线

风险典型现象设计防线
读写延迟不一致刚写入后读备库，读到了旧值。关键读粘主库；读己之写使用会话水位 / GTID 等待；把“可能旧读”显式暴露给业务。
脑裂网络分区后旧主和新主同时接收写入，恢复时数据分叉。多数派仲裁 + 有时效的主租约 + 强制围栏；任何没有确认旧主停止写入的提升都应被禁止。
复制延迟备库落后，切换后丢失窗口扩大，读流量也更陈旧。监控发送、接收、回放三段延迟；限流或降级写入；为备库保留回放和 IO 资源，不把监控只盯在“连接存在”。

📌面试与实践速记

复制不是备份

复制会把误删、逻辑错误同步过去；仍需独立备份、保留点恢复和恢复演练。

切换前先围栏

可用性切换的底线是单主写入。宁可短暂不可写，也不能让两个主持续产生冲突数据。

选择由 RPO / RTO 驱动

先定义业务允许的数据损失和恢复时间，再选择同步级别、仲裁与切换策略，而不是反过来套技术名词。

模式主库提交时机数据丢失风险性能典型实现
异步写完本地日志立即返回会丢（主库宕机时未传到从库的事务全丢）最高MySQL 默认、Redis 默认、PG 默认

配置与监控

-- MySQL 半同步配置
INSTALL PLUGIN rpl_semi_sync_master SONAME 'semisync_master.so';
INSTALL PLUGIN rpl_semi_sync_slave  SONAME 'semisync_slave.so';
SET GLOBAL rpl_semi_sync_master_enabled = 1;
SET GLOBAL rpl_semi_sync_slave_enabled  = 1;
-- 关键参数：等多久后退化成异步（防止从库挂了把主库拖死）
SET GLOBAL rpl_semi_sync_master_timeout = 1000;      -- 1000 毫秒
SHOW STATUS LIKE 'Rpl_semi_sync_master%';
--   Rpl_semi_sync_master_status = ON/OFF（OFF 说明已退化）

-- 复制延迟监控（最重要）
SHOW REPLICA STATUS\G        -- MySQL 8.0（旧名 SHOW SLAVE STATUS）
--   Seconds_Behind_Master: 0       <- 延迟秒数
--   Replica_IO_Running: Yes        <- IO 线程（拉 binlog）
--   Replica_SQL_Running: Yes       <- SQL 线程（回放）
--   Last_IO_Errno / Last_SQL_Errno <- 出错看这里
--   Retrieved_Gtid_Set / Executed_Gtid_Set

-- PostgreSQL
SELECT client_addr, state, sent_lsn, replay_lsn,
       pg_wal_lsn_diff(sent_lsn, replay_lsn) AS lag_bytes
FROM pg_stat_replication;
SELECT pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) FROM pg_stat_replication;

Seconds_Behind_Master 的坑：它衡量的是「从库当前执行的事件时间戳 − 从库当前时间」，在主库空闲时这个值可能是 0，但实际上从库可能已经落后很多（只是没有新事件）。更可靠的指标是 GTID 差值（Retrieved_Gtid_Set vs Executed_Gtid_Set）或 PG 的 LSN 字节差。

延迟原因、切换与一致性

延迟原因特征解法
大事务主库一个事务跑 10 分钟，从库必然落后 10 分钟拆事务；避免一次性 UPDATE 百万行
从库单线程回放MySQL 5.6 前 SQL 线程单线程开并行复制（slave_parallel_workers）
从库有查询压力从库 CPU 打满，回放变慢读写分离的读流量分流；加从库
从库配置差从库机器比主库弱同级配置（切换后要能扛住）
无主键表回放时全表扫描找行所有表必须有主键
网络跨地域复制压缩 binlog；专线

并行复制与延迟治理

-- MySQL 并行复制（解决单线程回放瓶颈）
STOP REPLICA;
SET GLOBAL slave_parallel_type = 'LOGICAL_CLOCK';   -- 按事务依赖并行
SET GLOBAL slave_parallel_workers = 8;              -- 并行 worker 数
START REPLICA;
--   8.0 默认 slave_parallel_workers=4、type=LOGICAL_CLOCK

-- 大事务拆分示例（避免从库长延迟）
-- 错误：
UPDATE orders SET status=1 WHERE created_at < '2025-01-01';   -- 可能 500 万行
-- 正确：按主键分批
UPDATE orders SET status=1 WHERE created_at < '2025-01-01' AND id BETWEEN ? AND ?;
--   每批 1000~5000 行，循环执行，批间 sleep 一点

-- 强制读主（解决主从延迟导致「刚写就读不到」）
--   方案 1：写后 1~2 秒内的读走主库（按业务判断）
--   方案 2：写请求返回时带上 GTID/位点，读时要求从库已追上该位点（等一会儿或换主）
--   方案 3：用 SELECT ... WAIT_FOR_EXECUTED_GTID_SET()（MySQL 8.0，会阻塞等待）
切换场景风险防护
计划内切换（升级/迁移）低（可以先确认从库已追上）先设只读、等延迟归零、再切
计划外切换（主库宕机）可能丢数据（异步复制）半同步 + 切换时对比 GTID，宁可不切也不丢
脑裂旧主恢复后同时有两个主在写旧主必须设为只读再接入；用 fence/STONITH
从库落后太多切换后丢大量数据切换前检查延迟；落后太多就不切，先修主库
异步复制一定不能用于金融场景吗？

取决于能不能容忍丢最后几秒。异步复制在主机宕机时会丢失「已返回成功但还没传到从库」的事务，通常是几十毫秒到几秒的量。金融核心系统一般要求 RPO=0，那就必须用半同步（至少保证一个从库收到）或多数派共识（Raft）。但要注意半同步的 timeout：从库挂了它会退化成异步，此时 RPO 又不为 0 了——所以生产上会配「半同步退化就告警」，或者用两个从库降低同时挂的概率。

主从延迟导致「刚下单查不到」怎么办？

四种解法，按侵入性从低到高：① 写后短期读主——写完把 user_id 存到 Redis（TTL 1~3 秒），这段时间内该用户的读走主库，最简单有效；② 强制走主——对一致性要求高的接口（订单详情、支付结果）直接读主；③ 等待位点——写操作返回时带上 GTID，读之前要求从库追上（会阻塞，慎用）；④ 从架构上避免——把「刚写入就要读」的场景改成写入时就把结果返回给前端（前端渲染而不是回查）。

Raft 的多数派和主从复制有什么本质区别？

三点：① 一致性保证——Raft 保证「已提交的条目在多数派存活下永不丢失」，主从（异步）不保证；② 选主方式——Raft 由集群自行选举且有任期（term）机制防止脑裂，传统主从靠外部工具（MHA/Orchestrator）切换，容易出错；③ 成员变更——Raft 有严格的成员变更流程，主从加节点要手工处理位点。代价是 Raft 需要至少 3 节点且写要等多数派（多一个 RTT），所以数据库层普遍仍用主从（性能优先），而元数据/协调层用 Raft（正确性优先）。

分布式系统 · 主备同步与故障切换 — 复制、RPO、RTO、脑裂防护

核心速览

一句话主库负责写、从库复制数据并提供读，实现读写分离与故障切换
三种复制方式异步（默认）、半同步、全同步
核心矛盾复制越同步，写入延迟越高、可用性越低
必须设计延迟监控、切换策略、如何避免丢数据
MySQL 主从复制四步：binlog -> 推送 -> relay log -> 回放

一、三种复制模式

模式主库何时返回数据安全性性能适用
异步写完本地就返回，不等从库最差，主库宕机会丢未同步数据最好默认，大多数场景
半同步等至少一个从库确认收到较好，保证至少一份副本中等对丢数据敏感的业务
全同步等所有从库都回放完最好最差，任一从库慢就拖垮极少使用

MySQL 的半同步有一个关键细节：它只保证从库收到 binlog，不保证回放完成（默认 AFTER_SYNC 模式）。设置为 AFTER_COMMIT 会略有不同，但工程上 AFTER_SYNC 更安全，也是主流选择。

二、复制延迟是怎么产生的

原因现象对策
从库单线程回放主库并发写，从库串行回放开启多线程复制（MTS，按库或按事务组并行）
大事务一个事务跑 10 分钟，从库就落后 10 分钟拆小事务
从库还在跑查询长查询占用资源，回放变慢从库只读轻查询，隔离资源
主库写入压力超过从库能力延迟持续增大加从库、升级从库规格
无主键表回放时全表扫描定位行强制所有表有主键
无主键是复制延迟的头号元凶

从库回放 UPDATE/DELETE 时，如果没有主键，就要对每一行做全表扫描比对，一个大表上的单条更新可能让从库落后几分钟。线上务必强制每张表都有主键。

三、读写分离的三个坑

刚写就读不到写后读必须走主库，或者等延迟追上（等 GTID / 位点）
从库延迟导致读到旧值关键业务强制走主库
大查询拖垮从库慢查询要限流，报表类查询走独立的从库

四、故障切换怎么做

阶段做什么风险
判断主库失效多次探测 + 多节点共识，避免误判网络抖动导致误切换
选新主选数据最全（GTID 最大 / 位点最新）的从库选错会丢数据

GTID（全局事务标识）让切换变得可靠得多：每个事务有全局唯一 ID，从库可以精确知道自己缺哪些事务，切换时不用再人工比对 binlog 文件名和位点。

五、深入自检

异步复制一定会丢数据吗？

主库宕机时会丢「已提交但还没同步到从库」的事务。窗口大小取决于复制延迟，通常毫秒级，但大事务或网络抖动时可能达到秒级甚至分钟级。

半同步能保证不丢吗？

大大缩小了窗口，但不能 100% 保证：超时后会退化成异步（这是为了避免主库被拖死）。而且它只保证从库收到，若从库收到后自己宕机且未落盘，仍可能丢。

Seconds_Behind_Master 为 0 就是没延迟吗？

不一定。它计算的是「当前正在回放的事务的时间戳」与从库时间的差，如果主库刚写入还没推过来，从库显示的就是 0。真正的延迟要用 GTID 或位点对比。

从库能写吗？

技术上能，但会造成数据不一致，绝对禁止。应该设为 read_only=ON，并且注意 super_read_only 也要开（否则有 SUPER 权限的用户仍能写）。

一主多从时从库之间延迟不同怎么办？

这正是读写分离的隐患：同一个用户两次读落到不同从库，可能看到不同版本的数据。解决：会话内绑定从库，或者读前等待位点追上（如 MySQL 的 WAIT_FOR_EXECUTED_GTID_SET）。

级联复制有什么用？

从库再挂从库，减轻主库的推送压力（主库只需要推给少数几个一级从库）。代价是末端从库延迟更大。适合从库数量很多（十几台以上）的场景。

记住一句异步快但会丢，半同步折中
延迟元凶大事务 + 无主键 + 单线程回放
读己之所写写后读走主库
切换基石用 GTID 而不是文件名+位点
