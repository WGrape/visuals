高可用架构设计

用冗余、无单点、故障转移，把系统的『不可用时长』压到极低。

高可用三板斧 HA

核心思路：任何组件坏了都有替身顶上

可用性常用『几个 9』衡量：99.9%(年停机≈8.8h)、99.99%(≈52min)、99.999%(≈5min)。提升路径：消除单点（每组件≥2副本）、健康探测+自动转移、容量冗余、多可用区/多地域部署。

冗余策略

简单公式

系统可用性 ≈ 1 − (各组件不可用时长之积) ；单点故障会让乘式变加式，故必须冗余

面试高频问答

Q：可用性 99.99% 意味着什么？
A：意味着一年累计不可用时间控制在约 52 分钟以内。要做到，任何关键路径都不能有单点，且故障转移要自动化而非人工。
Q：多活和主备怎么选？
A：主备成本低、实现简单，适合多数业务；多活容灾与容量更强但数据一致性复杂、成本翻倍，只在对连续性要求极高的核心系统使用。

高可用：先量化，再设计

「高可用」不是形容词，是数字。可用性 = 可用时长 / 总时长。行业用「几个 9」来分级，每多一个 9，年停机时间减少约 10 倍，成本也大致增加一个数量级。先和业务确认要几个 9，再选方案，否则要么过度设计，要么达不到。

级别年停机时间月停机时间典型场景 / 手段
99%（2 个 9）约 3.65 天约 7.3 小时单实例 + 手工恢复，内部系统
99.9%（3 个 9）约 8.76 小时约 43.8 分钟主备 / 多实例 + 自动重启，多数业务基线
99.99%（4 个 9）约 52.6 分钟约 4.4 分钟多可用区部署 + 自动故障转移，核心业务
99.999%（5 个 9）约 5.26 分钟约 26 秒多区域 + 全链路冗余 + 混沌工程，金融/电信级
串联累乘 vs 并联冗余：高可用的两条基本算术

消除单点：从下往上逐层做

高可用的工程落地，本质是逐层找出单点并消除它。典型链路自下而上有这些单点：

层级单点风险冗余手段
机房 / 区域机房断电、光纤挖断、自然灾害多可用区（同城双活）；关键业务多区域（异地多活）
网络入口单台负载均衡 / 单运营商线路LB 集群 + VIP/Anycast；多运营商 BGP；DNS 多解析
应用服务单实例崩溃、发布失败≥2 实例分布在不同机架/可用区；滚动发布 + 健康检查
注册发现注册中心集群全挂注册中心自身集群化；客户端缓存服务列表兜底
缓存单 Redis 实例、单分片热点主从 + 哨兵 / 集群分片；本地缓存兜底
消息队列单 Broker、单副本多副本 + 多分区 + ISR；生产者本地兜底队列
数据库主库宕机（最难的一环）主从 + 自动故障转移；半同步减丢失；分片 + 多副本
依赖的第三方外部 API 不可用熔断降级 + 超时控制 + 兜底数据

优先级：先消除「发生概率 × 影响面」最大的单点。通常数据库主库和网络入口排最前，因为它们一挂全站不可用且恢复慢。

三种容灾形态对比

主备（冷备 / 热备）

备用环境平时不承载流量或只承载少量，主出问题时切换过去。

  • 冷备：备机停机，需启动 → 恢复慢（分钟~小时）
  • 热备：备机运行并同步数据 → 切换较快（秒~分钟）
  • 成本低、实现简单，是多数系统的起点

双活 / 多活（同城）

两个机房同时承载流量，互为备份。

  • 切换几乎无感，资源利用率高（不再闲置一倍资源）
  • 难点在数据一致性：同城延迟低（<3ms）可做强一致同步；跨城则必须接受最终一致

异地多活（单元化）

按用户维度（如 user_id 取模）把流量切分到不同地域，各单元自治。

  • 最高可用性与扩展性，单地域故障只影响部分用户
  • 复杂度极高：需要流量调度、数据同步、单元封闭、跨单元兜底四套机制配套

故障转移（Failover）的关键细节

「能自动切换」只是及格线，真正决定可用性的是下面这些细节：

① 故障检测不能只看心跳。要组合：进程存活 + 端口探活 + 业务探活（真实查询）；多次失败再判定，防误判
② 防脑裂旧主可能只是网络分区而非真死。必须用 fencing：租约、STONITH、多数派投票，确保旧主不能再写
③ 数据丢失权衡异步复制切换会丢数据；半同步可保证至少一个副本收到。选哪个取决于业务能否容忍丢失
④ 切换要有幂等切换流程可能被重复执行，每一步都要可重入，且要有明确的「切换中」状态锁
⑤ 切后校验切换完成不等于可用：要检查复制拓扑、连接池指向、DNS 缓存、只读设置是否正确

RTO 与 RPO 必须提前定义：RTO（Recovery Time Objective）是「多久能恢复服务」，决定要不要做热备；RPO（Recovery Point Objective）是「最多丢多少数据」，决定用异步还是同步复制。这两个数字应由业务方给出，架构方案才有依据。

深入自检

三个 9 和四个 9 的成本差多少？

大致一个数量级。三个 9 靠多实例 + 自动重启 + 主备数据库就能达到；四个 9 要求多可用区部署、数据库自动故障转移、全链路无单点、完善的监控告警与值班响应；五个 9 则需要多区域、单元化、混沌工程常态化验证、以及 7×24 的快速响应团队。绝大多数业务做到三个 9 到四个 9 之间是性价比最高的。

为什么数据库是高可用最难的一环？

因为它是有状态的。无状态服务可以随意起新实例，而数据库新实例必须拥有一份正确且最新的数据副本。这带来三个难题：复制延迟（切过去数据可能不全）、脑裂风险（旧主还活着会造成双写）、以及切换点选择（哪个副本数据最新）。所以数据库高可用通常依赖成熟方案（如 Raft/Paxos 多数派）而非自研。

异步复制切换一定会丢数据吗？

只要主库已提交但 binlog 尚未传到从库，那部分数据就会丢。降低丢失的办法：半同步（至少一个从库收到才返回，仍可能丢——因为 ack 后主库崩溃、从库还没落盘的场景）、或多数派强一致（Raft，提交即多数派持久化，不丢但有延迟）。选择取决于 RPO：能容忍丢几秒数据用异步，不能容忍就用强一致方案并接受写入延迟上升。

多活架构里跨地域延迟怎么破？

核心原则是「让数据和计算在同一地域」。异地多活采用单元化：按用户维度切分，一个用户的全部请求和全部数据都在同一个单元内，跨单元调用极少。跨地域数据同步走异步消息队列 + 冲突解决策略（时间戳、版本号、业务规则）。真正无法切分的全局数据（如全局唯一 ID、库存）单独设计，或用「中心单元 + 局部单元」的混合模式。
