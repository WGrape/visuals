断电或进程崩溃时，你写入的文件可能只落了一半。要做到「要么完整新版本、要么还是旧版本」，靠的不是 write，而是 fsync + 原子 rename 的组合拳。

01安全写文件三步法

永远不要原地覆盖热文件。先写同目录临时文件，fsync 它，再 rename 到目标名——rename 在同一文件系统上是原子的，读方要么看到旧版、要么看到完整新版，绝不会看到半份。

# Python：原子替换一个配置文件
import os, tempfile
def atomic_write(path, data: bytes):
    d = os.path.dirname(path) or '.'
    fd, tmp = tempfile.mkstemp(dir=d)          # 同目录临时文件
    try:
        with os.fdopen(fd, 'wb') as f:
            f.write(data)
            f.flush()
            os.fsync(f.fileno())               # 数据真正落到盘
        os.replace(tmp, path)                  # 原子改名（跨平台）
    except BaseException:
        os.unlink(tmp)                         # 失败清场，绝不留半份
        raise
# 不要直接 open(path,'w').write(...) —— 崩溃会留下半份文件

02fsync / fdatasync / sync 怎么用

write() 只是把数据交给内核页缓存，电一断就没了。fsync 强制刷盘（数据+元数据），fdatasync 只刷数据（若大小不变可省一次元数据写），sync 刷全系统。

# 命令行观测与强制刷新
sync                                   # 把所有脏页刷盘（全系统）
sudo sh -c 'sync; echo 3 > /proc/sys/vm/drop_caches'  # 刷盘并清缓存（调试用）

# 磁盘 writeback 参数（决定脏页多久被内核自动刷）
cat /proc/sys/vm/dirty_expire_centisecs   # 脏页最长可逗留(厘秒)，默认 3000=30s
cat /proc/sys/vm/dirty_ratio             # 脏页占内存比例上限，触发同步写

# C：O_DSYNC 让每次写都等价于 fdatasync
fd = open("log", O_WRONLY|O_DSYNC); write(fd, buf)   # 返回即已落盘

03持久化 vs 性能的取舍

  • 每写必 fsync 最安全但最慢（数据库 WAL 是批量+周期 fsync 折中）。
  • 数据库层常见旋钮：innodb_flush_log_at_trx_commit=1（每次提交落盘）、=2（只写 OS 缓存，靠 OS 刷）、=0（每秒）。
  • ext4 的 barrier 默认开，保证「先数据后元数据」顺序；关掉能提速但掉电可能丢更多。
  • SSD 有电容断电保护的，可以适度放宽 fsync 频率；机械盘/HDD 不建议。
要点：判断标准：丢一条能否接受？能接受→每秒 fsync；不能→每次 fsync 或 O_DSYNC。永远别用『默认写缓存』当持久化保证。

04怎么验证崩溃一致性

  • 用 dm-delay / dm-flakey 注入「写一半断电」，再挂载检查文件是否仍是完整旧版或完整新版。
  • chaos 工具随机 kill -9 进程，重启后跑校验脚本比对哈希。
  • 数据库侧：kill -9 后重启，看能否正常 recovery，binlog/redo 是否连续。

第一层 · 概念与判定：什么时候必须 fsync

只要数据是崩溃后不能丢的（元数据、钱包流水、配置），写完就要 fsync；纯缓存/可重建的临时文件则不必。

Python 安全写：写临时 + fsync + 原子 rename + fsync 目录

# 安全写文件三步法（防半份 + 防断电丢）
import os
def safe_write(path, data):
    tmp = path + ".tmp"
    with open(tmp, "w") as f:
        f.write(data)
        f.flush()
        os.fsync(f.fileno())          # 落盘数据
    os.rename(tmp, path)              # 原子替换
    # 注意：rename 后还需 fsync 父目录，否则目录项可能没落盘
    dirfd = os.open(os.path.dirname(path), os.O_RDONLY)
    os.fsync(dirfd); os.close(dirfd)

数量级：一次 fsync 约 0.1–10ms（取决于盘与是否写透），比不 fsync 慢 10–1000 倍；所以高频写要靠批量与 WAL amortize。

第三层 · 排障与边界：四个坑

  • 只写不 fsync：数据在 page cache，断电即丢——以为写成功了其实没落盘
  • 覆盖式写：直接写原文件，崩溃时文件变成「半新半旧」无法恢复——必须写 .tmp 再 rename
  • 忘 fsync 目录：rename 成功但父目录项没落盘，崩溃后新文件「不存在」——rename 后 fsync 父目录
  • 误解 O_DIRECT：它绕过 page cache 但不保证顺序与原子，仍需 fsync/fua

第四层 · 原理与取舍

为什么「写临时文件 + rename」是原子且安全的？

因为 POSIX 保证 rename 对同一个文件系统是原子操作：要么旧文件在、要么新文件在，不会出现「写了一半」的中间态。配合先写 .tmp 再 rename，崩溃时要么看到旧文件（.tmp 残留可清），要么看到完整新文件。这才是「断电不丢、不半份」的标准做法，而不是原地覆盖。

fdatasync 比 fsync 快在哪，能随便用吗？

fsync 刷新数据+所有元数据（包括 mtime、大小）；fdatasync 在文件大小没变时只刷数据、跳过元数据更新，少一次元数据写，所以略快。但当本次写入改变了文件大小，两者差不多。对 append-only 日志可优先 fdatasync 省一点；对改变大小的写完仍建议 fsync 一次保元数据。

为什么 rename 之后还要 fsync 父目录？

因为 rename 只把「新文件已存在」这件事记进目录的 page cache，目录项本身没落盘。崩溃后文件系统恢复可能看不到这次 rename，新文件仍然「不存在」，但数据其实已经在盘上（成了孤儿 inode）。所以关键写入要 fsync 父目录，确保目录项持久化——这是最常漏的一步。
