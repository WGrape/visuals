Redis 应该承担哪种工作负载？

先按数据是否可重建、响应时延、更新方式和故障后能否恢复作决策，再选择缓存、计数、会话或专用存储。

第一步：明确数据的权威来源

Redis 把热点数据留在内存，适合以低延迟执行简单、原子的操作；这不等于每份数据都应该由它独占。购物车会话与商品价格的权威来源可能不同，故障后的恢复要求也不同。

问题适合 Redis 的回答应换方案或补措施的信号
丢失或回退后能否恢复？可从数据库重建的缓存、短期会话，或业务允许的持久化窗口。唯一的订单、余额等权威记录不能靠缓存层独占。
数据量是否能负担内存成本？高频、有限大小的热数据。冷数据、大对象或无边界增长的 key 集合会放大容量与成本。
操作是否适合服务端原子执行？计数、排行榜、去重以及有界集合。复杂关系查询、跨多条记录的强事务应回到专门的数据存储。
消息需要怎样的交付保证？可丢失的即时通知可考虑 Pub/Sub；需要持久消费时评估 Stream。需要复杂回放、严格交付语义与积压治理时，评估专用消息系统。

第二步：按场景选择角色，而不是按产品列功能

热点缓存

先确认缓存未命中时如何回源，以及写入后允许多长时间读到旧值；再确定 TTL、容量和故障降级。

计数与排行榜

INCR、ZINCRBY 把单 key 操作留在服务端；如果计数不可丢，仍需权威记录或可靠的落库链路。

锁与协调

SET NX EX 可以处理一些互斥场景；涉及长任务和强一致资源时，还需考虑续期、误释放及 fencing token。

消息与会话

区分可丢的广播、需重试的任务和可重建的会话；不要把“有发布订阅”当成可靠队列的承诺。

第三步：在选型时写下失败路径

  1. 如果 Redis 不可用：请求是回源、降级，还是直接失败？权威数据在哪里？
  2. 如果单个 key 变大或命令耗时变长：会不会阻塞同实例上的其他业务？
  3. 如果节点切换或从持久化文件恢复：业务能容忍怎样的丢失与陈旧窗口？
  4. 如果数据跨节点：是否需要重新设计 key、原子操作范围和访问路径？
边界判据：Redis 很适合“加速或维护可控规模的状态”，但是否能做唯一主存储，取决于业务明确接受的数据丢失窗口、内存成本和恢复方案，而不是名字里有没有“数据库”。

按问题继续深入

  • 需要选具体结构和命令：五类数据类型的取舍 · 按场景查命令。
  • 担心慢命令拖垮实例：线程模型与阻塞边界。
  • 决定允许丢多少数据：RDB / AOF 的恢复与窗口。
  • 需要切换或横向扩展：复制、哨兵与集群架构。
  • 要做事件广播：Pub/Sub 的可靠性边界。
