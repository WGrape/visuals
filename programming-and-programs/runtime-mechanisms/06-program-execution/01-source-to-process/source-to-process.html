全景

一条命令背后发生了什么

阶段一

编译与链接（构建期）

  1. 预处理（C/C++）：宏展开、头文件包含、条件编译。
  2. 编译：词法 → 语法 → 语义 → IR 优化 → 目标代码，产出 .o。
  3. 汇编：把汇编变成机器指令（可重定位目标文件）。
  4. 链接：符号解析、节合并、重定位；静态库直接拷入，动态库只记录依赖。
构建期的产物是一个符合操作系统格式的可执行文件（Linux 上是 ELF，macOS 是 Mach-O，Windows 是 PE），里面描述了各段内容与如何装载。
阶段二

装载：从文件到进程

  1. fork：复制当前进程（写时复制），得到新进程。
  2. exec：用新程序替换进程映像——建立新的虚拟地址空间。
  3. 按可执行文件头，把代码段、数据段 mmap 到虚拟内存（按需分页）。
  4. 装载动态链接器（如 ld.so），解析依赖的动态库并装载。
  5. 完成重定位与 GOT 填充；设置栈（argc/argv/env）。
按需分页：装载并不把整个文件读入内存，而是建立映射，真正访问时由缺页中断调入。所以启动快、内存省。
阶段三

runtime 初始化（语言相关）

语言main 之前还要做什么
Clibc 初始化、全局构造（C++ 的 static 对象构造）、设置堆
Go初始化调度器（GMP）、内存分配器与 GC、创建主线程与 sysmon、执行各包 init，最后调用 main.main
Java启动 JVM：类加载、内存区域划分、JIT 编译器就绪，再执行 main 方法
Python初始化解释器与对象系统、编译源码为字节码，再交给解释循环执行
Go 的 init 顺序容易踩坑：先初始化被依赖的包，再初始化当前包；同一包内多个 init 按文件名的字典序执行。不要在 init 里做有顺序依赖的复杂逻辑。

为什么启动速度差这么多

🐹
Go：快
静态链接 + 直接机器码，装载后少量 runtime 初始化即进入 main
☕
Java：较慢
JVM 自身启动、类加载、解释器就绪；且 JIT 未预热时性能未达峰值
🐍
Python：中等
解释器启动 + 编译为字节码；导入大量第三方包会显著拖慢启动
Serverless / 短任务场景特别在意启动速度，这也是 Go 与 Rust 在这类场景受欢迎的原因；Java 则通过 AOT（GraalVM Native Image）来缩短启动。
面试问答

高频问题

Q1：从敲下运行命令到 main 执行，中间有哪些阶段？
构建期：预处理（C/C++）、编译、汇编、链接产出可执行文件；运行期：fork/exec 创建进程、装载器把各段映射到虚拟内存、装载动态库并完成重定位、runtime/库初始化，最后调用 main。
Q2：fork 和 exec 分别做什么？
fork 复制当前进程创建子进程（写时复制）；exec 用新程序替换进程的地址空间与映像。两者组合实现「启动一个新程序」。
Q3：装载时是把整个程序读进内存吗？
不是。通常用 mmap 建立映射并按需分页，真正访问某页时才由缺页中断调入物理内存，因此启动更快、内存更省，代码段还能在进程间共享。
Q4：Go 程序在 main 之前做了什么？
初始化调度器（GMP）、内存分配器与 GC、创建主线程与 sysmon 监控线程，按依赖顺序执行各包的 init 函数，最后才调用 main.main。
Q5：为什么 Go 启动比 Java 快？
Go 是静态编译链接的机器码，装载后只需少量 runtime 初始化；Java 需要启动 JVM、加载类、初始化解释器与 JIT，且热点代码还要预热才能达到峰值性能。
Q6：什么是按需分页？好处是什么？
装载时只建立虚拟地址到文件的映射，不立即读入内容；访问时才触发缺页中断把页调入。好处是启动快、内存占用少，且未使用的代码永远不会占用内存。

从源码到进程的四步与耗时

阶段工具 / 产物关键事实
预处理cc -E → .i展开 #include/#define；删注释
编译cc -S → .s（汇编）含词法/语法/语义分析、优化、代码生成
汇编as → .o（目标文件）生成机器码 + 符号表 + 重定位表
链接ld → a.out符号解析 + 重定位；静态/动态两种
对比项静态链接动态链接
产物大小大（库被拷贝进来）小（只记依赖）
启动速度快（无需加载 .so）慢一点（要加载并重定位）
内存每进程一份库的副本多进程共享，省内存
更新改库要重新链接换 .so 即生效
Go 默认静态（CGO 关闭时）CGO 开启时动态

符号解析的两个经典错误：① undefined reference = 链接器找不到符号定义（库没给或顺序错）；② multiple definition = 同一个符号被定义多次（头文件里写了定义而非声明）。

观察每个阶段的命令

# 完整链路
gcc -E main.c -o main.i       # 预处理
gcc -S main.i -o main.s       # 编译成汇编
as   main.s -o main.o         # 汇编
ld   main.o -o a.out ...      # 链接（实际会链接 crt1.o、libc 等）

# 看目标文件
nm main.o
#   U printf           <- U = undefined，符号在本文件未定义，需要链接时解析
#   T main             <- T = text 段（代码）中有定义
#   D g_var            <- D = data 段
#   B g_uninit         <- B = BSS（未初始化数据，不占文件空间）

objdump -h main.o         # 各段信息
readelf -r main.o         # 重定位表：哪些位置的地址还没定
readelf -S main.o         # 段头表

# 动态链接相关
ldd a.out                 # 依赖的动态库
# 运行时延迟绑定：函数第一次调用时才解析地址（PLT/GOT 机制）
#   GOT: 全局偏移表（数据段，可写）   PLT: 过程链接表（代码段）
#   第一次调用：PLT -> 解析器 -> 填 GOT -> 跳转
#   后续调用：  PLT -> 直接读 GOT -> 跳转（只多一次间接跳转）
# 关闭延迟绑定：-Wl,-z,now（安全加固常用，启动变慢）
# Go 的四步（go build -x 可以看到）
go build -x -o app main.go
# 实际执行：compile（编译包）-> link（链接）
# 中间产物在 $GOCACHE 里
go tool compile -S main.go | head -30      # 看 Go 的汇编
go tool nm app | head -20                  # 看符号表
go tool objdump -s 'main.main' app         # 反汇编某个函数

# Go 的二进制特点
file app            # ELF executable, statically linked（默认静态）
ldd app             # not a dynamic executable（CGO 关闭时）
# 这就是为什么 Go 程序拷到任何同架构 Linux 都能跑
# 代价：二进制较大（最小 hello world 约 1.5~2MB）
# 裁剪：-ldflags="-s -w" 可减 25~30%

排障清单

症状原因处理
undefined reference to xxx库没链接；或库顺序错（依赖者要在前）把 -lfoo 放在依赖它的 .o 之后；检查 -L 路径
multiple definition of xxx头文件里放了变量定义头文件只放 extern 声明；或用 static/inline
C/C++ 混编链接失败C++ 的名字改编（name mangling）C 的头文件加 extern "C" { ... }
error while loading shared libraries运行时找不到 .soldconfig；LD_LIBRARY_PATH；或用 -Wl,-rpath 编进二进制
改了 .so 但没生效有缓存 / 路径不对ldconfig 刷新缓存；确认 ldd 指向的路径
静态链接报 glibc 警告glibc 的部分函数（getaddrinfo 等）动态依赖用 musl（Alpine）；或接受警告并静态链接其余部分
二进制太大符号表 + 静态链接-s 去符号；Go 用 -ldflags="-s -w"；strip

为什么库的顺序很重要：链接器按从左到右扫描，只会从后面的库里找当前「未定义符号」。所以 gcc main.o -lmath 能过，gcc -lmath main.o 会报 undefined reference。这是初学者的高频困惑点。
