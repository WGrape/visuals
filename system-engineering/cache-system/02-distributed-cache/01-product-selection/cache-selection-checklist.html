一、五问定方案

Q1：数据总量多大？单机内存装得下吗？
A：几十 GB 以内、单机能装下 → 单实例 + 主从即可，不必上集群。上百 GB 或需要线性扩展 → 必须分片/集群。这个判断直接决定架构复杂度上不上一个台阶。
Q2：value 的结构是什么？只用字符串够吗？
A：只存序列化后的对象（JSON/Protobuf）→ 纯 KV 产品足够。需要按字段读写、需要排行榜、需要计数、需要队列语义 → 必须有 Hash/ZSet/List/Stream 等结构，选 Redis 系。
Q3：缓存丢了可以接受吗？
A：能接受（缓存只是加速，丢了回源即可）→ 不需要持久化，反而要关掉持久化避免额外开销与写放大。不能接受（例如用它存会话、分布式锁、限流计数）→ 必须开持久化 + 高可用，且要考虑它已经不是"纯缓存"了。
Q4：能容忍多久的陈旧数据？
A：这个答案直接变成 TTL。容忍 5 分钟就设 5 分钟，别随手填 30 分钟。容忍度为 0 的强一致场景，缓存可能根本不该出现在架构里（见「收益与代价」）。
Q5：谁来运维？
A：有专职运维、需要定制与深度调优 → 自建。没有 → 云托管。别高估团队的运维意愿，缓存集群的故障往往发生在半夜。

二、把直觉变成可比较的打分表

对每个候选方案按下面维度打分（1–5），加权求和。重点是把"感觉 Redis 更好"变成"Redis 在结构丰富度上 5 分、Memcached 2 分，但我们只用 get/set，这一项权重设为 1"。

维度建议权重打分要点
数据结构匹配度高需要的结构是否原生支持，还是要客户端拼
容量与成本高内存占用、可否用磁盘型降本、扩容单价
性能（吞吐 / 延迟）中按实测，不要看宣传数字
高可用能力中高故障转移是否自动、RTO/RPO 多少
运维成本中高自建还是托管、监控告警是否现成
生态与迁移成本中客户端库成熟度、是否用了私有特性
团队熟悉度中出问题时能不能快速定位，这一项常被低估

⚠️ 权重里「团队熟悉度」不要设成 0。凌晨三点缓存集群出问题，团队熟悉的产品和不熟悉的产品，故障恢复时间可能差一个数量级。

三、五种选型反模式

  • 先选产品再定需求——"我们用 Redis"然后才想缓存什么。正确顺序是先量化和定义需求（收益与代价那一篇），再选工具。
  • 为了用上某个酷特性而选型——为了用 Stream 做消息队列而选 Redis，结果消息队列该有的可靠性全要自己补。
  • 把缓存当存储用——把唯一数据源放在缓存里，还不开持久化。缓存的定位是"可重建"，违背这一点迟早丢数据。
  • 忽略客户端库质量——服务端选得很好，客户端库连接池有 bug、超时设置不合理，线上一样炸。
  • 只测功能不测容量——上线前没压过"缓存全空"和"缓存全挂"两种极端状态，等到真发生才发现回源量扛不住。

四、选完之后必做的六件事

① 定 key 规范
业务前缀 + 版本 + 标识，例如 order:v2:{orderId}。带版本号才能在迁移时批量失效。详见 热 key 与大 key。
② 定 TTL 并写进文档
每个 key 的过期时间都要有依据（业务容忍度），不能是默认值。见 TTL / TTI。
③ 定淘汰策略并预留内存水位
内存上限要有余量，淘汰策略要按访问分布选（LRU 适合有明显热点的，LFU 适合长期稳定的）。见 LRU / LFU。
④ 定读写模式与失效路径
写库之后是删缓存还是更新缓存？后台管理、定时任务、订正脚本的写入口是否都覆盖了？见 缓存读写模式。
⑤ 定降级方案
缓存不可用时怎么办。必须有熔断/限流，否则缓存宕机反而压垮数据库。见 缓存雪崩。
⑥ 上监控
命中率、回源量、内存水位、慢查询、大 key。见 监控与预热。
