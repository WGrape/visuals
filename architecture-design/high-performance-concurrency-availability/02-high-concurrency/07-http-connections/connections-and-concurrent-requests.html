HTTP / 并发边界

连接数、并发请求与 QPS

“有 100 个用户”不能推导出“有 100 条连接”，也不能推导出“同时处理 100 个请求”。先明确每个数字在哪一层计数。

一个用户可以发起多个请求；一个客户端实例可以维护一个连接池；一条连接在不同 HTTP 版本下又能承载不同数量的同时进行的请求。

把五种数量分开

它们沿请求路径出现，但不存在固定的 1:1 换算。

用户 / 调用方

人、进程或业务租户等身份；一个用户可开多个页面或客户端。

客户端实例

浏览器、Session、HTTP 客户端对象；可能复用池内多条连接。

传输连接

H1/H2 通常是 TCP（HTTPS 再加 TLS）；H3 是基于 UDP 的 QUIC 连接。

在途 HTTP 请求

已发出但尚未完成的请求；是否已由应用处理需另看服务端边界。

完成 QPS

每秒完成多少次请求，是一段时间的速率，不是瞬时在途数量。

本地待发 ≠ 已发出。 排在任务队列或连接池里的请求可能尚未占用连接，更不能直接算作服务端正在处理的请求。

同一条连接可同时承载多少请求？

协议传输与复用单连接上的同时进行请求仍会受什么限制
HTTP/1.1TCP；可持久连接，前一个响应结束后可复用。通常不使用流水线时，每条连接仅 1 个活跃请求；要并行发出更多请求，通常开多条连接。连接池上限、服务端资源、排队与限流。历史上的 HTTP/1.1 流水线不是这里的默认假设。
HTTP/2通常运行在一条 TCP 连接上；多个请求映射为不同的并发流并复用连接。可以有多个；受对端协商的 SETTINGS_MAX_CONCURRENT_STREAMS 等约束，不是无限。流控、客户端/服务端设置与业务处理能力；底层 TCP 丢包仍可能影响同连接上的流。
HTTP/3基于 UDP 的 QUIC 连接，不是 TCP 连接；请求使用 QUIC 流。可以有多个；并发流数量仍受对端公布的 QUIC 流上限及其它资源约束。流控、服务器接纳与限速；QUIC 消除跨流的传输层队头阻塞，并不保证业务处理无排队。

不要把协议能力写成容量保证。 H2/H3 能在一条连接上多路复用，并不代表服务器会同时执行业务逻辑，也不代表每条连接必定只承载某个固定数目的流。

两个有前提的例子

示意 A · 非流水线 H1

1 个客户端，6 条连接

若连接均可用、各有待发请求，客户端最多能在这些连接上同时发送 6 个活跃请求。第 7 个可能等池内连接空闲。

不是 1 个用户 = 1 个请求。

示意 B · H2 多路复用

1 个客户端，1 条连接

假设双方设置允许并且对端实际允许 100 个并发流，且没有更早的瓶颈，那么这条连接可同时承载至多 100 个请求流；多余请求需要等待流名额或使用其它符合策略的连接。

100 是例子的协商值，不是 H2 的通用常数。

即使在途请求数相同，完成 QPS仍依赖请求耗时和实际完成情况。稳态、同一统计边界下，可用 平均在途量 ≈ 完成速率 × 平均驻留时间 分析，而不是简单用连接数计算吞吐。

Python 客户端默认行为不要猜

requests 常规使用基于 HTTP/1.1；会话里的连接池负责复用与配置连接数，增加线程或任务并不会自动启用 H2。aiohttp 的常规客户端请求也使用 HTTP/1.1；协程并发不等于单连接多路复用。

httpx 默认是 HTTP/1.1；需要安装 H2 支持（例如 httpx[http2]）并显式设置 http2=True。这只是允许协商 H2；对端不支持时仍可能使用 H1。是否使用 H3，需另选具备 H3 能力的实现与配置，不能从上述默认值推断。

排查时先问四个问题

  • 统计的是用户、客户端对象、TCP/QUIC 连接、流，还是某一端的在途请求？
  • 连接实际协商了 H1、H2 还是 H3？连接池和对端并发流上限是多少？
  • 排队发生在本地任务队列、连接池、网关还是服务内部？不同边界不能合并计数。
  • 讨论的是瞬时峰值、时间窗口平均并发，还是完成 QPS？

核心速览

一句话连接数是「同时在传的请求数」，并发数是「服务端同时在处理的请求数」
核心公式并发数 ≈ QPS × 平均响应时间（利特尔法则）
常见误解以为连接数越多吞吐越高——超过某个点后反而下降
池化的价值复用连接省掉握手，同时限制总量防止打爆下游
连接数、并发数、QPS 三者通过利特尔法则互相约束

一、三个数字的关系

# 利特尔法则：L = λ × W # L = 系统中的平均并发数（正在处理的请求数） # λ = 到达率（QPS） # W = 平均响应时间（秒） # 例：QPS = 1000，平均 RT = 50ms 并发数 L = 1000 × 0.05 = 50 # 意味着同一时刻平均只有 50 个请求在处理 # 反过来：如果连接池只有 20，平均 RT 50ms 最大 QPS = 20 / 0.05 = 400 # 连接池成了吞吐的天花板 # 再反过来：想支撑 2000 QPS，RT 50ms 需要并发 = 2000 × 0.05 = 100

二、连接数是不是越多越好

阶段现象原因
过少吞吐上不去，请求排队等连接连接池成为瓶颈，CPU 利用率低
合适吞吐随连接数线性增长CPU 被打满但还没过载
过多吞吐不涨，延迟飙升，错误率上升上下文切换、内存占用、锁竞争、下游被打爆
连接数过多的四个代价

① 内存：每条连接都有读写缓冲区，几万条连接就是几百 MB；② 上下文切换：活跃连接多，调度开销陡增；③ 下游压力：每个连接对应下游一个连接，会把数据库/缓存直接打爆；④ 排队恶化：并发越高，队列越长，延迟非线性增长。

三、连接池怎么设

经验起点连接数 = CPU 核数 × 2 ~ 4（IO 密集型可更大）
更靠谱的公式连接数 = QPS × RT，再留 20%~30% 余量
必须设超时获取连接超时、读写超时都要有，否则线程会永久阻塞
必须设上限池的最大值是保护下游的最后一道闸门
要监控等待连接的队列长度是最关键的信号
// Go 标准库 http.Transport 的关键参数 tr := &http.Transport{ MaxIdleConns: 100, // 总的最大空闲连接 MaxIdleConnsPerHost: 20, // 每个 host 的空闲连接（很关键） MaxConnsPerHost: 100, // 每个 host 的总连接上限 IdleConnTimeout: 90 * time.Second, // 空闲连接保留时长 } client := &http.Client{ Transport: tr, Timeout: 5 * time.Second, // 整体超时，必须有 } // 坑：MaxIdleConnsPerHost 默认是 2！ // 不显式调大的话，高并发下大量连接刚用完就被关闭， // 表现为大量 TIME_WAIT 与握手开销。

四、HTTP/1.1、HTTP/2 的差异

HTTP/1.1HTTP/2
一条连接同时传1 个请求（串行）多个请求（多路复用）
并发靠什么开多条连接（浏览器限 6 个/域名）一条连接即可
需要的连接数≈ 并发数远小于并发数（几十条足够）
队头阻塞连接级别TCP 级别（HTTP/3 才彻底解决）
header 开销每次都发完整 headerHPACK 压缩 + 连接级缓存

这也是为什么 HTTP/2 下连接池可以设得很小：一条连接就能承载几百个并发请求，连接数不再等于并发数。此时连接池的合理配置从「匹配并发数」变成「匹配带宽需求」。

五、深入自检

并发数 1000 是不是就要 1000 个线程？

不必。异步 IO（epoll / 协程）下，几个线程就能撑几万并发连接，因为大部分连接大部分时间是空闲的。真正需要的是「同时在 CPU 上执行的数量」，那应该匹配核数。

为什么加了连接数反而变慢？

超过了系统的最优并发点。此时 CPU 花在调度和锁竞争上的时间超过实际工作时间，延迟也因为排队而暴涨。判断方法：逐步加压，看吞吐何时不再增长。

TIME_WAIT 很多是不是有问题？

大量 TIME_WAIT 通常说明连接在被频繁创建和销毁（没复用），或者主动关闭方是自己。解决：开启 keep-alive、调大连接池、让客户端复用连接。

连接池大小和下游容量怎么匹配？

上游总连接数不能超过下游的最大连接数。如果 10 个实例各开 100 条连数据库，数据库就要承受 1000 条连接——很可能超出它的 max_connections。这就是为什么连接池要按「实例数」分摊。

怎么判断连接池是不是瓶颈？

看「等待获取连接的时间」。如果平均等待时间长、池的活跃连接长期打满，但下游 CPU 还很空闲，就说明池太小。反之如果下游已经饱和，加大池只会让情况更糟。

记住一句并发数 = QPS × RT
过多征兆延迟涨、吞吐不涨
Go 默认坑MaxIdleConnsPerHost 默认 2
HTTP/2 后连接数不必等于并发数
