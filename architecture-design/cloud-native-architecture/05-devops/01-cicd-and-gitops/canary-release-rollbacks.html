灰度发布：指标门槛、流量分配与回滚

把“发布成功”定义为可观测的用户结果，再用逐步放量控制一次变更的影响范围。

为什么部署完成不等于发布成功

灰度的四阶段流量分配与放行回滚门槛

新容器能启动、健康检查为绿，只说明服务进程活着；用户请求仍可能因为某个新代码路径报错、延迟变长或数据写错。灰度发布把少量真实流量先分配给新版本，在每一步比较错误率、延迟和关键业务结果，确认达到门槛后再扩大比例。回滚条件应该在发布前写好，避免故障发生时临时争论。

对照组需要尽量可比。若灰度只接到一个低负载地区，而旧版承受高峰，简单比较平均延迟会误导；若用户一次流程的多个请求落到不同版本，又可能出现会话状态不兼容。可以按用户或会话做稳定分流，并按地域、端点和设备分层观察。灰度比例不是唯一安全变量，受影响的绝对用户数、关键请求类型和持续时间同样重要。

逐步推演

设定门槛

发布前写明错误率、延迟、业务指标、最小样本数与自动暂停条件。

小流量验证

稳定分配用户或会话，比较相同类型请求的新旧版本表现。

逐步放量

每一档等待足够数据，再检查功能、容量与下游变化。

回滚与复盘

触发条件时切回流量，并单独处理数据与兼容性问题。

一次 1% → 10% → 50% → 100% 的发布

先在 1% 流量验证启动、主路径与埋点是否正常。样本太少时，即便没有错误也不能证明新版本可靠；要等待足够请求数。到 10% 时观察错误率、P95/P99 延迟、资源与关键转化。到 50% 时下游容量、缓存行为和数据库压力可能发生非线性变化。到 100% 后继续保持观察窗口，因为某些夜间任务、低频接口或长会话只有在更长时间后才触发。

门槛关注的证据触发动作
错误率新旧版本同类请求差异超过预设门槛暂停或回滚
延迟P95/P99 与超时数排除排队、冷启动和下游变化
业务指标下单、支付等完成率功能正确但结果退化仍需停放
数据正确性写入不变量和异常记录需考虑数据修复，单回滚代码不足够

回滚的边界：代码能退，数据未必能退

若新版本写入了旧版无法读取的数据库结构，直接切回旧代码可能让服务更坏。因此发布前要检查数据库迁移是否向前、向后兼容，常用步骤是先扩展结构、再让新旧版同时兼容、最后清理旧结构。消息格式、缓存键和外部 API 也有类似问题。回滚预案要明确流量切换、配置撤回、任务停止、数据修复和负责人。

自动化门槛应允许人工判断，但不能只凭一个短窗口上的零错误放量。低流量接口需要最小样本数或合成探针；高风险写路径可使用影子流量、只读验证或先对内部用户开放。若指标管道本身延迟五分钟，灰度每分钟推进一次就没有观察意义。

复盘一场发布事故

  1. 确认变更版本、开始时间、各阶段灰度比例和用户受影响范围。
  2. 对照新旧版本在同一地域和端点的指标，区分版本问题与全站依赖故障。
  3. 检查回滚是否真正恢复业务指标；对错误写入的数据制定单独修复方案。
  4. 更新发布门槛、自动暂停条件与演练脚本，让同类事故下次更早停止。

练习：新版本在 1% 流量零错误，但只有 20 次请求；在 10% 时支付成功率下降。你会继续放量吗？先列出样本量、支付端点分布和回滚条件，再给出决定。

门槛如何避免误报和漏报

错误率从 0.1% 升到 0.2% 看似翻倍，若灰度只有 20 个请求，可能只是一个偶然失败；若有百万请求，就需要立即关注。发布门槛应同时规定最小样本量、观察时间和允许的绝对失败数。还可以用同地域、同端点的旧版流量作对照，排除共享数据库故障。某些错误只发生在新用户、特定请求体或夜间定时任务，聚合指标会掩盖它们；因此关键路径要单独分桶。

灰度回滚并非只是把负载均衡权重改回零。队列里可能还有新版本生产的消息，数据库里可能已有新字段或错误值，前端静态资源也可能被浏览器缓存。回滚清单应包括代码、配置、消息消费者、缓存兼容性和数据修复。一次演练应真的从 10% 放量触发自动暂停，再确认用户请求恢复到旧版，并核对没有遗留副作用。

若企业采用 GitOps，Git 中的期望版本与现场紧急回滚状态还要重新对齐，否则控制器下一轮调谐可能把故障版本再次部署。发布系统应记录谁改变了期望状态、何时恢复以及回滚后哪个提交成为新基线。

指标缺失时怎么办

如果新版本发布后错误率指标突然没有数据，不能把“没有错误”当成零错误。埋点或指标管道可能被新版本破坏。发布系统应把关键指标缺失视为暂停信号，用健康探针、日志和业务事件交叉验证。回滚演练也应覆盖监控失明的场景。

灰度指标恢复后，也要确认新旧版本使用相同的采样率和埋点定义；否则两条曲线看似可比，实际分母不同。每次改变指标口径应记录版本与时间。

第一层 · 四种发布策略怎么选

灰度发布（金丝雀）的本质是：用一小部分真实流量验证新版本，确认没问题再放量。它解决的是「一次全量上线，出问题就是全站故障」。

策略流量切换方式回滚速度资源成本适用场景
重建 (Recreate)先停旧再起新慢（分钟级）1×非关键服务、可接受中断
滚动 (Rolling)逐批替换实例中（分钟级）1×默认选择，无状态服务
蓝绿 (Blue/Green)整批切换（两套并存）秒级（切流量即可）2×要求秒级回滚、有状态但要谨慎
金丝雀 (Canary)按比例逐步放量快（改权重）1.05~1.3×需要真实流量验证
影子 (Shadow/Mirror)复制流量到新版本，不影响用户—2×验证正确性但不影响线上
A/B + 特性开关按用户/规则分流秒级（关开关）1×功能级灰度、快速试错
  • 选择口诀：能接受多花一倍资源换秒级回滚 → 蓝绿；需要用真实流量验证 → 金丝雀；只想平滑替换 → 滚动；要零风险验证 → 影子。
  • 金丝雀的两个前提：① 有可判定的指标（错误率、延迟、业务指标）；② 有自动回滚能力（否则需要人盯，失去意义）。
  • 金丝雀不是「滚动发布的同义词」：滚动是「替换实例」，金丝雀是「按流量比例验证」——后者有观察期和决策点。

K8s / Argo Rollouts

# —— K8s 原生滚动发布（最简单）——
kubectl set image deploy/app app=repo/app:v2 --record
kubectl rollout status deploy/app --timeout=5m      # 阻塞等待完成
kubectl rollout history deploy/app                  # 看历史版本
kubectl rollout undo deploy/app                     # 回滚到上一版
kubectl rollout undo deploy/app --to-revision=3     # 回滚到指定版本
kubectl rollout pause deploy/app / resume          # 暂停/继续（金丝雀手动控制用）

# —— 关键参数：控制发布节奏 ——
# spec.strategy.rollingUpdate.maxSurge: 1       # 最多多起几个（默认 25%）
# spec.strategy.rollingUpdate.maxUnavailable: 0 # 最多允许多少不可用（设 0 = 零中断）
# spec.minReadySeconds: 30                      # 新 Pod ready 后再观察 30s 才算可用
# spec.progressDeadlineSeconds: 600             # 超过这个时间未完成则标记失败

# —— Argo Rollouts（金丝雀的事实标准）——
kubectl argo rollouts get rollout app --watch      # 实时观察灰度过程
kubectl argo rollouts promote app                  # 手动推进到下一阶段
kubectl argo rollouts abort app                    # 立即中止并全量回滚
kubectl argo rollouts retry rollout app            # 重试

# —— 必需的健康检查配置（否则灰度没有意义）——
# readinessProbe: 决定 Pod 是否接流量（不通过就不放量）
# livenessProbe:  决定 Pod 是否重启（不要与 readiness 用同一接口！）
# 两者都配，才能让故障实例自动退出灰度

# —— 用 curl 验证流量比例（简单场景）——
for i in $(seq 1 100); do curl -s api.example.com/version; done | sort | uniq -c

最容易漏的一条：minReadySeconds 默认是 0。这意味着 Pod 一 ready 就被认为可用并开始替换下一个——启动后 30 秒才崩溃的问题会被完全掩盖，造成「滚动发布成功但全站挂了」。建议设 30~60 秒。

第三层 · 排障清单

  • 灰度成功但全量后崩溃 → 灰度流量太小（1%）没覆盖到问题路径，或单例/批处理任务没进灰度。解法：关键功能要单独验证；有状态的后台任务不适合灰度，要单独处理。
  • 指标看起来正常但用户投诉 → 只看技术指标（错误率、延迟）不够，必须看业务指标（下单成功率、转化率、页面停留）。有些 bug 不会报错但会算错数。
  • 灰度期间数据库 schema 不兼容 → 这是灰度最大的坑。新旧版本同时在跑，数据库只能有一个版本。必须遵守扩展-收缩模式：① 先加新字段（新旧版本都能跑）；② 灰度切到只用新字段；③ 全量后再删旧字段。不要在同一次发布里改字段名并灰度。
  • 回滚后数据不一致 → 新版本写入了旧版本读不懂的数据。解法：数据格式要向后兼容，或回滚前先停止写入。这也是为什么「数据库迁移」要和「代码发布」分开做。
  • 回滚失败（比不回滚更糟） → 常见原因：镜像被清理、配置不兼容、有状态服务数据损坏。必须定期演练回滚，且保留至少 3 个历史版本。
  • 会话粘滞导致灰度不均 → 如果用户被粘在某个实例上，1% 流量可能实际是「1% 的用户 100% 的时间用新版本」。要按用户维度而非请求维度分流，或关闭会话粘滞。
  • 多个灰度同时进行互相干扰 → 指标无法归因。约定：同一时间只允许一个灰度；用特性开关做功能级并行灰度更可控。
  • Pod 启动慢导致发布超时 → 检查 progressDeadlineSeconds 和 readinessProbe 的 initialDelaySeconds。Java 应用启动 30s+ 很常见，探测配太激进会导致反复重启。

第四层 · 原理与取舍

灰度发布的全部难点都在两个问题上：① 怎么判定「新版本没问题」；② 怎么保证新旧版本共存时数据不出错。前者靠指标，后者靠发布纪律。

  • 指标判定的正确做法：对比基线，而不是看绝对值。正确指标是「新版本错误率 − 旧版本错误率」和「P99 延迟比」。而且要看分位数不看平均值——平均值会掩盖「5% 的请求慢了 10 倍」这种问题。Argo Rollouts 的 AnalysisTemplate 就是把这个对比自动化：同时查询 canary 和 baseline 的 Prometheus 指标，超阈值自动 abort。
  • 统计显著性问题：1% 流量下，如果错误率基线是 0.1%，灰度组的错误数可能只有个位数，统计上根本不可信。经验法则：要让灰度结论可信，至少需要几十到上百个错误样本。所以低错误率场景要么提高灰度比例（如 10%），要么延长观察时间。这是很多「灰度没发现问题」的真实原因——不是没问题，是样本不够。
  • 数据库兼容的扩展-收缩模式（Expand-Contract）：这是灰度能安全进行的前提。三步，每步一次独立发布：① Expand——加新列/新表，新旧代码都能工作（旧代码忽略新列）；② Migrate——双写，然后灰度切读，确认无误后停旧写；③ Contract——删除旧列/旧代码。每一步都要能单独回滚。跳过这个流程做灰度，几乎必然出数据事故。
  • 特性开关 vs 部署灰度：部署灰度控制「哪个版本的代码跑」，特性开关控制「哪个功能启用」。两者正交且应结合使用——部署用滚动/金丝雀保证安全，功能用开关保证可秒级关闭。开关的另一个价值是把「发布」和「上线」解耦：代码可以先全量部署但功能关闭，选个合适的时机打开开关（秒级生效、秒级回滚）。

灰度比例应该设多少？

没有固定答案，取决于你要在多短时间内发现多罕见的问题，以及能承受多大影响面。量化一下：如果故障率是 p，灰度比例是 r，那么灰度期间受影响的用户比例是 r，你发现它需要的时间约等于「灰度期间累计出足够多的错误样本」。所以：① 影响面约束——核心交易链路通常从 1~5% 起步（万一出问题只影响 5% 用户）；② 检出能力约束——如果基线错误率 0.5%，1% 流量每分钟 1000 请求 = 每分钟 0.05 个错误，要积累 30 个错误需要 10 小时，显然不现实。此时要么提高比例到 10~20%，要么延长观察时间，要么降低判定阈值（任何 5xx 都立即回滚）。实践中的折中：核心服务 5% → 20% → 50% → 100%，每级 10~30 分钟，配合「任何严重错误立即自动回滚」。

为什么数据库迁移必须和代码发布分开？

因为灰度期间新旧版本同时运行，但数据库只有一个版本。如果你在一次发布里同时做「改字段名」和「代码灰度」，那么：旧代码还在读旧字段（已被删 → 报错），新代码在读新字段（还没写完 → 读到空）。无论你怎么切流量都会有一部分请求失败。正确做法是扩展-收缩三步走，每步独立发布、独立回滚：先加新列并双写（旧代码不受影响）→ 灰度切读新列 → 确认稳定后停止写旧列 → 最后再删旧列。每一步都能单独回滚，且中间状态下新旧代码都能正常工作。这条纪律是「能安全灰度」的前提——很多团队说「我们做不了灰度」，根本原因就是数据库变更没有按这个流程拆。

自动回滚该不该开？

应该开，但阈值要保守，且要区分「技术错误」和「业务异常」。技术错误（5xx 率、panic、超时率）非常适合自动回滚，因为判据明确、误判成本低——宁可多回滚几次也不要出大故障。业务指标（转化率、GMV）不适合全自动回滚，因为波动大、归因难，容易误触发；更合适的是告警 + 人工确认。配置建议：① 硬阈值立即回滚（如 5xx 率 > 1% 持续 1 分钟）；② 软阈值告警（如 P99 上升 50% 持续 5 分钟）；③ 回滚要有冷却期和次数上限，避免在指标抖动时反复回滚（flapping）；④ 每次自动回滚都要记录并告警——回滚是信号，说明发布流程有问题，不能静静发生。

自检

为什么 1% 灰度零错误不能立即证明安全？

请求数可能太少，低频路径与高负载行为未被覆盖。

回滚代码为什么有时不能恢复服务？

新版本可能已经改变数据、消息或配置格式，旧版无法处理这些状态。
