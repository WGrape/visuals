TDengine 工作负载选型：设备子表和时序查询什么时候合适

从设备数据形态、时间窗口查询和集群运维成本判断是否选择超级表模型。

TDengine

先看读写路径

如果每台设备持续追加时间序列、常按设备和时间范围查询，TDengine 的“一个设备一张子表 + 超级表按标签跨设备查询”能将存储与查询边界对应起来。若主负载是任意维度 JOIN、复杂事务或非时序记录，应先验证现有关系库或分析系统。

  1. 每台设备会产生多少时间点？标签是否稳定，是否需要跨设备按标签聚合？
  2. 保留期、压缩率和副本数一起计算后，容量是否可接受？
  3. 窗口查询和时间范围过滤能否覆盖主要报表？

选型建议：
· IoT / 工业 / 车联网 / 国产化替代、设备数明确且巨大 → TDengine， SQL 友好、压缩比高、开源就有集群，是国产选型首选。
· 云原生监控告警 → Prometheus 生态不可替代。
· 已有 Telegraf、需通用时序 → InfluxDB。
Q："一个设备一张表"在设备数千万级会不会元数据爆炸？
A：这是最常见的质疑。TDengine 通过表元数据常驻内存 + 压缩存储来应对， 官方测试支持千万级表。但要注意：每张表都有固定元数据开销， 设备数超过千万、或设备维度频繁变化时仍需谨慎评估。 实践中若设备维度不稳定（如每次会话生成新 ID），应改用超级表 + 标签的常规模型。
