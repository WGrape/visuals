Redis Hash 数据结构演进史

从压缩列表到字典的完美平衡

Redis 2.0

ziplist 实现 Hash

2010 年，Hash 类型诞生。采用 ziplist（压缩列表）作为底层实现， field-value 对连续存储，内存紧凑。

// ziplist 存储结构
|zlbytes|zltail|zllen|field1|val1|field2|val2|...|zlend|

• zlbytes: 列表总字节数
• zltail: 尾节点偏移量
• zllen: 节点数量
•zlend: 结束标记 (0xFF)
连续内存存储 O(1) 首尾操作 小数据友好 无指针开销
Redis 2.2

字典雏形

开始引入 dict 字典结构，为后续编码转换做准备。 Hash 增长超过阈值时开始考虑字典实现。

// dictEntry 结构
void *key 8 bytes
void *val 8 bytes
dictEntry *next 8 bytes
每个 bucket: 24 bytes
O(1) 单点查询 哈希冲突链
Redis 3.0 ⭐ 重大改进

ziplist ↔ dict 编码转换

引入完整的编码转换机制。当 Hash 字段数小于 hash-max-ziplist-entries（512） 且每个 field/value 长度小于 hash-max-ziplist-value（64字节）时使用 ziplist， 否则转换为 dict。

ziplist 编码
优点: 内存紧凑
缺点: 查询 O(n)
适用: 小数据量
dict 编码
优点: 查询 O(1)
缺点: 内存开销大
适用: 大数据量
自动编码转换 阈值可配置 512 字段阈值 64 字节限制
Redis 4.0

渐进式 Rehash

引入渐进式 rehash 机制。当 dict 需要扩容/缩容时， 分多次完成，避免一次性大内存迁移导致的阻塞。

// 渐进式 Rehash 流程
Step 1: 创建新哈希表 ht[1]
Step 2: 每次操作迁移 1 个 bucket
Step 3: 迁移完成 → 交换 ht[0] ↔ ht[1]
特点: 读写操作分摊重哈希成本
零阻塞扩容 O(1) 均摊复杂度 后台分片执行
Redis 6.0

Hash 编码参数调整

优化 hash-max-ziplist-entries 默认值从 512 → 1000， hash-max-ziplist-value 从 64 → 512 字节。 适应更复杂的应用场景。

// Redis 6.0 配置
hash-max-ziplist-entries 1000
hash-max-ziplist-value 512 bytes
更大 ziplist 阈值 更灵活配置
Redis 7.0+ ⭐ 重大变革

listpack 替换 ziplist

Redis 7.0 将 Hash 的 ziplist 替换为 listpack。 listpack 是 ziplist 的改进版，解决了 ziplist 级联更新问题。

// listpack vs ziplist 区别
ziplist: 每个节点存储前节点长度
    → 删除中间节点可能级联更新

listpack: 存储总长度，跳过式遍历
    → 删除操作无需更新后续节点
无级联更新 listpack 编码 向后兼容 性能更稳定

演进总结

Redis Hash 从最初单一的 ziplist 实现，演变为智能的双编码系统：

ziplist/listpack → 自动转换 → dict

核心优化路径：
小数据省内存（紧凑存储）| 大数据保性能（O(1)查询）| 渐进式扩容（零阻塞）

这套"自动档"编码切换机制，让 Redis Hash 能够在不同数据规模下都保持最优表现。

Hash 的两种编码与阈值

编码底层触发条件特点
listpack（Redis 7+）紧凑的连续内存双向列表（原 ziplist 的替代）字段数 ≤ hash-max-listpack-entries（128）且每个 field/value 长度 ≤ hash-max-listpack-value（64 字节）极省内存（连续存储、无指针），但读写是 O(n)
hashtable标准字典（dict）任一条件超出（字段数 > 128 或 有值 > 64 字节）O(1) 读写，但每个 entry 有指针与结构体开销

关键：转换是单向的。一旦转成 hashtable，即使删掉大部分字段也不会变回 listpack（要重启或重建 key）。所以写入模式（是否会短暂超阈值）决定了长期的内存占用。

Hash 编码验证

# 查看与修改阈值
CONFIG GET hash-max-listpack-entries    # 128
CONFIG GET hash-max-listpack-value      # 64
CONFIG SET hash-max-listpack-entries 256

# 观察编码转换
HSET h1 f1 v1
OBJECT ENCODING h1          # "listpack"
# 写入一个超过 64 字节的 value
HSET h1 f2 "$(python3 -c 'print("x"*70)')"
OBJECT ENCODING h1          # "hashtable"（已转换，不可逆）

# 对比两种编码的内存
MEMORY USAGE h1
# 典型差异：listpack 比 hashtable 省 30%–60% 内存

# 扫描大 key
redis-cli --bigkeys
MEMORY USAGE <key>

# 生产推荐：用 hash 存对象（而不是多个 string key）
HSET user:1 name "a" age "20" city "bj"     # 一个 key 存整个对象
# 对比：SET user:1:name a / SET user:1:age 20 ...（key 数量暴涨，元数据开销大）

Redis 7.0 之前叫 ziplist，配置项是 hash-max-ziplist-entries/-value；7.0 起改名为 listpack（更安全的实现，解决了 ziplist 的级联更新问题）。升级时注意配置项改名。

选型与坑

场景做法理由
存对象（用户、商品、配置）用 Hash，而不是多个 StringKey 数量少几个量级，元数据开销小；可整取也可取单字段
字段多且有长文本拆成两个 Hash（短字段一个、长文本一个）避免长文本把整个 hash 撑成 hashtable
需要单独设置 TTL只能用 String（Hash 的字段不支持 TTL）Hash 只有整个 key 有过期时间
需要对字段做过期/排序用 ZSet 或另建索引Hash 无字段级过期与分数
购物车（用户id → 商品id → 数量）Hash：key=cart:userId，field=商品，value=数量天然契合，HINCRBY 方便
  • listpack 的 O(n) 陷阱：字段数在 100 以内时 O(n) 完全没问题（n 很小，且连续内存缓存友好），所以默认 128 是合理的。但如果把阈值调到几千，HGET 就变成几万次遍历了——阈值要按“字段数少、值短”来调。
  • 级联更新（旧 ziplist 的问题）：ziplist 每个节点存“前一个节点的长度”，插入一个变长的节点可能触发后续节点连锁扩容（最坏 O(n²)）。listpack 通过存自身长度解决了这个问题——这是 Redis 7 换掉 ziplist 的直接原因。
  • HGETALL 在大 Hash 上会阻塞：字段几万时 HGETALL/HKEYS 是重操作。用 HSCAN 分批遍历。
  • 序列化开销：hashtable 编码下每个 field/value 都要存 SDS，加上 dictEntry 的指针（约 30+ 字节/字段）。所以 1000 个短字段的 hash，hashtable 可能比 listpack 多占 2–3 倍内存。
  • 排障：OBJECT ENCODING → HLEN 看字段数 → MEMORY USAGE → 若大量 hash 是 hashtable 且字段很少，检查是否曾有超大 value 触发了不可逆转换。
为什么我的 hash 字段只有 50 个，却是 hashtable？

因为它曾经超过阈值（字段数 > 128，或曾经写过 > 64 字节的 value），转换不可逆。删掉大字段也不会变回 listpack。解决：重建 key，或调大阈值后重新写入。

Hash 的字段名能设置过期吗？

不能。Redis 的过期是 key 级的，Hash/ZSet/List 的单个字段都不支持 TTL。需要字段级过期要另建一个 ZSet（score 为过期时间戳）做定时清理。
