先问三个问题

选索引不是比谁「最先进」，而是回答三个具体问题：

  • 有多少条向量、多少维？能不能放进内存？——这决定了能不能用 HNSW
  • 要多高的召回率？延迟 SLA 是多少？——这决定了参数与是否要量化
  • 写入模式是什么？——只增不减、高频更新、还是需要频繁删除？

    按规模给的决策路径

    HNSW 参数调优

    参数含义典型值调大的效果代价
    M每个节点的邻居数16~64（常 32）召回↑内存↑、构建↑
    efConstruction建图时的搜索宽度200~500图质量↑、召回↑构建时间↑（一次性）
    efSearch（ef）查询时的搜索宽度从 64 起调召回↑延迟↑（可在线调）
    max_elements容量上限按预估量 ×1.2—预留不够要重建
    经验起手：M=32, efConstruction=300, efSearch=128，然后只调 efSearch：召回不够就翻倍（128→256→512），延迟太高就减半。efSearch 必须 ≥ K（要取 Top-K 就至少搜索 K 个候选项），通常设为 K 的 4~10 倍。

    IVF 系列参数调优

    参数含义典型值怎么调
    nlist聚成多少个桶（聚类数）√N ~ 4√N100 万条 → nlist ≈ 1000~4000
    nprobe查询时搜几个桶nlist 的 1%~10%唯一在线可调；召回不够就加大
    m（PQ 段数）向量切成几段d/8 左右768 维 → m=96（每段 8 维）
    nbits每段 centroid 的比特数8（256 个 centroid）调大精度↑、内存↑
    坑：nlist 设太大会导致每个桶样本太少、聚类质量差；设太小则桶内样本多、搜起来慢。经验是每个桶 1000~10000 条（100 万条数据 → nlist 取 100~1000 更合适，别机械套 √N）。另外必须保证训练样本足够，否则 KMeans 聚类没代表性。

    运维层面的考量

    构建时间与资源HNSW 构建最慢（CPU 密集、难并行）；IVF 需要 KMeans 训练，也要时间
    增量写入HNSW 支持增量插入；IVF 增量多了要重新聚类，否则分布漂移
    删除HNSW 多为标记删除，删多了要重建；IVF 重排桶即可
    持久化索引要能快照落盘，否则重启要全量重建
    分布式数据量大时要分片；Milvus 等已内置，自建要自己切
    过滤（Filtered Search）带属性过滤时，HNSW 可能"走进死胡同"，需要特殊处理

index.hnsw.efConstruction = 300
index.hnsw.efSearch = 128                 # 线上只调这个

# 场景 B：5000 万条，内存只够 16G  → IVF-PQ

index = faiss.IndexIVFPQ(quantizer, 768, nlist=4096, m=96, nbits=8)
index.train(train_vectors)                # 必须训练！样本 ≥ 39 × nlist
index.nprobe = 64                         # 线上调这个

# 场景 C：Qdrant / Milvus 生产配置（HNSW）
#   m = 16~32, ef_construct = 200~400
#   查询时按 SLA 动态传 ef / search_params

# 通用：一定做两段式
candidates = ann_index.search(q, k=200)   # 粗排，快
final = reranker.rerank(q, candidates, top_k=10)   # 精排，准

    🎯 常见问法与答题要点

    Q：HNSW 和 IVF-PQ 怎么选？

    A：核心看内存。HNSW 存原始向量 + 图结构，召回最高、延迟最低，但要能放进内存——千万级以内几乎无脑选 HNSW。亿级数据原始向量 300GB 放不下，就必须压缩：IVF-PQ 能把内存降到 1/10~1/30，代价是量化损失导致召回下降（通常 85%~95%），需要用「粗排 + 原始向量精排」的两段式补回来。

    Q：nlist 和 nprobe 怎么设？

    A：nlist（聚类数）经验是每个桶 1000~10000 条样本：100 万条取 100~1000，1000 万条取 1000~10000。设太大每桶样本少、聚类质量差；设太小桶内太多样本、搜起来慢。nprobe（查几个桶）是唯一能在线调的，通常取 nlist 的 1%~10%，召回不够就加大，延迟太高就减小。另外用 IVF 一定要先 train，训练样本量建议 ≥ 39 × nlist。

    Q：efSearch 设多少合适？

    A：原则是 efSearch ≥ Top-K，通常是 K 的 4~10 倍。取 K=10 时从 64 或 128 起步。它直接决定召回/延迟权衡：召回不够就翻倍（128→256→512），延迟超标就减半。正确做法是扫一遍 efSearch 画出召回-延迟曲线，选业务能接受的拐点，而不是凭感觉调。

    Q：为什么加了过滤条件后 HNSW 变慢甚至召回落？

    A：这是 HNSW 的经典问题：图是按「向量距离」建的，如果大部分邻居都不满足过滤条件（如 tenant_id=X），贪心搜索走进一个节点的邻居全被过滤掉，就卡在死胡同里，既慢又漏。解决办法：①按过滤字段分区建多个小索引；②用支持过滤感知图遍历的引擎（如 Milvus 的 iterative filter、Qdrant 的 payload index + 特殊遍历）；③过滤后候选太少时回退到暴力扫描。

    Q：PQ 量化后召回掉了怎么补？

    A：标准做法是两段式检索：第一阶段用 IVF-PQ 快速召回一个较大的候选集（如 Top-200~500），第二阶段用原始浮点向量对这些候选做精确重排（Rerank），取最终 Top-K。因为候选集只有几百条，精确重排代价很小，但能把「量化损失的召回」大部分补回来。这是工业界亿级向量系统的标配架构。

    Q：索引需要定期重建吗？

    A：看写模式。只增不减的文档库，HNSW 增量追加即可，基本不用重建。高频删除/更新的场景，HNSW 的标记删除会让图逐渐退化（有效边变少、查询路径变长），需要定期全量重建。IVF 类则要注意数据分布漂移——新增数据如果和训练时的分布差异大，原来的聚类中心就不再合适，也要重新 train。建议监控召回率，掉到阈值以下就触发重建。

    Q：能不能自己实现 ANN 索引？

    A：除非是学习或极特殊的场景，否则不建议。成熟的库（FAISS、hnswlib、Annoy、ScaNN）和引擎（Milvus、Qdrant、Weaviate、Elasticsearch dense_vector、pgvector）都经过大量优化和工程验证，覆盖内存管理、持久化、分布式、并发。自己实现很容易在召回率、内存、并发安全上踩坑。用成熟库 + 调好参数才是正解。
