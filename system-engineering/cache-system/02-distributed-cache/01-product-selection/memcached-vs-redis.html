⚔️ Memcached vs Redis：什么时候选谁

两者都是内存 KV 缓存，但 Redis 的数据结构、持久化与集群能力让它成为绝大多数场景的默认选择。

结论

默认选 Redis

先建立直觉：简易货架 vs 多功能仓库

Memcached 像一个简易货架：只能放一种规格的箱子（字符串），但取放极快，而且有多个搬运工同时干活（多线程）。

Redis 像一个多功能仓库：有各种专用货架（列表、集合、有序集合、哈希……），有账本（持久化），有分区（集群），还能干更多活（发布订阅、Lua、流）。功能多，但核心处理是单线程的。

性能：谁更快

不能简单说谁快。
• 小 value、极高并发：Memcached 的多线程能更好利用多核，吞吐可能更高。
• 大 value 或复杂操作：Redis 的数据结构（如只取 Hash 某个字段、ZSet 范围查询）能避免传输整个对象，反而更快。
• 单实例瓶颈：Redis 单线程意味着单实例 QPS 有上限（通常十万级），但可以通过集群分片线性扩展，这个限制在实践中不致命。
「Redis 单线程所以慢」是常见误解。Redis 的瓶颈通常是网络 IO 而非 CPU，单线程避免了锁竞争和上下文切换，实际非常快。6.0 之后网络读写也已多线程化。

功能差异带来的实际影响

关键洞察：Redis 的价值不只是「能存更多类型」，而是把计算下推到数据所在的地方（原子自增、服务端排序、集合运算），避免了「读出来 → 改 → 写回去」的网络往返与并发风险。

什么时候选 Memcached

  • ✅ 缓存模型非常简单，就是纯 String KV，且 value 都很小；
  • ✅ 需要极高吞吐且希望充分利用多核（单机几十万 QPS 以上）；
  • ✅ 已有成熟的 memcached 运维体系，且不需要持久化、集群、复杂结构；
  • ✅ 希望水平扩展靠加机器，由客户端做一致性哈希，逻辑简单。

什么时候选 Redis（绝大多数情况）

  • ✅ 需要除 String 外的任何数据结构（排行榜、队列、去重、关系）；
  • ✅ 需要持久化或重启后恢复；
  • ✅ 需要主从/哨兵/集群等原生高可用能力；
  • ✅ 需要发布订阅、Lua、分布式锁、限流等附加能力；
  • ✅ 希望生态成熟、文档丰富、招人容易。
一句话结论：除非你有非常明确的理由（极简 KV + 极高吞吐 + 已有 memcached 体系），否则默认选 Redis。它的功能覆盖面、生态和运维工具链的优势，在绝大多数项目中压倒性地超过 memcached 的多线程吞吐优势。

🎯 面试问答

Q：Redis 是单线程的，为什么还比 memcached 流行？
A：因为瓶颈不在 CPU。缓存操作的耗时主要在网络 IO 上，单线程避免了锁竞争和上下文切换，反而非常高效。而 Redis 提供的数据结构、持久化、集群、丰富的原子操作，带来的价值远大于多线程的那点吞吐优势。真正需要极致吞吐时，Redis 也能通过集群分片横向扩展。

Q：memcached 真的没有优势了吗？
A：仍有，但场景很窄：① 纯 String KV 且 value 很小时，多线程能更好地压满多核，单机吞吐可能更高；② 它的内存管理（Slab 分配）在长期运行下碎片较少（但也带来内存利用率低的问题）；③ 模型极简，运维心智负担小。所以一些超大规模、模型极简的缓存层（如早期 Facebook）仍会用它。但对绝大多数团队，Redis 是更省事的选择。

Q：两者的淘汰策略有什么不同？
A：Memcached 主要用 LRU，且是按 Slab 类分别做 LRU（这带来一个副作用：某个 Slab 类满了，即使其他类有空间也会淘汰，内存利用率不完美）。Redis 提供 8 种策略，包括 allkeys-lru、allkeys-lfu、volatile-*、随机淘汰和不淘汰（写满报错），且 LFU 支持概率计数与时间衰减，适应能力更强。

Q：能同时用两个吗？
A：技术上可以，但通常没必要。同时维护两套缓存会带来双倍运维成本、两套监控和更复杂的一致性管理，收益却很有限。合理的做法是先明确瓶颈：如果是吞吐，Redis 加分片就能解决；如果是大 value，优化数据结构和序列化更有效。只有当你已经确认瓶颈确实是「纯 KV 小对象吞吐」且扩 Redis 分片成本过高时，才考虑引入 memcached。

关键参数与监控

# Memcached 关键参数
memcached -m 4096 -t 8 -c 1024 -f 1.25 -n 48 -I 1m
#   -m 内存上限MB   -t 线程数(=核数)   -c 最大连接
#   -f slab 增长因子(默认1.25)   -n 最小chunk   -I 单个item最大
#   slab 增长因子太大 -> chunk 尺寸跨度大 -> 内存浪费
#   例：f=1.25 时 chunk 为 48,60,76,96,... 存 100 字节会用 120 的 chunk

# 看 slab 使用情况（判断内存浪费）
echo "stats slabs" | nc 127.0.0.1 11211 | grep -E 'chunk_size|used_chunks|free_chunks'
echo "stats items" | nc 127.0.0.1 11211

# Redis 关键参数
maxmemory 4gb
maxmemory-policy allkeys-lru      # 8 种：noeviction/allkeys-lru/volatile-lru/
                                  # allkeys-lfu/volatile-lfu/allkeys-random/
                                  # volatile-random/volatile-ttl
redis-cli info stats | grep -E 'keyspace_hits|keyspace_misses'   # 算命中率
redis-cli info memory | grep -E 'used_memory_human|mem_fragmentation_ratio'

命中率算法：hits / (hits + misses)。健康值 >95%，低于 90% 就要查是不是 TTL 太短、key 设计不合理或缓存容量不足。内存碎片率 mem_fragmentation_ratio 在 1.0~1.5 正常，>1.5 说明碎片多（可开 activedefrag yes），<1.0 说明在用 swap（危险，会极慢）。

决策流程与迁移要点

  • 默认选 Redis：生态、数据结构、持久化、集群、运维工具全面领先。Memcached 只在两个场景有优势：① 缓存的 value 很大且数量不多（如完整 HTML 页面、大 JSON），Memcached 的多线程 + slab 在这种场景吞吐更高；② 已有大量 Memcached 基础设施且只做纯 KV。
  • Memcached 的 1MB 限制是硬伤：很多团队一开始用得好好的，后来某个 value 变大就全部失败（SERVER_ERROR object too large for cache）。
  • Redis 单线程不是瓶颈：瓶颈通常是网络往返而不是 CPU。用 pipeline/MGET 批量化、或上集群分片，比换多线程方案有效得多。
  • Redis 6.0 的多线程 IO 只负责网络读写和协议解析，命令执行仍是单线程，所以不会有多线程的并发问题（如 Lua 脚本仍是原子的）。

Memcached 的 slab 为什么要按固定大小分块？

为了避免内存碎片。Memcached 把内存划分成若干 slab class，每类里是固定大小（如 96B、120B、152B…）的 chunk。好处是回收复用完全无碎片；代价是内部浪费——存 100 字节的数据会占用 120 字节的 chunk，且内存不会在 slab class 之间流动（可能出现某个 class 满了而其他 class 空闲）。所以增长因子 -f 设得越大浪费越多，设太小则 class 数量暴增。

Redis 单线程为什么还能有 10 万 QPS？

因为它的瓶颈不在 CPU 而在内存访问和网络。单线程带来的好处是：无锁、无上下文切换、无并发 bug，且数据结构操作都是 O(1)~O(logN) 的极短路径。10 万 QPS 意味着每条命令只花 10 微秒，而一次内存访问才 100ns——完全够用。真正的瓶颈是网络往返（0.2~1ms），所以用 pipeline 批量化能把吞吐再提 10 倍。

可以混用吗？

可以，而且有些大厂就这么干：小对象、需要结构的用 Redis；大 value 的纯缓存用 Memcached。但代价是运维两套系统、两套监控和两套扩容流程。绝大多数团队不值得——除非你的大 value 缓存量确实很大（几十 GB 以上）且 QPS 很高。
