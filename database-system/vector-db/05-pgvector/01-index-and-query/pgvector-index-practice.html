pgvector 把向量当普通列存，但索引选型和查询参数直接决定召回率与延迟。HNSW 快但占内存、IVFFlat 省内存但需训练，下面给可直接执行的建索引与调参清单。

01建索引：HNSW vs IVFFlat

HNSW 不需要训练数据、查询快，但构建慢且吃内存；IVFFlat 构建快、省内存，但建索引前要先跑一次查询让它『训练』聚类中心，且召回对 lists 敏感。

-- HNSW：m=每层连接数(默认16)，ef_construction=构建时考察邻居数(默认64)
CREATE INDEX ON items USING hnsw (embedding vector_l2_ops)
  WITH (m = 16, ef_construction = 64);

-- IVFFlat：lists=聚类中心数，建前先让优化器采样一次（执行任意一次近似查询）
CREATE INDEX ON items USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);
-- 然后跑一次：SELECT * FROM items ORDER BY embedding <=> '[...]' LIMIT 10;
-- 否则索引处于『untrained』状态，查询会退化为全表扫描

02查询与召回调参

HNSW 的 ef_search 控制查询时考察的候选数，越大召回越高、越慢；IVFFlat 的 probes 控制查几个聚类，同理。距离算子要和数据类型匹配（l2 / cosine / inner）。

-- HNSW：会话级调 ef_search（越大召回越高、越慢）
SET hnsw.ef_search = 40;            -- 默认 40，要更高召回设 80~200
SELECT id, embedding <=> '[0.1,0.2,...]' AS dist
FROM items ORDER BY embedding <=> '[0.1,0.2,...]' LIMIT 10;

-- IVFFlat：调 probes（默认 1，太低漏召回）
SET ivfflat.probes = 10;
SELECT id FROM items ORDER BY embedding <=> '[...]' LIMIT 10;

-- 召回率怎么量：用精确结果当基准
WITH exact AS (
  SELECT id FROM items ORDER BY embedding <=> '[...]' LIMIT 10)
SELECT count(*) FILTER (WHERE id IN (SELECT id FROM exact)) / 10.0 AS recall
FROM (SELECT id FROM items ORDER BY embedding <=> '[...]' LIMIT 10) sub;

04构建与内存注意事项

  • HNSW 建索引会锁表（8.x 仍建议低峰或并发可控时建）。
  • m 越大越准越占内存，16 是常见起点；亿级向量考虑分表或专用向量库。
  • 距离算子必须一致：建索引用的 ops 和查询用的 <=> 算子要匹配，否则不走索引。
  • 更新单行的 embedding 代价高（HNSW 需改图），高频更新场景慎用。
要点：pgvector 适合『已有 Postgres、向量规模中等、要事务+SQL 一体』的场景；超大规模、纯向量检索请用专用向量库。
