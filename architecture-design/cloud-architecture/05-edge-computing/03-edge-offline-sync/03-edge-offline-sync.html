1离线优先带来同步冲突

边缘与离线优先架构让客户端先写本地、再异步同步。好处是弱网可用；代价是多端可能并发修改同一份数据，必须有一套不靠中心锁的合并规则。这与"缓存回源"是两回事：回源解决"读一致性"，本文解决"写冲突"。

核心工具：CRDT、版本向量、last-writer-wins、最终一致。

2冲突解决策略对比

策略思想优点/代价
LWW最后写入覆盖简单，但可能丢更新
版本向量追踪每副本因果能检测并发，不自动合并值
CRDT数学可交换合并自动收敛，设计复杂

3版本向量检测并发

# 每个副本维护对其他副本已知版本的向量
local = {"A": 3, "B": 2, "C": 1}

def concurrent(v1, v2):
    # 互不 dominates → 并发（需合并）
    ge = all(v1.get(k,0) >= v2.get(k,0) for k in set(v1)|set(v2))
    le = all(v1.get(k,0) <= v2.get(k,0) for k in set(v1)|set(v2))
    return not (ge or le)

print(concurrent({"A":3,"B":2}, {"A":2,"B":3}))   # True: 并发写

检测到并发后，LWW 直接覆盖，CRDT 则按结构自动合并（如计数器用加法、集合用并集）。

4同步收敛

图：离线并发写经同步合并收敛到一致

第一层 · 概念与判定

判定用哪种策略：

  • 冲突极少且可丢更新（如"最后心跳"）→ LWW；
  • 需要检测"是否并发"但不强求自动值合并 → 版本向量；
  • 协作编辑/计数器/集合等需自动收敛 → CRDT；
  • 强一致要求 → 离线优先本身就不合适。

第二层 · 参数·命令·量化

量化与参数：

项说明
向量维度随副本数增长，需裁剪
CRDT 元数据带来额外存储/带宽
收敛时间取决于同步频率与网络

第三层 · 排障与边界

排障与边界：

  • LWW 丢更新：时钟漂移致错误覆盖，用混合逻辑时钟；
  • 向量膨胀：长期运行需墓碑清理与裁剪；
  • CRDT 语义不符：选错类型（如用 G-Counter 做需覆盖的值）；
  • 永久不收敛：某些副本永不在线，需最终同步窗口。

第四层 · 原理与取舍

原理取舍：

  • 离线可用性与强一致性天然冲突，只能取"最终一致"；
  • LWW 简单但牺牲更新安全；CRDT 安全但复杂且费空间；
  • 版本向量提供"因果可见性"而非值合并，需上层决策；
  • 结论：按"冲突频率 × 丢失代价"选策略，离线优先必须接受最终一致。
