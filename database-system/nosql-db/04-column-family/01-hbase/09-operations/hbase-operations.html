🔧 HBase 运维

启停、监控指标、常见故障、备份恢复与性能调优清单

日常操作命令

# 启停（先停 HBase 再停 HDFS；启动顺序相反）
$HBASE_HOME/bin/start-hbase.sh
$HBASE_HOME/bin/stop-hbase.sh
# 单节点
hbase-daemon.sh start master / regionserver / thrift

# Shell 常用
status 'simple' | 'detailed'      # 集群状态
whoami                            # 当前用户
list                              # 所有表
describe 't'                      # 表结构
count 't', INTERVAL => 100000     # 计数（大表很慢！）
exists 't'
is_enabled 't' / is_disabled 't'
disable 't'; enable 't'
truncate 't'                      # 清空（内部 disable+drop+create）
flush 't' / flush 'REGIONNAME'    # 手动刷写
compact 't' / major_compact 't'   # 手动压缩
split 't' / split 'REGIONNAME'
move 'ENCODED_REGION', 'server'   # 手动迁移 Region
balance_switch true|false         # 负载均衡开关
balancer                          # 立即触发均衡
hbck                              # 一致性检查（2.x 用 hbck2）

必须监控的指标

指标怎么看告警线

Region 数 / RSMaster UI> 500 关注，> 1000 处置
StoreFile 数Master UI / JMX接近 blockingStoreFiles(16) 告警
请求数JMX readRequestsCount/writeRequestsCount分布严重不均 = 热点
GC 时间RS 日志 / JMXFull GC 频繁或 > 1s 要调堆
MemStore 使用JMX接近 global.memstore.size(0.4) 会阻塞写
BlockCache 命中率JMX blockCacheHitRatio< 80% 说明缓存不够或读模式不佳
Compaction 队列Master UI持续积压说明写太快

常见故障与处置

🐢 写入变慢 / 被阻塞

  • 看 StoreFile 数是否撞上 blockingStoreFiles（默认 16）
  • 看 MemStore 是否撞上全局上限（0.4 堆）
  • compaction 队列是否积压
  • 对策：调大阈值、增加 compaction 线程、检查是否关闭了自动 compaction

🔥 Region 热点

  • Master UI 看各 RS 的 writeRequestsCount 差异
  • 定位集中写入的 rowkey 前缀
  • 对策：改 rowkey 加盐/hash、给大 key 单独打散

💥 RegionServer 频繁宕机

  • 先看日志：OOM？GC 超时？ZK session timeout？
  • OOM → 调大堆或调小 memstore/blockcache 比例
  • GC 长 → 换 G1GC、调 Region 数、减小单个 Region
  • ZK 超时 → 网络抖动或 RS 负载过高

⚠️ RIT（Region-In-Transition）卡住

  • 现象：Region 长时间处于 transitioning 状态
  • 常见于 split/merge/assign 失败
  • 处置：先查 Master 日志，2.x 用 hbck2 assigns 强制上线

💾 磁盘只增不减

  • delete 只写墓碑，major compaction 才真删
  • 大量删除后手动 major_compact
  • 旧 WAL 未清理：检查 replication 是否卡住

🌐 网络分区（脑裂风险）

  • RS 与 ZK 失联超过 session timeout → 被判定死亡
  • Region 被重分配到别的 RS
  • 老 RS 恢复后会被强制关闭（避免双写）

备份与恢复

方式做法适用
Snapshot（推荐）snapshot 't','snap1' → 只记文件列表，秒级完成最常用；clone_snapshot 建新表、restore_snapshot 回滚、ExportSnapshot 迁到另一集群
Export/ImportMapReduce 导出成 SequenceFile跨版本迁移、小规模
CopyTableScan 源表写入目标表同集群/跨集群表复制
HDFS 快照 / distcp直接拷贝 /hbase 目录整集群级；需先 flush + 停写
Replication配置主从集群实时同步容灾，不是备份（误删会同步过去）
# Snapshot 日常用法
snapshot 'user', 'user_20260101'
list_snapshots
clone_snapshot 'user_20260101', 'user_backup_copy'   # 从快照建新表（秒级）
restore_snapshot 'user_20260101'                     # 回滚（需先 disable + truncate）
delete_snapshot 'user_20260101'

# 跨集群导出（走 MapReduce，不动在线集群）
hbase org.apache.hadoop.hbase.snapshot.ExportSnapshot   -snapshot user_20260101 -copy-to hdfs://other-cluster:8020/hbase
⚠️ Replication 不是备份：主集群上误删的数据会实时同步到从集群。真正的防误删要靠 Snapshot + 保留策略。

滚动重启的正确姿势

  • balance_switch false 关闭自动负载均衡
  • 逐台 graceful_stop.sh <hostname>（先把 Region 迁走再停，避免大量 WAL 重放）
  • 确认该 RS 的 Region 已全部迁走
  • 改配置 / 升级，启动该 RS
  • 确认 Region 重新上线、本地性恢复后再处理下一台
  • 全部完成后 balance_switch true
    • 💡 千万别直接 stop-hbase.sh 再 start-hbase.sh——那样所有 Region 都要走 WAL split + 重放，恢复时间可能是滚动重启的十倍以上。

    🎯 常见问法与答题要点

    Q：RegionServer 频繁 OOM 怎么办？

    A：先看是哪种 OOM。常见原因与对策：①Region 太多 → MemStore 数量 = Region 数 × 列族数，全部吃堆，对策是减少 Region 数（调大 max.filesize / 预分区规划）；②memstore+blockcache 比例过高 → 两者默认共占 80% 堆，写多时 memstore 冲到上限触发强制 flush 甚至 OOM，对策是下调到 0.45/0.25 组合；③单次 scan 拉回太多数据 → 客户端缓存爆掉，对策是调小 caching、用分页；④堆本身太小 → 16~32GB 为宜，并用 G1GC。

    Q：写入突然被阻塞，怎么排查？

    A：HBase 有两道写阻塞闸门：①StoreFile 数达到 blockingStoreFiles（默认 16）——该 Store 停止写入等 compaction；②MemStore 总量达到 global.memstore.size（默认堆的 40%）——触发强制 flush，flush 跟不上就阻塞写。排查：Master UI 看 StoreFile 数与 compaction 队列，JMX 看 MemStore 用量。对策：调大阈值、增加 compaction 线程、减少列族、检查是否误关了自动 compaction。

    Q：Snapshot 为什么是首选备份方式？

    A：因为它几乎零成本：snapshot 只是把当前所有 HFile 的文件列表记下来（元数据操作，秒级完成），不拷贝任何数据。而 HFile 不可变，所以快照点的数据永远有效——被 compaction 合并掉的旧文件会被保留直到快照删除。它支持：clone_snapshot 秒级克隆一张新表（测试、抽样）、restore_snapshot 回滚、ExportSnapshot 跨集群迁移。相比之下 CopyTable/Export 要全表扫描，代价高得多。

    Q：为什么 Replication 不能当备份？

    A：因为它是实时同步：主集群上的 delete、drop table、误操作会在几秒内同步到从集群，两边一起遭殃。它的定位是容灾（主集群整体不可用时切到从集群），不是防误删。防误删要靠 Snapshot 配合保留策略（如每天一个快照保留 7 天）。

    Q：集群重启为什么要滚动而不是全停全起？

    A：全停全起时，所有 RegionServer 上的 MemStore 都来不及 flush，重启后每个 Region 都要走 WAL split + 重放，数据量大的集群恢复时间可能是几十分钟到数小时。滚动重启用 graceful_stop.sh，它会先把该 RS 的 Region 逐个迁移到别的节点（迁移前自动 flush），再停进程——基本没有 WAL 重放，对业务几乎无感。

    Q：Region 一直卡在 RIT 状态怎么办？

    A：RIT（Region-In-Transition）卡住通常是 split/merge/assign 某一步失败。处置：①先看 Active HMaster 日志找具体错误；②HBase 2.x 用 hbck2 工具：hbck2 assigns <ENCODED_REGION> 强制重新分配；③HBase 1.x 可用 hbck -fixAssignments（有风险，慎用）；④若因 HDFS 文件损坏，要修 HDFS 或丢弃该 Region 后从快照恢复。

    Q：磁盘空间只涨不降怎么办？

    A：三步排查：①delete 的数据没真删——墓碑要等 major compaction，手动 major_compact 't'；②旧 WAL 没清理——检查 replication 是否卡住（主集群会保留未同步的 WAL），或 hbase.region.server.logroll 配置；③snapshot 占着旧文件——compaction 后的旧文件如果有快照引用就不能删，list_snapshots 清理不再需要的快照。

    Q：怎么判断集群需不需要扩容？

    A：看四个信号：①单 RS Region 数 > 200；②HDFS 使用率 > 80%；③读写延迟持续上升且不是慢查询导致；④CPU 长期 > 70%或 compaction 持续积压。扩容时 RegionServer 要与 DataNode 一起加（保持数据本地性），加完后用 balancer 触发 Region 重新均衡。
