RBAC 与 ABAC：从角色到资源策略

用订单与后台管理权限矩阵，拆开“登录成功”“持有角色”和“可操作这条数据”三个判断。

认证先回答身份，授权再回答操作

认证确认请求主体是谁；授权判断这个主体现在能否对这项资源执行特定动作。令牌上的 role=admin 不等于所有 API 都应无条件放行：角色的签发方、适用租户、有效期，以及目标订单的归属都需要服务端验证。把“是否登录”作为全部接口的唯一检查，很容易形成横向越权或后台接口暴露。

可把一次判断表示为 allow(subject, action, resource, context)：主体包括用户/服务账号及其租户；动作是读、修改、审批；资源包含类型、归属、状态；上下文包括当前租户和业务时间。缺少必需属性或策略执行失败，默认拒绝并记录原因，但不把敏感规则详情返回给客户端。

权限矩阵：同一“读订单”动作有不同条件

请求主体可操作资源动作必须额外满足的条件
普通用户本租户自己的订单读取、申请取消订单所属用户相符；取消还要求状态可取消
租户客服被授予的本租户订单读取、备注当前租户匹配；仅允许客服职责范围
财务人员本租户结算单复核不能复核本人创建的单据；遵守职责分离
平台运维平台状态信息排障操作需审批/审计；不默认获得全部租户订单读取权

矩阵给出示意，不应把“所有 admin 都能看所有订单”当作系统默认规则；跨租户运营权限必须单独定义和审计。

图解：策略判定在数据入口之前

这张图是责任划分，而不是每次都先无约束加载完整资源：真实实现可以先用带租户/归属条件的查询获得资源，再对特殊动作做策略判定；关键是未经许可的数据不能先返回或写入。

逐步推演：把“租户客服看订单”写成规则

主体来自可信认证上下文

会话确定用户 u7、当前租户 t3、角色 support；请求路径里的租户 ID 只是用户提供的目标，不能作为主体的租户来源。

动作不能只是“有客服角色”

请求是 orders.read 还是 orders.refund？客服可读、可备注，不一定可退款。将动作与最小权限列表比较。

资源也参与判断

查询订单的 tenant_id、被分配的客服范围、隐私等级和状态。即使请求声称 tenant=t3，真实订单可能属于 t8。

允许后仍限制返回字段

条件全部成立才返回被许可字段；否则按接口策略返回 403 或不暴露资源存在性的 404。记录主体、动作、资源 ID 与拒绝原因，但日志不包含敏感凭证。

第一层 · RBAC 与 ABAC 各解决什么

模型核心问题适用场景代价
RBAC：用户 → 角色 → 权限一类岗位允许哪些动作？后台菜单、岗位操作、明确分工对象归属和条件多时角色膨胀
ABAC：属性 + 策略此主体此刻能操作这条资源吗？租户隔离、订单归属、审批状态、动态条件策略可解释性、性能与属性一致性要求更高
组合先用角色缩小动作，再用资源属性约束范围多数多租户后台必须保持规则唯一、避免不同服务各自放宽

第二层 · 策略示例与执行点

// 教学伪代码；subject 和 activeTenant 来自已校验的会话
if !hasPermission(subject.roles, "orders.read") { deny() }
order := findOrderWhere(id = requestedId, tenant_id = subject.activeTenant)
if order == nil { notFound() }
if subject.isCustomer && order.owner_id != subject.userId { deny() }
if subject.isSupport && !isAssignedTo(subject.userId, order.id) { deny() }
return redactForRole(order, subject.roles)

创建与修改路径同样要检查目标租户和被改字段，不要只保护 GET；批量操作需逐项约束，不能因为第一条记录通过就放行整批。策略执行点可以在应用服务、授权中间件或独立策略引擎，但最终数据访问仍需范围约束；前端隐藏按钮仅用于体验，不是授权措施。

第三层 · 故障与运营边界

  • 角色膨胀：为“只看一个租户的一类订单”创建几十个角色，通常应改为稳定的岗位权限 + 资源条件。
  • 权限缓存：撤销角色后旧令牌或缓存仍有效；设计短寿命、版本号/事件失效、关键动作回源校验，说明最大延迟窗口。
  • 租户切换：会话切换当前租户后，必须重新计算权限；不能复用上一租户的判定结果或未包含租户的缓存键。
  • 审计与职责分离：高风险操作记录主体、租户、动作、理由与审批链，避免同一人创建并复核同一笔资金单。

第四层 · 原理与取舍

有了 RBAC，还需要检查订单 owner_id 吗？

需要。RBAC 决定能否执行“读订单”这类动作；订单归属决定能否读这一个对象。即使用户拥有 orders.read，也可能只被授权读取自己或当前租户的订单。

把每项权限写进 JWT 就能做到即时撤权吗？

不能。已签发的离线校验令牌在过期前仍携带旧权限；需要短寿命、集中策略查询、授权版本或撤销机制，结合可接受的延迟窗口选型。

403 与 404 谁更安全？

已认证但被拒绝通常是 403；不应暴露资源存在性时可按接口契约统一返回 404。无论选择哪个状态码，服务端都必须真实拒绝访问，不能只改变提示文案。

自检

平台运维有 admin 角色，就能默认导出全部租户订单吗？

不能。需区分平台运维与业务数据权限；跨租户访问应单独授权、最小化、审批并审计。
