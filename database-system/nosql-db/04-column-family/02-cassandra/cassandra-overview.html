先建立直觉：没有总部的连锁店

传统分布式数据库有一个「总部」（主节点）负责协调。总部出问题，全局受影响。

Cassandra 没有总部——每个节点完全对等，任何一个都能接收读写请求。这带来两个直接结果：

  • ✅ 任何节点宕机都不影响服务（只要副本数足够）；
  • ✅ 加机器就是加能力，扩展近乎线性；
  • ⚠️ 代价：各节点需要时间同步状态，所以默认是最终一致。

数据模型：宽列（Wide Column）

Cassandra 的表是「分区 → 行 → 列」的多层结构。理解它的关键是 Partition Key 和 Clustering Key：

概念作用类比
Partition Key决定数据存在哪个节点邮编决定信送到哪个邮局
Clustering Key决定分区内的排序邮局内部的信件排列顺序
Primary Key= Partition Key + Clustering Key唯一标识一行
CREATE TABLE user_events (
    user_id     UUID,
    event_time  TIMESTAMP,
    event_type  TEXT,
    payload     TEXT,
    PRIMARY KEY ((user_id), event_time)   -- (分区键), 聚类键
) WITH CLUSTERING ORDER BY (event_time DESC);
查询必须带上 Partition Key（否则要全表扫描，代价极高）。而带上 Partition Key 后，按 Clustering Key 的范围查询非常高效——因为分区内是有序存储的。这是 Cassandra 数据建模的第一原则：先想清楚要怎么查，再反推 Key 怎么设计。

写入路径：为什么这么快

可调一致性

Cassandra 允许每次操作指定一致性级别，这是它最灵活也最重要的特性：

-- 常用级别
ONE             -- 一个副本响应即可（最快，最弱）
QUORUM          -- 多数派副本响应（常用，平衡）
LOCAL_QUORUM    -- 本地数据中心多数派（多 DC 场景推荐）
ALL             -- 所有副本（最强，最慢）

-- 强一致的判定公式：W + R > N
-- N = 副本数（replication factor）
-- 例：N=3, 写 QUORUM(2) + 读 QUORUM(2) = 4 > 3 → 强一致
这是 Cassandra 的精髓：它不是「只能最终一致」，而是把选择权交给你——按 W + R > N 公式，你可以针对每次读写权衡延迟与一致性。多数生产场景用 QUORUM / LOCAL_QUORUM。

适合与不适合

适合不适合
✅ 写多读少（日志、时序、消息）❌ 需要强一致事务（余额、订单）
✅ 跨地域多活部署❌ 复杂 JOIN 与即席查询
✅ 要求写入永不中断❌ 频繁更新同一行（会产生大量墓碑）
✅ 数据量持续增长、需线性扩展❌ 需要按任意字段查询（只能按 Key 查）
最大的坑：数据建模必须围绕查询设计。Cassandra 不支持任意条件查询——必须带 Partition Key，否则全表扫描。这意味着「先设计表，再想怎么查」的路子在这里走不通，必须先列出所有查询需求，再反推表结构。为不同的查询模式建多张表是正常且被鼓励的做法（用空间换查询能力）。

🎯 面试问答

Q：Cassandra 为什么没有单点故障？
A：因为它完全去中心化：所有节点地位对等，没有主节点或协调节点。任何节点都能接收读写请求，并作为 coordinator 把请求转发给负责该数据的副本节点。因此任意节点宕机都不会导致服务不可用（只要副本数配置合理）。这区别于 HBase 这类主从架构——后者的 HMaster 故障会影响元数据操作。代价是各节点需要时间同步状态，因此默认是最终一致。

Q：Partition Key 和 Clustering Key 有什么区别？
A：Partition Key 决定数据存在哪个节点（通过对 key 哈希），也决定了查询能否高效执行——查询必须带 Partition Key，否则要全表扫描。Clustering Key 决定分区内数据的物理排序，支持范围查询（如按时间倒序取最近 10 条）。类比：Partition Key 像邮编（决定送到哪个邮局），Clustering Key 像邮局内部的排列顺序（决定查找快慢）。

Q：为什么 Cassandra 写入这么快？
A：因为它是追加式写入，不做「读-改-写」。写操作只需：① 把变更顺序追加到 CommitLog（顺序磁盘 IO，很快）；② 写入内存中的 Memtable；然后立即返回成功。真正的落盘（刷成 SSTable）和合并（compaction）都是后台异步完成。这避免了随机 IO 和读改写开销。注意：Cassandra 的 UPDATE 在内部也是一次追加写入（新的时间戳版本），读取时才合并各版本。

Q：为什么有人说 Cassandra 删除数据会有问题？
A：因为删除在 Cassandra 里是写入一条「墓碑」（tombstone）标记，而不是立即物理删除——它需要等 compaction 时才真正清理，且必须传播到所有副本。问题在于：读取时要扫描并跳过这些墓碑，如果某个分区积累了大量墓碑（如频繁插入又删除、或大量写入 TTL 短的数据），读取会变得极慢甚至超时（触发墓碑阈值保护）。避免方法：不要在同一分区频繁增删、谨慎使用短 TTL、监控墓碑数量。
