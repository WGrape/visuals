🗄️ Ehcache：支持分层的 Java 本地缓存

除堆内缓存外，Ehcache 还支持堆外与磁盘分层，适合需要缓存大量数据又不愿占用 GC 堆的场景。

先建立直觉：家里的三层收纳

  • 堆内（Heap）：桌面上，拿取最快，但空间小，而且要定期整理（GC 要扫描它）。
  • 堆外（Off-Heap）：抽屉里，拿取稍慢，空间大，不用整理（不在 GC 管辖范围）。
  • 磁盘（Disk）：储藏室，最慢但容量几乎无上限。

Ehcache 的特色就是原生支持这三层，并且能在它们之间自动挪动数据。

三层对比

层级位置速度容量GC 影响
堆内 HeapJVM 堆最快受 -Xmx 限制有（对象会被扫描，数据量大时 GC 压力明显）
堆外 Off-Heap本机内存（非堆）快（需序列化）受物理内存限制无（不在 GC 范围）
磁盘 Disk本地文件系统慢（IO）受磁盘限制无
堆外的核心价值：避免 GC 压力。如果在堆里缓存几 GB 数据，GC 每次都要扫描这些对象，会造成明显的 STW 停顿。放到堆外后，GC 完全不管它们，停顿时间大幅缩短。代价是读写需要序列化/反序列化，且访问稍慢。
堆外不是万能药。序列化有 CPU 与延迟开销；数据仍在本机内存，进程重启后丢失；且需要自己管理内存释放（虽然 Ehcache 会做）。只在确实需要缓存大量数据且 GC 已成为瓶颈时使用。

基本配置

CacheManager cacheManager = CacheManagerBuilder.newCacheManagerBuilder()
    .with(CacheManagerBuilder.persistence("/tmp/ehcache-data"))   // 磁盘目录
    .withCache("userCache",
        CacheConfigurationBuilder.newCacheConfigurationBuilder(
            Long.class, User.class,
            ResourcePoolsBuilder.newResourcePoolsBuilder()
                .heap(1000, EntryUnit.ENTRIES)                    // 堆内 1000 条
                .offheap(100, MemoryUnit.MB)                      // 堆外 100MB
                .disk(1, MemoryUnit.GB, true))                    // 磁盘 1GB（持久化）
        .withExpiry(ExpiryPolicyBuilder.timeToLiveExpiration(Duration.ofMinutes(10)))
    ).build(true);
层级顺序很重要：Ehcache 按堆内 → 堆外 → 磁盘的顺序存放。热点数据在上层（快），被淘汰的降级到下层（慢但还在）。这本质上是一个单机内的多级缓存。

怎么选：
• 纯堆内、追求极致性能与命中率 → Caffeine（大多数场景的最优解）。
• 需要堆外或磁盘分层、缓存量超过堆容量 → Ehcache。
• 老项目已在用 Guava → 建议迁移到 Caffeine。

使用注意

  • 存堆外/磁盘的对象必须可序列化——这是硬要求。
  • 磁盘层要配置合理的目录与容量，并注意磁盘 IO 对延迟的影响。
  • Ehcache 3.x 与 2.x API 完全不兼容，升级要注意。
  • 与 Spring 集成时可用 @Cacheable，通过 JCacheCacheManager 接入。

🎯 面试问答

Q：什么时候需要堆外缓存？
A：当堆内缓存大量数据导致 GC 停顿变长时。典型信号：缓存几 GB 数据后，Full GC 从几十毫秒涨到几秒，STW 明显影响响应时间。此时把数据移到堆外，GC 不再扫描它们，停顿大幅缩短。判断方法：先看 GC 日志，确认老年代增长是否主要来自缓存对象。

Q：Ehcache 和 Caffeine 怎么选？
A：绝大多数情况选 Caffeine：它纯堆内性能最好、命中率最高（W-TinyLFU）、API 现代。只有当你的需求是「缓存量超过 JVM 堆、或必须落到磁盘」时，Ehcache 的分层能力才是决定性优势。如果数据量根本没那么大，用 Ehcache 反而引入了序列化开销和配置复杂度。

Q：堆外缓存的数据会丢失吗？
A：会，进程重启就丢——堆外内存和堆内一样是易失的。只有磁盘层可以持久化（需要显式配置 persistence 目录且 disk 层设为持久化）。所以如果需要「重启后缓存还在」的能力，必须启用磁盘持久层，并接受磁盘 IO 的速度。

Q：Ehcache 3 和 2 能混用吗？
A：不能，两者包路径和 API 完全不同（2.x 是 net.sf.ehcache，3.x 是 org.ehcache），配置文件格式也不兼容。升级需要重写配置与代码。3.x 的主要改进是引入了分层存储（tiers）模型和更现代的 Builder API，与 JSR-107 对齐更好。新项目直接用 3.x。

层级结构与配置

Ehcache 3 的核心概念是分层存储（tiering）：堆内 → 堆外 → 磁盘。数据按配置在各层之间流动，越往外容量越大、访问越慢。

层级位置速度容量序列化
堆内 heapJVM 堆，受 GC 管理最快（纳秒级）小（几百 MB）不需要（存对象）
堆外 offheapJVM 外内存，不受 GC 影响快（微秒级）较大（几 GB）需要序列化
磁盘 disk本地文件慢（毫秒级）大（几十 GB）需要序列化

配置示例

// Ehcache 3 典型配置（Java API）
CacheManager cm = CacheManagerBuilder.newCacheManagerBuilder()
    .with(CacheManagerBuilder.persistence("/tmp/ehcache-data"))   // 磁盘目录
    .withCache("userCache",
        CacheConfigurationBuilder.newCacheConfigurationBuilder(
            Long.class, User.class,
            ResourcePoolsBuilder.newResourcePoolsBuilder()
                .heap(1000, EntryUnit.ENTRIES)          // 堆内 1000 条
                .offheap(100, MemoryUnit.MB)            // 堆外 100MB
                .disk(1, MemoryUnit.GB, true))          // 磁盘 1GB（持久化=true）
        .withExpiry(ExpiryPolicyBuilder.timeToLiveExpiration(Duration.ofMinutes(10)))
        .build())
    .build(true);

Cache<Long, User> cache = cm.getCache("userCache", Long.class, User.class);
cache.put(1L, new User("tom"));
User u = cache.get(1L);

// Spring Boot（用 @EnableCaching + 配置）
// application.yml:
//   spring.cache.type: ehcache
//   spring.cache.ehcache.config: classpath:ehcache.xml

XML 配置

<!-- ehcache.xml（Spring 集成最常用） -->
<config xmlns='http://www.ehcache.org/v3'>
  <cache alias="userCache">
    <key-type>java.lang.Long</key-type>
    <value-type>com.example.User</value-type>
    <expiry>
      <ttl unit="minutes">10</ttl>          <!-- TTL：写入后 10 分钟 -->
      <!-- 或 <tti unit="minutes">5</tti>   TTI：闲置 5 分钟 -->
    </expiry>
    <heap unit="entries">1000</heap>        <!-- 堆内 1000 条 -->
    <offheap unit="MB">100</offheap>
    <disk-store unit="GB" persistent="false">1</disk-store>
  </cache>
</config>

堆外内存（offheap）是 Ehcache 相对 Caffeine/Guava 的核心优势：它不受 GC 管理，放几十 GB 也不会引起 GC 停顿。代价是必须序列化/反序列化（约 1~10 微秒/次）。所以典型配置是「堆内放热点、堆外放温数据、磁盘放冷数据」的三层结构。

调优与监控

# 关键参数与监控
#   命中率：cache.getStatistics() 或 JMX
#      CacheStatistics: getHits() / getMisses() / getEvictions()
#   目标：命中率 > 80%（本地缓存），若 <50% 说明该数据不该放本地缓存

# 调优清单
#   1) heap 条数按「热点数据量」设，不是按总数据量
#   2) 有 offheap 时，heap 层相当于 offheap 的 L1 缓存
#   3) 序列化要快：优先用 Ehcache 自带的或 FST/Kryo，避免 Java 原生序列化
#   4) 磁盘层必须配 persistence 目录，否则重启丢失
#   5) 集群同步（RMI/JGroups/ Terracotta）开销大，慎用

# Spring 使用
@Cacheable(value = "userCache", key = "#id")
public User getUser(Long id) { return userMapper.selectById(id); }

@CacheEvict(value = "userCache", key = "#user.id")
public void updateUser(User user) { userMapper.updateById(user); }
#   注意：本地缓存的 @CacheEvict <b>只清本机</b>，多实例下要配合消息广播
本地缓存和 Redis 该怎么分工？

本地缓存放「极热点 + 可容忍短暂不一致」的数据（如字典、配置、类目树），TTL 设短（1~5 分钟）；Redis 放「需要多实例一致」的数据。典型双层结构：本地 60s → Redis 300s → DB。本地缓存的价值是消灭网络往返（1ms → 100ns，快 10 倍）和降低 Redis 压力（热点 key 打爆单个 Redis 分片是常见故障）。

本地缓存最大的问题是什么？

多实例一致性。A 实例更新了 DB 并清了自己的缓存，B 实例的缓存还是旧的，可能持续几分钟不一致。三种解法：① TTL 短（最简单，推荐）——接受短暂不一致；② 消息广播失效（用 MQ/Redis PubSub 通知所有实例清缓存）——一致性好但有延迟和复杂度；③ 版本号/时间戳校验——读时比对版本。选①还是②取决于业务对一致性的容忍度。

Caffeine 和 Ehcache 选哪个？

默认选 Caffeine：命中率更高（W-TinyLFU）、API 更现代、性能更好、无依赖。选 Ehcache 的理由只有两个：① 需要堆外内存或磁盘分层（缓存数据量大到不能进 JVM 堆）；② 需要 JSR-107（javax.cache）标准 API 或已有 ehcache.xml 配置。除此之外没有理由在新项目用 Ehcache。
