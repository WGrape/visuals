gRPC 为什么比 HTTP+JSON 快？

「难道就一个二进制的区别，速度就快这么多吗？」——不是。编码只占六笔账里的一笔，而且是微秒级；真正的大头是 HTTP/2 多路复用与长连接省下的握手往返，那是毫秒级。

① 先回答那个问题：不是，二进制只是六笔账里的一笔

「gRPC 快是因为 Protobuf 是二进制的」——这句话不算错，但它是归因错误。把一次朴素 HTTP/1.1 + JSON 调用换成 gRPC，你换掉的是六个层面，编码格式只是其中之一，而且按耗时量级算，通常不是最大的那一笔。

层面换掉了什么省下的是什么量级谁是主力
① 编码JSON 文本 ↔ Protobuf 二进制解析与序列化的 CPU 时间、字节数微秒级—
② 连接短连接 / 队头阻塞 ↔ HTTP/2 多路复用长连接TCP + TLS 握手往返、慢启动反复触发毫秒级主力
③ 头部明文重复头部 ↔ HPACK 压缩每请求几十到几百字节小 body 时显著配角
④ 代码路径反射 ↔ 编译期生成的 stub反射查找、类型判断的 CPU 时间微秒~亚毫秒—
⑤ 内存临时字符串 / Map ↔ 直接写结构体字段分配次数与 GC 压力，主要影响尾延迟间接—
⑥ 往返次数N 次一元调用 ↔ 1 次流式调用N−1 个 RTT毫秒级高 RTT 时主力

一句话版本编码层省的是微秒，连接层省的是毫秒。两者相差两到三个数量级。所以「二进制让 gRPC 快很多」这个说法，把主角和配角搞反了。

② 最关键的一张图：微秒 vs 毫秒

把两件事放在同一条对数刻度轴上，结论就不需要争论了。

同一个「快」字，编码层省的是微秒，连接层省的是毫秒，两者相差两到三个数量级

编码差异：20–50 μs

一次 1 KB 左右的消息，JSON 解析换成 Protobuf 解码，单次省下的 CPU 时间大约在这个范围（随语言与字段数变化）。0.02–0.05 毫秒。

一次握手：1–60 ms

TCP 三次握手 1 个 RTT，TLS 1.3 再 1 个 RTT（TLS 1.2 是 2 个）。同机房 RTT 约 0.5–1 ms，跨城 20–30 ms —— 握一次手就是 1 到 60 毫秒。

算术结论省掉一次握手（比如把 3 次短连接调用并到 1 条长连接上），抵得上省掉几百到上千次编码差异。这就是为什么很多团队「把 JSON 换成 Protobuf，性能几乎没变」——他们优化的是那个微秒级的量，而瓶颈在毫秒级。

③ 编码层到底快在哪：不是「二进制所以快」这么一句

「二进制」三个字解释不了任何事，得说清楚读法的区别。JSON 解析是读文本，Protobuf 解码是读结构。

JSON 要先「读懂文本」才知道结构；Protobuf 的标签本身就写着结构

JSON 的四笔开销

① 逐字符扫描：必须读完才知道结构，无法跳过；
② 数字转换："12345" 要做字符串→整数/浮点转换，这是解析热点；
③ 键名哈希：无 schema，解析成 Map，键名要哈希与比较；
④ 临时对象：每个字符串、每个数字都可能产生新对象。

Protobuf 的四笔减免

① tag 即结构：tag 里带字段号与类型，按号定位，无需扫描；
② varint 移位：整数用移位还原，无字符串转换；
③ switch 分发：字段号是编译期已知的分支，无哈希；
④ 写入目标字段：生成代码直接赋值到结构体，少临时对象。

还有一个常被忽略的好处：前向兼容Protobuf 的 tag-length-value 让接收方可以跳过不认识的字段（因为长度写在前面）。所以加字段不用两边同时升级。这是工程价值，不是性能价值，但往往是团队选它的真正理由。

但别忘了体积的另一半Protobuf 比 JSON 小，一部分来自编码，一部分来自不带键名。JSON 里 "user_name" 这 11 个字节在 Protobuf 里是 1 个字节的字段号。字段多、键名长时差距明显；字段少、值很长时差距就小了。

④ 反证：只换编码，收益并没有想象的大

要证明「二进制不是主因」，最直接的办法是控制变量：分别只换一层，看各自贡献多少。

HTTP/1.1 + JSON（基线）
100%
HTTP/1.1 + Protobuf（只换编码）
约 82%
HTTP/2 + JSON（只换传输）
约 58%
HTTP/2 + Protobuf（= gRPC）
约 45%

这张表要看的是「谁贡献得多」只换编码：省约 18%；只换传输：省约 42%；两者都换：省约 55%。传输层的贡献是编码层的两倍多。

⚠️ 上面是示意量级，不是可引用的实测值。真实比例取决于 payload 大小、RTT、并发度、语言与框架实现。它说明的是结构关系（传输 > 编码），不是具体数字。要拿数字做决策，请在你自己的链路上压测。

这个结构关系还能推出两条很实用的结论：

反过来也成立

继续用 JSON，但把 HTTP/1.1 短连接换成 HTTP/2 + keep-alive + 连接池，往往能拿到 gRPC 收益的大部分。如果你的栈换不了 Protobuf，这条路的性价比更高。

只换编码会失望

只把 JSON 换成 Protobuf 而继续用「每次新建连接」的 HTTP/1.1，瓶颈完全没动，收益会小到让你怀疑是不是配错了。

⑤ HTTP/2 到底省了三件事

gRPC 跑在 HTTP/2 上，这是它相对「朴素 HTTP/1.1 + JSON」最大的结构性差异。

同样的 3 个并发调用：HTTP/1.1 要么排队要么多握手，HTTP/2 在一条连接上并发

① 多路复用

一条 TCP 上并发多个 stream，请求之间不再互相阻塞，也不必为并发多开连接。省的是握手往返和慢启动反复触发——对新连接来说，拥塞窗口要从头涨，前几个 RTT 的吞吐是被压着的。

② 头部压缩 HPACK

静态表（61 个常见头）+ 动态表 + 哈夫曼编码。重复的 :method、authorization、cookie 第二次起几乎不占字节。

③ 长连接与流控

连接常驻并配 keepalive，避免反复建连；流级 + 连接级流控窗口让多个流共享一条连接而不互相饿死。

当 body 只有几十字节时，省下的头部字节比省下的编码时间更有存在感

什么时候 HPACK 比 Protobuf 更重要当你的 RPC 是小 payload 高频调用（典型微服务：一个用户 ID 进去，一条记录出来，正文几十字节），每请求的头部可能是正文的好几倍。这种场景下 HPACK 省下的字节比 Protobuf 省下的更实在——而这一层跟「二进制」毫无关系，纯 HTTP/2 的功劳。

顺带一个生产坑：HTTP/2 的初始流控窗口是 65535 字节。跨洋 RTT 200 ms 时，单流理论吞吐只有 65535 / 0.2 ≈ 320 KB/s。不调大 INITIAL_WINDOW_SIZE，多路复用带来的吞吐会被窗口卡住。这是「换了 gRPC 怎么还是慢」的常见答案。

⑥ 代码路径：反射与代码生成

这一层常被忽略，但在某些语言里它的影响不比编码小。

环节典型 HTTP+JSON 框架gRPC
接口定义运行时靠文档 / 注解约定.proto 编译期生成 stub
参数绑定运行时反射读取字段、类型判断生成代码直接赋值到结构体字段
路由分发运行时匹配路径与方法方法表在生成代码里，分发是查表
类型错误运行时才发现编译期就能发现
中间对象常见 Map / 临时字符串 / 装箱少，主要是目标消息对象

为什么这一层容易被测出来反射调用在热路径上每次都要做字段查找、类型检查、装箱拆箱。这些操作单次是纳秒到微秒级，但一个请求里可能有几十个字段，累积起来就和序列化本身一个量级了。GC 压力同理——临时对象多了，尾延迟（P99）会明显变差，而平均延迟可能看不出来。

不过这一层不是 gRPC 独有的。用 JSON 但配一个代码生成的序列化器（如 FlatBuffers、Cap’n Proto，或带 schema 的 JSON 库），同样能消掉反射。所以它属于「gRPC 顺带带来的」，不是「只有 gRPC 才有」。

⑦ 什么时候 gRPC 并不快，甚至更慢

把话说完整：下面这些场景下，你换 gRPC 可能拿不到什么，甚至变糟。

① payload 很大

传 1 MB 的报文时，时间主要花在网络传输上，编码差异被稀释。若两边都开 gzip，文本和二进制压缩后的差距会进一步缩小。

② 跨公网、高 RTT

RTT 主导总耗时时，省下的那几十微秒根本看不见。此时该优化的是往返次数（批量、流式、就近接入），不是编码格式。

③ 低频调用

一天调几次的接口，长连接和多路复用的红利完全吃不到，还得承担连接保活的成本。

④ 已有高效 JSON 库

用 simdjson、或预编译 schema 的 JSON 序列化器，解析速度可以逼近二进制方案，差距会被压到很小。

⑤ 对方已经是 HTTP/2 + 连接池

如果你的 HTTP+JSON 栈本来就用 HTTP/2、keep-alive、连接池，那前面 §4 里最大的一笔（传输层）你已经拿到了，剩下的编码差异确实就只有那点微秒。

⑥ 浏览器 / 网关 / 调试

浏览器不能直接调 gRPC（需要 gRPC-Web 转译）；很多 API 网关、WAF、日志系统对 gRPC 的支持不如 HTTP/1.1 成熟；抓包调试也不如 JSON 直观。这些是工程成本，不该被性能数字盖住。

最容易被忽略的一条很多「gRPC 快 5 倍」的对比，对面站的是一个配置糟糕的 HTTP 客户端：每次新建连接、无连接池、无 keep-alive。这种对比测的不是协议，是配置。

⑧ Benchmark 的五个陷阱（看数字前先自查）

陷阱 1：拿「每次新建连接」的 HTTP 对比「长连接」的 gRPC

这是最常见的伪对比。测出来的差距里，绝大部分是握手，不是编码。公平做法是两边都配好连接池与 keep-alive，再比。

陷阱 2：跨语言比较

拿 Go 的 gRPC 对比 Python 的 json.loads，测到的主要差异是语言运行时，不是协议。要么同语言比，要么明确说明这是「技术栈对比」而非「协议对比」。

陷阱 3：payload 太小

几十字节的消息下，测的往往是框架的调度开销、内存分配、计时精度，序列化的那点差异淹没在噪声里。要测编码，就用接近生产的报文大小。

陷阱 4：没有预热

JIT 编译、连接池建立、动态链接、页缓存都需要时间。未预热的前几万次请求反映不了稳态。测之前先跑一段 warmup。

陷阱 5：只测序列化，或只测端到端

只跑 for i in range(N): dumps(obj) 测的是编码，拿这个数字说「接口快了 N 倍」是偷换概念。要证明端到端收益，就必须测端到端（含网络、含服务端处理）。

# 相对靠谱的自测方式：同语言、同连接策略、同 payload、预热后测端到端
# gRPC 侧
ghz --insecure --proto user.proto --call pb.UserService.Get     -d '{"id":1}' -c 50 -n 20000 localhost:9090

# HTTP 侧（务必显式开启长连接与连接池，否则测的是握手）
wrk -t4 -c50 -d30s -s post.lua http://localhost:8080/user/1

# 关键：两者都要看 P50 / P95 / P99，不要只看平均
# 编码差异常体现在 P99 与 CPU 占用上，平均值看不出来

⑨ 一句话回答，以及该怎么选

回答你的问题不是。二进制编码让每次序列化省下几十微秒；真正让你感觉「快很多」的，是 HTTP/2 的多路复用和长连接省掉的握手与往返——那是毫秒级，比前者大两到三个数量级。把 gRPC 的加速全归功于 Protobuf，是把配角当成了主角。

两个可以直接用的推论① 只把 JSON 换成 Protobuf、继续用短连接 → 收益会让你失望；
② 继续用 JSON、但换 HTTP/2 + keep-alive + 连接池 → 往往能拿到大部分收益。

场景建议理由
内部微服务、高频小报文gRPC 合适多路复用 + HPACK + 流式 + 强类型契约，几项红利都能吃到
对外开放 APIREST + JSON生态、可调试性、浏览器兼容比那点性能重要得多
已用 HTTP/2 + 连接池，只是想更快先别换协议最大的一笔已经拿到了，换协议收益有限、成本高
瓶颈在 RTT（跨公网 / 跨地域）先减往返次数批量、流式、就近接入；换编码对 RTT 无能为力
大报文、批量传输看压缩与分块瓶颈在网络传输，编码格式不是关键

最后一个提醒协议选型里，性能往往不是决定性因素。契约是否清晰、跨团队协作成本、可观测与排障能力、生态兼容性，这些通常比几毫秒更重要。先确认瓶颈真的在协议上，再动协议。

把「快」拆成六笔账

gRPC 快不是因为某个魔法，而是六个环节各自省了一点。拆开算才知道在什么场景下 gRPC 真的快、快多少。

环节HTTP+JSONgRPC节省
1. 序列化体积JSON 文本，含字段名Protobuf 二进制，字段号代替名字小 3~10 倍
2. 序列化 CPU文本解析（字符串、转义）二进制位操作快 5~20 倍
3. 协议开销HTTP/1.1 文本头，重复传HTTP/2 + HPACK 头压缩头开销降 80%+
4. 连接复用HTTP/1.1 每连接串行（或管道化有队头阻塞）HTTP/2 多路复用，单连接并发多流省 TCP 握手、少连接
5. 连接数每并发一个连接（或池）单连接多流连接数降 10~100 倍
6. 代码生成运行时反射解析编译期生成 stub 和解析代码省反射开销
场景gRPC vs JSON说明
小消息高频（内部微服务）快 2~5 倍头开销占比大，HTTP/2 头压缩收益明显
大 payload（>1MB）差距缩小瓶颈变成网络传输和压缩，序列化占比下降
跨公网/浏览器不适用浏览器无法直接调 gRPC（需 gRPC-Web 代理）
调试友好性JSON 完胜curl 直接调、肉眼可读
流式传输gRPC 完胜原生支持四种流式，HTTP/1.1 要自己搞 SSE/WebSocket
Protobuf 编码要点说明影响
字段号代替字段名1: xxx 而不是 "user_id": xxx这是体积小的主因
varint 变长编码小整数用 1 字节（如 <128）常见小值极省
zigzag 编码负数负数的 int32 只有 5 字节（不用 10 字节）sint32 比 int32 省
字段号 1~15 用 1 字节16 以上要多 1 字节高频字段放 1~15
默认值不编码值为 0/空串/False 时该字段完全不出现省空间，但无法区分「未设置」和「设为 0」（要 optional/wrapper）

示例

# ---------- 定义 ----------
syntax = "proto3";
service UserService {
  rpc GetUser (GetUserReq) returns (User);
  rpc ListUsers (stream GetUserReq) returns (stream User);  // 双向流
}
message GetUserReq {
  int64  user_id = 1;      # 字段号 1~15：编码用 1 字节，放高频字段
  string name    = 2;
}
message User {
  int64  user_id = 1;
  string name    = 2;
  sint32 score   = 3;      # sint32：负数用 zigzag，比 int32 省
}

# ---------- 生成代码 ----------
protoc --go_out=. --go-grpc_out=. user.proto
#   编译期生成 stub + 序列化代码（无反射）

# ---------- 体积对比（实测典型值）----------
#   同一条消息（含 user_id=12345, name="alice"）：
#     JSON:   {"user_id":12345,"name":"alice"}    = 32 字节
#     Proto:  0x08 0xB9 0x60 0x12 0x05 ...        =  9 字节
#   约 3.5 倍；字段越多、名字越长，差距越大（可达 10 倍）

# ---------- 调试 gRPC（没有 curl 那么方便，但有工具）----------
grpcurl -plaintext localhost:50051 list
grpcurl -plaintext -d '{"user_id":12345}' localhost:50051         UserService/GetUser

# ---------- HTTP/2 多路复用观察 ----------
#   一个 TCP 连接上并发多个 stream：
#     HEADERS frame (stream 1) + DATA frame (stream 1)
#     HEADERS frame (stream 3) + DATA frame (stream 3)   # 交错，互不阻塞
  • gRPC 快的本质是「二进制 + HTTP/2 + 代码生成」三件事，不是某一个单独的魔法。
  • 不要为了「快」盲目上 gRPC：如果你的服务瓶颈在数据库或业务逻辑，换 gRPC 毫无帮助。只有 RPC 本身的开销占比显著时才值得。
  • 浏览器场景用不了原生 gRPC：需要 gRPC-Web + 代理（Envoy）。对外部 API，REST+JSON 仍是更好的选择（生态、调试、缓存、CDN 都更成熟）。
  • Protobuf 的默认值不编码是个坑：无法区分「没设置」和「设成了 0」。proto3 用 optional 或 wrapper 类型（Int32Value）解决。
  • 字段号 1~15 只用 1 字节：把高频字段放在 1~15。字段号一旦上线就别改，改了就是破坏性变更。
  • HTTP/2 的多路复用有队头阻塞的隐患：虽然是流级别并发，但底层仍是单个 TCP，丢包时所有流都要等重传（TCP 队头阻塞）。QUIC/HTTP3 解决了这个。
  • gRPC 的流式是真正优势：四种流式（单向/双向）让实时推送、大文件传输比 REST 优雅得多。
gRPC 真的比 HTTP+JSON 快很多吗？

取决于场景，别信「快 10 倍」这类笼统说法。拆开看：① 序列化——Protobuf 比 JSON 小 3~10 倍、解析快 5~20 倍，这是最确定的收益；② 协议开销——HTTP/2 的 HPACK 头压缩让重复的请求头（尤其是长 header）开销降 80%+，小消息场景这一项收益最大；③ 连接复用——HTTP/2 单连接多路复用，省掉大量 TCP 握手和连接维护，高并发时这一项收益明显。合起来，在内部微服务、小消息、高并发的场景下，实测通常快 2~5 倍（延迟降 30~60%，CPU 降 30~50%）。但如果：④ payload 很大（>1MB）——瓶颈在网络传输，序列化那点差距被淹没；⑤ 瓶颈在数据库/业务逻辑——换协议毫无帮助；⑥ QPS 很低——绝对值省不了多少。建议：先用 pprof/火焰图确认序列化或网络开销真的占了显著比例，再决定换。

什么时候不该用 gRPC？

四种情况：① 对外开放的 API——浏览器无法直接调 gRPC（需要 gRPC-Web 代理），第三方集成成本极高，REST+JSON 的生态（文档、SDK、Postman、CDN 缓存）成熟得多；② 需要人工调试和排障——JSON 可以 curl 一下看结果，gRPC 要装 grpcurl 且消息是二进制，排障效率低（这也是很多团队内外网分治的原因：内部 gRPC、对外 REST）；③ 数据要给人看或要走 CDN/网关——JSON 能被 CDN、API 网关、日志系统直接理解和处理，二进制不行；④ 团队没有 IDL 管理经验——Protobuf 需要集中管理 .proto 文件和版本兼容，管理不善会变成噩梦。还有个隐性成本：Protobuf 的破坏性变更比 JSON 更危险——改字段号或类型会让旧客户端解析出错甚至崩溃，而 JSON 多一个字段通常无害。所以业界常见做法是内部服务间 gRPC、对外 REST、两边用 gateway 转换。

Protobuf 字段号为什么不能改？

因为 Protobuf 的 wire format 里，字段是用「字段号」标识的，不是用名字。线上传输的字节流是 [tag][value]，其中 tag 编码了字段号。如果你把一个字段的号从 2 改成 3：新版本发出去的消息里，那个值被标记成字段 3，而旧版本收到后在它的定义里找不到字段 3，就会把它当成未知字段丢弃——数据静默丢失，不报错。反过来更糟：如果你把字段 2 从 string 改成 int64，旧版本会尝试按 string 解析一段本来是整数的字节，得到乱码甚至解析失败。安全演进的规则只有三条：① 字段号永不复用（删除字段时用 reserved 2; 占位，防止后人误用）；② 新增字段用新号码，且旧版本会忽略它（这是安全的，但要注意默认值语义）；③ 改类型通常不安全，要新增一个字段、双写过渡、再下线旧的。实践建议：字段号 1~15 留给高频字段（编码只占 1 字节），上线前仔细设计，之后只增不改。
