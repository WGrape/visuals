TCP 零窗口与 Persist 探测：没丢包为什么连接还是停了

沿接收应用停止读取的时间线区分 rwnd=0、拥塞窗口、丢包与窗口更新丢失。

接收窗口是缓冲余量

TCP 接收端把收到的字节放入内核接收缓冲，应用调用 read 才会把数据逐步取走。接收窗口 rwnd 告诉发送端当前还可接收多少未处理数据。如果应用长时间不读，缓冲被填满，接收端可通告 rwnd=0；发送方此时暂停正常新数据发送。链路本身可能没有丢包、RTT 也正常，用户却看到上传或下载卡住。

零窗口与拥塞窗口 cwnd 小不同：rwnd=0 是接收端没有缓冲空间，cwnd 小是发送端认为网络路径需要收敛。二者都限制在途数据，但排查方向不同。抓包中要看对端窗口通告及窗口缩放协商，不能只看到发送端没包就判定网络断了。

一次时间线

服务器向客户端持续发送大文件，客户端程序因写磁盘很慢而暂时停止从 socket 读取。内核缓冲逐渐装满，客户端 ACK 中广告窗口从 64 KiB 缩小到 8 KiB，最终变成零。服务器仍可能收到这些 ACK，知道连接活着，但不再继续正常发送文件数据。客户端磁盘恢复后重新读取，内核窗口打开并发出窗口更新，服务器继续发送。

若这个“窗口重新打开”的更新包恰好丢失，服务器仍以为 rwnd=0，客户端却以为已通知对方，双方可能一直等待。TCP 因此使用 Persist 机制周期性探测窗口状态，使连接有机会重新同步。这种探测不是应用在发送新文件块，也不能拿它当作业务进度。

接收缓冲逐渐被文件数据填满。

通告零窗口

ACK 告诉发送方 rwnd=0。

发送方暂停

停止正常新数据，使用 Persist 探测。

窗口恢复

应用读取后通告新窗口，传输继续。

Persist 探测与保活不同

TCP keepalive 面向空闲连接存活检测；Persist/零窗口探测面向对端曾通告零窗口后，避免窗口更新丢失造成永久等待。两者触发条件和目标不同。抓包若见小探测段，先查此前是否有 Zero Window 通告，再区分是窗口探测、重传还是心跳。不同内核显示与计时方式可能不同，需结合连接状态和相邻报文解释。

探测存在不意味着连接能无限维持：应用长时间不读可能触发上层超时、代理关闭或操作系统资源限制。业务应明确慢消费者的等待上限和取消行为。

用数值看吞吐受限

假设路径 RTT 为 50 毫秒、网络可提供 100 Mbps，但接收窗口只能保持 16 KiB，理想窗口受限吞吐约 16 KiB/0.05s≈320 KiB/s，远低于链路速率。若窗口归零，正常新数据暂时完全停下。盲目把网卡从 1G 升到 10G 不会让接收应用读得更快。可以先查应用 CPU、磁盘、锁等待及接收缓冲大小，再判断是否需要调内核缓冲。

窗口变小不总是应用代码 bug：设备内存压力、代理背压或故意限速也可能造成慢读。增加接收缓冲可能缓解短时突发，却无法解决持续消费速度低于生产速度的问题，最终缓冲仍会填满。

抓包位置与窗口缩放

TCP 窗口字段基础宽度有限，连接建立时可协商窗口缩放。抓包工具显示的原始字段值与实际有效窗口可能不同；若漏抓 SYN，就可能不知道缩放因子。NAT、代理或 TCP 终止设备还会形成多段连接，客户端侧零窗口不一定等于源站侧零窗口。排障应按每一段四元组分别观察，并记录是哪一端通告的零窗口。

网卡卸载和抓包丢包也会让序列号与 ACK 轨迹看起来异常。先确认抓包完整、方向和相对序列号，再推断是哪一端处理不过来。若服务器发送端抓包没看到零窗口，但客户端抓包看到了，可能是中间路径丢包或观察点不一致。

修复与验收

复现时记录应用 read 调用频率、接收缓冲占用、窗口通告、磁盘写入耗时、CPU 与网络 RTT。若慢读由磁盘阻塞导致，优化写入或加异步缓冲；若代理队列积压，调小上游速率或加强背压；若确实需要更大短时突发缓冲，再审慎调节接收缓冲。修复后在相同大文件和并发下观察零窗口次数、停顿时长及端到端吞吐。

不要把所有停顿都称“丢包”。窗口为零时发送方按协议暂停，网络可能完全正常；只有把接收应用的消费速度纳入链路，才能解释现象。

自检

零窗口一定说明线路发生严重丢包吗？

不是。它通常表明接收端暂时没有缓冲空间，原因可能是应用慢读、内存压力或代理背压。
