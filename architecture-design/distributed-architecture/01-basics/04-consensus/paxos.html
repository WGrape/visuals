Paxos 共识算法

在"少数机器会挂、网络会丢"的环境下，让一群节点对"某件事的值"达成一致。Paxos 是共识算法的理论基石，Raft 是它的"易实现版"。

为什么需要共识 三类角色 Basic Paxos Multi Paxos Paxos vs Raft 面试要点

🤔 一、为什么需要共识

分布式系统里没有"全局时钟"、消息会丢会乱序，单台机器无法代表"全集群的事实"。共识（Consensus）解决的就是：即使在部分节点故障/网络异常时，存活节点仍能就某个值达成一致。

💡
共识 ≠ 复制：复制是把数据拷贝到多机；共识是"在不确定环境里，大家先商量好一个值再复制"。选主、配置变更、事务提交本质上都是共识问题。
Paxos 保证：只要多数派（> N/2）节点存活，系统就能持续就一系列值达成一致，且一旦某值被选定（chosen），永远不会被改成别的值。

🎭 二、三类角色

Proposer 提议者
提出"值"的提案（编号 n + value），发起协议。
Acceptor 接受者
决策者，存储提案、投票；通常 2F+1 个以容忍 F 个故障。
Learner 学习者
被告知最终选定结果，不参与投票（可理解为"同步副本"）。

🔁 三、Basic Paxos：两阶段提交

Prepare：Proposer 发带编号 n 的准备请求
编号 n 全局递增，用于排序。Acceptor 只承诺"不再接受编号 < n 的提案"，并把自己已接受过的最高编号提案返回。
Promise：Acceptor 响应
若 n 大于它见过的最大编号，则承诺并回复"我已接受过的提案（若有）"；否则忽略。
Accept：Proposer 收齐多数派 Promise 后发 Accept
value 取"Promise 中编号最大的已接受值"（没有则用自己最初想提的值）——这保证不会覆盖已被选定的值。
Accepted：Acceptor 接受并通知 Learner
Acceptor 若没承诺更高编号，则接受该值；多数派接受后该值被选定，Learner 学习到结果。
🔑
核心技巧：Prepare/Promise 阶段"抢占"编号，Accept 阶段"继承历史值"。正是"用最大编号 + 继承已选值"的设计，让 Paxos 在并发提议下仍能收敛到唯一值。

📜 四、Multi Paxos：连续达成共识

Basic Paxos 每次就一个值达成共识，开销大。Multi Paxos 把"选一个 Leader"和"日志序号"固定下来，让后续的 Accept 阶段不用每次都 Prepare，从而连续、高效地就一串值（日志）达成一致。

✅
Multi Paxos ≈ "先选一个稳定 Leader，之后的每个日志项基本只走 Accept 阶段"。这其实就是后来 Raft 的设计雏形——Raft 把"选主 + 日志复制"显式拆开，更易理解。

🎯 六、面试高频追问

Paxos 为什么需要两阶段？
单阶段无法应对并发提议与已选定值的冲突。阶段一"抢占+探明历史"，阶段二"在已知约束下提交"，二者配合保证安全性。
为什么是"多数派"？
任意两个多数派必有交集，保证"新提议能看到旧选定值"或"旧选定值已无法被推翻"，从而一致性成立。容错能力为 F 个故障需 2F+1 节点。
活锁（livelock）是什么？
两个 Proposer 不断用更高编号互相抢占，谁也定不下来。解法：选一个 Leader 专门提议，或用随机退避。

延伸阅读：Raft 日志复制与状态机 · ZAB 协议 · Raft 选举

Paxos 两阶段：把每个消息记住

阶段消息内容Acceptor 的动作
Phase 1aPrepare(n)提案号 n，不带值若 n > 已承诺的最大号 → 承诺不再接受 < n 的提案
Phase 1bPromise(n, v)承诺 + 已接受的 (nacc, vacc)若已接受过值，把值“捎带”回给 Proposer
Phase 2aAccept(n, v)提案号 n + 值 v若没承诺过更大的号 → 接受
Phase 2bAccepted(n, v)确认接受持久化 (n, v)，通知 Learner

关键机制只有两句：① 提案号全局递增且唯一（可用 round << 16 | serverId 生成）；② Proposer 必须沿用 Phase 1b 里带回来的值——这就是为什么 Paxos 一旦选定值就不会改变，也是安全性（不会选出两个值）的来源。

多数派（Quorum）与节点数：要背的数字

节点数 N多数派 Q可容忍故障 f评价
321最常用，成本最低
431不推荐：比 3 多一台，容错没变
532跨机房常用
743更高的写入延迟，很少用

公式：Q = ⌊N/2⌋ + 1，f = ⌊(N−1)/2⌋。两个多数派必然相交，交集里至少有一个节点同时知道两次决议——这条“相交性”是 Paxos/Raft 全部正确性的基石。

Multi-Paxos：怎么从 2 RTT 降到 1 RTT

Basic Paxos 每次决议都要走两阶段（2 次 RTT）。Multi-Paxos 的优化是：先选出一个稳定的 Leader，之后对连续的提案跳过 Phase 1，直接发 Accept —— 每个值只要 1 RTT。

变体选主每次决议 RTT日志连续性代表系统
Basic Paxos无2无（值独立）教学模型
Multi-Paxos有（长期）1无，需额外补洞Google Chubby / Spanner
Raft有（任期 term）1强制连续，简化实现etcd / Consul / TiKV
Zab有（epoch）1连续ZooKeeper

Raft 为什么更好落地：它用“日志必须连续”这一个约束，换掉了 Multi-Paxos 里最难的“空洞填补 + 乱序提交”逻辑。代价是 follower 日志落后时要用一致性检查回溯（nextIndex 递减）。

Paxos 活锁：为什么必须选主

经典活锁场景：Proposer A 发 Prepare(1) 刚要发 Accept，Proposer B 的 Prepare(2) 抢先到达，Acceptor 承诺不再接受 1；A 于是升级到 Prepare(3)，又把 B 的 2 挤掉……两个 Proposer 交替升级，永远选不出值。

  • 这不是死锁（系统没停，一直在跑），是活性失败（永远不进展）
  • FLP 不可能定理：异步网络下不存在既安全又保证终止的共识算法——只能靠随机退避降低概率
  • 工程解法：选主。同一时刻只让一个 Proposer 提案，冲突消失
  • 选主超时常用随机化退避（如 Raft 的 150 – 300 ms 随机选举超时），避免同时发起选举

工程落地的真实配置

etcd 参数与体检命令

# etcd（Raft）关键参数与观测
# 心跳间隔与选举超时：选举超时应 ≥ 10× 心跳
# etcd 默认 heartbeat=100ms, election=1000ms（正好 10 倍）
etcd --heartbeat-interval=100 --election-timeout=1000

# 跨地域部署必须放大（RTT 变大，否则频繁误判 leader 失效）
etcd --heartbeat-interval=500 --election-timeout=5000

# 看集群状态：关键看 raft term、raft index 是否一致
etcdctl endpoint status --write-out=table
etcdctl endpoint health --write-out=table

# 强制触发一次 leader 转移（滚动重启前很有用）
etcdctl move-leader <memberID>

# 磁盘慢会导致 etcd 频繁选主：用 fio 验证 fsync 延迟
# 要求：99th percentile fsync < 10ms（etcd 硬性建议）
fio --rw=write --ioengine=sync --fdatasync=1 --size=22m --bs=2300 \\
    --name=diskwrite --runtime=60

深入自检

Paxos 的“值一旦选定就不能改”怎么证明？

归纳法。假设值 v 在提案号 n 被首次选定（多数派接受）。对任意 n' > n 的提案，Proposer 做 Phase 1 时，那个多数派里至少一个节点会响应 Promise，并捎带回它已接受的 (n, v)。Proposer 必须沿用已被接受的最大号对应的值 → 就是 v。归纳下去，所有更大的提案值都是 v。

为什么节点数推荐奇数？

因为容错能力 f = ⌊(N−1)/2⌋：3 节点和 4 节点都只能容忍 1 台故障，但 4 节点要多花一台机器的成本，且多数派从 2 变成 3（写入更慢）。所以 4 节点是纯粹的浪费，这也是为啥没人部署 4 节点 etcd。

Learner 是干嘛的？为什么不能投票？

Learner 只接收已选定的值，不参与投票。作用是：① 新节点加入时先当 Learner 追数据，追上后再转为 Voter（避免拖慢多数派）；② 只读副本扩展读能力。etcd 3.4+ 支持 Learner 角色，Raft 论文里也有对应的 成员变更 处理。

Paxos 和 Raft 我该学哪个？

先学 Raft（有明确日志模型、可直接读 etcd 源码对照），再回头看 Paxos 理解“为什么 Raft 要做那些简化”。面试/实现用 Raft；理解分布式共识的本质约束（quorum 相交、提案号全序）看 Paxos。
