🛠️ MongoDB 生产实践

连接配置、写入关注、读写分离、监控指标与常见故障排查

上线前必配的几件事

  • 开启认证：--auth + 创建管理员与业务账号，禁止空密码外网访问
  • 副本集至少 3 节点：Primary + Secondary + Secondary（或 Arbiter），避免单点
  • 绑定内网 IP：bindIp 别写 0.0.0.0，配合安全组
  • 开启慢查询 Profiler：db.setProfilingLevel(1, {slowms: 100})
  • 设置 WiredTiger cache：默认取 (RAM-1GB) 与 RAM×50% 的较大者，容器里必须显式限制
  • 备份方案：mongodump（逻辑）或文件系统快照 / Ops Manager（物理）
    • writeConcern写要几个节点确认：w:1 / w:majority / w:"all"
    readPreference从哪读：primary / primaryPreferred / secondary / nearest
    readConcern读到什么程度：local / majority / snapshot
    journalWAL，默认开启，崩溃后重放恢复

    Write Concern：一致性与性能的旋钮

    读偏好怎么选

    readPreference行为适用风险
    primary（默认）只从主读要求读到最新主节点读压力大
    primaryPreferred优先主，主挂了读从兼顾可用与新鲜度主挂期间读到旧数据
    secondary只读从报表、离线分析可能读到明显滞后数据
    secondaryPreferred优先从，无从读主读多写少同上
    nearest按网络延迟选最近的多地域部署延迟最低但数据可能旧
    ⚠️ 经典事故：下单后立刻跳转详情页，读走了 secondary，oplog 还没同步过来，用户看到「订单不存在」。解决：这种 read-your-own-write 场景必须用 primary 或 readConcern: "majority"。

    连接与驱动配置

    // Node.js 驱动推荐配置
const client = new MongoClient(uri, {
  maxPoolSize: 100,             // 连接池上限（默认 100）
  minPoolSize: 10,              // 预热连接，避免冷启动抖动
  maxIdleTimeMS: 60000,         // 空闲连接回收
  serverSelectionTimeoutMS: 5000,   // 选节点超时，快速失败
  connectTimeoutMS: 10000,
  socketTimeoutMS: 45000,
  retryWrites: true,            // 自动重试可重试写
  retryReads: true,
  w: "majority",                // 写关注
  readPreference: "primaryPreferred"
});
    💡 连接池估算：需要的连接数 ≈ 并发请求数。默认 100 对多数服务够用；设太大反而会拖垮 mongod（每个连接约 1MB 栈开销）。多个服务共用集群时要算总和。

    必须监控的指标

    指标来源告警线
    oplog 窗口rs.printReplicationInfo()< 24h 警戒（从节点来不及追会全量同步）
    复制延迟rs.printSecondaryReplicationInfo()> 10s 关注
    慢查询数system.profile持续增长即排查
    连接数db.serverStatus().connections> 80% 上限
    Cache 使用率db.serverStatus().wiredTiger.cache"bytes read into cache" 持续高 = 内存不够
    锁/排队db.currentOp()长时间运行的 op 要 kill
    磁盘文件系统> 80% 要扩容（MongoDB 不自动收缩文件）

    典型故障与处置

    🐢 突然变慢

    • db.currentOp() 找长时间运行的 op，db.killOp() 杀掉
    • 看慢查询 profile，多半是新上线语句没走索引
    • 检查是否有后台建索引 / 分片迁移在跑

    🔗 连接池耗尽

    • 现象："connection pool exhausted" / 超时
    • 多半是驱动没复用 client（每次请求 new 一个）
    • 或 maxPoolSize 设太小而并发高

    💾 磁盘只增不减

    • 删文档不释放磁盘（空间留给复用）
    • 要真回收：副本集滚动执行 compact，或重建从节点
    • 更彻底：重新同步从节点再切主

    ⚠️ 主从切换后丢数据

    • 根因：writeConcern 用了 w:1
    • 关键写入改 w:"majority" + j:true
    • 回滚的写会写进 rollback 文件，可人工找回

    备份与恢复

    # 逻辑备份（可读、可跨版本，但慢）
mongodump --uri="mongodb://..." --out=/backup/20260101 --gzip

# 逻辑恢复
mongorestore --uri="mongodb://..." --gzip /backup/20260101

# 副本集隐藏节点做备份源（不打扰线上）
# 或用 LVM / 云盘快照做物理备份（快，但要停写或 fsyncLock）

# 按时间点恢复（需开启 oplog 备份）
mongorestore --oplogReplay --oplogLimit="1700000000:0" /backup/...
    ⚠️ mongodump 不是生产级全量备份方案：它对大集群很慢、备份期间影响性能、且不保证时间点一致（除非加 --oplog）。TB 级集群用文件系统快照或 Ops Manager 的持续备份。

    上线检查清单

    • ✓ 认证开启、账号按最小权限分配、bindIp 限制内网
    • ✓ 副本集 3 节点且节点分布在不同机架/可用区
    • ✓ 关键写入用 w: majority，读你写场景用 primary
    • ✓ 每个高频查询都有对应索引，explain 验证过
    • ✓ 慢查询 profiler 开启，有告警
    • ✓ oplog 窗口 > 24h，磁盘水位 < 80%
    • ✓ 备份可恢复（演练过恢复，不只是备份成功）

    🎯 常见问法与答题要点

    Q：writeConcern 选 w:1 还是 majority？

    A：看这笔写丢得起丢不起。w:1 只等主节点确认，最快，但主节点宕机且未完成复制时会丢（回滚）。w:majority 等多数节点确认，故障切换后数据一定还在，代价是延迟略高。生产建议：核心业务（订单、支付、账户）用 majority，日志/埋点这类可丢的用 w:1 换吞吐。

    Q：为什么刚写入的数据读不到？

    A：典型的 read-your-own-write 问题。写到了 primary，但读走了 secondary，oplog 还没同步过去。解决三选一：①该查询用 readPreference: primary；②用 readConcern: "majority"（只返回已被多数确认的数据）；③写完立刻读的场景走缓存或直接返回写入结果。

    Q：连接池该设多大？

    A：经验公式：maxPoolSize ≈ 单实例并发请求数，默认 100 通常够。设过大的危害是被忽略的一面——mongod 为每个连接分配约 1MB 栈内存，几千个连接就能吃掉几个 GB。另外要确认驱动是复用同一个 MongoClient（单例），每次请求 new client 是最常见的连接池耗尽原因。

    Q：删了数据磁盘为什么没变小？

    A：MongoDB 删除文档只是把它标记为可复用空间，不会把文件还给操作系统，因为预分配的数据文件后续还要写入。真要回收：①副本集滚动执行 db.runCommand({compact: "coll"})；②重建从节点（initial sync）后切主；③导出再导入。注意 compact 在 4.4+ 对主节点也会加锁，务必在从节点滚动做。

    Q：副本集最少几个节点？能用 2 个吗？

    A：最少 3 个（或 2 数据节点 + 1 仲裁 Arbiter）。2 个数据节点不行：挂掉一个后剩下 1 个无法形成「多数」（1/2 不是多数），集群会变成只读无法选出新主。Arbiter 只投票不存数据，能用但会浪费一台机器，生产建议直接上 3 个数据节点。

    Q：oplog 是什么？太小会怎样？

    A：oplog 是主节点记录所有写操作的定长集合（capped collection），从节点靠重放它来同步。它是定长的，写满了就覆盖最老的。如果从节点停机时间超过 oplog 覆盖的时间窗（oplog window），它就追不上了，只能全量重新同步（initial sync），代价极高。生产建议保证 oplog 窗口 > 24 小时，最好 72 小时。

    Q：慢查询怎么系统化排查？

    A：四步：①db.setProfilingLevel(1,{slowms:100}) 开采样；②从 db.system.profile 取 top 慢语句；③对每条跑 .explain("executionStats")，重点看 stage（COLLSCAN?）、totalKeysExamined/nReturned 比值；④补索引或改写法（避免无索引 $regex、大 skip、$unwind 后大 group）。
