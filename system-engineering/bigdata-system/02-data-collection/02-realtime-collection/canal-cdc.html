📡 CDC：捕获数据库的每一次变动

通过解析数据库日志（如 MySQL binlog）实时获取数据变更，比定时轮询更及时、更完整、对源库压力更小。

先建立直觉：看监控录像 vs 定时拍照

要知道仓库里发生了什么变化，有两种办法：

  • 定时轮询（查 updated_at）：每分钟拍一张照片，对比前后差异。缺点：两次拍照之间的变化会丢（删掉的东西永远看不出来），而且频繁拍照很累。
  • CDC（看监控录像）：直接读取数据库自己记的流水账（binlog），每一次增删改都完整记录。优点：不漏、及时、还能看到删除。

CDC 就是「看监控录像」——数据库本身就有完整的变更日志，我们只是去读它。

CDC 的三种实现方式

方式做法优点缺点
基于日志（主流）解析 binlog / WAL不侵入业务、能捕获删除、延迟低需数据库权限、解析有成本
基于触发器在表上建 trigger 写变更表实现简单影响业务性能，一般不推荐
基于查询定时按时间戳查增量最简单漏删除、有延迟、压库
基于日志的 CDC 是工业标准。因为它完全不侵入业务代码，且能捕获所有变更（包括 DELETE，这是轮询永远做不到的）。

Canal 的工作原理

ROW 格式的关键字段

一条 binlog 事件（ROW 格式）通常包含：

字段含义
typeINSERT / UPDATE / DELETE
table表名
before变更前的数据（UPDATE/DELETE 有）
after变更后的数据（INSERT/UPDATE 有）
ts变更时间戳
为什么 ROW 格式很重要？ROW 记录的是每一行的前后值，所以下游能精确知道改了什么。而 STATEMENT 格式只记录 SQL 语句——像 UPDATE t SET x=x+1 WHERE ... 这样的语句，下游无法得知到底哪些行被改、改成了什么。所以 CDC 必须用 ROW 格式。

典型应用场景

  1. 数据同步到数仓：业务库变更实时入湖入仓，替代定时抽取；
  2. 缓存一致性：数据库变更后自动删除/更新 Redis 缓存（比在应用代码里删更可靠，可重试）；
  3. 搜索引擎同步：MySQL 数据实时同步到 Elasticsearch；
  4. 异地多活 / 数据复制：跨机房同步；
  5. 审计与回溯：保留完整变更历史，可追溯「这条记录什么时候被谁改过」。

三个必须注意的点

① 消费必须幂等。MQ 可能重复投递，且 CDC 本身支持位点回退重放。所以下游写入要能处理重复事件——通常用 upsert（按主键覆盖）而不是追加。
② 事件可能乱序。尤其经过 MQ 分区后，同一主键的多个变更可能不按序到达。如果直接按顺序应用，可能把旧值覆盖到新值上。解法：按主键分区（保证同 key 有序），或用版本号/时间戳丢弃过期事件。
③ DDL 变更是隐蔽杀手。上游加了一列、改了字段类型，下游解析逻辑可能直接报错或静默出错。CDC 对 DDL 的支持通常弱于 DML。建议：建立 DDL 变更的通知与协同机制，下游要及时适配；并对解析失败设置告警而不是静默跳过。

🎯 面试问答

Q：CDC 和定时查询增量有什么区别？
A：三个关键差异：① 能否捕获删除——CDC 能（binlog 里有 DELETE 事件），轮询永远不能（记录都没了，查不到）；② 延迟——CDC 是秒级甚至亚秒级，轮询最快也是分钟级；③ 对源库压力——CDC 只是读日志文件，几乎不增加数据库负担；轮询要反复执行带索引的查询，数据量大时明显压库。所以只要条件允许（能开 binlog），都应该用 CDC。

Q：为什么 binlog 必须设成 ROW 格式？
A：因为 ROW 格式记录每一行的前后值，下游才能精确知道「哪一行从什么变成了什么」。而 STATEMENT 格式只记录 SQL 语句本身——遇到 UPDATE t SET x = x + 1 WHERE status = 1 这类语句，下游无法得知受影响的具体行和结果值，除非重新执行一遍（不现实且可能因环境差异结果不同）。所以 CDC 的前提就是 ROW 格式。另外还需账号有 replication 权限。

Q：Canal 和 Debezium 怎么选？
A：Canal：专注 MySQL，轻量易用，国内文档与案例丰富，适合只用 MySQL 且想快速落地的团队。Debezium：支持 MySQL、PostgreSQL、MongoDB、SQL Server、Oracle 等多种数据库，依托 Kafka Connect 生态，通用性和可扩展性更强，适合异构数据源或已在用 Kafka 的团队。如果用 Flink 做实时处理，Flink CDC（基于 Debezium）是更顺滑的选择——它把 CDC 源直接做成 Flink 的表。

Q：CDC 同步的数据会重复或乱序吗？
A：会，两者都需要处理。重复：MQ 可能重复投递、位点也可能回退重放 → 下游用 upsert（按主键覆盖）保证幂等。乱序：经过 MQ 多分区后，同一主键的多次变更可能乱序到达，直接应用会导致旧值覆盖新值 → 解法是按主键分区（保证同 key 在同一分区从而有序），或在事件中携带版本号/时间戳，丢弃比当前值更旧的事件。这两点是 CDC 落地最容易踩的坑。

CDC 工具选型：一张表定方案

CDC（变更数据捕获）的核心差别在两处：怎么读变更（解析 binlog / 查时间戳 / 触发器）和怎么保证不丢不重。

MySQL 前置配置

# MySQL 开启 binlog 的前置条件（缺一不可）
[mysqld]
server-id        = 1001          # 必须唯一，且 Canal 要用另一个 id
log-bin          = mysql-bin
binlog_format    = ROW           # 必须 ROW，STATEMENT 拿不到行数据
binlog_row_image = FULL          # 必须 FULL，MINIMAL 只有变化列，缺前镜像
# 验证
SHOW VARIABLES LIKE 'binlog_format';      # -> ROW
SHOW VARIABLES LIKE 'binlog_row_image';   # -> FULL
SHOW BINARY LOGS;
SHOW MASTER STATUS;                       # 记下 File + Position

# Canal 需要的账号权限（最小权限原则）
CREATE USER canal@'%' IDENTIFIED BY 'canal';
GRANT SELECT, REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO canal@'%';

选型的硬约束：binlog_format=ROW 是 Canal/Debezium 的前提，改成 STATEMENT 就直接不可用；binlog_row_image=MINIMAL 会导致只有变化后的列，做「前镜像对比」或删除事件解析时会缺字段。生产上建议 FULL + 定期清理（expire_logs_days=7）。

问题原因解法
位点丢失，数据重复位点存在本地文件，实例迁移就没了位点改存 DB / ZooKeeper；消费侧做幂等
DDL 导致解析失败表结构变了，旧解析器不认Canal 默认忽略 DDL；要 DDL 就开 tsdb 存历史表结构
大事务把 Canal 卡死单个事务 binlog 很大，解析内存爆拆事务；调大 Canal 的 transaction.size
主备切换后拉不到位点在新主上不存在开 GTID（gtid_mode=ON），按 GTID 定位而非文件名+位置
下游积压消费速度 < 生产速度加大并行度（按表/按主键分区）；异步化写入
乱序并发消费 + 分区键选错按主键做分区键，保证同一行的变更有序
  • 全量 + 增量的衔接是 CDC 最容易出错的地方：正确做法是「先记位点 → 全量快照 → 从位点追增量 → 合并去重」，而不是「全量完再开始拉增量」（会丢中间的变更）。Flink CDC 的 scan.incremental.snapshot.enabled=true 就是帮你做这件事。
  • 消费侧必须幂等：CDC 的语义是至少一次，重复投递是常态。落地时按主键做 UPSERT，或按 (binlog_file, position) 去重。
  • 删除事件：ROW 格式的 DELETE 只有前镜像（无后镜像），下游要能识别 op='d' 并做软删除或物理删除，别当成普通更新。
  • 延迟监控：监控「binlog 当前位点 - 消费位点」的字节差值而不是时间，时间在低流量时会假性正常。
CDC 和定时抽取（Sqoop/DataX）什么时候用哪个？

看是否需要增量和实时性。首次全量迁移用 DataX/Sqoop（简单、可控、可限速）；之后持续同步必须 CDC。CDC 的优势是毫秒级、只传变更、能拿到删除事件；定时抽取做不到这三点（删除尤其麻烦，只能靠全量对账）。

为什么 Canal 会拖垮 MySQL？

正常情况不会（只是读文件）。但三种情况会：① 全量快照时 Canal 会对表做 SELECT *，大表瞬间打满 IO；② binlog 堆积导致磁盘满，MySQL 无法写；③ Canal 伪装 slave 后，MySQL 的 sync_binlog 与半同步复制会受从库数量影响。解法：全量放在低峰、限速；binlog 保留 ≥3 天并监控磁盘。

怎么保证 CDC 数据不丢？

三个层次：① 位点持久化（不存本地文件）+ 位点与业务写入同一事务（或用支持事务的下游如 Kafka 事务）；② 至少一次 + 下游幂等（最实用）；③ 定期对账——按时间窗口比对源表和目标表的 checksum/count，这是兜底的最后一道防线，任何 CDC 方案都该配。
