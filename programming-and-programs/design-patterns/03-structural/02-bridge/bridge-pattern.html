🌉 桥接

把两个独立变化的维度拆开，用组合连接。

一句话记住遥控器和电视品牌分别发展；遥控器只对设备接口发指令。
问题从哪来图解协作动手试一试伪代码选型与边界
01 · 从问题出发

为什么会需要这个模式？

通知渠道有邮件/短信，消息等级有普通/紧急；继承组合会产生越来越多子类。

消息有普通/加急两类，渠道有邮件/短信两种时，继承可能出现 NormalEmail、UrgentEmail、NormalSms、UrgentSms 四个类；再加推送渠道，组合继续倍增。

😵 直接写会怎样

class UrgentEmailNotice { ... }
class UrgentSmsNotice { ... }
class NormalEmailNotice { ... }
class NormalSmsNotice { ... }

💡 关键转折

抽象层持有实现接口；两边可分别扩展，不形成乘法式子类。

把“消息规则”和“投递渠道”拆成两个独立轴。Notice 持有 Channel 接口，组合出需要的搭配。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

interface Channel { send(text) }
class Notice {
  constructor(channel: Channel) { this.channel = channel }
  send(text) { this.channel.send(text) }
}
class UrgentNotice extends Notice {
  send(text) { this.channel.send("[加急] " + text) }
}
new UrgentNotice(new SmsChannel()).send("付款失败")

读代码时抓住三件事

  1. Notice 保存的是 Channel 接口，不固定绑定 SmsChannel。
  2. UrgentNotice 只扩展消息规则，不实现具体协议。
  3. 新增渠道与新增消息类型各改自己的一侧。

换个业务场景，还能认出来吗？

图形编辑器可以把“形状”与“绘制后端”拆开：Circle/Rectangle 持有 Renderer，VectorRenderer 与 RasterRenderer 分别实现绘制。这样形状和渲染器独立扩展。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

两个维度都可能独立扩展，继承组合开始成倍增长

三个具体场景

  • 通知等级与投递渠道分别扩展
  • 形状与绘制后端分别扩展
  • 遥控器种类与设备品牌分别扩展

不适合或要小心

若只有一个变化维度，普通组合已足够。桥接的两侧都应有独立演进的理由。

只有一个稳定维度时，普通组合足够

最容易混淆的相邻模式

模式真正的区别
适配器为已经不兼容的接口做翻译；桥接提前把两个变化维度分离。
策略重点切换算法；桥接强调两个层次都能独立形成子类型或实现。

区分时问自己：是不是两个独立变化轴，而不只是切换一个算法？

落地前检查

  • 确认确有两个独立变化维度，而非想象中的扩展。
  • 接口保持稳定且足够小，避免抽象层知道渠道细节。
  • 测试每种抽象能与每种实现合理组合。
06 · 自己说一遍

两道检验理解的小题

新增微信渠道要增加 UrgentWechatNotice 吗？

不用；新增 WechatChannel，再注入现有 Notice。

如果新增 PushChannel，要修改 UrgentNotice 吗？

不需要；实现 Channel 并在组装处注入即可。

桥接模式：两个维度独立演化，用组合代替乘法式继承

一、问题：继承导致的类爆炸

假设有 3 种形状、3 种渲染方式。用继承要写 9 个类（CircleGL、CircleVulkan、CircleSoftware、SquareGL……）。再加一种形状就要加 3 个类。这就是笛卡尔积式膨胀。

// 桥接：把「形状」和「渲染」拆开，各自独立演化 type Renderer interface { // 实现层 DrawCircle(x, y, r float64) DrawRect(x, y, w, h float64) } type GLRenderer struct{} // 实现层的一种 type VulkanRenderer struct{} type SoftwareRenderer struct{} type Shape interface { // 抽象层 Draw() } type Circle struct { // 抽象层持有实现层的引用 = 桥 r Renderer x, y, rr float64 } func (c *Circle) Draw() { c.r.DrawCircle(c.x, c.y, c.rr) } // 使用：任意组合，无需新增类 c := &Circle{r: &GLRenderer{}, x: 0, y: 0, rr: 10} c.Draw() // 3 形状 + 3 渲染 = 6 个类，而不是 9 个；再加维度也只是加法

二、桥接 vs 适配器 vs 策略

模式意图何时引入结构
桥接让抽象与实现独立变化设计初期就预见两个维度会各自扩展抽象持有实现，两层平等
适配器让已有接口能配合事后发现接口不匹配才补救包装一个已有对象
策略替换算法运行期需要切换算法上下文持有策略
最容易记混的一点

桥接和适配器结构几乎一样（都是「持有另一个对象并转发」），区别只在时机与意图：桥接是提前设计、为了让两边独立演化；适配器是事后补救、为了让不兼容的东西能合作。桥接的两层是你自己设计的；适配器至少有一边是已有的、改不了的。

五、深入自检

怎么判断该不该用桥接？

问自己：这个系统是否存在两个正交的变化维度，且都可能各自增加？如果只有一个维度在变，用普通继承或策略就够；如果两个维度都固定不变，那就更不需要。

桥接会增加复杂度吗？

会引入额外的接口与间接层。如果维度其实不会扩展（比如渲染方式永远只有一种），桥接就是过度设计。判断依据是变化是否真实存在，而不是「万一以后要扩展」。

和抽象工厂能配合吗？

经常配合：抽象工厂负责创建「某一族的实现层对象」，桥接负责把抽象层和实现层连起来。比如工厂创建 Windows 平台的渲染器，桥接把它注入形状对象。

Go 里怎么写桥接最自然？

用接口表达实现层，抽象层结构体持有一个接口字段。这几乎是 Go 的原生写法，甚至不需要刻意「套模式」——因为 Go 没有继承，组合本来就是默认选择。

桥接和依赖注入是什么关系？

桥接的「抽象持有实现」本质上就是依赖注入：实现层通过构造参数传入，而不是在抽象层内部 new 出来。这让两层可以独立测试与替换。
