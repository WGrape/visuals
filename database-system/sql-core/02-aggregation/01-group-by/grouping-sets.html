GROUPING SETS：一次查询生成多个汇总层级

报表总计、小计和明细可以用明确的分组集合描述。

核心机制

GROUPING SETS 列出要计算的分组键组合。每个组合相当于一个分组聚合结果；空集合 () 表示全表总计。ROLLUP 适合有层级顺序的小计，CUBE 适合所有维度组合。

汇总层级缺失的列常显示 NULL，但源数据本身也可能为 NULL。支持 GROUPING 函数的数据库可用其标志区分“这一层没有按该列分组”和“真实值为空”。

用一个例子看过程

SELECT region, product, SUM(amount)
FROM sales
GROUP BY GROUPING SETS ((region, product), (region), ());

明细层

(region, product) 给出每个地区与产品组合的销售额。

地区小计

(region) 汇总该地区所有产品，product 显示汇总占位。

全表总计

() 汇总全部行；需要识别层级时增加 GROUPING 标志。

观察、原因与处理

观察原因或含义处理与验证
地区产品明细(region, product)用于下钻分析
地区合计(region)用于地区报表页脚
全局合计()用于整张报表总计

从三条销售记录推到六行结果

设原始记录为华东/书籍/100、华东/文具/50、华南/书籍/70。(region, product) 产生三个明细组；(region) 产生华东 150 与华南 70 两个地区小计；空分组 () 产生全局总计 220。一次 GROUPING SETS 查询输出六行，语义上近似对三个 GROUP BY 查询做 UNION ALL，但引擎可能共享扫描或聚合阶段。

区分汇总占位与真实缺失

汇总行的 product 显示 NULL，意思可能是“本层没有按 product 分组”，也可能是源数据中的 product 真为 NULL。支持 GROUPING(product) 的数据库可用标志区分两者。若直接把所有 NULL 显示成“全部商品”，真实缺失值也会被误标。报表应先识别层级，再决定展示标签。

ROLLUP(region, product) 通常产生明细、地区小计与全局总计；CUBE(region, product) 还会产生跨地区的商品小计。维度越多，CUBE 组合增长越快；只要指定层级的报表更适合显式 GROUPING SETS。结果行展示顺序仍应使用 ORDER BY 指定。

练习：报表口径与指标类型

需求只要“各地区各商品”“各地区小计”“全部总计”，不需要“跨地区按商品小计”。请写出三个 grouping set，并解释为什么无需 CUBE。如果统计客单价，不能对各组平均客单价再求平均；应先汇总销售额与订单数，再计算比率。改变聚合层级前先检查度量是否可加总。

边界与误区

SQL 方言对 GROUPING、ROLLUP 和结果排序有差异。多个分组层级可能增加计算与输出行数，报表展示仍需显式 ORDER BY。

性能与正确性的核对顺序

先用少量输入行手算每个层级的总和和输出行数，再执行 SQL 比较；若业务允许 source product 为 NULL，要加一条真实 NULL 样本检查展示标签。GROUPING SETS 的结果可能在同一个地区出现明细、小计与全局汇总，图表层如果简单再次 SUM，容易重复计数。因此应把层级标志作为数据的一部分传给展示层，禁止把不同层级混在一组中二次汇总。

生产数据上还要看分组基数与内存需求。多个维度组合可能生成大量聚合桶；先估计各组合的唯一键数，再看执行计划是否溢写磁盘。若报表频繁查询同一层级，可评估物化汇总，但要定义刷新延迟与源数据更正策略，避免用户看到不同层级的数字彼此对不上。

把层级作为明确字段传给前端

汇总结果最好增加一个可解释的层级标志，例如“明细”“地区小计”“全局总计”，而不是仅靠哪些列为 NULL 猜测。这样源数据真的含 NULL 时仍可正确展示，也能防止前端把三个层级再次混合求和。报表导出时要决定小计是否计入筛选后的分页；如果只在当前页重新合计，数字可能与全量总计不符。对物化汇总还要记录刷新时间：明细实时更新、小计延迟十分钟，用户看到的层级数字可能暂时不一致，需要在页面或 API 中标明。

自检

汇总行的 product 为 NULL，能断定原始 product 没有值吗？

不能。它可能只是该汇总层级未按 product 分组；可用 GROUPING(product) 等标志区分。
