🚶 迭代器

统一逐个访问元素，同时隐藏集合的内部结构。

一句话记住图书馆借阅员只说“下一本”，不用知道书架是数组还是树。
问题从哪来图解协作动手试一试伪代码选型与边界
01 · 从问题出发

为什么会需要这个模式？

调用方既要遍历数组又要遍历树；若直接依赖存储结构，换结构会改遍历代码。

报表模块直接用数组下标遍历订单。后来订单改存树结构，所有报表都要改循环；如果还要支持按时间倒序，又会出现更多遍历分支。

😵 直接写会怎样

for i in range(orders.length):
  render(orders[i])
// 假设 orders 永远是数组

💡 关键转折

集合提供迭代器，调用方只用 hasNext/next 或语言的 for-of 协议。

把遍历位置与推进规则放进迭代器。客户端只问“还有吗、下一个是谁”，不用知道数组下标或树遍历栈。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

iterator = collection.iterator()
while iterator.hasNext():
  item = iterator.next()
  visit(item)

// 树迭代器内部可维护 stack；调用方不需要知道。

读代码时抓住三件事

  1. hasNext 和 next 是外部遍历契约。
  2. 迭代器内部保存状态，不把游标暴露给客户端。
  3. 不同迭代器可提供不同顺序，如正序、倒序。

换个业务场景，还能认出来吗？

数据库游标、语言里的 for-of/Iterable 都体现了迭代思想。遍历远程数据时要暴露可能的失败与资源关闭，不应假装网络迭代等同内存数组。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

遍历方式要统一，集合内部结构不应泄漏

三个具体场景

  • 数组与树统一逐项访问
  • 同一集合提供正序与倒序
  • 分页数据隐藏取下一页的细节

不适合或要小心

迭代期间修改集合要定义规则：快照、失败即报错或弱一致。迭代器不自动解决并发安全。

远程迭代还需处理延迟、异常和资源关闭

最容易混淆的相邻模式

模式真正的区别
组合定义树形部分-整体结构；迭代器决定怎样访问结构中的节点。
访问者把对每种节点的操作分离出来；迭代器负责走到每个节点。

区分时问自己：要解决怎样走到每个节点，还是走到后对节点做什么？

落地前检查

  • 定义遍历期间集合被修改时的行为。
  • 测试空集合、末尾与重复 next。
  • 远程迭代要处理关闭、分页和失败恢复。
06 · 自己说一遍

两道检验理解的小题

把数组换成树，调用方循环要改吗？

若迭代器契约相同，就不必改；只换集合内部的迭代实现。

一个集合只能有一个迭代器吗？

不是。可同时提供正序、倒序、深度优先等多个迭代器，且各自保存独立游标。

模式速览：把「怎么遍历」从「存什么」里分离出来

迭代器解决的是一个很具体的问题：集合的内部结构可能变，但遍历它的方式不应该跟着变。把遍历逻辑挪到独立的迭代器对象里，调用方只需要知道「还有没有下一个」，不需要知道背后是数组、链表还是树。

意图不暴露集合内部结构，就能顺序访问它的元素
角色迭代器（定义接口）与聚合（提供迭代器）
何时用需要多种遍历方式、或不想暴露内部结构时
代价多一层间接；遍历中修改集合需要额外约定
迭代器把遍历状态从集合里挪出来，放进独立的游标对象

四种遍历方式怎么选

方式形态优点适合
直接下标循环用索引访问最快最直接数组、切片这类连续结构
迭代器对象显式的游标对象可支持多种遍历、可暂停恢复树、图、需要多种顺序
生成器风格用 yield 逐个产出写起来最简洁语言支持时优先选择
回调式遍历把处理函数传进去省去样板代码简单的一次性遍历

迭代器的真正价值

不是「能遍历」，而是遍历方式可以独立变化：同一个树可以有前序、中序、层序三种迭代器，客户端代码完全不用改。如果只是数组遍历，直接循环就好。

为什么有些语言里很少手写它

因为语言已经内置了：遍历协议、生成器、range 语法都在做同一件事。这时手写迭代器反而是重复造轮子，真正需要手写的是「非顺序结构的自定义遍历」。

Go 里的实现：从显式迭代器到函数式遍历

// 方式一：显式迭代器接口 type Iterator[T any] interface { HasNext() bool Next() T } // 方式二：函数式遍历（Go 1.23 起可直接 range 函数） func (t *Tree) All(yield func(v int) bool) { var walk func(n *Node) bool walk = func(n *Node) bool { if n == nil { return true } if !walk(n.Left) { return false // 调用方想提前结束 } if !yield(n.Value) { return false } return walk(n.Right) } walk(t.Root) } // 使用：和遍历普通集合一样自然 for v := range tree.All { if v > 100 { break // 提前退出，遍历会正确停止 } fmt.Println(v) } // 关键点： // 1) yield 返回 false 表示调用方不想继续，必须立刻停止 // 2) 递归遍历要保证每个分支都检查这个返回值 // 3) 这样遍历是惰性的，不需要先把整棵树展开成切片

深入自检：迭代器的五个问题

遍历时修改集合会怎样？

大多数实现会直接报错或行为未定义。常见做法是在集合上维护一个修改计数，迭代器每次取元素前比对，不一致就抛出并发修改异常。这是为了尽早暴露问题，而不是静默产生错乱结果。

迭代器是一次性的吗？

通常是：它持有游标状态，走完就结束了。想再遍历一次要重新索取一个。这与「集合本身可以反复遍历」不矛盾，因为集合负责创建新的迭代器。

惰性遍历有什么好处？

不需要把所有元素先准备好：可以边读边遍历大文件、可以遍历理论上无限长的序列、可以提前中断而不浪费已经做的准备工作。代价是每次取元素都有一点调用开销。

多种遍历顺序怎么组织？

提供多个创建方法，各自返回不同顺序的迭代器。集合本身不变，遍历策略独立演化。这正体现了这个模式的价值：把变化的部分（遍历方式）隔离在独立对象里。

什么时候不该用它？

当集合就是简单的连续结构、且只有一种遍历顺序时，直接循环最清楚。引入迭代器反而增加了一层间接，读者要先理解接口才能看懂代码。

核心价值遍历方式与存储结构解耦
关键角色迭代器 + 可迭代的集合
惰性边取边算，支持提前中断
失败约定遍历中修改要有明确行为
语言内置优先能 range 就别手写
手写场景树、图、分页游标、懒加载
