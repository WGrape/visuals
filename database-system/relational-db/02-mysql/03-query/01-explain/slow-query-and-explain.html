慢查询与执行计划

从慢日志抓问题 SQL，用 EXPLAIN 看懂它到底怎么跑的

一句话
先靠慢查询日志抓到问题 SQL，再用 EXPLAIN 看它到底怎么执行的
排查顺序
抓慢 SQL -> 看执行计划 -> 看扫描行数 -> 定索引 -> 改写法
EXPLAIN 关键列
type、key、rows、Extra 四列决定 80% 的判断
目标
把 type 提到 range 以上，把 rows 压到最小，消灭 Using filesort

一、怎么抓到慢 SQL

-- 1) 确认慢日志已开启 SHOW VARIABLES LIKE 'slow_query_log'; SHOW VARIABLES LIKE 'long_query_time'; -- 默认 10s，线上常设 0.5~1s SHOW VARIABLES LIKE 'log_queries_not_using_indexes'; -- 2) 临时开启（重启失效） SET GLOBAL slow_query_log = ON; SET GLOBAL long_query_time = 0.5; -- 3) 用 mysqldumpslow 聚合，别一条条看 mysqldumpslow -s t -t 10 /var/lib/mysql/slow.log # -s t 按总耗时排序 -t 10 取前 10 条 # -s c 按出现次数排序（适合抓高频小慢查询） -- 4) 也可以用 performance_schema 直接查 SELECT digest_text, count_star, avg_timer_wait/1e9 AS avg_ms FROM performance_schema.events_statements_summary_by_digest ORDER BY avg_timer_wait DESC LIMIT 10;

二、EXPLAIN 四列速判

列看什么好坏
type访问方式system / const / eq_ref / ref / rangeindex（全索引扫）、ALL（全表扫）
key实际用到的索引有值且是预期的那个NULL 表示没走索引
rows预估扫描行数接近结果行数远大于结果行数
Extra附加信息Using index（覆盖索引）Using filesort、Using temporary

type 从好到坏的完整顺序：system > const > eq_ref > ref > range > index > ALL。工程目标是至少到 range，全表扫（ALL）在大表上必须消灭。

三、索引为什么会失效

写法为什么失效怎么改
WHERE 中对列用函数YEAR(create_time)=2024 无法用索引定位改成范围：create_time >= '2024-01-01' AND < '2025-01-01'
隐式类型转换字符串列用数字查，会全表转换保持类型一致，加引号
LIKE '%abc'前缀通配符无法利用有序性改成 'abc%' 或用全文索引
OR 连接不同列优化器难以合并改成 UNION ALL，或分别建索引
违反最左前缀跳过联合索引的第一列调整查询条件或索引顺序
范围条件后的列范围之后的索引列不再生效把等值列放前面、范围列放最后
!= / NOT IN选择性差时走全表改写为 IN 或分批查
优化器判断全表更快返回行数占比高时回表不划算可接受，或加覆盖索引 / 强制索引

不要迷信「索引一定更快」

回表是有成本的：二级索引查出主键后还要再查一次聚簇索引。当查询结果占全表 20%~30% 以上时，优化器会认为直接全表扫更便宜 —— 这个判断通常是对的。

四、覆盖索引与回表

-- 索引 idx_age_name(age, name) -- 情况一：需要回表 SELECT * FROM user WHERE age = 20; -- 走 idx_age_name 拿到主键 id，再回聚簇索引取完整行 -- 情况二：覆盖索引，Extra 显示 Using index SELECT age, name FROM user WHERE age = 20; -- 索引里就有全部需要的列，不用回表，快很多 -- 情况三：即使 SELECT id 也是覆盖索引 SELECT id FROM user WHERE age = 20; -- 因为二级索引的叶子节点本来就带主键值

五、排序与分页的优化

问题现象解法
filesort 落盘Extra: Using filesort，排序数据量大让索引顺序与 ORDER BY 一致，或减小排序数据量
深分页LIMIT 100000, 20 极慢用上一页最大 id 做条件：WHERE id > last_id LIMIT 20
大分页计数COUNT(*) 慢用近似值、缓存计数、或单独维护计数表
SELECT * 拖慢多取了不需要的列，破坏覆盖索引只查需要的列

六、深入自检

rows 是准确值吗？是预估值，来自索引统计信息。统计信息过时会导致优化器选错索引，可以执行 ANALYZE TABLE 重新采样。
为什么有时候明明有索引却没用？三种常见原因：① 优化器认为全表更快（结果占比高）；② 索引列上做了运算或类型转换；③ 联合索引顺序不满足最左前缀。先看 rows 估算，再判断该不该干预。
FORCE INDEX 该用吗？谨慎。它相当于把优化器的判断写死在 SQL 里，数据分布变化后可能变慢。优先靠改写法和补索引解决，FORCE INDEX 作为兜底。
Using index 和 Using index condition 一样吗？不一样。Using index 是覆盖索引，不回表；Using index condition 是索引下推（ICP），在存储引擎层先过滤，减少回表次数，但仍会回表。
为什么加了索引写入变慢？每次 INSERT/UPDATE/DELETE 都要同步维护索引 B+ 树，索引越多维护成本越高。经验：单表索引控制在 5 个以内，联合索引优于多个单列索引。
EXPLAIN ANALYZE 有什么用？MySQL 8.0.18+ 支持，它会真正执行语句并给出实际行数与耗时，能看出预估与实际的偏差 —— 偏差大就说明统计信息不准。

慢查询的开启、阈值与分析流程

配置

-- 开启与配置（需要相应权限，8.0 可动态设置）
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;              -- 阈值，常用 0.5~2 秒
SET GLOBAL log_queries_not_using_indexes = ON;  -- 记录未走索引的（可能很吵，慎用）
SET GLOBAL min_examined_row_limit = 100;     -- 扫描行数少于此值不记
SHOW VARIABLES LIKE 'slow_query_log_file';

-- 分析工具
mysqldumpslow -s t -t 10 /var/log/mysql/slow.log        # 按总耗时排前 10
mysqldumpslow -s c -t 10 slow.log                        # 按出现次数
pt-query-digest slow.log > report.txt                    # 最详细，推荐
字段含义看什么
Query_time执行总耗时重点关注
Lock_time等待锁的时间大说明有锁竞争
Rows_sent返回行数和 Rows_examined 对比
Rows_examined扫描行数关键指标；扫描/返回比值大 = 索引差
  • 核心判据：Rows_examined / Rows_sent 的比值。扫描 10 万行只返回 10 行，说明索引没起作用，这是最该修的。
  • Lock_time 大：说明被别的锁堵住了，要去查 INNODB_TRX 找长事务。
  • 阈值别设太大：1 秒以上的慢查询往往已经造成用户可感知的卡顿；线上 OLTP 常设 0.5 秒甚至 0.1 秒。
  • 未走索引的日志要慎用：小表全表扫是正常的，开这个开关会被大量噪音淹没。
  • 慢日志有性能开销：高 QPS 下开启会损失几个百分点的吞吐，但通常值得。

优化清单与自检

  • 第一步永远是 EXPLAIN：看 type 是否为 ALL、key 是否为 NULL、rows 是否虚高。
  • 8.0 用 EXPLAIN ANALYZE：它给真实耗时与真实行数，能直接看出基数估计是否失准。
  • 统计信息陈旧：先 ANALYZE TABLE，很多「优化器选错索引」就解决了。
  • 加索引的三条原则：① 高频 WHERE/ORDER BY/GROUP BY 的列；② 区分度高的列在前；③ 尽量做成覆盖索引避免回表。
  • 联合索引注意最左前缀：(a,b,c) 能加速 a、a,b、a,b,c，但不能单独加速 b。
  • 深分页改键集分页：WHERE (score,id) < (?,?)，配合联合索引。
  • 大表改表走 OSC：gh-ost / pt-osc，直接 ALTER 会锁表。
  • 回表太多时：要么加覆盖索引，要么缩小查询列（别 SELECT *）。
  • 排序慢：看 Extra 是否有 Using filesort，尝试让排序走索引顺序。
  • 临时表慢：Using temporary 常见于 GROUP BY，考虑加索引或改写 SQL。
慢日志里有大量一样的 SQL，怎么优化？

优先做批量化：把 N 次单行查询改成一次 IN 或批量查询，往往比优化单条 SQL 收益大得多。

索引加了但优化器不用？

三种常见：区分度太低（优化器判断全表更划算）、统计信息不准、以及查询写法破坏了索引（函数包裹、隐式类型转换、左模糊）。

怎么判断该不该加索引？

看收益与代价：加速查询 vs 拖慢写入 + 占空间。写多读少的表要克制，每个索引都会让 INSERT/UPDATE 变慢。

慢查询排查的标准动作

慢查询排查不是「加个索引」就完事，而是有固定流程：先抓到慢 SQL，再定位是扫得多还是回表多还是排序多，最后才动手。

步骤做什么命令/工具
1. 抓开启慢日志，收集真实慢 SQLSET GLOBAL slow_query_log=ON; SET GLOBAL long_query_time=1;
2. 聚合按指纹聚合，找出 TOP N（而不是逐条看）mysqldumpslow -s t -t 10 slow.log；或 pt-query-digest
3. 看计划EXPLAIN 看访问类型和行数估计EXPLAIN FORMAT=JSON SELECT ...
4. 验证看真实开销而不是估计值EXPLAIN ANALYZE（MySQL 8.0.18+）
5. 改加索引 / 改写 SQL / 改表结构见下表
6. 复盘确认慢日志里该 SQL 消失隔天再看 pt-query-digest

Extra: Using where在存储引擎返回后再过滤配合 rows 大时说明索引没过滤干净

排查命令

-- 1. 开启慢日志（生产建议 long_query_time=0.5~1）
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;
SET GLOBAL log_queries_not_using_indexes = ON;   -- 可选：记录没走索引的
SHOW VARIABLES LIKE 'slow_query_log_file';

-- 2. 聚合分析（命令行）
mysqldumpslow -s t -t 10 /var/lib/mysql/slow.log       # 按总耗时 TOP10
mysqldumpslow -s c -t 10 /var/lib/mysql/slow.log       # 按出现次数 TOP10
pt-query-digest /var/lib/mysql/slow.log > report.txt   # 更详细，推荐

-- 3. 看执行计划
EXPLAIN SELECT * FROM orders WHERE user_id=1 AND status='paid';
EXPLAIN FORMAT=JSON SELECT ...;      -- 更详细，含 cost 估计
EXPLAIN ANALYZE SELECT ...;          -- MySQL 8.0.18+：真实执行时间！

-- 4. 实时看正在跑的慢查询
SELECT id, time, state, LEFT(info, 80) FROM information_schema.PROCESSLIST
WHERE command != 'Sleep' AND time > 2 ORDER BY time DESC;

-- 5. 统计信息更新（优化器选错索引时）
ANALYZE TABLE orders;
SHOW INDEX FROM orders;              -- 看 Cardinality（基数，越接近行数越好）
  • 先聚合再优化：一条慢 SQL 优化 100 倍，不如一条高频 SQL 优化 2 倍。永远从 pt-query-digest 的总耗时 TOP N 开始。
  • EXPLAIN 的 rows 是估计值：基于统计信息，可能严重不准。MySQL 8.0.18+ 用 EXPLAIN ANALYZE 能看到真实的行数和耗时，排查复杂 SQL 时务必用它。
  • 覆盖索引是最有效的手段之一：Using index 表示不用回表，能把随机 IO 变成顺序扫描，常常提速 5~10 倍。
  • 深分页要改写法：LIMIT 100000,20 要先扫 10 万行再扔掉。键集分页（记住上一页最后一条 id）能把延迟从秒级降到毫秒级。
  • 不要盲目加索引：每个索引都会让写入变慢、占用空间。先删掉重复和从未使用过的索引（sys.schema_unused_indexes 可以看）。
  • 区分「慢」的类型：并发慢（锁等待）和单条慢（扫得多）处理方式完全不同。看 PROCESSLIST 的 state 字段能区分。
为什么明明有索引，EXPLAIN 却显示全表扫描？

优化器是基于成本决定用不用索引的，不是「有就用」。当它估计用索引的回表成本高于全表扫描时就会放弃索引。最常见的触发条件：查询的行数占比太高（经验值 超过表总量的 20%~30%，回表的随机 IO 比顺序全扫还贵）。其他常见原因：① 索引列被函数/运算包裹（WHERE YEAR(date)=2024）；② 类型不匹配（字符串列用数字查，会隐式转换导致索引失效）；③ 统计信息过期，优化器估错了行数（ANALYZE TABLE 刷新）；④ 联合索引不满足最左前缀。排查顺序：先看 key 是不是 NULL、再看 rows 估计是否离谱、最后看 WHERE 条件写法。

加了索引还是慢，下一步查什么？

按这个顺序：① 看是不是回表太多——EXPLAIN 里 key 有值但 rows 很大，说明扫了索引还要回表几万次。解法是覆盖索引（把 SELECT 的列都放进索引）或缩小扫描范围；② 看 Extra 有没有 filesort/temporary——排序和临时表通常是真正的耗时大头，要靠索引的有序性消除（比如 ORDER BY 的字段正好是索引的一部分）；③ 用 EXPLAIN ANALYZE 看真实耗时分布——估计值会骗人，真实数据才知道时间花在哪；④ 看是不是锁等待——单条 SQL 很快但并发下慢，查 PROCESSLIST 和 innodb_lock_waits；⑤ 看是不是网络/结果集太大——返回几万行给客户端，慢的是传输不是查询。

long_query_time 设多少合适？

取决于业务对延迟的要求，没有通用值。经验起手式：① Web/API 服务：0.5~1 秒——用户对 >1s 有明显感知；② 内部系统/报表：2~5 秒；③ 调优攻坚期：临时设成 0.1 秒抓一周，能发现大量「单次不慢但高频」的问题 SQL，分析完再调回去。注意两个副作用：设太小会产生海量日志（磁盘和 IO 压力），建议配合 log_slow_rate_limit 或定期清理；另外记得开 log_queries_not_using_indexes 时要小心——它会记录所有未走索引的查询，包括那些扫描小表的正常查询，日志会爆炸。
