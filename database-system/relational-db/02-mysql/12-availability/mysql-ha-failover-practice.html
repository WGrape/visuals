MySQL高可用MGR故障切换
对照 MGR Orchestrator 校验
理论页画了 MGR / 主从 / MHA 的架构图。本页给运维动作：怎么切、怎么防脑裂、切完怎么校验。

01方案对照：MGR / 主从 / Orchestrator

方案切换方式脑裂风险适用
异步主从+VIP人工/脚本漂 VIP高（双写）读多写少、能容忍丢数据
半同步+VIP脚本检测切换中多数生产
MGR(单主)组内自动选主低（多数派）强一致首选
Orchestrator基于拓扑自动中低复杂拓扑、跨机房
要点：脑裂的本质是旧主没真死却继续写。所有防脑裂方案都靠 fencing：要么旧主被仲裁杀掉（STONITH），要么写被多数派拒绝（MGR）。

02MGR 故障切换与状态查看

MGR 单主模式下，主节点故障后组内自动选新主，应用通过读写分离中间件感知新主。

-- 查看组成员与角色
SELECT MEMBER_ID, MEMBER_HOST, MEMBER_ROLE, MEMBER_STATE
FROM performance_schema.replication_group_members;
-- 查看是否发生切换、当前主
SELECT * FROM performance_schema.replication_group_member_stats\G
-- 强制指定主（极低频，仅应急）
SELECT group_replication_set_as_primary('new_primary_uuid');
  • MEMBER_STATE 必须全是 ONLINE，否则集群不可用
  • 切换是秒级，但应用连接池要配置故障节点剔除 + 重连新主，否则连接池还指向旧主
  • MGR 要求每个事务的写集在多数派确认，网络分区时少数派自动只读，天然防脑裂

03Orchestrator / mysqlrpladmin 手动切换

基于拓扑的切换工具，适合还用传统主从、又想要自动化的场景。

# Orchestrator 手动/自动故障转移
orchestrator-client -c topology -i mydb-1   # 看复制拓扑
orchestrator-client -c failover -i mydb-1   # 对指定实例触发切换
orchestrator-client -c recover -i mydb-1    # 恢复（自动找新主）

# 官方 mysqlrpladmin（utilities 套件，已逐步淘汰）
mysqlrpladmin --slaves=slave1,slave2 --master=old-master \
  --new-master=candidate --rpl-user=repl:pass failover
要点：Orchestrator 的 recover 与 failover 区别：failover 是已知主挂了主动切；recover 是它自己探测后自动切。生产开 auto-recover + 告警。

04切后校验清单

  • 确认新主 READ_ONLY=OFF、旧主被置 READ_ONLY=ON（防双写）
  • 校验主从延迟 Seconds_Behind_Master / 延迟事务数接近 0
  • 应用写流量是否落到新主（看连接池路由、慢查询日志 host）
  • VIP / 域名 / 中间件配置是否已指向新主
  • 旧主恢复后先设为从库追平，再决定回归还是下线
问：半同步丢数据吗？

半同步要求至少一个从库收到 relay log 才提交，主宕机时若事务已发从库则安全；若主在收到 ACK 前宕机，事务在主上回滚、从库也没有，不会双写，但会存在主提交未达从的极小窗口，这是半同步与全同步的取舍。
