🧩 MongoDB 副本集与分片集群

副本集解决高可用，分片解决容量与吞吐——两套机制各自独立，又组合成 MongoDB 的水平扩展方案。

两个维度，各自解决不同问题

机制解决的问题本质
副本集 Replica Set高可用 + 数据冗余（主库挂了能自动切换）同一份数据复制多份
分片 Sharding容量 + 写吞吐（单机装不下/扛不住）不同数据分散到不同机器
记忆口诀：副本集是「复制」，分片是「拆分」。生产上的分片集群，每个分片本身就是一个副本集——既拆得开，又挂不了。

副本集：一主多从 + 自动选主

核心机制

  • oplog：主库上一个固定大小的循环集合（capped collection），记录所有写操作。从库异步拉取并重放。
  • 心跳与选主：节点每 2 秒互发心跳；主库失联超过 electionTimeoutMillis（默认 10000ms）触发选举，选出数据最新且优先级高的从库。
  • 多数派原则：写操作默认要 majority（超过半数节点）确认才返回成功，保证切换后不丢数据。

成员角色

角色能否被选为主作用
Primary—（就是主）接收所有写
Secondary✅复制数据，可承担读（需 readPreference）
Arbiter 仲裁者❌只投票不存数据，凑够奇数票（不推荐多用）
Hidden 隐藏❌用于备份/报表，不服务业务读
Delayed 延迟❌延迟 N 秒复制，用于误操作回滚
为什么副本数建议是奇数？因为选主要「超过半数」同意。3 节点允许 1 个挂；4 节点也只允许 1 个挂（需要 3 票，挂 2 个就选不出主了）——多花一台机器却没有换来更高的容错。所以推荐 3 / 5 / 7。

分片：按 shard key 拆数据

三个组件

组件职责要点
mongos路由层，接应用请求并转发无状态，可部署多个做负载均衡
Config Server存chunk 到分片的映射元数据本身也是副本集，挂了整个集群不可写
Shard真正存数据每个分片是一个副本集

Shard Key 怎么选（最重要）

Shard key 一旦选定几乎无法更改（4.4+ 支持 refine，5.0+ 支持 reshard，但代价很大）。它决定了三件事：数据能否均匀分布、查询能否定向到单个分片、能否支持高效范围查询。

类型做法优点缺点
范围分片按 key 的值域切 chunk✅ 范围查询快（可定位到少数分片）❌ 容易热点（如按时间分片，写入全落最新分片）
哈希分片对 key 做 hash 后分布✅ 分布极均匀，写入无热点❌ 范围查询要广播到所有分片（scatter-gather）
复合 / _zone组合字段或按区域打标签兼顾两者设计复杂
选 key 的三条经验：① 基数要高（低基数字段如「性别」会让数据只落在少数 chunk，且 chunk 不可再分 → 变成 jumbo chunk）；② 分布要均匀（避免单调递增的时间戳/user_id 做范围分片）；③ 要匹配查询模式（让大部分查询能带上 shard key，从而定向到单个分片，避免全分片广播）。
最常见的错误：用单调递增的 _id 或时间戳做范围分片。结果所有新写入都落到最后一个 chunk → 最后一台分片，写压力完全无法分摊，集群退化成单机。这种情况应改用哈希分片，或用「随机前缀 + 时间」的复合 key。

Chunk 与自动均衡

  • 数据按 shard key 切成 chunk（默认 64MB，可配置）。
  • Balancer 后台进程监控各分片的 chunk 数，差值超过阈值就自动迁移 chunk，保持均衡。
  • 迁移是在线的（先复制再切换路由），但对集群有额外负载，可通过 balancer window 限定只在业务低峰运行。

读写路由：定向 vs 广播

查询是否带 shard key行为性能
✅ 带完整 shard key定向查询（targeted），mongos 直接打到目标分片快
❌ 不带 shard key广播查询（scatter-gather），发给所有分片再合并慢，分片越多越慢
分片集群的性能红线：避免不带 shard key 的查询。分片数越多，广播查询的放大越严重（20 个分片就是 20 倍放大）。同理，不带 shard key 的排序 + 分页（skip/limit）代价极高——要在所有分片各自排序再归并。

什么时候该分片

  • ✅ 单机磁盘容量不够；
  • ✅ 写吞吐超过单机上限；
  • ✅ 单机的内存装不下热数据索引，导致大量磁盘随机读。
不要过早分片。分片会显著增加运维复杂度、限制查询灵活性、改变事务行为。如果单机副本集就能扛住，先纵向扩容 + 优化索引和 schema。

🎯 面试问答

Q：副本集和分片分别解决什么问题？
A：副本集解决高可用——同一份数据复制多份，主库挂了自动选新主；分片解决容量与吞吐——把不同数据分散到不同机器。两者正交：生产分片集群里，每个分片本身就是一个副本集，既拆得开又挂不了。
Q：副本集的节点数为什么建议奇数？
A：因为选主要「超过半数」同意。3 节点允许 1 个挂（还剩 2 个 > 1.5）；4 节点也只允许 1 个挂（需要 3 票，挂 2 个就选不出主了）。也就是说 4 节点比 3 节点多花一台机器，却没有换来更高的容错能力。所以推荐 3 / 5 / 7。如果确实只有 2 台数据节点，可以加一个不存数据的 Arbiter 凑票数，但不推荐作为常规方案。
Q：oplog 是什么？大小怎么定？
A：oplog 是主库上一个固定大小的循环集合（capped collection），记录所有写操作；从库异步拉取并重放来保持同步。它循环覆盖——写满后覆盖最老的记录。大小决定了「从库最多能落后多久」：如果从库停机时间超过 oplog 能覆盖的时间窗口，oplog 里最早的记录已被覆盖，从库就无法追平，只能做全量初始同步。所以运维上要给 oplog 预留足够容量（常见做法是覆盖 24~72 小时的写入量），并在计划内停机后尽快恢复。
Q：Shard key 应该怎么选？
A：三条标准：① 基数要高——低基数字段（如性别）会让数据只落在少数 chunk，且这种 chunk 无法再拆分，会变成 jumbo chunk；② 分布要均匀——避免用单调递增的时间戳或 _id 做范围分片，否则所有新写入都落到最后一个 chunk → 最后一台分片，写压力完全无法分摊；③ 匹配查询模式——让大部分查询能带上 shard key，从而定向到单个分片，避免全分片广播。写入热点明显时用哈希分片换取均匀分布。
Q：为什么不建议用自增 _id 或时间做 shard key？
A：如果用它们做范围分片，新数据的值总是最大的，会全部落到最后一个 chunk，也就是最后一台分片上。结果是：写入压力完全集中在一台机器，集群的写扩展能力退化成单机，而且 Balancer 会不停迁移这个持续增大的 chunk。解决办法：改用哈希分片（分布均匀但范围查询要广播），或用「随机前缀 / 高位哈希 + 时间」的复合 key 兼顾两者。
Q：mongos 和 config server 挂了会怎样？
A：mongos 无状态，挂一个不影响集群，生产通常部署多个做负载均衡（应用可以连多个 mongos）。但 config server 是关键的——它存着「chunk 到分片」的映射元数据，它不可用时集群无法做 chunk 迁移和路由刷新，会直接影响写入。所以 config server 必须本身是副本集（通常 3 节点），并且要重点监控。
Q：分片集群里不带 shard key 的查询会怎样？
A：会变成广播查询（scatter-gather）——mongos 把请求发给所有分片，各自执行后汇总结果。分片越多放大越严重（20 个分片就是 20 倍放大），而且不带 shard key 的排序 + skip/limit 分页代价尤其高（每个分片都要排一次再归并）。这是分片集群最主要的性能陷阱，设计 schema 时应确保核心查询都能带上 shard key。
