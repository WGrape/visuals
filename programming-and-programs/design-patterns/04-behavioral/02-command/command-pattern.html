🎮 命令

把一次操作包装成对象，方便排队、记录和撤销。

一句话记住遥控器按钮只知道“执行命令”，不关心灯或空调怎样工作。
问题从哪来图解协作动手试一试伪代码选型与边界
01 · 从问题出发

为什么会需要这个模式？

编辑器按钮直接操作文档，若要支持撤销、快捷键和操作历史，每个入口都需重复逻辑。

编辑器有工具栏按钮、快捷键、菜单入口都要执行“插入文本”。若三个入口直接改文档，后来要加撤销和操作历史，就要分别改三个入口，还可能行为不一致。

😵 直接写会怎样

button.onClick = () => doc.insert(cursor, text)
shortcut.onPress = () => doc.insert(cursor, text)
menu.onSelect = () => doc.insert(cursor, text)

💡 关键转折

命令对象保存接收者与参数，提供 execute；需要撤销时再定义 undo。

把“做什么”和“由谁触发”分开：触发器只持有 Command，命令保存执行所需的接收者与参数。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

class InsertTextCommand {
  constructor(doc, pos, text) {
    this.doc = doc; this.pos = pos; this.text = text
  }
  execute() { this.doc.insert(this.pos, this.text) }
  undo() { this.doc.delete(this.pos, this.text.length) }
}
cmd = new InsertTextCommand(doc, cursor, "Hello")
cmd.execute()
history.push(cmd)
// history.pop().undo()

读代码时抓住三件事

  1. Command 保存接收者与参数，所以稍后仍能执行。
  2. execute 只表达一次操作，不依赖按钮来源。
  3. undo 不等于自动回滚，必须设计对应逆操作和状态快照。

换个业务场景，还能认出来吗？

任务队列可把发送邮件命令排队执行；但队列化命令要考虑序列化、重试和幂等，不要把持有内存对象的命令原样跨进程发送。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

操作需要排队、记录、重放、撤销或被多种入口触发

三个具体场景

  • 编辑器插入文本后撤销
  • 菜单和快捷键执行同一操作
  • 任务队列保存待执行任务

不适合或要小心

撤销需要保存足够的前置状态；并非每种操作都能简单逆转，例如外部付款要用补偿操作。

外部副作用不一定可逆；撤销需保存足够状态或定义补偿

最容易混淆的相邻模式

模式真正的区别
备忘录保存状态快照供恢复；命令保存操作及可选逆操作。
策略选择一种算法完成当前任务；命令描述一次具体请求，可排队、记录、撤销。

区分时问自己：要保存“一次操作”，还是保存“某一刻的状态”？

落地前检查

  • 测试多个触发器执行同一个命令结果一致。
  • 撤销删除类命令前保存原数据。
  • 对支付等不可逆副作用使用补偿动作并处理重复执行。
06 · 自己说一遍

两道检验理解的小题

撤销删除文本时为什么要保存原文？

没有原文就无法恢复被删除的内容。

为什么付款命令的 undo 不能简单执行“负数付款”？

真实付款已产生外部副作用；撤销通常是退款等新的业务操作，必须考虑失败和幂等。

核心速览

一句话把一个请求封装成对象，从而支持排队、撤销、重做、日志
核心价值把「发起请求」和「执行请求」解耦，请求变成了可传递的数据
必备三件套Command 接口（Execute/Undo）、Invoker 调用者、Receiver 执行者
典型用途撤销重做、任务队列、宏命令、事务回滚、RPC 请求对象
命令模式：请求变成对象，于是可以被存储、排队和撤销

一、最小骨架

type Command interface { Execute() error Undo() error } // 具体命令：持有接收者与执行所需的全部参数 type SetTextCmd struct { editor *Editor old string new string } func (c *SetTextCmd) Execute() error { c.old = c.editor.Text // 先存下旧值，Undo 要用 c.editor.Text = c.new return nil } func (c *SetTextCmd) Undo() error { c.editor.Text = c.old return nil } // 调用者：只管触发与记录 type History struct{ done, undone []Command } func (h *History) Run(c Command) error { if err := c.Execute(); err != nil { return err } h.done = append(h.done, c) h.undone = nil // 新操作会清空重做栈 return nil } func (h *History) Undo() error { if len(h.done) == 0 { return nil } c := h.done[len(h.done)-1] h.done = h.done[:len(h.done)-1] if err := c.Undo(); err != nil { return err } h.undone = append(h.undone, c) return nil }
Undo 的实现有两条路

① 存快照：Execute 时保存旧状态，Undo 直接还原（简单，适合状态小的场景）；② 反向操作：为每一步操作写对应的逆操作（省内存，但要保证逆操作正确）。内存敏感或状态很大时用第二种。

二、命令模式带来的四种能力

能力怎么做例子
撤销/重做命令对象保存状态，维护 done / undone 两个栈编辑器、绘图工具
任务队列命令放进队列，工作线程逐个 Execute线程池、异步任务
延迟执行命令先存起来，满足条件再执行定时提醒、批处理
日志与恢复把所有命令序列化落盘，崩溃后重放WAL、事件溯源
宏命令一个命令内部持有命令列表一键执行多步操作

三、和它相近的模式

模式关注和命令的区别
命令把请求对象化请求可以被存储、撤销、排队
策略替换算法策略是「怎么做」，命令是「做什么」
观察者状态变化时通知观察者是被动触发，命令是主动执行
责任链沿链传递请求责任链不关心撤销，也不保存状态
备忘录保存与恢复对象状态备忘录只存状态，命令存的是「操作」

四、真实场景

文本编辑器每一次编辑是一个命令，Ctrl+Z 逐个 Undo
数据库事务每个操作可回滚，整体提交或回滚
消息队列消息就是命令对象，异步执行、可重试
遥控器/按钮按钮只知道触发命令，不知道控制什么设备
WAL 与事件溯源把命令序列化落盘，可回放重建状态
任务编排多个命令组合成一个宏命令，支持整体回滚

五、深入自检

每个操作都要写一个命令类，会不会太重？

Go 里可以用函数类型简化：type Command func() error，撤销则用一对函数 {Do, Undo func() error}。只有需要序列化、日志、复杂状态时，才值得定义完整的命令结构体。

Undo 一定会成功吗？

不一定。外部世界的操作不可逆（发邮件、扣款）。设计时要区分：内存状态可撤销，外部副作用不可撤销。后者要用「补偿操作」而不是 Undo。

命令模式和事件溯源是什么关系？

事件溯源是命令模式在架构层面的延伸：把每个命令（或命令产生的事件）持久化，系统状态 = 初始状态 + 所有事件重放。区别在于事件是「已发生的事实」，命令是「待执行的意图」。

命令对象要多大？

刚好够 Execute 用。不要塞进过多上下文，否则难以序列化、难以测试。需要共享的上下文通过 Execute(ctx) 传入。

并发下撤销怎么保证正确？

需要对同一个对象的命令串行执行，或者给命令加版本号（乐观锁）：执行命令时检查版本号是否仍匹配，不匹配则拒绝执行并提示用户。

记住一句请求变成对象，于是可存储、可撤销
Undo 两法存快照 / 写逆操作
Go 简化函数类型或 Do/Undo 函数对
不可逆操作用补偿而不是 Undo
