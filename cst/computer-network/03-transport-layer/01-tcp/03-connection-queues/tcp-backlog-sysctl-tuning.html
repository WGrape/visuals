上一页讲了半连接队列、全连接队列和 backlog 在握手里的位置。这一页把它落成可执行的调优：三个内核参数、怎么观测溢出、以及 SYN Flood 的防御清单。

01三个关键参数

参数默认值（典型）控制什么
net.core.somaxconn128全连接队列（accept 队列）上限，很多发行版偏小
net.ipv4.tcp_max_syn_backlog1024半连接队列上限，SYN Flood 时首先被打满
net.ipv4.tcp_syncookies1（开）队列满时回 SYN Cookie，不占内存建半连接
要点：隐藏坑：应用层 listen(backlog) 的实际生效值是 min(应用 backlog, somaxconn)。Nginx/Go 配了 1024 但 somaxconn 还是 128，队列照样只有 128。

02怎么观测队列溢出

用 ss 看监听套接字的 Recv-Q（全连接队列当前长度）和 Send-Q（队列上限），再用内核计数确认是否发生过溢出。

ss -lnt 'sport = :80'
# Recv-Q 持续贴近 Send-Q  -> 全连接队列满

# 半连接队列溢出计数（SYN 被丢）
netstat -s | grep 'SYNs to listened'
# 或
nstat -az TcpExtListenOverflows TcpExtListenDrops

03SYN Flood 防御清单

  • 开 SYN Cookie：net.ipv4.tcp_syncookies=1，队列满也能验证握手，不建半连接。
  • 调大半连接/全连接队列：tcp_max_syn_backlog 与 somaxconn 一起调，且应用 listen backlog 不低于 somaxconn。
  • 限速与过滤：边缘对单一源 IP 的新建连接限速；云厂商开 DDoS/CC 防护。
  • 应用层兜底：对新建连接做令牌桶限流、要求廉价校验（如 TLS 之前先过 CDN）。

04应用层怎么配合

# Nginx：listen 显式给 backlog
listen 80 default_server backlog=1024;

# Go http.Server：新建连接超时
# http.Server{ ReadTimeout: 5*time.Second,
#             ReadHeaderTimeout: 2*time.Second }

# 系统级生效
sysctl -w net.core.somaxconn=4096
 sysctl -w net.ipv4.tcp_max_syn_backlog=8192
问：为什么调了 somaxconn 还是排队？

因为还要看应用 listen 的 backlog 和它取 min；另外全连接队列满时，内核会直接丢弃新来的 ACK，客户端表现为连接超时而非拒绝，排障时要同时看 Recv-Q 和 ListenOverflows。

第一层 · 概念与判定：backlog 管的是哪两段队列

TCP 建连有两个队列：半连接队列（SYN 收到、未完成三次握手）和全连接队列（握手完成、等 accept 取走）。backlog 调优本质是防止高并发连接暴增时这两个队列溢出丢连接。

队列存放溢出后果
半连接 SYN 队列已收 SYN、未 ACK新连接 SYN 被丢/超时
全连接 accept 队列已建连、等 accept完成握手的连接被拒
应用 accept 慢队列堆积Overflow 计数涨

第二层 · 参数·命令·量化：内核参数与观测

参数默认作用
net.core.somaxconn128（部分 4096）全连接队列上限
net.ipv4.tcp_max_syn_backlog1024半连接队列上限
listen(fd, backlog)应用传值实际取 min(backlog, somaxconn)
syn cookies队列满时启用防 SYN flood 但丢选项

TCP backlog 调参与溢出观测

# 调大两个队列
sysctl -w net.core.somaxconn=4096
sysctl -w net.ipv4.tcp_max_syn_backlog=8192

# 看队列是否溢出（Recv-Q 长期贴着 Send-Q 即溢出）
ss -lntp
# 输出: State  Recv-Q Send-Q  Local Address:Port
#        LISTEN 200    4096    0.0.0.0:8080
#        ↑当前全连接等待数   ↑accept 队列上限(min(backlog,somaxconn))

# 溢出计数
nstat -az TcpExtListenOverflows TcpExtListenDrops

数量级：默认 somaxconn=128 很小，秒级上千新建连接时极易溢出；实际 accept 队列长度 = min(应用 backlog, somaxconn)，两者任一偏小都成瓶颈。

第三层 · 排障与边界：四个坑

  • 应用 backlog 被 somaxconn 盖住：代码写 listen(sfd, 1024) 但 somaxconn=128，实际队列只有 128——取 min 是铁律
  • 只调 somaxconn 不调 syn 队列：SYN flood 或瞬时暴增时半连接队列满，连接卡在握手前
  • accept 线程太慢：队列上限调得再大，消费慢照样堆积溢出，根因在应用吞吐
  • 容器/网络命名空间独立：sysctl 要在对应 netns 里设，宿主机调了容器不生效

第四层 · 原理与取舍

为什么实际 accept 队列是 min(backlog, somaxconn)？

因为 backlog 是应用向内核申请的期望值，而 somaxconn 是内核允许的上限，内核取两者较小值落地。所以任一方偏小都会成为天花板——常见错误是代码写了大 backlog，却忘了系统 somaxconn 默认只有 128。调优必须两者一起看。

半连接队列满了怎么办，syn cookie 是免费午餐吗？

满了会开启 syn cookie：不在内存里存半连接状态，而是把连接信息编码进 SYN+ACK 的序列号，等客户端 ACK 时解码还原。好处是扛住 SYN flood 不耗内存；代价是握手期间无法携带 TCP 选项（如窗口缩放、SACK），可能影响后续吞吐。所以优先把 tcp_max_syn_backlog 调大，cookie 是兜底而非首选。

全连接队列溢出为什么比想象中隐蔽？

溢出时内核直接丢弃完成三次握手的连接或回 RST，客户端表现为『连上了又被秒断』或『偶发连接失败』，服务端日志往往没报错，只悄悄累加 ListenOverflows/ListenDrops 计数。排查高并发连接失败，第一反应就该 ss -lntp 看 Recv-Q 是否贴着 Send-Q、再查 nstat 溢出计数。
