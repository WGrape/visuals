①三种 key 模型决定能表达什么

Doris / StarRocks 建表时必须选一种 key 模型，它决定了主键相同的两行怎么处理。 这是与 MySQL 最大的思维差异：这里的表更像「按 key 组织的物化结果」，不是逐行记录。

模型重复 key 的处理适用注意
Duplicate（明细）都保留日志、流水、需要保留每条原始记录最贴近传统表，存储最大
Aggregate（聚合）按指标列的聚合函数合并（SUM / REPLACE / MAX / MIN 等）本来就是统计结果的宽表查询时自动聚合，但导入阶段就已合并，原始明细不可恢复
Unique（主键）保留最新一条（按导入顺序）需要 Upsert 语义的维表、状态表本质是 REPLACE 聚合的特化；写入有去重开销
-- Aggregate 模型：key 列 + 带聚合类型的指标列
CREATE TABLE daily_sales (
  dt        DATE,
  shop_id   BIGINT,
  amount    DECIMAL(18,2) SUM,        -- 同 key 的行累加
  order_cnt BIGINT        SUM,
  status    VARCHAR(20)   REPLACE     -- 同 key 的行取最后一次
) AGGREGATE KEY(dt, shop_id)
DISTRIBUTED BY HASH(shop_id) BUCKETS 8;

-- Unique 模型：按主键保留最新
CREATE TABLE user_dim (
  user_id  BIGINT,
  name     VARCHAR(50),
  city     VARCHAR(50)
) UNIQUE KEY(user_id)
DISTRIBUTED BY HASH(user_id) BUCKETS 8;
选错的代价很高：建表后 key 模型不能改，只能新建表再导数据。 判断口径：需要原始明细 → Duplicate；查询永远是聚合结果 → Aggregate；需要更新覆盖 → Unique。 拿不准时先用 Duplicate，存储比返工便宜。

②分区与分桶

分区（Partition）

通常按时间做范围分区。作用：① 查询按时间裁剪直接跳过整个分区； ② 历史数据可整体删除/替换；③ 冷热分层存储的基础。

分桶（Bucket / Tablet）

分区内再按哈希分桶，决定数据在各节点间的分布与并行度。 桶数太少 → 并行度不够；太多 → 元数据膨胀、小文件多。

分桶列怎么选

选高基数且常用于 JOIN / 聚合分组的列（如 user_id、shop_id）。 直接决定能否用上 Colocate Join 与本地聚合。

桶数的经验值

通常按「单桶压缩后几百 MB ~ 1GB 量级」估，且不超过集群磁盘数的若干倍。 具体建议请以所用版本官方文档为准——不同版本对 tablet 数量的容忍度不同。

最容易犯的错：分桶列基数太低。用 status（只有几个取值）做分桶列， 数据会严重倾斜到少数几个桶里，查询并行度退化成 1，还造成热点。 另一个常见错是分桶列与 JOIN 键不一致，导致每次 JOIN 都要跨节点重分布数据。

③物化视图与 Rollup：预聚合的正确用法

物化视图把「按某组维度预聚合的结果」物理存下来，查询时自动命中，不必重扫明细。 关键限制是聚合必须与物化视图的定义匹配，否则不会命中。

查询物化视图定义能否命中
SELECT dt, SUM(amount) GROUP BY dtGROUP BY dt✓
SELECT dt, shop_id, SUM(amount) GROUP BY dt, shop_idGROUP BY dt✗ 维度更细，无法从粗结果还原
SELECT dt, SUM(amount) GROUP BY dtGROUP BY dt, shop_id✓ 可从细结果再聚合（上卷，多数实现支持）
SELECT dt, COUNT(DISTINCT uid)SUM(amount) GROUP BY dt✗ 聚合函数不匹配
设计原则：物化视图按「最细的常用维度」建，让更粗的查询能上卷复用。 不要为每种查询组合各建一个——每多一个物化视图，就多一份写入放大和存储。 一般先按实际的慢查询 Top N 建 2~5 个，再看效果。
COUNT(DISTINCT) 是预聚合的难点。去重视图无法直接上卷 （两个分组的基数不能相加）。解决方案通常是用位图（bitmap）类型存中间状态， 查询时再求并集计数。具体支持的函数与类型请以所用版本文档为准。

④建表自检清单

  1. key 模型：需要明细吗？需要更新吗？选错不可改。
  2. 分区键：查询是否总带时间条件？没有时间过滤的查询会扫全部分区。
  3. 分桶列：基数够高吗？与高频 JOIN / GROUP BY 的列一致吗？
  4. 字段类型：能用定长/小类型就不要用大类型；字符串维度考虑用低基数优化。 改列类型的代价与 MySQL 一样大。
  5. 索引：列存的点查依赖稀疏索引 + zonemap/min-max 跳过， 等值高频维度放前面。详见本学科「数据跳过」章节。
  6. 导入方式：实时流（Routine Load）还是批量（Broker Load / INSERT INTO SELECT）？见下一篇。
Q：Doris 和 StarRocks 差别大吗？
A：同源（StarRocks 从 Doris 分叉），核心概念、key 模型、SQL 语法高度相似， 本页讲的模型与建表思路两边通用。差异在执行引擎细节、优化器能力、生态集成与版本节奏上， 且在持续变化。选型请以当前版本的官方能力与 POC 实测为准。
Q：Unique 模型能当 OLTP 库用吗？
A：不能。它是批量导入 + 覆盖合并的语义，不是逐行事务。 单行高频更新、需要事务隔离、需要低延迟点查 → 那是 OLTP 库的职责。 把 OLAP 当 OLTP 用是常见的架构错配。

Doris/StarRocks 三种数据模型

模型特点适用 / 限制
Duplicate（明细）不聚合，原样存储所有行日志、明细查询；无主键去重，存储最大
Aggregate（聚合）按 key 预聚合，value 用 SUM/REPLACE/MAX 等报表、指标；查询时再聚合一次，且只能查聚合列
Unique（主键）按主键保留最新（本质是 REPLACE 聚合）需要 update 的维表；查询有 merge 开销
Primary Key（StarRocks 3.x）真正的行级更新 + 主键索引需要频繁 update/delete；内存存主键索引（约 10B/行）
参数默认值 / 建议说明
replication_num3副本数；单机测试设 1
分桶数 BUCKETS建议 每分区 10~30分桶数 ≈ 数据行数 / (压缩后单桶 1~10GB)
分区粒度按天/月时序数据必分区，便于 TTL 与裁剪
storage_formatV2支持 Bitmap/HLL 等新类型
enable_light_schema_changetrue3.x 起加列是秒级
单表分区数建议< 1000太多元数据压力大
compaction自动Accumulative + Base compaction；写入频繁时要监控堆积

分桶数怎么定：目标是每个 tablet（分桶）压缩后 1~10 GB。例如一天 300GB 原始数据、压缩比 5:1 = 60GB，则分桶数 = 60 / 5 ≈ 12。分桶太少并行度不够，太多元数据膨胀、导入变慢。

建表与导入

-- Aggregate 模型：按 dt/site 预聚合 pv，UV 用 HLL 近似去重
CREATE TABLE site_pv (
    dt       DATE,
    site_id  INT,
    pv       BIGINT SUM DEFAULT '0',      -- SUM 聚合
    uv       HLL HLL_UNION,               -- 近似去重，误差约 1~2%
    max_rt   INT MAX                      -- 取最大值
) AGGREGATE KEY(dt, site_id)
PARTITION BY RANGE(dt) (
    PARTITION p202610 VALUES [('2026-10-01'), ('2026-11-01'))
)
DISTRIBUTED BY HASH(site_id) BUCKETS 12
PROPERTIES ("replication_num" = "3");

-- Unique 模型：维表，需要更新
CREATE TABLE dim_user (
    user_id   BIGINT,
    name      VARCHAR(64),
    city      VARCHAR(32),
    updated_at DATETIME
) UNIQUE KEY(user_id)
DISTRIBUTED BY HASH(user_id) BUCKETS 10
PROPERTIES ("replication_num" = "3", "enable_unique_key_merge_on_write" = "true");
-- merge_on_write=true（2.0+）可让 Unique 表的查询不走 merge，性能接近 Duplicate
-- 导入方式
-- 1) Stream Load（HTTP，最常用，同步返回）
curl -X PUT http://fe:8030/api/db/tbl/_stream_load \
  -H "label:load_20261022" -H "column_separator:," \
  -T data.csv
-- 返回记好 Label，可用于幂等重投（相同 Label 会去重）

-- 2) Routine Load（持续消费 Kafka）
CREATE ROUTINE LOAD db.job ON tbl
COLUMNS(dt, site_id, pv)
PROPERTIES ("desired_concurrent_number"="3", "max_batch_interval"="20")
FROM KAFKA ("kafka_broker_list"="broker:9092", "kafka_topic"="topic",
            "property.group.id"="g1", "property.kafka_default_offsets"="OFFSET_BEGINNING");

-- 3) Broker Load（从 HDFS/S3 大批量）
LOAD LABEL db.l1 (DATA INFILE("hdfs://path/*") INTO TABLE tbl)
WITH BROKER broker_name;

-- 查看导入状态
SHOW LOAD WHERE LABEL = "load_20261022";

排障清单

症状原因处理
Aggregate 模型查明细查不到数据已被预聚合，明细行不存在需要明细就用 Duplicate 模型；或保留两份表
聚合结果看着不对查询时又聚合了一次（二次聚合）理解：存储时聚合 + 查询时再聚合；COUNT 要用 SUM 而不是 COUNT(*)
导入报 too many filtered rows数据格式/类型不匹配看 SHOW LOAD 的 ErrorLogUrls；设 max_filter_ratio
查询慢没命中分区/分桶裁剪；或分桶数不合理看 EXPLAIN 是否裁剪；调整分桶列（选高基数、常用于 join/过滤的列）
Unique 表查询慢查询时要 merge 多版本开 enable_unique_key_merge_on_write；或升级到 Primary Key 模型
Compaction 堆积写入频率高、版本多看 SHOW PROC '/compaction'；增加 compaction 线程；降低小批量写入频率
小文件多导入慢每次导入生成一个版本攒批写入（单次 ≥ 1万行，间隔 ≥ 10s）

Aggregate 模型最常见的坑：建表时 COUNT 类型的指标要写成 BIGINT SUM，查询时用 SUM(cnt)，用 COUNT(*) 会得到行数而不是总和。
