部署形态、备份恢复、监控指标、性能调优与常见故障处置

部署形态

形态角色说明
单实例一个进程搞定Community / Enterprise 都行；无 HA
因果集群Core Server + Read Replica生产标准形态
Core Server参与 Raft 共识，可写可读通常 3 或 5 台（奇数，容忍 1 或 2 台故障）
Read Replica异步追赶，只读横向扩展读能力，不参与选主，可任意数量
AuraDB官方托管免运维，按需付费

关键配置

# conf/neo4j.conf 常用项
server.memory.heap.initial_size=8G        # 堆初始
server.memory.heap.max_size=8G            # 堆上限（建议相同，避免动态扩容抖动）
server.memory.pagecache.size=16G          # 页面缓存（越大越好，通常 = 数据文件总大小）
server.default_database=neo4j
server.bolt.enabled=true
server.bolt.listen_address=:7687
server.http.enabled=true

# 集群
initial.dbms.default_primaries_count=3    # Core 数
initial.dbms.default_secondaries_count=2  # Read Replica 数
dbms.cluster.discovery.initial_members=core1:5000,core2:5000,core3:5000

# 事务
db.transaction.timeout=60s
dbms.memory.transaction.max_size=2G
💡 内存三块怎么分：堆(heap) 管查询执行与事务；页面缓存(pagecache) 管图数据在内存中的缓存（最关键，应尽量大）；剩下留给 OS。经验：pagecache ≈ 图数据文件大小，heap 8~16G，两者之和不超过物理内存的 80%。

# 在线备份（可从任一 Core 或 Read Replica 执行）
neo4j-admin database backup neo4j --to-path=/backup/neo4j --type=FULL
neo4j-admin database backup neo4j --to-path=/backup/neo4j --type=DIFF

# 恢复（需先停库）
neo4j-admin database restore --from-path=/backup/neo4j/neo4j-2026-01-01 neo4j

# 一致性检查
neo4j-admin database check neo4j
⚠️ Community Edition 不支持在线热备份，只能停库做 dump。生产环境若要求不停机备份，必须用 Enterprise 或 AuraDB。

常见故障与处置

🐢 查询突然变慢

  • 先看是不是新上线的查询：PROFILE 找全表扫描
  • 起点属性没建索引 → 建索引/约束
  • 可变长路径没限深度 → 加上限
  • 页面缓存命中率掉到 95% 以下 → 扩容 pagecache

💥 OOM / 堆溢出

  • 单个大事务（一次改几十万节点）→ 分批提交
  • 可变长路径爆炸 → 限深度 + 加 LIMIT
  • 笛卡尔积（多个 MATCH 无关联）→ 补上关联条件
  • RETURN 了大量路径对象 → 只返回需要的属性

📈 事务日志撑爆磁盘

  • 根因：长事务阻止日志裁剪
  • dbms.listTransactions() 找老事务并 kill
  • 离线导入任务忘记关闭会一直挂着

⚠️ Leader 频繁切换

  • 检查 Core 之间的网络延迟与抖动
  • 检查磁盘 IO 是否饱和（Raft 心跳超时）
  • 调整 raft 选举超时参数

性能调优清单

  • ✓ 给所有 MATCH 起点建索引/约束（最主要的一条）
  • ✓ pagecache 调到能装下整个图数据文件
  • ✓ 可变长路径一律带上限（*1..3）
  • ✓ 查询参数化，命中计划缓存
  • ✓ 大批量写用 CALL {} IN TRANSACTIONS 分批提交
  • ✓ 避免在大图上做无起点的全图遍历
  • ✓ 大属性（长文本）拆出去存，图上只留 id
  • ✓ 定期 neo4j-admin database check 检查一致性
  • ✓ 图建模时关系类型要细分（:WORKS_AT 比 :RELATED_TO 高效得多）
💡 建模层面的性能杠杆最大：把泛化的 :RELATED 拆成具体的 :KNOWS / :WORKS_AT / :LIVES_IN，遍历时就能按类型精准过滤，往往比调任何参数都有效。

🎯 常见问法与答题要点

Q：Neo4j 集群最少几台 Core？为什么？

A：通常 3 台或 5 台，必须是奇数。Core 之间用 Raft 共识，写入需要多数派确认：3 台允许 1 台故障（还剩 2 台构成多数），5 台允许 2 台故障。偶数台没有好处——4 台也只能容忍 1 台故障（多数派是 3），却多花一台机器。Read Replica 不参与共识，数量随意。

Q：Core 和 Read Replica 有什么区别？

A：Core 参与 Raft 共识、可读可写、有完整数据副本，数量有限（3~5）；Read Replica 异步从 Core 拉取事务日志追赶数据，只读、不参与选主、数量可任意扩展。Read Replica 的作用是横向扩展读能力，代价是数据可能略滞后（异步复制）。

Q：页面缓存（pagecache）设多大？

A：理想是能装下整个图数据文件，这样几乎所有遍历都在内存里完成。实践：先 du -sh data/databases/* 看数据文件大小，把 pagecache 设到接近它；再给 8~16G 堆；两者之和不超过物理内存的 80%（留一部分给 OS 文件缓存）。判断够不够看 page_cache_hit_ratio，低于 95% 就该加大。

Q：为什么事务日志会撑爆磁盘？

A：Neo4j 的事务日志只有在「没有更老的事务需要它」时才能裁剪。如果有一个长时间不提交的事务（比如一个跑了几小时的批量导入，或应用泄漏了未提交的事务），日志就要一直保留到它结束，磁盘会持续增长。排查用 CALL dbms.listTransactions() 找 elapsed 很大的事务，用 dbms.killTransaction() 杀掉。

Q：Community 版能用于生产吗？

A：能跑，但缺关键能力：没有在线热备份（只能停库 dump）、没有集群（无法 HA 与读扩展）、没有细粒度权限与运维监控工具。如果对可用性有要求，必须用 Enterprise；如果只是内部小系统且能接受停机备份，Community 也可以。

Q：查询突然 OOM 怎么排查？

A：四个常见原因：①可变长路径没限深度——路径数指数爆炸，最常见；②笛卡尔积——多个 MATCH 之间没关联条件，行数相乘；③单事务处理量太大——一次改几十万节点，改成 CALL {} IN TRANSACTIONS 分批；④RETURN 了完整路径对象——改成只返回需要的属性。用 PROFILE 看哪一步 Rows 突然放大，一眼就能定位。

Q：备份能不停机吗？

A：Enterprise 可以：neo4j-admin database backup 是在线热备份，支持 FULL / DIFF 增量，通常从 Read Replica 上做以完全不影响 Core。Community 不支持，只能停库后用 neo4j-admin database dump。这是选 Enterprise 最常见的理由之一。

Q：怎么判断图建模是否合理？

A：三个信号：①关系类型是否够具体——全是 :RELATED_TO 说明建模偷懒，应拆成 :KNOWS/:WORKS_AT 等语义明确的类型；②是否有超级节点——某个节点连了几十万条关系（如「中国」这个地点节点），遍历到它就慢，需要拆分或用关系属性过滤；③属性是否过大——节点上挂几 MB 的长文本会拖慢遍历，应拆到外部存储只留 id。
