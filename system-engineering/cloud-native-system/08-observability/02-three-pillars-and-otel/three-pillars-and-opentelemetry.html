可观测三支柱与 OpenTelemetry

指标告诉你「有没有问题」，日志告诉你「具体发生了什么」，追踪告诉你「在这一串调用里的哪一步」。三者回答的问题不同，缺一个就会卡在某个环节。

三支柱各自回答什么

支柱数据形态回答的问题成本特征
Metrics 指标聚合后的数值时间序列「有没有问题？有多严重？」基数固定，成本可控，适合长期保存
Logs 日志离散的文本/结构化事件「具体发生了什么？」随流量线性增长，高基数天然友好，但量大且贵
Traces 追踪带上下游关系的调用链「在这一串调用里的哪一步慢/错？」通常采样，成本取决于采样率

三者的分工可以类比：指标是仪表盘（发现异常），日志是行车记录仪（还原细节），追踪是导航路线（定位路段）。只装仪表盘的团队能发现问题但查不出原因，只留日志的团队能在事后翻出一切但难以实时发现。

典型排查路径

发现异常

错误率从 0.1% 涨到 5%，P99 延迟翻倍。指标告诉你「出问题了」并给出大致范围。

缩小范围

按服务、接口、实例分组，发现集中在某个服务的某个接口、某个可用区。

定位链路环节

拉取该接口的慢请求样本，看到耗时集中在调用下游数据库的那一跳，而不是本服务逻辑。

还原细节

按该时段的该服务过滤，看到大量连接池耗尽和超时报错，确认根因是下游容量不足。

防止复发

这次暴露了「连接池使用率」没有监控，补上指标与告警，下次能在恶化前发现。

为什么需要 OpenTelemetry

三支柱长期各自为政：指标用 Prometheus 客户端，日志用各自的日志库，追踪用各自的 SDK，厂商之间数据格式互不兼容。结果是接入成本高、切换厂商要重写一遍埋点。

OpenTelemetry（OTel）提供统一的 API、SDK 和数据协议（OTLP），让埋点一次、后端可换。它还统一了三支柱之间的关联方式：同一个请求产生的指标、日志、追踪可以携带相同的上下文标识，从而互相跳转。

关联：让三支柱真的连起来

三支柱如果各自孤立，价值大打折扣。OTel 的关键贡献是统一的上下文传播：

关联方式做什么带来什么
TraceID / SpanID 注入日志每条日志带上当前调用链标识从一条报错日志可直接跳到完整调用链
Exemplar（指标 → 追踪）指标数据点附带样本追踪的链接看到延迟尖峰时可以直接点进去看那次请求
统一资源属性服务名、实例、环境在三支柱里用同一套标签跨支柱过滤时口径一致，不会对不上

其中日志带 TraceID 是性价比最高的一项：实现简单（日志框架加个 MDC 字段），收益直接（从报错直接跳链路）。

采样：控制追踪成本的必要手段

策略做法优缺点
头部采样请求进入时就决定是否采样简单、成本低；但可能漏掉后来才变慢的请求
尾部采样请求结束后根据结果决定（出错/慢的必留）价值更高：错误和慢请求一定被保留；但需要在收集端缓存完整链路，实现更复杂
按比例采样固定百分比最简单，但低流量关键接口的样本可能太少
基于属性采样按服务/接口/重要性设不同采样率灵活，需要维护规则

实践中常见组合是「低比例基础采样 + 错误与慢请求全采」：既控制成本，又保证出问题时有样本可查。只做低比例均匀采样会在真正需要排查时拿不到数据。

落地建议

不要一次铺开所有埋点。推荐顺序：先统一日志带 TraceID（成本低、收益快）→ 再补关键路径的追踪（入口、跨服务调用、数据库/缓存/外部 API）→ 最后补齐指标（RED/USE 视角 + 业务关键指标）。

同时注意：可观测数据的成本会随服务规模线性甚至超线性增长。日志尤其容易失控——无节制的 debug 日志、把大对象整个序列化进日志、高频路径上打点，都会在账单上体现。上线前定好保留期与采样策略。

边界与误区

可观测性不等于监控。监控回答「已知的问题是否发生」（阈值告警），可观测性回答「未知的问题如何定位」（高基数、可任意下钻的数据）。买了可观测平台但只配了几个仪表盘，得到的仍然只是监控。

三支柱的适用场景与数据量

支柱回答什么典型数据量存储成本
Metrics有没有问题（趋势、阈值）小（预聚合，每点几字节）低，可存 1~2 年
Logs具体发生了什么最大（全量文本）高，通常存 7~30 天
Traces请求在哪里慢/错中（采样后）中，通常存 3~7 天

成本排序：Logs >> Traces > Metrics。一个日活百万的服务，全量日志可能是 每天几百 GB；而指标（预聚合、按时序压缩）可能只有 几十 MB。所以不要把所有信息都塞进日志——能聚合成指标的先聚合。

采样配置

# 采样策略：控制 trace 成本的关键
#   头部采样（Head-based）：请求进入时就决定是否采样
#     优点：实现简单、内存开销小
#     缺点：<strong>可能漏掉出错的请求</strong>
#   尾部采样（Tail-based）：等请求结束后再决定（可保留所有错误请求）
#     优点：<strong>错误请求 100% 保留</strong>
#     缺点：需在 Collector 侧缓存完整链路，内存开销大

# OTel Collector 的尾部采样配置
processors:
  tail_sampling:
    decision_wait: 10s          # 等待 10 秒再决定（要覆盖最长请求）
    num_traces: 100000          # 内存里最多缓存的 trace 数
    policies:
      - name: keep-errors       # <strong>所有错误链路全保留</strong>
        type: status_code
        status_code: {status_codes: [ERROR]}
      - name: keep-slow         # 慢请求（> 1s）全保留
        type: latency
        latency: {threshold_ms: 1000}
      - name: sample-rest       # 其余按 1% 采样
        type: probabilistic
        probabilistic: {sampling_percentage: 1}

采样率的经验值：生产环境 1%~10% 通常足够定位问题；错误与慢请求应 100% 保留（用尾部采样实现）。零采样或全采样都是错的——前者等于没有 tracing，后者成本高到无法长期运行。

OpenTelemetry 的核心概念

概念含义要点
Signaltraces / metrics / logs 三类统一协议，可分别接入
Span一次操作（有开始/结束/父子关系）trace 的基本单位
Trace一棵 span 树，代表一次完整请求通过 trace_id 串联
Context 传播跨服务传递 trace_idW3C traceparent 头
Collector接收、处理、导出解耦应用与后端
Attributespan 上的键值（如 http.status_code）高基数属性要谨慎

Trace Context

# W3C Trace Context 头格式（跨服务传播的标准）
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
#            │  │                                │                │
#            │  trace_id(32 hex)                 span_id(16 hex)   flags
#            version
#
# 关键：只要每个服务都透传这个头，整条链路就能串起来
# 常见 bug：<strong>中间件/网关没有透传</strong> → 链路断裂成多段

# Go 里手动创建 span
ctx, span := tracer.Start(ctx, "processOrder")
defer span.End()
span.SetAttributes(
    attribute.Int64("order.id", orderID),
    attribute.String("user.tier", tier),
)
if err != nil {
    span.RecordError(err)
    span.SetStatus(codes.Error, err.Error())   // <strong>标记错误，尾部采样靠这个</strong>
}

高基数属性的陷阱：不要把 user_id、order_id 这类基数无限的值作为 metric 的 label —— 每个唯一值都会创建一个独立时间序列，百万用户就是百万条序列，直接压垮时序库。trace 的 attribute 可以放（不建索引），metric 的 label 不行。

落地清单：从 0 到可用

步骤动作验收标准
1. 埋点接入 OTel SDK，关键路径加 span能看到跨服务链路
2. 传播确保网关/中间件透传 traceparent链路不断裂
3. 采集部署 Collector，配置采样trace 能落库
4. 关联日志里带上 trace_id能从日志跳到链路
5. 看板RED 指标 + 关键链路视图能回答「为什么慢」

最关键也最常被漏掉的是第 4 步：日志里没有 trace_id，就无法从一条错误日志跳到完整链路，三支柱仍然是割裂的。实现很简单——日志框架配置 MDC/context 注入 trace_id 即可，但价值极大。

  • RED 指标（服务级黄金三指标）：Rate（QPS）、Errors（错误率）、Duration（耗时分布）。
  • USE 指标（资源级）：Utilization（使用率）、Saturation（饱和度）、Errors（错误数）。
  • 服务用 RED，硬件/资源用 USE——这是两套互补的方法论，不要混用。

自检 Q&A

Q：有了日志还需要 tracing 吗？

A：需要，它们回答的问题不同。日志告诉你「某个服务内部发生了什么」，但无法回答「这次请求整体在哪一步慢」。跨 5 个服务的请求，靠日志关联需要人工拼时间戳，几乎不可行；tracing 直接给出瀑布图，一眼看出是哪个服务、哪个 span 慢。反过来，tracing 不含详细上下文（不会记录每个变量），所以定位到具体 span 后还要看日志。二者是互补而非替代。

Q：Metrics 和 Logs 能互相替代吗？

A：短期不能，长期可以部分转换。Metrics 的核心优势是便宜（预聚合），适合看趋势与告警；Logs 的优势是信息完整，适合事后深挖。实践中常见做法是从日志中提取指标（如统计错误日志条数生成 error_rate 指标）——这样既保留了细节，又有了便宜的趋势数据。但绝不能反过来「为了省钱只留指标」——出问题时没有细节就无法定位。

Q：trace_id 在异步/消息场景下怎么传？

A：通过消息头传递。生产者把当前 span context 注入到消息头（Kafka 的 header、RabbitMQ 的 properties），消费者从中提取并作为父 span 继续。OTel 提供了 TextMapPropagator 的 inject/extract 接口专门做这件事。常见坑：批量发送时一批消息共享同一个 trace，导致链路图混乱——应为每条消息单独创建 span，或用 link 关联。

Q：为什么我的 trace 总是断成两截？

A：某个环节没有透传 context。按可能性排查——① 网关/反向代理未转发 traceparent 头（检查 Nginx 是否透传自定义头）；② 异步处理时用了新的 context 而不是传递过来的（如 context.Background()）；③ 跨语言时 propagator 配置不一致（一个用 W3C、一个用 B3）。诊断：看断裂处两端的 trace_id 是否不同，相同则是 span 父子关系丢失，不同则是传播中断。

自检

有了全链路追踪，还需要日志吗？

需要。追踪擅长定位「哪一步慢/错」，但不记录业务细节（哪个用户的哪笔订单、参数是什么、走了哪个分支）。日志的高基数和自由文本特性正是追踪的短板，两者互补而非替代。
