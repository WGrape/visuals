🔄 连接生命周期
1. TCP accept → 创建 socket fd
2. 新建线程 → 分配 thread_stack
3. new THD() → 分配 THD 对象 & NET buf
4. 握手认证 → 填充 Security_context
5. dispatch_command() → 循环处理 SQL
6. close_connection() → 析构 THD
7. 线程退出 → 释放 thread_stack（或归池）

连接状态的观测命令

观测

-- 连接数全景
SHOW STATUS LIKE 'Threads%';
--   Threads_connected  当前连接数
--   Threads_running    真正在执行的（高说明并发压力）
--   Threads_cached     缓存中的空闲线程
--   Threads_created    累计创建过的线程数（增长快说明 thread_cache 太小）

SHOW VARIABLES LIKE 'max_connections';
SHOW STATUS LIKE 'Max_used_connections';      -- 历史峰值，据此调 max_connections

-- 看每个连接在干什么
SELECT id, user, host, db, command, time, state, LEFT(info, 80) AS sql_text
  FROM information_schema.PROCESSLIST
 WHERE command != 'Sleep'
 ORDER BY time DESC LIMIT 20;

-- Sleep 连接统计（连接泄漏的体检项）
SELECT user, host, COUNT(*) AS c
  FROM information_schema.PROCESSLIST
 WHERE command = 'Sleep'
 GROUP BY user, host ORDER BY c DESC LIMIT 10;

系统层

# 系统层：连接句柄与端口
ss -ant | awk '$1=="ESTAB"{print $4}' | sort | uniq -c | sort -rn | head
lsof -p $(pidof mysqld) | grep -c TCP

# 用 performance_schema 看连接的内存占用（8.0）
SELECT thread_id, user, current_memory
  FROM performance_schema.threads t
  JOIN sys.memory_by_thread_by_current_bytes m USING (thread_id)
 ORDER BY current_memory DESC LIMIT 10;

调 max_connections 前先算内存：连接数 × 每连接可能的缓冲区峰值。盲目把 151 提到 2000，在复杂查询下可能把内存吃光。

深入自检

max_connections 是 151，为什么实际能连的更少？

因为其中会保留 1 个连接给拥有 SUPER 权限的管理员用于救急，且内部还有后台线程占用。此外每个连接还要消耗文件描述符与内存，所以实际可用量还受操作系统与内存限制。

Threads_connected 很高但 Threads_running 很低说明什么？

说明大部分连接处于空闲（Sleep）状态——典型是连接池开得过大或连接未及时释放。这本身不消耗 CPU，但会占用内存与文件描述符，并在突发时迅速打满 max_connections。

wait_timeout 应该设多大？

要大于应用的连接空闲时长，否则连接池里的空闲连接会被服务端悄悄断开，应用拿到的是失效连接（表现为 Communications link failure）。常见做法：应用侧连接池的空闲检测时间小于 wait_timeout，或把 wait_timeout 调到 1~8 小时并让连接池做保活。

为什么不建议把 sort_buffer_size 这类参数调得很大？

因为它们是按连接、按需分配的：一个需要排序的查询就会分配一份（默认 256 KB，设成 8 MB 就是 32 倍）。并发一高，内存占用会成倍放大，反而引发 OOM。这类参数应优先靠索引与查询改写来减少对缓冲区的依赖。

连接池大小该怎么定？

经验公式：连接数 ≈ CPU 核数 × 2 + 磁盘数（对 CPU 密集型更小）。对多数 OLTP 应用，连接池 20~50 往往比 200 更快，因为过多并发会加剧锁竞争与上下文切换。关键是让 Threads_running 保持在个位数到十几的量级。
