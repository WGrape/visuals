① 核心结论 ② 完整流水线 ③ 别名可见性 ④ 为什么这样设计 ⑤ 常见疑问
一句话总结：你按 SELECT ... FROM ... WHERE ... 的顺序写， 数据库却按 FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT 的顺序执行。 这个错位解释了大量"看起来应该能跑却报错"的现象——最典型的就是 WHERE 里用不了 SELECT 的别名。

02完整流水线（含 CTE 与窗口函数）

FROM / JOIN：确定数据源，做表连接，产出一张"中间虚拟表" ② WHERE：逐行过滤，不满足的行直接丢弃（此时还没有分组、没有别名） ③ GROUP BY：按分组键归并成组（可能用临时表/排序） ④ HAVING：对"组"过滤（此时可用聚合函数） ⑤ 窗口函数：在保留行的前提下，为每行计算基于窗口的值 ⑥ SELECT：计算输出列、聚合结果，定义列别名（别名从这里才存在） ⑦ DISTINCT：去重 ⑧ ORDER BY：排序（可用别名） ⑨ LIMIT / OFFSET：最后截断返回结果
图 2：每一步都产出一张"中间虚拟表"交给下一步

CTE（WITH 子句）的位置

CTE 在整个查询开始前先执行，生成一个临时的命名结果集， 然后被主查询当作普通表引用：

WITH dept_avg AS (                    -- ① CTE 先算好
    SELECT dept, AVG(salary) avg_sal
    FROM employees GROUP BY dept
)
SELECT e.name, e.salary, d.avg_sal     -- ② 主查询再引用
FROM employees e
JOIN dept_avg d ON e.dept = d.dept
WHERE e.salary > d.avg_sal;            -- 高于部门平均的人

-- MySQL 8.0+ 才支持 CTE；也支持递归 CTE（WITH RECURSIVE）

03别名可见性：一张表说清

子句能引用 SELECT 里定义的别名吗原因
WHERE❌ 不能（标准 SQL）WHERE 在 SELECT 之前执行，别名还不存在
GROUP BY✅ 可以（MySQL 扩展）MySQL 允许，但这是非标准扩展；PG 也支持，Oracle 不支持
HAVING✅ 可以（MySQL）MySQL 扩展。但标准写法是重复聚合表达式
ORDER BY✅ 可以（标准）ORDER BY 在 SELECT 之后执行，别名已存在
LIMIT—LIMIT 不引用列
-- ❌ 报错：WHERE 里用 SELECT 定义的别名
SELECT salary * 12 AS annual FROM employees WHERE annual > 500000;

-- ✅ 方案 1：重复表达式
SELECT salary * 12 AS annual FROM employees WHERE salary * 12 > 500000;

-- ✅ 方案 2：包一层子查询
SELECT * FROM (
  SELECT salary * 12 AS annual FROM employees
) t WHERE annual > 500000;

-- ✅ 方案 3：用 HAVING（MySQL 支持引用别名，但需配合 GROUP BY 语义）
-- 最通用清晰的是方案 2

-- ✅ ORDER BY 可以直接用别名（标准行为）
SELECT salary * 12 AS annual FROM employees ORDER BY annual DESC;
跨数据库差异：MySQL 允许在 GROUP BY / HAVING 里用别名， 但这是它自己的扩展，SQL 标准和 Oracle 都不允许。 写可移植的 SQL 时，只在 ORDER BY 里用别名，其它地方重复表达式或包子查询。

04为什么设计成这个顺序？

🎯 性能：尽早过滤

WHERE 排在最前面，是为了尽可能早地减少数据量。 先过滤掉 90% 的行，后面的分组、排序、连接代价都会小一个数量级。 这是最重要的优化原则——谓词下推。

🧮 语义：分层计算

必须先有"行"（FROM/WHERE），才能"分组"（GROUP BY）； 必须先"分组"，才能算"组内聚合"并过滤（HAVING）； 最后才能"挑选输出列"（SELECT）。 顺序由数据依赖关系决定，不能颠倒。

🔤 别名：先定义后使用

别名在 SELECT 阶段才"诞生"， 所以只有 SELECT 之后的 ORDER BY 能用它。 这与大多数编程语言"先声明后使用"的规则一致。

📉 LIMIT 最后

只有全部计算、排序完成后才能安全地截断。 如果 LIMIT 提前，排序结果就不对了—— 这也是为什么"先 LIMIT 再 ORDER BY"是错的。

05常见疑问

Q：为什么 WHERE 里不能用 COUNT(*)，而 HAVING 里可以？
A：因为执行到 WHERE 时还没有分组，聚合值无从谈起。 HAVING 在分组之后执行，此时每组的聚合结果已经算出来了，自然可以过滤。 记住口诀：过滤原始行用 WHERE，过滤聚合结果用 HAVING。
Q：SELECT 里写的表达式会被计算几次？
A：逻辑上，WHERE 里重复写的表达式会被计算一次用于过滤， SELECT 里的同名表达式再算一次。 优化器通常能识别重复子表达式并复用，但不能保证。 对复杂/昂贵表达式，用 CTE 或子查询物化一次更稳妥。
Q：ORDER BY 和 GROUP BY 一起用会怎样？
A：MySQL 5.7 之前，GROUP BY 会隐式按分组列排序， 再加 ORDER BY 等于排两次（多余的排序）。 可用 ORDER BY NULL 显式禁止隐式排序。
MySQL 8.0 起不再隐式排序（除非你显式写 ORDER BY）， 且 ORDER BY NULL 被废弃——需要排序就明确写出来。
Q：LIMIT 和 ORDER BY 谁先执行？
A：ORDER BY 先，LIMIT 后。 先排好序，再取前 N 条。所以 SELECT ... ORDER BY id LIMIT 10 得到的是"最小的 10 个 id"， 而不是"先随便取 10 条再排序"。 深分页（LIMIT 100000, 10）慢正是因为要先排/扫完前 10 万行。
