01overcommit 与 OOM 兜底

第一层

概念与判定

Linux 允许「超额分配」（overcommit）：进程 malloc 到地址空间，但物理页在真正访问时才分配（缺页）。所以「申请成功」不代表「内存够用」。真不够时，内核只能杀进程。

overcommit_memory含义
0（默认）启发式：明显超额才拒绝
1总是允许（适合依赖 overcommit 的应用，如 Redis 建议）
2严格：总提交量不超过 CommitLimit
图：从内存压力到 OOM killer 的路径。
OOM killer 不是 bug，是最后兜底。它选一个「最该杀」的进程干掉，通常是大内存占用者。被杀进程收 SIGKILL，无法捕获。

03排障与边界

第三层

排障与边界

  • 容器退出码 137 = 128 + 9（SIGKILL），几乎一定是被 cgroup OOM 杀掉。查 memory.events 的 oom_kill。
  • dmesg -T | grep -i oom 能看到被杀进程、当时内存、调用栈（谁在申请内存）。
  • Redis 需要 overcommit_memory=1：它 fork 做 RDB 持久化，依赖 COW，严格 overcommit 下 fork 会失败。
  • OOM 前的「假死」：直接回收（direct reclaim）会让进程卡在缺页里，表现为 CPU 不高但无响应。看 vmstat 的 si/so 与 pgscan。
  • swap 与 OOM：有 swap 时内核先换出而不是立刻杀；容器常禁用 swap，所以更容易 OOM。

04原理与取舍

第四层

原理与取舍

OOM 的根源是「虚拟内存承诺」与「物理内存现实」的错配。overcommit 提高了内存利用率（多数进程申请远大于实际使用），代价是极端情况下的不可预测性。

策略收益代价
overcommit=1利用率高可能 OOM
overcommit=2不会 OOM（提交即保证）内存浪费、fork 易失败
cgroup 硬限租户隔离超限即杀，需容量规划
cgroup 软限 + 节流平滑降级延迟升高

深入 Q&A

Q：为什么 OOM killer 杀大进程而不是「罪魁祸首」？
A：内核很难判断「谁导致了内存增长」，只能按「谁占得多、杀了能释放多少」估算。所以常误杀缓存/数据库。

Q：怎么避免容器被 OOM？
A：给 memory.max 留 20–30% 余量、监控 memory.current 趋势、限制堆/运行时上限（如 JVM -Xmx），并设 memory.high 提前节流。
