🏛️ HBase 架构

HMaster、RegionServer、ZooKeeper、Meta 表与一次读写的寻址路径

三类角色

HMaster管理面：DDL、Region 分配、负载均衡、故障转移；不参与数据读写
RegionServer数据面：管理若干 Region，处理 put/get/scan；挂了由 HMaster 重新分配
ZooKeeper协调面：选主、RegionServer 注册与存活检测、Meta 表位置
Client先问 ZK 拿 Meta 位置 → 查 Meta 拿 Region 位置 → 缓存后直连 RS

RegionServer 内部

Meta 表与三级寻址

HBase 有两张系统表：hbase:meta（记录每个 Region 的 rowkey 区间与所在 RegionServer）和 hbase:namespace。客户端第一次访问要走「三级寻址」，之后缓存 Meta 结果直连目标 RegionServer。

  • Client 问 ZooKeeper：hbase:meta 表在哪个 RegionServer 上？
  • Client 访问该 RS，查 hbase:meta：我要的 rowkey 落在哪个 Region、哪个 RS？
  • Client 缓存这个映射，直接访问目标 RegionServer 读写
  • 缓存失效（Region 被迁移或 split）时收到 RegionMovedException，回到第 1 步重新寻址
    • 💡 这也是为什么批量写入要先按 rowkey 排序：相邻 rowkey 大概率命中同一个 Region，客户端缓存一次就能连续写入，否则每条都要重新寻址。

    HMaster 到底管什么

    职责说明宕机会怎样
    DDLcreate/alter/drop 表、列族变更无法建表改表（短期可容忍）
    Region 分配新表分配、RegionServer 上下线时重新分配无法完成故障转移
    负载均衡定期把 Region 在 RS 间搬匀（默认每 5 分钟）短期无影响
    分裂协调split 后把子 Region 分配到合适节点短期无影响
    清理回收 HDFS 上的旧文件（HFile、WAL）磁盘缓慢增长
    ⚠️ HMaster 不参与数据读写路径，所以挂掉后集群仍能正常读写（只是不能 DDL、不能故障转移）。生产部署 2 个 HMaster（一个 Active 一个 Backup），靠 ZK 选主。

    ZooKeeper 上的关键节点

    • /hbase/master — 当前 Active HMaster
    • /hbase/backup-masters — 备 HMaster 列表
    • /hbase/rs — 存活的 RegionServer 列表（临时节点，RS 挂了自动消失）
    • /hbase/meta-region-server — meta 表所在 RS
    • /hbase/splitWAL — WAL 拆分任务（故障恢复用）

    规模建议
    伪分布式（学习）1 节点跑 HMaster + RegionServer + 内置 ZK + 本地 FS
    小规模（≤10 节点）2 HMaster（1 Active + 1 Backup），3~5 ZK，RS 与 HDFS DataNode 同机部署
    中大规模HMaster 独立节点；RS 与 DataNode 同机（数据本地性）；ZK 独立 5 节点
    读写分离HBase 原生不做读写分离；靠多租户 (RSGroup) 或 Phoenix 只读副本
    💡 RegionServer 必须与 DataNode 同机部署，这样 Region 的 HFile 有很大概率就在本地磁盘上（数据本地性），避免读走网络。这是 HBase 部署最重要的原则之一。

    🎯 常见问法与答题要点

    Q：HMaster 挂了集群还能读写吗？

    A：能，但要尽快恢复。HMaster 不在数据读写路径上，客户端读写是直接连 RegionServer 的。所以 HMaster 挂掉后已加载的 Region 照常服务，影响的是：不能建表改表、RegionServer 再挂就没人做故障转移、负载均衡和文件清理停摆。生产必须配 2 个 HMaster（ZK 选主）。

    Q：一次 get 请求要经过几跳网络？

    A：首次访问是三跳：Client→ZooKeeper（问 meta 位置）、Client→meta 所在 RS（查 Region 位置）、Client→目标 RS（真正读写）。之后客户端缓存 Region→RS 映射，只需一跳直连。缓存失效（Region 迁移或分裂）时会收到异常并重新走三跳。这也是批量写要先排序 rowkey 的原因——排序后相邻 key 命中同一 Region，缓存利用率高。

    Q：ZooKeeper 在 HBase 里到底存了什么数据？

    A：存的都是少量元数据与协调状态，不是业务数据：Active HMaster 地址、备 Master 列表、存活 RegionServer 列表（临时节点，RS 挂了自动消失）、meta 表位置、WAL 拆分任务、分布式锁。业务数据的位置信息在 hbase:meta 表里，而 meta 表本身存在 RegionServer 上。

    Q：RegionServer 宕机后数据会丢吗？

    A：不会丢（只要 WAL 正常）。恢复流程：ZK 临时节点消失 → HMaster 感知 → WAL Split 把该 RS 的 WAL 按 Region 拆开 → 把这些 Region 分配到存活的 RS → 新 RS 重放 WAL 恢复尚未 flush 到 HFile 的那部分数据。所以关键是 WAL 一定要写成功，生产上不要关闭 WAL。

    Q：为什么 RegionServer 要和 DataNode 部署在一起？

    A：为了数据本地性。HBase 的 HFile 存在 HDFS 上，HDFS 把文件切成 block 分散在各 DataNode。如果 RS 和 DataNode 同机，那么它负责的 Region 的 HFile block 有很大概率就在本机磁盘，读的时候走本地 IO；不同机则每次读都可能跨网络。虽然 compaction 后本地性会下降、需要慢慢恢复，但初始部署必须同机。

    Q：Region 数量多少算健康？

    A：官方经验值：单台 RegionServer 管理 20~200 个 Region 比较健康。太少（<10）说明没分摊开、资源利用率低；太多（>1000）会导致 MemStore 摊薄产生大量小文件、flush/compaction 频繁、ZK 压力与 Master 负担增大。控制手段：预分区规划、调大 max.filesize、关闭不必要的自动 split。

    Q：HBase 怎么做读写分离？

    A：原生不支持（不像 MySQL 主从）。可选方案：①Phoenix 只读副本（把部分 Region 副本放在单独的 RS 上供读）；②应用层面用 RSGroup 把实时读写与离线分析隔离到不同机器组；③离线分析直接读 HDFS 上的 HFile（Snapshot + Spark），完全不打扰在线集群。第③种在实践中用得最多。
