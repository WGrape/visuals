为什么编译之后还要链接

大型程序被拆成许多源文件，编译器每个文件单独编译成目标文件（.o）。编译时 A 文件并不知道 B 文件里的函数最终会被放在内存的哪个地址，这些「跨文件的地址」只能留待链接阶段确定。

链接器做的三件事

两类典型链接错误：
• undefined reference：符号只被引用、找不到定义（忘了链接某个库或实现）。
• duplicate symbol：同一符号被定义了多次（头文件里写了非 inline 的函数定义、或重复链接）。

静态链接 vs 动态链接

维度静态链接（.a）动态链接（.so / .dll / .dylib）
链接时机构建时把库代码拷进可执行文件装载或运行时才绑定
产物体积大（每个程序都带一份库）小（多进程共享一份）

Go 为什么默认静态链接？为了部署简单——编译出单个二进制，拷到目标机器即可运行，不依赖系统库版本。C 程序默认动态链接 libc，所以常出现「glibc 版本不兼容」。
进阶

位置无关代码与 PLT / GOT

动态库被多个进程共享，且加载地址不固定，因此必须是「放哪都能跑」的代码。

📍
PIC（位置无关代码）
不直接使用绝对地址，改用相对寻址或通过 GOT 间接访问，使代码段可被多进程共享
📋
GOT（全局偏移表）
数据段里的一张地址表，记录外部符号的真实地址；代码通过查表间接跳转
🔀
PLT（过程链接表）
函数调用的跳板：第一次调用触发解析并填 GOT，之后再调用直接跳转
⏱️
延迟绑定 Lazy Binding
函数地址只在第一次被调用时才解析，避免启动时解析全部符号，加快启动
装载

装载：把程序放进内存

  1. 操作系统创建进程，建立独立的虚拟地址空间。
  2. 按可执行文件的段描述，把代码段、数据段映射到虚拟内存（通常用 mmap，按需分页调入）。
  3. 装载动态库，完成符号重定位与 GOT 填充。
  4. 初始化（如 .init 段、运行 Go 的 runtime 初始化）。
  5. 跳转到入口，开始执行 main。
为什么用 mmap 而不是 read？按需分页：程序很大也只需把真正访问到的页调入物理内存，启动更快、内存更省，且代码段可在进程间共享。
面试问答

高频问题

Q1：编译、链接、装载分别在做什么？
编译把单个源文件变成目标文件 .o（地址未定）；链接把多个 .o 与库合并，解析符号、重定位地址，产出可执行文件；装载由操作系统把可执行文件映射到虚拟内存并启动执行。
Q2：静态链接和动态链接的区别？
静态在构建期把库代码拷入可执行文件（体积大、部署简单、升级需重编）；动态在装载或运行时绑定共享库（体积小、可共享、便于升级，但依赖目标环境且可能出现版本冲突）。
Q3：undefined reference 是什么意思？
链接器找不到某个符号的定义。常见原因是忘记链接对应的库、函数只声明未实现、或 C/C++ 混合编译时名字修饰（name mangling）不匹配。
Q4：什么是重定位？
编译期不知道符号的最终地址，链接器在确定各段布局后，把这些「待填」的引用按最终地址回填的过程叫重定位。动态库还需在装载时再做一次。
Q5：GOT 和 PLT 的作用？
为了让代码段位置无关并支持共享：GOT 保存外部符号真实地址，PLT 是函数调用跳板。首次调用经 PLT 触发解析并填 GOT，之后直接跳转（延迟绑定）。
Q6：Go 程序为什么能在不同机器上直接跑？
Go 默认静态链接，把依赖（含 runtime）都打进单个二进制，不依赖目标机器的动态库版本，因此拷贝即可运行。

静态链接 vs 动态链接

维度静态链接动态链接
产物大小大（库代码拷进来）小（只记引用）
启动速度快（无需加载库）略慢（要找库、重定位）
内存占用每个进程一份库副本多进程共享一份物理内存
库更新必须重新链接换 .so 即可（需注意 ABI 兼容）
部署简单（单文件，无依赖）需处理依赖（容器里常见坑）
典型Go 默认静态链接C/C++ 默认动态链接

Go 为什么默认静态链接：为了部署简单——编译出一个二进制文件，拷到任何同架构的机器上就能跑，不用担心目标机器有没有 libc、版本对不对。代价是二进制更大（一个简单的 hello world 约 1.5 – 2 MB，而 C 的动态链接版本只有 约 16 KB）。

链接方式对比

# 静态链接
gcc -static main.c -o prog        # Go 默认就是这个行为
ldd prog                          # "not a dynamic executable"
ls -lh prog                       # 约 800KB（hello world）

# 动态链接（默认）
gcc main.c -o prog
ldd prog                          # 列出依赖的 .so
#   linux-vdso.so.1 (0x00007ffd...)
#   libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f...)
#   /lib64/ld-linux-x86-64.so.2 (0x00007f...)
ls -lh prog                       # 约 16KB

# Go 强制动态链接（需要用 cgo 或系统库时）
go build -ldflags="-linkmode=external"
# 或用纯静态（禁用 cgo）
CGO_ENABLED=0 go build            # 最常用，产出完全静态的二进制

# 常见坑：程序在开发机跑得好，部署报 "libc.so.6: version `GLIBC_2.32' not found"
#   原因：编译机的 glibc 比目标机新
#   三种解法：
#     ① CGO_ENABLED=0 go build         （最推荐，纯静态）
#     ② 在<b>目标环境或更老的镜像</b>里编译
#     ③ 用 alpine + musl（但 musl 与 glibc 有细微行为差异）

符号与重定位：链接器在做什么

步骤做什么工具
① 符号解析把每个符号引用绑定到定义（找不到就 undefined reference）nm
② 节合并所有 .text 合并、.data 合并readelf -S
③ 重定位修正符号的实际地址（此时才知道最终布局）objdump -r

符号与 ELF 工具

# ① 查看符号表
nm -C prog                     # -C 还原 C++ 名字（demangle）
# 符号类型：
#   T/t  已定义的<b>代码</b>符号（大写=全局，小写=局部）
#   D/d  已初始化的<b>数据</b>符号
#   B/b  BSS 段（未初始化数据）
#   U    <b>未定义</b>（需要外部提供，如 libc 的函数）
#   W    弱符号（可被覆盖）

# 典型错误：undefined reference to `foo'
#   原因：声明了但没定义 / 忘了链接某个 .o 或 -l 库
#   排查：nm 看符号是 U（未定义）还是 T（已定义）
nm prog | grep foo             # 显示 U foo -> 确实是未定义

# ② 查看 ELF 结构
readelf -h prog                # ELF 头（类型、架构、入口地址）
readelf -S prog                # 所有节（section）的列表
readelf -l prog                # 程序头（segment，装载时用到）
readelf -d prog                # 动态段（依赖哪些 .so）

# ③ 查看重定位表
objdump -r main.o              # 哪些位置需要修正地址
# RELOCATION RECORDS FOR [.text]:
# OFFSET   TYPE              VALUE
# 00000015 R_X86_64_PC32     printf-0x0000000000000004
#                            ^^^^^^ 链接时要把 printf 的真实地址填进去

# ④ 查看动态库的符号
nm -D /lib/x86_64-linux-gnu/libc.so.6 | grep printf
objdump -T libc.so.6 | grep printf

最容易混淆的两个错误：undefined reference 发生在链接期（符号找不到定义）；undefined symbol 发生在运行期（动态库加载时符号找不到）。前者通常是忘了链接某个库，后者通常是库版本不对。

动态链接的延迟绑定：GOT/PLT

概念作用位置
GOT（全局偏移表）存全局变量和函数的实际地址.got / .got.plt 节
PLT（过程链接表）跳转跳板，第一次调用时触发解析.plt 节
延迟绑定第一次调用时才解析地址，之后直接跳由 ld.so 完成

GOT/PLT 与调试

# 延迟绑定的流程（第一次调用 printf）
# ① 代码调用 printf@plt
# ② PLT 第一条指令：jmp *GOT[n]     -> 此时 GOT[n] 指向 PLT 的下一条指令
# ③ 于是跳回 PLT，push 符号索引，jmp PLT[0]
# ④ PLT[0] 调用 ld.so 的 _dl_runtime_resolve()
# ⑤ ld.so 查找 printf 的真实地址，<b>填回 GOT[n]</b>
# ⑥ 跳到 printf 执行
# ⑦ <b>之后再调用 printf@plt 时，GOT[n] 已是真实地址 -> 直接跳，无解析开销</b>

# 查看 PLT 和 GOT
objdump -d -j .plt prog         # 看跳板代码
readelf -r prog | grep -i plt   # .rela.plt 重定位项
readelf -S prog | grep got      # .got / .got.plt 节

# 关闭延迟绑定（安全加固/启动性能优化）
gcc -Wl,-z,now main.c -o prog   # 启动时全部解析（RELRO）
# 或环境变量：LD_BIND_NOW=1 ./prog

# 环境变量调试动态链接
LD_DEBUG=libs ./prog            # 看库的搜索过程
LD_DEBUG=bindings ./prog        # 看符号绑定
LD_LIBRARY_PATH=/my/lib ./prog  # 指定库搜索路径
LD_PRELOAD=./mylib.so ./prog    # 强制预加载（可覆盖函数，调试利器）

# 库搜索顺序
#   ① DT_RPATH（编译时写入，已废弃）
#   ② LD_LIBRARY_PATH
#   ③ DT_RUNPATH（现代，编译时写入）
#   ④ /etc/ld.so.cache（ldconfig 生成）
#   ⑤ 默认路径 /lib、/usr/lib

延迟绑定的取舍：好处是启动快（只解析真正用到的符号）；代价是 ① 第一次调用有额外开销；② GOT 可写带来安全风险（GOT 覆盖攻击）。所以现代系统默认开启 RELRO（-z relro，把 GOT 设为只读）——代价是启动时解析所有符号，启动略慢但更安全。

深入自检

为什么静态链接的 Go 程序在 Alpine 上也有问题？

如果用了 cgo（如依赖 glibc 的库、或用了 net 包的某些 resolv 模式），Go 会退化成动态链接，依赖系统的 glibc。而 Alpine 用的是 musl libc，与 glibc 不兼容，所以会出现“在 Ubuntu 编译的程序在 Alpine 上跑不了”。三种解法：① CGO_ENABLED=0 go build（纯静态，最推荐）；② 用 alpine:latest 作为构建环境（用 musl 编译）；③ 用 scratch 或 distroless 基础镜像 + 纯静态二进制。补充：即使是纯静态，Go 的 DNS 解析在 musl 上也有已知差异，必要时显式设置 GODEBUG=netdns=go 使用 Go 自己的解析器。

动态库版本冲突怎么解决？

这是“DLL Hell”在 Linux 上的版本。常见场景：两个程序依赖同一个库的不同版本。四种解法：① symbol versioning——glibc 用 GLIBC_2.x 版本标签，同一个 .so 里并存多版本符号，老程序仍绑定到老实现（这是 glibc 向后兼容的关键机制）；② soname——库文件名带主版本号（libfoo.so.1），不同主版本可以共存；③ rpath/runpath——程序自带库搜索路径（容器里常用）；④ 容器/静态链接——彻底隔离依赖（最省事）。排障命令：ldd（看依赖）、LD_DEBUG=libs（看搜索过程）、readelf -d（看 rpath）。

什么是 -fPIC？为什么动态库要用它？

-fPIC（Position Independent Code，位置无关代码）生成的代码不依赖自己的加载地址——用相对于 PC（程序计数器）的寻址，而不是绝对地址。因为动态库要被多个进程加载到不同地址（ASLR），如果代码里有绝对地址，就必须为每个进程做重定位（修改代码段，既慢又破坏共享）。用了 -fPIC 后，只需修改 GOT 表（数据段），代码段保持只读且可共享——这是动态库能省内存的根本原因。代价：-fPIC 代码略慢（约 1 – 5%，因为少了一个寄存器可用于优化）。

程序是怎么被加载执行的？

四个步骤：① fork——shell 调用 fork() 创建子进程；② execve——内核读 ELF 头，识别是动态还是静态链接；③ 装载——按程序头（segment）把代码段、数据段 mmap 到内存（注意是映射不是拷贝，真正访问时才通过缺页异常读入）；④ 跳转——若是动态链接，先跳到 ld.so（解释器），由它加载所有依赖库、完成重定位，再跳到程序入口 _start；_start 调用 __libc_start_main，初始化后调用 main，main 返回后调用 exit。实用命令：strace ./prog 能看到完整的 execve + mmap 过程。
