这一章解决什么问题

构建程序这一章讲的是代码是怎么被变成可执行的东西：语言的类型系统在什么时机检查、编译器的前端中端后端各自做什么、中间表示为什么存在、最后怎么生成目标代码。学完再看编译报错与性能问题，视角会完全不同。

语言分类静态与动态、编译与解释，差别在「什么时候做检查」
编译器结构前端管理解、中端管优化、后端管落地
中间表示承上启下的统一形态，让优化与目标无关
为什么值得学能解释报错来源、能读懂优化是否生效
编译的六步：前四步管理解，后两步管变快

知识地图：各阶段做什么

阶段输入与输出典型问题出错时的表现
词法分析字符流 → 记号流非法字符、未闭合的注释提示某个符号无法识别
语法分析记号流 → 语法树括号不匹配、结构不合法提示在某处期望某种结构
语义分析语法树 → 带类型信息的树类型不符、未定义名字类型错误、找不到声明
中间表示树 → 更接近指令的形式如何既通用又便于优化一般不直接报错
优化中间表示 → 优化后的中间表示等价变换是否安全优化不当可能改变行为
代码生成中间表示 → 目标指令指令选择、寄存器不够性能差、寄存器溢出

为什么中间表示这么重要

因为它把「理解语言」和「生成代码」解耦：没有它，每种语言到每种目标平台都要写一套编译器；有了它，前端只需产出中间表示，后端只需消费它，组合数量从乘积变成和。

静态类型到底在检查什么

它检查的是「操作是否合法」：能不能相加、参数类型对不对、返回值是否匹配。这些检查发生在运行之前，所以能在早期发现错误，代价是要写更多类型声明、灵活性略低。

高频问题

编译型和解释型到底怎么分？

严格说区别在「什么时候把源码变成可执行形式」：编译型在运行前完成，解释型在运行时边读边执行。现实中很多语言是混合的：先编译成字节码，再由虚拟机执行，还可能在运行中进一步编译热点代码。

为什么语法错误会一次性报很多？

因为解析器在遇到错误后会尝试恢复并继续，以便一次给出更多问题。恢复策略不同，后续报错的准确性也不同。所以看语法错误时通常先修第一个，后面的可能只是连锁反应。

左递归为什么要消除？

因为自顶向下的解析器遇到左递归会无限递归下去。改写文法可以把左递归变成等价的右递归或迭代形式，这样解析器就能正常工作。这是语法分析实现里最经典的变换之一。

优化会不会改变程序行为？

正确的优化不会，它只做等价变换：在语言规定的语义下结果一致。但在有未定义行为的场景（比如越界访问、数据竞争），优化可能让原本「碰巧能跑」的代码失效。这也是要避免未定义行为的原因。

为什么调试优化后的代码很难？

因为变量可能被放进寄存器、语句顺序被重排、某些计算被提前或直接消除。源码与指令不再一一对应，所以调试通常用关闭优化的版本，只在确认性能问题时才看优化后的结果。
