包是 Go 的封装与编译单元

Go 代码以「包」为单位组织，每个目录通常只放一个包。包把相关的类型、函数聚到一起，并通过名字大小写控制对外暴露。

package 声明

每个文件第一句都是 package

同一目录下的所有 .go 文件必须用相同的 package 名开头；可执行程序入口包名固定为 main。

// 在 model/ 目录下所有文件
package model

// 可执行程序
package main
导入：四种写法

import 的标准形式与变体

标准库、第三方包、相对（已弃用）以及「别名 / 点导入 / 匿名导入」三种特殊形式各有所用。

import (
    "fmt"                       // 标准写法
    "github.com/gin-gonic/gin" // 第三方
    json "encoding/json"        // 别名
    . "math"                    // 点导入：直接用 Sin 而非 math.Sin
    _ "image/png"               // 匿名导入：仅触发 init，不暴露标识符
)
⚠️ 匿名导入 _ 常用于注册驱动（如数据库/图片解码器），利用 init 副作用把实现挂进全局表。点导入会污染命名空间，生产代码应慎用。
初始化顺序

init 函数的执行时机

每个包可有多个 init()，在包变量初始化后、main 之前自动执行；导入链上被依赖的包先完成初始化。

package main

var A = setupA()       // 1. 包级变量初始化

func init() { fmt.Println("init 1") }  // 2. init 按出现顺序
func init() { fmt.Println("init 2") }

func main() { fmt.Println("main") }     // 3. 最后执行
依赖顺序保证：若 main 导入 p，则 p 的变量与 init 全部先于 main 的 init 和 main 执行。可用此机制做配置加载、连接池预热等。
可见性与标识符

再看一次大小写规则

跨包访问只认首字母大写；同一个包内（即使不同文件）所有标识符互通，不存在「文件私有」。

情况可见范围
大写开头包外可见（导出）
小写开头仅本包可见
同包不同文件小写也能互相访问
文件组织约定

目录即包，别过度嵌套

Go 反对深层目录嵌套。一个功能一个目录一个包，目录名用简洁小写、不用下划线或驼峰（如 user、usermodel 而非 user_model）。

包的初始化顺序：一张依赖图看明白

Go 程序的启动顺序是固定的：先按依赖顺序初始化所有包，最后才调用 main。理解这条线，就能解释「为什么我的 init 没按文件顺序执行」这类困惑。

启动链路：依赖包 init → 本包变量 → 本包 init → main
init 没有参数与返回值它只能做副作用：注册、校验、初始化全局变量
一个包可以有多个 init分散在不同文件里都可以，按文件名字典序执行
不要依赖 init 的顺序跨包的顺序由依赖决定，跨文件顺序不该被依赖
init 里不要做重活它发生在程序启动路径上，会拖慢启动且难以测试

import 的几种写法与各自的风险

除了最常见的按路径导入，Go 还有三种特殊写法。它们都有明确用途，但用错会带来可读性或副作用问题。

写法形式用途风险
普通导入import "net/http"最常见，用包名访问无
别名导入import h "net/http"解决同名冲突或缩短长包名滥用会让读者困惑
点导入import . "fmt"直接使用标识符，不需要前缀污染命名空间，测试外的代码不建议
空导入import _ "driver"只要副作用：执行 init 完成注册导入了却不直接用，需要注释说明原因
// 空导入的典型场景：注册数据库驱动 import ( "database/sql" _ "github.com/go-sql-driver/mysql" // 只为执行它的 init，注册 mysql 驱动 ) func main() { // 这里并没有直接使用 mysql 包，但 sql.Open 已经可用 db, err := sql.Open("mysql", "user:pass@/dbname") if err != nil { log.Fatal(err) } defer db.Close() } // 点导入在测试里比较常见（减少样板代码） // 但在业务代码里应当避免，因为读者无法判断标识符来自哪个包

可见性规则：internal 与目录结构

Go 用首字母大小写控制导出，这是最基础的规则；而 internal 目录提供了更进一步的限制：只有它的父目录树内的代码才能导入它。

大小写规则的本质

大写开头 = 导出，可被其他包访问；小写开头 = 包内私有。这条规则同时作用于变量、常量、类型、函数与结构体字段。注意：同一个包的不同文件之间不存在这个限制，包内所有文件互相可见。

internal 的作用范围

放在 a/internal/b 下的包，只能被 a 目录树内的代码导入。这让你可以在模块内部共享代码，同时对模块外彻底隐藏。它是 Go 官方提供的、比大小写更强的封装手段。

// 目录结构示例 // // myapp/ // go.mod module github.com/me/myapp // main.go // internal/ // config/ // config.go // 只有 myapp/... 可以导入 // pkg/ // client/ // client.go // 外部也可以导入 // 规则： // internal 的可见范围 = 它父目录及其所有子目录 // 上例中 github.com/me/myapp/... 都能导入 internal/config // 而 github.com/other/proj 导入会被编译器拒绝 // 实践建议： // - 不希望被外部依赖的实现细节放 internal // - 明确希望别人用的 API 放 pkg 或顶层目录 // - 目录层级控制在两三层内，过度嵌套只会增加查找成本

深入自检：包与文件的八个问题

一个目录里能放两个包吗？

不能（除了 _test 后缀的测试包）。同一个目录下的所有非测试文件必须声明同一个包名，否则编译报错。反过来，同一个包也不能分散在多个目录——目录即包，一个目录对应一个包，这是 Go 的硬性约定。

包名必须和目录名一样吗？

不强制，但强烈建议一致。导入时用目录路径，使用时用包名，两者不一致会让读者困惑。唯一常见的例外是目录名含连字符或版本号，这时包名取一个稳定的短名。

init 函数能被手动调用吗？

不能。init 由运行时自动调用，没有名字、没有参数、不能取地址。如果你需要「可手动调用的初始化」，应该写一个普通函数并显式调用。

循环导入会怎样？

编译报错：import cycle not allowed。Go 不允许包之间循环依赖。解决方式通常是把公共部分抽到第三个包，或者用接口把依赖方向反转，也就是依赖抽象而不是具体实现。

为什么不依赖 init 的执行顺序？

因为跨文件的顺序只是「文件名字典序」这一实现细节，重命名文件就会改变行为。真正可靠的依赖顺序只有一条：被依赖包的 init 一定先于依赖方。需要更明确的顺序时，显式调用函数。

go.mod 里的 module 路径有什么用？

它是这个模块被导入时的前缀，也是包的唯一标识。它通常等于仓库地址，这样 go 工具能直接去拉取。改了 module 路径等于换了一个模块，所有导入方都要跟着改。

vendor 目录还需要吗？

大多数场景不需要。Go Module 会把依赖缓存在本地模块缓存中，vendor 主要用于完全离线构建或需要锁定源码副本的场景。用了 vendor 后构建会优先使用它，需要注意与 go.mod 保持一致。

文件太大时应该怎么拆？

按职责拆而不是按大小拆：同一个类型的构造、方法、序列化可以分文件；常见命名是主逻辑放 xxx.go、测试放 xxx_test.go、包注释放 doc.go。目标是让人一眼知道该去哪个文件找。

第一层 · 概念与判定：目录、包、文件三者关系

一句话判据：一个目录 = 一个包（package），包是编译与封装的最小单位；文件只是包的物理切分。

概念粒度决定什么易错点
目录文件系统包名的作用域边界一个目录放两个 package 名会编译失败
包 package编译单元可见性、导入路径包名可与目录名不同（但不建议）
文件 .go物理切分无语义影响同一包下文件互相可见，不需 import
  • 信号一：想把代码拆成多个文件又不想写 import → 放同一目录、声明同一 package 名。
  • 信号二：想让外部只能用一部分 → 靠首字母大小写（大写导出、小写不导出），没有 public/private 关键字。
  • 信号三：想限制「只允许本项目内部用」→ 放 internal/ 目录。

关键认知：Go 没有「文件级」的可见性。同一包下所有文件的顶层标识符互相可见，切文件纯粹是为了可读性。

第二层 · 参数·命令·量化：import 写法、init 顺序与工具

import 写法与 init

// import 的四种写法
import "fmt"                        // 1) 标准形式
import (
    "os"
    f "fmt"                         // 2) 起别名
    _ "net/http/pprof"              // 3) 空导入：只执行 init，不用其标识符
    . "math"                        // 4) 点导入：标识符直接进当前作用域（不推荐）
)

// init 函数的特性：无参数无返回值、可有多个、按文件名字典序执行
func init() { /* 每个文件可写多个 init */ }

// internal 限制：internal 下的包只能被「internal 的父目录及其子目录」导入
// 例：a/b/internal/c 只能被 a/b/... 下的代码 import
命令 / 工具作用使用时机
goimports -w .自动增删 import 并按标准分组排序每次保存都该跑（IDE 保存即格式化）
gofmt -w .格式化代码（不含 import 处理）提交前
go vet ./...静态检查（如 Printf 占位符不匹配）CI 必跑
go list -deps .列出所有依赖包排查依赖膨胀
go mod why 包路径解释为什么会依赖某个包清理无用依赖

init 执行顺序的确定规则：先按依赖顺序初始化被导入的包 → 再按文件名字典序初始化本包各文件的 init → 最后 main。同一文件内多个 init 按出现顺序执行。

第三层 · 排障与边界：循环导入与命名冲突

现象原因怎么查 / 怎么办
import cycle not allowed两个包互相 import抽出第三个公共包；或用接口倒置依赖
found packages a and b同一目录出现两个 package 名统一 package 名；把测试用的 xxx_test 包拆到别处
use of internal package not allowed从 internal 的允许范围外导入确认导入路径在 internal 父目录子树内
改了代码但行为没变init 里有副作用，或空导入顺序影响检查 _ "xxx" 引入的副作用
undefined: xxx 但明明在同包该标识符首字母小写且在另一个包改名为大写导出
  • 排查顺序：先看报错是 cycle 还是 internal 还是命名冲突 → go list -deps 画依赖图 → 抽公共包解决。
  • 边界一：Go 禁止一切循环依赖，这是语言级硬约束（不像 Java/C++ 可以靠前向声明绕过）。
  • 边界二：点导入（. "math"）会污染命名空间，生产代码禁用，只在测试里偶尔用。
  • 边界三：internal 只对目录树生效，不是对整个 module——跨 module 无法用 internal 隐藏跨项目的包。

循环依赖定位

# 找出循环依赖（go vet 会直接报）
go vet ./...

# 打印依赖图看谁依赖谁
go list -f '{{.ImportPath}} -> {{join .Imports " "}}' ./... | grep -i 包名

第四层 · 原理与取舍：为什么 Go 禁止循环依赖

循环依赖被禁止，换来的是编译单元可以独立、并行、增量编译——包之间构成有向无环图，编译器能明确「先编谁后编谁」。C/C++ 靠头文件与前向声明允许循环引用，代价是编译速度慢、依赖分析复杂。

语言是否允许循环依赖怎么做到的代价
Go❌ 禁止包构成 DAG需要靠抽公共包 / 接口倒置来解耦
Java✅ 允许（类级别）JVM 运行时解析jar 之间循环依赖常见于大型项目
C/C++✅ 允许（靠前向声明）头文件重复包含 + 声明分离编译慢、依赖难分析
Rust❌ 禁止（模块间）crate 构成 DAG与 Go 类似
怎么优雅地解开循环依赖？

三种常用手法：① 抽出第三包（把两者都依赖的类型下沉）；② 依赖倒置（上层定义接口，下层实现，避免下层 import 上层）；③ 用函数参数传递（把依赖作为参数传入，而不是 import）。

包名一定要和目录名一致吗？

技术上不必，但强烈建议一致——不一致时 import 路径与包内引用名不同，读代码的人要来回对照，是常见的心智负担来源。

internal 和首字母小写有什么区别？

首字母小写是包内私有（跨包不可见）；internal 是目录树私有（跨 module 或跨子树不可见，但同子树内可以 import 并访问其导出标识符）。两者是不同维度的控制。
