TCP 与内核参数

关注 tcp_tw_reuse、接收/发送缓冲区、Nagle 与延迟确认、以及 TIME_WAIT 堆积；高并发短连接常见瓶颈就在端口与 TIME_WAIT。

问题 1
如何有效降低网络延迟？

优先减少 RTT：连接复用（长连接/连接池）、合并与批量请求、就近部署与 CDN；其次压缩报文、选高效序列化；最后再调 TCP 参数。

问题 2
连接池大小怎么定？

不是越大越好。受后端并发上限、文件描述符与对端连接数约束。先用压测找到吞吐拐点，通常以「后端核数 × 倍数」为起点逐步调。

问题 3
HTTP/2 比 HTTP/1.1 强在哪？

单连接多路复用，省去多条 TCP/TLS 握手与队头阻塞（应用层），头部压缩也更小。但要注意单连接拥塞与服务端并发模型也要跟上。

问题 4
TIME_WAIT 太多怎么办？

通常是高并发短连接客户端侧。可开启 tcp_tw_reuse（客户端）、复用连接、或让服务端做被动关闭方；避免盲目调小超时以免破坏连接可靠性。

网络调优：先看清楚瓶颈是「带宽」还是「连接」

网络性能问题通常分两类：带宽/吞吐不足（大流量传输）与连接/包处理瓶颈（高并发小包）。两者调优方向完全不同：前者靠大包、批量、零拷贝、多队列；后者靠连接复用、中断亲和、内核参数。

常见场景调优

① 高并发短连接

  • 问题：TIME_WAIT 堆积、端口耗尽、建连开销大。
  • 对策：长连接复用（连接池、Keep-Alive）；调大端口范围与队列。
  • 服务端优先让客户端主动关闭（避免服务端 TIME_WAIT）。
  • 监控：ss -s 看各类状态数量。

② 高 PPS 小包

  • 问题：软中断打满单核（si 高）。
  • 对策：多队列 RSS 绑核、RPS/XPS、增大 ring buffer。
  • 极致方案：DPDK/XDP 绕过内核协议栈。
  • 观测：/proc/softirqs、sar -n DEV、mpstat。

③ 大带宽传输

  • 问题：带宽 × 延迟 决定的窗口限制吞吐。
  • 对策：调大缓冲区、开启窗口缩放、用 BBR。
  • 减少拷贝：sendfile、批量发送。
  • 压缩要权衡 CPU 与带宽。

④ 延迟敏感服务

  • TCP_NODELAY 关闭 Nagle（避免小包等待）。
  • 开启 TCP_QUICKACK（视场景）。
  • 减少跨地域与跨可用区调用。
  • 关注 P99 而不是平均；看重传与 RTT。

⑤ 内核观测命令

  • ss -s：连接状态汇总。
  • ss -i：cwnd、rtt、重传。
  • sar -n DEV,ETCP,TCP 1：流量、重传、建连。
  • netstat -s：协议统计（重传、丢包、溢出）。
  • ethtool -S：网卡级统计与丢包。

⑥ 云环境注意

  • 云网卡有 PPS 与带宽双重上限。
  • 安全组、NAT 网关可能成为瓶颈与延迟来源。
  • 跨可用区调用的延迟与费用都要考虑。
  • 注意虚拟化层的开销（SR-IOV 可改善）。

深入自检

带宽和 PPS 哪个是瓶颈？

取决于包大小。万兆网卡传 1500 字节的大包只需约 80 万 PPS，而传 64 字节小包要 1400 万 PPS——后者通常先撞上 PPS 上限（网卡或 CPU 处理不过来），而不是带宽上限。所以小包场景要关注 PPS 与中断分布，大流量场景才关注带宽。

为什么软中断 si 会打满一个核？

因为网卡中断默认绑定到某个 CPU（常常是 CPU0），所有包的处理都压在它身上。解决：配置多队列 RSS 把队列分散到多核，或用 RPS 在软件层分发，并用 smp_affinity 正确绑定。监控 /proc/softirqs 可以看各核的分布是否均衡。

TIME_WAIT 多一定是问题吗？

不一定。TIME_WAIT 是 TCP 的正常状态（防止旧连接报文干扰新连接），服务端有大量 TIME_WAIT 说明是它主动关闭连接。问题在于占用内存与端口。若影响新连接，可让客户端主动关闭、开启 tcp_tw_reuse、或改用长连接。数量本身不是故障，关键看是否影响业务。

缓冲区是不是越大越好？

不是。太大会增加内存占用并提高延迟（缓冲膨胀），太小则限制吞吐。合理值约为 BDP（带宽 × RTT）。例如 1Gbps、RTT 100ms 的链路，BDP ≈ 12.5MB。现代 Linux 默认开启自动调优，通常不需要手工设置，除非是特殊的高带宽长延迟链路。

怎么定位是网络问题还是应用问题？

分层验证：① ping/arping 看基础连通与延迟；② iperf 测纯网络吞吐（若也不达标就是网络问题）；③ 应用层对比（同机回环 vs 跨机）；④ 看重传、丢包、RTT（ss -i、netstat -s）；⑤ 看连接状态与队列（ss -s、ss -lnt 的 Recv-Q/Send-Q）。若 Send-Q 长期非零，多半是应用读取慢。

为什么跨地域调用延迟大得超出预期？

因为物理距离决定了光速下限：北京到上海往返约 20-30ms，中国到美国西海岸约 150-200ms，再叠加多次往返（TCP 握手、TLS 握手、业务多次调用）会成倍放大。对策：减少往返次数（连接复用、批量、并行）、就近部署、用 CDN 与边缘计算、以及把串行的多次调用合并或异步化。
