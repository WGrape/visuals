网络轮询器（Netpoller）

Go 用 netpoller（基于 epoll/kqueue/iocp）把网络 IO 变成非阻塞，并与 GMP 调度协作：goroutine 在 IO 等待时让出线程，就绪后再被唤醒。

概述

让海量连接变廉价

传统「一连接一线程」在十万连接下内存与上下文切换爆炸。Go 用事件驱动 + 轻量 G，单机支撑海量连接。

事件驱动模型

底层是 epoll

netpoller 封装了各平台的 IO 多路复用（Linux epoll、macOS kqueue、Windows iocp），只用一个系统线程监听大量 fd。

// 伪流程
for { evs := epoll.Wait()
  for ev in evs {
    g := findG(ev.fd)
    injectG(g)  // 把对应 G 放回可运行队列
  }
}
G 在 IO 等待时让出

不占操作系统线程

当 goroutine 做网络读写而被阻塞，runtime 把它从 M 上摘下（park），M 转去跑别的 G；此时 OS 线程并不被这次 IO 占用。

这正是 Go 高并发的基石：少量 OS 线程靠 netpoller 调度海量 G，既非「一连接一线程」，也非「全异步回调地狱」。
就绪后唤醒

IO 完成再继续

netpoller 收到可读/可写事件，找到等待该 fd 的 G，把它重新入队，由调度器择机执行，从阻塞点继续。

与 channel 阻塞的区别

channel/锁阻塞由 runtime 直接调度；网络 IO 阻塞经由 netpoller 事件唤醒，二者都让 G 让出 M，但唤醒来源不同。

为何更省

一连接一线程：内存随连接线性涨；回调模型：逻辑碎片化。Go 模型：连接数 ↑ 只增 G（很小），阻塞成本低。

⚠️ 但 netpoller 只覆盖网络/定时器类 IO；磁盘文件 IO 在某些平台仍会占用线程（runtime 用专门线程池兜底）。
