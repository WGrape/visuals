正向代理、反向代理与 CONNECT：谁代表谁建立连接

沿浏览器经企业代理访问 HTTPS 网站、再经源站反向代理转发的双代理路径解释信任边界。

两种代理位于不同一侧

正向代理代表客户端向外访问目标，常用于企业出口、访问控制或缓存；反向代理位于服务端入口，代表多个后端接收客户端请求，常做 TLS 终止、路由和负载均衡。浏览器配置企业代理 P，经 P 访问 `shop.example.test`；网站前面还有反向代理 R，再由 R 把请求送到订单服务。两者都叫“代理”，但受谁管理、替谁隐藏地址和能看到哪些数据并不同。

客户端知道自己是否明确使用正向代理，通常不需要知道后端有哪些源站实例。反向代理对客户端表现为站点入口。网络中也可能有透明代理或服务网格 sidecar，但不能仅凭“中间有转发设备”就判断是哪一类，必须看连接发起方与协议终止点。

HTTP 明文代理请求

浏览器经显式正向代理访问明文 HTTP 时，可在代理连接上发送包含完整目标 URL 的请求，代理解析目标主机并向其转发。代理可能缓存响应、添加认证、记录访问日志。目标站点收到的源 IP 往往是代理出口而非终端；若业务按 IP 限流，应区分代理群体与真正用户身份，并设计可信转发信息。

代理缓存要遵守 HTTP 缓存指令及用户隔离。若带个人数据的响应被错误存入共享缓存，可能导致跨用户泄漏。代理添加的 Via、Forwarded 等头有助于链路诊断，但客户端也能伪造部分头，源站只能信任受控代理链路中被校验和覆盖的字段。

HTTPS 的 CONNECT 隧道

浏览器经显式 HTTP 代理访问 HTTPS 站点时，通常先向代理发送 `CONNECT shop.example.test:443`。代理若同意，建立到目标地址的 TCP 通道，并返回连接建立响应；之后浏览器在这个通道里与目标端进行 TLS 握手。普通隧道代理可看到目标主机和连接元数据，却不能直接读取 TLS 加密的 HTTP 路径与正文。若企业终端安装了受信任的代理根证书并做 TLS 检查，则代理可能终止并重新建立 TLS，这已是另一种明确的信任配置。

CONNECT 成功只说明隧道已建立，不保证 TLS 主机名验证或后续 HTTP 请求成功。若浏览器报证书错误，先区分拿到的是目标站证书还是企业检查代理证书。若代理不允许目标端口，可能在 TLS 之前就返回代理错误。

反向代理怎样处理请求

R 接受客户端连接，可以终止 TLS，依据 Host 和路径选订单后端，再建立独立的上游连接。此时客户端到 R、R 到后端是两段连接，超时、TLS、重试和连接池各有配置。若客户端请求已被后端提交，但 R 等响应超时并自动重试另一后端，仍可能重复执行非幂等写入。反向代理不提供分布式事务，业务要有幂等键和状态查询。

R 可以把客户端真实地址通过 Forwarded 或 X-Forwarded-For 传递给后端，但必须在边界清除外部用户伪造的同名头，并限定后端只信任 R。若 R 之后还有 CDN、网关等多层代理，需要约定哪个字段和哪个位置代表原始客户端；简单取列表第一个 IP 可能被伪造。

一次完整的地址视图

浏览器本地与企业代理 P 建 TCP；P 再向网站入口 R 建 TCP；R 再向订单服务 S 建上游连接。浏览器看到证书可能由 R 提供，P 在普通 CONNECT 隧道下不解密；S 看到的直接 TCP 对端是 R，R 看到的对端是 P。若要定位用户请求，需使用可信请求 ID 和代理链日志，把各段连接的时间、目标和状态拼起来。

这个例子解释了为何服务器 access log 只有代理 IP、而用户投诉来自不同地区。定位时先确认每段是否真有连接和响应，不要因为 R 返回 502 就断言 S 自己返回 502；502 也可能由 R 生成。

配置与验收

分别测试无代理直连、经 P 的 HTTP、经 P 的 HTTPS CONNECT、经 R 的后端路由。记录 DNS 是浏览器解析还是代理解析、每段 TLS 证书、Host/SNI、真实源 IP 和转发头。代理增加缓存或重试前，先验证用户隔离与写请求副作用；部署后监测每段建连耗时、上游错误与连接池状态。

若企业代理故障，外部站点可能仍健康；若 R 故障，浏览器即使能经 P 访问其他网站也无法访问该站。把链路分成客户端到 P、P 到 R、R 到 S 三段，是最有效的排障起点。

自检

普通 HTTPS CONNECT 代理能直接看到加密后的 HTTP 请求路径吗？

通常不能。它主要建立隧道并看到连接元数据；若显式做 TLS 检查并得到终端信任，才可能解密应用内容。
