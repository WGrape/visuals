语音合成模型对输入很敏感：喂 1998 和喂 一九九八，得到的读音可能完全不同。文本归一化（Text Normalization，TN）就是把「给眼睛看的文本」转成「给嘴读的文本」。这一步做不好，后面模型再强也读不对。

01为什么要归一化：模型的输入分布与书面文本不一致

  • 训练语料是朗读文本：录音念的是「一千二百八十」，不是「1280」
  • 书面符号在语音里没有读音：%、℃、https:// 都没有统一念法
  • 同一个符号在不同语境读法不同：3.14 在数学里是「三点一四」，在版本号里是「三点十四」
  • 不归一化时，模型只能靠猜，遇到训练集里没出现的形态就会读错或吞字
现象没做归一化时归一化后
金额¥1,280.50 逐字符念一千二百八十元五角
日期2026/10/26 念成一串数字二零二六年十月二十六日
比例3:2 念成「冒号二」三比二
手机号13800000000 念成一百三十八亿幺三八… 逐位读
要点：判断优先级永远是：先定语义，再套读法。同一个 3.14，在『圆周率』后面和『版本』后面读法完全不同，靠通用规则无法解决，必须结合上下文。
上下文语义（比分还是日期），再套读法规则 —— 顺序反了必然读错

03可复用的归一化代码

import re

NUM = {'0': '零', '1': '一', '2': '二', '3': '三', '4': '四',
       '5': '五', '6': '六', '7': '七', '8': '八', '9': '九'}

def read_digits(s):
    # 电话、编号这类要逐位读，1 读成 幺
    tbl = dict(NUM, **{'1': '幺'})
    return ' '.join(tbl.get(c, c) for c in s)

def read_decimal(s):
    # 3.14 -> 三点一四；小数部分必须逐位，不能当整数读
    a, b = s.split('.')
    return read_int(a) + '点' + ''.join(NUM[c] for c in b)

def read_int(s):
    # 只处理万以内，更长的交给完整实现
    s = s.lstrip('0') or '0'
    units = ['', '十', '百', '千']
    out, i = '', 0
    for ch in reversed(s):
        out = NUM[ch] + units[i] + out
        i += 1
    return out.replace('一十', '十')

def read_money(s):
    # 1280.50 -> 一千二百八十元五角
    ip, fp = (s.split('.') + [''])[:2]
    res = read_int(ip) + '元'
    if fp:
        res += ''.join(NUM[c] for c in fp[:2]) + ('角分' if len(fp) > 1 else '角')
    return res

# 应用顺序很重要：先长后短，否则小数会被整数规则先吃掉
def normalize(text):
    text = re.sub(r'([0-9]{4})[-/]([0-9]{1,2})[-/]([0-9]{1,2})', read_date, text)
    text = re.sub(r'\\￥?([0-9]+\\.[0-9]{1,2})', lambda m: read_money(m.group(1)), text)
    text = re.sub(r'([0-9]+)\\.([0-9]+)', lambda m: read_decimal(m.group(0)), text)
    text = re.sub(r'([0-9]+)%', lambda m: '百分之' + read_int(m.group(1)), text)
    text = re.sub(r'[0-9]+', lambda m: read_int(m.group(0)), text)
    return text
要点：三条实现经验：① 替换顺序必须先长后短，否则小数会被整数规则先吃掉；② 数字来源不确定时（编号还是数量）宁可逐位读，因为逐位读最多是不自然，读错则是错的；③ 一定要留不处理的出口，识别不了的原样输出比猜错更好。

04排障顺序与常见坑

  1. 先确认问题在前端还是后端：把归一化之后的文本单独打印出来，如果这里就是错的，跟声学模型无关
  2. 复现时保留原始字符串：线上只看到合成结果，看不到输入，排障会无从下手
  3. 对长尾做白名单：专有名词、品牌名、缩写优先用词典，不要指望规则
  4. 多语言要分开处理：中英文的数字读法、单位读法完全不同，不能共用一套规则
症状最可能的原因处理
数字读成一串整数规则没生效检查替换顺序是否被更早的规则吃掉
小数读成整数3.14 被读成三百一十四整数规则必须在小数规则之后
日期读成电话数字串没有语境判断按日期格式优先匹配
专有名词读错词典缺失加白名单，别用通用规则硬套
英文单词念成字母语种判断错误先做语种识别再走对应前端
要点：最后一招很实用：把归一化结果用 TTS 合成后自己听一遍。很多问题在文本上看不出来，一听就知道。

第一层 · 概念与判定：什么要规整、怎么算读错

文本规整（Text Normalization / TN）是把书写文本转成「能正确发音」的形式。数字、符号、缩写如果不处理，TTS 会逐字念（把 12345 念成「一二三四五」）。TN 与反向的 ITN（Inverse Text Normalization）是一对：一个负责念对，一个负责把识别结果还原成书写格式。

原文写法正确读法读错的典型表现判定要点
12345一万二千三百四十五「一二三四五」连续阿拉伯数字默认按数值读
3.14三点一四「三·一四」小数点念「点」，后面逐位
2024 年二零二四年「两千零二十四」年份按四位数逐位或「二零二四」
50%百分之五十「五零百分号」百分号要展开
¥199一百九十九元「幺九九元」货币符号要读出来
第 3 名第三名「第三七名」序数词处理

一句话判定：凡是「逐字念会明显不对」的符号与数字组合，都属于 TN 的处理范围。

第二层 · 参数·命令·量化：常见类型与读法规则

类型读法规则易错点
整数按数值分组（万/亿）英文按三位逗号，中文按四位
小数「点」后逐位读0 读「零」，不读「哦」
分数分母加「分之」1/2 读「二分之一」而非「一半」需看语境
电话号码通常逐位读不能按数值读，否则位数丢失
金额元/角/分 + 可能读「整」发票场景要读「整」
时间时+分，或 24 小时制7:30 可读「七点半」或「七点三十分」

数量级直觉：中文数字每 4 位一个单位（万、亿），所以 123456789 要读「一亿二千三百四十五万六千七百八十九」——单位插错一位（当成英文三位分节）就会差出十万八千里。

第三层 · 排障与边界：高频坑

排障清单（数字 TN 最易翻车的地方）：

  • 编号 vs 数量：订单号 10086 必须逐位读「一零零八六」，但「买了 10086 个」要按数值读 —— 靠上下文，纯规则会错
  • 连字符范围：第 3-5 章，应读「第三到第五章」，直接念「三杠五」是错的
  • 小数点后的 0：3.05 读「三点零五」，漏读零会变成「三点五」
  • 单位缺失：120 km/h 若只留 120，读法完全变味，单位要保留或转写
  • 中英混排：iPhone 15 里 15 念「十五」不是「一五」，专有名词里的数字走另一套规则
  • 歧义金额：1.5 万 vs 1.5 亿，单位量级不同，归一化后必须保留正确量级

验证方法：把规整结果再跑一遍 TTS 合成，人工听「是否像人念的」；更严谨的是用 TN 测试集（覆盖电话、金额、日期、分数、序数各一类）逐条比对。

第四层 · 原理与取舍

为什么数字规整这么难，不能一套规则通吃？

因为同一串数字在不同上下文读法完全不同。「10086」在手机号里逐位、在数量里按值、在年份里四位一组。纯正则无法判断语义，工业方案是先分类（NER 识别是电话/金额/日期/度量）再按类别规则，或者用序列模型端到端预测每个字符的读法标签。

TN 和 ITN 为什么分开做而不用一个模型？

二者方向不同、错误代价不同。TN 错了用户「听着别扭」但能懂；ITN 错了会把「一百元」写成「100 元」进数据库，是数据正确性问题。ASR 场景里 ITN 更要紧，所以常独立训练、独立评估，并额外统计关键字段（金额/日期/电话）准确率。

中英文 TN 最大差异是什么？

数字分节单位不同：英文三位一逗号（thousand/million/billion），中文四位一万/亿。此外英文百分号、序数（1st→first）、缩写（St.→Street）规则与中文体系不互通，所以多语种 TTS 必须按语种加载不同 TN 资源，不能共用。
