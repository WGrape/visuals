文件格式决定了「一次查询要读多少字节」。选型的优先级是：列裁剪能力 > 谓词下推 > 压缩率 > schema 演进。很多人只看压缩率，其实前两项的影响通常大一个数量级。

01四类格式的定位与差异

格式存储方式强项弱项典型用途
CSV / JSON行式、无 schema可读、通用、易交换无列裁剪、无谓词下推，解析慢临时数据交换、小数据集
Parquet列式（行组内列存）生态最广（Spark/Flink/Trino 都支持）、列裁剪好写入较慢，不支持原地修改数据湖与分析的主流选择
ORC列式 + 内置索引Hive 生态下性能最好，支持 ACID跨引擎支持不如 ParquetHive 数仓
Avro行式 + schema 随数据schema 演进最好，序列化紧凑无列裁剪，分析查询慢Kafka 消息、流式管道
Delta / Iceberg / Hudi表格式（底层仍是 Parquet）ACID、时间旅行、小文件治理需要额外的元数据管理生产级数据湖

df.write \
  .mode('overwrite') \
  .partitionBy('dt') \
  .option('compression', 'snappy') \      # 或 zstd（压缩更好，解压仍快）
  .parquet('/warehouse/events')

# 控制文件大小：输出前重分区，避免小文件
df.repartition(200, 'dt').write.partitionBy('dt').parquet(path)
# 经验值：单文件 128MB~1GB；小于 32MB 就该合并

# 读：只取需要的列（列裁剪生效的前提是直接读文件，而不是 SELECT *）
spark.read.parquet(path).select('user_id', 'amount', 'dt').show()

场景选什么理由注意
离线分析（扫描聚合）Parquet + ZSTD/Snappy列裁剪 + 谓词下推，扫描量最小配合分区使用
Kafka / 流式管道Avro + Schema Registryschema 演进安全，上下游不会因字段变更崩溃消费端要按 schema 版本解析

需要 UPDATE/DELETEDelta / Iceberg / Hudi普通 Parquet 不支持行级更新会带来额外的元数据与小文件问题
明细查询（按主键点查）HBase / KV 存储列式不适合点查（要读整个行组）列式是为扫描设计的

# 2) 事后合并（Spark）
spark.conf.set('spark.sql.shuffle.partitions', 200)
spark.sql("INSERT OVERWRITE TABLE events PARTITION (dt='2026-10-25') "
          "SELECT * FROM events_src WHERE dt='2026-10-25'")

# 3) 用表格式自动治理（Iceberg / Delta 的 compaction）
#    Iceberg: CALL system.rewrite_data_files(table => 'db.events')
#    Delta:   OPTIMIZE events ZORDER BY (user_id)
要点：小文件是列式存储的头号问题：每个文件都有 footer 与索引，文件太小会让元数据开销超过数据本身，还会拖慢任务启动（每个文件一个 task）。目标是单文件 128 MB ~ 1 GB。

03五个常见坑

  • 小文件爆炸：按分区写入时没有控制并发，一个分区出几千个文件。用 repartition 或表格式的自动合并解决。
  • schema 演进不兼容：Parquet 增加字段没问题，但改字段类型会导致读失败。需要改类型时应新建表并回填。
  • 压缩算法选错：GZIP 压缩率最高但不可切分（一个文件只能由一个 task 读），大文件必须用 Snappy/LZ4/ZSTD 这类可切分的。
  • 分区字段选错：按高基数字段（如 user_id）分区会产生海量目录，应按时间这类低基数且常用于过滤的字段分区。
  • 用 SELECT * 查列式表：把列裁剪的优势全废了，扫描量回到全表。
# 判断文件是否可切分（大文件必须可切分）
#   Snappy / LZ4 / ZSTD：块级压缩，可切分 ✓
#   GZIP：整体压缩，不可切分 ✗（一个 1GB 的 gz 文件只能单线程读）
#   BZIP2：可切分但极慢，基本不用

04常见疑问

问：Parquet 和 ORC 选哪个？

默认选 Parquet，因为跨引擎支持最好（Spark/Flink/Trino/Pandas/ClickHouse 都能读）。只有在纯 Hive 栈且需要事务表时，ORC 才有明显优势。

问：压缩该选 Snappy 还是 ZSTD？

推荐 ZSTD（级别 1~5）：压缩率通常比 Snappy 高 30%~50%，解压速度几乎相同。Snappy 的优势是压缩速度快，但分析场景下写一次读多次，解压速度更重要。

问：为什么我换了 Parquet 但查询没变快？

按这个顺序查：① 是否只 select 了需要的列；② 是否有分区且查询带了分区条件；③ 是否还有小文件；④ 是否有 UDF 强制读取整行。换格式只是前提，查询写法才决定能不能吃到红利。

问：一行数据很大（比如含大 JSON 字段）怎么办？

列式对超宽行不友好（一个行组可能装不下几行）。把大字段拆到单独的表或文件，热字段单独存，这也是列式设计里常见的冷热分离做法。
