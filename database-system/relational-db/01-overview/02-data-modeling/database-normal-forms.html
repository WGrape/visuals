数据库三范式

Database Normal Forms — 1NF / 2NF / 3NF

1

第一范式（1NF）— 原子性

三个范式各自要消除的依赖类型

First Normal Form · Atomicity

核心规则

表中每一列的值必须是不可再分的原子值，不允许列中存储集合、数组或重复组。

判断要点

✅ 每个字段只存一件事
✅ 没有"多值列"（逗号分隔的多个值）
✅ 没有重复列组（phone1, phone2, phone3...）
❌ 违反：一列塞多个值

❌ 违反 1NF 的表

学生ID姓名课程
001张三数学, 语文, 英语
002李四物理, 化学

"课程"列包含多个值，违反原子性 违反

✅ 符合 1NF 的表

学生ID姓名课程
001张三数学
001张三语文
001张三英语
002李四物理

每行只存一个课程，满足原子性 符合

2

第二范式（2NF）— 完全依赖

Second Normal Form · Full Functional Dependency

核心规则

在满足 1NF 的基础上，非主属性必须完全依赖于主键，不能只依赖主键的一部分（消除部分依赖）。

判断要点

🔑 主键是复合主键时才容易出现问题
✅ 每个非主列都"需要整个主键"才能确定
❌ 违反：非主列只由主键的一部分决定
📌 单列主键自动满足 2NF

❌ 违反 2NF 的表

📦 订单ID
(PK)		 🏷 商品ID
(PK)		 数量 商品名称 商品单价
O001P01 2 苹果手机 5999
O002P01 1 苹果手机 5999

商品名称/单价只依赖于商品ID，而非(订单ID+商品ID) 部分依赖

✅ 拆分为符合 2NF 的两张表

订单明细表

订单ID PK商品ID PK数量
O001P012
O002P011

商品表

商品ID PK商品名称单价
P01苹果手机5999

第三范式（3NF）— 消除传递依赖

Third Normal Form · No Transitive Dependency

核心规则

在满足 2NF 的基础上，非主属性不能依赖于另一个非主属性（消除传递依赖）。即 A→B→C 不允许存在。

判断要点

🔗 传递链：主键 → 非主A → 非主B
✅ 非主列应该直接依赖主键
❌ 违反：非主列通过另一个非主列间接依赖主键
📌 常见于"冗余信息"嵌套在同一张表

❌ 违反 3NF 的表

学生ID PK 姓名 系别ID 系别名称 系主任
S01张三D01计算机系王教授
S02李四D01计算机系王教授
S03王五D02数学系李教授

学生ID → 系别ID → 系别名称、系主任（传递依赖） 传递依赖

✅ 拆分为符合 3NF 的两张表

学生表

学生ID PK姓名系别ID FK
S01张三D01
S02李四D01
S03王五D02

系别表

系别ID PK系别名称系主任
D01计算机系王教授
D02数学系李教授

范式在做的事：消除冗余带来的不一致

范式化的根本动机只有一个：同一份事实不要在库里存两遍。存两遍就意味着更新时要改两处，漏改一处数据就自相矛盾了。

看一个最朴素的例子 —— 一张「订单明细」表：

order_items（未规范化） 订单号 | 下单日期 | 客户名 | 客户电话 | 商品名 | 单价 | 数量 1001 | 03-01 | 张三 | 138xxxx | 键盘 | 199 | 1 1001 | 03-01 | 张三 | 138xxxx | 鼠标 | 89 | 2 1002 | 03-02 | 张三 | 138xxxx | 键盘 | 199 | 1 问题： ① 张三换手机号 → 要改 3 行，漏一行就出现两个不同号码 ② 键盘改名或调价 → 要改 2 行 ③ 删除张三的全部订单 → 张三这个客户的信息也跟着消失了

范式就是一套逐步拆解这套冗余的规则。每一级范式都在消除某一类依赖问题。

1NF → 2NF → 3NF 各自说了什么

范式要求在解决什么
1NF每个字段原子，不可再分；没有重复的列组不能把「电话1,电话2,电话3」塞进一格，也不能出现重复的列
2NF在 1NF 基础上，非主键列必须依赖整个主键，不能只依赖其中一部分解决联合主键下的部分依赖：例如「商品名」只依赖商品号，不依赖订单号
3NF在 2NF 基础上，非主键列不能依赖另一个非主键列解决传递依赖：例如「客户名」依赖「客户号」，而客户号不是主键
BCNF更严格：任何决定因素都必须是候选键处理某些 3NF 仍存在的特殊异常

用上面的例子走一遍：

拆成三张表 orders(订单号 PK, 客户号, 下单日期) customers(客户号 PK, 客户名, 客户电话) products(商品号 PK, 商品名, 单价) order_items(订单号, 商品号, 数量) PK=(订单号, 商品号) 现在： 张三换手机号 → 只改 customers 一行 键盘调价 → 只改 products 一行 删光张三订单 → 客户信息仍在 代价：查询一次订单明细需要 JOIN 三张表

为什么实践中还要「反范式」

范式化牺牲的是读的性能与复杂度：每次查询要多表 JOIN，写起来也更啰嗦。于是现实工程中大量存在有意为之的冗余：

场景做法理由
订单表冗余下单时的价格与商品名快照式冗余商品价格会变，但订单必须保留成交那一刻的事实
统计字段（如评论数、点赞数）在父表里存一个计数值避免每次都 COUNT 一遍
宽表 / 汇总表把常用维度平铺到一张表报表与分析场景，JOIN 成本太高
数据仓库的星型模型维度表故意冗余成宽维度分析型系统本就该反范式

关键判断原则：冗余字段必须是「不会再变」或「允许短暂不一致」的。成交价格是历史事实，不会变 —— 可以冗余；当前商品价格会变，冗余就要承担同步的代价。

OLTP 与 OLAP 的不同取向

OLTP（业务库）

特点：大量小事务、频繁写入、要求强一致。

取向：以 3NF 为主，保证一处更新处处生效；只针对明确的热点做有节制的冗余（如计数列）。

典型：订单、账户、库存。

OLAP（分析库）

特点：批量导入、海量扫描、几乎不更新单条记录。

取向：维度建模（星型/雪花），事实表 + 维度表，允许大量冗余以换取扫描速度。

典型：报表、BI、用户行为分析。

一个常见误区：不要用同一套表同时干这两件事。业务库被分析查询拖垮是非常经典的故障模式 —— 正确做法是通过同步/ETL 把数据复制一份到分析侧，各自用各自合适的模型。

深入自检

范式是不是越高越好？

不是。范式越高，表拆得越碎，JOIN 越多，写 SQL 与优化的复杂度越高。绝大多数业务系统设计到3NF 就足够，BCNF/4NF/5NF 只在遇到明确的异常时才用。范式是手段，一致性才是目标。

冗余字段怎么保证一致性？

三种常见做法：① 同事务内更新 —— 最可靠，但会耦合两张表的写入；② 异步校正 —— 用消息队列或定时任务对账，允许短暂不一致；③ 不保证 —— 只用于历史快照类字段（本就不该被更新）。选哪种取决于这个字段的「正确性」有多重要。

外键约束该不该加？

视团队与规模而定。好处是数据库替你保证引用完整；代价是写入要多做检查、批量导入与分库分表时很麻烦。很多高并发系统会放弃物理外键，改为在应用层保证。如果用了外键，记得外键列一定要建索引，否则关联表的删除/更新会退化成全表扫描。

宽表会不会失控？

会。宽表一旦开了头，很容易不断加列到最后没人敢动。控制办法：① 明确宽表的用途与生成方式（通常由离线任务生成，业务代码不直接写）；② 加列要有评审；③ 拆分稳定列与易变列；④ 用视图或下游模型收口，避免所有查询都直接依赖最底层那张宽表。

范式速查与判定流程

范式要求消除的问题判定口诀
1NF列不可再分（原子性）重复组、多值列每格一个值
2NF消除部分依赖非主键依赖主键的一部分只对联合主键有意义
3NF消除传递依赖非主键列之间相互依赖每个列只依赖主键
BCNF每个决定因素都是候选键3NF 未覆盖的主键内部依赖比 3NF 更严
4NF消除多值依赖一个表里有多组独立多值较少用到

判定流程（自上而下）：

判定流程

# 逐步判定示例：订单表
#   原表：order_id, customer_id, customer_name, product_id, product_name, qty
#   主键：(order_id, product_id)
#
# 1NF：每个格子都是单一值 ✓
#
# 2NF：检查非主键列是否只依赖<strong>部分</strong>主键
#   ✗ customer_name 依赖 customer_id，而 customer_id 只依赖 order_id
#     → 部分依赖！拆出：
#        orders(order_id, customer_id)
#        customers(customer_id, customer_name)
#
# 3NF：检查非主键列之间是否有依赖
#   ✗ 若还有 order_id → customer_id → customer_name 的链
#     → 传递依赖，拆表（上面已拆）
#
# 最终结果：
#   orders(order_id, customer_id)
#   customers(customer_id, customer_name)
#   products(product_id, product_name)
#   order_items(order_id, product_id, qty)

2NF 只对联合主键有意义：如果表的主键是单列（如自增 ID），那它天然满足 2NF——因为不存在「部分」主键。这是很多人混淆的地方。

反范式：什么时候该倒过来

动机做法代价
减少 JOIN把常用字段冗余进主表更新时要同步多处
避免聚合查询存冗余的计数字段（如评论数）需用触发器/异步维护
历史快照订单里存下单时的商品名与价格数据冗余但正确
分析查询宽表（星型/雪花的事实表）ETL 成本

最关键的一条反范式：订单类表必须冗余「下单时的快照」。商品价格会变、用户名会改，但订单记录的是历史事实——「当时买了什么、花了多少钱」不能因为商品改价而变化。这不是冗余，这是语义要求。

反范式实践

-- 正确：订单项冗余商品快照
CREATE TABLE order_items (
  id BIGINT PRIMARY KEY,
  order_id BIGINT,
  product_id BIGINT,
  product_name VARCHAR(200),     -- <strong>下单时的名称（快照）</strong>
  unit_price DECIMAL(10,2),      -- <strong>下单时的价格（快照）</strong>
  qty INT,
  FOREIGN KEY (product_id) REFERENCES products(id)
);
-- 即使 products 表后来改了名称与价格，历史订单仍显示当时的数据
-- 这是<strong>正确且必要</strong>的冗余，不是设计失误

-- 冗余计数的维护（避免每次 COUNT(*)）
ALTER TABLE posts ADD COLUMN comment_count INT DEFAULT 0;
-- 用触发器或应用层维护：
--   INSERT 评论 → UPDATE posts SET comment_count = comment_count + 1
--   DELETE 评论 → UPDATE posts SET comment_count = comment_count - 1
-- 风险：并发下可能不准，需定期用 COUNT(*) 校准

实践中的平衡

场景建议范式级别理由
OLTP 交易系统3NF写入一致性优先
OLAP 分析反范式（宽表）查询性能优先
读多写少的详情3NF + 少量冗余平衡
配置/字典表随意数据量小，无所谓

判断的核心问题：这份数据被写的频率高，还是被读的频率高？

  • 写多 → 高范式：一处更新即可，不会出现不一致。
  • 读多 → 适度反范式：用冗余换查询速度，但要明确维护冗余的机制（触发器、异步任务、还是定期校准）。
  • 最危险的是「无意识的冗余」：冗余了字段却没想清楚怎么同步，迟早出现数据不一致且难以排查。

自检 Q&A

Q：是不是一定要满足 3NF？

A：不。3NF 的目标是消除更新异常（改一处要改多行、删数据误删其他信息）。如果某份冗余数据几乎不变（如字典表的名称），或者有明确的同步机制，反范式完全合理。真正的错误不是「违反 3NF」，而是冗余了却没维护。所以设计时应问：「这个冗余谁来更新？什么时候更新？不一致了会怎样？」——能回答清楚就可以冗余。

Q：外键要不要用？

A：互联网公司大多不用，但要看场景。不用的三个理由：① 性能：每次写入都要查父表并加锁；② 死锁：外键的隐式锁增加死锁概率；③ 运维：分库分表、数据迁移时是巨大阻碍。但如果数据一致性要求极高、写入量不大（如财务系统），外键是很好的最后防线——它能挡住所有写入路径（包括手工 SQL）。折中方案：用外键但只在核心表之间，或改为应用层校验 + 定期巡检。

Q：什么时候该拆表？

A：四个信号——① 更新异常：改一个属性要 UPDATE 很多行；② 插入异常：想插入某信息却因为没有主实体而插不进（如没有订单就不能记录新客户）；③ 删除异常：删一条记录把不该删的信息也删了；④ 列过多：一张表几十上百列，说明混了多个实体。反过来，拆得太碎也不好——每次查询都要 JOIN 五六张表，性能和可维护性都受损。

Q：宽表（大宽表）什么时候合理？

A：分析场景（OLAP）非常合理。宽表把维度字段全部冗余进事实表，查询时无需 JOIN，在列存 + 向量化执行下极快。代价是存储膨胀与 ETL 复杂度。判断标准：这份数据主要用于读分析，还是用于事务写入？ 分析型（报表、BI、用户画像）→ 宽表；事务型（订单、账户）→ 保持 3NF。数仓领域常见的「维度建模」（星型模型）本质就是在 OLAP 侧有意识地反范式。
