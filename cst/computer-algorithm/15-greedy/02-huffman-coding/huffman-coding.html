第 15 章 · 贪心

每次合并最小的两个

哈夫曼编码把字符放在叶子上满足前缀条件，反复合并权重最小的两个节点得到最小带权路径长，正确性来自最优子结构与贪心选择性质。

前缀编码：为什么要「无歧义」

把高频字符编成短码、低频编成长码就能压缩。但定长解码要求任何一个码字都不能是另一个码字的前缀，否则 0 和 01 同时存在时，收到 01 无法判断是「a」还是「b + …」。

满足这个条件的编码叫前缀码，它天然对应一棵二叉树：从根出发，左分支记 0、右分支记 1，字符只放在叶子上——叶子不会是任何其他叶子的祖先，前缀条件自动成立。

于是问题变成：给定字符频率，构造一棵使「频率 × 深度」之和最小的二叉树。

构造：每次合并最小的两个

算法：反复取出权重最小的两个节点，合并成一个新节点（权重为两者之和），放回集合，直到只剩一个节点。用小顶堆维护，每次取最小 O(log n)。

为什么最小两个一定要是最深的兄弟

  1. 最优子结构：设最优树 T 中权重最小的两个字符 x、y 是深度最大的兄弟叶子。把它们合并成一个权重 wx+wy 的新叶子，得到树 T′ 对应「n−1 个字符」的子问题。T′ 必须也是该子问题的最优树，否则用更优的替换能构造出比 T 更优的解，矛盾。
  2. 贪心选择性质：在最优树中，权重最小的两个字符总可以放在最深的一对兄弟位置——把它们与最深处的字符交换，代价不会增加（权重小、深度大 → 总代价下降或不变）。
  3. 于是「先合并最小两个」是安全的第一步，剩下的是同构的子问题 → 归纳成立。

这两条（最优子结构 + 贪心选择性质）是所有贪心正确性的通用骨架，见贪心证明与反例。

工程上哈夫曼很少单独使用，更多是作为 DEFLATE（gzip）、JPEG、PNG 压缩流程中的最后一步熵编码。

第一层 · 概念与判定：什么时候用哈夫曼

一句话判据：要给字符/符号设计「前缀编码」，且希望高频符号用短码——就是哈夫曼。

条件哈夫曼适用说明
需要前缀码（任一码不是另一码的前缀）✅保证解码唯一，无需分隔符
符号频率已知且差异明显✅频率差异越大，压缩收益越高
频率均匀（各符号差不多）⚠️压缩收益接近 0，定长码即可
需要随机访问某个符号❌变长码无法定位，用定长码
需要字典序保持❌哈夫曼不保序
  • 信号一：题目要求「最小带权路径长度 WPL」→ 哈夫曼。
  • 信号二：实际压缩场景（ZIP、JPEG 的熵编码段）→ 哈夫曼或算术编码。
  • 信号三：给定一组权值，要构造一棵「权值 × 深度」之和最小的二叉树 → 哈夫曼树。

前缀码的意义：不需要分隔符就能唯一解码。莫尔斯电码需要停顿分隔，哈夫曼码不需要——这是它实用的关键。

第二层 · 参数·命令·量化：构造步骤与复杂度

构造过程只有一句话：每次取权值最小的两个节点合并，重复 n-1 次。

步骤操作代价
① 建优先队列把 n 个权值建成最小堆O(n)（heapify）
② 循环 n-1 次取两个最小 → 合并 → 放回每次 O(log n)，共 O(n log n)
③ 回溯赋码从根 DFS，左 0 右 1O(n)
总计—O(n log n)；若频率已排序可用队列做到 O(n)

哈夫曼构造与 WPL 计算

import heapq
from collections import Counter, defaultdict

def huffman(freq):
    # freq: {symbol: weight}
    h = [[w, [s, '']] for s, w in freq.items()]
    heapq.heapify(h)                       # O(n)
    while len(h) > 1:                      # 合并 n-1 次
        lo  = heapq.heappop(h)
        hi  = heapq.heappop(h)
        for pair in lo[1:]: pair[1] = '0' + pair[1]   # 小的走 0
        for pair in hi[1:]: pair[1] = '1' + pair[1]   # 大的走 1
        heapq.heappush(h, [lo[0] + hi[0]] + lo[1:] + hi[1:])
    return h[0][1:]                        # [(symbol, code), ...]

# 计算 WPL（加权路径长度 = 压缩后的总位数）
def wpl(freq, codes):
    return sum(freq[s] * len(c) for s, c in codes)

text = "abracadabra"
freq = Counter(text)
codes = huffman(freq)
print(codes)                               # 每个符号的变长码
print("定长码位数:", len(text) * 3)          # 5 种符号需 3 bit 定长
print("哈夫曼位数:", wpl(freq, codes))       # 通常明显更少

量化参考：英文文本中字母频率差异大（e 约 12%、z 约 0.07%），哈夫曼能把每字符 8 bit 降到约 4～5 bit，压缩率约 40%。频率越均匀收益越小。

第三层 · 排障与边界：常见坑

坑后果正确做法
只有 1 个符号无法构造二叉树，编码为空串特判：给它分配 0
合并时左右顺序不固定编码不唯一（但 WPL 相同）答案不唯一是正常的，只要 WPL 最小
用 sort 代替堆O(n² log n) 超时用优先队列 O(n log n)
频率全为 0除零 / 空树过滤掉频率为 0 的符号
解码时不知道码表无法解码码表必须随数据一起存，这是哈夫曼压缩的实际开销
  • 排查顺序：先处理 n≤1 的特例 → 再确认用了堆 → 最后验证 WPL 是否真的最小（与定长码比较）。
  • 边界一：哈夫曼编码不唯一——左右子树交换、相同权值的选择顺序都会产生不同码，但 WPL 恒为最优。
  • 边界二：哈夫曼是贪心，它的正确性靠「最优子结构 + 贪心选择性质」证明，不是分治。
  • 边界三：实际压缩中码表本身要占空间，数据量很小时可能出现「压缩后反而变大」。

前缀码性质验证

# 验证解码唯一性：前缀码的关键性质
def is_prefix_free(codes):
    cs = [c for _, c in codes]
    return all(not c2.startswith(c1) for c1 in cs for c2 in cs if c1 != c2)

第四层 · 原理与取舍：为什么「每次取两个最小」是对的

贪心选择性质的证明思路：在最优前缀码树中，频率最低的两个符号一定是深度最大的兄弟节点。若不是，可以把它们与最深的兄弟交换而不增大 WPL——所以存在一个最优解包含「先合并两个最小」这一步，递归下去即得全局最优。

方案压缩率速度随机访问用在哪
定长码无压缩最快✅需要随机访问时
哈夫曼接近熵极限快（码表 + 查表）❌ZIP / JPEG / PNG 的熵编码段
算术编码更接近熵极限（可超 1bit/符号）较慢❌H.264 / Bzip2
LZ77 + 哈夫曼（Deflate）高（利用重复串）中❌gzip / zlib
哈夫曼能达到理论最优吗？

对于每个符号必须占整数个 bit 这一约束下，哈夫曼是最优的；但它无法突破「每符号至少 1 bit」的限制，所以压缩率略低于香农熵（当需要小数 bit 时）。算术编码能突破这个限制，代价是速度与专利/实现复杂度。

为什么实际压缩都用 Deflate 而不是纯哈夫曼？

因为自然语言有大量重复子串（如 the、ing），LZ77 先做字典替换消除重复，再对结果做哈夫曼消除频率不均——两步叠加效果远好于单独任一步。gzip 就是这么做的。

什么时候不该用哈夫曼？

需要随机访问（数据库存储）、需要保序（字典排序的索引）、或数据本身已经熵很高（已加密 / 已压缩）——后者再压只会变大。

让常用的字符说得更短

定长编码（如 ASCII）给每个字符相同位数，但字符出现频率差异巨大。哈夫曼编码的思路：给高频字符短码、低频字符长码，从而让总位数最小。它是一种前缀码，保证任何一个编码都不是另一个的前缀，因此可以无歧义地解码。

前缀码任一编码都不是其他编码的前缀 → 唯一可解码
贪心策略每次合并频率最小的两个节点
时间复杂度用优先队列 O(n log n)；n 为字符种类数
压缩率取决于熵；频率分布越不均，压缩越明显
编码长度期望长度接近信息熵 H，理论上最优前缀码
局限需要预先统计频率、需保存码表、不适合随机访问
自底向上合并最小频率，构造哈夫曼树

与其他编码方式对比

编码是否定长是否需要频率统计压缩率特点与应用
定长编码（ASCII/UTF-32）是否无压缩简单、可随机访问，但浪费空间
哈夫曼编码否（变长）是（一遍扫描）接近熵，分布不均时很好经典最优前缀码；用于 DEFLATE、JPEG、MP3 等环节
算术编码否（整体一个数）是可超过哈夫曼（可给小数位）更接近熵极限，但实现复杂、曾受专利限制

LZW / LZ77否（字典）否（自适应）对重复串有效，通用性好gzip、PNG、ZIP 的核心；无需预先统计
ANS / rANS否是接近算术编码，速度快现代压缩器（zstd、LZNA）常用，速度与压缩率折中优秀

为什么实际压缩器不单独用哈夫曼：真实数据有重复串（不是只有字符频率不均），所以主流做法是「LZ 系列做字典匹配消除重复 + 哈夫曼/ANS 做熵编码」两段式，gzip/zstd 都是这个结构。

构造过程与实现要点

① 构造步骤

  • 统计各字符频率，每个字符建一个叶节点。
  • 全部节点放入小顶堆。
  • 反复取出最小的两个，合并成父节点（权值相加），再放回堆。
  • 直到只剩一个节点，即为根。
  • 从根出发，左分支记 0、右分支记 1，得到各字符编码。

② 为什么这样是对的

  • 关键引理：频率最低的两个字符，一定在最优树的最深层且互为兄弟。
  • 否则可以交换它们到最深层而不增加代价，甚至更优。
  • 于是「合并这两个」是安全的第一步，问题规模减一，可递归（贪心选择 + 最优子结构）。

③ 工程细节

  • 码表要随数据一起保存，否则无法解码（小数据可能「压缩」后反而变大）。
  • 规范哈夫曼（canonical Huffman）：只存长度即可重建码表，DEFLATE 采用。
  • 自适应哈夫曼：边编码边更新频率，无需保存码表，但实现复杂。
  • 频率相同的字符编码不唯一，但总长度一定相同（都是最优）。

④ 局限与替代

  • 必须知道/统计频率，两次扫描（或自适应）。
  • 不适合需要随机访问或流式部分解码的场景。
  • 数据接近均匀分布时压缩率很低（熵接近 log₂n）。
  • 现代替代：ANS（非对称数系）速度更快、压缩率相当，被 zstd 等采用。

深入自检

为什么哈夫曼编码不会产生歧义？

因为它是前缀码：所有字符都对应树的叶子，而叶子之间没有祖先-后代关系，所以任何一个字符的编码都不会是另一个编码的前缀。解码时从根按比特走，走到叶子就输出字符并回到根，路径唯一确定。

哈夫曼编码一定比定长编码省空间吗？

不一定。当所有字符频率接近相等时，最优前缀码的期望长度接近 log₂n，与定长编码几乎一样，还要额外存码表，可能反而变大。它只在频率分布明显不均（熵远小于 log₂n）时才有效——这也是压缩的前提：数据要有冗余。

为什么要把码表存进压缩文件？

因为解压方必须知道「哪个比特串对应哪个字符」才能还原。规范哈夫曼通过约定规则，只需保存每个字符的码长就能重建码表，大幅减小码表体积。对很小的数据，码表开销可能超过压缩收益，所以压缩器通常对小数据直接存原文。

哈夫曼是最优压缩吗？

在「字符级前缀码」这个范围内是最优的（期望码长最接近熵）。但整体压缩不是最优：它无法利用字符间的相关性（如重复串），而 LZ 系列可以；且每个码字长度必须是整数比特，算术编码/ANS 可以用「小数比特」，压缩率更接近熵极限。

哈夫曼树和哈夫曼编码用在哪些地方？

它是许多格式的组成部分：DEFLATE（gzip/PNG/ZIP）、JPEG 的熵编码阶段、MP3/AAC 的部分环节、HTTP/2 的 HPACK 静态哈夫曼。通常不是单独使用，而是作为「消除符号冗余」的最后一步，前面先用字典/变换消除其他冗余。

贪心算法一定能得到最优解吗？

不是所有问题都可以，贪心需要「贪心选择性质 + 最优子结构」两个条件。哈夫曼编码满足，所以贪心最优；而 0-1 背包不满足贪心选择性质（按价值密度取不一定最优），必须用动态规划。判断能否用贪心，关键看局部最优选择是否一定包含在某个全局最优解里。
