资源风格

名词优于动词

用名词资源 + HTTP 方法表达操作（GET 查、POST 增、PUT/PATCH 改、DELETE 删）；路径表述层级，避免动词堆砌。

GET    /users        # 列表
GET    /users/1      # 详情
POST   /users        # 创建
DELETE /users/1      # 删除
输入校验

边界在入口

所有外部输入都不可信：用结构体 tag（如 validator）或手写校验，在 Handler 最前端拒绝非法请求。

type Req struct {
    Name string `json:"name" validate:"required,min=2"`
    Age  int    `json:"age"  validate:"gte=0,lte=150"`
}
validate.Struct(req)  // 返回具体错误
错误响应

统一错误体

约定固定错误结构（code/message/字段级错误），避免把内部 panic 透传给调用方；用中间件统一捕获。

{"error": {"code": "INVALID", "field": "age", "msg": "超出范围"}}
版本

兼容地演进

版本可放 URL 路径或请求头；破坏性变更才升主版本；用别名/适配层减少客户端迁移成本。

⚠️ 错误响应里不要泄露堆栈或内部路径，既不安全也不利于排障标准化。

好的 API 长什么样

API 一旦发布就很难改。设计阶段多花十分钟，能省掉后期半年的兼容包袱。

原则做法反例
资源导向URL 表示资源，方法表示动作GET /getUserById?id=1
名词复数/users /users/{id}/orders/getUsers
方法语义GET 幂等只读，POST 创建，PUT 整体替换，PATCH 局部更新用 GET 修改数据
版本可控路径或头部带版本，提前规划上线后才发现无法演进
统一错误结构错误码 + 消息 + 可选详情有时返回字符串有时返回对象
分页与排序参数统一，返回带总数或游标每个接口一套命名
GET /api/v1/users # 列表（支持分页） POST /api/v1/users # 创建 GET /api/v1/users/{id} # 详情 PUT /api/v1/users/{id} # 整体更新 PATCH /api/v1/users/{id} # 局部更新 DELETE /api/v1/users/{id} # 删除 GET /api/v1/users/{id}/orders # 子资源 // 统一响应 { "code": 0, "message": "ok", "data": { "id": 1, "name": "go" }, "trace_id": "a1b2c3" } // 统一错误 { "code": 40001, "message": "参数校验失败", "details": [{ "field": "email", "reason": "格式不正确" }] }
一致性优先同一系统内命名与结构保持统一。
错误码要分类便于客户端区分「重试有用」与「重试无用」。
带上 trace_id让用户报障时能直接定位到请求。
分页要统一offset/cursor 选一种，别混用。

参数校验放在哪一层

三段校验各有分工，缺一不可，但不要重复实现同一条规则。

层次校验什么失败时
协议层JSON 能否解析、字段类型是否匹配400，给出字段位置
业务入参层必填、格式、范围、长度400，给出字段级错误详情
业务规则层状态是否允许、余额是否足够409 或业务错误码
存储层唯一约束、外键映射成语义明确的错误
// 用 tag 声明规则，集中校验 import "github.com/go-playground/validator/v10" type CreateUserReq struct { Name string `json:"name" validate:"required,min=2,max=32"` Email string `json:"email" validate:"required,email"` Age int `json:"age" validate:"omitempty,gte=0,lte=150"` Phone string `json:"phone" validate:"omitempty"` } var validate = validator.New() func (r *CreateUserReq) Validate() error { if err := validate.Struct(r); err != nil { // 转换成友好的字段级错误 return ErrInvalidParam.WithDetails(parseFieldErrors(err)) } return nil } // 常用规则：required · omitempty · min/max · gte/lte · oneof · email · url · len

中文错误怎么做：注册自定义翻译器，把 validator 的英文提示映射成中文；或者直接自己维护一份「字段 → 规则 → 文案」的映射，比翻译器更可控。

错误设计：让调用方能正确处理

错误要能分类

客户端只关心三件事：要不要重试、要不要提示用户、提示什么。

type AppError struct { Code int `json:"code"` // 业务错误码 Message string `json:"message"` // 可展示给用户 Details any `json:"details,omitempty"` cause error // 内部原因，不外泄 } func (e *AppError) Error() string { return e.Message } func (e *AppError) Unwrap() error { return e.cause }

错误码怎么分

  • 按区间分段：参数类、权限类、资源类、限流类、系统类
  • HTTP 状态码表达大类，业务码表达具体原因
  • 不要把所有错误都塞成 500
  • 内部错误详情写日志，不返回给客户端

不要吞掉错误

  • 用 %w 包装保留链路：fmt.Errorf("query user: %w", err)
  • 用 errors.Is / errors.As 判断类型
  • 日志里记录完整错误，响应里只给概要
  • 忽略错误要写注释说明为什么

深入自检

REST 一定要严格遵守吗？

不必教条。REST 是一套成熟的默认约定，能省掉大量设计争论；但当业务动作确实难以映射成资源操作时（如「结算」「审核」），用一个明确的动作用例接口反而更清晰，关键是全系统保持一致。

校验应该手写还是用库？

格式类校验用库（tag 声明，效率高、一致性好）；跨字段与业务规则校验手写（库表达不了）。两者结合最实用：先跑 tag 校验，再跑手写的业务校验函数。

为什么不要把所有错误都返回 500？

500 意味着「服务端有问题」，客户端会认为重试可能成功或只能报障。参数错误、权限不足、资源不存在都有明确语义，返回对应的 4xx 才能让客户端做出正确处理，也避免污染服务端的错误率指标。

错误码和 HTTP 状态码重复吗？

不重复，二者粒度不同。HTTP 状态码面向通用协议（客户端、代理、浏览器），业务错误码面向具体业务原因。前者用于粗分与自动化处理，后者用于精确定位与用户提示。

API 版本怎么演进最省事？

优先做向后兼容的增量变更：新增可选字段、新增接口，而不是修改已有语义。确需破坏性变更时，通过 URL 路径或头部引入新版本，并给出明确的迁移期与弃用公告。

第一层 · 概念与判定

入参校验是 API 的第一道防线：在业务处理前用 struct tag + validator 把非法请求挡在门外，避免脏数据进入核心逻辑或触发 panic。

  • 分层：传输层（HTTP 绑定）校验结构合法、业务层校验领域规则。
  • 原则：不信任任何外部输入；「服务端校验」不可替代，客户端校验只是体验优化。
  • 代表库：go-playground/validator.v10。

第二层 · 参数·命令·量化

常用标签与示例：

示例

type Req struct {
    Name  string `json:"name"  validate:"required,min=2,max=32"`
    Age   int    `json:"age"   validate:"gte=0,lte=150"`
    Email string `json:"email" validate:"required,email"`
}

func handler(w http.ResponseWriter, r *http.Request) {
    var req Req
    if err := json.NewDecoder(r.Body).Decode(&req); err != nil { /* 400 */ }
    if err := validate.Struct(req); err != nil {
        // 把 ValidationErrors 聚合成字段级消息
    }
}

自定义校验： RegisterValidation("phone", phoneValidator) ；错误信息用命名化（如 zh 翻译）返回。

第三层 · 排障与边界

  • 漏校验导致 panic：只 Decode 不 Validate，下游对 nil/越界直接崩；Decode 后必须 Struct 校验。
  • 类型转换错误：JSON 数字给 string 字段、或溢出；用 json.Number 或严格类型。
  • 错误信息泄露内部实现：直接把 validator 错误暴露给前端；应映射为安全文案。
  • 国际化消息：默认英文错误，中文场景需注册翻译器（ut.Translator）。

第四层 · 原理与取舍

标签式声明校验把规则与结构体绑定，编译期可见、易维护；缺点是复杂跨字段规则（如「开始<结束」）需自定义验证函数或 Struct-Level 校验。服务端校验是强制底线，客户端校验只为减少往返与提升体验。

为什么不能只靠前端校验？

前端可被绕过（直接调接口/改包），后端不校验会让脏数据进库或触发服务端异常。

跨字段规则怎么写？

用 RegisterStructValidation 在结构体层面校验（如 compare start/end），或拆分到业务层校验。
