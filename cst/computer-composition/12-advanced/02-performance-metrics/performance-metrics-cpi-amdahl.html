性能度量：CPI、Amdahl 定律与 Roofline 模型

把「程序为什么慢」拆成可归因的数字：CPU 时间恒等式、CPI 的分解、并行的天花板，以及判断自己是访存受限还是算力受限的 Roofline 模型。

本文脉络一、基本公式二、CPI 分解三、Amdahl四、Roofline五、测量陷阱

一、CPU 时间的唯一基本公式

所有 CPU 性能优化，最终都要落回这个恒等式：

CPU 时间 = 指令数 × CPI × 时钟周期时间 = 指令数 × CPI / 主频 指令数 (IC) —— 由 ISA、编译器、算法决定 CPI (Cycles Per Instruction) —— 由微架构、流水线停顿、缓存未命中决定 时钟周期时间 —— 由工艺、微架构流水线深度、电压决定

这三个因子互相耦合，不能独立优化：把循环展开能减少指令数（少了分支和自增），但可能撑爆 I-cache 反而拉高 CPI；提高主频往往要拉长流水线，反而增加分支预测失败的代价。任何「改了就变快」的说法都要拿这三个因子重新算一遍。

二、CPI 不是一个数，是若干项之和

实际使用的 CPI 要拆开看，否则你根本不知道时间花在哪：

构成项含义典型来源
理想 CPI无任何停顿时的下限标量机理论值 1；n 发射超标量理论值 1/n；VLIW 看包密度
结构停顿抢不到功能部件除法器/乘加单元占用、访存端口冲突
数据停顿RAW 相关等待load-use 气泡、cache 未命中后的长依赖链
控制停顿分支预测失败预测错率 × 流水线深度 × 发射宽度
访存停顿缓存/内存延迟L1/L2/L3 miss 惩罚、TLB miss、NUMA 远端访问
现代 CPU 上访存停顿通常远大于其他项。一个 L3 miss 要等 200+ 周期，而典型程序每几十条指令就可能 miss 一次——这就是为什么「改算法提高局部性」的收益经常超过「改指令减少条数」。

MIPS 为什么不是好指标

MIPS = 主频 / (CPI × 10⁶)。问题在于它只体现指令执行速率，完全不体现每条指令做了多少事。一台 CISC 机器一条指令完成一串内存操作，一台 RISC 机器要五六条，MIPS 数值上 RISC 更低但实际更快。跨 ISA 比 MIPS 没有意义，跨编译器优化等级比也没有意义。

三、Amdahl 定律：并行的天花板

S(n) = 1 / ( (1 - p) + p / n ) p = 可并行部分占原执行时间的比例 n = 处理器数 n → ∞ 时：S_max = 1 / (1 - p)

最常见的误用

用「可并行的代码行数比例」代替 时间比例 p。那段并行代码可能只占 5% 时间，即使 100% 并行化，加速也不到 1.05 倍。

Gustafson 的反驳

现实中问题规模会随算力增长。固定时间而非固定规模时，加速比 S(n) = n - (n-1)(1-p)，可以接近线性。两者不矛盾，只是约束条件不同。

工程含义

优化顺序必须先 profiling。优先砍掉占比最大的那一项，而不是最容易下手的那一项。

串行段的隐藏成本

锁、屏障、归约、I/O、GC 停顿都会被算进「串行部分」，这是多线程程序加速比远低于核数的常见原因。

四、Roofline 模型：先判断你是哪种瓶颈

算术强度 I = 完成的浮点运算数 (FLOP) / 访存字节数 (Byte) attainable 性能 = min( 峰值算力, 带宽 × I )
区间特征该做什么
I < 脊点带宽受限（memory-bound）提高算术强度：向量化、循环分块（tiling）复用缓存、数据布局改 AoS→SoA、压缩/降精度减少字节数、预取
I > 脊点算力受限（compute-bound）提高指令效率：用 FMA 替代独立乘加、减少除法与超越函数、提高 ILP、用更宽的向量、考虑专用加速单元
脊点位置 = 峰值算力 / 内存带宽。这个值在不同机器上差异极大（消费级 CPU 约几 FLOP/Byte，加速卡可以到几十），所以同一段代码在不同硬件上的最优实现往往不同——这正是 Roofline 模型的实用价值。

五、测量本身也有陷阱

  1. 先问测的是什么 — Wall-clock / CPU time / 指令数 / 缓存未命中率 是四件不同的事。多线程程序的 CPU time 会随核数增长，只有 wall-clock 才反映用户感受。
  2. 跑够长时间 — 短于几毫秒的测试会被 CPU 频率调节、调度抢占、页错误、TLB 冷启动污染。至少要跑够能覆盖稳态的时间。
  3. 区分冷启动与稳态 — JIT 语言、按需分页、分支预测器训练、缓存预热都属于冷启动成本。生产环境是长跑，就别拿单次调用的延迟做优化目标。
  4. 多次取中位数而非均值 — 均值会被偶发抖动（GC、中断、NUMA 迁移）拉偏；中位数和 P99 更能反映真实分布。
  5. 用硬件性能计数器验证归因 — perf stat 直接给出 IPC、cache-miss、branch-miss、TLB-miss。先让数字解释清楚时间花在哪，再动手改。
关于具体数值（某款 CPU 的峰值算力、带宽、缓存延迟），不同代际和型号差异很大。请以目标机器的实测或厂商规格为准，本文给出的是方法论而非参数表。
一句话总结：先测量再优化：用 CPU 时间恒等式定位是「指令多」「CPI 高」还是「频率低」，用 CPI 分解定位停顿类型，用 Roofline 判断访存还是算力受限，用 Amdahl 判断并行化值不值。四个工具合起来才不会优化错地方。

三个模型怎么用：算得准才算懂了

CPI、Amdahl、Roofline 分别回答三个不同问题：程序跑多快、并行能加速多少、瓶颈是算力还是带宽。各自有明确的公式和适用边界。

CPI / IPCCPU 执行效率CPI = 总周期数 / 指令数；CPU时间 = 指令数 × CPI × 时钟周期优化要拆成「减少指令数」还是「降低 CPI」
Amdahl并行加速上限S = 1 / ((1-p) + p/n)，p=可并行比例，n=处理器数上限 = 1/(1-p)，串行 5% 时最多快 20 倍

公式与实测

# Amdahl 上限速算（串行比例 -> 最大加速比）
#   串行 50%  -> 最多 2x      串行 10% -> 最多 10x
#   串行  5%  -> 最多 20x     串行  1% -> 最多 100x
#   即使 n -> 无穷大，加速比也被 1/(1-p) 卡死

# Roofline 拐点（ridge point）
#   拐点算术强度 = 峰值算力 / 峰值带宽
#   例：A100  312 TFLOPS(fp16) / 1.5 TB/s = ~208 FLOP/Byte
#   低于 208 -> 带宽受限（memory-bound）
#   高于 208 -> 算力受限（compute-bound）

# 实测算术强度
#   AI = 总浮点运算次数 / 总内存访问字节数
#   用 perf 拿到计数器后自己算：
perf stat -e fp_arith_inst_retired.scalar_double,\
          fp_arith_inst_retired.128b_packed_double,\
          mem_inst_retired.all_loads,\
          mem_inst_retired.all_stores ./prog
  • CPI 高不等于 CPU 差：可能是缓存 miss 多、分支预测失败多、或依赖链太长。要拆开看（perf stat 能给出 stall 的分解）。
  • Amdahl 的残酷之处：就算你能并行 99%，1000 核也只能快 100 倍，剩下 900 核白给。所以并行优化的第一优先级是找串行段，而不是无脑加核。
  • Gustafson 更贴近实际：现实中机器变多时，人们会跑更大的问题（更大的模型、更多的数据）。这时可并行部分的工作量也在变大，加速比能接近线性。所以两个定律不矛盾，Amdahl 看固定问题，Gustafson 看固定时间。
  • Roofline 的算术强度是算出来的，不是猜的：先算出你的算法理论上要做多少 FLOP、要读写多少字节，画到图上，就知道该往哪个方向优化。
  • LLM 推理的两个阶段瓶颈不同：prefill（大矩阵乘）是算力受限；decode（逐 token、batch 小）是带宽受限——所以 decode 优化要靠批处理、KV Cache 量化、投机解码。
Amdahl 和 Gustafson 到底用哪个？

取决于问题规模是否随资源变化：Amdahl 假设问题规模固定（同一个任务，机器变多要求更快完成），上限是 1/(1-p)，适合回答「这个批处理任务能加速多少」；Gustafson 假设时间固定（给更多机器是为了在同样时间内解决更大的问题），加速比 n-(n-1)(1-p)，接近线性，适合回答「机器变多能训多大的模型」。判断方法很简单：老板说「这个任务太慢了」→ Amdahl；老板说「我们能不能做更大的」→ Gustafson。工程上常把两者一起报：既说明加速上限，也说明规模扩展潜力。

怎么用 Roofline 指导优化？

四步：① 算算术强度——数出算法的 FLOP 数和内存读写字节数，相除；② 画到 Roofline 图上（横轴算术强度，纵轴性能，屋顶是 min(算力上限, 带宽×AI)）；③ 看你的点在屋顶下方多远、偏向哪边——在斜线下方（左侧）是带宽受限，在水平线下（右侧）是算力受限；④ 定向优化——带宽受限就想办法减少数据搬运（算子融合、提高缓存复用、用低精度减少字节数、改数据布局提高局部性）；算力受限才去抠 FLOP（用 tensor core、减少冗余计算、更好的算法）。最常见的新手错误是在带宽受限的代码上拼命优化计算，结果毫无提升。

CPI 优化到多少算合理？

看处理器宽度：标量流水线理论 CPI=1，实际 1.2~2 算正常；4 发射乱序（现代 x86）理论 CPI=0.25（即 IPC=4），实际通用程序 IPC 1~2（CPI 0.5~1）算正常，高度优化的计算密集程序能到 IPC 3~4；GPU 不谈 CPI，看 SM 占用率和带宽利用率。判据不是绝对值，而是与自己基线比：先用 perf stat 记录当前的 IPC 和各类 stall，优化一项再看变化。另外注意 CPI 低不代表快——如果指令数暴涨（比如循环展开太激进导致指令缓存 miss），CPI 降了整体反而慢。
