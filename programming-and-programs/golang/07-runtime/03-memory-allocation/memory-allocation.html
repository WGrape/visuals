概述

为并发而生的分配器

Go 分配器目标是高并发下低锁竞争。核心是「线程本地缓存 + 中心池 + 堆」三级，小对象分配基本无锁。

三级缓存结构

无锁快路径

每个 P 有独立的 mcache，分配小对象直接取用、不加锁；mcache 空了向 mcentral 要一批；mcentral 不够再向 mheap 要 span。

// 伪结构
P.mcache  -> 指向本 P 的 mcache
mcache.alloc[class] -> 该 size class 的空闲对象链表
mcentral -> 管理一类 span，供多个 mcache 取用
mheap -> 持有所有 span，向 OS 要内存
span 与 size class

按规格切分

span 是连续页块；按「size class」把 span 切成等大的小格（如 8/16/32...字节档），对象按大小落入对应 class，减少碎片。

大于 32KB 的对象走「大对象」路径，直接从 mheap 分配专属 span，不经过 mcache 的 class 链表。
微对象分配

极小对象合并

对极小的对象（如几个字节），分配器会把多个合并进同一个机器字，进一步省内存——即 tiny allocator。

对齐

结构体字段顺序与对齐会影响实际占用；把小字段聚拢可减少 padding，降低整体内存。

与 GC 协作

分配触发回收

分配器在申请不到内存、或达到 GC 触发阈值时，会同 GC 协作标记/清扫；span 的空闲状态由 GC 维护。详见三色 GC 篇。

逃逸分析决定变量在栈还是堆：尽量让小对象留在栈，减少堆分配与 GC 压力。
调优与观测

用 pprof 看分配

高频堆分配可用 go tool pprof 的 alloc_space 定位；必要时用 sync.Pool 复用临时对象，降低分配速率。

⚠️ sync.Pool 里的对象可能在任意 GC 被清空，绝不能放「有状态且必须持久」的对象。

Go 内存分配的三级结构

Go 的分配器借鉴了 TCMalloc 的思路：按对象大小分级 + 按 P 缓存，让绝大多数小对象分配走无锁快路径，只在缺货时才向更上层申请。

mcache → mcentral → mheap 三级，越往上越慢但越少发生
mcache每个 P 独享，无锁，小对象分配的快路径。
mcentral按 size class 组织，负责给 mcache 补货。
mheap全局页分配器，兜底并向 OS 申请内存。
8KB 页Go 自己的页单位，与操作系统页无关。

对象怎么分级：tiny / small / large

类别大小走哪条路特点
tiny 微对象小于 16 字节且不含指针mcache 的 tiny 分配器多个微对象塞进同一块，最省
small 小对象16 字节 ~ 32KB按 size class 凑到最接近的档位约 60 多个档位，减少碎片
large 大对象大于 32KB直接向 mheap 申请整页 span按页取整，内部碎片更明显

为什么要有 size class？如果按真实大小切分，会产生无数种小块，回收后无法复用。把大小归并到有限档位后，任何一次释放都能被同档位的新分配复用。make([]byte, 100) 实际会占用 112 字节那一档。

逃逸分析：决定一个变量是栈还是堆

很多「Go 内存问题」其实是逃逸问题。只要编译器能证明变量的生命周期不会超出函数，就把它放栈上，函数返回即自动回收，GC 完全不参与。

func f() *User { u := User{Name: "a"} // 返回了指针 → 逃逸到堆 return &u } func g() int { s := make([]int, 4) // 未传出、大小固定 → 可能留在栈上 return s[0] } func h(x interface{}) {} // 传 interface{} 常常导致装箱逃逸 func i(n int) { b := make([]byte, n) // 大小在运行时才知道 → 通常逃逸 _ = b } # 查看逃逸分析结果 go build -gcflags='-m -m' ./... 2>&1 | grep escapes
返回指针变量被外部引用，必然逃逸
闭包捕获被闭包引用且闭包外泄时会逃逸
interface{}装箱常触发逃逸
动态大小长度是变量的 slice/map 通常逃逸
发送进 channel生命周期不可知，通常逃逸
栈上更快无需 GC 参与，随栈帧一起回收

和 GC 的关系：分配越快，GC 越频繁

分配速率是核心指标

GC 的触发与堆增长相关，而不是堆的绝对大小。

  • 分配越快，达到下一次 GC 阈值越早
  • 降低分配速率比降低堆占用更有效
  • 用 pprof 的 alloc_space / alloc_objects 定位热点

复用对象：sync.Pool

高频临时对象用对象池复用，能显著减少分配次数。

  • 适合短生命周期、可重置的对象（buffer、编码器）
  • Pool 中的对象可能被 GC 清空，不能当作缓存依赖
  • 注意取出后要 Reset，避免脏数据与内存泄漏

预分配容量

slice / map 预分配是最廉价的优化。

  • make([]T, 0, n) 避免多次扩容拷贝
  • map 预分配能减少 rehash
  • 字符串拼接用 strings.Builder 并 Grow

深入自检

小对象分配真的无锁吗？

快路径上无锁：每个 P 有自己的 mcache，分配时直接从对应 size class 的 span 上取一个槽位，全程不加锁。只有在 mcache 缺货、需要向 mcentral 或 mheap 补货时才会加锁，而这种情况占比很低。

为什么 Go 的页是 8KB 而不是操作系统的 4KB？

Go 的「页」是运行时的逻辑管理单位，与 OS 页解耦，可以更灵活地做 span 切分与归还。8KB 在减少管理开销与降低内部碎片之间取得平衡。

看到堆占用很高，是不是内存泄漏？

不一定。Go 的堆包含已分配但尚未回收的垃圾，GC 之后才会下降。判断泄漏要看 GC 之后的 heap_inuse 趋势：多次强制 GC 后仍单调增长，才更可能是泄漏。用 pprof 的 inuse_space 对比两个时间点。

sync.Pool 能彻底解决分配压力吗？

不能也不该。Pool 只是降低分配频率，对象仍会在 GC 时被清空；把 Pool 当作长期缓存会导致数据丢失与逻辑错误。它适合「高频临时、可重建」的对象。

大对象分配为什么更值得警惕？

大对象直接走 mheap，需要加锁且按页取整，碎片更明显；同时它更容易迅速推高堆占用、提前触发 GC。处理大 buffer 时应考虑复用或分块。
