2000 万源数据、20 万热点：Redis 缓存容量案例

源库有 2000 万行，预算只允许缓存约 20 万条。先估算热集和内存，再选淘汰策略，最后用命中率与回源压力验证方案。

先分清三个不同的数量

  • 源数据量：MySQL 有 2000 万行，不代表每行都要进 Redis，也不能直接换算成内存。
  • 热点条目数：计划缓存 20 万条，需要按真实访问分布和序列化后的 key/value 大小验证；热点集合会随时间变化。
  • 命中率：由请求落在当前缓存条目上的比例决定，不等于 20 万 ÷ 2000 万。1% 的条目可能承载大部分请求，也可能不是。
请求→Redis 命中则返回↘未命中查 MySQL→按规则写回缓存

这是旁路缓存（Cache Aside）读路径。缓存失效、回源并发和数据一致性仍要独立设计；淘汰策略只负责容量不足时选择候选键。

把过期、淘汰与热点治理分开

问题对应机制为什么单靠淘汰不够
数据过旧TTL、主动失效和更新后的缓存一致性策略LRU/LFU 只看容量与访问特征，不知道业务数据是否新鲜
内存到上限maxmemory 与按业务选定的淘汰策略策略可能近似采样，不能保证每次恰好保留“最热的 20 万条”
大量请求集中到一个 key本地副本、请求合并、拆分或限流单个热 key 的吞吐瓶颈与总容量不是同一个问题
缓存未命中压垮源库回源预算、预热、请求合并和异常场景保护即使命中率很高，峰值 QPS 的少量未命中也可能超过 MySQL 承载能力

选择与验证：先看负载，再看策略

  1. 测量访问分布、每条缓存对象的真实内存占用、峰值 QPS 和 MySQL 可承受的回源量，估算目标热集大小。
  2. 若 Redis 是可丢弃的纯缓存，可比较 allkeys-lru 与 allkeys-lfu：前者偏近期访问，后者利用近似频率和衰减；稳定热点与突发热点的表现不同。若同实例存放不能淘汰的数据，应先隔离实例或重审数据职责，而不是套用纯缓存策略。
  3. 按数据新鲜度设置 TTL；容量上限和 TTL 各解决不同的问题。用灰度或回放验证策略，不把 LFU 或 LRU 写成无条件最优解。
  4. 上线后同时看命中率、used_memory、evicted_keys、expired_keys、回源 QPS 和响应延迟。单看命中率可能掩盖大 key、冷启动或热点突变。
