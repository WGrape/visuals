05 · 推理

Prefill 与 Decode：同一模型里两种完全不同的负载

所有推理优化都建立在「prefill 算力密集、decode 带宽密集」这个区分上。分不清这两段，就会拿连续批处理去治 TTFT、拿量化去治长 prompt，优化方向全错。

一句话定位：一段并行吃 prompt，一段串行吐 token

prefill 把整段 prompt 一次性前向，所有位置并行算，是标准的大矩阵乘；decode 每次只算一个新 token，要读一遍全部权重但只做一次向量乘。前者算力瓶颈，后者带宽瓶颈。

瓶颈prefill：FLOPS；decode：显存带宽
并行度prefill 沿序列维并行；decode 只有一个位置（靠 batch 并行）
MFU 量级prefill 40%~60%；decode 常低于 5%
优化手段prefill：FlashAttention / chunked prefill；decode：量化 / 批处理 / 投机解码
同样的模型、同样的权重，两段负载的硬件画像完全不同

单请求 decode 上限（tok/s） ≈ 有效带宽 ÷ 权重字节数

这条公式解释了三个现象

① 量化能直接提速 decode（读的字节少了）；② batch 变大时吞吐线性涨但 TPOT 基本不变（权重只读一次，摊给多个请求）；③ 端侧出词速度天然低，因为内存带宽只有服务器的几十分之一。

批处理：唯一能让 decode 变「划算」的手段

单请求 decode 时，GPU 的算力单元 95% 在等内存。把 32 个请求拼成一个 batch，权重只读一遍、算 32 个 token，算力利用率立刻上来，吞吐接近 ×32，而 TPOT 只小幅上升。

技术解决什么代价典型收益
Static batching把固定数量的请求拼批短请求要等长请求，尾延迟高吞吐 ×8~16
Continuous batching每步动态进出请求（iteration-level）调度与 KV 管理复杂吞吐 ×2~4（相对静态）
PagedAttention按块分配 KV，消除碎片与预留需要块表管理显存利用率 +20%~40%
Chunked prefill把长 prompt 切成块，与 decode 混跑TTFT 略升长 prompt 时 TPOT 抖动大幅下降
Prefix caching相同前缀的 KV 复用命中率依赖场景系统提示词类场景 TTFT −50%+

排障：从 TTFT / TPOT 反推瓶颈

症状最可能原因下一步

原理与取舍：为什么不能「让 decode 也并行」

decode 的第 t+1 个 token 依赖第 t 个的输出，天然串行——这是自回归的定义。想打破它只有两条路：投机解码（小模型先猜几个、大模型一次验证）和并行解码（一次出多个位置再修正），前者是不改变分布的严格加速，后者是有损的。这也是为什么投机解码在延迟敏感场景特别受欢迎。

prefill 能不能也用 PagedAttention？

能，KV 的块分配对 prefill 同样适用；PagedAttention 本身不区分阶段，只是 decode 阶段收益最明显。

为什么 decode 的 MFU 这么低还不换硬件？

瓶颈是带宽不是算力，换更快的 HBM 才有效（H100 的 HBM3 比 A100 高 60%+）。用算力更强的卡（如纯 FP8 峰值高的卡）对 decode 帮助有限。

端侧为什么没有 continuous batching？

手机通常只有一个前台请求，batch=1，所以端侧的优化重点是「少读字节」（量化、稀疏、共享）而不是「拼批」。
