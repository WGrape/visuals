Go 项目布局实战：cmd / internal / pkg / go.mod

标准布局、internal 与 pkg 边界、go.mod 与依赖方向

项目布局Gointernal工程实践
布局 边界 go.mod 规则 错误
Go 没有官方强制布局，但社区形成了以 cmd / internal / pkg 为核心的分层约定。关键原则：对外暴露的放 pkg，只服务本项目的放 internal。

1标准布局

myproject/
├── cmd/                 # 各可执行文件入口
│   └── server/
│       └── main.go      # 只做 wiring，逻辑下沉到 internal
├── internal/            # 仅本项目可用，编译器强制禁止外部 import
│   ├── service/
│   └── repo/
├── pkg/                 # 可被其他项目 import 的公共库
│   └── client/
├── api/                 # proto / OpenAPI 定义
├── configs/             # 配置文件
├── go.mod
└── go.sum

2internal 与 pkg 的区别

目录谁可以 import用途
internal仅本模块内实现细节，禁止外泄
pkg任何模块稳定公共 API
cmd仅本目录程序入口与装配
要点：把东西放 internal 能『强制封装』——别人 import 你的模块时拿不到内部实现，避免误用。

3go.mod 示例

module github.com/me/myproject

require (
    github.com/gin-gonic/gin v1.10.0
    google.golang.org/grpc v1.64.0

replace example.com/foo => ./local/foo

4依赖方向规则

  • 依赖只能向下：cmd → internal → pkg，禁止反向。
  • internal 之间不要循环依赖；拆不出就说明边界没划清。
  • main.go 只做『读配置 + 建依赖 + 启服务』，不写业务逻辑。

5常见错误

  • 把所有代码平铺在根目录 → 没有封装边界，别人难以 import。
  • 把内部实现放 pkg → 对外暴露后无法自由改动。
  • 在 internal 里按『层』而不是『业务能力』分包，导致跨包大依赖。
要点：包名用单数小写（如 service，不是 services），且不要和父目录同名。

第一层 · 概念与判定：什么时候照搬标准布局

标准布局（cmd/ internal/ pkg/ go.mod）适合可独立运行、会被别人依赖或长期维护的项目。一次性脚本、纯库则不必全套。

项目类型要不要全套
多二进制服务/CLI 工具集✓ cmd/ 放每个入口
提供给外部的库✓ pkg/ 或根包 + go.mod
内部业务系统✓ internal/ 封实现
一次性脚本/练习✗ 单 main.go 即可

Go 标准项目骨架 + 依赖检查

# 标准骨架
myproj/
├── cmd/
│   ├── api/main.go        # 服务入口
│   └── worker/main.go     # 另一个二进制
├── internal/
│   ├── repo/              # 私有：仅本模块可见
│   └── svc/
├── pkg/                   # 可选：对外可复用
├── go.mod
└── Makefile

# 依赖方向铁律：上层依赖下层，internal 不被外引用
go list -f '{{ join .Imports "\n" }}' ./...   # 查实际依赖

数量级：一个中等服务 internal 下 5–15 个包常见；依赖层级控制在 3 层内，超过说明抽象漏了。

第三层 · 排障与边界：五个常见错误

  • 把私有代码放 pkg/：对外暴露了本该 internal 的实现，别人一依赖你就不能改了
  • 循环依赖：A 引 B、B 引 A——抽出公共包 C，或合并
  • main 包里塞业务：cmd 只该有 main+装配，逻辑进 internal/pkg，否则无法单测
  • go.mod 放错位置：多模块时放错根，import path 全乱
  • 大包怪兽：一个包 3000 行啥都装——按职责拆，单测才好写

第四层 · 原理与取舍

internal 目录为什么能强制封装？

Go 编译器规定：internal/ 下的包只能被 internal 目录的父目录及其子树引用。所以把不希望外部依赖的实现塞进 internal，别人 import 直接编译报错。这是语言级强制的封装边界，比文档约定可靠——这也是为什么业务系统优先用 internal 而非 pkg。

pkg 和 internal 到底怎么分？

经验法则：「以后可能单独开源/被别的团队 import」的才放 pkg；其余全进 internal。多数业务项目的 pkg 其实可以没有，默认一切 internal。放错到 pkg 的代价是失去改动的自由（对外契约一旦形成难改）。

为什么禁止循环依赖是 Go 的设计选择？

Go 故意让循环 import 编译失败，逼你明确定义依赖方向，避免「面条式」耦合。循环通常意味着两个包其实是一个更大职责——抽公共包或合并即可破解。代价是个别场景要多写一次接口，收益是整个项目可独立编译、可单测、可重用。
