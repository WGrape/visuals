02KV Cache 显存怎么估

\n
# KV Cache 显存（每 token 占用）的基本公式\n#   per_token_bytes = 2 (K 和 V) * layers * kv_heads * head_dim * dtype_bytes\n#   总显存 = per_token_bytes * seq_len * batch_size\n\ndef kv_cache_gb(layers, kv_heads, head_dim, seq_len, batch, dtype_bytes=2):\n    per_token = 2 * layers * kv_heads * head_dim * dtype_bytes\n    return per_token * seq_len * batch / (1024**3)\n\n# 例：32 层、8 个 KV head、head_dim=128、fp16(2 字节)\n#     单条 32k 上下文：\nprint(round(kv_cache_gb(32, 8, 128, 32768, 1), 2))     # 约 2.0 GB\n#     并发 16 条：\nprint(round(kv_cache_gb(32, 8, 128, 32768, 16), 2))    # 约 32 GB\n\n# 换成 int8 量化 KV：直接减半\nprint(round(kv_cache_gb(32, 8, 128, 32768, 16, 1), 2)) # 约 16 GB\n\n# 结论：并发 × 上下文长度 决定显存，不是模型参数量\n#   7B 模型 fp16 权重约 14 GB；而 16 路 32k 并发的 KV 要 32 GB\n#   → 长上下文场景下，显存的大头是 KV Cache 而不是权重
因素影响方向可控手段
上下文长度线性增长裁剪、摘要、滑动窗口
并发路数线性增长限流、批处理调度
层数 / KV head 数线性增长选模型时确定，改不了
dtypefp16→int8 减半KV 量化（精度略有损）
分页管理减少碎片浪费PagedAttention 类机制

03四个降本杠杆（按收益排序）

\n
    \n
  1. 裁剪上下文：只保留与当前问题相关的片段。收益最大，因为费用、显存、延迟三项同时下降。
    2. \n
  2. 稳定前缀换缓存命中：把系统提示、工具定义、固定文档放在最前面且保持不变，命中前缀缓存后输入费用可降一个量级。
    3. \n
  3. 限制输出长度与格式：输出单价更高，用结构化输出（JSON schema）避免冗长客套。
    4. \n
  4. 分级路由：简单问题走小模型/短上下文，复杂问题才上大模型 —— 往往 70% 的请求不需要最强的模型。

# 一个简单的成本观测：记录每次调用的 token 与估算费用\nimport time\n\nclass CostLog:\n    def __init__(self, price_in, price_out):\n        self.price_in = price_in    # 每 1k token\n        self.price_out = price_out\n        self.rows = []\n\n    def add(self, name, ti, to):\n        cost = ti * self.price_in / 1000 + to * self.price_out / 1000\n        self.rows.append((name, ti, to, round(cost, 4)))\n\n    def report(self):\n        # 按调用名聚合，找出最贵的环节\n        agg = {}\n        for name, ti, to, c in self.rows:\n            a = agg.setdefault(name, [0, 0, 0.0])\n            a[0] += ti; a[1] += to; a[2] += c\n        for name, (ti, to, c) in sorted(agg.items(), key=lambda x: -x[1][2]):\n            print(f\'{name:24s} in={ti:>8d} out={to:>6d} cost={c:>8.2f}\')\n\n# 用法：在每次调用后 add 一条，一天跑一次 report\n# 绝大多数团队第一次跑都会发现「某个环节占了 60% 以上的钱」

04常见误判

\n
问：上下文越长回答越好吗？

不一定。上下文变长会带来中间信息被忽略的现象（位置靠中间的内容召回率低于首尾），同时噪声变多。把无关内容塞进去通常比不放更差。

问：为什么同样的请求第二次便宜很多？

命中了前缀缓存。前提是与之前某次请求的前缀完全一致，所以系统提示、工具清单里不要放时间戳这类每次都变的东西。

问：把所有资料都塞进上下文，还是用检索？

资料量小且每条都用得上时才全塞；只要有一部分用不上，就应该检索后再塞。判断标准很简单：算一下这条内容的命中率，低于一半就别塞。
