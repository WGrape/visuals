一句话总结：Doris 与 StarRocks 是同源的国产 MPP OLAP 引擎， 设计目标是「比 ClickHouse 更通用」——补齐了多表 JOIN、高并发、MySQL 协议兼容与标准 BI 语义， 代价是单表扫描的极致性能略逊于 ClickHouse。

01定位：从 ClickHouse 的短板出发

ClickHouse 的痛点Doris / StarRocks 的解法
多表 JOIN 弱，大表 JOIN 易 OOMMPP 分布式 JOIN 优化器：Broadcast / Shuffle / Colocate 三种策略自动选择
高并发点查扛不住分区分桶裁剪更彻底 + 更强的并发调度，支持数百 QPS
协议不兼容，BI 工具接入麻烦原生兼容 MySQL 协议，Tableau / 帆软 / Superset 直接连
UPDATE 是异步 mutation，语义别扭支持 Unique Key 模型做真正的 upsert，写入即可见
运维需自己管分片路由内置 自动副本均衡、故障恢复，运维负担更小

一句话区分：ClickHouse = 单表扫描怪兽；Doris/StarRocks = 通用分析数据库。

02FE / BE 架构

图 1：FE 负责"想"（优化），BE 负责"做"（执行）——职责分离清晰

🧠 FE（Frontend）

Java 实现。管理库表元数据、接收 SQL、做基于代价的优化（CBO）、 生成分布式执行计划并下发给 BE。多个 FE 通过类 Raft 协议选主，元数据强一致。

💪 BE（Backend）

C++ 实现。负责数据存储（列存）与查询执行（向量化）。 Tablet 的多副本分布在不同 BE 上，BE 故障时 FE 自动调度副本补齐。

03数据分布：分区 + 分桶

两层分布是 Doris/StarRocks 的核心设计，也是 JOIN 优化的基础。

图 2：分区裁剪 + 分桶定位，两层剪枝把扫描量压到最小

三种数据模型（建表时指定）

模型KEY 语义适用场景
Duplicate KeyKEY 仅用于排序，不去重，全行保留日志、明细事实表（最快）
Aggregate KeyKEY 相同行的 value 列按聚合函数合并（SUM/REPLACE/MAX）指标预聚合，报表直接查
Unique KeyKEY 相同行保留最新，实现真 upsert维表、需要更新的状态表
Primary Key（StarRocks）Unique 的增强版，支持主键索引 + 部分列更新需要高频更新的场景
Unique Key 是 Doris 相对 ClickHouse 的一大优势：写入即可见的 upsert， 不需要像 ReplacingMergeTree 那样担心异步合并和 FINAL 的性能问题。

面试高频：大表 JOIN 慢，第一件事就是看执行计划（EXPLAIN）里用的是哪种 JOIN。 如果两个大表都按 JOIN KEY 分桶且桶数一致，把它们放进同一个 Colocation Group， 就能把 Shuffle Join 变成 Colocate Join，性能往往是数量级的提升。

05物化视图：自动的预聚合

Doris/StarRocks 的异步物化视图能自动改写查询：用户写 SQL 查明细表， 优化器发现能用物化视图回答问题，就透明地改写去查预聚合结果。

-- 建一张按天 + 城市预聚合的物化视图
CREATE MATERIALIZED VIEW mv_daily_city
BUILD IMMEDIATE REFRESH ASYNC EVERY (INTERVAL 1 HOUR)
AS SELECT
    event_date,
    city,
    COUNT(*)         AS cnt,
    SUM(amount)      AS total_amount
FROM events
GROUP BY event_date, city;

-- 用户仍写原 SQL，优化器自动改写命中视图
SELECT city, SUM(amount) FROM events GROUP BY event_date, city;

✅ 优势

对应用完全透明，不改 SQL 就能加速；增量刷新，成本低； 支持多表 JOIN 结果的物化（StarRocks 更强）。

⚠️ 注意

刷新有延迟（近实时非实时）；维度过多会导致视图膨胀； 需关注 EXPLAIN 确认是否真的命中。

06与 ClickHouse 怎么选

维度ClickHouseDoris / StarRocks
单表明细扫描更强，压缩与向量化极致也很强，略逊
多表 JOIN较弱，建议宽表化更强，CBO + 三种 JOIN 策略
高并发查询较弱（建议 <100 QPS）更好，数百 QPS 常见
Upsert / 更新异步 mutation，语义别扭Unique/Primary Key，写入即可见
协议与生态自有 HTTP/TCP 协议兼容 MySQL 协议，BI 接入零成本
运维复杂度分片路由、副本需自行管理FE/BE 内置均衡与恢复，更省心
典型场景日志/埋点明细、用户行为分析企业数仓、BI 报表、多维分析
Q：能不能两个一起用？
A：不少公司正是这么做的——ClickHouse 扛明细日志的 adhoc 探索（几万亿行、单表扫描）， Doris/StarRocks 扛对外 BI 报表（多表关联、高并发、语义层）。 上游共用一套 Kafka + Flink 同步链路，按场景分流。
