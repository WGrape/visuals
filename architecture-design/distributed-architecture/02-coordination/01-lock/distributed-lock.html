分布式锁

多台机器同时改同一份资源时，要有把"跨进程、跨机器"的锁。它比单机锁难在：加锁/解锁要原子、要能容错、要防死锁。

为什么需要 Redis 锁 ZooKeeper 锁 数据库锁 方案对比 面试要点

🎯 一、为什么需要分布式锁

单机里的 synchronized / ReentrantLock 只管一个 JVM 内的线程。当同一份数据被多个服务实例并发修改（超卖、重复对账、幂等防重），就需要一把所有实例都认的锁。

💥
典型场景：秒杀库存扣减、定时任务在多节点只跑一次、分布式事务防重提交。不加锁 → 超卖/重复执行。
一把合格的分布式锁要满足：互斥（任一时刻仅一个持有者）、不死锁（持有者挂了锁能释放）、谁加的锁谁解（防误删）、容错（锁服务本身高可用）。

🔴 二、Redis 分布式锁（最常用）

原子加锁：SET key uuid NX EX 30
一条命令同时完成"不存在才设"和"设置过期时间"，避免"SETNX 后崩溃没设过期"导致的死锁。value 用唯一 uuid 标识自己是持有者。
安全解锁：Lua 脚本校验 uuid 再删
不能直接 DEL——否则可能删掉别人刚拿到的锁。必须用 Lua 原子地"判断 value==我的uuid 才删除"。
看门狗自动续期
业务没跑完锁就快过期？Redisson 的 watch dog 在持有期间每 1/3 超时周期自动续期，直到主动释放。避免"业务没完锁先没"。
⚠️
主从切换的隐患：主库刚写入锁就宕机，从库还没同步就被提升为主——此时另一客户端也能加锁成功，出现"双持锁"。这就是 Redis 官方 Redlock 想解决的，但 Redlock 在分布式学界仍有争议（Martin Kleppmann 批评其依赖时钟假设）。

🟢 三、ZooKeeper 分布式锁

利用 ZK 的临时顺序节点：客户端在锁目录下创建临时顺序节点，序号最小的获得锁；其余监听前一个节点，前一个释放（节点消失）后自己顺位获得。

✅
优点：ZK 用临时节点保证"客户端宕机会话断开→节点自动消失→锁释放"，天然防死锁，且靠顺序节点实现公平排队，比 Redis 在"强一致"上更稳。缺点：性能与吞吐不如 Redis，依赖 ZK 集群。

🗃️ 四、数据库锁（兜底方案）

① 唯一索引 / 悲观锁
插入一条带唯一键的记录表示获锁；或 SELECT ... FOR UPDATE 行锁。简单但 DB 成瓶颈，且连接断开才能释放，一般不作首选。
② 乐观锁（版本号 / CAS）
更新时带版本号 UPDATE ... SET val=? , version=version+1 WHERE id=? AND version=old，影响行数为 0 即失败重试。适合冲突少的场景，但不是"锁"而是"无锁并发控制"。

📊 五、三种方案对比

方案优点缺点适用
Redis性能极高、实现简单主从切换可能双持锁（弱一致）绝大多数高并发业务
ZooKeeper强一致、防死锁、公平吞吐较低、依赖 ZK对正确性要求极高
数据库零额外组件性能差、易成瓶颈低频、简单场景兜底

🎯 六、面试高频追问

Redis 锁为什么要用 Lua 解锁、用 uuid 做 value？
防止 A 的锁过期后，B 拿到锁，A 执行完却把 B 的锁 DEL 了。uuid 保证只删自己的；Lua 保证"校验+删除"原子，不被中间插入。
锁过期时间设多少？业务没跑完怎么办？
宁大勿小易死锁，宁小勿大易并发。正解是看门狗自动续期：业务在跑就不断续，掉线就停止续期自然释放。
Redis 和 ZK 锁怎么选？
高并发、能接受极小概率双持 → Redis；金融级强一致、正确性优先 → ZK。也可 Redlock 折中（注意其争议）。

锁在进程内、数据库和分布式层级的整体分类见锁体系总览。延伸阅读：Redis 分布式锁实现详解 · 分布式缓存与三大问题 · ZooKeeper 详解

第一层 · 概念与判定：三种方案怎么选

一句话判据：要性能选 Redis，要强一致选 ZooKeeper/etcd，实在没有中间件才用数据库。

方案一致性性能什么时候用
Redis(SET NX PX)最终一致，主从切换可能丢锁最高（万级 QPS）绝大多数业务互斥场景
Redlock号称更强，但争议大中（要写多个实例）只有在对锁正确性要求极高且能接受复杂度时
ZooKeeper / etcd强一致（靠 ZAB / Raft + 临时顺序节点）中（千级 QPS）选主、强一致编排
数据库（唯一键 / for update）取决于 DB 隔离级别最低兜底，没有中间件时
  • 信号一：锁只是为了「防止重复处理」（如幂等、防止重复发券）→ Redis 足够，偶尔失效可接受。
  • 信号二：锁错了会造成资金或数据损坏 → 上 ZooKeeper/etcd，或用 DB 行锁 + 版本号。
  • 信号三：锁的持有时间很短（毫秒级）→ Redis；持有时间长（秒级以上）→ 必须考虑续租。

最常见的认知错误：以为 Redis 分布式锁是「绝对互斥」的。它在主从异步复制下会失效——主节点写完锁后宕机、从节点提升为主但锁未同步，第二个客户端就能再拿到锁。

第二层 · 参数·命令·量化：正确加锁与释放

Redis 分布式锁正确写法

# 正确加锁：一条命令完成「设值 + 过期」，原子
SET lock:order:123 <random_value> NX PX 30000
# NX = 仅当不存在才设置；PX 30000 = 30 秒过期（毫秒）
# <random_value> 必须全局唯一（UUID），用于释放时校验「是我的锁」

# 正确释放：必须用 Lua 保证「判断 + 删除」原子
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end

# 错误示范（千万别这么写）：
# SETNX lock 1 ; EXPIRE lock 30     —— 两步非原子，SETNX 后崩溃会导致锁永不释放
# GET lock → 判断是自己的 → DEL    —— 两步非原子，可能删掉别人刚获得的锁
参数建议值说明
锁过期时间 PX业务最大耗时的 2～3 倍太短会提前释放，太长故障后恢复慢
valueUUID / 雪花 ID释放时校验归属，防止误删别人的锁
续租间隔过期时间的 1/3看门狗机制，业务没跑完时续期
重试间隔10～100ms 加随机抖动避免大量请求同时抢锁造成惊群
Redlock 实例数5 个独立主节点需 N/2+1（即 3 个）成功才算拿到锁

量化参考：单机 Redis 加解锁约 0.1～0.3ms，理论 QPS 可达数万；但实际受网络 RTT 与客户端并发数限制，通常按 5000～20000 QPS 规划。

第三层 · 排障与边界：锁超时与误删

现象原因怎么查 / 怎么办
锁超时了业务还没跑完过期时间设短了，或业务偶发变慢加看门狗续租；或业务末尾再校验一次锁归属
A 的锁被 B 删了释放时没校验 value，直接 DEL必须用 Lua 脚本比对 value
主从切换后两个客户端都拿到锁异步复制，锁未同步到从节点接受它（业务幂等兜底），或换强一致中间件
抢锁 QPS 很高但成功率低大量请求同时重试重试加随机退避；或改用队列串行化
GC 停顿导致锁被别人拿走STW 期间无法续租Redlock 争议点之一；或改用有 fencing token 的方案
  • 排查顺序：先看锁的过期时间是否覆盖业务耗时 → 再确认释放用了 Lua → 再看是否有主从切换 → 最后看 GC/网络抖动。
  • 边界一：SETNX + EXPIRE 两条命令不是原子的，必须用 SET ... NX PX 一条命令。
  • 边界二：Redlock 依赖多个独立的 Redis 主节点（不是同一集群的分片），且要求各节点时钟不能有大的跳跃。
  • 边界三：即使用了 Redlock，GC 停顿或时钟回拨仍可能出问题——Martin Kleppmann 的著名批评就在这点；fencing token（单调递增令牌）才是严格解法。

第四层 · 原理与取舍：Redlock 为什么有争议

Redlock 的思路是「在 N 个独立节点上抢锁，拿到多数就算成功」，以此规避单点与主从切换问题。但 Martin Kleppmann 指出：它依赖「时钟大致正确」这一隐含假设，而 GC 停顿、时钟回拨、网络延迟都可能破坏它，导致两个客户端同时认为自己持有锁。

方案正确性性能复杂度适用
单 Redis + 随机 value基本可用（主从切换有风险）高低90% 场景
Redlock在时钟可靠时才更强中高要求极高且不信任单实例
ZooKeeper 临时顺序节点强（ZAB 保证）中中选主、严格互斥
etcd + Lease强（Raft 保证）中中K8s 生态首选
DB 行锁 + 版本号取决于隔离级别低低兜底 / 已有 DB
锁失效了会怎样，一定要上 Redlock 吗？

不必。绝大多数业务里，锁只是「降低并发冲突概率」的优化，真正的正确性靠业务层幂等或数据库唯一约束 / 乐观锁版本号兜底。锁偶尔失效时，兜底机制会拦住。

fencing token 是什么？

每次加锁返回一个单调递增的令牌，资源侧记录见过的最大令牌，拒绝更小令牌的写请求。这样即使客户端「以为自己还持有锁」（实际已过期被别人拿走），它的写也会被资源侧拒绝——从服务端堵住问题，而不依赖客户端的锁正确性。

为什么 ZooKeeper 的锁更可靠？

因为它是强一致 + 会话感知的：客户端与 ZK 的 session 断开后，临时节点自动消失，锁自动释放，不存在「客户端卡住导致锁长期不释放」的问题；且写入经过 ZAB 多数派确认，不会出现主从异步复制丢锁的情况。

核心速览

一句话在多进程之间就「谁现在能操作这个资源」达成互斥
必做三件事加锁带唯一标识、解锁只解自己的、锁必须有过期时间

一、正确的加锁与解锁

# 加锁：NX 保证互斥，PX 保证不会死锁 SET lock:order:123 <uuid> NX PX 30000 # 为什么 value 必须是随机唯一值？ # 因为解锁时要确认「这把锁是我加的」。 # 如果 A 的锁超时被 B 抢走，A 再来解锁就会误删 B 的锁。 # 解锁必须用 Lua 保证原子（比较和删除不能分两步） if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end # 错误示范：先 GET 判断再 DEL # 两步之间有窗口，可能删掉别人的锁

二、锁超时了业务还没跑完怎么办

这是分布式锁最难的问题。一旦业务执行超过 TTL，锁自动释放，另一个进程就能进来，互斥被破坏。

方案做法优点缺点
续期（看门狗）业务线程另起一个定时任务，快到期就延长 TTL主流做法（Redisson 的 watchdog）客户端宕机后要靠 TTL 兜底
设足够长的 TTL按业务 P99 耗时的几倍设置简单客户端宕机后锁要等很久才释放
业务侧兜底用数据库乐观锁/唯一索引做最后防线真正可靠要改业务逻辑
只锁短操作把长事务拆短，只锁关键的一小段最干净需要重新设计流程
最该记住的一条

分布式锁只能提供性能层面的互斥，不能提供正确性保证。要保证数据正确，必须在存储层用唯一索引、乐观锁（版本号）、状态机兜底。锁只是减少冲突、降低数据库压力的手段。

三、Redis 单节点 vs Redlock

单实例 / 主从 + LuaRedlock（多实例）
实现简单要向 N 个实例依次加锁，多数派成功才算
性能高低（N 次往返）
主从切换时可能失效：主加锁后未同步就挂了理论上更安全
争议无有著名争议（Martin Kleppmann 的批评）
工程建议绝大多数场景够用 + 业务兜底只在无法加业务兜底时用

Redlock 的争议核心：它依赖「多个独立实例的时钟大致同步」，而时钟不可靠（GC 停顿、时钟回拨、网络延迟）会导致锁失效。Martin Kleppmann 的著名批评指出，与其依赖锁，不如用fencing token——每次加锁返回一个单调递增的 token，存储层拒绝处理更旧 token 的请求。

四、可重入与公平性

可重入同一个线程可以多次获取同一把锁，需要计数（Redisson 用 hash 结构实现）
公平锁按请求顺序排队，避免饥饿；代价是性能下降
读写锁读共享、写独占，适合读多写少
自旋 vs 阻塞自旋适合极短等待，阻塞适合长等待（用 Redis 的 Pub/Sub 通知）

五、深入自检

为什么不能用 SETNX + EXPIRE 两条命令？

因为加锁成功但还没来得及设过期时间时进程崩溃，这把锁就永远不会被释放（死锁）。必须用一条原子的 SET ... NX PX。

主从切换时锁真的会失效吗？

会。主节点加锁成功后，数据还没同步给从节点主就挂了；从节点提升为主，没有这把锁的记录，另一个客户端就能加锁成功。这是 Redis 异步复制的固有代价。

fencing token 怎么用？

加锁时返回一个递增的序号，业务请求带上这个序号；存储层记录已处理的最大序号，遇到更小的就拒绝。这样即使锁失效，旧持有者的请求也不会破坏数据。这是唯一能保证正确性的方案。

锁的粒度怎么定？

尽量小。锁「订单 123」而不是锁「所有订单」。粒度越细，并发度越高，冲突越少。但要避免过细导致锁数量爆炸和复杂度上升。

用 etcd / ZooKeeper 会更好吗？

一致性更强（基于 Raft/ZAB），支持临时节点与顺序节点，天然解决「客户端宕机锁不释放」的问题。代价是性能低于 Redis、运维更复杂。对一致性要求高的场景（如选主）优先选它们。

记住一句锁只管性能，正确性靠存储层兜底
加锁三要素NX + PX + 唯一 value
解锁必须Lua 校验后删
超时对策看门狗续期 + 业务兜底
