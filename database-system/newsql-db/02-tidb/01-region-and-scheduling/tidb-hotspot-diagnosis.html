TiDB 热点 Region 诊断：写入打散、读倾斜与定位路径

一句话总结：TiDB 里最常见的一类性能问题不是 SQL 写得差，而是数据分布不均——所有写入挤在一个 Region、或者查询全打到某几个节点。Region 是 TiDB 调度的最小单位，理解「Region 怎么切、怎么搬、怎么判断热」是运维分布式库的基本功。

01Region 是什么：一条数据从哪里开始切

TiKV 把整个 key 空间按范围切成一段段 Region（默认大小在几十 MB 到近百 MB 量级，具体以版本文档为准）。每个 Region 是一个 Raft 组，有自己的 leader；PD 负责把 Region 的副本摆在不同机器上，并在负载不均时调度搬移。

概念是什么为什么要关心
Regionkey 范围的一段，Raft 组的基本单位分裂、迁移、热点的最小粒度
LeaderRegion 内负责读写的主副本读写都打在 leader 上，leader 分布决定负载均衡
Peer / 副本Region 的其他副本（默认 3 副本）副本位置决定容灾与读延迟
PD集群元信息与调度中心Region 分裂/迁移/打散的决策者
Store一个 TiKV 实例Region 在各 Store 间的分布决定磁盘与 CPU 是否均衡
要点：Region 太小 → 元数据与心跳开销大；太大 → 调度粒度粗、迁移慢。别手动频繁调这个默认值，除非有明确的诊断结论。

02三类热点：写入、读取、Region 本身

自增主键导致写入集中在最后一个 Region，是 TiDB 最典型的写热点
热点类型典型成因现象处理方向
写热点自增主键、按时间递增的索引某个 Region 写入量远高于其他；PD 无法靠分裂缓解（分裂后新的仍是最右）改主键分布：AUTO_RANDOM、UUID、雪花 ID；或用 SHARD_ROW_ID_BITS 打散
读热点小表被高频访问、某段 key 被集中扫描个别 Region 读 QPS 极高小表走缓存；Region 打散；考虑副本读分摊
Region 热点Region 内 key 过多、副本集中在一组机器调度频繁、某些 Store 磁盘/CPU 明显偏高检查 PD 调度是否被限流，检查副本放置约束
-- 建表时预先打散：避免「刚建的表只有一个 Region，导入全挤在上面」
CREATE TABLE orders (
  id   BIGINT PRIMARY KEY /*T![auto_rand] AUTO_RANDOM(5) */,
  uid  BIGINT NOT NULL,
  ctime DATETIME NOT NULL
) SHARD_ROW_ID_BITS = 4 PRE_SPLIT_REGIONS = 3;

-- 说明：
--   AUTO_RANDOM(5)        把自增主键换成随机分布，写入不再集中到最右 Region
--   SHARD_ROW_ID_BITS = 4 把行 ID 的高位打散（16 个分片）
--   PRE_SPLIT_REGIONS = 3 建表时就预先切好 Region，避开导入初期的单点

-- 注意代价：随机主键会损失范围扫描的局部性，
--          按主键范围查会变成跨 Region 扫描
要点：AUTO_RANDOM 换来的是写入分散，代价是主键范围查询变散。如果你的查询大量按主键范围扫，改用「业务前缀 + 随机后缀」的复合主键往往更平衡。

03怎么查：热点与倾斜的定位路径

  1. 先确认是不是热点：看各 Store 的 CPU / 磁盘 / QPS 是否明显不均，还是整体都高（整体高是容量问题，不是热点）。
  2. 定位到 Region：查热点 Region 列表，看读写流量集中在哪些 Region、属于哪张表。
  3. 关联到表与索引：Region 的 key 范围可以反推属于哪个表/索引；确认是主键还是二级索引造成的。
  4. 看执行计划：确认查询是否走了索引、是否有全表扫、估算行数与实际是否差很多。
  5. 决定动作：改主键 / 打散 / 手工分裂 / 调调度参数 / 加机器，按结论选。
-- ① 看热点 Region（系统表/监控项的名称随版本变化，以文档为准）
SELECT * FROM information_schema.tidb_hot_regions
  WHERE type = 'read' ORDER BY max_hot_degree DESC LIMIT 20;

SHOW TABLE orders REGIONS;             -- 看某张表的 Region 切分与分布

-- ② 看 Region 分布是否倾斜
SELECT store_id, COUNT(*) AS region_cnt
  FROM information_schema.tikv_region_status
  GROUP BY store_id ORDER BY region_cnt DESC;

-- ③ 看执行计划与真实行数（估算偏差大往往是统计信息过期）
EXPLAIN ANALYZE SELECT * FROM orders WHERE uid = 1001;
SHOW STATS_HEALTHY WHERE db_name='app' AND table_name='orders';   -- 健康度低就先 ANALYZE
ANALYZE TABLE orders;
要点：EXPLAIN ANALYZE 与 EXPLAIN 不是一回事：后者看优化器的估算，前者看实际执行。热点排查一定要用 ANALYZE 版本。

04运维边界：这些事别乱做

  • 不要频繁手工调 Region 大小：它是全局参数，改动影响整个集群的调度行为。
  • 不要在业务高峰做大规模 Region 迁移：PD 的调度会占用网络与磁盘 IO，通常要设调度窗口/限流。
  • 不要忽视统计信息：统计信息过期会让优化器选错索引，表现出来像「热点」，实际是计划错误。
  • 不要只加机器：如果热点源自自增主键，加机器只是让更多机器看着那一个 Region 忙。
  • 不要在没有基准的情况下调 PD 调度参数：先记录当前指标，一次只改一个参数。
  • 大导入要分批：单批写入量过大容易触发限流与写 stall，也加剧单点 Region 压力。

05常见疑问

问：为什么 PD 不自动把热点 Region 分裂开？

PD 会分裂 Region，但对自增主键场景无效：分裂后新写入依然落在「当前最大 key 所在」的那个 Region，热的是「最右端」这个位置，不是某个固定 Region。所以必须从主键分布上解决。

问：AUTO_RANDOM 和 UUID 主键哪个好？

AUTO_RANDOM 仍是 8 字节整型，索引与存储更紧凑，且保持一定局部性；UUID 是 36 字节字符串，索引膨胀明显、写入放大。优先 AUTO_RANDOM 或雪花 ID，UUID 作为跨系统全局 ID 更合适。

问：加了机器还是慢，一定是热点吗？

不一定。先排除三类：① 执行计划错误（统计信息过期）；② 单机资源瓶颈（CPU/磁盘 IO 打满）；③ 跨地域访问（读写跨了机房）。确认都不是，再看 Region 分布。

问：小表会被高频读成热点吗？

会，而且很常见——配置表、字典表被上万 QPS 读，一个 Region 扛不住。这类数据应该在应用侧缓存，而不是靠数据库打散，因为它根本不需要分布式能力。
