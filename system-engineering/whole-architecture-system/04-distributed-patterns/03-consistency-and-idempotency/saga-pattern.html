Saga 流程 Saga

正向一步步提交，失败则按相反顺序补偿

分布式事务无法用单库 ACID。Saga 把『大事务』拆成多个本地事务，每个都有对应的补偿操作(Tᵢ')。正向全成功则完成；某步失败则按逆序执行已完成步骤的补偿，回滚到一致状态。

面试高频问答

Q：Saga 能保证强一致吗？
A：不能，它是<b>最终一致</b>。补偿执行期间系统处于中间态，业务要能接受（如『已扣库存、支付失败、库存回补中』）。需要隔离级别与幂等配合。
Q：补偿操作和回滚一样吗？
A：不一样。补偿是『反向业务操作』（如退票而非撤销数据库），要考虑原操作已产生的外部副作用，且补偿本身也要幂等。

Saga：长事务的补偿式解法

在微服务里，一个业务动作常常横跨多个服务（下单 → 扣库存 → 支付 → 发券 → 通知）。用分布式事务（XA/2PC）强一致，会把所有服务绑在同一把锁上，吞吐极低且任一服务不可用就全盘阻塞。Saga 换了个思路：把长事务拆成一串本地事务，每个都有对应的补偿动作；正向全成功即完成，任何一步失败就反向执行前面各步的补偿，从而保证最终一致。

Saga 正向执行与反向补偿：T4 失败触发 C3 → C2 → C1

补偿设计的核心难点

① 隔离性缺失（最本质的问题）

Saga 只保证最终一致，不提供隔离。在 T2 已完成、C2 未执行的窗口里，其他事务可能读到「已被扣减但即将回滚」的库存——这就是脏读。

  • 应对：语义锁——在记录上加「冻结/处理中」标记，其他操作看到标记就拒绝或等待
  • 或设计上让中间状态对外不可见（先写待确认状态，完成后才发布）

② 补偿必须是幂等且可重试的

补偿本身也可能失败（网络、服务宕机），所以它必须能被反复调用直到成功。

  • 用幂等键 + 去重表保证不重复退款
  • 失败的补偿要进重试队列或告警人工介入，绝不能静默放弃

③ 补偿不是「物理撤销」

  • 扣款 100 的补偿是「退款 100」并生成退款流水，不是把原记录删掉
  • 已发出的短信无法撤回——这类步骤要么放最后，要么换成可撤销的动作
  • 所以流程设计时应把不可补偿的步骤尽量后置

④ 空补偿与悬挂

  • 空补偿：正向步骤实际没执行成功，补偿却被调用了 → 补偿要先检查正向是否成功
  • 悬挂：补偿先执行了，正向请求后到达并成功 → 需要记录补偿标记，拒绝迟到的正向
  • 两者都靠「事务状态记录表」解决：每步记录状态，补偿与正向都做状态校验

Saga vs TCC vs 本地消息表

方案一致性侵入性适用
Saga（补偿）最终一致中：每个服务要实现正向 + 补偿两个接口长流程、跨多服务、允许短暂不一致（下单、审批流）
TCC（Try-Confirm-Cancel）接近强一致（Try 阶段预留资源）高：每个服务要实现三个接口，且资源管理复杂资金、交易等要求高一致且需预留资源的场景
本地消息表 / 事务消息最终一致低：只需在本地事务里插一条消息记录单向通知类：下单后发通知、扣款后记积分
XA / 2PC强一致低（数据库层支持），但性能差同库多表或少数强一致场景；微服务下几乎不用

实践排序：优先「本地消息表」（最简单）→ 流程复杂时上「Saga」→ 资金强一致才考虑「TCC」。能用最终一致解决的，不要上强一致方案，因为后者的成本（性能、复杂度、可用性）高出一个数量级。

深入自检

Saga 能保证不出现中间状态被外部看到吗？

不能自动保证，这正是 Saga 与 ACID 事务的本质差别——它牺牲了隔离性（Isolation）。要缓解必须自己设计：① 语义锁，在执行的记录上打「处理中」标记，其他读写遇到该标记时拒绝或排队；② 状态机可见性控制，中间状态不对外暴露（如订单只有 PAYING/CONFIRMED，对外只展示 CONFIRMED）；③ 重要场景用 TCC 的 Try 阶段真正预留资源（冻结库存、冻结金额），使中间状态对外部也是自洽的。选择哪种取决于业务能否容忍「看到即将被回滚的数据」。

补偿失败了怎么办？

绝不能忽略。分级处理：① 自动重试（指数退避，重试到成功或达上限）；② 进入死信队列 + 告警，由运维/开发介入；③ 提供人工补偿工具（如手动退款入口）；④ 建立对账任务——定期比对各系统状态，发现不一致自动触发补偿或告警。对账是最后一道防线，任何分布式一致性方案都应该有它，因为理论上总有意料之外的边界情况。

编排模式下协调器挂了怎么办？

协调器本身必须持久化流程状态——每一步执行前后都要把状态写入数据库（这就是关键设计）。协调器重启后从持久化状态恢复，继续推进或补偿未完成步骤。所以选编排框架时，「状态持久化 + 恢复能力」是硬指标（Temporal、Camunda 都具备）。如果协调器无状态且流程状态只存在内存里，那它一挂整个流程就丢了，这是不可接受的。

为什么微服务下几乎不用 XA/2PC？

三个原因：① 可用性差——2PC 是阻塞协议，协调者宕机时参与者会一直持有锁等待，整个链路不可用；② 性能差——锁持有时间是整个事务时长（跨服务网络往返），吞吐下降一个数量级；③ 技术栈限制——要求所有参与者都支持 XA 协议，而很多 NoSQL、消息队列、第三方服务不支持。所以微服务架构普遍转向「最终一致 + 补偿」，用可用性和性能换取短暂的不一致窗口，并通过幂等、对账、人工兜底把风险控制在可接受范围。
