先建立直觉：两代产品的迭代

Guava Cache 是 Google Guava 库里的本地缓存，API 设计优雅（CacheBuilder、LoadingCache），多年来是 Java 本地缓存的事实标准。

Caffeine 由 Guava Cache 的原作者之一重写，API 几乎兼容 Guava，但内部算法换成了 W-TinyLFU，并改为异步淘汰，命中率和吞吐都显著更好。

结论先行：新项目直接选 Caffeine；老项目从 Guava 迁移到 Caffeine 成本很低（换包名 + 少量 API 调整）。

核心能力（两者都支持）

能力说明
容量限制maximumSize（条目数）或 maximumWeight（按权重，如字节数）
过期策略expireAfterWrite（写后过期）、expireAfterAccess（访问后过期）
自动加载LoadingCache：miss 时自动调用 CacheLoader 回源
软/弱引用允许 GC 回收（Guava 支持，Caffeine 也有对应 API）
移除监听removalListener：淘汰/失效时回调（可用于关闭资源）
统计recordStats()：命中率、加载次数、淘汰数

典型用法（Caffeine）

Cache<Long, User> cache = Caffeine.newBuilder()
    .maximumSize(10_000)                  // 容量上限
    .expireAfterWrite(5, TimeUnit.MINUTES) // 写入后 5 分钟过期
    .recordStats()                         // 开启统计
    .removalListener((k, v, cause) -> log.info("removed {}, cause={}", k, cause))
    .build();

// 方式一：显式查
User u = cache.getIfPresent(id);

// 方式二：自动加载（miss 时回源，且同一 key 只回源一次）
User u2 = cache.get(id, id -> userMapper.selectById(id));
cache.get(key, loader) 是最推荐的用法。它天然提供了加载保护——同一个 key 并发 miss 时只有一个线程真正回源，其他线程等待复用结果，这正好解决了缓存击穿。手写 getIfPresent + 手动回源就没有这个保护。

Caffeine 强在哪里

维度Guava CacheCaffeine
淘汰算法LRU（分段）W-TinyLFU（频次准入 + LRU 淘汰）
命中率良好更高，尤其在混合负载下
淘汰执行与写操作同步进行，有停顿异步交给线程池，读写不阻塞
并发分段锁（类似 ConcurrentHashMap）无锁读路径 + 环形缓冲，吞吐更高
维护状态稳定，新特性少持续维护，支持异步 AsyncCache

W-TinyLFU 为什么命中率更高

两个组件各解决一个经典盲区：
• TinyLFU 准入解决 LRU 的批量扫描污染——扫描来的数据频次只有 1，PK 不过缓存里的热数据，被挡在门外。
• Window 区解决 LFU 的新数据饥饿——新数据先在小 Window 里积累热度，不直接和大缓存里的老数据比频次。

选型建议

  • 新项目：直接用 Caffeine。
  • 已在用 Guava Cache：建议迁移到 Caffeine，API 高度相似，通常只需改 import 和 CacheBuilder → Caffeine.newBuilder()。
  • Spring Boot 用户：Spring 5+ 已把 Caffeine 作为默认的本地缓存实现，通过 spring.cache.type=caffeine 即可启用。

🎯 面试问答

Q：Caffeine 能完全替代 Guava Cache 吗？
A：在缓存场景基本可以，且通常更好。Caffeine 的 API 设计刻意与 Guava 保持高度相似，迁移通常只改包名和 builder 入口。需要注意的差异：① Caffeine 的 removalListener 是异步执行的（Guava 是同步）；② 部分不常用的 API（如 asMap 的某些视图行为）细节不同；③ Caffeine 不支持 Guava 的软引用/弱引用组合中的某些冷门配置。迁移后建议跑一遍基准验证。

Q：W-TinyLFU 比 LRU 好在哪，代价是什么？
A：好处：命中率明显更高，尤其在「有明显热点 + 偶尔批量扫描」的混合负载下；抗扫描污染能力强。代价：需要额外维护 Count-Min Sketch（极小内存，通常是 KB 级）和 Window 区，实现复杂度高于纯 LRU。但这个代价对用户是透明的——你只是换了个依赖，不需要自己实现算法。

Q：maximumSize 和 maximumWeight 怎么选？
A：如果缓存对象大小接近，用 maximumSize（按条目数），简单直观。如果大小差异很大（有的几百字节、有的几 MB），必须按权重限容，否则可能 10 万条里混入几千条大对象就把内存撑爆。用法：.maximumWeight(...).weigher((k,v) -> 估算字节数)。

Q：为什么推荐用 cache.get(key, loader) 而不是手动回源？
A：因为前者自带加载保护：同一个 key 并发 miss 时，只有一个线程真正回源，其余线程等待并复用结果。手动写 getIfPresent → 为 null → 查库 → put 在高并发下会让所有线程都去查库，正是缓存击穿。此外 get(key, loader) 还能自动处理「回源返回 null」（默认不缓存）和异常传播。
