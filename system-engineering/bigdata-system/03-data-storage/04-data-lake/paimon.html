流式 Lakehouse · LSM

Apache Paimon 深度解析

Paimon（原 Flink Table Store）把流计算与数据湖合二为一：用 LSM 树（SST + 日志）组织数据，既能像消息流一样实时更新、产出 changeloll，又能像表一样做批式分析。它是「流式数仓 / 流式湖仓」的新选择。

1它站在哪一层

Paimon 是表格式，但比 Iceberg/Hudi 更「流式原生」：数据落盘就用 LSM 结构，实时写入与实时读取都围绕 changelog 展开。

  • 实时 upsert 友好：主键表用 LSM 的 merge 能力，高频更新不退化成全量重写。
  • Changelog 产出：可作为流式作业的「物化结果 + 变更流」，下游直接消费 binlog 式变更。
  • 流批一体：同一张表，流式写、批式读，避免 Lambda 架构双写。
出身Paimon 由 Flink 社区孵化（原名 Flink Table Store），因此与 Flink 集成最深，也能被 Spark / Trino / StarRocks 读取。

2核心：LSM 表结构

主键表的存储借鉴 LSM-Tree：写入先进内存 memtable，flush 成有序的 SST 文件；后台 compaction 合并分层（L0→Ln），查询时多版本合并取最新。

写入经 memtable → SST，后台 compaction 分层，读时多版本合并取最新

3两种表：主键表 vs 仅追加表

类型主键表（PrimaryKey）仅追加表（Append）
用途变更频繁、需 upsert/去重日志、事件等只追加
底层LSM（SST + 合并）列式 Orc/Parquet
Changelog可产出 INSERT/UPDATE/DELETE仅 INSERT
典型维表、订单、用户画像埋点、审计日志
-- 主键表：实时 upsert，并对外暴露 changelog
CREATE TABLE dim_user (
  uid BIGINT, name STRING, ts BIGINT,
  PRIMARY KEY (uid) NOT ENFORCED
) WITH (
  'merge-engine' = 'deduplicate',   -- 同 key 去重/取最新
  'changelog-producer' = 'input');    -- 产出完整变更流

4Changelog 与流式数仓

changelog-producer 让主键表在写入时顺便产出规范的 changelog（INSERT/UPDATE_BEFORE/UPDATE_AFTER/DELETE）。下游 Flink 作业可把它当「物化表 + 实时变更流」消费，实现流批一体：一份存储同时服务实时计算与离线分析。

与 Hudi 增量查询的区别Hudi 的增量是「时间区间的文件差异」；Paimon 的 changelog 是「按 key 的完整行级变更」，更适合驱动下游状态精确更新（如宽表、物化视图）。

5运维要点

🧱 Compaction

LSM 必须定期合并 SST（full compaction / 分区级），否则读放大与 changelog 膨胀。流式写入可开启 auto-compaction。

🔑 分区与桶

用 bucket 做分桶以并行 upsert；桶数过小会热点、过大则小文件多。

⏱️ 快照清理

配置 snapshot 保留与 tag，兼顾时间旅行与存储成本。

写入吞吐 vs 读放大LSM 的随机写很强，但读要合并多层 SST；compaction 跟不上写入时，读延迟与 changelog 体积会恶化，需要按写入速率调桶数与 compaction 资源。

6与 Iceberg / Hudi 的取舍

三者都属 Lakehouse 表格式，但 Paimon 偏「流式 + changelog」。详见格式对比。

维度PaimonHudiIceberg
底层结构LSM文件 + 索引manifest 元数据
流式 changelog最佳增量查询弱
生态绑定偏 Flink偏 Spark最中立
典型场景流式数仓、实时维表CDC 入湖大规模分析
选型捷径已用 Flink 做流计算、想要「流批一体 + changelog 物化」→ Paimon；做 CDC 近实时数仓（Spark 生态）→ Hudi；跨引擎超大规模分析 → Iceberg。

第一层 · 概念与判定：Paimon 是什么

Apache Paimon 是流批一体的湖表格式，底层基于 LSM 结构，既能当批表用 SQL 查，又能作为流式 changelog 源被 Flink 实时消费。对比 Iceberg/Hudi（偏向批/列式 MVCC），Paimon 的强项是主键表的实时更新与流读。

表类型特点适合
主键表（PK）按 key 更新/删除，LSM 合并CDC、维表、状态
追加表（Append）只追加，不可更新日志、埋点

一句话判定：要「流式更新 + 流式读取 changelog」用 Paimon；纯离线批分析、和 Spark 生态强绑定可选 Iceberg。

第二层 · 参数·命令·量化：桶与合并

参数含义建议影响
bucket分桶数（并行单位）按数据量定过小倾斜、过大小文件
bucket-key分桶字段高基数列影响倾斜
merge-engine合并策略deduplicate/partial更新语义

snapshot.num-retained快照保留按合规存储空间

Paimon 主键表定义与流读

-- 建主键表：按 user_id 分桶，按主键去重更新
CREATE TABLE ods.user_profile (
  user_id BIGINT,
  name STRING,
  updated_at TIMESTAMP,
  PRIMARY KEY (user_id) NOT ENFORCED
) WITH (
  'bucket' = '8',                 -- 桶数，决定并行度与文件数
  'merge-engine' = 'deduplicate',
  'changelog-producer' = 'input',  -- 产出 changelog 供下游流读
  'snapshot.num-retained.min' = '5'
);

-- 流式写入（Flink）
INSERT INTO ods.user_profile
SELECT user_id, name, updated_at FROM kafka_cdc_source;

-- 流式读取 changelog（下游实时消费增删改）
SELECT * FROM ods.user_profile /*+ OPTIONS('scan.mode'='changelog') */;

数量级：每个 bucket 是一个 LSM 树，桶数 ≈ 写入/流读的并行度；桶太少单桶过大、Compaction 慢，太多则小文件泛滥。经验上单桶数据量控制在若干 GB 量级。

第三层 · 排障与边界：高频坑

踩坑清单：

  • 桶倾斜：bucket-key 选了低基数列，数据集中到少数桶，读写热点
  • 小文件爆炸：高频小批写入，LSM 层级文件过多，读放大、Compaction 跟不上
  • Compaction 滞后：更新延迟高、点查变慢，需调 compaction 线程与触发阈值
  • changelog 产出模式错：用 none 却做流读，拿不到正确的 -U/+U 更新行
  • 快照没清理：retained 设太大，存储被历史快照吃满
  • Flink 版本不兼容：Paimon 对 Flink 版本敏感，升级要查兼容矩阵

排查顺序：① 看各 bucket 文件大小分布是否均匀；② 查 Compaction 任务是否堆积；③ 确认 changelog 模式与下游读取方式匹配。

第四层 · 原理与取舍

Paimon 和 Iceberg 本质区别在哪？

Iceberg 用列式 MVCC + 快照清单，擅长大规模离线批读、隐藏分区演进；Paimon 用LSM-Tree，天然适合主键的实时 upsert 与按 key 的点查，并且能直接以流的形式吐出 changelog给下游 Flink 消费。简单说：要 CDC 实时入湖并流读，Paimon 更顺；纯离线分析 Iceberg 生态更成熟。

为什么主键表更新要用 LSM 而不是覆盖文件？

传统列式格式更新一行要重写整个文件，成本不可接受。LSM 把更新追加成新记录，读时再合并（merge-on-read），写入是顺序 IO、极快；代价是读路径要做合并、需要后台 Compaction 收尾。

changelog-producer 为什么重要？

下游如果是流作业，需要精确的「这行被删了/被改成 X」才能正确更新状态。若用 'none'，Paimon 只能从快照差算 changelog，可能丢失中间更新；设 'input' 则在写入时直接记录变更，下游拿到的是完整且有顺序的增删改流。
