迭代器与生成器

for 循环、列表推导、sum() 全都建立在「迭代协议」之上。生成器用 yield 把「一次性算完」变成「要一个算一个」——这是处理大文件、无穷序列、流式数据的核心武器。

迭代协议

可迭代对象 ≠ 迭代器

可迭代对象（iterable）有 __iter__，调用它返回一个迭代器；迭代器（iterator）额外有 __next__，每调用一次吐出下一个值，没了就抛 StopIteration。

📜
Iterable
str / list / dict / set / tuple / range / 文件对象；能放进 for
👉
Iterator
有状态的「游标」，记住走到哪了；只能前进不能回退
s = "abc"
it = iter(s)        # 可迭代 → 迭代器（调用 __iter__）
print(next(it))    # a
print(next(it))    # b
print(next(it))    # c
print(next(it))    # StopIteration 异常
判断技巧：迭代器一定是可迭代的（它也有 __iter__ 且返回自身），但可迭代对象不一定是迭代器。用 iter(x) is x 可区分。list 的迭代器是独立的 list_iterator 对象。
for 底层

for 循环就是「不断 next 直到 StopIteration」

手写 for 的等价展开，能看清协议全貌。for x in obj 实际是：先 it = iter(obj)，再循环 next(it)，捕获 StopIteration 退出。

# 下面两段完全等价
for x in [1, 2, 3]:
    print(x)

# 手写等价版
it = iter([1, 2, 3])
while True:
    try:
        x = next(it)
    except StopIteration:
        break
    print(x)

所以任何对象只要实现了 __iter__（或老式 __getitem__），就能进 for 循环。这也是自定义容器「变成可迭代」的标准做法。

生成器

含 yield 的函数就是生成器

调用含 yield 的函数不会执行函数体，而是返回一个生成器对象；每次 next() 推进到下一个 yield 并「挂起」，保留所有局部状态。它是迭代器最方便的写法。

def countdown(n):
    while n > 0:
        yield n        # 在这里暂停，返回值 n
        n -= 1

g = countdown(3)    # 没执行函数体，只拿到生成器
print(next(g))      # 3  （推进到 yield 3，暂停）
print(next(g))      # 2
print(list(g))      # [1]（把剩下的取完）
yield from 用于把另一个可迭代对象「逐个委托」出来，写嵌套生成器/递归生成器时很省事：yield from sub_gen 等价于 for x in sub_gen: yield x。
生成器表达式

把方括号换成圆括号就「懒」了

列表推导 [x for x in ...] 一次性生成整个 list；生成器表达式 (x for x in ...) 返回一个生成器，元素按需产生，不占额外内存。

lst = [i*i for i in range(1000000)]   # 立刻生成 100 万个元素
gen = (i*i for i in range(1000000))   # 只占一个对象

print(sum(gen))   # 流式累加，内存几乎不变

# 链式管道：每个环节都是惰性生成器
lines = (line.strip() for line in open("big.log"))
errs  = (l for l in lines if "ERROR" in l)
for e in errs: print(e)   # 一行行处理，不把整文件读进内存
⚠️ 生成器是「一次性」的：取完就没了，不能二次遍历。需要多次遍历就转成 list，或重新创建生成器。
为什么省内存

惰性 = 不必把所有数据同时放在内存里

生成器适合三种场景：数据量极大、无限序列、流水线处理。它和异步里的协程思想同源——都是「每次只取一步」，只是前者为了省内存，后者为了不阻塞。

场景list 推导生成器
读 10GB 日志❌ 内存爆✅ 逐行流式
斐波那契无穷序列❌ 无法表示✅ yield 无限产出
多步数据清洗每步都建中间 list✅ 管道式惰性

生成器是「同步」的惰性计算；想要「并发地」产出值，就升级到异步生成器（async def + yield）。两者共享同一套「惰性产出」心智模型。

迭代器 vs 可迭代对象 vs 生成器

概念定义判断方法能否多次遍历
可迭代对象 Iterable有 __iter__()isinstance(x, Iterable)能（每次 iter() 给新的）
迭代器 Iterator有 __iter__() 和 __next__()—不能（一次性，走完就空）
生成器 Generator含 yield 的函数，是迭代器的一种inspect.isgenerator(x)不能

关系：list 是可迭代对象但不是迭代器（iter(list) 才得到迭代器）；生成器既是可迭代对象也是迭代器（所以它只能遍历一次）。这是最常见的认知误区。

迭代器协议

from collections.abc import Iterable, Iterator

lst = [1, 2, 3]
print(isinstance(lst, Iterable))    # True
print(isinstance(lst, Iterator))    # False   <- list 不是迭代器！

it = iter(lst)
print(isinstance(it, Iterator))     # True
print(next(it), next(it), next(it)) # 1 2 3
next(it)                            # StopIteration（for 循环就是靠它结束的）

gen = (x*x for x in range(3))
print(isinstance(gen, Iterator))    # True    <- 生成器是迭代器
print(list(gen))                    # [0, 1, 4]
print(list(gen))                    # []      <- ⚠️ 第二次是空的！已耗尽

# for 循环的等价展开
for x in obj:
    ...
# 等价于：
it = iter(obj)
while True:
    try:
        x = next(it)
    except StopIteration:
        break
    ...

生成器：yield 的双向通信

方法作用说明
yield x产出值并暂停保存现场（局部变量、指令位置）
next(g)恢复执行到下一个 yield—
g.send(v)恢复并把 v 作为 yield 表达式的值实现协程的核心
g.throw(e)在暂停处抛出异常—
g.close()关闭生成器内部抛 GeneratorExit
yield from x委托给另一个生成器比 for + yield 简洁且支持 send 透传

生成器通信

# ① 双向通信：send()（这是生成器能做协程的原因）
def accumulator():
    total = 0
    while True:
        x = yield total        # yield 表达式的值来自 send()
        if x is None: break
        total += x

g = accumulator()
next(g)                        # 必须先"启动"到第一个 yield（ priming ）
print(g.send(10))              # 10
print(g.send(20))              # 30
g.close()

# ② yield from：委托给子生成器（优雅地"扁平化"）
def chain(*iters):
    for it in iters:
        yield from it          # 等价于 for x in it: yield x，但支持 send/throw 透传

list(chain([1,2], [3,4]))      # [1, 2, 3, 4]

# ③ 实用模式：流式处理大文件（内存恒定）
def read_lines(path):
    with open(path) as f:
        for line in f:         # 文件对象本身就是迭代器，逐行读不占内存
            yield line.rstrip()

def grep(lines, pattern):
    for line in lines:
        if pattern in line:
            yield line

# 管道式组合：内存占用与文件大小无关
for line in grep(read_lines("huge.log"), "ERROR"):
    print(line)
# 处理 100GB 的日志，内存只占几十 KB

# ④ 带状态的生成器（替代类）
def counter(start=0):
    n = start
    while True:
        n += 1
        yield n

itertools 用法

from itertools import *

# ① 处理无限序列（这是 itertools 的核心价值）
list(islice(count(10, 2), 5))            # [10, 12, 14, 16, 18]
list(takewhile(lambda x: x < 20, count(10, 3)))   # [10, 13, 16, 19]

# ② 前缀和 / 累积（比手写循环快且清晰）
list(accumulate([1,2,3,4]))              # [1, 3, 6, 10]
list(accumulate([1,2,3], lambda a,b: a*b))  # [1, 2, 6]  阶乘

# ③ groupby：必须先排序！（最常见的坑）
data = [("a",1), ("b",2), ("a",3)]
# ❌ 没排序：同名不连续 -> 分成 3 组
for k, g in groupby(data, key=lambda x: x[0]): print(k, list(g))
#   a [('a',1)] / b [('b',2)] / a [('a',3)]   <- 'a' 出现了两组！

# ✅ 先排序
data.sort(key=lambda x: x[0])
for k, g in groupby(data, key=lambda x: x[0]): print(k, list(g))
#   a [('a',1), ('a',3)] / b [('b',2)]   ✅

# ④ 滑动窗口（Python 3.10+ 用 pairwise，或自己实现）
def window(it, n=2):
    its = tee(it, n)                      # 分裂成 n 个
    for i, x in enumerate(its):
        for _ in range(i): next(x, None)  # 第 i 个跳过 i 个
    return zip(*its)

list(window([1,2,3,4], 2))                # [(1,2), (2,3), (3,4)]

# ⑤ 扁平化嵌套
list(chain.from_iterable([[1,2],[3,4]]))  # [1, 2, 3, 4]

tee() 的内存陷阱：分裂出的迭代器会缓存中间结果。如果一个走得快、一个走得慢，缓存会无限增长——在无限序列上使用 tee 几乎必然 OOM。只在序列有限且差距不大时用。

深入自检

生成器表达式 vs 列表推导，什么时候用哪个？

判断标准：要不要复用结果。需要多次遍历、索引访问、len()、或修改 → 用列表推导；只遍历一次（尤其是传给 sum()/max()/any()/''.join() 这类聚合函数）→ 用生成器表达式，省内存且不慢。注意一个反直觉的点：sum(x for x in a) 比 sum([x for x in a]) 通常更快（不用建列表），但 sorted(x for x in a) 和 sorted([x for x in a]) 中列表版略快（sorted 需要知道长度，列表推导有优化）。

生成器只能遍历一次，怎么避免这个坑？

三个办法：① 重新创建——把生成器表达式写成函数（def gen(): return (...)），需要时重新调用；② 转列表——数据量可控时直接 list(gen)；③ 用 tee 分裂——但要警惕内存。最实用的习惯：函数返回生成器（而不是生成器对象），这样调用方可以多次迭代。另外调试时注意——生成器耗尽不会报错，只是静默返回空，这是最难排查的一类 bug。

yield from 相比 for + yield 好在哪？

三个层次：① 简洁——一行替代三行；② 性能——在 C 层面直接传递，避免 Python 层的循环开销（约快 20 – 40%）；③ 最重要的：完整透传——send()、throw()、close() 都能穿透到子生成器，而手写 for + yield 会吞掉这些交互。这也是 asyncio 的 await（底层就是 yield from 的思路）能正常工作的基础。PEP 380 引入它的主要动机就是重构生成器（把大生成器拆成小的而不破坏语义）。

为什么要有“先启动”这一步（priming）？

因为生成器函数调用时并不执行函数体，只是返回一个生成器对象——要第一次 next() 才会执行到第一个 yield 处暂停。所以在使用 send() 之前必须先 next(g) 或 g.send(None)（二者等价），否则会报 TypeError: can't send non-None value to a just-started generator。标准做法是用装饰器自动 priming，或用 next(g, None)。asyncio 的协程也是同样的机制——理解这个有助于理解 await 的暂停/恢复。

第一层 · 四个概念的关系

很多人把「可迭代 / 迭代器 / 生成器 / 生成器表达式」混为一谈。它们的关系其实很清晰：可迭代是协议，迭代器是状态机，生成器是迭代器的语法糖。

概念定义怎么判断是否惰性
Iterable（可迭代）有 __iter__()isinstance(x, Iterable)不一定
Iterator（迭代器）有 __iter__() 和 __next__()next(x) 能用是
Generator（生成器）带 yield 的函数（或生成器表达式）inspect.isgenerator是
生成器表达式(x for x in ...)—是
列表推导[x for x in ...]—否（一次性构造）
  • 关键区别：Iterable ≠ Iterator。列表是 Iterable 但不是 Iterator（没有 __next__）；对它调用 iter() 会返回一个新的迭代器。这是为什么列表可以遍历多次而生成器只能遍历一次。
  • 生成器是「一次性」的：遍历完后就耗尽了，再次 for 循环什么都没有。这是最常见的坑。
  • 生成器的核心价值：惰性求值——不预先构造整个序列，而是按需产生。这让处理超大数据（甚至无限序列）成为可能，且内存占用恒定。

第二层 · 用法、内存与性能数字

代码

import sys
N = 10_000_000

lst = [i*i for i in range(N)]
sys.getsizeof(lst) + sum(sys.getsizeof(i) for i in lst[:1000]) * (N/1000)

# —— 处理大文件：只能用生成器 ——
def read_lines(path):
    with open(path) as f:
        for line in f:      # 文件对象本身就是迭代器，【逐行读】不加载全文
            yield line.rstrip('\n')

# 管道式处理：全程不落地，内存恒定
total = sum(int(l) for l in read_lines('huge.log') if l.startswith('OK'))

# —— 无限序列 ——
def fib():
    a, b = 0, 1
    while True:
        yield a
        a, b = b, a + b

性能反直觉点：生成器比列表推导慢（每个 next 都有函数调用开销）。生成器的价值是省内存不是省时间。数据量小时用列表更快。

第三层 · 常见坑与排障清单

  • 生成器只能遍历一次（最高频坑）：遍历完就空了。若需多次遍历，要么转列表（list(gen)），要么用 itertools.tee 分流，要么把生成器函数改成可重复调用的函数（每次调用返回新生成器）。
  • StopIteration 在生成器内部被吞：Python 3.7+ 规定，生成器里的 StopIteration 会被替换成 RuntimeError（PEP 479）。这是为了防止隐式的迭代终止。自定义迭代器要用 return 而不是 raise StopIteration。
  • 闭包捕获循环变量的经典陷阱：[lambda: i for i in range(3)] 三个函数返回的都是 2（因为共享同一个 i）。解法：[lambda i=i: i for i in range(3)]（用默认参数绑定）。生成器延迟求值会让这个问题更隐蔽。
  • 生成器没被消费就不执行：gen = (process(x) for x in data) 这行什么都不做，只有迭代时才执行。所以「生成器里的错误不会在创建时暴露」。调试时容易困惑。
  • 在生成器里修改被迭代的列表：会导致跳过元素或无限循环。遍历时不要修改原容器（要改就遍历副本 list(lst)）。
  • send() 前必须先 next()：生成器创建后停在函数开头，还没到 yield，直接 send 会报 TypeError: can't send non-None value to a just-started generator。
  • groupby 需要先排序：它只按连续的相同元素分组。要做全局分组必须先 sorted()。
  • 大文件读取忘记用生成器：f.readlines() 会把整个文件读进内存。直接 for line in f 即可（文件对象是迭代器）。
  • 生成器里的资源没关闭：生成器被提前放弃（如 break）时，finally 要等 GC 才执行。确定性的清理要用 contextlib.closing 或显式 close()。

第四层 · 原理与取舍

生成器的本质：一个可以暂停和恢复的函数。理解它的两个机制——暂停点在哪和状态存在哪——就理解了全部行为。

  • 暂停点：每次执行到 yield 时，函数暂停并把值返回给调用者，但整个栈帧被保留。下次 next() 时从 yield 之后继续执行，所有局部变量的值都还在。这就是「有状态迭代器」的实现方式——你不需要手写 self.index 之类的状态字段，函数的栈帧本身就是状态。
  • 为什么比手写迭代器类简单：手写迭代器要维护 __iter__、__next__、StopIteration、以及所有中间状态。生成器让编译器帮你做这些——yield 自动处理暂停/恢复，函数自然返回时自动抛 StopIteration。代码量通常少一半以上。
  • 代价一：一次性。因为状态在栈帧里，耗尽后无法重置。要重复用就得重新调用函数。
  • 代价二：无法随机访问。生成器只能向前，不能 gen[5] 或 len(gen)。需要索引/长度时只能用序列。
  • 代价三：性能略慢。每次 next() 是一次函数调用 + 栈帧恢复。数据量小时列表更快（列表推导是专门的 LIST_APPEND 字节码，高度优化）。
  • 协程的基础：yield 能接收值（x = yield），这让生成器变成了双向的。Python 的 async/await 协程最初就是用生成器实现的（现在有独立的协程对象，但语义一脉相承）。理解生成器是理解 asyncio 的前提。

生成器到底省的是什么？为什么它反而更慢？

省的是内存，不是时间。内存上：列表要同时持有 N 个元素（N 个指针 + N 个对象），生成器只需要一个栈帧（约 100~200 字节），与数据量无关——这是数量级的差异，处理 1000 万条数据时可能是 400MB vs 200 字节。时间上：生成器更慢，因为每产生一个值都要：保存栈帧 → 返回 → 调用者处理 → 恢复栈帧，这是一次完整的函数调用开销；而列表推导用的是专门优化的字节码（LIST_APPEND），直接在循环里追加，没有函数调用。实测生成器通常比列表推导慢 20~50%。所以选择标准很清楚：数据量小、要多次用、要索引 → 列表；数据量大、只遍历一次、或流式 → 生成器。很多时候还可以组合：中间结果用生成器省内存，最终结果 list() 落地。

为什么生成器只能遍历一次？有没有办法重复用？

因为生成器的状态就是函数栈帧。它执行到函数末尾（或 return）后，栈帧被销毁，状态就没了——不像列表那样数据还留在内存里。所以「遍历一次」是它的固有性质。三种重复用的办法：① 重新调用函数——list(fib_gen(10)) 而不是复用一个已耗尽的生成器对象，这是最干净的做法（把生成器函数当成「迭代器工厂」）；② 转成列表——data = list(gen)，代价是失去省内存的优势；③ itertools.tee——把一个迭代器分成多个，但它的实现是缓存已产生的元素，所以如果多个分支消费速度不一致，内存仍会增长（文档明确提醒：tee 之后应尽快消费，不要让某个分支落后太多）。实践中最推荐①——把生成器写成函数，需要时重新调用。

生成器和 async/await 有什么关系？

历史上是父子关系：Python 3.4 的 asyncio 就是用 yield from 实现的协程——因为 yield 的本质是「让出控制权」，而这正是协程需要的。3.5 引入了原生语法 async def / await 和独立的协程对象，但核心语义完全一样：await 就是「暂停并让出控制权，等结果好了再恢复」。两者现在的区别主要是：① 原生协程不能被 for 迭代（要用 async for + 异步生成器）；② 原生协程必须由事件循环驱动，不能自己 next()；③ 原生协程有更好的性能和更清晰的错误信息。理解生成器的「暂停-恢复」模型，是理解 asyncio 的最短路径——很多人在学 async 时卡住，根源是没搞清楚「暂停」到底暂停的是什么。另外还有个实用工具：异步生成器（async def + yield），用于流式产生异步数据（如分页拉取 API），用 async for 消费。
