什么时候适用？

判断信号：流量超过容量或非核心能力过载，必须保护关键业务。

  • 秒杀入口按令牌桶限制请求
  • 推荐模块过载时只保留下单
  • 高峰期对低优先级接口返回简化结果

和相近方案怎么区分？

相近方案选择边界
限流决定哪些请求可进入，超额请求会被拒绝或排队。
降级接受请求但减少可选功能；二者可同时使用。

限流算法 Rate Limiting

限流决定『放多少进来』

限流：在入口控制单位时间请求量，保护后端不被冲垮。令牌桶（有突发容量）与漏桶（平滑恒定速率）最常用；分布式场景需借助 Redis/网关统一计数。

降级策略 Degradation

  • 弃车保帅：关闭非核心功能（如推荐、评论），保住下单/支付。
  • 返回兜底：缓存值、默认值、静态页。
  • 读降级：查不到走默认；写降级：先入队异步处理。

三者配合

限流挡在门口 → 熔断切断故障依赖 → 降级保证核心可用。三者是高可用三件套。

面试高频问答

Q：令牌桶和漏桶分别适合什么？
A：令牌桶允许一定突发（攒令牌），适合有正常尖峰的 API；漏桶强制恒定速率输出，适合需要平滑流量的下游（如保护数据库写入）。
Q：限流应该放在哪一层？
A：越靠前越好：网关/接入层做全局限流，服务内再做更细的（按用户/按接口）限流，形成多层防护。

限流与降级：保护自己的两道闸门

限流回答「能不能让你进来」，降级回答「我扛不住时先放弃什么」。两者配合才是完整的流量治理：限流防外部过载，降级保内部核心。

限流 Rate Limit拒绝超出容量的请求，保护系统不被压垮（对调用方说「不」）
熔断 Circuit Break下游持续故障时停止调用，避免拖死自己（对依赖说「不」）
降级 Degrade关闭非核心功能，把资源让给核心链路（对自己说「取舍」）
拒绝服务 Shedding按优先级主动丢弃低价值请求，保住高价值请求
五层流量治理漏斗：从边缘到核心逐层收敛

四种限流算法

算法原理特点实现要点
固定窗口计数每 60s 一个窗口，计数超阈值即拒绝最简单；有临界突刺问题（59s 和 61s 各打满，实际 2 倍速率）Redis INCR + EXPIRE，或本地 AtomicInteger
滑动窗口计数把窗口切成小格，统计最近 N 格的总和精度高于固定窗口；内存占用与格数成正比Redis ZSET 存时间戳，ZREMRANGEBYSCORE 清理过期
漏桶 Leaky Bucket请求进桶，桶以恒定速率出水，桶满则拒绝强制匀速，绝对平滑；无法利用空闲容量，不支持突发适合对下游做「整形」保护，如消息队列消费
令牌桶 Token Bucket按速率生成令牌，请求取到令牌才通过，令牌可累积到桶上限允许突发（桶内积攒的令牌可一次性用完），最常用Guava RateLimiter（单机）、Redis+Lua（集群）、Sentinel

选哪个：要「限制平均速率但允许合理突发」→ 令牌桶（绝大多数场景）；要「严格匀速保护下游」→ 漏桶；要「精确控制任意窗口内的请求数」→ 滑动窗口。网关层常用令牌桶，因为它既保证长期平均速率不超标，又不误伤正常的短时抖动。

限流的三个维度与阈值怎么定

  • 维度：单机（本地计数器，快但不精确）/ 集群（Redis 共享计数，精确但有网络开销）/ 用户维度（防单用户刷）/ 接口维度（按接口重要性与成本分别配额）。生产上通常单机 + 集群两层，单机做粗粒度快速拒绝，集群做精确控制。
  • 阈值从压测来，不是拍脑袋。方法：压测得到单机容量 C（如 500 QPS 时 P99 仍在 200ms 内），集群阈值 = C × 实例数 × 安全系数（0.7~0.8）。留 20%~30% 余量应对实例宕机与流量不均。
  • 并发数限流比 QPS 更贴近本质。因为系统真正的瓶颈是「同时在处理的请求数」（线程池、连接池）。当下游变慢时，QPS 不高但并发堆积，此时 QPS 限流无效而信号量/线程池隔离有效。
  • 排队 vs 直接拒绝。秒杀一类场景可以排队（给用户「排队中」体验）；普通 API 应快速失败（返回 429），因为排队会占住连接与内存，反而加剧雪崩。
// Redis + Lua 令牌桶（集群维度，原子执行） local rate = tonumber(ARGV[1]) -- 每秒生成令牌数 local capacity = tonumber(ARGV[2]) -- 桶容量（允许的最大突发） local now = tonumber(ARGV[3]) local last = tonumber(redis.call('HGET', KEYS[1], 'ts') or now) local tokens = tonumber(redis.call('HGET', KEYS[1], 'tk') or capacity) tokens = math.min(capacity, tokens + (now - last) / 1000 * rate) if tokens < 1 then return 0 end -- 令牌不足，拒绝 redis.call('HMSET', KEYS[1], 'ts', now, 'tk', tokens - 1) return 1 -- 放行

降级：先想清楚放弃什么

按功能重要性分级

把功能分为 P0（不可降级：下单、支付、登录）、P1（可降级：推荐、评论、积分）、P2（可关闭：排行榜、个性化推荐、数据分析上报）。

  • 压力来时按 P2 → P1 顺序关闭
  • 这个分级表必须在平时就确定好并写进预案，不能临时讨论

三种降级形态

  • 功能关闭：直接不执行，返回空或默认（关闭评论、关闭推荐）
  • 降级到兜底数据：读缓存旧值、返回静态页、返回通用文案
  • 异步化：同步操作改成写消息队列后异步处理（如发放优惠券、生成报表）

自动 vs 手动降级

  • 自动：基于指标（错误率、RT、负载、线程池使用率）触发，响应快
  • 手动：运维在控制台一键开关，可控性强，适合大促等计划内场景
  • 生产建议两者都有：自动兜底 + 手动开关（手动优先级更高）

降级的副作用管理

  • 降级后要可观测：当前哪些开关被打开，必须在监控大盘可见
  • 要能快速恢复：开关生效要秒级，且恢复前先灰度验证
  • 要定期演练：未演练的降级开关等于没有，故障时不敢开

深入自检

限流阈值设成压测峰值合适吗？

不合适。压测峰值是「系统刚好不崩的临界点」，在这个点上延迟已经很高、错误率已经开始上升。正确做法是取「延迟可接受区间内的最大吞吐」：比如压测发现 500 QPS 时 P99 是 150ms（可接受），800 QPS 时 P99 跳到 2s（不可接受），那容量应取 500 而非 800，再乘 0.7~0.8 的安全系数得到阈值。另外还要考虑实例宕机后的流量重分配——10 台机器挂 1 台，剩余每台要多扛 11%。

被限流的请求应该排队还是直接拒绝？

取决于请求是否有等待价值。秒杀、抢票这类用户愿意等且等待时间短（秒级）的场景，排队体验更好；普通 API 应直接拒绝，因为：① 排队占用连接与内存，可能把整个网关拖垮；② 用户等待后超时，等于白等还浪费了资源；③ 客户端重试会进一步放大流量。折中方案是「短暂排队 + 超时快速失败」：最多等 200ms，等不到就返回 429 并带上 Retry-After。

熔断和降级是一回事吗？

不是。熔断是「对某个下游依赖」的保护机制：当该依赖错误率过高时，暂时停止调用它，快速失败并走兜底逻辑，等其恢复后再试探性放开——它是一种自动的、以依赖健康度为输入的开关。降级是「对自身功能」的取舍：主动关闭非核心功能以释放资源。两者常配合使用（熔断后走降级兜底），但触发条件与作用对象不同。

降级演练怎么做？

三个层次：① 开关有效性验证——定期（如每月）在预发/低峰时段逐个触发降级开关，确认代码路径真的生效、不会因降级代码本身有 bug 而报错；② 压力演练——在压测环境模拟 3~5 倍流量，观察自动降级是否按预期触发、核心链路是否存活；③ 生产混沌工程——随机注入故障（杀实例、网络延迟、依赖超时），验证完整预案。关键是要有明确的回滚手段和演练窗口，绝不能在生产高峰期做无准备的演练。
