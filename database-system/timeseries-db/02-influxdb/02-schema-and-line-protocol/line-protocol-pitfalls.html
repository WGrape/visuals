问：为什么写入返回 204 但查不到数据？

九成是时间戳问题：精度单位写错、时间戳落在保留期之外、或者用了未来时间。先用一个宽范围（如近 30 天）查一次确认。

问：tag 和 field 选错了能改吗？

能，但要重写数据：新建正确的 series 结构并把历史数据重新写入。所以上线前就要定好 schema，后期改的成本很高。

问：批次数千行好还是数百行好？

看失败代价：批太大，一次超时要重传几万行；批太小，请求开销占比高。经验起点是 5000 行/批或 1 MB，再按服务端表现微调。

第一层 · 概念与判定：一行怎么写

Line Protocol 是 InfluxDB 的写入行格式：measurement,tag_key=tag_value field_key=field_value timestamp。关键是 tag 与 field 的区别：tag 会被索引、用于 WHERE 过滤和 GROUP BY；field 存实际数值、不索引（或被倒排），是查询聚合的对象。

部分是否索引能否做条件过滤例子
measurement是（名）可cpu
tag是可（高效）host=web01
field否可（慢）usage=0.82
timestamp————纳秒整数

一句话判定：用来分组/过滤的维度放 tag，要聚合的数值放 field。把高基数维度误放进 tag 是 InfluxDB 最致命的错。

Line Protocol 正确写法与批量写入

# 正确的一行：tag 之间逗号、field 之间逗号、tag 与 field 之间空格
cpu,host=web01,region=us-west usage=82.5,load=1.3 1700000000000000000

# 带转义：location 值里含逗号，必须反斜杠转义
sensor,location=us\,east temp=21.4

# 字符串 field 必须双引号
app,env=prod msg="request timeout"

# 批量写：多行一次 POST，注意每行一个 measurement
curl -i -XPOST 'http://localhost:8086/write?db=mydb' --data-binary '
cpu,host=web01 usage=82.5
cpu,host=web02 usage=77.1
'

数量级：单行建议 < 1 KB；一次批量写建议 5000 行以内 / 数 MB，过大单批会超时或触发内存上限。

第三层 · 排障与边界：高频坑

写入失败/性能炸的清单：

  • tag 高基数：把 user_id、request_id、IP 当 tag，基数爆炸，索引膨胀到 OOM —— 和 Prometheus 同款坑
  • 逗号/空格未转义：location=us,east 被解析成两个 tag，数据全错位
  • field 类型不一致：同一个 field 先写 v=1（int）后写 v=1.0（float），InfluxDB 直接拒绝写入
  • 时间戳单位错：用毫秒却没写够位数，数据跑到 1970 或 1970 之后异常时间点
  • 字符串 field 漏引号：msg=hello 被当布尔 true 或解析失败
  • measurement 名带特殊字符：含空格/斜杠要加引号，否则语法错误

排查顺序：① 看返回 400 的具体错误信息（InfluxDB 会指出哪一行哪列）；② 查 series 基数是否失控；③ 确认 field 类型在 schema 内一致。

第四层 · 原理与取舍

为什么 tag 有索引而 field 没有？

时序查询的典型模式是「按维度过滤 + 对数值聚合」，tag 数量相对可控（主机、机房），建索引代价小、加速明显；field 是真正海量的采样值，若也索引会和反序列化开销同量级，得不偿失。代价是 field 上的 WHERE 只能顺序扫描。

为什么高基数 tag 在 InfluxDB 尤其致命？

它的 TSI（时间序列索引）为每个 series 维护倒排结构，tag 基数 = series 数，series 数直接决定内存与启动加载时间。百万级 series 内存轻松上 GB，千万级可能起不来。所以 schema 设计的第一原则就是tag 只能放低基数的枚举维度。

该用 InfluxDB 还是 Prometheus？

监控指标、拉模型、短期存储 → Prometheus；事件型/高写入、需要 SQL 类查询、长周期存储、多租户 → InfluxDB。二者都对高基数 tag 敏感，设计原则互通。
