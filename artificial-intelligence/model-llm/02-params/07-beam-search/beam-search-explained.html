Beam Search：保留多条最优路径的确定性解码

翻译和摘要的老王者，为什么到了对话和写作反而被弃用？

定位

不做随机采样，而是"多路并进找最优"

贪心解码每步只走概率最高的一个词，容易走进局部最优；Beam Search 每步保留概率最高的 B 条完整序列（束宽 beam width），最后输出整体概率最大的那条。它是确定性解码：同样输入永远同样输出。

过程

B=3 时的一步发生了什么

打分用累计 log 概率：逐词概率连乘会下溢，实践中用 log 概率求和；长序列天然吃亏（乘的负数多），所以常配长度惩罚（length penalty）防止系统偏向短输出。
反思

为什么 ChatGPT 们不用 Beam Search

输出千篇一律
永远选"最安全"的话，多样性归零——对话场景显得机械、没人味
高概率 = 高质量？
开放生成里人类偏好不等于模型概率最大；研究表明 beam 过宽反而产生重复、空洞的文本
计算贵
每步要算 B 份前向，显存与延迟按倍数涨；KV cache 也更难复用
随机性有价值
采样（温度/top-p）能带来自然表达与可控多样性，一个 seed 就能重 roll
场景

什么时候仍然用它

任务是否适合原因
机器翻译✅ 经典主场答案空间有限且有好坏之分，BLEU 时代的标准配置
摘要 / 受约束生成✅ 适合输出越"接近唯一正解"，搜索越有优势
对话 / 创意写作❌ 不适合需要多样性与自然度，采样更合适
推理链生成（CoT）⚠️ 视情况近年常用 Best-of-N / 验证器 / 搜索类方法替代传统 beam
面试问答

高频问题

Q1：Beam Search 和贪心解码的关系？
贪心是束宽 B=1 的特例：每步只保留一条路径。B 增大则搜索更充分、结果更好，但计算与显存开销线性增加，且输出永远确定。
Q2：为什么需要长度惩罚？
累计 log 概率是负数连加，序列越长分数越低，Beam 会系统性偏爱短输出。长度惩罚（除以长度的 α 次幂）校正这种偏置。
Q3：为什么对话模型不用 Beam Search？
开放对话没有唯一正确答案，概率最大 ≠ 人类偏好；Beam 输出保守重复、缺乏多样性，且计算开销大。采样类解码（温度 + top-p）更自然可控。
Q4：Beam width 越大效果一定越好吗？
不。研究表明束宽过大后翻译 BLEU 等指标反而下降，且开放生成中出现更多重复退化。存在一个适度区间（常见 4~10）。
Q5：Beam Search 和 Best-of-N 的区别？
Beam 是每步剪枝的确定性搜索，全程只维护 B 条路径；Best-of-N 是独立采样 N 个完整答案再挑最好的（可配验证器打分），天然并行、多样性更好，是推理模型时代的主流。
