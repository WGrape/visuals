🔑 HBase RowKey 设计

HBase 里最重要的一件事：查询条件怎么编码进唯一索引

为什么 RowKey 设计是 HBase 的头号问题

HBase 原生只有 rowkey 一个索引。列族、列限定符都只在 rowkey 定位之后做过滤，不参与定位。所以：

💡 「我的查询能不能高效」≡「查询条件能不能编码进 rowkey」。设计错了，再怎么加机器、调参数都救不回来——因为所有请求都会退化成全表 scan。
作用一：定位决定这条数据在哪个 Region、哪台机器
作用二：排序决定数据在磁盘上的物理相邻关系
作用三：查询唯一能走索引的查询入口（点查 / 范围扫）
作用四：分布决定写入是否均匀打散到所有 Region

三条基本原则

  • 唯一性：rowkey 必须唯一标识一行，否则后写的会覆盖先写的（同一 rowkey + 列 + ts 就是同一个 cell）
  • 长度适中：建议 10~100 字节，越短越好。每个 cell 都会完整存一份 rowkey，1 亿行 × 100 字节 = 10GB 纯 rowkey 开销
  • 散列性：前缀要能均匀打散到所有 Region，避免热点
    • ⚠️ rowkey 长度的隐藏代价：它不仅占磁盘，还占 MemStore 和 BlockCache 的内存，以及索引块的空间。一个 200 字节的 rowkey 相比 20 字节的版本，整体存储可能翻倍。

    四大经典设计模式

    ① 反转（Reversal）—— 打散单调递增

    适用于 timestamp / 自增 ID 这类单调 key。反转后低位变高位，新数据不再集中落在最后。

    // 原始：时间戳递增 → 新数据全打在最后一个 Region ❌
rowkey = "1700000000000"  "1700000000001"  "1700000000002" ...

// 反转：把变化最快的低位放到前面 ✅
rowkey = reverse("1700000000000") = "0000000000071"

// 更常见的做法：用 Long.MAX_VALUE - ts 再补零，实现「时间倒序」
rowkey = String.format("%019d", Long.MAX_VALUE - timestamp)
    优点缺点
    反转打散热点；实现简单牺牲了时间顺序——无法按时间范围连续 scan

    ② 加盐（Salting）—— 强制分散

    在 rowkey 前加一个随机/哈希前缀，把同一个业务 key 的数据强行分散到 N 个 Region。

    // 按 userId 哈希取模，前缀 0~15
byte salt = (byte) (Math.abs(userId.hashCode()) % 16);
rowkey = salt + "_" + userId + "_" + timestamp;
// 例：03_u12345_1700000000000

// 读取时要遍历所有 16 个前缀，或用并发 get 再聚合
    ⚠️ 加盐的代价：同业务 key 的数据不再连续，一次范围查询要并发查 N 个前缀再归并。N 取多少要权衡「打散程度」与「读放大倍数」，常见 8~64。

    ③ Hash 前缀 —— 均匀但彻底乱序

    // MD5 取前 4 位（16^4 = 65536 种前缀）
rowkey = MD5(userId).substring(0, 4) + "_" + userId;
// 例：a3f9_u12345

// 配合 HexStringSplit 预分区，天然均匀分布
create 't', 'cf', { NUMREGIONS => 16, SPLITALGO => 'HexStringSplit' }

    适合纯点查场景（知道完整 key，直接 get）。不适合范围扫。

    ④ 组合键（Composite）—— 最常用

    把多个查询维度按重要性从高到低拼接，兼顾定位与局部有序。

    // 场景：查「某用户某时间段的行为」
rowkey = userId + "_" + reverseTimestamp
// 例：u12345_9999999998299

// 前缀 scan 就能拿到该用户全部行为（按时间倒序）
scan 't', { STARTROW => 'u12345_', ENDROW => 'u12346' }

// 场景：物联网「设备 + 时间」
rowkey = deviceId + "_" + String.format("%019d", Long.MAX_VALUE - ts)

// 场景：社交「用户 + 关系类型 + 对方」
rowkey = userId + "_" + relationType + "_" + targetId

    场景对照表

    查询需求推荐 rowkey说明
    按用户查全部行为hash(u)%N + userId + revTs前缀打散 + 用户聚簇 + 时间倒序
    查某用户最近 N 条同上，scan 时 LIMIT时间倒序让「最近」就在最前面
    按时间范围扫描ts 或有界前缀 + ts必须用时间戳本身（不能反转），接受热点或加盐
    纯点查（知道完整 key）MD5(key).sub(0,4) + key最均匀分布，放弃范围能力
    多维度查询组合键 + Phoenix 二级索引rowkey 只能服务一种主查询，其余靠索引表
    时序/物联网deviceId + revTs同设备聚簇，注意设备数要够多才均匀
    大客户数据倾斜userId + random(0~N) + ts给热点 key 单独加盐

    常见反模式

    ❌ 纯时间戳开头新数据全打最后一个 Region
    ❌ 过长 rowkey每个 cell 都存一份，内存/磁盘双放大
    ❌ 中文/特殊字符字节序不直观，建议定长数字或 hex
    ❌ 分隔符用常见字符如 "_" 可能出现在数据里，用不可见字符或定长
    ❌ 长度不固定字典序会不符合预期（"9" > "10"）
    ❌ 全靠 scan + FilterFilter 是服务端过滤，不减少扫描量
    ⚠️ 字典序陷阱："10" < "9"（字符串比较），因为 '1' < '9'。数字型维度必须补零定长：String.format("%010d", num)。

    二级索引怎么办

    rowkey 只能服务一种查询顺序。需要第二种维度查询时的三种方案：

    方案做法适用
    全局索引表另建一张表，rowkey = 被索引列 + 原 rowkey简单可控，但要自己维护一致性
    Phoenix 二级索引CREATE INDEX，自动维护最推荐，支持全局/本地/覆盖索引
    协处理器Observer 在 put 时同步写索引灵活但侵入性强，慎用

    🎯 常见问法与答题要点

    Q：RowKey 为什么不能用时间戳开头？

    A：rowkey 按字典序全局有序，Region 是按 rowkey 范围切的。时间戳开头意味着新写入的 key 永远最大，全部落在最后一个 Region，也就是一台 RegionServer 上——其他机器完全空闲，这就是最经典的热点。解决方案：加 hash/salt 前缀打散，或用 Long.MAX_VALUE - ts 反转，或在前面加业务维度（如 userId）。

    Q：加盐后怎么查询？

    A：因为同一个业务 key 被分散到 N 个前缀，查询要并发向 N 个前缀发请求再归并。例如 salt 取 16，就要并发发 16 个 get/scan（或按前缀范围扫）。代价是读放大 N 倍的网络往返。所以 N 的选择是权衡：太小打不散热点，太大读放大严重，常见 8~64。

    Q：RowKey 多长合适？

    A：官方建议 10~100 字节，越短越好。因为每个 cell（每个版本、每列）都会完整存一份 rowkey：一张有一亿行、每行 10 列的表，rowkey 从 20 字节变 100 字节，就多出 80GB。而且 rowkey 还要占 MemStore、BlockCache 和索引块的内存。

    Q：为什么数字要补零定长？

    A：rowkey 是字节字典序比较，不是数值比较。字符串 "10" 与 "9" 比较时，先比第 1 个字符 '1' vs '9'，'1' < '9'，所以 "10" < "9" —— 与数值直觉完全相反。所有数字型维度都必须补零定长：String.format("%010d", 9) → "0000000009"，这样排序才正确。

    Q：想按多个维度查询怎么办？

    A：rowkey 只能服务一种主要查询顺序。需要第二种维度时：①最推荐用 Phoenix 二级索引（CREATE INDEX，自动维护，支持覆盖索引）；②自建全局索引表（rowkey = 索引列 + 原 rowkey，查两次，自己保证一致性）；③用协处理器同步写索引（侵入性强，慎用）。

    Q：设计好的 RowKey 长什么样？给个例子。

    A：场景：用户行为日志，主要查询是「查某用户最近的行为」，写入要均匀。设计：rowkey = String.format("%02d", Math.abs(userId.hashCode()) % 16) + "_" + userId + "_" + String.format("%019d", Long.MAX_VALUE - ts)。02d 哈希前缀打散到 16 个 Region 消除热点；userId 让同用户数据聚簇；反转时间戳让同用户内按时间倒序，「最近 N 条」直接 scan 前 N 条即可。

    Q：Filter 能替代 RowKey 设计吗？

    A：不能。Filter 是在 RegionServer 端逐条过滤，它减少了网络传输，但没有减少扫描的数据量——该读的 HFile 还是全读了。所以「用 SingleColumnValueFilter 按某列过滤」不等于「按该列走索引」。真正减少扫描量的只有：精确 rowkey 点查、收窄 STARTROW/STOPROW 范围、以及 Phoenix 二级索引。
