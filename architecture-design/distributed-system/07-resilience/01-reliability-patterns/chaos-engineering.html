混沌工程：主动注入故障，提前发现脆弱点

从稳态假设讲到五层注入、爆炸半径控制与落地路线

一、混沌工程不是「搞破坏」

混沌工程（Chaos Engineering）是在受控条件下主动注入故障，用实验验证系统对异常的耐受能力。它的关键词是「实验」：先提出稳态假设，再注入最小扰动，最后用监控数据判断假设是否成立。和「随机关服务看会不会挂」的区别，就在于有没有假设、有没有对照、有没有止损。

核心目标
在故障发生前发现它
把「未知的未知」变成「已知的已知」
不是什么
不是随机破坏、不是压测
压测验证容量，混沌验证容错
前置条件
已有监控、告警、回滚手段
没有可观测性就别做，否则只是制造事故
最低成本起步
先做「只读演练」与故障复盘
不必一上来就上 Chaos Mesh

先问自己三个问题

  1. 出问题能在几分钟内发现吗？（监控 + 告警是否覆盖核心指标）
  2. 发现后能一键止损吗？（回滚、降级、切流是否有开关且演练过）
  3. 最坏情况下影响面能限制在多少用户？（爆炸半径是否可控）

二、一次标准实验的六步

步骤要产出什么常见错误
定义稳态一组可量化指标（成功率、延迟、吞吐）只写「系统正常」，无法判定
提出假设可证伪的陈述句假设模糊，实验结论无法落地
设计注入故障类型、目标、时长、爆炸半径一上来就注入全集群网络分区
执行实验可随时中止的开关 + 值班人在场无人值守时跑实验
观测对照对照组与实验组指标对比只看总量，不看分位与分群
收敛改进缺陷单 + 修复 + 复验时间做完不复验，问题反复出现

三、故障注入的五个层次

延迟注入

把下游 RT 从 20ms 拉到 2s，最能暴露超时未设置、线程池打满的问题。

错误码注入

下游返回 500 / 429，检验重试是否幂等、熔断是否生效。

资源耗尽

CPU 打满、内存限制、磁盘写满，检验降级与优雅失败。

依赖不可用

Redis / MQ / 配置中心挂掉，检验是否有兜底路径。

时钟偏移

把机器时间拨快几分钟，检验证书、定时任务的健壮性。

分区（脑裂）

把集群切成两半，检验一致性协议与写保护。

四、爆炸半径与止损

四道防线

  1. 范围限定：只影响指定标签的 Pod / 指定比例流量，绝不默认全量。
  2. 时间限定：实验自动带 TTL（如 5 分钟），到点自动恢复，防止忘记。
  3. 中止开关：一键 kill 所有实验，且值班人清楚开关在哪。
  4. 熔断联动：稳态指标跌破阈值（如成功率 < 99.5%）自动停止实验并告警。
# Chaos Mesh 最小实验：只杀带 app=order 的 1 个 Pod，5 分钟自动结束 apiVersion: chaos-mesh.org/v1alpha1 kind: PodChaos metadata: name: order-pod-kill spec: action: pod-kill mode: one # 只影响一个，控制爆炸半径 duration: "300s" # TTL，到点自动恢复 selector: labelSelectors: app: order scheduler: cron: "0 3 * * *" # 低峰期执行

五、从 0 到 1 的落地路线

  1. 阶段一：只做复盘。把过去半年线上故障整理成「故障模式清单」，这是最便宜的素材来源。
  2. 阶段二：预发环境演练。在预发注入同一批故障，验证应急预案是否真的有效（多半会发现预案是过期的）。
  3. 阶段三：生产只读演练。只做「不写数据」的注入，如只读请求延迟，验证监控是否报警。
  4. 阶段四：生产小流量演练。在 1% 流量上注入，配自动中止，逐步放量到 5%、10%。
  5. 阶段五：常态化。纳入发布流程：核心服务每次大版本上线前跑一遍标准故障集。

没有专门的混沌平台也能开始

用 iptables/tc 注入网络延迟、用 kill -9 杀进程、改一个配置开关让下游返回错误 —— 工具不重要，假设与观测才重要。

六、深入自检

混沌工程和故障演练、压测有什么区别？

压测是「加负载到极限」，验证容量；故障演练是「模拟已知故障」，验证预案；混沌工程是「提出假设并设计实验」，目的是发现未知的脆弱点。三者互补，不可互相替代。

没有完善监控能做混沌工程吗？

不建议。混沌工程的输出是「稳态是否被破坏」，而这个判断完全依赖监控。监控缺失时做实验，等于闭着眼睛开车 —— 你只会制造一场真实事故。

为什么强调「假设」而不是「随便注入」？

没有假设就无法证伪，也无法度量改进。「杀一个节点后 P99 仍然低于 300ms」是可验证的；「看看系统扛不扛得住」不是。

生产环境做实验出事怎么办？

前提就是可控：小范围、有 TTL、有一键中止、有值班人。即便如此，第一次上生产仍应选择业务低峰，并把回滚脚本提前准备好、演练过。

怎么衡量混沌工程的收益？

看三类指标：① 实验发现并修复的缺陷数；② 同类故障的复发率是否下降；③ 故障平均恢复时间（MTTR）是否缩短。避免只汇报「做了多少次实验」这种虚荣指标。

优先级建议

如果只能做四项：单实例宕机、下游 RT 飙高、下游 5xx、消息重复投递。这四项覆盖了生产环境绝大多数故障形态，且注入成本低、风险可控。

混沌工程的正确做法与实验设计

混沌工程不是「随机制造故障」，而是用受控实验验证系统的稳态假设。核心是「先定义稳态指标，再注入故障，看指标是否还在范围内」。

常见误解实际做法
「就是搞破坏」是验证假设的实验，有明确的假设和验证指标
「生产环境乱搞」最小化爆炸半径：先单实例、先非高峰、有中止开关
「测试的一种」测试和混沌的区别：测试验证已知，混沌探索未知
「上了工具就是混沌工程」工具只是手段，实验设计才是核心
实验步骤内容要点
1. 定义稳态选一个可量化的业务指标作为「正常」标准如：下单成功率 >99.9%、P99 <500ms
2. 提出假设「注入 X 故障，稳态指标仍保持正常」假设要能被证伪
3. 设计爆炸半径从最小范围开始：单实例 → 单 AZ → 全量有随时中止的能力
4. 执行注入故障，同时监控稳态指标生产环境、业务低峰期
5. 验证稳态是否被破坏？系统是否自愈？记录真实观察 vs 假设的差距
6. 改进发现的问题进 backlog，修复后重跑实验混沌工程是持续过程
故障类型注入手段验证什么
实例宕机kill 进程 / 删 Pod服务发现和重建是否及时
网络延迟tc netem 加延迟超时和重试是否合理
网络丢包/分区iptables / 网络策略分区容忍、脑裂处理
CPU/内存打满stress-ng降级和限流是否生效
磁盘满/IO 慢填满磁盘 / dd 压测写失败处理、监控告警
依赖服务不可用返回 5xx 或超时熔断降级是否生效（最有价值）
时钟偏移修改系统时间证书、令牌、定时任务
下游返回慢注入延迟到依赖超时传递、线程池耗尽

注入命令

# ---------- Linux 原生故障注入 ----------
# 网络延迟 100ms ± 20ms
tc qdisc add dev eth0 root netem delay 100ms 20ms
tc qdisc del dev eth0 root                     # 恢复（务必记住！）

# 网络丢包 10%
tc qdisc add dev eth0 root netem loss 10%

# CPU 打满（4 核）
stress-ng --cpu 4 --timeout 60s
# 内存占用 2GB
stress-ng --vm 1 --vm-bytes 2G --timeout 60s

# 模拟依赖超时（iptables 丢弃到某端口的包）
iptables -A OUTPUT -p tcp --dport 3306 -j DROP
iptables -D OUTPUT -p tcp --dport 3306 -j DROP  # 恢复

# ---------- Kubernetes 混沌（Chaos Mesh）----------
kubectl apply -f - <<YAML
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata: {name: pod-kill, namespace: default}
spec:
  action: pod-kill              # 杀 Pod
  mode: one                     # 只影响一个（最小爆炸半径）
  selector:
    labelSelectors: {"app": "order-service"}
  scheduler:
    cron: "0 2 * * *"           # 每天凌晨 2 点（低峰期）
YAML

# 网络延迟注入
kind: NetworkChaos
spec:
  action: delay
  mode: all
  selector: {labelSelectors: {"app": "order-service"}}
  delay: {latency: "100ms", correlation: "50", jitter: "20ms"}
  duration: "60s"               # 重要：限定持续时间，自动恢复！

# ---------- 关键：自动恢复与中止 ----------
#   所有实验必须设 duration（到期自动恢复）
#   必须有「一键中止」按钮/命令
#   Chaos Mesh 支持 status.phase = Stopped 立即停止
  • 稳态指标必须是业务指标：不要用「CPU 使用率」当稳态，要用「下单成功率」「P99 延迟」这类用户可感知的指标。因为 CPU 高了不代表用户受影响。
  • 爆炸半径从小到大：单实例 → 单服务 → 单 AZ → 全区域。第一次就在生产全量注入是大忌。
  • 所有实验必须有自动恢复机制：duration、超时、以及人工中止开关。这是安全阀。
  • 最有价值的实验是「依赖服务不可用」：因为它能验证熔断、降级、超时传递——这些代码平时永远不会被执行，只有故障时才跑，不测就等于没有。
  • 混沌工程发现的问题要跟进修复并重跑：只跑实验不改代码没有意义。Netflix 的做法是把混沌实验做成常态化（持续随机注入）。
  • 记录「假设 vs 实际」：假设「延迟 100ms 不影响下单」，实际「下单成功率掉到 95%」——这个差距就是最有价值的产出。
  • 不要在高并发大促期间做：除非你的系统已经很成熟且你想验证极限。
混沌工程和故障演练有什么区别？

故障演练是「我知道会发生什么，演练一下流程」——比如「主库挂了，切从库」，重点验证人的操作和预案是否可行，结果是已知的（应该成功）。混沌工程是「我不知道会发生什么，做个实验看看」——比如「给订单服务的 Redis 注入 500ms 延迟，下单成功率会怎样？」，重点探索系统的未知行为，结果可能证伪你的假设（比如你以为会降级，结果线程池被打满导致雪崩）。核心区别：演练验证已知，混沌探索未知。实践上两者互补：演练保证「人知道怎么操作」，混沌保证「系统真的能扛住」。很多团队只做演练，结果线上真实故障时发现「预案里写的降级开关根本没生效」——因为那个开关的代码路径从来没被执行过，这正是混沌工程要发现的。

在生产环境做混沌工程是不是太危险？

有风险，但在预发/测试环境做等于没做——因为真实的配置、数据量、流量模式、依赖拓扑只有在生产才完整，很多故障（如连接池耗尽、缓存雪崩、重试风暴）在压不出的流量下根本复现不了。Netflix 的观点是：生产环境的混沌实验，恰恰是为了避免生产环境的真实故障。控制风险的六条实践：① 最小化爆炸半径——先单实例、先 1% 流量；② 选低峰期——业务量最低的时候；③ 自动恢复——所有实验设 duration，到期自动还原；④ 一键中止——有紧急停止开关且大家都知道在哪；⑤ 先有监控再看实验——如果连稳态指标都采集不到，就别做实验（你什么都观察不到）；⑥ 先在预发跑通流程——验证实验脚本本身没问题，再去生产。另外一条重要原则：如果实验结果未知到可能引发资损（如涉及资金、库存），就不要在生产做，改成在非生产的全链路环境做。

混沌工程能发现什么类型的问题？

最常发现的是「从未被执行过的容错代码路径」，这是它最大的价值。典型清单：① 超时设置不合理——上游 3 秒超时，下游 5 秒，永远等不到降级；② 重试风暴——依赖变慢时所有客户端同时重试，流量放大数倍把下游彻底打垮（必须配退避 + 熔断）；③ 熔断阈值配置错误——熔断条件过于宽松（等半天才熔断）或过于敏感（正常抖动就熔断）；④ 线程池/连接池耗尽——一个慢依赖耗尽所有线程，导致不相关的接口也全部不可用（这是最典型的雪崩路径）；⑤ 降级逻辑本身有 bug——降级分支从来没跑过，真正触发时报空指针；⑥ 监控告警缺失——故障发生了但没人知道，因为没有对应告警；⑦ 自愈时间超预期——Pod 重建要 5 分钟，SLA 要求 1 分钟。这些问题的共同特点是：平时 100% 不会暴露，只有故障时才显现——所以只有主动注入才能验证。
