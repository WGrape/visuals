🟢 主分片的写入职责

  • 写入的唯一入口（客户端不能直接写副本）
  • 在本地执行操作并维护自己的 Translog
  • 向同步副本转发操作，并汇总写入结果；确认语义受副本状态与持久性配置影响

🟠 副本分片的核心价值

  • 读扩展：分担搜索请求，提升并发能力
  • 高可用：主分片挂了，副本自动顶上去
  • 数据安全：主分片数据丢失时可以从副本恢复

核心速览

主分片是唯一入口客户端不能直接写副本，副本由主分片转发
Translog写内存 buffer 的同时记事务日志，防宕机丢失
refresh默认 1 秒，buffer → 新 segment，此刻才可被搜到
flushTranslog 刷盘 + 清空，触发时机由 translog 大小/时间决定

三个最容易混淆的概念

动作做了什么触发时机效果
refresh内存 buffer → 生成新 segment（进文件系统缓存，未 fsync）默认每 1 秒（index.refresh_interval）文档可被搜索
flush把文件系统缓存中的 segment fsync 落盘，并清空 TranslogTranslog 达 512MB 或 30 分钟数据持久化，Translog 清空
merge后台合并多个小 segment 成大 segment自动（后台线程，有限速）减少文件数、回收删除空间
💡 记忆口诀：refresh 管「能不能搜到」，flush 管「会不会丢」。文档写入后 1 秒可搜（refresh），但直到 flush 才真正落盘；中间这段靠 Translog 保证不丢。

一次完整写入的时间线

 ① 客户端发 index 请求到协调节点
 ② 协调节点按 routing（默认 _id 哈希）算出目标主分片，转发过去
 ③ 主分片本地执行：
      写入内存 buffer  ──┐
      追加 Translog     ─┘（两步都成功才算本地成功）
 ④ 主分片把操作并行转发给所有同步副本（in-sync replicas）
 ⑤ 副本各自执行 + 记自己的 Translog，ACK 回主分片
 ⑥ 主分片收到足够 ACK 后，向协调节点返回成功
 ⑦ 协调节点返回客户端
 ─────── 以上是同步路径（毫秒级）───────
 ⑧（后台）每 1s refresh → 新 segment → 可被搜索
 ⑨（后台）translog 达阈值 → flush → segment 落盘 + translog 清空
 ⑩（后台）segment 合并

写入的持久性配置

配置含义建议
index.translog.durabilityrequest（每次写都 fsync Translog，默认）／async（每 5 秒 fsync）默认 request 最安全；async 能提吞吐但宕机可能丢最后 5 秒
wait_for_active_shards要求多少分片副本可用才接受写默认 1（只要主分片在）；设为 all 或 2 更安全
?refresh=false（默认）／true（立即刷新）／wait_for（等下次 refresh）批量导入用 false；测试用 true

为什么主分片是唯一入口

顺序保证

所有写都先到主分片，由它定序再转发给副本。这样同一文档的操作在所有副本上顺序一致，不会出现「更新和删除到达顺序不同导致结果不一致」。

单一真相源

主分片负责维护版本号（_version）与并发控制。乐观并发控制（if_seq_no + if_primary_term）也在主分片上判定。

⚠️ 如果副本写失败，主分片会向 Master 报告，Master 把该副本从同步副本集（in-sync replicas）里移除；后续写入不再等它。等它恢复并追上后才会重新加入。这就是为什么副本短暂故障不会阻塞写入。

写入性能优化

手段做法收益
用 Bulk API每次批量 5~15MB / 几百~几千条减少网络往返与协调开销，收益最大
调大 refresh_interval批量导入时设 "refresh_interval":"-1"（关闭）不产生大量小 segment，省掉频繁 refresh 开销

并发写同一文档怎么办

ES 用乐观并发控制：每个文档有 _seq_no（序号）和 _primary_term（主分片任期）。更新时可带上期望值，不匹配就返回 409 冲突，由应用决定重试或合并。

PUT /my_index/_doc/1?if_seq_no=42&if_primary_term=3
{ "title": "new title" }
// 若期间被别人改过 → 409 VersionConflictException，客户端重试

🎯 常见问法与答题要点

Q：为什么 ES 写入是近实时的，而不是实时的？

A：因为写入先进内存 buffer，只有经过 refresh（默认每秒一次）生成新的不可变 segment 后，才会被 Lucene 检索到。这个 1 秒延迟换来的是「不用每次写都重建索引」的巨大性能收益。要立刻可见可以显式 refresh，但代价是产生大量小 segment、拖垮性能，只在低频场景用。

Q：写入返回成功后数据会丢吗？

A：默认配置下不会。写入时Translog 已 fsync 落盘（durability=request），即使节点立刻断电，重启后重放 Translog 就能恢复。只有把 durability 改成 async（每 5 秒才 fsync）时，才有最多 5 秒的丢失窗口。

Q：主分片挂了会怎样？

A：Master 节点检测到后，从同步副本集（in-sync replicas）里选一个提升为新主分片，整个过程通常几秒到几十秒。期间该分片的写入短暂不可用，读取可走其他副本。若一个同步副本都没有，集群会变红且该分片数据不可写（除非手工允许丢失）。

Q：能不能直接写副本分片？

A：不能。所有写都必须先到主分片，由它定序后转发给副本。这样保证同一文档的操作在所有副本上顺序一致，也保证版本号与并发控制有单一判定点。副本只能接受读请求（这也是它提供读扩展的方式）。

Q：refresh、flush、merge 分别做什么？

A：refresh 把内存 buffer 变成新的可搜索 segment（默认 1 秒，未 fsync）；flush 把缓存中的 segment 真正 fsync 落盘并清空 Translog（触发条件：translog 达 512MB 或 30 分钟）；merge 是后台把多个小 segment 合并成大的，减少文件数并回收被删除文档的空间。简单记：refresh 管「搜得到」，flush 管「不会丢」，merge 管「变整洁」。

Q：批量导入千万级数据怎么最快？

A：五件套——①Bulk API（每批 5~15MB）；②关闭 refresh（refresh_interval:-1）；③先去副本（number_of_replicas:0，导入完再加回）；④translog 改 async；⑤用自动生成 _id（省掉存在性检查）。这几项叠加通常能提速 5~10 倍。导入完记得把设置改回来。

Q：副本写失败会阻塞写入吗？

A：不会（短暂故障时）。主分片会把失败的副本报告给 Master，Master 把它从同步副本集中移除，后续写入就不再等它的 ACK。等该副本恢复并追上数据后，重新加入同步副本集。这套机制保证副本抖动不影响写入可用性。

Q：文档是不可变的，那更新是怎么实现的？

A：Lucene 的 segment 不可变，所以「更新」= 写一条新文档 + 把旧文档标记为删除。旧版本在下次 segment merge 时才被物理清除。这就是为什么频繁更新会产生大量垃圾、磁盘占用先涨后降，以及为什么 delete 后空间不会立即释放。
