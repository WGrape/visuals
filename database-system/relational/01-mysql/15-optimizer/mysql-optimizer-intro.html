MySQL 优化器详解（一）

优化器是什么、为什么非它不可、它靠哪三块基石（统计信息 / 代价模型 / 搜索策略）算出最优执行计划

①优化器是什么：SQL 执行链路里的「导航规划师」

一条 SQL 从客户端发到返回结果，中间要过好几道关卡。MySQL 把整条链路拆成了职责清晰的几段，优化器（Optimizer）夹在「解析器」和「执行器」之间：它不碰数据、不读磁盘，只负责在内存里把「怎么执行这条 SQL 最划算」想清楚，交给执行器去干。

用一句形象的话：SQL 是「声明式」语言——你只告诉数据库「我要什么」（SELECT 哪些列、FROM 哪些表、WHERE 什么条件），不告诉它「怎么拿」。解析器确认「这句话语法合法、表列都存在」；而「先扫哪张表、走不走索引、两张表用什么顺序 join、join 用哪种算法」这种「路线规划」，全归优化器管。它就像 GPS / 高德地图：目的地你已经给定，它负责算一条代价最低的路。

一句话定义
优化器是 MySQL 里「把一条合法的 SQL 转换成一棵代价最低的执行计划树」的组件；它基于代价（Cost）而非固定规则做决策，所以也叫 CBO（Cost-Based Optimizer，基于代价的优化器）。
②为什么非要有优化器：同一句话，能「走」出无数条路

关键矛盾在于：一条语义确定的 SQL，可以有数量极其庞大的「等价执行方案」，而不同方案之间的性能差距往往是几个数量级。没有优化器，系统只有两种下场：要么每次都傻乎乎全表扫描（正确但慢死），要么把执行路径写死在 SQL 里（丧失灵活性）。

例子：3 张表 JOIN + 过滤条件

SELECT * FROM A JOIN B ON A.id = B.aid JOIN C ON B.id = C.bid
WHERE A.status = 'paid' AND C.region = 'cn';

光是「表访问顺序」就有 3! = 6 种（A→B→C、A→C→B、B→A→C……）；每张表又能选择「全表扫描」还是「走某个索引」；JOIN 还能选「嵌套循环 / 哈希连接 / 批量主键访问」。组合起来可能上千种计划。其中有的计划要先扫大表再被 WHERE 砍掉 99% 的行（灾难），有的计划先用索引把两张表都缩到几行再 JOIN（飞快）。优化器的工作，就是从这上千种里挑出那条「最便宜」的。

❌ 糟糕的计划

先 SELECT * FROM C 全表扫 1000 万行，再 JOIN、再过滤 → 处理上千万行，磁盘 IO 爆表，几秒钟才出结果。

✅ 优化器选中的计划

先用 A.status='paid' 的索引把 A 缩到 5000 行，再用 B.aid 索引回表 JOIN，最后用 C.region 索引收口 → 总共只碰几万行，毫秒级返回。

为什么不能「让写 SQL 的人自己决定怎么执行」
把执行路径写死（比如强制指定 JOIN 顺序、强制走某索引）会丧失适应性：数据量变了、索引变了、统计信息变了，原本「最优」的路径可能瞬间变成最差的。优化器把「如何执行」从「写 SQL 的人」手里接管过来，根据当前数据和统计动态决定，这才是数据库「自治」的核心。
③实现原理总览：CBO 的三大支柱

现代 MySQL 优化器是一个基于代价的优化器（CBO）——它为每个候选执行计划估一个「代价数字」，选最小的那个。要算代价，它依赖三块基石：统计信息（世界长什么样）、代价模型（每种操作有多贵）、搜索策略（怎么在海量计划里高效找最优，而不是傻傻穷举）。

① 统计信息

Statistics

关于「数据和索引长什么样」的概要：表有多少行、每个索引有多少不同值（cardinality）、列值分布（直方图）。代价估算靠它估计「某条件会命中多少行」。

② 代价模型

Cost Model

给「读一页 / 比较一次 / 算一行」等操作定价的公式（IO 成本 + CPU 成本）。所有计划用同一把尺子量，才能比大小。

③ 搜索策略

Search Strategy

计划空间爆炸，不可能全试。用贪心 + 启发式剪枝（传统）或超图动态规划（新 Hypergraph）在可控时间内逼近最优。

下面三节逐一拆开。记住这个等式：代价(计划) = f( 统计信息 , 代价模型 )，而搜索策略决定要评估哪些计划。

④基石一：统计信息（Optimizer 眼里的「世界地图」）

优化器从不直接扫描全表来数「这个条件命中几行」——那太慢了。它靠预先收集、持续维护的统计信息来估算。InnoDB 的统计信息默认就是持久化开启的。

已核实（勿改）
InnoDB 持久化统计信息由 innodb_stats_persistent = ON 控制（MySQL 5.6 起默认开启），统计结果存放在系统库表 mysql.innodb_table_stats 和 mysql.innodb_index_stats 中，重启后不丢失。

核心统计项

统计项含义优化器怎么用它
n_rows（表行数）表里大约多少行估算全表扫描要处理多少行
cardinality（索引基数）索引列有多少个不同值基数越高，用这列过滤越「 Selective（选择性好）」，命中行越少 → 越倾向走索引
采样页统计靠随机抽样若干数据页推算（innodb_stats_persistent_sample_pages，默认 20 页）抽样推算，所以 cardinality 是估计值，可能不准
直方图 Histogram（8.0 引入）列值的真实分布分桶（ANALYZE TABLE t UPDATE HISTOGRAM ON col WITH 32 BUCKETS）应对数据倾斜：当 WHERE col > 1000 命中区间落在分布密集区时，估算更准

正因为统计是「抽样估计」，代价估算天然可能失真——这也是为什么有时优化器会「选错索引」：它的世界里那张地图画歪了（统计过期 / 数据严重倾斜没建直方图）。ANALYZE TABLE 就是去重新画地图。

一个容易踩的统计坑（已核实）
对 col IN (v1,...,vN) 这类「相等范围」，当范围个数 N >= eq_range_index_dive_limit（MySQL 8.0 默认 200）时，优化器会放弃精确但较慢的「索引下潜（index dive）」，改用统计信息估算命中行数——估算可能严重偏差，进而影响索引选择。范围很长时若怀疑估算失准，可调大该值或强制 FORCE INDEX。
⑤基石二：代价模型（给每个操作「定价」）

代价模型把「执行一个计划要消耗多少资源」折算成一个逻辑上的代价数字。这个数字没有物理单位，它的起源可以追溯到一个 1990 年代机械硬盘的「一次随机 IO」——随着硬件进步，各部件性价比变了，所以代价常数做成可配置的。

代价 ≈ IO 成本（读了多少页）+ CPU 成本（比较了多少次键、算了多少行）。MySQL 8.0 还做了一项关键改进：区分「从内存 buffer pool 读页」和「从磁盘读页」——内存页便宜得多。

已核实：MySQL 8.0 代价常数默认值（勿改）
代价常数存在 mysql.server_cost 与 mysql.engine_cost 两张系统表里，可在会话/全局级调整：
常数（cost_name）默认含义
io_block_read_cost1.0从磁盘读一个数据页
memory_block_read_cost0.25从内存（buffer pool）读一个页，比磁盘便宜 4 倍
row_evaluate_cost0.1读取并判定（evaluate）一行
key_compare_cost0.05比较一次键值
memory_temptable_create_cost / row_cost1.0 / 0.1建内存临时表 / 其每行成本
disk_temptable_create_cost / row_cost20 / 0.5建磁盘临时表 / 其每行成本（贵很多）

代价模型的意义在于统一度量衡：不管你是「全表扫描 + 100 万次行判定」，还是「索引范围扫 + 5000 行判定 + 几十页读」，都用同一套公式算出一个数，谁小谁就「看起来更优」。下面这个交互让你直观感受它是怎么比大小的。

⑥基石三：搜索与枚举（为什么不能「全试一遍」）

理论上，把所有可能的执行计划都算一遍代价、取最小，那叫「穷举最优」。但计划空间随表数量阶乘级爆炸：光是 5 张表 JOIN、每张表 5 个可用索引，候选计划就可能超过 5! × 5^5 ≈ 14400 种。表再多，穷举本身比执行还慢。所以优化器必须用启发式搜索在可控时间内逼近最优。

已核实：传统优化器的搜索方式
传统优化器（8.0 默认）用贪心搜索 + 剪枝：best_extension_by_limited_search() 逐步扩展 JOIN 顺序，配合 optimizer_prune_level = 1（默认开启）做启发式剪枝，提前砍掉看起来没希望的分支；optimizer_search_depth 限制搜索深度（默认 62，不等于强制全搜）。

代价是：贪心可能错过全局最优（局部最优 ≠ 全局最优）。MySQL 8.0.31 起在 HeatWave 中引入了全新的 Hypergraph Optimizer（超图优化器）：把查询建模成超图，用 DPhyp 动态规划搜索更大的计划空间，对复杂多表 JOIN 往往能找到更好的计划。

已核实
Hypergraph Optimizer 自 MySQL 8.0.31 随 HeatWave 引入，MySQL 9.0 起作为 opt-in 特性可通过 SET optimizer_switch='hypergraph_optimizer=on' 开启。它只改变「怎么执行」的规划，不改变查询结果语义。

传统：贪心 + 剪枝

快、稳定，绝大多数场景够用；缺点是有概率陷入局部最优，复杂 JOIN 选错顺序。

Hypergraph：动态规划

搜索空间更大、复杂查询更优；代价是优化本身更耗时，极多表 JOIN 时可能反而慢。故先做成可选项。

⑦优化器 vs 执行器：一个「想」，一个「干」
维度优化器 Optimizer执行器 Executor
职责决定「怎么执行最优」按优化器给的计划「真正去取数、计算」
是否碰数据否（只读统计信息做估算）是（调存储引擎接口、读页、取行）
产物一棵执行计划树（AccessPath）结果集（逐行通过迭代器上送）
核心问题Which plan is cheapest?How to fetch the next row?
可调旋钮optimizer_switch、代价常数、optimizer_search_depthJOIN buffer、sort buffer、tmp table 引擎

一句话：优化器是「军师」，执行器是「将军」。军师算好作战方案（计划树），将军带着兵（存储引擎）去打。下一篇《工作过程》会沿着这条链路，把优化器内部从解析到出计划的完整流水线走一遍。

⑧速查清单
  • 定位：优化器在解析器之后、执行器之前，把「SQL 语义」翻译成「代价最低的执行计划树」。
  • 动机：SQL 声明式、等价计划爆炸、代价差异巨大 → 必须有个组件来选路。
  • 三大支柱：统计信息（世界地图）+ 代价模型（统一定价）+ 搜索策略（高效找最优）。
  • 统计：InnoDB 持久化统计默认开；cardinality 是抽样估计，会失真；8.0 有直方图。
  • 代价：IO + CPU 逻辑单位；8.0 内存读 0.25 / 磁盘读 1.0；常数存在 server_cost / engine_cost 表。
  • 搜索：传统贪心+剪枝；8.0.31+ Hypergraph 动态规划（9.0 opt-in）。
  • 选错索引怎么办：多半是统计失真（ANALYZE TABLE 重算）或代价常数不匹配硬件，必要时用 FORCE INDEX / 优化器提示（hint）纠偏。
