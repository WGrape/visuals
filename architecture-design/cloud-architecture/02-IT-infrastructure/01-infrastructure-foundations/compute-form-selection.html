算力形态选型：物理机、虚拟机、容器与 GPU

隔离边界、启动速度、资源粒度与成本模型 — 五种算力形态的取舍

物理机→虚拟机→容器→裸金属→Serverless

一个通俗的比喻

选算力形态就像选出行方式：物理机是买车（完全掌控、要自己保养），虚拟机是租车（随租随还、车型受限），容器是打车（按里程付费、说走就走），Serverless 是坐地铁（只买这一段、完全不管车）。没有哪种最好，只有哪种更贴合你的行程与预算。

一、五种形态的核心差异

形态隔离层启动耗时资源粒度适合场景不适合场景
物理机无虚拟化，独占整机分钟–小时级整机数据库、对性能抖动极敏感的服务、需要特殊硬件流量波动大、需要快速扩缩
虚拟机Hypervisor 虚拟化秒–分钟级vCPU / 内存固定规格通用业务、需要强隔离与独立内核极高频启停、镜像体积敏感
容器操作系统级（命名空间 + cgroups）毫秒–秒级CPU 毫核 / 内存 MB 级微服务、CI 构建、弹性扩缩需要不同内核、需要完整系统级隔离
裸金属（云上物理机）无虚拟化 + 云管控分钟级整机既要物理机性能又想要云上弹性与运维小规模、成本敏感
Serverless / FaaS函数级沙箱毫秒级（但有冷启动）按调用计费事件驱动、突发流量、低频任务长驻连接、大内存常驻、超长执行

二、虚拟化开销到底在哪

⚙️ CPU 与内存

现代硬件辅助虚拟化（Intel VT-x / AMD-V）下，CPU 与内存访问的额外开销通常已经很小，大部分业务感知不到。真正影响性能的是宿主机超卖与邻居争抢，而不是虚拟化本身。

硬件辅助虚拟化超卖比

💾 I/O 路径

网络与磁盘 I/O 需要穿过虚拟化层，历史上开销较大。现代方案（SR-IOV、virtio、DPDK、用户态网络）已经把这条路大幅缩短，但在极高 PPS 或极低延迟场景下仍是选型考量。

📉 性能抖动

共享宿主机意味着会被"吵闹的邻居"影响。对延迟稳定性要求高的服务（如实时竞价、交易撮合）通常选择独占物理机或专用宿主机。

三、容器不是「轻量虚拟机」

维度虚拟机容器
隔离边界独立内核，Hypervisor 隔离，边界强共享宿主机内核，命名空间 + cgroups 隔离，边界弱
镜像内容完整操作系统应用 + 依赖（无内核）
启动速度秒–分钟级毫秒–秒级
密度单机数十个单机数百个
逃逸风险低（但存在）相对较高，共享内核是攻击面
共享内核是容器与虚拟机的根本区别，也是它的风险来源。多租户场景下，如果不同租户的代码跑在同一宿主机的容器里，隔离强度不如虚拟机。这也是为什么很多云厂商推出"安全容器"（轻量虚拟机 + 容器镜像）来补这个缺口。涉及不可信代码执行时，不要默认容器隔离足够。

四、GPU 与 AI 算力：选型看什么

  1. 显存容量优先于算力 — 大模型推理/训练的瓶颈常常是「装不下」而不是「算得慢」。先看单卡显存能否容纳模型 + KV Cache + 批大小。
  2. 卡间互联带宽 — 多卡训练/张量并行时，卡间互联（NVLink / 高速网络）的带宽往往比单卡算力更决定整体吞吐。
  3. CPU / 内存 / 存储的配比 — 数据加载与预处理跟不上时，GPU 会空转。检查数据管道是否能喂饱卡。
  4. 整机 vs 单卡 — AI 机型通常是整机打包的，CPU、内存、网卡、盘都是配套配置，单独升级某一项往往不可行。
  5. 成本形态 — GPU 单价高，闲置成本极显著。优先考虑共享调度、弹性伸缩与离线任务错峰，而不是常驻独占。
AI 算力的规格迭代很快，具体型号、显存与互联带宽以厂商当期文档为准。选型时把"显存容量、互联带宽、供给可得性、单价"四项单独列出来对比，比记型号更耐用。

五、四个成本陷阱

陷阱表现规避方式
只看单价不看利用率按整机付费但实际只用了三成先压测出真实利用率，再决定预留还是按量
忽略闲置开发环境、夜间、周末的机器照常计费定时伸缩、非生产环境自动关机
数据迁移与出口流量跨地域/出公网的流量费用被忽略提前算清流量模型，尽量同城同网
被锁在单一形态业务写好就绑死在某一种形态上用容器镜像 + 标准运行时保持可迁移性

一句话总结

选算力形态的核心不是「哪个更先进」，而是隔离边界、启动速度、资源粒度、成本模型四项是否匹配业务：要强隔离和独立内核选虚拟机，要弹性和密度选容器，要性能确定性选物理机或裸金属，要按需付费选 Serverless；AI 场景则优先看显存容量与卡间互联，再看算力。

四种计算形态对比

形态启动时间计费粒度隔离性适用
物理机小时~天月/年最强数据库、高性能计算
虚拟机分钟秒/小时强（Hypervisor）通用、需 OS 级隔离
容器秒秒中（共享内核）微服务、云原生
Serverless毫秒~秒按调用计费强（但受限）突发、低频、事件驱动

冷启动是关键差异：容器秒级、Serverless 毫秒到秒级（取决于运行时——Go/Node 约 50~200 ms，Java 可能 1~5 秒因 JVM 启动与类加载）。这决定了 Serverless 不适合对首字节延迟极敏感的同步接口，除非做预热。

选型的量化依据

维度问题结论
负载模式是持续运行还是突发？持续 → 容器/VM 更便宜；突发 → Serverless
利用率平均 CPU 利用率多少？< 30% 时 Serverless 划算；> 60% 用预留实例
运行时长单次执行多久？< 15 分钟可用 Serverless（多数平台有上限）
状态是否要本地状态？Serverless 无状态，状态必须外置
延迟能否容忍冷启动？不能 → 容器 + 预留 + 预热

成本估算

# 成本对比示例（示意，按月）
# 场景：日均 100 万次请求，单次执行 200 ms，内存 512 MB
#
# Serverless（如 Lambda）：
#   请求数费用：100万 × 30天 × $0.20/百万 = $6
#   执行时间：  100万 × 30 × 0.2s × 0.5GB × $0.00001667/GB-s ≈ $50
#   合计约 <strong>$56/月</strong>，且闲时几乎不花钱
#
# 容器（2 台 2C4G 常驻）：
#   2 × $30 = <strong>$60/月</strong>，闲时也照付
#
# 结论：
#   <strong>低频/突发 → Serverless 省；高频/持续 → 容器省</strong>
#   交叉点通常在「月请求数 × 执行时长」折算出的 CPU 利用率约 30~50% 处
#
# 注意还要算上：API 网关费、出网流量费（常是大头）、日志存储费

常被忽略的成本项：出网流量费通常远高于计算费（公网出流量约 ¥0.5~0.8/GB）。数据传输量大的服务，优化序列化与压缩、用内网通信，比纠结计算形态更省钱。

混合架构的常见组合

层形态理由
Web/API容器 + 自动伸缩需长连接、低延迟、可预测
异步任务Serverless突发、可接受排队、按量付费
定时批处理Serverless每天只跑几分钟，常驻太浪费

ML 推理GPU 容器 + 队列GPU 贵，需批处理提高利用率

判断一个组件该放哪的核心问题：它的负载曲线长什么样。画一张 24 小时的 QPS 曲线——如果是一条平稳的线，常驻资源最划算；如果是尖峰且谷底接近 0，Serverless 能省一大笔；如果是周期性波峰（如白天高、夜里低），用定时伸缩 + 预留基线的组合最合适。

自检 Q&A

Q：Serverless 一定更便宜吗？

A：不一定。它的单价（每 GB-秒）通常比容器的每 GB-秒贵 3~10 倍，优势来自「不为闲置付费」。所以利用率越低越划算。判据：把你的负载折算成「等效利用率」——若常驻容器的平均 CPU 利用率低于 30%，Serverless 通常更省；高于 50%，容器明显更省。另外要算全成本：API 网关、出网流量、日志、以及冷启动带来的体验损失。

Q：容器和虚拟机到底差在哪？

A：隔离层级不同。虚拟机虚拟了整套硬件，每个 VM 有独立内核，隔离性强但开销大（启动慢、内存占用多、性能损耗约 5~15%）。容器共享宿主内核，只隔离进程视图（namespace + cgroup），因此轻量得多（启动秒级、几乎无性能损耗），但隔离性弱——内核漏洞可能逃逸。所以多租户/不可信代码必须用 VM 或安全容器（如 Kata、gVisor）；可信的自有服务用容器。

Q：什么时候必须用物理机？

A：三种情况——① 需要极致的 IO 性能：数据库、分布式存储，虚拟化层的 IO 损耗与噪声邻居会显著影响延迟稳定性；② 需要特殊硬件：GPU/FPGA、特定网卡（RDMA）；③ 许可证限制：某些商业软件按物理 CPU 授权。除此之外，云上托管服务（RDS 等）通常比自建物理机更省心。要注意「需要物理机」和「需要可预测性能」是两回事——后者用专属实例（dedicated host）也能满足。

Q：如何评估要不要上 K8s？

A：看服务数量与部署频率。少于 5 个服务、每天部署次数个位数 → Docker Compose 或简单脚本就够，K8s 的学习与运维成本远超收益。超过 10 个服务、需要自动伸缩/滚动更新/服务发现/资源隔离 → K8s 的价值开始显现。中间地带可以先试试托管容器服务（如 ECS、Cloud Run），它提供容器部署能力但不暴露 K8s 的复杂度。不要为了「技术先进」上 K8s——它的运维复杂度是真实的。
