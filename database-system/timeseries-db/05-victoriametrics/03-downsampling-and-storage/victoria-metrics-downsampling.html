①为什么长期数据要降采样

监控/时序数据有两个特点：写入只增不减、越老越没人看明细。长期保留原始精度会带来存储膨胀和查询变慢——查"过去一年 CPU 均值"若还要扫每一条 10 秒级样本，代价巨大。降采样（downsampling）把老数据按更大时间粒度预聚合保存，既保住趋势又省空间。

核心权衡：降采样用"精度换存储与查询速度"。新鲜数据保留原始粒度，老数据只留分钟/小时级聚合。

②VictoriaMetrics 的两种降采样机制

VM 的降采样有两条路径：

摄入端 rollup（vmagent + 规则）

在采集侧用 stream aggregation 规则把原始系列实时聚合成分钟级，再写入；原始高精度数据可设短保留期，聚合数据长保留。

存储端 downsampling filter

VictoriaMetrics 支持按"数据年龄"自动降采样：超过 N 天的样本按配置的步长保留，旧样本被抽稀。

③配置示例

# 摄入端：vmagent 的 stream aggregation 规则（rollup）
- match: '{__name__=~"cpu_usage.*"}'
  interval: 1m            # 聚合成 1 分钟一个点
  outputs: [avg, max, min]   # 保留均值/最大/最小
  by: [instance, job]     # 按标签分组

# 存储端：downsampling（按数据年龄抽稀）
# -downsamplingPeriod=30d       旧于 30 天的进入降采样
# -downsamplingStep=1h          降采样后步长 1 小时

④精度损失与查询权衡

降采样后你查不到旧的秒级明细，但 avg/max/min 等聚合仍在。设计保留策略时：高频明细保留 7~15 天，分钟级聚合保留 90~180 天，小时级保留 1~2 年。这样"看趋势"和"查近因"都能满足。

数据年龄建议保留粒度用途
0~15 天原始（10s~1m）排障、查近因
15~180 天1 分钟聚合周/月趋势
180 天~2 年1 小时聚合长期容量规划

⑤与 Thanos / Cortex 的对比

Thanos/Cortex 也做降采样，但思路不同：Thanos 对块（block）做全局降采样生成独立的 5m/1h 分辨率块；VM 更偏向摄入端 rollup + 存储抽稀的组合，配置更轻量、单机也能跑。选型看你是已有 Prometheus 体系（Thanos 更顺）还是想用 VM 一体化。

rollup 规则示例

# vmagent 的 stream_aggregation 配置片段
stream_aggregation:
  - match: '{job=~".+"}'
    interval: 1m
    outputs: [avg, max, min, count]
    by: [__name__, instance, job]

排障：降采样后明细查不到、精度选择

明细消失：这是预期——降采样后旧数据只有聚合点。若必须保留明细，调长原始保留期或加大 downsamplingPeriod。

精度选择：步长太小省不了多少空间，太大则趋势失真；监控场景 1m/1h 通常够用。

rollup 与原始并存：rollup 产生的是新时间序列（带聚合后缀），不会覆盖原始序列，两者共存靠标签区分。

自检 Q&A

降采样会让告警变迟钝吗？

不会，因为告警看的是新鲜数据（原始粒度仍在保留期内）。降采样只影响历史查询的精度，不影响实时告警。

VM 单机也能降采样吗？

能。摄入端 rollup 靠 vmagent 即可，不依赖集群；存储端 downsampling 在单节点 VM 也支持，是 VM 相对 Thanos 轻量的优势之一。

rollup 产生的聚合序列怎么区分原始？

VM 会给聚合序列追加后缀（如 :avg、:max），并保留分组标签（by 指定的）。查询时按名字区分即可。
