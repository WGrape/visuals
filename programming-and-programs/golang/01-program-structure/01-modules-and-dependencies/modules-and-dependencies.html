概述

为什么需要 Modules

早期 GOPATH 要求代码必须放在固定路径下、无法锁定版本。Go 1.11 引入 Modules，让每个项目自带版本清单，彻底摆脱全局路径束缚。

go.mod 的结构

模块路径、Go 版本与依赖清单

go.mod 记录模块路径（import 前缀）、所需 Go 版本，以及直接/间接依赖。

module github.com/you/app

go 1.22

require (
    github.com/gin-gonic/gin v1.9.1
    golang.org/x/sync v0.6.0 // indirect
)

exclude github.com/bad/lib v1.0.0
replace old.io/lib => ./forks/lib
语义化版本与 MVS

最小版本选择（MVS）

Go 不取「最新版」，而是取「所有依赖约束要求的最高最小版本」——即满足各方下限的最高版本，保证可复现且避免意外升级。

版本格式 vMAJOR.MINOR.PATCH。v2+ 的模块必须在模块路径带 /v2 后缀，否则会被当作不兼容的不同模块。

replace 与 exclude

临时替换与排除

replace 可把某依赖指向本地路径或 fork；exclude 排除特定坏版本。多用于临时修复，正式发布前应尽量移除本地 replace。

// 本地调试 fork
replace github.com/foo/bar => ../bar

// 排除已知有问题的版本
exclude github.com/foo/bar v1.0.0

版本怎么选：最小版本选择 MVS

当多个依赖要求同一个模块的不同版本时，Go 采用最小版本选择：取所有要求中的最高版本。这与某些语言「取最新」或「取最先声明」都不同。

MVS：取所有要求中最高的那个版本
概念说明
语义化版本v主.次.修：主版本不兼容升级，次版本兼容新增，修订版修 bug
v2+ 路径主版本 ≥ 2 必须在模块路径后加 /v2
伪版本未打 tag 时用 v0.0.0-时间戳-提交哈希 表示
+incompatible未遵循模块规范的老项目标记
go.sum记录每个模块的哈希，防止依赖被篡改
GONOSUMDB/GOPRIVATE私有仓库跳过校验和数据库

v2 路径规则：module github.com/me/lib/v2，导入也必须写 github.com/me/lib/v2。这让 v1 与 v2 可以共存于同一个构建中，是 Go 解决版本共存的方式。

依赖管理的实践要点

日常流程

  • 加依赖：go get pkg@version
  • 删完代码后跑 go mod tidy
  • 提交 go.mod 与 go.sum 到仓库
  • 升级依赖显式执行，不要靠 tidy 悄悄升
# 查看可用升级 go list -m -u all # 升级到最新补丁版 go get -u=patch ./... # 升级某个依赖 go get github.com/gin-gonic/gin@latest go get github.com/gin-gonic/gin@v1.9.0

私有仓库

  • 设置 GOPRIVATE=git.company.com/*
  • 它会同时影响 GONOPROXY 与 GONOSUMDB
  • 配合 SSH 或带凭据的 HTTPS 访问
  • CI 里要配置好凭据
go env -w GOPRIVATE=git.company.com/* git config --global url.\"git@git.company.com:\".insteadOf \ \"https://git.company.com/\"

replace 的正确用法

  • 本地联调：replace pkg => ../local/pkg
  • 修 bug 临时替换到 fork
  • 不要把它留在最终提交里（会影响下游）
  • 多模块联调优先用 go.work
// go.work（本地多模块联调，不提交） go 1.22 use ( ./service-a ./service-b ./shared ) // go work init ./a ./b 创建 // go work sync 同步

深入自检

go.sum 要不要提交到仓库？

必须提交。它记录每个模块版本的加密哈希，保证你和 CI、同事拉到的是完全相同的依赖内容。缺少它或随意删除，会让依赖供应链的完整性失去保障。

为什么升级了依赖但代码里版本没变？

可能是 MVS 选择了更高版本，也可能是你没有真正执行 go get。用 go list -m all 查看实际生效版本，用 go mod why 查是谁引入的。

indirect 依赖需要手动管理吗？

一般不需要。它由 go mod tidy 自动维护。只有当间接依赖有安全漏洞、需要强制升级时，才在 require 里显式声明版本（此时它会变成直接依赖）。

replace 会有什么副作用？

replace 只对当前主模块生效，不会被下游模块继承。若把它提交进发布的库，使用者不会应用你的替换，容易产生「我这能编译，别人不行」的问题。

vendor 目录该用吗？

多数场景不需要。Go 模块缓存已经能保证离线与可复现。只有在需要完全锁定构建环境、或 CI 无法访问模块代理时，才考虑 go mod vendor。

go mod 常用命令

# 初始化与日常
go mod init github.com/me/proj      # 创建 go.mod
go mod tidy                          # 增删依赖、整理 go.sum（提交前必跑）
go get github.com/x/y@latest         # 加/升到最新
go get github.com/x/y@v1.2.3         # 指定版本
go get -u ./...                      # 升级所有直接依赖（谨慎）
go list -m all                       # 列出所有模块依赖
go list -m -versions github.com/x/y  # 看可用版本

# 诊断
go mod why github.com/x/y            # 为什么依赖它（谁引入的）
go mod graph                         # 依赖图
go mod verify                        # 校验 go.sum

# 常用环境变量
go env -w GOPROXY=https://goproxy.cn,direct    # 国内镜像
go env -w GOFLAGS=-mod=mod
go env -w GOPRIVATE=github.com/mycorp/*        # 私有仓库不走代理、不校验 sum

# vendor（把依赖拷进仓库，离线构建）
go mod vendor
文件 / 变量作用是否提交
go.mod依赖声明✅ 必提交
go.sum依赖哈希校验✅ 必提交
vendor/依赖副本看团队约定
GOPROXY代理地址国内配 goproxy.cn
GOPRIVATE私有仓库前缀配了才不走代理

版本规则：Go 用语义化版本 + 最小版本选择（MVS）——多个依赖要求不同版本时，选能满足全部要求的最低版本，而不是最新版。

第三层 · 排障与边界：依赖问题的定位

现象原因怎么查 / 怎么办
missing go.sum entrygo.sum 缺条目跑 go mod tidy
checksum mismatch依赖被改过 / 代理缓存污染go clean -modcache 后重装；确认代理可信
ambiguous import同一个包被两个模块提供go mod why 找来源，用 replace 统一
私有仓库拉不下来走了公共代理或需要认证配 GOPRIVATE / GONOSUMDB；配 git 凭证
module ... found, but does not contain package路径写错或版本不对确认导入路径与版本；大版本要加 /v2 后缀
  • 排查顺序：先 go mod tidy → 再 go mod why 找来源 → 再看 GOPROXY/GOPRIVATE 配置 → 最后清 modcache 重试。
  • 边界一：大版本号 ≥2 必须体现在导入路径里：github.com/x/y/v2，这是 Go Modules 的硬性规则，漏了 /v2 会报奇怪的错。
  • 边界二：go.sum 里记录的是所有历史依赖的哈希，不只是当前用的——所以 tidy 后它可能比预期长，这是正常的。
  • 边界三：replace 只在本模块生效，不会传递给下游——你 replace 的版本，别人拉你的库时不生效。

依赖排查命令

# 一键排查：谁引入了这个依赖
go mod why -m github.com/x/y

# 清缓存重来（解决 checksum mismatch 常用）
go clean -modcache && go mod download

# 查看最终选中的版本（MVS 的结果）
go list -m github.com/x/y

# CI 里校验依赖没被偷偷改过
go mod verify && go mod tidy -diff   # Go 1.23+ 支持 -diff
为什么会选「最低」版本而不是最新？

这是 Go 的最小版本选择（MVS）设计：保证构建的可复现性与向后兼容。只要你依赖的库声明 go 1.x 且遵循语义化版本，选最低满足版本就是安全的，也让依赖图更稳定（不会因为某个库升了小版本就把你的构建搞崩）。

go.sum 要不要提交？

必须提交。它记录每个依赖的加密哈希，防止依赖被篡改（供应链攻击）。CI 里应该跑 go mod verify。

replace 什么时候用？

两种场景：① 本地调试——把依赖指向本地目录，改了立刻生效；② 临时修复——上游有 bug 未发版，先 replace 到自己的 fork。注意它不传递给下游，所以正式修复还是要提 PR 给上游。
