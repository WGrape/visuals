Prometheus 时间线容量与上手陷阱

沿抓取间隔、标签基数、保留期与磁盘预算估算容量，并检查常见误配。

Prometheus

06上手时最容易踩的坑

  1. 把高基数标识当 label：user_id、order_id、URL 路径参数。每一组唯一 label 组合就是一条独立时间线，百万级时间线会直接拖垮 Prometheus。这类信息应该进日志或追踪系统。
  2. 用 Gauge 表示累计量：累计值必须用 Counter + rate()，否则服务重启导致归零时曲线会莫名其妙。
  3. 直接对 Counter 求平均：avg(http_requests_total) 没有意义，必须先 rate() 再聚合。
  4. 告警用瞬时值：瞬时抖动会疯狂刷屏。用 for: 5m 要求条件持续满足，或用 range 选择器看一段时间。
  5. 抓取间隔与告警判定周期脱节：间隔 60s 却写 for: 10s，条件还没被第二次求值就已经触发了。
版本相关提示：默认抓取间隔、默认保留期、告警规则字段、remote_write 的具体配置格式会随版本调整。请以你部署版本的官方文档为准，本文只讲机制不写死参数。

下面的默认值与经验数字仅作算例；版本、WAL 配置和实际压缩率不同，部署前应以运行实例和真实标签分布重新测量。

Prometheus 关键参数与容量估算

Prometheus 是拉取（pull）模型的时序库，理解它的抓取周期、标签基数、本地存储限制这三个参数，就能估算容量并避开最常见的坑。

参数默认值作用调优建议
scrape_interval15s（全局）/ 15s（job）多久抓一次指标核心业务 5~10s；一般 15~30s；调小成本线性上升
scrape_timeout10s单次抓取超时必须 < scrape_interval
evaluation_interval15s / 1m多久算一次告警规则通常和 scrape_interval 一致或 2 倍
--storage.tsdb.retention.time15d本地数据保留多久本地只做短期；长期用远程存储
--storage.tsdb.retention.size无（新版支持）按大小限制磁盘小的机器建议设，如 50GB
--storage.tsdb.wal-segment-size128MBWAL 分段大小一般不动
--query.max-concurrency20并发查询数查询多可调大
--query.timeout2m查询超时重查询会拖垮实例，务必保留
维度数量说明
单个样本大小~1~2 字节（压缩后）TSDB 用 delta + XOR 压缩，效率极高
series 数 = 容量主因见下100 万 series、15s 间隔 ≈ 每秒 6.7 万样本
内存估算~每百万 series 约 3~5 GB官方经验值，含 head block + 索引
磁盘估算每秒样本数 × 2 字节 × 保留秒数6.7 万/s × 2B × 15 天 ≈ 173 GB
基数爆炸警戒线单 metric >1 万 series 要警惕高基数 label 是头号杀手

运维命令

# 启动参数示例
prometheus \
  --config.file=/etc/prometheus/prometheus.yml \
  --storage.tsdb.path=/prometheus \
  --storage.tsdb.retention.time=15d \
  --storage.tsdb.retention.size=100GB \
  --web.enable-lifecycle \          # 支持热重载配置
  --web.enable-admin-api            # 支持删除 series 等管理操作

# 热重载（不用重启）
curl -X POST http://localhost:9090/-/reload

# 查看当前 TSDB 状态（最有用的容量诊断）
curl -s http://localhost:9090/api/v1/status/tsdb | jq
#   关注：headSeries / numSeries / headChunk / timeSeriesCount

# 基数排查：找出 series 最多的 metric（救命命令！）
topk(20, count by (__name__)({__name__=~".+"}))

# 找出某个 metric 下哪个 label 在爆炸
topk(20, count by (label_name)(metric_name))

# 单个 series 的字节占用估算
curl -s 'http://localhost:9090/api/v1/series?match[]=up' | jq '.data | length'
  • 基数爆炸是第一杀手：把 user_id、request_id、url_path（带参数）、trace_id 做成 label，会让 series 数从几千暴涨到百万级，直接 OOM。label 只能放低基数（有限枚举）的维度。
  • pull 模型的好处：① 服务端不需要知道被监控对象在哪（服务发现）；② 抓取失败立刻知道（up=0）；③ 可以在本地用 curl 手动验证；代价是需要网络可达被监控端（推模型更容易穿 NAT）。
  • Prometheus 不是长期存储：本地默认只留 15 天，且单机无副本。长期和HA 要靠远程存储（Thanos / Cortex / VictoriaMetrics / Mimir）。
  • 不要用 Prometheus 存业务明细：它是为指标设计的（数值型、可聚合），不是事件/日志系统。订单、用户行为明细应该进日志或数仓。
  • recording rule 是性能优化的利器：把常用但昂贵的查询预计算成新 series，能把仪表盘加载从 10 秒降到 100 毫秒。
  • scrape_interval 调小的代价是线性的：15s→5s 意味着数据量翻 3 倍。只给真正需要的核心指标用高频，其他保持 30s 或 60s。
为什么 Prometheus 不适合做长期存储？

设计定位决定了三点限制：① 单机、无副本——Prometheus 本身是单进程，数据存在本地磁盘，实例挂了数据就没了，也没有跨节点复制；② 本地存储有保留期（默认 15 天），它的 TSDB 是为「最近数据高频查询」优化的，不是为归档设计；③ 无法水平扩展——不能简单地加机器分摊数据，联邦（federation）只能解决聚合查询的问题，不能解决单实例容量问题。所以社区的标准答案是分层：Prometheus 负责抓取和短期告警（15 天），长期存储交给 Thanos（对象存储 + 全局查询）、Cortex/Mimir（多租户 + 水平扩展）或 VictoriaMetrics（单机性能更强、资源占用更低）。如果你的规模不大（<100 万 series），VictoriaMetrics 单机方案往往是最省心的选择。

series 数暴涨怎么排查和止血？

三步：① 定位——跑 topk(20, count by (__name__)({__name__=~'.+'})) 找出 series 最多的 metric，再对可疑 metric 跑 topk(20, count by (某个label)(该metric)) 看是哪个 label 在爆炸；② 止血——在 scrape_config 里用 metric_relabel_configs 把高基数 label drop 掉，或整个 metric 不采集： 

metric_relabel_configs:
  - source_labels: [url_path]
    regex: '/api/.*'
    action: drop
③ 清理历史——开 --web.enable-admin-api 后用 POST /api/v1/admin/tsdb/delete_series 删除已入库的脏数据。长期要做的是在代码层面禁止把高基数字段做成 label（如把 user_id 从 label 里去掉，只保留聚合后的计数），并建立 series 数的告警（如 prometheus_tsdb_head_series > 800000）提前预警。

pull 和 push 模型该怎么选？

Prometheus 的 pull 适合：长驻服务（你的 Web 服务、数据库、消息队列）——服务发现 + 定期拉取很自然，且拉不到立刻知道它挂了。不适合：短生命周期任务（CronJob、批处理、FaaS）——任务结束就没得拉了。后者的标准解法是 Pushgateway，但要注意它的定位是临时中转而非长期存储（Pushgateway 不会自动清理、没有 up 指标语义、多个实例推送会互相覆盖，官方明确说只用于批处理场景）。另外，如果你的网络架构是「被监控端在 NAT 后面 / 跨公网」，pull 会很麻烦，这时 push 模型（如 StatsD、OpenTelemetry 推）工程上更省事。现代趋势是 OpenTelemetry 统一采集 + 后端可选——既能推也能拉，不再二选一。
