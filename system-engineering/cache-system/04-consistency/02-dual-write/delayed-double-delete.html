权衡

多一次延迟换收敛

先建立直觉：擦黑板要擦两次

你在黑板上改一个数字。第一次擦黑板时，有同学正在抄旧内容；等你改完，他把自己抄的旧内容又写回了旁边的小黑板。所以你改完之后，需要等同学们都抄完，再去把小黑板擦一遍。

延迟双删就是这个「擦两次、中间等一会儿」的动作。

它要解决的问题

延迟双删是针对「先删除缓存，再更新数据库」策略的补救。这个策略的经典并发坑是：

  1. 写线程 A：删除缓存；
  2. 此时读线程 B 进来，缓存 miss，查库拿到旧值，并写回缓存；
  3. 写线程 A：更新数据库（新值）；
  4. 结果：缓存里是 B 写回的旧值，数据库是新值 → 长期脏数据，直到 TTL 过期。

延迟双删的做法是在第 3 步之后等待一小会儿，再删一次缓存，把 B 写回的旧值清掉。

// 伪代码：延迟双删
redis.del(key);              // ① 第一次删除
db.update(data);             // ② 更新数据库
Thread.sleep(500);           // ③ 等待并发读请求完成
redis.del(key);              // ④ 第二次删除，清理旧值

sleep 多久？

这是延迟双删最难的部分。sleep 时长必须大于「一次读请求从查库到写回缓存」的完整耗时，否则第二次删除发生在 B 写回之前，等于白删。经验值是几百毫秒到 1 秒（依据实际读耗时评估，可参考接口 P99 延迟），但这个值无法精确保证——这正是该方案的主要缺陷。

它真的值得用吗？

对比延迟双删先更库后删（Cache-Aside）
写操作耗时增加一次 sleep（几百 ms）无额外延迟
脏数据产生条件并发读落在删除与更新之间（较宽松）缓存恰好失效 + 读抢在写之前（极苛刻）
清理成功率依赖 sleep 时长，不保证删除失败才残留，可用重试兜底
复杂度中（要调 sleep 参数）低
结论：如果你使用的是推荐的「先更新数据库、再删除缓存」，脏数据产生的条件已经极其苛刻（缓存恰好失效 + 读操作抢在写之前完成），延迟双删带来的收益很小，却要付出一次 sleep 的延迟代价，通常不值得。延迟双删主要是为「先删缓存」策略打补丁。

更可靠的替代方案

  1. binlog 订阅删除：由 Canal 等中间件监听数据库变更并删除缓存，带重试与持久化，比 sleep 可靠得多。
  2. 重试队列：删除失败入队重试，解决偶发失败。
  3. 合理的 TTL：无论什么策略，都要给缓存设 TTL 作为最终兜底。
  4. 版本号 / CAS：写缓存时携带版本号，旧版本写入直接丢弃，从根上避免旧值覆盖。
一句话建议：与其依赖「sleep 猜一个时间」，不如用可重试的异步删除 + TTL 兜底。前者是概率性的，后者是确定性的。

🎯 面试问答

Q：延迟双删的 sleep 到底设多少？
A：原则是大于一次读请求「查库 + 写缓存」的耗时，实践中可参考该读接口的 P99 延迟再加余量，常见取值 500ms~1s。但这个值无法精确保证——网络抖动、数据库慢查询都可能让某个读请求超过这个时间，此时第二次删除就失效了。这正是延迟双删的固有缺陷，也是它逐渐被 binlog 订阅方案取代的原因。

Q：为什么现在不推荐延迟双删了？
A：两个原因：① 主流写策略已改为「先更新数据库、再删除缓存」，在该策略下脏数据产生条件极苛刻，延迟双删收益极小；② sleep 是一个不确定的猜测，既增加写延迟又不能保证成功，而 binlog 订阅 + 重试队列是确定性的方案。用它不如把架构做对。

Q：如果已经在用「先删缓存」，一定要加延迟双删吗？
A：强烈建议加，或者更好的是改成「先更库后删」。「先删缓存」在并发下产生脏数据的条件比较宽松（只要有一次并发读落在窗口内），不加补救会长期留下旧值。但即便要补救，优先级也是：先考虑改成「先更库后删」→ 其次用 binlog 订阅 → 最后才是延迟双删。

Q：第二次删除失败了怎么办？
A：和第一次删除一样需要重试兜底。如果第二次删除失败且没有重试，延迟双删就完全失效了——脏值会一直留到 TTL 过期。所以正确做法是：两次删除都要有失败重试机制（重试队列或 binlog 订阅），并且必须给缓存设 TTL 作为最后一道防线。

延迟双删的时机与参数

参数取值依据
第二次删除的延迟200~500ms必须 > 「读请求：查 DB → 写缓存」的耗时，通常 50~200ms
实现方式延迟消息队列 / 定时线程池不要在请求线程里 sleep，会占满线程池
重试次数3 次，间隔递增删失败要有兜底，否则不一致窗口变永久
TTL 兜底5~30 分钟所有主动失效都可能失败，TTL 是不一致的上界
适用前提已经用了「先删缓存再更新 DB」如果是「先更新 DB 再删缓存」，一般不需要双删

延迟双删解决的是什么：在「先删缓存 → 更新 DB」方案里，删除与更新之间有个窗口；此时若有读请求进来，会读到 DB 的旧值并写回缓存。之后这个旧值会一直待到 TTL 过期。延迟双删就是在 DB 更新完成后，再删一次，把这个窗口期被回填的脏数据清掉。

实现（不要用 sleep 阻塞请求）

# ❌ 错误：在请求线程里 sleep 300ms，高并发下线程池直接被打满
def update(item_id, val):
    cache.delete(key)
    db.update(...)
    time.sleep(0.3)          # 占着线程干等，QPS 直接腰斩
    cache.delete(key)

# ✅ 正确：投递延迟消息，由消费者执行第二次删除
def update(item_id, val):
    cache.delete(key)
    db.update(...)
    mq.send_delay("cache_del", {"key": key}, delay_ms=300)   # RocketMQ/RabbitMQ 延迟消息

@mq.consume("cache_del")
def on_delay_delete(msg):
    for i in range(3):                      # 失败重试 3 次
        try:
            cache.delete(msg["key"]); break
        except Exception:
            time.sleep(0.05 * (i + 1))      # 消费者里 sleep 无所谓
// Java：用定时线程池，别用 Thread.sleep 阻塞业务线程
private final ScheduledExecutorService sched = Executors.newScheduledThreadPool(2);

public void update(Long id, Item v) {
    redis.del(key(id));
    itemMapper.update(v);
    sched.schedule(() -> redis.del(key(id)), 300, TimeUnit.MILLISECONDS);
}

// RocketMQ 延迟消息（更可靠，支持重试与持久化）
// 延迟级别：1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h
// 选 1s 级别做双删即可，不必精确 300ms
Message msg = new Message("CACHE_DEL", key.getBytes());
msg.setDelayTimeLevel(2);     // 5s
producer.send(msg);

排障清单

症状原因处理
用了双删但仍有脏数据延迟 < 读请求回填耗时；或第二次删除失败先测「读 DB + 写缓存」的 p99 耗时，延迟要大于它；删除加重试
接口 RT 明显变长在请求线程里 sleep改延迟消息或定时线程池
消息堆积导致删除更晚延迟队列积压监控延迟队列堆积；双删是兜底，不能作为唯一手段
主从延迟导致读到旧值读从库，从库落后主库几百 ms~秒敏感读走主库；或延迟时间 > 主从延迟（不现实）——更推荐改用「先更新 DB 再删缓存」
最终还是不一致多实例并发写 + 乱序加版本号/乐观锁；或用 binlog 订阅统一删
改动量太大不想引入 MQ架构成本直接改成「先更新 DB 再删缓存 + 删除重试」，多数场景已足够

结论：延迟双删是「先删缓存」方案的补丁，不是首选方案。新系统直接用「更新 DB → 删缓存 → 失败重试」，简单且收敛窗口更短；对一致性要求极高的场景用 Canal 订阅 binlog 删缓存。
