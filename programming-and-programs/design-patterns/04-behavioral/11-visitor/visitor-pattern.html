01 · 从问题出发

为什么会需要这个模式？

语法树节点类型稳定，但要频繁新增格式化、类型检查、代码生成等操作。

语法树已有 Number、Add 等节点。现在需要格式化、类型检查、统计节点数；若把每种操作都塞入节点类，节点代码会随着新操作不断膨胀。

😵 直接写会怎样

class AddNode:
  format() ...
  typeCheck() ...
  countNodes() ...
  generateCode() ...  // 每加一种操作都改节点

💡 关键转折

节点提供 accept(visitor)；访问者按具体节点类型实现 visitX。

节点只提供 accept(visitor) 入口；访问者按节点类型实现操作。新增操作时新增访问者，结构中的节点可保持稳定。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

interface Visitor { visitNumber(node); visitAdd(node) }
class NumberNode {
  accept(visitor) { return visitor.visitNumber(this) }
}
class AddNode {
  accept(visitor) { return visitor.visitAdd(this) }
}
class PrettyPrinter implements Visitor {
  visitNumber(n) { return String(n.value) }
  visitAdd(n) { return n.left.accept(this) + "+" + n.right.accept(this) }
}

读代码时抓住三件事

  1. accept 是第一次分派：由具体节点选择 visitNumber/visitAdd。
  2. visitX 是第二次分派：访问者按节点类型执行逻辑。
  3. 复合节点的访问者方法可递归调用孩子的 accept。

换个业务场景，还能认出来吗？

编译器常用访问者对 AST 做静态检查、代码生成和优化分析。若语法节点经常新增，维护每个访问者的方法会很累；访问者适合节点结构相对稳定、操作经常新增。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

对象结构稳定，但要频繁增加作用于整棵结构的操作

三个具体场景

  • AST 增加格式化与类型检查
  • 文档树增加导出与统计
  • 商品结构增加税费和审计分析

不适合或要小心

新增节点类型会迫使所有访问者增加方法；若节点常变，访问者可能反而增加维护成本。

新增节点类型会迫使每个访问者增加方法

最容易混淆的相邻模式

模式真正的区别
策略替换一套算法；访问者让一套操作按多种节点类型分别执行。
组合构建树形节点结构；访问者把作用于整棵树的操作从节点类分离。

区分时问自己：新需求主要增加节点种类，还是增加针对已有节点的操作？

落地前检查

  • 新增节点类型前统计已有访问者数量。
  • 给每个访问者覆盖所有节点类型。
  • 避免访问者直接修改不该暴露的节点内部状态。
06 · 自己说一遍

两道检验理解的小题

新增“统计节点数”会修改所有节点吗？

通常只需增加一个 Visitor 实现，已有节点继续调用 accept。

访问者为何被说成“双重分派”？

执行结果同时由“具体节点类型”和“具体访问者类型”决定：节点的 accept 调用对应 visitX，访问者实现再决定操作。

核心速览

一句话把「对结构中各元素的操作」抽出来，从而不改元素类就能加新操作
解决什么元素类稳定、操作经常增加时，避免在元素类里堆一堆方法
代价加新的元素类型很痛苦——所有访问者都要改
所以适用元素种类稳定 + 操作频繁增加，反过来就别用
访问者：双分派让「新操作」只需加一个类，不用改元素

一、它解决了什么问题

假设有一棵表达式 AST：Number、Add、Mul。现在要支持「求值」「打印」「类型检查」。如果把这些方法都塞进节点类，加一个操作就要改三个类。

// 元素接口：只需要一个 accept type Node interface{ Accept(v Visitor) } type Number struct{ V int } func (n *Number) Accept(v Visitor) { v.VisitNumber(n) } type Add struct{ L, R Node } func (a *Add) Accept(v Visitor) { v.VisitAdd(a) } // 访问者接口：每种元素一个方法 type Visitor interface { VisitNumber(n *Number) VisitAdd(a *Add) VisitMul(m *Mul) } // 加新操作 = 加一个新的访问者，元素类完全不动 type EvalVisitor struct{ result int } func (e *EvalVisitor) VisitNumber(n *Number) { e.result = n.V } func (e *EvalVisitor) VisitAdd(a *Add) { a.L.Accept(e); l := e.result a.R.Accept(e); e.result = l + e.result } type PrintVisitor struct{ sb strings.Builder } type TypeCheckVisitor struct{ ty Type; err error } // 这就是「双分派」： // 第一层：node.Accept(v) 根据 node 的真实类型分派 // 第二层：v.VisitXxx(node) 根据 v 的真实类型分派

二、适用性的双向判断

维度适合访问者不适合访问者
元素种类稳定，很少增加经常增加新类型
操作种类经常增加稳定不变
加新操作的成本新增一个类改所有元素类
加新元素的成本改所有访问者新增一个类（反而更好）
这是整个模式最大的取舍

访问者让「加操作」变容易、让「加元素」变困难，这正好和「把方法放进元素类」相反。所以判断标准只有一句话：哪个变化更频繁，就让哪个容易加。AST、文件格式、报表结构这类元素稳定的场景才适合。

模式关注区别

四、真实场景

编译器 AST语义分析、类型检查、代码生成、优化各自一个访问者

文件系统遍历统计大小、查找、权限校验
序列化与反序列化同一结构写成 JSON、XML、Protobuf

五、深入自检

什么叫双分派？

普通方法调用只根据「接收者类型」分派一次。访问者做了两次：先根据元素类型决定调哪个 Accept，再根据访问者类型决定调哪个 Visit。两次分派合起来，就能在「元素 × 操作」的二维空间里精确定位。

Go 里没有方法重载，怎么实现？

用接口 + 每个元素一个具名方法（VisitNumber / VisitAdd），这正是上面示例的写法。虽然不如 Java 的重载优雅，但语义完全等价，而且更显式。

访问者能修改元素吗？

可以，但要注意：修改元素结构（增删节点）会让正在进行的遍历失效。安全做法是先收集要做的修改，遍历结束后再统一应用。

为什么很多人说访问者模式很少用？

因为它的适用条件很窄（元素稳定 + 操作多变），而且让代码变得间接、难读。在函数式语言里，模式匹配 + 递归往往能更简洁地表达同样的逻辑。

和模式匹配怎么比较？

模式匹配也能实现「按类型分派」，而且加新操作同样只需加一个函数。但模式匹配在加新类型时编译器会报错提醒（更友好），而访问者则是漏掉某个 Visit 才报错。Go/Rust 这类语言里，很多时候用类型开关（type switch）就够了。

记住一句元素稳定、操作多变时才用
核心机制双分派：Accept + Visit
最大代价加新元素要改所有访问者
经典场景编译器 AST、多态导出
