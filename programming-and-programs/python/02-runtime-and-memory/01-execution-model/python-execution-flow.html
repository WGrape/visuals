一句话总结：Python 的"慢"本质上是因为多了一层虚拟机抽象——每条字节码指令都需要 PVM 去解释、分发、执行，而 C 编译出来的是 CPU 能直接跑的指令。
更准确地说：Python 是 编译 + 解释 的混合模式，不是纯解释型语言。

从源码到结果：中间经历了什么

Python 常被叫做解释型语言，但它并不是「读一行执行一行」。真实流程是：先把源码编译成字节码，再由虚拟机执行字节码。理解这点，很多现象（比如 pyc 文件、语法错误发生在运行前）就都解释得通了。

执行链路：源码 → 语法树 → 字节码 → 虚拟机执行，字节码会被缓存
为什么先编译编译一次、执行多次，避免重复解析
语法错误何时报在编译阶段就报，所以一行没跑到也可能出错
字节码是什么类似汇编的中间指令，比源码更接近机器
虚拟机是什么一个基于栈的解释循环，逐条取出指令执行

字节码与缓存文件

编译产物会被缓存下来，这就是为什么第二次导入同一个模块明显更快。缓存是否失效，取决于源文件是否变化。

概念内容作用
代码对象编译后的字节码与常量、变量名运行时真正被执行的东西
缓存文件字节码写到缓存目录的文件避免每次重新编译
缓存判定按源文件的修改时间与大小判断变了才重新编译
缓存位置源码目录下的缓存子目录通常不需要提交到版本库
import dis def add(a, b): return a + b dis.dis(add) # 输出类似： # RESUME 0 # LOAD_FAST 0 (a) # LOAD_FAST 1 (b) # BINARY_OP 0 (+) # RETURN_VALUE # 怎么看： # LOAD_FAST 把局部变量压入栈顶 # BINARY_OP 弹出两个操作数，运算后再压回 # RETURN_VALUE 取栈顶返回 # 这正是「基于栈的虚拟机」的含义 # 手动编译，观察中间产物 code = compile("1 + 2", "<string>", "eval") code.co_code # 字节码字节序列 code.co_consts # 常量表 code.co_names # 名字表 # 缓存目录：源码所在目录下的 __pycache__ # 文件名形如 module.cpython-311.pyc，含实现与版本标识

命名空间与帧：变量存到哪去了

三个命名空间的分工

内置命名空间放语言自带的名字，全局命名空间放模块级名字，局部命名空间放函数内的名字。它们的生命周期不同：内置的随解释器，全局的随模块，局部的随一次函数调用。

为什么局部变量更快

因为局部名字在编译期就确定为一个固定槽位，运行时直接按索引取，不需要查字典；而全局名字要查字典。这也是把循环里反复访问的全局值存成局部变量能提速的原因。

内置命名空间语言自带的名字，解释器启动时就有
全局命名空间模块级名字，模块加载时创建
局部命名空间函数调用时创建，返回时销毁
查找顺序局部 → 外层 → 全局 → 内置
局部按槽位编译期确定，访问快
全局查字典运行时查找，访问慢一些
帧栈每次调用压入一个帧，保存局部状态
帧里有什么局部名字、求值栈、上一条指令位置

深入自检：执行模型的六个问题

Python 是编译型还是解释型？

两者都有：源码会被编译成字节码，字节码再由虚拟机解释执行。和 C 这类语言的差别在于，它编译到的是虚拟机指令而不是机器码，而且编译过程对用户是自动透明的。

为什么第一次运行慢一点？

因为要编译并写缓存文件。之后只要源文件没变，就直接加载缓存跳过编译。这也是为什么清理缓存目录后第一次启动会变慢。

缓存文件需要提交到版本库吗？

不需要，通常由构建产物忽略规则排除。它会随 Python 版本与源文件变化自动重新生成，提交反而会造成不同环境下的冲突。

语法错误为什么在没执行到时就报？

因为编译发生在执行之前，而且是整个模块一起编译。所以哪怕错误在最后一行、第一行也会先失败。这正是「先编译后执行」的直接证据。

能不能看到每行代码对应的字节码？

可以。用标准库里的反汇编工具查看函数或代码对象的字节码，它会列出每条指令的名字与参数。想知道某段写法到底做了多少次操作，这是最直接的办法。

为什么要了解字节码？

因为很多性能问题在源码层看不出来：两种写法看起来差不多，字节码可能差一倍。它还能解释一些反直觉的现象，比如为什么局部变量访问比全局快。

3.11+ 的自适应特化

机制说明效果
内联缓存字节码里缓存上次操作的类型与方法地址属性/方法访问显著变快
特化指令BINARY_OP_ADD_INT 等针对具体类型的快路径算术与下标操作加速
去优化类型变化时退回通用指令保证语义正确
warming同一条指令执行约 8 次后触发特化（阈值随版本变化）短命代码可能来不及特化

实用含义：热路径要在循环里反复执行才能吃到特化红利；单次调用的代码路径收益有限。

深入自检

.pyc 文件是机器码吗？

不是。pyc 只是把「词法分析 → 语法分析 → 编译」的结果（字节码 code object）序列化缓存下来，省掉每次导入都重新编译的开销；真正的执行仍由 PVM 逐条解释字节码。

Python 是编译型还是解释型？

两者兼有：源码先被编译成平台无关的字节码（这一步是编译），再由 PVM 解释执行字节码（这一步是解释）。所以「纯解释」的说法不准确，关键在于没有生成机器码（除非用 Cython/Nuitka/numba 之类）。

3.11 的自适应解释器做了什么？

它在字节码里加了一层内联缓存与类型特化：同一条指令反复执行同类操作时，会被替换成针对该类型的快路径（如整数加法专用指令），类型变化则去优化退回通用路径。这让热代码显著加速，而语义保持不变。

修改源码后 Python 怎么知道要重新编译？

通过比对源文件记录：pyc 头部存有源文件的 mtime 与 size。只要二者之一与当前源文件不符，就判定缓存失效并重新编译。这也是为什么「改了内容但 mtime 与大小都没变」时缓存不会刷新。

递归深度为什么有 1000 的限制？

因为每次函数调用都会占用 C 栈上的解释器帧，过深会导致 C 栈溢出（真正的段错误）。CPython 用 setrecursionlimit(1000) 提前抛出 RecursionError 来保护 C 栈。正确做法是改写成迭代算法；盲目调大只是把崩溃推迟且可能真的崩在 C 层。
