InnoDB B+ 树完整结构：每个节点都是一页

这一篇只讲结构：MySQL 在 B+ 树里存了什么、索引怎么找到数据、页和页怎么串起来。

一句话钥匙：B+ 树上每一个节点就是一个 16KB 的数据页，页与页靠「页号」互相引用。 下面所有内容都是这句话的展开。

1. 整棵树长什么样

下面是一棵真实的 InnoDB B+ 树。每个方框 = 一页，框顶写页号； 页里从上到下是页目录（槽）和记录格子。 每个记录格子分成两半：上半是「键」，下半是它「指向」的东西 （非叶页指向子页号，叶子页直接就是数据）。

根页用页号向下指，非叶页继续向下指；叶子页之间用双向箭头串成一条有序链表

只要抓住三层：页 38 是根（只有 2 个键）、页 30 / 页 36 是非叶页（装「键 + 子页号」）、 页 10 / 22 / 16 / 8 是叶子页（装真正的数据）。从根走到任意叶子，最多 3 步。

2. 格子里的数字：键 / 页号 / 行 id

图上出现好几种数字，最容易混。它们是三件不同的东西：

概念是什么说明
键 索引列的值。聚簇索引里就是主键值（= 行 id）；二级索引里是索引列的值。 决定排序与查找方向，这才是我们要查的东西
页号 页的物理编号（页 30 = 第 30 号页）。 只用来定位「去哪儿读这一页」；和键值毫无关系，也不连号
行 id 主键列的值 —— 它就是聚簇索引里的那个键，只是换了个说法。 二级索引靠它回表找到整行

同一个数字出现在好几层，是同一回事吗

是同一个值，但用途不同。以 7 为例：

  • 根页里的 7 → 意思是「页 36 子树里最小的键是 7」；
  • 页 36 里的 7 → 同样只是边界；
  • 只有页 8（叶子页）里的 7 是真实数据行——id=7 那一整行。
父页只存「边界值」，不是所有键。所以 1 / 3 / 5 / 7 出现在父页（各子页的最小值）， 而 2 / 4 / 6 / 8 只在叶子页。父页那份是刻意保留的副本，只为「比大小决定往哪走」； 真正的数据永远只有叶子页那一份。
键指向一行还是一页？非叶页的键指向一个子页：3 → 页22 读作 「id ≥ 3 的记录从页 22 开始找」，而不是「id=3 在页 22」。只有叶子页的键才指向一行。

3. 换成非聚簇（二级）索引，图怎么变

结构一点没变，变的只有键的值和叶子页里放的东西：

同一棵树建在 name 列上：键从 1/3/5/7 变成 ann/betty/carl/dave

聚簇索引（主键树）二级索引（如 name）
键主键值 = 行 id索引列的值（name）
叶子页记录键 + 整行所有列键 + 主键值，就两样：(ann, 1)
非叶页的键子页里最小的主键子页里最小的 name
取数叶子页里就是整行，直接返回只拿到主键，还得回表
所以「格子里的数字是什么」没有固定答案：它取决于这棵树建在哪一列上—— 主键树里是主键值，name 索引里是 name 值，联合索引 (a,b) 就是「先比 a 再比 b」。 页号的含义始终不变。

4. 哪些连续、哪些不连续（叶子层与页号）

这是最容易误解的一点，分三句话说：

对象连续？说明
键连续 主图那一排是 1 → 2 → … → 8，一个不缺、不重叠、不留空洞。任何存在的键都能在某一页找到。
页号不连续 同一排是 10 → 22 → 16 → 8，根本不递增；而且也不从 0 开始（页 0/1/2 是元数据页）。
叶子链表顺序— 由页头 prev / next 串成，顺序 = 键的顺序，与页号大小无关。

页号按分配顺序增长；「哪一页属于这棵索引树」是跳着的

结论：连续的是「键」，不是「页号」。 键区间完整覆盖（所以范围扫描不漏），但页在文件里是散布的、编号是跳的—— 0/1/2 是表空间元数据页，数据页从 3 往后按需分配，中间还夹着二级索引、undo、blob 的页。 图上那些页号只是示意，别当成「第几页就是第几段数据」。

5. 一页里面有什么

不管根页、非叶页还是叶子页，内部布局都是同一套模板，永远三样： 页目录（槽）、记录单向链表、最小 / 最大记录。

一页的内部：6 条记录分成 2 组（每组 3 条），一个槽管一组、只指向组内最大的那条；所有记录仍由 next_record 串成一条链

  • 最小 / 最大记录：两条虚拟记录，比页内所有键都小 / 都大，是链表的头和尾，让「往前找、往后找」永远有落点。
  • 记录单向链表：每条记录存了「下一条记录的偏移量」，串成一条按键值排序的链。物理位置乱序，逻辑顺序严格。
  • 页目录（槽）：把页内记录按 4~8 条分成若干组，每组给一个「槽」，槽里只记这组里最大那条记录的位置（不是每条都记）。找一行时：先在槽上二分判断落在哪一组，再进那一组顺着链表走几步。

6. 索引与数据怎么关联

表本身就是一棵按主键排序的 B+ 树（聚簇索引）；每多建一个索引，就多一棵 B+ 树， 结构完全相同，只是叶子页里装的东西不同。

聚簇索引的叶子装着整行；二级索引的叶子只装「索引列 + 主键」

查询方式过程
主键查询走聚簇索引，3 步到叶子页，页里就是整行，直接返回。
普通列查询走二级索引拿到主键值 → 回表再走一遍聚簇索引取整行。
覆盖索引SELECT 的列全在二级索引里（含主键），不用回表，EXPLAIN 显示 Using index。

一次查询的完整旅程

  1. 拿到主键值，比如 WHERE id = 7；
  2. 读根页：在槽上二分，7 落在键 7 这一组 → 顺着记录里的页号去页 36；
  3. 读页 36：7 指向页 8，继续往下；
  4. 读页 8（叶子页）：槽上二分 + 链上走几步，找到 id = 7 的记录；
  5. 聚簇索引的这一条记录就是整行，直接返回；二级索引则取出主键回表再来一遍。
真正可能产生磁盘 IO 的只有第 2~4 步的「读一页」，而根页几乎永远在 Buffer Pool 里， 所以千万级表的一次主键查询，实际往往只有 1~2 次物理 IO。
