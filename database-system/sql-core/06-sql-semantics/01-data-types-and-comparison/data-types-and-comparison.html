①数值类型：精度是硬要求

类型特点适用
TINYINT/SMALLINT/INT/BIGINT精确整数，1/2/4/8 字节计数、ID、状态码
DECIMAL(p,s) / NUMERIC精确定点数，以字符串方式存储计算金额、费率、任何对账字段
FLOAT/DOUBLE近似浮点，二进制无法精确表示 0.1科学计算、容忍误差的度量值
-- 浮点误差的经典演示
SELECT 0.1 + 0.2 = 0.3;              -- 多数库返回 0（false）
SELECT CAST(0.1 AS DECIMAL(10,2)) + CAST(0.2 AS DECIMAL(10,2));  -- 0.30 精确
金额绝不用浮点。单笔误差看似微小，累加百万笔后对账必然对不上， 且误差方向不可预测、无法追溯。两种正确做法： ① DECIMAL(18,2) 或更高精度； ② BIGINT 存最小单位（分、厘），显示时再除——运算快且无精度问题，是金融系统的常见选择。
INT 溢出与无符号：INT UNSIGNED 在 MySQL 里做减法时若结果为负会报错或溢出， 跨语言驱动也可能处理不一致。ID 与计数直接用 BIGINT，省下的空间远不如排障成本。

②字符类型与排序规则

对比CHAR(n)VARCHAR(n)
存储定长，不足补空格变长 + 长度前缀
尾部空格取出时被去掉（多数实现）保留
适用长度固定的短码（国家码、MD5、UUID 定长时）绝大多数场景
  • n 是字符数不是字节数（MySQL 5.0+）。VARCHAR(100) 能存 100 个汉字， 但 utf8mb4 下最多占 400 字节，索引长度限制按字节算，这是建组合索引时常踩的坑。
  • TEXT/BLOB 与大字段：行溢出存储，读取要多一次 IO。 SELECT * 会把它一起拖出来。大字段单独建表是常见设计。
  • 排序规则（collation）决定比较与排序行为，不只是「大小写」。 _ci 不区分大小写、_ai 不区分重音、_bin 按字节。 两列 collation 不同会导致 JOIN 时索引失效（见「过滤条件」篇）。
  • utf8 vs utf8mb4：MySQL 的 utf8 是残缺的 3 字节实现， 存不了 emoji 和部分生僻字。一律用 utf8mb4。

③时间类型与时区

类型是否随时区转换范围适用
DATE否1000-01-01 ~ 9999-12-31生日、日期维度
TIME否可超过 24 小时时长
DATETIME否，存字面值同上（MySQL）业务时间、不随部署地变化的时间
TIMESTAMP是，存 UTC 并按会话时区显示1970 ~ 2038（2038 问题）日志时间、跨时区系统
TIMESTAMPTZ（PG）是无 2038 限制推荐：统一存 UTC
三条实践建议： ① 服务端统一用 UTC 存储，展示层转本地时区——避免迁移机房、夏令时带来的混乱； ② 注意 TIMESTAMP 的 2038 上限，长周期业务用 DATETIME 或 TIMESTAMPTZ； ③ 精度要明确，DATETIME(3)/(6) 决定毫秒/微秒能否存下，后期改要重写表。
不要用字符串存时间。'2026-10-18' 格式下比较看似可行， 但无法用时间函数、索引选择率估算差、格式一变就全乱。 也不要用 UNIX 时间戳 INT——可读性差且同样撞 2038。

④JSON、布尔与枚举

JSON / JSONB

PG 的 JSONB 是二进制存储、可建 GIN 索引，适合半结构化、读多写少、schema 易变的扩展字段。 MySQL 的 JSON 需配合生成列 + 索引才能高效查询。 别把它当万能方案——核心查询字段仍应提升为正式列。

BOOLEAN

MySQL 用 TINYINT(1) 表示，PG/标准有真正的 BOOLEAN。 注意 MySQL 里 TRUE=1，应用层映射时容易与「数量 1」混淆。

ENUM

存储紧凑、可读性好，但改枚举值要 ALTER TABLE（末尾追加在部分版本是元数据操作， 中间插入要重建）。频繁变化的字典建议用独立字典表 + 外键/应用缓存。

SET / 位标志

用整型位运算存多状态（权限位、标签位图）。查询无法走普通索引（需位运算）， 但空间极省。适合状态数量固定且不多、不需要按位查询的场景。

Q：手机号、身份证号用什么类型？
A：一律 VARCHAR。它们虽然「看起来是数字」，但不需要参与算术运算， 可能有前导零、可能超长、可能有国家码前缀。用 BIGINT 存手机号会在国际号、补零上出问题， 而且 phone = 13800138000 这种查询会触发隐式转换导致索引失效。
Q：IPv4 地址怎么存？
A：推荐 INT UNSIGNED + INET_ATON()/INET_NTOA()（4 字节、可范围查询）， 或 PG 的 INET 类型（支持 IPv6、有专门的运算符与索引）。 用 VARCHAR(15) 是最省事但最占空间的选择。

高频陷阱

-- 浮点陷阱（必看）
SELECT 0.1 + 0.2 = 0.3;                    -- MySQL: 0 (false)！
SELECT CAST(0.1 AS DECIMAL(10,2)) + CAST(0.2 AS DECIMAL(10,2));  -- 0.30
--   正确：金额一律 DECIMAL，或存「分」为 BIGINT

-- 隐式转换导致索引失效（最常见的慢查询原因之一）
--   user_no 是 VARCHAR
SELECT * FROM t WHERE user_no = 12345;     -- <b>索引失效</b>：字符串列被转成数字比较
SELECT * FROM t WHERE user_no = '12345';   -- 正常走索引
--   判断方法：EXPLAIN 看 type=ALL 且 key=NULL

-- 字符集/排序规则不一致导致 JOIN 变慢
SELECT * FROM a JOIN b ON a.code = b.code;
--   若 a.code 是 utf8mb4_general_ci、b.code 是 utf8mb4_0900_ai_ci -> 索引不可用
--   SHOW CREATE TABLE 检查，统一为 utf8mb4_0900_ai_ci

-- NULL 比较陷阱
SELECT * FROM t WHERE col = NULL;          -- 永远返回 0 行！
SELECT * FROM t WHERE col IS NULL;         -- 正确
SELECT * FROM t WHERE col != 'x';          -- <b>col 为 NULL 的行不会返回</b>
SELECT * FROM t WHERE col != 'x' OR col IS NULL;   -- 完整写法

比较语义与三值逻辑

SQL 用三值逻辑：TRUE / FALSE / UNKNOWN。NULL 参与的比较结果是 UNKNOWN，而 WHERE 只保留 TRUE——这是所有 NULL 相关 bug 的根源。

表达式结果说明
NULL = NULLUNKNOWN要用 IS NULL
NULL <> 'x'UNKNOWNNULL 行会被过滤掉
NULL AND TRUEUNKNOWN
NULL OR TRUETRUEOR 里有一个 TRUE 就是 TRUE
NOT NULLUNKNOWN
NULL IN (1,2)UNKNOWN
NULL IN (NULL)UNKNOWN
COUNT(col)跳过 NULLCOUNT(*) 不跳过
SUM(col)跳过 NULL；全 NULL 返回 NULL用 COALESCE(SUM(col),0)

三值逻辑实测

-- 三值逻辑实测
SELECT
  (NULL = NULL)      AS a,   -- NULL
  (NULL <> 'x')      AS b,   -- NULL
  (NULL OR TRUE)     AS c,   -- 1 (TRUE)
  (NULL AND FALSE)   AS d;   -- 0 (FALSE)   <- AND 里有 FALSE 就是 FALSE

-- NOT IN 的经典陷阱（子查询里有 NULL 会导致 0 行）
SELECT * FROM t WHERE id NOT IN (SELECT id FROM s);
--   若 s.id 有 NULL -> 整个条件变成 UNKNOWN -> <b>返回 0 行</b>
--   解法 1：SELECT * FROM t WHERE id NOT IN (SELECT id FROM s WHERE id IS NOT NULL)
--   解法 2（推荐）：NOT EXISTS 不受 NULL 影响
SELECT * FROM t WHERE NOT EXISTS (SELECT 1 FROM s WHERE s.id = t.id);

-- 空字符串与 NULL 是两回事
SELECT * FROM t WHERE col = '';     -- 只匹配空串
SELECT * FROM t WHERE col IS NULL;  -- 只匹配 NULL

-- 类型对齐（JOIN 慢的隐形杀手）
--   两边类型不同（INT vs VARCHAR）-> 隐式转换 -> 索引失效
--   SHOW CREATE TABLE t\G 对比字段类型
  • 建表时把列设为 NOT NULL + 默认值：能消除绝大多数三值逻辑问题，且索引和比较都更快。允许 NULL 的列要多 1 字节/null 位图。
  • 金额用 DECIMAL 或「分」为单位的 BIGINT，绝不用浮点。若已用浮点，聚合时要 ROUND 后再比对。
  • WHERE 条件里的列不要套函数：WHERE DATE(created_at) = '2026-01-01' 会让索引失效，改成 WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02'。
  • 跨库迁移要检查类型映射：MySQL DATETIME（无时区）vs PG timestamp（无时区）/timestamptz（有时区）；MySQL TINYINT(1) 常被误当 boolean。
为什么 WHERE col != 'x' 查不到 NULL 的行？

因为 NULL != 'x' 的结果是 UNKNOWN，而 WHERE 只保留结果为 TRUE 的行。这不是 bug 而是 SQL 标准定义：NULL 表示「未知」，未知的值是否等于 'x' 也是未知的。所以业务上要显式写 OR col IS NULL，或者建表时就禁止 NULL。

DECIMAL 和 FLOAT 该选哪个？

金额、计量、任何需要精确比较的场景用 DECIMAL；科学计算、容忍误差且范围极大的场景用 FLOAT/DOUBLE。DECIMAL 在 MySQL 里是定点数（按字符串方式存），DECIMAL(10,2) 占约 5 字节，计算比浮点慢但精确。另一个常见做法：金额存整数「分」（BIGINT），既精确又快。

VARCHAR 长度该设多少？

UTF-8 下 MySQL 的 VARCHAR(n) 中 n 是字符数不是字节数（utf8mb4 每字符最多 4 字节）。设太长的代价：① 排序/临时表按定义长度分配内存（VARCHAR(2000) 参与排序会很吃内存）；② 行长度超限会溢出。建议按实际最大长度的 1.5~2 倍设，不要一律 255 或一律 8000。
