GPU 集群与弹性扩缩容

几百上千张加速器摆在机房里，它们不是「一个大模型摊在全部卡上」，而是几十上百个独立副本。这一页讲：副本怎么组织、请求到达有多不均匀、为什么扩容明明点了却迟迟不生效、以及容量到底该怎么算。

01三种「并行」别混

「多卡」在训练和推理里指的不是一回事，混淆会导致完全错误的容量规划：

方式解决什么卡间通信推理里用不用
张量并行 TP一张卡装不下模型（权重/显存不够）极密集（每层都要 all-reduce），强烈依赖 NVLink用，但通常只跨 2/4/8 卡，超过单机收益骤降
流水并行 PP模型更深、跨机分层放较稀疏（只在层边界传激活）推理少用（会引入气泡与额外延迟）
数据并行 DP = 副本应对并发：同一份权重复制多份，各服务一批请求无（副本间不通信）主力：吞吐靠它，弹性也靠它
一句话：TP 让一个模型装得下，DP（副本）让很多人同时用得上。图里那个「1024 个加速器」属于后者——它不是把一个模型拆到 1024 张卡（那样通信会吃掉所有收益），而是有很多个副本，每个副本占 1~8 张卡。TP 的细节见 模型服务与部署 的多卡并行一节。

02集群长什么样

三个工程结论：

  • 扩容最小粒度是「副本」，所以一次至少加 1~8 张卡，成本是台阶式跳变的。
  • 不同池子必须物理隔离。把长上下文和短请求混在一个池，一条大请求就能把所有人的 TTFT 拖长。
  • 副本数上限受路由层约束。副本越多，前缀亲和的命中率越低（同一前缀被打散到更多副本）。这是一个真实的取舍：弹性和缓存命中率是一对矛盾。

03请求到达从来不是均匀的

看这串真实感的到达时间戳：

请求 #8,214   +0 ms      ← 同一瞬间
请求 #8,215   +12 ms
请求 #8,216   +31 ms
请求 #8,217   +47 ms
请求 #8,218   +63 ms
... 后面还有成千上万个

毫秒级连发说明两件事：① 流量是突发（burst）的，几十毫秒内涌入的请求可能超过后面十分钟的总和；② 请求之间没有排队间隔，它们会同时争抢同一批算力。

三种不均匀叠加在一起：

突发

热点事件、push 推送、整点定时任务、智能体批量启动。持续几十秒到几分钟，峰值可达均值 5~20 倍。

潮汐

白天高、深夜低。可预测但跨度大，需要「平时小、高峰大」的弹性。

长尾

少数超长请求拖住队列与显存。不是流量问题，是资源占用分布问题。

关键矛盾：把集群按峰值准备 → 大部分时间闲着，钱白花；按均值准备 → 高峰期排队甚至超时。这就是弹性存在的理由：用时间换成本。但弹性有下限——扩得快不快，取决于下面第 5 节的冷启动。

04队列与容量估算

先明确：队列不是坏事。批处理需要队列来攒批（见 模型服务与部署），没有队列就没有高利用率。队列太长才是坏事，因为等待时间直接进用户的 TTFT。

容量估算用 Little 定律，一个式子顶一堆经验：

并发请求数 L  =  到达速率 λ  ×  平均停留时间 W

反推：给定 SLO（平均延迟 W）和预期流量（λ），
需要的并发数 L = λ × W
需要的副本数   = L / 单副本可承载并发

例：
  λ = 20 请求/秒，要求 W ≤ 3 秒  →  L = 60 个并发
  单副本（8k 上下文、7B FP16、A100 80G）可挂 30 并发
  → 至少 2 个副本；再乘 1.5 的安全水位 → 3 个副本

注意 "单副本可承载并发" 不是常数：
  上下文越长、输出越长、模型越大，并发数越低（受 KV Cache 显存限制）。
更准的做法：用压测测出「并发 vs TTFT/吞吐」曲线，而不是套公式。同一硬件下，8k 上下文的承载并发可能是 128k 上下文的十几倍，公式里的那个除数必须按真实流量分布加权。指标定义与压测方法见 推理指标与成本，KV 显存怎么算见 KV Cache 与推理显存。

05扩容为什么慢：冷启动三件事

这是弹性方案失败最常见的原因。点一下「扩容」，到真正能扛流量，要经过：

环节典型耗时为什么慢怎么优化
调度与拉镜像10~60 s调度到有空卡的节点；镜像动辄几 GB预留节点池（预热节点）；镜像预拉取
加载权重1~10 min70B FP16 是 140GB，要从存储搬到显存；存储带宽是瓶颈本机 NVMe 缓存权重；用更大带宽存储；量化减小体积
编译与预热10 s~5 minCUDA graph 捕获、kernel 自动调优、JIT；首请求通常极慢预热请求（warmup）打满几批；编译产物持久化复用
注册与探活5~30 s要等 readiness 通过才摘进负载均衡探针区分 liveness/readiness；就绪即注册

合计 5~15 分钟是常态。而突发洪峰往往只持续 2 分钟——等你扩完，流量已经走了。

因此真正的解法不是「扩得更快」，而是「不靠扩容」

  • 预留水位（headroom）：常备 30~50% 余量，把扩容当兜底而不是主力。
  • 按预测预扩：潮汐流量是可预测的，按历史曲线提前 30 分钟扩，比响应式扩容有效得多。
  • 降级优先：洪峰来的时候先降级（缩短输出、走小模型、命中缓存直返），比硬扛便宜得多。
  • 离线任务可让路：把批处理任务挪走或抢占，等于瞬间腾出大量算力。

06扩容指标选什么

指标适用性说明
队列深度 / 等待请求数首选与用户体感（TTFT）最直接相关；到阈值就该扩
TTFT P95 / P99首选结果导向，能自动覆盖你没建模到的瓶颈
KV Cache 占用率首选接近 100% 就意味着「加不进去了」，扩副本能直接缓解
GPU 利用率辅助「高」可能是健康的（批满载），也可能是病态的（大量重算前缀）。单看它会误判
CPU / 内存不要用与 GPU 服务能力几乎无关，常见误配置
QPS辅助同样的 QPS，长请求和短请求的资源消耗差几十倍，不能作为唯一依据
推荐组合：主指标用 队列深度 + TTFT P95，硬闸门用 KV 占用率 > 85%；扩容要快（阈值低、步长大），缩容要慢（观察窗口长、步长小），这样能避免频繁抖动。
# 典型 HPA 风格配置（示意）
metrics:
  - queue_depth:      { target: 4,   scaleUp: 30s, scaleDown: 300s }
  - ttft_p95_ms:      { target: 800, scaleUp: 60s, scaleDown: 600s }
  - kv_cache_usage:   { target: 0.85 }
behavior:
  scaleUp:   { step: 2, stabilization: 0s }     # 快扩
  scaleDown: { step: 1, stabilization: 600s }   # 慢缩（避免抖动）
min_replicas: 2        # 至少留冗余，否则单副本故障即全站不可用
max_replicas: 40       # 受配额与成本上限约束

07缩容与优雅下线

缩容比扩容更容易出事，因为缩掉的副本上可能有正在生成的请求。

  1. 先从路由摘流（不再派新请求给它），但保留在服务列表里一小段时间，让路由缓存与连接复用自然过期。
  2. 等在飞请求跑完（drain）。给一个上限，比如 60~120 秒；流式生成的请求可能很长，要按 P99 输出时长设。
  3. 超时则取消并返回明确错误，让客户端重试到其他副本——而不是静默丢连接。
  4. 再停进程、释放显存。
两个常见事故：① 直接 kill 进程，用户看到「回答生成到一半突然断了」；② 缩容太快，导致前缀缓存反复被清空，命中率断崖下跌、成本反升。所以缩容要「慢 + 分批 + 看命中率」。

08成本：预留与按量的取舍

方式单价启动适合
包年包月 / 预留最低（常见为按量的 30~50%）随时可用基座流量、稳定负载
按量实例较高分钟级（含系统启动）潮汐峰值的增量部分
竞价 / 抢占式最低分钟级，可能随时被回收离线批处理、可重试任务

务实的组合通常是三层：预留覆盖基线（约 60% 负载）+ 按量应对日间峰值 + 竞价跑夜间离线任务。纯按量看起来很「弹性」，但在稳定负载下会明显更贵；纯预留则会在峰值时排队。

09算一算：要几张卡

# 目标：7B 模型、8k 上下文、支撑 20 QPS、TTFT 与 TPOT 均在 SLO 内

1) 单副本能装下吗？
   权重 FP16: 7B x 2B = 14 GB
   KV Cache : 0.5 MB/token x 8192 token x 并发数
   80GB 卡：14 + KV。若并发 30 → KV ≈ 120GB ✗ 装不下
   所以要么量化、要么降并发、要么多卡

   INT8 权重 7GB、KV 用 FP8 减半 → 并发 30 时 KV ≈ 60GB
   14 → 7 + 60 = 67GB，80GB 卡可以，留 13GB 给激活与框架

2) 单副本吞吐够吗？
   压测得到：该配置下单副本约 8 请求/秒（TTFT 300ms、TPOT 40ms）
   → 20 QPS 需要 20 / 8 = 2.5 → 3 个副本

3) 加上安全水位与故障冗余
   3 x 1.5 ≈ 4.5 → 5 个副本（也保证了任意 1 个副本故障不掉容量）

4) 再对上成本
   5 副本 x 1 卡 = 5 卡；峰值若能翻倍到 10 卡，多出的 5 卡用按量。

# 结论：容量规划不是"算力除以算力"，
# 而是 显存(能挂多少并发) 与 吞吐(每秒服务多少请求) 两个约束同时满足。
两个约束哪个先撞：长上下文场景通常先撞显存（并发上不去）；短请求高 QPS 场景通常先撞吞吐（GPU 算力饱和）。先判断是哪一个，才知道该加卡还是该优化单卡效率。

10排障清单

症状大概率原因处理
扩容触发了但流量没改善新副本还在加载权重/预热，没进负载均衡看 readiness 时间线；预热请求；持久化编译产物
高峰期永远差一口气依赖响应式扩容，赶不上 2 分钟的洪峰改按预测预扩；常备 headroom；先降级
副本数来回抖动（flapping）扩容快、缩容也快，指标在阈值附近震荡缩容加长观察窗口与稳定期；扩缩用不同阈值（滞回）
加了卡但并发没上去撞的是吞吐不是显存，或路由没把请求分过去先 profile 是 compute-bound 还是 memory-bound；检查路由均衡
扩容后缓存命中率暴跌同一前缀被分散到更多副本控制副本数上限；加强前缀亲和；必要时把小池子固定住

11速记卡

问题一句话答案
「1024 张卡」是什么结构？不是一个大模型摊在全部卡上，而是很多副本，每副本 1~8 卡
TP 和 DP 各解决什么？TP 让模型装得下；DP（副本）让很多人同时用得上
扩容最小粒度？副本（1~8 卡），成本台阶式跳变
扩容为什么慢？拉镜像 + 加载几十上百 GB 权重 + 编译预热 + 探活，合计 5~15 分钟
那怎么办？预留 headroom、按预测预扩、先降级、让离线任务让路——别指望实时扩容
扩容指标看什么？队列深度 + TTFT P95 + KV 占用率；不看 CPU
扩和缩的策略差异？快扩慢缩（缩容加稳定期，避免抖动）
弹性的隐藏代价？副本越多，前缀缓存命中率越低——弹性和命中率是一对矛盾
回到全景：集群提供了算力，但请求怎么被组织成批、怎么被高效消费，见 模型服务与部署；整条链路见 一次请求的完整旅程。
