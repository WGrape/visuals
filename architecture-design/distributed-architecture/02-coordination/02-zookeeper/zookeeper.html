ZooKeeper

ZooKeeper 不是数据库，也不是消息队列，它是一个分布式协调服务：用一棵小树（ZNode）帮集群解决"统一命名、配置、选主、分布式锁、状态感知"。Hadoop/HBase/Kafka/ Dubbo 都靠它。

❓它解决什么问题

分布式系统里，有一类"小但难"的需求反复出现：谁是 Master？配置变了怎么通知？谁拿到了锁？ZK 把这些"协调逻辑"统一封装好，让你专注业务。

ZK 提供的核心能力

① 统一命名 / 服务注册发现：节点把地址写进 ZNode，别人来读。

② 配置管理：配置放 ZNode，变更后自动推送。

③ 分布式锁 / 选主：用临时有序节点实现。

④ 集群状态感知：节点上下线通过会话/临时节点自动反映。

🧭
定位：ZK 存储的是"元数据（小数据）"，不是业务大块数据。单节点通常有配额限制（默认 1MB/节点），当作"分布式的小记事本"。

🌳数据模型：ZNode 树

ZK 的数据是一棵层级树，每个节点叫 ZNode，路径如 /service/order/node1。

节点类型：持久(Persistent) / 临时(Ephemeral，会话断开即删) / 顺序(Sequential，自动追加单调递增序号)。分布式锁、选主靠"临时+顺序"节点实现：谁序号最小谁是 Master。

🤝一致性：ZAB 协议

ZK 的一致性由 ZAB（ZooKeeper Atomic Broadcast）保证，本质是一种为 ZK 定制的原子广播/主备协议（和 Raft 同源思路）。

ZAB 的两个阶段

① 崩溃恢复（选主）：Leader 挂了，剩余 Follower 选出新 Leader，并同步已提交的事务（类似 Raft 选举 + 日志匹配）。

② 消息广播（原子广播）：正常时 Leader 把写请求按 ZXID 顺序发给所有 Follower，多数派 ACK 后提交。

✅
顺序一致（Sequential Consistency）：ZK 保证从同一客户端发出的写操作按序生效，且所有客户端看到的更新顺序一致。它不是线性一致（写有广播延迟），但足够支撑协调场景。

👀Watcher 监听机制

客户端可以对 ZNode 注册 Watcher，节点变化（创建/删除/数据变更）时 ZK 主动推送一次通知。

关键特性：Watcher 是一次性的——触发后即失效，需重新注册（所以客户端要"循环监听"）。这避免了 ZK 长期维护大量监听带来的压力。
⚠️
典型误用："为什么配置改了没收到？"——多半是 Watcher 触发后没重新注册，或者用了getData 而非 exists 导致节点不存在时无法监听创建事件。

🎯面试要点速记

定位：分布式协调服务，存元数据（小数据），不是 DB/MQ。
模型：ZNode 树，节点分持久/临时/顺序；临时节点随会话消失。
一致性：ZAB 协议（崩溃恢复 + 原子广播），顺序一致性。
Watcher：一次性监听，触发后需重注册；用于配置推送/状态感知。
选主/锁：临时顺序节点，序号最小者获锁/Master。
对比：与 etcd 同源思想，ZAB vs Raft，树形 vs KV。
🔥
必考题："如何用 ZK 实现分布式锁？"——在锁目录下建临时顺序节点，判断自己是否序号最小；是则获锁，否则 watch 前一个节点，前一个释放（删节点）时收到通知再重试。用临时节点防止"持有者宕机不释放"导致的死锁。

znode 四种类型与 Watch 的致命细节

类型是否持久是否有序典型用途
PERSISTENT是否配置、静态元数据
EPHEMERAL随会话消失否服务注册（宕机自动摘除）
PERSISTENT_SEQUENTIAL是是命名、ID 生成
EPHEMERAL_SEQUENTIAL随会话消失是分布式锁、选主

Watch 是一次性的（one-time trigger）：触发一次就自动注销，想持续监听必须在回调里重新注册。这是 ZK 最容易踩的坑——很多“监听失效”的 bug 都源于此。

Curator 生产用法

// Curator 正确用法：用它的高层 Recipe，它内部处理了重注册
CuratorFramework client = CuratorFrameworkFactory.builder()
    .connectString("zk1:2181,zk2:2181,zk3:2181")
    .sessionTimeoutMs(15000)      // 建议 2~3 倍 tickTime 以上，别用默认
    .connectionTimeoutMs(10000)
    .retryPolicy(new ExponentialBackoffRetry(1000, 3, 15000))  // base=1s, 最多3次, 最大间隔15s
    .build();
client.start();
client.blockUntilConnected(10, TimeUnit.SECONDS);   // 等连接建立

// ① 分布式锁（内部用 EPHEMERAL_SEQUENTIAL + 监听前序节点，避免羊群效应）
InterProcessMutex lock = new InterProcessMutex(client, "/locks/order");
if (lock.acquire(5, TimeUnit.SECONDS)) {            // 一定要带超时！
    try { /* 临界区 */ } finally { lock.release(); }
}

// ② 服务注册（EPHEMERAL，会话断开自动摘除）
client.create().withMode(CreateMode.EPHEMERAL)
      .forPath("/services/order/" + addr, payload);

// ③ 配置监听（用 NodeCache/TreeCache，自动重注册 Watch）
NodeCache cache = new NodeCache(client, "/config/order");
cache.getListenable().addListener(() -> reload(cache.getCurrentData().getData()));
cache.start();

会话超时设置：客户端设的 sessionTimeout 会被服务端夹到 [4 s, 40 s]。建议设 10 – 15 s：太短（4 s）会因 GC 停顿误判宕机导致频繁摘除；太长（40 s）故障发现太慢。

集群规模与部署要点

节点数Quorum容错场景
1—0仅本地开发
321最常用，成本最低
532要求更高可用 / 滚动升级
743很少用，写性能明显下降
  • 必须奇数台：4 台和 3 台一样只能容忍 1 台故障，多花钱没收益
  • 跨机房要“多数派机房”：3 机房各 1 台，任一机房挂掉剩 2 台仍构成 quorum（2/3）✓
  • 若 2 机房布 2+1：机房 A 挂掉后只剩 1 台，无法构成 quorum，整个集群不可用 ✗
  • ZK 不是存储系统：znode 上限 1 MB，只放元数据（地址、状态、配置），别放业务数据
  • 磁盘要单独 SSD：事务日志（WAL）是顺序写，与普通 IO 混用会拖慢选主
  • 3.5.0+ 支持动态重配置（reconfig），扩容不用全量重启

深入自检

ZooKeeper 的 Watch 为什么设计成一次性的？

这是刻意的取舍：ZK 走的是“通知 + 拉取”模型，只告诉客户端“变了”，不推送具体变化内容。若做成持续监听，服务端要为每个连接维护 watch 表状态，客户端重连时还要做状态对账，复杂度高得多。一次性 watch 让服务端无状态，重连时客户端重新拉全量即可。代价就是必须自己重注册——所以生产环境都用 Curator 的 Cache（它帮你处理了）。

为什么不能用 ZK 存业务数据？

三个硬约束：① 单 znode 1 MB 上限；② 全量数据常驻内存（每个节点都持有完整数据树），数据量上 G 就直接 OOM；③ 写操作要过 Zab 两阶段 + 落盘，吞吐只有每秒几千次写。所以 ZK 定位是协调（锁、选主、服务发现、配置通知），存储请用 DB 或 etcd。

Zab 和 Raft 有什么区别？

核心目标一致（顺序一致的日志广播 + 选主），细节不同：① Zab 用 epoch，Raft 用 term，概念等价；② 选主时的日志比较：Raft 比较 (lastTerm, lastIndex) 选“最新”的，Zab 倾向于选 zxid 最大的节点（类似）；③ Zab 有显式的 DISCOVERY / SYNCHRONIZATION / BROADCAST 三阶段，新 Leader 上台会先做一轮全量同步（SNAP/DIFF/TRUNC），Raft 则是靠 nextIndex 逐步回溯。工程效果上差别很小。

服务发现用 ZK 还是 etcd / Consul？

新项目优先 etcd 或 Consul：etcd 用 Raft + gRPC + 原生 watch 流式推送（watch 是持续的，不用重注册）、有 Kubernetes 生态背书；Consul 自带健康检查 + DNS 接口，运维更友好。ZK 的主要优势是成熟稳定、Java 生态（Curator Recipes）齐全，存量系统继续用没问题，新建系统不建议再从 ZK 起步。
