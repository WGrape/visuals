🐘 HDFS：为大数据而生的文件系统

把文件切成块分散存到多台机器，用多副本保证可靠性——Hadoop 生态的存储基石。

先建立直觉：把一本大书拆开分给多人保管

一本 1000 页的书，一个人保管风险高（他丢了书就没了），而且他一个人也搬不动。

HDFS 的做法：把书拆成若干册（block），每册复印 3 份，分给不同人保管。另外派一个管理员（NameNode）专门记录「哪一册在谁那里」。

  • 有人要读书 → 先问管理员要「目录」，然后直接去找各册的保管人；
  • 某个保管人不在 → 没关系，这册还有 2 份副本在别人那；
  • 管理员不在 → 整个图书馆瘫痪（这是 HDFS 的经典弱点）。

架构

关键设计

① 大块存储（默认 128MB）

普通文件系统块是 4KB，HDFS 是 128MB（可配 256MB/512MB）。原因：减少元数据量 + 减少寻址开销。1PB 数据若按 4KB 分块会有 2.5 亿个块，NameNode 内存根本放不下；按 128MB 只有 800 万个。

副作用：小文件问题。一个 1KB 的文件也会独占一个块的元数据（虽然实际只占 1KB 磁盘）。海量小文件会：① 耗尽 NameNode 内存；② 让计算任务产生海量 map（每个小文件一个）。解法：合并小文件、用 HAR 归档、或用 Iceberg/Hudi 这类表格式管理。

② 多副本与机架感知

默认 3 副本，放置策略通常是：本节点 1 份 + 同机架另节点 1 份 + 不同机架 1 份。既保证单机故障不丢，也保证整机柜故障不丢。

③ 一次写入、多次读取

HDFS 不支持随机写和文件修改（只能追加）。这是它最重要的限制：文件一旦写完就不可更改。这个设计换来了极高的一致性简单性和吞吐，但也意味着HDFS 不适合需要随机更新的场景（那是 HBase 的领域）。也正因如此，数据湖格式（Iceberg/Hudi）才需要用「重写文件 + 元数据切换」来实现 UPDATE。

容错与高可用

问题机制
DataNode 挂了NameNode 检测心跳超时 → 标记失效 → 自动把其上的块补足副本
数据块损坏块带校验和，读取时校验；发现损坏则从其他副本读取并修复
NameNode 挂了早期是单点故障；现代用 HA 方案（Active/Standby + JournalNode + ZKFC 自动切换）
SecondaryNameNode 不是热备份！这是最经典的误解。它只是定期合并 fsimage 和 editlog（防止编辑日志无限增大），不能接管服务。真正的高可用要用 NameNode HA（Standby NameNode + JournalNode 共享编辑日志）。

常用命令

hdfs dfs -ls /warehouse              # 列目录
hdfs dfs -put local.txt /warehouse/  # 上传
hdfs dfs -get /warehouse/f.txt ./    # 下载
hdfs dfs -cat /warehouse/f.txt       # 查看
hdfs dfs -du -h /warehouse           # 查看占用
hdfs fsck /warehouse -files -blocks  # 检查块健康与副本数
hdfs dfsadmin -report                # 集群容量报告

HDFS 适合什么

适合不适合
✅ 大文件（百 MB~GB 级）顺序读写❌ 海量小文件
✅ 一次写入、多次读取❌ 随机写、文件修改
✅ 高吞吐批处理❌ 低延迟访问（毫秒级）
✅ 廉价机器集群、容忍硬件故障❌ 需要 POSIX 语义的应用

🎯 面试问答

Q：为什么 HDFS 的块要设这么大（128MB）？
A：为了减少元数据量和寻址开销。NameNode 要把所有块的映射关系放在内存里，如果按普通文件系统的 4KB 分块，1PB 数据会产生约 2.5 亿个块，元数据根本放不下。按 128MB 分块只有约 800 万个，完全可控。同时大块意味着顺序读写占比更高，磁盘寻址时间被摊薄，吞吐更高。代价是小文件场景浪费严重——一个 1KB 的文件也占一块的元数据。

Q：SecondaryNameNode 是 NameNode 的备份吗？
A：不是，这是最经典的误解。SecondaryNameNode 的职责只是定期把 fsimage（元数据快照）和 editlog（操作日志）合并，防止 editlog 无限增大、NameNode 启动过慢。它不保存最新状态，也无法接管服务。真正的高可用要用 NameNode HA：配置 Active/Standby 两个 NameNode，通过 JournalNode 共享 editlog，由 ZKFC 监控并自动故障切换。

Q：小文件太多会有什么后果？
A：两个层面：① NameNode 内存压力——每个文件（无论多小）都要占约 150 字节元数据，千万级小文件会耗尽 NameNode 堆内存，甚至导致其无法启动；② 计算效率低下——MapReduce/Spark 默认一个块一个 map 任务，几万个几 KB 的小文件会产生几万个任务，任务启动开销远超实际计算时间。解法：写入侧做小文件合并、定期 compaction、用 HAR 归档，或改用 Iceberg/Hudi 这类自带文件管理的表格式。

Q：HDFS 上的文件能修改吗？
A：不能随机修改，只能追加（append）。HDFS 的设计是「一次写入、多次读取」：文件写完后就不可更改。这个限制换来了极高的一致性和吞吐（不需要复杂的锁和一致性协议）。如果需要随机更新怎么办？① 用 HBase（构建在 HDFS 之上，支持随机读写）；② 用 Iceberg/Hudi 这类数据湖表格式——它们通过「重写整个文件 + 原子切换元数据」来模拟 UPDATE，对用户呈现可更新的表。
