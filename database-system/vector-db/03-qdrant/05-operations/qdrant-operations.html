①监控指标与告警项

Qdrant 暴露 Prometheus 格式指标（/metrics），自带的仪表盘够看个大概，但生产告警一定要基于指标而不是眼睛。

指标（前缀 qdrant_）看什么告警建议
collections_total / collections_vector_total集合数与向量总数突增突降（误删/误建）
rest_responses_duration_seconds各接口耗时分布search p99 超过预算
app_info / cluster_enabled版本与集群状态重启、版本漂移
cluster_peers_total集群节点数少于预期（节点掉线）
进程 RSS / 容器内存实际内存占用最容易漏且最致命
很多 Qdrant 指标是按需采集的（需要开 service.enable_tls 之外的监控配置或用 /metrics 直接抓）。上线前先确认指标真的能抓到，别等出事才发现面板是空的。

②零停机重建：双写 + 别名原子切换

零停机重建（换索引参数、换量化方案、换 embedding 模型）的标准做法是双写 + 别名切换，而不是原地改。

# 1) 建新集合并灌数据（新参数/新模型）
PUT /collections/docs_v2 { ... }

# 2) 生产流量仍指向老集合，同时双写
#    业务层：upsert 到 docs 与 docs_v2

# 3) 用真实 query 对比两边结果，算 recall 差异
#    确认 docs_v2 达标后再切

# 4) 别名原子切换（应用只认别名，永不改代码）
POST /collections/aliases
{
  "actions": [
    { "delete_alias": { "alias_name": "docs" } },
    { "create_alias": { "collection_name": "docs_v2", "alias_name": "docs" } }
  ]
}
别名不只是方便，它是唯一能让切换动作原子的手段。应用直接写死 collection 名的项目，每次重建都要改配置重启，既慢又容易出错。

③七类高频故障对照表

按「现象 → 最可能原因 → 验证方法」组织，覆盖线上最高频的七类：

现象最可能原因怎么验证
导入后查询很慢（秒级）优化器还没建 HNSW，数据在未索引缓冲看 indexed_vectors_count 是否等于 points_count
内存持续上涨不回落vacuum 未触发；或 payload 进了内存调低 deleted_threshold；开 on_disk_payload
删除后仍能搜到标记删除 + vacuum 异步等待 vacuum，或显式触发优化
过滤查询极慢过滤字段没建 payload 索引看是否走了全段扫描；补建索引
召回明显低于预期量化未开 rescore / oversampling关量化对比；开 rescore: true
写入突然变慢段过多 + 合并抢占 IO；或索引构建占 CPU看段数；限 max_optimization_threads
数据丢失（重启后）存储卷没挂载到宿主机先查 volume 挂载，这是容器部署第一坑

④升级与迁移的三个前提

升级和迁移有两件事必须先确认，否则回退会很痛苦：

  • 存储格式兼容性：Qdrant 大版本升级可能涉及数据格式变更，必须先在快照副本上演练，不要直接升生产。
  • 快照是否可降级恢复：通常高版本快照无法被低版本读取，回退方案只能是「部署高版本再导出兼容格式」或「保留原数据卷」。
  • 容器镜像固定版本号：用 qdrant/qdrant:v1.x.y 而不是 latest，避免重建容器时被动升级。
容器化部署的两个致命细节：存储目录必须挂载到持久卷（否则容器一重启数据全没），快照必须外传（否则和容器一起丢）。这两条在演练里各翻车过一次，代价都是全量重建。

⑤上线自检清单

上线前把这份清单过一遍：

  • 存储目录挂载到持久卷，且写入了宿主机路径核对无误
  • 快照定时任务已配，且做过一次真实恢复演练
  • 要过滤的字段都建了 payload 索引，未过滤字段没有多余索引
  • 量化已开 rescore + oversampling，并用 ground truth 量过 recall
  • 压测在索引建完之后做，指标含 p99 而非均值
  • 应用通过别名访问集合，不写死 collection 名
  • 内存告警阈值按「向量本体 + 图 + payload」的真实估算设置，不是拍脑袋

第一层 · 概念与判定：向量库运维在管什么

Qdrant 是开源向量数据库，核心单元是 Collection（一张向量表），里面存 Point（向量 + 可选 payload 元数据）。检索默认用 HNSW 近似近邻（ANN），配合 payload 做带过滤的向量检索。

对象是什么运维关注
Collection向量表（固定维度/距离）维度、距离、分片数
Point一条向量 + payload写入/删除/更新
HNSW图索引内存、召回率
Snapshot集合快照备份/迁移

一句话判定：运维三大件 = 索引参数调召回、内存容量规划、payload 过滤正确性。

第二层 · 参数·命令·量化：HNSW 与部署

参数含义默认/建议调大的代价
vector_size向量维度模型决定内存线性增
distancecosine/dot/euclid按模型影响排序
m每层邻居数16内存↑、召回↑
ef_construct建索引时的候选100建索引变慢
ef查询时候选随 ef_construct查询变慢、更准
shard_number分片数= 节点数并行度

建集合、调 HNSW、过滤检索、快照

# 建集合并写入（Python client）
from qdrant_client import QdrantClient
c = QdrantClient("localhost", port=6333)

c.recreate_collection(collection_name="docs", vectors_config={
    "size": 768, "distance": "Cosine"  # size 必须和 embedding 模型一致
})

# HNSW 调优（提高召回的代价是内存）
c.update_collection(
    collection_name="docs",
    hnsw_config={"m": 32, "ef_construct": 200})

# 带 payload 过滤的检索：只在一部分里做 ANN
c.search("docs", query_vector=v,
         query_filter={"must":[{"key":"lang","match":{"value":"zh"}}]},
         limit=10, with_payload=True)

# 快照备份（运维必备）
c.create_snapshot(collection_name="docs")

数量级：每条 768 维 float32 向量约 3 KB（不含 payload），HNSW 图本身另占向量体积的 1~2 倍内存；100 万条 ≈ 3 GB+，必须按内存规划节点。

第三层 · 排障与边界：高频坑

上线后出问题的清单：

  • 维度不匹配：collection 设 768 却写入 1024 向量，直接报错，常见于换 embedding 模型后忘改
  • 召回率不够：m/ef 太小，ANN 漏掉近邻，结果「搜不到明明该有的」
  • 内存爆：全量驻留内存，数据量涨了没扩容，OOM 被杀死
  • payload 过滤误解：过滤是先滤后搜还是先搜后滤？Qdrant 是带约束的 ANN，过滤太严会导致候选不足、召回骤降
  • 批量写入太慢：逐条 upsert，应改成每批几百上千条
  • 忘记快照/备份：节点故障后只能重建索引

排查顺序：① 确认维度和距离配置；② 用 recall 测试集量化召回率；③ 监控节点内存与段数量；④ 压测批量写入吞吐。

第四层 · 原理与取舍

为什么 Qdrant 默认用 HNSW 而不是暴力检索？

向量检索是高维距离计算，暴力检索每查一次都要和全量点积，百万级数据一次查询就是百万次乘法，太慢。HNSW 用分层图把复杂度降到对数级，牺牲少量召回换几百倍加速，是向量库的事实标准。

召回率和内存怎么权衡？

m（邻居数）和 ef 越大，图越密、召回越高，但内存和查询耗时同步上升。生产上先用 recall 测试集定一个能接受的最低召回（如 0.95），再在这个约束下把参数往小调以省内存。量化（scalar/产品量化）可进一步压缩内存。

什么时候不该用向量库？

数据量小（几万条）或要求100% 精确召回时，直接用 NumPy/FAISS 暴力检索更简单更快；需要强事务、复杂联表、和关系型数据深度耦合时，向量库也不是合适的主存储。

Qdrant 的运维难点不在功能，而在优化器的异步性和容器化的持久化。前者让「刚导入就压测」变成假数据，后者让「重启」变成数据事故。
