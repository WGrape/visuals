一句话总结：OLAP 快，不只是因为列存和向量化，更因为查询被横向拆到几十上百个节点并行跑。单机的 IO/CPU/内存上限，用 scale-out 摊薄。

01为什么必须并行

分析查询常要扫几十亿行、做多表 JOIN 和聚合。单机有三道墙：磁盘/网络 IO 上限、单核 CPU 算力、内存放不下中间结果。MPP（Massively Parallel Processing）把数据按分片分布在多台机器，查询也拆成多个并行任务，各节点同时 scan + 计算，最后汇总。

🚀 横向扩展

节点越多，scan 和聚合的并行度越高；容量和算力近似线性增长。

🧩 数据本地性

计算尽量下推到数据所在节点，减少跨网络搬数据。

⚖️ 负载均衡

按分片均匀分配任务；长尾慢节点是主要风险点。

02查询怎么拆成 Stage

SQL 经过 Parser、Analyzer 生成逻辑计划，优化器再生成物理计划。物理计划按数据重分布（Exchange）边界切成多个 Stage：每个 Stage 内部可以流水线并行，Stage 之间需要把数据按 key 重新分发。常见的 Exchange 类型：Shuffle（按 hash 重分布）、Broadcast（小表广播到所有节点）、Gather（各节点结果汇聚到协调节点）。

Stage 边界 = 数据需跨节点重分布的地方

03Pipeline 执行模型

单个 Stage 内部用 Pipeline（向量化/火山模型的改进）：一组算子串联成流水线，数据以 Batch（如 8192 行）为单位流式穿过算子，不在算子间落盘。这避免了"先算完 scan 再算 filter 再算 agg"的多趟物化开销，cache 友好、延迟低。

对比：Stage 之间因为要 Shuffle，往往需要落盘或网络传输（物化中间结果）；而 Pipeline 内的流式处理是本地的、不落盘的。

04数据重分布（Shuffle）

什么时候必须 Shuffle，什么时候可以 Broadcast？

场景重分布方式理由
两表按 join key 都不小Shuffle（双表都按 key hash 分发）让相同 key 落到同一节点再本地 join
一表很小（维度表）Broadcast（小表发到所有节点）避免大表移动，网络量 = 小表大小 × 节点数
GROUP BY 聚合Shuffle by group key相同分组必须汇到同一节点才能合并
最终结果返回Gather各分片结果汇聚到协调节点排序/截断

05分布式聚合的两阶段

聚合几乎是 OLAP 最高频的操作，MPP 用两阶段聚合避免把所有明细都搬到一处：

  • 本地预聚合（Partial / Local Agg）：每个节点先对自己分片的数据按 group key 做一遍聚合，数据量急剧缩小。
  • 全局聚合（Final / Merge Agg）：再按 group key Shuffle 到汇总节点，把各个节点的部分结果合并成最终结果。

例如 SUM(amount) 可逐节点先 SUM 再 SUM；COUNT(DISTINCT user) 则需要 bitmap/HyperLogLog 这类可合并结构，否则只能把去重后的明细搬到一处。

06常见瓶颈

🔥 数据倾斜

某个 key 的数据量是其他的百倍（热点用户/空值），该分片成为长尾，整体被它拖住。

🌊 Shuffle 网络

Stage 间的数据重分布是网络带宽与延迟的主要消耗点。

🐌 单 Stage 长尾

一个慢节点（GC/磁盘/网络抖）拖慢整个查询；需要副本重试或隔离。

07常见疑问

MPP 和单机多线程有什么区别？
单机多线程仍受限于一台机器的 IO/CPU/内存；MPP 把数据和计算分布到多台机器，突破单机上限，代价是网络 Shuffle 和协调机制。
什么时候用 Broadcast 而不是 Shuffle？
当一侧表足够小（通常几十 MB 以内），广播到所有节点的网络成本远低于移动大表。优化器会根据统计信息自动选，也可手动 hint。
数据倾斜怎么救？
热点 key 单独处理（如盐值打散再合并）、把倾斜 key 走广播、或配置倾斜 join 的运行时优化（如运行时识别热 key 换策略）。

排查口诀：先看 EXPLAIN 计划的 Stage 数和数据量估算，再找"哪个 Stage 最慢/哪个算子输出行数远超预期"，往往是倾斜或统计信息过期。

统计信息为什么影响并行计划质量？

优化器靠行数、NDV（不同值数）、直方图、列平均长度来估算每个算子的输出行数和代价，从而决定 Shuffle 还是 Broadcast、JOIN 顺序。统计信息过期或不准，计划可能选错，导致大表被广播或错误的 join 顺序——所以定期 ANALYZE 是 OLAP 性能基线的一部分。

深度补充：MPP 并行查询执行

第一层 · 概念与判定 MPP（大规模并行处理）把查询拆成在多节点同时执行的算子流水线，靠数据重分布（shuffle）完成 Join/聚合。判定：看执行计划是否出现 Exchange/广播算子与并行度。

阶段动作瓶颈
扫描并行各节点读本地分片本地 IO
数据重分布按 Join/聚合键 shuffle网络
本地计算每节点算部分结果CPU
汇总单/多节点聚合汇总节点

第三层 · 排障与边界

  • 数据倾斜：某 key 集中在单节点，其他空闲它最慢。
  • shuffle 数据量大，网络成为瓶颈，需调并行度与压缩。
  • 汇总节点单点，大结果聚合串行化。
  • 并行度过高超过核数，上下文切换反噬。
第四层 · 原理与取舍

MPP 用“把数据分桶并在多节点流水线执行”换近线性的扩展能力，代价是节点间 shuffle 的网络开销与协调成本。它和“单机多线程”的区别是扩展到整个集群，但也引入数据倾斜与网络瓶颈。权衡是“并行度 vs 协调与网络开销”：理想情况是数据本地化高、key 均匀，让每个节点负载均衡；倾斜时用加盐/两阶段聚合兜底。

实例与速查：MPP 倾斜处理

-- 数据倾斜典型现象：某 key 集中，单节点最慢、其他空闲
-- 处理手段（以常见 MPP 为例）：
--   1) 加盐：对热点 key 加随机前缀打散，两阶段聚合
--   2) 隔离热点：单独处理超大 key，其余正常聚合
--   3) 调并行度：让每个节点负载均衡，避免超核数

-- 观察各节点执行时间是否均衡（看执行计划的各分片耗时）
  • 数据倾斜：某 key 集中单节点，它是整体最慢的一环。
  • shuffle 数据量大，网络成瓶颈，调并行度与压缩。
  • 汇总节点单点，大结果聚合串行化，需两阶段聚合。
FAQ：并行度是不是越高越好？

不是。并行度超过物理核数后，线程/协程上下文切换与调度开销反噬，边际收益递减甚至变慢；同时更高的并行度意味着更细的 shuffle 分片，元数据与协调成本上升。经验值是“略低于或等于核数”，倾斜场景优先用加盐/两阶段聚合解决，而不是单纯加并行度。

常见误区与延伸

  • 误区一：并行度越高越快。超核数后上下文切换与协调开销反噬，通常略低于或等于核数。
  • 误区二：倾斜靠加机器解决。倾斜是数据分布问题，加机器只是复制瓶颈，需加盐/两阶段。
  • 延伸：Exchange（shuffle）是 MPP 主要网络瓶颈来源，colocate Join 可消除跨片 shuffle。
  • 延伸：汇总节点单点是大结果聚合的串行点，两阶段聚合把它从全局降到本地再汇总。

一句话总结：MPP 用分桶并行换近线性扩展，代价是 shuffle 网络与协调；理想是数据本地化高、key 均匀，倾斜用加盐兜底。

决策速记

  • 并行度：略低于或等于核数，过大反噬切换开销。
  • 治倾斜：加盐或两阶段聚合，而非加机器。
  • 减 shuffle：colocate Join 消除跨片，降网络。
  • 防单点：汇总节点两阶段，化全局为本地再汇。

一句话：MPP 用分桶并行换扩展，代价是 shuffle 与协调，倾斜用加盐兜底。

横向对比与追问

  • 与 SMP 比：SMP 共享内存多核，MPP 是独立节点的无共享集群，扩展性与故障隔离更好。
  • 与单机多线程比：MPP 扩展到整个集群，代价是网络 shuffle 与节点协调。
  • 追问：为什么数据本地化重要？减少 shuffle 就减少网络瓶颈，是 MPP 调优核心。
  • 追问：两阶段聚合为什么能减负？把全局聚合拆成本地预聚加小幅汇总，降网络量。

小结：MPP 用分桶并行换近线性扩展，调优围绕“倾斜、shuffle、并行度”三件事。
