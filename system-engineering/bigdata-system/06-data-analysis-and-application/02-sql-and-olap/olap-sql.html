先建立直觉：收银台 vs 财务报表

OLTP（联机事务处理）像收银台：一次操作一两行，要求快、准、可回滚——「扣掉这件商品的库存」。

OLAP（联机分析处理）像财务报表：一次扫描几百万行做汇总，要求能多角度切片——「今年各地区各品类的销售额同比」。

数据量当前数据（GB 级）历史数据（TB~PB 级）

多维聚合：一次算出所有层级

普通 GROUP BY 只能给你一个粒度的结果。而分析常常需要多个粒度的小计与合计——这就是 ROLLUP / CUBE / GROUPING SETS。

-- 想同时看：(地区,品类)、(地区)、(总计) 三个粒度
-- 笨办法：写三条 SQL 再 UNION

-- ROLLUP：按层级逐级上卷（有层次关系时用）
SELECT region, category, SUM(amount)
FROM sales
GROUP BY ROLLUP(region, category);
-- 产出：(北京,手机) (北京,电脑) (北京,NULL小计) (上海,...) (NULL,NULL总计)

-- CUBE：所有维度组合（无层次关系时用）
GROUP BY CUBE(region, category);
-- 产出：(地区,品类) (地区,NULL) (NULL,品类) (NULL,NULL) —— 全部组合

-- GROUPING SETS：精确指定要哪些组合（最灵活）
GROUP BY GROUPING SETS ((region, category), (category), ());
-- 只产出：(地区,品类) (品类小计) (总计)
怎么区分「小计行的 NULL」和「真实的 NULL」？用 GROUPING(col) 函数：返回 1 表示该列是聚合产生的 NULL（小计行），0 表示真实数据。配合它就能给小计行打上「合计」标签。

窗口函数：不折叠行的聚合

普通 GROUP BY 会把多行合并成一行；窗口函数则保留每一行，同时为它计算一个基于「窗口」（一组相关行）的值。

三类常用窗口函数

类型函数用途
排名ROW_NUMBER / RANK / DENSE_RANKTop N、去重取最新、分组排名
聚合SUM/AVG/COUNT OVER(...)累计求和、移动平均、占比
偏移LAG / LEAD环比、同比、相邻行对比
-- ① 每个品类内按销售额排名，取前 3
SELECT * FROM (
  SELECT category, product, amount,
         ROW_NUMBER() OVER (PARTITION BY category ORDER BY amount DESC) AS rn
  FROM sales
) t WHERE rn <= 3;

-- ② 累计求和（按日期累加）
SELECT dt, amount,
       SUM(amount) OVER (ORDER BY dt ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total
FROM daily_sales;

-- ③ 7 日移动平均
SELECT dt, amount,
       AVG(amount) OVER (ORDER BY dt ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS ma7
FROM daily_sales;

-- ④ 环比：取前一天的值
SELECT dt, amount,
       LAG(amount, 1) OVER (ORDER BY dt) AS prev_day,
       amount - LAG(amount, 1) OVER (ORDER BY dt) AS diff
FROM daily_sales;
窗口函数 vs GROUP BY 的核心区别：GROUP BY 会减少行数（多行聚合成一行），窗口函数保持行数不变（每行额外多一列聚合值）。要做「既看到明细、又看到汇总/排名」的分析，必须用窗口函数。

性能：为什么 OLAP 引擎快

技术原理效果
列式存储按列而非按行存储聚合查询只需读用到的列，IO 大幅减少
向量化执行批量处理数据（SIMD）CPU 利用率提升数倍
预聚合提前算好常用汇总查询直接读结果，秒级返回
物化视图把查询结果持久化重复查询直接命中
分区与索引跳过无关数据减少扫描量
列存的代价：单行读写变慢（要访问多个列文件）。所以列存适合分析（读多列少行），行存适合事务（读写整行）——这就是 OLAP 和 OLTP 存储引擎分道扬镳的根本原因。

写分析 SQL 的建议

  • 先想清楚粒度：结果集的一行代表什么（一个用户？一天？一个地区？）——这是最容易出错的地方；
  • 分区字段一定要带过滤：避免全表扫描；
  • 大表 JOIN 前先聚合：先各自聚合再 JOIN，数据量会小很多；
  • 用 CTE（WITH）拆解：把复杂查询拆成几步，可读性和可调试性都更好。

🎯 面试问答

Q：窗口函数和 GROUP BY 到底什么时候用哪个？
A：看你要不要保留明细行。GROUP BY 把多行压缩成一行（只要汇总结果时用）；窗口函数保留每一行，额外附加一个基于窗口的计算值（既要看明细又要看排名/累计/占比时用）。典型场景：算「每个用户占其所在地区销售额的比例」——明细要保留，必须用窗口函数。

Q：ROLLUP 和 CUBE 有什么区别？
A：ROLLUP 按层级逐级上卷，适合维度间有层次关系的场景（如 年→季→月，国家→省→市）：ROLLUP(region, category) 产出 (region,category)、(region)、(总计) 三级。CUBE 产出所有维度组合，适合维度间无层次的场景：会额外产出 (category) 这一级。如果维度有明确层次用 ROLLUP，需要任意组合用 CUBE，只需特定几种组合用 GROUPING SETS。

Q：为什么同样的 SQL 在 OLAP 引擎上快几十倍？
A：主要是列式存储 + 向量化执行。聚合查询通常只用到少数几列（如只看 amount 和 region），列存让引擎只读取这两列的数据，跳过其他几十列，IO 量可能减少 90% 以上。再加上向量化执行（批量处理而非逐行处理）、压缩编码、预聚合等技术，综合起来就是几十倍的差距。代价是单行读写变慢——所以 OLAP 引擎不适合做事务处理。

Q：分析查询跑得慢，一般怎么优化？
A：排查顺序：① 有没有加分区过滤——全表扫描是最常见的性能杀手；② 扫描了多少数据量——看执行计划的 scan 行数，能先过滤就先过滤；③ JOIN 顺序与数据量——先把各表聚合到最小再 JOIN，小表放右边（广播）；④ 是否重复计算——用 CTE 复用中间结果，或建物化视图；⑤ 数据倾斜——某个 key 特别大导致单任务极慢，需要加盐或单独处理。
