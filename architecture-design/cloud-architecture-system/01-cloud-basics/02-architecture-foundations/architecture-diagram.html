📋 请求链路说明

① 客户端发起 HTTPS 请求到 api.test-example.com
② DNS 解析 CNAME 到云厂商 ELB 地址
③ SLB 负载均衡器接收请求，进行四层/七层转发

一张典型的云上 Web 架构分层图

从用户发起请求到数据落库，请求会经过若干层。理解每一层解决什么问题、缺少它会怎样，比记住产品名字重要得多。

云上 Web 架构七层：DNS → CDN → WAF → SLB → 应用 → 中间件 → 数据

逐层解释：每层解决什么问题

层解决什么没有它会怎样关键配置
① DNS把域名解析成 IP；可做智能解析与故障切换用户无法访问TTL 不宜过长（否则切换慢）、多线路解析
② CDN把静态资源缓存到离用户最近的边缘节点所有请求回源，延迟高、源站压力大、带宽贵缓存策略、回源配置、刷新机制
③ WAF/高防拦截 SQL 注入、XSS、CC 攻击；清洗 DDoS 流量应用直接暴露在攻击下，被打穿即全站不可用规则集、CC 防护阈值、误拦排查
④ 负载均衡把流量分发到多台后端，做健康检查与故障摘除无分发无高可用，单台打挂就全站挂健康检查、会话保持、算法选择
⑤ 应用服务业务逻辑；无状态部署多实例（核心）优雅启停、探针、资源限制、水平伸缩
⑥ 中间件缓存抗读、MQ 解耦削峰、对象存储放文件、ES 做检索数据库直接承压，文件占满磁盘，搜索慢缓存一致性、消息幂等、索引设计
⑦ 数据层持久化与强一致（核心）主从复制、备份策略、容量监控、慢查询治理

架构演进：从简单到复杂

阶段一：单机（起步）

一台云主机跑应用 + 数据库 + 静态文件。

  • 优点：简单、便宜、部署快
  • 问题：无高可用，挂了全没；数据有丢失风险
  • 适用：原型、内部系统、流量极小

阶段二：分离（最常见）

应用与数据库分开部署；静态文件上对象存储 + CDN；数据库主从 + 自动备份。

  • 解决了数据安全与大部分性能问题
  • 成本增加不多，是性价比最高的一步
  • 适用：绝大多数中小业务

阶段三：横向扩展

应用多实例 + 负载均衡；加 Redis 缓存；数据库读写分离。

  • 应用无状态化是前提
  • 解决并发与读压力
  • 适用：有一定流量与可用性要求

阶段四：分布式与微服务

按业务拆分服务；引入消息队列异步化；数据库分库分表；多可用区部署。

  • 解决复杂性与规模问题
  • 代价：运维复杂度陡增
  • 适用：大流量、多团队、复杂业务

重要原则：按阶段演进，不要跳步。很多团队的失败在于「业务量还很小就上了微服务 + 分库分表」，结果复杂度和人力成本吃掉了全部收益。

设计一套架构要回答的六个问题

  • 流量多大？QPS 峰值、日活、带宽——决定要不要 CDN、要不要缓存、要几台机器。
  • 数据多大？总数据量与增长率——决定要不要分库分表、选什么存储。
  • 读写比例？读多写少还是相反——决定缓存策略与读写分离的价值。
  • 一致性要求？能否容忍短暂不一致——决定是否可以用最终一致方案换取性能。
  • 可用性要求？几个 9——决定冗余程度与容灾方案，也直接决定成本。
  • 团队能力？有多少人、会不会运维这套东西——这是最容易被忽略却最决定成败的一条。架构要能被团队真正维护住。

深入自检

为什么强调「应用无状态」？

因为它是横向扩展与高可用的前提。有状态意味着新实例缺少状态数据：会话在内存里 → 扩容后用户被随机分配到没有其会话的实例 → 反复掉登录；文件在本地磁盘 → 请求打到另一台机器就找不到文件；定时任务在实例内 → 多实例会重复执行。无状态化后，任意实例都能处理任意请求，于是可以：任意扩缩容、任意实例被替换（自愈与滚动发布）、流量任意调度（灰度与多活）。具体做法：会话放 Redis、文件放对象存储、定时任务加分布式锁或独立部署、业务状态放数据库。检验标准：随机杀掉一半实例，用户是否完全无感。

什么时候才需要引入消息队列？

三个明确场景：① 异步解耦——主流程不需要等待的动作（发通知、加积分、写日志、同步数仓），避免它们拖慢主流程或失败影响主流程；② 削峰填谷——流量突发（秒杀、大促、批量导入）时先入队，消费者按自身能力匀速处理，保护下游；③ 广播通知——一个事件多个订阅方各自处理（对应事件驱动架构）。不该引入的情况：需要同步返回结果的调用（登录校验、库存查询）、简单的两步调用（直接 RPC 更简单）。引入的代价是：最终一致、需要幂等、需要监控积压、多一个组件要运维。判断标准：这个动作「失败了可以稍后重试且不影响用户当前操作」吗？是，就可以异步化。

数据库什么时候要分库分表？

先看信号而不是拍脑袋：① 单表数据量达到千万~亿级，索引无法全部进内存，磁盘随机 IO 明显上升；② 慢查询增多，优化索引与 SQL 后仍然慢；③ 写入 QPS 接近单机上限，主从延迟持续增大；④ 单机连接数经常打满；⑤ DDL 与备份耗时不可接受。在动手之前必须按顺序尝试：优化索引与 SQL → 加缓存挡读 → 读写分离扩展读 → 归档历史数据 → 垂直拆分（按业务分库）→ 最后才水平分库分表。因为分片会带来分布式事务、跨片查询、扩容迁移三座大山，能不做就不做。另外注意：很多「数据量太大」其实是没有做历史数据归档造成的。

如何评估架构是否合理？

用几个可检验的标准：① 能否水平扩展——流量翻倍时，加机器能否线性提升容量？如果不能，瓶颈在哪一层？② 故障影响面——任意单个组件挂掉，影响多少功能？是否有单点？③ 发布是否无损——发布期间错误率是否上升？能否秒级回滚？④ 排障速度——线上出问题，多久能定位到具体服务与原因？有链路追踪吗？⑤ 成本与复杂度是否匹配业务规模——用微服务解决一个日活一千的系统，就是过度设计；⑥ 团队能否维护——文档、监控、值班是否健全。好的架构不是「用了多少先进组件」，而是「在当前的约束下做出了恰当的取舍」。
