字节序与内存对齐：那些「本地跑得好、上线就崩」的原因

字节序决定一个多字节整数在内存里怎么排；对齐决定结构体为什么「看起来多了几个字节」。这两件事在单机上几乎不可见，一旦涉及网络、文件格式、跨语言调用或 SIMD，就会集中爆发。

一句话定位：字节序是「约定」，对齐是「代价」

字节序没有对错，只有约定是否一致；对齐不是编译器抽风，而是硬件对「一次访问」的物理要求。前者靠协议固定，后者靠排版优化。

小端低字节在低地址（x86、ARM 默认、RISC-V）
大端高字节在低地址（网络序、部分嵌入式、Java 序列化）
对齐int 通常要求地址是 4 的倍数，double 是 8
缓存行64 字节；跨行访问要两次读取
同一个值，两种字节序的存储顺序完全相反

结构体为什么变大：padding 算一遍

struct A {          // 假设 char 1 字节、int 4 字节、8 字节对齐平台
  char  a;          // offset 0
  // 3 字节 padding
  int   b;          // offset 4
  char  c;          // offset 8
  // 3 字节 padding（结构体整体按最大成员对齐）
};                  // sizeof = 12，不是 6

struct B {
  int   b;          // 0
  char  a;          // 4
  char  c;          // 5
  // 2 字节 padding
};                  // sizeof = 8   ← 调整顺序省 4 字节

#pragma pack(1)     // 取消填充：sizeof=6，但成员可能未对齐
类型大小对齐要求未对齐访问的后果
char11无
int3244x86 慢；ARM 部分型号异常或陷入
int64 / double88同上，跨界更明显
SIMD（16/32B）16/3216/32必须对齐，否则 #GP
结构体按最大成员同上数组元素间距被 padding 撑大
省内存的排版口诀

按「大到小」排列成员，通常能把 padding 压到最少。百万级数组的元素结构体，每省 4 字节就是 4MB。

伪共享：对齐问题的另一个面孔

两个线程分别修改同一缓存行里的不同变量，看似无关，实际会因为这行缓存反复在核间失效而性能暴跌（可达 5~10 倍）。这就是伪共享，本质是「缓存行 64 字节」这个硬件事实泄漏到了软件层。

语言/库解决手段代价
C/C++alignas(64) + padding 占满一行每变量浪费 64B
Java@Contended（需开开关）同上
Go在结构体里加 [56]byte 填充同上
通用线程本地累加，最后合并多一次合并开销

原理与取舍：为什么要对齐

内存按「字」组织，一次访问只能取出对齐的字；未对齐访问需要两次读取 + 拼接，甚至在部分架构上直接触发异常。编译器插入 padding 是为了让每个成员都能被一次访问取出——它不是在浪费空间，而是在用空间买「单周期访问」。

为什么网络序选大端？

历史原因（早期网络设备用大端），加上大端在人工阅读 hexdump 时更符合书写顺序。今天它只是一个必须遵守的约定。

packed 结构体不是更省内存吗？

省内存但换来未对齐访问：在 x86 上慢，在 ARM 上可能异常，编译器也无法做向量化。除非在解析外部二进制格式，否则不要用 packed。

ARM 不是支持非对齐访问吗？

现代 ARMv7+ 支持普通 load/store 的非对齐访问，但原子操作、SIMD、独占访问仍要求对齐，而且跨页的未对齐访问会显著变慢。
