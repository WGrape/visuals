① ROWID 与主键索引

SQLite 的表本身就是一棵按 ROWID 组织的 B-tree。因此：

INTEGER PRIMARY KEY

直接成为 ROWID 的别名，无需额外索引，定位最快

其它类型主键

会额外创建唯一索引来维护主键约束

WITHOUT ROWID

表按主键组织，省一层间接查找；适合纯键值表与多列主键

隐式 ROWID

没声明主键的表也有 64 位 ROWID，可用 rowid 直接访问

-- 最快的主键形式
CREATE TABLE t1(id INTEGER PRIMARY KEY, name TEXT);

-- 会额外建索引（慢一些、占空间）
CREATE TABLE t2(id TEXT PRIMARY KEY, name TEXT);

-- 无 ROWID 表：按主键聚簇，适合键值表
CREATE TABLE kv(k TEXT PRIMARY KEY, v BLOB) WITHOUT ROWID;

-- 直接用 rowid 访问
SELECT rowid, * FROM t1 WHERE rowid = 5;
这就是为什么「SQLite 里整数主键最快」——它省掉了一次索引查找 + 回表。

② 创建索引与复合索引

CREATE INDEX idx_orders_user ON orders(user_id);
CREATE UNIQUE INDEX idx_users_email ON users(email);

-- 复合索引：顺序很关键（最左前缀原则）
CREATE INDEX idx_orders_user_time ON orders(user_id, created_at);
-- 能加速：WHERE user_id=?            ✅
--         WHERE user_id=? AND created_at>?  ✅
-- 不能加速：WHERE created_at>?        ❌（跳过了最左列）

③ 覆盖索引、部分索引与表达式索引

覆盖索引

把查询需要的列都放进索引，避免回表：CREATE INDEX i ON t(a, b, c) 让 SELECT c FROM t WHERE a=? AND b=? 只走索引

部分索引

只索引部分行：CREATE INDEX i ON t(created) WHERE status='pending'——索引更小、维护更快

表达式索引

CREATE INDEX i ON t(lower(email)) 让 WHERE lower(email)=? 走索引

排序方向

ORDER BY a DESC, b ASC 需要索引 (a DESC, b ASC) 才能避免排序

CREATE INDEX idx_cover ON orders(user_id, created_at, status);
-- SELECT status FROM orders WHERE user_id=? ORDER BY created_at  → 完全走索引

CREATE INDEX idx_pending ON orders(created_at) WHERE status = 'pending';
-- 只索引待处理订单，索引小很多

CREATE INDEX idx_email ON users(lower(email));
-- WHERE lower(email) = 'a@b.com' 可用索引

-- 验证是否用到索引
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE user_id = 1;
-- 输出含 "USING INDEX idx_..." 表示命中

④ ANALYZE 与统计信息

SQLite 的优化器依赖 sqlite_stat1 表中的统计信息来决定索引使用。没有统计信息时它靠猜测，大表上很容易选错。

-- 生成/更新统计信息（数据分布变化后要重跑）
ANALYZE;
ANALYZE orders;            -- 只分析某表

-- 查看统计
SELECT * FROM sqlite_stat1;

-- 关闭统计（调试用）
PRAGMA optimize;           -- 3.18+：按需自动 ANALYZE 需要更新的表
索引建了却不用的常见原因：① 没跑 ANALYZE——优化器不知道选择性；② 查询条件对列用了函数（应建表达式索引）；③ 类型不匹配（见数据类型页：'123' 不等于 123）；④ 使用了 OR 且各分支列不同；⑤ 优化器判断全表扫描更快（返回比例大或小表）。排查：用 EXPLAIN QUERY PLAN 确认，再针对性处理。

⑤ 维护与常见问法

-- 索引维护
REINDEX;                    -- 重建所有索引
REINDEX idx_name;           -- 重建指定索引
PRAGMA integrity_check;     -- 完整性检查
PRAGMA index_list(orders);  -- 查看表的索引
PRAGMA index_info(idx_name);-- 查看索引列

-- 删除无用索引
DROP INDEX idx_name;

⑥ 常见问法

Q：为什么 SQLite 里 INTEGER PRIMARY KEY 特别快？

A：因为它是 ROWID 的别名——SQLite 的表本身就是一棵按 ROWID 组织的 B-tree，所以按它查找直接就是树上的一次查找，不需要额外索引，也不需要回表。对比：若主键声明成 TEXT 或 INT PRIMARY KEY DESC，就不是 ROWID 别名，SQLite 会再建一个唯一索引，查找时先查索引拿到 ROWID 再回表，多一层间接、多占空间。此外：即使没声明主键，表也有隐式 ROWID，可用 rowid 访问。

Q：复合索引的列顺序怎么定？

A：遵循三条：① 最左前缀原则——只有从最左列开始连续使用才能命中（(a,b) 能优化 WHERE a=? 与 WHERE a=? AND b=?，但优化不了 WHERE b=?）；② 等值列在前、范围列在后——范围列之后的列无法再用于索引定位；③ 兼顾排序与覆盖——若查询有 ORDER BY，让索引顺序与之匹配可避免排序；若想避免回表，把需要的列也纳入索引。实践：先按查询条件排，再看能否顺带解决 ORDER BY 与覆盖。

Q：部分索引（Partial Index）有什么用？

A：它只为满足 WHERE 条件的行建立索引（CREATE INDEX i ON t(created) WHERE status='pending'）。好处：① 索引体积大幅缩小（只含热点子集）；② 写入维护成本更低（不满足条件的行插入时不更新索引）；③ 查询条件与索引的 WHERE 子句一致时可直接命中。典型场景：任务队列（只查 pending）、软删除（只索引 deleted_at IS NULL 的行）、状态机（只查未完成的订单）。注意：只有当查询的 WHERE 与索引的 WHERE 语义一致时，优化器才会使用它。

Q：建了索引却没生效，怎么排查？

A：五步：① EXPLAIN QUERY PLAN 确认是否出现 USING INDEX——没有则确实未命中；② 跑 ANALYZE（最常见原因：统计信息缺失导致优化器误判）；③ 检查是否对列用了函数（改成表达式索引或改写条件）；④ 检查参数类型是否匹配（SQLite 不做隐式转换，'123' 与 123 不等）；⑤ 检查是否返回比例过大或小表，此时全表扫描确实更快。另外：OR 连接不同列、LIKE '%x%' 也无法用普通 B-tree 索引。

Q：ANALYZE 是干什么的？什么时候跑？

A：ANALYZE 收集表与索引的统计信息（行数、各列的平均选择性等），写入 sqlite_stat1 表，供优化器估算各索引的代价。没有它，优化器只能靠启发式猜测，在大表或数据倾斜时极易选错索引。什么时候跑：① 初次导入大量数据后；② 数据分布发生显著变化后（如某状态占比突变）；③ 定期维护（可用 PRAGMA optimize 让它自动判断哪些表需要重新分析）。代价：ANALYZE 会扫描表，大库可能需要一段时间，建议在低峰执行。

Q：WITHOUT ROWID 表适合什么场景？

A：WITHOUT ROWID 让表直接按主键组织（主键就是聚簇索引），省掉「二级索引 → ROWID → 回表」这一层间接，按主键查找更快、更省空间。适合：① 纯键值表（k TEXT PRIMARY KEY, v BLOB）；② 多列复合主键的关联表；③ 主键是 TEXT/UUID 且主要按主键访问的表。不适合：① 表很大且有很多二级索引（二级索引要存完整主键，会膨胀）；② 行很大（会导致二级索引膨胀）；③ 频繁按非主键列扫描。建议：先按普通表建，确认为主键访问瓶颈后再改造，并用真实数据量测试。

SQLite 索引命令

-- 查看是否走了索引（最重要的排查手段）
EXPLAIN QUERY PLAN SELECT * FROM users WHERE email = 'a@b.com';
-- 输出示例：
--   SEARCH users USING INDEX idx_email (email=?)   ← 走索引了
--   SCAN users                                      ← 全表扫描！要优化

-- 输出中的关键字样：
--   SCAN TABLE      = 全表扫描（慢）
--   SEARCH ... USING INDEX = 用索引查找（快）
--   SEARCH ... USING COVERING INDEX = 覆盖索引（最快，不用回表）
--   USE TEMP B-TREE FOR ORDER BY = 排序用了临时结构（可优化）

-- 创建索引
CREATE INDEX idx_email ON users(email);
CREATE INDEX idx_name_age ON users(name, age);        -- 复合索引
CREATE UNIQUE INDEX idx_email_uniq ON users(email);   -- 唯一索引
CREATE INDEX idx_lower ON users(email COLLATE NOCASE);-- 大小写不敏感
CREATE INDEX idx_expr ON users(length(name));         -- 表达式索引(3.9+)
CREATE INDEX idx_partial ON users(age) WHERE age > 18;-- 部分索引(3.8+)

-- 统计信息与优化
ANALYZE;                          -- 收集统计信息，让查询规划器更准
PRAGMA optimize;                  -- SQLite 建议定期运行
PRAGMA index_list(users);         -- 看表上有哪些索引
PRAGMA index_info(idx_name_age);  -- 看索引包含哪些列

-- 索引维护
REINDEX;                          -- 重建索引
VACUUM;                           -- 整理数据库文件

索引设计与常见坑

场景索引方案说明
等值查询 WHERE a=?(a)最简单
等值 + 范围 WHERE a=? AND b>?(a, b)等值列在前
多等值 WHERE a=? AND b=?(a, b) 或 (b, a)顺序影响不大（区分度高的在前略优）
排序 ORDER BY b(b)避免临时排序
等值 + 排序 WHERE a=? ORDER BY b(a, b)完美，一次索引搞定
只查少数列覆盖索引 (a, b, c)不用回表，最快
  • 最左前缀原则：复合索引 (a, b, c) 相当于同时有了 (a)、(a,b)、(a,b,c) 三个索引，但不能加速只查 b 或 c 的查询。这是复合索引最容易被误解的地方。
  • 索引不是越多越好：每个索引都要在 INSERT/UPDATE/DELETE 时同步维护，写入变慢、文件变大。经验：单表索引控制在 5 个以内，删掉从未被使用的索引（用 EXPLAIN QUERY PLAN 验证）。
  • 函数会让索引失效：WHERE substr(name,1,1)='A' 用不上 name 的索引。解法：① 改成前缀匹配 LIKE 'A%'（可以用索引）；② 建表达式索引 CREATE INDEX ... ON t(substr(name,1,1))。
  • LIKE 的索引使用条件：'A%'（前缀）可以走索引；'%A' 和 '%A%'（包含）不能——需要全文索引（FTS5）或外部方案。
  • WAL 模式强烈推荐：PRAGMA journal_mode=WAL 让读写不互相阻塞（读不阻塞写、写不阻塞读），并发性能提升明显。代价是多出 -wal 文件，且网络文件系统上不支持。
  • ANALYZE 很重要：SQLite 的查询规划器依赖 sqlite_stat1 表的统计信息。数据大幅变更后不跑 ANALYZE，规划器可能选错索引。
  • 排障顺序：① EXPLAIN QUERY PLAN 看是否 SCAN；② 没走索引就检查 WHERE 条件与索引列的匹配（最左前缀、函数、类型）；③ 跑 ANALYZE；④ 考虑覆盖索引；⑤ 检查是否在事务里（SQLite 的写事务会锁全库）。
为什么建了索引还是全表扫描？

常见原因：① 违反最左前缀（查的条件不是索引最左列）；② WHERE 里对列用了函数或运算；③ 类型不匹配（存的是 TEXT 但用数字比较，SQLite 有类型亲和性规则）；④ 表太小（规划器认为全表扫描更快）；⑤ 没跑 ANALYZE 导致统计信息缺失。用 EXPLAIN QUERY PLAN 看具体原因。

SQLite 用的是 B+tree 吗？

不是，SQLite 用的是 B-tree（MySQL InnoDB 用 B+tree）。区别：B-tree 的每个节点都存数据，B+tree 只有叶子存数据、内部节点只做索引。所以 B+tree 的叶子有链表相连，范围扫描更高效；SQLite 的 B-tree 范围扫描要回到树上遍历。
