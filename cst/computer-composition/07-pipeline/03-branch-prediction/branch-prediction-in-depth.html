分支预测：95% 准确率为什么还是性能杀手

每 5~6 条指令就有一个分支，而流水线必须提前取指。猜错一次要清空 15~20 级前端。这一篇讲清 2 位计数器、TAGE、BTB 的原理，以及「准确率」和「性能损失」为什么不是一回事。

一句话定位：预测是为了「不停取指」

取指单元遇到分支时必须决定下一条取哪：顺序取下一条，还是跳到目标地址。等分支结果算出来再取，流水线就停了十几个周期，所以必须猜——猜对继续跑，猜错清空重来。

误预测代价约等于流水线深度（15~20 周期）
分支密度平均每 5~6 条指令 1 个分支
现代准确率95%~99%（大核）
关键结构方向预测器 + BTB + 返回地址栈
2 位饱和计数器：需要连续两次反向才翻转预测

把损失算成 CPI

CPI 增加 = 分支频率 × 误预测率 × 惩罚周期
误预测率分支频率 1/5分支频率 1/3含义
1%0.030.05几乎可忽略
5%0.150.25相当于慢了 15%~25%
10%0.300.50性能腰斩
20%0.601.00比不流水还慢
准确率不是线性指标

从 95% 提到 99%，误预测次数减少 5 倍，性能提升可能只有几个百分点——但某些分支密集的代码（解析器、状态机、虚函数调用）里，这 4 个百分点就是 20% 的差距。

预测器家族：从 2 位计数器到 TAGE

类型原理优点缺点
静态预测编译期决定（后向分支预测跳、前向预测不跳）零硬件成本准确率 70% 左右
1 位计数器记住上次结果简单循环边界必错两次
2 位饱和计数器连续两次反向才翻转循环只错一次对不规则分支无效
局部历史用该分支自己的历史做索引适合规律分支表容量压力大
全局历史（gshare）用最近 N 个分支的结果做索引能捕捉相关性历史混叠
Tournament两个预测器 + 选择器取长补短面积翻倍
TAGE多张不同历史长度的表投票现代主流，准确率最高实现复杂、训练慢

除了「跳不跳」，还要预测「跳去哪」：BTB（分支目标缓冲）缓存目标地址；函数返回用 RAS（返回地址栈）预测，因为同一个 return 指令的目标每次都不同。

代码层面：怎么让分支更好预测

// 难预测：数据驱动的分支
if (unlikely_condition) { ... }

// 好预测：循环边界（规律）
for (int i = 0; i < n; i++) { ... }

// 间接跳转是重灾区：虚函数、switch、函数指针表
switch (op) { case ADD: ... case MUL: ... }   // 目标多，BTB 压力大

// 无分支化：用算术或条件传送替分支
sum += cond ? x : 0;      // 可能编译成 cmov
mask = -(int)cond;        // 位掩码技巧

注意：无分支化不一定更快。cmov 会强制两条路径的数据都算出来，如果其中一条是昂贵的 load，反而更慢。要按「分支可预测性 + 两条路径的代价」判断。

排障：分支相关的问题定位

现象根因验证
同一段代码不同数据差 3 倍数据相关分支不可预测perf stat 看 branch-misses
虚函数调用密集处慢间接跳转 BTB 命中率低perf 看 iTLB/branch 事件
大 switch 性能悬崖跳转表 vs 比较链的选择看编译产物是否有 jump table
加了 if 反而更快帮助编译器生成更规整的布局对比汇编的跳转结构
Spectre 修补后变慢推测执行被限制（lfence/retpoline）属安全与性能的显式权衡

原理与取舍：为什么不能做到 100%

分支结果取决于运行时数据，而数据到达的时间晚于取指。理论上可以做到「预测所有可预测的模式」，但不可预测的分支（随机数据、哈希比较、解析器状态）没有规律可循。于是工程上转向两个方向：减少分支（谓词执行、向量化）和隐藏惩罚（更早解析分支、更小的冲刷范围）。

为什么循环边界用 2 位计数器只错一次？

进入循环时预测「跳」，最后一次退出时预测错 1 次并翻转到「不跳」；下次进入循环又会错 1 次。2 位计数器让「只错最后一次」成为可能，1 位则会错两次。

TAGE 是什么缩写？

TAgged GEometric history length——用几何级数长度的多段历史分别索引多张预测表，再由最长匹配的历史表给出预测，兼顾短规律与长规律。

分支预测和 Spectre 有什么关系？

Spectre 利用「预测执行会真的去读内存」这一点，通过缓存时序侧信道泄漏数据。修补手段（序列化、retpoline）本质是限制推测，代价是性能。
