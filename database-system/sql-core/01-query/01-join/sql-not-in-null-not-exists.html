SQL NOT IN 遇到 NULL：为什么三条候选一条也没返回

用集合 {1,2,3} 和子查询 {2,NULL} 手推三值逻辑、NOT EXISTS 与空值边界。

先手算一个反直觉结果

候选表 A 有 id=1、2、3；黑名单表 B 有 id=2 和 NULL。我们想找不在黑名单中的 id，写成 `WHERE A.id NOT IN (SELECT B.id FROM B)`。很多人预期返回 1、3，实际上在标准 SQL 的三值逻辑下可能一行都不返回。对 id=1 而言，`1 IN (2,NULL)` 相当于“1=2 或 1=NULL”：前者是假，后者是未知，假或未知仍是未知；NOT 未知仍是未知。WHERE 只保留条件为真的行，未知被过滤。id=3 同理；id=2 则明确命中，NOT 后为假。

NULL 表示缺失或未知的值，不是一个可以用普通等号匹配的特殊数字。`NULL = NULL` 也不是普通布尔真，而是未知。不同 SQL 方言在某些扩展操作符上有区别，但普通 `=`、IN 与 WHERE 的核心三值逻辑必须掌握。

图解：子查询含 NULL 的反连接

沿箭头逐步核对输入、变换和输出；下面的推演可以逐步切换。

把真、假、未知列出来

对子查询结果 {2,NULL}：1 与 2 不等、与 NULL 未知，所以 IN 未知、NOT IN 未知；2 与 2 相等，所以 IN 真、NOT IN 假；3 与 2 不等、与 NULL 未知，所以 IN 未知、NOT IN 未知。只有 NOT IN 为真的行能返回，此例没有。若 B 为空集，NOT IN 对非 NULL 候选一般为真；若 A.id 自身为 NULL，即使 B 只有 2，比较结果也需要单独处理。

这不是数据库“优化器坏了”，而是逻辑表达式的语义。执行计划可能把子查询改写为反连接，但必须保持 NULL 语义。只看计划形状，不能忽略查询结果的三值规则。

只找明确相等行，输出 1、3。

NOT EXISTS 的相关子查询

可改用 `WHERE NOT EXISTS (SELECT 1 FROM B WHERE B.id = A.id)`。对 A.id=1，B 中 2 不匹配，NULL 与 1 比较也不为真，因此子查询不存在行，NOT EXISTS 为真；3 同理；2 找到匹配行，返回假。于是输出 1、3。EXISTS 只关心子查询是否产生至少一行，SELECT 列写 1 或其他常量不改变存在性。相关子查询不必理解为“每行都真的完整扫描 B”，优化器可用索引或反半连接执行。

若 A.id 本身为 NULL，`B.id = A.id` 对任何 B.id 都不为真，所以 NOT EXISTS 会把这个 A 行保留下来；业务若只要有效 ID，需显式加 `A.id IS NOT NULL`。因此“把 NOT IN 全部替换成 NOT EXISTS”也不能不核对外表空值。需求是“未知 ID 也算未命中”还是“只看有效 ID”，需要写清楚。

过滤子查询 NULL 的另一种办法

若业务确认 B.id 的 NULL 不代表有意义的黑名单条目，可在子查询中显式 `WHERE B.id IS NOT NULL`，再使用 NOT IN。更稳妥的是从数据模型上对本应必填的黑名单 ID 加 NOT NULL 约束，阻止脏数据入表。不过若 NULL 表示“尚未确认的全局限制”一类特殊业务语义，直接过滤可能掩盖真实规则；先明确 NULL 从何而来。

对包含重复值的 B，IN 与 EXISTS 的结果通常仍按存在性判断，重复行不会让 A 多返回几次。直接 LEFT JOIN 再查右侧 IS NULL 也能表达某些反连接，但必须小心连接条件、右表可空列和重复行；选 `NOT EXISTS` 往往更直观。

SQL 语义与执行性能分开验收

先用四行玩具数据验证结果，再看执行计划与索引。B.id 上有索引时，优化器可能高效判断存在性；B 非常大且缺索引时，NOT EXISTS 也可能慢。`NOT IN` 的 NULL 安全处理可能影响优化器改写，但不能为追求速度牺牲正确性。实务上应给连接键明确约束、更新统计信息并查看实际行数。

某些方言提供 `IS DISTINCT FROM` 等空值安全比较，它把 NULL 当成可比较的状态，适合特定需求，但不能不加说明地替代所有反连接。设计时先写出 A.id 为 NULL、B.id 为 NULL、B 为空三种边界的期望答案。

自己复核

把 B 中的 NULL 删除，只保留 2，NOT IN 应返回 1、3；把 B 改为空，三个非空候选均应返回；再给 A 添一行 NULL，对比 NOT IN 与 NOT EXISTS 的结果。若结果与业务定义不同，修改谓词和约束，不要用 `COALESCE(id,-1)` 草率统一空值：-1 可能是真实 ID，哨兵值也会污染索引与统计。

改写

-- 陷阱复现：子查询里有一个 NULL，结果为空
SELECT * FROM users
 WHERE id NOT IN (SELECT user_id FROM orders);      -- orders.user_id 含 NULL -> 空集！

-- 写法 1：排除 NULL（最小改动）
SELECT * FROM users
 WHERE id NOT IN (SELECT user_id FROM orders WHERE user_id IS NOT NULL);

-- 写法 2：NOT EXISTS（推荐，NULL 安全）
SELECT * FROM users u
 WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);

-- 写法 3：LEFT JOIN + IS NULL（注意右表重复会造成行数放大，必要时 DISTINCT）
SELECT u.* FROM users u
  LEFT JOIN orders o ON o.user_id = u.id
 WHERE o.user_id IS NULL;

深入自检

为什么 NOT IN 遇到 NULL 会返回空集？

因为 SQL 是三值逻辑：x NOT IN (…, NULL) 展开为 NOT(x=a OR … OR x=NULL)。其中 x=NULL 恒为 UNKNOWN，而 TRUE OR UNKNOWN = TRUE、FALSE OR UNKNOWN = UNKNOWN——只要 x 不等于列表里任何非 NULL 值，整个表达式就是 UNKNOWN，取 NOT 后仍是 UNKNOWN，WHERE 不保留 UNKNOWN，于是没有任何行返回。

NOT EXISTS 为什么没有这个问题？

因为 NOT EXISTS 判断的是「子查询是否返回行」，而子查询里的等值条件 o.user_id = u.id 在遇到 NULL 时得到 UNKNOWN，该行不产生匹配——这是逐行存在性判断，语义上恰好就是我们要的「没有匹配的行」，因此 NULL 安全。

性能上 NOT IN 和 NOT EXISTS 谁更快？

现代优化器（MySQL 8.0.17+、PostgreSQL、Oracle）通常把两者都改写成 anti semi join，加上合适索引后性能接近。但在旧版本或子查询列可为 NULL 时，NOT IN 更容易退化成逐行判断。因此实践中推荐 NOT EXISTS，语义正确且不依赖优化器版本。

LEFT JOIN ... IS NULL 有什么坑？

右表一个键对应多行时会让结果行数放大（重复左表行），需要 DISTINCT 或先对右表去重。此外它的可读性不如 NOT EXISTS，优化器改写也不如 NOT EXISTS 直接。优点是能顺便取右表的列。

怎么快速判断一个查询是不是被 NULL 坑了？

先统计 COUNT(*) - COUNT(col) 看该列有多少 NULL；再把 NOT IN 改写成 NOT EXISTS 对比行数。若两者差异明显，基本就能确认是 NULL 语义问题，而不是数据本身的问题。

第一层 · 概念与判定：三者的语义差异

这三者看起来都是「在 A 但不在 B」，但遇到 NULL 时行为完全不同——这是 SQL 里最经典的陷阱之一。

写法语义遇到 NULL 时推荐
NOT IN (子查询)不在子查询结果集里子查询含 NULL → 结果恒为空！❌ 避免使用
NOT EXISTS不存在满足条件的行安全（NULL 不影响）✅ 首选
LEFT JOIN + IS NULL左连接后右表无匹配安全✅ 需要取右表字段时

为什么 NOT IN 遇 NULL 会返回空？因为 SQL 的三值逻辑：x NOT IN (1, 2, NULL) 会被展开为 x<>1 AND x<>2 AND x<>NULL，而 x<>NULL 的结果是 UNKNOWN，整个 AND 表达式即为 UNKNOWN，不会被 WHERE 选中——于是一行都返回不了。

  • 信号一：NOT IN 突然返回 0 行，但明明有数据 → 子查询里有 NULL。
  • 信号二：子查询的列没加 NOT NULL 约束 → 隐患。
  • 信号三：要「在 A 不在 B」→ 一律用 NOT EXISTS。

三种写法与 NULL 陷阱

-- 危险：如果 b.id 里有 NULL，整个查询返回 0 行
SELECT * FROM a WHERE a.id NOT IN (SELECT id FROM b);

-- 安全写法一：NOT EXISTS（推荐）
SELECT * FROM a WHERE NOT EXISTS (SELECT 1 FROM b WHERE b.id = a.id);

-- 安全写法二：LEFT JOIN + IS NULL
SELECT a.* FROM a LEFT JOIN b ON b.id = a.id WHERE b.id IS NULL;

-- 安全写法三：过滤掉 NULL 后再 NOT IN
SELECT * FROM a WHERE a.id NOT IN (SELECT id FROM b WHERE id IS NOT NULL);

-- 验证：检查子查询里有没有 NULL
SELECT COUNT(*) FROM b WHERE id IS NULL;   -- 非 0 就是隐患

性能提示：NOT EXISTS 通常比 NOT IN 快，因为它一旦找到匹配就停止扫描该行（半连接语义），而 NOT IN 需要先物化整个子查询结果。MySQL 5.6+ 对两者都做了优化，但 NOT EXISTS 仍是更稳的选择。

为什么 IN 没有这个 NULL 问题？

因为 x IN (1, NULL) 展开是 x=1 OR x=NULL。只要有一个为 TRUE，OR 就是 TRUE；UNKNOWN 只在不匹配时出现，不影响已匹配的行。OR 容忍 UNKNOWN，AND 不容忍——这就是 NOT IN（全是 AND）中招的原因。

NOT EXISTS 里为什么写 SELECT 1？

因为 EXISTS 只关心「有没有行」，不关心行的内容。写 SELECT 1、SELECT *、SELECT NULL 效果完全一样，优化器都会忽略选择列表。写 1 是为了表明「我不在乎内容」。

怎么彻底避免这个坑？

两条：① 团队规范上禁用 NOT IN (子查询)，一律用 NOT EXISTS；② 给参与关联列加 NOT NULL 约束，从源头消除 NULL。
