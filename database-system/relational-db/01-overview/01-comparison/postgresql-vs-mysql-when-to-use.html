数据库选型指南

PostgreSQL vs MySQL：什么时候该用哪个？

两者都是成熟、开源、世界顶级的的关系型数据库。问题从来不是"谁更强"，而是"你的场景更像谁的设计初衷"。本文用图解 + 场景对照 + 决策树，帮你一次选对。

一句话结论：把数据库当"可靠的关系型存储 + 事务引擎"用（Web 后端、CRM、电商订单、高并发读写）→ 选 MySQL；把数据库当"通用数据处理平台"用（复杂分析、地理空间、JSON 文档、自定义类型/函数、强一致性学术场景）→ 选 PostgreSQL。绝大多数互联网业务两者都能跑，真正分胜负的是边缘场景与长期可维护性。

MySQL 定位

"为 Web 而生的高性能事务型数据库"。设计目标是简单、快、稳定，在"读多写少 + 简单查询"上做到极致。Oracle 商业背书 + 云厂商深度集成。

PostgreSQL 定位

"最先进的开源关系型数据库 / 对象关系型数据库"。设计目标是标准合规、可扩展、功能全，像一门"带 SQL 的数据编程语言"。

2. 架构差异根源：为什么它们"性格"不同

选型要看表象，更要看底层设计哲学。两者的核心分歧从一开始的架构选择就注定了。

图 1：MySQL 把"存储"做成可插拔的插件生态；PG 把"一切"统一进一个强一致的内核。

MySQL 关键设计

可插拔存储引擎：InnoDB（事务、行锁、聚簇索引）是默认主力，但历史上 MyISAM、Memory 等各有取舍。优化器相对"务实"，对简单查询极快。线程池/连接模型轻量，高并发短连接表现好。

PostgreSQL 关键设计

进程每连接模型（新版有连接池方案），但内核统一、MVCC 实现更"干净"（基于事务 ID + 多版本行）。一切皆扩展：类型、操作符、索引方法（GiST/GIN/BRIN）、函数语言（PL/pgSQL、Python、C）都能自定义，被称为"可编程数据库"。

核心洞察：MySQL 的"可插拔"让它能在不同负载下换引擎（虽然现在基本只用 InnoDB）；PG 的"统一内核 + 扩展"让它能在不换数据库的前提下长出新能力（如 PostGIS 地理空间、TimescaleDB 时序）。一个是"换零件"，一个是"长器官"。

3. PostgreSQL 强在哪：它适合"复杂"和"严肃"

🧮 复杂查询与 SQL 标准

窗口函数、CTE（WITH 递归）、物化视图、丰富 JOIN 优化器。复杂报表 / 分析 SQL 写起来更顺、优化更好。

🗺️ 丰富数据类型

原生 JSONB（可建 GIN 索引）、数组、范围类型、UUID、几何、网络地址。文档型 + 关系型一库搞定。

📍 PostGIS 地理空间

工业级空间数据库能力，"附近的人/店/路线"首选，MySQL 空间功能弱很多。

🔧 强一致 & ACID 严谨

MVCC 实现干净，默认事务隔离级别 REPEATABLE READ 行为可预期，适合金融/学术级一致性要求。

🧩 可扩展（Extension）

TimescaleDB、pgvector（向量检索）、FDW（外部表）让 PG 变成时序/AI/联邦查询平台。

📜 标准兼容

高度遵循 SQL 标准，迁移到别的合规数据库（如 Oracle 部分场景）心智成本更低。

图 2：PG 的扩展能力让它"一个顶多个"，适合需求多变、想少引入中间件的项目。
典型用户画像（用 PG）：需要 GIS 的 LBS 应用 · 既要 SQL 又要存 JSON 的配置/元数据系统 · 写大量分析报表的 BI 后台 · 想用 pgvector 做 RAG/语义检索又不想单独上向量库 · 学术/金融等强一致性诉求。

4. MySQL 强在哪：它适合"快"和"规模"

⚡ 读密集 Web 性能

简单查询、主键/二级索引点查极快，配合缓冲池命中率，高 QPS 短连接场景是看家本领。

📈 运维生态成熟

主从复制、MGR 组复制、ProxySQL、各大云（RDS/PlanetScale）开箱即用，DBA 资料海量。

🧱 简单即稳定

心智负担低：默认 InnoDB 一把梭，不需要纠结"该用哪种索引/类型"，上手快、坑少。

🔁 复制与分片友好

基于 binlog 的复制生态极成熟，分库分表（ShardingSphere 等）方案久经考验。

🌐 云与托管首选

Aurora、PolarDB 等"MySQL 兼容"云原生引擎性能炸裂，迁移成本极低。

👥 人才池最大

几乎每个后端都写过 MySQL，招人、排错、找个现成解决方案都最容易。

图 3：MySQL 的甜区是"大量简单读 + 可靠写入"，靠复制与云原生横向吃下规模。
典型用户画像（用 MySQL）：标准 Web/App 后端（用户、订单、商品）· 高 QPS 读多写少的内容/社交 · 电商交易（强事务 + 简单模型）· 需要极致运维便利与云托管 · 团队以"快速交付"为优先。

6. 选型决策树：照着问自己 5 个问题

1

你需要地理空间 / 复杂自定义类型 / 向量检索吗？

需要 → PostgreSQL（PostGIS / 自定义类型 / pgvector 直接满足）。不需要 → 继续。

2

你的查询是不是"大量简单点查 + 高并发读"？

是，且要最省心的横向扩展与云托管 → MySQL。否，且有大量复杂联表/分析 SQL → PostgreSQL。

3

团队最熟哪个？DBA/资料/云支持哪个最齐？

以"交付速度"和"排错成本"优先 → 选最熟的。两者皆有 → 继续。

4

未来会不会"一个库长成平台"（少引中间件）？

希望文档/空间/向量/时序同库搞定 → PostgreSQL。愿意用专门中间件各司其职 → MySQL + 配套。

5

是全新项目还是接手遗留？

遗留系统 → 就地延续，别为"先进"重写。全新 → 回到 1~4 做理性选择。

7. 反模式与常见误区

❌ "PostgreSQL 永远比 MySQL 强"

错。在简单高并发读、云托管便利、人才密度上，MySQL 反而更优。PG 功能多 ≠ 你的场景需要。

❌ "MySQL 不能存 JSON"

MySQL 5.7+ 也有 JSON 类型，但索引（生成列 + 索引）和查询能力弱于 PG 的 JSONB + GIN，复杂文档查询仍逊色。

❌ "为先进而迁移"

遗留系统跑得好好的别重写。迁移的隐性成本（ORM 方言、存储过程、运维脚本）常被低估。

❌ "PG 进程模型扛不住高并发"

用 PgBouncer / 连接池即可，并非硬伤；但确实比 MySQL 线程模型"需要多想一步"。

❌ "两者语法完全一样"

都遵循 SQL 标准，但方言差异大（自增 vs SERIAL/IDENTITY、分页 LIMIT 一致但窗口函数细节有别、字符串拼接、存储过程语法）。别假设可无缝互换。

❌ "选完就一劳永逸"

规模上去后，两者都可能遇到单表过大、热点行、复制延迟。数据库选型只是开始，建模与调优才是胜负手。

✅事务边界清晰，避免长事务与锁等待
✅连接池配置正确（MySQL 连接模型 / PG + PgBouncer）
✅备份与 PITR（按时间点恢复）演练过

✅慢查询日志开启并定期 review

第一层 · 决策树：到底选哪个

大多数争论其实分不出胜负，因为两者都能覆盖 90% 的业务。真正拉开差距的是下面这几个明确的分叉点——按这个顺序问自己，通常三步就能定。

你的情况选谁原因
需要复杂查询：多层嵌套、CTE、窗口函数、数组/JSON 展开PGPG 的优化器更强（支持 Hash Join 全形态、并行查询更成熟）、SQL 标准支持更完整
需要半结构化：JSON 频繁查询/建索引PGJSONB + GIN 索引可高效检索；MySQL 的 JSON 只能整体存，查询基本全表扫
需要 GIS、全文检索（中文）、自定义类型/函数PGPostGIS 是事实标准；tsvector、扩展生态（pg_trgm、zhparser）成熟
超高并发简单读写（每秒几万次主键点查）MySQL连接是线程模型（PG 是进程模型），短连接/高并发场景开销更小
团队熟悉度 / 云上托管 / 已有运维体系跟团队走这个因素的权重往往高于所有技术差异
要在线加字段/加索引且不锁表MySQL 8 / PG 11+现代版本两者都支持 INSTANT/并发 DDL，但都有边界条件（见第三层）
  • 一句话总结：PG 是「功能更全的关系数据库」，MySQL 是「更轻更快、生态更偏向 Web 的关系数据库」。
  • 不要因为「听说 PG 更强」就迁。迁移成本（见第三层）通常远大于技术收益，除非你确实踩到了 MySQL 的能力边界。

-- —— 迁移前必查：对象与编码 ——
-- PG 侧
\l+                                    -- 列出库与编码
SELECT datname, pg_encoding_to_char(encoding) FROM pg_database;
SELECT tablename FROM pg_tables WHERE schemaname='public';

-- MySQL 侧
SHOW VARIABLES LIKE 'character_set%';
SHOW VARIABLES LIKE 'collation%';
SHOW CREATE TABLE orders\G            -- 拿到完整 DDL（含索引、外键、注释）

-- —— 类型映射（最容易出错的部分）——
-- TINYINT(1)      -> boolean / smallint     注意 MySQL 里 TINYINT(1) 常被当 bool
-- INT UNSIGNED    -> bigint                 PG 没有无符号，必须升一级防溢出
-- DATETIME        -> timestamp              PG 的 timestamp 不带时区，用 timestamptz 更安全
-- DATETIME(6)     -> timestamp(6)
-- DECIMAL(10,2)   -> numeric(10,2)          语义一致
-- VARCHAR(n)      -> varchar(n)             注意 n 是字符数还是字节数（两边都是字符数）
-- TEXT/BLOB       -> text / bytea
-- JSON            -> jsonb                  迁移时建议直接转 jsonb 而不是 json
-- AUTO_INCREMENT  -> GENERATED BY DEFAULT AS IDENTITY
-- 反引号 `col`    -> 双引号 "col"           未加引号的标识符 PG 会转小写！

-- —— 迁移后必做 ——
ANALYZE;                               -- PG 不会自动收集全部统计信息，导入后必须跑
SELECT setval(pg_get_serial_sequence('orders','id'), (SELECT max(id) FROM orders));
--   ^ 序列必须手动推进，否则插入立刻主键冲突

迁移后第一件事永远是 ANALYZE。PG 的 autovacuum 会做，但大批量导入后统计信息滞后会让执行计划错得离谱（看起来像「PG 很慢」，其实是统计信息没更新）。

第三层 · 迁移与使用的坑

  • 反引号 → 双引号，且 PG 会把未加引号的标识符转小写。这是迁移中最高频的错误：SELECT UserName FROM T 在 PG 里会变成 select username from t，如果表是用 "UserName" 建的就找不到。要么全改成小写下划线，要么全程加引号。
  • ONLY_FULL_GROUP_BY：MySQL 5.7+ 默认开，但很多老库关了。PG 从来不允许 SELECT 非聚合列不在 GROUP BY 里。迁移时会大面积报错，要么改写 SQL，要么改用 DISTINCT ON（PG 特有，很好用）。
  • 隐式类型转换：MySQL 很宽松（WHERE id = '123' 能走索引）；PG 严格，where id = '123'（id 是 int）通常也能转，但 where varchar_col = 123 会直接报错，且严格类型会导致索引失效。
  • 序列 vs AUTO_INCREMENT：PG 的序列独立于表，导入数据后必须手动 setval，否则第一条 INSERT 就主键冲突。
  • PG 的 VACUUM：更新/删除会产生死元组，不清理会导致表和索引膨胀、甚至事务 ID 回绕（autovacuum_freeze_max_age 默认 2 亿，接近时会强制 vacuum）。大表要单独调 autovacuum_vacuum_scale_factor（默认 0.2，大表可以调到 0.01）。
  • MySQL 的 utf8 是假的：utf8 只支持 3 字节，存不了 emoji 和部分生僻字；必须用 utf8mb4。这是历史包袱。
  • 在线 DDL 的边界：MySQL 8 的 INSTANT 只支持加列（末尾）、改默认值等少数操作；PG 加列带默认值在 11+ 也是瞬时的，但加索引仍需 CREATE INDEX CONCURRENTLY（且失败会留下 INVALID 索引，要手动清理）。

第四层 · 原理与取舍

核心差异来自 MVCC 的实现方式。它决定了两个数据库在「更新代价」「长事务影响」「清理机制」上的全部不同。

机制PostgreSQL（堆内多版本）MySQL InnoDB（undo 回滚段）
UPDATE 做了什么在原表插入一条新版本元组，旧版本原地留在表里原地更新，旧版本写入 undo log（集中存放）
后果表膨胀：频繁更新的表体积会增长，需要 VACUUM 回收undo 表空间增长：长事务会让 undo 无法回收
回滚 / 一致性读直接读堆里的旧元组沿 undo 链回溯重建旧版本
长事务的危害阻止 VACUUM 清理死元组 → 表和索引膨胀阻止 undo 清理 → undo 表空间暴涨（MySQL 8 可独立回收）
清理方式VACUUM（autovacuum 自动 + 手动）purge 线程异步清理 undo
HOT 优化有（同页内更新不更新索引）无对应机制
为什么 PG 需要 VACUUM 而 MySQL 不需要（看起来不需要）？

因为旧版本的存放位置不同。PG 把旧版本留在表文件里，所以必须有人把「对所有活跃事务都不可见的死元组」标记为空闲——这就是 VACUUM。MySQL 把旧版本放到专门的 undo 表空间，由后台 purge 线程异步回收，对使用者是透明的。所以严格说 MySQL 也有清理，只是不需要用户手动触发。代价是：PG 的代价是表膨胀（需要监控 n_dead_tup），MySQL 的代价是 undo 空间和历史版本链过长导致一致性读变慢——一个长事务跑几小时，MySQL 上后面所有需要回溯的事务都会越来越慢。

PG 进程模型是不是性能瓶颈？

是，但只在连接数很多时。每个 PG 连接是一个独立进程，内存开销约 5~10MB（MySQL 线程约 256KB~几 MB），且进程间上下文切换比线程重。所以：几百个连接两者都行；上千个连接时 MySQL 明显更从容。实践解法是 上连接池（PgBouncer，用 transaction 模式），把实际后端连接压到几十个——这几乎是所有 PG 高并发部署的标准做法。换句话说：PG 不是不能扛高并发，而是不能直接扛高并发短连接，需要连接池这一层。

「PG 更适合复杂查询」具体体现在哪？

三点最实在：① 优化器能力——PG 支持更完整的 Join 形态与并行执行计划（并行 Seq Scan / Hash Join / Aggregate），对大表分析型查询有质变；② 索引类型丰富——GIN 让 JSONB、数组、全文检索可以走索引（MySQL 的 JSON 基本只能全表扫），GiST 支撑 GIS 和范围类型，BRIN 让时序大表索引体积缩小几个数量级；③ SQL 表达力——CTE（含 MATERIALIZED 控制）、窗口函数、DISTINCT ON、FILTER 子句、LATERAL 子查询、自定义聚合函数。这三点叠加，让很多在 MySQL 里必须搬到应用层或离线数仓的计算，在 PG 里一条 SQL 就能解决。

什么时候应该坚持用 MySQL？

四条实在理由：① 团队和现有系统都在 MySQL 上——迁移成本远大于收益；② 高并发简单读写为主（典型的 Web CRUD、用户中心、订单），MySQL 的连接模型和生态工具链（分库分表中间件、审计、备份）更成熟；③ 依赖 MySQL 专有生态（如某些云 RDS 特性、binlog 订阅生态、已有的分库分表方案）；④ 需要极强的主从复制灵活性——MySQL 的 binlog 逻辑复制在级联、过滤、跨版本方面更灵活（PG 的逻辑复制不支持级联、DDL 不复制）。技术选型里「团队能稳定运维」这个因素的权重，通常高于所有特性对比。
