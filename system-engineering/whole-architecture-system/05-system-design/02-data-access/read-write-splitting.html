读写分离

主库扛写、多个从库扛读，用副本扩展读能力。

主从分流 Read/Write Splitting

写请求进入主库；副本接收复制，读请求可路由到合适的副本

大多系统读多写少。让主库负责写与强一致读，多个从库通过复制(如 MySQL binlog)异步同步，承接读流量。应用层或中间件按 SQL 类型路由。

必须面对的问题

  • 主从延迟：刚写入的数据从库可能还没同步到（读己之写失效）。
  • 解法：关键读走主库、写后强制读主、或用半同步复制。
  • 路由正确性：务必区分读写，避免把写发到从库。

面试高频问答

Q：主从延迟导致读到旧数据怎么办？
A：对一致性要求高的读（如支付后查余额）强制走主库；普通浏览走从库。也可采用『写后短暂读主』或会话级一致性策略。
Q：读写分离和 CQRS 什么关系？
A：读写分离偏『存储副本分担读压力』（同模型）；CQRS 偏『读模型结构都不同』。两者可叠加：CQRS 的读侧再配主从副本。

读写分离：一句话讲清它在解决什么

读写分离的本质，是把「读流量」从主库身上搬走。绝大多数业务是读多写少（常见 10:1 甚至 100:1），而单机数据库的连接数、CPU、IOPS 都是有限的。既然读操作不改变数据，那就可以让多台从库各自持有一份副本，把读请求分摊出去；只有写操作必须落在唯一的主库上，再由复制机制把变更同步给从库。

主库 Master唯一接受写入的节点，是所有数据的权威来源（source of truth）
从库 Replica只读副本，通过复制链路追赶主库；可横向扩展读能力
复制链路主库 binlog/redo → 传输 → 从库回放；这是延迟的根源
读路由由中间件或数据源框架决定这条 SELECT 发给谁
读写分离拓扑：写走主库，读分摊到多个从库，复制链路是延迟来源

主从延迟：读写分离唯一的硬伤

如果复制是同步的，那读写分离就没有一致性问题，但写入吞吐会被拖垮。现实里都走异步/半同步，于是存在一个时间窗口：主库已提交，从库还没追上。只要业务的读落在这个窗口里，就会看到「我刚改完怎么还是旧的」。

方案做法代价 / 适用
写后读主（最常用）一次会话内，写操作之后的一段时间内（如 1~3 秒，或用 GTID/位点判断）强制把读打回主库实现简单、可靠；主库会多承接一部分读，需控制时间窗
等位点 / GTID 追赶写入后拿到主库位点，读从库前等待其追上该位点（或超时降级到主库）一致性最强；会增加读延迟，从库卡住时要有超时兜底
半同步复制主库提交时至少等一个从库 ack 才返回（如 rpl_semi_sync）显著降低丢数据风险；写入 RT 上升，从库故障会拖慢写入
按业务分级账户余额、订单状态等强一致读走主；浏览列表、报表、搜索走从最实用；要求接口层面显式区分，不能一刀切
缓存兜底写完同步更新缓存，随后的读先查缓存绕过复制延迟；要处理缓存一致性，适合热点数据

判断延迟是否可控：监控 Seconds_Behind_Master 只是粗粒度，它在大事务执行期间会虚高。更靠谱的是用「心跳表」：主库每秒写一行时间戳，从库读取后计算差值，得到真实可观测延迟。

路由怎么做：三种实现位置

① 应用层数据源（最轻）

在 ORM / JDBC 层配置多数据源，用注解或 AOP 按方法名、事务只读标记切换。典型做法是 AbstractRoutingDataSource 配合 @Transactional(readOnly=true)。

  • 优点：无额外组件、链路短、易调试
  • 缺点：跨语言不通用；每个应用都要接一遍；Hint 需要显式写

② 中间件代理（最通用）

ShardingSphere-Proxy、ProxySQL 等部署在应用与数据库之间，解析 SQL 自动分流。

  • 优点：对应用透明、语言无关、可集中治理
  • 缺点：多一跳网络、解析有开销；自身要做高可用，否则成为单点

③ 客户端 SDK（折中）

ShardingSphere-JDBC 这类以库的形式嵌入应用，在本地完成路由直连数据库。

  • 优点：无中心化单点、性能好
  • 缺点：升级要发版；配置分散在各应用

必须绕开的坑

  • 事务里不要混读从库。只读事务可以；一旦事务内含写，后续所有读必须走主，否则破坏事务内的因果序。
  • 从库大查询会拖慢复制。报表类慢 SQL 建议单独抽一个「离线从库」，不与在线读池混用。
  • 不是读多就一定要分离。如果主库压力来自写（大量 UPDATE、热点行争用），加从库毫无帮助，应去做分片或写优化。
  • 从库延迟过大要自动摘除。负载策略应把延迟超阈值的从库降权或剔出读池，避免读到很旧的数据。
  • 故障切换要连着路由一起切。主库挂了提升从库为主时，指向旧主的写路由必须同步切换，否则双写。

深入自检

读写分离能提升写入性能吗？

不能。写仍然只有主库一个入口，反而因为要额外产出 binlog、等待半同步 ack，写入链路可能略微变慢。读写分离扩展的是读容量与读并发；写入瓶颈要靠分库分表、写优化（批量、异步化、削峰）或换更强的主库。

为什么有时从库延迟显示为 0，却依然读到旧数据？

Seconds_Behind_Master 衡量的是「已接收日志的回放进度」，不包含主库已提交但日志尚未传到从库的那段时间。网络拥塞、大事务未提交完时，这个指标会失真。用心跳表或 GTID 位点差才是端到端的真实延迟。

一主多从时，读请求应该怎么分配？

不要简单轮询。推荐按权重加健康度：配置基础权重（同规格权重相同），再结合实时延迟与连接数动态降权，延迟超阈值的直接摘除。同时要做「粘滞」——同一会话写后短期内固定在主库或同一从库，避免用户看到数据来回跳变。

从库连接被打满怎么办？

先确认是慢查询还是量太大。慢查询抽离到离线从库并加索引；量太大就继续加从库，同时在应用层加缓存挡一层。另外注意从库的 max_connections 往往配得比主库小，扩容时别只加机器不改参数。
