三者定位与现状

Hystrix、Resilience4j、Sentinel 代表了三种不同的设计取向，了解它们的出身就能理解取舍。

框架出身现状核心取向
HystrixNetflix，2012 年随微服务浪潮流行已停止维护（2018 年进入维护模式），新项目不建议线程池隔离 + 熔断，功能全但重
Resilience4j官方定位为 Hystrix 的轻量替代活跃维护，Java 8+ / 函数式风格轻量、模块化、只做熔断隔离不做流控
Sentinel阿里，2018 年开源活跃维护，Java 生态国内主流以流量控制为核心，控制台强大

一句话区分：Resilience4j 是「熔断隔离工具箱」，Sentinel 是「流量治理平台」。想治理流量选 Sentinel，只想给调用加个熔断器选 Resilience4j。

能力对比：直接看表

能力HystrixResilience4jSentinel
QPS 流量控制不支持（只有并发数）不支持核心能力，支持 QPS/并发/关联/链路
熔断支持（基于失败率）支持（失败率 + 慢调用比例）支持（失败率 + 慢调用 + 异常数）
隔离线程池 + 信号量信号量（推荐）＋ 可选线程池信号量式并发控制
系统自适应保护不支持不支持支持（按 CPU / LOAD / 总 RT / 入口 QPS）
热点参数限流不支持不支持支持（Top-K 热点自动识别）
预热 / 匀速排队不支持不支持支持（WarmUp、匀速器）
可视化控制台Dashboard（功能弱）无官方控制台功能完整，规则可动态推送
规则配置方式代码 / 配置代码 / 配置文件控制台动态下发 + 代码 + 多种数据源
语言支持JavaJavaJava 为主，有 Go / C++ 等多语言

注意：Resilience4j 的 RateLimiter 是有的，但它是简单的速率限制，没有 Sentinel 那样的关联限流、链路限流、热点限流与系统自适应。如果你的需求是「整个系统的流量治理」，Resilience4j 的限流能力不够。

选型决策：四种典型场景

  1. Java 微服务、需要完整流量治理 → Sentinel。要的是 QPS 限流、热点防护、系统自适应、动态规则推送与控制台，只有它能一站式满足。
  2. Java 项目、只需要熔断与重试 → Resilience4j。依赖轻（模块化按需引入）、无反射、函数式 API 清晰、与 Spring 生态契合好。引入成本低，不想要控制台时它是更干净的选择。
  3. 非 Java / 多语言栈 → 看语言生态：Go 用 go-zero 内置保护、gobreaker、或 Sentinel Go；Node/Python 多用 opossum / pybreaker。也可以把治理下沉到服务网格（Istio/Envoy 在 sidecar 层做限流熔断），业务代码零侵入。
  4. 老系统还在 Hystrix → 迁移到 Resilience4j 或 Sentinel。Hystrix 已停止维护，且线程池隔离模型开销大。迁移时主要替换注解与配置项，Semaphore 隔离可以直接对应。

关键参数与默认值

这三个框架的默认参数都不算保守，生产环境基本都需要按业务调整。

参数常见默认含义生产建议
慢调用 RT 阈值Sentinel 4900 ms（过大）超过此耗时的调用算「慢调用」按 P99 设定，典型 200~1000 ms，不要留默认
熔断失败率阈值50%失败率超过此值触发熔断核心链路可设 30%（更敏感），非核心 60%
最小请求数Resilience4j 100；Sentinel 5窗口内请求数不足则不熔断低 QPS 接口要调小，否则永远不熔断
熔断冷却时间5 s ~ 60 sOpen 转 Half-Open 的等待5~10 s 起步；按连续熔断次数指数递增更好
Half-Open 允许请求数Resilience4j 10；Sentinel 1半开态放行的探测请求数流量大时 1~5 个足够，防止试探流量打垮刚恢复的下游
滑动窗口大小Resilience4j 100 次调用；Sentinel 1 s / 10 格统计窗口高 QPS 用时间窗口，低 QPS 用计数窗口

最常见的配置错误：忘了改「最小请求数」。一个 QPS 只有 2 的接口，Resilience4j 默认要 100 个请求才判断，意味着 50 秒内永远不会熔断 —— 熔断等于没装。

深入自检

Hystrix 为什么被弃用了？

三个原因叠加：① Netflix 自己转向 adaptive concurrency limit，认为线程池隔离代价过高，官方宣布停止新功能开发；② 线程池隔离开销大，每个依赖一个池，依赖多了线程数爆炸，且线程切换有真实成本 —— 这也是后来者普遍改用信号量的原因；③ 生态上 Resilience4j 与 Sentinel 提供了更好的替代品。注意：已上线的 Hystrix 系统不必恐慌，它仍可用，只是不再演进。

线程池隔离和信号量隔离到底选哪个？

先看两者能力差异：线程池能主动超时中断（超时后线程可回收），信号量不能（只能拒绝，已进入的调用必须等它自己返回）；但信号量零线程开销。决策规则：调用依赖数量少（< 20）且需要严格超时控制 → 线程池；高频低延迟调用、依赖数量多 → 信号量。现代实践普遍转向信号量 + 客户端超时：因为超时控制可以交给 HTTP client 的 timeout 参数，不必用线程切换来实现。

有了服务网格，业务代码还需要这些框架吗？

看治理粒度。服务网格（Istio/Envoy）在 sidecar 层做限流熔断，优点是与语言无关、业务零侵入，适合做服务间的粗粒度保护；但它看不到方法级、参数级的差异 —— 比如「对某个热点商品 ID 限流」「对某个具体方法单独设阈值」网格做不到。所以成熟架构是两层都要：网格管服务间，业务框架管方法级与热点。若只上了一层，优先上业务框架（因为方法级保护更贴近故障点）。

熔断和限流的规则应该写到代码里还是控制台？

规则外置（控制台 / 配置中心）远优于硬编码。原因很实际：线上出现突发流量时，你需要在 1 分钟内调低阈值，而改代码要经历提交、评审、构建、发布，至少要几十分钟。Sentinel 在这方面做得最好（控制台动态推送 + 多种数据源持久化）；Resilience4j 也可通过 Spring Cloud Config 实现动态刷新。但要注意：外置规则必须有版本管理与审计，否则谁在什么时候改了什么会完全失控。
