搜索引擎选型：Elasticsearch vs Solr

两者都基于 Lucene，差异在分布式与生态，一张表看清

它们共享什么

Elasticsearch 和 Solr 都建立在 Apache Lucene 之上——倒排索引、分词器、相关性打分（BM25）这些核心检索能力二者基本一致。所以"谁搜得更准"不是主要分歧，分歧在分布式架构、易用性和生态。

📌 如果你的数据量很小，Lucene 之上的重量级分布式框架反而是负担；SQLite FTS5 或 Postgres 全文检索可能更合适。

两个选手的差异

🔍 Elasticsearch

分布式原生、REST/JSON 接口、近实时（NRT）、Kibana 生态、上手快、社区大。

🟦 Solr

老牌、SolrJ/HTTP、文本检索与配置能力强、SolrCloud 模式、企业集成成熟。

横向对比

上手成本低，文档与社区多中，配置项更密
典型场景日志/指标、搜索、可观测站内搜索、企业检索、文本分析

何时不该用它们

  • 数据量小、查询简单：Postgres 全文检索（tsvector）或 SQLite FTS5 就够了，省一套集群运维。
  • 纯向量相似性检索：向量数据库（Milvus / pgvector / Qdrant）更对口，不要硬用 ES 的向量字段凑合。
  • 简单 KV 前缀搜索：Redis 即可，不必引入搜索引擎。
⚠️ ES 的"近实时"不是"实时"：文档写入后要等 refresh（默认 1s）才可被搜到；对一致性要求极高的场景要调小刷新间隔或接受延迟。

第一层 · 先判定要不要用搜索引擎

信号该用什么
全文检索、模糊匹配、相关性排序ES / Solr（Lucene）
数据量小、查询简单Postgres FTS / SQLite FTS5

第二层 · 关键参数与数量级

  • refresh_interval 默认 1s：写入可见性的延迟来源，可调小但增加开销。
  • 分片数：单分片建议 10–50GB；分片过多管理开销大，过少无法并行。
  • 副本数：默认 1，读多可加副本，但占存储与堆。
  • BM25：Lucene 默认打分，k1≈1.2、b≈0.75，基本不用动。

第三层 · 搜索变差怎么查

  • 搜不到刚写入的：先确认 refresh 间隔与事务日志（translog）是否刷盘。
  • 相关性离谱：看分词器（analyzer）是否匹配业务语言（中文要 IK/ICU，不能按空格切）。
  • 集群变红：看是否有分片未分配（磁盘水位阈值默认 85%/90%）。
  • 查询慢：确认是否深分页（from+size 过大），改用 search_after / scroll。

第四层 · 原理与取舍

ES 和 Solr 的核心都是 Lucene 的倒排索引：词项 → 文档列表，配合 BM25 按相关性排序。ES 把 Lucene 做成了"分布式系统"（自动分片、副本、近实时），代价是运维复杂度与堆内存压力；Solr 同样基于 Lucene，但在企业级文本检索和显式配置上更老练。选型时真正要问的是：你更需要"开箱即用的分布式搜索 + 生态"，还是"可控的传统检索平台"。

ES 和向量数据库冲突吗？

不冲突，是互补。ES 擅长关键词/全文与过滤，向量库擅长语义相似。生产常做混合检索：ES 出关键词召回，向量库出语义召回，再rerank融合。纯语义场景才直接用向量库。
