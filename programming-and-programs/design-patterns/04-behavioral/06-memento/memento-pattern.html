01 · 从问题出发

为什么会需要这个模式？

画布编辑器要支持撤销，但历史管理器不该直接改画布内部字段。

画布编辑器要撤销拖动。若历史管理器直接读取画布的 shapes、selection、zoom 等私有字段，它就会依赖画布内部结构；画布一改，历史也要跟着改。

😵 直接写会怎样

history.push({shapes: canvas.shapes, zoom: canvas.zoom})
// shapes 是共享引用；后来拖动会一起改变历史

💡 关键转折

原发器生成/恢复快照；保管者只保存快照，不解释其中内容。

让画布自己生成和恢复快照；历史管理器只负责保管，不解析内部状态。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

class Canvas {
  save() { return Snapshot(deepCopy(this.shapes)) }
  restore(snapshot) { this.shapes = deepCopy(snapshot.shapes) }
}
undoStack.push(canvas.save())
canvas.move(shape, dx, dy)
canvas.restore(undoStack.pop())

读代码时抓住三件事

  1. save 由原发器创建快照，不暴露可变内部引用。
  2. restore 由原发器解释快照并重建合法状态。
  3. 历史栈只管存取顺序，可设置容量上限。

换个业务场景，还能认出来吗？

游戏存档能恢复角色位置、背包和任务进度。快照范围应明确：外部服务器状态、现实世界时间和未提交网络操作通常不能靠本地存档自动还原。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

要保存对象旧状态以支持撤销或恢复

三个具体场景

  • 画布撤销拖动与改色
  • 游戏存档恢复角色状态
  • 编辑器回到之前的文档版本

不适合或要小心

快照可能很大；可限制历史长度、保存增量或与命令模式结合。深浅拷贝必须按状态所有权设计。

快照会消耗空间；共享可变引用会让历史被后续修改污染

最容易混淆的相邻模式

模式真正的区别
命令保存操作及逆操作，适合可逆编辑；备忘录保存状态快照，适合复杂状态恢复。
原型复制对象用于创建新对象；备忘录复制状态用于以后恢复原对象。

区分时问自己：需要恢复旧状态，还是反向执行一条操作？

落地前检查

  • 测试快照创建后再改当前对象，快照不应变化。
  • 定义历史上限与增量存储策略。
  • 明确哪些外部副作用不在快照恢复范围内。
06 · 自己说一遍

两道检验理解的小题

历史栈为什么不直接改 shapes？

快照的创建与恢复由画布负责，历史栈只保管，避免破坏封装。

保存整个对象的浅拷贝为何可能让撤销失败？

嵌套可变数据若共享引用，后续编辑也会改到历史快照，恢复时拿不到旧状态。
