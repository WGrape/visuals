固定阈值为什么会失效

传统限流把阈值写死：比如单机 1000 QPS。它假设「1000 QPS 在任何时候都是安全的」，但这个假设在三个场景下直接崩塌。

场景发生了什么固定阈值的结果
下游变慢一次调用从 10 ms 涨到 200 ms，同样 QPS 下占用线程翻 20 倍QPS 没超限，但线程池先被打满，全站超时
机器规格不一8 核与 32 核混部，同一阈值对弱机过高、对强机过保守弱机先崩，强机长期浪费 60% 容量
流量模型变化从轻接口切到重接口（如批量导出），单请求成本涨 10 倍QPS 达标但 CPU 已经 95%，请求在排队

一句话总结：QPS 是「输入指标」，而系统真正承压的是「资源水位」。限流应该盯住水位，而不是盯住入口计数。

三个可用的水位信号

自适应限流需要一个能实时反映「我快撑不住了」的信号。三种主流信号各有适用面。

信号怎么采优点坑
CPU 使用率 / LOAD采样 /proc/stat 或容器 cgroup cpuacct最贴近真实瓶颈，通用性强有滞后，采样周期短会抖动；容器内可能读到宿主机值
排队延迟 / 平均 RT请求入队到出队的时间差对过载最敏感，滞后小RT 受下游影响，需剔除外部因素
成功率 / 错误率滑动窗口统计直接反映业务结果是「结果指标」，等它恶化时往往已经晚了

推荐组合：以 CPU 或排队延迟为主信号（快），以成功率作为兜底校正（准）。只用成功率是典型的马后炮。

三种自适应算法

拿到水位信号后，怎么把它变成阈值？工程上主流三种路线。

算法思路代表特点
PID 类反馈控制按「当前水位 − 目标水位」的偏差比例调节放行量通用自研、部分网关实现简单直观；参数难调，容易振荡
并发自适应（BBR 思路）不再限 QPS，改为限制「同时在处理的请求数」，按最小 RT 与当前 RT 推算最佳并发Sentinel 系统自适应、Kratos、BBR 拥塞控制理论扎实，对下游变慢极敏感；依赖 RT 采样质量
排队论 / 梯度用 Little's Law 由并发与 RT 反推可承载 QPSNetflix concurrency-limits平滑度好；模型假设较强，冷启动需预热

自适应限流的本质是一个负反馈闭环，与 TCP 拥塞控制同构

关键参数怎么配

自适应不是「装上就不管」，这几个参数直接决定它是保护还是添乱。

参数常见默认含义调错会怎样
目标水位（CPU）60% ~ 75%希望维持的 CPU 使用率设到 90% 基本失去保护意义（等它触发时已在排队）
调整周期1 s ~ 5 s多久重算一次阈值小于 500 ms 容易随 GC 抖动振荡；大于 30 s 反应太慢
单次调整幅度上限±20% ~ ±30%防止阈值剧烈跳动不限幅度会在流量拐点处剧烈振荡
恢复速率水位恢复后抬升阈值的速度抬太快会造成二次过载，抬太慢会长期浪费容量
最小阈值下限峰值的 10%防止阈值被压到 0 导致服务不可用不设下限，极端情况下会把自己「饿死」

落地建议：先只观察不生效（影子模式）跑 1~2 周，把自适应算出的阈值与人工阈值对比，确认趋势合理再开启。

深入自检

自适应限流和固定限流能同时开吗？

可以，而且是推荐做法：固定限流作为兜底硬上限（防止自适应算法异常时放出致命流量），自适应作为常态调节。生效规则取两者更严格的那个。例如固定 1000 QPS，自适应算出 600，最终按 600 放行；自适应异常算出 5000，则被 1000 兜住。

容器里读到的 CPU 是宿主机的，怎么办？

这是容器化场景最常见的坑。要用 cgroup 而不是 /proc/stat：cgroup v1 读 /sys/fs/cgroup/cpuacct/cpuacct.usage 增量除以 cpu.cfs_quota_us / cpu.cfs_period_us 得到的核数；cgroup v2 读 cpu.stat 的 usage_usec 增量。直接用 top 看到的是宿主线程数，会导致自适应完全失效。

为什么自适应会「振荡」？

三个典型原因：① 采样窗口太短，被 GC 或瞬时尖刺干扰；② 单次调整幅度无上限，一步砍太狠导致下一周期水位骤降又猛涨；③ 恢复速率快于降低速率。解法是对信号做滑动平均或 EWMA 平滑（常用衰减因子 0.8~0.9）、限制单次幅度、并让恢复明显慢于降低（这是控制系统里的「快降慢升」原则）。

自适应限流能保证不过载吗？

不能保证，它只能降低过载概率并缩短过载时长。因为反馈必然有滞后：从水位升高到阈值下调，至少要一个采样周期。在这期间流量仍在涌入。所以自适应之外必须配排队上限和超时作为最后防线，三者叠加才能把最坏情况控制住。
