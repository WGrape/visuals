先建立直觉：一个带工具箱的高速工作台

普通 KV 缓存（如 Memcached）只有一个抽屉：放字符串、取字符串。

Redis 是一整套工具箱：除了普通抽屉，还有清单（List）、表格（Hash）、集合（Set）、排行榜（ZSet），而且很多操作在服务端就能完成——比如「给排行榜加分并取前 10」，一条命令搞定，不用把数据取回来自己算。

五种核心数据结构与典型用途

结构特点典型用途
String最基础，可存文本/数字/二进制（≤512MB）缓存、计数器（INCR）、分布式锁
Hash字段-值映射，适合存对象用户信息、购物车（可单独改字段）
List有序可重复，双端操作队列、消息队列、最新列表
Set无序去重，支持交并差标签、共同好友、去重
ZSet带分数排序，去重排行榜、延迟队列、优先级队列
为什么结构这么重要？因为它把计算下推到数据所在的地方。比如排行榜：ZINCRBY 原子加分、ZREVRANGE 服务端排序取 Top N。如果用 String 存整个对象，你得「取出 → 反序列化 → 改 → 排序 → 序列化 → 写回」，既有网络开销又有并发覆盖风险。

为什么单线程还这么快

所有请求 ② 无法利用多核（需靠多实例/集群） ③ 大 key、复杂命令要格外小心 ④ 6.0 起网络 IO 已多线程化
单线程最重要的实践含义：千万不要执行慢命令。KEYS *、大 key 的 HGETALL、百万元素的集合运算，都会阻塞整个实例。要用 SCAN 代替 KEYS，避免大 key。

持久化：两种方式的取舍

方式原理优点缺点
RDB定时生成内存快照文件小、恢复快、对性能影响小可能丢失最后一次快照之后的数据
AOF记录每一条写命令数据更完整（最多丢 1 秒）文件大、恢复慢、需要重写
生产上通常两者都开：AOF 保证数据完整性，RDB 便于快速恢复和备份。Redis 重启时优先用 AOF 恢复（数据更全）。

高可用三件套

方案解决什么特点
主从复制数据冗余、读写分离从节点异步同步主节点数据
哨兵 Sentinel自动故障转移监控主节点，宕机自动提升从节点
Cluster 集群横向扩展（分片）数据按 slot 分布到多节点，突破单机内存与吞吐上限

典型使用场景

  • 缓存（最主流）：减轻数据库压力；
  • 计数器 / 排行榜：INCR、ZINCRBY；
  • 分布式锁：SET NX EX + Lua 释放；
  • 限流：滑动窗口、令牌桶（配合 Lua）；
  • 消息队列：List 或 Stream（轻量场景）；
  • 会话存储：分布式 Session；
  • 地理位置：GEO 命令。
注意边界：Redis 再强也是内存数据库。不要把它当主存储用（除非能接受持久化风险与内存成本），也不要用它存超大数据（内存很贵）。核心数据仍应落在关系型或专用存储中。

🎯 面试问答

Q：Redis 是单线程的，为什么还这么快？
A：因为瓶颈不在 CPU。Redis 的操作主要是内存访问（纳秒级）和网络 IO；单线程反而省掉了锁竞争、上下文切换、多线程同步的开销，代码路径极短。此外它的数据结构（哈希表、跳表等）专为单线程场景做了极致优化。Redis 6.0 起网络读写也已多线程化，进一步提升了高并发下的吞吐。真正要注意的是：单线程意味着一个慢命令会阻塞所有请求——所以必须避免 KEYS * 和大 key 操作。

Q：RDB 和 AOF 该选哪个？
A：生产环境通常两个都开。RDB 是定时内存快照：文件紧凑、恢复快、对运行时性能影响小，但会丢失最后一次快照之后的数据。AOF 记录每条写命令：最多丢 1 秒数据，但文件更大、恢复更慢、需要定期重写。两者都开时，Redis 重启优先用 AOF 恢复（数据更完整），同时保留 RDB 用于备份和快速全量恢复。如果只选一个：能容忍分钟级丢失用 RDB，要求更高用 AOF。

Q：Redis 能当数据库用吗？
A：能但不推荐作为唯一主存储，除非你清楚接受了权衡。可以的情况：数据可重建、能容忍 AOF/RDB 的持久化窗口（可能丢秒级数据）、数据量能装进内存且成本可接受。不应该的情况：核心业务数据不能丢、数据量远超内存、需要复杂查询与事务。更稳妥的架构：Redis 做缓存/加速层，核心数据放在关系型或专用存储，Redis 宕机后能从数据源重建。

Q：为什么不能执行 KEYS * 命令？
A：因为 Redis 单线程执行命令，KEYS * 会遍历全部 key，数据量达到百万级时耗时可达几百毫秒到数秒——期间整个实例无法处理任何其他请求，会造成大面积超时，生产环境等同于一次故障。替代方案：用 SCAN 增量迭代（每次只扫少量 key，不会阻塞），或直接从业务侧维护 key 索引。
