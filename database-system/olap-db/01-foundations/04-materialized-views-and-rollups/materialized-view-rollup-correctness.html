OLAP 物化视图与预聚合：SUM 能滚动，平均值为何会算错

用两个门店的订单金额手算可合并聚合状态，理解维度粒度、刷新与查询改写。

预聚合先回答“每行代表什么”

原始订单表有门店、日期、品类、金额和订单 ID。每天按门店与品类统计销售额，若每次都扫描一亿行明细，报表可能太慢。可以预先把“日期 × 门店 × 品类”聚合成小表或物化视图；同一粒度上的 SUM(amount)、COUNT(*) 等结果可由明细增量维护，再在更粗粒度上继续合并。但如果报表还要按用户年龄或订单渠道过滤，而预聚合里没有这些维度，就无法从已丢失的信息精确恢复结果。

物化视图的本质是提前保存某个查询的结果或中间状态。它不是“自动比原表快”的魔法：刷新数据、维护索引、占用存储都有成本。查询改写也受 SQL 形状、过滤条件、聚合函数及优化器能力约束。设计前先列出报表的 group by 维度与过滤维度，再决定预聚合粒度。

图解：平均值的正确滚动方式

沿箭头逐步核对输入、变换和输出；下面的推演可以逐步切换。

两个门店的平均值陷阱

门店 A 有 2 单，总额 200，平均 100；门店 B 有 8 单，总额 400，平均 50。全区域真实平均订单额是 (200+400)/(2+8)=60。若把两个门店的平均值直接相加除以 2，得到 75，错误地让只有 2 单的 A 与 8 单的 B 权重相同。正确的预聚合状态应保存 sum_amount 与 order_count，再在上层用 SUM(sum_amount)/SUM(order_count)。

SUM 与 COUNT 是可合并状态；AVG 可以转为 sum 与 count 的组合。MIN、MAX 也可跨不重叠分组继续合并。精确 COUNT(DISTINCT user_id) 通常不能只把各门店去重数相加，因为一个用户可能在多个门店下单；若需要全局精确去重，必须保存足够的信息或使用适合的算法与数据结构。近似去重草图如 HLL 可合并，但需明确误差边界。

粒度决定能否回答新问题

按“日 × 门店 × 品类”保存预聚合，可以求某日全门店某品类销售额，也可以汇总成月度，但若只保存月度总额，就无法准确回答某天金额；若未保存城市维度，能否按城市汇总取决于门店到城市的映射是否稳定且可追溯。订单退款若后来发生，原聚合状态需要相应负向更新或重算；只追加正金额会让报表越来越高。

维度表也可能发生历史变化：门店从上海迁到苏州，今天查询上月销售额，是按当时城市还是当前城市归属？两种口径均可能合理，但要在模型中明确。物化视图的分组键与数据血缘应能支持期望口径。仅写“按城市统计”是不完整的需求。

指标可保存的聚合状态跨组注意
销售额SUM(amount)可直接求和
平均订单额SUM(amount)+COUNT(*)合并后再除
最小金额MIN(amount)可取各组最小
精确 UV用户集合等充分信息分组去重数不能直接相加

刷新模式与可见性

全量刷新容易理解，但大表重算昂贵；增量刷新只处理新增或变更数据，但必须能正确处理删除、更新和迟到事件。同步维护让写入承担更多成本，异步刷新则带来新鲜度窗口。某些系统提供自动查询改写与刷新机制，行为和限制因产品而异。报表标题应标明数据截至时间，关键账务结果还需定义可接受延迟。

若一次刷新只完成了一半却把新旧结果混在一起，用户会看到不一致报表。应使用可原子切换的快照、版本或分区发布流程，让查询读取同一批次结果。实时增量与历史回补并行时，尤其要避免重复计数：同一订单事件既在增量流里处理、又被回补任务覆盖，应以订单 ID 与版本保证最终状态正确。

查询改写怎么验收

用 EXPLAIN 确认报表是读原始明细还是命中物化视图，再核对过滤条件是否完全覆盖、聚合粒度是否足够细。构造门店 A 两单、B 八单的样例，检查跨门店 AVG 返回 60。再放入一个跨店用户，检查精确去重没有把分组计数直接相加。最后加入一笔迟到退款，观察刷新后总额是否减少。

性能验收不要只看单次查询延迟，还要记录刷新耗时、写入放大、额外存储与数据新鲜度。若报表一天只跑一次，直接扫描列式明细可能比持续维护大量物化视图更简单。预聚合是用维护成本换查询成本，值得与实际负载一起量化。

一眼辨认错误答案

看到“把每日平均值相加再除以天数”，先查每天订单数是否相同；看到“各门店 UV 相加就是全城 UV”，先查用户是否跨店；看到“刷新成功即报表最新”，先查源数据有没有迟到与回补；看到“视图包含金额就能回答所有金额问题”，先查维度与过滤条件是否已经被聚合丢弃。这四个检查能覆盖很多分析报表的隐蔽错误。

练习：日表保存 date、store、sum_amount、order_count。写出月度平均订单额的计算式，并说明若需求新增“只看新用户”条件，为什么这张日表可能不够。

三类物化视图的刷新语义

类型刷新方式数据新鲜度代表

正确性核心：预聚合的定义必须与查询的定义严格一致，包括维度层级、时间边界、去重语义与过滤条件。任何一边走样，结果就不可信。

聚合状态的 State / Merge 模型（ClickHouse）

环节写法说明
写入侧（物化视图）sumState(amount) / uniqState(uid)存的是中间状态不是最终值
查询侧sumMerge(s) / uniqMerge(u)把多个状态合并成最终结果
存储类型AggregateFunction(sum, Decimal(18,2))列类型必须声明聚合函数与参数类型
引擎AggregatingMergeTree合并时把状态再合并一次

ClickHouse

-- 1) 明细表
CREATE TABLE orders_raw
(
    dt      DateTime,
    shop_id UInt32,
    amount  Decimal(18,2)
) ENGINE = MergeTree PARTITION BY toYYYYMM(dt) ORDER BY (dt, shop_id);

-- 2) 聚合状态表（存 State）
CREATE TABLE orders_agg
(
    day     Date,
    shop_id UInt32,
    s_amount AggregateFunction(sum, Decimal(18,2)),
    s_orders AggregateFunction(count)
) ENGINE = AggregatingMergeTree
PARTITION BY toYYYYMM(day) ORDER BY (day, shop_id);

-- 3) 物化视图：写入时同步聚合
CREATE MATERIALIZED VIEW orders_mv TO orders_agg AS
SELECT toDate(dt) AS day,
       shop_id,
       sumState(amount) AS s_amount,          -- 注意是 State
       countState()     AS s_orders
  FROM orders_raw
 GROUP BY day, shop_id;

-- 4) 查询：用 Merge 还原
SELECT day, shop_id,
       sumMerge(s_amount)  AS amount,
       countMerge(s_orders) AS orders
  FROM orders_agg
 WHERE day >= today() - 7
 GROUP BY day, shop_id;

PostgreSQL

-- PostgreSQL：全量刷新（CONCURRENTLY 不阻塞读，但要求有唯一索引）
CREATE MATERIALIZED VIEW mv_daily AS
SELECT date_trunc('day', created_at) AS day, shop_id, sum(amount) AS amount
  FROM orders GROUP BY 1, 2;

CREATE UNIQUE INDEX ON mv_daily (day, shop_id);   -- CONCURRENTLY 的前提
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_daily;   -- 不锁读
REFRESH MATERIALIZED VIEW mv_daily;                -- 快但排他锁

Rollup 的维度层级与一致性校验

层级粒度校验方法
L0 明细原始行行数与源表一致
L1 分钟/小时按时间聚合与 L0 按该粒度重算对比，差值为 0
L2 天按天聚合L2 = Σ(L1)，逐日对比
L3 月/维度汇总跨维度汇总各维度拆分之和 = 总计（可加性检查）

可加性陷阱：sum/count 可加，uniq/avg/max 不可直接相加。UV（去重数）不能由小时 UV 相加得到日 UV，必须保留中间状态（如 HLL）才能正确上卷。

对账

-- 一致性校验：用重算结果对比预聚合结果
SELECT day,
       (SELECT sum(amount) FROM orders_raw WHERE toDate(dt) = a.day) AS recomputed,
       a.amount AS precomputed,
       (SELECT sum(amount) FROM orders_raw WHERE toDate(dt) = a.day) - a.amount AS diff
  FROM orders_agg_daily a
 WHERE day >= today() - 30
HAVING diff != 0                       -- 有输出即不一致
 ORDER BY day;

深入自检

增量物化视图和全量刷新的本质区别是什么？

增量 MV 是在源表写入时把变更同步应用到预聚合结果（近实时、代价低但只跟随插入）；全量刷新是定时整体重算（结果始终与源表一致，但代价随数据量增长，且刷新期间数据陈旧或锁表）。

为什么 UV 不能按小时相加得到日 UV？

因为去重计数不具备可加性：同一个用户出现在两个小时里，小时 UV 各计 1，相加得 2，而日 UV 应是 1。正确做法是保留可合并的中间状态（HLL、uniqState），在上卷时合并状态再求值。

建好物化视图后为什么历史数据没进去？

ClickHouse 的物化视图只对建好之后的新写入生效，历史数据不会被自动处理。标准做法是建 MV 后立即执行一次回填（INSERT INTO 目标表 SELECT ... FROM 源表 WHERE 历史条件），并注意避免与实时写入冲突。

ClickHouse 的 State/Merge 为什么必须成对出现？

因为 AggregatingMergeTree 存的是聚合中间状态（如 sum 的累加器、uniq 的 HLL 结构），而不是最终数值。写入侧用 sumState 存状态，读取侧必须用 sumMerge 把状态合并回数值；混用会得到类型错误或无意义的结果。

如何保证预聚合的结果长期可信？

建立对账机制：定期对同一口径用明细重算，与预聚合结果对比，非零差异即告警（如上面对账 SQL）。同时把可加性约束写进设计文档——哪些指标能上卷、哪些必须保留状态，避免后人误用。

自检

A 店 2 单均价 100，B 店 8 单均价 50，全区平均订单额是 75 吗？

不是。应按订单数加权：总金额 200+400=600，总单数 2+8=10，平均为 60。

第二层 · 参数·命令·量化：刷新策略、粒度与验收参数

物化视图能不能用，取决于三件事：什么时候刷新、以什么粒度预聚合、查询会不会被自动改写。

刷新模式可见性延迟开销适用
ON COMMIT（事务提交即刷）几乎 0写入放大明显小表、要求强一致
ON DEMAND（定时/手动）取决于调度间隔（常见 5～60 分钟）集中在刷新窗口最常用
增量刷新（Fast Refresh）同上但只刷增量低有变更日志 / 支持增量的引擎
全量刷新同上高（重算全表）聚合逻辑跨行、无法增量时

ClickHouse 与 PostgreSQL 的物化视图写法

-- ClickHouse：AggregatingMergeTree + 物化视图（最典型的 Rollup 实现）
CREATE TABLE sales_raw (                  -- 明细表
    shop       String,
    region     String,
    amount     Decimal(18,2),
    qty        UInt64,
    ts         DateTime
) ENGINE = MergeTree ORDER BY (region, shop, ts);

-- 存「聚合状态」而不是最终值，这样才可继续上卷
CREATE MATERIALIZED VIEW sales_by_region
ENGINE = AggregatingMergeTree() ORDER BY (region)
AS SELECT
    region,
    sumState(amount) AS amount_state,     -- State：中间状态
    sumState(qty)    AS qty_state
FROM sales_raw
GROUP BY region;

-- 查询时用 Merge 把状态合并成最终值
SELECT region, sumMerge(amount_state) FROM sales_by_region GROUP BY region;

-- PostgreSQL：全量刷新（会锁表读）
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_name;   -- CONCURRENTLY 不阻塞读，需要唯一索引
关键参数作用常见取值
聚合粒度决定能回答多细的问题必须 <= 最细查询维度，否则无法下钻
-State 函数存中间状态以支持再上卷sumState / uniqState / quantilesState
-Merge 函数把状态合并成最终结果sumMerge / uniqMerge
ORDER BY决定聚合键与合并依据Rollup 的维度顺序：从粗到细
刷新间隔数据新鲜度与成本的权衡5 分钟（实时看板）/ 1 小时（日报）

量化口径：SUM / COUNT / MIN / MAX 可滚动，AVG 和 COUNT(DISTINCT) 不可直接滚动。AVG 必须存 (sum, count) 两个分量，DISTINCT 必须存 HLL / uniqState 这类近似状态。

第三层 · 排障与边界：结果对不上的排查路径

现象原因怎么查 / 怎么办
区域均值 ≠ 各门店均值的平均把 AVG 直接上卷了改成 SUM(sum)/SUM(count)，别对均值再求均值
UV 累加后比真实值大COUNT(DISTINCT) 跨组相加会重复计人改用 uniqState / HLL，或不允许跨维度加总
刷新后数据反而变旧刷新失败但没告警，读到上次结果查刷新任务日志；给物化视图加数据新鲜度监控
查询没走物化视图查询改写条件不满足（维度不匹配、函数不支持）用 EXPLAIN 看是否命中；手工改写 SQL 直查物化视图
刷新时写入抖动全量刷新占用大量 CPU / IO改增量刷新；把刷新窗口挪到低峰
  • 排查顺序：先用明细表跑一遍正确结果 → 再查物化视图 → 对比差异定位是「滚动方式错」还是「刷新没生效」。
  • 边界一：带时间窗口的聚合（如最近 7 天）无法简单上卷——7 天窗口与 1 天窗口之间不存在加法关系。
  • 边界二：维度层级必须显式声明（地区 → 省 → 市），否则引擎不知道该按哪条路径 Rollup。
  • 边界三：刷新是最终一致的：刚写入的明细在刷新前查不到，业务上要能接受这个延迟。
