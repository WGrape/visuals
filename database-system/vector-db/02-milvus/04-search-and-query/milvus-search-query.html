①三种读操作：search、query、hybrid_search

Milvus 的“读”不是一种操作，而是三种：search 按向量相似度取 top-K、query 按标量条件取全量、hybrid_search 对多个向量字段多路召回再融合。它们走的执行路径不同，性能特征也不同。
操作输入输出典型场景
search()查询向量 + limit + 可选 filter按相似度排序的 top-K（含 distance/score）语义检索、以图搜图、RAG 召回
query()纯过滤表达式满足条件的所有实体（不保证顺序）按 ID 批量取、按条件导出、count(*) 计数
hybrid_search()多个向量字段的查询 + rerank 策略融合排序后的 top-K稠密 + 稀疏（BM25）混合、图文跨模态
只有 search/hybrid_search 会用到 ANN 索引；query 完全靠标量索引过滤，没有相似度概念。想“按条件取最新的 10 条”，Milvus 的 query 不保证顺序，需要自己排序或用 search + 过滤。

②一次 search 在做什么

这解释了两个现象：① 每个 QueryNode 都要算出自己的局部 top-K，所以 limit 太小不会影响召回（但 ef/nprobe 会）；② 真正耗时的可能是最后一步回表——如果 output_fields 拉了整段正文，网络与对象存储 IO 会成为瓶颈。

③过滤表达式：把业务条件带进向量检索

# 基础组合
filter = 'tenant == "acme" and publish_ts > 1700000000'

# 集合与数组
filter = 'category in ["tech", "finance"]'
filter = 'array_contains(tags, "milvus")'

# JSON / 动态字段
filter = '$meta["lang"] == "zh"'

# 字符串匹配
filter = 'title like "Milvus%"'

先过滤还是先检索（pre-filter vs post-filter）

老版本是先 ANN 再过滤，条件很严时会“召回不足”——筛完可能只剩几条。新版本支持先算 bitset 再指导 ANN 遍历（迭代式过滤），命中率低的场景明显更好。

过滤字段必须建索引

没建 INVERTED 的过滤条件会退化成逐条比对，向量索引再好也救不了。所有出现在 filter 里的高频字段都该建标量索引。

过滤条件的选择率直接决定性能：千分之一级别的强过滤会让 ANN 索引几乎失效（大半个库都在 mask 外）。这类场景优先考虑按 tenant 建 Partition，或把强过滤字段做成 Partition Key。

④score 方向与阈值：最容易写反的一行代码

metric_type返回字段含义越…越相似阈值判断
L2欧氏距离（≥0）越小score < threshold
IP内积（未归一化时可正可负）越大score > threshold
COSINE余弦相似度（-1~1，归一化向量下 0~1）越大score > threshold
把 COSINE 的分数当成“距离”去做 score < 0.8 的过滤，结果是把最相似的全滤掉。做阈值截断前一定先确认 metric 方向。

另一个常见误解：语义相似度没有绝对阈值。0.82 分在短句匹配里可能很好，在长文档里可能很差。要设阈值，就先在自己的数据分布上看分数直方图，而不是照抄别人的经验值。

⑤分页与 iterator

offset + limit

传统深分页。offset 越大越慢（要算出并丢弃前面所有结果），且 offset + limit 有上限。只适合浅分页（前几页）。

search_iterator / query_iterator

服务端游标式分批返回，不受深分页上限约束，适合全量导出、批量重建索引、离线评估。

# 深分页 / 全量遍历用 iterator，别用 offset
it = client.query_iterator(collection_name="docs",
                           filter='tenant == "acme"',
                           output_fields=["doc_id", "text"],
                           batch_size=1000)
for batch in it:
    handle(batch)

⑥进阶检索形态

Range Search

不取 top-K，而是取相似度落在某个半径内的全部结果（radius + range_filter）。适合去重、聚类、“找出所有足够相似的”。

Grouping Search

按某个标量字段分组，每组只返回最优的一条（group_by_field）。适合“同一文档只出最相关的一个 chunk”。

Hybrid Search

多个向量字段（如 embedding 稠密 + sparse BM25）各自召回，再用 RRFRanker（倒数排名融合）或 WeightedRanker 合并。

Multi-Vector

一个 Collection 可有多个向量字段，各自建独立索引；单次 search 只针对一个字段，多路要走 hybrid_search。

# 稠密 + 稀疏混合检索
req_dense  = AnnSearchRequest([dense_vec],  "embedding", {"metric_type": "COSINE", "params": {"ef": 128}}, limit=50)
req_sparse = AnnSearchRequest([sparse_vec], "sparse",    {"metric_type": "IP"}, limit=50)

res = client.hybrid_search(collection_name="docs",
                           reqs=[req_dense, req_sparse],
                           ranker=RRFRanker(),
                           limit=10,
                           output_fields=["doc_id", "text"])
混合检索的价值不在“更高级”，而在补向量的短板：专有名词、型号、人名这类词 BM25 明显强于 Embedding。通用原理见混合检索。

⑦output_fields 与性能

  • 只取需要的字段：output_fields 里放整篇正文会让网络传输成为瓶颈，尤其是 top-K 较大时。
  • 大字段分开存：正文这类大文本放在关系库/对象存储，Milvus 只存 ID 和必要元数据，检索后回查。
  • 动态字段回表更贵：$meta 是 JSON，反序列化开销高于定长字段，高频字段尽量提升为显式字段。
  • 向量字段默认不返回：除非显式指定，避免把几百维向量传回来。

⑧完整示例：带过滤的语义检索

res = client.search(
    collection_name="docs",
    data=[query_vec],                          # 支持批量：传多条一次查完
    filter='tenant == "acme" and publish_ts > 1700000000',
    limit=10,
    output_fields=["doc_id", "title"],            # 不要拉整篇正文
    search_params={"metric_type": "COSINE", "params": {"ef": 128}},
    consistency_level="Bounded",
    partition_names=["2026_q4"],                  # 可选：分区裁剪
)

for hits in res:
    for h in hits:
        print(h["id"], h["distance"], h["entity"]["title"])
批量查询（data 传多条）比循环单条快得多——它把多次网络往返和多次段扫描合并成一次，是服务端最容易拿到的性能红利。
