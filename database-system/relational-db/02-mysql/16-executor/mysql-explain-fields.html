MySQL EXPLAIN 字段逐项解读

读懂 type / key / rows / Extra，从执行计划判断索引是否生效

MySQL执行计划EXPLAIN索引
怎么看 type 等级 key/rows Extra 信号
EXPLAIN 输出十几列，真正要盯的是 type、key、rows、Extra 四列：它们直接告诉你索引有没有生效、扫了多少行、有没有临时表/文件排序。

01怎么看 EXPLAIN

EXPLAIN SELECT * FROM orders WHERE user_id = 123 AND status = 'PAID';
-- 关注列：id / select_type / table / type / possible_keys / key / key_len / ref / rows / Extra
要点：多表 JOIN 时，从上到下读每一行就是一个「驱动—被驱动」的访问路径；rows 相乘约等于总扫描量。

02type 访问类型（好→差）

type含义
system / const最多一行，主键/唯一索引等值，最快
eq_refJOIN 命中主键/唯一索引，一行对一行
ref非唯一索引等值，如普通索引
range索引范围扫描（BETWEEN / IN / >）
index全索引扫描（比 ALL 好，仅读索引）
ALL全表扫描，需优化
要点：见到 ALL 优先建索引；range/index 可接受，但线上热点查询应尽量争取 ref 及以上。

03key / key_len / rows

列看什么
key实际选中的索引；NULL=没用上索引
key_len用到索引多少字节；可判断复合索引命中前缀
rows优化器估算扫描行数，越小越好
要点：rows 是估算值，实际可能差很多；统计信息过期时跑 `ANALYZE TABLE` 更新后再看。

04Extra 关键信号

Extra含义/行动
Using index覆盖索引，最好，不回表
Using where索引定位后还需回表过滤
Using index conditionICP，索引下推，优于纯 Using where
Using temporary用了临时表（分组/去重未用索引），优化
Using filesort额外排序（ORDER BY 未用索引），优化
要点：Using temporary + Using filesort 同时出现，通常意味着 GROUP BY / ORDER BY 列没走索引，是重点优化对象。

05常见疑问

问：possible_keys 有值但 key 是 NULL？

优化器判断全表比用索引更快（比如绝大部分数据都命中），或统计信息过期；可强制 `FORCE INDEX` 或 ANALYZE 后复评。

问：key_len 比预期小？

说明复合索引只命中了前面若干列（前缀）；把等值过滤列放在复合索引最左。

第一层 · 概念与判定

EXPLAIN 展示优化器选定的执行计划，是 SQL 调优的起点。重点看 type（访问类型）、key（实际用到的索引）、rows（估算扫描行）、Extra（额外操作）。

  • type 梯度（从差到好）：ALL → index → range → ref → eq_ref → const/system。
  • Extra 关键项：Using filesort / Using temporary / Using index（覆盖索引）。
  • 判定：type=ALL（全表扫描）或 Extra 出现 filesort/temporary → 基本要优化。

第二层 · 参数·命令·量化

访问类型与含义：

type含义典型场景
ALL全表扫描无可用索引
range索引范围扫描BETWEEN / IN / >
ref非唯一索引等值普通二级索引
eq_ref唯一索引等值JOIN 主键
const常量（主键等值）WHERE id=1
EXPLAIN SELECT * FROM orders WHERE user_id=10 AND status=1;
-- 看 key 是否命中、key_len 是否用到联合索引全部列、rows 估算是否合理

第三层 · 排障与边界

  • 全表扫描：没建索引或索引失效（函数包裹列、隐式类型转换、前导模糊 LIKE '%x'）。
  • Using filesort：排序无法用索引，临时文件外排；建 (过滤列, 排序列) 联合索引。
  • Using temporary：GROUP BY/DISTINCT 建临时表；减少分组列或加索引。
  • rows 估算偏差大：统计信息过期；ANALYZE TABLE 更新，或调 innodb_stats_sample_pages。

第四层 · 原理与取舍

优化器基于统计信息估算各路径代价（IO+CPU）选最优；统计信息不准或索引选择性差时它会选错计划。覆盖索引（Extra: Using index）可免去回表，是高频优化手段。JOIN 顺序也由优化器基于行估算决定，必要时用 STRAIGHT_JOIN 强制。

key 有值但 rows 仍很大？

可能只用到联合索引前缀，或索引选择性低；看 key_len 判断是否用全索引列。

为什么有时优化器不用我建的索引？

它估算走索引+回表的代价可能高于全表扫描，尤其命中行数比例高时；可 Analyze 或 USE INDEX 提示。
