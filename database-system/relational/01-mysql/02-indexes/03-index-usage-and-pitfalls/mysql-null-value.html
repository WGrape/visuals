①什么是 NULL

先看最根本的一点：NULL 不是一个「值」，而是一种「缺失 / 未知」的状态标记。它既不是数字 0，也不是空字符串 ''，也不是空集合。它代表「这里没有填 / 不知道」。

一句话
NULL = 缺失值 / 未知值（a missing or unknown value）。它和任何东西比较的结果，都不是 TRUE 也不是 FALSE，而是第三态 UNKNOWN。

几个最常被误解的等价判断，务必记牢：

表达式结果说明
NULL = 0NULLNULL 不等于 0
NULL = ''NULLNULL 不等于空字符串
NULL = NULLNULL两个「未知」无法相等，结果仍是未知
NULL <> NULLNULL「不等于」同样未知
10 + NULLNULL任何算术运算遇到 NULL，结果都是 NULL
NULL IS NULLTRUE唯二正确的判断方式之一：IS NULL
NULL IS NOT NULLFALSE另一个是 IS NOT NULL

正因为这点，SQL 用的是三值逻辑（Three-Valued Logic, 3VL）：TRUE / FALSE / UNKNOWN。普通语言里「非真即假」，SQL 里多了一个「不知道」。WHERE 子句只会保留结果为 TRUE 的行，UNKNOWN 会被当作 FALSE 一样过滤掉——这正是后面所有「查询陷阱」的根源。

②InnoDB 在磁盘上怎么存 NULL

这是用户问到的核心点。InnoDB（COMPACT / DYNAMIC 行格式）在每一行记录里放了一个 NULL 位图（NULL bitmap / NULL flags）：表中每个「允许为 NULL」的列，都对应 1 个 bit。N 个可空列就占 CEILING(N/8) 个字节（凑整到整字节）。

  • 某列是 NULL → 该 bit 置 1，并且数据区里不占用任何字节（变长列尤其省空间）。
  • 某列不是 NULL → 该 bit 置 0，数据照常存入。
  • 如果表里所有列都 NOT NULL，整张表根本不需要 NULL 位图，这部分直接省掉。
一个反直觉的细节
对变长列（VARCHAR 等），NULL 确实 0 字节 + 1 bit；但对定长列 CHAR(N)，即使为 NULL，InnoDB 仍会预留整列 N 个字符的宽度。这样做是为了让「把 NULL 原地改成有值」时不用挪动页内数据、不产生碎片。所以「NULL 一定不占空间」只对变长列成立，定长 CHAR 例外。

示例：id=1, name=NULL, age=20。name 是可空列，其 NULL 位被置 1，数据区里 name 的位置什么都没存；age 有值，照常占 4 字节（INT）。

关键点：NULL 位图是行级结构，所有索引记录都带它——包括二级索引。所以在二级索引的 B+Tree 记录里，NULL 同样用 1 个 bit 标记，变长列数据仍不占字节。这决定了「索引里也存 NULL、且能按 NULL 定位」。

③三值逻辑：为什么任何比较都是「未知」

把 NULL 看作「未知」。当你问「未知的值 等于 5 吗？」——答案是「不知道」，而不是「是」或「否」。只要参与比较的任意一边是 NULL，结果就是 UNKNOWN，与用 =、!=、<、> 哪个运算符无关。

最致命的一条
NULL = NULL 的结果是 UNKNOWN，不是 TRUE！所以你永远不能写 WHERE col = NULL 去找空值——它一行都捞不到。必须写 WHERE col IS NULL，IS NULL 是专门检测「NULL 标记」的谓词，不走普通比较逻辑。

④WHERE 里的常见陷阱（及为什么）

基于三值逻辑，下面这些写法会「悄悄」给出错误答案。用上面的 5 行示例表演示（age 列：12 / 32 / 22 / NULL / 12）：

idage

陷阱 1：col = NULL

返回 0 行。= 是普通比较，age = NULL 对每一行都是 UNKNOWN → 全被 WHERE 过滤。正确写法：col IS NULL。

陷阱 2：col != 'x'

会悄悄丢掉所有 NULL 行。NULL != 'x' 是 UNKNOWN，不被保留。结果只含「非 NULL 且不等于 x」的行。

陷阱 3：col NOT IN (a, b, NULL)

整个条件恒为 UNKNOWN → 0 行。因为等价于 col!=a AND col!=b AND col!=NULL，最后一个是 UNKNOWN，AND 链整体 UNKNOWN。

陷阱 4：col IN (NULL)

同样 0 行。col IN (NULL) ≡ col = NULL → UNKNOWN。想匹配 NULL 用 col IS NULL。

正确姿势
要把 NULL 当成一个明确的「状态」来比对，就：
  • 找空值：WHERE col IS NULL
  • 找非空：WHERE col IS NOT NULL
  • 要参与运算/比较：先用 COALESCE(col, 默认值) 或 IFNULL(col, 默认值) 把 NULL 转成具体值，再比。
⑤NULL 在 B+Tree 索引里怎么排？索引还能用吗？

好消息：标准 B+Tree 索引是存 NULL 的，而且 InnoDB 把 NULL 当作最小值来排序。于是：

  • ORDER BY col ASC：NULL 排在最前面（索引最左端）。
  • ORDER BY col DESC：NULL 排在最后面。
  • WHERE col IS NULL：能命中索引（ref 访问），因为 NULL 在 B+Tree 里就是一个可定位的区间。
  • WHERE col = NULL：不能用索引，而且本来就返回 0 行（见 ④）。
跨引擎大坑
MySQL / SQL Server 把 NULL 当最小值（ASC 在前）；PostgreSQL / Oracle 把 NULL 当最大值（ASC 在后）。同一句 ORDER BY age ASC，换数据库 NULL 的位置会反过来！需要确定性排序时，显式写 ORDER BY age IS NULL, age（把 NULL 永远推到末尾），或用 8.0.16+ 的 ORDER BY age ASC NULLS LAST。

⑥NULL 与索引失效：先破除一个流传很广的误区

先给结论，免得越看越晕：在 MySQL / InnoDB 里，「列上有 NULL 就会让索引失效」是一个误解。InnoDB 的 B+Tree 索引确实存 NULL，而且 col IS NULL、col IS NOT NULL 都能走索引（EXPLAIN 里是 ref / range 访问，key 列能看到用上了索引）。

那为什么到处都在传「NULL 导致索引失效」？
因为它把几件不同的事混在一起了：有人写错语法（= NULL）、有人给列套了函数（IFNULL(col,0)）、有人被 != 悄悄丢掉 NULL 行吓到。下面把真正会让查询用不上索引的几种情形拆开讲，并解释原因。

真坑 1：把 = 当成「找空值」——不仅 0 行，还不走索引

WHERE col = NULL 用的是普通比较运算符，对每一行都是 UNKNOWN → 优化器判它「恒假」，既不返回行，也不会去用索引。正确写法是 col IS NULL，它是专门的 NULL 标记判断，InnoDB 能在 B+Tree 里直接定位到 NULL 所在区间，命中索引。

❌ 失效：col = NULL

type: ALL / 恒假 key: NULL（没用索引） rows: 0（一行都返回不了）

✅ 命中：col IS NULL

type: ref key: idx_col rows: 仅 NULL 行（如 3 行）

真坑 2：给列套函数来处理 NULL（最隐蔽、最致命）

这是实战里最容易被踩的：为了「把 NULL 当 0 / 空串一起比」，写出 WHERE IFNULL(col, 0) = 0、WHERE COALESCE(col, '') = 'x'、WHERE ISNULL(col)。问题在于——索引建在 col 上，但你查询的却是 函数(col)。B+Tree 只按 col 的原值有序排列，根本没法用「函数算出来的结果」去定位，于是退化成全表扫描（type: ALL）。

这其实是「对列使用函数导致索引失效」的经典案例，只是它常披着「处理 NULL」的外衣出现。修复办法是把函数展开成索引友好的写法：

❌ 失效：IFNULL(col,0) = 0

type: ALL key: NULL rows: 全表（逐行算 IFNULL）

对列套了函数，索引用不上。

✅ 命中：col IS NULL OR col = 0

type: index_merge / ref key: idx_col rows: NULL 行 + 0 值行

两个分支都直接比列原值，都能用索引。

真坑 3：col != 'x' 不等于「等于非 x 的全部」

!= 技术上能走索引（range），但它会悄悄丢掉所有 NULL 行——因为 NULL != 'x' 是 UNKNOWN，不被保留。结果集少了一块，常被误以为「索引没生效 / 数据丢了」。想要「非 x 的全部含 NULL」，得显式补上：col != 'x' OR col IS NULL。

为什么会这样？一句话的底层原因
B+Tree 索引按「列的原值」有序存储，NULL 被当作一个最小值放进去。只要 WHERE 条件能直接拿「列原值 vs 常数」做比较（IS NULL、=、>、BETWEEN），索引就能用；一旦你对列做了运算或套了函数（IFNULL(col,0)、col + 1、DATE(col)），索引里的有序值和你查的值对不上，MySQL 只能全表扫。= 与 IS NULL 的区别同理：普通比较遇 NULL 得 UNKNOWN，优化器无法据此在索引上定位；IS NULL 是专门的标记判断，能直接在 B+Tree 里定位 NULL 区间。

交互：哪种写法会让索引失效？

点不同查询，看它是否命中索引以及为什么。重点对比 col = NULL 与 col IS NULL、IFNULL(col,0)=0 与 col IS NULL OR col=0。

⑦唯一索引：为什么能塞进多个 NULL

这是面试高频题。InnoDB 的唯一索引（UNIQUE）允许存在多个 NULL 值，不会报唯一冲突。原因同样是三值逻辑：唯一性检查在比较两行时，若某列是 NULL，NULL 与 NULL 不视为相等，于是「多个 NULL」互不相等、不违反唯一约束。

CREATE TABLE users (
  id INT PRIMARY KEY,
  email VARCHAR(255),
  UNIQUE (email)
);
INSERT INTO users VALUES (1, NULL), (2, NULL);  -- ✅ 成功，两行 email 都是 NULL
INSERT INTO users VALUES (3, 'a@b.com'), (4, 'a@b.com');  -- ❌ 报错：非 NULL 重复
业务陷阱
如果你的本意是「email 不能重复，包括不能重复留空」，那 UNIQUE(email) 会放行无数个空 email，数据完整性就破了。治本方案：列设为 NOT NULL + 合理默认值（如空字符串 ''），让 NULL 彻底退出业务域；MySQL 8.0 也可用函数索引 CREATE UNIQUE INDEX ... ((COALESCE(email,''))) 把 NULL 归一化后再约束。
⑧聚合函数怎么对待 NULL

聚合函数大多会忽略 NULL，只有 COUNT(*) 会把 NULL 行算进去。用同一张 5 行表（age: 12/32/22/NULL/12）：

表达式结果行为
COUNT(*)5数所有行，包括 NULL 行
COUNT(age)4只数 age 非 NULL 的行
SUM(age)78忽略 NULL，12+32+22+12
AVG(age)19.5= SUM/非NULL个数 = 78/4
MAX(age) / MIN(age)32 / 12忽略 NULL 后取极值
GROUP BY age4 组所有 NULL 归到同一个分组
COUNT(DISTINCT age)312/22/32 三种，NULL 不计入
为什么 AVG 会「偏小」
AVG(col) 的分母是「非 NULL 的行数」，分子也不含 NULL。如果大量行是 NULL，AVG 只统计了有值的那部分——这往往不是你想要的「平均值」。需要把 NULL 当 0 计入时，用 AVG(COALESCE(age,0))。

设计层面的建议
能 NOT NULL 就尽量 NOT NULL：省掉 NULL 位图、比较更简单、索引更紧凑、优化器统计更准。只有当「缺失」本身是有业务含义的信息（如「尚未填写」区别于「填了空字符串」）时，才用 NULL，并且所有查询都显式用 IS NULL / COALESCE 处理它。
