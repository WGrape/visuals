01两种向量：PromQL 的第一道门槛

区间向量是中间形态：它的唯一用途就是喂给 rate/increase/xxx_over_time 这类函数。
一句话区分：瞬时向量可以直接看、可以画图、可以聚合；区间向量是「喂给函数的原料」，本身不能直接用。所有 [5m] 这种方括号语法产生的都是区间向量，必须立刻套上 rate() / increase() / avg_over_time() / max_over_time() 等函数。

02选择器：先筛时间线，再算

# 精确匹配
http_requests_total{job="api", status!="200"}

# 正则匹配（完全锚定，不是子串）
http_requests_total{path=~"/api/.*", method=~"GET|POST"}

# 整体排除
http_requests_total{environment!~"test|dev"}
运算符含义注意
=相等—
!=不等—
=~正则匹配完全锚定：a=~"b" 等价于 a="b"，不是包含关系
!~正则不匹配同上
正则选择器在每次查询时对候选时间线逐一匹配，代价随基数线性增长。能用精确匹配就用精确匹配，复杂筛选优先用 recording rule 预计算。

03rate / increase / irate：计数器的三把刀

rate 窗口长度决定了曲线的平滑程度与响应速度，是 PromQL 调优的第一旋钮。
函数语义适用场景禁忌
rate(x[5m])每秒平均增长率，窗口内做外推修正仪表盘、告警的默认选择不要用在 Gauge 上
increase(x[5m])窗口内的总增量（等价于 rate × 窗口秒数）「过去 5 分钟有多少请求」这类计数问题同上
irate(x[5m])只用最后两个样本算瞬时速率需要最快反应速度的细粒度看图不要用于告警：太敏感，会疯狂抖动
avg_over_time(g[5m])窗口内平均值Gauge 类的平滑（内存、连接数）不要用在 Counter 上
最常见的误用：对 Gauge 用 rate()。对内存占用量求 rate 得到的是「内存增长速率」，几乎没人想要这个值；直接看 Gauge 原值或用 avg_over_time() 平滑才是正解。反过来，对 Counter 直接看原值也毫无意义——那只是一直上涨的总数。

04聚合：by 与 without 的方向不要搞反

# 按 job 汇总（保留 job，丢掉其他 label）
sum by (job) (rate(http_requests_total[5m]))

# 等价于：丢掉除 job 之外的所有维度
sum without (instance, method, status) (rate(http_requests_total[5m]))

# 常见组合
avg by (instance) (node_load1)                       # 每台机器的平均负载
max by (route) (histogram_quantile(...))             # 每条路由最慢的实例
count by (job) (up == 0)                             # 每个 job 挂了几个实例
topk(5, sum by (route) (rate(http_requests_total[5m])))  # 流量 Top5 路由
先 rate 再 sum，顺序不能反。sum(rate(...)) 是先对每条时间线各自算速率再相加；如果写成 rate(sum(...))，会先把不同实例的计数器加总（其中某个实例重启归零会被淹没），再算速率——得到的数字会明显偏低且无法修正重置。

05运算与向量匹配

标量与向量

node_memory_used_bytes / node_memory_total_bytes * 100   # 向量÷向量（自动按 label 对齐）
node_cpu_seconds_total * 1000                              # 向量×标量

向量与向量：必须说清怎么配对

# 一对一：按相同 label 集合配对
rate(http_requests_total[5m]) / rate(http_requests_duration_seconds_sum[5m])

# 多对一（group_left）：用信息量更多的那侧补充 label
method_code:http_errors:rate5m{job="api"}
  / ignoring(code) group_left
method:http_requests:rate5m{job="api"}
两个向量做二元运算时，Prometheus 要求它们标签集合能一对一对上。一侧维度更多、一侧更少时（比如分子有 code 分母没有），必须显式写 ignoring(...) 或 on(...)，否则查询直接报错。这是 PromQL 报错信息里最让人困惑的一类。

向量的四种类型与匹配规则

PromQL 的难点不在函数，而在向量类型和向量匹配。搞清楚 instant/range/scalar 以及 on/ignoring/group_left，大部分查询就能写对。

PromQL 实战

# ---------- 基础 ----------
up                                          # 抓取是否正常（1=正常）
up{job="api"}                               # 标签精确匹配
up{job=~"api|web"}                          # 正则匹配
up{job!="api", instance=~".*:9100"}         # 不等于 + 正则

# ---------- 速率（Counter 必配）----------
rate(http_requests_total[5m])                        # 每秒速率
increase(http_requests_total[1h])                    # 窗口内增量
irate(http_requests_total[5m])                       # 瞬时速率（只看最后两点）
delta(cpu_temp[2h])                                  # Gauge 的变化量

# ---------- 聚合 ----------
sum by (job) (rate(http_requests_total[5m]))
avg without (instance) (node_cpu_seconds_total)
topk(5, rate(http_requests_total[5m]))               # TOP 5
count(up == 1)                                        # 存活实例数

# ---------- 分位数（关键写法）----------
histogram_quantile(0.99,
  sum by (le) (rate(http_request_duration_seconds_bucket[5m])))

# ---------- 预测与趋势 ----------
predict_linear(node_filesystem_free_bytes[6h], 4*3600)   # 预测4小时后
deriv(node_filesystem_free_bytes[1h])                     # 每秒变化斜率

# ---------- 常用告警表达式 ----------
up == 0                                                    # 实例挂了
rate(http_requests_total{status=~"5.."}[5m]) > 0.05       # 错误率>5%
node_filesystem_avail_bytes / node_filesystem_size_bytes < 0.1   # 磁盘<10%
changes(up[10m]) > 2                                       # 10分钟内抖动>2次
  • 先 rate 再聚合：sum(rate(x[5m])) 是唯一正确顺序，反过来会报「range vector 不能直接聚合」。
  • 标签不匹配就没结果：两个向量做算术时标签集合必须一致（或用 on/ignoring）。查不出结果时先看是不是标签没配上。
  • 多对一要用 group_left：比如「每个 handler 的 QPS」除以「该实例的总 QPS」，右边只有一条，需要 on(instance) group_left。
  • absent() 是告警利器：指标不存在时 up == 0 也查不出来（因为 series 都没了），要用 absent(up{job=...})。这是「监控失效」场景的必备写法。
  • 查询慢先看 range 和基数：长 range（如 [7d]）+ 高基数 label 会让 PromQL 极慢甚至 OOM。大窗口查询放 recording rule 预计算。
  • irate 只用于看图：它只看最后两个样本，抖动极大。告警用 rate，排查尖峰用 irate。
为什么两个向量相除查不出结果？

因为 PromQL 的向量运算是按标签匹配的，标签对不上就得不到结果（不是报错，是静默地返回空）。比如 a 有标签 {job, instance, code}，b 只有 {job, instance}，直接 a / b 是无结果的。三种解法：① on(job, instance)——只按这些标签匹配，其他标签忽略；② ignoring(code)——排除这些标签后匹配剩下的；③ 如果是多对一（左边多条、右边一条，比如用每个 handler 的量除以该实例总量），必须加 group_left（或 group_right），否则同样无结果。排查技巧：先分别查两个向量，对比它们的标签集合，看差在哪，再决定用 on 还是 ignoring。这是 PromQL 最高频的问题，没有之一。

instant vector 和 range vector 到底怎么区分？

看有没有方括号：http_requests_total 是 instant vector（某一时刻每个时间序列各一个值）；http_requests_total[5m] 是 range vector（过去 5 分钟内每个时间序列的多个值）。关键的约束是：图表和大部分运算只接受 instant vector，而 rate/increase/delta/irate 这类「需要看一段时间」的函数只接受 range vector。所以你不能直接把 up[5m] 丢给图表（会报错），也不能对 up 直接用 rate（没有时间范围就没法算速率）。理解这一点后，PromQL 的写法就很自然了：先用 range vector 喂给 rate 类函数得到 instant vector，再对这个 instant vector 做聚合和运算——这就是 sum(rate(x[5m])) 这个最常见写法的由来。

怎么判断一个 PromQL 查询会不会很慢？

三个维度看成本：① 选中的 series 数——标签选择器越宽泛，命中的 series 越多，成本线性上升。{__name__=~'.+'} 这种全量匹配是灾难；② range 的长度——[5m] 和 [7d] 的样本量差 2000 倍，长窗口会把大量样本加载进内存；③ 聚合的维度数——by 的标签组合越多，产生的分组越多。经验判据：单次查询处理的样本数超过千万级（约几十秒到几分钟）就会明显变慢，超过亿级基本会 OOM。优化手段：① 用 recording rule 预计算（最有效，把分钟级查询变成秒级）；② 缩短 range；③ 加更严格的标签过滤；④ 给 --query.timeout 设上限（默认 2 分钟），避免慢查询拖垮整个实例；⑤ 对超大数据量，考虑用 Thanos Query 或 VictoriaMetrics（后者在大数据量查询上内存效率明显更好）。
