01选型前先画像：别拿参数表做决策

OLAP 选型最常见的失败，是把「引擎能力对比表」当成决策依据。能力表只能排除，不能选择——因为决定体验的是你的负载落在哪个区域，而不是引擎的全集能力。

Q：为什么"某某引擎支持 X 功能"不足以决策？
A：因为"支持"有实现质量差异。同样支持物化视图，一个能自动匹配改写、一个只能手动指定；同样支持 JOIN，一个走 Broadcast 秒回、一个走 Shuffle 跑五分钟。功能的存在性和它在你的数据规模下的表现，是两件事。
正确顺序是：先量化负载 → 再定候选 → 最后用你自己的查询实测。能力表只用在第一步之后做剪枝。

02负载画像的五个维度

维度要回答的问题为什么决定选型
数据新鲜度能接受多久的延迟？秒 / 分钟 / 小时 / 天决定要不要实时导入链路（Routine Load、Flink 写入）
查询形态单表聚合为主，还是多表大 JOIN？是否固定报表？决定是否必须 Colocate / Runtime Filter / 强 JOIN 能力
并发量同时跑多少查询？峰值 QPS 多少？列存引擎天然不适合高并发，需要预聚合或缓存
数据规模与增长当前多少 TB？月增长多少？保留多久？决定分区策略、冷热分层与存储成本
查询灵活性是固定看板，还是分析师临时探索？固定看板可预聚合；临时查询要求引擎足够通用
把这五个维度写下来，候选范围通常会从"五六个引擎"收敛到"一两个"。这比跑任何 benchmark 都省时间。

03标准基准集各自测什么

基准测什么适用局限
SSB（Star Schema Benchmark）星型模型下的单表/简单多表聚合看基础扫描与聚合能力，最快跑完JOIN 太简单，区分度低
TPC-H8 张表、22 条复杂分析查询事实上的入门标准，覆盖 JOIN / 子查询 / 聚合数据分布均匀，不含倾斜与更新
TPC-DS24 张表、99 条查询，含复杂多维与交互式最贴近真实数仓，区分度高跑起来重，且需要正确实现全部查询
业务自有查询集你真正的慢查询最有决策价值需要自己整理与脱敏
标准集的正确用法：用它做初筛和回归，不要用它做最终决策。最终决策必须用业务查询集——因为你的数据分布、倾斜程度、表结构长什么样，标准集完全不知道。

04怎么测才可信：六条硬规矩

① 用真实规模的数据。1 GB 数据上所有引擎都很快，差异被缓存与启动开销掩盖。至少用生产量级的十分之一。
② 每类查询跑多次，取中位数和 P99。第一次必然包含编译、缓存预热、连接建立，只看单次结果毫无意义。
③ 明确是否清空缓存。冷查询（清缓存）与热查询（缓存命中）代表两种场景，分开测、分开报。
④ 并发要测。单并发下的排名在高并发时经常反转——这正是列存引擎最脆弱的地方。
⑤ 同时导入。真实系统查询和写入是并发的，只读不写的测试会严重高估性能。
⑥ 记录配置。机器规格、副本数、分区分桶、压缩方式、会话参数，全部记下来，否则结果无法复现。
厂商公布的 benchmark 只能当参考。它们通常在最优配置、单一查询、无并发下取得。不是造假，但和你的场景差得很远。

05怎么读测试结果

现象可能的含义下一步
单并发快，并发一上去就崩每查询吃满资源，无资源隔离加资源组/队列，或做预聚合
冷查询慢、热查询极快缓存命中率高，依赖页缓存评估内存是否扛得住工作集
某几条查询特别慢通常是 JOIN 策略或数据倾斜看执行计划，检查分桶键与倾斜
导入时查询抖动剧烈compaction / 资源争抢错峰导入，限制导入资源
P99 远高于中位数存在长尾（大分区、倾斜、重试）按查询类型分桶，定位长尾来源
中位数决定"平均体验"，P99 决定"会不会被投诉"。选型报告里两个都必须有。

06六个常见陷阱

Q：测完发现引擎 A 全面优于引擎 B？
A：先怀疑测试。很可能是 B 的分桶键没设好、统计信息没收集、或用了默认配置。引擎间的差距通常没那么大，配置差距才是数量级的。
Q：能不能只测导入速度？
A：不能。导入是批处理可以错峰，查询延迟直接影响用户。导入慢可以用时间换，查询慢没法换。
Q：小数据量测试能不能外推？
A：不能。数据规模跨过内存容量、跨过分区数阈值后，瓶颈会整体切换（从 CPU 变为 IO，从扫描变为 shuffle）。
Q：同一份 SQL 在不同引擎上跑，结果对得上吗？
A：要验。窗口函数的 NULL 处理、去重语义、时区与精度都可能不同。性能对比的前提是结果一致。
Q：需不需要测故障恢复？
A：需要但常被跳过。至少测一次节点宕机时的查询失败率与恢复时间——副本配置不同，表现差别很大。
Q：测一次定终身？
A：负载会变。建议把基准查询集固化成回归测试，版本升级与数据量翻倍时各跑一次。

三大标准基准：分别测什么

基准查询数模型测什么适用
TPC-H22 个雪花模型（8 张表）即席分析查询最常用，入门必测
TPC-DS99 个星型+雪花（24 张表）含复杂子查询、窗口函数更贴近真实数仓
SSB（星型基准）13 个纯星型（1 事实 + 4 维）多表 JOIN + 聚合测试列存的 JOIN 性能
ClickBench43 个单大宽表（1 亿行）单表扫描/聚合/过滤ClickHouse 主导，测扫描性能

怎么选：TPC-H 是最通用的基线（所有产品都会公布）；TPC-DS 更贴近真实数仓（有复杂的多层子查询）；ClickBench 专测单表扫描能力（这是列存最擅长的）。但最重要的始终是你自己的真实 query——标准基准只能做初筛。

TPC-H 数据生成与测试

# 生成 TPC-H 数据（官方工具 dbgen）
git clone https://github.com/electrum/tpch-dbgen
cd tpch-dbgen && make
./dbgen -s 100          # -s 就是 scale factor，生成约 100GB
# 产出：lineitem.tbl, orders.tbl, customer.tbl ... 共 8 个文件

# 导入 ClickHouse
CREATE TABLE lineitem (
  l_orderkey    Int64, l_partkey Int32, l_suppkey Int32,
  l_linenumber  Int32, l_quantity Decimal(15,2),
  l_extendedprice Decimal(15,2), l_discount Decimal(15,2),
  l_tax Decimal(15,2), l_returnflag String, l_linestatus String,
  l_shipdate Date, l_commitdate Date, l_receiptdate Date,
  l_shipinstruct String, l_shipmode String, l_comment String
) ENGINE = MergeTree ORDER BY (l_shipdate, l_orderkey);

cat lineitem.tbl | clickhouse-client --query \
  "INSERT INTO lineitem FORMAT CSV" --format_csv_delimiter='|'

# 跑 Q1（典型的聚合查询）
SELECT l_returnflag, l_linestatus,
       sum(l_quantity), sum(l_extendedprice)
FROM lineitem
WHERE l_shipdate <= '1998-09-02'
GROUP BY l_returnflag, l_linestatus;

# 计时（注意要跑 3 次取后 2 次，第一次含冷缓存）
for i in 1 2 3; do
  /usr/bin/time -f "%e s" clickhouse-client --query "$(cat q1.sql)"
done

测量的三个纪律：① 跑 3 次取后 2 次（第一次含冷缓存和 JIT 预热）；② 关掉客户端的输出（> /dev/null），否则测的是打印速度；③ 记录并发数——单并发和 32 并发的结果可以差 10 倍。

实测指标怎么读（横向对比的方法）

指标含义好产品的量级注意
单表扫描速度每秒扫多少行10 亿 – 100 亿行/s（列存）看是否用了压缩/向量化
聚合吞吐GROUP BY 的速率亿级行/s基数影响极大
JOIN 性能大表 JOIN 耗时SF=100 下秒级内存消耗是关键
压缩率原始/压缩后3 – 10 倍列存 + 字典编码
导入速度每秒导入行数百万 – 千万行/s影响数据新鲜度
内存占用峰值内存取决于并发OLAP 最常见的失败原因

对比时的三个陷阱：① 硬件不一致——不同机器/磁盘（NVMe vs HDD）结果差数倍；② 索引/分区不同——有的产品建了物化视图或投影（如 ClickHouse 的 ORDER BY 就是稀疏索引），没建的自然慢；③ 并发度不同——单并发 vs 高并发结论可能反转。最可靠的做法：用你自己的数据和查询，在相同硬件上测。

Workload 分类：先搞清楚你是哪一类

类型特征查询模式适合的产品
Ad-hoc 即席分析分析师随便查，无固定模式大范围扫描 + 聚合ClickHouse / Doris（扫描快）
固定报表几十个固定 SQL 每天跑可预计算加物化视图/预聚合
高并发点查QPS 高、每次查少量按主键/索引查Doris/StarRocks（有索引）或 ES
实时写入 + 实时查秒级可见写入吞吐高Doris/StarRocks（支持实时导入）
湖仓分析数据在数据湖（Parquet/Iceberg）外表查询Trino / StarRocks 外表
  • 先分类再选型——把 workload 归到上面某一类，选型范围立刻缩小一半
  • 混合负载要拆开：高并发点查和大范围扫描不要放同一集群（资源互相抢）
  • 看写入模式：批量导入（推荐）vs 实时流式写入（对产品要求高很多）
  • 估算数据生命周期：只查最近 7 天 → 可以只保留热数据在 OLAP，冷数据留数据湖

深入自检

为什么我的 TPC-H 测试结果和官方差很多？

五个常见原因：① 硬件不同（尤其磁盘：SATA SSD vs NVMe 差 3 – 5 倍）；② 没建合适的 ORDER BY / 分区——ClickHouse 的 MergeTree 依赖 ORDER BY 做稀疏索引，建错了等于全表扫；③ 配置没调（如 max_threads、内存限制）；④ 数据是冷缓存——第一次查询要读盘；⑤ 官方用的是优化过的 schema 和参数（有时还包括物化视图）。建议：先在相同硬件上跑两个产品对比，绝对值不重要，相对差距才可信。

列存为什么快？核心原理是什么？

三个叠加效应：① 只读需要的列——查 3 列就不用读 50 列，IO 减少 10 倍以上；② 压缩率高——同列数据类型相同、重复度高，字典编码 + RLE + 位压缩能压到 1/3 – 1/10，进一步减少 IO；③ 向量化执行——一次处理一批（如 1024 个值）而非一行，充分利用 CPU 的 SIMD 指令和缓存。代价：单行写入慢（要拆列、压缩），所以 OLAP 库不适合高频单行写入。

什么时候 OLAP 库不该用？

四种情况：① 需要事务和行级更新（OLAP 库的 UPDATE 通常很弱或是异步合并）；② 高并发点查（每次按主键查一行——这是 OLTP 或 KV 存储的活，用 Redis/MySQL 更合适）；③ 数据量小（< 100 GB 且查询简单——PostgreSQL 甚至 DuckDB 就够了，引入 OLAP 库是过度设计）；④ 需要复杂的多表事务一致性。判断口诀：大批量扫描聚合 → OLAP；单条精确查询 → OLTP/KV。

怎么评估迁移到新 OLAP 库的成本？

五项成本：① SQL 方言改造——窗口函数、JSON 函数、日期函数的语法差异（通常要改 20 – 40% 的 SQL）；② 数据迁移——导出导入的时间和数据校验；③ 应用改造——驱动、连接池、错误处理；④ 运维学习——新产品的调优、监控、故障处理；⑤ 双跑期——通常要并行运行 1 – 3 个月做结果比对。经验数字：中型系统（几十个报表）的迁移通常要 2 – 6 人月，SQL 改造是大头。建议先迁一部分非核心报表验证。
