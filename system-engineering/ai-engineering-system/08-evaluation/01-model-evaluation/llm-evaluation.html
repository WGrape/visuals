Evaluation · 面试核心

大模型评估体系

「模型好不好」不能一句带过。面试常要求你设计评估方案：用什么指标、怎么避免自吹自擂、RAG/对话/Agent 各怎么评。本文给出通用评估框架（RAG 专项见 rag/rag-evaluation）。

01评估看什么：三维

① 能力

知识、推理、代码、数学、长上下文、多模态等「硬实力」。

② 对齐

有用、诚实、无害（3H），以及指令遵循、格式合规。

③ 工程

延迟(TPOT/TTFT)、吞吐、成本、稳定性、可复现。

关键点：不同应用侧重不同。客服机器人重「对齐+工程」，科研助手重「能力+长上下文」。评估方案要贴合场景。

02能力基准（Benchmark）

通用知识

MMLU（57 学科多选）、C-Eval / CMMLU（中文）、BBH（复杂推理）。

数学/推理

GSM8K（小学应用题）、MATH、GPQA（研究生级）。

代码

HumanEval、MBPP（函数级）；LiveCodeBench（防污染）。

长上下文

Needle-In-A-Haystack（大海捞针）、多文档 QA。

「刷榜」陷阱：很多基准已被训练数据污染，分数高≠真实能力强。面试要能指出这点，并强调用 held-out / 在线数据。

这里列出应用选型时常用的基准。各基准的测量目标、推理专项题型与分数解读见大模型评测与基准和推理能力评测基准。

03LLM-as-Judge

开放式生成无法用精确匹配，于是用更强的 LLM（如 GPT-4）当裁判，按维度（有用性、相关性、安全性）打分或 pairwise 比较。

  • 优点：接近人类语义判断、可规模化、成本低。
  • 缺点：裁判自身有偏见（位置偏见、长答案偏好、自我偏好）；需校准、需人工抽检一致性。
  • 改进：多裁判投票、成对比较代替绝对打分、用 rubric 约束。

04人工评估

对安全性、风格、复杂指令遵循等「机器难判」的维度，仍需人工标注（标注员按 rubric 给分或 pairwise 胜出）。它是金标准，但慢且贵，常用于终验与法官模型校准。

05工程指标

TTFT / TPOT

首 token、每 token 延迟（见 deploy 目录）。

Throughput

token/s、请求/s，决定并发容量。

成本

每千 token 费用、每请求 GPU 时。

06常见陷阱

数据污染

测试集泄露进训练，分数虚高。

指标错配

用 BLEU 评开放生成，意义有限。

裁判自偏

用自家模型当裁判易高分。

只看均值

长尾失败（幻觉/越狱）更致命。

07面试速记卡

三维

能力 + 对齐 + 工程，按场景取舍权重。

基准

MMLU/GSM8K/HumanEval/Needle 等，警惕污染。

LLM-as-Judge

可规模化但有偏见，需校准+人工抽检。

RAG 评估

检索/生成分层指标见 rag/rag-evaluation。

LLM-as-judge用强模型打分三种偏差：位置偏差（偏爱先出现的）、冗长偏差（偏爱长答案）、自我偏好（偏爱自己家的输出）
Exact Match / F1字符串或 token 级匹配对格式极敏感，必须先做规范化（大小写、空格、标点）

LLM-as-judge 的最小缓解动作：① 两个候选正反顺序各评一次，不一致就算平局；② 打分时给参考锚点答案；③ 明确要求「不因长度加分」。这三步几乎零成本。

自建评测流水线（可直接改）

评测 + 置信区间 + 样本量

import json, random, re

def normalize(s):
    """答案规范化：不做这一步，EM 会被大小写/空格/标点毁掉。"""
    s = s.strip().lower()
    s = re.sub(r"[\s]+", " ", s)
    s = re.sub(r"[.,;:!?'"]+$", "", s)
    return s

def evaluate(items, generate, n_boot=1000):
    hits = [1 if normalize(generate(q)) == normalize(g) else 0
            for q, g in items]
    acc = sum(hits) / len(hits)
    # bootstrap 置信区间：永远报区间，不要只报一个点
    n = len(hits); boots = []
    for _ in range(n_boot):
        sample = [hits[random.randrange(n)] for _ in range(n)]
        boots.append(sum(sample) / n)
    boots.sort()
    lo, hi = boots[int(0.025 * n_boot)], boots[int(0.975 * n_boot)]
    return {"acc": round(acc, 4), "ci95": [round(lo, 4), round(hi, 4)], "n": n}

# 样本量估算（比例估计）：n ≈ (1.96^2 · p(1-p)) / d^2
#   p=0.5, 允许误差 d=0.03  ->  n ≈ 1067
#   p=0.5, 允许误差 d=0.05  ->  n ≈  385
#   p=0.5, 允许误差 d=0.10  ->  n ≈   97
# 所以「200 条样本上高 3 个点」基本不值得写进结论。

# 固定性清单（复现实验的底线）
#   temperature=0（或固定 seed）
#   固定 prompt 模板与版本号，把模板存进结果文件
#   记录 model 版本、采样参数、token 用量与耗时

经验：自评分数和线上体验脱节，八成是因为评测集的分布和线上请求分布不一致，而不是模型不行。先拿线上真实请求的抽样做评测集，再谈分数。

排障清单与自检

  • 污染检查：用 n-gram 重合或检索比对，确认评测题没有出现在训练语料里；公开基准尤其要查。
  • 解析失败率单独统计：答案解析不出来时，是算错还是算对？很多榜单差异来自解析器。
  • 拒答率单独统计：「我不确定」被判错会掩盖真实能力，也会掩盖安全策略的变化。
  • 成本与延迟一起报：只报准确率的评测没有决策价值。
  • 线上 A/B 优先：离线基准只能做回归护栏，真正的取舍靠线上指标。
为什么自测分数很高但线上效果差？

三个高频原因：评测集分布偏、提示词模板与线上不一致、线上有检索/工具/多轮等评测里没覆盖的环节。

多少样本才够？

按允许误差反推：±3% 约需 1000 条，±5% 约需 385 条。100 条以内的结论只配当定性观察。

能不能只用 LLM 打分？

可以，但要满足三点：与人类标注做过一致性检验（常报 Spearman/Kendall 相关或一致率）、做双向顺序评测、并且对可程序化验证的任务（如 IFEval、代码）尽量改用规则判分。

评估不是打分，是一条闭环流水线

很多人以为评估就是「跑个榜单看分数」，但真正有用的评估是一条能反复跑的流水线：先把需求变成可判分的题目，再让模型产出，再用稳定的判分器打分，最后把错误归类回需求。缺了任何一环，分数都只是一串无法指导行动的数字。

评估闭环：分数只是中间产物，可执行的改进结论才是终点
离线评估用固定数据集跑分，快、可复现，适合回归与选模型
在线评估看真实流量的满意率与留存，慢但真，适合最终裁决
能力评估回答「模型会不会」，靠 Benchmark 与自建集
工程评估回答「线上能不能用」，靠延迟、成本、失败率

主流 Benchmark 横向对比：各自在测什么

榜单分数的意义完全取决于它测的是什么。选择题榜单测的是判别能力，生成类榜单测的是产出能力，偏好类榜单测的是人类主观感受，三者不能互相替代。选错榜单，优化方向就会跑偏。

基准主要测什么判分方式最需要警惕的坑
MMLU多学科知识与理解，覆盖面广四选一，匹配选项数据污染；对选项顺序与提示格式敏感
C-Eval / CMMLU中文学科、常识与中国语境选择题部分题目来源网络，需关注时效与污染
GSM8K小学应用题的多步算术推理抽取最终数值比对只看最终答案，过程错也能蒙对
MATH竞赛级数学与符号推导答案等价判定判分器实现质量直接决定分数
HumanEval / MBPP函数级代码生成执行单元测试测试较弱，容易被记忆；不代表工程能力
SWE-bench真实仓库里修 bug、加功能跑仓库自带测试环境重、成本高，但最接近真实生产力
MT-Bench / Arena多轮对话质量与人类偏好裁判模型打分 / 人类投票位置偏差、长度偏好、风格偏好
TruthfulQA抗常见误解与编造选择题与「有用性」存在张力，需权衡
长上下文基准长文档检索与跨段推理生成后比对只测检索不代表长文推理能力

实践建议：公开榜单只用来做粗筛与回归监测，真正决定上线的一定是用你自己的业务数据搭的私有评测集，哪怕只有一百条，信号也比通用榜单强得多。

裁判模型（LLM-as-Judge）的三种偏差与对冲

用模型给模型打分成本低、可规模化，但它自带系统性偏差。不知道偏差在哪，就会把偏差当成结论。

位置偏差

裁判倾向于认为先出现的答案更好。对冲：把两个答案交换顺序各判一次，只有两次结论一致才采信，不一致就记为平局或转人工。

长度与风格偏差

更长、更有条理、带 Markdown 小标题的回答更容易得高分，哪怕内容并不更正确。对冲：在打分提示里明确声明长度不代表质量，并对事实正确性单独设一项。

自我偏好偏差

裁判倾向于给与自己同族的生成结果打高分。对冲：用与被测模型不同来源的裁判，或者同时用多个裁判取多数，并定期用人工标注校准裁判的吻合率。

工程上还有一条硬要求：裁判的判分提示必须版本化。提示一改，历史分数就不可比，评估就失去回归价值。

一套能直接落地的评估配置

评估配置的核心是「可复现」：数据集版本、模型版本、推理参数、判分提示版本四件事都要锁死，否则不同时间跑出来的分数无法比较。

深入自检：把评估讲透的六个问题

为什么离线分数涨了，线上体验没变好？

三个常见原因：一是评测集与真实分布不一致，模型只是拟合了你的题目；二是评测集被反复用于调优，已经过拟合；三是在线体验还受延迟、UI、检索质量影响，模型分数只是其中一环。解决方法是让评测集来自真实日志，并保留一份从未参与调优的留出集。

到底该选哪个模型？

先在你的私有评测集上跑，再看成本与延迟，最后做小流量线上对比。通用榜单只适合排除明显不合适的候选，不适合做最终裁决。

评测集多少条才够？

取决于你要分辨的差距有多大。想可靠地区分两个相差很小的模型，需要几百条以上；只是想发现明显回退，五十到一百条高代表性样本就够用。关键是覆盖度与代表性，不是数量本身。

裁判模型和人工标注要怎么配合？

用人工标注做「标尺」：定期抽一批让人工和裁判同时打分，算吻合率。吻合率下降说明裁判提示或模型需要更新；日常大规模跑分仍用裁判，人工只负责校准与疑难案例。

安全性评估应该怎么做？

单独立项，不能混在能力评估里。要有专门的红队用例集：越狱提示、提示注入、敏感信息泄露、危险操作建议，并且判分标准要保守——宁可漏报也要保证高危用例不通过。

评估结果多久跑一次？

两类：每次提示词、检索策略、模型版本变动时跑一次回归；线上指标（满意率、转人工率、失败率）持续监控。前者防倒退，后者抓真实变化。
