标准布局

常见顶层

cmd/ 放各二进制 main；internal/ 放仅本项目使用的包；pkg/ 放可被外部 import 的库；api/ 放 proto/IDL；configs/ 放配置。

myproj/
  cmd/server/main.go
  internal/store/
  pkg/client/
  api/proto/
  configs/
internal

编译器帮你守隐私

internal 目录下的包只能被以 internal 父目录为根的子树导入，编译器强制；是隔离实现细节的利器。

internal/secret/        # 只能被 myproj/... 导入
pkg/public/          # 任何人都可导入
cmd 与 pkg

入口薄、逻辑厚

cmd 下的 main 只做装配（读配置、建依赖、启服务）；业务逻辑下沉到 internal/pkg，便于测试与复用。

让 main 尽量薄，依赖通过构造函数注入，单测就能直接测核心逻辑。
建议

别过度设计

小项目不必套全套目录；随规模增长再拆分。internal 优先于 pkg，能藏的都藏起来。

⚠️ 盲目照搬大厂布局会让小项目臃肿；结构服务于团队与规模，而非反之。

目录怎么分：按层还是按业务

两种主流分法各有适用场景。小项目按层清晰，大项目按业务才能避免「改一个功能要翻八个目录」。

按层 vs 按业务：取舍的关键
cmd/多个可执行入口各占一个子目录。
internal/编译器强制的外部不可见，放内部实现。
pkg/只有真的要被外部复用时才放。
api/接口定义（proto、openapi）集中管理。

Go 官方建议的目录约定

目录放什么是否必需
cmd/yourapp可执行程序入口，尽量薄有二进制就需要
internal/仅本模块可导入的代码强烈推荐，天然防误用
pkg/可被外部复用的库代码谨慎使用，别当杂物间
api/OpenAPI / proto / 接口定义有对外接口时
configs/配置模板与默认值可选
scripts/构建、部署、运维脚本可选
test/集成测试与外部测试数据可选
vendor/依赖副本一般不需要，交给模块缓存
myservice/ ├── cmd/ │ ├── api/main.go # HTTP 服务入口 │ └── worker/main.go # 后台任务入口 ├── internal/ │ ├── user/ # 用户域 │ │ ├── api/ # 接口层 │ │ ├── service/ # 业务逻辑 │ │ ├── dao/ # 数据访问 │ │ └── model/ # 领域模型 │ ├── order/ │ └── pkg/ # 内部公共库 │ ├── db/ │ └── cache/ ├── api/ # proto / openapi 定义 ├── configs/ ├── go.mod └── Makefile

internal 是免费的安全边界：放在 internal 下的包，外部模块根本无法 import，由编译器保证。这是 Go 里最划算的一条规定。

四个常见反模式

万能 utils 包

什么都往 util / common / helper 里塞，最后变成一个谁都不敢动的垃圾场。

  • 按用途命名：strconvx、timeutil、httputil
  • 只放真的多处复用的东西
  • 被单个域使用的代码就留在那个域里

循环依赖

Go 不允许包循环引用，出现时通常是分层没划清。

  • 把公共部分下沉到更底层的包
  • 用接口倒置依赖方向
  • domain 层不依赖 infra 层

过早抽象

只有一个实现就先写接口，反而增加噪音。

  • 接口在被需要时才提取（多个实现或要 mock）
  • Go 的惯例是小接口、在使用方定义
  • 先写具体类型，再按需抽取

深入自检

必须遵循某个固定的项目模板吗？

不必。官方只给出松散建议，没有强制标准。真正重要的是团队内一致与依赖方向清晰。直接抄一套大型模板给小项目，会增加无谓的心智负担。

internal 和 pkg 该怎么取舍？

默认放 internal。只有当某个包确实要被其他模块复用时才放 pkg，且要为它写文档与测试。把不确定的东西都放进 pkg，等于对外承诺了一个不稳定的 API。

什么时候该拆分模块（多 go.mod）？

当不同部分的发布节奏、依赖或团队边界明显不同时。拆模块的代价是版本管理与联调变复杂，单体模块内的多服务通常更省心。不要为了「看起来清晰」而拆。

领域模型和数据模型要不要分开？

中大型项目值得分开：领域模型表达业务，数据模型对应存储。二者分开后，数据库结构变化不会直接污染业务层。小项目可以共用，减少样板代码。

main.go 应该写多少代码？

越少越好：解析配置、初始化依赖、启动服务、处理信号。业务逻辑放在各自的包里，main 只做装配。这样也便于测试——main 通常是最难测的部分。

第一层 · 三个目录的语义边界

Go 的目录约定之所以能成为「事实标准」，靠的不是文档而是编译器强制。先记住三个核心目录的判断标准。

目录语义谁能 import强制力
cmd/项目的可执行入口，一个子目录一个二进制不提供（只被构建）约定
internal/仅本项目可见的私有代码仅该 internal 的父目录及其子树编译器强制
pkg/明确对外公开的库代码任何人约定
api/API 契约（proto / OpenAPI）不编译（契约文件）约定
web/ / static/前端资源、模板不编译约定
configs/配置模板与默认值不编译约定
scripts/ / build/构建、CI、部署脚本不编译约定
test/ / testdata/测试资源（testdata 会被 go 工具忽略）—工具强制忽略
  • 判断唯一标准：import 之后能不能编译通过。internal/ 是唯一由编译器强制的边界——放在 a/internal/x 的包，只有 a/ 子树内的代码能 import，外部 import 会直接报 use of internal package not allowed。
  • cmd/ 下每个子目录对应一个 main 包：cmd/api/main.go、cmd/worker/main.go。子目录名就是二进制名。不要在 cmd 里放业务逻辑。
  • 不要建 src/。这是从 Java/C++ 带过来的习惯，Go 的 GOPATH/src 时代才需要，module 时代完全不需要，多一层只会让 import 路径变丑。

常见错误问题正确做法
把所有代码塞进 pkg/pkg 语义是「公开可复用」，全塞进去等于没有边界默认放 internal/，确实要给别人用才放 pkg/
没有 cmd/，main.go 在根目录多二进制时无法组织，且根目录混杂根目录只放 go.mod/README 等元文件
按技术分层过细（controller/service/dao/dto/vo/...）Go 里每层一个包会产生大量无意义的类型转换按领域分包，包内自洽
util/ common/ helpers/会变成垃圾桶，最终无人敢改按职责命名：timeutil、httputil，或直接内联
循环依赖import cycle not allowed把共享的类型下移到第三包，或用接口反转依赖
配置文件带密钥进仓库泄露风险configs/ 只放模板，密钥走环境变量/密钥管理

Go 官方明确说过：不要盲目套用别人的项目结构。小项目（单二进制、几千行）完全可以只有一个 main 包加几个文件，等真的需要拆分时再分。过度分层是 Go 新手最常见的过度设计。

第三层 · 排障清单

  • use of internal package not allowed → 你在 internal 的可见范围外 import 了它。规则是：a/internal/x 只能被 a/ 子树内的包 import。要么把代码移到可见范围，要么把它挪出 internal。
  • import cycle not allowed → 两个包互相 import。三种解法：① 把双方都依赖的部分抽到第三个包；② 用接口反转——在上层定义接口、下层实现（Go 的隐式接口让这很容易）；③ 合并这两个包（很可能它们本就不该分开）。
  • no required module provides package → 依赖没加进 go.mod。跑 go mod tidy；若是私有仓库，还要配 GOPRIVATE/GONOSUMDB。
  • 构建了但二进制没更新 → 检查 go build 的输出路径，以及是否用了 -o 却跑的是旧文件。用 go build -o bin/xxx ./cmd/xxx 并且 CI 里加校验。
  • CI 里 go test ./... 很慢 → 加缓存：GOCACHE 与 GOMODCACHE 挂到持久卷；-count=1 避免用缓存结果（本地调试用）。
  • 多模块项目依赖本地改动 → 在主模块的 go.mod 里加 replace ../sub => ../sub，改完记得删或固定版本。
  • 编译产物里混进了前端资源 → Go 1.16+ 用 //go:embed：//go:embed all:web 把目录嵌进二进制。注意 embed 的路径不能以 / 开头也不能用 ..。

第四层 · 原理与取舍

Go 的目录约定能落地，靠的是三个语言/工具层面的机制：internal 的编译器可见性规则、包是最小复用单元、testdata 被工具链忽略。理解这三点，剩下的约定就能自己推导。

  • internal 是唯一被编译器强制的边界：规则精确定义为「.../internal/... 只能被以 internal 的父目录为前缀的包导入」。这条规则在 go build 时检查，无法绕过（除了 symlink 这种 hack）。所以它比任何文档约定都可靠——这也是 Go 项目结构能形成事实标准的原因。
  • 包是 Go 的最小封装单元：一个目录下的所有文件属于同一个包，包内没有私有边界（小写 只是包外不可见）。所以「分层」在 Go 里意味着「分成多个包」，而过细的分层会强迫你把内部类型导出（大写），反而削弱了封装。这就是 Go 社区普遍不推荐 controller/service/dao 三层分包的原因——它逼你导出大量本该私有的类型。
  • 依赖方向应指向抽象：Go 的隐式接口（无需 implements 声明）让「上层定义接口、下层实现」变得零成本。所以正确的分层是 handler → service 接口 → 实现，而不是按技术角色切包。测试时用 mock 替换实现也顺理成章。
  • testdata 的特殊性：任何名为 testdata 的目录会被 go 工具链完全忽略（不编译、不检查）。这是放测试固件的标准位置。
项目规模推荐结构理由
单文件 / 几百行一个 main.go拆包纯属负担
单二进制、几千行main.go + 2~5 个包按职责分，不按层分
多二进制 + 共享逻辑cmd/ + internal/cmd 只做装配，逻辑在 internal
要对外提供 SDK加 pkg/只有确实要公开的部分才放
大型单体（十万行+）按领域切分 internal/order、internal/payment领域内自洽，跨领域靠接口/事件
为什么官方说「不要盲目套用别人的项目结构」？

因为 golang-standards/project-layout 那个广为流传的仓库不是 Go 官方标准（它是社区项目，README 里明确写了这一点），里面的目录（如 pkg/、build/、deployments/）是给「足够大的项目」准备的全集。一个三个文件的小工具照抄它，会多出十几个空目录，纯粹是自找麻烦。官方的态度是：从最小结构开始，在真实需要出现时再拆分。判断「什么时候该拆」的信号：① 某个目录下的文件超过 10~15 个；② 出现了明确的复用需求（两个二进制都要用）；③ 出现了明确需要隐藏的实现细节（该进 internal）。不到这些信号就别拆。

internal 能不能防止别人 fork 后用？

不能。internal 是编译期的可见性约束，规则是「以 import 路径前缀判断」。如果别人 fork 了你的仓库，那他的代码就在同一个 module 内、路径前缀相同，就能 import。它防的是「别人 go get 你的模块后 import 你的 internal 包」这种场景——这是它的设计目标：让你能明确区分「这是我的实现细节，不要依赖它，我随时会改」。所以 internal 的价值是表达意图 + 防止意外依赖，不是访问控制或加密。真正不想让人用的代码，放在不公开的仓库里。

按领域分包和按技术分层，差别到底有多大？

差别在变化时的波及面。按技术分层（controller/service/dao）时，加一个字段要同时改 dto、vo、model、service、dao 五个包；按领域分包（order/、payment/）时，改订单逻辑基本只在 order/ 内完成，对外只暴露接口。更关键的是封装：跨包就必须导出（大写），按技术分层会逼你把大量内部类型导出，导致「谁都能改」；按领域分包时，领域内部的类型可以保持小写私有，只有跨领域的契约才导出。Go 之父 Rob Pike 说过「a little copying is better than a little dependency」——Go 的设计哲学倾向于适度的重复换取更低的耦合，这与「一切都要抽公共层」的直觉是相反的。
