数据湖小文件治理：合并文件为何不能直接删旧对象

用 10000 个 1 MB 文件推算元数据与扫描成本，理解压实、快照提交和并发写入安全性。

小文件问题先算数量

一次实时写入每分钟产出 10 个 1 MB 文件，一天就是 14400 个文件、约 14 GB 数据。若分析查询要列出每个对象、读取文件尾元数据并打开大量小文件，固定开销可能压过读取数据本身；任务调度会产生许多很小的扫描任务，元数据服务和对象存储请求数也会上升。把它们合成例如 128 MB 左右的文件后，文件数可下降两个数量级，但目标大小必须结合引擎、列式行组、网络带宽和查询选择性调整。

小文件并不只是“磁盘碎片”。在对象存储里，列举、读取、打开与调度文件都有代价；列式格式的行组与统计信息太碎还会削弱压缩和扫描效率。不过一味生成巨型文件也可能降低并行度，点查或分区裁剪要多读数据。理想文件大小是工作负载的结果，不是固定的神奇数字。

图解：小文件压实的快照切换

沿箭头逐步核对输入、变换和输出；下面的推演可以逐步切换。

压实有三阶段

压实任务先在某个表快照上选择同分区的候选小文件，再读取并生成若干新大文件，最后通过表格式的元数据事务提交新快照：新快照引用新文件，不再引用被替换的旧文件。提交前写好的大文件还不可被普通读者看见；提交成功后，新查询读新快照，正在读旧快照的查询可能仍需要旧文件。

这解释了为什么不能直接用文件系统命令删除旧对象。旧快照、长查询、时间旅行、分支或尚未完成的读任务可能仍引用它们。物理删除应交给有保留期与引用检查的过期清理流程。相反，压实生成大文件后若元数据提交失败，新文件可能成为孤儿，也要按安全规则清理，不能在失败瞬间凭猜测删除其他任务可能引用的对象。

逐步推演

读快照 S

选择 10000 个小文件并保留旧引用。

写大文件

按目标大小生成新对象，尚未对读者可见。

原子提交 S+1

元数据切换到新文件集合，合并并发写入。

安全清理

等旧快照不再被需要后删除旧文件。

并发写入的冲突

压实读取快照 S 时，实时写入者可能同时追加新文件并提交快照 S+1。压实提交必须基于表格式的并发控制规则，确认它替换的文件集合没有被不兼容地修改，并保留同时写入的新文件。若冲突，任务可能重试、重算或在允许条件下重基线。直接覆盖一份“当前文件列表”会丢掉并发写入；只有使用表格式的原子快照提交，读者才不会看到半新半旧文件集合。

分区范围也影响冲突概率。把每小时新文件压实成日文件，可能与同一天持续写入反复竞争；可先对冷分区做压实，再为热分区设置更短批次或阈值。压实与增量写入争抢 IO、CPU 和网络，放在低峰时段、控制并发并监控写入延迟通常更稳妥。

指标偏低或偏高的含义处理方向
平均文件大小过小会增元数据与调度成本微批写入与压实
单文件大小过大可能减并行度结合查询和行组测量
压实冲突率与并发写入争同一范围调整分区和调度
孤儿文件数写成功但元数据提交失败按引用与保留规则清理

数据正确性不能只看文件数

压实应该改变物理布局，不改变逻辑行集。输入若有 100 万条有效记录，压实后读取同一表快照的行数、主键集合和关键汇总应保持一致；如果表格式同时承载删除文件、更新或合并语义，读取时还要正确应用这些变更。只把数据文件字节拼接成大文件并不能保留列式格式和删除语义。

可构造一个测试：读者 R 在快照 S 开始查询，压实任务提交 S+1，再让 R 继续读取。R 应稳定看到 S 的结果；新读者读取 S+1，逻辑结果相同但文件计划不同。接着并发插入 100 条新记录，核对下一快照逻辑行数增加 100，压实没有覆盖新写入。

分区、聚簇和压实不同

分区按日期或地区缩小查询候选范围；聚簇或排序把相关值靠近，帮助数据跳过；压实主要把很多小文件改写成较合适的物理文件。这些动作可一起执行，但各有不同目标。对一个高基数字段逐值分区会产生海量分区和小文件，后期压实很难完全弥补错误分区设计。先看典型过滤条件与分区基数，再制定写入和压实策略。

若上游每条事件都提交一个独立表快照，除了小文件还会产生大量元数据版本。应考虑微批写入与快照过期策略。保留期不能只为省存储而设得极短：长查询、回滚审计和故障恢复都需要一定历史。根据读任务最长运行时间和业务追溯需求决定最短安全窗口。

运营指标与练习

每天记录每分区文件数、文件大小分布、小文件占比、查询计划文件数、对象存储请求、压实输入/输出字节、失败重试数和孤儿文件积压。优化前后比较查询 P95 与写入延迟，避免“查询省 20 秒，写入慢 2 分钟”。压实属于持续治理，写入模式不改，文件数还会再次增长。

练习：某分区有 10000 个 1 MB 文件，目标 128 MB。粗估合并后的文件数量，再说明为什么提交新快照后不能立即删除全部旧文件，以及哪些读者可能仍需要它们。

小文件问题的量化与危害

「小文件」不是感觉，是能算出来的：文件数远超合理值、平均大小远低于目标值。危害也是可量化的。

目标值与判据

# 目标文件大小（各格式的经验值）
#   HDFS / Hive 表      128 MB ~ 512 MB（对齐 block size）
#   Parquet / ORC       128 MB ~ 1 GB（列式，太小则压缩与索引都失效）
#   Iceberg / Delta     128 MB ~ 512 MB（官方推荐 128MB 左右）
#
# 判据：
#   平均文件大小 < 目标值的 1/4      -> 该合并
#   单分区文件数 > 1000              -> 元数据压力大
#   单次查询要打开的文件数 > 10000   -> 必崩或极慢
危害量化表现为什么
元数据爆炸NameNode 每个文件约 150~300 字节内存；1 亿小文件 = 数十 GBHDFS NameNode 全内存存元数据，是硬上限
查询变慢每个文件一次 open + seek，10000 个文件 = 上万次 IO打开文件、读 footer、建 reader 的固定开销无法摊销
压缩与索引失效几十 KB 的 Parquet 无法有效压缩，字典编码收益趋近 0列式格式的优势依赖足够的行数
调度压力Spark 默认一个文件一个 task，1 万小文件 = 1 万 tasktask 调度开销可能超过实际计算
成本上升对象存储按请求次数计费，读 1 万个小文件比读 10 个大文件贵得多云上尤其明显

合并策略：为什么不能直接删旧对象

在数据湖里删除文件不像删本地文件——快照/元数据还在引用它。直接删会导致正在读的查询失败、或表直接损坏。

层面能不能直接删原因
HDFS 文件不能正在运行的 task 持有 lease；删除会让读任务失败
Hive 分区目录不能Hive metastore 里还有分区元数据；删了就查不到（或报文件不存在）
Iceberg / Delta / Hudi不能快照（snapshot）仍指向这些文件，直接删 = 破坏时间旅行和并发读
对象存储（S3/OSS）技术上能删，但绝不能手动删同上，且没有回收站

合并与清理命令

# Iceberg 的标准做法（推荐）
#   1) 合并文件（产出新文件，旧文件还被旧快照引用）
spark.sql("""
  CALL catalog.system.rewrite_data_files(
    table => 'db.orders',
    strategy => 'binpack',
    options => map('target-file-size-bytes','134217728',
                   'min-file-size-bytes','67108864',
                   'max-concurrent-file-group-rewrites','20')
  )
""")
#   2) 清理不再被引用的旧文件（关键：只删「没有任何快照引用」的）
spark.sql("CALL catalog.system.expire_snapshots(
             table => 'db.orders', older_than => TIMESTAMP '...', retain_last => 5)")
spark.sql("CALL catalog.system.remove_orphan_files(table => 'db.orders')")
#      ^^^ 这一步才真正删物理文件，安全

# Hive 的合并（覆盖写）
INSERT OVERWRITE TABLE t PARTITION(dt='2026-10-01')
SELECT * FROM t WHERE dt='2026-10-01';
#   配合合并参数
SET hive.merge.mapfiles=true;
SET hive.merge.smallfiles.avgsize=134217728;   # 平均小于 128MB 才合并

# Spark 侧减少产出小文件（源头治理，最重要）
spark.sql.shuffle.partitions=200              # 别用默认 200 处理小数据
df.repartition(10).write.partitionBy("dt").parquet(path)
df.coalesce(1).write...                       # 小心：coalesce 会导致单 task 压力
  • 源头治理优先于事后合并：控制写入分区数（repartition 按数据量算）、开启 AQE、用流式写入的检查点间隔控制（Flink 的 checkpoint.interval 太小会产生大量小文件）。
  • 合并要在低峰做：rewrite_data_files 会重写全部数据，IO 和 CPU 开销大，且会产生新快照。
  • 保留快照的时间 = 你能回滚的窗口：expire_snapshots 的 older_than 通常设 3~7 天。保留期间旧文件占着存储，这是「可回滚」的成本，要算进预算。
  • 分区粒度别太细：按小时分区 + 低频写入 = 天然小文件。改成按天分区，或用 Iceberg 的隐藏分区（hour(ts)）让元数据更轻。
为什么 Iceberg 不能直接删文件？

因为 Iceberg 是快照隔离的：每次提交生成一个新快照，快照里是一份 manifest 列表，manifest 里记录具体文件路径。旧快照仍然指向旧文件，以支持时间旅行（VERSION AS OF）和并发读（正在读的事务持有旧快照）。直接删文件会让这些读操作失败。正确顺序是 rewrite → commit 新快照 → expire 旧快照 → remove_orphan_files，最后一步才真正删物理文件。

合并会不会影响正在运行的查询？

取决于表格式。Iceberg/Delta 不会：合并是原子提交，读者要么看到旧快照（含旧文件），要么看到新快照，不会读到中间状态（这就是 MVCC + 快照隔离的价值）。Hive 会：INSERT OVERWRITE 过程中分区目录被替换，正在读的查询可能失败或读到空——这是 Hive 表没有事务保证的硬伤，也是往 Iceberg 迁移的主要动因之一。

小文件合并的收益有多大？

实测上通常：查询耗时降 50%~90%（主要来自 open 次数和 task 数减少），存储降 10%~30%（压缩率提升），NameNode/元数据压力降一个数量级。投入产出比很高，是数据湖治理里优先级最高的一项。但如果查询本身只扫描少数分区，收益会小很多——先定位是哪些表/分区在拖后腿。

自检

新大文件写完后，为什么不能立即删除所有旧小文件？

旧快照或正在运行的查询仍可能引用旧文件；应在元数据提交和安全保留期之后清理。
