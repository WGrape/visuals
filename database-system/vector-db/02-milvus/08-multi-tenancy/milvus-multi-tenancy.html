①五种多租户方案：从强隔离到低成本

SaaS 场景下“每个客户的数据必须互不干扰”，Milvus 提供从粗到细的五档隔离：Database 级、Collection 级、Partition 级、Partition Key 级，以及完全共享 + 行级过滤。隔离越强，元数据与资源开销越大。

②横向对比

方案隔离强度资源开销租户规模跨租户查询
Database 级★★★★★高（每库独立元数据与资源）数十个困难
Collection 级★★★★中（每集合独立段与索引）数千个需应用层聚合
Partition 级★★★低（共享集合与索引配置）受分区上限约束容易（不指定分区即全扫）
Partition Key 级★★★低（自动路由，无需人工维护）数千个容易
行级过滤★★最低（全共享）无上限最容易
隔离强度不仅是“数据看不见”，还包括资源不互相拖累。行级过滤下，一个大客户的海量数据会让所有客户的查询变慢——这是它最大的隐性成本。

③逐个拆解

Database 级

每个租户一个 Database，Collection 重名也不冲突。适合租户少、要求物理级隔离（如私有化部署、合规要求高）的场景。缺点是元数据膨胀、运维对象变多。

Collection 级

最主流。每个租户可有不同的 Schema、维度、索引与一致性级别——大客户用小维度快索引、小客户用大维度省资源都行。缺点是 Collection 总数有上限，成千上万租户时元数据压力大。

Partition 级

一个 Collection 内按租户分区，共享同一套 Schema 与索引配置。查询指定分区名即可裁剪扫描范围，还能把冷租户的分区释放出内存。受分区数量上限约束。

Partition Key 级

建表时把 tenant_id 声明为 Partition Key，写入时自动路由，查询时指定该值即可命中对应分区。省掉了人工创建和维护分区，是租户多且数据量中等时的甜点方案。

行级过滤

所有租户共享一个 Collection，每次查询都带 tenant_id == "xxx"。租户数无上限、运维最简单，但过滤字段必须建 INVERTED 索引，且数据量增长会让过滤成本上升。

混合方案（现实中最常见）

头部大客户 → 独占 Collection / 资源组；长尾小客户 → 共享 Collection + Partition Key 或行级过滤。按客户体量分层比一刀切更经济。

④资源与权限隔离

资源组

把 QueryNode 分组，指定 Collection 加载到哪组，避免“一个大客户拖垮所有人”。大客户独占资源组，长尾共享。

RBAC

较新版本提供基于角色的访问控制：用户 → 角色 → 权限（对 Collection/Database 的读写）。配合多租户做越权防护，别只靠应用层过滤。

配额与限流

限制单租户的写入速率、Collection 数量、内存占用。向量库的写入很容易被打满，限流要在入口就做。

只用应用层过滤做多租户是危险的。一旦某个查询漏掉 tenant_id 条件，就会跨租户泄漏数据。至少要做两层：SDK 封装层强制注入过滤条件 + 数据库层的 RBAC / 分区隔离。

⑤怎么选：按租户数与数据量两个维度

租户数 < 50，且要求强隔离？
    └─ Database 级 / 独占集群
租户数 50 ~ 数千，数据量差异大？
    ├─ 每租户数据量都很大 → Collection 级
    └─ 每租户数据量小且均匀 → Partition Key 级
租户数 > 数千，单租户数据量很小（如个人用户）？
    └─ 共享 Collection + 行级过滤（tenant_id 必建索引）
有头部大客户 + 长尾小客户？
    └─ 混合：大客户独占 Collection/资源组，长尾走 Partition Key
决策时还要考虑未来迁移成本：从行级过滤迁到独占 Collection 相对容易（按租户导出重灌）；反过来则很痛苦。如果不确定，优先选隔离更强的方案。

⑥代码示例：Partition Key 方案

schema = client.create_schema(auto_id=False, enable_dynamic_field=True)
schema.add_field("chunk_id",   DataType.VARCHAR,     max_length=64, is_primary=True)
schema.add_field("tenant_id",  DataType.VARCHAR,     max_length=64,   # 分区键
                 is_partition_key=True)                                    # 自动分桶
schema.add_field("embedding",  DataType.FLOAT_VECTOR, dim=768)

index_params = client.prepare_index_params()
index_params.add_index(field_name="embedding", index_type="HNSW", metric_type="COSINE")
index_params.add_index(field_name="tenant_id", index_type="INVERTED")   # 仍需建标量索引

client.create_collection(collection_name="saas_docs", schema=schema,
                         index_params=index_params, num_partitions=128)

# 查询：指定 tenant_id 即可命中该租户的分区
res = client.search(collection_name="saas_docs", data=[query_vec], limit=10,
                    filter='tenant_id == "acme"', output_fields=["chunk_id"])
Partition Key 的基数要足够且分布均匀。若某租户的数据占了一半，它的分区会成为热点，该租户查询变慢——这时候就该把它单独拆成独占 Collection 了。

Milvus 多租户的四种方案

Partition Key 是 2.4 的推荐方案：建 collection 时指定 num_partitions=128 和 partition_key_field="tenant_id"，Milvus 自动把相同 tenant_id 的数据放到同一分区，检索时自动裁剪，既省资源又有不错的隔离性，还不用手动管理分区。

实操代码

from pymilvus import MilvusClient, DataType

client = MilvusClient(uri="http://localhost:19530")

# 方式 A：Partition Key（推荐，2.4+）
schema = client.create_schema(auto_id=False, enable_dynamic_field=True)
schema.add_field("id", DataType.INT64, is_primary=True)
schema.add_field("tenant_id", DataType.INT64)
schema.add_field("vector", DataType.FLOAT_VECTOR, dim=768)
schema.add_field("text", DataType.VARCHAR, max_length=2000)

client.create_collection(
    collection_name="docs",
    schema=schema,
    num_partitions=128,                        # Milvus 自动按 tenant_id 哈希分区
)
# 指定哪列是分区键
client.create_partition_key("docs", "tenant_id")   # 或建索引时指定
# 检索时带上 tenant_id，Milvus 自动只扫对应分区
res = client.search("docs", data=[qvec], filter="tenant_id == 42", limit=10)
# 方式 B：手动 Partition（2.4 之前，或需要精确控制时）
client.create_partition("docs", "tenant_42")
client.insert("docs", rows, partition_name="tenant_42")
res = client.search("docs", data=[q], partition_names=["tenant_42"], limit=10)
# 注意：单 collection 分区数上限 4096

# 方式 C：Database 级隔离（2.3+，最强隔离）
client.create_database("tenant_42_db")
client.using_database("tenant_42_db")

# 索引参数调优（HNSW）
index_params = client.prepare_index_params()
index_params.add_index(
    field_name="vector",
    index_type="HNSW",
    metric_type="COSINE",          # 或 L2 / IP
    params={"M": 16, "efConstruction": 200},
)
client.create_index("docs", index_params)
client.load_collection("docs")

# 检索时调 ef（召回 vs 耗时）
res = client.search("docs", data=[q], limit=10,
                    search_params={"params": {"ef": 64}})   # ef 越大召回越高

多租户排障

症状原因处理
collection 太多导致变慢元数据膨胀；每个 collection 都有开销改用 Partition Key 或过滤检索；collection 数控制在千级以内
分区数超上限手动分区超过 4096改用 Partition Key（上限 1024 但自动管理）或分库
跨租户数据串了检索时没传 filter / 没指定 partition每次检索必须带 tenant_id 条件；在 SDK 层封装强制校验
小租户拖累大租户共享资源，热租户占满大客户单独 collection/database；或用资源组（Resource Group）隔离
召回率低nprobe/ef 太小，或过滤后候选不足调大 nprobe（IVF）或 ef（HNSW）；注意后过滤会导致结果不足
内存占用大索引常驻内存；HNSW 尤其吃内存768 维 × 100 万条约需 3GB（HNSW 还要加图结构约 30%）；用 IVF_PQ 或 DiskANN
写入后查不到没 load 或没 flush写完 flush()；查询前 load_collection()

过滤检索的陷阱：如果用「先 ANN 再过滤」（后过滤），当 tenant_id 只占 1% 时，ANN 召回的 100 条里可能只有 1 条属于该租户，结果严重不足。Partition Key 与预过滤（Pre-filter）能保证候选集全部属于目标租户，这是分区方案的核心价值。

多租户的本质是在隔离强度与资源成本之间选点：租户少就往强隔离走，租户多就往共享走，体量分化就分层混合。无论选哪种，tenant_id 都必须建标量索引，越权防护都要做两层。
