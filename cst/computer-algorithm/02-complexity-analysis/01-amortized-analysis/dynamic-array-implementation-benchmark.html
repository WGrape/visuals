动态数组（Python list、Go slice、Java ArrayList）的核心不是「数组」，而是「满了就换更大的、把旧数据搬过去」。这一页把它从原理变成可运行的实现，并实测扩容成本为什么是均摊 O(1)。

01自己实现一个可扩容数组

下面这段 Python 用普通列表模拟「定长缓冲 + 负载因子扩容」：超过容量就申请 2 倍新缓冲，顺序拷贝，再指向新缓冲。

class DynArray:
    def __init__(self, cap=4):
        self.buf = [None]*cap
        self.cap = cap
        self.n = 0
    def append(self, x):
        if self.n == self.cap:        # 满了
            self._grow()
        self.buf[self.n] = x
        self.n += 1
    def _grow(self):
        new = [None]*(self.cap*2)      # 2 倍扩容
        for i in range(self.n):
            new[i] = self.buf[i]
        self.buf = new
        self.cap *= 2

02负载因子：2 倍还是 1.5 倍

扩容倍数直接决定两件事：扩容次数（越少越好）和冗余内存（越小越好），二者互相拉扯。

倍数扩容次数（N 次追加）扩容后冗余代价
2 倍约 log2(N) 次最高约 50%拷贝量摊下来最小
1.5 倍约 log1.5(N) 次最高约 33%拷贝总量略多
固定 +KN/K 次几乎无拷贝最频繁
要点：工程默认 2 倍（C++ vector、Go slice 都接近 2 倍）。1.5 倍能省内存但拷贝更频繁；只有当内存极度紧张时才值得降倍数。缩容一般不对称（用到 1/4 才缩回 1/2），否则会「扩容-缩容」来回抖动。

03实测均摊 O(1)

把「每次 append 的平均拷贝代价」画出来：单次最坏 O(N)，但平均摊下来是常数。下面估算 100 万元素的总拷贝次数。

# 总拷贝次数 = 1 + 2 + 4 + ... + N/2 ≈ N
# 100 万元素，2 倍扩容：拷贝约 1e6 次
# 平均每次 append 拷贝 ≈ 1 次  -> 均摊 O(1)
n = 1_000_000
total_copy = sum(2**k for k in range(int(n.bit_length())-1))
print(total_copy, total_copy/n)  # ≈ 1e6, 1.0

04什么时候该用 / 避坑

  • 数据量未知或会增长：用动态数组而不是预估一个定长数组。
  • 知道大致上限：先 reserve / make([]T, 0, cap) 预分配，避免反复扩容拷贝。
  • 频繁在头部插入删除：动态数组是 O(N) 搬移，改用链表或双端队列。
  • 需要缓存局部性：动态数组的连续内存对 CPU 缓存友好，优于链表。
问：为什么均摊 O(1) 不能替代尾延迟？

因为那一次「刚好满了」的 append 要搬整个数组，是真实的 O(N) 毛刺。延迟敏感场景（如高频交易、实时音频）要预分配或容忍毛刺，不能只看平均值。
