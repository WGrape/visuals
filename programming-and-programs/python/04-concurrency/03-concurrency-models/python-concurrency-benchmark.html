Python 并发选型实测：threading / multiprocessing / asyncio

三者对比、基准代码与典型数字

对比 基准 数字 决策
Python 的 GIL 决定了：CPU 密集型用多线程几乎无收益，IO 密集型才能靠并发起飞。下面用一组基准量化这个直觉。

1三者怎么选

模型受 GIL 影响适合场景开销
threadingCPU 不并行IO 密集（网络/磁盘）低
multiprocessing无 GILCPU 密集高（进程/内存）
asyncio单线程合作式大量 IO 且高并发低

2基准代码（CPU 密集求和）

import time, concurrent.futures as cf

def cpu_sum(n):
    return sum(i * i for i in range(n))

N = 4_000_000

t0 = time.time(); cpu_sum(N); print("single", time.time()-t0)

with cf.ThreadPoolExecutor() as e:
    t0 = time.time()
    list(e.map(cpu_sum, [N//4]*4)); print("thread", time.time()-t0)

with cf.ProcessPoolExecutor() as e:
    t0 = time.time()
    list(e.map(cpu_sum, [N//4]*4)); print("process", time.time()-t0)

3典型数字（4 核，N=400 万）

方案相对耗时说明
single1.0x基准
threading约 1.0xGIL 锁住，几乎无收益
multiprocessing约 0.3x4 进程近 4 倍加速

要点：数字随 CPU 核数 / 负载浮动，上表是方向性量级，不是精确值。

4决策表

  • 任务是网络请求 / 文件读写 / 数据库查询 → asyncio 或 threading。
  • 任务是数值计算 / 编解码 / 图像处理 → multiprocessing 或 C 扩展（释放 GIL）。
  • 并发量极大且多为等待 → asyncio 事件循环开销最低。
  • 简单脚本别过度设计：先单线程，瓶颈明确再上并发。

第一层 · 概念与判定：先分任务是 CPU 密集还是 IO 密集

并发选型的第一个分叉不是「用哪个库」，而是任务瓶颈在哪。CPU 密集看算力，IO 密集看等待。

任务特征首选为什么
纯计算、不等待（求和/加密/压缩）multiprocessing绕开 GIL，真正多核并行
等网络/磁盘/锁（爬虫/请求转发）asyncio 或 threading等待期间让出，不占线程
既有同步库、改动成本高threading改动最小，但 IO 密集才有效
CPU+IO 混合（读文件再算）进程池 + 异步算的部分进进程池，等的部分异步

一句话判定：先在代码里找「是不是大部分时间在 await / time.sleep / 等 socket」——是就 IO 密集，否则 CPU 密集。

核数查看 + 并发压测命令

# 看可用核数，决定进程/线程数
python -c "import os; print(os.cpu_count())"

# 绑核测，排除调度噪声（Linux）
taskset -c 0-3 python bench.py

# IO 密集压测：用 asyncio 并发 100 个 50ms 请求
python -m asyncio
>>> import asyncio, time
>>> async def main():
...     await asyncio.gather(*[asyncio.sleep(0.05) for _ in range(100)])
>>> t=time.time(); asyncio.run(main()); print(time.time()-t)  # ≈5.5s 串行 vs ≈0.55s 并发

数量级直觉：进程数超过核数只会更慢（上下文切换）；IO 并发数通常取 50–200，过大反而触发连接/文件描述符上限。

第三层 · 排障与边界：三个最常踩的坑

  • 以为 threading 能加速计算：CPython 有 GIL，同一时刻只有一个线程跑字节码，CPU 密集用 threading 反而因锁竞争略慢 5–10%
  • multiprocessing 传大对象：进程间靠 pickle 序列化，传几百 MB 数组比计算还慢；改用共享内存（multiprocessing.shared_memory）或放进程外存储
  • asyncio 忘写 await：协程不 await 就不调度，表现为「代码跑得飞快但结果全错/没发请求」；用 ruff 的 asyncio 规则或 IDE 警告兜底
  • 线程数 / 协程数过多：线程默认栈 8MB，开 1000 线程就吃 8GB；asyncio 虽轻量但同步阻塞调用会卡死事件循环
  • 死锁：asyncio 里 await 持有锁再去 await 别的协程，或 threading 嵌套加锁顺序不一致

第四层 · 原理与取舍

为什么 Python 多线程在 CPU 密集下不加速？

因为 GIL（全局解释器锁）规定同一时刻只有一个线程能执行 Python 字节码。多线程的「并行」只发生在 C 扩展释放 GIL 时（如 numpy 的部分运算），纯 Python 循环全程持锁，多个线程只能时间片轮转，还要额外付出锁竞争开销，所以不加速甚至变慢。要真并行只能多进程或换无 GIL 实现（PyPy 仍带 GIL，Cython 释放 GIL 需标注，Python 3.13 起实验性 nogil 构建）。

asyncio 比 threading 快在哪？

asyncio 是单线程协作式多任务：遇到 await 就主动让出，没有线程切换（≈微秒级 vs 线程毫秒级）和锁开销。它适合「大量短 IO 等待」——1000 个连接各等 50ms，事件循环在它们之间无缝切换。但它不魔法：遇到 CPU 密集代码会卡住整个循环，必须丢进 run_in_executor（本质是线程/进程池）。

选 multiprocessing 一定要付出序列化代价吗？

只有跨进程传数据才需要 pickle。如果数据一开始就在子进程里产生（如每个进程读自己的文件），或者走共享内存 / 内存映射 / 外部队列（Redis、ZeroMQ），就能避免大对象序列化。所以「进程慢」通常是用法问题：把输入数据设计成各进程自取，而不是主进程算好再广播。
