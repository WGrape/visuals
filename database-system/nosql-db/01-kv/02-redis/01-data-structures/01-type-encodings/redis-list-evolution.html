Redis List 数据结构演进史

从压缩列表到快速列表的链表进化

Redis 2.0

ziplist 实现 List

2010 年，List 类型诞生。底层采用 ziplist 压缩列表， 元素连续存储，内存紧凑，适合小数据量场景。

// ziplist 结构
|zlbytes|zltail|zllen|elem1|elem2|...|zlend|

• zlbytes: 总字节数 (4 bytes)
• zltail: 尾偏移量 (4 bytes)
• zllen: 元素数 (2 bytes)
• zlend: 结束标记 (0xFF)
连续内存 O(1) LPUSH/RPOP 小数据友好
Redis 2.2

linkedlist 登场

引入 linkedlist（双向链表）作为大数据量 List 的底层实现。 当列表元素增长超过 ziplist 阈值时，自动转换为链表。

// linkedlist 节点
listNode *prev 8 bytes
void *value 8 bytes
listNode *next 8 bytes
每节点: 24 bytes + 指针开销
O(1) 头插/尾插 双向遍历 无长度限制
Redis 2.4

ziplist ↔ linkedlist 转换

完善编码转换机制。当列表元素 ≤ list-max-ziplist-entries 时使用 ziplist， 超过阈值时转换为 linkedlist。

// 转换条件 (Redis 2.4)
ziplist: 元素数 ≤ 512
linkedlist: 元素数 > 512
自动编码切换 阈值可配置
Redis 3.2 ⭐ 重大变革

quicklist 统一天下

革命性突破！引入 quicklist 作为 List 的唯一底层实现。 它是 ziplist 和 linkedlist 的完美结合：每个节点是一个 ziplist， ziplist 之间用双向链表连接。

Redis 4.0

quicklist 优化

优化 quicklist 的 push/pop 操作，减少内存碎片。 引入新的参数 list-compress-depth 控制压缩深度。

// list-compress-depth
0: 不压缩
1: 头部和尾部各 1 个不压缩
2: 头尾各 2 个不压缩
...
目的: 减少 CPU 开销，保留热点访问
LZF 深度压缩 内存优化 尾部压缩
Redis 7.0+ ⭐ 底层升级

listpack 替换 ziplist

Redis 7.0 将 quicklist 内部的 ziplist 替换为 listpack。 解决了 ziplist 删除元素时的级联更新问题，性能更稳定。

// listpack vs ziplist
ziplist:
  每个节点存前节点长度
  → 删除中间节点需更新后续所有节点

listpack:
  只存总长度，逆向遍历
  → 删除任意节点只需更新长度字段
listpack 编码 无级联更新 向后兼容

演进总结

Redis List 的演进是一部"取长补短"的历史：

ziplist（紧凑但 O(n) 删除）+ linkedlist（灵活但费内存）= quicklist（完美平衡）

核心设计哲学：
分而治之 — 大链表拆成多个小 ziplist
双向遍历 — linkedlist 保留首尾指针
按需压缩 — LZF 减少冷数据内存

最终实现：O(1) 头尾操作 + 紧凑内存存储 + 无级联更新

List 的编码演进（三代）

版本编码底层内存问题
Redis < 3.2ziplist 或 linkedlist连续数组 / 双向链表链表每个节点 3 个指针（prev/next/value），开销大小列表用链表浪费内存
Redis 3.2 – 6.xquicklist链表 + 每个节点是一个 ziplist折中：既省内存又避免大块连续内存配置项复杂
Redis 7.0+quicklist2（listpack 版）链表 + 每个节点是 listpack同 quicklist，且无级联更新问题—
配置项默认值含义
list-max-ziplist-size-2每个 quicklist 节点的 ziplist 大小。正值=元素个数，负值=按字节：-1=4KB、-2=8KB、-3=16KB、-4=32KB、-5=64KB
list-compress-depth0节点压缩深度：0=不压缩；1=首尾各 1 个节点不压缩、中间压缩；2=首尾各 2 个...

quicklist 的设计取中：纯 ziplist 在元素多时（几万个）插入/删除要整体搬移内存；纯 linkedlist 每个元素多占约 24 字节指针。quicklist 把元素分装进多个 ziplist（每个约 8 KB），既控制了单块内存大小，又把指针开销摊薄到“每个节点一个”而不是“每个元素一个”。

List 编码与验证

# 查看配置
CONFIG GET list-max-ziplist-size     # -2  → 每个节点 8KB
CONFIG GET list-compress-depth       # 0   → 不压缩

# 观察编码（Redis 7 统一显示为 quicklist，但内部节点已是 listpack）
RPUSH mylist a b c
OBJECT ENCODING mylist      # "quicklist"
LLEN mylist
MEMORY USAGE mylist

# 验证压缩效果（元素多时才明显）
# 压入 10000 个元素，对比 compress-depth=0 与 =1 的内存
CONFIG SET list-compress-depth 1
MEMORY USAGE mylist

# 常用命令复杂度
# LPUSH / RPUSH / LPOP / RPOP : O(1)      ← 两端操作是 List 的核心优势
# LINDEX / LSET / LINSERT     : O(n)      ← 按下标访问很慢，别用 List 做随机读
# LRANGE 0 -1                 : O(n)      ← 大列表要小心
# LTRIM                       : O(n)

用法与坑

场景用 List？更合适的选择
消息队列（简单的生产者-消费者）可以（LPUSH + BRPOP）Stream（需要 ACK、多消费者组、持久化时）
最新动态/时间线（只看前 N 条）可以（LPUSH + LTRIM 保持长度）ZSet（需要按分数排序时）
栈/队列合适—
需要按下标随机访问不合适（O(n)）用 String 存 JSON，或用 Hash
需要去重不合适Set
需要防止重复消费不合适Stream 的消费者组 + ACK
  • BRPOP 是阻塞的，会占用一个连接：每个阻塞的客户端在服务端占一个 client 槽位。大量消费者要考虑连接数与 maxclients。另外阻塞连接受 timeout 影响（设 0 表示永不超时）。
  • List 做队列丢消息：RPOP 拿到消息后客户端崩溃 → 消息永久丢失。List 没有 ACK 机制。要可靠队列用 Stream（XREADGROUP + XACK + XPENDING 处理未确认）。
  • list-compress-depth 只对中间节点压缩：因为两端才是频繁操作的位置，压缩它们会白白消耗 CPU（每次操作都要解压）。设 1–2 通常性价比最高。
  • 大 List 的删除阻塞：几百万元素的 List 用 DEL 会阻塞主线程（毫秒到秒级）。用 UNLINK（异步删）或 LTRIM 逐步缩短。
  • 排障：OBJECT ENCODING → LLEN 看长度 → MEMORY USAGE → 若内存异常高，检查 list-compress-depth 是否为 0 且元素是否很大。
List 和 Stream 该选哪个做消息队列？

只需要“先进先出、能阻塞等待、丢几条无所谓”→ List 足够且更省。需要消费确认（ACK）、多消费者组、消息回放、失败重试 → 必须用 Stream。生产级队列建议直接上 Stream 或专业 MQ（Kafka/RabbitMQ）。

为什么 LPUSH 是 O(1) 而 LINSERT 是 O(n)？

quicklist 对两端做了优化（头尾节点直接定位），但中间位置必须遍历节点、再在 listpack 内查找/搬移。所以 List 是“两端操作快、中间操作慢”的结构，别当数组用。
