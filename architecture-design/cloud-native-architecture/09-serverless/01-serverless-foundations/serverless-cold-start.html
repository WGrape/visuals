Serverless 冷启动与延迟预算

一次请求触发新执行环境时，初始化时间会落到用户等待路径上。

核心机制

冷启动一般涉及分配执行环境、加载运行时和应用依赖、执行初始化代码，然后才进入处理函数。平台、镜像、语言和配置不同，阶段与耗时也不同。

热实例复用可避开部分初始化，但流量骤增、新版本发布或空闲回收后仍可能出现冷启动。应同时测首请求、稳态请求和突发扩容的延迟分布。

用一个例子看过程

用户请求 → 分配环境 → 加载代码与依赖 → 初始化连接 → 执行业务函数

拆分耗时

记录平台初始化、应用初始化、依赖连接和业务处理各段时间。

减轻初始化

精简依赖和启动工作；把必须的初始化留在正确时机。

验证策略

在真实突发、发布和空闲后场景测 P95/P99 与并发容量。

观察、原因与处理

观察原因或含义处理与验证
偶发高延迟新环境启动分开看冷/热请求的分布
扩容时失败下游连接或并发配额被冲击限制突发并检查下游容量
预热成本高持续占用预置实例按 SLO 与调用量权衡成本

冷启动到底耗在哪里

从请求到业务函数开始，可能经历调度执行环境、拉取或解压代码、启动语言运行时、载入依赖、执行全局初始化、建立下游连接。平台不一定暴露每段耗时，应用至少应区分初始化时间和处理时间，并用请求追踪标记是否为新环境。热实例复用可绕开部分初始化，但发布新版本、空闲回收和突发扩容仍会创建新环境。

假设一个函数的业务处理只要 30 毫秒，初始化要 700 毫秒；热请求约几十毫秒，冷请求却超过 700 毫秒。若冷请求仅占 1%，平均值仍可能很好看，但 P99 接近冷启动区间。监控应按冷/热、版本、地域与并发水平分组，观察 P95/P99 和失败率，而不是只记录平均耗时。

缓解措施与代价

措施可能收益代价或边界
精简依赖与包体缩短加载和初始化需要保证功能与可观测性
延迟初始化减少首请求非必需工作首次使用某功能时仍会等待
预置并发减少部分冷请求常驻资源和计费增加
连接复用与限流减轻下游冲击仍需处理连接失效与扩容

预热只能影响特定流量与平台行为，不能保证所有请求都热。更要注意函数扩容带来的数据库连接风暴：每个新实例都建连接，可能让下游先耗尽配额。应联合设置并发上限、连接池或代理以及数据库容量。

完整压测场景

测试包括空闲一段时间后的首请求、从零突然涌入 100 个并发、发布新版本后的第一波流量，以及下游短暂失败时的重试。分别记录端到端延迟、初始化耗时、实例创建数、连接数和错误率。若业务要求严格尾延迟，比较预置资源成本与迁移到长驻服务的成本，而不是只比较单次调用价格。

边界与误区

预置并发或预热可能降低部分冷启动，但会增加成本，也不能自动解决下游数据库连接风暴；供应商能力和计费方式应逐项核对。

把优化落到启动关键路径

先用追踪确定慢在平台调度、代码加载、应用初始化还是下游连接，不要直接把“冷启动”当作一个不可再分的数字。若大量时间花在全局导入依赖，可剔除不需要的包；若慢在启动时建立数据库连接，应检查连接创建是否可延后、可复用，以及突发实例数是否冲击数据库。延后初始化会把耗时转移到首次使用该功能，不能把它当成免费优化；要按用户真正访问的关键路径判断。

预置并发适合延迟要求严格、流量有规律的接口；低频批处理往往可以接受偶发冷启动以换取成本优势。也可以将对响应时间敏感的入口保持长驻服务，把异步处理放在 Serverless。分拆架构前要核对队列等待、重试与端到端完成时间，不要只让入口函数看起来更快。

预算一次突发扩容

假设平时保留 5 个热实例，突然有 100 个并发请求，每个实例只能同时处理 1 个请求；至少一部分请求要排队或等待新实例。即便单个冷启动只需 500 毫秒，100 个实例同时启动还可能争抢镜像下载、CPU 和数据库连接，使实际 P99 更长。压测要模拟突发到达，而不是把 100 个请求均匀摊到一分钟。比较方案时同时算预置实例费用、冷启动期间的用户损失和下游扩容能力，并记录平台并发配额与限流行为。

进一步验证

如果函数启动时需要读取密钥或配置服务，还要测这些外部依赖在冷启动路径上的延迟与失败率。把配置缓存进镜像会缩短启动，却可能带来过期和密钥轮换问题；每次启动都远程读取则更依赖控制面的稳定性。优化必须同时满足安全更新与尾延迟要求。

补充判断

测试报告应写明运行时、内存或 CPU 配额、包大小、地域、并发配额与平台版本。同一函数在这些条件变化后，冷启动分布可能明显不同；引用一次旧基准作为长期结论会误导容量规划。

第一层 · 概念与判定：冷启动到底冷在哪

冷启动指函数实例从零到能处理第一个请求的耗时。它不是一个整体，而是好几个阶段叠加，先拆开才能优化。

阶段做什么典型耗时能否优化
调度与资源准备分配容器/微虚拟机50 – 300 ms用预置并发规避
运行时初始化启动 JVM / Node / Python10 – 1000 ms换运行时（如 Go）
代码加载与初始化加载依赖、执行全局初始化10 ms – 数秒最该优化
VPC 网络配置（如启用）分配 ENI历史 1 – 10 s云厂商已大幅优化，但仍建议评估

判定原则：先看 P99 还是 P50 受影响。冷启动只影响首次请求，如果 QPS 高、实例常热，影响可忽略；如果流量稀疏或突发，冷启动会实打实反映在用户延迟上。

第二层 · 参数·命令·量化：各运行时差多少

运行时冷启动典型量级说明
Go / Rust（编译型）10 – 80 ms单二进制，最快
Node.js50 – 300 ms启动快，但依赖多时会变慢
Python100 – 500 ms导入重型库（pandas/numpy）会到秒级
Java（传统 JVM）1 – 5 sJVM 启动 + 类加载，最慢
Java（GraalVM 原生镜像）50 – 200 ms编译成原生可执行文件，接近 Go
容器镜像部署1 – 10 s拉取镜像 + 启动，比 zip 包慢一个量级

观测冷启动耗时

# 用云厂商 CLI 直接观察冷启动（以 AWS Lambda 为例）
# ① 更新代码后强制产生一次冷启动
aws lambda update-function-code --function-name myfn --zip-file fileb://fn.zip

# ② 立即调用，观察 Init Duration 字段
aws lambda invoke --function-name myfn /dev/stdout \
  --log-type Tail --query 'LogResult' --output text | base64 -d
# 日志中的关键字段：
#   Init Duration: 312.45 ms   <-- 这就是冷启动耗时
#   Duration: 8.32 ms          <-- 这是函数本身执行耗时

# ③ 连续调用第二次，Init Duration 消失 —— 实例已热
# 冷启动只发生在实例首次创建或并发扩容时

成本直觉：预置并发能彻底消除冷启动，但要为常驻实例付费。100 个预置实例、每实例 512 MB，按小时计费成本可能远超按量计费。

第三层 · 排障与边界

高频坑清单：

  • ① 把重活写在全局初始化里：如全局建数据库连接池、加载大字典，每次冷启动都重做
  • ② 依赖包过大：把整个 SDK 或全部库打进包，加载时间线性上涨
  • ③ 以为冷启动只发生一次：并发上升时每个新实例都要冷启动，突发流量会集体变慢
  • ④ 没设最小实例：流量归零后再来的第一个请求必然冷
  • ⑤ 用容器镜像而非 zip：方便但冷启动慢一个量级
  • ⑥ 在冷启动里做网络调用：拉远程配置、鉴权，把网络延迟算进冷启动

优化清单（按顺序做）：

  • ① 全局初始化只留必要的，连接改成懒加载（首次调用时建，后续复用）
  • ② 精简依赖包，移除未使用的库；Python 用 --target 只打包需要的
  • ③ 换更快的运行时（Go / Node 优于 Java / Python）
  • ④ Java 考虑 GraalVM 原生镜像或 SnapStart 类能力
  • ⑤ 对延迟敏感的核心接口配预置并发，其他接口按量
  • ⑥ 非核心路径用异步调用，让用户不等冷启动

第四层 · 原理与取舍

Serverless 一定比常驻服务慢吗？

稳态下不慢 —— 热实例的处理延迟与常驻容器几乎一样。Serverless 的代价集中在冷启动和多实例冷启动的集中爆发上。所以结论是：流量平稳时 Serverless 几乎无损，流量稀疏或突发时才明显。如果你的服务 QPS 恒定且很高，常驻容器反而更省成本。

预置并发该开多少？

按基线并发开，而不是按峰值开。比如平时 10 并发、峰值 200 并发，就预置 10–20，峰值超出部分的冷启动交给用户容忍（或异步化）。全部按峰值预置会失去 Serverless 的成本优势，那还不如直接用常驻容器。预置是为了消除常态冷启动，不是为了消除所有冷启动。

冷启动能被完全消除吗？

不能完全，只能降低概率和影响。因为以下情况必然产生新实例：并发超出现有实例数、实例被回收（通常 5–15 分钟空闲）、代码更新、可用区故障转移。能做的是：让冷启动更快（精简包、换运行时）、让它更少发生（预置并发、定时预热）、以及让它不影响用户（异步调用、预热请求）。

自检

平均延迟很低，为什么用户仍会遇到慢请求？

冷启动可能集中在尾部。需要看首请求和 P95/P99，而不只看平均值。
