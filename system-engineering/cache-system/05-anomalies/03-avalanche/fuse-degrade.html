先建立直觉：家里的空气开关

家里电器短路时，空气开关会立刻跳闸，而不是让电线烧起来。跳闸后你家这一路没电了（部分不可用），但保住了整栋楼的电路和你的电器（避免整体崩溃）。等故障排除，你再手动合上闸。

熔断就是这个空气开关：发现下游不对劲，就主动断开，不再把请求送过去，给下游喘息恢复的时间。

为什么必须「主动失败」？因为在高并发下，「等待超时」是最糟糕的选择：请求占着线程、连接池、内存不放，几秒钟就能把应用自身的线程池打满，导致故障从下游向上游蔓延（雪崩式级联故障）。快速失败虽然让用户看到一个错误，但保住了整个系统的其余部分。

熔断器的三态

状态行为转换条件
Closed 关闭正常调用下游，持续统计错误率与延迟错误率/慢调用率超过阈值 → Open
Open 打开直接返回失败或降级结果，不调用下游冷却时间结束 → Half-Open
Half-Open 半开放行少量请求做探测探测成功 → Closed；失败 → 回到 Open

降级：熔断之后给用户什么

熔断只是「不再调用」，还得回答「那返回什么」。这就是降级——准备一个兜底方案：

降级方式做法举例
返回默认值返回一个安全的空结果推荐列表返回空数组
返回静态内容用预先准备的静态数据商品页显示缓存的静态描述
返回旧快照用上一次成功的结果用本地缓存的旧值
关闭非核心功能牺牲次要功能保主流程大促时关闭「猜你喜欢」
直接报错明确告知稍后再试「服务繁忙，请稍后」
降级设计原则：核心链路优先保（下单、支付），非核心功能优先砍（推荐、评论数、个性化）。提前规划好每个接口的降级方案，而不是故障发生时临时想。

熔断 vs 限流 vs 降级

手段触发依据动作保护对象
熔断下游错误率/延迟断开调用，快速失败下游服务
限流自身 QPS拒绝超额请求自身服务
降级熔断/限流触发后返回兜底结果用户体验
它们是一条流水线：限流挡住过多流量 → 熔断发现下游不对劲就断开 → 降级负责断开后给用户什么。三者常一起出现，但职责不同。

缓存场景中的具体用法

  1. Redis 宕机 → 对 Redis 调用熔断，避免每次请求都等连接超时；
  2. 降级为「直接查库」或「查本地缓存」，同时限流保护数据库；
  3. 数据库压力仍过大 → 对数据库也熔断，返回兜底静态内容；
  4. Redis 恢复后，半开探测成功 → 自动切回正常链路。
别把熔断当万能药。熔断的代价是用户体验下降。阈值设置过灵敏会频繁误跳闸（明明只是网络抖动），过迟钝则起不到保护作用。需要结合实际 SLA 调优，并配置告警让人介入。

🎯 面试问答

Q：熔断和限流到底有什么区别？
A：看触发依据：熔断看的是下游的健康状况（错误率高不高、响应快不快），是「对方病了我就不找它了」；限流看的是自己的请求量（QPS 超没超），是「我自己扛不住了所以不接了」。熔断保护下游，限流保护自己。二者常配合使用。

Q：为什么要有 Half-Open 半开状态？
A：因为不能直接从 Open 跳回 Closed。如果熔断一结束就把全部流量放回去，而下游其实还没恢复，会立刻再次打垮它，陷入「熔断→恢复→再熔断」的震荡。半开状态先放少量探测请求验证下游是否真的好了，成功才逐步放量，失败则继续熔断。这是安全恢复的必要缓冲。

Q：熔断阈值一般怎么设？
A：没有固定值，要基于实际 SLA 调。常见起点：错误率超过 50%（或慢调用率超过 50%）且最小请求数达标（比如 10 秒内至少 20 个请求，避免样本太少误判），持续一段时间则跳闸；冷却时间 5~30 秒。最小请求数这个条件很容易被忽略，但它是防止低流量误跳闸的关键。

Q：降级方案应该什么时候设计？
A：必须提前设计，而不是故障时才想。做法：梳理核心链路，给每个外部依赖（Redis、MySQL、第三方 API）都明确写好降级分支，并定期演练。很多事故的真正教训不是「没有熔断」，而是「熔断了但降级分支返回了 null，导致上层空指针，反而引发更大故障」。

熔断与降级的关键参数

参数典型值说明
错误率阈值50%超过则打开熔断；Hystrix 默认 50%
最小请求数20（Hystrix 默认）样本太少不触发；防冷启动误熔断
滑动窗口10s 或 100 个请求统计窗口
熔断时长（sleep window）5s打开后多久进入半开
半开状态允许的请求1~3 个试探性放行；成功则关闭熔断
超时时间1~3s单次调用超时计入失败
并发隔离信号量 / 线程池限制对某依赖的并发数
降级策略返回默认值 / 缓存值 / 空结果必须预先定义而不是抛异常

熔断的三个状态：① Closed（正常）：统计错误率；② Open（打开）：直接拒绝所有请求（不再调用下游，快速失败），持续 sleep window；③ Half-Open（半开）：放行少量请求试探，成功则关闭、失败则重新打开。Open 状态不消耗任何下游资源，这是熔断与重试的本质区别。

熔断与重试是矛盾的：重试会增加下游压力，熔断是保护下游。正确顺序是先熔断后重试——熔断打开时连重试都不做，直接降级。

实现与配置

# Go：sony/gobreaker
import "github.com/sony/gobreaker"

var cb *gobreaker.CircuitBreaker

func init() {
    settings := gobreaker.Settings{
        Name:        "userService",
        MaxRequests: 3,                    // 半开状态允许的请求数
        Interval:    10 * time.Second,     // 统计周期（0 表示不重置计数）
        Timeout:     5 * time.Second,      // 打开状态持续多久后进入半开
        ReadyToTrip: func(counts gobreaker.Counts) bool {
            // 请求数 >= 20 且错误率 > 50% 才熔断
            return counts.Requests >= 20 &&
                   float64(counts.TotalFailures)/float64(counts.Requests) > 0.5
        },
    }
    cb = gobreaker.NewCircuitBreaker(settings)
}

func GetUser(id int64) (*User, error) {
    v, err := cb.Execute(func() (interface{}, error) {
        return callUserService(id)         // 可能失败的下游调用
    })
    if err == gobreaker.ErrOpenState {
        return getCachedUser(id)           // 降级：返回缓存或默认值
    }
    if err == gobreaker.ErrTooManyRequests {
        return nil, errors.New("too many half-open requests")
    }
    return v.(*User), err
}
# Java：Resilience4j 配置
resilience4j.circuitbreaker:
  instances:
    userService:
      slidingWindowType: COUNT_BASED
      slidingWindowSize: 100           # 统计最近 100 个请求
      minimumNumberOfCalls: 20         # 最少 20 个才计算错误率
      failureRateThreshold: 50         # 错误率 > 50% 熔断
      waitDurationInOpenState: 5s      # 打开状态持续 5 秒
      permittedNumberOfCallsInHalfOpenState: 3
      automaticTransitionFromOpenToHalfOpenEnabled: true
  # 注意：4xx 一般是客户端错误，不应计入熔断
  # 需要配置 ignoreExceptions 或 recordExceptions 区分

# Sentinel（阿里）的熔断：支持慢调用比例
#   慢调用比例 > 50% 且 最小请求数 > 5 -> 熔断
#   这比只看错误率更合理（下游变慢往往比报错更致命）

排障清单

症状原因处理
不该熔断时熔断了最小请求数太小；或 4xx 被算作失败提高 minimumNumberOfCalls；4xx 不算失败（5xx 才算）
熔断后一直不恢复半开请求仍失败；或状态没自动切换检查下游是否真的恢复；确认 half-open 转换配置
熔断了但仍有请求打到下游没在正确位置接入熔断要包裹整个下游调用，包括重试
降级返回的数据太旧缓存值过期太久降级数据单独设 TTL；或返回「服务暂不可用」而不是旧数据
重试 + 熔断导致放大熔断未打开时重试放大流量重试要有重试预算（如不超过总请求 10%）
全链路都熔断了一个下游挂了导致雪崩式熔断这是预期行为（保护系统）；关键是降级要可用
没有监控熔断状态只看到了请求失败必须监控熔断状态变化并告警

降级的三个层次：① 返回备用数据（缓存/默认值）—— 体验最好；② 返回部分结果（如只显示已有字段）；③ 直接拒绝并提示「稍后重试」。降级方案必须在设计阶段就定好，不能出故障时才想。
