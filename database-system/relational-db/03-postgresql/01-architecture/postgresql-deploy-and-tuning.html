02关键参数（按内存量级调）

参数常见值控制什么
shared_buffers物理内存 25%共享缓冲，缓存数据页
effective_cache_size物理内存 50~75%优化器估算的系统缓存
work_mem16~64MB/算子排序/哈希内存，过大会 OOM
max_connections100~500最大连接数，配连接池可压低
wal_buffers16MBWAL 写入缓冲
checkpoint_timeout5~15min检查点频率，影响写抖动
要点：max_connections 别盲目开到几千：每个连接都占内存。正解是前面架 pgbouncer，应用连池子，PG 只保持少量真实连接。

03慢查询与膨胀排查

膨胀大就 VACUUM（或 autovacuum 没跟上时手动 VACUUM FULL，但会锁表，挑低峰做）。

-- 1) 找慢 SQL：先开 auto_explain 或手动 EXPLAIN ANALYZE
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id=123;

-- 2) 看锁等待
SELECT pid, usename, state, wait_event_type, query
FROM pg_stat_activity WHERE wait_event_type='Lock';

-- 3) 看表/索引膨胀（粗略）
SELECT schemaname, relname, n_dead_tup, n_live_tup
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;

04备份与基础运维

  • 物理备份：pg_basebackup 做基础备份 + WAL 归档做 PITR。
  • 逻辑备份：pg_dump 单库/单表，便于跨版本迁移。
  • 监控：pg_stat_statements 统计最耗时 SQL（需提前 CREATE EXTENSION）。
问：为什么改了参数没生效？

很多参数是 `postmaster` 级，要重启；`sighup` 级只需 reload；`user`/`superuser` 级可在会话内 SET。改前先看 `pg_settings.context`，别白等 reload。

第一层 · 概念与判定：先找受限资源

PG 调优先问瓶颈在内存（shared_buffers/work_mem）、连接、IO（checkpoint）、还是统计/执行计划。盲目调参不如先定位。

症状怀疑点
大量磁盘读、缓存命中低shared_buffers 偏小
复杂查询报内存错/变慢work_mem 不足
连接数高、CPU 闲连接风暴/缺连接池
写入抖动、checkpoint 慢checkpoint/WAL 设置

第二层 · 参数·命令·量化：核心参数与经验值

参数经验取值作用
shared_buffersRAM 的 25%PG 自身缓存
effective_cache_sizeRAM 的 50%–75%帮优化器估缓存命中
work_mem每操作用量排序/哈希，别设太大
max_connections配合连接池设小直连过多拖垮
checkpoint_timeout5–15 min控制刷盘频率

PostgreSQL 核心调优参数

-- postgresql.conf 关键项
shared_buffers = 4GB                 -- 机器 16G 时取 25%
effective_cache_size = 12GB          -- 50%-75% RAM
work_mem = 64MB                      -- 每个排序/哈希操作，连接多时要小
max_connections = 100                -- 别直连爆，前面加 pgbouncer
checkpoint_timeout = 10min
wal_buffers = 16MB

-- 看缓存命中率（应 > 99%）
SELECT sum(heap_blks_hit)/(sum(heap_blks_hit)+sum(heap_blks_read)) FROM pg_stat_database;

数量级：shared_buffers 经验上限约 RAM 的 25%–40%（再大边际收益骤降）；work_mem 是每操作额度，100 连接各开 10 个排序就是 1000 倍，极易撑爆内存——要小。

第三层 · 排障与边界：四个坑

  • 连接风暴：max_connections 高 + 应用直连，短连接风暴打满，正确做法是前面挂 pgbouncer 连接池复用
  • work_mem 设太大：它是每操作额度，乘上并发就是天文数字，OOM 或 swap 反而更慢——宁小勿大
  • autovacuum 滞后：MVCC 旧版本不清理，表膨胀、索引失效、查询变慢——监控 pg_stat_user_tables 死元组
  • 统计信息过期：没定期 ANALYZE，优化器选错执行计划（全表扫代替索引）——看 default_statistics_target

第四层 · 原理与取舍

为什么 PG 前面一定要加连接池（pgbouncer）？

因为每个 PG 连接是一个后端进程，占内存且上下文切换贵；应用直连高并发时连接数爆炸，CPU 花在进程调度而非干活。pgbouncer 用少量常驻连接服务大量应用连接（事务级复用），把连接数压到数据库舒适区。所以 max_connections 该设小，连接池扛前面。

shared_buffers 为什么不是越大越好？

因为 PG 的数据还会借操作系统的页缓存（OS cache），二者互补。shared_buffers 太大，OS 页缓存被挤、且 PG 自身管理开销上升，边际收益在 25%–40% RAM 后急剧下降。effective_cache_size 则是告诉优化器「OS 层还有多少缓存可用」，帮它更准确地选索引还是顺序扫。

MVCC 为什么必须用 autovacuum 兜底？

PG 的 MVCC 更新/删除不直接改原行，而是留旧版本，旧版本要靠 vacuum 回收。不回收会导致表/索引膨胀、死元组累积、索引失效、查询越跑越慢，甚至事务 ID 回卷（xid wraparound）威胁数据可用。autovacuum 就是后台自动做这件事的保命机制。
