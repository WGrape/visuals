MySQL 执行器详解

输入是优化器给的执行计划（AccessPath 树），输出是一行行的结果——中间靠一棵 RowIterator 树把它们跑出来

① 先给结论 ② 输入：AccessPath ③ 计划 → 迭代器树 ④ 统一接口 RowIterator ⑤ 火山模型怎么跑 ⑥ 常见迭代器清单 ⑦ 新老执行器对比 ⑧ 输出是什么 ⑨ 执行过程演示 ⑩ 怎么观察 / 速记
①先给结论：输入是什么，输出是什么

执行器在整条 SQL 链路里的位置非常明确：它夹在优化器和存储引擎之间，是一个「照着图纸干活」的部件。

⬅ 输入：执行计划

优化器产出的AccessPath 树——一棵描述「先访问哪张表、用什么访问方式、怎么 JOIN、怎么排序」的计划树。它不是 EXPLAIN 打出来的那张表（那只是计划的一种展示形式）。详见 ②。

➡ 输出：结果

对 SELECT：一行行的结果行，边算边发给客户端（流式，不先把整个结果集攒在内存里）。
对 INSERT/UPDATE/DELETE：影响行数，并且真正去改存储引擎里的数据。详见 ⑧。

一句话
执行器 = 把「计划树」翻译成「一行行数据」的机器。它不做决策，只做执行；它的核心机制是迭代器（Iterator）模型。
②输入到底是什么：执行计划 = AccessPath 树

先破一个常见误解：执行计划不是 EXPLAIN 那张表格。EXPLAIN 只是把计划打印成人类可读的形式；计划本身在内存里是一棵 AccessPath 树，由优化器在 Optimize 阶段生成。

在 MySQL 8.0 的源码里，AccessPath 大致长这样（简化）：

struct AccessPath {
  // ① 这一步是什么类型的操作
  enum Type : uint8_t {
    TABLE_SCAN, INDEX_SCAN, REF, REF_OR_NULL, EQ_REF,
    ... MRR, ... DELETE_ROWS, UPDATE_ROWS
  } type;

  // ② 优化器估算出来的代价
  double cost{-1.0};

  // ③ 不同类型各自需要的参数（用 union 省空间）
  union {
    struct { TABLE *table; } table_scan;
    struct { TABLE *table; int idx; bool use_order; bool reverse; } index_scan;
    ...
  } u;
};
所以「计划」到底描述了什么
每个 AccessPath 节点回答三件事：做什么操作（type，比如全表扫 / 索引扫 / 等值引用）、对谁做（union 里的表、索引、方向等参数）、大概多贵（cost）。把这些节点按父子关系串起来，就是一条完整的取数路线。
注意：cost 是估算值，执行器并不用它
cost 是优化器挑路时用的依据；一旦计划定下来，执行器就只是照着走，运行时不再看 cost。想知道真实耗时和行数，要看 EXPLAIN ANALYZE（见 ⑩）。
③计划怎么被执行：AccessPath → RowIterator 树

执行器拿到 AccessPath 树后，会把它「翻译」成一棵迭代器树：每个 AccessPath 节点对应创建一个 RowIterator 对象，父子关系保持不变。

为什么叫「编译」
因为这一步是静态的翻译：把「描述怎么做」的数据结构，变成「真的会做」的对象。翻译完成后，执行就只剩下反复调用同一套接口——这正是迭代器模型的好处。
④统一接口：所有迭代器都只有这几个方法

MySQL 8.0 把执行器重写的第一件事，就是定一个通用 C++ 基类 RowIterator。不管是全表扫描、索引查找、JOIN、排序还是聚合，全都继承它、实现同一套接口：

class RowIterator {
 public:
  // 打开：申请资源、定位到起始位置；可重复调用以重置
  virtual bool Init() = 0;

  // 拉一行：把下一行读进记录缓冲。返回 0 = 拿到一行，-1 = 没有更多行了
  virtual int Read() = 0;

  // 设置 NULL 行标记（外连接补 NULL 时用）
  virtual void SetNullRowFlag(bool is_null_row) = 0;

  // 释放行锁：某行被过滤掉后，允许在低隔离级别下提前放锁
  virtual void UnlockRow() = 0;
};
方法作用关键点
Init()打开资源、做好取数准备可以被反复调用，每次调用都会把迭代器重置回起点。像 SortingIterator 就是把「排序」这件事放在 Init() 里做
Read()取下一行整个执行器的心脏。返回 0 表示拿到一行，返回 -1 表示数据取完了（EOF）
SetNullRowFlag()标记「这行是补出来的 NULL 行」外连接（LEFT JOIN）里右表无匹配时要补 NULL，靠它标记
UnlockRow()释放该行的锁行被 WHERE 过滤掉后，在较低隔离级别下可以提前放锁，减少锁持有时间
⑤火山模型：一行一行「拉」出来

这套 Init → Read → Read → … → 结束 的套路，就是数据库里经典的 Volcano（火山）模型 / 迭代器模型：每个关系运算都实现成迭代器，暴露 open → next → close 协议；MySQL 里对应 Init → Read → End。

执行主循环（语义化）

// 执行器入口，语义化伪代码
if (root->Init()) return error;      // 打开整棵树

while (root->Read() == 0) {        // 每拉一次 = 得到一行结果
    send_row_to_client(...);       // 立刻发走，不攒着
}

root->End();                        // 收尾，释放资源
这个模型带来的三个直接好处
  • 流式、省内存。行是一行一行往上冒的，不必先把中间结果全部物化。根拿到第 1 行就能发给客户端。
  • 可自由组合。每个迭代器只关心「我从儿子拉一行、加工后交给父亲」，接口统一，拼装新算子很容易。
  • 易扩展也易观测。想加测量（如 EXPLAIN ANALYZE）只要在迭代器外面包一层计时/计数的壳，不用改算子本身。
别和「推送」搞混
老执行器里混用了推和拉（有的算子推数据、有的拉数据），这也是它难维护的原因之一。新的迭代器执行器是统一的拉取模型：永远是父亲向儿子要。
⑥常见迭代器清单

MySQL 8.0 实现的迭代器有很多，按职责大致分几类（下面是其中常见的代表）：

类别迭代器干什么
取数
（叶子节点）		TableScanIterator全表顺序扫描，调存储引擎 ha_rnd_next 一行行取
IndexScanIterator全索引扫描，用 ha_index_next / ha_index_prev
IndexRangeScanIterator索引范围扫描，包装了老的 QUICK_SELECT_I
ConstIterator / FakeSingleRowIterator常量表（优化期已确定最多一行）取数
连接NestedLoopIterator嵌套循环连接（内连接 / 外连接 / 反连接）
RefIterator / EQRefIterator用某个键去右表取匹配行（ref / eq_ref）
RefOrNullIterator类似 ref，但要额外处理 NULL 的情况
HashJoinIterator哈希连接（8.0.18+）：也只是「另一个迭代器」，内存够就在内存做，不够就落盘
排序SortingIterator排序；排序动作发生在 Init() 里
SortBufferIterator / SortFileIterator从内存缓冲 / 临时文件里读已排好序的结果

AggregateIterator聚合，以及可选的分组
LimitOffsetIterator实现 LIMIT ... OFFSET

留意「物化」这个例外
流式是常态，但不是所有算子都能流式。排序必须先把数据收齐才能排；哈希连接要先建哈希表。MaterializeIterator、SortingIterator 这类节点会在内部先把数据攒起来——这也是为什么某些查询会突然产生临时表或落盘（Using temporary / Using filesort）。
⑦为什么要重写：新执行器 vs 老执行器

MySQL 8.0 之所以要大改执行器，是因为老实现里有六套各自为政的抽象，混着 C++ 类和 C 函数指针：

老的抽象负责什么
QUICK_SELECT_I各种基于索引的访问方式（range scan、index merge、group min/max）
READ_RECORD包装全表扫、全索引扫、sort buffer 结果等的读取
QEP_TAB（read_first_record）各种连接访问类型（REF / EQ_REF / 全文等）
QEP_operation临时表、join buffer（BNL / BKA）
QEP_TAB::next_select嵌套循环连接、GROUP BY 等
Query_resultUNION、EXISTS 提前结束、把结果发给客户端

❌ 老实现的问题

  • 没有统一接口，扩展性差
  • 实现方式不统一（C 函数指针 + C++ 类混用）
  • 抽象层次不清，代码难读难懂
  • 耦合度高，后续难以优化
  • 推送与拉取两种数据模型混用
  • 排序、去重、物化等操作甚至绕开了这些抽象，用特殊代码写

✅ 新实现的改进

  • 统一的 C++ 基类 RowIterator
  • 所有算子同一种写法，一套接口
  • 统一的拉取（Pull）模型
  • 算子可自由组合，加新算子容易
  • 天然支持在外面包一层做测量（EXPLAIN ANALYZE 就是这么实现的）
  • 逐行流式，内存占用更可控
⑧输出到底是什么

SELECT：一行行结果

根迭代器每 Read() 出一行，就交给结果发送逻辑立刻发给客户端。所以：

  • 客户端往往还没等查询跑完就已经收到前几行了；
  • 服务端不需要为整个结果集准备一大块内存；
  • 但如果上层还需要排序/去重，就会被迫先攒齐（见 ⑥ 的物化）。

DML：改动 + 影响行数

INSERT / UPDATE / DELETE 走的是对应的 DELETE_ROWS、UPDATE_ROWS 等计划节点：读到的行不发给客户端，而是交给存储引擎去改，并累计影响行数返回。

这也是为什么一条 UPDATE 的执行计划里，前面照样是「扫描 + 过滤」——先把要改的行捞出来，再改。

记住：输出是「行」，不是一个完整结果对象
无论 SELECT 还是 DML，执行器的产出粒度都是行。SELECT 的行流向客户端，DML 的行流向存储引擎。这个统一的「逐行」视角，正是迭代器模型的核心。

演示里值得注意的三件事
  • 被 WHERE 过滤掉的行不会「攒着」——过滤发生在行往上冒的过程中，不合格就丢弃并继续拉下一行。
  • 连接是「左边取一行、右边按 key 找匹配」——这就是嵌套循环的本质，也是为什么右表有索引时快得多。
  • 结束靠叶子返回 EOF——t1 扫完了，Read() 返回 -1，这个「没了」的信号会一路传回根，整棵树的执行就结束了。
⑩怎么观察执行器 + 速记

EXPLAIN FORMAT=TREE：直接看迭代器树

普通 EXPLAIN 给的是表格；FORMAT=TREE 给的是接近迭代器树形状的缩进输出，最能反映执行器实际拿到的是什么。

EXPLAIN FORMAT=TREE
SELECT * FROM t1 JOIN t2 ON t1.a = t2.a;

-> Inner hash join (t2.a = t1.a)  (cost=0.70 rows=1)
    -> Table scan on t2  (cost=0.35 rows=1)
    -> Hash
        -> Table scan on t1  (cost=0.35 rows=1)

EXPLAIN ANALYZE（8.0.18+）：真跑一遍并测量

它会在迭代器外面包一层测量节点，然后真正执行查询，输出实际的首行时间、末行时间、行数和循环次数：

EXPLAIN ANALYZE SELECT * FROM t1 JOIN t2 ON t1.a = t2.a;

-> Inner hash join (t2.a = t1.a) (cost=0.70 rows=1)
   (actual time=0.441..0.441 rows=0 loops=1)
    -> Table scan on t2 (cost=0.35 rows=1) (never executed)
    -> Hash
        -> Table scan on t1 (cost=0.35 rows=1)
           (actual time=0.220..0.220 rows=0 loops=1)
⚠ EXPLAIN ANALYZE 会真的执行这条 SQL
对 SELECT 只是多跑一遍；但对 UPDATE / DELETE，数据会被真的改掉。别在生产库上对写操作直接用它。

速记

问题答案
输入是什么优化器产出的AccessPath 执行计划树（不是 EXPLAIN 表格）
输出是什么SELECT → 一行行结果（流式发给客户端）；DML → 对存储引擎的改动 + 影响行数
怎么执行计划树 → RowIterator 迭代器树 → 火山/拉取模型跑起来
统一接口Init() 打开（可重置）、Read() 取一行（0=有行，-1=结束）、SetNullRowFlag()、UnlockRow()
数据怎么流动控制流向下问、数据流向上冒，每次一行（Pull 模型）
为什么 8.0 要重写老实现六套抽象混用 C 函数指针、推拉混用、难扩展；新实现统一 C++ 接口 + 统一 Pull
什么时候不能流式排序、去重、物化、哈希建表等必须先攒齐数据
怎么观察EXPLAIN FORMAT=TREE（看树形计划）、EXPLAIN ANALYZE（真跑并测量，写操作慎用）
一句话记住执行器
优化器决定「怎么走」，执行器负责「走一遍」——它拿到一棵 AccessPath 计划树，翻译成 RowIterator 树，然后从根开始一行一行往外拉，直到叶子说「没了」。
