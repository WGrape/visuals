①DDL 的三类操作与代价量级

DDL 操作数据字典而非数据本身，但「要不要动已有行」决定了它的代价量级。 理解这个分界，才能预判一次 ALTER 是毫秒级还是小时级。

类型例子是否重写表典型代价
仅改元数据（instant）改默认值、改名、改注释、加枚举末尾值否毫秒~秒，只锁字典
需重建索引但不改行加/删二级索引（部分实现支持 online）否（行不变）与表大小成正比，可在线
必须重写全表改列类型、改字符集、加列（老版本）、改主键是小时级 + 双倍空间 + 长时间锁
各版本差异极大，不要凭记忆操作。MySQL 8.0 引入了 instant ADD COLUMN（只改元数据）， 但只支持加在末尾等有限场景；PostgreSQL 11+ 加带默认值的列是即时的（默认值存字典）， 老版本会重写全表。执行前先确认你那个版本的官方行为表，并在从库/测试库实测。
-- 加列：确认是 instant 还是 rebuild（MySQL 8.0）
ALTER TABLE t ADD COLUMN c INT DEFAULT 0, ALGORITHM=INSTANT;   -- 成功=元数据操作
ALTER TABLE t ADD COLUMN c INT DEFAULT 0, ALGORITHM=INPLACE, LOCK=NONE;

-- PostgreSQL 11+：带默认值的加列是即时的，不需要重写
ALTER TABLE t ADD COLUMN c INT DEFAULT 0;   -- 已有行的值从字典取，不写盘

②在线变更：三种流派

原生 Online DDL

数据库自带的 ALGORITHM=INPLACE, LOCK=NONE / CONCURRENTLY。 优点是不引入外部依赖；缺点是支持的操作有限、大表仍会产生大量 IO 和复制延迟， 且失败回滚代价高。

外部工具（影子表）

pt-online-schema-change、gh-ost：建影子表 → 拷贝数据 → 用触发器或 binlog 追增量 → 重命名切换。 几乎不锁表、可控流，是生产大表的首选。缺点是需要额外磁盘空间、有切换瞬间的短暂锁。

停机变更

维护窗口内直接执行。最简单、最可控，适合能接受停机的中小系统， 或有从库可先切流量再改的场景。

选型口径：小表（几十万行内）直接 ALTER； 大表且操作被原生 online 支持 → 先试原生；大表 + 需要改列类型/字符集 → 上 gh-ost/pt-osc； 无论哪种，先在从库或影子环境演练并计时。

③五个高风险点

  1. 主从延迟：大表 DDL 在从库单线程回放时会造成显著延迟，读写分离架构下用户会读到旧数据。
  2. 空间翻倍：重建表需要额外的表大小空间 + binlog/undo，磁盘不足会在中途失败。
  3. 元数据锁（MDL）：DDL 要等所有对该表的事务结束；反过来它开跑后会阻塞后续所有查询。 一个忘记提交的长事务就能把整个表的访问堵死。
  4. 外键与触发器：带外键的表做 DDL 常被迫退化成 COPY 方式，且会级联检查。
  5. 应用兼容性：删列/改名后，还没发版的老代码会报错。正确顺序是 先让代码不再依赖该列 → 发版 → 观察 → 再删列（扩缩容式变更）。
最实用的一条检查：执行 DDL 前先查有没有长事务—— MySQL 看 information_schema.innodb_trx，PostgreSQL 看 pg_stat_activity 里 state <> 'idle' 且持续时间长的会话。 有长事务时开 DDL，等于主动制造一次全表阻塞。

Q：为什么大表加个索引也要小心？
A：建索引要扫描全表并排序，期间持有锁（版本相关）、产生大量 redo/undo 与 binlog， 在从库回放会造成延迟，还可能触发主从切换后的长时间恢复。用 CREATE INDEX CONCURRENTLY（PG）或 ALGORITHM=INPLACE, LOCK=NONE（MySQL）能减轻， 但仍有 IO 与复制延迟代价。

DDL 算法

-- 显式指定算法，避免优化器选错
ALTER TABLE orders ADD COLUMN remark VARCHAR(200), ALGORITHM=INSTANT;
ALTER TABLE orders ADD INDEX idx_user (user_id), ALGORITHM=INPLACE, LOCK=NONE;

-- ALGORITHM: DEFAULT / INSTANT / INPLACE / COPY
-- LOCK:      DEFAULT / NONE / SHARED / EXCLUSIVE
-- 指定 ALGORITHM=INSTANT 时若不支持会<strong>直接报错</strong>（而不是退化成 COPY）
--   这反而是好事：避免你以为秒级完成，实际锁表几小时

-- 检查 DDL 进度（8.0）
SELECT * FROM performance_schema.events_stages_current
WHERE event_name LIKE 'stage/innodb/alter%';

MDL 锁（元数据锁）是 DDL 最危险的陷阱：即使 DDL 本身不锁表，它也要先拿到 MDL 写锁。若此时有一个长事务持有读锁，DDL 会一直等待，且后续所有查询都会被这个 DDL 阻塞（MDL 是公平的，后来的要排队）——这就是“一个慢查询导致全表不可访问”的经典故障。所以执行 DDL 前必须先检查有无长事务。

大表变更的安全流程

步骤动作工具/命令
1. 检查长事务确认无超过 10 秒的事务information_schema.innodb_trx
2. 检查磁盘剩余空间 > 表大小 × 1.5df -h
3. 选工具大表用在线变更工具gh-ost / pt-osc
4. 限速控制对主库的影响--max-load / --chunk-size
5. 观察延迟从库延迟不超阈值Seconds_Behind_Master
6. 切换原子 rename工具自动完成

在线变更工具

# gh-ost：通过解析 binlog 同步增量，无需触发器
gh-ost \
  --alter="ADD COLUMN remark VARCHAR(200)" \
  --database=mydb --table=orders \
  --host=127.0.0.1 --user=gh --password=xxx \
  --max-load=Threads_running=50 \      # 主库压力大时自动暂停
  --critical-load=Threads_running=100 \
  --chunk-size=1000 \                   # 每批拷贝行数
  --throttle-flag-file=/tmp/ghost.pause \  # 创建该文件即暂停
  --execute

# pt-online-schema-change：基于触发器
pt-online-schema-change \
  --alter "ADD INDEX idx_user (user_id)" \
  D=mydb,t=orders \
  --chunk-size=1000 --max-load=Threads_running=50 \
  --execute

# 两者对比：
#   gh-ost    ：无触发器（对主库影响小），依赖 binlog（需 ROW 格式）
#   pt-osc    ：用触发器（增加主库写入负担），但适用性更广

为什么不能直接 ALTER 大表：即使 8.0 的 INPLACE，建索引仍要全表扫描，亿级表可能耗时小时级，期间锁等待与复制延迟都不可控。在线变更工具把操作拆成可限速、可暂停、可回滚的小批次，是生产唯一可接受的方案。

安全加字段流程

-- 安全的“加非空字段”流程（避免锁表太久）
-- 1) 先加可空字段（INSTANT，秒级）
ALTER TABLE orders ADD COLUMN status TINYINT DEFAULT NULL, ALGORITHM=INSTANT;
-- 2) 分批回填（控制事务大小，避免长事务与主从延迟）
UPDATE orders SET status = 1 WHERE status IS NULL AND id BETWEEN 1 AND 10000;
--   循环推进，每批 1 万行，批间 sleep 控制速率
-- 3) 最后改约束（此时无 NULL，瞬间完成）
ALTER TABLE orders MODIFY COLUMN status TINYINT NOT NULL DEFAULT 1, ALGORITHM=INPLACE;

-- 关键：不要一步到位 ADD COLUMN ... NOT NULL DEFAULT 1
--       老版本会重建整表并锁表

自检 Q&A

Q：为什么一个 SELECT 慢查询会导致 ALTER 卡住，然后全表不可用？

A：这是 MDL 锁队列问题。慢查询持有 MDL 读锁 → ALTER 申请 MDL 写锁被阻塞 → 后续所有 SELECT 申请读锁时发现有写锁在等待，也必须排队（MySQL 的 MDL 是公平队列，防止写锁饿死）。于是整个表的访问全部卡死。解法：① 执行 DDL 前查 innodb_trx 确认无长事务；② 给 DDL 设 lock_wait_timeout（如 10 秒），拿不到就放弃而不是无限等。

Q：加索引会锁表吗？

A：MySQL 5.6+ 的 InnoDB 在线加索引（ALGORITHM=INPLACE, LOCK=NONE）允许并发读写，不会锁表。但它仍要扫描全表构建索引树，会消耗大量 IO 与 CPU，并产生大量 redo/undo 日志，可能导致主从延迟。所以大表加索引仍建议在低峰执行，或用在线变更工具限速。

Q：gh-ost 和 pt-osc 选哪个？

A：优先 gh-ost。原因是它不用触发器——pt-osc 在原表上建三个触发器（INSERT/UPDATE/DELETE），会显著增加主库写入开销，且触发器本身有各种限制（如原表已有触发器就不行）。gh-ost 通过伪装成从库读取 binlog来同步增量变更，对主库影响小得多。前提是需要 binlog 为 ROW 格式且 binlog_row_image=FULL。

Q：删字段有什么风险？

A：两个——① 应用没改完就删：只要还有一个服务在 SELECT 该字段，就会立即报错（这是最常踩的，务必先全量灰度确认无引用）；② 磁盘空间不释放：InnoDB 删除字段后，已分配的表空间不会自动归还操作系统（需要 OPTIMIZE TABLE 重建，而这又会锁表）。所以生产上更常见的做法是先改名（标记为废弃）观察一段时间，确认无影响后再真正删除。
