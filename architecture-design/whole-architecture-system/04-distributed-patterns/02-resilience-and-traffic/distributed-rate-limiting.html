单机限流的误差有多大

最直觉的集群限流方案是「每台机器限 N QPS，全局就是 节点数 × N」。这个算法在三种情况下会显著偏离预期。

情况发生了什么实际 vs 预期
负载不均负载均衡有粘性（会话保持、一致性 hash），某台分到 2 倍流量该机先触发限流，其他机器还有余量 —— 全局提前被限，总吞吐偏低
扩缩容节点从 8 台扩到 20 台，但每台仍按旧阈值限流新扩容的容量用不上，要么人工改配置，要么全局超限
流量倾斜某个热点 key 的请求全打到少数几台整体 QPS 远未达上限，但热点分片已经过载

结论：单机限流只能保证「单机不被打垮」，无法保证「全局按计划放行」。要做配额控制（如开放 API 的 1000 次/分钟），必须有集群维度的计数。

三种主流方案

集群限流的核心矛盾是：计数要集中（才准），但请求要本地决策（才快）。三种方案在这一点上各有取舍。

方案做法精度每次请求开销失效风险
集中计数（Redis + Lua）令牌桶/计数器存 Redis，用 Lua 脚本保证「读-算-写」原子精确一次网络往返，典型 0.3~1 msRedis 挂了需降级为单机限流
网关统一限流在 API Gateway 单点做计数与限流精确几乎为零（同步调用前已判断）网关自身成为瓶颈与单点
本地均分 + 定期协调每台按 总配额/节点数 本地限流，定期（如 10 s）由中心校正有偏差，约 ±10%~20%零（纯本地内存）协调中心挂了可继续用旧值

选型口诀：精度要求高且 QPS 不高（< 5 万）→ Redis+Lua；已在网关层且网关性能充足 → 网关统一；超高 QPS 或对延迟极敏感 → 本地均分，接受一定误差。

Redis + Lua 的实现细节

这是最通用的方案，关键在于必须用 Lua 保证原子性，否则「判断 + 扣减」两步之间会被并发插入。

集群限流的典型链路：所有判定逻辑压进一次 Redis 调用

三个必须注意的点：

  1. 用 EVALSHA 而非 EVAL：脚本只需首次加载，后续传 SHA1，省去每次传输脚本正文的网络开销。
  2. key 要带上时间窗口：rate:{user}:{window_start}，配合 TTL 自动过期，避免历史数据堆积。
  3. Redis 不可用时要有降级：不能因为限流组件挂掉就全站不可用。常见策略是 Redis 超时（如 50 ms）就直接放行，同时告警；或者降级为本地保守限流。

热点与倾斜：集群限流的难点

即使计数准确，还有一个绕不开的问题：单个 key 的流量可能全部落在少数分片上。

Redis 单分片瓶颈

集群 Redis 里，一个 key 只会落在一个分片。若某热点用户 QPS 达 5 万，该分片的 CPU 会被这个 key 打满，其他 key 也跟着变慢。

拆分 key

把 u:123 拆成 u:123:0..15 共 16 个子 key 分散到不同分片，计数时求和。代价是读写成本 ×16。

本地 + 全局二级

先本地计数拦截大部分请求，只有本地放行时才去 Redis 校验全局配额。能把 Redis 压力降低一到两个数量级。

推荐架构：本地预限 + 全局精限。本地按 全局配额/节点数 × 1.2 先拦一道（宽松），通过的再走 Redis 精确计数。这样既挡住了绝大部分流量，又保证了精度。

深入自检

为什么不用 INCR + EXPIRE 两步，非要写 Lua？

因为两步不原子。典型竞态：请求 A 执行 INCR 得到 1，还没执行 EXPIRE 就崩溃了 —— 这个 key 永远不过期，该用户的配额被永久锁死。反过来，若并发下先 EXPIRE 再 INCR，也会重置别人的计数。所有「读-算-写」序列都必须放进单个 Lua 脚本，Redis 保证脚本执行的原子性。

滑动窗口怎么在 Redis 里实现？

用 ZSET 存时间戳：每次请求 ZADD key ts ts，再 ZREMRANGEBYSCORE key 0 (now-window) 清掉过期项，最后 ZCARD 得到窗口内请求数。三个操作同样要放进 Lua。代价是内存开销大：窗口 60 s、QPS 1000 就要存 6 万个成员。高 QPS 场景改用令牌桶（只存 last_time 与 tokens 两个字段），内存是常数级。

限流应该放在网关还是服务内？

两处都要，但职责不同。网关做粗粒度、租户级、防刷与配额控制，保护整个系统不被外部打穿；服务内做细粒度、依赖级、自适应保护，应对内部调用与下游变慢。只放网关会漏掉服务间的调用（内部流量不经过网关），只放服务内则挡不住入口的恶意流量。（另见「为什么不能只靠网关限流」专页。）

集群限流能精确到「不多限一个、不少限一个」吗？

能做到接近精确，但代价是每次请求一次 Redis 往返。要判断值不值：低频高价值场景（如付费 API 配额、短信发送）值得精确，因为少限会亏钱、多限会引客诉；高频低价值场景（如页面访问）不必精确，用本地均分省下的延迟与 Redis 成本远比那 10% 误差重要。
