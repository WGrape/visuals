先给结论

一句话：内存模型 ≠ 内存怎么分配，也不是 GMP、也不是 GC

在程序语言理论里，"内存模型（Memory Model）"是一个专门的概念，和"内存管理/分配""调度器""垃圾回收"是四个不同的话题。

「内存模型」回答的是：在并发 / 乱序执行下，一个协程对内存的写入，在什么条件下对另一个协程"可见"，以及操作之间有哪些顺序保证。它是一份并发可见性契约，不是"内存怎么被分配出来"。

四个常被混为一谈的词，各管一摊

① 内存模型 Memory Model
「契约/规则」层：并发下读写可见性与顺序的保证。Go 官方文档 The Go Memory Model 讲的就是它，核心是 happens-before。
② 内存分配 / 管理
「实现」层：堆内存怎么被切成小块、怎么快速发还。关键词 mcache/mcentral/mheap/span/size class。
③ GMP 调度
「调度」层：百万 goroutine 怎么映射到少量 OS 线程上跑。关键词 G / M / P / work-stealing。
④ 垃圾回收 GC
「清理」层：不再使用的内存何时被回收。关键词三色标记 / STW / write barrier。
记一句口诀：内存模型 = 规则（谁能看到谁的写）；内存分配 = 修路（内存怎么切）；GMP = 交警（谁在什么时候跑）；GC = 环卫（不用的内存何时扔）。四件事名字里都带"内存"，但层次完全不同。
定义

① 到底什么是「内存模型」（Memory Model）

它是编程语言理论里的一个形式化概念，和"内存布局长什么样"完全不是一回事。

为什么需要一份"内存模型"？

你写的代码顺序，不等于 CPU/编译器实际执行的顺序。现代体系里至少有三层"重排"会破坏直觉：

编译器重排
编译期为了优化，会在"不改变单线程结果"的前提下调换指令顺序。
CPU 乱序执行
多核 CPU 为吞吐会乱序/投机执行，写还可能先停在 store buffer 里没真正落到内存。
缓存不一致
每个核有独立缓存，A 核写的变量 B 核可能暂时从自己的缓存里读到旧值。
写缓冲 / 失效队列
写操作在真正全局可见之前，会经过 store buffer、invalidate queue 等中间环节。

这些优化让程序变快，但也带来一个麻烦：如果没有一份规则，你根本没法预测"我写的值，别人什么时候看得到、会不会被重排"。「内存模型」就是这份规则——它用 happens-before（先于发生）这种偏序关系，告诉你在哪些同步操作后，写结果一定对别人可见。

它只回答两个问题：
① 可见性（Visibility）：我写的这个值，你读的时候能不能看到？
② 顺序（Ordering）：操作 A 和操作 B，谁先"发生"才被保证？

它不回答：这块内存是从哪个池子分配的、goroutine 由哪个线程执行、垃圾什么时候收。那些是别的子系统的事。把"内存模型"理解成"Go 的内存长什么样 / 怎么分配"是这一领域最常见的误解——而本目录下那篇 《Go内存模型》可视化页恰恰把内存布局 + GMP + GC + happens-before 全塞进了一页，正是这种混淆的典型来源：它标题叫"内存模型"，内容却大多是另外三块。

内存模型是"规范层"（一份契约）；内存分配 / GMP / GC 是"实现层"的三个子系统。

小测试：面试官的"内存模型"到底指哪个？

点一下最符合你想法的说法，看它对应的真实话题——多数人一开始会选错。

→ 这是「内存分配 / 管理」，不是内存模型。它关心"变量放哪、谁来回收（栈自动 / 堆靠 GC）"，属于实现层，和并发可见性契约无关。
→ 这才是真正的「内存模型」。它在问 happens-before 与 data race：不加任何同步，答案是"未定义——可能看到旧值、可能看到新值、甚至可能看到撕裂的值"。这正是 The Go Memory Model 要规定的。
→ 这是「GMP 调度」，不是内存模型。它关心"执行权怎么流转"，属于调度层。调度层之上才谈可见性（内存模型不管谁跑，只管跑完之后别人能否看到写）。
→ 这是「GC 垃圾回收」，不是内存模型。它关心"内存何时释放"，属于清理层。
判断窍门：把对方的话里"内存"换成"并发可见性"读一遍——通顺，就是真·内存模型；换成"怎么分配 / 谁在跑 / 何时回收"才通顺，那就是另外三块。

同一句话，对应 4 个完全不同的知识域——所以回答前先澄清对方指哪个。

核心

③ 真·内存模型规定了什么：happens-before

如果确认对方问的就是内存模型，那答案几乎全绕着 happens-before（先于发生）转。

happens-before 是"偏序关系"，不是"时间先后"

说 A happens-before B，意思是：所有对 A 的写，B 及之后的操作都一定能看到，且编译器/CPU 不得把 B 之前的读写重排到 A 之后（在单线程语义可观察的范围内）。注意它是偏序——有些操作之间没有 happens-before 关系，它们就是"并发、不可比较"，谁先谁后未定义。

Go 内存模型给出的 happens-before 规则（面试常背清单）

单 goroutine 顺序
同一 goroutine 内，按程序顺序 hb。但重排不可被本 goroutine 观察，所以别以为"我写的顺序就是执行顺序"。
goroutine 创建
go f() 语句 hb 于新 goroutine 开始执行 → 创建前写的变量，新 goroutine 一定看得到。
channel 通信
带缓冲：第 k 次 send hb 第 k 次 receive；无缓冲：send hb receive；close hb receive 收到零值。
互斥锁 sync.Mutex
第 n 次 Unlock hb 第 n+1 次 Lock；RWMutex 的 RLock 也遵循对应规则。
WaitGroup
第 n 次 Done hb 第 n 次 Wait 返回。
Once / atomic
Once.Do(f) 中 f 的执行 hb 任何后续 Do 返回；Go 1.19+ 的 sync/atomic 提供 acquire/release/seqcst 语义。
Go 1.19（2022）对内存模型做了一次重要修订：重写文档使其与 C++ 内存模型对齐，并正式把 sync/atomic 的原子操作语义（relaxed / acquire-release / sequential consistency）写进了模型。所以"Go 没有正经内存模型"是过时说法。

经典反例：不加同步，内存模型说"结果未定义"

var a string
var done bool

func setup() {
    a = "hello, world"   // 写 a
    done = true            // 写 done
}

func main() {
    go setup()
    for !done {       // 空转轮询 done
    }
    print(a)        // 可能打印空串！
}

没有 happens-before 把 setup 的写和 main 的读连起来：编译器完全可以把 done = true 重排到 a = ... 之前，CPU 也可能让 main 核一直从自己的缓存读到 done == false 的旧值而永不退出循环，或退出后读到未初始化的 a。这恰恰是内存模型要告诉你"不能这么写"的地方。修法：用 channel 或 sync.Mutex / atomic.Bool 建立 happens-before。

误区澄清

④ 五个最常见的误区

误区 1：内存模型 = 内存布局（栈/堆长啥样）。 错。栈/堆布局是地址空间的划分，属于"内存管理"的入门知识；内存模型不关心地址，只关心并发可见性。
误区 2：内存模型 = GMP 调度。 错。GMP 决定"哪个协程由哪个线程在什么时候跑"；内存模型决定"跑完之后，写的结果别人能否看到"。一个管调度，一个管可见性，相关但不同层。
误区 3：内存模型 = GC 垃圾回收。 错。GC 管"不用的内存何时释放"，和"并发读写契约"毫无关系。
误区 4：Go 没有内存模型。 错。它有官方文档 The Go Memory Model，且 Go 1.19 还做了重要修订，引入了 atomic 的正式语义。
误区 5：happens-before 就是"时间上先发生"。 错。它是偏序关系，表达的是"可见性保证 + 禁止重排"，并不等于墙上时钟的先后。两个操作之间可能"互不 happens-before"，它们的顺序就是未定义的。
实战

⑤ 面试/考察时怎么答（标准模板）

四步回答法

① 先给定义
"内存模型是并发下的可见性契约，核心用 happens-before 描述读写何时对别的协程可见、顺序如何保证。"
② 讲规则
列 channel / mutex / atomic / WaitGroup / Once 如何建立 happens-before，并举 setup/done 反例。
③ 讲 Go 的特色
Go 首选用 channel 通信来共享内存；atomic 提供底层 acquire/release；1.19 修订对齐 C++ 模型。
④ 划清边界
"内存分配(GMP/GC)是相邻但不同的话题：分配管怎么切、调度管谁跑、GC 管何时扔，都不等于内存模型。"

一句话收尾："内存模型回答的是『并发下谁能看到谁的写』，不是内存怎么分配、也不是 goroutine 怎么调度——那三个是运行时另外两个子系统。"
