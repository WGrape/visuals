🔢 指令与数据的字节表示

用交互示例观察指令编码、进程地址空间与多字节数据的存放方式

指令长度 — 不一定只占 1 个字节！
x86/x64 架构的指令是变长的，从 1 字节到 15 字节不等。指令通常包含： 操作码（Opcode） + 操作数（Operand）。 操作码决定"做什么"，操作数决定"对谁做"。
内存区域（Memory Segments）— 程序内存布局
程序运行时，进程的虚拟地址空间通常包含代码、只读数据、已初始化数据、BSS、堆、映射区和栈等区域。 图中顺序只是常见布局示意；实际地址和排列受操作系统、链接器、ASLR 以及运行时分配影响，不能据此推断所有进程的固定地址。
多字节数据 — 跨多个地址怎么存？
int、float、指针等超过 1 字节的数据，需要占用连续的多个地址。 存储顺序有两种：小端序（Little Endian）和大端序（Big Endian）。 x86/x64 使用小端序：低位字节存在低地址。

内存对齐 — 为什么 int 要从 4 的倍数地址开始？
为了提高访问速度，多字节数据通常要求对齐到其大小的倍数地址。 比如 4 字节的 int 应该放在地址 0、4、8... 等 4 的倍数处。
📝 核心要点

📏 指令长度

  • x86 指令是变长的，1-15 字节
  • 操作码 + 操作数（寄存器/立即数/地址）
  • 复杂指令（如 MOV [EAX+4], EBX）更长

🗂️ 内存区域

  • 代码段：存放机器指令（只读）
  • 数据段：已初始化的全局变量
  • BSS：未初始化的全局变量
  • 堆：动态分配（malloc/new）
  • 栈：局部变量、函数参数

🔢 多字节数据

  • int/float：4 字节，连续 4 个地址
  • double/pointer(64位)：8 字节
  • 字符串：字符数组，以 \\0 结尾
  • 小端序：低位字节在低地址

一切都是字节，关键是「怎么解释」

内存里只有 0/1 序列，同样的 4 个字节，解释为 int、float 还是指令，结果完全不同。而多字节数据的字节顺序（大小端）与对齐方式，则是跨平台、网络通信、二进制文件解析中最容易踩的坑。这一页把这两个概念讲透。

字节序与对齐的实战

① 什么时候必须关心字节序

  • 网络通信：协议字段一律按网络序（大端）解析。
  • 二进制文件/协议：PNG、TCP 头、自定义协议都要明确字节序。
  • 跨架构数据交换：x86 写的数据给大端设备读。
  • 位域（bitfield）与联合体（union）的布局依赖实现，禁止用于跨端协议。

② 写出字节序无关的代码

  • 不要直接把结构体 memcpy 到网络上传输。
  • 按字段用移位组装：v = (b0<<24)|(b1<<16)|(b2<<8)|b3;
  • 或统一用 htonl/htons/ntohl/ntohs（注意 64 位用 htobe64）。
  • 序列化层（protobuf/msgpack）已处理，能不用裸结构体就别用。

③ 对齐为什么重要

  • 对齐访问一次总线即可；未对齐可能要两次并拼接。
  • 某些架构（早期 ARM、SPARC）未对齐访问直接崩溃。
  • 结构体有填充字节：字段顺序影响 sizeof 大小。
  • 技巧：把大字段放前面、相同类型放一起，可减少填充。

④ 结构体填充实例

  • struct{char c; int i;} 通常占 8 字节（c 后填 3 字节）。
  • 改成 {int i; char c;} 仍是 8 字节（尾部对齐到 4）。
  • 可用 #pragma pack(1) 取消填充，但会牺牲访问性能且不利于跨平台。
  • 网络协议建议手写序列化而不是依赖结构体布局。

深入自检

怎么判断一台机器是大端还是小端？

最经典的方法：把一个 int 赋值为 1，取它的第一个字节。若为 1 说明低位字节在低地址（小端），若为 0 则是大端。也可用联合体 union{int i; char c;} 来实现。实际工程中更推荐直接用语言提供的 API 而不是自己探测。

为什么网络字节序选了大端？

历史选择：早期网络协议（如 TCP/IP）在设计时大端更常见，且大端便于人阅读十六进制转储（高位在前）。这个约定延续至今，成为跨平台的统一标准。因此不管主机是什么序，收发网络数据都要做转换。

float 为什么不能用等号比较？

因为多数十进制小数无法用二进制精确表示（如 0.1），运算还会累积舍入误差。正确做法是比较差值是否小于一个允许的误差范围（epsilon），或者比较 ULP（用整数解释浮点位模式）。金额计算应使用定点数或十进制库，绝不用 float 表示钱。

结构体为什么会有填充字节？

为了让每个字段满足对齐要求，编译器会在字段之间插入未使用的填充字节。这是用空间换访问速度的取舍。调整字段顺序（大类型在前）可以减少填充；也可以用 pack 指令取消填充，但会带来性能损失与可移植性问题。

有符号数和无符号数混用有什么坑？

C/C++ 中混用会把有符号数隐式转换为无符号数，导致 -1 < 1u 居然为假（-1 变成极大的无符号数）。这类 bug 在循环条件、长度比较中极常见。对策：统一类型、开启编译器警告（-Wsign-compare）、尺寸类型用 size_t 并避免与负数比较。

64 位程序里 int 和指针一样大吗？

不一样。LP64 模型（Linux/macOS 64 位）下 int 仍是 4 字节，long 和指针是 8 字节；LLP64（Windows 64 位）下 long 仍是 4 字节，只有指针和 long long 是 8 字节。所以跨平台代码不要用 long 存储指针，要用 intptr_t/uintptr_t。
