① 进程模型：一个连接一个进程

PostgreSQL 采用多进程架构（与 MySQL 的「一连接一线程」不同）：

优点

进程隔离好，一个后端崩溃不会拖垮整个实例；便于调试与资源控制

代价

进程比线程重（内存、上下文切换），连接数上千时压力明显

对策

用连接池（PgBouncer / 应用层池），把实际后端连接控制在几十到几百

注意

work_mem 是每个排序/哈希操作的量，一个复杂查询可能用多份

③ 存储与逻辑结构层级

PG 的层级：实例（Cluster）→ 数据库（Database）→ 模式（Schema）→ 表/索引 → 表空间（Tablespace）。

  • Database 之间完全隔离：不能跨库 JOIN，连接时需指定库名（这与 MySQL 的「库」只是命名空间不同）；
  • Schema 是库内的命名空间：public 是默认 schema，可用它做多租户隔离或版本管理；
  • search_path 决定未限定对象名的解析顺序，错误配置会导致「建到了 public 却查不到」的经典问题；
  • Tablespace 只是目录映射，用于把对象放到不同磁盘。
SHOW search_path;                 -- 默认 "$user", public
SET search_path TO app, public;   -- 会话级调整

-- 查看对象所在 schema
SELECT schemaname, tablename FROM pg_tables WHERE tablename = 'orders';

④ 一条 SQL 的执行路径

从客户端到结果，大致经过五步：

  1. 连接与认证：Postmaster 接受连接、pg_hba.conf 校验、fork 出后端进程；
  2. 解析（Parser）：词法/语法分析 → 生成解析树；
  3. 重写（Rewriter）：应用规则系统（如视图展开、RLS 策略）；
  4. 计划（Planner/Optimizer）：基于统计信息与代价模型生成执行计划（表扫描方式、JOIN 顺序、是否并行）；
  5. 执行（Executor）：以火山模型（Volcano）逐行拉取（每个节点实现 next()），访问缓冲层、必要时写 WAL。
-- 观察计划与实际耗时
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT o.id, u.name FROM orders o JOIN users u ON u.id = o.user_id
WHERE o.status = 'paid' ORDER BY o.created_at DESC LIMIT 20;
-- 重点看：actual time、rows 估计 vs 实际（偏差大说明统计信息过期）、
--        Buffers: shared hit/read（缓存命中率）
关于「双缓存」：PG 用 shared_buffers，同时 OS 还会缓存文件页，因此存在两级缓存（有一点重复，但 PG 依赖 OS 缓存做预读与写合并）。EXPLAIN (BUFFERS) 中 shared hit 表示命中 PG 自己的缓冲；read 表示从 OS/磁盘读入。

⑥ 常见问法

Q：PostgreSQL 为什么用多进程而不是多线程？

A：历史与工程权衡：优点是隔离性好（一个后端崩溃不会影响其它连接，崩溃时共享内存由主进程重建）、便于调试与资源限制；代价是进程比线程重（内存占用、上下文切换），连接数上千时开销明显，因此生产环境必须用连接池（PgBouncer）。这不是性能劣势的根源——PG 通过共享内存 + 高效的进程调度，在中高并发下表现依然很好，关键是不要开几千个直连。

Q：shared_buffers 该设多大？为什么不是越大越好？

A：经验值是物理内存的 25%（官方建议），而不是像 MySQL 那样设到 70%。原因：PG 依赖操作系统的页缓存做二次缓存与预读，两者是叠加关系；若 shared_buffers 过大，会挤压 OS 缓存，反而降低整体命中率，而且检查点时要刷的脏页更多，造成 IO 尖峰。调优方法：用 pg_stat_database 的 blks_hit / (blks_hit + blks_read) 观察命中率，并结合实际负载逐步调整，别一次到位。

Q：work_mem 为什么容易导致内存爆掉？

A：因为 work_mem 是「每个排序/哈希操作」的上限，而不是「每个查询」或「每个连接」的上限。一个查询可能包含多个排序/哈希节点（如多次 ORDER BY + 多个 JOIN），并行查询还会乘上 worker 数。举例：work_mem=256MB、并发 100 个查询、每查询 3 个排序节点 → 理论峰值 256MB × 3 × 100 = 76GB。正确做法：全局设保守值（8~32MB），只对报表/批处理会话单独 SET。

Q：PG 的『数据库』和 MySQL 的『库』一样吗？

A：不一样。PG 的 Database 是完全隔离的：不能跨库 JOIN，连接必须指定库，权限、WAL 虽共享但逻辑上独立；MySQL 的 database/schema 基本只是命名空间，一条连接里可以 SELECT * FROM db1.t JOIN db2.t。PG 的替代方案：用 Schema 做库内命名空间隔离（可跨 schema 查询），用 postgres_fdw 或 dblink 实现跨库访问。迁移时的常见坑：把 MySQL 的「多库」直接映射成 PG 的「多 Database」会导致无法跨库查询。

Q：一条 SQL 在 PG 里是怎么执行的？

A：五步：① 连接认证（pg_hba.conf，fork 后端进程）；② 解析：词法/语法分析生成解析树；③ 重写：应用规则（视图展开、行级安全策略 RLS）；④ 计划：优化器基于统计信息与代价模型枚举路径，选择扫描方式、JOIN 顺序与方法、是否并行；⑤ 执行：火山模型逐行拉取（每个节点实现 next()），通过缓冲层访问数据，写操作产生 WAL。排查性能时看 EXPLAIN (ANALYZE, BUFFERS)：重点比较 rows 的估计值与实际值（偏差大 → 统计信息过期或选择性估算失误）。

Q：effective_cache_size 会分配内存吗？

A：不会。它只是告诉优化器「系统大概还有多少缓存可用」的一个提示值，用于估算索引扫描的 IO 代价（缓存命中多则代价低）。设得太小会让优化器倾向于全表扫描（误以为索引要大量随机 IO），设得过大则相反。建议设为 OS 页缓存的可用量（通常是内存的 50%~75%），它不消耗任何资源，只影响计划选择。
