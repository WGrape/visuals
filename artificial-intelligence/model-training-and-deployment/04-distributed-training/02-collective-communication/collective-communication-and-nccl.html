分布式训练通信与集合通信：AllReduce / NCCL / 带宽瓶颈

切分之后，卡与卡之间必须不断交换梯度、激活与权重。通信往往比计算更决定扩展效率——本文讲清七种集合通信原语、Ring AllReduce 为什么带宽最优、NCCL 怎么吃满 NVLink/IB，以及数据/张量/流水线三种并行的通信画像与排障。

为什么通信是分布式训练的命门

算力随 GPU 数量 线性增长，但模型里的参数、梯度必须在卡间同步——通信量随模型规模增长，却不随卡数线性下降。结果是：模型越大、卡越多，通信占比越高，扩展效率（强扩展的加速比）会明显偏离理想线。

  • 数据并行：每步要 AllReduce 一次全量梯度，通信量 ≈ 模型参数量的 2 倍（fp32）。
  • 模型并行：每一层前向/反向都要交换激活或中间和，通信 频率极高（每层一次）。
  • 流水线并行：通信量最小，但用「气泡」换来的——空等也是隐性代价。
一句话：计算可以堆卡，通信堆不动。能不能把通信藏进计算里（overlap），决定了加机器到底加不加得出速度。

七种集合通信原语

NCCL / Gloo / MPI 都围绕这一组原语实现，理解它们是看懂所有并行策略的前提。

原语做什么在训练中的典型用途
Broadcast把一份数据从根卡发到所有卡下发初始权重、下发超参
Scatter / Gather把一份数据切分下发 / 把各卡片段收回来数据分片加载、收集日志
Reduce所有卡同位置数据做求和/最大等，结果留在一张卡在某一卡汇总指标
AllReduce所有卡做 Reduce，且每张卡都拿到相同结果数据并行的梯度同步（最常用）
AllGather把所有卡的片段拼到每张卡张量并行里拼回完整激活/权重
ReduceScatter先做 Reduce 再按卡切分，每张卡只持有部分和的片段ZeRO 优化器状态切分、张量并行前置步骤
关键直觉：AllReduce = ReduceScatter 之后再 AllGather；Ring AllReduce 正是分两步走，所以带宽最优。

Ring AllReduce：为什么它带宽最优

把模型的梯度张量切成 N 块（N = GPU 数），让 N 张卡排成一个环，分两阶段走完：

阶段一 · ReduceScatter

环上每张卡把自己的第 i 块发给下家、收下家的第 i-1 块并累加，传递 N-1 轮。结束时，每张卡恰好持有「某一块」在所有卡上的完整求和，其余块仍是各碎片。

阶段二 · AllGather

再绕环 N-1 轮，把已经求完整的那一块传播出去。N-1 轮后，每张卡都集齐了全部 N 块的求和结果。

总通信量 ≈ 2·(N-1)/N · S ≈ 2S（S=梯度总字节数）；与 N 无关，只与数据量有关
这是 Ring 相比朴素「全部发到一台再广播」的优势：朴素要 2(N-1)S 且那台卡是瓶颈；Ring 把流量平摊到每张卡，没有单点瓶颈，且总流量不随卡数变坏。

NCCL 与硬件拓扑：吃满 NVLink 才快

NCCL（NVIDIA Collective Communications Library）会按实际拓扑自动选算法，决定走哪条物理通道。瓶颈几乎永远是带宽最低的那一段：

通道典型带宽范围含义
NVLink~300–900 GB/s同节点内 GPU 间全互联 mesh，张量并行的最优载体
PCIe 4/5~32–64 GB/s同节点 GPU↔CPU没 NVLink 时的兜底，慢一个量级
InfiniBand / RDMA~50–400 GB/s跨节点数据并行的主战场，需 GPUDirect

Tree 算法

按层级把卡分组聚合，延迟低、适合小消息；但聚合点可能成为带宽瓶颈，跨节点时常用。

Ring 算法

带宽最优、无单点瓶颈，适合大消息（梯度同步）；节点内走 NVLink，跨节点在每段上仍用 Ring/Tree 拼接。

经验法则：张量并行必须留在同一节点内（靠 NVLink）；数据并行可以跨节点（靠 IB）。把 TP 跨节点，通信立刻被 PCIe/IB 拖垮。

DP / TP / PP 的通信画像

维度通信原语通信量频率对带宽要求
数据并行 DPAllReduce 梯度~2×参数量/步每步 1 次中（可跨节点 IB）
张量并行 TP层内 AllReduce 激活/和~激活/中间量每层多次极高（需 NVLink）
流水线并行 PPP2P 收发激活小（激活切片）每微批 1 次低（但有气泡）
ZeROReduceScatter+AllGather拆开优化器状态每步若干次中（省显存换通信）
3D 并行 = 把 TP（高带宽、节点内）叠 DP（跨节点）叠 PP（少通信）。通信最贵的 TP 放在最内层，通信最省的 PP 放在最外层，这是 Megatron / FSDP 的标准排布。

把通信藏进计算里：六类优化

① 计算通信重叠

反向时，先算完的层其梯度立刻开始 AllReduce，不必等全部层反向完。把通信时间盖在后续层的计算下。

② 梯度累积

多个 micro-batch 的梯度在通信前先本地累加，减少 AllReduce 次数；同时让通信与下一轮前向重叠。

③ fp16/bf16 梯度

梯度用半精度通信，体积直接减半，精度损失通常可忽略。

④ 梯度 Bucketing

把小梯度拼成 ~25MB 的桶再发，摊薄启动延迟（NCCL 小消息延迟贵）。

⑤ 选高带宽后端

同节点优先 NVLink；跨节点开 GPUDirect/RDMA，避开 CPU 中转。

⑥ 通信域切分

节点内先 Reduce、节点间再 Reduce，分层集合通信减少跨节点流量。

这六条里，① 重叠是收益最大的——它把「通信时间」从关键路径上拿掉，是强扩展能否接近线性的关键。

排障与选型：加机器为什么不加速

常见元凶，按出现频率排序：

  • 通信没重叠：通信串行在关键路径上，卡在等网。看 profiler 里 NCCL 占比。
  • 带宽饱和：TP 跨节点 / PCIe 瓶颈 / IB 没跑满。先用 nvidia-smi dmon 看 nvlink 利用率。
  • 负载不均：长尾 batch、padding 导致部分卡先idle。PP 气泡、DP 不等长序列都会触发。
  • 拓扑错配：NCCL 选了慢通道（如没用上 NVLink），设 NCCL_DEBUG=INFO 看它实际走的算法与通道。
现象先查对策
加卡加速比远小于 NNCCL 时间占比开启 overlap / 梯度累积
同节点快、跨节点骤降IB / RDMA 配置核对 GPUDirect、拓扑
单卡显存爆、多卡没用满并行策略上 ZeRO / 调 TP-PP 配比
工具链：nvprof / Nsight Systems 看时间线；NCCL_DEBUG=INFO 看通道选择；nvidia-smi dmon -s pucvmet 看 NVLink 流量。先定位是「算慢」还是「等通信」，再决定加机器还是改重叠。
