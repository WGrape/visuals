第四层：物理硬件层

CPU 缓存、内存屏障、原子操作

硬件层决定了线程安全性的底线。CPU 缓存带来可见性问题，内存屏障保证顺序一致性，原子指令提供基本的线程安全操作。

❌ 非原子操作（竞态条件）

// 两个线程同时执行
int count = 0;
count++; // 非原子！

// 实际执行可能分解为:
① 读取 count (0) → 寄存器
② 寄存器 + 1
③ 写回 count (1)

结果：可能是 1 而非 2！

✓ 原子操作（CAS 机制）

// 使用 Compare-And-Swap
atomic.CompareAndSwap(&count, 0, 1)

// CPU 指令:
lock cmpxchg [count], eax

// 单条指令完成：
如果 count == 0 → count = 1
否则失败并重试

结果：保证原子性！

线程是「调度的基本单位」，进程是「资源的基本单位」

这是操作系统最经典的一句区分：进程拥有资源（地址空间、文件、信号），线程是 CPU 调度的最小单位。同一进程的线程共享地址空间，所以切换代价远小于进程切换，但也因此一个线程踩内存会带崩整个进程。

共享内容代码段、堆、全局变量、文件描述符
私有内容栈、寄存器、线程局部存储 TLS
用户级线程在用户态切换，快但无法用多核、阻塞会连累全部
内核级线程由内核调度，可利用多核，切换需陷入内核

线程模型与切换成本

模型映射关系切换成本能否多核阻塞影响代表
1:1（内核线程）一个用户线程 = 一个内核线程较高（陷入内核）能只阻塞自己Linux pthread、Java Thread
N:1（用户线程）多个用户线程 = 一个内核线程极低（用户态）不能一个阻塞全阻塞早期协程库、某些脚本引擎
M:N（两级）M 个轻量线程 → N 个内核线程低（多数在用户态）能调度器会另起线程Go goroutine、Erlang process
进程独立地址空间最高（页表、TLB 全换）能互不影响fork 出的独立程序

数量直觉：pthread 默认栈 8MB（虚拟内存），几千个线程就会耗尽虚拟地址空间并带来巨大调度开销；goroutine 起始 2KB 且按需增长，百万级也很轻松。这就是「高并发要用协程」的原因。

并发编程的实践要点

① 线程数该设多少

  • CPU 密集：约等于核数（或核数+1），再多只会增加切换开销。
  • IO 密集：可以远大于核数，经验公式 = 核数 × (1 + 等待时间/计算时间)。
  • 要用压测确定，不要拍脑袋；连接池、线程池要分别设置上限。
  • 注意：线程池太大还会耗尽内存与下游连接。

② 锁与同步

  • 互斥锁 mutex：保护临界区，要尽量短。
  • 读写锁 RWLock：读多写少时提升并发。
  • 自旋锁：临界区极短且多核时用，避免睡眠唤醒开销。
  • 无锁（原子操作/CAS）：性能好但难写对，注意 ABA 问题。
  • 条件变量：等待某个条件成立，必须配合 while 检查防虚假唤醒。

③ 常见并发问题

  • 数据竞争：未同步的共享读写 → 用工具检测（TSan、race detector）。
  • 死锁：锁顺序不一致 → 统一加锁顺序、用带超时的尝试锁。
  • 活锁/饥饿：反复重试或优先级不当 → 退避与公平调度。
  • 伪共享：多核写同一缓存行 → padding 对齐。
  • 线程泄漏：未回收的线程/协程堆积 → 监控数量与生命周期。

④ 协程（goroutine）为什么轻

  • 栈小且可增长：2KB 起步，按需扩缩。
  • 用户态调度：多数切换不进内核。
  • 调度器感知阻塞：遇到系统调用会另起 OS 线程，不让其他协程饿死。
  • 抢占：现代 Go 支持异步抢占，避免长循环独占。
  • 代价：runtime 复杂，且阻塞型 C 调用仍会占住线程。

深入自检

进程和线程的本质区别是什么？

进程是资源分配的基本单位（独立地址空间、文件描述符表、信号处理），线程是 CPU 调度的基本单位。同一进程的线程共享地址空间，因此创建快、切换轻、通信方便（直接读写共享变量）；代价是隔离性差——一个线程崩溃或破坏内存会影响整个进程。

为什么线程切换比进程切换快？

因为不需要切换页表（同一地址空间），从而避免了 CR3 切换带来的 TLB 失效与缓存流失，也不需要保存/恢复大量进程级资源。实际成本差异主要在 TLB 与 Cache 的「冷启动」上，这往往比寄存器保存的开销大得多。

协程能完全替代线程吗？

不能。协程适合高并发 I/O 型任务（网络服务、爬虫），在用户态切换、成本极低；但 CPU 密集的并行计算仍需内核线程来真正占用多核，且协程无法解决「某个计算长时间占用」的问题（需要让出点或抢占）。Go 的模型正是 M:N：协程负责并发结构，OS 线程负责真实并行。

线程池为什么比「每请求一线程」好？

因为线程的创建/销毁有成本，且无限制创建会耗尽内存与调度资源，导致性能雪崩。线程池通过复用线程、限制并发上限，把资源消耗变成可控的常数。关键参数：核心线程数、最大线程数、队列类型与长度、拒绝策略——都要按业务设定。

如何定位线程相关的问题？

常用手段：① 数量与状态（ps -L、/proc/PID/task、pprof goroutine）；② 栈采样（jstack、gdb thread apply all bt、Go pprof）；③ 锁竞争（perf lock、Java JFR）；④ 上下文切换（vmstat 的 cs 列、pidstat -w）；⑤ 竞态检测（Go -race、ThreadSanitizer）。

为什么有时候加线程反而变慢？

典型原因：① 锁竞争加剧，大量时间花在等待；② 上下文切换与缓存失效成本超过并行收益；③ 共享数据结构（如伪共享）导致缓存行反复失效；④ 下游（数据库、连接池）成为瓶颈。判断方法：看 CPU 是否花在 sys 态与等待上、看锁竞争指标、做吞吐-并发曲线找拐点。
