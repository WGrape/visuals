01CFS 的核心：谁欠得多，谁先跑

第一层

概念与判定

CFS 不看「优先级数字」，而看每个任务已经累计的 虚拟运行时间 vruntime。规则只有一条：

永远调度 vruntime 最小的任务。跑得越久，vruntime 涨得越快；权重越高，涨得越慢。这样长期看，每个任务获得的 CPU 时间与权重成正比。
vruntime 增量
实际运行时间 × (NICE_0_LOAD / 任务权重)
nice = 0
权重 1024，vruntime 与实际时间 1:1
nice = -20
权重 88761，vruntime 涨得极慢 → 获得约 87 倍 CPU
nice = +19
权重 15，vruntime 涨得极快 → 几乎抢不到 CPU
nice权重相对 CPU 份额（nice=0 为 1）

02红黑树：O(log n) 找最小 vruntime

图：CFS 用红黑树维护 vruntime 顺序，避免每次 O(n) 扫描。
为什么不用「排序数组」或「堆」？数组插入 O(n)，堆取最小 O(1) 但删除任意节点难。红黑树在插入、删除、取最小上都 O(log n)，且能快速处理「任务阻塞/唤醒时从树中摘除/插入」。

03调度周期与最小粒度

参数默认/典型含义
sched_latency6 ms（随 CPU 数缩放）所有可运行任务至少各跑一次的目标周期
min_granularity0.75 ms单次运行的最小时间片（任务太多时防止过度切换）
nr_running—就绪任务数；时间片 = sched_latency / nr_running，但不低于 min_granularity
# 查看调度参数
sysctl kernel.sched_latency_ns kernel.sched_min_granularity_ns
cat /proc/sys/kernel/sched_wakeup_granularity_ns

# 查看某进程的调度统计
cat /proc//schedstat   # 运行时间 / 等待时间 / 时间片数
cat /proc//sched | head -20
唤醒抢占有 sched_wakeup_granularity 门槛：被唤醒任务的 vruntime 必须比当前任务小至少这个值，才允许抢占。否则会出现「频繁唤醒 → 频繁切换」的抖动。

04组调度：按 cgroup 分 CPU

CFS 的公平性可以作用在任务组上，而不是单个任务。这样「一个组开 1000 个线程」也抢不走另一个组的份额：

cgroup v2 文件作用
cpu.weight组的相对权重（1–10000，默认 100）
cpu.max带宽限制，如 50000 100000 = 每 100ms 最多用 50ms
cpu.stat查看 nr_throttled/throttled_usec，判断是否被限流
# 给某个容器组限制 0.5 核
mkdir -p /sys/fs/cgroup/demo
echo "50000 100000" > /sys/fs/cgroup/demo/cpu.max
echo $$ > /sys/fs/cgroup/demo/cgroup.procs
cat /sys/fs/cgroup/demo/cpu.stat
容器「CPU 用不满但很慢」几乎都是 cgroup 限流：看 cpu.stat 里 nr_throttled 是否持续增长。这不是调度器 bug，是配额打满。

05EEVDF：6.6 之后的新调度器

Linux 6.6（2023）用 EEVDF（Earliest Eligible Virtual Deadline First）替换了 CFS 的核心选择逻辑：

对比CFSEEVDF
选择依据最小 vruntime最早「合格」虚拟截止时间
延迟敏感任务靠唤醒抢占粒度显式支持 sched_setattr 的 latency nice
公平性长期按权重长期按权重 + 短期延迟保证
接口nice / cgroup weight沿用 nice + 新增延迟偏好
EEVDF 解决的是 CFS 的老问题：CFS 对「刚睡醒、只差一点点 vruntime」的任务不够友好，导致交互延迟抖动。EEVDF 用虚拟截止时间让短任务更快拿到 CPU。

06排障与边界

第三层

排障与边界

  • 「CPU 有富余但进程慢」：先看 cpu.stat 是否 throttled，再看 /proc//schedstat 的等待时间占比。
  • 负载不均：NUMA 机器上任务可能集中在一个 node，用 numactl/taskset 绑定。
  • 线程数爆炸：nr_running 很大时，每个任务时间片被压到 min_granularity，切换开销上升；线程数应与核数同量级。
  • 实时任务抖动：cyclictest 测延迟，检查是否有长时间关中断或 SCHED_FIFO 死循环。

07原理与取舍

第四层

原理与取舍

CFS 的深刻之处在于把「公平」变成了一个可计算的不变量：每个任务的 vruntime 尽量相等。这样不需要为每个任务单独设优先级规则，只需调整权重。

设计收益代价
红黑树O(log n) 全操作指针开销、缓存不友好
vruntime公平可度量对延迟不敏感（EEVDF 补）
组调度多租户隔离层级计算复杂

深入 Q&A

Q：vruntime 会溢出吗？
A：用 64 位无符号数，按纳秒计可跑约 584 年；实际还会定期做「所有任务同时减去最小值」的归一化。

Q：睡眠很久的任务醒来会不会霸占 CPU？
A：不会。醒来时其 vruntime 会被抬到不小于队列最小值减去一个阈值，防止「睡久了攒下巨量信用」。
