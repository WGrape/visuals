💥 缓存击穿：一个热点 key 倒下的瞬间

某个被千万人访问的热点 key 恰好过期，瞬时海量请求同时发现缓存为空，一起冲向数据库。

💥

定义

单个热点 key 过期瞬间的并发风暴

🔒

互斥重建

只放一个线程去查库

🕰️

逻辑过期

物理不过期，靠逻辑时间续期

♾️

永不过期

热点 key 不设 TTL，异步更新

先建立直觉：演唱会散场时的那扇门

想象一场演唱会散场，几万人挤在一扇大门前。门本来是敞开的（缓存命中），大家顺畅地走出去，毫无压力。

突然，门关了一瞬间（key 过期）。这几万人同时发现「门关了」，于是全部转头去推旁边的备用小门（数据库）。备用小门只有一米宽，几万人同时推——门被挤塌了。

这就是击穿：不是门一直关着，而是恰好在关的那一瞬间，积压的流量全部涌向数据库。它和穿透的区别在于：这个数据是真实存在的、很热门的，只是缓存恰好失效了。

击穿的三个必要条件：① 该 key 是热点（高并发）；② 缓存刚好过期；③ 重建缓存（查库）需要一定耗时。三者同时成立才会击穿。所以它的影响范围是单点——一个 key，而不是一批。

为什么会击穿：并发重建的雪崩式重复

三条解法对照

① 互斥锁重建（最经典）

发现缓存为空时，先去抢一把分布式锁。抢到的那个线程去查库并写缓存；没抢到的线程不查库，而是睡眠一小会儿再重读缓存（或者干脆返回默认值/稍后再试）。

// 伪代码：互斥重建
val = redis.get(key)
if (val == null) {
    if (redis.setnx(lockKey, 1, 10s)) {      // 抢到锁
        try {
            val = mysql.query(key);           // 只有它查库
            redis.setex(key, ttl, val);
        } finally {
            redis.del(lockKey);               // 务必 finally 释放
        }
    } else {
        sleep(50ms);                          // 没抢到：等一下
        return getById(id);                   // 重试读缓存
    }
}
return val;
互斥锁的三个坑：
• 死锁：锁必须设过期时间，且释放要放 finally，否则重建线程挂掉会永久堵死。
• 超时：如果查库比锁的过期时间还长，锁提前失效，第二个线程又进来了。锁 TTL 要大于重建耗时。
• 等待风暴：大量线程同时 sleep 后同时重试（重试风暴）。用指数退避 + 抖动缓解。

② 逻辑过期（永不真正过期）

不给 key 设 Redis 的 TTL，而是把过期时间写进 value 里（比如 {data:..., expireAt: 1700000000}）。请求永远能读到数据（哪怕逻辑上过期了），只是发现「逻辑过期」的那个线程去异步重建。

  • 优点：请求永不阻塞，永远有数据返回（哪怕是旧数据），可用性最高。
  • 代价：会短暂返回陈旧数据，需要业务能容忍；实现比加锁复杂。
关键区别：互斥锁是「拿不到就等」，逻辑过期是「先给你旧的，我在后台悄悄换新的」。前者强一致，后者高可用。

③ 热点 key 永不过期 + 异步刷新

对可预测的热点（如首页 banner、热门商品），干脆不设过期时间，由一个后台定时任务或消息通知在数据变更时主动更新缓存。这样根本不存在「过期瞬间」。

三者怎么选

方案一致性可用性复杂度适合场景
互斥锁重建强（读到即最新）中（未抢到锁要等）低通用默认选择
逻辑过期弱（短暂陈旧）高（永不阻塞）中对延迟敏感的热点
永不过期 + 异步刷新取决于刷新时机高中可枚举的常驻热点
实践建议：普通热点用互斥锁；顶级热点（千万 QPS 级）叠加本地缓存 + 逻辑过期，让大部分请求根本不到 Redis。

🎯 面试问答

Q：击穿和穿透、雪崩怎么区分？
A：一句话：穿透=查不存在的数据（key 永远没有）；击穿=一个热点 key 过期瞬间被打（点的问题）；雪崩=一大批 key 同时过期（面的问题）。记忆法：穿透是「没有」，击穿是「一个」，雪崩是「一片」。

Q：用互斥锁会不会导致大量线程阻塞、请求超时？
A：会，这是它的代价。缓解办法：① 重试时用指数退避加随机抖动，避免同时醒来；② 设置最大等待次数，超限就返回降级数据（如兜底默认值、旧快照），而不是无限等；③ 对超级热点改用逻辑过期，让请求永不阻塞。不要指望一把锁解决所有量级。

Q：锁的过期时间该设多少？
A：必须大于一次完整重建的耗时，并留足余量。比如查库平均 200ms、最坏 1s，锁 TTL 至少设 3~5s。如果设得太短，重建还没完成锁就失效，第二个线程又进来查库，保护就失效了。同时要配合 finally 释放，避免拖到 TTL 才解锁。

Q：逻辑过期返回旧数据，业务上能接受吗？
A：取决于场景。能接受的：商品描述、文章内容、推荐列表、配置类数据——晚几百毫秒看到新值无伤大雅。不能接受的：库存余量、账户余额、订单状态——这些必须强一致，该用互斥锁甚至直接查库。判断标准：这份数据「旧一点」会不会造成资损或用户投诉？

第一层 · 概念与判定：击穿≠穿透≠雪崩

三个概念常被混用，必须先分清：

问题触发条件影响范围解法方向
击穿单个热点 key 失效瞬间这一个 key互斥重建/逻辑过期
穿透查不存在的数据持续的空查询布隆过滤器/空值缓存
雪崩大量 key 同时失效整片缓存错峰 TTL/高可用

一句话判定：「某个爆款被疯狂访问、偏偏它这一刻过期」= 击穿；大量请求直接打到 DB 把库打挂。

第二层 · 参数·命令·量化：互斥与逻辑过期

方案做法优点缺点
互斥锁重建只有一个线程查 DB 重建数据一致锁等待、怕死锁
逻辑过期value 带过期时间，异步重建无锁、响应快短期返回旧值
singleflight并发请求合并成一次简单有效依赖框架
预热+错峰TTL提前加载、加随机治本需预估热点

Redis 互斥锁 / singleflight 防击穿

# Redis 互斥锁重建（防止击穿）：用 SET NX 抢锁
import redis, json, time
r = redis.Redis()

def get_with_guard(key, load_from_db, expire=300, lock_ttl=3):
    val = r.get(key)
    if val is not None:
        return json.loads(val)
    # 抢锁：只有一个请求去查 DB
    lock = r.set(f"lock:{key}", "1", nx=True, ex=lock_ttl)
    if not lock:
        time.sleep(0.05)            # 没抢到，稍等重试取缓存
        return get_with_guard(key, load_from_db, expire, lock_ttl)
    try:
        data = load_from_db()        # 唯一查 DB 的线程
        r.set(key, json.dumps(data), ex=expire)
        return data
    finally:
        r.delete(f"lock:{key}")      # 释放锁，务必 finally

# 更省事的 singleflight（Go 标准库 extended 或 golang.org/x/sync/singleflight）
# 同一 key 的并发请求，只有一个真正执行，其余直接拿结果

数量级：锁 TTL 设 几秒 即可（重建 DB 查询通常毫秒~百毫秒级）；热点 key 的 QPS 可能 上万，不加保护 DB 连接瞬间被占满。

第三层 · 排障与边界：高频坑

防护失效的清单：

  • 把击穿当穿透治：布隆过滤器对「存在的热点 key 失效」无效，白忙一场
  • 锁没设超时：重建线程挂了，锁永不释放，key 永久无缓存
  • 锁粒度太粗：用一把全局锁，所有 key 串行重建，雪上加霜
  • 逻辑过期没兜底：异步重建失败，长期返回旧数据甚至脏数据
  • TTL 设成整点：热点集中整点过期，等于人工制造击穿窗口
  • 没预热：大促前热点未提前加载，开门瞬间击穿

排查顺序：① 监控 DB QPS 与缓存命中率，命中率骤降且 DB 飙升 = 击穿信号；② 看是否集中在某个/少数 key；③ 检查 TTL 分布是否有尖峰。

第四层 · 原理与取舍

互斥锁和逻辑过期该选哪个？

要强一致、不能返回旧值 → 互斥锁（代价是抢不到锁的线程要等/可能超时）；要极低延迟、能容忍极短旧值 → 逻辑过期（异步重建，请求不阻塞）。实践中常组合：平时逻辑过期保性能，极端热点再加单飞（singleflight）兜底。

为什么热点 key 失效那一刻最危险？

因为平时这些请求全被缓存接住了，DB 根本没承受过这个量。一旦同时失效，原本被缓存屏蔽的巨量并发瞬间穿透到 DB，而 DB 的连接池和 CPU 远小于缓存层，于是被瞬间打满、连锁超时——所以击穿的破坏力来自「平时被保护、毫无准备」。

singleflight 为什么比手写锁更稳？

它把同一 key 的并发请求合并成一次执行，天然无死锁风险、无需手动释放锁，且请求方拿的是同一份结果、零额外等待。手写 Redis 锁容易漏 finally、漏超时，singleflight 在进程内解决，少一次网络往返，是防击穿的工程甜点方案。
