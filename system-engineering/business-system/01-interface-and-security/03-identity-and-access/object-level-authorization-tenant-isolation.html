对象级授权与租户隔离：订单接口防越权

一个合法登录用户改了订单 ID，为什么仍可能读到别人的订单？沿读、写、列表和缓存四条路径追查。

BOLA/IDOR 的根源不是“订单号容易猜”

用户 u7 登录后请求 GET /tenants/t3/orders/8421。服务器验证了令牌，也检查了 orders.read，却直接执行 SELECT ... WHERE id = 8421。如果这笔订单归 t8 或属于 u9，响应就越过了对象边界。BOLA（对象级授权缺失）与 IDOR（不安全直接对象引用）关注的是“对这一个对象有没有权”，不取决于 ID 使用自增整数还是随机 UUID。随机 ID 降低猜测机会，但不能替代授权。

判断顺序：认证得到可信主体 → 识别有效租户与动作 → 对真实资源作归属判断 → 只返回允许字段。路径、请求体、查询参数中的 user_id 和 tenant_id 都来自客户端，不应直接成为授权依据。

图解：从可信主体到受约束的订单

租户 ID 从经过认证的主体/服务端选定的当前租户上下文获取，而不是从路由参数直接提升为权限。若业务支持用户主动切换租户，切换过程本身也必须校验该用户属于目标租户。

逐步推演：一笔跨租户订单

合法用户仍可发非法请求

用户 u7 的令牌有效，属于租户 t3。认证通过只证明请求来自 u7，不证明 URL 中的订单 8421 属于他们。

权限只是第一层

该用户有 orders.read。这个动作许可意味着能读“被授权的订单”，并不把某个 ID 自动归入授权集合。

数据库中的事实才是资源属性

订单 8421 的 tenant_id=t8。用 id=8421 AND tenant_id=t3 查询没有匹配行；资源端绝不能重新用仅有 ID 的查询兜底读取。

不泄露订单详情

统一按接口策略返回 404，或已认证但无权时返回 403；响应时间、错误消息和审计日志也应避免向调用者暴露其他租户的数据内容。

第一层 · 四条入口逐一划边界

入口容易漏掉的约束应落在何处
按 ID 读取有读权限但不属于用户/租户读取前将可信租户与归属作为查询条件
状态更新 / 删除先查权限、后按 ID 无条件更新更新语句包含同一归属条件与合法状态，检查影响行数
列表 / 批量列表只过滤用户，批量只检查第一项统一范围过滤，批量每项授权并明确部分失败语义
缓存 / 异步任务缓存键只有订单 ID；队列丢了租户上下文缓存键与作业上下文包含可信租户维度，再核对象归属

第二层 · 查询与更新示例

-- user_id、tenant_id 取自已校验的服务端上下文，不取自请求体
SELECT id, status, amount
  FROM orders
 WHERE id = :order_id AND tenant_id = :tenant_id AND owner_id = :user_id;

-- 修改时仍按归属和当前状态约束；影响 0 行不能报告成功
UPDATE orders SET status = 'CANCELLED'
 WHERE id = :order_id AND tenant_id = :tenant_id
   AND owner_id = :user_id AND status = 'CREATED';

客服、财务等特殊岗位有独立策略与受约束查询，不能简单跳过所有归属条件。服务端允许创建订单时，owner_id 和 tenant_id 应由可信上下文填充，不能直接绑定客户端任意传入的实体字段。跨服务访问要明确是以用户身份代理还是服务主体执行，避免“内部调用”成为免鉴权通道。

第三层 · 排障与边界

  • 读取安全、更新不安全：检查所有写操作是否使用同一可信租户和对象归属约束；“先查后改”之间可能状态改变，条件更新可收紧竞态窗口。
  • 批量越权：请求含多个订单 ID 时不可只验证第一个；选择整体拒绝还是逐项返回需有清楚契约，且绝不泄露未经授权记录。
  • 缓存串租：按 order:8421 单键缓存但不同租户可能复用标识；即使 ID 全局唯一，也要在缓存命中前后守住授权。
  • 租户管理员越权：租户内 admin 不等于平台 admin；平台人员跨租户排障应使用显式受控授权和审计，不默认开放业务数据。

第四层 · 原理与取舍

UUID 不可猜，为什么还要对象级授权？

标识可能出现在日志、通知、分享链接或其他客户端；权限不能建立在“别人不知道 ID”上。泄露一个 UUID 不应授予访问权限。

中间件已经验证了 orders.read，为什么数据库还要过滤？

中间件验证的是动作类别；归属随对象而变化，必须在读写数据时结合主体和资源判定。只有角色判断而无范围过滤仍会横向越权。

返回 404 是不是就解决了越权？

返回码只是是否暴露存在性的策略；若服务端内部已读取或修改未授权记录，再把结果包装成 404 仍然是越权。

自检

用户有 orders.read，GET /orders/8421 返回了别人的订单，问题在认证还是授权？

是对象级授权缺失。认证和动作级授权都可能正确，但资源的用户/租户归属没有被检查。

练习：给订单列表和“批量取消”分别写一条资源范围约束，并说明缓存命中时在哪里再次执行授权。
