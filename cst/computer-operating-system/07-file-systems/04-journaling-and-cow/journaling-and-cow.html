01崩溃一致性问题

第一层

概念与判定

文件系统最怕崩溃一致性：写一半断电，元数据与数据对不上（例如 inode 说有 100 块，实际只写了 50 块）。两种主流解法：

图：日志三段式提交；CoW 走「追加新块」。
机制思想
日志（Journaling）先把「要做的改动」记到日志区，提交后再真正写；崩溃后重放/丢弃未完成的日志
写时复制 CoW任何修改都写到新块，旧块保留；改完原子切换指针。旧版本仍在→快照天然可得
ext4 的 extents：用「起始块+连续长度」描述一片连续空间，代替老式多级间接块，大文件元数据更紧凑、分配更快。崩溃一致性靠 ordered/data=journal/writeback 三种日志模式保证。

02日志模式与快照

第二层

参数·命令·量化

挂载选项与模式

日志模式行为
data=ordered默认；元数据记日志，数据先写盘再提交元数据（折中）
data=journal数据也记日志，最安全但最慢
data=writeback只记元数据，崩溃可能丢/错数据，最快
# 看文件系统与日志状态
df -T /                          # 类型 ext4/xfs/btrfs
 dumpe2fs -h /dev/sda1 | grep -i 'journal'   # ext 日志大小
 mount | grep ' / '

# CoW 文件系统（btrfs/zfs）快照
btrfs subvolume snapshot / /snap1
zfs snapshot pool/fs@snap1

# 强制一致性检查（离线）
fsck -f /dev/sda1
data=writeback 慎用：崩溃后文件可能拿到别的文件的数据（旧块未清零），对多租户/安全场景是泄露风险。

03排障与边界

第三层

排障与边界

  • 断电后 fsck 慢：大文件系统日志重放/检查耗时。CoW 文件系统（btrfs/zfs）靠事务指针，通常挂载即一致，无需长 fsck。
  • 日志区写放大：data=journal 所有数据写两遍，写密集负载吞吐减半。
  • CoW 的碎片问题：频繁小改产生大量新块，旧块变碎片；需要定期「碎片整理/重新平衡」（btrfs balance）。
  • 快照占空间：CoW 快照保留旧块，长期不删会吃满磁盘，要配配额与回收策略。
  • 写屏障（barrier）：掉电时保证顺序，关掉会快但破坏一致性。SSD 有电容缓存时可谨慎评估。

04原理与取舍

第四层

原理与取舍

日志用「额外写一遍 + 原子提交」换一致性；CoW 用「不改原地、写新块」换一致性+快照。前者改原地、需重放，后者天然版本化但产生碎片与空间开销。

维度日志（ext4）CoW（btrfs/zfs）
一致性重放日志恢复事务指针原子切换
快照需 LVM/工具原生、秒级
碎片较少易产生，需整理
写放大journal 模式翻倍CoW 天然多写新块
fsck可能较慢通常挂载即一致

深入 Q&A

Q：为什么 CoW 文件系统快照几乎免费？
A：快照只记录「当前指针」，不改旧块；只有当你之后再改某块时，才复制出旧块保留给快照。所以未被修改的部分快照与当前共享存储。

Q：ext4 为什么不用 CoW？
A：历史包袱与就地更新简单；ext4 用日志+extents 在性能/兼容性上折中。需要原生快照通常上 xfs（有限）/btrfs/zfs。
