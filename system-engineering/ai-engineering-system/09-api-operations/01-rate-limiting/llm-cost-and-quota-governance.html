一句话原则

成本治理不是砍预算，而是让每一分钱都能回答「哪个功能、哪个用户、哪次请求花的」。

COST × QUOTA × FINOPS

LLM 成本与配额治理

限流解决「能不能发」，成本治理解决「发了值不值」。这一篇把 LLM 账单拆成四个乘法项，给出三层配额闸门与按收益排序的六条降本路径，并强调每一条都必须绑定质量指标。

1. LLM 的成本不是「一次调用多少钱」

把 LLM 成本理解成单价 × 次数，是绝大多数预算失控的起点。真实账单由四个乘法项构成， 其中输入 token 往往是被忽略的大头——尤其当系统自带长 system prompt、RAG 召回片段和历史对话时。

成本项怎么算为什么容易被忽略
输入 tokenprompt（含 system / RAG 上下文 / 历史）+ 工具返回结果长上下文下它会反超输出，成为主项
输出 token模型实际生成的文本长度单价通常是输入的数倍，且不可预测
请求次数RPM / 并发槽限流维度与计费维度不一致时会被重复计费
失败与重试超时、被拒、解析失败的调用已消耗 input token 但无产出

关键含义：输出 token 通常比输入贵数倍，所以「让模型多说」比「让模型多看」更花钱； 但长上下文场景（整本文档塞进去、超长对话历史）里，输入会反过来成为主项。两者都要单独计量， 否则你优化错方向。另一个隐性成本是失败重试：一次超时重试，前面已经烧掉的 input token 不会退钱。

最贵的 token 是没产生价值的 token。 用户中途关掉页面、下游解析失败、被安全策略拦截、输出超长被截断——这些请求都计费了却没交付价值。 先统计"计费但未交付"的比例，通常比优化单价收益更大。

2. 计量口径：钱要能归到「谁花的」

只记一个总数 本月花了 3 万 是没法治理的。计量必须能回答三个问题： 哪个功能、哪个用户/租户、哪次请求。

维度标签用途
功能feature=chat / summarize / extract判断哪个功能最烧钱，决定优化优先级
租户 / 用户tenant / user_id配额分配、异常用量发现、对内结算
请求trace_id单请求归因、慢调用与贵调用定位
模型model / provider模型分层是否真的生效

落地方式：在网关层给每次调用打上 feature / tenant / user_id 三个维度标签， 写进 trace 与计费日志。这三个标签必须在请求入口就确定，不能靠事后反推—— 事后反推的归因准确率通常低到不可用。

会话级聚合是关键。 单次调用的 token 数意义不大，真正决定成本的是"一个会话总共烧了多少"。 所以在 trace 之上还需要一层 session 聚合：会话总 token、轮次、平均上下文长度、重复内容占比。

3. 预算与配额：三层闸门

配额不是"设一个上限就完事"。工程上需要三层，且每层的触发动作不同。

层级粒度触发动作
硬上限租户 / 功能 / 全局直接拒绝并返回明确错误码，绝不放行
软阈值按日/周预算的 70–80%%告警 + 自动降级（切小模型、缩短上下文）
异常检测单用户 / 单会话与历史基线比较，突增时人工介入或临时限流
软阈值必须配「人能看到」。 很多团队设了 80% 告警却没人看，或者告警发到没人管的群。软阈值有效的唯一标准是： 有人收到后会真的去处理，且有明确的处理动作（限功能、降模型、找业务方确认）。

4. 降本六招，按收益排序

  1. 减少无效调用 — 请求去重、结果缓存、空输入拦截、用户已离开则取消生成。这一条通常收益最大且零风险。
  2. 缩短上下文 — 历史对话摘要化、RAG 召回重排后只留 top-k、去掉重复的系统提示。直接砍掉输入主项。
  3. 约束输出长度 — 给 max_tokens 设业务合理上限，并在提示里要求结构化简短输出。
  4. 模型分层路由 — 简单意图走小模型，复杂任务才上大模型。必须配质量抽检，否则容易静默劣化。
  5. 利用提示缓存 — 把稳定的 system prompt / 长文档前置，命中缓存的输入通常有明显折扣（以厂商实际政策为准）。
  6. 批处理 — 离线、非实时任务走批处理队列，通常用更低单价换取更长延迟。
别为了省钱把质量降没了。 降本必须绑定质量指标：切小模型后要对比同一批评测集的效果，缩短上下文后要对比召回率与答案完整度。 省下的钱如果换来用户流失，是负收益。任何降本动作上线前先跑评测，上线后持续看质量指标。

5. 落地清单

  • 网关已按 feature / tenant / user 三个维度打标，并能出账单
  • 输入与输出 token 分开统计，能看到各自占比
  • 会话级聚合可用：单会话总 token、轮次、平均上下文长度
  • 三层配额（硬上限 / 软阈值 / 异常检测）都已配置且各自有明确动作
  • 「计费但未交付」的比例有统计（取消、超时、被拦截、解析失败）
  • 每次降本动作都绑定了质量评测，上线后有持续监控
  • 限流维度（RPM/TPM/并发）与计费维度对齐，不会出现「限流通过但账单爆了」
