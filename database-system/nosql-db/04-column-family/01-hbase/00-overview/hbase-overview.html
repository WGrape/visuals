🐘 HBase 概览

构建在 HDFS 之上的分布式列族数据库：它能做什么、不能做什么

一句话定位

HBase 是运行在 HDFS 之上的、面向列族的分布式 NoSQL 数据库，是 Google BigTable 的开源实现。它把 HDFS「只能追加、不能随机改」的弱点补上了——提供低延迟的随机读写，同时保留 HDFS 的横向扩展与容错能力。典型规模：单集群数百节点、单表数十亿行、千万列。

数据模型稀疏、多维、按行键排序的映射表；无类型（全字节数组）
存储底座HDFS（默认），也可用本地 FS / 对象存储
协调能力ZooKeeper 负责选主、Region 寻址、故障检测
强一致每行（rowkey）由单一 RegionServer 负责 → 行级强一致

整体架构

四个关键机制

① LSM-Tree：写优先

写入先进内存 MemStore（有序），攒够了顺序刷成不可变的 HFile。随机写被转化成顺序写，所以 HBase 写入非常快；代价是读可能要合并多个文件，靠后台 compaction 缓解。

② Region 自动分片

表按 rowkey 范围横向切成多个 Region，分散到不同 RegionServer。Region 太大（默认 10GB）自动split 成两个，实现自动扩容。

③ 行级强一致

一个 rowkey 在任一时刻只属于一个 Region、由一个 RegionServer 服务，因此对该行的读写天然串行化。没有跨行事务（只有行内原子）。

④ 依托 HDFS 的容错

HFile 在 HDFS 上三副本；RegionServer 挂了，HMaster 把它负责的 Region 重新分配到别的节点，靠 WAL 重放恢复未刷盘的数据。

基本操作

# Shell 上手
hbase shell
> create 'user', 'info', 'stat'          # 建表，声明两个列族
> put 'user', 'u001', 'info:name', 'Alice'
> put 'user', 'u001', 'info:age', '30'
> get 'user', 'u001'                     # 取整行
> get 'user', 'u001', 'info:name'
> scan 'user', { STARTROW => 'u001', ENDROW => 'u010', LIMIT => 10 }
> delete 'user', 'u001', 'info:age'
> disable 'user'; drop 'user'            # 删表必须先 disable
> describe 'user'
> status 'detailed'

🎯 常见问法与答题要点

Q：HBase 和 HDFS 是什么关系？能脱离 HDFS 吗？

A：HBase 是跑在 HDFS 之上的数据库：HDFS 只提供「分块存储 + 多副本 + 顺序追加」，不支持随机修改和毫秒级查询；HBase 在它上面补齐了 MemStore + WAL + LSM 索引 + Region 路由，才有了随机读写能力。可以脱离 HDFS 改用本地文件系统（单机测试）或对象存储（如 S3A），但生产基本都用 HDFS，因为副本与容错全靠它。

Q：HBase 是 CP 还是 AP？

A：在 CAP 里偏 CP：网络分区时宁可让部分 Region 短暂不可用，也不返回不一致的数据。原因是每个 rowkey 只由一个 RegionServer 负责，主从切换期间该 Region 不可用（通常几秒到几十秒，取决于 WAL 重放量）。这与 Cassandra 的可调一致性形成鲜明对比。

Q：为什么 HBase 写这么快？

A：三个原因叠加：①LSM-Tree 把随机写变成顺序写——写入只进内存有序结构，攒够再顺序刷盘；②WAL 也是顺序追加；③写入不立刻修改磁盘上的旧文件（HFile 不可变），没有 B+Tree 那种随机页分裂。代价是读放大（要查多个文件），靠 compaction 和 BloomFilter 缓解。

Q：HBase 支持 SQL 吗？

A：原生不支持，只有类似 shell 的 put/get/scan。要 SQL 需要上层组件：Phoenix（最主流，把 SQL 编译成 HBase scan，支持二级索引）、Hive 外表（走 MapReduce/Spark，适合批处理）、Spark SQL。注意 Phoenix 的 SQL 能力不等于 MySQL，JOIN 和复杂子查询仍然受限。

Q：HBase 有事务吗？

A：只有行级原子性：对同一个 rowkey 的多个列（甚至跨列族）的 put 是原子的，checkAndPut/checkAndDelete 提供行级 CAS。没有跨行、跨表事务。需要跨行一致性时，得靠应用层做补偿或用 Phoenix 的事务支持（有限）。

Q：一张 HBase 表能有多大？

A：理论无上限，靠 Region 自动分裂横向扩展。生产上常见单表数 TB 到数十 TB、数十亿行。真正的限制不在表大小，而在Region 数量与 rowkey 设计：Region 过多（> 数千/节点）会拖累 flush 与 compaction，rowkey 设计不当会造成热点，这两点才是瓶颈。

Q：删除数据后空间会立刻释放吗？

A：不会。delete 只是写一个墓碑标记（tombstone），真正删除发生在后续的 compaction 合并文件的时候。所以删完立刻 scan 看不到（读时墓碑会屏蔽旧版本），但磁盘空间要等 major compaction 之后才回收。这也是为什么不能频繁做全表删除又期望马上腾空间。
