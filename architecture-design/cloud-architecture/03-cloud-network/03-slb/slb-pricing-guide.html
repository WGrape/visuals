💡 为什么要考虑带宽？

带宽是核心成本因素

  • ▸ SLB 作为流量入口，所有请求都经过它
  • ▸ 带宽直接决定了能承载的最大流量
  • ▸ 超出规格会触发限流，影响业务

带宽与性能指标的关系

  • ▸ 并发连接数 × 平均请求大小 = 带宽需求
  • ▸ 新建连接速率影响突发带宽峰值
  • ▸ 带宽不足会导致请求排队、超时

负载均衡产品怎么选：先分清四层与七层

选型的第一步不是比价格，而是确定工作层级——这决定了能提供什么能力，也决定了大致的价格区间。

类型工作层能力典型价格水平
四层负载均衡（L4）传输层（TCP/UDP）按 IP+端口转发，不解析内容；性能极高（百万级并发），延迟极低较低（按实例 + 流量/连接数计费）
七层负载均衡（L7）应用层（HTTP/HTTPS）可按域名、URL、Header 路由；支持 TLS 终止、HTTPS 证书托管、会话保持、改写较高（通常按 QPS / LCU 计费）
网关型负载均衡L3/L4 + 高级用于第三方安全设备（防火墙、IDS）的流量编排视厂商而定
传统型（已逐步淘汰）L4/L7 混合老产品，功能与性能均受限低，但不建议新业务使用
负载均衡计费四要素与常见隐性成本

成本估算：一个具体例子

场景：一个面向公网的 Web 服务 日均 PV 50 万 峰值 QPS 800 平均响应大小 30 KB 月出网流量 ≈ 50万 × 30KB × 30 天 ≈ 450 GB 费用构成（示意，实际以厂商报价为准）： ① 实例费 1 个实例 × 月费 ② 容量费 按峰值 QPS 800 对应档位 / 或 LCU ③ 流量费 450 GB × 单价 ④ 公网 IP 1 个（若绑定 EIP，闲置也收费） 优化点： · 上 CDN → 90% 静态请求由 CDN 承担，LB 流量降到 1/10，③大幅下降 · 开启 gzip/brotli → 响应体减小 60%~80%，③再降 · 图片转 WebP/AVIF → 传输量再降 30%~50% · 后端与 LB 同可用区 → 免跨区流量费 · 稳定负载买预留/包年 → ①②可降 30%~50% 结论：绝大多数「负载均衡太贵」其实是「流量太贵」， 解法在上游（CDN + 压缩 + 图片优化），而不是换 LB 规格。

选型决策树

按协议选

  • HTTP/HTTPS → L7（需要域名/URL 路由、证书托管、HTTPS 卸载）
  • 纯 TCP（数据库代理、MQ、游戏）→ L4
  • UDP（音视频、DNS、QUIC）→ L4（需确认支持 UDP）
  • gRPC/HTTP2 → L7（需确认支持）

按规模选

  • 小流量、起步阶段 → 弹性规格/按量付费，避免固定支出
  • 稳定中高流量 → 预留规格或包年，通常有折扣
  • 超大流量、极致性能 → 需关注单实例上限与是否需要分片/多实例

按可用区选

  • 必须选多可用区版本才有高可用（单可用区的 LB 是单点）
  • 注意跨可用区流量费——LB 与后端尽量同区，或评估「跨区费用 vs 可用性收益」
  • 同城双活/多区域 → 需要全局负载均衡（GSLB）配合 DNS 调度

功能清单核对

  • 健康检查（HTTP/TCP，可自定义路径与阈值）
  • 会话保持（Cookie 注入 or 源 IP）— 会影响均衡性，能不用就不用
  • TLS 版本与证书管理、是否支持 HTTP/2、HTTP/3
  • 访问日志与监控指标是否齐全（排障必需）
  • 是否支持权重、灰度、连接 draining（优雅摘除）

降本与避坑

  • 先优化流量再优化规格。流量费通常是大头，上 CDN + 开压缩 + 图片格式优化，效果远大于换便宜的 LB。
  • 清理闲置实例与公网 IP。测试环境的 LB、已下线业务绑定的弹性 IP，忘记释放会持续计费。
  • 注意跨可用区流量。LB 与后端不在同一可用区会产生双向跨区费用，流量大时这笔钱很可观。多可用区 LB 要注意它是否会产生跨区转发。
  • 弹性规格要设上限。按量计费的弹性 LB 在遭受攻击或流量异常时，费用可能失控，务必配置规格上限与预算告警。
  • 不要把 LB 当网关用。复杂的鉴权、限流、改写逻辑放在 LB 上（尤其是用大量重写规则）会拖累性能且难以维护，应交给 API 网关。
  • 预留规格要基于真实数据。先按量跑一到两个月，拿到真实的峰值与均值曲线再决定买什么档位，避免买多浪费或买少限流。

深入自检

四层和七层负载均衡性能差多少？

差距明显但不是绝对的。四层只做 NAT/DR 方式的转发，不解析报文内容、不需要建立完整的应用层连接，单机可以支撑百万级并发连接、吞吐达数十 Gbps，延迟增量通常在亚毫秒级。七层需要解析 HTTP 头、可能做 TLS 解密、路由匹配、改写，CPU 开销大得多，单机通常是万到十万级 QPS 量级，延迟增量也在毫秒级。不过现代云厂商的 L7 负载均衡（如基于 Envoy/DPDK 的实现）性能已经很强，对绝大多数业务都够用。选择时更应关注能力需求：需要按 URL 路由、证书托管、HTTP 特性就用 L7；代理数据库、MQ 或追求极致性能就用 L4。很多架构是两者叠加：L4 做第一层扛量，L7 做业务路由。

会话保持（Session Sticky）该开吗？

原则上能不开就不开。会话保持会把同一用户的请求固定到某台后端，带来三个问题：① 负载不均——某些用户请求量大导致热点；② 扩缩容与故障时，绑定到已下线实例的用户会话会中断；③ 掩盖了「应用有状态」这个根本问题，让架构无法真正水平扩展。正确做法是把应用改成无状态（会话放 Redis），然后关闭会话保持，让请求自由分发。例外情况：遗留系统短期内无法改造、或某些协议要求连续请求落到同一节点（如 WebSocket 的长连接、特定文件上传的分片合并），这时才开启，并尽量用 Cookie 方式而非源 IP（源 IP 方式在 NAT 出口下会把大量用户绑到同一台机器）。

负载均衡本身会不会成为瓶颈或单点？

云厂商的负载均衡通常是分布式集群 + 多可用区部署，本身不是单点（这是它相对自建 Nginx 最大的价值）。但仍有需要注意的地方：① 要选择多可用区版本，单可用区版本在该可用区故障时会整体不可用；② 有规格上限（最大并发连接、QPS、新建连接速率），超出会被限流，需要提前评估或在流量突增前扩容；③ 受攻击时可能触发限速或产生高额费用，需要配合高防与告警；④ 云厂商自身故障会波及——这是所有托管服务的固有风险，关键业务应考虑多厂商或多地域容灾。

怎么判断负载均衡配置是否正确？

四个检验点：① 健康检查是否真实——只检查端口通不够，应检查业务健康端点；阈值要避免抖动误判（连续几次失败才摘除，连续几次成功才恢复）；② 后端摘除是否优雅——后端实例下线时应先停止新请求、处理完存量再退出（连接 draining），否则发布期间会有错误；③ 超时配置是否合理——LB 的空闲超时要大于应用的正常响应与长连接维持时间，否则会断开长连接（如 WebSocket、SSE、长轮询）；④ 请求头是否透传——X-Forwarded-For / X-Forwarded-Proto 要正确传递，否则后端拿不到真实客户端 IP、生成的链接协议也会错。验证方法：发布与摘除实例时观察错误率是否上升，理想情况应为零。
