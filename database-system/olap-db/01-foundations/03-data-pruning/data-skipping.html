列式分析中的分区裁剪与数据跳过

能少读多少数据，往往比单核执行速度更影响分析查询。

核心机制

分区裁剪利用分区键排除整个时间或业务分区。数据跳过还可利用块级最小最大值、索引或排序键排除不可能命中的数据块。列裁剪只读取查询需要的列。

谓词下推把筛选尽量移到扫描阶段，但并非所有表达式都能下推。对分区列施加不可识别的函数，或者把数据随机散布，可能让裁剪效果变差。

用一个例子看过程

WHERE event_date >= DATE '2026-10-01'
  AND event_date < DATE '2026-11-01'
  AND region = 'east'

先看分区

时间范围能否排除其他月份分区；确认过滤条件与分区键类型一致。

再看数据块

region 若与排序/聚簇相关，块统计可进一步跳过不相关区域。

最后看列

只读取聚合需要的列，并检查解压和向量化执行的剩余成本。

观察、原因与处理

观察原因或含义处理与验证
扫描字节高时间条件未触发分区裁剪查看执行计划与分区命中数
块跳过率低过滤列在各块中分布太散评估排序键或聚簇策略
CPU 仍高表达式和聚合开销大看向量化、预聚合和列裁剪

三层“少读数据”

分区裁剪首先排除整个时间或业务分区。按月分区的事件表查询十月，若谓词能被引擎识别，其他月份可不进入扫描。块级数据跳过再利用最小最大值、排序键或索引排除不可能命中的块。列裁剪则只读取查询真正使用的列。这三层作用在不同粒度，不能把“有分区”误当成“分区内会读得很少”。

谓词下推把筛选尽量移到扫描阶段，但是否可下推取决于表达式与引擎能力。若过滤列在每个数据块都随机分布，块的最小最大值范围高度重叠，统计信息也难以跳过。把分区列包进引擎无法识别的复杂函数，可能降低分区裁剪效果。

从执行计划读证据

证据可能含义下一步
扫描分区数很高时间谓词未有效裁剪核对分区键类型和过滤条件
分区少但扫描字节仍高块值域重叠或过滤列分布散评估排序键与聚簇策略
扫描字节低但 CPU 高表达式或聚合开销大查看向量化、预聚合与函数成本
只读一列仍慢容量或排队成为瓶颈拆解 I/O、CPU 与队列时间

调优实验要固定数据规模和缓存状态，比较实际扫描行数、字节数与耗时。只看计划的估计值可能被过期统计误导；只看耗时又可能把缓存命中误认为布局改进。

练习：让时间条件可裁剪

查询按 event_date 分区的表时，用明确的半开区间表达十月：event_date 大于等于十月一日且小于十一月一日。检查计划是否只触达十月分区，再对 region 谓词比较块跳过率。若仍扫描大量块，问题可能在数据布局，而不只是 SQL 写法。

边界与误区

区块统计只能证明某些块不可能命中，不能保证所有数据布局都有效。不同引擎的索引、统计和下推能力各异，应以执行计划和实际扫描量验证。

一个可重复的调优实验

选取一条真实慢查询，记录原始数据量、分区数、扫描行数、扫描字节、CPU 时间和端到端耗时。先只改写时间过滤为与分区键同类型的半开区间，确认分区数量是否下降；再保持查询不变，改变数据的排序或聚簇策略，观察块跳过率；最后才比较列裁剪或表达式优化。每次只改一个因素，避免把缓存预热、并发波动和布局变化混在一起。

最小最大值索引对按时间排序的连续数据通常有效，因为不相关时间段的块范围分离；对随机 UUID 或每块都有所有 region 的数据则可能效果很差。数据重排又有写入放大和维护成本，不能为了单条查询盲目重建全表。评估时使用整体工作负载：既要看被优化查询，也要看写入吞吐、合并任务和其他查询是否退化。

让排序键服务主要工作负载

按时间排序可帮助时间范围查询跳过无关块，按客户排序则可能改善客户级查询；两者未必能同时达到最优。选排序或聚簇键前，统计真实查询的过滤列、时间范围、扫描字节和频率，再评估写入合并成本。若高频查询总是按日期加地区过滤，可测试两种键顺序并比较块值域；键的前缀顺序常影响跳过效果。数据增长后还要复测，因为初期小表全部可缓存时，任何布局看起来都很快。调优结论应基于稳定的数据规模和代表性并发。

进一步验证

在索引或排序优化前，先确认查询真正只需要哪些列。SELECT * 会让列式系统读取、解压许多无关列，掩盖分区和块跳过带来的收益。把返回字段限定为图表所需列，并记录网络传输字节，才能区分“扫描变少”与“结果发送变少”两种改善。

补充判断

如果查询过滤条件高度选择性却仍慢，还要检查结果集是否很大。数据跳过只减少读取，不能消除返回百万行的网络和客户端渲染成本；分页、预聚合或改变产品交互可能比继续加索引更有效。

数据裁剪手段与效果

手段原理典型裁剪率 / 适用
分区（Partition）按日期/地区分成子目录按分区键查询可裁掉 90%+ 数据；最有效
Min-Max 索引（Zone Map）每块记录列的最小最大值有序数据裁剪率 90%+；无序数据几乎无效
排序键 / 聚簇让相关数据物理相邻是 min-max 生效的前提
布隆过滤器判断某值是否不在块内高基数的等值查询；有 1% 假阳性（不会漏判）
二级索引 / 跳数索引额外索引结构ClickHouse 的 skip index；有存储与写入开销
列裁剪只读需要的列列存天然优势，宽表查询快 5~20×
物化视图 / 预聚合预先算好固定维度查询快 10~100×；牺牲灵活性
粗粒度索引（Granule）ClickHouse 默认 8192 行 一个 granule索引只记录 granule 级信息

为什么排序键是核心：min-max 索引的裁剪能力完全取决于数据是否局部有序。若按 ORDER BY (date, user_id) 存储，查 date='2026-10-22' 能精确定位到连续区间；若不排序，同一个 date 散落在所有块里，每个块的 min-max 都覆盖全范围，一块都裁不掉。

ClickHouse / Doris 实操

-- ClickHouse：建表时指定分区与排序键（最关键的两个决定）
CREATE TABLE events (
    date      Date,
    user_id   UInt64,
    event     LowCardinality(String),
    amount    Decimal(18,2)
) ENGINE = MergeTree
PARTITION BY toYYYYMM(date)        -- 按月分区，便于按 TTL 整月删除
ORDER BY (date, user_id, event)    -- 排序键决定 min-max 的裁剪能力
SETTINGS index_granularity = 8192; -- 默认 8192 行一个 granule

-- 查看一次查询到底读了多少数据（裁剪效果的直接证据）
SELECT query_duration_ms, read_rows, read_bytes,
       read_bytes / 1024 / 1024 AS read_mb, result_rows
FROM system.query_log
WHERE type = 'QueryFinish' ORDER BY event_time DESC LIMIT 5;
-- read_rows 远小于 total_rows 说明裁剪生效；接近全表说明没裁掉
-- ClickHouse：跳数索引（针对非主键列）
ALTER TABLE events ADD INDEX idx_amount amount TYPE minmax GRANULARITY 4;
ALTER TABLE events MATERIALIZE INDEX idx_amount;   -- 对存量数据生效

-- set 型索引适合高基数值的等值过滤
ALTER TABLE events ADD INDEX idx_user user_id TYPE set(0) GRANULARITY 4;
-- bloom_filter 适合 LIKE / IN
ALTER TABLE events ADD INDEX idx_event event TYPE bloom_filter(0.01) GRANULARITY 4;

-- Doris/StarRocks：前缀索引 + Bitmap/BloomFilter
CREATE TABLE t (
  dt DATE, k1 VARCHAR(20), k2 INT, v BIGINT SUM
) AGGREGATE KEY(dt, k1, k2)          -- 前 36 字节自动成为前缀索引
DISTRIBUTED BY HASH(k1) BUCKETS 10
PROPERTIES ("replication_num" = "3");
ALTER TABLE t SET ("bloom_filter_columns" = "k2");

裁剪失效排查

症状原因处理
加了索引但没变快排序键不含查询条件列；或数据无序把高频过滤列放进 ORDER BY 的前面
查询仍扫全表条件上用了函数（toDate(ts)='...'）改成对常量的范围条件：ts >= '2026-10-22' AND ts < '2026-10-23'
min-max 不起作用该列与排序键无关，值随机分布改排序键；或为该列建 skip index
分区裁剪没生效分区键与查询条件不一致查询条件要直接命中分区键；避免对分区键做函数变换
分区太多反而慢分区数几千上万，元数据开销大按月而不是按天分区；单表分区数控制在百级
小文件太多每批写入都生成新 part批量写入（单次 ≥ 1万行）；或定期 OPTIMIZE TABLE ... FINAL
读的字节数远大于结果没做列裁剪（用了 SELECT *）只查需要的列，列存下这一条能差 10 倍

判断标准：看 read_rows / total_rows。好的裁剪应该 < 1%；如果这个比例是 100%，说明所有裁剪手段都没生效，先查排序键和查询条件的写法。

自检

为什么给 WHERE 条件加了索引，查询仍可能扫描大量数据？

数据块值域可能高度重叠，或谓词无法利用该索引；需要核对布局、计划和实际扫描字节。
