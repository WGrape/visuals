构建系统基础：Make、CMake 与 Ninja 的分工

为什么需要构建系统、Make 的规则写法、CMake 的生成式工作流，以及并行构建的依赖完整性

构建系统MakeCMakeNinja增量构建
① 为什么需要 ② Make ③ CMake ④ 并行 ⑤ 疑问
一句话总结：构建系统做的事只有两件：描述依赖图（谁依赖谁），和决定哪些要重建（增量）。Make 直接用规则描述，CMake 用更高级的描述生成构建文件，Ninja 只负责飞快地执行。理解三者的分工，就不会纠结「该用哪个」。

01为什么需要构建系统

从源码到可执行文件的依赖链，以及三种构建工具的分工

小项目手写 gcc main.c -o app 没问题。但项目一大就会出现三类靠手工解决不了的问题：

🔗 依赖复杂度

几百个文件、跨目录、还依赖第三方库。谁先编译、谁要重编译，人脑维护不了。

⚡ 增量构建

全量编译一次几十分钟。改一个文件只重建受影响的部分，是构建系统最核心的价值。

🌍 跨平台

编译器路径、库后缀、链接参数在 Linux/macOS/Windows 上完全不同。

🔁 可重复性

「在我机器上是好的」——构建配置没固化，换台机器就编不出来。

要点：判断标准很简单：当你开始写 build.sh 拼一堆编译命令时，就该上构建系统了。

02Make：规则与时间��判定

Make 的核心是一行规则：目标 → 依赖 + 命令。判定时比较文件修改时间：如果任一依赖比目标新，就执行命令重建。

# 基本形态
target: prerequisites
recipe

# 实际例子
CC      = gcc
CFLAGS  = -O2 -Wall
OBJS    = main.o utils.o net.o

app: $(OBJS)
$(CC) $(OBJS) -o app

# 模式规则：所有 .c 生成同名 .o
%.o: %.c
$(CC) $(CFLAGS) -c $< -o $@

# 自动变量（写规则必记）
#   $@  目标名          $<  第一个依赖      $^  所有依赖
#   $?  比目标新的依赖   $*  模式匹配的主干

.PHONY: clean          # 声明伪目标：clean 不是文件
clean:
rm -f $(OBJS) app
概念含义注意
target要生成的东西（文件）同名文件不存在时一定执行
prerequisites依赖的文件或其他目标任一比目标新 → 重建
recipe重建命令必须用 TAB 缩进，空格会报错
.PHONY声明不是文件的伪目标clean/all 这类必须声明，否则同名文件会让规则失效
要点：Make 最常见的两个新手错误：① recipe 用了空格缩进；② 忘了声明 .PHONY。

03CMake：生成式构建

CMake 自己不编译，它生成 Make/Ninja/Visual Studio 的工程文件，再由后者执行。这一层间接换来的是跨平台能力。

cmake_minimum_required(VERSION 3.16)
project(myapp C)

set(CMAKE_C_STANDARD 11)
set(CMAKE_C_STANDARD_REQUIRED ON)

# 可执行文件 + 源文件
add_executable(app
    src/main.c
    src/utils.c
    src/net.c
)

# 头文件搜索路径
target_include_directories(app PRIVATE include)

# 链接库（现代 CMake 用 target_* 形式，作用域明确）
target_link_libraries(app PRIVATE m pthread)

# 编译选项
target_compile_options(app PRIVATE -Wall -Wextra)

# 查找第三方库
find_package(OpenSSL REQUIRED)
if(OpenSSL_FOUND)
    target_link_libraries(app PRIVATE OpenSSL::SSL)
endif()
# 典型工作流：源码外构建（build 目录与源码分离）
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build                 # 编译（-G 用什么就调什么）
cmake --build build --target clean
cmake --build build --parallel 8    # 并行

# 为什么用「源码外构建」：
#   构建产物都在 build/ 下，不会污染源码目录，清理只需删一个目录
工具定位适合不适合
Make规则执行器 + 依赖图小项目、Unix 脚本化构建跨平台、大型项目
CMake生成器（产出 Makefile/Ninja/VS 工程）C/C++ 事实标准，跨平台项目追求极致简洁的小项目
Ninja极快的执行器由 CMake/Meson 生成后使用手写（语法不友好）
Meson / Bazel 等各有侧重（速度 / 大规模多语言）大规模或多语言仓库小项目引入成本高
要点：记住这条链：CMake 描述「要构建什么」，Ninja/Make 负责「怎么快速构建」。新项目推荐 CMake -G Ninja。

04并行构建与依赖完整性

make -j8 / cmake --build . --parallel 8 能大幅提速，但它有一个前提：依赖图必须完整。缺依赖声明在串行时可能碰巧能过，并行时一定偶发失败。

  • 并行加速的极限：受依赖图的关键路径限制，不是核越多越快。链接阶段通常是串行的瓶颈。
  • 缺依赖声明的表现：并行构建偶发失败，重新跑一次又好了——这是典型的依赖缺失症状。
  • 头文件依赖最容易漏：改了头文件但 .o 没重建，程序行为和源码不一致，极难排查。
  • 伪目标的并行问题：多个目标写同一个文件时并行会冲突，需要显式声明顺序依赖。
# 解决「改了头文件不重编」：自动生成 .d 依赖文件
CFLAGS += -MMD -MP          # -MMD 生成 .d；-MP 为每个头文件生成空目标，避免删头文件后报错

%.o: %.c
$(CC) $(CFLAGS) -c $< -o $@

-include $(OBJS:.o=.d)      # 减号表示文件不存在也不报错（首次构建）

# CMake 会自动处理头文件依赖，这也是它比手写 Makefile 省心的关键点之一
要点：「改了头文件却没生效」是 C/C++ 构建里最经典的坑，根因几乎总是缺少 .d 依赖文件。用 CMake 或加 -MMD -MP 可根治。

05常见疑问

问：小项目也要用 CMake 吗？

如果是单文件练习，直接 gcc 就行。但只要超过五六个源文件、或者需要给别人用，上 CMake 的成本远低于收益——它顺手解决了头文件依赖、跨平台和 IDE 工程生成。

问：为什么 make 说「target is up to date」但我的改动没生效？

三种常见原因：① 改动的文件不在依赖列表里（典型是头文件）；② 时间戳问题（文件被回写成了旧时间，或时钟回拨）；③ 你改的是被 include 的生成文件，但生成规则没声明。

问：CMake 和 Makefile 能混用吗？

能。CMake 可以调用外部 Makefile（add_custom_target），也可以在 CMake 生成的 Makefile 里加自定义目标。但混用会让构建逻辑变复杂，新代码尽量统一到 CMake 体系。

问：构建慢该怎么优化？

按性价比排序：① 开并行（-j）；② 用 Ninja 替代 Make；③ 减少不必要的头文件依赖（前置声明、减少头文件包含）；④ 用 ccache 缓存编译结果；⑤ 拆分过大的翻译单元。
