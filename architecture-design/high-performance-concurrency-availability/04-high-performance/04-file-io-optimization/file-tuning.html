文件 IO 优化

提升磁盘吞吐、减少 syscall：批量、顺序化与零拷贝。

批量与缓冲

少 syscall 多干活

用带缓冲的写入（BufferedWriter）、累积到一定量再 flush，或用一次大块写替代大量小 write，能显著减少系统调用与上下文切换。

日志、WAL 等场景尽量追加写（append-only），让磁盘始终做顺序写；必要时用合并写把随机变成顺序。

fsync 策略的代价

每次写都 fsync 最安全但最慢；完全不 fsync 最快但可能丢数据。折中是按批次/定时 fsync，或依赖 WAL + 副本保证持久性。

问题 1
如何提升磁盘写入吞吐？

用缓冲/批量写减少 syscall，保持顺序追加写，增大写入块大小，必要时用零拷贝转发。关键是把「大量小 IO」聚成「少量大 IO」。

问题 2
零拷贝对文件服务有什么用？

文件下载/转发时用 sendfile/splice，数据直接在内核态从磁盘到网卡，省去两次拷贝和一次用户态中转，CPU 与内存都更省。

问题 3
fsync 太频繁会有什么问题？

每次 fsync 都触发一次持久化等待，把吞吐压到磁盘的「每秒 fsync 上限」。通常改为攒批 fsync 或依赖 WAL + 副本，在性能与安全间取平衡。

问题 4
预读（readahead）什么时候有效？

顺序读大文件时最有效，内核会提前把后续块读进缓存。随机读则几乎无效甚至污染缓存，此时应关小预读或改用 direct IO。

文件 I/O 调优的三层：应用 / 文件系统 / 设备

磁盘慢不一定换 SSD 才能解决。调优有三个层次：应用层（减少 IO 次数、批量、顺序化、缓存）、文件系统层（挂载选项、调度器、预读）、设备层（RAID、队列深度、SSD 特性）。先做应用层，收益最大成本最低。

常见场景的优化套路

① 日志类写入

  • 追加写（顺序），避免随机修改。
  • 批量刷盘：攒够一批或定时 fsync。
  • 按大小/时间滚动，避免单文件过大。
  • 异步写 + 独立磁盘，避免影响业务 IO。
  • 考虑压缩与采样，降低写入量。

② 数据库类

  • 数据与日志分盘（不同物理设备）。
  • 合理设置缓冲池大小，减少物理读。
  • SSD + 适当队列深度；机械盘减少随机。
  • 批量提交、组提交（group commit）降低 fsync 次数。
  • 定期维护：统计信息、碎片整理、压实。

③ 静态文件服务

  • sendfile 零拷贝。
  • 依赖页缓存：热文件自然留在内存。
  • 开启 gzip/brotli（注意 CPU 与缓存版本）。
  • 用 CDN 卸载源站压力。
  • 合理设置缓存头，减少回源。

④ 容器与云盘

  • 了解云盘的 IOPS/带宽上限与突发额度。
  • 容器写层开销：大量写应挂卷而非写容器层。
  • 注意 cgroup 的 IO 限制（blkio/io.max）。
  • 本地 SSD vs 网络盘延迟差异巨大。
  • 监控要看到设备层（云监控 + 系统指标）。

深入自检

为什么 iostat 显示 util 100% 但磁盘吞吐并不高？

因为 util 只表示设备「有请求在处理」，不代表带宽饱和。随机小 I/O 时，机械盘大量时间用于寻道旋转，SSD 则可能是写放大或垃圾回收。要结合 await、队列长度、读写带宽与 IOPS 一起看，并区分是随机还是顺序（可用 blktrace 或 iostat 的请求大小间接判断）。

noatime 为什么能提升性能？

因为默认每次读取文件都会更新 atime（访问时间）这个元数据，导致「读操作也要写盘」。用 noatime（或折中的 relatime）可以消除这些额外的元数据写，对读多写少的负载收益明显。风险是依赖 atime 的功能（某些邮件/备份工具）会失效。

SSD 上还需要 I/O 调度器吗？

通常需要关掉或选最简单的。传统调度器（cfq/deadline）的设计目标是优化机械盘寻道，对 SSD 没有意义反而增加开销。NVMe 用 none（noop）或 mq-deadline 即可，让设备自身的并行队列发挥作用。

为什么 SSD 写满后性能会下降？

因为 SSD 不能原地覆写，必须先擦除整块再写。可用空间不足时，每次写都要先做「读-改-擦-写」（写放大），还要频繁垃圾回收，延迟显著上升。对策：保留一定空闲空间（over-provisioning）、开启 TRIM、避免写满、监控磨损指标。

云盘（网络块存储）调优有什么不同？

关键差异：延迟高于本地盘（通常 0.5-2ms）、有 IOPS 与带宽的双重上限、可能有突发额度（burst credit）用尽后被限流。所以要：选择合适的盘型与容量（IOPS 常随容量提升）、监控额度消耗、批量大块写以提升效率、并避免依赖极低延迟的同步 fsync。

如何判断 IO 瓶颈是应用还是设备？

看三层指标：应用层的 IOPS 与请求大小（是否合理）、块层的队列与等待（是否有排队）、设备层的响应时间（是否真的慢）。若请求已经合并、批量且顺序，设备仍慢 → 设备问题；若大量随机小请求 → 应用问题（可通过改造访问模式大幅改善）。
