容器镜像分层与 Digest：同一个 tag 为什么可能部署出不同代码

沿 Dockerfile 构建、层缓存、多架构清单和部署拉取路径解释可复现性与密钥泄露边界。

tag 是名字，digest 指向内容

镜像通常由清单、配置和多个只读文件层组成，容器运行时把这些层与可写层组合成文件系统视图。`service:latest` 这类 tag 是仓库里的可变引用，今天可指向构建 A，明天可改指向构建 B；不同节点在不同时间拉取同一 tag，可能得到不同字节。Digest 是按内容计算的标识，部署固定 `service@sha256:...` 能更明确指定镜像对象。多架构镜像可能先指向一个镜像索引，再按 CPU 架构选择具体平台的清单与层；核对内容时应写清固定的是索引 digest 还是平台清单 digest。

固定 digest 不保证镜像安全，只解决“究竟拉了哪份内容”的一部分。镜像仍要有来源、签名或可信构建记录、漏洞扫描与更新流程。

图解：从构建到运行的镜像身份

沿箭头逐步核对输入、变换和输出；下面的推演可以逐步切换。

Dockerfile 顺序会改变缓存命中

假设先 `COPY . .`，再安装依赖。只改一行应用代码也会改变前面 COPY 步骤的输入，后续依赖安装层可能失去缓存而重新运行。若先复制依赖清单和锁文件、安装依赖，再复制应用源码，代码小改动通常只影响后段层，构建更快。具体缓存键取决于构建器、指令、上下文和构建参数；不能把“层完全等于 Dockerfile 一行”当作所有构建系统的物理实现定律。

构建上下文也要收敛。把测试数据、私钥、临时下载目录一并发送给构建器，会拖慢构建并增加泄露风险；`.dockerignore` 需与项目文件布局一致。多阶段构建可以把编译工具留在 builder 阶段，只把产物复制进运行阶段，减小运行镜像和攻击面。

删除文件不等于删掉旧层秘密

若某层执行 `COPY secret.txt /app/secret.txt`，下一层再 `RUN rm /app/secret.txt`，最终容器视图中看不到文件，但旧的只读层可能仍包含秘密，镜像历史和缓存也可能留痕。因此密钥不应通过构建上下文或命令参数进入持久层；应使用构建器支持的临时 secret 机制，并在泄露发生后轮换密钥、重建并清理受影响产物。单纯重新打 tag 不会改变已发布层内容。

镜像里也不应固化生产环境配置或个人令牌。运行时通过受控配置和凭据注入，并限制容器读取权限。Secret 对象本身还有存储与访问控制要求，不能因为名叫 Secret 就视为自动安全。

对象可否改变指向排障时看什么
tag可以重新指向不同镜像仓库当前指向与节点实际镜像
digest内容对象确定后不可改内容索引/平台清单的具体 digest
镜像只读层发布后内容固定历史层是否含秘密
运行容器进程不会随 tag 自动更新imageID、配置与创建时间

多架构镜像会选出不同结果

开发机是 arm64，生产节点是 amd64。相同 tag 可指向多架构索引，节点按平台拉到不同的二进制层；若某架构版本缺失或构建时依赖不一致，就会出现“本机能跑、线上不行”。构建与测试应覆盖目标平台，记录每个平台镜像的 digest、编译选项和基础镜像版本。交叉构建还可能使用仿真，测试速度和运行行为需分别验证。

同一个索引 digest 表示索引对象固定，但运行时实际选用的平台镜像仍取决于节点平台。发布说明要同时给出支持架构与实际部署节点，不能只写一个版本号。

镜像更新不等于旧容器更新

仓库把 `service:latest` 移到新镜像后，已经运行的容器不会自动替换文件系统或进程。编排系统要创建新 Pod 或容器，镜像拉取策略、节点已有缓存和部署配置决定它是否真的拿到新镜像。若同一 tag 被复用，排障时要看 Pod 实际 imageID/digest，而不是只看部署 YAML 里的 tag。生产发布更稳妥的方式是每次构建生成不可变版本或 digest，并让配置变更触发滚动发布。

回滚也必须有旧镜像 digest 与配置版本。若旧 tag 已被覆盖、旧层又被清理，口头上的“回滚到 previous”未必能实际拉到旧二进制。

一个 3 节点故障算例

节点 A 在上午拉取 `service:prod` 指向构建 X，节点 B/C 下午拉取同一 tag，此时它已指向构建 Y。若拉取策略或本地缓存不同，三节点可能同时服务两种代码，接口行为不一致。先读取每个运行实例的 imageID，核对对应 digest；随后固定目标 digest 并按滚动策略重建 Pod。若 Y 有漏洞，不能只把 tag 改回 X 而不重启已运行 Y 的实例。

排障还要比对配置、环境变量和数据版本。镜像一致是必要的发布证据，却不能证明业务运行状态完全一致。

验收与供应链记录

构建时记录源码提交、构建器版本、基础镜像 digest、锁文件、目标平台和输出镜像 digest；在干净环境重建并比较产物，若构建含时间戳或非确定性步骤，应说明差异来源。扫描镜像层是否误含秘密，确认非 root 用户、必要的文件权限和最小运行依赖。部署后抽样核对所有节点实际 imageID，并在回滚演练中验证旧 digest 仍可获取。

镜像分层使分发和构建高效，但只有明确可变 tag 与不可变内容、以及容器创建的时机，才能解释“同一个版本名为什么跑出两种程序”。

自检

仓库把 service:prod 指向新镜像，已运行的容器会自动替换成新代码吗？

不会。运行容器仍使用创建时的文件系统；需要按部署策略重新创建，并核对实际 imageID。
