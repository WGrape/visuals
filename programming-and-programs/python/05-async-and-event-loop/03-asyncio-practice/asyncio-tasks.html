asyncio 任务与并发

协程本身不会「并发跑」，它只是个能暂停的函数。asyncio 把它包装成 Task 交给事件循环调度，才能真正「同时等待多个 I/O」。gather / TaskGroup / wait_for 是并发编排的三件套。

运行与循环

asyncio.run 启动事件循环

asyncio.run(coro()) 创建事件循环、运行协程直到完成、再关闭循环。这是 3.7+ 的标准入口。事件循环负责在「await 点」切换协程。

import asyncio

async def main():
    print("start")
    await asyncio.sleep(1)   # 挂起，把控制权交还循环
    print("done")

asyncio.run(main())

「单线程、协作式多任务」是核心：协程只在 await 处让出控制权，没有「被强制打断」，所以不需要锁。事件循环怎么运转见事件循环图解；await 原理见async/await 入门。

Task 是什么

协程 + 循环 = Task

直接 await coro() 是「串行」的（等它跑完才下一步）。用 asyncio.create_task(coro()) 把协程包成 Task 并立即排进循环，它就开始「并发」跑了——之后你再 await 它拿结果。

async def job(n):
    await asyncio.sleep(n)
    return n

async def main():
    t1 = asyncio.create_task(job(1))  # 立即入队，开始跑
    t2 = asyncio.create_task(job(2))
    r1 = await t1                      # 这里才等结果
    r2 = await t2
    return r1, r2                     # 总耗时≈2s 而非 3s
记住：create_task 之后两个任务已在并发推进，你「先 create 再 await」的顺序决定了并发度。若写成 r1 = await job(1) 再 create_task(job(2))，就退化成串行了。
gather 并发

一次性并发多个协程

asyncio.gather(*aws) 把多个协程/任务并发调度，等全部完成返回结果列表。爬虫并发请求 N 个 URL 的典型写法。

import asyncio, time

async def fetch(url):
    await asyncio.sleep(0.5)     # 模拟网络 I/O
    return url

async def main():
    t0 = time.time()
    results = await asyncio.gather(
        fetch("a"), fetch("b"), fetch("c"))
    print(results, time.time()-t0)  # ['a','b','c'] ≈0.5s

asyncio.run(main())
⚠️ gather 有个坑：其中一个任务抛异常，其它任务不会被取消，且异常会包装抛出。若要「一出错就全部停」，用下面 3.11+ 的 TaskGroup。
TaskGroup

3.11+ 推荐：结构化并发

async with asyncio.TaskGroup() as g: 创建一组任务，任一任务失败会自动取消其余任务，异常汇总成 ExceptionGroup。这是「结构化并发」的标准做法。

async def main():
    async with asyncio.TaskGroup() as tg:
        t1 = tg.create_task(job(1))
        t2 = tg.create_task(job(2))
    # 退出 with 块 = 等所有任务完成（或全取消）
    print(t1.result(), t2.result())
TaskGroup 替代了 gather 的「异常不取消兄弟任务」缺陷，也替代了手搓 try/finally: task.cancel()。新代码优先用 TaskGroup（Python 3.11+）。
超时与取消

给等待加时限，超时就取消

asyncio.wait_for(aw, timeout) 给协程设超时，到点自动取消；task.cancel() 主动取消。协程要在 await 处响应取消（捕获 CancelledError 做清理）。

async def slow():
    await asyncio.sleep(10)

async def main():
    try:
        await asyncio.wait_for(slow(), timeout=2)
    except asyncio.TimeoutError:
        print("超时取消")

    # Python 3.11+ 还能用上下文管理器写法
    async with asyncio.timeout(2):
        await slow()

并发原语讲完，但「怎么在协程里安全地调用同步阻塞代码」「常见坑」在异步模式里接着说。它和线程的锁是不同思路：协程靠「不抢占」天然避开竞态，而非靠锁。

Task / Future / coroutine 三者关系

概念是什么能否被 await何时创建
coroutineasync def 调用后的对象能调用时（此时还没执行）
Task被事件循环调度执行的 coroutine能create_task()
Future一个“将来会有结果”的占位符能底层 API，通常不直接用

最关键的一点：async def f() 调用 f() 不会执行函数体，只创建一个协程对象；必须 await 或 create_task() 才会真正运行。新手最常见的错误就是写了 f() 却忘了 await，然后收到 RuntimeWarning: coroutine ... was never awaited。

并发 vs 串行对比

import asyncio

async def job(name, sec):
    print(f"{name} start")
    await asyncio.sleep(sec)
    return f"{name} done in {sec}s"

async def main():
    # ❌ 错误：直接 await 三个协程 -> 串行，共 3 秒
    r = [await job("a",1), await job("b",1), await job("c",1)]

    # ✅ 正确：create_task 并发 -> 共 1 秒
    tasks = [asyncio.create_task(job(n,1)) for n in "abc"]
    results = await asyncio.gather(*tasks)      # ['a done in 1s', ...]

    # ✅ 3.11+ 推荐：TaskGroup（异常会自动取消兄弟任务）
    async with asyncio.TaskGroup() as tg:
        tasks = [tg.create_task(job(n,1)) for n in "abc"]
    results = [t.result() for t in tasks]

asyncio.run(main())

gather / wait / as_completed 怎么选

函数返回异常行为适用场景
gather按传入顺序的结果列表return_exceptions=False 时第一个异常立刻抛出，其余继续跑最常用：要全部结果
as_completed按完成顺序逐个 yield需自己 try想流式处理先完成的
wait(done, pending) 两个集合不抛异常，需自己查需要超时控制（timeout=）
TaskGroup（3.11+）task.result()任一失败 → 自动取消全部并抛 ExceptionGroup强一致性任务组

超时与异常处理

import asyncio

# ① 超时控制（wait 的 timeout 参数最直接）
done, pending = await asyncio.wait(tasks, timeout=5)
for t in pending: t.cancel()          # 必须手动取消，否则任务还在跑

# ② 单个任务超时（更常用）
try:
    r = await asyncio.wait_for(job("x", 10), timeout=3)
except asyncio.TimeoutError:
    print("超时了，任务会被自动取消")

# ③ 流式处理先完成的（as_completed）
for coro in asyncio.as_completed(tasks):
    r = await coro
    print("完成一个:", r)

# ④ 允许部分失败（return_exceptions=True）
results = await asyncio.gather(*tasks, return_exceptions=True)
ok   = [r for r in results if not isinstance(r, Exception)]
bad  = [r for r in results if isinstance(r, Exception)]
print(f"成功 {len(ok)} 个，失败 {len(bad)} 个")

# ⑤ 3.11+ ExceptionGroup 捕获
try:
    async with asyncio.TaskGroup() as tg:
        tg.create_task(might_fail())
except* ValueError as eg:            # 注意是 except*
    print(f"有 {len(eg.exceptions)} 个 ValueError")

取消（cancel）的正确姿势

机制行为注意
task.cancel()在该任务下一个 await 点抛 CancelledError不是立刻杀掉，是协作式
捕获 CancelledError可以做清理，但必须重新抛出或返回吞掉它会让取消失效
asyncio.shield()保护内部任务不被外部取消外部取消后 shield 外的 await 仍会抛
wait_for 超时内部自动 cancel已执行的部分不会回滚

取消与清理

# 正确的可取消任务写法
async def cancellable_job():
    try:
        while True:
            await asyncio.sleep(1)
            await do_one_step()          # 每个 await 都是取消点
    except asyncio.CancelledError:
        # ① 做清理（关连接、回滚状态）
        await cleanup()
        raise                            # ② 必须重新抛出！否则取消被吞掉

# shield：保护关键操作不被取消（比如已经发出去的支付请求）
async def outer():
    try:
        await asyncio.shield(critical_payment())
    except asyncio.CancelledError:
        # 外层被取消了，但 critical_payment() 仍在后台跑完
        print("我取消了，但支付还在进行")
        raise

# 批量取消并等待清理完成
for t in tasks: t.cancel()
await asyncio.gather(*tasks, return_exceptions=True)   # 等所有清理跑完

取消是协作式的：如果你的循环里没有任何 await（纯 CPU 计算），cancel() 永远不会生效——因为它找不到让出点。这是“协程卡死”的常见原因。

陷阱现象解法
协程里调阻塞函数time.sleep(1) 卡住整个事件循环改 asyncio.sleep(1)；或用 run_in_executor
忘记 awaitRuntimeWarning，代码没执行开启 -W error::RuntimeWarning 让它变错误

# 后台任务的正确写法（防止被 GC）
background_tasks = set()

def spawn(coro):
    t = asyncio.create_task(coro)
    background_tasks.add(t)               # 强引用，防止被 GC
    t.add_done_callback(background_tasks.discard)
    return t

深入自检

gather 抛异常时其他任务会继续跑吗？

会。gather（默认 return_exceptions=False）在第一个异常发生时立即返回，但它不会取消其他任务——它们会继续在后台跑完。这经常导致“以为失败了就结束了，其实后台还在写数据”的诡异 bug。想要“一个失败全部取消”，用 3.11+ 的 TaskGroup，它才是符合直觉的语义。

asyncio 是多线程吗？能利用多核吗？

不是，默认单线程单事件循环，只能用一个核。要利用多核就上 多进程（每个进程跑一个事件循环），或用 run_in_executor 配合 ProcessPoolExecutor 把 CPU 密集部分丢出去。典型架构：N 个进程 × 每进程一个事件循环（Gunicorn + uvicorn workers = CPU 核数）。

为什么我的协程跑得比同步还慢？

三种可能：① 并发度太低——只是把一个请求包成 async，没有真正并发（检查是不是串行 await 了）；② 协程本身开销——如果任务极短（微秒级），调度开销会超过收益，同步反而更快；③ 事件循环被阻塞——混入了同步 IO 或 CPU 密集代码，把整个循环卡住。用 debug=True 看有没有“慢回调”告警，能立刻定位 ③。

生产环境部署 asyncio 服务要注意什么？

四点：① 进程数 = CPU 核数（uvicorn --workers），单进程只用一核；② 调大文件描述符（ulimit -n 100000）；③ 设置超时——每个外部调用都要有 wait_for，否则一个慢调用拖垮全部；④ 优雅关闭——捕获 SIGTERM，取消所有任务并等待清理（给 gather(..., return_exceptions=True) 一个 grace period，通常 10 – 30 s）。
