理论页讲了 Leader Election 与 Lease 的原理。本页给三种可落地的实现：etcd、Redis、ZooKeeper，并点出防脑裂的关键陷阱。

01etcd：lease + 原子 CAS

etcd 的 lease 自带 TTL 自动过期，配合事务 CAS 实现谁拿到 key 谁就是主，过期即释放。

# 申请一个 15s 的租约
lease=$(etcdctl lease grant 15 | awk '{print $2}')
# 用事务原子地把自己的租约绑到 leader key（仅当 key 不存在时才成功）
etcdctl txn put --lease=$lease leader/key "$(hostname)" \
  --precond='CREATE'
# 后台每 5s 续租（看门狗）
etcdctl lease keep-alive $lease &
# 失去主：进程退出 / 续租失败 => lease 过期 => key 消失 => 别人可抢
要点：etcd 客户端通常有 campaign/revoke 高层 API 封装上述流程，直接用更省心；续租间隔必须小于 lease TTL 的一半。

02Redis：SET NX + 看门狗

用 SET key val NX PX 原子抢锁，值用唯一 token 防止误删别人的锁；后台看门狗延长过期。

# 伪代码（Redisson 等已封装）
# 抢锁：仅当 key 不存在时设置，带 30s 过期和唯一 token
SET leader:svc "token-abc" NX PX 30000
# 续租（看门狗，每 10s 执行）
PEXPIRE leader:svc 30000
# 释放：用 Lua 保证只删自己的 token，避免误删他人锁
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
end
要点：Redis 主从异步复制下，主宕机瞬间锁可能未同步到从，从升级后丢锁——这是 Redis 锁的固有风险。要求强一致用 Redlock（多实例多数派）或 etcd/ZK。

03ZooKeeper：临时顺序节点

创建临时(ephemeral)顺序节点，序号最小者为主；会话断开节点自动消失，触发重新选主。

# Curator 的 LeaderLatch 封装了下面所有细节
# 1. 在 /election 下建 ephemeral_sequential 节点
# 2. 取自己序号；若自己是最小 => 成为 leader
# 3. 监听比自己小一号的节点；它消失 => 重新判断
# 伪代码：
path = zk.create("/election/node-", EPHEMERAL|SEQUENTIAL)
children = zk.get_children("/election")
if min(children) == path:  becomeLeader()
要点：ZK 的 ephemeral 节点依赖会话；网络抖动导致会话过期也会丢主，所以选主逻辑要能容忍短暂无主而非反复切换（加退避）。

  • 脑裂根因：旧主还活着却以为自己失主，继续写 => 双主。所有方案都靠 TTL/lease 过期兜底
  • 缓解：主在持锁期间做写操作前校验我还是主吗；写带 fencing token，旧主的 token 更小被拒
  • 切主后务必有退避 + 优雅降级，避免惊群式重新选主
问：fencing token 是什么？

一个单调递增的数字：每次选主成功 +1，写存储时带着它；存储只接受比已见最大 token 更大的写，旧主带着小 token 的写被拒绝，从而即使旧主脑裂也无法污染数据。
