❌ 单线程时代 (Redis 6.0前)

  • 🔒 所有操作串行执行
  • ⚠️ 大Value读写阻塞
  • 📉 QPS 受限于 CPU
  • 🐢 高并发下延迟飙升

✅ 多线程 I/O (Redis 6.0+)

  • ⚡ I/O 操作并行化
  • 🎯 命令执行仍单线程
  • 📈 QPS 提升 2-3 倍
  • 🔄 保持线程安全

⚙️ 配置参数

io-threads 4

IO 线程数量，建议 4-6。设为 1 则禁用多线程，设为 N 则开启 N-1 个 IO 线程。

io-threads-do-reads yes

是否在 IO 线程中执行读操作。开启后读操作也会并行化。

线程数计算公式

实际 IO 线程数 = io-threads - 1（主线程也算一个线程）

🎯 核心要点

🔑

关键：原子性保证

使用 Client 队列 + 互斥锁，确保同一 Client 的命令按序执行，避免数据竞争。

🧵

不是全量多线程

只有网络 I/O 并行化，核心数据操作仍是单线程执行，保持 Redis 简单性。

⚡

适用场景

高并发、短命令、高网络带宽利用的场景。不适合大 Key 重度操作。

🔧

性能调优

通过 redis-benchmark 测试，合理配置 io-threads 数量，找到最佳平衡点。

多线程不等于多命令并行

这是最容易误解的一点：Redis 6.0 引入多线程后，命令执行依然是单线程。多线程只用于网络 I/O 与协议解析（以及后台的 fsync、内存释放等慢活）。这样做既保住了单线程的全部优点（原子性、无锁、实现简单、无竞态），又把网络瓶颈这一最大的开销并行化了。

单线程部分命令执行、数据结构操作 —— 保证原子与无锁
I/O 线程socket 读写 + 协议解析并行，io-threads 控制数量
后台线程（bio）关闭文件、AOF fsync、惰性释放内存（lazyfree）
io-threads默认 1（关闭）；建议 4 或不超物理核一半
io-threads-do-reads是否并行「读+解析」，默认 no，需显式开启
适用条件网络/解析是瓶颈才有效；命令计算密集则无收益
执行单线程、I/O 多线程、慢活后台线程——三层分工

线程模型版本演进

版本关键变化解决的问题遗留限制
Redis 2.x-5.x纯单线程（含 I/O）模型简单、无锁、原子性天然保证万兆网卡与高管道场景下网络收发成为瓶颈
Redis 6.0引入 I/O 多线程（可选）并行处理 socket 读写与解析，提升吞吐命令执行仍单线程；配置不当收益有限
Redis 6.x客户端缓存（tracking）减少网络往返，降低服务端负载需要客户端支持与失效广播开销
Redis 7.x更多慢活移出主线程、function、sharded pub/sub降低主线程阻塞点核心执行模型不变
始终如此惰性删除 lazyfree / UNLINK把释放大对象的开销交给后台线程内存回收滞后，瞬时占用偏高

判断是否需要开启 I/O 多线程：先看瓶颈。若 CPU 的 syscall 开销高、单核跑满而多核空闲、QPS 卡在十几万上不去，开启 io-threads 通常有效；若瓶颈是大 Key、复杂 Lua、慢命令，开多线程没用，要改命令用法。

单线程为什么还能快，以及它的代价

① 快的四个原因

  • 纯内存操作，无磁盘 I/O 等待。
  • 单线程避免锁竞争与上下文切换。
  • 高效数据结构（哈希表、跳表、压缩列表）与渐进式 rehash。
  • 多路复用（epoll/kqueue）事件驱动，C10K 友好。

② 单线程的代价

  • 单条慢命令会阻塞所有请求：大 Key、O(N) 命令、复杂 Lua。
  • 无法利用多核并行计算：只能靠开多个实例/分片。
  • 网络收发占用主线程时间：这就是 6.0 要解决的问题。
  • CPU 密集型的排序/聚合（ZUNIONSTORE、SORT）代价被放大。

③ 配置建议

  • io-threads：4 起步，不超过物理核数的一半，8 核机器一般设 3-4。
  • io-threads-do-reads yes：只开 io-threads 不开启读，只有写并行。
  • 开启后要压测对比，注意延迟分布（P99）而非只看吞吐。
  • 实例 CPU 已跑满时，优先查慢命令而不是加线程。

④ 利用多核的正确姿势

  • 多实例：一台机器跑多个 Redis 进程，按端口/目录隔离。
  • 集群：Cluster 分片，把数据与 QPS 摊到多节点。
  • 读写分离：从节点承接读流量。
  • 不要指望「开多线程让单实例变多核」——执行仍是一核。

深入自检

既然多线程了，为什么还说 Redis 是单线程？

因为「命令执行」这条核心路径始终只有一个线程。多线程只负责网络读写的搬运与解析，真正操作数据结构、产生结果的仍然是主线程串行执行。所以原子性、无锁、无竞态这些单线程优势都还在，「一次只处理一个命令」的语义也没有变。

开启 io-threads 能提升多少？

取决于瓶颈位置。网络/解析是瓶颈时，官方与社区压测常见提升在 1-2 倍；如果瓶颈在命令执行本身（大 Key、复杂脚本）或者客户端并发不够，提升可能接近 0。所以一定要先定位瓶颈再决定是否开启，并用自己的流量做压测。

io-threads 设得越大越好吗？

不是。线程过多会带来调度与缓存局部性开销，收益很快饱和甚至下降。经验值是「不超过物理核数的一半」，8 核机器设 3-4 即可。另外只调 io-threads 而不开 io-threads-do-reads，则只有写回并行，读仍是主线程做。

单线程模型下，什么最容易把实例打挂？

三类：① O(N) 命令（KEYS、大范围 LRANGE/HGETALL/SMEMBERS）；② 大 Key 的删除与序列化（用 UNLINK/惰性释放缓解）；③ 复杂或死循环的 Lua 脚本。这三类都会长时间独占主线程，导致所有请求排队超时。

后台线程（lazyfree）会不会导致内存回收不及时？

会。惰性释放把「释放内存」交给后台线程，意味着删除大键后内存不会立刻下降，而是异步回收。好处是主线程不卡顿，代价是瞬时内存占用偏高。用 UNLINK 删除超大键时要留意内存曲线，避免误判为内存泄漏。

想提升单实例吞吐还有哪些手段？

按性价比排序：① 消除慢命令与大 Key；② 用 Pipeline/批量命令减少网络往返；③ 开启 I/O 多线程；④ 使用更高效的序列化与连接复用；⑤ 最后才是分片/扩容。绝大多数线上问题出在第①项。
