OpenAI / Anthropic / Gemini 接口协议有什么区别？

你在客户端里看到的「API 格式」下拉框，选的其实不是模型能力，而是请求体说哪种方言。同一个问题、同一份 JSON 语义，四个厂商用了四套字段名和嵌套层级。这篇把 Chat Completions、Responses、Messages、generateContent 四条线拆开对齐——端点、认证、系统提示位置、工具回传、流式结束标志，逐个字段对照。

OpenAI Chat Completions OpenAI Responses Anthropic Messages Gemini generateContent
◎
先搞清楚：这个下拉框到底在选什么

大模型接口从来没有统一标准。所谓「API 格式」，是客户端要用哪种 wire format（线路格式）发出请求。

所有厂商的对话接口，语义上都是同一件事：把「系统提示 + 多轮消息 + 工具定义」发给模型，拿回「文本 / 工具调用」。区别在于这套语义被编码成了什么形状的 JSON。客户端配置里的「API 格式」，就是让你选编码方式：

  • 原生（native）——直接说该厂商自己的协议，一个字段都不用翻译。例如对接 Anthropic 官方端点时选 Anthropic Messages (原生)。
  • 需开启路由——客户端不会把请求直连发出去，而是先送进它内置的路由 / 协议转换层，翻译成上游真正接受的格式再转发。多数聚合网关、客户端代理就是这么工作的。
客户端按所选格式发出请求 原生格式可绕过转换层直连 转换后再转发到目标端点
一句话：格式与「模型强不强」无关，只与「JSON 长什么样、以及谁来翻译」有关。模型名 + 端点 + 请求 schema，这三者必须同时匹配——只有两个对上，第三个错，表现出来就是「模型不可用 / 400 / 工具调用失效」这类看起来像模型故障的报错。

五种格式全景：一张表对齐

下拉框里出现的那几项，本质上就是下面这几条线路。第五项是 Google 官方提供的 OpenAI 兼容层，用于「客户端只会说 OpenAI 方言」的场景。

名称端点归属定位核心请求字段多轮状态
OpenAI Chat Completions POST /v1/chat/completions OpenAI 事实标准 / 兼容层基准 messages[] 无状态，每次重发全量
OpenAI Responses POST /v1/responses OpenAI 新一代主推，Agent 原生 input + instructions 默认有状态（可关）

OpenAI 系

Chat Completions

Authorization: Bearer sk-…

出现最早、生态最广。绝大多数第三方厂商、开源模型、聚合网关都实现它来「兼容 OpenAI」，所以它事实上成了行业通用语。OpenAI 官方说它继续受支持，但新能力（内置工具、Agent 循环）只会先出现在 Responses。

OpenAI 系

Responses

Authorization: Bearer sk-…

把「消息数组」升级成「有类型的 Items 数组」，把系统提示提到 instructions，把输出上限改名 max_output_tokens。默认帮你存状态（约 30 天），可用 previous_response_id 接力。没有 data: [DONE]。

Anthropic 系

Anthropic Messages

x-api-key: sk-ant-…
anthropic-version: 2023-06-01

系统提示单独放顶层 system，不进 messages；max_tokens 必填；消息内容是 typed content blocks（text / image / tool_use / tool_result）。角色只有 user 和 assistant，且必须交替。

Google 系

Gemini generateContent

x-goog-api-key: …（或 ?key=）

模型名写在 URL 路径里，不在 body；对话是 contents[].parts[] 两层嵌套，角色叫 user / model；系统提示用 systemInstruction；采样参数统一收进 generationConfig。

注意一个容易混的点：「OpenAI 兼容」指的是协议长相，不是「模型姓 OpenAI」。Claude、Gemini、Llama 都可以被网关包装成 OpenAI 兼容端点；反过来，Gemini 官方自己也提供 OpenAI 兼容入口。所以「这个模型能不能用某个格式」要分别看端点支持，而不是看厂商。
2
OpenAI 的两代接口：Chat Completions vs Responses

同一家公司、同一批模型，两个端点长得像但世界观不同：一个是「消息数组」，一个是「有类型的 Items 数组」。

核心差别：messages 把很多东西粘在一起，Items 把它们拆开

Chat Completions 里，一条 message 同时承担了「用户说的话 / 模型说的话 / 工具调用请求 / 工具返回结果」四种角色，全靠 role 字段区分。Responses 把每种情况拆成独立类型的 Item，语义更清晰、也更好解析。

逐项对照 & 迁移映射

概念Chat CompletionsResponses
请求体入口messages: [ … ]input: "字符串" 或 [ Items ]
系统提示messages 里 role: "system"顶层 instructions
输出上限max_tokens（已弃用）/ max_completion_tokensmax_output_tokens（最小 16）
输出结构choices[] → message.contentoutput[] → Items（按 type 遍历）
工具定义tools[].function.{name, parameters}tools[]（自定义函数 + 内置工具混写）
工具调用message.tool_calls[]function_call Item
工具结果回传{ role: "tool", tool_call_id, content }function_call_output Item（call_id）
多轮上下文客户端重发全量 messages默认存储；previous_response_id 接力
一次多结果n不支持（要多个就发多次）
流式结束data: [DONE]response.completed（无 [DONE]）

Responses 的优势

内置 web_search / file_search / code_interpreter / computer_use / 远程 MCP；reasoning item 可以在多轮之间保留，官方内部评测里同一模型换到 Responses 后 SWE-bench 有约 3% 提升；缓存命中率提升明显。

Responses 的代价

默认帮你存响应（约 30 天），需要 store: false 才无状态；previous_response_id 是 OpenAI 侧的能力，换供应商（如部分聚合网关）可能直接 400；流式事件全部换了名字，旧解析器要重写。

怎么选

纯问答 / 已有大量 Chat Completions 代码 → 不必急迁，它没被弃用。要做 Agent、要用内置工具、想省长会话缓存 → 上新项目直接用 Responses。

A
Anthropic Messages：五处和 OpenAI 长得不一样

骨架其实很接近（都是 role + content 的消息数组），差异集中在「系统提示放哪」「必填项」「内容块的形状」这三件事上。

请求骨架

POST https://api.anthropic.com/v1/messages
x-api-key: sk-ant-...
anthropic-version: 2023-06-01
content-type: application/json

{
  "model": "claude-sonnet-4-5",
  "max_tokens": 1024,              // ← 必填，漏了直接报错
  "system": "你是一个简洁的助手",     // ← 顶层，不放进 messages
  "messages": [
    { "role": "user",      "content": "用一句话解释闭包" },
    { "role": "assistant", "content": "闭包是能记住自身定义环境的函数。" }
  ],
  "temperature": 0.3,
  "stream": false
}

① max_tokens 必填

OpenAI 不给就用模型默认；Anthropic 不给会直接抛 BadRequestError。这是迁移时最常见的第一个报错。

② system 是顶层字段

它不占 messages 的一个位置。所以 OpenAI 的 messages 数组不能原样拷过来，必须把 role: system 那条抽出来改名。

③ 角色只有 user / assistant

没有 system、没有 tool 角色。工具返回结果要伪装成一条 user 消息里的 tool_result 块。且消息必须交替、首条必须是 user。

④ content 永远是块数组

哪怕只发一句话，也建议用 [{ "type": "text", "text": "…" }] 的形状；图片、工具调用、工具结果都是同级的块类型。

响应与结束原因

项OpenAI Chat CompletionsAnthropic Messages
取文本choices[0].message.contentcontent[0].text（遍历 content 找 type==text）
结束原因finish_reason: stop / length / tool_callsstop_reason: end_turn / max_tokens / tool_use / stop_sequence
用量字段usage.prompt_tokens / completion_tokensusage.input_tokens / output_tokens
取消/停止stop 参数stop_sequences
缓存prompt_cache_key（服务端自动）块上挂 cache_control（显式）
还有两处容易忽略：Anthropic 没有 embeddings 接口（要配 Voyage / Cohere 等）；它也没有 OpenAI 那种 response_format: json_object 的 JSON 模式开关，通常靠提示词约束。
G
Gemini generateContent：模型名在 URL，内容藏在 parts 里

它是四条线里结构最深的一个：contents[] → parts[] → 具体块，比 OpenAI 多一层嵌套。同时把「采样参数」整体收进 generationConfig。

请求骨架

POST https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-flash:generateContent
x-goog-api-key: ...
content-type: application/json

{
  "systemInstruction": { "parts": [ { "text": "你是一个简洁的助手" } ] },
  "contents": [
    { "role": "user", "parts": [ { "text": "用一句话解释闭包" } ] }
  ],
  "generationConfig": {
    "temperature": 0.3,
    "maxOutputTokens": 512,
    "topP": 0.95
  },
  "safetySettings": [
    { "category": "HARM_CATEGORY_HARASSMENT", "threshold": "BLOCK_ONLY_HIGH" }
  ]
}

响应形状

// 非流式响应
{
  "candidates": [
    { "content": { "role": "model", "parts": [ { "text": "闭包是…" } ] },
      "finishReason": "STOP",          // MAX_TOKENS / SAFETY / …
      "index": 0 }
  ],
  "usageMetadata": { "promptTokenCount": 10, "candidatesTokenCount": 20, "totalTokenCount": 30 },
  "modelVersion": "gemini-2.5-flash"
}

流式怎么发

方法名换成 :streamGenerateContent，并加 ?alt=sse：
POST /v1beta/models/{model}:streamGenerateContent?alt=sse

想用 OpenAI SDK 怎么办

Google 官方给了兼容入口：把 base_url 指向 https://generativelanguage.googleapis.com/v1beta/openai/，密钥仍用 AI Studio 的 key，模型名照旧填 Gemini 的。注意兼容层不支持 tools 和 response_format 同时使用。

⚙
工具调用：四步往返，四种表达

工具调用是最容易因为「协议不匹配」而坏掉的地方——四家都支持，但「怎么定义、怎么回调、结果怎么塞回去」三步全都不一样。

工具定义：同样是「查天气」，三种 schema

OpenAI（Chat / Responses 同源）

"tools": [{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "查询城市天气",
    "parameters": { /* JSON Schema */ }
  }
}]

多一层 function 包装，靠 type 区分自定义函数和内置工具。

Anthropic

"tools": [{
  "name": "get_weather",
  "description": "查询城市天气",
  "input_schema": { /* JSON Schema */ }
}]

结构更扁平：没有 type 包装，Schema 字段叫 input_schema 而不是 parameters。

Gemini

"tools": [{
  "functionDeclarations": [{
    "name": "get_weather",
    "description": "查询城市天气",
    "parameters": { /* Schema */ }
  }]
}]

再套一层 functionDeclarations；Schema 用 OpenAPI 子集写法，和纯 JSON Schema 有细微出入。

最常踩的坑

工具返回结果必须带上调用 ID 做关联。OpenAI 是 tool_call_id，Responses 是 call_id，Anthropic 是 tool_use_id，Gemini 靠 functionResponse.name 匹配。少传这个 ID，模型就会「忘记」自己刚才要调什么，表现为答非所问或反复调用同一个工具。

≈
流式输出：都是 SSE，结束标志全不一样

四家都用 Server-Sent Events 推送增量，但事件命名、增量字段位置、以及「怎么知道结束了」各有各的写法。给 Chat Completions 写的解析器，直接拿去解析另外三个必然出错。

最隐蔽的坑：很多「通用」流式解析器都硬编码了「看到 data: [DONE] 就收尾」。接 Responses 时会永远等不到这个标记，于是前端一直转圈、连接被挂住，直到超时。换端点时，流式收尾逻辑必须一起改，不只是改 URL。

⚠
踩坑清单（全是 400 和「模型不可用」）
  1. 模型名 + 端点 + 请求 schema 必须三者同时匹配。最常见的错误是把 Claude 模型配成 OpenAI 格式的 base_url，或者反过来。网关可以把 Claude 包装成 OpenAI 兼容端点，但那不代表你的请求体可以写 Anthropic 的 schema。
  2. base_url 结尾是 /v1 还是裸域名，决定 404 还是 200。OpenAI 形状的客户端会自己在后面追加 /chat/completions 或 /responses，所以 base 必须以 /v1 结尾；而 Anthropic 形状的客户端会自己追加 /v1/messages，base 反而是裸域名。搞反了两个方向都 404。
  3. Anthropic 漏 max_tokens 会直接报错，不像 OpenAI 有默认值。迁移脚本里最容易整批失败。
  4. 「输出上限」有四个字段名，还有一个已被弃用。Chat Completions 上是 max_tokens（已弃用，且对 o 系列推理模型无效）→ max_completion_tokens；Responses 是 max_output_tokens（最小 16）；Anthropic 是 max_tokens（必填）；Gemini 是 generationConfig.maxOutputTokens。
  5. 推理模型的思考 token 也算进这个上限。上限设太小，模型把预算全花在推理上，最后返回空文本——你会看到「请求成功但没有内容」，很容易误判成服务端故障。
  6. Anthropic 的工具结果必须是 user 消息里的 tool_result 块，不能像 OpenAI 那样新起一条 role: tool 的消息。
  7. Gemini 的模型名在 URL 路径里，不在 body。把模型名写进 body 会被忽略或直接 404；另外 v1beta 和 v1 支持的模型范围不同。
  8. Gemini 的 OpenAI 兼容层有限制。官方兼容入口是 /v1beta/openai/（少了 /openai/ 就 404）；兼容层不支持 tools 与 response_format 同时使用，且模型名仍要填 Gemini 自己的名字。
  9. 别把「格式」和「模型」混为一谈。OpenAI 兼容只是协议长相；Claude、Gemini、开源模型都能被包装成兼容端点。判断能力要看模型本身，判断怎么发请求才看格式。
  10. 有状态是 OpenAI 专属的便利，不是通用能力。previous_response_id / store 依赖 OpenAI 服务端存储。第三方网关常常直接拒绝带这些字段的请求（400），换供应商时这一层要拆掉。
  11. 工具调用是「协议兼容」里最难对齐的一环。很多网关能过纯文本，但工具调用必挂：可能是参数被序列化成了字符串而不是对象，也可能是结果里缺了 tool_call_id。上线前一定要专门跑一次工具调用冒烟测试。
  12. 只改 URL 不改解析器 = 线上事故。Responses 没有 data: [DONE]；Anthropic 是命名事件；Gemini 是 alt=sse。响应字段名（choices / output / content / candidates）也全变了。

🎯 30 秒结论（可以直接背）

结论：所谓「API 格式」，本质是同一套对话语义（系统提示 + 多轮消息 + 工具定义）的四种 JSON 编码方式。OpenAI Chat Completions 是事实标准、生态最广、无状态；OpenAI Responses 是它的下一代，把消息升级成有类型的 Items，默认有状态、内置工具；Anthropic Messages 走原生，系统提示提到顶层、max_tokens 必填、内容是一组 typed blocks、工具结果伪装成 user 消息；Gemini generateContent 把模型名放进 URL，内容藏在 contents[].parts[]，参数收进 generationConfig。

路由的含义：客户端选「原生」就是按上游自己的协议直发；选「需开启路由」则要先经过客户端内置的转换层做字段翻译。「需不需要转换」的判断标准只有一条——你请求体的形状，是否等于上游端点期望的形状。

一句话本质：格式差异不会影响模型能力，但会让你的代码在四个地方出错——系统提示的位置、输出上限的字段名、工具结果的回传方式、流式的结束标志。把这四点对齐，跨供应商切换就只是改一行 base_url 和模型名。
