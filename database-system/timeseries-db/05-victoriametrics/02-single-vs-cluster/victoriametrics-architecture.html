①为什么会有 VictoriaMetrics 这个生态位

Prometheus 的单机 TSDB 设计得非常克制：本地存储、无副本、无集群。这套设计在单机规模下极其可靠，但当指标规模、保留期、多租户三者任意一个往上走时，它就开始吃力。

VictoriaMetrics 的切入点很明确：保持 Prometheus 的数据模型和查询语言不变，只替换存储与查询引擎。它不要求你改埋点、改查询、改 Grafana 面板，这让迁移成本降到「改一个 remote_write 地址」的量级。

① 内存占用
同样的序列规模，常驻内存显著低于 Prometheus，因为索引结构与倒排表的组织方式不同。

② 磁盘占用
列式压缩 + 更激进的合并策略，单位序列的磁盘成本通常明显更低。

③ 保留期
长周期（数月到数年）历史数据的存放更从容，配合对象存储可进一步下沉冷数据。

④ 多租户
集群版原生支持按租户隔离配额与查询范围，这是 Prometheus 单机版没有的能力。

需要澄清一点：它不是 Prometheus 的替代品，而是 Prometheus 下游的长期存储与查询层。抓取、服务发现、告警规则评估这些仍由 Prometheus（或 vmagent）承担。

②两种形态：单节点版与集群版

这是选型时第一个要做的决定，也是最容易搞错的地方。

VictoriaMetrics 两种部署形态：单机版一个进程包办，集群版拆成 vminsert / vmstorage / vmselect
维度单节点版集群版
进程结构一个二进制包办写入/存储/查询vminsert / vmstorage / vmselect 三类角色
扩容方式纵向：加 CPU、内存、磁盘横向：按角色分别加节点
副本与高可用靠外部手段（双写、磁盘快照）vmstorage 可配置副本因子
多租户不原生支持原生按 accountID / projectID 隔离
运维复杂度低，几乎等于跑一个 Prometheus高，要管分片、副本、再平衡
查询路径本地直读vmselect 向各 vmstorage 扇出再归并

集群版的价值不在于「更快」，而在于把三种资源的伸缩解耦：写入压力大就加 vminsert（无状态，随便加），存储不够就加 vmstorage（有状态，要分片），查询慢就加 vmselect（无状态，随便加）。单机版三者绑在一起，只能整体加配置。

③存储结构：与 Prometheus TSDB 的差异

两者都采用「按时间分块 + 不可变大块 + 后台合并」的思路，但细节不同。

方面Prometheus TSDBVictoriaMetrics
近期数据Head Block 常驻内存，同时写 WAL同样有内存缓冲与 WAL，但索引更紧凑
落盘单元按 2 小时（可配）切成 block按时间分区下的 part，后台持续合并
索引常驻倒排索引整体在内存索引分块、按需加载
崩溃恢复重放 WAL 重建 head重放 WAL，恢复通常更快
冷数据需靠 remote_write 外送可把历史 part 下沉到对象存储

最直观的体感差异是内存曲线：Prometheus 的内存随活跃序列数近似线性上涨，而 VictoriaMetrics 因为索引按需加载，同样规模下的常驻内存往往低一个量级。这正是大规模场景下第一个被感知到的差别。

反过来说，不要在小规模场景为这个差异付出复杂度代价。几万活跃序列时两者都很轻松，直接跑 Prometheus 更简单。

④怎么接上去：remote_write 是唯一改动点

迁移之所以便宜，是因为 Prometheus 的 remote_write 协议是公开的数据推送通道，VictoriaMetrics 实现了同一个接收端协议。

# Prometheus 侧：唯一需要新增的配置
remote_write:
  - url: http://victoriametrics:8428/api/v1/write
    queue_config:
      max_samples_per_send: 10000   # 单批上限
      capacity: 100000              # 内存队列能缓冲多少样本
      max_shards: 30                # 并发发送通道数

# 查询侧：Grafana 换个数据源地址即可
#   类型仍选 Prometheus，URL 指向 vmselect
#   VictoriaMetrics 兼容 PromQL，并扩展出 MetricsQL

① 先双写
同时保留本地查询和远端查询，对照结果一致性，观察一段时间再切。

② 队列要监控
remote_write 的内存队列满了会丢样本。盯住队列长度与失败重试计数。

③ 乱序与去重
多副本 Prometheus 双写会产生重复样本，需要靠外部标签或去重策略处理。

④ 保留期分工
本地留短时间做快速排障，远端留长时间做趋势与复盘。

一个常被忽略的坑：remote_write 是推送，不是拉取。Prometheus 挂了就不会有数据进来，而 VictoriaMetrics 无法主动发现这一点。必须单独对「数据是否还在上报」做告警，否则会静默地看到一段空白而不知道原因。

⑤MetricsQL：兼容之上的扩展

VictoriaMetrics 接受标准 PromQL，同时提供自己的扩展方言。知道哪些是扩展，能避免写出「在 Prometheus 上跑不了」的查询。

能力标准 PromQLMetricsQL 扩展
基础选择、聚合、函数支持完全兼容
负偏移量 / 未来窗口不支持支持 offset 为负、向前看窗口
正则与标签过滤增强基础正则更灵活的 matcher 写法
聚合后处理受限可对聚合结果再运算
查询限流与租户隔离无集群版可按租户限制

实践建议：日常查询尽量写标准 PromQL。这样哪天要换回 Prometheus 或迁到别的兼容后端，查询语句不需要重写；只有在确实需要扩展能力时才用 MetricsQL，并明确标注出来。

⑥五个容易踩的坑

Q1：集群版是不是一定比单机版快？

不一定。集群版每次查询都要在 vmselect 上做一次扇出与归并，小规模数据下这个开销反而更大。集群版换的是容量与隔离，不是单查询延迟。

Q2：副本因子设成 2 就高枕无忧了？

副本解决单节点故障，不解决误删、误配、误操作。备份策略（快照 + 异地）仍然要单独做，二者不能互相替代。

Q3：降采样会不会丢掉排查所需的信息？

会。降采样把细粒度聚合成粗粒度后，单次毛刺、短时抖动就消失了。通常做法是原始数据保留一段较短时间，降采样数据保留很长时间，排查看原始、趋势看降采样。

Q4：既然兼容 PromQL，告警规则能直接搬吗？

规则表达式可以搬，但告警的评估位置要决定好：是继续让 Prometheus 评估（数据新、延迟低），还是放到 VictoriaMetrics 侧评估（可跨长周期、可全局）。两边都评估会出现重复告警。

Q5：磁盘便宜是不是就不用管基数了？

不是。高基数影响的不只是磁盘，还有内存、索引大小、查询延迟和合并开销。基数治理在哪个后端上都是必修课。

单机版 vs 集群版：架构对比

维度单机版集群版
组件1 个二进制（全功能）3 类：vminsert / vmselect / vmstorage
部署复杂度极低（一条命令启动）中（要规划分片与副本）
容量上限千万级 series（单机）线性扩展
副本靠外部（如双写）原生支持（-replicationFactor）
适用< 1000 万 series 用单机超大规模 / 需要高可用

官方建议：单机版能处理千万级活跃 series、每秒百万级数据点——这个规模覆盖了 90% 以上的场景。不要为了“听起来分布式”就上集群版，单机版的运维复杂度低一个数量级。

集群版三组件与数据流向

组件职责扩容方式无状态
vminsert接收写入，按一致性哈希分片后写入 vmstorage加实例（前端负载均衡）是
vmselect处理查询，向所有 vmstorage 并行查询后聚合加实例是
vmstorage存数据，负责持久化与压缩加节点（需重新分片）否（有状态）

集群部署命令

# 集群版启动示例
# ① 存储节点（3 个）
./vmstorage -storageDataPath=/data/vm -retentionPeriod=12 \
            -httpListenAddr=:8482 -vminsertAddr=:8400 -vmselectAddr=:8401

# ② 写入节点（指向所有 storage）
./vminsert -storageNode=node1:8400,node2:8400,node3:8400 \
           -replicationFactor=2        # 2 副本（推荐生产用 2）
# 监听 :8480 接收 Prometheus remote_write

# ③ 查询节点
./vmselect -storageNode=node1:8401,node2:8401,node3:8401 \
           -dedup.minScrapeInterval=30s   # 关键：副本去重
# 监听 :8481

# Prometheus 侧配置
remote_write:
  - url: http://vminsert:8480/api/v1/write

# Grafana 数据源指向 vmselect:8481/prometheus

# 关键参数：
#   -replicationFactor=2      副本数，一个节点挂了数据还在
#   -dedup.minScrapeInterval   必须 >= 采集间隔，否则副本间的数据不会被去重
#   -retentionPeriod=12        保留 12 个月（默认 1 个月）

-dedup.minScrapeInterval 是最容易忘的参数：开了副本后，同一份数据会被写 2 份，查询时如果不开启去重，查询结果会出现重复点（曲线毛刺）。该值必须大于等于 Prometheus 的 scrape_interval。

存储引擎：为什么这么省资源

设计说明效果
LSM 结构数据先写内存，定期合并落盘写入高效、顺序 IO
紧凑索引倒排索引做了内存优化内存约为 Prometheus 的 1/5 – 1/10
高压缩针对时序特性优化编码约 0.7 字节/点（Prometheus 约 1.7）
无 head block 全内存近期数据不必全部常驻内存内存占用大幅降低
全局索引分区按时间分区，旧分区可卸载长周期查询不影响内存

资源占用实测对比（同样 1000 万 series、1 个月数据）：Prometheus 约需 40 – 80 GB 内存；VictoriaMetrics 约需 4 – 8 GB。这就是它近年流行的主要原因——同等硬件能装下 5 – 10 倍的数据。

MetricsQL：相比 PromQL 的增强

功能PromQLMetricsQL
保留最后值需复杂写法last_over_time(m[5m])

负偏移不支持支持（可查未来/历史对比）
正则中的 .*必须写全可省略（自动补全）

MetricsQL 示例

# MetricsQL 实用示例
# ① 对比一周前的同一时刻（偏移）
rate(http_requests_total[5m]) offset 1w

# ② 取区间内的最后一个值（填补采集间隔造成的空洞）
last_over_time(temperature[5m])

# ③ 去掉所有标签做全局聚合
sum without() (rate(http_requests_total[5m]))

# ④ 正则自动补全（{} 里的 .* 可省略）
{__name__=~"http_.+"}          # 等价于 http_.+.* 的匹配

# ⑤ 多个查询合并
union(
  up{job="api"},
  up{job="web"}
)

# ⑥ 更准确的分位数（VM 修复了边界外插问题）
histogram_quantile(0.99, sum(rate(http_duration_bucket[5m])) by (le))

深入自检

什么时候该从单机版升级到集群版？

三个信号：① 单机内存吃紧（活跃 series 超过 2000 万，单机内存超过 32 GB 且持续增长）；② 需要副本高可用（单机版挂了就是全挂，集群版可配 -replicationFactor=2）；③ 写入吞吐超过单机上限（百万级/秒）。除此之外不要上集群版——它引入了 vminsert/vmselect/vmstorage 三类组件的运维、跨节点查询的复杂度，以及扩容时的重新分片问题。官方的说法很实在：单机版能撑住的场景就用单机版。

集群版扩容要注意什么？

关键难点是 vmstorage 扩容要重新分片：新增节点后，已有数据不会自动迁移，只有新写入的数据才会分到新节点——结果是老节点压力大、新节点空着，要等老数据过期后才逐渐均衡。所以在规划时就要预留足够的分片数，或者接受扩容后的短期不均衡。相比之下，vminsert 和 vmselect 是无状态的，直接加实例 + 前端负载均衡即可。

从 Prometheus 迁移到 VM 要改什么？

改动很小，这是 VM 的一大优势：① Prometheus 侧加 remote_write 指向 vminsert；② Grafana 数据源指向 vmselect 的 /prometheus 路径；③ 告警规则基本不用改（MetricsQL 兼容 PromQL）；④ 如果用了 Recording Rules，可以保留在 Prometheus 侧继续算。最稳妥的方式是双写一段时间（同时写 Prometheus 和 VM），用 Grafana 对比两边曲线一致后再切读。整个过程不需要重写任何查询。

VictoriaMetrics 的局限是什么？

三点：① 生态不如 Prometheus 完整——部分 Prometheus 生态工具（如某些 exporter 的特定行为）兼容性有细微差别；② 集群版的文档和案例相对少，遇到问题时可查资料少于 Thanos；③ 开源版与企业版有功能差异（如部分多租户、降采样功能在企业版）。另外，如果你的场景需要跨多个 Prometheus 实例的全局视图且已经在用 Thanos 全家桶，迁移成本要重新评估。但对新项目来说，VM 通常是更简单、更省资源的选择。
