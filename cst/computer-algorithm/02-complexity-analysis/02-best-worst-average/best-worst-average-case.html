第 02 章 · 复杂度分析

平均是输入取期望，均摊是操作取平均

最坏、最好、平均分别是对输入取最大最小与期望，均摊则是对操作序列取平均；随机化把最坏情况从「某个输入」变成概率事件。

三种情况到底在说什么

概念定义回答的问题
最坏情况在所有规模为 n 的输入中，代价的最大值最差会慢到什么程度（用于承诺上限）
最好情况在所有规模为 n 的输入中，代价的最小值参考价值有限，容易误导
平均情况在输入分布假设下的期望代价典型表现，但依赖分布假设
均摊代价一串操作的总代价除以操作次数单次虽贵但很少发生的情况

注意区分平均情况和均摊复杂度：平均是在输入上取期望（假设输入随机），均摊是在操作序列上取平均（输入可以是任意的）。动态数组的 push 是均摊 O(1) 而不是平均 O(1)。

三个典型例子

快速排序

  • 最好：每次划分均匀 → Θ(n log n)。
  • 最坏：每次基准都是极值（如已排序数组取首元素）→ Θ(n²)。
  • 平均：随机输入下 → Θ(n log n)。

插入排序

  • 最好：输入已有序，内层循环一次都不进 → Θ(n)。
  • 最坏：逆序 → Θ(n²)。
  • 这正是「对小规模或近乎有序的数据，插入排序可能快过快排」的原因。

哈希表查找

  • 最好 / 平均：O(1)。
  • 最坏：全部哈希冲突退化成链表 → O(n)。
  • 所以哈希的 O(1) 严格说是在哈希函数足够随机、负载因子受控前提下的期望值。

随机化：把最坏情况变成期望

快排最坏 Θ(n²) 的根源是「输入恰好让划分总是最差」。若随机选基准，那么无论输入是什么，划分的好坏都由随机数决定，最坏情况不再是某个固定输入——它变成了概率事件。

这类算法叫拉斯维加斯算法：结果一定正确，运行时间是随机的，复杂度说的是期望值。

随机化的价值在于：它不依赖输入的分布假设。平均情况分析要假设「输入随机」，而随机化算法对任意输入都有相同的期望表现——敌手无法构造出专门卡你的用例。

考试和面试里怎么答

  1. 先说最坏：默认的「时间复杂度」通常指最坏情况，不给说明时应按最坏答。
  2. 再说平均/期望，并且明确说出分布假设或随机化机制（“在输入随机时”“随机选基准时”）。
  3. 如果算法有均摊性质，单独说明是均摊，不要混进平均（动态数组 push、并查集路径压缩、单调递增栈都属于这一类）。
  4. 提到空间时别忘了递归栈：快排的 O(log n) 是平均递归深度，最坏可以到 O(n)。

一句话总结：最坏用来兜底，平均用来评估，均摊用来解释「偶尔很贵」。三者说的是不同的问题，不能互相替代。

同一段代码，三个不同的答案

问「这个算法多快」，其实从来不是一个问题，而是四个：最好情况、最坏情况、平均情况，还有经常被漏掉的均摊。它们回答的不是一回事，混淆它们是最常见的分析错误。

拿最朴素的线性查找举例：在一个数组里找某个数。

同一个线性查找，target 位置不同，代价完全不同
视角线性查找用在哪

最坏情况最后一个或不存在，O(n)最重要：给服务定 SLA、批量任务定超时
平均情况假设均匀分布，期望 n/2 次，仍是 O(n)评估日常开销；但必须先说清输入分布
均摊代价动态数组扩容：单次 O(n)，n 次摊还仍是 O(1)评估容器、缓存、堆的整体效率

为什么要区分：三个真实的分歧点

① 「平均」不是天然的

平均情况必须先假设一个输入分布。换一个分布，答案可能完全不同 —— 这是很多性能争论的根源。

快速排序的经典例子：如果每次都随机选基准，期望是 O(n log n)；如果输入几乎有序而总选第一个元素作基准，就退化到 O(n²)。算法没变，分布变了。

② O 记号自带「上界」语义

严格说 O(n) 表示「增长不超过线性」。所以「这个算法是 O(n²)」这句话在理论上也成立，只是不够紧。

这就是为什么严谨文档里会写 Θ（同阶）而不是 O：Θ(n log n) 既说清了上界也说清了下界。

③ 最好情况常常是陷阱

插入排序在已排好序的输入上是 O(n)，非常快 —— 于是有人拿它当卖点。但它不能改变逆序输入仍是 O(n²) 的事实。

反过来看，正因为「接近有序时插入排序极快」，工程上常把它用作小数组兜底（很多标准库的排序就是这么做的）。

④ 最坏情况才是验收标准

线上你不能假设用户给的是分布的平均值。服务要做容量规划、要写超时、要保证不被单个请求拖垮，靠的都是最坏情况。

这也是为什么很多安全敏感的场景宁可用看起来更慢、但没有病态输入的算法。

一个实用换算：如果每秒能做约 10⁷ 次简单操作，那么 n=10⁵ 时 O(n log n) 绰绰有余（约 0.17 秒），O(n²) 要 1000 秒。常数因子可以优化，数量级不行 —— 这就是为什么复杂度分析总是先看阶。

深入自检

为什么说「平均情况」容易骗人？

因为它依赖你对输入分布做的假设，而很多时候这个假设是隐式的。真实数据几乎从来不是均匀分布：日志有热度集中、用户 ID 有偏序、字符串长度差异极大。做法上，要么把分布假设明确写下并在监控里验证，要么干脆用最坏情况兜底。

均摊分析到底是什么思路？

它看的是一连串操作的总代价，而不是单次的最坏值。典型例子是动态数组扩容：单次插入如果需要把数组翻倍复制，是 O(n)；但因为每次扩容的容量呈等比增长，做 m 次插入的总代价是 O(m)，摊到每次就是 O(1)。评估容器类结构的整体效率时用这个视角才公平。

那我是不是永远只看最坏情况就够了？

不完全。最坏情况过于保守会让你错误地放弃好算法。合理的做法是：先用平均/期望成本做日常估算与时延估算，再用最坏情况做容量红线与降级预案，同时准备好针对病态输入的兜底（如快排退化时切堆排序）。两套数字都要有。

空间复杂度也要分最好最坏吗？

要，而且更容易被忽略。递归深度就是一个典型：理论上平衡的递归树是 O(log n) 栈深，退化成链就是 O(n) 栈深，直接导致栈溢出。这就是为什么很多库在递归时会监控深度并在超限时切换算法。
