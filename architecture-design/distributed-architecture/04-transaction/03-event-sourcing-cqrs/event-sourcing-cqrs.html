事件溯源与 CQRS：留痕、重放与读写分离

从事件表结构讲到投影、快照、延迟与适用边界

一、它们解决什么

事件溯源（Event Sourcing）：不存「当前状态」，而存「发生过的事件序列」，状态 = 事件按顺序重放的结果。CQRS：把「写模型」和「读模型」分开，写入走一套结构，查询走另一套为查询优化过的结构。两者经常一起用，但可以独立使用。

事件溯源
存事件而非状态
天然有审计日志、可回溯、可重放
适用：查询麻烦，必须配读模型
CQRS
读写模型分离
各自优化，读性能与写复杂度解耦
适用：读模型有延迟（最终一致）
两者组合
写侧事件 + 投影出读模型
既完整留痕又能高效查询
适用：复杂度显著上升

一句话类比

传统 CRUD 像只保存余额数字；事件溯源像保存每一笔流水，余额 = 把所有流水加一遍。前者丢了历史，后者随时能算出任意时刻的余额。

二、事件溯源长什么样

-- 传统表：只有当前状态 account(id, balance, updated_at) -- balance = 730 -- 事件表：只追加，永不 UPDATE / DELETE event_store( event_id BIGINT AUTO_INCREMENT, -- 全局有序 stream_id VARCHAR(64), -- 聚合根 ID，如 account-1001 version INT, -- 该流内版本号，用于乐观并发 event_type VARCHAR(64), -- Deposited / Withdrawn / Frozen payload JSON, -- {"amount":1000,"by":"u9"} occurred_at DATETIME(6) ) -- 账户 1001 的事件流 1 account-1001 v1 Opened {"init":0} 2 account-1001 v2 Deposited {"amount":1000} 3 account-1001 v3 Withdrawn {"amount":300} 4 account-1001 v4 Deposited {"amount":30} -- 当前余额 = 0 + 1000 - 300 + 30 = 730

事件的三个铁律

  • 不可变：事件一旦写入永不修改。要纠错就发一个新的「冲正事件」。
  • 命名用过去式：Deposited 而不是 Deposit，表示既成事实。
  • 只追加：事件表只有 INSERT，没有 UPDATE/DELETE（除非做合规删除）。

三、CQRS：读写为什么要分家

写侧关心的是「业务规则能否成立」，模型通常高度规范化、带大量约束；读侧关心的是「一次查出页面要的所有字段」，模型应该宽表、冗余、预聚合。用一套模型同时满足两边，结果就是两边都别扭。

维度写模型（Command）读模型（Query）
目标保证业务规则与一致性最快地满足查询
结构规范化、按聚合组织反规范化、宽表、按页面组织
一致性强一致（事务内）最终一致（有秒级延迟）
并发控制乐观锁 / 版本号无，只有读取
存储选型关系库、事件库ES、ClickHouse、Redis、物化视图

四、投影、快照与重放

投影 Projection

消费事件流，把事件「折叠」成读模型。一个事件可以有多个投影，同一个事件源能同时喂出订单列表、统计报表、搜索索引。

快照 Snapshot

事件太多时重放慢，每 N 个事件存一次状态快照，恢复时「快照 + 之后事件」。

重放 Replay

新增一个读模型时，把历史事件全部重放一遍即可构建，不用改线上业务。这是事件溯源最大的红利。

时间旅行

可以算出「截至上月底的余额」——把事件重放到那个时间点即可，传统 CRUD 做不到。

重放实战价值

线上发现某个读模型算错了：修好投影逻辑 → 清空该读模型 → 重放历史事件 → 数据自愈。如果用传统 CRUD，错的聚合结果往往无法还原。

五、代价与坑

问题表现应对
最终一致延迟写完立刻查，可能读到旧值写后读走主库，或返回版本号让前端轮询；UI 上说明
事件版本演进老事件结构变了，投影器不认事件向上兼容（只加字段）；不兼容时做升版本转换器
事件量膨胀几年后几亿条，重放很慢定期做快照；按时间分区归档冷事件
删除数据（GDPR）事件不可变，无法物理删除加密存储 + 丢弃密钥（crypto-shredding）
重复投递MQ 至少一次，投影可能重复执行投影幂等：记录已处理 event_id，或基于版本号覆盖写
学习曲线团队第一次用容易写成「CRUD + 事件日志」先在一个非核心域试点，跑通再推广

六、什么时候该用

适合用

  • 需要完整审计与可追溯：金融流水、库存变动、合规日志。
  • 需要回溯任意时点状态：对账、审计、「上季度末余额是多少」。
  • 读写压力差异巨大、查询形态多变：报表、搜索、多维度聚合。
  • 领域本身是事件驱动的：物流轨迹、订单状态机、审批流。

别用

  • 简单 CRUD 后台管理：直接一张表就够了，别自找麻烦。
  • 团队没有事件建模经验且工期紧：复杂度会反噬。
  • 强一致读写（写完必须立刻读到）：CQRS 的延迟会让你难受。

七、深入自检

事件溯源和「普通的操作日志」有什么区别？

操作日志是旁路记录，真实状态仍存在业务表里，两者可能不一致；事件溯源里事件就是唯一事实来源，业务表（读模型）只是它的投影，可以随时重建。

CQRS 一定要配事件溯源吗？

不一定。可以写侧用普通关系表，读侧用 CDC（如 Canal 订阅 binlog）同步到 ES，这也是 CQRS，只是变更源是 binlog 而不是事件流。反之事件溯源几乎必须配 CQRS，否则查询会很痛苦。

读模型延迟一般多少？能压到多低？

同机房内用 MQ/CDC 通常是几十毫秒到几百毫秒。要更低可以写侧同步双写读模型（牺牲一致性换延迟），或在写后读场景直接查写模型。

事件结构变了怎么兼容旧事件？

优先做向后兼容的增量修改（加可选字段、保留旧字段语义）。实在不行就在读取层加「升版本器」：把 v1 事件转成 v2 再交给投影器，事件库本身不动。

如何保证投影不丢事件？

① 事件库与投递用事务性发件箱（Outbox）保证不丢；② 投影器记录已消费位点，重启后从位点续；③ 定期用事件总数对账，发现偏差触发重放。

事件溯源与 CQRS：什么时候值得用

事件溯源（存事件而非状态）+ CQRS（读写分离模型）是很重的架构，收益明确但代价也明确。大多数系统不需要它。

维度传统 CRUD事件溯源
存什么当前状态（会被覆盖）不可变事件序列（只追加）
历史丢失（除非另记审计表）完整保留，可回溯任意时点
审计要额外做天然支持
读当前状态一次查询要重放事件（需快照优化）
改数据结构改表事件不可变 → 只能版本化
删除数据（GDPR）直接删很难（要做加密擦除）
复杂度低高
CQRS 维度写模型读模型
数据模型规范化、保证一致性反规范化、为查询优化
存储关系库（事务）可以是 ES / Redis / 宽表 / 物化视图
一致性强一致最终一致（有延迟）
优化目标写入正确性查询性能
场景推荐原因
普通业务 CRUD不用复杂度远超收益
需要完整审计的金融/账务强烈推荐账本天然就是事件流
需要「时间旅行」回放排查推荐能重放任意时刻
读写负载差异极大CQRS 单独用不一定要事件溯源
需要构建多个读视图推荐一份事件可以投影出多种视图
高并发秒杀谨慎事件流可能成为瓶颈

实现要点

# 事件溯源的存储结构（以订单为例）
#   event_store 表：
#     aggregate_id | version | event_type | payload(JSON) | occurred_at
#     ord-001      | 1       | OrderCreated  | {...}       | 2026-01-01
#     ord-001      | 2       | ItemAdded     | {...}       | ...
#     ord-001      | 3       | OrderPaid     | {...}       | ...
#
#   关键约束：(aggregate_id, version) 唯一 -> 乐观并发控制
#   写入时用 version 做 CAS：
#     INSERT ... WHERE NOT EXISTS(version = N)   # 冲突就重试

# ---------- 快照（避免每次重放全部事件）----------
#   每 N 个事件（如 50 个）存一次快照：
#     snapshot: aggregate_id | version | state(JSON)
#   读取时：取最新快照(version=V) + 重放 version>V 的事件

# ---------- 投影（Projection）构建读模型 ----------
#   异步消费者读事件流，更新读库：
#     on(OrderPaid)  -> UPDATE order_view SET status='paid' WHERE id=...
#     on(ItemAdded)  -> UPDATE order_view SET total=total+? WHERE id=...
#   用 Kafka + 消费者组，保证至少一次投递
#   注意：要幂等（用 event_id 去重）

# ---------- 事件版本化（schema 演进必备）----------
#   V1: {"type":"OrderCreated","amount":100}
#   V2: {"type":"OrderCreated","amount":100,"currency":"CNY"}
#   处理方式：
#     1. upcasting：读的时候把 V1 升级成 V2（推荐）
#     2. 弱 schema：只加可选字段，永远不改语义
#     3. 双写过渡期：同时写 V1 和 V2
  • 先问「真的需要历史吗」：如果业务只关心当前状态，事件溯源是纯负担。它是为审计、回放、时间旅行设计的。
  • 事件是不可变的，这是核心约束也是核心收益：不可变意味着可以安全地追加、可以并行投影、可以做审计；但也意味着错了不能改，只能发一个「冲正事件」（如 PaymentRefunded 抵消 PaymentCharged）。
  • 一定要做快照：一个聚合有上万个事件时，每次读都重放会慢到不能接受。标准做法是每 20~100 个事件存一次快照。
  • 读模型是最终一致的：写完到读库更新完成有延迟（通常几十毫秒到秒级）。UI 上要处理这个不一致（如提交后显示「处理中」，或用写后读一致性：写完立刻查写库）。
  • 事件 schema 演进是长期成本：业务变化后旧事件的格式还是要能读。upcasting（升级）是最常见的方案，但版本多了会很难维护。
  • GDPR 的「被遗忘权」很难实现：数据存在不可变事件里删不掉。常见解法是把个人敏感数据存在事件之外（加密密钥单独管理，删密钥即等于删除）。
  • CQRS 可以单独用：不需要事件溯源也能做读写分离（读库用物化视图/ES 同步）。这是更轻量的选择。
什么情况下绝对不该用事件溯源？

四种情况：① 简单的 CRUD 后台——增删改查就够的业务，上事件溯源会让每个操作都变成「定义事件 + 写处理器 + 写投影 + 处理版本」，开发效率暴跌；② 查询模式单一且简单——如果只有一个读视图，CQRS 的那套读写分离就是纯开销；③ 团队没有应对最终一致性的经验——读模型延迟会让 UI 出现「刚提交却查不到」，需要产品和技术共同设计，经验不足会反复出问题；④ 数据量极大且写入频繁——事件只追加意味着数据只增不减，加上快照和投影的存储，成本是传统 CRUD 的数倍。判断标准：问自己三个问题——需要审计追溯吗？需要回放历史状态吗？需要多个不同的读视图吗？三个都不是，就别用。CQRS 可以单独用（读写分离），这比事件溯源轻量得多，是更常见的折中。

事件溯源的并发冲突怎么处理？

靠 聚合 ID + 版本号的乐观并发控制。每个聚合（Aggregate）有一个递增的 version，写入新事件时要求 version 是期望值（CAS）：如果两个请求同时基于 version=5 修改，只有一个能写入 version=6，另一个失败后重新加载事件（现在到 version=6）再重试。实现方式是在 (aggregate_id, version) 上建唯一索引，插入重复 version 会报唯一键冲突。这个机制的好处是不需要加锁，吞吐高；代价是冲突时要重试（高并发写同一聚合时重试会变多）。几个实践要点：① 聚合的粒度要划小——如果一个聚合每秒被写几百次，考虑拆分（如按订单而不是按用户聚合）；② 重试要有限次，超过就返回失败让上层处理；③ 命令要幂等——重试时最好带上 command_id 去重，避免重复执行副作用（如重复扣款）；④ 数据库层面，PostgreSQL/MySQL 的唯一索引足够，不需要特殊存储。

读模型延迟导致用户体验不一致怎么办？

四种常用解法：① 写后读走写库——提交成功后，紧接着的那次查询直接查写模型（或返回命令执行结果），只有列表页/详情页的下次访问才走读模型。这是最简单有效的方案；② 前端乐观更新——提交后前端直接把新状态渲染出来，后台异步刷新。用户体验最好；③ 显示「处理中」状态——接受最终一致，明确告诉用户数据正在同步（适合本来就有异步语义的业务，如「转账处理中」）；④ 把延迟做到足够低——用 Kafka/CDC 把投影延迟压到 100ms 以内，大多数场景用户感知不到。选择依据是你的业务语义：如果操作本身就是异步的（下单、审批），用 ③ 最自然；如果是表单编辑保存，用 ① 或 ②。最不该做的是「假装是强一致的」——不处理这个延迟，用户会遇到「明明保存成功却看不到」，这是最难排查的一类 bug。
