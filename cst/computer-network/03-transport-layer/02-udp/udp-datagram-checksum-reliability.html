UDP 数据报边界、校验和与可靠性：简单协议不等于随便丢

沿一条实时语音数据报理解 8 字节头、消息边界、截断、分片和应用层补救。

UDP 的最小承诺

UDP 头部主要有源端口、目的端口、长度和校验和，共 8 字节。发送一次 UDP 数据报，接收端通常按一条数据报取得，而不是像 TCP 那样只看到连续字节流；这让语音帧、DNS 查询等消息边界清晰。UDP 不保证送达、不保证顺序、不自动重传，也不提供拥塞控制。它的“简单”只说明传输层不替应用做这些事，不能把 UDP 当作网络可以无限发包的许可。

应用每次读取的数据缓冲若太小，系统可能截断该数据报；剩余部分不会像 TCP 流一样自动留给下一次读取。实现应检查返回长度和截断标志，按协议限制单条消息大小。把两个连续 UDP 数据报当成一条可无限拼接的消息，也会破坏应用语义。

校验和能发现什么

UDP 校验和覆盖头部、数据以及与 IP 地址相关的伪首部，用来发现传输中部分位错误或错投。IPv4 中 UDP 零校验和有历史上的可选语义，IPv6 中一般要求校验和，存在特定隧道场景的严格例外；应用不要为了省事随意关闭。校验和只能检测错误，不能防止有意伪造或证明发件人身份，安全通信仍需 DTLS、QUIC 或应用层认证加密。

若校验失败，接收方通常直接丢弃报文，不会自动发一个“UDP 重传请求”。因此丢失可能由链路、队列、校验失败、接收缓冲溢出或应用未及时读包引起。看见应用层缺一帧，要结合网卡、内核和进程各层计数定位。

一次语音传输

语音应用每 20 毫秒产生一帧，带上帧序号和采样时间，通过 UDP 发出。接收端若看到序号 100、102，知道 101 缺失；若 101 之后才到，需决定在播放期限前能否插入。实时语音通常不能无限等待重传，可能使用抖动缓冲、丢帧隐藏或有限的前向纠错。文件下载则更重视完整性，可以在应用协议上实现确认、重传和哈希校验。

“UDP 不可靠”不代表基于 UDP 的应用不能可靠。QUIC 就在 UDP 之上实现确认、重传和流控制；反过来，UDP 语音选择不等所有帧，可能比 TCP 的有序交付更适合实时播放。可靠性是应用目标和上层协议设计，不是协议名字贴的标签。

数据报大小与分片

一个 UDP 数据报若超过路径可传的 IP 包大小，IPv4 可能发生分片或因 DF 被丢弃，IPv6 路由器不会中途分片。任一 IP 分片丢失，原数据报通常无法完整重组，丢包概率和排障复杂度上升。实际应用常把数据报控制在保守的路径尺寸，并使用路径 MTU 发现或分片避免策略，特别是经过 VPN、移动网络和隧道时。

UDP `sendto` 成功通常只表示本机内核接受了待发送数据，不保证远端已收到。若目标端口无服务，可能收到 ICMP Port Unreachable，但防火墙可能丢掉此反馈；不能依赖它作为可靠业务确认。需要业务确认时，在应用层设计 request ID 和应答超时。

端口与 NAT 状态

UDP 没有 TCP 握手，中间 NAT 或状态防火墙可能依据最近的出站数据报建立短期映射。长时间无流量后映射老化，外部再发来的包可能到不了内部进程；应用可能发送保活包、重新打洞或经中继通信。保活频率要兼顾网络设备超时、移动设备耗电和服务成本。STUN 只能帮助发现某些映射，不能保证穿越所有 NAT。

端口相同不代表与 TCP 服务可互通。DNS 通常使用 UDP 53，也可能切到 TCP 53；HTTP/3 使用 QUIC over UDP，和 TCP 443 的 HTTPS 是不同传输路径，防火墙规则要分别核对协议。

验证与压测

分别制造丢包、乱序、重复和大包，观察应用是否按设计处理。语音业务记录帧序号缺口、到达抖动和播放期限；可靠业务记录重试次数、去重和最终哈希。抓包时若只在发送端看到报文，不等于对端进程收到，还要检查接收网卡、内核 UDP 错误计数和进程读取速度。

在同一网络条件下比较 UDP 与 TCP 应用时，要把上层重试、加密、抖动缓冲和拥塞控制成本算进去。只比较 8 字节 UDP 头与 20 字节 TCP 头，无法推断真实用户延迟。

UDP 实测命令

# 探测路径 MTU（IPv4 不分片）
ping -M do -s 1472 10.0.0.2      # -s 是数据，+28 头部 = 1500；不通说明 MTU 更小
ping -M do -s 1400 10.0.0.2

# UDP 发/收测试
nc -u -l 9999                     # 服务端
echo -n "hello" | nc -u -w1 127.0.0.1 9999

# UDP 带宽与丢包测试（服务端 iperf3 -s）
iperf3 -c 10.0.0.2 -u -b 100M -t 30     # 报告里看 lost/total datagrams 与 jitter

# 看 UDP socket 与队列
ss -uanp

UDP sendto 成功只代表数据进了内核发送缓冲，不代表对端收到。要确认可达必须在应用层做 ACK 或依赖上层协议反馈。

UDP 可靠性该怎么做（工程方案对照）

问题UDP 自身工程做法
丢包不重传应用层 seq + ACK + 超时重传（QUIC、ENet、KCP 都这么做）
乱序不保证应用层序号重排（加接收窗口）
分片丢失任一分片丢失则整个包丢弃把包控制在 MTU 内；用 PMTUD 或固定 1200 字节
无流控/拥塞控制发送速率不受限，会压垮网络或自己自己实现拥塞控制（QUIC 用 CUBIC/BBR，WebRTC 用 GCC）
无连接状态每包独立自己维护连接（Connection ID，QUIC 的做法）
  • DNS 的 UDP 上限：传统 512 字节，EDNS0（RFC 6891）扩到 4096；超过则回 TC 标志位，客户端改用 TCP 重试。这也是 DNS 放大攻击的根源（小查询 → 大响应）。
  • 分片是性能杀手：一个 UDP 包拆成 10 个 IP 分片，丢 1 个就全废，等效丢包率放大 10 倍。永远避免 UDP 分片。
  • SO_RCVBUF 要够大：UDP 没有流控，突发流量瞬间堆满接收缓冲就会被内核静默丢弃。看 ss -uanp 或用 netstat -su 的 receive buffer errors 计数。
  • 校验和开销：UDP 校验和计算在高吞吐下是可见的 CPU 开销，某些内网场景用 SO_NO_CHECK（Linux）关闭以换取性能，前提是链路本身有 CRC 保护。
  • 选型建议：实时音视频、游戏状态同步、DNS、QUIC 用 UDP；需要可靠有序的批量数据传输用 TCP，或直接用 QUIC（在 UDP 上把可靠性实现了）。
UDP 单包最大真的是 65535 吗？

字段上限是 65535（含 8 字节头），即数据最多 65507 字节。但受 IP 层分片限制，实际工程上不该超过路径 MTU（通常 1200–1472），否则分片带来的丢包放大得不偿失。

为什么 UDP 的 connect() 也有用？

UDP 的 connect() 不建连接，只是记下对端地址：之后可用 send/recv 代替 sendto/recvfrom，且内核会过滤非该来源的包、返回 ICMP 不可达错误（能更早发现端口不可达）。

自检

UDP 的 sendto 返回成功，能证明远端应用已收到吗？

不能。它通常只表明本地内核接受了发送请求，后续链路、接收内核或应用仍可能丢包。
