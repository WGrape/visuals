时序压缩算法：Delta-of-Delta 与 Gorilla XOR

两个针对时序特性的压缩技巧、完整链路、实测预期量级，以及压缩率不达预期的排查路径

时序数据库压缩GorillaDelta-of-DeltaPrometheus
① 可利用特性 ② 时间戳 ③ 数值 ④ 完整链路 ⑤ 排障 ⑥ 疑问
一句话总结：时序数据压缩能压到十几分之一，不是靠通用压缩算法，而是靠两个针对时序特性的技巧：时间戳用 Delta-of-Delta（等间隔时全变 0），数值用 Gorilla XOR（相邻浮点异或后绝大多数是 0）。这两招是 Facebook Gorilla 论文提出的，后来被 Prometheus、InfluxDB 等大量借鉴。

01监控数据的两个可利用特性

⏱ 采集间隔固定

每 10 秒 / 15 秒 / 30 秒采一次，时间点之间的间隔几乎恒定。一阶差分是常数，二阶差分几乎全是 0。

📉 数值缓慢变化

CPU、内存、QPS 这类指标在相邻采样点之间变化很小，浮点的高位（指数 + 高位尾数）几乎不变。

🔁 序列数量远多于单点数据量

百万级序列 × 每序列上万点，单点省几个字节，总量就是几个数量级的差距。

❌ 可以接受有损（部分场景）

历史监控数据允许降精度/降采样换空间，这是通用数据库没有的自由度。

要点：这两个特性都是监控类时序的特性。如果是金融行情、高频传感这类剧烈跳变的数据，压缩率会明显下降——选型时要先判断数据形态。

02时间戳压缩：Delta-of-Delta

思路是对差分再取一次差分：如果采集完全等间隔，二阶差分恒为 0，那每个时间戳只需要 1 个 bit 来表示「间隔没变」。

原始时间戳（秒）:  1000   1010   1020   1030   1040
一阶差分 delta  :    -     10     10     10     10
二阶差分 DOD    :    -      -      0      0      0     ← 全是 0

Gorilla 的编码（按 DOD 的取值分档，越小用越少 bit）：
  DOD =  0              → 1 bit   '0'
  DOD ∈ [-63, 64]       → 9 bit   '10' + 7 bit
  DOD ∈ [-255, 256]     → 12 bit  '110' + 9 bit
  DOD ∈ [-2047, 2048]   → 16 bit  '1110' + 12 bit
  其他                  → 36 bit  '1111' + 32 bit

论文实测：约 96% 的时间戳可以用 1 bit 表示。
（采集抖动、漏采会让 DOD 非零，所以不会是 100%）
情况编码长度占比（论文实测量级）
间隔完全没变1 bit约 96%
小幅抖动（±1 分钟内）9~12 bit少量
较大跳变（补采、重启）16~36 bit极少量
要点：这解释了为什么采集间隔抖动会显著劣化压缩率：抖动让 DOD 不再是 0，1 bit 变成 9~12 bit，差了十几倍。

03数值压缩：Gorilla XOR

时间戳用二阶差分，数值用相邻浮点异或

浮点值不做差分，而是与前一个值做异或（XOR）。如果值没变，XOR 结果是 0，只存 1 个 bit；如果只有低位变化，XOR 结果的大部分高位是 0，只需存「有意义的那一小段位」。

情况存什么长度
值完全没变控制位 01 bit

有效位窗口需要重新界定11 + 前导零个数(5b) + 有效长度(6b) + 有效位约 13 + 有效位长度

04完整链路与实测预期

  1. 按序列分组：每条时间序列（series）独立成块压缩——同一序列内才有强相关性。
  2. 时间戳 Delta-of-Delta：把等间隔消掉。
  3. 数值 Gorilla XOR：把缓慢变化消掉。
  4. 再套一层通用压缩（可选）：字节流层面继续消除冗余。
  5. 按块（chunk / block）组织：压缩与查询都以块为单位，块太小则压缩差、块太大则查询要解压的多。

要点：标签（label）的字符串不要在每一点重复存。所有时序库都用「序列元数据字典 + 只存数据点」的方式，这也是为什么基数爆炸会同时搞垮内存和磁盘。

05排障：压缩率不达预期的排查

  • 采集间隔抖动：DOD 不为 0 会让时间戳从 1 bit 涨到 9~12 bit。检查采集端是否准时、是否有补采。
  • 数据剧烈跳变：值域跨度大的指标 XOR 后有效位很多。考虑降采样或降低精度存储。
  • 块太小：每个块独立压缩，块内样本数少时压缩的「参考窗口」不足。
  • 写入批次太碎：小块被频繁刷盘，既影响压缩率也增加文件数。
  • 序列基数爆炸：序列太多时，每个序列的块都没填满，压缩率自然差——这其实是内存问题伪装成了压缩问题。
  • 用了不适合的编码：浮点用 Delta、整数用 XOR，都可能适得其反。

06常见疑问

问：为什么不能直接用 gzip/zstd 压？

能用，但效果差很多。通用压缩只看到字节流，看不到「时间戳等间隔」「浮点缓慢变化」这些结构。正确做法是先用时序专用编码把结构消掉，再用通用压缩，两级叠加才是最好的结果。

问：压缩是有损的吗？

Gorilla 这类编码是无损的。有损的是降采样（downsampling）——把历史数据从 10 秒精度降到 5 分钟精度，这是另一个独立机制，通常由保留策略触发。

问：压缩会拖慢查询吗？

会有解压成本，但通常净收益为正：监控查询大多受 IO 限制，数据小了 → 读得少了 → 反而更快。只有 CPU 成为瓶颈时才需要重新权衡。

问：我的数据压不动，是不是产品不行？

先看数据形态。剧烈跳变、采集抖动、高基数这三种情况，换哪个产品都压不动。先解决数据侧的问题（稳定采集间隔、治理基数），再谈压缩。
