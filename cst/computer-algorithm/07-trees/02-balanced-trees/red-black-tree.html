红黑树：用颜色规则换取「大致平衡」

AVL 树追求严格平衡（左右子树高度差 ≤1），代价是插入删除常常要多次旋转。红黑树放松了要求：只保证最长路径不超过最短路径的两倍，换来的是插入删除最多 O(log n) 次重着色 + 最多 3 次旋转。这是一个非常划算的交换，所以它成为工程中最常用的平衡树。

插入修正的三种情形

① 父节点是黑色

  • 什么都不做：插入红色节点不破坏任何性质。
  • 这也是为什么新节点默认染红——尽量少破坏规则。

② 父红 + 叔红（红红叔）

  • 把父与叔染黑、祖父染红，然后把「祖父」当作新插入点继续向上修正。
  • 不需要旋转，只是重着色（recolor）。
  • 可能一直向上传递直到根，把根染黑即可。

③ 父红 + 叔黑（三角/直线）

  • 直线型（父与 newNode 同向）：父染黑、祖父染红，对祖父做单旋。
  • 三角型（方向不一致）：先对父反向旋转转成直线型，再按直线型处理。
  • 旋转后局部黑高恢复，修正结束（这是插入最多 2 次旋转的来源）。

④ 删除为什么更复杂

  • 删除黑节点会破坏黑高，需要「双重黑」的修正逻辑。
  • 情形更多：兄弟红/黑、兄弟的孩子颜色组合。
  • 最多需要 3 次旋转，是红黑树最难的部分。
  • 实务建议：真要手写，先吃透插入，删除照着成熟实现改写。

深入自检

为什么新插入节点要染成红色？

因为染红只可能破坏「红节点不能有红孩子」这一条（若父节点也是红），而染黑必然破坏「黑高一致」这一条。黑高不一致会影响整棵树，修复代价大得多。染红是「尽量少惹麻烦」的选择。

红黑树真的比 AVL 快吗？

取决于负载。查找密集时 AVL 更平衡、比较次数更少；增删密集时红黑树旋转次数少、均摊更优。综合来看增删查混合的场景红黑树更稳，所以它成为标准库与内核的默认选择。差距通常是常数因子级别，不要神化。

为什么数据库用 B+ 树而不是红黑树？

因为磁盘/SSD 的最小访问单位是页（通常 4KB-16KB），而 B+ 树是「多路」的，一个节点正好放一页、能存几百个键，树高只有 3-4 层，即 3-4 次 IO。红黑树是二叉树，百万数据要 20 层，就是 20 次随机 IO，慢一个数量级。此外 B+ 树的叶子有链表相连，范围扫描极高效。

红黑树和跳表怎么选？

需要严格的最坏情况保证 → 红黑树（跳表是期望 O(log n)）；追求实现简单、并发友好、范围查询 → 跳表。Redis 的 ZSet、LevelDB/RocksDB 的 MemTable 都用跳表，正是看中它实现简单、插入只需局部修改、易于做并发版本。

红黑树能保证 O(log n) 吗？

能。由性质 ④（红不连红）和 ⑤（黑高一致）可推出：从根到叶的路径长度最多是黑高的两倍，而黑高至少为 log₂(n+1)，因此树高 ≤ 2log₂(n+1)，所有操作是 O(log n) 的最坏情况（不是期望）。

实际工程中需要自己实现红黑树吗？

绝大多数情况不需要：C++ 用 std::map/set，Java 用 TreeMap，Python 用 sortedcontainers。自己实现的价值在于理解原理与面试；若确实要写（如内核、特殊内存布局），建议基于成熟的伪代码（CLRS 或 Linux rbtree）改写并做随机化对比测试。

第一层 · 概念与判定：红黑树的五条性质与识别

红黑树是一种自平衡二叉搜索树，它不追求严格平衡，而是用「颜色约束」把最长路径限制在最短路径的 2 倍以内。

#性质作用
1每个节点要么红要么黑基础
2根节点是黑保证路径起点一致
3所有叶子（NIL）是黑统一路径终点
4红色节点不能有红色孩子（不能连续红）核心约束
5从任一节点到其所有后代 NIL 的黑高相同核心约束

这五条推出关键结论：树高 h ≤ 2·log₂(n+1)，所以查找/插入/删除都是 O(log n)。

  • 信号一：需要「有序 + 频繁增删」→ 红黑树（C++ map/set、Java TreeMap 的默认实现）。
  • 信号二：需要严格平衡、几乎不修改 → AVL。
  • 信号三：只需取最值 → 堆，不要上红黑树。

红黑树 vs B+ 树：红黑树用于内存中的有序容器；B+ 树用于磁盘索引（扇出大、树更矮、叶子连成链表便于范围扫描）。场景完全不同。

第三层 · 排障与边界：红黑树的坑

坑后果正确做法
新节点插成黑色直接破坏黑高（性质 5）新节点必须是红色，红红冲突好修，黑高破坏难修
忘了处理「叔叔是红」要向上传递修复不彻底情形 1 要把祖父设为新的当前节点继续循环
内侧/外侧判断错旋转方向反了左-右 = 内侧，先左旋父；左-左 = 外侧，右旋祖父
根节点忘了强制变黑违反性质 2修复结束后无条件把根置黑
把 NIL 叶子当成不存在黑高算错NIL 是黑色节点，路径必须算到 NIL
  • 排查顺序：先确认新节点是红 → 再看叔叔颜色选情形 → 再确认旋转方向 → 最后强制根黑。
  • 边界一：插入修复的循环不变式是「当前节点是红色且父也是红色」，修到父变黑或当前节点成为根为止。
  • 边界二：删除修复比插入复杂得多（双重黑、兄弟的四种情形），工程上几乎不手写。
  • 边界三：红黑树不是严格平衡——最长路径可以是最短路径的 2 倍，这是它换取「更少旋转」的代价。

红黑树性质校验

# 验证红黑树性质（调试用）
def check_rb(root):
    def black_height(n):
        if n is None or n.is_nil: return 1
        lb, rb = black_height(n.left), black_height(n.right)
        assert lb == rb, "黑高不一致"          # 性质 5
        return lb + (0 if n.color == RED else 1)
    assert root.color == BLACK, "根必须是黑"    # 性质 2
    def no_red_red(n):
        if n is None or n.is_nil: return
        if n.color == RED:
            for c in (n.left, n.right):
                assert c is None or c.is_nil or c.color == BLACK, "连续红"  # 性质 4
        no_red_red(n.left); no_red_red(n.right)
    no_red_red(root)
    black_height(root)
为什么新节点要插成红色而不是黑色？

插红色只可能违反性质 4（红红冲突），修复是局部的（变色 + 最多 2 次旋转）；插黑色必然违反性质 5（黑高不一致），而黑高的破坏会影响整棵树，修复代价大得多。

红黑树和 AVL 到底选哪个？

工程默认红黑树：C++ map/set、Java TreeMap、Linux 内核 rbtree 都是它。理由是实际负载多为增删查混合，红黑树旋转次数少（插入最多 2 次）。只有在几乎只读、且能接受更高插入成本时 AVL 才更优。

数据库索引用红黑树吗？

不用。数据库索引用 B+ 树：它是多叉的，扇出大（一个节点存几百个键），所以树更矮（3～4 层就能存千万级数据），磁盘 I/O 次数少得多；而且叶子节点连成链表，范围扫描极快。红黑树是二叉的、为内存设计。
