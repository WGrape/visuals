📋 逐 步 拆 解
💻 Chrome
STEP 1
DNS 解析
输入 http://www.example.com，浏览器自动识别协议为 HTTP，默认端口 80。先解析域名为 IP：93.184.216.34。
💻 Chrome
STEP 2
TCP 三次握手
浏览器用随机临时端口（如 :51234）向服务器的 :80 端口发起 TCP 连接。
:51234（浏览器） ──TCP握手──▶ :80（Nginx）
💻 Chrome
STEP 3
发送 HTTP 请求到 Nginx 的 80 端口
GET /page HTTP/1.1 Host: www.example.com Connection: keep-alive
⚡ 这个请求到达的是 Nginx 进程（它正占着 80 端口等着呢）
🔄 Nginx
STEP 4
Nginx 收到请求，做反向代理转发
Nginx 根据 nginx.conf 配置，把请求转发给后端应用：
# nginx.conf 关键配置 server { listen 80; # ← Nginx 监听 80 端口！ server_name www.example.com; location / { proxy_pass http://127.0.0.1:3000; # ← 转发给本地 3000 端口的应用 } }
Nginx 自己不处理业务逻辑，它只是个"门卫"——收到请求后，帮你转给真正干活的程序。
⚙️ App
STEP 5
应用程序（Node.js）在 :3000 端口收到请求
处理业务逻辑：查数据库、组装数据、渲染模板，生成 HTML 字符串返回给 Nginx。
// Node.js 示例 app.listen(3000, () => { console.log('App running on port 3000'); });
⚙️ App
STEP 6
应用查询数据库（:3306）
应用通过 :3306 端口连接 MySQL，执行 SQL，拿到数据后拼成 HTML。 这个过程完全在服务器内部，浏览器感知不到
🔄 Nginx
STEP 7
Nginx 把应用的响应返回给浏览器
应用返回 HTML → Nginx 加上响应头 → 通过 :80 端口原路送回给浏览器。
HTTP/1.1 200 OK Content-Type: text/html <html>...网页内容...</html>
💻 Chrome
STEP 8
浏览器收到 HTML，开始渲染页面 ✅
解析 HTML → 下载 CSS/JS/图片 → 构建 DOM → 绘制到屏幕。 （到这里，和 80 端口的故事就结束了）
🔢 各个端口的角色
:80
Nginx 监听
浏览器直接跟它通信
:443
Nginx 监听（HTTPS）
加密版本，现代网站标配
:3000
Node.js 应用监听
Nginx 转发给它，浏览器看不到
:3306
MySQL 监听
只有应用能访问它
:随机
浏览器临时端口
操作系统自动分配，用完就释放
💡 一句话总结：
80 端口是 Nginx 监听的"前台大门"。浏览器只跟 Nginx 的 80 端口说话。
Nginx 收到请求后，在服务器内部转发给应用程序（:3000），应用再查数据库（:3306）。
浏览器全程只知道 80 端口的存在，完全不知道后面还有 Nginx → App → DB 这条链路。

核心速览

一句话从敲下回车到页面出现，中间经过了 DNS、TCP、TLS、HTTP、渲染这一整串环节
总耗时构成网络往返 + 服务端处理 + 资源加载 + 前端渲染
关键认知真正的瓶颈往往不是服务端处理，而是往返次数与串行依赖
优化抓手减少 RTT、复用连接、提前建立连接、消除串行
一次完整访问要花好几个 RTT，每个环节都能优化

一、逐环节拆解

环节做什么耗时量级优化
URL 解析浏览器判断协议、是否命中 HSTS 列表可忽略加进 HSTS 预加载列表
DNS递归查询，可能走浏览器/系统/路由器/运营商缓存0~100ms+dns-prefetch、减少域名数
TCP 握手SYN / SYN-ACK / ACK1 RTT连接复用、TCP Fast Open
TLS 握手协商密钥套件、验证证书TLS1.3 约 1 RTT会话复用、TLS1.3、0-RTT
HTTP 请求发送请求头与 body1 RTT（含服务端处理）HTTP/2 多路复用、压缩 header
首字节 TTFB服务端处理时间取决于后端缓存、CDN、后端优化
资源加载CSS/JS/图片等子资源往往是大头合并、缓存、CDN、预加载
渲染构建 DOM/CSSOM、布局、绘制与页面复杂度相关关键渲染路径优化
为什么要算 RTT 而不是带宽

一个典型页面要加载几十个资源，但每个资源可能只有几 KB。这种情况下耗时几乎全在等待往返上，带宽根本不是瓶颈。这就是为什么 HTTP/2 的多路复用、连接复用、CDN 就近接入能带来数量级的提升。

二、DNS 那一跳值得单独看

浏览器缓存命中则 0ms，Chrome 默认缓存约 60s
操作系统缓存hosts 文件与系统 DNS 缓存
路由器 / 本地 DNS家用路由器通常转发到运营商
递归查询根 -> 顶级域 -> 权威域名服务器，跨洲时很慢

优化手段：<link rel="dns-prefetch" href="//cdn.example.com"> 提前解析；或者用 preconnect 连 DNS + TCP + TLS 一起做完。

三、连接复用的价值

短连接长连接（Keep-Alive）HTTP/2
每请求握手每次都要首次首次
并发请求靠开多个连接（浏览器限 6 个/域名）串行复用一条一条连接多路复用
队头阻塞无（多连接并行）严重（必须等前一个响应）无（帧级别交织）
额外 RTT每请求 1~2 个00
# 用 curl 看每个阶段耗时 curl -w ' DNS 解析: %{time_namelookup}s TCP 连接: %{time_connect}s TLS 握手: %{time_appconnect}s 首字节 TTFB: %{time_starttransfer}s 总耗时: %{time_total}s ' -o /dev/null -s https://example.com # 典型输出解读： # time_namelookup 0.012 DNS # time_connect 0.045 TCP（减去 namelookup 即握手耗时） # time_appconnect 0.098 TLS（减去 connect 即 TLS 握手耗时） # time_starttransfer 0.210 TTFB（减去 appconnect 即服务端处理 + 请求发送） # time_total 0.350 总耗时（减去 starttransfer 即内容传输）

四、关键渲染路径

浏览器拿到 HTML 之后并不是立刻就能显示。要理解为什么 CSS 放头部、JS 放底部：

资源是否阻塞为什么
HTML阻塞一切所有内容的起点
CSS阻塞渲染（不阻塞 DOM 解析）没有 CSSOM 就无法构建渲染树，会白屏
同步 JS阻塞 DOM 解析与渲染JS 可能修改 DOM 或查询样式，浏览器必须停下来执行

五、深入自检

为什么 HTTP/2 不再需要合并小文件？

因为 HTTP/2 的多路复用让「多请求」几乎零额外成本，而合并文件会破坏缓存粒度（改一个小图标要让整个雪碧图失效）。但请求本身仍有开销，所以也不该走向另一个极端。

HTTPS 一定比 HTTP 慢吗？

握手阶段多 1~2 个 RTT，但之后对称加密的开销在现代 CPU 上可以忽略。加上 TLS1.3 与会话复用，长期连接下差距很小。而且 HTTPS 才能用 HTTP/2。

为什么有时候 TTFB 特别高但服务端很快？

三种可能：① 中间有代理/网关；② 服务端在等下游（数据库、缓存）；③ 开启了 Nagle 算法导致小包被延迟发送。排查时用服务端日志的时间戳对比。

preconnect 和 dns-prefetch 用哪个？

preconnect 更强（做完 DNS + TCP + TLS），但会占用连接资源；只对确定马上要用的关键域名用 preconnect，其余用 dns-prefetch。

首屏时间怎么优化最有效？

按收益排序：① 上 CDN 就近接入；② 关键 CSS 内联；③ JS 用 defer/async；④ 关键资源 preload；⑤ 服务端渲染或流式输出 HTML。

记住一句瓶颈多在往返次数，不在带宽
握手成本TCP 1 RTT + TLS 1 RTT
最强优化连接复用 + HTTP/2 + CDN
渲染阻塞CSS 阻塞渲染，同步 JS 阻塞解析
