开测前：服务器、资源与数据怎么准备？

同一个命令在不同 CPU、连接池、缓存或数据集上得到的数字不可直接比较。先冻结环境，再测量。

目标服务：把会影响结果的配置写下来

层次要记录/核对什么为什么
应用与实例代码版本、实例数、CPU 核数和配额、内存上限、worker/线程/协程数、队列容量、超时与限流阈值CPU throttling、工作池耗尽或队列增长会先限制吞吐
网关与协议负载均衡策略、TLS 终止点、HTTP 版本、keep-alive、连接与并发流限制、连接池和排队策略测到的可能是网关/协议的限制而非业务能力
数据库与缓存数据量、索引、连接池、读写比例、缓存冷热状态、外部依赖版本/限额空库或全热缓存不能代表实际工作负载
机器与网络磁盘与 IO、网卡/带宽、CPU 频率/配额、文件描述符上限、监听队列、端口资源连接失败、排队或磁盘瓶颈可能与应用代码无关

不要把“增大文件描述符/端口/队列”当作通用优化：先核对当前限制与监控，再在授权环境按容量规划调整并记录实际值。

把资源配置变成可以复核的清单

先记下配置的实际生效值，再做低档试跑。比如 3 个应用实例，每实例数据库连接池上限 20，则应用一侧理论上可能同时占用 60 条数据库连接；数据库本身还要留给其它服务与管理任务。把实例数翻倍而不核对数据库承载，可能只是把瓶颈下移。这里的 3 × 20 仅用于演示配置间的关系，不是推荐配置。

应用 worker/线程池、队列容量、连接池、超时与限流要同时记录配置值、运行时实际值、饱和信号。只看到“CPU 还没满”不足以排除连接池或队列先满；容器还应核对 CPU quota/节流，而不只看宿主机核数。

在 Linux 主机可用只读命令留底（是否适用取决于部署方式，容器内与宿主机的数值可能不同）：

nproc              # 当前环境可用 CPU 数（与容器 CPU quota 分开核对）
ulimit -n          # 当前 shell 的文件描述符软限制
free -h            # 主机内存概况
ss -s              # 当前 TCP socket 统计

还应从应用配置/监控系统导出实际 worker、连接池和队列指标；上面的命令不能代替服务端指标，也不应在未核对瓶颈前盲目调高系统限制。

负载发生器也要像服务器一样准备

  • 记录压测机 CPU/内存/文件描述符、网络接口及与目标的拓扑、TLS 与 DNS 条件；避免与目标共机导致资源争用，除非就是要测同机开销。
  • 核对能否维持目标连接数：本机端口资源、连接错误、发送带宽、CPU 饱和与丢包。必要时做分布式或多机对照，但不要贸然加大总流量。
  • 时钟同步并记录开始结束时间，保证客户端结果可与服务日志、网关和数据库监控对齐。

请求、账户和数据集

  1. 准备具有代表性的读/写比例、URL、请求体大小、认证方式、响应大小和数据分布；先人工确认返回的是预期业务结果，而非登录页或缓存的错误页。
  2. 写请求使用可清理、不会影响真实用户的测试数据；约定数据复位与清理方式。避免直接依赖真实第三方服务，测试替身的时延/错误模型也须记录。
  3. 固定重试、缓存策略、连接复用和超时；明确业务成功条件与各类失败的归属，统计窗口里不要悄悄修改配置。

开测检查表

  • 授权范围、维护窗口、联系人、回滚/停压方式与阈值已确认。
  • 客户端和服务端指标均可采集：成功/失败计数、RT 分位、active/queue、CPU/内存/IO/网络及下游状态。
  • 低档试跑已验证状态码、响应体和业务正确性；预热与正式窗口分开记录。
  • 所有资源配置、镜像/版本、实例数和数据集已存档，压测机未成为首个瓶颈。

若其中一项不满足，先修正环境再看结果指标。

环境决定结论：同样的代码，不同的数字

压测中最容易出错的环节往往不是压测本身，而是环境没对齐。同一份代码在三种环境下跑出来的数字可能相差数倍，如果不知道差在哪，就会得出错误的容量结论。

环境类型优点风险适合做什么
本地 / 开发机随手可跑、迭代快规格不同、混部干扰大、网络路径不同只用于发现明显性能问题
独立压测环境与生产隔离、可反复折腾规格或拓扑与生产不一致，数据不真实常规回归与容量粗估
生产影子 / 全链路规格与数据最接近真实风险高，需要流量隔离与限速上线前最终确认
生产灰度小流量完全真实只能观察不能施压，且影响真实用户验证真实体验与稳定性
规格对齐CPU、内存、磁盘类型、网卡，任何一项不同结论就不可迁移
拓扑对齐副本数、机房分布、链路上的中间件层数要一致
混部影响压测机与被测服务在同一台机器上，结果必然失真
数据对齐数据量级与冷热分布，比数据量本身更重要
依赖真实用 mock 的下游会把瓶颈藏起来
预热充分JIT、缓存、连接池都需要预热后才进入稳态

三类最容易漏掉的准备工作

负载发生器本身要准备

压测机也需要被当成服务器对待：看它的 CPU 是否打满、端口是否耗尽、连接数是否受限、GC 是否停顿。判断方法是增加压测机数量，如果吞吐随之上升，说明之前是压测机受限。

数据集要贴近真实分布

不要只用同一批 ID 反复打。真实流量是长尾分布的：少量热点 + 大量冷数据。用真实日志采样构造请求集，并单独设计冷启动场景，否则缓存命中率会骗过你。

# 一个贴近真实的请求集构造思路 # 1) 从真实日志采样接口与参数分布 sample_from_access_log(hours=24, rate=0.01) # 2) 保持接口比例，而不是均匀打 mix = { "GET /home": 0.45, "GET /detail": 0.35, "POST /order": 0.15, "GET /search": 0.05, } # 3) 参数按长尾分布取，而不是固定几个 ID item_id = zipf_sample(n_items=1_000_000, alpha=1.1) # 4) 账号与会话要够多，避免被单点限流或锁竞争干扰 user_pool = load_users(10000) # 5) 预热：先以目标负载的三成跑几分钟，等缓存与连接池稳定 warmup(qps=target*0.3, duration="5m") # 6) 正式压测：每级负载跑够时间再采样，跳过前 30 秒 for level in ramp_levels: run(qps=level, duration="10m", skip_first="30s")

机器规格记录核数、内存、磁盘类型、网卡带宽
实例数与拓扑副本数、机房、负载均衡配置
压测机独立与被测服务物理隔离，数量足够
压测机监控CPU、端口、连接数、GC 都要看

预热完成缓存、连接池、JIT 都已进入稳态
一定要用生产规格的机器吗？

如果结论要指导生产扩容，就必须。如果只是比较两次改动的相对差异，可以用较小规格，但必须保证两次用同一套环境，这样比较才有意义。

数据量要铺到和线上一样大吗？

数据量级会影响索引深度、缓存命中率与磁盘 IO 模式，所以越接近越好。至少要保证量级相同（比如同为千万行），否则测出来的查询耗时不可信。

能不能直接压生产？

谨慎场景不推荐。如果必须，要用影子流量或只读流量，并且限速、可随时中止、确保写操作不会产生真实副作用。更常见的折中是复制一份生产规格的独立环境。

压测结果波动大怎么办？

先找波动源：是否是 GC、定时任务、其他租户干扰、还是压测机自身抖动。每个负载级别跑足够长时间并多次重复，取稳定的区间而不是单次结果。

一句话总结：压测的准备工作中，大部分精力应该花在「让环境接近真实」上，而不是花在调压测工具参数上。环境不对，工具再准也只得到一个错误的数字。
