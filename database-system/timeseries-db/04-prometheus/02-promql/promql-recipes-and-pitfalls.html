PromQL 实战：常用查询模板与六个高频坑

四类指标的正确查法、可直接复用的查询模板、告警写法与排障顺序

PromQLPrometheus监控查询
① 四类指标 ② 查询模板 ③ 高频坑 ④ 疑问
PromQL 的力量来自「先选出一组时间序列，再对它们做速率或聚合」。写得对不对，取决于你是否清楚自己拿到的是瞬时向量还是区间向量。

01先分清四类指标该怎么查

同样一句查询，用在不同类型的指标上结论完全不同。这是 PromQL 最容易出错的地方。

类型特点正确用法错误用法
Counter只增不减，重启归零rate(x[5m])、increase(x[1h])直接取当前值（看不出趋势）
Gauge可增可减的瞬时值直接查询、avg_over_time、delta对它用 rate（语义错误）
Histogram多个 bucket 累计计数histogram_quantile(0.95, rate(...))对 _sum/_count 直接取分位数
Summary客户端算好的分位数直接读 quantile 标签对 summary 做聚合（不可加）
# Counter：每秒速率（最常用）
rate(http_requests_total{job="api"}[5m])

# Counter：一段时间内的增量（用于「过去 1 小时请求数」）
increase(http_requests_total{job="api"}[1h])

# Gauge：当前值 + 一段时间的变化
node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes
delta(node_filesystem_free_bytes[1h])       # 可能为负

# Histogram：P95 延迟（必须先 rate 再算分位数）
histogram_quantile(0.95,
  sum by (le, job) (rate(http_request_duration_seconds_bucket[5m])))
#   注意 by (le)：丢了 le 就算不出分位数

# Histogram：平均延迟（用 _sum / _count 更准）
sum(rate(http_request_duration_seconds_sum[5m]))
  / sum(rate(http_request_duration_seconds_count[5m]))
要点：rate 的窗口至少要覆盖 4 个采样点：15 秒采样时窗口不小于 1 分钟，30 秒采样时不小于 2 分钟。窗口太短会因为点数不足而剧烈抖动，太长则会抹掉毛刺。

02可直接复用的查询模板

下面这些是日常排查里用得最多的句式，替换指标名即可使用。

目的PromQL说明
CPU 使用率1 - avg(rate(node_cpu_seconds_total{mode="idle"}[5m]))用 idle 反推，比直接算各模式更稳
内存使用率1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes用 Available 而不是 Free（含可回收缓存）
磁盘剩余可用天数predict_linear(node_filesystem_free_bytes[6h], 7*24*3600) / (1024^3)线性外推，适合容量预警
错误率sum(rate(http_requests_total{code=~"5.."}[5m])) / sum(rate(http_requests_total[5m]))分子分母都要 rate，不能只 rate 分子
P99 延迟histogram_quantile(0.99, sum by (le) (rate(..._bucket[5m])))必须保留 le 标签
服务是否消失absent(up{job="api"} == 1)up 没数据不等于正常，必须用 absent 检测
Top Ntopk(10, sum by (instance) (rate(...[5m])))topk 结果不能用于告警（会抖动）
重启次数changes(process_start_time_seconds[1h])进程启动时间变化即重启
# 多条件组合：错误率超过 1% 且请求量足够大（避免低流量误报）
(
  sum(rate(http_requests_total{code=~"5.."}[5m])) by (job)
  / sum(rate(http_requests_total[5m])) by (job)
) > 0.01
and
sum(rate(http_requests_total[5m])) by (job) > 1

# 环比：和一周前同时段比较（用 offset）
sum(rate(http_requests_total[5m]))
  / sum(rate(http_requests_total[5m] offset 7d))

# 求「持续多久」而不是「是否发生」
avg_over_time((up == 0)[30m:1m])          # 子查询：过去 30 分钟里 down 的比例
要点：写告警规则时的两条铁律：① 分母也要做 rate（只 rate 分子会得到错误的比率）；② 加最小流量条件（否则夜间低流量时一个 500 就能让错误率到 100%）。

03六个高频坑

  • 对 Counter 直接取当前值：看不出趋势，且进程重启时会「下降」——必须用 rate/increase。
  • rate 窗口小于 4 个采样间隔：曲线剧烈抖动甚至出现空洞，至少取 4 个点。
  • histogram_quantile 忘记 by (le)：聚合时丢了 le，分位数结果是错的（通常接近 0）。
  • 用 sum(rate(...)) 时把不同含义的序列混在一起：先确认标签维度是否需要 by 分组。
  • 拿 topk 做告警：Top N 在并发相近时会来回跳，告警会反复抖动，应改用固定阈值。
  • 高基数标签做聚合：by (user_id) 这类会让查询内存暴涨，甚至打挂 Prometheus。
# 定位慢查询：先看返回多少序列
count(sum by (le, job) (rate(http_request_duration_seconds_bucket[5m])))

# 用 recording rule 预计算（把昂贵查询固化成新指标）
groups:
  - name: api
    interval: 30s
    rules:
      - record: job:http_requests:rate5m
        expr: sum by (job) (rate(http_requests_total[5m]))
      - record: job:http_request_duration:p95
        expr: histogram_quantile(0.95, sum by (le, job) (rate(http_request_duration_seconds_bucket[5m])))
# 之后查询直接读预计算结果，快一个数量级

04常见疑问

问：rate 和 irate 该用哪个？

看趋势用 rate（对窗口内所有点做平均，平滑）；看瞬时毛刺用 irate（只取最后两个点，敏感但抖）。告警用 rate，画「当前有多高」用 irate。注意 irate 对长窗口没有意义。

问：为什么我的 P99 比最大值还大？

因为 histogram_quantile 是在 bucket 之间做线性插值，当 bucket 边界设置不合理（比如只有 0.1/1/10 三档）时，插值结果会失真，甚至超过实际最大值。解决方法是把 bucket 划细，或改用 _sum/_count 算平均值。

问：查询很慢怎么办？

三个方向：① 减少参与计算的序列数（先在标签上过滤）；② 缩短时间范围与窗口；③ 用 recording rule 预计算。如果慢查询来自高基数标签，则要从采集侧降基数。

问：Prometheus 里查不到数据怎么排查？

按顺序查：① 目标是否 UP（Targets 页）；② 指标名/标签是否写对（用 {__name__=~".*keyword.*"} 搜）；③ 是否有数据但被过滤掉（去掉标签条件重试）；④ 时间范围是否正确。
