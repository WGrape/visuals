🕹️ 中介者

让多个对象通过一个协调者沟通，减少两两依赖。

一句话记住机场塔台统一调度飞机起降，飞机无需互相决定跑道顺序。

01 · 从问题出发

为什么会需要这个模式？

表单里地区、城市、邮编输入框互相通知；组件越多，两两引用越乱。

订单表单里的国家、城市、邮编、运费组件互相监听。增加一个“配送方式”后，多个组件都要更新监听逻辑，依赖关系接近网状。

😵 直接写会怎样

country.onChange = () => { city.reset(); postcode.reset(); shipping.refresh() }
city.onChange = () => { postcode.reset(); shipping.refresh() }
shipping.onChange = () => { city.filter(); postcode.reset() }

💡 关键转折

组件只把变化告诉 Mediator；Mediator 决定谁该更新。

组件只报告自身发生了什么；中介者统一解释交互规则并调用相关组件。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

class FormMediator {
  onRegionChanged(region) {
    city.setOptions(citiesFor(region))
    city.clear()
    postcode.clear()
  }
}
region.onChange(value => mediator.onRegionChanged(value))

读代码时抓住三件事

  1. 组件上报事件，不主动调用别的组件。
  2. 中介者持有交互规则，决定更新路径。
  3. 各组件保留自己的局部状态和显示职责。

换个业务场景，还能认出来吗？

多人聊天室也是常见例子：成员向 ChatRoom 发消息，由房间决定转发给谁。若每个成员直接保存所有其他成员，加入和离开都会改很多关系。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

多个对象相互通知形成密集网状依赖

三个具体场景

  • 表单地区、城市与邮编联动
  • 聊天室由房间转发消息
  • 航空塔台协调飞机起降

不适合或要小心

中介者可能膨胀成巨型规则类；可按业务流程拆分。它负责交互规则，不应吞掉各组件自身职责。

中介者可能膨胀成万能协调器，应按业务流程拆分

最容易混淆的相邻模式

模式真正的区别
观察者发布者广播状态变化，订阅者各自处理；中介者主动协调多个对象间的交互规则。
外观为复杂子系统提供单向高层入口；中介者协调同级对象之间持续的互动。

区分时问自己：只广播变化，还是集中决定参与者间的交互规则？

落地前检查

  • 别把所有业务规则堆成一个巨型中介者。
  • 组件事件命名要表达业务含义。
  • 测试一次变更会更新哪些组件，以及是否产生循环触发。

两道检验理解的小题

城市组件需直接引用地区组件吗？

不用；变更由中介者接收并协调。

为什么城市组件不直接清空邮编组件？

模式速览：把网状依赖压成一个中心

当一组对象互相调用、关系越来越乱时，中介者的做法是让它们都只跟一个中心对象说话。对象之间不再直接引用彼此，交互规则集中在中介者里，网状结构就变成了星形结构。

意图用中介对象封装一组对象的交互，降低耦合
角色中介者（协调规则）与同事（只与中介者通信）
何时用对象间交互复杂、关系呈网状、规则经常变
代价中介者容易膨胀成上帝类；交互路径变长
中介者把网状调用收敛为星形：所有交互都经由中心

四个相近模式的区别

模式通信方向谁决定行为适合
中介者同事只与中介者双向通信中介者集中决定交互规则复杂且集中
观察者发布者广播，订阅者被动接收订阅者各自决定一对多通知、发布方不关心谁听
门面外部单向调用门面门面只做转接简化复杂系统的入口
事件总线任意方发布与订阅订阅方分散决定跨模块解耦、不需要集中规则

中介者与观察者怎么选

关键看是否需要集中决策。如果交互有复杂的先后顺序与条件判断，集中在一个中介者里更好维护；如果只是「发生了什么，谁关心谁自己处理」，观察者更松散也更自然。

中介者与门面怎么选

门面是单向的：外部调用它，它转给内部，内部组件之间仍可能互相调用；中介者是双向的：它主动协调内部组件之间的交互。一个对外简化，一个对内解耦。

Go 里的实现：一个聊天室

// 中介者接口 type Room interface { Send(from string, msg string) Join(u *User) } // 具体中介者：集中管理所有交互规则 type ChatRoom struct { mu sync.Mutex users map[string]*User } func (r *ChatRoom) Join(u *User) { r.mu.Lock() defer r.mu.Unlock() r.users[u.name] = u } func (r *ChatRoom) Send(from string, msg string) { r.mu.Lock() defer r.mu.Unlock() for name, u := range r.users { if name == from { continue // 规则集中在这里：不回发给自己 } u.Receive(from, msg) } } // 同事：只依赖中介者，不认识其他同事 type User struct { name string room Room } func (u *User) Say(msg string) { u.room.Send(u.name, msg) // 只告诉中介者 } func (u *User) Receive(from string, msg string) { fmt.Printf("%%s 收到 %%s：%%s\n", u.name, from, msg) } // 关键点： // 1) 同事之间零引用，加人或移除只影响中介者 // 2) 交互规则集中在 Send 里，改规则只改一处 // 3) 中介者要处理并发，因为多个同事会同时调用它

深入自检：中介者的五个问题

中介者变成上帝类怎么办？

这是最常见的问题：所有规则都往里堆，最后它比原来的网状结构还难维护。应对办法是按业务场景拆分多个中介者、把纯计算逻辑下沉到领域对象、或者当规则真的复杂到一定程度时，改用状态机或流程编排。

同事之间完全不能通信吗？

不是绝对禁止。模式强调的是把交互规则集中，而不是禁止一切直接调用。如果两个同事之间的调用纯粹是数据查询、不涉及协调逻辑，直接调用反而更清楚。需要协调的才走中介者。

和事件总线冲突吗？

可以互补：模块之间用事件总线松散解耦，模块内部用中介者集中协调。判断标准是规则的归属：规则属于某个具体场景、需要集中控制，用中介者；规则分散在各订阅方、彼此独立，用事件总线。

性能上有什么代价？

多一层转发，而且中介者往往成为并发瓶颈：所有交互都经过它，锁竞争会集中在这里。高并发场景要注意锁粒度，必要时把中介者按场景分片。

什么时候不该用？

当对象之间只有简单的两三个调用关系时。引入中介者只会让简单的调用绕一圈，读者要先理解中介者才能看懂原本一眼就能看明白的交互。模式是为了降低复杂度，不是为了增加层次。
