🔄 读写流程

写入与读取的端到端路径、Scan 与一致性

写入路径（端到端）

  1. Client 定位目标 Region 所在的 RS（先查本地缓存的 meta 路由）。
  2. 写请求发到 RS：先追加 WAL（HDFS 副本落盘，保证崩溃可恢复）。
  3. 再写入对应列的 MemStore（内存，按 rowkey 排序）。
  4. 当 MemStore 达到阈值，异步 flush 成 HFile；Client 无需等待 flush 即可收到「写入成功」。
  5. 后台 Compaction 把零散 HFile 合并。

读取路径（端到端）

  1. Client 定位 Region → 直接请求 RS（不经由 HMaster）。
  2. RS 先查MemStore（含最新未落盘数据）。
  3. 再查 BlockCache，未命中则从 HFile 读；用 Bloom Filter 跳过确定不含该 key 的文件。
  4. 把来自 MemStore 与各 HFile 的多个版本合并，按时间戳返回最新可见值。

Scan 扫描

  • Scan 是「范围读」：按 rowkey 区间顺序遍历，可跨多个 Region。
  • Client 会并行向涉及的多个 RS 发请求，并批量化（caching/batch）减少 RPC 往返。
  • 注意：全表 Scan 很重，务必加起止范围或前缀过滤，避免压垮集群。

一致性模型

保证说明
行级原子性对同一行的 Put（无论多少列）是原子的；跨行不是
写后读一致（MVCC）写入成功后，同一 Client 立即可读到刚写的值
无跨行事务需要「转账式」原子操作要用 checkAndPut / 应用层 / Phoenix 有限事务

批量与异步写入

高吞吐写入应使用 BufferedMutator 或批量 put(List)，在客户端攒批后一次 RPC 发出，显著降低网络与 WAL 开销。

💡 WAL 能关吗？ 可以设 setDurability(SKIP_WAL) 关闭，写入更快但 RegionServer 崩溃会丢数据——只适合可重算的临时数据（如中间结果）。绝大多数场景应保持开启。
