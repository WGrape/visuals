为什么 Go 项目偏爱代码生成

Go 没有宏、没有注解运行时、泛型能力也有限，于是社区选择了一条实用路线：把重复、机械、易错的代码用工具生成出来。既保持静态类型与性能，又省掉手写样板。

代码生成：定义 → 工具 → 生成产物
go:generate写在源码注释里，go generate 会执行。
产物入库生成结果提交，构建不依赖工具链。
别生成业务逻辑生成物应保持机械、可重新生成。
手改即丢失需要修改就改模板或源定义。

自己写一个生成器：两条路

文本模板路线

用 text/template 拼出 Go 源码，简单直接。

tmpl := `package {{.Package}} func (s {{.Type}}) String() string { switch s { {{range .Values}}case {{.Name}}: return "{{.Text}}" {{end}}} return "unknown" }` t := template.Must(template.New("x").Parse(tmpl)) t.Execute(f, data) // 最后用 format.Source 格式化

适合结构固定的输出，缺点是容易拼出语法错误。

AST 路线

用 go/ast 构造语法树再打印，天然保证语法正确。

f := &ast.File{ Name: ast.NewIdent("model"), Decls: []ast.Decl{ &ast.GenDecl{ Tok: token.TYPE, Specs: []ast.Spec{typeSpec}, }, }, } printer.Fprint(out, token.NewFileSet(), f)

适合复杂或需要重排现有代码的场景，学习成本更高。

工程约定

  • 生成文件统一后缀（如 _gen.go / .pb.go）
  • 文件头写 DO NOT EDIT 标记
  • CI 里校验「重新生成后无 diff」
  • 生成器本身要有版本与测试

深入自检

生成的代码要不要提交到仓库？

通常要。这样构建环境不需要安装 protoc、mockgen 等一系列工具，构建可复现、编译更快。同时在 CI 里加一步「重新生成并比对，有 diff 就失败」，防止有人改了源定义却忘了重新生成。

go generate 和构建流程是什么关系？

go generate 不会在 go build 时自动执行，它是开发者显式触发的工具。这保证了构建的确定性与速度——构建只编译仓库里已有的代码。

为什么不建议生成业务逻辑？

生成物是「可随时重新生成」的，一旦里面混入手写的业务规则，就会出现「改了源定义会覆盖业务代码」的两难。生成层应只负责机械映射，业务判断留在手写代码里。

模板生成和 AST 生成怎么选？

输出结构固定、内容简单的用模板，几十行就能搞定；需要处理已有代码、结构多变、或要求语法绝对正确的用 AST。多数团队先用模板，复杂度上来后再换 AST。

生成器自身需要测试吗？

需要，而且很重要。生成器的 bug 会扩散到所有产物。最有效的测试是「黄金文件」：准备若干输入与期望输出，生成后逐字节比对，输出稳定即通过。

生成器选型：什么时候用哪种手段

Go 没有泛型宏和运行时反射式代码生成，官方给的是 go:generate + 独立生成器程序。选型的第一个判断：能不能用普通代码解决——能就不用生成。

手段适用不适用典型产物
go:generate + 生成器重复样板、协议/IDL 转代码逻辑会经常变的（改生成器和改产物会打架）*_mock.go、*.pb.go
text/template结构固定、参数化的代码需要理解已有代码语义CRUD、DTO、枚举方法
go/ast + go/printer需要读源码结构再产出简单重复（杀鸡用牛刀）接口包装、埋点注入
反射（运行时）框架级通用逻辑（序列化、ORM）能编译期解决的——反射有性能与类型安全代价—
泛型（Go 1.18+）优先于生成：容器、算法复用需要按类型生成不同方法名的场景—

# 然后：

# 2) protobuf

# 3) mock（gomock）
#go:generate mockgen -source=repo.go -destination=mock_repo.go -package=mock
mockgen -source=repo.go -destination=mock_repo.go -package=mock

# 4) go-zero 的 goctl：从 .api 一次生成 handler/logic/svc + 文档
goctl api go -api order.api -dir .
goctl model mysql ddl -src user.sql -dir ./model

# 5) 常用检查
gofmt -l .               # 生成的代码必须 gofmt 过
go build ./... && go vet ./...

go:generate 只是标记，不会自动跑，必须显式执行 go generate ./...。生成的文件建议：① 以 _gen.go 或 .pb.go 结尾便于识别；② 头部加 // Code generated by xxx. DO NOT EDIT.（很多 linter 会识别这行并跳过检查）；③ 提交进仓库（这样 CI 和别人 clone 后不用装生成器）。

写一个生成器的两种路线

路线 A：模板驱动

// 路线 A：text/template（结构固定时最快）
package main

import (
    "os"
    "text/template"
)

const tpl = `// Code generated by gen.go. DO NOT EDIT.
package {{.Package}}

{{range .Types}}
func (t *{{.Name}}) Clone() *{{.Name}} {
    if t == nil { return nil }
    out := *t
    return &out
}
{{end}}
`

func main() {
    t := template.Must(template.New("c").Parse(tpl))
    f, _ := os.Create("clone_gen.go")
    defer f.Close()
    t.Execute(f, map[string]any{
        "Package": "model",
        "Types":   []map[string]string{{"Name": "User"}, {"Name": "Order"}},
    })
}
// 注意：模板里 {{ }} 与 Go 源码的 {} 会打架，可用 {{"{"}} 或改用 delims

路线 B：AST 驱动

// 路线 B：go/ast（需要理解已有代码）
// 典型用途：扫出一个接口的所有方法，生成装饰器/埋点包装
package main

import (
    "go/ast"
    "go/parser"
    "go/token"
    "fmt"
)

func main() {
    fset := token.NewFileSet()
    pkgs, err := parser.ParseDir(fset, "./service", nil, parser.ParseComments)
    if err != nil { panic(err) }
    for _, pkg := range pkgs {
        ast.Inspect(pkg, func(n ast.Node) bool {
            ts, ok := n.(*ast.TypeSpec)
            if !ok { return true }
            it, ok := ts.Type.(*ast.InterfaceType)
            if !ok { return true }
            fmt.Println("interface:", ts.Name.Name)
            for _, m := range it.Methods.List {
                for _, nm := range m.Names {
                    fn := m.Type.(*ast.FuncType)
                    fmt.Printf("  method %s params=%d results=%d\n",
                        nm.Name, len(fn.Params.List), numResults(fn))
                }
            }
            return true
        })
    }
}
坑表现解法
模板定界符冲突Go 代码的 {} 被当成模板动作t.Delims("{{{", "}}}") 换成三括号
生成代码没 gofmtCI 卡住、diff 很大生成后跑 format.Source(src)（go/format）再落盘
import 没自动加编译失败用 golang.org/x/tools/imports.Process 自动整理
生成器和产物互相改改了产物被覆盖，改了生成器产物全变定死规则：产物永不手改，需求变就改生成器
go:generate 在 CI 里漏跑产物与源不同步CI 加一步 go generate ./... && git diff --exit-code
生成目录未在 git 里别人 clone 后编译不过产物提交进仓库，或用 vendor 固定生成器版本
泛型出来了，还需要代码生成吗？

需要的场景变少了，但没消失。泛型能解决「同一逻辑、不同类型」（如 Map[T,U]），但解决不了：① 从 IDL/proto/sql schema 生成代码；② 生成有具体名字的方法（如 Status.String()）；③ 生成带结构体字段级逻辑的代码（ORM、校验器）。判断标准：能不能用类型参数表达，能就用泛型（更安全、更好读），不能才生成。

go:generate 和 Makefile 脚本比有什么优势？

① 声明就在源码旁边，不会「忘了跑」；② go generate ./... 统一递归执行，不需要维护脚本清单；③ 与 go 工具链一体，跨平台。缺点是它不解决依赖顺序（生成器本身要先装好），所以大项目仍会配 Makefile 做 make gen 封装（先 go install 工具，再 go generate）。

生成的代码怎么测试？

两条原则：① 测生成器，不测产物——用 golden file 测试（把期望产物存在 testdata/，跑生成器后比对字节）；② 产物若有逻辑 bug，改生成器 + 更新 golden，不要手改产物。加 CI 检查 go generate && git diff --exit-code 能防止产物漂移。
