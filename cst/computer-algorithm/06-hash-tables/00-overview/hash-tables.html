第 06 章 · 哈希表

把键映射到存储位置

哈希函数让“按键找值”通常很快，但碰撞、负载率与扩容决定了它的实际边界。

核心速览

哈希函数key → 数组下标，要快且尽量均匀
碰撞 Collision不同 key 映射到同一位置，必然发生
负载因子 α元素数 / 桶数，决定性能与何时扩容
扩容 Rehashα 超阈值时扩容并重新分布所有元素

先建立直觉：数组 + 一个「算位置」的函数

数组按下标访问是 O(1)，这是所有数据结构里最快的查找。问题是下标必须是整数，而我们要用「名字」「字符串」「对象」来查。

哈希表的思路直白得惊人：用一个函数把任意 key 换算成数组下标，然后直接访问那个位置。

查「张三的成绩」：hash("张三") = 7 → 直接看 bucket[7]。不需要遍历、不需要比较、不需要排序——一步到位。

整个结构的复杂度就压在这一件事上：hash 函数要算得快，且要把不同的 key 尽量均匀地分散到各个位置。

碰撞：不可避免，只能应对

因为「key 的可能取值」远多于「数组位置数」，碰撞一定会出现——这是抽屉原理，不是设计缺陷。真正的问题是碰撞了怎么办。

策略做法优点缺点使用者
链地址法每个桶挂一个链表（或红黑树）实现简单；删除容易；对高负载容忍度高指针开销；缓存不友好Java HashMap、C++ unordered_map、Python dict（变体）
开放寻址冲突就往后探测空位无指针、内存紧凑、缓存友好容易聚集；删除需墓碑；负载率必须低Python dict、Redis 哈希表、Go map
一个重要的工程优化：Java 8 的 HashMap 在单个桶的链表长度超过 8 且总容量 ≥ 64 时，会把链表转换成红黑树，把最坏查找从 O(n) 降到 O(log n)。这是为了防御「有人恶意构造大量同哈希值的 key」导致的哈希碰撞攻击。

负载因子与扩容

负载因子 α = 元素数 / 桶数。它同时衡量「空间利用率」和「碰撞概率」——α 越大，碰撞越频繁。

  • 链地址法：α 可以 > 1，通常阈值设 0.75。
  • 开放寻址：α 必须 < 1（否则可能找不到空位），通常阈值 0.5~0.75。

扩容（rehash）：α 超过阈值时，新建一个约 2 倍大的数组，把所有元素重新计算位置搬过去。单次扩容是 O(n)，但它不常发生。

为什么是「均摊 O(1)」而不是「O(1)」？大多数插入是 O(1)，但偶尔触发一次 O(n) 的扩容。把这次开销摊到之前 n/2 次插入上，每次多摊 O(1)（等比数列求和收敛），所以均摊仍是 O(1)。这就是「均摊分析」的经典例子——和动态数组（ArrayList/Vector）扩容是同一个道理。
扩容时的一个陷阱：一次性搬迁大表会造成明显卡顿。生产级实现（如 Redis 的 dict）采用渐进式 rehash——同时保留新旧两个哈希表，每次增删改查时顺带搬迁一小部分，把 O(n) 的开销分摊到多次操作中，避免单次长停顿。

复杂度：真实的边界

操作平均最坏说明
查找 getO(1)O(n)最坏：所有 key 都碰撞到一个桶
插入 putO(1)O(n)含均摊的扩容成本
删除 removeO(1)O(n)开放寻址要用墓碑标记
遍历O(n)O(n)顺序无意义
「平均 O(1)」依赖三个前提：① 哈希函数分布均匀；② 负载因子受控（及时扩容）；③ key 的哈希值不会被恶意构造。三者任一失效，性能就会退化。这也是为什么语言运行时会给字符串哈希加随机化种子——防止攻击者预先算出碰撞值。

什么时候不该用哈希表

  • ❌ 需要顺序：范围查询、前驱后继、按序遍历 → 用平衡搜索树（哈希把键打散了，顺序信息丢失）。
  • ❌ key 是可变对象：改了 key 的内容，它的哈希值就变了，元素会「丢失」——必须用不可变对象做 key。
  • ❌ 只需要极值：用堆更省。
  • ❌ 数据量极小：几十个元素时，直接顺序扫描可能更快（常数小、无哈希开销）。
必须同时正确实现 hashCode 和 equals。Java 的约定：equals 相等的两个对象，hashCode 必须相等；反之不要求（碰撞允许）。如果只改了其中一个，哈希表会彻底失效——同一个对象放进去却取不出来。

🎯 面试问答

Q：哈希表的冲突怎么处理？两种方式各有什么优劣？

A：两种主流方式。链地址法：每个桶挂一个链表，冲突的元素串起来；优点是实现简单、删除方便、对高负载容忍度高，缺点是指针开销和缓存不友好（Java HashMap、C++ unordered_map 用这个）。开放寻址：冲突就按规则往后探测空位；优点是无指针、内存紧凑、缓存友好，缺点是容易「聚集」、删除必须做墓碑标记、负载因子必须严格小于 1（Python dict、Redis、Go map 用这个）。

Q：为什么哈希表的插入是「均摊 O(1)」？

A：因为扩容不是每次都发生。大多数插入只做一次哈希 + 一次写入，是 O(1)；但当负载因子超阈值时，要新建一个约 2 倍大的数组并把 n 个元素全部重新搬运，这是 O(n)。把这次开销摊到触发它之前的约 n/2 次插入上，每次多摊 O(1)（等比数列求和收敛到常数），所以均摊仍是 O(1)。这和动态数组 ArrayList 的扩容分析完全一致，是「均摊分析」的经典例子。

Q：负载因子是什么？为什么开放寻址必须小于 1？

A：负载因子 α = 元素数 / 桶数，同时衡量空间利用率和碰撞概率。链地址法下 α 可以大于 1（链表可以无限加长），通常阈值设 0.75；开放寻址下所有元素都必须放在数组里，如果 α ≥ 1 就可能根本找不到空位，插入会陷入死循环，所以必须严格小于 1，工程上通常取 0.5~0.75。α 越大碰撞越频繁，探测次数越多，性能越差。

Q：为什么哈希表的遍历顺序看起来是乱的？

A：因为元素位置由哈希值决定，而不是插入顺序。哈希函数的设计目标就是「把键均匀打散」，所以它天然会破坏任何原有顺序。这也是哈希表无法支持范围查询、前驱后继、有序遍历的根本原因——顺序信息在哈希过程中被丢弃了。如果需要有序，要用平衡搜索树（红黑树 / B+ 树）；如果既要 O(1) 查找又要保持插入顺序，可以在哈希表之外额外维护一个双向链表（这就是 LinkedHashMap 的做法）。

Q：为什么 Java 要求同时重写 hashCode 和 equals？

A：因为哈希表依赖两者的一致性约定：equals 相等的两个对象，hashCode 必须相等（反之不要求，碰撞是允许的）。查找时先用 hashCode 定位桶，再用 equals 在桶内比对。如果只重写 equals 而没重写 hashCode，两个「逻辑相等」的对象会算出不同的桶，导致放进去却取不出来；如果只重写 hashCode 而没重写 equals，桶内比对就会失败。两者必须成对重写。

Q：什么时候不该用哈希表？

A：四种情况：① 需要顺序——范围查询、前驱后继、有序遍历，哈希把键打散了做不到，要用平衡搜索树；② key 是可变对象——改了内容哈希值就变，元素会「丢失」，必须用不可变对象做 key；③ 只需要极值——用堆更省；④ 数据量极小——几十个元素时直接顺序扫描可能更快（常数小、没有哈希开销）。此外要警惕哈希碰撞攻击：攻击者构造大量同哈希值的 key 可以把 O(1) 拖成 O(n)，所以语言运行时通常给字符串哈希加随机化种子。
