01 · 从问题出发

为什么会需要这个模式？

每次创建图表都重新配置颜色、坐标轴、规则很费事；已有一个正确模板。

报表模板里有色板、坐标轴、多个序列。如果每次重新构造，调用方会重复十几行配置；若只做浅拷贝，又可能在修改副本序列时意外改变原模板。

😵 直接写会怎样

copy = template  // 只是另一个引用
copy.series[0].color = "red"
// template.series[0].color 也变成 red

💡 关键转折

原型提供 clone；复制后只改个性化字段。

复制的是对象图而非变量名。先判断哪些字段可共享、哪些字段会变，再由 clone 定义明确的复制策略。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

class ChartTemplate {
  clone() {
    return ChartTemplate(
      style = copy(this.style),
      axes = deepCopy(this.axes),
      series = deepCopy(this.series))
  }
}
sales = template.clone()
sales.title = "本周销售"

读代码时抓住三件事

  1. clone 决定每个字段的复制深度，不是盲目 JSON 序列化。
  2. 可变 axes/series 要复制，否则副本互相影响。
  3. 调用方拿到副本后只改差异部分，这是原型的价值。

换个业务场景，还能认出来吗？

游戏角色可从“基础法师”模板复制技能、初始属性与装备，再给不同 NPC 调整名字和等级；技能定义若不可变可共享，生命值等运行时状态必须独立。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

已有正确样板，复制后只改变少量字段

三个具体场景

  • 复制图表模板再换数据源
  • 从游戏角色模板创建 NPC
  • 复制复杂文档样式再改标题

不适合或要小心

关键是复制深度：共享可变列表会互相污染。数据库连接等外部资源通常不能直接复制。

有外部句柄或复杂可变对象图时，要先定义复制深度和资源所有权

最容易混淆的相邻模式

模式真正的区别
建造者从一系列步骤组装对象；原型以已有对象为起点复制。
享元多个对象主动共享不变部分；原型创建独立副本，但可按策略共享不可变资源。

区分时问自己：目标是独立副本，还是有意共享同一份不变状态？

落地前检查

  • 列出可变字段和外部资源，逐项确定复制策略。
  • 测试改副本不会改变模板和另一副本。
  • 不要复制打开的文件句柄、连接等无法安全克隆的资源。
06 · 自己说一遍

两道检验理解的小题

浅拷贝含可变数组的模板会怎样？

两个对象可能共用数组；改副本也会改模板，需按字段定义复制策略。

深拷贝是否意味着所有字段都必须复制？

不是。不可变对象可以共享；关键是任何可变状态都不能造成意外的相互影响。

模式速览：用复制代替构造

原型解决的是「创建对象很贵，但新对象和已有的差别很小」这一类问题：与其从头构造，不如拿一个现成的复制一份再改。它的核心是一个克隆方法，而不是一堆构造参数。

意图通过复制已有实例来创建新实例，避免昂贵的构造过程
角色原型接口（声明克隆）、具体原型、客户端
何时用构造成本高、对象差异小、需要运行时决定类型
代价深浅拷贝要分清；含引用的对象克隆容易出错
原型的流程：先备好样板，需要时复制并微调

四种创建方式怎么选

方式机制何时更好
直接构造调用构造函数，传全部参数参数少、构造便宜、类型确定
工厂方法由子类决定创建哪种产品类型在编译期分化、有清晰层级
原型克隆复制现有实例再改构造昂贵、差异小、类型运行时才定
构建器分步设置参数后一次性生成参数多且可选组合复杂

最大的收益在哪里

在于跳过昂贵的构造过程。如果创建对象需要读配置、建连接、算缓存，而新对象与已有对象只在两三个字段上不同，那么复制显然更划算。

最大的风险在哪里

在于浅拷贝。如果只复制了指针，两个实例会共享同一份可变数据，改一个影响另一个，而且这种 bug 往往很久后才暴露。

Go 里的实现：克隆与注册表

// 原型接口：只需要会克隆自己 type Prototype interface { Clone() Prototype } type Config struct { Name string Timeout int Headers map[string]string // 引用类型，克隆时要小心 } func (c *Config) Clone() Prototype { h := make(map[string]string, len(c.Headers)) for k, v := range c.Headers { h[k] = v // 逐个复制，避免共享同一个 map } return &Config{ Name: c.Name, Timeout: c.Timeout, Headers: h, } } // 注册表：按名字管理一批原型 type Registry struct { items map[string]Prototype } func (r *Registry) Register(name string, p Prototype) { r.items[name] = p } func (r *Registry) Create(name string) (Prototype, bool) { p, ok := r.items[name] if !ok { return nil, false } return p.Clone(), true } // 使用：拿到的是独立副本，可以放心改 c, _ := reg.Create("default") cfg := c.(*Config) cfg.Timeout = 30 // 关键点： // 1) 值类型的字段直接赋过去就是复制 // 2) 切片、映射、指针必须显式复制，否则是共享 // 3) 注册表里的原型应当视为不可变模板，不要直接改它

深入自检：原型的五个问题

深拷贝和浅拷贝怎么选？

看字段是否可变、是否希望共享。不可变的字段共享是安全的、也更快；可变字段必须复制。实际中最稳妥的是：先全量深拷贝保证正确，确认有性能问题后再针对性优化。

克隆和重新构造，哪个更快？

取决于构造的成本。如果构造只是填几个字段，克隆反而更慢（多一次拷贝）；如果构造涉及 IO、计算、配置解析，克隆就快得多。所以这个模式不是通用替代品，而是针对性优化手段。

循环引用的对象怎么克隆？

需要记录「已复制过的对象」，遇到重复引用时直接复用副本，否则会无限递归。这也是通用深拷贝库都要维护映射表的原因。如果对象图里有环，手写克隆要格外小心。

克隆后还要初始化吗？

有时需要。有些字段不适合被复制，比如唯一标识、创建时间、已建立的连接、运行时句柄。这些应该在克隆后重置或重新建立，否则会出现两个实例共用同一个 ID 或连接的情况。

什么时候不该用原型？

当对象结构简单、构造便宜时。这时引入克隆接口与注册表只是增加复杂度，直接构造更清楚。另外，如果类的字段经常变动，克隆方法也要跟着改，容易漏掉新加的字段。

核心价值用复制跳过昂贵的构造
关键接口一个克隆方法
深拷贝是底线引用字段必须显式复制
重置运行时字段标识、时间、连接不该照抄
注册表按名字管理一批模板
模板要不可变别直接改注册表里的原型
循环引用用映射表避免无限递归
适用配置模板、复杂对象、运行时定类型
