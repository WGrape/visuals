①五层结构：Database → Collection → Partition → Segment → Entity

Milvus 的数据组织是一棵自顶向下收窄的树：Database 做租户/业务隔离，Collection 是建 Schema 和索引的地方，Partition 是物理分组，Segment 是存储与检索的最小单位，Entity 是一行数据。理解这五层的边界，才知道该在哪一层做隔离、在哪一层做优化。

②Schema 与字段类型

Collection 在建的时候必须声明 Schema。字段分两大类：向量字段（参与相似度计算、建 ANN 索引）和标量字段（用于过滤、排序、回表展示）。

向量字段类型

类型存什么常见维度 / 用途
FLOAT_VECTOR32 位浮点稠密向量768 / 1024 / 1536 维，文本 Embedding 的绝对主力
FLOAT16_VECTOR
BFLOAT16_VECTOR		半精度稠密向量显存/内存紧张时的压缩方案，召回损失很小
BINARY_VECTOR位向量（0/1）图像指纹、SimHash，用 HAMMING / JACCARD 度量
SPARSE_FLOAT_VECTOR稀疏向量（词权重）BM25 / SPLADE 稀疏检索，与稠密向量做混合检索

标量字段类型

类型说明建索引建议
BOOL / INT8/16/32/64整型与布尔低基数用 INVERTED，高基数用 STL_SORT
FLOAT / DOUBLE浮点，注意精度比较INVERTED / STL_SORT

字段数量、VARCHAR 长度、向量维度都有上限（维度上限通常 32768）。维度是建表时就固定的，换 Embedding 模型等于换维度，往往要重建 Collection——这是 RAG 项目最容易踩的坑。

③主键与 auto_id

自己指定主键

auto_id=False：用业务 ID（如 MySQL 主键、文档 ID）。好处是天然幂等——重复插入同一 ID 会覆盖，能做断点续跑；删除时也直接用业务 ID。

服务端生成

auto_id=True：Milvus 分配雪花类递增 ID。好处是写入无需查重；代价是业务侧拿不到自然键，必须把业务 ID 另存一个标量字段，更新/删除要先查后删。

主键类型只能是 INT64 或 VARCHAR，且一个 Collection 只有一个主键字段。RAG 场景的推荐做法：auto_id=False + 业务 doc_id 作主键，文档更新时直接 upsert 覆盖。

④动态字段与 JSON

开启 enable_dynamic_field=True 后，写入时 Schema 里没声明的字段会被塞进保留字段 $meta（JSON 类型），查询时可以按 $meta['author'] 过滤。

好处

元数据演进不用改表：今天加 category，明天加 source，直接写就行。适合元数据不稳定的探索期。

代价

动态字段无法保证类型一致，过滤前要做类型转换，性能弱于显式字段；序列化体积也更大。稳定下来的高频过滤字段应该提升为显式字段并建索引。

折中做法

显式声明 80% 会被过滤的字段，剩下的塞进 $meta 兜底；对 $meta 里确实要高频过滤的键单独建 JSON path 索引。

⑤Partition 与 Partition Key

Partition 是 Collection 内的物理分组：查询时指定分区名就能只扫这部分数据，等价于“手工分区裁剪”。Partition Key 则是把这件事自动化——指定一个标量字段，Milvus 按其哈希值自动把数据分到不同分区。

维度手工 PartitionPartition Key
谁来创建业务侧显式创建 + 写入时指定分区名建表时声明字段，写入自动路由
分区数量有限（上限约 1024，版本相关）同样受数量上限约束，但无需人工维护
典型用法按时间（2026_q3）、按大客户切分，冷热分区可单独加载/释放按 tenant_id 自动分桶，天然做多租户隔离
注意分区过多会产生大量小 Segment，反而拖慢检索分区键基数要足够且分布均匀，否则出现热点分区
Partition 不是“缩小召回范围以提升精度”的工具——它只是减少扫描量。如果过滤条件本来就高度选择，用 INVERTED 标量索引 + 过滤表达式往往更灵活。

⑥Shard 与 Replica

Shard（num_shards）

写入通道数。每条数据按主键哈希落到某个 shard，对应一条独立的 WAL 流。提升写入吞吐靠它；shard 太多会让每个 shard 的 batch 变小、Segment 变碎，反而不利于检索。

Replica（num_replicas）

把若干 QueryNode 组织成一组，共同承载同一批 Segment 的读请求。提升查询 QPS 与容灾靠它；它消耗额外内存（同一份数据多份驻留）。

一句话记忆：shard 决定写多快，replica 决定读多快。写入瓶颈加 shard，读 QPS 瓶颈或需要滚动升级时加 replica。

⑦Segment 生命周期

Segment 是 Milvus 里索引和并行的最小单位。理解它的状态机，几乎能解释 Milvus 一半的行为：为什么刚写入的数据能立刻查到、为什么过一会儿才变快、为什么删除了空间没释放。
  • Growing：数据先进 WAL 再进 QueryNode 内存，可立即被检索，走暴力计算（小数据量下反而最快）。
  • Sealed：达到大小/时间阈值或手动 flush() 后封口，DataNode 把它序列化写入对象存储。
  • Indexed：IndexNode 异步对该段建索引，就绪前检索仍走暴力，就绪后切换为 ANN。
  • Compacted：后台把多个小段合并成大段，并把“软删除”的数据真正清除——删除不释放空间的原因基本都在这里。

⑧建模示例：一个文档库 Collection

from pymilvus import MilvusClient, DataType

client = MilvusClient(uri="http://localhost:19530")

schema = client.create_schema(auto_id=False, enable_dynamic_field=True)
schema.add_field("doc_id",     DataType.INT64,       is_primary=True)
schema.add_field("tenant",     DataType.VARCHAR,     max_length=64)   # 高频过滤 → 显式字段
schema.add_field("publish_ts", DataType.INT64)                          # 时间范围过滤
schema.add_field("text",       DataType.VARCHAR,     max_length=4096)
schema.add_field("embedding",  DataType.FLOAT_VECTOR, dim=768)           # 向量字段：维度建表后不可改

index_params = client.prepare_index_params()
index_params.add_index(field_name="embedding", index_type="HNSW",
                       metric_type="COSINE", params={"M": 16, "efConstruction": 200})
index_params.add_index(field_name="tenant",    index_type="INVERTED")
index_params.add_index(field_name="publish_ts", index_type="INVERTED")

client.create_collection(collection_name="docs", schema=schema,
                         index_params=index_params, num_shards=2)
把高频过滤字段显式声明 + 建 INVERTED 索引，是这个建模里最关键的一步；不建索引的过滤条件会退化成全段扫描。

⑨建模决策清单

决策点怎么定
维度由 Embedding 模型定死，改模型 ≈ 重建表。提前确认模型与降维方案。
主键能用业务 ID 就用业务 ID（auto_id=False），换来自幂等写入与直接删除。
过滤字段80% 会被过滤的字段显式声明 + 建标量索引；元数据易变的部分交给 $meta。
分区租户数少且固定 → 手工 Partition；租户多或不确定 → Partition Key。
shard 数按写入峰值定，通常个位数起步；别为了“看起来分布式”开几十个。
索引先和数据量、内存、召回目标对齐，见Milvus 索引类型。
本页数值（上限、默认值）随版本演进，给出的是 Milvus 2.x 常见取值，落地前请用你部署版本的官方文档核对。
Milvus 的数据模型可以概括为一句话：Collection 定结构，Partition 定分组，Segment 定执行，Entity 定内容。把「哪些字段会被过滤」和「数据会被切成多大的段」这两件事想清楚，后面索引、一致性、容量规划的问题都会简单很多。
