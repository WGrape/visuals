✍️ 手写 LRU：哈希表 + 双向链表

经典面试题，也是理解缓存淘汰的最佳入口。目标是 get 和 put 都做到 O(1)。

易错点

忘记更新访问时间

先建立直觉：一排按新鲜度排列的挂钩

想象墙上一排挂钩，越靠左越新鲜。每次你用了某件衣服，就把它取下来挂到最左边；挂钩满了，就摘掉最右边那件。

问题在于：如果每次都要从头找到那件衣服，效率就是 O(n)。所以我们再加一个索引本（哈希表），记下每件衣服挂在哪个钩子上——这样一步就能找到它。

哈希表负责「找到它」，双向链表负责「挪动它」，两者配合就是 O(1) 的 LRU。

为什么必须是双向链表

结构删除节点结论
数组删除需移动元素 O(n)❌
单链表删除需先找前驱 O(n)❌
双向链表已知节点即可摘除 O(1)✅
关键点：哈希表让我们能直接拿到节点本身（不只是值），而双向链表让我们能在知道节点的情况下 O(1) 摘除它（因为它同时持有 prev 和 next 指针）。单链表做不到后者——你必须从头遍历找前驱节点。

结构示意

Go 实现

type entry struct {
    key, value int
    prev, next *entry
}

type LRUCache struct {
    cap  int
    m    map[int]*entry
    head, tail *entry   // 哨兵节点，简化边界处理
}

func NewLRU(cap int) *LRUCache {
    h, t := &entry{}, &entry{}
    h.next, t.prev = t, h
    return &LRUCache{cap: cap, m: make(map[int]*entry), head: h, tail: t}
}

func (c *LRUCache) Get(key int) int {
    if e, ok := c.m[key]; ok {
        c.moveToHead(e)          // 关键：命中后必须刷新新鲜度
        return e.value
    }
    return -1
}

func (c *LRUCache) Put(key, value int) {
    if e, ok := c.m[key]; ok {  // 已存在：更新值 + 移到头部
        e.value = value
        c.moveToHead(e)
        return
    }
    e := &entry{key: key, value: value}
    c.m[key] = e
    c.addToHead(e)
    if len(c.m) > c.cap {
        victim := c.tail.prev    // 最久未使用
        delete(c.m, victim.key)  // 别忘删 map，否则内存泄漏
        c.remove(victim)
    }
}

func (c *LRUCache) remove(e *entry) {
    e.prev.next, e.next.prev = e.next, e.prev
}
func (c *LRUCache) addToHead(e *entry) {
    e.prev, e.next = c.head, c.head.next
    c.head.next.prev, c.head.next = e, e
}
func (c *LRUCache) moveToHead(e *entry) {
    c.remove(e)
    c.addToHead(e)
}

五个易错点

易错点后果正确做法
Get 命中后没有移到头部访问顺序不更新，LRU 退化成 FIFO命中必须 moveToHead
Put 已存在时只改值不移动同上，顺序失真更新值后也要移到头部
淘汰时只删链表不删 map内存泄漏，map 无限增长两个结构都要删
忘记设置容量上限判断缓存无限增长插入后检查 len > cap
不用哨兵节点头尾插入/删除要写大量边界判断，易错用 head/tail 哑节点，逻辑统一
并发安全：上面的实现不是线程安全的。生产环境要么加 sync.Mutex（简单但串行化），要么用分片锁（如 Caffeine 的做法），要么直接使用成熟库。

操作复杂度原因

PutO(1)同上

🎯 面试问答

Q：为什么哈希表里要存节点指针，而不是只存值？
A：因为拿到值之后还要把它移到链表头部，这个操作需要节点对象本身（它有 prev/next 指针可以直接摘除）。如果 map 只存值，你就得遍历链表去找到这个节点，退化为 O(n)。map 存节点 = 用空间换 O(1) 的移动能力。

Q：单链表为什么不行？
A：删除一个节点需要知道它的前驱。单链表只能从头遍历找前驱，是 O(n)。双向链表因为节点自带 prev，拿到节点后直接 e.prev.next = e.next 就能摘除，是 O(1)。这正是必须双向的原因。

Q：哨兵节点有什么用？
A：它让「插入到头部」「删除尾部」不再需要判断「链表是否为空」「是不是第一个节点」等边界情况。head 和 tail 永远存在，所有插入删除都是统一的指针操作。代价只是两个空节点，收益是代码大幅简化、不易出错。

Q：这个实现能直接用在生产吗？
A：不建议。它有三个生产级缺陷：① 非线程安全，需要加锁；② 无过期时间（TTL），数据永不主动失效；③ 无容量外的保护（无统计、无命中率监控、无淘汰回调）。生产请用 Caffeine（Java）、groupcache/自研分片锁（Go）或 Redis 等成熟方案。手写版的价值在于理解原理和应对面试。

第一层 · 数据结构选择的理由

手写 LRU 的标准答案是 哈希表 + 双向链表。理解「为什么必须是这两个组合」，比背代码重要得多。

操作哈希表单独链表单独哈希 + 双向链表
get(key)O(1)O(n)（要遍历找）O(1)
put(key, val)O(1)O(n)（找位置）O(1)
删除任意节点O(1)O(1)（若有指针）O(1)
找到最久未用的做不到（无序）O(1)（尾节点）O(1)
维护访问顺序做不到天然有序天然有序
  • 哈希表解决「快速定位」：O(1) 找到 key 对应的节点。
  • 双向链表解决「维护顺序 + O(1) 删除」：为什么要双向？因为删除一个节点需要修改它前驱的 next 指针——单链表没有前驱指针，删除就要 O(n) 查找前驱。这是「双向」的唯一理由，但它是必需的。
  • 哨兵节点（dummy head/tail）：用两个不存数据的哨兵节点，可以消除所有边界判断（头插、尾删都不用判断空）。这是实现技巧，不是必需但强烈推荐。
  • 顺序约定：通常规定「越靠近头部越新」。所以 get/put 后把节点移到头部，淘汰时删尾部。

第二层 · 完整实现与复杂度

Go 实现

// —— Go 实现（哈希表 + 双向链表，含哨兵）——
type entry struct {
    key, value int
    prev, next *entry
}

type LRUCache struct {
    cap    int
    m      map[int]*entry
    head, tail *entry   // 哨兵节点：head.next = 最新，tail.prev = 最旧
}

func NewLRU(capacity int) *LRUCache {
    h, t := &entry{}, &entry{}
    h.next, t.prev = t, h          // 互相指向（空链表）
    return &LRUCache{cap: capacity, m: make(map[int]*entry), head: h, tail: t}
}

func (c *LRUCache) Get(key int) int {
    if e, ok := c.m[key]; ok {
        c.moveToHead(e)            // 【关键】访问后移到头部
        return e.value
    }
    return -1
}

func (c *LRUCache) Put(key, value int) {
    if e, ok := c.m[key]; ok {
        e.value = value
        c.moveToHead(e)
        return
    }
    e := &entry{key: key, value: value}
    c.m[key] = e
    c.addToHead(e)
    if len(c.m) > c.cap {
        c.removeTail()             // 超容量 -> 淘汰最久未用
    }
}

// —— 三个原子操作（所有 bug 都出在这里）——
func (c *LRUCache) remove(e *entry) {
    e.prev.next = e.next
    e.next.prev = e.prev
    e.prev, e.next = nil, nil      // 【防止内存泄漏】
}

func (c *LRUCache) addToHead(e *entry) {
    e.prev = c.head
    e.next = c.head.next
    c.head.next.prev = e
    c.head.next = e
}

func (c *LRUCache) moveToHead(e *entry) {
    c.remove(e)                    // 先摘下来
    c.addToHead(e)                 // 再插到头
}

func (c *LRUCache) removeTail() {
    if c.tail.prev == c.head { return }   // 空
    e := c.tail.prev
    delete(c.m, e.key)             // 【别忘了删 map！】
    c.remove(e)
}

// —— 复杂度 ——
//   Get: O(1)   Put: O(1)   空间: O(cap)
//   常数很小：只有几次指针操作和一次 map 访问
维度数值说明
时间复杂度Get/Put 均 O(1)几次指针操作 + 一次 map 访问
空间复杂度O(cap)链表节点 + map 条目（存了两份引用）
每条目额外开销约 50~100 字节链表节点的 2 个指针 + map 条目
并发版开销加锁：约 20~50ns/次sync.Mutex 或 RWMutex
分片优化分 N 片可降低锁竞争代价：全局 LRU 顺序被破坏（变成分片内 LRU）

面试常问的两个延伸：① 为什么不用单链表？（删除要 O(n) 找前驱）；② 怎么支持并发？（加锁，或分片降低竞争）。

第三层 · 常见错误清单

  • 忘了在淘汰时 delete(map, key) → 链表里删了但 map 里还在，下次 Get 会返回一个已从链表摘除的节点，导致 moveToHead 时崩溃或链表断裂。这是最常见的 bug。
  • remove 后没把 prev/next 置 nil → 节点被 map 或局部变量引用时无法 GC，造成内存泄漏（虽然 Go 有 GC，但链表结构互相引用会延长生命周期）。
  • Put 已存在的 key 时没有移到头部 → 更新操作也算「使用」，必须刷新顺序。漏了会导致刚更新的数据被淘汰。
  • Put 超容量时先插后删导致容量短暂超限 → 通常无害，但如果要求严格，可以先判断再插入。
  • 哨兵节点的初始化顺序错 → head.next = tail 和 tail.prev = head 都要设，且要在任何操作之前。
  • 容量为 0 的边界 → NewLRU(0) 后 Put 会立刻淘汰自己。要先判断 cap > 0（或允许容量 0 时直接不存）。
  • 并发访问没加锁 → map 并发读写会直接 panic（concurrent map read and map write）。单测要用 -race。
  • 以为 LRU 能抗扫描污染 → 不能。一次全表扫描会把所有热数据冲掉（这是 LRU 的固有弱点，需要 ARC/LRU-K/W-TinyLFU）。
  • 用 slice 实现导致 O(n) → 每次移动元素要拷贝，容量大时性能崩塌。必须用链表。
  • 用 container/list 时类型断言出错 → list.Element.Value 是 interface{}，取出后要断言，且存储时要存指针否则拿不到 map 的 key 去删除。

第四层 · 原理与取舍

LRU 的假设是时间局部性：最近被访问的，很可能马上再被访问。这个假设在大多数场景成立，但也有明确的失效情况——理解它什么时候失效，比会实现更重要。

  • LRU 失效场景一：扫描污染。一次全表扫描（如 SELECT * FROM big_table）会顺序访问大量数据，把缓存里真正的热数据全部挤掉，扫描结束后缓存里全是只访问一次的数据。命中率会断崖式下跌，需要很久才恢复。解法：LRU-K（访问 K 次才进缓存）、ARC（自适应）、W-TinyLFU（频率过滤）。
  • LRU 失效场景二：无局部性的随机访问。如果访问模式本身就是随机的（如扫描型任务），LRU 和不缓存没区别，甚至更差（多了维护链表的开销）。
  • LRU 失效场景三：循环访问模式。缓存容量 N，循环访问 N+1 个不同的数据——每次都是 miss（经典 Belady 异常场景）。此时加大缓存容量反而可能降低命中率（Belady 现象，虽然只存在于 FIFO，但类似的效应在 LRU 上也有体现）。
  • 为什么生产环境很少手写 LRU：因为已有成熟实现（Caffeine、Go 的 hashicorp/golang-lru、Redis 的近似 LRU）解决了并发、内存、统计等所有工程问题。手写 LRU 的价值是理解数据结构，不是用于生产。
  • Redis 为什么用「近似 LRU」：因为维护精确的 LRU 链表需要为每个 key 存前后指针（内存开销大），且每次访问都要移动节点。Redis 的做法是随机采样 N 个 key（默认 5 个），淘汰其中最久未用的——用极小的代价换来了接近 LRU 的效果。这是工程上非常典型的「用少量精度换大量成本」的取舍。

为什么必须是双向链表？单链表不行吗？

不行，除非你愿意付出 O(n)。原因很具体：当我们访问某个节点后要把它移到链表头部，这个操作分两步——① 从原位置删除该节点；② 插到头部。第①步「删除」需要修改前驱节点的 next 指针（让前驱跳过当前节点，直接指向后继）。单链表的节点只有 next 没有 prev，所以你拿不到前驱，只能从头遍历去找——这就是 O(n)。而双向链表有 prev 指针，可以直接拿到前驱，删除就是 e.prev.next = e.next; e.next.prev = e.prev 两步，O(1)。所以「双向」不是多余的设计，而是 O(1) 删除这个核心需求的直接结果。这也是为什么几乎所有「需要 O(1) 删除任意节点」的数据结构（LRU、LFU、各种 LRU 变体）都用双向链表。另外一个细节：如果用哨兵节点（不存数据的 head/tail），连「删除的是头/尾节点」的边界判断都能省掉，代码会干净很多。

并发情况下怎么做？加锁性能会不会很差？

最简单是全局 sync.Mutex（或 RWMutex，但读操作也要写链表，所以用 Mutex 就够）。性能量化：一次加锁+解锁在无竞争时约 20ns，而有竞争时会退化到几百 ns 甚至更高（涉及内核态的 futex 等待）。所以：低并发（QPS <10万）全局锁完全够用；高并发下会成为瓶颈。优化手段按效果排序：① 分片（Sharding）——按 key 哈希分成 N 个独立的 LRU（每片一把锁），把锁竞争降低到 1/N。代价是破坏了全局的 LRU 顺序（变成「分片内 LRU」），在分片数不多（如 16~64）时影响可接受；② 无锁化（如用 CAS + 原子操作）——实现复杂，收益有限；③ 用现成的高性能库——Caffeine（Java）用了类似 ConcurrentHashMap 的分段 + 无锁读 + 环形缓冲区异步处理，性能极高；Go 可以用 hashicorp/golang-lru。实践建议：不要自己造，用成熟实现——它们已经处理了并发、内存、统计等所有问题，而且性能比手写的好。手写 LRU 的价值是面试和理解原理。

Redis 的近似 LRU 到底损失了多少命中率？

损失很小，通常在几个百分点以内。Redis 的做法（maxmemory-samples，默认 5）：需要淘汰时，随机抽 5 个 key，比较它们的「空闲时间」（lru 字段），淘汰最久的那个。这显然不是全局最优，但：① 采样 5 个时，效果已经相当接近精确 LRU；② Redis 3.0 后引入了淘汰池（pool of 16 candidates），把多次采样的结果累积起来比较，效果进一步提升——实测与精确 LRU 的命中率差距通常在 1~3%；③ 调到 maxmemory-samples 10 时几乎与精确 LRU 无差别，代价只是淘汰时多比较几次（淘汰本身是低频操作）。而收益是巨大的：每个 key 只需存一个 24 bit 的 lru 字段（redisObject 里本来就有空间），不需要维护链表的两个指针（每个 key 省 16 字节），也不需要每次访问都移动节点。对于有几百万 key 的实例，这是几十 MB 的内存节省和显著的 CPU 节省。这是「用 1~3% 命中率换取大量内存和 CPU」的经典工程取舍，非常划算。附带一提，Redis 的 allkeys-lfu 模式用的是类似的近似思路（8 bit 的对数计数器 + 衰减），同样以极低成本获得了频率信息。
