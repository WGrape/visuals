♻️ 享元

共享大量对象中相同的不变部分。

一句话记住森林有十万棵树，树种贴图共用，坐标各不相同。
问题从哪来图解协作动手试一试伪代码选型与边界
01 · 从问题出发

为什么会需要这个模式？

地图标记都保存相同图标、颜色、字体，会重复占用大量内存。

地图上有十万个同类标记，每个标记都保存一份相同的图标像素、字体和颜色。这些数据加起来占用大量内存，而每个标记真正不同的只是坐标和名称。

😵 直接写会怎样

for point in points:
  markers.push(Marker(iconBytes=loadIcon("shop"),
                      font=Font("Sans", 12),
                      x=point.x, y=point.y))

💡 关键转折

把可共享的内在状态放进享元；坐标等外在状态在调用时传入。

把图标/字体等内在不变状态抽成共享 Style；坐标和名称留在每个标记的外在状态中。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

class StyleFactory {
  cache = Map()
  get(kind) {
    if (!cache.has(kind)) cache.set(kind, immutableStyle(kind))
    return cache.get(kind)
  }
}
for marker in markers:
  draw(factory.get(marker.kind), marker.x, marker.y)

读代码时抓住三件事

  1. cache 的 key 必须能唯一标识共享状态，例如树种+绘制规格。
  2. 共享 Style 应不可变，防止一棵树改动影响所有树。
  3. x/y 不存进 Style，否则所有同类标记会重叠。

换个业务场景，还能认出来吗？

文字编辑器中的每个字符位置不同，但同一字体规格的字形轮廓可共用。享元适合对象数量巨大且重复信息多的场景，不是所有对象都必须缓存。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

海量对象共享大量不变数据，内存重复已可测量

三个具体场景

  • 森林场景复用树种贴图
  • 地图标记复用图标与字体
  • 文本编辑器复用字形轮廓

不适合或要小心

不要把每个对象独有的可变状态写进共享实例；先测量内存收益。

共享状态必须不可变；缓存本身要有生命周期与容量策略

最容易混淆的相邻模式

模式真正的区别
单例限制某个类只有一个实例；享元按 key 管理多个共享实例。
原型复制对象产生独立副本；享元主动共享不变数据以节约内存。

区分时问自己：是全类只允许一个，还是按 key 共享多种对象？

落地前检查

  • 先测量对象数量和重复内存，确认收益。
  • 共享对象设计为不可变。
  • 缓存生命周期和上限要有策略，避免享元工厂本身无限增长。
06 · 自己说一遍

两道检验理解的小题

共用同一贴图的树能有不同位置吗？

能；贴图共享，位置作为外在状态在每次绘制时传入。

为什么 x/y 不应放在共享 Style 中？

坐标是每棵树自己的外在状态；放进共享对象会让同类树只能共用一个位置。
