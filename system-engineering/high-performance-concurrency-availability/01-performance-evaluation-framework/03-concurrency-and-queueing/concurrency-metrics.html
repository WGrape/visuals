并发数怎么测，才不会把连接数当请求数？

并发是一个某段边界内的在途数量。先选边界，再分清 active 与 waiting，最后才讨论平均、峰值和“最多能同时处理多少”。

连接、并行处理、in-flight：三个不同的数

连接数 · 通道

客户端与服务端之间的 TCP / QUIC 通道，可以空闲或复用。HTTP/2 等协议可在同一连接上传输多个请求；连接数不等于请求数。

并行处理数 · 占位

在指定处理阶段实际占用处理位的请求数。处理位也可能在等待下游 IO；它不一定等于 CPU 上真正同时执行的线程数。

in-flight · 未完成

在约定起止边界内已开始、但尚未结束的请求数。边界若包含排队，等待的请求也可能计入；不要把它直接当作并行处理数。

例如三个客户端请求都已被网关接纳，业务层同时只能处理两个，第三个在网关队列等待：此刻网关在途数是 3，业务处理位占用数是 2，网关等待数是 1。连接可能是 1 条、多条，也可能含空闲连接，不能凭这三个请求反推出连接数。三者是不同观察口径，不是每次都满足固定大小关系；更不是这段时间内的请求总量。

想知道等待的请求算不算在途？继续看请求生命周期与观测边界。

先画清三处边界

客户端未完成

从约定的请求开始时刻，到完整响应或本地终止。若起点设在取连接前，连接池等待也须纳入；本地尚未开始请求的待提交任务单列。

网关已接纳

请求进入网关到离开网关，若有网关内排队，通常也属于该边界的在途量；是否排队取决于实现。

业务处理中

进入业务处理位到释放。可能包括业务逻辑等待数据库/源站的时间，不包括进入该位之前的网关队列。

同一个请求在网关队列中，可以同时是“网关在途”和“网关等待”；queue 与 in-flight 不天然互斥。看完整生命周期 →

采集哪一类数？

指标类型起止事件 / 口径看出什么
active requestsGauge（个）进入业务处理位 +1，释放时 -1；超时、失败、取消也要按实际释放事件处理处理位是否接近上限
waiting requestsGauge（个）进入待处理队列 +1，开始处理或被取消/拒绝 -1等待是否持续积压
pool wait / queue wait耗时分布（ms）从开始等待池资源/处理位到获取或结束哪段造成 P95/P99 恶化
completed / rejectedCounter（次）完成、拒绝分别 +1；相邻采样差 ÷ 秒得到各自速率供应是否超过处理能力
TCP / QUIC connections、H2 streams各自的 Gauge（条/流）建连/断连、流创建/结束连接池与多路复用情况，不是 active requests

如果一次客户端调用超时，但服务端尚未停止，客户端指标可先归零，业务 active 仍可能为 1；不应要求两端数值始终相同。

平均并发与峰值并发必须分开报

窗口平均 L = ∫ 在途请求数 N(t) dt ÷ 窗口时长

例如 10 秒窗口前 9 秒始终有 10 个请求，最后 1 秒有 100 个：时间平均为 (9×10 + 1×100) ÷ 10 = 19，瞬时峰值为 100。每隔 10 秒抓取一次 Gauge 可能完全错过突刺；缩短采样间隔、记录高水位和入口/出口事件，再按实际窗口求平均。

“最大可承受并发 4,000”是可接纳量描述，不能直接当作这段窗口的实测平均 L。甚至在有上限时，也应结合拒绝率、队列等待、资源饱和与成功吞吐判断是否工作在可持续区间。

怎样把它和 QPS 联系起来

L平均 = λ完成 × W同边界平均

若客户端在稳定窗口内完成 8 次/秒，端到端平均驻留 2 秒，则客户端平均未完成请求约 16 个；这不是“开 16 个线程就能保证 8 QPS”。延迟随负载变化，连接池、账号 RPM 和服务端资源还会限制结果。业务层 active 数如果要代入，W 必须换成业务层的占位时间，而非客户端全程 RT。

逐步推导 Little 定律；继续看吞吐平台和瓶颈。

评估问题清单

  1. 标明作用域：客户端实例、Key、接口、网关实例或整个服务？多实例的 Gauge 求和时，是否有重复统计或不同步的采样？
  2. 同时报告 active、waiting、拒绝及它们的时间窗口；短突刺看高水位，持续负载看时间平均与长期队列增速。
  3. 对照完成/成功 QPS、业务段和端到端 P95/P99、CPU/IO/线程池等饱和度；只有并发升高而成功吞吐不再增长，通常是在制造等待。
  4. 连接数与流数独立排查：HTTP/1.1、HTTP/2、HTTP/3 的连接关系并不相同。
下一步：用指标做 QPS 容量评估 · 看尾延迟。

并发与排队的核心指标

指标定义怎么读
QPS / TPS每秒请求数 / 每秒事务数吞吐上限，压测曲线的拐点就是容量
并发数（Concurrency）同时在系统内的请求数不是 QPS
响应时间 RT从发出到收到必须看分位数，平均值会被长尾掩盖
Little's LawL = λ × W并发数 = 吞吐 × 响应时间。三者知二求一
p50 / p95 / p99 / p999分位响应时间SLA 通常签 p99；p99.9 才是用户真正投诉的那些
利用率 ρλ / μ 或服务繁忙比例ρ > 0.8 后延迟指数恶化
排队时延 Wq（M/M/1）ρ / (μ - λ)ρ=0.5→2ms，ρ=0.9→18ms（μ=500）
系统容量（M/M/c）c × μc 个服务员，利用率 ρ = λ/(c·μ)

Little's Law 实战用法：已知目标 QPS 1000、p99 响应时间 200ms，则系统内平均要有 1000 × 0.2 = 200 个并发请求在处理中。如果连接池/线程池只给了 50，那么 QPS 最多 50 / 0.2 = 250——连接池大小本身就是吞吐上限，压测上不去先查这个。

计算与压测命令

# Little's Law 三式互推
L = λ * W        # 并发数 = 吞吐 × 响应时间
λ = L / W        # 吞吐 = 并发数 / 响应时间
W = L / λ        # 响应时间 = 并发数 / 吞吐

# 例：200 并发、平均 RT 100ms -> λ = 200 / 0.1 = 2000 QPS
# 例：要 5000 QPS、RT 50ms -> 需要 L = 5000 * 0.05 = 250 并发

# M/M/1 排队时延（μ=500 帧/秒的服务能力）
for rho in (0.5, 0.7, 0.8, 0.9, 0.95):
    lam = 500 * rho
    print(rho, round(rho / (500 - lam) * 1000, 1), 'ms')
# 0.5 -> 2.0ms   0.7 -> 4.7ms   0.8 -> 8.0ms
# 0.9 -> 18.0ms  0.95 -> 38.0ms
# 压测：并发数必须显式设置，且要压到拐点之后
wrk -t4 -c200 -d30s --latency http://localhost:8080/api   # -c 是并发连接数
# 输出 Latency 的 50%/75%/90%/99% 和 Req/Sec

# 关键：逐步提高 -c 画吞吐曲线，找拐点
for c in 10 50 100 200 400 800; do
  wrk -t4 -c$c -d10s http://localhost:8080/api | grep 'Requests/sec'
done
# 吞吐不再增长甚至下降、而 RT 持续上升的那个点 = 系统容量上限

# 注意：wrk 的 -c 是连接数，若用 keepalive 才等于并发请求数
# 数据库连接池、线程池、HTTP client 连接池都会成为隐形瓶颈

压测与容量排查

症状原因处理
并发增加但 QPS 不涨池子（连接/线程）打满了查连接池大小、线程池队列；用 Little's Law 反推瓶颈容量
QPS 涨但 p99 暴涨ρ 接近 1，排队主导延迟限流比排队好：超过容量的请求快速失败，保住已受理请求的延迟
压测结果波动大测试机本身成瓶颈 / GC / CPU 争抢压测机与被测机分离；关闭 CPU 节能；跑多次取稳定段
平均 RT 好看但用户投诉看的是平均值，长尾被掩盖只看分位数；p99 与 p50 差 10 倍说明有严重的长尾
加了机器 QPS 不线性增长有串行瓶颈（锁、单点的 DB 主库、全局计数器）找 Amdahl 定律里的串行部分；先拆锁/分片
队列长度一直不为 0到达率持续大于服务率要么扩容要么限流；队列只是把问题推迟，不会消失
  • 限流的正确姿势：在入口限而不是在队列尾部限。放在队列尾部的限流只是把拒绝推迟，资源已经被消耗了。
  • 超时预算要递减：调用链 A→B→C，A 的超时必须 > B 的超时 > C 的超时，否则下游还在算、上游已经放弃，白白浪费资源。
