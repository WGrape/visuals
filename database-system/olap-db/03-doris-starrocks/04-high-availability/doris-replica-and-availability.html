Doris / StarRocks 副本与高可用

FE 元数据高可用、BE 多副本与 Tablet 自动修复、弹性扩缩容

DorisStarRocksFEBETablet 副本
① 架构回顾② FE 高可用③ BE 与 Tablet④ 读写高可用⑤ 弹性扩缩容⑥ 常见坑⑦ 常见疑问
一句话总结：Doris / StarRocks 的高可用靠两点——FE 元数据多副本选主保证控制面不挂，BE 数据多副本 + Tablet 自动修复保证数据面不丢。

01架构回顾

🧠 FE（Frontend）

负责 SQL 解析、优化、元数据管理、集群调度。元数据（表结构、Tablet 分布）存在 FE。

⚙️ BE（Backend）

负责数据存储与查询执行。表按分区、分桶切成多个 Tablet，真正的数据落在 BE。

两者分离：FE 挂了不影响已有 BE 的数据（数据在 BE 上），但元数据操作和写入需要 FE 在线。

02FE 高可用

  • FE 通常有 奇数个（1 / 3 / 5）：一个 Leader 处理写，Follower 通过共识协议（BDB-JE / Raft 类）同步元数据并选主。
  • Leader 挂了，剩余 Follower 重新选主，集群继续服务，元数据不丢。
  • 偶数个 FE 会多出"脑裂/选不出主"的风险，所以坚持奇数。

03BE 与 Tablet 副本

一张表按分区 + 分桶切成很多 Tablet（数据分片），每个 Tablet 默认 3 副本，分散在不同 BE 节点。

机制行为
写入三副本写多数派成功即返回，后台补齐其余副本
修复某 BE 下线/坏盘，FE 检测到副本缺失，自动从其他副本补全到新 BE
均衡FE 持续把 Tablet 在 BE 间均衡分布，避免热点

04读写高可用

  • 写：三副本多数派成功即可，单副本暂时不可达不影响写入成功。
  • 读：从任一健康副本读取；某个副本落后或损坏时，FE 路由到其他副本。
  • 查询：BE 多节点并行执行，单点 BE 故障由副本接管，查询整体不中断。

05弹性扩缩容

加 BE 节点后，FE 会自动把部分 Tablet 迁移到新节点以实现均衡；减节点时先把其 Tablet 迁走再下线。迁移是后台进行，在线查询通常不受影响，但需控制迁移并发，避免占用过多网络和 IO 影响在线负载。

06常见坑

🧩 FE 偶数部署

偶数 FE 在故障/网络分区时可能选不出主，导致元数据面不可用；务必奇数。

🚧 副本缺失

副本数不足（如只剩 1 份）时相关 Tablet 查询会失败或降级；监控副本健康度。

🌊 迁移打满

大规模扩缩容或故障后修复，Tablet 迁移可能占满带宽/IO，需限速。

07常见疑问

FE 和 BE 的高可用是独立的吗？
基本独立。BE 故障由数据副本接管，FE 故障由元数据选主接管。但"建表/改 schema/写入"这类需要 FE 的操作，在 FE 全部不可用时无法进行。
副本数能临时降低吗？
可以（如为省存储降为 2），但容错能力下降——任一副本故障就只剩单份，再坏就丢数据。生产一般保持 3。
扩容真的无感吗？
数据迁移在后台进行，查询走的是已有副本，所以查询层无感；但迁移会消耗网络和磁盘 IO，若不限速会与在线负载争抢，需调低迁移并发和带宽上限。

运维清单

项建议
FE 数量奇数（3 起步）；1 个仅适合测试，无高可用
Tablet 副本生产 3 副本；监控副本缺失/落后

故障恢复BE 下线后尽快补齐，避免副本长期不足
元数据备份定期备份 FE 元数据，灾难恢复的最后防线
为什么 Tablet 是副本管理的基本单位而不是整表？

整表做副本粒度太粗：一张大表只能在少数节点间复制，无法在集群内均衡，单表过大也会让单 BE 撑不住。切成 Tablet 后，成千上万个小分片可以灵活分布到任意 BE、独立修复与均衡，扩缩容和故障恢复都能"小步快跑"，不会牵动整表。

深度补充：Doris / StarRocks 副本与高可用参数

第一层 · 概念与判定 两者都是 MPP 分析库，表属性里设副本数（replication_num）决定容错与读扩展。判定：建表时按重要性与集群规模选 2~3 副本。

项建议值含义
replication_num3（默认）/ 2（小集群）每 Tablet 副本数
副本均衡自动按磁盘容量节点故障后补副本
FE 角色1 Leader + 多 FollowerBDB 选主
BE 心跳默认 5s 超时判定节点存活

第三层 · 排障与边界

  • 副本数越多写延迟越高（每次写要同步多副本），不是越多越好。
  • 节点盘满会触发副本迁移风暴，需设磁盘水位告警。
  • FE Follower 数应为奇数（3/5）以满足多数派选主。
  • 误把高可用当备份：副本防节点故障，不防误删，仍需定期备份。
第四层 · 原理与取舍

多副本用“空间与写延迟”换可用性与读吞吐，靠 Quorum/多数派保证一致性。FE 用 BDB JE 做元数据强一致选主，BE 存数据副本并定期均衡。权衡是“副本数 vs 写入成本与磁盘占用”，常见 3 副本在“允许坏 1 节点仍可写”与“成本”之间取平衡；关键表可临时升副本，冷表降副本省空间。

FAQ：副本能当备份用吗？

不能。副本防“节点/盘故障”导致的数据不可用，但不防“误删表/误更新”这类逻辑错误，副本之间会同步这些错误。真正的数据安全仍需定期备份（export/snapshot）并异地保留。

常见误区与延伸

  • 误区一：副本越多越安全。副本提升可用性但每次写入要同步多副本，写延迟与磁盘占用线性上升。
  • 误区二：副本等于备份。副本防节点故障，不防误删/误更新，仍需定期备份并异地保留。
  • 延伸：FE 用 BDB JE 做元数据强一致选主，奇数个（3/5）才能形成多数派，2/4 个会脑裂风险。
  • 延伸：BE 的 Tablet 均衡按磁盘容量自动调度，盘满会触发迁移风暴，需水位告警前置。

一句话总结：副本用空间与写延迟换可用性与读扩展，常见 3 副本在“坏 1 节点仍可写”与“成本”间取平衡，关键表升副本、冷表降副本。

决策速记

  • 副本数：常见 3 副本平衡可用与写成本，冷表可降。
  • FE 数：奇数个（3/5）满足多数派选主，别用 2/4。
  • 副本非备份：仍要定期备份防误删/误更新。
  • 磁盘水位：盘满触发迁移风暴，需告警前置。

一句话：副本用空间与写延迟换可用与读扩展，3 副本是常用平衡点。

横向对比与追问

  • 与 ClickHouse 比：CK 用 ReplicatedMergeTree + Keeper 做副本，Doris 用 BE Tablet 均衡，二者都靠元数据服务。
  • 与 TiDB 比：TiDB 副本在 TiKV 层（Raft），Doris 在 BE 层，副本协议与粒度不同。
  • 追问：为什么 FE 要奇数？BDB 选主需多数派，偶数个会在平票时无法决出。
  • 追问：副本数=1 会怎样？单点故障即不可用，且无法做副本均衡与故障补副本。

小结：副本用空间换可用，3 副本是“坏 1 仍可写”与成本的常用平衡。

先记三件事

  • 第一件：副本用空间与写延迟换可用，常见 3 副本平衡成本。
  • 第二件：FE 要奇数个以满足多数派选主，别用 2 或 4。
  • 第三件：副本不是备份，误删仍需定期备份。

高可用落地速记

  • 副本数：生产默认 3 副本（Tablet 三备份），单 BE 宕机 FE 自动切换且数据不丢；1 副本仅用于测试，宕机即不可用。
  • FE 角色：3 Follower 选主或 1 Follower 加 N Observer；Observer 不投票只承接读，扩读流量优先加 Observer。
  • 巡检清单：看 BE 心跳是否超时、副本补齐进度（Inconsistent 数）、磁盘剩余是否够再触发补副本。
