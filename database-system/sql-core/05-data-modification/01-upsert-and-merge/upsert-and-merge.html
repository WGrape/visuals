①为什么不能先查后写

「存在就更新，不存在就插入」的朴素写法是 SELECT 判断再决定 INSERT/UPDATE。 它在并发下必然出错：两个请求同时查到「不存在」，然后都去 INSERT，一个成功一个唯一键冲突。

UPSERT 把「判断 + 写入」合并成一条原子语句
唯一索引是 UPSERT 的前提。没有唯一键，数据库无从判断什么叫「已存在」， 所谓 UPSERT 就退化成无条件插入。先确保冲突列上有 PRIMARY KEY 或 UNIQUE。

②三种语法的语义差异

数据库语法冲突判据特点
MySQLINSERT ... ON DUPLICATE KEY UPDATE任意唯一键冲突可用 VALUES(col) 引用待插入值
PostgreSQL / SQLiteINSERT ... ON CONFLICT (col) DO UPDATE指定列/约束可加 WHERE 条件成为条件更新；DO NOTHING 即忽略
SQL 标准 / Oracle / SQL ServerMERGE INTO ... WHEN MATCHEDON 条件表达力最强（可同时处理删除），语法最冗长
-- MySQL
INSERT INTO daily_stat (dt, biz, cnt) VALUES ('2026-10-18', 'order', 1)
ON DUPLICATE KEY UPDATE cnt = cnt + VALUES(cnt);

-- PostgreSQL
INSERT INTO daily_stat (dt, biz, cnt) VALUES ('2026-10-18', 'order', 1)
ON CONFLICT (dt, biz) DO UPDATE SET cnt = daily_stat.cnt + EXCLUDED.cnt;

-- SQL 标准 MERGE
MERGE INTO daily_stat t
USING (SELECT DATE '2026-10-18' dt, 'order' biz, 1 cnt) s
ON (t.dt = s.dt AND t.biz = s.biz)
WHEN MATCHED     THEN UPDATE SET t.cnt = t.cnt + s.cnt
WHEN NOT MATCHED THEN INSERT (dt, biz, cnt) VALUES (s.dt, s.biz, s.cnt);
语义细节差异必须实测： ① MySQL 的 ON DUPLICATE KEY 在任意唯一键冲突时触发（可能是你没想到的那个索引）； PG 的 ON CONFLICT 必须指定列或约束名，更精确。 ② 自增 ID 的消耗：MySQL 的 UPSERT 冲突时仍可能消耗一个自增值，导致 ID 空洞。 ③ 影响行数各库含义不同（MySQL 插入=1、更新=2、未变=0）。

③并发、死锁与幂等

  1. UPSERT 不是无锁的。它要在唯一索引上加锁判断冲突，高并发对同一键的 UPSERT 会排队， 若一个事务里 UPSERT 多个键且顺序不一致，就会死锁。批量时按同一顺序（如主键升序）排序后执行。
  2. 先删后插的写法更危险。DELETE + INSERT 顺序做幂等会产生 gap lock 与更多 undo， 且中间态会让其他事务读到「不存在」。优先用 UPSERT。
  3. 幂等设计的核心是业务唯一键。用「订单号 + 业务类型」这类天然唯一键作冲突判据， 而不是依赖数据库自增 ID。
  4. 批量 UPSERT 与单条 UPSERT 的锁范围不同。多行 VALUES 的 UPSERT 可能扩大锁范围， 大批量时建议分批（如每批 500~1000 行）。
Q：ON CONFLICT DO NOTHING 值得用吗？
A：值得，它是实现「不存在才插入」幂等的最简写法，比 INSERT IGNORE 更精确 （INSERT IGNORE 会吞掉所有错误，包括非空约束违反、类型转换失败，排查时非常痛苦）。 但要注意：DO NOTHING 时如果你想拿到已有行的 ID，需要再查一次或用 RETURNING 配合 CTE。
Q：怎么拿到 UPSERT 后的主键？
A：PostgreSQL 用 RETURNING id（UPDATE 分支也能返回）； MySQL 用 LAST_INSERT_ID()，但冲突更新分支下它不可靠， 常见做法是 ON DUPLICATE KEY UPDATE id = LAST_INSERT_ID(id) 显式把 ID 写回去再取。

④典型应用场景

计数与统计累加

日活、库存扣减、点赞数。把「多行明细」变成「一行聚合」， 用 cnt = cnt + 1 原子累加，避免读写竞态。

幂等写入

消息队列重复消费、接口重试。以消息 ID 或业务单号作唯一键， 重复投递时 DO NOTHING 或 DO UPDATE 为幂等更新。

缓存表 / 物化视图刷新

按主键覆盖写入最新快照，无需关心是否已存在。

配置与开关表

以 (tenant, key) 唯一，写入即覆盖。比「先查再插」少一次往返。

不适合用 UPSERT 的场景：需要记录历史变更（应写流水表而非覆盖）、 更新逻辑依赖旧值做复杂判断（应在事务里显式 SELECT ... FOR UPDATE）、 以及大批量初始化（用 COPY/LOAD DATA 更快）。

语法对比

-- MySQL
INSERT INTO users (id, name, login_count)
VALUES (1, 'Alice', 1)
ON DUPLICATE KEY UPDATE
  name = VALUES(name),              -- VALUES() 取插入时提供的值
  login_count = login_count + 1;    -- 相对更新

-- PostgreSQL（更精确：可指定是哪个约束冲突）
INSERT INTO users (id, name, login_count)
VALUES (1, 'Alice', 1)
ON CONFLICT (id) DO UPDATE          -- 明确指定冲突目标（唯一列或约束名）
SET name = EXCLUDED.name,           -- EXCLUDED 引用「想插入的那行」
    login_count = users.login_count + 1
WHERE users.name IS DISTINCT FROM EXCLUDED.name;   -- <strong>可加条件</strong>

-- PG 的 DO NOTHING（存在则跳过）
INSERT INTO users (id, name) VALUES (1, 'Alice')
ON CONFLICT (id) DO NOTHING;

-- MySQL 的等价写法
INSERT IGNORE INTO users (id, name) VALUES (1, 'Alice');

PG 的 ON CONFLICT (col) 比 MySQL 更安全：它能精确指定「是哪个唯一约束冲突时才更新」。MySQL 的 ON DUPLICATE KEY 会在任何一个唯一键冲突时触发，若表上有多个唯一索引，可能不是你想要的行为。

陷阱：影响行数与非确定性

问题说明应对
影响行数语义MySQL：插入=1，更新=2，无变化=0判断结果别只看行数
多唯一键MySQL 任一冲突即触发，顺序不确定避免多唯一键，或改用 PG
并发插入同一新键可能死锁或报错重试
自增 ID 跳跃MySQL 的 InnoDB 会预分配 ID不要依赖自增连续
触发器更新路径触发 UPDATE 触发器注意逻辑差异

影响行数

# MySQL 影响行数的三种值（最容易踩坑）
#   1  → 插入了新行
#   2  → 更新了已存在的行
#   0  → 行存在但<strong>SET 后值没变</strong>（未实际更新）
#
# 所以不能写：
#   if affected_rows == 1: print('新增')
# 正确判断应基于业务逻辑或先 SELECT

# 自增 ID 跳跃的原因：InnoDB 在 INSERT 时先分配自增 ID，
#   若 ON DUPLICATE KEY 走了更新路径，这个 ID 就<strong>被丢弃了</strong>
#   所以连续 upsert 会让 auto_increment 值远大于实际行数
# 这是<strong>正常现象</strong>，不要当成 bug，也不要依赖 ID 连续

并发安全：UPSERT 本身是原子的（依赖唯一索引），但两个事务同时插入同一个不存在的键时，可能一个成功一个报死锁或唯一键冲突。应用必须有重试——这是使用 UPSERT 的必备配套。

批量 UPSERT 与性能

批量 upsert

-- 批量 upsert（比逐条快 10 倍以上）
INSERT INTO daily_stats (dt, user_id, pv, uv)
VALUES
  ('2026-10-22', 1, 10, 5),
  ('2026-10-22', 2, 20, 8),
  ('2026-10-22', 3, 5,  3)
ON DUPLICATE KEY UPDATE
  pv = pv + VALUES(pv),
  uv = uv + VALUES(uv);

-- 注意：批量时 VALUES() 引用的是<strong>对应行</strong>的值

-- 性能要点：
#   1) 唯一索引是前提（没有唯一键则退化成纯插入）
#   2) 单批 500~2000 行（太大锁等待久，太小往返多）
#   3) 批量时务必按<strong>主键顺序</strong>排列，减少死锁概率
#   4) MySQL 8.0.20+ 推荐用新写法（VALUES() 已废弃）：
INSERT INTO t (id, v) VALUES (1, 10) AS new
ON DUPLICATE KEY UPDATE v = t.v + new.v;
场景推荐方案理由
计数累加UPSERT + 相对更新避免先查后写的竞态
幂等写入UPSERT + 幂等键重复投递不产生重复数据
全量覆盖REPLACE INTO（MySQL）会删旧行再插，注意自增 ID 变化
大批量导入LOAD DATA 或临时表 + JOIN比逐条 upsert 快得多

REPLACE INTO 的危险：它是先 DELETE 再 INSERT，不是 UPDATE。后果：① 自增 ID 会变；② 未指定的列被重置为默认值（数据丢失！）；③ 触发 DELETE 触发器。绝大多数场景应该用 ON DUPLICATE KEY UPDATE。

自检 Q&A

Q：UPSERT 能保证幂等吗？

A：它保证了数据库层面的幂等（同一主键不会重复插入），但业务幂等还需要幂等号。典型场景：消息队列重复投递同一条「创建订单」消息，若用订单号做唯一键 upsert，第二次会被当作更新——可能覆盖掉期间的其他变更。正确做法是单独的幂等表（记录已处理的 message_id），先判重再处理。UPSERT 解决的是「重复插入」，不是「重复执行业务逻辑」。

Q：为什么我的 UPSERT 很慢？

A：三个常见原因——① 没有唯一索引：退化成纯 INSERT（甚至更慢，因为要判重）；② 逐条执行：每条一次往返，应批量（500~2000 行/批）；③ 更新的列上有索引：每次更新都要维护索引，索引越多越慢。另外 MySQL 的 ON DUPLICATE KEY 在高并发下会有间隙锁竞争，死锁较多——按主键顺序批量能显著缓解。

Q：并发下 UPSERT 报死锁怎么办？

A：这是正常的，必须重试。成因是两个事务以不同顺序插入/更新相同的键区间，形成循环等待。缓解手段：① 批量时按主键排序（让所有事务以相同顺序加锁，最重要的优化）；② 减小单批大小；③ 降低隔离级别到 READ COMMITTED（减少间隙锁）；④ 应用侧捕获死锁错误（MySQL 1213 / PG 40P01）并重试——这是必备的，不要指望完全避免。

Q：MERGE 和 INSERT ON CONFLICT 怎么选？

A：在 PostgreSQL 上用 ON CONFLICT，别用 MERGE（PG 15 才引入 MERGE，且 ON CONFLICT 更成熟、性能更好）。在 SQL Server/Oracle 上只能用 MERGE，但它有已知的 bug 历史（尤其早期版本），使用时要注意：① 用 HOLDLOCK 提示避免竞态；② 避免在 MERGE 里做复杂逻辑；③ 已知问题包括错误的结果与索引损坏（老版本）。能用 INSERT/UPDATE 分开写清楚的，就不必用 MERGE。
