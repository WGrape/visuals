TiDB 架构与原理

TiDB / TiKV / PD / TiFlash 四大组件如何拼出一个"像 MySQL 一样的分布式数据库"

TiDBTiKVPDRaftPercolatorHTAP
① 整体架构 ② TiKV 存储 ③ PD 调度 ④ 分布式事务 ⑤ HTAP ⑥ 常见坑
一句话总结：TiDB 的设计可以概括为「计算与存储分离 + 存储层用 Raft 保证一致 + 用 TSO 授时做全局 MVCC」。 TiDB 层无状态负责 SQL，TiKV 层负责分布式 KV 存储，PD 负责元数据与调度，TiFlash 负责列存分析。

01整体架构

图 1：TiDB 四大组件与数据流向

🧠 TiDB Server

无状态的 SQL 层。负责协议兼容、解析、优化、执行下推。 不存数据，可以随意扩缩容，前面挂 LVS/Nginx 即可。

💾 TiKV Server

分布式 KV 存储引擎（Rust 编写）。数据按 Region 切分， 每个 Region 一个 Raft Group 保证多副本一致。底层用 RocksDB。

📡 PD Server

Placement Driver，集群大脑。管理 Region 位置元数据、 发起调度（分裂/迁移/均衡）、提供 TSO 全局授时。

📊 TiFlash

列存副本，以 Raft Learner 身份异步复制 TiKV 的数据， 只参与复制不参与投票。用于 AP 查询，与 TP 物理隔离。

02TiKV：Region 与 Raft

TiKV 把整个 key 空间按字节序 Range 切成一段段 Region（默认 96 MB）， 每个 Region 是一个独立的 Raft Group。

图 2：Region 是数据分片与 Raft 复制的基本单位

自动分裂与合并

  • Region 超过 96 MB 自动分裂成两个 → 无需人工规划分片。
  • Region 太小或数据删除过多会自动合并，避免元数据膨胀。
  • 分裂是元数据操作（只改 Range 边界），不搬数据，极快。
写热点问题：自增主键意味着新数据 key 单调递增， 所有写入都落在最后一个 Region 的同一台机器上——形成写热点，扩容也没用。
解法：① 用 SHARD_ROW_ID_BITS 打散行 ID； ② 用 AUTO_RANDOM 代替 AUTO_INCREMENT； ③ 主键用 UUID/雪花 ID。这是 TiDB 上最常见的性能问题，面试高频。

03PD：调度与授时

🗺️ 元数据管理

记录每个 Region 的 Range、Leader 位置、副本分布。 TiDB 层先问 PD 拿路由，再直连对应 TiKV。

⚖️ 调度

监控各节点负载，自动发起 Leader 均衡（分散读写压力） 与 Region 均衡（分散存储压力）。扩容后自动搬迁数据。

🕐 TSO 全局授时

提供单调递增的全局时间戳。这是实现 全局一致性快照读与分布式事务定序的基础—— TiDB 能支持「跨节点的一致性读」，靠的就是它。

PD 本身也用 Raft 保证高可用，通常部署 3 个节点。

04分布式事务：Percolator 模型

TiDB 的事务实现源自 Google Percolator：乐观锁 + 两阶段提交 + 全局时间戳。

图 3：Percolator 用 primary key 的单点状态代替传统协调者的事务日志

三种隔离级别支持

隔离级别TiDB 支持说明
Repeatable Read✅默认，快照隔离（SI），无幻读
Read Committed✅（5.0+）每条语句取新快照
Serializable❌ 不支持TiDB 的 SI 不等于可串行化

乐观锁 vs 悲观锁

TiDB 3.0 之前只有乐观锁——事务提交时才检测冲突，冲突就整体重试。 这在热点行竞争下表现很差。3.0.8 之后引入悲观锁（默认行为）， 在 SELECT FOR UPDATE 和 DML 时就上锁，贴合 MySQL 的使用习惯。

Q：TiDB 完全兼容 MySQL 吗？
A：高度兼容但不是 100%。常用 SQL、协议、客户端驱动都兼容，但仍有差异： 不支持 Serializable 隔离级别、存储过程/触发器/外键支持有限、 自增 ID 行为不同（不保证连续）、部分函数与语法有差异。 迁移前务必用官方工具做兼容性评估。
Q：TiDB 和 MySQL 分库分表怎么选？
A：如果业务已经能很好地按分片键拆、跨片查询很少、团队有中间件运维经验—— 分库分表成本更低、延迟也更低。如果需要全局一致性、弹性扩缩容、不想改业务代码—— 选 TiDB。核心判断是业务的分布式复杂度能否被分片键约束住。
