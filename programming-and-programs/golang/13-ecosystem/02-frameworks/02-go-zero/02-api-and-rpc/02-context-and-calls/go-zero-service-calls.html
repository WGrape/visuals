go-zero 里，怎么调「别人的服务」

内部服务（自己家的 RPC）和外部服务（第三方 HTTP 接口）调用方式不同。这篇讲清规范、配置、svc 注入，以及两端各自的示例代码。

总览 内部服务 zrpc 外部服务 httpc 配置与注入 内外对比 易踩坑
先看全景

一句话区分：内部走 zrpc，外部走 httpc

本课比较内部 zrpc 与第三方 HTTP 的接入方式、配置和 ServiceContext 复用；RPC 契约、生成代码与故障处理的细节见go-zero RPC 通信详解。

核心规范：无论内部外部，客户端都在 main → svc.ServiceContext 里建一次，logic 只管「调」，不负责「连」。 这样连接数可控、配置外置、测试可替换 —— 和「不用全局变量」那篇是一回事。

内部服务 · zrpc

调自家 RPC 服务（推荐 zrpc / gRPC）

如果你调用的是另一个 go-zero 服务，双方用 proto 定义契约，goctl 生成客户端，注入 svc 后直接调。

① 定义 proto（被调用方 user 服务）

// user.proto
syntax = "proto3";
package user;

service User {
  rpc GetUser (GetUserReq) returns (GetUserResp);
}

message GetUserReq { int64 id = 1; }
message GetUserResp {
  int64  id    = 1;
  string name  = 2;
}

② 生成 RPC 代码（含客户端）

goctl rpc protoc user.proto --go_out=. --go-grpc_out=. --zrpc_out=. \
  --style gozero     # 生成 user.pb.go + 服务端 + 客户端

③ 在 svc 里注入 RPC 客户端

// internal/svc/servicecontext.go
import user "yourorg/app/user/rpc/user"  // 生成的客户端包

type ServiceContext struct {
    Config  config.Config
    UserRpc user.User            // ✅ RPC 客户端，注入进来
}

func NewServiceContext(c config.Config) *ServiceContext {
    return &ServiceContext{
        Config:  c,
        UserRpc: user.NewUser(c.UserRpc), // 连接只建一次
    }
}

④ 在 logic 里调用（业务侧）

// internal/logic/ordercreate.go
func (l *OrderCreateLogic) OrderCreate(req *types.OrderCreateReq) (*types.OrderCreateResp, error) {
    // 直接通过 svcCtx 调内部 user 服务，无需自己建连接
    u, err := l.svcCtx.UserRpc.GetUser(l.ctx, &user.GetUserReq{Id: req.UserId})
    if err != nil {
        return nil, err
    }
    // ...用 u.Name 继续写下单逻辑
    return &types.OrderCreateResp{Ok: true}, nil
}
📌 内部调用之所以用 gRPC：性能高、强类型契约、自带超时/重试/熔断/服务发现（etcd）。go-zero 的 zrpc 把这些开箱即用，省去你手搓 HTTP 客户端。
外部服务 · httpc

调第三方 HTTP 接口（推荐 httpc）

调外部系统（支付、短信、地图、天气等）走 HTTP。go-zero 自带 rest/httpc：类型化请求、内置超时、熔断、还能走服务发现。

① 在 svc 里建 httpc 客户端（同样注入）

// internal/svc/servicecontext.go
import "github.com/zeromicro/go-zero/rest/httpc"

type ServiceContext struct {
    Config  config.Config
    PayHttp httpc.Service          // ✅ 外部支付网关客户端
}

func NewServiceContext(c config.Config) *ServiceContext {
    return &ServiceContext{
        Config:  c,
        PayHttp: httpc.NewService(c.PayHttp), // 按配置建客户端
    }
}

② 在 logic 里发起调用

// internal/logic/pay.go
var payResp PayQueryResp
err := l.svcCtx.PayHttp.Do(l.ctx, http.MethodPost,
    "/v1/pay/query", req, &payResp)   // 自动超时+熔断
if err != nil {
    return nil, err
}

最简形式：没有 Target 时直接 Do

// 只想简单发个请求、不配服务发现
var resp WeatherResp
err := httpc.Do(ctx, http.DefaultClient, http.MethodGet,
    "https://api.weather.com/now?city=bj", nil, &resp)
📌 为什么不直接用 net/http？可以用，但 httpc 帮你统一了超时、熔断（breaker）、重试和服务发现，和 go-zero 的服务治理理念一致，也更容易被 svc 统一注入管理。
配置与注入

配置都外置到 yaml，连接都在 main 建

内部 zrpc 和外部 httpc 的配置同样写在 etc/xxx.yaml，由 config.go 映射，main 启动时注入 svc。

config.go（结构）
type Config struct {
    rest.RestConf
    UserRpc zrpc.RpcClientConf  // 内部
    PayHttp httpc.ServiceConf   // 外部
}
etc/xxx.yaml（配置）
UserRpc:
  Etcd:
    Hosts: [127.0.0.1:2379]
    Key:   user.rpc
PayHttp:
  Target: "https://pay.example.com"
  Timeout: 3s

这套「配置外置 + main 建连接 + svc 注入 + logic 调用」的流程，正是 go-zero 替代全局变量、统一管理外部依赖的标准做法（详见「全局变量与 svc」篇）。

避坑

三个最容易犯的错

❌ 不要在 logic 里现建客户端

每次请求 new 一个连接成本极高且无法复用。客户端必须在 svc 建一次，logic 复用。

❌ 不要把地址/密钥硬编码在代码里

一律走 etc/xxx.yaml + config.go，方便多环境切换和保密。

❌ 不要用全局变量存客户端

全局 client 难测试、难替换、难感知生命周期。交给 svc 注入，与「不用全局变量」规范一致。

内部 RPC 与第三方 HTTP 的调用方式

场景用什么关键点
调用本项目的 RPC 服务zrpc.MustNewClient(c.OrderRpc) + 生成的 client客户端在 ServiceContext 里建一次，全局复用
调用第三方 HTTPrest 客户端或直接用 net/http必须设超时；复用 http.Client 而不是每次新建
调用其他语言的 RPCgRPC 原生客户端（跨语言天然支持）proto 契约要统一维护
需要服务发现zrpc 内置（etcd / k8s endpoints）配置文件里指定 Etcd.Hosts 或开启 k8s 模式
需要负载均衡zrpc 默认带 P2C（Power of Two Choices）比轮询更能应对慢节点

配置与代码

// config 里的 RPC 配置（直连模式）
OrderRpc:
  Endpoints: ["127.0.0.1:8080", "127.0.0.1:8081"]   # 多地址自动负载均衡
  Timeout: 800   # 毫秒

// etcd 服务发现模式
OrderRpc:
  Etcd:
    Hosts: ["127.0.0.1:2379"]
    Key: order.rpc

// ServiceContext 里建客户端（只建一次！）
orderclient.NewOrder(zrpc.MustNewClient(c.OrderRpc))

// logic 里调用
resp, err := l.svcCtx.OrderRpc.CreateOrder(l.ctx, &orderpb.CreateReq{Uid: uid})

// 调第三方 HTTP：务必复用 client 并设超时
var cli = resty.New().SetTimeout(3 * time.Second)   // 全局复用
resp, err := cli.R().SetContext(ctx).Get("https://api.example.com/x")

// ❌ 反例：每次请求都 http.Client{} + 30s 默认无超时
//   -> 连接不复用（TIME_WAIT 堆积）+ 下游挂了会把协程全卡死
  • 超时必须设，且层层递减：网关 3s → 业务 1s → 单 RPC 800ms → 单次 DB 300ms。
  • 重试要谨慎：只对幂等的读操作重试；写操作重试可能造成重复下单。go-zero 的 zrpc.Retry 要显式开启，别默认打开。
  • 重试会放大流量：下游已经过载时重试会雪上加霜，要有熔断配合（go-zero 的 breaker 默认在 zrpc 上开启）。
  • 客户端是长连接：放在 ServiceContext 里复用，不要在 logic 里每次 new。
  • 错误不要吞掉：RPC 返回的错误要包装成业务错误再往上抛，保留错误链（%w）。

排障清单

  • 连不上：先看配置里的 Endpoints/Etcd Key 是否正确，再 telnet 端口，最后看服务是否注册成功。
  • 超时：先量下游真实耗时（看链路或下游监控），再判断是超时设太短还是下游真的慢。
  • 大量 connection refused：可能是下游实例已下线但服务发现没摘掉（etcd TTL / k8s endpoints 延迟）。
  • context deadline exceeded：上游预算用完；检查超时是否层层递减，别让下游超时大于上游。
  • 熔断打开：go-zero 的 breaker 在错误率达到阈值后会短路，属于保护行为；此时应该修下游而不是关掉熔断。
go-zero 的 RPC 默认有熔断吗？

有。zrpc 客户端默认启用 breaker（滑动窗口统计错误率），错误率超阈值后会直接返回而不发请求，给下游恢复的时间。

直连和 etcd 模式怎么选？

本地开发 / 固定地址用直连；生产多实例、需要弹性扩缩容时用 etcd 或 K8s 服务发现。

调用第三方 HTTP 要不要走 zrpc？

不用，zrpc 是给内部 gRPC 用的。第三方 HTTP 用 resty / net/http，重点是超时、重试与连接池三项要配好。
