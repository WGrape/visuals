SSA 中间表示

每个变量只赋值一次

SSA 形式下每个变量只被定义一次，极大方便数据流分析（如常量传播、死代码消除）。Go 的编译器大量基于此。

// 普通: x = 1; x = 2
// SSA:  x1 = 1; x2 = 2   (x 被拆成不同版本)
中端优化

函数内联是重头戏

包括逃逸分析（配合栈分配）、函数内联、边界检查消除、常量折叠等。内联能把小函数展开、消除调用开销。

内联有阈值控制；太激进会膨胀代码。go build -gcflags=-m 能看哪些函数被内联、哪些逃逸。

SSA：编译器里的通用中间语言

SSA（Static Single Assignment，静态单赋值）要求每个变量只被赋值一次。这个约束让数据流变得极其清晰，绝大多数优化都建立在它之上。

// 源代码 x := 1 if cond { x = 2 } return x + 1 // SSA 形式（示意） v1 = 1 if cond → b2 else b3 b2: v2 = 2 ; jump b4 b3: v3 = 1 ; jump b4 b4: v4 = φ(v2, v3) // φ 节点按来源块选择值 v5 = v4 + 1 return v5
单赋值每个值只定义一次，定义点即使用点。
基本块一串顺序执行的指令，块间由跳转连接。
φ 节点在汇合点按来源路径选择值，解决分支合并。
多阶段从 generic 逐步降级到架构相关，最后出机器码。

为什么这对写业务的人也有用：SSA 让「常量折叠」「死代码消除」「公共子表达式消除」变得容易。你写的朴素代码能被自动优化，前提是别让信息在到达编译器前就丢失（例如过早装箱成 interface）。

寄存器分配是后端最关键的一步：变量多于寄存器时，多出来的要溢出（spill）到栈上，每次访问多一次内存读写。这也是「局部变量太多会稍微变慢」的根源。

Go 汇编为什么看起来不一样

Plan 9 风格

Go 使用 Plan 9 汇编语法，与常见的 AT&T / Intel 语法都不同。

  • 操作数顺序与 AT&T 相反，更像 Intel
  • 寄存器名不带 % 前缀
  • 指令后缀含义不同（Q=64 位，L=32 位）
  • 引入 SB/SP/FP 等伪寄存器便于表达偏移

伪寄存器

这是最容易困惑的地方：SP 在 Go 汇编里不是硬件栈指针。

  • FP 用于访问参数（symbol+offset(FP)）
  • SP 是伪栈指针，指向当前帧局部区
  • 硬件栈指针写作 SP 时需加前缀区分
  • 这让编译器能在不固定真实栈布局的情况下重排代码

什么时候需要写汇编

  • 标准库中需要极致性能的原子、加解密、数学原语
  • 需要访问 Go 没有暴露的 CPU 指令
  • 启动阶段与运行时自身
  • 业务代码几乎不需要，可读性与可移植性代价过高

深入自检

SSA 的 φ 节点是什么，为什么必须有？

当控制流从多个分支汇合时，同一个源变量在不同路径上有不同值。SSA 要求单赋值，因此引入 φ 节点在汇合点按来源块选择正确的值。它是保持 SSA 形式与表达分支语义的桥梁。

为什么局部变量多了性能会下降？

寄存器数量有限，寄存器分配器放不下的变量会溢出到栈。栈访问比寄存器慢一个数量级，且增加内存流量。通常影响很小，但在紧密循环里能被测量出来。

看汇编能解决什么问题？

回答「编译器到底做了什么」：这个函数有没有被内联、越界检查是否被消除、有没有意外分配、热循环里是不是有多余的内存读写。它是性能调优的最后一层证据。

为什么业务代码不建议写汇编？

代价太高：失去可移植性、失去编译器优化、调试困难、GC 需要手写栈映射信息。标准库写汇编是因为收益覆盖成本，业务场景通常有更高层的优化手段。

Go 汇编的 SP 到底怎么理解？

Go 汇编里的 SP 是伪寄存器，指向当前函数帧的局部区起点，便于用固定偏移表达变量；硬件栈指针另有表示。这个设计让编译器可以自由调整真实栈布局而不必重写汇编。
