一句话总结：InfluxDB 是最流行的推模式（push）通用时序数据库。 它的三件套是：Line Protocol 行协议写入、 TSM（Time-Structured Merge Tree） 存储引擎、 Retention Policy + Continuous Query 做数据生命周期管理。

01数据模型：measurement / tag / field

这是理解 InfluxDB 的第一步，也常与 Prometheus 的 metric/label 混淆。

图 1：measurement + tags 唯一确定一条 series，fields 是这条 series 上的采样值
概念InfluxDB对应的关系型数据库概念
measurementcpu, http_requests表（table）
tag key/valuehost="web1", region="us"带索引的列（只存字符串）
field key/valueusage=0.64, count=42不带索引的列（数值/字符串/布尔）
point一行完整数据行（row）
seriesmeasurement + tag set无直接对应
retention policy数据保留多久无（相当于自动 TTL）

02Line Protocol 写入协议

纯文本行协议，简单到可以直接用 curl 或 nc 写入：

# 语法：measurement,tag_set field_set timestamp
cpu,host=web1,region=us-west usage_user=23.4,usage_sys=5.6 1700000000000000000

# 一次写多个 point（换行分隔，批量写入效率高）
cpu,host=web1 usage=23.4 1700000000000000000
cpu,host=web2 usage=45.1 1700000000000000001
mem,host=web1 used_percent=67.2 1700000000000000000
# HTTP API 写入
curl -i -XPOST 'http://localhost:8086/write?db=mydb' \
  --data-binary 'cpu,host=web1 usage=23.4'
为什么用行协议？时序数据的写入量极大，JSON 的解析开销不可接受。 行协议是最简文本格式：一次批量写几千行，服务端顺序解析， 配合 TSM 的顺序写，吞吐可达每秒数十万点。
注意：行协议里 tag 与 field 的顺序会影响解析（必须 tag 在前、field 在后）， 且类型一旦确定不能改（同一 field 先写整数再写浮点会报错）。 这是生产中最常见的写入失败原因。

03TSM 存储引擎

TSM（Time-Structured Merge Tree）是 InfluxDB 自研的列式存储引擎， 针对时序做了专门优化，与通用的 LSM-Tree（如 RocksDB）有显著区别。

图 2：TSM 引擎——WAL + Cache → TSM File → 后台合并；过期按 shard 整体删除

Shard：按时间切分的存储单元

InfluxDB 按 Retention Policy 里的 shard group duration（默认 7 天或 1 天） 把数据切成一个个 shard。查询带时间范围时能直接跳过无关 shard； 过期时整个 shard 目录删掉——这是它比 MySQL 的 DELETE 高效得多的原因。

04查询语言：InfluxQL 与 Flux

语言风格状态示例
InfluxQL类 SQL，易上手1.x 主力，2.x 仍支持 SELECT mean(usage) FROM cpu WHERE host='web1' AND time > now()-1h GROUP BY time(1m)
Flux函数式管道，能力强2.x 主推 from(bucket:"m") |> range(start:-1h) |> filter(fn:(r)=>r.host=="web1") |> aggregateWindow(every:1m, fn:mean)

Flux 更强大（支持跨 measurement JOIN、多数据源、复杂变换）， 但学习曲线陡；InfluxQL 简单直观但能力有限。2.x 时代两者共存。

-- InfluxQL 常用模式
-- 1. 时间窗口聚合（降采样的核心）
SELECT mean("usage_user") FROM "cpu"
WHERE time > now() - 6h
GROUP BY time(5m), "host"          -- 按 5 分钟窗口、按 host 分组

-- 2. 填充缺失值（避免图表断点）
GROUP BY time(1m) fill(previous)

-- 3. 保留策略查询
SELECT * FROM "autogen"."cpu"       -- 指定 RP

05保留策略与连续查询

⏳ Retention Policy（RP）

定义数据在库里保留多久。到期后整个 shard 删除， 代价极低。可设多个 RP（如 7 天高精度 + 1 年降采样）。

🔄 Continuous Query（CQ）

后台自动、增量执行的聚合查询，把高精度数据降采样写入另一个 measurement/RP，实现分层存储。

-- 创建 30 天保留策略
CREATE RETENTION POLICY "30d" ON "mydb"
  DURATION 30d REPLICATION 1 DEFAULT

-- 创建连续查询：每 5 分钟把 cpu 聚合成 5 分钟精度，写入 cpu_5m
CREATE CONTINUOUS QUERY "cq_cpu_5m" ON "mydb"
BEGIN
  SELECT mean("usage_user") AS "usage_user"
  INTO "30d"."cpu_5m"
  FROM "autogen"."cpu"
  GROUP BY time(5m), "host"
END
这套机制的价值：原始秒级数据只留 7 天（可排查故障）， 降采样后的分钟级数据留 1 年（可看趋势）， 总存储量可能只有全量保留的 1%——这是时序系统能长期运行的关键。

数据模型measurement + tag + fieldmetric + label（无 field 区分）

集群开源版单机，集群是商业版单机为主，靠 Thanos / VictoriaMetrics 扩展

Q：什么时候选 InfluxDB 而不是 Prometheus？
A：① 客户端无法被拉取（如 IoT 设备在 NAT 后、边缘设备）→ 必须推模式； ② 需要存储非数值数据（字符串 field、布尔）或需要 field 概念； ③ 已有 Telegraf 采集生态。 反之，如果是 K8s/微服务监控 + 告警，Prometheus 生态更成熟，优先选它。
Q：InfluxDB 的高可用怎么做？
A：开源版（2.x）仍是单机，高可用要靠双写 + 反向代理或定期备份； 生产级集群需要InfluxDB Enterprise / Cloud 商业版。 这也是很多公司在大规模场景下转向 VictoriaMetrics、TDengine 或 ClickHouse 的原因之一。
