CockroachDB 架构与原理

默认 Serializable 的分布式 SQL，设计受 Google Spanner 启发

CockroachDBSpannerSerializableRaftHLC
① 定位与血统 ② 对等架构 ③ 混合逻辑时钟 ④ 可串行化事务 ⑤ 地理分区 ⑥ 对比与选型
一句话总结：CockroachDB 的设计目标是「打不死的 Postgres」—— 节点可同时承担 SQL 接入与存储职责，支持跨地域部署，并默认提供 Serializable（可串行化）隔离级别。其设计受 Google Spanner 启发，但不是 Spanner 的开源实现。

01定位与血统

特性说明
血统受 Google Spanner 论文启发（但不用 TrueTime 硬件时钟）
协议兼容 PostgreSQL 线协议（不是 MySQL）
一致性默认 Serializable——最高隔离级别
部署原生支持跨地域/跨云多活
语言Go 编写，单二进制部署简单
名字由来蟑螂（Cockroach）——寓意"杀不死"
与 Spanner 的关键差异：Spanner 依赖 Google 数据中心的 原子钟 + GPS（TrueTime）硬件来保证全局时间误差极小。 普通机房没有这种硬件，所以 CockroachDB 改用 HLC（混合逻辑时钟）+ 不确定性区间来近似——这是它最重要的技术创新。

02完全对等的架构

图 1：CockroachDB 没有中心化组件——这是它与 TiDB / OceanBase 最大的架构差异

🔀 Gateway 节点

客户端连到的那个节点叫 Gateway，负责 SQL 解析与路由。 但任何节点都能当 Gateway，挂了换一个连即可。

📦 Range

数据按 key 范围切成 Range（默认 64 MB，比 TiDB 的 Region 小）， 每个 Range 一个 Raft Group，超过阈值自动分裂。

🗺️ 元数据存储

Range 的位置信息也存在 KV 里（两层 meta Range）， 同样是 Raft 多副本。避免了独立的元数据服务。

03混合逻辑时钟 HLC

分布式事务需要全局排序，而物理时钟在跨节点间必然有偏差（时钟漂移）。 CockroachDB 的解法是 HLC（Hybrid Logical Clock，混合逻辑时钟）：

图 2：HLC 用「物理时间取大 + 逻辑计数」在没有原子钟的条件下近似全局时钟
为什么这很重要：有了全局定序，CockroachDB 才能实现 分布式 Serializable——整个集群的事务看起来像按某个顺序串行执行。 这是它能放心用于金融、库存等强一致场景的基础， 也是它相比 TiDB（只支持 SI 快照隔离）最显著的优势。

04事务：Serializable + 无锁

机制说明
隔离级别默认 Serializable；可降级为 Snapshot（性能更好）
并发控制MVCC + 乐观并发，读不加锁，写不阻塞读
提交协议并行提交（Parallel Commits）优化过的 2PC，把 2 次 RTT 降为 1 次
写意向写入先写 Write Intent（带事务标记），提交时转为正式值
冲突处理检测到读写冲突时，后到的事务重启（retry）而非阻塞
不确定性重启读到落在时钟不确定区间的值 → 主动推进时间戳重试
图 3：并行提交把事务提交延迟从 2 RTT 降到 1 RTT

05地理分区：跨地域部署的杀手锏

CockroachDB 可以按行的某个字段值把数据固定在特定地域， 满足数据主权（GDPR）与低延迟访问的需求。

-- 按 region 字段把数据钉在对应地域
ALTER TABLE users
  PARTITION BY LIST (region) (
    PARTITION us_west VALUES IN ('us-west'),
    PARTITION eu      VALUES IN ('europe'),
    PARTITION ap      VALUES IN ('asia')
  );

-- 让欧洲用户的读写只在欧洲节点完成，延迟从 200ms 降到 5ms
ALTER PARTITION europe OF TABLE users
  CONFIGURE ZONE USING
    constraints = '[+region=eu]',
    lease_preferences = '[[+region=eu]]';

🌍 低延迟

把数据的 Raft Lease（租约）放在离用户最近的地域， 读无需跨洲，延迟大幅下降。

⚖️ 合规

用 constraints 强制某国数据不出境， 满足 GDPR 等数据驻留要求。

🛡️ 存活目标

可配置 zone survivability（机房级） 或 region survivability（城市级），按业务等级选择。

Q：CockroachDB 的 Serializable 有什么代价？
A：为了可串行化，事务遇到冲突或时钟不确定性时会自动重启（retry）， 高冲突场景下重试率上升、吞吐下降。应用需要实现重试逻辑。 实践中可用 SELECT FOR UPDATE 提前加锁减少冲突， 或在对一致性要求不高的场景降级到 Snapshot 隔离换取性能。

-- 1) 看集群健康与副本状态（先看这个，再看别的）
SELECT node_id, address, is_live, ranges, leaseholders
FROM crdb_internal.kv_node_status ORDER BY node_id;

-- 2) 看 range 分布是否均衡（不均衡就是热点或容量问题）
SELECT range_id, start_key, end_key, replicas, range_size / 1024 / 1024 AS mb
FROM crdb_internal.ranges ORDER BY range_size DESC LIMIT 20;

-- 3) 看副本不足的 range（有输出说明有副本没补上）
SELECT range_id, replicas FROM crdb_internal.ranges
WHERE array_length(replicas, 1) < 3 LIMIT 20;

-- 4) 改 zone 配置：跨地域部署把副本分布写清楚
ALTER DATABASE app CONFIGURE ZONE USING
  num_replicas = 5,
  constraints = '{+region=us-east: 2, +region=us-west: 2, +region=eu: 1}';

-- 5) 陈旧读：用 5 秒前的快照读，避免跨地域 round-trip
SELECT count(*) FROM orders AS OF SYSTEM TIME '-5s' WHERE status = 'PAID';

-- 6) 会话级参数（排查写冲突时临时用，别长期开）
SET default_transaction_isolation = 'SERIALIZABLE';
SHOW ZONE CONFIGURATION FOR TABLE orders;

跨地域写延迟怎么估：一次写入要等多数派副本确认，耗时约等于一轮跨地域 RTT × 需要确认的副本轮次。同地域 3 副本常在个位数毫秒，跨洲 5 副本轻易到上百毫秒 —— 这是地理分区必须先把数据 locality 设对的原因。

第三层 · CockroachDB 的六个高频故障

  • 节点反复重启 / 自杀：多半是节点间时钟偏移超过 --max-offset（默认 500 ms）。查 NTP 偏移，把 chrony/ntpd 配好再上线。
  • 写冲突报 40001：这不是 bug 而是 Serializable 下的正常重试信号；客户端必须捕获并实现重试，Go 用 crdb.ExecuteTx 之类的封装。
  • 单个 range 特别大且不分裂：单调递增主键（如自增 ID、时间戳前缀）导致写入集中在最后一个 range；改用 UUID 或哈希前缀打散。
  • 跨地域查询慢：数据 locality 没设对，读要跨区取；用 REGIONAL BY ROW 表或 follower reads。
  • 长事务被别的写推走：CRDB 会主动 abort 阻塞别人的事务；把大事务拆小，避免交互式事务里等人。
  • 副本长期不足：节点下线或磁盘满后副本无法补齐；查 crdb_internal.ranges 里 replicas < 3 的行，并看磁盘水位。

排查顺序：节点存活与时钟 → range 均衡与副本数 → 事务重试率 → 慢查询里的 locality。前两项是集群健康，后两项是应用适配。

第四层 · 为什么能 Serializable 又不用锁

Serializable 不是最慢的隔离级别吗，为什么 CRDB 敢默认开？

它用的是乐观并发 + 混合逻辑时钟：事务并行执行，提交时检查读写冲突，冲突则让一方重试（40001）。代价转移到重试率上，冲突少时几乎无成本，冲突多时重试会毁掉吞吐。

HLC（混合逻辑时钟）解决什么问题？

纯物理时钟有偏移，纯逻辑时钟无法做跨节点快照读。HLC 把两者结合：用物理时钟保证接近真实时间，用逻辑部分保证因果序，从而在不依赖原子钟的前提下给出全局有序的时间戳。

地理分区的代价是什么？

把数据按地域绑定后，跨地域访问同一行会变慢，且 locality 变更要重新搬迁数据；所以得先在业务上想清楚「哪些数据只属于哪个地域」，再落到表结构。
