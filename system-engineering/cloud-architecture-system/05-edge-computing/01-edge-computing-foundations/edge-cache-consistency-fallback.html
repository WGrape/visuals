边缘缓存：一致性、回源与故障降级

从一次跨地域读取看清边缘节点的低延迟收益，以及 TTL、失效传播与回源风暴的代价。

把缓存放近用户能省哪段时间

边缘节点位于用户较近的网络位置，可缓存静态资源、可公开的 API 响应或经过正确隔离的个性化结果。命中时可省掉到中心区域的跨地域往返与源站处理；未命中仍要回源。边缘缓存不能让数据天然保持最新：更新发生在中心系统后，各边缘节点可能在 TTL 到期、主动失效或重新验证前继续返回旧副本。因此设计时要先给内容分级，而不是一律设置很长 TTL。

公开图片、版本化 JS 可用长 TTL 加内容哈希；商品价格、库存和授权状态需要更严格的时效与失效规则。带用户身份的响应若错误地以公共 key 缓存，可能发生跨用户数据泄露。缓存键要包含必要的租户、语言、设备或版本维度，同时警惕维度过多导致命中率下降。

逐步推演

分类内容

区分不可变静态资源、可短时陈旧数据和必须实时确认的数据。

设计键与 TTL

选择缓存键、有效期与主动失效机制。

处理未命中

回源、合并请求并保护源站容量。

演练故障

测节点切换、源站不可用、陈旧内容与跨用户隔离。

一次价格更新的时间线

中心数据库把价格从 100 改为 90，边缘 A 的缓存仍有 100，边缘 B 因首次访问回源拿到 90。用户在不同区域看到不同价格，说明边缘缓存提供的是有条件的时效保证。若业务允许 30 秒陈旧，可设置 TTL 并记录最大允许滞后；若结算价格必须准确，最终支付应回到权威服务确认，不应只相信页面缓存。

策略优点风险与前提
固定 TTL简单、减轻回源有效期内可能过期
主动失效更新后较快传播失效事件可能延迟或丢失
条件请求再验证可利用版本与 ETag仍需要回源往返
版本化 URL不可变资源易长期缓存引用版本必须同步更新

回源风暴和边缘故障

热门 key 同时过期，大量边缘请求可能瞬间打到源站。可对同 key 合并回源、加入 TTL 抖动、预热热点，并给源站设置限流。源站短时故障时，边缘可在业务允许范围内提供 stale 内容，但需标明最大陈旧时间；支付、权限等敏感数据通常不能无限期继续使用旧值。边缘节点自身不可用时，要有切换到其他节点或直接回源的路径，并评估额外延迟。

失效传播也要可观测。记录缓存命中率、回源率、对象年龄、失效事件延迟与用户区域。全站命中率很好，不代表关键接口正确：一个价格接口的少量过期响应可能比图片缓存未命中更严重。把性能 SLO 与数据新鲜度 SLO 分开衡量。

设计检查

  1. 按内容分类确定权威数据源、允许陈旧时长和缓存键。
  2. 演练价格更新、授权撤销与版本发布，核对各边缘节点收敛时间。
  3. 压测热门 key 失效和源站故障，观察回源峰值与降级策略。
  4. 为个人数据设计严格隔离，测试不同用户、租户和地区是否出现交叉命中。

练习：商品详情页允许价格显示最多陈旧 30 秒，但下单必须使用实时价格。请指出页面缓存和结算接口各自应该做什么，并说明源站故障时如何提示用户。

一致性目标必须能测量

“最终会更新”不够具体。为每类数据定义更新后 95% 和 99% 边缘节点达到新版本所需时间，以及最长容忍陈旧窗口。主动失效链路若发生丢消息，可由 TTL 作为最终收敛兜底；若 TTL 很长，则必须监控失效覆盖率。对结算和权限撤销，优先让权威服务复核或使用版本校验。缓存架构的成功标准同时包含命中延迟、新鲜度和源站安全，不只是一张命中率曲线。

缓存键和失效事件的联动

假设价格页缓存键只包含商品 ID，实际响应还取决于地区和货币。边缘节点即使命中最新商品版本，也可能给另一地区显示错误币种。缓存键必须覆盖所有会改变响应的维度，但不能把每次请求唯一的追踪 ID 加进去，否则命中率会接近零。主动失效时可按商品 ID 找到相关区域的缓存条目，或使用版本号让旧条目自然失效。每个策略都要测试“更新已提交、失效消息延迟”“边缘节点离线后恢复”“源站短时不可用”三种时序。只有同时约定最大陈旧时间和回源失败行为，才能向产品方解释用户究竟会看到什么。

边缘离线时的写入比读取更复杂：如果允许本地暂存修改，恢复联网后可能与中心数据冲突，需要版本号、合并规则和用户提示。若业务不接受冲突，就应在离线时禁用该写操作。缓存策略不能代替跨地域写入的一致性协议。

验收时按地区抽样访问同一对象，记录响应版本与年龄；只看边缘节点自身的失效日志，无法证明用户实际拿到的是新版本。

自检

高缓存命中率能证明价格一定正确吗？

不能。命中率衡量是否回源，不衡量对象是否满足新鲜度要求。

为什么不能把用户响应仅按 URL 缓存？

URL 相同但用户权限或租户不同，可能让一个用户读到另一个用户的数据。
