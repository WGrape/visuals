观察者模式：状态变化如何通知订阅者

让发布者只负责事件，不直接依赖每个下游行为。

学完能解释什么

  • 认识 Subject、Observer、订阅和通知的职责
  • 区分同步观察者回调与异步消息队列
  • 预防重复订阅、异常传播与忘记取消订阅

逐步看机制

观察者登记回调

Subject 保管订阅集合，并返回可取消订阅的句柄；不需要了解具体 UI 或日志类。

观察者解决什么耦合

订单状态变化时，页面、审计日志和通知模块都可能需要响应。订单对象不应直接持有三个具体实现；Subject 只公布事件，Observer 自行订阅。模式减少编译/结构依赖，但不会自动带来跨进程交付、消息持久化或顺序保证。

可取消订阅的简化实现

class Subject {
  constructor() { this.listeners = new Set(); }
  subscribe(listener) {
    this.listeners.add(listener);
    return () => this.listeners.delete(listener);
  }
  emit(event) {
    for (const listener of [...this.listeners]) listener(event);
  }
}

const changed = new Subject();
const unsubscribe = changed.subscribe(event => console.log(event));
changed.emit({ type: 'order-paid', orderId: 42 });
unsubscribe();

遍历订阅集合的快照可避免通知过程中取消订阅扰乱当前迭代。实际系统还要约定一个回调抛错时是否继续通知其他人，以及是否允许回调再触发同一事件。

三个容易误用的边界

  • 同步不等于可靠投递：进程退出后事件不会被重放；跨服务可靠通知应考虑持久化消息与消费者幂等。
  • 解耦不等于无序：订阅顺序若影响业务正确性，说明事件边界或业务事务需要重新设计。
  • 订阅要有生命周期：重复订阅或忘记取消，会产生重复处理与内存引用。

自检

Observer 与消息队列有什么关键差别？

本例在同一进程和调用链内同步通知，没有持久化、重试或跨服务交付保证；消息队列需要另行处理这些语义。
