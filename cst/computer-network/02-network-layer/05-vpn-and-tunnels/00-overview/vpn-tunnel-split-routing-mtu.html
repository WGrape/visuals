VPN 隧道、全流量与分流：连接后为什么某些网站变慢

沿远程员工访问内网的路径解释加密封装、路由选择、DNS 与有效 MTU。

隧道改变的是路径与封装

VPN 客户端在普通网络之上建立一条到 VPN 网关的受保护通道，把原始 IP 包封入外层包传输。远程员工访问内网 10.30.0.0/16 时，系统路由表把该前缀交给虚拟网卡；VPN 软件加密或封装后从物理网卡发向网关；网关解封装并转发到内网。不同 VPN 技术如 IPsec、WireGuard、TLS VPN 在握手、封装和管理上不同，但都必须解决身份、密钥、路由与回程问题。

“VPN 已连接”只说明隧道控制面可能建立，不能证明内网应用可用。还要看虚拟接口地址、目的路由、网关策略、内网 DNS 与服务器回程。用户打开公网网页失败也可能是 VPN 改了默认路由或 DNS，而不是公网网站坏了。

全隧道与分流

全隧道把默认路由也导向 VPN，访问公网网站先到企业网关再出互联网，便于统一安全控制，但可能增加 RTT 和网关带宽压力。分流只让企业网段经 VPN，普通互联网流量继续走本地出口，通常节省带宽与延迟，却需要明确哪些业务必须经企业策略。配置错误时，内网域名解析出私有地址，但流量没有相应 VPN 路由，就会“能解析、连不上”。

分流不能只按 URL 字符串决定，因为路由实际按 IP 前缀选择；同一域名可能有多个地址，CDN 或 SaaS 地址会变。若企业用域名动态调整隧道路由，需要处理 DNS 缓存、地址变化和冲突网段。用户家庭 LAN 恰好也使用 10.30.0.0/16 时，前缀冲突会让目标走错出口，应规划地址或使用更具体路由与代理策略。

逐步推演

建立隧道

客户端与网关认证并建立加密通道。

选择路由

内网前缀或默认路由指向虚拟网卡。

封装传输

外层包到 VPN 网关，内层包到业务主机。

验证业务

核对 DNS、回程、MTU 与访问权限。

一次封装路径

用户应用向 10.30.4.8:443 发 TCP 数据。内层 IP 包目的仍是 10.30.4.8；外层包的目的则是公网 VPN 网关 198.51.100.9。家庭路由器只知道外层公网路径，企业网关解封装后才看见内层目的并转发。中间网络通常看不到加密隧道里的应用正文，但仍可能看到网关地址、包大小与时间。保护范围依协议配置，不能笼统说 VPN 让所有通信在任何端点都不可见。

网关到内网服务器是否继续加密是另一段链路，服务器本身是否使用 HTTPS 也独立。VPN 保护到网关，不替代应用层身份验证和最小权限；一台设备连入 VPN 不应自动获得全部内网服务访问权。

隧道会吃掉 MTU

如果物理路径 MTU 为 1500，外层 IP、UDP、加密等头部占用一部分，内层可用包尺寸就更小。源主机仍发送 1500 字节内层包时，网关可能分片、丢弃或依赖路径 MTU 反馈。若必要 ICMP 被挡，常出现“ping 小包能通、文件传输卡住”的 PMTU 黑洞。TCP 可在边界谨慎做 MSS 调整，UDP/QUIC 则需自己的包大小策略。

隧道内外可能有两次拥塞控制和不同队列，特别是 VPN 基于可靠传输再承载 TCP 时，外层重传与内层重传可能互相影响。应按实际 VPN 技术和链路条件测试，不可仅看虚拟网卡显示的标称速率。

DNS 与身份边界

企业内网域名可能只由内部 DNS 解析，VPN 客户端需把相关查询送到内网解析器。全隧道通常让查询随默认路径走企业；分流需要明确域名后缀、解析器与 DoH 策略。浏览器若启用外部 DoH，可能绕过系统内部解析，造成“命令行可解析、浏览器打不开”。

连接 VPN 的设备仍要验证用户与设备身份，密钥和证书需要更新与吊销。共享一个长期预共享密钥给所有人，会让离职、设备遗失时难以单独撤销。VPN 是连接手段，不是完整的零信任授权模型。

故障排查与验收

按“隧道握手—虚拟接口—路由表—DNS—目标端口—业务响应”顺序核对。分别访问内网 IP、内网域名和公网网站，观察它们走物理出口还是隧道。抓包时在物理口看到外层网关地址，在虚拟口看到内层目的；两个观察点不能混用。测试全隧道和分流策略时，还要检查用户所在家庭网段冲突、IPv6 是否绕过策略及断线后的流量行为。

上线验收包括密钥轮换、客户端断网重连、网关故障切换和大文件传输。只验证一次登录成功，会遗漏最常见的路由、DNS 与 MTU 问题。

自检

VPN 显示已连接，就能证明内网域名和大文件都可访问吗？

不能。还需检查分流路由、内部 DNS、回程策略和隧道有效 MTU。
