Flink 并行度与背压排障

从 Task Slot、数据倾斜、背压与状态大小寻找流作业的瓶颈。

并行度、背压与排障

项说明
并行度算子并行实例数；受 key 分布与 slot 数共同限制
Task SlotTaskManager 的资源单位；建议 slot 数 ≈ CPU 核数
算子链（operator chaining）相邻算子合并到同一线程，减少序列化与网络开销
数据倾斜某个 key 的量远超其他 → 一个 subtask 成为瓶颈解法：加盐打散后再聚合、或本地预聚合
背压下游处理慢导致上游阻塞在 Web UI 的 BackPressure 页面定位源头算子
  • 先定位背压源头：从 sink 往 source 方向看，第一个「背压高」的算子就是瓶颈，而不是看最慢的那个。
  • 状态过大的表现：checkpoint 时间越来越长、最终超时失败。对策：设 State TTL、减小窗口、换 RocksDB + 增量 checkpoint。
  • 增量 checkpoint：RocksDB 状态下只上传变化的文件，能把 checkpoint 从分钟级降到秒级。
  • GC 压力大：用 HashMapStateBackend + 大状态时常见，改成 RocksDB 把状态移出堆。
  • 并行度不是越大越好：超过 key 基数或 slot 数的部分不会带来收益，还会增加 checkpoint 开销。

运维命令

# 常用运维命令
flink run -d -p 8 -c com.x.Job app.jar          # 提交，并行度 8
flink list                                       # 查看作业
flink savepoint <jobId> hdfs:///sp/              # 触发 savepoint
flink cancel -s hdfs:///sp/ <jobId>              # 取消前先存 savepoint（优雅停）
flink run -s hdfs:///sp/savepoint-xxx app.jar    # 从 savepoint 恢复

# 关键区别：
#   Checkpoint = 自动、用于故障自动恢复、由 Flink 管理生命周期
#   Savepoint  = 手动、用于版本升级/迁移、需显式指定路径
Flink 和 Spark Streaming 怎么选？

要低延迟 + 事件时间 + 精确一次状态 → Flink（毫秒~秒级、真流）；要高吞吐 + 已有批处理能力复用、延迟能接受秒~分钟级 → Spark Structured Streaming（微批）。

watermark 该怎么设？

先统计真实数据的乱序程度（如 max(event_time 落后 processing_time 的分位数），再取略大于 P99 的值。设太小会丢数据，设太大会让窗口迟迟不触发。

窗口一直不输出是为什么？

最常见是 watermark 没有推进：某个并行度上没有数据流入，watermark 就停在那里。解法是设 withIdleness() 让空闲分区也能推进 watermark。
