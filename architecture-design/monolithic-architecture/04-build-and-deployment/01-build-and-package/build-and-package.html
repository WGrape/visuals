单体架构的构建与打包

单体虽部署简单，但“一个包“也意味着：代码越多，构建越慢、启动越久、包越大。理解这些曲线，才能提前应对。

构建流程随规模恶化变慢的根因缓解手段

🔄 一、典型的单体构建流程

编译
源码→字节码
→
单测
单元测试
→
打包
jar/war/zip
→
产物
一个可部署包

整条链路是串行的：任何一处改动，都要重新走完整个流程再上线。

📈 二、随规模恶化的三条曲线

指标随代码量变化影响
构建时间近似线性增长改一行等很久，反馈慢
启动时间随 Bean/组件增多变长部署、回滚、本地调试都变慢
包体积持续膨胀传输、拉取镜像更耗时

🐢 三、变慢的根因

  • 全量编译/测试：单体没法只编译“变的那一块”。
  • 启动时装配重：框架要扫描并初始化全部组件（如 Spring 全容器）。
  • 依赖臃肿：一个包要带上所有模块的第三方依赖。

🚀 四、缓解手段

✅
  • 构建缓存与增量编译：只重建变化模块（如 Gradle 增量、Bazel）。
  • 分层测试：单测快跑，集成测试少量精选，别全量慢测阻塞。
  • 懒加载 / 组件扫描收窄：减少启动时的无谓装配。
  • 模块化：让构建工具能按模块增量，是治本的方向。
