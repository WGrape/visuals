分层架构

最经典、最基础的架构风格：把系统按职责切成横向层，层与层之间单向依赖。

什么时候适用？

判断信号：应用职责能按表示、业务、数据访问划清，且主要是进程内调用。

  • 常规企业应用把 HTTP、用例和数据库职责分开
  • 团队需要清楚的模块边界与单向依赖规则
  • 从混杂的控制器中抽出稳定业务逻辑

和相近方案怎么区分？

相近方案选择边界
整洁架构都强调边界；整洁架构进一步要求依赖方向指向业务核心，数据库只是外层细节。
微服务跨进程拆分部署；分层架构可完全在一个进程内实现。

最小伪代码

function placeOrder(request):
  dto = web.parse(request)
  order = application.place(dto)
  // application 调用 repository.save(order)
  return web.respond(order)

边界：分层不是每层都必须转发空壳方法；跨层调用规则应明确，避免业务逻辑泄漏到控制器。

四层经典模型 Layered

表现层 → 业务层 → 持久层 → 数据层，调用自上而下、禁止逆向越层

核心约束是单向依赖：上层可以调用下层，下层永远不知道上层的存在（依赖倒置可让下层依赖抽象接口）。这样每层可独立替换与测试。

优点与代价

  • 优点：结构清晰、易于理解、每层可单独测试与替换（如换数据库不动业务层）。
  • 代价：层一旦变多，容易退化为『贫血模型 + 透传层』；跨层改动要改多处；性能上多层封装有开销。

常见变体

  • 经典三层：表现 / 业务 / 数据。
  • DDD 四层：接口层 / 应用层 / 领域层 / 基础设施层。
  • 严格分层：只能依赖相邻下层；松散分层：可跨层依赖。

面试高频问答

Q：为什么禁止表现层直接访问数据库？
A：破坏分层会让业务规则散落到各处、无法复用也无法单测；强制经业务层可保证事务、权限、校验集中可控。
Q：分层架构和微服务冲突吗？
A：不冲突。分层是『一个进程内的纵向切分』，微服务是『跨进程的横向切分』；一个微服务内部通常仍用分层组织代码。

分层是最基础也最容易被做坏的架构

分层架构的思想是按职责把系统切成若干层，依赖单向向下。它简单、易理解、易分工，是绝大多数系统的起点。但它也最容易退化成「每层都在转发」的形式主义，或者让业务逻辑泄漏到 Controller 里（贫血模型）。

表现层处理协议与展示：HTTP、参数校验、视图渲染
应用层用例编排：组合领域对象完成一个业务动作
领域层业务核心：实体、值对象、领域服务、业务规则
基础设施层技术细节：数据库、缓存、MQ、外部服务
依赖倒置领域层定义接口，基础设施实现，反转依赖方向
严格分层 vs 松散分层是否允许跨层调用；严格更清晰但可能有转发开销

关键认知：分层是「手段」不是「目的」。如果每层只是转发而没有任何职责，那这个分层就是负担。判断标准：每一层都应该有只有它能做的事情。

实践要点

① 避免贫血模型

  • 把业务规则放进领域对象，而不是全塞进 Service。
  • 例：Order.cancel() 应该自己判断状态与规则，而不是 OrderService 里一堆 if。
  • Service 负责编排（调用多个领域对象、事务、外部调用）。

② 依赖倒置怎么用

  • 领域层定义 Repository 接口，基础设施层实现。
  • 这样领域层不依赖任何框架与数据库。
  • 测试时可以用内存实现替换，无需数据库。
  • 这是分层架构能否「可测试」的关键。

③ 跨层调用怎么办

  • 原则上不允许：表现层直接访问领域层会绕过应用层的事务与编排。
  • 简单查询（CQRS 的 Q 侧）可以放宽，直接走查询通道。
  • 若频繁需要跨层，说明层次划分不合理，应重新划分。

④ 什么时候加一层

  • 有明确的新职责（如防腐层 ACL、网关聚合层）。
  • 不是「为了将来可能用到」而加——YAGNI。
  • 反模式：Manager、Helper、Util 这类无明确职责的层。
  • 每层要有自己的模型（DTO / Domain / PO 分离）。

深入自检

为什么分层架构容易变成「贫血模型」？

因为很多人把分层理解为「Controller 收参数、Service 写逻辑、DAO 存数据」，实体只剩字段与 getter/setter，业务规则全在 Service 里。这样领域对象没有行为，业务规则难以复用与测试，Service 会越来越臃肿。对策是把状态与行为放回到领域对象。

什么是依赖倒置，为什么重要？

依赖倒置指「高层模块不依赖低层模块，二者都依赖抽象」：领域层定义 Repository 接口（抽象），基础设施层实现它。这样领域层不再依赖数据库与框架，既便于替换实现，也让领域逻辑可以在没有数据库的情况下被单元测试。

严格分层和松散分层怎么选？

严格分层（只能调下一层）规则清晰、依赖可控，但可能为了绕过而产生「传声筒」代码；松散分层（允许跨层）更灵活但依赖会逐渐混乱。实务建议：写路径严格（保证事务与编排），读路径可适度放开（如直接走查询服务，避免层层转发）。

DTO、Domain、PO 为什么要分开？

因为它们的变化原因不同：DTO 面向接口契约（随外部需求变）、Domain 面向业务（随规则变）、PO 面向存储（随表结构变）。混用会让「改表结构」影响接口，或「改接口」影响数据库，耦合严重。代价是需要写转换代码（可用 MapStruct 之类工具）。

分层架构适合微服务吗？

适合作为「每个服务内部」的组织方式。微服务解决的是服务间的边界与部署问题，分层解决的是单个服务内部的职责划分，二者是不同层面、可以共存。常见组合：服务间按业务能力拆分，服务内用分层（或六边形）组织。

如何判断分层是否合理？

三个检查：① 每层是否有只有它能做的职责（否则可以合并）；② 改动一个需求时是否总是要改所有层（过度耦合的信号）；③ 新同事能否在 5 分钟说清每层该放什么（规则是否清晰可执行）。
