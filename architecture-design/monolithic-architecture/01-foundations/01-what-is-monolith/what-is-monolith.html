什么是单体架构

单体架构（Monolithic Architecture）把全部业务功能打包进一个可部署单元——一个进程、一个包、一次部署。它不酷，却是绝大多数系统真实的起点。

核心定义它长什么样单体≠不可拆分为何是起点一句话总结

🎯 一、先把定义钉死

一句话：单体架构是“一个部署单元承载全部功能“的架构形态。下面把这句话拆开。

单体架构 = 把所有功能（UI、业务逻辑、数据访问）编译/打包成一个可部署产物，运行在单个进程里，共享同一个数据库。
维度单体架构对照：微服务
部署单元一个包 / 一个进程多个独立部署的服务
进程单进程内函数调用跨网络 RPC / HTTP
数据通常共享一个数据库各服务自有数据库
团队边界一个团队即可交付多团队各自拥有服务
💡
本质是一种“部署形态"，不是“能不能模块化”。一个单体内部照样可以划分清晰的模块——只是它们最终被一起打包、一起上线。

🧱 二、它长什么样

典型单体就是一个被分层的大盒子：请求从上层进来，逐层向下，最后落到同一个数据库。

表现层 / API 层
Controller、页面、REST 接口
业务逻辑层
Service、领域规则
数据访问层
DAO、ORM、Repository
共享数据库
同一份表，多个模块共用

所有层都在同一个进程里，调用是内存里的函数跳转，延迟几乎为零。这既是它的简单之处，也是它日后扩展受限的根源。

🔍 三、单体 ≠ 不可拆分

最常见的误解：把“单体“和“意大利面代码“画等号。两者没有必然联系。

✅ 好的单体
模块化单体
清晰的模块边界
单向依赖、无环
一处变更影响可控
❌ 坏的单体
大泥球
模块互相纠缠
改一处牵全身
无人敢动核心代码
✅
结论：单体是部署粒度的选择，模块化是内部结构的选择，两者正交。先学会把单体写“好”，再谈要不要拆。

🌱 四、为什么它常是起点

  • 认知负荷低：没有网络调用、没有分布式事务，本地一个断点就能看完一条链路。
  • 运维简单：一个包、一个进程、一个数据库，监控与排障的图纸很小。
  • 端到端一致易保证：一个本地事务就能跨多个“模块“保证 ACID。
  • 演进空间大：内部先模块化，等真出现扩展/组织瓶颈，再局部抽取成服务。

🛗 五、一句话总结

如果有人 30 秒问你“单体架构是啥"
它就是一个把所有功能打包成一个进程一起部署的架构。简单、一致、好调试；代价是扩展与组织上会被“一起变大“反噬。把它写好（模块化），它就能陪你走很远——真到瓶颈时，再按功能逐步拆出去。
