07 数据仓库 · 分层架构

数仓分层 ODS / DWD / DWS / ADS
为什么要分这么多层

刚接触数仓的人最常问："直接从业务库抽出来算好指标不行吗？为什么要搞 ODS、DWD、DWS、ADS 四五层？"答案是：不分层，你省下的是今天的建模时间，付出的是未来每一次需求变更都要重做一遍的代价。本文讲清每一层到底在解决什么问题、层与层之间怎么流转，以及哪些"看起来聪明"的做法其实是反模式。

1先给结论：分层不是为了"规范"，是为了解决四个具体问题

🔧 解耦

上游业务库改了个字段名、加了个枚举值，只影响 ODS→DWD 这一层，下面的几十张报表不用动。没有分层，改一处要动全部。

♻️ 复用

"下单金额"这个口径在 DWS 算一次，10 个报表都从它取。不分层，10 个报表各写一遍 SQL，算出 10 个不同的数。

🔍 可溯源

报表数字对不上时，能一层层往下追：ADS → DWS → DWD → ODS → 业务库。不分层就是一团 SQL，查无可查。

💰 省算力

明细层只清洗一次并持久化，上层全部复用。不分层则每个需求都从原始明细重扫一遍全表，计算成本成倍浪费。

一句话分层本质是把"从原始数据到业务指标"这条长链路切成若干段，每段只做一类事，并留下中间产物。中间产物就是复用与溯源的基础。

2分层全景

标准五层：ODS → DWD → DWS → ADS，DIM 横向贯穿

3逐层拆解：每层到底干什么

ODS 原始数据层

  • 职责：把源数据原封不动搬到数仓。只做技术加工（格式转换、分区、压缩）不做业务加工。
  • 为什么必须保留：一旦 DWD 的清洗逻辑有 bug、或口径要重算，可以从 ODS 重跑而不用再去打扰业务库。ODS 是数仓的"后悔药"。
  • 存储策略：增量表（_di，按天分区）或全量快照（_df，每天一份完整快照，便于取历史状态）。

DWD 明细数据层

  • 职责：清洗 + 标准化 + 口径统一。过滤脏数据、去掉测试账号、脱敏手机号、统一时间/金额单位、把枚举值映射成可读含义。
  • 关键动作：维度退化：把常用的维度字段冗余进事实表（如把 user_level、region_name 直接放进订单明细），这样下游不必每次都 join 维表。
  • 粒度：最细的业务事实。一行 = 一次真实发生的业务动作。
  • 这一层是数仓的"地基"：它决定了所有上层能算出什么。DWD 建模错了，上层全部跟着错。

DWS 汇总数据层

  • 职责：按主题域（交易、用户、流量、商品）和常用维度做聚合，产出"可复用"的中间粒度。
  • 判断标准：如果有 3 个以上报表都要"按天按用户的成交金额"，就该在 DWS 建一张 dws_user_trade_1d，而不是让 3 个报表各扫一遍明细。
  • 粒度选择：不要太粗（失去复用性），也不要太细（等于没聚合）。典型：一天 × 一个用户 × 一个品类。

ADS 应用数据层

  • 职责：为具体的一个报表 / 接口 / 看板服务。可以直接被 BI 工具或 API 读取。
  • 特点：允许高度定制、允许冗余、不追求复用。这里追求的是"查询快、字段对得上"。
  • 常见做法：把结果同步到 MySQL / ClickHouse / Redis，供在线接口毫秒级查询。

DIM 公共维度层

  • 职责：存放描述性数据（谁、什么、哪里）。如用户画像、商品属性、地区、日期。
  • 拉链表：维度会缓慢变化（用户等级从 V1 升到 V2）。用 start_date / end_date 记录每条状态的有效区间，就能查"用户在下单当时的等级是什么"。

4命名规范：从表名就能看出它在哪层

命名模板：  <层>_<主题域>_<业务对象>_<粒度>_<刷新周期>

ods_order_di            ODS 层 · 订单 · 日增量(daily incremental)
ods_user_df             ODS 层 · 用户 · 日全量(daily full)
dwd_trade_order_di      DWD 层 · 交易域 · 订单明细 · 日增量
dws_user_trade_1d       DWS 层 · 用户粒度 · 交易汇总 · 1 天
dws_shop_sales_1m       DWS 层 · 店铺粒度 · 销售汇总 · 1 月
ads_gmv_daily_report    ADS 层 · GMV 日报
dim_user                DIM 层 · 用户维度

常见周期后缀：_di 日增量 · _df 日全量 · _1d 天汇总 · _1w 周汇总 · _1m 月汇总
为什么命名规范重要数仓的表动辄上千张。规范的命名让"这张表属于哪层、什么粒度、多久刷新一次"直接可读，大幅降低沟通与排障成本。也便于用规则自动做生命周期管理（如 ODS 保留 90 天自动清理）。

5反模式：这些做法会让分层名存实亡

❌ 跨层引用

ADS 直接读 ODS、或 DWS 跳过 DWD 从 ODS 取数。后果：清洗口径被绕过，同样的指标在不同报表中不一致；且依赖图变成网状，改一处不知道会影响谁。

❌ 烟囱式开发

每个需求都从 ODS 写一条独立长 SQL 直达 ADS。后果：短期快，半年后几百条重复 SQL，"订单金额"有七八个版本，谁也说不清哪个对。

❌ 层级过度膨胀

搞出 DWD / DWM / DWS / DWT / ADS 五六层，每层差异模糊。后果：链路太长，排查要跨 6 张表；调度依赖复杂，一处失败全线阻塞。三四层足够绝大多数场景。

❌ 在 DWD 做聚合

明细层混入了汇总指标。后果：粒度混乱，别人 join 这张表时容易重复计数（把汇总值又 SUM 了一遍）。明细层就应该是纯明细。

6该分几层：不要教条

团队规模 / 场景建议分层理由
初创 / 报表 < 20 个ODS → DWD → ADS（3 层）复用需求少，先保证口径统一和可溯源即可
中型 / 多主题域ODS → DWD → DWS → ADS（4 层）最主流：复用价值开始显现，DWS 能省下大量重复计算
大型 / 强治理要求4 层 + DIM + 指标体系 + 数据资产平台靠平台化工具强制规范，而非靠人自觉
实时数仓同样分层，但用流（Flink）实现每层ODS 是 Kafka Topic，DWD/DWS 是 Flink 状态 + 实时写入的存储
判断要不要加一层的唯一标准：这一层的产物会被 3 个以上下游复用吗？是 → 值得独立成层；否 → 直接在上层写 SQL 就行，不要为了"看起来规范"硬分层。

7常见误区

"分层就是把数据复制好几份，浪费存储"
算错账了。存储是廉价的，重复计算和口径不一致导致的人工对账成本才是昂贵的。而且分层不是简单复制——每层数据量递减：ODS 100TB → DWD 80TB（清洗掉脏数据）→ DWS 5TB（聚合）→ ADS 几百 GB。上层的存储开销远小于明细层。
"ODS 层做点清洗也没关系吧"
最好不要。ODS 的价值就在于"它是源系统的忠实副本"。一旦你在 ODS 里改了字段，源系统再变一次，你就分不清哪些改动是源系统的、哪些是你自己加的，溯源链断裂。清洗统一放到 DWD。
"ADS 表也要追求复用"
不需要。ADS 的定位就是"为某个具体需求服务"，可以高度定制、可以冗余、可以一次性的。复用性应该在 DWS 层解决。要求 ADS 复用，反而会让它被多个需求拉扯成不伦不类的中间物。
"有了湖仓（Iceberg/Hudi），分层就过时了"
没有。湖仓解决的是存储与事务问题（ACID、时间旅行、Upsert），分层解决的是数据组织与口径治理问题，两者是不同层面。实际上湖仓让分层更好落地：每层可以是 Iceberg 表，享受事务与时间旅行能力。
