构建产物

裁剪与版本

-ldflags="-s -w" 减小体积；用 -X 注入 version/git 信息；多平台交叉编译只需 GOOS/GOARCH。

go build -ldflags="-s -w -X main.version=$(git rev-parse --short HEAD)" -o app .
GOOS=linux GOARCH=arm64 go build -o app-arm .
CGO 与交叉

默认关闭最省心

CGO_ENABLED=0 产出纯 Go 静态二进制，交叉编译与容器化最简单；启用 cgo 才需要目标平台 C 工具链。

CGO_ENABLED=0 GOOS=linux go build -o app .
# 多阶段镜像里常用此方式
容器化

多阶段构建

用多阶段 Dockerfile：构建阶段编译，运行阶段只拷二进制，镜像小且不含工具链。

FROM golang:1.22 AS build
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -o /app .
FROM gcr.io/distroless/static
COPY --from=build /app /app
ENTRYPOINT ["/app"]
运维要点

可观测可重启

暴露 /healthz 健康检查、/metrics 指标；用 SIGTERM 优雅退出（停收新请求、排空在途）；日志走 stdout 交给采集。

⚠️ 容器里用 distroless/scratch 时，注意时区与 CA 证书需显式拷入，否则时间/HTTPS 会异常。

从代码到镜像：构建要点

# 静态链接的小镜像（推荐） CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \ go build -trimpath -ldflags='-s -w' \ -o bin/app ./cmd/api # 参数说明 # CGO_ENABLED=0 不依赖 libc，镜像可用 scratch/distroless # -trimpath 去掉本地绝对路径，二进制可复现 # -s -w 去掉符号表与调试信息，体积明显变小 # GOOS/GOARCH 交叉编译，无需目标平台的机器 # 需要保留调试信息时去掉 -s -w # 需要 cgo 时必须带目标平台的 C 工具链

多阶段构建是容器化的标准做法：编译阶段用完整的 Go 镜像，运行阶段只拷贝二进制，镜像体积能从几百 MB 降到十几 MB。

FROM golang:1.22-alpine AS builder WORKDIR /src COPY go.mod go.sum ./ RUN go mod download COPY . . RUN CGO_ENABLED=0 go build -trimpath -ldflags='-s -w' -o /out/app ./cmd/api FROM gcr.io/distroless/static-debian12 COPY --from=builder /out/app /app USER nonroot:nonroot EXPOSE 8080 ENTRYPOINT ["/app"]
多阶段构建编译环境与运行环境分离。
静态链接CGO_ENABLED=0 才能放进极小镜像。
体积裁剪-s -w 去掉符号与调试信息。
不可变镜像配置靠环境变量注入，不打包进镜像。

容器里的 Go 程序：三个必调项

问题表现处理
CPU 配额不感知容器限 2 核，Go 仍按宿主机核数设 GOMAXPROCSGo 新版本已自动感知 cgroup 限额；旧版本用 automaxprocs
内存限制不感知容器限 512MB，Go 按宿主机内存决定 GC 目标用 SetMemoryLimit 设软上限，或调 GOGC
优雅退出被 SIGTERM 直接杀掉，进行中的请求中断监听信号并调用 Shutdown，配合 preStop
// 容器感知的推荐设置 import ( _ "go.uber.org/automaxprocs" // 自动按 cgroup 设 GOMAXPROCS "runtime/debug" ) func init() { // 设软内存上限，配合容器 limit debug.SetMemoryLimit(512 << 20) // 512MB } // 优雅退出 quit := make(chan os.Signal, 1) signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM) <-quit ctx, cancel := context.WithTimeout(context.Background(), 20*time.Second) defer cancel() srv.Shutdown(ctx)

为什么退出要留时间：K8s 发送 SIGTERM 后会有 graceful period（默认 30 秒），超时才 SIGKILL。应用必须在这段时间内完成「停止接收 → 处理完存量 → 释放资源」，否则就是有损发布。

健康检查与发布

三类探针

  • startup：启动慢的应用用它，避免被 liveness 误杀
  • liveness：是否还活着，失败则重启容器
  • readiness：是否能接流量，失败则从 Service 摘除

readiness 应当检查关键依赖；liveness 不要检查依赖，否则依赖抖动会引发大面积重启。

就绪与预热

  • 监听端口后再标记 ready
  • 需要预热缓存时先加载再 ready
  • 关闭时先置 not ready，等存量请求结束

发布策略

  • 滚动更新 + 优雅退出是基线
  • 金丝雀/灰度降低风险暴露面
  • 蓝绿切换适合需要快速回滚的场景
  • 任何策略都要能一键回滚

深入自检

为什么 Go 程序在容器里会用掉超出预期的 CPU？

旧版本 Go 按宿主机 CPU 核数设置 GOMAXPROCS，导致在限额很小的容器里仍创建大量系统线程与 GC worker，产生大量上下文切换。新版本已能感知 cgroup，旧版本建议引入 automaxprocs。

内存 OOM 但 Go 的堆看起来不高，为什么？

进程内存不只是 Go 堆，还包括栈、运行时结构、cgo 分配、以及尚未归还给操作系统的回收内存。Go 的 GC 与内存归还策略与容器 limit 不完全一致，用 SetMemoryLimit 可以让 GC 更贴近容器的真实上限。

-s -w 会影响排查问题吗？

会一点：去掉符号与调试信息后，崩溃栈的可读性下降，pprof 与 delve 的体验会受影响。一般生产用裁剪版，排查时构建一份未裁剪的版本。

为什么容器里要跑非 root 用户？

降低逃逸风险：以 root 运行的进程一旦被攻破，攻击者拿到的权限更大。distroless 等基础镜像提供 nonroot 用户，只需在 Dockerfile 里加一行 USER。

发布时如何做到无损？

三件事：应用正确处理 SIGTERM 并优雅退出；K8s 配置 preStop 等待与足够的 terminationGracePeriodSeconds；readiness 探针在退出前置为失败，让流量先摘走。三者缺一都可能有损。
