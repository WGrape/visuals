CPU 与内存之间的三条总线 — 所有操作的物理基础

下面用 地址 数据 控制 三类信号建立教学模型。 现代处理器访问主存还要经过缓存、内存控制器和具体内存协议；图中的线路与时序不是某一款 DDR 系统的实际引脚图。

地址总线（Address Bus）— "去哪里"的问题

在简化的字节寻址模型中，地址信号用于选择目标位置。若有 32 个独立地址位，理论上可表示 2³² 个字节地址，即 4 GiB 地址空间； 这不等于某台计算机的物理内存上限，实际还受内存控制器、地址映射和体系结构限制。点击下方按钮比较地址位数。

数据总线（Data Bus）— "传什么"的问题

数据总线是双向的：读操作时内存→CPU，写操作时 CPU→内存。 数据通路的宽度决定一次可传输多少 bit。若示例通路宽 64 bit，一次可传 8 字节；CPU 的 32/64 位称谓不直接决定内存总线宽度。 点击按钮看数据在线流动的过程。

控制总线（Control Bus）— "做什么"的问题

控制信号协调读写方向和完成时机。图中以 CPU 与内存直接交互作抽象示意，现代主存请求通常由内存控制器转换为具体协议命令。 核心控制信号包括：
READ# 读信号   WRITE# 写信号   M/IO# 内存/IO选择   READY 就绪信号   CLK 时钟同步

内存阵列（Memory Array）— 地址如何映射到存储单元

内存内部像一个巨大的表格。地址经过行解码器和列解码器，定位到具体的存储单元。 点击任意一个单元格，查看地址如何一步步分解为 Bank/Row/Column。

读数据全过程（Memory Read）— 从 CPU 发地址到拿到数据的完整时序

读数据 = CPU 从内存取一个值。过程分 5 步：①CPU发地址 ②CPU拉低READ#信号 ③内存收到后查地址 ④内存把数据放到数据总线 ⑤CPU采样数据。点击"逐步播放"观看每一步的信号变化。

写数据全过程（Memory Write）— 从 CPU 发数据到内存存入的完整时序

写数据 = CPU 往内存存一个值。过程分 5 步：①CPU发地址 ②CPU把数据放到数据总线 ③CPU拉低WRITE#信号 ④内存收到后把数据存到目标单元 ⑤内存拉高READY确认完成。

取指令全过程（Instruction Fetch）— CPU 取下一条要执行的指令

取指 = 读数据的特殊形式。CPU 把 PC（程序计数器）的值作为地址发到地址总线， 内存返回该地址处的机器码（指令）到指令寄存器（IR）。本质上就是一次读操作，但地址来源是 PC 而非通用寄存器。

DRAM 内部到底做了几次动作

真正有意思的部分在第 ⑤ 步。DRAM 不是一个能随机访问任意字节的大数组，它是按「行」操作的二维 Magellan阵列：

行命中（row buffer hit）比跨行快得多：同一行内连续读几乎不用重复 ACT —— 这就是「顺序访问远快于随机」的物理根源 ② 一次搬运 64 字节是因为 burst 传输天然一次搬一个突发长度，正好对应一条 cache line 所以「只改一个 int」实际可能导致：整行进来、整行写回去 —— 局部性好不好，直接决定你用掉多少个 DRAM 周期
DRAM 三步：激活行 → 读列 → 预充电
环节典型耗时量级说明
CPU 寄存器约 1 个周期最快，指令直接可用
L1 Cache数个周期分指令/数据的两小块，追求极低延迟
L2 Cache十几周期每个核独享或少量共享
L3 Cache几十周期多核共享，容量最大

把这条链路翻译成优化动作

  • 按行主序遍历。二维数组 a[i][j] 在内存里是按行连续存放的，内层循环走 j 是顺序访问；走 i 则是每次跨越一整行 —— 这正是 row buffer hit 与 not hit 的区别。
  • 减少跨 cache line 的伪共享。两个频繁写的变量若落在同一条 cache line 里，不同核写不同变量也会互相作废数据 —— 这是多核程序里最隐蔽的性能杀手之一。
  • 数据结构最好连续内存。数组（AoS/SoA）比链表/指针结构对缓存更友好，这也是很多高性能引擎偏爱连续容器的原因。
  • 减少地址Translation overhead。TLB 未命中要遍历多级页表。使用大页或与访问模式匹配的 Hugepage 能显著降低 TLB 压力。
  • 不要越过 NUMA 边界。多路服务器上访问「属于另一个 CPU 的内存」要跨互联总线，延迟与带宽都差一截。线程与内存应尽量绑定在同一 NUMA 节点。

深入自检

为什么 Cache 的最小单位是 64 字节而不是一个字节？

因为 DRAM 的一次突发传输天然一次吐出一小段数据，而且缓存管理的元数据（标签、有效位、一致性状态）需要一个 ample 的最小粒度。以 64 字节为界运输，可以在「标签开销」和「传输浪费」之间取得很好的平衡；再小一部分会让管理成本失控。

为什么明明只读一个 int，性能却和读一大片差不多？

因为系统一定会把包含它的整条 cache line（64 字节）从内存搬到缓存里。单次请求的延迟是固定的 —— 无论你要一个字节还是六十四字节，都要经历同样的行激活、列读出、总线传输。所以写过的 localityns 优化才会强调「把要用的数据放在相邻位置」。

MMU 和 TLB 是什么关系？

MMU 是负责地址转换的硬件单元，页表是它要查的数据结构；TLB 则是它的缓存 —— 记录最近用过的「虚拟页→物理页框」映射。每次访问内存原则上都要两次访问（先查页表再访数据），TLB 命中后只需一次。TLB 未命中时会去遍历多级页表，代价很大。

为什么随机访问比顺序访问慢这么多，即使都在内存里？

同样是读一万次，顺序访问几乎都在同一行甚至同一 burst 里完成，row buffer hit 率极高；随机访问每次都要重新激活不同的行，还要经历预充电，行冲突会进一步拉长等待。再加上 TLB、各级 Cache 的命中率差异，最终性能常常差出一个数量级。

存储层次的数字：从 0.5ns 到 10ms

层次结构能成立，靠的是两个经验规律：时间局部性（刚访问的很快再访问）和空间局部性（访问了 A 就会访问 A 旁边）。下面这张表是所有性能优化的基准尺。

命中率怎么算：AMAT 与有效带宽

层次结构好不好，用一个公式算清楚：AMAT（平均内存访问时间）= 命中时间 + 缺失率 × 缺失代价。

AMAT 手算示例

# 例：L1 命中 1ns，缺失率 5%，L2 命中 4ns，L2 也 miss 才去主存 80ns
# 两级简化版（假设 L2 命中率 95%）：
AMAT = 1 + 0.05 x (4 + 0.05 x 80) = 1 + 0.05 x 8 = 1.4 ns

# 若命中率掉到 80%（遍历一个大数组、步长为 cache line 的倍数）：
AMAT = 1 + 0.20 x (4 + 0.05 x 80) = 1 + 1.6 = 2.6 ns   # 慢了近一倍

# 若彻底失序（随机访问 4GB 数组，每次都去主存）：
AMAT = 1 + 1.00 x 80 = 81 ns                            # 慢 80 倍
访问模式原因相对性能
顺序遍历数组完美空间局部性，一次取 64B 全用上1x（基准）
步长 stride=1 的多维数组（C 行优先）连续~1x
按列遍历 C 二维数组每次跳一行，cache line 只用一个元素5~20x 慢
步长 = cache line 大小的整数倍每次都落在同一个 cache set，冲突失效10x+ 慢（典型如 stride=4096）
链表遍历节点随机分布，无法预取3~10x 慢
随机访问大数组必然 miss TLB + cache50~100x 慢
  • cache line = 64B：一次内存读写的最小单位。一个 uint64 数组，一次 miss 会顺带取回 8 个相邻元素。
  • 伪共享（false sharing）：两个线程改两个不同的变量，但它们落在同一条 cache line 上 → cache 一致性协议反复失效，性能可能掉 10 倍。解法：结构体填充到 64B 对齐（Go 里 _ [56]byte，Java @Contended）。
  • TLB：地址翻译的缓存，L1 TLB 通常只有 64 项 4K 页 = 覆盖 256KB。访问超过这个范围就要走页表。用 大页（2M/1G）可把覆盖面积扩大 512 倍，是数据库/虚拟机标配优化。
  • 预取：硬件预取器只认规律步长（前进/后退的单位步长），链表指针这种无规律地址它无能为力，需要 __builtin_prefetch 手动提示。
为什么容量翻倍，性能只提升一点点？

因为性能主要由缺失率决定，而缺失率随容量是平方根级下降（经验规律：容量 ×4，miss rate ÷2）。所以 L2 从 512K 加到 1M 几乎无感，但访问模式从随机改成顺序，可能直接快 50 倍——改算法比加硬件有效得多。

Belady 异常是什么？

直觉上 cache 越大命中率越高，但对 FIFO 置换算法存在反例：增大容量后命中率反而下降（因为 FIFO 完全不看访问历史）。LRU 和 OPT 都属于「栈算法」，不存在这个异常。这也是为什么实际硬件用 LRU 的近似（如伪 LRU、CLOCK），而不用 FIFO。

写回（write-back）和写直达（write-through）怎么选？

现代 CPU 的 L1/L2 几乎都是写回：只改 cache，行被替换时才写回主存，省掉大量写流量，代价是要维护 dirty 位和一致性（MESI）。写直达 simple 但写带宽吃不住，只在需要强一致的场景（如某些外设 DMA 缓冲区）用，通常配合 no-write-allocate。
