依赖图与增量构建：为什么「该重编的没重编」是最难查的 bug

依赖图的性质、时间戳与内容哈希两种判定、漏依赖的三种表现，以及增量提速的优化顺序

一句话总结：增量构建的正确性完全取决于依赖图准不准：漏一条边，该重编的没重编（程序行为与源码不一致，极难排查）；多一条边，白白多重建（只是慢，不会错）。所以构建系统的设计哲学是宁可多重建，不可漏重建。

01依赖图是什么

依赖图是有向无环图（DAG），改动沿边向下传播
性质说明为什么
有向边表示「谁依赖谁」方向错了会导致反向重建
无环不能有循环依赖有环就无法确定构建顺序，构建系统会报错
拓扑序执行依赖先于目标构建这是调度的唯一依据
可并行无依赖关系的分支可同时构建并行加速的来源
要点：循环依赖是构建系统唯一会直接报错的结构问题。出现时通常是模块划分有问题（A 依赖 B 的同时 B 又依赖 A），应该抽取公共层。

02怎么判断「要不要重建」

方式判据优点缺点
时间戳（Make 默认）依赖的 mtime > 目标的 mtime简单、快不可靠：时钟回拨、文件回写、复制丢失时间戳都会误判
内容哈希（Bazel / ccache）依赖内容的哈希与上次不同可靠，不受时间影响；支持远程缓存计算哈希有开销（但现代算法很快）
混合先用时间戳粗筛，命中再算哈希兼顾速度与可靠实现复杂
# 时间戳判定的经典失效场景
#   1) 从版本库 checkout 旧版本：文件 mtime 变成 checkout 时刻
#      → 明明是旧代码，却比目标文件"新"，触发无谓的全量重建
#   2) 两台机器时间不同步，或 NFS 挂载导致时间偏移
#      → 该重建的没重建
#   3) 构建产物被复制/打包时丢失 mtime
#      → 下次构建全量重来

# 内容哈希的做法（伪代码）
for each target:
    key = hash(
        hash(所有依赖文件的内容),
        命令行参数,
        编译器版本
    )
    if key != 上次记录的 key:
        重建
    else:
        直接复用缓存的产物

# 这就是 ccache / Bazel / 远程缓存的核心思路
要点：时间戳判定的问题不会让构建「出错」，只会让构建多干或多漏。但因为「漏」的表现是程序行为诡异，代价往往比想象中大得多。

03漏依赖的三种典型表现

现象根因修法
改了头文件没生效.o 的依赖里没有头文件加 -MMD -MP 生成 .d；或用 CMake（自动处理）
改了配置文件没生效配置被嵌进产物，但未声明为依赖把配置/生成脚本声明进依赖列表
换了编译器没重编编译器不在依赖图里把工具链版本纳入缓存 key（ccache/Bazel 会自动算）
并行构建偶发失败两个目标会写同一文件，但没声明顺序显式加顺序依赖；或让产物路径不冲突
  • 最阴险的是「改了头文件没生效」：编译链接都正常，程序跑起来行为不对，往往要花很久才想到是构建问题。
  • 排查手法：删掉 build 目录全量重编，如果行为就对了 —— 99% 是依赖图缺失。
  • 验证手法：改一个头文件，看预期该重建的目标是否真的重建了（用 make -n 干跑看命令）。

04怎么让增量构建更快

  1. 开并行：make -j$(nproc) 或 cmake --build . --parallel。性价比最高。
  2. 换 Ninja：启动开销小，依赖检查快，大项目差异明显。
  3. 减少头文件耦合：用前置声明替代 include、把私有声明移进 .c —— 这是最根本的优化。
  4. 用 ccache：内容哈希缓存，切换分支来回编译时几乎秒出。
  5. 拆分大翻译单元：单个 .c 过大时无法并行，拆开能提高并行度。
  6. 避免「全项目都依赖」的公共头：改一次触发全量重建，是增量构建的头号杀手。
优化手段收益成本
并行 -j数倍零成本，先做这个
Ninja 替代 Make10%~30%（大项目更多）低（改一行 -G）
ccache切换分支场景极大低（配一次）
减少头文件耦合最根本需要重构，成本高
预编译头 / 模块大引入复杂度，谨慎评估
要点：优化顺序建议：并行 → Ninja → ccache → 头文件重构。前三项几乎零成本，先拿完再考虑重构。

05常见疑问

问：为什么我改了一行，却重建了大半个项目？

说明那个文件在依赖图的上游（被大量模块 include）。这既是构建问题也是架构信号——一个头文件被全项目依赖，通常意味着抽象层次需要调整。

问：什么时候该 clean 全量重编？

出现这些情况就全量重来：① 换编译器/工具链；② 切换大版本分支；③ 构建出现无法解释的行为异常；④ 依赖配置（CMakeLists）有大改。把这些当成常规动作，不要试图省。

问：内容哈希一定比时间戳好吗？

正确性上更好，但不是免费的：要读文件内容算哈希、要维护缓存仓库。小项目用时间戳足够；大型仓库、需要远程缓存共享产物时，内容哈希才明显更划算。

问：构建产物要不要进版本库？

不要。构建产物放进 .gitignore，源码里只保留构建配置。进版本库会带来冲突、体积膨胀和「本地产物与源码不一致」的问题。
