垃圾回收与内存管理

Python 不用你手动 free，但不代表「不会内存泄漏」。引用计数负责即时释放，分代垃圾回收负责收拾它搞不定的循环引用；理解这套双机制，才能看懂内存涨不停的真正原因。

引用计数

每个对象都记着「有几个人在用我」

CPython 给每个对象维护一个引用计数（ob_refcnt）。引用 +1/−1 都即时发生；归零时立刻销毁对象、释放内存。这是 Python 内存管理的主力。

import sys
a = [1, 2, 3]
print(sys.getrefcount(a))   # 2（a + getrefcount 临时引用）
b = a                           # 引用 +1
print(sys.getrefcount(a))   # 3
del b                          # 引用 -1

引用计数为什么是主流？因为它确定性——对象一没人用就立刻释放，不用等 GC 触发。代价是「非线程安全」，所以 CPython 才需要 GIL 来保护计数操作（这也解释了 GIL 存在的根因）。

循环引用

引用计数救不了的「死循环」

如果 A 引用 B、B 又引用 A，它们的计数都永远 ≥1，引用计数无法回收——这就是循环引用。需要「垃圾回收器（GC）」定期扫描来兜底。

class Node:
    pass
a = Node(); b = Node()
a.other = b; b.other = a      # 互相引用
del a; del b               # 引用计数不为 0，对象没释放！

import gc
gc.collect()              # GC 找出这对孤岛并回收
⚠️ 常见泄漏来源：缓存用 dict 存对象且不清理、事件监听器互相引用、用列表当「已处理」集合又忘了删。这些都会形成循环/常驻引用，引用计数无能为力。
分代回收

GC 把对象按「年龄」分三代

Python 的 gc 模块采用分代收集：新对象在第 0 代，活得越久越往上搬。新生代扫描频繁、老生代扫描稀疏——因为「活过一轮的对象更可能继续活着」，少扫它们能省 CPU。

🌱
第 0 代
新分配对象，回收最频繁
🌿
第 1 代
挺过一轮 GC 的对象
🌳
第 2 代
长期存活，极少扫描
import gc
print(gc.get_threshold())   # (700, 10, 10) 各代触发阈值
print(gc.get_stats())        # 查看各代回收次数/耗时
gc.collect(0)                # 只回收第 0 代
GC 默认只处理「可能形成循环」的容器（list/dict/set/自定义对象），纯 int/str 不会进 GC。性能敏感场景可用 gc.disable() 关掉、靠引用计数，但要自己保证无循环引用。
弱引用

weakref：引用但不增加计数

弱引用（weakref.ref）指向对象但不增加其引用计数。对象被正常回收后，弱引用自动变 None。它是打破循环引用、做缓存的标准手段。

import weakref
a = {"k": 1}
r = weakref.ref(a)
print(r())            # {'k': 1}
del a
print(r())            # None（原对象已回收）

# 缓存最佳实践：WeakValueDictionary
from weakref import WeakValueDictionary
cache = WeakValueDictionary()   # 值不被引用时自动从缓存移除

和名称绑定与对象语义连起来看：普通赋值建立「强引用」（撑住对象），弱引用则允许对象在别处无人用时被回收。缓存、观察者模式都靠它避免泄漏。

内存池

小块内存走 pymalloc，不找系统要

为减少频繁向 OS 申请/释放内存的开销，CPython 用 pymalloc 管理 ≤512 字节的小对象：在「内存池」里切分复用。大对象才直接走系统 malloc。

对象大小分配器说明
≤ 512 字节pymalloc 内存池按 8 字节对齐的「块」复用，快
> 512 字节系统 malloc/free直接走 C 运行时
同类型小对象free listlist/dict 等维护空闲对象链表，新建省初始化
⚠️ del obj 只是把引用计数 −1，对象是否真释放取决于还有没有人引用它；它不保证立刻归还内存给系统。内存「涨了不降」往往不是泄漏，而是对象还被某处引用着，或内存池还留着备用。

引用计数 + 分代回收的双机制参数

机制默认参数含义
引用计数每个对象维护 ob_refcnt归零立即释放（确定性），但无法处理循环引用
分代回收 gen0 阈值700gen0 对象数减去上次回收后存活数超过 700 时触发 gen0 回收
gen1 阈值10gen0 被回收 10 次后触发一次 gen1
gen2 阈值10gen1 被回收 10 次后触发一次 gen2（全量）
查看/修改gc.get_threshold() / gc.set_threshold(a,b,c)返回 (700, 10, 10)
手动回收gc.collect(gen)gen=2 为全量回收
关闭/冻结gc.freeze()把当前对象移出 GC 追踪，减少后续扫描量

分代假设：越年轻的对象越可能死。新对象进 gen0，存活过一次回收就升代。绝大多数对象活不过 gen0，所以扫描 gen0 就能回收大部分垃圾，代价很低。

能被 GC 回收的对象范围

对象类型引用计数分代 GC 是否追踪说明
int / float / str是否不可变、不可能形成环
list / dict / set是是容器可以持有自身形成环
自定义类实例是是可能有环
tuple是视内容而定含容器元素时会被追踪
带 __del__ 的环是是（但 3.4+ 可解）PEP 442 后大部分环可被回收，但资源释放时机不确定

GC 观测

python - <<'PY'
import gc, sys
print("thresholds:", gc.get_threshold())          # (700, 10, 10)
print("counts:", gc.get_count())                  # (gen0数, gen1数, gen2数)

class Node:
    def __init__(self): self.ref = None

a, b = Node(), Node()
a.ref = b; b.ref = a                              # 循环引用
print("referrers before del:", len(gc.get_referrers(a)))
del a, b                                          # 引用计数不归零，靠 GC 回收
print("collected:", gc.collect())                 # 返回回收的对象数

# 哪些对象在被追踪
print("tracked objects:", len(gc.get_objects()))
gc.freeze()                                       # 启动后冻结，减少后续扫描
print("after freeze, gen0:", gc.get_count())

深入自检

引用计数已经能回收垃圾，为什么还要分代 GC？

因为引用计数处理不了循环引用：a.ref = b 且 b.ref = a 时，即使外部都不再使用，两个对象的计数也都不为零。分代 GC 用可达性分析专门清理这类环。

三个阈值 700/10/10 怎么理解？

gen0 阈值 700：距上次 gen0 回收后新创建并被追踪的对象数超过 700 就触发 gen0 回收；gen1 阈值 10：gen0 回收累计 10 次触发一次 gen1；gen2 阈值 10：gen1 累计 10 次触发全量。用 gc.get_count() 可看当前计数。

gc.collect() 应该经常调用吗？

一般不该。手动全量回收要遍历所有被追踪对象，代价高，而且会打乱分代策略。典型用法是在明确的阶段边界（如批处理结束、fork 子进程前）调用一次，或配合 gc.freeze() 减少常驻对象被反复扫描。

为什么 del 之后 RSS 不下降？

CPython 的 pymalloc 把内存按 arena/pool 管理，归还给解释器内的空闲链表后通常不立即还给操作系统（尤其碎片化时），所以进程 RSS 看起来不降但内存可被后续分配复用。判断内存是否泄露要看趋势与 tracemalloc 的分配来源，而不是单次 RSS。

如何判断是不是真的内存泄漏？

两步：① 用 objgraph.show_growth() 在多次请求/迭代间比较，持续增长的类型就是嫌疑；② 用 tracemalloc 比较两次快照，拿到具体分配栈。若增长类型数稳定、GC 后回落，则只是缓存膨胀而非泄漏。
