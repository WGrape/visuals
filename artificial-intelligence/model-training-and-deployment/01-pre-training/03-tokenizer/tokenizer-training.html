分词器训练
Tokenizer 是怎么"炼"出来的

模型看不懂汉字或字母，只能处理数字。分词器（Tokenizer）负责把文本切成 token——模型能处理的最小单元。它通常在正式预训练之前，用训练语料单独训练，是整个旅程里容易被低估、却直接决定效率与效果的一环。

第 1 步 · 定位

为什么分词器要"先训练"

模型内部全是矩阵运算，喂进去的必须是整数 ID。分词器干两件事：把文本切成词片（token），再映射成 ID。它的切法（词表）直接影响三件事：序列长度、训练成本、跨语言/跨领域效果。

序列长度
切得越碎，同一句话 token 越多，注意力计算量随长度平方增长。
训练成本
token 数 ≈ 算力与金钱。压缩率高，同样的语料 token 更少、更省。
领域效果
医疗/代码分词器能把专业词切成整块，模型更容易学到语义。
它和模型是强绑定的：分词器的词表大小、embedding 矩阵维度必须一致；换分词器通常意味着要重训 embedding 层，甚至部分重训。所以词表设计是"一次定终身"的基建决策。
第 2 步 · 主流算法

BPE / WordPiece / Unigram 怎么选

主流子词（subword）算法都追求同一个目标：高频词保留为整体，低频词拆成小块，从而兼顾词汇表大小和未登录词（OOV）覆盖。三者思路略有不同。

算法核心思路代表特点
BPE
Byte-Pair Encoding		从字符出发，反复把"出现频次最高的相邻对"合并成新符号GPT-2/3/4、Llama、DeepSeek贪心合并，简单稳定，最常用
WordPieceBPE 的变体，合并依据"似然提升"而非纯频次BERT、多语言模型更看重合并带来的概率增益
Unigram
(SentencePiece)		先给一个大词表，再按语言模型概率逐步删掉不重要的符号T5、Llama 2(部分)、多语种基于概率的"自顶向下"裁剪，适合多语言
图 1：BPE 把高频相邻字符对逐步合并成子词，最终得到一张"词表 + 合并规则"
中文通常 1–2 字一个 token，英文一个词约 1–3 个 token；代码因符号多、重复模式明显，对分词器特别敏感（好的代码分词器能显著降本）。
第 3 步 · 动手流程

训练一个分词器的五步

分词器不是"下载的"，是用你的训练语料"练"出来的。标准流程如下：

图 2：分词器训练流水线——语料采样决定词表长什么样，因此必须与模型训练语料同分布
  • ① 采样语料：从训练集里抽样，尽量覆盖真实分布（含代码、多语种）。
  • ② 预切分（pre-tokenization）：先按空格/正则把文本切成"词候选"，再在候选内部合并。
  • ③ 统计频次：BPE 数相邻 pair 频次，Unigram 估每个符号的语言模型概率。
  • ④ 合并 / 裁剪：BPE 反复合并到目标词表大小；Unigram 从大表逐步删到目标大小。
  • ⑤ 保存：产出 vocab.json + merges.txt（或 SentencePiece 的 .model），供训练时调用。
经验：分词器语料 ≈ 模型训练语料的子集且同分布。用中文为主就多采中文，做代码模型就多采代码——否则专业词会被切碎，模型"看不懂"自己的领域。
第 4 步 · 关键决策

vocab_size 与领域适配

词表大小怎么定

  • 太小：序列被切得很碎，上下文变长、算力变贵，且难表达低频专业词。
  • 太大：embedding 表 + 输出投影矩阵变重（词表头是参数量的大头之一），且很多稀有符号用不上，浪费容量。
  • 常见取值：7B 级 32k、大模型 64k~128k；多语种 / 代码模型倾向更大词表以压短序列。

领域适配的两条路

从头训分词器
领域语料与通用语料差异极大时（如纯代码、纯医学），重新训一个专属分词器，但要配套重训 embedding，成本高。
续训 / 扩词表
在开源分词器基础上，加入领域新符号并初始化其 embedding（如从相近 token 平均得到），代价小、更常用。
坑：直接换分词器不重训 embedding，新 token 的向量是随机的，模型会"吐乱码"直到这部分被充分训练。领域续训时务必初始化新 embedding 并多训几步。
第 5 步 · 最小实现

用 tokenizers 库训一个 BPE

from tokenizers import Tokenizer
from tokenizers.models import BPE
from tokenizers.trainers import BpeTrainer

tok = Tokenizer(BPE())   # ① 选模型
trainer = BpeTrainer(vocab_size=32000, special_tokens=["<pad>","<unk>","<bos>","<eos>"])
tok.train(["corpus.txt"], trainer)   # ② 用语料训练
tok.save("tokenizer.json")   # ③ 保存词表+合并规则
Hugging Face 的 tokenizers 库几行就能训出生产级 BPE/WordPiece/Unigram。训练完成后，它产出的 tokenizer.json 会随模型一起发布——推理时用的必须和训练时完全一致的那个分词器，否则 ID 对不上，模型"读不懂"输入。
收尾 · 一句话带走

所以，分词器训练是什么

分词器训练 = 在预训练之前，用训练语料单独练出一个"切词词表"（BPE/WordPiece/Unigram）， 决定文本怎么被切成 token、序列多长、成本多高。它和模型强绑定—— 词表大小与 embedding 必须一致，换分词器往往要重训 embedding。 一句话：分词器是容易被低估的基建，切得好，同样的算力能塞下更多"意思"。

训练一个分词器：参数怎么定

分词器只需要语料和词表大小，但几个参数直接决定模型后来的效率：词表越大，同样文本 token 数越少（推理更快），但 embedding 表和输出层越大（显存更贵）。

参数常见取值影响怎么定
vocab_size32K / 50K / 100K / 128K越大 → 同文本 token 越少、推理越快；但 embedding 参数 = vocab×hidden 越大中文模型普遍要大（汉字信息密度高），32K 会严重膨胀
算法BPE / Unigram / WordPieceBPE 最通用；Unigram(LM) 支持概率采样，可做 subword regularization新模型多用 BPE；SentencePiece 库两者都支持
character_coverage中文/日文 0.9995，英文 1.0控制多少字符被纳入基础字符集，太低会产生大量 <unk>多语种混训练取 0.9999 以上
压缩率基准中文 1 字 ≈ 0.6~1.5 token衡量词表好坏的核心指标拿验证集算 bytes/token，比基准高说明词表不匹配域
模型词表中文压缩率（字/token）备注

训练与评估

# 用 SentencePiece 训练一个 BPE 分词器
spm_train --input=corpus.txt \
          --model_prefix=tok \
          --vocab_size=100000 \
          --character_coverage=0.9995 \
          --model_type=bpe \
          --num_threads=32

# 训练完评估压缩率（关键一步，别只看 loss）
spm_encode --model=tok.model --output_format=piece < dev.txt | wc -l
wc -c < dev.txt      # 字节数 / token 数 = bytes per token

# 常见参考值：
#   英文语料   4~5 bytes/token
#   中文语料   2~3 bytes/token（越大越差，说明拆得太碎）
  • 词表大小必须是 2 的幂附近吗：不是必须，但 embedding 层按 2 的幂对齐能提速（GPU 更高效）。常见做法取 65536 或其倍数。
  • 一定要保留特殊 token：<pad> <unk> <bos> <eos> <mask>，以及你业务要用的（如工具调用的 <|im_start|>）。训练后加不进去。
  • 数字处理：默认会把 12345 拆成 12+345，严重影响算术能力。主流做法是强制按单个数字切分（digit split），LLaMA/Qwen 都这么做。
  • 多语种词表要按语料配比采样：直接把中文语料丢给英文词表训，中文 token 数会膨胀 2~3 倍，推理成本和上下文占用都翻倍。
  • 词表一旦训练完就锁死：后续改词表必须重训模型（embedding 和输出层维度变了）。所以宁可一开始留大一点。
词表是不是越大越好？

不是。三个反作用力：① 显存——embedding + 输出层参数 = 2 × vocab × hidden，128K 词表、4096 hidden 就是 10 亿参数，占了 7B 模型的七分之一；② 长尾 token 训练不充分——低频 token 的 embedding 得不到足够梯度，反而是噪声；③ 输出层 softmax 成本——每步都要对全词表算 logits，词表翻倍这一层计算量就翻倍。所以是权衡：中文/多语种值得开大（100K~150K），纯英文 32K~50K 就够。

为什么中文模型需要更大的词表？

因为 BPE 是靠「合并高频相邻字节对」建词表的，训练语料里中文占比低时，汉字很难被合并成多字词，结果一个汉字被拆成 2~3 个 UTF-8 字节 token。表现就是：同样一段中文，GPT-2 词表要 2.5 倍 token 数，而 Qwen 的 15 万词表接近 1 字 1 token。token 数直接影响上下文窗口能装多少内容、推理要算多少步、以及 API 花多少钱，所以对中文场景词表大小是硬指标。

能复用别人的词表吗？

可以，而且通常是更好的选择：① 省掉训练成本；② 方便做模型间权重迁移和蒸馏；③ 生态兼容（社区已经有适配的推理部署配置）。代价是你的域可能不匹配（比如医疗、代码）。折中做法：在已有词表基础上增量加 token（新增 special token 或高频领域词），只初始化新 token 的 embedding 并继续预训练，比从头训一个词表稳妥得多。
