先建立直觉：快递分拣中心

如果每个商家都要自己给每个客户送货，物流会乱成一团。现实中是：商家把包裹送到分拣中心（Kafka），客户按需来取。

Kafka 就是这个分拣中心：上游系统（埋点、业务库、日志）把数据写进来，下游系统（Flink、Spark、数仓）按需读出去。双方互不感知，可以独立扩缩容。

核心价值：解耦。没有 Kafka 时，N 个上游和 M 个下游要写 N×M 条对接；有了 Kafka，变成 N + M 条。这是实时数据架构选择 Kafka 的根本原因。

分区：吞吐的关键

分区数决定了最大并行度。一个分区同一时刻只能被一个消费者消费（在一个消费者组内），所以 消费者数量 ≤ 分区数 才有意义。想提高吞吐就要增加分区数——但分区不是越多越好。
分区过少分区过多
❌ 并行度不足，吞吐上不去❌ 文件句柄、内存开销增大
❌ 无法水平扩展消费者❌ Leader 选举变慢，恢复时间变长
❌ 端到端延迟增加

经验估算：目标吞吐 ÷ 单分区吞吐（通常几千~几万条/秒），再留出余量。日后可扩容分区，但会改变 key 到分区的映射，影响按 key 保序的场景。

不丢不重：两个配置

① 生产者端防丢：
• acks=all（等所有副本确认，而不是只等 leader）
• retries 设置重试次数
• enable.idempotence=true（幂等生产者，避免重试导致重复）
• 必要时用事务（transactional.id）保证「写 Kafka 与提交 offset」的原子性
② 消费者端防丢/防重：
• 处理完再提交 offset（enable.auto.commit=false + 手动提交），否则可能「提交了但没处理完就崩溃」→ 丢数据
• 若先处理再提交，崩溃会导致「处理了但没提交」→ 重复消费，需要下游幂等（如用主键 upsert）
现实选择：通常保证「不丢」，靠下游幂等解决「重复」。因为精确一次（exactly-once）代价高，而幂等写入（upsert 按主键）通常更简单可靠。

常见坑

  • 消息体过大：默认单条上限 1MB，超限要调 max.request.size，但大消息会显著影响吞吐——建议只传关键字段或传引用。
  • 消费积压：消费者跟不上生产速度，lag 持续增大。要么加消费者（加分区），要么优化消费逻辑。
  • 乱序：Kafka 只保证分区内有序。要全局有序就只能用一个分区（牺牲吞吐）——通常应按业务 key 分区，保证同一 key 有序即可。

🎯 面试问答

Q：分区数怎么定？
A：核心公式：分区数 ≥ 目标吞吐 ÷ 单分区吞吐。单分区吞吐通常在几千到几万条/秒（取决于消息大小和硬件）。同时要考虑消费者数量——一个分区在同一消费组内只能被一个消费者消费，所以分区数也决定了最大并行度。不要盲目设很多：分区过多会增加文件句柄与内存开销、拖慢 Leader 选举。建议先估算、留 2~3 倍余量，并支持后续扩容。

Q：如何保证数据不丢失？
A：两侧都要配置：生产者——acks=all（等所有副本确认）+ 开启幂等（enable.idempotence=true，防重试重复）+ 合理重试次数。消费者——关闭自动提交（enable.auto.commit=false），业务处理成功后再手动提交 offset。另外 broker 端要设置合理的 replication.factor（通常 3）和 min.insync.replicas（通常 2）。

Q：重复消费能完全避免吗？
A：很难完全避免，且代价很高。「处理完 → 提交 offset」这两步不是原子的：处理成功但提交前崩溃，重启后就会重复消费。要做到精确一次需要 Kafka 事务 + 下游支持（如 Flink 的两阶段提交）。工程上更常见的做法：接受「至少一次」语义，让下游写入幂等——比如按主键做 upsert，重复写入结果一致。这样既简单又可靠。

Q：Kafka 能保证全局顺序吗？
A：不能，Kafka 只保证分区内有序。要保证全局顺序，只能用一个分区——但那样就完全没有并行度，吞吐极低。正确做法：按业务 key 分区（如订单 ID），保证「同一个 key 的消息进入同一分区从而有序」，而不同 key 之间可以并行。绝大多数业务真正需要的只是「同一实体的事件有序」，而非全局有序。
