调 SQL 不是猜，是先看 EXPLAIN，再对症下药。这里给一套可复用的读计划方法和常见反模式→改写对照。

01先会读 EXPLAIN

重点看三列：type（访问类型，const>ref>range>index>ALL，ALL 是全表扫描要警惕）、rows（估算扫描行数）、Extra（Using filesort / Using temporary / Using where 都是信号）。

EXPLAIN SELECT * FROM orders WHERE user_id=42 AND status='paid' ORDER BY created_at;
-- 关注：
-- type: 若是 ALL，又没有 Using index，说明没用上索引
-- key:  实际用到的索引（NULL = 没用）
-- rows: 估算行数，越大越慢
-- Extra: Using filesort(额外排序) / Using temporary(用临时表) 都要优化
-- MySQL 8 可用 EXPLAIN ANALYZE 看真实耗时与行数

02常见改写套路

  • 避免 SELECT *：只取需要的列，才可能走覆盖索引（Extra 出现 Using index）。
  • 函数包列会让索引失效：WHERE DATE(created_at)='2026-10-01' → WHERE created_at>='2026-10-01' AND created_at<'2026-10-02'。
  • 大 IN 改成 JOIN 小表，或拆成多批；IN 列表过长优化器会放弃索引。
  • OR 跨不同列常导致全表扫：(a=1 OR b=2) → UNION ALL 两个索引查询。
  • 深分页 LIMIT 100000,20 极慢：改用游标 WHERE id>last_id ORDER BY id LIMIT 20。
要点：索引失效第一元凶：对列做运算/函数、隐式类型转换、前模糊 '%abc'、or 条件组合不当。

03索引提示与覆盖

优化器选错索引时用提示纠正；优先构造覆盖索引避免回表。

-- 强制走某索引（慎用，版本升级后可能失效）
SELECT * FROM orders USE INDEX(idx_user) WHERE user_id=42;
-- 覆盖索引：索引本身含查询所需全部列，无需回表
-- CREATE INDEX idx_cover ON orders(user_id, status, created_at);
-- 这样 (user_id,status) 过滤 + created_at 排序都可在此索引完成

第一层 · 概念与判定：什么时候该重写 SQL

重写信号来自执行计划：全表扫描、嵌套子查询爆炸、深分页、对列套函数导致索引失效。先 EXPLAIN 看 type/rows/Extra，再决定怎么改。

SQL 重写：子查询/JOIN/深分页/函数

-- 1. 子查询改 JOIN（避免 DEPENDENT SUBQUERY 逐行执行）
-- 慢：
SELECT * FROM orders
WHERE user_id IN (SELECT id FROM users WHERE city='BJ');
-- 快：
SELECT o.* FROM orders o
JOIN users u ON o.user_id = u.id AND u.city='BJ';

-- 2. 深分页用 keyset 代替 OFFSET
-- 慢：SELECT * FROM t ORDER BY id LIMIT 10 OFFSET 1000000;
-- 快：
SELECT * FROM t WHERE id > 1000000 ORDER BY id LIMIT 10;

-- 3. 列上别套函数，否则索引失效
-- 慢：WHERE DATE(created) = '2026-01-01'
-- 快：WHERE created >= '2026-01-01' AND created < '2026-01-02'

数量级：深分页 OFFSET 到百万级时，数据库要先扫描并丢弃前 100 万行，耗时从毫秒变秒级；keyseet 改写法把复杂度从 O(offset+n) 降到 O(n)。

第三层 · 排障与边界：四个坑

  • 列上套函数导致索引失效：WHERE DATE(created)=... / WHERE amount*1.1>... 让优化器只能全表扫——把函数移到常量侧
  • 隐式类型转换：字符串列传数字、或反之，MySQL 做转换后索引同样失效——类型要对齐
  • OR 连接非索引列：OR 一端没索引，整体退回全表扫——改 UNION 或补索引
  • 深分页无脑 LIMIT OFFSET：越翻越慢，还占临时空间——上 keyset/游标分页

第四层 · 原理与取舍

为什么嵌套子查询常比 JOIN 慢？

因为早期 MySQL 对 DEPENDENT SUBQUERY 是外层每行都执行一次子查询（O(N×M)），而 JOIN 能让优化器用哈希/索引连接一次性完成（接近 O(N+M)）。改写 JOIN 后优化器还有更多选择（连接顺序、索引），代价模型更准确。所以「子查询改 JOIN」是第一优先的改写。

深分页为什么 OFFSET 越大越慢，keyset 怎么解？

因为 OFFSET 1000000 要求数据库先读出前 100 万行再丢弃，扫描和临时排序成本随 offset 线性涨。keyset 分页用「上一页最后的主键」做 WHERE id > last_id，直接从索引定位起点，跳过前面所有行，复杂度只与本次 LIMIT 有关，与页数无关。

为什么对列套函数会让索引失效？

因为索引是按列的原始值排序的，一旦列被函数处理（DATE()/计算/转换），优化器无法确定索引的有序性还能用，只能放弃索引改全表扫。正确做法是把函数移到等号右边作用在常量上，让列保持「裸」状态参与比较，索引才生效。
