什么时候适用？

判断信号：交互系统需要把输入处理、业务数据与呈现职责分开。

  • Web 控制器查订单后渲染页面
  • 桌面应用的数据变化驱动视图更新
  • 同一模型支持不同界面展示

和相近方案怎么区分？

相近方案选择边界
MVPPresenter 更完整地协调视图，View 通常更被动。
MVVMViewModel 借助数据绑定同步 View，常见于前端与移动端。

最小伪代码

function showOrder(request):
  id = request.path.orderId
  order = orderModel.find(id)
  return orderView.render(order)

边界：Web MVC 常由 Controller 将数据传给 View；传统桌面 MVC 可由 View 观察 Model。

MVC 三角色 Model-View-Controller

用户操作经 Controller，Controller 改 Model，Model 变更通知 View 重绘

Model：业务数据与规则；View：用户界面；Controller：接收输入、调用 Model、选 View。三者各司其职，便于并行开发与测试。

与 MVP / MVVM

  • MVC：View 可直接读 Model（耦合略高）。
  • MVP：Presenter 隔离 View 与 Model，View 被动。
  • MVVM：ViewModel 经数据绑定自动同步 View（前端/移动端常见）。

面试高频问答

Q：MVC 里 View 能不能直接访问 Model？
A：传统 MVC 允许 View 订阅 Model 自动刷新（如桌面控件）；Web MVC 中通常 View 由 Controller 注入数据、不直接读库，以降低耦合。看具体变形。
Q：MVC 属于架构还是设计模式？
A：它介于两者之间，是『架构模式』（组织整个应用的结构），比 GoF 的『设计模式』粒度更大。

MVC：三层分工的由来

MVC 的目标只有一个：把「数据」「展示」「控制」分开，让它们可以独立变化。它诞生于 1979 年 Smalltalk，是最古老也最被误用的架构模式之一。理解它的关键不是记住三个字母，而是理解谁依赖谁、谁通知谁。

经典 MVC：Controller 居中调度，Model 与 View 通过观察者解耦

三层的职责边界（最容易搞混的地方）

层应该做不应该做常见越界症状
Model持有数据、执行业务规则、校验、持久化拼 HTML、读 HTTP 请求、知道界面长什么样实体类里出现 toHtml()、getRequest()、拼接提示文案
View渲染、格式化、展示模型状态、收集用户输入直接查数据库、执行业务计算、修改模型状态模板里写 SQL、在 JSP 里做业务判断（经典的 Model 1 反模式）
Controller解析请求参数、调用 Model、选择 View、处理跳转写业务规则、直接操作数据库、拼装复杂数据Controller 上千行、Service 层只剩一行转发（贫血）

一句话判断：业务规则无论从 Web、命令行、定时任务还是消息触发，都应该是同一份代码——这份代码属于 Model。如果换一种入口就要重写，说明业务漏在 Controller 里了。

MVC 的几种变体

经典 MVC（桌面/前端）

Model 通过观察者主动通知 View 更新。Controller 只负责把用户操作翻译成 Model 调用。

  • Model 与 View 双向：View 读 Model，Model 通知 View
  • 常见于 Swing、早期前端框架、iOS（UIKit）

Web MVC（后端，最主流）

请求-响应模型下，View 无法长期订阅 Model，于是改成「Controller 拿到 Model 数据后推给 View 渲染」。

  • Model 不再主动通知（无长连接），由 Controller 拉取
  • Spring MVC、Django、Rails、ASP.NET MVC 都是这种
  • 所以很多人觉得「MVC 里的 Model 就是数据容器」——这是变体带来的误解

MVP（Model-View-Presenter）

View 与 Model 完全不通信，全部经 Presenter 中转；Presenter 持有 View 接口以便单元测试。

  • 优点：View 极薄、Presenter 可脱离 UI 测试
  • 缺点：Presenter 容易臃肿，接口数量爆炸

MVVM（Model-View-ViewModel）

用数据绑定替代手动同步：ViewModel 暴露可观察属性，View 自动跟着变。

  • Vue、React（配合状态库）、WPF、Android Jetpack 都属此类
  • 双向绑定省代码，但调试困难（不知道是谁改了什么）

为什么你的 MVC 变成了「贫血三层」

最常见的退化形态：Controller → Service → Dao 三层，但 Service 里只有一行 return dao.findById(id)，所有业务判断散落在 Controller 和 SQL 里。这不是分层，这是「穿了三层衣服的二层」。

症状 1Service 没有行为，只有转发；实体类全是 getter/setter（贫血模型）
症状 2业务规则写在 Controller 里，换个入口就要复制一遍
症状 3校验逻辑一半在前端、一半在数据库约束，中间层没有
症状 4单元测试只能测 Dao，因为 Service 没逻辑可测

怎么破：把「这个操作是否允许」「状态怎么流转」「金额怎么算」这类规则放进领域对象里（充血模型），Service 只做编排（加载对象 → 调用对象方法 → 持久化）。判断标准：这条规则能不能脱离数据库单独测试？能，说明它在正确的位置。

Web MVC 的实际请求链路

HTTP Request ↓ DispatcherServlet（前端控制器） ↓ HandlerMapping：URL → Controller 方法 ↓ 参数绑定 / 数据校验 / 类型转换 ↓ Controller：调用 Service（业务编排） ↓ Service：领域对象执行业务规则 → Repository 持久化 ↓ 返回 ModelAndView 或 @ResponseBody 的 DTO ↓ ViewResolver：选择视图 / HttpMessageConverter 序列化 HTTP Response // 横切关注点由拦截器/切面处理，不污染 Controller： // 鉴权、日志、限流、事务、异常处理（@ControllerAdvice）

深入自检

MVC 和三层架构（表现层/业务层/数据层）是一回事吗？

不是，粒度和视角都不同。三层架构是按职责的纵向分层，描述请求从界面到数据库经过的层次，关注「数据往哪流」；MVC 是表现层内部的组织方式，关注「界面与数据如何解耦」。典型组合是：表现层用 MVC，下面是业务层（Service/Domain）与数据访问层（Dao/Repository）。所以两者是互补而非互斥——说「我们用三层架构」和「表现层用 MVC」并不冲突。

前后端分离后还需要 MVC 吗？

后端还需要，但 View 的含义变了。前后端分离后后端不再渲染 HTML，View 变成了「JSON/DTO 序列化」，Controller 直接返回数据（@RestController）。此时后端实际是 MC 两层 + 下面的 Service/Repository。前端则独立演进出了自己的 MVVM（Vue/React 组件 + 状态管理）。所以 MVC 没有消失，而是被拆到了两端：前端 MVVM 负责界面，后端 MVC 负责接口与业务编排。

Model 到底是不是数据库表？

不是，这是最常见的误解。Model 是「领域模型」，包含数据与行为（业务规则）。数据库表只是它的一种持久化形式。实践中常把 Model 拆成几种对象：① Entity/DO——与表结构对应，持久化用；② Domain——含业务行为的领域对象（真正的 Model）；③ DTO/VO——跨层或跨服务传输用；④ ViewModel——界面展示用。混淆这些对象（尤其是把 DO 直接返回给前端）会导致数据库结构外泄、接口难以演进。

Controller 里能不能写业务逻辑？

原则上不能，但现实中有灰色地带。判断标准：这段逻辑是否只服务于这个 HTTP 接口？如果是「参数格式转换、分页参数处理、HTTP 状态码选择」这类与协议强相关的，放 Controller 合理；如果是「订单能否取消、折扣怎么算、库存是否充足」这类业务规则，必须下沉到 Service/Domain——因为定时任务、消息消费、RPC 调用都可能触发同样的规则，放在 Controller 就必然重复。一个简单的检验：把 Controller 的代码复制到一个单元测试里，能不能不启动 Web 容器就跑通？
