①五类约束的语义差别

约束保证什么NULL 处理实现依赖
PRIMARY KEY唯一且非空隐含 NOT NULL唯一索引（InnoDB 下即聚簇索引）
UNIQUE唯一多数实现允许多个 NULL唯一索引
NOT NULL列不可为 NULL—列属性
FOREIGN KEY值必须在父表存在含 NULL 的外键行不校验需在父表被引用列上有索引
CHECK表达式为真表达式为 NULL 时视为通过MySQL 8.0.16 起才真正强制执行
两条容易被忽略的 NULL 规则： ① UNIQUE 允许多个 NULL——想让「邮箱唯一但可为空」就得接受多个空邮箱， 或用部分唯一索引（WHERE email IS NOT NULL）绕开； ② CHECK 遇到 NULL 视为通过——CHECK (age > 0) 拦不住 age IS NULL， 必须同时加 NOT NULL。

②外键：要不要用

这是争议最大的一条。技术上的取舍很清楚，工程上取决于团队与规模。

用的理由

数据库层面保证引用完整性，杜绝孤儿数据；级联删除/更新语义明确； 减少应用层重复校验代码；数据比代码活得久。

不用的理由

每次写都要查父表，有额外开销；锁范围扩大（插入子表要锁父表对应行）， 并发下更容易死锁；阻碍分库分表与在线 DDL；批量导入要按依赖顺序或临时关闭检查。

实践口径：单体库、团队规模小、强一致要求高 → 用外键，代价可控收益明确。 高并发写入、要分库分表、有复杂迁移流程 → 不用外键，改由应用层保证并加定期巡检任务查孤儿数据。 中间形态：核心关联表用外键，日志/流水类不用。关键是团队内统一，不要一半一半。
CREATE TABLE order_item (
  id         BIGINT PRIMARY KEY,
  order_id   BIGINT NOT NULL,
  CONSTRAINT fk_item_order FOREIGN KEY (order_id)
    REFERENCES orders(id) ON DELETE CASCADE
);
-- ON DELETE 可选：RESTRICT(默认，阻止) / CASCADE(级联删) / SET NULL / NO ACTION
-- ⚠️ 级联删除会静默删掉大量子表数据，生产上慎用，建议改为业务层软删除

③主键选型：自增 vs UUID vs 雪花

方案优点缺点适用
自增 BIGINT AUTO_INCREMENT顺序写入、页分裂少、索引紧凑、范围查询友好分库分表需额外分配机制；ID 可推测（暴露业务量）单体库首选
UUID v4全局唯一、可客户端生成、不可推测36 字节、完全随机 → 聚簇索引页分裂严重、缓存命中率低尽量避免作聚簇主键
UUID v7 / ULID全局唯一 + 时间有序，缓解随机写问题仍比 BIGINT 宽，生态支持较新分布式且必须客户端生成 ID
雪花 ID（Snowflake）8 字节、趋势递增、含时间信息依赖机器号分配与时钟，时钟回拨要处理分布式系统主流
MySQL InnoDB 下随机主键的代价被严重低估。聚簇索引按主键物理排序， 随机 ID 的插入会落在任意页中间，导致频繁页分裂、碎片化、缓冲池命中率下降， 写入吞吐可能差一个数量级。如果必须用 UUID，至少用 v7/ULID，或把它当业务唯一键而另设自增聚簇主键。

④约束与性能、迁移

  • 唯一约束 = 唯一索引，有写放大与空间成本；高并发下唯一性检查可能成为热点 （如秒杀场景对同一商品 ID 的插入）。
  • 外键列必须自己建索引。InnoDB 会自动为外键列建索引，但删除约束后不会自动清理； 其他引擎/库可能完全不自动建，导致级联删除时全表扫父表。
  • 批量导入：临时禁用外键检查（SET FOREIGN_KEY_CHECKS=0）可大幅提速， 但导入后必须重新校验引用完整性，否则会留下脏数据。
  • 加约束会全表校验。给已有大表加 UNIQUE 或 NOT NULL 前， 先跑一遍 SELECT 确认没有违反数据，否则 DDL 会在扫完大半后才失败。
  • 约束是最后一道防线，不是业务逻辑。"金额不能为负"这类规则应同时在应用层校验 （给用户友好报错）和数据库层约束（保证任何写入路径都拦得住）。
Q：CHECK 约束 MySQL 老版本不生效怎么办？
A：8.0.16 之前的 MySQL 会解析但忽略 CHECK。替代方案： 用 ENUM/触发器模拟，或依赖应用层校验 + 定期巡检 SQL。
Q：唯一索引冲突该怎么处理？
A：两条路径：① 业务上确实不该重复 → 捕获唯一键冲突错误返回友好提示（幂等设计的一部分）； ② 语义是「存在则更新」 → 用 UPSERT（见下一篇）。不要用先 SELECT 再 INSERT 的方式，那有并发竞态。

约束类型与开销

约束作用检查时机性能开销
PRIMARY KEY唯一且非空，决定物理存储顺序（InnoDB）每次写入建索引，必要开销
UNIQUE唯一（允许多个 NULL）每次写入建索引，同 PK
NOT NULL禁止空值每次写入几乎为零
FOREIGN KEY引用完整性每次写入都要查父表较高，且会加锁
CHECK自定义条件每次写入低（但 8.0.16 前被忽略）
DEFAULT默认值插入时零

约束定义

-- MySQL 的重要历史坑：8.0.16 之前 CHECK 约束会被<strong>解析但忽略</strong>
CREATE TABLE t (age INT, CHECK (age > 0));   -- 5.7 里这行完全不生效！
-- 所以老版本只能靠触发器或应用层保证

-- 外键的隐藏代价：会在父表上加<strong>共享锁</strong>
-- 子表插入时，需要确认父表记录存在 → 对父行加 S 锁
-- 高并发下这会成为死锁来源，且难以排查

-- 查看某表的所有约束
SELECT constraint_name, constraint_type, table_name
FROM information_schema.table_constraints
WHERE table_schema = 'mydb';

外键为何在生产常被禁用：三个原因——① 性能：每次写入都要额外查父表并加锁；② 死锁：外键的隐式锁增加死锁概率；③ 运维：分库分表、数据迁移、批量导入时外键是巨大阻碍。所以互联网公司普遍在应用层保证引用完整性，数据库只留 PK/UNIQUE/NOT NULL。

NULL 与唯一索引的交互

数据库唯一索引中的 NULL说明
MySQL允许多个 NULLNULL 不参与唯一性比较
PostgreSQL允许多个 NULL同上（15 版起可用 NULLS NOT DISTINCT 改变）
SQL Server只允许一个 NULL行为不同，迁移时必踩
Oracle允许多个 NULL同 MySQL

NULL 与唯一索引

-- 陷阱：想做“手机号唯一但允许未填写”，结果填了多个 NULL 不报错
CREATE TABLE users (phone VARCHAR(20) UNIQUE);
INSERT INTO users (phone) VALUES (NULL);   -- 成功
INSERT INTO users (phone) VALUES (NULL);   -- <strong>也成功！</strong>

-- 正确做法：用空串或哨兵值代替 NULL
ALTER TABLE users MODIFY phone VARCHAR(20) NOT NULL DEFAULT '';
-- 此时唯一约束才会真正生效（空串会重复检查）

-- 或用部分唯一索引（PostgreSQL）
CREATE UNIQUE INDEX idx_phone ON users(phone) WHERE phone IS NOT NULL;

约束的在线变更

操作安全做法风险
加 NOT NULL先加可空 → 分批回填 → 再加约束直接加会锁表且失败
加 UNIQUE先查重（GROUP BY ... HAVING count>1）有重复数据会失败
加外键先清理孤儿数据有孤儿行会失败
删约束直接删元数据风险低

变更前置检查

-- 加唯一索引前必做的查重
SELECT email, COUNT(*) c FROM users GROUP BY email HAVING c > 1 LIMIT 10;
-- 有结果说明已存在重复，必须先清洗才能加 UNIQUE

-- 加外键前必做的孤儿检查
SELECT c.* FROM orders c
LEFT JOIN users p ON c.user_id = p.id
WHERE c.user_id IS NOT NULL AND p.id IS NULL;
-- 有结果 → 存在引用不存在的用户，加外键会失败

-- MySQL 8.0 支持在线加 NOT NULL（前提是数据已满足）
ALTER TABLE users MODIFY email VARCHAR(100) NOT NULL, ALGORITHM=INPLACE;

自检 Q&A

Q：主键该用自增还是 UUID？

A：优先自增（BIGINT）。原因是 InnoDB 的聚簇索引按主键顺序存储：自增 ID 是顺序写入，页利用率高、几乎无页分裂；UUID 是随机的，每次插入可能落在任意页，导致频繁页分裂、碎片化、缓存命中率下降，写入性能可能差 2~5 倍，表体积也明显更大。若必须用 UUID（如分布式 ID），至少用时间有序的 UUIDv7/雪花 ID，或把 UUID 作为唯一索引而主键仍用自增。

Q：CHECK 约束遇到 NULL 会怎样？

A：视为通过。因为 NULL > 0 的结果是 UNKNOWN，SQL 里 UNKNOWN 不被视为违反约束。所以 CHECK(age > 0) 挡不住 age = NULL 的插入。要真正约束必须同时声明 NOT NULL：age INT NOT NULL CHECK (age > 0)。这是三值逻辑在约束上的直接体现。

Q：唯一索引和唯一约束有什么区别？

A：MySQL 里几乎没区别——声明 UNIQUE 约束时会自动创建同名唯一索引，物理上完全一样。真正的区别在语义与外键引用：唯一约束可以被外键引用，唯一索引不能（标准 SQL 层面）。PostgreSQL 里两者都是用唯一索引实现，但 information_schema 中分类不同。实践中不用纠结，直接用 UNIQUE 约束声明即可。

Q：为什么不推荐在数据库层做业务校验？

A：要看校验的性质。结构性约束（非空、唯一、引用）放数据库是对的——数据库是最后防线，能挡住所有写入路径（包括手工 SQL、数据迁移工具）。但业务规则（如优惠券每人限领 3 张、余额不能为负）放数据库会让规则分散、难以测试、难以变更，且很多规则需要跨表跨服务判断，数据库表达不了。判据：能用一行约束表达的放数据库，需要逻辑判断的放应用层。
