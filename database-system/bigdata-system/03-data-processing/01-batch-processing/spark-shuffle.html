04 批处理计算 · Shuffle 与分区

Spark Shuffle 到底发生了什么
为什么它是 Spark 最贵的操作

一句 groupBy 或 join 就能让原本跑 3 分钟的作业变成 30 分钟。这个"突然变慢"的开关就是 Shuffle：它强制把数据按 key 重新洗牌，跨网络、跨磁盘搬一遍。本文把 Shuffle 的两端（Map 端写、Reduce 端读）拆开讲清楚，说清它到底在哪些地方花掉了时间，以及为什么"AQE + 广播 join + 预聚合"能救命。

1Shuffle 是什么：一句话定义

Shuffle（洗牌）= 把数据按 key 重新分发，让"相同 key 的所有记录"最终落到同一个分区里。

为什么必须要洗牌？要算 groupBy(city).sum(amount)，就必须保证"所有 city='BJ' 的记录"在同一个计算任务里才能求和。但数据原本按文件块分散在 100 台机器上，BJ 的记录散落各处。Shuffle 就是那个"把散落的同 key 数据聚到一起"的动作——它无法避免，只能优化。

哪些操作会触发 Shuffle

算子是否 Shuffle说明
groupByKey / reduceByKey / aggregateByKey是按 key 聚合，必须重分发
join / leftOuterJoin / cogroup是两张表按 join key 对齐
distinct是本质是按整行做 groupBy
repartition(n)是强制全量重分区（含随机打散）
sortBy / orderBy是全局排序需范围重分布
coalesce(n)（减少分区）否只合并已有分区，不跨节点搬数据
map / filter / flatMap否窄依赖，一条进一条出，原地算
union否只是把分区拼起来
宽依赖 vs 窄依赖触发 Shuffle 的算子产生宽依赖（父分区被多个子分区依赖，Stage 必须在此切开）；不触发的产生窄依赖（一对一或多对一，可在同一 Stage 内流水线执行）。Stage 的边界就是 Shuffle 的边界——你在 Spark UI 上看到几个 Stage，基本就是几次 Shuffle + 1。

2Shuffle 全景：Map 端写 + Reduce 端读

Shuffle 的两阶段：Map 端按分区写好放本地，Reduce 端跨网络去拉

3Map 端（Shuffle Write）内部细节

每个 Map Task 都要为下游 R 个 Reduce 各准备一份数据。Spark 的做法不是"开 R 个文件"，而是内存中分区 + 排序 → 溢写 → 最后合并成一对文件。

三个关键设计

🗂 只产出 2 个文件

每个 Map Task 最终只写 1 个 .data + 1 个 .index。所有 Reduce 分区的数据段顺序拼在 .data 里，.index 记录每段起始偏移。这样文件数从 M×R 降到 2×M，彻底解决了早期 Hash Shuffle 的文件句柄爆炸问题。

📐 排序（可关）

默认按 partitionId + key 排序落盘，好处是 Reduce 端归并代价低、且能提前聚合。但排序本身要 CPU。若下游不需要排序（如 groupBy 后直接写文件），可关掉排序换 CPU。

⚡ Map 端预聚合

reduceByKey 会先在 Map 端对每个桶内做一次局部合并再发送，网络传输量骤降。groupByKey 不会预聚合，全量搬运——这是两者性能差距巨大的根本原因。

经典坑：groupByKey vs reduceByKey
同样是"按 key 求和"，groupByKey 把每个 key 的全部原始值都搬到 Reduce 端（10 亿条 → 搬 10 亿条）；reduceByKey 在 Map 端先局部 sum（10 亿条 → 每个 Map 每 key 只发 1 条）。能用 reduceByKey / aggregateByKey，永远不要写 groupByKey。

4Reduce 端（Shuffle Read）内部细节

  1. 发请求：Reduce Task 启动后，先向 Driver 的 MapOutputTracker 查询"每个 Map Task 在哪台机器、哪个文件"，然后向所有 Map 所在节点发起拉取。
  2. 边拉边聚合：数据到达后进入内存缓冲区，reduceByKey 类算子会边拉边做 combine，把内存占用压住。
  3. 内存不够就溢写：缓冲满了就排序后溢写到磁盘，最后把所有溢写段 + 内存中的数据做多路归并，得到按 key 有序的结果。
  4. 输出：归并后的结果交给下游算子，或写为新的 RDD 分区。
为什么 Reduce 端容易 OOM？如果某个 key 的数据量极大（数据倾斜），那么这一个 Reduce Task 要拉取的数据量就是其他的成百上千倍——缓冲区撑爆、溢写写满本地磁盘、且整个 Stage 要等它一个人跑完。这就是为什么倾斜会让作业"卡在最后 1 个 Task 上 99%"。

5Shuffle 的演进：四种实现

实现核心思路文件数状态
Hash Shuffle
（Spark 0.8 之前）		每个 Map 为每个 Reduce 各写一个独立文件M × R已废弃。1000 Map × 1000 Reduce = 100 万个文件，句柄与随机写直接崩溃
Consolidated Hash Shuffle同核上先后执行的 Map 复用同一批文件C × R（C=核数）缓解但未根治，已废弃
Sort Shuffle
（Spark 1.2+ 默认）		内存分区 → 排序 → 溢写 → 合并成 data+index 两个文件2 × M当前默认。文件数与 R 无关，顺序 IO
Tungsten Sort Shuffle操作二进制页而非 Java 对象，避开反序列化与 GC2 × M自动启用（条件满足时）：无聚合、无排序、分区数 < 16777216
Push-based Shuffle
（Spark 3.2+）		Map 端主动推送并合并到中间 External Shuffle Service，而非 Reduce 来拉合并后更少适合超大规模 Shuffle（数千 Executor），减少随机小 IO

6怎么优化：从最有效到最次要

🥇 广播 join 代替 Shuffle join

小表（默认 < 10MB，可调 spark.sql.autoBroadcastJoinThreshold）直接广播到每个 Executor 内存，大表原地查，完全没有 Shuffle。收益最大，永远优先检查这一条。

🥈 能预聚合就预聚合

reduceByKey / aggregateByKey 代替 groupByKey；SQL 里优先让 SUM/COUNT 在 Map 端先合并（Spark 会自动做部分聚合）。

🥉 先过滤再 Shuffle

把 filter / 列裁剪尽量提前。Shuffle 的数据量 = 参与的数据行数 × 列宽，能在洗牌前砍掉 90% 行，Shuffle 就省 90%。

4️⃣ 合理设置分区数

spark.sql.shuffle.partitions 默认 200——小数据量时 200 个空任务纯浪费；大数据量时又太少导致单 Task 过大。经验值：总数据量 / 每个 Task 期望处理 128~256MB。

5️⃣ 开启 AQE（自适应查询执行）

Spark 3.0+ spark.sql.adaptive.enabled=true。它能在运行时看到真实数据量后：自动合并过小的分区、自动拆分倾斜分区、自动把 SortMergeJoin 转成 BroadcastJoin。现代 Spark 强烈建议开启。

6️⃣ 解决数据倾斜

加盐（salt）打散热点 key、两阶段聚合、广播小表、开启 AQE 倾斜处理。详见本学科「数据倾斜」专题。

// 典型生产配置（Spark 3.x）
spark.sql.adaptive.enabled=true                    // 开 AQE
spark.sql.adaptive.skewJoin.enabled=true           // 自动处理 join 倾斜
spark.sql.adaptive.coalescePartitions.enabled=true // 自动合并小分区
spark.sql.autoBroadcastJoinThreshold=64MB          // 放宽广播阈值
spark.sql.shuffle.partitions=800                   // 按数据量估算
spark.shuffle.file.buffer=1m                       // Map 端写缓冲
spark.reducer.maxSizeInFlight=96m                  // Reduce 单次拉取上限

7常见误区

"Shuffle 慢就是网络慢，加带宽就好"
不一定。Shuffle 的瓶颈常常是磁盘随机 IO（Reduce 从 N 台机器各拉一小段 = 大量小随机读）和 CPU（排序、序列化、压缩）。盲目加带宽收益有限，更有效的是减少 Shuffle 数据量本身（广播、预聚合、提前过滤）。
"分区数越多越并行，就越快"
错。分区数 R 决定了：文件段数 = M×R（虽合并但段变多）、Reduce Task 数（调度开销）、每个 Task 的数据量。R 过大 → 海量小 Task、元数据爆炸、小文件问题；过小 → 单 Task 数据过大、容易 OOM、并行度不足。让单个 Task 处理 128~256MB 是常用起点。
"repartition 和 coalesce 差不多"
完全不同。repartition(n) 一定触发全量 Shuffle（因为它要保证数据均匀分布，会做随机打散）；coalesce(n) 减少分区时只把相邻分区合并，不 Shuffle。想减少分区用 coalesce，想重新打散（比如解决倾斜）才用 repartition。
"Shuffle 数据一定会落盘，很安全不会丢"
落盘不等于不重算。Shuffle 中间文件写在 Executor 本地磁盘。如果 Executor 所在节点宕机、或开启了动态资源回收把 Executor 撤掉，那些文件就没了——Spark 会重新调度上游 Stage 重算一遍（这就是 Stage 重试 代价巨大的原因）。生产上常配合 External Shuffle Service，让文件生命周期脱离 Executor。
