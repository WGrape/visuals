DNSSEC 验证链：RRSIG、DNSKEY 与 DS 怎样防止假答案

从根域到业务域手推信任链，并解释 SERVFAIL、密钥轮换和不加密的边界。

要防的是被伪造的解析结果

DNS 查询可能经过递归解析器和网络路径，攻击者若能让客户端接受假的 A 记录，就可能把用户导向错误地址。DNSSEC 让区域的权威数据附带数字签名，验证解析器可检查数据来源和完整性，拒绝无法通过信任链验证的答案。它不加密查询名称，旁观者仍可能看到传统 DNS 流量；若要保护客户端到解析器的通道，还需 DoT/DoH 等机制。

DNSSEC 也不证明网站内容可信或 TLS 证书正确。它只能确认 DNS 数据与已签名区域的授权链一致。域名被合法管理员错误配置成恶意 IP，签名仍可能有效；应用仍要验证 HTTPS 证书和业务身份。

三种记录各做什么

DNSKEY 公布区域用于验证签名的公钥；RRSIG 对具体记录集提供签名；父区域里的 DS 记录把对子区域关键 DNSKEY 的摘要纳入父级签名体系。验证解析器从已知的根信任锚出发，检查根到顶级域、顶级域到业务域的 DS/DNSKEY 关系，再验证目标 A 或 AAAA 记录集的 RRSIG。只有链条连续、签名和有效期正确，才可称该答案被验证。

不能只在业务域放一把 DNSKEY 就宣布全网会信任它。若父区域没有相应 DS，验证链可能止于父级，子区域可能被视为未签名而非已验证；若父级 DS 指向旧密钥而子区域已换新，验证会失败。部署时必须协调注册商或父区的 DS 更新。

一次假 A 记录的尝试

攻击者向验证解析器注入 `api.example.test A 203.0.113.66`，却没有该记录集对应的有效 RRSIG。解析器从信任链找到业务域 DNSKEY 后，签名校验不通过，拒绝把假答案作为有效结果返回。若客户端使用不验证的解析器，它可能仍受缓存投毒或其他伪造影响；因此要确认实际递归解析器确实开启验证。

DNSSEC 可认证不存在记录的否定回答，常通过 NSEC/NSEC3 等记录证明某个名字或类型不存在，防止攻击者随意伪造 NXDOMAIN。否定证明具体实现较复杂，但排障至少要区分“被验证的不存在”和“签名链坏了导致 SERVFAIL”。

为什么会出现 SERVFAIL

验证解析器若看到签名过期、签名尚未生效、DS 与 DNSKEY 不匹配、必要 DNSKEY 或 RRSIG 记录缺失，可能返回 SERVFAIL，而不是给出被认为不可信的答案。没有验证的解析器可能仍返回 A 记录，造成“某些网络能访问、某些网络不行”。此时不能简单关掉验证，先对比权威记录、父区 DS、系统时间和签名有效期。

时间错误尤其隐蔽：签名有生效与到期时间，权威服务器或验证解析器时钟异常都可能引发失败。大 DNSSEC 应答还可能触发 UDP 截断与 TCP 回退，因此需要确保 DNS TCP 通路可用。

密钥轮换与撤销

轮换密钥需要给缓存传播和父区 DS 更新留重叠窗口。若先删除旧 DNSKEY、旧 DS 仍被递归解析器缓存，会形成断链；若新 DS 已发布而子区尚未提供新密钥，也会失败。应规划发布、等待缓存、切换签名、更新 DS、观察验证成功率，再移除旧材料的顺序。具体 KSK/ZSK 策略依 DNS 平台而异，不能只在一个控制台点击“更新”就认为全链完成。

私钥应严密保护，DNSKEY 公钥则可公开。若签名私钥泄漏，需要按既定轮换和事件响应流程处理；继续使用被盗密钥会让攻击者伪造看似合法的记录。

如何验证与验收

从权威服务器查目标记录、RRSIG、DNSKEY，并从父区查 DS；再用开启验证的递归解析器查询目标名称。分别测试正常存在、无记录、密钥轮换期间和故意错误的测试区域，记录结果是可验证、不安全但可解析，还是验证失败。浏览器网页能打开只证明某条解析与 HTTPS 路径工作，不证明 DNSSEC 已开启。

运行监控应看签名到期、父区 DS 匹配、验证失败率与权威查询时延。把 DNSSEC、DoH/DoT 和 TLS 放在一张信任边界图里，才能说明每一段保护了什么。

自检

DoH 已加密，为什么还可能需要 DNSSEC？

DoH 保护客户端到解析器的传输；DNSSEC 验证权威数据的签名链，解决的是不同信任边界。
