微服务：拆分的收益与代价同样真实

微服务不是「把单体拆小」这么简单，它是一整套组织 + 技术 + 运维的变革。Martin Fowler 的总结很中肯：微服务的好处只有在你同时具备自动化部署、监控、快速恢复能力时才能兑现；否则你只会得到一个「分布式单体」——比单体更难维护。

单体 vs 微服务：拆开的每个服务都需要配套基础设施

什么时候该拆：五个信号

信号具体表现说明
团队协作受阻几十人在一个代码库，发布互相排队，冲突频繁康威定律：组织结构会反映到系统结构
发布频率受限改一行要全站回归、全站发布、全站回滚独立部署是微服务最大的工程收益
模块资源需求不同某模块是 CPU 密集，某模块是内存密集，某模块流量是百倍差异需要独立扩缩容
故障域过大一个模块的 bug 导致整个应用崩溃拆分后故障被隔离
技术栈需要差异化某模块要 GPU、要特定语言、要特定存储单体难以容纳异构技术

反向信号（不该拆）：团队小于 10 人、业务还在快速试错、没有自动化运维能力、模块边界还不清晰、强一致事务是核心。这些条件下应该先做「模块化单体」——在单体内部划清模块边界，等条件成熟再拆。

怎么拆：边界划分的三个依据

① 按业务能力（推荐）

围绕「这个服务能独立提供什么业务价值」划分，如用户、订单、库存、支付、物流。

  • 优势：边界稳定（业务能力比技术实现稳定得多）
  • 与 DDD 的限界上下文（Bounded Context）天然契合

② 按领域子域（DDD）

把领域分成核心域（竞争力所在）、支撑域、通用域，核心域重点投入。

  • 优势：资源投入有侧重，核心域可自研，通用域可买
  • 子域 → 限界上下文 → 服务，是一条清晰的推导链

③ 按数据所有权

最硬的判据：谁能改这份数据，谁就是它的主人。

  • 每个服务独占自己的数据库，其他服务只能通过 API 访问
  • 如果两个服务都要写同一张表，说明边界划错了
  • 共享数据库是微服务最常见的失败模式——它让服务在数据库层面重新耦合

反面教材：按技术层拆

拆成「Controller 服务」「Service 服务」「Dao 服务」是典型错误。

  • 一次业务要跨三个服务，延迟与复杂度暴涨
  • 改一个业务要同时改三个服务并协调发布
  • 这叫「分布式单体」，比单体更糟

必须配套的基础设施

微服务把复杂度从代码转移到了基础设施。下面这些缺一项就会在生产上付出代价：

服务发现实例动态上下线，必须自动感知（Nacos / Eureka / Consul / K8s Service）
配置中心配置不能散落在各服务，要集中管理并支持动态刷新
API 网关统一入口，收敛鉴权、限流、路由、日志
熔断限流降级防止故障沿调用链扩散（Sentinel / Resilience4j / Istio）
链路追踪跨服务定位问题的唯一手段（TraceId 贯穿，Jaeger / SkyWalking）
日志聚合日志分散在各实例，必须集中检索（ELK / Loki）
监控告警指标、日志、追踪三件套 + 业务指标大盘
CI/CD 与编排独立部署的前提（Jenkins/GitLab CI + Kubernetes）
分布式事务方案Saga / TCC / 事务消息 + 幂等 + 对账

重要提醒：如果团队还没有上述设施，不要先拆微服务。正确顺序是先建基础设施（至少监控 + 发布流水线 + 链路追踪），再拆服务。

微服务的真实代价

  • 网络调用不可靠。函数变 RPC，多了超时、重试、幂等、序列化、服务发现一整套问题。
  • 分布式事务难。原本一个数据库事务解决的事，现在要 Saga 补偿 + 幂等 + 对账。
  • 调试变难。没有调用栈，一次请求跨十几个服务，必须靠 TraceId 串联；本地难以复现全链路。
  • 运维复杂度的量级提升。服务数量 × 每个服务都要监控、告警、发布、扩容、日志。
  • 数据一致性天然变弱。跨服务查询不能 JOIN，要做数据冗余或聚合服务，冗余就有同步延迟。
  • 测试成本高。集成测试要起多个服务，契约测试（Pact）成为必需。
  • 不是拆得越细越好。服务过细会导致「一次下单调 20 个服务」，延迟与故障率随调用链长度指数上升。适度聚合比过度拆分更实用。

深入自检

微服务和 SOA 有什么区别？

两者思想同源（都是把系统拆成可复用的服务），但实施重点差别明显：SOA 强调服务复用与企业级集成，通常用重量级的 ESB（企业服务总线）做集中编排、协议转换与消息路由，服务之间依赖智能管道；微服务强调团队自治与独立交付，主张「哑管道 + 智能端点」——去掉 ESB，用轻量 HTTP/gRPC 与消息中间件直连，每个服务拥有自己的数据库，可独立部署。另外微服务更强调去中心化治理：不要求全公司统一技术栈，各团队自选。可以说微服务是 SOA 思想在「轻量协议 + 容器化 + DevOps」条件下的一次重新落地。

服务拆分后，跨服务的查询怎么办？

三种主流做法：① API 组合（最常用）——由一个聚合服务（或 BFF）分别调用各服务再拼装，简单直接，缺点是延迟累加、可用性是各服务的乘积；② 数据冗余/读模型——各服务订阅事件，在本地维护一份查询所需的冗余数据（CQRS 思路），查询本地完成，速度快但有一致性延迟；③ 共享报表库/数据湖——把各服务数据同步到统一的分析存储（ES、ClickHouse、数仓），服务于复杂查询与报表，不适合实时业务。选择取决于查询的实时性要求与复杂度。

每个服务都必须有自己的数据库吗？

这是微服务的重要原则（Database per Service），但不是绝对的教条。独占数据库的价值在于：数据所有权清晰、schema 可独立演进、服务可独立扩展、避免数据库层面的隐式耦合。违反它的代价是服务表面上分开了，实际仍靠共享表耦合，改一次 schema 要协调多个团队——这是最常见的微服务失败模式。例外情况：报表类只读共享库、遗留系统过渡期的临时共享。但核心业务数据建议严格独占，通过 API 或事件对外提供。

怎么避免拆出「分布式单体」？

分布式单体的特征是：服务分开了，但任何改动都要同时修改并协调发布多个服务。避免方法：① 边界按业务能力而非技术层划分；② 严格执行数据所有权独占；③ 服务间只通过稳定的 API / 事件契约通信，不共享库表与内部模型；④ 允许服务间有适度的冗余，而不是把所有公共逻辑都抽成共享库（共享库会变成新的耦合源）；⑤ 每个服务可由一个团队独立开发、测试、部署——如果做不到，说明边界划错了；⑥ 用契约测试保证接口演进不破坏调用方。检验标准很简单：「一个常见需求变更，需要修改并协调发布几个服务？」答案是 1 才是健康的。
