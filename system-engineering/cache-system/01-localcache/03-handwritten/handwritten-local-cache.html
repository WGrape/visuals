先建立直觉：一个会自己整理的抽屉

最朴素的写法是 Map<K,V>，但它只进不出，迟早撑爆内存。一个可用的本地缓存，本质上是「一个会自己整理的抽屉」——满了要扔东西，过期了要清理，多人同时开抽屉不能打架。

要解决的四件事：

  1. 容量控制：最多放多少？超了淘汰谁？
  2. 过期清理：TTL 到了怎么发现？
  3. 并发安全：多线程同时读写怎么办？
  4. 淘汰策略：LRU / LFU / FIFO 选哪个？

版本一：Map + 容量检查（不可用，但能看清问题）

type SimpleCache struct {
    mu   sync.Mutex
    data map[string]item
    cap  int
}

func (c *SimpleCache) Get(k string) (any, bool) {
    c.mu.Lock(); defer c.mu.Unlock()
    it, ok := c.data[k]
    if !ok { return nil, false }
    if time.Now().After(it.expire) {   // 惰性删除：发现过期就删
        delete(c.data, k)
        return nil, false
    }
    return it.val, true
}
三个问题：① 全局一把锁，高并发下所有读写串行，性能极差；② 只有惰性删除——过期但永不被访问的数据会一直占着内存；③ 没有淘汰策略，满了之后直接拒绝或无限增长。

版本二：可用的实现

① 并发：用分段锁代替全局锁

把数据分成 N 个段（shard），每段一把锁。不同段的访问互不干扰，并发度提升 N 倍。这是 ConcurrentHashMap 和 Caffeine 的思路。

const shardCount = 32   // 通常取 2 的幂，便于位运算定位

type ShardedCache struct {
    shards [shardCount]*shard
}
type shard struct {
    mu   sync.RWMutex    // 读多写少，用读写锁
    data map[string]item
}

func (c *ShardedCache) shardFor(k string) *shard {
    h := fnv32(k)
    return c.shards[h % shardCount]   // 或 h & (shardCount-1)
}
为什么用读写锁？缓存的典型负载是读远多于写。RWMutex 允许多个读并发，只在写时独占，比 Mutex 吞吐高得多。

② 过期：惰性删除 + 定期清理

方式做法优点缺点
惰性删除Get 时检查是否过期，过期就删零额外开销不访问的过期数据永不释放
定期删除后台协程定时扫描一小批，删除过期的能回收冷数据有扫描开销
必须两者结合。只用惰性 → 内存泄漏；只用定期 → 扫描成本高且清理不及时。实践：定期任务每次只扫一小部分（分批处理），且限制单次耗时，避免影响主流程。

③ 淘汰：LRU 是最省事的选择

容量满了要淘汰。最简单有效的是 LRU（哈希表 + 双向链表，O(1)）。详见「手写 LRU」。

还缺什么才能上生产

缺失项说明
命中率统计没有它就无法判断缓存是否有效
加载保护防止缓存击穿（同一个 key 只有一次回源）
空值缓存防止缓存穿透
容量按权重不同 value 大小不同，应按字节数而非条目数限容
淘汰回调淘汰时释放资源（如关闭文件句柄）
预热与持久化重启后快速恢复
结论：手写实现适合学习原理和极简场景。生产环境应直接使用成熟库：Java 用 Caffeine（W-TinyLFU，命中率高）、Go 用 ristretto / freecache / bigcache。它们解决了上面所有问题，且经过大量生产验证。

🎯 面试问答

Q：为什么不能直接用 map 加一把大锁？
A：性能问题：所有读写串行化，高并发下锁争用成为瓶颈，多核优势完全发挥不出来。解法是分段锁（sharding）：把数据分成 32 或 64 段，每段独立加锁，不同 key 大概率落在不同段，并发度提升几十倍。这是 ConcurrentHashMap、Caffeine、Go 的 bigcache 等的标准做法。

Q：为什么惰性删除不够，还要定期清理？
A：因为惰性删除只有在 key 被访问时才会触发。如果一个 key 写入后再也没人读，它即使早已过期也会永远占着内存——这就是内存泄漏。在「写入多、访问少」或「一次性写入」的场景下，泄漏会非常严重。定期清理负责扫描并回收这些「没人关心的过期数据」，两者缺一不可。

Q：容量限制应该按条目数还是按内存大小？
A：理想情况按内存大小（字节权重）。因为 value 大小可能相差极大——1000 条 1KB 的数据和 1000 条 1MB 的数据，占用差 1000 倍，按条目限容会严重失控。但精确统计字节数有开销，所以很多实现采用折中：按条目限容 + 限制单条最大尺寸，或用估算的权重。Caffeine 支持 weigher 自定义权重，Go 的 freecache 则直接按字节管理。

Q：生产上到底该自己写还是用库？
A：用库。手写代码的价值是理解「容量、过期、并发、淘汰」这四件事为什么必须同时解决——这是面试和理解原理的好素材。但生产要的是经过验证的实现：Caffeine（Java）、ristretto/bigcache/freecache（Go）。它们还额外提供了命中率统计、加载保护、异步淘汰等能力，自己补齐这些的成本远高于直接用库。
