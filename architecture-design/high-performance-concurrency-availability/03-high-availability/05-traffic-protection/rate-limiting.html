限流（Rate Limiting）

当流量超过系统承载能力，与其被压垮，不如主动拒绝一部分。限流是保护系统的第一道闸门。本文讲清三种经典算法：令牌桶、漏桶、滑动窗口。

🎯为什么需要限流

系统容量有限。突发流量（秒杀、爬虫、重试风暴）会瞬间打满 CPU/连接/线程，引发雪崩。限流 = "量力而行，超了就拒"。

🧭
核心思想：用有损服务换系统存活。拒绝 10% 的请求，好过 100% 请求都超时、整站不可用。

🎟️令牌桶（Token Bucket）

以固定速率往桶里放令牌，请求来了先拿令牌，拿到才放行，拿不到就拒绝。桶有容量上限，可应对突发。

特点：允许突发（桶里攒着的令牌可瞬间消费）；长期速率受限。最常用（Guava RateLimiter、Sentinel 都支持）。

🪣漏桶（Leaky Bucket）

请求像水倒入桶，桶以恒定速率漏出（处理）。桶满则溢出（拒绝）。强调"恒定输出速率"，平滑流量。

特点：不管入水多猛，出水速率恒定 → 绝对平滑，但不支持突发（多余的水直接溢出）。适合"必须匀速"的场景（如网络流量整形）。
⚖️
令牌桶 vs 漏桶：令牌桶"进可突发、出受限"；漏桶"进可接受、出恒定"。一个保突发、一个保平滑，按需选用。

🪟滑动窗口（Sliding Window）

把时间切成小格，统计"最近一个时间窗口内"的请求数，超过阈值就拒绝。比固定窗口更精准。

方式说明问题
固定窗口每 1 秒最多 N 次窗口临界处可能双倍放行（如 0.9s 和 1.1s 各 N 次）
滑动窗口统计最近 N 秒请求数更平滑、无临界突刺，但需记录时间戳、稍重
✅
实践：Redis 的 INCR + EXPIRE 可做简单固定窗口；滑动窗口常用 Redis Sorted Set（zset）存时间戳，统计窗口内数量。更省内存的变体是滑动日志/滑动计数器。

⚖️三者对比

算法突发平滑实现难度典型
令牌桶✅ 支持中中Guava/Sentinel
漏桶❌ 不支持强中网络整形
滑动窗口❌强略高Redis zset

🌐分布式限流

单机限流无法约束"集群总流量"。分布式限流需要一个全局计数器，通常借助 Redis 或专门的限流组件。

方案：① 集中式（所有节点向 Redis 原子计数，如 Lua 脚本保证原子）；② 网关层限流（在 API 网关统一做，最省心）；③ 分桶（按用户/IP 维度分别限流，防单用户打爆）。
🧩
维度：限流可分 QPS（每秒请求数）、并发数（同时处理数）、连接数。热点用户/接口还要做"细粒度限流"（如单用户每分钟 100 次）。

🎯面试要点速记

目的：用有损服务换系统存活，防雪崩。
令牌桶：按速率发令牌，桶有容量→支持突发。
漏桶：恒定速率流出→绝对平滑，不支持突发。
滑动窗口：统计最近窗口请求数，比固定窗口更准，无临界突刺。
分布式：用 Redis/Lua 或网关层做全局计数，可分维度限流。
维度：QPS / 并发 / 连接；按用户/接口/IP 细分。
🔥
必考题："令牌桶和漏桶的区别？"——令牌桶进可突发（攒令牌瞬间消费）、漏桶出恒定（绝对平滑）。一个适合"允许短时高峰"，一个适合"必须匀速"。

限流放在哪一层，比用什么算法更关键

同样的令牌桶算法，放在不同位置效果完全不同：越早拦截，浪费的资源越少。在网关就把流量挡掉，后面的服务、缓存、数据库都不用付出代价。

限流的五道闸门：越靠外越便宜，越靠内越精准

四种算法的取舍：记住各自的一句话

算法之间没有优劣，只有适配的场景。判断的切入点是两个问题：要不要允许突发？输出是否匀速？

算法核心机制能否突发输出是否匀速典型场景
固定窗口计数每段时间一个计数器，到点清零边界处可翻倍否实现最简单，要求不高的粗限流
滑动窗口把窗口切成小格，按格加权统计少量较平滑需要更准确计数，且要控制内存
令牌桶按速率往桶里放令牌，取到才放行能突发，最多一桶否最常见：允许短时突发，长期受控
漏桶请求入桶，按固定速率漏出处理不能是需要严格匀速，保护下游恒定速率
// 令牌桶（Redis + Lua，保证原子性） -- KEYS[1]=桶的 key ARGV[1]=速率(个/秒) ARGV[2]=桶容量 ARGV[3]=当前时间戳(毫秒) local rate = tonumber(ARGV[1]) local cap = tonumber(ARGV[2]) local now = tonumber(ARGV[3]) local b = redis.call("HMGET", KEYS[1], "tokens", "ts") local tokens = tonumber(b[1]) local ts = tonumber(b[2]) if tokens == nil then tokens, ts = cap, now end -- 按时间差补充令牌，但不超过桶容量 local delta = math.max(0, now - ts) / 1000 tokens = math.min(cap, tokens + delta * rate) if tokens < 1 then redis.call("HMSET", KEYS[1], "tokens", tokens, "ts", now) return 0 -- 拒绝 end redis.call("HMSET", KEYS[1], "tokens", tokens - 1, "ts", now) return 1 -- 放行 -- 关键点：读-算-写必须在一个 Lua 里完成，否则并发下会超发

限流、熔断、降级不是一回事

限流：管住自己被多少人叫

针对外部进来的流量，按配额拒绝超额部分，保护自己不被压垮。触发条件是「量太大」，动作是拒绝一部分请求。

熔断：管住自己去叫谁

针对自己调用的下游，当下游错误率或延迟超阈值时快速失败，给下游恢复时间。触发条件是「下游不健康」，动作是暂时不再调用。

降级：少做一点也要给出结果

在资源紧张或依赖不可用时，主动关闭非关键能力，保证核心流程可用。触发条件是「资源不够或依赖挂了」，动作是削减功能而非拒绝全部。

三者的关系是层层收敛：限流挡住进来的、熔断切断出去的、降级保证剩下的还能用。只做限流不做熔断，下游故障时仍然会在超时上浪费资源。

分布式限流的三种做法与代价

单机均摊总数除以机器数，简单但机器数变化就不准
中心计数Redis 集中计数，准确但每次请求多一次网络往返
批量取令牌一次取一批本地慢慢用，兼顾准确与性能
本地 + 定期同步本地计数、周期性上报校准，容忍短时误差
按维度限流用户、租户、接口、IP 分开设限，避免互相影响
拒绝也要快被限流的请求要立刻返回，不要排队
返回重试时间带上提示，避免客户端无脑重试
留观测限流触发量本身就是要监控的信号
限流阈值定多少合适？

从容量评估的结果倒推：取系统在满足延迟目标前提下的可持续吞吐，再留出突发余量。凭感觉拍一个数字，要么浪费容量，要么挡不住。更稳的做法是配合自适应限流，按实测延迟动态收窄。

被限流的请求应该排队还是直接拒绝？

绝大多数场景直接拒绝更好。排队会把延迟转移成更长的等待，而且队列本身会占资源，容易演变成拥塞。只有确实不能失败的任务才考虑排队。

为什么固定窗口在边界处会翻倍？

因为计数在窗口切换时清零。如果在第一段的末尾来了一批、第二段的开头又来了一批，两段各自都没超限，但合起来在极短时间内通过了双倍流量。滑动窗口与令牌桶都是为了解决这个边界问题。

令牌桶允许突发会不会打垮下游？

会，如果桶容量设得过大。桶容量决定了瞬时可放过的最大量，保护恒速下游时应该用漏桶或把桶容量调小；允许突发的场景才把容量放大。
