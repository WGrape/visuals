一句话总结：ClickHouse 里 MergeTree 存数据，Distributed 只是逻辑视图——它不存数据，只负责把查询拆到各分片并行执行、再把结果汇聚。

01单机与集群：两种引擎

📦 MergeTree（及家族）

真正存数据的引擎，落在本地磁盘。单机能跑，但容量和算力受单机限制。

🌐 Distributed

逻辑引擎，不存数据。它指向一组分片（本地表），负责把查询分发和汇聚。可以把它理解为"集群的视图"。

所以集群部署的典型形态是：每个节点上既有本地 MergeTree 表（存数据），再建一个 Distributed 表（对外查询入口）。

02分片（Shard）

分片是数据的水平拆分：按 sharding_key（如 `rand()` 或某列 hash）把数据分布到不同分片，突破单机容量。每个分片可以有多副本。

  • 分片数决定总容量和并行度。
  • 分片键选择影响数据均衡：用随机或高基数列，避免热点分片。

03副本（Replica）

副本是同一分片的冗余拷贝，用 ReplicatedMergeTree 引擎，基于 ZooKeeper / ClickHouse Keeper 同步元数据与数据块。

  • 写入落到任一副本，由 Keeper 协调同步到其他副本。
  • 读可以从任一健康副本取，实现读横向扩展与高可用。
  • 一个副本宕机，其他副本继续服务；恢复后自动补齐。

04Distributed 查询路由

查询下发到各分片并行，结果在发起节点汇聚

查询经过 Distributed 表时：把 SQL 改写后下发到各分片并行执行，分片返回中间结果，由发起节点（initiator）汇聚、合并、排序/截断。大数据集的汇聚可能落盘，是聚合查询的潜在瓶颈点。

05写入怎么写

方式取舍
写本地表（推荐）客户端按 sharding_key 自己路由到目标分片写入，不经过 Distributed，避免分布式表做写入缓冲导致的不一致和阻塞
写 Distributed 表方便但会把写入先缓在某一节点再分发，易积压、易丢；一般不作为高频写入入口
写入 + 副本同步写一份副本即可，Keeper 协调同步到其他副本；注意副本延迟

06常见坑

🌀 数据分布不均

sharding_key 选错导致某分片远大于其他，成为热点与容量瓶颈。

🐢 副本延迟

读副本若延迟大，可能读到旧数据；写后立刻跨副本读需谨慎。

🧱 Keeper 瓶颈

Keeper 是元数据与协调中枢，负载过高会成为整集群瓶颈，需独立部署与监控。

07常见疑问

Distributed 表会存数据吗？
不会。它只是把查询路由到背后各分片的本地表，本身不持有数据。删掉 Distributed 表不会丢数据。
为什么推荐写本地表而不是 Distributed 表？
Distributed 表做写入时会先缓在接收节点再异步分发，既增加延迟又可能在节点故障时丢数据；直写本地表让数据按分片键直接落位，路径更短更可靠。
副本数越多越好吗？
副本提升可用性和读吞吐，但每次写入都要同步到更多副本，写延迟和 Keeper 压力上升。一般 2~3 副本是常见平衡。

部署与运维清单

项建议
分片键高基数 / 随机（rand() 或 hash(高基列)），避免热点
副本数2~3，平衡可用性与写成本
Keeper独立部署、奇数节点、单独监控；它是集群中枢
写入入口直写本地表；勿把 Distributed 当高频写入缓冲
汇聚保护控制单查询返回行数，必要时分页/限流，避免 initiator 落盘爆炸
Distributed 表查询为什么有时慢在"汇聚"？

各分片并行算完之后，发起节点要把所有分片的部分结果合并（排序、聚合、去重、LIMIT）。如果结果集巨大或涉及全局去重（如 DISTINCT），汇聚阶段会成为瓶颈，甚至落盘。优化思路：让各分片尽量完成本地聚合（两阶段聚合）、减少返回列与行数、必要时用物化视图预聚合。

深度补充：ClickHouse 分布式表与分片副本

第一层 · 概念与判定 Distributed 表是“逻辑视图”，本身不存数据，把查询路由到各分片的本地表。判定：写优先直写本地表（{shard}），读才走 Distributed，避免双写放大。

对象作用注意
Distributed 表跨分片路由查询不存数据
本地表（MergeTree）真实存数据按分片键分布
分片键rand() 或 hash(列)决定均衡
副本ReplicatedMergeTree + Keeper需 Zoo/Keeper

第三层 · 排障与边界

  • 经 Distributed 写入会先在接收节点缓存再异步分发，增加延迟且故障可能丢。
  • 跨分片 JOIN 默认 broadcast/segment，大表 JOIN 易 OOM，改用本地表或 colocate。
  • 副本依赖 Keeper（ZooKeeper 替代），Keeper 抖动会卡写入。
  • 分片键选错导致数据倾斜，需重建表重导。
第四层 · 原理与取舍

Distributed 用“逻辑分片 + 查询时路由”实现水平扩展，代价是协调节点要做汇总、跨分片操作复杂。直写本地表把数据按分片键直接落位，路径最短最可靠；走 Distributed 写入只适合简单入口场景。权衡是“入口便利 vs 写入可靠性与延迟”，高吞吐写入几乎都选直写本地表 + 异步分发。

实例与速查：ClickHouse 建表

-- 1) 本地表（真实存数据，按分片键分布）
CREATE TABLE local_orders ON CLUSTER ck
(
  id UInt64, user_id UInt64, amount Decimal(18,2), ts DateTime
)
ENGINE = ReplicatedMergeTree('/ck/t/{shard}/local_orders','{replica}')
PARTITION BY toYYYYMM(ts) ORDER BY (user_id, id);

-- 2) Distributed 逻辑表（不存数据，路由查询）
CREATE TABLE dist_orders ON CLUSTER ck
AS local_orders
ENGINE = Distributed(ck, default, local_orders, rand());
  • 写入优先直写本地表（按分片键落位），别全走 Distributed 缓存再分发。
  • 跨分片 JOIN 大表易 OOM，改用 colocate 或分别查询后应用层合并。
  • 副本依赖 Keeper，Keeper 抖动会卡写入。
FAQ：为什么经 Distributed 写入会变慢还可能丢？

Distributed 表自身不存数据，写入时先在接收节点缓存、再异步分发到各分片，增加一层延迟；若接收节点在分发前故障，缓存数据会丢失。直写本地表让数据按分片键直接落位，路径最短、最可靠，是高吞吐写入的推荐方式。

常见误区与延伸

  • 误区一：所有写入都走 Distributed 表。Distributed 只路由不存数据，写入会缓存再异步分发，增延迟且有丢数风险。
  • 误区二：Distributed 表能替代本地表。它只是逻辑视图，真实数据在本地表（MergeTree）上。
  • 延伸：ReplicatedMergeTree 依赖 Keeper 做副本元数据协调，Keeper 抖动会直接卡写入。
  • 延伸：分片键选错导致倾斜，需重建表并重导，所以建表前务必想清分片与桶数。

一句话总结：高吞吐写入直写本地表、查询走 Distributed；Distributed 是路由层不是存储层，分片键与副本策略在建表时一次定好。

决策速记

  • 写入直写本地表：路径最短最可靠，别全走 Distributed。
  • 查询走 Distributed：它是路由视图，不存数据。
  • 依赖 Keeper：副本元数据协调，Keeper 抖动卡写入。
  • 定分片键：选错需重建重导，建表前想清分片与桶。

一句话：高吞吐写本地、查分布式；Distributed 是路由层不是存储层。

横向对比与追问

  • 与 TiDB 比：TiDB 用 Region 自动分片，CK 要手动建 Distributed + 本地表，运维心智不同。
  • 与 Doris 比：Doris 的 tablet 均衡自动化程度更高，CK 的分片键与副本需手动规划。
  • 追问：为什么 CK 强调直写本地表？因为 Distributed 写入有缓存与丢数风险，直写最可靠。
  • 追问：ReplicatedMergeTree 为什么依赖 Keeper？副本元数据与选主都靠它协调。

小结：CK 的高性能来自“分片并行 + 列存”，但分片键与副本策略要在建表时定好。
