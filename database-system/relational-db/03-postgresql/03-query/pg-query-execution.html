① 从 SQL 到结果：五阶段

与 MySQL 的一个显著差异：PG 的 DDL 也在事务里，可以 BEGIN; ALTER TABLE ...; ROLLBACK;，这在迁移脚本中非常实用。

② 三种表扫描方式

方式何时使用代价特征
Seq Scan 全表扫描返回比例大（通常 > 5%~10%）、无可用索引、表很小顺序 IO，单行成本高但无随机跳转
Index Scan 索引扫描选择性好（返回少量行）随机 IO：索引查到 ctid 后回表，可能放大
Index Only Scan所需列都在索引中 且 可见性映射已设置不回表，最快；依赖 VACUUM 更新 VM
Bitmap Index/Heap Scan中等选择性（返回较多但非全表）先位图化再按物理顺序读，把随机 IO 变顺序 IO
为什么有时候有索引却走了全表扫描？优化器估算返回行数占比：若超过约 5%~10%，Index Scan 的随机 IO 代价会超过顺序扫描，此时全表扫描确实更快。random_page_cost（默认 4.0）是这一判断的关键参数——使用 SSD 时应调低到 1.1~1.5，否则优化器会过度偏好全表扫描。

③ JOIN 的三种算法

算法适用代价内存
Nested Loop外表行数少、内表有索引O(N × log M)极小
Hash Join大表与大表等值连接，无索引O(N + M)需 work_mem 放哈希表
Merge Join两侧已有序（索引扫描或已排序）O(N + M)（含排序代价）小
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders o JOIN users u ON u.id = o.user_id WHERE o.status='paid';

-- 典型计划片段
-- Hash Join  (cost=.. rows=..) (actual time=.. rows=..)
--   Hash Cond: (o.user_id = u.id)
--   ->  Seq Scan on orders o   (rows=50000)
--   ->  Hash  (rows=10000)     Batches: 1  Memory Usage: 890kB
--        ->  Seq Scan on users u
Hash Join 的致命信号：Batches: N（N>1）。这说明哈希表放不下 work_mem，被切分成多个批次并写入临时文件，性能会显著下降。对策：① 增大该会话的 work_mem；② 减少参与 JOIN 的列（只选需要的列）；③ 让小表更小（先过滤再 JOIN）；④ 给小表的连接键建索引，引导优化器走 Nested Loop。

④ 读懂 EXPLAIN

EXPLAIN (ANALYZE, BUFFERS, VERBOSE, FORMAT TEXT) SELECT ...;

-- 关键字段解读
-- cost=0.43..1234.56    启动代价..总代价（单位 arbitrary，用于比较）
-- rows=1000             优化器估计的返回行数
-- width=48              估计的平均行宽（字节）
-- actual time=0.05..8.7 实际启动..完成时间（毫秒，累计！）
-- rows=982              实际返回行数
-- loops=3               该节点被执行的次数（嵌套循环内会被多次执行）
-- Buffers: shared hit=120 read=35   缓存命中 120 页、磁盘读 35 页
观察点判断处理
rows 估计 vs 实际 差 10 倍以上统计信息过期或选择性估算失误ANALYZE 表名；或调 default_statistics_target；或用扩展统计（多列相关）
Seq Scan 出现在大表上缺索引 / 索引不可用 / 返回比例大补索引；检查是否对列用了函数导致失效
Hash Join 出现 Batches>1work_mem 不足增大 work_mem 或减少数据量
actual time 在某节点特别高瓶颈节点针对该节点优化（索引、改写、预聚合）
shared read 很大缓存命中低增大 shared_buffers、优化访问路径、预热
多列相关性陷阱：优化器默认假设各列独立。若 city 与 zip 高度相关，WHERE city='北京' AND zip='100000' 的选择性会被严重低估（估出远多于实际的行数）。解法：CREATE STATISTICS s1 (dependencies) ON city, zip FROM t; ANALYZE t;

⑤ 并行查询

PG 9.6+ 支持单查询内的并行：由 leader 进程 + 若干 worker 协作（Gather / Gather Merge 节点）。

-- 关键参数
SHOW max_parallel_workers_per_gather;   -- 单个 Gather 最多几个 worker（默认 2）
SHOW max_parallel_workers;              -- 实例总并行 worker（默认 8）
SHOW max_worker_processes;              -- 后台进程总上限（默认 8）
SHOW parallel_setup_cost;               -- 启动并行的代价（默认 1000）
SHOW parallel_tuple_cost;               -- 每行传递代价（默认 0.1）
SHOW min_parallel_table_scan_size;      -- 表多大才考虑并行（默认 8MB）

-- 临时关闭并行做对比测试
SET max_parallel_workers_per_gather = 0;

能并行

Seq Scan、Bitmap Heap Scan、Hash Join、Aggregate、某些排序

不能并行

Index Scan（并行 index scan 有限制）、游标 FETCH、写操作

调优

OLAP 场景可调大 worker 数；OLTP 高并发场景建议调小，避免抢资源

内存

每个 worker 都会单独使用 work_mem，内存要按 worker 数放大估算

⑥ 常见问法

Q：为什么有索引却还是走全表扫描？

A：三种常见原因：① 返回比例大——索引扫描需要随机回表，当返回行数占比超过约 5%~10%，随机 IO 的总代价高于顺序扫描，此时全表扫描确实更快（这是优化器的正确判断，不是 bug）；② 索引不可用——对列使用了函数（WHERE lower(name)=?）、类型不匹配（varchar 列与数字比较）、或使用了 LIKE '%x%'；③ 统计信息过期，导致行数估计错误。排查：先看 EXPLAIN 中 rows 的估计与实际是否吻合，再针对性处理；SSD 环境记得把 random_page_cost 从默认 4.0 调到 1.1~1.5。

Q：Index Scan、Index Only Scan、Bitmap Scan 有什么区别？

A：Index Scan：按索引顺序逐个取 ctid 回表，随机 IO，适合返回少量行；Index Only Scan：所需列全在索引里，完全不回表，最快，但依赖可见性映射（VM）已设置——所以要及时 VACUUM；Bitmap Scan：先在位图中收集所有符合条件的 ctid，再按物理顺序回表，把随机 IO 转成近似顺序 IO，适合中等选择性（返回几百到几万行）。选择逻辑基本是：少量 → Index；中量 → Bitmap；大量 → Seq。

Q：Hash Join 出现 Batches > 1 说明什么？

A：说明哈希表无法放入 work_mem，被切分成多个批次，部分数据要写入磁盘临时文件，性能明显下降（可能慢数倍）。对策：① 提高该会话的 work_mem；② 只 SELECT 需要的列（减小哈希表）；③ 先过滤再 JOIN，让「小表」更小；④ 给连接键建索引引导走 Nested Loop；⑤ 若是多列 JOIN 导致行宽过大，考虑拆分。实践：报表类会话可单独 SET work_mem='256MB'，全局保持保守。

Q：EXPLAIN 里的 cost 和实际时间单位是什么？怎么看瓶颈？

A：cost 是优化器内部的无量纲估算值（以顺序读一个页为 1.0 基准），只能用于比较不同计划；actual time 才是真实毫秒，且是累计值（父节点包含子节点耗时，需配合缩进看）。找瓶颈的方法：① 看 actual time 最大值所在节点；② 注意 loops（嵌套循环内节点会被执行多次，实际总耗时 = time × loops）；③ 比较 rows 的估计值与实际值，差 10 倍以上说明统计信息有问题；④ 看 Buffers 的 read（磁盘读）判断缓存命中。

Q：什么是扩展统计（Extended Statistics）？什么时候需要？

A：优化器默认假设各列相互独立。当列之间存在相关性（如 city 决定 zip、status 与 created_at 相关）时，多条件的选择性会被严重低估或高估，导致计划错误。PG 10+ 提供扩展统计解决：CREATE STATISTICS s (dependencies, ndistinct) ON city, zip FROM t; ANALYZE t;。dependencies 记录函数依赖（用于修正多列 AND 条件的选择性），ndistinct 记录列组合的不同值个数（用于 GROUP BY 估算）。判断信号：EXPLAIN 中多列条件后的 rows 估计与实际差一个数量级以上。

Q：并行查询该怎么调？为什么 OLTP 场景反而要关小？

A：并行查询适合大表扫描、聚合、OLAP，可显著缩短单查询耗时；但它会一次性占用多个 worker 进程与多份 work_mem，在高并发 OLTP 下会抢走大量资源，导致其它请求变慢、整体吞吐下降。调优建议：① OLAP/报表库把 max_parallel_workers_per_gather 调到 4~8；② OLTP 库保持 0~2，或直接对关键路径关闭；③ 注意 max_worker_processes 是全局上限，包含并行与后台进程；④ 内存规划要按「worker 数 × work_mem」计算，避免 OOM。
