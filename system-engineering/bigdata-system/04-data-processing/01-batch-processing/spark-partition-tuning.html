Spark 分区数、AQE 与数据倾斜调优

从单分区大小和慢任务证据判断是否该调整分区或作业计划。

关键参数与并行度

参数默认值调优建议
spark.sql.shuffle.partitions200最常调；数据量大时设 400~2000
spark.executor.memory1g4~8g 常见
spark.executor.cores12~5；超过 5 会导致 HDFS 吞吐下降
spark.executor.memoryOverheadmax(384m, 10%)堆外不足会被 YARN kill
spark.default.parallelism集群核数RDD 操作的默认分区数
spark.sql.adaptive.enabledfalse强烈建议开启（AQE）

关键配置

# 并行度的经验公式
#   目标分区数 ≈ 总核数 × 2~4
#   单分区大小建议 128 MB（与 HDFS 块对齐）
#   例：1 TB 数据 → 约 8000 个分区

spark-submit \
  --master yarn --deploy-mode cluster \
  --executor-memory 8g --executor-cores 4 --num-executors 25 \
  --conf spark.sql.shuffle.partitions=1000 \
  --conf spark.sql.adaptive.enabled=true \        # AQE：自动合并小分区、处理倾斜
  --conf spark.sql.adaptive.skewJoin.enabled=true \
  --conf spark.serializer=org.apache.spark.serializer.KryoSerializer \
  app.jar

# AQE（自适应查询执行，3.0+）能自动做三件事：
#   1) 合并 shuffle 后的小分区（解决小文件问题）
#   2) 倾斜 join 自动拆分（解决数据倾斜）
#   3) 运行时切换 join 策略
# <strong>开启 AQE 通常无需其他调优就能获得明显提升</strong>

自检 Q&A

Q：Executor 数量与并行度怎么配？

A：并行度 = 分区数，不是 executor 数。Executor 提供的是执行槽位（cores），若分区数远小于总核数，核会闲置。经验：分区数 ≈ 总核数 × 2~4。单 executor 的 cores 建议 2~5——超过 5 时，单个 JVM 内的多线程会争抢 HDFS 连接与 GC 资源，吞吐反而下降。

Q：为什么我的 Spark 作业 90% 的时间花在 GC 上？

A：典型原因是数据都堆在 JVM 堆里（用了 RDD 或缓存了大量对象）。三种解法——① 改用 DataFrame（Tungsten 用堆外内存 + 二进制格式，对象开销极小）；② 减少 cache/persist，或改用 MEMORY_AND_DISK_SER（序列化后存，体积小但读取要反序列化）；③ 调大 executor 内存或改用 G1GC。最根本的是 ①。

Q：shuffle.partitions=200 什么时候要改？

A：几乎总是要改。200 是通用默认值，但——数据量小时（几百 MB）200 个分区会产生大量小文件，应调小到 20~50；数据量大时（TB 级）200 个分区意味着单分区几 GB，会 OOM 或极慢，应调大到 1000~5000。判据是单分区目标 128 MB：分区数 = 总数据量 / 128 MB。开 AQE 后可以让引擎自动合并小分区，容错性更好。

Q：Spark 比 Hive 快在哪？

A：核心是内存计算 + DAG 调度。Hive 把每个 MR 作业的中间结果落盘，多个作业串联时 IO 开销巨大；Spark 把整个 DAG 放在内存里，中间结果能复用就不落盘，只在 shuffle 时写盘。此外 Spark 有线程级的任务调度（MR 是进程级，启动开销大）与 Catalyst 优化。典型提速 3~10 倍，但数据量远超内存时优势会缩小（都要落盘）。
