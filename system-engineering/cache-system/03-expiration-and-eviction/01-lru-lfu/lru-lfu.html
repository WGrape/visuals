🧹 LRU vs LFU：该淘汰谁

内存满了要淘汰数据。LRU 淘汰「最久没用」的，LFU 淘汰「用得最少」的——两者各有盲区。

各自盲区

批量扫描 / 历史包袱

先建立直觉：整理你的书桌

书桌只能放 5 本书。新书来了要挤掉一本，你挤掉哪本？

  • LRU 的思路：挤掉最久没翻过的那本。假设是「最近翻过的书，接下来还会翻」。
  • LFU 的思路：挤掉翻的次数最少的那本。假设是「翻得多的书更重要」。

两种想法都合理，但都会在特定情况下出错。

LRU：最近最少使用

LRU（Least Recently Used）维护一个按访问时间排序的链表：每次访问把数据移到头部，淘汰时从尾部删除。

优点：实现简单（哈希表 + 双向链表，O(1) 访问与更新），对时间局部性好的负载命中率很高。
盲区：一次性的批量扫描（如全表遍历、离线任务）会访问大量只会被用一次的数据，这些数据把真正的热数据挤到尾部淘汰掉，导致缓存污染。此外它无法区分「访问 1000 次的老热点」和「刚访问 1 次的新数据」。

LFU：最不经常使用

LFU（Least Frequently Used）为每个 key 维护访问计数，淘汰计数最小的。它认为「访问频次高 = 更重要」。

优点：能识别真正的热点，抗批量扫描——因为扫描来的数据计数只有 1，很快被淘汰，不会挤掉高频热点。
盲区一：历史包袱。一个昨天很热、今天无人问津的数据，累积了很高的计数，会长期赖在缓存里出不去。需要老化机制（定期衰减计数）来缓解。
盲区二：新数据饥饿。刚进入缓存的数据计数为 0 或 1，很容易在下一次淘汰时被优先踢掉，永远来不及积累热度。这对「新内容需要曝光」的场景（如新发布文章、新品）很不友好。

工程上的折中

因为两者各有盲区，实际系统很少用「纯 LRU」或「纯 LFU」：

  • Redis：采用近似 LRU——不维护全局链表，而是随机采样若干个 key（默认 5 个，可配置），淘汰其中最久未访问的。用极低的精度损失换取巨大的性能提升。Redis 4.0 起也支持 LFU 模式（用 Morris 计数器做概率递增 + 时间衰减）。
  • Caffeine：使用 W-TinyLFU——用 TinyLFU（Count-Min Sketch）做准入判断，配合 LRU 段做淘汰，兼顾频次与新鲜度，命中率显著高于纯 LRU。
  • ARC：同时维护 LRU 和 LFU 两个队列，根据实际命中情况动态调整两者比例。
选型直觉：大多数场景 LRU 已足够好且最便宜；若负载有明显的热点且存在批量扫描，考虑 LFU 或 W-TinyLFU；不要为了让「算法先进」而增加复杂度。

🎯 面试问答

Q：LRU 为什么会被批量扫描污染？
A：因为 LRU 只看最近一次访问时间，不看访问次数。一次全表扫描会顺序访问几百万条数据，每条都被「刚访问过」，于是它们占据链表头部；而真正的热数据被挤到尾部，在扫描期间被逐个淘汰。扫描结束后，缓存里全是再也不会被访问第二次的冷数据，命中率断崖式下跌。

Q：LFU 的新数据为什么会被饿死？
A：因为新数据刚进缓存时计数是 0 或 1，而老数据已经累积了很高的计数。淘汰时总是挑计数最小的，新数据还没来得及积累热度就被踢掉。解决办法通常是：给新数据一个初始计数（不是 0）、或者用「窗口 LFU」（只在滑动窗口内计数）、或者像 W-TinyLFU 那样用准入机制单独保护新数据。

Q：Redis 的 LRU 为什么是「近似」的？
A：维护一个全局精确 LRU 链表，每次访问都要移动节点，代价很高（需要额外指针、加锁、内存开销）。Redis 的做法是随机采样：淘汰时随机取 N 个 key（默认 5），从中挑最久未访问的淘汰。用一点点精度损失换取 O(1) 的开销。调大 maxmemory-samples 可以提高精度、更接近真实 LRU，但会增加 CPU 消耗。

Q：生产上到底该选 LRU 还是 LFU？
A：默认选 LRU（Redis 的 allkeys-lru），它简单且在多数负载下表现良好。换 LFU 的信号：存在明显稳定的热点集合，且时不时有批量扫描/离线任务污染缓存（命中率周期性下跌）。Redis 中可用 allkeys-lfu。更强的选择是用 Caffeine 这类本地缓存（W-TinyLFU），它在混合负载下命中率通常最高。

Redis 的近似 LRU：不维护全局链表，而是随机采样 N 个 key（默认 5），淘汰其中最久未访问的。maxmemory-samples 越大越接近真 LRU——设为 10 时已非常接近真 LRU，而开销远低于维护精确链表。这是典型的「用少量精度换大量实现简单性」。

LRU 实现

# 手写 LRU（哈希表 + 双向链表，O(1)）
from collections import OrderedDict

class LRUCache:
    def __init__(self, capacity):
        self.cap = capacity
        self.m = OrderedDict()      # 有序：尾部=最近使用

    def get(self, key):
        if key not in self.m: return -1
        self.m.move_to_end(key)     # 访问 → 移到尾部（最近）
        return self.m[key]

    def put(self, key, value):
        if key in self.m:
            self.m.move_to_end(key)
        self.m[key] = value
        if len(self.m) > self.cap:
            self.m.popitem(last=False)   # 淘汰头部（最久未用）

# 复杂度：get/put 都是 O(1)
#   哈希表保证 O(1) 查找，链表保证 O(1) 移动
#   只用哈希表（无顺序）无法知道谁是「最久未用」
#   只用链表（无哈希）查找是 O(n)

LRU 的失效场景：扫描污染

典型问题：一次全表扫描式的批量访问，会把真正的热点数据全部挤出去。

扫描污染

# 场景：缓存容量 100，热点数据 A~Z 常驻
#   此时执行了一次全量扫描，访问了 1 万个冷数据
#   LRU 结果：<strong>热点数据全被淘汰</strong>，扫描后命中率暴跌
#
# 三种解法：
# 1) LRU-K：访问 K 次才进入缓存（扫描数据只访问 1 次，不会挤掉热点）
#     代价：需要维护「历史访问队列」，内存增加
#
# 2) 双队列（MySQL InnoDB 的做法）：
#     新数据进 young 区边缘，再次访问才晋升到 hot 区
#     InnoDB 参数：innodb_old_blocks_time（默认 <strong>1000 ms</strong>）
#       1 秒内被重复访问才算真正的热点，避免全表扫描污染
#
# 3) 分层缓存：批量扫描走独立缓存空间，不污染主缓存
#     最简单，实践中常用
方案原理代价
LRU-KK 次访问才入缓存额外历史队列
双队列（InnoDB）新数据需再次访问才晋升参数需调优
TTL 兜底热点不会因 TTL 消失太久不解决污染
独立缓存空间批量任务用另一份缓存最简单有效

LFU 的老化问题：一个曾经很热但现在无人访问的数据，因频次计数很高而永远不会被淘汰——占着位置不放。解决办法是频次衰减：定期把所有计数减半，或给计数加时间衰减因子。

LFU 实现

# LFU 实现要点：双哈希表 + 频次链表
#   key_to_val:  key -> (value, freq)
#   freq_to_keys: freq -> OrderedDict of keys
#   min_freq:     当前最小频次（<strong>淘汰时直接用</strong>）
import collections

class LFUCache:
    def __init__(self, capacity):
        self.cap = capacity
        self.minf = 0
        self.kv = {}                              # key -> (val, freq)
        self.fk = collections.defaultdict(collections.OrderedDict)

    def get(self, key):
        if key not in self.kv: return -1
        val, f = self.kv[key]
        del self.fk[f][key]                       # 从旧频次桶移除
        if not self.fk[f] and self.minf == f:
            self.minf += 1                        # <strong>该桶空了，提升 minf</strong>
        self.fk[f+1][key] = None
        self.kv[key] = (val, f+1)
        return val

    def put(self, key, value):
        if key in self.kv:
            self.kv[key] = (value, self.kv[key][1])
            self.get(key)                         # 提升频次
            return
        if len(self.kv) >= self.cap:
            k, _ = self.fk[self.minf].popitem(last=False)   # 淘汰最小频次里最久的
            del self.kv[k]
        self.kv[key] = (value, 1)
        self.fk[1][key] = None
        self.minf = 1

Redis 的 LFU 用 8 位 Morris 计数器做概率递增（不是精确计数），并带对数衰减：lfu-decay-time（默认 1 分钟）控制衰减速度。这样既省内存（1 字节），又天然解决了老化问题。

自检 Q&A

Q：什么时候 LFU 优于 LRU？

A：当访问模式稳定、热点长期不变时。典型如字典表、热门商品、配置文件——这些数据长期被高频访问，LFU 能牢牢保住它们。反之，如果热点随时间迁移（如新闻、热搜、当天活动），LRU 更合适，因为 LFU 会困在历史热点里。判断方法：看你的访问分布是否随时间变化。不确定就用 LRU，它更稳健。

Q：Redis 的淘汰策略怎么选？

A：按是否为缓存定位。纯缓存（数据丢失可从库重建）→ allkeys-lru（对所有 key 淘汰，最充分利用内存）。混合用途（部分 key 不能丢）→ volatile-lru（只淘汰设了 TTL 的，永久 key 保留）。需要保住热点 → allkeys-lfu。绝不要用默认的 noeviction——内存满会导致写入报错，生产事故。另外注意 volatile-* 策略在没有 key 设 TTL 时会退化成 noeviction。

Q：LRU 命中率上不去怎么排查？

A：三步——① 看缓存容量是否够：工作集（热点数据总量）超过缓存容量时，命中率天然上不去（称为缓存抖动），要么扩容，要么缩小工作集；② 看是否有批量扫描污染（前面说的）；③ 看 TTL 是否过短：数据还没被再次访问就过期了。用 INFO stats 看 evicted_keys（淘汰数）与 keyspace_misses 的增速——淘汰快说明容量不足，命中低但淘汰慢说明是 TTL 或 key 设计问题。

Q：为什么数据库（如 InnoDB）不用纯 LRU？

A：因为数据库面临严重的扫描污染。一次全表扫描会把整个 Buffer Pool 的热点页全部冲掉，严重影响正常查询。InnoDB 的做法是改良的分代 LRU：链表分 young/old 两段，新页先插在 old 区头部，只有在 old 区存活超过 innodb_old_blocks_time（默认 1000 ms）后再次被访问，才晋升到 young 区。全表扫描的页在同一个查询内被访问，间隔远小于 1 秒，所以不会晋升——热点被保住了。这是工程上处理 LRU 缺陷的经典范例。
