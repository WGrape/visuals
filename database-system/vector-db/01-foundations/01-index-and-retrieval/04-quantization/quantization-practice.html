①三个必开开关与它们的协作关系

量化的概念不难，难的是开了量化之后召回掉了 10 个点却不知道从哪查。这一页把三个必开开关、四个产品的具体配置、以及「量化了内存却没降」这类现象逐个拆开。

开关作用不开的后果
oversampling粗筛时多召回 N 倍候选低 bit 量化直接返回前 K，召回大幅下降
rescoring用原始向量对候选精排量化距离的误差没有被纠正，排序错乱
always_ram / 原向量保留把量化码或原向量常驻内存每次查询都读盘，延迟飙到几十毫秒
三者的关系：oversampling 决定「给多少候选」，rescoring 决定「用谁重排」，always_ram 决定「重排时要不要读盘」。只加一个通常没用，必须成套开。

②Qdrant：scalar / binary / product 配置

Qdrant 的量化配置挂在 collection 级别，可用 quantization_config 或 PATCH 动态调整：

# 标量量化（int8）：最常用，4× 压缩
PUT /collections/docs
{
  "vectors": { "size": 768, "distance": "Cosine", "on_disk": false },
  "quantization_config": {
    "scalar": {
      "type": "int8",
      "quantile": 0.99,      # 关键：裁掉 1% 的极端值，防离群维度毁掉区间
      "always_ram": true     # 量化码常驻内存（只有 1/4 大小）
    }
  }
}

# 二值量化：32× payload，必须配 oversampling
{
  "quantization_config": { "binary": { "always_ram": true } }
}

# 乘积量化：压缩更狠但更慢
{
  "quantization_config": { "product": { "compression": "x16", "always_ram": true } }
}

查询时通过 params.quantization 控制重排：

POST /collections/docs/points/search
{
  "vector": [...],
  "limit": 10,
  "params": { "quantization": { "rescore": true, "oversampling": 2.0 } }
}
参数默认调大调小
scalar.quantile0.99更稳（少裁剪）→ 精度略高更抗离群 → 精度可能降
oversampling2.0召回↑ 延迟↑延迟↓ 召回↓，低于 1.5 慎用
always_ramtrue（建议）延迟低、内存占用增加省内存，但重排要读盘

③Milvus：量化绑定在索引类型上

Milvus 的量化能力绑定在索引类型上，不是独立开关 —— 这一点和 Qdrant 不同，选错索引就没有量化：

索引量化方式压缩比备注
IVF_SQ8标量 int8约 4×最常用的「省内存又不掉精度」选项
IVF_PQ乘积量化由 m 决定（m=96/768 维约 32×）需训练码本，精度损失明显
HNSW本身不含量化1×要量化需配 refine 相关参数或换索引
DISKANN磁盘索引 + 内存量化码视配置亿级以上、内存放不下的场景
AUTOINDEX托管调优自动Zilliz Cloud 场景，省心但不可控
# Milvus：IVF_SQ8，量化 + 重排
index_params = {
    "index_type": "IVF_SQ8",
    "metric_type": "COSINE",
    "params": {"nlist": 1024},
}
collection.create_index("embedding", index_params)

# 查询参数：nprobe 控制扫多少桶，与 oversampling 等价
collection.search(..., param={"metric_type": "COSINE", "params": {"nprobe": 32}})
Milvus 的版本间参数演进较快（如 refine / refine_type / refine_k 这类「量化后精排」参数在不同版本可用性和命名有差异）。配置前请核对当前版本的官方文档，不要照搬旧文章。

④pgvector：用列类型表达精度

pgvector 走的是另一条路：用不同的列类型表达精度，用表达式索引做量化：

CREATE EXTENSION vector;

-- 半精度：2× 压缩，精度几乎无损
CREATE TABLE docs (id bigserial PRIMARY KEY, emb halfvec(768));
CREATE INDEX ON docs USING hnsw (emb halfvec_cosine_ops);

-- 二值：32×，适合高维大模型 embedding
CREATE TABLE docs_bq (
  id bigserial PRIMARY KEY,
  emb vector(1536),
  emb_bin bit(1536)
);
CREATE INDEX ON docs_bq USING hnsw (emb_bin bit_hamming_ops);

-- 写入时同步二值化
UPDATE docs_bq SET emb_bin = binarize(emb);

注意 pgvector 的维度上限：vector 可建索引的上限是 2000 维，halfvec 是 4000 维。3072 维的 embedding 在 pgvector 里必须用 halfvec 或做降维，直接建 vector(3072) 索引会报错。

⑤Elasticsearch：索引类型后缀即量化档位

Elasticsearch / OpenSearch 把量化做成了索引类型后缀，选索引类型即选精度：

索引类型量化压缩比适用
hnsw（float）无1×精度基线
int8_hnsw标量 int84×默认推荐，几乎无损
int4_hnsw标量 int48×内存紧张时
bbq_hnswBetter Binary Quantization约 32×高维大模型向量，需 oversampling
int8_flatint8 + 暴力4×小数据集、要求确定性召回

{
  "mappings": {
    "properties": {
      "emb": {
        "type": "dense_vector",
        "dims": 1024,
        "index": true,
        "similarity": "cosine",
        "index_options": {
          "type": "bbq_hnsw",
          "m": 16,
          "ef_construction": 100
        }
      }
    }
  }
}

⑥离群维度：量化最隐蔽的失败模式

离群维度是量化落地最常见的静默失败。某些 embedding 模型的输出里，个别维度的取值范围是其余维度的几十倍（这是训练目标带来的结构性偏置，不是脏数据）。

如果按全局 min/max 线性切分，若某维跨度是 [-50, 50] 而其他维都在 [-0.2, 0.2]，那么 256 个桶里绝大部分桶都被这一维占掉，别的维只剩几个桶可落 —— 量化几乎等于把信息抹平。

症状诊断方法修法
量化后召回掉 5–10 点打印每维 min/max，看是否有 10× 以上的跨度差改用分位数裁剪（quantile 0.99）
少数 query 完全查不到对比同一 query 在 FP32 与量化下的结果集提高 oversampling，或对这些维度单独处理
量化前后排序完全一致可能量化根本没生效检查索引类型 / 是否误用了 FP32 索引
另一条思路是从源头解决：部分模型支持降维输出（如 3072 → 1024 维，Matryoshka 表示学习），降维本身就能省 3 倍，还顺带缓解离群维度问题 —— 比压位宽更划算。

⑦原向量存在哪：决定真实收益边界

rescoring 要拿「原始向量」重排，那原始向量存在哪？这决定了量化的真实收益边界。

原向量存放位置省内存效果重排延迟适用
不保留原向量（只留量化码）最大无法重排，召回最差几乎不该选
内存中保留只省了「没被重排用到」的部分，实际省得少最低小数据集，延迟敏感
磁盘 / mmap 保留接近理论压缩比中（随机读，靠 OS page cache）大规模、可接受 p99 抬高
保留低精度副本（如 SQ6）介于两者之间低折中方案，Milvus/DiskANN 常见做法
所以「我开了 BQ，内存应该省 32 倍」是个常见误判。真实占用 = 量化码 + 图邻接表 + 若非盘存则还有原向量。三者相加后经常只省 5–10 倍。上线前务必用 ps / 监控实测 RSS，而不是相信配置文件。

⑧四步测量流程与代码

固定流程，四步，不要跳：

  1. 建 ground truth：同一批数据建 FLAT / 暴力索引，对 500–1000 条代表性 query 取 top-100，存下来当标准答案。
  2. 量 FP32 基线：量化索引关掉，量 recall@10 / recall@100 与 p99 延迟，确认 ground truth 与基线一致（recall 应 ≈ 1.0）。
  3. 开量化扫参：固定 oversampling ∈ {1, 1.5, 2, 3, 4}，各量一次 recall 与 p99，画曲线找拐点。
  4. 定档并留回退：选满足召回目标的最小 oversampling；量化配置应能通过一次 API 调用关掉，作为线上兜底。
# recall@K 的最小实现（K 与 ground truth 的 K 必须一致）
def recall_at_k(truth_ids, got_ids, k):
    t, g = set(truth_ids[:k]), set(got_ids[:k])
    return len(t & g) / k

# 循环扫 oversampling，一次出一张表
for os in [1.0, 1.5, 2.0, 3.0, 4.0]:
    res = search(q, limit=10, params={"quantization": {"rescore": True, "oversampling": os}})
    print(os, recall_at_k(truth[q], [r.id for r in res], 10), p99())

⑩速记卡

三个必开开关

oversampling + rescore + always_ram，缺一不可。

Qdrant

scalar.int8 + quantile 0.99，查询侧 rescore/oversampling。

Milvus

量化绑索引：IVF_SQ8 / IVF_PQ，HNSW 本身不含量化。

pgvector

用类型表达精度：halfvec / bit；vector 索引上限 2000 维。

ES

用索引类型后缀：int8_hnsw / bbq_hnsw。

离群维度

分位数裁剪，或改用可降维的 embedding（Matryoshka）。

真实收益

量化码 + 图 + 可能残留的原向量，实测常只省 5–10 倍。

验证顺序

FLAT ground truth → FP32 基线 → 扫 oversampling → 定档留回退。

量化上线的判据只有一条：在满足 recall 目标的前提下，实测 RSS 真的降了。配置文件里的压缩比不算数。
