关注行为而非身份

接口让调用方依赖「能力」而非具体类型，是 Go 解耦的核心。标准库大量使用小接口（如 io.Reader）。

type Reader interface {
    Read(p []byte) (n int, err error)
}
// 任何有 Read 方法的类型都满足 Reader
// 调用方只认 Reader，不关心是文件/网络/内存
实现条件：结构化

方法集匹配即可，无需声明

类型只要拥有接口要求的全部方法（签名一致），就自动实现该接口。这叫「鸭子类型 / 结构化类型」。

type Speaker interface { Speak() string }
type Dog struct{}
func (d Dog) Speak() string { return "woof" }
// Dog 自动实现 Speaker，无需写 implements
var s Speaker = Dog{}  // 合法
接口值：类型 + 值

著名的 nil 接口陷阱

接口变量内部是 (具体类型, 具体值) 二元组。只有「类型和值都为 nil」时接口才等于 nil；若类型非空、值 nil，接口 != nil。

func bad() error {
    var p *MyErr = nil
    return p   // 返回的是 (type=*MyErr, value=nil)
}

e := bad()
if e != nil {       // true！因为类型非空
    fmt.Println("got error")  // 会打印
}
⚠️ 避免此陷阱：错误返回处直接 return nil，不要把 nil 指针赋给接口变量再返回。
常用内置接口

都是小接口，自由组合

标准库把能力拆成极小的接口，再组合使用（如 io.ReadWriter = Reader + Writer）。

空接口与 any

any = interface{}

空接口没有方法，任何类型都满足它，常用于承载未知类型（如 JSON 解码到 map[string]any）。过度使用会丢失类型安全。

实践建议

优先定义具体小接口而非 any；只有真正异构集合（如配置、插件载荷）才用 any，并尽快用类型断言/type switch 收窄回具体类型。

接口值的内部结构：为什么会有判空陷阱

接口变量不是一个简单的指针，它内部是两个字段：动态类型 与 动态值。理解这一点，所有关于接口的困惑都会消失。

接口值的两字段结构：判空要看两个字段，而不是只看值
var p *MyType = nil var i any = p // 类型字段非空，值字段为空 i == nil // false，因为类型字段非空 p == nil // true // 典型翻车现场： func do() error { var p *MyErr = nil if badCondition { p = &MyErr{} } return p // 条件不满足时，返回的 error 不是 nil } // 正确写法：显式返回 nil func doFixed() error { if !badCondition { return nil // 直接返回字面量 nil } return &MyErr{} } // 经验：不要把具体类型的 nil 指针直接赋给接口返回

方法集规则：值接收者与指针接收者

这条规则决定了哪个类型实现了这个接口，是最容易出错的地方。记住一句口诀：指针类型的方法集更大，值类型只拥有值接收者的方法。

接收者写法值类型的方法集指针类型的方法集谁实现了接口
值接收者包含该方法包含该方法（自动解引用）两者都实现
指针接收者不包含该方法包含该方法只有指针类型实现
混合使用只含值接收者的方法含全部方法只要有一个指针方法就只能用指针
type Speaker interface { Speak() string } type Dog struct{ name string } func (d Dog) Speak() string { return d.name } // 值接收者 var s1 Speaker = Dog{"a"} // 可以 var s2 Speaker = &Dog{"b"} // 也可以，指针拥有值方法 type Cat struct{ name string } func (c *Cat) Speak() string { return c.name } // 指针接收者 var s3 Speaker = &Cat{"c"} // 可以 var s4 Speaker = Cat{"d"} // 编译错误：值类型没有该方法 // 选型建议： // - 需要修改接收者内部状态，必须用指针接收者 // - 结构体较大避免拷贝，用指针接收者 // - 同一类型的方法接收者风格要统一，不要有的值有的指针 // - 含互斥锁等不可拷贝字段的类型，一律用指针接收者

类型断言与类型开关

断言的两种形式

单返回值形式在失败时直接 panic，双返回值形式返回是否成功，是推荐的写法。断言只对接口值有意义，对具体类型做断言是编译错误。

类型开关的用途

当一个接口可能有多种实现、需要分别处理时，用类型开关比一连串断言更清晰。但如果分支越来越多，通常说明该接口设计得不够小，应该拆成多个接口而不是在一个地方分支。

// 安全写法：带 ok 的双返回值 if v, ok := x.(string); ok { // v 是 string } // 类型开关 switch v := x.(type) { case string: // v 是 string case int: // v 是 int case nil: // x 是 nil 接口 default: // 其他 } // 接口之间的转换：从大接口取小接口 if w, ok := r.(io.Writer); ok { // r 同时也实现了 Writer } // 编译期断言：确保某类型实现了某接口 var _ Speaker = (*Dog)(nil)

接口设计原则：小而组合

接口要小一个方法最好，两三个也可以，再多就该拆
在使用方定义接口由调用方按需声明，而不是实现方预先定义
接受接口返回结构入参用接口便于替换，返回值用具体类型便于使用
不要为测试造大接口接口越大，模拟实现越痛苦
组合优于继承把小接口嵌成大接口
单方法接口带 er 后缀如 Reader、Writer、Closer
空接口要慎用用了它就失去了类型检查，应有明确理由
空接口不等于泛型需要类型安全时优先考虑泛型
什么时候该用空接口而不是泛型？

当容器需要存放真正异构的值、或者确实要在运行时判断类型时，用空接口。如果只是同一个算法作用于多种类型，泛型更合适，因为它保留编译期类型检查，也免去了断言。

接口嵌套有深度限制吗？

没有硬性限制，但嵌套过深会让方法集难以理解。实践中一般控制在两三层以内，比如标准库里把读、写、关闭组合成一个更大的接口。

为什么推荐在使用方定义接口？

因为接口表达的是我需要什么，而不是我提供什么。在使用方定义，接口天然是最小的，而且实现方不需要为了适配某个大而全的接口而被迫实现一堆用不到的方法。

接口比较时什么情况下会 panic？

当接口的动态类型不可比较（比如切片、映射、函数）时，用等号比较两个接口会在运行时 panic。如果拿不准动态类型是否可比较，应该用反射的相等判断，或者避免直接比较接口。

一句话总结：Go 的接口是隐式实现的结构化契约，小接口、在使用方定义、自由组合，这三条是用好它的关键。

接口值的内部结构与 nil 陷阱

Go 的接口值是一个两字长的结构体：(动态类型, 动态值)。所有「接口相关的诡异行为」都能从这个结构推出来。

内部结构

// runtime 里的定义（简化）
type iface struct {         // 有方法的接口
    tab  *itab              // 类型信息 + 方法表指针
    data unsafe.Pointer     // 指向实际数据的指针
}
type eface struct {         // interface{}（空接口）
    _type *_type
    data  unsafe.Pointer
}
// 结论：任何接口值都占 <b>16 字节</b>（64 位下两个指针）
情况== nil 的结果说明
var w io.Writer = niltrue类型和值都为 nil
var p *MyType = nil; var w io.Writer = pfalse经典陷阱：类型不为 nil，只是值是 nil
var w io.Writer = (*MyType)(nil)false同上
var e any = niltrue
函数返回 error 接口，内部返回了 *MyErr(nil)!= nil最常踩：if err != nil 永远成立

typed nil 陷阱

// 经典陷阱（面试必考）
type MyErr struct{ Msg string }
func (e *MyErr) Error() string { return e.Msg }

func doIt() error {
    var e *MyErr = nil        // 具体类型的 nil 指针
    if false { e = &MyErr{"x"} }
    return e                  // 包装成 error 接口 -> 不再是 nil！
}
fmt.Println(doIt() == nil)    // false ！！！

// 正确写法：不要提前声明具体类型
func doIt() error {
    if false { return &MyErr{"x"} }
    return nil                // 直接返回字面量 nil
}

// 或者显式判空后再返回
func doIt() error {
    var e *MyErr
    if e != nil { return e }
    return nil
}

记忆口诀：接口只有「类型和数据都为 nil」时才等于 nil。所以永远不要让函数返回一个「非空类型的 nil 指针」当作 error——这是 Go 里最著名的一个坑（官方 FAQ 里就有）。反过来，这也是为什么 errors.Is/As 比直接比较更安全的理由之一。

方法集规则与接口设计

接收者T（值）的方法集*T（指针）的方法集能否满足接口
func (t T) M()包含 M包含 M都能
func (t *T) M()不包含包含 M只有 *T 能

方法集与断言

type Reader interface{ Read() }

type A struct{}
func (a A) Read() {}        // 值接收者

type B struct{}
func (b *B) Read() {}       // 指针接收者

var _ Reader = A{}          // OK
var _ Reader = &A{}         // OK（指针方法集包含值方法集）
var _ Reader = B{}          // 编译错误！B 的方法集不含 Read
var _ Reader = &B{}         // OK

// 空接口与类型断言
var x any = 42
if v, ok := x.(int); ok { fmt.Println(v) }     // 安全写法
v := x.(int)                                    // 不安全，失败会 panic

// 接口组合（Go 里最推荐的复用方式）
type ReadWriter interface {
    io.Reader
    io.Writer
}

// 编译期断言：确认某类型实现了某接口（写在包顶层）
var _ io.Writer = (*MyWriter)(nil)
实践理由
接口要小（1~3 个方法）小接口易实现、易组合、易 mock。io.Reader 只有一个方法，却能支撑整个生态
在使用方定义接口，不在实现方Go 的惯例：实现方只管写 struct，接口由调用者按需声明（否则会造出一堆大接口）
接收者要统一同一类型混用值/指针接收者容易踩方法集坑；通常全用指针
需要修改状态 / 大对象 → 指针接收者值接收者会复制整个对象；且修改不生效
map/slice/chan 不需要指针它们本身就是引用语义的头部结构
接口值作为 map 的 key 会怎样？

可以，但要注意：接口值相等要求动态类型相同且动态值相等。如果动态值是不可比较类型（slice、map、function），运行时会 panic: hash of unhashable type。这是很隐蔽的运行时崩溃，尤其当接口里塞了 slice 时。

接口调用比直接调用慢多少？

约 1~5 ns 级别，来自 itab 的间接跳转，且无法内联。单次看微不足道，但在极热的循环里（如每秒上亿次调用）会有可观测影响，且阻碍内联会让优化失效。对策：热路径用具体类型或泛型（泛型在编译期单态化，无此开销）。

什么时候该用接口而不是泛型？

判断标准是是否需要运行时多态。接口是运行期动态派发（同一份代码处理不同类型，类型在运行时才知道）；泛型是编译期单态化（类型在编译期确定，生成多份代码）。要往一个 []Writer 里塞不同实现 → 接口；要写一个 Map[T,U] 且类型编译期已知 → 泛型（更快、类型更安全）。
