文件 IO 模型

缓冲 IO、mmap、direct IO 与异步 IO——看清磁盘读写的几种姿势。

缓冲 IO 为什么快

→

→
内核异步刷盘

大多数语言默认「缓冲 IO」：数据先进内核页缓存，由内核择机批量写盘。读也优先命中页缓存。这样把大量小 IO 合并成少量大 IO。

mmap 内存映射

把文件当内存用

mmap 把文件直接映射到进程虚拟地址空间，免去「内核缓冲 → 用户缓冲」的拷贝，适合大文件随机访问与进程间共享。

模型特点适用

顺序 vs 随机

顺序读写能充分利用预读与连续带宽，比随机寻道快几个数量级。设计文件格式与写入顺序时，尽量让访问模式是顺序的。

问题 1
缓冲 IO 为什么比直接读写快？

它把多次小写入先攒进内核页缓存，再批量、顺序地刷盘，并用预读加速顺序读。应用程序不必等磁盘，吞吐因此大幅提升。

问题 2
mmap 适合什么场景？

大文件的随机读、进程间共享内存、以及需要避免「内核→用户」拷贝的场景。但 mmap 的缺页与写回由内核调度，对小文件反而是额外开销。

问题 3
direct IO 和缓冲 IO 怎么选？

数据库这类自带缓存的软件常用 direct IO 绕过页缓存、自己精确控制；普通应用用缓冲 IO 即可，省心且通常更快。

问题 4
为什么顺序写比随机写快这么多？

机械/SSD 都对连续块友好：顺序写减少寻道与写放大，还能配合预读。随机写则频繁寻道、产生碎片，吞吐骤降。

文件 I/O 的四种方式

读写磁盘有多种路径，差别在拷贝次数与是否经过页缓存：标准 I/O（带用户态缓冲）、直接系统调用（read/write）、mmap（省一次拷贝）、直接 I/O（绕过页缓存）。选错会让性能差好几倍。

性能要点与调优

① 顺序 vs 随机

  • 机械盘随机 I/O 比顺序慢百倍（寻道）；SSD 也慢数倍。
  • 设计上尽量顺序写（追加日志 WAL 就是这个思路）。
  • 随机读尽量合并、预读、或放内存。
  • LSM-Tree 正是把随机写转成顺序写的经典设计。

② 页缓存与内存

  • 页缓存用空闲内存，不是浪费——可回收。
  • 可用内存 = free + buff/cache 中可回收部分。
  • 数据库场景可能希望减少页缓存（O_DIRECT）避免双份缓存。
  • madvise/fadvise 可提示访问模式，改善预读与回收。

③ 持久化与 fsync

  • write() 返回不代表落盘，掉电可能丢失。
  • fsync 代价高（机械盘可达毫秒级），要控制频率与批量。
  • 不同需求不同策略：日志类可每秒 fsync，金融类每笔。
  • 注意 fdatasync 与 fsync 的区别（后者还同步元数据）。

④ 观测与定位

  • iostat -xz 1：await（含排队）、util、队列长度。
  • util 高不一定饱和（RAID/SSD 可并行），要看 await 与队列。
  • iotop 看进程级；pidstat -d 按进程统计。
  • 深入用 blktrace / bpftrace 看块层与设备层。
  • 区分：应用问题（同步写太多）vs 设备问题（磁盘慢）。

深入自检

为什么 write() 返回了数据还可能丢？

因为 write() 通常只把数据写进内核页缓存就返回，真正的落盘由内核异步完成（回写线程、脏页比例阈值、时间阈值）。只有调用 fsync/fdatasync（或打开 O_SYNC）才能保证数据到达持久存储。这也是数据库必须处理刷盘策略的原因。

mmap 一定比 read 快吗？

不一定。mmap 的优势是省一次拷贝、便于随机访问与共享；但它有缺页开销、TLB 压力、以及脏页回写时机不可控的问题。小文件的顺序读用 read 可能更快（还受益于预读）；大文件随机访问或跨进程共享只读数据时 mmap 更合适。

什么是零拷贝，为什么重要？

零拷贝指数据在传输过程中不在内核态与用户态之间来回拷贝，也不重复经过 CPU。典型是 sendfile：文件页缓存数据直接交给网卡 DMA 发送。省掉两次拷贝与两次上下文切换，对静态文件服务、消息中间件（Kafka 用 sendfile 提升消费者吞吐）收益巨大。

iostat 里 util 100% 但吞吐很低，说明什么？

说明设备「忙」但没干多少活——通常是随机 I/O 导致的：机械盘大量时间花在寻道，SSD 可能是小写放大。util 只表示设备有请求在处理，不代表带宽打满。要结合 await（响应时间）、队列长度、以及读写吞吐一起判断。SSD/NVMe 支持多队列并行，util 的含义也更弱。

数据库为什么常用 O_DIRECT？

因为它想自己管理缓存（缓冲池），避免「页缓存 + 数据库缓冲池」两份内存与双重 LRU 决策；同时希望精确控制刷盘时机以满足持久性语义。代价是失去内核预读与缓存复用，必须自己做预读、对齐与合并——这也是数据库 I/O 层复杂的原因。

LSM-Tree 为什么写性能好？

因为它把随机写转换为顺序写：写入先追加到内存表与日志文件（顺序），再批量、有序地合并到磁盘。代价是读放大（可能要查多层）与写放大（合并重写）。这是典型的「用读性能换写性能」的取舍，适合写多读少的场景（如 HBase、RocksDB）。
