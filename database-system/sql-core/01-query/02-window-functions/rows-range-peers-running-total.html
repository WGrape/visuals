SQL 窗口帧手算：ROWS 和 RANGE 遇到同一天两行时为何累计值不同

用三笔订单逐行算累计金额，讲透同值组、排序稳定性、默认窗口帧与 LAST_VALUE 陷阱。

分区、排序、窗口帧各负责一层

窗口函数保留每一行，同时在一组相关行上计算结果。PARTITION BY 决定分组边界，ORDER BY 决定组内顺序，窗口帧再决定“当前行计算时究竟看哪些行”。把三者混成“窗口就是前面所有行”，遇到同一天多笔订单或 LAST_VALUE 时很容易写错。不同数据库对未显式写窗口帧时的默认行为有差异，尤其是排序存在同值行时；生产 SQL 应尽量把关键帧写清楚。

本课以三笔订单为例：id=1 和 id=2 都在 10 月 1 日，金额分别 10 和 20；id=3 在 10 月 2 日，金额 5。希望回答两个不同问题：“按订单逐笔累计”与“截至当天累计”，二者不应在同一天第二笔之前得到同一个值。

沿箭头逐步核对输入、变换和输出；下面的推演可以逐步切换。

ROWS 是物理行数边界

若按 day、id 排序，使用 SUM(amount) OVER(ORDER BY day, id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)，第 1 行只看金额 10，输出 10；第 2 行看 10+20，输出 30；第 3 行看 10+20+5，输出 35。ROWS 的 CURRENT ROW 指当前这一物理行，不会自动把其他同一天行全部装进来。这里额外按 id 排序是为了明确同一天内部先后；若只 ORDER BY day，同值行谁先算可能取决于执行计划，结果行与 id 的对应关系不稳定。

若业务仅要“每笔订单之后的余额”，还要确认 day、id 的顺序真能代表发生顺序。订单 ID 不一定等于创建时间，必要时使用事件时间加稳定唯一键，处理同一时刻的并列情况。

RANGE 会把同值行放进当前组

使用 SUM(amount) OVER(ORDER BY day RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) 时，同一天的两行是 peer，同属于排序值 10 月 1 日；两行都看到截至当天的 10+20=30，第 3 行看到 35。因此结果为 30、30、35。RANGE 的 CURRENT ROW 在这种边界下指当前排序值所在的同值组边界，不等于“当前行编号”。若 ORDER BY day,id，则每行排序键不同，peer 关系改变，不能照搬 30、30、35 的结论。

RANGE 还可用于按排序值范围定义如“此前 7 天”的窗口，但日期时间区间语法和允许的 ORDER BY 表达式依数据库而异。ROWS 7 PRECEDING 指前七行，不是前七天；若某天有一万行，二者的业务含义差得很远。

一个默认帧陷阱

不少数据库在写了 ORDER BY、却没写显式窗口帧时，聚合窗口采用从分区开头到当前 peer 组的默认范围，结果更像上面的 RANGE 累计；但具体 SQL 方言与函数限制要核对。若开发者原本想逐笔累计，线上同一天插入第二笔后第一笔的累计值可能变化。写显式 ROWS 帧并给出稳定排序键，比猜默认规则更稳健。

另一个常见误用是 LAST_VALUE(amount) OVER(PARTITION BY customer ORDER BY day)。若默认帧只到当前行或当前 peer，LAST_VALUE 往往返回截至当前的最后值，而不是整个客户分区的真正最后一笔。要取完整分区末值，应显式让帧延伸到 UNBOUNDED FOLLOWING，并定义唯一排序；也可根据方言改用其他明确写法。

NULL、并列和执行计划

ORDER BY 列如果有 NULL，不同数据库对 NULL 排序位置的默认约定可能不同；明确处理缺失日期或使用方言支持的 NULLS FIRST/LAST。相同排序键下，ROWS 帧的计算顺序需要额外稳定键，否则两次运行可能把 10 和 20 的逐笔累计分配给不同 id。RANGE 与 peer 组的值虽相同，但窗口可能更大；在大量重复键和复杂窗口表达式中要检查执行计划及内存使用。

窗口函数通常在 WHERE、GROUP BY 等逻辑处理之后作用于当前结果行集。若先过滤掉某些订单，累计的输入也变了；如果要“先算全量累计再筛出今天”，可能需要子查询或 CTE，把计算与过滤的层次分开。

何时该用 GROUP BY

要得到每天一行的日收入，用 GROUP BY day 更直接；要保留每笔订单又附上当天总额或截至当天累计，用窗口函数。也可以先按天 GROUP BY 生成日汇总，再对日汇总做跨天累计，这样避免同日多行 peer 的歧义。预聚合与窗口并用时应检查金额单位、退款负数和重复订单处理；SQL 语法正确不保证业务口径正确。

窗口帧的选择应写在报表定义中：是“前 7 行交易”“此前 7 个自然日”“本月截至当前日期”还是“截至此笔交易”。中文描述若不明确，开发实现可能各有一套。

验收三笔订单

在数据库里插入 id1/day1/10、id2/day1/20、id3/day2/5，分别执行显式 ROWS 与 RANGE 版本。核对预期 10、30、35 与 30、30、35；再把插入顺序打乱，确认带 id 排序的 ROWS 结果稳定。最后新增 day1/id4/7，观察“逐笔累计”和“截至当天累计”如何变化，并检查 LAST_VALUE 是否真正返回全分区末行。

上线前把数据库产品与版本写进测试说明，因为窗口帧语法、默认值和 RANGE 对日期的支持存在方言差异。一个三行最小样本比只看大报表总额更容易暴露同值行错误。

自检

ORDER BY day 且 10 月 1 日有两行，RANGE 到 CURRENT ROW 是否一定只包含当前这一行？

不是。同一天的排序值相同，通常是 peer 组；两行都可包含当天两笔金额，得到 30。
