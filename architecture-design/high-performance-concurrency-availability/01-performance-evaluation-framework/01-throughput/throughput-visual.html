⚙️ 影响吞吐量的核心因素
🧵
并发度 / 线程池大小

适度提高可利用的请求并发可能让资源保持忙碌；达到 CPU、IO 或上游瓶颈后，增加并发通常只会拉长等待与延迟，甚至降低吞吐。线程数与在途请求数不是同一指标。

⏱️
平均响应时间 RT

RT 越短，同样并发下吞吐量越高。优化 DB 查询、缓存命中率可直接提升吞吐量。

💽
I/O 能力

磁盘 I/O、网络带宽是常见瓶颈。异步 I/O、NIO 可以显著提升吞吐量。

🗄️
数据库连接池

DB 连接数不足时会产生等待，是压测中最常见的吞吐量瓶颈之一。

🔒
锁竞争 / GC

高并发下锁争用和频繁 GC 会产生 Stop-the-World，导致吞吐量陡降。

📦
请求体大小

大请求体占用带宽，序列化/反序列化消耗 CPU，同等时间内处理请求数减少。

🧑‍🔬 如何正确评估吞吐量
Step 1：确定测试目标场景

选定要评估的接口/功能，明确是读多写少还是混合场景，决定测试数据集规模。

Step 2：用压测工具施加负载

常用工具：JMeter、wrk、ab（Apache Bench）、k6、Gatling。设置并发用户数、Ramp-up 时间，模拟真实流量形态。

Step 3：统计通过测量窗口的请求数

在系统稳定运行阶段（排除预热期）统计：完成的请求总数 ÷ 统计时长 = TPS/QPS。

Step 4：绘制吞吐量 vs 并发数曲线

逐步增加并发，观察吞吐量变化。曲线会经历：上升 → 平台期 → 拐点（系统过载）→ 下降三个阶段。

Step 5：找到最优工作点（拐点）

吞吐量开始下降前的最高点即为系统最大吞吐量。此时 RT 还在可接受范围内，是最佳运行点。

Step 6：关注有效吞吐量

总 TPS 中需剔除失败请求。高错误率下的高 TPS 毫无意义。有效吞吐量 = 成功请求 ÷ 统计时长。

📊 吞吐量与并发数的关系曲线

💡 随并发增大：吞吐量先上升，到达 最优工作点 后趋于平稳，最终因资源争用而 下降 ——这是设计容量规划的关键依据

吞吐量、QPS、TPS、并发：别再混着用

这四个词经常被当成同义词，其实它们量的东西完全不同。吞吐量是「产出」，并发是「在途」，延迟是「停留时间」，三者被利特尔法则绑在一起，只要知道其中两个，第三个就能算出来。

吞吐量 Throughput单位时间完成的工作量。单位可以是 req/s、MB/s、token/s，取决于系统
QPS每秒请求数。偏「请求计数」，是吞吐量最常用的一种表示
TPS每秒事务数。一个业务事务可含多次请求，因此 TPS 通常明显低于 QPS
并发 Concurrency同时在系统内部的请求数，也就是「发出去还没回来」的量
响应时间 RT从发出到收到响应的时间，要看分位数而不只看平均
利特尔法则并发 = 吞吐 × 响应时间。稳态下必然成立，是容量估算的地基
经典吞吐-并发曲线：吞吐会饱和，延迟却会继续飙；曲线膝点才是合理的容量目标

由利特尔法则可以直接推出一个极实用的估算：吞吐上限 ≈ 并发上限 ÷ 平均响应时间。如果线程池最多同时处理 1000 个请求、平均耗时 50ms，那么这台机器的吞吐天花板大约是每秒两万，再往上压并发只会增加排队长度，不会增加产出。

三个阶段的真实表现

把并发一点点加上去，系统会依次进入三个区域。判断当前在哪个区域，比记住任何数字都重要。

阶段并发增加时吞吐响应时间系统表现与对策
轻载区近似线性上升基本不变资源还有余量，吞吐是主要矛盾，可以继续加压
饱和区增速明显放缓开始上升到达膝点，某处资源（CPU/连接/锁）已接近满，此时加并发只换排队
过载区不再上升甚至回落急剧恶化排队失控、超时重试形成正反馈，必须限流与降级而非继续加压

为什么过载后吞吐会下降？

因为系统开始把资源花在「处理排队」本身：上下文切换、超时判定、重试重放、GC 回收堆积对象。有效工作占比下降，吞吐自然回落，这就是所谓的拥塞崩溃。

膝点才是容量目标

峰值吞吐往往伴随不可接受的延迟。工程上一般把目标定在膝点略左侧：留出足够余量，让突发流量落在饱和区而不是直接滑进过载区。

代码里的并发与吞吐：一个直观换算

下面这段伪代码说明了三者的关系：并发数固定时，想提高吞吐只能缩短响应时间；反过来，如果响应时间被下游拖长，同样的并发下吞吐必然掉下来。

// 并发模型：同时最多 N 个请求在途 N = 200 // 并发上限（连接池 / 线程池 / 信号量） RT = 0.05 s // 平均响应时间（注意用稳态值） QPS = N / RT // 利特尔法则：200 / 0.05 = 4000 req/s // 情况 A：下游变慢，RT 涨到 0.2s QPS = 200 / 0.2 = 1000 req/s // 吞吐直接掉到四分之一 // 情况 B：想把 QPS 拉回 4000，只能加大并发 N = 4000 * 0.2 = 800 // 代价：连接池与内存压力翻四倍 // 结论：降低 RT 永远优于堆并发 // 堆并发 = 更多的连接、更多的内存、更长的排队、更差的尾延迟

这也解释了一个常见现象：下游稍微慢一点，整个系统的吞吐就会断崖式下降，因为并发资源是固定的，而每个请求占用的时间变长了。

压测时最容易踩的五个坑

为什么压测结果比线上好很多？

常见原因是数据太热：压测反复打同一批请求，缓存命中率接近满分，数据库几乎不干活。线上是冷热混合、长尾分布。正确做法是构造贴近真实分布的数据集，并单独测冷启动。

为什么客户端成了瓶颈？

压测机自身也可能打满：CPU 用尽、端口耗尽、连接数受限、GC 停顿。判断方法是看压测机资源是否饱和，以及吞吐是否随压测机增加而提高；如果加了压测机吞吐就涨，说明之前是客户端受限。

为什么测出来的延迟偏乐观？

这叫协调遗漏：当服务端变慢时，固定并发的压测客户端会等上一个请求返回才发下一个，于是慢的时间段内发出的请求更少，样本被自动「美化」。需要按时间驱动发压而不是按并发驱动。

只看平均响应时间为什么会被骗？

平均值掩盖长尾。九成请求 20ms、一成请求 2s，平均也会显示约 218ms，看起来还行，但对那一成用户就是完全不可用。必须同时看 P95 / P99 / P999 与最大值。

吞吐达标就能上线吗？

不够。还要看：错误率是否升高、P99 是否在可接受范围、资源水位是否留有突发余量、以及停止压测后系统能否在预期时间内恢复（有没有堆积未消化、连接池是否泄漏）。

三个指标的关系：Little's Law

吞吐（QPS）、并发数、延迟不是三个独立指标，它们被一个公式锁死：L = λ × W。知道任意两个就能推出第三个，这是所有压测数据分析的基础。

手算示例与排队论

# Little's Law：  并发数 L = 吞吐 λ(请求/秒) x 平均延迟 W(秒)
#
# 例 1：单机要撑 1000 QPS，平均延迟 50ms，需要多少并发？
#   L = 1000 x 0.05 = 50        -> 至少 50 个并发连接/线程
#
# 例 2：并发 200、平均延迟 20ms，吞吐上限是多少？
#   λ = L / W = 200 / 0.02 = 10000 QPS
#
# 例 3（最有用）：延迟从 20ms 劣化到 200ms，并发不变，吞吐会掉多少？
#   λ = 200 / 0.2 = 1000 QPS    -> 掉到 1/10，这就是「雪崩」的数学解释

# 排队论视角（M/M/1）：
#   利用率 ρ = λ/μ ，响应时间 W = 1/(μ - λ)
#   ρ=0.5 -> W=2/μ ； ρ=0.9 -> W=10/μ ； ρ=0.99 -> W=100/μ
#   结论：利用率超过 0.8 之后，延迟呈双曲线爆炸，必须留余量
利用率 ρ排队等待占比工程建议
0.5延迟 = 空闲时的 2 倍日常水位建议区间
0.7≈3.3 倍扩容触发线（很多公司定在 0.7）
0.85 倍压测目标上限，超过就该扩
0.910 倍已进入危险区，抖动会被放大
≥1.0∞（排队无限增长）必然雪崩，必须有限流

压测与瓶颈判断

# 压测输出解读（wrk）
wrk -t8 -c100 -d30s --latency http://host/api
#   Requests/sec:   8500.12      <- 吞吐 λ
#   Latency  12.35ms   (P99 88.10ms)   <- 延迟 W
#   代入 Little's Law: L = 8500 x 0.01235 ≈ 105  (与 -c100 吻合，说明压满了)

# 判断瓶颈：并发加大，吞吐不涨 = 已到瓶颈；延迟同时涨 = 排队
for c in 20 50 100 200 400; do
  printf "c=%-4s " $c
  wrk -t8 -c$c -d10s http://host/api | grep -E 'Requests/sec|Latency' | tr '\n' ' '
  echo
done

吞吐优化：先找瓶颈，别瞎调

  • 第一步永远是测，不是猜。先 wrk 压出基线，再加并发找拐点，最后用 profile 定位。Go 用 pprof，Java 用 async-profiler，C/C++ 用 perf。
  • CPU 密集型：看火焰图找热点函数；常见收益点是减少分配（对象复用、sync.Pool）、批量化（减少函数调用与锁次数）、算法降复杂度。
  • IO 密集型：吞吐上不去往往是并发度不够而不是 CPU 不够——加并发数，或改异步/批量（Redis pipeline、MySQL 批量 insert、Kafka 批量发送）。
  • 批量化的收益是量级级的：Redis 单条 get 受 RTT 限制（1ms 下最多 1000 QPS/连接），pipeline 一次打包 100 条可到 10 万 QPS；MySQL 逐条 insert（每次 fsync）约 千级 TPS，批量 + 单事务可到 万级。
  • 锁是吞吐杀手：全局锁/大粒度锁会把多核压成单核。按核拆分（分段锁、shard）、用无锁结构（atomic、RCU）、或干脆用单线程 + 多实例（Redis 模型的精髓）。
  • 超时与重试会反噬：下游变慢 → 上游超时 → 重试 → 流量翻倍 → 下游更慢。重试必须加退避 + 熔断，且重试次数上限 ≤2。
优化手段典型收益风险
批量 / 流水线10~100 倍（IO 密集场景）单批太大导致延迟变长，要限制批大小
连接池复用3~10 倍（省握手）池太小成瓶颈，太大压垮下游
本地缓存热点5~20 倍（省网络 + 省序列化）一致性变差，需失效机制
异步化削峰，吞吐更平稳复杂度上升，排查变难
锁粒度细化核数倍（8 核最多 8 倍）并发 bug 风险
算法降复杂度可能 >100 倍（O(n²)→O(n)）无
并发数越大吞吐越高吗？

不是。并发增大时吞吐先线性上升，到瓶颈后持平甚至下降，而延迟持续上升。所以压测一定要扫并发，只看单点并发的 QPS 毫无意义——报「我们的服务能扛 2 万 QPS」而不说延迟和并发数，是没有意义的数字。

为什么平均延迟看着正常，用户却说慢？

因为平均值掩盖长尾。1000 个请求里 990 个 10ms、10 个 2s，平均只有 30ms，但 1% 的用户觉得卡死。必须看 P99 / P999，而且 P99 的目标通常要定得比平均值严格得多（如平均 20ms / P99 <100ms）。

吞吐突然掉一半，怎么快速定位？

按四层顺序排查，每步只要几秒：① top 看 CPU 是不是打满/有没有 swap；② vmstat 1 看 r（运行队列）和 cs（上下文切换）是否异常；③ 看下游依赖（DB 慢查询、Redis 延迟、RPC 超时率）；④ 看是不是流量结构变了（来了个大客户、某个批量接口被调用、缓存集体失效）。大多数情况是④。
