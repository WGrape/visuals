跨语言开销

不是免费的

每次 Go 调 C 都要做一次栈切换与参数转换（runtime 进入 C 线程上下文），开销远高于普通 Go 调用；高频调用会成瓶颈。

cgo 调用无法被 Go 调度器管理，调用期间占用一个 OS 线程（g0/m 的 C 栈），大量并发 C 调用会吃光线程。

cgo 做了什么：在两个世界之间搭桥

cgo 让你在 Go 里调用 C 函数、使用 C 的库。但它不是「免费的函数调用」——每次跨越边界都要切换栈、切换调用约定，并且会占用一个操作系统线程。

Go 与 C 两个世界的边界与代价
栈切换调用 C 前从 goroutine 栈切到系统栈。
占住 MC 执行期间该线程无法服务其他 goroutine。
GC 看不见C 分配的内存不受 GC 管理，必须手动释放。
交叉编译难启用 cgo 后需要目标平台的 C 工具链。

指针传递规则：最容易踩的雷

不能长期保存 Go 指针

C 代码不能把传入的 Go 指针保存起来，等 Go 侧返回后再使用。

  • Go 的堆对象会被 GC 移动或回收
  • cgo 有运行时检查（cgocheck）会直接报错
  • 需要长期保存就在 C 侧 malloc 并拷贝一份

C 内存必须手动释放

GC 完全不知道 C 分配了什么。

p := C.malloc(C.size_t(1024)) defer C.free(p) // 忘了就是泄漏 // 典型泄漏：循环中 C.CString 却没 free for _, s := range list { cs := C.CString(s) C.process(cs) // 缺 C.free(unsafe.Pointer(cs)) }

别在 C 回调里用 Go

从 C 回调进 Go 需要额外通道，且仍受栈与调度约束。

  • 用 //export 导出函数供 C 调用
  • 回调中不要做阻塞操作
  • 注意不要在回调里触发大量分配

什么时候别用 cgo

能用纯 Go 就用纯 Goencoding/json、crypto 等多数场景纯 Go 已够快
系统调用用 syscall简单系统调用不必引入 cgo
追求交叉编译启用 cgo 后 CGO_ENABLED=0 的静态构建失效
追求小镜像需要 C 运行库，distroless/scratch 部署变复杂
高频小调用单次开销相对大，应批量化或改纯 Go
必须用闭源库只有头文件和 .so 时，cgo 仍是合理选择

替代方案优先级：纯 Go 实现 → syscall / x/sys → cgo → 独立进程 + RPC。把 C 依赖放到独立进程里，用本地 socket 通信，能换回完整的交叉编译与崩溃隔离，代价是多一次 IPC。

深入自检

为什么 cgo 调用多的时候线程数暴涨？

每次 cgo 调用都会占住一个 M，且这段时间它不能执行其他 goroutine。运行时为了保证并发度会新建线程，于是线程数远超 GOMAXPROCS。这不是泄漏，是 cgo 的固有行为。

cgo 调用会阻塞调度器吗？

不会阻塞整个调度器，但会占用一个线程。若大量 goroutine 同时进入 cgo，线程数会随并发调用数增长。控制并发 cgo 调用数是常见的优化手段。

C.CString 忘了 free 会怎样？

每次调用都在 C 堆上分配一块内存，Go 的 GC 完全看不到它，于是持续增长直到进程 OOM。这类泄漏在 pprof 的 Go heap 里看不到，需要用系统级工具（如 valgrind、RSS 监控）发现。

为什么禁用 cgo 后有些包不能用？

部分标准库和第三方包依赖 cgo（如 os/user、net 的某些解析路径、数据库驱动）。设置 CGO_ENABLED=0 时会走纯 Go 的替代实现，功能可能有细微差异，需要实测验证。

cgo 调用的性能大概什么量级？

单次跨边界调用的开销通常在几十到上百纳秒量级，远高于普通函数调用。因此正确的用法是批量化：一次调用处理一批数据，而不是在循环里逐条调用。

cgo 的代价与适用场景

cgo 不是「Go 调 C」那么简单：每次跨越边界都要切换栈、切换调度模型、可能阻塞 M。先量化代价，再决定要不要用。

代价项数字/表现说明
单次调用开销~50~150 ns（纯 Go 函数调用约 1~5 ns）差 20~100 倍
栈切换从 Go 的可增长栈切到系统栈每次调用都要做
调度影响C 调用期间占住整个 M（系统线程）C 函数阻塞会占掉一个线程
GMP 影响C 阻塞时不算在 GOMAXPROCS 里，Go 会新建 M大量 cgo 调用会看到线程数暴涨
无法内联/逃逸分析跨语言边界，编译器优化全失效
构建需要 C 编译器，交叉编译失效CGO_ENABLED=0 才能静态编译

cgo 基本用法

package main

/*
#include <stdlib.h>
#include <string.h>

static int add(int a, int b) { return a + b; }

static char* dup_str(const char* s) {
    char* p = (char*)malloc(strlen(s) + 1);
    strcpy(p, s);
    return p;                       // C 分配的内存，Go 侧必须手动释放
}
*/
import "C"
import "unsafe"

func main() {
    // 1) 简单类型直接传
    r := C.add(C.int(1), C.int(2))

    // 2) 字符串：Go string -> C char*
    cs := C.CString("hello")
    defer C.free(unsafe.Pointer(cs))        // 必须释放！CString 用的是 C 的 malloc

    // 3) C char* -> Go string
    cp := C.dup_str(cs)
    s := C.GoString(cp)
    C.free(unsafe.Pointer(cp))              // C 侧分配的，也要释放

    // 4) 切片传指针（不要传 Go 指针给 C 长期保存！）
    buf := make([]byte, 1024)
    C.memcpy(unsafe.Pointer(&buf[0]), unsafe.Pointer(cs), 5)
    _ = r; _ = s
}

longC.longint64（Linux 64 位）
char*C.CString / C.GoStringstring

structC.struct_xxxstruct{...}（字段布局需对齐）

  • Go 指针不能传给 C 长期保存——这是 cgo 的硬性规则。Go 的 GC 会移动/回收对象，C 侧持有的指针会失效。必须存的话，先在 C 侧 malloc 一份拷贝过去。
  • C 代码不能回调 Go 并长期持有 Go 内存——同样原因。回调可以，但传入的 Go 指针只在回调期间有效。
  • C.CString / C.CBytes 分配的内存必须手动 C.free，否则泄漏（Go GC 管不到）。这是 cgo 最常见的内存泄漏源。
  • 不要在热路径调 cgo：如果循环里调 100 万次，150ns × 100 万 = 0.15 秒纯开销。正确做法是把循环移进 C 侧，一次调用处理整批数据。

纯 Go 重写逻辑不复杂最快、可交叉编译、首选

为什么 cgo 这么慢？

因为它跨越了两个完全不同的运行时边界：① 栈切换——Go 用的是可增长的 goroutine 栈，C 需要系统栈，调用时要切换；② 调度器让渡——进入 C 前要通知调度器「这个 M 要离开 Go 世界」，保证 GC 不会在不知情的情况下扫描/移动栈；③ 阻塞语义——Go 假设 C 调用可能长时间阻塞，会把它当作阻塞系统调用处理。这些都是必要的正确性开销。

怎么判断 cgo 是不是性能瓶颈？

① pprof 里看 runtime.cgocall 的占比（超过 10% 就要警惕）；② 看进程线程数——cgo 调用多时线程数会远超 GOMAXPROCS（用 ps -o nlwp 看）；③ 做个 A/B：把 cgo 调用换成空函数，看 QPS 变化。最快的优化通常是批量化：把 N 次调用合成 1 次。

交叉编译和 cgo 冲突怎么解决？

核心矛盾：cgo 需要目标平台的 C 编译器和目标平台的 C 库。三条路：① CGO_ENABLED=0——最简单，前提是依赖的库有纯 Go 实现（如用纯 Go 的 SQLite 驱动代替 cgo 版）；② 用交叉编译工具链（如 x86_64-linux-musl-gcc + CC 环境变量）；③ 在目标平台的容器/机器上构建。Docker 多阶段构建 + musl 是生产上最常见的方案。
