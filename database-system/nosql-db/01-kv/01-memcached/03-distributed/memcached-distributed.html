先建立直觉：把人和座位排在同一个圆环上

普通哈希分片（hash(key) % N）的问题是：N 一变，几乎所有 key 的映射都变了。从 3 台扩到 4 台，大约 75% 的 key 会跑到新位置——缓存几乎全部失效，数据库瞬间被压垮。

一致性哈希换了个思路：把节点和 key 都映射到一个顺时针的环上（想象 0~2³² 的圆环）。key 顺时针遇到的第一个节点就是它的归属。这样增删节点只影响环上相邻的一小段——从 N 台扩到 N+1 台，只有约 1/N 的 key 需要迁移。

一致性哈希原理

第一个节点 扩容 N4 加入时： 只有 N3→N4 弧段上的 key 需要迁移（约 1/N） 其余 key 归属不变

虚拟节点：解决负载不均

问题：节点数量少时，它们在环上的位置可能分布不均，导致某些节点承担远多于其他的 key（数据倾斜）。

解法：虚拟节点——每个物理节点映射到环上的多个位置（如 150~200 个虚拟节点）。这样环上点位密集且均匀，负载自然均衡。

方案虚拟节点数负载均衡
无虚拟节点1❌ 节点少时严重倾斜
少量虚拟节点10~50⚠️ 一般
大量虚拟节点150~200✅ 良好（推荐）

关键特性与限制

特性说明
服务端无集群各实例互不相识，不通信、不复制、不故障转移
客户端路由客户端持有实例列表，按一致性哈希决定发往哪个实例
无数据冗余每个 key 只存在一个实例上，该实例宕机 → 其数据全部丢失
扩容影响约 1/N 的 key 需重新映射 → 这部分缓存 miss
节点宕机的后果比想象中严重。Memcached 没有副本机制——某实例挂掉，它上面的所有 key 全部消失，这些请求全部穿透到数据库。如果有 10 个实例挂掉 1 个，就意味着约 10% 的流量瞬间打到数据库。缓解：① 部署足够多的实例，降低单实例故障的影响面；② 数据库侧做好限流与熔断；③ 关键业务考虑改用 Redis Cluster（有副本与自动故障转移）。

扩容的正确姿势

  1. 在低峰期操作：扩容会导致约 1/N 的 key miss，避免在高峰期放大冲击；
  2. 分批加入：一次加太多节点会造成大规模 miss；
  3. 预热新节点：如果可能，提前把将要迁移的 key 加载进去；
  4. 监控数据库 QPS：扩容后观察是否有穿透尖峰；
  5. 确保客户端一致性哈希实现一致：不同客户端库的实现细节不同（哈希函数、虚拟节点数），混用会导致同一个 key 被路由到不同实例——这是很隐蔽的 bug。
最后一是最容易踩的坑：如果服务 A 用 Java 客户端、服务 B 用 Python 客户端，而两者的一致性哈希实现（哈希算法、虚拟节点数量、节点排序方式）不一致，那么同一个 key 在不同服务眼里属于不同实例——缓存命中率会莫名其妙地低。务必统一客户端实现与配置。

🎯 面试问答

Q：一致性哈希解决了什么问题？
A：解决扩缩容时缓存大规模失效的问题。普通取模分片 hash(key) % N 在 N 变化时会让几乎全部 key 重新映射（3→4 台约 75% 失效），导致缓存雪崩。一致性哈希把节点和 key 映射到同一个环上，增删节点只影响环上相邻的一小段，仅约 1/N 的 key 需要迁移，把冲击降了一个数量级。

Q：为什么需要虚拟节点？
A：为了解决负载不均。物理节点较少时，它们随机落在哈希环上的位置可能很不均匀——某些节点负责的弧段很长，承担远多于其他节点的 key（数据倾斜）。虚拟节点让每个物理节点在环上占多个位置（通常 150~200 个），环上点位变得密集均匀，负载自然就均衡了。虚拟节点越多分布越均匀，但元数据开销越大——150~200 是常用取值。

Q：Memcached 节点宕机了会怎样？
A：它没有副本和故障转移机制——某实例宕机，其上的所有 key 全部丢失，访问这些 key 的请求全部穿透到数据库。若有 10 个实例挂 1 个，约 10% 流量瞬间打到数据库，可能引发连锁故障。缓解：部署较多实例降低单点影响面、数据库侧做限流熔断、客户端快速剔除故障节点。如果对可用性要求高，应考虑 Redis Cluster——它有副本复制和自动故障转移。

Q：不同语言的客户端能混用吗？
A：要非常小心。一致性哈希没有强制的统一标准，各客户端库在哈希函数、虚拟节点数量、节点排序方式上可能有差异。如果服务 A 用 Java 客户端、服务 B 用 Python 客户端而实现不一致，同一个 key 会被路由到不同实例，导致缓存命中率莫名其妙偏低。务必：① 统一客户端库的一致性哈希实现；② 明确配置相同的虚拟节点数；③ 上线前用同一个 key 在不同客户端验证路由结果一致。
