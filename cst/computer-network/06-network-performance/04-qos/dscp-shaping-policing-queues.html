QoS、DSCP、整形与监管：视频会议卡顿时该怎么分配带宽

用语音和备份共用出口的例子区分标记、排队、整形和直接丢弃。

先看瓶颈在哪里

语音包小但对时延和抖动敏感，云备份包大且可容忍等待。两者共用 20 Mbps 上行，若备份长期占满链路，语音会在路由器或运营商设备排队。QoS 的作用是让网络按业务目标安排有限的发送机会；它不能创造额外物理带宽，也不能修复服务器自身处理慢。实施前要找到真正瓶颈，确定上行还是下行，并测空闲与负载时的延迟。

若本地路由器以 100 Mbps 发向实际只有 20 Mbps 的运营商接入链路，排队可能发生在运营商不可控设备。可在本地略低于实际瓶颈速率整形，让队列回到可控位置，再给实时流合理调度。测速数值波动时应留余量，避免高峰时整形速率反而大于真实线路。

DSCP 是标签，不是保证

IP 头中的 DSCP 字段可标记业务期望的转发类别。网络设备可按它进入不同队列，或在边界重写、忽略它。把语音标成高优先级但出口设备完全不读 DSCP，效果为零；跨运营商路径也不能假定标记始终保留。标记应在可信边界分类，不能让任意用户把所有大流都自称最高优先级。

DSCP 影响的是逐跳处理策略，不证明报文已经加密或拥有业务权限。设计时记录入口如何分类、设备如何映射到队列、出口是否重写，再用实际抓包和队列计数验证。

整形与监管的不同动作

整形 shaping 把超出设定速率的流量暂存并平滑发出，所以增加等待但可减少瞬时丢包；监管 policing 在超出令牌桶或速率限制时直接丢弃或重新标记，通常更容易触发 TCP/QUIC 降速。两者都可用令牌桶描述突发额度，但副作用不同。对实时语音，过大整形队列会造成延迟；对备份，适当整形往往比让运营商设备盲目丢包更可控。

假设上行 20 Mbps，备份持续发 18 Mbps，会议高峰需要 4 Mbps，总需求 22 Mbps。必须降备份、缓冲它或丢掉部分流量；不存在只改 DSCP 就让两者都稳定达到各自峰值的魔法。可给实时队列合理保留并限制备份速率，同时监控总吞吐和备份完成时间。

令牌桶还能区分短时突发与长期超额。假设监管速率为 10 Mbps、桶里预留 1 Mb 令牌，一次短突发可先消耗令牌；若持续以 20 Mbps 发送，令牌很快耗尽，超额包会被丢弃或降级。整形则把部分超额包留在队列里等待令牌恢复。比较两种策略时，要看突发后队列多久排空、业务 P99 延迟及重传量，而不是只看平均速率是否达到 10 Mbps。

优先队列的饥饿风险

严格优先队列先发高优先级包，低优先级在高优先级持续满载时可能长期得不到机会。若把所有业务都标高优先级，分类失去意义，也可能让普通业务饥饿。可为实时类设置带宽上限或保证、为普通类使用公平队列，让重要流量优先但不无限吞噬链路。不同设备支持的队列算法、缓冲和调度粒度不同，配置前要看实测。

QoS 还受包大小影响。一条 1500 字节大包一旦开始在慢链路发送，后来的小语音包必须等这一个包发完；更好的排队调度只能影响后续包，不能瞬间中断已在物理线上发送的帧。

与拥塞控制的交互

TCP/QUIC 依据丢包、ECN 和 RTT 等信号调节发送量。监管丢包可让大流降速，但也增加重传；整形可降低丢包，却可能形成深队列，使 RTT 上升。AQM 与公平队列可在队列持续变深前反馈拥塞，通常需要与端点行为配合。QoS 配置应同时看语音 P99 延迟、备份吞吐、丢包和队列长度，而不是只看某条规则的命中计数。

如果应用本身突发超出能力，网络 QoS 只能做最后一层保护。业务侧还应限速、分批发送或在高峰暂停备份。

一次验收实验

先无备份测会议端到端抖动与丢包，再启动备份，观察上行队列和 P95/P99 延迟。随后仅改变整形速率与队列策略，重复相同负载，报告会议质量和备份完成时长。若会议改善但备份几乎停滞，检查优先队列是否让低优先级饥饿。再模拟多个会议并发，确认高优先级类自身不会把链路打满。

跨多个站点时，分别确认每个瓶颈设备理解同一 DSCP 策略；只在入口标记、出口不识别，无法保障端到端体验。

QoS 配置

# 打 DSCP 标记（iptables）
iptables -t mangle -A POSTROUTING -p udp --dport 5060 -j DSCP --set-dscp 46   # SIP 语音
iptables -t mangle -A POSTROUTING -p tcp --dport 22 -j DSCP --set-dscp-class CS6

# Linux 队列（HTB：分层令牌桶）
tc qdisc add dev eth0 root handle 1: htb default 30
tc class add dev eth0 parent 1: classid 1:1 htb rate 100mbit ceil 100mbit
tc class add dev eth0 parent 1:1 classid 1:10 htb rate 30mbit ceil 100mbit prio 1   # 高优先
tc class add dev eth0 parent 1:1 classid 1:20 htb rate 50mbit ceil 100mbit prio 2   # 中
tc class add dev eth0 parent 1:1 classid 1:30 htb rate 20mbit ceil 80mbit  prio 3   # 低
# 按 DSCP 分流到不同 class
tc filter add dev eth0 protocol ip parent 1:0 prio 1 handle 46 fw flowid 1:10

# 限速（TBF：令牌桶）
tc qdisc add dev eth0 root tbf rate 10mbit burst 32kbit latency 50ms

# 查看与统计
tc -s qdisc show dev eth0
tc -s class show dev eth0
tc filter show dev eth0

# 抓包看 DSCP
tcpdump -i eth0 -nn -v ip | grep -i tos

Shaping vs Policing 与落地

维度Shaping（整形）Policing（监管）
超出速率时缓存排队（延迟增加）直接丢弃或降级标记
方向只能用于出方向出入方向都可以
延迟影响引入排队延迟不引入延迟
突发容忍能吸收突发超出即丢
典型命令tc tbf / htbiptables limit / tc police
适用自己出口要做平滑（如对接运营商固定带宽）接入口限制对方速率

令牌桶参数：CIR（承诺速率）、CBS（承诺突发大小，桶容量）、EIR/EBS（超额速率与超额突发）。桶容量决定了能容忍多大的突发：CBS 太小 → 正常突发也被丢；太大 → 限速形同虚设。经验值 CBS ≈ CIR × 目标延迟。

  • DSCP 只在你的网络里有效：出公网时绝大多数运营商会重置 DSCP 为 0（不信任客户标记）。所以 QoS 主要用于企业内网和 IDC 内部，公网加速要靠专线或 CDN。
  • 不要过度分类：8 个队列通常够了。分太多队列会让配置复杂、排障困难，且每个队列都要分配带宽保证，反而降低利用率。
  • 优先队列的副作用：高优先队列若不限速，会饿死低优先队列。必须给每个 class 配 rate（保证）和 ceil（上限）。
  • HTB 的借用机制：ceil 高于 rate 时，空闲带宽可被借用（提高利用率），拥塞时按比例收回。这是 HTB 比单纯限速好用的地方。
  • 排障顺序：① tc -s class 看各队列是否真的有流量（分类是否正确）；② 看 dropped 计数（判断是否被限速/丢弃）；③ 抓包确认 DSCP 标记是否被打上、是否被中间设备改写；④ 确认是否在正确的方向（shaping 只能出方向）。
为什么我配了 QoS 但没有效果？

三种常见原因：① 标记没打上或被打在错误位置（要在流量进入队列之前打）；② 队列没按 DSCP 分流（缺 tc filter）；③ 出公网被运营商重置 DSCP。先在内网可控链路上验证。

限速用 shaping 还是 policing？

限制自己发出的流量用 shaping（平滑，避免 TCP 因突发丢包而降窗）；限制别人发来的流量用 policing（直接丢，让对方的 TCP 感知并降速）。入方向无法 shaping——包已经到了。

自检

给所有流量都标最高 DSCP，是否能让所有请求更快？

不能。物理带宽不变，分类失去区分作用，高优先级持续满载还可能导致其他队列饥饿。
