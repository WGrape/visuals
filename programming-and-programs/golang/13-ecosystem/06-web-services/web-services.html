REST vs gRPC

各有所长

REST/JSON 易调试、浏览器友好、生态广；gRPC/Protobuf 强类型、低延迟、流式，适合服务间高频调用。

网关

统一出入口

API 网关做路由、鉴权、限流、熔断；Go 写网关（如基于 gin/kratos）性能强，是微服务常见落点。

内部用 gRPC、对外暴露 REST 时，常由网关做协议转换与聚合。
框架定位

按需取舍

Gin 轻量灵活、生态大；go-zero 内置服务治理（限流/熔断/缓存）；选框架看团队与治理需求，而非一味追新。

本仓库已有专页

Gin、go-zero 等框架的深入用法见 13-ecosystem 下的对应页面，本篇只做生态定位。

怎么选

看边界

对外/前端 → REST；内部高频/流式 → gRPC；要治理 → 带中间件的框架；小服务 → 标准库也能扛。

⚠️ 别为「看起来高级」引入 gRPC；REST 在多数业务场景仍是最省心的选择。

Go 的 Web 技术栈全景

Go 的 Web 生态有一个显著特点：标准库足够强。很多团队直接用 net/http 就能交付，框架更多是提供工程约定与效率工具。

选型：什么时候用什么

直接用标准库

适合：接口少、依赖少、追求可控与稳定。

  • Go 1.22 起路由能力已够用
  • 零第三方依赖，升级成本低
  • 需要的功能自己写几十行中间件

轻量框架（gin/echo/chi）

适合：接口较多，需要路由分组、绑定、校验等成套能力。

  • gin 生态最大、性能口碑好
  • echo 结构清晰、文档友好
  • chi 贴近标准库，中间件生态丰富

全栈框架（go-zero/kratos）

适合：中大型团队，需要代码生成、规范统一与配套治理能力。

  • 从 api 或 proto 生成代码，减少样板
  • 内建限流、熔断、缓存、链路
  • 代价是学习成本与框架约束

服务分层：HTTP 进来之后怎么走

请求 → 中间件（日志/鉴权/限流/恢复） → 路由匹配 → Handler：解析与校验参数 → Service：业务规则与事务编排 → Repo/DAO：数据访问（DB / Cache / RPC） → 组装响应与错误 // 典型 Handler 只做三件事 func (h *Handler) CreateOrder(w http.ResponseWriter, r *http.Request) { var req CreateOrderReq if err := decodeAndValidate(r, &req); err != nil { writeErr(w, err) // ① 解析校验 return } res, err := h.svc.Create(r.Context(), &req) // ② 交给业务层 if err != nil { writeErr(w, err) return } writeJSON(w, res) // ③ 输出 }
Handler 保持薄只做协议转换，不含业务规则
业务层可测不依赖 HTTP，便于单测
ctx 一路传超时与取消才能真正生效
错误统一出口一处转换为响应格式

深入自检

Go 写 Web 一定要用框架吗？

不一定。标准库 net/http 已经覆盖了路由、中间件、静态文件、TLS 等基础能力，Go 1.22 后路由还增强了。框架的价值在于约定与效率，团队小、接口少时不用框架反而更省心。

gin 和 echo 该怎么选？

两者都能胜任大多数场景。gin 生态与资料最多、性能口碑好；echo 的 API 设计更规整、文档清晰。若团队已有经验就沿用，没有强约束时按社区活跃度与文档质量选。

go-zero 这类全栈框架适合什么场景？

中大型团队、需要统一工程规范与内建治理能力（限流、熔断、链路、缓存）的场景。它用代码生成减少样板，但也带来约定与学习成本。小项目接入会显得过重。

ORM 该不该用？

取决于团队对 SQL 的掌控度。贴近 SQL 的写法（database/sql + sqlx）可控性最好，出问题容易排查；ORM（gorm、ent）能显著提升开发效率，但复杂查询需要理解它的行为，且容易产生意外 SQL。

HTTP 和 gRPC 怎么选？

对外（浏览器、第三方）用 HTTP/JSON；内部服务间高频调用用 gRPC（强类型、二进制、流式支持）。很多团队是「外部 HTTP 网关 + 内部 gRPC」，在网关做协议转换。

Go Web 服务的关键配置

项目默认值建议 / 说明
http.Server.ReadTimeout0（不限）5~10s；从连接建立到读完请求
ReadHeaderTimeout02s；防 Slowloris 慢速攻击
WriteTimeout010~30s
IdleTimeout060~120s；keep-alive 空闲上限
MaxHeaderBytes1MB请求头大小上限
MaxRequestBody无（需自己控制）用 http.MaxBytesReader 限制
Gin 的 TrustedPlatform空反代后要设，否则 ClientIP() 拿到的是代理 IP
GOMAXPROCSCPU 核数容器里要显式设（或用 automaxprocs）
容器内存 limit—Go 不感知 cgroup 限制，要用 SetMemoryLimit（1.19+）

容器里的经典问题：Go 的 GOMAXPROCS 读的是宿主机的 CPU 核数，在限制为 2 核的容器里可能设成 64，导致大量 goroutine 争抢 2 个核，调度开销剧增。解决：用 go.uber.org/automaxprocs，或容器设 GOMAXPROCS=2。同理 GC 也不感知 cgroup 内存限制，1.19+ 用 debug.SetMemoryLimit。

中间件与框架代码

// 1) 超时与请求体大小限制
func limitBody(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        r.Body = http.MaxBytesReader(w, r.Body, 8<<20)   // 8MB，超过返回 413
        next.ServeHTTP(w, r)
    })
}

// 2) 超时中间件（每个请求独立的 deadline）
func timeout(d time.Duration) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            ctx, cancel := context.WithTimeout(r.Context(), d)
            defer cancel()
            next.ServeHTTP(w, r.WithContext(ctx))
        })
    }
}

// 3) 恢复 panic（否则一个 panic 会打挂整个服务）
func recoverer(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if err := recover(); err != nil {
                log.Printf("panic: %v\n%s", err, debug.Stack())
                http.Error(w, "internal error", 500)
            }
        }()
        next.ServeHTTP(w, r)
    })
}

// 4) 优雅退出（K8s 必须）
srv := &http.Server{Addr: ":8080", Handler: mux}
go srv.ListenAndServe()
quit := make(chan os.Signal, 1)
signal.Notify(quit, syscall.SIGTERM, syscall.SIGINT)
<-quit
ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
defer cancel()
srv.Shutdown(ctx)      // 停止新请求，等待进行中的完成
// 5) 健康检查（K8s 探针必需，不能带业务逻辑）
mux.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
    w.WriteHeader(200); w.Write([]byte("ok"))          // liveness：进程活着就行
})
mux.HandleFunc("/readyz", func(w http.ResponseWriter, r *http.Request) {
    if err := db.PingContext(r.Context()); err != nil {  // readiness：依赖就绪
        http.Error(w, "db down", 503); return
    }
    w.WriteHeader(200); w.Write([]byte("ready"))
})
// 关键：liveness 不要检查依赖，否则依赖抖动会导致 Pod 被反复重启

// 6) 优雅处理 context 取消（避免 goroutine 泄漏）
func handler(w http.ResponseWriter, r *http.Request) {
    ctx := r.Context()
    rows, err := db.QueryContext(ctx, "SELECT ...")   // 用 QueryContext 不是 Query
    if err != nil {
        if errors.Is(err, context.Canceled) {
            return          // 客户端断了，直接返回，别写响应
        }
        http.Error(w, "err", 500); return
    }
    defer rows.Close()
    // ...
}

排障清单

症状原因处理
容器里 CPU 高但吞吐低GOMAXPROCS 按宿主机核数设置用 automaxprocs，或显式设 GOMAXPROCS
容器里 OOMGo 不感知 cgroup 内存限制1.19+ 用 debug.SetMemoryLimit；或设 GOGC 降低
一个 panic 打挂服务没有 recover 中间件加 recover 中间件；Gin 用 gin.Recovery()
滚动更新时 502没做优雅退出srv.Shutdown + K8s preStop sleep
ClientIP() 拿到代理 IP没设 TrustedPlatformGin 设 SetTrustedProxies 或用 X-Forwarded-For
goroutine 泄漏客户端断开后处理还在跑用 r.Context()；DB 调用带 Context
慢客户端拖死服务没设 ReadHeaderTimeout设 2s；前面加 Nginx 缓冲请求
大请求体把内存打爆没限制 body 大小http.MaxBytesReader；Nginx 的 client_max_body_size

liveness 与 readiness 必须分开：liveness 只检查「进程是否存活」，readiness 才检查「依赖是否就绪」。如果把 DB 检查放进 liveness，DB 抖动会导致所有 Pod 被反复 kill 重启，故障放大。
