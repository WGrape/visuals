先建立直觉：图书借阅排行榜

图书馆按「累计借阅次数」决定哪些书下架。听起来合理，但有两个问题：

  • 问题一：一本十年前的畅销书累计借阅 5000 次，现在根本没人看，却因为分数高永远不下架（历史包袱）。
  • 问题二：一本刚上架的新书借阅 0 次，立刻就被下架了，永远没机会变热（新数据饥饿）。

所以实用的 LFU 必须做两件事：让老分数随时间衰减（老化），给新书一点初始分或保护期。

基础结构：频次分桶

朴素做法是每次淘汰时遍历全部 key 找最小频次（O(n)），不可接受。正确做法是按频次分桶：相同频次的数据放在一个桶里，桶之间用链表串起来，淘汰时直接取最小频次桶。

桶内为什么还要 LRU？因为同一频次的多个数据，需要一个稳定的淘汰顺序，否则任意性太大。桶内按最近访问排序，等价于「频次相同时用 LRU 兜底」。

老化：让历史分数随时间衰减

这是解决历史包袱的关键。常见做法：

方式做法特点
定期减半每隔一段时间所有计数 /= 2简单，衰减较猛
减固定值定期所有计数 -= k低频数据更快归零
时间衰减计数乘以一个随时间衰减的因子平滑，Redis LFU 采用
滑动窗口 LFU只统计最近一个时间窗口内的访问最彻底，但需保留窗口数据
// Redis LFU 的做法（简化理解）
// 计数只有 8 bit（0~255），用概率递增：频次越高越难再涨
// 并配有衰减因子 lfu-decay-time：距离上次访问越久，衰减越多

// 概率递增：不是每次访问都 +1
double p = 1.0 / (baseval * lfu_log_factor + 1);
if (random() < p) counter++;

// 衰减：获取时按「距上次访问的分钟数 / decay_time」扣减
int decay = (now_minutes - last_access) / lfu_decay_time;
counter = max(0, counter - decay);
为什么用概率递增？计数只有 8 bit，如果严格 +1，一个访问 300 次的热点会溢出。概率递增让计数增长越来越慢（对数型），用极小的空间表达「访问了很多次」这个语义，且天然区分热度层级。

新数据保护

问题：新数据频次为 1，会立刻成为最小频次桶的成员，下一次淘汰就被选中——永远来不及变热。
解法做法
初始频次不为 0新数据进来直接给一个中等频次（如 5），获得缓冲期
准入阶段独立先用 LRU 窗口筛选，通过后才进入 LFU 主区（W-TinyLFU 的思路）
保护期新数据在一段时间内不参与淘汰

负载特征LRU朴素 LFULFU + 老化

结论：朴素 LFU 问题很多，必须配套老化与新数据保护才有实用价值。这也是为什么生产上更常见的是 W-TinyLFU、ARC 这类混合策略，而非纯 LFU。

🎯 面试问答

Q：LFU 的计数器会无限增长吗？
A：朴素实现会（访问百万次计数就是百万），所以必须限制位宽并配合衰减。Redis 的做法：计数只占 8 bit（上限 255），并采用概率递增——频次越高，再涨一次的概率越低（对数型增长），既避免溢出又节约内存；同时用 lfu-decay-time 让久未访问的计数随时间衰减。

Q：老化和「滑动窗口」有什么区别？
A：老化是对现有计数做衰减（保留计数，只是变小），实现轻量；滑动窗口是只统计最近窗口内的访问（需要额外记录窗口数据），更准确但更重。Redis 用前者（省内存），一些本地缓存用后者（更准）。共同目标都是：让频次反映「近期热度」而非「历史累计」。

Q：为什么 LFU 需要桶内再按 LRU 排序？
A：因为同一频次下可能有多个数据，需要一个确定性且合理的淘汰顺序。如果随意挑一个，可能会淘汰掉「刚访问过但恰好频次相同」的数据。桶内按最近访问排序，相当于频次相同时用 LRU 兜底，兼顾两者的优点。

Q：生产上该自己实现 LFU 吗？
A：基本不需要。Redis 已内置 allkeys-lfu / volatile-lfu；Caffeine 的 W-TinyLFU 在多数场景下优于手写 LFU。自己实现的价值在于理解「频次统计 + 老化 + 新数据保护」这三件事为什么缺一不可。真要自研，建议直接实现 W-TinyLFU 或 ARC。
