如何选择

看时机

编译期已知结构 → 代码生成；类型在运行期才确定 → 反射；想分析/改写代码 → go/ast。

⚠️ 反射绕开类型系统，维护成本高；能用生成的就别反射，能用接口的就别反射。

反射三定律：reflect 的心智模型

反射让程序在运行时检查与操作自身的结构。理解下面三条，能避开绝大多数使用错误。

反射三定律：取出来、还原回去、可设置才能改
TypeOf拿到类型信息：名字、字段、方法。
ValueOf拿到值信息：可取、可设、可调用。
Kind底层种类，判断分类必须用它。
CanSet改之前先判断，否则会 panic。

反射的典型用法

// ① 遍历结构体字段与 tag t := reflect.TypeOf(User{}) for i := 0; i < t.NumField(); i++ { f := t.Field(i) fmt.Println(f.Name, f.Type, f.Tag.Get("json")) } // ② 通过反射设置字段（必须传指针） func SetField(obj any, name string, value any) error { v := reflect.ValueOf(obj) if v.Kind() != reflect.Ptr || v.Elem().Kind() != reflect.Struct { return errors.New("need pointer to struct") } f := v.Elem().FieldByName(name) if !f.IsValid() || !f.CanSet() { return errors.New("field not settable") } fv := reflect.ValueOf(value) if !fv.Type().AssignableTo(f.Type()) { return errors.New("type mismatch") } f.Set(fv) return nil } // ③ 动态调用函数 fn := reflect.ValueOf(strings.ToUpper) out := fn.Call([]reflect.Value{reflect.ValueOf("go")}) fmt.Println(out[0].String()) // GO
遍历字段序列化、校验、ORM 映射的基础
读取 tagtag.Get 拿不到就返回空串
动态调用Call 的参数与返回都是 []reflect.Value
判断 nilinterface/map/ptr/func/chan/slice 才能 IsNil
零值判断用 IsZero 而不是和零值比较
导出字段非导出字段不能 Set，会 panic

反射的代价与替代方案

维度反射替代方案
性能明显更慢，且难以内联代码生成、泛型、直接调用
类型安全运行时才发现错误泛型在编译期检查
可读性逻辑隐晦，难调试显式代码更易维护
灵活性最高，可处理未知类型生成式方案需要预先知道类型
// 泛型能在不少场景替代反射（Go 1.18+） func Map[T, R any](in []T, f func(T) R) []R { out := make([]R, 0, len(in)) for _, v := range in { out = append(out, f(v)) } return out } // 对比反射版：无运行时开销，编译期检查类型 // 结论：能静态表达的就用泛型，只有真正「运行时才知道结构」才用反射

该用反射的地方

  • 序列化与反序列化（encoding/json）
  • 依赖注入与配置绑定
  • ORM 与参数校验库
  • 测试框架的 mock 与断言
  • 写通用工具库且类型无法预知

不该用的地方

  • 热路径上本可以静态写明的逻辑
  • 只为省几行代码而引入
  • 可以用泛型表达的通用逻辑
  • 能用代码生成提前确定的映射

安全守则

  • 取值前先 IsValid
  • 设置前先 CanSet
  • 类型断言前先 Kind/Type 判断
  • 不确定时用 recover 兜底

深入自检

为什么传值进去反射改不了？

reflect.ValueOf(x) 得到的是 x 的副本，对它 Set 不会影响原变量，且 CanSet 为 false。必须传指针 reflect.ValueOf(&x)，再 .Elem() 拿到指针指向的可设置值。

Type 和 Kind 到底看哪个？

判断「是什么分类」（结构体、切片、整数）用 Kind，因为自定义类型不会改变底层种类；需要名字、字段、方法等具体信息时才用 Type。混用会导致自定义类型判断失败。

反射真的很慢吗？

是的，通常比直接调用慢一个数量级以上，且会阻碍内联与逃逸分析优化。但只在热路径上才需要担心——配置加载、启动期映射这类一次性操作完全可以接受。

Go 有泛型了，反射还会被淘汰吗？

不会完全淘汰。泛型解决「类型参数化」，反射解决「运行时才知道结构」。像 JSON 编解码必须处理任意传入的类型，这类场景仍然依赖反射。但两者确实有重叠，能用泛型时应优先用泛型。

反射代码怎么避免 panic？

严格遵守三步检查：IsValid 确认值存在、CanSet 确认可写、AssignableTo 或 ConvertibleTo 确认类型兼容。对不确定的外部输入，还应在入口用 recover 兜底并转换为错误返回。
