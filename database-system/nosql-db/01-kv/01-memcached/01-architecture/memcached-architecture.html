一句话概括设计哲学

Memcached 的一切设计都围绕「简单 + 快」。它不做持久化、不做服务端集群、不支持复杂数据结构、没有事务与 Lua——换来的是极低的单次操作延迟和几乎为零的运维心智负担。当你的需求就是「纯粹的 KV 缓存」时，这个取舍非常划算。

整体架构

1. 多线程 + 非阻塞 I/O

这是 Memcached 与 Redis 在架构上最本质的差异：Memcached 是多线程的。

  • 主线程：只负责 accept() 新连接，然后轮询分发给某个 worker 线程。
  • worker 线程（默认 4 个，-t 调整）：每个 worker 独立持有一个 libevent 事件循环，负责自己那批连接的读、解析、执行、写回。
  • libevent：底层封装 epoll（Linux）/ kqueue（BSD），提供统一的非阻塞 I/O 抽象。

并发安全怎么保证？靠细粒度锁：

需要保护的做法
Slab 分配 / 回收slab 级别的锁（较粗，但操作极快）
哈希表分段锁 / 原子操作
统计计数原子变量
item 的引用计数原子操作 + refcount
和 Redis 的对比记忆：Redis 是「单线程执行命令 + I/O 可选多线程」，靠无锁换简单；Memcached 是「多线程全程处理 + 细粒度锁」，靠多核换取更高吞吐。因为 Memcached 只做简单的 get/set，锁的临界区极短，多线程的优势能充分发挥。

2. Slab 内存分配器（核心）

如果直接用 malloc/free 分配每个 item，会产生大量内存碎片——长期运行后明明有空闲内存却分配不出连续块。Slab 就是为了消灭碎片。

  1. 启动时通过 -m 向操作系统一次性申请一大块内存（如 64MB）。
  2. 把这块内存切成若干 1MB 的 page。
  3. 每个 page 被指派给某个 slab class，并按该 class 的 chunk 大小切成等份。
  4. 存 item 时，找能装下它的最小 class，从该 class 的空闲 chunk 链表里取一块。
slab classchunk size能装下（大致）
class 196 B很小的 key/value
class 2120 Bclass 1 × 1.25

……由 -f（growth factor，默认 1.25）决定
class N最大 1 MB单个 item 上限就是 1MB
两个硬限制：① 单个 item 最大 1MB（value 上限），超过会直接报错；② key 最长 250 字节。这两条是 Memcached 的硬约束，设计时必须遵守。
Slab 的经典问题：内存浪费。一个 100 字节的 value 会被放进 chunk=120 的 class，浪费 20 字节；如果大量 item 的大小刚好卡在两个 class 之间，浪费率会很明显。调优手段：调小 -f（如 1.1）让档位更密，或用 -o slab_reassign 开启 slab 自动重分配，让空闲 page 从冷 class 迁到热 class。

3. 哈希表 + 惰性过期

  • 哈希表：key → item 指针，支撑 O(1) 查找。采用渐进式扩容（迁移时仍有锁保护，不会一次性阻塞）。
  • LRU 链表：每个 slab class 各维护一条。访问过的 item 被移到链表头；需要空间时从尾部淘汰。
  • 惰性过期：不会主动扫描过期 key。只有 get 到某个 key 时才检查它的过期时间——过期就当作不存在并回收 chunk。这样省掉了定期扫描的开销。
注意「LRU 是按 class 独立的」这个细节。这带来一个反直觉现象：全局内存没满，但某个 class 满了，依然会淘汰该 class 里的热数据。这正是 slab 需要调参/开启自动重分配的原因。

4. 无服务端分布式

这是 Memcached 与 Redis Cluster 的第二大差异：Memcached 服务端之间完全不通信，每个实例都是孤岛。

  • ✅ 优点：加机器极其简单（启动新实例 + 更新客户端配置），服务端零协调成本。
  • ❌ 缺点：路由逻辑全在客户端；扩容时命中率会下降（除非用一致性哈希）。
# 客户端（如 spymemcached / pylibmc）做的事：
# 1. 对每个 key 算 hash
# 2. 在「虚拟节点环」上顺时针找第一个节点 → 目标服务器
# 3. 一致性哈希保证：扩容 N→N+1 时只有约 1/(N+1) 的 key 需要迁移

# 服务端完全不知道集群的存在
memcached -m 1024 -p 11211 -t 8 -c 4096

🎯 面试问答

Q：Memcached 的线程模型是怎样的？
A：多线程 + libevent 非阻塞 I/O：主线程只负责 accept 新连接并轮询分发；N 个 worker 线程（默认 4，-t 调整）各自持有一个 libevent 事件循环，独立处理自己那批连接的读、解析、执行、写回。并发安全靠细粒度锁（slab 锁、哈希表分段锁、统计用原子变量、item 用 refcount）。这与 Redis「命令执行单线程」形成鲜明对比——Memcached 因为只做简单的 get/set，锁临界区极短，多线程能充分发挥多核优势。
Q：Slab 分配器解决了什么问题？
A：解决内存碎片。如果每个 item 都直接 malloc/free，长期运行会产生大量不连续的小空洞，导致「有空闲内存却分配不出连续块」。Slab 的做法是：启动时一次性申请一大块内存 → 切成 1MB 的 page → 每个 page 按某个 slab class 的 chunk 大小等分 → 相同大小档位的 chunk 复用。因为同一个 class 内 chunk 大小一致，回收后可以直接复用，几乎不产生碎片。代价是item 大小与 chunk 不匹配造成的内部浪费，可通过调小 -f 或开启 slab 自动重分配缓解。
Q：Memcached 单个 value 最大能存多少？
A：默认上限 1MB（因为单个 page 就是 1MB，chunk 最大不能超过 page）。可以用 -I 参数调大（最大 128MB），但官方并不推荐——大 item 会严重加剧 slab 的内部浪费，并阻塞 worker 线程。正确做法是在业务侧拆分，或者改用没有这个限制的 Redis（value 上限 512MB）。此外 key 最长 250 字节。
Q：Memcached 的过期 key 是怎么清理的？
A：主要靠惰性过期：不会主动扫描全库找过期 key，而是只有 get 到某个 key 时才检查它的过期时间——如果已过期，就当作不存在并返回 miss，同时回收该 chunk。这样完全省掉了定期扫描的 CPU 开销，代价是「过期的 key 如果一直没人访问，会一直占着内存」，直到被 LRU 淘汰。
Q：为什么 Memcached 没有服务端集群？这样利弊是什么？
A：这是它的设计取舍：每个实例完全独立、彼此不通信，路由（一致性哈希）由客户端完成。优点：加机器极其简单（启动新实例 + 改客户端配置），服务端零协调开销，不会出现脑裂、选主等分布式问题；缺点：扩容时命中率会下降（一致性哈希可把影响降到约 1/(N+1)），客户端要实现路由逻辑，也没有服务端的高可用切换（实例挂了就是挂了，靠客户端摘除）。
Q：Memcached 和 Redis 该怎么选？
A：如果你的需求就是纯粹的 KV 缓存、value 较大、想压满多核、不需要持久化和复杂数据结构 → Memcached 更简单更快。如果需要丰富的数据结构（排行榜/队列/集合运算）、持久化、主从高可用、Lua 脚本、事务、发布订阅 → Redis。现实中 Redis 用得远多，因为大多数缓存场景都多少需要一点数据结构能力；Memcached 主要在「极简 KV + 极致吞吐」的传统大型站点（如早期的 Facebook、Wikipedia）中保留优势。
