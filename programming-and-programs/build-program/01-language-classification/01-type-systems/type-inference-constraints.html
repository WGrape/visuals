类型推断：约束生成、合一与多态边界

从简单函数推导类型，再看为什么递归、自引用与副作用会让推断变复杂。

类型推断在推什么

静态类型语言不一定要求程序员给每个变量写注解。编译器可根据表达式产生类型约束，再求出满足约束的类型。例如函数 id(x) = x 的参数先赋一个未知类型 α；返回表达式也是 x，因此返回类型与 α 相同，得到 α→α。调用 id(3) 时，把 α 与整数类型合一，调用结果为整数。这里的推断发生在编译或检查阶段，不等于运行时动态类型。

函数应用 f(x) 会产生约束：f 必须是从 x 的类型到某个结果类型的函数。加法表达式可能要求操作数满足数值类型规则；成员访问要求对象有对应结构。约束互相冲突时，编译器应指出冲突来源，而不是随便选一个类型。不同语言支持的泛型、子类型和隐式转换不同，推断算法也不必相同。

逐步推演

分配未知量

为参数和表达式引入 α、β 等类型变量。

生成约束

函数调用、返回、加法等语法结构产生类型关系。

合一求解

让兼容类型相等，发生冲突或自引用时报错。

泛化与实例化

按语言规则决定 let 绑定能否在不同调用处使用不同类型。

合一怎样找到类型或报错

对 twice(f, x) = f(f(x))，设 x:α，第一次 f(x) 的结果为 β，所以 f 至少满足 α→β；第二次 f 接收 β，又需要 f 的输入与 β 一致。在简单单态推断下合一得到 α=β，故 f:α→α，twice:(α→α)→α→α。这个推导依赖该语言对函数和多态的规则，换成支持更复杂多态的系统可能有不同表达能力。

程序片段约束结论
id(x)=x返回类型=参数类型α→α
id(3)α=整数结果为整数
x+1x 需满足加法规则按语言确定数值类型
x(x)α 必须包含自身作为参数在常见简单类型系统中失败

出现检查为什么不可省

若对 x(x) 粗略地产生“x 的类型 α 必须等于 α→β”，会得到一个无限展开的类型 α=(α→β)=(α→β)→β……。普通 Hindley–Milner 风格的有限简单类型系统会用 occurs check 拒绝这种自引用。若实现只把类型变量指向函数类型而不检查包含关系，后续合一可能无限递归或产生错误的类型结论。

let 绑定的多态也要区分定义和使用。若 let id = x => x 被泛化为 ∀α.α→α，后续对整数与字符串的两次调用可以各自实例化 α。但带可变引用等副作用的表达式不能随意按同一规则泛化，否则不同调用可能共享一个实际存储单元却被当作不同类型；许多语言因此设置值限制或其他约束。

推断结果如何验证

  1. 对每个表达式明确生成了哪些约束，不要用“编译器猜出来”跳过过程。
  2. 合一时记录类型变量替换，出现函数类型自引用就做 occurs check。
  3. 把泛型函数的定义处泛化与调用处实例化区分开。
  4. 用错误用例检查诊断质量：例如把字符串传给只接受数值的加法。

练习：写出 compose(f,g,x)=f(g(x)) 中 f、g、x 和返回值之间的类型关系。再说明若 g 的输出与 f 的输入不能合一，错误应落在哪一次函数应用上。

分支汇合也会产生类型约束

考虑 if condition then 1 else 2，两个分支都是整数，整个表达式可推断为整数；若 else 返回字符串，简单静态类型系统会要求两分支类型合一，可能报错。支持联合类型或共同父类型的语言则可能给出更宽的结果类型。推断结论依语言规则，不是所有编译器都必须接受或拒绝相同代码。循环、模式匹配与重载也会增加约束，可能需要显式注解帮助消歧。

类型推断不是“省略所有类型设计”。公开 API 的注解有助于表达契约，错误消息也更容易定位；局部变量则适合让编译器推断。泛型代码需要区分“对任意 α 都能工作”与“这次调用恰好选择了整数”。前者是定义处的能力，后者是调用处的实例化。若把一次调用推导出的具体整数反写到泛型定义上，后续字符串调用就会被错误拒绝。

工程上可保存每一步的约束来源，让诊断指向真正冲突的表达式，而不是只说“类型不匹配”。

类型错误定位

若约束来自函数调用、分支返回和赋值三处，编译器应保留约束的源码位置。最终合一失败时，展示两个冲突类型及其来源，比只指向最后一个 token 更有帮助。推断算法的结果不仅是类型，也是可解释的诊断链。

必要时给递归函数写出输入和返回类型注解，可帮助编译器缩小推断空间，也让调用者看清 API 契约。

自检

类型推断是否等于运行时才知道类型？

不是。许多静态类型系统在编译或检查时根据约束推断类型。

为什么 x(x) 在普通简单类型推断中出问题？

它要求 x 的类型包含自身作为函数参数，有限类型合一的 occurs check 会拒绝。
