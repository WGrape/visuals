01故障主线与排查顺序

第一层

概念与判定

把前面的机制串起来：线上「慢/卡/崩」大多能归到几条主线——CPU 饱和、内存压力/OOM、IO 瓶颈、锁/ syscall 风暴、容器配额、中断不均。下面用真实套路演示定位。

现象优先怀疑
响应慢但 CPU 闲等 IO / 锁（D 状态）、网络 RTT
CPU 高、sy 占比大内核锁竞争 / syscall 风暴 / 中断
内存涨、随机被杀OOM killer（退出码 137）
写偶发卡顿脏页回写阈值 / 磁盘饱和
容器内慢、宿主正常配额太小 / 嘈杂邻居
排障顺序建议：先看资源（USE）→ 再定层次（CPU/内存/IO/网络）→ 再下钻（perf/strace/网络抓包）。不要一上来就改参数，先取证。

02三套排查脚本

第二层

参数·命令·量化

三套现成排查脚本

# ① CPU 饱和：找热点进程/线程
top -H -p $(pidof app)
vmstat 1          # r 列 > 核数 即饱和
perf top -p $(pidof app)

# ② 内存压力：谁在涨、会不会 OOM
watch -n1 'cat /sys/fs/cgroup/app/memory.current'
cat /sys/fs/cgroup/app/memory.events      # oom_kill
 dmesg -T | grep -i oom

# ③ IO 瓶颈：是否磁盘拖后腿
iostat -xz 1       # await/%util/aqu-sz
 iosnoop            # eBPF：每个 IO 的延迟（需要 bcc）
问题关键证据命令
CPU 饱和vmstat r、mpstat、perf
OOMmemory.events、dmesg|grep oom
IO 瓶颈iostat -xz、iosnoop
网络ss -ti、sar -n DEV、tcpdump
别在线上直接 strace -p 核心服务：ptrace 会让目标进程所有 syscall 串行化、严重降速，可能把小问题拖成大故障。先用 perf/eBPF 轻量取证。

03排障与边界（案例）

第三层

排障与边界

  • 案例 A：接口偶发 2s 卡顿——vmstat 看到 b 高且 wa 高 → iostat 某盘 %util=100% → 定位到同步写日志未限流，改异步+批量后消失。
  • 案例 B：容器频繁重启——退出码 137 → memory.events 有 oom_kill → 内存限太小，调大 memory.max 并降堆。
  • 案例 C：CPU 用满但 QPS 不涨——perf 热点在锁（spin_lock/futex）→ 伪共享或锁粒度粗，缩小临界区后吞吐翻倍。
  • 案例 D：单核 100%、其他闲——/proc/interrupts 中断全压 CPU0 → 配 smp_affinity / 开 irqbalance。
  • 案例 E：load 高 CPU 闲——大量 D 状态等 NFS → 挂载参数/网络问题，非 CPU 瓶颈。

04原理与取舍

第四层

原理与取舍

多数 OS 故障是「资源错配」：要么配额错（内存/CPU 太小）、要么架构错（同步写、锁粒度粗、单线程处理）、要么硬件错（磁盘慢、网络远）。工具只负责把「错配」暴露成可量化的证据。

根因类解法方向
配额错调 cgroup / JVM 堆 / 连接池
架构错异步化、削峰、锁拆分、批处理
硬件错换盘（NVMe）、就近、加缓存
干扰绑核、irq 亲和、隔离嘈杂邻居

深入 Q&A

Q：为什么查问题要先看 vmstat 1 一眼？
A：它能在一屏内同时暴露 CPU 饱和（r）、IO 等待（wa）、内存换页（si/so）、上下文切换（cs）。一秒定位大方向，远比乱猜高效。

Q：perf 火焰图怎么看？
A：横轴是采样占比（越宽越热），纵轴是调用栈。找最宽的「塔顶」函数，就是优化热点；若在库/内核里，就查调用它的业务路径。
