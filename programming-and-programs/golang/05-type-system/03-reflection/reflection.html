反射是运行时的自省

reflect 包让你拿到任意 interface{} 的类型与值信息，并在满足条件时修改它。序列化、ORM、配置绑定都依赖它。

何时才用反射

能不用就不用

反射绕过了编译期类型检查，代码难读、易 panic、性能也有开销。只有「类型在写代码时还不知道」时才用（如通用 JSON/ORM）。

⚠️ 经验：先把逻辑用接口/泛型写出来，实在抽象不动时再上反射。反射是最后手段，不是首选。
Type 与 Value

两层对象

TypeOf 拿类型元数据，ValueOf 拿值的容器。两者可互转：Value 能取 Type，Type 能构造零值 Value。

v := 42
vt := reflect.TypeOf(v)   // int
vv := reflect.ValueOf(v) // Value 装着 42
fmt.Println(vt.Kind(), vv.Int()) // int 42

// 从 Type 造零值
z := reflect.Zero(vt).Interface() // 0
Display：递归打印

顺着 Kind 走

用 reflect 遍历 struct 字段、slice/array 元素、map 键值，递归打印任意结构——这是理解反射最直观的练习。

func display(v reflect.Value, path string) {
    switch v.Kind() {
    case reflect.Struct:
        for i := 0; i < v.NumField(); i++ {
            display(v.Field(i), path+"."+v.Type().Field(i).Name)
        }
    case reflect.Slice, reflect.Array:
        for i := 0; i < v.Len(); i++ {
            display(v.Index(i), fmt.Sprintf("%s[%d]", path, i))
        }
    default:
        fmt.Printf("%s = %v\n", path, v.Interface())
    }
}
示例：编解码 S 表达式

反射做序列化

模仿 encoding/json，用反射把任意 Go 值编码成 Lisp 风格 S 表达式，再反解回来——经典教材案例。

编码时按 Kind 分派：基础类型直接写、复合类型写括号包裹的递归；解码时反向构造 Value 并设值。
通过 Value 修改值

可设置性（Settability）

只有「可取地址且未被导出的副本」的 Value 才能修改。传指针并用 Elem() 取到可寻址元素，否则 Set 会 panic。

x := 10
p := reflect.ValueOf(&x)   // *int 的 Value
p.Elem().SetInt(20)        // 改到 x = 20

// v := reflect.ValueOf(10); v.SetInt(30) // panic: 不可设置
获取结构体字段标签

ORM/校验的基础

字段上的 `json:"..."` 等标签在运行时可通过 Type 的 Field.Tag 读取，框架据此做映射。

type User struct{ Name string `json:"name"` }
t := reflect.TypeOf(User{})
tag := t.Field(0).Tag.Get("json") // "name"
几点忠告

克制使用

反射代码易 panic（类型不符），务必检查 Kind/CanSet；性能敏感路径避免热循环里反复 reflect；能写泛型就别反射。

类型断言 vs 反射

若只关心几种已知类型，用 type switch 比反射更清晰、更快。

为什么这么慢：反射调用要 ① 校验类型与可设置性（CanSet/CanInterface）② 把参数装箱成 []reflect.Value（堆分配）③ 运行时查方法表 ④ 无法内联、无法做逃逸优化。每一步都抵消了编译器的优化。

反射基准与优化

# 实测反射开销（自己跑一遍最直观）
go test -bench=. -benchmem ./...

func BenchmarkDirect(b *testing.B) {
    for i := 0; i < b.N; i++ { _ = add(1, 2) }        // ~2 ns/op
}
func BenchmarkReflectCall(b *testing.B) {
    v := reflect.ValueOf(add)
    args := []reflect.Value{reflect.ValueOf(1), reflect.ValueOf(2)}
    for i := 0; i < b.N; i++ { _ = v.Call(args) }     // ~150 ns/op
}

# 关键优化手段
# ① 缓存 reflect.Type（不要每次都 TypeOf）
var userType = reflect.TypeOf(User{})     // 包级变量，只算一次

# ② 缓存字段索引（FieldByName 是字符串查找，很慢）
idx, ok := userType.FieldByName("Name")   // 只在初始化时做一次
// 之后用 v.Field(idx.Index[0])

# ③ 能用类型断言就别用反射
if u, ok := x.(*User); ok { /* 快得多 */ }

# ④ 热路径用代码生成替代（stringer / easyjson / protoc-gen-go / msgp）

反射三定律与常见坑

  • 反射三定律：① 反射可以把「接口值」转成「反射对象」（reflect.ValueOf）；② 反射对象可以转回接口值（Value.Interface()）；③ 要修改反射对象，它的值必须可设置（addressable/settable）。
  • 最大的坑：CanSet。reflect.ValueOf(x) 传的是副本，不可设置。必须传指针再取 Elem：reflect.ValueOf(&x).Elem()。这是 90% 的反射报错来源（reflect: reflect.Value.Set using unaddressable value）。
  • 未导出字段不能读写：即使通过反射，CanSet() 对未导出字段返回 false，强行 Set 会 panic。这是 Go 用反射实现的封装保护。
  • 反射会让逃逸分析失效：传给 Value.Call 的参数会逃逸到堆上（因为编译器不知道反射会怎么用），增加 GC 压力。-benchmem 里能看到 B/op 明显上升。
  • 什么时候该用反射：序列化/反序列化、ORM、依赖注入、通用校验、测试框架、代码生成工具的运行时部分。什么时候不该用：热路径、能用泛型（Go 1.18+）替代的场景、能用接口替代的场景。
  • 泛型的出现减少了对反射的需求：Go 1.18 之后，很多“用反射写通用容器/工具”的场景可以用泛型，既保持通用性又零运行时开销。优先泛型，反射兜底。
为什么 json.Marshal 这么慢？

它对每个字段都要做反射：查 tag、查类型、判断是否 omitempty、做装箱。这也是 easyjson、jsoniter、sonic 存在的原因——它们用代码生成或unsafe绕过反射，快 3–5 倍。高 QPS 服务值得换。

反射能绕过私有字段吗？

不能（会 panic）。可以用 unsafe + reflect.NewAt 强行读写，但那是未定义行为，会破坏 Go 的内存安全保证，且随版本可能失效。生产代码绝对不要这么做。

第一层 · 反射能做什么、什么时候该用

反射的本质：在运行时检查和操作类型信息。Go 的反射建立在 reflect.Type（类型元数据）和 reflect.Value（值 + 可寻址性）两个概念上。

能力reflect 实现代价
读取类型名/字段/标签reflect.TypeOf + Field(i).Tag低
动态读写字段Value.Field(i).Set(...)中（要 CanSet）
动态调用函数Value.Call(args)高（要构造参数）
判断类型/接口实现Kind() / Implements()低
动态创建实例reflect.New(t)中
修改不可导出字段做不到（CanSet=false）—
  • 该用的三个场景：① 序列化/反序列化（encoding/json 就是反射实现的）；② 框架/ORM/依赖注入（需要扫描结构体标签）；③ 通用工具（深拷贝、map 与 struct 互转、参数校验）。
  • 不该用的场景：能静态写清楚的就不要用反射。反射换来的是灵活性，代价是性能、类型安全和可读性。
  • 三条硬性限制：① 改不了不可导出字段（CanSet() == false，用 unsafe 能绕过但强烈不建议）；② 反射调用无法被内联；③ 编译期类型检查全部失效，错误推迟到运行时。

第二层 · API 速查与性能数字

API 与性能

// —— 最常用的 API 组合 ——
t := reflect.TypeOf(x)        // 类型元数据；传指针要先 t.Elem()
v := reflect.ValueOf(x)       // 值；要【修改】必须传入指针：reflect.ValueOf(&x).Elem()

// 1) 遍历字段 + 读 tag（ORM/校验器的核心）
t := reflect.TypeOf(u)
for i := 0; i < t.NumField(); i++ {
    f := t.Field(i)
    name := f.Tag.Get("json")            // 读 struct tag
    if name == "-" { continue }
    if f.PkgPath != "" { continue }      // 【非导出字段】PkgPath 非空，跳过
    fmt.Println(f.Name, f.Type, name)
}

// 2) 动态设置字段值（必须可寻址 + 可导出）
v := reflect.ValueOf(&u).Elem()
f := v.FieldByName("Name")
if f.IsValid() && f.CanSet() {
    f.SetString("new")                    // 或用 f.Set(reflect.ValueOf(val))
}

// 3) 动态调用函数
fn := reflect.ValueOf(myFunc)
args := []reflect.Value{reflect.ValueOf(1), reflect.ValueOf("a")}
out := fn.Call(args)                      // 返回 []reflect.Value

// 4) 创建实例
newPtr := reflect.New(t)                  // *T
elem := newPtr.Elem()                     // 可写的 T

// 5) 判断零值 / 判断 Kind
v.Kind() == reflect.Struct                // Kind 是【底层类别】，Type 是具体类型
v.IsZero()                                // Go 1.13+

// —— 性能数字（数量级，务必记住）——
//   直接字段访问：        ~1 ns
//   接口方法调用：        ~2~5 ns
//   反射读字段：          ~50~100 ns      （慢 50~100 倍）
//   反射设置字段：        ~100~200 ns
//   反射调用函数：        ~200~500 ns     （最慢）
//   反射 + 缓存 Type 信息：~20~50 ns     （缓存元数据能省一半）
//   json.Marshal(小结构体)：~500~1000 ns
//
// 结论：反射单次是【几十到几百纳秒】。
//   在每次请求调用几十次的场景 -> 完全无感
//   在每字节/每循环调用的场景 -> 会成为瓶颈
优化手段效果说明
缓存 reflect.Type 与字段偏移2~5×收益最大：Type 信息只需解析一次（jsoniter/easyjson 的核心优化）
用 FieldByIndex 而非 FieldByName2~3×ByName 要做字符串比较（甚至线性查找）
改用代码生成（easyjson、protobuf）10~50×彻底去掉反射，代价是多一个生成步骤
用 unsafe 绕过接近直接访问不推荐：丧失内存安全保证，Go 版本升级可能失效
用泛型（Go 1.18+）替代部分场景接近直接访问编译期单态化，类型安全且无反射开销

Go 1.18 泛型出来后，很多原本必须用反射的场景（容器、通用算法）可以用泛型实现——类型安全 + 零运行时开销。新代码优先考虑泛型。

第三层 · 排障清单

  • reflect: Set using unaddressable value → 你传的是值而不是指针。修改必须 reflect.ValueOf(&x).Elem()。这是最常见的反射错误。
  • CanSet() == false → 字段是不可导出的（小写开头）。Go 的反射不允许通过反射修改未导出字段（这是语言的安全边界）。要么改成导出字段，要么提供 Setter 方法。
  • reflect.ValueOf(nil) 得到零 Value → Value.IsValid() == false，后续所有操作都会 panic。调用前必须检查 IsValid()。
  • 指针解引用搞错层级：TypeOf(&x) 得到的是 *T，要 .Elem() 才是 T。嵌套指针要多次 Elem()。
  • Kind 与 Type 混淆：type MyInt int 的 Type 是 MyInt 但 Kind 是 Int。判断「是不是整数」用 Kind，判断「是不是这个具体类型」用 Type。混用会导致逻辑判断错误。
  • 接口值的反射：对 interface{} 做 ValueOf 得到的是动态类型的值。要拿接口本身需 ValueOf(&iface).Elem()。
  • panic 而非返回错误：反射的很多操作（类型不匹配时）会 直接 panic 而不是返回 error。公共库里必须 defer recover()，或先做类型检查。
  • 性能问题定位：如果 pprof 里 reflect.Value.Call / FieldByName 占比高，按第二层的优化表处理（首选缓存 Type）。
  • 结构体标签拼写错误：json:"name" 写成 json:name（少了引号）会静默失效——tag 不报错，只是 Get 返回空。用 go vet 能查出来。

第四层 · 原理与取舍

理解反射只需搞清两件事：① 接口值的内部表示（type + value 二元组）；② 可寻址性（addressability）决定能不能改。

  • 接口的内部结构：Go 的接口值在运行时是 (type, value) 二元组（非空接口是 itab + data）。reflect.TypeOf 取的是 type 部分，reflect.ValueOf 取的是 value 包装。反射之所以能工作，就是因为接口值里带了类型信息——这也是为什么静态类型语言里只有支持「带类型信息的多态」才能有反射。
  • 可寻址性：reflect.ValueOf(x) 传值时会拷贝一份，这份拷贝是「不可寻址的」（没有原始内存地址），所以不能 Set。传 &x 再 .Elem() 得到的 Value 指向原始内存，才 CanSet()。这是 Go 反射最容易困惑的设计，但它保证了「反射不会意外修改调用方的副本」。
  • 性能开销的三个来源：① 类型元数据的查找与解析（Type 的方法要做大量查找）；② 值包装（每个 reflect.Value 都要装箱，涉及内存分配）；③ 无法内联 + 无法静态优化（编译器完全不知道你在做什么）。缓存 Type 能消除①，但②③是固有的。
  • 为什么 encoding/json 慢：它每次编解码都要反射遍历字段、解析 tag、做类型转换。虽然内部缓存了 Type 信息，但② ③ 两个开销躲不掉。这就是为什么 easyjson（代码生成）能快 4~6 倍。

为什么反射不能修改未导出字段？

这是 Go 的语言安全边界，不是技术限制。设计意图是：如果反射能改未导出字段，那么包封装就会被彻底打破——任何第三方库都能修改你结构体的私有状态，破坏你的不变式（invariant）。所以 Go 让 CanSet() 对未导出字段返回 false，从 API 层面堵死这条路。技术上可以用 unsafe 绕过（拿到字段地址后直接写内存），但强烈不建议：① 失去内存安全保证；② 依赖编译器实现细节，Go 版本升级可能失效；③ 代码无法 review 和维护。如果确实需要外部写入私有字段，正确的做法是提供导出的方法（Setter）或在包内提供构造函数——这才是符合语言设计的解法。

反射的开销在什么情况下真的会成为瓶颈？

用一个量化判断：单次反射操作约 50~500ns。假设你的接口总耗时预算是 50ms，那么调用 10 万次反射才占 0.5~5ms（10%）——大多数业务代码根本达不到这个调用量。真正会出问题的场景：① 序列化/反序列化高频数据（如每秒几十万条消息的 JSON 编解码）——这是标准库 json 慢的根源，也是 jsoniter/sonic 存在的理由；② 内层循环里的反射（如遍历百万行做类型转换）；③ ORM 的批量操作（每行都要反射扫描字段）。判断是否优化的硬指标：pprof 里反射相关函数占比 >10% 才值得动。而且优先用「缓存 Type 元数据」这种低成本优化（2~5 倍），而不是一上来就上代码生成（要改构建流程）。

泛型能完全替代反射吗？

不能，两者解决问题的层次不同。泛型解决「同一段代码处理多种类型」（编译期单态化，零运行时开销，类型安全）；反射解决「运行时才知道类型」（如解析一个未知的 JSON、扫描任意结构体的 tag）。关键区别：泛型要求类型在编译期已知。所以 json.Unmarshal(data, &v) 这种「数据是运行时来的、要填进调用方给的类型」的场景，泛型做不到，必须反射（或代码生成）。反过来，写一个 Map[T, U] 或者通用排序函数，泛型就能完全替代反射且更好。实践建议：能用泛型就用泛型（类型安全 + 零开销），必须运行时动态时才用反射。Go 1.18 之后，很多原本用反射的通用库都开始提供泛型版本。
