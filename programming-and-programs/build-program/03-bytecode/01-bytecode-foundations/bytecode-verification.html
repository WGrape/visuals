字节码验证：执行前检查控制流与栈

虚拟机可以先验证指令序列的基本约束，再把它交给解释器或 JIT。

核心机制

栈式字节码的每条指令有栈效果：push 增加元素，add 消费两个并产出一个。控制流的汇合点还需有兼容的栈高度和类型状态。

验证器通常还检查跳转目标、局部变量使用和指令操作数。具体规则取决于 VM；验证通过不意味着程序逻辑正确，也不能代替运行时权限与资源限制。

用一个例子看过程

PUSH 2   ; 栈 [2]
PUSH 3   ; 栈 [2,3]
ADD      ; 栈 [5]
RETURN   ; 返回 5

建立控制流

确定入口、跳转目标和基本块，拒绝落在非法指令中间的目标。

传播栈状态

沿每条边计算栈高度与类型；出现下溢或不兼容汇合则拒绝。

交给执行器

验证后的代码仍需处理运行时异常、越界和资源耗尽。

观察、原因与处理

观察原因或含义处理与验证
栈下溢ADD 前不足两个操作数静态计算每条路径的栈效果
汇合冲突两条路径到同一位置的类型不兼容检查分支和合并状态
非法跳转目标不在有效指令边界验证目标偏移和代码范围

把指令看成栈状态变换

一个简化栈机可以规定 PUSH n 把一个整数压栈，ADD 弹出两个整数并压入和，RETURN 弹出一个返回值。对 PUSH 2; PUSH 3; ADD; RETURN，栈高度依次为 0→1→2→1→0。若代码从空栈直接执行 ADD，验证器不用运行程序就能发现栈下溢。除了高度，还要检查类型：把字符串和整数送进只接受整数的 ADD，可能在验证阶段被拒绝，也可能按语言规则在运行时处理。

一旦出现跳转，不能只线性扫指令。验证器先构造控制流图，再把栈状态沿每条可达边传播到后继基本块；两条路径汇合时，栈高度和类型状态必须满足该 VM 的合并规则。循环会让状态反复传播，直到不再变化。跳转到不存在的偏移，或跳进一条指令的中间，也应被拒绝。

验证通过说明被检查的结构约束成立，不说明程序不会除零、访问缺失资源或耗尽内存，更不说明业务结果正确。权限和资源隔离仍需要运行时机制。

练习：手算两个分支

分支 A 在汇合点前 PUSH 一个整数，分支 B 什么也不压；汇合点第一条指令是 ADD。请分别计算两条路径的栈高度，并说明为什么不能只测试走分支 A 的一次运行。验证要覆盖所有可达控制流路径，而不是依赖测试样本恰好触发错误分支。

边界与误区

一些动态语言的字节码不采用强静态类型验证，但仍会做格式或运行时检查。不要把某个 VM 的验证规则当作所有字节码的共同规范。

数据流分析为什么需要不动点

控制流图中出现循环时，块入口状态可能从前驱再次传回来。验证器反复计算“指令变换后的状态”，再与目标块已有状态合并，直到所有块入口都不再改变，这就是不动点。若栈高度或类型无法按规则合并，程序应被拒绝或交由运行时检查。为了让过程终止，状态抽象需要有限或满足收敛条件；真实 VM 的验证规则比简单计数更复杂。

例如某分支推送整数 2，另一个分支推送字符串“2”，两条路径都到达只接受整数的 ADD。若合并状态只能得到“未知类型”，验证器可能不能证明 ADD 安全；采用动态类型语义的 VM 则可能允许代码执行，在运行时决定加法或报错。讨论字节码安全时要先说明是哪种语言、哪种 VM、哪些性质由静态验证保证。

验证器的安全边界

若字节码来自不可信来源，非法跳转、越界操作数或类型混淆可能成为运行时崩溃甚至逃逸的入口，因此验证器本身也是攻击面。解析时要先检查长度和索引边界，再构造控制流；不要在确认偏移合法前直接按它访问指令数组。验证器要对畸形输入快速拒绝，防止攻击者提交极大控制流图消耗 CPU 或内存。即使验证成功，仍要用权限隔离、资源配额和运行时边界保护宿主环境。结构正确的字节码仍可能写出无限循环或发起不被允许的外部访问。

进一步验证

一个有效测试是自动生成畸形控制流：随机跳转偏移、缺失操作数、分支汇合时不一致的栈高度，以及深层循环。验证器应稳定拒绝非法输入，而不是崩溃、无限循环或消耗无界内存。对可信编译器输出和不可信外部字节码采用不同测试集。

补充判断

同一控制流图中，不可达代码是否仍需验证由 VM 规范决定。有的格式要求所有指令结构合法，有的检查只传播可达路径。实现与测试必须遵循目标 VM 的规范，不能凭一次样本运行结果猜测。

字节码校验的检查项

检查类别具体内容目的
结构检查魔数 0xCAFEBABE、版本号、常量池合法性确认是合法的 class 文件
类型检查操作数栈上的类型与指令要求匹配防止类型混淆攻击
栈深度检查每条指令处操作数栈深度确定且一致防止栈上溢/下溢
控制流检查跳转目标必须是指令边界且在本方法内防止跳到指令中间执行非法字节码
局部变量检查使用前必须已初始化（除 int 的 0 初始化）防止读到未定义值
访问权限不能访问 private 字段/方法类型安全
final 语义final 类不能被继承，final 字段不能被写语言语义保证

为什么需要校验：字节码不一定由 javac 生成，可能是手写的、被篡改的、或从网络下载的。JVM 必须在运行前确认它不会破坏类型系统——否则攻击者可以构造「把 int 当对象引用用」的字节码，直接读写任意内存。这是 JVM 安全模型的第一道防线（第二道是安全管理器与类加载隔离）。

深入自检

为什么 Java 的校验能在加载时完成，而某些语言需要运行时检查？

因为 JVM 字节码是强类型的、栈深度静态可确定的。校验器沿控制流做一遍数据流分析，就能确认所有路径上类型一致。像 C 那样的语言无法做到，因为指针运算让类型不可静态判定。

校验会影响启动速度吗？

会，但很小。JVM 只对首次加载的类做完整校验，且校验主要是线性扫描，通常占启动时间的百分之几。Java 7 引入 StackMapTable 后，校验从「多遍迭代」优化为「单遍」，进一步加快。

手改字节码为什么容易 VerifyError？

因为 StackMapTable 必须与代码严格一致。改了指令却没更新栈帧表，或者跳转目标偏移算错（字节码里的偏移量是按字节算的），都会失败。这就是必须用 ASM/ByteBuddy 这类库的原因。

-Xverify:none 为什么不该用？

它关闭了类型安全保证。恶意或损坏的字节码会直接执行，可能读写任意内存、绕过访问控制。生产环境永远不要开。

Android 的 Dalvik/ART 有类似机制吗？

有，但设计不同：dex 是寄存器架构（不是栈式），校验更复杂；ART 在 AOT 编译时做大部分验证，运行时开销更小。

自检

为什么“字节码验证通过”不能保证运行时不出错？

它只保证被检查的结构和类型约束；除零、缺失资源和业务逻辑错误仍可能发生。
