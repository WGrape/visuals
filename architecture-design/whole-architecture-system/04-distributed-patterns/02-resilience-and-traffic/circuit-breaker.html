什么时候适用？

判断信号：下游持续失败或超时，继续调用会耗尽上游资源。

  • 支付供应商异常时快速失败
  • 推荐服务故障时回退空结果
  • 半开探测恢复后的下游

和相近方案怎么区分？

相近方案选择边界
重试重试尝试克服瞬时失败；熔断在持续失败时停止继续施压。
限流限流按流量控制进入量；熔断根据下游健康状态暂停调用。

最小伪代码

if breaker.state == OPEN:
  if not cooldownExpired(): return fallback()
  breaker.enterHalfOpen(maxProbes=1)
if not breaker.allowRequest(): return fallback()
try:
  result = callDownstream(timeout=500ms)
  breaker.recordSuccess()  // 探测成功可闭合
  return result
catch error:
  breaker.recordFailure()  // 超阈值或探测失败则断开
  return fallback()

边界：熔断不修复下游。阈值、窗口、半开并发和回退结果应按业务影响设置。

三态机 Circuit Breaker

打开态直接拒绝请求，给依赖喘息时间

调用方对某个易失败的依赖加装断路器：关闭态正常放行并统计失败率；超阈值转打开（直接快速失败，不发真实请求，避免线程堆积）；冷却后进入半开试探，成功则恢复，失败则继续打开。

为什么需要它

  • 防止一个慢/挂的依赖耗尽调用方线程池（舱壁外再加一道闸）。
  • 给故障服务恢复时间，而非持续被打。
  • 配合降级返回兜底数据。

面试高频问答

Q：熔断和降级是什么关系？
A：熔断是『切断故障链路』的机制；降级是『切断后给什么兜底』的策略。通常一起用：熔断打开 → 走降级逻辑（返回缓存/默认值）。
Q：熔断阈值怎么设？
A：常见：在 N 秒内失败率超过 X%（如 50%）且请求数达最小样本，则打开。阈值要按依赖的 SLA 与流量调，过严会误伤、过松则不护。

熔断器：像空气开关一样保护调用链

电路里的保险丝在电流过大时熔断，保护电器不被烧毁。软件熔断器同理：当某个下游服务的失败率超过阈值时，立即停止调用它并直接返回错误或兜底，不再让请求堆积在等待队列里。它的价值不是「修好下游」，而是防止故障沿调用链向上传播造成雪崩。

熔断器三态机：Closed → Open → Half-Open → Closed

熔断 vs 限流 vs 超时 vs 重试

超时 Timeout

单次调用的最长等待时间。是所有韧性措施的地基——没有超时，任何熔断限流都无从谈起（因为请求永远不返回）。

  • 必须逐层收敛：下游超时 < 上游超时
  • 区分连接超时（短）与读超时（按 P99 设定）

重试 Retry

对失败请求重新发起。危险操作——重试会放大流量，是雪崩的常见帮凶。

  • 只对幂等操作重试；写操作必须带幂等键
  • 限制重试次数（1~2 次）+ 退避（指数退避 + 抖动）
  • 只对超时/连接错误重试，不对业务错误（如余额不足）重试

限流 Rate Limit

控制「自己能接多少」——对入口流量做配额。

  • 保护对象是自己，决策依据是自身容量
  • 熔断保护的对象也是自己，但决策依据是下游健康度

熔断 Circuit Breaker

当下游不健康时停止调用它，避免等待与资源占用。

  • 必须有兜底逻辑（fallback），否则熔断等于把错误直接抛给用户
  • 必须与降级联动：熔断 → 走降级 → 返回兜底数据

协同关系：超时是地基 → 重试要克制且与幂等配合 → 熔断在下游持续故障时快速止损 → 限流保证自身不被打穿 → 降级提供兜底体验。五者构成一个完整的韧性体系，缺一环都会留缺口。

资源隔离：熔断的另一种形态

即使不熔断，也可以通过隔离把故障限制在局部。三种主流做法：

隔离方式做法适用
线程池隔离每个依赖一个独立线程池，某依赖慢只会打满它自己的池依赖较少、调用量大的场景（Hystrix 默认）；线程切换有开销
信号量隔离每个依赖一个计数器，超过并发上限直接拒绝（不新建线程）高频低延迟调用；开销极低，但无法做到超时中断
bulkhead 舱壁（连接/实例级）为不同租户或不同依赖分配独立的连接池、独立实例组多租户 SaaS；避免一个租户打满全部资源

为什么隔离重要：没有隔离时，一个慢依赖会占满所有工作线程，导致「明明其他接口跟这个依赖无关，也全部超时」——这就是典型的故障扩散。隔离把共享资源切成互不影响的隔间，正如船舱的水密隔舱。

深入自检

熔断器打开后，请求直接失败，用户体验不就变差了吗？

所以熔断必须配 fallback（兜底）。熔断返回给用户的不是错误，而是降级结果：返回缓存的旧数据、返回默认推荐列表、返回「服务繁忙请稍后」的友好提示、或直接走本地静态兜底。关键认知是：下游已经不可用时，用户本来就拿不到正确结果，与其让他等 30 秒后超时报错，不如 10 毫秒返回一个次优但可用的答案。这就是「快速失败优于慢速失败」。

为什么重试会引发雪崩？

重试放大流量。假设下游已经过载、成功率降到 50%，此时上游对每个失败请求重试 2 次，下游收到的请求量就变成 3 倍——原本 1000 QPS 变成 3000 QPS，成功率进一步下降到 20%，于是重试更多，形成正反馈直到彻底崩溃。这就是「重试风暴」。防御手段：① 重试预算（重试请求占总请求的比例上限，如 10%）；② 只在熔断未打开时重试；③ 指数退避加抖动打散重试时间；④ 重试只针对幂等操作。

熔断的统计窗口用固定窗口还是滑动窗口？

滑动窗口更准确。固定窗口（如每分钟清零）有边界问题：59 秒时大量失败、01 秒时又大量失败，两个窗口各自都没到阈值但实际已经持续失败。滑动窗口（记录最近 N 次调用或最近 N 秒的每个小格）能连续反映真实的失败趋势，反应也更及时。Sentinel、Resilience4j 默认都用滑动窗口。代价是稍高的内存与实现复杂度，通常值得。

熔断后如何优雅恢复？

直接全量放开是危险的——下游可能只是勉强恢复，瞬间全量流量会把它再次打垮（二次雪崩）。正确做法：① Half-Open 状态只放行极少量请求（1~5 个）；② 成功则逐步放量（线性或指数增加）；③ 任一失败立即回到 Open 并重置冷却计时，可按连续失败次数递增冷却时长（指数退避）；④ 恢复期间保持监控，观察错误率与 RT 是否真的回到正常水位。
