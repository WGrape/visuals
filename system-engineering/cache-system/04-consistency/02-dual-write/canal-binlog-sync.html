之前的方案是：改数据的人顺手去通知缓存（应用代码里写一行 redis.del）。问题是这个人可能会忘、会喊错、喊的时候正好网络不好——于是缓存就失联了。

binlog 订阅换了个思路：数据库自己有一本「变更流水账」（binlog），让一个专门的中间件（如 Canal）盯着这本账，只要账上记了「某行改了」，它就自动去删对应缓存。应用代码完全不用管这事。

架构与数据流

它解决了什么

原有问题binlog 方案如何解决
应用代码里删缓存，删除失败就丢了订阅链路自带重试与位点，失败可重放
多处代码改同一张表，容易漏写删除逻辑统一在订阅端处理，应用零侵入
应用重启导致删除动作丢失binlog 持久化在数据库，位点可续传
无法追溯「缓存为什么没删」有完整事件流，可监控、可对账

它的代价与风险

① 引入异步延迟。从数据库提交到缓存被删除，中间有毫秒到秒级的延迟。这期间读请求会拿到旧值。对绝大多数业务可接受，但对强一致场景（余额、库存）不适用。
② 增加运维复杂度。要多维护一套 Canal/MQ/消费者链路，需要监控消费位点积压。积压过大意味着缓存长期不更新。
③ 消费必须幂等。MQ 可能重复投递，删除操作本身是幂等的（DEL 多次无副作用），但如果消费者做的是「更新缓存」而非「删除」，就必须处理乱序问题（用版本号或时间戳丢弃旧事件）。
④ binlog 格式要求。MySQL binlog 需设为 ROW 格式才能拿到完整的行变更前后数据；STATEMENT 格式只有 SQL 语句，无法据此推导受影响的行。

「删除」还是「更新」？

方式优点风险
收到变更就 DEL幂等、无需关心顺序、实现简单下次读会 miss，需回源
收到变更就 UPDATE缓存始终有值，无回源抖动事件乱序会写入旧值，需版本号保护
推荐「删除」。幂等性带来的健壮性，远大于「少一次回源」的收益。这也是为什么绝大多数中间件默认采用删除模式。

什么规模才值得上？

  • 小项目 / 简单读写：应用里直接删缓存 + TTL 兜底就够了，不要过度设计。
  • 中大型、多服务写同一批表：binlog 方案价值明显，能杜绝漏删、便于统一治理。
  • 强一致要求：不要指望缓存，直接读主库或改用强一致存储。

🎯 面试问答

Q：binlog 订阅能完全保证一致性吗？
A：不能，它保证的是最终一致。数据库提交到缓存删除之间存在异步延迟（毫秒到秒级），这期间读到的是旧值。它的核心价值不是「零延迟」，而是「删除动作不会丢」——相比应用内直接调用，它把一次性的、可能失败的调用，变成了可重试、可回放、可监控的流程。

Q：Canal 是怎么拿到 binlog 的？
A：它伪装成 MySQL 的从库。MySQL 主从复制时，从库会向主库发起 dump 请求拉取 binlog；Canal 就是模拟这个协议，让主库把它当作一个从库，把 binlog 推给它。这也是为什么它需要数据库账号有 replication 相关权限，并且 binlog 要开启且为 ROW 格式。

Q：消费积压了会怎样？
A：积压意味着缓存删除被延迟，积压越久，缓存与数据库偏离越久，可能长时间返回旧值。严重时会形成「缓存看起来正常，实际全是过期数据」的隐蔽故障。必须监控消费位点 lag 并设置告警；同时保留 TTL 作为兜底，避免永久脏数据。

Q：小项目有必要上 Canal 吗？
A：通常没必要。它引入了一整套中间件链路（Canal + MQ + 消费者）和运维负担。小项目用「先更新数据库、再删除缓存 + 删除失败重试 + 合理 TTL」已经足够可靠。判断标准：是否有多个服务写同一批表、是否经常漏删、是否需要追溯缓存失效原因——有这些诉求再上。

Canal 工作原理与前提

Canal 伪装成 MySQL 的从库，接收主库的 binlog 并解析成变更事件，投递给下游（MQ/缓存/ES）。

前提配置要求检查命令
binlog 开启log-bin=mysql-binSHOW VARIABLES LIKE 'log_bin'
binlog 格式必须为 ROWSHOW VARIABLES LIKE 'binlog_format'
row imagebinlog_row_image=FULLMINIMAL 会缺旧值，无法做 diff
server_id全局唯一SHOW VARIABLES LIKE 'server_id'
账号权限REPLICATION SLAVESHOW GRANTS

MySQL 配置

-- MySQL 侧必需配置（my.cnf）
[mysqld]
log-bin=mysql-bin
binlog_format=ROW          -- STATEMENT 无法解析出行级变更
binlog_row_image=FULL      -- 记录完整前后镜像
server_id=1

-- 创建 Canal 账号
CREATE USER canal IDENTIFIED BY 'canal';
GRANT SELECT, REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'canal'@'%';
FLUSH PRIVILEGES;

-- 验证 binlog 是否正常产出
SHOW MASTER STATUS;        -- 看 File 与 Position 是否在推进
SHOW BINLOG EVENTS LIMIT 5;

为什么必须 ROW 格式：STATEMENT 只记录 SQL 语句，Canal 无法得知具体哪一行变了（尤其含 NOW()、UUID() 等非确定性函数时更糟）。ROW 记录每行的前后镜像，才能还原出精确的变更。

Canal 关键参数与位点管理

参数默认值说明
canal.instance.master.address—主库地址，格式 host:port
canal.instance.filter.regex.*\\..*订阅的库表正则，建议只订阅需要的表
canal.mq.topic—投递的 MQ topic
canal.instance.memory.batch.modeMEMSIZE按条数还是按内存攒批
canal.instance.memory.buffer.size16384环形缓冲区大小（条）
canal.instance.memory.buffer.memunit1024单条事件内存估算（字节）

Canal 配置

# canal.properties 关键配置
canal.serverMode = kafka            # 投递模式：tcp / kafka / rocketmq
canal.destinations = example
canal.instance.filter.regex = mydb\\.orders|mydb\\.users   # 只订阅这两张表

# instance.properties
canal.instance.master.address = 127.0.0.1:3306
canal.instance.dbUsername = canal
canal.instance.dbPassword = canal
canal.instance.connectionCharset = UTF-8
canal.instance.filter.black.regex = mydb\\.temp_.*        # 排除临时表

# MQ 投递（保证顺序的关键：按主键分区）
canal.mq.topic = canal_orders
canal.mq.partitionHash = mydb\\.orders:id                # 同一 id 进同一分区

位点（position）是 Canal 的命门：Canal 记录已消费的 binlog 文件名与偏移量。位点丢失会导致重放或漏数据。生产必须保证位点持久化（默认存在本地 meta.dat）并定期备份；HA 场景要配置 canal.instance.global.spring.xml 使用共享存储或 ZooKeeper 保存位点，否则主备切换后位点不一致。

消费侧的幂等与顺序

binlog 投递是至少一次语义——重复投递不可避免，消费侧必须能处理。

问题原因方案
重复消费位点未及时提交或 MQ 重投幂等：按主键 upsert，或用 (binlog_file, pos) 去重
乱序MQ 多分区并行消费按主键分区（partitionHash）保证同 key 有序
漏数据位点超前提交处理成功后再提交位点
回环同步目标又写回源库过滤掉 Canal 自己的变更（用不同 server_id 或打标记）

幂等消费

# 幂等消费模板：用 binlog 位点做去重，天然幂等
def consume(event):
    key = f"{event['table']}:{event['pk']}"
    # 关键：比较位点，只应用更新的变更，旧的重放直接丢弃
    last = redis.get(f"canal:pos:{key}")
    if last and event['pos'] <= int(last):
        return                       # 重复或过期事件，跳过

    if event['type'] == 'DELETE':
        cache.delete(key)
    else:
        # UPDATE/INSERT 都走 upsert，天然幂等
        cache.set(key, serialize(event['after']))

    redis.set(f"canal:pos:{key}", event['pos'])

# 注意：位点比较只保证“不倒退”，若同一行在同一位点内有多次变更
# 需配合 binlog 内的行内序号，或用 updated_at 版本号兜底

自检 Q&A

Q：Canal 同步延迟高怎么排查？

A：分层定位——① Canal 到主库的拉取延迟：看 Canal 日志里的位点与 SHOW MASTER STATUS 的差距；② 解析与投递延迟：看堆积（canal.instance.memory.buffer 是否打满）；③ 下游消费延迟：看 MQ 的 lag。最常见的是下游消费慢（如写 ES 批量太小），加大批量通常最有效。另外大事务（一次改几十万行）会让 Canal 产生巨量事件，是延迟尖刺的典型来源。

Q：DDL 变更会导致同步中断吗？

A：加字段通常安全，改字段类型/删字段危险。Canal 会解析 DDL 事件，但下游若没有对应的表结构适配逻辑，会解析失败或写入错误。生产做法：① DDL 先在下游执行再在源库执行（保证下游结构更新）；② 或订阅时过滤 DDL 事件，由人工同步结构——后者更可控，推荐。

Q：Canal 和直接双写（应用同时写库与缓存）怎么比？

A：Canal 的优势是解耦与可靠——应用不感知同步逻辑，同步由数据变更事件驱动，不会因应用异常而漏掉。劣势是有延迟（通常毫秒~秒级）且增加运维组件。双写的问题是一致性难保证（写库成功写缓存失败就脏了）。所以对一致性要求高的场景 Canal 更优；能接受秒级延迟的话，Canal 几乎是标准答案。

Q：MySQL 主从延迟会不会影响 Canal？

A：不会直接影响，但要理解 Canal 是独立的“从库”，它连的是主库（或指定的某个实例）。如果 Canal 连主库，那么主库压力大时 Canal 拉取也会变慢；如果配置了读写分离让 Canal 连从库，则从库延迟会直接叠加到同步延迟上。生产一般让 Canal 直连主库，因为从库延迟不可控。
