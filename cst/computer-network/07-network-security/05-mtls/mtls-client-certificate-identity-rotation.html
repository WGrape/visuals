双向 TLS：服务之间如何验证彼此身份、轮换证书

用订单服务调用支付服务说明服务端证书、客户端证书、SAN 身份与授权规则。

普通 TLS 只验证一侧也很常见

浏览器访问 HTTPS 网站时通常由客户端验证服务器证书，服务器不要求浏览器提供证书，用户身份可通过登录会话判断。双向 TLS（mTLS）在握手中增加服务端对客户端证书的验证：订单服务确认自己连接的是支付服务，支付服务也确认来访方持有被信任的订单服务凭据。它适合服务间身份，但不会自动决定“订单服务能否退款十万元”，授权仍需业务或策略层检查。

客户端证书和服务端证书都有有效期、用途和身份字段，双方都要验证签名链与目标身份。只要证书由同一个 CA 签发就放行所有操作，会把整个信任域误当作单一权限。应把证书身份映射为具体服务主体，再按方法、资源和环境授权。

一次握手中的两份身份

订单服务向 `pay.internal` 建立 TLS，先验证支付服务证书链和 SAN 是否匹配预期服务名；支付服务在配置要求客户端认证时请求客户端证书，订单服务提交自己的证书并证明持有对应私钥，支付服务验证其链、有效期、用途及主体身份。握手成功后双方建立加密通道，但支付服务还需根据“订单服务”身份判断是否允许调用扣款、查询或退款接口。

证书中的 DNS SAN 或 URI SAN 可以承载服务身份，具体格式要由组织统一定义。IP 地址、Kubernetes Pod 名和临时主机名可能频繁变化，直接绑定到它们会增加轮换成本。证书的 Common Name 在许多现代验证场景不应替代 SAN；排障应看实际验证库使用的身份字段。

代理终止会改变身份边界

若订单服务经服务网格 sidecar 或入口代理访问支付服务，mTLS 可能终止在代理之间；支付应用看到的直接连接来自本地代理，而不是订单进程的证书。策略必须明确是代理替工作负载证明身份，还是应用自己做端到端 mTLS。若后端只信任代理转发的 `X-Service-Identity` 头，而外部客户端能绕过代理直连后端并自造该头，就会形成身份伪造风险。

图上要标清每段 TLS 从哪到哪，证书由谁持有，后端哪些端口只允许受控代理访问。mTLS 保护传输与服务身份，不替代服务内部参数校验、租户隔离和审计。

证书轮换为何难

证书通常是短期有效以降低长期凭据泄漏风险。轮换时新证书、旧证书和信任根可能短时间重叠，调用方与被调方必须都能接受过渡期的合法身份。若先删旧根，再更新一部分服务，旧客户端会握手失败；若先换支付证书却忘记更新订单侧信任库，也会出现单方向可用、另一方向不可用。应先分发新信任、再颁发新证书、验证覆盖率，最后撤销旧材料。

自动轮换也会失败：节点离线、时钟漂移、证书文件权限、热加载未生效，都可能造成到期前后大面积故障。监控要按服务和实例记录证书剩余有效期、最近成功加载时间和握手失败原因，而不是只看 CA 控制台“已签发”。

私钥与撤销

私钥必须留在受控边界，避免写入镜像、日志或普通配置仓库。证书泄漏后，仅等待它自然过期可能不够；可通过吊销、缩短有效期、撤销服务授权和网络阻断等措施降低风险。不同客户端对 CRL/OCSP 或内部吊销列表的支持不同，需要演练真实撤销效果。若使用短寿命证书，仍要知道已签发的旧身份在多长时间内可能继续有效。

服务账号被禁用后，已建立的长连接可能继续传数据，具体取决于代理和应用是否重新评估授权。高风险操作应在请求层检查权限，不要只靠建立连接时的一次验证。

排障与验收

订单到支付连接失败时，先看 DNS 与 TCP，再看客户端是否信任支付证书、支付端是否请求并接受订单证书、证书 SAN 与用途是否正确、双方时钟是否一致。抓包可定位 TLS Alert 出现的阶段，但加密握手细节可能要结合端点日志。区分“证书不被信任”“身份不匹配”“证书已过期”和“握手成功但业务拒绝”四种原因。

验收应包含允许的订单服务、无证书客户端、持其他服务证书的客户端、过期证书和轮换期间新旧证书。通过测试不应只看握手成功，还要验证最小授权：订单服务能扣款，不应自动拥有管理证书或任意退款权限。

mTLS 流程与身份

步骤内容单向 TLS 是否有
1. 服务端发送证书服务端发送自己的证书链有
2. 客户端验证服务端校验链 + 主机名有
3. 服务端请求客户端证书CertificateRequest仅 mTLS
4. 客户端发送证书客户端发自己的证书链仅 mTLS
5. 客户端证明持有私钥CertificateVerify（对握手摘要签名）仅 mTLS
6. 服务端验证客户端校验链 + 身份 + 是否在白名单仅 mTLS

关键点：客户端发证书还不够——必须做 CertificateVerify（用私钥对握手内容签名），否则任何人拿到证书公钥都能冒充。证书是公开的，私钥才是身份。

身份载体字段示例适用
SAN（URI）subjectAltName: URIspiffe://cluster/ns/default/sa/api服务身份（推荐）
SAN（DNS）subjectAltName: DNSapi.internal.example.com服务或设备
SAN（Email）subjectAltName: emailops@example.com人员
CNsubject CN—已废弃，不要依赖

mTLS 实操

# 测试 mTLS（双向认证）
curl --cert client.pem --key client.key --cacert ca.pem https://api.internal/

# 看服务端是否要求客户端证书
openssl s_client -connect api.internal:443 -CAfile ca.pem
# 输出中出现 "Acceptable client certificate CA names" = 服务端要求客户端证书

# 生成客户端证书
openssl req -new -newkey rsa:2048 -nodes -keyout client.key -out client.csr \
  -subj "/CN=api" -addext "subjectAltName=URI:spiffe://cluster/ns/default/sa/api"
openssl x509 -req -in client.csr -CA ca.pem -CAkey ca.key \
  -CAcreateserial -out client.pem -days 365

# 查看证书身份
openssl x509 -in client.pem -noout -text | grep -A2 'Subject Alternative Name'
openssl x509 -in client.pem -noout -subject -issuer -dates

# Nginx mTLS 配置
# ssl_client_certificate /etc/ssl/ca.pem;
# ssl_verify_client on;              # on = 强制，optional = 可选
# ssl_verify_depth 2;
# 然后把 $ssl_client_s_dn 或 $ssl_client_escaped_cert 传给后端做鉴权

证书轮换的正确姿势

阶段操作时长
1. 发布新根/中间 CA把新 CA 加入信任列表（与旧 CA 并存）立即
2. 签新证书用新 CA签发服务端与客户端证书立即
3. 部署新证书服务端/客户端加载新证书（同时信任新旧 CA）滚动发布
4. 等待重叠期结束确保所有节点都已更新≥ 证书 TTL
5. 移除旧 CA从信任列表删除旧 CA最后
  • 核心原则：先加信任，再换证书，最后删旧的。顺序反了（先签新证书再更新信任库）会导致仍在用旧信任库的一方验证失败——这是证书轮换事故的头号原因。
  • 重叠期要 ≥ 证书有效期（现在证书普遍 90 天甚至 47 天，所以自动化是必须的）。用 cert-manager / SPIRE / Vault 自动签发与轮转，别手工。
  • 短证书 + 自动轮换：现代做法是签小时级到天级的证书（SPIFFE 甚至 15 分钟–1 小时），把吊销问题变成“等它过期”，从而不需要 CRL/OCSP。
  • 吊销的尴尬：CRL 列表越来越大、OCSP 每次都要查询，而浏览器/客户端普遍“软失败”（查不到就放过）。所以真正的安全依赖短有效期而非吊销列表。
  • 排障顺序：① openssl s_client 看服务端是否要求客户端证书；② 确认客户端证书链完整（含中间 CA）；③ 看 SAN 是否匹配服务端期望的身份；④ 看证书是否过期；⑤ 看信任库是否包含签发 CA（轮换场景最常见）。
  • K8s / 服务网格：Istio/Linkerd 用 SPIFFE 身份 + 自动 mTLS，证书默认有效期 24 小时并自动轮转，业务代码零感知。这是目前最省心的落地方式。
mTLS 的客户端证书会被中间人拿到吗？

不会。TLS 1.3 握手中客户端证书是加密传输的（在握手完成后的加密通道里），且即使被截获，攻击者没有私钥也无法完成 CertificateVerify。所以证书本身不是秘密，私钥才是。

证书快过期了怎么平滑轮换而不中断？

双 CA 并存 + 滚动更新：先把新 CA 加进所有节点的信任库，再逐个节点换用新 CA 签发的证书，等全部更新完（至少一个证书周期）后再移除旧 CA。全程无中断。

自检

mTLS 握手成功，能证明该服务有权执行任意支付操作吗？

不能。握手认证服务身份，具体扣款、查询或退款权限仍须在策略和业务层判断。
