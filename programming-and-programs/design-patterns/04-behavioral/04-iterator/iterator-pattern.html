01 · 从问题出发

为什么会需要这个模式？

调用方既要遍历数组又要遍历树；若直接依赖存储结构，换结构会改遍历代码。

报表模块直接用数组下标遍历订单。后来订单改存树结构，所有报表都要改循环；如果还要支持按时间倒序，又会出现更多遍历分支。

😵 直接写会怎样

for i in range(orders.length):
  render(orders[i])
// 假设 orders 永远是数组

💡 关键转折

集合提供迭代器，调用方只用 hasNext/next 或语言的 for-of 协议。

把遍历位置与推进规则放进迭代器。客户端只问“还有吗、下一个是谁”，不用知道数组下标或树遍历栈。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

iterator = collection.iterator()
while iterator.hasNext():
  item = iterator.next()
  visit(item)

// 树迭代器内部可维护 stack；调用方不需要知道。

读代码时抓住三件事

  1. hasNext 和 next 是外部遍历契约。
  2. 迭代器内部保存状态，不把游标暴露给客户端。
  3. 不同迭代器可提供不同顺序，如正序、倒序。

换个业务场景，还能认出来吗？

数据库游标、语言里的 for-of/Iterable 都体现了迭代思想。遍历远程数据时要暴露可能的失败与资源关闭，不应假装网络迭代等同内存数组。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

遍历方式要统一，集合内部结构不应泄漏

三个具体场景

  • 数组与树统一逐项访问
  • 同一集合提供正序与倒序
  • 分页数据隐藏取下一页的细节

不适合或要小心

迭代期间修改集合要定义规则：快照、失败即报错或弱一致。迭代器不自动解决并发安全。

远程迭代还需处理延迟、异常和资源关闭

最容易混淆的相邻模式

模式真正的区别
组合定义树形部分-整体结构；迭代器决定怎样访问结构中的节点。
访问者把对每种节点的操作分离出来；迭代器负责走到每个节点。

区分时问自己：要解决怎样走到每个节点，还是走到后对节点做什么？

落地前检查

  • 定义遍历期间集合被修改时的行为。
  • 测试空集合、末尾与重复 next。
  • 远程迭代要处理关闭、分页和失败恢复。
06 · 自己说一遍

两道检验理解的小题

把数组换成树，调用方循环要改吗？

若迭代器契约相同，就不必改；只换集合内部的迭代实现。

一个集合只能有一个迭代器吗？

不是。可同时提供正序、倒序、深度优先等多个迭代器，且各自保存独立游标。

第二层 · Go 里四种遍历方式的代价对比

方式内存能否提前退出适用主要代价
一次性构造 sliceO(n) 全量能数据量小（< 1 万）先把全部数据装进内存
回调（func(yield)）O(1)能（返回 false）Go 1.23 前的通用做法控制流反转，break/return 难写
通道 channelO(缓冲)能（close + return）跨 goroutine / 流水線忘记退出会泄漏 goroutine
iter.Seq（Go 1.23+）O(1)能（break 即可）惰性序列、数据库游标需要 Go 1.23 及以上
// Go 1.23 range-over-func：写一个返回 iter.Seq 的惰性迭代器
func Lines(r io.Reader) iter.Seq[string] {
	return func(yield func(string) bool) {
		sc := bufio.NewScanner(r)
		for sc.Scan() {
			if !yield(sc.Text()) { // 调用方 break → yield 返回 false → 这里 return
				return
			}
		}
	}
}

// 调用方：语法和普通遍历一样，但内存是 O(1)
for line := range Lines(file) {
	if strings.Contains(line, ‘ERROR’) {
		fmt.Println(line)
		break // 提前退出会一路传到 yield，文件不会被继续读
	}
}

// 带错误的序列用 iter.Seq2（第一项是值，第二项是 error）
func Rows(q *sql.DB) iter.Seq2[Row, error] {
	return func(yield func(Row, error) bool) {
		rs, err := q.Query(‘select id, name from users’)
		if err != nil {
			yield(Row{}, err)
			return
		}
		defer rs.Close() // defer 在这里安全：函数返回时一定关闭
		for rs.Next() {
			var r Row
			if err := rs.Scan(&r.ID, &r.Name); err != nil {
				yield(Row{}, err)
				return
			}
			if !yield(r, nil) {
				return
			}
		}
	}
}

// 通道版（跨 goroutine 时用）：重点是有退出路径
func LinesCh(ctx context.Context, r io.Reader) <-chan string {
	ch := make(chan string)
	go func() {
		defer close(ch) // 关键：无论怎么退出都要 close，否则接收方永远阻塞
		sc := bufio.NewScanner(r)
		for sc.Scan() {
			select {
			case ch <- sc.Text():
			case <-ctx.Done(): // 关键：给一个退出出口
				return
			}
		}
	}()
	return ch
}

为什么通道版必须有 ctx：如果接收方提前 return 不再读，发送方会永远卡在 ch <-，goroutine 和它持有的 Reader 都无法回收 —— 这是线上最常见的 goroutine 泄漏来源之一。

第三层 · 迭代器的六个高频坑

  • 遍历中修改集合：增删元素会让迭代器下标错位或死循环；要么先快照，要么用支持并发修改的结构。
  • 通道迭代器泄漏：见上，必须有 defer close(ch) + ctx 退出路径，且接收方要用 for range ch。
  • 迭代器持有大对象：闭包里引用了整个切片或文件句柄，迭代期间这些内存无法释放；只捕获需要的字段。
  • 游标没关：数据库/文件迭代器提前 break 会跳过后续的 Close()；用 defer 写在 yield 函数体内。
  • 无限序列没有退出条件：迭代器天然可以无限（如随机数、心跳包），调用方必须有 break 或 Limit。
  • 并发遍历同一迭代器：迭代器通常有内部状态（当前位置），不可并发共享；每个 goroutine 各自创建一份。

选型口诀：小数据用 slice，惰性大数据用 iter.Seq，跨 goroutine 才用 channel。能用 range 就不要手写 HasNext/Next。

第四层 · 为什么大多数语言里很少手写迭代器

既然语言内置了 for/range，这个模式还有什么用？

内置语法只能遍历语言已知的集合（slice、map）。真正需要手写的是数据源不在内存里的场景：数据库游标、分页 API、文件流、树/图遍历、无限序列 —— 这些必须用惰性迭代器避免一次性加载。

迭代器和生成器是一回事吗？

生成器是语言提供的一种写法（yield 关键字），产出物就是迭代器；迭代器是接口契约。Go 1.23 之前没有生成器语法，所以用闭包回调或通道模拟，效果相同但写法笨重。

惰性求值的代价是什么？

每次取元素都要走一次函数调用（无法内联时约几纳秒级开销），且调试栈变深；所以热路径上的小集合不要为了优雅改成惰性，直接构造 slice 更快也更易读。

模式速览：把「怎么遍历」从「存什么」里分离出来

迭代器解决的是一个很具体的问题：集合的内部结构可能变，但遍历它的方式不应该跟着变。把遍历逻辑挪到独立的迭代器对象里，调用方只需要知道「还有没有下一个」，不需要知道背后是数组、链表还是树。

迭代器的真正价值

不是「能遍历」，而是遍历方式可以独立变化：同一个树可以有前序、中序、层序三种迭代器，客户端代码完全不用改。如果只是数组遍历，直接循环就好。

为什么有些语言里很少手写它

因为语言已经内置了：遍历协议、生成器、range 语法都在做同一件事。这时手写迭代器反而是重复造轮子，真正需要手写的是「非顺序结构的自定义遍历」。

Go 里的实现：从显式迭代器到函数式遍历

// 方式一：显式迭代器接口 type Iterator[T any] interface { HasNext() bool Next() T } // 方式二：函数式遍历（Go 1.23 起可直接 range 函数） func (t *Tree) All(yield func(v int) bool) { var walk func(n *Node) bool walk = func(n *Node) bool { if n == nil { return true } if !walk(n.Left) { return false // 调用方想提前结束 } if !yield(n.Value) { return false } return walk(n.Right) } walk(t.Root) } // 使用：和遍历普通集合一样自然 for v := range tree.All { if v > 100 { break // 提前退出，遍历会正确停止 } fmt.Println(v) } // 关键点： // 1) yield 返回 false 表示调用方不想继续，必须立刻停止 // 2) 递归遍历要保证每个分支都检查这个返回值 // 3) 这样遍历是惰性的，不需要先把整棵树展开成切片

深入自检：迭代器的五个问题

遍历时修改集合会怎样？

大多数实现会直接报错或行为未定义。常见做法是在集合上维护一个修改计数，迭代器每次取元素前比对，不一致就抛出并发修改异常。这是为了尽早暴露问题，而不是静默产生错乱结果。

迭代器是一次性的吗？

通常是：它持有游标状态，走完就结束了。想再遍历一次要重新索取一个。这与「集合本身可以反复遍历」不矛盾，因为集合负责创建新的迭代器。

惰性遍历有什么好处？

不需要把所有元素先准备好：可以边读边遍历大文件、可以遍历理论上无限长的序列、可以提前中断而不浪费已经做的准备工作。代价是每次取元素都有一点调用开销。

多种遍历顺序怎么组织？

提供多个创建方法，各自返回不同顺序的迭代器。集合本身不变，遍历策略独立演化。这正体现了这个模式的价值：把变化的部分（遍历方式）隔离在独立对象里。

什么时候不该用它？

当集合就是简单的连续结构、且只有一种遍历顺序时，直接循环最清楚。引入迭代器反而增加了一层间接，读者要先理解接口才能看懂代码。
