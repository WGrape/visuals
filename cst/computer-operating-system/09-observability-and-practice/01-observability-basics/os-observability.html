操作系统可观测性：从症状找到资源瓶颈

把 CPU、内存、磁盘与进程证据串成一次可复验的排查。

学完能解释什么

  • 将用户症状映射到 OS 的资源信号
  • 区分使用率、饱和、错误率和排队延迟
  • 按整机 → 进程/线程 → 调用栈收集证据

逐步看机制

定义时间窗与对照

记录请求延迟、错误率、负载和发布/流量变化；只看单次 top 截图不足以定位。

四种证据不要混为一谈

使用率说明资源工作了多久；饱和说明还有多少工作在排队；错误说明请求或设备是否失败；延迟说明完成一次工作花了多久。CPU 使用率不高但运行队列长，可能是限额、调度或采样口径问题；load average 也不是 CPU 百分比，它还可能包含等待不可中断 IO 的任务。

从哪里看起

现象先取的证据下一步
CPU 持续高top / pidstat -u，user/sys 与线程分布perf 或语言 profiler 采样调用栈，不先猜业务函数
内存持续涨RSS、页缓存、major faults、swap in/out区分可回收缓存、堆增长和 OOM 事件；对比快照
请求慢但 CPU 不高iostat 延迟与队列、网络重传、进程阻塞状态沿请求链路定位等待点，避免只优化 CPU

工具语义随系统版本变化：采样窗口、容器资源限额和单位必须记录。strace 可见系统调用但有开销；生产环境先缩小目标进程与时间窗。

一次可复验的排查记录

  1. 写清症状：例如 P99 从 200 ms 升到 1 s，持续十分钟。
  2. 收集同一窗口的整机与进程指标，标注发布时间与流量。
  3. 提出可证伪假设：线程在 IO 等待，而不是“机器不够快”。
  4. 选择低扰动的采样方法定位等待/热点；保留结果与条件。
  5. 只改一个变量，在相同负载下复验延迟、错误和资源成本。

自检

内存 RSS 增长就一定是内存泄漏吗？

不一定。它可能是进程堆、内存映射或缓存增长；还要看对象存活、可回收页、换页与同负载对照。

可观测性 ≠ 监控

监控回答「预设的问题是否正常」（CPU 高不高、接口挂没挂）；可观测性回答「没预设过的问题能不能查明白」。区别的关键在于：可观测的系统保留了足够的上下文（高基数维度、完整调用链、结构化日志），让你能在事后提出任意问题。

指标 Metrics聚合数值，成本最低，适合告警与趋势
日志 Logs离散事件，信息最全，成本最高
链路 Traces请求跨服务的完整路径，定位瓶颈
基数 Cardinality维度取值组合数，是指标成本的关键
SLO / SLI把「用户感受到的可靠性」量化成目标
USE / RED两套经典的资源/服务排查方法

排查顺序建议：RED（哪个服务出问题）→ USE（哪类资源饱和）→ Traces（哪一段慢）→ Logs/Profiling（为什么慢）。跳步容易在错误的方向上深挖。

Linux 上的观测工具箱

① 快速巡检 60 秒

  • uptime：负载均值（注意要看核数归一化）。
  • dmesg -T | tail：OOM、磁盘错误、网络异常。
  • vmstat 1：r 运行队列、si/so 换页、us/sy/id CPU 分布。
  • mpstat -P ALL 1：各核是否均衡、是否有单核打满。
  • pidstat 1：按进程看 CPU/内存/IO。
  • iostat -xz 1：磁盘 await、util、队列。
  • sar -n DEV 1：网卡流量与错包。

② 深入定位

  • top/htop：交互查看；perf top：CPU 热点函数。
  • perf record -g + 火焰图：找 CPU 热点与调用栈。
  • strace -p：看系统调用（注意有开销）。
  • ss -s / ss -i：连接状态、cwnd、rtt。
  • /proc/PID/* 与 /proc/PID/status：进程细节。
  • eBPF 工具（bcc/bpftrace）：低开销的内核级观测。

③ 内存相关

  • 不要只看 free：buffer/cache 是可回收的，要看 available。
  • free -m + cat /proc/meminfo：看细节（Slab、Shmem、AnonPages）。
  • OOM：dmesg 里有 killed process 与打分；关注 oom_score_adj。
  • 泄漏排查：持续增长的 RSS + 定期采样对比，或 pprof heap。

④ 建立体系

  • 先定义 SLI/SLO，再决定采集什么——避免「什么都采、什么都用不上」。
  • 指标要有统一命名与标签规范（服务名、实例、接口、状态码）。
  • 告警要可行动：没有明确处理动作的告警就是噪声。
  • 日志要结构化并带 trace_id，否则排查时无法串联。
  • 保留容量与成本：日志最贵，指标次之，链路靠采样。

深入自检

监控和可观测性到底差在哪？

监控是「验证已知假设」（CPU 是否 >80%），可观测性是「支持未知探索」（为什么只有某类用户的请求慢）。后者要求数据保留高基数维度（用户 ID、URL、版本）与完整上下文，而这些在纯指标系统里往往因为成本被舍弃。

为什么 P99 比平均值重要？

因为用户体验由最差的请求决定：一个页面要发 20 个请求，只要有 1 个慢，用户就要等。平均延迟好看但 P99 很差的接口，实际体感是「时不时卡一下」。所以 SLO 通常用分位数而不是均值。

为什么要避免高基数标签？

因为时序数据库按「标签组合」存储序列：一个 user_id 标签若有百万取值，就会产生百万条时间序列，索引与存储成本爆炸。正确做法：高基数信息放日志与链路（天然支持），指标只保留低基数维度（服务、接口、状态码）。

CPU 使用率高就一定是 CPU 瓶颈吗？

不一定。要区分：us（用户态）高才是真的计算密集；sy 高可能是系统调用过多；wa 高说明在等 IO（瓶颈是磁盘/网络）；si/hi 高是软硬中断。还要看运行队列（r）是否堆积——这才是「饱和」的信号。USE 方法就是在教我们区分这些。

负载均值（load average）怎么读？

它是「可运行 + 不可中断睡眠」状态的进程数均值。要先除以 CPU 核数再判断：8 核机器上 load 8 是刚好打满，load 16 说明有一半在排队。注意它包含 D 状态（等 IO），所以 load 高但 CPU 空闲，通常是磁盘或网络问题。

线上出问题第一步该做什么？

先止损再定位：能回滚就回滚、能降级就降级、能扩容就扩容，把用户影响降到最低；同时保留现场（摘掉一台机器不重启、抓 perf/堆转储/日志）。事后再做复盘（blameless postmortem）。永远不要在故障中「边想边改生产」。
