页表与 TLB：一次内存访问为什么可能要查四次页表

虚拟内存让每个进程都以为自己独占内存，代价是每次访问都要把虚拟地址翻译成物理地址。翻译靠页表，而页表在内存里——于是又需要 TLB 来缓存翻译结果。这是「缓存套缓存」的经典结构。

一句话定位：地址翻译是查表，TLB 是这张表的缓存

虚拟地址被切成若干段，每段是一个页表索引，逐级查到最终的物理页帧，最后拼上页内偏移。4 级页表意味着最坏 4 次内存访问；TLB 把最近用过的翻译结果缓存起来，命中就只需 1~2 个周期。

页大小4KB（12 位偏移）、2MB / 1GB 大页
x86-64 页表4 级（PML4→PDPT→PD→PT），48 位虚拟地址
TLB 命中1~2 周期；缺失要页表游走
大页一项覆盖 2MB，TLB 覆盖范围放大 512 倍

2MB 大页能大幅降低 TLB 压力，但会增加「内部碎片」（分配 2MB 但只用 100KB 就浪费 1.9MB），也可能让内存回收变慢。数据库（如 Oracle、PostgreSQL 的 huge_pages）通常是受益方，小内存容器则要谨慎。

// 改法一：用 2MB 大页，页表项降到 512 个
// 改法二：把随机访问改成块内顺序（提升局部性）
// 改法三：预取（硬件预取器对跨页随机访问几乎无效）

判断依据：perf stat -e dTLB-load-misses,page-faults。如果 dTLB miss 占访问数的比例超过几个百分点，且每次 miss 都伴随多次内存访问，就说明 TLB 覆盖范围不够。

原理与取舍：为什么是四级而不是一级

一级页表要为整个地址空间建表：48 位地址、4KB 页意味着 2³⁶ 个页表项，每项 8 字节就是 512GB——每个进程光页表就装不下。多级页表按需分配，只用到的分支才建表，空间从「地址空间大小」降到「实际使用量」。代价是查询变慢，于是又用 TLB 把常用翻译缓存起来。

TLB 缺失时谁去走页表？

早期是硬件（x86 的 page table walker），现代多是硬件自动游走；某些架构（如 MIPS）由软件在异常处理里完成，灵活性高但更慢。

进程切换为什么要刷新 TLB？

因为不同进程的虚拟地址含义不同。PCID/ASID 标签可以让不同进程的 TLB 项共存，避免全量刷新（这也是 Meltdown 修补后性能损失的关键缓解手段）。

为什么缺页比 TLB 缺失慢这么多？

TLB 缺失最多走 4 次内存（几百纳秒），缺页要去磁盘/SSD 取 4KB 数据（几十微秒到几毫秒），差 3~4 个数量级。
