SSH 主机密钥、用户认证与端口转发：第一次连接该信谁

从登录远程服务器到转发数据库端口，区分服务器身份、用户身份和隧道可达范围。

登录之前先确认服务器是谁

SSH 客户端连接远端 22 端口时，双方协商算法并建立加密通道；服务器用主机密钥证明自己持有对应私钥。客户端将服务器公钥指纹与已知记录或可信渠道给出的指纹比较。首次连接常见的“是否信任此主机”提示是一种 TOFU（首次使用时建立信任）的过程；若盲目接受一个被劫持的连接，后续加密也可能只是在和攻击者安全通信。

主机密钥变更可能是服务器重装、地址被重新分配，也可能是中间人攻击。遇到 known_hosts 警告，应通过独立渠道核对新指纹，再更新记录，不能把删除 known_hosts 当作万能修复。DNS 能解析到某 IP 不等于该主机身份可信。

用户公钥认证是另一方向

主机身份确认后，服务器还需验证来访用户。常见公钥认证中，用户把公钥放入服务器授权列表，客户端用私钥完成签名证明；私钥不应复制到服务器的 authorized_keys 中。用户名、允许的公钥、账户权限决定可登录范围。密码认证可作为其他方案，但在公网环境下需考虑暴力尝试、防护和多因素认证。

“有 SSH 密钥”还不等于拥有 root 权限。登录后的文件权限、sudo、审计与命令限制继续生效。私钥宜有本地保护，自动化密钥应限定用途和轮换周期，离职或设备丢失时要能撤销。

本地端口转发怎么走

假设数据库只监听远端内网 `db.internal:5432`，工程师可以在本机建立一个本地端口，SSH 客户端把连到该端口的字节经加密连接送到 SSH 服务器，再由服务器连接数据库。概念命令形如 `ssh -L 15432:db.internal:5432 user@jump`；本机程序随后连 `127.0.0.1:15432`。这不表示数据库搬到了本机，最终能否连接仍取决于跳板机到数据库的网络权限和数据库自身认证。

默认应把本地监听限定在回环地址，避免让同一局域网其他主机也能通过工程师电脑进入数据库。隧道保护客户端到跳板机一段，跳板机到数据库是否另有 TLS 要单独确认。转发只搬运字节，不自动检查 SQL 权限。

远程与动态转发

远程端口转发 `-R` 让远端某端口的连接经 SSH 回到客户端侧，常用于临时暴露本地开发服务，但如果远端绑定到公共接口，暴露范围会扩大。动态转发 `-D` 可在本地提供 SOCKS 代理，浏览器或程序通过它选择目标；目标 DNS 在本地还是代理侧解析，依客户端配置而定。三种转发模式的“谁监听、谁发起到目标”不同，画出路径再配置可减少误用。

某些 SSH 服务端会禁止端口转发或限制可达目标。登录成功但转发失败时，查服务器 AllowTcpForwarding、PermitOpen 等策略和目标路由，不要直接给账户更高系统权限。

隧道不是完整授权

SSH 可加密和认证到跳板机的连接，却不会替后端服务做用户级授权。多人共用同一跳板账户时，数据库可能只看到同一个来源地址，审计困难。更好的做法是每人独立身份、最小权限与目标服务自己的认证，并记录谁在何时建立了哪条转发。对长期业务连接，不宜把个人工作站上的临时 SSH 隧道当作高可用生产链路。

端口转发还可能绕过原计划的网络分区。安全团队应明确允许哪些源、目标和端口，必要时限制跳板机向外连接。不能只因为“SSH 是加密的”就放行任意内部目标。

一次排障

连接失败先看 DNS 与 TCP 22，再看主机指纹、用户认证、服务器会话权限；端口转发失败则分段看本地监听、SSH 通道、跳板机到目标的 TCP、目标应用认证。用本机直连 `127.0.0.1:15432` 能建立 TCP，不证明数据库接受了用户登录。日志要区分 SSH 握手失败、转发请求被拒和数据库返回鉴权错误。

验收还要模拟 SSH 连接断开：本地隧道会失效，应用连接池如何感知并重连？如果会重放写请求，仍需要数据库事务或业务幂等设计。

主机密钥与认证方式

机制说明关键点
主机密钥（Host Key）服务器证明自己身份首次连接记录到 ~/.ssh/known_hosts；变更会强警告（防 MITM）
主机密钥算法ed25519 / ecdsa / rsa / dsa推荐 ed25519（短、快、安全）；dsa 已废弃
密码认证最简单易被爆破，建议禁用 PasswordAuthentication no
公钥认证推荐私钥留本地，公钥放 ~/.ssh/authorized_keys
证书认证大规模场景CA 签发的 SSH 证书，避免逐台分发公钥
StrictHostKeyChecking行为适用
yes未知主机拒绝连接生产/自动化（最安全）
accept-new（默认较新版本）未知主机自动接受并记录日常使用
no自动接受且不检查变更测试环境（有 MITM 风险）

SSH 常用命令

# 生成密钥（推荐 ed25519）
ssh-keygen -t ed25519 -C "me@example.com"
ssh-copy-id user@host                  # 分发公钥

# 权限必须正确，否则 SSH 会拒绝使用该密钥
chmod 700 ~/.ssh && chmod 600 ~/.ssh/id_ed25519 && chmod 644 ~/.ssh/authorized_keys

# 调试连接（看认证过程与卡在哪一步）
ssh -vvv user@host
# 常见输出：Offering public key → 被拒说明 authorized_keys 或权限有问题

# 端口转发
ssh -L 8080:127.0.0.1:80 user@host      # 本地转发：访问本机 8080 = 访问远端 80
ssh -L 0.0.0.0:8080:10.0.0.5:80 user@host   # 允许他人访问（需 GatewayPorts）
ssh -R 9000:127.0.0.1:3000 user@host    # 远程转发：把本机 3000 暴露到远端 9000
ssh -D 1080 user@host                   # 动态转发（SOCKS5 代理）

# 跳板机
ssh -J jump@ bastion user@target
# ~/.ssh/config
# Host target
#   ProxyJump bastion

# 连接复用（避免每次重新握手）
# Host *
#   ControlMaster auto
#   ControlPath ~/.ssh/cm-%r@%h:%p
#   ControlPersist 10m

安全加固与排障

配置项推荐值作用
PermitRootLoginno 或 prohibit-password禁止 root 直接登录
PasswordAuthenticationno只允许密钥，杜绝爆破
PermitEmptyPasswordsno禁空密码
Port非 22（可选）减少扫描与噪音（非安全措施）
MaxAuthTries3限制尝试次数
AllowUsers / AllowGroups显式白名单最小权限
ClientAliveInterval60（配 ClientAliveCountMax 3）约 3 分钟断开无响应连接
LoginGraceTime30限制登录耗时
  • known_hosts 变更警告：服务器重装/换 IP 后主机密钥变了，SSH 会报 REMOTE HOST IDENTIFICATION HAS CHANGED 并拒绝连接。确认是合法变更后用 ssh-keygen -R host 删除旧记录，不要盲目删（可能正遭受 MITM）。
  • 权限问题是最常见的密钥认证失败原因：~/.ssh 必须 700、私钥 600、authorized_keys 644，且家目录不能是全局可写。
  • 端口转发的安全默认：-L 默认只监听 127.0.0.1，监听 0.0.0.0 需要服务端 GatewayPorts yes，且等于把内网暴露出去，慎开。
  • 连接挂死的常见原因：中间 NAT/防火墙空闲超时（见 TCP keepalive 那篇）。解决：ServerAliveInterval 60 或服务端 ClientAliveInterval 60。
  • scp/rsync 的坑：scp 已不推荐（协议老旧），改用 rsync -avzP 或 sftp；rsync 的 -P 等于 --partial --progress，支持断点续传。
  • 排障顺序：① ssh -vvv 看卡在哪（DNS？TCP？认证？）；② telnet host 22 或 nc -vz host 22 确认端口通；③ 服务端看 /var/log/auth.log。
为什么加了公钥还要输入密码？

三种常见原因：① 服务端 authorized_keys 或 .ssh 权限不对；② 服务端 PubkeyAuthentication 被关或 AuthorizedKeysFile 路径不对；③ 本地有多个密钥，SSH 试完了不匹配的没试对的（用 -i 指定或在 config 里 IdentityFile）。

SSH 隧道算不算 VPN？

-D 动态转发是 SOCKS5 代理，只能代理支持 SOCKS 的应用且要逐应用配置；VPN 是系统级三层隧道。临时访问内网用 -L 更直接，长期多资源访问才需要 VPN。

自检

SSH 本地端口转发成功，是否表示数据库无需再做认证？

不表示。隧道只提供到目标的网络通道，数据库仍应独立验证用户与权限。
