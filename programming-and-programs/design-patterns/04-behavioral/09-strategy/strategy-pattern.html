🧭 策略

把可互换的算法封装起来，由使用方选择。

一句话记住导航可以选最快、最短或避开收费道路的路线算法。

01 · 从问题出发

为什么会需要这个模式？

运费计算因普通、加急、自提而不同；把所有公式塞进订单对象会让它不断增长。

运费有普通、加急、自提三种算法。订单类若直接 switch 配送方式，未来新增冷链运费就得改订单类，而且各类价格测试会混在一起。

😵 直接写会怎样

function shippingCost(order, mode):
  if mode == STANDARD: return 5 + order.weight * 2
  if mode == EXPRESS: return 15 + order.weight * 4
  if mode == PICKUP: return 0

💡 关键转折

Context 持有 Strategy 接口，运行时注入某个算法。

把每套可互换公式放进一个 Strategy。订单只调用 cost(order)，策略选择发生在组装处。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

interface ShippingStrategy { cost(order) }
class StandardShipping implements ShippingStrategy {
  cost(order) { return 5 + order.weight * 2 }
}
class ExpressShipping implements ShippingStrategy {
  cost(order) { return 15 + order.weight * 4 }
}
order.shipping = new ExpressShipping()
fee = order.shipping.cost(order)

读代码时抓住三件事

  1. 所有策略都遵守 cost(order) 契约并返回相同单位。
  2. Order 不检查策略具体类型。
  3. 策略的选择可以来自用户偏好、配置或业务规则，但要集中管理。

换个业务场景，还能认出来吗？

压缩器可在 gzip、zstd、无压缩策略之间切换；排序器也可注入不同比较策略。策略的价值在于让同一调用方自由替换一组算法。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

存在多套可互换算法，调用方需要按条件选用

三个具体场景

  • 普通/加急/自提运费计算
  • 最短/最快路径规划
  • gzip/zstd/无压缩的编码选择

不适合或要小心

策略选择本身仍要有规则；别把选择逻辑又散落到所有调用点。与状态模式相比，策略通常由外部选择，状态由对象的生命周期迁移。

策略选择规则应集中；所有策略须遵守相同结果语义

最容易混淆的相邻模式

模式真正的区别
状态行为随对象内部状态迁移；策略通常由外部显式选择一种算法。
模板方法用继承保留固定算法骨架；策略用组合替换整个算法或其中一段。

区分时问自己：算法由谁切换：外部选择，还是对象状态自行迁移？

落地前检查

  • 对所有策略做相同边界条件测试。
  • 策略返回值单位与错误语义要统一。
  • 选择规则不应重复散落到每个调用点。
06 · 自己说一遍

两道检验理解的小题

新增次日达会改订单的 cost 逻辑吗？

不用；新增实现 ShippingStrategy 的策略并在选择处注入。

如果普通运费改为阶梯价格，要改 Order 吗？

不用；只修改或替换 StandardShipping，并验证同一策略契约。

第二层 · 什么时候该把 if-else 换成策略

判据阈值结论
分支数量≥ 3 且预计还会加换策略
单分支代码量≥ 10 行换策略，否则 if 更直观
分支是否要运行时切换是（配置/用户选择）换策略，用 map 注册
分支是否要单独测试是换策略，可独立注入 fake
分支只在一处且永不变是保持 if，别过度设计
// Go 里最地道的写法：接口 + map 注册 + 工厂函数
type Pricer interface {
	Price(ctx context.Context, o Order) (int64, error)
}

type pricerRegistry struct {
	mu    sync.RWMutex
	items map[string]Pricer
}

func (r *pricerRegistry) Register(name string, p Pricer) {
	r.mu.Lock()
	defer r.mu.Unlock()
	r.items[name] = p
}

// 关键：找不到策略要报错，不要静默走默认 —— 静默默认会掩盖配置错误
func (r *pricerRegistry) Get(name string) (Pricer, error) {
	r.mu.RLock()
	defer r.mu.RUnlock()
	p, ok := r.items[name]
	if !ok {
		return nil, fmt.Errorf('unknown pricer: %s', name)
	}
	return p, nil
}

// 初始化时集中注册，读配置决定用哪个
func NewRegistry() *pricerRegistry {
	r := &pricerRegistry{items: map[string]Pricer{}}
	r.Register('vip', VipPricer{})
	r.Register('normal', NormalPricer{})
	r.Register('promo', PromoPricer{})
	return r
}

// 单方法策略直接用函数类型，更轻（Go 惯用法）
type PriceFunc func(context.Context, Order) (int64, error)
func (f PriceFunc) Price(ctx context.Context, o Order) (int64, error) { return f(ctx, o) }

性能量级：map 查找约几十纳秒、接口调用因无法内联多几纳秒。除非在极热的循环里（每秒千万次以上），否则这点开销远小于它带来的可维护性 —— 不要为了省这几纳秒把策略写回 switch。

第三层 · 策略模式的六个高频坑

  • 找不到策略时静默走默认：配置写错了却按默认逻辑跑，错误被掩盖到很晚才发现；必须显式报错。
  • 策略持有可变状态：注册进去的是单例，多个请求并发调用会互相污染；策略要么无状态，要么每次新建。
  • 策略数量爆炸：几十个策略类且每个只有几行 → 考虑用配置表 + 表达式引擎，而不是铺类。
  • 策略依赖具体上下文：接口参数写成了 *AppContext，导致策略无法单测；只传它真正需要的参数。
  • 注册顺序有隐式依赖：注册代码散落各处，顺序不确定 → 集中在一个初始化函数里注册。
  • 策略与选择逻辑混在一起：在策略里判断「该用哪个策略」 → 选择逻辑应放在工厂或配置层。

判断该不该抽策略：看分支会不会继续增加。两个固定分支用 if 完全合理，第三次出现同样形状的分支时再抽，这时模式收益才大于成本。

第四层 · 策略、模板方法、状态模式的边界

策略和模板方法都能消除 if，怎么选？

策略替换的是整个算法（调用方选一个实现全部替换）；模板方法固定的是算法骨架（只替换其中某几步）。判断信号：如果各分支的流程顺序都一样，用模板方法。

策略模式和状态模式长得很像，区别在哪？

策略是调用方显式选择，一次调用内不变；状态是对象自己随着内部状态改变行为，切换发生在运行时且通常由状态机驱动。

策略模式真的实现了开闭原则吗？

只实现了一半：新增策略不用改已有代码（对扩展开放），但总要有一处地方知道有哪些策略（注册或工厂），那处仍要改。这是它的真实边界，别神化。

一、什么时候该把 if-else 换成策略

信号症状说明
分支超过 3 个switch 越来越长加一种就要改调用方，违反开闭
分支里有复杂逻辑每个 case 几十行应该各自成类，独立测试
运行期才决定按配置/用户类型选择策略天然支持动态切换
分支会持续增加每次需求都加一种提前用策略避免腐化

二、Go 里最地道的写法

// 1) 策略就是一个函数类型，不需要接口和结构体 type PriceFn func(order Order) int // 2) 各个策略只是普通函数 func normalPrice(o Order) int { return o.Amount } func vipPrice(o Order) int { return int(float64(o.Amount) * 0.8) } func promoPrice(o Order) int { return o.Amount - 50 } // 3) 注册表：把「选择逻辑」集中到一处 var strategies = map[string]PriceFn{ "normal": normalPrice, "vip": vipPrice, "promo": promoPrice, } // 4) 调用方不再有分支 func Price(o Order, kind string) int { fn, ok := strategies[kind] if !ok { return normalPrice(o) } // 兜底策略 return fn(o) }
Go 的简化

Go 有头等函数，绝大多数策略模式可以退化成「函数类型 + map 注册表」，不需要定义接口和一堆结构体。只有当策略需要多个方法或自带状态时，才值得用接口。

三、策略 vs 其他

模式换什么怎么换典型场景
策略整个算法组合注入多种计价/排序/压缩算法
模板方法算法中的步骤继承/接口实现流程固定、步骤可变
状态对象行为随内部状态变状态对象驱动转换订单状态流转
命令把请求封装成对象排队、撤销、记录任务队列、undo
桥接抽象与实现独立变化双向组合跨平台渲染

区分策略与状态最快的方法：策略由外部选择（调用方说用哪种），状态由内部驱动（对象自己根据当前状态切换行为，状态之间还能互相转换）。

五、深入自检

策略会不会让类变多？

会。每个策略一个类/函数，但换来的是「加策略不改调用方」和「每个策略可独立测试」。判断标准：分支超过 3 个且会继续增长时，这笔交易划算。

策略之间需要共享数据怎么办？

通过上下文对象传入，而不是让策略持有引用。这样策略保持无状态、可复用、可并发。如果确实需要状态，就把它作为策略自己的私有字段，并在文档里说明线程安全性。

选策略的逻辑放哪？

集中在工厂或注册表里，而不是散落在业务代码。这样「哪种情况用哪个策略」只有一处定义，改规则时不至于漏改。

和函数式选项（Functional Options）冲突吗？

不冲突，反而常搭配：用 Options 配置对象的各个维度，其中一个维度就是「选择哪个策略」。两者都是「把变化点外置」的思想。

策略模式的代价是什么？

调用方必须知道有哪些策略可选（增加了认知负担），且策略数量多时注册表会变大。另外策略接口设计不当会导致「胖接口」——某些策略根本用不到某些方法。
