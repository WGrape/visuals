①COUNT 的四种写法各数什么

写法统计对象含 NULL？典型代价
COUNT(*)行数数所有行，不看列值最低，优化器可选最小索引
COUNT(1)行数同 COUNT(*)与 COUNT(*) 基本等价
COUNT(col)该列非 NULL 值的个数跳过 NULL需读该列，可能回表
COUNT(DISTINCT col)该列去重后的值个数跳过 NULL需排序或哈希去重，最贵
COUNT(*) 与 COUNT(1) 没有性能差别， 优化器都会改写成同一形式，老资料里「用 1 更快」的说法早已不成立。 真正有差别的是 COUNT(col)——它必须判断该列是否为 NULL，且如果该列不在索引里就要回表。
-- 用 COUNT(*) 与 COUNT(col) 的差值探测 NULL 数量
SELECT COUNT(*) AS total,
       COUNT(phone) AS has_phone,
       COUNT(*) - COUNT(phone) AS null_phone
FROM users;

-- 多列同时去重计数（标准 SQL 支持，MySQL 也支持）
SELECT COUNT(DISTINCT user_id, product_id) FROM orders;
InnoDB 里 COUNT(*) 为什么慢？因为它没有像 MyISAM 那样维护一个行计数器—— MVCC 下「当前事务能看到多少行」取决于快照，无法用一个全局数字回答。 所以大表精确计数只能扫（优化器会挑最小的二级索引扫，而不是聚簇索引）。 解决路径：近似值用 SHOW TABLE STATUS / 统计信息；精确值维护计数表或用缓存； 带条件的计数用汇总表（summary table）预聚合。

②DISTINCT 的真实成本

DISTINCT 不是「过滤」，而是一次去重运算——要么排序后相邻去重（O(n log n)）， 要么建哈希表去重（O(n) 内存）。理解这点就能解释它为什么常常成为慢查询的元凶。

去重一定要「看见全部数据」之后才能输出结果的第一行——这也是它天然不利于流式响应
  1. DISTINCT 作用于整个 SELECT 列表的组合，不是作用于第一个列。SELECT DISTINCT a, b 是 (a,b) 组合去重。
  2. SELECT DISTINCT a 与 GROUP BY a 在无聚合时等价，多数优化器生成相同计划。
  3. DISTINCT 与 ORDER BY 字段不一致会强制额外排序，甚至报错（PG 要求 ORDER BY 的表达式必须出现在 SELECT DISTINCT 列表中）。
  4. 有索引时能跳过去重：若去重的列上有索引，优化器可用「索引跳跃扫描 / loose index scan」只读每个不同值的第一条，代价骤降。MySQL 对 GROUP BY 有此优化，DISTINCT 支持度较弱。
Q：SELECT DISTINCT 能加速 COUNT 吗？
A：常见误解。COUNT(DISTINCT col) 与先 DISTINCT 再 COUNT 代价相当， 真正的加速来自索引覆盖 + loose scan。数据量大又要求精确，就建汇总表。

③DISTINCT 与 GROUP BY 的分工

维度DISTINCTGROUP BY
目的去掉重复行分组后每组产出一行（通常配聚合）
能否带聚合函数能但语义奇怪天然搭配
能否 HAVING不能能
是否排序不保证历史上 MySQL 会隐式排序，8.0 起不再保证
输出列限制只能输出去重列可输出分组列 + 聚合结果
-- 两种写法等价（无聚合时）
SELECT DISTINCT dept FROM emp;
SELECT dept FROM emp GROUP BY dept;

-- 但一旦要统计，只能用 GROUP BY
SELECT dept, COUNT(*) FROM emp GROUP BY dept;

-- 去重后再统计人数：先收敛到键，再 JOIN 明细
SELECT COUNT(*) FROM (SELECT DISTINCT user_id FROM orders) t;
ONLY_FULL_GROUP_BY：开启后（MySQL 5.7+ 默认），SELECT 列表里的非聚合列 必须出现在 GROUP BY 中或函数依赖于分组列。它拦住的是「返回哪一行的值是随机的」这类不确定查询， 不要为了跑通旧 SQL 去关掉它——正确做法是补全 GROUP BY 或用 ANY_VALUE() 显式表态。

④精确 vs 近似：什么时候不必较真

精确计数

扫索引 / 汇总表 / 计数表。适合财务、库存、对账，以及任何用户会「拿它做决策」的场景。

近似计数

读统计信息或系统表的估算值，零成本但可能差 10%~50%。适合「约 120 万条」这类展示， 以及是否走某个执行路径的优化器决策。

基数估算（UV 类）

HyperLogLog 类结构，用几 KB 内存估出亿级去重基数，误差约 1%~2%。 Redis 的 PFCOUNT、部分数据库的近似 APPROX_COUNT_DISTINCT 即为此。

预聚合

按天/按维度写汇总表，查询直接读汇总。写入侧多花一点，读取侧快几个数量级。 日报、看板、大盘类需求的标准解法。

经验口径：「总数」展示用近似，翻页到第 N 页这种需要精确边界的用精确， UV/DAU 这类去重基数可以接受 1%~2% 误差就用 HLL。 先问清楚业务能不能容忍误差，再决定架构——这一步省下来的资源往往比优化 SQL 大得多。
