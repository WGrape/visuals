模型格式与推理运行时

safetensors / GGUF / ONNX / TensorRT 各自解决什么问题，以及按硬件、目标、模型支持度选推理引擎的五步决策顺序。

先分清两件事：格式 vs 运行时

模型格式（存什么）
权重文件怎么组织、用什么精度、元数据怎么记。 决定"这个文件能不能被某个引擎加载"。
运行时 / 引擎（怎么跑）
调度、批处理、显存管理、算子实现。 决定"同样的权重跑多快、能撑多少并发"。
两者可以自由组合，但不是任意组合都支持： 常见误解是"转成 ONNX 就一定更快"——格式只决定能否加载，加速来自引擎的算子融合与调度。

常见格式对照

格式定位典型用途
safetensorsHugging Face 生态的默认权重格式，不带执行代码，加载快且安全训练产出、模型分发、再量化前的源
GGUF面向 CPU / 端侧的单文件格式，内置量化类型与元数据llama.cpp / Ollama 本地跑、Mac、嵌入式
ONNX跨框架的计算图表示，不绑定训练框架小模型、CV/传统 ML 部署、ORT 推理
TensorRT / engine planNVIDIA 编译后的硬件相关产物固定 GPU 型号、追求极致延迟
TorchScript / torch.exportPyTorch 原生的可序列化图PyTorch 体系内部部署
安全提醒：老式的 .bin（pickle）加载时会执行任意代码， 从非可信来源下载模型有风险。优先选择 safetensors。

运行时选型

选型决策顺序

  1. 先看硬件：只有 CPU 就用 GGUF + llama.cpp 系；有 NVIDIA 再看下面。
  2. 再看目标：要吞吐（多并发、长对话）→ 连续批处理系；要单请求极低延迟（实时语音、实时翻译）→ 编译优化系。
  3. 确认模型支持：新架构（新注意力变体、MoE）往往要等引擎跟进，社区版可能落后于官方模型发布。
  4. 确认功能叠加：量化 + 投机解码 + 前缀缓存 + 结构化输出能否同时开，各版本差异很大。
  5. 最后压测：用真实请求分布（输入长度、输出长度、并发）测，不要用固定长度的合成 benchmark 下结论。
一条务实建议：先用生态最成熟、社区最活跃的那一个跑起来并压测， 把瓶颈定位清楚（是 prefill 慢、decode 慢、还是排队慢），再决定要不要换引擎。 过早做引擎选型优化，收益通常不如先把请求调度和显存管理调对。

先分清三件事：框架、格式、运行时

新手最容易混的概念有三个。把它们分开，选型就清楚了一半：

训练框架PyTorch / JAX 等，产出 checkpoint，关注易用性与生态。
存储格式权重与结构被怎么序列化成文件：决定了能否跨框架、是否安全、能否 mmap。
推理运行时真正执行计算的引擎：ONNX Runtime、TensorRT、vLLM、llama.cpp……

一个「模型的文件夹」里通常包含这些东西：

model-dir/ ├── *.safetensors 或 pytorch_model.bin # 权重（可能切片成多个） ├── config.json # 架构超参（层数、头数、维度） ├── generation_config.json # 默认采样参数、停止 id ├── tokenizer.json / tokenizer_config # 分词器 ├── special_tokens_map.json └── *.model / merges.txt # 部分分词器的词表文件

注意：文件名里的超参必须和权重张量的形状一致，否则加载会直接报 shape mismatch。很多「模型加载失败」其实是 config.json 被替换或版本不匹配。

主流格式速览

格式谁在用特点适合场景
PyTorch .pt / .bin训练与 Python 侧推理生态最全，但基于 pickle，加载会执行反序列化逻辑研究、微调中间产物
SafeTensorsHugging Face 生态默认只存张量+元数据，无代码执行风险；支持 mmap 零拷贝、按需加载绝大多数场景的首选
GGUFllama.cpp 及其衍生（Ollama 等）单文件封装权重+tokenizer+元数据，内置多种整数量化本地/CPU/Apple 芯片、离线部署
ONNX跨框架部署计算图层面的开放标准，不绑定训练框架想把同一个模型跑在不同硬件/语言栈上
TensorRT engineNVIDIA GPU 高吞吐针对具体显卡做 kernel 选择与融合编译，速度极致线上 Serving 追求极致延迟/吞吐
环境专用格式CoreML / OpenVINO / TFLite面向特定硬件（苹果神经引擎、Intel、移动端）端侧、嵌入式、隐私合规

SafeTensors 为什么能取代 pickle：pickle 的本质是「按指令重建任意 Python 对象」，一旦文件被投毒，加载时就可能执行任意代码。SafeTensors 只允许「按偏移量取一块字节当作某种 dtype 的张量」，结构上无法携带可执行逻辑，而且支持内存映射——20GB 的模型不必先完整读进内存，多个进程还能共享同一份物理内存。

量化的名字到底在说什么

量化就是用更少的比特存每个权重，换显存下降与带宽节省。常见命名例如 Q4_K_M，可以拆成三部分读：

Q4每个权重约 4 bit（还有 Q2/Q3/Q5/Q6/Q8）。
K / S / _0量化方案的代际/家族，影响分组方式与重要权重的处理。
S / M / L同样 bit 下保留多少高精度权重；越大越准也越大越慢。
对称 vs 非对称是否假设数值围绕 0 对称；非对称多一个零点，拟合更准但多一次计算。

两条经验：① 优先选对而我们常说的「低比特不一定更快」—— INT4 权重需要反量化后才能计算，只有在访存受限（batch 小、decode 阶段）时才显著加速，compute-bound 场景反而可能更慢；② 量化前一定保留一份 fp16 基线，用困惑度或自建小评测对比，别只看模型体积。

运行时怎么选

需求优先候选理由
GPU 上服务大语言模型、要高吞吐vLLM / TensorRT-LLM 类连续批处理 + PagedAttention 类机制，把 batch 利用率做满
本地跑、Mac 或纯 CPUllama.cpp 生态（GGUF）依赖少、量化成熟、启动快
跨 CPU/GPU/多种语言栈ONNX Runtime一套 IR 多处执行，Windows/Linux/Web 都有后端
NVIDIA 上极限延迟编译型引擎（TensorRT 路线）按卡型做 kernel 调优，但需要按型号重新编译
验证想法、快速起 API轻量包装层 / 托管服务先把链路跑通，再考虑优化

一条现实建议：不要一开始就上编译型方案。先用标准权重 + 通用运行时跑通并拿到基线（延迟、吞吐、显存、质量），再按瓶颈决定是否转 ONNX / 编译 / 量化。免先验能不能跑，再问跑多快，因为转换链路常常因为不支持的算子卡住。

深入自检

为什么有的模型下载下来几十 GB，跑起来显存还要更多？

因为推理显存 = 权重大致量 + KV Cache + 激活中间结果 + 框架本身的开销。KV Cache 随 batch 数与上下文长度线性增长，长对话场景往往比权重还大。所以「能加载」和「能服务多少并发」是两件事，容量规划一定要把 KV Cache 算进去。

INT8 量化一定会掉多少精度？

没有固定数字。它取决于权重分布是否集中、有没有做逐通道/逐组缩放、是否保留了敏感层（如归一化层、嵌入层、输出头）的高精度、以及下游任务对误差的敏感程度。多数 8bit 方案在通用任务上损失很小，而 4bit 以下对某些推理类任务影响明显，必须实测。

GGUF 和 safetensors 是竞争关系吗？

不是，它们解决不同层面的问题：safetensors 是「安全的权重容器」，GGUF 是「面向本地推理的一体化封装 + 量化体系」。同一个模型常常先有 safetensors 版本，再被转换成带不同量化等级的 GGUF 供 llama.cpp 使用。

转 ONNX 失败了怎么办？

先定位是哪个算子不支持：① 用最新版转换工具与运行时，很多算子支持是逐步补齐的；② 对不支持的部分写自定义算子或用已有算子改写；③ 把模型按结构的天然边界切分成多个子图导出。实在转不动就把 torchScript/原框架推理作为 fallback，或改用厂商直接提供的适配版本。
