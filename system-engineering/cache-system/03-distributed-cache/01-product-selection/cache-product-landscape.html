一、五个生态位，一次看清

生态位代表产品核心取舍什么时候选它
通用内存缓存（Redis 系）Redis、Valkey、KeyDB、Dragonfly数据结构丰富、生态成熟；内存成本随数据量线性上涨默认选择。需要 Hash/ZSet/Stream、需要持久化和高可用时
纯 KV 多线程Memcached简单、多线程吞吐高、Slab 分配避免碎片；仅支持字符串 value，无持久化value 都小于 1 MB、只做 get/set、追求极致简单与多核利用
应用内内存网格Hazelcast、Apache Ignite与应用同进程，可近端计算；运维与语言绑定较深JVM 技术栈、需要分布式数据结构或计算下推
磁盘型 Redis 兼容Pika、Kvrocks、Tendis用 SSD 换内存成本，容量可到 TB 级；延迟高于纯内存数据量大但不那么热，纯内存成本扛不住
云托管云厂商 Redis / 兼容服务免运维、弹性扩缩、自带监控；有厂商绑定与版本滞后团队没有专职运维，或流量波动大需要弹性

⚠️ 上面每个产品的线程模型、许可协议、版本能力差异很大且变化很快（例如 Redis 生态在 2024 年出现过许可变更并催生了社区分支）。 选型前请务必用你准备部署的具体版本官方文档核对，不要依据二手文章做决定。

二、Redis 系内部怎么选

维度RedisValkey / KeyDB 等多线程分支Dragonfly
命令模型主流版本单线程执行命令（6.0 后网络 IO 多线程）多线程执行，命令语义基本兼容多线程，主打单节点高吞吐
选型理由生态最全、文档最多、云厂商支持最好想在单机上吃满多核想用更少节点扛更高 QPS
风险单线程下大 key / 复杂命令会阻塞分支版本与主线能力可能有差异生态与运维工具链相对薄

单线程不是缺点而是设计取舍：命令天然原子、实现简单、无锁竞争。 真正的问题是"一个慢命令会堵住后面所有命令"——所以大 key、KEYS *、大范围 ZRANGE 才是生产事故源头，而不是单线程本身。

三、按场景直接给答案

Q：只做简单的对象缓存，value 都是 JSON 字符串，选谁？
A：两者都行。需要持久化、高可用、丰富数据结构就 Redis；追求极简部署和多线程吞吐、且能接受重启即失忆，Memcached 也完全够用。
Q：数据量 500 GB，纯内存成本太高怎么办？
A：三条路——① 冷热分离，只把热数据放内存，冷数据直接查库；② 上磁盘型兼容产品（Pika/Kvrocks/Tendis）；③ 重新审视是不是缓存了不该缓存的东西（见「收益与代价」里 key 基数过大的反例）。
Q：要不要上云托管？
A：看运维能力。自建意味着你要负责扩缩容、备份、故障转移、版本升级、监控告警全套。团队没有专职运维时，云托管的总成本通常更低。
Q：能不能同时用 Redis 和 Memcached？
A：可以但很少有必要。多一个组件就多一套监控与故障模式，除非有明确的测量数据证明拆分带来收益，否则不要为了"用上不同工具"而堆组件。

四、选型时的三个反模式

  • 按"名气"选型——因为大厂在用所以用，但你的场景其实是纯 KV，Memcached 更简单。
  • 按"功能丰富度"选型——选了功能最全的产品，结果只用 get/set，却要为它的内存占用和运维复杂度买单。
  • 忽略退出成本——用了某个产品的私有特性（特定命令、特定模块），将来想迁移时发现改不动。优先用标准命令集。

分片与扩缩容的底层原理见 一致性哈希、虚拟节点与哈希槽对比； Redis 本身的集群、持久化与内存细节见 NoSQL 数据库 / Redis 子学科。

五类缓存产品定位图

选型一句话：热点 + 可容忍短暂不一致 → Caffeine；共享 + 需要丰富结构 → Redis；超大吞吐纯 KV → Memcached；需要在数据侧做计算 → Hazelcast。绝大多数业务是 Caffeine（L1）+ Redis（L2） 两层。

W-TinyLFU 为什么命中率高：它把缓存分成窗口区（Window，约 1%）和主区（Main，约 99%）。新来的 key 先进入窗口区用 LRU 淘汰，只有被证明“够热”的才能晋升进主区；主区用 TinyLFU（一种极省内存的频率草图，每个 key 只占几 bit）按频率淘汰。这个设计同时解决了 LRU 的“突发流量污染”和 LFU 的“新热点爬不上来”两个老问题。

Caffeine 生产配置

// Caffeine 生产配置（Java）
Cache<String, Object> cache = Caffeine.newBuilder()
    .maximumSize(100_000)                    // 按条数（推荐，比按权重快）
    .expireAfterWrite(60, TimeUnit.SECONDS)  // 写后 60s 过期
    .refreshAfterWrite(30, TimeUnit.SECONDS) // 关键：30s 后异步刷新，避免阻塞读
    .recordStats()                           // 开启统计，必开
    .build();

// 异步刷新：命中时若已过 refresh 期，返回旧值 + 后台加载新值
// 对比 expireAfterWrite 到期后同步加载（会阻塞请求）—— 这是防击穿的关键手段
LoadingCache<String, User> users = Caffeine.newBuilder()
    .maximumSize(10_000)
    .refreshAfterWrite(1, TimeUnit.MINUTES)
    .build(key -> queryUserFromDB(key));     // 自动回填

// 看命中率（必须监控）
System.out.println(cache.stats());
// CacheStats{hitCount=95234, missCount=4766,
//            loadSuccessCount=4766, totalLoadTime=1234567890,
//            evictionCount=1200, evictionWeight=1200}
// hitRate = 95234/100000 = 95.2%

// 与 Redis 组成二级缓存
Object v = localCache.get(k, key -> {
    String s = redis.get(key);               // L1 miss -> 查 L2
    if (s == null) { s = db.query(key); redis.setex(key, 3600, s); }
    return s;
});

二级缓存架构与一致性处理

L1（本地）+ L2（Redis） 是标准组合：L1 挡掉绝大部分重复读，L2 保证多实例间共享与相对一致。

问题现象解法
L1 数据过期A 实例改了数据，B 实例本地还是旧的L1 TTL 设短（10 – 60 s）+ 变更时广播失效
广播风暴大量 key 变更导致消息刷屏批量合并失效消息；只对热点 key 广播
缓存不一致窗口Redis 已更新，L1 未失效接受（业务上通常允许秒级）；关键数据不走 L1
冷启动雪崩实例重启后 L1 全空预热：启动时加载 Top-N 热点

L1 失效广播实现

# 用 Redis 发布订阅广播 L1 失效事件
# ① 变更方：更新 Redis 后发一条失效消息
redis.set(key, new_val)
redis.publish("cache:invalidate", json.dumps({"keys": [key]}))

# ② 各实例订阅并在本地删除
pubsub = redis.pubsub()
pubsub.subscribe("cache:invalidate")
for msg in pubsub.listen():
    if msg["type"] == "message":
        for k in json.loads(msg["data"])["keys"]:
            local_cache.invalidate(k)     # 只删本地，下次读自动回填

# ③ Redis 6.0+ 的更优方案：客户端缓存（tracking）
#    服务端主动通知失效，无需自己搭 pubsub
redis-cli CLIENT TRACKING ON REDIRECT 1234    # 1234 是另一个连接 ID
# 注意：这是「服务端辅助的失效通知」，仍需客户端实现缓存逻辑

深入自检

有了 Redis 为什么还要本地缓存？

两个不可替代的价值：① 延迟——本地 1 μs vs Redis 0.5 ms，差 500 倍；② 削峰——极热 key（如顶流明星主页）每秒几十万次读，全打 Redis 会把单分片打爆（Redis 单分片约 10 万 QPS，且热 key 无法分散到多分片）。本地缓存在每个实例各存一份，N 个实例就把 Redis 压力降为 1/N。

本地缓存会不会导致实例间数据不一致？

会，这是它的固有代价。控制手段：① TTL 短（10 – 60 s），把不一致窗口压到秒级；② 广播失效（Redis pubsub 或 Redis 6 tracking）做到准实时；③ 关键数据不走 L1——余额、库存这类强一致数据只允许走 DB 或 Redis。判断标准是：不一致窗口内会不会造成业务损失。

Hazelcast 这类内存网格什么时候用？

当你需要把计算下推到数据所在节点时——比如对缓存中的大量数据做聚合、或者需要分布式数据结构（分布式 Map/Queue/Lock）且不想单独部署 Redis。典型场景是有状态的流式处理、会话集群。代价是运维复杂度明显高于 Redis，且生态小。一般业务不要为了“听起来高级”而引入。

缓存产品迁移怎么做到不停机？

标准四步：① 双写（同时写新旧两套，读仍走旧）；② 双读 + 比对（读旧，异步比对新旧一致性，观察 1 – 2 天）；③ 灰度切读（按 1% → 10% → 100% 逐步把读切到新）；④ 停写旧并观察后下线。全程旧系统保持可回滚。关键是第 ② 步的一致性比对——没有它就不要切，否则线上数据不一致很难察觉。
