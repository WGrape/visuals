耗时从哪来：一次查询算几次

向量检索的单次查询耗时，核心来自"要和多少个候选向量做距离计算"：

单查耗时 ≈ 候选数 × 向量维度 × 每次距离的计算量
  • 暴力（FLAT）：候选数 = 全量 N，必须和每一行都算一次距离。N 越大越慢，线性增长。
  • ANN（如 HNSW）：靠索引跳过绝大多数向量，候选数 ≈ O(log N)，只访问图上少数节点。

假设维度 d=768，单次内积约 768 次乘加。下面给出不同数量级下的实测量级估计（CPU 单线程粗略、用于建立直觉，非精确 benchmark）。

维度的影响

耗时与维度 d 成正比。从 384 → 768 → 1536，单次距离计算量翻倍再翻倍：

维度 d相对计算量对 FLAT对 ANN
3841×快一半略快
7682×基准基准
15364×慢约 4 倍访问节点数略增，整体约 2–3×
高维还会带来"维度灾难"：距离分布趋同，暴力意义下降，ANN 索引也更难建。能用 768 就别盲目上 1536，除非精度确实不够。

内存才是真正的瓶颈

耗时之外，内存往往先爆。float32 每维 4 字节：

内存 = N × d × 4 字节（未压缩，HNSW 还要额外存图边）
数据量768d float32PQ 压缩后(~1/32)
100 万~3 GB~0.1 GB
1000 万~30 GB~1 GB
1 亿~300 GB ❌~10 GB

HNSW 因为是图结构，还要额外存邻居边（约 N×M×4 字节，M 通常 16~64），实际内存比裸向量还大。所以亿级数据几乎必须用 IVF-PQ / 磁盘索引（DiskANN）/ 分布式。

工程经验数据（量级参考）

  • Faiss HNSW，100 万 × 768d：单查 ~1–2 ms，单线程可达数千 QPS；efSearch=64~128 时召回@10 约 95–99%。
  • 内存够时：HNSW 是"又快又准"的默认选择，直到内存放不下。
  • 千万~亿级：IVF-PQ（nprobe 调召回）或 Milvus/Weaviate 的分布式分片；单分片控制在千万级以内。
  • 批量检索（batch）：一次查 100 个 query 比单个查 100 次快数倍（向量化 + 更好利用缓存）。

结论速记

  • 暴力扫描耗时 ∝ N × d；ANN 耗时 ∝ log(N) × d。数据量越大，ANN 优势越夸张。
  • 维度翻倍 → 耗时翻倍；别无脑上高维。
  • 真正卡住你的是内存：亿级必须量化 / 磁盘 / 分片。
  • 选型顺序：小数据用 FLAT 保准确；中大数据 HNSW；超大数据 IVF-PQ/DiskANN。详见《向量索引选型指南》。

一次向量查询的时间都花在哪

要优化延迟，先得知道它在哪。一次「输入一句话，返回最相关的十条」的完整耗时大致是这样分布的：

先给每一段打点计时，再决定优化哪一段
端到端拆解：Embedding 与重排经常是更大的那一块

ANN 的永恒三角：召回率 / 延迟 / 内存

任何近似索引都是在三个目标之间做交换，你只能同时满足其中两项：

要高召回 + 低延迟就得把完整、不压缩的索引常驻内存，成本高。
要低延迟 + 省内存就得接受压缩带来的召回损失。
要高召回 + 省内存就得允许更多计算，延迟上升。
唯一的免费午餐是减少数据量或维度 —— 这两项降下来，三者同时变好。

因此优化的第一步永远是「能不能少一点」，而不是「怎么搜更快」：减少向量维度（很多 embedding 模型支持截断到 384 或 768 维而损失很小）、清理无效数据、把冷数据归档。

主流索引的三个旋钮

索引关键参数含义调大/调小会怎样

三条实用结论：

  1. HNSW 的内存开销常常被低估。除了每个向量的 d×4 字节，还要加上多层图的边（每个节点约 M×2 条邻接），通常整体比原始向量还大。百万级 1536 维向量轻松吃掉十几个 GB。
  2. efSearch 是唯一值得在线反复调的旋钮。构建参数一旦定型就改不了（除非重建），而 efSearch 可以每个请求传不同的值 —— 这就为「重要请求用高精度、普通请求用低精度」留出了空间。
  3. 量化后通常要做一次「精排」。常见的 IVF-PQ 组合会先用量化向量粗召回一大批，再对头部候选用完整精度重算距离，在省内存的同时把召回损失补回来。

把延迟压下来的七件事

① 先打点给每一段计时，别盲目优化。
② 降维度1536 → 768 或 384，常常几乎无感地省一半。
③ 过滤上移强过滤条件做成分区，避免候选被大量丢弃。
④ 批量请求把多个查询合成一个 batch，摊薄开销。
⑤ 就近部署Embedding 服务与向量库尽量同机房，避免网络叠加。
⑥ 预热 intindex冷启动时索引从磁盘加载会产生长尾延迟。
⑦ 缓存高频 query 的结果与 embedding 都可缓存。

关于 mmap 的一个真实陷阱：很多向量库支持把索引放在磁盘上用内存映射访问。它看起来很美（省内存），但当内存不足以放下热数据时，每次缺页都要读盘，延迟会出现非常长的尾 —— 表现就是 p50 很好看而 p99 灾难。判断是否能在 SSD 上跑的关键是看 p99，而不是平均值。

深入自检

为什么我的 p99 比 p50 慢十倍？

常见原因有三：① 冷启动/缺页 —— 索引或部分数据还没进内存；② 请求倾陡 —— 某些查询的候选特别多（比如带低效过滤条件）；③ 并发排队 —— 高峰期算力饱和导致排队时间暴涨。分别对应三种解法：预热、优化过滤、限流或扩容。只看平均值会完全看不见这些问题。

量化一定能加速吗？

不一定。它主要降低内存占用与内存带宽压力，这在向量数量大、索引无法完全常驻内存时会明显加快（少了很多缺页）；但如果索引本来就全部躺在内存里、且计算单元是瓶颈，那么每次距离计算要多一步解码，可能反而变慢。要不要量化，取决于你的瓶颈是带宽还是算力。

HNSW 构建很慢怎么办？

它的构建复杂度不低，efConstruction 与 M 越大越慢。可以：① 构建期适当降低这两个参数，再用稍大的 efSearch 补偿；② 分批构建；③ 降低维度；④ 先聚类（IVF）再在每簇内建小图，即「分而治之」的混合结构。多数库已经提供这类混合索引。

多少数据量需要考虑分片？

粗略地说：单机内存放得下、单核 CPU 能撑住目标 QPS 就不用分。一旦索引内存超过单机合理配比（比如超过可用内存的六到七成）或单节点 QPS 扛不住，就该横向分片。分片后每个请求要查所有分屑片再合并，因此分片数也不是越多越好 —— 同样要在并行收益与扇出成本之间取平衡。
