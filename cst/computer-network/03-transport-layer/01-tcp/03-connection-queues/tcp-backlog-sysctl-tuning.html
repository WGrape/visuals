上一页讲了半连接队列、全连接队列和 backlog 在握手里的位置。这一页把它落成可执行的调优：三个内核参数、怎么观测溢出、以及 SYN Flood 的防御清单。

01三个关键参数

参数默认值（典型）控制什么
net.core.somaxconn128全连接队列（accept 队列）上限，很多发行版偏小
net.ipv4.tcp_max_syn_backlog1024半连接队列上限，SYN Flood 时首先被打满
net.ipv4.tcp_syncookies1（开）队列满时回 SYN Cookie，不占内存建半连接
要点：隐藏坑：应用层 listen(backlog) 的实际生效值是 min(应用 backlog, somaxconn)。Nginx/Go 配了 1024 但 somaxconn 还是 128，队列照样只有 128。

02怎么观测队列溢出

用 ss 看监听套接字的 Recv-Q（全连接队列当前长度）和 Send-Q（队列上限），再用内核计数确认是否发生过溢出。

ss -lnt 'sport = :80'
# Recv-Q 持续贴近 Send-Q  -> 全连接队列满

# 半连接队列溢出计数（SYN 被丢）
netstat -s | grep 'SYNs to listened'
# 或
nstat -az TcpExtListenOverflows TcpExtListenDrops

03SYN Flood 防御清单

  • 开 SYN Cookie：net.ipv4.tcp_syncookies=1，队列满也能验证握手，不建半连接。
  • 调大半连接/全连接队列：tcp_max_syn_backlog 与 somaxconn 一起调，且应用 listen backlog 不低于 somaxconn。
  • 限速与过滤：边缘对单一源 IP 的新建连接限速；云厂商开 DDoS/CC 防护。
  • 应用层兜底：对新建连接做令牌桶限流、要求廉价校验（如 TLS 之前先过 CDN）。

04应用层怎么配合

# Nginx：listen 显式给 backlog
listen 80 default_server backlog=1024;

# Go http.Server：新建连接超时
# http.Server{ ReadTimeout: 5*time.Second,
#             ReadHeaderTimeout: 2*time.Second }

# 系统级生效
sysctl -w net.core.somaxconn=4096
 sysctl -w net.ipv4.tcp_max_syn_backlog=8192
问：为什么调了 somaxconn 还是排队？

因为还要看应用 listen 的 backlog 和它取 min；另外全连接队列满时，内核会直接丢弃新来的 ACK，客户端表现为连接超时而非拒绝，排障时要同时看 Recv-Q 和 ListenOverflows。
