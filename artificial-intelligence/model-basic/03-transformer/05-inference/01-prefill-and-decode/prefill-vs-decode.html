05 · 推理

Prefill 与 Decode：同一模型里两种完全不同的负载

所有推理优化都建立在「prefill 算力密集、decode 带宽密集」这个区分上。分不清这两段，就会拿连续批处理去治 TTFT、拿量化去治长 prompt，优化方向全错。

一句话定位：一段并行吃 prompt，一段串行吐 token

prefill 把整段 prompt 一次性前向，所有位置并行算，是标准的大矩阵乘；decode 每次只算一个新 token，要读一遍全部权重但只做一次向量乘。前者算力瓶颈，后者带宽瓶颈。

瓶颈prefill：FLOPS；decode：显存带宽
并行度prefill 沿序列维并行；decode 只有一个位置（靠 batch 并行）
MFU 量级prefill 40%~60%；decode 常低于 5%
优化手段prefill：FlashAttention / chunked prefill；decode：量化 / 批处理 / 投机解码
同样的模型、同样的权重，两段负载的硬件画像完全不同

算一遍：为什么 decode 上限就是「带宽 ÷ 权重」

单请求 decode 上限（tok/s） ≈ 有效带宽 ÷ 权重字节数
硬件 / 模型权重（bf16）有效带宽理论 tok/s实测（约）

这条公式解释了三个现象

① 量化能直接提速 decode（读的字节少了）；② batch 变大时吞吐线性涨但 TPOT 基本不变（权重只读一次，摊给多个请求）；③ 端侧出词速度天然低，因为内存带宽只有服务器的几十分之一。

批处理：唯一能让 decode 变「划算」的手段

单请求 decode 时，GPU 的算力单元 95% 在等内存。把 32 个请求拼成一个 batch，权重只读一遍、算 32 个 token，算力利用率立刻上来，吞吐接近 ×32，而 TPOT 只小幅上升。

技术解决什么代价典型收益
Static batching把固定数量的请求拼批短请求要等长请求，尾延迟高吞吐 ×8~16
Continuous batching每步动态进出请求（iteration-level）调度与 KV 管理复杂吞吐 ×2~4（相对静态）
PagedAttention按块分配 KV，消除碎片与预留需要块表管理显存利用率 +20%~40%
Chunked prefill把长 prompt 切成块，与 decode 混跑TTFT 略升长 prompt 时 TPOT 抖动大幅下降
Prefix caching相同前缀的 KV 复用命中率依赖场景系统提示词类场景 TTFT −50%+

排障：从 TTFT / TPOT 反推瓶颈

症状最可能原因下一步
TTFT 高、TPOT 正常排队（并发满）或 prefill 被打断看排队时长；开 chunked prefill
TTFT 正常、TPOT 抖动KV Cache 不足触发抢占/换页开 PagedAttention；降并发或降 batch
TTFT 和 TPOT 都高模型太大 / 量化没开 / 带宽被其他进程占先量化到 fp8/4bit，再测
吞吐上不去但 GPU 利用率低batch 太小，调度没拼满调大 max_num_seqs，检查调度器
长 prompt 一来整个服务卡住prefill 独占算力，挤掉 decodechunked prefill + prefill/decode 分离部署

原理与取舍：为什么不能「让 decode 也并行」

decode 的第 t+1 个 token 依赖第 t 个的输出，天然串行——这是自回归的定义。想打破它只有两条路：投机解码（小模型先猜几个、大模型一次验证）和并行解码（一次出多个位置再修正），前者是不改变分布的严格加速，后者是有损的。这也是为什么投机解码在延迟敏感场景特别受欢迎。

prefill 能不能也用 PagedAttention？

能，KV 的块分配对 prefill 同样适用；PagedAttention 本身不区分阶段，只是 decode 阶段收益最明显。

为什么 decode 的 MFU 这么低还不换硬件？

瓶颈是带宽不是算力，换更快的 HBM 才有效（H100 的 HBM3 比 A100 高 60%+）。用算力更强的卡（如纯 FP8 峰值高的卡）对 decode 帮助有限。

端侧为什么没有 continuous batching？

手机通常只有一个前台请求，batch=1，所以端侧的优化重点是「少读字节」（量化、稀疏、共享）而不是「拼批」。

算一遍：两个阶段的瓶颈为什么完全不同

Prefill 和 Decode 做的是同一套矩阵运算，但形状完全不同：Prefill 一次算 [batch, prompt_len, hidden]，是矩阵乘矩阵（计算密集）；Decode 每次只算 [batch, 1, hidden]，是矩阵乘向量（访存密集）。这就是必须分开优化的根本原因。

维度PrefillDecode工程含义
输入形状整段 prompt 一起算每步只算 1 个 tokenPrefill 可并行，Decode 只能串行推进
瓶颈算力（FLOPS）显存带宽（GB/s）Prefill 看 GPU 算力，Decode 看 HBM 带宽
主要开销QKV 投影 + FFN 的 GEMM反复读取 KV Cache + 权重Decode 每步都要把权重读一遍
关键指标TTFT（首 token 延迟）TPOT（每 token 延迟）、吞吐交互式场景看 TTFT，批处理看吞吐
批处理效果批量大反而更慢（总量变大）批量越大单 token 成本越低连续批处理（continuous batching）专门解决这个
典型量级几百 ms ~ 数秒（长 prompt）每 token 10~50 ms两者优化手段互不通用

量化一个直觉：一个 7B 模型用 FP16 存储约需 14 GB 显存放权重。Decode 每生成一个 token 都要把这 14 GB 读一遍 —— 在 2 TB/s 的 HBM 带宽下，理论下限约 7 ms/token。这就是为什么单请求 Decode 几乎无法更快，唯一的出路是批处理：一次读权重同时服务几十个请求。

所有推理优化里，优先级最高的两项是连续批处理与 KV Cache 复用：前者把 Decode 的权重读取成本摊到多个请求，后者直接省掉重复的 Prefill。量化（FP8/INT8）虽然能省带宽，但会牺牲精度，通常放在这两项之后。

上线前逐条核对：

  • TTFT 与 TPOT 必须分开监控：混在一起看平均值会掩盖真实问题。
  • 并发上不去先看 KV Cache 显存，而不是先怀疑算力。
  • Prefill 长、Decode 短的场景（长文档问答）与反之的场景（短问长答）要分开调优。
  • 系统提示词固定时一定要开 prefix caching，收益几乎白拿。
  • 批处理不是越大越好：批太大 TTFT 会显著变差，要按 SLO 反推上限。
  • Decode 的理论下限是带宽决定的：算一遍「权重字节 ÷ HBM 带宽」就知道还能不能更快。
  • 量化前先确认精度是否有评估集，否则只是把问题从慢变成错。
  • 流式输出要区分 ITL（token 间延迟）与总耗时，用户感知的是流畅度不是总时长。
  • 压测必须用真实长度分布：用 100 token 的 prompt 测出来的结论对长文本无效。
