优化器：是什么、为什么、实现原理

优化器在 SQL 执行链路中的定位（解析器与执行器之间）；为什么非它不可（声明式语言、等价计划爆炸、代价差异巨大）；CBO 三大支柱——统计信息、代价模型（8.0 默认代价常数）、搜索策略（贪心剪枝与 Hypergraph）。

 📄

优化器：完整工作过程

从解析、预处理、逻辑优化（子查询扁平化/谓词下推/等值推导）、物理优化（访问路径/JOIN 顺序与算法/代价估算）、计划改进，到生成 AccessPath 执行计划树交给火山迭代器执行的七阶段全流水线，含 EXPLAIN 与 optimizer_trace 观测方法。

 📄

EXPLAIN 详解：它不是优化器，是报告单

厘清核心误解——EXPLAIN 不是优化器本身，而是读取并展示优化器已生成计划的诊断命令；讲清普通 EXPLAIN（不执行）/ EXPLAIN ANALYZE（8.0.18+ 真执行）/ FORMAT 三种输出，逐列解读 12 个字段，重点拆解 type 访问类型天梯与 Extra 信号，并区分 EXPLAIN 与 optimizer_trace 的 what / why 定位。
🧠

执行器：输入是执行计划，输出是结果集

执行器的输入输出边界：输入是优化器生成的 AccessPath 计划树（而非 EXPLAIN 表格），输出是逐行结果集或 DML 影响行数；AccessPath 如何一一编译成 RowIterator 树，Init/Read/UnlockRow/SetNullRowFlag 统一接口，火山拉取模型下控制流向下问、数据流向上冒的逐行执行过程，TableScan/Ref/NestedLoop/Sorting/Materialize 等常见迭代器清单，以及与老执行器六套抽象（QUICK_SELECT_I、READ_RECORD、QEP_TAB 等）的对比；附 EXPLAIN FORMAT=TREE 与 EXPLAIN ANALYZE 观察方法。
