⚡ 执行流程
1
🎯 线程启动
用户代码创建 Thread 对象，调用 start() 方法，线程进入就绪状态
2
📋 OS 调度
操作系统决定哪个线程获得 CPU 时间片，线程进入运行状态
3
🔒 获取 GIL
线程尝试获取 GIL 锁，只有持有 GIL 的线程才能执行 Python 字节码
4
💻 执行字节码
在线程内部，Python 虚拟机执行字节码指令序列
5
⏰ GIL 释放
每执行一定数量字节码或遇到 I/O 操作时，GIL 被释放
6
🔄 循环切换
其他等待中的线程获得 GIL，继续执行，形成"伪并发"
⚠️
CPU 密集型瓶颈
由于 GIL 限制，多线程对 CPU 密集型任务几乎没有加速效果，反而因为线程切换开销而变慢
✅
I/O 密集型优势
对于网络请求、文件读写等 I/O 等待操作，线程可在等待期间释放 GIL，让其他线程工作
🔄
线程切换机制
每 100 个字节码指令（可配置），Python 会自动切换线程，也可在 I/O 操作时切换
🛡️
线程安全保证
GIL 天然保证了 Python 对象引用的线程安全性，但需注意用户自定义的锁和共享资源

GIL：理解 Python 并发的起点

全局解释器锁（GIL）是 CPython 里的一把互斥锁：同一时刻只有一个线程能执行 Python 字节码。这一条约束决定了 Python 并发的全部取舍。

GIL 的持有与释放
GIL 是解释器级不是语言规范，其它实现（Jython 等）没有。
保证对象安全简化引用计数与内存管理的实现。
I/O 时会释放所以 I/O 并发仍然有效。
CPU 密集需多进程绕过 GIL 的正道是多进程或 C 扩展。

三套并发工具怎么选

方案适用能否用多核代价
threadingI/O 密集（网络、磁盘）❌ 受 GIL 限制切换开销、需处理同步
multiprocessingCPU 密集（计算、图像处理）✅ 真正并行内存占用高、进程间通信成本
asyncio高并发 I/O（大量连接）❌ 单线程内并发需全链路 async，阻塞代码会卡住
concurrent.futures统一线程池/进程池接口取决于选哪种 Executor抽象层，内部仍是上面两者
C 扩展释放 GIL计算密集且不想多进程✅ 扩展内部可释放需要写 C 或用 numpy 这类库
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor # I/O 密集 → 线程池 with ThreadPoolExecutor(max_workers=20) as ex: results = list(ex.map(fetch, urls)) # CPU 密集 → 进程池 with ProcessPoolExecutor() as ex: results = list(ex.map(heavy_compute, data)) # 判据一句话： # 在等别人（网络/磁盘）→ 线程或协程 # 自己在算（循环/加密/图像）→ 进程

numpy / pandas 这类库为什么能并行？它们在底层 C 代码里主动释放了 GIL，因此单个调用内部可以使用多核。这也是科学计算场景不必强行上多进程的原因。

线程同步：锁、条件与队列

为什么需要锁

count += 1 是「读—改—写」三步，GIL 可能在中间切换。

import threading count = 0 lock = threading.Lock() def inc(): global count for _ in range(100000): with lock: # 加锁才安全 count += 1 ts = [threading.Thread(target=inc) for _ in range(4)] [t.start() for t in ts] [t.join() for t in ts] print(count) # 400000（不加锁会小于这个值）

注意：GIL 不保证复合操作的原子性，它只保证单条字节码不被打断。

优先用队列

queue.Queue 自带锁，是线程间传递数据最省心的方式。

from queue import Queue q = Queue(maxsize=100) def producer(): for i in range(10): q.put(i) # 满了会阻塞 def consumer(): while True: item = q.get() if item is None: break handle(item) q.task_done()

比手写锁 + 列表更少出错。

常见同步原语

  • Lock：互斥，最基本
  • RLock：同一线程可重入
  • Condition：等待某个条件成立
  • Event：一个线程通知其它线程
  • Semaphore：限制并发数量
  • Barrier：多个线程在某点汇合

深入自检

有了 GIL 是不是就不需要锁了？

不是。GIL 只保证单条字节码的执行不被打断，而 count += 1、list.append 之外的许多操作都是多步的。只要存在「读—改—写」或多个状态需要保持一致，就必须加锁。

为什么我的多线程程序比单线程还慢？

如果任务是 CPU 密集的，多线程不但无法并行，还要额外承担 GIL 切换与上下文切换的开销。这类任务应当改用多进程、或交给能在内部释放 GIL 的库（如 numpy）。

线程池开多大合适？

I/O 密集场景可以远大于 CPU 核数，常见经验是「并发请求数 × 每个请求的等待占比」，从 10~50 起调并结合压测；CPU 密集则接近核数即可。盲目加大只会增加内存与切换开销。

daemon 线程是什么？

设置为守护线程后，主程序退出时不会等待它结束，会被直接终止。适合日志上报、监控这类后台任务；但如果它在退出时做关键收尾（如写文件），就可能丢失，应显式 join。

asyncio 能替代线程吗？

在高并发 I/O 场景更合适：单线程内切换协程，没有线程的内存与切换成本。但它要求整条调用链都是 async，混入一个阻塞调用就会卡住整个循环。CPU 密集仍需多进程。
