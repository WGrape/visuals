概述

接口而非实现

database/sql 定义通用 SQL 接口，具体能力由驱动（如 go-sql-driver/mysql）提供；通过匿名导入注册驱动。

database/sql 内置连接池：SetMaxOpenConns / SetMaxIdleConns / SetConnMaxLifetime 控制池行为。
打开与驱动

匿名导入注册

sql.Open 仅校验参数不建连；真正建连延迟到首次使用；驱动通过 import _ 触发 init 注册到 sql.Register。

import (
    "database/sql"
    _ "github.com/go-sql-driver/mysql"
)
db, err := sql.Open("mysql", "user:pwd@/dbname")
db.SetMaxOpenConns(20)
err = db.Ping()  // 真正建立连接
查询

Scan 到变量

Query/QueryRow 取多行/单行；用 Scan 把列填进变量；注意 NULL 用 sql.NullString 等可空类型接。

var name string
err := db.QueryRow("SELECT name FROM u WHERE id=?", 1).Scan(&name)

rows, _ := db.Query("SELECT id,name FROM u")
for rows.Next() {
    var id int; var n string
    rows.Scan(&id, &n)
}
写入

Exec 改数据

INSERT/UPDATE/DELETE 用 Exec；LastInsertId、RowsAffected 取结果；参数占位符用 ?（具体看驱动）。

res, _ := db.Exec("INSERT INTO u(name) VALUES(?)", "Li")
id, _ := res.LastInsertId()
事务

Begin/Commit/Rollback

db.Begin 开事务，tx 上的操作在同一连接；成功 Commit，出错 Rollback；用 defer tx.Rollback() 兜底。

tx, _ := db.Begin()
defer tx.Rollback()
tx.Exec("UPDATE a SET ...")
tx.Exec("UPDATE b SET ...")
tx.Commit()

database/sql 的分层设计

标准库的 database/sql 不包含任何具体数据库实现，它只提供连接池与通用 API，真正干活的是第三方驱动。这个设计让切换数据库时业务代码几乎不用改。

database/sql 是接口与池，驱动负责具体协议
sql.DB 是池它不是单个连接，而是连接池的句柄。
全局复用sql.DB 应作为长期对象全局保存。
驱动单独引import _ "driver" 只注册不直接调用。
并发安全sql.DB 可被多个 goroutine 同时使用。

连接池四个参数怎么配

参数含义建议配错的后果
SetMaxOpenConns同时打开的最大连接数按数据库承受能力设，如 50~200太大压垮数据库；太小请求排队
SetMaxIdleConns空闲保留的连接数约为 MaxOpenConns 的 1/4太小频繁建连；太大浪费资源
SetConnMaxLifetime连接最长存活时间小于数据库/中间件的空闲超时，如 30 分钟太长会用到已被服务端关掉的连接
SetConnMaxIdleTime连接最长空闲时间几分钟到十几分钟太长占用无用连接
db, err := sql.Open("mysql", dsn) if err != nil { return err } // sql.Open 不会真正建连，必须 Ping 验证 ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second) defer cancel() if err := db.PingContext(ctx); err != nil { return err } db.SetMaxOpenConns(100) db.SetMaxIdleConns(25) db.SetConnMaxLifetime(30 * time.Minute) db.SetConnMaxIdleTime(10 * time.Minute) // 查看运行时状态 stats := db.Stats() log.Printf("inuse=%d idle=%d wait=%d", stats.InUse, stats.Idle, stats.WaitCount)

判断池是否不够用：看 db.Stats().WaitCount 与 WaitDuration。如果等待次数持续增长，说明并发超过了池容量，需要调大或优化慢查询。

查询的正确姿势与必踩的坑

Query 必须关 Rows

rows 用完必须 Close，否则连接一直被占用。

rows, err := db.QueryContext(ctx, q, args...) if err != nil { return err } defer rows.Close() // 必须！ for rows.Next() { var u User if err := rows.Scan(&u.ID, &u.Name); err != nil { return err } out = append(out, u) } // 循环结束后还要检查一次错误 if err := rows.Err(); err != nil { return err }

永远用参数化查询

拼接 SQL 就是注入漏洞。

// ❌ 拼接：注入风险 q := "SELECT * FROM users WHERE name = '" + name + "'" // ✅ 占位符：驱动负责转义 rows, err := db.QueryContext(ctx, "SELECT id, name FROM users WHERE name = ?", name) // PostgreSQL 占位符是 $1 $2，而非 ?

注意 NULL 与 Scan

  • 可能为 NULL 的列用 sql.NullString 等类型，或指针
  • Scan 的目标数量必须与列数一致
  • 时间字段需要 DSN 开启 parseTime
  • 查询单行用 QueryRow，注意处理 sql.ErrNoRows

事务：什么时候用，怎么写才不出错

tx, err := db.BeginTx(ctx, &sql.TxOptions{ Isolation: sql.LevelReadCommitted, ReadOnly: false, }) if err != nil { return err } // 关键：用 defer 保证任何路径都能回滚 defer func() { if p := recover(); p != nil { tx.Rollback() panic(p) } }() if _, err := tx.ExecContext(ctx, "UPDATE a SET x=? WHERE id=?", x, id); err != nil { tx.Rollback() return err } if _, err := tx.ExecContext(ctx, "UPDATE b SET y=? WHERE id=?", y, id); err != nil { tx.Rollback() return err } return tx.Commit() // 提交后事务结束，不能再使用
事务绑定一条连接期间独占，不要在事务里做慢操作
超时要用 ctxBeginTx + ExecContext 全链路带 ctx
回滚要幂等已提交或已回滚后再 Rollback 会返回错误，可忽略
别跨事务用连接tx 里只能用 tx 的方法，不能用 db
事务要短长事务会长时间占住连接并放大锁范围
错误后别再用出错后事务已不可用，直接回滚

深入自检

sql.Open 成功了就是连上了吗？

不是。sql.Open 只做参数校验与池的初始化，不会建立真实连接。要确认连通性必须调用 Ping 或 PingContext。这是新手最常踩的坑之一。

为什么服务跑一段时间后数据库报 too many connections？

常见原因有三个：rows 没有 Close 导致连接不释放；MaxOpenConns 设得比数据库上限还大；慢查询堆积导致连接被长期占用。先用 db.Stats() 看 InUse 与 WaitCount 定位。

QueryRow 查不到数据时会返回错误吗？

会，返回 sql.ErrNoRows。这是一个特殊的哨兵错误，应当显式判断并转换为业务上的「不存在」，而不是当作系统错误上报。

事务里能不能调 db.Query？

不能。事务绑定在一条具体连接上，用 db.Query 会走另一条连接，从而脱离事务。事务中所有操作都必须使用 tx 的方法。

连接池参数有万能值吗？

没有。它取决于数据库规格、查询耗时与并发量。经验起点是：MaxOpenConns 按数据库 CPU 与连接成本估算（常见几十到两百），MaxIdleConns 取其 1/4，ConnMaxLifetime 小于服务端空闲超时。最终以压测与监控为准。
