02宏内核：Linux 的选择

Linux 把一切放进内核态，换来最短调用路径：一次文件读不需要跨进程 IPC，直接函数调用。

优点

性能高（无 IPC 开销）、实现直接、调试方便（一个 gdb 看全部）。

缺点

稳定性风险（驱动 bug = 内核 panic）、内核体积大、内存占用高。

缓解手段

可加载模块（LKM）、eBPF、用户态驱动（FUSE、DPDK、io_uring）、KFENCE/KASAN 检测。

03微内核：把一切赶出内核

微内核只保留「无法放到用户态」的最小机制，其余（文件系统、驱动、网络）都变成用户态服务，通过 IPC 通信。

维度微内核表现代价
隔离性服务崩溃不影响内核—
安全性攻击面极小（seL4 经过形式化验证）—
性能每次服务调用要跨进程 IPCIPC 开销是主要瓶颈
实时性QNX 中断延迟微秒级、可预测需要精心设计优先级
微内核的性能痛点催生了 L4 家族的优化：把 IPC 做成同步的「寄存器直传」，减少拷贝。seL4 的 IPC 约 300 cycles，已接近函数调用量级。

04混合内核：Windows NT 与 XNU

纯粹的两端都不好用，现实中主流是混合：

Windows NT
微内核核心（调度/中断/同步）+ Executive（对象管理、内存、IO 管理器）+ HAL；图形子系统 win32k 放在内核态以降低延迟。
XNU (macOS)
Mach（任务/线程/VM/IPC）+ BSD（POSIX/FS/网络）+ IOKit（驱动），Mach 与 BSD 同处内核态。
混合内核的代价是边界模糊：一个内核态驱动/图形模块的漏洞，仍可提权到 ring0。这也是为什么 Windows 和 macOS 都在推用户态驱动框架（UMDF / DriverKit）。

05Linux 的模块化与可加载内核模块

Linux 虽是宏内核，但用 LKM 做到「按需加载」：

# 查看已加载模块
lsmod

# 查看模块信息与参数
modinfo nf_conntrack

# 加载/卸载
modprobe nf_conntrack
modprobe -r nf_conntrack

# 运行时改参数（在 /sys/module//parameters/）
sysctl net.netfilter.nf_conntrack_max
概念说明
insmod vs modprobe前者只加载指定 .ko；后者会解析依赖并加载整条链
/lib/modules/$(uname -r)/模块目录，与内核版本严格绑定
dkms内核升级后自动重编第三方模块（如 NVIDIA 驱动）
模块签名Secure Boot 下未签名模块会被拒绝加载

06eBPF：不编译内核也能扩展内核

eBPF 让用户态把一段经过验证器校验的字节码挂到内核钩子上（kprobe、tracepoint、XDP、cgroup），无需改内核源码、无需重启：

# 用 bpftrace 统计每个进程的 read() 次数
bpftrace -e 'tracepoint:syscalls:sys_enter_read { @[comm] = count(); }'

# 用 bpftool 看已加载的程序
bpftool prog list
钩子用途
kprobe/kretprobe内核函数入口/返回动态插桩
tracepoint内核预置静态探针（稳定 ABI）
XDP网卡驱动层收包，超高性能过滤/转发
cgroup按容器/进程组做策略
eBPF 是「宏内核的模块化补丁」：既不牺牲性能（JIT 后接近原生），又避免每次改动都重启内核。

08速记卡

宏内核

一切进 ring0，性能最高、隔离最弱。Linux。

微内核

只留调度+IPC+VM，隔离最强、IPC 最贵。QNX/seL4。

混合

折中；NT/XNU；图形常在 ring0。

Linux 模块化

LKM 按需加载，dkms 随内核重编。

eBPF

验证过的字节码挂内核钩子，不重启扩展内核。

判据

驱动崩了崩整机 = 宏内核特征。
