①四种导入方式怎么选

方式数据源语义适用
Routine LoadKafka（持续消费）常驻任务，准实时日志、行为流实时入仓
Stream LoadHTTP 推送（本地文件/程序）单次同步导入，返回即成功小批量、脚本导入、程序直写
Broker LoadHDFS / 对象存储异步批量，可重试大批量离线导入、历史数据回灌
INSERT INTO ... SELECT库内其他表 / 外部表同步执行ETL 加工、表间转换
每条导入都是一个「事务」：要么整批可见，要么整批不可见，不会出现部分可见。 这带来两个实践结论：① 批太小会导致事务过多、版本堆积、compaction 压力大； ② 批太大失败时回滚成本高。常见做法是攒批到「几十秒~几分钟的数据量」再提交—— 具体阈值按数据速率与压测结果定。
-- Routine Load：常驻消费 Kafka
CREATE ROUTINE LOAD db.job_orders ON orders
COLUMNS TERMINATED BY ","
PROPERTIES ("desired_concurrent_number"="3", "max_batch_interval"="30")
FROM KAFKA ("kafka_broker_list"="broker:9092", "kafka_topic"="orders");

-- 导入任务出问题时的排查顺序
SHOW ROUTINE LOAD;            -- 看状态与进度
SHOW ROUTINE LOAD FOR db.job_orders;   -- 看具体的错误行与原因

②JOIN 优化：Colocate 与 Runtime Filter

Colocate Join

两张表用相同的分桶列、相同的桶数、相同的副本分布时， 相同 key 的行一定落在同一台机器上，JOIN 可以本地完成，免去重分布。 这是大表 JOIN 大表最有效的优化。

Bucket Shuffle Join

只把右表按左表所在节点重分布，比全量重分布传输量小。 在无法 Colocate（分桶列不同）时的次优选择。

Broadcast Join

把小表广播到所有节点。右表很小的星型模型维表关联首选， 大表广播会打爆网络与内存。

Runtime Filter

大表 JOIN 小表时，先扫小表生成运行时过滤条件（bloom / min-max / in list） 下推到大表扫描，大幅减少读取量。星型模型的性能关键。

优化顺序： ① 先看执行计划确实用了哪种分布方式（EXPLAIN 里会显示）； ② 大表 JOIN 大表优先改造成 Colocate； ③ 星型模型确认 Runtime Filter 已生效（有时因类型不匹配或统计信息缺失而不下推）； ④ 最后才考虑调 session 变量或加 hint。

③查询调优的常见问题

现象可能原因排查
没有命中分区裁剪时间列上包了函数，或条件不是范围形式EXPLAIN 看扫描的分区数
没走物化视图维度或聚合函数与定义不匹配确认查询能否从物化视图上卷得到
COUNT(DISTINCT) 极慢高基数列精确去重改用 bitmap 或近似函数（接受误差时）
JOIN 慢且网络打满两表都做了全量重分布改 Colocate 或用 Broadcast
导入后查询变慢版本堆积、compaction 没跟上看 tablet 版本数与 compaction 状态
内存超限大结果集排序 / 大 JOIN / 广播了不该广播的表看 query profile 的内存峰值算子
不要照抄网上调优参数的数值。执行内存、并行度、compaction 线程这类参数 与集群规模、数据量、并发强相关，同一份参数在小集群上救命、在大集群上可能压垮节点。 先通过 profile 定位到具体算子，再有针对性地调。

④日常运维关注点

  1. 导入延迟：Routine Load 的 lag 是最直接的实时性指标，要有告警。
  2. Compaction 压力：写入过快会产生大量待合并版本，影响查询性能与磁盘占用。
  3. Tablet 分布均衡：节点扩容/下线后要重新均衡，否则出现热点节点。
  4. 存储增长：列存压缩比高但明细表仍会快速增长，配合分区做生命周期管理（冷热分层/过期删除）。
  5. 慢查询归档：定期收集慢查询，判断是该加物化视图、改模型，还是该拒绝这类查询。
Q：实时写入和查询性能冲突怎么办？
A：这是 OLAP 的固有矛盾——写入越实时，小文件与版本越多，查询越慢。 三种缓解：① 攒批，用几分钟延迟换更大的批次； ② 读写分离，查询走独立副本； ③ 分层——实时层存最近几小时用明细，历史层转成预聚合。 先明确业务能接受多少延迟，再定架构。
Q：该不该用 INSERT 逐行写？
A：不该。列存的写入路径是为批量设计的，逐行 INSERT 会产生大量小事务与版本， 迅速拖垮集群。应用侧应攒批后走 Stream Load，或写入 Kafka 由 Routine Load 消费。
