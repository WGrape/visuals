wrk：多线程、事件驱动的 HTTP 压测工具

wrk 用少量负载端线程配合事件通知管理多条连接；它的 -c 表示连接数，不是 ab 的并发请求数，更不是服务端业务处理位数。

工作方式：线程、连接、请求分开看

wrk 将连接分配给多个负载端线程，由事件驱动的 IO 循环发出请求并接收响应。-t 是压测机线程数，-c 是要保持的总连接数，-d 是持续时间。单条连接上的请求次数可以很多；连接数不等于整轮请求总量，也不保证服务端同一时刻处理了同样数量的请求。普通 wrk 用连接上的响应推动后续请求，并非精确的恒定到达率发生器。

为了可靠测量，要同时看压测机 CPU、端口、文件描述符、网络和目标监听队列；wrk 可能先触及客户端瓶颈。具体安装及默认值以官方 README与本机 wrk --help 为准。

命令：本机低负载教学示例

# 2 个负载端线程、10 条连接、持续 15 秒，附延迟分布
wrk -t2 -c10 -d15s --latency http://127.0.0.1:8100/ping

# 添加请求头，并设置请求超时
wrk -t2 -c10 -d15s --timeout 2s -H 'Accept: application/json' http://127.0.0.1:8100/ping

# 运行单独准备的 Lua 脚本（下一节为 request.lua 内容）
wrk -t2 -c10 -d15s -s request.lua http://127.0.0.1:8100/

命令只供已授权的本机示例服务阅读与复现；目录中并未提供或执行 request.lua。

重要参数速查

参数含义注意
-t N / --threads N压测机使用的线程数多开线程不保证更多有效吞吐；别当成服务端线程
-c N / --connections N总连接数与 ab 的请求并发定义不同；核对本机端口/FD 与服务端连接限制
-d 时长 / --duration 时长测试持续时间，如 15s、2m总请求数是运行结果而非此参数直接指定
--latency输出详细延迟统计与百分位结合错误和超时一起看，勿只挑成功样本
--timeout 时长响应超时阈值，如 2s与业务 SLO 的时间边界分开定义
-H '名称: 值' / --header加入请求头需与真实请求的缓存/认证语义一致
-s 文件 / --script 文件载入 LuaJIT 脚本，定制请求或处理结果每请求执行脚本逻辑可能限制压测端性能

Lua：让请求符合业务语义

例如本机示例接口支持以下路径时，可将这段内容保存为 request.lua，再使用上一节命令；静态设置可减少每请求动态计算的开销。

wrk.method = "GET"
wrk.path = "/ping?kind=demo"
wrk.headers["Accept"] = "application/json"

wrk 还提供 request()、response(status, headers, body) 等钩子，可构造动态请求或校验响应；启用逐请求处理会影响发生器上限，脚本的业务校验结果也应单独统计。详见 官方脚本接口。

输出怎么读

  • Latency 一行给平均值、标准差及最大值；--latency 增加百分位分布。Req/Sec 的线程统计与最终 Requests/sec 的总体速率不是同一个展示层次。
  • requests in ... 和 Requests/sec 反映工具完成量和平均速率，Transfer/sec 是传输速率；不能直接等同业务成功吞吐。
  • Socket errors: connect, read, write, timeout（有错误时）分别反映连接、读取、写入和超时问题；配合状态码与响应体核验业务成功条件。工具未内建你业务的成功规则。

结果要与端到端指标与服务端监控交叉验证，不要用连接数倒推 QPS 或硬件容量。

核心速览

一句话用多线程 + 事件驱动制造高并发 HTTP 负载的命令行压测工具
三个核心参数-c 并发连接数、-t 线程数、-d 持续时间
必须配合-s Lua 脚本，否则只能压 GET，无法模拟真实业务
输出看什么Requests/sec、Latency 分布、Socket errors
wrk 压测四步：定并发 -> 定时长 -> 造请求 -> 看分位

一、最常用的几条命令

# 基础：12 线程、400 连接、压 30 秒 wrk -t12 -c400 -d30s http://127.0.0.1:8080/api/order # 带 Header 与 POST body（用 Lua 脚本） wrk -t8 -c200 -d60s -s post.lua http://127.0.0.1:8080/api/order # 输出延迟分布（需要 --latency） wrk -t4 -c100 -d30s --latency http://127.0.0.1:8080/health # 参数直觉： # -t 线程数：通常等于 CPU 核数，wrk 每个线程管理一部分连接 # -c 连接数：真正决定并发压力，远大于 -t # -d 时长 ：太短测不出稳定态，建议 30s 起步，正式压测 5~10 分钟

二、Lua 脚本：让压测贴近真实

-- post.lua wrk.method = "POST" wrk.headers["Content-Type"] = "application/json" wrk.headers["Authorization"] = "Bearer test-token" local counter = 0 -- 每个请求前调用，用来生成不同的 body function request() counter = counter + 1 local body = string.format( '{"user_id":%d,"sku":"SKU-%d","num":1}', 100000 + (counter % 50000), -- 别只用同一个用户，避免全部命中缓存 counter % 1000 ) return wrk.format(nil, nil, nil, body) end -- 可选：每个请求后处理响应 function response(status, headers, body) if status ~= 200 then -- 统计异常，wrk 默认不区分业务错误 end end
最常见的三个错误用法

① 压测机和被测机在同一台机器：压测本身抢占 CPU，结果毫无意义；② 只压同一个 URL 同一个参数：全命中缓存，测出的是缓存性能不是系统性能；③ 并发数远小于系统容量：测出的延迟是「空闲系统延迟」，看不出排队。

三、结果怎么读

字段含义关注点
Requests/sec吞吐 QPS核心指标，但要结合延迟一起看
Latency 平均值平均延迟参考意义有限，容易被长尾拉偏
Latency P99 / 99%99 分位延迟真正要看的指标，对应用户体验
Latency Distribution延迟分布直方图看是否有明显的双峰（部分请求特别慢）
Socket errors连接/读/写/超时错误数只要非 0 就说明已经压过头了
Non-2xx responses业务错误wrk 默认不统计，需要用 Lua 脚本自己数

四、找到容量上限的递增压测法

# 阶梯加压，每次记录 QPS 与 P99 for c in 50 100 200 400 800 1600; do echo "=== c=$c" wrk -t8 -c$c -d60s --latency http://target/api | grep -E "Requests/sec|99%" done # 典型曲线： # c=50 QPS 4800 P99 12ms # c=200 QPS 18500 P99 25ms <- 线性增长区 # c=400 QPS 32000 P99 60ms <- 开始饱和 # c=800 QPS 33500 P99 210ms <- 吞吐不涨，延迟暴涨 = 到拐点了 # c=1600 QPS 31000 P99 900ms <- 过载，吞吐反而下降 结论：容量上限约 32000 QPS，最佳工作点在 200~400 并发之间

五、深入自检

-t 和 -c 到底什么关系？

-t 是 wrk 的工作线程数（通常设成 CPU 核数），-c 是总连接数，连接会被平均分给各线程。决定压力大小的是 -c，-t 只影响 wrk 自己能不能跑满。

为什么 QPS 上不去？

先看 wrk 自己是不是瓶颈：单机 wrk 一般能跑几万 QPS，如果被测机器 CPU 还很低但 QPS 不涨，很可能是压测机或网络先到上限，需要多台压测机。

wrk 和 ab、jmeter 怎么选？

wrk 单机性能最强、脚本灵活，适合纯 HTTP 接口压测；ab 最简单但不支持脚本和长连接场景；jmeter 功能全（支持复杂场景、图形化）但单机能力弱、资源占用高。

压测为什么要预热？

因为 JIT 编译、连接池建立、缓存预热、DNS 解析都需要时间。直接开始计时会把冷启动的慢请求算进去，导致结果偏低。建议先空跑 30 秒再正式计时。

延迟分布出现双峰说明什么？

通常意味着存在两类请求：命中缓存的（快）和回源的（慢），或者部分请求触发了 GC、锁等待、慢查询。双峰比单纯的 P99 高更值得深挖。

记住一句不看平均延迟，只看 P99
三参数-t 核数、-c 并发、-d 至少 30s
必须写脚本否则测的是缓存不是系统
找拐点阶梯加压，QPS 不涨即为上限
