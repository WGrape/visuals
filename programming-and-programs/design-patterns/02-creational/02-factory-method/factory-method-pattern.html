01 · 从问题出发

为什么会需要这个模式？

导出流程固定，但 PDF 与 CSV 的创建细节不同；每加一种格式就修改流程，分支会不断增长。

假设导出器已有 PDF、CSV 两种格式。下个月要接入 HTML，业务流程其实仍是“准备数据→导出→返回文件”。如果流程直接 new 具体导出器，每次加格式都要进入流程函数改条件，还可能忘记异常处理或日志。

😵 直接写会怎样

function exportReport(format, data):
  if format == "pdf": exporter = PdfExporter()
  else if format == "csv": exporter = CsvExporter()
  // 新增格式时继续改这里
  return exporter.export(data)

💡 关键转折

父类定义使用产品的流程和创建入口；子类只负责决定创建哪种具体产品。

将“哪个类被创建”的选择从通用流程里抽出去。每个具体创建者覆盖 createExporter，run 仍只面向 Exporter。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

interface Exporter { export(data) }
abstract class ExportCreator {
  abstract createExporter(): Exporter
  run(data) { return this.createExporter().export(data) }
}
class PdfCreator extends ExportCreator {
  createExporter() { return new PdfExporter() }
}

读代码时抓住三件事

  1. Exporter 是产品契约：run 只调用它承诺的方法。
  2. createExporter 是变化点：由子类决定产品类型。
  3. run 是不变骨架：日志、错误处理和返回方式可统一放这里。

换个业务场景，还能认出来吗？

UI 框架中的 DialogCreator 可以统一执行 show() 流程，WindowsDialogCreator 和 WebDialogCreator 分别创建原生或网页对话框。识别关键：创建者子类决定一种产品，后续流程只看产品接口。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

产品类型会增加，但创建后使用产品的流程稳定

三个具体场景

  • 报表导出扩展 PDF、CSV、HTML
  • 跨平台按钮创建后都执行 show
  • 插件为同一处理流程提供不同解析器

不适合或要小心

只有一个固定产品时直接构造更简单。与简单工厂相比，扩展点在创建者子类，而非一个不断变大的 switch。

产品固定且创建简单时，直接构造更清楚

最容易混淆的相邻模式

模式真正的区别
简单工厂通常在同一个函数用参数和 switch 选择具体类；新增产品会修改这个选择函数。
抽象工厂同时生产一整组相关产品；这里每次只通过一个工厂方法得到一种产品。

区分时问自己：变化的是一种产品的创建者，还是一整套相关产品？

落地前检查

  • 确认产品确实有稳定的共同接口。
  • 给新创建者做契约测试：所有产品都能执行 export(data)。
  • 如果只有固定一种产品，不要为消除一个 new 引入继承层次。

两道检验理解的小题

第一层 · 本质与识别信号

一句话本质：把「创建哪个对象」的决定权交给子类，调用方只依赖抽象接口。它解决的是「我要一个 Product，但具体是哪种 Product 得由别的因素决定」。

识别信号（出现任一就该考虑）说明
代码里出现 switch (type) { case A: new A(); ...}最典型的信号：创建逻辑随类型分支
构造一个对象需要先做一堆准备工作读配置、连资源、校验参数——这些不该散落在调用处
调用方不应该知道具体类名如插件、驱动、多实现切换
对象创建后还需要多步初始化才能用工厂能保证「拿到的就是可用状态」
单元测试需要替换真实对象工厂方法是注入 mock 的最自然切口
  • 与「简单工厂」的区别：简单工厂是一个 static 方法里写 switch（不是 GoF 23 种模式之一，只是惯用法）；工厂方法是定义一个创建接口，让子类决定——多了一层继承/多态。
  • 与「抽象工厂」的区别：工厂方法创建一种产品；抽象工厂创建一族产品。
  • 不要为了用而用：只有一种实现、且永远不会有第二种时，直接 new 最清晰。

第二层 · 骨架代码与量化对比

Go 实现

// —— Go 版：用函数式工厂替代继承（Go 没有继承，idiomatic 写法）——
type Product interface{ Do() string }

type ConcreteA struct{}
func (ConcreteA) Do() string { return "A" }

type ConcreteB struct{}
func (ConcreteB) Do() string { return "B" }

// 工厂方法：返回接口，隐藏具体类型
type Creator func(cfg Config) (Product, error)

func NewCreator(kind string) Creator {
    switch kind {
    case "a": return func(Config) (Product, error) { return ConcreteA{}, nil }
    case "b": return func(Config) (Product, error) { return ConcreteB{}, nil }
    default:  return nil       // 或返回错误，不要让调用方 nil panic
    }
}

// 调用方：完全不知道 ConcreteA/B 的存在
p, err := NewCreator(os.Getenv("KIND"))(cfg)

// —— 注册式工厂（插件场景，避免 switch 越来越长）——
var registry = map[string]Creator{}

func Register(kind string, c Creator) { registry[kind] = c }

// 各实现在自己的 init() 里自注册，新增实现【零改动】工厂代码
func init() { Register("a", func(Config) (Product, error) { return ConcreteA{}, nil }) }

func Create(kind string, cfg Config) (Product, error) {
    c, ok := registry[kind]
    if !ok { return nil, fmt.Errorf("unknown kind %q", kind) }
    return c(cfg)
}
维度直接 new简单工厂(static)工厂方法抽象工厂
新增一种产品改所有调用处改工厂方法（1 处）新增一个子类（0 处改动）新增一个族工厂
调用方知道具体类是否否否
符合开闭原则否部分是是
类的数量最少+1+N（每产品一个 Creator）+N（每族一个）
适用产品数1少量一种产品、多种实现一族产品

Go 里最常见的形式是「注册式工厂」：init() 里自注册到 map。它同时满足了开闭原则和「没有继承」的语言现实，是 Go 生态的标准做法（database/sql 的 driver 注册就是这个模式）。

第三层 · 常见误用与排查清单

  • 工厂类变成上帝类：一个工厂里塞了 20 个 createXxx，任何新增都要改它。解法：按族拆分，或改成注册式（各实现自注册）。
  • 工厂方法返回 nil 而不是错误：调用方拿到 nil 接口，一调用就 panic。必须返回 error，或者返回「空对象」（Null Object 模式）而不是 nil。
  • 过度设计：只有一种实现、且业务上确定不会有第二种，却硬套工厂。这是设计模式最常见的滥用——模式的价值在于应对变化，没有变化就没有价值。
  • 工厂里塞业务逻辑：工厂只负责创建。一旦开始在里面做校验、计算、甚至发消息，它就变成了隐藏的业务层，难测又难改。
  • 循环依赖：工厂需要知道所有具体类，而具体类又需要工厂（如自注册时）。Go 里通常用独立的 registry 包来打破（三方都不依赖对方）。
  • 并发安全：注册式工厂的 map 若在运行时被并发写入，需要加锁或改用 sync.Map。通常只在 init 阶段注册就不需要。
  • 测试时工厂难以替换：把工厂作为依赖注入（传 Creator 函数进去），而不是在业务代码里直接调全局工厂函数。

第四层 · 原理与取舍

工厂方法的本质是依赖倒置：高层模块不依赖低层模块的具体实现，双方都依赖抽象。它的收益和代价都来自于这层间接。

  • 收益：调用方与具体类解耦 → 新增实现不改调用方 → 可测试（注入 mock）→ 创建逻辑集中（初始化一致性有保障）。
  • 代价：类/函数数量增加（每个产品一个 Creator）、调用链多一层（调试要跳一次）、类型信息被隐藏（静态分析工具看不到具体实现，IDE 跳转会跳到接口）。
  • 性能影响：基本为零。多一次函数调用会被内联优化掉；返回接口会有一次装箱，但在绝大多数场景可忽略。不要以性能为由拒绝工厂，也不要指望它带来性能提升。
  • 判断该不该用的最终标准：问自己「这个创建逻辑，半年内会因为什么而变化？」如果答不上来，就别用。
工厂方法和抽象工厂怎么选？

看产品的维度。工厂方法是「一个产品接口，多个实现」——比如 Logger 接口有 FileLogger、KafkaLogger。抽象工厂是「一族相关产品，需要成套切换」——比如 UI 主题工厂同时产出 Button、Dialog、ScrollBar，且必须保证 Mac 系的三个组件一起用、Windows 系的三个一起用（不能混）。判断方法：如果各个产品可以独立选择实现，用工厂方法；如果必须成套、混用会出错，用抽象工厂。绝大多数业务场景是前者——这也是抽象工厂在实际项目中出现频率远低于工厂方法的原因。

Go 没有继承，还能算工厂方法吗？

算。模式的核心意图是「让创建延迟到可替换的实现」，不是「用继承实现」。Go 用「返回接口的函数」或「注册到 map 的构造函数」达到了完全相同的效果，而且因为不用继承，反而更灵活（函数是一等公民，可以直接传递和组合）。Go 标准库里到处是这个模式：sql.Open(driver, dsn) 通过注册的 driver 返回 *sql.DB；crypto 的 hash 注册；encoding 的 codec 注册。所以学设计模式要学意图，不要学 UML 图里的继承箭头——后者是 C++/Java 时代的实现细节。

什么时候工厂是反模式？

三种情况：① 只有一种实现且不会变——多一层间接只增加认知负担；② 工厂本身成为变化的热点——每次新增都要改工厂，违背了开闭原则的初衷（这时该换注册式或 DI 容器）；③ 用它来「隐藏」真正的问题——比如对象构造需要 15 个参数，用工厂包起来只是把问题藏起来，真正该做的是拆分对象或引入建造者模式。另外要警惕：如果工厂的作用是「根据环境变返回不同实现」，考虑用配置注入可能更直接——不是所有变化都必须用模式解决。
