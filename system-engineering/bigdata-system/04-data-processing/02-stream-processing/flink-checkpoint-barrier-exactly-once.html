Flink Checkpoint 手推：Barrier 对齐、状态恢复与端到端精确一次

沿双输入算子的两条数据流，解释快照记录什么、慢通道为什么拖住对齐，以及外部 Sink 的条件。

Checkpoint 要解决什么

流作业一直在处理事件：源的消费位置、窗口累计值、去重状态和定时器都在变化。若任务失败后只重启算子却不恢复这些状态，可能漏算或重复计算。Checkpoint 在某个逻辑时刻为算子状态和输入位置建立一致快照，失败后从同一快照恢复，并从对应位置继续消费。快照不是简单地“把内存复制一次”：多个并行算子之间还有飞行中的记录，必须确定哪些记录属于快照之前，哪些属于之后。

Barrier 是随数据流传播的快照边界标记。同一编号的 Barrier 经过源、算子和下游，帮助各算子记录同一个全局进度。Checkpoint 存在外部持久存储中，通常应与作业节点故障域分开；只放在易失本地盘上，节点故障后可能无法恢复。状态后端、增量快照和存储实现会影响耗时，但不改变一致边界的基本目的。

双输入对齐的四步

假设一个 JOIN 算子有左输入 A 和右输入 B。Checkpoint 7 的 Barrier 先从 A 到达，此时算子要避免继续把 A 上属于 Barrier 之后的记录混入快照前状态；它暂时阻塞 A，同时继续处理 B 中 Barrier 之前的记录。等 B 的 Barrier 7 也到达，算子对齐了两条输入，保存状态快照，再向下游发送 Barrier 7，恢复两侧正常处理。

慢通道或背压会让另一个 Barrier 迟迟不到，对齐期间缓冲增长、Checkpoint 时间变长。若 A 很快、B 很慢，不能只记录 A 的位置就宣布整个双输入状态一致。实际系统可使用非对齐 Checkpoint，把在途数据或缓冲也纳入快照，以减少背压下的对齐等待；代价是快照数据量和恢复工作可能增加。何时开启应以背压、存储带宽与恢复目标实测。

暂缓 A 的后续记录，继续处理 B 的旧记录。

B 收到 Barrier 7

两侧对齐，保存一致状态。

任务中途失败

从故障点恢复

Checkpoint 7 完成后，作业又处理了部分新事件，但在 Checkpoint 8 完成前失败。恢复时回到最近成功的 Checkpoint 7：状态回到当时的计数、窗口和定时器，源也回到对应消费位置，再重放后续事件。算子内部某些事件会重算，这是正常的；“精确一次”通常指最终受管理状态或结果的效果恰好一次，而不是每条代码路径只执行一遍。

如果源无法从保存的位置重放，恢复就可能漏数据；如果源的消费位置与状态不在同一一致快照里，恢复就可能重复或跳过。Kafka 等可重放源适合这一模型，但仍要设置保留时间足够覆盖最长故障与恢复窗口。恢复期间若消息已经过期，即使 Checkpoint 文件完好也无法完整重建。

组件快照或恢复要点常见误区
Source保存可重放位置数据保留不足会断档
双输入算子对齐 Barrier 或保存在途数据只看单侧位置不一致
状态后端持久化窗口和定时器本地易失副本不能抗节点故障
Sink提交或去重协议内部精确一次不自动延伸到外部

Sink 决定端到端语义

Flink 内部状态按 Checkpoint 恢复，并不自动保证外部数据库或支付接口精确一次。假设算子已把订单写进外部库，但 Checkpoint 尚未完成就失败；恢复后同一事件会重放，外部库可能收到第二次写入。解决办法包括支持 Checkpoint 协调提交的事务 Sink、按稳定事件 ID 做幂等 UPSERT，或可安全去重的下游协议。具体方法要看外部系统能力和业务结果定义。

事务 Sink 通常先写临时事务，等对应 Checkpoint 完成再提交；故障恢复时识别已提交与未提交事务。外部系统若不支持所需事务语义，宣传“Flink exactly once”也不能推断邮件、短信或资金效果只有一次。以实际 Sink 做故障注入测试：在外部写入后、Checkpoint 确认前杀掉任务，核对最终记录数。

Checkpoint 与 Savepoint

Checkpoint 面向自动容错，系统周期生成并管理，可能按保留策略清理。Savepoint 通常用于人工触发的升级、迁移或有计划停止，保留和恢复流程由运维管理。二者都涉及状态快照，但用途、生命周期和兼容性检查不同。修改状态算子 ID、状态类型或序列化格式后，旧快照未必能恢复到新代码；上线前要做一次真实恢复演练。

窗口聚合的状态可能巨大，Checkpoint 变慢还需检查状态大小、TTL 是否合理、并行度与分区键是否倾斜。将 Checkpoint 间隔调得极短会增加持续写入负担；调得过长则故障后重放更多数据。需共同观察完成时长、失败率、对齐耗时、快照字节、恢复时长和端到端延迟。

用一个故障实验验收

构造左流订单、右流支付，按订单 ID JOIN，输出到有唯一订单键的结果表。让 A 的 Barrier 先到并人为放慢 B，观察对齐耗时与缓冲。Checkpoint 7 成功后输入若干订单，再在外部 Sink 写入之后杀掉任务。恢复后检查源位置、JOIN 状态、结果表唯一键以及重复事件计数。这样能分别验证算子一致性与 Sink 的幂等性。

练习：Checkpoint 8 进行中失败，Checkpoint 7 已完成。恢复应选择哪个快照？若外部 Sink 只支持普通 INSERT，为什么结果仍可能出现重复行？

Checkpoint 关键参数与默认值

参数常见取值含义
execution.checkpointing.interval需显式设置（如 30s~5min）触发周期，不设则关闭 checkpoint
min-pause-between-checkpoints间隔的一半（如 15s）两次 checkpoint 之间的最小间隔，防止连续触发
execution.checkpointing.timeout10 min超时未完成则丢弃该次 checkpoint
max-concurrent-checkpoints1并发进行数；大于 1 时可与 min-pause 配合提速
checkpointing.modeEXACTLY_ONCE（默认）/ AT_LEAST_ONCE语义强度
externalized-checkpoint-retentionRETAIN_ON_CANCELLATION取消作业后保留 checkpoint，便于恢复
aligned-checkpoint-timeout默认 1s（可配 0）对齐等待超过该时长转为非对齐 checkpoint
state.backendhashmap（内存）/ rocksdb（大状态）决定状态容量与 GC 行为

对齐（aligned）checkpoint 会暂停处理该通道的后续数据直到 barrier 到齐，反压时会显著拉长完成时间；非对齐（unaligned）把在途数据也写入快照，适合反压严重场景，但快照会变大。

Barrier 对齐与端到端语义

语义保证实现要求代价
At-most-once可能丢无最低
At-least-once不丢，可能重复checkpoint + 重放下游需幂等
Exactly-once（Flink 内部状态）状态不重不漏对齐 barrier + 可重放 Source对齐开销
端到端 Exactly-once连同 Sink 一起不重不漏两阶段提交 Sink 或幂等 Sink事务开销 / 幂等键

端到端 exactly-once 的两种落地路径：

  • 两阶段提交 Sink（如 FlinkKafkaProducer）：预提交写事务 → checkpoint 成功后再 commit。事务未提交前数据对外不可见，失败则 abort。
  • 幂等 Sink（如带主键的 UPSERT）：靠目标端的主键覆盖实现「重复写无副作用」，通常比 2PC 更快，但要求目标支持幂等写。
  • Kafka 侧要点：事务超时 transaction.timeout.ms 必须大于 checkpoint 间隔，且小于 broker 端 transaction.max.timeout.ms（默认 15 分钟），否则事务被提前中止。

配置与运维命令

代码配置

StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();
env.enableCheckpointing(30_000);                     // 30s 一次
env.getCheckpointConfig().setCheckpointingMode(CheckpointingMode.EXACTLY_ONCE);
env.getCheckpointConfig().setMinPauseBetweenCheckpoints(15_000);
env.getCheckpointConfig().setCheckpointTimeout(10 * 60_000);
env.getCheckpointConfig().setMaxConcurrentCheckpoints(1);
env.getCheckpointConfig().setExternalizedCheckpointCleanup(
    ExternalizedCheckpointCleanup.RETAIN_ON_CANCELLATION);
env.getCheckpointConfig().enableUnalignedCheckpoints();   // 反压严重时开启
env.setStateBackend(new EmbeddedRocksDBStateBackend(true)); // 增量 checkpoint

运维

# 从 savepoint 恢复（不要指望自动恢复：显式指定路径）
flink run -s hdfs:///savepoints/savepoint-abc123 -d yourjob.jar

# 手动触发 savepoint / 取消并保留 savepoint
flink savepoint <jobId> hdfs:///savepoints
flink cancel -s hdfs:///savepoints <jobId>

# 看 checkpoint 指标（关注这几个）
#   lastCheckpointDuration              完成耗时
#   lastCheckpointSize                  快照大小（决定能否按 interval 完成）
#   numberOfCompletedCheckpoints        成功次数
#   numberOfFailedCheckpoints           失败次数（持续增长要查原因）
curl -s http://jm:8081/jobs/<jobId>/checkpoints | python3 -m json.tool

深入自检

Checkpoint 和 Savepoint 有什么区别？

Checkpoint 由系统按周期自动触发，用于故障自动恢复，生命周期由 Flink 管理（默认成功完成后可保留，取消作业时按配置清理）；Savepoint 由用户手动触发，用于计划内停机、版本升级、迁移，需显式指定路径且不会自动删除。

为什么 barrier 对齐会造成延迟？

对齐要求算子等待所有输入通道的 barrier 到齐，期间先到的通道要暂停处理后续数据（数据被缓冲）。当某条通道反压、barrier 迟迟不到时，完成时间会被显著拉长，甚至超时失败。非对齐 checkpoint 把在途数据一并写入快照来规避这个等待。

Flink 内部 exactly-once 等于端到端 exactly-once 吗？

不等。内部 exactly-once 只保证 Flink 算子状态不重不漏；若 Sink 是普通写入（如追加写文件、非幂等 DB insert），故障恢复重放仍会产生重复输出。要做到端到端，Sink 必须支持两阶段提交或幂等写。

Kafka 事务超时该怎么配？

producer 的 transaction.timeout.ms 要大于 checkpoint 间隔（保证 checkpoint 完成前有足够时间提交），同时小于 broker 的 transaction.max.timeout.ms（默认 900000 ms，即 15 分钟）。典型配置：checkpoint 1 分钟、事务超时 5~10 分钟。

状态很大时应该关注什么？

三件事：① 用 RocksDB + 增量 checkpoint，避免每次全量上传；② 给状态设 TTL（State TTL），避免无界增长；③ 关注 lastCheckpointSize 与 duration 的趋势，若单次快照时间接近或超过 interval，说明配置已到极限，需要扩并行度或缩减状态。

自检

Flink 状态恢复后每个事件都只执行过一次，因此普通外部 INSERT 一定不会重复吗？

不一定。失败后事件可能重放；外部 Sink 必须具备事务提交或幂等去重能力。
