⚙️ 进程模型

PostgreSQL 采用"每连接一进程"模型，每个客户端连接由独立的 postgres 后端进程 处理。

  • 主进程 (postmaster)：监听端口、管理连接、进行认证
  • 后端进程：处理 SQL 执行，每个连接一个
  • 后台进程：WAL 写入器、检查点、VACUUM 等

💾 共享内存

所有后端进程共享一块内存区域，避免数据不一致。

  • Buffer Pool：缓存数据页，减少磁盘 IO
  • WAL Buffer：暂存事务日志
  • Lock Manager：管理并发锁

🔄 MVCC 多版本并发控制原理

PostgreSQL 通过 MVCC 实现读写不互斥的并发控制，让读操作永不阻塞写操作。

T1
事务 A 开始

BEGIN;

T2
事务 A 执行 UPDATE

UPDATE users SET name='Alice' WHERE id=1;

旧版本: xmin=T1, xmax=T2, name='Tom'
新版本: xmin=T2, xmax=∞, name='Alice'
T2
事务 B 读取（快照隔离）

SELECT * FROM users WHERE id=1;

→ 看到 name='Tom'
（因为事务 A 还未提交）

T4
事务 A 提交

COMMIT;

T5
事务 B 再次读取

→ 仍看到 name='Tom'

（快照隔离！事务 B 的快照从 T2 就锁定了）

📋 关键概念

  • xmin：插入该行的事务 ID
  • xmax：删除/更新该行的事务 ID（未设置=活着）
  • t_ctid：行在表中的物理位置指针

👁️ 可见性判断规则

  • xmin 事务已提交
  • xmin < 当前快照的 XID
  • xmax 未提交或已回滚

📊 PostgreSQL 索引类型

🌲
B-Tree
默认索引

适用：=, <, >, <=, >=, BETWEEN, LIKE

最通用的索引类型，平衡读写性能。

#️⃣
Hash
等值查询

适用：= 精确匹配

不支持范围查询，但等值查询最快。

🗺️
GiST
几何/范围

适用：地理位置、全文检索、树形结构

PostGIS 插件使用此索引。

📑
GIN
倒排索引

适用：JSONB、数组、全文搜索

适合多值列（数组包含查询）。

📦
BRIN
块范围索引

适用：时序数据、日志、顺序写入的大表

空间极小（O(1)），适合物理顺序与值相关的场景。

🔢
Partial
部分索引

适用：只索引满足条件的行

CREATE INDEX ON orders WHERE status='pending'

📝 总结与选型建议

✅ 选择 PostgreSQL 当

  • 需要复杂数据分析、报表
  • GIS 地理信息系统
  • 需要 JSONB 高效查询
  • AI/向量相似搜索
  • 时序数据监控（TimescaleDB）
  • 企业级应用、ERP
  • 需要从 Oracle 迁移

✅ 选择 MySQL 当

  • 传统 Web 应用、CMS、电商
  • 互联网大流量写入
  • 需要分库分表
  • 团队更熟悉 MySQL
  • 需要成熟的主从复制
  • 使用 PHP 作为后端
  • 简单 CRUD 场景

核心差异一句话总结

MySQL：简单、快速、互联网标配 → PostgreSQL：功能完备、企业级、标准遵循

MySQL 追求 pragmatism（实用主义），PostgreSQL 追求 correctness（正确性）。两者都是优秀的选择，关键在于理解你的业务场景。

PostgreSQL 观测

-- PostgreSQL：看参数与实时状态
SHOW shared_buffers;
SELECT name, setting, unit, source FROM pg_settings
WHERE name IN ('shared_buffers','work_mem','max_connections','synchronous_commit');

-- 看缓存命中率（低于 99% 就该考虑加内存或优化）
SELECT sum(heap_blks_hit) / (sum(heap_blks_hit) + sum(heap_blks_read)) AS hit_ratio
FROM pg_statio_user_tables;

-- 看死元组（VACUUM 是否跟得上）
SELECT relname, n_live_tup, n_dead_tup,
       round(n_dead_tup * 100.0 / greatest(n_live_tup, 1), 2) AS dead_pct,
       last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC LIMIT 10;

-- 慢查询（需要 pg_stat_statements 扩展）
SELECT substring(query, 1, 60) AS q, calls,
       round(total_exec_time::numeric, 1) AS total_ms,
       round(mean_exec_time::numeric, 2) AS avg_ms
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;

MySQL 观测

-- MySQL：对应观测
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
SHOW ENGINE INNODB STATUS\G      -- 看 BUFFER POOL AND MEMORY 段

-- 缓冲池命中率（低于 99% 需关注）
SELECT (1 - (SELECT variable_value FROM performance_schema.global_status
             WHERE variable_name = 'Innodb_buffer_pool_reads') /
            (SELECT variable_value FROM performance_schema.global_status
             WHERE variable_name = 'Innodb_buffer_pool_read_requests')) AS hit_ratio;

-- 慢查询
SELECT digest_text, count_star, round(avg_timer_wait/1e9, 2) AS avg_ms
FROM performance_schema.events_statements_summary_by_digest
ORDER BY avg_timer_wait DESC LIMIT 10;

选型上最实用的一句话：MySQL 在互联网高并发简单查询场景生态最成熟，PostgreSQL 在复杂查询、数据类型丰富度（jsonb/数组/地理）、以及 DDL 事务性上更强。真要迁移，最大的工作量往往不在 SQL 语法，而在隔离级别默认值的差异导致的并发行为变化。

迁移与检查清单

迁移项差异点处理方式
自增主键AUTO_INCREMENT vs 序列改成 GENERATED BY DEFAULT AS IDENTITY，并重置序列起始值
字符串比较MySQL 默认不区分大小写（ci 排序规则）PG 区分大小写，需改用 ILIKE 或 citext
反引号MySQL 用 ` 包裹标识符PG 用双引号，且未加引号的会被折叠成小写
INSERT IGNORE / ON DUPLICATE KEYPG 无对应语法改用 ON CONFLICT ... DO NOTHING/UPDATE
LIMIT n, mPG 用 LIMIT m OFFSET n改写分页语句
字段类型DATETIME / TINYINT改用 TIMESTAMP / SMALLINT
事务 DDLMySQL DDL 隐式提交PG 可以放进事务，迁移脚本可整体回滚

上线前逐条核对：

  • 先确认隔离级别：MySQL 默认 RR、PG 默认 RC，迁移后并发行为会变。
  • PG 必须关注 VACUUM：死元组堆积会导致表膨胀与查询变慢，长事务会阻塞回收。
  • work_mem 是每个排序操作都要分配，设太大会在并发排序时 OOM。
  • MySQL 的行长度限制（约 65535 字节/行）在大 VARCHAR 场景容易触顶。
  • 两边都要看缓存命中率，低于 99% 说明内存或索引有问题。
  • 连接数都不要盲目调大：用连接池（PgBouncer / ProxySQL）更有效。
  • JSON 场景优先 PG 的 jsonb + GIN，可索引且支持包含查询。
  • MySQL 的 utf8 不是真 UTF-8，要用 utf8mb4（否则 emoji 存不进去）。
  • 迁移要做双向灰度与数据比对，不能只跑通一遍就切换。
  • 慢查询分析都要先开统计：PG 装 pg_stat_statements，MySQL 开 performance_schema。
