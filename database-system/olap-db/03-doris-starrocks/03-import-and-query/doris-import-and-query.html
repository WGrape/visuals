①四种导入方式怎么选

方式数据源语义适用
Routine LoadKafka（持续消费）常驻任务，准实时日志、行为流实时入仓
Stream LoadHTTP 推送（本地文件/程序）单次同步导入，返回即成功小批量、脚本导入、程序直写
Broker LoadHDFS / 对象存储异步批量，可重试大批量离线导入、历史数据回灌
INSERT INTO ... SELECT库内其他表 / 外部表同步执行ETL 加工、表间转换
每条导入都是一个「事务」：要么整批可见，要么整批不可见，不会出现部分可见。 这带来两个实践结论：① 批太小会导致事务过多、版本堆积、compaction 压力大； ② 批太大失败时回滚成本高。常见做法是攒批到「几十秒~几分钟的数据量」再提交—— 具体阈值按数据速率与压测结果定。
-- Routine Load：常驻消费 Kafka
CREATE ROUTINE LOAD db.job_orders ON orders
COLUMNS TERMINATED BY ","
PROPERTIES ("desired_concurrent_number"="3", "max_batch_interval"="30")
FROM KAFKA ("kafka_broker_list"="broker:9092", "kafka_topic"="orders");

-- 导入任务出问题时的排查顺序
SHOW ROUTINE LOAD;            -- 看状态与进度
SHOW ROUTINE LOAD FOR db.job_orders;   -- 看具体的错误行与原因

②JOIN 优化：Colocate 与 Runtime Filter

Colocate Join

两张表用相同的分桶列、相同的桶数、相同的副本分布时， 相同 key 的行一定落在同一台机器上，JOIN 可以本地完成，免去重分布。 这是大表 JOIN 大表最有效的优化。

Bucket Shuffle Join

只把右表按左表所在节点重分布，比全量重分布传输量小。 在无法 Colocate（分桶列不同）时的次优选择。

Broadcast Join

把小表广播到所有节点。右表很小的星型模型维表关联首选， 大表广播会打爆网络与内存。

Runtime Filter

大表 JOIN 小表时，先扫小表生成运行时过滤条件（bloom / min-max / in list） 下推到大表扫描，大幅减少读取量。星型模型的性能关键。

优化顺序： ① 先看执行计划确实用了哪种分布方式（EXPLAIN 里会显示）； ② 大表 JOIN 大表优先改造成 Colocate； ③ 星型模型确认 Runtime Filter 已生效（有时因类型不匹配或统计信息缺失而不下推）； ④ 最后才考虑调 session 变量或加 hint。

③查询调优的常见问题

现象可能原因排查
没有命中分区裁剪时间列上包了函数，或条件不是范围形式EXPLAIN 看扫描的分区数
没走物化视图维度或聚合函数与定义不匹配确认查询能否从物化视图上卷得到
COUNT(DISTINCT) 极慢高基数列精确去重改用 bitmap 或近似函数（接受误差时）
JOIN 慢且网络打满两表都做了全量重分布改 Colocate 或用 Broadcast
导入后查询变慢版本堆积、compaction 没跟上看 tablet 版本数与 compaction 状态
内存超限大结果集排序 / 大 JOIN / 广播了不该广播的表看 query profile 的内存峰值算子
不要照抄网上调优参数的数值。执行内存、并行度、compaction 线程这类参数 与集群规模、数据量、并发强相关，同一份参数在小集群上救命、在大集群上可能压垮节点。 先通过 profile 定位到具体算子，再有针对性地调。

④日常运维关注点

  1. 导入延迟：Routine Load 的 lag 是最直接的实时性指标，要有告警。
  2. Compaction 压力：写入过快会产生大量待合并版本，影响查询性能与磁盘占用。
  3. Tablet 分布均衡：节点扩容/下线后要重新均衡，否则出现热点节点。
  4. 存储增长：列存压缩比高但明细表仍会快速增长，配合分区做生命周期管理（冷热分层/过期删除）。
  5. 慢查询归档：定期收集慢查询，判断是该加物化视图、改模型，还是该拒绝这类查询。
Q：实时写入和查询性能冲突怎么办？
A：这是 OLAP 的固有矛盾——写入越实时，小文件与版本越多，查询越慢。 三种缓解：① 攒批，用几分钟延迟换更大的批次； ② 读写分离，查询走独立副本； ③ 分层——实时层存最近几小时用明细，历史层转成预聚合。 先明确业务能接受多少延迟，再定架构。
Q：该不该用 INSERT 逐行写？
A：不该。列存的写入路径是为批量设计的，逐行 INSERT 会产生大量小事务与版本， 迅速拖垮集群。应用侧应攒批后走 Stream Load，或写入 Kafka 由 Routine Load 消费。

导入命令

-- Stream Load：curl 直传 CSV（label 必须唯一，用于幂等去重）
curl -v --location-trusted -u root: \
  -H "label:load_20261022_01" \
  -H "column_separator:," \
  -H "columns:dt,user_id,amount" \
  -T data.csv \
  http://fe_host:8030/api/db/orders/_stream_load

-- Routine Load：持续消费 Kafka
CREATE ROUTINE LOAD db.order_load ON orders
COLUMNS(user_id, amount, dt)
PROPERTIES (
  "desired_concurrent_number" = "3",
  "max_batch_interval" = "20",      -- 每 20 秒攒一批
  "max_batch_rows" = "300000",      -- 或攒够 30 万行触发
  "max_error_number" = "100"        -- 错误行数上限，超过则任务暂停
)
FROM KAFKA (
  "kafka_broker_list" = "broker1:9092,broker2:9092",
  "kafka_topic" = "orders",
  "property.group.id" = "doris_cg"
);

label 是幂等的键：同一个 label 重复提交，Doris 会直接返回上次的结果而不会重复写入。这是做“至少一次”投递时保证不重不漏的关键。

导入参数调优

参数默认值调优建议
max_batch_rows200000行宽较窄可加到 50 万，减少版本数
max_batch_interval10 s实时性要求不高时调到 30~60 s，攒大批
max_batch_size100 MB与行数共同触发，先到先生效
desired_concurrent_number3分区数多时可提到 5~10，但会占用更多执行资源
max_error_number0生产建议放宽到 100~1000，避免个别脏数据导致任务卡死

写入放大问题的根因：每次导入生成一个新版本（tablet version）。小批量高频写入会让版本数飙升，查询需要合并大量版本，性能急剧下降。

版本堆积排查

-- 查看版本堆积情况（COMPACTION 状态）
SHOW PROC '/dbs/db/orders/partitions';
-- 关注 VisibleVersionCount，> 100 说明导入批次过碎

-- 手动触发合并
ALTER TABLE orders COMPACT;

查询侧：分区裁剪与前缀索引

  • 分区裁剪：按日期分区后，WHERE dt = '2026-10-22' 只扫对应分区，这是 OLAP 提速的第一手段。
  • 分桶裁剪：分桶键上的等值条件可进一步定位到具体 tablet。
  • 前缀索引：Doris 自动取表的前 36 字节作为前缀索引，建表时把高频过滤列放在最前面。
  • 物化视图：预聚合常用维度组合，查询自动命中，避免每次全量聚合。

执行计划判读

-- 查看执行计划，确认是否命中分区裁剪
EXPLAIN SELECT dt, sum(amount) FROM orders WHERE dt >= '2026-10-01' GROUP BY dt;

-- 关注输出里的 partitions 字段：
--   partitions=1/30   → 命中裁剪，只扫 1 个分区 ✓
--   partitions=30/30  → 全表扫描 ✗（WHERE 条件没落到分区列上，或类型不匹配）

自检 Q&A

Q：Routine Load 任务突然 PAUSED 了，怎么查？

A：SHOW ROUTINE LOAD\G 看 ErrorLogUrls 和 ReasonOfStateChanged。最常见三种：① 错误行数超过 max_error_number（脏数据）；② Kafka offset 越界（topic 被清理或重置）；③ 表结构变更导致列解析失败。修完用 RESUME ROUTINE LOAD 恢复。

Q：导入很慢，先看什么？

A：看 BE 的 并发导入任务数是否被占满（SHOW BACKENDS 里的 running txn）。若已满，说明并发上限不够或上游写太快；若没满还慢，则是单批太小——把 max_batch_interval 调大攒批，通常能提升数倍吞吐。

Q：为什么查询没走分区裁剪？

A：三个高频原因——① WHERE 条件对分区列做了函数变换（如 DATE(dt)），导致无法下推；② 分区列是字符串而传入的是数字（隐式转换）；③ 用了 OR 连接多个条件。把条件改成对分区列的直接范围比较即可。

Q：Stream Load 返回成功但查不到数据？

A：多半是事务还没提交可见。Stream Load 返回时数据已写入但可能处于 COMMITTED 而非 VISIBLE 状态，通常秒级内转为可见。若长时间不可见，检查 BE 是否有节点失联。
