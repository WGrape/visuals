分布式数据库的全局时钟：TSO、HLC 与外部一致性

为什么事务需要一个「全局时间」，三种授时方案各自付出什么代价

NewSQLTSOHLC外部一致性快照读
① 为什么需要 ② 三种方案 ③ TSO 细节 ④ 四种读 ⑤ 排障 ⑥ 疑问
一句话总结：分布式数据库要把「很多台机器上的事件」排成一条线，就必须有全局时间概念。三种主流做法是 TSO 单点/少量节点授时、HLC 混合逻辑时钟、TrueTime 带误差区间的物理时钟。它们解决的是同一个问题（给事务定序），但代价完全不同：TSO 简单但多一次 RPC，HLC 无中心但可能有因果外的偏差，TrueTime 精度高但依赖专用硬件。

01为什么必须有全局时钟

📸 快照读需要「同一时刻」

一条查询要读到「某个时间点的一致性状态」。如果各节点各用自己的物理时钟，同一个快照在 A 节点是 10:00:00.000、在 B 节点是 10:00:00.008，读到的就是撕裂的数据。

🔢 事务需要全序

并发事务要能排序：T1 提交后开始的 T2 必须看见 T1。没有全局时钟就只能靠「谁先拿到锁」这类局部顺序，跨节点时无法成立。

🔁 多副本要能对齐版本

Raft/Paxos 解决副本间的一致，但不解决「读应该看到哪个版本」。时间戳才是读的路径选择依据。

⏱ 跨地域要给出延迟承诺

陈旧读（stale read）要回答「最多旧多久」，这必须由一个可度量的时间基准来表述。

要点：判断一个分布式库的时间语义，先问一句：它的时间戳是谁发的？ 答案决定了延迟、一致性和故障时的行为。

02三种授时方案对比

方案代表产品时间从哪来能否保证外部一致性主要代价
TSO（时间戳预言机）TiDB（PD 授时）中心化的授时节点发号，单调递增能（单点发号天然全序）每次取 ts 一次 RPC，中心点故障/抖动影响全局
HLC（混合逻辑时钟）CockroachDB物理时钟 + 逻辑计数，节点间通信时推进能保证因果一致，跨节点无通信的事务可能存在时钟偏差无单点；但需处理「不确定区间」和读刷新
TrueTimeSpannerGPS + 原子钟，返回区间 [earliest, latest]能（提交时等到区间过去）依赖专用硬件；误差越大，提交等待越久
纯物理时钟 + NTP不建议用于强一致事务各节点本地时钟不能（时钟偏移无法界定）便宜但读不到正确版本

外部一致性（external consistency / linearizability）的通俗定义：如果事务 T1 提交完成后，T2 才开始，那么 T2 一定能读到 T1 的写入。注意它强于「可串行化」——可串行化只要求并发事务等价于某个串行顺序，不要求这个顺序与真实时间一致。

03TSO 是怎么工作的

中心化授时：所有节点向同一个授时源取时间戳，天然全序

TiDB 由 PD（Placement Driver）承担授时职责：事务开始时取一个 start_ts，提交时取一个 commit_ts，中间所有读到的数据都按 start_ts 过滤版本。Percolator 风格的两阶段提交第一步「Prewrite」只加锁，第二步「Commit」写入 commit_ts，数据在 commit_ts 生效的瞬间对外可见。

环节发生什么延迟构成
取 start_ts向 PD 请求一个时间戳1 次 RPC（PD 在同城约 0.2~1ms 量级）
Prewrite主锁 + 各参与者写入锁与数据1 轮到所有参与分片的 RPC，取最慢的那个
取 commit_ts再向 PD 请求一个时间戳1 次 RPC
Commit提交主锁，异步提交其余写主锁 1 次 RPC 即可返回（其余异步）
要点：所以一个最简单的单行事务也要 2 次授时 RPC，这是 TSO 方案最常被吐槽的地方。优化手段通常是「一次取一批时间戳」或「本地缓存+预取」，具体策略与开关需查对应产品文档。

04四种读：到底读到哪个版本

读的类型语义延迟典型用途
强一致读（当前读）取最新 ts，可能要等未决议的事务 / 遇锁要清锁最高（可能阻塞在锁冲突上）支付、库存扣减等不能读旧的场景
快照读（指定历史 ts）读过去某个时间点的一致状态中（不需要处理当前锁）对账、数据核对、可重复读
陈旧读（stale read）允许读几秒前的数据，换更低延迟与更高可用低（通常可路由到本地/近端副本）大量只读查询、看板、报表
Follower / 副本读从非 leader 副本读，减轻 leader 压力低，但一致性取决于产品是否做了副本读的一致性校验读多写少、能容忍轻微延迟的场景
-- TiDB：读指定时刻的快照（读到的内容由时间戳决定，不受当前写影响）
SELECT * FROM orders AS OF TIMESTAMP '2026-10-25 10:00:00' WHERE user_id = 1001;

-- TiDB：陈旧读（读 5 秒前的数据，语法与开关随版本变化，以产品文档为准）
SELECT * FROM orders AS OF TIMESTAMP NOW(6) - INTERVAL 5 SECOND WHERE user_id = 1001;

-- CockroachDB：跟随者读 / 历史读（同样以版本为准）
SELECT * FROM orders AS OF SYSTEM TIME '-5s' WHERE user_id = 1001;
SELECT * FROM orders AS OF SYSTEM TIME '2026-10-25 10:00:00' WHERE user_id = 1001;
要点：用陈旧读之前必须确认一件事：业务能不能接受这几秒的旧数据。余额、库存、幂等判断一律不能开；列表页、统计看板通常可以。

05排障与边界：时钟相关的坑

  • 「读不到自己刚写的」：多半是读走了副本读/陈旧读，或者连接被路由到了还没追上日志的节点。先确认读的一致性级别。
  • 主从切换后时间回退：授时节点切换时若处理不当，可能发出比之前更小的时间戳。产品一般会用「持久化已发出水位」来防，但故障演练必须覆盖这条。
  • 跨地域事务延迟陡增：TSO 方案下每次取时间戳都要跨地域 RTT。把事务改成小事务 + 就近读是常见优化方向。
  • NTP 抖动：物理时钟参与的方案（HLC、TrueTime）对时钟漂移敏感，节点间时钟偏移过大可能触发事务重试或直接拒绝写入。
  • 「外部一致性」不是默认项：有些产品的最高隔离级别仍不保证外部一致性，需在文档里确认，别想当然。
  • 批量任务的时间戳：大事务持锁时间长，会让后续读的锁清理变慢；导入类任务应拆批。
-- 排查「读不到刚写的数据」的常用路径
-- 1) 确认当前会话的一致性/陈旧读设置（变量名随产品与版本不同）
SHOW VARIABLES LIKE '%stale%';
SHOW VARIABLES LIKE '%read%';

-- 2) 看事务与锁：是否有长时间未决的事务挡住了读
SELECT * FROM information_schema.data_lock_waits LIMIT 20;      -- TiDB
SHOW CLUSTER STATEMENTS LIMIT 20;                                -- 看长事务

-- 3) 看副本延迟：副本落后多少决定陈旧读能读到多新的数据
SELECT * FROM information_schema.tidb_hot_regions LIMIT 20;      -- 热点 Region

06常见疑问

问：TSO 单点挂了怎么办？

授时服务本身是高可用的（TiDB 的 PD 是 Raft 组），不是真单点。但它仍是全局关键路径：PD 抖动会影响所有事务取时间戳。所以生产上 PD 的部署位置、网络质量和时钟源都要单独保障。

问：HLC 有时间偏差，是不是就不安全了？

HLC 保证的是因果一致：有因果关系的事务一定按顺序可见。两个毫无通信的并发事务，HLC 可能给出与真实物理时间相反的顺序——这在多数业务里无所谓，但如果你的业务依赖「墙钟时间上的先后」，就要显式同步一次（比如让它们访问同一行）来建立因果。

问：为什么 TrueTime 要「等待」？

因为它返回的是区间而不是一个点。事务提交时必须等到「自己的时间戳肯定已经过去」，后面的事务才不可能错过它。误差越小等得越短——所以 Google 要上 GPS 和原子钟把误差压到毫秒级。

问：我做业务开发，需要关心这些吗？

至少要关心两件事：① 你的读是强一致还是陈旧读（决定能不能读到旧数据）；② 事务里跨了多少个分片（决定延迟和冲突概率）。剩下的交给 DBA。
