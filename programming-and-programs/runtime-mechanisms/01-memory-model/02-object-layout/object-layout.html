是什么

对象在内存里怎么摆

一个对象（结构体实例）在内存中通常是一块连续区域：各字段按声明顺序排布，中间可能插入填充字节（padding）以满足对齐要求。对象大小 = 各字段大小 + 填充。

规则

对齐：为什么要「凑整」

⚙️
硬件要求
CPU 按字长访问内存；未对齐访问在部分架构上会直接报错（如 ARM 早期），在 x86 上虽可用但更慢
📦
单次访存
对齐的数据可一次总线周期读完；跨两个字的未对齐数据需要两次访存再拼接
🧮
对齐值
通常等于该类型的大小（int64 按 8 对齐，int32 按 4 对齐），上限常为一个字长
📐
整体对齐
结构体整体大小需是其最大字段对齐值的整数倍，数组连续存放时才不会错位
演算

手算一个对象多大

// Go 示例
type Bad struct {
    a bool    // 1 字节，对齐 1
    b int64   // 8 字节，对齐 8
    c int32   // 4 字节，对齐 4
}
// 布局：a(1) + pad(7) + b(8) + c(4) + pad(4) = 24 字节

type Good struct {
    b int64   // 8
    c int32   // 4
    a bool    // 1
}
// 布局：b(8) + c(4) + a(1) + pad(3) = 16 字节

// 同样的字段，换个顺序省了 1/3 内存
什么时候值得优化：对象数量巨大（百万级缓存条目、大数组）时，省下的内存直接转化为更低的 GC 压力与更好的缓存命中率。少量对象则不必纠结。
进阶

缓存行与伪共享

CPU 缓存以缓存行（Cache Line，通常 64 字节）为单位加载。若两个无关的变量恰好落在同一缓存行，且被不同 CPU 核频繁写入，就会互相使对方的缓存失效——这叫伪共享（False Sharing），是并发程序里隐蔽的性能杀手。

😵
表现
加了多线程反而更慢；两个线程写不同的变量，却出现大量缓存一致性流量
💊
解法
按缓存行填充（padding）把变量隔开到不同缓存行；或让每个核写自己的计数、最后汇总（Go 的 pprof 中常见此模式）
面试问答

高频问题

Q1：为什么要内存对齐？
CPU 按字长访问内存，对齐的数据可一次访存取完；未对齐数据可能跨越两个字，需要两次访存再拼接，在部分架构上甚至会触发异常。对齐是牺牲少量空间换取访问效率。
Q2：结构体字段顺序会影响大小吗？
会。字段间为满足对齐会插入填充字节。把对齐值大的字段放前面（从大到小声明），能减少填充，显著降低对象体积。
Q3：什么是伪共享？
两个被不同 CPU 核频繁写入的变量落在同一缓存行，导致缓存行在核间反复失效与同步，性能急剧下降。解决办法是按缓存行填充隔离变量，或让各核写独立副本最后汇总。
Q4：结构体整体大小为什么要按最大对齐值补齐？
因为数组元素连续存放。若整体大小不是最大对齐值的整数倍，第二个元素开始就会错位，破坏每个字段的对齐。
Q5：优化对象布局真的有用吗？
在对象数量巨大时很有用（百万级缓存、大数组）：省内存、降低 GC 压力、提升缓存命中率。对象数量少时收益有限，可读性优先。

对齐的三条规则与一个后果

内存对齐不是优化技巧，而是硬件的要求：CPU 按固定宽度读取内存，跨边界访问要么慢，要么直接出错。理解三条规则，就能手算出任何结构体的布局。

规则内容后果
成员对齐每个成员的起始地址必须是其对齐值的整数倍成员之间可能出现空隙
整体对齐结构体的对齐值等于最大成员的对齐值决定了整体大小的粒度
尾部填充结构体总大小必须是其对齐值的整数倍末尾也会补字节
数组间距数组元素之间也要满足对齐元素大小已含尾部填充，所以自动满足
布局推导：成员对齐 → 内部填充 → 尾部补齐 → 总大小
对齐值从哪来通常与类型大小相关，比如 8 字节类型按 8 对齐
为什么有空隙为了让下一个成员落在合法地址上
为什么尾部也要补否则数组里第二个元素就会错位
字段顺序有影响把大对齐的成员放前面，通常能省下填充

手算一遍：为什么换一下顺序就变小了

下面是一个具体的推演。关键观察是：填充只出现在「对齐要求不同」的成员之间，把相同对齐要求的成员聚在一起，就能少填。

什么时候值得优化布局

当这个结构体的实例数量极大时。省下 8 字节在百万级对象上就是 8MB 内存，而且更小的对象意味着更好的缓存命中率。如果只有几十个实例，优化布局毫无意义。

什么时候不要动

如果这个结构要与其他系统对齐（网络协议、文件格式、C 接口），字段顺序就是契约的一部分，不能为了省内存重排。可读性与稳定性优先于几个字节。

缓存行与伪共享：多核下最容易忽略的坑

CPU 不是按字节读内存，而是按缓存行整块加载，常见一行 64 字节。这带来一个反直觉的问题：两个互不相关的变量如果被放在同一行，反而会互相拖慢。

伪共享：无关的变量落在同一缓存行，导致多核写互相拖慢

深入自检：内存布局的六个问题

为什么编译器要插入填充字节？

因为成员必须落在合法地址上。如果 CPU 要求 8 字节类型从 8 的倍数地址开始，而它前面只有一个字节的成员，编译器只能补 7 个字节把它推到合法位置。这是一种用空间换访问速度的交易。

重排字段一定更省吗？

通常按对齐值降序排列最省，但不绝对。最可靠的办法是用语言提供的大小查询函数实测，而不是靠推算。而且重排会改变字段的书写顺序，可能降低可读性，需要权衡。

结构体大小会随平台变化吗？

会。指针大小、对齐规则都与平台和编译器有关。所以不要硬编码大小，需要固定布局时应该显式指定对齐与打包方式，并用静态断言检查。

为什么有时候要主动降低对齐？

当结构体要紧凑地写进文件或网络报文时，填充字节会浪费带宽、还可能导致不同端解析不一致。这时会用打包指令去掉填充，代价是访问变慢甚至在某些平台上出错，所以要谨慎并明确标注。

伪共享只在多核下出现吗？

是的。单核上线程交替执行，不存在缓存行在核心间来回转移的问题。所以伪共享的典型症状是：单线程跑很快，一旦多线程并发写就急剧变慢，而且加的线程越多越慢。

怎么确认是不是伪共享？

用性能分析工具看缓存未命中指标，或者做对照实验：把变量之间加上填充或不加，比较吞吐。如果填充后明显变快，基本可以确认。不要一开始就加填充，那是把结构体变大来赌一个未证实的原因。
