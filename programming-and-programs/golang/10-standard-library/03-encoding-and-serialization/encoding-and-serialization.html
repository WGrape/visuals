JSON

export 字段才编码

只有导出的（首字母大写）字段参与编解码；struct tag 控制键名与忽略；json.Marshal/Unmarshal 处理 []byte，Encoder/Decoder 处理流。

type User struct {
    Name  string `json:"name"`
    Email string `json:"email,omitempty"`
    pwd   string // 小写，不编码
}
b, _ := json.Marshal(User{Name: "Li"})
// {"name":"Li"}
XML

标签与属性

encoding/xml 用 tag 映射元素与属性；适合与老系统或配置文件对接，结构比 JSON 更繁。

type Note struct {
    XMLName xml.Name `xml:"note"`
    Title   string   `xml:"title"`
    Body    string   `xml:"body"`
}
gob

Go 对 Go 的高效

gob 是 Go 专有二进制格式，无需 schema、比 JSON 快且小，常用于 RPC 与本地持久化；跨语言不可用。

var buf bytes.Buffer
enc := gob.NewEncoder(&buf)
enc.Encode(data)
dec := gob.NewDecoder(&buf)
dec.Decode(&out)

流式场景优先用 Encoder/Decoder 而非一次性 Marshal，省内存、可边读边写。

Go 有哪些编码方案，怎么选

选择编码格式本质上是三选二：可读性、体积/速度、跨语言与模式演进。Go 标准库提供了 JSON、XML、Gob、Base64、CSV 等，社区还有 Protobuf、MsgPack 等。

JSON 性能：什么时候该优化，怎么优化

先确认瓶颈

基准测试先跑起来，别凭直觉优化。

func BenchmarkMarshal(b *testing.B) { u := User{...} for i := 0; i < b.N; i++ { json.Marshal(u) } } go test -bench=. -benchmem
  • 关注 allocs/op，往往比 ns/op 更值得优化
  • 大部分开销来自反射与临时分配

优化手段

  • 用指针接收大结构体，避免值拷贝
  • 复用 bytes.Buffer / sync.Pool 承载 Encoder
  • 高频固定结构可手写 MarshalJSON
  • 改用生成式库（如 easyjson、ffjson）或 Protobuf
  • 减少嵌套与 interface{}，字段类型越具体越快

常见坑

  • time.Time 默认 RFC3339，跨语言要统一格式
  • int64 大整数在 JS 里会精度丢失，可改 string
  • map 的 key 会被排序，顺序不保证稳定语义
  • nil slice 序列化为 null，空 slice 为 []

自定义编解码：两个接口

// 自定义序列化：实现 Marshaler func (u User) MarshalJSON() ([]byte, error) { type Alias User // 避免递归调用自身 return json.Marshal(struct { Alias Age int `json:"age"` }{Alias: Alias(u), Age: calcAge(u)}) } // 自定义反序列化：实现 Unmarshaler func (u *User) UnmarshalJSON(b []byte) error { type Alias User aux := struct { *Alias Created string `json:"created"` }{Alias: (*Alias)(u)} if err := json.Unmarshal(b, &aux); err != nil { return err } // 再按自定义格式解析 Created return nil } // 关键技巧：定义本地 Alias 类型打断点，避免无限递归

什么时候该自定义：字段格式需要兼容旧协议、要做脱敏、要把多种输入格式归一。不要用它来做复杂业务逻辑，序列化层保持简单可测。

深入自检

为什么 JSON 反序列化必须传指针？

Unmarshal 需要修改目标变量的值。Go 是值传递，传值只会修改副本，调用方拿不到结果，而且会因为不可寻址而报错。传指针（通常是 &u）才能让修改生效。

omitempty 有什么坑？

它按零值判断，因此 0、false、空字符串、nil 都会被省略。对于「0 是有意义的值」的字段（如数量为 0），省略后接收方可能误判。需要区分时应改用指针类型或自定义 MarshalJSON。

大 JSON 怎么处理不爆内存？

用 json.Decoder 流式读取，逐个 Token 或逐个对象处理，而不是一次性 Unmarshal 整个数组。写也一样，用 Encoder 边生成边写。这是处理日志文件与大响应的标准做法。

int64 在浏览器里为什么会变？

JavaScript 的数字是双精度浮点，安全整数上限约 2^53。超过的 int64（如雪花 ID）会精度丢失。常见做法是序列化时改成字符串，前端按字符串处理。

Gob 值得用吗？

两端都是 Go、且不需要人读的场景下挺好用：无需 tag、支持接口与复杂类型。但它不跨语言，协议演进能力弱于 Protobuf。一旦将来可能有非 Go 客户端，就不要用。

第一层 · 怎么选（决策表）

Go 的序列化选型其实只有三个维度要权衡：跨语言吗？要不要人可读？性能敏感吗？三者基本不可能同时满足。

格式跨语言人可读有 schema速度体积典型用途
JSON✓✓✗中大API、配置、日志
Protobuf✓✓✗✓（.proto）快小gRPC、跨服务通信
MessagePack✓✗✗快小缓存、Redis
gob✗（仅 Go）✗✗中中Go 进程间、RPC
Avro✓✗✓（动态）快小大数据、Kafka
TOML/YAML✓✓✗慢大配置文件
CSV✓✓✗快中数据导出/导入
  • 默认答案：对外 API 用 JSON，内部 RPC 用 Protobuf，配置文件用 YAML/TOML，纯 Go 内部用 gob。
  • gob 的定位容易搞错：它是Go 专有的（其他语言没有成熟实现），所以只在「两端都是 Go」时才可用。它的优势是零 schema、支持任意类型（包括接口、函数外的几乎所有类型），序列化时自带类型信息。
  • 不要自己造二进制格式：除非有极端需求，用成熟格式能省掉兼容、安全（反序列化漏洞）等一大堆坑。

第二层 · 用法、标签与基准数字

Go 代码

// —— JSON：最常用的标签写法 ——
type User struct {
    ID       int64     `json:"id"`                  // 重命名为小写
    Name     string    `json:"name"`
    Password string    `json:"-"`                   // 【永远不序列化】
    Email    string    `json:"email,omitempty"`     // 空值不输出
    Created  time.Time `json:"created"`             // RFC3339 格式
    Internal string    `json:",omitempty"`          // 保持字段名 + omitempty
}

// 流式编码（大对象/网络传输用，避免一次性构造大 []byte）
enc := json.NewEncoder(w)          // w 可以是 http.ResponseWriter
enc.SetEscapeHTML(false)           // 关掉 HTML 转义（< > & 会被转成 <）
enc.Encode(u)

// 流式解码（处理大 JSON / 流式响应）
dec := json.NewDecoder(r)
dec.DisallowUnknownFields()        // 【严格模式】未知字段报错，抓 API 变更
var u User
if err := dec.Decode(&u); err != nil { /* ... */ }

// 数字精度坑：JSON 的数字默认解成 float64
var m map[string]interface{}
json.Unmarshal([]byte(`{"id":12345678901234567890}`), &m)
//   m["id"] 是 float64，大整数会【丢精度】！
dec2 := json.NewDecoder(strings.NewReader(s))
dec2.UseNumber()                   // 解成 json.Number（保留原始字符串）

// —— gob：Go 专用，支持接口 ——
var buf bytes.Buffer
enc := gob.NewEncoder(&buf)
enc.Encode(myStruct)               // 首次编码会写入类型定义
gob.Register(MyImpl{})             // 【接口必须注册具体类型】
var out MyStruct
gob.NewDecoder(&buf).Decode(&out)

// —— 性能技巧 ——
// 1) 复用 Encoder/Decoder，避免重复分配
// 2) 大 JSON 用 json.RawMessage 延迟解析
type Envelope struct {
    Type string          `json:"type"`
    Body json.RawMessage `json:"body"`   // 先不解析，按需再解
}
库相对性能说明
encoding/json1×（基线）标准库，反射实现，兼容性最好
jsoniter2~3×兼容 encoding/json 的 API，jsoniter.ConfigCompatibleWithStandardLibrary
sonic（字节）3~5×基于 SIMD + JIT，大 JSON 收益明显，小对象可能不如 jsoniter
easyjson4~6×代码生成，零反射，但要跑生成步骤
protobuf5~10×（且体积小 30~50%）跨语言首选

换 JSON 库前先测：sonic 对大 JSON（>1KB）收益大，对小对象（几十字节）可能反而更慢（JIT 预热与 SIMD 启动开销）。务必用自己的真实数据压测。

第三层 · 常见坑与排障清单

  • 大整数丢精度（最常见也最隐蔽）：json.Unmarshal 到 interface{} 时数字变成 float64，超过 2⁵³ 的整数会丢精度。订单号、雪花 ID、金额分都会中招。解法：① 用具体结构体而不是 map；② 用 UseNumber()；③ 用 json.Number。
  • time.Time 的格式与时区：JSON 用 RFC3339。坑：① 不带时区信息会被当 UTC；② 反序列化后时区可能丢失；③ 自定义格式要写 MarshalJSON。建议统一用带时区的 RFC3339 并在 API 文档中写明。
  • omitempty 对 0 值也生效：Age int 为 0 时会被省略，导致「0」和「未设置」无法区分。需要区分时用指针（*int）或 sql.NullInt 类似类型。
  • HTML 转义：json.Marshal 默认把 <、>、& 转义成 \u003c 等。json.Encoder 用 SetEscapeHTML(false) 关掉（Marshal 无法关，要用 Encoder）。
  • 循环引用会无限递归：json: unsupported value: encountered a cycle。结构体互相引用时会出现，需要自定义 Marshal 或在 DTO 里断开。
  • gob 的接口必须 Register：忘了注册会得到 gob: type not registered for interface。且编码端和解码端都要注册相同的名字。
  • gob 的类型演进：新增字段通常安全（默认值），但删除字段或改类型会导致解码失败或不匹配。gob 不适合长期持久化。
  • 反序列化不可信数据是安全风险：尤其是 gob 和 encoding/binary——构造恶意数据可能导致内存耗尽或 panic。对外接口只接受 JSON/Protobuf，且要限制输入大小（用 io.LimitReader）。
  • 并发安全：*json.Encoder 不是并发安全的，要每个 goroutine 一个，或用 sync.Pool 复用。

第四层 · 原理与取舍

性能差异的根源只有一条：反射 vs 代码生成。encoding/json 在运行时通过反射遍历字段、查 tag、做类型转换，这些开销在热路径上非常可观；代码生成方案（easyjson、protobuf）在编译期就生成了专门的编解码函数，运行时只是顺序调用。

  • 为什么标准库坚持用反射：为了零代码生成步骤、任意类型可用。这是 Go「简单可依赖」的设计取向——宁可慢一点，也不想让每个项目都跑一遍代码生成器。这个取舍在绝大多数场景是对的。
  • 什么时候真的需要换库：先量化。一个经验判断：如果序列化在你的接口耗时里占比 <5%，不要换（复杂度不值得）；如果 >20%（常见于高频内部 RPC 或大 JSON 处理），值得换。
  • Protobuf 为什么又快又小：① 字段用编号（1、2）而不是名字，省掉字段名；② varint 变长编码（小整数只占 1 字节）；③ 不需要分隔符和转义（二进制 TLV 格式）；④ 生成的代码零反射。所以典型场景下比 JSON 快 5~10 倍、体积小 30~50%。
  • Protobuf 的代价：需要维护 .proto 文件、跑代码生成、不可自描述（拿到二进制不知道 schema 就解不开，调试麻烦）。所以对外 API 通常还是 JSON——可调试性更重要。
  • JSON 也有「半编译」优化：标准库会为每个类型缓存反射得到的编解码器（sync.Map），所以第二次编码同一类型会快很多——这就是基准测试要预热的原因。

gob 到底什么时候该用？

只在两个条件同时满足时：① 通信两端都是 Go；② 需要序列化复杂类型（接口、私有字段、复杂嵌套）。典型场景是 Go 写的分布式系统内部通信（如早期的 RPC、某些任务队列）。它的优势很实在：不需要写 proto、不需要生成代码、能直接传接口值（只要 Register 过）。但缺点同样明显：不能跨语言、不适合长期存储、类型演进脆弱。所以现在的实际建议是：新项目优先用 Protobuf，因为「两端都是 Go」这个约束迟早会被打破（要接别的语言的服务、要接数据分析管道、要用现成的可观测性工具）。gob 更适合快速原型和纯内部的小工具。

什么时候该换掉 encoding/json？

先做量化，不要凭感觉。三步：① 用 pprof 看序列化在 CPU 火焰图里的占比；② 用真实数据（不是玩具数据）跑基准测试，对比标准库与候选库；③ 评估迁移成本（API 兼容性、边界行为差异、依赖增加）。经验阈值：占比 <5% 不换；5~20% 看情况（如果能无痛替换就换）；>20% 值得认真评估。另外要注意数据规模的影响：sonic 这类 SIMD 库对大 JSON（几 KB 以上）收益显著，但对几十字节的小对象可能反而更慢。所以「换库」不是一刀切，可以只在热点路径用快库，其他地方继续用标准库（jsoniter 的兼容模式让这种混用很容易）。最后提醒：换库有行为差异风险（如数字精度、HTML 转义、错误信息的处理），上线前必须跑全量回归。

Protobuf 的字段规则怎么演进才不踩坑？

三条铁律：① 字段编号一旦用过，永不复用——删字段要把编号放进 reserved，否则后来者复用这个编号会导致新旧数据互相解析错乱（这是最经典的 Protobuf 事故）；② 新增字段必须是 optional/带默认值，这样旧版本解析新数据时用默认值、新版本解析旧数据时也用默认值，双向兼容；③ 不要改字段类型（int32 → int64 在某些编码下兼容，但 string → bytes 这类改动会出问题）。另外两个实践建议：枚举的第一个值必须是 0（proto3 的默认值要求），以及用 reserved 明确标记废弃编号和名字（防止别人误用）。最后，wire 兼容性只是二进制层面——语义兼容（字段含义变了但类型没变）是更隐蔽的坑，要靠代码 review 和文档来保障。
