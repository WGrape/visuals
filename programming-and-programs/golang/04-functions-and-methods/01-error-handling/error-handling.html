错误是值，不是异常

Go 把错误当作普通返回值处理，显式 if err != nil 让失败路径一目了然。panic 只用于真正不可恢复的程序错误。

error 接口

只要实现 Error() string

标准库 error 就是接口；函数返回非 nil 表示出错。自定义错误只需提供 Error 方法。

type error interface { Error() string }

// 自定义
type MyErr struct{ Code int }
func (e *MyErr) Error() string { return fmt.Sprintf("code %d", e.Code) }

// 快速构造
err := errors.New("something wrong")
错误包装与判定

Wrap 保留链，Is/As 做判断

用 fmt.Errorf("...: %w", err) 包装能保留原始错误；errors.Is 比较根因，errors.As 提取特定类型。

if err != nil {
    return fmt.Errorf("read config: %w", err)
}

// 调用方
if errors.Is(err, os.ErrNotExist) { ... }

var my *MyErr
if errors.As(err, &my) { fmt.Println(my.Code) }
不要只打 err 字符串就当成新错误返回——会丢失类型信息，导致上层无法用 Is/As 判定根因。
panic：中断执行

栈展开到 recover 或进程退出

panic 会立即停止当前函数、运行已注册的 defer，并向上展开；若无人 recover，程序崩溃并打印栈。

⚠️ 不要用 panic 处理可预期的普通错误（如用户输入非法）。panic 应保留给「程序员 bug / 不可恢复状态」。
recover：捕获 panic

只能在 defer 中生效

recover 必须在 defer 函数里直接调用才有效，用于把 panic 转成 error，常见于服务器防止单请求拖垮整体。

func safe(f func()) (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("panic: %v", r)
        }
    }()
    f()
    return nil
}

错误处理的三层能力：判定、包装、携带信息

Go 的错误处理只有三件事：判断发生了什么、取出具体类型、保留调用链。掌握这三层，就能写出既清晰又可诊断的错误处理代码。

能力函数作用典型写法
判定errors.Is(err, target)判断链上是否有某个哨兵错误if errors.Is(err, sql.ErrNoRows)
取类型errors.As(err, &target)从链上取出某个具体错误类型取出自定义错误读字段
包装fmt.Errorf 加占位符加上下文同时保留原错误fmt.Errorf("read config: %%w", err)
解包errors.Unwrap(err)取下一层错误，通常不直接用由 Is 与 As 内部递归使用
合并errors.Join(a, b)把多个错误合成一个批量操作后统一返回
// 1) 哨兵错误：包级导出，供调用方比较 var ErrNotFound = errors.New("not found") func Find(id int) (*Item, error) { if id <= 0 { return nil, ErrNotFound } // ... } // 2) 调用方用 Is 判定，而不是比较字符串 if errors.Is(err, ErrNotFound) { // 处理未找到 } // 3) 中间层加上下文，用占位符保留原错误 func Load(id int) (*Item, error) { it, err := Find(id) if err != nil { return nil, fmt.Errorf("load item %%d: %%w", id, err) } return it, nil } // 4) 自定义错误类型，携带结构化信息 type OpError struct { Op string Path string Err error } func (e *OpError) Error() string { return e.Op + " " + e.Path + ": " + e.Err.Error() } // 关键：实现 Unwrap，让 Is 与 As 能穿透到内层 func (e *OpError) Unwrap() error { return e.Err } // 调用方取出具体类型，读结构化字段 var oe *OpError if errors.As(err, &oe) { log.Println("failed path:", oe.Path) }

注意最后那个 Unwrap 方法：自定义错误类型只有实现它，判定与取类型才能继续往下一层查找。少了它，包装链就断了。

错误该在哪一层处理：边界原则

底层：只加上下文，不做决策

越靠近错误发生的地方，越应该只做一件事：补充上下文后向上返回。它不知道调用方想重试还是降级，所以不适合在这里打日志或做业务决策。

顶层：统一处理，只处理一次

在程序的边界（HTTP 处理函数、命令行入口、任务调度入口）统一记录日志、转换成对外错误码、决定是否重试。同一个错误只应被处理一次，层层打日志会让排查变成噪音。

不要忽略错误忽略的错误会在最意想不到的地方变成别的故障
不要重复记录底层加上下文、顶层打日志，中间不要各打一次
对外不暴露内部细节顶层要转换成安全的对外描述
错误里带关键字段带上 id、路径、参数，排查时能省大量时间

panic 与 recover：什么时候该用

Go 的惯例是错误用于可预期的失败，panic 用于程序无法继续的情况。把 panic 当成异常处理来用，是初学者最常见的误用。

场景该用什么理由
文件不存在、网络超时error可预期的失败，调用方能处理
参数非法但来自外部error外部输入不可信，不该让程序崩
数组越界、nil 解引用panic（运行时自动触发）属于程序缺陷，应该暴露出来
初始化时就注定无法工作panic继续运行只会产生更诡异的错误
库内部不可恢复panic但公共接口边界应转成 error 返回
// 在 goroutine 入口加保护，避免一个 panic 拖垮整个进程 func safeGo(fn func()) { go func() { defer func() { if r := recover(); r != nil { log.Printf("panic recovered: %%v\n%%s", r, debug.Stack()) } }() fn() }() } // 三条硬规则： // 1) recover 必须在 defer 中直接调用，写在别的函数里无效 // 2) 只能恢复当前 goroutine 的 panic，子协程的 panic 无法被父协程捕获 // 3) 恢复后程序从 panic 点之后继续，状态可能不一致， // 通常只用于记录日志并让该协程安全退出，不要假装没发生过

深入自检：错误处理的六个问题

为什么每个 err 都要写一遍判断？

这是 Go 刻意的设计：让错误处理的路径显式出现在代码里，而不是像异常那样隐式跳转。代价是代码略长，好处是任何一处可能失败的地方都看得见。可以通过提前返回、把错误作为返回值的一部分来减少重复样板。

哨兵错误和自定义类型怎么选？

如果调用方只需要判断是不是这一类错误，用哨兵错误；如果需要携带额外信息（路径、字段、重试次数），用自定义类型并实现 Unwrap。两者也可以结合：类型里包一个哨兵错误。

包装时用哪个占位符有区别吗？

有本质区别。用于包装的占位符会把错误包进链里，之后可以追溯；而普通格式化只是把错误信息拼成字符串，原错误就丢失了，调用方再也无法判定。所以只要这个错误还可能被上层识别，就必须用包装占位符。

错误可以忽略吗？

不应该静默忽略。如果确实无法处理，至少要显式注释说明原因，或者记录到日志与指标里。最常见的反模式是写成下划线丢弃变量，这会掩盖真正的故障原因。

defer 里返回的错误怎么不丢？

关闭资源时的错误常常被忽略。正确做法是用命名返回值，在 defer 里判断关闭是否出错，如果原错误为空就用关闭错误覆盖它，否则记录日志。这样至少不会静默丢掉信息。

错误链太长会不会影响性能？

包装本身开销很小，但在极热的路径上频繁包装会产生较多小对象。一般业务不必在意；如果在每秒百万次的循环里，可以考虑只在边界处包装一次，而不是每一层都包装。

错误包装的黄金规则：每层只加自己的上下文，不要重复。错误链应该是 处理订单失败: 查询用户: dial tcp 10.0.0.1:3306: connect: connection refused，而不是每层都写一遍底层错误。判断时用 errors.Is(err, sql.ErrNoRows)，不要用字符串匹配（错误消息会变）。

代码模板

// 1) 自定义错误类型（带码与上下文）
type AppError struct {
    Code    int
    Message string
    Err     error        // 底层错误，用于 Unwrap
}

func (e *AppError) Error() string {
    if e.Err != nil { return fmt.Sprintf("[%d] %s: %v", e.Code, e.Message, e.Err) }
    return fmt.Sprintf("[%d] %s", e.Code, e.Message)
}
func (e *AppError) Unwrap() error { return e.Err }       // 关键：让 errors.Is/As 能穿透

// 2) 判断与提取
var ErrNotFound = errors.New("not found")

func Get(id int64) (*User, error) {
    u, err := db.Query(id)
    if errors.Is(err, sql.ErrNoRows) {
        return nil, fmt.Errorf("user %d: %w", id, ErrNotFound)   // 包装后仍可用 Is 判断
    }
    if err != nil {
        return nil, fmt.Errorf("query user %d: %w", id, err)
    }
    return u, nil
}

// 调用方
if errors.Is(err, ErrNotFound) { http.Error(w, "not found", 404); return }

var pathErr *os.PathError
if errors.As(err, &pathErr) { log.Printf("path=%s op=%s", pathErr.Path, pathErr.Op) }
// 3) defer 里的错误也要处理（最常被忽略）
func copyFile(dst, src string) (err error) {
    s, err := os.Open(src)
    if err != nil { return err }
    defer s.Close()                        // 只读文件，Close 错误可忽略

    d, err := os.Create(dst)
    if err != nil { return err }
    defer func() {
        if cerr := d.Close(); cerr != nil && err == nil {
            err = cerr                     // 写入文件，Close 可能报 flush 失败
        }
    }()
    _, err = io.Copy(d, s)
    return err                             // 命名返回值，defer 能改
}

// 4) 不要忽略错误（用 _ 前先想清楚）
n, _ := w.Write(b)                          // 忽略错误前要确认真的无所谓
// lint 工具：errcheck 能扫出所有被忽略的错误

// 5) panic 只用于「不可能发生」的情况
// ❌ 不要：if err != nil { panic(err) }     // 库代码绝对不能 panic
// ✅ 可以：初始化阶段的配置错误（fail fast）
// 服务入口必须有 recover，避免一个 panic 打挂整个进程

排障清单

症状原因处理
errors.Is 判断不出来用了 %v 而不是 %w改成 %w；错误链断了就找不回
错误信息重复堆叠每层都加了完整描述每层只加自己的上下文；最底层保留原始错误
nil 判断失效返回了 typed nil（(*MyErr)(nil)）不要用具体类型的 nil 作为 error 返回

panic 打挂服务库代码 panic 或没 recoverHTTP 服务加 recover 中间件；库代码返回 error

Go 1.13 之后的标准做法：底层用哨兵错误或自定义类型，中间层用 fmt.Errorf("...: %w", err) 加上下文，上层用 errors.Is/errors.As 判断。永远不要用 err.Error() == "xxx" 或字符串包含判断。

Go 代码

import (
    "errors"
    "fmt"
)

var ErrNotFound = errors.New("not found")

// —— 1) 自定义错误类型（带上下文）——
type ValidationError struct {
    Field  string
    Reason string
}
func (e *ValidationError) Error() string {
    return fmt.Sprintf("field %s: %s", e.Field, e.Reason)
}

// —— 2) 错误包装：用 %w 保留错误链 ——
func GetUser(id int) (*User, error) {
    u, err := db.Query(id)
    if err != nil {
        return nil, fmt.Errorf("查询用户 %d 失败: %w", id, err)
        //                                            ^ %w 是关键
    }
    return u, nil
}

// —— 3) 判定：errors.Is（会沿错误链向上找）——
if errors.Is(err, ErrNotFound) {
    // 处理未找到（即使 err 被包装了多层也能匹配）
}

// —— 4) 取出具体类型：errors.As ——
var ve *ValidationError
if errors.As(err, &ve) {
    fmt.Println("校验失败的字段:", ve.Field)
}

// —— 5) 多个错误聚合（Go 1.20+）——
err = errors.Join(err1, err2, err3)
//   errors.Is / As 会对每个错误都尝试匹配

// —— 6) panic 的正确用法：只在「程序无法继续」时 ——
func MustParse(s string) *Template {
    t, err := Parse(s)
    if err != nil {
        panic(fmt.Sprintf("模板解析失败（这是配置错误，程序无法启动）: %v", err))
    }
    return t
}
//   MustXxx 系列约定：失败即 panic，用于【初始化阶段】

// —— 7) recover 必须在 defer 里，且只能恢复【当前 goroutine】——
func safeRun() {
    defer func() {
        if r := recover(); r != nil {
            log.Printf("recovered: %v", r)
            // 【注意】recover 后函数返回，不会回到 panic 点继续执行
        }
    }()
    risky()
}

// —— 8) 子 goroutine 的 panic 无法被外层 recover ——
go func() {
    defer func() { recover() }()   // 【必须在 goroutine 内部 defer】
    risky()
}()

最关键的一条：用 %w 而不是 %v 包装错误。%v 会切断错误链，导致上层的 errors.Is/As 全部失效。

进阶层 · 排障与性能清单

  • errors.Is 匹配不上 → 中间某一层用了 %v 而不是 %w 包装，错误链断了。全链路检查。
  • 错误信息只有一句 connection refused，不知道是哪一步 → 没有包装上下文。每一层都要加「我在做什么」的信息。
  • 子 goroutine panic 导致整个进程崩溃 → recover 只对本 goroutine 有效。每个 goroutine 都要有自己的 defer recover。这是服务稳定性的常见杀手。
  • defer 里的错误被吞掉 → defer f.Close() 的错误没人处理。正确：defer func() { if err := f.Close(); err != nil { log... } }()。
  • 错误被重复记录 → 底层记一次日志、上层又记一次，日志里同一错误出现 3~5 次。约定：只在「处理错误」的地方记日志，只向上传递的地方不要记。
  • 忽略错误 → _ = doSomething()。除非你明确知道这个错误无关紧要，否则至少要记日志。用 golangci-lint 的 errcheck 能自动检查。
  • panic 用于业务错误 → 会导致服务崩溃。业务错误必须返回 error。panic 只用于「程序逻辑上不可能到达」的情况（如配置缺失、初始化失败）。
  • 错误创建的开销：fmt.Errorf 涉及格式化，比 errors.New 慢（约 几百 ns vs 几十 ns）。在热路径上预先定义错误变量：var ErrXxx = errors.New(...)，而不是每次 fmt.Errorf。
  • 错误字符串拼接进日志太慢 → 高频路径上 log.Errorf("%v", err) 会触发格式化。可以只在真正要输出时格式化。
做法开销适用

fmt.Errorf~200~500ns需要动态上下文
