压测通用方案：先问问题，再给负载

压测不是把并发数调到最大，而是在明确的工作负载和服务目标下，找到可复现、可持续且有安全余量的工作点。

范围先行

只对自有或明确授权的隔离环境测试；明确服务负责人、允许时段、目标主机、共享依赖与停止阈值。本文命令仅作本机教学示例，不对任何系统发起负载。

一、写下要回答的问题

  • 容量：某版本、某请求组合在成功率和 P99 达标时，能持续完成多少业务请求？
  • 回归：相同环境、数据、负载下，新旧版本的成功吞吐与尾延迟是否变化？
  • 瓶颈：首先饱和的是压测机、网关、应用、数据库还是某个外部依赖？

定义测试对象（单实例/集群、接口/事务）、数据集、请求比例、认证与缓存命中情况，以及 SLO 的窗口和分母。容量评估课解释为什么单一峰值 QPS 不足以回答这些问题。

二、选负载模型，而不只是选工具

闭环：固定并发

每个请求完成后才补下一个。ab 的 -c 是并发请求数；wrk 常用固定连接数施压。服务变慢时，发出速率可能随之降低，导致过载被掩盖。

开环：固定到达率

按照计划的速率发起请求，不等前一批完成；适合模拟外部独立到达，但需有界队列和明确停止条件。ab、普通 wrk 命令不是固定到达率发生器。

两种模型回答不同问题，不应把固定连接数/并发数当作固定 QPS。混合读写与多接口时还须固定流量占比和数据大小。

三、按阶段执行并留证据

  1. 空载校验：确认接口返回正确、业务成功条件和埋点齐备；在小流量下测基线，排除压测机与网络瓶颈。
  2. 预热：预热连接、JIT、缓存和连接池，记录预热时长；冷启动如属目标场景，则单独测试。
  3. 分档：从低负载开始，每档按约定时长观察并重复；负载间隔让队列和资源恢复，持续采集客户端与服务端数据。
  4. 停止：触发预设错误率、P99、排队增速或资源阈值立即停止加压；保留原始输出与时间戳。
  5. 复验：在相同版本、配置、数据和流量组合下重复，注明变更因素与波动范围。

下一步按准备清单冻结环境，再用结果指标判断哪一档可持续。

四、写出可复现的报告

记录测试目标及授权范围、客户端/服务端规格、版本与参数、测试时段、预热/正式窗口、并发或到达模型、请求体、成功判据、样本数、错误与超时处理、各档成功 QPS 和 P50/P95/P99，以及 CPU/内存/网络/队列等证据。结论写作“在本配置与负载下满足 SLO 的工作点”，而不是无条件的“系统最大 QPS”。

路线：环境与资源准备 → 结果和指标 → 注意事项 → ab / wrk。

五种压测，目标各不相同

「压测」不是一个动作，而是五类目标不同的测试：基准（求基线、比版本）、负载（验证目标容量是否达标）、压力（找极限与拐点）、稳定性（长跑查泄漏）、破坏性（注入故障验韧性）。混在一起做，什么都测不清楚。

基准测试低负载下测基线，用于版本对比
负载测试在目标压力下验证指标是否达标
压力测试不断加压直到性能明显恶化，找拐点
稳定性测试长时间（数小时到数天）运行，查泄漏与退化
破坏性测试注入故障（宕机、网络分区），验证降级与恢复
容量测试确定满足目标所需的资源量

执行与结果解读

① 标准流程

  • 准备：环境、数据、挡板、监控、通知。
  • 预热：低流量跑 5-10 分钟。
  • 基准：低负载记录基线。
  • 阶梯：逐级加压并记录。
  • 分析：找拐点、定位瓶颈。
  • 复测：优化后再测，验证收益。

② 怎么找拐点

  • 画「QPS-延迟」曲线：延迟开始陡升的那点。
  • 同时看错误率与资源使用率。
  • 拐点通常伴随某个资源达到 80%+ 或池耗尽。
  • 拐点 QPS 才是可承诺的容量（再打折留余量）。

③ 结果要输出什么

  • 结论先行：能否达标，余量多少。
  • 关键数据：拐点 QPS、P50/P99、错误率、资源水位。
  • 瓶颈定位：哪个资源/哪个调用。
  • 容量模型：QPS 与机器数的关系。
  • 风险与建议：需要优化或扩容的点。

④ 常见误读

  • 把「最大 QPS」当容量：那时延迟已不可接受。
  • 忽略错误率：超时返回也算「完成」会虚增吞吐。
  • 只测单接口：混合负载下的资源竞争没体现。
  • 不复测：优化后不验证等于没优化。
  • 把压测当一次性活动：应该常态化做回归。

深入自检

压测应该控制并发还是控制 QPS？

取决于目的：验证「能否支撑 X QPS」用固定 QPS（到达率）模式，因为这才对应真实流量目标；探索系统容量上限用阶梯并发，观察延迟何时恶化。恒定并发模式有个陷阱：当系统变慢时，实际 QPS 会自动下降，看起来「没崩」但实际已不可用。

为什么压测要先预热？

因为系统启动初期有大量一次性成本：JIT 编译、类加载、连接池建立、缓存填充、数据库连接认证、DNS 解析等。不预热会把这些成本算进稳态性能，得出过于悲观的结论。通常预热 5-10 分钟或直到指标稳定。

稳定性测试要关注什么？

关注随时间累积的问题：内存泄漏（RSS 单调上涨）、连接/文件句柄泄漏、磁盘与日志膨胀、缓存无限增长、定时任务堆积、GC 频率变化、以及长时间运行后的性能退化（如碎片、统计信息过期）。建议 8 小时以上，并对比首尾指标。

破坏性测试（混沌工程）怎么做才安全？

原则：先有假设再实验、从小范围开始、随时可终止、在生产要有熔断开关。常见实验：杀实例、网络延迟/丢包注入、CPU 打满、磁盘 IO 打满、依赖超时。关键不是「搞坏系统」，而是验证「故障时系统行为符合预期且能恢复」。

压测中发现瓶颈后应该怎么办？

按「定位 → 优化 → 复测」循环：先用 Trace/火焰图确认瓶颈，再做针对性优化（索引、缓存、批量、异步、算法），然后复测验证收益。切忌一次改多个点，那样分不清哪个改动有效。每轮只改一处、只测一处。

没有压测环境怎么办？

可选方案：① 影子流量（复制生产流量到影子服务，写操作隔离）；② 生产限时限量压测（低峰期、逐步加压、随时可停）；③ 单实例压测 + 系数外推（误差较大，需谨慎）；④ 用历史峰值数据推算容量模型。无论哪种，都要明确标注结论的不确定性。
