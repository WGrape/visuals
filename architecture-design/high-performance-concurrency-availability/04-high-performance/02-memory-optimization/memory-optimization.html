大对象与缓存策略

大对象优先用流式/分块处理，避免一次性载入；缓存要有上限与淘汰（LRU/TTL），否则会从「省时间」变成「吃内存」。

问题 1
如何降低服务的常驻内存？

先取样看对象分布；删掉无限增长的缓存、给缓存加 TTL/LRU；复用缓冲、预分配切片；大对象用流式处理；必要时换更紧凑的序列化（如 protobuf 替代 JSON）。

问题 2
对象池适合什么场景？

适合高频、短生命周期、可安全复用的对象（缓冲区、临时结构体）。但池子本身有上限，复用前必须重置状态，否则会串数据。

问题 3
零拷贝为什么省内存又省 CPU？

它减少用户态与内核态之间的数据复制，少一次缓冲分配，也少一次拷贝带来的 CPU 与缓存开销。典型如 sendfile、mmap、splice。

问题 4
GC 太频繁和内存有什么关系？

分配速率越高，GC 触发越频繁，STW 与回收成本越高。降低分配量（复用、预分配）能同时减小内存峰值与 GC 压力。

优化的顺序：先减少「不必要」，再优化「必要」

内存优化最容易犯的错是过早做底层优化（对象布局、压缩指针），而忽略了真正的大头：缓存无上限、重复数据、全量加载、无界队列。正确顺序是：先砍掉不必要的内存占用，再优化必要部分的表示方式。

语言层面的要点

① GC 语言（Java/Go）

  • 堆大小要设上限，并留余量（-Xmx、GOMEMLIMIT）。
  • 减少临时对象：复用缓冲区、避免循环内创建。
  • 注意堆外：DirectBuffer、JNI、mmap 不受 GC 管理。
  • 关注 GC 频率与停顿（P99 停顿比吞吐更重要）。
  • Go 特别要防止 goroutine 泄漏与无界 channel。

② C/C++

  • 配对分配与释放；优先 RAII/智能指针。
  • 用对象池与内存池减少碎片。
  • 换用 jemalloc/tcmalloc 改善多线程分配。
  • 工具：ASan/Valgrind 查越界与泄漏。

③ 数据结构选择

  • 大量小对象 → 用数组/结构体数组（SoA）替代对象数组。
  • HashMap 要注意负载因子与初始容量（避免频繁扩容）。
  • 稀疏数据用稀疏结构或压缩位图（RoaringBitmap）。
  • 大表列式存储 + 字典编码，节省数倍内存。

④ 运行时配置

  • JVM：选择合适的 GC（G1/ZGC）、设置 MaxDirectMemorySize。
  • Go：GOGC 调节 GC 目标、GOMEMLIMIT 限制上限。
  • 线程栈：-Xss 或 ulimit -s，避免过多线程。
  • 容器：所有上限都要显式设置，不要依赖宿主探测。

⑤ 验证与回归

  • 优化前后用同一负载对比 RSS/PSS 与 GC 指标。
  • 做长时间稳定性测试，确认无泄漏。
  • 关注性能是否倒退（压缩/紧凑可能增加 CPU）。
  • 把内存指标纳入发布门禁。

深入自检

为什么加了缓存反而内存爆了？

因为缓存没有上限或没有淘汰策略，本质上变成了「内存泄漏」。任何缓存都要回答三个问题：最多占多少（容量上限）、什么条件下淘汰（LRU/LFU/TTL）、以及是否需要按大小而非条数限制（防止大对象撑爆）。用条数限制时尤其要小心大小不均的对象。

对象池一定更快吗？

不一定。对象池减少分配与 GC 压力，但引入了归还、重置、并发管理的开销，而且池本身可能成为内存占用大头（池太大）或瓶颈（池太小）。现代 JVM/Go 的分配器已经很快，小对象通常不需要池；真正值得池化的是大对象、昂贵资源（连接、线程）与高频临时缓冲。

如何降低 GC 停顿？

思路有四个：① 减少分配量（复用、紧凑、避免临时对象）；② 控制堆大小（堆越大单次回收成本越高，但太小会频繁 GC，要平衡）；③ 选合适的收集器（G1/ZGC/Shenandoah 面向低延迟）；④ 关注晋升与老年代增长（对象过早晋升会加速老年代膨胀）。同时要监控 P99 停顿而不是平均停顿。

堆外内存有什么坑？

三个主要坑：① 不受 GC 管理，忘记释放就是泄漏；② 排查困难（工具链不完善，需要 pmap/NMT）；③ 分配失败时表现为 OOM 而不是 GC 触发。使用堆外要配套：明确的生命周期管理、容量上限配置、监控指标、以及压测验证。Netty 的 DirectBuffer 泄漏是最常见的例子。

大表/大集合怎么处理最省内存？

按场景选择：① 列式存储（只加载需要的列）；② 字典编码（重复字符串存 ID）；③ 压缩位图（RoaringBitmap 做集合运算）；④ 分页/流式处理（不全量加载）；⑤ 放到堆外或专门的缓存服务。关键是避免「把全量数据变成对象图」——对象头与指针的开销往往比数据本身大几倍。

内存优化怎么验证有效？

要同时看三个指标：① RSS/PSS 是否下降（真实物理内存）；② 延迟与吞吐是否不退化（紧凑/压缩可能增加 CPU）；③ 长时间运行是否稳定（无泄漏、无 GC 恶化）。做法是同一负载下 A/B 对比，并跑 8 小时以上的稳定性测试。只改一处、只测一处方能归因。
