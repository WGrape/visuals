先建立直觉：两套监控，盯的对象不同

服务可观测性盯的是「系统」：CPU、内存、QPS、错误率、响应时间——它保证服务不挂。

数据可观测性盯的是「数据本身」：行数对不对、空值率有没有飙升、分布有没有漂移、有没有按时产出——它保证数据可信。

关键区别：服务正常 ≠ 数据正确。一个 ETL 任务可以成功执行、不报任何错，但因为上游逻辑变更，产出的每一行的金额都是错的。传统服务监控完全发现不了这类问题——这正是数据可观测性存在的理由。

四支柱

监控什么：三个层次

层次监控对象典型指标
管线健康任务是否按时成功任务成功率、运行时长、SLA 达成率、积压量
数据质量产出的数据是否可信行数波动、空值率、唯一值数、分布漂移、跨表一致性
资源成本资源消耗是否异常计算资源用量、存储增长、单任务成本、扫描量

与数据质量的关系

数据质量数据可观测性
关注点数据是否符合标准能否快速发现并定位不符合标准的情况
手段定义规则、校验、清洗采集指标、建监控、设告警、做溯源
关系质量规则是输入，可观测性是承载这些规则的运行时系统
一句话：数据质量定义「什么是对的」，数据可观测性保证「不对的时候你能马上知道并找到原因」。两者是同一个体系的两面。

落地路径

  1. 先监控管线健康（任务成不成功、按时没按时）——这是最基础也最优先的，否则连「数据有没有产出」都不知道；
  2. 再补数据质量监控（行数、空值率、分布漂移）；
  3. 再接入血缘，实现影响分析；
  4. 最后做告警治理——分级、路由到 owner、避免告警疲劳。
告警疲劳是最大的落地障碍。如果每天收到几百条告警，人会本能地全部忽略，等于没有监控。原则：① 告警要可行动（收到就知道该做什么）；② 要分级（严重问题才打电话，轻微问题发群消息）；③ 定期复盘与裁剪，删掉那些「永远被忽略」的告警。

🎯 面试问答

Q：数据可观测性只是加监控吗？
A：远不止。它是「监控 + 质量 + 血缘 + 告警」的闭环：监控负责发现，日志负责定位，血缘负责评估影响面，告警负责通知到人。只加监控而不接血缘，会出现「知道某张表出问题了，但不知道该通知谁」；只加监控而不设合理告警，会淹没在噪声里。目标是让数据问题从「被动发现」变成「主动感知」。

Q：先建监控还是先建质量规则？
A：先建管线监控（任务是否按时成功）。这是最基础的一层——如果连「数据有没有按时产出」都不知道，讨论数据对不对毫无意义。很多团队的数据事故其实是「任务挂了但没人知道，报表一直展示昨天的数据」。管线监控跑通后，再逐步加行数、空值率、分布等质量维度。

Q：为什么任务成功了数据还是错的？
A：因为「任务成功」只表示代码没抛异常，不代表产出正确。典型场景：① 上游逻辑变更（如状态枚举值改了），下游 SQL 没适配，算出的结果静默错误；② 上游数据本身就有问题（埋点错误），下游忠实加工；③ 分区写错，数据写到了错误的日期分区。这类问题只有「数据层监控」能发现——比如行数骤降、空值率飙升、分布漂移。这正是数据可观测性的核心价值。

Q：怎么避免告警疲劳？
A：三个手段：① 分级——严重问题（核心表无产出）电话/短信，一般问题（行数波动 20%）群消息，轻微问题只记录看板；② 路由——告警直接通知表的 owner，而不是广播给所有人；③ 收敛——同一根因的多个告警合并成一条（如上游失败导致下游 10 个任务失败，只报上游那一条）。另外要定期复盘：把「长期被忽略」的告警阈值调松或直接关掉。

数据可观测性五维度

维度回答的问题典型检测手段告警方式
新鲜度数据有多旧？max(更新时间) 与当前的差值超过 SLA 阈值告警
体量数据量正常吗？行数/字节数与历史同比环比突降 50% 或突增 10×告警
分布值域合理吗？均值/分位数/NULL 率漂移分布距离超阈值告警
模式结构变了吗？字段名/类型/枚举值比对结构变更即告警
血缘影响谁？表级依赖图上游故障自动通知下游

与数据质量的区别：数据质量是定义规则并校验（如“金额必须 > 0”）；可观测性是不预设规则、通过统计异常自动发现。前者能抓住已知问题，后者能发现你没想到会出的问题——比如某个渠道的埋点静默失效导致该渠道数据量归零。

落地：关键指标与阈值

检测项计算方式建议阈值
表行数漂移(今日行数 - 近7日中位数) / 中位数绝对值 > 30% 告警
NULL 率突变某列 NULL 占比的日环比绝对变化 > 5 个百分点
唯一值数下降某维度列的 distinct 数下降 > 20%（可能丢了维度）
数值分布漂移PSI 或 JS 散度PSI > 0.25 显著漂移
数据延迟now() - max(event_time)超过 SLA（如 > 2 小时）
分区缺失预期分区是否存在任一缺失即告警

PSI 实现

import numpy as np

def psi(expected, actual, buckets=10):
    '''群体稳定性指标 PSI，判断两个分布是否发生漂移'''
    def hist(x):
        # 用 expected 的分位切桶，保证两分布可比
        edges = np.percentile(expected, np.linspace(0, 100, buckets + 1))
        edges[0], edges[-1] = -np.inf, np.inf
        cnt, _ = np.histogram(x, bins=edges)
        return np.clip(cnt / len(x), 1e-6, None)   # 防除零
    e, a = hist(expected), hist(actual)
    return float(np.sum((a - e) * np.log(a / e)))

# 判读标准（业界通用）
#   PSI < 0.10   无显著变化
#   0.10 ~ 0.25  需关注
#   > 0.25       显著漂移，必须排查
# 用途：监控特征分布、模型打分分布，是数据/模型监控的核心指标

告警治理：避免告警疲劳

最大的落地障碍不是技术，而是告警太多导致无人看。

原则做法效果
分级P0（阻断下游）/ P1（需当日处理）/ P2（观察）只有 P0 才打电话
抑制上游故障时不重复报下游所有表告警量降 一个数量级
收敛同一根因的多条告警合并成一条避免刷屏
认领每条告警有明确 owner避免无人处理
复盘统计误报率，持续调阈值误报率应 < 20%

判据：如果一个数据团队每天收到 > 50 条数据告警，基本等于没有告警——大家会自动忽略。目标是把日均有效告警压到 5 条以内。

自检 Q&A

Q：数据质量监控和可观测性要不要都做？

A：要，但分工不同。质量规则（唯一性、非空、外键）用于守住关键底线，比如金额不能为负——这类必须硬校验，失败就阻断。可观测性用于发现未知异常，比如某个埋点静默失效。只做前者会漏掉没写规则的问题；只做后者，关键字段的硬错误又可能被淹没在统计噪声里。

Q：PSI 和 KS 检验怎么选？

A：PSI 更适合工程监控。它给出单一数值且有公认阈值（0.1/0.25），便于设告警；KS 检验给出 p 值，但样本量大时任何微小差异都显著（大样本下 p 值几乎总是 < 0.05），不适合直接做告警阈值。所以线上监控常用 PSI，做严谨的统计推断时才用 KS。

Q：怎么快速定位数据异常的根因？

A：沿血缘图向上游追溯，并做维度下钻。标准流程：① 确认异常指标与影响范围（哪张表、哪个分区）；② 看上游输入是否同样异常（区分是上游传入还是本任务算错）；③ 按关键维度下钻（渠道、地区、版本），定位是哪个子集的贡献——总量正常但某个子集归零是最常见的隐藏故障。

Q：表结构变更（加字段/改类型）怎么处理？

A：加字段是安全的，改类型和删字段是破坏性的。监控上：加字段只需更新模式基线；改类型要检查下游所有读取方是否兼容（如 int → string 会让数值比较静默失效）；删字段必须先在血缘图里确认无下游引用。实践建议是用 schema registry 管理变更，把结构变更作为一等事件纳入监控，而不是靠人工通知。
