云平台架构 / 发布与部署

云资源的声明式交付

VPC、负载均衡、实例组和权限也是上线的一部分；基础设施即代码让它们的变化可评审、可追踪。

声明式模型 状态与漂移 安全边界 发布协同

01 / 先描述目标状态，再查看差异

基础设施即代码（IaC）把云资源的目标状态写成版本化配置：网络、路由、实例组、负载均衡和访问权限一起评审。工具比较期望状态与实际状态，产出变更计划；确认后才执行。它不是把控制台点击步骤搬进脚本。

  1. 声明配置记录两 AZ 的子网、私网应用实例组与负载均衡。
  2. 预览计划列出新增、修改和删除；重点核对是否会替换资源或扩大公网暴露面。
  3. 审批资源负责人确认成本、配额、依赖和影响窗口。
  4. 应用在受控环境执行；再检查真实资源与计划是否一致。

应用制品部署与云资源变更的频率不同：调整负载均衡权重可能由发布流程控制，改子网与数据库拓扑则应走更严格的基础设施评审。

02 / 状态文件与漂移是两类不同风险

状态文件

记录资源标识与依赖关系；远端存储应启用加密、访问限制、版本保护和并发锁，防止两个作业同时修改同一环境。状态可能含敏感值，不应提交到公开仓库。

配置漂移

有人在控制台手动改了安全组或实例规格，代码与实际环境便不一致。定期执行只读预览、核对变更来源；紧急修复之后要回写声明文件。

“计划无差异”只说明管理范围内的配置与状态一致，不代表外部依赖或业务流量已健康；发布后仍要验证服务行为。

03 / 生产环境的三道护栏

护栏具体做法挡住什么问题
环境隔离生产与测试使用独立状态、账户/项目及受控凭据误把测试变更应用到生产
最小权限流水线身份按资源和操作授权，秘密由专用服务下发制品构建任务顺手改动整个云账号
危险变更审查对数据库删除、VPC 替换、入口开放进行人工确认和备份校验一次计划清空持久数据或扩大攻击面

IaC 的“回滚”不是无条件套用旧配置：删除资源后再创建可能换地址或丢状态。先查看计划、备份和资源依赖，必要时采取前向修复。

04 / 与应用发布如何配合

要把订单 API 扩到第二个 AZ：先用 IaC 增加子网和实例组、调整负载均衡目标及路由；计划确认不替换数据库 → 验证新 AZ 实例可达且已就绪 → 交付流水线部署同一制品摘要 → 小比例引流 → 演练单 AZ 故障 → 最后更新运行手册与成本基线。

这里的顺序是先建立能承接流量的资源，再放流量；撤销时通常反向操作，但须先排空请求和后台任务，不能直接删除承载中的资源。云原生的声明式交付概念可继续阅读 IaC 与声明式 API。

一句话：把云资源变更纳入交付闭环，才能追溯“代码没变、系统为什么坏了”。
