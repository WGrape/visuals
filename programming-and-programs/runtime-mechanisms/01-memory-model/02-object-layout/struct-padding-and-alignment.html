01对齐规则到底在对齐什么

\n
// Go 里三种典型类型的大小与对齐（64 位平台）\n//   bool   : size=1  align=1\n//   int32  : size=4  align=4\n//   int64  : size=8  align=8\n//   *T     : size=8  align=8    指针一律 8 字节\n//   string : size=16 align=8    指针 8 + 长度 8\n//   []T    : size=24 align=8    指针 8 + 长度 8 + 容量 8\n//   map    : size=8  align=8    本身就是指针\n//   struct{}: size=0 align=1    特殊：空结构体不占空间\n\n// 规则一：字段起始地址必须是自身对齐数的整数倍 → 不足就插 padding\n// 规则二：结构体自身对齐数 = 所有字段中最大的对齐数\n// 规则三：结构体总大小必须向上补齐到自身对齐数的整数倍\n\ntype Bad struct {\n\tFlag bool   // offset 0，占 1 字节\n\tID   int64  // offset 8（要对齐到 8）→ 0~7 之间有 7 字节 padding\n\tNum  int32  // offset 16，占 4 字节\n}                 // 总大小 24：末尾再补 4 字节到 8 的倍数\n\ntype Good struct {\n\tID   int64  // offset 0\n\tNum  int32  // offset 8\n\tFlag bool   // offset 12\n}                 // 总大小 16：末尾补 3 字节\n\n// 验证（不要靠猜，直接打印）\nimport (\n\t"fmt"\n\t"unsafe"\n)\nfmt.Println(unsafe.Sizeof(Bad{}), unsafe.Alignof(Bad{}))   // 24 8\nfmt.Println(unsafe.Sizeof(Good{}), unsafe.Alignof(Good{})) // 16 8
类型（64 位）sizealign备注
bool11放最后最省
int8 / uint811同上
int1622成对放一起
int32 / float3244跟在 8 字节后面
int64 / float6488排最前面
指针 / map / chan88同为 8 字节
string168指针+长度
slice248指针+长度+容量
interface{}168类型指针+数据指针
要点：对齐不是浪费：未按对齐访问的内存，在某些架构上会触发多次读取甚至异常。填充换来的是单次访问完成，这是硬件要求。

  • 省内存的三个量级：① 字段重排（省填充）；② 用更小的类型（int64 → int32，前提是值域够）；③ 去掉指针（指针 8 字节 + 指向的对象另算）。
    • \n
  • 收益什么时候才明显：对象数量 × 节省字节。一个 1000 万条的记录，每条省 8 字节 = 省 80 MB，还能少一次 cache miss。
    • \n
  • slice of struct vs slice of pointer：[]T 连续存储、遍历友好；[]*T 每个元素多一次跳转，但元素大时移动便宜。
    • \n
  • 别过度优化：只有被大量创建的类型才值得调；一个程序里只有几个热类型需要重排。

03缓存行与 false sharing

\n
// 缓存行通常是 64 字节：两个无关变量落在同一行，会互相拖慢\ntype Shared struct {\n\tA int64 // 被 goroutine 1 疯狂写\n\tB int64 // 被 goroutine 2 疯狂写\n}   // A、B 相邻，大概率在同一缓存行 → 伪共享\n\n// 修法：按缓存行填充（Go 里用空数组占位）\ntype Padded struct {\n\tA int64\n\t_ [56]byte // 8 + 56 = 64，占满一行\n\tB int64\n\t_ [56]byte\n}\n\n// 验证：两个 goroutine 各写各的字段，对比耗时\nfunc BenchmarkShared(b *testing.B) {\n\tvar s Shared\n\tb.RunParallel(func(pb *testing.PB) {\n\t\tfor pb.Next() {\n\t\t\ts.A++ // 与 s.B 互相使对方的缓存行失效\n\t\t}\n\t})\n}
现象判断依据处理
多核下加得越多反而越慢核数增加吞吐不升反降查是否伪共享，加填充
相邻字段被不同线程写字段在同一缓存行按 64 字节对齐隔开
计数器性能差全局计数器被所有核争改成分片计数（每核一份）后汇总
atomic 操作很慢同一行的 cache line 反复失效分片 + 填充
要点：false sharing 的典型量级：修复后多线程自增吞吐可以提升数倍。但它只在「多核高频写相邻变量」时才出现，单线程场景不用管。

04什么时候不要重排

\n
问：字段重排会不会影响可读性？

会。语义相关的字段放一起更好读，按大小排会打散语义。折中：只在确认是大批量创建的热类型上重排，并留注释说明原因。

问：为什么有时候加了字段大小没变？

新增字段正好填进了原本的 padding 里。比如 int64 + int32（16 B，含 4 B 填充）再加一个 int32，大小仍是 16 —— 填充被利用了。

问：要不要为了对齐把 int32 都改成 int64？

不要。改大只会更占内存；对齐的收益来自「减少填充」，而不是「统一字段宽度」。统一宽度反而会迫使小字段也占 8 字节。
