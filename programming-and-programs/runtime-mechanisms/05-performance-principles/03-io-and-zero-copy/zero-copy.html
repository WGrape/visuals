零拷贝：文件传输为什么能少几次内存拷贝

把一个文件从磁盘发到网络，传统写法要在内核态与用户态之间来回拷贝四五次。零拷贝不是「一次拷贝都不做」，而是「去掉不必要的 CPU 拷贝与上下文切换」，把数据搬运交给 DMA 和内核。

先建立直觉：一次普通文件发送发生了什么 日常代码 read(file)+write(socket) 看起来只有两步，底层却要把数据在「内核缓冲区」和「用户缓冲区」之间反复搬。每一次搬移都消耗 CPU 周期，且每次系统调用都要在用户态和内核态之间切换。数据量越大、请求越频繁，这些拷贝的占比越高，CPU 反而比磁盘/网卡更先成为瓶颈。

所谓「拷贝次数」指 CPU 参与的数据复制次数（DMA 在设备与内核缓冲区间的搬运不占 CPU，通常不算在内）。零拷贝的目标，就是把这些 CPU 拷贝尽可能压缩到 0 或 1 次。

传统路径：4 次拷贝 + 4 次上下文切换 假设网卡与磁盘都走 DMA：① 磁盘 DMA 把数据读入内核页缓存；② CPU 把数据从内核页缓存拷贝到用户缓冲区（read 返回）；③ CPU 再把用户缓冲区的数据拷贝回内核 socket 缓冲区（write 调用）；④ 网卡 DMA 从 socket 缓冲区发出。其中 ②③ 两次 CPU 拷贝完全是为了「让应用程序看一眼数据」，多数场景其实看都不看就转发了。

图：②③ 两次 CPU 拷贝是零拷贝要消除的主要对象。

方案一：mmap + write 用 mmap 把内核页缓存直接映射到用户空间，省掉「内核→用户」那一次拷贝；应用 write 时再把页缓存拷到 socket 缓冲区。拷贝次数从 4 降到 3，但仍需一次 CPU 拷贝和一次系统调用。适合「需要读取并加工数据再发送」的场景。

注意 mmap 在小文件、随机写场景收益有限，且映射区过大可能触发额外的页表与缺页开销。

方案二：sendfile（最常用的零拷贝） sendfile(out_fd, in_fd, ...) 让数据完全在内核态内流动：页缓存 → socket 缓冲区，由内核完成，应用不参与数据搬运。在支持「DMA 收集拷贝」的网卡上，连「页缓存→socket 缓冲区」这次 CPU 拷贝也能省掉——网卡直接从页缓存 DMA 取数，真正做到0 次 CPU 拷贝。这是静态文件服务器、消息中间件高吞吐传输的基石。

图：sendfile 让数据在内核内直达，应用只发一个系统调用。

方案三：splice / 管道中转 splice 通过内核管道（pipe）在两个文件描述符间移动数据，同样避免用户态拷贝，且能处理「两个都是文件描述符」的通用场景（不只是 socket）。它移动的是内核里的页面引用而非逐字节拷贝，适合在用户态完全不参与时做高效转发。

与 sendfile 相比，splice 更通用（源/目标都可不是 socket），但需要一对 pipe fd 作为中转，使用上稍繁琐。

三方案怎么选

方案CPU 拷贝次数系统调用能否加工数据典型用途
read + write2 次2 次能（用户态可见）需要读取并修改内容的通用场景
mmap + write1 次2 次能（映射可见）需读取/校验再发送的中等场景
sendfile0~1 次1 次不能（纯内核转发）静态文件服务、大文件下载、MQ 落盘转发
splice0~1 次1 次不能fd 间通用零拷贝转发（含非 socket）

为什么它能快：把 CPU 从搬运工变回调度员 传统方式里 CPU 花大量时间在「搬数据」，而这些数据应用根本不修改。零拷贝把搬运交给 DMA 与内核，CPU 只负责「下指令 + 维护描述符」，腾出的算力去处理更多连接、做业务逻辑。在千兆/万兆网卡的大文件场景，零拷贝常带来数倍吞吐提升。

💡 类比：传统方式像快递员把包裹从仓库搬到自己车上、再搬回分拣中心、再搬上卡车——其实仓库和卡车可以直接对接。零拷贝就是拆掉中间那两道「人工搬运」，让仓库（磁盘）和卡车（网卡）通过调度中心（内核）直接交接。
⚠️ 避坑：零拷贝只优化「转发不修改」的场景。如果你的业务逻辑必须读取内容（如加解密、压缩、按行解析），那次 CPU 拷贝在所难免，强行零拷贝反而要绕路。先确认「应用是否真的需要看数据」。

面试问答

Q：零拷贝是不是一次拷贝都不做了？
不是。它消除的是CPU 参与的冗余内存拷贝和多余的上下文切换；磁盘/网卡与内核缓冲区间的 DMA 搬运仍存在（但不占 CPU）。在支持 DMA 收集的现代网卡上，sendfile 可实现 CPU 拷贝 0 次。
Q：mmap 和 sendfile 哪个更快？
纯转发（不修改内容）用 sendfile 更少拷贝、更少系统调用，更快；若必须在用户态读取或修改数据，mmap 省一次拷贝但仍需一次，比 read+write 好，但比 sendfile 多一步。
Q：为什么 Kafka / 高性能网关大量用零拷贝？
它们的核心动作是「从磁盘/页缓存把消息原样发给网络」，数据无需修改。用 sendfile/transferTo 把搬运交给内核与 DMA，单机可支撑极高吞吐，CPU 不被拷贝拖累。

零拷贝的三种实现与实测收益

「零拷贝」不是真的 0 次拷贝，而是避免 CPU 在内核态和用户态之间来回搬数据。理解那 4 次拷贝 + 4 次上下文切换，就知道省在哪。

方式拷贝次数上下文切换说明
传统 read + write4 次（DMA×2 + CPU×2）4 次磁盘→内核缓冲→用户缓冲→socket缓冲→网卡
mmap + write3 次4 次省掉内核→用户那一次 CPU 拷贝
sendfile2 次（DMA×2）2 次数据在内核里直接从 fd 到 fd，不进用户态
sendfile + SG-DMA1 次（真正意义的零 CPU 拷贝）2 次网卡支持 scatter-gather 时，连内核内的那次也省了
系统调用原型适用限制
sendfilesendfile(out_fd, in_fd, offset, count)文件 → socket（最典型）Linux 2.6.33 起 out_fd 可以是任意 fd；之前必须是 socket
splicesplice(fd_in, off_in, fd_out, off_out, len, flags)两个 fd 间，至少要有一个是管道需要借助 pipe 中转
mmapmmap(NULL, len, PROT_READ, MAP_SHARED, fd, 0)需要随机访问或多次读同一文件有缺页开销；小文件不划算
direct IOopen(..., O_DIRECT)数据库自管缓存绕过 page cache，需自己对齐
SO_ZEROCOPYsocket 选项网络发送Linux 4.14+；有额外的通知开销

代码示例

# ---------- sendfile（最经典的零拷贝）----------
#include <sys/sendfile.h>
int fd_in  = open("bigfile.iso", O_RDONLY);
int fd_out = socket(...);                    // 或另一个文件 fd
off_t offset = 0;
// 直接从文件描述符搬到 socket，数据不经过用户态
ssize_t n = sendfile(fd_out, fd_in, &offset, file_size);

# ---------- mmap ----------
void *p = mmap(NULL, len, PROT_READ, MAP_PRIVATE, fd, 0);
write(sockfd, p, len);                       // 少一次内核->用户拷贝
munmap(p, len);

# ---------- Java 的 transferTo / transferFrom（底层就是 sendfile）----------
FileChannel src = new FileInputStream("f").getChannel();
SocketChannel dst = SocketChannel.open(addr);
src.transferTo(0, src.size(), dst);          // 零拷贝

# ---------- Go 的 SendFile ----------
// net/http 对大文件已经自动用了 sendfile
// 手动：syscall.Sendfile(outFd, inFd, &offset, count)

# ---------- Kafka 为什么快：正是用了 sendfile ----------
#   消费者读消息时：磁盘 -> page cache -> 网卡，不进 JVM 堆
#   这也是 Kafka 敢说「顺序读写 + 零拷贝 = 接近网络上限」的原因

# 实测参考（1GB 文件，千兆网）：
#   read+write:  CPU 占用高，吞吐 ~600 MB/s
#   sendfile:    CPU 降 60%+，吞吐 ~900 MB/s（接近网卡上限）
  • 零拷贝的「零」指的是 CPU 拷贝：DMA 拷贝（磁盘→内存、内存→网卡）依然存在，只是由 DMA 控制器做，不占 CPU。
  • Kafka、Nginx、RocketMQ 快的秘密之一：都用 sendfile。Nginx 的 sendfile on; 是默认开启的。
  • sendfile 不适合「要改数据」的场景：因为数据不进用户态，你没法在传输过程中加密、压缩、修改。要做这些只能用 mmap 或普通 read。
  • 小文件用零拷贝反而慢：sendfile 有系统调用和内核路径切换的固定开销，通常 >1MB 才有明显收益。几 KB 的文件用普通 read 更快。
  • mmap 有缺页开销：首次访问每个页都会触发缺页异常，随机访问大文件时可能比 read 还慢。顺序大文件传输用 sendfile，随机访问用 mmap。
  • Go 的 io.Copy 会自动优化：如果 src 是 *os.File、dst 是 *net.TCPConn，标准库会尝试 sendfile。
  • 直接 IO（O_DIRECT）不等于零拷贝：它绕开 page cache，是给数据库自管缓存用的，和 sendfile 是两回事。
零拷贝到底省了什么？

省的是 2 次 CPU 拷贝 + 2 次上下文切换。传统 read()+write() 发一个文件的过程是：① DMA 把磁盘数据拷到内核缓冲区；② CPU 把内核缓冲区拷到用户缓冲区（read 返回）；③ CPU 把用户缓冲区拷到 socket 缓冲区（write 调用）；④ DMA 把 socket 缓冲区拷到网卡。其中 ② 和 ③ 是 CPU 亲自搬的，而且每次拷贝都伴随一次用户态↔内核态的切换（read 一次、write 一次，各 2 次切换）。sendfile 把 ②③ 合并成内核里的一次指针传递，数据自始至终没进用户态——CPU 拷贝从 2 次降到 0 次，上下文切换从 4 次降到 2 次。收益是双向的：CPU 占用大幅下降（高吞吐时尤其明显），且因为少了一次数据搬运，延迟也更低。如果网卡再支持 scatter-gather DMA，连内核里那次 buffer 到 socket buffer 的拷贝也省了，就是真正意义上的「零 CPU 拷贝」。

什么情况下零拷贝没有收益？

四种典型：① 小文件——sendfile 的固定开销（系统调用、内核路径切换）在几 KB 的数据上占比很高，可能比普通 read 还慢，经验值是 >1MB 才划算；② 需要修改数据——加密、压缩、加协议头，都必须让数据进用户态，sendfile 用不了；③ 数据不在页缓存里且后续要多次访问——第一次读取的磁盘 IO 是省不掉的，如果之后还要反复读同一份数据，page cache 命中后的普通 read 已经很快了；④ 网络不是瓶颈——如果瓶颈在磁盘 IO 或应用层逻辑，优化 CPU 拷贝毫无意义。判断方法很简单：用 perf 看 CPU 是不是花在 copy_user_enhanced_fast_string 之类的拷贝函数上，是才值得优化。

Kafka 为什么能做到那么高的吞吐？

四个因素叠加，零拷贝是其中之一：① 顺序磁盘 IO——消息只追加写、顺序读，顺序写的磁盘吞吐接近内存（这也是为什么 Kafka 敢用磁盘而不是内存队列）；② page cache 而不是 JVM 堆——数据放在 OS 的页缓存里，避免了 JVM GC 开销和堆内存翻倍（不用在堆里再存一份）；③ sendfile 零拷贝——消费者拉取消息时，数据从 page cache 直接到网卡，不进 JVM、不做 CPU 拷贝；④ 批量与压缩——生产者批量发送、端到端压缩，减少了网络往返和传输字节数。合起来的效果是：Kafka 的瓶颈通常在网卡而不是 CPU 或磁盘，这也是它能支撑百万级 TPS 的原因。对比之下，很多消息队列慢在「数据在用户态和内核态之间反复搬运 + GC 压力大」。

自检

给一个「读取上传文件 → 计算哈希 → 再原样存盘」的流水线，零拷贝在哪一环能省、哪一环不能省？
答：「原样存盘」可零拷贝转发；但「计算哈希」必须读取内容，这一环的 CPU 拷贝无法省，否则哈希无从算起。
