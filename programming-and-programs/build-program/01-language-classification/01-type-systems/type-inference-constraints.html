类型推断：约束生成、合一与多态边界

从简单函数推导类型，再看为什么递归、自引用与副作用会让推断变复杂。

类型推断在推什么

静态类型语言不一定要求程序员给每个变量写注解。编译器可根据表达式产生类型约束，再求出满足约束的类型。例如函数 id(x) = x 的参数先赋一个未知类型 α；返回表达式也是 x，因此返回类型与 α 相同，得到 α→α。调用 id(3) 时，把 α 与整数类型合一，调用结果为整数。这里的推断发生在编译或检查阶段，不等于运行时动态类型。

函数应用 f(x) 会产生约束：f 必须是从 x 的类型到某个结果类型的函数。加法表达式可能要求操作数满足数值类型规则；成员访问要求对象有对应结构。约束互相冲突时，编译器应指出冲突来源，而不是随便选一个类型。不同语言支持的泛型、子类型和隐式转换不同，推断算法也不必相同。

逐步推演

分配未知量

为参数和表达式引入 α、β 等类型变量。

生成约束

函数调用、返回、加法等语法结构产生类型关系。

合一求解

让兼容类型相等，发生冲突或自引用时报错。

泛化与实例化

按语言规则决定 let 绑定能否在不同调用处使用不同类型。

合一怎样找到类型或报错

对 twice(f, x) = f(f(x))，设 x:α，第一次 f(x) 的结果为 β，所以 f 至少满足 α→β；第二次 f 接收 β，又需要 f 的输入与 β 一致。在简单单态推断下合一得到 α=β，故 f:α→α，twice:(α→α)→α→α。这个推导依赖该语言对函数和多态的规则，换成支持更复杂多态的系统可能有不同表达能力。

程序片段约束结论
id(x)=x返回类型=参数类型α→α
id(3)α=整数结果为整数
x+1x 需满足加法规则按语言确定数值类型
x(x)α 必须包含自身作为参数在常见简单类型系统中失败

出现检查为什么不可省

若对 x(x) 粗略地产生“x 的类型 α 必须等于 α→β”，会得到一个无限展开的类型 α=(α→β)=(α→β)→β……。普通 Hindley–Milner 风格的有限简单类型系统会用 occurs check 拒绝这种自引用。若实现只把类型变量指向函数类型而不检查包含关系，后续合一可能无限递归或产生错误的类型结论。

let 绑定的多态也要区分定义和使用。若 let id = x => x 被泛化为 ∀α.α→α，后续对整数与字符串的两次调用可以各自实例化 α。但带可变引用等副作用的表达式不能随意按同一规则泛化，否则不同调用可能共享一个实际存储单元却被当作不同类型；许多语言因此设置值限制或其他约束。

推断结果如何验证

  1. 对每个表达式明确生成了哪些约束，不要用“编译器猜出来”跳过过程。
  2. 合一时记录类型变量替换，出现函数类型自引用就做 occurs check。
  3. 把泛型函数的定义处泛化与调用处实例化区分开。
  4. 用错误用例检查诊断质量：例如把字符串传给只接受数值的加法。

练习：写出 compose(f,g,x)=f(g(x)) 中 f、g、x 和返回值之间的类型关系。再说明若 g 的输出与 f 的输入不能合一，错误应落在哪一次函数应用上。

分支汇合也会产生类型约束

考虑 if condition then 1 else 2，两个分支都是整数，整个表达式可推断为整数；若 else 返回字符串，简单静态类型系统会要求两分支类型合一，可能报错。支持联合类型或共同父类型的语言则可能给出更宽的结果类型。推断结论依语言规则，不是所有编译器都必须接受或拒绝相同代码。循环、模式匹配与重载也会增加约束，可能需要显式注解帮助消歧。

类型推断不是“省略所有类型设计”。公开 API 的注解有助于表达契约，错误消息也更容易定位；局部变量则适合让编译器推断。泛型代码需要区分“对任意 α 都能工作”与“这次调用恰好选择了整数”。前者是定义处的能力，后者是调用处的实例化。若把一次调用推导出的具体整数反写到泛型定义上，后续字符串调用就会被错误拒绝。

工程上可保存每一步的约束来源，让诊断指向真正冲突的表达式，而不是只说“类型不匹配”。

类型错误定位

若约束来自函数调用、分支返回和赋值三处，编译器应保留约束的源码位置。最终合一失败时，展示两个冲突类型及其来源，比只指向最后一个 token 更有帮助。推断算法的结果不仅是类型，也是可解释的诊断链。

必要时给递归函数写出输入和返回类型注解，可帮助编译器缩小推断空间，也让调用者看清 API 契约。

HM 的两条核心规则：① 泛化只在 let 处发生（所以 let f = fun x -> x 是多态的，而 fun f -> (f 1, f true) 不行——因为 lambda 参数不泛化）；② 类型变量一旦被合一就全局生效（所以推断是「全局」的，一处改动可能影响很远）。

算法实现

# 简化版合一算法
def unify(t1, t2, subst):
    t1, t2 = resolve(t1, subst), resolve(t2, subst)

    if isinstance(t1, TypeVar):
        if t1 != t2:
            if occurs(t1, t2, subst):
                raise TypeError(f"recursive type: {t1} = {t2}")   # occurs check！
            subst[t1] = t2
        return
    if isinstance(t2, TypeVar):
        return unify(t2, t1, subst)

    if t1.kind == 'fn' and t2.kind == 'fn':
        unify(t1.arg, t2.arg, subst)        # 参数逆变
        unify(t1.ret, t2.ret, subst)        # 返回协变
        return
    if t1.kind == t2.kind and t1 == t2:
        return                               # 基础类型相同
    raise TypeError(f"cannot unify {t1} with {t2}")

def occurs(v, t, subst):
    """occurs check：v 是否出现在 t 里（防止无限类型）"""
    t = resolve(t, subst)
    if t == v: return True
    if t.kind == 'fn': return occurs(v, t.arg, subst) or occurs(v, t.ret, subst)
    return False
# 漏掉 occurs check 会导致 a = a -> a 这样的无限类型，程序死循环
# 算法 W（HM 推断）骨架
def infer(env, expr):
    if expr is Var:
        return instantiate(env[expr.name])           # 实例化
    if expr is Lam:
        tv = fresh_typevar()                          # 为参数引入新类型变量
        env2 = env.extend(expr.param, tv)
        t_body = infer(env2, expr.body)
        return FnType(tv, t_body)
    if expr is App:
        t_fun = infer(env, expr.fn)
        t_arg = infer(env, expr.arg)
        t_ret = fresh_typevar()
        unify(t_fun, FnType(t_arg, t_ret))            # 关键：合一
        return resolve(t_ret)
    if expr is Let:
        t_val = infer(env, expr.value)
        t_gen = generalize(env, t_val)                # 泛化（let 才有）
        return infer(env.extend(expr.name, t_gen), expr.body)

# 复杂度说明

#   - 整体近似线性，但<b>最坏情况是指数的</b>（某些病态输入）
#   - 实践中 HM 推断非常快，这也是 OCaml/Haskell 编译快的原因之一

排障清单

症状原因处理
推断出无限类型导致死循环没做 occurs check必须加 occurs check
错误信息指向很远的地方HM 是全局推断，错误位置可能偏离多写类型标注；好的编译器会记录约束来源
let 多态没生效值限制（value restriction）ML 的限制：只有「语法上是值」才泛化
推断太慢约束求解是 NP 难的（某些系统）加类型标注；限制推断范围
子类型导致推断失败HM 不支持子类型改用双向检查或约束系统
递归函数推断失败需要显式类型标注递归定义要先给出类型（HM 的限制之一）

HM 的适用边界：它非常适合函数式语言（ML/Haskell），但不支持子类型、重载、隐式转换——这些会让合一变成约束求解，复杂度和错误信息质量都急剧恶化。这也是为什么 Scala/TypeScript 的错误信息通常比 Haskell 难懂。

自检

类型推断是否等于运行时才知道类型？

不是。许多静态类型系统在编译或检查时根据约束推断类型。

为什么 x(x) 在普通简单类型推断中出问题？

它要求 x 的类型包含自身作为函数参数，有限类型合一的 occurs check 会拒绝。
