🕰️ 逻辑过期：让缓存永不真正消失

不给 Redis 设 TTL，把过期时间写进 value 里；请求永远有数据返回，由后台线程悄悄换新。

一致性换可用性

先建立直觉：便利店的「赏味期限」

便利店的便当不会一到点就被机器自动扔掉（物理过期），而是贴着一张赏味期限标签（逻辑过期）。店员巡检时看到某盒过了期，就把它换掉——但在换之前，货架上始终有东西。

Redis 的 TTL 是「到点自动消失」，逻辑过期是「贴个标签，过期了也还在，等人来换」。这就是本质区别。

一句话对比：
• 物理过期（TTL）：到点 key 消失 → 读请求 miss → 必须查库重建 → 这就是击穿的根源。
• 逻辑过期：key 永远在 → 读请求永远命中 → 不存在 miss → 击穿被从根上消除。

数据结构与流程

// value 里带上逻辑过期时间
type CacheItem struct {
    Data     string `json:"data"`
    ExpireAt int64  `json:"expire_at"`   // 逻辑过期时间戳
}

// 写入时：不设 TTL，但写入 expireAt
item := CacheItem{Data: encode(u), ExpireAt: now + 300}
redis.Set(key, encode(item))          // 注意：没有 EX / TTL

读取时判断 expireAt：未过期直接返回；已过期则先照旧返回旧数据，同时抢锁异步重建。

三个实践要点

① 重建失败不要紧。逻辑过期下重建是「尽力而为」：抢不到锁就算了（别人在重建），查库失败也算了（下次再试）。因为旧数据还在，用户不会被卡住——这是它最大的韧性所在。
② 内存不再自动回收。没有 TTL 意味着 key 永远不会自动过期。必须有兜底清理机制：定期扫描删除长期未被访问的 key，或对冷数据补设一个较长的物理 TTL 作为保险。否则已下线的数据会永久占着内存。
③ 首次写入要预热。逻辑过期的前提是「key 存在」。如果这个 key 从未被写入过（冷启动），依然会 miss。所以热点数据要提前预热，或者 miss 时走互斥锁兜底。

什么时候用逻辑过期

  • ✅ 顶级热点：首页、爆款商品、热搜榜——绝对不能让请求等待。
  • ✅ 能容忍短暂陈旧：商品描述、文章内容、推荐列表。
  • ❌ 强一致场景：库存、余额、订单状态——旧值会造成资损，宁可等也要拿准确值。

🎯 面试问答

Q：逻辑过期能彻底消除击穿吗？
A：能消除「过期瞬间大量miss」这个击穿成因，因为它根本没有 miss。但它不能解决「key 从来没被写入过」的情况（冷启动）——那种仍是 miss，需要预热或用互斥锁兜底。另外如果整个 Redis 实例宕机，所有 key 一起消失，那是雪崩问题，要靠集群和多级缓存解决。

Q：返回旧数据的时间窗口有多长？
A：约等于一次重建的耗时（通常几十到几百毫秒），加上发现过期到抢到锁之间的延迟。只要你能容忍这个量级的陈旧，逻辑过期就很划算。如果业务要求「必须最新」，就不要用它。

Q：为什么还要抢锁？直接让每个发现过期的线程都去重建不行吗？
A：技术上「能跑」，但会造成重复查库：一万个请求发现过期，就查一万次库，这正是击穿要避免的。抢锁保证同一时刻只有一个线程重建，数据库压力恒定为 1 次。区别是：互斥锁里没抢到锁要等，逻辑过期里没抢到锁直接返回旧值，不阻塞。

Q：没有 TTL，冷数据怎么办？
A：必须自己兜底。常见做法：① 定时任务扫描长期未访问的 key 并删除；② 写入时额外设一个很长的物理 TTL（如 7 天）作为保险，逻辑过期负责业务语义、物理 TTL 负责内存兜底；③ 依赖 Redis 的 maxmemory-policy 在内存压力下淘汰。不要完全放任不管。

逻辑过期的实现与三种写法

核心思路：不给 Redis 设 TTL（或设很长），而是在value 里存一个业务过期时间，读取时判断是否过期；过期则由当前线程（或异步）重建。

三种写法

# 写法 1：最简版（<strong>有击穿风险</strong>）
def get_v1(key):
    v = redis.get(key)                  # JSON: {"data":..., "expire_at":...}
    if v is None:
        return rebuild(key)             # 过期或未命中都重建 → 并发全打到 DB
    obj = json.loads(v)
    if time.time() > obj["expire_at"]:
        return rebuild(key)             # <strong>多个线程同时发现过期，全部重建</strong>
    return obj["data"]

# 写法 2：加互斥锁（防击穿）
def get_v2(key):
    obj = json.loads(redis.get(key) or "null")
    if obj and time.time() <= obj["expire_at"]:
        return obj["data"]
    if redis.setnx(f"lock:{key}", 1, ex=10):      # 抢到锁才重建
        try:
            data = db.query(key)
            redis.set(key, json.dumps({
                "data": data, "expire_at": time.time() + 300}))
            return data
        finally:
            redis.delete(f"lock:{key}")
    return obj["data"] if obj else None    # <strong>没抢到锁：返回旧值！</strong>

# 写法 3：异步刷新（体验最好）
#   未抢到锁的线程返回旧值，并<strong>提交一个后台任务</strong>去刷新
#   用户永远拿到数据（哪怕是旧的），延迟不受重建影响
写法击穿风险返回旧值复杂度
1. 直接重建有否（阻塞等待）低
2. 互斥锁无是中
3. 异步刷新无是（且后台更新）高

写法 2 的关键价值：没抢到锁的线程返回已过期的旧值，而不是等待或报错。这就是“逻辑过期”名字的含义——数据在逻辑上过期了，但物理上还在，可以用来兜底。这是它优于“物理过期 + 互斥重建”的地方：后者在重建期间其他线程只能等待。

与物理 TTL 的对比

维度物理 TTL（EXPIRE）逻辑过期
过期判定Redis 自动删除应用代码判断
过期后数据不存在仍在（可返回旧值）
击穿风险有（需额外防）低（天然有兜底）
内存占用过期即释放过期数据仍占内存
实现成本零需封装
适用场景通用默认热点 key、重建代价高

选择判据：

  • 普通 key → 物理 TTL 足够，简单可靠。
  • 热点 key 且重建代价高（如复杂聚合、调外部接口）→ 逻辑过期，用旧值兜底避免大量线程等待。
  • 不能返回旧值（如库存、价格）→ 都不能用，应走主动更新 + 短 TTL，或直接从库读。

生产实现的三个细节

  • 兜底 TTL 必须同时设置：逻辑过期依赖应用判断，若应用有 bug 或 key 长期无人访问，过期数据会永久占内存。做法是同时给 Redis 设一个远长于逻辑过期时间的物理 TTL（如逻辑 5 分钟、物理 24 小时）作为最后防线。
  • 锁超时必须大于重建耗时：锁的 ex 若小于重建时间，会出现“锁已过期但重建未完成”，其他线程又进来重建。设为重建 P99 的 2~3 倍。
  • 防止死锁：用 SET NX EX 原子设置（不要用 SETNX + EXPIRE 两步，中间崩溃会死锁），并在 finally 里释放。更稳妥的是给锁加唯一值（UUID），释放时校验，避免误删别人的锁。

生产实现

# 生产级实现（含物理 TTL 兜底 + 安全释放锁）
import uuid, time, json

def get_with_logic_expire(key, loader, logic_ttl=300, phys_ttl=86400, lock_ttl=30):
    raw = redis.get(key)
    obj = json.loads(raw) if raw else None

    # 1) 未过期 → 直接返回
    if obj and time.time() <= obj["expire_at"]:
        return obj["data"]

    # 2) 过期 → 抢锁重建
    token = str(uuid.uuid4())
    got = redis.set(f"lock:{key}", token, nx=True, ex=lock_ttl)
    if got:
        try:
            data = loader()
            redis.setex(key, phys_ttl, json.dumps({      # <strong>物理 TTL 兜底</strong>
                "data": data, "expire_at": time.time() + logic_ttl}))
            return data
        finally:
            # 只删自己的锁：用 Lua 保证“比较+删除”原子
            redis.eval(
                "if redis.call('get',KEYS[1])==ARGV[1] then "
                "return redis.call('del',KEYS[1]) else return 0 end",
                1, f"lock:{key}", token)
    # 3) 没抢到锁 → 返回旧值（哪怕过期），保证可用
    return obj["data"] if obj else None

自检 Q&A

Q：逻辑过期和“缓存永不失效”是一回事吗？

A：不是。逻辑过期的 value 里有明确的过期时间戳，读取时会判断并返回“已过期”的信号触发重建；缓存永不失效（无 TTL 也无逻辑时间）则永远不会更新，数据会一直陈旧。前者是可控的短暂不一致，后者是数据永久错误。所以实现逻辑过期时，expire_at 字段是必需的，不能只存 data。

Q：返回旧值会不会造成业务问题？

A：看数据的性质。允许短暂陈旧的数据（商品描述、文章内容、推荐列表）→ 完全没问题，这正是逻辑过期的价值所在。不允许陈旧的（库存余量、实时价格、账户余额）→ 不能用逻辑过期，这类数据本就不该用缓存兜底，应直读数据库或走主动更新。判据是“用户看到 5 分钟前的值会不会造成损失”。

Q：热点 key 重建时，其他线程返回旧值会不会导致“脏读很久”？

A：不会，只会脏很短时间。因为抢到锁的那个线程会完成重建并写入新值，后续请求立刻拿到新数据。所谓“脏”只发生在重建进行中的那几十毫秒。相比之下，不加锁的方案里所有线程各自重建，数据库压力暴增且重建时间更长，脏窗口反而更大。所以逻辑过期 + 互斥锁是把“长时间不可用/超压”换成“极短时间陈旧”，是划算的交换。

Q：如果持有锁的线程崩溃了怎么办？

A：靠锁的 TTL 自动释放，这就是必须用 SET NX EX（原子设值+过期）而不是两步操作的原因。若用 SETNX 后还没来得及 EXPIRE 就崩溃，锁会永久存在（死锁），该 key 再也无法更新。所以：① 一定要原子设置过期时间；② 过期时间要足够长（覆盖重建耗时）；③ 释放时校验 token 避免误删他人锁。这三条是分布式锁的标准要求。
