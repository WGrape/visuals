go-zero RPC 通信详解

zrpc = gRPC + 服务发现 + 负载均衡 + 超时/重试/熔断。本文把一次 RPC 调用的全链路拆开讲，配代码、配时序图。

概念

zrpc 到底是什么

zrpc 封装 gRPC 服务与客户端的常用治理能力；调用语法可以很简洁，但超时、网络故障和重试仍是远程调用语义。

zrpc 是 go-zero 自带的 RPC 包，导入路径为 github.com/zeromicro/go-zero/zrpc。它建立在 gRPC 与 protobuf 之上；服务发现、负载均衡、熔断和观测能力来自 go-zero 的集成，具体行为仍取决于版本与配置。

首次接触 go-zero 的读者可先看框架快速上手；本页拆解 RPC 契约、生成代码和故障处理。内部 RPC 与第三方 HTTP 的接入选择见服务调用实践。

与直接使用 gRPC 的区别

gRPC 提供传输、序列化、拦截器和可扩展的客户端能力；zrpc 把 etcd 注册发现、客户端治理和观测集成到 go-zero 的配置与生成代码中，减少应用侧组装工作。

两种角色

Server：实现 proto 里定义的 service 方法；Client：通过生成的 client 调用对端。一个服务可以同时是两者。

第 1 步

定义 proto 契约

proto 是服务之间的「接口文档」，双方按它生成代码，强类型、不会调错字段。

user.proto 示例

syntax = "proto3";
package user;

// go_package 决定生成代码的位置
option go_package = "./user;user";

service User {
  rpc GetUser(GetUserRequest) returns (GetUserResponse);
  rpc Login(LoginRequest) returns (LoginResponse);
}

message GetUserRequest { int64 id = 1; }
message GetUserResponse {
  int64 id = 1;
  string name = 2;
}
message LoginRequest {
  string username = 1;
  string password = 2;
}
message LoginResponse { string token = 1; }
第 2 步

一条命令生成全套代码

goctl 会生成 pb.go（消息）、grpc.pb.go（gRPC 桩）、以及 zrpc 的 server/client 封装。

生成命令

goctl rpc protoc user.proto \
  --go_out=. \
  --go-grpc_out=. \
  --zrpc_out=. \
  -m        # -m 顺带生成 yaml 配置与 main

产物结构：

user/
  user.pb.go          # 消息结构体
  user_grpc.pb.go     # gRPC 接口 + 客户端
internal/server/
  userserver.go       # 服务端注册
internal/logic/
  getuserlogic.go     # 你的实现
  loginlogic.go
user.go               # main
etc/user.yaml

在 logic 里实现方法

func (l *GetUserLogic) GetUser(in *user.GetUserRequest) (*user.GetUserResponse, error) {
    u, err := l.svcCtx.UserModel.FindOne(l.ctx, in.Id)
    if err != nil {
        return nil, err
    }
    return &user.GetUserResponse{Id: u.Id, Name: u.Name}, nil
}
第 3 步

客户端怎么调用

调用方不写连接、不写拨号。在 config 配 etcd，svc 建 client，logic 直接方法调用。

1）config 声明下游 RPC

type Config struct {
    rest.RestConf
    UserRpc zrpc.RpcClientConf   // 关键：下游 RPC 配置
}

2）svc 注入 client

type ServiceContext struct {
    Config  config.Config
    UserRpc user.User
}
func NewServiceContext(c config.Config) *ServiceContext {
    return &ServiceContext{
        Config:  c,
        UserRpc: user.NewUser(zrpc.MustNewClient(c.UserRpc)),
    }
}

3）logic 里一行调用

resp, err := l.svcCtx.UserRpc.GetUser(l.ctx, &user.GetUserRequest{Id: 1})
if err != nil {
    return nil, err
}
// resp.Name 即可使用

第 4 步

拦截器：RPC 的「中间件」

想在每次调用前后统一做事（日志、鉴权、追踪）？用拦截器，不用改业务。

服务端拦截器（记录耗时）

srv := zrpc.MustNewServer(c.RpcServerConf, func(s *grpc.Server) {
    s.AddUnaryInterceptor(func(ctx context.Context, req interface{},
        info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (interface{}, error) {
        start := time.Now()
        resp, err := handler(ctx, req)
        logx.Infof("%s cost=%v err=%v", info.FullMethod, time.Since(start), err)
        return resp, err
    })
})
defer srv.Stop()
if err := srv.Add(user.RegisterUserServer, userServer.NewUserServer(ctx)); err != nil {
    logx.Fatal(err)
}
srv.Start()

客户端拦截器（透传 header）

client := zrpc.MustNewClient(c.UserRpc, zrpc.WithUnaryClientInterceptor(
    func(ctx context.Context, method string, req, reply interface{},
        cc *grpc.ClientConn, invoker grpc.UnaryInvoker, opts ...grpc.CallOption) error {
        ctx = metadata.AppendToOutgoingContext(ctx, "x-trace-id", traceId())
        return invoker(ctx, method, req, reply, cc, opts...)
    }))
第 5 步

超时 / 重试 / 熔断

RPC 调用一定要设防护，否则一个慢下游能把整条链路拖死。

超时：在 yaml 配

UserRpc:
  Etcd:
    Hosts: [127.0.0.1:2379]
    Key: user.rpc
  Timeout: 3000        # 单此调用超时(ms)

熔断：包裹调用

err := breaker.Do("user-rpc:GetUser", func() error {
    _, e := l.svcCtx.UserRpc.GetUser(l.ctx, req)
    return e
}, nil)

重试：客户端配置

UserRpc:
  Timeout: 3000
  Retries: 1           # 失败重试次数（谨慎，需幂等）
重试的前提是接口幂等（重复调用不产生副作用）。下单、扣款这类写操作不要盲目重试，否则会重复扣钱。
防护优先级建议：超时必配（防止无限等待）→ 熔断保护下游（防止雪崩）→ 重试只给只读/幂等接口（提升可用性）。

go-zero RPC 的超时与重试配置

参数位置默认值建议
Timeout客户端 yaml2000 ms按 P99 设定，不要全用默认
MaxConns客户端 yaml0（不限）高并发时设 100~500，防止连接爆炸
Etcd/Endpoints服务发现—生产用 etcd，直连只用于本地调试
NonBlock客户端falsetrue 时服务不可达立即报错而非阻塞
Sync/Async服务端—Sync: false 时自动异步处理

超时必须逐段变短：调用链的超时应该是上游 > 下游。若上游 2 秒、下游 3 秒，上游早已超时放弃，下游还在算——白白消耗资源。正确做法是从最下游开始定超时，逐层向上累加。

配置示例

# 客户端配置（etc/*.yaml）
OrderRpc:
  Etcd:
    Hosts:
      - 127.0.0.1:2379
    Key: order.rpc
  Timeout: 800          # 毫秒，按下游 P99 设定
  MaxConns: 200         # 最大连接数，防连接爆炸
  NonBlock: false

# 服务端配置
Name: order.rpc
ListenOn: 0.0.0.0:8080
Timeout: 3000           # 服务端自身的处理超时
MaxConns: 10000
Etcd:
  Hosts:
    - 127.0.0.1:2379

拦截器

// 自定义拦截器（服务端）
func LoggerInterceptor(ctx context.Context, req interface{},
    info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (interface{}, error) {
    start := time.Now()
    resp, err := handler(ctx, req)          // 执行实际逻辑
    logx.WithContext(ctx).Infow("rpc",
        logx.Field("method", info.FullMethod),
        logx.Field("cost", time.Since(start).Milliseconds()),
        logx.Field("err", err))
    return resp, err
}

// 注册
s := zrpc.MustNewServer(c.RpcServerConf, func(grpcServer *grpc.Server) {
    pb.RegisterOrderServer(grpcServer, svc)
})
s.AddUnaryInterceptors(LoggerInterceptor)   // 追加自定义拦截器

熔断参数：go-zero 的 breaker 默认基于滑动窗口内的错误率（默认 5 秒内采样，错误率超 50% 触发）。可通过 WithBreaker 自定义。注意它是客户端侧熔断，保护的是调用方不被拖垮。

proto 与代码生成约定

proto 定义

syntax = "proto3";

package order;
option go_package = "./order";

message CreateOrderReq {
  int64  user_id = 1;      // 字段号 1~15 只用 1 字节编码，<strong>高频字段优先用小号</strong>
  string sku_id  = 2;
  int32  count   = 3;
}

message CreateOrderResp {
  string order_id = 1;
}

service Order {
  rpc Create(CreateOrderReq) returns (CreateOrderResp);
}

代码生成

# 生成代码
goctl rpc protoc order.proto --go_out=./ --go-grpc_out=./ --zrpc_out=.

# 目录约定（goctl 生成，勿手工改动生成文件）
#   order/
#     order.pb.go        由 protoc 生成
#     order_grpc.pb.go   由 protoc-gen-go-grpc 生成
#     order.go           goctl 生成的客户端封装
#   internal/
#     logic/             <strong>业务代码写这里</strong>（不被覆盖）
#     server/            服务注册
#     svc/               依赖注入上下文
#   etc/order.yaml       配置
  • internal/logic 是唯一应该手写业务的地方——重新生成 proto 不会覆盖它。
  • 字段号一旦上线就不能改：改字段号等于改了 wire format，老客户端会解析错。要废弃字段用 reserved 占位。
  • 字段号 1~15 的 tag 只占 1 字节，16 及以后占 2 字节——高频字段留给小号。

自检 Q&A

Q：go-zero 的 RPC 和 gRPC 原生有什么区别？

A：go-zero 是在 gRPC 之上的工程化封装：内置了服务发现（etcd）、负载均衡（P2C）、熔断、限流、超时、链路追踪，并把这些能力做成 yaml 配置而非手写代码。原生 gRPC 只提供通信骨架，治理能力都要自己接拦截器实现。所以差异不在协议（都是 gRPC/HTTP2），而在开箱即用的治理能力。

Q：RPC 调用超时该怎么排查？

A：分层定位——① 看是客户端超时还是服务端超时（日志里 context deadline exceeded 出现在哪一侧）；② 若服务端很快返回但客户端报超时，检查服务发现是否拿到了不可用的地址（etcd 里有已下线的实例）；③ 若服务端本身就慢，往下钻它依赖的 DB/缓存。关键工具是链路追踪——没有 tracing 时，超时问题在跨 3 个服务的调用链上几乎无法定位。

Q：NonBlock 该设 true 吗？

A：看场景。设为 true 时，服务不可达会立即返回错误而不是等待——适合启动阶段或强依赖检查（快速失败）。但生产环境通常设 false：服务短暂不可达时，阻塞等待能让服务恢复后自动连上，避免因启动顺序导致的首次调用失败。折中是设 false 但把 Timeout 调小。

Q：proto 改了字段类型怎么办？

A：兼容性分三种。安全：int32 → int64（wire 兼容）、加新字段（老端忽略）。危险：改字段号、改 string ↔ bytes 语义、改有符号/无符号。绝不能改字段号。要改类型，正确做法是新增一个字段（用新号），老字段标 reserved，双写一段时间后下线——这是 protobuf 演进的标准流程。
