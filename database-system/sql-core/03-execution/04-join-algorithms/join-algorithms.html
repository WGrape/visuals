①三种物理 JOIN 算法

SQL 里的 INNER/LEFT/RIGHT/OUTER 说的是语义（结果集包含哪些行）， 执行计划里的 Nested Loop / Hash / Merge 说的是算法（怎么把两张表的行配对）。 两者正交：同一个 LEFT JOIN，优化器可能用三种算法中的任何一种。

三种物理 JOIN 算法的适用边界

②Nested Loop：驱动表决定一切

Nested Loop 的思想最简单：外层取一行，拿关联键去内层查匹配的行。 它的代价 = 外层行数 × 单次内层查找代价。所以关键变量有两个：

  • 外层（驱动表）要小——过滤后剩多少行，决定内层被查找多少次。这就是「小表驱动大表」说法的来源， 更准确的说法是「过滤后结果小的表作驱动表」。
  • 内层的关联列必须有索引——有索引时单次查找是 O(log n)，无索引就是全表扫， 整体退化成 O(N×M)。MySQL 里后者表现为 Using join buffer (Block Nested Loop)，是危险信号。
-- 假设 orders 过滤后 100 行，users 100 万行且 id 是主键
SELECT u.name, o.amount
FROM orders o
JOIN users u ON u.id = o.user_id     -- 驱动表 = orders(100 行)，内层走主键
WHERE o.created_at >= '2026-01-01';  -- 100 次主键查找，毫秒级

-- 反过来若优化器选错驱动表，变成 100 万次查找，就是秒级到分钟级
「小表驱动大表」不是让你改 SQL 里 JOIN 的书写顺序。 优化器会自己重排（除了用 STRAIGHT_JOIN 固定时）。 真正要做的是：① 让驱动表上的过滤条件能用索引，把结果集压小； ② 保证被驱动表的关联列有索引。

③Hash Join：大表等值的默认答案

分两个阶段：build——把较小的一侧读进内存建哈希表；probe——流式读较大的一侧， 对每行算哈希去表里找匹配。复杂度约 O(N+M)。

维度说明
适用条件只支持等值条件（=）。>、LIKE、非等值无法用。
内存哈希表要能放下 build 侧。放不下会分片落盘（PG 的 Batches: N），性能下降。
不需要索引这是它相对 Nested Loop 最大的优势——临时关联、ETL 场景无需建索引。
首次输出延迟必须先读完整个 build 侧才能输出第一行，所以不适合需要快速返回首屏的场景。
外连接支持各版本支持程度不同（MySQL 对 LEFT JOIN 的 Hash 支持是逐步补齐的）。
什么时候你会看到它：大表 JOIN 大表、被驱动表关联列没索引、 或优化器判断「建哈希比百万次索引回表更便宜」时。它不是「坏事」—— 在没有合适索引的前提下，Hash Join 往往是最优解。

④Merge Join 与其他形态

Merge Join 要求两侧输入按关联键有序，然后像归并两个有序数组一样推进游标。 若输入已有序（索引扫描、或上游刚排序过），它就是 O(N+M) 且几乎不占额外内存。

  • 若输入无序，优化器要先排序，代价可能超过收益——这时不如 Hash Join。
  • 支持非等值条件（如 >=、范围重叠），这是它相对 Hash Join 的独有能力。
  • 半连接 / 反连接（Semi / Anti Join）：EXISTS、IN、 NOT EXISTS 会被优化成这类算子，找到第一个匹配就停止，比完整 JOIN 更省。
  • 笛卡尔积：忘了写关联条件，或条件写错导致两表无条件配对，输出 N×M 行。 这是最危险的执行计划形态，看到 rows 相乘要立刻停。
Q：IN 和 EXISTS 到底哪个快？
A：现代优化器对非相关的 IN (subquery) 大多会改写成半连接，两者计划相同。 差别出现在 NOT IN（NULL 语义陷阱，见「过滤条件」那篇）和相关子查询能否去关联化上。 不要背结论，看执行计划。
Q：JOIN 顺序优化器会自己排吗？
A：会，但表多时会用贪心或遗传算法做近似搜索，可能选到次优。 MySQL 的 join_buffer_size、PG 的 join_collapse_limit 都会影响搜索范围。 超过 10 张表的复杂 JOIN 建议拆成几步 + 临时表，降低优化器出错概率。

三种 JOIN 算法对照

算法核心思路复杂度适用场景
Nested Loop外层逐行，内层全扫匹配O(N×M)小表 × 小表；内表有索引时变快
Hash Join小表建哈希表，大表探测O(N+M)大表等值连接首选
Merge Join两表排序后归并O(N+M) + 排序代价已排序 / 非等值但有序

选择逻辑：

  • 连接条件是等值且一侧较小 → Hash Join（绝大多数场景的最优解）。
  • 一侧极小（如几条）且另一侧有索引 → Index Nested Loop（避免建哈希表）。
  • 两侧都已按连接键有序（如有索引或刚排过序）→ Merge Join 省去排序。
  • 非等值连接（>、BETWEEN、LIKE）→ 只能 Nested Loop（哈希与归并都要求等值）。

Merge Join 的真实代价：虽然扫描是 O(N+M)，但前期的排序是 O(N log N)。只有当输入已有序（走索引扫描）时才真正省力——优化器算的就是“排序代价 + 归并代价”是否低于“哈希代价”。

内存与溢出诊断

-- MySQL：确认是否用了 Block Nested Loop（无索引时的退化形式）
EXPLAIN SELECT * FROM orders o JOIN users u ON o.user_id = u.id;
-- 若 Extra 出现 "Using join buffer (Block Nested Loop)" → 内表无索引，
--   退化成 O(N×M)。<strong>解决方案是给连接列加索引</strong>，而不是调 join_buffer_size

-- PostgreSQL：看是否落盘
EXPLAIN (ANALYZE, BUFFERS) SELECT ...
-- 关注 "Batches: 2" 或 "Sort Method: external merge  Disk: xxx kB"
--   Batches > 1 说明哈希表溢出分片了 → 调大 work_mem
SET work_mem = '64MB';   -- 可按会话调整，注意并发数 × work_mem 的总量

驱动表选择与执行计划

驱动表（外层表）的选择直接影响代价：Nested Loop 中内层表会被扫描 N 次，所以大表应作外层、小表作内层且内层有索引；Hash Join 中应该用小表建哈希表。

场景最优驱动表原因
Nested Loop + 内表索引行数多的作驱动内表走索引，每行代价固定
Hash Join小表作 build 侧哈希表更小，可放内存
带 WHERE 过滤过滤后行数少的作驱动先过滤再连接，中间结果小

谓词下推

-- 关键优化：谓词下推（先过滤再连接）
-- ✗ 先连接后过滤（中间结果巨大）
SELECT * FROM orders o JOIN users u ON o.user_id = u.id
WHERE o.created_at >= '2026-10-01';

-- ✓ 优化器通常会自动下推，等效于：
SELECT * FROM (SELECT * FROM orders WHERE created_at >= '2026-10-01') o
       JOIN users u ON o.user_id = u.id;

-- 确认下推是否生效：看 EXPLAIN 里 orders 的 rows 是否已减少
-- 若没下推（如用了 OR、函数包裹），改写 SQL 或加索引

多表 JOIN 的顺序爆炸：N 个表连接的可行顺序是 N! 量级（还有左右/深树的组合）。优化器不会穷举——MySQL 在表数超过 optimizer_search_depth（默认 62）时用贪心，PostgreSQL 在超过 join_collapse_limit（默认 8）时用遗传算法。所以超过 8~10 个表的大 JOIN 要手工拆分成临时结果，别指望优化器。

自检 Q&A

Q：为什么 EXPLAIN 显示用了 Nested Loop 而不是 Hash Join？

A：常见三个原因——① MySQL 8.0.18 之前不支持 Hash Join（只有 Block Nested Loop），老版本必须靠索引；② 连接条件不是等值（Hash Join 只支持等值）；③ 优化器估算认为一侧极小、走索引更快。诊断：先看数据库版本，再确认连接条件是否等值，最后看内表连接列有没有索引——没索引时 Nested Loop 是灾难。

Q：大表 JOIN 大表怎么办？

A：三种递进手段——① 加索引 + 谓词下推，先把两侧结果集缩到最小；② 分批处理：按主键或时间分片，每批 JOIN 后合并，避免单次大事务与临时表溢出；③ 冗余换连接：在事实表里冗余维度字段（宽表化），彻底消除 JOIN——这是数仓里最常见也最有效的办法。若都不行，就该考虑走 Spark/Flink 而非在数据库里硬算。

Q：join_buffer_size 调大有用吗？

A：作用有限且容易误导。它只影响 Block Nested Loop 一次能缓存多少行，但复杂度仍是 O(N×M)，调大只是减少内表扫描的轮数。真正的解法是给连接列加索引，让 Nested Loop 变成 Index Nested Loop（复杂度降到 O(N log M)）。此外它是按连接分配的，并发高时过大会导致内存暴涨——全局调到几百 MB 是危险的。

Q：LEFT JOIN 和 INNER JOIN 性能有差别吗？

A：通常 LEFT JOIN 更慢，但不是因为算法不同，而是因为它限制了优化器的自由度：LEFT JOIN 保证左表行不丢失，优化器不能随意调整连接顺序（某些情况下也不能把左表放内层）。 INNER JOIN 则允许优化器自由重排。所以语义允许时优先用 INNER JOIN——这不是微优化，在大表多连接时可能差一个数量级。
