向量库在业务系统中的职责

Embedding 负责产生表示，向量索引负责召回相近 ID，业务库或对象存储负责权威原文与事务。

01为什么需要向量数据库

文本/图像经 Embedding 后变成高维向量。语义检索 = 找「与查询向量最相似的 Top-K 个」。当库里有百万/十亿级向量时，逐一计算余弦相似度（O(N·d)）不可接受，需要专用索引结构来加速且可扩展地检索。

向量库不是普通数据库加一列向量，而是围绕「相似度检索」优化的索引 + 存储 + 过滤 + 扩展性系统。

先搞清楚向量是从哪来的

向量数据库本身不生产语义 —— 它只是一个能高效做「最近邻查找」的容器。语义来自嵌入模型（embedding model）：把文本、图片、音频映射成一个高维数组，使得「意思相近的东西，在空间里也靠得近」。

同一个模型把问题变成点， 然后去找空间里离它最近的 k 个点。 这叫近似最近邻（ANN）检索， 向量库的全部本领基本就在这儿。
嵌入模型把语义变成坐标，向量库负责找最近的点

它到底解决了数据库的什么问题

传统数据库的索引（B+ 树、倒排索引）是为了精确匹配设计的：等于某个值、落在某个区间、包含某个词。面对「找和这句话意思最像的十条」这种请求，它们无能为力。

维度传统数据库向量数据库
擅长精确查询、范围查询、事务、聚合相似性检索（top-k 近邻）
索引结构B+ 树、哈希、倒排索引HNSW、IVF、PQ 等图/聚类/量化结构
查询语义AND/OR、范围、聚合距离度量：余弦 / 内积 / 欧氏
结果性质确定答案近似答案（用少量召回率换巨大速度）
常见搭配业务主数据作为旁路，与业务库配合回取原文

一句关键认知：向量库通常不单独提供答案内容。它帮你快速找出「最相近的 id」，随后你还要拿这些 id 去业务库或对象存储里取回原文、标题、时间戳等。把向量库当成「语义索引」而不是「数据库替代品」，设计会清晰很多。

05与 RAG 的关系

向量库是 RAG 的检索底座：文档切块 → Embedding → 入库；用户提问 → 向量化 → ANN 检索 Top-K → 拼进 prompt。RAG 效果好不好，一半取决于向量检索质量（召回率、重排）。详见 rag 目录。

实战坑：相似度 0.9 也可能召回错文档（语义歧义、切块边界、元数据过滤缺失）。这不是向量库 bug，而是「检索链路」问题——需配合重排(rerank)与混合检索。

它在完整系统里的位置

离线 ingestion 文档 → 切分（chunk）→ embedding → 写入向量库（同时带上 metadata 与原文 id） 在线查询（RAG 的典型形态） 用户问题 ↓ embedding 查询向量 ↓ ANN 检索 top-k 候选片段 id 列表 ↓ 回表取原文（业务库 / 对象存储） 组装 prompt → 送给大模型 → 回答 注意中间那步「回表」： 向量库存 Vectors + metadata；原文通常仍存在原处。

什么时候其实不需要专门的向量数据库：

  • 数据量很小（几万条以内）且变更不频繁 —— 直接内存里用 numpy 暴力算，几毫秒出结果，还绝对精确。
  • 已经用了支持向量类型的数据库（如带向量扩展的关系库）且规模适中 —— 增加一个专用组件带来的运维成本未必划算。
  • 检索请求极少 —— 批处理地算一遍也没什么不可以。

真正的分水岭在于：数据量上到百万级以上、要求低延迟 top-k、还要同时做元数据过滤 —— 这时专门的向量索引才有明显价值。
