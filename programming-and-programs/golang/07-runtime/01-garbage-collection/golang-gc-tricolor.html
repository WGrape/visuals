🛡️ 写屏障 (Write Barrier) 演示

在并发标记期间，Mutator（你的业务代码）可能修改对象引用。 比如把 B.next = D 改成 B.next = E，而此时 B 已经变黑了（不会再扫）， 如果没有写屏障，E 就会被漏标，导致活对象被错误回收 💀。

Golang 使用 Dijkstra 写屏障：当黑色对象写入新引用时，自动把被引用对象染灰。

💡 核心思想

三色标记法把对象分成 白、灰、黑 三组。从根对象出发，用 BFS 方式遍历引用图， 标记过程结束后，仍然白色的对象就是垃圾，可以回收。 整个过程可以和用户代码并发执行，只短暂 STW。

📋 GC 四个阶段

① Mark Setup — STW，开启写屏障
② Marking — 并发标记，找到所有可达对象
③ Mark Termination — STW，关闭写屏障
④ Sweep — 并发清扫，回收白色对象内存

🤔 为什么用三色？

传统的"标记-清除"需要长时间 STW，程序完全停顿。
三色标记 + 写屏障让 GC 可以和 Mutator 并发工作， 这是 Go 低延迟 GC 的关键设计（目标 < 1ms STW）。

⚙️ Go 中的实际对应

  • runtime.gcStart() — 触发 GC，进入 Mark Setup 阶段
  • gcBgMarkWorker — 后台 goroutine 并发执行标记工作
  • writeBarrier — 编译器在指针写操作前插入的屏障指令
  • runtime.GC() — 手动触发 GC（通常不需要，Go 自动管理）
  • GOGC 环境变量 — 控制 GC 触发阈值，默认 100（堆增长 100% 触发）
  • GODEBUG=gctrace=1 — 打印 GC 日志，观察实际回收行为

三色标记：用三个集合描述一次 GC

Go 的 GC 是并发三色标记清除。所谓三色，就是把堆上的对象按「扫描进度」分成三类，让标记工作能与业务协程同时推进。

三色的含义与「黑不能指向白」不变式
白还没访问到；结束时仍是白就是垃圾。
灰已发现但字段没扫完，在待处理队列里。
黑自己与字段都扫完，本次确认存活。
写屏障并发修改时保住不变式的一小段编译器插入代码。

一次 GC 的四个阶段与两次 STW

阶段是否停顿做什么耗时特征
Sweep TerminationSTW清扫上一轮残留，开启写屏障，扫描根极短，通常微秒到亚毫秒
Mark并发从灰队列出发遍历对象图，与业务同时跑主要耗时，占用约 25% CPU
Mark TerminationSTW关闭写屏障，完成收尾标记与统计很短，通常亚毫秒级
Sweep并发回收白色对象，按需归还内存给 OS与业务并发，不阻塞分配

为什么还要两次 STW？根集合（栈、全局变量）必须在一致状态下扫描，而打开写屏障、切换标记状态也需要一个全局同步点。这两次停顿都被压缩到极短，剩下的重活全部并发完成——这是 Go GC 停顿能做到毫秒以下的原因。

写屏障：并发标记的安全带

业务协程在标记期间仍在改指针。如果放任不管，就可能出现「黑对象新增指向白对象的引用，而该白对象再也没人能发现」——对象被误回收。写屏障就是编译器在每次指针写入时插入的一小段保护代码。

// 语义示意（非真实源码） writeBarrier(slot *unsafe.Pointer, ptr unsafe.Pointer) { shade(*slot) // 删除屏障：把被覆盖的旧引用置灰 shade(ptr) // 插入屏障：把新写入的引用置灰 *slot = ptr } // Go 1.8 起使用混合写屏障（插入 + 删除） // 带来的直接好处：不再需要在标记结束时重新扫描栈 // 从而把第二次 STW 从「与栈数量成正比」压缩到近乎恒定
插入屏障新引用指向白对象时，把白置灰
删除屏障旧引用被覆盖前，把旧目标置灰
混合屏障两者结合，兼顾正确性与停顿
代价每次指针写入多几条指令，写入变慢一点
只在标记期开非标记阶段写屏障是关闭的
对使用者透明写业务代码无需感知

什么时候触发 GC，怎么调

GOGC=100（默认）堆比上次 GC 后的存活堆增长 100% 时触发
GOGC=off关闭自动 GC，只能手动 runtime.GC()
调小 GOGC更早更频繁 GC：堆占用低，CPU 开销高
调大 GOGC更少 GC：CPU 省，但堆占用高
memory limit可用 SetMemoryLimit 设定软上限，防止 OOM
手动触发runtime.GC() 用于压测与关键节点，不建议常态调用

调优的正确顺序：先看是不是分配太多（pprof 找热点 → 复用与预分配），再考虑调 GOGC。单纯把 GOGC 调大只是把问题推后，堆峰值反而更高。

深入自检

三色标记会不会漏掉对象？

有了写屏障就不会。写屏障保证「黑对象新增的白色引用会被置灰」，从而破坏条件被消除。Go 1.8 起使用混合写屏障，连栈都不需要在标记结束时重新扫描，正确性由编译器插入的代码保证。

为什么 Go 的 STW 能这么短，JVM 的 CMS 却要重新扫描？

关键在于混合写屏障把栈也纳入保护，省掉了标记结束时的栈重扫。栈重扫的耗时与 goroutine 数量和栈大小成正比，正是老一代收集器停顿的主要来源。

GC 占用 25% CPU 是什么意思？

指并发标记阶段最多会用到约四分之一的 CPU 资源来做标记工作（由专门的 GC worker 协程承担）。它不是「总 CPU 的四分之一被浪费」，而是标记工作的调度上限，用于平衡吞吐与回收速度。

对象被回收了，为什么 RSS 不下降？

Go 回收的是自己的堆空间，不一定立刻把物理页还给操作系统。运行时会保留一部分以便后续复用，并按策略逐步归还。观察应使用 Go 自己的指标（HeapAlloc、HeapInuse），而不是进程 RSS。

碰到 GC 压力大的服务，第一步做什么？

先量化：打开 pprof 看 alloc_space 找分配热点，看 heap profile 找占用大户；再判断是分配速率问题还是存活对象过多。前者靠复用与预分配，后者要查是否真有泄漏或缓存无上限。
