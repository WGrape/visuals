后训练 · 方法四

RL 强化学习后训练
Reinforcement Learning Post-training

SFT 让模型"会答"，DPO 让模型"讨喜"，但想让模型"会思考、能自我验证、推理更强"，往往要靠强化学习。 它用"奖励信号"直接优化策略：经典的 RLHF（用人类偏好训奖励模型 + PPO），以及近年引爆推理的 RLVR / GRPO（用"答案对不对"这种可验证奖励）。 下面把两种范式和完整训练过程讲清。

第 1 步 · 定义

RL 后训练到底在做什么

一句话：把"生成回答"当成一个序贯决策问题——模型每生成一个 token 就是一步动作，环境（奖励模型或可验证判题器）给一个分数，目标是最大化"期望总奖励"。 和 SFT/DPO 不同，RL 不只"模仿/比较现成回答"，而是让模型去探索出更高奖励的回答方式——这正是它能练出更强推理的原因。

RLHF（偏好驱动）

奖励来自奖励模型 RM（用人类偏好训出来的打分器）。擅长把回答调成"人类觉得好"的形态：更有用、更无害、更自然。

RLVR / GRPO（可验证驱动）

奖励来自判题器：答案对就 +1，错就 0（如数学/代码能自动判对错）。专门练"推理正确率"与"长链条思考"。

图 1：RL 后训练站在 SFT 之上，用奖励信号把策略推向"更高分"的回答分布
第 2 步 · 动机

为什么 DPO 不够，还要 RL

DPO 只能比较"已经存在的两个回答"，它本身不产生新回答。而 RL 的模型每步都在采样、都在"试"——它能发现训练数据里没有、但奖励更高的回答套路（比如更长的中间推导、自我检查）。这在数学、代码这类任务上带来过阶跃式提升。

能力SFTDPORL（RLVR）
学会格式✅✅✅
调主观偏好❌✅✅（需 RM）
探索出新答法❌❌✅ 核心优势
练推理正确率弱弱✅ 最强
工程复杂度低低高
现实选型：多数团队"先 SFT，再 DPO"就够用；只有当目标是推理能力跃升（数学/代码/科学题）、或确实需要一个"奖励"而非"偏好对"时，才上 RL。RLVR 因为奖励可自动判定，近年比 RLHF 更常被用于推理模型。
第 3 步 · 两种范式

RLHF 与 RLVR / GRPO

① RLHF：奖励模型 + PPO

先用偏好数据训一个奖励模型 RM（给任意回答打一个标量分），再用 PPO 让策略去最大化 RM 分数，同时用 KL 惩罚锚住参考模型，防止跑飞。

图 2：RLHF 的四模型架构——能力最强但最重

② RLVR / GRPO：可验证奖励，省掉价值网络

RLVR（Reinforcement Learning with Verifiable Rewards）用"答案对错"做奖励，不再需要人类偏好的奖励模型。GRPO 进一步改进：对同一问题采样一组回答，用这组回答奖励的均值作基线来算相对优势，从而省掉了 Critic 价值网络——显存和稳定性都更好。

图 3：GRPO 用"组内相对优劣"替代价值网络，是推理模型最常用的 RL 配方
为什么 GRPO 适合推理：数学/代码一题能自动判对错，于是奖励可验证、可批量生成。模型在大量"试错—被判分"的循环里，逐渐学会"先列步骤、再自我验证、最后给答案"这类高奖励行为——这是纯 SFT/DPO 喂不出来的。
第 4 步 · 训练过程

RL 后训练的完整流程

六个环节：准备 prompt 池 → 采样回答 → 打分（RM 或判题器）→ 估计优势 → 策略更新（含 KL）→ 评测。PPO 与 GRPO 只在"优势估计"那步不同，其余一致。

图 4：RL 训练是一个"采样—打分—更新"的反复循环；评测要防奖励黑客

目标函数（PPO 视角）

maxθ E [ R(x, y) − β · KL( πθ(y|x) ‖ πref(y|x) ) ]

R 是奖励（RLHF 来自 RM，RLVR 来自判题）；β·KL 把策略拉住，别为了刷分而丧失基本能力。GRPO 把 R 换成"组内相对优势"，于是省掉 Critic，其余思想一致。

奖励黑客 Reward Hacking
模型找到"骗高分"的捷径（如套话、重复、格式骗分）却不真变好。靠多维评测 + 人类抽检发现。
KL 失控
β 太小 → 策略偏离 SFT 太远，能力崩坏；β 太大 → 学不动。需调参+早停。
训练不稳定
RL 天然有方差。GRPO、小批量、长 warmup 都能提升稳定性。
第 5 步 · 实现

最小可运行骨架

用 TRL 的 GRPOConfig + GRPOTrainer，只需一个可验证奖励函数（这里用"答案是否匹配标准解"）和 SFT 起点模型，比手写 PPO 简洁很多。

from datasets import load_dataset
from transformers import AutoTokenizer, AutoModelForCausalLM
from trl import GRPOConfig, GRPOTrainer

model_id = "Qwen/Qwen2.5-7B-Instruct"   # SFT 起点
tok = AutoTokenizer.from_pretrained(model_id)
model = AutoModelForCausalLM.from_pretrained(model_id, torch_dtype="bfloat16")

ds = load_dataset("json", data_files="data/math_prompts.jsonl")["train"]

# 可验证奖励：抽取模型答案，与标准解比对
import re
def reward_correct(completions, **kw):
    outs = [c[0]["content"] if isinstance(c, list) else c for c in completions]
    scores = []
    for o in outs:
        m = re.search(r"\\boxed\\{([^}]*)\\}", o)       # 取 \\boxed{} 里的答案
        pred = m.group(1).strip() if m else ""
        scores.append(1.0 if pred == kw["gold"] else 0.0)
    return scores

cfg = GRPOConfig(
    output_dir="ckpt/grpo",
    num_generations=8,          # ⚠ 每题采样 G 个回答，G 即组大小
    learning_rate=1e-6,
    max_completion_length=1024, # 允许长链条思考
    beta=0.0,                   # GRPO 用组内基线，常把 KL 设小
    bf16=True,
    report_to="none",
)

GRPOTrainer(
    model=model,
    args=cfg,
    train_dataset=ds,
    reward_funcs=reward_correct,
).train()
RLHF 的奖励模型别省质量：如果走 RLHF 而非 RLVR，那么 RM 的校准直接决定上限——RM 偏一点，策略就往偏处优化（奖励黑客）。RM 要用多维度、低噪声的偏好数据，且和策略保持"同步更新"式的迭代训练。

评测要同时看"分数"和"真质量"

# 训练曲线:奖励均值 ↑ 是必要条件,但不是充分条件
# 必须额外看:
#   1) 验证集正确率(RLVR) / 人类胜率(RLHF) 是否真涨
#   2) 回答长度与模式是否异常(长度作弊/套话)
#   3) 通用能力回归(指令遵循/安全)有无退化
# 任一项异常 → 停训调参,不要被奖励曲线骗了
第 6 步 · 小结

踩坑清单与一句话总结

常见坑表现怎么解
奖励黑客奖励涨但真实质量不涨多维评测 + 人工抽检；奖励加格式/长度惩罚
KL 失控策略跑飞，能力崩坏调大 β；早停；控制单步更新幅度
训练不稳定loss 剧烈抖动GRPO 替代 PPO；小批量；长 warmup
没先 SFT冷启动太差，RL 学不动用合格的 SFT 模型作起点
RM 有偏RLHF 越训越歪高质量偏好数据；RM 与策略同步迭代
只练推理忘通用数学涨了但聊天变差奖励混合通用任务；双轨评测

一句话：RL 后训练 = 把"生成回答"当作决策过程，用奖励信号（RM 或判题器）反复"采样—打分—更新"策略，逼出 SFT/DPO 学不到的更强推理与探索能力。

RLHF 用人类偏好训奖励模型 + PPO，最重但也最通用；RLVR / GRPO 用"答案对错"做可验证奖励，省掉价值网络、专为推理而生。它站在 SFT 之上，是后训练链路里最贵、也最能拉开上限的一环。

PPO / GRPO 的工程账：显存、吞吐与稳定性

RLHF 之所以难，不在于算法，而在于它要同时跑 4 个模型、在线采样、还要对抗训练不稳定。理解这四份显存，才知道为什么 RLHF 贵。

GRPO 伪代码与超参

# GRPO 的核心（伪代码，看懂这段就懂了）
for prompt in batch:
    samples = actor.sample(prompt, n=G)        # G=8~16 条
    rewards = reward_model(samples)            # 每条打个分
    # 关键：组内归一化，不需要 critic
    adv = (rewards - rewards.mean()) / (rewards.std() + eps)
    loss = -mean(adv * logprob(samples))       # 策略梯度
    loss += kl_coef * KL(actor || reference)   # 约束别跑太远

# 典型超参（7B, GRPO）
G (group size):        8~16        # 太小方差大，太大成本高
kl_coef:               0.001~0.04  # 0 也可以（DAPO 等改进）
learning_rate:         1e-6~3e-6   # 比 SFT 小一个量级
temperature:           0.7~1.0     # 采样温度，训练时也要保持探索
max_new_tokens:        1024~4096
num_iterations:        1           # on-policy，通常不复用旧样本

# 工程上省显存的常见做法
#   - vLLM 做 rollout（比 HF generate 快 5~10 倍）
#   - Actor 用 FSDP / ZeRO-3 分片
#   - Reference 用 LoRA 的 base（disable adapter 即得）
#   - Reward 模型可以很小（1B~3B 就够做评分）
  • RLHF 的收益分布不均：对有明确对错的任务（数学、代码、逻辑推理）提升巨大（R1 类模型在数学上能提 20~40 分）；对主观任务（写作、闲聊）提升有限，主要改善的是「格式和安全」。所以资源有限时，优先在可验证任务上做 RL。
  • 可验证奖励（RLVR）是当前主流：数学对答案、代码跑单测、SQL 执行比对——这类奖励不需要奖励模型，不会 hacking，是 DeepSeek-R1 效果爆发的关键。
  • 「啊哈时刻」不是训练目标：模型自发出现自我反思/长思考，是 RL 在可验证任务上的副产品，硬去模仿它反而没用。
  • 先 SFT 打底再 RL：直接在 base 上做 RL，样本效率极低（大量采样都是无效格式）。标准流程是 SFT →（DPO）→ RL。
  • rollout 是最大瓶颈：RLHF 训练时间里 80% 以上花在采样生成上。用 vLLM/SGLang 加速 rollout，比优化训练框架收益大得多。
为什么 GRPO 能省掉 Critic？

PPO 需要 Critic 来估计「这个状态原本值多少分」，从而算出「这一步比平均好多少」（优势函数）。GRPO 的洞察是：同一个 prompt 采样 G 条回复，这 G 条的平均分本身就是很好的基线——用组内均值和标准差归一化 rewards，就直接得到了优势，不需要额外的价值网络。代价是：① 每个 prompt 要采样 G 条（G=8~16），采样成本上升；② 组内方差小时优势估计噪声大。但综合下来，省掉一个和 actor 同规模的网络 + 对应的训练不稳定，通常是划算的，这也是 GRPO 迅速成为主流的的原因。

KL 惩罚要不要开？

趋势是越用越小，甚至关掉。早期 PPO 用较大 KL 系数（0.05~0.1）防止跑飞；GRPO 常用 0.001~0.04；DAPO、Dr.GRPO 等改进工作直接去掉 KL，理由是：如果 reward 设计得好（可验证奖励），模型没有 hacking 空间，KL 反而是束缚，限制了探索。实践建议：先用小 KL（0.01）跑通，观察 reward 和生成质量；如果 reward 涨但质量没提升，先怀疑 reward hacking 而不是加大 KL；只有当模型输出开始崩坏时才提高 KL。

RLHF 要多少算力才够？

粗略量级（7B 模型，可验证任务）：入门级——单节点 8×80G，跑几千步、几万条采样，1~2 天能看到明显提升；有竞争力——几十到上百节点周级训练，采样量在百万级。影响成本的关键是 rollout：长思考（CoT）模型的每条采样要生成几千 token，采样成本是短回答的 5~10 倍。所以工程优化的第一优先级是提高 rollout 吞吐（vLLM/SGLang + 连续批处理 + 前缀缓存），第二优先级才是训练框架。如果只有 1~2 张卡，建议先做 DPO 或直接用现成的 RL 数据集做 SFT 蒸馏，性价比更高。
