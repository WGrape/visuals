TLS 证书链与主机名校验：锁标志从哪里来

沿浏览器验证证书的顺序解释信任根、中间证书、SAN、有效期和常见故障。

加密与身份验证是两件事

TLS 握手会协商密钥并加密后续流量，但客户端还必须确认“对方确实是我想访问的站点”。服务器提供证书和相关链信息，客户端验证签名链是否能连到本地信任的根证书、证书是否在有效期内、主机名是否匹配以及用途是否适合服务端认证。只有双方把加密与身份校验都做对，浏览器锁标志才有意义。

证书中的公钥不是直接拿来加密整个网页；现代 TLS 通常通过密钥交换建立会话密钥，再用对称加密保护数据。证书主要把站点身份与公钥绑定。把“有 HTTPS”解释为内容一定真实也不准确：恶意网站也可申请自己域名的合法证书，TLS 证明的是当前连接的域名身份，不证明网页业务内容可靠。

链是怎样搭起来的

假设服务器证书由中间 CA I 签发，I 又由根 CA R 签发。浏览器或操作系统预装并信任 R，服务器通常发送自己的证书和必要的中间证书，让客户端能逐级验证签名。根证书通常不需要服务器重复发送。若服务器漏配 I，部分客户端可能因本地刚好缓存了 I 而可用，另一些客户端却报“不完整证书链”。

证书链验证不是只看证书文件数量，还要检查各级签发关系、用途、约束与有效期。根信任来自客户端自身的信任库，而不是服务器说“请相信这个根”。企业代理若在终端安装了自己的根证书，可能对内部流量进行 TLS 检查；诊断时应明确这是受管设备的信任策略变化。

SAN 与主机名

浏览器访问 `api.example.test`，证书需要在 Subject Alternative Name 中包含该 DNS 名称或有效通配匹配。证书只覆盖 `www.example.test` 时，访问 api 子域会失败，即使两者指向同一个 IP。一个 IP 上可服务多个域名，客户端通过 TLS ClientHello 中的 SNI 等信息帮助服务器选择相应证书，之后仍要对访问的主机名做校验。

通配证书 `*.example.test` 常覆盖一层子域，例如 `api.example.test`，却不能按想当然覆盖 `a.b.example.test` 或裸域 `example.test`。具体匹配遵守客户端规则。排查证书错误时要记录访问 URL 的主机名、实际握手拿到的证书 SAN、SNI 值，而非只看证书文件在磁盘上存在。

有效期与时间问题

证书有 Not Before 和 Not After 时间。若客户端时钟严重偏差，合法证书也可能被判为尚未生效或已过期。证书更新时，负载均衡器、反向代理和各地域节点可能尚未全部加载新证书；从一个节点验证成功，不代表所有接入点已完成切换。监测应覆盖各域名和代表性节点，并在到期前留出更新与回滚时间。

服务器证书、私钥和中间证书要相互对应。把新证书配上旧私钥会导致握手失败；只上传新证书但未重载服务也可能继续展示旧证书。私钥应按最小权限保存，不能为了方便排查把内容贴进公开日志或页面。

撤销与信任边界

证书可能在到期前被撤销，例如私钥泄漏。OCSP、CRL 等机制提供撤销状态信息，但客户端是否阻断连接、是否使用 stapling、离线时如何处理取决于实现与策略。不能把“证书仍在有效期内”当作绝对安全证明。对于高价值系统，还需监控证书签发记录和异常替换。

证书正确也不代表端到端都加密：若 TLS 在 CDN 或负载均衡终止，后端链路可能重新建立 TLS，也可能是其他保护方式。系统图要标出每段连接的终止点、证书和信任域，才说得清数据在哪些节点可见。

一次故障排查

用户报告“浏览器提示证书不安全”。先确认访问的准确域名与时间，再看实际握手证书的 SAN、签发者、有效期和完整链。若只有某地域报错，检查该地域入口或 CDN 节点是否加载旧证书；若只有老系统报错，检查其信任库和中间链。若通过代理访问才报错，记录代理证书和终端信任配置。

修复后应分别从浏览器和命令行按相同主机名验证 TLS，并确认 HTTP 请求实际到达预期应用。不要通过关闭证书校验来“解决”生产故障，那只是移除了身份验证。

自检

证书由公开 CA 签发，但 SAN 没有访问的域名，浏览器应接受吗？

不应接受。签名链可信还不够，访问主机名必须匹配证书允许的身份。
