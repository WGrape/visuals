向量数据库与 ANN 检索

Embedding 把文本变成向量后，问题变成「在千万向量里找最近邻」。暴力比对太慢，于是有了向量库与近似最近邻（ANN）。面试常问：HNSW 是什么？召回率和延迟怎么权衡？选哪个库？

01为什么需要向量数据库

文本/图像经 Embedding 后变成高维向量。语义检索 = 找「与查询向量最相似的 Top-K 个」。当库里有百万/十亿级向量时，逐一计算余弦相似度（O(N·d)）不可接受，需要专用索引结构来加速且可扩展地检索。

向量库不是普通数据库加一列向量，而是围绕「相似度检索」优化的索引 + 存储 + 过滤 + 扩展性系统。

02精确 vs 近似（ANN）

精确最近邻 (Exact / KNN)

结果 100% 正确，但慢，只适合小数据。

近似最近邻 (ANN)

用少量精度换大幅加速，召回率 90%+ 即可，工业默认。

实际系统几乎都用 ANN：宁可漏掉个别最相似项，也要把毫秒级延迟和海量规模跑出来。

03主流索引算法

IVF（倒排）

先聚类分桶，查询只搜最近的几个桶，缩小范围。快但依赖聚类质量。

PQ（乘积量化）

把高维向量切成多段分别压缩，用近似距离代替全量计算，省内存。

HNSW（分层可导航小世界）

用多层图做「高速公路式」导航，查询沿边快速逼近近邻。最常用。

LSH（局部敏感哈希）

相似向量高概率落入同桶，靠哈希快速粗筛。实现简单但精度一般。

04HNSW 直觉图解

查询从最上层稀疏层进入，靠长边快速「空降」到目标附近，再下钻到稠密层精确定位。类似「先坐高铁到城市，再走路到门口」。内存换速度，召回率高、延迟低。

05与 RAG 的关系

向量库是 RAG 的检索底座：文档切块 → Embedding → 入库；用户提问 → 向量化 → ANN 检索 Top-K → 拼进 prompt。RAG 效果好不好，一半取决于向量检索质量（召回率、重排）。详见 rag 目录。

实战坑：相似度 0.9 也可能召回错文档（语义歧义、切块边界、元数据过滤缺失）。这不是向量库 bug，而是「检索链路」问题——需配合重排(rerank)与混合检索。

06选型对比

FAISS

Meta 开源库，索引算法全、轻量，常作为其他系统的内核；偏「库」非「服务」。

Milvus / Qdrant

生产级向量数据库，分布式、可扩展、带过滤与运维，适合大规模。

Chroma / pgvector

轻量/嵌入式，Chroma 适合原型；pgvector 让 Postgres 直接存向量，复用现有栈。

选型看：规模（百万 vs 十亿）、是否要分布式、是否要元数据过滤、团队运维能力。

先搞清楚向量是从哪来的

向量数据库本身不生产语义 —— 它只是一个能高效做「最近邻查找」的容器。语义来自嵌入模型（embedding model）：把文本、图片、音频映射成一个高维数组，使得「意思相近的东西，在空间里也靠得近」。

同一个模型把问题变成点， 然后去找空间里离它最近的 k 个点。 这叫近似最近邻（ANN）检索， 向量库的全部本领基本就在这儿。
嵌入模型把语义变成坐标，向量库负责找最近的点

它到底解决了数据库的什么问题

传统数据库的索引（B+ 树、倒排索引）是为了精确匹配设计的：等于某个值、落在某个区间、包含某个词。面对「找和这句话意思最像的十条」这种请求，它们无能为力。

维度传统数据库向量数据库
擅长精确查询、范围查询、事务、聚合相似性检索（top-k 近邻）
索引结构B+ 树、哈希、倒排索引HNSW、IVF、PQ 等图/聚类/量化结构
查询语义AND/OR、范围、聚合距离度量：余弦 / 内积 / 欧氏
结果性质确定答案近似答案（用少量召回率换巨大速度）
常见搭配业务主数据作为旁路，与业务库配合回取原文

一句关键认知：向量库通常不单独提供答案内容。它帮你快速找出「最相近的 id」，随后你还要拿这些 id 去业务库或对象存储里取回原文、标题、时间戳等。把向量库当成「语义索引」而不是「数据库替代品」，设计会清晰很多。

距离度量怎么选

度量公式要点适合场景注意
余弦相似度只看方向，不看长度文本语义（绝大多数通用 embedding）默认选项；很多模型在训练时就已归一化，此时与内积等价
内积 Dot方向 × 长度某些显式优化了内积的模型未归一化时长度会影响结果，不要混用
欧氏距离 L2几何直线距离图像/坐标类，某些需要真实距离的场景受维度灾难影响更明显，且必须同一模型同一预处理

不可混用原则：索引建立时用的度量必须与查询时一致；同一个库里不同集合用不同度量也完全可以，但一个集合内部必须统一。

它在完整系统里的位置

离线 ingestion 文档 → 切分（chunk）→ embedding → 写入向量库（同时带上 metadata 与原文 id） 在线查询（RAG 的典型形态） 用户问题 ↓ embedding 查询向量 ↓ ANN 检索 top-k 候选片段 id 列表 ↓ 回表取原文（业务库 / 对象存储） 组装 prompt → 送给大模型 → 回答 注意中间那步「回表」： 向量库存 Vectors + metadata；原文通常仍存在原处。

什么时候其实不需要专门的向量数据库：

  • 数据量很小（几万条以内）且变更不频繁 —— 直接内存里用 numpy 暴力算，几毫秒出结果，还绝对精确。
  • 已经用了支持向量类型的数据库（如带向量扩展的关系库）且规模适中 —— 增加一个专用组件带来的运维成本未必划算。
  • 检索请求极少 —— 批处理地算一遍也没什么不可以。

真正的分水岭在于：数据量上到百万级以上、要求低延迟 top-k、还要同时做元数据过滤 —— 这时专门的向量索引才有明显价值。

深入自检

向量检索为什么是「近似」的？

因为高维空间里精确最近邻的代价非常高（维度灾难让各种剪枝结构失效）。实际系统都会接受「绝大多数情况下找到真正最近的那些点」这一近似目标：通过图索引 HNSW 或聚类倒排 IVF 只访问一小部分候选，把延迟从「扫全库」降到毫秒级，代价是偶尔可能漏掉一两个真正的近邻。

什么时候应该用关键词检索而不是向量检索？

当需要精确匹配时：订单号、SKU、错误码、专有名词、人名的精确拼写、布尔条件过滤。向量检索的优势是「语义相近」，但它对精确符号、稀有字符串、需要完全命中的场景天生不擅长。生产系统常用混合检索（关键词 + 向量两条路都走，再用融合算法合并结果）。

换 embedding 模型会怎样？

必须全量重建索引。不同模型的向量空间完全不可比 —— 同一句话在两个模型里是两个不同的点，混在一起检索毫无意义。所以模型选型要在项目早期定好，并且把「模型版本」写进每条数据的 metadata，便于将来区分与迁移。

chunk 切分为什么这么重要？

因为检索的最小粒度就是 chunk。切得太大，噪声多、语义不集中、塞进 prompt 还占 token；切得太小，丢失上下文、一句话被拆散。常见的做法是按语义边界切 + 相邻块之间保留少量重叠，并用实际检索效果（召回相关文档的准确率）来调参，而不是拍脑袋定字数。
