指令格式与寻址方式：CPU 到底怎么「读懂」一条指令

指令是软件与硬件之间唯一合法的语言。它的编码方式（定长/变长）、操作数来源（寄存器/内存/立即数）决定了译码器复杂度、代码密度和流水线难度。

一句话定位：opcode 说什么，操作数说在哪

一条指令至少包含两部分：做什么（操作码）和对谁做（操作数）。操作数可以来自寄存器、立即数、内存，而「内存地址怎么算出来」就是寻址方式——它是 ISA 里最影响编译器与性能的设计之一。

定长指令ARM64 / RISC-V 基础指令 4 字节，译码简单
变长指令x86 1~15 字节，代码密度高但译码贵
三地址add rd, rs1, rs2（RISC 风格，结果单独存）
二地址add eax, ebx（x86 风格，结果覆盖一个源）
三种典型格式：定长编码让并行译码成为可能

七种寻址方式及其代价

方式示例地址怎么来典型用途
立即数add eax, 5常数直接编码在指令里常量运算
寄存器add eax, ebx操作数就在寄存器最快（0 次访存）
直接mov eax, [0x1000]指令里给出绝对地址全局变量（位置无关码少用）
间接mov eax, [ebx]寄存器里存地址指针
基址+偏移mov eax, [rbp-8]寄存器 + 常数偏移局部变量、结构体成员
变址mov eax, [rbx+rcx*4]基址 + 索引 × 元素大小数组遍历
PC 相对lea rax, [rip+0x20]当前指令地址 + 偏移位置无关代码、跳转
为什么 PC 相对寻址重要

位置无关可执行文件（PIE）与共享库必须能在任意基址加载，PC 相对寻址天然满足这一点；绝对地址则需要重定位表，加载时打补丁。

定长 vs 变长：一笔明账

维度ARM64 / RISC-V（定长）x86-64（变长）
指令长度4 字节1~15 字节，平均 4~5
译码可并行译码多条，边界天然对齐需逐字节扫描前缀，译码器复杂
代码密度较低（简单指令也要 4 字节）较高（常用指令短编码）
扩展性靠预留编码空间靠前缀与保留位
典型取舍硬件简单、频率高、功耗低兼容性极强、前端复杂但缓存友好

这不是「谁更先进」的问题，而是历史包袱与目标的差异：x86 要兼容 40 年的二进制，ARM 从嵌入式起步、以能效为先。RISC-V 则把「可扩展」写进了设计目标。

算一算：一条 load 的地址怎么产生

# C 源码
int arr[100];
x = arr[i];

# 编译成 RISC-V（示意）
slli  t0, a1, 2        # i * 4
add   t0, a0, t0       # &arr + i*4
lw    a2, 0(t0)        # 从该地址读 4 字节

# 同样的事在 x86-64 只需一条（变长指令，复杂寻址）
mov   eax, DWORD PTR [rdi + rsi*4]

x86 的「复杂寻址」把三条指令压成一条，代码更短、取指压力更小；RISC 把地址计算暴露给编译器，硬件只需简单加法。两种路线的性能差异，最终由「译码复杂度 vs 指令数」的平衡决定。

排障：ISA 层面的典型困惑

现象原因怎么理解
汇编里同一条指令长度不同x86 变长编码 + 前缀用 objdump -d 看真实字节
改一行代码指令数暴增编译器选了不同寻址方式看 -S 输出，比较 lea/mov 组合
跳转范围不够报错短跳转只有 8 位偏移编译器自动换长跳转，手写汇编要注意
对齐后代码变慢热点循环跨缓存行/译码边界perf 看 i-cache miss
同一份源码两个平台差 2 倍指令密度与前端宽度不同对比 IPC 与指令数

原理与取舍：ISA 设计的三条硬约束

  1. 兼容性：已发布的编码不能改语义，只能加新前缀/新扩展（x86 的 VEX、RISC-V 的扩展位）。
  2. 译码可行性：定长指令可以多条并行译码；变长指令必须顺序扫描，前端宽度受限。
  3. 寄存器数量：x86-64 有 16 个通用寄存器，ARM64 有 31 个。寄存器少 → 更多 spill 到栈；多 → 指令编码需要更多位。
为什么 RISC 指令要定长？

定长让「第 N 条指令的起始位置」可以直接算出（基址 + 4N），译码器可以并行取多条、流水线不用等上一条译码完。

x86 为什么不改成定长？

二进制兼容是它的生命线。改编码等于让过去四十年的软件全部失效，代价无人能承受。

寻址方式多是不是更好？

对编译器友好、代码密度高，但会增加译码与地址生成的复杂度，也挤占编码空间。RISC 倾向于「少而规整」，把组合留给编译器。
