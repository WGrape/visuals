🔥 热 key 与大 key：缓存运维的两大杀手

一个 key 被打爆（热 key）或一个 key 太大（大 key），都能让看似健康的 Redis 集群出问题。

🔥

热 key

单 key QPS 极高，压垮单分片

🐘

大 key

单 key 体积大，阻塞与网络打满

🔍

如何发现

热点探测 / 大 key 扫描

🛠️

如何治理

本地缓存 / 拆分 / 压缩

先建立直觉：一条车道堵死 vs 一辆超宽车

高速公路有很多车道（Redis 分片），绝大多数车流被均匀分散。但：

  • 热 key：几万辆车全都挤向同一条车道——其他车道空着，这一条堵死。
  • 大 key：一辆超宽卡车——它一辆就占满路面，后面的车全被堵住，且过收费站特别慢。

两者都会让「整体资源充足」的系统出现局部瘫痪。

热 key（Hot Key）

为什么危险

Redis 集群按 key 分片，一个 key 只会落在一个分片上。所以单个 key 的访问量无法被集群横向分散——你加再多机器，这个 key 的压力还是全在那一个分片上。

典型后果：某分片 CPU 打满、带宽打满、响应变慢 → 该分片超时 → 上游重试 → 压力更大 → 最终分片不可用。而集群其他分片资源闲置，形成「整体很闲但服务不可用」的怪象。

常见来源

  • 爆款商品、热搜词条、头部主播直播间；
  • 秒杀活动的商品库存 key；
  • 全局配置、首页 banner 等所有请求都要读的 key。

治理手段

手段做法效果
本地缓存热点 key 在应用进程内再缓存一份✅ 最有效，大部分请求不到 Redis
key 分片（打散）stock:1001 → stock:1001:0~9 十个副本✅ 把压力分到多个分片
读写分离该 key 的读走从节点⚠️ 缓解，从节点也有限
限流对该 key 的访问量做上限保护性兜底
// key 打散：把热 key 拆成 N 份，随机选一份读写
idx := rand.Intn(10)
key := fmt.Sprintf("stock:%d:%d", itemID, idx)
// 读：随机挑一个；写：需要更新全部 10 份（或用一致性策略）
打散的代价：写操作要更新所有副本，且要保证一致性；读时要处理「某个副本还没更新」的情况。只在读极多写极少的热 key 上使用。

大 key（Big Key）

为什么危险

Redis 是单线程处理命令的（工作线程），一个命令执行慢就会阻塞后面所有命令。操作一个包含百万元素的集合，可能耗时几百毫秒甚至数秒——期间整个实例的所有请求都在排队。

其他危害

  • 网络打满：一次读取几 MB，网卡带宽瞬间耗尽。
  • 删除阻塞：直接 DEL 一个大集合，释放内存本身就要很久，同样阻塞。
  • 内存不均：集群中某分片内存远高于其他，触发淘汰或 OOM。
  • 持久化卡顿：AOF 重写、RDB fork 时大 key 会放大开销。

治理手段

手段做法
拆分一个大 Hash 拆成多个小 Hash（按字段哈希分桶）
压缩value 序列化后压缩（注意 CPU 权衡）
只取需要的部分用 HMGET 代替 HGETALL，用 LRANGE 分页
异步删除用 UNLINK 代替 DEL（Redis 4.0+，后台线程释放内存）
改用合适结构用 zset 代替超大 list，用 HyperLogLog 做基数统计
异步删除很重要：DEL bigkey 是同步的，会阻塞；UNLINK bigkey 只是把 key 从字典摘除、真正的内存释放交给后台线程，几乎不阻塞。删除大 key 时应优先用 UNLINK。也可用 HSCAN 逐步删除。

如何发现它们

问题发现手段
大 keyredis-cli --bigkeys 扫描；MEMORY USAGE key 查单个；定期巡检脚本
热 keyredis-cli --hotkeys（需 LFU 淘汰策略）；MONITOR 采样统计（有性能损耗）；客户端埋点上报；代理层统计
MONITOR 慎用：它会把每条命令打印出来，对性能影响很大，只适合短时间的诊断采样，不能长期开着。

🎯 面试问答

Q：为什么加了 Redis 集群节点，热 key 问题还是没解决？
A：因为 Redis 分片是按 key 路由的——同一个 key 永远只会落到同一个分片，它的访问量不可能被分摊到其他节点。集群扩容只能分散「不同 key」的压力。要解决热 key，必须改变访问结构：要么在应用层加本地缓存让请求根本不到 Redis，要么把 key 打散成多份让它们落在不同分片。

Q：DEL 和 UNLINK 有什么区别？
A：DEL 是同步释放内存，大 key 会长时间阻塞主线程；UNLINK 先把 key 从键空间摘除（立即可见为已删除），实际内存回收交给后台线程异步完成，几乎不阻塞。Redis 4.0+ 支持。删除大 key 时应始终用 UNLINK，或用 HSCAN/LTRIM 分批处理。

Q：多大的 key 算大 key？
A：没有绝对标准，通常经验值：String 类型 value > 10KB，或集合元素数量 > 5000~10000。更重要的是看操作耗时——如果某个 key 的操作让实例出现毫秒级以上的延迟尖刺，就该处理了。因为 Redis 单线程，判断标准是「会不会明显阻塞后续命令」。

Q：热 key 用本地缓存会不会导致不一致？
A：会，这是它的代价。本地缓存无法被中心化地主动失效，所以各节点可能短暂持有不同版本的数据。缓解办法：① 设很短的本地 TTL（如 1~5 秒），不一致窗口极小；② 通过消息队列广播失效通知；③ 只在能容忍秒级陈旧的数据上使用（如商品描述），库存余额这类强一致数据不要这么做。
