CAP 理论

分布式系统的核心约束：一致性 (Consistency)、可用性 (Availability)、分区容错性 (Partition Tolerance)
在分区情况下，一致性和可用性只能二选一

三种分布式系统类型

由于网络分区必然发生，分布式系统只能选择实现其中两种特性

CA 系统

一致性 + 可用性

假设网络永远不会断开。不追求分区容错，在没有分区发生的情况下，同时保证一致性和可用性。 现实分布式系统中不存在，因为分区必然发生。

传统单机数据库 PostgreSQL (单节点)
CP 系统

一致性 + 分区容错

遇到分区时，拒绝请求以保证一致性。宁可返回错误，也绝不错写数据。 适合对数据准确性要求极高的场景，如金融、分布式锁、协调服务。

Redis Cluster ZooKeeper Etcd HBase MongoDB (多数派模式)
AP 系统

可用性 + 分区容错

遇到分区时，继续服务但可能返回旧数据。保证系统可用，但会短暂不一致。 适合对可用性要求高、能容忍最终一致的场景，如社交Feed、缓存、CDN。

Cassandra DynamoDB Riak CouchDB Redis Sentinel

💡 核心洞察

CAP 并不意味着"永远只能选择两个"。

在没有网络分区的正常情况下，可以同时保证一致性和可用性。
CAP 理论描述的是当分区发生时的权衡选择。

现代分布式系统的设计哲学：选择 AP + 最终一致性，通过其他机制（向量时钟、版本向量、Gossip 协议等）
在分区恢复后将数据最终同步一致。

📊 CAP 三特性详细对比

特性 定义 核心问题 典型场景
C 一致性 所有节点在同一时刻看到相同的数据 分布式事务、共识算法 银行转账、分布式锁、配置中心
A 可用性 每个请求都能在有限时间内得到响应 故障检测、熔断降级 电商详情页、社交Feed、内容推荐
P 分区容错 系统能容忍节点间的网络断开 网络不可靠、节点故障 所有真实分布式系统

CAP：一个被误读最多的定理

CAP 定理说的是：在一个分布式（网络分区可能发生）系统里，一致性（C）、可用性（A）、分区容错性（P）三者不可兼得，必须在 C 与 A 之间做出选择。注意：P 不是可选项——网络分区是客观存在、无法避免的物理事实，所以真正的选择只有 CP 还是 AP。

CAP 三选二：分布式下实际是 CP 与 AP 的选择

三个字母的准确含义

字母严格定义通俗理解容易混淆的点
C 一致性每次读都能读到最近一次成功写入的结果（线性一致/强一致）所有节点在同一时刻看到的数据完全一样不是「数据最终会一样」——那是最终一致，属于放弃 C
A 可用性每个非故障节点收到的请求，都能在有限时间内得到响应系统一直能应答，不会拒绝也不会无限等待不是「100% 成功」——响应可以是旧数据，但不能不响应
P 分区容错网络分区（节点间消息丢失或延迟不可控）时系统仍能继续运行网线断了、机房隔离了，系统不能整个垮掉不是可选项——分布式环境下分区一定会发生，只能选 C 或 A

关键澄清：CAP 讨论的是分区发生期间的取舍。在没有分区的正常运行状态下，系统完全可以同时提供强一致和高可用。很多争论源于把「平时」的行为也套进 CAP。

CP 与 AP 的实际例子

CP 系统：宁可拒绝，也不能错

典型是分布式协调与元数据存储：etcd、ZooKeeper、Consul（默认）、HBase。

  • 分区发生时，少数派节点拒绝读写（返回错误），多数派继续工作
  • Raft/ZAB 用多数派投票保证已提交数据不丢
  • 应用表现：选举期间（通常秒级）服务不可用，但恢复后数据绝对正确
  • 适合：配置中心、分布式锁、主节点选举、元数据

AP 系统：宁可暂时不一致，也要能应答

典型是服务发现与高可用存储：Eureka、Cassandra、Dynamo、DNS。

  • 分区发生时各分区都继续接受读写，恢复后做冲突合并
  • 应用表现：永远能写入，但可能读到旧值或需要冲突解决
  • Eureka 的「自我保护」就是典型 AP 行为：宁可保留可能失效的实例，也不清空注册表
  • 适合：服务注册发现、社交动态、会话存储

同一个系统可以在不同维度做不同取舍

这是进阶认知：CAP 不是给整个系统贴一个标签，而是逐个操作逐个数据分析。

  • 例如：账户余额走 CP（强一致），用户昵称走 AP（最终一致）
  • 同一数据库：写主库要求 CP，读从库接受 AP
  • 所以问「MySQL 是 CP 还是 AP」没有意义，要问「哪个配置下的哪个操作」

PACELC：对 CAP 的重要补充

CAP 只说了「分区发生时（P）在 C 与 A 之间怎么选」，但没说没发生分区时怎么办。PACELC 补上了这一半：

PACELC： If Partition (P) → 在 A（可用性）与 C（一致性）之间选：else Else (E) → 在 L（延迟 Latency）与 C（一致性）之间选 即： 有分区时：PA 或 PC 无分区时：EL 或 EC 例如： PA/EL → 分区时保可用，平时保低延迟（Dynamo、Cassandra 默认） PC/EC → 分区时保一致，平时也保一致（etcd、ZooKeeper、Raft 强一致读） PA/EC → 分区时保可用，平时走强一致读（部分可调一致性的系统）

为什么这个补充重要：大多数系统在 99.99% 的时间里并没有分区，此时真正的权衡是「要不要为了强一致而承受更高的延迟（如跨机房同步、读主库、多数派确认）」。PACELC 提醒你：即使选了 AP，平时也仍然要决定读写走本地副本（快但可能旧）还是走主副本（准但慢）。

常见误解澄清

  • 误解一：「CAP 三选二，我选 CA」。分布式系统中网络分区是客观存在的，不能靠设计消除。声称放弃 P 的系统要么不是分布式（单机数据库），要么在分区时会直接崩溃（既不满足 C 也不满足 A）。
  • 误解二：「最终一致就是满足 C」。CAP 里的 C 特指强一致（线性一致）。最终一致意味着存在一段时间窗口内读不到最新写入，这就是放弃了 C。
  • 误解三：「BASE 是对 CAP 的推翻」。BASE（Basically Available、Soft state、Eventually consistent）其实是 CAP 中 AP 方向的工程化表达：接受分区期间的可用性与软状态，靠最终一致收敛。
  • 误解四：「选了 AP 就不用管一致性了」。放弃强一致不等于放弃一致性，仍要设计冲突解决、幂等、对账来保证数据最终正确，只是把一致性保证从「同步」变成了「异步收敛」。
  • 误解五：「CAP 只适用于数据库」。任何有状态、多副本、需要跨节点协作的组件都适用：缓存、配置中心、服务注册、分布式锁、消息队列，无一例外。

深入自检

Redis 集群是 CP 还是 AP？

这个问题本身就问错了——要看具体配置和场景。Redis Cluster 主从之间是异步复制，主节点写入后立即返回（不等从库确认），分区时若客户端连到少数派主节点仍可写入，恢复后该期间的数据会被丢弃——从这个角度看它是 AP。但 Redis Cluster 在主节点失联时，少数派一侧会停止接受写入（cluster-require-full-coverage、节点超时判定），这又带有 CP 色彩。更准确的说法是：Redis 的设计倾向于「性能与可用性优先，接受故障时少量数据丢失」，不适合做强一致存储。要用 Redis 做分布式锁时，正是这个特性导致了主从切换下的锁失效问题，需要 Redlock 或改用 etcd/ZooKeeper 这类 CP 系统。

为什么金融系统强调 CP，而社交系统可以 AP？

因为不一致的代价不同。金融系统里「读到旧余额」可能导致超额支取、重复扣款，是直接的资损，且无法用补偿轻易挽回——所以它宁可在分区期间停止服务（不可用）也要保证数据正确。社交系统里「好友晚几秒看到我的动态」几乎无成本，而「刷不出来」是明确的用户流失——所以它选择继续服务，接受短暂不一致。判断方法：问「如果此时让用户看到旧数据，最坏后果是什么」，后果可接受用 AP，不可接受用 CP。

能同时做到强一致和高可用吗？

在没有分区的正常情况下可以——这也是绝大多数系统平时的状态：主从同步正常、网络通畅，系统既一致又可用。CAP 限制的是「分区发生时必须二选一」这一瞬间。另外，通过多数派复制（如 Raft），只要超过半数节点间通信正常，就能同时保证一致与可用，此时「分区」只影响被隔离的少数派——这就是 CP 系统在工程上仍能做到高可用的原因：它牺牲的是少数派节点的可用性，换取整体的数据正确性。

如何为一个新系统做 CAP 取舍？

不要一次性给整个系统贴标签，按数据逐个判断。步骤：① 列出系统里的所有有状态数据；② 对每种数据问「短暂不一致会导致什么后果」，后果是否可补偿；③ 后果严重且不可补偿（余额、库存、订单状态）→ CP，用强一致存储与同步复制；④ 后果轻微或可补偿（昵称、动态、计数、推荐）→ AP，用异步复制 + 最终一致；⑤ 对 AP 的数据补齐三件套：幂等、冲突解决策略、定期比对修复。这样同一个系统里可以并存 CP 与 AP 组件，是生产上最常见也最务实的形态。
