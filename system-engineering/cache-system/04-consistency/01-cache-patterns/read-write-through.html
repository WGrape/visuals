什么时候适用？

判断信号：希望应用只面对缓存接口；缓存代理有能力可靠地访问权威数据库。

  • 多服务访问同一商品数据：Read-Through 代理统一处理未命中加载。
  • 库存写入需要同步确认权威数据：Write-Through 等数据库提交后才返回成功。
  • 日志聚合写入量大、允许秒级延后：Write-Behind 先可靠入队，再批量刷库。

和相近模式怎么区分？

相近方案选择边界
Read-Through 与 Cache-Aside读未命中时，前者由缓存代理查询数据库；后者由业务应用查询并回填。
Write-Through 与 Write-Behind前者成功通常意味着同步写库已完成；后者成功只代表写入可靠待刷记录，数据库可能仍是旧值。

核心伪代码

function readThrough(key):
  return cache.getOrLoad(key, loader=db.get)

function writeThrough(key, value):
  db.update(key, value)
  cache.set(key, value)
  return ACK

function writeBehind(key, value):
  durableQueue.append(key, value)
  cache.set(key, value)
  return ACK  // 后台重试刷库，需顺序和去重

Read-Through 可与不同写策略组合；Write-Behind 必须设计队列持久化、顺序、重试、回放与故障恢复。

缓存层

统一代理

Read-Through

应用只和缓存交互；缓存未命中时由缓存层自己加载数据并回填，对应用透明。

Write-Through

写请求交给缓存代理，由代理同步写数据库并维护缓存；只有按其契约两步都成功才确认。写延迟包含数据库耗时，两步之间失败仍需要恢复策略。

Write-Behind

写请求先进入缓存层的待刷队列，后台再批量落库。响应可以更快，但数据库在一段时间内仍是旧值；若待刷记录未持久化，进程崩溃可能丢写入。

对比

模式负责的路径确认语义与风险
Read-Through读未命中回源不决定写库时机
Write-Through同步写库数据库写成功后确认；要处理部分失败
Write-Behind异步刷库先确认、后落库；要持久化待刷记录

🎯 面试问答

Q：Read-Through 与 Cache-Aside 区别？
A：未命中时由缓存层回源，应用只调用缓存层；Cache-Aside 则由应用回源并回填。
Q：Write-Behind 风险？
A：未刷库的记录若丢失会丢数据，还要处理顺序、重试和故障恢复。
Q：何时用 Write-Through？
A：需要同步确认数据库写入，且能接受相应延迟与部分失败处理成本。

一、四种缓存写策略对照

策略写数据时做什么一致性性能风险
Cache Aside（旁路）更新 DB，然后删除缓存较好最好删除失败会短期不一致
Write Through写缓存，缓存同步写 DB好写延迟高写多场景拖慢吞吐
Write Back（回写）只写缓存，异步批量落库差最好缓存宕机会丢数据
Write Around绕过缓存直接写 DB一般写快刚写的数据读会 miss
为什么 Cache Aside 是「删缓存」而不是「更新缓存」

两个原因：① 更新缓存的代价高——一次写操作就要重新计算并序列化整个缓存对象，而这个对象未必马上被读；② 并发下更新顺序可能错乱，A 写库后 B 再写库，但缓存里 B 先写 A 后写，留下旧值。删除则让下一次读自然回源重建，天然规避了顺序问题。

二、Read Through 的实现要点

func (c *Cache) Get(key string) (Value, error) { v, ok := c.local.Get(key) if ok { return v, nil } // 关键：同一个 key 只允许一个 goroutine 回源，避免缓存击穿 single := c.sf.Do(key, func() (interface{}, error) { v, err := c.db.Load(key) if err != nil { return nil, err } if v == nil { // 空值也要缓存，防止穿透（但要短 TTL） c.local.Set(key, Null, 60*time.Second) return Null, nil } c.local.Set(key, v, c.ttl()+jitter()) return v, nil }) return single }

三、Write Through 什么时候值得用

写少读多写延迟可以接受，换取强一致
数据不能丢不能接受 Write Back 的丢失窗口
缓存层已封装好如某些 ORM 缓存、本地 + 远程两级缓存库
读写比例极高一次写换来无数次命中，很划算

反过来，写密集场景（计数、点赞、实时状态）绝不要 Write Through：每次写都要同步落库，缓存反而成了放大器。这类场景应该走 Write Back + 异步批量落库，或者干脆用 Redis 自增再定期持久化。

四、延迟双删：工程上最实用的补丁

Cache Aside 在并发读写下仍有一致性窗口：读线程在写线程「更新 DB」和「删除缓存」之间读了旧值并回写。延迟双删就是为了关掉这个窗口：

// 1) 先删缓存（降低读到旧值的概率） cache.del(key) // 2) 更新数据库 db.update(row) // 3) 睡眠一小段时间后，再删一次 // 这段 sleep 要大于「一次读请求 + 回源写入缓存」的耗时 time.Sleep(500 * time.Millisecond) cache.del(key) // 更稳的做法：第 3 步用消息队列的延迟消息， // 失败可重试，不阻塞主流程

五、深入自检

Write Through 能保证强一致吗？

只能保证「缓存与 DB 在写入成功后一致」，但无法消除并发窗口：两个写请求到达顺序与落库顺序不一致时，仍可能留下旧值。真正的强一致需要锁或版本号（CAS）参与。

Write Back 丢失数据能接受吗？

只在数据可重建时接受。比如会话缓存、排行榜（可从日志重算）。账务、库存这类不能丢的场景必须用 Write Through 或直接写库。

为什么空值也要缓存？

防止缓存穿透：恶意或程序性查询不存在的 key，每次都会打到数据库。缓存一个「空」标记（TTL 设短，比如 60 秒）能把这类请求挡在缓存层。

延迟双删的 sleep 时间怎么定？

要大于「读请求从缓存 miss 到回源写入缓存」的完整耗时，通常取业务读耗时的 P99 再加点余量。不确定就先按 500ms 起步，观察回源时序再调。

多级缓存（本地 + Redis）怎么写？

写入时本地与 Redis 都要失效，且本地缓存的失效最好通过消息广播（如 Redis Pub/Sub）通知所有实例。只靠本地 TTL 过期会有一段较长的窗口。
