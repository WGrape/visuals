⚡ CDN 核心原理

📍

就近访问 (Anycast)

DNS 智能解析将用户请求路由到地理位置最近的 CDN 节点，减少网络延迟，提升访问速度

💾

内容缓存 (Cache)

CDN 节点缓存源站静态资源（图片/CSS/JS/视频），用户重复访问时直接命中缓存，减轻源站压力

⚖️

负载均衡 (GSLB)

全局负载均衡器综合考虑节点负载、用户位置、网络质量，智能分配最优访问节点

🔄

回源优化 (Origin Shield)

多级缓存架构，边缘节点 → 区域中心 → 源站，避免大量回源请求压垮源站服务器

CDN 的本质：把内容搬到离用户更近的地方

CDN（Content Delivery Network）解决的问题是物理距离带来的延迟与源站压力。光速在光纤中约 200km/ms，从北京到深圳一个来回就是几十毫秒；如果内容能放在用户所在城市的机房里，这个延迟就消失了。

CDN 就近命中：命中率越高，回源越少、延迟越低

CDN 是怎么工作的：五步走

① DNS 调度用户解析域名时，CDN 的权威 DNS 根据用户 IP 返回最近的边缘节点 IP（而不是源站 IP）
② 边缘节点接请求用户的请求直接打到最近的边缘节点，不经过源站
③ 命中则直接返回节点上已有该资源且未过期 → 直接返回，全程不回源（最快）
④ 未命中则回源节点上没有或已过期 → 节点向源站拉取，缓存后再返回给用户
⑤ 缓存到期后重新校验过期后可用条件请求（If-None-Match / If-Modified-Since）向源站确认是否变更
调度方式原理优缺点
DNS 调度（最常用）权威 DNS 根据用户 LocalDNS 的 IP 判断位置，返回就近节点 IP简单通用；缺点是依赖 LocalDNS 的准确性（用户用了异地 DNS 会调度错误）
HTTPDNS / 302 调度客户端直接用 HTTP 请求解析，或用 302 重定向到最佳节点调度精准（拿到的是真实用户 IP）；需要客户端或协议层支持
Anycast多地节点宣告同一 IP，由 BGP 路由把流量引到最近的节点调度极快、抗 DDoS 好；成本高，多用于 DNS 服务与大型厂商

缓存策略：CDN 配置的核心

按内容类型分策略

  • 静态资源（js/css/图片/字体）：长缓存（如 30 天~1 年）+ 文件名带哈希（app.a1b2c3.js），内容一变文件名就变，无需刷新
  • HTML 页面：短缓存或不缓存；若要缓存需配合合理的失效策略
  • API 响应：一般不缓存；确需缓存要严格设置 Vary 与 Cache-Control
  • 视频/大文件：开启分片缓存与 Range 请求支持

Cache-Control 常用指令

  • max-age=31536000：浏览器/CDN 缓存一年
  • s-maxage：只对共享缓存（CDN）生效，优先级高于 max-age
  • no-cache：可以缓存，但每次使用前必须向源站校验
  • no-store：完全不缓存（敏感数据用这个）
  • must-revalidate：过期后必须校验，不允许返回陈旧内容

缓存键（Cache Key）

决定「什么算同一份资源」。默认是完整 URL，可按需调整。

  • 可以忽略某些查询参数（如时间戳、埋点参数），提高命中率
  • 也可以加入 Header/Cookie（如多语言站点要按语言区分）
  • 配错会导致「用户 A 看到用户 B 的内容」——涉及个性化的内容务必把区分维度加入缓存键

缓存刷新（Purge）

  • 按 URL 刷新：精确，适合少量内容
  • 按目录刷新：批量
  • 刷新有生效延迟（几十秒~几分钟），且通常有配额限制
  • 最佳实践：用「文件名带哈希」避免依赖刷新——发布即新 URL，无需 purge

CDN 还能做什么

  • 隐藏源站 IP。用户只看到 CDN 节点，源站不暴露，大幅减少被直接攻击的可能（配合只允许 CDN 回源 IP 访问源站）。
  • 抗 DDoS 与大流量冲击。CDN 的带宽总量远大于单台源站，天然吸收流量峰值；再配合高防可抵御攻击。
  • TLS 终止与 HTTP/2、HTTP/3。在边缘完成 HTTPS，并支持 HTTP/3（QUIC）改善弱网表现。
  • 压缩与图片处理。自动 Brotli/Gzip 压缩、图片格式转换（WebP/AVIF）、裁剪、缩放、水印——减少传输量效果显著。
  • 边缘计算。在 CDN 节点上跑代码（Edge Functions / Lambda@Edge），做 A/B 分流、鉴权、重定向、个性化，无需回源。
  • 动静分离与加速。静态资源走 CDN，动态请求通过 CDN 的动态加速（优化回源链路路由）回源，也能降低延迟。

常见坑

  • 缓存了不该缓存的内容。把带用户信息的页面缓存成公共内容，导致用户信息泄露——这是 CDN 最严重的事故类型。涉及个性化的响应必须设 Cache-Control: private 或用 Vary 正确区分。
  • 刷新后没生效。原因可能是：浏览器本地缓存未过期（CDN 刷新不影响浏览器）、多层 CDN 缓存、或刷新还在生效中。排查要分清是哪一层。
  • 命中率低。常见原因：URL 带随机参数、缓存时间过短、资源分散在多个域名、或源站返回了 no-cache 头。命中率低意味着花了 CDN 的钱却没效果。
  • 回源流量超预期。命中率低或缓存时间过短会导致回源流量巨大，源站带宽成本反而上升。要先优化命中率再评估成本。
  • HTTPS 证书配置。证书过期会导致全站不可访问；回源是 HTTP 还是 HTTPS 要明确，且源站要能校验 SNI。
  • 跨域（CORS）问题。字体、脚本走 CDN 后变成跨域资源，需要正确配置 CORS 头，否则资源加载失败。

深入自检

CDN 缓存和浏览器缓存有什么区别？

位置和作用域不同。浏览器缓存（私有缓存）在用户本机，只对该用户生效，由响应头的 Cache-Control 控制；CDN 缓存（共享缓存）在 CDN 边缘节点，为该节点覆盖的所有用户共享，同样由 Cache-Control 控制，但可以用 s-maxage 单独指定。一次请求的查找顺序是：浏览器缓存 → （若未命中）CDN 边缘节点 → （若未命中）源站。关键区别：CDN 刷新（purge）只能清掉 CDN 上的内容，清不掉用户浏览器里已缓存的资源——这就是为什么「我刷新了 CDN 但用户还是看到旧的」很常见。解决办法是资源文件名带内容哈希（app.a1b2c3.js），内容变了 URL 就变，浏览器自然会去取新的，无需任何刷新操作。

CDN 命中率低怎么优化？

按影响面从大到小排查：① 去掉 URL 中的随机参数——很多前端会加 ?t=timestamp 或统计参数，导致每次都是新 key，在 CDN 上配置「忽略指定查询参数」或干脆去掉；② 延长缓存时间——静态资源应设为月级甚至年级；③ 检查源站响应头——源站若返回 no-cache/no-store 或很短的 max-age，CDN 会遵循（除非配置了强制覆盖）；④ 收敛域名——资源分散在多个域名会分散热度，降低命中率；⑤ 预热——大促或新版本发布前，主动把热点资源推送到边缘节点，避免冷启动时的回源高峰；⑥ 合理设置缓存键——不要无谓地把 User-Agent、Cookie 加入缓存键。目标命中率：静态资源应在 95% 以上。

动态内容能用 CDN 加速吗？

不能直接缓存，但可以「动态加速」。原理是：CDN 厂商在骨干网上有优化的链路，用户请求先到最近的边缘节点，然后通过优化过的内部路由回源（而不是走公网），避开公网拥塞与绕路，从而降低延迟、提高稳定性。此外还可以做：① 边缘计算——把部分逻辑（鉴权、重定向、A/B 分流）放到边缘执行，减少回源；② 局部缓存——动态页面中变化不频繁的部分（如商品详情的静态描述）用 ESI 或边缘包含技术分段缓存；③ TCP/TLS 优化——边缘与用户之间是近距离连接（握手快），边缘到源站保持长连接复用，整体延迟低于用户直连源站。综合下来动态加速通常能降低 20%~40% 的延迟。

CDN 出故障时怎么应急？

预案要在平时就准备好：① 保留绕过 CDN 的直连入口——一个不经过 CDN 的备用域名或 IP，CDN 故障时切换 DNS 到源站（前提是源站带宽与防护能扛住，否则等于被压垮）；② 降低依赖——确保核心 API 不依赖 CDN，静态资源 CDN 挂了时页面至少能加载（可用多 CDN 或本地兜底）；③ 多 CDN 容灾——配置多家厂商，用 DNS 或 HTTPDNS 做故障切换，代价是成本与管理复杂度；④ 监控——监控 CDN 的可用性、命中率、回源量、错误率，并区分「CDN 的问题」与「源站的问题」（看回源错误率）；⑤ 了解厂商的 SLA 与故障通知渠道。最重要的一点：提前演练切换流程，否则真正出故障时 DNS 切换可能因 TTL 太长而迟迟不生效。
