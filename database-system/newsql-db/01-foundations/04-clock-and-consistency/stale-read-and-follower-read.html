陈旧读与副本读：用「旧一点」换「快很多」

判定哪些查询能接受旧数据，以及开之前的四个风险和三种用法

一句话总结：强一致读最安全但最慢——它可能要跨地域取时间戳、可能撞上锁、还可能被长事务挡住。陈旧读和副本读是用「读到几秒前的数据」换「更低的延迟、更高的吞吐、更少的跨地域流量」。关键不是能不能开，而是哪一类查询配得上这个折中。

01什么时候该用陈旧读：五个判定信号

信号说明结论
查询是只读且不影响业务决策列表、详情展示、看板图表可以开
查询量很大、读延迟是主要瓶颈读 QPS 高、每次都要走 leader适合开
能接受数据延迟数秒业务方明确说「晚几秒没关系」可以开
涉及余额/库存/幂等判断读到旧数据会直接算错禁止开
「写后立即读」的一致性要求刚提交就要能查到（如提交后跳转详情页）禁止开
要点：一个非常好用的判断句式：「这条 SQL 读到的值会被用来做写决策吗？」 会 → 强一致读；不会 → 可以考虑陈旧读。

02强一致读到底慢在哪

  1. 取时间戳：向授时服务要一个 ts，跨地域时这是一次实打实的 RTT。
  2. 等未决事务：如果目标数据上有「正在提交但还没确定」的事务，读必须等它落地，不能猜。
  3. 遇锁清理：读到别的事务留下的锁时，需要判断锁的持有者是否还活着（可能触发事务状态查询，甚至回滚残留事务）。
  4. 只能走 leader：Raft 组的 leader 承载强一致读，follower 不能直接提供（除非产品做了专门的副本读一致性协议）。
读方式是否要取最新 ts是否可能遇锁等待能否走副本典型延迟量级
强一致读是是否（一般）跨地域可达数十毫秒
陈旧读否（用旧 ts）基本不（旧快照上的锁早解了）可以本地/近端，可降到毫秒级
副本读取决于实现取决于实现是取决于副本所在位置

03陈旧读的四个风险

  • 副本落后不可控：允许读多旧，取决于副本当前的复制延迟。若副本落后超过你设的陈旧窗口，读可能直接报错或回退到强一致读。
  • 写后读不一致（read-your-writes）：用户提交表单后立刻刷新列表看不到自己的数据——这是最容易被投诉的一类 bug。
  • 单调读被破坏：两次连续查询可能落到不同副本，出现「第二次读到的比第一次更旧」。需要在同一会话内固定时间戳来避免。
  • 跨行不一致：虽然是快照读（单事务内一致），但如果业务用多条独立 SQL 拼一个视图，不同 SQL 用了不同 ts，拼出来的结果就不一致。
要点：前两条靠「业务分级」解决，后两条靠「会话内固定时间戳/用事务包裹」解决。

04怎么用：把陈旧读限制在安全范围

-- 反例：整个会话都开陈旧读，写后读必然出问题
-- 正例：只对「明确的只读查询」单独指定历史时间戳

-- ① 单条语句级（推荐）：只在看板/报表这类查询上用
SELECT status, COUNT(*) FROM orders
  AS OF TIMESTAMP NOW(6) - INTERVAL 5 SECOND
  GROUP BY status;

-- ② 会话级（谨慎）：确认该连接后续全是只读查询
SET SESSION tidb_read_staleness = -5;    -- 变量名以产品文档为准
SELECT ...;                              -- 这批查询都读 5 秒前
SET SESSION tidb_read_staleness = 0;     -- 用完必须关掉

-- ③ 事务内保持一致视图：多条 SQL 用同一个 ts
BEGIN;
SET TRANSACTION READ ONLY AS OF TIMESTAMP NOW(6) - INTERVAL 5 SECOND;
SELECT ...;   -- 这组查询看到的是同一个快照
SELECT ...;
COMMIT;
做法适用场景注意
语句级 AS OF推荐，单条只读查询不影响其他 SQL，范围最好控制
会话级变量一批连续的只读查询用完必须关，否则后续写入逻辑读到旧数据
只读事务 + 固定 ts多条 SQL 要组成一致视图能同时解决单调读与跨行不一致

05副本读（Follower Read）

副本读是让读流量落到非 leader 副本，用来分摊 leader 压力、并把读拉近到用户所在地域。它和陈旧读经常一起用，但两者正交：陈旧读讲的是读到多旧，副本读讲的是从哪台机器读。

  • 副本读不等于可以读任意旧数据——是否做一致性校验（如 Raft 的 read index）由产品决定，必须查文档。
  • 副本落后太多时，读通常会被拒绝或超时，不是无限等下去。
  • 跨地域部署下，把读放到本地副本是降低延迟最有效的手段之一，效果远好过在应用侧做缓存。
  • 注意副本被大量读打满后，可能影响它作为高可用副本的本职工作（参与选举、追日志）。
要点：把「读流量可以走副本」当成架构能力，把「陈旧读」当成业务许可——两个都要确认过再上线。

06常见疑问

问：陈旧读会不会读到「写了一半」的数据？

不会。陈旧读读的是某个完整时间点的一致性快照，事务原子性仍然成立——要么整个事务可见，要么不可见。它牺牲的是「新鲜度」，不是「一致性」。

问：我设了 5 秒陈旧，副本落后 10 秒会怎样？

取决于产品实现：可能报错让应用重试、可能自动回退到强一致读、也可能等副本追上。生产前必须做一次「停掉一个副本再查」的演练，看实际的失败形态。

问：能不能对整库默认开陈旧读省事？

不建议。默认强一致 + 按需例外，才是安全的方向。默认陈旧读会把「读旧数据」变成系统默认行为，迟早有一个新同学在某条资金 SQL 上踩到。

问：缓存和陈旧读该选哪个？

目标是降低数据库压力 → 缓存更彻底；目标是降低跨地域读延迟、且要保住 SQL 能力 → 陈旧读/副本读更合适。两者可以叠加，但叠加后「数据有多旧」会变成多级延迟的累加，一定要能解释清楚。

各数据库怎么开：命令对照

陈旧读 / 副本读不是「关掉一致性」的开关，而是显式声明能容忍多少延迟。下面按产品列出真实可用的语句，注意默认值各不相同。

产品开启方式默认可容忍陈旧度典型收益
TiDBSET SESSION tidb_replica_read = 'leader-and-follower'leader（读主）由副本回放延迟决定，可用 tidb_read_staleness=-5 明确 5 秒跨地域读延迟可从数十毫秒降到个位数
TiDB（历史读）SET SESSION tidb_snapshot = '2026-10-25 15:00:00'关闭秒级到小时级对账、回溯、一致性快照导出
CockroachDBSELECT ... AS OF SYSTEM TIME follower_read_timestamp()强一致（读 leaseholder）该函数返回约 4.8 秒前的时间戳跨区域读延迟大幅下降
YugabyteDBSET yb_read_from_followers = on + yb_follower_read_staleness_ms关闭默认约 30000 ms（可调整）读吞吐随副本数线性扩展

TiDB 的三种陈旧读

-- TiDB：三种读法
SET SESSION tidb_replica_read = 'leader';              -- 默认：只读主副本
SET SESSION tidb_replica_read = 'leader-and-follower';  -- 允许读从副本（随机选）
SET SESSION tidb_replica_read = 'follower';             -- 只读从副本

-- 明确「最多容忍 5 秒陈旧」（TiDB 5.4+）
SET SESSION tidb_read_staleness = -5;
SELECT * FROM orders WHERE id = 1;      -- 若副本落后超过 5s，会自动回退到读主

-- 历史读：读到指定时刻的一致快照
SET SESSION tidb_snapshot = '2026-10-25 15:00:00';
SELECT count(*) FROM orders;            -- 该时刻的完整快照
SET SESSION tidb_snapshot = '';         -- 用完必须清掉，否则后续查询全在历史快照上

CockroachDB

-- CockroachDB：follower reads 与历史读
SELECT * FROM orders AS OF SYSTEM TIME follower_read_timestamp();
SELECT * FROM orders AS OF SYSTEM TIME '-10s';            -- 明确 10 秒前
SELECT * FROM orders AS OF SYSTEM TIME '-1h';             -- 受 GC TTL 限制，默认 25 小时内的历史可读

-- 会话级开启（较新版本）
SET default_transaction_use_follower_reads = on;

-- 查看 GC 设置：历史读能回溯多久由它决定
SHOW ZONE CONFIGURATION FOR TABLE orders;   -- 看 gc.ttlseconds，默认 90000（25 小时）

MySQL / PostgreSQL 的落后观测

-- MySQL / PostgreSQL：先看副本落后多少，再决定能不能读副本
SHOW REPLICA STATUS\G          -- MySQL 8.0+（8.0 之前为 SHOW SLAVE STATUS）
--   关注 Seconds_Behind_Master、SQL_Delay、Retrieved_Gtid_Set vs Executed_Gtid_Set

SELECT client_addr, state, sent_lsn, replay_lsn,
       pg_wal_lsn_diff(sent_lsn, replay_lsn) AS bytes_behind,
       replay_lag
FROM pg_stat_replication;       -- PostgreSQL：replay_lag 是时间落后量

一个容易忽略的点：副本读也可能阻塞。如果副本正在回放一个大事务，读请求可能撞上锁等待或必须等待回放推进；所以「副本读一定快」不成立，必须配超时和回退策略。

落地清单：把陈旧读限制在安全范围

陈旧读的正确用法不是全局打开，而是按查询分级：能容忍的走副本，不能容忍的走主，并且在代码里显式标注，避免后来者误用。

场景能不能用陈旧读理由建议配置
看自己的订单详情不能刚写入就要能读到（读己之所写）读主，或写入后 1 秒内强制读主
首页推荐 / 热门榜可以容忍分钟级陈旧副本读 + 缓存
报表 / 对账视情况需要一致快照而非实时用历史读（AS OF / tidb_snapshot）而不是副本读
库存扣减不能需要先读后写，陈旧会超卖读主 + 事务内的原子扣减
搜索/筛选列表可以容忍秒级副本读，容忍 5s
跨地域就近读可以网络延迟远大于陈旧窗口副本读 + 明确的 staleness 上限
  • 先保证「读己之所写」：用户写完立刻读的场景必须走主，这是最容易出客诉的一条。
  • 陈旧读要带上明确上限（如 5 秒），超过自动回退读主，不要无限容忍。
  • 报表类用历史读而不是副本读：副本读在不同副本间可能不一致，导致同一查询两次结果不同。
  • 监控副本延迟：Seconds_Behind_Master / replay_lag 要设告警，延迟高时自动关掉副本读。
  • 事务内不要混用：开启陈旧读后事务里既有历史快照又有当前写，语义会非常难推理。
  • 用完要清掉会话变量：tidb_snapshot 忘了清空会让后续所有查询都读历史。
  • 扣减类业务不要靠陈旧读提速，改成原子操作（UPDATE ... SET n = n - 1 WHERE n > 0）。
  • 跨地域部署优先用 follower read，它比「异步复制到远方再读」的延迟低一个数量级。
  • 压测要包含副本延迟场景：只在健康副本上测出来的性能不代表真实故障时的表现。
