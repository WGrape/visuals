CLAUDE.md 的三级层级与加载规则

层级路径作用范围优先级
企业管理级/etc/claude-code/CLAUDE.md全组织强制最先加载
用户级~/.claude/CLAUDE.md你所有项目次之
项目级<repo>/CLAUDE.md本项目（最常用）次之
目录级<repo>/sub/CLAUDE.md该子目录最具体，最后加载

加载规则：Claude Code 启动时，会把用户级 + 项目级 + 当前工作目录链上的所有 CLAUDE.md 全部读进系统提示。子目录的 CLAUDE.md 在接触到该目录下的文件时才被惰性加载——这是控制上下文占用的关键机制。

CLAUDE.md 该写什么、不该写什么（附预算）

内容类型建议理由
构建/测试命令✅ 必写模型猜不到的项目特定命令
代码风格约定✅ 必写（但要简短）命名、错误处理、注释语言
架构边界✅ 必写哪些目录是禁区、分层依赖方向
常见坑✅ 高价值“别改这个文件，会导致 XX”
完整 API 文档❌ 不要需要时再读，占了窗口就是浪费
整份代码规范❌ 不要用 linter 自动检查，比提示词可靠
大段示例❌ 不要放进 docs/ 让它按需读取

预算原则：CLAUDE.md 是每次对话都必然消耗的固定成本。经验值是控制在 200 行 / 2k token 以内。写得越啰嗦，每轮对话的可用窗口越小，而且关键指令会被淹没在噪声里。宁可短而准，不可长而全。

上下文窗口管理：什么时候该 /compact

信号含义动作
上下文占用 < 50%健康继续
50% – 70%开始变慢、成本上升考虑 /compact
> 70%可能截断早期内容立即 /compact
出现“对话过长”提示已到上限/clear 或新开会话
  • /compact 保留摘要：把历史对话压缩成要点，保留关键决策，释放大部分 token
  • /clear 全清：彻底重来，适合切换到完全无关的任务
  • 任务边界处主动清：完成一个独立任务后 /clear，比一直堆积更高效
  • 大文件别直接读：用 rg -n 定位行号后读区间（Read(file, offset, limit)）
  • 长输出要落盘：让模型把长结果写进文件，而不是全量回显到对话里

让记忆真正起作用的 5 个实践

  • ① 把 CLAUDE.md 提交进 git：团队共享同一份约定，新人和 AI 看到的是同一套规则
  • ② 用“禁忌”而非“建议”：不要用 X 比 建议用 Y 更有效，因为前者是可判定的
  • ③ 给出具体命令：go test ./... -race 远好于“运行测试”
  • ④ 用目录级 CLAUDE.md 做局部约束：只在需要时加载，不占全局预算
  • ⑤ 定期修剪：项目演进后删掉过时条目，过期的记忆比没有记忆更有害

深入自检

CLAUDE.md 和 .cursorrules / AGENTS.md 有什么区别？

本质都是项目级提示词文件，只是不同工具的约定文件名：Cursor 用 .cursorrules、Codex 和一些 Agent 框架用 AGENTS.md、Claude Code 用 CLAUDE.md。可以同时维护并用软链接同步，内容侧重相同——都是“AI 必须遵守的项目约定”。

记忆会不会随着对话丢失？

分两类：写入 CLAUDE.md 的是持久化的（文件在磁盘上，下次会话自动加载）；只在对话里说的是会话级的，/clear 或关掉会话就没了。所以重要约定一定要让模型写进 CLAUDE.md（用 /memory），而不是口头交代。

子目录 CLAUDE.md 为什么不生效？

因为它是惰性加载的——只有当 Claude Code 读取了该目录下的文件时才会加载。如果你从没碰过那个目录，里面的 CLAUDE.md 就不会进上下文。这不是 bug 而是刻意设计（控制上下文长度）。想让它必然生效，就写到项目根的 CLAUDE.md 里。

CLAUDE.md 写太长会有什么具体后果？

三个后果：① 每轮对话都扣掉这部分 token，长任务更早触顶；② 指令遵循度下降——关键规则淹没在大段文字里，模型更容易漏掉（这是“大海捞针”效应）；③ 成本线性上升。建议定期用 /memory 复查，把能改成 linter 规则的删掉，把示例代码挪到 docs 让它按需读取。
