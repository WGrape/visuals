常用设计模式（Go 视角）

Go 不强调经典 23 种模式，而是用接口、组合与并发原语自然表达。一篇讲清 Go 里真正常用的几种。

概述

用组合代替继承

Go 没有继承，模式靠接口 + 结构体嵌入 + 函数实现。很多经典模式在 Go 里被语言特性直接消解。

例如策略/模板方法，用函数字段或接口字段即可，无需一层层抽象类。
创建型

选项模式最常见

构造函数用「选项模式」（可变参数函数）逐步配置；单例多用 sync.Once 或包级变量懒初始化。

func NewServer(opts ...Option) *Server {
    s := defaultServer()
    for _, o := range opts { o(&s) }
    return s
}
s := NewServer(WithPort(8080), WithTLS(true))
结构型

装饰即包装

中间件/装饰器用函数包装 Handler/接口；适配器用单方法接口对接异构实现；组合（embedding）实现「has-a」。

type Logger struct{ next Handler }
func (l Logger) Handle(r Req) { log(r); l.next.Handle(r) }
行为型

接口解耦

策略=接口字段；观察者=注册回调切片；状态机=状态接口切换。Go 的接口隐式实现让这些格外轻量。

隐式接口

实现方无需声明「我实现了 X」，只要方法集匹配，天然解耦调用方与实现方。

并发型

Go 的拿手好戏

fan-in/fan-out、worker pool、pipeline、or-channel 取消，都是用 channel + goroutine 组合而成，远超传统模式的表达力。

这些并发模式在标准库与社区库中反复出现，是 Go 工程师的必备套路。

Go 里的设计模式：先忘掉 UML

经典设计模式是为类与继承设计的。Go 没有继承、有组合、函数是一等公民，因此不少模式在 Go 里要么简化成几行，要么根本不需要。

经典模式在 Go 里的形态说明
策略函数类型或接口 + map 查表多数情况直接传函数就够
装饰器http.Handler 包装、中间件链函数签名相同即可层层包装
工厂简单构造函数 NewXxx很少需要抽象工厂
单例包级变量 + sync.Once用到时才初始化
模板方法传入函数参数代替继承把变化的部分作为参数
观察者channel 或回调切片channel 天然适合事件分发
适配器包一层实现目标接口常见于对接第三方库
建造者函数式选项模式解决多可选参数最自然
组合优于继承嵌入结构体与方法提升。
小接口接口在使用方定义，按需最小。
函数是值行为可以直接当参数传递。
先写具体再抽象出现第二个实现时再提取接口。

函数式选项：Go 里最实用的模式

type Server struct { addr string timeout time.Duration maxConn int tls bool } type Option func(*Server) func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } } func WithMaxConn(n int) Option { return func(s *Server) { s.maxConn = n } } func WithTLS() Option { return func(s *Server) { s.tls = true } } func NewServer(addr string, opts ...Option) *Server { s := &Server{ addr: addr, timeout: 30 * time.Second, // 默认值 maxConn: 100, } for _, o := range opts { o(s) } return s } // 使用：可读性高，新增选项不破坏调用方 s := NewServer(":8080", WithTimeout(5*time.Second), WithTLS())

为什么不用一堆构造函数？可选参数一多，NewServer(a, t, n, tls) 这样的签名既难读又不兼容演进。选项模式让调用点自解释，且新增选项不影响老代码。

中间件与依赖注入

中间件链

相同签名的函数可以无限包装，这就是 Go 的装饰器。

type Middleware func(http.Handler) http.Handler func Logging(next http.Handler) http.Handler { return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) { start := time.Now() next.ServeHTTP(w, r) log.Printf("%s %s %v", r.Method, r.URL.Path, time.Since(start)) }) } // 使用：mux 被层层包裹 h := Logging(Auth(Recover(mux)))

顺序即执行顺序：最外层最先执行，也最后返回。

依赖注入

Go 的依赖注入通常就是构造函数传接口，不需要框架。

type UserRepo interface { Get(ctx context.Context, id int64) (*User, error) } type UserService struct { repo UserRepo // 依赖抽象，测试时换 mock log *slog.Logger } func NewUserService(r UserRepo, l *slog.Logger) *UserService { return &UserService{repo: r, log: l} } // 在 main 里装配真实依赖 svc := NewUserService(mysqlRepo, logger)

好处：业务层不依赖具体存储，单测时传入 mock 即可。

单例与池

  • 单例用包级变量 + sync.Once，天然并发安全
  • 对象复用用 sync.Pool，注意会被 GC 清空
  • 连接池由 database/sql 等库内部管理
  • 不要在 init 里做重活（拖慢启动且难测试）

反模式：为了模式而模式

过度抽象接口只有一个实现就先不抽接口
万能 Manager职责不清的类最终什么都能干
深层包装三层以上的中间件链难以理解
全局状态隐藏的依赖让测试无法隔离
照搬 Java 结构继承体系在 Go 里会变得拧巴
忽略错误处理任何模式都不能掩盖 err 处理
// ❌ 反模式：为单个实现硬造接口与工厂 type UserService interface { Create(*User) error } type UserServiceImpl struct{} type UserServiceFactory interface { Create() UserService } // 三层抽象，实际只有一个实现 // ✅ 直接写具体类型，需要时再抽 type UserService struct{ repo *UserRepo } func (s *UserService) Create(u *User) error { ... }

判断标准：抽象如果没带来「可替换」或「可测试」的实际收益，就是纯粹的噪音。Go 的惯例是先具体、后抽象——当第二个实现出现时再提取接口，此时接口形状自然是对的。

深入自检

Go 还需要学经典设计模式吗？

需要理解其解决的问题，但不必照搬结构。很多模式在 Go 里被语言特性简化了：策略变成传函数、装饰器变成函数包装、观察者变成 channel。真正要掌握的是「依赖倒置」与「组合优先」这两个底层原则。

什么时候该提取接口？

出现第二个实现时、需要在测试中替换依赖时、或者接口应在调用方定义以表达它真正需要的能力时。提前为一个实现造接口，往往造出的是错误的抽象。

函数式选项和直接传配置结构体哪个好？

参数少且必填为主时用配置结构体更直接；可选参数多、需要演进、希望调用点自解释时用选项模式。Go 标准库与主流库在复杂构造上更倾向选项模式。

组合（嵌入）能替代继承吗？

在「复用实现」上可以，嵌入会提升方法集；但它没有多态的「is-a」语义——接口才是 Go 表达多态的方式。把嵌入当成多重继承来设计层次结构，很快就会遇到方法冲突与语义混乱。

依赖注入需要框架吗？

大多数项目不需要。构造函数传依赖已经足够清晰，且在编译期可见。只有在依赖关系极其庞大、装配逻辑复杂时，才考虑 wire 这类编译期注入工具——它生成装配代码，不做运行时反射。

Go 与 Java 模式的根本差异：Go 没有类继承，靠接口 + 组合。所以 GoF 里基于继承的模式（模板方法、工厂方法）在 Go 里都会退化成「接口 + 函数」，代码量通常少 50% 以上。不要照搬 Java 的模式写法，那会得到很啰嗦的代码。

代码模板

// 1) 选项模式（Go 最重要的一pattern，替代构造器重载）
type Server struct {
    addr     string
    timeout  time.Duration
    maxConns int
    tls      bool
}

type Option func(*Server)

func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } }
func WithMaxConns(n int) Option          { return func(s *Server) { s.maxConns = n } }
func WithTLS() Option                    { return func(s *Server) { s.tls = true } }

func NewServer(addr string, opts ...Option) *Server {
    s := &Server{addr: addr, timeout: 30 * time.Second, maxConns: 100}  // 默认值
    for _, o := range opts { o(s) }
    return s
}
// 用法：NewServer(":8080", WithTimeout(5*time.Second), WithTLS())
// 优点：加参数不破坏兼容；默认值集中；可读性好
// 2) 中间件模式（装饰器，最常用）
type Middleware func(http.Handler) http.Handler

func Chain(h http.Handler, mws ...Middleware) http.Handler {
    for i := len(mws) - 1; i >= 0; i-- {     // 逆序包装，保证执行顺序符合直觉
        h = mws[i](h)
    }
    return h
}

func Logging(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        next.ServeHTTP(w, r)
        log.Printf("%s %s %v", r.Method, r.URL.Path, time.Since(start))
    })
}

// 用法：http.ListenAndServe(":8080", Chain(mux, Logging, Auth, Recover))

// 3) 单例（sync.Once）
var (
    instance *DB
    once     sync.Once
)
func GetDB() *DB {
    once.Do(func() { instance = newDB() })   // 只执行一次，并发安全
    return instance
}
// 注意：Once 内的 panic 也算「执行过」，之后不会重试

// 4) 策略模式（用函数类型，比接口更轻）
type CachePolicy func(key string) bool
var Policies = map[string]CachePolicy{
    "lru": lruPolicy,
    "lfu": lfuPolicy,
}

排障清单

症状原因处理
照搬 Java 模式导致代码很绕Go 无继承，硬套会多余用接口+组合+函数；能用函数就别用接口
sync.Once 后实例是 nilOnce 里 panic 了Once 内不要 panic；或捕获后重试自己实现
选项模式参数不生效Option 覆盖顺序错了后应用的 Option 会覆盖前面的；注意顺序
中间件执行顺序不对Chain 的包装方向反了逆序包装，第一个中间件最先执行
接口定义过大接口方法太多难实现接口要小（Go 惯例 1~3 个方法）；在使用方定义
过度抽象为不存在的变化点做设计Go 社区倾向先写具体代码，需要时再抽象
单例难测试全局状态用依赖注入；测试时传 mock

Go 的模式哲学：① 接口由使用方定义（不是实现方）；② 接口要小（io.Reader 只有一个方法）；③ 优先用函数而不是接口；④ 不要为假想的需求做抽象。Go 标准库是最好的模式教材。
