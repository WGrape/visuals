GROUPING SETS：一次查询生成多个汇总层级

报表总计、小计和明细可以用明确的分组集合描述。

核心机制

GROUPING SETS 列出要计算的分组键组合。每个组合相当于一个分组聚合结果；空集合 () 表示全表总计。ROLLUP 适合有层级顺序的小计，CUBE 适合所有维度组合。

汇总层级缺失的列常显示 NULL，但源数据本身也可能为 NULL。支持 GROUPING 函数的数据库可用其标志区分“这一层没有按该列分组”和“真实值为空”。

用一个例子看过程

SELECT region, product, SUM(amount)
FROM sales
GROUP BY GROUPING SETS ((region, product), (region), ());

明细层

(region, product) 给出每个地区与产品组合的销售额。

地区小计

(region) 汇总该地区所有产品，product 显示汇总占位。

全表总计

() 汇总全部行；需要识别层级时增加 GROUPING 标志。

观察、原因与处理

观察原因或含义处理与验证
地区产品明细(region, product)用于下钻分析
地区合计(region)用于地区报表页脚
全局合计()用于整张报表总计

从三条销售记录推到六行结果

设原始记录为华东/书籍/100、华东/文具/50、华南/书籍/70。(region, product) 产生三个明细组；(region) 产生华东 150 与华南 70 两个地区小计；空分组 () 产生全局总计 220。一次 GROUPING SETS 查询输出六行，语义上近似对三个 GROUP BY 查询做 UNION ALL，但引擎可能共享扫描或聚合阶段。

区分汇总占位与真实缺失

汇总行的 product 显示 NULL，意思可能是“本层没有按 product 分组”，也可能是源数据中的 product 真为 NULL。支持 GROUPING(product) 的数据库可用标志区分两者。若直接把所有 NULL 显示成“全部商品”，真实缺失值也会被误标。报表应先识别层级，再决定展示标签。

ROLLUP(region, product) 通常产生明细、地区小计与全局总计；CUBE(region, product) 还会产生跨地区的商品小计。维度越多，CUBE 组合增长越快；只要指定层级的报表更适合显式 GROUPING SETS。结果行展示顺序仍应使用 ORDER BY 指定。

练习：报表口径与指标类型

需求只要“各地区各商品”“各地区小计”“全部总计”，不需要“跨地区按商品小计”。请写出三个 grouping set，并解释为什么无需 CUBE。如果统计客单价，不能对各组平均客单价再求平均；应先汇总销售额与订单数，再计算比率。改变聚合层级前先检查度量是否可加总。

边界与误区

SQL 方言对 GROUPING、ROLLUP 和结果排序有差异。多个分组层级可能增加计算与输出行数，报表展示仍需显式 ORDER BY。

性能与正确性的核对顺序

先用少量输入行手算每个层级的总和和输出行数，再执行 SQL 比较；若业务允许 source product 为 NULL，要加一条真实 NULL 样本检查展示标签。GROUPING SETS 的结果可能在同一个地区出现明细、小计与全局汇总，图表层如果简单再次 SUM，容易重复计数。因此应把层级标志作为数据的一部分传给展示层，禁止把不同层级混在一组中二次汇总。

生产数据上还要看分组基数与内存需求。多个维度组合可能生成大量聚合桶；先估计各组合的唯一键数，再看执行计划是否溢写磁盘。若报表频繁查询同一层级，可评估物化汇总，但要定义刷新延迟与源数据更正策略，避免用户看到不同层级的数字彼此对不上。

把层级作为明确字段传给前端

汇总结果最好增加一个可解释的层级标志，例如“明细”“地区小计”“全局总计”，而不是仅靠哪些列为 NULL 猜测。这样源数据真的含 NULL 时仍可正确展示，也能防止前端把三个层级再次混合求和。报表导出时要决定小计是否计入筛选后的分页；如果只在当前页重新合计，数字可能与全量总计不符。对物化汇总还要记录刷新时间：明细实时更新、小计延迟十分钟，用户看到的层级数字可能暂时不一致，需要在页面或 API 中标明。

第一层 · 概念与判定：什么时候该用 GROUPING SETS

一句话判据：一次扫描，出多个不同粒度的汇总行。当你需要的小计维度彼此不是包含关系（既不是 ROLLUP 那种逐级上卷，也不是 CUBE 那种全组合）时，就该用它。

写法产生的分组适用场景扫描次数
GROUP BY GROUPING SETS ((a),(b),())a 小计 / b 小计 / 全表总计维度平级、只要指定几种1 次
GROUP BY ROLLUP (a,b)(a,b) / (a) / ()维度有层级，逐级上卷1 次
GROUP BY CUBE (a,b)(a,b) / (a) / (b) / ()所有维度组合都要1 次
UNION ALL 多个 GROUP BY手工指定老版本数据库兼容写法N 次（每个分支一次）
  • 识别信号一：报表要「分地区小计 + 分品类小计 + 一个总计」，但地区与品类没有层级关系 → GROUPING SETS。
  • 识别信号二：你现在写了 3 个 UNION ALL，每个只是 GROUP BY 不同 → 改成 GROUPING SETS，扫描次数从 3 降到 1。
  • 识别信号三：只用 ROLLUP 却要删掉中间层级 → 不要硬凑，直接用 GROUPING SETS 枚举。

第二层 · 参数·命令·量化：语法、支持度与区分 NULL 的关键函数

核心难点只有一个：小计行的汇总列是 NULL，但原始数据的 NULL 也是 NULL——必须用 GROUPING() 区分。

GROUPING SETS 标准写法与 GROUPING() 用法

-- 标准写法：一次扫描出三种粒度
SELECT
  region,
  category,
  SUM(amount)          AS total,
  GROUPING(region)     AS g_region,   -- 该列被小计聚合掉 = 1，否则 0
  GROUPING(category)   AS g_category
FROM sales
GROUP BY GROUPING SETS ((region), (category), ())
ORDER BY g_region, g_category, region, category;

-- 把「小计产生的 NULL」替换成可读标签
SELECT
  CASE WHEN GROUPING(region)   = 1 THEN 'ALL' ELSE region   END AS region,
  CASE WHEN GROUPING(category) = 1 THEN 'ALL' ELSE category END AS category,
  SUM(amount) AS total
FROM sales
GROUP BY GROUPING SETS ((region), (category), ())
ORDER BY region, category;
数据库是否支持 GROUPING SETS备注
PostgreSQL 9.5+✅ 完整支持支持 GROUPING SETS / ROLLUP / CUBE / GROUPING()
Oracle 9i+✅ 完整支持GROUPING_ID() 可用，可一次算出分组编号
SQL Server 2008+✅ 完整支持写法相同
MySQL 5.7 / 8.0❌ 不支持只有 WITH ROLLUP；多维度小计要写 UNION ALL
Hive 0.10+ / Spark SQL✅ 支持配合 GROUPING__ID（注意是双下划线）
ClickHouse⚠️ 部分用 WITH ROLLUP / WITH CUBE / WITH TOTALS 代替

量化口径：GROUPING SETS 相对 N 个 UNION ALL，逻辑读次数约为 1/N（同一份基表只扫一次）；但当分组数很多时，单次扫描的内存占用会上升，需留意 work_mem。

第三层 · 排障与边界：最容易出错的四个地方

现象原因怎么查 / 怎么办
小计行和真 NULL 行混在一起分不清直接用 IS NULL 判断分组列改用 GROUPING(col) = 1 判断；MySQL 无此函数，需自己加标记列
结果行数比预期多GROUPING SETS 会为每个分组各出一批行先单独跑 SELECT COUNT(*) FROM (各分组行数) 加总核对
ORDER BY 后小计行位置乱跑NULL 的排序位置各库不同（PG 默认 NULL 最大，MySQL 最小）显式写 ORDER BY GROUPING(region), region，或 NULLS LAST
加了 WHERE 后小计消失WHERE 在聚合前过滤，HAVING 在聚合后过滤过滤明细用 WHERE；过滤小计行用 HAVING 或外层再包一层
  • 排查顺序：先看行数对不对 → 再看 NULL 是真 NULL 还是小计 → 再核对 ORDER BY → 最后看过滤条件放错层。
  • 边界一：GROUPING SETS 里写 () 表示「全表总计」，别漏。
  • 边界二：一个 GROUPING SETS 里最多分组数受数据库限制（Oracle 上限 4096 列组合），超过要拆查询。
  • 边界三：与 DISTINCT、窗口函数混用时先跑小样本验证语义。

行数核对

-- 快速核对：各分组分别有多少行，加总应等于 GROUPING SETS 的总行数
SELECT 'region' AS g, COUNT(*) FROM (SELECT region FROM sales GROUP BY region) t
UNION ALL
SELECT 'category', COUNT(*) FROM (SELECT category FROM sales GROUP BY category) t
UNION ALL
SELECT 'total', 1;

第四层 · 原理与取舍：为什么它比 UNION ALL 好，代价是什么

本质：UNION ALL 是每个分支各扫一次基表；GROUPING SETS 只扫一次，在聚合阶段把同一行投放到多个分组。优化器实现上通常有两种做法——

实现方式做法优点代价
多次扫描 + 合并内部展开成多个聚合再 UNION实现简单，老优化器就能做收益有限，主要省 SQL 书写
单次扫描 + 多分组投放一行数据同时写入多个分组的聚合状态I/O 与 CPU 显著下降需要同时维护 N 组聚合状态，内存上升
为什么有了 ROLLUP 还要 GROUPING SETS？

ROLLUP 只能表达「有层级的上卷」(a,b) → (a) → ()。当维度是平级的、或者你只要其中几种组合时，ROLLUP 会多出不需要的中间层级，只能靠外层过滤——那不如直接枚举 GROUPING SETS。

MySQL 上怎么替代？

MySQL 8.0 只有 WITH ROLLUP。要「多粒度小计」就老老实实写 UNION ALL，或者把结果在应用层拼装；也可以先 GROUP BY 到一张汇总宽表（明细已经聚合过一次）再在汇总表上做多次查询，成本会低很多。

代价是什么，什么时候不该用？

分组数越多，单次扫描要维护的聚合状态越多。如果分组数超过十几组、且基表极大，内存可能成为瓶颈。这种情况下可以拆成两三个 GROUPING SETS 分别跑，反而更稳。

自检

汇总行的 product 为 NULL，能断定原始 product 没有值吗？

不能。它可能只是该汇总层级未按 product 分组；可用 GROUPING(product) 等标志区分。
