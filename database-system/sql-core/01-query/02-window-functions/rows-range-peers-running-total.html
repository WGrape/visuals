SQL 窗口帧手算：ROWS 和 RANGE 遇到同一天两行时为何累计值不同

用三笔订单逐行算累计金额，讲透同值组、排序稳定性、默认窗口帧与 LAST_VALUE 陷阱。

分区、排序、窗口帧各负责一层

窗口函数保留每一行，同时在一组相关行上计算结果。PARTITION BY 决定分组边界，ORDER BY 决定组内顺序，窗口帧再决定“当前行计算时究竟看哪些行”。把三者混成“窗口就是前面所有行”，遇到同一天多笔订单或 LAST_VALUE 时很容易写错。不同数据库对未显式写窗口帧时的默认行为有差异，尤其是排序存在同值行时；生产 SQL 应尽量把关键帧写清楚。

本课以三笔订单为例：id=1 和 id=2 都在 10 月 1 日，金额分别 10 和 20；id=3 在 10 月 2 日，金额 5。希望回答两个不同问题：“按订单逐笔累计”与“截至当天累计”，二者不应在同一天第二笔之前得到同一个值。

沿箭头逐步核对输入、变换和输出；下面的推演可以逐步切换。

ROWS 是物理行数边界

若按 day、id 排序，使用 SUM(amount) OVER(ORDER BY day, id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)，第 1 行只看金额 10，输出 10；第 2 行看 10+20，输出 30；第 3 行看 10+20+5，输出 35。ROWS 的 CURRENT ROW 指当前这一物理行，不会自动把其他同一天行全部装进来。这里额外按 id 排序是为了明确同一天内部先后；若只 ORDER BY day，同值行谁先算可能取决于执行计划，结果行与 id 的对应关系不稳定。

若业务仅要“每笔订单之后的余额”，还要确认 day、id 的顺序真能代表发生顺序。订单 ID 不一定等于创建时间，必要时使用事件时间加稳定唯一键，处理同一时刻的并列情况。

RANGE 会把同值行放进当前组

使用 SUM(amount) OVER(ORDER BY day RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) 时，同一天的两行是 peer，同属于排序值 10 月 1 日；两行都看到截至当天的 10+20=30，第 3 行看到 35。因此结果为 30、30、35。RANGE 的 CURRENT ROW 在这种边界下指当前排序值所在的同值组边界，不等于“当前行编号”。若 ORDER BY day,id，则每行排序键不同，peer 关系改变，不能照搬 30、30、35 的结论。

RANGE 还可用于按排序值范围定义如“此前 7 天”的窗口，但日期时间区间语法和允许的 ORDER BY 表达式依数据库而异。ROWS 7 PRECEDING 指前七行，不是前七天；若某天有一万行，二者的业务含义差得很远。

一个默认帧陷阱

不少数据库在写了 ORDER BY、却没写显式窗口帧时，聚合窗口采用从分区开头到当前 peer 组的默认范围，结果更像上面的 RANGE 累计；但具体 SQL 方言与函数限制要核对。若开发者原本想逐笔累计，线上同一天插入第二笔后第一笔的累计值可能变化。写显式 ROWS 帧并给出稳定排序键，比猜默认规则更稳健。

另一个常见误用是 LAST_VALUE(amount) OVER(PARTITION BY customer ORDER BY day)。若默认帧只到当前行或当前 peer，LAST_VALUE 往往返回截至当前的最后值，而不是整个客户分区的真正最后一笔。要取完整分区末值，应显式让帧延伸到 UNBOUNDED FOLLOWING，并定义唯一排序；也可根据方言改用其他明确写法。

NULL、并列和执行计划

ORDER BY 列如果有 NULL，不同数据库对 NULL 排序位置的默认约定可能不同；明确处理缺失日期或使用方言支持的 NULLS FIRST/LAST。相同排序键下，ROWS 帧的计算顺序需要额外稳定键，否则两次运行可能把 10 和 20 的逐笔累计分配给不同 id。RANGE 与 peer 组的值虽相同，但窗口可能更大；在大量重复键和复杂窗口表达式中要检查执行计划及内存使用。

窗口函数通常在 WHERE、GROUP BY 等逻辑处理之后作用于当前结果行集。若先过滤掉某些订单，累计的输入也变了；如果要“先算全量累计再筛出今天”，可能需要子查询或 CTE，把计算与过滤的层次分开。

何时该用 GROUP BY

要得到每天一行的日收入，用 GROUP BY day 更直接；要保留每笔订单又附上当天总额或截至当天累计，用窗口函数。也可以先按天 GROUP BY 生成日汇总，再对日汇总做跨天累计，这样避免同日多行 peer 的歧义。预聚合与窗口并用时应检查金额单位、退款负数和重复订单处理；SQL 语法正确不保证业务口径正确。

窗口帧的选择应写在报表定义中：是“前 7 行交易”“此前 7 个自然日”“本月截至当前日期”还是“截至此笔交易”。中文描述若不明确，开发实现可能各有一套。

验收三笔订单

在数据库里插入 id1/day1/10、id2/day1/20、id3/day2/5，分别执行显式 ROWS 与 RANGE 版本。核对预期 10、30、35 与 30、30、35；再把插入顺序打乱，确认带 id 排序的 ROWS 结果稳定。最后新增 day1/id4/7，观察“逐笔累计”和“截至当天累计”如何变化，并检查 LAST_VALUE 是否真正返回全分区末行。

上线前把数据库产品与版本写进测试说明，因为窗口帧语法、默认值和 RANGE 对日期的支持存在方言差异。一个三行最小样本比只看大报表总额更容易暴露同值行错误。

窗口帧的三种模式

模式按什么界定窗口相同值的处理典型用途
ROWS物理行数同值也可能被切开移动平均（固定行数）
RANGE值的范围同值必定在同一组（PEERS）累计求和、按值聚合
GROUPSpeer 组的个数（PG 11+）按组计数介于两者之间

最关键的差异：RANGE 会把排序键相同的所有行视为一个整体（称为 peer），要么全在窗口内、要么全在窗口外；ROWS 严格按行数切，可能把相同值的行切开。

ROWS vs RANGE

-- 示例数据：amount = [100, 200, 200, 300]
SELECT id, amount,
  SUM(amount) OVER (ORDER BY amount ROWS UNBOUNDED PRECEDING)  AS sum_rows,
  SUM(amount) OVER (ORDER BY amount RANGE UNBOUNDED PRECEDING) AS sum_range
FROM t;

-- 结果对比（关键看 amount=200 的两行）：
--  id | amount | sum_rows | sum_range
--   1 |    100 |      100 |       100
--   2 |    200 |      300 |       500   ← <strong>RANGE 直接跳到 500！</strong>
--   3 |    200 |      500 |       500   ← 两行相同（peer 一起算）
--   4 |    300 |      800 |       800
--
-- 解释：RANGE 模式下，amount=200 的两行是 peer，
--       UNBOUNDED PRECEDING 包含<strong>所有值 ≤ 200 的行</strong>
--       所以第 2 行的窗口已包含第 3 行 → 100+200+200 = 500

默认帧：容易忽略的坑

如果写了 ORDER BY 但没写帧子句，默认是 RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW——即「从开头到当前行（含所有 peer）」。

写法实际帧注意
OVER (ORDER BY x)RANGE UNBOUNDED PRECEDING ~ CURRENT ROW默认不是 ROWS！
OVER ()整表（无 ORDER BY 时）所有行一组
OVER (PARTITION BY p)整个分区同上
ROWS UNBOUNDED PRECEDING从首行到当前行显式指定才安全

移动平均

-- 陷阱：想算「移动平均（最近 7 天）」，用 RANGE 会算错
-- ✗ RANGE 按值界定，若某天有多条记录，窗口会包含所有同值的行
AVG(v) OVER (ORDER BY dt RANGE BETWEEN 6 PRECEDING AND CURRENT ROW)

-- ✓ 若想按「最近 7 行」算，必须显式 ROWS
AVG(v) OVER (ORDER BY dt ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)

-- ✓ 若想按「最近 7 天」算（日期类型是连续的），用 RANGE 才对
AVG(v) OVER (ORDER BY dt RANGE BETWEEN INTERVAL 6 DAY PRECEDING AND CURRENT ROW)
--   注意：RANGE + INTERVAL <strong>要求 ORDER BY 列是日期/数值类型</strong>
--   且 MySQL 8.0 / PG 11+ 才支持

对重复值敏感的场景必须用 ROWS：比如「最近 7 笔订单」，若同一天有 3 笔，RANGE 会把 3 笔都算进去（变成 9 笔），结果错误。先想清楚要「7 行」还是「7 天」，再选 ROWS 还是 RANGE。

常用窗口函数与代价

函数用途对帧的敏感
ROW_NUMBER()连续序号（同值也给不同号）不敏感（只看位置）
RANK()排名，同值同号，跳号不敏感
DENSE_RANK()排名，同值同号，不跳号不敏感
SUM/AVG/COUNT累计/移动聚合高度敏感
LAG/LEAD取前/后 N 行不敏感（用偏移量）
FIRST_VALUE/LAST_VALUE窗口首/末值敏感（注意默认帧！）

函数与陷阱

-- LAST_VALUE 的经典陷阱
SELECT id, v,
  LAST_VALUE(v) OVER (ORDER BY id) AS wrong,      -- ✗ 默认帧到 CURRENT ROW
  LAST_VALUE(v) OVER (ORDER BY id
    ROWS BETWEEN UNBOUNDED PRECEDING
             AND UNBOUNDED FOLLOWING) AS right    -- ✓ 延伸到末尾
FROM t;
-- 默认帧是 "... AND CURRENT ROW"，所以 LAST_VALUE 就是当前行！
--   wrong 列等于 v 本身，毫无意义
-- <strong>用 LAST_VALUE 必须显式写 UNBOUNDED FOLLOWING</strong>

-- 性能提示：窗口函数需要排序
--   PARTITION BY a ORDER BY b  →  需要按 (a, b) 排序
--   若 (a,b) 上有索引，可省去排序（EXPLAIN 里无 "Using filesort"）
--   大表上无索引的窗口函数会产生<strong>磁盘临时表</strong>，很慢

自检 Q&A

Q：为什么我的累计求和在同一值的行上结果相同？

A：因为你用了默认的 RANGE 帧。排序键相同的行互为 peer，窗口要么全包含要么全不包含，所以它们的累计值相同。如果你期望「逐行递增」，必须显式写 ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW。这是窗口函数最常见的「结果不对」的原因，而且很容易被误认为是数据库的 bug。

Q：ROW_NUMBER 和 RANK 怎么选？

A：看同值时是否接受并列。ROW_NUMBER 给 1,2,3,4（同值也分先后，顺序不确定）；RANK 给 1,2,2,4（并列后跳号）；DENSE_RANK 给 1,2,2,3（并列不跳号）。业务上「前三名」如果用 RANK，可能出现并列第二导致没有第三名——此时该用 DENSE_RANK。另外 ROW_NUMBER 在值相同时顺序是不确定的，需要稳定结果必须加一个唯一列作为次排序键。

Q：窗口函数为什么这么慢？

A：主要成本是排序。每个 OVER (PARTITION BY a ORDER BY b) 都需要一次排序，多个窗口函数若排序键相同可复用一次排序，不同则各自排序。优化手段——① 建 (a, b) 复合索引让数据已有序，省去排序；② 减少不同排序键的窗口函数数量；③ 调大 sort_buffer_size 避免落盘。用 EXPLAIN 看是否出现 Using temporary; Using filesort。

Q：能在 WHERE 里过滤窗口函数的结果吗？

A：不能，必须用子查询或 CTE。因为 SQL 的执行顺序是 WHERE → GROUP BY → 窗口函数 → ORDER BY，窗口函数在 WHERE 之后才计算，所以 WHERE 里引用它属于「引用了还不存在的东西」。正确写法：SELECT * FROM (SELECT ..., ROW_NUMBER() OVER(...) rn FROM t) x WHERE x.rn = 1。这也是为什么「取每组第一行」要包一层子查询。

自检

ORDER BY day 且 10 月 1 日有两行，RANGE 到 CURRENT ROW 是否一定只包含当前这一行？

不是。同一天的排序值相同，通常是 peer 组；两行都可包含当天两笔金额，得到 30。
