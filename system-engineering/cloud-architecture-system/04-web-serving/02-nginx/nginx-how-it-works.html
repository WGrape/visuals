①先给结论：NGINX 快不是因为「算得快」，而是换了个并发模型

理解 NGINX，最关键的不是记住多少配置项，而是看懂它对「高并发」这件事给出的答案和传统服务器完全不同。

传统做法是 一个连接配一个执行体（一个进程 / 一个线程）。连接一多，内存被栈吃光、上下文切换把 CPU 吃掉——这就是著名的 C10K 问题。

NGINX 的做法是：极少数几个 worker 进程，每个跑一个单线程事件循环，把上万个连接都变成循环里的「状态机条目」。连接不再对应执行体，只对应一个 fd 和一小块内存。

支柱一 · 事件驱动 + 非阻塞

worker 用 epoll（Linux）/ kqueue（BSD）等 IO 多路复用，一个线程盯住成千上万个 fd，谁就绪处理谁，绝不为某个连接干等。

支柱二 · Master-Worker 多进程

worker 数与 CPU 核数相当，吃满多核；worker 之间不共享内存、无需加锁，一个挂了 master 立刻补一个。

支柱三 · 模块化流水线

请求被拆成 11 个阶段依次流过，每个功能（重写、鉴权、限流、代理、压缩、日志）都是挂在某个阶段上的模块，按需装配。

本篇的定位：同目录的 《NGINX 实现架构》 是架构图集（看图速览）；本篇讲原理——为什么这么设计、每一步具体怎么运转。两者配合看。

②核心架构：Master-Worker 进程模型

启动后 NGINX 有两种进程，职责截然不同：

Master 进程做什么

以较高权限启动，读 nginx.conf、bind() 监听端口，然后 fork() 出 worker。之后它就只负责：接信号、管 worker 生死、热重载 / 热升级。它完全不处理请求。

Worker 进程做什么

真正的干活者：accept() 新连接、读写数据、跑 11 个阶段、转发上游。每个 worker 是单线程事件循环，彼此独立、内存不共享。

为什么用多进程不用多线程

进程间内存隔离 → 几乎不需要加锁；一个 worker 崩溃不会拖垮其它 worker，master 会立刻重新拉起。代价：需要跨进程共享的状态必须显式放进共享内存。

为什么端口不会冲突？所有 worker 都是 master fork() 出来的，继承了 master 已经 bind 好的监听 fd——所以虽然多个 worker 都在「监听」同一个端口，实际上共享的是同一个 socket，不存在重复绑定。

③工作原理的灵魂：单线程事件循环

这是 NGINX 全部高性能的来源。worker 进程启动后，就进入一个永不退出的循环：

// 语义化伪代码（非源码直抄）
while (true) {
    events = epoll_wait(epfd, timeout);   // ① 问内核：哪些 fd 就绪了？
    for (ev in events) {
        if (ev.fd == listen_fd)  handle_new_connection();   // 新连接
        else if (可读)            handle_read(ev.fd);       // 请求数据到了
        else if (可写)            handle_write(ev.fd);      // 缓冲区腾出空间
    }
    process_timers();                       // ② 处理超时（keep-alive、上游超时…）
}
唯一的铁律：任何可能阻塞的操作，都必须注册成事件后立刻返回，绝不能占着线程干等。
读请求头没读全？把 fd 放回 epoll 等下次通知。等上游响应？同样注册事件返回。磁盘读文件慢？交给 sendfile 或线程池。正是因为「从不干等」，一个单线程 worker 才能同时照看上万条连接。

④一个请求的完整生命周期

1
客户端发起 TCP 三次握手
握手由内核完成，连接先进监听 socket 的全连接队列。此时 NGINX 应用层还不知情。
2
某个 worker 的 epoll 发现「监听 fd 可读」
监听 fd 可读 = 全连接队列里有新连接。worker 调用 accept() 拿到一个新的连接 fd，把它加入自己的 epoll 关注集合。
3
读取并解析请求头（非阻塞）
尝试读取 HTTP 请求头。没读全就立刻返回，等下一次 epoll 通知再继续——绝不卡住整个 worker。
4
依次流过 11 个处理阶段
从 POST_READ 到 LOG，每个阶段上挂着相应的模块 handler。详见下一节的逐阶段拆解。
5
产生响应内容
静态文件走 sendfile 零拷贝；动态请求走 proxy_pass / fastcgi_pass 转发上游（见第 ⑥ 节）。
6
写回客户端 → LOG 阶段记日志
若开启 keep-alive，连接不关闭，回到 epoll 等待该客户端的下一个请求；否则四次挥手关闭。
「新连接来了该哪个 worker 接？」这是经典的惊群问题。历史上靠 accept_mutex 让 worker 轮流持有监听锁来避免全被唤醒；现代内核有了 EPOLLEXCLUSIVE（NGINX 1.11.3+）或 SO_REUSEPORT，内核自己只会唤醒一个，因此 accept_mutex 现在默认是 off。

⑤核心难点：请求的 11 个处理阶段

NGINX 把一次 HTTP 请求的处理切成 11 个阶段（Phase）顺序执行，模块把自己的 handler 挂到某个阶段上。这是理解 NGINX 配置「为什么这些指令会这个顺序生效」的钥匙。

为什么这个顺序重要？举个例子：limit_req（限流）挂在 PREACCESS，而 auth_basic（鉴权）挂在 ACCESS——所以限流发生在鉴权之前，被限流掉的请求根本不会去做密码校验。再比如 realip 在 POST_READ，是最早能拿到并改写「客户端真实 IP」的地方，后面所有基于 IP 的限流/鉴权看到的都是改写后的值。

⑧几个让它更快 / 更稳的关键机制

sendfile 零拷贝

发静态文件时用 sendfile()，数据在内核态直接从文件页缓存送进网卡，不经过用户态来回拷贝，省掉 2 次拷贝和上下文切换。

内存池 ngx_pool_t

每个请求一个内存池，所有临时分配都从池里拿，请求结束整池释放——不需要逐个 free，既快又几乎不会有内存碎片和泄漏。

accept_mutex / 惊群

让 worker 轮流拿锁避免全被唤醒。默认 off（1.11.3 前为 on，默认延迟 500ms）；现代内核的 EPOLLEXCLUSIVE 或 reuseport 已原生解决惊群，无需再开。

热重载（SIGHUP）

master 收到 SIGHUP 重新读配置，起一批新 worker 接管新连接，旧 worker 把手上存量请求处理完再优雅退出——配置更新不断连。

热升级（USR2 + WINCH）

换二进制不中断服务：发 USR2 起一套新 master + 新 worker 与旧的并存，再 WINCH 让旧 worker 逐步退出，新旧两套都能随时回滚。

upstream keepalive

与上游之间复用长连接，避免每个请求都重新握手。注意：这些空闲的 upstream 连接同样占用连接槽和 fd。

信号速查：QUIT 优雅关闭 · HUP 热重载配置 · USR1 重新打开日志文件 · USR2 热升级 · WINCH 让旧 worker 优雅退出 · TERM 立即停止。

⑨常见误区与速记

误区 1：「worker 越多越好」

❌ worker 是单线程跑满一个核的，超过 CPU 核数并不会更快，只会多占内存、增加调度开销。容器里尤其要小心：auto 可能检测到宿主机的核数而非 cgroup 配额，导致起出几十个 worker。

误区 2：「worker_connections 就是能服务的客户端数」

❌ 它统计的是全部连接，包括与上游的连接。做反向代理时每个并发请求占 2 条，实际能服务的请求数约为 worker_processes × worker_connections / 2。

误区 3：「调大 worker_connections 就能提高并发」

❌ 真正的天花板往往是文件描述符：worker_rlimit_nofile、systemd 的 LimitNOFILE、OS 的硬限制，取最小值。只改 nginx.conf 可能被 systemd 悄悄覆盖。

误区 4：「NGINX 里一个连接就是一个线程」

❌ 恰恰相反——这正是它高效的原因。连接只是一个 fd 加一小块内存，由 worker 的事件循环统一照看。

误区 5：「accept_mutex 一定要开，不然会惊群」

❌ 现代内核（EPOLLEXCLUSIVE，NGINX 1.11.3+）或用 reuseport 时内核只会唤醒一个 worker，accept_mutex 默认已经是 off；开启反而增加抢锁开销。
