LEFT JOIN 中 ON、WHERE 与 NULL 的边界

把右表条件放在 ON 或 WHERE，结果可能完全不同。

核心机制

LEFT JOIN 保留左表的每一行。找不到匹配时，右表列被填成 NULL。ON 决定哪些右表行能够匹配；WHERE 在连接结果形成后继续筛选整行。

SQL 的比较有 TRUE、FALSE、UNKNOWN 三种结果。NULL = 1 得到 UNKNOWN；WHERE 只保留 TRUE，所以在 WHERE 中筛右表字段常会删除未匹配的左表行。

用一个例子看过程

SELECT u.id, o.id FROM users u
LEFT JOIN orders o ON o.user_id=u.id AND o.status='paid';
-- 所有用户仍在；没付费订单的用户其 o.id 为 NULL。

形成匹配

ON o.user_id=u.id AND o.status=paid 只选择付费订单参与匹配。

补齐左行

无匹配订单的用户仍输出一行，右表字段为 NULL。

再执行 WHERE

若加 WHERE o.status=paid，上一步补齐的行因 UNKNOWN 被过滤。

观察、原因与处理

观察原因或含义处理与验证

把两种写法落到具体数据

假设 users 有 Alice、Bob、Carol 三人；orders 只有 Alice 的 paid 订单和 Bob 的 pending 订单。若把 o.status = 'paid' 写在 ON 中，连接时 Bob 的 pending 订单不算匹配，但 Bob 和 Carol 的左表行仍保留，右表列补 NULL。若把相同条件写在 WHERE 中，Bob 和 Carol 的结果行都会被筛掉，只剩 Alice。语句看起来只是移动了一个条件，结果却从“所有用户及其付费订单”变成“有付费订单的用户”。

当未匹配行的 o.status 为 NULL 时，o.status = 'paid' 的结果是 UNKNOWN，而 WHERE 只保留 TRUE。NULL = NULL 同样不会得到 TRUE；检查缺失值应使用 IS NULL。优化器可以改变物理执行顺序，但不能改变这个语义结果。

反连接和重复行

要找“没有付费订单的用户”，先在 ON 中限定 paid，再用 WHERE o.id IS NULL 查补齐行，其中 o.id 应为右表非空主键。若误用允许 NULL 的列判断，真实匹配行可能被错当成未匹配。另一种写法是 NOT EXISTS 相关子查询，它直接表达“某种订单不存在”。是否更快取决于索引、基数与优化器计划，不能只凭 SQL 形式猜测。

如果 Alice 有两笔 paid 订单，LEFT JOIN 会输出两行 Alice。做用户级报表时要先确认连接基数，再使用聚合、去重或预聚合。把重复误认为优化器故障，会掩盖真实的一对多关系。

练习：把需求分别改写成“展示所有用户”“只展示付费用户”“查找从未付费的用户”，为每条 SQL 选择 ON、WHERE 或 NOT EXISTS，并用上表手算返回行数。

边界与误区

优化器可重排物理执行，但必须保持 SQL 语义。对 NULL 值做等号比较应使用 IS NULL / IS NOT NULL；部分方言还有专用的 NULL 安全比较。

检查真实查询时的顺序

先用极小的手工数据覆盖“有匹配”“只有不满足条件的右表行”“完全无右表行”三种情况，并写出期望结果；再看实际 SQL。之后才使用 EXPLAIN 检查索引和连接算法。性能计划不能替代语义验证：即便优化器把 LEFT JOIN 在特定条件下化简为 INNER JOIN，也必须与原 SQL 在该条件下的结果一致。若报表还需要聚合，先确认右表一对多会生成多少行，再聚合，以免把每个用户的金额重复计数。

COUNT 的另一处陷阱

LEFT JOIN 补出的行在右表列上是 NULL。按用户分组后，COUNT(*) 会把这条补齐行计为 1，而 COUNT(o.id) 只统计非空的右表主键；因此“无订单用户的订单数”应根据需要选后者。若右表真实匹配多行，COUNT(o.id) 会给出多行数量，COUNT(DISTINCT o.id) 才去重。把 ON/WHERE 的条件位置与 COUNT 的对象同时检查，才能防止报表既漏用户又错计数量。

第一层 · ON 与 WHERE 的本质区别

这是 SQL 最容易出错的地方：ON 决定「怎么匹配」，WHERE 决定「保留哪些行」。对 LEFT JOIN 来说，把条件放错位置会让它退化成 INNER JOIN。

条件位置作用时机对 LEFT JOIN 的影响
ON 子句匹配阶段（决定右表哪些行能匹配上）不匹配的左表行仍然保留（右表列填 NULL）
WHERE 子句过滤阶段（匹配完成后筛掉行）会过滤掉右表为 NULL 的行 → 退化成 INNER JOIN

SQL 对比

-- —— 经典陷阱：LEFT JOIN 写成了 INNER JOIN ——
-- 场景：查出所有用户，以及他们的【有效】订单（status=1）

-- ❌ 错误：条件写在 WHERE -> 没有有效订单的用户被过滤掉了
SELECT u.name, o.id
FROM user u
LEFT JOIN orders o ON u.id = o.user_id
WHERE o.status = 1;
--   结果：只返回有有效订单的用户
--   原因：没有订单的用户 o.status 是 NULL，NULL = 1 结果为 UNKNOWN -> 被 WHERE 过滤

-- ✅ 正确：条件写在 ON -> 没订单的用户仍然出现（o.id 为 NULL）
SELECT u.name, o.id
FROM user u
LEFT JOIN orders o ON u.id = o.user_id AND o.status = 1;
--   结果：所有用户都返回，没有效订单的 o.id 为 NULL

-- ✅ 等价写法（显式处理 NULL）
SELECT u.name, o.id
FROM user u
LEFT JOIN orders o ON u.id = o.user_id
WHERE o.status = 1 OR o.status IS NULL;
--   注意：这个写法在【右表本来就有 status IS NULL 的行】时会出错！

-- —— 找出「没有订单的用户」（LEFT JOIN + IS NULL 的标准用法）——
SELECT u.name
FROM user u
LEFT JOIN orders o ON u.id = o.user_id
WHERE o.id IS NULL;                    -- 【注意用主键判 NULL，最可靠】
--   用 o.id（主键，非空）判断，避免右表本来就有 NULL 列的误判

-- —— 三值逻辑速查 ——
--   NULL = 1      -> UNKNOWN（被 WHERE 过滤）
--   NULL <> 1     -> UNKNOWN（也被过滤！）
--   NULL IS NULL  -> TRUE
--   NULL AND TRUE -> UNKNOWN
--   NULL OR TRUE  -> TRUE      <- 注意这个
--   NOT NULL      -> UNKNOWN

记忆口诀：LEFT JOIN 想保留左表全部行 → 右表的条件必须写在 ON 里。写在 WHERE 里就等于 INNER JOIN 了。

SQL 陷阱

-- —— 最危险的陷阱：NOT IN 遇到 NULL ——
SELECT * FROM users WHERE id NOT IN (SELECT user_id FROM orders);
--   如果 orders.user_id 里有【任何一个 NULL】-> 整个查询返回【空集】！
--   原因：x NOT IN (1, 2, NULL) 等价于 x<>1 AND x<>2 AND x<>NULL
--         x<>NULL 是 UNKNOWN -> 整个表达式为 UNKNOWN -> 一行都不返回

-- ✅ 正确写法 1：NOT EXISTS（推荐，语义清晰且不受 NULL 影响）
SELECT * FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);

-- ✅ 正确写法 2：LEFT JOIN + IS NULL
SELECT u.* FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE o.user_id IS NULL;

-- ✅ 正确写法 3：排除 NULL（不推荐，容易漏）
SELECT * FROM users WHERE id NOT IN (SELECT user_id FROM orders WHERE user_id IS NOT NULL);

-- —— COUNT 的三种写法差异 ——
--   表有 10 行，其中 col 有 3 个 NULL
SELECT COUNT(*)    FROM t;   -- 10  【统计行数】
SELECT COUNT(col)  FROM t;   -- 7   【跳过 NULL】
SELECT COUNT(1)    FROM t;   -- 10  （与 COUNT(*) 等价，某些旧版本略慢）

-- —— AVG 的陷阱 ——
--   col 值为 10, 20, NULL
SELECT AVG(col) FROM t;              -- 15     （只算非 NULL：(10+20)/2）
SELECT SUM(col)/COUNT(*) FROM t;     -- 10     （30/3，把 NULL 当 0）
SELECT SUM(col)/COUNT(col) FROM t;   -- 15     （与 AVG 一致）
--   【注意】很多业务想要的是「把 NULL 当 0」，那就用 COALESCE：
SELECT AVG(COALESCE(col, 0)) FROM t; -- 10

-- —— LEFT JOIN 后的计数膨胀 ——
--   user 3 行，orders 每个用户 2 单
SELECT COUNT(*) FROM user u LEFT JOIN orders o ON u.id=o.user_id;  -- 6（膨胀！）
SELECT COUNT(DISTINCT u.id) FROM user u LEFT JOIN orders o ON ...;  -- 3（正确）

NOT IN 遇到 NULL 返回空集是 SQL 里最隐蔽的坑之一。养成用 NOT EXISTS 的习惯，一劳永逸。

第三层 · 排障清单

  • LEFT JOIN 结果行数和 INNER JOIN 一样（少了数据） → 右表条件写在 WHERE 了。移到 ON。这是最高频的问题。
  • 查询突然返回 0 行 → 检查是否有 NOT IN + 子查询含 NULL。改用 NOT EXISTS。
  • col = NULL 查不到数据 → 要用 IS NULL。= NULL 永远返回 UNKNOWN。
  • COUNT 的结果比预期少 → 用了 COUNT(可空列)。改用 COUNT(*)。
  • LEFT JOIN 后 SUM/COUNT 变大 → 一对多关系导致行膨胀。解法：① 先聚合右表再 JOIN（JOIN (SELECT user_id, SUM(...) GROUP BY user_id) t）；② 用 COUNT(DISTINCT 左表主键)。
  • 多个 LEFT JOIN 导致结果爆炸 → 每个一对多都会乘一次（2×3×4 = 24 行）。必须先把每个右表聚合到「一对一」再 JOIN。
  • 平均值偏低/偏高 → AVG 忽略了 NULL，但你的业务语义可能是「NULL 当 0」。用 COALESCE 明确。
  • ORDER BY 带 NULL 的顺序不符合预期 → 各数据库不同：MySQL/SQL Server 把 NULL 排最前（升序时），PostgreSQL/Oracle 排最后。要显式写：ORDER BY col IS NULL, col（把 NULL 放最后）或 ORDER BY col NULLS LAST（PG/Oracle 支持）。
  • 索引列允许 NULL 导致索引行为异常 → IS NULL 在某些数据库上能用索引（MySQL 可以），但 col <> 1 不会包含 NULL 的行。建议关键列设 NOT NULL + 默认值，从根源避免。
  • 外连接 + 聚合导致 NULL 传播 → SUM(NULL + x) 结果是 NULL。用 COALESCE(SUM(x), 0)。

第四层 · 原理与取舍

所有 NULL 相关的问题，根源都是同一条：SQL 使用三值逻辑（TRUE / FALSE / UNKNOWN），而 NULL 表示「未知」而不是「空」。

  • 为什么是三值逻辑：NULL 的语义是「值未知」。那么「未知的值等于 1 吗？」答案既不是 TRUE 也不是 FALSE，而是不知道（UNKNOWN）。这个哲学选择导致了所有 NULL 相关的反直觉行为。理解这一点，就能推导出所有规则，而不用死记。
  • WHERE 只保留 TRUE：WHERE 子句里的条件为 UNKNOWN 的行会被丢弃（和 FALSE 一样）。所以 WHERE col = 1 会同时丢掉 col IS NULL 的行——这是很多人没意识到的。
  • 为什么 NOT IN 会返回空集：x NOT IN (a, b, c) 展开为 x<>a AND x<>b AND x<>c。只要集合里有一个 NULL，就有 x <> NULL → UNKNOWN → TRUE AND TRUE AND UNKNOWN = UNKNOWN → 所有行都不满足 → 空集。这是三值逻辑最著名的陷阱。
  • ON 与 WHERE 的执行顺序：对 LEFT JOIN，逻辑上是「先按 ON 做外连接（保证左表行全部保留）→ 再按 WHERE 过滤」。所以 WHERE 里对右表的条件会把「补了 NULL 的行」过滤掉，效果等价于 INNER JOIN。
  • 设计建议：尽量用 NOT NULL。允许 NULL 的列会带来：① 三值逻辑的复杂性；② 索引和统计信息的行为差异；③ 应用代码要到处判断。所以建表时给合理的默认值（空字符串、0、''）比允许 NULL 更好。例外：「确实未知」的语义（如「用户未填写」）用 NULL 是合适的。

为什么 NOT IN 遇到 NULL 会返回空集？这个坑怎么避免？

因为 x NOT IN (集合) 会被展开成一串 AND 连接的不等式：x<>a AND x<>b AND x<>c。如果集合里有一个 NULL，那么其中一项变成 x <> NULL，其结果是 UNKNOWN（不是 TRUE）。而三值逻辑里 TRUE AND UNKNOWN = UNKNOWN，UNKNOWN 在 WHERE 中会被当作不满足。所以结果是：每一行都不满足条件 → 返回空集。这个坑特别隐蔽，因为它在子查询「碰巧没有 NULL」时工作正常，一旦数据里出现 NULL 就突然返回空——而且是静默的（不报错，只是结果不对）。避免方法：① 永远用 NOT EXISTS 代替 NOT IN——NOT EXISTS 用的是「存在性判断」，不涉及与 NULL 的比较，所以完全不受影响，而且语义更清晰、优化器通常也能生成更好的计划。这是最推荐的做法，应该变成肌肉记忆；② 用 LEFT JOIN + IS NULL（效果相同，某些场景更快）；③ 如果一定要用 NOT IN，必须加 WHERE col IS NOT NULL 过滤（但容易漏，不推荐）。顺带说，IN（不带 NOT）是安全的——因为 x IN (1,2,NULL) 展开是 OR 连接，只要有一项 TRUE 就成立。

LEFT JOIN 到底什么时候用 ON，什么时候用 WHERE？

判断标准只有一条：这个条件是「匹配规则」还是「结果过滤」。放 ON：条件描述的是「右表的哪些行算匹配上了」——比如「只要有效订单」o.status = 1，这是匹配规则的一部分，不满足的行不算匹配，但左表的行仍要保留（右表列填 NULL）。放 WHERE：条件描述的是「最终结果里要保留哪些行」——比如「只要 VIP 用户」u.is_vip = 1，这是对左表本身的过滤，放 ON 或 WHERE 对 LEFT JOIN 的效果是一样的（因为是过滤左表，不涉及右表 NULL）。所以核心区别只在针对右表的条件：放 ON 保留左表全部行，放 WHERE 则把没匹配上的行也过滤掉（退化成 INNER JOIN）。一个快速自检方法：写完 LEFT JOIN 后问一下「没匹配上的左表行还在吗？」——如果不在，说明你把右表条件放错位置了。另外提醒：这个区别只对 OUTER JOIN 有意义，对 INNER JOIN 来说 ON 和 WHERE 的效果完全相同（优化器也会等价处理）。

COUNT(*)、COUNT(1)、COUNT(列) 有什么区别？

三个层次的区别：语义上——COUNT(*) 统计行数（不关心列值，NULL 也算）；COUNT(1) 统计「表达式 1 非 NULL 的行数」，而常量 1 永远非 NULL，所以等价于 COUNT(*)；COUNT(列) 统计该列非 NULL 的行数，会跳过 NULL。结果上——只有 COUNT(列) 可能与前两者不同（当列可为 NULL 时）。性能上——现代数据库（MySQL 5.7+、PostgreSQL）对三者一视同仁，优化器会选择最小的可用索引来计数，没有实质差异；老的说法「COUNT(1) 比 COUNT(*) 快」是没有根据的（甚至有些时候 COUNT(列) 更快，因为它能用该列的窄索引）。实践建议：统一用 COUNT(*)——语义最清晰（就是数行数）、不会有跳过 NULL 的意外、且性能不差。只有在「我想知道这一列有多少个非空值」这种明确意图时才用 COUNT(列)。另外提一个相关陷阱：COUNT 在 LEFT JOIN 后会膨胀——因为一对多会产生多行，此时要 COUNT(DISTINCT 左表主键) 或者先聚合右表再 JOIN。

自检

LEFT JOIN 后写 WHERE o.status = paid，为何无订单用户消失？

其 o.status 为 NULL，比较结果 UNKNOWN；WHERE 不保留 UNKNOWN。
