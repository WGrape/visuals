文档数据库选型：MongoDB vs CouchDB vs DynamoDB

三个主流文档库的差异，以及在哪该用哪一个

文档模型适合什么

文档数据库（如 MongoDB）用半结构化的 BSON/JSON 存数据：一个"订单""文章""用户档案"就是一整篇文档，嵌套结构天然贴合对象。它最适合：schema 经常变、读写都以"整篇文档"为单位、字段参差不齐的数据。它不适合：需要跨文档强事务的账务、以及大量多对多关联与复杂 join。

📌 文档库不是"不要 schema"，而是 schema 由应用层负责（schema-on-read），灵活但要求你自己在代码里约束。

三个常见选手

🍃 MongoDB

BSON 文档、聚合管道、副本集 + 分片、支持多文档事务，生态最大。

🛋️ CouchDB

HTTP/JSON 原生、MVCC、离线优先、双向复制与冲突解决，适合边缘与同步。

⚡ DynamoDB

AWS 全托管 KV + 文档、单表设计、毫秒级、按 RCU/WCU 弹性容量。

选型建议

  • 通用应用、要生态和灵活查询：MongoDB，绝大多数场景的默认答案。
  • 设备离线、要双向同步：CouchDB 的复制模型天生为这个设计。
  • 极致规模 + 不想运维 + 在 AWS：DynamoDB，按容量付费、毫秒级。
⚠️ DynamoDB 的"简单"是有代价的：查询基本被主键和索引框死，表结构设计（单表设计）要从访问模式反推，后期改起来很痛。别拿它当 MongoDB 用。

第一层 · 先判定要不要文档库

信号该用什么
数据嵌套、结构常变、按整篇读写文档数据库
强一致多文档事务（账务）关系数据库
大量多对多 join关系数据库 / 图数据库
离线优先、要双向同步CouchDB
超大规模 KV、ServerlessDynamoDB

第二层 · 建模与容量关键数字

  • 嵌入 vs 引用：一对少、一起访问的放文档内（嵌入）；一对多且独立演进的用引用（避免文档膨胀与 16MB 上限）。
  • MongoDB 文档上限 16MB：超过要考虑 GridFS 或拆集合。
  • DynamoDB 单 item 上限 400KB：超过要拆或存 S3。
  • 分片键：MongoDB 选高基数的键，避免"热点分片"。

第三层 · 文档库踩坑怎么查

  • 查询全表扫：确认是否建了合适索引（MongoDB 最左前缀）。
  • 文档无限膨胀：嵌入数组不断 push，触及 16MB 或拖慢读取——改为引用或定期归档。
  • 跨文档一致性：MongoDB 多文档事务有开销，别在热路径滥用；DynamoDB 跨分区事务昂贵。
  • DynamoDB 容量爆：RCU/WCU 预估不足，突发被限流——开按需模式或提前规划。

第四层 · 原理与取舍

文档库用"聚合根"思想：一次访问单元就是一篇文档，数据库不需要跨文档 join 就能返回完整对象，所以读放大小、易水平扩展。代价是：跨文档的关系和事务变弱，冗余与最终一致开始出现。本质上它把"灵活 + 易扩展"放在前面，"强关系 + 强一致"往后放。CouchDB 更极端——用最终一致和冲突复制换来了离线优先与简单复制。

文档库能替代关系库吗？

不能一刀切。报表、强事务账务、复杂关系网络仍是关系库/图库的领地。文档库适合"以对象为中心"的业务数据，不是所有数据的归宿。
