OceanBase 架构与原理

LSM-Tree 存储引擎、Paxos 多副本与「三地五中心」——金融级分布式数据库

① 整体架构 ② LSM 存储引擎 ③ 多副本与 Paxos ④ 多租户 ⑤ 与 TiDB 对比 ⑥ 常见疑问
一句话总结：OceanBase 是蚂蚁集团自研的金融级分布式关系型数据库。 核心特色是LSM-Tree 存储引擎（高压缩、低写放大）、 基于 Paxos 的多副本强一致，以及原生多租户资源隔离。 它在支付宝核心链路与多地多活场景中经过了最严苛的验证。

01整体架构

图 1：OceanBase 是「每个节点都既算又存」的对等架构

🔌 OBProxy

无状态接入层。负责把 SQL 路由到数据所在的 OBServer（避免额外网络跳）。 对应用伪装成 MySQL，可独立部署或与应用同机部署。

🖥️ OBServer

核心节点，同时包含 SQL 引擎与存储引擎。 数据以分区为单位分散在各 OBServer 上，本地读写优先。

🎛️ RootService

总控服务，由所有 OBServer 通过选举产生（不独立部署）。 管理元数据、分区分布、每日合并调度、DDL 执行。

🏢 多租户 Tenant

集群内可创建多个逻辑租户，CPU/内存/IO 硬隔离。 一个集群服务多个业务，资源互不抢占。

02存储引擎：LSM-Tree

OceanBase 的存储引擎是经典的 LSM-Tree 架构，把随机写转成顺序写：

图 2：LSM-Tree 写入走内存 + 顺序日志，后台合并成压缩的基线 SSTable
「每日合并」是 OceanBase 的特色设计：在业务低峰期（可配置）触发一次全量 Major Compaction， 把所有增量数据合并进基线 SSTable。这让层数始终保持很少（通常 2 层）， 读放大远小于 RocksDB 式的多层 LSM——这是它敢用在金融核心链路的底气之一。

与 B+ 树引擎的对比

维度B+ 树（InnoDB）LSM-Tree（OceanBase）
写入模式随机写（可能触发页分裂）顺序追加，吞吐高
空间放大页内碎片，约 1.5×合并前有多版本，合并后压缩比高
读延迟稳定，2～3 次 IO需查多层，靠 BloomFilter + 每日合并优化
压缩比一般很高（基线数据静态，可重度压缩）
适用读多写少、延迟敏感写入密集、数据量大

03多副本与 Paxos

每个数据分区有多个副本（通常 3 个），组成 Paxos 组： 一个 Leader 负责读写，多数派确认才算提交。与 TiDB 用 Raft 类似， 但 OceanBase 用的是 Multi-Paxos。

图 3：三地五中心——5 个副本跨 3 城市，任一城市故障仍可提供服务且 RPO=0
核心机制：Paxos 组保证多数派确认才提交，因此任一少数派节点故障都不会丢数据（RPO=0）。 Leader 故障时剩余多数派自动选新主，RTO 通常在 30 秒以内。 这就是「金融级高可用」的技术基础。

04多租户资源隔离

OceanBase 原生支持在一个物理集群内创建多个逻辑租户， 每个租户有独立的 CPU、内存、IOPS 配额，硬隔离互不抢占。

🏢 租户 Tenant

相当于一个逻辑数据库实例，有自己的用户、库表、资源规格。 租户之间数据完全隔离，看不到对方。

📐 资源规格 Unit

定义 CPU 核数、内存大小、IOPS。租户通过 Unit 分布在多个 OBServer 上， 实现资源弹性伸缩。

💰 价值

一套集群替代多个独立 MySQL 实例， 资源利用率大幅提升，运维收敛到一套系统——这是它在大型企业受欢迎的原因。

-- 创建资源规格
CREATE RESOURCE UNIT unit_1c2g
  MAX_CPU = 1, MEMORY_SIZE = '2G', MAX_IOPS = 2000;

-- 创建资源池
CREATE RESOURCE POOL pool_app
  UNIT = 'unit_1c2g', UNIT_NUM = 3, ZONE_LIST = ('z1','z2','z3');

-- 创建租户（MySQL 兼容模式）
CREATE TENANT tenant_app
  RESOURCE_POOL_LIST = ('pool_app'),
  PRIMARY_ZONE = 'z1',
  CHARSET = 'utf8mb4',
  OB_COMPATIBILITY_MODE = 'mysql';

06常见疑问

Q：OceanBase 的「每日合并」会不会影响业务？
A：合并会消耗 CPU 和 IO，但 OceanBase 把它调度在业务低峰期（可配置时间窗口）， 并且有限速机制控制资源占用。这也是为什么它敢用「全量合并」这个看起来很重的策略—— 通过时间换空间，把读放大压到最低。
Q：LSM-Tree 的读放大怎么解决？
A：三招：① BloomFilter 快速判断某层是否含目标 key，跳过无关 SSTable； ② 每日合并把层数压到 2 层左右；③ 缓存（Block Cache / Row Cache）命中热数据。 实际生产中 OceanBase 的读延迟是可控的，代价主要在冷数据的首次读取。
Q：为什么 OceanBase 敢用在金融核心？
A：三个硬指标——RPO=0（Paxos 多数派确认，不丢数据）、 RTO < 30s（自动选主恢复）、三地五中心（城市级故障可容忍）。 再加上蚂蚁自身双十一的极端流量验证，是少数经过金融级考验的国产数据库。
