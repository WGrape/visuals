01 · 从问题出发

为什么会需要这个模式？

HTTP 请求有方法、URL、头、超时、正文；长参数列表容易把可选项填错。

请求对象构造函数若有八个参数，调用 Request('POST','/orders',null,3000,true,null,body,false) 时无法一眼看出每个位置代表什么；漏掉 URL 或把 timeout 写成负数也可能直到发送时才报错。

😵 直接写会怎样

request = Request("POST", "/orders", null, 3000,
                  true, null, payload, false)
// 第 5 个 true 是什么？哪些字段必须填写？

💡 关键转折

Builder 收集配置步骤，build() 统一校验并产出完整对象。

把每个配置项变成有名字的步骤，并在 build() 时集中校验；调用方看到的是意图，而不是一串位置参数。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

request = RequestBuilder()
  .method("POST")
  .url("/orders")
  .header("Content-Type", "application/json")
  .body(payload)
  .build()  // 校验后返回不可变 Request

读代码时抓住三件事

  1. 链式方法返回 this，使多个配置步骤可读。
  2. build 是唯一交付入口，负责必填项和跨字段规则。
  3. 返回的 Request 应保存数据快照，避免 Builder 后续修改污染旧结果。

换个业务场景，还能认出来吗？

创建一份云服务器配置时，可依次选择 CPU、内存、地域、安全组，再由 build 检查地域与实例规格是否兼容。这比多个布尔参数更容易检查。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

一个对象的配置步骤多、可选项多或有跨字段约束

三个具体场景

  • HTTP 请求含方法、头、正文与超时
  • 云服务器实例配置 CPU、地域与网络
  • 复杂 SQL 查询分步设置过滤、排序与分页

不适合或要小心

不要为了两个简单参数引入 Builder。build() 后最好返回不可变结果，避免半成品对象继续被修改。

两个简单参数就能说明意图时，不需要 Builder

最容易混淆的相邻模式

模式真正的区别
抽象工厂创建一组相关产品；建造者分步骤构造一个复杂对象。
原型复制现成样板；建造者从配置步骤新组装对象。

区分时问自己：是在分步组装一个新对象，还是一次选择一族对象？

落地前检查

  • 明确默认值与必填项，避免静默填错。
  • 测试非法组合，例如 GET 正文、负超时。
  • 复用 Builder 时确认上次配置是否被清理或复制。
06 · 自己说一遍

两道检验理解的小题

为什么在 build() 校验？

各配置步骤可按不同顺序执行；最终统一校验才能保证对象完整。

Builder 是否必须使用链式写法？

不必须。关键是分步配置和最终校验；链式调用只是提高可读性的一种接口形式。

一句话把「复杂对象的构造过程」和「它的表示」分离，一步步装配
解决什么构造函数参数太多、参数之间有约束、可选参数组合爆炸
典型形态链式调用 Xxx().A().B().Build()
与工厂的区别工厂一次调用出成品；建造者分多步装配，适合参数多且有校验
建造者四步：默认值 -> 链式赋值 -> 集中校验 -> 产出成品

一、它解决的具体痛点

假设要构造一个 HTTP 客户端：超时、重试、代理、TLS、连接池、Header、限流……用构造函数会变成这样：

// 反例： telescoping constructor，参数顺序极易搞错 NewClient(3*time.Second, 3, nil, tlsCfg, 100, hdrs, rate) // 建造者：只设关心的，其余走默认值 c, err := client.NewBuilder(). Timeout(3 * time.Second). Retry(3). MaxIdle(100). Build()

二、完整实现骨架

type Config struct { timeout time.Duration retry int maxIdle int baseURL string } type Builder struct { c Config err error // 累积错误，Build 时统一返回 } func NewBuilder() *Builder { return &Builder{c: Config{timeout: 5 * time.Second, retry: 1, maxIdle: 64}} } func (b *Builder) Timeout(d time.Duration) *Builder { if d <= 0 { b.err = errors.New("timeout must be positive") } b.c.timeout = d return b } func (b *Builder) Build() (*Config, error) { if b.err != nil { return nil, b.err } if b.c.baseURL == "" { return nil, errors.New("baseURL required") } cfg := b.c return &cfg, nil // 返回副本，避免后续修改影响已产出对象 }
三个关键细节

① 错误累积：链式调用无法在每一步返回 error，所以在 Builder 里存一个 err，Build 时统一返回；② 返回副本：Build 返回内部配置的拷贝，防止外部继续改；③ 默认值在 NewBuilder 里给，而不是零值，这样调用方只写差异项。

三、和其他创建型模式的边界

模式关注点什么时候选它
建造者分步骤构造 + 参数校验可选参数多、有约束关系、需要校验
工厂方法由子类决定创建哪种产品产品类型在运行期才确定
抽象工厂创建一整族配套产品要成套替换（如整套 UI 组件）
原型通过克隆创建对象构造成本高且新对象和旧对象差别小
可选参数 / 变长选项函数式选项 Options PatternGo 里更地道的写法：WithTimeout(d) 作为可变参数

Go 社区其实更常用 Functional Options：NewClient(WithTimeout(d), WithRetry(3))，它比 Builder 更短，但缺点是不好做「跨参数的联合校验」和「分步构造」。参数之间有依赖（比如填了 TLS 就必须填 CA 路径）时，Builder 更稳。

HTTP / RPC 客户端超时、重试、拦截器、连接池

五、深入自检

Builder 线程安全吗？

通常不安全。Builder 是有状态的可变对象，应在单个 goroutine 内使用完毕后丢弃。产出后的 Config 如果不可变，则可以安全共享。

什么时候不值得用 Builder？

参数少于 4 个、且没有约束关系时，直接用构造函数或函数式选项更清爽。Builder 引入了额外类型和样板代码，简单场景是净负担。

为什么 Build 要做校验而不是在 Set 里？

Set 里只能校验单参数，Build 里能校验参数之间的关系：例如 retry > 0 时 timeout 必须 >= retry * 单次超时。这类跨字段约束只能在最终阶段检查。

建造者和「流式接口」是一回事吗？

不是。流式接口只是一种调用风格；建造者是「构造与表示分离」的思想。流式接口可以用于任何对象，建造者也可以不用链式调用。
