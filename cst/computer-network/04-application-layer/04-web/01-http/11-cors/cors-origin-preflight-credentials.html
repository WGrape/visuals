CORS、预检与凭据：浏览器为什么拦了已返回 200 的接口

沿跨源页面调用 API 解释 Origin、OPTIONS、允许凭据与服务端真实授权。

先认清同源的三个部分

浏览器把协议、主机名和端口都相同的地址视作同源。`https://app.example.test` 与 `https://api.example.test` 主机不同；同一主机从 443 换到 8443 端口也不同源。页面中的 JavaScript 发跨源请求时，同源策略限制脚本读取响应；CORS 是服务器用响应头告诉浏览器哪些源可读。服务器收到请求并执行成功，浏览器仍可能因响应头不符合规则而拒绝把结果交给脚本，因此网络面板里看到 HTTP 200 不等于前端拿到了数据。

CORS 是浏览器执行的读取边界，不是网络防火墙，也不是服务端身份认证。命令行程序、移动 App 或恶意服务器可以直接请求 API，不受浏览器 CORS 检查。敏感操作必须在服务端验证用户身份和权限，不能靠“没有 Access-Control-Allow-Origin”保护接口。

路径图：一次跨源 API 调用

箭头表示本例中的处理次序；每个环节的状态都要分别验证，不能由前一环节成功推断后一环节成功。

一次简单跨源请求

页面从 `https://app.example.test` 向 `https://api.example.test/data` 发 GET，浏览器带 `Origin: https://app.example.test`。API 若允许它，可回 `Access-Control-Allow-Origin: https://app.example.test`，浏览器才向脚本暴露响应。若 API 回的是别的源或没回允许头，服务器可能仍完成处理，浏览器只阻止页面读结果。出错时要同时看请求是否发出、响应头和浏览器控制台。

若响应因请求 Origin 而变化，共享缓存要正确按 Origin 区分，避免将某个允许源的响应头缓存给另一个源。动态回显 Origin 也必须先对照允许列表，不能不经检查就反射任意来源。

什么时候先发 OPTIONS

某些方法、请求头或内容类型使跨源请求需要预检。浏览器先发 OPTIONS，带 `Access-Control-Request-Method` 和 `Access-Control-Request-Headers`，询问目标 API 是否允许后续真实请求。服务器返回允许方法、允许头、允许源等信息后，浏览器才发送实际业务请求。预检通过不等于业务一定成功，真实请求仍可能因认证、参数或后端故障失败。

不是所有跨源请求都预检，也不是“POST 必然先发 OPTIONS”。例如请求是否属于简单请求还涉及方法、头和 Content-Type 等条件。预检缓存可由 Access-Control-Max-Age 控制，但浏览器可能有上限；修改 CORS 配置后，旧预检结果可能暂时继续影响客户端。

凭据与 Cookie

若跨源请求需要浏览器带 Cookie，前端需使用相应 credentials 选项，服务器要回 `Access-Control-Allow-Credentials: true`，并且允许源必须是明确的源，不能用 `*`。Cookie 自身还受 Domain、SameSite 和 Secure 限制：CORS 头允许读响应，不会替浏览器突破 Cookie 的发送规则。把 CORS 配对正确但 Cookie 不到服务端，应继续检查这些属性。

浏览器发送跨源请求可能带凭据，但服务器仍必须校验会话与 CSRF 防护。允许某个源读取响应也不等于授权该源的所有用户做所有操作；Origin 是页面来源，不是用户身份。

常见错误拆解

预检返回 404，通常是网关或服务端未处理 OPTIONS；预检响应漏 `Access-Control-Allow-Headers`，自定义头的真实请求不会发出；真实响应漏允许源，则实际业务可能已执行但前端读不到。重定向、代理缓存和错误页也可能把正确 CORS 头丢掉。不能只给成功 200 配头，401、403、500 等错误响应也要让允许的前端能读取足够诊断信息。

把 `Access-Control-Allow-Origin: *` 加到所有接口似乎省事，却会扩大跨源可读范围，且带凭据场景不成立。应按 API 用途维护允许来源列表，并测试不允许来源确实无法让浏览器脚本读取。

安全测试与验收

从允许源和不允许源各发 GET、带自定义头的 POST、带凭据请求，记录是否有 OPTIONS、实际请求是否发出、响应是否可被 JavaScript 读取。再用命令行直接调用同一 API，确认服务端认证授权不会因绕过浏览器而失效。对有副作用的接口，核查跨站诱导请求是否仍受 CSRF 和业务授权限制。

若前端报 CORS 错误，先定位失败发生在预检还是实际响应，再查 Origin、允许头、Cookie 属性与代理转发。把所有失败都归因于“后端没开跨域”会漏掉 TLS、网络、认证或网关错误。

简单请求 vs 预检的判定

同时满足以下三条才是简单请求（不触发预检），任意一条不满足就要先发 OPTIONS 预检：

  • 方法是 GET / HEAD / POST 之一
  • 除浏览器自动加的头外，只含 CORS 安全列表头：Accept、Accept-Language、Content-Language、Content-Type、Range 等
  • Content-Type 只能是 application/x-www-form-urlencoded、multipart/form-data、text/plain 之一

所以 Content-Type: application/json、带 Authorization 头、用 PUT/DELETE、带自定义头（如 X-Request-Id）——全部会触发预检。这是很多“为什么多了一次请求”的答案。

响应头作用注意
Access-Control-Allow-Origin允许的源带凭证时不能为 *，必须回具体源
Access-Control-Allow-Methods预检响应：允许的方法逗号分隔，如 GET, POST, PUT
Access-Control-Allow-Headers预检响应：允许的请求头客户端自定义头必须列在这里
Access-Control-Allow-Credentials允许带 cookie/凭证true；此时 Allow-Origin 不能是 *
Access-Control-Max-Age预检结果缓存秒数浏览器上限不同（Chrome 600 s，Firefox 86400 s）
Access-Control-Expose-Headers允许 JS 读取的响应头默认只能读 Cache-Control、Content-Language、Content-Type、Expires、Last-Modified、Pragma

CORS 验证命令

# 模拟简单请求
curl -i -H 'Origin: https://a.com' https://api.example.com/data
# access-control-allow-origin: *

# 模拟预检（触发条件：PUT + application/json + 自定义头）
curl -i -X OPTIONS https://api.example.com/data \
  -H 'Origin: https://a.com' \
  -H 'Access-Control-Request-Method: PUT' \
  -H 'Access-Control-Request-Headers: content-type,x-request-id'
# 期望响应：
# access-control-allow-origin: https://a.com
# access-control-allow-methods: GET, POST, PUT, DELETE
# access-control-allow-headers: content-type,x-request-id
# access-control-max-age: 600

# 带凭证（前端 fetch 需 credentials: 'include'）
curl -i -H 'Origin: https://a.com' -H 'Cookie: s=1' https://api.example.com/me

Nginx 配置与高频坑

Nginx CORS 配置

# Nginx 标准 CORS 配置（注意必须回显具体 Origin）
map $http_origin $cors_origin {
    default "";
    "~^https://(a\.com|b\.com)$" $http_origin;
}
server {
    location /api/ {
        add_header Access-Control-Allow-Origin $cors_origin always;
        add_header Access-Control-Allow-Methods 'GET, POST, PUT, DELETE, OPTIONS' always;
        add_header Access-Control-Allow-Headers 'Content-Type, Authorization, X-Request-Id' always;
        add_header Access-Control-Allow-Credentials 'true' always;
        add_header Access-Control-Max-Age 600 always;
        # 关键：预检直接返回 204，不要打到后端
        if ($request_method = OPTIONS) { return 204; }
        proxy_pass http://backend;
    }
}
  • 最常见错误 1：Access-Control-Allow-Origin: * 与 Allow-Credentials: true 同时出现 → 浏览器直接拒绝。带凭证必须回具体源。
  • 最常见错误 2：只在业务响应里加 CORS 头，OPTIONS 请求被后端当作普通请求处理（返回 404/405 或未带 CORS 头）→ 预检失败，真正的请求根本不会发。
  • 最常见错误 3：add_header 不加 always，Nginx 只对 200/204/301/302/304 生效，4xx/5xx 响应没有 CORS 头 → 前端看不到错误详情，只报笼统的 CORS error。
  • 跨域 cookie 还需要 SameSite=None; Secure：否则浏览器根本不会在跨站请求里带 cookie。
  • 预检的性能代价：每个非简单请求多一次 RTT。用 Access-Control-Max-Age 缓存；或改用简单请求（如用 text/plain 传 JSON 字符串，但可读性差）；或让前端与 API 同域（反向代理到同一域名下）。
  • CORS 不是安全边界：它只约束浏览器。服务端仍必须对请求做鉴权——攻击者用 curl 可以完全绕过 CORS。
为什么控制台报 CORS error 但 Network 里看到了 200？

响应到达了浏览器，但缺少/不匹配 CORS 响应头，浏览器拦截了结果并不交给 JS。要看具体原因，检查响应头里的 Access-Control-Allow-* 是否齐全、Origin 是否匹配。

后端没收到请求，只有 OPTIONS 记录，为什么？

预检 OPTIONS 没通过（没返回 204 + 正确的 CORS 头），所以浏览器没有发出真正的请求。在网关层直接处理 OPTIONS 即可。

自检

浏览器报 CORS 错误，是否证明服务器完全没有处理业务请求？

不一定。失败可能发生在实际响应的读取检查阶段，服务器已经执行；需看预检与真实请求是否分别发出。
