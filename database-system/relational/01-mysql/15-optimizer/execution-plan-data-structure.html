执行计划的数据结构：它是一棵什么样的树

从 JOIN + QEP_TAB 数组到 AccessPath 树，再到 RowIterator 迭代器树 —— 把一个执行计划"拆开"看清楚每个字段装的是什么

① 先给结论 ② 三层结构总览 ③ 老表示：QEP_TAB 数组 ④ 新表示：AccessPath 树 ⑤ 一棵真实的计划树 ⑥ 计划树 → 迭代器树 ⑦ EXPLAIN 三种输出 ⑧ optimizer_trace ⑨ 一节点里装了什么 ⑩ 误区
①先给结论

执行计划（Query Execution Plan）就是"数据库打算怎么把这张表、这个 JOIN、这个排序跑出来"的一棵物理算子树。它不是 SQL 文本，也不是 AST —— AST 说的是"你要什么"，执行计划说的是"我打算怎么干"。

在 MySQL 里，这棵树的具体"容器"经历过一次换代（已核实，勿改）：

版本承载结构形状能表达的计划
MySQL 8.0.22 之前JOIN 对象 + QEP_TAB 数组本质是一维数组（线性表）只能表达左深树（left-deep）
MySQL 8.0.22 起AccessPath 树真正的树（节点带 child / outer / inner 指针）可表达bushy（丛生）计划，配合 Hypergraph 优化器

而真正跑起来时，还要再变一次：AccessPath 树由 CreateIteratorFromAccessPath() 转换成一棵 RowIterator 树，执行器对它做 Init() / Read() 的火山模型调用。

一句话记忆 QEP_TAB 是"排好队的一张表清单"，AccessPath 是"真正的一棵树"，RowIterator 是"能跑起来的那棵树"。三者的信息量基本一致，只是形状与用途不同。
②三层结构总览：别把三种"计划"混为一谈

很多人说"执行计划"时其实混了三样东西。先把它们分开，后面才不会乱：

三层："说什么" → "怎么干" → "跑起来"

③老表示：JOIN + QEP_TAB 数组（8.0.22 之前）

老版本里，每一个 Query_block（一个 SELECT 块）在优化时都被当成一个 JOIN 对象处理 —— 因为在 MySQL 眼里"一切查询都是 join"，单表查询就是只有一张表的 join。JOIN::optimize() 是优化的统一入口。

const_tablesuint其中有几张是常量表（能提前用主键/唯一键算出唯一值，先算掉）

best_positionsPOSITION*搜索过程中，每个"位置"选中的最优访问方式（含代价、行数、扇出）

JOIN_TAB / QEP_TAB / QEP_shared：三者什么关系

这是最容易绕晕的地方。它们不是三个并列的东西，而是"公共部分被抽出来复用"：

JOIN_TAB 管"选"，QEP_TAB 管"干"；公共的 QEP_shared 被两者共享

为什么老结构"只能表达左深树"

因为 qep_tab 是一维数组：第 0 项是驱动表，第 1 项 join 第二张，第 2 项再 join 第三张…… 每一步的"外侧"永远是前面所有步的结果，内侧永远是一张基表。这种形状就是左深树。

数组天然只能表达左深树；要表达 bushy 就必须有真正的树节点

④新表示：AccessPath 树（MySQL 8.0.22 起）

AccessPath 定义在 sql/join_optimizer/access_path.h。它是一个典型的"一个结构体 + 一个 union + 一个类型枚举"设计：所有算子共用同一份外壳，具体参数按 type 去解释 union 里对应的那一段。

一个 AccessPath 节点 = 算子类型 + 代价基数 + 谓词/有序性 + 子节点 + 专有参数

AccessPath::Type 按"几目运算"分类更好记

分类代表枚举值装的参数（union 段）
叶子：怎么把数据取出来TABLE_SCAN、INDEX_SCAN、REF、EQ_REF、INDEX_RANGE_SCAN、INDEX_MERGE、INDEX_SKIP_SCAN、MRR、CONST_TABLE、FULL_TEXT_SEARCH哪张表、哪个索引、是否反序、是否覆盖索引、range 方案
单目：对上游结果再加工FILTER、SORT、AGGREGATE、TEMPTABLE_AGGREGATE、LIMIT_OFFSET、WINDOW、MATERIALIZE、STREAM、REMOVE_DUPLICATES_ON_INDEXchild 指针 + 该动作的参数（排序键、分组项、limit/offset、临时表参数）
双目：把两个结果合起来NESTED_LOOP_JOIN、HASH_JOIN、BKA_JOIN、WEEDOUT、NESTED_LOOP_SEMIJOIN_WITH_DUPLICATE_REMOVALouter / inner 两个子指针 + join 条件 + join 类型
特殊收尾ZERO_ROWS、ZERO_ROWS_AGGREGATED、FAKE_SINGLE_ROW、ALTERNATIVE、DELETE_ROWS、UPDATE_ROWS空结果 / 常量结果 / 候选方案容器 / DML 目标表
为什么要这么设计（一个结构体 + union） 因为优化器要在极短时间内造出、比较、丢弃成千上万个候选计划。用同一个结构体承载所有算子，配合 union，可以：① 统一用指针串成树，不用为每种算子建 C++ 类做虚函数分发；② 遍历/拷贝/估算代价的代码可以写成通用的 walk_access_paths；③ 内存上更紧凑。代价是"类型不安全"——必须严格按 type 访问对应的 union 段。
⑤一棵真实的计划树长什么样

用一条普通的两表 JOIN + 过滤 + 排序 + 分页查，看它在 EXPLAIN FORMAT=TREE 下的样子 —— 这个输出几乎就是 AccessPath 树的原文（缩进 = 父子关系，括号里 = 代价与行数）：

EXPLAIN FORMAT=TREE
SELECT o.id, c.name
FROM   orders o
JOIN   customer c ON o.cid = c.id
WHERE  c.city = 'BJ'
ORDER  BY o.amount DESC
LIMIT  10\G

*************************** 1. row ***************************
EXPLAIN:
-> Limit: 10 row(s)  (cost=1250.75 rows=10)
    -> Sort: o.amount DESC, limit input to 10 row(s) per chunk  (cost=1250.75 rows=980)
        -> Nested loop inner join  (cost=1152.60 rows=980)
            -> Filter: (c.city = 'BJ')  (cost=102.25 rows=98)
                -> Table scan on c  (cost=102.25 rows=980)
            -> Index lookup on o using cid (cid = c.id)  (cost=9.52 rows=10)

树的形状：叶子取数 → 双目 JOIN 合起来 → 单目排序 → 单目截断

读树的顺序 自底向上看（数据流动方向）：下面两个叶子先取数 → JOIN 把它们拼起来 → Sort 排序 → Limit 截断。
自顶向下看（调用方向）：执行器先 Init() 根节点的 Limit，它递归初始化子节点，然后反复 Read() 根节点，每次 Read 会向下要一行、再向上返回一行。
⑥计划树 → 能跑的迭代器树

AccessPath 只是"图纸"，它自己不会取数。执行前由 CreateIteratorFromAccessPath() 把每个节点翻译成一个 RowIterator 对象（定义在 sql/iterators/）。

AccessPath::Type对应的 RowIterator干的事
TABLE_SCANTableScanIterator顺序扫全表
INDEX_SCANIndexScanIterator沿索引顺序扫
INDEX_RANGE_SCANIndexRangeScanIterator索引范围扫描
REF / EQ_REFRefIterator 等用索引等值查找
NESTED_LOOP_JOINNestedLoopIterator外层一行、内层查一次
HASH_JOINHashJoinIteratorbuild 哈希表 + probe
FILTERFilterIterator对上游每行套 WHERE
SORTSortingIteratorfilesort 排序
AGGREGATEAggregateIteratorGROUP BY 分组聚合
LIMIT_OFFSETLimitOffsetIteratorLIMIT / OFFSET 截断
MATERIALIZEMaterializeIterator把子树结果落到临时表

RowIterator 的接口只有四个关键方法

class RowIterator {
  // 初始化：打开表、分配 buffer、准备 join/排序状态。返回 true 表示出错
  bool Init();

  // 取下一行：0 = 取到一行；-1 = 没有更多行（EOF）；1 = 出错
  int  Read();

  // 外连接时把当前行标记为 NULL 扩展行
  void SetNullRowFlag(bool is_null_row);

  // 释放行锁（SKIP LOCKED 等场景）
  void UnlockRow();
};

形状一一对应，只是从"描述"变成了"可执行对象"

⑦EXPLAIN 的三种输出分别对应什么

同一棵树，EXPLAIN 能给你三种"视图"。搞清楚对应关系，你就知道该看哪个：

输出看到的是适合干什么
普通 EXPLAIN（表格）把计划线性化成一张表：一行 = 一个"表访问步骤"（id / select_type / table / type / possible_keys / key / key_len / ref / rows / filtered / Extra）。注意：它丢失了树的缩进关系，多表时靠 id 与顺序推断快速看每张表用什么索引、扫描多少行
FORMAT=TREEAccessPath 树的原文：缩进即父子，每个节点带 (cost=… rows=…)看"树形结构"最准——本文讲的这棵树，就长这个样
FORMAT=JSON树 + 更细的代价信息（cost_info：query_cost、每步 prefix_cost / read_cost / eval_cost）、used_columns、attached_condition 等要看代价构成、被下推的条件细节
EXPLAIN ANALYZE（8.0.18+）真执行一遍，并给出每个节点的实际耗时与实际行数（actual time=… rows=… loops=…）对比"估的行数"和"真的行数"，定位统计信息失真
最容易踩的坑 很多人只看普通 EXPLAIN 的 rows 列，就以为看懂了计划。其实 rows 是单个步骤的预估扫描行数，不是最终返回行数；真正的总代价要看 FORMAT=JSON 里的 query_cost，或 FORMAT=TREE 根节点的 cost。
⑧optimizer_trace：看"计划是怎么被挑出来的"

执行计划只是最终答案。optimizer_trace 能看到搜索过程——也就是那一大堆被淘汰的 POSITION / AccessPath 候选：

SET optimizer_trace = 'enabled=on';
SELECT ...;                       -- 跑你的查询
SELECT * FROM information_schema.OPTIMIZER_TRACE\G
SET optimizer_trace = 'enabled=off';
trace 阶段对应结构里的什么
join_preparationQuery_block 的逻辑改写（外转内、等值推导等）
rows_estimation每张表的行数/代价估算，含 range_analysis：table_scan 的 rows/cost、potential_range_indexes、best_covering_index_scan
considered_execution_plans核心：逐个候选 join 顺序/访问方式的代价对比，就是 POSITION / AccessPath 候选集的比拼现场
attaching_conditions_to_tables谓词下推：哪些条件最终挂到 QEP_TAB::condition() / filter_predicates
finalizing_query / join_execution收尾（排序、临时表）与执行阶段
EXPLAIN 与 optimizer_trace 的分工 EXPLAIN 回答 what（最后选了哪个计划）；optimizer_trace 回答 why（为什么是它，其他方案各多少钱）。
⑨总结：一个计划节点里到底装了什么

把上面所有内容收拢，任意一个执行计划节点（QEP_TAB 或 AccessPath）都必然包含这五类信息：

① 我是谁

算子类型：type（TABLE_SCAN / REF / HASH_JOIN / SORT …）或 join_type（JT_ALL / JT_REF …）

② 我作用于谁

目标表 / 子计划：叶子是 TABLE* + 索引，非叶子是 child 或 outer / inner 指针

③ 我怎么取数

专有参数（union 段）：索引号、key_len、是否覆盖、range 方案、排序键、分组项、临时表参数…

④ 我顺手过滤什么

condition() / filter_predicates：被下推到我这层的谓词

⑤ 我有多贵

cost / init_cost / num_output_rows（或 POSITION 里的代价与扇出）—— 优化器靠它做取舍

整棵树再加上顺序语义：叶子在下、结果在上；执行时自顶 Init()、自顶 Read() 向下拉取、数据自底向上流动。这就是执行计划数据结构的全部骨架。

⑩常见误区
"执行计划是一棵二叉树"
不一定。它是一棵算子树的通用形态：叶子（取表）、单目（Filter/Sort/Aggregate/Limit）、双目（Join/Weedout）混合。而且老结构（QEP_TAB 数组）压根不是树，是一条左深链。只有 8.0.22+ 的 AccessPath 才是真正的树，且能表达 bushy 形状。
"EXPLAIN 的 rows 就是最终返回行数"
不是。它是该步骤的预估扫描行数（检查行数），不是输出行数，更不是最终结果行数。真正的输出行数看 AccessPath 的 num_output_rows；想看真实值用 EXPLAIN ANALYZE 的 actual rows。
"AccessPath 和 QEP_TAB 是完全不同的两套东西"
是演进关系，不是并列关系。8.0 后期 QEP_TAB 依然存在于传统优化器路径中，并且专门提供了 QEP_TAB::access_path() 方法，把"这张表定下来的访问方式"包装成一个 AccessPath，供统一的迭代器创建流程使用。可以理解为：传统优化器产出线性计划，再挂到 AccessPath 这层统一外壳上执行。
"计划树节点里存了真实数据行"
不存。节点只存元数据（算子、索引、谓词、代价、子节点指针）。真实数据行只在执行时由 RowIterator::Read() 一行一行产出、向上传递。唯一"存数据"的例外是 MATERIALIZE 类算子在运行时把结果落到临时表。
