FTP 主动与被动模式：为什么登录成功却列不出文件

用两条 TCP 连接解释 PORT、PASV、防火墙入站和 SFTP/FTPS 区别。

FTP 把控制和数据分开

传统 FTP 客户端先连接服务器的控制端口，登录、切换目录、发 LIST 或 RETR 等命令；传输目录列表和文件时另建数据连接。于是“控制连接登录成功”只证明一条路径通，数据连接可能因 NAT 或防火墙失败。这个设计与普通 HTTP 下载的一次请求/响应模型不同，排障要记录控制连接和数据连接各自的源、目的 IP/端口。

FTP 明文用户名、密码与内容不适合直接在不可信网络使用。现代场景可使用 FTPS（在 FTP 上加 TLS）或 SFTP（SSH 文件传输协议），二者不是同一种协议，也不是简单换一个端口就互通。生产选型应优先满足传输加密、身份验证与审计要求。

主动模式怎样建数据连接

客户端向服务器控制连接发送 PORT 命令，告诉服务器“请连接我声明的客户端地址与端口”。服务器随后主动连接客户端的该端口传数据。若客户端在家用 NAT 后面，PORT 报文里的内网地址不能被服务器直接访问；客户端防火墙也常默认拒绝外来连接，所以控制连接正常而目录列表挂住。某些 FTP ALG 尝试读取控制命令并改写地址/开口，但若控制通道加密，ALG 未必能看见内容。

主动模式并不意味着客户端没有先主动连接服务器：控制连接仍由客户端发起，区别在数据连接由服务器主动连向客户端。考试题常把“谁主动”说得含混，应明确是哪一条连接。

逐步推演

控制连接

客户端连接服务器并完成登录。

选择模式

主动 PORT 或被动 PASV 协商数据端点。

建立数据连接

主动模式由服务器连客户端，被动由客户端连服务器。

验证传输

LIST、RETR、STOR 分别测试。

被动模式怎样建数据连接

客户端发 PASV，服务器返回一个可供客户端连接的数据地址和端口；客户端再主动连接这个服务器数据端口。因为控制和数据连接都由客户端发起，被动模式通常更适合客户端在 NAT 后的情况。但服务器需要允许相应被动端口范围入站，并正确向外公布地址；若它错误地在 PASV 回复里给出 10.0.0.5 等内网地址，公网客户端仍无法连接。

服务器在反向代理、NAT 或容器后面时，被动端口范围和公网映射要一致。EPSV 等扩展可避免某些地址嵌入问题，并适应 IPv6 等环境。若 FTPS 加密控制连接，中间 NAT ALG 可能无法修正旧式 PASV 回复，因此应在服务器本身配置正确的对外地址和端口范围。

一次失败时间线

用户能输入用户名密码成功，发 LIST 后客户端等待。抓包显示控制连接到 21 通，服务器 PASV 回了 192.168.10.8:50042；客户端在公网不能到达这个私有地址。修复应让服务器公布可达的外部地址，并在网关映射 50042 所属被动端口范围。若 PASV 地址正确但 SYN 无回应，查服务器和边界防火墙；若 TCP 连通但文件传到一半断，查超时、MTU 和服务器存储。

不要只因“FTP 登录成功”就宣布服务健康。LIST、下载 RETR、上传 STOR 可能分别涉及权限、数据端口和磁盘路径，应逐项测试。

FTPS 与 SFTP 不是同义词

FTPS 仍遵循 FTP 的控制/数据连接体系，只是增加 TLS 保护；显式 FTPS 通常在传统控制端口上协商 TLS，隐式模式有不同端口约定。SFTP 则运行在 SSH 连接之上，用自己的消息协议传文件，常复用一条加密连接，不使用 FTP 的 PORT/PASV 机制。把 SFTP 服务端用普通 FTP 客户端配置为“启用 SSL”，往往不会成功。

选型时检查客户端兼容、用户认证、密钥管理、防火墙开放端口及审计。多数新系统如果没有兼容传统 FTP 的要求，使用 SFTP 或 HTTPS 上传下载通常更容易通过现代网络边界。

验收与安全边界

分别从同网段、公网 NAT 后与企业代理环境测试主动/被动模式，记录控制和数据连接端口。服务端限制被动端口范围，只开放必要地址段，防止把大量高端口长期暴露。验证目录隔离、上传大小、恶意文件扫描和账户最小权限。故障复盘时画出两条 TCP 连接，比只贴一个“连接超时”截图更能定位问题。

若业务只需用户下载公开文件，HTTP Range 和 CDN 可能比 FTP 更合适；若需要安全批量文件交换，先确认 SFTP 与 FTPS 的真实协议需求，再部署。

自检

FTP 控制连接登录成功，能证明数据连接一定可用吗？

不能。数据连接另行建立，NAT、防火墙和被动端口配置可能让 LIST/RETR 失败。
