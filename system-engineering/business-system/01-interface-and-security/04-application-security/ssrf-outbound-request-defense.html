SSRF 防线：外部 URL 抓取与出站边界

“根据用户提供的图片 URL 生成缩略图”为什么可能让服务端访问内部地址？从输入到真正建立连接逐层设防。

SSRF 利用的是服务端比用户更大的网络权限

图片抓取服务接收一个 URL，代替用户发起请求。即使前端不能直接访问内部管理 API、数据库或云实例元数据，服务端所在网络可能可以。仅仅检查字符串里“没有 localhost”远远不够：目标可能是域名、IPv6、重定向后的地址，DNS 结果还可能在校验与连接之间改变。威胁边界是“不可信目标地址”进入“有内网访问权的出站客户端”。

最稳妥的业务方案通常是只允许由服务端预先批准的目的域名与 HTTPS 协议；若确实必须抓取任意公开图片，要结合规范化解析、最终连接 IP 校验、出站网络隔离与严格的客户端限制，而不是依赖单个正则。

图解：在 URL、DNS、连接和网络四处守边界

要防 DNS 重绑定，不能只在“预检查”解析一次，随后让 HTTP 客户端重新解析并连接不同 IP。客户端必须保证它连接的实际地址也经过策略验证，或通过受控出站代理固定访问路径。

逐步推演：缩略图服务如何安全抓取

根据业务允许列表解析

用标准 URL 解析器规范化 scheme、主机、端口；只允许 HTTPS 与事先批准的目标域，拒绝嵌入凭证、非预期端口或非 HTTP 协议。字符串包含判断不等于精确域名匹配。

检查所有解析地址

核对 A/AAAA 结果与网络策略，拒绝本机、私有、链路本地、保留及云元数据访问范围（按环境维护规则）；重定向后的每个新 URL 都重新开始验证，不允许隐式跨信任域。

实际连接目的也受控

使用能控制解析与实际目标一致性的出站客户端或专用代理；系统级出站策略防止工作负载访问内部控制面/元数据服务。只在应用层验证一次、随后由底层库自由重解析是不完整的。

限制成本与数据暴露

设置连接与总超时、响应字节上限、重定向跳数及允许的 MIME 类型。错误和日志可记录规范化目的域与追踪 ID，但不要回显内部网络细节或完整凭证。

第一层 · 不同防线的职责

防线能防什么不能单独解决什么
目标允许列表缩小业务可访问的域、端口、协议允许域指向内部地址或重定向后的目标
解析与 IP 判定识别本机、私有、链路本地及不允许的目的地客户端后续重解析、连接与检查结果不一致
受控 HTTP 客户端/代理绑定目标、复检跳转、限制时长与数据量主机/容器天然可连整个内网
出站网络隔离即使应用漏检，仍阻止访问内网控制面业务层面只该抓取特定公开域名的要求

第二层 · 出站策略示意

// 教学伪代码：真实实现需使用可约束实际连接地址的客户端
url = parseAndCanonicalize(userSuppliedUrl)
requireHttpsAndAllowedHostPort(url)
for each requestTarget including redirects:
    requireHttpsAndAllowedHostPort(requestTarget)
    addresses = resolveAllAAndAAAA(requestTarget.host)
    requireEveryAddressAllowed(addresses, deploymentEgressPolicy)
    response = fetchWithVerifiedDestination(requestTarget, addresses,
                                             timeout, maxBytes, maxRedirects)
requireAllowedContentType(response)

“解析全部地址后都允许”只是安全策略的一层；仍应保证实际连接使用核对过的目标，处理代理/HTTP 客户端行为，并配置独立的网络出口限制。若采用专用抓取工作负载，将它与数据库凭证、管理 API 和元数据访问权限隔离，比让业务主服务任意连外网更容易收敛风险。

第三层 · 常见旁路与排障

  • DNS 重绑定或地址变换：预检与连接之间目标改变，或 IPv4/IPv6/映射地址的判定不一致；检查日志中解析值与实际远端地址是否一致。
  • HTTP 重定向：第一跳是允许域，下一跳却指向内部服务；禁用自动重定向，或每跳按同一规则重新判定并限制跳数。
  • 云元数据与服务网格：应用认为目标不是数据库，但工作负载仍可能读到控制面/元数据端点；以网络策略和身份权限作为最后屏障。
  • 代理配置：环境变量代理或透明代理可能改变 DNS 与连接位置；把代理行为纳入实际部署边界评估，不能只看本机解析结果。

第四层 · 原理与取舍

只禁止 localhost 与 127.0.0.1 就安全了吗？

不安全。还有私网、链路本地、IPv6、云元数据、域名解析变化及重定向等路径。业务允许列表与出站隔离通常比维护几个禁止字符串更可靠。

请求 URL 看起来是 https://trusted.example，为什么还要验证 IP？

域名不是固定地址，解析或跳转可能指向不该访问的网络段；必须检查最终实际连接目标，并让网络出口策略承担最后一道防线。

如果要支持用户提交任意公开图片网址怎么办？

这比固定允许列表难。应使用专用低权限抓取服务、严格的协议/目标判定、受控出站代理、响应资源上限和错误隔离，并明确哪些目的地永远不可达。

自检

初始 URL 通过了允许列表，但返回 302 指向内部地址，是否能跟随？

不能无条件跟随。每个跳转目标都要重新做协议、域名、解析地址与实际连接判定；更简单的策略是直接关闭自动跳转。
