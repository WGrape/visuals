一句话总结：调用约定是编译器和被调用方之间的"君子协议"——约定参数放哪、谁清栈、返回值怎么回、寄存器谁来保存。错一处，跨函数/跨语言调用就会崩。

01为什么需要调用约定

函数调用时，调用方和被调用方必须就"参数放哪里、结果怎么返回、栈由谁清理"达成一致，否则读取错位。这份约定就是 ABI（Application Binary Interface）的一部分，与语言/平台/编译器强相关。

02栈帧布局

一次函数调用会在栈上压出一个栈帧，通常包含：

  • 返回地址：函数执行完回到调用方的哪条指令。
  • 参数：调用方压入（或寄存器传入后溢出到栈）。
  • 保存的寄存器 / 旧帧指针：被调用方要保存调用方现场。
  • 局部变量：本函数声明的变量。
每个栈帧携带返回地址，构成调用链回溯的基础

03参数传递：栈传参 vs 寄存器传参

约定参数放哪谁清栈特点
cdecl从右到左压栈调用方支持变长参数（printf），但调用方清栈略慢
stdcall从右到左压栈被调用方代码更小，不支持变长参数（Win32 API）
fastcall / 现代 ABI前几个寄存器传，其余压栈约定一致减少栈访问，更快（System V AMD64 / Windows x64）

04寄存器保存约定

  • 调用者保存（caller-saved）：被调用方可以随意破坏，调用方若需要就在调用前自己存好。
  • 被调用者保存（callee-saved）：被调用方若要用，必须先保存到栈、返回前恢复，保证调用方看到的值不变。

这套分工让"频繁调用的小函数"不必每次都保存所有寄存器，减少无谓的压栈。

05实际影响

🔗 跨语言互调

C++ 导出的符号名会被改编（name mangling），要用 extern "C" 固定成 C 约定才能被其它语言按 cdecl 调用。

📉 栈溢出

递归过深或大局部变量（大数组）撑爆栈；栈通常比堆小得多。

📏 对齐

ABI 规定参数/结构的对齐与填充，影响大小与访问正确性（见对象布局）。

06常见疑问

为什么 cdecl 允许变长参数而 stdcall 不行？
因为变长参数（如 printf）只能在运行时由调用方知道数量，必须由调用方负责清栈；stdcall 由被调用方清栈，它事先不知道参数个数，无法正确清理。
现在主流为什么用寄存器传参？
寄存器访问比内存快几个数量级。现代 ABI（System V AMD64、Windows x64、ARM AAPCS）都把前几个整数/浮点参数放寄存器，只有超出部分才溢出到栈，大幅减少栈读写。
调用约定和"值传递/引用传递"是一回事吗？
不是。值/引用是语言层面的语义（拷贝还是传地址）；调用约定是二进制层面"这个地址或这个值到底放寄存器还是栈、谁清栈"。引用传递在 ABI 上通常就是传一个指针（一个寄存器或栈槽）。

关键事实速查

平台 ABI前 N 个整型参数浮点
System V AMD64 (Linux)6 个放 RDI/RSI/RDX/RCX/R8/R9前 8 个放 XMM0-7
Windows x644 个放 RCX/RDX/R8/R9前 4 个放 XMM0-3
ARM AAPCS前 4 个放 R0-R3前 8 个放 S0-S7/D0-D7
为什么了解 ABI 对排查问题有用？

崩溃栈回溯、core dump 分析、跨语言（FFI）调用、甚至某些安全漏洞（栈溢出、ROP）都建立在栈帧与调用约定之上。知道返回地址在栈帧什么位置、callee-saved 寄存器为何值会"神秘恢复"，能让你在汇编级排障时不再盲人摸象。

深度补充：调用约定与栈帧 ABI 参数

第一层 · 概念与判定 调用约定规定“参数怎么传、栈谁清理、返回值放哪”，ABI 是二进制的互操作契约。判定：跨语言调用（FFI/cgo）、崩溃栈回溯、汇编调试时都必须对照 ABI。

平台 / 约定前 N 个参数栈清理返回值
System V AMD64RDI RSI RDX RCX R8 R9调用方RAX
Windows x64RCX RDX R8 R9被调方RAX
ARM64 AAPCSX0-X7被调方X0
cdecl（32位）全部入栈调用方EAX

第三层 · 排障与边界

  • 调用约定不匹配导致参数错位、栈破坏——FFI 必须显式声明。
  • 栈帧缺帧指针（FPO/-fomit-frame-pointer）会让回溯工具拿不到栈。
  • 可变参数函数依赖约定布局，手写汇编极易错。
  • ABI 版本不一致（如 glibc 符号版本）造成运行时符号找不到。
第四层 · 原理与取舍

用寄存器传参减少访存、提升速度，代价是调用方与被调方对寄存器分工达成强约束（即 ABI）；栈清理归调用方还是被调方，决定变长参数与可变栈帧的实现复杂度。权衡是“性能（寄存器）vs 灵活（栈）”。崩溃分析时栈帧与返回地址链就是按这套约定还原的，所以 ABI 是调试与安全的地基。

实例与速查：调用约定速查

# 查看一个函数调用在 x86-64 上的反汇编（System V）
objdump -d ./a.out | grep -A12 '<main>'
# 参数依次进入 rdi, rsi, rdx, rcx, r8, r9；返回值放 rax
# Windows x64 改为 rcx, rdx, r8, r9，且由被调方清理栈

# cgo 必须显式声明约定，否则参数错位
/*
#include <stdint.h>
uint64_t add(uint64_t a, uint64_t b);   // 默认 cdecl 风格由编译器安排
*/
  • 跨语言调用（cgo/FFI）必须显式声明调用约定，否则参数错位。
  • 崩溃栈回溯依赖帧指针，编译开 -fomit-frame-pointer 会让 gdb/perf 难回溯。
  • 可变参数函数布局严格依赖约定，手写汇编极易出错。
FAQ：为什么有时参数看起来“少了一个”？

常见原因是把结构体整体当一个参数（实际按 ABI 展开或传指针），或混用了不同约定的库。Windows x64 和 System V 的前 4 个寄存器顺序不同，跨平台调用务必查对应 ABI 文档，用 dump/调试器核对实际寄存器布局。

常见误区与延伸

  • 误区一：参数都进栈。现代 AMD64 前 6 个整型/前 8 个浮点参数走寄存器，只有溢出才入栈。
  • 误区二：栈由被调方清理更快。cdecl 由调用方清理，支持可变参数；stdcall 由被调方清理，调用点更短。
  • 延伸：可变参数函数（如 printf）依赖约定布局与栈上取参，手写汇编极易错，尽量用编译器生成的胶水。
  • 延伸：ABI 还涵盖结构体内存对齐、异常展开（unwind）表，这些在崩溃回溯与 C++ 异常中缺一不可。

一句话总结：调用约定与 ABI 是二进制互操作的契约，跨语言调用务必显式声明并对照平台文档，是调试与安全的地基。

决策速记

  • 跨语言调用：显式声明调用约定，否则参数错位。
  • 调试友好：保留帧指针（-fno-omit-frame-pointer）便于回溯。
  • 平台差异：AMD64 与 Windows x64 寄存器顺序不同，各查文档。
  • 别手写汇编：可变参数与寄存器布局极易错，用编译器胶水。

横向对比与追问

  • 与 ARM64 比：AAPCS 用 X0-X7 传参，AMD64 System V 用 RDI 起，寄存器数量与顺序都不同。
  • 与 Windows x64 比：前者调用方清栈，后者被调方清栈，影响可变参数与栈帧设计。
  • 追问：为什么浮点参数单独占 X0-X7/V0-V7？因为 ARM 把通用与向量寄存器分开编址。
  • 追问：32 位 cdecl 为何全入栈？当年寄存器少，统一入栈最简单且兼容变参。

小结：跨平台调用前先查对应 ABI 文档，寄存器的分配是性能与约束的折中。

先记三件事

  • 第一件：调用约定规定参数怎么传、栈谁清，ABI 是二进制互操作契约。
  • 第二件：跨语言调用必须显式声明约定，否则参数错位。
  • 第三件：调试崩溃要保留帧指针，别开 -fomit-frame-pointer。

ABI 不兼容排障

  • 符号找不到或段错误：多因 C++ 未用 extern C 或混用不同编译器 ABI（libstdc++ 与 libc++），导出名与调用约定对不上。
  • 栈被破坏：调用约定不匹配（谁清栈）会导致返回值后栈指针错位，表现为随机崩溃。
  • 排查顺序：先确认同一工具链与运行时，再用 nm/objdump 看符号修饰，最后核对结构体对齐与位宽跨平台一致。
