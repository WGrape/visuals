TDengine 原理图解

「一个设备一张表」——国产时序数据库的极致压缩与写入设计

TDengine超级表 STable一个设备一张表列式压缩IoT
① 核心设计思想 ② 超级表模型 ③ 存储与压缩 ④ 集群架构 ⑤ SQL 与查询 ⑥ 对比与选型
一句话总结：TDengine 最有争议也最有效的设计是「一个数据采集点一张表」—— 每个设备/传感器单独建表。看似疯狂（百万设备就百万张表）， 但这样同一设备的数据物理上完全连续，压缩比和查询效率都达到极致。 配合「超级表 STable」做模板与聚合，解决了管理问题。

01核心思想：一个设备一张表

图 1：「一设备一表」带来的三个好处

💾 省掉冗余列

device_id 不需要在每行重复存储， 它在表名里。这对海量小点的数据节省非常可观。

🗜️ 时序压缩

同一设备的数据物理连续、值变化平滑， 有利于 Delta 等按类型编码；实际压缩比取决于采样规律、字段类型与数据变化，应使用真实数据测量。

⚡ 按设备定位

查某个设备的时间范围，直接定位到那张表， 可减少无关设备的数据扫描；与关系表分区或索引方案相比是否更快仍取决于查询和数据布局。

🔒 写入无锁竞争

不同设备写不同的表，天然无冲突， 并发写入吞吐随设备数线性扩展。

02超级表 STable：解决"表太多怎么管"

百万张表无法逐个管理。TDengine 引入 超级表（STable）作为模板： 定义表结构 + 标签（tags），子表继承结构并绑定具体标签值。

图 2：超级表统一管理子表的结构与标签
-- 1. 创建超级表（列 + 标签）
CREATE STABLE sensors (
    ts   TIMESTAMP,
    temp FLOAT,
    hum  FLOAT
) TAGS (
    location NCHAR(20),
    model    NCHAR(20)
);

-- 2. 创建子表（可自动创建）
CREATE TABLE d001 USING sensors TAGS ('beijing', 'model-A');
CREATE TABLE d002 USING sensors TAGS ('shanghai', 'model-B');

-- 3. 写入（只写子表，或用自动建表语法）
INSERT INTO d001 VALUES (NOW, 23.1, 60);
INSERT INTO d002 USING sensors TAGS ('shenzhen','model-A') VALUES (NOW, 26.5, 70);

-- 4. 跨设备聚合查询（查超级表）
SELECT AVG(temp), MAX(hum) FROM sensors
WHERE location = 'beijing' AND ts > NOW - 1d
GROUP BY location;

03存储与压缩

  • 列式存储：每个采集列单独存，同列数据同质 → 压缩友好。
  • 按时间分块：数据按时间切分成数据块（默认按天）， 每块内建索引与预聚合信息（min/max/sum/count），可做块级裁剪。
  • 两级压缩：先用列式专用编码（Delta、RLE、位图等），再用通用压缩（LZ4/ZSTD）。
  • 乱序数据处理：支持乱序写入，会在后台重整，但乱序比例高会显著影响压缩比与性能。
压缩比依赖数据特征。官方宣称的高压缩比（1/10）是针对 变化平缓、等间隔上报的典型工业/监控数据。 如果数据值剧烈随机抖动、或时间戳严重乱序，压缩比会明显下降。 选型时务必用自己的真实数据做 PoC 验证，不要只看宣传数字。

04集群架构

🖥️ taosd 数据节点

核心进程，负责存储与查询。多个 taosd 组成集群， 数据按 vnode（虚拟节点）分片存储。

📡 taosAdapter

接入层，提供 REST API、兼容 InfluxDB Line Protocol、 OpenTSDB、Prometheus 等多种写入协议。

🧠 mnode（管理节点）

管理元数据（表、STable、vnode 分布、用户）， 通过 Raft 保证一致，通常部署 3 个。

🛡️ 多副本

每个 vnode 有多个副本（Raft 组）， 支持机架/机房级容灾，副本数在创建数据库时指定。

-- 创建库时指定副本数与保留策略
CREATE DATABASE iot
  REPLICA 3            -- 3 副本
  KEEP 365             -- 数据保留 365 天
  BLOCKS 6             -- 每个 vnode 的内存块数
  PRECISION 'ms';      -- 时间精度（ms/us/ns）

05SQL 与特色查询

TDengine 用标准 SQL，且支持很多时序专属语法，学习成本低：

-- 降采样（按时间窗口聚合）
SELECT AVG(temp) FROM sensors
WHERE ts > NOW - 7d
INTERVAL(1h);                    -- 按 1 小时窗口

-- 窗口聚合 + 按标签分组
SELECT AVG(temp) FROM sensors
INTERVAL(10m) GROUP BY location;

-- 状态窗口（按状态值变化切窗口，工业场景常用）
SELECT COUNT(*) FROM d001
STATE_WINDOW(status);            -- status 值变化才切新窗口

-- 插值填充（处理缺失采样点）
SELECT INTERP(temp) FROM d001
WHERE ts > NOW-1h EVERY(1s) FILL(linear);

-- 会话窗口（间隔超过阈值就切窗口）
SELECT COUNT(*) FROM d001 SESSION(ts, 10s);
STATE_WINDOW 和 INTERVAL 是 TDengine 的实用特色： 工业场景常要统计「设备处于某状态持续了多久」「每次开机运行了多久」， 这些用标准 SQL 写很痛苦，TDengine 提供了原生语法。

Q："一个设备一张表"在设备数千万级会不会元数据爆炸？
A：这是最常见的质疑。TDengine 通过表元数据常驻内存 + 压缩存储来应对， 官方测试支持千万级表。但要注意：每张表都有固定元数据开销， 设备数超过千万、或设备维度频繁变化时仍需谨慎评估。 实践中若设备维度不稳定（如每次会话生成新 ID），应改用超级表 + 标签的常规模型。

建库建表参数与命令

TDengine 的核心设计是一个采集点一张表 + 超级表（STable）聚合。数据模型定对了，压缩率与查询性能才有保障。

核心 DDL / DML

-- 创建数据库：这几个参数直接决定存储与保留
CREATE DATABASE power
    DAYS 10            -- 每个数据文件存 10 天数据（默认 10）
    KEEP 3650          -- 数据保留 3650 天（默认 3650）
    CACHE 16           -- 每个 vnode 的内存缓存大小（MB）
    BLOCKS 6           -- 每个 vnode 的内存块数
    PRECISION 'ms'     -- 时间精度：ms / us / ns
    COMP 2;            -- 压缩：0 不压 / 1 一阶段 / 2 两阶段（默认 2）

-- 超级表：定义 schema + 标签
CREATE STABLE meters (
    ts TIMESTAMP,
    current FLOAT,
    voltage INT,
    phase FLOAT
) TAGS (location BINARY(64), group_id INT);

-- 子表：一个采集点一张，写入时自动创建
CREATE TABLE d1001 USING meters TAGS ('Beijing.Chaoyang', 1);
INSERT INTO d1001 USING meters TAGS ('Beijing.Chaoyang', 1)
       VALUES (NOW, 10.2, 220, 0.31);

-- 查询：对超级表查就是对所有子表查
SELECT AVG(current) FROM meters
WHERE ts >= NOW - 7d AND location LIKE 'Beijing%'
INTERVAL(1h) GROUP BY location;
参数默认值含义建议
DAYS10单个数据文件覆盖的天数查询多按天就设 1~10；归档场景可大
KEEP3650（10 年）数据保留天数按合规与磁盘定，到期自动删
COMP2（两阶段压缩）压缩等级默认即可，关压缩只在调试时用
PRECISIONms时间戳精度设备是秒级的别用 us，会浪费
CACHE16 MBvnode 写缓存写密集可调大，读多写少不必
VGROUPS自动（按 CPU 核数）vnode 分片数分片数 = 并行度，别设太少
REPLICA1副本数（企业版）生产环境至少 3

运维命令

# 运维命令（taos shell 内）
SHOW DATABASES;                     -- 看库参数
SHOW VGROUPS;                       -- 看分片分布
SHOW TABLES LIKE 'd%';              -- 看子表
DESCRIBE meters;                    -- 看超级表结构

# 备份与恢复
taosdump -D power -o /backup/power       # 导出
taosdump -i /backup/power                # 导入（会建库）

# 压测：先造数据再测，否则结论不可信
taosBenchmark -t 1000 -n 100000 -y       # 1000 张表，每张 10 万行

# 观察压缩效果
SELECT table_name,
       ROUND(compression_ratio, 2) AS ratio
FROM information_schema.ins_tables
LIMIT 20;
设计决策推荐做法反例原因
表怎么建一个采集点一张子表一张大表存所有设备单表按时间有序，压缩率高；标签过滤走 STable
标签放哪放 TAGS（稳定、低基数）把经常变的字段放 TAGSTAG 变更代价高
时间精度按设备实际精度一律用 ns精度越高存储与时间索引开销越大
查询方式对 STable 查 + TAG 过滤逐子表 UNION前者由引擎优化，后者计划膨胀
降采样用 INTERVAL + 预聚合每次扫原始点原始数据量大时差距是数量级的

TDengine 的压缩来自三点：列式存储 + 差分/游程编码 + 一设备一表的天然时间有序。实践中常见 5~10 倍压缩率，慢变浮点（如温度）更高。如果压缩率明显低于这个量级，先检查是不是「一张大表混装所有设备」。

上线前逐条核对：

  • 先定数据模型再建库：一设备一表 + 超级表，这是压缩率与查询性能的前提。
  • 时间精度按实际需要选，不要默认用最高精度。
  • KEEP 要按磁盘容量反推：保留天数 × 日增数据量 × 压缩后大小。
  • vgroups 决定写入并行度，太少会成为瓶颈。
  • 写入必须批量：单条 INSERT 的吞吐比批量低一个数量级。
  • 查询必须带时间范围，否则扫全表。
  • 高基数字段不要放 TAGS，TAG 适合放设备位置、型号这类稳定属性。
  • 长期趋势查询用 INTERVAL 预聚合，不要每次扫原始点。
  • 备份要实测恢复：taosdump 导出的必须能导回。
  • 容量规划要算上副本：3 副本时磁盘需求直接 ×3。
