什么时候适用？

判断信号：服务实例地址频繁变化，调用方不能维护静态 IP 列表。

  • 容器实例弹性扩缩容
  • 故障实例从可用列表摘除
  • 多个实例间按健康状态做路由

和相近方案怎么区分？

相近方案选择边界
负载均衡发现负责取得可用实例列表；负载均衡在列表中选目标，二者常配合。
API 网关网关是外部入口；服务发现帮助内部调用方定位服务实例。

最小伪代码

instances = registry.healthy("order-service")
target = loadBalancer.choose(instances)
try:
  return http.get(target + "/orders/42", timeout=1s)
catch Timeout:
  markSuspect(target)

边界：健康检查与注册信息可能滞后；调用方仍需超时、重试预算和故障处理。

如何选择服务发现模式

当实例地址随扩缩容不断变化时，调用方应依赖服务名而非固定 IP。架构上先决定由客户端选实例，还是由代理、网关或平台代选。

  • 客户端发现：调用方自己获取实例列表并负载均衡，调用链较短，但每种客户端都要维护发现逻辑。
  • 服务端发现：调用方只访问稳定入口，路由层负责实例选择；需要规划入口容量与故障处理。
  • 平台边界：Kubernetes Service 与 DNS 已提供服务发现；混合环境再评估独立注册中心。

服务发现：为什么需要它

传统单体部署在固定机器上，IP 写进配置文件就行。但在云环境和容器编排里，实例会随时被创建、销毁、迁移，IP 是动态的、不可预测的。服务发现就是回答一个问题：「我现在要调 order-service，该连哪个 IP:Port？」

服务发现三段式：注册 → 发现 → 直连调用

两种发现模式

模式工作方式代表优缺点
客户端发现消费者向注册中心查询实例列表，自己选一个（负载均衡在客户端）Eureka + Ribbon、Nacos、Consul + 自研少一跳、性能好；但每种语言都要实现客户端，升级成本高
服务端发现消费者只访问一个固定入口（LB / 代理），由它查询注册中心并转发K8s Service + kube-proxy、AWS ALB、Nginx + Consul客户端极简、语言无关；多一跳网络，代理要高可用
DNS 发现注册中心提供 DNS 接口，服务名解析为多个 A 记录K8s CoreDNS、Consul DNS通用性最好（任何语言都会 DNS）；TTL 缓存导致变更不及时，健康检查弱

Kubernetes 的做法：Pod 启动时由 kubelet 注册，Endpoints/EndpointSlice 维护实例列表，Service 提供稳定的 ClusterIP 与 DNS 名，kube-proxy（或 eBPF）负责转发。这属于「服务端发现 + DNS」的组合，对应用完全透明。

健康检查：发现系统的灵魂

服务发现的可靠性完全依赖健康检查——如果实例已经不可用但还在列表里，调用方就会持续失败。三种探针层层递进：

存活探针 Liveness进程是否还活着？失败则重启容器。不要依赖外部依赖，否则依赖抖动会导致无谓重启
就绪探针 Readiness能否接流量？失败则从负载均衡摘除，但不重启。这是最关键的探针
启动探针 Startup慢启动应用的保护，允许前 N 秒不做存活检查，避免启动未完成就被杀

常见错误：把就绪探针写成「检查端口是否能连上」——进程还活着但线程池已满、依赖数据库连接已断，这种实例端口是通的却无法服务。就绪探针应该做一个轻量的真实业务检查（如查一次数据库 SELECT 1），但不能太重，否则频繁探测本身就拖垮实例。

自我保护机制：Eureka 的经典设计——当短时间内大量实例心跳失败时，注册中心会停止剔除，保留现有列表。因为更可能是网络分区导致注册中心收不到心跳，而不是实例真的都挂了。这体现了 CAP 中的 AP 取舍：宁可保留可能失效的实例，也不能把健康的全删掉。

注册中心的 CAP 取舍

AP 型（Eureka / Nacos 临时实例）

优先保证可用性。注册中心各节点对等，即使网络分区也能继续提供服务列表。

  • 代价：节点间数据可能短暂不一致，可能拿到已下线实例
  • 补偿：客户端要做重试 + 熔断，不能盲目信任列表
  • 适合：实例数量大、变更频繁、短暂不一致可接受的业务

CP 型（ZooKeeper / etcd / Consul）

优先保证一致性，用 Raft/ZAB 等共识算法保证各节点数据一致。

  • 代价：选举期间（秒级）不可写，注册会短暂失败
  • 优势：列表准确，不会有「幽灵实例」
  • 适合：实例数适中、对准确性要求高的场景；也常用于配置管理与分布式锁

选型结论：服务发现场景通常选 AP——因为拿到一个失效实例可以由客户端熔断兜住，而注册中心整体不可用会导致全站调用瘫痪。但配置管理、分布式锁这类场景必须选 CP（etcd/ZK）。

深入自检

注册中心挂了，服务之间还能互相调用吗？

设计良好的系统应该能。关键在于客户端本地缓存：消费者启动时拉取一次服务列表并缓存在内存，之后通过长轮询/推送增量更新。注册中心不可用期间，调用方用缓存的列表继续直连——此时 IP 依然有效，只是新增或下线的实例感知不到。所以注册中心短暂的不可用不应该造成业务中断，这也是为什么服务发现通常选 AP 而非 CP。

实例下线时怎么做到无损？

顺序非常重要，反了就会造成请求失败：① 先调用下线接口或在注册中心摘除自己（不再有新流量进入）；② 等待一小段时间（大于调用方缓存刷新周期，如 30s），让所有消费者更新列表；③ 再执行优雅关闭，处理完存量请求；④ 最后停止进程。Kubernetes 里对应 preStop hook + terminationGracePeriodSeconds，并且要注意 Endpoint 的变更传播有延迟。

为什么不建议用 DNS 做服务发现？

三个硬伤：① DNS 有 TTL 缓存，实例变更后最长要等一个 TTL 才生效，而很多客户端甚至不遵守 TTL；② DNS 无法表达实例权重、元数据、健康状态，只能给 IP 列表；③ UDP 查询丢包时缺少可靠的重试语义。所以 DNS 适合做「粗粒度入口定位」（如找到某个 Service 的 ClusterIP），不适合做精细的实例级发现。

心跳间隔和超时时间怎么定？

权衡「故障发现速度」与「误判概率」。心跳太密（1s）会给注册中心带来巨大压力；超时太短（<3 倍心跳间隔）会因为一次网络抖动就误剔除健康实例。经验值：心跳 5~30s，超时设为 3 倍心跳间隔（如心跳 10s、超时 30s）。同时要有「连续 N 次失败才剔除」的判定，以及前面提到的自我保护机制，防止网络分区时大规模误剔除。
