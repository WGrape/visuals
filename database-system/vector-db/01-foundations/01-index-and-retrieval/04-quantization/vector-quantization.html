①先算一笔内存账：为什么必须量化

向量数据库的成本几乎全部压在内存上。假设用 float32 存 768 维向量，一条就是 768 × 4 = 3072 字节；一千万条是 30.7 GB，一亿条是 307 GB。再加上 HNSW 图的邻接表，真实占用还要再多一成到一倍。

这个量级下，想让单机扛住、想让云账单可接受，唯一有效的手段就是量化（Quantization）：用更少的 bit 表示同一个向量，用可控的召回损失换内存和延迟。

精度每条字节（768 维）1 亿条总量压缩比典型召回损失
float32（FP32）3072 B307.2 GB1×（基准）0
float16 / halfvec1536 B153.6 GB2×≈0
SQ8（int8）768 B76.8 GB4×0.5–2%
SQ4（int4）384 B38.4 GB8×2–5%
PQ，m=96 / nbits=896 B9.6 GB32×3–8%
BQ（1 bit/维）96 B9.6 GB32×5–15%
上表的「压缩比」只算了向量本体。图索引的邻接表不跟着压缩，它的开销在低 bit 场景会反超本体 —— 见第 ⑥ 节，这是量化算账时最常见的漏项。

②四条技术路线与各自压缩的对象

不同路线压缩的对象不一样，理解这一点比记参数重要。

标量量化 SQ

逐维度把 float32 映射成 int8/int4，保留每个维度自己的 min/max 或分位数。不改变维数，只降低每维位宽，因此对任意距离度量都成立，实现最简单、精度损失最小。

乘积量化 PQ

把 D 维切成 m 段，每段单独做 k-means 得到 256 个聚类中心（nbits=8）。向量最终存成 m 个聚类 ID（m 字节），距离用查表相加（ADC）算出来。

二值量化 BQ

只看每一维的符号，正数为 1、负数为 0，一条 768 维向量压成 96 字节。距离退化成 Hamming 距离或 XOR+popcount，是吞吐最高的路线。

残差量化 RQ

先粗量化，再对「残差」继续量化，多级叠加逼近原始向量。常与 PQ 组合成 IVF-RQ / RABITQ 这类复合索引，在超大规模下才划算。

一句话分工：SQ 保精度、PQ 压到底、BQ 拼吞吐、RQ 压极限。工程上 90% 的场景用 SQ8 或 SQ4 就够了，PQ/BQ 属于「内存真的不够」时才上的重武器。

③标量量化 SQ：为什么 int8 几乎无损

SQ 的做法是给每一维定一个区间 [min, max]，把区间线性切成 256 份（int8）或 16 份（int4），存下落在第几份。解码时按区间中点还原。

# SQ8 的本质：per-dimension 线性映射
# 训练阶段：统计每一维的 min/max（或 0.99 分位数）
# 编码阶段：q = round((x - min) / (max - min) * 255)
# 解码阶段：x' = min + q / 255 * (max - min)
#
# 误差上界 = 每维区间宽度 / 255 / 2
# 768 维、取值大致落在 [-0.3, 0.3] 时，
# 单维误差 ~0.0012，累积后对余弦相似度的影响在 1e-3 量级
# —— 这就是 SQ8 往往能做到「几乎不掉召回」的原因

那 SQ4 为什么也常常够用？因为最近邻排序靠的是相对距离而不是绝对数值。只要量化误差在所有向量上同分布，它主要在互相抵消，排序很少翻转。真正会翻的是「第 9 名和第 10 名本来就几乎同分」的边界情形 —— 而这部分本来也该由重排（rerank）来救。

SQ 的经典翻车点：离群维度。LLM 的 embedding 里常有个别维度出现极大值（几十甚至上百），一旦用全局 min/max 定区间，正常值全被压进一两个桶，量化等于失效。解法是改用分位数裁剪（如 0.99 quantile）把极端值截断，Qdrant 的 quantile 参数就是干这个的。

④乘积量化 PQ：子空间切分与查表距离

PQ 不按维度切，而是按子空间切。以 768 维、m=96 为例：每 8 维组成一个子空间，每个子空间用 k-means 训练 256 个中心，任意子向量用 1 个字节（中心编号）表示。整条向量于是只剩 96 字节。

参数含义怎么调代价
m子空间个数 = 最终字节数dim/8 起手；768 维常用 m=48~96m↑ 精度↑ 内存↑
nbits每段中心数 = 2^nbits几乎固定为 8；12 位需 1.5 字节nbits↑ 精度↑ 码本↑
训练样本k-means 输入至少 256 × m 条，推荐 10 万条以上样本不足时码本退化
PQ 必须有训练阶段，且码本绑定了数据分布。换了 embedding 模型、换了数据域，码本必须重训并重建索引 —— 这是 PQ 比 SQ 麻烦的根本原因。

⑤二值量化 BQ：1 bit 一维的适用前提

BQ 只保留符号位：b = 1 if x > 0 else 0。距离用 Hamming 距离，CPU 上可以靠 XOR + popcount 一条指令算 64 维，GPU 上吞吐更是量级提升。

适用条件说明
维度足够高（建议 ≥ 1024）维度越高，符号位保留的方向信息越充分；768 维以下损失明显
向量已归一化或分布对称若整体偏移到正半轴，符号位全为 1，信息量为零
必须有重排（rescoring）BQ 只用于粗筛，靠 oversampling 拿 3–4 倍候选再用原向量精排
量化后一定要算实际内存见第 ⑥ 节，图索引开销可能比省下的还多

oversampling: 3.0 的意思是：先用 BQ 召回 30 条（10 × 3），再用原始向量精排取前 10。这个倍数就是「召回率」和「延迟」的旋钮 —— 官方经验值 2–4，低于 2 通常召回掉得厉害。

⑥最易漏算的一项：图索引开销不压缩

这是量化算账时最容易被忽略、也最容易造成「明明量化了内存却没降」的一条。HNSW 每个节点要存邻居 ID 列表，level 0 最多 2M 个邻居，每个 ID 4 字节，所以平均每条约 2M × 4 = 128 B（M=16）的图开销。

方案向量本体图开销（M=16）合计/条图占比
FP323072 B128 B3200 B4%
SQ8768 B128 B896 B14%
SQ4384 B128 B512 B25%
PQ m=9696 B128 B224 B57%
BQ96 B128 B224 B57%
算清这笔账：从 FP32 压到 BQ，向量本体省了 32 倍，但总占用只省了 3200 / 224 ≈ 14 倍。如果还想更省，要么降低 M（牺牲召回），要么换 IVF/PQ 体系（少用图），要么上磁盘索引（DiskANN）——单靠压向量位宽会很快撞到图开销这堵墙。

⑦压缩比—召回曲线与 rescoring 的赎金

量化不是免费的。压缩比越高，越依赖「多召回一些再精排」来把召回率赎回来，而精排需要原始向量还在（内存或磁盘上），于是内存省了一部分、延迟涨了一部分。

方案建议 oversampling相对 FP32 召回相对 FP32 延迟省内存
SQ8 + rescore1.5–2×98–99.5%1.1–1.3×约 4×
SQ4 + rescore2–3×95–98%1.3–1.6×约 6×
BQ + rescore3–4×90–97%1.4–2.0×约 10–14×（含图开销）
PQ + rescore2–4×88–96%1.5–2.2×约 10–14×（含图开销）
上表是量级参考，不是承诺值。真实损失强依赖数据分布与维度，必须用你自己的数据 + FLAT ground truth 实测（方法见 召回评测）。

⑨速记卡

量化解决什么

内存与延迟，代价是召回。它是精度换钱的旋钮，不是免费优化。

SQ8 的定位

默认首选。4× 压缩、几乎不掉召回、无需训练、可随时开关。

PQ 的本质

子空间切分 + 码本查表。必须训练，换域即失效。

BQ 的前提

维度够高 + 必须重排 + 先算图开销。低维直接崩。

最大的坑

图开销不压缩。BQ/PQ 时图可能占 57%，实际只省 14 倍。

最常漏的开关

oversampling + rescore。不开重排，量化召回必掉。

离群维度

用分位数裁剪（quantile 0.99），否则正常值被压成一桶。

怎么验证

FLAT 建 ground truth → 量 recall@K → 找 oversampling 拐点。

量化的账要算两本：省下多少内存，和付出多少召回。只算前一本，上线后就会被 badcase 追着改。
