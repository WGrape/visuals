制品与环境管理：从一次构建到多环境部署

「同一个镜像跑到生产」是持续交付的前提。要做到这一点，必须把「构建时确定的」和「部署时才知道的」彻底分开。

不可变制品原则

不可变制品（Immutable Artifact）指的是：构建产物一旦生成就不再修改，测试环境验证的那个二进制，就是上生产的那个二进制。它带来的最大好处是消除了「在 A 环境测过、在 B 环境行为不同」这类问题。

反模式问题正确做法
每个环境各自编译打包编译环境、依赖版本可能不同，产物行为不一致只构建一次，产物在各环境间流转
部署时修改配置文件内容改过之后的产物不再是被测过的那个配置外置，部署时注入，产物本身不动
在生产环境打补丁/热修复生产与版本库脱节，下次发布会被覆盖走完整流程，从源码重新构建发布
用 latest 标签部署无法回溯到底跑的是哪一版用不可变标识（digest 或版本号）

镜像标签：tag 和 digest 的区别

容器镜像有两个标识：tag（如 v1.2.3）和 digest（内容哈希，如 sha256:...）。tag 是可变的——同一个 tag 可以被重新推送覆盖；digest 由内容决定，内容不变 digest 就不变。

因此部署时应该用 digest（或至少用不可变的语义化版本号），而不是可变的 tag。否则「回滚到上一个版本」可能拉到完全不同的内容，而「当前跑的是哪个版本」也会变成一个无法回答的问题。

环境与配置的三层分离

代码、配置、密钥

代码进镜像；配置（数据库地址、超时时间、特性开关）外置为环境变量或配置文件；密钥（密码、证书、token）进专门的密钥管理系统，不进镜像也不进代码库。

泄露半径完全不同

配置泄露通常只是暴露了架构信息；密钥泄露意味着直接失守。而且密钥需要轮换，轮换不应该触发重新构建和发布。

差异越多，未测路径越多

理想情况是各环境只差一个配置文件。环境间行为差异越大，测试环境的结论对生产的参考价值就越低。

部署后确认生效

确认应用读到的确实是本次注入的配置，而不是镜像里打包的默认值。这类「配置没生效」的故障非常常见。

环境策略：几个环境才够

环境目的与生产的差异
本地/开发快速迭代依赖常用 mock 或容器化本地服务；差异最大
测试/集成自动化验证配置尽量接近生产，数据量可以小
预发/Staging发布前最后验证配置应与生产一致，否则验证意义有限
生产对外服务基准

环境不是越多越好。每多一个环境，就多一份配置需要维护、多一条未充分测试的路径。常见的高性价比组合是「本地 + 测试 + 预发 + 生产」四个；预发环境如果配置与生产不一致，就退化成了第二个测试环境，价值很低。

制品仓库与供应链

制品需要集中存放并管理生命周期：版本保留多久、如何清理、如何做漏洞扫描、如何签名验证来源。这些属于软件供应链安全的范畴——近年来针对构建和分发环节的攻击显著增加，「我们只从官方源拉取依赖」已经不够。

最小实践：锁定依赖版本（lock 文件必须提交）、对制品做签名或至少记录 digest、对镜像做漏洞扫描并纳入发布门禁、保留构建溯源信息（哪个 commit、哪个构建环境产出的）。

边界与误区

不可变制品不等于「所有配置都要外置」。默认配置打包在镜像里是合理的，只有确实因环境而异的部分才需要外置——过度外置会让部署清单变得庞大且容易出错。判断标准是：这个值在不同环境会不同吗？

制品与环境：一张表管住映射关系

核心原则是 12-Factor 的「一份制品，多处部署」：构建一次，把环境差异全部外置成配置，绝不为每个环境重新构建。

环境制品来源配置来源谁可以发布数据
local本地 build.env.local（不入库）开发者本地 mock / 种子数据
dev每次 commit 都构建的 :sha-xxxxConfigMap + 环境变量自动（合并即部署）脱敏后的数据子集
test / stagingrelease 候选 tagConfigMap + Secret自动（打 tag 时）生产数据的脱敏副本
prod只从 release tag 构建，或 promotion（把 staging 镜像重新打 tag）ConfigMap + Secret（密钥用外部 KMS/Vault）人工审批 + 灰度真实数据

标准构建-推送-部署流程

# 1) 构建：tag 用 git sha，保证可追溯
IMG=registry.example.com/app/order
SHA=$(git rev-parse --short HEAD)
docker build -t $IMG:$SHA -t $IMG:latest .

# 2) 推：只推 sha tag（latest 只用于本地）
docker push $IMG:$SHA

# 3) 部署：环境差异只在 configmap / env，不重build
kubectl -n prod set image deploy/order order=$IMG:$SHA
kubectl -n prod rollout status deploy/order --timeout=180s
kubectl -n prod rollout undo deploy/order        # 出问题秒回滚

# 4) 看这个镜像到底是哪个 commit 构建的（可追溯性的关键）
docker inspect $IMG:$SHA --format '{{index .Config.Labels "org.opencontainers.image.revision"}}'
# 构建时记得加标签：docker build --label org.opencontainers.image.revision=$SHA
tag 策略例子优点缺点
git sha:a1b2c3d可追溯、天然不可变不直观，看不出版本
语义化版本:1.4.2直观需要人工维护，容易忘
:latest:latest方便生产禁止：无法回滚、无法追溯、缓存陷阱
分支名:main跟随分支内容会变，破坏不可变性

推荐组合：:<git-sha> 作为部署用的唯一 tag，同时打 :<semver> 供人阅读。生产永远不要用 latest——K8s 的 imagePullPolicy: Always 会造成「同一个 deployment 里不同 Pod 跑着不同代码」的诡异状态。

环境一致性与安全检查清单

  • 构建要可复现：锁依赖（package-lock.json / go.sum / poetry.lock），基础镜像用固定 digest 而不是 tag：FROM node:20@sha256:...。
  • 多阶段构建瘦身：编译镜像 1GB+，运行镜像用 distroless 或 alpine 可压到 20~50MB，启动更快、攻击面更小。
  • 不要在镜像里塞密钥：任何写进 Dockerfile 的 ENV SECRET= 都会被 docker history 看到，且进了镜像层就删不掉。用 K8s Secret / Vault / 云厂商 KMS 注入。
  • 非 root 运行：USER 10001，配合 K8s runAsNonRoot: true、readOnlyRootFilesystem: true。
  • 镜像签名与扫描：cosign sign + admission 校验 + trivy image 扫 CVE，能拦住绝大部分供应链风险。
  • 环境差异清单化：把「dev 和 prod 到底差在哪」写成一张表（DB 地址、MQ topic、限流阈值、超时时间、特性开关），每次新增环境差异都要过 review——差异越多，「在我这儿是好的」事故越多。

多阶段构建 + 扫描 + 签名

# 镜像瘦身：多阶段构建示例
FROM golang:1.22 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o /app ./cmd/server

FROM gcr.io/distroless/static-debian12
COPY --from=build /app /app
USER 10001
ENTRYPOINT ["/app"]

# 扫描与签名
trivy image --severity HIGH,CRITICAL registry.example.com/app/order:a1b2c3d
cosign sign registry.example.com/app/order:a1b2c3d
cosign verify registry.example.com/app/order:a1b2c3d

# 看镜像到底有几层、多大（瘦身前后对比）
docker history registry.example.com/app/order:a1b2c3d
为什么不能为每个环境单独构建？

因为你测试过的就不是你要上线的那个东西。dev 构建和 prod 构建即使源码一样，编译器版本、基础镜像补丁、依赖的小版本都可能不同，导致「staging 没问题，prod 挂了」。一次构建多处部署（build once, deploy many）是消除这类问题的唯一办法。

配置该放 ConfigMap 还是环境变量？

两者都会被 Pod 直接读到，都不是安全的——密钥必须走 Secret 或外部 KMS。实践建议：非敏感的普通配置放 ConfigMap（改起来方便、可版本化）；需要被进程感知的少量关键项放 env（改 env 会触发滚动更新）。注意 ConfigMap 挂载为 volume 时更新有 约 60 秒同步延迟，env 则需重启才生效。

回滚到底是回滚什么？

优先回滚镜像（kubectl rollout undo，秒级，最安全）；只有当问题是数据库 schema 变更引起的，才需要回滚 schema——所以 schema 变更必须向后兼容（先加字段、双写、再删旧字段，分 2~3 次发布）。这是「不可变制品」原则下最容易被忽视的例外。

自检

为什么不能在生产环境直接改配置而不走流程？

直接改会让「实际运行配置」与「版本库里的配置」产生偏差（配置漂移）。下一次正常发布会用版本库里的配置覆盖掉它，导致故障莫名其妙地复现。紧急修改也必须事后同步回版本库。

一、制品到底是什么

形态内容优点注意
容器镜像应用 + 运行时 + 系统依赖环境一致性最好必须按 digest 引用，别用 latest
二进制 / jar / wheel编译产物体积小、启动快需锁定运行时版本
Helm Chart / K8s 清单部署描述可参数化多环境模板要保持幂等
静态资源包前端构建产物可直接上 CDN带 hash 文件名便于长期缓存

关键区分：制品（Artifact）是构建产物，不可变；配置（Config）是环境参数，可变。把配置打进制品，就等于为每个环境重新造一个制品，测试验证过的东西和上线运行的东西不再是同一个。

二、环境分层的现实取舍

环境目的数据常见做法
本地 dev开发自测假数据 / 少量种子docker compose 起依赖
集成 dev/test联调与自动化回归脱敏或合成数据每次合并触发自动部署
预发 staging上线前最后验证生产同构、数据脱敏与生产同版本、同配置结构、规模缩小
生产 prod真实流量真实数据灰度发布 + 可观测 + 快速回滚
环境不一致是最大的故障温床

典型症状：测试环境一切正常，上线就炸。根因往往是 N 个环境里有 N 份不同的依赖版本、N 套不同的中间件参数。对策只有一条——环境差异收敛到配置文件与基础设施代码（IaC），应用制品保持唯一。

三、配置怎么管

环境变量最简单，适合少量标量；缺点是没有结构、不好审计
配置文件随镜像或挂载 ConfigMap；注意改动要触发滚动更新
配置中心Nacos / Apollo / etcd；支持动态推送与灰度，但要防配置错误引发雪崩
密钥管理Secret / Vault；绝不能进 Git，且要支持轮换

一条硬规则：密钥与配置分离。配置可以明文、可以进 Git；密钥必须走独立的密钥管理系统，并且有加密存储、访问审计、定期轮换三件套。

四、版本与追溯

# 制品版本建议包含：语义化版本 + 构建号 + commit app:1.4.2+build.318.commit.9f2a1c # 部署一定要按 digest 而不是 tag，tag 可以被覆盖 image: registry/app@sha256:9f2a1c... # 每次发布记录四要素，方便出事时秒级定位 # 版本 / 部署时间 / 部署人 / 变更内容（含配置变更）

五、深入自检

为什么不能用 latest 标签？

latest 是可变引用：今天的 latest 和明天的不一样。用它会导致「三个副本跑着三个版本」「回滚回到的不是上一版」。用 digest 才能保证部署与回滚都精确。

配置中心推送会不会引发雪崩？

会。错误配置会被瞬间推到所有实例。因此配置中心必须支持：灰度推送、按批次生效、快速回滚，并且客户端要对配置做本地校验（校验失败则拒绝生效、保留旧值）。

预发环境有必要和生产 1:1 吗？

结构要一致，规模可以缩小。关键是依赖组件的版本、参数类型、网络拓扑一致，这样性能之外的绝大多数问题都能在预发暴露。规模只影响容量类问题，留给压测解决。

数据库迁移算不算制品的一部分？

算变更，但不建议和代码部署绑死在同一原子操作里。推荐「扩展-迁移-收缩」三段式：先加兼容的新字段/新表，再双写迁移数据，最后在确认无依赖后再删旧字段——这样任何一步都能回滚。

构建产物要不要存源码关联信息？

必须存。出事时要能回答「线上这个二进制是哪次提交编译的」。把 commit、构建时间、构建环境写入制品元数据，并在启动时暴露到 /health 或 /info。
