分布式缓存

缓存是提升性能的"第一杠杆"，但"缓存与数据库一致性"和"穿透 / 击穿 / 雪崩"三大问题是面试几乎必考的送命题。

更新策略 缓存穿透 缓存击穿 缓存雪崩 双写一致性 面试要点

📝 一、缓存更新策略

策略读写评价
Cache Aside（旁路）先查缓存，未命中查 DB 再回写先更新 DB，再删缓存最常用，简单可控
Read/Write Through应用只操作缓存，由缓存层同步落库对应用透明，但实现复杂
Write Behind—只写缓存，异步批量落库性能极高，但可能丢数据
✅
业界主流 = Cache Aside：读"缓存 miss → 查 DB → 回填"；写"更新 DB → 删除缓存"。为什么删而不是更新缓存？ 避免并发写导致缓存脏数据，且懒加载更高效。

🕳️ 二、缓存穿透：查不存在的数据

请求的数据在缓存和数据库里都不存在（如恶意刷 id=-1），每次都穿透到 DB，缓存形同虚设，DB 被打爆。

解法
① 缓存空值：把"查无此物"也缓存一个短 TTL 的空结果，挡住重复请求；② 布隆过滤器（Bloom Filter）：在缓存前加一层，快速判断"这个 key 一定不存在就直接拒绝"；③ 接口层做参数校验/限流。
💡
布隆过滤器用位数组+多个哈希，说"不存在"就一定不存在，说"存在"可能误判——用极小空间挡住绝大多数穿透攻击。

💥 三、缓存击穿：热点 key 突然过期

某个极端热点 key 在失效瞬间，海量并发同时打到 DB——一个 key 的"过期"引发雪崩式冲击（区别于全局雪崩）。

解法
① 互斥锁 / 分布式锁：只允许一个线程去查 DB 并回写，其余等待重试；② 逻辑过期：缓存不真设 TTL，value 里带过期时间，发现"逻辑过期"时异步重建、旧值先返回；③ 热点 key 设不过期（靠后台刷新）。

🌨️ 四、缓存雪崩：大量 key 同时失效

大量缓存 key 在同一时刻集中过期，或缓存服务整体宕机，请求全部涌向 DB，导致 DB 瞬间过载甚至连锁崩溃。

解法
① 过期时间加随机抖动（如 base±random），避免集体到点；② 多级缓存（本地 + Redis + DB）降低对单点的依赖；③ 高可用：Redis 集群 + 限流熔断降级；④ 服务层做限流/熔断保护 DB。
⚠️
三者的区别：穿透=查"不存在"的数据；击穿=一个"热点"过期；雪崩=大量 key "同时"过期/缓存挂掉。一个针对非法 key，后两个针对过期与集群失效。

🔄 五、缓存与数据库双写一致性

先更新 DB 还是先删缓存？经典答案：先更新数据库，再删除缓存（Cache Aside）。但仍存在极小窗口问题。

为什么"先删缓存再更 DB"更糟
A 删缓存 → B 读 miss 读旧 DB 回填旧值 → A 更 DB。结果缓存是旧值，长期不一致。
"先更 DB 再删缓存"的残留窗口
读请求在"DB 更完、缓存未删"之间读到旧值并回填。概率极低（要求读比写慢），但存在。
加强：延迟双删 / 订阅 binlog
写后延迟再删一次；或 canal 订阅 MySQL binlog，异步删除/更新缓存，最终一致更稳。
💡
现实取舍：绝大多数业务接受"Cache Aside + 最终一致"。要求强一致时，让读请求也走 DB 或加锁，但会损失性能。

🎯 六、面试高频追问

穿透、击穿、雪崩分别怎么答？
先点明区别（非法 key / 单点过期 / 集体过期），再各给对策：空值+布隆过滤 / 互斥锁+逻辑过期 / 随机 TTL+多级缓存+限流熔断。
先更新 DB 还是先删缓存？
先更新 DB，再删缓存（Cache Aside）。原因：反序会造成"删缓存→读旧值回填→更新DB"的脏数据；正序窗口更小。
布隆过滤器误判怎么办？
误判只发生在"说存在其实可能不存在"——此时会放行进 DB 一次，但绝不会漏掉"真正不存在"的。配合空值缓存即可兜底。

分布式缓存的路由与容量

方案原理扩容时的数据迁移
取模 hashhash(key) % N全部失效（N 变了所有 key 重映射）
一致性哈希key 与节点映射到同一 hash 环只迁移 1/N 的数据
一致性哈希 + 虚拟节点每节点 100~200 个虚拟节点负载均衡，迁移量 1/N
哈希槽（Redis Cluster）16384 个固定槽按槽迁移，精确可控
参数 / 指标值说明
Redis Cluster 槽数16384为什么是 16384：心跳包用 bitmap 表示，16384/8=2KB，正好合适
虚拟节点数100~200 每物理节点太少不均，太多内存开销
缓存命中率目标> 90%低于 80% 说明容量或 key 设计有问题
单 Redis 实例 QPS10 万级（简单命令）单线程模型
集群节点数上限Redis Cluster 官方建议 < 1000节点多了 gossip 开销大
cluster-node-timeout15000ms节点失联判定时间，影响故障切换速度
大 key 阈值> 10KB（string）/ > 5000 元素（集合）大 key 造成阻塞与迁移困难

一致性哈希为什么能只迁移 1/N：节点和 key 都在同一个 0~2³² 的环上，key 顺时针找最近的节点。加一个节点时，只有该节点逆时针到上一个节点之间的 key 需要迁移，其余 key 的归属完全不变。从 3 个节点扩到 4 个，只迁移约 1/4 的数据，而取模 hash 会迁移 几乎全部（命中率瞬间跌到接近 0）。

命令与配置

# Redis Cluster 运维
redis-cli --cluster create 127.0.0.1:7001 127.0.0.1:7002 127.0.0.1:7003 \
                           127.0.0.1:7004 127.0.0.1:7005 127.0.0.1:7006 \
          --cluster-replicas 1          # 每个主节点 1 个副本

redis-cli --cluster info 127.0.0.1:7001
# 看：槽分配、keys 分布、每个主节点的副本数

redis-cli --cluster check 127.0.0.1:7001     # 检查槽是否完整覆盖

# 扩容：加节点并迁移槽
redis-cli --cluster add-node 127.0.0.1:7007 127.0.0.1:7001
redis-cli --cluster reshard 127.0.0.1:7001 --cluster-from <源id> \
          --cluster-to <新节点id> --cluster-slots 4096
# 迁移过程中服务不中断，只影响被迁移的槽
# 命中率监控（必须接）
redis-cli info stats | grep -E 'keyspace_(hits|misses)'
#   keyspace_hits:100000
#   keyspace_misses:5000
#   命中率 = hits / (hits + misses) = 95.2%

# 命中率突降的排查顺序：
# 1) 是否扩容/缩容了（数据迁移导致大量 miss）
# 2) 是否批量过期（TTL 设成一样，同时失效）
# 3) 是否有新流量（新 key 从未缓存过）
# 4) 是否内存满了被驱逐（看 evicted_keys）
redis-cli info stats | grep evicted_keys      # 非 0 说明容量不够
redis-cli info memory | grep used_memory_human

# 热 key 检测
redis-cli --hotkeys                            # 需要 maxmemory-policy 是 LFU 类
redis-cli --bigkeys                            # 找大 key
# 热 key 解决方案：本地缓存一份 / key 打散（key:1 ~ key:10 随机后缀）

症状原因处理

TTL 加随机抖动是必做的：ttl = base + random(0, base*0.2)。如果一批 key 在同一秒写入且 TTL 相同，它们会在同一秒集体失效，那一瞬间全部请求打向 DB —— 这就是缓存雪崩。

核心速览

一句话把缓存从进程里搬出来，做成多个应用实例共享的独立服务
和本地缓存的区别本地缓存每人一份、不一致但零网络；分布式缓存一份共享、一致但有网络开销
核心难题路由（数据在哪台）、扩缩容（数据怎么搬）、高可用（节点挂了怎么办）
典型选型Redis 主从/哨兵/Cluster、Memcached
本地缓存 vs 分布式缓存：共享一份换来一致性，代价是多一跳网络

一、为什么需要它

问题本地缓存的表现分布式缓存的表现
多实例不一致A 更新了 B 没更新，用户刷新看到旧值所有人读同一份，天然一致
缓存命中率每个实例各自预热，总量放大 N 倍一份数据服务所有实例，内存利用率高
容量上限受单机内存限制可水平扩展到 TB 级
访问延迟纳秒~微秒级，几乎为零毫秒级，多一次网络往返
故障影响进程挂了缓存就没了独立进程，应用重启不影响

二、数据怎么分布到各节点

方案做法扩缩容代价适用
取模 hashhash(key) % NN 变化时几乎全部失效节点数固定的小集群
一致性哈希哈希环，只迁移环上一小段只影响 1/N 的数据经典方案，Memcached 客户端常用
哈希槽（Redis Cluster）16384 个槽分配给节点按槽迁移，可控且可观测Redis 官方集群方案
客户端路由客户端直连，无代理需客户端支持，升级麻烦性能敏感场景
代理层路由Twemproxy / Codis / Proxy多一跳，但客户端简单多语言、客户端不好统一时
哈希槽为什么是 16384

Redis Cluster 用 CRC16(key) mod 16384 决定槽位。槽数固定后，扩缩容变成「把某些槽从一个节点搬到另一个节点」，迁移粒度可控、进度可观测；节点间心跳只需 2KB 位图就能表达自己负责哪些槽。

三、高可用三种形态

主从复制一主多从，读写分离；主挂了需要人工或自动切换
哨兵 Sentinel哨兵进程监控主节点，自动故障转移；但仍是单主写入
Cluster 集群多主多从 + 自动分片 + 自动故障转移；容量与可用同时解决

选择建议：数据量小、写少读多用主从 + 哨兵就够；数据量超过单机内存或写压力大再上 Cluster，因为 Cluster 会带来多 key 操作受限、事务受限、客户端复杂度上升等成本。

四、必须提前设计的四件事

事项不做的后果常见做法
Key 命名与过期内存无限增长、无法按业务清理业务前缀:ID，统一设置 TTL 且加随机抖动
热点 key单节点被打爆，集群整体不可用本地缓存 + 随机后缀拆分成多个 key
大 key网络阻塞、迁移卡住、删除卡顿拆分、压缩、改用合适结构；删除用 UNLINK
缓存与 DB 一致性读到脏数据旁路缓存：先更新 DB 再删缓存；失败重试或延迟双删

五、深入自检

分布式缓存能当数据库用吗？

只在你能接受数据丢失时。Redis 持久化（RDB/AOF）只是降低丢失窗口，在主从异步复制下，主节点宕机仍会丢掉未同步的写入。需要强一致就得用支持持久化的存储。

为什么不直接扩大本地缓存？

本地缓存的容量受单机内存限制，且实例越多内存浪费越大；更重要的是本地缓存无法解决一致性问题——除非引入失效广播，而那又变成了分布式系统。

一致性哈希为什么还要虚拟节点？

物理节点少时数据分布容易倾斜，且节点性能不同无法加权。虚拟节点让一个物理节点对应环上多个点，分布更均匀，也能按权重调节点数。

缓存节点宕机一定会导致雪崩吗？

只要做了三件事就不会：TTL 加随机抖动错开失效、熔断/降级兜底、以及缓存集群本身的高可用（主从切换）。最危险的是「冷启动后瞬间全量回源」。

多 key 操作（MGET、事务）在集群下怎么办？

Redis Cluster 要求所有 key 在同一槽，可用 hashtag 强制：把 key 写成 user:{1001}:profile 与 user:{1001}:orders，只对大括号内的部分做哈希，就能落在同一槽。

记住一句共享一份换一致性，代价是一跳网络
路由首选哈希槽（Redis Cluster）
三大坑热点 key / 大 key / 缓存雪崩
一致性默认解更新 DB 后删除缓存
