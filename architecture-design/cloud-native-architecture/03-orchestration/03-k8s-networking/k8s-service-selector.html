🔷 K8S Service与Pod关系详解

📚 核心概念

Service是Kubernetes中的抽象层，定义了一组逻辑上的Pod访问策略。它提供了一个稳定的网络入口，屏蔽了后端Pod的动态变化。

Pod是Kubernetes的最小部署单元，包含一个或多个容器。Pod有独立的IP地址，但这个IP会随着Pod的重启、迁移而变化。

Label是附加到K8S对象（如Pod）上的键值对，用于组织和选择对象子集。格式：key: value

Selector是Service连接Pod的桥梁！

Service通过selector字段定义标签选择器，用于匹配拥有对应标签的Pod。只有标签完全匹配的Pod才会被该Service代理。

💡 Selector工作原理

1️⃣ 标签匹配流程

  • Step 1: 管理员创建Pod时，为Pod打上Label标签
  • Step 2: 创建Service时，在spec.selector中定义标签选择器
  • Step 3: K8S控制平面持续监控，将Selector与所有Pod的Label进行匹配
  • Step 4: 匹配成功的Pod被自动加入到Service的Endpoints列表
  • Step 5: Service将流量负载均衡到这些Pod

2️⃣ Selector类型

  • Equality-based (基于等值): environment = production 或 environment != qa
  • Set-based (基于集合): environment in (production, qa) 或 environment notin (dev)
  • Service使用的Selector: 通常是简单的key: value映射（等值匹配）

3️⃣ YAML配置示例

apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  selector:
    app: nginx      # 👈 这就是Selector！
    env: prod       # 必须同时匹配这两个标签
  ports:
    - protocol: TCP
      port: 80
      targetPort: 8080
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx    # Pod的Label
      env: prod     # Pod的Label
  template:
    metadata:
      labels:
        app: nginx  # 👈 Pod模板中的Label定义
        env: prod
    spec:
      containers:
      - name: nginx
        image: nginx:latest
        ports:
        - containerPort: 8080

🔑 关键规则总结

  • 多标签AND关系: Service的selector中所有键值对都必须匹配，Pod才会被选中
  • 动态更新: 当Pod的Label变化时，Service会自动更新Endpoints列表
  • 跨Namespace: Service默认只能选择同一Namespace内的Pod
  • 无Selector的Service: 可以创建没有selector的Service，手动配置Endpoints（用于访问外部服务）
  • 标签建议: 使用有意义的标签，如app, version, env, tier等

深入自检

Service 的 ClusterIP 是真实网卡吗？

不是。ClusterIP 是虚拟 IP，不存在于任何网卡上，只存在于 kube-proxy 写的 iptables/IPVS 规则里。这就是为什么在节点上 ping 它有时不通、但 curl 端口 可以。

为什么 Pod 就绪了还是访问不到？

最常见三种：① readinessProbe 未通过，Pod 不在 Endpoints 里；② targetPort 写错，流量打到了没有监听的端口；③ 网络策略 NetworkPolicy 拒绝了流量。

Service 能做会话保持吗？

可以，设置 sessionAffinity: ClientIP，并可用 sessionAffinityConfig 设超时。但要注意它基于客户端 IP，经过 NAT 后多个用户可能被当成同一个，且会影响负载均衡均匀度。

EndpointSlice 和 Endpoints 有什么区别？

Endpoints 把所有后端塞进一个对象，规模大时更新代价高；EndpointSlice 把后端切成多个（默认每片最多 100 个），更新只影响小片，显著降低了大规模服务下的控制面压力（k8s 1.21+ 默认启用）。

跨命名空间怎么访问？

用全限定域名：svc.namespace.svc.cluster.local。Service 的 selector 只能选本命名空间的 Pod，跨命名空间访问需要显式写全域名，或用 ExternalName 做一层映射。

第二层 · kube-proxy 模式与转发链路参数

模式工作方式规模上限适用
userspace转发回用户态进程很小，已基本不用仅历史版本
iptables写 iptables 规则做 DNAT规则上万条后更新变慢中小规模默认
IPVS内核哈希表 + 多种调度算法可支撑上万 Service大规模集群首选
nftables新一代包过滤框架较新版本提供逐步替代 iptables 的方向
参数 / 对象默认值说明
EndpointSlice 每片 endpoint 数100超过就自动再开一片
kube-proxy 同步周期30 s（含抖动）全量同步代价随规模增长
Service ClusterIP从 --service-cidr 分配纯三层虚拟 IP，ping 不通是正常的
conntrack 表容量依节点内存而定打满会丢包并报 table full
NodePort 端口范围30000-32767默认受限，可调整
externalTrafficPolicyCluster改 Local 可保留源 IP，但要承担跨节点转发

排查常用命令

# 看 Service 选中了哪些 Pod
kubectl get endpointslices -l kubernetes.io/service-name=my-svc -o yaml
kubectl get ep my-svc                      # 旧版 Endpoints 对象

# 看转发规则（iptables 模式）
iptables-save -t nat | grep -i my-svc
# IPVS 模式
ipvsadm -Ln | grep -A2 -i cluster-ip

# conntrack 打满的自查
cat /proc/sys/net/netfilter/nf_conntrack_count
cat /proc/sys/net/netfilter/nf_conntrack_max

第三层 · 访问不通时的排查顺序

  • 第一步：kubectl get endpointslices 看有没有 endpoint —— 为空说明 selector 没匹配到 Pod，先核对 Pod 的 label
  • 第二步：kubectl get pod --show-labels 确认 label 拼写与命名空间，Service 只能选到同命名空间的 Pod
  • 第三步：进 Pod 里直接 curl ClusterIP:port，排除 DNS 干扰
  • 第四步：curl PodIP:port 直连，能通说明问题在转发链路上
  • 第五步：看 readinessProbe —— 未就绪的 Pod 不会进 endpoint，这是最高频的坑
  • 第六步：节点上查 conntrack 与 iptables/IPVS 规则是否同步
症状原因处理
endpoint 为空label 不匹配或 Pod 未就绪修 label / 修 readinessProbe
ClusterIP 偶发超时conntrack 表满或规则未同步扩容 conntrack 或换 IPVS
能通但源 IP 不对externalTrafficPolicy=Cluster 做了 SNAT改 Local（需保证本节点有 Pod）
Headless 解析不到没用 ClusterIP=None 或 Pod 未就绪检查 Service 定义与就绪状态
跨节点不通CNI 插件或节点防火墙问题查网络插件状态与节点安全组
