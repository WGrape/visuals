解耦应用与缓存

先建立直觉：两块白板，只擦了一块

老师在前后两块白板上写了同样的内容。现在要改一个数字，他走到前面改了，但还没来得及走到后面改——这一瞬间，两块白板内容不一致。更糟的是，如果他改完前面就忘了后面，不一致就会一直持续下去。

数据库和缓存就是这两块白板。「更新数据库」和「更新缓存」是两个独立的写操作，中间存在时间窗，且任一失败都会留下不一致。这就是双写一致性问题的全部根源。

重要前提：在分布式系统里，强一致（任何时刻读到的都是最新）几乎不可能在不牺牲性能的前提下做到。工程上的目标通常是最终一致：允许短暂不一致，但要保证最终会收敛，且不一致窗口尽可能小。

四种更新策略与各自的风险

策略顺序主要风险评价
先更新缓存，再更新数据库cache → db更新数据库失败 → 缓存是新值、库是旧值，永久脏数据❌ 不推荐
先更新数据库，再更新缓存db → cache更新缓存失败 → 缓存是旧值，直到过期；并发下还可能写覆盖⚠️ 一般
先删除缓存，再更新数据库del → db删除后、更新前有新读请求 → 把旧值重新写回缓存⚠️ 有经典坑
先更新数据库，再删除缓存db → del删除缓存失败 → 短期读到旧值；并发下窗口极小✅ 推荐（Cache-Aside）

为什么推荐「先更新数据库，再删除缓存」

为什么「先更库后删」风险更小？因为要产生脏数据，需要两个极难同时满足的条件：

  1. 此刻缓存恰好已经失效（否则 B 直接读到缓存，不会查库）；
  2. B 的「查库 → 写缓存」这一小段，必须完整地落在 A 的「更新库」之前（通常只有毫秒级窗口）。

而「先删缓存」的坑只需要一次普通的并发读就会触发，条件宽松得多。

那如果删除缓存失败了？

这是「先更库后删」的主要残余风险：库更新成功，但删缓存失败 → 缓存里一直是旧值，直到 TTL 过期。

兜底手段做法效果
重试删除失败后放入重试队列，异步重试几次解决偶发网络抖动
设置较短 TTL即使删失败，旧值也会较快过期缩小不一致窗口
订阅 binlog 删除用 Canal 等中间件监听数据库变更，删除缓存解耦，且自带重试与持久化
canals/binglog 方案的关键价值在于：把「删缓存」这件事从应用代码里的一次性调用，变成一个可重试、可监控、有持久化的独立流程。即使应用重启、网络抖动，也不会丢掉删除动作。

什么时候不能用「删除」，必须「更新」

删除缓存的策略有一个隐含代价：下一次读必然 miss，要重新查库。如果写非常频繁而读也很频繁，会造成「写一次删一次，读一次查一次库」的抖动。

  • 读多写少（绝大多数场景）→ 用删除，简单可靠。
  • 写极频繁、每次写完立刻被读 → 可考虑更新缓存，但要解决并发写覆盖（加锁或版本号）。
另一个常见错误：更新缓存时的并发写覆盖。两个线程同时更新，A 先读库后写缓存、B 后读库先写缓存，最终缓存是 A 的旧值。解法：更新缓存也要保证顺序，或用分布式锁 / 版本号（CAS）。这也是「删除优于更新」的另一个理由——删除是幂等的，不存在顺序问题。

实践清单

  1. 读流程：先读缓存，命中返回；未命中查库并写入缓存（Cache-Aside）。
  2. 写流程：先更新数据库，再删除缓存。
  3. 删除失败要重试（重试队列或 binlog 订阅）。
  4. 给缓存设 TTL，作为一致性的最后兜底。
  5. 对一致性要求极高的场景（余额、库存），不要依赖缓存，直接读库或走强一致存储。

🎯 面试问答

Q：为什么「先更新缓存再更新数据库」是最差的？
A：因为一旦数据库更新失败，缓存里就是一个数据库里根本不存在的值，而且没有任何机制会自动修正它（缓存不会自己变回旧值，TTL 到期后才会重新加载）。相比之下，「先更库后删缓存」即使删除失败，最坏也只是多读一会儿旧值，TTL 一到自动恢复。判断标准：哪种失败留下的脏数据更难自愈。

Q：「删除缓存」和「更新缓存」哪个更好？
A：绝大多数情况删除更好，两个理由：① 幂等——删除一次和删除多次效果一样，不存在并发写覆盖的顺序问题；② 懒加载——删掉后如果没人读，就省了一次无谓的写。只有在「写完后立刻会被大量读取」且写操作本身不频繁时，主动更新才划算。

Q：能保证强一致吗？
A：在这种架构下很难，且代价极高（需要分布式事务或两阶段提交，会严重拖慢性能）。业界普遍接受最终一致：不一致窗口通常在毫秒到秒级，且会随下一次删除/过期自动收敛。如果业务真的要求强一致（如账户余额），正确做法通常不是「优化缓存」，而是这个数据不放缓存，直接读主库。

Q：延迟双删是什么，有必要吗？
A：延迟双删是「先删缓存 → 更新数据库 → sleep 一小会儿 → 再删一次缓存」。它的目的是清理在更新数据库期间被并发读请求写回的旧值。在「先删缓存」策略下它是有意义的补救；但在推荐的「先更库后删」策略下，脏数据产生的条件已经极苛刻，延迟双删收益很小，却要引入一次 sleep（增加写延迟），通常不值得。

四种双写方案的量化对比

方案一致性窗口风险适用
先更新 DB，再删缓存毫秒级删缓存失败 → 短期脏读（但会随 TTL 或下次删除收敛）推荐默认方案
先删缓存，再更新 DB百毫秒级删后、更新前被读 → 缓存被回填旧值，且长期不收敛不推荐（需延迟双删）
先更新缓存，再更新 DB—DB 失败则缓存是脏的且无 TTL 兜底不推荐
先更新 DB，再更新缓存毫秒级并发下更新顺序颠倒导致长期不一致不推荐（改成删除而非更新）

为什么「删缓存」优于「更新缓存」：① 更新缓存可能白做（写完没人读）；② 并发写时两个请求到达 DB 的顺序与到达缓存的顺序可能相反，导致缓存里是较旧的值且长期不修复；③ 缓存 value 常常是复杂计算结果（join 多张表），重建成本高于简单删除后按需加载。

「先删缓存再更新 DB」为何更糟：删完到 DB 提交之间有窗口，此时读请求会查到旧 DB 值并写回缓存，之后这个旧值会一直待到 TTL 过期——不像「先 DB 后删」那样有后续删除来收敛。

落地实现

# 推荐：更新 DB -> 删缓存 -> （可选）延迟双删兜底
def update_item(item_id, new_val):
    with db.transaction():
        db.execute("UPDATE items SET val=%s WHERE id=%s", new_val, item_id)
    # 删除失败也要重试，不能静默
    try:
        cache.delete(f"item:{item_id}")
    except Exception as e:
        mq.send("cache_invalidate_retry", {"key": f"item:{item_id}"})  # 走重试队列

# 延迟双删：仅用于「先删缓存」这类方案，或作为极端场景兜底
# sleep 时间要 > 一次读请求的耗时（读DB+写缓存），通常 200~500ms
cache.delete(key)
db.update(...)
time.sleep(0.3)        # 或投递一个 300ms 的延迟消息，别真的 sleep 阻塞请求
cache.delete(key)      # 清掉窗口期被回填的旧值
// 更彻底：用 binlog 订阅（Canal/Debezium）异步删缓存，业务代码不碰缓存
// 1) 业务只写 DB
// 2) Canal 伪装成 MySQL slave 读 binlog
// 3) 消费端按表名+主键拼出 cache key 并删除
// 优点：业务零侵入、保证「DB 成功就一定删」、可重试可重放
// 代价：引入中间件、有秒级延迟（通常 < 500ms）

一致性问题排查

症状原因处理
改完数据读到的还是旧值删缓存失败 / 主从延迟导致读到从库旧值删缓存加重试；读主库或等主从追平；关键业务用「写后读主」
不一致长期不恢复用了「先删缓存再更新 DB」被回填旧值，且 TTL 很长改方案；或加延迟双删；缩短 TTL 作为兜底
缓存中出现了不存在的数据缓存穿透查到空后没写入空值标记空结果也缓存（短 TTL，如 60s）+ 布隆过滤器
主从延迟导致的不一致写主读从，从库延迟几百 ms~秒读一致性敏感的请求走主库；或用「写后 N 秒内读主」
并发更新后值来回跳两个写请求乱序加版本号 / 乐观锁；或让缓存只存不可变数据
缓存与 DB 都更新成功但值不同更新缓存 + 更新 DB 双写顺序颠倒改成「更新 DB + 删除缓存」，从根上消除顺序问题
  • TTL 是最后一道保险：任何主动失效方案都可能失败，给所有缓存设 TTL（如 5~30 分钟）能保证不一致有上界。
  • 强一致需求（余额、库存）：不要靠删缓存，改用「DB 事务内扣减 + 读时直接查 DB」，或用分布式锁串行化。
