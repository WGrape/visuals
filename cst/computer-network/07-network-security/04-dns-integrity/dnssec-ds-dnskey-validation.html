DNSSEC 验证链：RRSIG、DNSKEY 与 DS 怎样防止假答案

从根域到业务域手推信任链，并解释 SERVFAIL、密钥轮换和不加密的边界。

要防的是被伪造的解析结果

DNS 查询可能经过递归解析器和网络路径，攻击者若能让客户端接受假的 A 记录，就可能把用户导向错误地址。DNSSEC 让区域的权威数据附带数字签名，验证解析器可检查数据来源和完整性，拒绝无法通过信任链验证的答案。它不加密查询名称，旁观者仍可能看到传统 DNS 流量；若要保护客户端到解析器的通道，还需 DoT/DoH 等机制。

DNSSEC 也不证明网站内容可信或 TLS 证书正确。它只能确认 DNS 数据与已签名区域的授权链一致。域名被合法管理员错误配置成恶意 IP，签名仍可能有效；应用仍要验证 HTTPS 证书和业务身份。

三种记录各做什么

DNSKEY 公布区域用于验证签名的公钥；RRSIG 对具体记录集提供签名；父区域里的 DS 记录把对子区域关键 DNSKEY 的摘要纳入父级签名体系。验证解析器从已知的根信任锚出发，检查根到顶级域、顶级域到业务域的 DS/DNSKEY 关系，再验证目标 A 或 AAAA 记录集的 RRSIG。只有链条连续、签名和有效期正确，才可称该答案被验证。

不能只在业务域放一把 DNSKEY 就宣布全网会信任它。若父区域没有相应 DS，验证链可能止于父级，子区域可能被视为未签名而非已验证；若父级 DS 指向旧密钥而子区域已换新，验证会失败。部署时必须协调注册商或父区的 DS 更新。

逐步推演

建立信任锚

验证解析器信任根区域的公钥。

检查 DS

父区签名的 DS 指向子区 DNSKEY。

验证 RRSIG

用 DNSKEY 检查目标记录集签名。

给出结果

有效则返回；断链或过期则拒绝。

一次假 A 记录的尝试

攻击者向验证解析器注入 `api.example.test A 203.0.113.66`，却没有该记录集对应的有效 RRSIG。解析器从信任链找到业务域 DNSKEY 后，签名校验不通过，拒绝把假答案作为有效结果返回。若客户端使用不验证的解析器，它可能仍受缓存投毒或其他伪造影响；因此要确认实际递归解析器确实开启验证。

DNSSEC 可认证不存在记录的否定回答，常通过 NSEC/NSEC3 等记录证明某个名字或类型不存在，防止攻击者随意伪造 NXDOMAIN。否定证明具体实现较复杂，但排障至少要区分“被验证的不存在”和“签名链坏了导致 SERVFAIL”。

为什么会出现 SERVFAIL

验证解析器若看到签名过期、签名尚未生效、DS 与 DNSKEY 不匹配、必要 DNSKEY 或 RRSIG 记录缺失，可能返回 SERVFAIL，而不是给出被认为不可信的答案。没有验证的解析器可能仍返回 A 记录，造成“某些网络能访问、某些网络不行”。此时不能简单关掉验证，先对比权威记录、父区 DS、系统时间和签名有效期。

时间错误尤其隐蔽：签名有生效与到期时间，权威服务器或验证解析器时钟异常都可能引发失败。大 DNSSEC 应答还可能触发 UDP 截断与 TCP 回退，因此需要确保 DNS TCP 通路可用。

密钥轮换与撤销

轮换密钥需要给缓存传播和父区 DS 更新留重叠窗口。若先删除旧 DNSKEY、旧 DS 仍被递归解析器缓存，会形成断链；若新 DS 已发布而子区尚未提供新密钥，也会失败。应规划发布、等待缓存、切换签名、更新 DS、观察验证成功率，再移除旧材料的顺序。具体 KSK/ZSK 策略依 DNS 平台而异，不能只在一个控制台点击“更新”就认为全链完成。

私钥应严密保护，DNSKEY 公钥则可公开。若签名私钥泄漏，需要按既定轮换和事件响应流程处理；继续使用被盗密钥会让攻击者伪造看似合法的记录。

如何验证与验收

从权威服务器查目标记录、RRSIG、DNSKEY，并从父区查 DS；再用开启验证的递归解析器查询目标名称。分别测试正常存在、无记录、密钥轮换期间和故意错误的测试区域，记录结果是可验证、不安全但可解析，还是验证失败。浏览器网页能打开只证明某条解析与 HTTPS 路径工作，不证明 DNSSEC 已开启。

运行监控应看签名到期、父区 DS 匹配、验证失败率与权威查询时延。把 DNSSEC、DoH/DoT 和 TLS 放在一张信任边界图里，才能说明每一段保护了什么。

DNSSEC 记录与信任链

记录作用位置
RRSIG对一组记录的数字签名与被签记录同区
DNSKEY区的公钥（ZSK + KSK）区自身
DS子区公钥的哈希摘要，由父区签名父区（形成信任链）
NSEC / NSEC3证明某个名字不存在（防伪造 NXDOMAIN）区自身
CDS / CDNSKEY子区向父区提交 DS 更新子区
密钥用途常见算法
KSK（密钥签名密钥）只签 DNSKEY 集合，其哈希进父区 DS算法 8（RSA/SHA-256）、13（ECDSA P-256）
ZSK（区签名密钥）签区内所有其它记录同上，可更频繁轮换

信任链（Chain of Trust）：根区（预置信任锚）→ 用根的 DS 验证 com. 的 DNSKEY → 用 com 的 DS 验证 example.com. 的 DNSKEY → 用 example.com 的 ZSK 验证 A 记录的 RRSIG。每一跳的 DS 都在父区，所以篡改子区签名会被父区的 DS 校验发现。

DNSSEC 验证命令

# 查看 DNSSEC 记录
dig example.com DNSKEY +multiline
dig example.com DS +short
dig example.com A +dnssec          # 看返回的 RRSIG
dig com DS +short                  # 父区的 DS

# 验证（delv 是最好的工具）
delv example.com A
delv +vtrace example.com A         # 显示完整信任链验证过程
delv +root=example.com @8.8.8.8 example.com A

# 用 dig 手动跟踪（看每一级是否有 ad 标志）
dig +trace +dnssec example.com

# 关键标志位
#   flags: ... ad   → Authentic Data，验证成功（由递归服务器返回）
#   flags: ... do   → DNSSEC OK，客户端请求了 DNSSEC
#   没有 ad 且返回 SERVFAIL → 验证失败！

# 验证失败时看 RRSIG 有效期（时间不同步会导致验证失败）
dig example.com A +dnssec | grep -A2 RRSIG

部署与常见故障

  • 验证失败的头号原因是时钟不同步：RRSIG 有明确的有效期（inception/expiration），验证方时钟偏差大会判定签名“尚未生效”或“已过期”，直接返回 SERVFAIL。必须先保证 NTP 正常。
  • SERVFAIL 是 DNSSEC 失败的典型表现：普通解析失败是 NXDOMAIN（正常的不存在），而签名验证失败是 SERVFAIL。看到大量 SERVFAIL 优先怀疑 DNSSEC。
  • 响应变大 → 触发分片与放大：DNSSEC 让响应从几十字节涨到几 KB（含 RRSIG、DNSKEY），容易超过 512 字节 → 需要 EDNS0 / TCP；同时放大倍数上升（约 8–50 倍），被用于 DDoS 反射攻击。
  • NSEC 的“区枚举”问题：NSEC 会列出所有存在的名字，等于把整个区公开（zone walking）。NSEC3 用哈希解决（但仍可能被暴力枚举，需用高迭代次数 + 加盐）。
  • 密钥轮换流程：先发布新密钥 → 等旧 TTL 过期 → 用新密钥签名 → 更新父区 DS → 等父区 DS 的 TTL → 撤销旧密钥。顺序错了会导致全网验证失败（这是 DNSSEC 部署事故的主要来源）。建议用自动化工具（如 dnssec-signzone、CDS/CDNSKEY 自动提交）。
  • 排障顺序：① delv 看具体哪一级失败；② 查 RRSIG 有效期与本机时钟；③ dig +trace +dnssec 逐级验证 DS/DNSKEY 是否匹配；④ 检查父区 DS 是否与实际 DNSKEY 一致（密钥轮换后最容易不一致）。
DNSSEC 能加密 DNS 查询吗？

不能。它只提供完整性与来源认证（证明数据没被篡改、确实来自权威服务器），不提供机密性——查询内容仍是明文。要防窃听需要 DoT/DoH。两者互补，常一起部署。

为什么有些 DNSSEC 验证失败只影响部分地区？

通常是缓存与 TTL 问题：旧的 DS/DNSKEY 还在某些递归服务器的缓存里，而权威已经轮换。等 TTL 过期即可恢复，也说明轮换时等待时间不足。

自检

DoH 已加密，为什么还可能需要 DNSSEC？

DoH 保护客户端到解析器的传输；DNSSEC 验证权威数据的签名链，解决的是不同信任边界。
