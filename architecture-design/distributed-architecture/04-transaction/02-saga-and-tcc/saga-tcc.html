分布式事务：TCC 与 Saga 全解析

预留-确认-释放 vs 正向提交-反向补偿，一次讲清选型与三大坑

一、为什么 2PC 不够用

单体库里一条 BEGIN ... COMMIT 就能保证原子性。拆成微服务后，订单、库存、支付各在自己的库，本地事务管不到别人。经典 2PC（XA）能解决，但它在整个准备阶段都占着锁，协调者宕机还会让参与者悬挂，在高并发长链路下吞吐极差。于是有了两条柔性路线：TCC 与 Saga。

2PC / XA
强一致、同步阻塞
准备阶段全程持锁，协调者单点风险
适用：短事务、低并发、同机房
TCC
Try-Confirm-Cancel
业务侵入大，但一致性强、可控
适用：金融、交易核心
Saga
正向 + 反向补偿
一阶段就提交，靠补偿回滚
适用：长流程、跨企业、可接受最终一致
本地消息表 / Outbox
发消息与本地事务同库
实现简单，只能保证「最终通知到」
适用：大部分异步场景

二、TCC：把一件事拆成三步

TCC 要求每个参与者自己实现三个方法：Try 预留资源、Confirm 确认扣减、Cancel 释放预留。注意 Try 阶段不真正扣减，只是冻结额度。

// 参与者接口（伪代码，Go 风格） type TccAction interface { Try(ctx, bizID string, amount int) error // 预留：UPDATE stock SET frozen=frozen+? WHERE id=? AND avail>=? Confirm(ctx, bizID string) error // 确认：UPDATE stock SET avail=avail-?, frozen=frozen-? Cancel(ctx, bizID string) error // 释放：UPDATE stock SET frozen=frozen-? } // 协调者：只有所有 Try 都成功才 Confirm，否则对成功者逐个 Cancel func (c *Coord) Run(ctx context.Context, branches []TccAction, bizID string) error { done := make([]TccAction, 0, len(branches)) for _, b := range branches { if err := b.Try(ctx, bizID, 1); err != nil { for _, d := range done { _ = d.Cancel(ctx, bizID) } // 反向补偿 return err } done = append(done, b) } for _, d := range done { if err := d.Confirm(ctx, bizID); err != nil { return err } // Confirm 失败需重试到底 } return nil }

Try 阶段为什么用「冻结」而不是「扣减」

因为 Try 后事务还没定，不能真的动余额。冻结相当于给这笔业务「占位」，其他并发业务看到可用量已经减少，但账还没真正动 —— Confirm 时才落账。

三、TCC 的三大坑：空回滚、幂等、悬挂

问题怎么发生的后果标准解法
空回滚Try 还没执行（网络丢包/超时），Cancel 先到了Cancel 找不到预留记录，误判成功或直接报错Cancel 时若无预留记录，插入一条空的回滚记录再返回成功
幂等网络重试导致 Confirm/Cancel 被调用多次重复扣减或重复解冻用 bizID + 分支号做唯一键或状态机，重复调用直接返回上次结果
悬挂Cancel 先到并完成，迟到的 Try 才执行资源被永久冻结，没人再解冻Try 前检查是否已有该 bizID 的回滚记录，有则直接放弃

这三条是 TCC 的必修课

只要自己写 TCC，就必须同时处理这三个异常，缺一个都会在故障演练时暴露。成熟框架（Seata、Hmily、ByteTCC）已经内置了这几条，自研前先想清楚。

四、Saga：一阶段提交 + 反向补偿

Saga 把长事务拆成一串本地短事务，每个都有对应的补偿动作。和 TCC 最大的不同是：Saga 的正向操作会立即提交，所以中间状态对外可见（这就是「最终一致」里的「中间不一致」）。

维度TCCSaga
一阶段是否提交否（Try 只预留）是（正向操作真实生效）
隔离性较好（预留即占位）无隔离，中间态可见（需语义锁/状态机兜底）
业务侵入高：每个服务要实现三个方法中：每个服务要实现一个补偿动作
补偿难度Cancel 只需解冻，逻辑简单补偿可能失败，需要重试与人工兜底
适用场景资金、交易、强一致订票、审批、跨企业长流程
典型时长秒级秒到天级

五、编排 vs 协同：谁来驱动

编排 Orchestration

有一个协调者按流程逐个调用服务并负责补偿。流程集中可见、易改易观测；缺点是协调者可能变成「上帝服务」。

协同 Choreography

每个服务订阅上一步的事件自行推进，失败时发反向事件。耦合低、扩展性好；缺点是流程散落在各处，出问题难还原全貌。

选型建议

流程步骤 ≤ 5、需要强管控的用编排（推荐用状态机/工作流引擎）；步骤多、参与方跨团队的用协同，但一定要配链路追踪 + 全局流程 ID，否则排查会非常痛苦。

六、补偿设计四条原则

  1. 补偿必须幂等：网络重试是常态，补偿动作要能重复执行而不出错。
  2. 补偿要能「重入」：如果补偿本身失败，要有重试队列 + 最大次数 + 告警人工介入，不能静默丢弃。
  3. 补偿不一定要恢复原值：比如已发出的短信无法收回，补偿可以是「发一条更正通知」+ 标记状态。
  4. 补偿顺序按业务定：通常逆序，但涉及资金时优先退钱，避免用户资金长时间被占用。

七、深入自检

TCC 和 Saga 到底选哪个？

看两件事：能不能接受中间态、补偿好不好写。资金类业务中间态不可接受（用户能看到余额少了但订单没成），选 TCC；订票/审批这类长流程，补偿好写且中间态可接受，选 Saga。

Saga 没有隔离性会出什么问题？

典型是脏写覆盖：Saga A 扣了库存还没提交，Saga B 读到旧值也扣了，最后超卖。缓解手段：① 在业务层加语义锁（把记录标记为「处理中」）；② 用状态机让并发操作被拒绝；③ 补偿时做余额校验而非简单加回。

Confirm 阶段失败了怎么办？

Confirm 失败不能回滚（其他分支可能已确认），只能重试到底：同步重试 + 异步任务兜底 + 超过阈值告警。所以 Confirm 必须幂等且逻辑极简。

有了消息队列是不是就不需要 Saga/TCC 了？

消息队列解决的是「通知可靠到达」，不解决「业务原子性」。本地消息表/Outbox + MQ 能覆盖大多数最终一致场景，且实现最轻；只有需要「要么全成要么全撤」时才上 TCC/Saga。

分布式事务会不会严重影响性能？

会。TCC 多两次网络往返 + 预留记录写入；Saga 多了补偿分支。经验上核心链路耗时增加 2~5 倍。所以原则是能不用就不用：先考虑能不能把相关服务合并、或用异步最终一致代替。

Saga 与 TCC 的对比

维度SagaTCC
阶段一阶段提交 + 补偿（反向操作）Try - Confirm / Cancel 两阶段
隔离性无隔离（中间状态可见）Try 阶段预留资源，有弱隔离
侵入性低（只需写补偿逻辑）高（每个操作要拆成三个方法）
业务改造小大（要支持资源预留）
一致性最终一致；可能脏读最终一致；预留期间不会被别人用
适用场景长流程、无法预留资源的金融、库存等需要资源隔离的
失败处理按正向顺序的逆序执行补偿调用各分支的 Cancel
关键设计点说明注意
补偿必须幂等可能被重试多次用事务编号去重
补偿必须能成功「允许空补偿」没做过 Try 也要能 Cancel 成功
防悬挂Cancel 不能比 Try 先到记录事务状态，Cancel 时发现没 Try 就记下，后续 Try 直接拒绝
幂等控制全局事务 ID + 分支 ID唯一索引防重复提交
超时时间Try 阶段要设超时超时后自动 Cancel，防资源长期占用

Saga 最大的问题是「无隔离」：比如「下单 → 扣库存 → 扣余额」，如果扣库存成功后扣余额失败，会执行「返还库存」补偿；但在补偿完成前，其他用户能看到库存已被扣减（脏读）。TCC 用 Try 阶段预留（冻结而非真正扣减）来解决这个问题，代价是每个服务都要写三个方法，改造量很大。

实现代码

// TCC 的三个方法（以扣库存为例）
// Try：预留（冻结库存，不真正扣减）
func (s *StockService) Try(ctx context.Context, txID string, itemID int64, n int) error {
    // 幂等：同一 txID 重复调用直接返回成功
    if s.isDone(txID, "try") { return nil }
    // 检查是否 Cancel 过（防悬挂）
    if s.isCancelled(txID) { return ErrCancelled }

    _, err := db.ExecContext(ctx, `
        UPDATE stock SET frozen = frozen + ?, available = available - ?
        WHERE item_id = ? AND available >= ?`, n, n, itemID, n)
    if err != nil { return err }
    // affected rows = 0 表示库存不足，Try 失败
    return s.markDone(txID, "try")
}

// Confirm：真正扣减（释放冻结）
func (s *StockService) Confirm(ctx context.Context, txID string, itemID int64, n int) error {
    if s.isDone(txID, "confirm") { return nil }        // 幂等
    _, err := db.ExecContext(ctx, `
        UPDATE stock SET frozen = frozen - ?, total = total - ?
        WHERE item_id = ? AND frozen >= ?`, n, n, itemID, n)
    return err
}

// Cancel：释放预留
func (s *StockService) Cancel(ctx context.Context, txID string, itemID int64, n int) error {
    if s.isDone(txID, "cancel") { return nil }         // 幂等
    // 允许空补偿：即使没 Try 过，也不报错（但要记录）
    _, err := db.ExecContext(ctx, `
        UPDATE stock SET frozen = frozen - ?, available = available + ?
        WHERE item_id = ? AND frozen >= ?`, n, n, itemID, n)
    return err
}
# Saga 编排（Orchestration）示例
class SagaOrchestrator:
    def execute(self, tx_id, steps):
        """steps: [(do_fn, compensate_fn, args), ...]"""
        done = []
        try:
            for do_fn, _, args in steps:
                do_fn(tx_id, *args)
                done.append((do_fn, _, args))
            self.confirm_all(tx_id)          # 全部成功
        except Exception as e:
            # 逆序补偿
            for do_fn, comp_fn, args in reversed(done):
                for attempt in range(3):     # 补偿必须重试到成功
                    try:
                        comp_fn(tx_id, *args)
                        break
                    except Exception:
                        time.sleep(0.1 * (attempt + 1))
                else:
                    # 补偿彻底失败 -> 必须告警，人工介入
                    alert(f"saga compensate failed: tx={tx_id}")
            raise

# 关键：补偿失败不能静默！必须进入「人工处理队列」
# 生产系统要有对账任务，定期扫描长时间未完成的事务

TCC 的三个必须：① Try/Confirm/Cancel 都要幂等；② Cancel 要允许空补偿（没 Try 也能成功）；③ 要防悬挂。这三条是 TCC 落地的硬性要求，缺一个就会在异常时序下出错。
