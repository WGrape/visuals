🍪 模板方法

固定算法骨架，把少数步骤留给子类定制。

一句话记住烘焙流程先和面、再烘烤、最后装盘；不同面包替换配方细节。

01 · 从问题出发

为什么会需要这个模式？

CSV 和 JSON 导入都要打开文件、解析、校验、保存；复制整个流程会让关键顺序漂移。

CSV 与 JSON 导入都要打开文件、解析、验证、保存和关闭。若复制两份完整流程，JSON 版本可能忘记关闭流，CSV 版本可能跳过校验；公共约束逐渐漂移。

😵 直接写会怎样

function importCsv(file): open(); parseCsv(); validate(); save(); close()
function importJson(file): open(); parseJson(); save(); close()
// JSON 分支忘记 validate

💡 关键转折

父类定义不可随意改的流程，子类实现差异步骤。

在父类固定步骤顺序与资源清理，只把 parse 留给子类覆盖。公共流程只维护一份。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

abstract class Importer {
  import(file) {
    stream = open(file)
    try {
      rows = this.parse(stream)  // 子类实现
      validate(rows)
      save(rows)
    } finally { stream.close() }
  }
  abstract parse(stream)
}
class CsvImporter extends Importer { parse(s) { return readCsv(s) } }

读代码时抓住三件事

  1. 模板入口固定整体算法顺序。
  2. 钩子方法 parse 是明确的扩展点。
  3. finally 保证正常和异常路径都释放资源。

换个业务场景，还能认出来吗？

测试框架的 setUp → test → tearDown 是模板方法的另一种形式：子类提供具体测试动作，框架保留生命周期顺序。变化点过多时，组合策略通常比继承更清楚。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

总体流程固定，仅少数步骤因类型不同

三个具体场景

  • CSV/JSON 导入共用打开、校验与保存
  • 测试框架固定 setUp/test/tearDown
  • 构建流程固定打包、检查和发布顺序

不适合或要小心

继承会让子类与父类耦合；变化维度多时可用组合和策略。不要让子类重写整个模板入口破坏约束。

继承耦合较强；变化维度多时更适合组合策略

最容易混淆的相邻模式

模式真正的区别
策略通过组合替换算法对象；模板方法通过继承覆盖少数步骤。
建造者分步骤构造一个对象；模板方法固定一段处理算法的执行顺序。

区分时问自己：是固定流程中替换少数步骤，还是自由替换一套算法？

落地前检查

  • 模板方法避免被子类整体重写。
  • 测试所有子类都遵守公共校验与清理。
  • 只开放真正需要变化的钩子，减少继承耦合。
06 · 自己说一遍

两道检验理解的小题

为什么 close() 放在父类模板中？

资源释放是所有导入都必须遵守的共同步骤，放父类能防遗漏。

为什么把 close 放入 finally 而不是 parse 后面？

parse 或 validate 抛错时，finally 仍会执行，避免资源泄漏。
