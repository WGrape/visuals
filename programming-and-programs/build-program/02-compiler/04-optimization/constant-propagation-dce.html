常量传播与死代码删除：编译优化如何保持语义

在一个小型中间表示上逐步计算常量、折叠分支，并辨认哪些代码绝不能删除。

优化的输入是有语义的程序

常量传播利用已知值替换变量，例如 x=2; y=x+3 可推出 y=5；常量折叠再把可计算表达式化简。若条件 if y>4 在当前路径恒真，可以删去不可能执行的另一分支。死代码删除则移除结果永远不会被使用、且没有可观察副作用的计算。关键限定是“没有可观察副作用”：写文件、抛异常、修改共享状态和可能陷入无限循环的操作，不能只因返回值无人读取就随意移走。

编译器常在控制流图和 SSA 等中间表示上完成这些分析。SSA 中每个变量版本只赋值一次，使定义到使用的关系更清晰；分支汇合点的 φ 值可能来自不同路径，只有能证明所有可达路径都相同，才能把它当常量。优化是基于程序语义的证明，不是文本替换。

逐步推演

建立数据流

在控制流图中找变量定义、使用与路径汇合。

传播常量

把能证明恒定的值送到使用点，折叠表达式。

删无效路径

条件恒定时移除不可达分支，再检查无用定义。

验证语义

比较副作用、异常、终止行为和数值边界。

手算一段代码的优化结果

考虑 x=2; y=x+3; if (y>4) { z=y*2 } else { z=99 }; return z。在不考虑异常与特殊数值语义的简化整数模型中，可传播 x=2、得到 y=5，条件为真，保留 z=10，最终返回 10。未执行的 else 分支可删除；x、y、z 的中间赋值若不再有调试或其他可观察要求，也可能被继续消除。实际语言对整数溢出、异常和调试信息有具体规定，不能把这个玩具推导无条件套给所有语言。

阶段已知事实允许的变换
传播x=2把 y=x+3 变为 y=2+3
折叠y=5把 y>4 变为真
删不可达分支条件恒真删除 else 路径
删无用定义最终只返回 10移除无副作用的中间计算

别名与副作用让推理变难

若把常量存入内存位置 *p=2，随后调用未知函数，编译器不一定能证明函数没有通过别名改写该位置。于是再读 *p 时不能安全地当作 2。类似地，一个看似无人使用的函数调用可能写日志、发网络请求、修改全局变量或抛异常，死代码删除不能只看返回值是否用到。语言内存模型、调用约定和优化级别决定编译器能证明哪些性质。

优化次序也会互相促进：常量传播使分支变为恒真，删分支又让变量定义变成无用，下一轮死代码删除可继续简化；迭代到不再变化可得到更充分结果。但激进优化会增加编译耗时和代码体积，也可能影响调试体验，不代表所有级别都应该启用全部变换。

验证优化正确性

  1. 为每个变换写清前提：值恒定、路径可达性、无副作用、数值语义可保持。
  2. 用差分测试比较优化前后的输出、异常、外部写入与终止行为。
  3. 加入分支汇合、指针别名、函数调用、整数边界和浮点特殊值用例。
  4. 对性能同时测运行时间、编译时间和目标代码大小，避免“更短的 IR”被误当成整体更快。

练习：unused = sendEmail() 的变量从未被读取，为什么不能把这一行删掉？若函数改为纯函数 square(3)，哪些信息足以证明可以删除？

用抽象值表示“已知”和“未知”

编译器在分析每个变量时可以使用一个简单抽象域：尚未到达定义、确定常量 c、或值不确定。沿直线代码传播时，常量可一路传下去；两条分支汇合若分别给出 2 和 3，结果就不再是同一个常量，不能把后续使用替换成 2。若两个分支都给出 2，则可以继续传播。这个“在控制流汇合处合并事实”的步骤解释了为什么优化器需要数据流分析，而不仅是对每行代码做局部替换。

数值语义也限定优化。整数溢出在不同语言中可能回绕、抛错或具有未定义行为；浮点加法还涉及 NaN、无穷大和舍入误差，不能无条件把代数恒等式当作机器运算恒等式。即使某表达式结果无人使用，它若可能抛错或终止进程，也未必是死代码。一个可靠的优化 pass 会清楚声明前提，并通过 IR 验证器、边界测试和优化前后差分测试守住语义。

差分测试

让同一组输入分别运行未优化与优化后的程序，比较返回值、异常、日志和外部状态。对浮点 NaN、整数边界、分支汇合、别名写入和可能抛错的调用单独建例。只比较最终数值而忽略副作用，会漏掉错误优化。

优化 pass 的顺序可影响结果：传播常量后需要重新分析可达性，删去分支后又会出现新的无用定义。迭代到稳定时还应限制编译时间成本。

自检

常量传播和死代码删除为什么经常反复执行？

传播会暴露恒定分支，删分支又产生新的无用定义，下一轮可以继续简化。

变量的值无人使用，是否足以删除其定义语句？

不足以。定义语句可能有外部副作用、异常或其他可观察行为。
