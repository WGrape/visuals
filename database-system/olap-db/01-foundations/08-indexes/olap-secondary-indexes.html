一句话总结：排序键（主键）只能按前缀裁剪；二级索引用更轻量的结构，把"这一块里有没有我要的数据"回答到单个 granule/数据块级别。

01为什么排序键不够

列存表通常有一个排序键 / 主键（如按时间）。查询带时间范围时能高效裁剪；但查询条件是非前缀列（如 WHERE user_id = 123），排序键就帮不上忙——只能全分区扫描。二级索引就是为这种"非排序键过滤"场景补的轻量结构。

02跳数索引（Data Skipping）

跳数索引不给每行建条目，而是给每个数据块（granule / 行组）存一个摘要，查询时先读摘要，整块整块地跳过无关数据。

📊 minmax

每块存列的最大/最小值。范围查询 dt BETWEEN a AND b 时，块的 [min,max] 与查询区间无交集就整块跳过。最便宜，适合有序/时间列。

🌫️ bloom filter

每块存一个布隆过滤器，回答"这个值可能在 / 一定不在"。等值或 IN 查询时跳过确定不含的块。有误判但不漏。

🧮 set / token

记录块内出现的离散值集合（低基数列），或按 token 建摘要，用于枚举/包含判断。

minmax 摘要让 75% 的数据块免于读取

03Bitmap 索引

对低基数列（如性别、城市、状态、枚举），Bitmap 索引给每个不同值维护一个位图：第 i 位为 1 表示第 i 行属于该值。多个条件的 AND/OR 直接做位运算，极快。

维度说明
适用基数低（几十到几千个值）；高基数会让位图数量爆炸、存储膨胀
优势多条件交集/并集用位与/或，比回表过滤快几个数量级
代价写入时要更新位图；高基数列退化成"每行一个位图"反而更慢更大
进阶Roaring Bitmap 压缩位图，是 COUNT(DISTINCT) 精确去重的基础

04倒排索引

倒排索引是"值 → 行号列表"的映射，适合文本搜索、多值字段、ARRAY 包含查询（如 tags CONTAINS 'ai'）。它不关心列是否有序，靠 token 分词建立 term→doc 的列表。

与跳数索引的区别：倒排能精确定位到行（或行组），而跳数索引只能到"块"级别做排除；倒排对包含/模糊匹配友好，跳数索引对范围/等值排除友好。

05选择矩阵

查询类型列基数首选索引
范围过滤（时间/数值）任意排序键 + minmax 跳数
等值 / IN（非排序键）中低bloom 跳数索引
多条件 AND/OR 过滤低bitmap 索引
文本 / 包含 / ARRAY任意倒排索引

06代价与坑

✍️ 写入放大

每行写入要同步更新索引结构，写入吞吐会下降；ClickHouse 等常在后台合并（merge）时重建跳数索引，避免逐行维护。

💾 存储开销

索引要占空间，尤其是 bitmap 高基数、倒排大数据集。

🔄 合并一致性

数据块被合并（compaction）后，块级摘要必须随新块重建，否则索引失效。

07常见疑问

跳数索引会漏数据吗？
minmax 和 set 是确定的（不漏）；bloom 有"假阳性"——可能误判某块含数据而去读它，但绝不会漏掉真正含数据的块。所以 bloom 只会多读、不会少读。
bitmap 为什么怕高基数列？
每个不同值一个位图，若列有上百万个不同值，就要维护上百万个位图，存储和构建成本爆炸，且位图变得稀疏、位运算收益消失。
排序键和跳数索引怎么配合？
排序键负责"大粒度、前缀"的裁剪（最便宜），跳数索引负责"非前缀列、块级"的精细排除。两者叠加，能同时压低扫描的分区数和块数。

引擎落地对照

为什么"建索引"前先确认排序键？

很多"加索引提速"的需求，其实用对排序键（让高频过滤列成为前缀）就能解决，零写入成本。只有过滤列无法成为排序前缀时，才需要二级索引。盲目加索引只会拖慢写入、增加存储。

深度补充：OLAP 二级索引（跳数 / Bitmap / 倒排）

第一层 · 概念与判定 OLAP 列存下二级索引用于跳过无关 granule，典型三类：跳数索引（min/max、set、bloom）、Bitmap（高基数列等值/集合）、倒排（文本/多值）。判定：按查询谓词形态选型。

索引适合谓词代价
跳数（min/max/bloom）范围 / 存在性小、写入友好
Bitmap等值 / IN / 集合并交高基数列友好
倒排文本 / 多值包含写入与空间大
主键序前缀范围免费，靠排序

第三层 · 排障与边界

  • Bitmap 在低基数列上膨胀，反而慢于扫描。
  • 跳数索引粒度（granule）太粗，跳过率低。
  • 倒排对大文本写入放大明显，需控制文档量。
  • 索引建错列（查询从不谓词）纯浪费写入与空间。
第四层 · 原理与取舍

二级索引用“额外结构 + 写入成本”换查询时跳过数据块，代价是写入放大与存储。列存本身靠排序（主键序）就免去部分索引需求，跳数索引几乎免费所以首选；Bitmap 在高基数列的等值过滤上极快但占空间；倒排为文本多值而生。权衡是“查询加速 vs 写入/存储开销”，按真实谓词分布选型，避免为低频查询付费。

实例与速查：OLAP 二级索引

-- ClickHouse 跳数索引（granule 级 min/max，写入友好）
CREATE TABLE logs (ts DateTime, level String, msg String)
ENGINE = MergeTree ORDER BY (level, ts)
SETTINGS index_granularity = 8192;

-- Bitmap 索引常用于高基数列的等值/集合过滤（如 ClickHouse 的 groupBitmap）
SELECT groupBitmap(user_id) FROM events WHERE day = '2026-10-27';

-- 倒排用于文本/多值包含，写入与空间成本大
  • Bitmap 在低基数列上会膨胀，反而慢于直接扫描。
  • 跳数索引粒度（granule）太粗，跳过率低，可调整 index_granularity。
  • 索引建在查询从不谓词的列上纯浪费写入与空间。
FAQ：列存还需要二级索引吗？

需要，但优先级不同。列存靠“主键排序”已能服务前缀范围查询（免费）；二级索引用来服务非前缀谓词：跳数索引几乎免费、首选；Bitmap 适合高基数列的等值/集合；倒排为文本多值而生。按真实谓词分布选型，避免为低频查询付费。

常见误区与延伸

  • 误区一：OLAP 也要像 OLTP 那样建很多二级索引。列存靠排序已服务前缀查询，乱建索引只增写入。
  • 误区二：Bitmap 一定快。低基数列上 Bitmap 会膨胀，反而慢于扫描。
  • 延伸：跳数索引几乎免费，是首选；倒排为文本/多值而生，写入与空间成本大。
  • 延伸：物化视图/投影（projection）是列存另一类“预计算索引”，适合固定聚合模式。

一句话总结：OLAP 二级索引按真实谓词形态选型，跳数首选、Bitmap 管高基等值、倒排管文本，避免为低频查询付费。

决策速记

  • 首选跳数：几乎免费，服务非前缀谓词。
  • 高基等值用 Bitmap：低基数列上会膨胀反而慢。
  • 文本多值用倒排：写入与空间成本大，按需。
  • 别乱建：索引建在从不谓词的列上纯浪费。

一句话：OLAP 二级索引按谓词形态选型，避免为低频查询付费。

横向对比与追问

  • 与 OLTP 二级索引比：OLTP 的 B+Tree 索引几乎必建，OLAP 列存靠排序已服务前缀查询。
  • 与物化视图比：二级索引是“加速谓词”，物化视图是“预计算聚合”，层次不同。
  • 追问：为什么 Bitmap 在高基数列才高效？低基数列 Bitmap 基数低、位数组长反而膨胀。
  • 追问：跳数索引为什么不免费到零成本？它仍要随写入维护 granule 的 min/max。

小结：OLAP 索引按谓词形态选，跳数首选、Bitmap 管高基、倒排管文本。
