先确认是不是真上涨

别把缓存当成泄漏

内存「持续单调上涨、不回落」才可疑。很多上涨是正常的：缓存预热、连接池增长、批处理堆积。先拉长观察窗口、看是否触及上限后平台化。

区分三件事：内存泄漏（该释放的没释放）、缓存无上限（设计问题）、周期性波动（正常）。

问题 1
内存持续上涨怎么排查？

先拉长窗口确认是「单调不回落」而非正常波动或缓存预热；再用对应工具的堆/内存快照，对比加压前后的差异，找出只增不减的对象类型与引用链；顺着引用根（全局缓存、单例、闭包）定位到具体代码。最后修复并验证内存曲线走平。

问题 2
如何区分内存泄漏和正常增长？

看是否「到顶后平台化」：缓存、连接池增长到上限会稳定；泄漏是持续单调上升、GC/回收后也不回落。对比多次快照，若某类对象只增不减且没有对应业务合理持有，就是泄漏。

问题 3
堆看起来正常但进程内存还在涨？

那大概率是 native 内存：直接内存/堆外缓冲、JNI、压缩库、或 glibc 内存池没归还操作系统。需要查直接缓冲用量、第三方 native 库，以及用 pmap/smem 看 RSS 构成。

问题 4
Go 里怎么快速定位内存泄漏？

用 pprof 的 heap profile，在问题前后各取一份，用 pprof -base 做差，直接看到增长的对象类型与分配栈；常见元凶是全局 map 不删、goroutine 泄漏持有引用、或 ticker/channel 未关闭。

排查流程

① 确认是否真的泄漏

  • 多次采样 RSS / 堆占用（间隔数小时）。
  • 观察 Full GC 后老年代是否回落。
  • 区分「泄漏」与「缓存 warm up 的正常增长」。
  • 看是否在压测/大促后才出现。

② 判断泄漏位置

  • 堆：堆转储（jmap/heapdump）分析。
  • 堆外：pmap -x 对比、NMT、检查 DirectBuffer。
  • 线程：线程数 × 栈大小，看线程 dump。
  • 句柄：lsof / /proc/PID/fd 数量。

③ 分析堆转储

  • 按「保留大小 Retained Size」排序找大对象。
  • 看 GC Root 到该对象的引用链（谁在持有）。
  • 对比两次转储，看增长最快的类型。
  • 常见结论：某个静态 Map 或缓存持有了全部对象。

④ 修复与验证

  • 加上限与淘汰策略（容量、TTL）。
  • 显式注销监听器、remove ThreadLocal、关闭资源。
  • 修复后长跑验证（8 小时以上）看曲线是否平稳。
  • 加监控：RSS、堆、线程数、缓存大小的趋势告警。

深入自检

RSS 一直涨，但堆转储看不出问题，为什么？

泄漏不在堆里。常见是：堆外内存（DirectByteBuffer、JNI、压缩库）、mmap 映射、线程栈（线程数增长）、Metaspace（类加载）、或者 glibc 分配器的碎片。排查方法：对比 pmap -x 的多次快照看哪一段在涨；Java 用 NMT 看各分类；检查线程数与 DirectBuffer 用量。

为什么 ThreadLocal 在线程池里特别危险？

因为线程池的线程长期存活且被复用，ThreadLocal 的值挂在线程的 ThreadLocalMap 上，只要线程不销毁就不释放。若每次请求都 set 而不 remove，内存会随请求累积，而且还会造成「请求间数据串味」的正确性问题。正确用法是在 finally 中 remove。

缓存导致的泄漏和正常缓存有什么区别？

区别在于「是否有上限与淘汰」。设置了容量上限（maximumSize）与 TTL 的缓存是有界增长的，属于正常设计；没有上限、或 key 无限增多（如把每个请求参数当 key）的缓存就是泄漏。另外按条数限制但 value 很大的缓存，也可能因为总字节数失控而撑爆内存——应按权重限制。

如何判断是否类加载器泄漏？

信号：Metaspace/PermGen 持续增长、堆里出现大量同名但不同 ClassLoader 的 Class 对象、常见于反复热部署或动态生成类的框架。排查：堆转储里看 ClassLoader 的引用链，通常是某个静态字段或线程持有了旧 ClassLoader。对策：确保反注册、清理静态引用、避免线程持有应用类。

内存泄漏的监控怎么做？

三层：① 进程层——RSS/PSS 趋势告警（连续 N 小时单调上涨）、堆占用与 GC 后回落情况；② 组件层——缓存大小、线程/协程数、连接池、DirectBuffer 用量；③ 容器层——cgroup memory.current 与 OOM 事件。趋势型告警（而非阈值型）对泄漏最有效，因为泄漏是「缓慢单调」的。

修复泄漏后如何确认真的修好了？

做长时间稳定性测试：在接近生产的负载下跑 8-24 小时，观察 RSS 与堆占用曲线。健康曲线是「锯齿状但有上界」（GC 回收后回落），而不是单调上升。同时对比修复前后的 Full GC 频率与老年代占用。最好再加压测 + 长跑的组合验证。
