海象运算符 :=

在表达式里顺便赋值

3.8 引入的 := 让「计算并绑定」能在条件/推导式里一次完成，避免重复调用昂贵的函数。

# 普通写法：先调一次判断，再调一次用值
len(if (n := len(data)) > 10:
    print(n, data)

# while 读取直到 EOF
while (line := f.readline()):
    process(line)
⚠️ 别滥用——海象会让表达式变长变绕。只在「同一个值要算一次、判断一次、用一次」的场景才划算，否则老老实实先赋值。
f-string：内插格式化

最常用也最安全

前缀 f"..." 里用 {expr} 直接嵌入任意表达式；还能加格式说明（:.2f、:>5、:, 千分位）。

name = "Py"
print(f"hello {name}")              # hello Py
print(f"{3.14159:.2f}")            # 3.14
print(f"{1234567:,}")              # 1,234,567
print(f"{name=}")                   # name='Py'（3.8+ 调试神器）
print(f"{name.upper():>10}")         # 右对齐宽 10
比 % 格式化和 .format() 都更直观，且不会把用户输入当格式串（安全）。需要动态格式时再退回 .format()。
三元表达式

一行版 if/else

语法是 a if 条件 else b——和很多语言「条件 ? a : b」顺序相反，中间是条件。

v = "大" if x > 10 else "小"
# 别和海象混得太复杂：
v = "空" if not (s := data) else s
⚠️ 三元适合简单二选一。如果分支体很大或要执行语句（不返回值），还是用完整 if/else——硬塞三元会牺牲可读性。
枚举 Enum：替代魔法数字/字符串

用名字代替裸值

用 enum.Enum 把一组相关常量收拢成类型，避免到处散落 "red"、1 这类魔法值，且可遍历、可比较。

from enum import Enum, auto
class Color(Enum):
    RED = auto()
    GREEN = auto()
    BLUE = auto()

c = Color.RED
if c == Color.RED:
    print("红")
for member in Color:
    print(member)            # 可遍历
相比 Go 的 iota 常量族，Enum 更面向对象：成员有名字、可带方法、可防止用错类型。需要「值就是整数」且要互转时，用 IntEnum。
解包：序列与星号

一次性拆出多个变量

元组/列表/可迭代对象都能「解包」赋给多个变量；* 收集剩余项成列表；还能交换、忽略不需要的值。

a, b = 1, 2            # 并行赋值
a, b = b, a              # 无临时变量交换
x, *mid, last = [1,2,3,4]   # x=1 mid=[2,3] last=4
first, *_ = items        # 只要第一个，忽略其余

# 函数参数解包
print(*nums)            # 展开成位置参数
func(**kwargs)           # 展开成关键字参数
解包让「返回多值」成为常态（函数 return a, b 实际返回元组，调用方直接拆）。比 Go 的 a, b := f() 体验一致，但 Python 还支持 * 收集，更灵活。
可变默认参数：经典大坑

默认值是「定义时」算一次的

函数默认参数在函数定义时求值并复用，不是每次调用新建。用可变对象（list/dict/set）当默认值，会在多次调用间共享状态。

def bad(x, buf=[]):      # buf 跨调用共享!
    buf.append(x)
    return buf
bad(1); bad(2)           # 返回 [1] 然后 [1, 2] —— 意外累积

# 正确写法：用 None 占位，函数内新建
def good(x, buf=None):
    buf = buf or []
    buf.append(x)
    return buf
⚠️ 这是 Python 面试/笔试高频题。记住铁律：默认参数永远用不可变对象（None / 数字 / 字符串 / 元组）。需要可变默认值就传 None 再在函数体初始化。这和「名称绑定」语义息息相关（见名称绑定与对象篇）。

性能实测代码

# 实测：join vs +=（最经典的性能陷阱）
import timeit

code_concat = '''
s = ""
for i in range(100000):
    s += str(i)
'''
code_join = '''
parts = []
for i in range(100000):
    parts.append(str(i))
s = "".join(parts)
'''
print("+=      ", round(timeit.timeit(code_concat, number=10), 3), "s")
print("join    ", round(timeit.timeit(code_join,   number=10), 3), "s")
# 典型结果：+= 约 0.6s，join 约 0.06s -> 快 10 倍
# 数据量越大差距越大：CPython 对 += 有优化，但仍远慢于 join
# 原因：字符串不可变，每次 += 都要分配新对象并拷贝

# 实测：列表 vs 生成器（内存）
import sys
lst = [i*i for i in range(10_000_000)]
gen = (i*i for i in range(10_000_000))
print("列表内存:", sys.getsizeof(lst)/1024**2, "MB")      # 约 400 MB
print("生成器内存:", sys.getsizeof(gen), "bytes")          # 约 100 字节
# 差 400 万倍！但要记住：生成器只能遍历一次

# 实测：in set vs in list（n=100万）
import random
data = list(range(1_000_000))
s = set(data)
print("in list:", round(timeit.timeit(lambda: 999999 in data, number=1000), 4))
print("in set :", round(timeit.timeit(lambda: 999999 in s,    number=1000), 4))
# list 约 5ms，set 约 0.00005ms -> 快 10 万倍（O(1) 哈希）

内存模型：可变对象是最大的坑

陷阱现象正确写法
可变默认参数def f(x, lst=[]) 的 lst 跨调用共享def f(x, lst=None) + 内部判断
*args 里的列表重复[[]] * 3 三个是同一个列表[[] for _ in range(3)]
闭包捕获循环变量所有 lambda 捕获到同一个 i（最终值）lambda x=i: ... 默认参数绑定
浅拷贝list(a) 只拷一层，嵌套仍共享copy.deepcopy()

可变对象陷阱

# ① 可变默认参数（Python 最著名的坑）
def add_item(x, lst=[]):        # ❌ lst 在函数定义时就创建了，所有调用共享
    lst.append(x)
    return lst
print(add_item(1))   # [1]
print(add_item(2))   # [1, 2]   <- 意外！

def add_item_ok(x, lst=None):   # ✅
    if lst is None:
        lst = []
    lst.append(x)
    return lst

# ② 列表重复
a = [[]] * 3
a[0].append(1)
print(a)             # [[1], [1], [1]]   <- 全是同一个对象！
b = [[] for _ in range(3)]
b[0].append(1)
print(b)             # [[1], [], []]     ✅

# ③ 闭包捕获
funcs = [lambda: i for i in range(3)]
print([f() for f in funcs])          # [2, 2, 2]   <- 全是最后一个值
funcs = [lambda i=i: i for i in range(3)]   # ✅ 用默认参数"钉住"
print([f() for f in funcs])          # [0, 1, 2]

# ④ 深浅拷贝
import copy
a = [[1,2],[3,4]]
b = a[:]             # 浅拷贝：外层新、内层共享
b[0].append(9)
print(a)             # [[1,2,9],[3,4]]  <- 原数组被改！
c = copy.deepcopy(a) # ✅ 完全独立

match-case（3.10+）：什么时候比 if/elif 好

match-case 用法

# 命令分发：if/elif 链 vs match
# ❌ if/elif 版本（冗长且慢）
def handle(cmd):
    if cmd[0] == "go" and len(cmd) == 2:
        return f"go to {cmd[1]}"
    elif cmd[0] == "stop":
        return "stopping"
    elif cmd[0] == "load" and len(cmd) == 3:
        return f"load {cmd[1]} -> {cmd[2]}"
    else:
        return "unknown"

# ✅ match 版本（可同时解构 + 绑定 + 守卫）
def handle(cmd):
    match cmd:
        case ["go", dest]:
            return f"go to {dest}"                    # 解构并绑定 dest
        case ["stop"]:
            return "stopping"
        case ["load", src, dst]:
            return f"load {src} -> {dst}"
        case ["go", dest] if dest == "home":          # 守卫条件
            return "going home"
        case _:
            return "unknown"

# match 还能匹配类型与属性（比 isinstance 链清晰）
match event:
    case ClickEvent(x=x, y=y) if x > 100:
        print(f"click at {x},{y}")
    case KeyEvent(key="Enter"):
        print("pressed Enter")
    case {"type": "error", "code": 500}:              # 匹配字典结构
        print("server error")
    case _:
        print("other")

# 性能：match 通常比等价的 if/elif 链略快（CPython 有优化）
# 但差距不大，主要收益是<b>可读性</b>与<b>解构能力</b>

match 的真正价值不是替代 if/elif，而是结构化模式匹配——它能同时判断结构并解构绑定变量（case ["go", dest] 一行顶三行），还能匹配类型、字面量、映射。处理解析后的 JSON/AST/命令时特别好用。

深入自检

列表推导一定比 for 循环快吗？

绝大多数情况是，但收益来自“省掉 append 的方法查找”，通常只有 20 – 40%。如果循环体里有复杂计算（如函数调用、IO），这点差异完全被淹没，此时应该优先保证可读性。另外，如果推导式里要过滤 + 复杂转换，写成显式循环反而更清晰。不要为了省 20% 而牺牲可读性。

什么时候该用生成器而不是列表？

三个信号：① 数据量很大或无限（读大文件、流式数据）——列表放不下；② 只需要遍历一次且要尽早中断（如 any()/next() 找到就停）；③ 构建成本高，且可能根本用不到全部元素。反过来，如果需要多次遍历、随机访问、或要 len()，就必须用列表。注意生成器只能消费一次——这是最常见的 bug 来源（第二次遍历得到空结果，且不报错）。

dataclass 相比普通类有什么实际好处？

四个自动生成的方法：__init__、__repr__、__eq__、以及（frozen=True 时）__hash__。写一个 5 字段的类能省 20 – 30 行样板代码。此外还支持 slots=True（3.10+，省内存约 40% 且属性访问更快）、order=True（可比较）、field(default_factory=list) 正确处理可变默认值。现代 Python 里，数据容器类默认就该用 dataclass。

类型注解会影响运行时性能吗？

基本不会。注解存在 __annotations__ 里，运行时不做检查——Python 是渐进类型，类型错误不会在运行时报错。唯一的开销：① 模块导入时求值注解表达式（几毫秒，可用 from __future__ import annotations 变成字符串避免）；② 存储 __annotations__ 字典（可忽略）。真正的价值在静态检查（mypy/pyright）和 IDE 补全——这能在上线前抓到大量 bug，收益远大于那点开销。
