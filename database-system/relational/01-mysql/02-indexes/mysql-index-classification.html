MySQL 索引分类全景

为什么随口能报出一堆索引名，却说不清怎么归类？——因为它们来自 4 个正交的分类角度，每个索引都同时贴在 4 个维度上

① 先说清"乱"的根源 ② 为什么要分这么多角度 ③ 角度一·数据结构 ④ 角度二·物理存储 ⑤ 角度三·字段特性 ⑥ 角度四·字段个数 ⑦ 串起来：一个索引 = 4 个标签 ⑧ 为什么这么复杂（收口）
①先说清"乱"的根源：名字混了 4 个维度

你随手就能报出：聚簇索引、主键索引、二级索引、普通索引、唯一索引、Hash 索引、B+树索引、全文索引、前缀索引、联合索引、单列索引……名字确实多。

但真要"分一下类"，很多人就卡住。原因很简单：这些名字根本不是同一层级的概念——它们是从 4 个不同角度对"索引"贴的标签。一个真实存在的索引，会同时在这 4 个角度里各占一个位置。所以你以为在列"同一种东西的名单"，其实是在混着念 4 张表里各挑出来的词。

看这张图就懂了

同一堆名字，被 4 条"车道"各自收走了一部分。"主键索引"比较特殊：它既落在物理存储车道（它通常就是聚簇索引），也落在字段特性车道（它是带 NOT NULL+唯一约束的主键）。这正是混乱的来源——一个名字可能横跨两个角度。

②为什么要按这么多角度分类：每个角度回答的是不同的问题

分类不是为了炫技，而是因为每个角度关心的是索引的一个完全不同、互相独立的侧面。把这 4 个问题依次想一遍，一个索引就被完整描述清楚了：

按数据结构问的是
"它底层怎么存的、怎么查的？"
按物理存储问的是
"整行数据放在哪棵树里？"
按字段特性问的是
"这列加了什么约束？"
按字段个数问的是
"用了几个列、顺序怎么排？"

打个比方：给人归类时，性别 / 职业 / 血型 / 国籍 也是 4 个正交维度，同一个人在每个维度各有一个值。你不会问"性别和职业哪个更好"，因为它们根本不在一条线上。"聚簇索引 vs B+树索引哪个好"也是同样的错误——一个在讲物理存储，一个在讲数据结构，回答的是不同的事。

一句话心法

想说清一个索引，就从 4 个角度各取一个标签叠起来：结构 + 存储 + 特性 + 个数。比如"主键 (id)" = B+树 + 聚簇 + 主键 + 单列。

③角度一·按数据结构：B+Tree / Hash / Full-text

这一维决定"索引长什么样、查起来什么复杂度、支持哪些查询"。InnoDB 里绝大多数索引都是 B+Tree，但 MySQL 还支持另外两种结构。

B+Tree 索引（默认，最常用）

平衡多路查找树，所有数据在叶子节点，叶子之间用双向链表串起来。优点一大堆：有序（天然支持 ORDER BY、范围 BETWEEN、> <）、高度低（百万数据也就 3~4 层）、查询稳定 O(log n)。InnoDB 的聚簇索引和二级索引底层都是 B+Tree。

Hash 索引

对索引列算哈希值，映射到桶，等值查询 O(1) 极快。但致命短板：不支持范围、不支持排序、不支持模糊匹配（哈希打乱了顺序），还可能有哈希冲突。MySQL 里只有 Memory 引擎原生支持用户显式 Hash 索引；InnoDB 的自适应哈希索引 (AHI) 是引擎自己默默给热点 B+Tree 页加的加速层，对你透明、不能手动建。

Full-text 索引（全文索引）

为大段文本搜索设计，底层是倒排索引（词 → 出现位置）。用 MATCH(col) AGAINST('词') 查询，而不是 LIKE '%xx%'（后者用不了 B+Tree，只能全表扫）。有停用词、最小词长等机制。

结构等值范围 / 排序模糊文本默认底层
B+Tree✅✅❌—
Hash✅ 极快❌❌Memory 引擎
Full-text部分靠相关性✅倒排索引
④角度二·按物理存储：聚簇索引 / 二级索引

这一维回答"整行数据放在哪棵树里"。详见《聚簇索引详解》，这里只勾重点。

聚簇索引（Clustered）

叶子节点存的就是整行数据，索引顺序 = 数据物理顺序。每表只能有 1 个。InnoDB 默认就是主键；没主键会自动选唯一非空键，再没有就偷偷生成 row_id。

二级索引（辅助 / Secondary）

叶子节点只存索引列 + 主键值，不存整行。查到主键后还要回表（Bookmark Lookup）去聚簇索引拿整行。一个表可以有多个二级索引。

最容易混淆的点

"聚簇索引"和"B+树索引"不是二选一。在 InnoDB 里，聚簇索引的底层就是一棵 B+Tree。一个说的是"物理存储位置"（角度二），一个说的是"数据结构"（角度一）。所以你会看到"聚簇的 B+树索引"这种正常说法——它同时占了两个维度。

⑤角度三·按字段特性：主键 / 唯一 / 普通 / 前缀

这一维看"这列上建索引时带了什么约束或特殊用法"。它们大多是 B+Tree（角度一）+ 二级（角度二），差别在约束和用途。

类型核心约束NULL每表数量备注
主键索引
PRIMARY KEY		NOT NULL + 唯一不允许1 个默认就是聚簇索引
唯一索引
UNIQUE		值唯一允许多个 NULL多个允许重复 NULL 值
普通索引
INDEX/KEY		无约束，只加速允许多个最宽松
前缀索引
INDEX(col(20))		只索引前 N 个字符—多个省空间，但可能破坏覆盖/排序

前缀索引的用法

-- 对很长的 varchar 只取前 20 个字符建索引，省空间
ALTER TABLE article ADD INDEX idx_title (title(20));

适合 VARCHAR(255) 这类长文本。代价：排序 / GROUP BY 在该列上可能用不上这个索引，且无法"覆盖"超长部分。

⑥角度四·按字段个数：单列索引 / 联合索引

这一维看"索引由几个列组成、列的顺序怎么排"。

单列索引

只建在一个列上。最简单，但多个单列索引在 WHERE a=? AND b=? 时往往只能用到其中一个（MySQL 5.6+ 有 Index Merge，但远不如联合索引高效）。

联合索引（复合）

多个列按顺序合成一个索引，遵循最左前缀原则：先用最左列才能命中，跳列则后面的用不上。列顺序直接影响能覆盖哪些查询，要按"区分度 + 查询频率"排。

-- 联合索引 (a, b, c)
ALTER TABLE t ADD INDEX idx_abc (a, b, c);
-- 能用上：a=? / a=? AND b=? / a=? AND b=? AND c=?
-- 用不上 (跳过了最左 a)：b=? AND c=? / c=?
SELECT * FROM t WHERE b=1 AND c=2;  -- 索引失效
与角度三的叠加

联合索引也能带约束：UNIQUE(a, b) 就是"唯一 + 联合"——既落在字段特性（唯一）车道，又落在字段个数（联合）车道。又一个"同一条索引占两个维度"的例子。

⑦串起来：一个真实索引 = 4 个维度的组合

把 4 个角度叠在一起，每个索引都能在下面这张表里找到自己的"坐标"。注意同一个词（如"主键"）会同时出现在两列：

建表语句里的索引数据结构物理存储字段特性字段个数
PRIMARY KEY(id)B+Tree聚簇主键单列
UNIQUE(email)B+Tree二级唯一单列
INDEX(name)B+Tree二级普通单列
UNIQUE(a, b)B+Tree二级唯一联合
INDEX(a, b, c)B+Tree二级普通联合
FULLTEXT(content)Full-text二级*普通单列/多列

* 全文索引在 InnoDB 中也以独立结构存在，可视为"非聚簇"的一类。

⑧为什么会有这么多分类（收口）

回到你的问题："为什么有这么多复杂的索引分类？" 答案就是——这不是"复杂"，而是"把一件多维的事拆开讲"。一个索引在工程上同时要回答 4 件事：

1
结构决定能力
B+Tree 才能范围/排序，Hash 只能等值，Full-text 才擅长搜文本——选结构就是选"能回答什么查询"。
2
存储决定代价
聚簇把数据塞进索引省一次回表；二级索引要回表。这是性能分析里"回表"的来源。
3
特性决定约束
主键/唯一在加速之外还保数据正确性（不能重复、不能为空），普通索引只管快。
4
个数决定覆盖
联合索引靠最左前缀同时服务多个查询、还能覆盖索引；单列索引则各管一摊。
落地用法：别再问"哪个索引好"

建索引时，从 4 个角度挨个想一遍：用什么结构？（多数 B+Tree）放不放数据？（主键聚簇）加不加约束？（唯一/普通）几个列、什么顺序？（单列/联合 + 最左前缀）。把 4 个标签定下来，一个索引就设计清楚了。性能排查时也照这 4 条：回表看物理存储、命中看字段个数（最左前缀）、范围失效看数据结构。
