四层与七层负载均衡：流量怎么选后端、故障怎么摘除

用订单 API 的两台服务器说明五元组、Host/路径路由、健康检查和会话状态。

负载均衡先决定看哪一层

四层负载均衡通常根据 IP、端口和传输协议等信息选择后端，再维持连接或数据报的转发关系；七层代理解析 HTTP 等应用协议，可按 Host、路径、请求头等选择后端，也能做 TLS 终止、重写和缓存。四层不一定“更快到永远优于七层”，七层也不代表天然安全：能力与成本取决于工作负载、设备、加密边界和配置。

例如 `api.example.test/orders` 与 `api.example.test/images` 共用公网入口，七层代理可按路径送不同服务；四层入口若不解读 HTTP，通常只能按地址端口等维度分流。若入口要按 URL 路由 HTTPS，必须在能够读取 HTTP 的位置终止或处理相应加密，不能假设中间设备能看见密文中的路径。

连接如何分配

客户端向 VIP:443 建立连接。四层均衡器可依据源/目的地址和端口、协议选择后端 A，并在连接状态里记住映射，后续包保持到 A；七层代理可能先接受客户端连接，再单独建立到后端的连接。轮询、最少连接、哈希等算法解决的是分配策略，不能替代后端容量评估。若 A 的请求平均耗时是 B 的十倍，简单轮询可能让 A 积压。

HTTP/2 的一条连接可承载多个请求流，按“连接数最少”并不一定等于按“请求负载最少”。对长连接、流式响应和普通短请求应分别观察活跃请求、CPU、队列和后端延迟。算法要与实际工作负载指标对应。

健康检查怎样定义可用

TCP 端口能连接，只证明内核和监听路径可达；应用可能因数据库故障而全部返回 500。HTTP 健康检查可访问指定路径并验证状态或关键依赖，但如果检查太重，会给依赖持续增加负担；如果检查太浅，又会把坏节点留在池中。应区分存活、就绪和关键业务可用，并设置连续失败阈值、检查间隔与恢复滞后，避免单次抖动频繁摘入摘出。

节点被摘除后，已有连接会怎样处理取决于均衡器模式与排空设置。直接杀掉后端可能中断正在支付的请求；滚动发布应先停止接新请求，再让已有请求完成或超时。健康检查通过也不意味着所有用户身份和所有路径都正常，重要业务仍需端到端探测。

一次故障时间线

后端 A 的数据库连接池耗尽，A 的 TCP 443 仍能接入。若负载均衡只做端口探测，约一半订单请求会打到 A 并超时；改为合适的就绪检查后，A 在连续失败达到阈值时被摘除，新流量转到 B。B 必须有足够余量承受故障后的全部流量，否则摘掉坏节点后会把好节点也压垮。恢复 A 时应逐步放量，避免瞬时请求全涌入刚启动的实例。

若 A 已处理订单但客户端没拿到响应，负载均衡重试到 B 可能重复创建。写请求的安全重试要靠业务幂等键和结果查询，不能由均衡器盲目对所有 5xx 自动重放。

会话粘性与真实地址

某些系统把会话只存后端 A 内存，必须让同一用户持续回到 A，常用 Cookie 或哈希做粘性。这样会限制扩缩容和故障切换：A 下线时会话可能丢失。更稳健的方案是共享会话存储或无状态可验证令牌，并确保撤销策略。粘性可以作为兼容措施，不应掩盖后端状态设计问题。

代理模式下后端看到的 TCP 对端可能是负载均衡器，而非用户。可由可信代理传递 Forwarded 或 X-Forwarded-For 等信息，但后端必须只信任来自指定代理的字段，先清理用户伪造的同名头。四层直通、NAT 与直回模式对真实源地址保留和回程路径的要求不同，部署前要看实际流量拓扑。

选型与验收

若只需简单 TCP 分流并希望保留端到端 TLS，可考虑四层模式；若要按 Host/路径路由、鉴权或改写 HTTP，则需七层能力。验收应测后端逐个下线、健康检查误报、连接排空、证书轮换、长连接、WebSocket/HTTP2 以及峰值时单节点故障。比较 P95/P99 延迟与错误率，而不是只看每秒分配了多少连接。

记录每个后端的接入请求、当前连接、错误、排队和健康状态。若外部用户报 502，要能判断是入口与后端建连失败、后端返回错误，还是入口自身资源不足。

负载均衡配置

# Nginx（L7）健康检查与负载均衡配置
upstream backend {
    least_conn;                      # 或 ip_hash / hash $key consistent / random
    server 10.0.0.1:8080 max_fails=3 fail_timeout=30s;
    server 10.0.0.2:8080 max_fails=3 fail_timeout=30s;
    server 10.0.0.3:8080 backup;     # 备份节点
    keepalive 32;                    # 到后端的长连接池
}
server {
    location / {
        proxy_pass http://backend;
        proxy_next_upstream error timeout http_500 http_502 http_503 http_504;
        proxy_next_upstream_tries 3;
        proxy_connect_timeout 1s;    # 连后端超时，要短
        proxy_read_timeout 30s;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
    }
}

ipvsadm -A -t 10.0.0.100:80 -s wlc        # 加权最少连接

健康检查的关键参数

参数常见值说明
检查间隔 interval5 – 10 s太密增加后端负担，太疏故障发现慢
超时 timeout2 – 5 s必须小于间隔
连续失败阈值 unhealthy threshold2 – 3 次防止偶发抖动导致误摘除
连续成功阈值 healthy threshold2 – 3 次防止刚恢复就被打爆
总摘除时间interval × 阈值（如 5s × 3 = 15 s）这就是故障切换的真实延迟

算一下切换时间：间隔 10 s、失败阈值 3 次 → 最长 30 s 才摘除故障节点。这 30 秒里用户的请求一直在失败。要想快速切换必须缩短间隔（如 2 s × 2 = 4 s），代价是检查流量翻倍。

  • 健康检查必须分“存活”和“就绪”：Liveness（进程活着吗，挂了就重启）vs Readiness（能服务吗，不就绪就从 LB 摘掉）。只用存活探针会导致“进程活着但连不上 DB”的机器继续接流量。
  • 不要用 TCP 端口检查代替 HTTP 检查：端口通不代表应用健康（可能线程池满了、DB 连不上）。正确做法是 /health 接口检查关键依赖，但不要检查太深（检查所有下游会让一个下游故障导致所有实例被摘除 → 雪崩）。
  • 慢启动（Slow Start）：新加入或刚恢复的节点权重从小到大逐步提升（HAProxy 的 slowstart），避免刚启动（JIT 未预热、缓存为空）就被打死。
  • 连接池与超时：LB 到后端要开 keepalive（keepalive 32），否则每次请求都重新握手；proxy_connect_timeout 要短（1–2 s），proxy_read_timeout 按业务 P99 设置。
  • 常见事故：健康检查接口太重（每次查 DB）→ 检查本身压垮服务；或所有实例同时被摘除（因为都依赖同一个挂掉的组件）→ 全站 503。健康检查只查自身关键路径，不查可选依赖。
为什么后端已经挂了，LB 还在往它发流量？

健康检查还没达到失败阈值（间隔 × 次数）。缩短间隔和阈值能加快摘除，但会带来误判风险。另外要确认健康检查的路径是否真的反映了服务状态。

L4 和 L7 该选哪个？

追求极致性能、不需要 HTTP 语义、且后端自己处理 TLS → L4（NLB/LVS）。需要按 URL 路由、灰度、鉴权、限流、可观测 → L7（ALB/Nginx/Envoy）。很多架构是 L4 做入口 + L7 做业务路由两层叠加。

自检

后端 TCP 端口能连接，就能证明所有业务请求都健康吗？

不能。应用或依赖可能故障；应结合就绪检查与端到端业务探测。
