前一页把 NewSQL 出现的理由和三条技术路线讲清了。这一页落地：什么规模才真的需要 NewSQL、和分库分表比怎么选、以及迁移的大致路径与容量量化。

01先问三个问题

  • 数据量/并发是否真到了「单机写不下或分库分表」的规模？小数据量上分布式只是增加运维成本。
  • 是否需要跨分片的强一致事务？如果只是最终一致，分库分表 + MQ 可能更轻。
  • 团队能否运维分布式（多副本、再平衡、备份恢复）？NewSQL 把复杂度藏在系统里，但出事时你得会查。
要点：一句话：当你开始为分库分表的跨分片事务、扩缩容、全局索引头疼时，NewSQL 的性价比才显现。

02与分库分表对照

维度分库分表 + 中间件原生 NewSQL
跨分片事务要自己写/用中间件，易踩坑内置 2PC/HTAP，开箱即用
扩容手工迁移分片，灰度复杂在线再平衡，加节点自动均衡
SQL 兼容常被裁剪，跨分片 join 受限更接近完整 SQL
运维复杂度你管分片规则你管集群，系统管分片

03迁移路径

  1. 评估：梳理跨分片事务、热点表、SQL 兼容性，确认收益大于成本。
  2. 双写灰度：新库与旧库双写，读先走旧库校验一致性。
  3. 数据同步：用 CDC/导入工具全量+增量同步，做对账。
  4. 切读：把读流量按比例切到新库，观察。
  5. 切写：写流量切换，旧库保留一段时间回滚。
  6. 下线：确认稳定后下线旧分库分表。

问：小团队值不值得上 NewSQL？

如果你的痛点是「分库分表太难维护」且数据量在中大型，值得；如果只是想「看起来先进」，分库分表或托管云数据库更省心。NewSQL 的隐性成本是分布式运维能力。

第一层 · 概念与判定：先问三个问题

NewSQL（TiDB/CockroachDB/OceanBase）解决的是「既要分布式扩展、又要强一致事务」。先确认你真的需要它，而不是被名词吸引。

你的情况建议
单库能扛，只是偶尔高峰加缓存/读写分离，别上 NewSQL
已分库分表但苦于跨分片事务考虑 NewSQL它原生支持
强一致事务跨多节点是刚需NewSQL分库分表补事务极痛
纯 KV / 只读分析NoSQL / 数仓更合适NewSQL 杀鸡用牛刀

NewSQL 迁移：双写灰度 + 部署

# 迁移常用路径：双写 + 灰度
1. 老库照常写；新库通过 binlog/CDC 同步（如 TiDB DM）
2. 开启双写（先老后新），比对一致性
3. 灰度切读流量到新库，观察
4. 全量切写，保留老库回滚窗口

# 容量起步（TiDB 为例）
tiup cluster deploy demo v7.1.0 ./topo.yaml  # 至少 3 PD + 3 TiKV + 2 TiDB

数量级：TiDB 单 TiKV 副本建议 200GB–500GB 数据；跨地域多副本的 RT 比单机 MySQL 高 1–3ms，但吞吐随节点近线性升。

第三层 · 排障与边界：迁移四个坑

  • 双写不一致：老库成功新库失败没人发现——必须对账任务定时比对，差量自动修
  • 热点 Region：自增 id / 时间戳做主键会打在同一 Region——改用打散主键或 SHARD_ROW_ID_BITS
  • 大事务：NewSQL 对单事务大小敏感，超过几 GB 易失败——拆批
  • 回滚窗口太短：切写后老库很快下线，出问题无处回退——留 ≥2 周

第四层 · 原理与取舍

为什么 NewSQL 不干脆取代分库分表？

因为 NewSQL 的强一致事务有跨节点延迟代价：提交要走 Raft/Paxos 多数派，RT 比单机多 1–3ms。分库分表把数据按业务切好，单分片内仍是单机事务，延迟低。所以「是否需要跨分片强一致事务」是分水岭——不需要就别为 NewSQL 的复杂度买单。

迁移为什么一定要双写而不是直接切？

因为任何一次性切换都是赌：新库可能有未知的性能拐点或兼容差异。双写让两份数据并存、可比对，读流量灰度切过去验证，写切过去前还有老库兜底。这是以「短期双份写入成本」换「零停机、可回滚」——分布式迁移的底线做法。

自增主键在 NewSQL 为什么是反模式？

NewSQL 数据按 Range 分片，自增 id 是单调的，所有新写入都落同一个最新 Region，该 Region 成为写入热点，扩展能力被废掉。正确做法是随机/哈希前缀主键或显式打散，让写入均匀落到多个 Region——这是 NewSQL 上手最容易踩、也最伤性能的坑。
