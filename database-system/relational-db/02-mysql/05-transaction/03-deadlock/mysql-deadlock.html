MySQL 死锁：成因、检测与排查

从循环等待讲到间隙锁死锁，配上可复现的 SQL 与线上排查命令

一句话记住

死锁不是「锁太多」，而是加锁顺序成了环。把顺序统一，环就断了。

二、死锁的四要素与循环等待

死锁只在四个条件同时成立时发生：互斥、持有并等待、不可抢占、循环等待。数据库里前三条基本无法消除（锁本来就是互斥的、事务未提交前不能抢锁），所以工程上唯一的抓手是打破「循环等待」。

条件含义在 InnoDB 里的现实能否消除
互斥同一时刻同一资源只能被一个事务占有行锁/间隙锁天然互斥不能
持有并等待已拿着锁还去申请新锁一个事务里多条 SQL 很常见难（只能缩短事务）
不可抢占不能强行夺走别人已持有的锁只能等或超时回滚不能
循环等待A 等 B、B 等 A 形成闭环由加锁顺序决定能：统一加锁顺序

三、场景一：交叉更新（最经典）

两个事务按相反顺序更新同一批行。这是教科书式的死锁，也是最容易复现的一种。

-- 事务 A -- 事务 B BEGIN; BEGIN; UPDATE account SET bal=bal-100 UPDATE account SET bal=bal-50 WHERE id = 1; -- 拿到 id=1 行锁 WHERE id = 2; -- 拿到 id=2 行锁 UPDATE account SET bal=bal+100 UPDATE account SET bal=bal+50 WHERE id = 2; -- 等 B 放 id=2 WHERE id = 1; -- 等 A 放 id=1 -- 此刻：A 等 B，B 等 A -> 成环 -> 死锁 -- InnoDB 回滚其中一个，另一个报 ERROR 1213 (40001): Deadlock found

修法

给要更新的 id 排序，两个事务都按 id 从小到大加锁，环就不存在了：UPDATE ... WHERE id IN (1,2) ORDER BY id，或应用层先排序再逐条更新。

四、场景二：间隙锁与插入意向锁

在 可重复读（RR） 下，DELETE/UPDATE ... WHERE 不存在的记录 或范围条件会加间隙锁。两个事务可以先各自在同一段间隙上加间隙锁（间隙锁之间是兼容的），随后再插入时申请插入意向锁，互相阻塞 —— 这就是「看起来没碰同一行却死锁」的常见来源。

锁类型加锁语句示例锁住什么互相兼容吗
记录锁 Record LockUPDATE ... WHERE id = 10（命中）单条索引记录同记录互斥
间隙锁 Gap LockSELECT ... WHERE id BETWEEN 5 AND 15 FOR UPDATE两条记录之间的开区间间隙锁之间兼容
临键锁 Next-KeyRR 下的范围查询默认记录 + 前面那段间隙区间重叠即互斥
插入意向锁INSERT 前的意向申请插入点对应的间隙与已存在的间隙锁互斥

为什么它更隐蔽

间隙死锁的语句往往没有任何一行是重复的，看业务日志很难察觉。排查时重点看 SHOW ENGINE INNODB STATUS 里的 lock_mode X locks gap before rec 字样。

五、InnoDB 的处理链路

机制触发条件行为可调参数
锁等待超时等待超过阈值报 1205，只回滚当前语句（不是整个事务）innodb_lock_wait_timeout（默认 50）
死锁主动检测wait-for graph 出现环报 1213，整个事务回滚innodb_deadlock_detect（可关，不建议）

两个易混点

  • 1205 不等于死锁：1205 是等太久，事务没回滚，可以继续跑；1213 才是死锁，整个事务被回滚。
  • 死锁回滚的是整事务：被回滚的事务里前面已经执行的 UPDATE 全部失效，应用必须能重放。

六、线上排查四板斧

  1. 看最近一次死锁详情：SHOW ENGINE INNODB STATUS\G 的 LATEST DETECTED DEADLOCK 段，里面有两条事务各自的 SQL、持有的锁、等待的锁、以及谁被回滚。
  2. 查当前锁等待：SELECT * FROM performance_schema.data_lock_waits; 与 data_locks（MySQL 8.0），5.7 用 information_schema.innodb_locks / innodb_lock_waits。
  3. 定位阻塞源头：从 innodb_trx 里找 trx_started 最早、trx_rows_modified 大的长事务，它往往是「占了锁不干活」的元凶。
  4. 开全量记录：innodb_print_all_deadlocks = ON，把每次死锁都写进 error log，便于事后统计高频语句。
-- 8.0：谁在等谁 SELECT r.trx_id waiting_trx, r.trx_query waiting_query, b.trx_id blocking_trx, b.trx_query blocking_query, b.trx_started, b.trx_rows_modified FROM performance_schema.data_lock_waits w JOIN performance_schema.data_locks l1 ON w.requesting_engine_lock_id = l1.engine_lock_id JOIN performance_schema.data_locks l2 ON w.blocking_engine_lock_id = l2.engine_lock_id JOIN information_schema.innodb_trx b ON b.trx_id = w.blocking_trx_id JOIN information_schema.innodb_trx r ON r.trx_id = w.requesting_trx_id ORDER BY b.trx_started;

七、避免死锁的七条实操

① 统一加锁顺序

批量更新前先按主键排序，或一次性 WHERE id IN (...) 让优化器决定。

② 缩短事务

把 RPC、查缓存、算报表挪到事务外；事务里只留必须原子的写。

③ 让索引生效

没索引会退化成全表锁，锁面暴增，死锁概率直线上升。

④ 降低隔离级别

业务允许时用 RC，能去掉大部分间隙锁，代价是失去可重复读。

⑤ 减少热点行

计数器、库存单行改成多行分桶 + 汇总，或异步合并写入。

⑥ 用 SELECT ... FOR UPDATE 先锁后写

把「读-算-写」压缩成一次加锁，避免中间态。

⑦ 重试必须幂等

死锁回滚后重放，SQL 要能安全重复执行（用唯一键 / 版本号兜底）。

别用「关掉死锁检测」来消警报

innodb_deadlock_detect=OFF 后死锁会退化成 50 秒超时，高并发下会堆积大量等待线程，通常比死锁本身更致命。只有在极高并发且已把等待超时调得很小（如 3~5s）时才考虑。

八、深入自检

死锁和锁等待超时，应用层处理有什么区别？

死锁（1213）会回滚整个事务，应用必须重新执行整个业务单元；锁等待超时（1205）只回滚当前那条语句，事务还在，可以选择重试这条语句或整体回滚。所以代码里的 catch 必须区分这两个错误码，不能一律「重试一次」。

为什么有时死锁日志里看不到完整的 SQL？

因为 SHOW ENGINE INNODB STATUS 只保留最近一次死锁，且长 SQL 会被截断。生产环境应打开 innodb_print_all_deadlocks，让每次死锁都落 error log。

RC 隔离级别真的能减少死锁吗？

能。RC 下基本没有间隙锁（除外键与唯一性检查），锁的范围从「记录+间隙」缩小到「记录」，交叉概率大幅下降。代价是同一事务内两次读可能不一致，需要业务能接受。

死锁被回滚后，重试会不会造成数据错误？

如果重试前不检查状态，可能重复扣款/重复发货。正确做法是：① 用唯一业务键做幂等（如订单号+操作类型）；② 或用版本号 CAS；③ 重试前先查一次当前状态，判断该步骤是否已生效。

如何提前发现「潜在死锁」而不是等线上报？

压测时开启全量死锁日志统计高频语句；代码评审时检查跨表/跨行更新是否有固定顺序；对核心链路做并发一致性测试（同一批 id 随机顺序并发更新，看是否出现 1213）。

死锁的成因、定位与规避手册

InnoDB 会自动检测死锁并回滚其中一个事务，但这不意味着可以忽略——死锁意味着吞吐损失和请求失败。重点在读懂死锁日志和统一加锁顺序。

要素说明要点
死锁检测InnoDB 默认开启，用等待图检测环innodb_deadlock_detect=ON（默认）
回滚策略回滚持有锁最少（影响行数小）的事务返回 1213 错误：Deadlock found
锁等待超时没检测到环但一直等，超时放弃innodb_lock_wait_timeout 默认 50 秒
隔离级别RR（默认）有间隙锁，死锁概率高于 RC高并发写场景可评估 RC + row binlog
锁类型记录锁 / 间隙锁 / 临键锁（next-key）RR 下范围查询会锁间隙，是死锁高发区
经典死锁场景成因规避
加锁顺序相反事务 A 锁 (1→2)，事务 B 锁 (2→1)统一按同一顺序（如按 id 升序）更新
间隙锁冲突RR 下 DELETE WHERE id BETWEEN 锁了间隙用 RC；或改成先查 id 再按主键删
唯一键冲突并发插入相同唯一键先查后插改成 INSERT ... ON DUPLICATE KEY UPDATE
更新不存在的行RR 下 UPDATE ... WHERE id=不存在 加间隙锁先 SELECT 确认存在；或用 RC
大事务持锁久事务里夹了 RPC/慢查询缩短事务，把非 DB 操作移出事务

定位命令

-- 看最近一次死锁的详细信息（最常用！）
SHOW ENGINE INNODB STATUS\G
-- 找 "LATEST DETECTED DEADLOCK" 段落，包含：
--   *** (1) TRANSACTION:  事务1 的 SQL、持有的锁、等待的锁
--   *** (2) TRANSACTION:  事务2 的 SQL、持有的锁、等待的锁
--   *** WE ROLL BACK TRANSACTION (1)    <- 谁被回滚了

-- 打开死锁日志到错误日志（推荐长期开启）
SET GLOBAL innodb_print_all_deadlocks = ON;
--   所有死锁（不只最近一次）都会写入 error log，便于统计

-- 关键参数
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';      -- 默认 50 秒
SHOW VARIABLES LIKE 'innodb_deadlock_detect';       -- 默认 ON
SHOW VARIABLES LIKE 'transaction_isolation';        -- 默认 REPEATABLE-READ

-- 调优常用
SET GLOBAL innodb_lock_wait_timeout = 10;           -- 缩短，快速失败
SET GLOBAL transaction_isolation = 'READ-COMMITTED'; -- 减少间隙锁（需评估）

-- 实时看锁等待（MySQL 8.0）
SELECT waiting_pid, waiting_query, blocking_pid, blocking_query
FROM sys.innodb_lock_waits;

-- 8.0 之前用 information_schema
SELECT * FROM information_schema.innodb_lock_waits;
SELECT * FROM information_schema.innodb_locks;
  • 统一加锁顺序是最有效的规避手段：批量更新时先按主键排序再执行（ORDER BY id 或在应用侧排），能把「交叉加锁」的死锁基本消灭。
  • 缩短事务：事务里不要有 RPC 调用、文件 IO、用户交互。持锁时间越短，撞锁概率越低。
  • 死锁不是错误，是正常现象：高并发系统里偶发死锁是可接受的，只要应用层有重试。真正的目标是让死锁率低到不影响业务。
  • 重试要带退避：捕获 1213 错误后重试，但要随机退避（如 10~100ms 随机），否则大量请求同时重试会再次撞上。
  • 死锁检测的代价：每个锁等待都要遍历等待图，高并发下 CPU 开销可观。极端场景（如秒杀单行热点）可以关掉检测改用超时（innodb_deadlock_detect=OFF），但要设短超时。
  • RC vs RR：RC 下没有间隙锁（除外键和唯一键检查），死锁概率显著低于 RR。很多互联网公司把默认隔离级别改成 RC，但要配 binlog_format=ROW。
怎么读懂 SHOW ENGINE INNODB STATUS 的死锁日志？

抓三个部分：① 两个事务各自的 SQL——(1) TRANSACTION 和 (2) TRANSACTION 下面会列出正在执行的语句，先看清是哪两条 SQL 撞了；② 锁信息——LOCK WAIT ... lock_mode X ... waiting 表示它在等什么锁，holds the lock(s) 或 lock struct(s) 表示它持有什么锁。注意锁的模式（X=排他、S=共享）和类型（RECORD=记录锁、GAP=间隙锁、next-key）；③ 谁被回滚——最后一行 WE ROLL BACK TRANSACTION (1/2)。判断成因的关键是把两个事务的「持有」和「等待」画成一张图，看是否成环。如果只是看最近一次不够，务必打开 innodb_print_all_deadlocks，把所有死锁写进 error log 才能做统计和趋势分析。

死锁和锁等待超时有什么区别？怎么处理？

死锁是「互相等待成环」，InnoDB 能主动检测，立刻回滚其中一个（错误码 1213），响应快；锁等待超时是「单向等待太久」，没有环（比如 A 持锁不放在做别的事，B 一直等），只能等 innodb_lock_wait_timeout（默认 50 秒，太长！）到期后放弃（错误码 1205）。处理差异：死锁要靠改加锁顺序/缩事务根治；锁超时除了这两点，还要注意把超时时间调短（生产建议 5~15 秒，50 秒意味着一个请求卡了近一分钟才失败，线程池很容易被打满）。两者都需要在应用层做重试。

为什么 RR 隔离级别更容易死锁？

因为 RR（可重复读）下有间隙锁（Gap Lock）和临键锁（Next-Key Lock），而 RC（读已提交）基本没有。间隙锁锁的是「记录之间的空隙」，比如 UPDATE ... WHERE id BETWEEN 10 AND 20 在 RR 下会锁住 (10,20] 这个区间，包括那些还不存在的行。这导致两个事务即使操作完全不同的行，只要它们的范围有重叠就会互相阻塞，死锁概率大幅上升。典型坑：UPDATE t SET ... WHERE id = 123 而 123 不存在时，RR 下会加一个间隙锁，两个事务都这么做就会死锁。规避方法：① 改用 RC（需 binlog_format=ROW）；② 先 SELECT 确认行存在再更新；③ 范围操作改成先查 id 列表、再按主键精确更新（主键精确匹配只加记录锁，不加间隙锁）。
