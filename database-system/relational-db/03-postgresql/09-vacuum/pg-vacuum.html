VACUUM 与 autovacuum

① 为什么需要 VACUUM

PostgreSQL 的 MVCC 让 UPDATE 变成「插入新版本 + 旧版本标记删除」。旧版本（死元组 dead tuple）不会自动消失：

  • 它们仍占用磁盘页，让表与索引变大（膨胀），IO 变多；
  • 它们仍在索引里，让索引扫描要多走无效条目；
  • 它们可能阻塞事务 ID 回卷防护（需要 freeze）。

VACUUM 的职责就是：把不再被任何事务可见的行版本标记为可复用、更新可见性映射（VM）与空闲空间映射（FSM）、回收事务 ID（freeze）、更新统计信息（配合 ANALYZE）。

② 三种清理方式对比

命令作用锁是否还空间给 OS
VACUUM标记死元组可复用、更新 VM/FSM、freeze不阻塞读写❌ 不释放（除文件尾部全空）
VACUUM FULL重写整表，彻底收缩ACCESS EXCLUSIVE（阻塞一切）✅ 释放
VACUUM ANALYZE清理 + 更新统计信息不阻塞读写❌
ANALYZE只更新统计信息（优化器用）不阻塞读写—
pg_repack在线重建，锁时间极短短暂排他✅ 释放
-- 单表清理并更新统计
VACUUM (ANALYZE, VERBOSE) orders;

-- 全库（需 superuser 或有权限；不建议在业务高峰跑）
VACUUM ANALYZE;

-- 并行清理大表（PostgreSQL 13+ 支持 PARALLEL）
VACUUM (PARALLEL 4) big_table;
「VACUUM 后文件没变小」不是 bug。它只是把空间标记为可复用。若确实要收缩文件，用 pg_repack（在线）而不是 VACUUM FULL（长时间锁表，且需要额外一倍磁盘）。

③ Autovacuum：什么时候自动清

autovacuum 守护进程周期性检查各表的死元组数量，达到阈值就触发清理：

触发阈值 = autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × 表行数
（默认：50 + 0.2 × n，即死元组超过约 20% 时触发） 
-- 全局参数
SHOW autovacuum;                        -- on
SHOW autovacuum_vacuum_scale_factor;    -- 0.2
SHOW autovacuum_vacuum_threshold;       -- 50
SHOW autovacuum_max_workers;            -- 3
SHOW autovacuum_naptime;                -- 15s

-- 对高频写入的大表单独调参（关键调优手段！）
ALTER TABLE events SET (
  autovacuum_vacuum_scale_factor = 0.01,   -- 死元组 1% 就清
  autovacuum_vacuum_threshold = 1000,
  autovacuum_vacuum_cost_delay = 2,        -- 更积极
  autovacuum_vacuum_cost_limit = 2000
);

成本限制

autovacuum_vacuum_cost_delay / cost_limit 控制清理速度，避免抢业务 IO；默认偏保守，高写入库要放宽

worker 数量

autovacuum_max_workers（默认 3）；大表多、写入高时应调大，但每个 worker 都吃 IO

监控

pg_stat_user_tables.last_autovacuum、n_dead_tup；以及 pg_stat_progress_vacuum 查看进度

表级调参

热点大表一定要单独设置更小的 scale_factor，否则 20% 阈值意味着上千万死元组

④ 事务 ID 回卷与 freeze

PostgreSQL 的事务 ID 是 32 位（约 42 亿）。若长时间不清理，ID 会耗尽并回卷，导致「未来事务的数据突然变成过去」——这是灾难性的。防护机制是 freeze：把足够老的行版本标记为「冻结」（对任何事务都可见），从而释放它们占用的事务 ID。

-- 查看各表离强制 freeze 还有多远（关键监控项！）
SELECT c.oid::regclass AS table,
       age(c.relfrozenxid) AS xid_age,
       pg_size_pretty(pg_total_relation_size(c.oid)) AS size
FROM pg_class c
WHERE c.relkind IN ('r','m','t')
ORDER BY age(c.relfrozenxid) DESC LIMIT 20;

-- 手动 freeze（VACUUM FREEZE 会立即冻结，而不是惰性）
VACUUM (FREEZE, VERBOSE) old_table;
危险线：autovacuum_freeze_max_age 默认 2 亿。当某表的 xid_age 接近它时，autovacuum 会强制对该表做 aggressive vacuum（即使它很干净）；若到 20 亿（约 2^31）仍未冻结，PostgreSQL 会拒绝写入并进入单用户模式。务必监控 age(relfrozenxid)，并在低峰期对大表分批执行 VACUUM FREEZE。

⑤ 什么会阻止 VACUUM 回收

阻塞源现象排查
长事务（未提交）它启动之后的死元组都不能回收pg_stat_activity 中 state='idle in transaction'
非活跃复制槽主库必须保留备库未消费的版本pg_replication_slots.active = false
未消费的逻辑复制订阅端掉线，WAL 与旧版本被保留pg_stat_replication、订阅端状态
孤儿预备事务2PC 事务未提交/回滚pg_prepared_xacts
长时间运行的查询快照持有导致版本不可回收慢查询监控
hot_standby_feedback备库长查询反馈，主库保留版本备库 pg_stat_activity
-- 找出最老的活跃事务
SELECT pid, state, xact_start, now() - xact_start AS dur, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start LIMIT 5;

⑥ 常见问法

Q：VACUUM 和 VACUUM FULL 的区别？生产环境该用哪个？

A：VACUUM 在线整理：标记死元组可复用、更新 VM/FSM、做 freeze，不阻塞读写，但不把空间还给操作系统；VACUUM FULL 重写整表并真正收缩文件，但持有 ACCESS EXCLUSIVE 锁（阻塞所有读写）且需要约一倍的额外磁盘空间。生产环境首选常规 VACUUM（交给 autovacuum），确需收缩文件用 pg_repack 在线重建；VACUUM FULL 只在维护窗口使用。

Q：为什么 autovacuum 跑得很勤，表还是在膨胀？

A：常见原因：① 表太大而 scale_factor=0.2 意味着要积累上千万死元组才触发——应对热点大表单独设 0.01~0.05；② cost_delay 过大导致清理速度跟不上产生速度；③ max_workers 不够，大表排队；④ 存在长事务/非活跃复制槽使死元组无法回收（清理了但回收不了）；⑤ 索引膨胀需要 REINDEX CONCURRENTLY。排查顺序：先查 n_dead_tup 与 last_autovacuum，再查阻塞源。

Q：什么是事务 ID 回卷（wraparound）？怎么预防？

A：事务 ID 是 32 位，约 42 亿个。若老的行版本长期不冻结，可用 ID 会耗尽并回卷，导致数据可见性混乱。PG 用 freeze 把足够老的版本标记为「永远可见」，释放其占用的 XID。预防：① 监控 age(relfrozenxid)，超过 1.5 亿就要关注；② 保证 autovacuum 能正常跑（不要在大表上禁用）；③ 对归档表在低峰期手动 VACUUM FREEZE；④ 及时清理长事务与孤儿复制槽。一旦接近 20 亿，数据库会拒绝写入——这是必须避免的严重事故。

Q：ANALYZE 和 VACUUM 是一回事吗？

A：不是。VACUUM 管空间与可见性（回收死元组、更新 VM/FSM、freeze）；ANALYZE 管统计信息（收集列的分布、NULL 比例、最常见值等，供优化器估算选择性与行数）。因此 「统计信息过时导致执行计划变差」要跑 ANALYZE，而不是 VACUUM。autovacuum 会在清理时顺便触发 autoanalyze。大批量导入数据后应显式执行 ANALYZE 表名。

Q：VACUUM 会阻塞业务吗？

A：常规 VACUUM 不会阻塞读写（只拿不冲突的锁），但会消耗 CPU 与 IO，因此用 cost_delay/cost_limit 限速。例外：① VACUUM FULL 持排他锁，完全阻塞；② 清理索引时会短暂持有锁；③ 在需要截断文件尾部的罕见情形下，需要短暂排他锁（PG 会尽量避免并可能放弃截断）。实践：让 autovacuum 平稳运行，避免在业务高峰手动全库 VACUUM。

Q：索引也会膨胀吗？怎么处理？

A：会。B-tree 索引中的死索引项由 VACUUM 清理，但索引页的空闲空间难以复用，长期随机写入（如随机 UUID 主键）会造成索引膨胀、层数变深。处理：① REINDEX INDEX CONCURRENTLY idx_name;（在线重建，PG 12+）；② REINDEX TABLE CONCURRENTLY t;；③ 用 pgstattuple 或 pgstatindex 评估 avg_leaf_density（低于 50% 通常值得重建）；④ 根本上避免随机键，用顺序或时间有序的主键。
