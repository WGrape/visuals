01用 perf 测 CPI 与瓶颈类型

经验阈值：CPI < 0.5 通常计算密集；CPI > 1 多半在等内存或分支。CPI 高看 cache-miss，分支多折看 branch-miss。

# 统计一段程序的硬件计数器
perf stat -e cycles,instructions,cache-misses,branch-misses ./app
# 关注：
#   CPI = cycles / instructions  （>1 多说明停顿多）
#   cache-misses 高 -> 内存受限
#   branch-misses 高 -> 分支预测差

02套 Amdahl 算加速上限

要点：Amdahl 的教训：优化前先用 perf 找到「串行热点」在哪。把 1% 的串行改成并行毫无意义，把 90% 的热点并行化才是正路。
def speedup(p, n):
    # p: 可并行比例(0~1), n: 处理器数
    return 1 / ((1-p) + p/n)
print(speedup(0.9, 8))    # 约 4.7x
print(speedup(0.9, 100))  # 约 9.2x，收益已很小
# 串行部分 10% 时，无论堆多少核，上限 10x

03画 Roofline 看卡点

Roofline 用「算术强度 = FLOPs / 字节」做横轴，纵轴是可达性能（FLOPs/s）。应用点落在「带宽斜坡」还是「算力天花板」决定该优化什么。

你的点落在含义该怎么做
斜坡区（左）被内存带宽限制减少访存、提升缓存命中、用向量化
天花板（右）被算力限制减少冗余计算、用更快指令/更多核
二者之间部分重叠先算算术强度再定方向
  • 工具：Intel VTune、pcm-memory（测内存带宽）、likwid（测 FLOPs 与强度）。
  • 先量算术强度 = 总 FLOPs / 总访存字节，再对照机器的峰值带宽与峰值算力。

04常用工具清单

  • perf：Linux 通用，计数器丰富。
  • VTune / pcm：Intel 平台细到顶层的 Top-down 分析。
  • likwid：轻量，适合批量测 FLOPs 与带宽。
  • nvvp / Nsight：GPU 侧对应工具。
问：CPI 很低但程序还是很慢，为什么？

CPI 低只说明「每条指令停顿少」，不代表「干的活有用」。可能是指令总数太大（算法低效）、或 true 受限于内存带宽（看 cache-miss 与算术强度），这时要看 Roofline 而非 CPI。
