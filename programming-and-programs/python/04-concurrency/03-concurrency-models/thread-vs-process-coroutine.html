线程、进程、协程：怎么选

三者解决的是不同的问题：进程为「真并行」、线程为「轻量共享」、协程为「高并发不阻塞」。在 GIL 的约束下，选错模型要么跑不满 CPU、要么并发上不去。这一篇给你一张决策表。

三者本质

进程、线程、协程是三个层级

进程是 OS 资源分配最小单位，各自独立内存；线程是进程内的执行流，共享内存；协程是用户态的「轻线程」，在单线程内手动切换，不靠 OS 调度。

📦
进程 Process
独立内存、自带 GIL、开销大、真正并行
🧵
线程 Thread
共享内存、受 GIL、轻量、需加锁
🍃
协程 Coroutine
单线程内切换、万级并发、靠 await

GIL 只在单进程内生效。所以多线程无法多核并行，但多进程可以（每个进程一把 GIL）。协程更极端——它根本不在意 GIL，因为它压根不并行，只是「不阻塞地快速切换」。

GIL 下真相

看懂 GIL 才能选对

GIL 让「同一进程的多线程」无法在多核上同时跑 Python 字节码。结论：CPU 密集用多进程，I/O 密集用多线程或协程，高并发网络用协程。

import time, threading, multiprocessing as mp

def cpu_task(n):
    while n > 0: n -= 1

# CPU 密集：多线程被 GIL 卡住，不如单线程
t0 = time.time()
ts = [threading.Thread(target=cpu_task, args=(10**7,)) for _ in range(4)]
[t.start() for t in ts]; [t.join() for t in ts]
print("thread:", time.time()-t0)

# CPU 密集：多进程真并行，明显更快
t0 = time.time()
with mp.Pool(4) as p: p.map(cpu_task, [10**7]*4)
print("process:", time.time()-t0)
GIL 的完整机制（为什么存在、何时释放、3.13 no-GIL）见GIL 完全解析；I/O 时为何释放 GIL 见GIL 与 I/O 细节。
决策表

先判场景，再选模型

一句话口诀：算得多 → 多进程；等得多（网络/磁盘）→ 多线程或协程；连接多/高并发 → 协程。

场景首选为什么
图像/数值计算、加密多进程绕过 GIL，真多核并行
爬虫、调用外部 API多线程 / 协程I/O 等待时释放 GIL
Web 服务器万级连接协程 asyncio单线程扛海量并发，开销极小
混合（既算又等）进程+线程/协程计算交给进程，I/O 交给线程
⚠️ 别用多线程跑 CPU 密集任务——在 CPython 下它可能比单线程还慢（GIL 争抢开销）。也别用多进程跑海量 I/O——进程内存开销大、上下文切换贵，协程更合适。
统一接口

concurrent.futures 一把梭

无论选线程还是进程，推荐用 concurrent.futures 的统一 API：把「执行器」抽象掉，业务代码几乎不变，将来切换模型只换一个类名。

from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

# I/O 密集：线程池
with ThreadPoolExecutor(max_workers=20) as ex:
    r = list(ex.map(fetch_url, urls))

# CPU 密集：进程池（只改这一行）
with ProcessPoolExecutor(max_workers=4) as ex:
    r = list(ex.map(cpu_task, data))

协程不属于这个执行器家族，但它有自己的「并发原语」（asyncio.gather / TaskGroup），详见asyncio 任务与并发。线程共享内存带来的「竞态」问题，见锁与同步原语。
