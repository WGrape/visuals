✅ 优劣势详解

✅ RabbitMQ 优势

  • ✦延迟最低 (微秒级)，适合实时性要求高的场景
  • ✦支持多种 Exchange 路由策略，非常灵活
  • ✦多协议支持 (AMQP/MQTT/STOMP/WebSocket)
  • ✦内置 Web 管理界面，开箱即用
  • ✦多语言客户端成熟 (Java/Python/Go/PHP等)
  • ✦消息可靠性高，ACK 机制完善

❌ RabbitMQ 劣势

  • ✘吞吐量较低 (万级)，不适合大数据场景
  • ✘Erlang 语言栈，二次开发门槛高
  • ✘集群扩展较复杂，动态扩容不便
  • ✘不支持消息回溯，消息消费后无法重新处理

✅ RocketMQ 优势

  • ✦吞吐量高 (百万级)，经阿里双十一万亿级验证
  • ✦严格顺序消息 + 事务消息 + 延迟消息原生支持
  • ✦支持消息回溯，按时间/偏移量重新消费
  • ✦Java 实现，方便二次开发和定制
  • ✦消息重试机制完善 (服务端 ConsumeQueue)
  • ✦支持亿级消息堆积，不影响性能

❌ RocketMQ 劣势

  • ✘社区生态相对 Kafka 较小 (主要在中文圈)
  • ✘客户端语言支持不如 RabbitMQ 丰富
  • ✘早期版本依赖 NameServer 单点 (已改善)
  • ✘配置相对复杂，学习曲线中等

✅ Kafka 优势

  • ✦吞吐量最高 (千万级)，大数据场景首选
  • ✦生态最丰富 (Kafka Connect / KStreams / KSQL)
  • ✦顺序 I/O + 页缓存 + 零拷贝，性能极致
  • ✦支持流处理，可构建实时数据管道
  • ✦社区活跃，Apache 顶级项目
  • ✦新版去除 ZooKeeper 依赖 (KRaft 模式)

❌ Kafka 劣势

  • ✘运维复杂度高，分区/副本/ISR 需精细调优
  • ✘不支持优先级消息、延迟消息等高级特性
  • ✘拉模式 (Pull) 可能造成空轮询
  • ✘单机分区数过多时性能下降明显
🎯 选型建议

🟠 选 RabbitMQ 当……

需要极低延迟（微秒级）、复杂路由逻辑、多协议接入（MQTT/IoT 场景）、或者团队规模小希望开箱即用。

实时通知 请求削峰 IoT 消息 简单异步

🔴 选 RocketMQ 当……

需要顺序消息、事务消息、延迟消息、消息回溯等高级特性；业务消息场景（订单、支付）；希望 Java 技术栈方便定制。

电商订单 金融交易 事务最终一致 延迟任务

🟣 选 Kafka 当……

日志收集、流处理、大数据管道、高吞吐量场景；需要构建实时数据平台；团队有能力运维较复杂的分布式系统。

日志收集 流处理 大数据管道 事件溯源

📋 快速决策树

1️⃣ 需要 极低延迟 (微秒级)？ → RabbitMQ

用数字对比：吞吐、堆积与可靠性

三款消息队列的定位差异，本质是存储模型与投递语义的差异，最终表现为吞吐与堆积能力的数量级差别。

维度RabbitMQRocketMQKafka说明
模型交换机 + 队列（AMQP）Topic + 队列分区日志（append-only）Kafka 的日志模型是吞吐高的根本原因
单节点吞吐万级 ~ 十万级 /s十万级 /s十万 ~ 百万级 /s（批量）1KB 消息、批处理后的量级
堆积能力受内存/磁盘限制，堆积多时性能下降明显支持百万级堆积支持 TB 级堆积（磁盘顺序写）堆积是 Kafka/RocketMQ 的强项
延迟微秒 ~ 毫秒级毫秒级毫秒 ~ 十毫秒级（批量换取吞吐）要极低延迟选 RabbitMQ
顺序保证单队列有序队列内有序分区内有序Kafka 全局有序需要单分区
消费模型推（push）+ 确认拉（长轮询）拉（消费者主动拉取）拉模型更适合批量与回放
重放能力消费即删除按 offset 回退天然支持重放（保留期内的任意 offset）需要重算历史数据时至关重要
事务/精确一次有 confirm 与事务（性能差）事务消息（半消息）幂等生产者 + 事务（EOS）精确一次代价都不低

一句话总结选型：要极低延迟与复杂路由 → RabbitMQ；要稳定在线业务与事务消息 → RocketMQ；要吞吐、堆积与重放（日志、流处理）→ Kafka。

运维命令

# Kafka：看积压（lag）是最日常的运维动作
kafka-consumer-groups --bootstrap-server localhost:9092 \
    --describe --group my-group
#   LAG 列就是每个分区落后多少条；持续增长 = 消费跟不上

# 看 topic 的实际大小与分区分布
kafka-topics --bootstrap-server localhost:9092 --describe --topic my-topic
kafka-log-dirs --bootstrap-server localhost:9092 --describe --topic-list my-topic | grep -E 'size|topic'

# 消费者重放：把 offset 回退到指定位置
kafka-consumer-groups --bootstrap-server localhost:9092 --group my-group \
    --reset-offsets --to-earliest --execute --topic my-topic
kafka-consumer-groups --bootstrap-server localhost:9092 --group my-group \
    --reset-offsets --shift-by -1000 --execute --topic my-topic   # 回退 1000 条

# RabbitMQ：看队列深度与未确认数
rabbitmqctl list_queues name messages messages_ready messages_unacknowledged
rabbitmqctl list_consumers

# RocketMQ：看消费进度
mqadmin consumerProgress -n localhost:9876 -g my-group

选型时最容易被忽略的一条：消费者数量受分区/队列数限制。Kafka 一个分区只能被同组的一个消费者消费，所以「消费者加到 50 个」是没用的，必须先有 50 个分区。分区数要在建 topic 时就按峰值规划，后续扩容分区会打乱 key 的分布。

选型决策与检查清单

你的需求选择理由
延迟必须 < 5 msRabbitMQ推模型 + 内存优先，延迟最低
日消息量 > 10 亿Kafka顺序写 + 批量，吞吐最高
需要重放最近 7 天数据Kafka日志模型天然支持按 offset 重放
需要事务消息（本地事务 + 发消息原子）RocketMQ半消息机制成熟
复杂路由（按规则分发到不同队列）RabbitMQExchange 的 direct/topic/headers 灵活
流处理（窗口、join）KafkaKafka Streams / Flink 生态完整
团队规模小、运维能力弱云厂商托管版自建 Kafka 的运维成本不低

上线前逐条核对：

  • 分区/队列数按峰值规划：消费者数量不能超过分区数，扩容分区代价很高。
  • 消息要带唯一 key：既是顺序保证的依据，也是去重与排查的抓手。
  • 必须开启持久化与多副本，否则宕机即丢数据。
  • 消费端必须幂等：任何「精确一次」都有边界条件，业务侧兜底最稳。
  • 积压要监控 lag 而不是只看队列长度：lag 持续增长才是真积压。
  • 重试要有死信队列：失败消息不能无限重试把消费堵死。
  • 刷盘策略要明确：异步刷盘性能好但宕机可能丢，同步刷盘反之。
  • 保留期要按磁盘算：日增数据量 × 保留天数 × 副本数。
  • 顺序与并发是矛盾的：要严格顺序就得牺牲并行度，很少有两者兼得。
  • 压测要用真实消息大小：1 KB 与 100 KB 的结论完全不可比。
