①更新与删除为什么特别贵

向量列的更新和删除在 pgvector 里比普通列贵得多，因为 HNSW 是图结构：删一个点只是标记，图不会立刻修复；插入一个点要更新多处邻接表。

操作代价后果对策
INSERT要维护图的邻接关系写入吞吐低于普通表批量写入，避免逐条
UPDATE 向量列等价于删 + 插最贵，且留下死元组尽量避免更新向量本身
DELETE标记删除，图不修复搜索仍会经过死节点，召回与延迟双降定期 VACUUM；大量删除后 REINDEX
大量删除后索引膨胀索引大小与查询延迟都上升REINDEX INDEX CONCURRENTLY
「每天全量重建向量表」这种设计在 pgvector 上会非常痛：HNSW 重建可能要数小时。正确做法是分区表 + 只重建变化的分区，或者改用「增量插入 + 定期 REINDEX」的策略。

②TOAST：大向量的隐性成本

Postgres 的行有宽度限制，大向量会触发 TOAST（超尺寸数据外置存储）。这不影响索引可用性，但会影响顺序扫描、备份大小和复制流量。

维度 × 类型单行大小是否 TOAST备注
768 × float32约 3 KB否（通常）还算正常
1536 × float32约 6 KB是外置存储，seq scan 变慢
3072 × float32约 12 KB是必然 TOAST，且无法建 vector 索引
3072 × halfvec约 6 KB是可建索引，仍是 TOAST
备份和逻辑复制会把 TOAST 数据一起带走。千万级向量表的 pg_dump 可能几十 GB、耗时数小时 —— 规划备份窗口时要把这部分算进去，别只算业务数据。

③内存命中率决定 p99

pgvector 的性能高度依赖「索引能不能留在内存里」。共享缓冲区命中率是关键指标：

-- 看索引大小
SELECT pg_size_pretty(pg_relation_size('docs_emb_hnsw'));

-- 看缓冲区命中率（理想 > 0.99）
SELECT sum(blks_hit)::float / (sum(blks_hit) + sum(blks_read)) AS hit_ratio
FROM pg_stat_database;

-- 看 HNSW 实际扫描量（0.8+）
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM docs ORDER BY emb <=> $1 LIMIT 10;
配置作用建议
shared_buffers缓存数据与索引页设为实例内存的 25%，且要能装下 HNSW 索引
effective_cache_size告诉优化器 OS 缓存有多少设为内存的 50–75%
work_mem排序/哈希内存影响大 LIMIT 的排序，适度提高
实例内存决定性因素索引 + 热数据必须装得下，否则 p99 会抖

⑥去留判断的五条线

最后给一条判断线，避免在 pgvector 上硬扛：

你的处境结论
向量 < 1000 万，p99 要求 > 20 ms，团队已有 Postgres留在 pgvector，性价比最高
向量 < 1000 万，但 p99 要求 < 10 ms先试调优；仍不行则迁移
向量 > 1000 万评估专用库；pgvector 的索引构建与 VACUUM 会成为长期负担
需要频繁更新向量（如实时个性化）pgvector 的 UPDATE 代价很高，倾向于专用库
已有数据在 Postgres，且向量只是辅助召回留在 pgvector，用 SQL 过滤融合
迁移到专用向量库不是「升级」，是把一个库的问题换成两个库的一致性问题。只有在向量规模或延迟真的顶不住时，这笔交换才划算。

⑦速记卡

更新最贵

UPDATE 向量列 = 删 + 插，还留死元组。

删除要善后

标记删除 + 图不修复；大量删后 REINDEX。

TOAST

1536 维起行数据外置，备份与复制流量变大。

内存决定 p99

索引装不进 shared_buffers，p99 必然抖。

量级参考

100 万×768：p50 2–5ms，p99 5–15ms。

打折前提

无过滤、单租户、warm cache —— 实际要打折。

七类故障

结果数不足、召回低、建索引 OOM 是前三名。

去留判断

千万级内没硬延迟要求，留在 pgvector 更划算。

pgvector 的取舍可以用一句话概括：用「向量检索的中等性能」换「省掉一整套系统」。这笔交换在千万级以内几乎总是划算的。
