编译器结构：前端、中端与后端

为什么编译器要分三段？前端管「这是什么语言」，中端管「怎么更快」，后端管「跑在什么机器上」——一次看懂编译器的骨架与完整流水线。

核心动机

为什么编译器要分成前端、中端、后端

本质是一个「乘法变加法」的工程问题。

假设有 N 种语言（Go、Rust、C++）和 M 种目标机器（x86、ARM、RISC-V）。如果每种语言都为每种机器单独写一套编译器，需要 N × M 套——这是乘法级的工作量。

引入中间表示（IR）后：前端只负责把各语言翻译成统一的 IR，后端只负责把 IR 翻译成各机器码，中间的优化对 IR 做一次即可。于是工作量变成 N + M，且优化只需写一遍就能让所有语言、所有机器共用。

📥
前端 Front End
依赖源语言，产出与机器无关的 IR；做词法、语法、语义分析
⚙️
中端 Optimizer
不依赖语言也不依赖机器，只在 IR 上做优化变换
📤
后端 Back End
依赖目标机器，做指令选择、寄存器分配，产出机器码
经典例子：LLVM 就是这套设计的典范——Clang（C/C++ 前端）、Rustc、Swift 都产出 LLVM IR，共享同一个优化器和 x86/ARM/WebAssembly 等后端。这也是现代语言能快速支持多平台的原因。
全景

一条完整的编译流水线

从字符流到可执行文件，每一步都在做什么。

前端

前端：把字符流变成有含义的树

🔤
词法分析 Lexer
把字符流切成 Token：标识符、关键字、运算符、字面量。丢掉空格与注释
🌳
语法分析 Parser
按文法把 Token 组织成 AST（抽象语法树），检查结构是否合法
🔎
语义分析
类型检查、符号表解析、作用域判定；结构对但含义错在这里报错
// 源码
int sum = a + 10;

// ① 词法 → Token 流
[int] [sum] [=] [a] [+] [10] [;]

// ② 语法 → AST
      (=)
     /   \
  sum    (+)
         /  \
        a    10

// ③ 语义：sum/a 是否已声明？a 能否与 int 相加？
语法正确 ≠ 语义正确。int x = "hello"; 在语法上完全合法（类型+标识符+赋值），只有语义分析（类型检查）才会报错。
中端

中端：与语言、机器都无关的优化

优化只在 IR 上做一次，所有语言和机器都能共享。

优化做什么举例
常量折叠编译期算出常量表达式x = 2 * 3 → x = 6
常量传播把已知常量代入后续使用a=5; b=a+1 → b=6
死代码消除删掉永远不会被用到或不可达的代码if (false) {...} 整块删除
公共子表达式消除重复计算只算一次a+b 出现两次只算一次
函数内联把小函数体直接嵌入调用处消除调用开销，为进一步优化打开空间
循环优化循环不变量外提、强度削弱、展开for 里不变的表达式提到循环外
逃逸分析判断对象是否逃出函数，决定能否栈上分配Go 编译器的关键优化
优化的前提是「不改变可观察行为」。编译器可以自由重写代码，只要程序对外的结果一致——这个契约叫语义保持，也是所有优化合法性的底线。
后端

后端：落到具体机器

🧩
指令选择
把 IR 操作映射到目标架构的指令集（如 x86 的 mov/add、ARM 的 ldr/add）
🗂️
寄存器分配
决定哪些变量常驻寄存器、哪些溢出到栈；经典算法是图着色（Graph Coloring）
📐
指令调度
重排指令顺序以填满 CPU 流水线、减少等待（受数据依赖约束）
📦
目标代码生成
产出汇编或可重定位目标文件（.o），后续交给链接器
为什么寄存器分配是难点？寄存器数量极少（x86-64 约 16 个通用寄存器），而程序里的变量成千上万，且变量间存在「同时存活」冲突。这是一个 NP 完全问题，实际用图着色的启发式算法解决；分配不当就会频繁 spill（溢出到内存），性能骤降。
面试问答

高频问题

Q1：编译器为什么要分成前端、中端、后端？
为了把「N 种语言 × M 种机器」的乘法工作量变成「N + M」的加法。前端按语言产出统一 IR，后端按机器消费 IR，优化只需在中端对 IR 做一次，所有语言与机器共享。LLVM 是这一设计的代表。
Q2：词法分析、语法分析、语义分析分别在做什么？
词法把字符流切成 Token（去空格注释）；语法按文法把 Token 组织成 AST，检查结构合法性；语义做类型检查、符号解析与作用域判定，检查含义合法性。语法正确不代表语义正确。
Q3：AST 和 IR 有什么区别？
AST 贴近源语言语法结构（有 if、for 等节点，层次深）；IR 更接近机器、更线性（如三地址码、SSA），便于做数据流分析与优化。前端产出 AST，再转换为 IR 交给中端。
Q4：编译器优化能改变程序行为吗？
不能改变「可观察行为」。优化必须保持语义等价；只有在这个前提下，编译器才可自由重排、内联、消除代码。
Q5：什么是逃逸分析，它带来什么优化？
分析对象是否会被函数外部引用。若不会「逃逸」，就可以栈上分配（减少 GC 压力）、甚至做标量替换（把对象拆成若干局部变量、完全不分配）。Go 编译器的重要优化之一。
Q6：寄存器分配为什么难？常用什么算法？
寄存器极少而变量极多，且存在同时存活冲突，本质是图着色（NP 完全）问题。实践用 Chaitin/Briggs 等启发式图着色算法；无法分配到寄存器时溢出（spill）到栈。
