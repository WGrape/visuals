Phoenix、Hive、Spark、Solr/ES 二级索引与 HBase 在大数据栈中的位置

HBase 在大数据栈里的位置

HBase 自己只提供「按 rowkey 的高吞吐随机读写」。要 SQL、要分析、要全文检索，都要靠生态组件补齐。

Phoenix：给 HBase 加 SQL

Phoenix 是 HBase 最主流的 SQL 层：把 SQL 编译成原生 HBase scan（不是 MapReduce），因此延迟很低。它还提供了 HBase 原生没有的二级索引。

-- 建表（映射到 HBase 表）
CREATE TABLE user (
  id VARCHAR PRIMARY KEY,          -- PRIMARY KEY 映射到 rowkey
  "info"."name" VARCHAR,           -- 列族.列限定符
  "info"."age" UNSIGNED_INT,
  "stat"."pv" UNSIGNED_LONG
) COLUMN_ENCODED_BYTES = 0;

-- 二级索引：让非 rowkey 列也能走索引
CREATE INDEX idx_age ON user ("info"."age");
CREATE INDEX idx_name_age ON user ("info"."name") INCLUDE ("info"."age");  -- 覆盖索引
CREATE LOCAL INDEX idx_local ON user ("stat"."pv");   -- 本地索引（同 Region）

-- 查询（会走索引）
SELECT name, age FROM user WHERE age > 18 ORDER BY age LIMIT 10;

-- Upsert（Phoenix 里 insert 和 update 都是 upsert）
UPSERT INTO user VALUES ('u001', 'Alice', 30, 128);
UPSERT INTO user (id, "stat"."pv") VALUES ('u001', 129);
索引类型存储适用代价
全局索引 Global独立的索引表读多写少写时要同步索引表（跨 Region，有网络开销）
本地索引 Local索引数据与主数据同 Region写多读少读时要扫每个 Region
覆盖索引 Covered索引表 INCLUDE 常用列固定查询模式索引表变大，但查询不回主表
⚠️ Phoenix 的 SQL 不等于 MySQL：复杂 JOIN、子查询、聚合能力都有限，且没有跨行事务。它定位是「HBase 上的 OLTP 加速层」，不是通用关系库。

检索层：Solr / ES 做全文与多维检索

HBase 只能按 rowkey 查，全文检索与多维组合查询要外挂搜索引擎。两种主流架构：

方案 A：双写（应用维护）

应用同时写 HBase 和 ES，查询时先查 ES 拿 rowkey 列表，再批量 get HBase 拿明细。

优点：简单可控。缺点：一致性要自己保证。

方案 B：Lily HBase Indexer

通过 HBase Replication 把 WAL 推给 Indexer，异步写入 Solr/ES。

优点：解耦、准实时。缺点：多一个组件要运维，有延迟。

🎯 常见问法与答题要点

Q：Phoenix 和 HBase 是什么关系？

A：Phoenix 是跑在 HBase 之上的 SQL 层：它把 SQL 编译成原生 HBase 的 scan/put（不是 MapReduce），所以延迟很低（毫秒~秒级）。它补齐了 HBase 最大的短板——没有二级索引。表映射方式：PRIMARY KEY → rowkey，普通列 → 列族.限定符。注意它的 SQL 能力不等于 MySQL，复杂 JOIN 和子查询受限。

Q：Phoenix 全局索引和本地索引怎么选？

A：看读写比例。全局索引是独立的索引表，查询时直接定位到索引行，读最快；但写入时要跨 Region 同步更新索引表（额外网络往返），写代价高——适合读多写少。本地索引的索引数据与主数据放在同一个 Region，写入时是本地操作（写快），但查询时每个 Region 都要扫一遍再汇总（读慢）——适合写多读少。

Q：Hive 查 HBase 为什么慢？

A：因为 Hive 外表走的是 MapReduce/Tez 批处理，每次查询都要启动任务、全量扫 HBase 表、再 shuffle 聚合，延迟是分钟级的。它的定位是离线批处理，不是在线查询。如果要低延迟 SQL 用 Phoenix；如果要快速的大扫描分析用 Spark 直读 HFile（还能加 STARTROW/STOPROW 下推）；如果要完全不影响线上，用 Snapshot + Spark 读快照文件。

Q：离线分析怎么才能不影响在线集群？

A：最佳方案是 Snapshot + Spark 直读 HFile：先 snapshot（秒级元数据操作），然后 Spark 任务直接读快照引用的 HFile 文件，完全绕开 RegionServer。在线集群既不承担 scan 压力，也不会有 BlockCache 污染和 compaction 干扰。这是生产上做大规模离线分析的标准姿势。

Q：HBase 怎么做全文检索？

A：HBase 本身没有全文检索能力，要外挂搜索引擎。两种架构：①应用双写——同时写 HBase 和 ES，查询时先查 ES 拿 rowkey 列表再批量 get HBase 取明细，简单可控但要自己保证一致性；②Lily HBase Indexer——通过 HBase Replication 把 WAL 推给 Indexer 异步写 Solr/ES，解耦且准实时，代价是多一个组件、有一定延迟。

Q：实时写入 HBase 的主流方案是什么？

A：Kafka → Flink → HBase。Flink 消费 Kafka，做清洗/聚合后用 HBaseSink 批量写入（配 writeBufferSize 与批量提交）。要点：①按 rowkey 排序提高 Region 缓存命中；②开批量写缓冲（2~6MB）；③上游削峰避免打爆 RegionServer；④必要时用 Phoenix 的 upsert 语义简化幂等处理。如果是历史数据初始化，用 BulkLoad 而不是流式写入。

Q：HBase 生态里哪些组件是必需的，哪些是可选的？

A：必需：HDFS（存储）、ZooKeeper（协调）——这两个没得选。强烈建议：Phoenix（SQL + 二级索引，几乎是生产必备）。按需：Spark/Flink（计算与接入）、Solr/ES（全文检索）、Kafka（消息队列）、Ambari/CM（集群管理）。可选：Hive（离线 HQL）、Sqoop/DataX（关系库迁移）。
