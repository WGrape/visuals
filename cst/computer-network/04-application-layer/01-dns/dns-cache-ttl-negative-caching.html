DNS 缓存、TTL 与负缓存：改记录为何还没生效

从一次域名迁移解释各层缓存、TTL 倒计时、NXDOMAIN 与回滚窗口。

先区分谁在缓存

浏览器、操作系统、应用运行时、递归 DNS 解析器都可能缓存解析结果；权威 DNS 保存域名记录，但不负责把所有客户端缓存立即清空。用户访问 example.test 时，若本机或递归解析器已有有效 A 记录，可以直接返回，不必每次问根、顶级和权威服务器。DNS TTL 表示记录可被缓存的期限，由缓存方从取得记录时开始计时，而不是“权威修改后再等一整段”。

不同客户端可能使用不同递归解析器，也可能有应用自己的连接池或固定解析缓存。因此同一时刻有的用户看到新 IP、有的还看到旧 IP 是常见过渡状态。更重要的是 DNS 解析成功不等于应用立刻切换：已有 TCP/TLS 连接可能继续使用旧地址直到连接关闭。排查需分别核对解析结果与实际连接的远端 IP。

一次切换时间线

计划把服务从旧 IP A 切到新 IP B。若旧记录 TTL 是 3600 秒，先在足够早的时间把 TTL 调低，例如 300 秒，并等待旧缓存过期；随后确认新服务器、证书和健康检查都准备好，再改权威 A 记录为 B。修改后，新查询会取得 B，但仍持有旧结果的递归解析器会在剩余 TTL 内继续返回 A，因此旧服务器要保留一段过渡期。

把 TTL 从 3600 秒改为 300 秒的瞬间，不会让已经拿到旧 3600 秒记录的缓存提前失效。若切换时先停 A，再去权威端降 TTL，用户仍可能在旧 IP 上遇到故障。计划回滚也要考虑新记录的缓存期：改回 A 不会让所有拿到 B 的客户端立即回到 A。

逐步推演

提前降 TTL

等旧的长 TTL 缓存自然过期。

准备新目标

验证新 IP 的应用、证书和健康状态。

修改权威记录

新查询得到 B，旧缓存仍可暂时返回 A。

观察与回滚

看实际连接远端 IP，保留 A 到过渡结束。

NXDOMAIN 与负缓存

域名不存在时，解析器可缓存 NXDOMAIN 等否定回答，缓存时长由相关 DNS 规则和权威区域 SOA 等信息决定。若先让用户访问尚未创建的 api.example.test，随后才添加记录，某些客户端可能仍在负缓存期内看到“不存在”。这与 A 记录旧 IP 的缓存不同：问题发生在“无记录”的结果也能被缓存。

另有 NODATA 情况：域名本身存在，但请求的记录类型没有答案，例如有 A 记录却没有 AAAA。不要把所有“没查到 IP”统称 NXDOMAIN。诊断时看响应码、查询类型、权威回答以及递归解析器的返回，才能知道应新增记录、等待负缓存还是修复权威服务器。

CNAME 链和多种 TTL

若 www.example.test CNAME 到 edge.example.test，解析链中的别名与目标 A/AAAA 记录可以各自有 TTL。改变 CNAME 目标与改变目标地址是两种操作；旧 CNAME 或旧目标记录都可能继续被缓存。CDN 切换时尤其要看完整链路，不能只 `dig` 最后一个 IP 就断言权威配置已全局生效。

多条 A/AAAA 记录也可能被不同解析器以不同顺序返回，客户端还有自己的选择逻辑。若只从本机抽样一次，容易错把负载均衡的多答案行为看成缓存未更新。固定查询的 DNS 服务器和记录类型，多次比较权威与几个代表性递归解析器，更能解释差异。

为什么 TTL 不是强一致承诺

缓存实现可能设置最小或最大 TTL；某些系统还会在上游故障时提供过期答案。操作系统、应用和代理也可能超出 DNS 规范地持有连接或解析结果。TTL 是设计切换窗口的重要参数，却不是全球所有用户绝对同步的开关。对重要迁移应保留旧目标可用、监测两端流量并设置可回退时间。

DNSSEC 用于验证 DNS 数据来源与完整性，但不会把 TTL 变成实时推送。HTTPS 证书、源站 Host 路由和负载均衡配置也必须覆盖新旧路径。域名解析正确而 TLS 证书不匹配，会把 DNS 迁移误表现为网站整体不可用。

诊断与验收

分别查询权威服务器和常用递归解析器的 A、AAAA、CNAME，记录 TTL 剩余值、响应码与最终地址。再用客户端实际连接日志或抓包查看访问的是哪个 IP。若本机 DNS 已返回 B，但连接仍向 A，检查连接池、浏览器缓存或应用固定解析；若递归返回旧记录，看其 TTL 是否仍有效。

切换验收应包括旧地址过渡期间仍能服务、部分用户解析到 B 后业务正常、负缓存样本可恢复以及回滚演练。不要在解析尚未收敛时删除旧服务器或撤销旧证书。

TTL 取值与负缓存的确切规则

场景推荐 TTL理由
稳定不变的记录（主站 A）3600 – 86400 s减少递归查询压力
准备切换/灰度中的记录60 – 300 s快速回滚；切换前至少一个旧 TTL 周期就要改
CDN / 负载均衡后的 CNAME300 – 3600 s交给 CDN 自己的调度
MX / TXT（邮件相关）3600 s 以上避免邮件服务频繁查询
故障演练 / 蓝绿切换30 – 60 s代价是递归查询量翻几十倍

负缓存（Negative Caching）：查询一个不存在的域名（NXDOMAIN）或类型不存在（NODATA）时，递归服务器也会缓存这个“不存在”的结果，时长取 SOA 记录中 MINIMUM 字段与 SOA 自身 TTL 的较小值（RFC 2308）。这就是为什么“刚创建的域名立刻查不到”——上一次的 NXDOMAIN 还在被缓存。

查看 TTL 与清缓存

# 查看权威返回的 TTL（第二列就是剩余 TTL，会递减）
dig example.com
# ;; ANSWER SECTION:
# example.com.        300     IN      A       93.184.216.34
#                     ^^^ 剩余缓存秒数

# 看负缓存时长：查 SOA 的最后一个字段
dig example.com SOA +multiline | grep -i minimum
# 或用一个肯定不存在的名字看 SOA 返回
dig this-does-not-exist-xyz123.example.com
# 返回的 AUTHORITY SECTION 里的 SOA 就带负缓存 TTL

# 逐级对比，判断是缓存还是权威问题
dig @8.8.8.8   example.com +short
dig @1.1.1.1   example.com +short
dig @ns1.example.com example.com +short   # 权威直查，绕过所有缓存

# 清本机缓存
sudo systemd-resolve --flush-caches        # systemd-resolved
sudo dscacheutil -flushcache               # macOS
ipconfig /flushdns                         # Windows

dig 输出里的 TTL 是递归服务器处的剩余时间，不是权威设定的原值；想看原值要直连权威服务器查询（dig @ns）。

缓存层级与常见坑

层级是否受 TTL 控制备注
浏览器缓存部分（Chrome 有独立 DNS 缓存，约 60 s）chrome://net-internals/#dns 可清
操作系统 / stub resolver是systemd-resolved、nscd、dnsmasq
本地递归 DNS（路由器/运营商）是，但可能强制最小值部分 ISP 无视短 TTL
公共 DNS（8.8.8.8 / 1.1.1.1）是通常较守规矩
Java JVM默认永久缓存（networkaddress.cache.ttl）需设 -Dsun.net.inetaddr.ttl=60，否则服务重启才生效
  • Java 的大坑：JVM 默认无限缓存 DNS 结果（安全策略），导致 DNS 切换后 Java 服务永远连老 IP，必须重启。生产上务必设置 networkaddress.cache.ttl=60（正数=秒）。
  • TTL=0 的坏处：每次解析都递归一次，DNS 成为可用性依赖项；递归服务器挂了就等于域名全挂。
  • 轮询负载不均：多条 A 记录做轮询时，客户端往往只用第一个，且被各级缓存“锁死”，流量分布极不均匀。要真正的负载均衡请用 LB 或 CDN。
  • 排障步骤：① 直连权威确认数据对；② 换多个公共 DNS 对比；③ 看 SOA MINIMUM 判断负缓存；④ 查本机/浏览器/JVM 缓存。
域名刚解析好，立刻 dig 却报 NXDOMAIN？

典型的负缓存：上一次查询的不存在结果被按 SOA MINIMUM 缓存了。等缓存过期或换一台递归 DNS 查即可。避免在正式解析前用不存在名字做过探测。

为什么相同 TTL 的两条 A 记录，返回的剩余 TTL 不一样？

因为它们是在不同时刻被缓存进递归服务器的，剩余时间各自递减。这是正常的，也说明解析结果来自缓存而非实时权威查询。

自检

先把 TTL 从一小时改成五分钟，是否能立即让所有旧缓存五分钟后失效？

不能。已缓存的旧记录仍按当时取得的一小时 TTL 倒计时；应提前降 TTL 并等待旧缓存过期。
