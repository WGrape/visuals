CDN 原理与搭建实战

从「为什么要 CDN」到「云接入 / 自建 Nginx 边缘节点」一次讲透

① 是什么② 核心原理③ 请求流程 ④ 关键概念⑤ 云CDN接入⑥ 自建CDN⑦ 自建vs云

1CDN 是什么，解决什么问题

CDN（Content Delivery Network，内容分发网络）= 把内容缓存在离用户更近的边缘节点上，让用户就近获取，而不是每次都跨地域打到源站。

🌍 降低延迟

用户从「本地边缘节点」拿数据，省去跨城/跨国长途，RTT 从几百 ms 降到十几 ms。

🛡️ 减轻源站压力

大部分请求被边缘节点命中，源站只需服务「未命中回源」的少量流量，扛得住突发峰值。

📈 提升可用与扩展

节点多、天然冗余；单点故障可被调度层绕开，整体可用性远高于单源站。

本质一句话：把「计算/存储离数据近」反转为「把数据副本放到离用户近」——用空间（多副本）换时间（延迟）和抗压能力。

2核心原理：调度 + 缓存 + 回源

CDN 三大支柱：调度（把用户导向最近的节点）、缓存（节点存内容）、回源（没有就找源站要）。

2.1 调度：怎么让用户「就近」？

DNS 调度（最常用）

用户访问 cdn.example.com，该域名 CNAME 到 CDN 厂商的调度域名；CDN 的权威 DNS 根据用户本地 DNS 的 IP 归属（地域/运营商）返回最近边缘节点的 IP。配置简单，但精度受「本地 DNS」位置影响。

HTTPDNS / 302 调度

APP 内置 HTTPDNS SDK 直接拿「用户真实 IP」向调度服务请求节点 IP，避免本地 DNS 偏差；或用 302 重定向把请求导到具体节点。精度高，需客户端配合。

Anycast（BGP 任播）

多个节点用同一个 IP 公告，由骨干网路由把用户包送到「网络最近」的节点。无需 DNS 解析差异，就近性极佳，但需自有 AS 与 BGP 能力（大厂/自建常用）。

IP 调度 / 边缘计算

在更靠近用户的 PoP 做 L7 路由与改写，结合实时负载做节点间二次分发，适合动态加速。

2.2 缓存与回源

命中 vs 回源：缓存命中率 = 命中数 / 总请求数。命中率越高，源站压力越小、成本越低。缓存未命中时，边缘节点才向上（父层或直接源站）回源取数据并缓存，供后续请求复用。

4必须掌握的关键概念

边缘节点 / PoP

部署在运营商骨干、离用户近的缓存服务器，是真正对外服务的节点。

源站 Origin

内容的「真相源」（你的对象存储 / 服务器）。CDN 只缓存副本。

缓存 TTL

资源在边缘的存活时间。到期或主动刷新后失效，下次回源。静态资源可设长（天级），动态资源短或不过期。

缓存命中率

核心 KPI。命中走边缘，回源走源站；命中率每升 1% 都直接省钱省压。

缓存刷新 / 预热

刷新：主动让边缘旧内容失效（URL/目录刷新）；预热：提前把内容推到边缘，避免首波用户回源「冷启动」。

回源 / 回源比

未命中请求打到源站的比例。回源比过高说明缓存策略有问题，源站会被打爆。

5方式一：接入云厂商 CDN（最省事）

适合绝大多数业务：不用运维节点，几步配置即可。以阿里云/腾讯云/CDN 通用流程为例。

配置要点

  • 源站：填你的服务器 IP、域名或对象存储（OSS/COS/S3）。建议源站仅对 CDN 回源 IP 开放（隐藏源站，见安全篇）。
  • 缓存规则：按文件后缀设 TTL——.jpg/.css/.js 长缓存（30d），.html 短缓存或不过期，带版本号 hash 的资源可永久缓存。
  • CNAME：把加速域名 CNAME 到厂商给的调度域名，DNS 解析即生效。
  • HTTPS：上传证书或在厂商申请免费证书，开启全链路 HTTPS（用户→CDN、CDN→源站可分别配置）。
  • 刷新/预热：发版后刷新对应 URL 或目录；大促前预热热点资源。

6方式二：自建 CDN（原理级实现）

当你有多地域服务器、想完全掌控或做特殊加速时，可用 Nginx 做边缘缓存 + 智能调度（DNS/Anycast） 拼出一个轻量 CDN。

6.1 边缘节点：Nginx 反向代理 + 缓存

每个边缘节点就是一个开了 proxy_cache 的 Nginx，把回源结果缓存下来，后续请求直接命中本地。

# nginx.conf —— 边缘节点缓存配置
proxy_cache_path /data/cdn_cache levels=1:2 keys_zone=edge_cache:200m
                 max_size=20g inactive=7d use_temp_path=off;

server {
    listen 80;
    server_name cdn.example.com;

    location / {
        proxy_pass http://origin_backend;   # 回源地址
        proxy_cache edge_cache;
        proxy_cache_key $scheme$host$request_uri;  # 缓存键
        proxy_cache_valid 200 302 7d;        # 200/302 缓存7天
        proxy_cache_valid 404 1m;
        proxy_cache_lock on;                # 回源合并，防雪崩
        proxy_cache_use_stale error timeout updating; # 源站挂时用旧内容

        add_header X-Cache-Status $upstream_cache_status; # HIT/MISS 便于观测
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

upstream origin_backend {
    server origin.example.com:80;   # 源站
    keepalive 32;
}
$upstream_cache_status：HIT 命中、MISS 回源、BYPASS 跳过、EXPIRED 过期、UPDATING 更新中、STALE 用旧值。拿它算命中率是标配。

6.2 调度层：让用户就近落到节点

方案 A：智能 DNS（geoip）

用 bind + geoip 或云解析，按用户本地 DNS 的 IP 地域返回不同边缘节点 IP。配置简单、零客户端改动，但精度受本地 DNS 位置影响。

# 伪配置：华北回北京节点，华南回广州节点
view "north" {
  match-clients { geoip:cn-north; };
  zone "cdn.example.com" {
    A 1.2.3.4;   # 北京节点
  };
}

方案 B：Anycast（BGP 任播）

各地节点用相同 IP 向运营商公告路由，骨干网自动把用户流量送到网络最近节点。就近最准，但需要自有 AS、IP 段与 BGP 运维能力——通常是大厂/专业 CDN 的选择。

6.3 节点间内容同步（可选）

简单架构下节点各自独立回源即可（命中率略低但实现简单）。若想「一处回源、多节点共享」可做父层/中间层：边缘 → 区域父节点 → 源站，父层缓存被多边缘复用，进一步降回源。也可用 rsync / 对象存储主动分发静态资源到各节点。

自建的代价：你要自己运维节点、监控、证书、调度、容量与故障切换，且单节点带宽/覆盖远不及商业 CDN。除非有多地域闲置服务器或强管控需求，否则首选云 CDN；自建更适合做「原理学习」或「特定链路加速」。

7自建 vs 云 CDN：怎么选

维度云厂商 CDN自建 CDN
接入成本低（控制台/API）高（搭节点+调度）
节点覆盖全球几百~上千 PoP仅你有的地域
运维负担厂商负责全部自己扛
可控性中（受限于产品）完全可控
成本模型按流量/带宽付费服务器+带宽固定投入
适用绝大多数业务、出海、突发峰值原理学习、特殊加速、强管控
一句话：生产业务直接上云 CDN（省心、覆盖广）；想深入理解 CDN 或做定制化加速，用 Nginx + 智能 DNS 自建一套做实验——原理完全一致。

缓存头与命中判定

CDN 的行为完全由源站返回的 HTTP 缓存头决定。配错头，CDN 就只会回源，白花钱。

响应头作用示例说明
Cache-Control: max-age=N浏览器缓存时长max-age=3600浏览器侧，不影响 CDN
Cache-Control: s-maxage=NCDN/共享缓存时长s-maxage=86400CDN 优先看这个
Cache-Control: public/private能否被共享缓存缓存publicprivate 的响应 CDN 不缓存
Cache-Control: no-cache可以缓存但每次要校验no-cache不是「不缓存」，是「先问」
Cache-Control: no-store完全不缓存no-store敏感数据用这个
stale-while-revalidate=N过期后先给旧的，同时后台刷新max-age=60, stale-while-revalidate=600显著降低回源与等待
stale-if-error=N源站出错时用旧副本stale-if-error=3600源站故障时的兜底
Vary按什么维度区分缓存Vary: Accept-EncodingVary 维度越多，命中率越低
ETag / Last-Modified协商缓存校验ETag: 'abc123'命中 304 可省掉传输

命中验证

# 看 CDN 到底有没有命中（各家头不同，但思路一致）
curl -I https://cdn.example.com/app.js
#   x-cache: HIT / MISS / EXPIRED        （阿里云/腾讯云常见）
#   cf-cache-status: HIT / MISS / DYNAMIC （Cloudflare）
#   age: 3600                             （该副本已缓存多少秒）
#   via / x-served-by                     （经过了哪些节点）

# 连续请求两次比较 age：age 一直为 0 说明每次都回源
for i in 1 2 3; do curl -sI https://cdn.example.com/app.js | grep -i '^age'; sleep 1; done

# 带条件请求验证协商缓存
ETAG=$(curl -sI https://cdn.example.com/app.js | grep -i etag | tr -d '\r' | cut -d' ' -f2)
curl -I -H "If-None-Match: $ETAG" https://cdn.example.com/app.js
#   返回 304 Not Modified 即协商缓存生效

源站缓存配置

# Nginx：按文件类型设置缓存策略（源站侧给 CDN 正确的信号）
location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|woff2)$ {
    # 带 hash 的静态资源可以长期缓存
    add_header Cache-Control 'public, max-age=31536000, immutable';
    add_header Vary 'Accept-Encoding';
    expires 1y;
}

location ~* \.(html)$ {
    # HTML 是入口，不能长缓存，否则发版不生效
    add_header Cache-Control 'public, max-age=0, must-revalidate';
}

location /api/ {
    # 接口默认不缓存；个别接口可单独开
    add_header Cache-Control 'no-store';
    proxy_pass http://backend;
}

# 开启 gzip/brotli 后必须加 Vary: Accept-Encoding，否则会串味
gzip_vary on;
场景缓存时长理由
带内容 hash 的静态资源（app.a1b2c3.js）1 年 + immutable内容变了文件名就变了，可永久缓存
不带 hash 的图片/字体1 天 ~ 7 天更新时靠刷新或版本号
HTML 入口页0 ~ 几分钟 + must-revalidate必须能立刻生效
API 响应不缓存（no-store）除非明确标注可缓存
用户个性化内容不缓存或 Vary 严格防串号（缓存事故高发区）
大文件下载按热度分层 + Range 支持支持 Range 才能续传

提升命中率最有效的三招：① 忽略查询字符串中不影响内容的参数（如 ?utm_source=）；② 减少 Vary 维度；③ 静态资源文件名带内容 hash后设为长期缓存。命中率每提升 10 个百分点，回源带宽与源站压力都直接下降。

回源、刷新与检查清单

概念含义典型配置
回源CDN 未命中时向源站取数据回源超时 5~30s，失败重试 1~2 次
回源 HOST回源请求带的 Host 头必须与源站虚拟主机配置一致，配错会 404
预热主动把资源推到 CDN 节点发版前预热热门资源，避免首次访问全回源
刷新（purge）主动清除 CDN 缓存按 URL / 目录刷新，有配额限制（常见每日数百~数千条）
缓存键用什么标识一份缓存默认 URL；可配置忽略参数、忽略大小写
分片回源大文件分块回源提升大文件首包速度

# 腾讯云：tccli cdn PurgeUrlsCache --Urls '["https://cdn.example.com/app.js"]'

#   -H 'Authorization: Bearer $TOKEN' -H 'Content-Type: application/json' \
#   -d '{"files":["https://cdn.example.com/app.js"]}'

# 刷新有配额，改名的成本更低：发版时文件名带 hash，就永远不用刷新
#   app.js -> app.3f2a1b.js

上线前逐条核对：

  • 静态资源文件名带内容 hash，然后设 1 年缓存 + immutable，可彻底免刷新。
  • HTML 入口不设长缓存，否则发版后用户看到的还是旧页面。
  • 开启 gzip/brotli 必须配 Vary: Accept-Encoding，否则压缩与非压缩版本会串。
  • 个性化响应不能缓存，或用 Vary: Cookie 严格区分（后者命中率极低）。
  • 忽略不影响内容的查询参数（utm、timestamp），命中率能显著提升。
  • 回源 HOST 要与源站虚拟主机一致，配错的表现是全站 404。
  • 源站要能承受全量回源：刷新缓存或节点故障时会瞬间放大流量，需要限流保护。
  • 监控命中率与回源带宽：命中率突降通常说明缓存头被改坏了。
  • 刷新有配额且是异步的，不要依赖它做紧急回滚，改文件名更可靠。
  • HTTPS 证书要在 CDN 侧配置，且注意回源是 HTTP 还是 HTTPS（影响链路加密范围）。
  • 开启 stale-if-error：源站短暂故障时用户仍能看到旧内容。
