📖 当前阶段说明

Redis 的字典（dict）内部使用两个哈希表：ht[0] 和 ht[1]。

平时只有 ht[0] 在工作，ht[1] 处于未分配状态。

当负载因子（used / size）超过阈值时，Redis 会触发扩容，分配一个更大的 ht[1]，然后渐进式地把 ht[0] 的元素搬过去。

为什么不一次性搬完？

Redis 的字典（dict）用哈希表实现。当负载因子过高/过低时需要 rehash（扩容或缩容）。如果像教科书那样一次性搬迁所有桶，一个存了几千万个键的实例会造成秒级甚至分钟级阻塞——这在单线程模型下是不可接受的。所以 Redis 采用渐进式 rehash：同时持有 ht[0] 与 ht[1]，每次增删改查顺手搬一个桶，把一次大停顿摊薄成无数次极小开销。

触发扩容负载因子 = used/size ≥ 1（无 BGSAVE）或 ≥ 5（有子进程）
触发缩容负载因子 < 0.1 时收缩，避免稀疏表浪费内存
rehashidx记录搬迁进度；-1 表示未在 rehash
新表大小扩容为大于 used*2 的第一个 2^n；缩容同理取最小够用的 2^n
搬迁节奏每次 CRUD 搬 1 个桶 + 定时事件（serverCron）辅助搬 100 个桶
结束条件全部搬完后 ht[0] 释放，ht[1] 变为 ht[0]，rehashidx 归 -1
两表并存 + rehashidx 游标：把 O(N) 停顿摊成 O(1) 增量

rehash 期间的读写规则

操作在 rehash 期间的行为原因与设计考量
查找（GET/HGET 等）先查 ht[0]，未命中再查 ht[1]数据分散在两张表，必须都查；代价是至多两次哈希查找
插入（SET/HSET 等）只写入 ht[1]保证 ht[0] 只会越搬越少，不会新增，搬迁必然收敛
删除 / 更新两张表都要处理目标键可能在任一表中
遍历（SCAN）两张表都会遍历，并对同一键做去重避免漏键；扩容期间可能重复返回少量键
阻塞风险单次只搬一个桶，单桶元素过多时仍可能偏慢大 Key（百万字段 Hash）的一个桶很长，这是大 Key 危害的根源之一
RDB/AOF 期间有子进程时提高扩容阈值（负载因子 5）利用 Copy-On-Write 特性，避免在 fork 后频繁写导致内存暴涨

关键副作用：rehash 进行中，内存占用是「旧表 + 新表」之和。一个占 10GB 的实例在扩容瞬间会短暂接近 20GB，若机器内存不足会触发 OOM 或开始淘汰。这就是为什么必须给 maxmemory 留足余量。

工程实践与排查

① 什么时候会 rehash

  • 写入量持续增长，键数量跨过表大小的阈值。
  • 大量删除后负载因子低于 0.1，触发缩容（通常发生在清空缓存、批量过期后）。
  • 扩容阈值在有 BGSAVE/BGREWRITEAOF 子进程时放宽到 5，避免 COW 内存暴涨。

② rehash 会造成卡顿吗

  • 正常情况不会：每次只搬一个桶，是 O(1) 级别。
  • 例外：单个桶的链表很长（哈希冲突严重或大 Key），搬这个桶就要遍历整条链。
  • 另有定时任务在空闲时主动搬 100 个桶（有 1ms 时间上限），避免客户端不活跃时永远搬不完。
  • 表现：INFO 里 dict_rehash 相关计数增长、延迟毛刺。

③ 如何降低影响

  • 避免超大 Key：一个 Hash 别塞几十万字段，拆成多个键。
  • 预留内存：maxmemory 设置要考虑 rehash 峰值（建议不超过物理内存 70%）。
  • 批量删除会触发缩容 rehash，尽量错峰或分批。
  • 关注 mem_fragmentation_ratio 与 used_memory 曲线。

④ 与 SCAN 的关系

  • SCAN 在 rehash 期间会同时扫描两张表并去重，保证不漏。
  • 但扩容中的键可能被返回两次，业务侧要幂等。
  • 缩容期间则可能出现少量键未被返回（设计上接受的权衡）。
  • 需要严格全量时，别依赖 SCAN，用离线 RDB 分析。

深入自检

渐进式 rehash 解决了什么问题？

解决了一次性 rehash 的长时间阻塞。Redis 单线程处理命令，若一次性搬迁千万级键，会造成秒级以上的停顿，所有客户端请求被挂起。渐进式把搬迁拆到每次命令执行中，每次只搬一个桶，把不可用的长停顿变成可接受的微小开销。

为什么插入只写新表？

这是保证搬迁能收敛的关键。如果新写入还进旧表，旧表可能永远搬不完（边搬边涨）。规定「新增只进 ht[1]」后，ht[0] 的存量只减不增，搬迁必然在有限步内结束。

为什么有子进程时扩容阈值放宽到 5？

因为 BGSAVE/BGREWRITEAOF 依赖 fork 的写时复制（COW）。rehash 会大规模迁移内存页，导致大量页被修改、被复制，内存占用可能暴涨甚至触发 OOM。放宽阈值可以尽量避免在有子进程时做大规模内存迁移。

rehash 期间为什么内存会翻倍？

因为两张哈希表同时存在：ht[0] 还持有未搬走的数据，ht[1] 已分配为更大的空间。在搬迁完成前，进程需要同时容纳两者。峰值大约是「旧表实际占用 + 新表容量」，接近翻倍。所以容量规划必须给 rehash 留余量。

大 Key 为什么在 rehash 时特别危险？

因为搬迁的最小单位是一个「桶」，如果某个键（如百万字段的 Hash）本身非常大，它所在的桶链表很长，搬这个桶就要遍历并重新计算大量元素，单次操作耗时可达毫秒级，表现为明显延迟毛刺。这也是为什么要拆分大 Key。

搬迁过程中如果不再有请求怎么办？

Redis 有兜底：时间事件（serverCron）会主动执行 rehash，一次最多搬 100 个桶并受 1ms 时间限制。这样即使客户端完全空闲，搬迁也会持续推进并最终完成，不会永久停在中间状态。
