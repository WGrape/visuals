推理成本怎么算：从 GPU 时租到单 token 成本

三输入成本模型、四个降本杠杆的性价比排序、五个监控指标

推理成本GPU批处理量化缓存
① 成本模型 ② 降本杠杆 ③ 监控指标 ④ 疑问
推理成本 = 单卡每秒成本 ÷ 单卡每秒输出 token 数 ÷ 利用率。把这三个数算清楚，才能判断「换小模型 / 上量化 / 加批处理」哪个更划算。

01成本模型的三个输入

输入怎么得到典型量级注意
单卡每秒成本时租 ÷ 3600A100 约 1~2 美元/时 → 约 0.0003~0.0006 美元/秒含机器其他成本则再 ×1.3
单卡输出吞吐压测实测（benchmark_serving）7B 模型、批 32 时通常几十~几百 tokens/s不能按理论算力算，实测才准
利用率GPU 忙时占比（DCGM / nvidia-smi 采样）线上常见 30%~60%，做好的能到 80%+这是最大的降本空间
输入 token 成本与输出分开算Prefill 通常比 Decode 便宜（可批处理）长 prompt 场景不能忽略
# 手算示例（数字仅示意，替换成自己的实测值）
gpu_hourly = 2.0                    # 美元/小时
per_sec    = gpu_hourly / 3600      # 0.00056 美元/秒
out_tps    = 200                    # 实测：单卡输出 200 tokens/s
util       = 0.5                    # 实测：GPU 利用率 50%

cost_per_token = per_sec / out_tps / util
print(cost_per_token)               # 5.6e-6 美元/token
print(cost_per_token * 1000 * 7.2)  # 每百万 token 约 40 美元（按 1 美元=7.2 元折算约 288 元）

# 同样配置下把利用率提到 80%：
print(per_sec / out_tps / 0.8 * 1e6)  # 直接降到 3.5 美元/百万 token，降幅 30%
要点：算成本时最容易漏掉的是利用率。很多团队只算「跑满时能到多少 tokens/s」，而线上实际只用了 30%~50%，真实成本是理论值的 2~3 倍。

02四个降本杠杆，按性价比排序

杠杆典型收益代价优先级
提高利用率（连续批处理、错峰、合并小请求）成本降 30%~50%调度改造，几乎无质量损失① 最高
缓存与去重（prefix caching、结果缓存）命中率高时可降 50%+需要缓存策略与失效管理② 高
模型路由（简单问题走小模型）按分流比例线性下降需要一个分类器或规则③ 中高
量化（FP8 / INT8 / INT4）显存与带宽省 2~4 倍精度损失，需评估集验证④ 中
蒸馏 / 换小模型成本降一个数量级能力下降明显，需重新验证⑤ 视业务而定
投机解码延迟降 1.5~3 倍（吞吐提升有限）需 draft 模型与接受率调优⑥ 延迟敏感时才做

def route(q):
    if is_simple(q):        # 规则或小模型判断

03要监控的五个指标

  • GPU 利用率：低于 50% 说明调度或批处理有巨大空间，是最该看的一个数。
  • 每请求 token 数（输入 + 输出）：直接决定成本，异常增长通常意味着提示词失控或死循环。
  • TTFT 与 TPOT：分开看。TPOT 升高往往意味着批处理过大或显存压力。
  • 缓存命中率：命中率下降说明系统提示词被频繁改动，或请求顺序不利于复用。
  • 单请求成本：按业务维度（用户/功能）拆分，才能知道哪个功能最烧钱。

04常见疑问

问：自建一定比调 API 便宜吗？

不一定。自建有固定成本（机器、运维、闲置），只有在利用率能做高、且规模足够大时才划算。粗略判断：如果 GPU 利用率长期低于 40%，或者每天请求量不足以让一张卡持续忙碌，调 API 通常更便宜。

问：量化到底损失多少精度？

FP8 几乎无损（多数任务上差异 < 1%），INT8 在复杂推理任务上可能掉几个点，INT4 需要看具体任务。必须先有评估集再决定，不能只看困惑度。

问：为什么我加了批处理，延迟却变差了？

因为批越大，单个请求排队越久、Prefill 越慢。批处理提升的是吞吐，不是延迟。要为延迟和吞吐分别设上限：批大小按 SLO 反推，而不是越大越好。

问：怎么判断该不该用小模型？

做一个抽样评估：拿 200~500 条真实请求，分别跑大模型和小模型，人工或模型打分对比。如果小模型在简单子集上达标，就按难度路由；不要用「感觉差不多」来决定。
