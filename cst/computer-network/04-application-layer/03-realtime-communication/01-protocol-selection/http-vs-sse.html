四种「实时」方案的取舍

浏览器要与服务端保持「实时」，有四条路：轮询（定时问）、长轮询（挂着等）、SSE（服务端单向推）、WebSocket（双向全双工）。它们不是替代关系，而是「延迟、开销、复杂度」三个维度上的不同落点。

轮询简单、兼容性最好；空响应多、延迟取决于间隔
长轮询减少空响应；每次要重连，服务端要hold 住连接
SSE基于 HTTP、单向推送、自动重连、天然文本流
WebSocket独立协议、双向、低开销；需处理心跳/重连/代理
SSE 优势复用 HTTP 基础设施、断线自动重连、实现极简
WS 优势双向、二进制、延迟最低、适合高频交互

选型一句话：只需要服务端往客户端推（通知、进度、AI 逐字输出）→ SSE 最省事；需要双向高频（聊天、协同、游戏）→ WebSocket；数据本来就慢 → 轮询也够用，别过度设计。

SSE 实战要点

① 服务端怎么写

  • 响应头：Content-Type: text/event-stream、Cache-Control: no-cache。
  • 建议 X-Accel-Buffering: no（Nginx 下避免被缓冲）。
  • 消息格式：data: xxx\n\n，可用 event: 与 id:。
  • 定期发注释行 : ping\n\n 保活，防止中间设备超时断开。

② 客户端怎么用

  • new EventSource(url)，监听 message 或自定义事件名。
  • 断线会自动重连，可用 id / Last-Event-ID 实现续传。
  • 注意：原生 EventSource 只能 GET，不能带自定义请求头（需带 token 时放 URL 或改用 fetch 流）。
  • 浏览器对同域 HTTP/1.1 连接数有限制（6 个），SSE 会占掉一个。

③ SSE 的局限

  • 只能服务端→客户端，客户端要发数据还得走普通请求。
  • 只支持 UTF-8 文本（二进制要 base64）。
  • HTTP/1.1 下占用连接数；HTTP/2 下多路复用可缓解。
  • 某些代理/网关会缓冲，需要正确设置响应头与关闭缓冲。

④ 为什么 LLM 流式输出偏爱 SSE

  • 交互模式正好是「一次请求、服务端持续吐 token」——单向推送。
  • 基于 HTTP，穿越代理与网关无障碍，无需额外协议支持。
  • 浏览器原生支持且自动重连，前端实现只需几十行。
  • OpenAI 等主流 API 的 streaming 模式正是 SSE（data: {...} + [DONE]）。

深入自检

SSE 和 WebSocket 到底选哪个？

看是否需要客户端持续向服务端发送数据。只需要服务端推（通知、进度、流式输出）→ SSE，因为它复用 HTTP、自动重连、实现简单；需要双向实时（聊天、协同、游戏）→ WebSocket，它的帧开销更小、支持二进制、延迟更低。很多系统其实两者混用：控制信令走 WebSocket，日志/进度走 SSE。

SSE 为什么会被 Nginx 缓冲住？

因为 Nginx 默认会缓冲上游响应，导致 event-stream 不能实时到达客户端。解决办法：设置 X-Accel-Buffering: no 响应头（或在 Nginx 配置 proxy_buffering off），并关闭 gzip 缓冲。类似地，某些 CDN 与云网关也需要额外配置才支持流式。

EventSource 不能自定义请求头怎么办？

原生 EventSource 确实不支持自定义 header（如 Authorization）。常见做法：① 把 token 放在 URL 查询参数（注意泄漏风险与日志）；② 用 cookie 鉴权（同域）；③ 改用 fetch + ReadableStream 手工解析 SSE 格式（灵活性最高，但要自己处理重连）。

长轮询还有存在的价值吗？

有，主要在兼容性与环境限制场景：一些老旧代理、企业网关对长连接支持不好，或者服务端框架难以 hold 住大量并发连接。它的优势是每次都是普通 HTTP 请求，穿透性最好。但新项目若环境允许，通常优先 SSE 或 WebSocket。

SSE 的连接数限制会带来什么问题？

HTTP/1.1 下浏览器对同一域名通常只允许 6 个并发连接，每个 SSE 会长期占用一个，多个标签页或页面里多个 SSE 可能把连接池占满，导致其他请求排队。解决：使用 HTTP/2（多路复用）、合并成一个 SSE 通道用事件名区分、或用 SharedWorker 共享连接。

流式输出时前端要注意什么？

四点：① 增量渲染要节流（每帧合并更新），避免频繁 DOM 操作；② 处理不完整的多字节字符（先缓冲再解码）；③ 服务端可能中途出错，要约定错误事件与结束标记（如 [DONE]）；④ 做好取消（AbortController）与超时，避免用户离开后还在接收。此外要考虑 Markdown 增量渲染的解析器兼容。
