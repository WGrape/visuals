CPU 性能剖析

先量化再优化——用 top、perf 与火焰图把 CPU 热点看清楚。

为什么要先量再调

量化为先

没有基线的优化都是盲调。先用 top、vmstat、pidstat 拿到 CPU 使用率、用户态/内核态占比与上下文切换次数，建立「优化前」的数字，才能判断改动是否有效。

性能优化遵循「测量 → 定位 → 假设 → 验证」的循环，第一步永远是拿到可复现的负载和明确指标。

CPU 时间分为 用户态（user） 与 内核态（sys）。user 高通常是算法或逻辑自身消耗；sys 高往往是频繁系统调用、锁竞争或上下文切换。

定位热点的三件套

工具看什么典型信号
top / htop整体与进程占用某进程长期 100%
pidstat -u分线程、分核个别线程异常
perf调用栈热点某函数占比高

火焰图怎么读

火焰图读法

横轴是采样数量（非时间顺序），纵轴是调用栈深度；越宽的方块占用 CPU 越多。找最宽且靠近顶层的方块，就是最值得优化的热点函数。

用 perf record -F 99 -g 采样，再用 FlameGraph 脚本生成 SVG，即可在浏览器里层层下钻。

问题 1
CPU 使用率 100% 一定有问题吗？

不一定。单进程跑满一个核可能是正常的高负载计算；但要警惕 多核整体 100% 且吞吐没上去——那往往是死循环、锁竞争或频繁 GC。

问题 2
user 高和 sys 高怎么区分对待？

user 高优先看算法与热点函数（perf 火焰图）；sys 高优先看系统调用次数与上下文切换（vmstat 1 的 cs 列）以及锁竞争（perf lock）。

问题 3
火焰图为什么顶层方块不代表瓶颈？

顶层是采样时正在执行的函数，但瓶颈常在被它反复调用的「宽」函数上。应沿最宽路径从下往上看，找到占比最高且可优化的那一帧。

问题 4
Go / Python 的栈能被 perf 抓到吗？

Go 自带 pprof 直接采样 CPU 火焰图；CPython 因 GIL 与解释执行，需 py-spy 或 perf 配合调试符号才能看到 Python 层栈。
