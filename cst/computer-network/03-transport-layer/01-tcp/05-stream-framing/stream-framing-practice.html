TCP 流边界实战：长度前缀 / 分隔符 / JSONL 怎么写对

应用层如何把字节流切成完整消息：四种方案、可直接抄的实现、五个高频坑。

TCP网络编程粘包帧
长度前缀 分隔符 坑 选型
TCP 是字节流，没有消息边界。应用层必须自己把字节流切成一条条消息：长度前缀、分隔符、JSONL、protobuf 变长，四种各有所长。这里给可直接照抄的实现与排雷清单。

01长度前缀帧：最通用

先发 4 字节大端长度，再发 payload。读端先读满 4 字节拿到长度，再读满 payload。这是 RPC / 消息队列最常用的方案。

// Go：写一帧（4 字节大端长度 + body）
func writeFrame(w io.Writer, body []byte) error {
    var hdr [4]byte
    binary.BigEndian.PutUint32(hdr[:], uint32(len(body)))
    if _, err := w.Write(hdr[:]); err != nil { return err }
    _, err := w.Write(body)
    return err
}

// 读一帧：先读长度，再读足 body；net.Conn 不保证一次读全
func readFrame(r io.Reader) ([]byte, error) {
    var hdr [4]byte
    if _, err := io.ReadFull(r, hdr[:]); err != nil { return nil, err }
    n := binary.BigEndian.Uint32(hdr[:])
    buf := make([]byte, n)
    if _, err := io.ReadFull(r, buf); err != nil { return nil, err }
    return buf, nil
}

# Python：struct 打包长度（网络字节序 '>I' = 4 字节无符号）
import struct, socket
def send_frame(sock, body: bytes):
    sock.sendall(struct.pack('>I', len(body)) + body)
def recv_frame(sock):
    hdr = recv_exact(sock, 4)          # 循环读满 4 字节
    n = struct.unpack('>I', hdr)[0]
    return recv_exact(sock, n)
def recv_exact(sock, n):
    buf = b''
    while len(buf) < n:
        chunk = sock.recv(n - len(buf))
        if not chunk: raise ConnectionError('peer closed')
        buf += chunk
    return buf

02分隔符与 JSONL

文本协议（如 Redis 的 RESP、日志管道）常用换行或特定分隔符。' ' 分隔的 JSON Lines 可读性最好，但 body 本身不能含未转义的换行；需要转义时改用 netstring 或长度前缀。

# Python：JSONL 一行一条消息，send 端每条加 \n
import json
def send_jsonl(sock, obj):
    sock.sendall((json.dumps(obj) + "\n").encode())
def recv_jsonl(sock):
    buf = b''
    while True:
        buf += sock.recv(4096)
        if b'\n' in buf:
            line, buf = buf.split(b'\n', 1)
            return json.loads(line.decode())   # 注意 buf 需缓存到下次

03五个高频坑

  • partial read：一次 recv 可能只到半条消息，必须循环读到满足长度再解析。
  • 粘包：两次 send 可能被 TCP 合并成一次 recv，读端按长度切，永远别假设一次 recv 对应一条消息。
  • 拆包：一条消息可能分两次 recv 才到全，buf 必须跨调用缓存。
  • Nagle + 小包：频繁发小帧会等合并，延迟飙升，交互式协议设 TCP_NODELAY。
  • 长度上限：必须校验 n，拒绝超大值（防内存打爆），例如 cap 在 16MB 以内。
要点：核心心法：先按「长度/分隔符」把字节流切成完整帧，再对整帧做反序列化。任何直接 json.loads(sock.recv(...)) 的写法都是错的。

第一层 · 概念与判定：为什么要自己分帧

TCP 是字节流，没有消息边界。你 write 两次、对方可能一次 read 全收（粘包）或一次只收到半条（拆包）。任何「应用层协议」都必须自己定义帧边界。

方案适用不适合
长度前缀二进制/高性能协议纯文本调试
分隔符（如 \n）JSONL/文本行内容可能含分隔符
定长字段固定且小变长消息
结束标记 + 转义简单文本需额外转义逻辑

第二层 · 参数·命令·量化：长度前缀怎么写对

项建议
长度字段宽度4 字节 uint32 足够（最大 4GB 消息）

长度前缀收发（含防半包/粘包/上限）

# 长度前缀：先发 4 字节长度，再发 body（Python 示例）
import struct, socket
def send_msg(sock, body: bytes):
    sock.sendall(struct.pack('>I', len(body)) + body)

def recv_msg(sock):
    hdr = b''
    while len(hdr) < 4:
        hdr += sock.recv(4 - len(hdr))      # 循环收满头
    n = struct.unpack('>I', hdr)[0]
    if n > 16 * 1024 * 1024: raise ValueError('frame too large')
    buf = b''
    while len(buf) < n:
        buf += sock.recv(n - len(buf))      # 循环收满 body
    return buf

数量级：4 字节长度单帧最大 4GB；生产一般把上限设 1–16MB，超过说明该换分片或流式传输。

第三层 · 排障与边界：五个高频坑

  • 半包：一次 recv 没收满帧——必须循环读直到满足长度，不能假设一次 recv 收全
  • 粘包：一次 recv 收到两条——按长度切分，剩余字节留作下一帧缓冲
  • 长度字段被当 body：长度含义（含不含头）两端不一致，解析全错位
  • 整数溢出：用 2 字节长度却被超长消息撑爆——按消息上限选宽度
  • 分隔符误吞数据：用 \n 分隔但 body 含换行——要么转义，要么改用长度前缀

第四层 · 原理与取舍

为什么 TCP 不替我们保留消息边界？

因为 TCP 的设计目标是可靠字节流，不是消息。它只保证字节顺序和送达，把「消息」概念留给应用层，才能灵活适配各种协议（HTTP/2 帧、gRPC、自定义二进制）。如果硬要保留边界（如 UDP 的 datagram），就牺牲了流控、拥塞控制、重传——这正是 UDP 快但不靠谱的原因。所以分帧是应用层必须自己做的事。

长度前缀和分隔符哪个更好？

长度前缀更通用、可含任意二进制（性能协议首选），代价是解析时要先读头再读体、要处理半包；分隔符（JSONL 用 \n）可读、易调试、天然流式，但 body 不能含分隔符，否则要转义。经验：内部高性能二进制用长度前缀；对外/日志/管道用 JSONL 分隔符，省去自研解析。

为什么还要给长度设上限？

因为读帧前要先信任对端给的「长度」，若对端发来或乱码产生一个 4GB 的长度值，接收方会尝试分配/等待 4GB 内存或数据，直接 OOM 或被慢速攻击拖死。上限把风险封死：超过即断连，是防御性编程的基本动作，和「读文件限制大小」同理。
