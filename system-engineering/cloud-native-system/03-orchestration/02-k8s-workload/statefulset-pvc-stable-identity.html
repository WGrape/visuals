StatefulSet 与 PVC：Pod 重建后名字没变，数据就一定安全吗

沿 db-0 故障重建，区分稳定身份、卷声明、物理存储与数据库复制。

无状态副本和有状态副本的差别

普通 Web 服务的三个 Pod 可以互换，请求发给任何一个都能处理；数据库节点常有成员 ID、日志位置和本地数据，不能随意当成相同副本。StatefulSet 给每个副本稳定序号和名字，例如 db-0、db-1、db-2；结合无头 Service 可获得可预测的网络身份。它还可通过 volumeClaimTemplates 为每个序号创建独立 PVC，使 db-0 重建后仍引用自己的持久卷声明。

“稳定”指控制器努力维持标识和存储关联，不表示 Pod 永远不重启、IP 永不变，也不表示数据库数据自动复制到别的节点。网络身份通常依靠名字与 DNS，具体记录可用性受 Pod Ready 状态与 Service 配置影响；客户端仍应处理连接失败与重试。

db-0 故障的时间线

起初 db-0 挂载自己的 PVC，写入一批日志。节点故障后，旧 Pod 不再正常提供服务，控制器尝试在合适节点重建 db-0。新 Pod 使用同一序号、同一 PVC 声明和稳定名字；能否成功挂载取决于底层 PV、存储访问模式、拓扑位置、卷附着和旧节点是否完成安全卸载。若卷只允许单节点读写，在旧节点状态未知时，新节点可能需要等待卷分离，避免同时写同一块存储。

一旦新 Pod 能挂卷，文件是否完整仍取决于数据库的刷盘、日志恢复与存储可靠性。StatefulSet 不验证数据页校验和，也不会自动修复业务层复制协议。若底层 PV 本身损坏，固定名字也救不回数据；应有备份、复制和恢复演练。

PVC、PV 与存储类各负责什么

PVC 是工作负载提出的容量、访问模式等存储需求；PV 是满足它的实际存储资源抽象；StorageClass 通常定义动态供应方式与参数。绑定后，PVC 为 Pod 提供相对稳定的存储引用。删除 Pod 通常不会自动删除对应 PVC，但删除 StatefulSet、缩容以及设置了 PVC 保留策略后的具体行为需要按版本与配置核对。不能以为“缩容后旧卷一定永远保留”，也不能未经确认就手工删除卷。

存储访问模式如 ReadWriteOnce 描述底层访问约束，不等于数据库可以多进程安全写入；即使存储允许多节点共享，数据库文件格式未必允许并发写。网络文件系统的持久化与锁语义也会影响数据库正确性。选择卷时要同时考虑延迟、吞吐、可用区拓扑和恢复时间。

层次提供什么不保证什么
StatefulSet稳定 Pod 序号数据库复制
Headless Service可预测的成员 DNS固定 IP 或固定主节点
PVC/PV存储声明与实际卷内容绝不损坏
数据库日志恢复与选主底层卷必定可用

顺序创建与滚动更新

StatefulSet 默认通常按序创建和删除 Pod，配合 Ready 状态推进，有利于有序启动；也有并行 Pod 管理策略可选。滚动更新时如何逐个替换，仍要确认数据库自己的主从关系、仲裁和升级兼容性。控制器保证 Kubernetes 资源趋近目标状态，不了解数据库当前领导者是否可安全下线。

三副本数据库如果升级时同时失去两份有效副本，可能失去多数派。即便控制器逐个更新，也要检查每一步成员是否追平、剩余仲裁是否足够、客户端是否正确切换。数据库 Operator 能编码部分领域规则，但也须审查它的故障与升级流程。

服务发现和读写路由

Headless Service 可让客户端发现每个有身份的 Pod，但“知道 db-0 地址”不代表 db-0 永远是主节点。领导者可能切换到 db-1，应用需要通过数据库协议、代理或 Operator 提供的服务路由找到正确写入口。把 StatefulSet 序号硬编码成主从角色，会在故障切换后写错位置。

Pod IP 会变化，DNS 记录也有缓存和生效时间；长连接在重建后需要重连。若使用固定域名做成员互联，要验证启动与就绪探针、DNS 解析、网络策略和证书里的名字一致。稳定身份减少发现成本，不能消除网络故障。

一套最小演练

部署三副本测试库，记录 db-0 的 Pod 名称、IP、PVC、PV 与数据库日志位置。删除 db-0 Pod，观察新 Pod 名字保留、IP 可能变化、PVC 是否仍绑定同一卷；再模拟节点不可用，观察卷分离与重新挂载耗时。最后验证数据库集群成员关系、已提交数据和主节点路由。演练完成后测试备份恢复，而不是只测试 Pod 自动重建。

自检

新 Pod 仍叫 db-0 并挂上原 PVC，能否据此断言数据一定完整且它仍是主节点？

不能。存储完整性与数据库主从选举由各自机制保证，StatefulSet 只管理身份和资源关联。
