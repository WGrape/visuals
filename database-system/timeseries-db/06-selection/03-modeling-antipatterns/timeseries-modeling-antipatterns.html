①高基数：时序库的头号杀手

基数（cardinality）指"时间序列的总数"——它等于所有标签取值组合的数量。时序库的索引和内存开销随基数线性甚至超线性增长，高基数会让写入变慢、内存暴涨、查询超时。这是时序库区别于关系库最关键的性能维度。

一条铁律：序列数 = 标签 A 取值数 × 标签 B 取值数 × …。任何一个高基数字段做标签，都会让总序列数爆炸。

②标签设计的反模式

  1. 用用户 ID / 设备 ID 做标签：若有 1000 万用户，每个用户一条序列，直接千万级基数，内存和索引崩掉。
  2. 用随机数 / 时间戳 / 请求 ID 做标签：每个样本都是"新序列"，索引无限增长，这是最致命的一种。
  3. 标签组合爆炸：3 个各有 1000 取值的标签，组合出 10 亿序列。
  4. 把本应是指标的量做成标签：如把"响应码 200/500"当标签而非用不同指标名。

③反模式案例

做法后果序列数
user_id 做标签每用户一条线= 用户数（可达千万）
request_id 做标签每请求一条线= 请求数（无限）
status(200/500) 做标签可接受= 少量枚举
region/service 做标签推荐= 少量枚举

正解：把高基数维度放在指标名或度量值里（如按 user_id 聚合后的指标），把低基数、用于分组过滤的维度（region、service、status）做标签。

④建模取舍：什么该做标签

判断标准：这个维度是否会用来分组/过滤，且取值是否可控（低基数）？ 是 → 标签；否（高基数或仅做展示）→ 用指标名/字段/外部关联表承载。

# 反例：user_id 做标签 → 百万序列
cpu_usage{user_id="u_88231", region="cn"} 10.2

# 正例：user_id 不作为标签，低基数维度才做标签
http_requests_total{service="api", status="500", region="cn"} 12

⑤监控与治理高基数

上线前用基数估算公式算一遍；运行中监控各指标的 series 数，对异常增长设告警；定期对"影子/孤儿"序列做清理（TTL 或 drop 规则）。

标签设计决策表

维度是否做标签理由
region / cluster是低基数、常分组
service / pod谨慎pod 数可能上千，按 service 更稳
status code是固定少量枚举
user_id / device_id否高基数，改用指标名或聚合
trace_id / request_id绝对否无限增长，致命

基数影响量化

设标签取值数分别为 a、b、c，则序列数 ≈ a×b×c。例：service(20) × region(5) × status(3) = 300 序列（健康）；若再乘 user_id(1,000,000) → 3 亿序列（灾难）。经验上限：单实例建议控制在百万级序列以内，超了要考虑拆分集群、降维度或换方案。

排障：查询变慢/内存暴涨的根因

绝大多数时序库性能问题根因是高基数：索引（倒排/标签索引）占用内存随序列数增长，查询要扫描大量序列。

定位：看各指标的 series 数排名、找突然暴涨的指标；止血：下线/改写高基数标签、加 drop 规则、提高 TTL 让孤儿序列过期。

自检 Q&A

高基数指标已经上线了怎么办？

先止血：用 relabel/drop 规则丢弃高基数标签维度，或只保留聚合后的指标；再治理：把高基数维度移出标签，改存到可外部关联的地方（如日志/明细表），指标只保留低基数分组。

为什么关系库不怕高基数、时序库怕？

关系库按行存、按主键/索引查，基数高只是行多；时序库要把每个唯一标签组合当成一条独立的时间线来维护索引与内存，基数高等于“线”多，而线数直接决定内存与写入开销。

InfluxDB/TDengine/VM 对高基数态度一样吗？

本质都一样怕高基数，但实现不同：InfluxDB 的 series 基数、VM 的时间线、TDengine 的子表数，都是同一类问题。缓解手段也都是“把高基数移出标签/子表键”。
