🚦 状态

把不同状态下的行为分给不同状态对象。

一句话记住地铁闸机在“锁定”和“已解锁”时，对推门动作反应不同。
问题从哪来图解协作动手试一试伪代码选型与边界
01 · 从问题出发

为什么会需要这个模式？

订单的待支付、已支付、已取消对 cancel/pay 有不同规则；巨型 if/else 难以维护。

订单有待支付、已支付、已取消。pay 和 cancel 在每个状态下的行为不同；若状态数和操作数都增长，一个巨型 switch 会变成难以检查的状态转移矩阵。

😵 直接写会怎样

function pay(order):
  if order.status == PENDING: charge(); order.status = PAID
  else if order.status == PAID: return AlreadyPaid
  else if order.status == CANCELLED: return Invalid
// cancel、refund 等函数再重复判断 status

💡 关键转折

Context 持有当前 State；每个状态决定可执行动作和下一状态。

让订单把操作委托给当前 State。每个状态对象定义此时可做什么、何时迁移到哪个状态。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

interface OrderState { pay(order); cancel(order) }
class Pending implements OrderState {
  pay(order) { charge(order); order.state = new Paid() }
  cancel(order) { order.state = new Cancelled() }
}
class Paid implements OrderState {
  pay(order) { return AlreadyPaid }
  cancel(order) { return RefundRequired }
}

读代码时抓住三件事

  1. Context 对外保持稳定操作接口，并持有当前 State。
  2. 具体状态实现此时的行为与合法转移。
  3. 外部副作用失败时不能提前切换状态，要明确定义事务顺序。

换个业务场景，还能认出来吗？

网络连接可处于 Disconnected、Connecting、Connected；send() 在三个状态下分别拒绝、排队或真正发送。状态模式让这些行为在各状态类中明确。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

同一对象在不同生命周期状态下对同一操作有不同反应

三个具体场景

  • 订单待支付/已支付/已取消
  • 网络连接断开/连接中/已连接
  • 地铁闸机锁定/解锁

不适合或要小心

不要只为两个简单布尔分支引入一堆类。状态迁移应明确定义非法操作及副作用失败时的处理。

简单的两分支不必造状态类；迁移和副作用失败须定义清楚

最容易混淆的相邻模式

模式真正的区别
策略算法通常由调用方按需求选择；状态通常由对象自身生命周期迁移。
责任链请求沿处理器链传递；状态模式只把操作委托给当前状态。

区分时问自己：行为是随内部状态迁移，还是由外部主动选择算法？

落地前检查

  • 列出状态×操作矩阵，定义每个格子的行为。
  • 测试非法转移和重复操作。
  • 副作用与状态写入之间要处理失败、并发和幂等。
06 · 自己说一遍

两道检验理解的小题

已支付订单再次 pay() 会走 Pending.pay() 吗？

不会；订单委托给当前 Paid 状态，按 Paid 的规则响应。

支付失败时是否应该先把订单设成 Paid？

不应该；应先确认支付成功或定义可靠的中间态，再完成状态迁移，避免状态与外部事实不一致。
