Java 内存模型 JMM：可见性、有序性与 happens-before

多线程下「看到什么值、指令按什么顺序执行」的规则

一句话：JMM 定义多线程程序中变量的「可见性」与「有序性」规则；它不规定单线程内顺序，只规定跨线程何时能看到彼此的写入。

01为什么需要 JMM

现代 CPU 有缓存与指令重排。若无统一规则，线程 A 的写入可能停留在自身缓存、线程 B 永远看不到；或编译/CPU 重排后，其他线程观察到“不可能”的执行顺序。JMM 用 happens-before 给出可依赖的保证。

02主内存与工作内存

所有变量存于主内存；线程有自己的工作内存（缓存副本）。线程读写为：主内存→工作内存→CPU，写回反之。可见性问题就来自副本未及时刷回。

概念类比
主内存共享变量真身
工作内存线程私有副本/缓存
交互lock/unlock、read/write、load/store、use/assign（JMM 的 8 个原子操作）

03happens-before 规则

  • 程序顺序：同一线程内，前面的操作 happens-before 后面的。
  • 监视器锁：unlock 某锁 happens-before 随后对该锁的 lock。
  • volatile：写 volatile 变量 happens-before 随后对该变量的读。
  • 线程启动：Thread.start() happens-before 新线程首动作。
  • 线程终止：线程所有动作 happens-before 其他线程检测到它结束（join 返回）。
  • 传递性：A hb B 且 B hb C ⇒ A hb C。
要点：有 happens-before 关系，就能保证“前面的写入对后面可见、且不被重排到后面”。

04volatile 的三重语义

语义保证不保证
可见性写立即刷主内存、读立即取最新—
有序性禁止该变量相关的读写重排不保证复合操作原子
原子性—不保证 i++ 这类读-改-写
// volatile 保证可见+有序，但不保证原子
private static volatile boolean stop = false;
// 写线程
stop = true;            // 对其他线程立即可见
// 读线程
while (!stop) { /* 能及时退出 */ }
// 但 count++ 仍非线程安全，需用 AtomicInteger 或 synchronized

05synchronized vs volatile vs atomic

机制原子性可见性有序性适用
synchronized是是（解锁前刷回）是（临界区内）复合操作/临界区
volatile否是是（本变量）状态标志、双重检查
AtomicX是(CAS)是是计数器、无锁更新

06双重检查锁 DCL 陷阱

单例的 DCL 必须给实例字段加 volatile，否则其他线程可能拿到“半初始化”对象：构造未完成就被发布。

class Singleton {
  private static volatile Singleton instance; // 必须 volatile
  static Singleton get() {
    if (instance == null) {                 // 第一次检查
      synchronized (Singleton.class) {
        if (instance == null)               // 第二次检查
          instance = new Singleton();        // volatile 防重排，避免半初始化
      }
    }
    return instance;
  }
}

07常见疑问

问：加了 volatile 就能线程安全了吗？

不能。它只解决可见与单变量有序，i++/复合条件仍要锁或原子类。

问：synchronized 会不会很慢？

早期重量级锁确实贵；现代 JVM 有锁偏向、轻量锁、自旋，低竞争下很轻，高竞争才膨胀为重量级。
