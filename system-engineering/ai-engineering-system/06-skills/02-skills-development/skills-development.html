Skills 技能开发

Agent 模块化能力包

Agent 技能 · 模块化能力

在 Agent 体系里，Skill（技能）是一段「可被 Agent 按需加载的专业能力包」——包含它需要的知识、流程与工具调用指引，通常以一个声明文件（如 SKILL.md）描述「何时用、怎么用」。

一、Skill 与 Tool 的区别

维度ToolSkill
本质一个可被调用的函数（确定性接口）一组「知识+流程+可能调用多个 Tool」的能力包
粒度细（一次调用）粗（一个任务领域）
触发模型决定传参调用由描述（description）匹配「是否适合当前任务」后加载
例子send_email(to,body)「邮件营销起草技能」含写法规范+调多个 Tool
形象化理解：Tool 是「螺丝刀」——你拿起来就能拧；Skill 是「宜家安装说明书」——告诉你什么时候该用螺丝刀、按什么顺序装、注意什么，可能还要用到扳手（其他 Tool）。

二、一个 Skill 的典型结构

skills/
  pdf-summary/
    SKILL.md            # 名称、描述、触发条件、步骤
    scripts/extract.py  # 辅助脚本
    references/style.md # 参考资料
---
# SKILL.md 关键字段
name: pdf-summary
description: 当用户需要「总结/提取 PDF 内容」时使用；擅长长文档摘要。
steps:
  - 用 extract.py 抽取文本
  - 按 references/style.md 的规范分节总结
  - 调用 write_file 落盘

三、设计原则

🎯

单一职责

一个 Skill 解决一类问题，别做成「万能包」。

🔎

描述即入口

description 要写清「何时用」，模型靠它决定是否加载。

🧩

可组合

Skill 内部调用通用 Tool，彼此不硬耦合。

📏

精简上下文

只在被选中时才加载，避免一直占 token。

四、开发流程

  1. 定义接口：明确 Skill 解决什么任务、何时触发（写清 description）。
  2. 编写指引：把「专家怎么做」写成可操作步骤与规范。
  3. 接入工具：需要执行时调用既有 Tool，或写辅助脚本。
  4. 测试：用真实任务验证触发是否准确、结果是否正确。
  5. 发布：注册到技能目录，供 Agent 发现与加载。
⚠️ description 写得模糊，模型要么「该用不用」（漏触发），要么「不该用硬用」（误触发）。这是 Skill 质量的第一杠杆。

Skill 是什么：把「怎么做」打包成可复用能力

一次性的提示词写好了只能自己用一次；Skill 则是把指令、脚本、参考资料打包成一个可发现、可复用、可版本化的能力单元。模型平时只知道它的名字和简介，命中场景时才加载细节。

渐进式披露：元数据常驻、正文按需、资源最后取
指令用自然语言写清楚流程、分支与验收标准。
脚本确定性的活交给代码，别让模型每次现场发挥。
资源模板、样例、参考文档，按需取用不常驻。
可发现靠 description 被模型选中，写不好等于不存在。

Skill 与相邻概念的边界

概念是什么何时用与 Skill 的关系
Prompt一次性或模板化的输入文本临时、单次任务Skill 是可复用、可版本化的提示词集合
工具 / MCP可被模型调用的能力接口需要访问外部系统Skill 可以规定「怎么正确使用这些工具」
子 Agent有独立上下文的执行单元任务可拆分、需隔离上下文Skill 可被子 Agent 加载，二者互补
工作流 / 编排外部代码写死的流程流程固定、要求强一致Skill 更灵活，把判断交给模型
RAG 知识库检索外部知识知识量大且常变Skill 可内嵌检索步骤，外层是流程

一句话区分：工具解决「能不能做」，Skill 解决「按什么步骤做才做得好」。

目录结构与最小骨架

my-skill/ ├── SKILL.md # 必需：元数据 + 正文指令 ├── scripts/ # 可选：可执行脚本（确定性工作） │ └── extract.py ├── references/ # 可选：按需读取的参考文档 │ └── schema.md └── assets/ # 可选：模板、样例文件 └── report-template.md SKILL.md 开头（元数据）: --- name: pdf-extract description: 从 PDF 抽取文本与表格并输出结构化结果。 当用户提到 PDF、发票、合同、扫描件、抽取表格时使用。 ---
name小写连字符，与目录名一致
description写「做什么」+「什么时候用」，这是被选中的关键
正文步骤化、带分支、给示例、说清边界
scripts重复且确定的操作，越早脚本化越稳
references大而少用的内容放这里，避免正文臃肿

写好一个 Skill 的六条原则

  1. description 写触发条件，不写功能简介。模型靠它判断要不要用，必须包含用户可能说的关键词与场景。
  2. 正文要可执行。避免「要注意质量」这类空话，写成能一步步照做的动作。
  3. 确定性的活交给脚本。解析、格式化、校验、批量处理，用代码比让模型每次自由发挥稳定得多。
  4. 给反例与边界。明确写出「不要做什么」「遇到 X 走哪条分支」，比只写正例有效。
  5. 控制篇幅。正文保持在必要范围，细节下沉到 references，按需再读。
  6. 给一个完整示例。一次「输入 → 过程 → 输出」的示范，胜过三段抽象描述。

怎么验证一个 Skill 真的有用

触发测试

准备两组输入：应该触发的和不该触发的。

  • 应该触发的表述要覆盖口语、专业术语、错别字
  • 不该触发的用来检查是否误抢其它场景
  • 触发错了就改 description，而不是改正文

过程测试

看执行是否符合预期步骤，而不只是看最终答案。

  • 是否按正文顺序走
  • 分支判断是否走对
  • 有没有跳过校验直接出结果

回归测试

改一次就跑一遍固定用例集，防止越改越差。

  • 保留 5~10 个典型用例
  • 记录每次改动前后的表现
  • 用真实任务而非人造玩具题

深入自检

Skill 和「把提示词存成文件」有什么区别？

关键差别在渐进式披露与可发现性。普通提示词要么全量塞进上下文，要么根本不被看到；Skill 让模型平时只持有简短元数据，命中时才加载正文，因此可以同时挂载几十个能力而不挤爆上下文。

为什么我的 Skill 从来没被触发？

九成是 description 的问题：只写了功能名，没写用户会怎么说、什么场景该用。把用户真实表述里的关键词写进去（含同义词与俗称），并明确写出不适用的场景以便区分。

脚本和指令，怎么判断该放哪个？

判据是「这一步是否需要判断与创造」。解析文件、格式转换、批量改名、数值校验这类确定性操作放脚本；需要理解语义、做取舍、组织语言的放指令。脚本还能顺带省 token。

一个 Skill 应该做多少事？

一个 Skill 对应一类稳定复现的工作流。如果正文里出现两套完全不同的分支，且各自很长，就该拆成两个。反之如果两个 Skill 总是一起被触发，就该合并。

Skill 会不会让上下文越来越臃肿？

设计上不会，前提是遵守三层结构：元数据常驻、正文命中才读、大部头资料放 references 按需取。真正导致臃肿的是把所有细节都堆进 SKILL.md 正文。
