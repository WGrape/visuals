概述

测试是一等公民

Go 测试四类：单测 / 示例 / 基准 / Fuzz

测试文件以 _test.go 结尾、与被测包同目录；函数名 TestXxx(t *testing.T) 会被 go test 自动发现，无需框架。

测试文件分三类：功能测试 TestXxx、性能基准 BenchmarkXxx、可执行的示例 ExampleXxx。三者共享 testing 包。
测试函数

从最小例子开始

t.Error 标记失败但继续；t.Fatal 立即终止本测试；t.Run 创建带名字的子测试，方便定位。

func TestAdd(t *testing.T) {
    if got := Add(2, 3); got != 5 {
        t.Errorf("Add(2,3)=%d, want 5", got)
    }
}
表驱动测试

Go 的测试惯用法

用一组用例（含输入与期望）循环执行，新增场景只加一条数据；配合子测试能单独跑某个用例。

func TestAdd(t *testing.T) {
    cases := []struct{ a, b, want int }{
        {1, 2, 3}, {0, 0, 0}, {-1, 1, 0},
    }
    for _, c := range cases {
        if got := Add(c.a, c.b); got != c.want {
            t.Errorf("Add(%d,%d)=%d want %d", c.a, c.b, got, c.want)
        }
    }
}
子测试

命名与并行

t.Run(name, fn) 创建子测试，名字拼成 测试/子项；子测试可单独运行（go test -run 'TestAdd/负数'），也可用 t.Parallel() 并行。

for _, c := range cases {
    c := c
    t.Run(c.name, func(t *testing.T) {
        t.Parallel()
        if got := Add(c.a, c.b); got != c.want {
            t.Errorf("got %d want %d", got, c.want)
        }
    })
}
示例函数

可执行的文档

ExampleXxx 带 // Output: 注释时会被执行并校验输出；它既是测试也是文档，go doc / pkg.go.dev 都会展示。

func ExampleAdd() {
    fmt.Println(Add(2, 3))
    // Output:
    // 5
}
TestMain

全局前置后置

需要一次性 setup/teardown（如起测试库、建连接）时，用 TestMain(m *testing.M) 接管测试生命周期。

func TestMain(m *testing.M) {
    setup()
    code := m.Run()   // 运行所有测试
    teardown()
    os.Exit(code)
}

几类测试各解决什么问题

Go 把测试做进工具链，不同类型的测试只是文件命名与函数签名不同。理解各自用途，就能搭出一套成本合理的测试体系。

类型函数签名用途运行方式
单元测试TestXxx(t *testing.T)验证函数行为，覆盖面最广go test
基准测试BenchmarkXxx(b *testing.B)测量性能，看耗时与分配go test -bench
示例测试ExampleXxx()可执行的文档，输出会被校验go test
模糊测试FuzzXxx(f *testing.F)随机输入探索边界，找崩溃输入go test -fuzz
集成测试用构建标签隔离需要真实依赖，跑得慢go test -tags integration
// 表驱动测试：Go 里最常用的组织方式 func TestAdd(t *testing.T) { cases := []struct { name string a, b int want int }{ {"正数", 1, 2, 3}, {"负数", -1, -2, -3}, {"零值", 0, 0, 0}, } for _, c := range cases { t.Run(c.name, func(t *testing.T) { got := Add(c.a, c.b) if got != c.want { t.Errorf("Add() = %%d, want %%d", got, c.want) } }) } } // 子测试的好处： // 1) 失败信息里能看到是哪个用例 // 2) 可以用 -run 单独跑某个子测试 // 3) 每个子测试独立统计结果 // 并行只在互不依赖、不修改共享状态的用例上用 t.Run("parallel", func(t *testing.T) { t.Parallel() // ... })

表驱动的好处是加用例只需加一行，而且错误定位精确。它几乎能覆盖所有输入输出明确的场景。

基准测试：结果怎么读

基准测试输出三列，每列回答一个问题。只看其中一列很容易得出错误结论。

输出列含义怎么用
每次操作耗时平均每次操作花多少纳秒比较不同实现的速度
每次操作分配字节平均每次操作分配多少内存找出内存分配的热点
每次操作分配次数平均每次操作发生多少次分配分配次数多往往比字节数更致命
func BenchmarkConcat(b *testing.B) { // 准备工作不计入计时 data := make([]string, 1000) b.ResetTimer() for i := 0; i < b.N; i++ { _ = concat(data) } } // 常用参数： // go test -bench=. 跑所有基准 // go test -bench=. -benchmem 连内存分配一起看 // go test -bench=. -benchtime=5s 每个基准跑够 5 秒，结果更稳 // go test -bench=. -count=5 跑 5 轮，便于比较 // 常见误区： // 1) 不重置计时，把准备时间算进去了 // 2) 循环体内有额外分配，掩盖了被测代码的真实开销 // 3) 结果被编译器优化掉，可用包级变量接住返回值避免 // 想比较两次改动的性能差异，要用专门的基准比较工具， // 而不是只跑一次看数字

测试怎么写才有用

测行为，而不是测实现

好的测试只关心给定输入应该得到什么输出，不关心内部怎么实现。如果把实现细节也断言进去，那么任何重构都会导致一堆测试失败，测试就从资产变成了负担。

覆盖率的正确用法

覆盖率是找盲区的工具，不是质量指标。很高的覆盖率也不意味着没有缺陷，因为它测不到该测但没想到的场景。正确用法是看哪些分支从未被执行过，然后判断那里是否需要补用例。

优先测边界空输入、零值、最大值、错误路径
一个用例一组断言失败时能立刻定位
用子测试命名让失败信息可读
不要测私有细节否则重构会牵连一片
外部依赖要可替换用接口或内存实现、临时目录
并行要谨慎共享状态会导致偶发失败
基准要重置计时准备时间不应计入
覆盖率看盲区不要追求百分比

深入自检：测试的六个问题

测试文件必须叫特定后缀吗？

是的，只有以测试后缀结尾的文件才会被测试构建包含，它们也不会被打进正式产物。测试文件可以和被测对象同一个包（能访问未导出成员），也可以用包名加后缀的外部测试包，后者更适合验证公开行为。

怎么在测试里清理资源？

用清理注册函数，它会在该测试及其子测试结束时执行，比手动 defer 更适合有子测试的场景。更早的写法是在入口函数里做全局前置与后置，但一个包只能有一个。

依赖外部服务时怎么测？

优先把外部依赖抽象成接口，测试时换成内存实现或假实现。确实需要真实依赖时，用构建标签隔离成集成测试，让它默认不跑，避免在普通开发中拖慢反馈。

随机失败的测试怎么处理？

说明存在不确定性：时间、并发、随机顺序、共享状态。要么消除不确定性（注入时钟、去掉并行、隔离状态），要么把它标记为不稳定测试单独处理。绝不能靠重跑掩盖，那等于放弃了发现真实问题的机会。

什么时候该写模糊测试？

当输入空间大、边界难以穷举时特别有价值：解析器、编解码、校验逻辑。它会持续生成新输入，发现让程序崩溃的输入后会自动保存为回归用例。

测试代码需要像生产代码一样规范吗？

需要。测试也是长期维护的代码，可读性差、逻辑混乱的测试最终会被人跳过或删掉。但也不必过度抽象，测试里适度的重复反而让每个用例独立易懂。

第一层 · 四种测试的边界

Go 的测试分类不靠框架而靠约定 + 标准库。搞清楚四种测试的边界，就不会写出「单元测试跑得很快但什么也没测到」这种测试。

类型范围速度是否需要外部依赖占比建议
单元测试单个函数/方法（依赖全部 mock）毫秒级否70~80%
集成测试多个组件 + 真实依赖（DB/Redis）秒级是15~25%
端到端测试完整链路（含 HTTP 服务）秒~分钟是少量
基准测试性能按 -benchtime否热点路径必备
  • 判定标准：能不能在断网、无数据库的环境下跑完？能 → 单元测试；不能 → 集成测试。这条标准比任何定义都管用。
  • Go 的约定：文件名 _test.go；函数 TestXxx(t *testing.T)；基准 BenchmarkXxx(b *testing.B)；示例 ExampleXxx；模糊测试 FuzzXxx（1.18+）。
  • 测试文件属于同包还是 _test 包：package foo（白盒，能测未导出函数）vs package foo_test（黑盒，只测公开 API）。推荐用黑盒，除非确实需要测内部细节——黑盒测试不会因重构而失效。

第二层 · 命令、参数与模式

命令与代码

# —— 常用命令 ——
go test ./...                        # 跑所有
go test ./pkg/foo -v                 # 详细输出
go test -run TestName ./...          # -run 支持正则： -run 'TestUser/创建'
go test -race ./...                  # 【竞态检测】CI 必开
go test -count=1 ./...               # 【禁用缓存】结果缓存默认开启，改了代码要用
go test -cover ./...                 # 覆盖率
go test -coverprofile=c.out && go tool cover -html=c.out   # 可视化覆盖率
go test -timeout 30s ./...           # 防止测试挂死（默认 10m）
go test -shuffle=on ./...            # 随机顺序，暴露【测试间依赖】问题
go test -p 4 ./...                   # 并行包数（默认 GOMAXPROCS）

# —— 基准测试 ——
go test -bench=. -benchmem ./...     # -benchmem 显示【每次分配次数与字节数】
go test -bench=. -benchtime=10s      # 跑更久以获得稳定结果
go test -bench=BenchmarkX -count=6 | tee old.txt   # 多次采样
benchstat old.txt new.txt            # 对比（需 go install golang.org/x/perf/cmd/benchstat）
#   看三个值：时间/op、字节/op、分配次数/op
#   【分配次数】往往比时间更重要（GC 压力）

# —— 常用断言与辅助 ——
# 表格驱动测试（Go 的标准范式）
tests := []struct{
    name string
    in   int
    want int
    wantErr bool
}{
    {"正常", 1, 2, false},
    {"边界", 0, 0, false},
    {"负数", -1, 0, true},
}
for _, tt := range tests {
    t.Run(tt.name, func(t *testing.T) {
        got, err := f(tt.in)
        if (err != nil) != tt.wantErr { t.Fatalf(...) }
        if got != tt.want { t.Errorf("f(%d)=%d, want %d", tt.in, got, tt.want) }
    })
}

# —— 清理与并行 ——
t.Cleanup(func(){ os.Remove(tmp) })  # 【推荐】替代 defer，子测试也生效
t.Parallel()                          # 并行执行（注意：闭包要重新绑定循环变量）
for _, tt := range tests {
    tt := tt                          # 【Go 1.22 前必须】避免闭包捕获同一个变量
    t.Run(tt.name, func(t *testing.T){ ... })
}
参数 / 技巧作用经验值
-race竞态检测CI 必开；慢约 10 倍，本地按需
-count=1禁用结果缓存改了代码但测试还是绿的时候用它
-shuffle=on打乱顺序排查「测试间有依赖」的隐性 bug
-timeout超时保护默认 10m，CI 里设短点
t.Cleanup资源清理优于 defer（子测试作用域正确）
t.Parallel()加速IO 型测试收益大；注意共享状态

testdata/ 目录放测试固件go 工具会忽略该目录

覆盖率目标别追 100%：核心业务逻辑 70~85% 是合理区间。为了凑覆盖率而写的测试（只调用函数不验证行为）比没有更糟——它给了虚假的安全感。

第三层 · 排障清单

  • 改了代码测试还是通过 → 结果被缓存了。用 go test -count=1。这是最常见的困惑。
  • -race 报数据竞争 → 找共享变量的并发访问。常见来源：测试里起 goroutine 没等待、全局变量被并行测试修改、t.Parallel 下的共享状态。解法：加同步、或去掉并行。
  • 测试在本机过、CI 挂 → 排查：① 时区/语言环境；② 依赖了本机文件或环境变量；③ 端口冲突（并行跑时）；④ 时间敏感（用了 time.Now()）——应该注入时钟接口而不是直接调用。
  • 测试相互污染 → 用 -shuffle=on 能暴露。典型原因：修改全局状态（如全局配置、单例）没恢复。解法：t.Cleanup 里恢复原值，或把全局状态改成依赖注入。
  • 闭包捕获循环变量 → for _, tt := range tests { t.Run(..., func(){ use(tt) }) } 在 Go 1.22 之前所有子测试拿到的是同一个 tt。解法：循环内 tt := tt。
  • 基准测试结果不稳定 → 原因：① 跑得太短（用 -benchtime=10s）；② 后台有其他负载；③ 编译器优化掉了被测代码（用 runtime.KeepAlive 或把结果赋给包级变量 sink）。用 benchstat 做统计对比，别只看单次数字。
  • 测试很慢 → ① IO 型测试加 t.Parallel()；② 用 testdata 里的固定数据而非随机生成；③ 把集成测试与单元测试分开（用 build tag 或放到不同目录），让单元测试能快速跑。
  • mock 太重、改一点就要改一堆 mock → 说明接口设计有问题（接口太大）。Go 的哲学是小接口——只 mock 你真正需要的那一两个方法。或者用真实实现（如用 SQLite 内存库代替 mock DB）。
  • go test 编译很慢 → 挂缓存：GOCACHE 与 GOMODCACHE 在 CI 里做持久化。

第四层 · 原理与取舍

Go 测试体系的设计哲学：用最少的框架、最多的约定。标准库只提供 testing 包和 go test 工具，其余（断言、mock）都交给社区或自己写。这个取舍值得理解。

  • 为什么标准库不提供断言库：官方的观点是「断言库让测试变得像另一门语言」，且 if got != want { t.Errorf(...) } 的表达力其实足够。代价是每个项目都在重复写这段代码；收益是没有框架锁定、错误信息可控（好的错误信息比断言库更重要）。实践中 testify/assert 用得很广，但要知道它是可选的。
  • 表驱动为什么是 Go 的标准范式：因为 Go 没有测试框架提供的「参数化测试」装饰器，所以就用切片 + 循环 + t.Run 实现。这个模式的优点：新增用例只是加一行数据，且每个子测试有名字（-run 'TestX/用例名' 可单独跑）。
  • mock 的取舍：mock 让测试快且确定，但过度 mock 会让测试测的是 mock 而不是代码（改动实现时测试仍绿，但真实行为已错）。判断标准：如果 mock 的逻辑复杂到需要自己写测试，那它就不该被 mock——改用真实实现（内存版 SQLite、本地 Redis、httptest 服务器）。
  • httptest 是最好的例子：httptest.NewServer 起一个真实的本地 HTTP 服务来测你的 HTTP 客户端——比 mock http.Client 接口真实得多，且不需要写 mock。这是「用真实依赖的轻量版本」优于「mock」的典型。
  • 模糊测试（Fuzz，1.18+）：随机生成输入来发现崩溃和边界问题。它会自动把失败的输入存进 testdata/fuzz/ 作为回归用例。对解析器、编解码器这类输入空间大的函数收益最高。
做法优点代价建议
纯标准库 + 表驱动零依赖、可控样板代码多小项目首选
testify断言简洁、有 mock 工具多一个依赖广泛使用
httptest 起真实服务测到真实行为稍慢HTTP 相关首选
接口 + 手写 mock快、确定要维护 mock接口要小
真实轻量依赖（SQLite 内存等）最真实启动稍慢DB 层推荐
模糊测试能发现意想不到的崩溃慢、需长时间跑解析器类函数
单元测试该 mock 掉数据库吗？

分两种情况。测业务逻辑时：应该隔离——用接口 + mock 或内存实现，让测试毫秒级完成且不受环境影响。关键是接口要小（如 UserStore 只有 Get/Save 两个方法），这样 mock 很轻。测数据访问层本身时：不能 mock——mock 掉数据库后你测的是 mock 而不是 SQL。这时应该用真实的轻量数据库：SQLite 内存模式（注意方言差异）、dockertest 起一个真实容器、或者专门的测试库实例。判断原则很简单：被测代码的核心价值是什么，就别 mock 什么。业务逻辑的价值是「规则是否正确」，所以 mock 掉存储；数据访问层的价值是「SQL 是否正确」，所以必须用真数据库。

覆盖率多少合适？

没有统一数字，但要区分「覆盖到」和「测到了」。覆盖率只统计「代码是否被执行过」，不统计「行为是否被验证」。一行代码被执行但没人检查它的输出，覆盖率照样 100%。所以：① 核心业务逻辑 70~85% 是合理目标；② 基础设施代码（配置、错误处理）可以低一些；③ 100% 通常不值得——最后那 15% 往往是不可达的错误分支，为了覆盖它们要写大量 mock，投入产出比极差；④ 更重要的是看「没覆盖的部分是什么」——如果覆盖率 80% 但那 20% 恰好是支付、权限、边界处理，那这个覆盖率是危险的。所以正确的做法是：看覆盖率报告找出未覆盖的关键分支，而不是追数字。另外提醒：覆盖率低的模块要重点看，但覆盖率高的模块也不能掉以轻心。

为什么我的基准测试结果是 0 ns/op？

因为编译器把你的测试代码优化掉了。Go 的编译器会做死代码消除：如果 BenchmarkX 里调用了 f(x) 但没使用返回值，而 f 又无副作用，编译器会直接删掉这个调用，循环体变成空的 → 0 ns/op。三种解法：① 把结果赋给包级变量（如 var sink int，然后 sink = f(x)）——最常见；② 用 runtime.KeepAlive(result)；③ 用 testing.B 的 b.ReportAllocs() 配合检查分配次数（如果分配次数也是 0，说明确实被优化了）。顺便说，-benchmem 里的 allocs/op 往往比 ns/op 更有指导意义——因为分配次数直接决定 GC 压力，而 GC 是 Go 服务尾延迟的主要来源。优化的目标常常是「把每次操作的分配从 5 次降到 0 次」，而不是「快 10%」。
