08 数据湖与湖仓一体 · 开放表格式

Iceberg / Hudi / Delta Lake
湖仓到底比数据湖多了哪一层

"往对象存储上扔一堆 Parquet 文件"就有了数据湖——但它连 UPDATE 都做不了，两个作业同时写会互相踩踏，读的时候还可能读到写了一半的文件。表格式（Table Format）就是补上这一层的元数据与事务规范。本文讲清表格式到底解决了什么、三大表格式的设计差异，以及 Copy-on-Write 与 Merge-on-Read 的取舍。

1裸数据湖的四个致命问题

假设你只有 S3 / HDFS 上的一个目录，里面是按天分区的 Parquet 文件：

s3://lake/orders/
  ├── dt=2026-09-01/  part-0001.parquet  part-0002.parquet
  ├── dt=2026-09-02/  part-0001.parquet
  └── dt=2026-09-03/  part-0001.parquet

❌ 没有原子性

一个作业写 10 个文件，写到第 7 个时挂了。读者看到的是 7 个文件的半截数据——没有"提交"的概念，无法回滚。

❌ 没有隔离性

两个作业同时往同一分区写，文件互相覆盖或混杂。没有任何并发控制。

❌ 改不了一行

要 UPDATE 一条记录（比如 GDPR 删除用户数据），Parquet 是不可变的，只能重写整个分区的所有文件。

❌ 没有一致快照

一个长查询跑了 10 分钟，期间上游又写了新文件。查询前后读到的数据集不一致，结果是错的且不可复现。

表格式的解法在数据文件之上加一层元数据层，记录"这张表当前由哪些数据文件组成"。所有变更都通过元数据原子切换完成——数据文件本身依然不可变，变的是"哪些文件算这张表"。这就是湖仓能支持 ACID、UPDATE、时间旅行的全部秘密。

2表格式在架构中的位置

湖仓 = 廉价存储 + 表格式元数据 + 可插拔引擎

3三大表格式：出身与设计取向

🧊 Apache Iceberg

出身：Netflix 2018，为解决 Hive 表的正确性问题而生。
取向：规范优先。定义了一套开放的、与引擎无关的表规范，追求"一份数据、任意引擎都能正确读"。
强项：隐藏分区、分区演进、Schema 演进最完整、元数据设计最利于大规模表。

🔥 Apache Hudi

出身：Uber 2016，为解决"HDFS 上做增量更新"而生（Uber 有海量行程记录需要 Upsert）。
取向：更新优先。围绕 Upsert 与增量拉取（Incremental Pull）深度优化。
强项：Upsert 性能、增量查询、CDC 入湖、内置 Clustering 与 Compaction 服务。

🔺 Delta Lake

出身：Databricks 2019，作为其平台的原生表格式。
取向：与 Spark 深度绑定，追求开箱即用与商业版增强。
强项：Spark 生态集成最无缝、事务日志模型直观、Databricks 上有额外优化（Z-Order、Liquid Clustering）。

5更新机制：Copy-on-Write vs Merge-on-Read

这是表格式最重要的一个设计权衡，直接影响你的读写性能。Parquet 不可变，所以"更新一行"只有两条路：

📋 Copy-on-Write（COW）

做法：更新时，把涉及到的整个数据文件读出来 → 改 → 写成新文件，元数据指向新文件。
读性能：⭐⭐⭐ 最优，读的全是干净的 Parquet。
写性能：⭐ 差，改 1 行也要重写整个文件（写放大严重）。
适用：读多写少（典型的报表 / 分析场景）。

🔀 Merge-on-Read（MOR）

做法：更新不重写原文件，而是追加一个"增量日志文件"（delta log / avro）。读的时候把基线文件 + 增量日志合并。
读性能：⭐⭐ 稍差，读时要做合并。
写性能：⭐⭐⭐ 最优，只追加小文件。
适用：写多读少 / 高频 Upsert（CDC 入湖、实时更新）。

MOR 的隐藏成本：Compaction增量日志会越攒越多，读性能持续劣化。必须定期跑 Compaction（压缩合并）把日志合并回基线文件。这意味着：MOR 不是免费的——它把写时成本推迟到了后台的压缩任务上。选 MOR 就要同时规划好 Compaction 的调度与资源。

6怎么选

你的场景推荐原因
通用分析型湖仓、需要多引擎（Spark + Trino + Flink）Iceberg引擎中立性最好，规范最开放，元数据设计最适合超大规模表
数据库 CDC 实时入湖、高频 Upsert、需要增量拉取HudiUpsert 索引与增量查询是它最核心的设计目标
已重度使用 Databricks / 纯 Spark 栈、要开箱即用Delta Lake与 Spark 集成最无缝，商业版优化最多
分区规则可能变、或希望用户不用感知分区字段Iceberg隐藏分区 + 分区演进是它独有的强项
需要严格的 Schema 演进（改列名、改类型不丢数据）Iceberg用字段 ID 而非列名追踪，改名安全
已在 Hive 上、想渐进改造视情况Hudi / Iceberg 都能相对平滑迁移，Hudi 对 Hive 兼容更好
2026 年的现实三者正在互相靠拢：Iceberg 补强了 Upsert 与行级删除，Hudi 也在增强分区演进与多引擎支持，Delta 在提升开放性（UniForm 支持生成 Iceberg 元数据）。如果是新项目且没有强绑定，Iceberg 是目前社区动能最强的默认选择——尤其在"不想被单一厂商锁定"时。

7常见误区

"用了表格式，就能像 MySQL 一样随便 UPDATE 单行"
不能。表格式的 UPDATE 代价远高于数据库：即使改 1 行，也要重写（COW）或追加+合并（MOR）一整个文件级别的数据。它适合"批量更新一批数据"，不适合高并发单行点更新——那是数据库（或 KV 存储）的活。
"湖仓 = 数据湖 + 表格式，所以能完全替代数仓"
要看"数仓"指什么。湖仓替代的是存储与事务层，但分层建模、维度建模、指标治理这些"数据组织"的工作一件都没少——你依然要设计 ODS/DWD/DWS/ADS。湖仓只是让这些层建在同一套开放存储上，且互相之间可以事务一致。
"时间旅行能无限回退，不用备份了"
不能当备份用。表格式有 expire snapshots / vacuum 机制，会定期清理旧快照与被删数据文件（否则存储无限膨胀）。默认保留期通常只有几天到几十天。真要做长期备份，仍需独立快照到另一个存储桶/账号。
"小文件问题表格式自动解决了"
没完全解决。表格式提供了工具（Iceberg 的 rewrite_data_files、Hudi 的 Clustering、Delta 的 OPTIMIZE），但需要你主动调度执行。流式高频写入依然会产生海量小文件，不跑 compaction 照样查询变慢。
