高可用与连接池

Patroni / repmgr 故障切换，PgBouncer 连接池，读写分离与连接风暴。

① 可用性的三个层次② 崩溃恢复：数据库自己能做的事③ 主备高可用方案④ 备份策略：RPO 与 RTO⑤ 连接池与连接治理⑥ 常见问法

① 可用性的三个层次

单机可靠性

WAL + 检查点保证崩溃后不丢已提交数据；但主机故障即服务中断

主备高可用

流复制 + 自动故障切换（Patroni/repmgr），RTO 秒~分钟级

备份与恢复

基础备份 + WAL 归档，支持 PITR；防误删与灾难

只读扩展

备库承担读流量（hot standby），提升整体吞吐

延迟备库

故意延后应用 WAL，用于救回人为误操作

多活/分片

Citus、分片中间件或应用层分库分表；复杂度显著上升

关键认知：高可用（HA）不能替代备份。主备复制会把误删操作同步到备库，因此「防误删」必须靠 PITR 备份或延迟备库。

② 崩溃恢复：数据库自己能做的事

PG 启动时若发现数据目录不是「干净关闭」，会自动进入恢复：从最近的 checkpoint 开始重放 WAL，把已提交事务的修改补齐，未提交的根据 clog 判为不可见。

# 关键参数
checkpoint_timeout = 5min          # 检查点最大间隔
max_wal_size = 2GB                 # 触发检查点的 WAL 软上限
checkpoint_completion_target = 0.9 # 刷页时间占比（越大越平滑）
full_page_writes = on              # 防部分写（torn page）

-- 观察上次检查点时间
SELECT * FROM pg_control_checkpoint();
参数调大的影响调小的影响
checkpoint_timeout崩溃恢复时间变长，但 IO 更平稳恢复快，但检查点频繁、IO 抖动
max_wal_size同理；代价是 pg_wal 占用更多空间检查点更频繁
checkpoint_completion_target刷页更平滑，减少尖峰刷页更集中，可能造成卡顿

③ 主备高可用方案

方案特点适用
手工 promote简单，但 RTO 取决于人非关键系统
Patroni最主流：基于 etcd/Consul/ZK 做共识，自动选主、防脑裂、支持 pg_rewind生产首选
repmgr轻量、易上手，自带 switchover/failover 命令中小规模

连接池 + VIP配合 PgBouncer / HAProxy 做连接层 failover，让应用无感所有方案的补充

④ 备份策略：RPO 与 RTO

方式RPORTO防误删
pg_dump（逻辑）备份点长（需导入）✅（可单表恢复）
pg_basebackup + WAL 归档秒级中（需恢复+重放）✅（PITR 到误操作前）
流复制备库0（同步）短（promote）❌（会同步误操作）
延迟备库—短✅（延迟窗口内）
快照（LVM/云盘）快照点短部分
必须演练恢复。「有备份」≠「能恢复」。定期做恢复演练并计时，验证：① 备份文件完整可用；② WAL 归档链完整无断档；③ 恢复后数据一致（校验关键表行数）；④ RTO 满足 SLA。

⑤ 连接池与连接治理

PG 是一连接一进程，连接数过多会严重拖垮性能（内存 + 上下文切换 + 快照维护）。因此连接池是必需的。

方案层级特点
PgBouncer独立中间件最常用；支持 session/transaction/statement 三种池化模式
应用层池（HikariCP 等）应用内简单有效，但多实例时总连接数会叠加
pgpool-II中间件池化 + 读写分离 + 复制管理（功能多但也更复杂）
Odyssey中间件多线程、高性能，支持更细粒度路由
PgBouncer 模式选择：session（最兼容，连接独占直到断开）；transaction（推荐，事务结束即归还，复用率最高，但不支持预处理语句/会话级 advisory lock 的跨事务语义）；statement（最激进，不支持多语句事务，很少用）。

⑥ 常见问法

Q：有了主从复制，还需要备份吗？

A：必须需要。复制是实时的：主库上的误删、误 UPDATE、DROP TABLE 会立刻同步到备库，主备一起「被误删」。备份（尤其 PITR）才能把数据恢复到误操作之前的时间点。三层防护：① 实时备库应对主机故障（RTO 短）；② PITR 备份应对数据损坏与误操作；③ 延迟备库（如延迟 1 小时）提供快速救回通道。此外，备份必须定期演练恢复，否则「有备份」只是心理安慰。

Q：RPO 和 RTO 分别指什么？PG 里怎么达成？

A：RPO（恢复点目标）：最多能丢失多少数据；RTO（恢复时间目标）：多久能恢复服务。达成手段：① RPO=0 → 同步复制（synchronous_commit=on/remote_apply + 至少一个同步备），代价是写延迟；② RPO=秒级 → 异步流复制；③ RTO 短 → 自动故障切换（Patroni）+ 连接池/VIP 让应用无感；④ RTO 长但 RPO 精确 → PITR 恢复（需基础备份 + 完整 WAL 归档）。两者要分别承诺，不能混为一谈。

Q：脑裂（split-brain）是什么？怎么防？

A：指两个节点都认为自己是主库并同时接受写入，导致数据分叉且难以合并。PG 自身不提供自动选主与脑裂防护，需要外部方案：① 奇数节点的分布式共识（etcd/Consul/ZooKeeper，Patroni 的做法）——只有获得多数派投票才能成为主；② fencing / STONITH：确认旧主已隔离（断网、关机、回收 VIP）后才让新主上线；③ 看门狗（Linux watchdog）在失去心跳时自动重启；④ 云环境可用云厂商的互斥机制。核心原则：宁可短暂不可用，也不能出现双写。

Q：PgBouncer 的三种池化模式怎么选？

A：session：客户端连接期间独占后端连接，兼容性最好，但复用率低（等同于限制总连接数）；transaction（推荐）：事务结束就归还连接，复用率最高，是绝大多数场景的选择，代价是不支持跨事务的会话状态（预处理语句、会话级 advisory lock、SET 的会话变量等）；statement：每条语句后归还，不支持多语句事务，几乎不用。实践：Web/OLTP 用 transaction 模式，并让应用避免依赖会话级状态（或改用 SET LOCAL）。

Q：连接数设置多少合适？为什么不能太大？

A：实际后端连接建议控制在几十到几百，绝不要上千。原因：PG 是一连接一进程，每个后端都有独立的内存（本地缓存、Catalog 缓存、work_mem 等，通常几 MB 起步），且快照维护、锁表、VACUUM 判断的成本都随连接数（活跃事务数）增长——连接越多，Vacuum 越难回收、快照越大。实践：用 PgBouncer 把成千上万的应用连接复用到几十个后端连接上；max_connections 设为「峰值后端连接 + 管理预留」。

Q：怎么设计一套完整的 PG 高可用方案？

A：分层设计：① 数据层：1 主 + 2 备（至少一个同步备，用 ANY 1 避免单备故障拖死主库）；② 选主层：Patroni + 3 节点 etcd（奇数、跨机架）；③ 接入层：HAProxy/PgBouncer 做读写分离与健康检查路由；④ 备份层：每日/每周基础备份 + 持续 WAL 归档（异地存储），并配置延迟备库；⑤ 监控：复制延迟、连接数、长事务、age(relfrozenxid)、磁盘与 WAL 目录容量、autovacuum 状态；⑥ 演练：定期做 switchover 与恢复演练并计时。外加：DDL 上线规范（lock_timeout）、慢查询治理、容量规划。
