TSDB 原理

比较关系型数据库与时序专用存储的取舍，理解 Series、压缩、降采样和产品边界。

Series 基数与标签设计

标签组合决定独立时间线的数量；样本量相同，基数也可能相差几个数量级。

 📘

基数爆炸治理：为什么序列数会失控

序列数是标签取值数的乘积、五步定位法、止血与重建手段，以及五条标签设计规则。
📘

Counter、Gauge 与 rate：计数器重置后曲线为什么会乱跳

用四个采样点手算增量、重置、缺测和聚合，区分“当前值”与“增长速度”。
📘

时序数据乱序与迟到：设备补报会怎样改写一分钟报表

以离线设备补传温度为例，区分事件时间、写入时间、去重键、水位线和重算边界。
📘

保留策略与降采样

原始数据和长期趋势需要不同时间粒度；聚合规则必须保持指标语义。

 📘

连续查询（CQ）

周期性自动聚合并物化到新时间线；对比查询时降采样，讲清「太晚降采样」陷阱。
📘

时序压缩算法：Delta-of-Delta 与 Gorilla XOR

两个针对时序特性的压缩技巧、完整链路、实测预期量级，以及压缩率不达预期的排查路径。

 📘

存储布局：WAL、内存块、Block 与 compaction

写入路径的每个环节、Block 内部结构、chunk 大小的权衡，以及重启/删除/保留策略的底层行为。
🌊

数据模型、Line Protocol、TSM 与 shard；区分 1.x 的 RP/CQ 和 2.x 的 bucket/task。

TDengine 原理

一设备一表的设计取舍、超级表与标签、存储压缩、taosd/mnode 集群、INTERVAL 与 STATE_WINDOW。
📘

TDengine 超级表与标签：设备数据怎样建模

以十万台设备的温度采集为例，设计超级表、子表、标签和查询，并识别高基数陷阱。
🛰️

TDengine 集群与高可用：mnode、dnode 与多副本

mnode 管元数据与负载均衡、dnode/vnode 做数据分片与副本、多副本一致性与故障切换流程，以及虚拟节点与「一设备一表」如何决定集群扩展方式。
🔥

Prometheus 原理图解：拉取模型、架构与定位

为什么坚持拉取而不是推送、Retrieval/TSDB/Rules/Alertmanager 如何分工； 拉模型带来的三个必然推论（采样而非事件、时间戳由抓取方决定、必须暴露全量快照）； 与 InfluxDB、TDengine 的定位差异，以及上手最容易踩的五个坑。
🏷️

数据模型与四种指标类型

指标名 + 完整 label 集合唯一确定一条时间线，基数是各 label 取值数的笛卡尔积； Counter 必须配 rate、Gauge 直接读、Histogram 可跨实例聚合算分位数、Summary 直出但不可聚合； 直方图的两个陷阱（桶内插值误差、样本太少不谈 P99），以及命名与标签设计原则。
🔍

PromQL 入门：向量、rate 与聚合

区间向量不能直接画图，必须先套 rate/xxx_over_time； rate 窗口至少要覆盖 4 倍抓取间隔，irate 反应最快但不适合告警； sum by 与 without 的方向、先 rate 再 sum 的顺序不能反、向量匹配要显式写 ignoring/on， 以及 QPS/错误率/P99/磁盘预测六个常用套路。

 🔍

PromQL 实战：模板与高频坑

四类指标的正确查法、可直接复用的查询模板、告警写法与排障顺序。
💾

TSDB 存储：Head Block、WAL 与 Compaction

为什么是「不可变 block + 合并」而不是原地更新； 内存主要被活跃时间线数吃掉而非样本总量，因此高基数才是杀手； 长周期查询为什么比近期查询贵几个数量级；保留期的四种做法与 remote_write 必须自我监控。

 💥

基数爆炸：Prometheus 最常见的自伤

序列数怎么算、多少算多、三条排查命令与五种降基数手段。
🚨

规则与告警：Recording Rule 与 Alertmanager

Prometheus 只判定、Alertmanager 只通知，分工搞混就配不对； for 必须大于抓取间隔；Recording Rule 的 level:metric:operations 命名约定与「预计算后不能再套 rate」； Alertmanager 的分组、抑制、静默、路由四机制，以及「触发了有没有事可做」这条告警存在性标准。
📦

VictoriaMetrics：Prometheus 的远端存储

兼容 remote_write 与 PromQL，单机版一个二进制全干、集群版拆成 vminsert/vmselect/vmstorage； 写入与查询压力来源不同所以拆开各自横向扩展；单机版是默认起点而非「低配」； 与 Thanos（旁路增强）、Mimir（重写 Prometheus）的三条不同路径。
🏗️

VictoriaMetrics 架构：单机版与集群版的分野

为什么它能接在 Prometheus 下游；单节点版一个进程包办 vs 集群版拆成 vminsert / vmstorage / vmselect 三层可独立伸缩；存储结构差异与内存曲线差别；remote_write 是唯一改动点的接入步骤；MetricsQL 兼容边界与「日常查询尽量写标准 PromQL」的实践建议；集群版不是更快而是容量与隔离、副本不等于备份等五个常见坑。
📉

VictoriaMetrics 降采样与存储：原生 rollup 与压缩

原生降采样与 rollup 规则的配置、不可逆与可重算的取舍、存储块与索引结构、指标压缩率与 retention 在集群版与单节点版的差异。
⚖️

时序数据库选型：从四个问题到 POC

数据谁产生、基数多大、存多久、谁来消费——这四个问题直接决定候选范围； Prometheus / VictoriaMetrics / InfluxDB / TDengine / TimescaleDB 的定位对比与四种常见组合模式； POC 必须测真实基数、峰值写入、最重查询、稳态资源、故障行为；以及五个高频选型误区。
📐

时序库容量规划与成本估算

选型前必须量出的四个输入（活跃序列数、采样间隔、单样本字节、保留期）及各自易错点；磁盘/内存/CPU 三个维度的估算关系式与「不是同比例增长」的现象；压测要找的六个拐点（写入、基数、查询并发、长周期、恢复时间、合并开销）；机器之外的对象存储、跨机房流量、运维人力、迁移四类隐性成本；以及基数治理、磁盘满行为、备份演练、监控的监控、断流告警五项上线自检。
🚧

时序库的边界：什么数据不该用时序库

需要事务与强一致的 OLTP、低基数低频的事件记录、需要灵活关联分析的关系型场景，以及误用时序库后的迁移与代价。
