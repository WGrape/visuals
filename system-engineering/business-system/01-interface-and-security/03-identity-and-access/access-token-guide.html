Access Token：身份的数字化身

Access Token 解决的问题是：HTTP 是无状态的，怎么让服务端知道「你是谁、你能干什么」。答案是登录后发一个凭据，之后每次请求带上它，服务端验证凭据即可，无需每次查库或维持会话。

Token 认证完整流程：登录 → 签发 → 携带 → 校验 → 刷新

Token vs Session：怎么选

维度Session（服务端会话）Token（如 JWT）
状态存储服务端保存会话（内存 / Redis）服务端不存，凭据自包含
校验方式拿 sessionId 查存储本地验签 + 校验声明（exp、iss 等）
扩展性需共享存储（Redis）才能多实例天然无状态，任意实例可校验
跨域/跨服务受 Cookie 域限制，跨服务要额外处理放在 Header 里，天然支持跨域与跨服务
主动失效容易——删掉服务端会话即可困难——签发后到过期前始终有效，需黑名单补救
大小Cookie 里只有一个 id，很小Token 本身较大（几百字节~几 KB），每请求都要传
适用传统 Web 应用、需要即时踢人的后台前后端分离、移动端、微服务、第三方授权

现实做法：不是二选一，而是混合——用 JWT 做无状态校验，同时在 Redis 里维护一份「已吊销列表」或「会话版本号」，兼顾扩展性与可控性。

JWT 的结构

SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV └──── Header ────┘ └──── Payload ────┘ └───── Signature ─────┘ Header（头部） ：声明算法与类型 { "alg": "HS256", "typ": "JWT" } Payload（载荷）：存放声明（claims），Base64URL 编码 —— 注意：只是编码，不是加密！ 注册声明（标准）： iss 签发者 sub 主题（通常是用户 ID） aud 受众 exp 过期时间（Unix 秒） nbf 生效时间 iat 签发时间 jti JWT ID（唯一标识，可用于防重放与吊销） 自定义声明： { "sub": "10001", "roles": ["admin"], "tenant": "t-88" } Signature（签名）：对前两段做 HMAC 或 RSA 签名 HMACSHA256( base64(header) + "." + base64(payload), secret ) 作用：防篡改 —— 改了 payload 签名就对不上 ⚠ 关键认知：JWT 默认只防篡改，不防读取。任何人拿到 token 都能解出 payload。 所以绝不能在 payload 里放密码、身份证号、密钥等敏感信息。 需要保密时应使用 JWE（加密的 JWT）。

安全实践清单

存储与传输

  • 全程 HTTPS——Token 在 HTTP 明文传输等于直接泄露
  • 优先 HttpOnly + Secure + SameSite Cookie——防 XSS 读取
  • 若存 localStorage：方便但会被 XSS 窃取，需要严格的 CSP 与输入过滤
  • 不要在 URL 里带 Token——会被浏览器历史、Referer、服务器日志记录

有效期与刷新

  • access_token 短（15min~2h），refresh_token 长（7~30d）
  • refresh_token 用一次即轮换（rotation），检测到重用则判定泄露并吊销整条链路
  • refresh_token 存服务端（可吊销），access_token 保持无状态
  • 改密码、登出、风控封禁时，必须吊销该用户的所有 refresh_token

签名与密钥

  • 对称（HS256）密钥要足够长且严格保密；多服务共享密钥会扩大泄露面
  • 对外/第三方场景用非对称（RS256/ES256）：私钥签发、公钥验签
  • 必须校验 alg——防止 alg=none 与算法混淆攻击（把 RS256 换成 HS256 并用公钥当密钥）
  • 密钥要支持轮换（kid 头部 + JWKS 端点）

校验要点（缺一不可）

  • 验签 → 校验 exp（过期）→ 校验 nbf（未生效）→ 校验 iss/aud（签发者与受众）
  • 校验必需的业务声明是否存在（如 tenant、roles）
  • 查黑名单（jti）以支持主动吊销
  • 绝不用「解码即可信」——没有验签的 payload 可被任意伪造

常见漏洞与防护

  • Token 泄露。最短效的防护是缩短有效期 + HTTPS + 安全的存储方式；其次是绑定客户端特征（IP 段、UA、设备指纹）做异常检测。
  • 无法主动失效。这是 JWT 最大的工程痛点。补救方案：① 短有效期 + 黑名单（只存被吊销的 jti，量小）；② 在 token 里放会话版本号，改密码时递增版本号，校验时比对；③ 关键操作二次校验（如支付前重新验证）。
  • 重放攻击。抓到 token 后重复使用。防护：HTTPS + 短有效期 + 敏感操作加一次性 nonce 或时间戳窗口。
  • 越权（最常被忽略）。Token 只证明「你是谁」，不证明「你能访问这个资源」。必须做资源级鉴权：校验 token 里的 userId 是否真的拥有该订单/该文档。
  • 把敏感信息放进 payload。JWT 只是 Base64，可被任意解码。只放非敏感的标识与权限信息。
  • Token 过大。塞进大量权限、菜单、部门信息会让 token 达到几 KB，每个请求都传一遍浪费带宽。权限信息应在服务端按需查询，token 里只放最小标识。

深入自检

Token 该存在 localStorage 还是 Cookie？

取舍在 XSS 与 CSRF 之间。localStorage：不会被 CSRF 自动携带（因为要 JS 主动读取再放入请求头），但会被 XSS 直接窃取——任何一处 XSS 漏洞都能拿走 token；Cookie（HttpOnly + Secure + SameSite）：JS 读不到，能防 XSS 窃取，但会被浏览器自动携带，需要 SameSite=Lax/Strict 与 CSRF Token 防御 CSRF。当前较主流的建议是：优先用 HttpOnly + Secure + SameSite 的 Cookie 存 refresh_token（长生命周期，最需要保护），access_token 可存内存（页面刷新则用 refresh 换新的），这样即使 XSS 也难以长期持有凭据。无论哪种，都必须配合严格的 CSP、输入过滤与输出转义，因为存储方式只是降低风险，不能替代 XSS 防护。

JWT 为什么不能主动失效？有什么补救办法？

因为 JWT 是无状态的：服务端签发后不保存任何记录，校验时只验签和看 exp，所以没有地方可以标记「这个 token 已作废」——只要签名对、没过期，它就被认为是有效的。三种补救：① 黑名单——在 Redis 存被吊销的 jti（或整 token 的哈希），校验时查一次，代价是引入了状态（但只存少量被吊销的，量远小于全量会话）；② 版本号/最小生效时间——token 里带 tokenVersion，用户改密码或登出时递增 DB 中的版本，校验时比对，不匹配即失效，代价是校验要查一次 DB 或缓存；③ 极短有效期——access_token 只活 5~10 分钟，靠 refresh_token 续期，这样即使无法即时失效，影响窗口也很小（最常用、最实用）。生产上通常是三者组合：短有效期 + refresh 可吊销 + 关键操作二次验证。

refresh_token 为什么要轮换（rotation）？

轮换指每次用 refresh_token 换新的 access_token 时，同时返回一个新的 refresh_token 并作废旧的。好处是能检测泄露：如果攻击者窃取了 refresh_token 并使用，旧 token 被作废；当合法用户下一次用已被作废的旧 token 刷新时，服务端就能发现「同一个 refresh 被用了两次」，判定为泄露，立即吊销该用户整条 token 链并要求重新登录。这把「泄露后长期有效」变成了「泄露后很快被发现并阻断」。实现要点：旧的 refresh_token 需要一个短暂的宽限期（防止并发请求误判），并记录 token 家族（family）以便整体吊销。

微服务之间怎么传递身份？

推荐做法是「透传 + 内部增强校验」，而不是每个服务重新登录。流程：① 网关校验外部 token，解析出 userId/tenant/roles，② 把这些身份信息放进内部请求头（如 X-User-Id）传给下游，③ 下游信任该头——但这有安全前提：网关必须剥离外部传入的同名头（防伪造），且内网通信应有 mTLS 或服务间签名（防内部越权），④ 更严格的做法是网关重新签发一个内部短效 token，下游验签后使用，这样不依赖「信任请求头」这种隐式约定。另外要注意：下游服务仍需做资源级鉴权——知道 userId 不等于能操作该资源，判断是否拥有该订单/文档必须由持有数据的服务完成。
