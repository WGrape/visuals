异构计算：CPU、GPU、NPU 各自该干什么

CPU 强在延迟与通用性，GPU 强在吞吐，NPU 强在能效。真正的工程问题不是「谁更快」，而是「这段计算该放在哪、数据要搬几次、搬运的代价有没有超过计算本身」。

一句话定位：延迟优化 vs 吞吐优化

CPU 用大缓存、乱序、分支预测把「单条指令的延迟」压到最低；GPU 用几千个简单核心 + 高带宽显存把「单位时间完成的操作数」推到最高。同一个矩阵乘，CPU 可能 90% 时间在等数据，GPU 则能靠并行把算力吃满。

CPU几十个强核，适合控制流与串行依赖
GPU数千 SIMT 核心，适合规则并行
NPUMAC 阵列 + INT8/INT4，适合固定形状推理
关键约束数据搬运能耗与带宽，往往比计算更贵
四种算力的分工不是性能排序，而是「问题形状」的匹配

峰值 TOPS 的水分

标称 TOPS 通常按「理想形状 + 最低精度 + 全流水」计算。真实模型里有 LayerNorm、Softmax、转置等非矩阵算子，NPU 要么不支持、要么效率极低，实际利用率常常只有峰值的 20%~40%。

数据搬运才是大头

操作能耗量级相对值
一次 INT8 乘加~0.1 pJ1×
一次 FP32 乘加~1 pJ10×
从 L1 读 1 bit~1 pJ10×
从 DRAM 读 1 bit~100 pJ1000×
跨芯片（PCIe）传 1 bit~500 pJ5000×

这张表解释了为什么「把模型切成两半分别放 CPU/GPU」经常更慢：中间结果的搬运成本可能超过省下的计算。也解释了为什么端侧强调「一次加载、多次复用」，以及为什么大模型推理的瓶颈是显存带宽而不是算力。

# 典型的异构流水线（推理）
x = preprocess(x)            # CPU：控制流、前后处理
x = x.to(device)             # H2D 拷贝 ← 常见瓶颈
y = model(x)                 # GPU/NPU：批量矩阵运算
y = y.to("cpu")              # D2H 拷贝
post = postprocess(y)        # CPU

# 优化方向：合并拷贝、用 pinned memory、异步流水、算子融合

原理与取舍：为什么要「专用」

通用处理器把面积花在缓存、乱序、分支预测上，这些对规则并行毫无用处。专用加速器把面积全给 MAC 阵列与片上缓存，于是同样的功耗下算力高一个数量级——代价是失去通用性：形状变了、精度变了、算子不支持了，就要回退，回退的代价往往比不用加速器还高。

GPU 能替代 CPU 吗？

不能。GPU 的执行模型要求「同一段代码作用在大量数据上」，遇到分支发散、串行依赖、频繁系统调用就退化。异构的本质是让合适的单元做合适的事。

NPU 和 GPU 的差别到底在哪？

GPU 保留可编程性（能跑任意 kernel），NPU 把数据流固化（卷积/矩阵乘的专用流水线），所以 NPU 能效更高但只对特定算子高效。

Chiplet 为什么突然流行？

因为大芯片良率随面积指数下降，把大 die 拆成小 die 分别制造再封装，成本更低；同时可以混用不同工艺（计算用先进工艺、IO 用成熟工艺）。

第一层 · 概念与判定：四种算力各自适合什么

类型擅长不擅长典型形态
CPU复杂逻辑、分支、串行任务大规模同构并行计算通用服务器、控制面
GPU大规模同构并行（SIMT）分支密集、不规则访存训练、推理、图形
NPU / TPU定死的矩阵乘与卷积非矩阵类算子端侧推理、数据中心推理
FPGA低延迟、可定制流水线开发周期长、成本高网络加速、金融行情

判定口诀：任务是否可切分成成千上万个互不依赖的相同操作？是 → 加速器；否（重度串行、大量分支）→ 留给 CPU。现实中大多是混合：CPU 控流程，加速器算热点。

查看加速器状态与利用率

# 看系统识别到的加速器
lspci | grep -iE 'nvidia|amd/ati|tpu|fpga'

# NVIDIA：查看 GPU 利用率、显存、温度（每 1 秒刷新）
nvidia-smi dmon -s pucvmet -d 1
# 关键列：
#   sm%   流处理器利用率（GPU 计算是否跑满）
#   mem%  显存带宽利用率（注意不是显存占用率）
#   enc/dec% 编解码引擎利用率

# 找出 GPU 利用率低的常见原因：数据加载跟不上
nvidia-smi --query-gpu=utilization.gpu,utilization.memory,memory.used --format=csv

# 看 PCIe 带宽（主机到设备的数据搬运是否成为瓶颈）
lspci -vv | grep -i 'lnksta'

关键认知：算力差距是 20–50 倍，但带宽差距只有 10–20 倍，所以很多任务不是算不完，而是数据喂不进去 —— 这就是常说的 memory-bound。

GPU 利用率高但吞吐没提升batch 太小、kernel 启动开销大加大 batch、做算子融合

训练速度忽快忽慢其他任务抢占 / 数据 pipeline 抖动隔离 GPU、固定数据加载线程数
推理延迟不达标没有用批处理或用错精度开动态 batching、上 FP16/INT8
CPU 和 GPU 都很闲在等 IO 或同步查数据 IO、减少主机-设备同步次数

排查顺序：

  • ① 先确认瓶颈在哪一侧：GPU 闲 = CPU/IO 瓶颈；GPU 满 = 已达算力上限
  • ② 用 nvidia-smi dmon 看 sm% 与 mem%，两者都低才是真闲
  • ③ 检查主机到设备的数据搬运：PCIe 或 NVLink 是否打满
  • ④ 用 nsys / nvprof 做时间线分析，定位最耗时的 kernel
  • ⑤ 确认做了异步：数据传输与计算是否 overlap（用 CUDA stream）

第四层 · 原理与取舍

为什么 GPU 核心频率比 CPU 低，却快那么多？

因为核心数量级不同：CPU 通常 8–64 个复杂核心，GPU 有数千到上万个简单核心。GPU 用「更多更简单的核心 + 更高带宽显存」换来吞吐，代价是每个核心能力弱、频率低、无法处理复杂分支。所以 GPU 赢在吞吐，CPU 赢在延迟与灵活性。

把任务搬到 GPU 就一定快吗？

不一定。常见反例：① 小矩阵运算 —— 数据搬运时间远超计算时间，搬过去反而更慢；② 分支密集逻辑 —— GPU 的 SIMT 遇到分支要串行执行两条路，效率暴跌；③ 不规则访存 —— 无法合并访存，带宽利用率低。先算一下算术强度（每字节数据做多少次运算），太低的任务不值得搬。

异构系统的最大工程代价是什么？

不是硬件，是编程模型与数据搬运。把算法拆成「CPU 部分 + 加速器部分」本身就有成本，还要处理数据在两种内存之间的搬运（PCIe 带宽远小于 HBM）、不同厂商的软件栈（CUDA / ROCm / oneAPI）、以及显存与主机内存的容量差异。所以只有当热点足够集中（如一个大矩阵乘）时，异构化才划算。
