01 · 从问题出发

为什么会需要这个模式？

图片加载耗时，或敏感文档读取需要授权；客户端仍希望调用同一接口。

读取文档可能很慢，也可能需要权限。若客户端自己先检查权限、再懒加载真实文档，每个入口都要重复这套控制，漏掉一个入口就可能造成越权读取。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

interface Document { read(user) }
class SecureProxy implements Document {
  constructor(docId, loader, authorization) {
    this.docId = docId; this.loader = loader
    this.auth = authorization; this.real = null
  }
  read(user) {
    if (!this.auth.canRead(user, this.docId)) throw Forbidden
    if (this.real == null) this.real = this.loader()
    return this.real.read(user)
  }
}

读代码时抓住三件事

  1. Proxy 与 RealDocument 实现同一接口，能透明替换。
  2. 代理可以控制访问时机、权限和缓存。
  3. 真实对象只负责核心读取，控制逻辑不散落在调用方。

换个业务场景，还能认出来吗？

ORM 的懒加载对象在访问属性时才查数据库；远程代理把本地方法调用转成网络请求。但远程调用有延迟和失败语义，不能假装与内存调用完全一样。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

访问真实对象需要控制时机、权限或远程连接

三个具体场景

  • 敏感文档读取前鉴权
  • 大图片首次访问才加载
  • 远程服务提供本地接口代理

不适合或要小心

权限检查必须可信。代理重点是控制访问；装饰器重点是叠加职责。

不要让代理隐藏网络延迟或错误；权限须在可信边界执行

最容易混淆的相邻模式

模式真正的区别
装饰器侧重叠加职责，组合多个包装层；代理侧重控制真实对象的访问。
适配器使不同接口相互兼容；代理与真实对象通常接口相同。

区分时问自己：主要目的是控制访问，还是叠加可选功能？

落地前检查

  • 权限验证放在不可绕过的可信入口。
  • 明确缓存是否会导致过期数据或跨用户泄漏。
  • 远程代理要公开超时与失败语义，不要悄悄吞异常。
06 · 自己说一遍

两道检验理解的小题

为什么代理与真实对象实现同一接口？

客户端不必改调用方式，代理决定何时访问真实对象。

代理能保证所有调用都安全的前提是什么？

客户端不能绕过代理直接访问真实对象；真实对象或服务端仍应守住最终授权边界。

Go 实现示例

type UserRepo interface { Get(id int64) (*User, error) } // 真实对象 type DBRepo struct{ db *sql.DB } func (r *DBRepo) Get(id int64) (*User, error) { /* 查库 */ return nil, nil } // 缓存代理：接口完全一致，调用方无感知 type CacheProxy struct { inner UserRepo cache map[int64]*User mu sync.RWMutex } func (p *CacheProxy) Get(id int64) (*User, error) { p.mu.RLock() if u, ok := p.cache[id]; ok { p.mu.RUnlock(); return u, nil } // 短路 p.mu.RUnlock() u, err := p.inner.Get(id) // 必要时才穿透 if err != nil { return nil, err } p.mu.Lock(); p.cache[id] = u; p.mu.Unlock() return u, nil } // 使用：类型仍是 UserRepo var repo UserRepo = &CacheProxy{inner: &DBRepo{db: db}, cache: map[int64]*User{}}

代理 vs 装饰器 vs 适配器

维度代理 Proxy装饰器 Decorator适配器 Adapter
接口是否变化不变不变变成另一个
关注点控制访问（能否、何时）增强行为（加什么）解决不兼容
是否可嵌套通常一层可多层叠加通常一层
生命周期可延迟创建真实对象通常在已有对象上加包装已有对象
典型例子RPC stub、ORM 懒加载日志中间件、加密流第三方 SDK 包装

实战提醒

① 别在代理里做重逻辑代理应承担「横切关注点」（缓存、鉴权、日志），业务逻辑放真实对象。
② 缓存代理要处理失效没有过期与主动失效的缓存代理，本质是内存泄漏 + 数据陈旧。
③ 注意透明性代理的返回值语义必须与真实对象一致（包括错误类型），否则调用方会踩坑。
④ 别滥用动态代理反射魔法会让调用链难以追踪和调试，能用静态包装就别用反射。

深入自检

代理和中间件是不是一回事？

思想上非常接近：HTTP 中间件就是典型的代理/装饰器 —— 它拿到请求，可以短路、可以增强、可以拒绝。区别只是「代理」这个说法多用于对象与 RPC 场景，「中间件」多用于请求处理链。

虚拟代理和懒加载有什么区别？

懒加载是目的，虚拟代理是实现手段之一。你也可以用 sync.Once、getter 函数实现懒加载；虚拟代理的特点是对调用方完全透明。

保护代理和「在业务方法里 if 判断权限」哪个好？

代理的好处是权限逻辑集中且不可绕过；写在业务方法里则容易遗漏。但代理只适合横切式的粗粒度权限，涉及数据行级权限时仍需在业务层判断。

代理会不会让性能更差？

多一层调用本身开销极小，但远程代理涉及网络往返，代价极大（毫秒级 vs 纳秒级）。所以远程代理要特别注意批量接口、连接复用与超时控制。

如何在 Go 里优雅地做「可插拔代理」？

定义接口 + 函数式包装：type Middleware func(UserRepo) UserRepo，用 chain(repo, withCache, withMetrics) 组合。这比层层嵌套结构体更灵活，也更容易测试。
