Go 内存模型详解：并发可见性与 happens-before

这是「真·内存模型」的落地页：它不讲内存怎么分配、不讲 GMP、不讲 GC，只回答一个问题——在并发下，一个 goroutine 对内存的写入，在什么条件下能被另一个 goroutine 看到，以及操作之间有哪些顺序保证。核心就是 happens-before 与同步原语。

边界厘清 happens-before 规则清单 同步原语对照 data race 不是同步的 面试四块
先划边界

一、先说清：内存模型 ≠ 内存分配 ≠ GMP ≠ GC

国内面试里「内存模型」常被用得不严谨。动手看规则前，先把四个名字里都带「内存」的话题对号入座，否则后面会越看越乱。

「内存模型」是一份并发可见性契约：规定在并发 / 乱序执行下，一个协程对内存的写入，在什么条件下对另一个协程可见，以及操作之间有哪些顺序保证。它只回答「谁能看到谁的写」。

四个常被混为一谈的词，各管一摊

① 内存模型 Memory Model
「契约/规则」层：并发下读写可见性与顺序的保证。Go 官方文档 The Go Memory Model 讲的就是它，核心是 happens-before。本页只讲这一块。
② 内存分配 / 管理
「实现」层：堆内存怎么被切成小块、怎么快速发还。关键词 mcache/mcentral/mheap/span/size class。
③ GMP 调度
「调度」层：百万 goroutine 怎么映射到少量 OS 线程上跑。关键词 G / M / P / work-stealing。
④ 垃圾回收 GC
「清理」层：不再使用的内存何时被回收。关键词三色标记 / STW / write barrier。
记一句口诀：内存模型 = 规则（谁能看到谁的写）；内存分配 = 修路（内存怎么切）；GMP = 交警（谁在什么时候跑）；GC = 环卫（不用的内存何时扔）。四件事名字里都带「内存」，但层次完全不同。

内存模型是「规范层」（一份契约）；内存分配 / GMP / GC 是「实现层」的三个子系统。

本目录里那篇《Go内存模型》可视化页恰恰把内存布局 + GMP + GC + happens-before 全塞进了一页，标题叫「内存模型」、内容却大多是另外三块——正是这种混淆的典型来源。本页只聚焦规范层。若你想厘清「面试官问的到底是哪一块」，另有一篇《「Go 内存模型」到底在问什么》专门做术语定位。
核心

二、happens-before 到底是什么

整份内存模型，几乎全绕着 happens-before（先于发生）转。先把它吃透。

happens-before 是「偏序关系」，不是「墙上时钟先后」

说 A happens-before B，有两层含义：

① 可见性保证
所有对 A 的写，B 及 B 之后的操作都一定能看到。写结果不会「还没传过去」。
② 禁止重排
编译器 / CPU 不得把 B 之前的读写重排到 A 之后（在可被观察到的范围内）。

它是偏序：有些操作之间没有 happens-before 关系，它们就是「并发（concurrent）、不可比较」，谁先谁后未定义。注意 happens-before 还有传递性：若 A hb B 且 B hb C，则 A hb C。多数正确的并发程序，就是把一串同步事件拼成一条可见性链。

为什么需要它？你写的代码顺序，不等于 CPU / 编译器实际执行的顺序：

编译器重排
编译期为优化，在「不改变单线程结果」前提下调换指令顺序。
CPU 乱序执行
多核为吞吐会乱序 / 投机执行，写可能先停在 store buffer 里没真正落内存。
缓存不一致
每核有独立缓存，A 核写的变量 B 核可能暂时从自己缓存读到旧值。
多字撕裂读
大于一个机器字的变量读写，会被拆成多次机器字操作，顺序未指定（可能读到「撕裂」的值）。

A hb B hb C 形成一条链（传递性）；X、Y 与它们互不 happens-before，顺序由实现自由决定。

常见误区：「happens-before 就是时间上先发生」。错。它表达的是「可见性保证 + 禁止重排」，并不等于墙上时钟的先后。两个操作之间如果「互不 happens-before」，那它们的执行顺序就是未定义的——哪怕你用 time.Sleep 赌它「肯定先跑完」也没用。
规则清单

三、Go 内存模型给出的 happens-before 规则

下面这些就是「能建立 happens-before 边界」的官方规则（节选自 The Go Memory Model）。记住它们，就握住了内存模型的骨架。

七条同步规则（面试常背）

① 单 goroutine 顺序
同一 goroutine 内，按程序顺序 hb。但注意：重排不可被本 goroutine 观察，别以为「我写的顺序就是执行顺序」。
② 包初始化 init
若 p 导入 q，则 q 的 init 完成 hb p 的任何函数开始；main.main 的开始 hb 所有 init 完成之后。
③ goroutine 创建
go f() 语句 hb 于新 goroutine 开始执行 → 创建前写的变量，新 goroutine 一定看得到。
④ channel 通信
无缓冲：send hb receive；带缓冲：第 k 次 send hb 第 k 次 receive；close hb 收到零值的 receive。
⑤ 互斥锁 sync.Mutex
第 n 次 Unlock hb 第 n+1 次 Lock 返回。解锁把你的写「发布」给下一个加锁者。
⑥ WaitGroup / Once
第 n 次 Done hb 第 n 次 Wait 返回；Once.Do(f) 中 f 的执行 hb 任何后续 Do 返回。
⑦ sync/atomic（Go 1.19 起正式为顺序一致）
一个原子的写 hb 后续观察到该值的原子读。Go 1.19 把 sync/atomic 的语义正式钉死为 sequentially consistent（对齐 C++ SC / Java volatile）。Go 1.19 还新增了类型化原子：atomic.Int64 / Bool / Pointer[T] 等，把「该字段必须原子访问」写进类型里，避免漏写原子访问。
经典反例（没有同步，内存模型说「结果未定义」）：done 用普通 bool 轮询、a 用普通 string 赋值——编译器可把 done=true 重排到 a="..." 之前，CPU 也可能让主协程一直从自己缓存读到 done==false 而永不退出，或退出后读到未初始化的 a。修法正是下面第四节的同步原语。
Go 1.19（2022 年 8 月，文档版标记 "Version of June 6, 2022"）对内存模型做了一次重要修订：把单一的 happens-before 拆成 sequenced-before（程序内顺序）与 synchronized-before（同步事件），happens-before 是二者的传递闭包；并以 DRF-SC（data-race-free ⇒ sequential consistency）为目标，对齐 C/C++/Java 的保证。所以「Go 没有正经内存模型」是过时说法。这次修订没有改变已有程序的可观察行为，只是把长期默认遵守的契约写成了严谨可验证的文本。
对照演示

四、四个同步原语：没同步 vs 同步

这是内存模型最实用的部分。点下面的原语，看「不加同步 → 结果未定义（data race）」与「加同步 → 保证可见」的对照。左侧是错的，右侧是对的。

❌ 没同步：普通读写，未定义
✅ 加锁：Unlock hb 下一次 Lock
var x int
func writer() { x = 100 }
func reader() { println(x) }
// 两 goroutine 并发读写 x
// 无 happens-before → data race
// reader 可能读到 0 / 100 / 撕裂值
var x int
var mu sync.Mutex
func writer() {
    mu.Lock()
    x = 100
    mu.Unlock()      // 发布写
}
func reader() {
    mu.Lock()        // 取到写
    println(x)
    mu.Unlock()
}

第 n 次 Unlock happens-before 第 n+1 次 Lock 返回。锁把临界区里的写「发布」给下一个拿到锁的 goroutine。

❌ 没同步：只靠普通变量
✅ 通信：send hb receive
var x int
func main() {
    go func() { x = 100 }()
    // 无同步
    println(x)  // data race
}
var x int
func main() {
    ch := make(chan int)
    go func() {
        x = 100
        ch <- 0        // send
    }()
    <-ch             // receive（hb send）
    println(x)    // 保证看到 100
}

无缓冲 channel：send happens-before receive。Go 首选用「不要通过共享内存来通信，而要通过通信来共享内存」——channel 的通信本身就是同步语义。注意这里 x 的写 hb send（同 goroutine 顺序），send hb receive（channel 规则），receive hb println（同 goroutine 顺序），由传递性保证可见。

❌ 没同步：普通赋值
✅ 原子：写 hb 观察到该值的读
var x int64
func writer() { x = 100 }
func reader() { println(x) }
// 即便 int64 是单字
// 原子性 ≠ 可见性
// 无 hb → 仍可能看不到
var x atomic.Int64
func writer() {
    x.Store(100)   // 原子写
}
func reader() {
    v := x.Load()    // 原子读
    println(v)      // 保证一致
}

「int 是单字，所以 x=5 天然原子、不用同步」——这是错的，原因有二：原子性 ≠ 可见性；且多字变量（如 struct、int64 在某些 32 位平台）会被拆成多次操作。sync/atomic 默认顺序一致，写 hb 后续观察到该值的原子读。最佳实践用类型化原子 atomic.Int64 / Bool / Pointer[T]，避免漏写原子访问。但记住：原子操作只保单变量，不保多变量间的复合操作。

❌ 没同步：靠 Sleep 赌顺序
✅ WaitGroup：Done hb Wait 返回
var x int
func main() {
    go func() { x = 100 }()
    time.Sleep(time.Second)
    println(x)  // 仍是 race！
}
var x int
var wg sync.WaitGroup
func main() {
    wg.Add(1)
    go func() {
        x = 100
        wg.Done()   // 发布
    }()
    wg.Wait()       // hb Done
    println(x)    // 保证看到 100
}

time.Sleep 不建立 happens-before——「它睡够 1 秒肯定先跑完」只是赌运气，内存模型不承认。第 n 次 Done happens-before 第 n 次 Wait 返回，所以 Wait 返回后读到的必然是 Done 之前写完的值。

危险区

五、data race：内存模型说「未定义」的那类 bug

当两段访问同一内存、至少其一是写、且它们之间没有 happens-before——这就是 data race。它不在「未定义行为」里被宽容，而是要被工具抓出来的。

data race 的正式判定

两个对同一个变量 v 的访问，若至少一个是写，且二者之间不存在任何 happens-before 关系，则构成 data race。一旦有 race，程序的行为是未定义的——没有「可能会怎样」，而是「任何事都可能发生」（读到旧值、读到撕裂值、崩溃、或更隐蔽的逻辑错乱）。

一个正确（race-free）的并发程序的判定标准：每一个共享读，都能通过一条 happens-before 边，回溯到它所观察到的那个写。同步原语存在的意义，就是帮你画出这些边——它们不是普通的锁，而是「带着友好 API 的内存屏障（fence）」。

撕裂读：大于一个机器字的变量

内存模型明确规定：大于单个机器字的读写，会被拆成多次机器字大小的操作，顺序未指定。所以即便一个 struct / int64 的「整体赋值」看起来是一步，另一个 goroutine 也可能在中途读到一半旧、一半新的值——这就是撕裂（torn）读。原子或锁能避免它。

用 race detector 抓它：go run -race

Go 自带基于 ThreadSanitizer 的竞态检测器，给每个内存访问记录「向量时钟」，发现「同一地址、至少一写、且互不 happens-before」的访问对就报警。开启方式统一是 -race：

# 开发 / CI 阶段使用
go run  -race ./main.go
go test  -race ./...
go build -race ./cmd/app

# 报告示例（节选）
==================
WARNING: DATA RACE
Write at 0x00c00001a0e0 by goroutine 7:
  main.worker()  main.go:14 +0x44
Previous read at 0x00c00001a0e0 by goroutine 6:
  main.main()    main.go:21 +0x88
==================

代价约为 5–10× 变慢、约 2× 内存，所以它是开发与 CI 工具，不是生产开关。两个重要前提：它只报告实际执行到的代码路径上的 race，所以测试覆盖率很关键；且它报的是「race」本身，race 即未定义行为，发现就必须修。

小测：下面哪段是 data race？

→ 不是 race。两个访问都是读，没有写，不满足「至少一是写」的条件，不构成 data race（两个读之间顺序无所谓，结果都合法）。
→ 是 race。两段都是写、且互不 happens-before，典型的并发写冲突，结果未定义。
→ 不是 race。send hb receive，由传递性，A 对 x 的写在 B 读之前已可见，存在 happens-before 边，程序 race-free。
→ 不是 race。go 语句 hb 新 goroutine 开始，所以创建前对 x 的写在子 goroutine 里一定可见——这正是「goroutine 创建」规则。
避坑

六、这些「看起来像同步」其实都不建立 happens-before

面试和代码 review 里最高频的误判。下面每一项都不提供内存可见性保证。

写法为什么没用正确替代
time.Sleep睡眠不建立任何 happens-before 边，只是赌时间。channel / WaitGroup / Mutex
fmt.Println 等打印打印是普通函数调用，内存模型不保证它「顺带」把前面的写发布出去。显式同步原语
普通变量赋值 / 读单条读写本身没有同步语义，多 goroutine 共享就是 race。atomic / Mutex
「它肯定先跑完」的直觉没有同步事件，调度顺序不等于可见性顺序。用同步事件建边
goroutine 退出内存模型规定：一个 goroutine 的退出不保证 happens-before 任何事件，激进的编译器甚至可能删掉整段无同步的写。用 channel / Mutex 收尾
反例：go func(){ a="hello" }(); print(a)——对 a 的赋值后面没有任何同步事件，不保证被任何其它 goroutine 观察到；激进编译器甚至可能把整个 go 语句删掉。若必须被观察到，一定要用锁或 channel 建立相对顺序。
面试

七、把「Go 内存」拆成 4 大块，就不会再混

面试官一句「Go 的内存模型」可能指四件完全不同的事。建议直接拆开，先澄清边界再展开。

Go 内存相关的 4 大块

① Go Memory Model
并发读写可见性 · happens-before · data race · Mutex / Channel / Atomic
② Go 内存分配
栈 / 堆 · 逃逸分析 · mspan / mcache / mcentral / mheap · size class
③ Go GC
三色标记 · 写屏障 · STW · GC 调优（GOGC）
④ GMP 调度
G / M / P · work-stealing · 抢占式调度

第一句话怎么答（直接背）：「如果说的是 Go Memory Model，它主要解决并发场景下不同 goroutine 对共享内存的访问问题，规定什么条件下一个 goroutine 对内存的写入能被另一个 goroutine 观察到，以及操作之间的顺序关系。核心是 happens-before、data race，以及 Mutex / Channel / Atomic 等同步机制建立的可见性保证。」

如果被追问「具体讲讲」，按这条主线走

沿着「普通读写 → 有没有同步 → 有没有 happens-before → 有没有 data race → Mutex/Channel/Atomic 如何建立同步关系」讲下去，就是「Go 内存模型」这道面试题的主线。

如果面试官其实想问「内存怎么分配 / GMP / GC」，你就说：「若指 runtime 的内存管理，我可以再展开堆栈、逃逸分析、mspan/mcache/mcentral/mheap、三色标记与 GMP 调度。」——先把概念边界划清，这个回答非常稳。
