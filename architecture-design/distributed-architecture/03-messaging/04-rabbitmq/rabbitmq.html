AMQP · 灵活路由

RabbitMQ 深度解析

RabbitMQ 是实现了 AMQP 协议的消息中间件，最大特点是以 Exchange + Binding 为核心的灵活路由：消息先发给交换器，按规则（直接 / 广播 / 主题 / 头）投递到一个或多个队列。适合复杂路由、任务分发、企业集成。

1核心模型：Producer → Exchange → Queue → Consumer

和 Kafka「直接写 topic」不同，RabbitMQ 多了一个 Exchange 路由层，消息不直接进队列。

Exchange 依据 binding key 把消息投递到一个或多个队列

2四种 Exchange 类型

类型路由规则典型用途
DirectroutingKey 精确匹配 bindingKey点对点、按任务类型分发
Fanout广播到所有绑定队列（忽略 key）事件通知、缓存失效
TopicroutingKey 按 . 分隔，#/* 通配按业务域订阅（订单.*）
Headers按消息头属性匹配（非 key）复杂多条件路由
# 声明 topic 交换器并把队列绑定到 "order.*"
channel.exchange_declare('orders','topic')
channel.queue_bind(queue='q1', exchange='orders', routing_key='order.created')
# 发消息：匹配 order.created 的队列收到
channel.basic_publish('orders','order.created', body)
与 Kafka 对比Kafka 的路由是「partition key → 固定分区」，订阅模型是 consumer group；RabbitMQ 用 Exchange/Binding 表达任意拓扑的投递关系，路由表达力更强但吞吐通常低一个量级。

3可靠性机制

✅ 消息确认

Consumer 处理完发 basic.ack；未 ack 且连接断开，消息重新入队。

🔁 发布确认

Publisher Confirm 让 broker 确认消息已落盘/路由，防发丢。

💀 死信交换器

消费失败/超时的消息进 DLX，可重试或告警，避免「毒消息」卡住队列。

⏱️ 镜像队列

经典版用镜像队列做 HA（3.8 后逐步迁移到 Quorum Queue / Raft）。

持久化三件套消息不丢需要：队列持久化 + 消息 delivery_mode=2 + 发布确认。三者缺一都可能丢消息。

4集群与多租户

RabbitMQ 节点组成集群共享元数据；队列数据默认只在单个节点（镜像/Quorum 复制到多节点）。它还内置 vhost 做多租户隔离，以及完善的 管理面板与权限体系，运维体验在消息中间件里数一数二。

5运维要点与坑

  • 队列过长：队列堆积百万条时内存与调度压力陡增，务必设 TTL / 死信，控制队列长度。
  • 消息体积：RabbitMQ 不擅长超大消息，大 payload 走对象存储、队列只传引用。
  • 流控（flow control）：内存触顶时 broker 会对生产者限流，体现为 publish 阻塞，要监控 disk_free_limit 与内存水位。
顺序性RabbitMQ 默认不保证跨队列、甚至队列内消费顺序（prefetch>1 时）；需要严格顺序的场景更适合 Kafka 单分区。

6什么时候选 RabbitMQ

与 Kafka/RocketMQ/Pulsar 的取舍见MQ 对比。

场景推荐理由
复杂路由 / 任务分发RabbitMQExchange/Binding 表达力强
超高吞吐日志流Kafka / PulsarRabbitMQ 吞吐低 1~2 个量级
事务消息 / 海量堆积RocketMQ更适合电商交易链路
严格顺序Kafka 单分区RabbitMQ 顺序保证弱
一句话要「把一条消息智能地送到多个不同目的地」选 RabbitMQ；要「海量、高吞吐、可重放的日志流」选 Kafka/Pulsar；要「事务型业务消息」选 RocketMQ。
