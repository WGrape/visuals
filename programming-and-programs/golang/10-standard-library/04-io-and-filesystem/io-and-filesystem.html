一切皆流

io.Reader/io.Writer 是 Go IO 的核心抽象：只要实现了 Read/Write 就能互相拼接，文件、网络、内存、压缩都统一处理。

正因为统一接口，标准库里 io.Copy(dst, src) 能在任意两端之间搬运数据，无需关心来源。
Reader/Writer

实现一次到处用

函数签名尽量接收 io.Reader 而非具体 *os.File，可测试性更好；bytes.Buffer、strings.Reader 都是常见实现。

func count(r io.Reader) (int, error) {
    n, err := io.Copy(io.Discard, r)  // 读但不存
    return int(n), err
}
文件与目录

os 包管文件系统

os.Open 只读、os.Create 覆盖创建、os.ReadFile/WriteFile 一次性读写；os.MkdirAll 递归建目录，defer f.Close() 别忘。

f, _ := os.Create("out.txt")
defer f.Close()
f.WriteString("hi")

b, _ := os.ReadFile("in.txt")
os.MkdirAll("a/b/c", 0o755)
缓冲

减少系统调用

bufio.Reader/Writer 在内存中缓冲，按行/按词读取更高效；Scanner 按行扫描是处理文本文件的利器。

f, _ := os.Open("log.txt")
sc := bufio.NewScanner(f)
for sc.Scan() {
    line := sc.Text()  // 逐行
}
临时文件

用系统机制

ioutil 已弃用，改用 os.CreateTemp / os.MkdirTemp 创建带随机名的临时文件/目录，结束后记得清理。

⚠️ 临时文件要显式清理（defer os.Remove），否则会堆积；生产环境注意放在合适的 tmpfs/目录。

io.Reader / io.Writer：Go I/O 的地基

Go 的 I/O 哲学是用两个最小接口组合出一切。文件、网络、内存缓冲、压缩流、加密流都实现同一对接口，因此可以任意串联。

组合式 I/O：层层包装，接口统一
接口极小Read / Write 各一个方法，实现成本极低。
可组合压缩、加密、缓冲、限流都能串起来。
短读是正常的Read 允许返回少于请求的长度。
EOF 是约定读到末尾返回 io.EOF，要与真错误区分。

必须掌握的四个工具函数

函数作用要点
io.Copy(dst, src)把 src 全部拷到 dst内部有缓冲，优先用 ReadFrom/WriteTo 优化
io.ReadAll(r)一次性读全部内容会全部载入内存，大文件别用
io.LimitReader(r, n)限制最多读 n 字节处理不可信输入时防止被打爆
io.TeeReader(r, w)读的同时写一份到 w适合做校验和、抓包式日志

os.Open / Create打开文件，注意 defer Close

深入自检

为什么 io.Copy 比自己 Read/Write 循环好？

io.Copy 会优先使用底层的 ReadFrom 或 WriteTo 实现，在文件或网络之间拷贝时可以走零拷贝路径（如 sendfile），并自带合适大小的缓冲区。自己写循环通常更慢也更容易漏掉短写处理。

bufio.Writer 忘了 Flush 会怎样？

数据留在缓冲区里没有真正写入，可能丢失最后一部分内容。这是最常见的文件写入 bug。正确做法是 defer 或显式 Flush，并检查它的错误——Flush 的 error 同样重要。

io.ReadAll 有什么风险？

它会把全部内容读进内存。面对不受控大小的输入（用户上传、外部响应）时，可能被一次大请求打爆内存。应当用 io.LimitReader 设上限，或改用流式处理。

Read 返回的 n 小于请求长度，是出错了吗？

不是。短读完全合法，常见于网络流与压缩流。正确写法是循环读直到 n 为 0 或遇到错误，只在 err != nil 且 err != io.EOF 时才认为是失败。

os.IsNotExist 之外还要注意什么？

Stat 可能因为权限不足、路径中有非目录、符号链接循环等原因失败，这些都不是「不存在」。把非 IsNotExist 的错误一律当成不存在，会掩盖真实问题。

IO 接口的组合设计

接口方法用途
io.ReaderRead(p []byte) (n int, err error)一切的源头
io.WriterWrite(p []byte) (n int, err error)写入
io.CloserClose() error释放
io.ReadWriterReader + Writer双向
io.ReadCloserReader + CloserHTTP body 就是它
io.SeekerSeek(offset, whence)随机访问

Go IO 的设计精髓是「小接口 + 自由组合」：Reader 只有一个方法，所以任何东西都能是 Reader（文件、网络连接、字符串、内存缓冲、甚至另一个 Reader 的装饰）。然后用包装器组合出功能：bufio 加缓冲、gzip 加解压、io.LimitReader 加限制。

接口组合

// 组合的力量：层层包装
f, _ := os.Open("data.gz")
defer f.Close()

r := bufio.NewReader(f)          // 1) 加缓冲（减少系统调用）
gz, _ := gzip.NewReader(r)       // 2) 解压
lr := io.LimitReader(gz, 1<<20)  // 3) 限制最多读 1 MB（防解压炸弹）
io.Copy(io.Discard, lr)          // 4) 丢弃（只关心能否读完）

// 常用包装器
io.LimitReader(r, n)             限制读取量
io.TeeReader(r, w)               读的同时写一份到 w（<strong>调试神器</strong>）
io.MultiReader(r1, r2)           顺序拼接多个 Reader
io.MultiWriter(w1, w2)           同时写多个目标
bufio.NewScanner(r)              按行扫描

// io.Copy 内部用 32 KB 缓冲，且会优先用 ReaderFrom/WriterTo
//   （如 sendfile 零拷贝），比手写循环更优

文件操作

// Scanner 的默认限制：单行最多 <strong>64 KB</strong>
scanner := bufio.NewScanner(f)
scanner.Buffer(make([]byte, 1024*1024), 10*1024*1024)  // 调到 10 MB
for scanner.Scan() {
    line := scanner.Text()
}
if err := scanner.Err(); err != nil {
    // 常见错误：<strong>bufio.Scanner: token too long</strong>
}

// 忘记 Flush 的经典 bug
w := bufio.NewWriter(f)
w.WriteString("data")
// defer f.Close()  ← <strong>Close 不会自动 Flush bufio.Writer！</strong>
defer w.Flush()        // 必须显式 Flush，且要在 Close 之前

// 原子写入（避免读到半个文件）
tmp := path + ".tmp"
os.WriteFile(tmp, data, 0644)
os.Rename(tmp, path)   // <strong>同分区的 rename 是原子的</strong>
// 跨分区 rename 会退化成「复制+删除」，不原子

bufio.Writer 的 Flush 必须显式调用：这是 Go 里最经典的数据丢失 bug 之一。f.Close() 只关闭底层文件，不会把缓冲区里的数据刷出去。正确顺序是 defer 里先 w.Flush() 再 f.Close()，或者用 defer 的逆序特性安排好。

遍历与路径处理

遍历与路径

// 高效遍历：WalkDir（Go 1.16+，比 Walk 少一次 stat）
err := filepath.WalkDir(root, func(path string, d fs.DirEntry, err error) error {
    if err != nil { return err }
    if d.IsDir() {
        if d.Name() == ".git" { return filepath.SkipDir }  // 跳过目录
        return nil
    }
    info, _ := d.Info()          // 需要大小时才 stat
    fmt.Println(path, info.Size())
    return nil
})

// filepath vs path 的区别（重要！）
path.Join("a", "b")          // "a/b"      ← 始终用 /
filepath.Join("a", "b")      // Windows: "a\b"，Unix: "a/b"
// <strong>处理本地文件路径用 filepath，处理 URL 用 path</strong>

// 路径清理（防目录穿越）
clean := filepath.Clean(userInput)
if strings.HasPrefix(clean, "..") {
    return errors.New("非法路径")
}
// 更稳妥：用 filepath.Rel 检查是否在根目录内
rel, err := filepath.Rel(baseDir, target)
if err != nil || strings.HasPrefix(rel, "..") { /* 拒绝 */ }
函数作用陷阱
filepath.Join拼接并清理会 Clean，可能改变语义
filepath.Clean规范化路径"a/../b" → "b"
filepath.Abs转绝对路径依赖当前工作目录
filepath.Rel计算相对路径安全检查的好工具

自检 Q&A

Q：io.Copy 为什么比手写循环快？

A：两个原因——① 它用 32 KB 的缓冲，避免了小 buffer 导致的频繁系统调用；② 更关键的是它会检查类型：如果源实现了 WriterTo 或目标实现了 ReaderFrom，就直接调用，从而启用零拷贝（如 Linux 的 sendfile，数据不经过用户态）。手写循环通常两个都做不到。所以复制数据一律用 io.Copy，别自己写。

Q：读取超大文件（几十 GB）要注意什么？

A：绝不能一次读入内存。三条实践——① 流式处理：用 bufio.Reader 或 Scanner 分块读；② 控制内存：处理 CSV/日志时逐行解析，不要把行存进切片；③ 考虑 mmap：随机访问为主的场景可用 syscall.Mmap（但要注意它占用的是虚拟内存，且大文件在 32 位系统上地址空间不够）。另外注意Scanner 的 64 KB 行限制，日志里有超长行时会报错。

Q：os.ReadFile 和 os.Open 怎么选？

A：按文件大小。os.ReadFile 一次性读入，代码简单，适合配置文件、小数据集（< 100 MB）；os.Open + 流式读取适合大文件或只需部分内容的场景。判断依据是内存峰值：ReadFile 会让内存峰值至少等于文件大小（加上 GC 压力可能是 2 倍）。另外 ReadFile 内部会根据 Stat 预分配容量，比 ioutil.ReadAll 少几次扩容。

Q：写文件如何保证不丢数据？

A：取决于「丢」的场景。进程崩溃 → 只需正确 Flush（数据已在内核页缓存）；系统崩溃/断电 → 必须 f.Sync()（触发 fsync 落盘）。但 fsync 很慢（毫秒~几十毫秒），所以一般做法是：① 普通数据靠定期刷盘；② 关键数据（如配置、状态）显式 Sync()；③ 需要原子替换时用「写临时文件 → Sync → Rename → Sync 目录」。最后的同步父目录常被遗漏——不 sync 目录，rename 本身可能没落盘。
