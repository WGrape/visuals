①为什么 SQL 不标准

SQL 有 ANSI/ISO 标准，但每家数据库只实现其中一部分，并加入大量私有扩展。结果是"会写 MySQL 不一定会写 PostgreSQL"，迁移时最容易在分页、拼接、取前 N 行、布尔、引号、自增这些"小地方"翻车。

结论：把 SQL 当"方言"对待，而不是"通用语言"。跨库项目要么统一数据库，要么在 ORM/查询层收敛差异。

③窗口函数与 CTE 的兼容性

好消息是窗口函数和CTE（WITH）在现代主流库中已高度一致（PG、MySQL 8、SQL Server、Oracle 都支持）。但细节仍有差异：FETCH FIRST WITH TIES、WINDOW 子句、NULLS FIRST/LAST 并非全都支持。

④写出可移植 SQL 的准则

  1. 分页用标准写法：OFFSET ... FETCH 比 LIMIT 更标准，但 MySQL 老版本只认 LIMIT——折中是用 ORM 层抽象。
  2. 字符串拼接统一用 CONCAT()，避免 || 在 MySQL 下的陷阱。
  3. 标识符用双引号还是反引号：只在必要时加，且用目标库的风格；跨库项目建议统一小写无空格命名，干脆不引号。
  4. 别依赖数据库私有函数：如 MySQL 的 GROUP_CONCAT、PG 的 string_agg——在应用层或 ORM 里聚合。

⑤什么时候该放弃可移植性

当某项能力只有原生特性才能做好时（如 PG 的 JSONB/GIN、MySQL 的 GIS、SQL Server 的窗口聚合），直接在应用层封装并明确"该模块绑定某库"，比强行写最低公约数 SQL 更有性价比。可移植性不是目标，可维护性与正确迁移才是。

可移植性检查清单

① 所有分页用统一抽象；② 不写 || 拼接（MySQL 下是 OR）；③ 标识符命名规避引号；④ 不调用非标准聚合/窗口扩展；⑤ 迁移前用 EXPLAIN 在目标库验证执行计划；⑥ 用 COALESCE 而非库专属空值函数。

排障：迁移时最易踩的坑

MySQL→PG 最常见：① || 含义不同导致拼接变 OR；② 反引号在 PG 报错；③ LIKE 大小写敏感由 collation 决定；④ 自增改为 SERIAL/IDENTITY 后插入语句要去掉显式赋值；⑤ 布尔在 MySQL 是 TINYINT，应用层类型映射要对上。

自检 Q&A

ORM 能完全屏蔽方言差异吗？

不能。ORM 只覆盖常见 CRUD 与分页，复杂查询、原生函数、特定索引（如 PG 的 GIN）仍要写方言 SQL，且 ORM 生成的 SQL 在换库时往往要重新验证。

应该一开始就为可移植设计吗？

多数中小项目不必。绑定一个数据库、把差异收敛在少量数据访问层更务实。只有确实要支持多库（如做 BI 产品）时才值得投入抽象层。

LIMIT 和 FETCH 选哪个？

新项目且目标库都支持就用 OFFSET...FETCH（SQL 标准）；要兼容 MySQL 5.x 就用 LIMIT。两者性能本质一样，差异在兼容性。
