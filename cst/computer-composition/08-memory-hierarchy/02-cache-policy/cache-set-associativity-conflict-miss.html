CPU 缓存组相联手算：为什么隔 4 KiB 访问会撞到同一组

用 32 KiB、64 B 缓存行、8 路组相联的玩具缓存，算出 64 组与冲突失效。

先把容量拆成行、组和路

假设一个 32 KiB 的缓存，每行 64 B，8 路组相联。总行数是 32768/64=512 行；每组能放 8 行，所以共有 512/8=64 组。地址先按 64 B 行大小切成“块”，块号对 64 取模决定落到哪一组；同组的 8 个路位可容纳不同标签的行。缓存控制器用标签判断目标块是否已在组中，命中后把字节偏移交给 CPU。

这是一套教学用简化模型。真实处理器的各级缓存可能使用不同寻址、替换、预取、共享和散列策略，不能拿这组参数预测某个型号的实际延迟。手算的价值是识别容量失效与冲突失效为什么不同。

图解：玩具缓存中的九块冲突

沿箭头逐步核对输入、变换和输出；下面的推演可以逐步切换。

4 KiB 步长为何可能冲突

64 B 行的行内偏移占 6 位，64 组的组索引也占 6 位。若依次访问地址 0、4096、8192……，每次相差 4096/64=64 个块，块号对 64 取模的结果始终为 0，所以它们都映射到同一组。该组只有 8 路：前 8 个不同地址可占满 8 路，第 9 个地址进入时必须逐出其中一个。若访问循环反复轮到 9 个地址，替换策略与访问顺序可能导致大量冲突失效，即使全部数据只有 9×64=576 B，远小于缓存总容量。

“9 个地址一定每次都不命中”还取决于替换策略和循环顺序；在 LRU 风格的严格顺序轮换中会出现非常糟的情况。题目要说明假设。硬件预取、地址散列和缓存共享也可能改变真实测量结果，不能把玩具模型的 100% 失效率直接写成生产结论。

逐步推演

算总行数

32 KiB / 64 B = 512 行。

算组数

512 行 / 8 路 = 64 组。

算映射

4 KiB 步长对应 64 个块，组号不变。

第九块到来

同组八路已满，必须选择一行逐出。

三类失效放在一起比较

首次访问某块必然不在缓存，称冷失效或强制失效；工作集总量超过缓存容量，即使完全相联也装不下，称容量失效；工作集总量能装下，却因为映射规则让太多块挤进同一组，称冲突失效。上面 576 B 的九地址例子主要说明冲突。改成每次跨 64 B 且只扫 9 行，它们分布到不同组，通常不会产生同样冲突。

提高组相联度可降低某些冲突，但也可能增加标签比较、功耗和访问路径复杂度。把数据结构加填充或改变步长有时能错开映射；然而填充也增加内存占用和带宽，应以真实 CPU 的性能计数器和基准测试验证。不能看见缓存未命中就默认是“缓存太小”。

数组布局如何触发

二维数组按行连续存放，按行遍历通常具有空间局部性：一次取入缓存行后可消费相邻元素。按列跨大步长访问会频繁跳到新行，若步长恰好与组映射周期相关，还可能形成冲突。结构体数组与数组的结构体也影响每条缓存行里是否有需要的字段。访问模式、缓存行利用率和预取行为往往比几条算术指令更决定性能。

多核还要考虑缓存一致性与伪共享：两个线程更新同一缓存行的不同变量，会让该行在核间反复转移。这不是本课的“同一组内多个行争路位”冲突失效；两者都与缓存行有关，但病因和优化方法不同。看到多线程程序慢，应分别检查未命中与缓存行共享。

手算与验证流程

在纸上列出地址、块号、组号、标签：0/64=0，组 0；4096/64=64，组 0；8192/64=128，组 0，依此类推。第九个不同块也到组 0，就触发逐出。对比把第二个地址改成 64，块号 1、组 1，便能看出地址步长影响。若缓存改为 16 路、容量仍 32 KiB，则组数降为 32，映射周期也变了，需重新计算，不能只说“路数更多就一定全程更快”。

真实程序可以固定数组规模与访问顺序，多次测量并控制编译优化、预取、NUMA 和其他线程干扰；结合 L1/L2 miss、LLC miss 与 cycles 指标判断。仅凭一个 wall clock 差异无法证明组冲突。

常考小结

组数 = 容量 ÷ 行大小 ÷ 路数。地址可拆成标签、组索引和行内偏移；组相联度只允许同组内有有限个不同标签。容量足够仍可能发生冲突失效；改变访问步长和数据布局有时比增大容量更有效。练习：容量 32 KiB、行 64 B、8 路时，地址 0 与 4096 是否同组？第九个同组不同标签地址到来时会发生什么？

相联度三档与参数计算

映射方式一个块能放哪冲突失效硬件成本命中率
直接映射唯一一个位置最严重最低（1 个比较器）最低
组相联（N 路）某个 set 里的 N 个位置中等中等（N 个比较器）高
全相联任意位置无冲突失效最高（全并行比较）最高

参数计算

# 地址划分公式（必背）
#   块大小 B = 2^b 字节      -> 块内偏移 b 位
#   cache 共 C 字节，N 路组相联
#   组数 S = C / (B x N)     -> 组索引 s = log2(S) 位
#   标记 tag = 地址总位数 - s - b
#
# 例：32KB cache，64B 块，8 路组相联，32 位地址
#   b = log2(64)  = 6 位（偏移）
#   S = 32768 / (64 x 8) = 64 组
#   s = log2(64)  = 6 位（组索引）
#   tag = 32 - 6 - 6 = 20 位
#
#   每组的标记位数 = 8 路 x (20 tag + 1 valid + 1 dirty) = 176 位
#   总标记开销 = 64 组 x 176 = 11264 位 = 1.4 KB（约 cache 容量的 4%）

# 判断两块是否冲突：
#   冲突 <=> (addr1 >> b) % S == (addr2 >> b) % S
#   即「组索引相同」
#
# 经典冲突步长：
#   数组 stride = S x B = 64 x 64 = 4096 字节 = 1024 个 int
#   -> 遍历 a[0], a[1024], a[2048]... 全部落在同一组，8 路全被挤掉

复现代码

// 复现冲突失效（实测，通常慢 5~10 倍）
#include <stdio.h>
#include <time.h>
int main() {
    static int a[1 << 22];              // 16MB，远超 cache
    long n = 1L << 26;
    for (int stride = 1; stride <= 4096; stride *= 2) {
        clock_t t = clock();
        long s = 0;
        for (long i = 0; i < n; i++)
            s += a[(i * stride) & ((1 << 22) - 1)];
        double el = (double)(clock() - t) / CLOCKS_PER_SEC;
        printf("stride=%5d  %.3fs\n", stride, el);
    }
}
// 典型结果：stride=1..512 差不多快；stride=1024/2048/4096 突然变慢数倍
//   -> 因为都映射到同一组/少数几组，有效 cache 容量骤降

冲突失效的解法

手段做法效果代价
提高相联度8 路 → 16 路冲突失效大幅下降比较器与布线成本；延迟略增
加大 cache组数变多冲突概率下降面积与功耗
硬件：victim cache小块全相联缓存存放被挤出的块消除大部分冲突失效少量额外硬件
软件：改变数据布局数组填充（padding）错开组索引最实用浪费一点内存
软件：分块 blocking把大矩阵切成 cache 能装下的小块矩阵乘法可提速 2~5 倍代码复杂度
软件：改访问顺序避免 stride 为 2 的幂避免最坏的冲突—

填充与分块

// 数组填充：把可能冲突的数组错开
// 问题：a 和 b 可能被映射到同一组，交替访问时互相挤掉
#define PAD 64                      // 错开一组
int a[SIZE];
int pad[PAD];                       // 填充，让 b 的起始地址换到别的组
int b[SIZE];

// 矩阵分块（blocking / tiling）：最经典的 cache 优化
//   朴素三重循环：cache miss 率高，因为 B 的一列跨很多行
for (i) for (j) for (k) C[i][j] += A[i][k] * B[k][j];   // B 按列访问，差

//   分块后：每块装进 cache，重复利用
#define BLK 32                      // 块大小：使 3 x BLK x BLK x 4B 能装进 L1/L2
for (ii = 0; ii < N; ii += BLK)
  for (jj = 0; jj < N; jj += BLK)
    for (kk = 0; kk < N; kk += BLK)
      for (i = ii; i < ii+BLK; i++)
        for (j = jj; j < jj+BLK; j++)
          for (k = kk; k < kk+BLK; k++)
            C[i][j] += A[i][k] * B[k][j];
//   实测：N=1024 时可提速 2~5 倍（取决于 BLK 与 cache 大小）
为什么相联度不是越高越好？

因为边际收益递减 + 延迟上升。从直接映射到 2 路，命中率提升很明显；从 8 路到 16 路通常只提升 1~2 个百分点；再到全相联几乎没变化。同时更高相联度意味着每次访问要并行比较更多标记（更多比较器、更长的关键路径），会拉低主频。所以现代 CPU 的 L1 通常是 8 路、L2 是 8~16 路、L3 可能到 16~32 路——正是这个权衡的结果。

伪共享和冲突失效是一回事吗？

不是。冲突失效是单线程内的容量/映射问题（不同数据争同一组）；伪共享（false sharing）是多核间的一致性问题：两个核访问两个不同变量，但它们落在同一条 cache line上，导致 MESI 协议反复把该行标为无效，性能可能掉 10 倍。解法也不同：冲突失效靠布局/分块，伪共享靠按 cache line（64B）对齐填充。

怎么在真实程序里发现冲突失效？

用 perf：① perf stat 看 cache-misses 占比，若 >10% 就有问题；② perf record -e cache-misses + perf report 定位到具体函数甚至代码行；③ 用 perf c2c（cache-to-cache）看伪共享。另外可以做实验验证：改数据布局或访问顺序，看 miss 数是否骤降——这才是确认冲突失效的判据。

自检

总数据只有 576 B，小于 32 KiB 缓存，为什么仍会逐出缓存行？

九个不同块映射到同一组，而该组只有八路；这是组映射造成的冲突失效。
