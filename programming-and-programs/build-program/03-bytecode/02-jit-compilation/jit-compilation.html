JIT 编译与运行时优化

字节码为何接近原生速度：HotSpot 分层编译、去优化与逃逸分析

字节码之所以"跨平台又能快"，关键在执行端：解释器先跑起来，JIT 在运行时把热点编译成机器码。这一页讲清 HotSpot 的分层编译、去优化与逃逸分析。

一、解释器 vs JIT

方式启动峰值性能内存
纯解释秒级低小
JIT 编译略慢（编译开销）接近原生大（存机器码/Profile）
AOT快中~高中

二、HotSpot 的分层编译（Tiered）

0

纯解释

无 Profile，最快启动。

1

C1 简单

带基础 Profile 的快速编译。

2

C1 全 Profile

收集分支/类型信息供 C2 用。

3

C2 优化

激进优化：内联、逃逸分析、向量化。

JIT 不是"编译一次就定型"：当 Profile 失真（如数据类型变了），会去优化（deopt）回退到解释或更低层，保证正确性优先。

概念与判定

  • 什么时候 JIT 才划算：代码是"热点"（反复执行）才值得编译；冷路径一直解释反而更省。
  • JIT ≠ AOT：JIT 看运行时 Profile 做激进优化，AOT 在构建期编译、优化保守。

参数·命令·量化

  • JVM 开关：-XX:+TieredCompilation（默认开）、-XX:CompileThreshold 控制解释多少次后触发 C2。
  • GraalVM 提供高性能 JIT（Graal）与 Native Image（AOT）两条路。
  • 典型：C2 编译后的热点比解释快 10~100 倍，但首次编译有毫秒~秒级停顿。

排障与边界

  • 去优化抖动：Profile 反复变化导致编译/回退震荡，表现为偶发卡顿；看 -XX:+PrintCompilation。
  • 逃逸分析失效：一旦对象"逃逸"（被全局引用/线程共享），栈上分配与锁消除就做不了。

原理与取舍

  • 解释+JIT 混合：用启动速度换峰值性能，是 JVM/V8 的主流选择。
  • Tracing JIT（如 LuaJIT）：跟踪热点路径编译，对动态语言更友好，但实现复杂。
