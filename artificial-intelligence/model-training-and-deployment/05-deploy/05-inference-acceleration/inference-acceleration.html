推理优化

推理加速进阶：Continuous Batching、PagedAttention、投机解码

大模型推理的瓶颈不在算力，而在显存带宽和调度浪费。本文讲清推理的两个阶段差异、为什么 KV Cache 会成为显存杀手，以及 continuous batching、PagedAttention、投机解码这三项把吞吐拉起来的核心技术。

推理的两个阶段，瓶颈完全不同

Prefill（预填充）
  • 一次性处理整个 prompt
  • 大量矩阵乘，算力密集 compute-bound
  • 决定 TTFT（首 token 延迟）
Decode（解码）
  • 每次只生成一个 token
  • 要反复读模型权重和 KV Cache，带宽密集 memory-bound
  • 决定 TPOT / 出字速度
绝大多数在线服务的 token 都花在 decode 阶段，而 decode 的瓶颈是"把权重从显存搬到计算单元"的带宽，不是算力。所以推理优化的第一原则是：提高 batch 大小，让一次权重加载服务更多请求。

KV Cache：提速的关键，也是显存杀手

decode 时为了避免重算历史，把每一层注意力的 Key/Value 缓存下来。代价是显存随 batch × 序列长度 × 层数 × 头数 线性增长，长上下文场景下非常可观。

已知优化方向：MQA / GQA 减少 KV 头数、KV Cache 量化（fp8/int8）、跨请求前缀共享（Prompt Caching）、以及下面要讲的分页管理。

Continuous Batching：别让 GPU 空等

核心思想：把"批"从静态改为动态——调度粒度从"整批"降到"单步"。某个请求生成结束（遇到 EOS）就立刻退出，空出的槽位马上塞入排队的新请求。这是现代推理框架（vLLM、TGI、SGLang 等）吞吐远超朴素实现的最大原因。

PagedAttention：解决 KV Cache 的碎片与预留浪费

朴素实现会为每个请求按最大长度预留一整块连续显存。问题：

内部碎片：请求只生成 200 token 却占了 2048 的坑，剩下的用不上也给别人用不了
外部碎片：不同长度的请求反复申请释放，显存被切成碎块，明明有空间却分配不出

PagedAttention 的解法：借鉴操作系统的虚拟内存分页——把 KV Cache 切成固定大小的"页"（block），按需分配、逻辑上连续但物理上可以不连续，用页表做映射。

收益：① 显存浪费大幅下降 → 同样的卡能塞下更大的 batch → 吞吐更高；② 相同前缀的请求可以共享页（如相同的 system prompt、并行采样、beam search），进一步省显存。

投机解码 Speculative Decoding

decode 阶段一次只出 1 个 token，却要完整读一遍模型权重，非常浪费。投机解码用"小模型先猜、大模型批量验"来打破这个限制：

为什么能加速：decode 是带宽瓶颈而非算力瓶颈，把"γ 次权重读取"压成"1 次"，就把串行变成了并行。理论上可保证输出分布不变（无损加速），实际加速比取决于草稿模型的命中率。
命中率受任务类型影响很大：代码、格式化输出、常见套话命中率高（加速明显）；高度发散的创作类命中率低，收益有限甚至反而变慢。

其它常用手段速览

手段解决什么
算子融合 / FlashAttention减少显存读写次数（把多步合并成一个 kernel），注意力显存从 O(n²) 降到 O(n)
量化（INT8/FP8/INT4）减少权重体积与带宽压力，直接提速；详见「大模型量化详解」
Prompt Caching / 前缀缓存相同前缀只算一次，显著降低 TTFT 与成本
张量并行（推理侧）模型太大单卡放不下时切分，并分摊带宽压力
MQA / GQA减少 KV 头数，直接缩小 KV Cache
分离式部署（prefill/decode 分开）两阶段特性不同，分开部署可各自优化资源配比

怎么衡量优化效果

TTFT
首 token 延迟，用户"等多久开始出字"
TPOT / tokens-per-sec
出字速度，决定长回答体验
吞吐 tokens/sec
整集群的总产出，决定成本
吞吐和延迟往往互相拉扯：batch 越大吞吐越高，但单请求排队更久、延迟上升。选型时要按业务定 SLO（比如 P99 TTFT < 1s），再在此约束下把吞吐压到最高。

面试速记卡

  • 两阶段：prefill 算力密集（定 TTFT），decode 带宽密集（定出字速度）。
  • 第一原则：decode 是带宽瓶颈 → 加大 batch 让一次权重读取服务更多请求。
  • Continuous Batching：调度粒度降到单步，结束即补位，是吞吐提升的最大来源。
  • PagedAttention：KV Cache 分页管理，消除碎片与预留浪费，支持前缀共享。
  • 投机解码：小模型草稿 + 大模型并行验证，分布不变的无损加速；收益取决于命中率。
  • 指标三角：TTFT / TPOT / 吞吐，吞吐与延迟互相拉扯，按 SLO 定。

推理加速手段的量化收益

手段典型加速精度代价备注
FP32 → FP162~3×几乎无损Tensor Core 需要 FP16；注意溢出
FP16 → INT8（PTQ）再 2~4×0.5~2% 掉点需校准，推荐 per-channel
INT8 → INT4（GPTQ/AWQ）再 1.5~2×1~3% 掉点LLM 常用 AWQ（保激活离群）
算子融合（Conv+BN+ReLU）1.2~1.5×无损省掉中间显存读写
TensorRT / ONNX Runtime2~6×（相比 PyTorch eager）无损/微小含融合、内核自动调优
torch.compile（2.0+）1.3~2×无损一行代码，性价比最高
KV Cache生成阶段 5~10×无损空间换时间，显存占用增加
连续批处理（vLLM）吞吐 2~4×无损解决 padding 与静态批的浪费
FlashAttention2~4×（长序列）无损IO 感知，显存从 O(n²) 降到 O(n)
投机解码2~3×无损（输出分布一致）小模型打草稿，大模型并行验证
剪枝 / 稀疏化1.5~3×1~3% 掉点需硬件支持稀疏才有实际加速
蒸馏2~10×（模型变小）1~5% 掉点本质是把大模型的能力搬进小模型

加速的优先顺序（性价比排序）：① 开 torch.compile/TensorRT（一行代码，无损）；② 算子融合 + 精度降到 FP16（无损，2~3 倍）；③ 批处理 / 连续批处理（吞吐提升最猛）；④ 量化到 INT8（开始有掉点，需评测）；⑤ 最后才是改模型结构（剪枝、蒸馏）。

可直接用的代码

import torch

# 1) torch.compile：一行，通常 1.3~2x，无精度损失
model = torch.compile(model, mode="max-autotune")   # mode: default/reduce-overhead/max-autotune

# 2) FP16 / BF16
model = model.half()                    # FP16，注意梯度溢出需 GradScaler（推理不用）
model = model.to(torch.bfloat16)        # BF16，动态范围同 FP32，A100/H100 上首选

# 3) 自动混合精度推理
with torch.autocast("cuda", dtype=torch.bfloat16):
    out = model(x)

# 4) 动态量化（CPU，最快见效）
import torch.quantization as Q
qmodel = Q.quantize_dynamic(model, {torch.nn.Linear}, dtype=torch.qint8)
# 典型：BERT-base 从 400MB 降到 100MB，CPU 推理快 2~4x

# 5) ONNX 导出 + ORT 优化
torch.onnx.export(model, dummy, "m.onnx", opset_version=17, dynamic_axes={"x": {0: "B"}})
# 然后用 onnxruntime-gpu 或转成 TensorRT engine
# TensorRT：融合 + 内核自动调优 + INT8 校准
trtexec --onnx=m.onnx --saveEngine=m.engine \
        --fp16 --workspace=4096 \
        --optShapes=x:1x3x224x224 --maxShapes=x:32x3x224x224
# 输出会打印每层耗时，直接定位瓶颈算子

# INT8 校准（PTQ，需 500~1000 条代表性样本）
trtexec --onnx=m.onnx --int8 --calib=calib.cache --saveEngine=m_int8.engine

# vLLM 连续批处理 + PagedAttention
python -m vllm.entrypoints.openai.api_server \
  --model meta-llama/Llama-2-7b --dtype bfloat16 \
  --max-model-len 4096 --gpu-memory-utilization 0.9 \
  --enable-prefix-caching          # 相同 system prompt 复用 KV，省 30%+ 算力

加速排障清单

症状原因处理
开了 FP16 结果全 nan激活/梯度溢出（FP16 上限 65504）改用 BF16；或关键层（LayerNorm、Softmax）保留 FP32
量化后掉点严重per-tensor 量化遇到离群通道改 per-channel 量化；LLM 用 AWQ/SmoothQuant 平滑离群值
加速了但吞吐没变瓶颈不在算力（是访存或 CPU 前处理）先 profile：看 GPU 利用率；< 50% 说明是数据搬运或前处理瓶颈
batch 加大后延迟暴涨显存带宽饱和 / padding 浪费用动态 batch（按长度分桶）；LLM 用连续批处理
TensorRT 编译很久内核自动调优要试很多实现编译一次存 engine 复用；--workspace 给足
torch.compile 报错 / 不生效图被打破（动态控制流、.item()、print）看 TORCH_LOGS=graph_breaks；减少动态分支
显存不够KV cache 与激活占大头开梯度检查点（训练）、量化 KV cache、PagedAttention（vLLM）
小 batch 下加速不明显kernel 启动开销主导用 CUDA Graph 把多次启动合并；或加大 batch

先测再优化：用 torch.profiler 或 Nsight 看清楚是 compute-bound 还是 memory-bound。大多数推理瓶颈其实是访存（读权重），这时量化（减少要读的字节数）比换更快的算子更有效。
