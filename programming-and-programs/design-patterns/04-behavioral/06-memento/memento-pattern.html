01 · 从问题出发

为什么会需要这个模式？

画布编辑器要支持撤销，但历史管理器不该直接改画布内部字段。

画布编辑器要撤销拖动。若历史管理器直接读取画布的 shapes、selection、zoom 等私有字段，它就会依赖画布内部结构；画布一改，历史也要跟着改。

😵 直接写会怎样

history.push({shapes: canvas.shapes, zoom: canvas.zoom})
// shapes 是共享引用；后来拖动会一起改变历史

💡 关键转折

原发器生成/恢复快照；保管者只保存快照，不解释其中内容。

让画布自己生成和恢复快照；历史管理器只负责保管，不解析内部状态。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

class Canvas {
  save() { return Snapshot(deepCopy(this.shapes)) }
  restore(snapshot) { this.shapes = deepCopy(snapshot.shapes) }
}
undoStack.push(canvas.save())
canvas.move(shape, dx, dy)
canvas.restore(undoStack.pop())

读代码时抓住三件事

  1. save 由原发器创建快照，不暴露可变内部引用。
  2. restore 由原发器解释快照并重建合法状态。
  3. 历史栈只管存取顺序，可设置容量上限。

换个业务场景，还能认出来吗？

游戏存档能恢复角色位置、背包和任务进度。快照范围应明确：外部服务器状态、现实世界时间和未提交网络操作通常不能靠本地存档自动还原。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

要保存对象旧状态以支持撤销或恢复

三个具体场景

  • 画布撤销拖动与改色
  • 游戏存档恢复角色状态
  • 编辑器回到之前的文档版本

不适合或要小心

快照可能很大；可限制历史长度、保存增量或与命令模式结合。深浅拷贝必须按状态所有权设计。

快照会消耗空间；共享可变引用会让历史被后续修改污染

最容易混淆的相邻模式

模式真正的区别
命令保存操作及逆操作，适合可逆编辑；备忘录保存状态快照，适合复杂状态恢复。
原型复制对象用于创建新对象；备忘录复制状态用于以后恢复原对象。

区分时问自己：需要恢复旧状态，还是反向执行一条操作？

落地前检查

  • 测试快照创建后再改当前对象，快照不应变化。
  • 定义历史上限与增量存储策略。
  • 明确哪些外部副作用不在快照恢复范围内。
06 · 自己说一遍

两道检验理解的小题

历史栈为什么不直接改 shapes？

快照的创建与恢复由画布负责，历史栈只保管，避免破坏封装。

保存整个对象的浅拷贝为何可能让撤销失败？

嵌套可变数据若共享引用，后续编辑也会改到历史快照，恢复时拿不到旧状态。

模式速览：把状态存成快照，但不拆开封装

备忘录解决的是矛盾：想保存对象状态以便恢复，但不希望为了取出状态而暴露它的内部细节。做法是让对象自己生成一个「状态快照」交给外部保管，外部只保管、不解读，需要时原样还回去。

意图捕获并外部化对象状态，之后可恢复，且不破坏封装
角色原发器（产生与恢复）、备忘录（快照）、管理者（保管）
何时用撤销重做、事务回滚、存档、草稿恢复
代价快照占内存；深拷贝有开销；版本过多要管理
备忘录的流转：快照由原发器生产、管理者保管、原发器消费

四种「保存状态」的做法对比

做法机制封装性适合
备忘录对象自己导出与导入快照最好，外部看不懂内容需要严格封装的场景
深拷贝整个对象复制一份完整实例取决于拷贝实现结构简单、状态不多
命令模式撤销记录操作并反向执行好，先记动作操作可逆且代价低
版本历史只记录变更增量中等状态很大、变更很小

备忘录与命令撤销的区别

备忘录存的是状态的快照，恢复时直接覆盖；命令模式存的是操作的逆动作，恢复时反向执行一遍。前者实现简单、恢复准确，但占内存；后者省内存，但要求每个操作都能正确取反。

为什么要专门有个管理者

为了让原发器不必记住历史，也让客户端不必知道快照长什么样。管理者只负责「存」和「取」，是典型的职责分离：谁产生、谁保管、谁消费，三者互不知道对方细节。

Go 里的实现：一个可撤销的编辑器

// 备忘录：只保存状态，不提供解读方法 type snapshot struct { text string cursor int } // 原发器：唯一能读写快照内容的角色 type Editor struct { text string cursor int } func (e *Editor) Save() snapshot { return snapshot{text: e.text, cursor: e.cursor} } func (e *Editor) Restore(s snapshot) { e.text = s.text e.cursor = s.cursor } // 管理者：只保管，不解读 type History struct { stack []snapshot } func (h *History) Push(s snapshot) { h.stack = append(h.stack, s) } func (h *History) Pop() (snapshot, bool) { n := len(h.stack) if n == 0 { return snapshot{}, false } s := h.stack[n-1] h.stack = h.stack[:n-1] return s, true } // 使用 ed := &Editor{} his := &History{} his.Push(ed.Save()) // 改动前先存一份 ed.text = "new text" if s, ok := his.Pop(); ok { ed.Restore(s) // 回滚 } // 关键点： // 1) 快照类型是小写未导出的，外部包拿得到但读不懂 // 2) 快照应该是值语义，避免后续修改影响已存的版本 // 3) 历史要有上限，否则内存会无限增长

深入自检：备忘录的五个问题

快照里如果存了引用会怎样？

会变成浅拷贝：原对象继续修改引用指向的内容，之前的快照也被改了，回滚就失效了。所以生成快照时，对可变字段必须做深拷贝，或者把快照设计成不可变结构。

历史记录无限增长怎么办？

设上限：超过一定步数就丢弃最旧的，或者定期做一次全量快照、只保留之后的增量。这也是很多编辑器的做法：内存里的撤销步数有限，持久化时才保留完整历史。

备忘录和直接序列化有什么区别？

序列化得到的是可跨进程、可持久化的字节，但会暴露结构、还要处理版本兼容；备忘录是进程内的对象快照，更轻量、更保密，但不适合跨进程。需要存档到磁盘时通常还是要用序列化。

为什么强调不让外部解读快照？

因为一旦外部能读，就等于绕过了封装直接依赖内部字段。将来内部改结构，所有读快照的地方都要跟着改。让快照对外只是一个不透明的值，内部结构就能自由演化。

并发下要注意什么？

快照必须反映一个一致的状态点。如果对象在生成快照的同时被修改，可能存到一个「改了一半」的状态。做法是在生成与恢复时加锁，或者让状态本身是不可变的。

三个角色原发器、备忘录、管理者

对外不透明外部只保管，不解读
历史要设上限防止内存无限增长
