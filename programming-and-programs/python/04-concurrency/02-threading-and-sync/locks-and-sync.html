锁与同步原语：线程安全的正确姿势

「GIL 不是线程安全的万能锁」——这是最大的误区。GIL 只保证字节码级不崩溃，不保证你的「读-改-写」不被另一个线程打断。共享可变状态要自己加锁，否则 count += 1 都会丢更新。

竞态条件

GIL 不保护你的「读改写」

count += 1 在字节码层面是「取→加→存」三步。两个线程可能都取到旧值、各自存回，结果只 +1 而不是 +2。GIL 让单条字节码原子，但保不住多步操作。

import threading
counter = 0
def inc():
    global counter
    for _ in range(100000):
        counter += 1          # 非原子：会丢更新

ts = [threading.Thread(target=inc) for _ in range(2)]
[t.start() for t in ts]; [t.join() for t in ts]
print(counter)            # 经常 < 200000
⚠️ 最大误区：以为「有 GIL 就线程安全」。GIL 防的是解释器崩溃，不是业务逻辑竞态。任何「检查再修改」「读改写」共享状态，都要同步。
Lock / RLock

用 with 锁住临界区

Lock 是互斥锁，同一时刻只放一个线程进临界区；用 with lock: 自动加锁/释放，最安全。RLock 可重入，同一线程能多次acquire而不死锁（递归函数常用）。

counter = 0
lock = threading.Lock()
def inc():
    global counter
    for _ in range(100000):
        with lock:        # 进入临界区才允许改
            counter += 1

# RLock：同线程可重入，适合调用链里多次加锁
rlock = threading.RLock()
def a():
    with rlock: b()   # b() 再次 acquire 不会死锁
def b():
    with rlock: pass
临界区越小越好——只在「确实改共享状态」的那几行加锁，别把整个函数包住，否则多线程退化成串行，白用线程。
其它原语

不止 Lock：按语义选工具

信号量限制并发数、Event 做线程间信号、Condition 做「等条件满足」，各有适用场景。

原语语义典型用途
Lock/RLock互斥保护临界区
Semaphore最多 N 个同时进限流、连接池大小
Event一次性信号广播主线程通知工作线程启动/停止
Condition等某个条件成立生产者-消费者就绪通知
sem = threading.Semaphore(3)   # 同时最多 3 个线程进入
def work():
    with sem:
        do_io()

这些原语都来自标准库 threading。它们解决「共享内存」的同步；如果你用多进程（各自内存独立），要换成 multiprocessing 里的同名原语或通过 Queue/共享内存通信。

Queue 首选

多数场景：用 Queue 代替手搓锁

queue.Queue 是线程安全的「生产者-消费者」管道，内部已加锁。把「共享状态」变成「通过队列传递数据」，能大幅减少自己加锁出错的概率。

import queue, threading
q = queue.Queue(maxsize=10)

def producer():
    for i in range(20): q.put(i)   # 满则阻塞

def consumer():
    while True:
        item = q.get()              # 空则阻塞，自带锁
        process(item)
        q.task_done()

for _ in range(3): threading.Thread(target=consumer, daemon=True).start()
经验法则：能用 Queue / 不可变数据 / 每线程独享状态解决的问题，就别用 Lock。锁越多，死锁和性能坑越多。
死锁

两个锁互相等待，谁都不放

线程 A 持锁1等锁2、线程 B 持锁2等锁1，永久卡住。避免法：固定加锁顺序、用 with 保证释放、必要时 acquire(timeout=) 设超时。

l1, l2 = threading.Lock(), threading.Lock()

# 危险：两个线程以相反顺序加锁 → 死锁
def t1():
    with l1:
        with l2: work()

# 安全：所有路径统一先 l1 后 l2
def safe():
    with l1:
        with l2: work()

# 或加超时，避免无限等
if l2.acquire(timeout=1):
    try: work()
    finally: l2.release()

选型与同步是并发的两根支柱：先读线程/进程/协程选型定模型，再用本篇的锁/队列保证线程安全。协程（asyncio）则基本不用这些锁，靠「单线程不抢占」天然避开竞态（见异步模式）。

五种同步原语：选错就出 bug

原语用途能否重复获取典型场景
Lock（互斥锁）最简单，一次一人否（会死锁）默认选择，保护共享变量
RLock（可重入锁）同一线程可多次获取是递归函数、一个方法调另一个加锁方法
Semaphore限流：最多 N 个同时—限制并发数（如最多 10 个下载）
Event一个线程通知其他线程—启动信号、一次性通知
Condition等待某条件成立内部用 RLock生产者-消费者
Barrier等 N 个线程都到齐再继续—分阶段并行计算

同步原语用法

import threading

# ① Lock：最常用，务必用 with（自动释放，异常也安全）
lock = threading.Lock()
counter = 0

def increment():
    global counter
    for _ in range(100000):
        with lock:                  # ✅ 等价于 try/finally 的 acquire/release
            counter += 1
# ❌ 不要这样写：忘记 release 或中途异常会导致死锁
#   lock.acquire(); counter += 1; lock.release()

# ② RLock：同一线程可重复获取（Lock 会死锁）
rlock = threading.RLock()
def outer():
    with rlock:
        inner()                     # inner 里也 with rlock -> Lock 会死锁，RLock 不会

# ③ Semaphore：限制并发数（比 Lock 更适合"资源池"）
sem = threading.Semaphore(10)       # 最多 10 个同时运行
def download(url):
    with sem:
        return fetch(url)

# ④ Event：一次性通知（比忙等高效得多）
ready = threading.Event()
def worker():
    ready.wait()                    # 阻塞直到 set()
    do_work()
def starter():
    init()
    ready.set()                     # 通知所有等待者

# ⑤ Condition：生产者-消费者（wait/notify 的标准模式）
cv = threading.Condition()
queue = []
def consumer():
    with cv:
        while not queue:            # ⚠️ 必须用 while 而不是 if（防虚假唤醒）
            cv.wait()
        item = queue.pop(0)
def producer(item):
    with cv:
        queue.append(item)
        cv.notify()                 # 或 notify_all()

死锁四条件：互斥、占有且等待、不可抢占、循环等待。只要破坏任意一个即可避免。最实用的破法是破坏循环等待——所有线程按相同的顺序获取锁（如按 id 排序）。

GIL 下到底要不要加锁？

这是最常被误解的问题。GIL 保证的是“字节码执行的原子性”，不保证“你的逻辑的原子性”。

操作是否原子要不要锁
x += 1❌ 不是（LOAD → ADD → STORE 三步）必须加锁
list.append(x)✅ 是（GIL 保证单条字节码原子）可不加
d[k] = v✅ 是可不加
d[k] = d[k] + 1❌ 不是（读-改-写）必须加锁
queue.Queue 操作✅ 是（内部已加锁）可不加
if k in d: d[k] = v❌ 不是（检查与使用之间有窗口）必须加锁

GIL 与原子性实测

# 实测：不加锁的 counter 一定出错（但不一定每次都错，所以更危险）
import threading
counter = 0

def unsafe_inc():
    global counter
    for _ in range(200000):
        counter += 1        # 实际是 tmp=counter; tmp=tmp+1; counter=tmp 三步

threads = [threading.Thread(target=unsafe_inc) for _ in range(4)]
[t.start() for t in threads]; [t.join() for t in threads]
print(counter)              # 期望 800000，实际常常只有 400000-700000

# 为什么"有时对有时错"？
#   因为 GIL 每 5ms 切换一次（sys.getswitchinterval()）
#   切换点如果正好在 LOAD 和 STORE 之间，另一个线程的写入就被覆盖了
#   -> 这是典型的竞态条件（race condition），极难复现和排查

# 用 dis 看明白为什么 += 不是原子的
import dis
def f():
    global counter
    counter += 1
dis.dis(f)
# LOAD_GLOBAL  counter      <- ① 读
# LOAD_CONST   1
# BINARY_OP    +=           <- ② 算
# STORE_GLOBAL counter      <- ③ 写   <- 切换可能发生在 ①②③ 任意之间

# ✅ 正确做法（三选一）
#   ① 加锁
#   ② 用 queue.Queue 传递数据（内部线程安全）
#   ③ 改用单线程 + asyncio（消除共享状态，最彻底）

锁的性能开销与粒度权衡

操作典型耗时说明
无竞争加锁/解锁约 50 – 100 ns现代 Linux 的 futex 很快
有竞争加锁约 1 – 10 μs要陷入内核等待
长时间等待毫秒级取决于持锁时间
对比：一次简单函数调用约 100 ns锁开销约等于一次函数调用

结论：无竞争的锁很便宜（约 100 ns），不要过早优化掉必要的锁。真正的问题是锁竞争和持锁时间过长——如果 4 个线程都在抢同一把锁做 200 万次自增，加锁版本可能比不加锁还慢几倍（来回切换）。

锁优化策略

# 优化策略①：减小锁粒度（把大锁拆成多个小锁）
# ❌ 一把大锁保护整个字典 -> 所有操作串行
lock = threading.Lock()
cache = {}
def get(k):
    with lock: return cache.get(k)

# ✅ 分片锁：按 key 哈希到 N 把锁，冲突概率降为 1/N
NUM = 16
locks = [threading.Lock() for _ in range(NUM)]
def get(k):
    with locks[hash(k) % NUM]:
        return cache.get(k)

# 优化策略②：减小持锁范围（不要在锁里做 IO！）
# ❌ 持锁期间做网络请求 -> 其他线程全被阻塞
with lock:
    data = requests.get(url)      # 100ms！
    cache[k] = data

# ✅ 先做慢操作，再短促加锁
data = requests.get(url)          # 锁外做
with lock:
    cache[k] = data               # 只保护真正需要保护的部分

# 优化策略③：读写分离（读多写少用 RWLock，标准库没有，需第三方）
#   pip install readerwriterlock
#   或用 copy-on-write：读不加锁，写时复制整个结构再原子替换引用

深入自检

有了 GIL，多线程是不是就没用了？

不是。GIL 只在执行字节码时被持有，遇到 IO、sleep、C 扩展的耗时操作都会释放。所以：IO 密集任务多线程完全有效（文件、网络、数据库）；CPU 密集任务多线程无效（要用多进程）。判断方法：看瓶颈是 CPU 还是等待——top 里 CPU 打满 → 进程；CPU 很闲但慢 → IO → 线程/协程。

怎么避免死锁？

四条实用规则：① 固定加锁顺序——所有代码按同一顺序获取多把锁（如按对象的 id 排序），这能直接破坏循环等待；② 用 with 自动释放，避免忘记 release；③ 加锁带超时——lock.acquire(timeout=5)，拿不到就放弃并报错（比永久卡死好排查）；④ 持锁期间不调用外部代码（避免别人在你不知情时加别的锁）。调试技巧：用 faulthandler.dump_traceback_later(10) 或 threading.settrace 打印所有线程的堆栈，能直接看出谁在等谁。

Lock 和 RLock 该选哪个？

默认用 Lock。只在确实需要重入时用 RLock（如递归函数、或方法 A 调用同样加锁的方法 B）。RLock 的代价：① 需要记录持有者和计数，比 Lock 慢约 2 – 3 倍；② 它掩盖了设计问题——如果你需要重入，通常说明锁的层级划分不合理，更好的做法是拆分出不需要加锁的内部方法（如 _get_unlocked()），让公共方法负责加锁、内部方法不加锁。

多线程共享数据的最佳实践是什么？

优先级从高到低：① 不共享——用 concurrent.futures 让每个任务返回独立结果，由主线程汇总（最推荐，几乎无 bug）；② 用线程安全容器——queue.Queue 传递消息，这是生产者-消费者的标准解法（内部已加锁，你不用管）；③ 不可变数据——共享只读对象无需加锁；④ 最小锁——实在要共享可变状态，就锁住尽可能小的范围。经验谈：90% 的并发 bug 都能通过“改成不共享”消除，而不是通过“加锁加得更精细”。
