01 · 从问题出发

为什么会需要这个模式？

语法树节点类型稳定，但要频繁新增格式化、类型检查、代码生成等操作。

语法树已有 Number、Add 等节点。现在需要格式化、类型检查、统计节点数；若把每种操作都塞入节点类，节点代码会随着新操作不断膨胀。

😵 直接写会怎样

class AddNode:
  format() ...
  typeCheck() ...
  countNodes() ...
  generateCode() ...  // 每加一种操作都改节点

💡 关键转折

节点提供 accept(visitor)；访问者按具体节点类型实现 visitX。

节点只提供 accept(visitor) 入口；访问者按节点类型实现操作。新增操作时新增访问者，结构中的节点可保持稳定。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

interface Visitor { visitNumber(node); visitAdd(node) }
class NumberNode {
  accept(visitor) { return visitor.visitNumber(this) }
}
class AddNode {
  accept(visitor) { return visitor.visitAdd(this) }
}
class PrettyPrinter implements Visitor {
  visitNumber(n) { return String(n.value) }
  visitAdd(n) { return n.left.accept(this) + "+" + n.right.accept(this) }
}

读代码时抓住三件事

  1. accept 是第一次分派：由具体节点选择 visitNumber/visitAdd。
  2. visitX 是第二次分派：访问者按节点类型执行逻辑。
  3. 复合节点的访问者方法可递归调用孩子的 accept。

换个业务场景，还能认出来吗？

编译器常用访问者对 AST 做静态检查、代码生成和优化分析。若语法节点经常新增，维护每个访问者的方法会很累；访问者适合节点结构相对稳定、操作经常新增。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

对象结构稳定，但要频繁增加作用于整棵结构的操作

三个具体场景

  • AST 增加格式化与类型检查
  • 文档树增加导出与统计
  • 商品结构增加税费和审计分析

不适合或要小心

新增节点类型会迫使所有访问者增加方法；若节点常变，访问者可能反而增加维护成本。

新增节点类型会迫使每个访问者增加方法

最容易混淆的相邻模式

模式真正的区别
策略替换一套算法；访问者让一套操作按多种节点类型分别执行。
组合构建树形节点结构；访问者把作用于整棵树的操作从节点类分离。

区分时问自己：新需求主要增加节点种类，还是增加针对已有节点的操作？

落地前检查

  • 新增节点类型前统计已有访问者数量。
  • 给每个访问者覆盖所有节点类型。
  • 避免访问者直接修改不该暴露的节点内部状态。
06 · 自己说一遍

两道检验理解的小题

新增“统计节点数”会修改所有节点吗？

通常只需增加一个 Visitor 实现，已有节点继续调用 accept。

访问者为何被说成“双重分派”？

执行结果同时由“具体节点类型”和“具体访问者类型”决定：节点的 accept 调用对应 visitX，访问者实现再决定操作。
