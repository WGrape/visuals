数据备份与复制：一份通用知识大纲

MySQL、Redis、Elasticsearch、Milvus、Kafka 的备份方案看着千差万别，其实都能拆成同一组要素。这篇给你一个能“套”到任何存储系统上的模型，从此不用逐个死记。

三道防线五要素模型三种范式复制通道确认点系统解剖全景对照跨地域容灾设计检查表速记口诀延伸阅读

🧱先分清三件事：副本、备份、容灾

绝大多数“记不住”，是因为把这三件事混成了一个词。它们防的是完全不同的故障，代价和手段也完全不同。先建立这条主线，后面所有方案都能挂上去。

一句话记住：副本抗硬件坏，备份抗人搞错，容灾抗地方没。三者不能互相替代——副本会把误删同步到从库，备份如果和生产放在同一个机房，地域故障时会一起丢。

🧩通用五要素：任何系统都能拆成这五个问题

看到任何一款存储，问这五个问题，它的备份方案就自动浮现了。这也是本篇的核心骨架，后面所有系统都按这五列展开。

① 数据单位是什么？被切分的粒度：MySQL 的库表、ES 的 index、Milvus 的 collection、Kafka 的 topic、Redis 的 KV。
② 冗余单位是什么？复制跟随哪个对象一起走：MySQL 是整实例，ES 是分片（shard），Kafka 是分区（partition），Milvus 是段（segment）落到共享存储。
③ 复制通道传什么？物理日志（字节级 WAL）、逻辑日志（行事件 / 消息）、还是状态快照（整份文件）。这决定了能不能跨版本、追赶快不快。
④ 什么时候算写成功？异步、半同步、多数派、全同步。这一档直接决定 RPO，也决定尾延迟。
⑤ 历史怎么留、怎么回到过去？全量 + 增量的组合，能否时间点恢复（PITR），备份放在哪个故障域。
记忆技巧：前四问描述“现在的第二份数据在哪、有多新”，第五问描述“昨天的那份还在不在”。前者叫高可用，后者叫可恢复，两件事都要做。

🔀三种复制范式：看似不同，其实只有这三种

所有系统的冗余方案，本质上落在下面三种拓扑之一。点选切换，观察数据流向与节点职责的变化。

📦复制通道：传的到底是什么

“复制”不是一个动作，而是三种可选的内容。选了哪种，就决定了跨版本兼容性、追赶速度和故障后需要重建多少数据。

物理日志 WAL / Redo

传的是磁盘块的字节变化。最贴近存储引擎，重放最快、体积最小，但和版本、页格式强耦合，通常不能跨大版本或跨引擎使用。

逻辑日志 Binlog / 消息

传的是行的变更事件或消息本身（MySQL row 格式 binlog、Kafka 的消息日志）。可读、可跨版本、能用来做订阅与回放；代价是重放要做一遍完整逻辑，且依赖幂等与顺序。

状态快照 RDB / 段文件

传的是某一时刻的整份数据。用于初次全量同步或备份（Redis RDB、ES snapshot、Milvus 的 binlog 段）。追赶要靠“快照 + 之后的增量日志”组合，缺一不可。

通用组合：先快照把基线搬过去，再用增量日志追平，之后保持增量流。几乎所有系统的“加入一个新副本”都是这三步——MySQL 用备份+binlog 位点，Redis 用 RDB+命令流，Kafka 新副本从分区开头或指定位点拉取。

🎚️确认点四档：决定 RPO 的那个旋钮

同样叫“有副本”，确认时机不同，故障时丢的数据量可以差好几个数量级。这一档是设计里最该显式写清楚的。

档位何时向客户端确认故障时可能丢什么代价常见代表
异步主节点本地写成功即返回尚未发出的全部事务/消息延迟最低、吞吐最高；RPO 等于复制延迟MySQL 默认复制、Redis 默认复制
半同步至少一个副本收到日志后返回收到但未落盘/未回放的部分延迟上升；副本失联要决定阻塞还是降级MySQL semi-sync、Redis WAIT
多数派超过半数成员持久化后返回理论上不丢已确认数据需要奇数成员与选举；成员不足时拒绝写入Raft（etcd/ZK）、Kafka ISR、MySQL 组复制
全同步全部副本完成约定动作后返回趋近于 0任一副本或网络抖动都会拖慢甚至阻塞写入强一致存储、部分托管服务的多 AZ 写入
易踩的坑：“收到”不等于“已落盘”，更不等于“已回放”。半同步只保证日志到了对端，不保证对端已经应用；切换时仍可能有一段未回放的数据，需要等待或回滚补齐。

🗺️全景对照表：一张表看完全部

同一张表、同一组列。差别只在每个格子填什么——这正是这套模型想给你的东西。

系统冗余单位复制通道确认语义历史与备份手段
MySQL实例级主备（也有组复制/PXC）binlog（row 为主）+ relay log；新库用备份+位点异步 / 半同步 / 组复制多数派全量备份 + binlog → 时间点恢复（PITR）
Redis实例级主从；Cluster 下按槽分片命令流增量（复制积压区）+ RDB 全量异步；可用 WAIT 显式等待 N 个副本RDB 快照 + AOF 重放；AOF 用于把丢失窗口压到秒级
Elasticsearch分片：主分片 + 副本分片translog 与段复制；副本重放主分片的操作等待 in-sync 副本组；wait_for_active_shards 控制需活跃份数（默认 1，仅主分片）快照到共享仓库（增量），支持按索引恢复
Milvus段（segment）落到共享对象存储；计算节点无状态WAL 日志代理（Pulsar / Kafka；2.6 起可选原生 Woodpecker WAL）依赖底层日志持久化；查询侧可选一致性级别（Strong / Bounded / Session / Eventual）对象存储自有多副本与跨桶复制；原始数据可重灌重建
Kafka分区 + 副本；ISR 为同步集合消息日志本身，跟随者拉取acks=0 / 1 / all 配合 min.insync.replicas保留期提供重放窗口；MirrorMaker 2 做跨集群；分层存储把老数据下沉
etcd / ZooKeeper集群成员；法定多数派Raft / ZAB 日志多数派提交后才算成功快照 + WAL；成员数决定可容忍失败数
HDFS / 对象存储数据块多副本（常为 3）或纠删码写入管线顺序传递管线上的副本依次确认跨集群复制 / 版本控制 / 跨区域复制
怎么读这张表：先看“冗余单位”判断它能扛几个节点挂；再看“确认语义”判断 RPO；最后一定要看“历史与备份手段”——前三列都挡不住一次误删。

🌍跨地域：把副本放到另一个故障域

同城多机房、两地三中心、异地多活……名字很多，选择只有两个维度：是否同步和备端是否接流量。

同城双活 / 多 AZ

距离近、延迟可控，可以做到同步或准同步复制，RPO 很低；代价是写延迟受网络往返影响，且仍扛不住整个地域级别的事件。

异地异步 / 主备

跨地域几乎都用异步复制（Kafka 的 MirrorMaker 2、ES 的跨集群复制 CCR、MySQL 的跨地域主从）。RPO 等于复制延迟，切换需要人工或编排介入，还要处理消费位点/GTID 的对齐。

同步的代价

跨地域同步写入会把一次往返延迟（几十到上百毫秒）压进每条写路径，尾延迟和可用性都会恶化；因此只有极少数“RPO 必须为 0”的场景才值得。

位点对齐是被低估的难点

MQ 切过去要对齐消费位点，数据库要对齐 GTID / 日志位置。切错位点会造成重复消费或漏消费，比切换动作本身更容易出错。

备份也要异地

如果备份文件仍放在生产机房，地域级故障时会和线上数据一起丢失。至少保一份跨地域、且不可被生产流程直接删除的副本（不可变存储 / 独立账号）。

🧭设计检查表：照着走一遍

新接手一个系统，或者要给它设计冗余方案时，按这个顺序过一遍。

定目标：明确 RPO 与 RTO，以及要扛的故障域是单机、机架、机房还是地域。没有这一步，后面所有选择都没有依据。
选冗余：副本数 + 放置策略（跨机架 / 跨可用区）+ 确认档位。副本数决定能扛几个节点，放置策略决定它们会不会一起挂。
定通道：物理日志、逻辑日志还是快照；同时明确“追赶”和“重建”两条路径分别怎么走、要多久。
补历史：全量备份周期 + 增量日志保留时长，验证能否真正做时间点恢复。
定切换：探测 → 围栏旧主 → 选择最新副本 → 切流 → 重建旧主。任何跳过围栏的切换都有可能脑裂。
演练与观测：监控复制延迟、副本健康度、备份可用性；定期做真实恢复演练，而不只是检查备份“生成成功”。

🚫六个常见反模式

反模式为什么危险应该怎么做
把复制当备份误删、写错代码、数据污染会原样同步到所有副本保留独立备份与时间点恢复能力，副本与备份职责分离
只堆副本数不跨故障域副本全在同一机架/同一可用区，断电或网络故障一起挂显式配置机架感知、可用区分布，并验证放置结果
认为半同步就是 RPO=0ACK 通常只代表对端收到，不代表已持久化或已回放明确 ACK 语义；切换时等待回放或接受补齐窗口
备份从不演练恢复时才发现备份损坏、缺文件、版本不兼容定期做真实恢复演练，并测量实际 RTO
备份与生产同域且可被删除地域故障或勒索攻击时一并丢失异地保存 + 不可变存储/独立权限，保留多个时间点
MQ 只配副本不留重放窗口消费者修好时数据已过期被清理，无历史可补保留期要覆盖“发现故障到修复完成”的窗口；长期归档交给外部存储

⚡速记：三句话 + 五问

三道防线

副本抗硬件坏，备份抗人搞错，容灾抗地方没。三者缺一不可，不能互相替代。

三种范式

日志复制（各自有盘、重放日志）、共享存储（节点无状态、数据在对象存储）、分片加副本（分片管容量、副本管容灾）。

三步加入

一个新副本进来永远是：先快照搬基线，再用增量日志追平，最后保持增量流。

万能五问（对着任何系统都能问）：数据单位是什么 → 冗余单位是什么 → 复制通道传什么 → 何时算写成功 → 历史怎么留、怎么回到过去。把这五问答完，这个系统的备份方案你就讲清楚了。

典型配置速查

Kafka：副本数 3 + min.insync.replicas=2 + acks=all + 关闭 unclean 选主；
ES：主分片数建索引时固定、副本数可随时调整，副本不与主分片同节点；
MySQL：row 格式 binlog + 半同步/组复制 + 全量备份保留 PITR 能力。

面试常问

复制和备份的区别、异步与半同步的 RPO 差异、为什么多数派需要奇数成员、为什么副本不能替代备份、Kafka 如何做到不丢消息、ES 主分片数为什么不能改。

一句话总纲

先看它把什么切成块，再看每块复制几份、靠什么同步、什么时候算成功，最后问昨天的那份还在不在。
