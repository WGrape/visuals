📐 表/模式设计

列族、版本、TTL、压缩与建表清单

列族设计

  • 列族数量要少（通常 2~3 个）。每个列族有独立的 MemStore、HFile 与刷写节奏；列族多 → 内存/IO 放大。
  • 把访问模式不同的列分开：热数据一个列族、冷数据一个列族（可分别设不同 TTL/压缩）。
  • 列族名尽量短（会拼进每个 cell 的 key 里，影响存储）。

列 / 限定符设计

  • 限定符可以很动态、很多（无需建表声明），适合「属性名不固定」的场景（如标签、特征）。
  • 但不要把本该是 rowkey 维度的值塞进限定符——限限定符不参与前缀扫描优化。

版本与 TTL

属性含义建议
VERSIONS每个 cell 保留的历史版本数默认 1；需要「取历史值」时设 2~N，但别太大
TTL数据存活时间，过期在 Compaction 中清除日志/时序类可设几天~几十天，省空间
MIN_VERSIONS即便过 TTL 也至少保留的版本数配合 TTL 保留基线版本

压缩与块

  • 压缩：列族级，推荐 SNAPPY 或 LZ4（速度快、压缩比好）；ZSTD 压缩比更高、CPU 略多。能显著省 HDFS 空间与 IO。
  • BLOCKSIZE：HFile 数据块大小，随机读小一点（如 8~16KB），顺序扫描大一点（如 64KB）。
  • Bloom 类型：ROW（按 rowkey 过滤，最常用）或 ROWCOL（按 rowkey+列 过滤，更精细但更占空间）。

建表清单（Checklist）

  1. 列族控制在 2~3 个，按访问模式拆分；
  2. 规划好 rowkey（参考行键设计篇）；
  3. 建表时做预分区，给定 split keys；
  4. 设好 VERSIONS / TTL / 压缩 / Bloom；
  5. 估算 Region 大小与数量，避免初期单 Region 或过多小 Region。
create 'user_profile',
  {NAME => 'base', VERSIONS => 1, TTL => '30D', COMPRESSION => 'SNAPPY', BLOOMFILTER => 'ROW', BLOCKSIZE => '16384'},
  {NAME => 'tags', VERSIONS => 3, TTL => '90D', COMPRESSION => 'LZ4'},
  {SPLITS => ['2','4','6','8']}
💡 表结构一旦建好，列族不能轻易增减（需 disable 表，较重）。所以列族设计要提前规划；而限定符可随时动态加。
