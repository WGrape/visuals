Qdrant 过滤向量检索：Payload 索引与召回取舍

把“语义相近”和“满足业务条件”同时纳入查询，检查过滤选择率、延迟与召回。

向量相似度之外还有业务约束

文档检索常要求“只在当前租户、可见权限、指定语言或时间范围内找最相近结果”。在 Qdrant 中，一个 point 关联向量与 payload；payload 过滤表达结构化条件，向量索引负责近似邻居搜索。若先在全库取前 10 个近邻，再把其他租户的数据过滤掉，可能只剩一两个结果，甚至漏掉符合条件的真正最佳邻居。权限条件也不能只在最终页面隐藏，查询和结果访问都要严格执行。

过滤条件的选择率会改变最优执行路径：高选择率可在较大候选集合中做 ANN，极低选择率时可能先缩小候选再精确计算更合适。具体策略由版本、payload 索引、向量索引和查询规划决定，不能假定“建了 HNSW 后所有过滤查询都一样快”。应以真实租户规模和过滤组合测延迟与召回。

逐步推演

定义可见集合

明确租户、权限、语言和时间等硬过滤条件。

建立候选

让过滤参与检索规划，而非只在全局 topK 之后删除。

向量排序

在允许的候选集合中寻找相近点并返回前 K。

验证结果

以精确搜索作参照，比较召回、延迟和权限隔离。

一个多租户检索例子

用户 A 问“上季度续约条款”，检索必须同时满足 tenant=A、access=allowed、language=zh，然后按向量相似度排序。若 A 只有全库 0.1% 的文档，全局近邻前 100 名里可能几乎没有 A 的文档。先取全局前 100 再过滤，不等价于在 A 的可见集合里找前 10。正确查询应把过滤条件纳入检索过程，并在应用层复核权限。

路径优点风险
全局 ANN 后过滤实现直观稀有过滤条件下召回不足
先过滤再精确算距离候选很少时结果完整候选很多时成本可能高
索引辅助过滤 ANN平衡候选缩小与近似搜索依赖 payload 索引与规划效果

Payload 索引该建在哪里

常用等值、范围或地理过滤字段可以按 Qdrant 支持的类型建立 payload 索引，让规划器更快判断符合条件的点数。并非所有字段都值得索引：索引会占用存储和内存，也带来更新成本。先分析线上查询里真正高频的过滤字段和组合，再为它们建立索引。tenant_id、时间、状态等字段要保证写入类型一致，否则字符串“10”与数值 10 可能产生不同过滤结果。

向量更新、payload 更新和删除也会影响索引与搜索可见性。批量导入后立刻查询，需按一致性与等待参数确认数据是否已经可检索；不同部署与版本细节应以当前文档为准。应用侧应把权限过滤视为必要的安全约束，即便向量检索返回异常，也不能把未经授权的 point 直接送给模型。

怎样测过滤召回率

  1. 从真实查询中抽取宽过滤、窄过滤和多条件组合样本，记录各自候选集合大小。
  2. 对小样本使用精确搜索作为参考结果，比较 ANN 返回的前 K 命中率与排序差异。
  3. 同时测 P50/P95 延迟、payload 索引内存和更新吞吐，不能只看单次搜索速度。
  4. 为租户隔离准备负向测试：跨租户 point 即使向量极相近，也不得进入候选和最终上下文。

练习：全库一百万文档，租户 A 有 300 篇，查询先取全局最近 50 篇再做 tenant 过滤。解释为什么可能返回 0 条，并给出一个精确参考实验来量化漏召回。

权限过滤不能只靠召回模型

相似度模型学习的是语义距离，并不知道用户能否查看一份文档。权限必须作为硬条件，在查询请求中带上当前租户和访问范围；应用收到结果后还应按权威权限源复核，防止索引更新延迟或配置错误泄漏数据。把权限信息仅写进文档正文、期待向量模型“理解不能返回”，不是访问控制。

衡量过滤效果时同时记录候选集大小。一个 tenant 有 10 篇文档，精确扫描可能已经足够快；另一个 tenant 有千万篇，则需要索引和 ANN 协同。若只在平均租户上压测，会低估最小租户的漏召回和最大租户的扫描压力。建立宽、中、窄三档过滤样本，并为每档报告 Recall@K、P95 延迟、索引内存和更新后的可见性延迟，才能做可靠选型。

结果解释

在小候选集合中，相似度分数的差异可能很小。应用不应把第一个结果直接当成事实；仍需展示来源、更新时间和权限范围，并在生成回答时保留可核对引用。过滤决定“能看什么”，向量排序决定“先看什么”，职责必须分清。

过滤与向量检索的三种结合方式

方式做法召回质量适用场景
后置过滤先 ANN 取 top-k×N 再过滤高（不损失召回）过滤比例 < 50%，最常用
前置过滤先按条件筛出候选集再检索取决于候选集是否覆盖过滤极严（< 5%）
混合/图内过滤HNSW 遍历时跳过不匹配点中等，可能漏过滤比例 50%~95%

核心矛盾：过滤比例越高，ANN 图遍历越容易被“截断”——HNSW 沿边走时遇到大量不匹配节点，提前耗尽候选队列，导致召回率断崖下跌。这是纯向量库做过滤检索的最大陷阱。

带过滤的检索

from qdrant_client import QdrantClient, models

client = QdrantClient("localhost", port=6333)

# 关键参数：hnsw_ef 决定候选队列宽度，过滤越严越要调大
client.search(
    collection_name="docs",
    query_vector=vec,
    query_filter=models.Filter(
        must=[models.FieldCondition(key="tenant_id",
              match=models.MatchValue(value="t_001"))]
    ),
    limit=10,
    search_params=models.SearchParams(hnsw_ef=512),  # 默认 128，严过滤时提到 256~1024
)

payload 索引：过滤性能的分水岭

不过滤的 payload 字段会逐条反序列化比对，在百万级上是秒级；建索引后降到毫秒级。

字段类型应建索引类型说明
精确值（字符串/ID）keyword等值匹配，最常用
整数/浮点数integer / float支持范围查询
布尔bool开销极小
地理位置geo支持半径/多边形
数组/多值keyword（自动多值）任一命中即算匹配
全文text分词匹配，慎用（开销大）

建索引

# 创建 payload 索引（必须先建，否则过滤走全扫）
client.create_payload_index("docs", "tenant_id",
                            field_schema=models.PayloadSchemaType.KEYWORD)
client.create_payload_index("docs", "created_at",
                            field_schema=models.PayloadSchemaType.INTEGER)

# 验证：查看集合信息里的 indexed_vectors_count 与 segments
info = client.get_collection("docs")
print(info.payload_schema)      # 确认索引已建立

# 常见坑：先写入再建索引是允许的，但建索引期间会锁段，
# 大集合建议在业务低峰执行，或一开始就规划好字段

判据：凡是出现在过滤条件里的字段都必须建索引。宁可多建——keyword 索引的内存开销远小于一次全表扫描的代价。

召回率实测与调优

召回率测量

# 用暴力检索当真值，测 ANN+过滤的真实召回率
def recall_at_k(client, vec, flt, k=10, ef=128):
    truth = client.search("docs", vec, query_filter=flt, limit=k,
                          search_params=models.SearchParams(exact=True))  # 暴力
    ann = client.search("docs", vec, query_filter=flt, limit=k,
                        search_params=models.SearchParams(hnsw_ef=ef))
    t = {str(p.id) for p in truth}
    a = {str(p.id) for p in ann}
    return len(t & a) / len(t)

# 扫不同 ef 找拐点
for ef in [64, 128, 256, 512, 1024]:
    print(ef, round(recall_at_k(client, vec, flt, 10, ef), 3),
          client.search.__name__)   # 实际要额外计时
过滤比例建议 hnsw_ef预期召回
< 20%128（默认）> 0.95
20%~50%256> 0.95
50%~80%5120.90~0.95
> 80%1024+ 或改用前置过滤需实测，可能仍偏低

ef 与延迟是线性关系：ef 翻倍，检索耗时近似翻倍。所以调优目标是找到满足召回要求的最小 ef，而不是一味调大。

自检 Q&A

Q：为什么加了过滤后召回率突然掉到 60%？

A：HNSW 图遍历时，大量邻居被过滤条件排除，候选队列提前耗尽，搜索被困在局部区域。三个递进的处理办法——① 调大 hnsw_ef（最直接）；② 提高 m（图连接度，需重建索引）；③ 过滤极严时改用前置过滤 + 暴力：先按条件筛出小候选集，再在小集合上精确检索。

Q：payload 存多大合适？

A：payload 默认存磁盘但过滤时会被读入内存，过大会拖慢检索。经验是单条 payload 控制在几 KB 内，且不要把长文本原文塞进 payload——只存用于过滤的字段和少量展示字段，原文留在主库用 ID 关联。

Q：多租户场景怎么隔离最干净？

A：两种方案。按租户分 collection：隔离彻底、过滤零开销，但租户多时 collection 数量爆炸，每个都有最小内存开销。单 collection + tenant_id 过滤：运维简单，但必须建 keyword 索引且调大 ef。判据是租户数量与单租户数据量——租户少且每户数据大 → 分 collection；租户多且每户数据小 → 单 collection + 过滤。

Q：exact=True 和 ANN 结果不一致，能信哪个？

A：exact=True 是暴力全扫，结果就是真值，用它做基准测召回是对的。但它不适合线上（O(n) 复杂度）。若两者差距过大（召回 < 0.9），说明 ANN 参数需要调，或者数据分布/维度有问题（高维且聚类明显时 HNSW 表现会下降）。

自检

“先取全局 topK，再过滤”与“过滤后取 topK”是否等价？

通常不等价。符合条件的近邻可能排在全局 topK 之外。

为什么 payload 索引不是越多越好？

索引占用资源并增加更新成本，应服务真实高频过滤条件。
