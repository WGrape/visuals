一句话总结：PD 持续把 Region 副本在 TiKV 节点间搬来搬去以实现均衡与容灾——但"搬数据"要占用网络和 IO，必须限速，否则会拖累在线查询。

01为什么需要再平衡

  • 扩缩容：加节点要把数据迁过去，减节点要把数据迁走。
  • 容量/负载不均：某些 TiKV 磁盘或 CPU 更满。
  • 热点：某个 Region 读写过高，需分散到不同节点/Leader。
  • 容灾：保证每个 Region 的多个副本不落在同一故障域。

02PD 的调度维度

调度类型目标
Region 均衡各 TiKV 上的 Region 副本数量大致相等
Leader 均衡读写 Leader 尽量分散，避免单节点成为读热点
热点调度对高读写 Region 做分割、迁移或 Leader 转移
故障/隔离节点下线、Label 约束的副本放置

03迁移的本质

一次 Region 迁移是：在目标节点复制一份该 Region 的副本，同步追上增量，再删除源节点上的旧副本。所以迁移期间短暂地"多一份副本"，对空间和 IO 都有瞬时压力。

04迁移的代价

🌐 网络带宽

跨节点拷贝 Region 数据，节点间带宽被占。

💽 目标节点 IO

目标节点写新副本，磁盘与 CPU 受压。

📤 源节点读

源节点要读出待迁移数据，影响自身读写。

因此调度必须限速：控制同时进行的迁移数与单迁移带宽，避免与在线负载争抢。

05热点打散实践

  • 分裂热点 Region：让过大的 Region 按 key 一分为二，分散负载。
  • Leader 转移 / 均衡：把读 Leader 从热节点移到空闲节点。
  • Scatter / 调度过滤：对特定区间打散或暂停某些调度。
  • 写入侧打散：分片键加前缀哈希，从源头避免集中（见分片键设计）。

06运维注意

项建议
迁移并发控制 PD 调度并发与带宽上限，避免高峰期全速
监控关注 Pending / Transfer Leader / 各节点 Region 与 Leader 数差异
Region 数量Region 过多会增加 PD 调度与心跳开销，单 Region 不宜过小
扩容节奏分批上线新节点，让均衡平稳进行，避免一次性大搬移

07常见疑问

扩容真的对在线无感吗？
查询走的是已有副本，所以查询层无感；但数据迁移在后台消耗网络和磁盘 IO，若不限速会与在线负载争抢，需调低调度并发与带宽上限。
为什么 Region 太多反而慢？
每个 Region 都有心跳、调度元信息和 Raft 状态。Region 数量爆炸会让 PD 的元数据与调度压力、TiKV 的 Raft 心跳开销显著上升，反而拖慢整体。
热点只靠 PD 自动调度够吗？
不够。PD 能迁移和均衡，但如果是写入按顺序主键集中在最新区间，根因在分片键。源头打散 + PD 调度双管齐下才有效。

调度限速参数（TiDB 例）

参数/手段作用
store limit限制单 TiKV 的快照/leader 调度速率
replication max-snapshot限制同时进行的 Region 复制数
region-split-limit限制单位时间分裂速度，避免瞬间 Region 爆炸
scatter-range对指定 key 范围做打散调度
为什么"均衡"和"热点"是两件事？

均衡是让 Region/ Leader 数量在节点间大致相等，解决的是"长期容量与负载分布"；热点是某个具体 Region 读写异常高，即使数量均衡也可能存在。均衡不一定消除热点，热点需要额外的分裂、Scatter 或写入侧打散。

深度补充：TiDB 再平衡与迁移代价

第一层 · 概念与判定 TiDB 的数据按 Region（默认 96MB）切分，PD 根据容量与负载把 Region 在 TiKV 节点间调度。判定信号：pd-ctl store 看 leader/region 分布、store size 是否倾斜。

操作量级 / 参数代价
Region 分裂达 96MB 自动分裂几乎无感
Region 迁移默认限速 ~几十 MB/s跨节点网络 IO
Leader 转移毫秒级元数据极轻
热点调度Hot Region 独立策略需识别写入热点

第三层 · 排障与边界

  • 扩容后迟迟不均衡：看 PD 的 scheduler 是否被禁用、region-schedule-limit 是否过小。
  • 迁移打满带宽影响在线：调小 replica-schedule-limit / store limit add。
  • 写入热点集中在单 Region：用 SHARD_ROW_ID_BITS 打散自增 ID。
  • 误删调度器导致倾斜长期不收敛。
第四层 · 原理与取舍

再平衡用“移动 Region 而非移动整库”实现细粒度均衡，代价是迁移期间的跨节点 IO 与短暂副本不一致（靠 Raft 收敛）。延迟换均衡的旋钮是各类 schedule-limit：调大收敛快但抢 IO，调小在线稳但均衡慢。核心权衡是“均衡速度 vs 在线抖动”，大集群应分批限速而非一次性全量调度。

实例与速查：TiDB 调度与热点

# 查看各 store 的 leader/region 分布与容量
pd-ctl store

# 限制 Region 调度速度，避免迁移打满带宽
pd-ctl config set region-schedule-limit 16
pd-ctl config set replica-schedule-limit 8

# 建表时打散自增热点（写入集中在尾部 Region）
CREATE TABLE t (id BIGINT) SHARD_ROW_ID_BITS = 4 PRE_SPLIT_REGIONS = 2;
  • 扩容后不均衡：确认 scheduler 未被禁用、region-schedule-limit 足够。
  • 迁移期跨节点 IO 大：临时下调 replica/region limit 保在线。
  • 写热点：用 SHARD_ROW_ID_BITS 或随机分桶键打散。
FAQ：迁移会弄丢数据吗？

不会。Region 迁移基于 Raft，先在新节点补齐副本并追平日志，再由 Leader 切换、旧副本下线，全程强一致；真正的风险是迁移期间的跨节点带宽占用影响在线读写，所以要用限速旋钮控制节奏。

常见误区与延伸

  • 误区一：扩容后立刻均衡。PD 受 schedule-limit 约束，均衡是渐进的，临时调大限速要记得调回。
  • 误区二：迁移不影响在线。迁移跨节点搬运 Region，带宽打满会抬升读写延迟，必须限速。
  • 延伸：TiDB 的 Region 是调度与复制的最小单位，所有均衡、故障恢复、热点打散都围绕它展开。
  • 延伸：PD 还负责时间戳（TSO）分配，它是集群的“全局时钟”，PD Leader 切换会短暂影响事务吞吐。

一句话总结：再平衡用“移动 Region”换集群均衡，代价是迁移 IO，旋钮是各类 schedule-limit，大集群分批限速优于一次性全量。

决策速记

  • 均衡节奏：PD 受 schedule-limit 约束，渐进均衡，临时调速后调回。
  • 限速：迁移跨节点搬 Region，用 replica/region limit 保在线。
  • 打散热点：写热点用 SHARD_ROW_ID_BITS 或随机分桶键。
  • 别禁调度：scheduler 被禁会导致倾斜长期不收敛。

一句话：再平衡用移动 Region 换均衡，代价是迁移 IO，分批限速优于全量。

横向对比与追问

  • 与 OceanBase 比：TiDB 的再平衡围绕 Region + PD，OB 围绕 Tablet + 每日合并，调度单位不同。
  • 与 Redis Cluster 比：Redis 用槽位（slot）再分片，扩缩容迁移的是槽而非 Region。
  • 追问：为什么迁移要限速？因为搬运 Region 是跨节点 IO，不限速会饿死在线读写。
  • 追问：PD 单点怎么办？PD 本身是多数派（etcd 类）高可用，Leader 切换短暂影响 TSO。

小结：分布式存储的再平衡都是“移动最小单位 + 限速”，差别在最小单位与元数据服务。

速记口诀

口诀：Region 是单位，PD 来调度，迁移要限速，热点靠打散。

  • 再平衡是移动 Region，代价是跨节点 IO。
  • 临时调大 schedule-limit 后记得调回。

先记三件事

  • 第一件：TiDB 再平衡以 Region 为最小单位，由 PD 调度。
  • 第二件：迁移是跨节点 IO，必须用 schedule-limit 限速护在线。
  • 第三件：写热点用 SHARD_ROW_ID_BITS 或随机分桶键打散。
