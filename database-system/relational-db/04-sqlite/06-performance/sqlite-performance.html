事务批量写、WAL、索引、预编译语句、PRAGMA 调优等实践要点。

① 事务：最大的性能杠杆

SQLite 中每条 DML 语句默认是一个独立事务，而每个事务提交都要fsync（确保持久）。因此插入 1 万条会产生 1 万次 fsync——极慢。把它们包进一个事务是最大的提速手段。

-- 慢：每条语句一个事务（10000 次 fsync）
for i in range(10000): conn.execute("INSERT INTO t VALUES (?)", (i,))

# 快：显式事务（1 次 fsync）
import sqlite3
conn = sqlite3.connect('app.db')
conn.execute("PRAGMA journal_mode=WAL")
with conn:                                  # 自动 commit
    for i in range(10000):
        conn.execute("INSERT INTO t VALUES (?)", (i,))
# 实测差距可达 100 倍以上
WAL 模式（强烈建议开启）：PRAGMA journal_mode=WAL; 把回滚日志改成写前日志：读不阻塞写、写不阻塞读，且提交时只需一次追加写。代价：多出 -wal 文件、需要定期 checkpoint、网络文件系统上不支持。

② 关键 PRAGMA 调优

PRAGMA建议值作用权衡
journal_modeWAL读写并发、提交更快需定期 checkpoint；不支持网络文件系统
synchronousNORMAL（WAL 下）控制 fsync 频率OFF/FULL：OFF 掉电可能损坏；FULL 最安全但慢
cache_size-65536（64MB）页缓存大小（负值为 KB）越大越占内存
temp_storeMEMORY临时表/排序放内存大排序会吃内存
mmap_size268435456（256MB）内存映射读文件减少拷贝，但占用地址空间
page_size4096 或 8192页大小（建库前设置）大页利于大 BLOB 与扫描；小页利于随机读写
foreign_keysON启用外键（默认关闭！）略慢，但保证一致性
busy_timeout5000遇到锁时等待毫秒数避免立刻报 database is locked
-- 建库后立即设置（page_size 必须在创建任何表之前）
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA cache_size = -65536;      -- 64MB
PRAGMA temp_store = MEMORY;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;

③ 批量导入加速

-- 导入优化的「组合拳」
PRAGMA journal_mode = OFF;        -- 或 MEMORY（导入期间可不记日志）
PRAGMA synchronous = OFF;
PRAGMA cache_size = -262144;      -- 256MB
PRAGMA temp_store = MEMORY;

BEGIN;
-- 用预处理语句 + 批量参数
INSERT INTO t VALUES (?, ?, ?);   -- executemany 批量绑定
COMMIT;

-- 导入完成后恢复
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
ANALYZE;                          -- 别忘了更新统计信息！

④ 并发与锁

SQLite 的锁是库级的：写操作需要独占整个数据库文件。因此写并发为 1——这是它的设计取舍（换取零配置与单个文件）。

模式写时能否读写时能否写
rollback journal（默认）❌ 读写互斥❌
WAL✅ 读不阻塞写❌ 写仍串行
-- 应对 "database is locked"
PRAGMA busy_timeout = 5000;      -- 等 5 秒而不是立刻报错

-- 应用层最佳实践
-- ① 写操作加全局锁/队列，串行化
-- ② 缩短写事务（不要在事务里做耗时计算或网络请求）
-- ③ 用连接池，控制并发写
-- ④ 读多写少场景：WAL + 多个只读连接
-- ⑤ 写压力大时考虑分库（按业务拆成多个 .db 文件）
典型死锁场景：在事务中执行了耗时操作（HTTP 请求、大量计算），导致写锁长时间持有，其他连接全部阻塞并报 database is locked。原则：事务要「短」——只在事务里做数据库操作。

⑤ 常见问法

Q：为什么 SQLite 插入很慢？怎么提速？

A：最常见原因是每条 INSERT 都在独立事务里，而每次提交都要 fsync，1 万条就是 1 万次 fsync。提速组合拳：① 把批量插入包进一个显式事务（效果最显著，可达百倍）；② 开启 WAL 模式；③ 用预处理语句 + executemany；④ 大量导入时先插数据、后建索引；⑤ 导入期间临时关闭 journal/synchronous，结束后恢复并 ANALYZE。注意：不要为了提速而长期关闭 synchronous（OFF 会在掉电时损坏数据库）。

Q：WAL 模式有什么好处？有什么代价？

A：好处：① 读不阻塞写、写不阻塞读（默认 rollback journal 模式下读写互斥）；② 提交更快——只需向 WAL 文件追加，不必写回滚日志并多次 fsync；③ 并发性显著提升。代价：① 多出 -wal 与 -shm 文件，不能只拷贝 .db 文件做备份（要 VACUUM INTO 或 sqlite3 的 backup API）；② WAL 文件会增长，需要 checkpoint 回收（默认自动，1000 页触发）；③ 不支持网络文件系统（NFS/SMB 上锁语义不可靠）；④ 写仍然串行（库级写锁）。结论：单机应用强烈建议开启 WAL。

Q：synchronous 各档位怎么选？

A：FULL：每次提交都 fsync，最安全，掉电不丢已提交数据，但最慢；NORMAL：在 WAL 模式下检查点时才 fsync，推荐与 WAL 搭配——正常关机/进程崩溃不丢，但操作系统崩溃或掉电可能丢失最近几个事务；OFF：完全不 fsync，最快，但掉电或系统崩溃可能损坏数据库文件（不只是丢数据）。建议：生产用 WAL + NORMAL；只有可重建的导入过程才临时用 OFF，并务必恢复。

Q：遇到 database is locked 怎么办？

A：它表示写锁冲突（SQLite 的写锁是库级独占的）。解决：① 设置 PRAGMA busy_timeout = 5000（等 5 秒而不是立刻报错）——这是最基本的防护；② 缩短写事务，绝不在事务里做网络请求或耗时计算；③ 应用层把写操作串行化（单写者队列）；④ 开启 WAL 让读不被阻塞；⑤ 写压力大时拆分数据库文件（按业务分库）。注意：busy_timeout 对「死锁」无效（如同一连接内嵌套写事务），那种情况要改代码结构。

Q：SQLite 能支撑多大的数据量与并发？

A：数据量：理论上限约 281TB（默认页大小下），实践中几十 GB 的单文件都很常见，性能与运维成本在 GB 级以内最舒适；超过几十 GB 后备份、VACUUM、恢复都会变慢。并发：读可并发（WAL 下数千读连接可行），写严格串行（库级写锁）。因此它适合读多写少、单写者的场景：移动 App、桌面软件、嵌入式设备、边缘缓存、小型 Web 应用（几百 QPS 写入以内）。不适合：高并发写入、多机共享（网络文件系统上锁不可靠）、需要横向扩展的场景——这时应选 PostgreSQL/MySQL。

Q：VACUUM 是什么？什么时候需要？

A：删除/更新数据后，SQLite 默认不会把空闲页还给文件系统（只是标记为可复用，存在 freelist 中）。VACUUM 会重建整个数据库文件，回收空闲空间、整理碎片、并可能减小文件大小。何时需要：① 大量删除后文件仍很大；② 想减小文件便于分发/备份；③ 长期大量写入后碎片化严重。代价：需要约一倍的磁盘空间并全程加锁（阻塞读写）。替代：VACUUM INTO 'new.db'（3.27+）可在线生成整理后的副本而不阻塞原库；开启 PRAGMA auto_vacuum=INCREMENTAL 可做增量回收（但会增加写入开销）。

第一层 · 先判断瓶颈在哪

现象最可能的原因验证方法
写入很慢（每条都要等）每条语句一个事务，各自等 fsync把批量写包进一个事务，看是否快一个数量级
读多写少但读也慢缺索引，走了全表扫描EXPLAIN QUERY PLAN 看是否 SCAN
并发写互相阻塞写锁是库级的，写会阻塞所有其他读写开 WAL 模式；长的写事务拆小
数据库文件很大、查询变慢碎片 + 统计信息过期跑 VACUUM 和 ANALYZE
启动/连接慢每次都重新打开并做完整性检查复用连接，别反复开关

SQLite 的性能问题八成是事务粒度问题，不是 SQL 写得不好。因为默认每条语句都独立成事务，而每个事务提交都要等一次磁盘 fsync——机械盘上一次 fsync 可能是毫秒级，几千条就是几秒。

第二层 · 五个立竿见影的配置与写法

-- ① WAL 模式：读写不再互相阻塞（最关键的一项）
PRAGMA journal_mode = WAL;          -- 写进 WAL 文件，读仍读主库
PRAGMA synchronous = NORMAL;        -- WAL 下 NORMAL 已足够安全，比 FULL 快很多

-- ② 批量写必须包进一个事务（差距可达几十倍）
BEGIN;
INSERT INTO events(ts, uid, amount) VALUES (?, ?, ?);
-- ... 重复上千条 ...
COMMIT;                             -- 只在 COMMIT 时 fsync 一次

-- ③ 索引：看执行计划确认有没有用上
EXPLAIN QUERY PLAN SELECT * FROM events WHERE uid = 1001;
--   出现 "SCAN events"       → 全表扫描，需要建索引
--   出现 "SEARCH ... USING INDEX" → 用上了索引
CREATE INDEX idx_events_uid ON events(uid);

-- ④ 统计信息：优化器靠它估算代价，数据大变后要刷新
ANALYZE;

-- ⑤ 内存与临时文件（按需调整，值需按机器内存定）
PRAGMA cache_size = -16000;         -- 负数表示 KB，这里约 16MB
PRAGMA temp_store = MEMORY;         -- 临时表/排序放内存
PRAGMA作用注意
journal_mode = WAL读写并发，写不阻塞读会产生 -wal / -shm 文件；需要文件系统支持共享内存
synchronous控制 fsync 时机OFF 有丢数据风险；WAL 下 NORMAL 是常见选择
cache_size页缓存大小负值单位是 KB
temp_store临时数据放内存还是磁盘MEMORY 快但吃内存
busy_timeout遇到锁时等多久再报错并发写必设，否则频繁 SQLITE_BUSY

WAL 是最值得先做的一项：它把「写阻塞读」变成「读写并发」，代价只是多两个文件。绝大多数并发问题开 WAL 就缓解了。

第三层 · 排障清单与常见错误

  • SQLITE_BUSY 频繁：没设 busy_timeout，或写事务太长。设超时 + 拆小事务。
  • 写入只有几百 TPS：几乎一定是没用事务批量。包进事务后通常能上万。
  • 索引建了没生效：查询条件上对列做了函数或类型转换；或者统计信息过期（跑 ANALYZE）。
  • 复合索引顺序错：遵循等值在前、范围在后；(a, b) 能优化 a=? AND b>?，反过来不行。
  • SELECT COUNT(*) 很慢：SQLite 没有计数缓存，大表 count 必须扫索引。需要精确值就接受这个代价，或自己维护计数表。
  • 文件只增不减：删数据不会缩小文件，需要 VACUUM（会重写整个库，要额外磁盘空间）。
  • 跨进程并发写：SQLite 写锁是库级的，多进程同时写必然串行。高并发写场景应换客户端/服务器型数据库。
-- 定位慢查询：先看执行计划，再看索引与统计
EXPLAIN QUERY PLAN
SELECT e.* FROM events e JOIN users u ON e.uid = u.id
WHERE e.ts > '2026-10-01' AND u.city = 'bj';
--   关注：SCAN（全表扫）出现在哪张表 → 那张表缺索引
--   关注：join 顺序是否符合「小表驱动大表」

-- 看库的实际状态
PRAGMA database_list;
PRAGMA index_list('events');         -- 有哪些索引
PRAGMA index_info('idx_events_uid'); -- 索引包含哪些列、顺序
PRAGMA page_count;                   -- 页数（估算体积）
PRAGMA freelist_count;               -- 空闲页（多 → 该 VACUUM）

-- 慢查询计时（命令行）
sqlite3 app.db ".timer on" "SELECT ..."

-- 完整性检查（性能突然变差时先排除损坏）
PRAGMA integrity_check;

第四层 · 什么时候不该用 SQLite

场景SQLite 是否合适原因
单机应用、移动端、嵌入式非常合适零配置、无网络开销
读多写少的小中型站点合适配合 WAL 够用
单机缓存 / 本地分析非常合适比文件读写强得多
高并发写（多进程同时写）不合适写锁是库级的，必然串行
数据量超过单机存储不合适没有分片能力
需要网络访问 / 多机共享不合适它是库文件不是服务

SQLite 的定位是「嵌入式的、零运维的库」，不是「小型的数据库服务器」。它的性能上限很高（在合适的用法下能到上万 TPS），但并发写模型决定了它不适合多写者场景。判断标准就一句：会不会有多个进程同时写？

为什么开了 WAL 写入还是慢？

先确认有没有用事务批量。WAL 解决的是读写并发，不解决 fsync 次数。每条 INSERT 一个事务的话，fsync 次数没变，速度不会改善。

synchronous 设成 OFF 安全吗？

不安全。断电或崩溃时可能丢失最近提交的事务，甚至损坏数据库。想要性能又想安全，用 WAL + NORMAL，这是最常见的组合。

索引是不是越多越好？

不是。每个索引都会拖慢写入（每次 INSERT 都要更新所有索引），也占空间。只在真正被查询条件用到的列上建，并定期检查有没有从未被使用的索引。

VACUUM 能经常跑吗？

它会重写整个数据库文件，期间需要额外磁盘空间并持有锁。建议在低峰手动触发，或用 auto_vacuum 让空间逐步回收（但会带来额外碎片整理开销）。
