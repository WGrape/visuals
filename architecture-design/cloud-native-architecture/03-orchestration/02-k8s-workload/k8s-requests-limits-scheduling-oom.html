Kubernetes requests 与 limits：能调度为什么还会 OOMKilled

用两台 4 Gi 节点和三个 Pod 手算放置，再区分 CPU 限流、内存 OOM 与节点驱逐。

requests 和 limits 管不同问题

Pod 的资源 requests 告诉调度器预计至少需要多少 CPU、内存；调度时，节点现有请求量加上新 Pod 的请求量不能超过可分配资源。limits 是容器运行时的上限约束：CPU 超额通常被限速，内存超过限制可能触发 OOM 杀死容器。节点的 allocatable 小于物理总量，因为系统与 Kubernetes 组件也要留资源。不能把“节点有 4 Gi 物理内存”直接当成可供所有 Pod 请求的 4 Gi。

requests 不是预先划出完全独占的物理内存。节点可以按请求量安排多个 Pod，而它们的实际内存使用可能同时超过请求；若实际总量逼近节点可用内存，还可能发生节点内存压力和驱逐。容器 limits 与节点整体容量是两道不同边界。

手算三只 Pod 的放置

假设一台节点的可分配内存恰好 4 Gi，已有两个 Pod，各请求 1.5 Gi、限制 3 Gi。调度器看到请求总量 3 Gi，仍剩 1 Gi；第三只也请求 1.5 Gi 的 Pod 不能放在该节点，因为 3+1.5=4.5 Gi 超过 4 Gi，尽管当前实际使用可能只有 2 Gi。若有第二台空闲节点，第三只可放到第二台，前提是其他约束也满足。

前两只 Pod 同时实际使用 2.8 Gi，各自都低于 3 Gi limit，却合计 5.6 Gi，超过节点可用量，可能造成节点级内存压力。limits 合计可以高于节点容量，调度器主要按 requests 做放置。要避免高峰一起增长时拥挤，需要以真实峰值和安全余量设请求、合理控制 limits，并观察节点内存压力。

CPU 和内存超限表现不同

CPU 是可压缩资源：达到 CPU limit 后，容器通常被 CFS 配额等机制限制运行时间，表现为延迟上升和 CPU throttling，而不是因 CPU 用得多就被 OOM 杀死。内存不可像 CPU 那样暂缓使用；容器达到其内存限制时可能被 OOM killer 杀死，Pod 状态中出现 OOMKilled，随后按重启策略重启。进程内存泄漏、缓存无界、突发批处理与 JVM 堆外内存都可能触发。

若节点整体内存紧张，kubelet 的驱逐与容器级内存 limit OOM 是不同事件。排查时看 Pod 的 lastState、事件、节点 MemoryPressure、容器内存工作集、OOM 次数及同节点其他 Pod，而不是只看到重启就提高 limit。提高 limit 可能把风险推给整台节点。

现象常见原因优先观察
Pending请求放不下或约束不匹配调度事件
延迟高且 CPU 满CPU limit 限速throttling 指标
OOMKilled容器内存超限lastState 与峰值
Evicted节点资源压力Node condition 与事件

QoS 分类不能当作万能保护

Kubernetes 常见 QoS 类别有 Guaranteed、Burstable 与 BestEffort。容器对 CPU 和内存都设置相等的 request/limit，且 Pod 内各容器满足条件时，通常归 Guaranteed；设置部分请求或上下限不同常属于 Burstable；完全不设相关资源请求限制则可能是 BestEffort。QoS 会影响内存压力时的驱逐排序，但 Pod 优先级、超出请求量和节点状态也参与决策，不能承诺 Guaranteed 永远不会被终止。

一个 Pod 里的 sidecar 也要计入资源，调度器按 Pod 内容器的有效请求量计算。只给主容器设置预算、忘了日志或代理 sidecar，会让实际占用与请求不符。init container 的资源计算也有特定规则，需按 Pod 资源模型核对。

如何设初值与复核

从监控中拿 CPU 使用分位数、内存工作集峰值、GC/堆外占用和启动峰值。requests 需要支撑常态性能与可靠调度，limits 要防止失控消耗同时不截断合法峰值。CPU limit 设得太紧会导致频繁 throttling，即便节点还有空闲 CPU；内存 limit 设得太松可能导致节点风险。没有单一比例适用于所有服务。开发、压测与生产流量形态不同，应以实际工作负载校准。

发布后同时看 Pending 的调度事件、CPU throttling、OOMKilled、节点驱逐和 HPA 扩容行为。HPA 若按 CPU 利用率相对 request 计算，request 改动会影响扩容信号；调资源不是纯容量改动，也可能改变自动扩容动作。

一次事故的追踪顺序

若新 Pod 一直 Pending，先看调度器事件是否提示 Insufficient memory、节点污点、亲和性或 PVC 约束；若已运行后 OOMKilled，看容器内存 limit 与峰值；若延迟飙高但未 OOM，看 CPU throttling 与排队；若多个 Pod 同时被驱逐，看节点 MemoryPressure。将“放不下”“跑太慢”“容器被杀”“节点驱逐”分开处理，比一律加节点有效。

requests / limits 与 QoS 等级

QoS 等级条件调度依据资源紧张时
Guaranteed所有容器的 CPU/内存 requests == limits 且都设置按 requests 预留最后被驱逐（OOM 评分最低）
Burstable至少一个容器设置了 requests 或 limits，且不满足 Guaranteed按 requests 预留中间优先级
BestEffort未设置任何 requests/limits不预留最先被驱逐
字段作用不设的后果
requests.cpu调度器据此选节点（可预留）按 0 计算，可能被塞到满节点
limits.cpuCFS 配额上限（默认周期 100ms）不限，但可被节流影响邻居
requests.memory调度预留 + OOM 评分依据不预留，OOM 时优先被杀
limits.memory超过即 OOMKilled可吃满节点内存，触发节点级驱逐

CPU 是可压缩资源：超过 limit 只会节流（throttling），容器变慢但不死；内存是不可压缩资源：超过 limit 直接 OOMKilled。这是两类资源行为差异的根本。

OOM 评分与驱逐顺序

因素规则数值
OOM 评分范围-1000（最不会被杀）到 1000（最容易被杀）Guaranteed 常被设为 -998
评分计算基于内存 requests 占节点可分配内存的比例占比越高越容易被杀
BestEffort评分固定最高最先被杀
驱逐阈值（kubelet 默认硬驱逐）memory.available < 100Mi、nodefs.available < 10%、imagefs.available < 15%触发后按 QoS 顺序驱逐 Pod
软驱逐 + 宽限期可配 eviction-soft 与 eviction-soft-grace-period给应用缓冲时间

设置建议与排障清单

场景建议理由
关键在线服务内存 requests=limits；CPU 只设 requests 或 limit 放宽内存不设 limit 风险大；CPU limit 过严会节流
批处理 / 离线任务低 requests + 高 limits（Burstable）提高装箱率，闲时能用空闲资源
Java / JVM 应用显式设置堆大小（-XX:MaxRAMPercentage=75）避免 JVM 认为可用内存是节点内存而超限被杀
有突发流量的服务CPU limit 至少为 requests 的 2~4 倍给突发留出突发额度
节点稳定性给系统组件预留 kube-reserved / system-reserved避免系统进程与业务争抢资源
  • 不要迷信「不设 limit 更好」：内存不设 limit 会在节点压力时被优先杀；合理做法是设 limit 并留足余量。
  • HPA 与 requests 联动：HPA 的利用率是「实际用量 / requests」，requests 设错会导致扩容阈值失真。
  • limits 之和可以超过节点容量（overcommit），但 requests 之和不能超过——这正是调度与运行时的区别。

深入自检

requests 和 limits 到底差在哪？

requests 是调度依据：调度器累加节点上所有 requests，放不下就不调度；limits 是运行时上限：CPU 超了被 CFS 节流，内存超了被 OOMKilled。requests 之和不能超过节点可分配量，limits 之和可以（超卖）。

为什么 CPU 超限不会杀容器而内存会？

CPU 是可压缩资源：超额时内核只是不给你更多时间片（节流），进程变慢但能继续运行；内存是不可压缩资源：一旦超额，内核只能选择一个进程杀掉来回收内存，所以表现为 OOMKilled（退出码 137）。

Guaranteed 一定不会被 OOM 吗？

不会绝对安全，但在资源紧张时优先级最高：其 OOM 评分最低（如 -998），且只有在 requests==limits 且全部设置时才算 Guaranteed。若节点真的内存耗尽，仍可能因为内核层面 OOM 而被杀，只是排在最末。

为什么 CPU limit 会导致延迟毛刺？

因为 CFS 按 period（默认 100ms）分配配额：配额在一个周期内用尽后，容器会被节流到下一个周期才开始继续运行。表现为请求延迟出现与周期相关的规律性毛刺，指标上 container_cpu_cfs_throttled_seconds_total 持续增长。

JVM 容器里为什么特别容易 OOMKilled？

旧的 JVM（未开启 UseContainerSupport）会按节点内存而非容器 limit 来计算堆大小，于是把堆开到远超 limit，加上堆外内存（元空间、线程栈、DirectBuffer）后超过 limit 被杀。现代 JDK 默认识别 cgroup，但仍建议显式设置 -XX:MaxRAMPercentage（如 75%）给堆外留余量。

自检

两只 Pod 的请求总量是 3 Gi、limits 总量是 6 Gi，调度器主要依据哪个量放置第三只？

主要按 requests 与节点 allocatable 计算；第三只再请求 1.5 Gi 会超过 4 Gi。
