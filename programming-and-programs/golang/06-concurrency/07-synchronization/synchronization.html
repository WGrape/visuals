概述

共享可变状态需要保护

多个 goroutine 同时读写同一变量会出现竞争条件（race condition），结果不可预测。互斥锁是最基础的防线。

sync.Mutex 互斥锁

临界区串行化

进入临界区前 Lock，离开时（通常 defer）Unlock。同一时刻只有一个 goroutine 能持有锁。

var mu sync.Mutex
var balance int

func Deposit(n int) {
    mu.Lock()
    defer mu.Unlock()
    balance += n
}
func Balance() int {
    mu.Lock()
    defer mu.Unlock()
    return balance
}
RWMutex 读写锁

读多写少更高效

多个读可并发（RLock），写独占（Lock）。适合缓存、配置这类读远多于写的场景。

var rw sync.RWMutex
func Get(k string) (string, bool) {
    rw.RLock(); defer rw.RUnlock()
    v, ok := m[k]; return v, ok
}
func Set(k, v string) {
    rw.Lock(); defer rw.Unlock()
    m[k] = v
}
sync.Once 惰性初始化

保证只执行一次

单例、全局连接池等「只初始化一次」的场景用 Once.Do，并发调用也安全且只跑一次。

var once sync.Once
var conn *DB
func GetConn() *DB {
    once.Do(func() { conn = connect() })
    return conn
}
内存同步语义

锁不只是互斥

锁还建立了 happens-before 关系：Unlock 之前的内存写，对后续 Lock 的 goroutine 可见。没有锁，编译器/CPU 的乱序优化会让另一个 goroutine 看到陈旧值。

这正是第 6 章「内存模型」要解决的问题：并发正确性靠同步原语建立的可见性保证，而非运气。
竞争条件检测

-race 帮你抓 bug

Go 内置竞态检测器：go test -race / go run -race。它能在测试/运行中报告对共享变量的并发读写冲突。

⚠️ -race 有性能/内存开销，仅用于测试环境；上线构建一般不开。但它抓出的 race 是真实 bug，必须修。
sync.Cond 条件变量

等待某个条件成立

需要「等某条件再继续」时，Cond 配合锁比忙等（轮询）高效：Wait 释放锁并阻塞，Signal/Broadcast 唤醒。

Goroutines 和线程

Go 的 goroutine 是用户态轻量线程，由 runtime 调度到 OS 线程上；同步原语工作在 goroutine 语义之上。
