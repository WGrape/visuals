读 config.json 的最小核对脚本

import json, sys c = json.load(open(sys.argv[1] + "/config.json")) need = ["hidden_size", "num_hidden_layers", "num_attention_heads", "num_key_value_heads", "intermediate_size", "hidden_act", "rms_norm_eps", "rope_theta", "vocab_size", "tie_word_embeddings"] for k in need: print(f"{k:28s} {c.get(k, ' <缺失>')}") head_dim = c.get("head_dim", c["hidden_size"] // c["num_attention_heads"]) print(f"{'head_dim(推导)':28s} {head_dim}") print(f"{'KV/层/token(数)':28s} {2 * c['num_key_value_heads'] * head_dim}")

最后一行算出来的数乘上「层数 × 序列 × batch × 字节」就是 KV Cache 的真实大小。做容量规划、判断能不能开 32K 上下文，都用它，而不是猜。

换模型时最容易踩的五个坑

  1. RoPE base 默认 10000：加载器若没读 rope_theta，长文能力会静默消失。先跑 4K→32K 的检索测试。
  2. Qwen 的 qkv bias：从 Llama 系代码迁过来时，attention_bias=false 会让权重加载失败或丢掉 bias。
  3. tie embedding 判定：用 lm_head.weight in state_dict 判断，不要靠模型名猜。
  4. head_dim 不能整除：部分模型的 head_dim 是独立字段（不是 d/h），必须显式读。
  5. 滑动窗口：Mistral 的 4096 窗口意味着超长上下文的 KV 不会线性增长，按线性公式估会高估显存。

原理与取舍：为什么大家都在趋同

十年演化后，decoder-only + Pre-RMSNorm + SwiGLU + RoPE + GQA 已成为事实标准，因为这套组合在「训练稳定性 / 计算效率 / 长文能力」三角上最优。分叉出现在两处：如何省 KV（GQA 用减头、MLA 用低秩）和如何扩大容量而不涨算力（MoE）。看懂这两个分叉，就理解了 2024 年之后所有新模型的结构创新。

为什么不是所有模型都用 MLA？

训练成本高、实现复杂，且与现有推理框架（vLLM/SGLang）的集成需要专门适配；GQA 的实现简单、生态成熟。

MoE 一定比稠密好吗？

在「总参数受限但推理算力敏感」的场景好；但如果显存受限（要装下所有专家），稠密模型反而更划算。

结构差异会影响 tokenizer 吗？

会。词表大小与分词规则不同，同一段文本的 token 数可能差 30%，直接影响成本与上下文可用长度。

第一层 · 概念与判定：现代 LLM 架构的共同底座

先记共同点，再看差异——现代主流 LLM 都是 Decoder-only + RMSNorm + RoPE + SwiGLU，差别主要在注意力与稀疏化上。

组件共同做法为什么
结构Decoder-only自回归生成最简单高效
归一化RMSNorm + Pre-LN比 LayerNorm 更快、训练更稳
位置编码RoPE相对位置 + 可外推
FFNSwiGLU同等参数下效果优于 ReLU/GELU
注意力GQA / MQA / MLA压缩 KV cache，这是各家分歧点
  • 信号一：要在有限显存跑长上下文 → 关注 KV cache 压缩（GQA/MQA/MLA）。
  • 信号二：要在相同算力下训更大模型 → 关注 MoE 稀疏化（DeepSeek）。
  • 信号三：要中文效果好 → Qwen 的中文词表与语料更有优势。

选型提示：这些架构细节对使用方的影响主要体现在「显存占用、推理速度、长上下文能力」上，而不是「能不能用」。

# 从 config 一眼看出架构差异
from transformers import AutoConfig
for name in ("meta-llama/Meta-Llama-3-8B", "Qwen/Qwen2-7B", "deepseek-ai/deepseek-llm-7b-base"):
    c = AutoConfig.from_pretrained(name)
    print(name)
    print("  n_heads:", getattr(c, 'num_attention_heads', None),
          "| kv_heads:", getattr(c, 'num_key_value_heads', None),   # < GQA 关键指标
          "| rope_theta:", getattr(c, 'rope_theta', None),
          "| vocab:", getattr(c, 'vocab_size', None))

# GQA 判断：num_key_value_heads < num_attention_heads 即为 GQA
# 8 heads / 4 kv_heads => 每 2 个 query head 共享一份 K/V，KV cache 减半

# KV cache 显存估算（每 token）
# 2(K,V) * n_layers * n_kv_heads * head_dim * dtype_bytes
# 例：32 层 * 8 kv_heads * 128 dim * 2 bytes * 2 = 128KB / token（粗略量级）

量化参考：GQA 把 KV cache 压缩到 1/(组数)。如 8 个 query head 配 4 个 kv head，KV cache 直接减半——这对长上下文的显存占用是决定性的。

第三层 · 排障与边界：迁移与部署的坑

坑后果正确做法
按 LLaMA 的写法硬套 QwenQKV bias 等细节不同，结果偏差用官方 / HF 的实现，别手写
以为所有模型都支持同样的长上下文超长时效果崩查具体模型的训练长度与 rope_scaling
词表大小搞错导致乱码tokenizer 不匹配必须用配套的 tokenizer
MoE 模型按 dense 估显存严重低估MoE 要算激活参数 + 全部参数的显存
量化后精度骤降某些架构对量化更敏感先小样本验证；用 AWQ/GPTQ 等成熟方案
  • 排查顺序：先看 config 的 kv_heads / 是否 MoE → 再确认 tokenizer 配套 → 再估显存 → 最后做量化验证。
  • 边界一：MoE 模型的显存要装下全部专家参数，但每个 token 只激活少数专家——所以「显存按总量算、算力按激活量算」。
  • 边界二：不同厂商的 tokenizer 不能混用，即便都是 BPE。中文场景尤其要注意词表覆盖。
  • 边界三：长上下文的宣称值与实际可用长度常有差距，实测时建议做「针尖检索」测试（把关键信息放在不同位置看能否召回）。

第四层 · 原理与取舍：GQA / MQA / MLA / MoE 的取舍

技术做法收益代价
MHA（原始）每个 head 独立 K/V质量最好KV cache 最大
MQA所有 head 共享一份 K/VKV cache 压缩到 1/n_heads质量损失相对大
GQA分组共享（如 8→4）折中：压缩明显、损失小需调组数
MLA（DeepSeek）低秩压缩 K/V 再还原压缩更强实现复杂
MoE每层多个专家，只激活少数同等算力下参数量更大显存要装全部专家；路由需稳定
GQA 会影响生成质量吗？

影响很小，这是它被广泛采用的原因。实测中从 MHA 换成 GQA（如 8→4 甚至 8→2）在多数基准上损失在个位数百分点以内，却能把 KV cache 减半——在长上下文场景下这个交换非常划算。

MoE 为什么省算力但不省显存？

因为每个 token 只经过少数专家（如 8 选 2），所以前向计算量小；但所有专家的参数都必须常驻显存，因为不同 token 会路由到不同专家。所以「算力按激活算、显存按总量算」。

做应用时该关心这些架构差异吗？

多数情况下不用关心模型结构本身，但要关心它的工程后果：显存占用、推理吞吐、长上下文可用长度、中文/代码能力、许可证。这些才是选型时真正该对比的指标。
