云上部署拓扑与故障域

一套 API 上云之后，先决定实例在哪里、流量怎么进来、故障被限制在哪个可用区；再谈如何发版。

请求路径 副本摆位 故障演练 落地清单

01 / 从一条请求画出部署拓扑

以订单 API 为例：用户访问统一域名，云负载均衡只把请求交给已就绪的应用实例；实例在私有子网中访问托管数据库。DNS 不等于负载均衡，可用区冗余也不等于数据库自动恢复。

  1. 入口DNS 指向公网负载均衡；TLS、WAF 等能力按业务需要放在入口处。
  2. 路由负载均衡跨两个可用区选择健康后端；故障后停止向失效实例转发。
  3. 应用实例放在私网，按可用区分散部署；出站访问依赖显式路由和权限。
  4. 数据应用用私网地址连接数据库；备份、复制和故障切换分别规划。

注意：负载均衡的“健康”可能只是端口可连。就绪检查应验证应用已加载配置并能处理请求，但不能每次都用昂贵的写库操作；存活检查主要判断进程是否需要重启，两者不要混为一谈。

02 / 多可用区要分开考虑应用与数据

应用副本

至少分散到两个 AZ，避免一次可用区故障清空全部实例；容量要预留单 AZ 故障后的承载能力。会话存储和本地文件不能默认随实例迁移。

数据库副本

区分主从复制、跨 AZ 高可用、只读副本和备份。只读副本不一定能自动提升为主库；跨区复制方式决定数据丢失窗口（RPO）。

网络与权限

入口只开放必要端口；应用和数据库分层使用安全组/访问规则。管理入口与业务入口分开，避免把数据库直接暴露到公网。

跨 AZ 既提高可用性，也增加网络延迟与传输费用；批量任务、连接池和数据位置必须一起算。选机型和故障域可继续阅读 地域、可用区与故障域。

03 / 单 AZ 失效时系统怎样退化？

故障点用户看到什么应该验证什么
一个应用实例失效少量请求可能失败；随后流量绕开坏实例探测超时、摘流速度、重试是否造成重复写入
一个 AZ 故障剩余 AZ 流量上升，延迟可能升高剩余副本容量、扩容配额、跨 AZ 数据库切换时间
数据库主库故障写请求暂停；应用连接可能需要重建实际 RTO/RPO、连接重试退避、幂等与超时设置

多 AZ ≠ 零中断。负载均衡摘流、数据库主从切换和应用重新建立连接都需要时间；用演练而非架构图验证恢复目标。

04 / 上线前的最小检查清单

  • 明确峰值流量、可用性目标、允许的数据丢失窗口与恢复时间。
  • 确认应用实例至少跨两个 AZ，故障后剩余容量与自动扩容配额足够。
  • 测通用户入口 → 负载均衡 → 私网实例 → 数据库，并记录端口和权限边界。
  • 分别演练实例摘流、AZ 故障和数据库主库切换，观察真实延迟与错误率。

一句话：部署拓扑定义“故障在哪里停止传播”，发布流程才定义“新版本怎样安全进入拓扑”。
