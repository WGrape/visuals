术语含义常见误解
命中 / 未命中key 存在于缓存并返回 / 不存在需回源把"key 存在但已逻辑过期"当成命中——那是逻辑过期方案，不算真正命中
回源未命中时穿透到数据源查询并回填以为回源只发生在 key 不存在时；key 被淘汰、过期、缓存宕机都会回源
命中率命中次数 / 总查询次数只看比例不看回源绝对量（见「收益与代价」）
TTLTime To Live，写入后经过多久失效与 TTI 混淆
TTITime To Idle，多久没被访问就失效与 TTL 混淆。热点数据用 TTI 可以长期驻留，用 TTL 会被无谓地清掉
淘汰 / 驱逐内存达到上限时按策略移除 key与"过期"混为一谈。过期是时间到了，淘汰是空间不够
穿透查询根本不存在的数据，缓存永远不命中与击穿混淆
击穿单个热点 key 过期瞬间，大量并发同时回源与穿透、雪崩混淆
雪崩大批 key 同时失效或缓存集群整体不可用只理解成"同时过期"，忽略了集群宕机这种更致命的情况
预热上线/大促前主动把数据灌进缓存只预热不校验，结果灌进去的 key 格式和线上读的不一致
大 key / 热 key单 key value 过大 / 单 key 访问量过高以为集群能自动分散——热 key 只会打到一个分片上

🔀 三、最容易混淆的四组概念

① 过期（expire） vs 淘汰（evict）
过期是时间维度——key 到了 TTL 就该失效；淘汰是空间维度——内存满了必须腾地方。 一个 key 可能还没过期就被淘汰（内存不足），也可能过期了还占着空间（没到删除时机）。 配置时要分别设：maxmemory + maxmemory-policy 管淘汰，EXPIRE 管过期。
② 穿透 vs 击穿 vs 雪崩
穿透＝查不存在的数据；击穿＝一个热点 key 刚好过期；雪崩＝一批 key 同时失效或缓存整体挂了。 判断口诀：看"有多少个 key"和"这个 key 到底存不存在"。 详见 缓存异常总览。
③ 本地缓存 vs 分布式缓存
本地缓存快（无网络）但每个实例一份、互不可见、容量受堆限制； 分布式缓存慢一点（一次网络 RTT）但全局一份、容量可独立扩展。 答案通常不是二选一，而是多级（见 多级缓存架构）。
④ 一致性 vs 可用性
缓存只要存在，就必然有"数据源已变、缓存未变"的窗口。 能做的只是缩短窗口（延迟双删、binlog 订阅）或缩小影响面（版本号、短 TTL）， 不可能做到"永远一致"。声称缓存能做到强一致的方案，通常要么没有真正并发写入，要么在某个角落仍有窗口。

🎤 五、面试怎么串起来讲

面试官问"讲讲缓存"，最稳的三段式：

📘
第一段：为什么用。"缓存是用一致性和复杂度换速度。我们先量化了回源成本和命中率，确认划算才上。"
第二段：怎么保证不出事。"三个经典问题：穿透用布隆过滤器和空值缓存，击穿用互斥重建或逻辑过期，雪崩用随机过期时间＋熔断降级。 一致性上我们用的是 Cache-Aside ＋延迟双删。"
第三段：怎么知道它健康。"看命中率、回源量、内存水位三个指标，命中率突降会告警； 另外定期排查大 key 和热 key。"

能主动补一句"缓存宕机时我们会降级成限流直查，避免回源打爆数据库"，基本就是满分答案—— 因为这句话说明你意识到了缓存是放大器而不只是加速器。

层级典型延迟相对倍数说明
CPU 寄存器0.3 ns1×1 个时钟周期
L1 Cache1 ns3×约 32 – 64 KB
L2 Cache4 – 7 ns10×约 256 KB – 1 MB
L3 Cache20 – 40 ns50×多核共享，几 MB 到几十 MB
主存 DRAM80 – 100 ns200×随机访问
NVMe SSD 随机读10 – 100 μs10 万×比内存慢 3 个数量级
机械硬盘寻道5 – 10 ms1000 万×随机 IO 是灾难

跨地域 RTT（京↻沪）25 – 40 ms—决定了能否跨地域部署缓存

怎么用这张表：判断某个优化值不值得做，就看它把数据从哪一级移到了哪一级。把一次访问从 SSD（100 μs）挪到内存（100 ns）是 1000 倍的提升，值得大动干戈；从 L3（30 ns）挪到 L1（1 ns）只有 30 倍，且通常不由应用控制。

三级淘汰策略对比

策略命中率（稳定负载）应对突发热点实现复杂度代表
FIFO低差（会淘汰刚起来的热点）极低基本不用
LRU高中低（哈希表 + 双向链表 O(1)）Redis（近似 LRU）
LFU高（稳定场景最高）差（新热点爬不上来）中需衰减机制
W-TinyLFU最高好（窗口区接纳新热点）高Caffeine

Redis 用的是“近似 LRU”：不是维护全局链表，而是每个 key 记录最近访问时间戳，淘汰时随机采样 N 个（默认 maxmemory-samples=5）取其中最久未用的。这是典型的用精度换内存与性能：全局链表要为每个 key 存前后指针（约 32 字节/键），千万级 key 就是几百 MB 纯开销。

Redis 淘汰配置与命中率

# Redis 淘汰策略配置
maxmemory 4gb                    # 必须设！不设则内存打满后写入报错/被 OOM kill
maxmemory-policy allkeys-lru     # 8 选 1，见下表
maxmemory-samples 5              # 近似 LRU 采样数：5 够用，10 更准但更慢

# 八种策略怎么选
#   noeviction      写满后报错（默认）—— 只有当你把 Redis 当存储时才用
#   allkeys-lru     全体 key 中淘汰最久未用 【缓存场景默认推荐】
#   volatile-lru    只在设了 TTL 的 key 中淘汰
#   allkeys-lfu     全体中淘汰访问最少的（v4.0+）
#   volatile-lfu    只在有 TTL 的 key 中按频率淘汰
#   allkeys-random  随机淘汰
#   volatile-random 有 TTL 的里随机
#   volatile-ttl    淘汰剩余 TTL 最短的

# 看命中率（最关键的健康指标）
redis-cli INFO stats | grep -E "keyspace_hits|keyspace_misses"
# 命中率 = hits / (hits + misses)
#   命中率 < 80%  -> 缓存策略或容量有问题
#   命中率   0%   -> 可能根本没生效（key 不匹配）

缓存路径：请求从浏览器到数据库的 6 层

层级位置典型 TTL挡掉的比例
① 浏览器缓存客户端本地由 Cache-Control 决定30 – 60%（静态资源）
② CDN 边缘缓存运营商节点分钟 – 小时60 – 90%（静态 + 部分动态）
③ 网关/Nginx 缓存接入层秒 – 分钟部分热点接口
④ 本地缓存应用进程内（Caffeine）秒级（10 – 60 s）70 – 90%（热点 key）
⑤ 分布式缓存Redis 集群分钟 – 小时90 – 99%
⑥ 数据库MySQL 等—剩下的 1 – 10%

每一层都要有 TTL 上限：本地缓存 TTL 太长会导致多实例间数据长时间不一致；经验值是 10 – 60 秒，配合 Redis 的发布订阅或 client-side caching（tracking） 主动失效。

HTTP 与 Nginx 缓存配置

# HTTP 缓存头（浏览器 + CDN 层）
Cache-Control: public, max-age=3600          # 强缓存 1 小时
Cache-Control: no-cache                      # 每次都校验（走 ETag/304）
Cache-Control: no-store                      # 完全不缓存（敏感数据）
Cache-Control: private, max-age=0, must-revalidate
ETag: "abc123"                               # 协商缓存的资源指纹
Vary: Accept-Encoding                        # 按请求头分别缓存

# Nginx 反向代理缓存
proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=mycache:100m
                 max_size=10g inactive=60m use_temp_path=off;
location /api/ {
    proxy_cache mycache;
    proxy_cache_valid 200 302 10s;           # 200/302 缓存 10 秒
    proxy_cache_valid 404      1m;           # 404 也缓存，防穿透
    proxy_cache_lock on;                     # 关键：singleflight，防击穿
    proxy_cache_use_stale error timeout updating; # 后端挂了先用旧值
    add_header X-Cache-Status $upstream_cache_status;  # HIT/MISS/BYPASS
}

深入自检

命中率多少算健康？

看层级：分布式缓存 > 95%、本地缓存 > 80% 算健康。但更要看绝对量——命中率 99% 但 miss 的 1% 是每秒 1 万次，DB 照样被打垮。所以监控要同时看命中率和回源 QPS 绝对值，后者才是 DB 的真实压力。

TTL 设多长合适？

两个原则：① 按数据变更频率——变更频繁的设短（秒级），静态数据可以小时级；② 加随机抖动——TTL = base + random(0, 0.2 × base)，防止同时过期引发雪崩。常见档位：用户信息 10 – 30 min、商品详情 5 – 30 min、配置类 1 – 5 min、热点榜单 10 – 60 s。

Write-through 和 Write-back 怎么选？

Write-through（同步写 DB）安全但每次写都要等 DB，适合写少且不能丢的场景（如余额）；Write-back（只写缓存，异步刷）快但宕机会丢，适合写多、可容忍少量丢失的场景（如浏览量计数、草稿）。业务系统里用得最多的是第三种——Cache Aside（写 DB 后删缓存），因为它最简单且不会丢数据。

缓存是不是加得越多越好？

不是。每加一层就多一份一致性成本和排查难度。判断标准：① 这层能挡掉多少回源？（< 10% 就不值得）；② 数据不一致会造成多大损失？（金融数据别乱加本地缓存）；③ 运维能 hold 住吗？（多一层 = 多一个排查点）。很多系统的合理答案是只用 Redis 一层，热点再加本地缓存。
