ab：按请求总量与并发数做 HTTP 基线测试

ApacheBench（ab）适合对单个 HTTP URL 做简单、可复现的基线测试。先理解请求尝试数、同时在途数与真实成功吞吐的区别。

工作方式与适用范围

-n 指定计划发送的请求总数；-c 指定一次同时进行多少个请求。完成后有剩余量就继续发，因此不是“一批 30 个做完，再做下一批”；整轮 500 次也不意味着任何时刻有 500 个在途。连接是否复用由 -k 等设置影响，服务端工作线程数不由 -c 直接决定。等待响应才继续补足并发的测试不等于固定到达速率测试。

适用于简单单接口的基线或小范围回归；复杂业务流程、混合流量、精确到达率和服务端瓶颈定位，需要结合其它工具及服务端监控。先看环境准备与安全边界。

命令：只针对本机示例接口

# 本机已启动并获授权的示例服务；不在此处运行
ab -n 500 -c 30 http://127.0.0.1:8100/ping

# 按时间观察、复用连接；先用低负载确认服务正常
ab -t 15 -c 10 -k http://127.0.0.1:8100/ping

# 本机测试接口若支持 POST，可从已有文件读入请求体
ab -n 100 -c 5 -p payload.json -T application/json http://127.0.0.1:8100/items

payload.json 须由测试者准备、并确保接口可安全写入；示例地址只是占位，不暗示正在运行服务。-t 与 -n 同时指定时有上限交互，采用时间档测试应单独核对实际完成量。

重要参数速查（Apache httpd 2.4）

参数含义注意
-n N整轮请求尝试总数；默认 1与任一时刻的在途请求数不是一回事
-c N同时进行的请求数；默认 1不是服务端线程数，也不等于 wrk 的连接数
-t 秒测试的最大持续时间内部隐含较大的请求数上限（50,000），不保证恰好运行到该秒数
-k启用 HTTP Keep-Alive默认不启用；会改变建连开销与结果
-s 秒socket 超时，默认 30 秒httpd 2.4.4+；超时样本要单列
-H '名称: 值'添加请求头检查认证/路由/缓存相关请求头是否与真实流量一致
-p 文件、-T 类型POST 文件内容；设置 Content-Type需测试者自行提供文件，验证写入副作用
-m 方法指定 HTTP 方法httpd 2.4.10+；并不自动构造请求体
-l不把响应体长度变化本身计作错误动态页面可能需要，但不可因此忽略异常响应
-e 文件、-g 文件分别导出百分位 CSV、每次测量的制表数据保留原始统计及同一口径的时间窗口

读懂输出，而不是只抄一个 QPS

  • Complete requests 是工具完成的请求数；Failed requests 关注连接、接收、长度等失败。HTTP 非 2xx 响应通常另列在 Non-2xx responses，不应把“Failed = 0”直接解释成业务成功率 100%。
  • Requests per second 是完成请求数 ÷ 测试总耗时（请求/秒）；含非业务成功响应时不是成功 QPS。
  • 第一行 Time per request 约为总耗时 × 并发数 ÷ 完成数（ms），代表每个请求的平均经历时间；第二行 Time per request (mean, across all concurrent requests) 约为总耗时 ÷ 完成数（ms），是跨并发摊平的时间，不要把第二行叫单个用户感受到的 RT。
  • Percentage of the requests served within a certain time 提供完成请求耗时分位；配合超时与失败，以及服务端日志和业务成功条件分析。若测试只运行很短、窗口内非稳态，分位数不能代表长期 P99。

核验来源与限制

参数、版本和输出字段可对照 Apache httpd 2.4：ab 官方手册，本机用 ab -h 核验安装版本。ab 的并发目标、网络条件与服务行为都会改变结果；不要用一个命令宣称生产容量。

比较 wrk 的线程与连接参数 · 回到 压测指标。

核心速览

一句话Apache 自带的单线程 HTTP 压测工具，最简单但能力有限
两个核心参数-n 总请求数、-c 并发数
致命限制单线程，在高速网络上自己会先成为瓶颈
适合快速验证、内网低速接口；正式压测用 wrk / vegeta
ab 四步：设总量 -> 设并发 -> 看输出 -> 判断是否该换工具

一、常用命令

# 基础：1000 个请求，100 并发 ab -n 1000 -c 100 http://127.0.0.1:8080/api/health # POST 请求（-p 指定 body 文件，-T 指定 Content-Type） ab -n 5000 -c 200 -p post.json -T application/json http://127.0.0.1:8080/api/order # 带 Header（-H 可多次） ab -n 1000 -c 50 -H "Authorization: Bearer xxx" http://127.0.0.1:8080/api/user # 开启 Keep-Alive（-k），否则每个请求都要重新握手 ab -n 10000 -c 200 -k http://127.0.0.1:8080/api/health # 设置超时（-s，单位秒，默认 30） ab -n 1000 -c 100 -s 5 http://127.0.0.1:8080/api/health # 输出更详细（-g 生成 gnuplot 数据，-e 生成 CSV） ab -n 1000 -c 100 -g result.tsv http://127.0.0.1:8080/

二、输出怎么读

Concurrency Level: 100 Time taken for tests: 3.245 seconds Complete requests: 1000 Failed requests: 0 Requests per second: 308.17 [#/sec] (mean) Time per request: 324.503 [ms] (mean) <- 这个除以并发才是单请求耗时 Time per request: 3.245 [ms] (mean, across all concurrent requests) Transfer rate: 102.34 [Kbytes/sec] received Percentage of the requests served within a certain time (ms) 50% 18 66% 22 75% 28 90% 45 <- 90% 的请求在这个时间内完成 95% 62 98% 95 99% 120 100% 310 (longest request) # 关键提醒： # "Time per request: 324.503ms" 是 <总时间/并发数> 的视角， # 不要误以为单请求耗时 324ms —— 真正接近用户感知的是下面的百分位表。

三、ab 的四个硬限制

限制说明后果
单线程所有并发在一个线程里用事件驱动实现压不出高 QPS，测的是 ab 自己的天花板
只支持 HTTP/1.1不支持 HTTP/2、WebSocket测不了现代协议
结果精度粗百分位只到 1ms 粒度，且没有 P99.9长尾问题看不出来
不支持动态参数无法按响应内容决定下一个请求测不了有依赖关系的业务流
怎么知道是 ab 压不动了

同时看两件事：① 被测机器的 CPU 是否还很低；② 跑 ab 的机器 CPU 是否接近 100%。如果压测机单核跑满而被测机还闲着，就是 ab 到瓶颈了 —— 换 wrk（多线程）或多机压测。

四、和 wrk / vegeta 怎么选

工具并发模型脚本能力适合
ab单线程事件驱动无快速验证、内网接口、低 QPS
wrk多线程 + 事件驱动Lua 脚本，强大正式压测首选，单机能力强
vegetaGo 协程，恒定速率配置驱动需要精确控制 QPS 的场景
jmeter线程池图形化，功能全复杂业务场景、非技术同学使用

五、深入自检

为什么 ab 的结果经常比 wrk 低很多？

因为 ab 是单线程。在千兆网 + 短响应场景下，ab 自己往往只能压到几千 QPS，而 wrk 能上几万。测出来的数字是工具的上限而不是服务的上限。

-n 和 -c 怎么配？

经验：-n 至少是 -c 的 20 倍，且 -n 总数不低于几千，否则统计意义不足。时长方面，ab 没有 -d 参数，只能通过调 -n 来控制总时长。

为什么一定要加 -k？

不加 -k，每个请求都要重新 TCP 握手（甚至 TLS 握手），测出来的是握手性能而不是服务性能。加了 -k 才能测出真实的业务处理能力。

Failed requests 非 0 一定有问题吗？

不一定。ab 会统计「响应长度不一致」为失败（它有 Length 检查），如果接口返回的动态内容长度本来就会变，就会误报。要看下面的具体分类再判断。

ab 还能用吗，是不是过时了？

它仍然是「快速验证服务是否正常」最方便的工具——几乎所有环境都自带、命令极短。但正式性能评估确实应该用 wrk 或 vegeta。定位是「随手一测」而不是「出报告」。
