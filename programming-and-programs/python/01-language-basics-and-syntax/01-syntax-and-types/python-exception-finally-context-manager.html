Python 异常与上下文管理器：return 遇到 finally 会发生什么

用文件写入失败的时间线解释异常传播、清理顺序、with 的退出协议与吞错风险。

异常路径也必须完成清理

打开文件后写入一半发生异常，程序不应把文件句柄、锁或数据库连接一直占着。Python 的 try/finally 允许在正常返回和异常传播两条路径上都运行清理代码。`with` 把“进入资源作用域、退出时清理”封装为上下文管理协议，适合文件、锁、连接与临时事务。它解决的是资源生命周期，不自动保证业务操作原子成功：文件写了一半后关闭，文件内容仍可能是半成品。

把异常处理与清理混在一个宽泛 except 里，容易漏掉没有预料到的异常。finally 即使没有 except 也会执行；清理之后原异常通常继续向上传播。上层应只捕获自己能处理的异常，保留错误栈和上下文，而不是用 `except Exception: pass` 假装操作成功。

图解：异常与清理的两条控制路径

沿箭头逐步核对输入、变换和输出；下面的推演可以逐步切换。

手推 return 与 finally

函数在 try 中准备 `return 1`，进入 finally 后执行日志与释放资源，最后把 1 返回。如果 finally 里又写 `return 2`，后一个返回会覆盖前一个，调用者收到 2；若 try 中本来抛了异常，finally 里的 return 甚至会压掉原异常。这通常是危险写法。类似地，finally 中新抛出的异常会改变向上传播的错误；需要把清理异常与原始错误都记录清楚。

Python 3.14 起对某些 finally 控制流会有新的编译期提醒或限制变化，阅读具体版本文档时应核对；稳妥的编码习惯是让 finally 只负责必要清理，不在里面 return、break 或 continue。这样调用者能看到原始结果或异常。考题若问“finally 一定执行吗”，也要限定正常解释器控制流：进程被强杀、系统断电等情况下无法保证执行。

with 背后的进入与退出

进入 `with resource as value` 时，解释器调用上下文管理器的进入方法，取得绑定值；离开代码块时调用退出方法。无论块内正常结束还是抛异常，退出方法都有机会清理。若退出方法在有异常时返回真值，它表示异常已经处理，原异常会被抑制；返回假值或 None，原异常继续传播。这个语义非常强，写自定义上下文管理器时不能为了“确保退出”总返回 True，否则真实故障会悄悄消失。

`contextlib.contextmanager` 让生成器在 yield 前后分别执行进入与退出逻辑。yield 之后的清理通常放在 finally 里；若异常从 with 块传回生成器，处理方式仍决定是否传播。异步资源要用 async with 和对应的异步进入、退出协议，不能用普通 with 假设异步关闭会自动 await。

文件写入与原子替换

若目标是“生成完整配置文件后对外可见”，直接 `with open(target, 'w')` 写入虽然会正确关闭句柄，但中途失败可能留下截断文件。更合适的流程是写到同目录临时文件，写完并校验后按文件系统语义原子替换目标；需要抗断电持久化时，还要考虑 fsync 文件与目录及文件系统保证。资源清理与数据原子发布是两个不同要求。

数据库事务也类似：上下文管理器可能在成功时提交、异常时回滚，但具体行为由驱动或封装决定。不要从 `with connection` 语法推断所有库都自动关闭连接或回滚。明确查该对象的 `__enter__`、`__exit__` 契约，并在异常路径写测试。

异常链帮助定位根因

处理底层异常后需要给上层更有意义的业务错误，可用 `raise DomainError(...) from original_error` 保留直接原因。若仅重新抛出，用裸 `raise` 保留当前异常栈；重新构造相同类型而不传原因，可能丢掉关键现场。日志也不要在每一层重复打印同一栈，造成噪声；在真正处理或边界处记录一次，并带上请求 ID、资源名等上下文。

只捕获预期可恢复的异常，例如文件不存在后创建默认配置；权限不足、磁盘满则不应被当作“没有配置”处理。捕获太宽会把编程错误和运行环境故障伪装成业务空值。finally 的任务是释放已取得的资源，不负责把所有错误吞掉。

三个小实验

先写一个函数，try 中 `return 1`，finally 只打印“cleanup”，确认返回 1；再把 finally 改成 `return 2`，观察结果变 2。第二个实验让 try 抛 ValueError、finally 做清理并不返回，观察 ValueError 向外传播。第三个实验写自定义上下文管理器，让退出方法分别返回 False 和 True，观察 with 块内异常是否被抑制。每次都检查清理计数恰好一次。

执行顺序的完整矩阵

场景exceptelsefinally最终返回/抛出
无异常跳过执行执行以 try 块的 return 值为准
有异常且被捕获执行跳过执行以 except 块的 return 值为准
有异常未捕获不匹配则跳过跳过执行异常继续向外传播
finally 里有 return——执行并直接返回异常被吞掉

两条硬规则：① finally 无论是否异常都会执行（即使 try 里有 return、break、continue）；② 不要在 finally 里写 return，它会吞掉正在传播的异常。

上下文管理器的实现与等价写法

类实现

class Resource:
    def __enter__(self):
        print("acquire"); return self
    def __exit__(self, exc_type, exc, tb):
        print("release", exc_type)
        return False      # 返回 True 会吞掉异常；False 或 None 让异常继续传播

with Resource() as r:
    raise ValueError("boom")        # 会看到 “release <class ValueError>” 然后异常继续抛出

# 等价的手写形式（with 的本质）
r = Resource()
try:
    _ = r.__enter__()
    raise ValueError("boom")
except BaseException as e:
    if not r.__exit__(type(e), e, e.__traceback__):
        raise
else:
    r.__exit__(None, None, None)

contextlib

from contextlib import contextmanager, ExitStack, suppress

@contextmanager
def managed():
    print("acquire")
    try:
        yield "resource"          # yield 处执行 with 体
    finally:
        print("release")          # 退出时必定执行

with managed() as r:
    print(r)

# 动态管理多个资源（数量在运行时才知道）
with ExitStack() as stack:
    files = [stack.enter_context(open(f)) for f in ["a.txt", "b.txt"]]
    ...

# 明确忽略某类异常
with suppress(FileNotFoundError):
    open("maybe.txt").close()

深入自检

try 里有 return，finally 还会执行吗？

会。finally 在控制流离开 try 块之前执行，包括 return、break、continue 甚至异常传播。这也是释放资源必须放 finally 的原因。

finally 里修改返回值会生效吗？

要看改的是名字还是对象：return 时返回值已经绑定，finally 里给变量重新赋值不会改变已绑定的返回值；但如果返回的是可变对象并在 finally 里修改其内容，调用方会看到改动。

__exit__ 返回 True 和 False 有什么区别？

返回 True 表示“异常已处理”，with 语句吞掉该异常继续往下执行；返回 False 或 None 则异常继续向外传播。多数资源管理类应返回 False，避免意外吞错。

什么时候用 @contextmanager，什么时候写类？

简单的一次性资源（获取-释放成对）用 @contextmanager 更短；需要复用、需要状态、或要在多处使用则写类实现 __enter__/__exit__。用 @contextmanager 时注意 yield 必须包在 try/finally 里，否则异常路径不会释放。

异常处理的性能代价有多大？

现代 CPython（3.11+ 零开销异常）里，try 块本身几乎不花成本，成本发生在抛出与捕获（构造 traceback、遍历栈帧），量级约微秒级，比一次函数调用慢 1~2 个数量级。因此异常适合错误处理，不适合做正常的控制流。

自检

`try: return 1`，`finally: return 2`，调用方得到什么？原异常又会怎样？

得到 2；finally 的 return 会覆盖 try 的返回值，也可能压掉原异常，因此应避免这样写。
