01 · 原则从问题里长出来

直接写会有什么代价？

04 · 把原则写进代码

最小伪代码

interface Channel { send(text) }
interface Rule { format(text) }
class Notice {
  constructor(rule: Rule, channel: Channel) {
    this.rule = rule; this.channel = channel
  }
  send(text) { this.channel.send(this.rule.format(text)) }
}
notice = Notice(UrgentRule(), SmsChannel())

从代码中带走三件事

  1. 找出独立变化轴，而不是看到继承就一律重写。
  2. 抽象只表达稳定契约，不把 Email 的专有参数塞进 Channel。
  3. 在组装处选择实现；业务流程只依赖接口。
05 · 原则不是教条

对应哪些模式？什么时候收手？

  • 桥接：两个独立维度由组合连接
  • 策略：注入可替换算法
  • 装饰器：组合叠加可选职责

继承不是错误：稳定的 is-a 关系、共享不变量和模板流程仍可用继承。问题是用继承表示“可以自由拼装的能力”。

加急通知和短信渠道都可能增加新类型，为什么不要建立 UrgentSmsNotice？

两个维度的组合会成倍扩张；让 UrgentNotice 持有 Channel，可分别新增消息规则或渠道。

第二层 · Go 嵌入的三个真坑与对应写法

坑现象正确写法
方法集污染只想复用字段，却把对方的方法也导出去了，意外实现某个接口用命名字段而不是匿名字段
字段提升冲突两层都有同名方法，外层调用直接编译失败显式指定 x.Inner.Method()
零值不可用嵌入指针字段，零值对象是 nil，一调用就 panic提供构造函数，或嵌入值类型
JSON 序列化嵌入字段被拍平进外层，字段名对不上协议显式加 json:"..." tag
副本共享嵌入的是指针，两个外层对象共享同一份状态明确谁负责初始化，文档写清所有权
// 坑 1：匿名嵌入会让外层意外获得内层的方法集
type ReadOnly struct{ mu sync.Mutex }          // 有 Lock/Unlock 方法
type Service struct{ ReadOnly }                // 匿名嵌入 → Service 也有 Lock/Unlock
// 后果：Service 意外满足 sync.Locker，被别人当锁用；且 API 表面变大
// 修：改成命名字段，只复用数据不复用行为
type ServiceOK struct{ ro ReadOnly }

// 坑 2：零值不可用
type Cache struct{ m map[string]string }
// var c Cache; c.m['a'] = 'b'  → panic: assignment to entry in nil map
// 修：构造函数保证可用
func NewCache() *Cache { return &Cache{m: make(map[string]string)} }

// 坑 3：JSON 拍平，协议对不上
type Meta struct {
	ID   string `json:'id'`
	Time int64  `json:'time'`
}
type Resp struct {
	Meta            // 匿名 → 输出 {"id":..,"time":..}
	Data string     `json:'data'`
}
// 想要 {"meta":{...}} 就要命名字段： Meta Meta `json:'meta'`

判断标准一句话：要复用行为（方法）才用匿名嵌入；只想复用数据或不想扩大 API，一律用命名字段。

第三层 · 组合落地的检查清单

  • 先问‘这个类型是 is-a 还是 has-a’：has-a 一律组合，is-a 也要先确认基类是否真的稳定。
  • 接口只在使用方定义：不要先从实现抽象出接口，而是调用方需要什么方法就定义多大的接口（1~3 个方法最佳）。
  • 嵌入前先列方法集：写下嵌入后外层会多出哪些方法，只要有一个不该出现，就改成命名字段。
  • 每个组合对象都要能零值或构造后可用：避免出现‘必须调用 Init 才能用’的类型。
  • 不要在组合层做类型断言：出现 switch v := x.(type) 说明抽象没到位，考虑把差异做成字段或策略。
  • 测试替身要容易注入：依赖写成接口字段，测试直接塞 fake，这是组合优先最大的实际收益。
  • 别为了‘以后可能扩展’先分层：只有两个实现时先用 if，第三个实现出现再抽接口。

继承的真正问题不是‘不好’，而是它把父类实现细节变成了子类的公共契约：父类改一个内部方法就可能破坏所有子类。组合把这条隐式契约切断，代价是需要多写一点转发代码。

第四层 · 什么时候用继承（或嵌入）反而更好

有没有适合‘像继承一样’组织的场景？

有：当层次是稳定的分类学而不是行为复用时（如 AST 节点、错误类型、协议消息），基类几乎不会改，用继承/嵌入表达‘都是同一种东西’反而更清晰。

Go 没有继承，怎么表达‘多个实现共享默认行为’？

嵌入一个实现了默认行为的结构体，外层只覆盖需要改的方法；这与继承效果相同，但外层可以选择不暴露嵌入体的方法（命名字段）从而避免 API 膨胀。

组合太多层会不会更难读？

会。组合超过三层、且每层只转发调用时，说明抽象过度；判断信号是找不到任何一层有独立逻辑，此时应该合并成一层。

继承的问题：为什么会想换掉它

继承是最容易被滥用的复用手段。它把父类与子类在编译期焊死，父类的任何改动都会波及所有子类，这就是所谓「脆弱基类问题」。

继承的层次困境 vs 组合的按需装配
脆弱基类父类改动波及所有子类。
组合爆炸多维度能力会让类数量指数增长。
无法拒绝子类被迫接受父类的方法。
组合可替换持有接口即可运行时替换行为。

Go 怎么做到组合优先

// ① 接口表达能力，小接口优先 type Flyer interface{ Fly() } type Swimmer interface{ Swim() } // ② 组合：类型只实现它真的有的能力 type Penguin struct{ name string } func (p Penguin) Swim() { fmt.Println("swim") } // Penguin 不实现 Fly —— 编译期就不会被当成 Flyer type Sparrow struct{ name string } func (s Sparrow) Fly() { fmt.Println("fly") } func (s Sparrow) Swim() { fmt.Println("not good") } // ③ 嵌入复用实现（不是继承） type Logger struct{ prefix string } func (l Logger) Log(m string) { fmt.Println(l.prefix, m) } type Service struct { Logger // 复用 Log 的实现 store Store // 组合一个依赖 } // ④ 行为参数化：把变化的部分作为函数传入 func Run(fetch func() ([]byte, error)) error { ... }
目的继承的做法Go 的做法
复用实现子类继承父类嵌入 + 方法提升
表达多态父类引用指向子类接口
替换行为覆写方法传入函数或接口实现
扩展能力加子类 / 加父类方法加接口，按需实现
共享状态protected 字段显式字段 + 方法

Go 的根本差异：嵌入只复用实现，不产生「is-a」关系。*Penguin 不能当作 Animal 使用——多态完全由接口承担。这让类型关系更扁平，也避免了层次爆炸。

什么时候仍然适合「像继承一样」组织代码

可以用的场景

  • 实现几乎不变、层次很浅（1~2 层）
  • 只是想少写几行样板，用嵌入完全够
  • 装饰器：包装一个接口并增强它
  • 测试桩：嵌入接口只实现关心的方法
// 装饰器：包装接口，增强行为 type LoggingStore struct { Store // 嵌入接口 log *slog.Logger } func (s LoggingStore) Get(id int64) (*User, error) { s.log.Info("get", "id", id) return s.Store.Get(id) // 转发 }

应当避免的场景

  • 为了「统一基类」而造抽象父类
  • 子类需要拒绝父类的某些方法
  • 层次超过两层且各层都在加方法
  • 用类型判断来区分行为（应改用多态）

判断标准

问自己一个问题：这个类型是为了复用代码，还是为了被当作另一种类型使用？

  • 前者 → 组合 / 嵌入
  • 后者 → 接口
  • 两者都要 → 组合实现 + 接口暴露

深入自检

组合一定比继承好吗？

不是绝对，但适用范围更广。继承在实现稳定、层次极浅时确实简洁；问题在于它容易被扩展到不适合的场景。组合的代价是需要多写一些转发代码，换来的是可替换性与更低的耦合。

Go 的嵌入就是继承吗？

不是。嵌入会提升字段与方法，写起来像继承，但它不产生多态：外层类型不能被当作内层类型使用。Go 里多态只由接口提供。把嵌入当继承来设计层次，很快会碰到语义混乱。

什么时候该用嵌入而不是普通字段？

当你希望外层类型直接暴露内层的方法（作为自己的 API 一部分）时用嵌入；当内层只是被使用的依赖、不希望暴露其方法时用普通字段。后者更常见，也更符合「最小暴露」原则。

组合会不会导致转发代码太多？

会一点。可以通过只组合真正需要的接口（而不是整个大接口）、或使用代码生成与装饰器模式来减少样板。若转发代码多到难以维护，通常说明接口划分过粗。

怎么判断该抽接口还是该用组合？

需要「被当作多种类型使用」→ 接口；需要「把已有实现拿来用」→ 组合。多数情况是两者配合：用组合搭出实现，用接口对外暴露能力。
