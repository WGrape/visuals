什么时候适用？

判断信号：事实发生后多个下游可独立响应，业务允许异步与最终一致。

  • 订单支付后积分与通知各自消费
  • 库存变化触发搜索索引更新
  • 设备遥测驱动多个实时分析服务

和相近方案怎么区分？

相近方案选择边界
观察者模式观察者通常是进程内回调；跨服务事件需要持久化、重试和幂等。
同步 RPCRPC 调用方等待结果；事件驱动的下游可异步处理，但要接受延迟与乱序。

最小伪代码

transaction:
  order.markPaid()
  outbox.insert(OrderPaid(order.id))
// 提交后由发布器把 outbox 送入总线
on OrderPaid(event):
  if not processed(event.id): grantPoints(event.orderId)

边界：事件是已发生事实；可靠投递需要 outbox/重试等机制，消费者要能处理重复与乱序。

事件流模型 EDA

一个事件可被多个消费者独立订阅；生产者不直接调用消费者

核心角色：事件（『发生了什么』的事实，如 OrderCreated）、生产者（发出事件）、经纪人/总线（Kafka、RabbitMQ）、消费者（各自订阅关心的事件）。

两种典型模式

  • 事件通知：只通知『发生了什么』，消费者自己去拉详情（耦合低、需回查）。
  • 事件携带状态(Event Carried)：事件里带上完整数据（自治、但可能冗余）。
  • 事件溯源 Event Sourcing：状态由一连串事件重放得到，而非直接存当前值。

优缺点

面试高频问答

Q：事件驱动和事件溯源是一回事吗？
A：不是。事件驱动是『通信风格』（用事件解耦服务）；事件溯源是『存储风格』（用事件序列表达状态）。事件溯源是事件驱动的一种进阶用法。
Q：如何保证事件不丢、不重复消费？
A：不丢靠消息队列持久化+确认机制；不重复靠消费者幂等（用事件ID/业务唯一键去重）。顺序性靠分区键绑定。

事件驱动：把「调用」换成「通知」

传统调用是命令式的：A 明确要求 B 做某件事，A 必须知道 B 存在、B 的地址、B 的接口，并且要等 B 返回。事件驱动改成声明式：A 只广播「发生了什么」，谁关心谁订阅，A 不关心也不等待。

命令式调用 vs 事件驱动：耦合方向发生了反转

三种事件模式

模式事件内容优点缺点 / 注意
事件通知（Event Notification）只说「发生了什么」，如 OrderPaid{orderId}，订阅方需回查详情耦合最低、事件体小、稳定订阅方要额外查询；高频查询会给源服务压力
事件携带状态（Event-Carried State）事件里带上完整快照，如订单全部字段订阅方无需回查，可用性高（源服务挂了也能处理）事件体大；数据 schema 变更要兼容；可能泄露信息
事件溯源（Event Sourcing）不存当前状态，只存事件序列，状态靠重放事件得出完整审计轨迹、可时间旅行、天然支持回放重建查询需投影（读模型）；重放慢需快照；学习成本高

选型：普通业务用事件通知（最常用、最稳）；对可用性要求高或订阅方多的场景用事件携带状态；事件溯源只在确实需要审计与回放能力（金融账本、协作编辑）时才用，不要为了炫技上。

消息中间件的关键机制

投递语义

  • 至多一次：可能丢，绝不重复（生产者发完不等确认）
  • 至少一次：绝不丢，可能重复（默认，需消费端幂等）
  • 恰好一次：需事务 + 幂等共同保证（Kafka 事务、Flink 两阶段提交）
  • 实践：绝大多数系统用「至少一次 + 消费端幂等」实现业务上的恰好一次

顺序保证

  • Kafka 只保证分区内有序——所以按同一 key（如订单 ID）路由到同一分区
  • 需要全局有序时只能单分区，吞吐极低，应极力避免
  • 更好的办法：用状态机 + 版本号容忍乱序，乱序事件丢弃或暂存

消费模型

  • 点对点/队列：一条消息只被一个消费者实例处理（任务分发）
  • 发布订阅：一条消息被每个订阅组各处理一次（广播通知）
  • 消费者组：组内竞争（分摊），组间广播（各得一份）

积压与重放

  • 消息可重放是事件驱动相对同步调用的一大优势：修好 bug 后重放历史消息即可补数据
  • 积压的处理：扩容消费者（受分区数限制）、批量消费、或直接跳过（有损时需确认可接受）
  • 必须监控积压量而非只看是否在线

事件驱动的真实代价

事件驱动不是银弹，它把「编译期可见的调用关系」变成了「运行期隐式的订阅关系」，带来三类明确成本：

① 可观测性下降一个业务动作的结果散落在多个消费者里，必须靠 TraceId 串联全链路，否则无法排查
② 一致性变弱只能保证最终一致；需要设计幂等、补偿、对账三件套
③ 调试困难没有「调用栈」，出问题要看消息流转；本地难以复现，需完整的消息回放环境
④ 消息契约管理事件 schema 演进必须向后兼容；应建 schema registry 与版本策略
⑤ 循环依赖风险A 发事件触发 B，B 又发事件触发 A——隐式循环极难发现，需要拓扑可视化

什么时候不该用：需要强一致（转账核心）、需要立即拿到返回值（登录校验）、流程非常简单（就两步同步调用）、团队缺乏消息中间件运维能力。这些场景下同步调用的确定性和简单性价值更大。

深入自检

事件驱动能完全替代同步调用吗？

不能，也不应该。需要立即得到结果的场景必须用同步调用：登录鉴权要立刻知道 token 是否有效、库存校验要立刻知道能否下单、支付要立刻知道是否成功。事件驱动适合「后续动作」：下单成功后发通知、加积分、更新推荐、同步数据仓库。实践上是混合架构——核心链路用同步保证确定性与一致性，旁路动作异步化提升性能与解耦。

如何保证本地事务与消息发送的一致性？

这是经典难题：先写库后发消息，发消息失败则数据不一致；先发消息后写库，写库失败则下游看到不存在的数据。三种解法：① 本地消息表——业务与消息记录在同一本地事务里写入，后台任务扫描未发送的消息投递，失败重试（最常用，RocketMQ 事务消息也是这个思路）；② 事务消息——半消息 + 本地事务回调 + 回查；③ 监听 binlog（CDC）——用 canal/Debezium 捕获数据变更再发消息，对业务零侵入。

Kafka 为什么只保证分区内有序？

因为分区是并行的最小单位。若要全局有序，只能设 1 个分区、1 个消费者，那么所有并行能力（多分区、多消费者、多 Broker 分担）全部失效，吞吐降到单机水平。所以设计上用「按业务 key 分区」把需要有序的消息路由到同一分区——例如同一订单的所有状态变更都按 orderId 分区，这样该订单内是有序的，而不同订单之间可以并行处理，既保证了业务需要的顺序又保留了扩展性。

事件 schema 变更怎么处理？

遵循「向后兼容」原则：只允许新增可选字段，不允许删除或改字段语义与类型。消费者遇到未知字段应忽略而非报错（宽容读取）。破坏性变更要走「双写迁移」：同时发布 v1 和 v2 两个主题 → 消费者逐步切到 v2 → 全部切换完成后下线 v1。用 Schema Registry（Avro/Protobuf）可以做兼容性自动校验，在发布前拦截不兼容的变更。另外建议事件里带上 schema 版本号，便于消费者识别与兼容处理。
