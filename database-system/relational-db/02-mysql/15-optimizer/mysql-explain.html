MySQL EXPLAIN 详解

EXPLAIN 到底是不是「MySQL 的优化器实现」？它的工作原理是什么、输出怎么读、和优化器 / optimizer_trace 又是什么关系（结论先行：它是优化器的「报告单」，不是优化器本身）

① 先给结论 ② 它在链路的位置 ③ 工作原理 ④ 12 字段详解 ⑤ 重点：type 与 Extra ⑥ EXPLAIN vs trace ⑦ 误解清单
①先给结论：EXPLAIN 不是优化器，是优化器的「报告单」

一句话直接回答你的问题：EXPLAIN 不是 MySQL 优化器（Optimizer）的实现。它是 MySQL 提供的一条诊断命令——在优化器把一条 SQL 优化完、产出「执行计划」之后，EXPLAIN 把那棵计划读出来、格式化给你看。打个比方：

  • 优化器 = 后厨的厨师，负责把「菜怎么做最省时省力」想清楚，并真正下锅。
  • EXPLAIN = 你点完菜后，服务员递来的「后厨做菜流程单」——它不炒菜，只是把厨师已经定好的流程打印出来给你看。
为什么这个区分很重要
很多人把「看 EXPLAIN」等同于「在看优化器干活」。其实优化器在 EXPLAIN 输出之前早就跑完了。EXPLAIN 只是「事后读结果」的工具，它既不参与「选计划」、也不参与「算代价」——那两套逻辑是优化器自己的事。搞清楚这一点，才不会把「EXPLAIN 看不懂」误以为「优化器有问题」。

接下来的几节会展开：它到底夹在链路的哪里、它「做」了什么、为什么是「看计划」而非「做计划」、以及当 EXPLAIN 不够用时该去找谁（optimizer_trace）。

注意图里的方向：EXPLAIN 读取的是「优化器 → 执行计划树」这个结果，不是反过来。所以当你敲下 EXPLAIN SELECT ...，MySQL 内部其实先走了一遍优化流程（生成计划），再把计划转成你能读的表格——你看到的不是「优化器正在思考」，而是「优化器已经想好的结论」。

③EXPLAIN 工作原理：它到底「做」了什么

把上面那句话再拆细。EXPLAIN 的行为分三种形态，关键差异在于它有没有真的去执行那条查询。

形态一：普通 EXPLAIN（不执行查询）

对 SELECT / DELETE / INSERT / REPLACE / UPDATE 都能用。它复用优化器生成计划的代码路径，得到那棵计划树，然后把它「描述（describe）」成表格 / JSON / TREE 输出。它不真正取数据、不碰存储引擎的读路径，所以即便一条 SQL 要跑十分钟，EXPLAIN 也能秒回——这是它最安全、最常用的形态。

-- 只看计划，不执行
EXPLAIN SELECT * FROM orders WHERE user_id = 42 ORDER BY created_at DESC LIMIT 10;

-- JSON 格式：含代价估算、更细的执行细节
EXPLAIN FORMAT=JSON SELECT ...;

-- TREE 格式（8.0.16+）：可读的嵌套计划树
EXPLAIN FORMAT=TREE SELECT ...;
一个常被忽略的细节：普通 EXPLAIN 也「会执行一部分」
说「EXPLAIN 完全不执行」是 99% 成立的经验法则，但非 100%。当一条 SQL 含有 派生表（DERIVED，FROM 子句里的子查询）、物化子查询（MATERIALIZED） 或 依赖子查询（DEPENDENT SUBQUERY） 时，为了能「描述」这些结构，MySQL 会先把它们物化 / 执行出来，再描述结果。所以极端情况下（比如一个超大的派生表），EXPLAIN 本身也可能并不轻量——但主体是「不执行主查询」的。

形态二：EXPLAIN ANALYZE（8.0.18+，真正执行）

它真的把整条查询跑一遍（包括所有副作用），只是把结果行丢弃，只保留「测量数据」：每个计划节点的首行耗时 / 末行耗时 / 实际行数 / 循环次数（loops）。输出强制为 TREE 格式。

-- 真正执行并测量：预估 vs 真实
EXPLAIN ANALYZE SELECT c.email, o.id
  FROM customers c JOIN orders o ON o.customer_id = c.id
  WHERE c.country = 'DE' ORDER BY o.ordered_at DESC LIMIT 50;

-- 典型输出（节选）
-> Nested loop inner join  (cost=108 rows=20) (actual time=0.25..12.3 rows=1450 loops=1)
   -> Table scan on o  (cost=50 rows=200) (actual time=0.10..3.5 rows=2000 loops=1)
   -> Single-row index lookup on c using PRIMARY  (rows=1) (loops=1450)
预估 vs 真实：慢查询的主战场
绝大多数的「坏计划」都源于优化器对某一步会产出多少行估计错了。普通 EXPLAIN 只给你 rows=20 这样的预估值；EXPLAIN ANALYZE 告诉你「其实产了 1450 行」。两者差距越大，越说明统计信息失真——这时去 ANALYZE TABLE 重算统计往往就解决了。

形态三：FORMAT 三种输出

格式特点何时用
TRADITIONAL（默认，表格）一行一表，12 列，最直观日常快速诊断，一眼看 type / key / Extra
FORMAT=JSON结构化，含 cost_info、各节点细节想看代价、访问路径细节
FORMAT=TREE（8.0.16+）嵌套计划树，显示节点层级与算法多表 JOIN 看执行顺序；EXPLAIN ANALYZE 强制用
④输出 12 个字段详解

默认表格一行对应「计划里被访问的一张表」（含派生表、临时表），共 12 列。下面按「怎么读」的重要性排序列出。

字段含义怎么读
idSELECT 的编号相同 id 从上往下一起处理；id 越大越先执行（子查询通常更大）；NULL 是结果集（如 UNION RESULT）
select_type查询类型SIMPLE / PRIMARY / SUBQUERY / DERIVED / MATERIALIZED / UNION …；DEPENDENT SUBQUERY 要警惕（外层每行进子查询，易慢）
table本行访问的表可能是真实表、派生表 <deriven_N>、UNION 结果 <unionM,N>
partitions命中的分区非分区表为 NULL
type访问类型（最核心）怎么找行，性能好→差见下节排序
possible_keys可能考虑的索引候选名单，NULL 表示没可用索引
key实际用的索引NULL = 没用索引（配 type:ALL 即全表扫）；可用 FORCE INDEX 纠正
key_len用了索引多少字节联合索引里判断生效到第几列；允许 NULL 的列额外 +1 字节
ref和索引比的是什么const（常量）/ 表.列（关联列）/ func（函数）
rows预估扫描行数是估计值不是真实值；JOIN 各表 rows 相乘≈总考察组合数，乘积大就是坏计划
filtered存储引擎返回后通过 WHERE 过滤的%rows × filtered / 100 ≈ 传给下一步的行数；值低 + rows 高 = 读很多只留很少
Extra额外信息（第二核心）见下节：Using index 好；Using filesort / Using temporary 要优化
两张表怎么对应真实目录
输出里「一行一表」的顺序，就是 MySQL 实际读取这些表的顺序（JOIN 顺序），而不是你 SQL 里写的顺序。所以多表 JOIN 看 EXPLAIN，重点看它先扫了哪张、后扫了哪张。
⑤重点读两个字段：type 与 Extra

type 是判断「查得快不快」的命门——它描述 MySQL 用什么方式定位行。性能从好到坏（已核实的官方排序）：

system > const > eq_ref > ref > fulltext > ref_or_null >
index_merge > unique_subquery > index_subquery > range > index > ALL

优化目标：至少到 range，理想是 ref / eq_ref / const；出现 index（全索引扫）或 ALL（全表扫）要重点查。下面这个评级器，点选任意类型看它的等级与是否需要警惕：

type 访问类型评级器
选一个 access type，看它在「性能天梯」上的位置与解读（纯规则判定，结论稳定可靠）。

Extra：决定「要不要优化」的另一半

Extra 值含义信号
Using index覆盖索引，所需列全在索引里，无需回表好
Using index condition索引下推（ICP），在索引层就过滤，减少回表好
Using where在 Server 层再过滤一次正常
Using filesort无法用索引排序，需额外排序要优化
Using temporary用了临时表（GROUP BY / DISTINCT / UNION 常见）要优化
Select tables optimized away聚合被索引直接满足，最优好
实战口诀
日常看 EXPLAIN，先盯 type 别出现 ALL / index，再盯 Extra 别出现 Using filesort / Using temporary。这两处干净，95% 的慢查询都能定位出来。
⑥EXPLAIN vs optimizer_trace：what 与 why 的区别

回到开头那个混淆：既然 EXPLAIN 是「报告单」，那「报告单」只告诉你优化器最终选了什么（what），不告诉你为什么选这个、为什么没选你预期的那个（why）。要追问 why，得请出 optimizer_trace。

三件套定位切换：EXPLAIN / EXPLAIN ANALYZE / optimizer_trace
点三个按钮，看清它们各自「做什么、是否执行查询、回答什么问题」——直观理解「EXPLAIN 不是优化器」。

做什么：读取优化器已生成的计划并格式化输出。

是否执行查询：基本不执行（DERIVED / 物化子查询会先物化）。

回答：「计划长什么样？走了哪个索引？访问类型是啥？」= what（最终方案）。

看不到：为什么没选你预期的索引、各候选代价差多少。

做什么：真把查询跑一遍，测量每步真实耗时与行数。

是否执行查询：是，完整执行（结果丢弃，仅留测量值）。

回答：「预估行数和真实行数差多少？哪一步最慢？」= 实测验证。

典型用途：发现优化器估计失准 → 去 ANALYZE TABLE 更新统计。

做什么：把优化器「思考全过程」记成 JSON，存进 information_schema.OPTIMIZER_TRACE。

是否执行查询：视情况（trace 记录的是优化决策，不一定执行主查询）。

回答：「为什么选 A 不选 B？索引代价怎么算的？连接顺序怎么评估的？」= why（决策过程）。

典型用途：range_analysis 看各索引 range 成本，considered_execution_plans 看不同 JOIN 顺序总成本。

-- 用 optimizer_trace 追问「为什么没选我预期的索引」
SET optimizer_trace = 'enabled=on';
SELECT * FROM Country WHERE continent='Asia' AND population > 5000000;
SELECT * FROM information_schema.optimizer_trace\G
SET optimizer_trace = 'enabled=off';  -- 用完关掉，避免开销
三者关系一句话
优化器是干活的引擎；EXPLAIN 是「看它干了啥」的窗口；EXPLAIN ANALYZE 是「看它干完到底花了多久」的秒表；optimizer_trace 是「看它脑子里怎么想的」的录音笔。三者都是围绕优化器的观测工具，哪一个都不是优化器本身。
⑦关于 EXPLAIN 的四个常见误解
  • 误解 1：EXPLAIN 就是优化器（的实现）。错。优化器是生成计划的引擎，EXPLAIN 是读取并展示计划的命令。还原句：EXPLAIN 报告优化器，而非实现优化器。
  • 误解 2：EXPLAIN 完全不执行任何东西。基本对，但有例外——含 DERIVED 表、MATERIALIZED、DEPENDENT SUBQUERY 时，MySQL 会先把这些子结构物化 / 执行出来才能描述。
  • 误解 3：EXPLAIN 里的 rows 是真实行数。错。它是预估值，来自统计信息；真实行数要看 EXPLAIN ANALYZE 的 actual rows。
  • 误解 4：EXPLAIN 看到计划「差」就说明查询一定慢。不一定。EXPLAIN 不执行，估计可能严重偏离真实；要确认慢，得上 EXPLAIN ANALYZE 拿实际耗时。
什么时候该用哪个
先 EXPLAIN 快速看计划是否异常（有无 ALL、有无 filesort/temporary）→ 若发现优化器选错（比如没走预期索引），再用 optimizer_trace 看它为什么这么选 → 若怀疑统计失真，用 EXPLAIN ANALYZE 拿真实行数、再 ANALYZE TABLE 修正。三者配合，才是完整的调优闭环。
