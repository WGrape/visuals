Memory Architecture

OpenClaw 记忆系统架构

基于文件化记忆 + 可扩展检索的混合架构，与 Claude Code 有本质区别。OpenClaw 采用了更像传统 RAG 的检索增强方案。

Architecture

核心设计理念

OpenClaw 的记忆系统与 Claude Code 最根本的区别：不是「把所有文件拼接到上下文」，而是「按需检索相关记忆」。

Retrieval

混合检索流程

当用户发起请求时，OpenClaw 会经历以下检索流程，找到最相关的记忆片段：

1

查询解析 Query Understanding

将用户的自然语言查询转换为检索向量和关键词集合。同时提取实体、时间、意图等元信息。

2

BM25 关键词检索

在 .openclaw/memory/ 目录中对所有 Markdown 文件进行倒排索引匹配。找出包含精确关键词的记忆片段。

3

向量语义检索

将查询向量与存储的 embedding 进行余弦相似度计算。找出语义上最相关但可能不包含精确关键词的记忆。

4

分数加权融合

将 BM25 分数和向量相似度分数按权重合并。权重可配置，通常语义权重略高。融合后得到最终排序列表。

5

时间衰减加权

每条记忆有指数衰减的权重。decay_rate 通常设为 0.95^t（t = 天数）。同时考虑访问频率boost。

6

Rerank 精排

用交叉编码器对 Top-K 候选记忆重新评分，确保真正相关的内容排在最前面。输出最相关的 N 条记忆片段。

7

注入上下文

将检索到的记忆片段插入到 prompt 的专用区域。记忆是「片段级」注入，而非整文件注入。

OpenClaw Memory System · 2026

记忆分层：把 token 花在刀刃上

层级内容生命周期典型预算
L0 工作记忆当前对话的滑动窗口会话内8k – 32k token
L1 情节记忆本次会话的摘要与关键决策会话结束后落盘1k – 4k token
L2 语义记忆跨会话沉淀的事实/偏好（MEMORY.md）长期2k – 8k token
L3 档案记忆原始日志、完整文档永久归档按需检索，不进窗口

核心思想：上下文窗口是最贵的资源，所以要分层——越靠近“当下”的数据越精炼、越常驻；越久远的数据越原始、越按需加载。L2 是可写的长期记忆，L3 是只读的档案库。

写入策略：什么该记住、什么该忘

内容是否写入理由
用户明确的偏好/禁忌✅ 必写跨会话稳定，价值最高
项目架构与关键命令✅ 写每次都要用到
本次任务的中间推理❌ 不写一次性，污染长期记忆
已经完成并归档的事❌ 移入 archive保留可查但不占预算
可能变化的信息（版本号）⚠️ 写但标注时间防止过期记忆误导

最关键的纪律是“忘”：长期记忆的价值 = 准确度 × 相关性，堆积越多准确度越低（过期信息会误导模型）。所以要定期做两件事：① 把完成任务后不再需要的移到 archive；② 给事实加时间戳，过期自动降级。

检索：怎么从记忆里捞出该用的那几条

记忆系统不是“全部塞进提示词”，而是检索后按需注入。常见三路：

  • ① 常驻：MEMORY.md 的核心条目每次都加载（预算 1k – 2k token）
  • ② 关键词命中：对话里出现的实体名（项目名、人名、模块名）触发对应记忆文件加载
  • ③ 语义检索：把记忆条目 embedding 后按相似度取 top-3 ~ 5（混合 BM25 更稳）

记忆检索与预算控制

# 记忆检索的最小实现
def recall(query, budget_tokens=2000):
    hits = []
    # ① 常驻：核心条目必带
    hits += load_core("MEMORY.md")
    # ② 实体命中：提取专有名词精确匹配文件名
    for ent in extract_entities(query):
        hits += grep_memory_files(ent)
    # ③ 语义兜底：RRF 融合 BM25 + 向量
    hits += hybrid_search(query, top_k=5)
    # ④ 去重 + 按预算截断（关键！）
    return dedup_and_truncate(hits, budget_tokens)

# 预算控制伪代码
def dedup_and_truncate(hits, budget):
    seen, out, used = set(), [], 0
    for h in sorted(hits, key=lambda x: -x.score):
        if h.id in seen: continue
        if used + h.tokens > budget: break
        out.append(h); seen.add(h.id); used += h.tokens
    return out

压缩（compact）：对话变长后的标准动作

策略做法信息损失适用
滑动窗口只保留最近 N 轮大（早期决策全丢）无长期依赖的闲聊
摘要压缩让模型把历史总结成要点中（细节丢）最常用
分层压缩早期重度摘要 + 近期原文小长任务推荐
结构化抽取只保留决策/待办/约定中（过程丢）工程类对话

推荐做法：触发阈值设在上下文占用 50 – 60%，压缩时保留 ① 最近的 3 – 5 轮原文 ② 之前所有的决策与待办摘要 ③ 关键代码片段（原文保留）。压缩后立刻写一份到当天的记忆日志，防止摘要本身丢失。

深入自检

记忆文件和 RAG 有什么区别？

RAG 是检索外部知识库（文档、网页），记忆系统是检索自身经历（之前说过什么、做过什么）。关键差别：记忆是增量写入的（对话产生新记忆），而知识库通常是静态导入的。所以记忆系统必须解决 写入时机、去重、遗忘 三个 RAG 不用管的问题。

长期记忆会不会越写越乱？

会，这是所有记忆系统的头号难题。三种治理手段：① 结构化——强制用固定模板/条目化，别写散文；② 定期合并——把多条相关记忆聚合成一条（类似数据库的 compaction）；③ 冲突解决——同一事实的最新版本覆盖旧版本，冲突时保留两条并标注时间。不做这三件事，几千条记忆后会检索出大量互相矛盾的条目。

为什么要把日志和 MEMORY.md 分开？

因为二者访问模式完全不同：MEMORY.md 是每次都要读的高价值索引，必须小而准；日志是偶尔回溯的原始流水，量大但访问少。混在一起会导致 MEMORY.md 膨胀，每轮对话都被迫消耗大量 token 读一堆用不到的流水账。

记忆系统怎么评估效果？

看三个指标：① 召回率——该想起来的事有没有想起来（构造测试：过 N 轮后问之前的约定）；② 精确率——注入的记忆是否与当前任务相关（不相关记忆会干扰）；③ token 成本——每轮平均注入多少。理想状态是高召回 + 高精确 + 低开销，三者冲突时优先保召回（漏掉关键信息比多读几百 token 更糟）。
