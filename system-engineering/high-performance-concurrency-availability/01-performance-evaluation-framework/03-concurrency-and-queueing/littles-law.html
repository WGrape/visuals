Little 定律：QPS = 并发数 ÷ 耗时？

对，但分子必须是同一观测边界内的平均未完成请求数，分母是请求在该边界内的平均停留时间。这是一条统计关系，不是性能魔法。

先把三个字母翻译过来

L = λ × W　→　λ = L ÷ W
L · 个测量窗口中系统内的平均请求数；不是单个时间点的峰值，也不必然等于线程数。
λ · 次/秒请求流过选定边界的平均速率；稳态时到达≈完成，求吞吐应使用完成速率。
W · 秒每个请求在同一个边界中的平均停留时间；可能含队列，也可能只含业务处理。

量纲检验：(次/秒) × (秒/次) = 个在途请求。若 W 是毫秒，计算前先除以 1,000。

为什么它成立？看「请求占用的时间面积」

  1. 在一段足够长且负载相对稳定的时间 T 内，平均有 L 个请求待在系统里；总占用约为 L × T（请求·秒）。
  2. 这段时间约完成 λ × T 个请求，每个在系统里平均待 W 秒；总占用也约为 λ × T × W。
  3. 两边代表同一批请求在同一边界内占用的总时间，因此 L × T ≈ λ × T × W，消去 T 得 L = λW。

测量窗口边缘会有未完成请求；窗口足够长、系统无持续无限积压时，边缘影响通常相对变小。定律不要求请求时间服从某种特定概率分布。

生活例子 → API

奶茶店

店内平均 20 位顾客（包含等候和制作），从进门到拿到饮料平均 5 分钟，稳态每分钟完成约 20 ÷ 5 = 4 单。若只数制作台上的订单，就只能除以「在制作台停留的时间」。

HTTP 接口

客户端发出后到收到完整响应平均有 200 个未完成请求，端到端平均耗时 1 秒，稳态完成速率约 200 次/秒。此时 W 若含网关等待，L 也须含等在网关的那些请求。

同为 100 QPS，为什么在途数不同？

设两种独立的稳态情境都在同一客户端调用边界内每秒完成 100 次请求，且无持续积压；取该边界内每次调用的平均耗时，而不是某次最慢耗时：

平均耗时 0.2 秒

100 × 0.2 = 20

时间平均约有 20 个未完成调用。

平均耗时 2 秒

100 × 2 = 200

时间平均约有 200 个未完成调用。

变慢十倍而完成速率保持不变，平均在途量就变为十倍；但这不是“设 200 个并发就能获得 100 QPS”。增加负载可能让排队更长、完成速率下降。此处的 20 / 200 是窗口内时间平均，不是某一瞬间的值；压测命令的 -n 500 是总请求量，-c 30 是客户端并发目标，两者也都不是公式中实测的 L。看 500 次、并发 30 的压测例子。

自己算一次（稳态示意）

完成速率约 200 次/秒

两个输入量独立给定；改变在途量后 W 可能随排队与资源竞争改变。本工具不模拟瓶颈、峰值或账户限额。

三个最容易算错的地方

  • 把峰值当平均：「最多 4,000 个同时处理」是容量描述，不是已测得 L=4,000；只有长期实际占满且边界一致时才可代入平均值。
  • 把客户端 RT 除以业务层 L：客户端 RT 含网络、网关排队等；业务层 L 不含它们，结果不再是业务完成速率。看两种正确的统计边界。
  • 当成容量上限公式：λ 由真实完成量测得，W 会随负载变化。若 CPU 只能稳定完成 1,000 次/秒，不会因多开请求就无限提高 QPS；继续加负载常使队列和 W 变大。

工程上怎么用

测得稳定完成 QPS 为 500 次/秒、客户端同口径平均 RT 为 0.4 秒，则客户端平均在途量约 500 × 0.4 = 200 个。这有助估算一个起点，而非保证设 200 协程即可达到 500 QPS；还要观察速率限额、连接池、服务能力、错误率和 P95/P99。到达 QPS、准入 QPS、完成 QPS 与成功 QPS 的口径不能混用。

为什么它成立：看时间轴上的面积

利特尔法则不需要排队论推导，用一张面积图就能理解：把每个请求在系统中的停留画成一根竖条，阴影部分的总面积既等于「吞吐 × 平均停留时间」，也等于「平均在途数 × 时长」，两边相等，法则就得出来了。

L = λ × W 的直观来源：同一个面积，两种算法
L（在途数）系统内部正在处理的请求数量，是状态量
λ（吞吐）单位时间完成的请求数，是速率量
W（停留时间）一个请求从进到出的平均时间，是时间量
成立条件稳态：长期看进去的和出来的数量相等，不要求分布形态

这条法则的力量在于它几乎不需要假设：不管请求怎么来、服务怎么排队、分布有多怪，只要系统没有长期堆积，它就成立。这也是它能成为容量估算地基的原因。

三个字母最常见的误解

容易搞错的点错误理解正确理解
吞吐用哪个值用峰值 QPS 代入必须用同一稳态区间内的平均吞吐
延迟用哪个值用 P99 或平均值随意代入公式里是平均停留时间，代入口径必须一致
在途数怎么数只算正在 CPU 上跑的包含排队中的、等 IO 的，只要在系统内都算
稳态前提任何时刻都成立瞬时值会波动，只有足够长的时间平均后才成立
系统边界随便划定边界一改，L、λ、W 三个值同时变，必须固定边界
因果方向提高并发就能提高吞吐并发是结果也是约束，吞吐上限由最慢环节决定

边界一致是前提

如果你算的 L 是「整个服务」，而 W 只算了「数据库查询时间」，那三个量不在同一个边界内，公式必然对不上。每次用公式前，先画一个框，明确框住了什么。

它不能告诉你为什么慢

利特尔法则是恒等式，不是因果模型。它能算出「在途有多少」，但不能告诉你慢在哪里。想知道原因，还得看排队分解与资源饱和度。

工程上的四种用法

把它当成一个代数式用，知道任意两个量就能求第三个。下面四个是最常见的场景，几乎覆盖日常容量讨论。

# 用法一：已知并发与耗时，估算吞吐上限 QPS_max = 并发上限 / 平均耗时 # 200 / 0.05s = 4000 # 用法二：已知目标 QPS 与耗时，反推需要多少并发 需要并发 = 目标QPS * 平均耗时 # 4000 * 0.05s = 200 # 用法三：已知在途数与吞吐，反推真实平均耗时 实际耗时 = 在途数 / 吞吐 # 100 / 1000 = 0.1s # 用法四：给线程池定大小（CPU 密集 vs IO 密集） # CPU 密集：线程数 ≈ 核数，再多只是增加切换 # IO 密集：线程数 ≈ 核数 * (1 + 等待时间/计算时间) N_threads = cores * (1 + wait_time / cpu_time) # 一个直观例子： # 8 核，平均每次请求 CPU 5ms、等待下游 45ms # N = 8 * (1 + 45/5) = 8 * 10 = 80 个线程 # 对应吞吐上限 = 80 / 0.05s = 1600 QPS

深入自检：把公式用对的六个问题

为什么我算出来的值和监控对不上？

九成是边界或口径不一致：监控里的 QPS 可能是网关层的，而在途数统计的是服务层的；或者耗时只算了业务逻辑，没算排队。先把三个量统一到同一个边界和同一段时间，再比对。

并发数和线程池大小是一回事吗？

不完全是。利特尔法则里的并发是「系统内的请求数」，线程池大小是「同时能处理的请求数上限」。当系统未饱和时，在途数小于线程数；饱和后，多出来的请求在队列里等待，在途数会超过线程数。

提高并发一定能提高吞吐吗？

在未饱和区间可以，接近饱和后就不行了。并发超过系统处理能力时，多出来的请求只是在排队，吞吐不再增加，而延迟会线性增长。这也是为什么压力测试要找膝点而不是找峰值。

排队时间和处理时间怎么分开看？

用利特尔法则可以拆：总停留时间 W = 排队时间 + 服务时间。如果能测到服务时间（比如业务内部计时），那么 W 减去它就是排队时间。排队时间占比高，说明容量不足；服务时间占比高，说明代码或下游慢。

开环和闭环模型下公式还成立吗？

成立，但含义不同。闭环模型（固定并发）下吞吐与耗时互相制约；开环模型（固定到达率）下如果到达率超过处理能力，系统会无限堆积，这时不存在稳态，公式也就失效了——这本身就是一条有用的判断。

为什么还要看分位数？

因为公式只约束平均值。平均耗时正常但 P99 很差，说明长尾问题严重，平均值完全看不出来。平均值用于容量计算，分位数用于体验判断，两者都要看。
