编程范式：过程式、面向对象与函数式

三种看待问题的方式。它们不是互斥的阵营，而是同一个工具箱里的不同工具。

是什么

范式是「组织代码的思维方式」

编程范式不是语法特性，而是看待和分解问题的方式：程序是由「一步步指令」构成，还是由「相互作用的对象」构成，还是由「函数的组合」构成。

📋
过程式 / 指令式
按步骤修改状态：变量、循环、条件
🧱
面向对象 OOP
把数据与行为封装成对象，靠消息传递协作
🔗
函数式 FP
把计算看成函数组合，强调不可变与无副作用
现代语言多是「多范式」：Go 偏过程式但支持一等函数与接口；Python/JS 都能写 OOP 也能写 FP；Scala/Rust 更是显式融合。范式是工具箱，不是阵营。

三种范式的核心差异

函数式要点

函数式最值得借鉴的三件事

🧊
不可变
数据创建后不再修改，避免共享可变状态带来的并发问题
🧪
纯函数
相同输入必得相同输出、无副作用 → 易测试、易推理、易缓存
🔗
声明式与组合
用 map/filter/reduce 表达「要什么」而非「怎么做」，代码更短更清晰
// 指令式：描述「怎么做」，引入中间变量与可变状态
let result = [];
for (let i = 0; i < users.length; i++) {
    if (users[i].active) result.push(users[i].name);
}

// 声明式：表达「要什么」，无中间状态
const result = users.filter(u => u.active).map(u => u.name);
实践

实际项目里怎么选

  • 业务实体建模 → 面向对象直观（订单、用户、库存各有状态与行为）。
  • 数据转换与流水线 → 函数式的 map/filter/reduce 更清晰、更少 bug。
  • 底层与性能敏感路径 → 过程式最可控。
  • 并发密集 → 优先不可变数据、减少共享状态（Go 的「用通信共享内存」也是同一思路）。
不要为了范式而范式。强行把简单逻辑写成纯函数链，或为了「面向对象」给每个数据结构都配一层类，都会让代码更难读。范式服务于可读性与可维护性。
面试问答

高频问题

Q1：面向对象和面向过程的区别？
面向过程按步骤组织代码，关注「怎么做」，数据与操作分离；面向对象把数据与行为封装成对象，通过对象协作完成功能，更利于建模复杂业务与隔离变化。
Q2：什么是纯函数？有什么好处？
相同输入必定产生相同输出、且不产生可观察副作用的函数。好处是易测试、易推理、可缓存、可安全并发执行。
Q3：为什么函数式更适合并发？
因为它强调不可变数据与无副作用，消除了共享可变状态，从根上减少了数据竞争，因此不需要大量加锁也能安全并发。
Q4：不可变数据有什么代价？
每次「修改」都要创建新副本，可能带来额外的内存分配与 GC 压力。实践中常用结构共享（持久数据结构）或只在必要处使用不可变。
Q5：声明式和命令式有什么区别？
命令式描述执行步骤（怎么做），声明式描述目标结果（要什么）。声明式通常更简洁、更少中间状态错误，如 SQL、map/filter/reduce。
