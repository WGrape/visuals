gRPC、HTTP/2 流与 Deadline：一次 RPC 超时之后发生了什么

用订单调用库存服务解释 protobuf 消息帧、四种调用模式、截止时间和取消传播。

RPC 把网络调用包装成方法

调用方写 `Reserve(item, count)` 看起来像本地函数，实际上客户端要序列化请求、建立或复用连接、经网络送到服务端、等待处理并反序列化响应。gRPC 常以 Protocol Buffers 描述服务与消息，基于 HTTP/2 流承载 RPC。一个 TCP 连接可同时有多个 HTTP/2 流，但它们仍共享 TCP 的拥塞与丢包影响。RPC 的类型定义提高接口一致性，却不能让网络延迟和部分失败消失。

服务定义应区分必填业务语义、字段默认值与兼容演进。新增字段通常可让旧客户端忽略，但删除或重用字段编号可能造成数据误解。线上的请求与响应还可能经过代理，代理是否完整支持 HTTP/2、trailers 与流式传输会影响调用。

四种调用形态

一元 RPC 是一次请求对应一次响应；服务端流允许一次请求逐条接收多个响应；客户端流允许持续发送多个消息后得到响应；双向流可双方独立连续发送。流式并不意味着一次发完所有数据才交付，也不保证应用不会因背压而暂停。每个流上消息有边界和顺序，服务要定义中断后是否可恢复，以及已经处理到哪条消息。

例如上传库存变更流中途断线，客户端不能仅凭“没收到最终响应”断定所有记录都未生效。应使用业务序号、批次 ID 或幂等键，服务端能查询已提交进度。网络层可靠字节流不等于整个流式业务具有原子性。

Deadline 是总预算

订单接口剩余 600 毫秒，调用库存服务时应传递一个到期时间或剩余预算。库存服务还要访问数据库，不能再无条件给数据库完整的 600 毫秒，否则整条链路会越过用户截止时间。gRPC deadline 到达后客户端可取消等待并收到 DEADLINE_EXCEEDED，但服务端可能已开始甚至已提交业务操作；取消信号不具备“撤销数据库事务”的魔法。

如果客户端没有设置 deadline，依赖故障时调用可能等待太久；若设得比正常 P99 还短，会制造大量伪故障。应按端到端目标、网络延迟、后端处理和排队留预算，并分场景测分位数。调用链每层重新设相同超时是常见错误。

状态码与 HTTP 状态不是一回事

gRPC 应用状态常通过 gRPC status 和相关 trailers 表达，HTTP/2 状态为 200 并不保证业务 RPC 成功。反向代理若不支持 trailers 或意外把 gRPC 请求转成普通 HTTP/1.1，客户端可能得到难解释的协议错误。监控要记录 gRPC 方法、应用状态、HTTP/2 连接错误、流重置与超时来源，而不是只看网关 HTTP 200 比例。

服务端抛出异常时应映射成明确的业务或系统状态，避免把权限错误、参数错误都伪装为 UNAVAILABLE。调用方据此决定是否重试，但重试规则仍要看方法是否幂等和是否可能已经提交。

重试与透明性边界

读取库存可在短暂不可用时按预算重试，预留库存则必须有业务幂等标识。即使 gRPC 客户端库支持自动重试，也不能把“请求发出后响应丢失”变成安全重复写入。客户端需限制次数、退避和总 deadline，并记录每次 attempt；后端需以事务或唯一约束保证重复请求不重复扣减。

流式 RPC 更复杂：断线后恢复时，已经发送但未确认的消息处于未知状态。设计显式的应用层进度确认，比简单从头重播整个流更可靠。若需要严格一次处理，必须说明存储、去重和故障恢复语义。

负载与背压

HTTP/2 有连接和流级流量控制，gRPC 客户端与服务器框架也会限制缓冲和并发流。生产者持续发送而消费者处理慢时，写入可能阻塞或占用越来越多内存。应限制每条消息大小、每连接并发、服务端工作队列，并观察窗口阻塞、队列长度与消息处理耗时。流式接口不天然比批量 API 更省内存。

长连接经负载均衡时，按连接数平均不一定按 RPC 请求数平均；一个热客户端可能在一条连接上发很多调用。选路与扩容要看方法级 QPS 和服务端负载，而不只是 TCP 连接数。

故障实验

模拟库存服务处理 700 毫秒、订单仅剩 600 毫秒：观察客户端超时、服务端是否收到取消、数据库是否已经提交、订单如何查询最终状态。再测试代理丢 trailers、HTTP/2 流重置和慢消费者，确认监控能区分协议错误、应用错误与 deadline。把“调用像函数”还原成真实网络时间线，才能设计可靠的 RPC。

验收还要比较一次一元调用与长流连接在代理切换时的行为。前者可重建单次请求，后者需要确认已经处理的消息位置，并核对背压和取消是否沿整条链路传播。

自检

gRPC 客户端收到 DEADLINE_EXCEEDED，能证明库存服务没有提交吗？

不能。超时只说明客户端未在期限内得到成功结果，服务端可能已执行；应查询业务状态或用幂等键重试。
