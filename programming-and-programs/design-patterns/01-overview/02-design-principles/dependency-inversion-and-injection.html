01 · 原则从问题里长出来

直接写会有什么代价？

订单服务直接构造某支付 SDK，并到处使用 SDK 专有请求与错误码。测试订单规则也必须连真实支付沙箱。

先看问题写法

class CheckoutService {
  pay(order) {
    client = new StripeSdk(secret)
    return client.createCharge({amount_cents: order.total})
  }
}

关键转折

先由业务定义 PaymentPort.charge(amount)。支付供应商的适配器实现它；构造器只接收这个契约。

04 · 把原则写进代码

最小伪代码

interface PaymentPort { charge(amount): Receipt }
class CheckoutService {
  constructor(payment: PaymentPort) { this.payment = payment }
  pay(order) {
    order.ensurePayable()
    return this.payment.charge(order.total)
  }
}
class StripeAdapter implements PaymentPort {
  charge(amount) { return mapReceipt(stripe.charge(toCents(amount))) }
}

从代码中带走三件事

  1. DIP 是依赖方向：业务不依赖具体 SDK。
  2. DI 是传入依赖的做法，不要求引入容器框架。
  3. 端口由业务需要定义，别照搬第三方 SDK 的全部方法。
05 · 原则不是教条

对应哪些模式？什么时候收手？

  • 适配器：把外部接口翻译成业务契约
  • 工厂方法：创建具体实现但消费端只见接口
  • 代理：保持接口并控制访问

不是每个类都需要接口。只有真实的替换边界、外部依赖或测试隔离需求，才值得引入抽象。

依赖注入和依赖倒置是一回事吗？

不是。依赖倒置规定高层依赖抽象；依赖注入是把依赖从外部传入的一种实现手段。
