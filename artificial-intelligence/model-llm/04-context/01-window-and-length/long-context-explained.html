长上下文 Long Context

从「能写 2K」到「能读 100K+ 文档」，长上下文是近三年最卷的方向之一。面试高频问题：上下文长度到底受什么限制？RoPE 怎么外推？KV Cache 为什么吃显存？FlashAttention 省在哪？本节图文讲清。

01为什么需要长上下文

短上下文（如 2K/4K）只能处理单轮对话或短文档；长上下文让模型直接「一口气读完整本书、整个代码仓库、整段对话历史」，从而省去复杂的切分与检索。典型场景：长文档问答、代码库级补全、多轮 Agent 记忆、整本法律/医学卷宗分析。

📄 长文档理解

一次性塞入论文、报告、合同，避免 RAG 切片的召回偏差。

💻 仓库级编码

把整个项目作为上下文，跨文件推理依赖与调用链。

🧠 长程记忆

Agent 把历史轨迹放进上下文，替代外部记忆存储。

注意权衡：长上下文 ≠ 一定更好。越长越贵、越易「中间遗忘」（lost in the middle），许多任务上 长上下文 + RAG 混合 才是性价比最优解。

02位置编码与「外推」难题

Transformer 本身对序列长度没有先验——是位置编码把「第几个 token」注入模型。问题来了：训练时最多见过 4K 长度，推理时给 32K，模型能认得出「第 30000 个位置」吗？这就是长度外推（extrapolation）问题。

绝对位置编码

每个位置一个学习向量，长度写死，几乎无法外推——超出训练长度直接没见过。

RoPE（旋转位置编码）✅

用旋转把位置信息编码进 Q/K，相对位置可在注意力的点积中自然表达，是当前主流（LLaMA / Qwen / DeepSeek）。

RoPE 外推的核心思路：不硬撑到没见过的远距离，而是「缩放/插值」让推理时的位置分布尽量贴近训练分布。

PI（Position Interpolation）

把位置下标线性缩放 x → x·L_train/L_infer，把推理位置「压」回训练区间内。简单有效，但短距离分辨率下降。

NTK-aware / YaRN

不缩放所有频率，而是对不同频率分量区别处理（高频少动、低频多补），兼顾外推与局部精度；YaRN 是主流增强版。

03注意力复杂度与 KV Cache 显存

这是长上下文的物理瓶颈。设序列长度 n、头维度 d、层数 L、头数 h：

计算复杂度

自注意力对每个 token 都要和前面所有 token 算点积 → O(n²·d)。n 翻倍，算力约翻 4 倍。

显存（KV Cache）

每生成一个新 token，都要缓存之前所有 token 的 K、V。缓存量 ≈ 2·n·L·h·d·bytes，随 n 线性增长，但长上下文时这往往比权重还占显存。

一句话：算力吃在「算」上（O(n²)），显存吃在「存」上（O(n) 的 KV Cache）。长上下文之所以贵，是两个瓶颈叠加。

04高效注意力：怎么把 O(n²) 降下来

MQA / GQA ✅

多查询（MQA）让所有头共享一组 K/V，分组查询（GQA）折中。KV Cache 显存直接降数倍，是长上下文落地的必选项。

FlashAttention

不把巨大的注意力矩阵物化到显存，而是分块在 SRAM 上算、只写回最终结果。省显存 + 提速，且数值等价。

滑动窗口 / 稀疏

每个 token 只关注附近窗口或关键 token（如 Mistral 的滑动窗口、StreamingLLM 的「注意力汇聚」）。牺牲全局但换长度。

线性注意力

用核技巧把 softmax 重写，复杂度降到 O(n)；代价是表达力弱于 softmax，多用于超长序列辅助。

落地结论：现实长上下文模型几乎都是 RoPE 外推 + GQA + FlashAttention 三件套打底，再叠加窗口/稀疏等策略。

05长文本训练策略

直接拿 4K 模型去训 128K 数据，既贵又难收敛。常见「分阶段」做法：

  • 继续预训练（ continual pretrain ）：用长文档数据，在已有短模型上继续训，让模型适应长序列分布。
  • 序列并行 / Ring Attention：把超长序列沿设备切分，用环形 all-gather 跨卡算注意力，突破单卡显存上限。
  • 阶段式长度课程：8K → 32K → 128K 逐步加长度，配合位置编码插值，稳定且省算力。
  • 数据配比：长文本数据稀缺，需合成「书本/代码库/长对话」样本，并控制短数据比例防止遗忘。

06推理与工程优化

PagedAttention（vLLM）

像操作系统分页一样管理 KV Cache，把不连续的显存块拼起来，消除碎片，吞吐大幅提升。

KV Cache 量化

把 K/V 从 FP16 压到 INT8/INT4，显存直接减半或更多，几乎不掉点。

投机解码

小模型先「猜」多步、大模型一次验证，缓解长上下文下逐 token 慢的问题。

上下文压缩 / 召回

对过长历史做摘要或检索式裁剪，只把相关片段送进上下文（与 RAG 互补）。

07面试速记卡

瓶颈两套

算力 O(n²)（算）+ KV Cache O(n)（存），长上下文贵在两者叠加。

RoPE 外推

PI 缩放 / NTK / YaRN，让超训练长度的位置被平滑映射。

三件套

RoPE 外推 + GQA（省 KV）+ FlashAttention（省显存提速）。

并非银弹

「lost in the middle」+ 成本高，长上下文常需与 RAG 混合。

KV Cache 显存：一个能直接套的公式

长上下文真正的成本不是「能不能塞进去」，而是 KV Cache 显存 和 注意力计算量。先会算，再谈方案。

显存与计算量手算

# KV Cache 显存（每 token，不含模型权重）
#   bytes/token = 2(K和V) x layers x kv_heads x head_dim x dtype_bytes
#
# 例：Llama-3-8B 配置：32 层、kv_heads=8(GQA)、head_dim=128、FP16(2 bytes)
#   = 2 x 32 x 8 x 128 x 2 = 131072 bytes ≈ 128 KB / token
#
#   上下文 8K  -> 1.0 GB
#   上下文 32K -> 4.0 GB
#   上下文 128K-> 16.0 GB     <- 单卡就放不下了
#   再乘 batch：128K x batch=8 -> 128 GB

# 注意力计算量：O(n^2)，n 翻倍计算量翻 4 倍
#   FLOPs ≈ 2 x 2 x layers x heads x head_dim x n^2   (QK^T + AV)
#   prefill 是算力瓶颈，decode 是<b>显存带宽</b>瓶颈（每生成 1 token 要读整个 KV Cache）

# 首 token 延迟(TTFT) 与 每 token 延迟(TPOT)
#   TTFT ∝ n^2（prefill 计算） -> 长文本首字慢
#   TPOT ∝ n   （decode 每步读 KV）-> 越长生成越慢
上下文长度KV Cache（8B/FP16）prefill 相对计算量工程现实
4K~0.5 GB1x单卡轻松
8K~1 GB4x主流默认档
32K~4 GB64x（相对 4K）需 GQA + 高效实现
128K~16 GB1024x必须分页/切分，单卡 batch 要很小
1M~128 GB65536x必须稀疏/检索式，不能全注意力

关键技术词：GQA（ grouped-query attention，多个 query head 共享 K/V head）把 KV Cache 直接降到 1/8；MLA（多头潜在注意力，DeepSeek）再压一个量级；PagedAttention（vLLM）把 KV 按块分配，消除碎片，吞吐提升 2~4 倍。这三项是长上下文能落地的工程基础。

长上下文的能力边界与外推方法

「支持 128K」不等于「128K 范围内都好用」。实测中的两个经典现象决定了你怎么用长窗口。

现象 / 方法说明对你的影响
Lost in the Middle长上下文里模型对开头和结尾记得最好，中间部分召回率显著下降（U 形曲线）重要信息放首尾，不要埋在中间；或显式编号/小标题
大海捞针（Needle in a Haystack）在长文本里插一句无关事实，问模型能不能找回来评估长上下文能力的事实标准，要看热力图而非单点
位置外推（RoPE 外推）训练 4K 直接推理 8K，效果明显劣化不要裸外推
NTK-aware 插值改 RoPE 基频，无需微调即可扩到 2~4 倍成本低，短上下文性能几乎无损
YaRNNTK + 注意力温度校正，少量微调可扩到 8~16 倍开源模型扩窗的主流做法
滑动窗口注意力每层只看局部 w 个 token，多层堆叠扩大感受野计算量 O(n·w) 而非 O(n²)
稀疏 / 检索式只 attend 到检索出来的 top-k 块超长（百万级）唯一可行路径

#   ② PagedAttention（vLLM）：消除碎片，同样显存多开 2~4 倍并发
#   ③ KV Cache 量化（FP8 / INT8）：显存再减半，质量损失很小
  • 不是越长越好：上下文变长会稀释注意力，短任务用长上下文反而准确率下降、成本飙升。实践上是「够用就好 + 检索补充」。
  • 成本是平方级：同样是 10 万 token，一次 10 万的长请求 vs 10 次 1 万的请求，前者 prefill 计算量约 10 倍于后者（O(n²)），但省掉的重复 prompt 可能更贵——要做实测权衡。
  • prefix caching：多轮对话/固定 system prompt 场景下，把不变前缀的 KV 缓存复用，首 token 延迟可降 50%~90%，是投入产出比最高的一招。
  • RAG 和长上下文不是二选一：长上下文适合「信息密度高、需要全局理解」（合同、代码库）；RAG 适合「语料巨大、只需局部命中」（知识库问答）。混合做法：先用 RAG 缩到 20~50K，再交给长上下文模型精读。
为什么模型号称 128K，实际 32K 之后就开始胡说？

两个原因：① 训练分布——模型在训练时见到的大部分样本远短于标称上限，长距离的注意力模式没被充分训练；② Lost in the Middle——位置编码对中间区域的相对距离感知更弱。所以标称长度是「能塞进去」，不是「能可靠使用」。验收方式必须是大海捞针热力图，而不是看宣传数字。

KV Cache 能不能 offload 到 CPU/磁盘？

能，但要算账。PCIe 带宽约 16~32 GB/s，而 HBM 是 2~3 TB/s，差 100 倍。decode 是带宽瓶颈，一旦 offload，每 token 延迟会从 20ms 涨到几百 ms。适用场景只有吞吐优先、延迟不敏感的离线批处理；在线服务基本不用。

怎么判断该上长上下文还是该做 RAG？

看三个数：① 语料总量——超过单次窗口 10 倍以上就必须 RAG；② 命中位置是否可预测——可预测（按用户/按文档）就 RAG，不可预测（要全文找关联）才用长上下文；③ 成本——长上下文每次都要付全部 token 的钱，RAG 只需付检索到的部分。日均请求量大时，RAG 的成本优势是数量级的。
