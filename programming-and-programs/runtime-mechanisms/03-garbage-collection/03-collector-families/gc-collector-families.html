一句话总结：没有"最好"的 GC，只有"最合适"的 GC。核心权衡是吞吐量、停顿时间、内存与 CPU 开销——压低停顿往往要拿吞吐或内存来换。

01为什么有这么多回收器

不同应用对 GC 的要求截然不同：后台批处理要吞吐高（总工作时间多）；交互服务要停顿短（用户不卡）。回收器就是在"尽量少占用 CPU/内存"和"尽量短停顿"之间找不同平衡点，于是演化出不同家族。

02回收器家族对比

回收器方式停顿吞吐适用
Serial单线程回收长（会 Stop-The-World）中小堆 / 单核 / 客户端
Parallel多线程回收长（STW 但快）最高批处理、吞吐优先
CMS并发标记清除较短（并发，但碎片+CPU）较高中低延迟老方案（已退场）
G1分区域增量回收可控（可设停顿目标）高大堆+中低延迟主流
ZGC / Shenandoah并发 relocation亚毫秒（几乎不 STW）略低超大堆+极低延迟
越靠右停顿越短，但往往吞吐/内存代价越高

03核心指标

⏱️ 停顿时间

STW 时长，直接影响延迟；ZGC 可压到亚毫秒。

🚀 吞吐量

花在业务 vs GC 的时间比；Parallel 最高。

💾 内存开销

并发回收要预留空间做转储/并发标记，堆占用更高。

🧮 CPU 占用

并发回收与后台整理消耗 CPU，高负载下要算账。

04怎么选

场景推荐
小堆 / 客户端 / 单核Serial，简单够用
批处理 / 吞吐优先Parallel
大堆 + 中低延迟主流G1（设停顿目标）
超大堆 + 极低延迟ZGC / Shenandoah

05常见误区

  • "低停顿回收器是全能升级"：ZGC/Shenandoah 用更高内存与 CPU 开销换停顿，堆不够大或 CPU 紧张时反而更糟。
  • "GC 调优就是调小堆"：堆太小会频繁 GC，太大则单次回收更慢；要结合停顿目标与对象存活率。
  • "没有 Full GC 就安全"：并发回收失败会退化为 STW 全量回收，需监控并发模式失败。

06常见疑问

G1 怎么做到"可预测停顿"？
G1 把堆切成很多小 Region，优先回收垃圾最多的 Region（Garbage-First），并能在设定的停顿预算内停下，而不是一次性回收整个堆。
ZGC 为什么能亚毫秒停顿？
它用着色指针标记对象状态、用读屏障在访问时完成并发 relocation，几乎不需要 STW 来搬移对象，所以停顿与堆大小基本无关。
为什么 CMS 被淘汰了？
CMS 并发标记清除会产生内存碎片（只能清除不能压缩），碎片到一定程度会触发长时间 Serial Old 全量回收，反而更卡；G1/ZGC 用分区/并发压缩规避了这个问题。

调优要点

旋钮作用
最大堆 -Xmx决定 GC 频率与单次代价，先给够再谈调优
停顿目标（G1/ZGC）设 MaxGCPauseMillis / 软目标，过激会增大 CPU 开销
并发线程数并发回收占用的 CPU，需与业务争抢权衡
触发阈值老年代/Region 占用到多少启动回收
为什么"吞吐"和"停顿"通常只能二选一？

要缩短停顿，就要把更多回收工作并发化、增量化和预留更多空间，这些都会消耗额外的 CPU 与内存；省下这些资源去做并发/增量，吞吐量就上去了但停顿变长。所以选回收器本质是选业务更怕"卡一下"还是更怕"总工作时间少"。

深度补充：GC 回收器选型参数

第一层 · 概念与判定 GC 回收器的核心矛盾是“吞吐 vs 停顿 vs 内存”。判定：延迟敏感选低延迟回收器（G1/ZGC/Shenandoah），吞吐优先选 Parallel，嵌入式/极简选 Serial/Go 三色标记。

回收器典型停顿算法适用
Go 三色标记亚毫秒级并发并发标记 + 混合写屏障Go 默认
G1十到数百 ms分区域增量服务端默认
ZGC亚 10ms 且不清零堆染色指针 + 读屏障大堆低延迟
Shenandoah亚 10ms Brooks 指针 + 读屏障大堆低延迟

第三层 · 排障与边界

  • GC 停顿超 SLA：先调 -Xmx 与回收器，再看对象存活率（是不是缓存泄漏）。
  • Go GC 触发由 GOGC（默认 100，即堆增 100% 触发）控制，可降到 50 换更低延迟、更高 CPU。
  • ZGC 需要 64 位平台与较大预留内存（染色指针占地址位）。
  • 误把“分配速率高”当“内存泄漏”，应先看存活对象而非峰值。
第四层 · 原理与取舍

并发回收器用“运行时与业务线程并发”把停顿拆小，代价是读屏障/写屏障的常驻开销与更高 CPU。染色指针（ZGC）把标记信息塞进指针空闲位，避免对象头改动；Go 的写屏障在混合屏障下同时处理栈与堆，简化并发安全。权衡本质：用 CPU 与内存余量换可预测的短停顿。

实例与速查：GC 参数与验证

# Go：把 GC 触发阈值从 100 调小到 50，换更低延迟、更高 CPU
GOGC=50 ./app

# Java：ZGC 开启（大堆低延迟），注意需要 64 位平台
java -XX:+UseZGC -Xmx32g -jar app.jar

# 观察 Go GC 频率
GODEBUG=gctrace=1 ./app
  • Go GOGC 是“堆增长百分比触发”，调小更频繁但每次工作量更小、停顿更短。
  • ZGC/Shenandoah 适合 8GB+ 堆且延迟敏感，小堆用 G1 更划算。
  • 先抓火焰图确认是“分配/GC”瓶颈，再动回收器，不要提前优化。
FAQ：GC 停顿突然变长？

先看是不是某次大对象分配或一次性的超大堆增长；再查是否关闭了并发（如强制 STW 的某些诊断参数）。ZGC 停顿与堆大小基本无关，若变长通常是 GC 日志/元空间或系统页回收干扰，需结合 pprof 与系统指标看。

常见误区与延伸

  • 误区一：低延迟回收器一定更省 CPU。ZGC/Shenandoah 用读屏障摊薄停顿，常驻开销与峰值 CPU 反而更高。
  • 误区二：GOGC 调小一定更好。调小降低停顿但增加 GC 频率与 CPU，吞吐场景可能反而变慢。
  • 延伸：Go 的辅助 GC（GC assist）会在分配快于回收时让业务协程帮忙标记，所以 GOGC 不是唯一旋钮，分配速率同样关键。
  • 延伸：分代 GC（Go 1.24+ 的实验）用“新生代小范围回收”进一步降低老年代扫描成本，是吞吐与延迟的新平衡点。

一句话总结：回收器选型是“吞吐、停顿、内存”三角权衡，先量瓶颈再定旋钮，别盲信某一项指标。

决策速记

  • 选回收器：低延迟选 ZGC/Shenandoah，吞吐选 Parallel/G1，嵌入选 Serial。
  • 调旋钮：Go 用 GOGC 平衡延迟与频率；JVM 用 -Xmx 与回收器组合。
  • 先量后调：火焰图确认 GC 是瓶颈，再动回收器与参数。
  • 看存活：停顿长先查对象存活率，再怀疑 GC 本身。

横向对比与追问

  • 与 Go 比：Java 的 ZGC/Shenandoah 用读屏障，Go 用写屏障（混合屏障），机制不同但目标同为低停顿。
  • 与 C/C++ 比：后两者常手动管理或引用计数，无 Stop-The-World，但易泄漏与悬垂指针。
  • 追问：为什么 Go 不用分代？历史上为简单与并发，近年实验分代以降老年代扫描成本。
  • 追问：GOGC=off 意味着什么？完全关闭自动 GC，靠手动 runtime.GC()，只适合极特殊场景。

小结：选回收器先看语言生态与停顿预算，再谈算法细节。

收集器选型速记

  • 吞吐优先：Parallel 用多核做 STW 回收，适合离线批处理，单次停顿长但总吞吐高。
  • 延迟优先：CMS、G1、ZGC、Shenandoah 把回收并发化；ZGC/Shenandoah 停顿与堆大小解耦，大堆低延迟首选。
  • 选型口诀：小堆求简单用 Serial；吞吐用 Parallel；可预测停顿用 G1；超低延迟大堆用 ZGC/Shenandoah。
