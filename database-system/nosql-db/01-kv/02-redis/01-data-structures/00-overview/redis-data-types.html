OBJECT ENCODING 与配置

# 查看某个 key 实际用了什么编码（排障与优化的第一步）
127.0.0.1:6379> SET small "hi"
OK
127.0.0.1:6379> OBJECT ENCODING small
"embstr"                          # 短字符串 -> embstr（一次内存分配）
127.0.0.1:6379> SET big "<44字节以上的长字符串...>"
OK
127.0.0.1:6379> OBJECT ENCODING big
"raw"                             # 长字符串 -> raw（两次分配：robj + sds）

127.0.0.1:6379> HSET user name tom age 20
(integer) 2
127.0.0.1:6379> OBJECT ENCODING user
"listpack"                        # 小 hash -> listpack（连续内存，省 5-10 倍）
127.0.0.1:6379> CONFIG SET hash-max-listpack-entries 1    # 强制降级阈值
OK
127.0.0.1:6379> OBJECT ENCODING user
"hashtable"                       # 超阈值 -> hashtable（指针多，内存翻倍）

# 看内存占用（含元数据开销）
127.0.0.1:6379> MEMORY USAGE user
(integer) 96                      # 实际比你想的大得多！

# 相关配置项（redis.conf）
hash-max-listpack-entries 512      # hash 用 listpack 的最大字段数
hash-max-listpack-value  64        # 单字段最大字节
zset-max-listpack-entries 128      # zset 更保守（因为要维护分数）
zset-max-listpack-value   64
set-max-intset-entries    512      # set 全整数时的上限
list-max-listpack-size    -2       # quicklist 每个节点的字节上限

embstr 为什么是 44 字节：Redis 的 redisObject（16 B）+ sdshdr8（3 B）+ 字符串（N B）+ 结尾 \0（1 B），要塞进 jemalloc 的 64 字节分配单元，所以 16 + 3 + N + 1 ≤ 64 → N ≤ 44。超过就得分两次分配（raw），内存碎片和访问次数都增加。

内存开销实测：为什么小 key 特别亏

存储内容直觉大小Redis 实际占用开销倍数
key=user:1 → value=tom约 13 B约 100 – 120 B约 9×
key=user:10086 → 32 B JSON约 50 B约 150 B约 3×
100 万个短 key 的 Hash（listpack）—约 20 – 30 MB—
100 万个短 key 的 String—约 100 – 150 MB5×

开销来自哪：每个 key 都要有 dictEntry（24 B）+ redisObject（16 B）+ sds 头（3 – 9 B）+ key 字符串本身 + 各种指针。短数据场景下元数据能占 50 – 90%。

内存优化三板斧

# 优化手段①：用 Hash 的 listpack 把多个字段压在一起
# ❌ 100 万个独立 String：约 150 MB
SET user:1:name tom
SET user:1:age 20
# ✅ 10 万个 Hash（每个 10 字段）：约 30 MB，省 5 倍
HSET user:1 name tom age 20
# 原理：listpack 是连续内存，省掉了每个字段的 dictEntry + robj

# 优化手段②：key 名尽量短（key 名也占内存！）
SET user_profile_10086_name tom      # ❌ key 就 24 字节
SET u:10086:n tom                    # ✅ 短 key，100 万 key 省 10+ MB

# 优化手段③：整数用 int 编码（0 额外分配）
SET counter 42
OBJECT ENCODING counter   # "int" -> 值直接存在指针位，不分配 sds

# 体检命令
redis-cli INFO memory | grep -E "used_memory_human|mem_fragmentation_ratio"
redis-cli --bigkeys        # 找大 key
redis-cli MEMORY DOCTOR    # 官方诊断建议

转换是不可逆的：一旦因为超阈值转成 hashtable，即使后来删元素也不会变回 listpack。所以如果写入时曾短暂超过阈值（比如批量导入时），需要重写一遍 key 才能恢复紧凑编码。

深入自检

ZSet 为什么同时用跳表和字典？

因为两种操作需求不同：按分数范围查 / 排序需要有序结构（跳表，O(log N) 范围扫描）；按成员查分数需要 O(1) 的 KV 查找（字典）。Redis 让两者共享同一份成员和分数的指针，所以内存只多了一份索引结构，却同时获得了两种能力。这是典型的“用空间换两种时间”。跳表参数：最大层数 32，晋升概率 p = 0.25。

为什么 ZSet 的 listpack 阈值（128）比 Hash（512）小这么多？

因为 ZSet 在 listpack 里要同时存成员和分数，且插入时要按分数排序做插入——这是 O(n) 的内存移动（memmove）。元素越多，插入越慢，所以要更保守。ZSet 的 listpack 是按分数有序的紧凑数组，查找用线性扫描，128 个元素是“扫描成本”与“内存节省”的平衡点。

用 String 存 JSON 还是用 Hash？

看访问模式：整读整写（如缓存渲染好的页面）→ String + JSON，简单且一次 IO；频繁改单个字段 → Hash，因为 String 要“读全量→改→写回”，在多客户端并发下会产生覆盖丢失，而 HSET field 天然是原子的。另外 Hash 在小对象下（listpack）比 String 省内存。

String 的 embstr 在什么情况下被破坏？

只要对值做追加或修改就会转 raw：APPEND 一个字符后，OBJECT ENCODING 就从 embstr 变成 raw，因为 embstr 是只读的（一次分配、连续内存，无法原地扩展）。同理，整数 int 编码一旦 APPEND 也会转 raw。所以计数场景要一直用 INCR（保持 int 编码，零分配）。
