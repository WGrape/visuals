🔄 HBase 读写流程

一次 put 与一次 get/scan 在服务端的完整路径，以及为什么这样设计

写路径（put）

  • 寻址：Client 查缓存的 Region→RS 映射（首次走 ZK + meta 三级寻址）
  • 发请求：把 put 发给目标 Region 所在的 RegionServer
  • 加行锁：对该 rowkey 加行级写锁，保证行内原子
  • 写 WAL：追加到 HLog（HDFS 顺序写），默认 SYNC_WAL 刷盘
  • 写 MemStore：按 key 有序插入内存跳表
  • 释放锁 + 返回：客户端收到成功
  • 异步 flush：MemStore 达 128MB → 后台刷成新 HFile

    • 写路径的三种持久级别

    WAL 级别行为性能风险
    USE_DEFAULT / SYNC_WAL写入并刷到 HDFS慢最安全（默认）
    ASYNC_WAL异步刷盘快宕机可能丢最后若干条
    SKIP_WAL完全不写 WAL最快RS 宕机必丢，仅用于可重建的批量导入

    读路径（get / scan）

    HBase 读取要合并多个来源并挑出正确的版本，这是 LSM 结构的固有复杂度。

  • 查 MemStore（最新的未刷盘数据）
  • 查 BlockCache（内存中的热 data block）
  • 对该 Store 的每个 HFile：先问 BloomFilter「有没有这个 rowkey」，没有就跳过
  • 有的话：读 Trailer → 内存中的 Index → 定位 Data Block → 读入（并放入 BlockCache）
  • 把所有来源的结果放进一个最小堆做归并（类似多路归并排序）
  • 按 (key, 列, 时间戳倒序) 依次弹出，跳过被墓碑标记的和超过 VERSIONS 数量的
  • 过滤列族/列、应用 filter，返回给客户端

    • scan 的两个隐形陷阱

    ① 缓存行数（caching）

    客户端每次 RPC 默认只取 100 行（hbase.client.scanner.caching）。扫 100 万行就是 1 万次 RPC。批量扫描要把它调到 500~1000。

    但别调太大：一次取太多会长时间占用服务端资源并吃客户端内存。

    ② 大 scan 要关 BlockCache

    全表扫描会把 BlockCache 里真正的热数据全部挤掉（缓存污染）。用 setCacheBlocks(false)，扫描走独立的扫描路径。

    写缓冲与批量提交

    // Java API：批量写推荐姿势
Table table = conn.getTable(TableName.valueOf("user"));
table.setAutoFlushTo(false);          // 关闭自动 flush（老 API）
table.setWriteBufferSize(6 * 1024 * 1024);  // 缓冲 6MB 再批量提交

List<Put> puts = new ArrayList<>();
for (...) { puts.add(new Put(rowkey).addColumn(...)); }
table.put(puts);                       // 一次 RPC 提交一批
table.flushCommits();                  // 显式提交剩余

// BufferedMutator（新 API，推荐）
BufferedMutatorParams params = new BufferedMutatorParams(TableName.valueOf("user"))
    .writeBufferSize(6L * 1024 * 1024);
BufferedMutator mutator = conn.getBufferedMutator(params);
mutator.mutate(puts);
mutator.flush();
    💡 三个写入优化：①批量 put（减少 RPC）；②按 rowkey 排序（提高 Region 缓存命中）；③批量导入用 BulkLoad（直接生成 HFile 绕过 WAL 与 MemStore，最快且不产生写放大）。

    BulkLoad：绕过写入路径

  • 用 MapReduce / Spark 按 HBase 格式直接生成 HFile
  • 调用 LoadIncrementalHFiles 把 HFile 直接搬到 Region 目录
  • Region 立即可见新数据

    • 优点：不写 WAL、不占 MemStore、不触发 flush 与 compaction，对在线集群几乎零影响。适合离线批量导入、数据迁移、初始化。缺点：不实时、需要额外计算资源。

    🎯 常见问法与答题要点

    Q：为什么 HBase 写入快但读取相对慢？

    A：写入快是因为 LSM 把随机写变成顺序写：只做一次 WAL 顺序追加 + 一次内存插入，没有随机磁盘 IO 和页分裂。读取慢是因为一次读要合并多个来源（MemStore + 多个 HFile），文件越多越慢（读放大）。这是典型的「写优化换读性能」的权衡，靠 BloomFilter、BlockCache、Compaction 三件套来补。

    Q：put 是同步还是异步？返回成功代表落盘了吗？

    A：返回成功代表：WAL 已 sync 到 HDFS + 数据已在 MemStore。注意数据还没有变成 HFile。不过这不影响持久性——即使 RegionServer 立刻宕机，重启后重放 WAL 就能恢复。所以默认配置下 put 返回成功 = 数据不会丢。

    Q：SKIP_WAL 能不能常用？

    A：不能。跳过 WAL 意味着数据只在 MemStore 里，RegionServer 一挂，所有未 flush 的数据永久丢失（MemStore 在内存，进程死了就没了）。它只适合可重建的批量导入（数据还有源头，丢了大不了重跑）。批量导入更推荐 BulkLoad，比 SKIP_WAL 更快更安全。

    Q：scan 很慢，怎么排查？

    A：按顺序检查：①是否走 rowkey——不带 STARTROW/STOPROW 的全表 scan 必然慢；②caching 是否太小——默认 100 行/RPC，扫百万行要上万次 RPC，调到 500~1000；③是否指定列族/列——不指定会读所有列族的所有文件；④是否开了 BlockCache——大 scan 要 setCacheBlocks(false) 避免污染缓存；⑤文件数是否过多——看是否需要 compaction；⑥用 Filter 在服务端过滤，别在客户端全量拉回再过滤。

    Q：get 和 scan 的区别？get 是不是更快？

    A：get 本质是「限定到单行 rowkey 的 scan」，实现上就是 STARTROW=STOPROW=该 key 的 scan。因为能精确定位到一个 Region 的一个位置，所以肯定比范围 scan 快得多。设计上应该尽量让查询变成 get 或小范围 scan——这就是 rowkey 设计的重要性。

    Q：为什么 scan 要关掉 BlockCache？

    A：避免缓存污染。BlockCache 是 LRU，一次全表扫描会把上百万个 block 塞进缓存，把真正的热数据（比如最近活跃用户）全部挤出去，导致线上点查性能断崖下跌。所以离线/全量扫描必须 scan.setCacheBlocks(false)，让这次扫描不写缓存。

    Q：批量导入千万行数据，最快的方式是什么？

    A：BulkLoad。它绕过整个写入路径：用 Spark/MapReduce 直接按 HFile 格式生成文件，再用 LoadIncrementalHFiles 直接挂到 Region 目录下。不写 WAL、不进 MemStore、不触发 flush/compaction，对在线集群几乎零影响，速度通常比逐条 put 快一个数量级。缺点是数据不是实时的，需要额外跑一个计算任务。

    Q：setAutoFlushTo(false) 有什么风险？

    A：关闭自动 flush 后 put 会先攒在客户端缓冲区，攒够 writeBufferSize 才真正发出去。风险是：进程崩溃时缓冲区里的写入会丢（还没发出去）。所以必须在关键节点显式 flushCommits()。另外缓冲区太大会吃客户端内存，一般 2~6MB 比较合适。
