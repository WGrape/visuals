定位

解释器在做什么

解释器读入程序（源码、AST 或字节码），直接执行其语义而不先翻译成机器码。它是「边读边做」，编译器是「先翻好再跑」。

🌳
树遍历解释器
直接在 AST 上递归求值，最简单
📜
字节码解释器
先把 AST 编译成字节码，再循环解释执行
⚡
JIT 混合
解释执行 + 热点代码编译为机器码
形态一

树遍历解释器：最直接也最慢

// AST 节点：Binary(左, 操作符, 右)
func Eval(node Node, env Env) Value {
    switch n := node.(type) {
    case *Number:   return n.Value
    case *Binary:
        l := Eval(n.Left, env)
        r := Eval(n.Right, env)
        switch n.Op {
        case "+": return l + r
        case "*": return l * r
        }
    }
}
为什么慢：每次求值都要遍历树节点、做类型判断与动态分派；同一段代码执行一万次就要遍历一万次。对 for 循环体这种热点非常吃亏。
形态二

字节码解释器：先编译成紧凑指令

把 AST 先「压平」成线性指令序列，再用一个循环逐条 dispatch——避免反复遍历树。

; 源码：a = 1 + 2
PUSH 1
PUSH 2
ADD          ; 弹出两个，压入结果
STORE a      ; 存到变量 a
风格指令形态代表特点
栈式PUSH/ADD，操作数在栈上JVM、CPython指令紧凑、易移植；但指令数多
寄存器式ADD r1, r2, r3Lua 5、Dalvik指令少、访存少；指令更宽
dispatch 优化：简单的 switch dispatch 开销大。常见优化有「直接线程代码（direct threading）」——把跳转地址直接内联在指令数组里，减少分支预测失败。
形态三

向 JIT 演进：解释 + 热点编译

关键思想：不要一上来就编译所有代码（编译很贵），而是只对真正跑得多的代码付编译成本。这也是「启动快」和「峰值性能」能兼得的原因。

面试问答

高频问题

Q1：解释器和编译器的本质区别是什么？
解释器直接执行程序的语义（边分析边执行），不产出独立的机器码；编译器先把程序翻译成机器码（或字节码），再由硬件或虚拟机执行。前者启动快、运行慢，后者启动慢、运行快。
Q2：树遍历解释器为什么慢？
每次执行都要递归遍历 AST 节点并做动态类型判断；重复执行的代码无法复用分析结果，热点代码尤其吃亏。
Q3：栈式字节码和寄存器式字节码的区别？
栈式用操作数栈传递中间结果（如 PUSH/ADD），指令紧凑、易移植，但指令条数多；寄存器式在指令里显式指定寄存器（如 ADD r1,r2,r3），指令更少、访存更少，但指令更宽。JVM 是栈式，Lua 5 是寄存器式。
Q4：JIT 是怎么决定编译哪些代码的？
通过计数器统计方法调用次数与循环回边次数，超过阈值即判定为热点并触发编译。这是分层编译的基础。
Q5：什么是去优化（deoptimization）？
JIT 基于运行时假设（如某调用点总是同一类型）做投机优化；当假设被破坏时，需要丢弃已编译代码、恢复到解释执行的状态继续执行，保证语义正确。
Q6：「Python 是解释型语言」这个说法准确吗？
准确的说法是「CPython（Python 的主流实现）是字节码解释器」。语言规范本身不规定实现方式，Python 也有 PyPy 这类带 JIT 的实现。区分「语言」与「实现」很重要。
