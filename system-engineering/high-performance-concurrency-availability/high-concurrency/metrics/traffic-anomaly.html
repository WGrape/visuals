流量异常全景图谱

流量突刺、洪峰、热点、缓存击穿、重试风暴、惊群、DDoS……把所有「流量不对劲」的情况一次讲清

00 先搞清楚：什么是「流量异常」

所谓流量异常，就是系统实际承受的流量，在大小、分布、时序上明显偏离「正常基线」——既可能是来得太猛（突刺），也可能是来得不均（热点），还可能是来得不是时候（缓存同时失效）。

每个系统都有一条由容量规划决定的基线流量曲线（baseline）：平时就这么高，早晚有起伏，大促会抬高整体水位。异常不是「超过基线」这么简单——骤降、倾斜、抖动同样是异常，因为它们都意味着「系统正在偏离你预期可控的状态」。

流量曲线偏离基线带，即进入「异常」区间

💡 为什么工程师要专门研究流量异常？ 因为系统往往是按「基线 × 安全系数」设计的。一旦流量以某种意想不到的方式偏离，单点瓶颈、级联雪崩、数据错乱就会接踵而至——而它们的成因和解决手段完全不同。下面这张分类框架，就是为了让你「看到异常 → 能立刻归类 → 知道该上哪套武器」。

  • 量级异常：总量或瞬时量偏离基线（最常见于大促、爆款、故障重试）。
  • 分布异常：总量没超，但「谁在打」失衡——一个点被打爆，其余很闲。
  • 时序/行为异常：量也许正常，但节奏或成分不对（缓存同时过期、慢调用堆积、机器流量）。

💡 一个异常常常横跨多个维度。例如「秒杀」既是量级异常（瞬时洪峰），又是分布异常（单商品热点）。分类的意义不是贴标签，而是帮你同时把多套应对手段叠加上去。

02 维度一 · 量级异常：流量「来太猛」

流量突刺 / 流量尖刺Traffic Spike / Surge

在极短时间内（秒级到分钟级）出现远超基线的尖峰，随后迅速回落。典型如：一条爆款内容突然刷屏、明星官宣引发瞬时涌入、某定时任务（如缓存集中过期）到点同时重算。

典型场景热点事件引爆、定时 TTL 到点、秒杀开始的 0.1 秒
核心成因外部不可控刺激 + 内部同步行为（如同一时刻过期）
主要危害瞬时压垮线程池/连接池，触发连锁拒绝
关键指标QPS 瞬时尖峰、P99 RT 抖动、连接数瞬时打满
特征：尖、短、高应对：限流 + 排队削峰
流量洪峰 / 流量峰值Traffic Peak / Flood

流量整体抬升并持续数小时甚至数天，典型如双 11、618、春晚红包。它不是「一下子上去」，而是「高位运行很久」。难点在于持续压力下的资源供给、慢请求累积和不均衡。·

典型场景电商大促、节日红包、开学季报名
核心成因可预期的业务高峰，容量需提前规划
主要危害长时段高水位，任何小瓶颈都会被放大
关键指标水位持续性、资源利用率趋势、慢查询堆积
特征：高、久、可预期应对：预案 + 弹性扩容 + 提前压测
突发流量 / 瞬时激增Burst Traffic

比洪峰更「随机」的短期抬升：可能是一次异地备份同步、一波推送触达、或上游一次批量重试。和突刺的区别在于——突刺是「尖」，突发是「一小段明显高于是的台阶」。

典型场景推送广播、批量任务、朋友圈式事件扩散
核心成因上游行为模式变化，难以精确预测时点
主要危害若突发叠加在基线小高峰上，会越过容量阈值
关键指标短期斜率（增长速率）、队列积压速率
特征：台阶式抬升应对：弹性 + 背压（backpressure）
流量骤降 / 跌零Traffic Drop

很多人只盯着「涨」，但骤降同样是异常：可能意味着上游挂了、被限流、链路断链，或业务逻辑出问题（如优惠券失效导致没人下单）。掉量和掉量成因天差地别。

典型场景网关故障、DNS 解析失败、上游服务雪崩
核心成因链路断裂 or 业务异常，而非「用户变少」
主要危害误判为「系统空闲」，掩盖真实故障
关键指标QPS 断崖、错误率反向上升、依赖调用失败
特征：断崖式下跌应对：告警 + 依赖健康探测

03 维度二 · 分布异常：流量「来得不均」

热点流量 / 热 KeyHotspot / Hot Key

总量没超，但 disproportionate（不成比例）的流量集中打在某一个或几个资源上：某个爆款商品、某个大 V 主页、某个被全网点名的接口。结果是「集群很闲、单点被打爆」。在缓存语境下也叫「热 Key」。·

典型场景顶流主播带货、热搜事件、排行榜头部
核心成因真实世界幂律分布（二八甚至一九）
主要危害单节点/单分片 CPU 打满，拖累整集群
关键指标单 Key 访问频次、节点间 QPS 方差、热点 TopN
特征：总量正常、单点爆应对：本地缓存 + Key 分片 + 多副本
流量倾斜 / 数据倾斜Traffic / Data Skew

集群里各节点的负载差距巨大。常见成因：哈希分片没选好（如按 user_id 取模，但某大 V 的 id 段集中）、用了有偏的路由规则、或客户端带 Session 粘性的负载不均。本质是分布策略把流量推成了偏态。

典型场景分库分表热点分片、一致性哈希缺虚拟节点
核心成因分片键选择不当、缺虚拟节点、IP 哈希粘滞
主要危害倾斜节点先挂，引发「木桶短板」式雪崩
关键指标节点 CPU/QPS 极差、分片大小方差
特征：集群内不均衡应对：一致性哈希+虚拟节点、重分片

04 缓存三连：流量「来得不是时候」的经典三件套

这三类异常都表现为「缓存没接住，流量直接砸到数据库」。名字很像，但触发机制完全不同——这是高频考点，务必分清。

① 缓存击穿Cache Breakdown

某个热点 Key 在失效瞬间，恰好有海量并发请求同时读到它——发现缓存没了，于是同一时刻全部去查数据库，把 DB 打爆。

对象：单 Key时机：刚好过期那一刻规模：并发回源
② 缓存雪崩Cache Avalanche

大量 Key 在同一时间段集中过期（常因批量设置相同 TTL），或缓存服务整体宕机，导致瞬间海量请求穿透到 DB，DB 直接被打死。

对象：大量 Key时机：同一时刻批量失效规模：全量回源
③ 缓存穿透Cache Penetration

请求的数据根本不存在（或已被删），缓存层查不到，数据库也查不到，于是每一次请求都穿透到 DB 空跑。既浪费资源，又常被恶意利用（如扫描不存在的 ID）。

对象：不存在的数据时机：持续、常态规模：每次都回源
对比项击穿 Breakdown雪崩 Avalanche穿透 Penetration
失效对象单个热点 Key大量 Key 同时不存在的数据
触发时机该 Key 过期的那一刻批量 TTL 同一时刻到点持续、常态发生
回源规模并发回源（同 Key）全量回源（多 Key）每次都回源（空查）
根因热点 + 集中失效TTL 设置雷同查不存在/已删数据
主要对策互斥锁/单飞(singleflight)、逻辑过期TTL 加随机抖动、多级缓存、DB 熔断布隆过滤器、缓存空值

💡 一个记忆口诀：击穿是「一个点到期被踩爆」；雪崩是「一批点同时到期被埋」；穿透是「查的东西压根不在，还一直来」。三者都靠缓存层没接住把流量甩给 DB，但解法各不相同。

05 风暴与惊群：失败和唤醒也会被「放大」

重试风暴 / 重试放大Retry Storm / Amplification

下游一抖，上游就重试；每个上游每个请求都重试 N 次，流量被乘数级放大。更糟的是：重试本身又加重下游负担，下游更抖，于是重试越多 → 越失败 → 再重试的正反馈。

典型场景DB 抖动、依赖超时、网络分区
核心成因无界重试 + 无退避 + 多层叠加
主要危害把瞬时小故障放大成全局雪崩
关键指标重试率、下游错误率、重传包量
特征：乘法放大应对：退避+抖动、重试预算、熔断
惊群效应 / 羊群效应Thundering Herd

一个事件唤醒了一大批本来在等待的进程/线程/协程，但只有一个能「赢」，其余白醒一场——既浪费 CPU，又造成瞬时争抢。经典案例：缓存失效后所有请求都去重建；或 accept() 上大量 worker 同时被唤醒抢一个连接。

典型场景缓存失效重建、锁释放瞬间、连接就绪
核心成因「都等着同一个信号」的唤醒机制
主要危害瞬时 CPU 尖峰 + 大量无效竞争
关键指标上下文切换数、瞬时 CPU、锁等待
特征：一呼百应应对：singleflight、惊群唤醒优化

💡 重试风暴 vs 惊群：前者是「主动反复发」，后者是「被动被同时叫醒」。但二者常一起出现——缓存过期既引发惊群（大家一起重建），又因重建慢诱发上层重试，叠加成灾难。

06 维度三 · 恶意流量：成分不对的异常

DDoS / CC 攻击Distributed Denial of Service

DDoS 用海量「肉鸡」从网络层（带宽/连接）压垮你；CC（Challenge Collapsar） 更阴——模拟真实 HTTP 请求打应用层（查库存、下订单），看似正常流量，实则耗尽业务资源。本质都是人为制造的流量异常。

DDoS：网络层洪流CC：应用层伪造请求应对：清洗 + 限流 + WAF + 验证码
爬虫 / 机器人流量Bot / Crawler Traffic

搜索引擎、比价脚本、抢票软件会无视业务节奏地高频抓取。良性爬虫可控，恶意的会在大促时「帮倒忙」——把本就紧张的库存/详情接口打满，挤掉真实用户。

特征：高频、规律、UA 集中应对：UA 识别、行为风控、按身份限流
慢调用 / 慢请求堆积Slow Request Pile-up

量没超，但单个请求变慢（GC、锁、慢 SQL、下游拖沓）。由于连接/线程被长时间占用，「在途请求」越积越多，可用容量被悄悄吃掉，最终看似流量正常却全面超时。这是最隐蔽的「时序异常」。

特征：量正常、RT 涨、堆积应对：超时 + 熔断 + 异步化 + 慢查询治理

07 怎么识别：盯紧这几条曲线

异常不会自己举手。要靠多维指标的组合来判断，单一数字（尤其平均值）极易被骗（详见 P 指标分位数）。

观测维度看什么对应哪类异常
QPS 曲线瞬时尖峰 / 持续高位 / 断崖突刺、洪峰、骤降
RT（尤其 P99）尾部延迟抬升、毛刺慢调用、热点、雪崩前兆
错误率 / 5xx反向上升（常伴流量下降）重试风暴、雪崩、攻击
连接 / 线程池使用率打满、等待队列拉长突刺、慢堆积、惊群
节点方差某节点 CPU/QPS 远高于其他热点、倾斜
缓存命中率骤降击穿、雪崩、穿透
DB QPS / 慢查询缓存命中率掉后 DB 暴涨缓存三连

💡 识别的关键不是「看一个绝对值」，而是看「相对基线的偏离」和「指标之间的联动」。比如「QPS 没涨，但 RT 的 P99 翻倍、错误率悄悄抬头」——这往往是慢调用堆积或雪崩前兆，比单纯流量暴涨更危险。

08 怎么应对：一套武器库

不同异常用不同武器。下面按「防御层级」排布，从最外层到最内层：

手段干啥用主要克制哪类异常
限流（令牌桶/漏桶/滑动窗口）拦在门外，超了就拒突刺、洪峰、DDoS、爬虫
排队 / 削峰（消息队列）把瞬时洪流拉平成长流秒杀、突发、洪峰
降级扛不住就返回兜底/静态雪崩、依赖故障、洪峰
熔断下游已挂，别再傻调重试风暴、慢调用扩散
隔离（舱壁模式）坏流量不拖垮好流量热点、单依赖故障
本地缓存 + 多副本把热点挡在离用户最近处热 Key、击穿
TTL 随机抖动 + 逻辑过期避免同时失效雪崩、击穿
布隆过滤器 + 缓存空值拦截不存在的数据穿透
退避 + 抖动 + 重试预算不让重试滚雪球重试风暴
singleflight / 互斥重建只让一个去回源惊群、击穿
一致性哈希 + 虚拟节点让分布重新均匀倾斜
弹性扩容 + 预热容量跟得上预期高峰洪峰、突发

⚠️ 别只在网关层限流（这点在高可用资料里反复强调过）：网关挡得住入口，但内部服务之间的调用、重试、级联同样会产生异常流量。限流、熔断、隔离必须在每一层都做，形成纵深防御。
