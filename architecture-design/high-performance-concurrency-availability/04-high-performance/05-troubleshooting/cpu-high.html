单核高 vs 整体高

两种形态，两种思路

单核 100% 多为某个死循环或热点函数；多核整体高可能是并发设计问题、锁竞争或 GC 风暴。先区分再深入。

常见原因速查

  • 死循环 / 条件写错导致无限迭代
  • 频繁 GC（对象分配过快）
  • 锁竞争、CAS 自旋
  • 正则回溯、大对象序列化
  • 频繁系统调用与上下文切换
问题 1
CPU 高怎么系统排查？

按「整机 → 进程 → 线程 → 热点」逐级下钻：先用 top 看哪台机器、哪个进程；pidstat -u -t 1 分线程定位；再用 perf top/record 抓热点函数并生成火焰图，看最宽的栈帧是谁。

问题 2
单核 100% 和整体 100% 区别在哪？

单核高通常是某一个线程的死循环或热点函数；整体高往往是并发设计问题、全局锁竞争或 GC 风暴。前者下钻到线程，后者要看锁与 GC 指标。

问题 3
怎么判断 CPU 高是 GC 引起的？

看 GC 日志 / 监控里 GC 耗时与频率，若 CPU 高与 GC 时间高度重合、且对象分配速率很高，基本是 GC 压力。对策是减少临时对象、复用缓冲、调 GC 参数。

问题 4
死循环导致的 CPU 高有什么特征？

某个线程长期 100%、火焰图顶部是同一个业务函数、且代码里存在条件永远满足的循环。用 py-spy / pprof 抓栈一眼能看出卡在哪一行。

CPU 高的排查路径：从进程到线程到代码

CPU 飙高的排查是一条清晰的收敛路径：整机 CPU → 哪个进程 → 哪个线程 → 哪段代码。每一步都有对应工具，五分钟内通常能定位到具体函数。关键是按顺序走，别跳步。

第一步top/htop 看整机与进程 CPU，确认 us/sy/si 分布
第二步top -H -p PID 或 pidstat 找出高 CPU 线程
第三步把线程 ID 转成十六进制，在栈里定位线程
第四步jstack/goroutine dump/perf 看该线程在做什么
第五步perf record 生成火焰图，确认热点函数

快速定位命令清单

① 找到进程与线程

  • top / htop：按 P 排序。
  • top -H -p <PID>：看进程内线程。
  • pidstat -u -p <PID> 1：进程 CPU 细分。
  • ps -eLo pid,tid,pcpu,comm | sort -k3 -r | head：线程级排序。

② 看线程在做什么

  • 线程 ID 十进制转十六进制（jstack 里是十六进制）。
  • JVM：jstack <PID> 找 nid。
  • Go：pprof goroutine 或 SIGQUIT dump。
  • 通用：cat /proc/<TID>/stack、gdb thread apply all bt。

③ 采样与火焰图

  • perf top -p <PID>：实时热点。
  • perf record -F 99 -g -p <PID> -- sleep 30。
  • 生成火焰图：perf script | stackcollapse-perf | flamegraph。
  • Java 建议用 async-profiler（开销更低、栈更准）。

④ 常见陷阱

  • 只看整机 CPU 平均值：要按核看，可能单核打满。
  • 把 sy 高当成业务问题：可能是系统调用或切换过多。
  • 容器里看到的是宿主的 CPU 核数。
  • 没有符号表导致栈看不懂。
  • 采样时间太短或负载不典型。

深入自检

CPU 100% 一定是死循环吗？

不一定。常见原因按概率排序：业务量真的增长（正常打满）、低效算法、GC 频繁、锁竞争、正则回溯、日志过多、以及死循环。区分方法：看 CPU 是均匀分布在多个函数还是集中在一个，看线程栈在做什么，看 QPS 是否同步增长（若 QPS 没涨而 CPU 涨，才是异常）。

为什么 top 显示 CPU 200%（多核）？

top 默认按单核 100% 计：一个进程用满两个核就是 200%。要看整体利用率需除以核数。注意区分：多线程进程可以超过 100%，单线程进程最多 100%（除非有超线程与内核线程）。htop 也遵循同样约定，按 F2 可切换显示方式。

jstack 里的 nid 怎么对应线程？

jstack 输出的 nid 是线程（LWP）ID 的十六进制表示。做法：先用 top -H 找到高 CPU 线程的 TID（十进制），用 printf '%x\n' TID 转成十六进制，再在 jstack 输出里搜索 nid=0x<该值>。找到后就能看到这个线程正在执行的 Java 栈，从而定位代码。

GC 导致的 CPU 高怎么判断？

看三个信号：① GC 日志频率与单次耗时（或 JVM 的 GC 时间占比）；② 堆占用曲线是否锯齿状且频繁触顶；③ 火焰图中 GC 线程占比高。若确认是 GC，方向是：调大堆、减少分配速率（复用对象、减少临时对象）、或换低延迟收集器（G1/ZGC）。注意 GC 高往往是「分配太多」的结果而非原因。

容器里 CPU 高但宿主机不高，是什么情况？

通常是容器 CPU limit 较低：容器内看到的使用率是相对于自己的配额，而非宿主全部核。另外容器内 ps/top 可能显示宿主的核数，导致百分比计算混乱。建议用 cgroup 的 cpuacct / cpu.stat 直接读取真实用量与节流情况。

如何防止 CPU 问题复发？

四条：① 建立性能基线并纳入发布门禁（每次发布跑基准）；② 持续剖析（continuous profiling）保留历史火焰图；③ 设置合理的告警（CPU 使用率 + 延迟 + 错误率联动，而非单一阈值）；④ 复盘时把「为什么没有更早发现」作为必答项，补齐监控与预案。
