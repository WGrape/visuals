📈 缓存监控与预热：让缓存可观测、可预期

没有监控的缓存等于盲跑；没有预热的大促等于裸奔。这两件事决定缓存是资产还是隐患。

📈

核心指标

命中率、内存、延迟

🚨

关键告警

命中率骤降、内存超阈值

🔥

预热

提前把热点填进缓存

🧪

预热要点

限速、验证、避开高峰

先建立直觉：仪表盘 + 提前备货

开车不能没有仪表盘（监控），大促不能不做备货（预热）。缓存也一样：监控告诉你现在怎么样，预热决定关键时刻扛不扛得住。

必须监控的指标

指标含义健康参考异常说明
命中率命中次数 / 总查询次数> 90%（越高越好）骤降可能是雪崩或大量新 key
内存使用率used_memory / maxmemory< 70%~80%接近上限会触发淘汰，命中率下降
淘汰数（evicted）因内存不足被淘汰的 key 数越低越好，理想为 0持续大于 0 说明容量不足
过期删除数expired_keys与写入量匹配不增长可能是清理没触发
平均/尾延迟P99、P999 延迟与基线一致尖刺可能来自大 key
连接数connected_clients稳定暴涨可能是连接泄漏
回源量 / DB QPS穿透到数据库的量低且平稳上升说明缓存失效面变大
慢查询slowlog无或极少多是大 key 或复杂命令
命中率是最核心的单一指标。它直接反映「缓存有没有在干活」。命中率掉到 90% 以下，通常意味着缓存策略、容量或数据分布出了问题，要立刻排查。

告警应该关注什么

预热：为什么要做

冷启动时缓存是空的，所有请求都会穿透到数据库。如果这时候流量已经很高（大促开始、服务重启后上线），数据库会瞬间承压。

典型场景：大促零点，活动页开放瞬间几十万 QPS。如果缓存是空的，这几十万请求全部打向数据库——数据库必挂。预热就是让这几十万请求在到达之前就有缓存。

预热的三种方式

方式做法适用
启动时加载应用启动时把配置、字典、热点数据加载进本地缓存数据量小且固定
定时刷新任务定时把热点数据集批量写入 Redis可枚举的热点集合
离线分析 + 推送分析历史访问日志找出 top N 热点，提前写入大促、大型活动
// 启动时预热示例
func warmUp() {
    keys := loadTopNHotKeys(10000)          // 从离线分析或配置读取
    sem := make(chan struct{}, 50)          // 限速：并发 50
    for _, k := range keys {
        sem <- struct{}{}
        go func(k string) {
            defer func() { <-sem }()
            v, err := db.Query(k)
            if err == nil && v != nil {
                redis.SetEX(k, ttlWithJitter(300), v)   // TTL 带抖动，防雪崩
            }
        }(k)
    }
}

预热的四个要点

  1. 必须限速：预热本质是对数据库发起大量查询，不做限速会把数据库打挂——你是在保护它，不是在攻击它。
  2. TTL 要加抖动：批量预热的数据如果 TTL 相同，会在同一时刻集体失效，人为制造一次雪崩。
  3. 避开业务高峰：在活动开始前完成，不要边跑业务边大量预热。
  4. 预热后要验证：抽样检查热点 key 是否真的写进去了、内容是否正确、命中率是否达到预期。
最容易犯的错：预热时不限速、不加 TTL 抖动。结果：预热把数据库压垮，或者预热的数据几小时后同时过期引发雪崩——预热本身变成了故障源。

监控 + 预热的闭环

  1. 平时监控命中率与热点分布，识别出稳定的热点集合；
  2. 把这些热点作为预热清单固化下来；
  3. 每次发布/重启/大促前执行预热；
  4. 预热后验证命中率是否恢复到基线；
  5. 持续监控，发现新的热点，更新清单。

🎯 面试问答

Q：命中率多少算健康？
A：一般要求 90% 以上，理想 95%~99%。但要看场景：纯热点数据可以做到 99%；长尾内容多的业务（如用户个人数据）可能只有 70%~80%，也属正常。更重要的是看趋势——相比基线突然下降才是问题信号，往往意味着雪崩、容量不足或缓存策略被改坏了。

Q：预热会不会反而把数据库打挂？
A：会，这是预热最常见的自伤。预热本质是对数据库发起成千上万次查询，如果不加控制，其冲击不亚于一次缓存雪崩。必须做三件事：① 限速（控制并发数和 QPS，如并发 50）；② 避开高峰（在活动开始前完成）；③ 分批可中断（出问题能立刻停）。同时给预热数据加 TTL 抖动，防止几小时后集体过期。

Q：冷启动时如何避免数据库被打爆？
A：组合拳：① 预热——提前把可枚举的热点填进缓存；② 限速/熔断——对回源查询限流，超出就降级；③ 互斥重建——同一个 key 只允许一个请求回源，避免重复查询；④ 灰度放量——新实例逐步接入流量，给缓存填充留出时间；⑤ 保留旧实例——发布时先不摘掉老实例，等新实例缓存热了再切。

Q：淘汰数（evicted）持续不为零意味着什么？
A：意味着内存不够用了，Redis 在不断淘汰数据来腾空间。这会直接导致命中率下降（刚写入的数据可能马上被挤掉），形成「写入→淘汰→再写入」的恶性循环，还会增加延迟。处理方式：① 扩容内存或分片；② 检查是否有大 key 或内存泄漏（过期数据没被清理）；③ 调整 maxmemory-policy；④ 缩短非热点数据的 TTL 让它更快释放。健康状态下这个值应该接近 0。
