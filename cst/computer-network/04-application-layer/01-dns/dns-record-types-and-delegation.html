DNS 记录类型与委派：A、AAAA、CNAME、MX、TXT 各管什么

沿网站与邮件同域部署的例子区分记录用途、权威委派和错误配置。

域名不是一个 IP 字典

DNS 是分布式名称系统，查询必须带记录类型。同一名称可以有 A（IPv4 地址）、AAAA（IPv6 地址）、TXT 等多类记录；找网站地址的 A 查询不会自动返回邮件服务器配置。域名层次通过 NS 记录和委派划分管理边界，递归解析器沿委派链找到相应权威服务器。缓存和 TTL 影响查询速度与变更传播，但不改变每种记录的语义。

例如 `www.example.test` 要服务网页，`example.test` 要收邮件，`_acme-challenge.example.test` 用于某种域名控制验证。它们可能由不同记录类型和不同系统维护。把所有服务都写成一个 A 记录，既不能表达邮件优先级，也不能证明域名所有权。

A、AAAA 与 CNAME

A 记录把名称指向 IPv4 地址，AAAA 指向 IPv6 地址。一个名称可有多条地址记录，客户端可能按自身策略选择，并不保证按权威返回顺序轮流访问。CNAME 则把一个名称作为另一个名称的别名，解析器还需继续查询目标地址。例如 `www.example.test` CNAME 到 `edge.cdn.test`，后者再返回 A/AAAA。别名可以方便 CDN 或服务迁移，但增加一层查询和缓存状态。

CNAME 所在名称通常不应同时有其他普通数据记录；区域顶点还必须有 SOA、NS 等记录，因此不能按标准直接把顶点当作普通 CNAME 用。某些 DNS 提供商有 ALIAS/ANAME 等供应商能力，行为要按其文档确认。误把“网站指向 CDN”做成顶点 CNAME，可能影响邮件与权威记录。

定位区域

从父区域 NS 委派找到真正的权威服务器。

按类型查询

网页查 A/AAAA/CNAME，邮件查 MX。

追踪目标

CNAME 与 MX 主机还需解析最终地址。

核对缓存

按各记录 TTL 和否定缓存验证变更。

MX 与邮件路由

MX 记录指出接收该域邮件的主机及优先级，发信服务器会先找目标域的 MX，再解析 MX 主机的地址。例如 `example.test MX 10 mail1.example.test` 与 `MX 20 mail2.example.test` 表达优先尝试 mail1 的常见配置；优先级数字更小通常更优先。邮件服务器名称应能正确解析地址，并配置接收、反垃圾和 TLS 等相关能力，仅有 MX 不会自动建立邮箱。

SPF、DKIM、DMARC 等邮件身份机制常依赖 TXT 或特定 DNS 名称，但它们各管不同验证问题。TXT 是承载文本数据的记录类型，并不是“万能安全开关”；复制别人配置而不理解实际发信源，可能使合法邮件被拒。

NS、SOA 与委派

父区域通过 NS 等信息把子区域的权威责任交给指定服务器。若 `dev.example.test` 独立交给开发团队管理，父区域的委派和子区域的权威数据必须匹配。某些情况下还需要 glue 地址记录帮助解析器找到位于被委派域内部的名称服务器，避免“为了查 NS 地址又得先问它自己”的循环。SOA 包含区域管理与序列等信息，也与否定回答缓存有关。

排查委派问题时，直接询问你以为的权威服务器并不足够；递归解析器是否能从父区域走到它，同样重要。父区域指向旧 NS、子区域只有新 NS 时，直接查询新服务器可能成功，普通用户却持续失败。

一次变更的依赖链

将网站迁到 CDN，通常改 www 的 CNAME；若邮件继续使用旧服务器，MX 不应随着网页迁移随意改动。新建 `_acme-challenge` TXT 用于证书验证时，要确认添加到真正权威的区域，而不是只在另一个控制台里建了同名区域。修改 NS 代表改变权威管理边界，比修改单条 A 记录影响更广，应计划新旧服务同时可用的过渡期。

TTL 可以分别设置在 CNAME、目标 A/AAAA、MX 等记录上。换了 CNAME 目标但旧别名仍在缓存时，仍会访问旧目标；负缓存也可能让刚新建的验证记录暂时查不到。部署应按记录类型和完整链路验收。

诊断与自测

用指定记录类型分别查询 A、AAAA、CNAME、MX、TXT、NS，记录回答来自哪个权威区域。对于 CNAME 追到最终地址，对于 MX 再查邮件主机地址，对于子域委派从父区域开始走完整链。若只有网页不通，重点查 A/AAAA/CNAME 与 HTTP；若邮件不通，先查 MX 与接收服务，不要因为网站能访问就认定 DNS 全部正确。

最后区分 NXDOMAIN（名称不存在）与 NODATA（名称存在但该类型无记录）。同一个名称的 A 查询有结果、AAAA 查询无结果，是正常的 IPv4 单栈配置，不应直接报告“域名不存在”。

DNS 查询命令

# 查各类记录
dig example.com A +short
dig example.com NS +short
dig example.com MX +short
dig example.com SOA +multiline
dig example.com TXT +short
dig _sip._tcp.example.com SRV +short

# 完整跟踪一次解析（从根服务器开始，看委派链）
dig example.com +trace
# 输出依次是：根(.) → com. → example.com. → 最终 A 记录

# 指定某台权威服务器查（绕过缓存，验证子区是否正确委派）
dig @a.iana-servers.net example.com NS +norecurse
dig @ns1.example.com example.com AXFR     # 区域传送（仅授权时才允许）

委派与排障清单

  • 胶水记录（glue record）：当子区的 NS 名字本身在子区内时（如 example.com 的 NS 是 ns1.example.com），父区必须同时返回该 NS 的 A/AAAA，否则死循环。用 dig +trace 能看到 ADDITIONAL 段里的胶水记录。
  • CNAME 三大禁忌：① 与 CNAME/MX/NS/A 等记录同名冲突；② 不能用在根域（example.com 本身），需要 apex 别名时用云厂商的 ALIAS/ANAME/flatten；③ 链太长（CNAME 指 CNAME 再指 CNAME）会拖慢解析并放大超时。
  • SERIAL 忘了加：改了记录但 SERIAL 没变 → 从服务器不会同步 → 表现为“有的用户生效有的没生效”。
  • TTL 与变更：计划切换前先把 TTL 降到 60–300 s（提前至少一个旧 TTL 周期改），切换完成后再调回。
  • 排查顺序：dig +short 看是否解析 → dig +trace 看断在哪一级 → dig @权威 验证权威数据 → dig @8.8.8.8 对比递归结果（判断是否缓存未更新）。
为什么我改了 DNS，有些地方还是老 IP？

递归服务器按 TTL 缓存，且部分 ISP/公共 DNS 会忽略过短 TTL（强制最小缓存，如 60 s 或更长）；还有浏览器/操作系统自身缓存（Chrome 的 DNS 缓存、systemd-resolved）。排查时分别用 dig @8.8.8.8 和 dig @权威 对比。

MX 的值为什么不能直接写 IP？

MX 指向的是邮件交换主机名，协议要求通过名字再解析地址；直接填 IP 会导致部分 MTA 拒收或无法回退到备用 MX。

自检

给 example.test 配一个 A 记录，能让它自动接收邮件吗？

不能。收信通常需要正确的 MX、可解析的邮件主机及实际运行的邮件服务；A 记录只提供地址映射。
