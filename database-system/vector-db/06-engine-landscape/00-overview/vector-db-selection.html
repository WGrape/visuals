①四个层次：先确定你要哪一层

向量检索能力现在有四种形态，它们不是「同一件事的不同实现」，而是不同层次的抽象。选型的第一步不是比较产品，而是先确定你需要哪一层。

形态代表你要自己解决什么适合
算法库FAISS、ScaNN、hnswlib持久化、增删改、并发、过滤、服务化全部自己做离线批处理、嵌入进自己的服务
数据库扩展pgvector、Oracle AI Vector、SQL Server无（复用数据库能力）已有该数据库，规模中等
专用向量库Qdrant、Milvus、Weaviate部署运维（自建时）向量是核心场景，规模从百万到亿级
托管服务Pinecone、Zilliz Cloud、Qdrant Cloud几乎不用管基础设施不想运维、预算充足
一个常见误判：把 FAISS 当向量数据库用。FAISS 没有 CRUD、没有持久化保证、没有并发控制、过滤能力极弱 —— 它是一组索引算法，不是一个可以放生产的存储服务。

④成本对比：三项相加才是真实成本

成本比较不能只看单价，要看你为「省事」付了多少、为「性能」省了多少。一个常被忽略的事实：embedding 调用费用常常超过向量库本身的费用。

成本项自建（Qdrant/Milvus）pgvector（已有 PG）托管 serverless
机器/内存主要成本，按向量总量线性增量成本低（复用现有实例）按存储 + 请求计费
人力运维中（分布式更高）接近零接近零
embedding 调用同一笔钱（与选型无关）同一笔钱同一笔钱
迁移与锁定低（开源可搬）低较高（API 与数据格式绑定）
峰值弹性需预留容量受实例规格限制好（serverless 弹性）
做成本对比时的正确姿势：把「embedding 调用费 + 向量库费 + 人力折算」三项加起来。只比向量库单价，会得出「托管更贵」的结论，但忽略了自建的人力成本；只比机器费，又会忽略 embedding 才是大头。

⑤七条不太会错的判断

几条不太会错的判断：

  1. 向量 < 100 万、已在用 Postgres → pgvector。不要为了「专业」引入新系统。
  2. 100 万 – 1000 万、想少运维 → Qdrant 单机或托管版。
  3. 1000 万以上、需要按角色扩展 → Milvus 分布式或 Zilliz Cloud。
  4. 已有 ES 集群且向量只是补充 → 直接用 ES 的 dense_vector，别再加一个系统。
  5. 需要内置向量化 + BM25 混合 → Weaviate。
  6. 完全不想运维、预算够 → 托管服务，但提前设计好退出路径。
  7. 只是做实验或离线批处理 → FAISS，别上服务。

⑥速记卡

先定层次

库 / 扩展 / 专用库 / 托管，四个层次不是同一件事。

FAISS 不是数据库

无 CRUD、无持久化保证、无并发控制。

第二问是过滤

复杂 SQL 过滤只有 pgvector 能优雅支持。

默认答案

已在用 PG 且千万级内 → pgvector。

规模分界

100 万 / 1000 万 / 1 亿 是三档分水岭。

成本大头

embedding 调用常超过向量库本身。

托管代价

省运维但绑定 API，要提前设计退出路径。

别过度设计

百万级以下引入专用库，多数是负收益。

选型问题里最贵的错误是过度设计：百万级数据引入分布式向量库，换来的是长期运维负担和更高的故障面。
