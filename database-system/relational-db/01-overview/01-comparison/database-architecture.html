SQL 从接入到落盘的六层

为什么要把「服务层」和「存储引擎层」分开：这是 MySQL 的一个标志性设计 —— 解析、优化、执行这些通用逻辑与「数据到底怎么存」解耦，于是可以插件式地换引擎（InnoDB、Memory…）。很多其它数据库则是自顶到底一体设计，这带来了更强的整体优化能力，但灵活性较弱。

优化器：不只是「用不用索引」

优化器做的是一件很难的事：在巨大的等价写法空间里，挑一个它认为最便宜的。常见动作包括：

改写把子查询转成 JOIN、把外连接转成内连接（条件允许时）、常量折叠。
选索引对每个表选择访问方式：全表扫、索引扫、范围扫。
定顺序多表 JOIN 时决定谁先谁后 —— 这个选择空间随表数阶乘增长。
选算法嵌套循环、哈希 JOIN、归并 JOIN 等。

它是基于代价（CBO）而不是基于规则（RBO）：靠统计信息估算每种方案要读多少行、多少页，再挑代价最小的。这解释了一个高频故障 —— 统计信息过期 → 行数估算严重偏差 → 选了一个灾难性的执行计划。

优化器失灵的典型信号 EXPLAIN ANALYZE 里： rows = 10 ← 优化器估的 actual rows = 500000 ← 真实的 两者差几个数量级，说明统计信息或数据分布不靠谱。 常见原因： · 表刚发生大量写入，没有及时 ANALYZE / 统计刷新 · 相关列之间存在相关性，优化器假设它们独立 · 谓词涉及函数、隐式转换，导致无法估算 应对：刷新统计信息 → 改写 SQL → 必要时用提示（hint）固定计划

一只 SQL 的完整生命周期（以 UPDATE 为例）

UPDATE t SET a = 1 WHERE id = 7; ① 连接 + 解析 + 优化：决定走主键索引 ② 执行器调引擎：取 id=7 这一行 └─ 若不在 Buffer Pool → 从磁盘读入并缓存 ③ 记录 undo（旧值，用于回滚与 MVCC） ④ 在 Buffer Pool 里修改这一页 → 变成脏页 ⑤ 写 redo log（prepare 状态） ⑥ 写 binlog（用于复制与恢复） ⑦ redo log 标记 commit ← 两阶段提交在此收口 ⑧ 后台线程择机把脏页刷到磁盘 关键点： · 用户感知到的「写成功」发生在第 ⑦ 步，此时数据页可能还没落盘 · 真正保证不丢的是 redo log，而不是数据页 · 这就是 WAL（预写日志）的核心思想

第 ⑤⑥⑦ 步的两阶段提交值得单独理解：redo 与 binlog 是两套独立的日志，必须保证它们要么都有、要么都没有。做法是让 redo 先进入 prepare、写完 binlog 再让 redo commit。崩溃恢复时，如果 redo 是 prepare 但找不到对应的 binlog 就回滚，否则提交 —— 用这个规则保证两份日志一致。

深入自检

缓冲池命中率不高怎么办？

先看是不是数据量远大于内存：如果是，要么加内存，要么控制热数据集（归档冷数据、拆分库表）。其次看访问模式：大量随机访问会让缓存在无效数据上反复换入换出。还要注意全表扫描这类一次性访问会把真正的热页挤出去 —— 成熟的实现会把缓冲池分成新生代/老年代来缓解，理解这个机制有助于判断要不要干预。

为什么加了索引却没有变快？

按顺序排查：① 查询里是否对列做了函数运算或类型转换（会导致索引失效）；② 是否不满足最左前缀；③ 返回的行数是否本来就很多（索引只在定位上帮你，取几万行依然慢）；④ 优化器估算是否严重偏差；⑤ 是否发生了大量回表。看执行计划，而不是猜。

连接池该怎么配？

核心是不要开太大。数据库的并发处理能力有限，连接过多会让大量线程互相争抢锁与 CPU，反而降低吞吐。经验做法是：连接数 ≈ 数据库能承受的并发查询量（通常远小于应用线程数），其余请求在应用侧排队。同时要设好空闲超时与最大生命周期，避免连接泄漏与长连接被中间件悄悄断开。

读写分离要什么时候引入？

当读压力成为瓶颈且读可以容忍轻微延迟时。要注意两个前提：① 主从延迟会让刚写入的数据在从库读不到，业务必须能接受或显式走主库；② 要有一致性的路由策略（写完立刻读的场景强制走主）。过早引入只会增加复杂度，先把单库的索引与 SQL 优化做干净往往收益更大。

聚簇索引 vs 堆表的实际影响：

  • 聚簇索引（MySQL）：按主键顺序存储，主键范围扫描极快；但二级索引要回表两次（先查二级索引得主键，再查主键索引得数据）。所以主键选择至关重要——自增 ID 优于随机 UUID。
  • 堆表（PG）：所有索引地位相同，都指向物理位置；按主键查不比按其他索引快；但更新时若行变大需要迁移，所有索引都要更新（HOT update 可优化）。

结论：MySQL 的主键设计影响全局性能（聚簇）；PG 的主键只是普通索引。这是两者调优思路的根本差异之一。

并发行为差异

-- 关键差异演示：同样的并发更新，行为不同
-- 场景：两事务同时更新同一行

-- MySQL：后到的事务<strong>等待</strong>，直到锁超时（默认 50 秒）
--   ERROR 1205 (HY000): Lock wait timeout exceeded

-- PostgreSQL：后到的事务<strong>立即报错</strong>（READ COMMITTED 下会等待，
--   但在 REPEATABLE READ / SERIALIZABLE 下报：
--   ERROR: could not serialize access due to concurrent update

-- 这对应用的影响：
#   MySQL：需要设合理的锁等待超时（<strong>50 秒太长</strong>，建议 5~10 秒）
#   PG：需要<strong>实现重试逻辑</strong>，否则并发更新频繁失败
#       标准重试次数 3 次，退避 10ms/50ms/200ms

选型提示：MySQL 的间隙锁在高并发写入下容易产生死锁；PG 的 SSI 更优雅但需要应用层处理序列化失败异常。无论选哪个，应用都要有重试与幂等——这不是数据库能替你解决的事。

PG 的 JSONB 优势在哪：JSONB 是二进制存储 + GIN 索引，可以高效地做「JSON 里某个 key 等于某值」的查询，且支持部分更新。MySQL 的 JSON 是文本存储，需要用生成列 + 索引才能高效查询，能力明显弱一档。所以如果业务大量使用 JSON 字段，PG 是更好的选择。

JSON 处理对比

-- PG JSONB 的高效用法
CREATE TABLE events (
  id BIGSERIAL PRIMARY KEY,
  data JSONB
);
CREATE INDEX idx_data ON events USING GIN (data);      -- GIN 索引

-- 高效的包含查询（走 GIN 索引）
SELECT * FROM events WHERE data @> '{"user_id": 123}';
--   @> 是「包含」操作符，能走索引

-- 提取并建表达式索引（更省空间）
CREATE INDEX idx_uid ON events ((data->>'user_id'));
SELECT * FROM events WHERE data->>'user_id' = '123';

-- MySQL 的等价做法（更笨重）
ALTER TABLE events ADD COLUMN user_id INT
  GENERATED ALWAYS AS (JSON_EXTRACT(data, '$.user_id')) STORED;
CREATE INDEX idx_uid ON events(user_id);

自检 Q&A

Q：MySQL 和 PostgreSQL 到底选哪个？

A：除非有明确需求偏向某方，选团队更熟悉的。两者在常规 OLTP 上能力相当。差异化需求才起作用：需要JSONB/PostGIS/复杂查询/自定义类型 → PG；需要成熟的分库分表生态、与云厂商深度集成、简单运维 → MySQL。另外要考虑团队技能栈与运维工具——切换成本往往远高于能力差异带来的收益。

Q：为什么 MySQL 建议用自增主键？

A：因为 InnoDB 是聚簇索引——数据物理上按主键顺序存放。自增 ID 是顺序插入，总是在 B+ 树最右侧追加，页利用率高、几乎无页分裂；随机 UUID 会插入树的随机位置，导致频繁页分裂、碎片化、随机 IO，写入性能可能差 2~5 倍，表体积也更大。PG 是堆表，主键随机的影响小得多——这正是两者架构差异的实际体现。

Q：PostgreSQL 的 autovacuum 是什么，为什么要关注？

A：它是回收死元组（dead tuple）的后台进程。PG 的 MVCC 是「更新=插入新版本」，旧版本不会立即删除，需要 vacuum 标记空间可复用。若 vacuum 跟不上，会出现表膨胀（体积持续增长、查询变慢），极端情况下事务 ID 回绕导致数据库拒绝写入。关键参数：autovacuum_vacuum_scale_factor（默认 0.2，即 20% 的行变更时触发），大表应调小。这是 PG 运维最重要的监控项。

Q：SQLite 能用在生产吗？

A：能，但有明确边界。适合：嵌入式、移动应用、单机工具、读多写少的边缘服务、单机分析。不适合：多机并发写、需要网络访问的场景（SQLite 的写锁是库级，写并发为 1）。值得注意的是，SQLite 的可靠性极高（测试覆盖率 100% MC/DC），很多场景比「跑一个数据库服务」更稳。判断标准很简单：是否需要多个进程/机器同时写入。
