📄 什么是页面（Page）？

InnoDB 存储数据的最小单位，默认大小 16KB。所有数据（表数据、索引）都存储在页面中。页面是磁盘与内存之间交换数据的基本单位。

🌲 B+ 树结构

  • 根节点：查询的入口，常驻内存
  • 内节点：只存储键值和子页面指针
  • 叶子节点：存储完整行数据，通过双向链表连接
  • 树高度：通常 2-3 层，一次查询只需 2-3 次 IO

💾 Buffer Pool（缓冲池）

内存中的页面缓存区。查询时先检查页面是否已在 Buffer Pool 中：

  • 命中（Hit）：直接从内存读取，无磁盘 IO
  • 未命中（Miss）：从磁盘加载页面到 Buffer Pool，触发磁盘 IO
  • 脏页（Dirty Page）：内存中修改过的页面，需要刷回磁盘

⚡ 一次查询的 IO 过程

  • ① 访问根页面（通常在内存）
  • ② 根据键值找到子页面指针
  • ③ 加载子页面（可能触发磁盘 IO）
  • ④ 在叶子页面中查找记录
  • ⑤ 返回结果

📄 InnoDB 页面（Page）结构

页面是 InnoDB 存储数据的最小单位，默认大小 16KB（16384 字节）

📋 Page Header（页面头部） 38 字节
包含：页号、上下页指针、页类型、LSN 等元数据
∞ Infimum + Supremum（边界记录） 26 字节
虚拟的最小和最大记录，作为页内记录的边界
📝 User Records（用户记录区） 变长
实际存储的行数据，按主键顺序线性存放
示例：[id=1, name=Alice] [id=2, name=Bob] ... [id=99, name=Zoe] 每个记录包含：记录头(5B) + 变长字段长度 + NULL标志 + 数据
🟡 Free Space（空闲空间） 变长
尚未使用的空间，插入新记录时从这里分配
📑 Page Directory（页目录） 变长
槽位（Slot）目录，每 4-8 条记录一个槽，用于二分查找加速
🔒 File Trailer（文件尾部） 8 字节
校验位（Checksum），用于检测页面是否损坏

📌 页内记录查找过程

当页面加载到内存后，查找一条记录的过程：

  • 第1步：通过 Page Directory 二分查找，定位到记录可能所在的槽位
  • 第2步：在槽位指定的范围内，线性扫描找到目标记录
  • 第3步：返回记录数据

🔄 页面加载过程（Page Fault → Buffer Pool）

  • 1. 查询需要页面 P → 检查 Buffer Pool
  • 2. 页面不在内存（Miss） → 触发页面 IO
  • 3. 检查 Buffer Pool 是否有空闲空间：
    • 有空闲 → 直接加载
    • 无空闲 → 从 LRU 尾部淘汰页面（如果是脏页，先刷盘）
  • 4. 从磁盘读取页面 P：offset = page_no × 16KB
  • 5. 页面 P 加载到 Buffer Pool → 后续访问零 IO

一次主键查询要读几次磁盘

InnoDB 的数据组织方式是索引组织表：数据就放在聚簇索引的叶子页里。要找到一行，就是从树根往下走到叶子 —— 每下降一层，理论上可能需要一次磁盘 IO。

所以这个问题的答案等价于：这棵 B+ 树有多高？

B+ 树：非叶子当路标，数据全在叶子

把数字算一遍最有说服力（InnoDB 默认页 16KB）：

非叶子页能装多少个路标？ 一个条目 = 主键（假设 bigint 8 字节）+ 子页指针（6 字节）≈ 14 字节 16KB / 14B ≈ 1170 个分支 叶子页能装多少行？ 假设一行数据约 1KB 16KB / 1KB ≈ 15 行 于是： 高度 2 → 1170 × 15 ≈ 1.7 万行 高度 3 → 1170² × 15 ≈ 约 2 千万行 高度 4 → 1170³ × 15 ≈ 上百亿行 结论：几千万行的主键查询，理论 IO 也只有 3 次左右

为什么实际 IO 往往更少

上面的估算是「每次下探都要真读一次磁盘」的最坏情况。现实中绝大多数非叶子页常驻在 Buffer Pool：

  • 树的上层节点数量极少（根节点只有一个），且被反复访问，几乎永远在缓存里。
  • InnoDB 的 Buffer Pool 会把热访问的页缓存住，真正产生磁盘 IO 的常只有最后取叶子页这一步。
  • 如果这条数据刚被读过（比如二级索引回表的邻近数据），可能连叶子 IO 都省了。

由此得到一条非常重要的实践判断：索引的有效性几乎完全取决于体量与随机 IO 次数。一个「高度 3 的树」和一个「扫全表」的差别，是 3 次 IO 与几十万次 IO 的差别 —— 这就是为什么有没有索引会差好几个数量级。

二级索引为什么慢一点：回表

访问方式路径代价
聚簇索引查询直接走到叶子，数据就在那里最少，基准
二级索引查询先在二级索引树找到主键值，再拿主键去聚簇索引查一次多一棵树的遍历（回表）
覆盖索引二级索引叶子页里已有所需字段不回表，接近聚簇索引的效率
全表扫描按页顺序扫完所有叶子行数越多越灾难
二级索引 → 主键 → 聚簇索引：两次树遍历

这就是为什么「覆盖索引」如此重要：把查询需要的列都放进索引里，就不必回表，把随机 IO 直接消掉。

顺序 IO 与页分裂

机械磁盘和 SSD 都偏好连续的访问。InnoDB 的页在磁盘上是否相邻，直接决定了它能不能利用顺序 IO 与预读。

自增主键为什么友好

新行的主键总比已有的大，永远往最右边追加写：叶子页几乎总是「追加」而不是「中间插入」，页分裂少、碎片少、写入接近顺序。

再加上相邻页在空间上也是相邻的，范围查询时能吃到线性预读的好处。

随机主键的代价

用 UUID 之类的随机值当主键，新行可能落在树的任意位置：频繁页分裂、页变得稀疏（碎片）、写入变成随机 IO。

三个可见后果：插入吞吐下降、表体积变大、缓存命中率降低。所以即使要用 UUID，也应当至少让它有序（如时间前缀的 UUID v7 思路）。

直观对比（同一个 insert 量级） 顺序主键： 写入位置单调递增 → 页几乎只在最右侧分裂 → 顺序 IO → 吞吐高、碎片少 随机主键： 写入位置随机分布 → 中间页频繁分裂 → 随机 IO → 吞吐低、页稀疏、表膨胀 → 后续范围扫描也变慢（物理上不再相邻）

深入自检

为什么说是千万行还能保持三层？

因为 B+ 树的扇出（fan-out）极高：每个非叶子页能装一千多个路标。树的高度随数据量呈对数增长，而这里的「对数的底」是一千 —— 从一千万到一百亿，高度才从 3 涨到 4。这就是索引能够对抗数据量增长的数学基础。

为什么有时候明明有索引，优化器却全表扫描？

因为优化器算的是总成本而不是「有没有用索引」。当过滤条件命中的行占比很高（比如超过全表的两成），二级索引每命中一行就要回一次表 —— 全是随机 IO，加起来比老老实实顺序扫全表还贵。这也是为什么低选择性的列（性别、状态）单独建索引价值不大。

Buffer Pool 命中率该关注什么？

关注命中率与页的冷热分布。OLTP 系统通常希望命中率在 九成以上；如果命中率上不去，多半是数据量远超内存、或访问模式太随机。此外要留意 Buffer Pool 的新生代/老年代设计：全表扫描这类一次性访问不能把真正的热页挤出去。

覆盖索引要把所有列都写进去吗？

不必，代价也要算。索引本身也占空间，且列越多单个索引页能放的条目越少（树的扇出下降）。合理做法是只把高频查询需要的那几列放进 INCLUDE（MySQL 的联合索引里放在索引列的尾部），并用实际执行计划验证是否真的达成了覆盖。
