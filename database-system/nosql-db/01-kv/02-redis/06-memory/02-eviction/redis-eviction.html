淘汰过程演示

第 1 步：内存检测

每次写入操作前，Redis 检查 used_memory 是否超过 maxmemory。如果未超限，正常写入。

第 2 步：选择候选集

根据当前选中的策略，从候选键集合中筛选可淘汰的键。

第 3 步：排序与淘汰

按照策略定义的排序规则，选出最应该被淘汰的键并删除。

第 4 步：写入新值

释放足够空间后，新的键值对被写入内存。如果空间仍然不足，重复第 2-4 步。

策略选择

noeviction

不淘汰任何键。当内存满时，所有写入操作（SET、LPUSH 等）返回错误，只允许读操作和 DEL 等删除操作。

LRU vs LFU 原理

LRU（Least Recently Used）

每个键记录最后一次被访问的时间戳。淘汰时选择最近最少使用的键。Redis 采用近似 LRU，随机采样 N 个键，选其中最久未被访问的。

LFU（Least Frequently Used）

每个键维护一个访问频率计数器。淘汰时选择访问频率最低的键。频率计数器会随时间衰减，保证热度时效性。

选型建议

若 Redis 只承载可重建的缓存，可比较 allkeys-lru 与 allkeys-lfu：前者偏向近期访问，后者偏向持续高频访问。用真实流量观察命中率、淘汰次数、回源 QPS 与数据库延迟，再决定容量和策略。

淘汰不是后台任务，而是写命令的一部分

理解 Redis 内存淘汰的关键：它不是一个独立的后台线程在跑，而是在每个写命令执行之前同步检查「内存是否超限，超限就当场淘汰」。这意味着淘汰的开销是由业务写入请求直接承担的——当淘汰量很大时，吞吐下降与延迟上升会立刻体现在业务上。

关键认知：maxmemory 限制的是「数据相关内存」，但进程实际占用还包括缓冲区、碎片、COW 等。所以 maxmemory 通常只能设为物理内存的 60-75%，否则容易被系统 OOM Killer 杀掉。

运维与调优清单

① 怎么设 maxmemory

  • 单机单实例：物理内存的 60-70%（留出碎片与 fork 空间）。
  • 单机多实例：总和不超过 70%，并预留每个实例的峰值。
  • 有持久化：进一步下调，COW 峰值可能达到数据量的一定比例。
  • 务必显式设置，64 位系统默认 0 即不限制。

② 监控指标

  • evicted_keys：持续增长说明内存不足或策略不匹配。
  • 命中率 = hits/(hits+misses)：低于预期要扩容或换策略。
  • used_memory vs used_memory_rss：比值即碎片率，>1.5 需关注。
  • expired_keys：判断是否出现过期风暴。
  • 延迟监控：淘汰期间的 P99 会明显变差。

③ 降低淘汰压力

  • 过期时间加随机抖动，避免集中过期。
  • 控制大 Key：占用大且被淘汰时代价高。
  • 缩短 key 名与 value（尤其大量小对象场景）。
  • 合理设置 ziplist/listpack 阈值，让小对象用紧凑编码。
  • 必要时扩容或分片，而不是死扛淘汰。

④ 主从与集群注意

  • 淘汰只在主节点发生，DEL 会同步到从节点与 AOF。
  • 从节点若内存不足会自行淘汰，可能与主不一致（需排查）。
  • 集群按分片独立淘汰，热倾斜会让单分片先满。
  • 扩缩容迁移期间，源与目标节点内存都要留余量。

深入自检

为什么淘汰会影响延迟？

因为淘汰是在写命令执行前同步完成的：主线程要采样候选键、比较、删除、并把删除同步给从节点和 AOF。淘汰量越大，这段逻辑耗时越长，而期间其他请求全部排队。所以 evicted_keys 高速增长时，P99 延迟会明显恶化。

maxmemory 设成物理内存的 90% 会怎样？

很危险。除数据外，进程还要容纳客户端缓冲区、复制缓冲区、内存碎片，以及 BGSAVE 期间 fork 的 COW 页、rehash 期间的双表。这些都不受 maxmemory 限制，累加起来很容易超过物理内存，触发系统 OOM Killer 直接杀进程。

淘汰了很多键，为什么内存没降？

常见原因：① 内存被缓冲区/碎片占用，不是数据；② 用了 lazyfree，释放是异步的，内存曲线滞后；③ 大量小对象删除后分配器未归还 OS（rss 不降但可复用）；④ 从节点或复制积压占用。要看 used_memory 与 rss 分别分析。

noeviction 下写入失败，业务应该怎么处理？

业务需要捕获 OOM 错误并降级：可以回源数据库、返回兜底值、或触发扩容告警。更好的做法是提前预防——设置合理的 maxmemory、监控内存水位（如 80% 告警），在达到上限前就扩容或清理，而不是等写失败再响应。

过期键为什么没有立刻释放内存？

Redis 用「惰性删除 + 定期采样删除」两种方式：键过期后只有在被访问时才会立即删除，或者被后台定期任务随机采样命中后删除。因此过期键可能短暂残留在内存中，导致 used_memory 短暂超过预期。大量键同时过期时更明显，这就是要加 TTL 抖动的原因。

如何安全地进行大规模清理？

要点：① 分批（SCAN + 每次几十到几百个键），避免一次性阻塞；② 删除大键用 UNLINK 而非 DEL；③ 放在低峰期执行并观察延迟与主从延迟；④ 清理前确认这些键确实是垃圾（避免误删持久数据）；⑤ 若目的是降内存，优先清理大 Key（--bigkeys / --memkeys 定位），收益最大。
