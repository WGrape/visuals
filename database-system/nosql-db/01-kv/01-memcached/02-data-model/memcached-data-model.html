🔑 Memcached 数据模型

只有 String、key 最长 250 字节、value 最大 1MB、TTL 最长 30 天——极简模型背后的四个硬约束和设计影响。

🔤

只有 String

没有 List/Hash/Set/ZSet

📏

key ≤ 250B

且不能含空格和控制字符

📦

value ≤ 1MB

由 slab page 大小决定

⏳

TTL ≤ 30 天

超过会被当作 Unix 时间戳

模型有多简单

Memcached 的数据模型可以一句话说完：一个全局的 key → value 字典，value 永远是字节串。没有类型、没有嵌套、没有服务端计算能力。

# 全部核心操作就这么几条
set     key flags exptime bytes   # 存（存在则覆盖）
add     key flags exptime bytes   # 只在不存在时存
replace key flags exptime bytes   # 只在存在时存
append  key flags exptime bytes   # 追加到已有 value 后
prepend key flags exptime bytes   # 追加到已有 value 前
get     key1 key2 ...             # 批量取
gets    key1 ...                  # 取（带 CAS 令牌）
delete  key                       # 删除
incr    key value                 # 数值自增（原子）
decr    key value                 # 数值自减（原子）
cas     key flags exptime bytes casunique  # 乐观锁写入
注意 get 支持一次取多个 key——这是 Memcached 提升吞吐的关键手段之一，能显著摊薄网络往返（RTT）。

四个硬约束

约束具体值为什么超了会怎样
key 长度≤ 250 字节协议与内存布局的固定上限报 CLIENT_ERROR bad key
value 大小≤ 1 MB（默认）slab 的 page 就是 1MB报 SERVER_ERROR object too large
过期时间≤ 30 天（2592000 秒）协议规定：大于该值会被当作Unix 时间戳见下方注意
flags16/32 位无符号整数由客户端自定义语义，服务端不解释—
TTL 的坑：60×60×24×30 = 2592000。Memcached 协议规定——exptime > 2592000 时，会被解释为「Unix 时间戳」而不是「秒数」。所以想设「永久有效」要显式写 0，千万不要写一个很大的秒数（如 99999999），否则会被当成时间戳 1973 年——立刻过期。

flags 字段：客户端的自定义空间

每条 item 里有个 flags，服务端完全不解释，原样存原样返回。客户端通常用它标记序列化方式：

# 常见的 flags 约定（不同客户端实现不同）
flags = 0   → 原始字符串
flags = 1   → JSON 序列化
flags = 2   → 压缩后的数据
flags = 4   → 数字（用于 incr/decr）

# 服务端视角：flags 只是跟着 value 一起存回的一个整数
# 客户端视角：get 回来后先看 flags，决定怎么反序列化

CAS：乐观锁

Memcached 没有事务，但提供了一个轻量级的乐观并发控制——gets + cas。

  1. gets key 返回值里带一个64 位的 cas unique 令牌（每次 item 变更都会递增）。
  2. 客户端基于读到的值做计算。
  3. cas key ... <cas_token> 写回。如果期间 item 已被别人改过（令牌不匹配），写入失败，客户端自行重试。
gets counter      → VALUE counter 0 1 17
100
END   # 令牌 = 17
# 另一个客户端把 counter 改成了 200，令牌变成 18
cas counter 0 0 3 17
101
  → EXISTS   # 令牌过期，写入被拒
CAS 解决的是「读-改-写」并发覆盖问题（check-and-set）。它不是锁——失败的一方需要自己重试。注意：只有使用 gets 获取令牌，才能用 cas；用 get 拿不到令牌。

incr / decr：一个常被忽略的细节

  • 只能对十进制数字字符串操作，且结果不会低于 0（decr 到 0 就停）。
  • 操作的是字符串，不是二进制整数——Memcached 内部会解析成 uint64 计算再转回字符串。
  • incr 一个不存在的 key 会失败（不像 Redis 的 INCR 会从 0 开始）。
  • incr/decr 不会刷新过期时间（这一点和 Redis 一致）。

没有复杂类型，怎么办

需要 List / Hash / Set 这些结构时，Memcached 只能在客户端序列化：

需求Memcached 的做法代价
存对象把对象序列化成 JSON / protobuf 存成 String改一个字段也要整体取回 → 反序列化 → 改 → 序列化 → 写回
排行榜 TopN把整个排行榜序列化存一个 key更新要整体重写，并发下容易覆盖（需 CAS）
计数器可以用 incr/decr✅ 这个是原生支持的
集合去重只能整体序列化不支持服务端集合运算
这正是选择 Redis 的主要理由。如果业务里大量出现「只改对象里的一个字段」或「服务端做集合运算/排序」，Memcached 的极简模型会让客户端代码变得很啰嗦，而且读写放大明显（每次都要传整个对象）。

key 命名规范（实践建议）

# 推荐：业务前缀 + 冒号分隔 + 版本，语义清晰且便于统计
user:profile:10086
order:detail:20240315:9527
api:ratelimit:uid:10086:2024031510

# 避免
# ① 过长（接近 250 字节上限）
# ② 含空格、换行、控制字符（协议按空格分割，会直接报错）
# ③ 无前缀（后续难以按业务批处理和排查）
命名空间小技巧：Memcached 没有 Redis 的 db0/db1 多库概念，也没有按前缀批量删除的能力。变通做法是在 key 里嵌入「版本号」（如 v2:user:10086），需要整体失效时升级版本号即可实现「逻辑清空」。

🎯 面试问答

Q：Memcached 支持哪些数据类型？
A：只有 String（字节串）。它就是一个全局的 key → value 字典，value 永远是二进制字节串，没有 List / Hash / Set / ZSet，也没有服务端计算能力。需要复杂结构时只能在客户端序列化成字符串再存，代价是「改一个字段也要整体读写一遍」。这是它与 Redis 最直观的差异，也是多数场景选择 Redis 的主要原因。
Q：Memcached 的 key 和 value 各有什么限制？
A：key ≤ 250 字节，且不能包含空格、换行等控制字符（文本协议按空格分割字段，含空格会直接报 CLIENT_ERROR bad key）。value 默认 ≤ 1MB（因为 slab 的 page 就是 1MB），可用 -I 调大但不推荐。此外 TTL ≤ 30 天，且要注意「超过 2592000 秒会被当成 Unix 时间戳」这个协议陷阱。
Q：Memcached 的过期时间有什么坑？
A：协议规定 exptime ≤ 2592000（30 天）时按「秒数」解释，超过则按「Unix 时间戳」解释。所以：① 想永久有效要显式写 0；② 千万不要图省事写一个很大的秒数（如 99999999），它会被当成 1973 年的时间戳，导致 key 立刻过期。另外 Memcached 采用惰性过期——不主动扫描，只在 get 时检查，所以过期 key 若无人访问会一直占内存直到被 LRU 淘汰。
Q：Memcached 的 CAS 是什么？解决什么问题？
A：CAS（Check-And-Set）是一种乐观并发控制，用于解决「读-改-写」并发覆盖。流程：gets key 拿到值和一个 64 位 cas 令牌 → 客户端基于该值计算 → cas key ... <token> 写回；若期间 item 已被别的客户端修改（令牌已变化），写入返回 EXISTS 表示失败，客户端需自行重试。注意必须用 gets（不是 get）才能拿到令牌，且 CAS 不是锁——失败方要自己处理重试。
Q：incr / decr 有什么注意事项？
A：四点：① 操作的是十进制数字字符串，不是二进制整数；② 结果不会低于 0（decr 减到 0 就停住，不会变负）；③ 对不存在的 key 执行 incr 会失败——这点和 Redis 的 INCR 不同（Redis 会当作 0 开始）；④ incr/decr 不会刷新过期时间。另外它们是原子操作，可以安全地用于计数和限流。
Q：Memcached 没有多 DB，怎么做命名空间隔离？
A：Memcached 只有一个全局 keyspace，没有 Redis 的 db0/db1，也不支持按前缀批量删除。业界常用的变通做法是在 key 里嵌入版本号或业务前缀，例如 v2:user:profile:10086；需要「整体失效某个命名空间」时，把版本号升级成 v3 即可实现逻辑清空（旧 key 会自然过期被 LRU 淘汰）。key 命名建议统一为「业务前缀 + 冒号分隔」的格式，便于统计和排查。
