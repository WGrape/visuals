客户端 / 上游保护

上游 API 的客户端控制

批量处理网页时，先决定本地最多等多少、同时发多少、每个 Key 多快发，再规定失败后是否重试。它们是不同的闸门。

“创建了 10,000 个异步任务”只说明本地有很多待完成任务；其中多少已发送、多少在上游处理，必须分别观察。

请求进入上游前的五道边界

顺序是示意，关键是每层明确预算并留下可观测的状态。

01 / 存放有界待发队列

满了阻塞生产者或明确拒绝，避免把全部输入变成大量驻留内存的任务。

02 / 启动固定数量的 worker

有限个消费者从队列取工作；已取出、等待闸门的任务仍未必已发送。

03 / 速率按 Key 的 RPM 闸门

控制每个凭证的发送次数；每次重试也需重新计入预算。

04 / 同时并发 semaphore

限制本地同时执行的单次发送；等待令牌或退避时不占用它。

05 / 退出超时与有界重试

限制每次尝试及整体期限；失败后按规则等待，不无限重放。

示意配置：队列最多 100 个待取任务，16 个 worker，发送闸门 8 个槽位。队列满时 put 等待，因而不会一次性创建 10,000 个等待中的协程；16 个 worker 中最多 8 个可同时执行发送，剩余可能等速率或闸门。以上数值都不是服务商限额。

并发、RPM 和服务能力不是同一个数字

本地并发上限

例如 8 表示本客户端同一时刻最多执行 8 次发送。慢请求会占槽更久；它不限定一分钟内发送多少次。

连接池和 HTTP 协议还可能更早地排队。先看连接与流的区别。

每个 Key 的发送预算

例如假设自己配置 400 RPM，意思是该凭证在选定限流策略下控制发送频率，并非可同时处理 400 个请求。

若多个进程共用 Key，单进程计数器无法汇总总量；需要共享限流器或保守拆分预算。

不要把供应商的并发描述当个人配额。 Jina Reader 文档中的约 4,000 个并发请求是服务能力的近似表述，不能据此认定你的 Key 有 4,000 个独占槽位，或推断内部队列、锁和 429 的触发路径。Reader 的实际 RPM、套餐与响应行为请以当时官方文档及账户信息为准。

把约束落成控制流程

下面是无网络请求的说明性伪代码。send_once、限流器和队列均为抽象接口，不是可直接运行的 SDK 示例。

queue = BoundedQueue(capacity=100)
slots = Semaphore(8)
gate = PerKeyLimiter(configured_budget_by_key)  # 示例预算，非供应商配额
start_fixed_workers(count=16, run=worker)
for job in lazy_source():
    await queue.put(job)                     # 满时背压；不要预建海量任务
await queue.join()
await stop_fixed_workers()

async def worker():
    while True:
        job = await queue.get()
        try:
            if job is STOP: return
            await handle(job)
        finally:
            queue.task_done()

async def handle(job):
    for attempt in range(1, 4):              # 总共最多 3 次尝试
        if job.deadline_expired(): return fail(job, "整体期限已到")
        while True:
            if not await gate.wait_until_eligible(job.key, job.deadline):
                return fail(job, "整体期限已到")
            async with slots:
                if job.deadline_expired(): return fail(job, "整体期限已到")
                if not gate.try_take_now(job.key):
                    continue                  # 令牌被其他任务先取走；释放槽后再等
                try:
                    reply = await send_once(job, timeout=min(10, job.remaining()))
                except Timeout:
                    reply = RetryableFailure("timeout")
                break                         # 离开 semaphore，再决定重试
        if reply.ok: return succeed(job, reply)
        if not job.retry_safe or reply.reason not in (429, 503, "timeout"):
            return fail(job, reply.reason)
        if attempt == 3: return fail(job, "尝试次数用尽")
        delay = max(parse_retry_after(reply), jittered_backoff(attempt))
        if delay > 30 or delay >= job.remaining():
            return fail(job, "等待超出重试预算")
        await sleep(delay)                     # 不占发送槽；下次仍须重新过 RPM 闸门

伪代码省略停止信号的投递、取消传播、指标记录及异常分类。try_take_now 必须是对同一 Key 的原子取令牌操作；先等到有资格，再入并发闸门，取不到令牌就释放闸门重等，避免在速率等待时长期占用发送槽。

超时与 Retry-After 要有共同预算

分别约束队列等待时间、连接/读取等单次尝试超时和从入队算起的整体截止时间。仅设 socket 超时，排队和退避仍可能无限延长用户等待。

Retry-After 可能是秒数，也可能是 HTTP 日期。有效时不要早于服务端指定时刻重试；同时使用带抖动的指数退避，避免同批客户端一起再次冲击。若指定等待超过本地最多 30 秒的示意预算，放弃或延期任务，而不是把等待截短后提前发送。

只对可安全重试的操作重放，例如幂等读取，或有幂等键、去重保障的写入。429 不必然意味着并发超标；503 和超时也不能单凭状态码判断内部瓶颈。响应异常、超时和取消要记录并释放队列与并发资源。

至少观察这几组指标

  • 队列当前长度、入队等待与被拒数：判断输入是否超过本地消化能力。
  • 按 Key 的令牌等待、实际发送次数（含重试）、429 数量：判断速率边界。
  • 占用中的发送槽、连接池等待、请求耗时与完成 QPS：定位瓶颈属于哪一层。
  • 超时、Retry-After、重试次数与最终失败数：检查是否发生重试放大。
