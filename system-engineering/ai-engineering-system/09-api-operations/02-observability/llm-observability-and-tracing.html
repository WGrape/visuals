一句话原则

可观测的目标不是「系统没报错」，而是能回答每一块钱、每一秒、每一个差评发生在哪一次调用上。

OBSERVABILITY × TRACING × QUALITY

LLM 可观测性与链路追踪

QPS、延迟、错误率全绿，用户却在抱怨——因为「返回 200」和「答对了」是两件事。这一篇给出 LLM 场景的 trace span 划分、从资源到业务的四层指标，以及把线上质量信号反哺评测集的闭环。

TTFT/TPOTSpan 链四层指标静默劣化隐式信号回归评测

1. 为什么传统监控在 LLM 上不够用

传统服务监控看三件事：QPS、延迟、错误率。LLM 应用这三个指标全绿，体验依然可能很差—— 因为「返回 200」和「答对了」是两件事。

传统指标在 LLM 场景的问题
QPS同样 QPS，长上下文和短上下文的成本与负载差一个数量级
延迟 P99LLM 是流式输出，首字延迟(TTFT)与总时长是两种体验，混在一起看没意义
错误率HTTP 200 但内容被截断、拒答、格式错、幻觉——全都不算错误
最危险的是「静默劣化」。 换了个模型版本、改了句提示词、召回策略调了参数——全链路无报错、延迟正常、错误率为零， 但答案质量悄悄掉了 20%。没有质量侧的可观测，这种劣化能持续几周才被业务方发现。

2. Trace 的骨架：一次 LLM 调用该记什么

把一次 LLM 请求拆成可归因的 span 链，是后续所有分析的基础。 最小可用的 span 划分如下：

Span含义关键字段
request入口请求整体feature, tenant, user_id, trace_id
retrievalRAG 召回（若有）召回条数、重排后条数、耗时
prompt-assembly提示拼装模板 ID、上下文 token 数、是否截断
llm-call模型调用model, TTFT, 总耗时, in/out token, 重试次数
parse结果解析/工具调用json 解析成败、工具名、参数
post后处理与返回安全拦截、格式校验、是否降级

每个 span 至少记录：开始时间、耗时、输入/输出 token、模型名、是否命中缓存、是否重试、错误类型。 没有这些字段，事后就无法回答「慢在哪、贵在哪、错在哪」。

敏感内容要脱敏后再落库。 Trace 里如果存原始 prompt 与回复，等于把用户数据复制了一份到日志系统。 推荐做法：默认只存模板 ID + 变量哈希 + 长度，需要排查时按 trace_id 申请解密查看原始内容。

3. 四层指标，从资源到业务

层级指标回答什么问题
资源层token 消耗、RPM/TPM 水位、并发槽占用容量够不够、花了多少钱
链路层TTFT、TPOT、总时长、重试率、缓存命中率慢在哪、稳不稳
质量层拒答率、截断率、格式解析失败率、评测集得分答得对不对、格式对不对
业务层会话轮次、任务完成率、重试提问率、人工接管率、差评率用户有没有真的解决问题
把四层指标放在同一张看板上，且下钻链路打通。 看到"业务层差评率涨了"能一路下钻到"某模型版本的 llm-call P95 变慢且截断率升高"， 这个可观测体系才算真的能用。

4. 质量信号与反馈闭环

质量侧不能只靠离线评测集——它覆盖不到线上长尾。需要把线上信号接回来。

  1. 显式信号 — 点赞/点踩、评分、举报。最直接但覆盖率低（通常个位数百分比）。
  2. 隐式信号 — 用户是否追问、是否复制结果、是否重新生成、会话是否提前中断。覆盖率高但噪声大，需要聚合看趋势。
  3. 自动信号 — 格式校验失败、工具调用参数不合法、安全策略拦截、输出长度异常。这些是纯粹的负样本，零成本可得。
  4. 抽样人工评测 — 按 feature + model 分层抽样，人工打分。成本最高但最可信，用于校准上面三类信号。

闭环的关键是把这些信号反哺到评测集：线上发现的 bad case 固化成回归用例， 下次改提示词/换模型时自动跑一遍。这样评测集会随业务演进，而不是一开始就写死然后永远过时。

5. 落地清单

  • 每次调用都有 trace，且 span 链完整（入口 → 召回 → 拼装 → 调用 → 解析 → 返回）
  • TTFT 与总时长分开统计
  • 输入/输出 token、模型名、重试次数、缓存命中都已落字段
  • 原始 prompt/回复默认不落库，或已脱敏并有访问控制
  • 质量侧至少有一个线上指标（拒答率、截断率、格式失败率）
  • 线上 bad case 能固化进评测集，形成回归
  • 看板支持从业务指标下钻到单次 trace
