01最小可用 pipeline

批处理为主的场景，Spark + 调度（Airflow/DolphinScheduler）就够了；有实时需求才上 Flink。

采集  Kafka（日志/事件流）
  -> 处理  Flink / Spark Structured Streaming（清洗、聚合）
  -> 存储  湖仓（Iceberg/Hudi on 对象存储）或 HDFS
  -> 服务  OLAP（Doris/ClickHouse）供查询与看板

要点：小数据量（GB 级、单日百万条以内）用一套 PostgreSQL + 定时脚本往往比搬出 Kafka+Flink+Spark 省心得多。大数据组件的价值在「规模与实时」，不在「听起来先进」。

03数据分层

  • ODS：贴源层，原始落地，几乎不改。
  • DWD：明细层，清洗、脱敏、统一口径。
  • DWS：汇总层，按主题轻度聚合。
  • ADS：应用层，直接喂给看板/服务。

层与层之间用调度保证依赖顺序，避免「上游还没算完下游就来取」。

04排障与容量陷阱

  • 数据倾斜：某 key 特别大，单 task 拖垮全局 → 加盐打散或预聚合。
  • 背压：Flink 下游慢导致上游积压 → 看反压指标、加资源或限流上游。
  • 小文件爆炸：流式小批次写湖仓会堆出海量小文件 → 定时 compaction。
  • 资源错配：把计算节点和存储节点混部却没隔离，互相抢。
问：什么时候该从「单库+脚本」升级到大数据栈？

当单机写不进（写吞吐到顶）、算不动（批处理超时）、或需要实时（分钟级以内）时再升。提前上重武器只会把简单问题复杂化——很多团队卡在「为了用而用」。

第一层 · 概念与判定：最小可用 pipeline 长什么样

一条最小 pipeline 只回答三件事：数据从哪来、存哪、怎么算、结果去哪。不足这四条就不叫 pipeline，只是脚本。

环节最小组件跳过会怎样
采集 / 接入Kafka 或 S3 落地没有统一入口，下游各读各的，schema 失控
存储一个湖仓（Hudi/Iceberg on S3）数据堆在散落文件，没法增量读
计算Spark / Flink / DuckDB全靠手写 SQL 脚本，无法调度与重试
调度Airflow / DolphinScheduler依赖靠人记，失败没人重跑
产出结果写回库或下发算完即弃，业务用不上

Spark 提交 + Iceberg 建表示例

# Spark 提交：控制并发与内存，避免 OOM
spark-submit --master k8s://... \
  --conf spark.executor.instances=3 \
  --conf spark.executor.memory=16g \
  --conf spark.executor.cores=4 \
  --conf spark.sql.shuffle.partitions=200 \
  app.py

# Iceberg 表建表（分区按天，控制小文件）
CREATE TABLE lake.events (id bigint, ts timestamp, payload string)
PARTITIONED BY (days(ts))
TBLPROPERTIES ('write.target-file-size-bytes'='536870912')

容量直觉：shuffle 分区数按「Executor 总核数 × 2～3」设；单分区目标文件 512MB，过小会产生海量小文件拖垮元数据。

第三层 · 排障与边界：四个高频坑

  • 小文件爆炸：流式每 5 分钟提交一次，几月后元数据被压垮——用 rewrite_manifests / OPTIMIZE 定时合并
  • schema 漂移：上游加字段下游崩——读写用 schema evolution，下游默认宽容模式（多字段忽略、少字段填 null）
  • 迟到数据：事件时间晚到导致分区遗漏——用 watermark + 允许延迟窗口，或定时重算近 N 天
  • 任务依赖死锁：A 等 B、B 等 A，调度器干转——用 Airflow 的 depends_on_past 与明确的 DAG 边界
  • 资源抢占：Spark 和 Flink 混部抢核——用 K8s 的 resource quota 与 priority class 隔离

第四层 · 原理与取舍

为什么不直接上 Hadoop 全家桶？

传统 HDFS + Hive 需要常驻集群与专人运维，小数据量下性价比极低。现代做法是存算分离：对象存储（S3/OSS）当底座，计算按需起 Spark/Flink，峰时扩容、谷时归零，成本按扫描量计。只有数据量稳过 PB 级、且查询模式固定，自建集群才划算。

湖仓（Lakehouse）和纯数仓（如 ClickHouse）怎么选？

湖仓（Iceberg/Hudi + Trino）胜在一份存储多种计算、可回溯、成本低，适合离线/准实时与数据科学；ClickHouse 等专数仓胜在单表极速聚合，适合固定报表与服务端查询。常见架构是湖仓做底座，热数据同步到 ClickHouse 扛高并发读。

为什么要有调度层，Cron 不够吗？

Cron 只管「到点跑」，不管依赖、重试、告警、血缘。真实 pipeline 是 DAG：任务失败要自动重试并通知，上游晚到下游要等，改动要可回溯。没有调度层，这些全靠人肉，规模一大必然漏跑和脏数据。
