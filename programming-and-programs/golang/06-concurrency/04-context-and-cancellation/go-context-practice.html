01超时控制

ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()
select {
case res := <-doWork(ctx):
    fmt.Println(res)
case <-ctx.Done():
    fmt.Println("超时:", ctx.Err())  // context.DeadlineExceeded
}

02取消传播

父 context 取消，所有派生的子 context 一起取消；子取消不影响父。这是「一对多撤收」的关键。

要点：每个 WithCancel/WithTimeout 都必须配对一次 cancel()，否则 context 树节点泄漏（连带 timer 不释放）。用 defer cancel() 最稳。
ctx, cancel := context.WithCancel(parent)
go workerA(ctx)
go workerB(ctx)
// 某处触发：cancel() 会同时让 A、B 的 <-ctx.Done() 就绪
cancel()

03WithValue 反模式

  • 别拿 context 传「可选业务参数」——那是函数参数该干的，放 context 里调用方和函数都看不清依赖。
  • 只在跨进程边界传「请求域」数据：trace id、用户身份、超时预算。
  • key 用自定义类型而不是字符串，避免不同包误覆盖。
// 反例：把业务参数塞进 context
tx := context.WithValue(ctx, "userID", id)  // 别这样
// 正例：显式参数 + 只透传请求元数据
func Handler(uid int, req *http.Request) { ... }

04接入 HTTP/gRPC 与泄漏排查

  • 泄漏排查：go tool pprof 看 goroutine 栈，定位卡在 `<-ctx.Done()` 却永远不返回的 goroutine。
  • 测试：用 context 包的 `go test` 配合 `-race` 与 `WithCancel` 模拟取消，验证下游真的早退。
问：context 和 goroutine 泄漏有什么关系？

context 只负责「发取消信号」，收不收、收了退不退，是 goroutine 自己的事。如果 worker 只在 `select` 里读业务 channel 而没监听 `<-ctx.Done()`，cancel 信号发了它也听不见，就泄漏了。

// HTTP：把请求 ctx 传下去，handler 超时即中断下游
func handler(w http.ResponseWriter, r *http.Request) {
    ctx, cancel := context.WithTimeout(r.Context(), 3*time.Second)
    defer cancel()
    result, err := queryDB(ctx, r.URL.Query().Get("q"))
    // gRPC 同理：grpc-go 的 RPC 自带 ctx，服务端 ctx.Err() 能感知客户端断开
}

第一层 · 概念与判定：什么时候该上 context

context 解决三件事：取消信号、超时截止、请求域传值。不是所有函数都需要它——纯本地计算、没有 IO 等待的函数硬塞 context 反而啰嗦。

场景用 context说明
HTTP/gRPC 请求处理链✓请求结束要取消下游
带超时的下游调用✓WithTimeout/WithDeadline
跨 goroutine 共享请求 ID✓WithValue
纯 CPU 计算无 IO✗传 context 没意义

Go context 超时 + 透传子 goroutine

// 标准套路：拿到 ctx，defer cancel，超时 100ms
ctx, cancel := context.WithTimeout(ctx, 100*time.Millisecond)
defer cancel()                 // 防止 goroutine/资源泄漏
resp, err := doRPC(ctx, req)
if err != nil {
    if errors.Is(err, context.DeadlineExceeded) {
        // 超时分支
    }
}

// 把 ctx 透传给子 goroutine
go func(ctx context.Context) {
    select {
    case <-ctx.Done():          // 父取消/超时这里立刻收到
        return
    case resCh <- work():
    }
}(ctx)

数量级：一个请求链路里 ctx 派生十几层是常态；cancel 是幂等的，重复调用安全；但漏写一次 cancel 就泄漏一个 timer/goroutine。

第三层 · 排障与边界：五个经典坑

  • 开了 goroutine 却没传 ctx：父请求取消了，子 goroutine 还在跑——必须把 ctx 当第一个参数透传下去
  • 忘记 defer cancel()：WithCancel/Timeout 背后挂了 timer 和 goroutine，不 cancel 就泄漏
  • 用 context.Value 当正常参数：它本意只放请求域元数据（traceID/user），塞业务参数破坏可读性且无类型检查
  • 传 nil context：应传 context.Background()/TODO()，传 nil 调用方一取就 panic
  • 在库里擅自存 context 到结构体：context 应是显式参数，存进 struct 让生命周期不可控

第四层 · 原理与取舍

为什么 context 要作为第一个参数显式传递，而不是全局或 struct 字段？

因为取消是树状的、有作用域的：一个请求派生出 N 个子调用，父取消要能广播给全部子孙。显式参数让调用链一眼可见取消边界，也避免把生命周期悄悄绑死在结构体上。Go 官方约定 ctx 是第一个形参，正是为了让「取消信号往哪传」在签名上就清楚。

WithValue 为什么劝你少用？

因为它绕过了编译期类型检查：取值时靠 key 断言，写错 key 取不到、类型不对就 nil/panic，IDE 也帮不上忙。它只适合放真正的请求域元数据（trace id、租户），不该替代函数参数。能写成普通参数的，一律别进 context.Value。

cancel 为什么必须调用，且放在 defer？

WithCancel/WithTimeout 会挂一个定时器 + 一个 goroutine 监听，不 cancel 它们就一直活着（泄漏）。defer cancel() 保证函数退出时一定释放，且 cancel 幂等——多次调用无害。这是 Go 里最容易被忽视、也最容易累积成内存/goroutine 泄漏的地方。
