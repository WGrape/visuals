04 · 把原则写进代码

最小伪代码

function exportPdf(data) { validatePdf(data); renderPdf(data) }
function exportCsv(data) { validateCsv(data); renderCsv(data) }
// 先保留独立语义。若共同审计规则重复出现：
function withAudit(exporter, data) {
  audit.start(data)
  return exporter(data)
}

从代码中带走三件事

  1. DRY 指不要多处维护同一条知识。
  2. KISS 要求当前设计尽量容易理解。
  3. YAGNI 要求不为尚未证实的需求预付复杂度。
05 · 原则不是教条

对应哪些模式？什么时候收手？

  • 工厂方法：产品种类真的扩展时再引入
  • 策略：算法真的需要互换时再抽出
  • 建造者：参数复杂到影响可读性时再使用

“重复三次再抽象”只是启发式，不是硬规则。安全修复或核心业务不变量即使只重复两处，也可能值得统一。

两段代码看起来一样，就应该立刻抽成一个函数吗？

不一定。先看它们是否表达同一知识、是否因同一原因变化；只看文本相似容易得到错误抽象。

三个原则各管一件事

KISS、DRY、YAGNI 常被一起提起，但它们针对的是不同的问题，甚至会互相冲突。

原则全称主张针对的问题
KISSKeep It Simple, Stupid保持简单，优先选最直白的方案过度设计带来的复杂度
DRYDon not Repeat Yourself每条知识只应有一个权威表达重复导致的维护不一致
YAGNIYou Aren not Gonna Need It不要为假想的未来需求写代码猜测未来造成的浪费
Rule of Three三次法则出现三次再抽象过早抽象的折中判据
奥卡姆剃刀如无必要勿增实体同等效果下选假设最少的多余的中间层与概念
KISS 看方案同样效果选更简单的。
DRY 看知识重复的是知识而非代码行。
YAGNI 看未来没发生的需求不要预先实现。
三次法则给 DRY 一个可执行的触发点。

DRY 最容易被误用

DRY 针对的是知识的重复，不是代码形状的相似。两段代码长得像，但表达的是不同的业务规则，强行合并会让它们被绑死。

// ❌ 假 DRY：把两个业务规则合并成一个带标志的函数 func Calc(amount float64, userType string) float64 { if userType == "vip" { return amount * 0.8 } return amount * 0.95 } // 之后「会员折扣」和「促销折扣」规则要分开演进，就麻烦了 // ✅ 更好：各自独立，重复一点点没关系 func VipDiscount(amount float64) float64 { return amount * 0.8 } func PromoDiscount(amount float64) float64 { return amount * 0.95 } // 真正该 DRY 的是这种：同一条规则散落多处 // 订单、结算、报表里各写一遍税率计算 → 必须抽出来

该 DRY 的

  • 业务规则与计算公式
  • 校验逻辑与常量定义
  • 协议与数据结构定义
  • 错误处理与转换的样板

不该 DRY 的

  • 恰好相似但语义不同的逻辑
  • 为了省几行而引入的复杂抽象
  • 会绑定两个独立演进方向的代码
  • 只出现一次的「重复」

三次法则怎么用

第一次写直白实现；第二次遇到，忍住；第三次出现，此时你已经清楚共同点在哪里，抽象出来的形状才是对的。

  • 两次就抽象，往往是错的方向
  • 三次抽象，模式已经自然浮现
  • 抽象后仍要保留可读性

YAGNI：为假想未来写的代码是负债

// ❌ YAGNI 反面教材：为「将来可能支持」预留扩展点 type Exporter interface { Export(data any) error } type JSONExporter struct{} type XMLExporter struct{} // 还没人用 type CSVExporter struct{} // 还没人用 type YAMLExporter struct{} // 还没人用 func NewExporter(format string) Exporter { switch format { ... } // 为四种格式写分发 } // ✅ 现在只需要 JSON，就直接写 func ExportJSON(data any) ([]byte, error) { return json.Marshal(data) } // 真需要第二种格式时，再加接口也不迟 —— 那时你才知道共同点在哪
预留扩展点没被使用的抽象就是纯负债
配置开关满天飞没人改动的开关是噪音
通用化过早只有一个用例的通用函数往往猜错形状
过度参数化参数越多越难用也越难测
为性能预留没测过就优化的方向常是错的
删除比添加更难没人用的代码很少被删掉

但要区分：YAGNI 不适用于已经确定的需求。下个月明确要支持的第二种格式，现在就按两种来设计是合理的。YAGNI 反对的是「说不定哪天会需要」。

怎么保持简单：四个可执行习惯

  1. 先写能跑的最简单版本，再按真实反馈演进，而不是一开始就设想完整形态。
  2. 命名即设计。想不出一个准确的名字，通常说明这个东西的职责还没想清楚。
  3. 控制函数与类型的规模。一个函数超过一屏、一个结构体超过十来个字段，就该问问是否职责过多。
  4. 删掉没人用的代码。版本控制能找回来，留着只会增加阅读负担与维护成本。
可读性优先聪明的写法若不直白就是负债
少即是多API 表面越小越容易用对
先具体后抽象抽象的形状由真实用例决定
复杂度守恒复杂度不会消失，只会被转移
评审看删减好的评审常常是在做减法
简单≠简陋简单是理解成本低，不是功能少

深入自检

DRY 和 YAGNI 冲突时怎么办？

看这段重复是「同一条知识的两个副本」还是「两个恰好相似的独立规则」。前者 DRY 优先（不一致会直接出 bug）；后者 YAGNI 优先（过早合并会绑死两个演进方向）。三次法则提供了折中：等第三次出现再决定。

简单到什么程度算够？

判据是可理解性：一个不熟悉这段代码的同事，能否在合理时间内看懂并安全修改。如果每次改动都要先理解一堆间接层，就说明不够简单。

删掉不用的代码真的安全吗？

在版本控制下是安全的——需要时能找回来。真正的风险是「不确定有没有人用」，此时可以通过静态分析、日志埋点或分阶段删除来确认，而不是永远留着。

为什么「预留扩展点」通常不划算？

因为预留的形状往往猜错。真实需求到来时，你才发现扩展点开错了位置，反而要绕开它。直接写当前需要的实现，等真的出现第二种情况时重构，成本通常更低。

简单和完备怎么权衡？

在满足当前已知需求的前提下选最简单的方案，同时确保它易于修改。简单不等于僵化：留出改的余地（清晰的边界、明确的依赖），比预留未用的扩展点更有效。
