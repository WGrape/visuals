🔷 让核心不依赖框架

六边形与清洁架构：守住依赖方向

当单体变大，最怕的是“业务核心“被 Web 框架、数据库、消息中间件绑架。六边形（端口-适配器）与清洁架构，就是用来把核心护起来的。

六边形架构清洁架构依赖规则与单体结合

🔷 一、六边形架构（端口与适配器）

核心思想：应用是个“六边形”，对外只暴露端口（接口），具体技术通过适配器插进来。

Web 适配器
HTTP / REST
⇄
应用核心
端口 · 用例
⇄
DB 适配器
JPA / MyBatis
💡
业务核心不 import 任何框架。换 Web 框架？换数据库？只要重写适配器，核心一行不动。这正是单体的“抗脆弱“设计。

🧅 二、清洁架构（同心圆）

清洁架构把依赖方向画成同心圆：越往里越核心、越稳定；越往外越易变（框架、数据库、UI）。

实体 / 企业业务规则
用例 / 应用业务规则
接口适配器（Controller / Presenter）
框架与驱动（Web / DB / 外部）

⬆️ 三、唯一铁律：依赖向内

源码依赖只能指向圆心。外层可以知道内层，内层永远不知道外层存在。这样最易变的外层（框架）可被替换，而稳定的业务核心不受波及。

实现手段通常是"依赖倒置"：内层定义接口，外层去实现它。

🏛️ 四、和单体怎么结合

  • 在模块化单体的每个模块内，再用清洁架构守住“核心不依赖技术”。
  • 框架（Spring、Django）被推到最外层适配器，核心领域代码可独立测试。
  • 未来若拆分，每个模块核心可近乎原样搬进对应微服务。
