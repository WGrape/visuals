💾 存储引擎

LSM、WAL、MemStore、HFile 与 Compaction

LSM 树思想

HBase 的写性能来自 LSM-Tree（日志结构合并树）：写操作先进内存、顺序批量落盘，再用后台合并来消除随机写。这把昂贵的「随机写磁盘」变成了廉价的「顺序追加写」。

三层存储结构

组件位置作用
WAL / HLog磁盘（HDFS）写前日志：数据进 MemStore 之前先顺序追加到 WAL，用于崩溃恢复，防止内存数据丢失
MemStore内存写缓存：按 rowkey 排序的内存结构，写满后刷盘成 HFile
HFile / StoreFile磁盘（HDFS）只读的有序文件，真正持久化的数据；每个列族一个 Store 对应一组 HFile

写入（存储视角）

  1. Client 写请求到 RS → 先顺序追加 WAL（HDFS 多副本，保证不丢）。
  2. 再写入MemStore（内存，按 key 排序）。
  3. MemStore 达到阈值（默认 128MB 或全局比例）→ flush 成 HFile 落盘。
  4. WAL 也可被回收（已落盘的 HFile 对应的日志即可清理）。

Compaction：合并与清理

🧩

Minor Compaction

把若干小的相邻 HFile 合并成较大的 HFile（不处理已删除/过期的「墓碑」标记），轻量、频繁。

🧹

Major Compaction

把一个 Store 下所有 HFile 合并成一个，并真正清除被删除、过 TTL、超版本的数据；重、IO 大，通常定时（如周末）执行。

读取与缓存

  • BlockCache：读缓存（默认 LRU），把经常读的 HFile 数据块放内存，加速重复读。
  • Bloom Filter：每个 HFile 带布隆过滤器，快速判断「某 rowkey 是否可能在本文件」，避免无效 IO。
  • 读路径：先查 MemStore，再并行查相关 HFile（借助 Bloom 跳过无关文件），合并多版本后返回最新可见值。

HFile 结构（简述）

一个 HFile 大致是：Trailer（文件索引根）→ 多个 Data Block（数据）→ 多级 Index → Bloom Block → Meta。读时先读 Trailer 拿到索引，再二分定位目标 block，避免全文件扫描。

⚠️ 小文件风暴：写入过猛或 Region 过多，会刷出海量小 HFile，Compaction 追不上，读放大严重。对策：合理预分区、控制写入速率、调大 MemStore、监控 Compaction 队列。
