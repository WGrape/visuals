G-M-P 模型下，goroutine 太多、syscall 蒙住 M、GC STW，都会让吞吐掉下去。关键是能用 schedtrace / trace 把问题看清楚。

01GOMAXPROCS 与容器陷阱

GOMAXPROCS 决定并行执行的 OS 线程上限（P 的数量）。在容器里若没设 GOMAXPROCS，Go 会按宿主物理核数初始化，可能远超容器 CPU quota，导致大量时间片争抢与 throttling。用 uber 的 automaxprocs 自动对齐。

# 启动前设（容器里强烈建议）
export GOMAXPROCS=4
go run main.go

# Go 1.25+ 已内置自动按 cgroup 限额设 GOMAXPROCS；老版本引入：
import _ "go.uber.org/automaxprocs"   # 自动设成 cgroup CPU quota

# 运行时也能改
runtime.GOMAXPROCS(4)

02怎么观测调度

  • GODEBUG=schedtrace=1000：每 1 秒打印调度器摘要（gomaxprocs、idle、runqueue 长度）。
  • GODEBUG=schedtrace=1000,scheddetail=1：再展开每个 P 的本地队列。
  • runtime.NumGoroutine()：实时 goroutine 数，暴涨常意味泄漏。
  • pprof：goroutine / threadcreate profile 看阻塞点。
GODEBUG=schedtrace=1000 ./app
# 输出示例：
# SCHED 1000ms: gomaxprocs=4 idleprocs=1 threads=8 spinningthreads=1 \
#   idlethreads=3 runqueue=3 [2 0 1 0]  <- 方括号内是各 P 的本地运行队列长度
# runqueue 长期很大 => 生产者远快于消费者，需限流或加 worker

03常见阻塞与排查

syscall 会占用一个 M（P 被解开去找别的 M），大量阻塞 syscall 会耗尽线程；GC STW 与 mark 阶段也会暂停所有 G。用 go tool trace 看时间线最准。

# 生成 trace（运行时开启）
import "runtime/trace"
f, _ := os.Create("trace.out")
trace.Start(f); defer trace.Stop()
// 复现负载后退出，用浏览器打开看 G/M 阻塞、GC、syscall 时间线
go tool trace trace.out

# 常见信号
# - Syscall 占比高 => 减少阻塞系统调用，或挪到专用 worker
# - GC 频繁/STW 长 => 降分配、调 GOGC、看 heap profile
