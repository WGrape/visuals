💡 什么是分布式系统？

定义：分布式系统是由多个独立的计算机节点组成的系统，这些节点通过网络通信协调工作，对用户呈现为单一的连贯系统。

简单来说：多台机器 → 协同工作 → 看起来像一台机器

📊 数据一致性级别

强一致
线性一致性 (Linearizability)

所有操作按全局时钟顺序执行，读一定能读到最新写入的值。开销最大，但最安全。

顺序一致
顺序一致性 (Sequential Consistency)

所有节点看到的操作顺序一致，但不要求与全局时钟一致。性能较好。

因果一致
因果一致性 (Causal Consistency)

只保证有因果关系的操作顺序一致，没有因果关系的可以乱序。平衡了一致性和性能。

最终一致
最终一致性 (Eventual Consistency)

允许暂时不一致，但经过一段时间后最终会达到一致。Redis、Cassandra 等采用此模型。

第一层 · 分布式的八个核心难题

分布式系统之所以难，是因为引入了单机不存在的失效模式。把问题列清楚，比记住各种算法更重要——每个技术都是为了解决其中一两个问题。

难题具体表现典型解法
1. 网络不可靠丢包、延迟、分区超时 + 重试 + 幂等
2. 延迟不确定有时 1ms 有时 10s超时预算、异步化
3. 部分失败部分节点成功部分失败幂等 + 重试、事务
4. 时钟不可靠各机器时钟有偏差逻辑时钟（Lamport/向量时钟）、不用本地时间做排序
5. 节点会挂宕机、变慢（比挂更难处理）副本 + 故障检测 + 选主
6. 一致性难副本数据不一致共识算法（Raft/Paxos）
7. 并发难同时修改同一数据锁 / MVCC / 乐观并发
8. 可观测性差出问题不知道在哪traceId + 指标 + 日志
  • 最反直觉的两条：① 「变慢」比「挂掉」更难处理——挂掉能被快速检测到，变慢却可能让你的超时判断失准；② 不能用本地时钟判断事件顺序——各机器时钟偏差可能达几十毫秒甚至几秒。
  • 分布式的根本矛盾：你想让多台机器像一台一样工作，但每台机器都有自己的时钟、自己的状态、且随时可能失联。所有算法都是在与这个矛盾妥协。

量化

# —— Quorum 配置的量化 ——
#   N = 副本数，W = 写需要确认的副本数，R = 读需要查询的副本数
#   强一致条件：W + R > N   （保证读集合与写集合有交集）

#   常见配置：
#   N=3, W=1, R=3   -> 写快读慢（写一份就返回，读要问全部并取最新）
#   N=3, W=2, R=2   -> 【平衡，最常见】
#   N=3, W=3, R=1   -> 写慢读快（写全部才返回，读一个即可）
#   N=3, W=1, R=1   -> 【不满足强一致】可能读到旧数据（最终一致）

# —— 可用性与副本数的关系 ——
#   容忍 f 个节点故障需要：N >= 2f + 1
#     容忍 1 个故障 -> N >= 3
#     容忍 2 个故障 -> N >= 5
#   （因为多数派是 N/2+1，剩下的必须还能形成多数派）

# —— 延迟的量化（跨地域 RTT 参考）——
#   同机房：<1ms
#   同城（不同机房）：1~3ms
#   跨城（如北京-上海）：20~30ms
#   跨国：100~300ms
#   -> 每次【同步】跨地域往返都会把这个数字加进你的接口延迟
#   -> 所以强一致 + 多地域部署 = 延迟必然高，这是物理限制

# —— 可用性的量化 ——
#   可用性 = MTBF / (MTBF + MTTR)
#   3 个 9 (99.9%)  = 每年停机 8.76 小时
#   4 个 9 (99.99%) = 每年停机 52.6 分钟
#   5 个 9 (99.999%)= 每年停机 5.26 分钟
#   串联系统的可用性 = 各组件可用性的【乘积】
#     10 个 99.9% 的组件串联 -> 99.0%（可用性被严重稀释！）
#   -> 这就是为什么【减少依赖】比【提升单个组件可用性】更有效

记住 W + R > N 这条公式——它是所有 quorum 系统（Cassandra、Dynamo、Raft 的读写）的设计基础。调 W/R 就是在调「写延迟 vs 读延迟 vs 一致性」。

第三层 · 排障清单

  • 超时设了但服务还是被拖垮 → 检查超时是否只在最外层设了。每一跳都要有超时，且层层递减（总预算 1s，调 A 给 500ms，A 调 B 给 300ms）。
  • 重试导致数据重复 → 缺幂等。所有写操作都要有幂等键（客户端生成唯一 ID），服务端用唯一约束或去重表保证。
  • 时钟问题导致数据错乱 → 用本地时间戳做排序或判断过期。解法：用逻辑时钟/版本号，或至少用单调时钟（time.Since 而非 time.Now 相减）。
  • 脑裂（两个节点都认为自己是主） → 没有用多数派或租约。解法：共识算法（Raft）或 租约 + fencing token。
  • 慢节点比挂掉的节点更致命 → 慢节点不会触发故障检测，但会拖慢每个请求。解法：响应时间也作为健康指标（不只是存活探测）、对冲请求（发给多个副本取最快的）、熔断。
  • 级联故障（雪崩） → 一个服务挂了导致依赖它的全挂。防护：超时、熔断、降级、限流、重试预算。
  • 分布式事务难以调试 → 必须有 traceId 贯穿全链路，且每步都要记日志。没有可观测性的分布式系统等于盲飞。
  • 数据不一致但不知道哪里出问题 → 要有对账机制：定期比对各副本/各系统的数据，发现不一致就告警或自动修复。这是最终一致系统的必备组件。
  • 配置不一致 → 各节点配置不同导致行为不同。解法：配置中心 + 版本化 + 灰度下发。

第四层 · 原理与取舍

分布式系统的所有设计，本质上都在回答一个问题：当「某些节点不可达」时，我是继续服务（可能返回旧数据）还是拒绝服务（保证一致）？这个选择决定了系统是 CP 还是 AP。

  • CAP 的常见误解：CAP 不是「三选二」，而是「分区发生时二选一」。网络正常时（大多数时候）C 和 A 可以同时满足；只有在分区真的发生时，才必须在 C 和 A 之间取舍。而且分区是必然会发生的（网络故障是常态），所以这个选择是真实的，不是理论。
  • PACELC 补充了 CAP 的不足：CAP 只说了分区时的情况，PACELC 指出即使没有分区，系统也在「延迟(Latency)」和「一致性(Consistency)」之间取舍——强一致需要等所有副本确认，必然增加延迟。所以更完整的表述是：分区时选 A 还是 C，平时选 L 还是 C。
  • 为什么 FLP 不意味着共识不可用：FLP 说「异步网络下不存在总是能终止的共识算法」。但现实网络不是纯异步的——它有超时。Raft/Paxos 通过超时来「猜测」节点是否故障，在超时内网络恢复的情况下能正常工作。代价是：如果超时设置不当（网络比超时还慢），可能反复选主导致不可用。所以 FLP 的现实含义是：共识算法没有正确性保证的终止性，实践中靠「合理设置超时」来让它工作。
  • 减少依赖比提升可用性更有效：串联系统的可用性是各组件可用性的乘积。10 个 99.9% 的组件串联只有 99.0%。所以：能不同步调用就不要同步调用（改异步/消息）、能降级就降级（非核心依赖失败就跳过）、能缓存就缓存（不依赖实时查询）。这是架构层面最重要的优化。
取舍选择代价适用
强一致 vs 高可用CP（Raft/ZooKeeper）分区时不可用配置、元数据、锁、选主

CAP 到底该怎么理解？是不是只能三选二？

不是「三选二」，准确的说法是：C(一致性)、A(可用性)、P(分区容错) 中，P 是分布式系统的必选项——因为网络分区必然会发生，你没有选择「不分区」的自由。所以真正的选择是：当分区发生时，你要 C 还是要 A。选 CP：分区时少数派拒绝服务（保证数据一致），典型如 ZooKeeper、etcd、HBase。选 AP：分区时两边都继续服务（返回可能陈旧的数据），典型如 Cassandra、Dynamo、DNS。而在网络正常的时候（占绝大多数时间），C 和 A 是可以同时满足的——这正是 CAP 常被误解的地方，也是为什么 PACELC 要补充说「平时是延迟(L)与一致性(C)的取舍」：即使没有分区，强一致也要付出等待副本确认的延迟代价。所以实际的系统往往是混合的：核心元数据用 CP（如选主、配置），业务数据用 AP（如用户资料、动态），并且可以通过调 W/R 参数在同一套系统里灵活切换。

为什么「慢节点」比「挂掉的节点」更难处理？

因为故障检测依赖超时，而慢节点恰好在超时的灰色地带。挂掉的节点很明确：连接被拒绝、心跳超时（比如 3 秒没心跳就判定死亡）。但慢节点是「还活着，只是响应要 5 秒」——它可能在超时前返回（你就会等满 5 秒），也可能刚好超时（你会重试，但它其实马上就要成功了）。这带来三个具体问题：① 资源占用——每个慢请求都占着一个线程/连接，累积起来就耗尽了；② 重试放大——你以为它挂了就重试，但慢节点其实在处理，重试让它的负担更重，形成正反馈；③ 无法用「存活探测」发现——它响应健康检查（很轻量），只是业务请求慢，所以不会被摘除。应对手段：① 把响应时间也作为健康指标（不只是探活），慢节点自动降权或摘除；② 对冲请求（Hedged Requests）——同一个请求发给多个副本，取最先返回的（Google 的经典论文，能把 P99 延迟显著降低，代价是少量额外负载）；③ 熔断——持续慢就断开；④ 尾延迟采样——监控 P99/P999 而不只是平均值，平均值会完全掩盖「5% 的请求慢 10 倍」这种问题。

设计分布式系统最重要的是什么？

先想清楚「什么情况下可以不一致」，而不是一味追求强一致。这是最实用的经验。具体来说三个建议：① 区分数据的关键程度——配置和元数据必须强一致（用 CP），业务数据通常可以接受秒级甚至分钟级不一致（用 AP + 缓存）。把整个系统都做成强一致，代价高且没必要；② 减少同步依赖——可用性是乘积关系，每加一个同步依赖就稀释一次。能异步就异步（消息队列），能降级就降级（非核心依赖失败直接跳过），能缓存就缓存。这是架构层面收益最大的优化；③ 可观测性先行——分布式系统出问题是常态，没有 traceId + 指标 + 日志，你根本无法定位。可观测性不是「以后再加」的锦上添花，而是设计阶段就要考虑的基础设施。最后一条务实建议：能用成熟组件就别自己造——Raft（etcd）、消息队列（Kafka）、分布式缓存（Redis Cluster）这些都有成熟实现，自己实现共识算法或分布式事务的出错概率极高。分布式系统的复杂度在于「你不知道的部分」，而不是「你知道的部分」。
