容器运行时

镜像如何变成进程——runc、containerd 与 OCI 标准的分工

OCIrunccontainerd沙箱

一句话：镜像（静态文件）通过 OCI 标准变成运行中的容器，runc 负责真正建出进程，containerd/CRI-O 负责调度与管理，gVisor/Kata 提供更强隔离。

OCI 标准：镜像与运行时的契约

Open Container Initiative 定义了两套规范：镜像规范（镜像怎么打包成 layers）和运行时规范（一个“OCI bundle”——rootfs + config.json——如何被启动）。只要有符合规范的镜像和运行时，Docker、containerd、Podman 之间就能互操作。

runc：把 bundle 变成进程

runc 是一个轻量的 CLI，读取 OCI bundle 后用 Linux 的 namespaces（隔离）和 cgroups（限额）创建容器进程。它本身不常驻，每创建一次就退出。你很少直接敲 runc——它被 containerd/CRI-O 在底层调用。

# 典型调用（被高层运行时封装）
runc create -b <bundle> mycontainer
runc start  mycontainer

containerd 与 CRI-O：Kubernetes 的左右手

组件职责
containerd / CRI-O实现 CRI（容器运行时接口），接收 kubelet 请求，拉镜像、管生命周期
runc底层真正建进程（OCI 运行时）
gVisor / Kata安全沙箱运行时，提供 VM/用户态内核级隔离

为什么需要沙箱运行时

默认 runc 共享宿主机内核，隔离靠 namespace/capabilities，攻击面仍较大。对多租户/不可信负载，可用 gVisor（用户态内核，syscall 拦截）或 Kata Containers（每个容器一个轻量 VM），把逃逸风险限制在沙箱内。

概念与判定

  • OCI bundle：一个目录，含 rootfs/ 和 config.json，是运行时的输入。
  • 高层 vs 低层运行时：containerd/CRI-O 管调度，runc 管建进程；K8s 通过 CRI 只跟高层打交道。

参数·命令·量化

  • 查看运行时：crictl info / docker info | grep Runtime。
  • 直接看 bundle：runc spec 生成默认 config.json（含 mounts/process/cgroups 配置）。
  • 容器资源上限写在 config.json 的 linux.resources（CPU quota、memory limit）。

排障与边界

  • 容器起不来：先看 crictl ps -a + crictl logs；runc 层用 journalctl -u containerd。
  • OOM：cgroup 内存超限被 kill，dmesg 看 OOM-kill；确认 limit 是否过小。

原理与取舍

运行时隔离强度开销适用
runc中（共享内核）最低默认、可信负载
gVisor高（用户态内核）中多租户、不可信代码
Kata最高（轻量 VM）高强隔离合规场景
