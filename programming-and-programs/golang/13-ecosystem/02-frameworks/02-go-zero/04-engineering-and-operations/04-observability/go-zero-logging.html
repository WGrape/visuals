在 go-zero 中打印日志

用内置 logx 库，从「打印一行字」到「全链路可追踪」一次讲透

logx 核心库 Info / Error / Slow / Stat / Severe 结构化字段 Trace 透传 yaml 配置
① 为什么用 logx ② 快速上手 ③ 五个通道 ④ 结构化日志 ⑤ 串联上下文 ⑥ 配置详解 ⑦ 进阶用法 ⑧ 完整示例 ⑨ 常见坑

①为什么用 logx，而不是 zap / logrus

go-zero 自带日志库 github.com/zeromicro/go-zero/core/logx。99% 的场景不需要引第三方日志库——它已经把微服务最需要的几件事内置了：

统一 JSON 格式

默认输出 JSON，字段固定（time / level / caller / content…），方便 ELK / Loki / Grafana 直接采集。

自动注入链路

配 WithContext(ctx) 后，日志自动带上 trace/span ID，跨服务串成一条调用链。

多通道分流

Info / Error / Slow / Stat / Severe 走不同逻辑，慢请求、统计指标可单独采集。

零额外依赖

与 goctl 生成的服务天然集成，svc.NewServiceContext 里一行 logx.MustSetup 就接管了。

一句话：go-zero 项目里，直接 import logx 开打；只有要对接特殊日志后端（发到 Kafka、写 ES）才需要自定义 Writer（见 ⑦）。

②快速上手：打印第一行日志

最朴素的用法，和 fmt.Println 一样简单，但输出是结构化 JSON：

package main

import "github.com/zeromicro/go-zero/core/logx"

func main() {
    // 用 goctl 生成的服务会由 svc 自动 SetUp，这里手动初始化一次
    logx.MustSetup(logx.LogConf{Mode: "console", Encoding: "plain"})

    logx.Info("服务启动完成")                         // 普通信息
    logx.Infof("当前在线用户数: %d", 1024)            // 带格式化
    logx.Error(err)                                  // 记录错误
    logx.Errorf("查询用户 %d 失败: %v", uid, err)        // 带格式化
}

默认 Encoding: json 时输出（一行）：

{"@timestamp":"2026-08-30T22:00:00.123+08:00","level":"info","caller":"main.go:10","content":"服务启动完成"}
每条日志都自动带 @timestamp（ISO 时间）、level、caller（文件名:行号）、content。开发期把 Encoding 设成 plain 看人话，上线再切回 json。

③五个「通道」：不只是 info / error

go-zero 把日志分成几条语义不同的通道。理解它们，日志才有「可观测性」：

Info

正常流程：启动、配置加载、关键节点。量不要太大。

Slow

耗时超过 StatSlowThreshold（默认 500ms）的慢操作，方便定位性能瓶颈。

Stat

统计类数据：请求计数、耗时分布。可直接喂监控系统。

Error

出错了但服务还能跑。ErrorStack(err) 会把堆栈一起打出来。

Severe

要命的错误（DB 连不上等）。logx.Must(err) 会直接 panic/退出。

logx.Info("订单创建成功", orderId)
logx.Slow("数据库查询过慢", cost)          // 建议配合 WithDuration
logx.Stat("http.request")                     // 统计埋点
logx.Error(err)                              // 普通错误
logx.ErrorStack(err)                        // 错误 + 完整堆栈
logx.Severe("无法连接数据库，服务不可用")
注意：Error / Slow 只会记录，不会让程序崩溃。要「出错即终止」请用 logx.Must(err)——它会写 Severe 日志后 panic 或 os.Exit(1)（由 ExitOnFatal 开关决定）。

④结构化日志（带字段）

比起把变量塞进字符串，用字段能让日志被检索（比如按 user_id 过滤）。go-zero 提供两类写法：

写法 A：Infow / Errorw 的 ...LogField 参数

logx.Infow("用户登录",
    logx.Field("user_id", uid),
    logx.Field("ip", clientIP),
    logx.Field("success", ok),
)

logx.Errorw("下单失败",
    logx.Field("order_id", orderId),
    logx.Field("reason", err.Error()),
)

写法 B：链式 WithFields（先攒字段，多次复用）

logger := logx.WithContext(ctx).WithFields(
    logx.Field("trace_id", traceID),
    logx.Field("biz", "payment"),
)
logger.Info("开始扣款")
logger.Error(chargeErr)   // 这条也会带上上面两个字段
logx.Field(key, value) 返回一个 LogField，不会马上打印，要交给 Infow/Errorw 的变参，或 WithFields 链式调用才会输出。直接 logx.Field(...) 是无效代码。

⑤在服务里「串联上下文」——最关键的一步

在 go-zero 的 handler / logic 里，你拿到的 ctx 里已经带着 trace / span ID（来自 OTEL 或内部 trace 中间件）。用 logx.WithContext(ctx) 打日志，这些链路 ID 会自动出现在每条日志里，跨服务一眼就能追到同一次请求。

在 logic 中这样用（l.ctx 是 go-zero 注入的 context）：

func (l *OrderLogic) CreateOrder(req *types.Req) (*types.Resp, error) {
    // 关键：把 ctx 传进去，日志自动带 trace / span
    logx.WithContext(l.ctx).Infof("创建订单 user=%d", req.UserId)

    order, err := l.svc.OrderModel.Insert(l.ctx, req)
    if err != nil {
        // 错误日志同样带链路 ID，方便全链路定位
        logx.WithContext(l.ctx).Errorw("插入订单失败",
            logx.Field("user_id", req.UserId),
            logx.Field("err", err.Error()),
        )
        return nil, err
    }
    return &order, nil
}
坑：只写 logx.Info(...) 是不带 trace 的。务必养成 logx.WithContext(ctx).Info(...) 的习惯，否则日志在 ELK 里就追不到是哪次请求了。

⑥配置详解：用 yaml 控制日志行为

go-zero 服务里，config.yaml 的 Log 段会由 svc.NewServiceContext 自动 logx.MustSetup，不用手写。常见配置如下：

Log:
  ServiceName: order-api        # volume 模式会在文件名前缀加服务名+主机名
  Mode: console                 # console(终端) | file(文件) | volume(k8s)
  Encoding: json                # json(机器读) | plain(人读, 开发用)
  Level: info                   # debug | info | error | severe
  Path: logs                    # 日志目录，默认 logs
  TimeFormat: "2006-01-02T15:04:05.000Z07:00"
  Rotation: daily               # daily(按天) | size(按大小)
  KeepDays: 7                   # 保留天数
  MaxSize: 512                  # size 模式下单文件上限 MB
  MaxBackups: 10                # size 模式备份数
  Compress: false               # 是否压缩旧日志
  Stat: true                    # 是否写统计日志
字段取值默认值说明
Modeconsole / file / volumeconsole输出到终端 / 文件 / k8s 带主机名
Encodingjson / plainjsonJSON 便于采集，plain 便于肉眼
Leveldebug / info / error / severeinfo低于该级别不输出
Path字符串logs文件模式下的目录
ServiceName字符串空volume 模式必需，否则报错
Rotationdaily / sizedaily按天滚动 / 按大小滚动
KeepDays整数0(全留)保留天数，到期删除
MaxSize整数 MB0(不限)仅 size 模式生效
Compresstrue / falsefalse压缩历史日志
Stattrue / falsetrue是否输出 Stat 统计日志
MaxContentLength整数0(不限)单条日志内容截断长度
Level: error 时，Info / Slow / Stat 都会被屏蔽，只打 Error 和 Severe。调试时临时调成 debug 能看到更多（前提是代码里用了 logx.Debug）。

⑦进阶：耗时、全局字段、自定义输出

带耗时：WithDuration

start := time.Now()
// ... 一段业务 ...
logx.WithContext(ctx).WithDuration(time.Since(start)).Slow("慢查询")
// 输出会多一个 duration 字段，配合 Slow 通道做性能监控

全局字段：AddGlobalFields

给之后所有日志统一加上环境/版本等字段，省得每条都写：

logx.AddGlobalFields(
    logx.Field("env", "prod"),
    logx.Field("version", "v1.3.0"),
)

自定义输出：SetWriter / AddWriter

要把日志同时发到 Kafka、ES 或远程收集器，实现 logx.Writer 接口（Info/Error/Slow/.../Close 几个方法），再 SetWriter 接管，或 AddWriter 叠加到现有输出之上：

type kafkaWriter struct{ prod *kafka.Producer }
func (w *kafkaWriter) Info(v any, fields ...logx.LogField)  { w.send("info", v, fields) }
func (w *kafkaWriter) Error(v any, fields ...logx.LogField) { w.send("error", v, fields) }
// ... 实现 Slow/Stat/Severe/Stack/Close/Alert ...

logx.AddWriter(&kafkaWriter{prod: prod})  // 在原有文件/控制台基础上叠加
多数可观测性方案（如接入 Prometheus + Loki + Tracing）用 file 模式把 JSON 日志落盘，再由 Filebeat / Promtail 采集即可，不必自己写 Writer。

⑧完整可运行示例

下面是一段可直接放进 internal/logic/*.go 的综合示例，覆盖：配置注入、链路透传、结构化字段、耗时统计、错误分级。

package logic

import (
    "context"
    "time"

    "github.com/zeromicro/go-zero/core/logx"
)

type GreetLogic struct {
    ctx    context.Context
    svcCtx *svc.ServiceContext
}

func NewGreetLogic(ctx context.Context, svcCtx *svc.ServiceContext) *GreetLogic {
    return &GreetLogic{ctx: ctx, svcCtx: svcCtx}
}

func (l *GreetLogic) Greet(name string) (string, error) {
    start := time.Now()
    // 1) 常规信息，自动带 trace/span（因为传了 l.ctx）
    logx.WithContext(l.ctx).Infow("收到问候请求",
        logx.Field("name", name),
    )

    if name == "" {
        // 2) 参数错误：用 Error + 字段，方便检索
        logx.WithContext(l.ctx).Errorw("name 为空",
            logx.Field("name", name),
        )
        return "", errors.New("name required")
    }

    // 3) 模拟一次下游调用
    msg, err := l.svcCtx.UserRpc.SayHello(l.ctx, name)
    if err != nil {
        // 4) 下游失败：带堆栈 + 字段，且带链路 ID
        logx.WithContext(l.ctx).Errorw("调用 UserRpc 失败",
            logx.Field("name", name),
            logx.Field("err", err.Error()),
        )
        return "", err
    }

    // 5) 统计耗时，慢了进 Slow 通道，正常进 Stat
    cost := time.Since(start)
    logger := logx.WithContext(l.ctx).WithDuration(cost)
    if cost > 500*time.Millisecond {
        logger.Slow("问候处理偏慢")
    } else {
        logger.Info("问候处理完成")
    }

    return msg, nil
}

⑨常见坑 & 速查

配置没生效

自己写的 main 里忘了 logx.MustSetup；goctl 生成的服务会在 svc.NewServiceContext 自动调用，前提是 config 里嵌了 logx.LogConf。

日志没 trace

直接 logx.Info 不带链路。永远用 logx.WithContext(ctx).Info(...)。

Level 调高丢日志

Level: error 会把 Info/Slow/Stat 全屏蔽，排查时记得调低。

Field 不打印

logx.Field 只是构造器，必须交给 Infow/Errorw 或 WithFields 才会输出。

Error ≠ panic

logx.Error 不会中断程序；要「出错即停」用 logx.Must(err)。

plain vs json

开发用 plain 看人话，生产用 json 便于采集。

速查表：
logx.Info / Infof 普通信息 · logx.Error / Errorf / ErrorStack 错误 · logx.Slow / Slowf 慢操作 · logx.Stat / Statf 统计 · logx.Severe 致命 · logx.WithContext(ctx) 链路透传 · logx.Field(k, v) 结构化字段 · logx.WithDuration(d) 耗时 · logx.MustSetup(c) 初始化。

API 以当前 go-zero 版本（master / latest）为准；logx.WithFields(ctx, ...) 旧写法已被 ContextWithFields 取代，新代码请用 WithContext(ctx).WithFields(...) 链式。

第一层 · logx 的等级与用法

logx 是 go-zero 内置的日志库，特点是结构化、带 traceId、支持自动切割与异步写入。理解它的等级划分和「什么时候该记什么」比记住 API 更重要。

等级用途生产是否开启示例
Debug调试细节（变量值、分支）关（开会产生海量日志）logx.Debugf
Info关键业务事件（下单、登录）开logx.Infof
Slow慢调用（超过阈值）开logx.Slowf（独立文件）
Error可恢复的错误开logx.Errorf
Severe严重错误（会 panic 或影响核心流程）开logx.Severef
  • 必须用 WithContext：logx.WithContext(ctx).Errorf(...) 会自动带上 traceId，这是跨服务串联的唯一手段。用 logx.Errorf 会丢失 traceId。
  • Slow 是 logx 的特色：慢日志会单独写到一个文件（slow.log），方便单独告警和排查。go-zero 的 RPC/HTTP 客户端默认会记录超过阈值的调用。
  • 不要记录敏感信息：密码、token、身份证、手机号要脱敏后再写日志。这是合规红线。

第二层 · 配置与命令

配置与代码

# —— 配置（etc/*.yaml）——
Log:
  ServiceName: user-api          # 服务名，日志文件名前缀
  Mode: file                     # console | file | volume
  Encoding: json                 # json | plain（生产用 json 便于采集）
  Level: info                    # debug | info | error | severe
  Path: /var/log/user-api        # 日志目录
  MaxSize: 100                   # 单文件最大 MB（超过则切割）
  MaxBackups: 7                  # 保留多少个旧文件
  MaxAge: 7                      # 保留天数
  Compress: true                 # 压缩旧日志
  KeepDays: 7                    # 全局保留天数
  Stats: true                    # 开启统计（会输出 QPS/耗时等指标）
  TimeFormat: "2006-01-02T15:04:05.000Z07:00"

# —— 代码里的用法 ——
import "github.com/zeromicro/go-zero/core/logx"

logx.WithContext(ctx).Infof("user %d login from %s", uid, ip)
logx.WithContext(ctx).Errorf("query db failed: %v", err)
logx.Slowf("slow call: %dms", cost)          # 慢日志，独立文件

# 手动设置日志器（测试时用）
logx.SetLevel(logx.ErrorLevel)                # 提高等级减少噪音
logx.Disable()                                # 测试里完全关闭

# —— 日志会输出成这样（json 模式）——
# {"@timestamp":"2024-01-01T10:00:00.000+08:00","level":"info",
#  "content":"user 123 login from 1.2.3.4","trace":"a1b2c3d4e5f6",
#  "caller":"logic/login.go:42"}

# —— 关键字段说明 ——
#   trace:  traceId，跨服务串联的【关键】
#   caller: 文件名:行号，定位问题用
#   span:   spanId（链路追踪用）
#   duration: 耗时（Stats 开启时）
参数默认建议说明
Modeconsolefile（生产）console 输出到标准输出（容器环境常用）
Encodingjsonjson便于日志采集（ELK/Loki）
Levelinfoinfo生产不要开 debug

容器环境建议 Mode: console + Encoding: json，让日志采集器（Fluent Bit / Filebeat）从 stdout 收集，不要写文件（容器文件系统是临时的）。

第三层 · 排障清单

  • 日志里没有 traceId → 用了 logx.Errorf 而不是 logx.WithContext(ctx).Errorf。这是最高频的问题，会直接导致跨服务无法串联。
  • 日志量太大把磁盘写满 → 检查：① 是否在生产开了 debug；② 是否有循环里的高频日志；③ MaxBackups/MaxAge 是否配置了。必须配切割和保留策略。
  • 日志影响性能 → 高频路径上的日志（尤其带 %+v 打印大结构体）开销可观。logx 是异步写的，但格式化本身是同步的。热路径要减少日志或用条件判断。
  • 敏感信息进日志 → 密码、token、身份证号。必须脱敏。建议在封装层统一处理（如 maskPhone()）。
  • 日志丢失 → logx 是异步写入的，进程退出时缓冲区可能未刷盘。关键日志要确保 flush，或用 logx.Close()（在服务优雅退出时调用）。
  • 慢日志没有输出 → 检查是否用了 logx 自带的客户端（go-zero 的 RPC/HTTP 客户端会自动记 Slow）。自己写的调用要手动 logx.Slowf。
  • 日志时间不对（差 8 小时） → 时区问题。配置 TimeFormat 带时区，或确保服务器时区正确。
  • 找不到日志在哪 → Mode: file 时日志写到 Path 目录下，按服务名命名（如 user-api.log、user-api-slow.log）。
  • 第三方库的日志没接入 logx → 需要设置该库的 logger 为 logx 的适配器（如 gorm 的 SetLogger）。

第四层 · 原理与取舍

日志系统的核心矛盾：日志越多越好排查，但越多越贵（磁盘、性能、噪音）。logx 的设计取舍值得理解。

  • 为什么是异步写：同步写日志会让业务线程阻塞在磁盘 IO 上（机械盘一次写可能 10ms）。logx 用异步 channel + 后台 goroutine 批量写，让业务几乎无感。代价是：① 进程崩溃时可能丢最后几条日志；② 需要优雅退出时 flush。这个取舍在生产环境是值得的——因为「日志写满导致服务卡死」比「丢几条日志」严重得多。
  • 为什么 Slow 要单独文件：因为慢日志是最高价值的排查信号（它直接指向性能问题），但混在普通日志里会被淹没。独立文件后可以：① 单独设置告警（慢日志数量突增立即告警）；② 单独采样（普通日志可以采样降量，慢日志全保留）；③ 快速定位（不用 grep 海量日志）。这是很有价值的设计。
  • 为什么 traceId 这么重要：微服务下一个请求会经过 5~10 个服务，每个服务都记日志。没有 traceId 时，你只能靠「时间戳 + 猜测」去关联；有了 traceId 就能一条命令捞出整条链路的所有日志。所以「日志必须带 traceId」是硬性原则，而它依赖「ctx 一路传下去」——这也是为什么 Go 强调 context 传递。
  • 结构化（JSON）vs 纯文本：纯文本对人友好但对机器不友好（要正则解析）；JSON 反过来。生产环境必须用结构化，因为日志量大了之后你不可能一条条看，必须靠查询（level=error AND trace=xxx）。可读性靠日志平台（Kibana/Grafana）的展示层解决。
做法优点代价
全量结构化日志可查询、可聚合量大、贵
采样（如 10%）省成本低频问题可能采不到
分级存储（error 全留，info 采样）平衡配置复杂
慢日志/错误日志独立高价值信号不淹没多几个文件
敏感字段脱敏合规要额外处理
生产环境日志等级怎么设？

默认 info，生产不开 debug。但更精细的做法是分级：① error/severe 全量保留（这是排查问题的主要依据，量也不大）；② info 按重要性区分——关键业务事件（下单、支付、登录）单独用一个标志（如 biz 字段）标记并全量保留，普通流程日志可以采样；③ debug 默认关闭，需要排查时动态临时开启（通过配置中心下发，而不是重启服务）——这要求你的日志等级支持运行时调整。另外两个实践要点：慢日志必须全量（它的量通常很小但价值极高）；日志要有 rate limit——同一个错误在一秒内重复 1000 次时，只记前几条 + 计数，否则一次故障就能把日志系统打垮（这也是日志爆炸的常见原因）。

日志该记什么、不该记什么？

该记的：① 状态变化（订单从 A 变到 B、用户登录成功）——这些是业务排查的主线；② 外部调用（请求哪个服务、耗时、结果）——跨服务问题的关键证据；③ 错误与异常（含完整上下文：输入参数、错误链）；④ 关键决策分支（走了兜底逻辑、触发了熔断）——这些往往是最难猜的。不该记的：① 敏感信息（密码、token、身份证、完整手机号）——合规红线，必须脱敏；② 循环内的每条记录（如批量处理 10000 条，记 1 条汇总 + 异常即可）；③ 大对象全量打印（%+v 一个大结构体可能有几 KB，日志会爆炸）——只打关键字段；④ 可推导的信息（如「开始处理」「结束处理」这种没有信息量的）。判断原则：这条日志能不能帮我回答「为什么会发生这件事」？不能就别记。

logx 的 traceId 是怎么传的？

依赖 context。go-zero 的中间件（HTTP 和 RPC 都有）会在请求入口生成一个 traceId（或从上游的请求头里取，如果上游传了的话），塞进 ctx；然后这个 ctx 一路传下去，logx.WithContext(ctx) 就能从中取出 traceId 打到日志里；当你用 go-zero 的客户端调下游时，客户端会自动把 traceId 放进请求头传过去。所以整条链路是自动串联的——前提是你全程传 ctx。三个会断链的地方：① 用了 logx.Errorf 而不是 WithContext(ctx)；② 起新 goroutine 时没传 ctx（或传了 context.Background()）；③ 调用下游时没用 go-zero 的客户端，导致 traceId 没传过去（此时下游会生成新的 traceId，链路就断了）。所以「context 一路传下去」不是 Go 的形式主义，而是可观测性的基础设施——这也是 Go 为什么把 ctx 作为所有函数的第一个参数。
