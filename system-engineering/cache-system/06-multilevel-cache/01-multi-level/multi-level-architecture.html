两类缓存，两个位置

CDN 和可配置缓存的反向代理位于应用之前，主要缓存符合规则的 HTTP 响应；L1 和 Redis 位于应用读数据的路径上。不能把它们写成“本地 → Redis → CDN”的同一段应用代码查找顺序。个性化或敏感响应通常要绕过共享缓存，具体由 HTTP 缓存头、鉴权和业务规则决定。

请求流转

可缓存的请求先到 CDN，未命中再进入反向代理和应用。应用读取数据时先查本地 L1，再查 Redis L2，最后回源 DB；命中任一适用层便返回。回源后可按数据的更新要求回填 L2 与 L1，HTTP 响应是否缓存则单独按入口规则决定。不同业务链路可以省略某一层。

收益、成本与失效

边缘缓存减少跨地域流量，本地缓存降低单机读取延迟，Redis 分担跨实例热点，DB 保持权威。层级越多，失效传播、观测和容量治理越复杂：L1 可用短 TTL 加主动失效消息控制陈旧窗口，Redis 和边缘层分别设置键失效与响应刷新策略；具体一致性方案见缓存双写一致性。

🎯 面试问答

Q：每个请求都会依次查询 CDN、L1、Redis 吗？
A：不会。CDN 只处理适合共享的响应；应用需要读数据时，才进入 L1、Redis 与 DB 的查找链。
Q：层级越多越好吗？
A：不是。增加一层要同时承担缓存收益、失效传播、观测与维护成本。
Q：L1 和 L2 怎么分工？
A：L1 缓解单实例热点，L2 提供跨实例共享；两者仍需设计明确的过期与失效规则。
