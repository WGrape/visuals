启动与基础配置

# 最小启动
memcached -m 1024 -p 11211 -u nobody -d

# 生产常用组合
memcached \
  -m 4096 \          # 最大内存 4GB（建议物理内存的 60~70%）
  -p 11211 \
  -u memcached \
  -t 8 \             # worker 线程数 ≈ CPU 核数
  -c 4096 \          # 最大并发连接
  -f 1.15 \          # chunk 增长因子（小 value 多时调小）
  -I 1m \            # 单 item 上限
  -d                 # 守护进程
-m 不是硬上限，是「缓存可用上限」。Memcached 实际进程占用会略高于这个值（还有哈希表、连接缓冲等开销）。单机建议不要超过物理内存的 70%，避免 swap——一旦开始 swap，Memcached 的性能会断崖式下降。

客户端要做的三件事：① 连接池（避免频繁建连）；② 一致性哈希路由（多实例时）；③ 故障节点摘除与恢复探测。

提升吞吐的四个手段

1. 批量 get（收益最大）

# ❌ 逐个取：N 次网络往返
for uid in uids:
    data = mc.get("user:%d" % uid)

# ✅ 批量取：1 次网络往返
keys   = ["user:%d" % uid for uid in uids]
result = mc.get_multi(keys)      # 一次拿回所有命中的
为什么收益这么大？Memcached 单次操作通常在亚毫秒级，此时网络 RTT（0.1~1ms）往往是主要开销。批量 get 把 N 次 RTT 压缩成 1 次，实测吞吐常常能提升数倍。建议一次批量 50~200 个 key，太多会让单次响应包过大反而变慢。

2. 连接池 + 长连接

Memcached 协议简单、无状态，非常适合长连接复用。务必用连接池，避免每次请求都 TCP 三次握手。

3. 合理设置过期时间

  • 给不同业务设置不同的 TTL，并加随机抖动，避免同时过期造成「雪崩」。
  • 不要追求「永久不过期」——那样内存会被冷数据占满，只能靠 LRU 被动淘汰。
base_ttl = 3600
ttl = base_ttl + random.randint(0, 300)   # 加 0~5 分钟抖动

4. 大 value 压缩 / 拆分

硬约束：单个 value ≤ 1MB。接近上限的大 value 会：① 加剧 slab 内部浪费；② 阻塞 worker 线程；③ 网络传输慢。建议：超过 100KB 就考虑在客户端压缩（gzip/snappy），或拆成多个小 key 分批取。

CAS 实战：防止并发覆盖

# 场景：多个请求同时给用户的积分 +10
# ❌ 不加保护：读 100 → 各自算出 110 → 都写 110（实际应得 120）

# ✅ 用 gets + cas（伪代码）
while True:
    value, cas_token = mc.gets("points:10086")
    new_value = value + 10
    if mc.cas("points:10086", new_value, cas_token):
        break          # 写入成功
    # 否则：期间被别人改过，令牌失效，重试
重试要设上限（如 3~5 次），否则高冲突下会变成活锁。冲突非常频繁的场景，说明这个数据结构可能不适合放缓存，考虑改用 Redis 的原子 INCRBY（服务端计算，天然无冲突）。

上线的正确姿势

  1. 新缓存接入时先「双写观察」：同时写缓存和 DB，读仍走 DB，观察一段时间确认无误再切读。
  2. 缓存预热：大促/重启前把热点数据提前灌进去，避免冷启动把 DB 打挂。
  3. 降级开关：缓存挂掉时要有「直接回源」或「返回兜底数据」的开关，而不是整体不可用。
  4. 监控告警：命中率、evictions、连接数三项必须有告警。
记住 Memcached 的定位：它是纯缓存，不是存储。任何时刻都不能假设「缓存里一定有」——缓存未命中时要能正确地回源，这是使用缓存的第一原则。

🎯 面试问答

Q：Memcached 启动时最关键的参数有哪些？
A：四个：-m 最大内存（建议物理内存的 60~70%，别让它 swap）、-t worker 线程数（≈ CPU 核数）、-c 最大并发连接（默认 1024，高并发要调大）、-f chunk 增长因子（默认 1.25，小 value 多的场景可降到 1.1~1.15 减少内存浪费）。另外建议用 -u 指定非 root 用户、-d 以守护进程运行。
Q：怎么用 Memcached 提升吞吐量？
A：收益最大的是批量 get（get_multi）：Memcached 单次操作是亚毫秒级，网络 RTT 才是主要开销，把 N 次往返压成 1 次，吞吐常能提升数倍（建议每批 50~200 个 key）。其次是连接池长连接（避免反复握手）、TTL 加随机抖动（防雪崩）、大 value 压缩或拆分（超过 100KB 就该处理）。
Q：Memcached 怎么做并发安全的「读-改-写」？
A：用 CAS（gets + cas）：gets 拿到值和一个 64 位令牌 → 客户端计算新值 → cas 带令牌写回；若期间 item 已被改过（令牌不匹配）则返回 EXISTS 表示失败，客户端重试。重试要设上限（3~5 次）避免活锁。如果冲突极其频繁，说明这个数据结构不适合放缓存，改用 Redis 的 INCRBY 更合适——它在服务端完成计算，天然无冲突。
Q：Memcached 最重要的监控指标是什么？
A：命中率 = get_hits / (get_hits + get_misses)，健康值应 > 90%，低于 80% 就要排查。其次看三个：evictions（持续上涨 = 内存不足，需要扩容或缩短 TTL）、bytes / limit_maxbytes（内存使用率）、curr_connections（接近 -c 上限要调大）。排查内存浪费则用 stats slabs 看每个 class 的 chunk 使用情况。
Q：为什么整体内存没满却在淘汰数据？
A：因为 LRU 是按 slab class 独立的，不是全局的。Memcached 把内存切成 1MB 的 page，每个 page 只服务于某一个 chunk 大小档位；如果某个档位（class）的 chunk 被占满，即使其他档位还有大量空闲 page，也只能淘汰本 class 内的 LRU 数据。解决办法：① 调小 -f 让档位更密；② 开启 slab 自动重分配（-o slab_reassign），让空闲 page 从冷 class 迁到热 class；③ 尽量让 value 大小分布集中，避免横跨多个档位。
Q：Memcached 重启或扩容后命中率下降怎么办？
A：两种情况的应对不同：扩容导致的下降是正常的——一致性哈希下只有约 1/(N+1) 的 key 需要重新路由，命中率会在一段时间后自然回升。重启导致的下降则是冷启动，缓解办法是上线前做缓存预热（提前把热点数据灌进去），否则瞬间的大量回源可能把数据库打挂。另外新接入缓存时建议先「双写观察」——同时写缓存和 DB 但读仍走 DB，确认无误后再切读。
