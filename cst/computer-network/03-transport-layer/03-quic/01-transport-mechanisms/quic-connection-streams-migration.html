QUIC 连接、流与迁移：HTTP/3 为什么不同

沿一次移动网络切换说明 UDP、TLS 1.3、连接 ID、流和丢包恢复的分工。

QUIC 在哪一层工作

QUIC 通常运行在 UDP 之上，在用户态实现可靠传输、拥塞控制、加密与多路流；HTTP/3 则把 HTTP 语义映射到 QUIC 流。UDP 提供数据报承载，本身不保证可靠；“HTTP/3 用 UDP”不表示页面内容可以任意丢失。QUIC 用确认、丢包检测、重传和流量控制实现需要的可靠性，但重传时通常在新的包中发送原有数据，而不是机械重发同一个加密数据包。

QUIC 与 TLS 1.3 握手紧密集成，应用数据通常受加密保护。这样减少了单独的 TCP 握手与 TLS 握手串联等待，但实际首字节时延仍取决于网络 RTT、证书验证、服务器处理和是否可恢复会话。不能把所有 HTTP/3 请求都说成零 RTT，首次连接、恢复连接和 0-RTT 数据有不同条件。

一次连接的四个阶段

客户端先向服务器 UDP 端口发送 QUIC Initial 包，携带握手相关信息；服务器返回握手数据并完成密钥建立。随后双方可在同一连接上创建多个双向或单向流，每个流有自己的偏移和流级流量控制。页面的 HTML、CSS 与图片可映射到不同流，连接层则共同管理拥塞控制和加密状态。

QUIC 包丢失时，同一流中缺失的数据会影响该流按序交付；其他流的数据可以独立交付给应用。这解决了 TCP 上 HTTP/2 多路复用仍受连接级字节流丢失阻塞的问题。但所有流共享同一网络瓶颈与连接拥塞窗口，丢包仍可能降低整体吞吐，不代表其他流完全不受影响。

连接 ID 为什么有用

传统 TCP 连接常以源 IP、源端口、目的 IP、目的端口识别。手机从 Wi-Fi 切到蜂窝网络后，源地址和端口变化，原 TCP 连接通常不能直接沿用。QUIC 使用连接 ID 帮助双方在地址变化后关联同一逻辑连接，再通过路径验证确认新地址可用。迁移完成前要控制对未验证地址的发送量，避免被利用进行放大攻击。

连接 ID 不保证任何情况下都能无缝迁移。中间设备可能阻断 UDP，服务器或客户端可能禁用迁移，连接状态也可能已过期。运营时需要观察迁移成功率、重试和回退到 HTTP/2 的比例，而不是只看功能开关已经打开。

0-RTT 的收益和限制

恢复曾建立的会话时，客户端在特定条件下可发送 0-RTT 早期数据，减少等待。但早期数据具有重放风险，服务端不应把它无条件用于扣款、创建订单等非幂等操作。服务器可以拒绝 0-RTT 并要求正常握手；客户端必须处理这种情况。对 GET 类读取也要确认是否真的没有副作用，如计费下载或一次性令牌消费。

0-RTT 不等于完全没有网络往返，也不意味着所有请求都可安全重放。性能报告应分别统计首次握手、恢复握手、早期数据成功与早期数据被拒绝的比例，并把 DNS、服务器处理与页面资源加载时间单独列出。

与 TCP + TLS 的取舍

HTTP/2 基于 TCP，一个丢失的 TCP 字节会阻塞连接内后续字节的交付，即使它们属于不同 HTTP 流。HTTP/3 基于 QUIC，把可靠交付的顺序边界下沉到各流，并整合握手与迁移。与此同时，QUIC 依赖 UDP 通路、需要新的可观测性方法，用户态实现也有 CPU 与内存成本。某些网络会限制 UDP，服务应保留可用的 TCP 回退路径。

QUIC 的加密使网络中间设备更难直接看到传输细节；排障应结合端点日志、QUIC 统计和受控密钥日志，而不能照搬 TCP 抓包里的序列号分析。安全策略也要识别它是业务流量，不应简单把所有 UDP 当成无关噪声。

怎样做真实对比

在同一地区、设备和资源集上比较 HTTP/2 与 HTTP/3 的首字节时间、页面完成时间、丢包时延、CPU 使用与回退率。模拟移动网络切换、2% 丢包和受限 UDP 三种场景，分别看收益与失败。只在低延迟无丢包实验室测一次，很难看出独立流和迁移的价值。

检查服务器是否真的协商了 h3、证书是否正常、Alt-Svc 是否被客户端采用，并记录连接 ID 迁移事件。若页面慢在图片解码或后端数据库，改用 QUIC 不会自动解决应用瓶颈。

浏览器不会直接用 HTTP/3 首次访问：必须先通过 HTTP/1.1 或 HTTP/2 拿到 Alt-Svc 响应头，才知道该域名支持 h3。所以首访仍是 h2，第二次才走 h3。

连接迁移、0-RTT 与落地坑

  • 连接迁移：手机从 Wi-Fi 切到 4G，IP+端口变了，TCP 连接必断；QUIC 靠 Connection ID 保持连接，只需做路径验证（PATH_CHALLENGE / PATH_RESPONSE）防止地址被劫持。
  • 0-RTT 有重放风险：0-RTT 数据在拿到密钥前就发出，攻击者可重放它。只应对幂等请求启用 0-RTT（GET、可去重读操作），写操作必须等 1-RTT 握手完成。服务端应开启重放防护（单播 Anti-Replay）。
  • 流类型：双向流（客户端发起的请求/响应）与单向流（QPACK 头部压缩的编码器/解码器流、服务端推送）。HTTP/3 中客户端发起的双向流 ID 为 0,4,8…；服务端单向流为 3,7,11…（最低 2 bit 区分类型与发起方）。
  • UDP 被限速/被封：部分运营商、企业防火墙对 UDP 做限速或直接丢弃，表现为 h3 连不上但 h2 正常。生产环境必须保留 HTTP/1.1+HTTP/2 回退（Alt-Svc + 浏览器自动降级）。
  • CPU 开销：QUIC 加解密与拥塞控制在用户态，同等流量下 CPU 明显高于内核 TCP（常见 2–3 倍）。大规模部署要评估 CPU 或把 TLS offload 到专用层。
  • NAT/负载均衡：L4 负载均衡若按四元组哈希转发，QUIC 连接迁移（CID 不变、四元组变）会导致流量被转到错误后端；需要支持 QUIC CID 路由的 LB（如按 CID 做一致性哈希）。
QUIC 真的完全消除了队头阻塞吗？

没有。它消除了连接级队头阻塞（丢包不再影响其它流），但单条流内仍然必须按序交付——一个流内丢包，该流的后续数据仍要等重传。所以“多路复用 + 大文件”场景仍建议拆流或分片传输。

为什么 QUIC 强制最小 MTU 1200？

为了保证在 IPv6 + 各种隧道封装下也能不分片地发出去（IPv6 不允许中间设备分片）。QUIC 首包必须 ≥ 1200 字节（含填充），否则会被用作放大攻击的探针。

自检

HTTP/3 使用 UDP，是否意味着丢包时应用数据不会重传？

不是。UDP 自身不重传，但 QUIC 在其上实现可靠交付、确认和丢包恢复。
