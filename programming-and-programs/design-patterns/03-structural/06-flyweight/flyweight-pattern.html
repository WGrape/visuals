♻️ 享元

共享大量对象中相同的不变部分。

一句话记住森林有十万棵树，树种贴图共用，坐标各不相同。
问题从哪来图解协作动手试一试伪代码选型与边界
01 · 从问题出发

为什么会需要这个模式？

地图标记都保存相同图标、颜色、字体，会重复占用大量内存。

地图上有十万个同类标记，每个标记都保存一份相同的图标像素、字体和颜色。这些数据加起来占用大量内存，而每个标记真正不同的只是坐标和名称。

for point in points:

                      font=Font("Sans", 12),

💡 关键转折

把可共享的内在状态放进享元；坐标等外在状态在调用时传入。

把图标/字体等内在不变状态抽成共享 Style；坐标和名称留在每个标记的外在状态中。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

class StyleFactory {
  cache = Map()
  get(kind) {
    if (!cache.has(kind)) cache.set(kind, immutableStyle(kind))
    return cache.get(kind)
  }
}
for marker in markers:
  draw(factory.get(marker.kind), marker.x, marker.y)

读代码时抓住三件事

  1. cache 的 key 必须能唯一标识共享状态，例如树种+绘制规格。
  2. 共享 Style 应不可变，防止一棵树改动影响所有树。
  3. x/y 不存进 Style，否则所有同类标记会重叠。

换个业务场景，还能认出来吗？

文字编辑器中的每个字符位置不同，但同一字体规格的字形轮廓可共用。享元适合对象数量巨大且重复信息多的场景，不是所有对象都必须缓存。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

海量对象共享大量不变数据，内存重复已可测量

三个具体场景

  • 森林场景复用树种贴图
  • 地图标记复用图标与字体
  • 文本编辑器复用字形轮廓

不适合或要小心

不要把每个对象独有的可变状态写进共享实例；先测量内存收益。

共享状态必须不可变；缓存本身要有生命周期与容量策略

最容易混淆的相邻模式

模式真正的区别
单例限制某个类只有一个实例；享元按 key 管理多个共享实例。
原型复制对象产生独立副本；享元主动共享不变数据以节约内存。

区分时问自己：是全类只允许一个，还是按 key 共享多种对象？

落地前检查

  • 先测量对象数量和重复内存，确认收益。
  • 共享对象设计为不可变。
  • 缓存生命周期和上限要有策略，避免享元工厂本身无限增长。
06 · 自己说一遍

两道检验理解的小题

共用同一贴图的树能有不同位置吗？

能；贴图共享，位置作为外在状态在每次绘制时传入。

为什么 x/y 不应放在共享 Style 中？

坐标是每棵树自己的外在状态；放进共享对象会让同类树只能共用一个位置。

模式速览：把「相同的部分」只存一份

享元解决的是海量相似对象带来的内存压力。思路是把对象状态切成两半：可以共享的叫内部状态，随场景变化的叫外部状态。内部状态只存一份，外部状态由调用方在使用时传入。

意图共享细粒度对象，用少量实例支撑大量逻辑对象
内部状态可共享、不随场景变的部分，存在享元里
外部状态随场景变的部分，由调用方每次传入
核心判断状态能不能拆、拆完共享部分是否足够多
享元的流程：拆状态、共享内部、外传外部

四个相似概念的区别

概念目的共享什么生命周期
享元省内存，支撑海量细粒度对象不可变的内部状态长期存在，按池管理
缓存省计算，避免重复取数计算结果可过期、可淘汰
对象池省创建销毁开销整对象的复用权借出与归还
单例保证全局只有一个整个实例随进程

享元与缓存的边界

享元存的是不可变、可共享的固有属性，比如字符的字形、棋子的颜色与种类；缓存存的是算过一次的结果，目的是避免重复计算，可以失效。享元一般不设失效，因为它本身就是稳定的模板。

享元与对象池的边界

同一个实例是否可以被同时使用？享元可以：多人同时引用同一个字符对象是安全的，因为它不可变；对象池不行：借出期间别人不能用，用完要归还。这是两者最本质的区别。

Go 里的实现：共享不可变模板

// 享元：只包含可共享的内部状态，且不可变 type Style struct { Font string Size int Color string } // 工厂：保证相同内部状态只创建一次 type StyleFactory struct { mu sync.Mutex pool map[string]*Style } func (f *StyleFactory) Get(font string, size int, color string) *Style { key := fmt.Sprintf("%s-%d-%s", font, size, color) f.mu.Lock() defer f.mu.Unlock() if s, ok := f.pool[key]; ok { return s // 命中，直接复用 } s := &Style{Font: font, Size: size, Color: color} f.pool[key] = s return s } // 外部状态由调用方每次传入，不存进享元 func (s *Style) Render(x, y int, text string) string { return fmt.Sprintf("在 (%d,%d) 用 %%s 绘制 %%s", x, y, text) } // 关键点： // 1) 享元里的字段必须是不可变的，否则共享就不安全 // 2) 位置、内容这类随场景变的东西，一律作为参数传入 // 3) 工厂要加锁，因为可能被并发调用 // 4) 池要有规模预估，键的组合爆炸反而会适得其反

深入自检：享元的五个问题

怎么判断该不该用享元？

看三个条件：对象数量极大、对象之间有大量重复的状态、这些重复状态可以剥离出来且不可变。三个都满足才值得。如果只有几百个对象，直接创建更清楚。

外部状态变多了怎么办？

这是享元最容易失控的地方：如果几乎每个字段都随场景变，能共享的所剩无几，拆分的收益就抵消不了复杂度。这时说明它不适合这个场景，应该考虑别的方式，比如对象池或值压缩。

享元池会不会无限增长？

会。如果键的组合空间很大，池里可能积累大量只用一次的实例，反而比不共享更占内存。解决办法是预估组合数量、设置上限、或者对冷门实例做淘汰。

并发下安全吗？

只要享元不可变就安全：多个 goroutine 同时读同一个实例完全没问题。不安全的是工厂本身，创建与查找需要加锁或用并发安全的容器。这也从侧面说明：享元必须不可变。

和字符串驻留是一回事吗？

思路完全一样。很多语言对字符串字面量做驻留，相同内容只存一份，这正是享元思想的典型应用。文本编辑器里的字符样式、游戏里的粒子贴图、地图上的图标，都是同类场景。
