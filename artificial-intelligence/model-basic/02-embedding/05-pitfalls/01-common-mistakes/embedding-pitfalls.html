Embedding 五大踩坑

这些坑在真实项目里反复出现，而且失败得很隐蔽——代码不报错，只是效果差。

1. 五个最常见的 Embedding 踩坑

1.1 坑①：入库与查询模型不一致

图：两条路径必须同模型，否则向量空间断裂。
这是 RAG 第一坑。模型版本、维度、归一化方式、前缀规则，任何一项不一致，旧向量库即失效。

1.2 坑②：维度 / 归一化没对齐

  • 查询向量维度与索引维度不一致（如一个 768 一个 1536）→ 直接报错或结果乱。
  • 索引按 float32 建、查询传了未归一化向量，却用点积当余弦 → 长度长的向量被错误加权。
  • Matryoshka 模型截断维度后，索引与查询截断位数必须一致。

1.3 坑③：切块把语义切碎

硬按 200 字符切，句子从中间断，向量变成'半句话'。症状：召回的内容'看起来相关但答非所问'。解决见切块策略页（父子块 + 重叠）。

1.4 坑④：检索结果没过滤就喂 LLM

top-k 里常混着低相关甚至错误来源。不重排、不过滤元数据（时间/权限），LLM 就会被噪声带偏。接一道 rerank 与元数据过滤是标配。

1.5 坑⑤：拿降维后的坐标算相似度

t-SNE / UMAP 只为'看'，距离已被扭曲。真实检索永远在高维原空间算。降维图里'离得远'不代表真不相关。
