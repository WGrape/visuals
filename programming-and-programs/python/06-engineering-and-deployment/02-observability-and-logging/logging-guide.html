日志：用 logging 替代 print

print 只适合临时调试：不能分级、不能写文件、不能区分模块、生产环境关不掉。标准库 logging 用「logger / handler / formatter」三层架构，把「记什么、写到哪、长啥样」解耦开。

级别

五个级别，按严重程度递增

DEBUG < INFO < WARNING < ERROR < CRITICAL。设了级别后，低于它的日志不输出——生产调成 INFO，排查问题临时调 DEBUG，不用删代码。

setLevel
控制输出门槛
import logging
logging.warning("磁盘快满了")     # WARNING 及以上默认输出
logging.info("启动完成")        # INFO 默认不显示（门槛是 WARNING）
默认级别是 WARNING，所以新手常以为 logging.info 「没生效」——其实是被级别过滤了。记得 setLevel(logging.INFO)。
三层架构

logger 发、handler 送、formatter 打扮

Logger 是入口（你调用它）；Handler 决定送到哪（控制台 / 文件 / 网络）；Formatter 决定格式（时间、级别、模块名）。一个 logger 可挂多个 handler。

代码调用 logger.info()
↓
Logger（含层级名，如 app.db）
↓ 按级别过滤
Handler × N：StreamHandler(控制台) / FileHandler(文件) / ...
↓
Formatter：%(asctime)s %(levelname)s %(name)s %(message)s

层级：logger 名用点号分隔（app.db 是 app 的子 logger），子 logger 默认把日志「冒泡」给父 handler。所以一般在根 logger 配一次 handler，各模块用自己名字的 logger 即可。

basicConfig

快速起步：basicConfig

简单场景用 logging.basicConfig(...) 一次性配好级别、格式、输出目标，不用手动拼 handler。

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(name)s: %(message)s",
    datefmt="%H:%M:%S",
)
logging.info("服务启动")
# 14:03:21 [INFO] __main__: 服务启动
⚠️ basicConfig 只在「根 logger 还没 handler」时生效一次。多次调用只有第一次有效——复杂配置要用 dictConfig 或显式加 handler。
写文件+轮转

日志落盘并自动切割，别撑爆磁盘

用 FileHandler 写文件；生产必须配 RotatingFileHandler（按大小）或 TimedRotatingFileHandler（按时间）做轮转，否则单文件无限增长。

from logging.handlers import RotatingFileHandler
import logging

h = RotatingFileHandler("app.log", maxBytes=5*1024*1024, backupCount=3)
h.setFormatter(logging.Formatter("%(asctime)s %(levelname)s %(message)s"))

log = logging.getLogger("app")
log.addHandler(h)
log.setLevel(logging.INFO)
log.info("写入文件，满 5MB 自动切到 app.log.1")
同时挂控制台 + 文件两个 handler 很常见：控制台给人看（INFO），文件记详细（DEBUG）。各自 setLevel、各自 formatter 互不影响。
模块用法

每个模块用 getLogger(__name__)

在模块顶层创建 logger 时，名字用 __name__（即模块路径）。这样既不会重复创建，又能通过名字精确定位日志来源、按模块开关级别。

# myapp/db.py
import logging
log = logging.getLogger(__name__)   # 名字 = "myapp.db"

def query():
    log.debug("执行查询")        # 日志自动带 db 模块名

# 入口处统一配置根 logger 的 handler 即可
logging.getLogger("myapp").setLevel(logging.DEBUG)

这和编码规范是配套的：统一日志入口、不裸用 print、配置与代码分离。依赖装好后，日志是部署到生产前的最后一块拼图（见FastAPI 部署）。

五个级别怎么用（不是随便选的）

级别数值用途生产是否开启
DEBUG10调试细节（变量值、流程分支）关（排查时临时开）
INFO20关键业务节点：启动、下单、支付成功开
WARNING30可自愈的异常（重试成功、降级）开
ERROR40需要人介入的错误开（要告警）
CRITICAL50系统即将崩溃开（要告警）

判断标准：WARNING 是“我处理了，但你应该知道”；ERROR 是“我处理不了，需要人来看”。最常见的误用是把所有异常都记 ERROR——结果告警泛滥，真正的错误被淹没。

一个硬规则：ERROR 级别的日志必须能触发告警，否则就降级成 WARNING。反过来说，如果一条 ERROR 没人看，它就不该是 ERROR。

性能陷阱：日志也能拖垮服务

logger.debug(f"x={compute()}")f-string 总会执行，即使 DEBUG 关闭logger.debug("x=%s", compute())

日志性能写法

# ✅ 惰性格式化：只有真正要输出时才格式化
logger.debug("user=%s action=%s", user_id, action)   # ✅ 推荐
logger.debug(f"user={user_id} action={action}")      # ❌ 即使不输出也会执行 f-string

# 昂贵参数的惰性求值
if logger.isEnabledFor(logging.DEBUG):              # ✅ 先判断再算
    logger.debug("state=%s", expensive_dump())

# 采样：高频日志只打 1%
class SamplingFilter(logging.Filter):
    def __init__(self, rate=0.01): self.rate = rate
    def filter(self, record):
        return random.random() < self.rate

# 高频路径的正确做法：聚合后打，而不是每条打
counter = 0
def on_event():
    global counter; counter += 1
    if counter % 1000 == 0:
        logger.info("processed %d events", counter)   # 每 1000 条打一次

实测数量级：一条日志的完整开销约 10 – 100 μs（格式化 + IO）。如果请求处理只要 1 ms，打 20 条日志就会让耗时翻倍。所以热路径上要么不打，要么用 异步 handler（QueueHandler）。

异步日志

# 异步日志：把 IO 挪出主线程（高并发服务必备）
from logging.handlers import QueueHandler, QueueListener
import queue, logging

q = queue.Queue(maxsize=10000)                  # 有界，满了降级
handler = QueueHandler(q)
root = logging.getLogger()
root.addHandler(handler)

# 后台线程负责真正写盘
real = logging.FileHandler("app.log")
listener = QueueListener(q, real)
listener.start()
# 退出时：listener.stop()

# 好处：主线程的日志调用变成「入队」，从 100μs 降到 ~1μs
# 代价：进程被 kill 时可能丢最后几条（用 atexit 保证 flush）

结构化日志：让机器能读

JSON 结构化日志

# 生产推荐：JSON 格式（可被 ELK / Loki / ClickHouse 直接解析）
import logging, json, sys

class JsonFormatter(logging.Formatter):
    def format(self, record):
        d = {
            "ts": self.formatTime(record, "%Y-%m-%dT%H:%M:%S"),
            "level": record.levelname,
            "logger": record.name,
            "msg": record.getMessage(),
            "module": record.module,
            "line": record.lineno,
        }
        if record.exc_info:
            d["exc"] = self.formatException(record.exc_info)
        # 关键：把业务字段塞进 extra
        for k, v in getattr(record, "fields", {}).items():
            d[k] = v
        return json.dumps(d, ensure_ascii=False)

h = logging.StreamHandler(sys.stdout)
h.setFormatter(JsonFormatter())
logging.getLogger().addHandler(h)

# 使用：用 extra 带上可检索的字段
logger.info("order created", extra={"fields": {
    "order_id": "ORD123", "user_id": 10086, "amount": 9900
}})
# 输出：{"ts":"...","level":"INFO","msg":"order created",
#        "order_id":"ORD123","user_id":10086,"amount":9900}

结构化日志的核心价值：可以做聚合查询。有了 order_id 字段，就能在 Kibana 里直接搜“这个订单的所有日志”，或用 sum(amount) 统计流水——纯文本日志做不到这些。

  • 必带字段：trace_id（串联一次请求）、user_id、业务主键
  • 禁止打敏感信息：密码、身份证、完整卡号（脱敏后再打）
  • 统一时间格式：ISO 8601 + 时区，别用本地时间让人猜
  • 异常要带堆栈：logger.exception() 自动带 exc_info

配置方式：dictConfig 才是正解

dictConfig 完整示例

# 生产配置（一次写对，别用 basicConfig）
LOGGING = {
    "version": 1,
    "disable_existing_loggers": False,      # 关键！否则第三方库日志全没了
    "formatters": {
        "json": {"()": "myapp.log.JsonFormatter"},
        "plain": {"format": "%(asctime)s %(levelname)-8s %(name)s %(message)s"},
    },
    "filters": {
        "sample": {"()": "myapp.log.SamplingFilter", "rate": 0.01},
    },
    "handlers": {
        "console": {"class": "logging.StreamHandler",
                    "formatter": "json", "level": "INFO"},
        "file": {"class": "logging.handlers.RotatingFileHandler",
                 "filename": "app.log",
                 "maxBytes": 200 * 1024 * 1024,   # 200MB 一个文件
                 "backupCount": 10,               # 保留 10 个 -> 最多 2GB
                 "formatter": "json", "encoding": "utf-8"},
        "error": {"class": "logging.handlers.RotatingFileHandler",
                  "filename": "error.log", "level": "ERROR",   # 单独收集便于告警
                  "maxBytes": 100 * 1024 * 1024, "backupCount": 5},
    },
    "loggers": {
        "": {"handlers": ["console", "file", "error"], "level": "INFO"},
        # 第三方库太吵？单独调高级别
        "urllib3":     {"level": "WARNING"},
        "asyncio":     {"level": "WARNING"},
        "sqlalchemy.engine": {"level": "WARNING"},
        # 自己的模块可以开 DEBUG
        "myapp.payment": {"level": "DEBUG", "propagate": True},
    },
}
logging.config.dictConfig(LOGGING)

两个必知参数：RotatingFileHandler 按大小切分，TimedRotatingFileHandler 按时间切分（when='midnight'、backupCount=7）。生产建议按大小切——按时间切在流量突增时仍可能撑爆磁盘。

深入自检

为什么用了 logging 却什么都没输出？

三个常见原因：① 没设 level——root logger 默认 WARNING，logger.info() 被过滤掉了，要 logging.basicConfig(level=logging.INFO)；② 在 import 阶段就调用了 basicConfig 或被后续覆盖；③ disable_existing_loggers=True（dictConfig 默认就是这个！）——它会禁用所有已存在的 logger，导致第三方库日志消失。务必显式设成 False。

每个模块都要 logger = logging.getLogger(__name__) 吗？

是的，这是标准做法。用 __name__ 的好处是 logger 名字带完整模块路径（如 myapp.payment.service），可以按模块精细控制级别——排查支付问题时只把 myapp.payment 调到 DEBUG，其他保持 INFO，日志量可控且精准。不要直接用 root logger，那样无法区分来源。

日志打太多磁盘满了怎么办？

四道防线：① RotatingFileHandler + backupCount（硬上限，最基础）；② 降级策略——队列满时丢弃低级别日志（QueueHandler 的 maxsize）；③ 采样——高频 INFO 日志按 1% 采样；④ 集中式日志——直接打到 stdout，由容器/采集器收走，本地不留文件（云原生的推荐做法）。

日志、指标、链路追踪三者什么关系？

日志（Logging）记录离散事件（“用户 X 下单了”），适合查细节；指标（Metrics）记录聚合数值（QPS、错误率、p99），适合看趋势和告警；链路追踪（Tracing）记录一次请求的完整路径，适合定位哪个环节慢。三者靠 trace_id 串联——这就是结构化日志必须带 trace_id 的原因。经验比例：指标用于告警，日志用于排查，追踪用于定位瓶颈。
