排队时延与缓冲膨胀：带宽够为何还是卡

用家庭上行链路和小包交互说明队列长度、利用率、突发与尾延迟。

一条链路的四段时间

一个包端到端经历处理、排队、发送和传播等时间。传播时延由距离和介质决定，发送时延约为包大小除以链路速率；排队时延则取决于前面已有多少包。链路空闲时排队几乎没有，链路满载时包可能在网关缓存中等很久。用户感受到的 RTT 会在上行视频、备份或下载占满链路时突然变大，并非光纤传播速度突然变慢。

例如一个 1500 字节包走 10 Mbps 上行链路，纯发送时间约 1.2 毫秒。若前面排着 100 个同样大小的包，单是等待它们发完就约 120 毫秒，尚未计算其他网络段。带宽更大能降低相同队列的发送时间，但若设备也配置更大的缓存且持续填满，延迟仍可能显著增长。

利用率接近上限时

到达速率长期低于服务速率时，队列可在突发后逐渐排空；若到达速率持续超过服务速率，队列增长直到缓存耗尽，随后丢包或阻塞。即使平均到达速率略低于链路速率，短时突发也会排队。随着利用率逼近 100%，排队时间通常对抖动越来越敏感，不能只看五分钟平均利用率 80% 就断言不会拥塞。

把“传输 1 GB 文件用了多久”的吞吐测试与“游戏操作的 P99 延迟”分开。大缓冲可能让下载吞吐看起来平稳，却让小交互包被排在大量数据后。吞吐好、延迟差的组合正是缓冲膨胀的典型信号之一，但还要排除 Wi-Fi 干扰、服务器处理慢和终端 CPU 忙。

一次家庭网络算例

家庭上行 10 Mbps，云备份以接近 10 Mbps 连续上传，视频会议麦克风每隔几十毫秒发小包。若路由器使用简单先进先出队列，语音包可能排在备份数据后，出现数百毫秒延迟和抖动。仅把语音应用“换成 UDP”不会自动插队，UDP 包同样要经过物理链路队列。应在瓶颈前控制备份速率、使用合适队列管理或按业务分类公平调度。

若互联网接入设备之后还有更慢的实际链路，把整形放在更快的本地出口并略低于真实瓶颈速率，可以让可控路由器先排队，而不是让不可控设备缓存堆积。设定速率要留协议开销余量，并在不同时间段实测；运营商实际速率可能波动。

AQM 与公平队列做什么

主动队列管理可在队列形成较大持续延迟前丢弃或标记部分包，给拥塞控制反馈；公平队列把不同流量分开调度，避免一个大流长期压住小流。它们要配合发送端拥塞控制，不能凭一个参数保证所有应用零延迟。某些实时流不按拥塞信号减速时，限速与准入控制仍是必要的。

ECN 可通过显式拥塞标记反馈，而不一定要丢包；是否有效取决于端点与路径支持。TCP 与 QUIC 等协议如何响应丢包或 ECN 也会影响队列恢复。排障需要看设备实际启用的队列算法、丢包或标记率、每类流量延迟，不能只看“QoS 已开启”四个字。

如何区分排队与传播

空闲时测到的 RTT 接近路径的传播、处理和基本发送开销；负载下 RTT 减去空闲 RTT，可粗略反映额外排队和其他负载效应。实验可同时进行受控大流上传与小包 ping，记录 RTT 的 P50、P95、P99 和丢包。若上传一启动尾延迟剧增，停止后很快恢复，优先怀疑瓶颈队列。再用多点测量确认是在家庭网关、接入链路还是远端路径。

ICMP ping 可能被路由器限速或低优先级处理，不能仅凭中间一跳 ping 变慢就断言转发数据也同样变慢。结合端到端业务时延和接口队列统计，结论更稳妥。

优化后的验收

先给出两个目标：下载或上传吞吐不低于业务底线，同时交互流在负载下的 P95/P99 延迟不超过约定值。对照测试前后同样的客户端、时间窗、并发和负载，记录丢包、ECN、队列长度和整形速率。若降低速率后延迟改善但吞吐下降过多，逐步调节瓶颈前整形与队列参数。

不要无限增加设备缓冲来“消灭丢包”。队列只是把丢包推迟成等待，对实时业务未必更好。选择要基于实际应用的时延与吞吐目标，而非单一的链路利用率。

排队延迟的量化

链路利用率 ρ平均排队中的包数相对空队列的延迟倍数体感
50%12×正常
70%2.33.3×可接受
80%45×开始明显
90%910×明显变慢
95%1920×接近不可用
99%99100×排队爆炸

上表按 M/M/1 排队模型：系统中的平均包数 L = ρ/(1−ρ)，延迟随利用率非线性上升。这就是“带宽明明够用，一到高峰期就卡”的数学解释——不是带宽不够，是队列排队。

Bufferbloat（缓冲膨胀）：队列缓冲太大时，突发流量把缓冲填满却迟迟排不出去，延迟从几毫秒涨到几百毫秒甚至数秒，而吞吐量看起来仍是满的。典型场景：家用路由器一边下载一边视频通话，通话卡成 PPT。

队列大小后果适用
太小（< BDP）丢包多，带宽跑不满低吞吐场景
= BDP理想：既能跑满带宽又不额外排队理论上界
太大（>> BDP）Bufferbloat：延迟飙升大多数默认配置的现状

BDP（带宽时延积） = 带宽 × RTT。例：1 Gbps × 20 ms = 2.5 MB。队列缓冲超过这个值就是纯粹的延迟负担。

排队延迟实测

# 测空载延迟 vs 满载延迟（判断 bufferbloat）
ping -c 20 8.8.8.8                      # 空载基线（如 10 ms）
#  同时跑满带宽：
iperf3 -c server -P 8 -t 60 &
ping -c 20 8.8.8.8                      # 满载时延（若涨到 500ms+ 就是 bufferbloat）

# 现代队列管理（fq_codel / CAKE）
tc qdisc replace dev eth0 root fq_codel
tc qdisc replace dev eth0 root cake bandwidth 100mbit nat
tc -s qdisc show dev eth0

# 限速 + 抗 bufferbloat（家宽/网关常用）
tc qdisc add dev eth0 root cake bandwidth 100mbit besteffort

# 看队列丢包与积压
tc -s qdisc show dev eth0     # 看 dropped、backlog
cat /proc/net/softnet_stat    # 看软中断丢包（第 2 列）

缓解手段与排障

  • 根本解法是主动队列管理（AQM）：fq_codel（默认已集成在多数 Linux）或 CAKE。它们在队列还没满时就主动丢包/标记 ECN，向 TCP 发出拥塞信号，让发送方降速——用少量丢包换极低延迟。
  • ECN（显式拥塞通知）：不丢包，而是在 IP 头打标记告知拥塞。需两端都开启（sysctl net.ipv4.tcp_ecn=1），配合 AQM 效果最好。
  • 不要把缓冲调大来解决丢包。丢包是拥塞的信号，加大缓冲只是把信号藏起来，让延迟恶化。这条对交换机、网卡 ring buffer、socket buffer 都适用。
  • 网卡 ring buffer：ethtool -g eth0 看；突发流量场景适当调大（ethtool -G eth0 rx 4096），但同样别无脑加大。
  • 排障顺序：① 空载 vs 满载延迟对比，确认是否 bufferbloat；② tc -s qdisc 看 backlog 与 dropped；③ 换 fq_codel/CAKE 复测；④ 检查是否有不必要的多层限速（如 tc + 硬件队列）。
  • 应用层配合：BBR 拥塞控制对深缓冲链路比 CUBIC 友好（它测最小 RTT，能感知到排队）；sysctl -w net.ipv4.tcp_congestion_control=bbr。
带宽跑满了但延迟只有几十毫秒，是 bufferbloat 吗？

不算。判断标准是空载与满载延迟的比值：延迟增加 5–10 倍、达到数百毫秒才算典型的 bufferbloat。几十毫秒可能是正常的排队与串行化时延。

为什么限速反而让网络感觉更快？

把瓶颈从“运营商/设备的巨大缓冲”移到你自己可控的队列（CAKE/tbf）后，队列长度变短、延迟下降。交互式应用（游戏、语音）会明显变流畅，代价是总吞吐略降。

自检

把语音流从 TCP 改为 UDP，就一定能避开链路上的排队吗？

不能。UDP 包同样经过瓶颈队列；还需速率控制、公平调度或合适的队列管理。
