05 流处理 · 时间语义

Watermark 与迟到数据：流处理如何判断"时间到没到"

批处理里，"这个小时的数据"是明确的——跑任务时数据都躺在磁盘上。但流处理里，数据是边来边算的：系统根本不知道还有没有 10:00 的数据在路上。Watermark 就是为了回答这个问题而发明的机制：它是一种"我确信不会再有更早数据了"的声明。本文讲清三种时间语义、乱序的根源、Watermark 如何推进窗口，以及迟到数据的三条处理路线。

1先分清三种"时间"

一切混乱的源头：一条数据至少带着三个不同的时间戳，而窗口该按哪个切，决定了结果的正确性。

同一条数据上的三个时间戳

时间语义取自哪里确定性典型用途
Event Time
事件时间		数据自身携带的业务时间戳（由产生端写入）确定、可重现：重放历史数据结果一致绝大多数业务场景的正确选择：按"用户行为发生的小时"统计
Processing Time
处理时间		算子所在机器的系统时钟不确定：重跑结果会变，受负载影响只关心"现在"的监控告警；对乱序零容忍、要求极低延迟
Ingestion Time
摄入时间		数据进入 Flink / 引擎时由 Source 打的当前时间介于两者之间源端没带时间戳，又想要比 Processing Time 稳定一点的场景
为什么 Event Time 才是"对"的？业务问的是"昨天 10 点有多少订单"，不是"机器昨天 10 点处理了多少条"。如果按 Processing Time 切窗口，一次 GC 停顿、一次回溯消费历史数据、一次作业重启，都会让结果完全不同。Event Time 保证：同样的输入数据，无论何时跑、跑几次，结果都一样——这是流处理的正确性基石。

2乱序：为什么数据不按时间先后到达

如果数据严格按 Event Time 递增到达，窗口到点就能直接关。但现实永远不会这么理想：

📶 网络抖动

移动端 App 埋点，弱网时数据缓存在本地，恢复后一次性补传——几小时前的数据现在才到。

🔀 多分区并行

Kafka 一个 Topic 有 8 个分区，消费者并发拉取。分区之间没有任何顺序保证，Partition-3 拉到 10:05 的数据时，Partition-7 可能还在处理 10:01 的。

🐢 上游系统延迟

数据库 CDC 同步卡了、批处理任务补数、跨机房同步——都会制造"旧数据晚到"。

🔁 作业故障回溯

作业挂了从 Checkpoint 恢复，会重新消费一段历史数据，这些数据的 Event Time 远早于当前。

核心矛盾窗口不能无限等下去（否则永远不出结果、状态无限膨胀），但关早了又会漏掉迟到的数据。Watermark 就是在"等多久"和"多快出结果"之间的一个显式、可调的折中。

3Watermark 是什么：一句话定义

Watermark(t) 的含义一条流中插入的特殊标记，声明："事件时间 ≤ t 的数据，我已经全部看完了，后面不会再来了。"
它是一个单调递增的时钟，告诉引擎"可以把 t 之前的窗口关掉、触发计算了"。
⚠️ 注意：这是一个启发式的猜测，不是绝对保证——它猜错了，就会有迟到数据。

单调递增乱序（Bounded Out-of-Orderness）最常见的生成方式

// Flink：允许 3 秒乱序
WatermarkStrategy
  .<Event>forBoundedOutOfOrderness(Duration.ofSeconds(3))
  .withTimestampAssigner((event, ts) -> event.getEventTime());

// 生成规则：Watermark = 目前见过的最大 EventTime - 3秒 - 1毫秒
// 含义：我容忍最多 3 秒的乱序，超过 3 秒才来的就是迟到数据

Watermark 推进与迟到数据的产生

4Watermark 如何决定窗口关闭

Watermark 到达算子
→
检查所有窗口
窗口 end ≤ Watermark ?
→
触发计算
输出窗口结果
→
（默认）清理状态
关键规则一个窗口 [start, end) 会在 Watermark ≥ end 时被触发。注意"≥ end"，不是"> start"——窗口是左闭右开的，end 本身属于下一个窗口。

多并行度下的取小规则

一个算子并行度为 4，每个子任务各有自己的 Watermark。下游算子看到的 Watermark 是所有上游的最小值：

上游分区 Watermark:  [10:05]  [10:08]  [10:03]  [10:07]
                                  ↓ 取 min
下游算子看到的:      [10:03]     ← 必须取最小，否则会漏数据

// 直觉：木桶效应。最慢的那一路还没到 10:05，
// 下游就不能假设"10:05 之前的数据都齐了"。
Idle Source（空闲源）陷阱如果某个 Kafka 分区长时间没有数据，它的 Watermark 会卡住不动，导致整个下游的 Watermark（取 min）永远不推进 —— 所有窗口都不触发，作业看起来"卡死"了。
解法：标记空闲源 .withIdleness(Duration.ofMinutes(1))，让空闲分区在一定时间后暂停参与 min 计算。

5迟到数据：三条处理路线

Watermark 是猜测，猜错了必然有迟到数据。怎么处理，取决于业务能不能接受"结果后来被修正"。

路线做法结果正确性状态开销适用
① 直接丢弃
（默认）		窗口触发后清状态，迟到数据扔掉会丢数据最小实时监控大屏、趋势类指标，少量丢失无妨
② 允许迟到
allowedLateness		窗口触发后状态再保留一段时间，期间每条迟到数据重新触发一次计算最终正确（但会输出多次结果）中等要求准确、下游能接受增量修正结果
③ 侧输出
sideOutput		超过允许迟到期的数据，丢到一条独立的旁路流不丢，只是分流可控需要兜底：迟到数据单独落库、事后对账补偿
 
// Flink：完整兜底组合
OutputTag<Event> lateTag = new OutputTag<Event>("late-data") {};

SingleOutputStreamOperator<Result> result = stream
    .keyBy(Event::getUserId)
    .window(TumblingEventTimeWindows.of(Time.minutes(10)))
    .allowedLateness(Time.minutes(2))          // ② 窗口再等 2 分钟
    .sideOutputLateData(lateTag)               // ③ 超时的丢到旁路
    .aggregate(new MyAggregateFunction());

// 单独消费旁路，落库/告警/对账
DataStream<Event> lateStream = result.getSideOutput(lateTag);
lateStream.addSink(new LateDataSink());
语义提醒开了 allowedLateness 后，一个窗口可能输出多次结果（首次触发 + 每条迟到数据再触发一次）。如果下游是"只写一次"的存储（如 HBase 覆盖写），这没问题；如果是"累加"的存储（如 INSERT 到 MySQL），必须改成幂等 upsert，否则数字会重复累加。

6乱序容忍度设多大：一个实操方法

设太小 → 大量迟到数据被丢，结果不准；设太大 → 窗口迟迟不触发，延迟变高、状态堆积。经验做法：

  1. 先量化再拍板：在作业里埋一个指标，统计 ProcessingTime - EventTime 的分位数（P95 / P99 / P99.9）。
  2. 初始值：取 P99 作为乱序容忍度。这样 99% 的数据都能进窗口。
  3. 再观察：看侧输出流里迟到数据的量。若占比 > 0.1%，说明设小了，往上调。
  4. 权衡延迟：乱序容忍度 = 3s，意味着窗口最快也要等到 窗口结束 + 3s 才输出，这就是额外的固有延迟。
不要设成几分钟"保险"乱序容忍度直接转化为两部分成本：① 结果延迟；② 状态大小（所有未触发窗口的数据都得留在 State 里）。设成 5 分钟，意味着状态里始终压着 5 分钟的数据量，Checkpoint 也会变大变慢。

7常见误区

"Watermark 到了，说明所有数据都到齐了"
错。Watermark 只是一个启发式声明——"我猜不会再有更早的了"。它不保证。正因为会猜错，才需要 allowedLateness 和侧输出兜底。
"Watermark 会随真实时钟自动走"
错。Watermark 只会随数据推进——它由"目前见到的最大 Event Time"推导出来。如果上游完全不发数据，Watermark 就永远不动，窗口永远不触发。这正是 Idle Source 问题的根源。
"用 Processing Time 就没有乱序问题，所以更好"
代价是正确性。Processing Time 窗口确实永不迟到、延迟最低，但结果是不可重现的：一次作业重启、一次回溯消费、一次机器负载波动，同一份数据算出来的数都不一样。除了"实时性压倒一切"的监控场景，业务统计都应该用 Event Time。
"allowedLateness 开得越大越准，那就开大点"
有代价。窗口状态要一直保留到 allowedLateness 结束，状态越大 → Checkpoint 越大越慢 → 恢复越久；同时结果延迟也越大。正确做法是先量测真实乱序分布，再按需设置，而不是拍脑袋开大。
