分库分表 / 数据分片

单库扛不住时，把数据按规则拆到多个库/表，水平扩展容量与性能。

分片拓扑 Sharding

同一张逻辑表，物理上落在不同库不同机

当单表/单库达到容量或连接数瓶颈，按<b>分片键</b>(sharding key，如用户ID)把数据分布到多实例：<b>水平分表</b>（同库多表）、<b>水平分库</b>（跨实例）。路由层（如 ShardingSphere、Vitess）屏蔽底层拆分。

分片键选择

  • 选高频查询维度，让大部分请求落单分片。
  • 避免数据倾斜（某 key 过热）。
  • 避免跨分片 join / 分布式事务——能避免就设计掉。

代价

  • 跨分片查询/聚合变复杂（需汇总多个分片）。
  • 扩容需数据再平衡（一致性哈希可减迁移量）。
  • 分布式事务更难。

面试高频问答

Q：分库分表和读写分离能一起用吗？
A：能，且常叠加：先按业务/分片键分库分表解决容量，再对每个分片做主从读写分离解决读压力。两者解决不同维度问题。
Q：一致性哈希在分片里的价值？
A：扩容加节点时，一致性哈希只需迁移邻近部分数据而非全量重分布，大幅降低再平衡成本与抖动。
