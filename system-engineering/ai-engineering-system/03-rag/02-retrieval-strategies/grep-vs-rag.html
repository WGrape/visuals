代码检索：何时用 grep，何时用 RAG？

按查询类型、仓库规模、更新频率和延迟要求选择检索方式

代码检索的核心需求

代码 ≠ 自然语言文档。代码有它特殊的检索属性：

已知符号
精确匹配
功能意图
语义召回
最终验证
读取源码
关键洞察：查找已知函数名、变量名和类名时，精确匹配通常是第一步；若只知道“哪里处理登录失败”这类意图，语义检索或多轮关键词搜索也可能有用。
精确检索示例
# 在代码库中查找已知符号和路径
grep -rn "getUserById" --include="*.ts"
grep -rn "import.*AuthService" --include="*.ts"
grep -rn "shell/" --include="*.md" --include="*.json" --include="*.js" | grep -v ".git"

grep 只做一件事：字符串匹配。但配合 LLM 的推理能力，效果出奇地好。

仅靠向量检索时要处理的三个问题
缺陷一：向量化会丢失精确符号
embedding 可能把不同符号映射到相近向量；已知符号和调用关系仍需关键词或结构化检索核对。
缺陷二：索引构建成本高且过期快
代码变更后要维护索引新鲜度，构建与更新成本取决于仓库规模、切分方式和增量更新能力；直接搜索当前文件无需预建索引。
缺陷三：检索粒度难以控制
代码按行、函数或文件切分，各有上下文取舍；召回后仍需读取完整定义及调用方。关键词搜索通常能直接给出文件和行号。

grep 方案

  • 零构建成本，随用随搜
  • 延迟取决于仓库大小与搜索范围
  • 符号匹配确定，但同名结果仍需核对
  • 天然支持正则表达式
  • 文件变化实时可见
  • 返回行号，可精确读取上下文
  • 不依赖任何额外基础设施

RAG 方案

  • 需要检索索引和更新机制
  • 建索引有前置成本
  • 可能返回语义相近但错误的结果
  • chunk 切分策略复杂
  • 索引实时性难保证
  • 可保留文件和位置元数据，仍需核对源码
  • 依赖 embedding 模型质量

LLM 承担"语义理解"，grep 承担"精确定位"。职责分离，各司其职。

工程哲学总结

已知名称或调用点时，先用关键词和结构化检索定位；自然语言意图较模糊、仓库较大且索引可保持新鲜时，可补充语义召回。两种方式可以组合，最终都要读取当前源码验证。

选型回答：三个判断维度

面试官问这题，真正想考察的是你对"工具与问题匹配"的判断力，而不是 RAG 知识本身。

第一层：代码的本质决定检索策略

已知函数名、类名或变量名时优先精确搜索；只有功能描述而不知道符号时，语义检索可以帮助找候选。

第二层：工程成本与实时性

比较仓库变化频率、增量索引能力、查询并发与延迟目标。直接搜索读取当前文件；索引检索要付出构建和同步成本。

第三层：LLM 已经替代了 RAG 的"语义桥"角色

LLM 可推断关键词并迭代搜索，也可结合语义召回与调用图。无论哪种方案，回答或修改代码前都要打开当前文件核实。

延伸：大型代码库的 Code RAG 方案；Claude Code 的本地检索工作流。
