01什么是系统调用

第一层

概念与判定

系统调用（system call）是用户态程序进入内核态的唯一合法入口。它不是普通函数调用，而是一次受控的「特权切换」。

判据是系统调用不是系统调用
是否切换 CPU 特权级是，ring3 → ring0否，全程 ring3
是否经过内核代码是否（纯用户态库函数）
例子read/write/fork/mmapstrlen/memcpy/printf 的格式化部分
printf 不是系统调用——它先在用户态格式化字符串，最后调用 write 才真正陷内核。所以「打印很多但写得少」时，printf 的开销主要在格式化而非 syscall。

02一次系统调用的完整路径

图：从 printf 到 sys_write 的完整路径。红色为进入内核，绿色为返回用户态。
  1. 应用调用 printf → libc 在用户态完成格式化，拼出缓冲区。
  2. libc 调用 write(fd, buf, n) 的封装：把系统调用号放进 rax，参数放进 rdi/rsi/rdx/r10/r8/r9。
  3. 执行 syscall 指令：CPU 切到 ring0，跳转到内核预设的入口 entry_SYSCALL_64。
  4. 内核保存用户寄存器、检查参数合法性，按 rax 查 sys_call_table 调用 sys_write。
  5. 内核完成实际工作（拷数据、操作文件/设备），把返回值写回 rax。
  6. 执行 sysret 返回用户态，libc 检查 rax 是否为负错误码（如 -EFAULT），转为 errno。

03系统调用 vs 普通函数调用

维度普通函数调用系统调用
特权级不变（ring3）切换 ring3 → ring0 → ring3
栈用户栈内核栈（每个线程独立内核栈，通常 8–16 KB）
开销几 ns ~ 几十 ns100–500 ns（含模式切换、TLB/分支预测扰动）
可中断性不会被内核抢占点打断可能被信号/调度打断
参数传递寄存器 + 栈，任意复杂类型寄存器传参，指针需内核 copy_from_user 校验
错误报告返回值/异常返回负 errno，且不设置用户态 errno（由 libc 转）
高频 syscall 是性能杀手：每秒百万次 gettimeofday 会让 CPU 大量耗在模式切换。解法是批量（readv/writev/io_uring）、缓存（vDSO）、合并（缓冲区）。

04系统调用号、寄存器与 ABI

x86-64 Linux 的 syscall ABI 是硬约定，写汇编或分析 core dump 时必须背下来：

寄存器作用
rax入参：系统调用号；返回：返回值（负数为 -errno）
rdi / rsi / rdx第 1 / 2 / 3 个参数
r10 / r8 / r9第 4 / 5 / 6 个参数
rcx / r11被 syscall 指令覆盖（存返回地址 / RFLAGS），不要依赖
# 手写一次 write(1, "hi\n", 3)
mov $1, %rax      # 1 = sys_write
mov $1, %rdi      # fd = stdout
lea msg(%rip), %rsi
mov $3, %rdx      # count
syscall
msg: .ascii "hi\n"

调用号定义在 arch/x86/entry/syscalls/syscall_64.tbl，可用 ausyscall --dump 或 /usr/include/asm/unistd_64.h 查看。

05vDSO：不陷内核也能读时间

如果每次读时间都陷内核，代价太高。Linux 用 vDSO（virtual dynamic shared object）把一小段内核代码映射进用户地址空间：

调用方式典型耗时
clock_gettime(CLOCK_MONOTONIC)走 vDSO，纯用户态~20–30 ns
gettimeofday走 vDSO（若可用）~25 ns
clock_gettime(CLOCK_REALTIME) 首次可能陷内核校准~300 ns
read 等真实 IO必然陷内核数百 ns 起

vDSO 靠内核在共享页里维护实时数据（如 vdso_data 的 seqcount），用户态读取时用序列锁保证一致性，不需要 syscall。

命令验证：strace -c -e trace=clock_gettime ./prog 若显示 0 次调用，说明走的是 vDSO。

06用 strace 看清 syscall

# 统计每个 syscall 的次数、耗时、错误
strace -c -f ./server

# 只看与文件相关的调用
strace -e trace=openat,read,write,close ./prog

# 跟踪子进程并打印时间戳
strace -f -tt -T -p 1234
常见输出含义
= -1 ENOENT文件不存在（高频但常被忽略）
= -1 EAGAIN非阻塞 IO 暂无数据，属正常
= -1 EINTR被信号打断，需重试
restart_syscall被信号打断后内核自动重启阻塞调用
strace 会拖慢程序 10–100 倍：它用 ptrace 让每次 syscall 都停两次（进入+返回）。生产环境慎用，改用 perf trace 或 eBPF（bpftrace）采样。

07排障与边界

第三层

排障与边界

  • 「Too many open files」：不是 syscall 失败，而是 EMFILE（进程 fd 用尽）或 ENFILE（系统 fd 用尽）。查 ulimit -n 与 /proc/sys/fs/file-max。
  • 「Operation not permitted」：EPERM 常见于容器里缺 capability（如 CAP_SYS_ADMIN），而非真的没 root。
  • seccomp 拦截：容器默认 seccomp 白名单会拒绝部分 syscall（如 ptrace/mount），表现为 EPERM 或进程被 SIGSYS 杀死。
  • 参数指针非法：内核用 copy_from_user 校验用户指针，传野指针返回 EFAULT 而非段错误。
  • x32 ABI 混淆：32 位程序在 64 位内核上用不同调用号（__NR_* 带 0x40000000 位），混用会得到 ENOSYS。

08原理与取舍

第四层

原理与取舍

为什么必须陷内核？因为硬件把「能执行特权指令」的能力绑定在 ring 级别上。只有 ring0 能改页表、开关中断、直接访问设备寄存器。用户态要这些能力，只能通过受控入口请求。

设计选择好处代价
陷门式 syscall隔离强、可审计每次切换 100–500 ns
vDSO常用只读数据零切换只适用于无副作用操作
io_uring批量提交/完成，摊薄切换复杂度高、需内核 5.1+
seccomp-bpf按 syscall 号过滤，缩小攻击面误杀合法调用难排查

深入 Q&A

Q：为什么 syscall 比 int 0x80 快？
A：int 0x80 走完整的中断门，要查 IDT、压栈、走通用中断返回；syscall 是专用指令，用 MSR 直接跳到入口，省掉中断控制器的往返。

Q：一个 syscall 能被信号打断吗？
A：能。阻塞中的 syscall 收到信号会返回 EINTR；若 handler 带 SA_RESTART，内核会自动重启，应用看不到中断。

09速记卡

唯一入口

用户态进内核只能靠 syscall（或异常/中断），没有别的合法路径。

寄存器约定

rax=号/返回值，rdi,rsi,rdx,r10,r8,r9=参数。

开销量级

100–500 ns，比函数调用贵 1–2 个数量级。

vDSO

读时间不陷内核，~25 ns。

strace 会拖慢

10–100 倍；生产用 perf/eBPF。

错误约定

内核返回负 errno，libc 转成 -1 + errno。
