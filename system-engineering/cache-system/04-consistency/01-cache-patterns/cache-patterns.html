什么时候适用？

判断信号：读多写少、数据库查询昂贵，而且业务能明确接受多长时间的旧值；先确定谁负责回源与写库。

  • 商品详情页的热点商品：应用用 Cache-Aside 缓解数据库读压力，并在改价后删缓存。
  • 多应用共用同一缓存代理：用 Read-Through 集中处理未命中加载，减少每个应用重复写回源逻辑。
  • 计数或遥测写入量大且允许延后落库：用 Write-Behind 批量刷库，配可靠队列和恢复流程。

和相近模式怎么区分？

相近方案选择边界
Cache-Aside 与 Read-Through前者由应用回源并回填；后者由缓存层在未命中时加载。两者都描述读路径。
Write-Through 与 Write-Behind前者写库完成后确认；后者先确认、后刷库。后者吞吐较高，但必须承担持久化与故障恢复。

核心伪代码

function readAside(key):
  value = cache.get(key)
  if value == MISS:
    value = db.get(key)
    cache.set(key, value, ttl)
  return value

function writeAside(key, value):
  db.update(key, value)
  cache.delete(key)

// Through/Behind 的 DB 访问位于缓存层实现中。

选型关键：Cache-Aside 简单但并非强一致；Through 依赖缓存层的读写代理能力；Write-Behind 用延迟和丢失风险换写吞吐。

为什么 Cache-Aside 最流行

应用自行管理回源与失效，接入简单。读：缓存未命中→查库→回填；写：先提交数据库→删除缓存。缓存故障会把更多流量推向数据库，需要限流和回源保护。

对比

模式数据库访问责任确认时机与主要代价
Cache-Aside应用负责读库和写库写库后删缓存；有并发旧值回填窗口
Read-Through缓存层负责读未命中的回源只规定读路径，不规定写库时机
Write-Through缓存层同步写库数据库写成功后确认；延迟较高
Write-Behind缓存层异步刷库先确认、后落库；需可靠队列和恢复

🎯 面试问答

Q：为什么 Cache-Aside 常见？
A：应用可直接控制读库、写库与缓存失效，接入门槛低；缓存异常时仍要保护数据库。
Q：Write-Through 和 Write-Behind 区别？
A：前者同步写库后确认；后者先确认、异步刷库，必须处理待写数据持久化与恢复。
Q：写时删缓存还是更新缓存？
A：常用删缓存并让读请求懒加载，可减少双写步骤；并发旧值回填窗口仍需单独处理。

四种模式速查：先问「谁负责写缓存」

读写模式的区别本质上只有一个问题：缓存是由应用代码维护，还是由缓存层自己维护。想清楚这一点，四种模式就不再需要死记。

模式谁写缓存一致性写延迟适用
Cache-Aside应用自己：读时回填，写时删除较弱，依赖删除时机低最通用，读多写少
Read-Through缓存层自己：未命中时它去库里取同 Aside，但对应用透明低希望应用代码更干净
Write-Through缓存层同步写库再写缓存强，写穿即一致较高，每次写多一跳一致性要求高、写不太频繁
Write-Behind缓存层先写缓存，异步批量落库最弱，有丢失窗口最低写极密集、可容忍短暂丢失
读写路径对照：Aside 与 Through 的区别在「谁来维护缓存」，不在读路径

Cache-Aside 的细节：为什么是删缓存而不是更新缓存

这是最常被追问的一题。答案是两个原因叠加：避免无效写入，避免并发下的顺序错乱。

原因一：更新可能白做

如果这个值写入后很少被读，那么每次写都顺手更新缓存是纯粹的浪费。删除则更懒惰也更划算：下次真有人读时才重新加载，天然淘汰冷数据。

原因二：并发下会写脏

两个并发写 A 后 B，若更新缓存的顺序反过来，缓存里留下的是旧值 A，而数据库是 B，从此读到的一直是错的——直到缓存过期。删除则不会留下错误值，最多只是多一次回源。

# 推荐顺序：先更新数据库，再删除缓存 def update_item(item_id, new_val): db.update(item_id, new_val) # 1) 数据源先落定 cache.delete(item_id) # 2) 让缓存失效 # 为什么不反过来（先删缓存再更新库）？ # T1 删缓存 -> T2 读未命中 -> T2 回源读到旧值 -> T2 回填旧值 # -> T1 更新库完成 # 结果：缓存里是旧值，且要等过期才恢复，窗口更长 # 先更库再删缓存也有小窗口，但概率极低： # 要求「缓存刚好失效」且「回源读发生在更新前、回填发生在删除后」 # 实际中可用「延迟双删」进一步收敛： def update_item_safe(item_id, new_val): db.update(item_id, new_val) cache.delete(item_id) schedule_after(500ms, lambda: cache.delete(item_id)) # 补刀

Cache-Aside 下仍然会遇到的三个坑

缓存删除失败了怎么办？

删除失败意味着缓存里一直是旧值，而且没有过期兜底就会长期错误。做法是给删除加重试与兜底：失败后写入重试队列异步补偿，同时给所有缓存设置合理的过期时间作为最后一道防线。

延迟双删真的有必要吗？

它解决的是极小概率的并发脏读窗口。多数业务不需要；只有在数据一致性要求很高、且确实观测到这类问题时才引入，否则只是增加一次额外的缓存操作成本。

热点 key 失效会怎样？

这就是缓存击穿：一个极热的 key 过期瞬间，大量请求同时回源，把数据库打穿。常见解法是互斥重建（只放一个线程去回源，其他等待）、或者逻辑过期（物理上永不过期，由后台异步刷新）。

Write-Behind 丢数据能接受吗？

只在特定场景可以：写入极密集、单条价值不高、可容忍进程崩溃时丢失最近一小段写入，比如计数、埋点、点赞数。涉及金额与订单的关键数据绝不能用。

怎么选：一张决策清单

默认选择读多写少、通用场景：Cache-Aside
想简化代码希望应用不关心缓存：Read-Through
写后必须立刻一致Write-Through，接受写延迟
写极其密集Write-Behind，接受短暂丢失
数据几乎不变长过期时间 + 启动时预热
强一致要求不要靠缓存模式解决，考虑事务与读主库
务必设过期所有 key 都要有兜底过期时间
删除要重试失效操作失败必须补偿

一句话记忆：缓存模式解决的是「性能与一致性的取舍」，它不能创造一致性——如果你需要强一致，正确做法是绕过缓存直接读数据源，而不是找一个更聪明的缓存模式。
