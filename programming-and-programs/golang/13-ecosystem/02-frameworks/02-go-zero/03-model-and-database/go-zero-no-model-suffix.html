为什么 go-zero 生成的 model 文件没有 _model 后缀？

你观察得完全对：默认 gozero 风格下，goctl 吐出来的文件名是 usermodel_gen.go，而不是 user_model.go，更不会是 xxx_model.go 这种「带 _model 后缀」的样子。这篇把「为什么没有」讲到底——核心是 goctl 怎么拼基础名、以及 --style 怎么二次格式化它。

先给结论

默认风格下，_model 这个下划线被「风格格式化器」吃掉了

goctl 并不是「给 model 文件统一加 _model 后缀」；相反，它先把「表名 + _model」拼成一个基础名，再把这个基础名整个丢进 FileNamingFormat 按 --style 重新拼写。默认 gozero 是「无分隔符连写」，于是下划线没了 → usermodel_gen.go。

记住这三条就够了：

① model 文件的基础名 = 表名 + "_model"（goctl 内部拼的），不是「文件名 + 后缀」。
② 这个基础名会整体过一遍 --style 格式化：gozero 把所有词连写 → 下划线消失；go_zero 才保留下划线。
③ 所以默认生成的文件是 usermodel_gen.go（连写），只有当你显式用 --style go_zero 时才会变成 user_model_gen.go（带下划线）。

实际产物

你用默认 go-zero 生成时，看到的真实文件名

以一张叫 user 的表、一个叫 login 的 @handler 为例，什么参数都不加（即默认 gozero） 跑出来的文件：

model/ ├── usermodel_gen.go ← 自动生成，可覆盖 ├── usermodel.go ← 你手写扩展放这 └── vars.go internal/handler/ ├── loginhandler.go ← 没有 _handler 后缀 └── routes.go internal/logic/ └── loginlogic.go ← 没有 _logic 后缀
重点：这里从头到尾没有 _model、_handler、_logic 这种「带下划线的后缀」。唯一出现的 _gen 是真后缀（详见第 ④ 节），它跟 style 无关、永远在。
源码机制

goctl 到底怎么拼出基础名？

三个目录（model / handler / logic）的「基础名」来源完全不同，这是理解「为什么没下划线」的关键。下面三段都来自 go-zero 源码。

① model：基础名 = 表名 + "_model"

在 goctl model 的生成代码里，文件名是这样来的：

modelFilename, _ := format.FileNamingFormat(g.cfg.NamingFormat,
    fmt.Sprintf("%s_model", tn.Source()))   // 表名 + "_model" 拼成基础名
name := util.SafeString(modelFilename) + "_gen.go"   // 末尾再接 _gen.go

注意：goctl 是先自己把 _model 拼进基础名的，这张表叫 user，基础名就是 user_model。这个 _model 是「内部拼接」出来的，不是给文件加的「类型后缀」。

② handler / logic：基础名 = handler名 + "Handler"/"Logic"（驼峰连写）

在 goctl api 的 gogen 里，handler、logic 的文件名基础串是驼峰拼接的（没有下划线）：

// @handler login  → 基础名 loginHandler（login + Handler 连写）
// @handler login  → 基础名 loginLogic  （login + Logic  连写）
filename := format.FileNamingFormat(style, baseName)  // baseName 形如 loginHandler

所以 Handler / Logic 也是「拼进基础名的词」，不是独立后缀。gozero 下连写 → loginhandler；go_zero 下在词界插下划线 → login_handler。

③ 结构体名：走另一条路，永远 PascalCase

同一个生成过程里，Go 标识符和文件名是分开算的。结构体名来自 ToCamel()：

"upperStartCamelObject": in.Name.ToCamel(),   // user → UserModel（PascalCase）
"lowerStartCamelObject": stringx.From(in.Name.ToCamel()).Untitle(),

所以无论文件名变成 usermodel_gen.go 还是 user_model_gen.go，结构体始终叫 UserModel。文件名怎么拼，和代码里怎么命名是两码事。

核心解答

「为什么没有 _model 后缀」的两个原因

合起来就解释了你的观察。

原因 1：默认风格是 gozero
源码里 DefaultFormat = "gozero"，即「无分隔符连写小写」。基础名 user_model 过一遍 → 词全连起来 → usermodel。下划线是风格的产物，默认风格把它吞了。网上有些旧文档说「默认是 go_zero」，那是错的。
原因 2：_model 不是「后缀」而是「基础名的一部分」
goctl 是「表名 + _model」先拼好再整体格式化。它从来没有「在文件名末尾统一贴 _model 后缀」这一步。所以不存在「_model 后缀被去掉」这回事——它从一开始就被并进连写里了。

图：基础名 user_model 经过 FileNamingFormat 后，下划线「存不存在」完全由 style 决定。

澄清概念

真后缀 vs 拼接词：别把两件事混为一谈

很多人以为 go-zero 给各类文件统一加了 _model / _handler / _logic 后缀。其实只有 _gen 是真正的「固定后缀」。

这串字符性质说明
_gen真后缀（固定）在 FileNamingFormat 之后用 + "_gen.go" 拼上，不受 style 影响，永远有。标记「这是生成物、可被覆盖」。
model（在基础名里）拼接词goctl 把 表名 + "_model" 拼进基础名，再整体被 style 格式化。gozero 下它和表名连写 → usermodel。
Handler / Logic拼接词gogen 把 handler 名和 Handler/Logic 驼峰连写拼成基础名。gozero 下连写 → loginhandler / loginlogic。
所以准确的说法是：默认 gozero 风格下，model / handler / logic 的「词」都和主体连写，没有任何带下划线的后缀；唯一恒在的后缀是 _gen（且它紧跟在风格化之后的名字上，如 usermodel_gen.go）。你看到没有 _model 后缀，完全正确。

怎么复现

想看到带 _model 下划线的文件名？

用 --style go_zero 显式指定即可。它是「每次生成时传参」，不会改你已经手写的代码。

# api 服务
goctl api go -api user.api -dir . --style go_zero

# mysql model
goctl model mysql ddl -src user.sql -dir . --style go_zero

# 或写进 goctl.yaml 固定项目默认（推荐团队统一）
# namingFormat: go_zero
但注意：切换 style 不会自动重命名已有的老文件。如果你中途改风格，旧文件（usermodel_gen.go）和新生成规则（user_model_gen.go）会共存、冲突。所以一个项目从一开始就定死一种风格。

第一层 · 概念与判定：文件名到底谁在决定

一句话判据：goctl 生成的文件名 = 基础名 + 固定后缀，再按 --style 做单词分隔。你看到的「没有 _model 后缀」，是因为默认风格把 user_model 变成了 usermodel——后缀一直都在，只是下划线被风格吃掉了。

概念是什么举例
基础名来自表名或 handler/logic 名表 user → 基础名 user
固定后缀goctl 按类型硬编码拼上model 层固定拼 _model

  • 信号一：你用默认 goctl 生成 → 得到 usermodel.go（连写）。
  • 信号二：你指定 --style go_zero → 得到 user_model.go（下划线）。
  • 信号三：结构体名永远是 PascalCase（UserModel），不受风格影响——它是另一条代码路径。

最容易混的两件事：「真后缀」（goctl 硬拼的 _model）和 「拼接词」（风格产生的连写）。前者一定存在，后者才随 --style 变化。

切换命名风格的三条命令

# 默认风格：连写
goctl model mysql datasource -url="root:pwd@tcp(127.0.0.1:3306)/demo" \
  -table="user" -dir="./model"

# 指定下划线风格：得到 user_model.go
goctl model mysql datasource -url="root:pwd@tcp(127.0.0.1:3306)/demo" \
  -table="user" -dir="./model" --style go_zero

# 全局改默认风格（写进 ~/.goctlrc，之后所有命令生效）
goctl env -w style=go_zero

# 查看当前生效的配置
goctl env --list
  • 拼接规则（model 层）：文件名 = {表名}{"_model"} 再套风格 → 默认得到 usermodel。
  • 拼接规则（handler / logic 层）：文件名 = {接口名}handler / {接口名}logic，如 loginhandler.go。
  • 结构体名：走另一条路，永远转成 PascalCase，与 --style 无关。

量化提醒：一个中等项目 model 目录通常 20～60 个文件；风格必须在项目第一次生成时就定下来，中途切换会产生两套并存的文件。

第四层 · 原理与取舍：为什么要做风格转换

本质：goctl 内部统一用「单词序列 + 后缀」表示文件名，最后一步才按风格渲染成字符串。这样设计的好处是「生成逻辑」与「命名规范」解耦——同一套模板能输出四种风格，团队各用各的而不必改生成器。

设计好处代价 / 陷阱
风格与生成逻辑解耦一套模板支持 4 种风格新手容易困惑「为什么没有后缀」
默认 gozero（连写）文件名最短，无平台兼容问题可读性一般，usermodel 不如 user_model 直观
结构体名固定 PascalCase符合 Go 导出规则，不随风格漂移与文件名不同步，容易误以为不一致是 bug
为什么我看到的 model 文件不带 _model 后缀？

后缀一直在。表 user 生成的基础文件名是 user_model，默认 gozero 风格把下划线去掉变成 usermodel。想要看得到下划线，用 --style go_zero。

团队应该用哪种风格？

推荐 go_zero（下划线）：可读性最好，且与 Go 社区普遍习惯一致。默认连写风格在长表名下尤其难读（如 userorderaddressmodel.go）。

中途能不能换风格？

技术上可以，但要一次性全量重生成并清理旧文件。建议在 ~/.goctlrc 里固化，避免每个人本地风格不一致导致提交冲突。
