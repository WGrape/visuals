①子查询与 CTE 各自解决什么问题

两者都能把「一步算不出来的查询」拆成多步，但拆法完全不同：子查询是嵌套的，写在外层语句的 WHERE / FROM / SELECT 里；CTE 是平铺的，用 WITH 先声明一段结果集，后面的主查询像用表一样引用它。

子查询（Subquery）

出现在另一个语句内部。按是否引用外层列分为非相关与相关；按出现位置分为 标量子查询、IN 子查询、派生表（FROM 里）。

CTE（Common Table Expression）

WITH name AS (...) SELECT ...。作用域只在紧跟的那条语句内，可读性好， 且能被同一条语句多次引用；加 RECURSIVE 后可自引用处理树/图。

为什么要有两种

历史原因：CTE 是 SQL:1999 才标准化的。更实际的差别在优化器如何处理—— 派生表与 CTE 的物化/合并策略不同，这会直接影响性能。

-- 子查询写法：层层嵌套，读起来要从里往外
SELECT o.id, o.amount
FROM orders o
WHERE o.user_id IN (SELECT id FROM users WHERE vip = 1)
  AND o.amount > (SELECT AVG(amount) FROM orders);

-- CTE 写法：先命名中间结果，主查询读起来像一句话
WITH vip AS (SELECT id FROM users WHERE vip = 1),
     avg_amt AS (SELECT AVG(amount) AS v FROM orders)
SELECT o.id, o.amount
FROM orders o
JOIN vip ON vip.id = o.user_id
CROSS JOIN avg_amt
WHERE o.amount > avg_amt.v;
判断标准：如果这段中间结果只被引用一次，两种写法通常生成相同执行计划，选可读性好的； 如果被引用多次，必须在「CTE 物化一次」和「展开两次」之间权衡。若中间结果你还要在别处复用， 那它应该是视图或临时表，不是 CTE——CTE 的作用域只有一条语句。

②相关子查询：逐行执行的陷阱

相关子查询的判定标准只有一个：子查询里出现了外层表的列。这意味着它不能先算完再比对， 只能对外层的每一行各跑一次。

-- 相关：子查询引用了外层 o.user_id，orders 每行都要跑一次内层
SELECT o.id,
       (SELECT u.name FROM users u WHERE u.id = o.user_id) AS user_name,
       (SELECT COUNT(*) FROM items i WHERE i.order_id = o.id) AS item_cnt
FROM orders o;
相关子查询的逐行绑定 vs JOIN 的一次性关联
不要把「相关子查询」等同于慢。现代优化器会做子查询去关联化（decorrelation）， 把它改写成 JOIN 再执行。真正的风险是：① 去关联失败（子查询里含聚合、LIMIT、非等值条件时更容易失败）； ② 标量子查询返回多行会直接报错而不是变慢。判断依据是执行计划里是否还出现 "dependent subquery"， 不是 SQL 看起来嵌套了几层。
形态出现位置返回典型改写
标量子查询SELECT 列表单列单行LEFT JOIN（注意一对多会放大行数）
IN 子查询WHERE单列多行JOIN / EXISTS
派生表FROM多行多列CTE（可读性）或合并进主查询
相关子查询任意依赖外层行JOIN + 聚合，或窗口函数

③递归 CTE：处理树与图

普通 CTE 不能引用自己；加上 WITH RECURSIVE 后可以。固定写法是 锚成员 UNION ALL 递归成员，递归成员引用 CTE 自身，直到不再产生新行。

-- 从根节点 1 出发，求整棵子树及深度
WITH RECURSIVE sub AS (
  SELECT id, parent_id, name, 0 AS depth, CAST(name AS CHAR(1000)) AS path
  FROM category WHERE id = 1            -- 锚成员：起点
  UNION ALL
  SELECT c.id, c.parent_id, c.name, s.depth + 1, CONCAT(s.path, ' > ', c.name)
  FROM category c
  JOIN sub s ON c.parent_id = s.id      -- 递归成员：引用 sub 自身
  WHERE s.depth < 10                    -- 深度护栏，防环
)
SELECT * FROM sub ORDER BY path;
  1. 锚成员先执行，产出第一批行；递归成员拿这批行去关联，产出第二批……直到空集。
  2. UNION ALL 不去重、快；UNION 去重、能天然防重复访问，但代价高。有向无环图用 ALL，有环图要考虑去重。
  3. 必须写终止护栏：WHERE depth < N 或用 path 判断是否已访问。数据有环而没护栏会跑到超时或撑爆临时空间。
  4. 递归成员里不允许出现聚合、ORDER BY、LIMIT、外层子查询（各库限制略有差异）。
Q：递归 CTE 和「存 path 字段 + LIKE '1/%' 查询」怎么选？
A：读多写少、层级固定且浅 → path 方案简单、可加索引前缀匹配；层级深、频繁移动子树 → 递归 CTE 更省心， 但每次查询都要遍历祖先链。千万级节点的树两者都吃力，要考虑闭包表（closure table）。

④物化、合并与重复执行

同一个 CTE 被引用两次，优化器有两条路：合并（inline）——把定义展开两次，各自优化； 物化（materialize）——先算一次存进临时空间，之后直接读。选错会差一个数量级。

场景更优策略原因
CTE 结果小、能作为过滤条件大幅裁剪后续物化算一次很便宜，裁剪收益大
CTE 结果巨大、只被引用一次合并物化要落盘，白花一次 IO
CTE 带不确定性函数（RAND()、NOW()）物化合并会导致两次调用结果不一致
CTE 被引用多次且含聚合物化避免重复聚合
各库默认值不一样，别靠记忆。PostgreSQL 12 之前 CTE 总是物化（所以带过滤条件的 CTE 会莫名变慢）， 12 起改为默认可合并，可用 MATERIALIZED / NOT MATERIALIZED 显式指定。 MySQL 8 长期倾向于把派生表合并进外层，必要时用 optimizer hint 或加 LIMIT 强制物化。 SQL Server 基本总是内联。涉及具体版本行为请以官方文档与执行计划为准。
-- PostgreSQL 12+ 显式控制
WITH vip AS MATERIALIZED (SELECT id FROM users WHERE vip = 1)
SELECT ... FROM orders JOIN vip ON ...;

WITH tiny AS NOT MATERIALIZED (SELECT id FROM users WHERE vip = 1)
SELECT ...;

⑤常见陷阱

Q：子查询里 NOT IN 为什么一行都不返回？
A：子查询一旦含 NULL，x NOT IN (..., NULL) 的结果是 UNKNOWN 而非 TRUE，整条谓词不成立。 改用 NOT EXISTS（对 NULL 安全），或在子查询里加 WHERE col IS NOT NULL。
Q：SELECT 里的标量子查询返回多行怎么办？
A：直接报错（"Subquery returns more than 1 row"）。要么加 LIMIT 1 + 确定排序， 要么改用 JOIN——但要注意 JOIN 会把左表行数放大，需要配合聚合或窗口函数。
Q：CTE 里写 ORDER BY 有用吗？
A：没用。SQL 是集合语义，中间结果的顺序不保证传递到最终结果，优化器会丢弃它。 排序只在最外层 ORDER BY 才生效。想让 CTE 内排序起作用必须配 LIMIT，那属于实现细节而非标准保证。
Q：递归 CTE 报错 "recursive reference must not appear..."？
A：递归成员里引用自身的位置受限——通常只允许出现在 FROM 中，且不能在外连接的内侧、不能出现在聚合里。 把聚合挪到外层 SELECT 通常能绕过。
Q：派生表和 CTE 我要统一用哪个？
A：一次性、只用一次 → 两者等价，选团队习惯；被引用多次或需要递归 → 只能 CTE。 另外 CTE 可以引用前面定义的 CTE，派生表做不到这种链式声明。

NOT IN 的 NULL 陷阱：SELECT * FROM a WHERE id NOT IN (SELECT id FROM b)——如果 b.id 里有 NULL，整个查询返回空集。因为 x NOT IN (1, NULL) 展开是 x<>1 AND x<>NULL，后者是 UNKNOWN，整体即为假。解决：用 NOT EXISTS，或加 WHERE id IS NOT NULL。

写法对照与优化

-- ❌ NOT IN 的 NULL 陷阱
SELECT * FROM orders
WHERE user_id NOT IN (SELECT user_id FROM blacklist);
-- 若 blacklist.user_id 有 NULL，结果为空！

-- ✅ 方案 1：NOT EXISTS（推荐，语义正确且通常更快）
SELECT * FROM orders o
WHERE NOT EXISTS (SELECT 1 FROM blacklist b WHERE b.user_id = o.user_id);

-- ✅ 方案 2：过滤掉 NULL
SELECT * FROM orders
WHERE user_id NOT IN (SELECT user_id FROM blacklist WHERE user_id IS NOT NULL);

-- ✅ 方案 3：LEFT JOIN + IS NULL
SELECT o.* FROM orders o
LEFT JOIN blacklist b ON o.user_id = b.user_id
WHERE b.user_id IS NULL;
-- 递归 CTE：查组织层级
WITH RECURSIVE org AS (
    SELECT id, name, parent_id, 1 AS level
    FROM dept WHERE parent_id IS NULL        -- 锚点：根节点
    UNION ALL
    SELECT d.id, d.name, d.parent_id, o.level + 1
    FROM dept d JOIN org o ON d.parent_id = o.id   -- 递归：子节点
)
SELECT * FROM org ORDER BY level, id;
-- 必须：UNION ALL（不是 UNION）；递归部分必须引用 CTE 自身
-- 死循环防护：加 depth 限制 或 MySQL 的 cte_max_recursion_depth（默认 1000）

-- CTE 的物化控制（PG 12+）
WITH c AS MATERIALIZED (SELECT ...) SELECT ...;      -- 强制物化
WITH c AS NOT MATERIALIZED (SELECT ...) SELECT ...;  -- 强制内联
-- 何时用 MATERIALIZED：CTE 被引用多次且计算昂贵时（物化一次复用）
-- 何时用 NOT MATERIALIZED：CTE 结果大但外层有强过滤（内联后能下推过滤）

-- ClickHouse 的坑：CTE 会被当成文本替换
WITH x AS (SELECT ... FROM big_table)
SELECT count() FROM x UNION ALL SELECT sum(v) FROM x;
-- big_table 会被扫<b>两次</b>！要用临时表或物化视图代替

EXISTS vs IN 的选择：子查询结果集大时用 EXISTS（找到即停）；结果集很小时用 IN（可以做成常量列表）。但更重要的是 EXISTS 不受 NULL 影响，语义更安全，所以实践中更推荐 EXISTS。
