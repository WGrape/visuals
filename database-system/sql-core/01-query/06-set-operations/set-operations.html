①四种集合运算的语义

集合运算把两条 SELECT 的结果按行合并。前提是两段结果的列数相同、对应位置类型兼容， 结果集的列名取自第一段。

运算语义去重相对代价
UNION ALL并集不去重最低，直接拼接
UNION并集去重需要额外排序/哈希去重
INTERSECT交集去重需要比对两侧
EXCEPT / MINUS差集（左有右无）去重需要比对两侧
默认就写 UNION ALL。只有当你明确需要去重时才升级成 UNION。 很多代码里的 UNION 是历史遗留——两段结果本来就不可能有交集（比如按时间分区的两段）， 去重纯粹是白花一次排序。这是最容易白捡的性能优化。
-- 分库汇总：两段不可能重叠，ALL 才对
SELECT id, amount FROM orders_2025
UNION ALL
SELECT id, amount FROM orders_2026;

-- 求「有订单但没付款的用户」：差集语义最直白
SELECT user_id FROM orders
EXCEPT
SELECT user_id FROM payments;
去重是按整行比较的，且遵循 NULL 相等规则。与 DISTINCT 一致， 集合运算认为两个 NULL 相等（这与 = 的三值逻辑不同）。所以 SELECT NULL UNION SELECT NULL 返回一行。

②ORDER BY / LIMIT 的作用域

集合运算里排序子句的位置是个高频错误点：各分支内的 ORDER BY 不保证最终结果有序， 也不保证被保留，只有放在整条语句最后的那一个 ORDER BY 作用于最终结果。

-- ✗ 意图是各自的 top 10，实际可能被优化器丢弃，且结果无序
SELECT id FROM a ORDER BY ts DESC LIMIT 10
UNION ALL
SELECT id FROM b ORDER BY ts DESC LIMIT 10;

-- ✓ 用括号/派生表把 LIMIT 包起来，再在外层排序
SELECT * FROM (
  (SELECT id, ts FROM a ORDER BY ts DESC LIMIT 10)
  UNION ALL
  (SELECT id, ts FROM b ORDER BY ts DESC LIMIT 10)
) t
ORDER BY ts DESC;
Q：各分支的 ORDER BY 配了 LIMIT 就能保留吗？
A：多数实现会保留（因为语义上必须先取 top N 才能合并），但最终顺序仍需最外层 ORDER BY 保证。 不要依赖「看起来有序」的中间结果。

③与 OR / JOIN / FULL OUTER 的等价改写

OR → UNION ALL

单表上跨列的 OR 常导致索引失效。若 a、b 各自有索引， 拆成两条再 UNION ALL，各走各的索引。注意要自行保证不重复： 两条件同时成立的行会出现两次，需按主键去重。

INTERSECT → INNER JOIN

按主键求交集，INNER JOIN 通常更快且能用上索引； 区别是 JOIN 对重复行的处理是按组合展开，而 INTERSECT 去重。先用 DISTINCT 收敛到键再 JOIN。

EXCEPT → LEFT JOIN ... IS NULL

经典改写：SELECT a.* FROM a LEFT JOIN b ON a.k=b.k WHERE b.k IS NULL。 语义等价的前提是 b.k 唯一；否则需先对 b 去重。

MySQL 没有 FULL OUTER JOIN

用 LEFT JOIN ... UNION ALL ... RIGHT JOIN WHERE 左键 IS NULL 模拟； 或用 UNION（去重）合并左右外连接。

-- OR 改写：注意去重
SELECT * FROM t WHERE a = 1
UNION ALL
SELECT * FROM t WHERE b = 2 AND a <> 1;   -- 补上互斥条件避免重复

-- 或更稳妥：按主键去重
SELECT * FROM t WHERE id IN (
  SELECT id FROM t WHERE a = 1
  UNION ALL
  SELECT id FROM t WHERE b = 2
);

④代价与注意点

  • UNION 的去重代价是 O(n log n) 或一次哈希建表，数据量百万级时非常明显；能用 ALL 就别用 UNION。
  • INTERSECT / EXCEPT 在 MySQL 8.0.31 之前不支持，需要 JOIN / NOT EXISTS 改写。
  • 参与运算的两段若来自不同库/实例，集合运算只能在应用层或中间件做。
  • 列顺序靠位置匹配，不靠名字。两段 SELECT 列顺序写反不会报错，只会静默返回错误数据—— 建议显式写别名并在最外层 ORDER BY 校验。
  • 类型不兼容会触发隐式转换，进而导致索引失效与结果偏差（如数字与字符串比较）。
Q：UNION 去重时 NULL 怎么处理？
A：所有 NULL 视为同一值，多个 NULL 行会合并成一行。这与 GROUP BY、DISTINCT 一致。
Q：分页时 UNION 结果怎么保证稳定？
A：最外层 ORDER BY 必须包含唯一键作为最后一项， 否则排序键相同的行顺序不确定，翻页会重复或漏行。参考「键集分页」那篇。

四种集合运算对照

运算语义去重代价量级
UNION并集去重（需排序/哈希）最贵，O(n log n)
UNION ALL并集不去重最便宜，直接拼接
INTERSECT交集去重中等，需两遍扫描
EXCEPT / MINUS差集（左减右）去重中等，同上

能用 UNION ALL 就别用 UNION：去重要额外做一次排序或建哈希表，在百万行上是数倍差距。只有在确实需要去重、或两源有重叠且逻辑要求唯一时才用 UNION。

去重粒度

-- 陷阱：UNION 的去重是整行比较，包含所有列
SELECT id, name FROM a
UNION
SELECT id, name FROM b;
-- 若 a 有 (1,'x')、b 有 (1,'x') → 只留一行
-- 若 a 有 (1,'x')、b 有 (1,'y') → 两行都留

-- 想按“主键去重”而非整行去重，应改用 ROW_NUMBER
SELECT id, name FROM (
  SELECT id, name,
         ROW_NUMBER() OVER (PARTITION BY id ORDER BY updated_at DESC) rn
  FROM (SELECT * FROM a UNION ALL SELECT * FROM b) t
) x WHERE rn = 1;

NULL 在集合运算中的行为

关键差异：集合运算的去重把 NULL 视为相等（与 = 比较的行为相反）。所以两行都是 NULL 会被合并成一行。

场景结果说明
UNION 两侧各有 NULL 行合并为一行去重时 NULL = NULL 成立
INTERSECT 含 NULL能匹配上同上，两边 NULL 视为相同
EXCEPT 含 NULLNULL 行会被减掉左侧 NULL 在右侧也出现时被剔除

这与 WHERE 里的 NULL 行为不一致，是集合运算最容易踩的坑。如果业务上要区分“未知”与“相同”，必须先 COALESCE 成哨兵值。

列数、类型与排序规则

  • 两侧列数必须相同，否则直接语法报错。
  • 对应列的类型必须兼容，MySQL 会隐式转换（易踩坑），PostgreSQL 要求可隐式转换，否则报 UNION types ... cannot be matched。
  • 结果集的列名取自第一个 SELECT，后续 SELECT 的别名被忽略。
  • ORDER BY 只能写在最后一条 SELECT 之后，且只能引用第一个 SELECT 的列名或位置编号。
  • ORDER BY 1（位置编号）在集合运算里是常见写法，但可读性差且列顺序变动时易错，建议显式别名。

排序写法

-- 正确：ORDER BY 写在最后，引用第一个 SELECT 的列名
SELECT id, name, created_at FROM orders_2025
UNION ALL
SELECT id, name, created_at FROM orders_2026
ORDER BY created_at DESC
LIMIT 100;

-- 错误：在单个分支里写 ORDER BY（语法错误或无效果）
SELECT id FROM a ORDER BY id      -- ✗
UNION ALL
SELECT id FROM b;

自检 Q&A

Q：UNION 和 OR 什么时候等价？

A：把两个条件拆成两次查询再 UNION，通常比 OR 更快——因为 OR 常导致索引失效而走全表。但两者语义不等价：UNION 会去重，OR 不会。要等价需写成 UNION ALL 且确保两条件互斥（无重叠行）。

Q：怎么判断两表差异（有/没有的行）？

A：双向差集：左减右 + 右减左。更高效的是一次全外连接加状态标记：SELECT COALESCE(a.id,b.id) id, CASE WHEN a.id IS NULL THEN 'only_b' WHEN b.id IS NULL THEN 'only_a' ELSE 'both' END FROM a FULL OUTER JOIN b ON a.id=b.id。

Q：EXCEPT 在 MySQL 里没有怎么办？

A：MySQL 8.0.31 之前不支持 INTERSECT/EXCEPT。替代写法：差集用 LEFT JOIN ... WHERE b.id IS NULL 或 NOT EXISTS；交集用 INNER JOIN 或 IN。注意 NULL 语义差异——NOT IN 遇 NULL 会返回空集，务必用 NOT EXISTS。

Q：为什么 UNION ALL 结果行数比预期多？

A：UNION ALL 不做任何去重，两源若有重叠就会重复出现。这是它的正确行为——常用于「分库分表汇总」或「按月份分区合并」，此时各源互斥，行数应该正好相加。若不该多，说明上游有重复数据，而不是 UNION ALL 的问题。

第一层 · 概念与判定：三种集合运算

运算语义数学符号是否去重典型用途
UNION合并两个结果A ∪ B去重合并同类数据
UNION ALL合并两个结果A ∪ B不去重性能更好，首选
INTERSECT取交集A ∩ B去重找共同部分
EXCEPT / MINUS取差集（在 A 不在 B）A − B去重找差异（Oracle 叫 MINUS）
  • 信号一：合并两个查询且不需要去重 → UNION ALL（比 UNION 快很多）。
  • 信号二：需要「两个表都有」→ INTERSECT（可用 INNER JOIN 替代）。
  • 信号三：需要「在 A 不在 B」→ EXCEPT（可用 NOT EXISTS 替代）。

关键性能点：UNION 会做一次去重（排序或哈希），UNION ALL 不会。在确认没有重复时，UNION ALL 能省掉这一步，大结果集下差距明显。

第二层 · 参数·命令·量化：语法与规则

集合运算语法

-- 基本规则：两个查询的列数、列类型必须对应；列名取自第一个查询
SELECT id, name FROM t1
UNION ALL
SELECT id, name FROM t2;

-- UNION（去重）vs UNION ALL（不去重）
SELECT city FROM customers
UNION                        -- 去重：需要额外排序/哈希
SELECT city FROM suppliers;

SELECT city FROM customers
UNION ALL                    -- 不去重：直接拼接，更快
SELECT city FROM suppliers;

-- INTERSECT：两个表都出现过的城市（MySQL 无 INTERSECT，用 INNER JOIN 替代）
SELECT city FROM customers
INTERSECT
SELECT city FROM suppliers;
-- MySQL 替代写法
SELECT DISTINCT c.city FROM customers c JOIN suppliers s ON s.city = c.city;

-- EXCEPT：在 A 不在 B（Oracle 用 MINUS，MySQL 用 NOT EXISTS 替代）
SELECT city FROM customers
EXCEPT
SELECT city FROM suppliers;
-- MySQL 替代写法
SELECT DISTINCT city FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM suppliers s WHERE s.city = c.city);

-- ORDER BY 只能写在最后，且作用于整个结果
SELECT id, name FROM t1 UNION ALL SELECT id, name FROM t2 ORDER BY id;

ORDER BY 放最后只能有一个，作用整体不能给单个分支加 ORDER BY

第四层 · 原理与取舍：集合运算 vs JOIN

取差集EXCEPTNOT EXISTS / LEFT JOIN IS NULLNOT EXISTS 更快
同时取多列关联不适合JOIN 更自然JOIN
什么时候用集合运算，什么时候用 JOIN？

核心区别：集合运算是「纵向」拼行（行数相加），JOIN 是「横向」拼列（列数相加）。要合并同类记录用 UNION ALL；要按关联键把两张表的字段拼到一起用 JOIN。

为什么 EXCEPT 常被 NOT EXISTS 替代？

两个原因：① MySQL 不支持 EXCEPT，只能替代；② NOT EXISTS 可以提前终止（找到匹配就停），而 EXCEPT 通常要物化两个结果集再做差，大数据量下 NOT EXISTS 更快。

UNION 的去重是怎么实现的？

通常是「排序去重」或「哈希去重」：把所有行排一遍/建哈希表，相邻/哈希相同的只留一条。这就是为什么它比 UNION ALL 慢——多了一次 O(n log n) 或额外的内存开销。
