IEEE 754：为什么 0.1 + 0.2 不等于 0.3

浮点数不是「带小数点的十进制数」，而是「二进制科学计数法 + 一段固定长度的有效数字」。理解这 32 个位怎么切分，才能解释累积误差、精度丢失、NaN 传播，以及为什么深度学习要用 bf16 而不是 fp16。

一句话定位：符号 + 指数 + 尾数

把数写成 ±1.xxxx × 2^e，然后只存三段：符号位、指数（加偏置后存成无符号）、尾数（省掉前导 1）。位数分配决定了「能表示多大范围」和「能保留多少位有效数字」，而这两件事是互相抢的。

float321+8+23，约 7 位十进制有效数字
float641+11+52，约 16 位有效数字
fp161+5+10，范围小（±65504），精度约 3 位
bf161+8+7，范围同 float32，精度约 2~3 位
单精度位布局：指数管范围，尾数管精度

bf16 为什么在训练里更受欢迎

bf16 牺牲精度保住范围，不需要 loss scaling 就不会溢出；fp16 精度更高但范围窄，梯度稍大就变 Inf，必须配 loss scaling。推理侧则常用 fp16/int8，因为激活值范围可控。

0.1 + 0.2 的完整解释

0.1 = 0.0001100110011... (二进制无限循环)
     → float32 只能存 24 位有效数字，round-to-nearest-even 后
0.1f = 0.100000001490116119384765625
0.2f = 0.200000002980232238769531250
和   = 0.300000011920928955078125
0.3f = 0.300000011920928955078125  ← 巧合相等

# 在 Python（float64）里：
>>> 0.1 + 0.2
0.30000000000000004

这不是「浮点有 bug」，而是十进制小数在二进制里大多是无理循环小数，和十进制写不出 1/3 是一回事。推论有三条：不要用 == 比较浮点；求和顺序会影响结果；大数加小数会「吃掉」小数。

特殊值、舍入与「非规格化数」

默认舍入模式是「就近舍入、偶数优先」（round-to-nearest-even），它保证舍入无系统性偏差。x86 还提供 MXCSR 控制位切换舍入模式，但业务代码几乎不该改它。

非规格化数会拖慢计算

部分硬件处理非规格化数要陷入微码，速度慢一个数量级。所以一些推理框架默认开 flush-to-zero（把非规格化数当 0），这对模型精度影响很小，但要清楚这是一次「精度换速度」的显式取舍。

原理与取舍：为什么不用定点数

定点数（如 Q16.16）精度均匀、运算快、无惊喜，但动态范围窄：音频、图像、梯度、logits 的取值范围能差十几个数量级，定点要么溢出要么精度不够。浮点用「指数」换来了巨大动态范围，代价是精度不均匀——数值越大，绝对精度越差（相对精度恒定）。理解这一点，就知道为什么归一化对数值稳定如此重要。

为什么浮点数的相对精度是恒定的？

因为尾数位数固定，有效数字位数就固定，所以误差总是「当前值 × 2⁻²³」量级。这也是为什么 1e-8 与 1e8 的相对误差相同，但绝对误差差 16 个数量级。

denormal 数有什么用？

它让「最小规格化数」与 0 之间平滑过渡（渐进下溢），避免两个很小的数相减突然变成 0。音频与物理仿真里这个性质很重要。

float64 一定比 float32 准吗？

计算本身更准，但如果输入只有 float32 精度，结果的有效位数不会凭空增加。另一个反例：x87 的 80 位扩展精度曾导致「同一表达式在不同优化级别结果不同」。

动手验证：把位模式打出来

背结论不如亲手拆一次。下面三段代码分别用 Python / Go / C 把浮点数的二进制位打出来，对着位模式数一遍，比读十页规范管用。

Python：拆位与正确比较

# Python：struct 是最快的位级观察工具
import struct
def bits(x, fmt='>d'):
    return format(struct.unpack('>Q' if fmt=='>d' else '>L',
                                struct.pack(fmt, x))[0], '064b' if fmt=='>d' else '032b')

print(bits(0.1, '>d'))     # 0 01111111011 1001100110011001...(1001 循环)
print(bits(0.1, '>f'))     # 单精度：0 01111011 10011001100110011001101
print(0.1 + 0.2 == 0.3)    # False
print(struct.pack('>d', 0.1+0.2) == struct.pack('>d', 0.3))   # False
print(float.fromhex('0x1.999999999999ap-4'))   # 0.1 的精确十六进制写法

# 正确比较：绝对误差 + 相对误差一起看
import math
print(math.isclose(0.1+0.2, 0.3, rel_tol=1e-9, abs_tol=1e-12))   # True

Go：位模式与金额处理

// Go：math.Float32bits / Float64bits 直接拿位模式
package main

import (
    "fmt"
    "math"
)

func main() {
    fmt.Printf("%032b\n", math.Float32bits(0.1))              // 00111101110011001100110011001101
    fmt.Printf("%064b\n", math.Float64bits(0.1))
    fmt.Println(0.1+0.2 == 0.3)                               // false
    fmt.Println(math.Abs((0.1+0.2)-0.3) < 1e-9)               // true

    // 金额一律用整数「分」，不要用 float64
    var cent int64 = 1999
    fmt.Println(cent/100, "元", cent%100, "分")               // 19 元 99 分
}

C：%a 与 NaN 判定

// C：%a 打印精确的十六进制浮点，是调试精度的利器
#include <stdio.h>
#include <math.h>
int main(void) {
    printf("%a\n", 0.1);                  // 0x1.999999999999ap-4
    printf("%.20f\n", 0.1);               // 0.10000000000000000555
    printf("%d\n", 0.1 + 0.2 == 0.3);     // 0
    printf("%.17g %.17g\n", 0.1 + 0.2, 0.3);
    printf("%d\n", isnan(sqrt(-1.0)));     // 1：NaN 的唯一可靠判定是 isnan
    return 0;
}

工程清单：浮点到底怎么不出错

浮点问题 90% 不是「精度不够」，而是用错了场景（金额、等值比较、累加、大数吃小数）。按下面的规则走。

  • 金额一律整数或十进制类型：以「分」为单位的 int64 上限约 9.2×10¹⁷ 分 ≈ 92 万亿元，足够绝大多数业务。
  • 等值比较用区间：fabs(a-b) <= eps * max(1.0, fabs(a), fabs(b))，eps 双精度取 1e-12，单精度取 1e-6。
  • 绝对误差阈值单独给：当真值可能接近 0 时，纯相对误差会失效，必须配 abs_tol。
  • 累加用补偿算法：Kahan / Neumaier 求和，或 pairwise 分治累加，能把 10⁶ 项求和误差从 1e-10 降到 1e-16。
  • 别把大数和小数相加：1e16 + 1 == 1e16（双精度在 1e16 处 ULP 已经是 2），先排序再从小到大加。
  • 警惕 NaN 传播：NaN 参与任何比较都返回 false，x != x 是唯一不依赖库的 NaN 判定。
  • -0.0 == 0.0 为真，但 1/-0.0 = -Inf，做除法或取倒数前先判断符号位。
  • 不要用浮点做循环计数器：for (double x = 0; x != 1.0; x += 0.1) 可能永不终止。
  • 序列化用十六进制或字符串：%.17g 或 float.hex()，十进制短写会丢位。
  • 跨语言传输要对齐精度：JSON number 是双精度，int64 超过 2^53 必须传字符串（JS 会静默丢精度）。
为什么 0.1+0.2 != 0.3 而不是别的数？

因为 0.1 和 0.2 在二进制里是无限循环小数，存入 double 时都被就近舍入，两个舍入后的误差恰好同向叠加，使 0.1+0.2 的结果比 0.3 的 double 表示大 1 个 ULP（5.55e-17）。换成 0.1+0.3 就刚好相等——这不是规律，是巧合。

float32 够用吗，什么时候会出问题？

float32 只有 24 位有效尾数，约 7 位十进制。毫秒级 Unix 时间戳（1.7e12）用 float32 存会丢精度，这是最典型的事故：精度只剩约 2 分钟。同理，超过 16,777,216 的整数就再也无法精确表示。

深度学习用 bf16 不会崩吗？

bf16 保留 float32 的 8 位指数（动态范围一致），只把尾数砍到 7 位。训练中梯度对尾数不敏感、对范围敏感，所以 bf16 比同样 16 位的 fp16（10 位尾数、5 位指数）更稳；代价是需要 fp32 主权重做累加（mixed precision）。

怎么判断我这段代码会不会有精度问题？

三个信号：① 数值跨度超过 10⁸；② 出现减法且两数接近（灾难性抵消）；③ 累加项数超过 10⁵。命中任意一条，就换算法（如用 hypot 代替 sqrt(a*a+b*b)，用 log-sum-exp 代替直接取 exp）。
