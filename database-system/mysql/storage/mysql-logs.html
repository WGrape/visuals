Redo Log — 重做日志

保证事务的持久性（Durability），核心思想：WAL（Write-Ahead Logging，先写日志再写磁盘）

📌 核心概念

Redo Log 记录的是数据页的物理修改，用于崩溃后将已提交但未刷盘的数据恢复到一致状态。

  • ✅ 采用 WAL 机制：事务提交时先写 redo log（顺序IO），再异步刷脏页（随机IO），大幅提升性能
  • ✅ 崩溃恢复（Crash Recovery）时，重放 redo log 中已提交事务的修改
  • ✅ 循环写入，默认两个文件：ib_logfile0、ib_logfile1
  • ✅ innodb_flush_log_at_trx_commit：0=不保证；1=每次提交 fsync（默认，最安全）；2=写 OS buffer 每秒 fsync

Undo Log — 回滚日志

保证事务的原子性（Atomicity），实现回滚和 MVCC 快照读

📌 核心概念

Undo Log 记录的是数据被修改前的版本，用于事务回滚和 MVCC 的快照读。

  • ✅ 事务修改记录前，先将旧版本写入 undo log
  • ✅ 事务回滚时，利用 undo log 恢复数据到修改前状态（原子性）
  • ✅ MVCC 中，普通 SELECT（快照读）通过 undo log 链读取历史版本，实现非锁定读
  • ✅ INSERT Undo：事务提交后可立即删除；UPDATE Undo：需支持 MVCC，等无事务访问后才可 purge

两阶段提交（Two-Phase Commit）

保证 Redo Log 与 Binlog 的数据一致性，是 MySQL 主从复制安全性的基石

📌 为什么需要两阶段提交？

MySQL 有两套独立的日志：

  • Redo Log：InnoDB 引擎层，用于崩溃恢复
  • Binlog：MySQL Server 层，用于主从复制和按时间点恢复

若先写 redo 再写 binlog（或反过来），崩溃时两套日志可能不一致——主库用 redo 恢复的数据，从库通过 binlog 复制后得到不同结果。

两阶段提交通过 Prepare → Commit 两个步骤保证两者完全一致。

🚨 崩溃恢复判断逻辑

重启后，InnoDB 扫描处于 Prepare 状态的 redo log 事务，对照 binlog 决定如何处理：

Redo Log 状态Binlog 状态恢复操作
PREPARE✅ 完整写入✅ 提交事务（补写 COMMIT 标记到 redo）
PREPARE❌ 不完整❌ 回滚事务（利用 undo log）
COMMIT任意✅ 已提交，无需处理

💡 面试高频问题

  • Q：为什么有了 binlog 还需要 redo log？
    A：binlog 是 Server 层日志，主要用来做主从复制；redo log 是 InnoDB 特有，用来保证崩溃恢复。两者职责不同，缺一不可。
  • Q：两阶段提交能否去掉？
    A：不能。没有两阶段提交，redo log 和 binlog 可能不一致，导致主从数据不一致。
  • Q：undo log 会不会影响性能？
    A：有开销（写 undo、维护版本链），但 MVCC 避免了读写互阻，整体并发性能更好。
  • Q：redo log buffer 什么时候刷盘？
    A：① 事务提交时（由 innodb_flush_log_at_trx_commit 控制）；② buffer 空间不足；③ 后台线程每秒刷；④ checkpoint 触发。
