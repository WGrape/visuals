直接写会有什么代价？

一个 Bird 接口同时要求 fly、layEgg。企鹅无法飞，蝙蝠不会下蛋；硬实现只会制造异常和无意义方法。

先看问题写法

interface Bird { fly(); layEgg() }
class Penguin implements Bird {
  fly() { throw UnsupportedOperation }
  layEgg() { ... }
}

关键转折

拆出 Flyable、EggLayer 等小契约；只让真正具备能力的对象实现。调用方依赖它所需的小接口。

04 · 把原则写进代码

最小伪代码

interface Flyable { fly() }
interface EggLayer { layEgg() }
class Sparrow implements Flyable, EggLayer { ... }
class Penguin implements EggLayer { ... }
function startFlight(actor: Flyable) { actor.fly() }
// Penguin 不能被传给 startFlight，错误在边界暴露。

从代码中带走三件事

  1. LSP 关注可替换后的行为承诺，不只是类型检查通过。
  2. ISP 关注客户端只依赖所需方法。
  3. 契约测试应验证返回值、异常、副作用与顺序约束。
05 · 原则不是教条

对应哪些模式？什么时候收手？

  • 策略：每种算法实现必须守住相同结果语义
  • 装饰器：包装层应保持原接口的行为承诺
  • 代理：控制访问仍需让客户端理解失败语义

接口越小并非越好；拆分应由使用者的不同需求驱动。不要把一个稳定契约机械拆成几十个单方法接口。

实现了同一个接口，就一定满足里氏替换吗？

不一定。若某实现抛出接口未约定的异常、收紧前置条件或改变结果语义，类型相同也不能安全替换。

里氏替换原则：子类必须能替换父类

LSP 的形式化表述很抽象，实践上可以浓缩成一条：任何使用父类型的地方，换成子类型都不能出错。在 Go 里，它表现为「实现接口的类型不能违反接口的隐含约定」。

// 违反 LSP 的典型：实现改变了约定语义 type Reader interface{ Read(p []byte) (n int, err error) } // ❌ 一个「读取器」在没数据时直接 panic type BadReader struct{} func (BadReader) Read(p []byte) (int, error) { panic("no data") // 调用方期望返回 io.EOF } // ✅ 遵守约定 type GoodReader struct{ done bool } func (r *GoodReader) Read(p []byte) (int, error) { if r.done { return 0, io.EOF } r.done = true return copy(p, []byte("ok")), nil }
LSP 要求违反的表现例子
不改变前置条件子类要求更强的参数校验接口说接受空串，实现却报错
不弱化后置条件该做的事没做全Writer 只写了一半却返回成功
不抛新异常引入调用方没预期的失败遇到空数据 panic 而非返回 EOF
保持不变式破坏调用方依赖的状态约定Sort 实现改变了相等元素的顺序要求
能替换实现可以随时换，调用方无感。
守约定接口文档里的语义也是契约的一部分。
不加强前置不能比接口要求得更严格。
不削弱结果不能比接口承诺的做得更少。

接口隔离：小接口的力量

客户端不应该依赖它用不到的方法。接口越小，实现越容易，组合越灵活。

胖接口 vs 小接口
// Go 标准库的典范：一个方法一个接口 type Reader interface{ Read(p []byte) (n int, err error) } type Writer interface{ Write(p []byte) (n int, err error) } type Closer interface{ Close() error } // 需要组合时再拼起来 type ReadWriter interface{ Reader; Writer } type ReadWriteCloser interface{ Reader; Writer; Closer } // 函数参数只声明它真正需要的 func SaveTo(w io.Writer, data []byte) error { ... } // 传 *os.File、*bytes.Buffer、http.ResponseWriter 都行

Go 的惯例：在使用方定义接口

为什么在使用方定义

接口表达的是「我需要什么」，而不是「我能提供什么」。

  • 接口自然保持最小（只写用到的）
  • 提供方不必为了迎合多个调用方而膨胀
  • 调用方之间互不干扰
  • 测试时只需 mock 自己用到的部分
// 使用方包里定义 package order type UserStore interface { Get(ctx context.Context, id int64) (*User, error) } // 只需要 Get，就只声明 Get type Service struct{ users UserStore }

返回结构，接受接口

Go 社区广为流传的一条经验。

// ✅ 接受接口：调用方可以传任意实现 func NewService(s Store) *Service // ✅ 返回具体类型：调用方能看到全部能力 func NewStore() *MySQLStore // 不是铁律：确实需要返回抽象时也完全可以 func NewStore(dsn string) Store

接口过大的信号

  • 写 mock 时大部分方法都返回 nil
  • 实现里某些方法直接 panic("not implemented")
  • 调用方只用得到其中一两个方法
  • 接口一改，一堆实现跟着改

深入自检

LSP 和接口隔离是两回事吗？

是两个原则但高度相关。LSP 关注「实现能否替换抽象」；接口隔离关注「抽象本身是否足够小」。接口越小，实现越容易遵守约定，LSP 也就越容易满足。

接口是不是越小越好？

倾向于小，但不是无条件。一个方法一个接口在标准库很成功，因为它们语义极其稳定。业务接口若切得过碎，会导致概念泛滥、难以理解。判断标准是「这个接口能否独立表达一个完整的能力」。

为什么建议在使用方定义接口？

因为接口的意义是「我需要什么」。由使用方定义，接口天然最小化，也不会被多个调用方的需求拉扯成胖子。提供方只需实现它即可。

返回具体类型会不会破坏抽象？

不会。返回具体类型让调用方看到完整能力，将来要抽象时依然可以再加接口。过早返回接口反而会限制调用方，并让 API 演进变复杂。

怎么发现接口设计得不好？

两个信号最明显：一是写测试时 mock 大部分方法都是空实现；二是实现里出现 panic("not implemented")。两者都说明接口包含了调用方并不需要的能力。
