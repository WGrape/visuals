支付回调处理：验签、去重、乱序和对账怎样一起守住订单状态

用“支付成功通知重复三次且晚于退款通知”的时间线，推演安全与业务状态边界。

回调不是一条可信的“支付成功”字符串

支付渠道向商户服务器推送异步通知，可能重复、延迟、乱序，也可能被攻击者伪造。处理时先按渠道协议验证签名、证书或密钥版本，核对商户号、订单号、金额、币种和事件类型，再进入状态机。只验证“签名格式正确”而不核对金额和订单归属，可能把别人的订单或错误金额映射到本地交易。回调地址应使用受保护的 HTTPS，日志避免写出完整敏感载荷或密钥。

不同渠道的签名串拼接、时间戳、证书轮换和重放窗口各有契约，不应假设所有回调都能用同一套字符串排序算法。若签名通过但业务字段异常，应记录并报警，不能简单回复成功后悄悄丢掉事件。

为什么渠道会重复通知

渠道发出“支付成功”后没有及时收到商户的确认响应，通常会再次投递。网络超时不表示商户没处理：第一次可能已把订单改成 PAID，却在回包前断开。因此处理逻辑必须幂等。可为渠道事件 ID 或“渠道交易号+事件类型”建立唯一约束，同时对本地订单状态采用条件更新。重复通知到来时识别为已处理，返回渠道要求的确认格式，而不是再次扣库存、发券或记账。

仅把事件 ID 放 Redis 且给很短 TTL 风险较大：延迟重投或重建缓存后可能再次执行副作用。关键账务结果应在持久化事务中受唯一约束和状态机保护，缓存只可辅助降载。

逐步推演

验证来源与金额

先按渠道规则验签，再核订单、币种和金额。

事务去重

持久化事件 ID 与状态条件更新，重复通知只确认。

处理乱序

退款终态不被旧支付成功事件覆盖。

查询与对账

回调丢失时主动查，账单定期核差异。

一条故意打乱的时间线

10:00 渠道完成支付，发出成功事件 E1；商户处理成功但确认响应丢失。10:02 用户申请退款，退款成功事件 R1 先被商户收到并处理。10:03 渠道又重投 E1。若代码简单执行“收到支付成功就把订单改为 PAID”，会把已退款订单倒退成已支付，可能再次发货。正确做法是检查订单当前状态和事件对应的支付尝试、退款单：PAID→REFUNDING→REFUNDED 是业务状态链，旧支付成功事件在 REFUNDED 后只能作为已知事实确认，不能覆盖新终态。

若 R1 在本地尚无支付记录时先到，也不能直接丢弃。要暂存待关联事件，主动查询渠道的支付与退款交易，或进入异常队列人工核查；回调顺序并非业务事实顺序。记录渠道事件发生时间与接收时间，两者不等同。

事件可能的到达顺序正确动作
支付成功 E1第一次收到验签核金额，事务推进 PAID
退款成功 R1可能先于重投 E1推进退款状态并记录退款单
支付成功 E1 重投可能在已退款后收到识别旧事件，确认但不倒退订单
渠道账单回调丢失后到达发现漏单并进入核查流程

事务边界与下游副作用

在一个数据库事务里验证本地订单版本、插入已处理事件记录、更新支付状态和写待发布的业务事件，可减少“状态已改但发货消息没发”的裂缝。向 MQ 发布仍可能重复，消费者应按事件 ID 幂等。调用物流或积分服务不应放在回调 HTTP 线程里无限等待；先可靠记录，再异步推进，并监控待处理积压。

回复渠道确认的时机要按渠道契约：如果本地持久化失败，应让渠道可重试；如果持久化成功但后续异步发货失败，不应通过让渠道无限重投支付通知来代替内部补偿。对账系统必须能发现支付渠道成功而本地一直 UNKNOWN 的漏单。

验签之外还要防重放

有些渠道通知包含时间戳和随机串。验签通过的旧通知被重新发送，签名依然可能正确，所以还需按渠道事件 ID、交易号、时间窗口及状态机防重放。时间窗口过窄可能拒绝正常延迟通知，过宽会扩大攻击窗口，应结合渠道的实际重试期限。证书轮换时要在有效窗口内支持新旧可信公钥，并记录使用哪个版本验证，不能在报错时临时关闭验签。

回调接收端还应限制请求体大小、解析深度和来源流量，避免把验签接口变成资源消耗点。IP 白名单可辅助，但单靠源 IP 不等于身份验证，尤其在代理或渠道地址变更时。

主动查询与账单对账

回调是及时通知，不是唯一事实来源。支付请求超时后应按订单号主动查询渠道；每日或按业务要求下载渠道账单，逐笔比较本地订单、渠道交易号、金额、退款状态和手续费。差异分成“渠道有本地无”“本地标成功渠道无”“金额不符”“退款状态不同”，每类有独立处理与审计流程。不能把所有差异自动改成本地成功，账务修正需要权限和留痕。

对账可能在下一日才发现问题，所以用户界面也要能展示处理中和异常状态。关键订单可提高主动查询频率，但要受渠道 API 配额控制。

验收四种注入故障

重复 E1 三次、让 R1 先于 E1 到达、在本地事务提交后丢确认响应、让渠道成功但所有回调都丢失。每种情况检查本地支付单、退款单、库存或权益、副作用事件和最终对账记录；正确结果应当只有一次有效支付推进、一次退款推进，旧事件不能使状态倒退。再用错误金额、过期证书和被篡改报文验证拒绝路径。

监控按渠道统计验签失败、重复率、乱序率、UNKNOWN 积压、主动查询成功率和账单差异金额。业务最终成功率比单纯“回调接口返回 200”更能说明系统健康。

自检

订单已 REFUNDED 后收到旧的支付成功重投，能把订单状态直接改回 PAID 吗？

不能。应按事件 ID 和支付尝试去重、核对状态转移，旧事件只能作为已知支付事实确认，不能覆盖退款终态。
