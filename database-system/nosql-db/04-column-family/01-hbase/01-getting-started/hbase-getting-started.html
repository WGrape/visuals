Shell 与 Java API 核心用法

环境

  • 本地学习可用伪分布式（单机起 HBase + 本地 HDFS/ZK）。
  • 交互用 HBase Shell（JRuby 脚本）；编程用 Java API（官方最完整），也有 Thrift/REST 网关供其他语言。

Shell 常用命令

list                                    # 列出所有表
create 'user', 'base', 'tags'            # 建表，声明两个列族
describe 'user'                          # 查看表结构
put 'user', 'uid001', 'base:name', 'Alice'   # 写
put 'user', 'uid001', 'base:age',  '30'
get 'user', 'uid001'                     # 按 rowkey 读一行
scan 'user', {LIMIT => 10}               # 扫描前 10 行
scan 'user', {ROWPREFIXFILTER => 'uid'}  # 按前缀扫描
disable 'user'  ;  drop 'user'           # 先 disable 再 drop

建表（带预分区与参数）

Java API 核心片段

Configuration cfg = HBaseConfiguration.create();
try (Connection conn = ConnectionFactory.createConnection(cfg);
     Table table = conn.getTable(TableName.valueOf("user"))) {

  // 写
  Put put = new Put(Bytes.toBytes("uid001"));
  put.addColumn(Bytes.toBytes("base"), Bytes.toBytes("name"), Bytes.toBytes("Alice"));
  table.put(put);

  // 读
  Get get = new Get(Bytes.toBytes("uid001"));
  Result r = table.get(get);
  byte[] name = r.getValue(Bytes.toBytes("base"), Bytes.toBytes("name"));

  // 扫描
  Scan scan = new Scan().withStartRow(Bytes.toBytes("uid")).setCaching(100);
  try (ResultScanner scanner = table.getScanner(scan)) {
    for (Result row : scanner) { /* 逐行处理 */ }
  }
}

先接受一个观念：它不是「表」

带着关系库的直觉学 HBase 会处处碰壁。最需要替换掉的三个观念：

关系库的直觉HBase 的现实
一行就是一条记录，列是固定的一行可以有任意多个列，不同行的列可以完全不同（稀疏）
改一个值就是原地覆盖写入是追加一个新版本，旧版本按时间戳保留
表由行和列组成数据由 RowKey + 列族 + 列限定符 + 时间戳 四维定位
数量要少（通常 1~3 个） 因为每个列族对应独立的存储文件（HFile），flush 与 compaction 都以列族为单位 —— 列族越多，写放大与文件数越多
四维定位：RowKey + 列族 + 限定符 + 时间戳

数据是怎么存的：LSM 思路

HBase 用的是 LSM 树（日志结构合并树），和 B+ 树的思路完全相反：不做原地修改，只做追加写，后台再合并。

写入路径 ① 先写 WAL（HLog）—— 顺序写，保证不丢 ② 再写内存里的 MemStore（按 RowKey 有序） ③ 客户端即可返回「写成功」 ④ MemStore 攒够后 flush 成磁盘上的 HFile（不可变） ⑤ 后台持续把多个小 HFile 合并（compaction） 读取路径 ① 先查 BlockCache（读缓存） ② 再查 MemStore（最新的数据在这里） ③ 再查各个 HFile（用 Bloom Filter 快速跳过不含目标的文件） ④ 合并多个来源的结果，按时间戳取正确版本
为什么这么做代价
把随机写变成顺序写（WAL 与 flush 都是追加）读放大：一个 key 可能分散在多个 HFile 里，要查多份
写入吞吐极高，适合写密集场景写放大：compaction 会反复重写数据
天然保留多版本需要后台 compaction 持续整理，占用 IO

这也是为什么 HBase 适合「写多、按 key 随机点查、范围扫描」，而不适合「反复随机更新同一批行」或「复杂多条件查询」。

RowKey 设计是最重要的一件事

HBase 的数据按 RowKey 的字典序全局排序，并据此切分成多个 Region 分布到不同机器。这意味着 RowKey 直接决定了数据分布与访问效率 —— 设计错了，性能问题几乎无法通过调参挽救。

所有写入都打这儿）→ 热点 解法：给 RowKey 加前缀把压力打散 ① 加盐：RowKey = hash(原key) 的前几位 + 原key → 写入分散，但范围扫描变难 ② 反转：把固定前缀反转（如反转时间戳/手机号） → 适合尾部区分度高的键 权衡本质：越打散 → 写越均衡、读（尤其是范围扫描）越难；越有序 → 扫描友好、写易热点
RowKey 决定分布：太有序会热点，太随机则扫描失效

三条设计原则：① 长度适中（太长浪费存储与内存，常见几十字节量级）；② 把最常用的查询维度放在前面；③ 如果需要范围扫描，就别把打散前缀放在最前面，或者用「业务键 + 时间」的组合并接受一定程度的局部热点。

上手：几条最常用的操作

# 进入 shell hbase shell # 建表：指定列族（列族要少） create 'user', 'info', 'stat' # 写入（put = 新增一个版本） put 'user', 'rk001', 'info:name', '张三' put 'user', 'rk001', 'info:age', '30' put 'user', 'rk001', 'stat:login', '1' # 单行读 get 'user', 'rk001' get 'user', 'rk001', 'info' # 只取一个列族 get 'user', 'rk001', 'info:name' # 范围扫描（按 RowKey 字典序） scan 'user', {STARTROW => 'rk001', STOPROW => 'rk100'} scan 'user', {LIMIT => 10} # 删除（是打墓碑标记，compaction 时才真删） delete 'user', 'rk001', 'info:age' # 查看与禁用 describe 'user' disable 'user'; drop 'user'

关于 scan 的两条提醒：① 一定要带 STARTROW / STOPROW，否则就是全表扫；② 大 scan 要设 caching 与合适的批量，避免一次拉回过多数据把客户端或 RegionServer 打爆。

深入自检

什么时候不该用 HBase？

四种情况：① 需要复杂条件查询、多表 JOIN、二级索引（原生不支持，要额外方案）；② 数据量其实不大（几千万行以内，关系库更省事）；③ 需要强事务与跨行一致性（只有单行原子）；④ 频繁随机更新少量行的 TP 型负载。它是为海量稀疏数据的「点查 + 范围扫」设计的。

为什么列族数量要少？

因为每个列族有独立的 MemStore 与 HFile 集合。列族多会带来：flush 时产生更多小文件（触发更频繁的 compaction）、内存按列族成倍占用、Bloom Filter 等元数据也成倍增加。经验是一到三个列族，并且把经常一起访问的列放在同一个列族。

compaction 为什么会拖慢集群？

它要把多个 HFile 读出来、合并排序、重新写出，是 IO 与网络（跨节点时）密集的操作。写入量大时会产生大量小文件，触发频繁 compaction，形成「越写越慢」的循环。缓解手段：调大 flush 阈值让单个文件大一些、限制 compaction 的速度与并发、写入时批量提交、避开高峰期做大合并。

RowKey 加了盐之后怎么扫描？

这是打散与有序的固有矛盾。常见做法是按前缀分片并行扫：既然知道有 N 个盐前缀，就并发扫 N 个区间再在客户端合并。另一种思路是换一种打散方式（比如用业务 ID 的哈希做前缀、而把时间放在中间），让同一个业务的记录仍然相邻 —— 设计 RowKey 时就把未来的查询方式想清楚，比事后补救有效得多。
