✍️ 手写 LRU：从思路到可运行代码

面试高频题，也是理解缓存淘汰最好的入口。核心是「哈希表定位 + 双向链表维护顺序」。

🗺️

哈希表

O(1) 定位节点

🔗

双向链表

O(1) 摘除与插入

🎭

哨兵

省掉边界判断

⚠️

易错

命中必须刷新顺序

先建立直觉：一排按新鲜度排列的挂钩

墙上有一排挂钩，越靠左越新鲜。用了哪件衣服就把它挂到最左边；挂钩满了就摘掉最右边那件。

难点是「快速找到并移动」。如果每次都要从头找那件衣服，就是 O(n)。所以我们加一个索引本（哈希表）记下位置，再让每个挂钩同时指向左右邻居（双向链表），就能 O(1) 完成移动。

为什么必须双向链表

结构删除一个已知节点结论
数组需移动后续元素 O(n)❌
单链表需先遍历找前驱 O(n)❌
双向链表已知节点即可摘除 O(1)✅
关键点：哈希表让我们直接拿到节点对象；双向链表让节点自带 prev 指针，从而能 O(1) 摘除。单链表做不到后者——必须从头遍历找前驱。

完整实现（Go）

type node struct {
    key, val  int
    prev, next *node
}

type LRUCache struct {
    cap        int
    m          map[int]*node
    head, tail *node   // 哨兵（哑节点）
}

func Constructor(capacity int) LRUCache {
    h, t := &node{}, &node{}
    h.next, t.prev = t, h
    return LRUCache{cap: capacity, m: map[int]*node{}, head: h, tail: t}
}

func (c *LRUCache) Get(key int) int {
    if n, ok := c.m[key]; ok {
        c.moveToFront(n)     // 命中必须刷新新鲜度！
        return n.val
    }
    return -1
}

func (c *LRUCache) Put(key int, value int) {
    if n, ok := c.m[key]; ok {
        n.val = value
        c.moveToFront(n)
        return
    }
    n := &node{key: key, val: value}
    c.m[key] = n
    c.pushFront(n)
    if len(c.m) > c.cap {
        victim := c.tail.prev
        delete(c.m, victim.key)   // 务必同时删 map
        c.remove(victim)
    }
}

func (c *LRUCache) remove(n *node) {
    n.prev.next, n.next.prev = n.next, n.prev
}
func (c *LRUCache) pushFront(n *node) {
    n.prev, n.next = c.head, c.head.next
    c.head.next.prev, c.head.next = n, n
}
func (c *LRUCache) moveToFront(n *node) {
    c.remove(n)
    c.pushFront(n)
}

结构示意

五个易错点

易错点后果正确做法
Get 命中后不移到头部顺序不更新，退化成 FIFO命中必须 moveToFront
Put 已存在只改值不移动同上改值后也要移动
淘汰时只删链表不删 map内存泄漏两个结构都要删
忘记判断容量无限增长插入后检查 len > cap
不用哨兵节点边界判断繁琐易错用 head/tail 哑节点
并发安全：上述实现非线程安全。生产需要加锁（sync.Mutex）或分段锁；更推荐直接用成熟库。

复杂度

操作复杂度说明
GetO(1)哈希定位 + 摘插
PutO(1)同上
空间O(cap)每 key 一个节点 + 一个 map 项

🎯 面试问答

Q：哈希表为什么存节点而不是值？
A：因为命中后还要把节点移到链表头部，这需要节点对象本身（它有 prev/next 指针可直接摘除）。若 map 只存值，就得遍历链表找节点，退化为 O(n)。map 存节点 = 用空间换 O(1) 的移动能力。

Q：单链表为什么不行？
A：删除节点需要前驱指针。单链表只能从头遍历找前驱，O(n)。双向链表节点自带 prev，拿到节点后 n.prev.next = n.next 即可摘除，O(1)。这是必须双向的根本原因。

Q：哨兵节点有什么用？
A：让「插入头部」「删除尾部」不再需要判断「链表是否为空」「是不是首节点」。head/tail 永远存在，所有操作都是统一的指针交换。代价两个空节点，收益是代码大幅简化。

Q：这个实现能用于生产吗？
A：不建议。三个缺陷：① 非线程安全；② 无 TTL，数据永不主动失效；③ 无统计与保护（无命中率、无加载保护、无空值缓存）。生产请用 Caffeine（Java）或 ristretto/bigcache/freecache（Go）。手写版的价值是理解原理与应对面试。

数据结构与复杂度

LRU 的核心矛盾是：查要 O(1)（哈希表）和排序要 O(1) 更新（链表）。解法是哈希表 + 双向链表——哈希表负责定位，链表负责维护顺序。

方案getput评价
数组 / 单链表O(n)O(n)不可用
哈希表 + 单链表O(1)O(n)（找前驱）勉强
哈希表 + 双向链表O(1)O(1)标准解
LinkedHashMap（Java）O(1)O(1)实际项目直接用它
container/list（Go）O(1)O(1)同上

Python 手写版

# Python 版（用 OrderedDict 最简，但面试要手写双向链表）
class Node:
    __slots__ = ('k', 'v', 'prev', 'next')    # __slots__ 省内存
    def __init__(self, k=0, v=0):
        self.k, self.v, self.prev, self.next = k, v, None, None

class LRUCache:
    def __init__(self, capacity: int):
        self.cap = capacity
        self.map = {}
        self.head = Node(); self.tail = Node()      # 哨兵节点，省掉边界判断
        self.head.next = self.tail; self.tail.prev = self.head

    def _remove(self, n):
        n.prev.next, n.next.prev = n.next, n.prev

    def _add_front(self, n):        # 插到 head 之后 = 最新
        n.next = self.head.next; n.prev = self.head
        self.head.next.prev = n; self.head.next = n

    def get(self, key: int) -> int:
        if key not in self.map: return -1
        n = self.map[key]
        self._remove(n); self._add_front(n)         # 访问后提到最前
        return n.v

    def put(self, key: int, value: int) -> None:
        if key in self.map:
            n = self.map[key]; n.v = value
            self._remove(n); self._add_front(n)
            return
        n = Node(key, value)
        self.map[key] = n; self._add_front(n)
        if len(self.map) > self.cap:                # 超容量，删尾部
            old = self.tail.prev
            self._remove(old); del self.map[old.k]

Go 并发版

// Go 版（并发安全 + 泛型）
type entry[K comparable, V any] struct {
    key   K
    value V
    prev, next *entry[K, V]
}

type LRU[K comparable, V any] struct {
    cap   int
    m     map[K]*entry[K, V]
    head, tail *entry[K, V]
    mu    sync.Mutex
}

func NewLRU[K comparable, V any](cap int) *LRU[K, V] {
    l := &LRU[K, V]{cap: cap, m: make(map[K]*entry[K, V], cap)}
    l.head, l.tail = &entry[K, V]{}, &entry[K, V]{}
    l.head.next, l.tail.prev = l.tail, l.head
    return l
}

func (l *LRU[K, V]) Get(k K) (V, bool) {
    l.mu.Lock(); defer l.mu.Unlock()
    if e, ok := l.m[k]; ok {
        l.moveToFront(e)
        return e.value, true
    }
    var zero V
    return zero, false
}

func (l *LRU[K, V]) Put(k K, v V) {
    l.mu.Lock(); defer l.mu.Unlock()
    if e, ok := l.m[k]; ok {
        e.value = v; l.moveToFront(e); return
    }
    e := &entry[K, V]{key: k, value: v}
    l.m[k] = e; l.addFront(e)
    if len(l.m) > l.cap {
        old := l.tail.prev
        l.remove(old); delete(l.m, old.key)
    }
}

工业实现的额外考量

考量朴素 LRU 的问题工业做法
并发全局锁在热点 key 上成为瓶颈分段锁（Java 的 ConcurrentHashMap 思想）/ 每核一份 + 定期合并
过期LRU 只有容量淘汰，没有时间淘汰TTL/TTI；用时间轮或分层队列做批量过期
命中率LRU 对扫描型访问表现差（一次全表扫描会把热数据全挤掉）W-TinyLFU（Caffeine）：用频率草图过滤一次性访问
锁竞争每次 get 都要写（移动节点）延迟移动 / 只记录访问日志异步重排（Redis 的近似 LRU 思路）
内存开销每个节点要两个指针（16 字节）+ map 开销小对象用数组+索引代替指针

标准库用法

// 实际项目直接用标准库（不要重复造轮子）
// Java: LinkedHashMap 三行搞定
Map<K, V> lru = new LinkedHashMap<>(capacity, 0.75f, true) {   // accessOrder=true
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> e) {
        return size() > capacity;
    }
};
//   注意：LinkedHashMap <b>不是线程安全的</b>，并发场景要加锁或用 Caffeine

// Go: 用 groupcache/lru 或 hashicorp/golang-lru
import lru "github.com/hashicorp/golang-lru/v2"
c, _ := lru.New[string, int](128)
c.Add("a", 1)
v, ok := c.Get("a")
c.RemoveOldest()

// Caffeine（Java 生产首选，命中率显著高于 LRU）
Cache<K, V> c = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofMinutes(10))
    .recordStats()                  // 开启统计，能看命中率
    .build();
c.stats().hitRate();                // 查命中率
为什么 Caffeine 的 W-TinyLFU 比 LRU 好？

核心是区分「一次性访问」和「真正的热点」。LRU 只看最近访问时间，一次全表扫描（或遍历所有商品）会把所有热数据挤出去——这叫 LRU 的污染问题。W-TinyLFU 用 CountMin Sketch（一种概率频率结构，每个 key 只占几个 bit）估计访问频率，新进入缓存的候选项必须在频率上打败被淘汰项才能真正进入。在真实的 trace 上，命中率通常比 LRU 高 5~15 个百分点。代价是维护频率草图的额外内存（很小）。

LRU 的 get 也要修改结构，会不会很慢？

单次操作是 O(1)（几个指针赋值，几十纳秒），本身不慢。慢的是并发场景下的锁竞争：get 是写操作，必须加锁，热点 key 上会形成串行瓶颈。工业解法：① 分段锁（把缓存分成 N 段，各自一把锁）；② 读不移动、只记日志（Redis/Caffeine 的做法）——get 时只把 key 记录到一个 ring buffer，由后台线程批量重排；③ 用近似 LRU（随机采样几个淘汰候选，省掉精确维护）。

什么时候该自己写 LRU？

几乎只有面试。生产环境直接用：Java → Caffeine（或 LinkedHashMap + 锁）；Go → hashicorp/golang-lru 或 ristretto；Python → functools.lru_cache（装饰器，最简单）或 cachetools。自己写的价值在于理解「哈希表 + 双向链表」这个组合为什么能同时做到 O(1) 查找和 O(1) 更新——这是很多缓存/调度系统的基础模式（如 Linux 的 LRU 页面链表、Memcached 的 slab LRU）。
