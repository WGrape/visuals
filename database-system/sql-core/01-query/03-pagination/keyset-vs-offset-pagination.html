深分页与游标分页：OFFSET 100000 为什么越来越慢

用按时间倒序的订单列表，推算跳过行成本，并解释并发插入后的重复与漏读。

两种分页回答同一个界面需求

订单列表每页 20 条，按创建时间倒序显示。常见写法是 `ORDER BY created_at DESC LIMIT 20 OFFSET 100000`：数据库要先定位有序结果的前 100020 条，再丢掉前 100000 条，才把最后 20 条交给页面。即使有合适索引，深处的 OFFSET 往往仍需要沿索引跳过大量条目；若还要回表读取宽列或排序未走索引，成本更高。不能只看到返回 20 行就推断数据库只处理了 20 行。

游标分页也称 keyset pagination：上一页最后一条是 `(created_at=10:00:00, id=900)`，下一页直接查询排序键小于该元组的行，按同一顺序取 20 条。索引可从游标附近继续扫描，成本更接近一页大小，但前提是排序键与谓词能一起利用索引。

图解：五条订单的两次翻页

沿箭头逐步核对输入、变换和输出；下面的推演可以逐步切换。

为什么要加唯一的第二排序键

很多订单在同一秒创建，若只按 created_at 排序，数据库可以任意排列同时间行。上一页最后一条时间为 10:00:00，下页只写 `created_at < 10:00:00`，会漏掉同一秒还没显示的订单；写 `<=` 又会重复上一页的若干订单。可用 `(created_at DESC, id DESC)` 建立稳定全序，下一页谓词是“时间更早，或时间相同且 id 更小”。某些数据库支持元组比较 `(created_at,id) < (?,?)`，但方言和 NULL 排序规则要核对。

若 ID 并非单调创建，也不影响它作为同时间的稳定 tie-breaker，只要唯一且排序固定。若 sort key 可以更新，某条记录可能在翻页期间移动位置，仍可能出现重复或遗漏；关键导出任务需要固定快照或记录高水位线。

并发插入怎样影响 OFFSET

第一页读取前 20 条后，有新订单插入排序最前面。第二页用 OFFSET 20，会先跳过“新订单 + 原第一页前 19 条”，于是原第一页第 20 条可能再次出现在第二页。这是位置偏移随数据变化的结果。游标根据上一页最后的排序键继续找更旧记录，新插在最前面的订单通常不会扰乱后续页，但它也不会在当前翻页会话里被看到；要刷新列表才能看到新记录。

游标分页并不自动提供完整一致快照。并发删除、排序键更新、权限变化仍会改变后续可见集合。如果要求“导出开始时的所有订单恰好一次”，需数据库快照、稳定水位或业务版本规则，并明确长事务的资源成本。

场景OFFSET游标
浅页实现直接也高效

并发头部插入可能重复或漏项后续页通常不受头部插入扰动

索引如何配合

对于 `WHERE tenant_id=? ORDER BY created_at DESC,id DESC`，可考虑以 tenant_id 开头、后接排序列的复合索引。游标谓词和排序方向要与索引能力相配；混合升降序、表达式排序、NULLS FIRST/LAST 在不同数据库中的优化不同。用 EXPLAIN 或实际执行统计比较扫描行数、排序节点、回表次数和延迟，而不是只凭 SQL 形式判断。

若需要精确跳到“第 5001 页”，游标方案没有天然的随机页码定位；可以保存里程碑游标、按时间区间跳转，或接受 OFFSET 的代价。产品界面通常更适合“下一页/加载更多”，而财务报表可能需要明确页码与稳定快照。两者可按用例分别选择。

三条查询的手算

假设排序后 id 依次为 105、104、103、102、101，页大小 2。第一页返回 105、104；此时新插入 106，序列变为 106、105、104、103、102、101。OFFSET 2 的第二页得到 104、103，重复 104。以第一页末尾 104 为游标，第二页查 id<104，得到 103、102。若 104 被删除，游标仍可按其记录的排序键继续，因为不需要再次找到 104 这行。

实际列表按 created_at、id 排序时，游标应同时携带两个值，而不是只携带 id。为防篡改或跨租户复用，可在应用层把排序字段、租户与过滤条件编码进受保护的游标，解码时验证它仍适用于当前查询。

常见误区

“加 LIMIT 20 就只扫描 20 行”忽略了 OFFSET；“按时间排序天然稳定”忽略了并列时间；“游标一定完全无重复漏读”忽略了更新和删除；“加一个索引就能解决所有深分页”忽略了扫描和回表。优化前用代表性数据量测试第 1 页、第 100 页和最深页，记录实际扫描行数及 P95。练习：上例新插入 id 106 后，分别列出 OFFSET 第二页和游标第二页，并解释为什么不同。

为什么 OFFSET 慢：数据库必须真的读出并丢弃前 m 行，因为 SQL 语义要求从第 m+1 行开始返回。它没有「跳到第 m 行」的能力——行没有固定地址（MVCC、删除留下的空洞都让物理位置不连续）。所以 OFFSET 越大，丢弃的工作越多。

实现与优化

-- OFFSET 分页（浅分页可用）
SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 100000;
-- 慢：要扫 100020 行

-- 键集分页（推荐）
SELECT * FROM orders WHERE id > 100000 ORDER BY id LIMIT 20;
-- 快：索引直接定位到 id=100000 之后

-- 键集分页要求：排序列<b>唯一且有序</b>
-- 若排序列可能重复（如 created_at），要用复合游标：
SELECT * FROM orders
WHERE (created_at, id) > ('2026-10-22 10:00:00', 12345)
ORDER BY created_at, id
LIMIT 20;
-- 用 (created_at, id) 复合索引支撑
-- 优化 1：延迟关联（deferred join）—— 大 OFFSET 的救急方案
-- 先只查 id（走覆盖索引，不回表），再关联取完整行
SELECT o.* FROM orders o
INNER JOIN (
    SELECT id FROM orders ORDER BY id LIMIT 20 OFFSET 100000
) t ON o.id = t.id;
-- 原理：子查询只扫索引（不回表），回表次数从 100020 降到 20
-- 实测能快 5~10 倍

-- 优化 2：覆盖索引（让 OFFSET 分页也能走索引）
CREATE INDEX idx_orders_cover ON orders(id, status, amount);
SELECT id, status, amount FROM orders ORDER BY id LIMIT 20 OFFSET 100000;
-- 不回表，全在索引里完成

-- 优化 3：用书签记录上一页位置（键集分页的工程实现）
-- 返回给前端的 cursor 要加密或至少编码，避免暴露 id 规律
-- 常见做法：base64(created_at + id)

最实用的组合：产品上把「跳到第 N 页」改成「上一页/下一页」或「加载更多」，就能全面使用键集分页。「跳页」这个需求本身就是性能杀手，很多产品在深分页时直接不给跳页（如 Twitter、微博的时间线）。

第一层 · 概念与判定：两种分页怎么选

维度OFFSET 分页游标（keyset）分页
写法LIMIT n OFFSET mWHERE id > :last_id LIMIT n
能否跳页✅ 可以任意跳❌ 只能顺序翻
深翻性能O(m)，越深越慢O(1)，恒定
数据变动时可能重复/漏行稳定（基于游标位置）
总页数需要 COUNT(*)不需要
适用后台管理、页数少信息流、无限滚动、深翻
  • 信号一：产品形态是「信息流/无限下拉」→ 必须用游标分页。
  • 信号二：需要「跳到第 57 页」→ 只能 OFFSET（并接受深翻慢）。
  • 信号三：数据会实时新增 → OFFSET 会导致重复展示，游标不会。

核心差异：OFFSET 是「跳过前 m 行」——数据库必须真的把前 m 行读出来再丢弃；游标是「从某个位置继续」——用索引直接定位，一步到位。

第二层 · 参数·命令·量化：写法与性能数据

两种分页写法

-- OFFSET 分页（页数少时没问题）
SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 40;          -- 第 3 页

-- 游标分页（需要记录上一页最后一个 id）
SELECT * FROM orders WHERE id > 12345 ORDER BY id LIMIT 20;
-- 下一页用本页最后一条的 id 作为 :last_id

-- 多列排序时的游标（如按 created_at DESC, id DESC）
SELECT * FROM orders
WHERE (created_at, id) < ('2025-01-01 10:00:00', 999)        -- 行值比较（MySQL 8 / PG）
ORDER BY created_at DESC, id DESC LIMIT 20;
-- 或展开写
WHERE created_at < '2025-01-01 10:00:00'
   OR (created_at = '2025-01-01 10:00:00' AND id < 999)

-- 延迟关联：优化 OFFSET 深翻（减少回表）
SELECT o.* FROM orders o
JOIN (SELECT id FROM orders ORDER BY id LIMIT 1000000, 20) t USING (id);
-- 内层只扫覆盖索引拿 id，外层只回表 20 行

-- 建索引支撑游标分页
CREATE INDEX idx_orders_created_id ON orders(created_at DESC, id DESC);

量化结论：OFFSET 的耗时与偏移量成正比（O(m)）；游标是 O(1)。第 1 页两者差不多，第 1000 页差上百倍。

第四层 · 原理与取舍：为什么 OFFSET 无法优化

因为 OFFSET m 的语义就是「先算出前 m 行，再丢弃」——数据库没有任何捷径能跳过它们（除非有预计算的行号）。这是语义决定的，不是索引能解决的。

方案原理代价
游标分页用索引直接定位起始位置不能跳页；需要有序唯一列
延迟关联只在覆盖索引上 OFFSET，减少回表仍要扫 m 行，只是每行更轻
预计算行号冗余一列存行号/页码写入时要维护，数据变动即失效
搜索引擎ES 的 search_after引入新组件
游标分页要求排序键唯一吗？

必须。如果排序键有重复（如只按 created_at 排，同一秒有多条），游标位置会有歧义，可能漏行或重复。标准做法是追加主键作为第二排序键：ORDER BY created_at DESC, id DESC，游标用 (created_at, id) 二元组。

既想跳页又想快，有折中吗？

有几种：① 限制最大页数（如只允许前 100 页）；② 用延迟关联把 OFFSET 的回表成本降到最低；③ 按时间/区间先粗筛（如「只看 2025 年」），把 m 变小；④ 引入 ES。实际中第 ① 种最常用——业务上很少真的需要跳到第 5000 页。

数据新增时 OFFSET 为什么会重复展示？

因为 OFFSET 是按位置取的。你在第 1 页时，别人插入了 10 条新数据；你翻到第 2 页时，整体向后移了 10 行——于是第 1 页的最后 10 条又出现在第 2 页。游标分页基于值（id > last_id），不受新增影响。
