一套能回答“系统到底扛不扛得住”的指标体系

不要只报一个 QPS。评估需要同时回答：请求进来多少、完成多少、等了多久、错了多少、资源还剩多少余量，以及这些结果是否达到服务目标。

测量前，先写清指标契约

每个数字都应附上：对象（服务、接口、Key、机房）、观察边界（客户端、网关、业务层）、事件或状态（发起、接纳、完成、成功）、单位和时间窗口、负载组成（请求大小、缓存命中率、上下游条件）。否则两个仪表盘同叫“QPS”，可能根本不可比。

速率是区间值

例如 10 秒内完成 1,000 次，平均完成速率为 100 次/秒。短时 1 秒峰值可能更高，不能代替持续承载能力。

在途量是状态量

例如一瞬间业务层正在处理 80 个请求；评估吞吐关系时要统计时间平均，不能只取最大值。

延迟是样本分布

平均 RT 与 P50/P95/P99 回答不同问题。百分位要标明所选请求、统计窗口与超时/失败的处理方式。

核心指标字典：流量、体验、可靠性、饱和度

示例：数字组合比单个 QPS 更有用

以下仅是同一段 10 秒窗口的示意：客户端发起 2,000 次（到达平均 200 次/秒），网关接纳 1,900 次（190 次/秒），业务完成 1,800 次（180 次/秒），其中成功 1,750 次、失败 50 次。

成功 QPS = 175；完成请求的成功率 = 1,750 / 1,800 ≈ 97.2%

还有 100 次未接纳；若窗口起点/终点边界量、取消和重试影响暂不计，接纳比完成多 100 次，表示业务内未完成量净增。不能简单说“系统支持 200 QPS”：那只是客户端发起速率。判断是否满足 SLO，还需看成功请求和失败/超时的耗时分布、P99、队列增速及资源情况。

公式要用相同边界，容量要靠测量

平均在途量 L = 稳态完成速率 λ × 同边界平均停留时间 W

Little 定律不是硬件容量公式。网关队列若计入 W，也必须计入 L；若用业务处理中的 L，W 只能是业务段的占位时间。业务能力、连接流限制、账户 RPM 与 P99 目标仍需分别测量与验证。

从指标到决策的学习路线

  1. 先统一术语，明确 QPS/TPS/RT 的口径；认识吞吐与请求速率。
  2. 用 延迟分位数、并发/排队指标找用户体验和瓶颈之间的联系。
  3. 最后按 QPS 容量评估流程验证“满足成功率和尾延迟目标的持续负载”，而不是追求压测瞬时最大值。
  4. 确定瓶颈后，进入 高性能优化方法论，按 CPU、内存、网络与文件 IO 分层改进，再回到同一口径复验。

延伸学习：网络带宽、RTT、丢包与 PPS；高并发场景术语；云原生可观测性。

四类指标：一张字典表

性能指标看起来多，其实只有四类：流量、体验、可靠性、饱和度。判断一个指标属哪一类，决定了你该拿它做什么决策——流量看趋势、体验看分位、可靠性看比例、饱和度看余量。

两套现成的方法论：USE 与 RED

不用从头设计指标体系，两套成熟模板覆盖了绝大多数场景：USE 看资源，RED 看服务，两者互补，一起用才完整。

USE：面向资源

对每个资源（CPU、内存、磁盘、网络、连接池）问三件事：使用率 Utilization 有多满、饱和度 Saturation 排了多少队、错误 Errors 出了多少次错。适合定位「机器层面的瓶颈」。

RED：面向服务

对每个服务问三件事：请求速率 Rate、错误率 Errors、耗时 Duration。适合回答「用户感受到的服务怎么样」，是微服务观测的常用默认集。

指标之间的换算关系

很多指标不是独立的，它们之间可以互相推导。掌握这几条关系，就能用现有的监控数据算出缺失的那一项。

# 1) 利特尔法则：在途 = 吞吐 × 耗时 L = QPS * avg_latency # 2) 成功率与错误率 error_rate = errors / total success_rate = 1 - error_rate # 3) 可用性与不可用时长（常说的几个九） # 99.9% -> 每月约 43 分钟不可用 # 99.99% -> 每月约 4.3 分钟不可用 downtime_per_month = 30*24*60 * (1 - availability) # 4) 分位数不能相加，但延迟可以拆解 total = queue_time + service_time + network_time # 5) 饱和度判断：用队列长度而不是 CPU # CPU 100% 但队列为 0：满负荷但没排队，还能撑 # CPU 80% 但队列持续增长：已经开始排队，快撑不住了 # 6) 有效吞吐 vs 原始吞吐 goodput = QPS * success_rate # 只有成功的才算有效产出
在途数= 吞吐 × 平均耗时
有效吞吐= QPS × 成功率
总延迟拆解排队 + 服务 + 网络
可用性换算几个九对应多长不可用时间
饱和度看队列队列比 CPU 更早报警
分位不可相加不要对 P99 做算术平均

指标体系最常见的误用

为什么看板上一片绿，用户却在投诉？

典型原因是只看成功率和平均延迟。成功率只看「有没有报错」，但慢到超时也同样是坏的；平均延迟看不出长尾。把 P99 与超时率放上看板，很多问题立刻显形。

指标越多越好吗？

不是。指标过多会导致告警疲劳，真正出问题时没人看。更好的做法是每个服务只保留核心四项（速率、错误、耗时、饱和度），其余指标放在需要下钻时才查的详情页。

告警阈值怎么定？

优先基于目标反推：先定体验目标（比如 P99 小于 300ms），再倒推对应的资源水位作为告警线。凭经验拍阈值的后果是要么天天响，要么从来不响。

为什么要有饱和度告警？

因为它是最早的信号。等到错误率和延迟都变差时，系统往往已经过载；而队列长度、连接池占用这类饱和度指标在问题发生前就会上升，给你留出处理时间。

分位数怎么算才靠谱？

注意两点：一是不要在客户端侧用平均值冒充 P99；二是分位数不能跨时间简单平均（五个一分钟的 P99 平均 ≠ 五分钟的 P99），要保留原始数据或用直方图合并。

如何判断指标是否该保留？

问一句：这个指标变化的时候，我会做什么动作？如果答案是「什么都不做」，那它就应该从看板上撤下来。能驱动决策的指标才有留在首页的价值。
