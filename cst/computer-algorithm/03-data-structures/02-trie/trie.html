第 03 章 · 数据结构概览

把公共前缀合并成一条路径

Trie 让查找代价只与字符串长度有关而与词表规模无关，是前缀查询、自动补全与异或极值问题的标准结构。

前缀树解决的是「按前缀查」

哈希表能告诉你一个字符串在不在，但没法高效回答“所有以 app 开头的词有哪些”。Trie（前缀树 / 字典树）把公共前缀合并成一条路径，让查询代价只和字符串长度有关，和集合里有多少词无关。

查 apple：从根沿 a→p→p→l→e 走 5 步，最后一步落在带 end 标记的节点上 → 存在。查 ap：走 2 步后节点没有 end 标记 → 不在集合里（但它是一个前缀）。

插入、查询与复杂度

class Trie:
    def __init__(self):
        self.children = {}          # char -> Trie
        self.is_end = False

    def insert(self, word):
        node = self
        for ch in word:
            node = node.children.setdefault(ch, Trie())
        node.is_end = True

    def search(self, word):        # 完整词是否存在
        node = self._walk(word)
        return node is not None and node.is_end

    def starts_with(self, prefix):  # 是否存在该前缀
        return self._walk(prefix) is not None
  • 插入 / 查询 / 前缀判断：O(L)，L 是字符串长度，与词表规模无关。
  • 空间：最坏 O(总字符数)，但实际取决于共享前缀的程度——词典类数据压缩效果好，随机字符串则每个节点几乎独占。
  • 节点的子节点表是空间瓶颈：字符集小时用数组 O(1) 跳转但浪费空间；字符集大（Unicode）用哈希表或有序映射更省。

三个常见变种

压缩前缀树（Radix Tree / Patricia Tree）

把只有一个孩子的链压缩成一个节点，节点上存一段字符串而不是单个字符。节点数大幅下降，指针跳转变少，是很多路由表和存储引擎索引的实际形态。

01 Trie（二进制 Trie）

把整数按二进制位插入，用来求“与 x 异或的最大值”：每一步贪心走向与当前位相反的分支。它是位运算与 Trie 的结合，复杂度 O(位数)。

后缀树 / 后缀数组

把所有后缀插进 Trie，可以 O(模式长度) 完成子串匹配、最长重复子串等。后缀树空间大，工程上更多用后缀数组 + LCP。

Trie 与哈希表怎么选

维度哈希表Trie
精确查找期望 O(1)，常数小O(L)，需逐字符走
前缀查询 / 自动补全做不到（只能全量扫）天然支持
字典序遍历不支持DFS 即得有序结果
空间紧凑节点多、指针开销大
最长公共前缀、模糊匹配不合适合适

一句话：只判存不存在用哈希，要碰前缀就用 Trie。两者可以并存——用哈希做精确命中缓存，用 Trie 做补全候选。

Trie 解决的是「前缀」这一类问题

哈希表能在一大堆字符串里 O(1) 地告诉你「这个词在不在」，但它答不了这些问题：所有以 go 开头的词有哪些？能不能边打字边提示？能不能按字典序列出来？

Trie（字典树 / 前缀树）就是为此设计的：把公共前缀合并成共享的路径。查询时间与「词的长度」有关，而与词典里有多少个词无关。

共享公共前缀是 Trie 的核心：节点代表前缀，边代表字符
操作Trie哈希表说明
精确查找一个词O(L)O(L) 期望哈希要算哈希值；Trie 逐字符走
找所有带某前缀的词O(L + 结果数)无法做到（要全表扫）这是 Trie 的主场
按字典序输出DFS 天然有序需要排序输入法的候选排序依赖这点
插入O(L)O(L) 期望同阶，但 Trie 每次都要建节点
删除O(L)，注意回收空路径O(1)Trie 需要回溯清理无用节点

实现一个够用的 Trie

class Node: __slots__ = ('child', 'end', 'cnt') # cnt: 有多少词经过此节点，便于删除 def __init__(self): self.child = {} self.end = False self.cnt = 0 class Trie: def __init__(self): self.root = Node() def insert(self, word): p = self.root for c in word: p.cnt += 1 p = p.child.setdefault(c, Node()) p.cnt += 1 p.end = True def search(self, word): # 完整词是否存在 p = self.root for c in word: if c not in p.child: return False p = p.child[c] return p.end def starts_with(self, prefix): # 是否存在该前缀 p = self.root for c in prefix: if c not in p.child: return False p = p.child[c] return True def collect(self, prefix, limit=None): # 列出该前缀下所有词 p = self.root for c in prefix: if c not in p.child: return [] p = p.child[c] out = [] def dfs(node, cur): if len(out) == limit: return if node.end: out.append(cur) for ch, nxt in node.child.items(): dfs(nxt, cur + ch) dfs(p, prefix) return out

三个实现要点：

  • 子节点用哈希映射而不是定长数组。定长数组（如 26 个 slot）在字符集小且密集时才划算；一旦要支持中文、表情、URL 字符，绝大多数 slot 是空的，用 map[char]*Node 更省。字符集固定且极窄时（比如只有 0/1）定长数组依然最快。
  • 加一个「经过计数」。删除时要判断子树是否已空，有 cnt 可以直接判断，比递归回溯检测子节点是否为空更省事。
  • 加 with limit 的收集。自动补全场景永远只要前若干条，没必要把整个子树遍历完。

耗空间怎么办：三条优化路线

① 压缩前缀树 Radix Tree

把只有一个孩子的节点与它的孩子合并，边上存储一整段字符串而不是单字符。golf 这条长长的独链会被压成一个节点。

代价：插入时要 split 已存在的边，代码复杂度上升。收益：深度大幅下降、指针数量骤减。路由表的最长前缀匹配和 IP 路由查找基本都用这个形态。

② 换底层容器

子节点较少时，用一个排序的小数组 + 二分查找比哈希映射更省内存且缓存友好；子节点多时再退化为哈希。

也可以改成双数组 Trie（DAT）：用两个整型数组表达整棵树，极度紧凑，适合做成静态词典离线分发。

③ 用其它结构替代

如果只是要「前缀是否存在」，排序后的字符串数组 + 二分也能做到 O(L log n)，空间小得多。如果只关心查找不要遍历，哈希表最省。

选型从来不是「Trie 更高级所以用它」，而是「我到底要不要前缀能力」。

空间复杂度怎么估：朴素实现大约是 节点数 × (一个指针+K个子节点指针的额外开销)。在 Python/Java 这种每个对象都有对象头的语言里，一个节点可能几十上百字节，n 个词大多数 char 要占一个节点 —— 词典到百万级时内存会非常可观，这就是必须用上面三种手段优化的缘由。

深入自检

Trie 真的比哈希表快吗？

不一定，而且常常更慢。Trie 的优势在于能力（前缀遍历、字典序）而不是速度：哈希表一次哈希、一次比较就能定好一整段数组下标，而 Trie 要逐字符走下去，每一步都是一次随机的指针跳转（缓存不友好）。如果你只需要精确查找，哈希表通常是更好的选择。

为什么教科书总强调 char→child 的映射方式？

因为它决定了内存占用与速度的平衡。字符集很小且固定（如小写字母 26 个）时用数组，O(1) 寻址最快；字符集大或稀疏（中文、Unicode）时用哈希或跳表式结构，牺牲一点速度换取大幅节省的空间。这个选择在工程上往往是相关的第一个问题。

后缀树、后缀自动机和 Trie 是什么关系？

可以把 Trie 理解成「把一批字符串的前缀组织起来」，后缀类结构则是「把一个字符串的所有后缀组织起来」。后者用于解决子串类问题（最长重复子串、最长公共子串、多模式匹配），能力更强但结构也复杂得多，AC 自动机可以看作 Trie 加上了失败指针以支持同时匹配多个模式串。

面试与刷题时该怎么写？

抓住三件事：① 节点结构体里有 children 与 isEnd 两个字段；② 遍历时注意空安全的下探写法；③ 如果需要删除，先想清楚要不要回收空路径。多数题目只需要插入、查找、前缀查找这三个接口就够，不要过早过度实现。
