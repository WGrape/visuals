①批量化的收益来自哪里

把 1000 条单条 INSERT 换成 1 条 1000 行的 INSERT， 性能提升往往不是 1000 倍但也能到几十倍。省掉的是三项固定成本：

网络往返

每条语句一次 RTT。同城 0.2ms 看起来小，1000 次就是 0.2 秒纯等待；跨地域会更糟。

事务与日志开销

每条语句一个事务（自动提交）就要一次 fsync 级别的日志落盘。 合成一个事务只需一次提交。

解析与计划开销

语法解析、权限校验、优化器决策。批量语句只做一次； 配合预编译语句（prepared statement）还能跨批次复用计划。

但不是越大越好。单条语句过长会带来： ① 单事务过大 → 锁持有时间长、undo/redo 膨胀、回滚极慢； ② 包体超过 max_allowed_packet 直接报错； ③ 主从复制把大事务整体传输，从库回放卡住造成延迟。 常见经验值：每批 500~2000 行，具体按行宽与压测结果调整。

②批量插入

-- 多行 VALUES（最通用）
INSERT INTO t (a, b) VALUES (1,'x'), (2,'y'), (3,'z');

-- 从查询结果插入：ETL 与归档的主力
INSERT INTO archive SELECT * FROM orders WHERE created_at < '2025-01-01' LIMIT 10000;

-- MySQL 高速导入：LOAD DATA（比 INSERT 快一个数量级）
LOAD DATA LOCAL INFILE '/tmp/orders.csv' INTO TABLE orders
  FIELDS TERMINATED BY ',' ENCLOSED BY '"' LINES TERMINATED BY '\n';

-- PostgreSQL：COPY
COPY orders (id, amount) FROM STDIN WITH (FORMAT csv);
方式速度适用注意
多行 VALUES中应用内小批量写入控制每批行数与包大小
INSERT ... SELECT高库内搬数据、归档大事务，要分批 + 限流
LOAD DATA / COPY最高初始化、离线导入绕过部分约束检查与触发器，导入后要校验
批量接口（executemany / addBatch）中高应用层最常用注意驱动是否真的做了批量
驱动层的「批量」可能是假的。某些驱动默认只是把多条语句拼起来逐条发， MySQL 需要连接参数 rewriteBatchedStatements=true 才会真正重写成多行 VALUES。 用抓包或看慢日志确认实际发出的语句形态。

③批量更新与删除

批量 UPDATE：不同行不同值

-- CASE 写法：行数不多时简单直接
UPDATE t SET amount = CASE id
  WHEN 1 THEN 100 WHEN 2 THEN 200 WHEN 3 THEN 300 END
WHERE id IN (1,2,3);

-- JOIN 临时/派生表：行数多时更清晰、也能走索引
UPDATE t
JOIN (SELECT 1 id, 100 v UNION ALL SELECT 2, 200 UNION ALL SELECT 3, 300) s
  ON t.id = s.id
SET t.amount = s.v;

批量 DELETE：必须限流

-- ❌ 一次删 500 万行：长事务 + 大锁 + undo 爆掉 + 主从延迟
DELETE FROM logs WHERE created_at < '2025-01-01';

-- ✓ 分批删，每批之间留出呼吸空间
DELETE FROM logs WHERE created_at < '2025-01-01' ORDER BY id LIMIT 5000;
-- 循环执行直到影响行数为 0，每轮 sleep 100ms
更优雅的方案：分区 + DROP PARTITION。 按时间分区的日志表，清理历史数据直接 DROP PARTITION， 是元数据操作，秒级完成且不产生大量 undo。这是设计层面解决清理问题，比任何 DELETE 优化都彻底。

写入放大检查清单

  • 表上有几个二级索引？每多一个索引，一次插入就多一次索引写入。
  • 是否有触发器、外键约束？都会把一次写入放大成多次校验。
  • 批量导入时可临时关闭 binlog（从库场景）或外键检查，但事后必须校验。
  • 批量写后建议 ANALYZE 更新统计信息，否则优化器会用旧分布做决策。

④安全与可回滚

  1. 先 SELECT 验证影响范围：把 UPDATE/DELETE 的 WHERE 原封不动写成 SELECT COUNT(*) 跑一遍，确认行数符合预期。这条能救 90% 的生产事故。
  2. 开启事务并在提交前检查：BEGIN; ...; SELECT ROW_COUNT(); ROLLBACK; 试跑一遍。
  3. 禁止无 WHERE 的 DML。很多客户端与规范检查工具会拦截，值得开启。
  4. 备份优先于回滚：大批量变更前先备份目标数据（CREATE TABLE bak AS SELECT ...）， 回滚比恢复更快。
  5. 灰度顺序：先在从库/影子库验证 → 小批量（100 行）跑一次 → 观察监控 → 全量。
  6. 限流：批量任务要能随时暂停。带 LIMIT 的循环天然支持， 一条大语句跑到一半想停只能 kill，回滚还要等。
Q：TRUNCATE 和 DELETE 怎么选？
A：TRUNCATE 是 DDL，重置自增计数、不写逐行日志、无法回滚、不能带 WHERE、 会锁整表，速度极快。DELETE 是 DML，可回滚、可带条件、会写日志。 清测试表用 TRUNCATE，清生产数据用分批 DELETE。另外 TRUNCATE 通常无法触发 DELETE 触发器， 有外键引用时也可能被拒绝。
Q：批量插入时有重复数据怎么办？
A：三条路：① 用 UPSERT 按唯一键覆盖；② 用 INSERT IGNORE / ON CONFLICT DO NOTHING 跳过； ③ 先灌进临时表，用 INSERT ... SELECT ... WHERE NOT EXISTS 去重后再写入。 大批量选 ③，代价最低且可校验。

第一层 · 概念与判定：什么时候必须批量

一句话判据：影响行数超过几千行，就必须分批。单条大事务会带来锁表、主从延迟、回滚段膨胀三连击。

场景单条大 SQL分批理由
更新 10 万行❌✅锁范围大、主从延迟
更新 100 行✅⚠️ 不必一次搞定更简单
删除历史数据（百万级）❌✅推荐用分区 DROP 更快
导入 100 万行❌✅批量 INSERT 也要分批提交
ALTER TABLE❌—用 pt-online-schema-change / gh-ost
  • 信号一：DBA 告警「主从延迟 > 10 秒」→ 多半有大事务。
  • 信号二：SHOW PROCESSLIST 里一条 UPDATE 跑了几十秒 → 拆。
  • 信号三：运维要「清理三个月前数据」→ 优先考虑分区，而不是 DELETE。

核心认知：大事务的问题不在「慢」，而在「长时间持锁 + 从库回放串行」。主库上 3 秒完成的大事务，从库可能要 30 秒回放——因为从库是单线程（或有限并行）重放。

第二层 · 参数·命令·量化：分批模板与批次大小

分批模板

-- 分批 UPDATE 模板（按主键切段，每批 1000 行）
-- 循环执行直到影响行数为 0
UPDATE orders
SET status = 2
WHERE status = 1 AND id >= :start_id AND id < :start_id + 1000;
-- 应用层：start_id 从 MIN(id) 开始，每次 += 1000，直到 affected_rows = 0

-- 分批 DELETE（同样按主键切段）
DELETE FROM logs WHERE created_at < '2025-01-01' AND id < :max_id LIMIT 1000;

-- 大批量 INSERT：一条语句插多行（比逐条快 10 倍以上）
INSERT INTO t (a, b) VALUES (1,'x'), (2,'y'), (3,'z'), ...;  -- 每批 500~1000 行

-- MySQL 的 INSERT 批量上限受 max_allowed_packet 限制
SHOW VARIABLES LIKE 'max_allowed_packet';   -- 默认通常 4MB / 64MB

-- PostgreSQL 用 COPY 最快
COPY t FROM '/path/to/file.csv' WITH (FORMAT csv);
参数默认值 / 建议说明
每批行数500～5000太小则往返多，太大则锁持有久；1000 是常用起点
批间间隔10～100 ms让主从复制跟上，避免延迟累积
max_allowed_packet4MB（MySQL 5.7）/ 64MB（8.0）限制单条 INSERT 的大小
innodb_lock_wait_timeout50 秒分批时要小于这个值，避免互相等锁
bulk_insert_buffer_size8MBMyISAM 批量插入缓冲（InnoDB 不适用）

量化参考：逐条 INSERT 1 万行约需 10～30 秒；改为每批 1000 行的批量 INSERT 可降到 0.5～2 秒，快 10～20 倍（省掉大量网络往返与事务开销）。

第三层 · 排障与边界：批量操作的坑

现象原因怎么查 / 怎么办
主从延迟飙升大事务在从库串行回放慢SHOW SLAVE STATUS 看 Seconds_Behind_Master；改分批
锁等待超时批次之间互相抢锁缩小批次；按主键有序切段避免交错
binlog 暴涨、磁盘满大事务产生巨大 binlog 事件分批；监控 max_binlog_cache_size
回滚特别慢大事务回滚要撤销所有 undo分批后每批独立提交，回滚只需撤最后一批
DELETE 后空间没释放InnoDB 只标记删除，空间复用不返还 OSOPTIMIZE TABLE（会锁表）或用分区 DROP
批量 INSERT 报 packet too large超过 max_allowed_packet调大参数或减小批次
  • 排查顺序：先看主从延迟 → 再看锁等待 → 再看 binlog 增长 → 最后看磁盘。
  • 边界一：分批必须按主键/唯一索引有序切段，否则各批扫描范围重叠，反而更慢。
  • 边界二：每批独立提交，这样中途失败只丢最后一批，且回滚快。
  • 边界三：删除超大量数据时，分区 + DROP PARTITION 比 DELETE 快几个数量级（秒级 vs 小时级），且不产生 undo。

大事务监控

-- 监控：当前有没有大事务在跑
SELECT trx_id, trx_started, trx_rows_locked, trx_rows_modified,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS secs
FROM information_schema.innodb_trx
WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 10
ORDER BY secs DESC;

-- 看 binlog 当前大小，判断是否有异常大事务
SHOW BINARY LOGS;
批次大小取多少最好？

经验起点 1000 行/批。太大（>1万）会长时间持锁、从库回放慢；太小（<100）往返开销占比高。实际要根据单行大小和锁竞争情况压测调整——目标是「单批耗时控制在 100ms 以内」。

为什么不直接一条 SQL 改完？

因为一条大 UPDATE 会在一个事务里锁住所有涉及的行，期间业务读写全部阻塞；且从库回放时是单线程，主库 3 秒、从库可能 30 秒，造成严重延迟。分批把「一次长锁」拆成「多次短锁」，代价是总耗时略长。

删除历史数据最快的方式是什么？

如果按时间删除，用分区表 + DROP PARTITION——它是元数据操作，秒级完成，不产生 undo 与 binlog 大事件。若已经是普通表，先改造成分区表（用 pt-online-schema-change 在线改），之后就能持续用 DROP 清理。
