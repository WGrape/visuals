覆盖率

看哪里没测到

-cover 给出整体比例；-coverprofile 生成明细，go tool cover -func 看逐函数，-html 可视化为网页。

go test -cover ./...
go test -coverprofile=c.out .
go tool cover -func=c.out     # 每函数覆盖率
go tool cover -html=c.out     # 浏览器高亮未覆盖行
竞态检测

专治并发幽灵

-race 在运行时插桩，检测对同一个变量的并发读写且无同步；能抓到大部分数据竞争，但会显著拖慢并增内存。

go test -race ./...

// 典型竞争：两个 goroutine 同时写同一变量
var x int
go func() { x++ }()
go func() { x++ }()   // race detector 会报
实践建议

CI 里默认开

把 -race 放进 CI 的测试步骤；覆盖率设阈值防止退化。竞态检测有开销，本地/CI 跑，生产二进制一般不带。

⚠️ -race 只能发现「实际触发」的竞争，并非证明无竞争；仍要结合设计（channel/锁）消除共享写。

覆盖率：怎么测，怎么看

# 控制台看总覆盖率 go test -cover ./... # 生成覆盖率文件并可视化 go test -coverprofile=cover.out ./... go tool cover -func=cover.out # 按函数列出 go tool cover -html=cover.out # 浏览器里逐行标色 # 统计模式：set / count / atomic go test -covermode=count -coverprofile=cover.out ./... # count：记录执行次数，可看出「跑过几次」 # atomic：并发安全版，配合 -race 使用 # 合并多个包的覆盖率 echo 'mode: count' > all.out grep -h -v '^mode:' *.out >> all.out
语句覆盖率Go 默认统计的是语句是否被执行过。
绿色/红色-html 里绿色为已覆盖，红色为未覆盖。
count 模式能看出分支被执行了多少次。
按包统计整体覆盖率会被无关包稀释。

覆盖率的正确用法：它是找盲区的工具，不是质量证明。100% 覆盖率不等于没有 bug——它只说明每行都跑过，不说明断言是否充分、边界是否覆盖。

覆盖率的三个误区

高覆盖率 ≠ 高质量

只调用不断言，覆盖率一样很高。

// 覆盖率 100%，但什么都没验证 func TestAdd(t *testing.T) { add(1, 2) // 没断言！ } // 有价值的测试 func TestAdd(t *testing.T) { if got := add(1, 2); got != 3 { t.Errorf("add(1,2) = %d, want 3", got) } }

只测正常路径

  • 错误分支往往才是出问题的地方
  • 边界值：0、负数、空串、超长、nil
  • 并发与超时路径容易被忽略
  • 关注「未覆盖的红色块」集中在哪

为了覆盖率写测试

  • 测实现细节会导致重构即失败
  • 应测可观察行为而非内部步骤
  • 表驱动测试能低成本覆盖多分支
  • 把覆盖率当作入口，而不是目标

竞态检测：-race 是怎么工作的

-race 启用的是 ThreadSanitizer：它在编译时插桩，记录每次内存访问与同步事件，用向量时钟判断是否缺少同步。

# 开启竞态检测跑测试 go test -race ./... # 运行时也开启 go build -race -o app . # 典型报告 WARNING: DATA RACE Write at 0x00c0000100a0 by goroutine 7: main.inc() /app/main.go:12 +0x... Previous read at 0x00c0000100a0 by goroutine 6: main.inc() /app/main.go:10 +0x... Goroutine 7 (running) created at: main.main() /app/main.go:20 +0x...
维度说明
检测能力发现实际发生过的未同步访问，不是静态推断
漏报没被调度到的竞争路径不会报，因此需要多次运行
误报基本没有，报告出来通常就是真问题
性能代价内存约 5~10 倍，CPU 约 2~20 倍
适用场景CI 测试、预发压测，不建议长跑在生产
平台限制需要特定平台支持，交叉编译时不可用

常见修复手段：用互斥锁保护共享变量；改用 channel 传递所有权；使用 sync/atomic 做原子读写；或者干脆消除共享（每个 goroutine 用自己的副本最后汇总）。

典型竞态场景与修复

// ① 循环变量捕获（经典陷阱） for _, v := range items { go func() { process(v) }() // 所有 goroutine 共享同一个 v } // 修复：作为参数传入 for _, v := range items { go func(v Item) { process(v) }(v) } // ② 无保护的计数器 var count int go func() { count++ }() go func() { count++ }() // 修复：atomic 或 mutex var count atomic.Int64 go func() { count.Add(1) }() // ③ map 并发读写（会直接 panic） m := map[string]int{} go func() { m["a"] = 1 }() go func() { _ = m["a"] }() // 修复：加 sync.Mutex 或改用 sync.Map // ④ 懒初始化 var once sync.Once once.Do(func() { conn = connect() }) // 用 once 而不是 if conn == nil
闭包传参循环里起 goroutine 务必传值
共享变量要么加锁，要么不共享
map 并发读写都需保护，否则直接崩溃
懒加载用 sync.Once 而非手写判断
测试要并发跑-race 才更容易命中
CI 必开把 -race 纳入流水线

深入自检

覆盖率到多少才算够？

没有通用阈值。核心业务与复杂分支建议 70%~90%，简单 CRUD 可以更低。更实际的判据是：红色块是否集中在高风险逻辑上。强行追求 100% 往往导致测试与实现耦合过深。

-race 没报错是不是就没有竞态？

不能保证。它只能发现本次执行中实际发生的竞争。未被调度触发的路径会漏掉。因此需要配合并发压力测试、多次重复运行，以及代码层面的设计约束。

为什么 -race 这么慢，能在生产开吗？

插桩带来大量额外内存与 CPU 开销，通常不适合长期跑在生产。推荐在 CI、预发环境、灰度小流量或短时排查时开启。

map 并发读也会出问题吗？

并发只读是安全的；一旦有一个写者，所有读写都必须同步，否则可能触发运行时的并发 map 读写检测并直接 panic，或者读到不一致的数据。

竞态和死锁怎么区分？

竞态是结果不确定（读到旧值、数据被破坏），程序通常还能跑；死锁是程序卡住（互相等待、channel 无人配对），表现为 goroutine 全部阻塞。前者靠 -race，后者靠 goroutine profile 与运行时死锁检测。
