🍪 模板方法

固定算法骨架，把少数步骤留给子类定制。

一句话记住烘焙流程先和面、再烘烤、最后装盘；不同面包替换配方细节。

01 · 从问题出发

为什么会需要这个模式？

CSV 和 JSON 导入都要打开文件、解析、校验、保存；复制整个流程会让关键顺序漂移。

CSV 与 JSON 导入都要打开文件、解析、验证、保存和关闭。若复制两份完整流程，JSON 版本可能忘记关闭流，CSV 版本可能跳过校验；公共约束逐渐漂移。

😵 直接写会怎样

function importCsv(file): open(); parseCsv(); validate(); save(); close()
function importJson(file): open(); parseJson(); save(); close()
// JSON 分支忘记 validate

💡 关键转折

父类定义不可随意改的流程，子类实现差异步骤。

在父类固定步骤顺序与资源清理，只把 parse 留给子类覆盖。公共流程只维护一份。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

abstract class Importer {
  import(file) {
    stream = open(file)
    try {
      rows = this.parse(stream)  // 子类实现
      validate(rows)
      save(rows)
    } finally { stream.close() }
  }
  abstract parse(stream)
}
class CsvImporter extends Importer { parse(s) { return readCsv(s) } }

读代码时抓住三件事

  1. 模板入口固定整体算法顺序。
  2. 钩子方法 parse 是明确的扩展点。
  3. finally 保证正常和异常路径都释放资源。

换个业务场景，还能认出来吗？

测试框架的 setUp → test → tearDown 是模板方法的另一种形式：子类提供具体测试动作，框架保留生命周期顺序。变化点过多时，组合策略通常比继承更清楚。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

总体流程固定，仅少数步骤因类型不同

三个具体场景

  • CSV/JSON 导入共用打开、校验与保存
  • 测试框架固定 setUp/test/tearDown
  • 构建流程固定打包、检查和发布顺序

不适合或要小心

继承会让子类与父类耦合；变化维度多时可用组合和策略。不要让子类重写整个模板入口破坏约束。

继承耦合较强；变化维度多时更适合组合策略

最容易混淆的相邻模式

模式真正的区别
策略通过组合替换算法对象；模板方法通过继承覆盖少数步骤。
建造者分步骤构造一个对象；模板方法固定一段处理算法的执行顺序。

区分时问自己：是固定流程中替换少数步骤，还是自由替换一套算法？

落地前检查

  • 模板方法避免被子类整体重写。
  • 测试所有子类都遵守公共校验与清理。
  • 只开放真正需要变化的钩子，减少继承耦合。
06 · 自己说一遍

两道检验理解的小题

为什么 close() 放在父类模板中？

资源释放是所有导入都必须遵守的共同步骤，放父类能防遗漏。

为什么把 close 放入 finally 而不是 parse 后面？

parse 或 validate 抛错时，finally 仍会执行，避免资源泄漏。

第二层 · Go 里没有继承，模板方法怎么写

Go 没有 abstract，模板方法通常落成"固定流程 + 注入变化点"，三种写法按复杂度递增：

// 写法一：函数字段（变化点 < 3 个时最轻）
type Report struct {
	fetch    func(ctx context.Context) ([]Row, error) // 变化点
	render   func(rows []Row) string                  // 变化点
}

// 模板方法：流程固定，变化点由调用方注入
func (r Report) Run(ctx context.Context) (string, error) {
	rows, err := r.fetch(ctx) // 1. 取数（变）
	if err != nil {
		return '', err // 2. 统一错误处理（不变）
	}
	sort.Slice(rows, func(i, j int) bool { return rows[i].At.Before(rows[j].At) }) // 3. 排序（不变）
	return r.render(rows), nil // 4. 渲染（变）
}

// 写法二：接口 + 组合（变化点 >= 3 个，或需要多个模板复用同一组变化点）
type Step interface {
	Fetch(context.Context) ([]Row, error)
	Render([]Row) string
}
type Template struct{ Step }        // 嵌入接口，模板只依赖抽象
func (t Template) Run(ctx context.Context) (string, error) { /* 同上 */ }

// 写法三：钩子（可选步骤，默认空实现）
type Hooks struct {
	Before func(context.Context) error // 钩子：不实现就是空操作
	After  func(string) error
}
func (h Hooks) before(ctx context.Context) error {
	if h.Before == nil {
		return nil // 关键：钩子必须允许为 nil，否则调用方被迫写空函数
	}
	return h.Before(ctx)
}
写法适用规模优点代价
函数字段变化点 ≤ 3最轻、零接口、易读结构体字段多时显得散
接口 + 嵌入变化点 ≥ 3 或跨模板复用可被多模板复用、易测接口一旦定死难加步骤
钩子（可空函数）步骤可选调用方只写关心的钩子太多会变成配置地狱
泛型约束同流程多类型编译期绑类型、无反射约束表达式可读性差

第三层 · 模板方法最容易踩的六个坑

  • 流程膨胀：模板方法里塞进 if/else 分支处理特例 → 说明该拆成两个模板，或把分支下沉为钩子。
  • 钩子滥用：钩子多于 3 个时，调用方不知道该实现哪个 → 只保留‘确实有人会用’的钩子，其余删掉。
  • 抽象方法 vs 钩子混淆：抽象方法必须实现、钩子可选；把可选步骤写成抽象方法会逼调用方写空实现。
  • 变化点泄漏到模板：模板里出现 if type == A → 变化点没抽象干净。
  • 错误处理不统一：每个变化点各写各的错误 → 模板方法的核心价值之一就是统一错误与日志，别交出去。
  • 测试困难：模板是具体结构体时没法替换步骤 → 依赖接口，测试时注入 fake 步骤。

自检一句话：模板方法里只应该出现流程顺序、错误处理、公共日志，出现业务判断就是抽象漏了。

第四层 · 什么时候不该用模板方法

变化点很多、且每个变化点本身也有多种实现，怎么办？

换策略模式或组合：模板方法适合‘流程固定、步骤替换’，一旦一个步骤有 3 种以上独立实现并且要运行时切换，就该把步骤提成策略对象。

模板方法和回调有什么区别？

回调是把一段行为交给别人在‘某个时刻’调用，调用方不知道整体流程；模板方法是父类/模板掌握整体流程，只把某些步骤留空。判断标准：谁掌握流程顺序。

继承式模板（Java abstract class）的最大风险？

子类能看到并覆盖父类的非 final 方法，等于把流程也开放了；所以 Java 里模板方法通常声明为 final，只放开抽象方法。

一、最小骨架

type DataSync interface { Fetch() []byte // 抽象步骤：拉数据 Parse(b []byte) []Row // 抽象步骤：解析 Validate(r []Row) error // 钩子：默认校验，可覆盖 } func Sync(d DataSync) error { // 模板方法：流程定死，不希望子类改顺序 raw := d.Fetch() rows := d.Parse(raw) if err := d.Validate(rows); err != nil { return err } return store(rows) } // 具体子类只要实现三个方法，流程永远一致

注意这里用接口 + 函数而不是继承 —— Go 没有类继承，用「接口约束 + 模板函数」是更符合语言习惯的写法，效果等价于模板方法，而且避免了继承带来的强耦合。

二、钩子方法是什么

钩子是有默认实现、子类可选覆盖的方法。它让子类在不改流程的前提下微调行为：

钩子类型作用例子
分支钩子返回一个 bool 决定某步是否执行needCache() bool 决定是否走缓存
扩展钩子空实现，子类可插入前后逻辑beforeSave() / afterSave()
默认实现钩子提供通用实现，特殊子类才覆盖Validate() 默认非空校验
强制抽象步骤必须实现，没有默认Fetch() / Parse()

三、模板方法 vs 策略 vs 回调

模板方法策略模式回调函数
复用方式继承（或接口+固定流程）对象组合传函数
谁控制流程父类调用方调用方
能替换什么只能替换个别步骤整个算法都能换某一步的实现
耦合度较高，子类绑死父类低最低
典型场景流程稳定、步骤多变多种算法平级可选一次性的小定制
常见误用

把流程方法也写成可覆盖的，子类一改顺序，上游假设全崩。正确做法是：流程方法用 final / 不导出函数锁死，只暴露步骤。

四、真实场景

构建/部署流水线拉代码-编译-测试-发布 固定，各语言只实现编译与测试
数据导入框架读-清洗-校验-落库固定，各数据源实现读与洗
测试框架setUp / runTest / tearDown 三件套
订单处理校验库存-扣减-支付-通知，各业务类型只改校验与通知
报表导出查询-组装-渲染-写出，各格式只实现渲染

五、深入自检

模板方法是不是违反里氏替换？

不违反：子类只覆盖「预留的抽象方法」，不改变基类对外承诺的行为契约。但如果子类覆盖了流程方法本身，就破坏了契约，这也是为什么流程必须锁死。

为什么现在很少提这个模式？

因为它和「继承」绑定，而现代实践更偏好组合。在 Go/Rust 这类无继承的语言里，模板方法往往被改写为「接口 + 模板函数」或「策略 + 默认实现」，本质思想没变。

和建造者模式怎么区分？

建造者关心「如何一步步构造出一个复杂对象」，步骤顺序由调用方（Director）决定；模板方法关心「一个算法的流程骨架固定，其中几步留给子类」。前者产出对象，后者执行算法。

钩子会不会让流程变得不可预测？

会，所以要克制。经验法则：钩子只用于可选增强和分支开关，不允许钩子改变步骤顺序或跳过必做步骤。
