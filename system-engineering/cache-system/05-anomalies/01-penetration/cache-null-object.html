🥤 缓存空值：把「查不到」也变成一个事实

数据库返回空也写入缓存，让下一次相同查询止步于缓存层——对付穿透最省事的兜底手段。

🥤

占位值

查不到就写一个空标记

⏱️

短 TTL

1~5 分钟，别太长

🧯

兜底角色

配合布隆过滤器收尾

⚠️

内存风险

随机 key 会把内存撑爆

先建立直觉：门卫的「黑名单便签」

把缓存想成大楼门卫。正常情况门卫手里有一份住户名单，来人报名字，名单上有就放行。

问题是：有个陌生人每天来问「302 室的张三在吗？」，门卫查不到，就每次都打电话去物业（数据库）确认，物业也说没有。这通电话每天打一百次，物业烦死了。

缓存空值就是门卫学聪明了：第一次确认「没有这个人」之后，他在便签上记一笔「张三 = 查无此人」。下次再有人问，他看一眼便签就直接回绝，不再打电话。

实现：一个占位值 + 一个短 TTL

核心只有两步：查库为空也要写缓存，并且给一个较短的过期时间。代码里通常用一个特殊字符串（如 "NULL" 或 "__EMPTY__"）作为占位标记，避免和真实数据混淆。

// Java 风格伪代码
public User getById(long id) {
    String key = "user:" + id;
    String cached = redis.get(key);
    if (cached != null) {
        return NULL_MARK.equals(cached) ? null : deserialize(cached);
    }
    User u = userMapper.selectById(id);
    if (u == null) {
        redis.setex(key, 60, NULL_MARK);   // ① 空也缓存  ② TTL 短
        return null;
    }
    redis.setex(key, 300, serialize(u));
    return u;
}
为什么不能直接用 null 当占位值？大多数 Redis 客户端里 get 返回 null 既可能表示「key 不存在」，也可能表示「值就是空」，两者无法区分。你必须写进一个真实存在的字符串标记，读出来后再翻译成业务上的 null。

TTL 为什么必须短

这是这个方案唯一的、也是最容易踩的坑。占位值意味着「此刻这条数据不存在」。但数据是会变的：

典型事故：用户注册后立即查询自己的资料，却返回「用户不存在」。原因就是注册前的那次查询写入了长 TTL 的空值。正确做法：写入数据时主动 DEL 掉对应的空值占位，或者把 TTL 压到 1 分钟级别。

它的内存风险：随机 key 攻击

空值缓存有一个致命的规模问题：攻击者只要构造大量不同的、不存在的 key，你就要为每一个 key 缓存一个空值。一亿个随机 id = 一亿条缓存记录，Redis 内存直接打满，甚至触发淘汰把正常热点数据挤掉。

场景空值缓存表现更合适的方案
少量重复的无效 id（业务 bug）✅ 非常合适，几乎零成本空值缓存即可
海量随机 key（攻击）❌ 内存被撑爆布隆过滤器 + 限流
能被枚举的合法 id 空间⚠️ 可用但要控 TTL布隆过滤器更稳

与其他手段的配合关系

  1. 参数校验先挡掉 id<=0 这类非法输入；
  2. 布隆过滤器挡掉绝大部分不存在的 key；
  3. 空值缓存接住布隆过滤器误判漏过来的少量请求；
  4. 限流控制总体请求量级。
一句话定位：空值缓存不是最强的方案，但是最便宜、最兜底的方案。它单独面对海量随机 key 会失效，但作为布隆过滤器之后的最后一道防线，性价比极高。

🎯 面试问答

Q：缓存空值会不会把 Redis 撑爆？
A：会，这正是它的主要风险。攻击者用海量不同的随机 key 请求，每个都写一个空值，内存迅速耗尽，甚至触发 maxmemory 淘汰把真正的热点数据挤出去。应对：必须配合参数校验与限流；面对大规模随机 key 场景，改用布隆过滤器（它不随请求量增长，只与合法 key 总量有关）。

Q：业务上真的创建了数据，怎么让用户立刻查到？
A：两个办法：① 在创建数据的代码里主动 DEL 掉那个 key（推荐，最及时）；② 把空值 TTL 设得很短（1 分钟左右），让它自然过期。不要依赖「等它自己过期」作为唯一手段，那会导致用户困惑。

Q：占位值该用什么？能用空字符串吗？
A：可以用空字符串，但不推荐——如果你的业务里合法数据本身就可能序列化成空串，就会混淆。更稳妥是用一个不可能与真实数据冲突的特殊标记，比如 "__NULL__"、"__EMPTY__"，或者在值里加一个类型字段。关键原则是：占位值必须能与「真实数据」和「key 不存在」两者都区分开。

Q：空值缓存和布隆过滤器能互相替代吗？
A：不能，它们是互补的。布隆过滤器挡在缓存之前、不占 Redis 内存、能挡海量随机 key，但有误判且要维护同步；空值缓存在缓存之内、改动极小、能兜住布隆漏过的请求，但占内存。生产上通常两者一起上：布隆挡大头，空值收尾。

缓存穿透的方案对比

方案原理代价 / 局限
缓存空值查不到也写进缓存（短 TTL）内存被无效 key 占用；TTL 内数据出现会有短暂不一致

互斥锁同 key 只放行一个回源解决击穿不是穿透

误判率 p默认 0.01~0.03只可能误判「存在」，不会漏判
位数组长度 mm = -n·ln p / (ln 2)²n=1 亿、p=1% 时 m ≈ 9.6 亿位 ≈ 114 MB
哈希函数个数 kk = (m/n)·ln 2n=1 亿、m=9.6 亿时 k ≈ 6.6 ≈ 7

空值缓存 vs 布隆过滤怎么选：空值缓存实现最简单，TTL 设 60~300 秒，能挡住重复攻击，适合大多数场景；布隆过滤器适合 key 基数极大且攻击 key 随机的场景（每次都是新 key，缓存空值挡不住）。两者常一起用。

# 方案 1：缓存空值（最实用）
def get_item(item_id):
    key = f"item:{item_id}"
    v = cache.get(key)
    if v == NULL_SENTINEL:          # 用特殊标记区分「不存在」和「缓存没命中」
        return None
    if v is not None:
        return v
    v = db.query(item_id)
    if v is None:
        cache.set(key, NULL_SENTINEL, ex=random.randint(60, 300))   # 加随机抖动防同时过期
        return None
    cache.set(key, v, ex=600)
    return v
# 注意：TTL 加随机抖动，避免同一时刻大量空值同时过期造成二次冲击
# 方案 2：布隆过滤器（RedisBloom 模块或 Guava）
# RedisBloom 命令
#   BF.RESERVE myfilter 0.01 1000000     # 误判率 1%，预期 100 万元素
#   BF.ADD myfilter item123
#   BF.EXISTS myfilter item123           # 0=一定不存在, 1=可能存在

import redis
r = redis.Redis()
def get_item_bf(item_id):
    if not r.execute_command("BF.EXISTS", "item_filter", item_id):
        return None                      # 一定不存在，直接返回，不打 DB
    return get_item(item_id)             # 可能存在，走正常流程

# 初始化：把所有存在的 id 灌进过滤器
# 新增数据时同时 BF.ADD（注意：删除数据无法从 BF 移除）

# 手写布隆过滤器（理解原理）
import mmh3, math

class BloomFilter:
    def __init__(self, n, p=0.01):
        self.m = int(-n * math.log(p) / (math.log(2) ** 2))    # 位数组长度
        self.k = max(1, int(self.m / n * math.log(2)))          # 哈希函数个数
        self.bits = bytearray((self.m + 7) // 8)

    def add(self, s):
        for i in range(self.k):
            self.bits[(mmh3.hash(s, i) % self.m) // 8] |= 1 << ((mmh3.hash(s, i) % self.m) % 8)

    def __contains__(self, s):
        return all(self.bits[(mmh3.hash(s, i) % self.m) // 8]
                   & (1 << ((mmh3.hash(s, i) % self.m) % 8)) for i in range(self.k))

排障清单

症状原因处理
加布隆过滤器后查不到新数据新增数据没同步进过滤器写入 DB 时同时 BF.ADD；或用异步同步
删除的数据还能查到标准 BF 不支持删除换 Counting Bloom Filter；或改用空值缓存
误判率比预期高实际元素数远超预设 n按实际规模重建；n 要按峰值预估
内存占用大m 按 n 和 p 算出来的放宽 p 到 3% 可省约 30% 空间
空值缓存把内存撑爆无效 key 太多缩短 TTL；先用布隆过滤器在前面挡一层
数据新增后 TTL 内读不到空值还没过期新增时主动删除对应的空值缓存
穿透但没查出来源没有监控监控 缓存未命中率和 DB QPS；异常时告警

布隆过滤器的两个「反直觉」点：① 说「不存在」是确定的，说「存在」是可能的（有误判）；② 空间只与预期元素数和误判率有关，与元素本身大小无关——所以存 URL（几十字节）和存整数（8 字节）占用完全一样。
