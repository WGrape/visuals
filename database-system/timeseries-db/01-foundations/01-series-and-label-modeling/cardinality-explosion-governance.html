基数爆炸治理：为什么序列数会失控，以及怎么止血

序列数是标签取值数的乘积、五步定位法、止血与重建手段，以及五条标签设计规则

一句话总结：时序库最容易被拖垮的不是数据量，而是序列数。序列数 = 指标名 × 各标签取值数的乘积，所以只要往标签里塞一个无界的值（user_id、request_id、URL 路径），序列数就会爆炸。基数爆炸会同时打爆内存、磁盘、查询速度和采集端。

01为什么基数这么致命

序列数是标签取值数的乘积，一个无界标签就能让总量失控

🧮 是乘积不是加法

加一个 10 取值的标签，序列数乘以 10。加一个 10 万取值的标签，就乘以 10 万。

🧠 每条序列都要占内存

活跃序列常驻内存（head block），每条都有索引、块、元信息——内存是第一受害者。

💾 压缩率跟着崩

序列多了每个块填不满，压缩的参考窗口变短，磁盘占用反而涨得更快。

🐢 查询全面变慢

聚合要遍历所有匹配序列；序列多则索引大、解压多、结果集大。

📡 采集端同步受损

抓取体积变大、耗时变长，可能触发超时，进一步造成数据缺口。

要点：判断标准：一个标签的取值空间是不是有界的、且不会随时间无限增长。不是 → 它就不该是指标标签。

02怎么发现：定位是哪个标签在炸

  1. 先看总序列数趋势：如果它在持续增长（而不是稳定波动），就已经有问题了。
  2. 找出序列数最多的指标：按指标名分组统计，通常前几名就是元凶。
  3. 找出该指标里基数最高的标签：逐个标签统计取值数。
  4. 看标签取值的样例：如果看到 id、uuid、路径带参数，基本可以确认。
  5. 对比变更前后的序列数：新版本上线后序列数台阶式上涨 = 新加了高基数标签。
# Prometheus / PromQL：定位基数问题（指标名以实际版本为准）
# ① 总活跃序列数（看趋势比看绝对值更重要）
prometheus_tsdb_head_series

# ② 序列数最多的指标 TOP10
topk(10, count by (__name__)({__name__=~".+"}))

# ③ 某个指标里，哪个标签的取值最多（逐个标签试）
count(count by (path)    (http_requests_total))
count(count by (user_id) (http_requests_total))
count(count by (status)  (http_requests_total))      # 对比：低基数标签只有个位数

# ④ 看新写入的序列增速（判断是不是刚引入的问题）
sum(rate(prometheus_tsdb_head_series_created_total[5m]))

# ⑤ 抓取体积异常大也是信号
scrape_samples_scraped          # 每次抓取的样本数
scrape_duration_seconds         # 抓取耗时（变长会导致超时丢数据）
要点：count by (__name__)({__name__=~".+"}) 这类查询本身很重，不要在已经很卡的生产环境反复跑。可以在低峰执行，或改用 TSDB 自带的分析工具。

03怎么治理：止血 → 重建 → 预防

阶段做什么具体手段
① 止血（立刻降负载）把高基数标签从指标里去掉采集端/远端写配置里用 metric_relabel_configs 丢弃该标签（drop），先恢复服务
② 重建（保住可观测性）把高基数维度挪到合适的地方用户/订单/请求这类维度去日志或链路追踪；URL path 改成路由模板（/user/:id）
③ 预防（不再复发）建立规则与卡点标签白名单、上线前检查序列数增量、对新增指标做评审
# Prometheus：用 metric_relabel_configs 丢弃高基数标签（止血手段）
scrape_configs:
  - job_name: 'app'
    static_configs:
      - targets: ['app:8080']
    metric_relabel_configs:
      # 直接丢掉无界标签（最有效，但要确认没有报表依赖它）
      - target_label: user_id
        replacement: ''
      - action: labeldrop
        regex: 'user_id|request_id|trace_id'

      # 或者：把高基数的 path 归一化成路由模板（保住维度、砍掉基数）
      - source_labels: [path]
        target_label: route
        regex: '/user/([0-9]+)/.*'
        replacement: '/user/:id'
      - action: labeldrop
        regex: 'path'

04标签设计规则：什么该放、什么不该放

维度适合做标签不该做标签（改去日志/追踪）
基础设施instance、job、region、zone、node容器 ID、Pod UID（可用但注意生命周期短）
请求method、status、route（模板化）URL 明细、query 参数、request_id
业务tenant、plan、channel、product_lineuser_id、order_id、session_id
版本version、build（注意发版会新增序列）git commit hash（每次发版都变）
  • 规则一：取值必须有上界。能被用户行为决定取值的，一律不做标签。
  • 规则二：取值不能随时间无限增长。Pod UID、commit hash 这类会随发布不断新增。
  • 规则三：基数要可预估。新增标签前先算「乘上去会不会翻倍」。
  • 规则四：能用枚举就别用自由文本。错误详情这类自由文本应放日志。
  • 规则五：高基数需求用日志/追踪满足。指标的优势是聚合与告警，不是查明细。
要点：一个好用的判据：「这条查询的结果，我会想按这个维度做告警吗？」不会 → 它就不该是指标标签。

05常见疑问

问：序列数多少算多？

没有绝对值，看增长趋势和单机承载。关键信号是：序列数是否随发布/时间持续增长、内存是否吃紧、抓取是否变慢。稳定在一个量级通常没问题，持续线性增长一定有问题。

问：我必须按 user_id 查指标怎么办？

说明这个需求本质上不是指标场景。正确做法是：指标只保留聚合维度（按租户/渠道），用户级明细走日志或链路追踪系统。强行用指标承载高基数，代价是拖垮整个监控系统。

问：丢了标签会不会影响已有看板？

会。所以止血是临时手段，正确流程是：先确认有哪些看板/告警依赖该标签，改掉它们（或改为从日志侧取数），再丢标签。不要先丢再看。

问：加一个低基数标签也有影响吗？

有，但是乘法关系：加一个 5 取值的标签，序列数变 5 倍。每加一个标签前都要算这笔账——这也是为什么标签设计要克制。
