时序数据库如何选型

先区分监控抓取、设备主动上报、时间线规模和长期保留，再对比不同产品。

把业务需求变成可测量的条件

  1. 数据从常驻服务被抓取，还是从 NAT 后的设备持续推送？
  2. 标签的取值组合会产生多少条活跃时间线？查询是否依赖按字段过滤？
  3. 高精度点保存多久，趋势数据是否要降采样，长期存储的成本如何计算？

05主流产品对比

产品定位数据模型特点
Prometheus监控告警事实标准metric + labels 拉模式（pull）、PromQL 强大、单机为主；长存储需接 Thanos/VictoriaMetrics
InfluxDB通用时序数据库measurement + tags + fields 客户端写入；1.x/2.x 与 3.x 的引擎、查询语言和部署能力需分别核对
TDengine国产，IoT/工业场景超级表（STable）+ 子表 以设备子表和超级表组织数据；压缩与写入效果取决于负载和部署
VictoriaMetricsPrometheus 的长期存储兼容 Prometheus 内存占用低、性能高，Prometheus 生态的增强替代
TimescaleDB基于 PostgreSQL 的时序扩展关系表 + hypertable 完整 SQL、可 JOIN 业务表；适合不想引入新技术的团队
ClickHouse通用 OLAP（也能存时序）宽表 可用 TTL、物化视图等能力管理时序数据；需自行设计相应的数据模型与保留方案
选型直觉：
· 云原生监控告警 → Prometheus（+ VictoriaMetrics 做长期存储）
· IoT / 设备上报 / 国产化 → TDengine
· 想用 SQL 且数据量中等 → TimescaleDB
· 已有 ClickHouse 且量大 → 直接用，配合物化视图做降采样

选择产品之后还要验证

对真实写入速率、基数、查询窗口和保留期做压测；同时比较压缩比、故障恢复与迁移成本。产品宣传的吞吐和压缩数字不能替代工作负载。
