理解线程状态机，很多「为什么卡住了」「为什么没执行」的问题就有了答案。

动手看：竞态是怎么发生的

import threading, time count = 0 def inc_no_lock(): global count for _ in range(200000): count += 1 # 读 → 改 → 写，中间可能被切换 ts = [threading.Thread(target=inc_no_lock) for _ in range(4)] [t.start() for t in ts] [t.join() for t in ts] print(count) # 期望 800000，实际常常更小 # 交错过程： # 线程A 读到 count=100 # 线程B 读到 count=100（A 还没写回） # 线程A 算出 101 写回 # 线程B 算出 101 写回 ← 两次自增只加了 1
元素值 / 说明
线程数4
每线程自增200000
期望结果800000
典型实际结果小于 800000，且不固定
原因自增不是原子操作，GIL 可能在中间切换
修复用 Lock 保护，或改用单线程累加

重点：结果每次都可能不同，这正是并发 bug 最难排查的地方——它不确定、难以稳定复现。

加锁之后：正确但要知道代价

import threading count = 0 lock = threading.Lock() def inc_with_lock(): global count for _ in range(200000): with lock: count += 1 # 结果稳定为 800000 # 代价： # 1) 加锁/解锁本身有开销 # 2) 锁争用会让线程串行执行，失去并发性 # 3) 锁粒度过大 → 并发退化；过小 → 容易漏保护 # 更高效的思路：让每个线程算自己的部分，最后汇总 def worker(n): local = 0 for _ in range(n): local += 1 # 纯局部变量，无需加锁 return local with ThreadPoolExecutor(max_workers=4) as ex: total = sum(ex.map(worker, [200000] * 4))

避免死锁

  • 按固定顺序获取多把锁
  • 用 with 语句确保一定释放
  • 设置超时：lock.acquire(timeout=1)
  • 尽量减小锁的粒度与持有时间

调试技巧

  • 打印线程名与状态定位卡点
  • threading.enumerate() 看存活线程
  • faulthandler.dump_traceback 打印全部栈
  • 用 queue 传递数据，减少共享状态

什么时候别用线程

  • CPU 密集计算 → 用进程池
  • 成千上万并发连接 → 用 asyncio
  • 只是想「后台跑个任务」→ 线程池即可
  • 共享状态太多 → 重新设计数据流

深入自检

为什么 start() 之后不能立刻拿到结果？

start 只是让线程进入就绪状态，真正的执行时机由调度决定。要等待结果必须调用 join()，或者用线程池的 future.result() 来获取。

join 的作用是什么，不加会怎样？

join 会阻塞当前线程直到目标线程结束。主程序若不 join 就退出，非守护线程会被解释器等待完成（Python 会等它们结束才退出），但你的后续逻辑可能在线程完成前就执行了，导致读到不完整的结果。

加了锁为什么程序变慢很多？

锁把并发段变成了串行段。如果锁的粒度太大（比如整个循环都包住），多线程几乎退化成单线程，还要额外付出加锁开销。应当只保护真正需要互斥的那几行。

daemon=True 有什么风险？

主程序退出时守护线程会被直接终止，正在进行的收尾（写文件、提交事务）可能丢失或处于不完整状态。适合用于可以随时放弃的后台任务，关键收尾要显式 join。

多线程和 asyncio 能混用吗？

可以，但要有明确分工：asyncio 负责高并发 I/O，遇到无法异步的阻塞库时用 run_in_executor 丢到线程池执行。关键是别在协程里直接调用阻塞函数，那会卡住整个事件循环。

GIL 的本质影响：同一时刻只有一个线程执行 Python 字节码。所以多线程对CPU 密集任务完全没有加速，甚至因为切换开销而更慢；对 IO 密集任务有效（因为等 IO 时会释放 GIL）。要利用多核必须用 ProcessPoolExecutor。

线程安全代码

import threading, time
from concurrent.futures import ThreadPoolExecutor

# 1) 计数器必须用锁（即使是 += 也不原子）
counter = 0
lock = threading.Lock()

def inc():
    global counter
    for _ in range(100000):
        with lock:                  # 不加锁结果会小于预期
            counter += 1

# 为什么 += 不原子？
# 它编译成三条字节码：LOAD / ADD / STORE
# 线程可能在 LOAD 之后被切换，导致两个线程读到同一个旧值

# 2) 生产者-消费者：用 Condition 而不是忙等
cond = threading.Condition()
queue = []

def producer():
    for i in range(10):
        with cond:
            queue.append(i)
            cond.notify()            # 通知一个等待者

def consumer():
    while True:
        with cond:
            while not queue:         # while 不是 if（防虚假唤醒）
                cond.wait()          # 释放锁并等待，被唤醒后重新加锁
            item = queue.pop(0)

# 3) 用 Queue 更省心（内部已实现锁与条件变量）
from queue import Queue
q = Queue(maxsize=100)
q.put(item)              # 满了会阻塞
item = q.get(timeout=5)  # 超时抛 Empty
q.task_done()            # 配合 q.join() 等待全部处理完
# 4) 线程池的正确用法
from concurrent.futures import ThreadPoolExecutor, as_completed

# IO 密集：线程数可以远大于 CPU 核数
with ThreadPoolExecutor(max_workers=50) as ex:
    futs = {ex.submit(fetch, url): url for url in urls}
    for fut in as_completed(futs):
        url = futs[fut]
        try:
            data = fut.result(timeout=10)
        except Exception as e:
            print(url, "failed:", e)

# CPU 密集必须用进程池
from concurrent.futures import ProcessPoolExecutor
with ProcessPoolExecutor(max_workers=os.cpu_count()) as ex:
    results = list(ex.map(cpu_heavy, data))
# 注意：传给进程池的函数和参数必须可 pickle

# 5) 检测竞态（开发期）
# threading.settrace 可以挂钩，但更实用的是：
#   - 用 Queue 传递数据而不是共享变量
#   - 用 threading.local() 存线程私有状态
local = threading.local()
local.value = 1      # 每个线程有独立副本

第二层 · GIL 的实测数字与选型

场景多线程收益原因
网络请求 / 文件读写明显提升等待 IO 时会释放 GIL
正则、序列化、纯 Python 计算几乎无提升始终占用 GIL
NumPy / pandas 大矩阵运算部分提升底层 C 代码会主动释放 GIL
C 扩展里的计算取决于扩展是否释放 GIL看扩展实现

GIL 的切换间隔由 sys.getswitchinterval() 控制，默认 0.005 秒；把它调小会让切换更频繁、单线程更慢，一般不需要动。

可以直接跑的对比代码

import sys, threading, time
print(sys.getswitchinterval())        # 默认 0.005 秒

def io_bound():
    time.sleep(0.5)                  # 模拟 IO：等待时会释放 GIL

# 4 个 IO 任务并发，总耗时约 0.5 秒而不是 2 秒
ts = [threading.Thread(target=io_bound) for _ in range(4)]
t0 = time.time()
[t.start() for t in ts]; [t.join() for t in ts]
print('IO 密集型并发耗时 %.2fs' % (time.time() - t0))

# CPU 密集型：改用进程池才能真正并行
from concurrent.futures import ProcessPoolExecutor
with ProcessPoolExecutor() as ex:
    list(ex.map(sum, [range(10_000_000)] * 4))

第三层 · 线程的坑与替代方案

  • 锁要成对且有序：多个锁按固定顺序获取，否则必然死锁；能用 RLock 就不要用裸 Lock 处理可重入场景
  • 信号量与事件的取舍：限制并发数用 Semaphore，等某个条件成立用 Event 或 Condition
  • 线程池的容量按下游承受能力定，不按 CPU 核数定；IO 型可以远大于核数
  • CPU 密集型不要硬扛：改用 ProcessPoolExecutor，或者换成异步 IO 处理高并发 IO
需求选什么理由
高并发网络 IOasyncio / 异步框架单线程即可支撑上万连接
CPU 密集计算ProcessPoolExecutor绕过 GIL，真正多核
少量 IO + 要共享状态threading共享内存方便，心智负担小
定时任务 + 后台清理threading.Timer / 守护线程简单直接
