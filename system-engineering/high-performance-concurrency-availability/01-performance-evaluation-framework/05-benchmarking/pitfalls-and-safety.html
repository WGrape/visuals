压测注意事项：保护系统，也保护结论

一次压测若影响共享服务，或只测出了压测机上限，哪怕数字很大也没有参考价值。

范围、止损与清理

  • 只测自有或明确授权的隔离目标；确认域名/IP、允许时段、负责人、监控值守及共享依赖。第三方 API 的文档配额不代表压测许可。
  • 事先设定成功率、P99、持续积压、CPU/内存/网络与下游错误等阈值；达到停止条件就停止升档、撤销负载并确认系统恢复，不以打崩为目标。
  • 写请求必须有专用账户和可清理数据；隔离消息、邮件、付款、告警等有副作用的路径。准备恢复/回滚步骤与测试后的数据核对。

最常见的测量陷阱

  1. 测错对象：把非 2xx 响应、重定向到登录页、缓存命中结果当成功；抽样检查状态码和响应体/业务字段。
  2. 生成器先饱和：压测机 CPU、带宽、端口或文件描述符先满，增加客户端并发只增加本地等待；两端都要监控。
  3. 闭环掩盖拥塞：服务变慢后客户端等结果再发，实际到达率下降；若目标是固定到达速率，要换模型并记录被丢弃/积压的请求。
  4. 预热与窗口混杂：冷启动、JIT、缓存升温及恢复期间混入正式统计；显式分段，既保留冷启动结果又独立报告稳态。
  5. 只看平均与成功样本：超时/失败被过滤会让 P99 看上去变好；对比工具的延迟分布、超时和业务日志。
  6. 测试条件漂移：请求体变小、数据库变空、缓存由冷转热、依赖被替身替换或自动扩缩容发生时，不能把两次结果直接作版本比较。

工具边界与报告约束

ab 的 -c 是客户端并发请求数；wrk 的 -c 是连接数。两者都不能直接读作服务端业务并行数。常规固定并发/连接压测也不等于恒定到达率；客户端测得的 Requests/sec 未必是业务成功吞吐。

保留命令、工具版本、服务器配置、请求与响应样本、失败分类、完整时序和监控截图/导出数据。一个结果只对当时版本、环境、数据与负载模型成立；生产容量还需故障切换与流量突刺余量。
