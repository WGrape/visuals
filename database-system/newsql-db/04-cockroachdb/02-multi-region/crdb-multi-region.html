①先定生存目标，再定表布局

多区域部署的核心问题是：当整个区域挂掉时，你要的是「数据不丢」还是「服务不停」。 这个选择决定了副本怎么放，也决定了写入延迟。

生存目标含义代价
Zone（机房级）存活容忍单个可用区故障副本跨机房，写延迟 = 同城往返
Region（地域级）存活容忍整个城市/地域故障副本跨城，写延迟 = 跨城往返（几十毫秒级）
这是无法绕开的物理约束。「跨地域强一致」意味着每次写入都要等跨城的多数派确认， 写入延迟不可能低于跨城 RTT。想低延迟就只能放松一致性（异步复制）或放松生存目标。 先接受这个权衡，再谈优化。

②三种表类型的取舍

REGIONAL BY TABLE（默认）

数据整体放在一个主区域，其他区域访问要跨区。 写入最快、本地读快、跨区读慢。适合「绝大多数请求来自同一区域」的业务。

REGIONAL BY ROW

按行的区域列自动决定该行放在哪个区域。 本地读写都快，跨行事务慢。适合「用户数据与其所在地区强绑定」的场景（数据合规、本地化）。

GLOBAL

所有区域都有完整可读副本，本地读极快，但写入需要全区域一致，写最慢。 适合读多写少的参考数据（配置、字典、价格表）。

-- 按行分区：用 region 列决定行的归属
ALTER TABLE users SET LOCALITY REGIONAL BY ROW;

-- 全局表：读多写少的字典表
ALTER TABLE configs SET LOCALITY GLOBAL;

-- 读历史数据用 follower reads，避免跨区访问 leaseholder
SELECT * FROM orders AS OF SYSTEM TIME INTERVAL '10s';
各版本语法与可用表类型有差异（例如 GLOBAL 表的引入时间、 REGIONAL BY ROW 对主键的要求）。请以所用版本的官方文档为准，不要凭记忆写 DDL。

③延迟从哪里来

副本放得越远，写入越慢——这是物理规律，不是配置问题
优化顺序： ① 确认副本位置是否符合你真正需要的生存目标（很多时候副本放得比需要更远，白白付延迟）； ② 让计算靠近数据（应用部署到主区域，或用 REGIONAL BY ROW）； ③ 读多写少的场景用 GLOBAL 表 + Follower Reads； ④ 批量写入合并事务，摊掉每事务的固定 RTT。

④上线前要确认的事

  1. 时钟偏差监控：节点时钟漂移会直接影响 HLC 的正确性边界，必须有告警。
  2. 副本放置可视化：能随时回答「这张表的副本现在在哪几个区域」。
  3. 故障演练：真的拔掉一个 zone / region，验证生存目标是否达成、恢复耗时多久。
  4. 应用层重试：跨区部署下冲突概率更高，重试逻辑必须完整（见「数据分布」篇）。
  5. 跨区流量成本：云厂商的跨地域流量是收费的，副本同步会持续产生费用。
Q：能不能既跨地域容灾又低延迟写入？
A：不能同时满足。要么接受跨城写入延迟（同步复制 + 强一致）， 要么用异步复制换低延迟（主区写、备区异步追，故障时可能丢少量数据）。 这是一致性、可用性、延迟三者取二的经典权衡，没有银弹。
Q：多区域下自增主键还能用吗？
A：能用但不推荐——它同时带来写热点（尾部 Range）和跨区协调开销。 建议用随机/哈希前缀的 UUID 类主键，把写入打散。
