RocketMQ 深度解析

RocketMQ 是阿里开源、现属 Apache 的分布式消息中间件，为电商级交易链路而生：主打事务消息、海量堆积、低延迟高可靠。它的架构刻意弱化 ZooKeeper，用自研 NameServer 做轻量路由。

1架构：NameServer + Broker + 生产/消费

没有 ZK 依赖——NameServer 是无状态路由表，Broker 主从复制保证可靠。

Producer/Consumer 先问 NameServer 取路由，再直连 Broker
  • NameServer：轻量、无状态、节点间不通信，仅维护 Topic→Broker 路由；Broker 心跳注册。
  • Broker：核心存储与投递节点，分 Master/Slave，支持同步/异步复制。
  • Topic / MessageQueue：Topic 逻辑概念，物理上拆成多个 MessageQueue（类似 Kafka 分区），是并行与顺序的单位。

2存储：CommitLog + ConsumeQueue

RocketMQ 所有消息顺序写进一个统一的 CommitLog（顺序 IO，性能关键），再为每个 Topic 的 MessageQueue 建轻量的 ConsumeQueue 索引（offset + 物理偏移 + tag 哈希），消费时先查索引再随机读 CommitLog。这种「单日志 + 多索引」避免 Kafka 那种分区级多文件。

为何能海量堆积顺序写 CommitLog + 索引轻量，使 RocketMQ 在磁盘上堆积亿级消息仍能稳定消费，且读写互不严重干扰。

3招牌能力：事务消息

电商「下单一半成功」的难题，RocketMQ 用两阶段 + 回查解决：

Half 消息对消费者不可见，事务提交后才转为可投递
  • Half 消息：先发一条对消费者不可见的「预备消息」，保证 broker 可用。
  • Commit / Rollback：本地事务成功就提交，失败就回滚，消息才对消费者可见。
  • 事务回查：若 broker 迟迟没收到二阶段指令（如 Producer 宕机），会回查本地事务状态，最终决定提交或回滚——这是可靠性的兜底。
和本地事务表 / Kafka 事务对比RocketMQ 事务消息把「DB 事务 + 发消息」的原子性交给 broker 协调，比自研本地消息表省心，是交易链路的常用方案。

4运维要点

🔁 重试与死信

消费失败自动重试（默认 16 次），最终进 %DLQ% 死信队列，需人工兜底。

⏱️ 延迟消息

支持分级延迟（18 个固定等级），精确到任意时间的延迟需自己叠加。

🔢 顺序消息

同一 MessageQueue 内保证顺序，下单等强顺序场景按业务 key 路由到同一队列。

🛡️ 高可用

Broker 主从 + Dledger（Raft）实现自动选主，避免单点。

NameServer 不是注册中心兜底NameServer 节点互不通信，任一时点路由可能短暂不一致；部署要多个节点且不要和 Broker 混部过度。

# 3) 按消息 ID / key 查一条消息（排查丢了还是没发）

# 4) 生产端关键设置（同步发送 + 超时 + 重试）
DefaultMQProducer p = new DefaultMQProducer('producer_group');
p.setNamesrvAddr('127.0.0.1:9876');
p.setSendMsgTimeout(5000);      // 跨机房适当加大
p.setRetryTimesWhenSendFailed(2);
p.start();

消费吞吐怎么估：单条处理耗时 t（秒）× 并发线程数 n → 理论吞吐约 n / t 条/秒。例如每条处理 20 ms、64 线程 → 约 3200 条/秒。所以当 Diff 持续增长时，先算这个数，再决定是加线程、加消费者实例，还是优化单条处理。

第三层 · RocketMQ 的六个高频坑

  • 消费线程数没调：默认 20/64 对慢消费（每条几十毫秒）完全不够；先按上面的公式算需要多少并发。
  • 消费端抛异常就无限重试：失败消息进 %RETRY% 反复重试，遇到「永远失败」的消息会堵住后面；要设最大重试次数并转死信队列。
  • 把消息体当数据库用：4 MB 上限 + 大消息拖慢刷盘与网络；大文件走对象存储，消息里只放引用。
  • Tag 过滤写错：Tag 过滤在 Broker 端做，订阅关系要与发送一致；用 SQL92 属性过滤要先在 Broker 开启。
  • 顺序消息没用对：顺序性只在同一个 MessageQueue 内保证；要保证全局顺序就得只用一个队列（代价是吞吐）。
  • 以为同步刷盘更安全就全开：SYNC_FLUSH 明显降低吞吐；除非能接受丢失，否则用同步复制（主从）而不是同步刷盘。

排查顺序：consumerProgress 看 Diff → 算吞吐公式 → 看是线程不够还是单条太慢 → 再看重试队列有没有堵。

第四层 · 它和 Kafka 的分工

RocketMQ 和 Kafka 该怎么选？

Kafka 在高吞吐日志流与生态上更强；RocketMQ 在业务消息语义上更贴心：延迟消息、事务消息、消息重试与死信、Tag 过滤都是内置能力，业务系统少写很多代码。

事务消息是怎么做到的？

两阶段：先发半消息（对消费者不可见），本地事务执行完再提交或回滚；若长时间不确认，Broker 会回查生产者的本地事务状态。所以生产者必须实现回查接口。

延迟消息为什么是固定级别而不是任意时间？

因为 Broker 为每个延迟级别维护独立队列并按时间扫描，固定级别让实现简单可控；需要任意时长就得自己在消费侧做定时或外部调度。
