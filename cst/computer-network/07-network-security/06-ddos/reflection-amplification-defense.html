反射放大 DDoS：为什么受害者没有请求却收到大量响应

从伪造源地址、开放 UDP 服务到上游清洗，理解防护为何必须跨层协作。

反射和放大是两步

某些无连接或弱认证的 UDP 服务会根据请求返回响应。攻击者若能在网络中发送源 IP 被伪造成受害者地址的请求，服务会把响应发给受害者，这叫反射；若响应字节明显多于请求字节，攻击流量还会被放大。DNS、NTP 等协议的错误开放配置都可能被滥用，问题不在协议名字本身，而在允许伪造来源、开放服务与响应比例的组合。

攻击者的目标可能是打满受害者接入带宽、耗尽边界设备状态或拖垮应用。受害者看到大量来自正常第三方服务器的 UDP 响应，不能因为源地址属于合法机构就认定这些流量是正常业务。需要看目的端口、请求上下文和流量突然增长的时间线。

为什么本地防火墙不够

若受害者接入链路只有 1 Gbps，而反射流量达到 10 Gbps，即使受害者机房防火墙最终丢弃所有包，入站链路在到达防火墙前已被占满。流量型 DDoS 需要运营商、上游清洗或 Anycast/CDN 等更早位置共同处理。应用层 WAF 可以筛 HTTP 请求，却不能把早已打满链路的 UDP 流量变没。

上游清洗要能区分合法 DNS/NTP 等业务与异常反射包，误封也会影响正常用户。配置防护前先了解哪些端口是真实业务入口，记录正常峰值与地域分布。

逐步推演

攻击者把请求源地址伪装成受害者。

开放服务响应

第三方 UDP 服务向受害者回包。

放大流量

总响应可能打满入站链路。

上游防护

源地址过滤、限制反射面、清洗与容量分散。

源地址伪造的根因

若网络边界允许客户发送源 IP 不属于其分配前缀的包，攻击者才更容易把受害者 IP 写成源地址。接入运营商和企业出口实行源地址校验或出站过滤，可减少伪造流量离开源网络。这是从攻击源侧解决问题，受害者自己无法替全互联网部署。对开放 UDP 服务，限制递归查询来源、限制响应、更新软件和监控异常放大流量，可减少成为反射器。

真正的互联网防护需要多方协作：源网络阻止伪造、服务提供者避免开放反射面、受害者与上游在容量充足的位置清洗。只在网站服务器上加一条 iptables 规则，覆盖不了所有环节。

一次故障识别

电商入口突然不可用，边界接口入站打满，抓包样本显示大量从多个 DNS 服务器来的响应，内部没有对应请求。首先确认这些包是否属于反射流量，并记录目标 IP、入站速率和正常业务受影响范围。若只把每个 DNS 源地址逐个封禁，攻击者可换其他反射器，而且封禁列表会迅速膨胀。更应让上游按流量特征、目的与合法服务情况过滤或牵引清洗。

分析时不要把 DNS 正常高峰、CDN 健康探测与反射攻击混成一类。流量突然变化、请求与响应不匹配、地域分布异常、目的端口与业务不符都是线索，需要结合全量或采样流量记录。

与 SYN Flood、HTTP 洪泛的区别

反射放大多在网络或传输层制造大流量；SYN Flood 针对 TCP 建连状态或队列；HTTP 洪泛可能每个请求都像正常用户，却耗尽应用或数据库资源。三者入口不同、保护点也不同。SYN Cookie 或 backlog 调整不能解决公网链路被 UDP 反射流量占满；CDN 缓存也不能代替内网状态防火墙容量治理。先测是 bit/s、包/秒、连接/秒还是应用请求/秒触顶。

攻击还可能同时使用多种流量，因此防护要有分层指标和升级路径，不能只配置一个“DDoS 开关”。

容量与预案

正常流量基线应覆盖日周期、营销活动和地域差异，设置带宽、包率、连接新建、HTTP 错误等告警。与上游预先约定触发清洗的联系人、牵引方法、合法业务白名单及回切条件。重要服务可用 Anycast、冗余入口和容量分散降低单点压力，但多点也需要一致的证书、配置和健康检查。

防护策略要演练误报：把合法促销峰值误判为攻击会直接伤害用户。上线后对照真实业务成功率，而不仅是清洗设备报告“丢弃了多少包”。

复盘与长期修复

保留攻击期间的流量样本、设备计数、上游处理时间、业务错误率和恢复时间。若自家 DNS 或其他 UDP 服务也被外界当反射器使用，应修正开放范围与响应策略，避免只关注自身受害。源地址过滤、服务安全配置和上游合作是长期措施。

练习：一台 1 Gbps 接入的服务器在本地防火墙丢掉全部 5 Gbps 入站攻击流量，用户是否一定恢复？答案通常是否定的，因为瓶颈在防火墙之前的链路。

自查与防护

# 自查：我的服务器会不会被利用？
# Memcached（绝不能监听公网 UDP）
ss -lntup | grep 11211
nmap -sU -p 11211 --script memcached-info <ip>

# NTP monlist（老版本才有）
ntpdc -n -c monlist <ip>

# DNS 开放递归
dig @<ip> example.com               # 能查说明是开放递归
dig @<ip> example.com ANY           # 看响应是否远大于查询

# 防护：关闭/限制
# memcached 只监听内网并禁用 UDP
memcached -l 127.0.0.1 -U 0
# NTP 升级到 4.2.7p26+（monlist 已移除），并加 restrict default noquery
# DNS 只对内网开递归
# named.conf: recursion no;  或 allow-recursion { 内网段; };

# 应急响应：限速（示例，按协议限速）
iptables -A INPUT -p udp --dport 11211 -j DROP
iptables -A INPUT -p udp --dport 53 -m hashlimit \
  --hashlimit-name dns --hashlimit-above 100/sec --hashlimit-mode srcip -j DROP

防护体系

层次措施谁来做
源头BCP38 / BCP84 源地址验证（ISP 在接入层过滤伪造源 IP）运营商（根本解法，但全球推进慢）
反射源关闭/加固开放服务（memcached、NTP、DNS 递归）每个服务器管理员
受害者侧上游清洗、Anycast 分散、CDN 吸收、云厂商 DDoS 防护云厂商 / IDC
协议层禁用无认证的 UDP 放大服务、限制响应大小（DNS Response Rate Limiting）服务运营方
  • BCP38 是唯一的根本解：如果每个 ISP 都在接入时校验源 IP 属于该客户，伪造就不可能发生。但因为是“为别人做贡献”，全球部署率仍不高（约 70%）。
  • DNS RRL（Response Rate Limiting）：对相同类型的响应限速（如每客户端每秒 5 个 NXDOMAIN），能把 DNS 的放大能力压到接近 1:1，是 DNS 服务器的必备配置。
  • 不要以为自己不会被利用：一台默认配置暴露在公网的 memcached / Redis / NTP / DNS 递归服务器，都会成为攻击放大器。这既是安全问题也是道德与合规问题（你的机器在攻击别人）。
  • 云上防护：AWS Shield、Cloudflare、阿里云 DDoS 高防等通过 Anycast + 大带宽清洗吸收流量。关键是把源站 IP 隐藏起来（只暴露防护节点），否则攻击者绕过防护直打源站。
  • 应急响应顺序：① 确认攻击类型（抓包看协议/端口/源分布）；② 联系上游做黑洞或清洗；③ 在边界限速/丢弃该协议；④ 长期：上 CDN/高防 + 隐藏源站 + 自查开放服务。
  • 应用层 DDoS 更易被忽视：不需要大流量，只需精准打慢接口（如搜索、导出），几千 QPS 就能打垮。防御靠限流 + 降级 + 验证码 + 弹性扩容。
为什么我的服务器会被用来攻击别人？

因为服务监听在公网且协议本身“小请求大响应”（如 memcached 的 stats、NTP 的 monlist、DNS 的开放递归）。攻击者伪造源 IP 后，你的服务器就在不知情地放大流量攻击受害者。修复：只监听内网、禁用 UDP、限制递归。

加带宽能防 DDoS 吗？

对拥塞型攻击（打满带宽）只能缓解，因为攻击流量可以远大于你的带宽（几百 Gbps 甚至 Tbps）。真正的防线是上游清洗 + Anycast 分散 + CDN 吸收，让攻击流量在到达你之前就被稀释和过滤。

自检

受害者本地防火墙能丢弃攻击包，为什么业务仍可能不可用？

入站链路可能在到达本地防火墙前就被打满，需要上游或更早的网络位置处理。
