Redis String 数据结构演进史

从 C 字符串到 SDS 的性能优化之路

Redis 2.0

SDS 初代版本

2010 年，Redis 首次引入 SDS 作为字符串实现。 此前直接使用 C 字符串（char*），存在缓冲区溢出和 O(n) 长度获取问题。

// sdshdr (Redis 2.0 - 2.6)
int len 4 bytes
int free 4 bytes
char buf[] 柔性数组
头部大小: 8 bytes
O(1) 长度获取 二进制安全 空间预分配 惰性释放
Redis 2.2

APPEND 优化

引入高效的字符串追加（APPEND）操作。通过记录已用长度 len， 避免每次追加都重新分配内存。

// 追加操作流程
1. 检查 free >= 追加长度?
2. 是 → 直接追加，更新 len
3. 否 → 重新分配，预分配策略
APPEND 时间复杂度降低 减少内存重分配
Redis 2.4

预分配策略优化

优化内存预分配算法。当字符串小于 1MB 时，倍增预分配； 大于 1MB 时，每次多分配 1MB。显著减少内存碎片。

// 预分配算法 (Redis 2.4+)
if (newLen < 1MB) {
    alloc = newLen * 2; // 倍增
} else {
    alloc = newLen + 1MB; // 固定增量
}
内存利用率提升 减少碎片
Redis 3.2 ⭐ 重大重构

SDS 类型分桶 + EMBSTR

3.2 是转折点！引入 5 种 SDS 类型，头部从 8 字节压缩到 1-3 字节。 短字符串使用 embstr 编码，string 和 redisObject 连续内存分配。

// SDS_TYPE_5 (短字符串)
flags 1 byte
buf[] 内嵌
头部: 1 byte
// SDS_TYPE_8 (长字符串)
uint8_t flags 1 byte
uint64_t len 8 bytes
uint64_t alloc 8 bytes
char buf[] 柔性数组
头部: 17 bytes
SDS_TYPE_5/8/16/32/64 embstr 编码 44字节阈值 连续内存分配

演进总结

Redis String 从最初的简单封装，到今天的高性能动态字符串， 经历了多次精妙的优化：

空间换时间（预分配）→ 类型分桶（SDS_TYPE_X）→ 内存对齐（embstr）

每一个版本都在追求更低的内存开销和更高的访问效率。 这也是 Redis 能够成为内存数据库标杆的核心秘密之一。

String 三种编码与切换阈值

编码底层结构触发条件内存/性能特点
int直接把整数存在指针位（不用分配 SDS）值为整数且能用 long 表示最省：零额外分配
embstr一次分配：redisObject + SDS 连续内存字符串长度 ≤ 44 字节一次分配、一次释放，缓存友好
raw两次分配：redisObject 与 SDS 分开字符串长度 > 44 字节分配两次，可独立扩容

为什么是 44 字节：SDS 的 sdshdr8 头部为 3 字节（len、alloc、flags）+ 结尾 \0 共 4 字节；jemalloc 的 64 字节内存块减去 redisObject（16 字节）与 sdshdr8 开销，剩余可存 44 字节内容。超过 44 就放不进一个 64 字节块，只好拆成两次分配（raw）。

String 编码验证

# 查看编码类型（最直接的验证方式）
SET k1 12345
OBJECT ENCODING k1          # "int"
SET k2 "hello"
OBJECT ENCODING k2          # "embstr"
SET k3 "$(python3 -c 'print("x"*45)')"
OBJECT ENCODING k3          # "raw"（>44 字节）

# 看内存占用与序列化长度
MEMORY USAGE k1
STRLEN k2
DEBUG OBJECT k1             # 看 refcount、serializedlength 等（生产慎用 DEBUG）

# 关键：编码只升不降（int → raw 后不会自动变回 int）
SET k1 12345
APPEND k1 "abc"             # 变成 raw
OBJECT ENCODING k1          # "raw"
SET k1 12345                # 重新 SET 才能回到 int

String 的工程用法与坑

  • 编码只升不降：int → embstr/raw 之后，即使把值改回小整数也不会自动降级，必须重新 SET。所以在长期运行实例上看到 raw 编码不一定是“值很大”。
  • 共享整数池：Redis 启动时预建 0 – 9999 的整数对象（OBJ_SHARED_INTEGERS = 10000），这些值不额外占内存。所以大量小整数（计数器、状态位）非常省。
  • INCR 的最大值：只能对能用 long long 表示的整数操作（±2^63−1），超出报 ERR increment or overflow。计数器溢出是经典故障。
  • 大 value 的危害：单 key 几百 KB 甚至 MB 会让 ① 网络传输慢；② 删除时阻塞（DEL 大对象耗时明显，可用 UNLINK 异步删）；③ 主从同步/持久化放大。建议单 value 控制在 10 KB 以内。
  • 批处理优先：MSET/MGET 或 pipeline 能把 N 次往返压成 1 次。实测跨机房 RTT 0.5 ms 时，100 次 GET 从 50 ms 降到约 1 ms。
  • 排障：OBJECT ENCODING 确认编码 → MEMORY USAGE 看占用 → --bigkeys 或者 redis-cli --memkeys 扫大 key。
为什么 embstr 改一下就变成 raw？

因为 embstr 是只读优化的连续内存，任何修改（APPEND、SETRANGE）都可能要扩容，Redis 直接把它转成 raw 再操作。这是“优化只适用于不变的对象”的典型设计。

String 能存多大？

单个 value 最大 512 MB（受 proto-max-bulk-len 限制）。但工程上远不该到这个量级——大 value 会带来删除阻塞、网络毛刺、持久化放大等一系列问题。
