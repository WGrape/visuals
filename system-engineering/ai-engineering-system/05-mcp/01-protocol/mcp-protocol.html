MCP 协议

Model Context Protocol 详解

Model Context Protocol · 开放标准

MCP 是连接「大模型」与「外部世界（工具、数据、提示）」的开放标准协议。它把过去每家自己写一套 tool-calling 集成，统一成「即插即用」的接口——就像 USB 让所有外设共用一个口。

一、为什么需要 MCP

之前（各自为政）之后（MCP 标准化）
每个工具写一套私有适配代码一个 MCP Server 可被任意支持 MCP 的客户端复用
换模型/换应用要重写集成Server 与 Client 解耦，可独立替换
上下文/权限各自实现协议统一定义资源、工具、采样等原语
形象化理解：MCP 像「AI 的 USB-C 口」。键盘、U 盘、显示器只要做 USB 接口，就能插到任何带 USB 口的电脑上——不用为每个电脑各做一种键盘。

二、架构：Host / Client / Server

  • Host：运行 LLM 的应用（如 IDE 插件、桌面客户端），内部起多个 Client 各自连一个 Server。
  • MCP Server：把某个能力（查数据库、读文件、调 API）暴露成标准接口的独立进程。
  • 传输层：进程内用 stdio（本地）；远程用 Streamable HTTP（取代旧 SSE）。

三、核心原语（Server 能暴露什么）

🧰

Tools

可调用函数，LLM 主动调用（带参数），如 query_db。

📄

Resources

可读取的上下文数据，如文件、日志，由应用决定何时注入。

💬

Prompts

预定义的提示模板，用户主动触发。

🎲

Sampling

Server 反向请求 LLM 生成内容（Server 调模型）。

🌱

Roots

Host 告知 Server 可访问的「根目录/作用域」边界。

🔔

Notifications

单向异步通知（无需回复），如文件变化。

四、生命周期与消息

  1. 初始化握手：Client 发 initialize（带协议版本、能力），Server 回 initialize 结果，再互发 initialized 通知。
  2. 能力发现：Client 用 tools/list、resources/list 拉取 Server 提供的能力。
  3. 调用：LLM 决定调用 tools/call，Server 返回结果，Client 回填给模型。
  4. 关闭：任一方发 shutdown 后断开。
// 一次典型调用（JSON-RPC 2.0）
{"jsonrpc":"2.0","id":1,"method":"tools/call",
 "params":{"name":"query_db","arguments":{"sql":"SELECT 1"}}}
// 返回
{"jsonrpc":"2.0","id":1,"result":{"content":[{"type":"text","text":"..."}]}}
⚠️ 安全：MCP Server 拥有真实执行权。务必做最小权限、用户确认、输入校验、沙箱隔离。一个「能执行任意 shell」的 Server 等于把服务器钥匙交出去。

为什么需要一层协议：三种集成方式对比

在 MCP 之前，让模型用上外部系统只有两条路：为每个系统手写适配，或者为每个模型写一份工具声明。两条路的成本都是乘法级的。MCP 想做的是把乘法变成加法：能力提供方只实现一次，所有支持协议的客户端都能用。

一次完整会话：从握手到调用

MCP 建立在 JSON-RPC 之上，会话有明确的生命周期：先协商能力，再互相发现，最后才是调用。跳过前两步直接调用是不允许的。

MCP 会话时序：先握手协商，再列能力，最后调用

握手阶段为什么不能省？因为它要做版本协商与能力协商：双方确认都能说哪个协议版本，以及各自支持哪些可选能力（比如是否支持资源订阅、是否支持采样）。这样老客户端遇到新服务端也能安全地降级工作。

传输层：stdio 与 Streamable HTTP 怎么选

协议本身不绑定传输方式，但两种主流传输的适用边界非常清晰：本地能力走 stdio，远程能力走 HTTP。

stdio：本地进程

客户端把服务端作为子进程启动，通过标准输入输出收发 JSON-RPC 消息。优点是零网络配置、天然隔离在本机、启动即用；缺点是只能本机、难以多客户端共享、进程生命周期绑定在客户端上。适合本地文件、命令行工具、本机数据库。

Streamable HTTP：远程服务

服务端作为独立的 HTTP 服务部署，客户端用 POST 发消息，服务端可选择用流式响应回传。优点是可远程部署、可横向扩展、多客户端共享；缺点是要自己做鉴权、会话保持、断线重连与可观测。适合企业内部系统与多用户服务。

stdio 优点零配置、无端口、天然本机隔离
stdio 局限不能远程、不能共享、随客户端生死
HTTP 优点可远程、可扩展、多客户端复用
HTTP 代价要鉴权、要会话、要可观测

通知不需要回包，用于事件与进度上报

安全边界：工具比资源危险得多

把外部能力接进模型之后，最大的风险不是「答错」，而是被诱导去做不该做的动作。所以安全设计的核心原则是：只读能力放宽，写能力收紧。

最小权限只授予完成任务必需的目录与接口范围，用 Roots 限定文件边界
人类在环写操作、删除、对外发送这类动作必须经用户明确确认后再执行
不可信输入网页、文档、邮件里的文字可能藏着指令，工具返回值要当数据处理而非命令
审计留痕记录每次调用的工具名、参数与结果，出事后能回放
超时与限流防止一个失控的调用循环把外部系统打挂
敏感信息脱敏工具返回的密钥、证件号进入上下文前先处理
提示注入为什么在 MCP 场景下更危险？

因为模型不只是「读到恶意文本」，它还有手（工具）。一段网页里的隐藏指令如果让模型调用了发邮件或删文件的工具，后果就从「答错」升级为「真的做了」。所以除了在提示层防御，更关键的是在工具层设闸门：写操作必须确认，权限必须收窄。

Resources 和 Tools 应该怎么划分？

凡是只读、可反复读取、适合直接塞进上下文的，做成 Resource；凡是有副作用、需要参数触发动作、执行代价高的，做成 Tool。划分清楚后，权限模型也能自然分层：Resource 默认可读，Tool 逐个审批。

Sampling 是什么，为什么它很特殊？

Sampling 是反向的：不是模型调用服务端，而是服务端请求客户端让模型再生成一段内容。它让服务端能在自己内部嵌套使用模型能力。因为方向反转，权限上要格外谨慎，必须让用户知道并同意，否则等于把模型的调用权交给了外部服务。

为什么工具描述要写得非常克制？

工具描述直接进入提示词，会占用上下文并影响模型选择。描述写得又长又宽泛，模型容易误调用；写清楚「什么时候用、什么时候不要用」，比堆功能介绍有效得多。

一个最小 Server 长什么样

下面用伪代码展示服务端要做的三件事：声明能力、提供工具列表、执行调用。真实实现只需换成对应语言的 SDK 即可，结构完全一致。

server = MCPServer(name="repo-helper") # 1) 声明一个工具：名字、说明、参数 Schema @server.tool( name="search_code", description="在仓库中按关键词搜索代码；只在需要定位实现时用", schema={"keyword": str, "max_results": int}, ) def search_code(keyword, max_results=20): hits = repo.grep(keyword, limit=max_results) return {"results": hits} # 结构化返回，便于模型引用 # 2) 声明一个只读资源：用 URI 寻址 @server.resource("repo://README.md") def readme(): return {"text": repo.read("README.md")} # 3) 启动时声明自己支持的能力 server.capabilities = {"tools": True, "resources": True} server.serve(transport="stdio") # 本地用 stdio，远程换 http # 约定： # - 出错返回结构化错误，而不是抛异常崩溃 # - 长任务上报 progress，并响应 cancel # - 描述里写清适用边界，避免误调用

把这段与前面的时序图对着看：服务端实现的是「被调用的一侧」，而握手、发现、调用这套流程由协议保证，服务端不需要关心客户端是谁。
