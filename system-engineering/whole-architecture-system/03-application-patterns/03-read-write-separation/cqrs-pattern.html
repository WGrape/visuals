什么时候适用？

判断信号：写入规则与读取视图的模型需求差异明显，值得分别设计。

  • 写订单重规则、查订单列表重聚合
  • 读流量远高于写流量且要独立扩展
  • 需要多个专用查询投影

和相近方案怎么区分？

相近方案选择边界
数据库读写分离读写分离可只是主从副本路由；CQRS 把命令模型与查询模型的职责分开。
事件溯源事件溯源用事件记录事实历史；CQRS 不要求以事件作为权威存储。

最小伪代码

function createOrder(cmd):
  transaction:
    order = Order.create(cmd.items)
    writeStore.save(order)
    outbox.insert(OrderCreated(order.id))
// 提交后发布器投递 outbox，消费者幂等更新读模型
on OrderCreated(event):
  readStore.upsert(project(event.orderId))

边界：异步投影有延迟；需要定义读己之写体验、重建投影和重复事件处理。简单 CRUD 未必需要 CQRS。

CQRS 读写分家 Command Query Responsibility Segregation

写请求与读请求走独立路径；读侧可由写侧异步更新，也可共用存储

传统 CRUD 用同一模型既读又写，复杂查询会把写模型撑得很难看。CQRS 把『改数据(Command)』和『查数据(Query)』拆开：写侧聚焦领域规则，读侧直接投喂前端要的扁平 DTO（可由写侧事件异步同步）。

何时值得用

  • 读写负载差异巨大（读多写少）。
  • 查询模型远比写入模型复杂（多表 join、聚合）。
  • 需要与事件溯源配合。

代价

  • 最终一致性：读模型滞后于写。
  • 两套模型、两套存储，复杂度翻倍。
  • 小系统用了是过度设计。

面试高频问答

Q：CQRS 一定要配合事件总线吗？
A：不一定。简单场景可让写侧直接更新读库（同步）；但 CQRS 真正的威力在配合事件/消息做异步投影，实现读写物理隔离。
Q：CQRS 和读写分离(主从)一样吗？
A：不一样。读写分离是『同一数据的副本分担读压力』；CQRS 是『读模型和写模型结构都不同』，读侧可能是为查询量身定制的视图。
