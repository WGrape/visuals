先建立直觉：工厂的流水线排班表

工厂有几十道工序，有的必须等前一道完成，有的可以并行，还有的要每天早上 8 点开始。你需要一张排班表说清楚：谁先谁后、什么时间、失败了怎么办。

Airflow 就是数据世界的排班表。它用 DAG（有向无环图）描述任务依赖：箭头表示依赖，无环保证不会死循环。

核心概念

概念含义
DAG有向无环图，描述一整条流水线（如「每日用户报表」）
TaskDAG 中的一个节点，一个具体的操作
OperatorTask 的类型（BashOperator、PythonOperator、SparkSubmitOperator…）
DAG RunDAG 的一次具体执行实例（如 2026-10-20 那一次）
Task Instance某个 Task 在某个 DAG Run 中的一次执行
execution_date本次运行对应的数据时间（不是实际启动时间）
最反直觉的概念：execution_date。它表示这批数据属于哪个时间窗口，而不是「任务什么时候跑的」。比如每天 2 点跑「昨天的数据」，那么 10 月 21 日 2 点启动时，execution_date 是 10 月 20 日。理解这一点才能正确写分区和补数逻辑。

一个典型 DAG

from airflow import DAG
from airflow.operators.bash import BashOperator
from airflow.operators.python import PythonOperator
from datetime import datetime, timedelta

default_args = {
    'owner': 'data-team',
    'retries': 2,                      # 失败自动重试 2 次
    'retry_delay': timedelta(minutes=5),
    'depends_on_past': False,          # 是否依赖上一次运行成功
}

with DAG(
    dag_id='daily_user_report',
    default_args=default_args,
    schedule_interval='0 2 * * *',     # 每天凌晨 2 点
    start_date=datetime(2026, 1, 1),
    catchup=False,                     # 不自动补跑历史
    max_active_runs=1,                 # 同时只跑一个实例
    tags=['report'],
) as dag:

    extract = BashOperator(
        task_id='extract_from_mysql',
        bash_command='python /opt/jobs/extract.py {{ ds }}',   # ds = execution_date
    )

    transform = PythonOperator(
        task_id='transform',
        python_callable=do_transform,
    )

    load = BashOperator(
        task_id='load_to_hive',
        bash_command='hive -f /opt/jobs/load.sql',
    )

    check = PythonOperator(
        task_id='quality_check',
        python_callable=assert_row_count,
    )

    extract >> transform >> load >> check    # 定义依赖

调度流程

关键实践

① catchup 要显式设置。默认 catchup=True 会从 start_date 起把所有历史周期一次性补跑，可能瞬间生成成千上万个任务把集群打满。生产 DAG 通常设 catchup=False，需要补数时手动触发指定日期。
② 任务要幂等。同一天的数据跑两次，结果应该一致。这依赖分区覆盖写（INSERT OVERWRITE 到当天分区）而非追加写。这样重试才安全。
③ 用 Jinja 模板传日期，不要自己算。用 {{ ds }}（execution_date，格式 YYYY-MM-DD）、{{ execution_date }} 等内置变量。Airflow 会自动按 DAG Run 填充，回填历史时会自动用对应的历史日期——这是正确补数的前提。
④ 别在 DAG 文件顶层写重逻辑。Airflow 会频繁解析所有 DAG 文件（默认每分钟），顶层代码每次都会执行。重逻辑（如查数据库、读大文件）会严重拖慢调度器。只把定义放在顶层，把实际逻辑放进 Operator。
⑤ 加质量校验任务。在链路末尾加一个 quality_check 任务做行数/空值校验，失败则阻断下游。这比事后发现报表错了要便宜得多。

🎯 面试问答

Q：execution_date 为什么不是「任务运行的时间」？
A：因为 Airflow 的设计理念是「按数据时间调度」而非「按启动时间调度」。execution_date 表示这批数据属于哪个时间窗口。例如每天 2 点处理昨天的数据，10 月 21 日 2 点启动的那次运行，其 execution_date 是 10 月 20 日。这样设计的好处是补数（backfill）很自然：补跑 10 月 1 日的数据时，execution_date 就是 10 月 1 日，SQL 里的分区字段自动正确，无需改代码。

Q：为什么我的 DAG 一上线就跑了几百次？
A：因为 catchup 默认为 True。Airflow 会从 start_date 起，把所有未被执行的调度周期一次性补跑。如果 start_date 设的是半年前且按天调度，就会瞬间生成上百个 DAG Run。解决：生产 DAG 显式设 catchup=False；确实需要补历史数据时，用命令行指定日期范围手动 backfill，而不是靠 catchup。

Q：任务失败了会自动重试吗？怎么设置？
A：会，通过 default_args 里的 retries（重试次数）和 retry_delay（重试间隔）设置。但前提是任务必须幂等——重试时应该覆盖写当天分区，而不是追加，否则会产生重复数据。另外可设置 depends_on_past=True 让任务依赖自己上一次运行成功，适合严格按天串行、不能跳天的场景。

Q：Airflow 和 DolphinScheduler 怎么选？
A：Airflow：用 Python 定义 DAG，代码化管理、易做版本控制和 CI，生态最广（Operator 覆盖几乎所有系统），社区最大，是业界事实标准；适合有工程能力的团队。DolphinScheduler：可视化拖拽配置，上手快、对非工程背景的成员友好，国产且中文支持好；适合偏好 UI 操作、或团队工程化程度不高的场景。数据团队规模较大、依赖复杂时，Airflow 的可维护性优势更明显。

核心概念与 DAG 写法

概念含义说明
DAG有向无环图，一个工作流定义在 dags/ 下的 Python 文件
TaskDAG 里的一个节点由 Operator 实例化
Operator任务类型模板BashOperator、PythonOperator、MySqlOperator…
TaskFlow@task 装饰器（2.0+）推荐写法，自动处理 XCom
XCom任务间传递小数据只适合传小数据（默认限制 48KB），大数据走对象存储
Executor怎么执行任务LocalExecutor / CeleryExecutor / KubernetesExecutor
Pool并发槽位限制控制同时跑的任务数，防止打爆下游

DAG 示例

from airflow.decorators import dag, task
from airflow.operators.bash import BashOperator
from airflow.utils.dates import days_ago
from datetime import timedelta

@dag(
    dag_id="etl_orders",
    schedule="0 2 * * *",              # 或 @daily / timedelta(hours=1)
    start_date=days_ago(1),
    catchup=False,                     # <b>关掉回填，否则会补跑历史所有周期</b>
    max_active_runs=1,                 # 同时只跑一个周期
    default_args={
        "owner": "data",
        "retries": 2,
        "retry_delay": timedelta(minutes=5),
        "execution_timeout": timedelta(hours=2),   # 超时保护，必配
        "email_on_failure": False,
    },
    tags=["etl"],
)
def etl_orders():

    @task
    def extract(ds=None):
        # ds 是逻辑日期（execution_date），不是「现在」
        return f"/data/orders/{ds}.parquet"

    @task
    def transform(path: str) -> int:
        # ...处理...
        return 12345

    @task
    def load(n: int):
        print(f"loaded {n} rows")

    # 依赖：extract -> transform -> load
    load(transform(extract()))

    # 混用传统 Operator
    bash = BashOperator(task_id="notify", bash_command="echo done")

etl_orders()

最容易踩的三个坑：① catchup=True（默认）会让新上线的 DAG 从 start_date 开始补跑所有历史周期，可能瞬间产生几千个任务——新 DAG 一定要 catchup=False；② start_date 必须是过去的固定时间，用 datetime.now() 会导致调度永不触发；③ 不要用 datetime.now() 取业务时间，要用 ds（逻辑日期），否则重跑时数据会错。

调度语义、重试与排障

参数作用建议值
schedule调度周期（cron 或 @daily）cron 表达式
catchup是否补跑历史周期False（新 DAG）
max_active_runs同时运行的 DAG 实例数1（防止并发写同一分区）
retries / retry_delay失败重试2 次 / 5 分钟
execution_timeout单次运行超时必配，否则任务可能永久挂起
depends_on_past依赖上一周期成功慎用（会导致卡住）
pool / pool_slots限制并发按下游承载力设

Airflow 和 DolphinScheduler / XXL-Job 怎么选？

Airflow：Python 定义 DAG，生态最全（几百个 Provider），适合数据工程；缺点是 UI 偏技术、权限模型弱、Scheduler 性能在 DAG 极多时需要调优。DolphinScheduler：可视化拖拽、中文友好、自带多租户与资源文件管理，国内数据团队常用。XXL-Job：轻量、Java 生态、适合业务定时任务而非数据管道。选型看团队语言和数据量：Python + 复杂依赖链 → Airflow；需要可视化与中文支持 → DolphinScheduler；只是定时跑个 Java 方法 → XXL-Job。

为什么强调 ds 而不是 now()？

因为调度系统的核心是可重跑。Airflow 的 ds（逻辑日期）表示「这次运行处理的是哪一天的数据」，而 now() 是「实际运行时刻」。如果用 now() 去拼分区路径或查询条件，那么重跑 10 月 1 日的任务时，它会去读写今天的分区——数据就错了。这是数据调度里最经典的错误，正确做法是所有时间相关的逻辑都用 ds / data_interval_start / data_interval_end，保证「同样的输入 → 同样的输出」。

任务失败重试会不会造成数据重复？

会，所以每个任务都要幂等。常见做法：① 写分区用 INSERT OVERWRITE（覆盖整分区），重跑结果一致；② 用 INSERT ... ON DUPLICATE KEY UPDATE 或 MERGE；③ 先写临时表再原子切换。另外要注意任务粒度：一个任务里既写库又发消息，重试会重复发消息——所以副作用操作要么幂等，要么单独拆成任务。
