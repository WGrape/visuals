1为什么需要采用决策框架

大模型不是银弹。当团队拿到一个需求时，最常见的失败不是模型选错，而是根本不该用 LLM：任务如果是确定性的、可枚举的、对准确率要求 100% 且结果可验证，规则引擎或传统机器学习往往更便宜、更可控。采用决策框架的意义，是把"要不要上 LLM"从拍脑袋变成一张可复用的评估表，避免把 PoC 做成 production 才发现成本爆炸。

核心判断：LLM 擅长"模糊输入→结构化/自然语言输出"的映射，且不要求每条规则都预先编码；它不擅长"必须零误差、可形式化验证、延迟预算极低"的场景。

2三维评估模型

把任务拆成三个正交维度分别打分，再综合判断。每个维度分高=适合 LLM，分低=谨慎或回避。

维度适合 LLM 的信号不适合 LLM 的信号
输入的模糊性自然语言、非结构化、意图需推断严格表单、字段固定、强类型
输出的容错性草稿、建议、摘要、可人工复核金融记账、处方、控制指令
规则的可枚举性规则多到写不完、经常变规则清晰、稳定、可穷举

三维都偏"适合"才建议直接上 LLM；若"容错性"低，必须配合人工复核或确定性兜底（见第三层）。

3成本与 ROI 的量化

落地前先算清单位经济：每次调用的 token 成本、QPS 带来的月度账单、以及替代掉的人力成本。一个常见误区是只看 API 单价，忽略重试、长上下文缓存未命中、以及评估与运维的人力。

# 粗略月度成本模型
per_call_input = 1500      # tokens
per_call_output = 600
price_in = 0.0000025       # 美元 / token (示例)
price_out = 0.00001
monthly_calls = 2_000_000
cost = monthly_calls * (per_call_input*price_in + per_call_output*price_out)
print(f"月调用成本 ≈ ${cost:,.0f}")
# ROI = (节省的人力小时 * 小时单价 - 成本) / 成本

第一层 · 概念与判定

判定清单（满足越多越该用 LLM）：

  • 输入是非结构化/自然语言，难以写成固定 schema；
  • 需要"理解"语义而非精确匹配；
  • 规则数量庞大或频繁变化，维护成本高；
  • 输出允许人工或自动复核，非直接执行致命操作；
  • 有足量高质量样本可做评估。

出现以下任意一条，优先不用 LLM：金额/医疗/控制指令且不可复核；结果需形式化证明；延迟预算 < 20ms；每秒百万级调用且成本敏感。

第二层 · 参数·命令·量化

成功指标要可度量，建议同时定义业务指标与质量指标：

类别指标示例目标
业务人工处理时长下降、转化率、工单关闭率环比 +X%
质量人工抽检合格率、幻觉率、偏离率≥ 95%
成本单次调用成本、月度账单、ROIROI > 1
体验用户满意度 CSAT、重试率CSAT ≥ 4/5

成本公式：月成本 = 月调用数 ×(输入 tokens × 单价_in + 输出 tokens × 单价_out)，别忘了缓存命中率与重试倍率。

第三层 · 排障与边界

落地常见坑：

  • 评估集偏乐观：用生产分布外的样例评估，上线即翻车；
  • 无确定性兜底：低容错场景直接让 LLM 执行，出事才加校验；
  • 成本失控：长上下文每次全量重发，缓存未命中；
  • 指标自欺：只报"整体准确率"，掩盖长尾失败。
何时必须加人工复核环

当任务的错误代价高（财务、合规、安全）且模型在长尾样本上不可靠时，采用"LLM 产出 → 规则/模型二次校验 → 人工抽检"的环，而不是直接对客。

第四层 · 原理与取舍

原理上的取舍：

  • 灵活性 vs 可控性：LLM 用"涌现泛化"换掉了"可穷举的规则保证"，代价是输出不可形式化验证；
  • 开发成本 vs 运行成本：规则系统前期贵、运行便宜且稳定；LLM 前期便宜、运行贵且波动；
  • 可解释性：规则可逐条追溯，LLM 归因困难，监管场景是硬伤。

结论：把 LLM 当作"高柔性、中可靠、高单位成本"的组件，用决策框架决定它该不该出现在链路里、以及需要哪些护栏。
