一句话总结：同样一条 SQL，不同的执行计划可能差出几个数量级。优化器的核心工作是把逻辑计划变成代价最低的物理计划——靠统计信息估算，靠规则下推，靠经验重排。

01优化器做什么

SQL 是"做什么"，不是"怎么做"。优化器分两步：

  • 逻辑计划：把 SQL 解析成关系代数树（scan / filter / join / agg / project）。
  • 物理计划：给每个逻辑算子选具体实现（hash join vs broadcast join、hash agg vs sort agg、扫本地表 vs 扫分布式表），并决定执行顺序。

分布式 OLAP 还要额外决定：查询在哪些节点并行、数据怎么 Shuffle、哪些算子下推到存储层。

02代价模型（CBO）

基于代价的优化器（Cost-Based Optimizer）依赖统计信息估算每个计划的代价：

📏 行数

表总行数、过滤后估计行数（基于选择率）。

🔢 NDV

列的不同值数（Number of Distinct Values），决定 GROUP BY / JOIN 输出规模。

📊 直方图

列值分布，估算范围查询的选择率，避免被"平均值"骗。

📦 列大小

每行平均字节，估算 IO 与网络传输量。

代价函数通常是 IO 成本 + CPU 成本 + 网络成本 的加权；统计信息过期会导致估算偏差，进而选错计划。

03谓词下推（Predicate Pushdown）

把 WHERE 过滤条件下推到尽可能靠近数据源的位置：

  • 下推到 scan 层：减少后续算子处理的数据量，有时能直接触发分区裁剪和跳数索引。
  • 下推到存储节点（算子下推）：让过滤在 BE/数据节点本地完成，避免把无关数据通过网络搬出来。
  • 投影下推（列裁剪）：只读取查询用到的列，配合列存进一步减少 IO。
过滤越靠近源，跨网络搬的数据越少

04JOIN 重排与策略

决策规则/启发
JOIN 顺序多表 join 通常 left-deep，先 join 选择性高（结果小）的表，让中间结果尽早缩小
JOIN 策略大表×大表 → Shuffle Hash Join；大表×小表 → Broadcast Join
星型模型事实表很大、维度表很小，维度表广播，事实表本地扫描，避免事实表移动
分布对齐两表按相同 key 分桶（Colocate），可免去 shuffle 直接本地 join

05Runtime Filter

Runtime Filter 是 OLAP 的"杀手锏"：在查询运行时，build 端（小表）先把 join key 的过滤条件（常是 bloom filter）推给 probe 端（大表）的 scan，让大表在扫的时候就提前丢掉不满足的行，大幅减少后续 Shuffle 和 join 的数据量。对星型模型（大事实表 join 小维度表）效果尤其明显。

代价：build 端要先跑出过滤条件，probe 端要等一下（有超时兜底），所以是"用一点延迟换大量 IO 节省"。

06怎么读 EXPLAIN

  • 看计划树的算子类型和顺序，确认 join 策略、是否下推、是否广播。
  • 对比估算行数和实际行数：差距大说明统计信息过期。
  • 找长尾算子：某个 scan/agg 输出远超预期，通常是倾斜或漏下推。
  • 关注Shuffle 数据量：是网络瓶颈的直接指标。

07常见疑问

为什么同一 SQL 有时快有时慢？
可能统计信息变了导致计划变；也可能runtime filter 是否生效、是否命中缓存、集群负载不同。先看 EXPLAIN 和实际行数是否匹配估算。
Runtime Filter 一定有用吗？
不一定。build 端数据量大或过滤性差时，bloom filter 几乎全匹配，收益很小；且 probe 端要等 build 端，极端情况拖慢。优化器会根据 build 端大小选择性开启。
为什么不直接用 RBO（规则优化）？
规则能纠正明显傻计划（如总是先 join 再过滤），但"哪种 join 策略更快"必须靠代价比较，规则给不出——所以现代 OLAP 都是 CBO 为主、RBO 为辅。

调优清单

症状排查/手段
全表扫描不裁剪确认过滤列是否为排序键前缀；否则加跳数索引/bitmap
估算行数远大于实际统计信息过期 → ANALYZE / 收集统计
大表被广播统计信息误判小表大小；或强制 shuffle hint
Shuffle 量爆炸检查是否漏了谓词/投影下推；是否 join key 选择率高
星型 join 慢开启 runtime filter；维度表广播；事实表按 join key 分桶
统计信息要收集哪些、多久一次？

至少包括行数、每列 NDV、直方图、NULL 比例、列平均长度。在批量导入后或大表结构变化后收集；高频写入的表可设定时任务。统计信息不准是"计划突然变差"的头号原因。

深度补充：OLAP 查询优化器与执行计划

第一层 · 概念与判定 优化器把 SQL 重写成代价更低的执行计划：谓词下推、列裁剪、Join 重排、聚合拆分。判定：慢查询先看 EXPLAIN，定位是否下推/剪列/选错 Join 顺序。

优化作用看哪
谓词下推在数据源处过滤扫描行数
列裁剪只读用到的列IO 量
Join 重排小表驱动、广播中间结果大小
聚合拆分两阶段（本地+全局）网络 shuffle

第三层 · 排障与边界

  • 谓词没下推（视图/函数包裹列）导致全量扫描。
  • Join 顺序选错，中间结果爆炸，需 hints 或重写。
  • 缺少统计信息，代价估算失真，计划次优。
  • 聚合未两阶段，单节点做全局聚合成瓶颈。
第四层 · 原理与取舍

优化器用“基于代价的搜索 + 规则改写”换高效计划，代价是优化本身耗时与统计信息维护。CBO 依赖准确的列统计（基数、NDV、直方图），统计过时就会选错计划。权衡是“计划质量 vs 优化开销”：简单查询靠规则下推足够，复杂多 Join 必须靠 CBO + 及时 ANALYZE。EXPLAIN 是诊断的第一现场。

实例与速查：读懂执行计划

-- 看计划是否下推 / 剪列 / 选对 Join 顺序
EXPLAIN ANALYZE
SELECT user_id, count(*) FROM events
WHERE ts > '2026-10-01'          -- 先看这层谓词是否下推
GROUP BY user_id;

-- 缺少统计信息时刷新，让 CBO 估算准确
ANALYZE TABLE events;
  • 谓词被函数包裹（WHERE year(ts)=2026）无法下推，全量扫描。
  • Join 顺序选错，中间结果爆炸，需 hints 或重写。
  • 统计信息过时，代价估算失真，计划次优，需 ANALYZE。
FAQ：EXPLAIN 里出现 Exchange 算子代表什么？

Exchange 表示数据需要跨节点重分布（shuffle），通常出现在跨分片 Join 或全局聚合。它意味着网络开销，是 MPP 查询的主要瓶颈来源之一。看到它就要关注数据倾斜与并行度：能否用 colocate Join 消除 shuffle、聚合能否两阶段（本地+全局）降低网络量。

常见误区与延伸

  • 误区一：看到慢就加索引。先 EXPLAIN 看是否下推/剪列/选错 Join 顺序，很多慢是计划错误而非缺索引。
  • 误区二：统计信息一劳永逸。数据分布变化后代价估算失真，需定期 ANALYZE。
  • 延伸：聚合未两阶段会单节点串行，应拆本地聚合加全局汇总，减少网络 shuffle。
  • 延伸：Join 重排小表驱动/广播，中间结果大小决定瓶颈，hints 或重写可纠偏。

一句话总结：优化器用代价搜索加规则改写换高效计划，依赖准确统计；EXPLAIN 是诊断第一现场，谓词下推与剪列是首要检查点。

决策速记

  • 先 EXPLAIN：慢未必缺索引，多是计划错（未下推/选错序）。
  • 查统计：分布变化后 ANALYZE，否则估算失真。
  • 促下推：避免函数包裹列，让谓词在数据源过滤。
  • 两阶段聚合：避免单节点串行，降低网络 shuffle。

一句话：优化器用代价搜索换高效计划，EXPLAIN 是诊断第一现场。

横向对比与追问

  • 与 OLTP 优化器比：OLTP 优化器重索引选择与计划稳定性，OLAP 优化器重分布式 shuffle 与并行度。
  • 与 MPP 比：优化器决定“怎么分与怎么聚”，MPP 决定“并行执行”，二者接力。
  • 追问：为什么 CBO 依赖统计信息？没有基数估算，代价模型无处下手，计划易次优。
  • 追问：Hints 该不该用？只在优化器选错且验证有效时用，否则随数据变化失效。

小结：优化器是“基于代价 + 规则”的搜索，EXPLAIN 与 ANALYZE 是两大诊断工具。

速记口诀

口诀：先 EXPLAIN 看下推，再 ANALYZE 更统计，两阶段降 shuffle。

  • 统计过时计划次优，需刷新。
