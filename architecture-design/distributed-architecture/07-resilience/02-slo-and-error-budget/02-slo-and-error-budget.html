SLO 与错误预算

SLI/SLO/SLA 的区别，错误预算如何把可靠性变成可消耗的额度

SLISLOSLA错误预算

一句话：可靠性不能喊口号。SLO 用数字定义“够可靠”，错误预算把这份可靠性变成可消耗的额度——花完就要踩刹车。

SLI / SLO / SLA 三层

概念是什么例子
SLI 指标可度量的实际表现请求成功率、P99 延迟、可用性
SLO 目标给 SLI 设的内部目标“月度成功率 ≥ 99.9%”
SLA 协议对外承诺+违约补偿“99.5% 否则赔款”

关键关系：SLA 必须宽松于 SLO，SLO 必须宽松于实际 SLI。三层之间留buffer，才不会一波动就违约。

错误预算（Error Budget）

错误预算 = 1 − SLO 目标。SLO 99.9% 意味着允许的失败比例是 0.1%/月，这就是“预算”。预算没花完，可以大胆迭代；预算耗尽，就冻结新功能、优先还债。它把“可靠性”和“发布速度”拉到同一张资产负债表上。

预算充足

正常发版、做实验、试新功能。

预算告急

收紧变更、暂停非必要发布、集中排障。

预算耗尽

冻结功能发布，所有精力回归稳定性。

怎么告警：多窗口燃烧率

简单“成功率<99.9% 就报警”噪声太大。Google SRE 推荐多窗口燃烧率（burn rate）：同时看“短期快烧”和“长期慢烧”两个窗口，既抓突发故障，也抓慢性劣化，同时把噪声压到最低。

  • 燃烧率 = 实际错误率 / 预算允许错误率。>1 表示在消耗预算。
  • 快窗口（如 1h）抓急性故障，慢窗口（如 6h/1d）抓缓降，两者都满足才告警。

概念与判定

  • SLO 是内部的：不必对外公开；SLA 才是对客户的硬承诺，且要有赔偿条款。
  • 选哪些 SLI：用户最能感知的指标（成功率、延迟、可用性），不要堆几十个。

参数·命令·量化

目标月度允许停机错误预算
99%~7.3 小时1.0%
99.9%~43 分钟0.1%
99.95%~22 分钟0.05%
99.99%~4.4 分钟0.01%
  • 燃烧率 > 1 ⇒ 正在超支预算；常见告警阈值设在 1h/6h 双窗口。
  • Prometheus 示例：( (1 - errors[1h]/requests[1h]) < 0.999 ) and ( (1 - errors[6h]/requests[6h]) < 0.999 ) 作为最简双窗口近似。

排障与边界

  • 预算总被烧光：说明 SLO 定太高或系统真不稳；先降发布节奏、补可靠性，而不是偷偷调高 SLO。
  • SLO 成摆设：没人看预算、烧光也不刹车，等于没设；要与发布门禁联动。

原理与取舍

  • 过严：团队寸步难行、永远在修稳定性；过松：用户感知到故障却不告警。
  • 错误预算 vs 混沌/压测：预算告诉你“还能承受多少失败”，混沌/压测验证“失败时会怎样”，三者共同构成韧性闭环。
