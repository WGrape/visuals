工具接口、闭环与避坑

Agent 工具设计 · 实现与闭环

工具（Tool）是 Agent 与外部世界交互的「手」。模型本身只能「想」和「说」，真正读数据、改状态、调服务都靠工具。工具设计的好坏，直接决定 Agent 能不能稳定干活。

一、工具的接口契约

一个可被模型调用的工具，至少要有三件套：

字段作用要点
name唯一标识动词化、无歧义，如 search_flights
description自然语言说明写清「做什么、何时用」，模型靠它选工具
parametersJSON Schema参数名、类型、是否必填、枚举值
{
  "name": "get_weather",
  "description": "查询某城市当前天气，规划出行前调用",
  "parameters": {
    "type": "object",
    "properties": {
      "city": {"type":"string","description":"城市名，如 北京"},
      "unit": {"type":"string","enum":["celsius","fahrenheit"]}
    },
    "required": ["city"]
  }
}

二、Function Calling 闭环

  1. 用户提问，模型结合「工具清单」判断是否需调用工具。
  2. 若需要，模型输出结构化调用请求（工具名+参数），而非自然语言。
  3. 运行时（Runtime）真正执行工具，拿到结果（observation）。
  4. 把结果回填给模型，模型决定「继续调工具」还是「直接回答」。

三、实现要点与坑

🧱

薄封装

工具应是「对已有 API/代码的薄壳」，把不确定性留在内部，对外只暴露干净参数。

🛡️

错误处理

工具失败要返回可懂的错误信息，而非抛异常中断整个循环。

🔐

权限与沙箱

写操作/外部调用需用户确认或限制在沙箱内。

📏

结果裁剪

返回过长会撑爆上下文，应摘要或分页。

⚠️ 工具描述里若暗示「我能做 X」但实际实现不支持，模型会反复尝试并失败（hallucinated tool use）。描述必须与实现严格一致。
形象化理解：Agent 像「带对讲机的现场指挥」，工具是「派出去干活的工人」。指挥不能直接搬砖，只能通过派人（工具）去干；派人前得说清「去哪、干啥、带什么」（参数），工人回来报告（observation），指挥再决定下一步。

工具调用循环：Agent 的最小骨架

Agent 与普通对话的区别，就在这一个循环：模型不直接回答，而是先决定「要不要用工具、用哪个、传什么参」，拿到结果后再决定下一步，直到认为可以回答为止。

Agent 的核心循环：决策 → 调用 → 执行 → 观察 → 再决策
工具是模型的手脚模型本身不知道今天的天气、数据库里的订单，工具负责把外部世界接进来。
循环要有上限必须设最大步数与最大耗时，否则一个错误判断能让 Agent 无限打转。
观察要可理解工具返回给模型的内容应简洁、结构化，冗长原始返回会挤爆上下文。
失败要回灌把错误信息原样回传给模型，它往往能自我纠正参数重试。

工具定义：写清楚比写多更重要

工具用 JSON Schema 描述。模型完全依赖 description 判断「该不该用、什么时候用」，所以描述的质量直接决定调用准确率。

{ "name": "query_order_amount", "description": "按日期区间查询订单总金额。仅支持已结算订单；查退款请用 query_refund_amount。日期格式为 YYYY-MM-DD。", "parameters": { "type": "object", "properties": { "start_date": {"type": "string", "description": "开始日期，含当天"}, "end_date": {"type": "string", "description": "结束日期，含当天"} }, "required": ["start_date", "end_date"] } }
要素怎么写反例
name动词开头、语义唯一，如 search_flight用 tool1、query 这种无法区分的名字
description说清用途 + 边界 + 不适用时用谁只写「查询数据」
parameters参数少而原子，每个字段都写 description塞一个万能 params 对象
required真的必填才标，能推导的让模型填全部必填导致频繁调用失败
返回值固定结构、字段稳定、错误可读直接抛异常栈给模型

三类工具与它们各自的风险

只读查询类

搜索、查库、读文件、调 API 取数。风险最低，可以放宽自动执行。

  • 要限制返回条数与体积，避免冲爆上下文
  • 加缓存，重复查询直接命中
  • 超时设短一些，快速失败让模型换招

写入变更类

下单、发消息、改数据库、改文件。必须加确认与幂等。

  • 幂等键：同一意图重复调用只生效一次
  • 敏感操作走人工确认或白名单
  • 记录审计日志，能追溯是谁让模型做的

执行代码类

跑 Python、执行 shell。风险最高，必须沙箱化。

  • 容器隔离、无外网或白名单外网、只读挂载
  • CPU / 内存 / 时间三重限额
  • 输出截断，防止巨量日志回流

并行调用与依赖：什么时候能一起发

当模型一次产出多个 tool_call 时，要判断它们之间有没有依赖。没有依赖就并发执行，能省掉好几轮往返。

无依赖可并发查北京天气 + 查上海天气 → 一起发
有依赖必须串行先查用户 ID → 再用 ID 查订单
部分依赖分批第一批并发，拿到结果后再发第二批
写操作谨慎并发有副作用的调用并发可能乱序，建议串行或加锁
并发要有上限限制单次并发数，避免一次打出几十个请求
失败要能单独重试某一个失败不要整批回滚

失败处理：把错误变成模型的输入

失败类型现象处理方式
参数不合 schemaJSON 缺字段、类型错本地校验后把具体错误回灌，让模型重发
工具不存在模型编造了工具名返回可用工具清单，引导模型重选
权限不足越权访问被拒明确告知权限边界，不要静默失败
超时执行超过阈值返回超时信号，让模型换策略或拆小任务
业务错误查无此单、余额不足返回结构化错误码与说明，模型可解释给用户
步数耗尽循环超过上限强制收尾：总结已得信息并说明未完成部分

关键原则：不要把异常吞掉。把「发生了什么、为什么、可以怎么改」结构化地回传给模型，它的自我修复能力通常比硬编码兜底更通用。

权限、隔离与工具生态

最小权限

每个工具只拿完成任务必需的权限。Agent 的破坏力 = 它能调用的工具 × 工具的权限。

  • 凭据按工具隔离，不共用超级账号
  • 只读工具用只读账号
  • 敏感参数（金额、收件人）由系统注入，不依赖模型生成

人在回路

高风险动作交给人类确认，是成本最低的一道防线。

  • 转账、删除、对外发送 → 强制确认
  • 确认界面要展示真实参数，不是模型的话术
  • 记录决策依据，便于复盘

统一协议

工具数量变多后，用统一协议（如 MCP）把「工具注册、发现、调用」标准化，避免每个 Agent 各写一套适配层。

  • 工具一次实现，多个 Agent 复用
  • 权限与审计集中在服务端
  • 便于跨语言、跨进程部署

深入自检

工具是不是越多越好？

不是。工具越多，模型选错的概率越高，描述占用的上下文也越大。经验上同一场景保持十几个以内，超过就做分层：先用一个「路由工具」选择类别，再加载该类别的少量工具。

模型总是不调工具，直接瞎答怎么办？

常见原因有三个：description 写得不像「工具」而像「说明」；system 里没强调「不确定时必须查证」；历史里有过直接回答被接受，模型学到了捷径。修描述 + 显式要求查证 + 给出 few-shot 示范，通常能显著改善。

工具返回很大，上下文一下就满了，怎么处理？

三招：让工具默认返回精简字段（只给关键列）；把大结果落盘或入库，只回传摘要与引用 ID；必要时用子 Agent 先消化原始内容，只把结论回传给主 Agent。

并行工具调用会不会导致结果错乱？

只要把每次调用的 tool_call_id 原样带回，模型能分辨哪个结果对应哪次调用。真正的风险在写操作：并发的写可能乱序或重复，因此写类工具应当串行化并做幂等。

为什么必须限制循环步数？

模型可能陷入「查不到 → 换个参数再查」的死循环，每一步都在烧钱。设最大步数（如 10~20）与最大耗时，超限时强制收尾总结，是 Agent 稳定性的基本保障。
