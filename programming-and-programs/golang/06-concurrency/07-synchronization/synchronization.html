共享可变状态需要保护

多个 goroutine 同时读写同一变量会出现竞争条件（race condition），结果不可预测。互斥锁是最基础的防线。

sync.Mutex 互斥锁

临界区串行化

进入临界区前 Lock，离开时（通常 defer）Unlock。同一时刻只有一个 goroutine 能持有锁。

var mu sync.Mutex
var balance int

func Deposit(n int) {
    mu.Lock()
    defer mu.Unlock()
    balance += n
}
func Balance() int {
    mu.Lock()
    defer mu.Unlock()
    return balance
}
RWMutex 读写锁

读多写少更高效

多个读可并发（RLock），写独占（Lock）。适合缓存、配置这类读远多于写的场景。

var rw sync.RWMutex
func Get(k string) (string, bool) {
    rw.RLock(); defer rw.RUnlock()
    v, ok := m[k]; return v, ok
}
func Set(k, v string) {
    rw.Lock(); defer rw.Unlock()
    m[k] = v
}
sync.Once 惰性初始化

保证只执行一次

单例、全局连接池等「只初始化一次」的场景用 Once.Do，并发调用也安全且只跑一次。

var once sync.Once
var conn *DB
func GetConn() *DB {
    once.Do(func() { conn = connect() })
    return conn
}
内存同步语义

锁不只是互斥

锁还建立了 happens-before 关系：Unlock 之前的内存写，对后续 Lock 的 goroutine 可见。没有锁，编译器/CPU 的乱序优化会让另一个 goroutine 看到陈旧值。

这正是第 6 章「内存模型」要解决的问题：并发正确性靠同步原语建立的可见性保证，而非运气。
竞争条件检测

-race 帮你抓 bug

Go 内置竞态检测器：go test -race / go run -race。它能在测试/运行中报告对共享变量的并发读写冲突。

⚠️ -race 有性能/内存开销，仅用于测试环境；上线构建一般不开。但它抓出的 race 是真实 bug，必须修。
sync.Cond 条件变量

等待某个条件成立

需要「等某条件再继续」时，Cond 配合锁比忙等（轮询）高效：Wait 释放锁并阻塞，Signal/Broadcast 唤醒。

通道与锁：各用在什么地方

用通道的场景

当目的是传递数据或交接所有权时，用通道更自然：生产者把结果交给消费者、任务分发、信号通知、控制并发数量。它把同步和通信合成一步，代码意图更清楚。

用锁的场景

当目的是保护一块共享状态时，用锁更简单：缓存、计数器、配置热更新、连接池的空闲列表。这类场景用通道反而要绕一圈，而且容易把状态管理逻辑写得更复杂。

最常见的几种并发问题

锁被拷贝会怎样？

会复制锁的内部状态，导致两个副本互不认识，保护完全失效，而且这类问题不会报错、只会偶发。所以结构体里有锁时，一律用指针传递。

忘记解锁会怎样？

其他 goroutine 会永久阻塞，表现为程序卡死而不是报错。所以解锁一定要写在 defer 里，这样即使临界区中途返回或 panic 也能释放。

两把锁互相等待会怎样？

死锁。典型场景是两个 goroutine 以相反顺序获取同一对锁。解决方法是全局固定加锁顺序，或者只锁一把大锁，或者用带超时的尝试加锁。

原子操作和锁能混用吗？

不要对同一个变量混用。原子操作与锁是两套内存同步机制，混用会让代码看起来同步了，实际存在竞态。一个变量要么始终用原子操作，要么始终用锁保护。

goroutine 泄漏怎么排查？

常见原因是通道没人接收或没人关闭，导致发送方永久阻塞。排查手段：查看运行中的协程数量与栈、用带超时的 select、确保每个启动的协程都有明确的退出路径。

读写锁的读锁可以重入吗？

不可以。如果在持有读锁时再次请求读锁，而中间有写锁在等待，就会死锁。这是写优先策略决定的，所以不要在读锁保护的代码里再次获取同一把读锁。

解锁用 defer保证任何路径都会释放
锁不跨函数临界区尽量短，别在锁里做网络请求
锁不可拷贝含锁的结构体用指针传递
固定加锁顺序避免死锁最简单有效的办法
必跑竞态检测测试时开启竞态检测
通道要有人收没人接收就会泄漏
等待组传指针传值会复制计数导致永远等不到
对象池不是缓存里面的对象随时可能被清掉

Go 同步原语选型表

原语适用场景关键数值 / 注意
sync.Mutex通用互斥无竞争约 20ns；竞争严重时走信号量，可能 µs~ms 级
sync.RWMutex读多写少读并发安全；写锁会阻塞新来的读锁，防止写饥饿
sync.Once单例 / 只执行一次的初始化Do 内 panic 也算执行过，不会再重试
sync.WaitGroup等待一组 goroutineAdd 必须在 goroutine 外先调用，否则有竞态
sync.Cond等待条件成立必须在锁内 Wait；被唤醒后要用 for 重新检查条件
sync.Map读多写少 / key 稳定后基本只读写多或需遍历时反而比 map+Mutex 慢
sync/atomic单一变量的原子读写/CAS比 Mutex 快一个量级；只支持固定类型
errgroup.Group一组任务 + 错误传播 + 可选并发上限SetLimit(n) 限并发
semaphore(x/sync)精确限流Acquire(ctx, n) 可取消

选择顺序：能用 channel 表达所有权转移就用 channel；只是保护一个计数器就 atomic；保护一段临界区或复合不变量才用 Mutex。不要为了「看起来并发」而用 channel 代替 Mutex。

正确用法与反例代码

// 反例：WaitGroup.Add 放在 goroutine 里 —— 可能主协程先 Wait 返回
for i := 0; i < n; i++ {
    go func() {
        wg.Add(1)          // ❌ 竞态：Add 可能发生在 Wait 之后
        defer wg.Done()
    }()
}
wg.Wait()

// 正例：Add 在启动前
for i := 0; i < n; i++ {
    wg.Add(1)              // ✅
    go func(i int) { defer wg.Done(); work(i) }(i)   // 注意传参，别闭包捕获循环变量
}
wg.Wait()

// Go 1.22+ 循环变量每次迭代独立，闭包捕获已安全；1.21 及以前必须显式传参
// Cond 正确姿势：Wait 必须在循环中检查条件
var mu sync.Mutex
var cond = sync.NewCond(&mu)
var ready bool

// 等待方
mu.Lock()
for !ready {          // for 不是 if：可能被虚假唤醒
    cond.Wait()       // 内部会临时释放 mu，返回前重新加锁
}
mu.Unlock()

// 通知方
mu.Lock()
ready = true
cond.Broadcast()      // 一个等待者用 Signal()，多个用 Broadcast()
mu.Unlock()

// errgroup + 并发上限
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(10)                       // 最多 10 个并发
for _, item := range items {
    item := item
    g.Go(func() error { return process(ctx, item) })
}
if err := g.Wait(); err != nil {     // 第一个非 nil error，且会 cancel ctx
    return err
}
