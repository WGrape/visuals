inode、硬链接与软链接：删掉文件名后数据去哪了

用两个名字指向同一 inode 的例子，手推目录项、链接计数、打开句柄与符号链接的变化。

先把名字和文件分开

在典型 Unix 文件系统中，目录保存“名字 → inode 编号”的映射；inode 记录文件类型、权限、大小、时间戳和数据块位置等元数据。打开 `/work/report.txt` 时，内核逐层解析目录名，找到最后的目录项，再由 inode 定位文件内容。文件名一般不直接保存在 inode 中，所以同一 inode 可以有多个名字。`ls -i` 可观察 inode 编号，但编号只在同一个文件系统内有意义，不能把不同挂载点的相同编号当作同一文件。

路径还有权限边界：能否打开文件不仅看文件本身权限，也要看沿途目录是否允许搜索。目录读权限和搜索执行权限含义不同；没有目录的搜索权限，即使知道文件名也可能无法访问。理解路径解析过程有助于排查“文件明明存在却报 Permission denied”。

图解：一个 inode 的三个不同引用

沿箭头逐步核对输入、变换和输出；下面的推演可以逐步切换。

硬链接是第二个名字

假设 `report.txt` 指向 inode 41，链接计数为 1。创建硬链接 `archive.txt` 后，两个目录项都指向 inode 41，链接计数变 2。修改任一名字对应的文件内容，另一个名字读到相同数据，因为两者并非两份拷贝。删除 `report.txt` 只移除一个目录项，链接计数变 1，`archive.txt` 仍可访问原内容。再删除 `archive.txt`，名字都消失；若没有进程继续打开该文件，数据块才可被回收。

硬链接通常不能跨文件系统，因为 inode 编号和块位置属于各自文件系统；对目录创建普通硬链接也通常受限制，以免形成目录环。硬链接指向 inode，而不是“先指向原文件名再转向数据”，因此重命名或删除第一个名字不影响第二个名字。

逐步推演

创建 a

目录项 a 指向 inode 41，链接数 1。

创建硬链接 b

b 也指向 inode 41，链接数 2。

创建软链接 c

c 保存路径 a，不直接指向 inode 41。

删除 a

b 仍可读，c 的目标路径悬空。

软链接保存一段路径

符号链接可理解为一个特殊文件，内容是目标路径，例如 `current → report.txt`。访问 `current` 时，路径解析器继续解释这段目标路径；删除或移动 `report.txt` 后，`current` 可能成为悬空链接。软链接可以跨文件系统，也可以指向目录，但相对路径相对于符号链接所在目录解释，而不是相对于当前 shell 工作目录解释。这个细节在部署目录切换中很常见。

`lstat` 查看链接对象自身，`stat` 通常跟随链接查看目标；实际命令和 API 的跟随行为要核对选项。若程序为了安全要检查路径，就不能先检查后在不受控时间里打开同一路径并假定目标不变；并发重命名或软链接替换会造成 TOCTOU 竞态，关键操作应使用合适的目录句柄与原子打开方式。

对象保存的关键内容删除 a 后
硬链接 b指向 inode 41 的目录项仍有效
软链接 c目标路径 a悬空
已打开描述符内核打开文件引用仍可读至关闭
inode 41元数据与块映射等无链接和打开引用才回收

打开的文件还能读吗

进程打开文件得到文件描述符后，内核持有打开文件对象与底层 inode 的引用。此时另一个进程把最后一个名字 unlink 掉，路径查找已找不到它，但已打开的文件描述符一般仍可读写原文件。磁盘空间可能直到最后一个描述符关闭才释放。日志服务删除巨大日志文件却磁盘未下降，常见原因就是进程还握着句柄；需要让服务重新打开日志或关闭句柄，而不是反复删除路径。

`rename` 修改目录项映射，常用于在同一文件系统内切换名字。已有文件描述符仍引用原来的打开文件对象，新路径解析则可能落到新 inode。读取者若需要“始终看到同一版本”，应明确是先打开文件后持续读，还是每次从路径重新打开。两者对热更新的体验不同。

手推一张状态表

起点 inode 41、链接计数 1、打开句柄 0。创建 `archive.txt` 后计数 2。进程 P 打开 `report.txt`，句柄 1；删除 `report.txt`，计数 1、P 仍可读；删除 `archive.txt`，计数 0，但 P 仍可读；P 关闭句柄后，文件系统才有机会回收 inode 和块。若此时另有符号链接 `current → report.txt`，它早在 `report.txt` 删除时就已悬空，与 inode 41 是否仍被 P 打开无关。

删除目录项前应确认操作的是链接自身还是链接目标。许多命令会跟随符号链接读取内容，但删除符号链接通常删除的是链接对象；误用递归工具和路径尾斜杠可能改变语义，生产脚本应使用测试目录验证。

常见考点与排障

“硬链接数归零后立刻释放磁盘”少了打开句柄条件；“软链接是同一 inode 的第二个名字”混淆了路径内容与 inode 指向；“文件名就在 inode 里”忽略了目录项；“同名文件一定是同一文件”忽略了重命名和不同挂载点。这些错误都可以用目录项、inode、打开对象三层图反驳。

排查磁盘占用时同时看路径可见文件与被删除但仍打开的句柄；排查部署切换时看软链接目标是否使用相对路径、是否跨文件系统以及进程是否缓存了旧句柄。练习：`a` 和 `b` 是硬链接，`c` 是指向 `a` 的软链接。删除 `a` 后，谁仍能读到数据？为什么？

硬链接与符号链接的逐项对照

维度硬链接（hard link）符号链接（symlink）
本质同一个 inode 的第二个目录项独立 inode，内容存目标路径字符串
inode 号相同不同（有自己的 inode）
跨文件系统不支持支持
链接目录通常禁止（避免环路）可以
目标删除后数据仍在（link count 减 1）变成悬空链接（dangling）
ls -l 第二列累加到 inode 的 link count始终为 1
典型大小0（不占额外数据块）等于路径字符串长度（≤ 60 字节可存于 inode 内，即 fast symlink）

关键机制：unlink 删除的是目录项，不是数据。只有当 inode 的 link count 归零、且没有进程持有该文件描述符时，数据块才会被真正释放。

可执行的诊断命令

命令

# 看 inode 号与链接数
ls -i file.txt
stat file.txt          # Inode / Links / Size / Blocks

# 建链接
ln file.txt hard.txt              # 硬链接：Links 变 2，Inode 相同
ln -s /abs/path/file.txt soft.txt # 软链接：独立 inode，大小=路径长度

# 反查：由 inode 号找所有硬链接
find /mount/point -inum 12345678

# 悬空链接检测
find /path -xtype l

# inode 使用情况
df -i /mount/point
tune2fs -l /dev/sdXN | grep -E "Inode count|Inode size|Block count"

# 已删除但仍被进程占用的文件（空间不释放的元凶）
lsof +L1
lsof | grep deleted

复现

# 复现"删了文件但磁盘没释放"
python - <<'PY'
import os
f = open("/tmp/big.bin", "wb")
f.write(b"x" * 200_000_000)      # 200 MB
# 此时 rm /tmp/big.bin，df 显示空间未释放，因为进程还持有 fd
# lsof | grep deleted 能看到 (deleted) 标记
PY
# 处理：重启或让进程关闭 fd；紧急时 truncate 该 fd
: > /proc/<PID>/fd/<FD>

深入自检

为什么删除一个文件后磁盘空间没有释放？

因为 unlink 只删除目录项。只要还有进程持有该文件的打开文件描述符，inode 与数据块就不会释放。lsof +L1 能列出被删除但仍占用的文件，重启进程或 truncate 对应 fd 才会真正释放。

硬链接和拷贝有什么区别？

硬链接是同一个 inode 的第二个名字，共享同一份数据块，改一处处处可见，不额外占空间；拷贝生成新的 inode 与新的数据块，两份互不影响，占用翻倍。

符号链接能跨文件系统，硬链接为什么不能？

硬链接必须在同一个 inode 编号空间内引用 inode，而 inode 号只在本文件系统内唯一。跨文件系统无法保证唯一性，因此内核限制硬链接不能跨设备。符号链接只存路径字符串，与目标 inode 无关，所以可以跨。

为什么一般不允许对目录建硬链接？

会破坏目录树的树形结构：目录的 .. 项与硬链接组合会形成环路，导致遍历工具死循环、fsck 无法判定。内核仅允许 . 和 .. 这类由系统维护的特殊链接。

如何判断两个路径是不是同一个文件？

看 inode 号与设备号：stat 输出的 Inode 与 Device 都相同，就是同一个文件（硬链接）。只比较路径字符串或文件名会被软链接和挂载点骗过。

自检

a 与 b 是硬链接，c 指向路径 a。删除 a 后，b 和 c 各会怎样？

b 仍通过同一 inode 读到数据；c 保存的目标路径 a 已不存在，因而悬空。
