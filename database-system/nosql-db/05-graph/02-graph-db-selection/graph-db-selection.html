图数据库选型：Neo4j vs Neptune vs TigerGraph vs ArangoDB

关系密集的场景该用谁，一张表看清四个主流选手的差异

什么时候才该上图数据库

图数据库擅长的是关系密集、需要多跳遍历的场景：社交网络、反欺诈关系链、知识图谱、推荐召回、IT/服务拓扑。判断标准很简单——如果你的查询里有大量"朋友的朋友""这笔钱经过了哪些账户"，关系库要靠递归 JOIN，深度一多加索引也救不了；图库走指针邻接，代价只跟路径长度有关。

📌 如果只是单跳查询或纯聚合分析，关系库 / 文档库 / 数仓往往更便宜。图库不是"更先进的数据库"，而是"为关系而生的数据库"。

四个主流选手

🕸️ Neo4j

原生图存储、Cypher 查询语言、单机能力强、因果集群。生态最成熟，资料最多。

☁️ Neptune

AWS 全托管，同时支持 Gremlin 与 Cypher（及 SPARQL），和云上其他服务天然集成。

⚡ TigerGraph

分布式原生图、自研 GSQL、面向十亿级边、实时多跳与图算法。

🔶 ArangoDB

多模型数据库（文档 + 图 + 键值），用统一 AQL 查询，图只是其中一种用法。

选型建议

  • 要生态、要快上手、规模中等：Neo4j，踩坑资料最多。
  • 已经在 AWS、想少运维：Neptune，和 IAM / Lambda / S3 打通省事。
  • 边规模上十亿、要实时多跳与图算法：TigerGraph。
  • 本来就用 ArangoDB 存文档，偶尔做图查询：直接用它的图能力，不必再引一个引擎。
⚠️ 原生图 vs 多模型：多模型图（如 ArangoDB）胜在"一个数据库多种用法"，但深层多跳性能通常不如原生图存储。关系密集是核心需求时，优先原生图。

第一层 · 先判定要不要图数据库

信号含义该用什么
查询含多跳关系（A→B→C）关系深度是核心原生图数据库
只有单跳或聚合关系不密集关系库 / 文档库 / 数仓
需要图算法（PageRank、社区发现）拓扑分析TigerGraph / Neo4j GDS
偶尔查关系，主要存文档图是附属需求多模型库（ArangoDB）

第二层 · 语言与规模的关键数字

  • Cypher：声明式，用 ()-[]->() 描述图模式，学习曲线低。
  • Gremlin：命令式图遍历，灵活但更偏过程式。
  • GSQL：TigerGraph 的 SQL 风格图语言，擅长编译成分布式执行。
  • 规模阈值：节点/边在千万级以内多数图库都轻松；十亿边以上要认真看分片与图算法性能。

第三层 · 选型踩坑怎么查

  • 多跳变慢：确认是否走了索引邻接，而不是被当表做 JOIN；超深遍历要加深度上限防爆炸。
  • 图算法跑不动：Neo4j 的算法在 GDS 库，单机内存受限；大规模要 TigerGraph 或外推到 Spark GraphX。
  • 云账单超预期：Neptune 按实例+IO 计费，图写入放大时要注意。
  • 多模型"什么都行却都不精"：ArangoDB 图在超深多跳下性能不如原生图，先压测再决定。

第四层 · 原理与取舍

图库的核心卖点是 index-free adjacency（无索引邻接）：节点直接持有关系的物理指针，走一步关系的代价是常数级，与全图规模无关。关系库要做多跳就得层层 JOIN + 索引回表，深度增加代价指数上升。代价是：图库的写入和分布式分片比关系库复杂，且通用聚合分析能力弱——它把"走关系"做到了极致，其他方面就让位。

原生图和 RDF 三元组库怎么选？

属性图（Neo4j/TigerGraph）更贴近工程直觉、带类型的边和属性；RDF（语义网）强在推理与标准三元组，常见于知识图谱语义层。多数业务系统选属性图即可。
