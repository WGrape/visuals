分区与分桶裁剪：让查询少读一到两个数量级的数据

三层裁剪机制、分区粒度怎么选、分桶键的两个相反目标，以及六种让裁剪失效的写法

OLAP分区裁剪分桶执行计划数据跳过
① 三层裁剪 ② 分区 ③ 分桶 ④ 排障 ⑤ 疑问
一句话总结：分析型查询动辄扫几亿行，唯一能让它变快的办法就是少读数据。分区裁剪负责「跳过整个分区」，分桶裁剪负责「在分区内再跳过大部分桶」，MinMax 索引/Zone Map 负责「跳过文件块」。这三层加起来，往往能把扫描量降一到两个数量级。

01三层裁剪：从粗到细

层级依据粒度谁决定失效后果
分区裁剪分区键（通常是日期）整个分区目录建表时的 PARTITION BY + 查询条件扫全部分区
分桶裁剪分桶键的哈希值分区内的桶建表时的 DISTRIBUTED BY / BUCKETS扫该分区全部桶
块级裁剪每块的 min/max 统计数据块 / Granule排序键 + 写入时自动收集的统计读进不需要的块
要点：三层的前提都是「查询条件直接命中键」。任何对键做函数变换、类型转换，都可能让优化器认不出来，从而全层失效。

02分区：怎么切、切多细

分区键绝大多数情况下是时间（按天或按月），因为分析查询几乎都带时间范围，而且过期数据要能整块淘汰（TTL）。

切分粒度适合场景优点问题
按天日均有较大数据量、查询常按天过滤裁剪粒度细、TTL 灵活分区数增长快（一年 365 个），元数据压力上升
按月数据量中等、查询常按月/跨月分区数可控按天查也要扫整个月
按小时数据量极大、且查询集中在最近几小时裁剪最激进分区数爆炸，慎用
按业务键（如租户）多租户且查询几乎总带租户隔离效果好时间过滤失效；低基数租户易倾斜
-- Doris / StarRocks 分区 + 分桶的典型写法
CREATE TABLE events (
  dt        DATE           NOT NULL,
  uid       BIGINT         NOT NULL,
  province  VARCHAR(32),
  amount    DECIMAL(18,2)
)
PARTITION BY RANGE(dt) (
  PARTITION p202610 VALUES [('2026-10-01'), ('2026-11-01')),
  PARTITION p202611 VALUES [('2026-11-01'), ('2026-12-01'))
)
DISTRIBUTED BY HASH(uid) BUCKETS 16
PROPERTIES ("replication_num" = "3");

-- 命中分区键 + 分桶键：两层裁剪都生效
SELECT province, SUM(amount) FROM events
WHERE dt BETWEEN '2026-10-01' AND '2026-10-07' AND uid = 9527
GROUP BY province;

-- 反例：对分区键套了函数 → 优化器无法裁剪，扫全表
SELECT * FROM events WHERE DATE_FORMAT(dt, '%Y-%m') = '2026-10';
-- 改写成范围条件，裁剪才能生效
SELECT * FROM events WHERE dt >= '2026-10-01' AND dt < '2026-11-01';
要点：分区数不是越多越好。分区过多会让元数据膨胀、导入变慢、计划时间变长。日分区已经能满足绝大多数场景。

03分桶：选什么键、多少个

分桶的作用有两个：裁剪（点查命中单桶）和打散（聚合/JOIN 时并行度）。两者对键的要求是相反的——这决定了你必须先想清楚这张表主要怎么用。

目标该选什么键原因
点查裁剪（WHERE uid = ?）高频点查的那一列哈希后直接定位到一桶
聚合并行（GROUP BY uid）分组键同组数据落在同桶，可本地聚合
JOIN 性能两表的 JOIN 键（且桶数成倍数关系）可以做桶间本地 JOIN（Colocate / Shuffle 消除）
避免倾斜高基数的列低基数列会让某些桶特别大
  • 桶数经验起点：与集群的 CPU 核数、节点数有关，常见做法是取「节点数 × 单节点核数」的 1~2 倍量级，再按实测调整。
  • 不要用低基数列分桶：比如按「省份」分桶，北京上海那几个桶会明显偏大，成为长尾。
  • 不要用会变的列做分桶键：分桶键一般不可更新，改了就相当于搬数据。
  • 桶数改起来代价大：改桶数通常要重写整表，所以建表时就要想好。
  • 小表不要分太多桶：每个桶都有元数据与文件开销，小表分几十个桶是浪费。
要点：分桶是建表时就要定下来的决策，后期改代价很大。如果拿不准，宁可取稍大一点的桶数。

04排障：裁剪失效的六种常见写法

写法问题改成什么
WHERE DATE_FORMAT(dt,...) = ...对分区键套函数，优化器认不出改写成 dt >= x AND dt < y 的范围条件
WHERE dt = 20261001（整数 vs DATE）类型不一致触发隐式转换用与列类型一致的字面量
WHERE dt IN (...) OR province = ...OR 条件让裁剪无法下推拆成两条 SQL 用 UNION ALL
WHERE uid + 0 = 9527对分桶键做了运算直接写 uid = 9527
WHERE uid = CAST(? AS ...)（参数类型不定）预处理语句类型不确定导致转换绑定与列一致的类型
查询里根本没带分区键没有可裁剪依据确认业务是否允许补上时间范围
-- 确认裁剪是否生效：看执行计划里的分区/桶数量
EXPLAIN SELECT province, SUM(amount) FROM events
WHERE dt BETWEEN '2026-10-01' AND '2026-10-07' AND uid = 9527
GROUP BY province;

-- 重点看这几项：
--   partitions    命中的分区数（远小于总分区数 → 分区裁剪生效）
--   桶/tablet 数   命中的桶数（=1 说明分桶裁剪生效）
--   扫描行数       估算与实际是否相差一个数量级以上（差太多通常是统计信息过期）

-- 统计信息过期也是「看起来没裁剪」的常见原因
ANALYZE TABLE events;    -- 或对应产品的统计信息收集命令

05常见疑问

问：分区和索引是一回事吗？

不是。分区是物理目录的切分（数据本身就分开存放），索引是额外的查找结构。分区裁剪是「根本不打开那个目录」，比索引过滤更彻底、成本更低。

问：为什么我按天分区了，查询还是很慢？

按顺序排查：① 查询条件里有没有带分区键？② 带了但是不是套了函数/类型不匹配？③ 分区裁剪生效了，但分桶键没命中（扫了整个分区的全部桶）？④ 两层都生效但块级没裁剪（排序键与过滤条件不匹配）？用 EXPLAIN 逐层确认。

问：分桶键和排序键该选同一列吗？

看场景。同一列 → 该列的过滤与聚合都最优，但其他列就完全无裁剪。一般分桶键选点查/JOIN 列，排序键选范围过滤列，两者分开覆盖不同的查询模式。

问：桶数设错了能改吗？

能，但代价大（通常要重写整表）。所以建表前用「节点数 × 核数」估一个量级，上线后看桶的大小是否均衡（单桶过大或过小都说明桶数不合适）。

验证：裁剪到底有没有生效

「以为生效」和「真的生效」之间只差一个 EXPLAIN。判据很明确：执行计划里必须出现分区过滤（PartitionFilters / PartitionCount）且数量远小于总分区数。

ClickHouse：量化扫描比例

-- ClickHouse：跑完后看实际读了多少行/多少字节（最硬的证据）
SELECT query_duration_ms, read_rows, read_bytes,
       formatReadableSize(read_bytes) AS readable,
       round(read_rows / greatest(total_rows_approx, 1), 4) AS ratio
FROM system.query_log
WHERE type = 'QueryFinish' AND has(tables, 'default.events')
ORDER BY event_time DESC
LIMIT 5;

裁剪失效最常见的三个写法：① 对分区列套函数（substr(dt,1,7)）；② 分区列参与运算（dt + 1 > x）；③ 类型不匹配导致隐式转换（字符串分区列与数字比较）。改回直接比较即可。

分桶怎么定 + 上线检查清单

分区解决「扫多少目录」，分桶解决「目录内怎么切、join 怎么对齐」。分桶定错了，要么小文件爆炸，要么并行度上不去。

决策项怎么定典型取值定错的后果
分区粒度按查询最常见的过滤跨度天（日志）/ 月（归档）太细：小文件多、元数据膨胀；太粗：裁剪没收益
分区键WHERE 里出现频率最高且基数适中dt、region选错键等于不裁剪
分桶键join key 或高基数的 group by 键user_id、order_id选低基数列会严重倾斜
分桶数集群 executor 核数的整数倍核数 × 1~3，且每桶 128MB~1GB太多：小文件；太少：并行度不足
排序键过滤 + 排序最常用的列组合分区内再按时间排没有排序则 min/max 索引失效

Spark：分桶表与验证

-- Spark：写分桶表（桶数固定后不能轻易改，先算好）
CREATE TABLE events_bucketed (
    uid BIGINT, dt STRING, amt DECIMAL(18,2)
) USING parquet
PARTITIONED BY (dt)
CLUSTERED BY (uid) SORTED BY (uid) INTO 64 BUCKETS;

-- 写入时必须显式分桶，否则只是普通表
INSERT OVERWRITE TABLE events_bucketed PARTITION (dt='2026-10-01')
SELECT uid, amt FROM src WHERE dt='2026-10-01'
CLUSTER BY uid;

-- 启用桶 join（两表桶数相同或成倍数关系才有意义）
SET spark.sql.autoBroadcastJoinThreshold = -1;   -- 关掉广播强制走 shuffle/bucket join
SET spark.sql.sources.bucketing.enabled = true;

-- 检查小文件情况
SELECT dt, count(*) AS files, round(avg(size)/1048576, 2) AS avg_mb
FROM (SELECT dt, input_file_name() AS f, length(f) AS size FROM events_bucketed WHERE dt='2026-10-01') t
GROUP BY dt;

上线前逐条确认：

  • 用 EXPLAIN 确认裁剪生效，而不是凭经验判断——这是唯一可靠的判据。
  • 分区列不要套函数或做运算，否则优化器无法把过滤条件下推。
  • 分区数控制在万级以内：Hive Metastore 在分区数上十万时元数据操作会明显变慢。
  • 单分区文件大小 ≥ 128MB（HDFS 块大小量级），小于 32MB 就应当合并。
  • 分桶数 = 核数整数倍，且能整除未来的扩容规模（如 64 → 128）。
  • 分桶键必须是高基数列，用性别、状态这类低基数列会造成严重倾斜。
  • 两表 join 要桶数成倍数关系才能走 bucket join，否则退化成 shuffle。
  • 统计信息要定期更新：Hive/Spark 的代价估计依赖它，过期会导致选错计划。
  • 归档分区单独处理：冷分区压缩 + 合并小文件，别和热分区用同一套参数。
