①结论先行：你说的「HTTP 协议」其实混了两层东西

很多人问「HTTP 有哪些协议，SSE 和 Chunked 有啥区别」——这个问法本身就把两个不同层次的机制摆在了同一个擂台上。Chunked 是传输编码（怎么把不定长的 body 分片发出去），SSE 是应用层事件协议（在流式连接上怎么把数据组织成一条条事件）。它们不是同一种东西，更不是二选一：SSE 几乎总是「跑在」Chunked 之上的。
一句话回答你的三个问题：
① 「HTTP 有哪些协议」：HTTP 本身是一个应用层协议；但人们常说的「流式»相关机制」是——Chunked（传输编码）、SSE（事件协议）、WebSocket（独立全双工协议）、gRPC streaming（基于 HTTP/2 的 RPC 流式）、长轮询（伪流式）、multipart/x-mixed-replace（老式流式）。
② 「SSE 和 Chunked 都是啥」：Chunked = 分块传输（HTTP/1.1）；SSE = 服务端单向推送事件（建立在持久连接 + 通常为 chunked 之上）。
③ 「火山那个接口怎么流式返回的」：它不是 SSE，而是 POST + HTTP Chunked + 每个 chunk 是一个 JSON 对象（音频以 base64 放在 data 字段里），服务端边合成边用 chunk 推出去，客户端读流逐段解码播放。详见 ⑦。

②HTTP 家族里和「流式 / 推送」相关的机制全景

先把层次理清楚。从下到上，一条「流式返回」通常横跨三层：TCP（字节流） → HTTP 传输（是否分块、是否多路复用） → 应用消息格式（事件 / JSON / 帧）。下面这张图把常见机制按「层次 + 通信方向」归了位：

普通 HTTP 请求-响应 Content-Length / chunked 都行 Chunked + 自定义 JSON 流 如火山 TTS（单向、自己解析） SSE（单向推送） text/event-stream，建立在 chunked 上 WebSocket（双向） Upgrade 后独立帧协议 gRPC streaming（双向） 基于 HTTP/2 DATA 帧 长轮询 / multipart/x-mixed-replace（伪流式，已较少用）
图 1 · 红色虚线标出「Chunked 作为底层传输，支撑了上层 SSE 与自定义 JSON 流」

普通 HTTP（请求-响应）

一问一答，响应体可整段发（Content-Length）也可分块（chunked）。「流式」指的是分块，但语义上仍是一次性答完。

Chunked（传输编码）

HTTP/1.1 的 Transfer-Encoding: chunked，解决「不知道总长也能边产边发」。本身不定义消息边界。

SSE（事件协议）

W3C/WHATWG 标准，text/event-stream，单向（server→client），浏览器原生 EventSource 自动解析与重连。

WebSocket（全双工）

借 HTTP 握手升级后，变成独立双向帧协议，客户端也能随时发。适合聊天、协同。

gRPC streaming

基于 HTTP/2，强类型、跨语言，server/client/bidirectional 三种流式。适合微服务内部。

长轮询 / multipart

伪流式：长轮询是「服务器憋住响应直到有数据」；multipart/x-mixed-replace 是老式逐帧替换（如 MJPEG）。

③Chunked 是什么：只是「把 body 分片发出去」

Chunked（分块传输编码）是 HTTP/1.1 的 Transfer-Encoding 机制。当一个响应的总长度在写完之前还不知道（比如流式生成、边查库边返回），服务端就不能提前写 Content-Length，于是改用 chunked：把 body 切成若干块，每块前面带一个十六进制长度，最后用长度为 0 的块表示结束。

报文长什么样

HTTP/1.1 200 OK
Content-Type: application/json
Transfer-Encoding: chunked     # 关键：不写 Content-Length

1a                          # 第一块长度 = 26 字节（十六进制）
{"data":"UklGRiQAAA..."}  # 第一块数据
c                          # 第二块长度 = 12 字节
{"usage":1}              # 第二块数据
0                           # 长度为 0 的块 = 结束标志
                            # 后面跟一个空行
关键点： ① Chunked 只解决「不定长 body 怎么边生成边发送」，它不定义「一条业务消息在哪结束」——两个 chunk 之间只是字节边界，没有语义边界。
② Chunked 是 HTTP/1.1 专属概念。HTTP/2 用原生的 DATA 帧做流式分片，不再使用 Transfer-Encoding: chunked（HTTP/2 里该头会被禁止）。
③ 服务端就算用了 chunked，也可能等全部数据生成完再一次性 flush——那样虽然「分了块」，但并没有「边生成边推」。真正的流式 = chunked（或 HTTP/2 帧）且服务端一边产生一边写 socket。
常见误解：「Chunked 就是流式推送」
不对。Chunked 是传输层面的分块能力；是否「边生成边推」取决于服务端是否边产边写。一个用 chunked 但先 buffer 完整响应再 flush 的接口，对客户端而言仍然是一条「等很久才到」的响应，谈不上实时流。

④SSE 是什么：在流式连接上组织「一条条事件」

SSE（Server-Sent Events，服务端推送事件）是 HTML5/WHATWG 标准。它建立在一条保持打开的 HTTP 连接之上（通常是 HTTP/1.1 的 chunked 持久连接，或 HTTP/2 流），用一种固定的文本格式把数据组织成事件，每条事件以空行 \n\n 分隔。

响应头与消息格式

HTTP/1.1 200 OK
Content-Type: text/event-stream   # 必须是这个 MIME
Cache-Control: no-cache
Connection: keep-alive
# 底层通常用 Transfer-Encoding: chunked 来一块块推

# 一条事件：字段 + 空行
event: message
data: 你好，这是第一段
id: 1

data: 这是第二段（多行 data 会拼成一个字段）
data: 续行内容

event: done
data: {"total":2}

字段

data: 事件负载（可多行拼接）；event: 事件类型；id: 事件 ID（断线续传用）；retry: 重连毫秒数。

方向

单向：只能 server→client。客户端想发消息得另开一条请求（或用 WebSocket）。

浏览器 API

原生 EventSource：自动解析 text/event-stream、自动重连、按 event 名分发 onmessage。

底层是啥

SSE 的「传输」在 HTTP/1.1 下就是 chunked，在 HTTP/2 下是 DATA 帧。SSE 是上层协议，chunked 是它脚下的鞋。

两个容易踩的坑： ① 浏览器原生 EventSource 只支持 GET，不支持 POST。所以凡是 POST 触发的流式（比如带 JSON body 的语音合成），不能用 EventSource，只能自己用 fetch + 读 response.body 流来解析（见 ⑧）。
② SSE 要求服务端绝对不能设置 Content-Length，且保持连接打开；否则 EventSource 会以为响应结束了。

⑤SSE vs Chunked：核心区别对照

维度Chunked（分块传输编码）SSE（服务端推送事件）
所在层次HTTP 传输层（怎么把 body 分片）应用层事件协议（怎么组织消息）
它定义什么每块的长度前缀 hex\r\n数据\r\n 与结束块 0\r\n\r\n事件字段 data:/event:/id: + \n\n 作为消息边界
消息边界无（只有字节/chunk 边界，无业务语义）有（每个 \n\n 是一条完整事件）

⑥关键澄清：SSE 和 Chunked 不是「二选一」

这是整个问题里最大的误区。SSE 和 Chunked 不是同一层的替代品，而是上下层搭档。正确的提问方式不是「用 SSE 还是用 Chunked」，而是：「我要不要 server→client 的单向事件推送？要 → 用 SSE（它自动踩在 chunked 上）；不要事件格式、只想自己流式吐任意数据 → 直接用 chunked + 你自己的消息格式」。

只用 Chunked（不要 SSE）

比如「流式返回一个大 JSON / 一段音频 / 一段日志」，客户端自己按 chunk 边界或换行累积解析。火山 TTS 就是这种（见 ⑦）。灵活，但重连、事件分发要自己写。

只在 SSE 上发事件

服务端返回 text/event-stream，浏览器 EventSource 自动按 \n\n 切事件、自动重连。省客户端代码，但只能 GET、只能文本、只能单向。

两者都「用」

SSE 运行时底层就是 chunked——你写 SSE 时同时在用 chunked，只是不用自己管分块细节。所以它们从不互斥。

类比
Chunked 像「快递一箱一箱地发，每箱贴了重量标签」；SSE 像「每箱里的零件还贴了序号和名称，按序号拼起来就是一件成品」。你可以只要「一箱一箱发」（裸 chunked），也可以在箱里再贴序号（SSE）。后者天然包含前者。

⑦实战：火山引擎单向流式 TTS 是怎么流式返回的

以你给的文档（单向流式语音合成 HTTP）为例。接口地址 POST https://openspeech.bytedance.com/api/v3/tts/unidirectional。文档原文写得很清楚：「基于 HTTP Chunked 协议的单向流式合成接口」。

先给结论：它既不是 SSE，也不是 WebSocket——它是 POST + HTTP Chunked + 每个 chunk 是一个 JSON 对象。服务端一边用大模型合成音频，一边把每段音频 base64 编码塞进 data 字段，用 chunked 一个 chunk 一个 chunk 推出来；客户端读流，每收一个 chunk 就解析这个 JSON、把 data 解码成音频片段，边收边送播放器，实现「字还没读完，声音已经出来了」。

请求（Header + Body）

# 请求头
POST /api/v3/tts/unidirectional HTTP/1.1
Host: openspeech.bytedance.com
X-Api-Key: <你的 API Key>
X-Api-Resource-Id: seed-tts-2.0
X-Api-Request-Id: 9f1c2e3a-...   # uuid，标识本次请求
Content-Type: application/json

# 请求体（一次性输入整段文本）
{
  "req_params": {
    "text": "今天天气真好，我们去散步吧",
    "speaker": "zh_female_xxx",
    "audio_params": { "format": "mp3", "sample_rate": 24000 }
  }
}

响应：分块 + 每个 chunk 一个 JSON

响应头大致是 Transfer-Encoding: chunked（因为是 HTTP/1.1 流式）。响应体被切成多个 chunk，每个 chunk 是一个完整的 JSON 对象，关键字段来自文档的「响应参数」：

# 中间若干 chunk：每段音频
{"code":0, "message":"OK",
 "data":"UklGRiQAAABXQVZFZm10IBAAAA...",   # 本段音频，base64（mp3/wav）
 "audio_info":"{\"sample_rate\":24000,\"format\":\"mp3\"}",
 "logid":"20260922xxxx"}

# 末尾 chunk：带用量统计，表示合成结束
{"code":0, "message":"OK",
 "usage":{"text_words":12}}     # 计费字数，也充当「结束」信号
为什么它「不是 SSE」？因为响应 MIME 不是 text/event-stream，也没有 data: / event: / \n\n 那套事件格式；它只是「chunked 传输 + 裸 JSON 流」。而且它是 POST 触发——浏览器 EventSource 不支持 POST，所以客户端必须用 fetch 读流（见 ⑧）。这恰好印证了 ⑥：流式返回 ≠ SSE，SSE 只是流式的一种「带事件格式的上层封装」。
图 3 · 单向、无事件格式、chunked 承载裸 JSON：这就是火山 TTS 的流式形态
本地用 curl 验证流式：加 -N（禁用缓冲，等价于 --no-buffer）才能看到「一段一段蹦出来」，否则 curl 会攒够了再打印：
curl -N -X POST https://openspeech.bytedance.com/api/v3/tts/unidirectional -H "X-Api-Key: xxx" -H "Content-Type: application/json" -d '{"req_params":{"text":"你好","speaker":"..."}}'

⑧怎么解析服务端返回：不同格式、不同解析

先说一个最容易被坑的前提：当你用 fetch 读流时，你拿到的字节流已经是「去除了 chunk 长度前缀」的。浏览器 / HTTP 客户端库在把 body 交给你之前，早已把 1a\r\n{...}\r\n0\r\n\r\n 这层「传输帧」拆掉了。所以——你要解析的永远是「应用层消息格式」，而不是 chunk 帧。各种流式协议「解析上的区别」，本质上只在于应用层用什么方式定「一条消息在哪结束」。
图 4 · 同样一份 chunked 流，应用层可以是裸 JSON、SSE、也可以是长度前缀——解析器面对的是不同边界规则

五种常见返回格式：边界规则对照

返回格式「一条消息」的边界怎么定解析器要维护的状态半包怎么处理典型场景
行分隔 JSON
（NDJSON）		每行一条 JSON，以 \n 分隔暂存「半行」的字符串缓冲不足一行先攒，下次拼火山 TTS、日志流、LLM 增量结果
SSE 事件流事件以空行 \n\n 分隔；行内 field: value半事件缓冲 + 当前事件的字段累加器不足 \n\n 先攒进度推送、通知、token 流
长度前缀
（二进制 / protobuf）		头部固定 N 字节声明本消息长度已读字节数 / 状态机（len→payload）不足长度先攒，等齐再切自定义二进制、gRPC-web

半包是流式解析唯一的「共性难题」：一次 read() 返回的网络字节，常常把一条消息从中间切断（比如 JSON 只来了半行、长度前缀只来了 3 字节）。所有流式解析器都必须有一个跨 read 的缓冲区和「边界检测」——区别只是边界在哪儿（换行 / 空行 / 长度）。下面五段逐一带解析代码。

① 行分隔 JSON（NDJSON，如火山 TTS）—— 按 \n 切，半行留在缓冲

const res = await fetch('/api/v3/tts/unidirectional', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ req_params: { text: '你好', speaker: '...' } })
});
const reader = res.body.getReader();
const dec = new TextDecoder('utf-8');
let buf = '';                      // 跨多次 read 的「半行」缓冲

while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  buf += dec.decode(value, { stream: true });

  // 按换行切出「完整的一行」；最后一行若没读完，留在 buf 里下次再拼
  let i;
  while ((i = buf.indexOf('\n')) >= 0) {
    const line = buf.slice(0, i).trim();
    buf = buf.slice(i + 1);
    if (!line) continue;             // 空行跳过（有的服务用空行当分隔）
    try {
      const obj = JSON.parse(line);
      if (obj.data) playAudio(atob(obj.data));    // 逐段 base64 解码 → 播放
      if (obj.usage) console.log('合成结束', obj.usage);
    } catch (e) {
      console.warn('非 JSON 行，丢弃', line);
    }
  }
}
if (buf.trim()) { /* 连接结束时 buf 里若还剩半行，按业务决定丢弃或补解析 */ }

② SSE 事件流（POST 触发、EventSource 用不了时，用 fetch 手动解析）—— 按 \n\n 切事件

// 适用：POST 触发、不能用 EventSource 时，自己解析 text/event-stream
const res = await fetch('/api/sse-proxy', { method: 'POST', body });
const reader = res.body.getReader();
const dec = new TextDecoder('utf-8');
let buf = '';                      // 跨多次 read 的「半事件」缓冲

while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  buf += dec.decode(value, { stream: true });

  let i;
  while ((i = buf.indexOf('\n\n')) >= 0) {     // 事件以空行分隔
    const raw = buf.slice(0, i);
    buf = buf.slice(i + 2);
    const ev = {};
    for (const line of raw.split('\n')) {
      if (!line || line.startsWith(':')) continue;   // 注释行以 : 开头
      const ci = line.indexOf(':');
      const field = ci === -1 ? line : line.slice(0, ci);
      const val = ci === -1 ? '' : line.slice(ci + 1).replace(/^ /, '');
      if (field === 'data') ev.data = (ev.data ? ev.data + '\n' : '') + val;
      else ev[field] = val;
    }
    if (ev.event) dispatch(ev.event, ev);
    else if (ev.data !== undefined) onmessage(ev.data);
  }
}

③ 长度前缀（二进制 / protobuf 流）—— 先读 N 字节长度，再读 N 字节载荷

// 适用：自定义二进制协议 / protobuf 流，每条消息前挂 N 字节长度
const res = await fetch('/api/bin', { method: 'POST', body });
const reader = res.body.getReader();
let buf = new Uint8Array(0);

const append = (c) => {                       // 拼到尾部
  const n = new Uint8Array(buf.length + c.length);
  n.set(buf); n.set(c, buf.length); buf = n;
};
const consume = (k) => { buf = buf.slice(k); };   // 丢弃前 k 字节

while (true) {
  const { value, done } = await reader.read();
  if (value) append(value);
  while (buf.length >= 4) {                       // 至少有 4 字节长度前缀
    const len = new DataView(buf.buffer, buf.byteOffset).getUint32(0);  // 大端 4 字节
    if (buf.length < 4 + len) break;              // 载荷还没收齐，等下次
    const payload = buf.slice(4, 4 + len);
    handle(payload);                            // 一条完整消息
    consume(4 + len);
  }
  if (done) break;
}

④ WebSocket —— 浏览器已去帧，onmessage 直接拿到完整消息

// 浏览器 WebSocket：帧已被浏览器解析，onmessage 直接拿到完整消息
const ws = new WebSocket('wss://host/api');
ws.onmessage = (e) => {
  // e.data 已经是去帧后的完整应用消息（字符串 / Blob / ArrayBuffer）
  handle(e.data);
  // 想发消息：ws.send(...) —— 浏览器自动加帧
};

// 只有「自己实现 WS 服务端 / 网关 / 解析原始 TCP」才需要手解帧：
//   首字节 = FIN(1) + RSV(3) + opcode(4)
//   次字节 = MASK(1) + payload-len(7)；len=126/127 时再读 2/8 字节扩展长度
//   客户端发往服务端必须掩码（mask），服务端发往客户端不掩码

⑤ gRPC（HTTP/2）—— 每条消息前缀 [1 标志][4 长度]，其后才是 protobuf

// gRPC：HTTP/2 DATA 帧里，每条消息前缀 [1 字节 compressed][4 字节长度]，其后才是 protobuf
// 浏览器无原生 gRPC 客户端，通常 grpc-web 转一道；这里给「流式字节」的解析思路
const res = await fetch('/api/grpc-stream', { method: 'POST', headers: { 'Content-Type': 'application/grpc' }, body });
const reader = res.body.getReader();
let buf = new Uint8Array(0);
const append = (c) => { const n = new Uint8Array(buf.length + c.length); n.set(buf); n.set(c, buf.length); buf = n; };

while (true) {
  const { value, done } = await reader.read();
  if (value) append(value);
  while (buf.length >= 5) {                       // 1 字节标志 + 4 字节长度
    const compressed = buf[0];                     // 0=未压缩 1=grpc 编码
    const len = new DataView(buf.buffer, buf.byteOffset).getUint32(1);
    if (buf.length < 5 + len) break;
    const msg = buf.slice(5, 5 + len);
    handleProtobuf(msg);                          // 交给 protobuf 运行时反序列化
    buf = buf.slice(5 + len);
  }
  if (done) break;
}
对比一句话： · NDJSON / SSE 用「文本分隔符」定边界（\n / \n\n），解析器维护字符串缓冲 + 按分隔符切；
· 长度前缀 / gRPC 用「二进制长度头」定边界，解析器维护字节缓冲 + 状态机（先读长度再读载荷）；
· WebSocket 的边界由帧定义，而浏览器已帮你去帧，所以你几乎不用写解析；
· SSE 用 EventSource 时连分隔符解析都免了，只有 POST 触发才需要 ② 那样手动解。核心差异一句话：边界规则不同，但「缓冲 + 等齐一条再处理」的套路完全一致。

⑨交互：你到底该选哪种「流式」

回答下面几个问题，实时得到推荐方案：

通信方向 单向（server→client） 双向（也要客户端发）
触发方式 GET 即可 需要 POST / 带大 body
是否要浏览器自动重连 要（断线续传） 不要 / 自己管
是否跨语言强类型 RPC 否（前端 / REST） 是（微服务间）

⑩误区与选型速记

误区一：「SSE 和 Chunked 选一个用」
错。Chunked 是传输编码（HTTP/1.1 下层），SSE 是建立在它之上的事件协议。SSE 运行时底层就是 chunked。正确问法：「要不要事件格式？要→SSE；不要、自己吐数据→chunked + 自定义格式」。
误区二：「流式返回 = SSE」
不对。流式只是「响应体边生成边推」，可以由 chunked（裸数据）、SSE（事件）、WebSocket（帧）、gRPC（HTTP/2 帧）等多种方式承载。火山 TTS 是 POST + chunked + 裸 JSON，连 SSE 都不是。
误区三：「Chunked 就一定实时」
不一定。Chunked 只是分块能力；服务端若先 buffer 完整响应再 flush，客户端仍要等很久。实时 = chunked/帧 且 服务端边产边写。
误区四：「EventSource 能发 POST」
不能。浏览器原生 EventSource 仅支持 GET。POST 触发的流式必须用 fetch + ReadableStream 自己解析。
误区五：「HTTP/2 也用 chunked」
不用。HTTP/2 用原生 DATA 帧做流式，明确禁止 Transfer-Encoding: chunked。SSE 跑在 HTTP/2 上时，传输层换成帧，应用层 text/event-stream 格式不变。

一句话速记

HTTP 流式 = 传输分块 + 应用消息格式，两层叠加。
· Chunked：HTTP/1.1 的传输编码，解决「不定长也能边发边推」，无消息边界；HTTP/2 下被帧取代。
· SSE：单向事件协议（text/event-stream + data:/\\n\\n），跑在 chunked 之上，浏览器 EventSource 自动解析重连，仅 GET。
· WebSocket：借 HTTP 握手升级后的独立双向帧协议。
· gRPC streaming：基于 HTTP/2 的跨语言强类型流式 RPC。
· 火山 TTS：POST + chunked + 每个 chunk 一个 JSON（data 为 base64 音频）——裸 chunked 流，不是 SSE。
