先建立直觉：关系数据库 vs 图数据库

同样表示「张三认识李四」，两种数据库做法完全不同：

  • 关系数据库：把「认识」存成一行记录，查「张三的朋友的朋友」需要两次 JOIN（先查朋友，再 JOIN 查他们各自的朋友）。随着层数增加，JOIN 的代价指数增长。
  • 图数据库：张三节点上直接存着指向李四的指针。查「朋友的朋友」就是顺着指针走两步——每走一步的代价是常数，与全库数据量无关。
这个差异叫 Index-free Adjacency（无索引邻接），是图数据库高性能的根本原因。它不是「图数据库做了更好的索引」，而是根本不需要索引——邻接关系直接编码在存储结构里。

属性图模型的四个要素

要素说明示例
节点 Node表示实体(n:Person {name:'张三'})
标签 Label节点分类，一个节点可有多个标签:Person、:Actor
关系 Relationship连接两个节点，必须有类型和方向-[:KNOWS]->
属性 Property节点和关系都可带键值对{since: 2019}
关系必须有方向，但查询可以忽略方向。存储上关系总是有方向的（从 a 指向 b），但 Cypher 里可以写 -[:KNOWS]-（不带箭头）表示双向匹配。设计时应按业务语义的自然方向建模，查询时按需忽略。

Index-free Adjacency：为什么快

建模的四个原则

  1. 以关系为中心：把业务里需要反复遍历的连接显式建成关系，而不是塞进某个 JSON 字段里（否则又回到了 JOIN 的老路）。
  2. 用标签做分类：比给节点加一个 type=... 属性更好——标签上可以建索引，查询更快也更清晰。
  3. 关系也可以带属性：如「认识多久」「购买金额」。这往往比再建一个中间节点更简洁。
  4. 避免过度建模：不是所有东西都要变成节点。像「性别」「状态」这种低基数、不需要遍历的值，作为属性即可。
判断「该做节点还是属性」的经验法则：如果这个东西需要被独立查询、需要被多个实体共享、或者本身有复杂属性→ 做成节点；如果只是描述性的、不需要单独遍历的标签值→ 做成属性。

什么时候不该用图数据库

  • ❌ 主要是聚合统计（按地区求和、按时间分组）——关系型或 OLAP 引擎更合适；
  • ❌ 大量批量更新——图数据库的优势在于遍历，不在于批量写入；
  • ❌ 数据结构非常扁平、关系很少——用图是杀鸡用牛刀，还增加了运维复杂度。

🎯 面试问答

Q：Neo4j 的关系一定要有方向吗？
A：存储上一定有方向（每条关系都从起始节点指向终止节点），但查询时可以忽略方向——Cypher 里写 -[:KNOWS]-（不带箭头）就是双向匹配。建模时应按业务语义的自然方向来定义（如「张三 认识 李四」而非反过来），这会让查询更直观；需要反向查询时用无方向语法即可。

Q：什么是 Index-free Adjacency？
A：「无索引邻接」——每个节点直接在存储层持有指向相邻节点的物理指针，遍历时顺着指针走即可，不需要在运行时做表连接或索引查找。这带来的关键性质是：遍历代价只与「邻居数量」相关，与「全库数据量」无关。所以查三度人脉在 100 万节点和 1 亿节点的库里耗时接近，这正是图数据库相对关系数据库在多层关系查询上的数量级优势。

Q：什么时候该把东西建成节点，什么时候建成属性？
A：看它是否需要被独立遍历和共享。做成节点：需要独立查询、被多个实体引用、本身有复杂属性（如「公司」「城市」）。做成属性：纯描述性、低基数、不需要单独遍历（如「性别」「状态」「颜色」）。误判的典型后果：把本该是节点的东西做成属性，之后要按它做关联查询时，就退化成了全图扫描。

Q：图数据库能替代关系数据库吗？
A：不能，二者定位不同。图数据库擅长多跳关系遍历（社交网络、风控链路、路径规划），但不擅长大规模聚合统计和批量更新。关系数据库擅长结构化存储、事务、聚合查询，但多跳 JOIN 代价极高。实践中常共存：关系库存业务主数据，图库承载关系网络（通过 CDC 同步），各自发挥优势。
