一致性模型

"一致性"不是只有"强"和"弱"两档。从最强的线性一致到最弱的最终一致，中间有清晰谱系。搞清楚每个模型的"保证边界"，面试才能答到点子上。

一致性谱系 线性一致 顺序一致 因果一致 最终一致 如何选型 面试要点

📊一致性谱系（由强到弱）

🧭
核心直觉：一致性越强 = 各副本表现得"像单机"；越弱 = 允许短暂分歧，换更高可用与性能。没有"最好"，只有"最合适"。

🎯线性一致（Linearizability）

最强的一致性。要求：每个操作都像在"全局同一时刻"原子完成，且结果对所有观察者立即可见、符合真实时间顺序。

判定标准：若操作 A 在真实时间上先于 B 完成，则所有节点都必须表现出"A 先于 B"。读一定能读到"最新一次写"。
✅
实现代价：通常需要"全局唯一序列/共识"（如 Raft 单 Leader 串行 apply）。写入要经过共识，延迟高、吞吐受限。etc/d/ZK(可配置) 接近线性一致。
🩺
典型误用：把"线性一致"和"原子性"混为一谈。原子性＝事务要么全做要么不做；线性一致＝跨副本的"实时可见顺序"。两者正交。

🔢顺序一致（Sequential Consistency）

比线性一致弱：所有节点看到的操作顺序一致，且每个节点的操作保持自身程序顺序，但不必符合真实时间。

与线性一致的区别：线性一致要求"按真实时间"；顺序一致只要求"存在一个全局一致顺序"，不要求这个顺序等于真实时间顺序。
🐘
代表：ZooKeeper 提供的就是顺序一致性——客户端写按序生效、所有客户端看到相同顺序，但不保证"写完成那一瞬间"全局立即可见。

🔗因果一致（Causal Consistency）

再弱一档：有因果关系的操作必须保序，没有因果关系的可乱序（并发）。是个很好的"性价比"模型。

💡
适用：社交、协作编辑（如 Google Docs 的 OT/CRDT 思路）、评论系统——既保留"逻辑顺序"，又允许高并发，是最终一致与强一致之间的甜点。

🌊最终一致（Eventual Consistency）

最弱：没有读写顺序保证，但只要停止写入，经过一段时间所有副本会收敛到相同值。

代表：DNS、CDN、Cassandra（可调）、Redis 主从异步复制、各类缓存。性能最高、可用性最好，但"读到旧值"是常态。
✅
何时够用：只要业务能容忍"短暂旧数据"（如商品浏览量、排行榜、头像），最终一致就是最优解。配合"读己之写"等增强，体验几乎无差。

🧭如何选型

模型代价适用典型系统
线性一致高延迟、低吞吐锁、选主、账务核心etcd/Raft、ZK(可配)
顺序一致中协调、配置ZooKeeper
因果一致中低社交、协作社交平台、CRDT
最终一致低、高扩展缓存、统计、浏览DNS/Cassandra/Redis
⚖️
经验法则：核心链路用强一致（哪怕慢点），边缘/高并发用最终一致。一个系统往往是"混合一致性"——不同数据不同等级。

🎯面试要点速记

谱系：线性 → 顺序 → 因果 → 会话/单调 → 最终，由强到弱。
线性一致：全局原子+实时可见，代价最高；靠共识实现。
顺序一致：全局顺序一致但不管真实时间；ZK 即此。
因果一致：保因果顺序，并发可乱；社交协作甜点。
最终一致：停写后收敛；性能最好；缓存/统计场景。
选型：核心强一致，边缘最终一致，混合使用。
🔥
必考题："线性一致和最终一致的区别？"——线性一致＝所有副本像单机、读写实时有序（慢但准）；最终一致＝允许短暂分歧、停写后收敛（快但可能读到旧值）。结合 CAP 答更完整。

第一层 · 五种一致性的强度阶梯

一致性模型是一把从强到弱的阶梯。强度越低，性能越好、可用性越高，但对应用的要求也越高。选哪一级是分布式设计最核心的取舍。

模型保证什么性能代价典型实现应用感受
线性一致（Linearizable）等同于单机：任何读都能看到最近一次写入最高（每次要全局同步）Raft/ZooKeeper（写）、etcd最直观，像操作一个变量
顺序一致所有节点看到相同的操作顺序（但不必与真实时间一致）高分布式共享内存操作顺序全局一致
因果一致只保证有因果关系的操作顺序（并发操作可乱序）中COPS、部分 KV 存储不会出现「先看到回复后看到原文」
最终一致不保证顺序，只保证「最终」会收敛最低DNS、Cassandra、异步主从可能读到旧数据
读己所写自己写的自己一定能读到低（客户端级保证）会话一致性最常用的一条实用保证
  • 判断口诀：线性一致 = 全局只有一个「现在」。写完立刻读，一定能读到新值——无论是哪个节点处理这个读。这是唯一让分布式系统「看起来像单机」的模型。
  • 为什么最终一致最常用：因为它性能最好且容忍分区。代价是应用要能接受「读到旧数据」，且要解决冲突（后写覆盖、向量时钟等）。
  • 「读己所写」是最重要的实用保证：用户改了自己的昵称，刷新后必须看到新的（哪怕别人看到的还是旧的）。这条通常通过会话粘滞或写后读主库实现，成本很低。

判定与配置

# —— 一致性判定的经典例子（务必理解）——
# 场景：x 初值为 0
#   客户端 A 写 x=1，然后告诉客户端 B「我写完了」
#   客户端 B 读 x

# 线性一致：B 必须读到 1（因为写操作在【真实时间】上已经完成）
# 最终一致：B 可能读到 0（副本还没同步过来）  <- 这就是「不一致窗口」

# 场景：判断因果 vs 并发（向量时钟）
#   向量时钟：每个节点维护 [A:1, B:0, C:0] 这样的向量
#   比较规则：V1 <= V2 当且仅当 V1 的每个分量 <= V2
#     [1,0,0] <= [1,1,0]   -> 因果在前（V1 可能发生于 V2 之前）
#     [1,0,0] vs [0,1,0]   -> 【并发】（互不可比）-> 需要冲突解决
#     [2,0,0] vs [1,1,0]   -> 并发（A 的第二笔 vs B 的第一笔）

# —— Quorum 配置速查 ——
#   N=3:
#     W=2,R=2 -> 强一致（读写都过半数）【推荐】
#     W=1,R=3 -> 写快，读要读全部并取版本最新的
#     W=3,R=1 -> 写要全部确认（慢），读一个即可
#     W=1,R=1 -> 【不是强一致】，可能读到旧副本
#   N=5:
#     W=3,R=3 -> 强一致，容忍 2 副本故障

# —— 判定「读到的值是不是最新的」——
#   写入时返回【版本号/时间戳】；读取时带上版本号，
#   如果副本的版本 < 已知版本，就换一个副本读（或等同步）

最实用的一条工程经验：关键写入后立刻读的场景，直接读主库。这比任何复杂的 quorum 配置都简单可靠，代价只是主库的读压力。

第三层 · 排障清单

  • 「刚写完读不到」 → 读写分离架构下的经典问题。解法按成本递增：① 写完后的读走主库（最常用，如 1 秒内）；② 会话粘滞到主库；③ 用版本号/GTID 等待从库追上（MySQL 的 WAIT_FOR_EXECUTED_GTID_SET）；④ 上强一致存储。
  • 跨服务的数据不一致（A 服务看到新值，B 服务看到旧值） → 各服务用的存储副本不同。解法：统一数据源、或用消息队列保证顺序、或用对账定期修复。
  • 时钟偏差导致顺序错乱 → 用本地时间戳排序。解法：用逻辑时钟/版本号，或者用 TrueTime（Spanner 的做法，用 GPS + 原子钟把偏差压到 <10ms 并显式等待这个不确定性）。
  • 并发写入冲突（后写覆盖先写） → 最终一致系统的常见问题。解法：① 版本号 + CAS（乐观锁）；② 向量时钟检测并发冲突并交给应用/用户解决；③ CRDT（无冲突的数据结构，如计数器、集合）；④ 最后写入胜出（LWW，简单但会丢数据）。
  • 以为用了强一致其实没有 → 常见原因：W+R ≤ N；或者读的是本地缓存；或者用了异步复制却当同步用。要明确验证配置。
  • 链表式复制（A→B→C）延迟累积 → 链条越长，末端延迟越大。MySQL 5.7+ 支持并行复制缓解。
  • 缓存与数据库不一致 → 更新数据库后没删缓存，或删了缓存但数据库还没提交。顺序必须是：先提交数据库，再删缓存（反过来会有窗口期把旧值重新写入缓存）。
  • 对账发现不一致但不知道原因 → 说明缺少变更审计。关键数据要有「谁在什么时候改了什么」的记录（binlog/WAL 就是天然来源）。

第四层 · 原理与取舍

理解一致性只需要抓住一条主线：一致性强度 = 你能容忍多少「信息传播延迟」。线性一致要求传播延迟为零（不可能），最终一致允许任意延迟。

  • 为什么线性一致这么贵：因为它要求「任何读都能看到全局最近的写入」，这意味着读操作必须与写操作做全局同步（确认自己拿到的是最新的）。在分布式系统里，这需要至少一次往返通信（问 Leader 或问多数派）。所以线性一致的读延迟 = 一次 RTT，而且每次读都要——这就是为什么它性能差。
  • 租约（Lease）是如何优化的：Leader 在租约期内独占读权限。因为租约保证了「这段时间内不会有人能写」，所以 Leader 可以本地直接读而无需通信。这是用「时间假设」换「通信开销」的经典技巧——代价是依赖时钟（租约到期判断），且 Leader 故障时要等租约过期才能接管（影响故障切换时间）。
  • 因果一致为什么是好的折中：它只约束「有因果关系」的操作（如「回复」必须在「原文」之后），而允许并发操作乱序。这符合大多数应用的直觉，且不需要全局同步（只需传递因果依赖，用向量时钟即可）。代价是向量时钟的体积随节点数增长，且冲突需要应用层解决。
  • Spanner 的 TrueTime 是个例外：Google 用 GPS + 原子钟把时钟偏差压到 <10ms，然后在提交时显式等待这个不确定性窗口（commit wait）。这样它用「物理时钟 + 等待」实现了全球范围的外部一致性（比线性一致更强）——代价是每次写要等约 10ms。这是「用硬件解决分布式难题」的典型案例，普通公司做不到（没有原子钟）。

线性一致和串行化（Serializable）是一回事吗？

不是，这是两个不同维度的概念，非常容易混淆。线性一致是关于「单个对象」的实时性保证：它要求在真实时间上，读操作必须看到最近一次完成的写。它不关心事务、不关心多个对象。串行化是关于「事务」的隔离级别：它要求并发事务的执行效果等价于某种串行顺序。它不关心实时性——一个串行化的系统完全可以返回「稍旧但一致」的数据（只要存在一个合法的串行顺序）。两者组合出的最强保证是 Strict Serializability（严格串行化）= 串行化 + 线性一致，即「事务既等价于串行执行，又遵守实时顺序」。Spanner 提供的「外部一致性」大致就是这一级。实践意义：数据库的隔离级别（READ COMMITTED / REPEATABLE READ / SERIALIZABLE）讲的是串行化这一轴；而分布式副本的读写一致性讲的是线性一致这一轴。配置系统时要分别考虑，不要混为一谈。

「读己所写」为什么这么重要又这么便宜？

重要是因为它直接对应用户的主观体验：用户改了头像、发了评论、下了订单后刷新，必须看到自己的操作生效了。如果看到的是旧数据，用户会认为「系统坏了/我的操作丢了」，然后重复操作（下单点了两次）或者投诉。别人看到旧数据用户能容忍，自己看不到自己的操作是绝对不能容忍的。便宜是因为它只需要在单个用户维度做保证，不需要全局同步：① 最简单——写操作后的一小段时间（如 1~3 秒）内，该用户的读强制走主库；② 或者用会话粘滞（把用户绑定到某个副本）；③ 或者客户端记住自己最后写入的版本号，读的时候要求副本版本 ≥ 该版本号（否则换副本或等）。这三种方案都不需要跨节点协调，成本极低。所以工程上的标准做法是：用「读主库 + 版本号」满足读己所写，其余读全部走从库/缓存——用最低成本拿到最关键的保证。

最终一致系统怎么解决冲突？

四种主流方案，按复杂度递增：① LWW（最后写入胜出）——用时间戳取最新的，简单但会静默丢数据（两个并发写，一个被扔掉），适合能接受丢失的场景（如最后一次登录时间）；② 版本向量 + 暴露冲突——检测到并发写时，把两个版本都保留，交给应用层或用户决定（如 Git 的合并冲突、CouchDB 的 _conflicts）。这是数据最安全的做法，但要求应用能处理多版本；③ CRDT（无冲突复制数据类型）——设计特殊的数据结构，使得任何顺序的合并都得到相同结果（如计数器用 G-Counter、集合用 OR-Set）。这是数学上最优雅的方案，无需协调就能收敛，但只适用于特定数据类型（不是所有业务都能建模成 CRDT）；④ 应用层语义合并——根据业务规则合并（如购物车取并集、库存取最小值）。实践建议：先想清楚「冲突真的会发生吗」——很多场景按用户/租户分区后，同一个数据只会被一个写者修改，根本不会冲突。真的会冲突时，优先选②（暴露冲突，让用户/业务决定），因为它不会静默丢数据。

分布式系统 · 一致性模型 — 线性 / 顺序 / 因果 / 最终 | 面试核心图解

核心速览

一句话一致性模型是「系统对读写顺序的承诺」，越强越容易写对程序，代价越高
最强线性一致 Linearizability：看起来像只有一份数据、只有一个副本
最弱最终一致：只要不再写入，副本终会收敛
工程常见顺序一致、因果一致、读己之所写、单调读
一致性强度从强到弱：越往上越像单机，越往下越便宜

一、六种常见模型对照

模型承诺典型实现代价
线性一致操作在某个瞬间原子生效，且符合真实时间顺序Raft/Paxos 的读走主或读索引最高，每次都要多数派
顺序一致所有进程看到相同的操作顺序，但顺序可与真实时间不同全局排序广播高
因果一致有因果（先读后写、先后发生）的操作按因果序被看到向量时钟、因果广播中
读己之所写自己写的值，自己一定能立刻读到写后把读路由到主/会话粘滞低
单调读不会读到比上次更旧的值会话内固定读同一副本低
最终一致停止写入后，副本终会一致异步复制 + 冲突解决最低
线性一致 vs 可串行化：名字像但不是一回事

线性一致描述的是单个对象、实时顺序的保证；可串行化描述的是事务——多个对象的多个操作等价于某种串行执行。一个系统可以同时具备两者（严格可串行化），也可以只具备其一。

二、会话一致性：最终一致系统的救命稻草

很多系统的底层是最终一致的，但对用户体验来说「读到自己刚写的东西」是刚需。这类保证被称为会话一致性，实现成本远低于全局线性一致：

读己之所写写后一段时间内读主库，或带上写入版本号让副本等待追上
单调读同一用户固定路由到同一副本（粘滞会话）
单调写同一用户的写操作串行化到同一节点
写后读写入成功后返回新版本号，读时校验副本是否已追上

三、代价：为什么不能全都线性一致

维度线性一致最终一致
延迟每次写要等多数派确认，跨地域时是几十到几百毫秒本地写本地返回
可用性网络分区时少数派不可用（CAP 中的 C 优先）分区期间仍可读写（A 优先）
吞吐受限于共识组可水平扩展
编程难度低，像写单机程序高，要处理冲突与陈旧读

CAP 的正确表述常被误传。准确说法是：在网络分区（P）发生时，系统只能在一致性（C）和可用性（A）之间选一个。没有分区时，绝大多数系统两者都能提供。

四、实践中的选择

账号、余额、库存强一致（线性一致或可串行化）
配置、元数据、选主强一致
社交动态、评论、点赞数最终一致 + 读己之所写
商品详情页、缓存最终一致，容忍秒级延迟
搜索索引最终一致，定期重建
日志、监控数据最终一致即可

五、深入自检

最终一致是不是「不一致」？

在有新写入的时间段内，副本之间确实可能不同。关键是要有收敛保证：冲突怎么解（最后写入胜出、版本号、CRDT、人工介入）。没有明确冲突解决策略的最终一致，才是真的不安全。

读主库能保证线性一致吗？

不一定。Raft 这类系统里，主节点可能因网络分区而被孤立，旧主仍会自认为是主。正确做法是用 ReadIndex 或 Lease Read：读之前先确认自己的主身份依然有效。

为什么有时读到的数据会「回到过去」？

因为你的读被路由到了不同的副本。客户端先读了新副本、后读了旧副本，就会出现单调读违例。解决办法是会话内绑定副本，或者携带版本号让落后的副本先追上。

CRDT 是什么，什么时候用？

冲突无关数据类型：通过数学性质保证「任意顺序合并都能收敛到同一结果」。适合计数器、集合、协作编辑这类可交换合并的场景；不适合有全局约束的操作（如库存不能为负）。

时钟能用来判断先后吗？

物理时钟不可靠（有漂移、有 NTP 回拨），不能用于判断因果。判断因果要用逻辑时钟（Lamport 时钟只给全序，向量时钟能判断并发）。

记住一句一致性是系统对读写顺序的承诺
最强线性一致（像单机）
最实用最终一致 + 会话保证
CAP 正解分区发生时才二选一
