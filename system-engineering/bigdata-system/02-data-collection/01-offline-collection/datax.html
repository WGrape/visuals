先建立直觉：万能数据转接头

你有 MySQL、Oracle、HDFS、Hive、Elasticsearch 等十几种系统，要在它们之间搬数据。每种组合都写一遍代码？那是 N×M 的工作量。

DataX 的做法是「转接头」：每种数据源实现两个插件——Reader（读出来）和 Writer（写进去）。任意 Reader + 任意 Writer 自由组合，N×M 就变成了 N + M。

架构

一个典型配置

{
  "job": {
    "setting": {
      "speed": {
        "channel": 4,          // 并发通道数
        "byte": 1048576        // 限速：1MB/s（保护源库！）
      },
      "errorLimit": {
        "record": 100,         // 允许 100 条脏数据，超过则失败
        "percentage": 0.02
      }
    },
    "content": [{
      "reader": {
        "name": "mysqlreader",
        "parameter": {
          "username": "ro_user", "password": "***",
          "column": ["id", "user_id", "amount", "created_at"],
          "splitPk": "id",                      // 按此列切分并发
          "connection": [{
            "table": ["orders"],
            "jdbcUrl": ["jdbc:mysql://slave:3306/db"]
          }],
          "where": "created_at >= '2026-10-20'"   // 增量条件
        }
      },
      "writer": {
        "name": "hdfswriter",
        "parameter": {
          "path": "/warehouse/ods/orders/dt=2026-10-20",
          "defaultFS": "hdfs://nn:8020",
          "fileType": "orc",
          "writeMode": "overwrite"               // 覆盖写，保证幂等
        }
      }
    }]
  }
}

三个关键配置

① splitPk：并发切分的依据

DataX 按 splitPk 把数据切成多段并行读取。必须选分布均匀的字段（通常是主键），否则切分不均，某些通道特别慢（数据倾斜）。

坑：如果 splitPk 字段分布不均（如大部分值相同），并发会失效；如果字段有 NULL 或类型不合适（如字符串型主键在某些数据库上切分效率低），也会出问题。建议用数值型自增主键。

② speed：限速保护源库

这是最容易闯祸的地方。DataX 默认不限速，全速读取会把生产库拖垮。必须做三件事：① speed.byte 设字节限速；② speed.channel 控制并发；③ 只读从库，绝不直接压主库。

③ errorLimit：脏数据容忍度

类型转换失败、字段超长等会产生脏数据。设置容忍阈值，超过则任务失败而不是静默丢数据。

全量 vs 增量

方式做法适用
全量覆盖每次全部重导，覆盖写目标分区小表、维表
按时间戳增量where updated_at > 上次位点有可靠更新时间字段
按自增 ID 增量where id > 上次最大 ID只有插入的表
CDC（binlog）解析数据库日志需要捕获删除、要求实时
时间戳增量的经典坑：会漏掉「回溯更新」。如果用 updated_at > 上次位点，那么一条昨天创建但今天才被更新（更新时间早于上次同步位点之前完成）的记录可能被漏掉。缓解：① 位点往前回退一段时间（如往前 5 分钟）做重叠同步；② 目标端用 upsert 保证重复无害；③ 对准确性要求高的场景改用 CDC。

DataX vs Sqoop

维度DataXSqoop
数据源支持非常丰富（几十种，含非关系型）主要关系型数据库 ↔ Hadoop
配置方式JSON 配置文件命令行参数
限速原生支持（byte/record）较弱
底层单进程多线程MapReduce（启动慢）
现状活跃（阿里开源，DataX-Web 等生态）已基本停止维护
建议：新项目优先选 DataX（或 SeaTunnel 等新一代工具），Sqoop 已不活跃。若只做 MySQL↔Hive 的简单同步，两者都可用，但 DataX 的限速能力对保护生产库更友好。

🎯 面试问答

Q：DataX 会把生产库拖垮吗？
A：会，如果不限速。DataX 默认全速读取，高并发大批量查询会占满源库的 CPU、连接数和 IO。必须做的三件事：① 配置 speed.byte（字节限速）和 speed.channel（并发数）；② 只连只读从库，绝不直连主库；③ 安排在业务低峰期执行。此外建议在源库侧也设置只读账号和资源限制，做双重保护。

Q：splitPk 应该怎么选？
A：选数值型、分布均匀、有索引的列，通常是自增主键。原因是 DataX 按这个字段把数据切成多段并行读取，如果字段分布不均（如某值占了 80% 的行），切出来的某些段会特别大，形成数据倾斜，整体速度取决于最慢的那个通道。避免：字符串主键（切分效率低）、有大量 NULL 的列、低基数列（如性别、状态）。

Q：增量同步怎么保证不漏数据？
A：时间戳增量有个经典漏洞：一条记录在上次同步之后才被更新，但更新时间落在窗口边缘，可能被漏掉。三层防护：① 位点往前回退一段时间（如 5 分钟）做重叠同步；② 目标端用 upsert（按主键覆盖）而非追加，让重复同步无害；③ 定期做全量对账（比对行数与关键字段总和）来兜底。对准确性要求极高的场景，应改用 CDC（解析 binlog），它能捕获所有变更包括删除。

Q：DataX 和 Sqoop 选哪个？
A：新项目选 DataX。理由：① 数据源支持广得多（Sqoop 主要只做关系库与 Hadoop 之间）；② 原生限速，对生产库更友好；③ 单进程多线程启动快（Sqoop 走 MapReduce，启动开销大）；④ 社区活跃（Sqoop 已基本停止维护）。只有一种情况 Sqoop 仍有优势：需要与 Hadoop 生态深度集成、依赖 MapReduce 的分布式能力做超大规模并行抽取——但这种场景现在更多用 Spark 直接读 JDBC。

架构与核心参数

DataX 是单机多线程的离线同步框架（不是分布式）：Reader → Channel → Writer。它的性能调优本质上就是调并发和批量。

概念作用配置位置调优要点
Job一次同步任务json 顶层—
Reader读源端（MySQL/PG/HDFS/ODPS...）content[0].readerquerySql 或 column+where
Writer写目标端content[0].writerpreSql/postSql、写入模式
Channel并发通道数（= 并发度）setting.speed.channel核心参数，默认 1
Byte 限速总字节速率上限setting.speed.byte默认不限，生产要限
Record 限速总记录速率上限setting.speed.record默认不限
batchSize单批写入条数writer 里默认 1024，大字段要调小

配置与运行

{
  "job": {
    "setting": {
      "speed": {
        "channel": 4,              // 并发度，<b>核心调优参数</b>
        "byte": 10485760,          // 限速 10MB/s，防止打爆源库
        "record": 10000
      },
      "errorLimit": {
        "record": 0,               // 允许的错误记录数，<b>0 = 有错就失败</b>
        "percentage": 0.02
      }
    },
    "content": [{
      "reader": {
        "name": "mysqlreader",
        "parameter": {
          "username": "root", "password": "xxx",
          "column": ["id", "name", "created_at"],
          "splitPk": "id",        // <b>按此列切分并发，必须是有序且分布均匀的整型</b>
          "where": "created_at >= '2026-10-01'",
          "connection": [{
            "querySql": ["select id,name,created_at from orders"],
            "jdbcUrl": ["jdbc:mysql://10.0.0.1:3306/demo"]
          }]
        }
      },
      "writer": {
        "name": "hdfswriter",
        "parameter": {
          "defaultFS": "hdfs://ns",
          "path": "/warehouse/ods/orders/dt=2026-10-01",
          "fileName": "orders",
          "fileType": "parquet",
          "writeMode": "overwrite"     // append / overwrite / nonConflict
        }
      }
    }]
  }
}

# 运行
python datax.py job.json
python datax.py -j"-Xms1g -Xmx4g" job.json     # 调 JVM 堆

最重要的两个参数：① splitPk——不配置的话即使 channel=4 也只有一个通道在干活（无法切分），必须指定一个分布均匀的整型主键；② speed.byte——从生产库同步一定要限速，否则会把源库打垮。这是 DataX 最常见的两个事故点。

调优与排障

问题原因解法
配了 channel=4 但没加速没配 splitPk，无法切分指定均匀分布的整型主键
源库被打垮没限速 / 并发太高设 speed.byte；channel 从 2 起步
OOM单批太大 / JVM 堆太小调小 batchSize；-j"-Xmx4g"
同步慢（大表）并发不足或单表太大提高 channel（但要限速）；按时间/ID 区间拆成多个 job
数据不准writeMode 用错 / 重复跑用 overwrite + 分区目录；或先删后写
字段类型不匹配两端类型映射错误检查 reader/writer 的 column 类型，用 cast
中文乱码JDBC URL 没指定编码加 ?characterEncoding=utf8

调优与校验

# 并发度怎么定（经验公式）
#   channel = min(源库可承受并发, 目标端可承受并发, 数据量 / 单通道吞吐)
#   MySQL 源：通常 2~8（太多会导致源库锁等待）
#   HDFS/OSS 目标：可以更高（8~16）
#   先压测：channel 从 2 开始，逐步加倍，看源库负载与总耗时

# 大表拆分（单表上亿行时的标准做法）
#   按主键区间拆成多个 job，每个 job 用 where 限定范围
#   where: "id >= 0 and id < 10000000"
#   where: "id >= 10000000 and id < 20000000"
#   好处：可并行、可断点续跑、单 job 失败影响小

# 监控同步进度（DataX 自带日志）
#   看日志末尾的汇总：
#   任务启动时刻 / 结束时刻
#   任务总计耗时 / 平均流量 / 记录写入速度 / 读出记录总数 / 读写失败总数
#   关键指标：读出记录总数 是否 == 源端 count(*)

# 校验一致性（必做）
#   1) 条数对比：源 count(*) vs 目标 count(*)
#   2) 抽样 checksum：按主键排序后取若干段比对
#   3) 关键字段 sum/max 对比
DataX 和 Sqoop 怎么选？

DataX 更通用（支持 20+ 种数据源互相同步，包括非 Hadoop 系），Sqoop 专注 Hadoop ↔ RDBMS。选型看：① 目标是不是 HDFS/Hive —— 是的话 Sqoop 也能用；② 需不需要 MySQL→MySQL、MySQL→ES 这类非 Hadoop 链路 —— DataX 强；③ 生态 —— Sqoop 与 Hadoop 集成更紧密（可直接建 Hive 表）。Sqoop 已进入 Attic（退役），新项目优先 DataX 或 Flink CDC。

DataX 和 Flink CDC 怎么选？

看离线还是实时：DataX 是批量离线同步（每次全量或按条件增量，靠调度周期跑）；Flink CDC 是实时流式（读 binlog，秒级延迟，能拿到删除事件）。首次全量迁移用 DataX 简单可控；持续同步必须 CDC。另外 DataX 是单机的（受单机资源限制），Flink CDC 是分布式的——数据量超过单机能力（比如几百 GB 每小时）就必须上 Flink。

怎么保证 DataX 同步的数据一致性？

四道防线：① 幂等写——用 overwrite 写分区，重复跑结果一样；② 错误限制设 0——有脏数据就失败，不要静默跳过（errorLimit.record=0）；③ 条数校验——同步后对比源端和目标端 count；④ 对账任务——定期对关键表做 checksum 比对。另外要注意：同步期间源端有写入的话，全量同步的结果是不一致的——要么在低峰期跑，要么用 CDC。
