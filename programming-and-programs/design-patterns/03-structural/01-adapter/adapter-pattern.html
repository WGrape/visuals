🔌 适配器

把外部接口翻译成业务已经理解的接口。

一句话记住旅行插头转换器让不同插头接进同一个插座。
问题从哪来图解协作动手试一试伪代码选型与边界
01 · 从问题出发

为什么会需要这个模式？

业务要求 send(message)，外部 SDK 却只有 publish(payload)；若直接调用 SDK，字段差异会散落到业务代码。

业务已经依赖 notifier.send({text})，新短信 SDK 却只接受 sdk.publish({body, recipient})。如果把映射散落在十个调用点，SDK 以后改字段名就要改十处。

😵 直接写会怎样

sdk.publish({body: message.text, recipient: user.phone})
// 页面、订单服务、任务服务各写一遍字段映射

💡 关键转折

适配器实现目标接口，内部持有第三方对象并完成参数、结果和错误翻译。

业务继续说自己的接口语言；适配器在边界一次性翻译参数、返回值和错误。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

interface Notifier { async send(message) }
class SmsAdapter implements Notifier {
  constructor(sdk) { this.sdk = sdk }
  async send(message) {
    try {
      return await this.sdk.publish({ body: message.text,
                                      recipient: message.phone })
    } catch (error) { throw translate(error) }
  }
}

读代码时抓住三件事

  1. 适配器实现目标接口 send，而不是让业务改成 publish。
  2. 它通过组合持有第三方对象，便于替换与测试。
  3. 参数、返回值和错误都属于接口翻译范围。

换个业务场景，还能认出来吗？

旧数据库返回 snake_case 字段，新领域层使用 camelCase；可以在持久化边界做 DTO 映射。若映射包含复杂业务决策，应检查领域边界，而不是无限加厚适配器。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

已有接口不兼容，业务侧需要保持原有契约

三个具体场景

  • 把短信 SDK 的 publish 翻译成 send
  • 把旧系统字段转换为新领域 DTO
  • 把第三方支付错误码映射为业务异常

不适合或要小心

适配器只翻译边界；若塞进大量业务规则，说明领域职责可能放错位置。

翻译层若不断装入业务规则，应重新检查领域边界

最容易混淆的相邻模式

模式真正的区别
装饰器保持接口并叠加行为；适配器改变接口形状使其兼容。
外观简化复杂子系统入口；适配器重点翻译两个不兼容契约。

区分时问自己：你要改变接口形状，还是保持接口并增加行为？

落地前检查

  • 给所有适配器跑同一份目标接口契约测试。
  • 明确超时、错误码、空值和单位的转换。
  • 别让第三方类型泄漏到业务接口签名。
06 · 自己说一遍

两道检验理解的小题

更换短信 SDK 后业务侧的 send 调用要改吗？

不需要；实现另一个 Notifier 适配器，并保持同一契约。

对象适配器一定要继承第三方 SDK 类吗？

不需要。通过组合持有 SDK 往往更灵活，也能避免依赖第三方继承能力。

核心速览

要解决的问题接口不兼容，插不上老组件、第三方库的接口形状对不上
做法加一层转换，不改两端把「被适配者」的接口转成「目标接口」
别称Wrapper 包装器Go 里极常见，几乎每天在写
与装饰器区别适配器换接口，装饰器加功能这是最容易混淆的一对

它长什么样

适配器在中间做翻译：对外是 Target，对内调 Adaptee

两种实现

方式实现手段优点缺点Go 里的情况
对象适配器组合：Adapter 持有 Adaptee 实例松耦合、可适配多个 Adaptee要写转发方法Go 首选（无继承）
类适配器继承 Adaptee 并实现 Target可覆写 Adaptee 行为强耦合、多继承语言才行Go 不支持继承，用嵌入近似

Go 里的典型写法

// 目标接口：业务代码只依赖它 type Notifier interface { Send(title, body string) error } // 已存在的第三方组件（接口形状不匹配） type SmsClient struct{} func (s *SmsClient) Push(phone string, text string) (int, error) { return 0, nil } // 适配器：把 Push 转成 Send，并补上号码等上下文 type SmsNotifier struct { client *SmsClient phone string } func (a *SmsNotifier) Send(title, body string) error { _, err := a.client.Push(a.phone, title+": "+body) // 参数转换 return err } // 使用：上层只认 Notifier，换短信厂商只需换一个适配器 var n Notifier = &SmsNotifier{client: &SmsClient{}, phone: "138****"} _ = n.Send("告警", "CPU 超过 90%")

和它长得像的三个模式

模式目的是否改变接口一句话区分
适配器 Adapter让不兼容的能一起工作是（换成目标接口）事后补救，两端都不改
装饰器 Decorator在不改接口的前提下加功能否接口不变，行为增强
外观 Facade给复杂子系统一个简出入口否（新造一个）为了简单，而不是为了兼容
桥接 Bridge让抽象与实现各自独立演化否设计期就规划好两个维度

什么时候用

① 接入第三方 / 遗留代码对方接口与你定义的不一致，又改不了对方的源码。
② 隔离外部依赖把 SDK 包装成自己的接口，将来换厂商只改适配器一处。
③ 统一多个实现多个厂商接口各不相同，用适配器统一成一个内部接口。
④ 测试替身给真实组件套一个适配层，测试时替换成假实现。

深入自检

适配器算不算「过度设计」？

关键看是否真的隔离了变化。如果一个第三方 SDK 只在一处调用、且几乎不会换，直接调用更清晰；如果它出现在多个地方、或有替换计划，包装一层是划算的。

对象适配器和「直接写个新函数」有什么区别？

函数也能做转换，但适配器把它变成了类型，可以注入、可以替换、可以组合进更大的结构。在需要依赖注入与多态的场景，类型比函数更合适。

Go 里用嵌入（embedding）算类适配器吗？

不算严格的类适配器（Go 没有继承与多态覆写）。嵌入更像是语法糖式的组合：外露方法自动提升，但你仍然可以在外层定义同名方法覆盖它。本质上还是对象适配器。

适配器会不会掩盖设计问题？

会。如果系统里到处都是适配器，说明接口契约没有统一。这时应该考虑定义一套稳定的核心接口，而不是不停打补丁。

如何避免适配器变成大泥球？

遵守两条：① 适配器只做转换，不放业务逻辑；② 转换失败要显式返回错误，不要吞掉。业务逻辑应该留在调用方或领域层。
