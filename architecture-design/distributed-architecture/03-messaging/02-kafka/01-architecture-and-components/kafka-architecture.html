Apache Kafka 架构图

Producer (生产者)

应用程序向 Kafka 发送消息的客户端。
根据 key 决定写入哪个 Partition，默认采用 hash(key) % partitions 策略。

Broker

Kafka 集群中的服务节点，负责接收消息、存储分区、管理副本。
每个 Broker 持有多个 Partition 的部分数据。

Topic & Partition

Topic 是消息的逻辑分类，Partition 是物理存储单元。
Partition 数量决定了并行消费的上限。

Leader & Follower

每个 Partition 有 1 个 Leader 和 N-1 个 Follower。
所有读写操作都经过 Leader，Follower 异步同步。

ISR (In-Sync Replicas)

与 Leader 保持同步的副本集合。
acks=all 时需等待 ISR 全部确认才返回成功。

Consumer Group

同一 Group 内的 Consumer 负载均衡消费 Partition。
不同 Group 可独立消费同一 Topic，互不影响。

Kafka 架构：一张图看全貌

Kafka 的角色是分布式事件流平台。理解它的关键在于四个概念的分层关系：Topic 是逻辑分类 → Partition 是并行与有序的单位 → Segment 是磁盘上的实际文件 → Offset 是位置坐标。

Kafka 整体架构：Producer → Topic（多 Partition）→ Broker → Consumer Group

核心概念速查

概念是什么关键点
Broker一个 Kafka 服务节点多个 Broker 组成集群；每个分区的 Leader 分散在不同 Broker 上
Topic消息的逻辑分类只是逻辑概念，真正承载数据的是分区
Partition分区，Topic 的物理分片并行度与顺序的基本单位；分区内有序，分区间无序
Offset消息在分区内的序号单调递增、不可变；消费者靠提交 offset 记录进度

Replica分区副本Leader 对外服务，Follower 同步；ISR 是同步中的副本集合

为什么 Kafka 快：四个设计要点

① 顺序磁盘 IO

Kafka 只在日志文件末尾追加写入，不做随机写。顺序写的磁盘吞吐常常高于随机内存访问。

  • 对比：传统 MQ 用「随机写 + 内存索引」会随数据量增长而变慢
  • Kafka 的数据量增长时性能基本恒定

② 零拷贝（sendfile）

消费者读数据时，用 sendfile 让数据直接从磁盘文件进入网卡缓冲区，跳过「内核→应用→内核」的两次拷贝与上下文切换。

  • 这是 Kafka 高吞吐的关键之一
  • 代价：零拷贝路径上无法对数据做加工

③ 批量与压缩

生产者按 batch.size 与 linger.ms 攒批发送，批量压缩（snappy/lz4/zstd）降低网络与磁盘开销。

  • 攒批会略微增加延迟，需要权衡
  • 压缩率取决于内容，文本类通常 3~5 倍

④ 分区并行

不同分区可以分布在不同 Broker，读写天然并行。

  • 分区数是吞吐的「上限旋钮」——分区太少，加再多消费者也没用
  • 分区不是越多越好：文件句柄、内存、选举时间都会增加

分区与消费者的关系（最易错的点）

规则只有两条，但很多人搞混：

组内竞争同一 Consumer Group 内，一个分区只能被一个消费者消费；消费者数 ≤ 分区数才有意义
组间广播不同 Group 各自消费全量消息，互不影响（各自维护自己的 offset）
分区数 < 消费者数多余的消费者闲置，不提升吞吐——这是最常见的「以为扩容了其实没有」
分区数 > 消费者数一个消费者消费多个分区，是正常状态
Rebalance消费者增减或分区数变化时触发重新分配，期间消费暂停——应尽量避免因超时误判触发

分区数怎么定：估算公式 ≈ 目标吞吐 / 单分区吞吐。单分区吞吐经验值：生产约 几 MB/s ~ 十几 MB/s（取决于副本数与 acks）；消费还受业务处理速度限制——如果每条消息要处理 50ms，单分区每秒最多 20 条。分区数可以后期增加（会导致 key 的分区映射变化），但不能减少，所以初期宁可略多。

可靠性配置三件套

参数作用推荐配置
acks生产者要求多少个副本确认后才算发送成功0（不等确认，最快可能丢）/ 1（等 Leader，默认）/ all（等 ISR 全部，最安全）

replication.factor每个分区的副本总数生产环境至少 3
enable.idempotence生产者幂等，避免重试造成重复与乱序开启（true），单分区单会话内保证不重复不乱序
unclean.leader.electionISR 全挂时是否允许非同步副本成为 Leaderfalse（宁可不可用，也不丢数据）
auto.offset.reset消费者无 offset 或 offset 越界时从哪开始earliest（从头）/ latest（从最新）；按需选择，勿用默认

不丢消息的完整配置：acks=all + replication.factor=3 + min.insync.replicas=2 + enable.idempotence=true + unclean.leader.election.enable=false + 消费端处理完业务再提交 offset。缺任何一环都可能丢消息或重复消费。

深入自检

如何保证消息顺序？

Kafka 只保证分区内有序。要保证某类消息的顺序，就应让它们进入同一分区：① 发送时指定相同的 key（如 orderId），默认分区器会按 key 哈希路由到固定分区；② 该分区只能被消费者组内的一个消费者消费（这是天然成立的）；③ 生产者开启幂等并设 max.in.flight.requests.per.connection ≤ 5，避免重试导致的乱序；④ 若需要严格不重不乱，使用事务（Kafka Transactions）或业务侧加版本号。注意：增加分区数会改变 key→分区 的映射，破坏原有顺序，所以如需顺序，扩容要谨慎规划。

消息重复了怎么办？

Kafka 默认提供「至少一次」投递，重复是必然的（消费者处理完未提交就宕机、或 Rebalance 后从旧 offset 重新消费）。正确做法不是在 Kafka 层面消灭重复，而是让消费逻辑幂等：① 用消息 key 或业务唯一键建去重表（唯一索引）；② 或用状态机判断（订单已是 PAID 则跳过）；③ 或用 Kafka 事务 + 幂等生产者实现「读取 → 处理 → 写外部系统 → 提交 offset」的原子性（Kafka Streams 的 exactly-once）。绝大多数业务用「至少一次 + 消费幂等」即可，成本远低于事务方案。

消费者积压严重怎么处理？

先定位瓶颈：① 分区数不足——消费者数已等于分区数仍积压，说明单分区处理太慢，需要增加分区；② 业务处理慢——优化单条处理逻辑，或改为批量处理（一次 poll 一批，批量写库）；③ 下游依赖慢——异步化或加缓存；④ 消费线程模型不合理——Kafka Consumer 不是线程安全的，常见做法是「单线程 poll + 多线程处理 + 按分区保序提交」。临时救急可以加消费者（但不能超过分区数）。另外要监控 lag 而不是只看是否在线。

Kafka 适合做业务消息中间件吗？

取决于需求。Kafka 强在高吞吐、可重放、流式处理，但它缺少传统 MQ 的一些能力：原生不支持单条消息的延迟投递、死信队列、消费重试间隔、消息标签过滤、事务回滚到队列等。如果业务需要这些（如订单超时关闭、失败重试退避），用 RocketMQ/RabbitMQ 更顺手，或者自己在 Kafka 之上用「重试主题 + 延迟主题」实现。反过来，如果是日志采集、埋点上报、CDC 同步、流式计算，Kafka 几乎没有对手。选型看场景，不要迷信单一产品。
