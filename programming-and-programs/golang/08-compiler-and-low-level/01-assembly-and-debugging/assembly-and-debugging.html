查看汇编

-S 输出汇编

go build -gcflags=-S 或 go tool compile -S 能看到每个函数的 Plan9 汇编，对照源码理解内联、边界检查消除等。

go build -gcflags="-S" main.go
# 或只编一个文件
echo package main > /tmp/x.go
GOSSAFUNC=main go build  # 生成 SSA 可视化 HTML

dlv 支持断点、单步、查看变量与 goroutine 栈；可 attach 到进程或调试测试。

dlv debug ./cmd/app

Plan9 汇编约定

不是 Intel 语法

Go 汇编是抽象的 Plan9 风格（如 MOVL、函数栈帧用 FP/SP 伪寄存器），与具体 CPU 语法不同，主要用于 runtime 手写优化。

业务代码几乎不需要手写汇编；了解即可，遇到 runtime 源码里的汇编函数知道它在做什么。

调试前先关掉优化

默认构建会做内联与寄存器优化，导致断点落不进去、变量显示 optimized out。调试构建要显式关闭。

# 调试构建：关闭内联与优化 go build -gcflags='all=-N -l' -o app . # 常用调试命令 dlv debug ./cmd/app # 直接编译并进入调试 dlv exec ./app # 调试已编译的二进制 dlv attach <pid> # 附加到运行中的进程 dlv core ./app core.dump # 分析 core dump # delve 内部常用指令 b main.main # 打断点 b file.go:42 c / continue # 继续 n / next # 单步（不进入函数） s / step # 单步（进入函数） p x # 打印变量 args / locals # 查看参数与局部变量 goroutines # 列出所有 goroutine goroutine 12 # 切换 goroutine bt / stack # 打印调用栈
-N -l关闭优化与内联，让断点与变量可用。
dlv attach排查线上卡死、CPU 飙高时最有用。
goroutines查看全部协程状态，定位阻塞点。
core dump事后分析崩溃现场，不必复现。

死锁与阻塞：怎么快速定位

全部 goroutine 都在等

pprof 的 goroutine profile 会直接告诉你卡在哪一行。

  • 大量 semacquire → 锁竞争
  • chan receive/send → channel 没人配对
  • select → 所有分支都不可走
  • 运行时自带的死锁检测会打印完整栈

CPU 跑满但不干活

典型是死循环或忙等。

  • CPU profile 会显示一个平坦的高占比函数
  • 检查循环退出条件与 select 的 default 分支
  • Go 1.14+ 有异步抢占，单 goroutine 死循环不会卡死整个 P

内存持续上涨

先区分是泄漏还是还没 GC。

  • 连续两次 heap profile 做 diff
  • 看 inuse_space 的趋势而非 alloc_space
  • 常见泄漏源：未 Stop 的 ticker、无上限缓存、未关闭的连接

深入自检

变量显示 optimized out 怎么办？

说明构建时开启了优化。用 go build -gcflags=all=-N -l 重新编译即可。注意 all= 前缀表示对所有依赖包生效，否则只作用于当前包。

线上服务能直接 attach 吗？

可以，但要明白 delve 会短暂挂起进程，对延迟敏感的服务要在低峰或摘流后操作。更安全的做法是抓取 pprof 与 goroutine dump，离线分析。

pprof 常开会不会影响性能？

CPU profile 是采样式（默认每秒 100 次），常开开销很小；但不要长时间连续抓取。trace 的开销明显更大，建议在排查时短时开启。记得限制 /debug/pprof 的暴露范围。

core dump 怎么产生和分析？

先在目标环境允许生成 core（ulimit -c unlimited，配置 kernel.core_pattern），进程崩溃后得到 core 文件，用 dlv core ./app core 打开，可以像调试现场一样查看崩溃时的栈与变量。

为什么本地能复现，线上复现不了？

通常是并发时序、数据量或依赖状态不同。优先收集线上证据（pprof、goroutine dump、日志 trace id），而不是试图在本地复现。有了栈和 profile，多数问题不需要复现就能定位。
