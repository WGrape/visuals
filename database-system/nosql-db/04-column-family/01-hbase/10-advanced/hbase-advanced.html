🚀 HBase 高级特性

协处理器、过滤器、计数器、BulkLoad、快照、复制与多租户隔离

协处理器（Coprocessor）

协处理器是 HBase 的「插件机制」，让你把自定义逻辑推到 RegionServer 上执行，避免把海量数据拉到客户端。分两类：

类型类比触发时机典型用途
Observer数据库触发器put/get/delete/scan 前后、Region 事件、Master 事件二级索引同步、权限校验、审计日志、数据校验
Endpoint存储过程客户端显式调用服务端聚合（count/sum/avg），避免拉全量数据
// Observer 示例：写入时同步维护索引（RegionObserver）
public class IndexObserver implements RegionObserver {
  @Override
  public void postPut(ObserverContext<RegionCoprocessorEnvironment> e,
                      Put put, WALEdit edit, Durability durability) {
    // 在 put 之后，把索引行写到索引表
    indexTable.put(buildIndexRow(put));
  }
}

// 静态装载（hbase-site.xml，需重启；全局生效）
<property>
  <name>hbase.coprocessor.region.classes</name>
  <value>com.xxx.IndexObserver</value>
</property>

// 表级装载（无需重启，推荐）
alter 't', METHOD => 'table_att',
  'coprocessor' => 'hdfs:///cp/index.jar|com.xxx.IndexObserver|1001|'
⚠️ 协处理器运行在 RegionServer JVM 里，一个 bug 或死循环能让整台 RS 挂掉。生产上慎用，能用 Phoenix 二级索引解决的就别自己写。

过滤器（Filter）

Filter 在 RegionServer 端执行，减少网络传输——但注意：它不减少扫描的数据量（该读的 HFile 还是全读了）。

Filter作用
RowFilter按 rowkey 过滤（支持正则、子串）
PrefixFilterrowkey 前缀匹配（可优化为范围 scan）
SingleColumnValueFilter按某列的值过滤
FamilyFilter / QualifierFilter按列族 / 限定符过滤
PageFilter每 Region 返回 N 行（注意：是每 Region 不是总数）
ColumnPaginationFilter列级分页
FilterList组合多个 Filter（AND / OR）
// Java：组合过滤器
FilterList fl = new FilterList(FilterList.Operator.MUST_PASS_ALL);
fl.addFilter(new PrefixFilter(Bytes.toBytes("u123")));
fl.addFilter(new SingleColumnValueFilter(
    Bytes.toBytes("cf"), Bytes.toBytes("status"),
    CompareOperator.EQUAL, Bytes.toBytes("active")));
fl.addFilter(new PageFilter(100));
scan.setFilter(fl);

// Shell
scan 't', { FILTER => "PrefixFilter('u123') AND
                       SingleColumnValueFilter('cf','status',=,'binary:active')" }
💡 能用 STARTROW/STOPROW 就别用 Filter：前者直接收窄扫描范围（走索引边界），后者只是服务端逐条过滤。PrefixFilter 是个例外——HBase 能把它优化成范围 scan。

计数器（Counter）

increment 是 HBase 提供的原子自增，在 RegionServer 端完成「读-改-写」，无需客户端往返，也无需加锁。

// 原子自增（返回新值）
long n = table.incrementColumnValue(
    Bytes.toBytes("user#123"),      // rowkey
    Bytes.toBytes("stat"),          // 列族
    Bytes.toBytes("pv"),            // 限定符
    1L);                            // 步长

// Shell
incr 't', 'row1', 'stat:pv', 1
get_counter 't', 'row1', 'stat:pv'

适用场景：点赞数、PV/UV、库存扣减等高频计数。不适合：需要精确事务的金融场景（increment 与 put 混用时有语义陷阱）。

BulkLoad：绕过写入路径的批量导入

优点

  • 不写 WAL、不占 MemStore
  • 不触发 flush 与 compaction
  • 速度通常比逐条 put 快一个数量级
  • 对在线读写几乎零影响

限制

  • 不是实时的（要跑一个计算任务）
  • 需要额外计算资源
  • 生成的文件必须按 rowkey 有序
  • 不触发 WAL，数据无法靠 WAL 恢复（但已在 HFile 里）

快照（Snapshot）

HBase 的 snapshot 是元数据操作：只记录当时所有 HFile 的文件列表，不拷贝数据。因为 HFile 不可变，快照点的数据天然冻结。

操作命令用途
创建snapshot 't','snap1'秒级完成
克隆建表clone_snapshot 'snap1','t_copy'秒级克隆一张新表（测试/抽样）
回滚restore_snapshot 'snap1'需先 disable + truncate
跨集群导出ExportSnapshot走 MapReduce，不打扰在线集群
删除delete_snapshot 'snap1'释放被引用的旧文件

复制（Replication）

主集群的 WAL 异步推送到从集群重放，用于容灾与读写分离。

异步WAL 异步推送，有秒级延迟
主→从1.x 单向；2.x 支持双向（需防循环）
串行按 Region 串行重放，保证顺序
非备份误删会同步过去，不能防误操作

多租户：RSGroup

RSGroup 把 RegionServer 分组，把表/命名空间绑定到指定组，实现物理资源隔离——离线分析的重扫描不会拖垮在线点查。

# 创建组、加入服务器、绑定表
add_rsgroup 'online'
move_servers_rsgroup 'online', ['rs1:16020','rs2:16020']
move_tables_rsgroup 'online', ['user','order']
add_rsgroup 'offline'
move_servers_rsgroup 'offline', ['rs3:16020','rs4:16020']
move_tables_rsgroup 'offline', ['log','dump']
get_rsgroup 'online'
balance_rsgroup 'online'

特性说明
CheckAndPut / CheckAndDelete行级 CAS（compare-and-set），实现乐观锁
Append原子追加到某个 cell（HBase 有原生 append 操作）
Mob（中等对象）100KB~10MB 的中等对象特殊存储，避免拖累 compaction
ACL / 权限RWXCA 五级权限，可到列族/列粒度

Procedure V22.x 的分布式事务框架，保证 DDL 等操作的状态一致性

🎯 常见问法与答题要点

Q：协处理器 Observer 和 Endpoint 有什么区别？

A：Observer 是触发器——挂在 put/get/delete/scan 等钩子点上，被动执行，典型用途是同步维护二级索引、权限校验、审计日志。Endpoint 是存储过程——客户端显式调用，在服务端多个 Region 上并行执行后汇总结果，典型用途是服务端聚合（count/sum/avg），避免把海量数据拉回客户端。

Q：为什么协处理器要慎用？

A：因为它运行在 RegionServer 的 JVM 内部，与 HBase 核心共享资源。一个死循环、一个未捕获异常、一次大内存分配，都可能让整台 RS 挂掉，进而影响其上所有 Region 和所有表。而且它难以测试、难以灰度、升级 HBase 时可能不兼容。所以原则：能用 Phoenix 官方二级索引解决的，绝不自己写协处理器。

Q：Filter 能提升查询性能吗？

A：要分清楚「减少网络传输」和「减少扫描量」。Filter 在 RegionServer 端执行，确实减少了返回给客户端的数据量，但它没有减少实际扫描的 HFile 数据量——该读的 block 还是全读了，只是过滤掉了。所以 Filter 不能替代 rowkey 设计。真正减少扫描量的只有：精确 rowkey 点查、收窄 STARTROW/STOPROW、以及 Phoenix 二级索引。

Q：increment 是原子的吗？能用于库存扣减吗？

A：是原子的——它在 RegionServer 端完成完整的「读-改-写」，不需要客户端往返，也不会被其他写入打断。适合 PV/UV、点赞数这类计数。但用于库存扣减要小心：increment 只能保证自身的原子性，不能保证「检查库存 > 0 再扣减」这个复合操作的原子性（需要用 checkAndPut 或在应用层加锁）。金融级场景建议还是用关系库。

Q：BulkLoad 和逐条 put 差多少？

A：通常快 一个数量级，而且对在线集群几乎零影响。原因是它绕过了整条写入路径：不写 WAL（省一次 HDFS 写）、不进 MemStore（省内存与 flush）、不触发 compaction（省大量 IO）。代价是需要额外跑一个 Spark/MapReduce 任务，且不是实时的。所以初始化、数据迁移、每日批量导入都该用 BulkLoad。

Q：PageFilter(100) 为什么返回的不是 100 行？

A：因为 PageFilter 是每个 Region 返回 N 行，而不是总数 N 行。如果 scan 跨了 10 个 Region，最多会返回 10×100 = 1000 行。要做真正的分页，要么配合 STARTROW 手动推进（游标分页），要么在客户端再做一次截断，要么用 Phoenix 的 LIMIT/OFFSET。

Q：RSGroup 解决什么问题？

A：多租户资源隔离。没有 RSGroup 时，一张离线分析大表的全表扫描会把所有 RegionServer 的 CPU/IO 打满，拖垮同机上的在线点查表。RSGroup 把 RegionServer 分成「在线组」和「离线组」，把表绑定到各自组，做到物理级别的隔离——离线任务再重也影响不到在线服务。

Q：checkAndPut 怎么用？

A：它提供行级 CAS（compare-and-set）：只有当某个 cell 的当前值等于期望值时，才执行这次 put，整个操作原子。典型用途是实现乐观锁：table.checkAndPut(row, cf, "lock", CompareOperator.EQUAL, Bytes.toBytes("0"), put)——只有 lock 列还是 0 时才写入，用来抢占锁或避免覆盖。失败时返回 false，客户端可重试。
