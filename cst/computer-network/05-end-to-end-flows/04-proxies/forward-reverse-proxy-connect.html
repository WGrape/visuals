正向代理、反向代理与 CONNECT：谁代表谁建立连接

沿浏览器经企业代理访问 HTTPS 网站、再经源站反向代理转发的双代理路径解释信任边界。

两种代理位于不同一侧

正向代理代表客户端向外访问目标，常用于企业出口、访问控制或缓存；反向代理位于服务端入口，代表多个后端接收客户端请求，常做 TLS 终止、路由和负载均衡。浏览器配置企业代理 P，经 P 访问 `shop.example.test`；网站前面还有反向代理 R，再由 R 把请求送到订单服务。两者都叫“代理”，但受谁管理、替谁隐藏地址和能看到哪些数据并不同。

客户端知道自己是否明确使用正向代理，通常不需要知道后端有哪些源站实例。反向代理对客户端表现为站点入口。网络中也可能有透明代理或服务网格 sidecar，但不能仅凭“中间有转发设备”就判断是哪一类，必须看连接发起方与协议终止点。

HTTP 明文代理请求

浏览器经显式正向代理访问明文 HTTP 时，可在代理连接上发送包含完整目标 URL 的请求，代理解析目标主机并向其转发。代理可能缓存响应、添加认证、记录访问日志。目标站点收到的源 IP 往往是代理出口而非终端；若业务按 IP 限流，应区分代理群体与真正用户身份，并设计可信转发信息。

代理缓存要遵守 HTTP 缓存指令及用户隔离。若带个人数据的响应被错误存入共享缓存，可能导致跨用户泄漏。代理添加的 Via、Forwarded 等头有助于链路诊断，但客户端也能伪造部分头，源站只能信任受控代理链路中被校验和覆盖的字段。

HTTPS 的 CONNECT 隧道

浏览器经显式 HTTP 代理访问 HTTPS 站点时，通常先向代理发送 `CONNECT shop.example.test:443`。代理若同意，建立到目标地址的 TCP 通道，并返回连接建立响应；之后浏览器在这个通道里与目标端进行 TLS 握手。普通隧道代理可看到目标主机和连接元数据，却不能直接读取 TLS 加密的 HTTP 路径与正文。若企业终端安装了受信任的代理根证书并做 TLS 检查，则代理可能终止并重新建立 TLS，这已是另一种明确的信任配置。

CONNECT 成功只说明隧道已建立，不保证 TLS 主机名验证或后续 HTTP 请求成功。若浏览器报证书错误，先区分拿到的是目标站证书还是企业检查代理证书。若代理不允许目标端口，可能在 TLS 之前就返回代理错误。

反向代理怎样处理请求

R 接受客户端连接，可以终止 TLS，依据 Host 和路径选订单后端，再建立独立的上游连接。此时客户端到 R、R 到后端是两段连接，超时、TLS、重试和连接池各有配置。若客户端请求已被后端提交，但 R 等响应超时并自动重试另一后端，仍可能重复执行非幂等写入。反向代理不提供分布式事务，业务要有幂等键和状态查询。

R 可以把客户端真实地址通过 Forwarded 或 X-Forwarded-For 传递给后端，但必须在边界清除外部用户伪造的同名头，并限定后端只信任 R。若 R 之后还有 CDN、网关等多层代理，需要约定哪个字段和哪个位置代表原始客户端；简单取列表第一个 IP 可能被伪造。

一次完整的地址视图

浏览器本地与企业代理 P 建 TCP；P 再向网站入口 R 建 TCP；R 再向订单服务 S 建上游连接。浏览器看到证书可能由 R 提供，P 在普通 CONNECT 隧道下不解密；S 看到的直接 TCP 对端是 R，R 看到的对端是 P。若要定位用户请求，需使用可信请求 ID 和代理链日志，把各段连接的时间、目标和状态拼起来。

这个例子解释了为何服务器 access log 只有代理 IP、而用户投诉来自不同地区。定位时先确认每段是否真有连接和响应，不要因为 R 返回 502 就断言 S 自己返回 502；502 也可能由 R 生成。

配置与验收

分别测试无代理直连、经 P 的 HTTP、经 P 的 HTTPS CONNECT、经 R 的后端路由。记录 DNS 是浏览器解析还是代理解析、每段 TLS 证书、Host/SNI、真实源 IP 和转发头。代理增加缓存或重试前，先验证用户隔离与写请求副作用；部署后监测每段建连耗时、上游错误与连接池状态。

若企业代理故障，外部站点可能仍健康；若 R 故障，浏览器即使能经 P 访问其他网站也无法访问该站。把链路分成客户端到 P、P 到 R、R 到 S 三段，是最有效的排障起点。

三种代理与关键头

类型代理谁客户端是否知道典型用途
正向代理代理客户端访问外网知道（要主动配置）公司上网代理、翻墙、爬虫 IP 池、缓存
反向代理代理服务端接收请求不知道（以为在访问真实服务器）Nginx、CDN 回源、负载均衡、TLS 终结、WAF
透明代理客户端无感知地劫持流量不知道运营商缓存、企业审计（需 iptables TPROXY）
HTTP 头含义注意
X-Forwarded-For（XFF）经过的客户端 IP 链，逗号分隔最左是最原始客户端；但可被伪造
X-Real-IPNginx 常用，单个 IP只保留原始 IP
X-Forwarded-Proto原始协议（http/https）TLS 在代理终结时后端需要它判断
X-Forwarded-Host原始 Host多级代理时保留
Via经过的代理标识RFC 7230，用于检测环路
Forwarded标准化的替代头（RFC 7239）更规范但普及度低

真实 IP 的正确取法：从信任的代理链的最右侧往左数。Nginx 用 real_ip_header X-Forwarded-For + set_real_ip_from 10.0.0.0/8 指定可信代理段，这样 $remote_addr 就会变成真实客户端 IP。绝不能直接信任 XFF 最左值——客户端可以伪造。

代理配置

# Nginx 反向代理标准配置
location / {
    proxy_pass http://backend;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
}

# 让后端拿到真实 IP（在最后一跳代理上）
set_real_ip_from 10.0.0.0/8;
set_real_ip_from 172.16.0.0/12;
real_ip_header X-Forwarded-For;
real_ip_recursive on;

# 正向代理（CONNECT 方法，用于 HTTPS 隧道）
curl -x http://proxy:8080 https://example.com
curl -x socks5://127.0.0.1:1080 https://example.com

# 测试代理是否生效
curl -x http://proxy:8080 -I https://ifconfig.me

CONNECT 隧道与排障

HTTPS 走正向代理必须用 CONNECT：客户端发 CONNECT example.com:443 HTTP/1.1，代理建立到目标的 TCP 隧道后回 200 Connection established，之后客户端与目标直接做 TLS 握手——代理看不到也改不了里面的内容（这正是 HTTPS 不能被中间人解密的原因）。

  • 为什么反向代理看得到明文：因为 TLS 在代理处终结（代理持有证书），代理解密后转发给后端（可能再加密）。这是 WAF、路由、灰度能工作的前提，也意味着代理是安全边界，必须重点保护。
  • 常见故障 1：后端拿到的是代理 IP → 没配 XFF 或 set_real_ip_from。日志、限流、风控全部失效。
  • 常见故障 2：无限重定向 → 代理终结了 TLS，但后端不知道（没有 X-Forwarded-Proto），后端把请求重定向到 HTTPS，代理再转发...循环。解决：传 X-Forwarded-Proto: https 并让后端识别。
  • 常见故障 3：Host 头不对 → proxy_set_header Host 没设，后端拿到的是 upstream 名字而非真实域名，导致路由错误或 cookie 域名不对。
  • 常见故障 4：代理环路 → A 代理转发到 B，B 又转回 A。用 Via 头检测，或限制转发层数。
  • 超时设置：proxy_connect_timeout（建连，1–5 s）、proxy_send_timeout、proxy_read_timeout（等后端响应，按业务 P99）。三个都要设，否则慢后端会耗尽代理的连接。
代理能看到 HTTPS 的内容吗？

取决于代理类型。正向代理用 CONNECT 隧道时看不到（端到端加密）；反向代理终结 TLS时能看到明文（这是设计如此）；企业审计型代理会做 MITM（在客户端装根证书），可以解密——所以公司电脑能审计 HTTPS 流量。

XFF 里有多个 IP，该用哪个？

语义上最左是原始客户端，但可以被伪造。安全做法是：只信任自己可控的代理添加的那一跳，从右往左跳过所有可信代理，第一个不可信的就是真实 IP（Nginx 的 real_ip_recursive on 就是这个逻辑）。

自检

普通 HTTPS CONNECT 代理能直接看到加密后的 HTTP 请求路径吗？

通常不能。它主要建立隧道并看到连接元数据；若显式做 TLS 检查并得到终端信任，才可能解密应用内容。
