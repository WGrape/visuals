缓存架构

判断何时需要缓存、将缓存放在哪里，以及如何约束数据新鲜度和故障影响。

先判断是否需要缓存

缓存是数据的派生副本。引入它之前，先确认读请求是否真的受后端延迟或容量限制，并写下可接受的数据滞后时间。若瓶颈在慢查询、索引或接口调用，优先处理原始瓶颈。

设计问题需要确认的约束
读负载热点是否集中，命中率能否足以降低源站压力？
数据新鲜度业务能接受多长时间的旧值？哪些操作必须直接读取权威数据？
故障行为缓存不可用时，数据库能否承受回源流量？是否需要限流或降级？
写入成本数据变化后，谁负责失效、重试和监控？

选择缓存所在层

客户端与 CDN

适合可公开复用、允许按版本或有效期更新的内容；重点是发布后的刷新与回源策略。

应用本地缓存

读取延迟低，但每个实例各有副本；要评估实例间失效传播和内存占用。

共享缓存

多个实例共用数据，便于统一失效；要计入网络访问、集群可用性与热点 key 的代价。

多层组合会提高命中率，也会增加失效路径。只有在单层方案无法满足延迟或容量目标时再叠加层次。

明确一致性与降级边界

确定数据库等权威数据源、缓存失效的触发者和失败重试机制。TTL 可限制旧值存活时间，但不能单独保证业务要求的强一致；对资金、库存最终确认等读写，应按业务规则读取或更新权威数据。缓存失效时还要限制回源量，避免把缓存故障放大为数据库故障。

具体读写时序与双写一致性见缓存读写模式和双写一致性；穿透、击穿与雪崩的处理见缓存异常总览；多层部署见多级缓存架构。
