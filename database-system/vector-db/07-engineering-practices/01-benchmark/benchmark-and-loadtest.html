①公开 benchmark 为什么不可用

公开 benchmark 几乎不能用于选型决策。原因不是厂商造假，而是压测的前提条件被隐藏了：用的是什么数据集、带不带过滤、召回率多少、索引参数多少、冷缓存还是热缓存 —— 任何一项不同，结果就差几倍。

隐藏前提不同取值带来的差异为什么容易被忽略
是否带过滤过滤严格时性能可降 5–10 倍多数 benchmark 用无过滤场景
recall@K 水平recall 0.90 与 0.99 的延迟差 2–3 倍只报 QPS 不报 recall
冷 / 热缓存冷启动首查可能慢 10 倍以上压测通常跑在热缓存上
索引参数M 从 16 调到 32，内存翻倍、延迟变化参数往往不公开
单租户 vs 多租户共享资源下互相干扰benchmark 通常单租户独占
并发模型单线程 QPS × 并发 ≠ 饱和 QPS压测工具配置不透明
所以正确做法只有一条：用你自己的数据、你自己的过滤条件、你自己的召回目标，压你自己的候选引擎。公开数据只能用来排除明显不合适的选项。

②八个必须写明的前提

一份可信的压测报告必须写明以下八项，缺一项结论就不可复现：

前提示例写法为什么必须写
数据规模与维度1000 万 × 1536 维，float32决定内存与图规模
距离度量cosine（向量已归一化）影响算法实现路径
索引类型与参数HNSW，M=16，efConstruction=200参数不同结果不可比
查询参数ef_search=64，top_k=10这是延迟的直接旋钮
recall@100.955（对 FLAT ground truth）没有召回数字的 QPS 没有意义
过滤条件与选择率tenant_id 等值过滤，选择率约 8%过滤是最主要的性能变量
并发数与缓存状态32 并发，热缓存（预热 1000 次）并发与缓存决定吞吐上限
硬件规格8 vCPU / 32 GB / NVMe跨硬件比 QPS 等于没比
最常见的不诚实（往往是无意的）：只报 QPS 不报 recall。把 ef 调到 8 能得到极高的 QPS，但召回可能只有 0.7。任何「QPS 比对手高 5 倍」的结论，先问它的 recall 是多少。

③六步压测顺序与并发扫描表

压测不是「跑个工具看数字」，顺序错了结论就废了：

  1. 建 ground truth：同一批数据用暴力检索生成 top-100，作为召回基准（方法见召回评测页）。
  2. 灌数据并等索引建完：这一步最容易被跳过。Qdrant 看 indexed_vectors_count，Milvus 看索引构建完成，pgvector 看 CREATE INDEX 结束。
  3. 预热：先跑 1000 次查询把缓存填满，再开始正式测量。
  4. 扫并发：并发从 1、4、8、16、32、64 依次增加，每档记录 QPS、p50/p95/p99。
  5. 定拐点：QPS 不再随并发增长、而 p99 快速上升的那个点，就是这台机器的饱和点。
  6. 同档位复测 recall：确认在不同并发下召回没有变化（正常情况下不应变化）。

④吞吐与延迟关系：Little's Law

两个常被算错的吞吐概念：

误解正确关系
「单线程 QPS × 并发数 = 饱和 QPS」只在完全线性区成立。实际受 CPU 核数、IO、锁竞争限制，必然饱和
「QPS 越高越好」应在目标 p99 约束下比 QPS。脱离延迟讲吞吐没有意义
「平均延迟 20 ms 就够快」向量检索的延迟分布长尾明显，p99 可能是 p50 的 5–10 倍，要看 p99
「资源占用低就是好」占用低可能意味着索引没建完、或走了暴力扫描

并发与吞吐的关系可以用 Little's Law 做个粗算：

并发数 L = 吞吐 QPS × 平均延迟 R
  → QPS = L / R

例：目标 500 QPS、平均延迟 20 ms
  → 需要并发 L = 500 × 0.02 = 10

反过来验证：32 并发、p99 130 ms 时
  → 理论 QPS ≈ 32 / 0.13 ≈ 246（远低于报告的 760，
     说明 p50 决定了吞吐，而 p99 决定了用户感受 —— 两者都要看）

⑤工具选择与各自的坑

工具选择：

工具适合注意
VectorDBBench多引擎横向对比内置数据集；仍要替换成自己的数据复核
ann-benchmarks索引算法层面的 recall-QPS 曲线纯算法视角，不含数据库开销
各产品的 benchmark 脚本单产品深度压测Qdrant / Milvus / Weaviate 都有官方脚本
k6 / locust + 真实 query 集最贴近生产需要自己搭，但结论最可信
pgbench / sysbenchpgvector 的 SQL 层压测要自己写向量查询 SQL
无论用哪个工具，query 集必须来自真实日志。用随机向量压测会高估性能，因为随机向量的分布比真实 embedding 更均匀、更难区分，某些索引结构反而更快。

⑥速记卡

公开 benchmark

只能排除明显不合适的选项，不能用于决策。

八个前提

规模/维度/度量/索引参数/查询参数/recall/过滤/并发缓存硬件。

最重要一条

没有 recall 数字的 QPS 没有意义。

顺序

ground truth → 灌数据等索引建完 → 预热 → 扫并发。

拐点判读

QPS 不增而 p99 快速上升处 = 饱和点，别报后面的数字。

Little's Law

QPS = 并发 / 平均延迟，用于粗算所需并发。

看 p99

向量检索长尾明显，p99 常是 p50 的 5–10 倍。

query 集

必须来自真实日志，随机向量的结论不可信。

压测最容易犯的错不是选错工具，而是在索引没建完、缓存没预热的情况下测出漂亮数字，然后在生产上被打脸。
