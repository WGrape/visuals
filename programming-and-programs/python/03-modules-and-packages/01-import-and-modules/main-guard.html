if __name__ == "__main__"：模块入口守卫

这行看似仪式感的代码，决定了「同一份 .py 既能当库被 import，又能当脚本直接跑」。理解 __name__ 在两种场景下的区别，是写出可复用、可测试模块的分水岭。

__name__可复用可测试无副作用Windows 多进程
__name__ 是什么为什么需要可复用与可测试Windows 多进程
__name__ 是什么

每个模块都自带一个 __name__ 变量

当文件被直接运行（python foo.py）时，__name__ 被设为字符串 "__main__"；当文件被导入时，__name__ 等于它自己的模块名。守卫就是靠这个区别分流。

# foo.py
print(__name__)   # 直接运行 → "__main__"
                 # 被 import   → "foo"

if __name__ == "__main__":
    main()          # 只有直接运行时才执行

把「程序入口」包进守卫，模块顶层就只剩下定义（函数/类/常量），没有自动执行的副作用——这正是导入系统期望的「干净模块」形态。

为什么需要

不加守卫会发生什么？

若把「启动逻辑」裸写在顶层，别人 import 你的模块时这些逻辑会立刻执行——可能连数据库、弹窗、甚至进入无限循环，导致无法把你的代码当库复用。

❌
无守卫
import 即触发 main()，副作用不可控
✅
有守卫
import 只拿定义，运行才触发入口
# 反例：测试这个模块会直接把服务起起来
app.run()          # 裸写在顶层，import 就执行

# 正例：把入口收进守卫
def main():
    app.run()
if __name__ == "__main__":
    main()
⚠️ 即使你「现在只把它当脚本用」，也建议加上守卫。未来把它拆成可复用模块、或写单元测试时，这一行能省掉大量重构。
可复用与可测试

守卫让「库」和「工具」合二为一

同一文件：对外暴露函数供其它代码 import 调用，对内提供命令行入口供人直接运行。测试时 import 它、只测函数，不会被入口代码干扰。

# 既能被 import，又能当 CLI 跑
def add(a, b): return a + b

if __name__ == "__main__":
    # 命令行入口：解析参数、打印结果
    import sys
    print(add(int(sys.argv[1]), int(sys.argv[2])))

# 别处：from calc import add  ← 不会触发上面的打印
进阶：参数解析交给 argparse，入口逻辑放进 main() 并返回退出码；这样既能 sys.exit(main())，也方便测试 main 的返回值。
Windows 多进程

多进程代码必须进守卫，否则无限递归 fork

Windows 没有 fork，multiprocessing 靠「重新 import 主模块」来重建子进程。若进程启动代码不在 __main__ 守卫里，子进程一导入又启动进程、再导入……死循环。

import multiprocessing as mp

def f(x): return x * x

# 必须收进守卫，Windows 下才不会递归爆炸
if __name__ == "__main__":
    with mp.Pool(4) as p:
        print(p.map(f, [1, 2, 3]))

这跟线程/进程/协程选型直接相关：多进程是绕过 GIL 做 CPU 并行的主要手段，而它的可移植写法强制要求这一行守卫。

导入一个模块时到底发生了什么

理解入口守卫的前提，是先理解导入会执行模块代码。Python 里没有「声明」和「执行」的分离，模块顶层的每一行语句在导入时都会真跑一遍。

导入流程：模块顶层代码会被执行，而且只执行一次
导入即执行顶层语句都会跑，包括打印、建连接、起线程
只执行一次多次导入同一个模块，缓存保证只跑一次
每次都新建命名空间所以模块间同名变量互不干扰
入口名字的取值作为主程序运行时是一个值，被导入时是另一个值

入口名字的两种取值

每个模块都有一个记录「我是怎么被加载的」的变量。它的取值决定了这段顶层代码是「被直接运行」还是「被别人导入」，这正是入口守卫判断的依据。

加载方式该变量的取值守卫内的代码典型场景
直接运行该文件主程序标记会执行命令行工具、脚本入口
被其他模块导入模块名不执行作为库被复用
用模块方式运行主程序标记会执行运行包内模块
被交互环境加载模块名不执行调试与探索
# 推荐的入口写法 def main(): # 真正的逻辑放在函数里，便于被测试和复用 print("running") if __name__ == "__main__": main() # 为什么把逻辑放进函数？ # 1) 顶层变量会变成模块级全局，放进函数才是局部 # 2) 函数可以被测试直接调用 # 3) 导入时不会有任何副作用 # 命令行参数解析也放进去 if __name__ == "__main__": import argparse p = argparse.ArgumentParser() p.add_argument("--verbose", action="store_true") args = p.parse_args() main(args)

最常见的错误：把启动逻辑直接写在顶层。这样一旦有人导入这个模块，服务就启动了、文件就被写了、线程就跑起来了，而导入方往往完全不知情。

哪些代码必须放进守卫

多进程必须放进去

这是硬要求。多进程在启动子进程时会重新导入主模块，如果创建进程的代码在顶层，子进程又去创建新的子进程，会无限递归地分裂下去。放进守卫后，子进程导入时入口名字不是主程序标记，就不会再触发创建。

有副作用的代码都应该放进去

包括：启动服务、建立连接、读写文件、注册信号处理、打印大量输出、运行耗时任务。判断标准很简单：如果别人只是想用你这个函数，这段代码应该跑吗？不该跑，就放进守卫。

多进程启动代码必须放进守卫，否则递归分裂
服务启动导入时不该自动起服务
资源连接建立连接的动作不该在导入时发生
文件读写避免导入即写文件
注册信号库模块不应注册全局信号
耗时任务导入应快速完成
命令行解析只有作为入口时才需要
测试代码不要放在模块顶层

深入自检：入口守卫的六个问题

不加守卫会怎样？

模块被导入时，顶层的所有语句都会执行。轻则打印多余输出、建了没用的连接；重则启动服务、起线程、写文件，甚至在多进程场景下递归创建进程。这类问题在本地直接运行时完全看不出来，只在被导入时才暴露。

为什么多进程一定要加？

因为它的启动机制需要重新导入主模块来还原函数定义。如果创建进程的代码在顶层，这次导入又会执行创建，形成无限递归。这是唯一一个「不加就必然出错」的场景。

逻辑一定要放进函数吗？

不是强制，但强烈建议。直接写在守卫里也能工作，但放进函数后可以被测试调用、可以被其他入口复用，而且避免把临时变量变成模块级全局。

一个文件可以有多个入口吗？

可以写多个判断，但通常没必要。更常见的做法是只有一个入口函数，在里面根据参数分发到不同子命令。

包里也有类似机制吗？

有。包目录下可以放一个特殊文件作为入口，用模块方式运行包时它会被执行。它内部同样建议只做一件事：调用真正的入口函数。

交互式环境里为什么取不到主程序标记？

因为交互环境本身是主程序，你在里面定义或导入的模块都不是以主程序身份加载的。所以要调试入口逻辑，应该直接运行文件，或者显式调用入口函数。

__name__ 的取值规则与三种启动方式

if __name__ == "__main__" 的判断依据是解释器给模块起的这个名字。只有被当作「主程序」直接运行的那一个模块叫 __main__，其他都叫自己的模块名。

启动方式__name__ 的值说明
python app.py"__main__"最直观；sys.path[0] = 脚本所在目录
python -m app"__main__"推荐；sys.path[0] = 当前目录，且用的是包路径导入
import app"app"不会执行 guard 里的代码
from pkg import app"pkg.app"同上
python -c "import app""app"同上
exec(open('app.py').read())"__main__"在哪个作用域执行就是那个作用域的名字

实测 __name__ 取值

# 文件：demo.py
print("top:", __name__)

def main():
    print("main():", __name__)

if __name__ == "__main__":
    main()

# 三种跑法的输出对比：
# $ python demo.py
#   top: __main__
#   main(): __main__
#
# $ python -c "import demo"
#   top: demo                     <- 只打印这一行，guard 里的没执行
#
# $ python -m demo
#   top: __main__                 <- 同 python demo.py

推荐的标准结构：把所有逻辑放进函数，guard 里只写一行 main()。这样做的好处是：① 模块被导入时不执行任何副作用；② 其他程序可以 from app import main 复用；③ 单元测试可以直接调用 main() 而不必起子进程。

必须用 guard 的场景与常见坑

场景不加 guard 会怎样说明
multiprocessing（spawn/forkserver）无限递归创建子进程，直接崩子进程会重新导入主模块；不加 guard 就会再次执行创建子进程的代码
模块被 import 时跑起来导入即执行，副作用不可控测试、文档生成、打包都可能触发
Windows / macOS（默认 spawn）必崩Unix 默认 fork 不重新导入，所以「在我机器上好好的」
python -m 启动包相对导入失败需要包结构 + guard 配合

multiprocessing 与 CLI 入口

# 正确写法（multiprocessing 在 Windows/macOS 上必须这样）
import multiprocessing as mp

def worker(x):
    return x * x

def main():
    with mp.Pool(4) as pool:
        print(pool.map(worker, range(10)))

if __name__ == "__main__":      # 少了这行，spawn 模式下会无限创建子进程
    mp.freeze_support()         # 打包成 exe（Windows）时也需要
    main()

# 命令行入口的推荐写法（可复用、可测试）
#   mypkg/cli.py
def main(argv=None):
    import argparse
    p = argparse.ArgumentParser(prog="mypkg")
    p.add_argument("--n", type=int, default=1)
    args = p.parse_args(argv)
    print(args.n * 2)
    return 0

if __name__ == "__main__":
    raise SystemExit(main())

#   pyproject.toml 里注册成命令（装完就能 mypkg 直接跑）
#   [project.scripts]
#   mypkg = "mypkg.cli:main"
  • Jupyter / REPL 里 __name__ 是 "__main__"（在单元格里），所以直接粘贴带 guard 的代码会执行——这与「导入不执行」的直觉相反。
  • 不要在 guard 外做重活：模块顶层的 open()、连接数据库、启动线程，都会在任何一次 import 时执行。放在 main() 里。
  • 不要在 guard 里定义函数给外部用：被导入时这些函数根本不存在。函数要定义在模块顶层。
  • 测试友好：main(argv) 接受可选参数列表，测试时直接 main(["--n", "3"])，不用 mock sys.argv。
为什么 Windows 上多进程不加 guard 会崩？

因为 Windows 没有 fork()，spawn 模式要重新导入主模块才能在子进程里重建函数对象。导入时模块顶层代码全部执行——包括「创建 Pool」那行，于是子进程又去创建孙进程，无限递归。Unix 默认 fork（直接复制内存，不重新导入）所以不报错，但 Python 3.14 起 Linux 默认也改成 forkserver 了，所有平台都必须加 guard。

python -m pkg 和 python pkg/main.py 有什么区别？

两个关键差异：① sys.path[0]——-m 是当前工作目录，直接跑脚本是脚本所在目录，这决定了能 import 到什么；② 包的初始化——-m pkg 会先执行 pkg/__init__.py，直接跑 pkg/main.py 不会，因此 main.py 里的相对导入会失败。所以带包结构的项目一律用 -m。

可以用 if __name__ == "__main__" 做单元测试吗？

能但不推荐。代码写在 guard 里就无法被测试导入（导入时 __name__ 不是 __main__）。正确做法是逻辑放函数、guard 只做调用，测试直接 import 函数。这也是「main guard 里只写一行 main()」这条经验的核心理由。
