SQLite 事务与锁

autocommit、五级锁状态、WAL 模式下的读写并发，以及写热点瓶颈。

① 事务与 ACID② 三种事务模式与锁的获取时机③ 锁的层级与状态机④ 并发控制实践⑤ 常见问法

① 事务与 ACID

BEGIN;                  -- 默认 DEFERRED（延迟获取锁）
-- 或 BEGIN IMMEDIATE;  -- 立即获取写锁（推荐用于写事务）
-- 或 BEGIN EXCLUSIVE;  -- 独占（其他连接连读都不行，WAL 下）

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;                 -- 提交（fsync）
-- ROLLBACK;            -- 回滚

-- 保存点（部分回滚）
SAVEPOINT sp1;
-- ... 一些操作
ROLLBACK TO sp1;        -- 回滚到保存点，事务继续
RELEASE sp1;

原子性

靠 rollback journal 或 WAL 实现；崩溃后可回滚或重做

一致性

约束（NOT NULL、UNIQUE、CHECK、外键）在事务内检查

隔离性

WAL 下提供快照隔离：读事务看到开始时的快照，不受并发写影响

持久性

由 synchronous 控制 fsync 时机（FULL/NORMAL/OFF）

② 三种事务模式与锁的获取时机

模式锁获取时机特点适用
BEGIN DEFERRED（默认）首次读时取 SHARED；首次写时才升级为 RESERVED延迟加锁，但可能在升级时失败（SQLITE_BUSY）只读或先读后写的短事务
BEGIN IMMEDIATE开始时即取 RESERVED 写锁避免中途升级失败，失败可安全重试写事务推荐
BEGIN EXCLUSIVE开始时取 EXCLUSIVE 独占锁其他连接连读都被阻塞（WAL 下读仍允许）批量导入、迁移
DEFERRED 的经典问题：两个事务都以 DEFERRED 开始、先读后写，读到快照后再想升级为写锁时，会发现对方已持有写锁 → SQLITE_BUSY 且无法安全重试（因为读到的快照已失效）。对策：写事务一律用 BEGIN IMMEDIATE，把冲突暴露在事务开始处，便于重试。

③ 锁的层级与状态机

WAL 模式下的差异：写者持有写锁时读者仍可正常读（读的是 WAL 之前的快照），因此不会出现「写阻塞读」。但写与写仍然互斥。

④ 并发控制实践

-- 必备设置
PRAGMA journal_mode = WAL;      -- 读写不互斥
PRAGMA busy_timeout = 5000;     -- 遇到锁等待 5 秒
PRAGMA foreign_keys = ON;       -- 每个连接都要开

-- 写事务推荐写法（以 Python 为例）
import sqlite3
conn = sqlite3.connect('app.db', isolation_level=None)   # 关闭隐式事务
conn.execute("PRAGMA journal_mode=WAL")
conn.execute("PRAGMA busy_timeout=5000")

def transfer(a, b, amount):
    for attempt in range(3):                  # 失败重试
        try:
            conn.execute("BEGIN IMMEDIATE")   # 立即取写锁
            conn.execute("UPDATE accounts SET balance=balance-? WHERE id=?", (amount, a))
            conn.execute("UPDATE accounts SET balance=balance+? WHERE id=?", (amount, b))
            conn.execute("COMMIT")
            return True
        except sqlite3.OperationalError as e:
            conn.execute("ROLLBACK")
            if 'locked' not in str(e) and 'busy' not in str(e):
                raise
    return False

① 写事务用 IMMEDIATE

把锁冲突提前暴露，便于安全重试

② 设置 busy_timeout

遇到锁时等待而非立刻失败

③ 事务要短

绝不在事务里做网络请求、耗时计算

④ 单写者

应用层用队列/锁把写操作串行化

⑤ 读连接池

多个只读连接并发；WAL 下不受写阻塞

⑥ 重试机制

捕获 SQLITE_BUSY 后重试（配合 IMMEDIATE）

⑤ 常见问法

Q：SQLite 支持并发写吗？

A：不支持真正的并发写：写锁是库级的，同一时刻只允许一个写者。但读可以并发——尤其在 WAL 模式下，读不阻塞写、写不阻塞读（读者看到事务开始时的快照）。因此它的定位是「单写者 + 多读者」：适合移动 App、桌面软件、嵌入式、边缘缓存、低写入 QPS 的 Web 应用；不适合高并发写入与多机共享（网络文件系统上文件锁不可靠）。实践：应用层把写串行化 + 开启 WAL + busy_timeout + 短事务。

Q：BEGIN、BEGIN IMMEDIATE、BEGIN EXCLUSIVE 有什么区别？

A：BEGIN（DEFERRED，默认）：开始时不加锁，首次读时取 SHARED，首次写时才尝试升级为 RESERVED——问题在于升级可能失败（SQLITE_BUSY），且此时已读到的快照失效，无法安全重试；BEGIN IMMEDIATE：立即获取 RESERVED 写锁，冲突在事务开始时就暴露，可安全重试——写事务推荐；BEGIN EXCLUSIVE：获取 EXCLUSIVE 独占锁，其他连接连读都被阻塞（WAL 模式下读仍允许），用于批量导入与迁移。口诀：读用 DEFERRED，写用 IMMEDIATE，迁移用 EXCLUSIVE。

Q：为什么会出现 SQLITE_BUSY / database is locked？

A：因为写锁是库级独占的：当有连接持有写锁（RESERVED/PENDING/EXCLUSIVE）时，其他连接想写就会被拒绝。常见诱因：① 写事务太长（事务里做了网络请求、大量计算、等待用户输入）；② 并发写连接过多；③ 使用了 DEFERRED 事务导致中途升级失败；④ 未设置 busy_timeout，遇锁立刻报错；⑤ WAL 检查点被阻塞导致 WAL 文件堆积。对策：设 busy_timeout、用 IMMEDIATE、缩短事务、应用层串行化写、必要时拆分数据库文件。

Q：WAL 模式下还需要担心锁吗？

A：仍需担心「写与写」的冲突，但不必担心「写阻塞读」。WAL 让读者读取事务开始时的快照，因此写事务进行中读者仍可正常查询——这是相对默认 rollback journal 模式的巨大改进。但写锁依然独占：同一时刻只能有一个写事务，第二个写者会收到 SQLITE_BUSY。此外：WAL 需要检查点把日志合并回主库文件，若检查点被长读事务阻塞，WAL 文件会持续增长。实践：WAL + busy_timeout + 短事务 + 单写者队列，基本可以消除锁问题。

Q：什么是 SQLITE_BUSY_SNAPSHOT？怎么处理？

A：它发生在 WAL 模式下：事务以 DEFERRED 开始并读取了某个快照，之后想升级为写事务，但期间已有其他写者提交——此时读到的快照已过期，SQLite 拒绝升级并返回 SQLITE_BUSY_SNAPSHOT（而非普通 BUSY）。关键：这种情况不能通过等待解决，必须回滚整个事务重新开始。处理：① 捕获该错误 → ROLLBACK → 用 BEGIN IMMEDIATE 重新开始；② 根本对策：写事务一律用 BEGIN IMMEDIATE，从一开始就拿写锁，就不会出现「读到过期快照后想写」的情形。

Q：外键约束为什么不生效？

A：因为 SQLite 默认关闭外键（PRAGMA foreign_keys 默认 OFF，为向后兼容）。每个连接都必须显式执行 PRAGMA foreign_keys = ON;，且必须在事务之外执行（事务内无效）。表现：插入不存在的外键值、删除父行时子行未级联，且不报错。补充：① 该设置不持久化，连接池新建连接时要重新设置；② 可用 PRAGMA foreign_key_check; 检查现有数据是否有违反；③ 开启后 ON DELETE CASCADE、ON UPDATE 等动作才会生效。

SQLite 的锁与关键参数

概念取值 / 默认说明
锁状态UNLOCKED → SHARED → RESERVED → PENDING → EXCLUSIVE写操作最终要拿到 EXCLUSIVE
journal_modeDELETE（默认）/ WALWAL 是必选项：读写不互相阻塞
synchronousFULL（默认）/ NORMAL / OFFNORMAL 在 WAL 下安全且快；OFF 断电可能损坏
busy_timeout0（不等待）建议设 5000ms，否则立刻报 database is locked
cache_size-2000（2MB）负值是 KB，正值是页数；可调到 -64000（64MB）
wal_autocheckpoint1000 页WAL 达到多少页自动 checkpoint（1000 页 ≈ 4MB）
foreign_keys关闭必须每个连接显式 PRAGMA foreign_keys=ON
写并发同时只有 1 个写者这是 SQLite 的根本限制
读并发（WAL）多个读者不阻塞写者DELETE 模式下读会阻塞写

WAL vs DELETE 的实际差别：DELETE 模式下，写入时要拿 EXCLUSIVE 锁，所有读都被阻塞；WAL 模式下写者只把修改追加到 -wal 文件，读者读的是原 db 文件 + wal，读写不互斥。这是 SQLite 并发能力的分水岭。

配置与代码

-- 必做的初始化（每个连接都要执行）
PRAGMA journal_mode = WAL;           -- 持久性设置，执行一次即可
PRAGMA synchronous = NORMAL;         -- WAL 下安全，比 FULL 快很多
PRAGMA busy_timeout = 5000;          -- 遇锁等 5 秒而不是立即报错
PRAGMA foreign_keys = ON;            -- 每个连接都要设！
PRAGMA cache_size = -64000;          -- 64MB 缓存
PRAGMA wal_autocheckpoint = 1000;    -- 默认 1000 页

-- 查看当前设置
PRAGMA journal_mode;
PRAGMA busy_timeout;
# Python 正确用法
import sqlite3

def connect(path):
    con = sqlite3.connect(path, timeout=5.0, isolation_level=None)  # autocommit 模式
    con.execute("PRAGMA journal_mode=WAL")
    con.execute("PRAGMA synchronous=NORMAL")
    con.execute("PRAGMA busy_timeout=5000")
    con.execute("PRAGMA foreign_keys=ON")
    return con

# 写事务：用 BEGIN IMMEDIATE，避免死锁升级
con = connect("app.db")
con.execute("BEGIN IMMEDIATE")       # 立即拿 RESERVED 锁，防止升级失败
try:
    con.execute("UPDATE accounts SET bal = bal - 100 WHERE id = 1")
    con.execute("UPDATE accounts SET bal = bal + 100 WHERE id = 2")
    con.execute("COMMIT")
except Exception:
    con.execute("ROLLBACK")
    raise

# 关键：BEGIN IMMEDIATE vs BEGIN DEFERRED
# DEFERRED（默认）：先读时拿 SHARED，写时想升级到 RESERVED
#   -> 若此时别人也在写，升级会失败并报 "database is locked"，且无法重试
# IMMEDIATE：一开始就拿 RESERVED，避免升级失败
#   -> 写事务一律用 BEGIN IMMEDIATE

排障清单

症状原因处理
database is locked没设 busy_timeout；或写并发设 busy_timeout=5000；写事务用 BEGIN IMMEDIATE；串行化写
写操作偶发失败（升级失败）用了 DEFERRED 事务先读后写改成 BEGIN IMMEDIATE
读也变慢了journal_mode 是 DELETE（读写互斥）改成 WAL
WAL 文件一直很大有长事务阻止 checkpoint缩短事务；检查是否有未关闭的读连接；手动 PRAGMA wal_checkpoint(TRUNCATE)
外键约束没生效每个连接都要设 foreign_keys=ON封装连接函数统一设置
多进程写入冲突SQLite 只支持单写者写操作集中到一个进程；大数据量换 MySQL/PG
断电后数据库损坏synchronous=OFF至少用 NORMAL；关键数据用 FULL
database or disk is full磁盘满或 WAL 太大清磁盘；checkpoint 收缩 WAL

SQLite 的适用边界：单写者 + 本地存储 + 中小数据量（< 100GB）是它的主场。一旦需要多机并发写，就应该换客户端-服务器型数据库，这是架构性的限制，调参解决不了。
