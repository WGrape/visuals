实时视频推理排队：模型吞吐够不够，画面结果新不新

用 30 FPS 摄像头与 10 FPS 模型手算队列积压，比较逐帧处理、抽帧、丢旧帧和动态批处理。

实时性的核心是结果对应现在

一个摄像头每秒送来 30 帧，模型每秒只能处理 10 帧。若所有帧都排进 FIFO 队列，队列每秒净增加约 20 帧；过 5 秒积压约 100 帧，相当于摄像头 3.3 秒的视频。此时模型可能一直满负荷运行，吞吐看起来很高，报警却反映几秒前的画面。安防、交通或互动产品更关心“从采集到结果”的年龄，而不是模型每秒完成多少帧。

完整链路还有采集、编码、网络、解码、预处理、模型、后处理和结果发布。每一帧应带可信的采集时间戳，记录各阶段时间；只用推理开始到结束的耗时会漏掉最长的队列等待。

四种常见处理方式

逐帧处理适合离线归档或对每帧完整性有要求的任务，但持续超负载时不能叫实时。按固定间隔抽帧，例如每 3 帧取 1 帧，把 30 FPS 降到 10 FPS，平均负载接近模型容量；若一个事件只持续 50 毫秒，仍可能刚好漏掉。丢旧帧、保留最新帧能保持画面新鲜，却舍弃过程信息；适合只关心当前状态的任务。动态批处理把多路摄像头的帧合并，提高 GPU 利用率，但等凑批的时间会增加首帧延迟。

选哪种策略由业务语义决定。火灾烟雾可能持续较久，可抽帧加连续确认；生产线高速瞬时缺陷可能需要硬件触发、专用轻模型或边缘预筛，不能靠随机丢帧碰运气。

算一算队列上限

若业务要求结果年龄不超过 500 毫秒，摄像头 30 FPS，每路理论上半秒会产生 15 帧。队列若允许累积 100 帧，仅队列等待就可能超过上限。可为每路设置很短的“最新帧槽”，新帧覆盖未处理旧帧，并把丢帧数、结果年龄和事件漏检率作为共同指标。模型容量仍只有 10 FPS，不能宣称覆盖了所有 30 帧；新鲜度改善与完整性损失要同时报告。

多路摄像头共用 GPU 时还要保证公平性。一个高帧率源不能占满队列，让低帧率但更重要的摄像头长期饥饿。可按源限速、加权调度或设置优先级，随后观察每路 P95 年龄和漏检率。

策略结果新鲜度保留的信息代价
全部 FIFO超载后持续变差每帧都处理内存和等待不断增加
固定抽帧较稳定规则采样时刻可能漏掉短事件
只保留最新较新当前状态舍弃过程帧
动态批处理依等待上限多路吞吐更高凑批增加延迟

时间戳与帧重排

编码视频可能有 B 帧等重排，解码输出顺序、显示时间戳和网络到达顺序不一定相同。推理若按网络包到达时间排序，可能把事件前后颠倒。应在解码后使用正确的展示时间戳或采集时间戳，并处理时钟不同步、丢包和时间戳跳变。直播切换、摄像头重启或网络恢复时，旧缓存帧可能突然补到；过旧帧要按业务策略丢弃或转入离线补算。

检测结果也要携带原帧 ID、采集时间和模型版本。下游看板不能只显示“有人”而不标明判断对应哪一秒；报警系统更需要知道是新事件还是迟到的旧帧。

批处理不是免费加速

GPU 一次处理 8 帧可能比单帧调用 8 次总耗时短，但第一帧要等其他帧凑齐。可设置最大批量和最大等待时间，例如最多 8 帧或等待不超过 40 毫秒，并按实时性目标调节。批处理还可能把不同分辨率画面补齐到共同尺寸，增加计算或影响小目标效果。固定在实验室测吞吐，再直接推线上 P99 延迟，结论常会失真。

背压应向摄像头接入或抽帧层反馈，不能只在模型前无限加内存队列。队列长度、丢帧原因、GPU 利用率、预处理耗时与结果年龄共同决定瓶颈位置。

事件级结果怎样稳定

单帧模型在强光、遮挡时可能偶尔误报。可要求同一目标连续若干帧出现再告警，或用轨迹跟踪减少抖动；但连续确认会增加事件发现延迟，抽帧还会改变“连续三帧”对应的真实时间。规则宜写成真实毫秒和可观察帧数的组合，并在处理缺帧时明确定义行为。事件结束也要有滞后或冷却窗口，避免“出现—消失”反复通知。

验收要用带时间标注的视频记录“事件发生到报警”的分布，而不只统计逐帧准确率。对短事件、遮挡、网络卡顿和摄像头重启分别测漏报与延迟。

一次端到端压测

同时接入目标数量和分辨率的摄像头，逐步从 5 路加到 20 路。记录采集 FPS、输入 FPS、实际推理 FPS、每路丢帧、队列深度、P50/P95/P99 结果年龄和事件级召回。分别试 FIFO、每 3 帧抽 1、只保留最新帧和有限等待的动态批处理，画出新鲜度与漏检率的关系。最终配置要写清在超载时优先保留什么、舍弃什么，而不是只给一个“实时 30 FPS”的口号。

实时推理的时延预算与帧率

指标典型目标说明
端到端时延（玻璃到玻璃）< 200ms超过 200ms 人能明显感到「不同步」
视频会议可接受延迟< 150ms超过 400ms 对话开始互相打断
云端游戏 / 云渲染< 60ms含编码 + 网络 + 解码，预算极紧
30 FPS 的帧间隔33.3ms推理必须快于帧间隔，否则必然丢帧
60 FPS 的帧间隔16.7ms很多模型单帧推理就超过 16.7ms，必须靠批处理/降分辨率
批大小 B 的吞吐增益B=8 相比 B=1 常 3~5×但时延也上升到约 2~3×，是吞吐与时延的取舍
队列利用率 ρ = λ/μ建议 ≤ 0.7ρ→1 时排队时延趋于无穷（M/M/1 的 Wq ∝ 1/(1-ρ)）

排队论判据：设到达率 λ（帧/秒）、服务率 μ（帧/秒）。平均排队时延 Wq = ρ / (μ - λ)。当 ρ 从 0.5 升到 0.9，Wq 从 2ms 涨到 18ms（μ=500 时）——容量利用率超过 0.8 后延迟会指数恶化，这是实时系统最核心的直觉。

丢帧策略与实现

# 最实用的实时推理队列：只保留最新帧，过期帧直接丢弃
import threading, queue, time

# maxsize=1 的队列 = 天然背压：新帧挤掉旧帧，保证处理的永远是「最新鲜」的帧
frame_q = queue.Queue(maxsize=1)

def producer(cap):
    while True:
        ok, frame = cap.read()
        if not ok: break
        if frame_q.full():
            try: frame_q.get_nowait()      # 丢弃旧帧
            except queue.Empty: pass
        frame_q.put((time.time(), frame))  # 带上采集时间戳

def consumer(model):
    while True:
        t0, frame = frame_q.get()
        freshness = time.time() - t0       # 帧龄，用于判断是否已过期
        if freshness > 0.2:                # 超过 200ms 预算，跳过推理直接显示上一帧结果
            continue
        out = model.infer(frame)
# 动态批处理（dynamic batching）：在时延预算内尽量凑批
# Triton Inference Server 的 preferred_batch_size + max_queue_delay_microseconds
# 配置示例（config.pbtxt）
dynamic_batching {
  preferred_batch_size: [4, 8]        # 凑到 4 或 8 就发，不到就等延时上限
  max_queue_delay_microseconds: 5000  # 最多等 5ms，超时就按现有批次发
}
# 效果：单卡吞吐提升 3~4x，p99 时延增加约 5ms（= queue delay 上限 + 批处理时间）

实时链路排障

症状原因处理
时延随并发线性上升GPU 排队，ρ 接近 1限流（拒绝超额请求）比排队好；或降分辨率/帧率把 μ 提上去
间歇性卡顿（jitter）批处理凑不满时等待 max_queue_delay；或 GPU 被其他任务抢占固定批大小 + 超时发送；用 MPS / 独占 GPU 避免抢占
画面越来越滞后队列无限增长（生产者快于消费者）必须用有界队列（maxsize=1 或 2），让旧帧被丢弃而不是堆积
丢帧率突然升高输入源帧率波动 / 解码慢统计 frames_dropped / frames_total；先看是解码还是推理成为瓶颈
GPU 利用率低但延迟高batch=1 导致 kernel 启动开销占比大；或数据搬运（H2D/D2H）耗时开启动态批处理；用 pinned memory + 异步拷贝；尝试 CUDA Graph 减少启动开销
首帧特别慢模型加载 / CUDA 初始化 / 显存分配服务启动时预热一次；CUDA context 初始化常需 200ms~1s
  • 确定性优先：实时系统里「稳定的 100ms」比「平均 50ms 但偶尔 500ms」体验好得多，优化目标是 p99 而不是平均值。
  • 降级顺序：降帧率 → 降分辨率 → 跳帧推理（每 N 帧推一次，中间用光流/插值）→ 返回上一帧结果。

深入自检

为什么队列要设为 maxsize=1 而不是更大的缓冲？

实时场景里旧帧没有价值——用户要的是「现在」的画面。大缓冲只是把延迟藏起来，画面越播越滞后。maxsize=1 是主动丢帧，用「丢掉的帧」换「新鲜的帧」。

批处理会破坏实时性吗？

会，但可以控制在预算内。关键参数 max_queue_delay_microseconds 就是「为凑批愿意等多久」，设为 5ms 意味着最坏情况多等 5ms。时延预算 200ms 时完全可以接受，换来 3~4 倍吞吐。

ρ 到 0.9 到底有多糟？

M/M/1 下 Wq = ρ/(μ-λ)。μ=500 帧/秒：ρ=0.5→2ms，ρ=0.8→8ms，ρ=0.9→18ms，ρ=0.95→38ms。利用率从 0.8 到 0.95，延迟涨了近 5 倍，而吞吐只涨了 19%。这就是留余量的理由。

怎么判断该优化模型还是该加卡？

先算单卡的 μ（实测吞吐）。若 λ/μ > 0.7 且模型已量化/已 TensorRT 化，就该加卡；若模型还是 FP32 未优化，先把 μ 提上去，通常能拿 2~5 倍，比加卡便宜得多。

自检

模型始终 100% 忙、每秒处理 10 帧，就能说明实时报警没有延迟积累吗？

不能。30 FPS 输入到 10 FPS 处理的 FIFO 队列每秒积压约 20 帧，结果会越来越旧。
