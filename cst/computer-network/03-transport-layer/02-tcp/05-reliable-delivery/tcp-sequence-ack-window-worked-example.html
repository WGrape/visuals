TCP 序列号、ACK 与滑动窗口手算

用四个连续报文段算确认号、接收窗口和在途数据，区分流量控制与拥塞控制。

序列号按字节计数

TCP 为字节流编号，序列号表示报文段中第一个数据字节的位置；ACK 号通常表示接收方下一步期待的字节序号。假设发送方的第一个数据字节序号为 1000，发送 300 字节后，下一段数据从 1300 开始。接收方完整收到这 300 字节，返回 ACK=1300，表示小于 1300 的连续字节已收到。不能把“第一个包”当成序号 1 来数，因为序列号不是报文段编号。

SYN 和 FIN 在序列空间各占一个位置，即使不携带应用数据。建立连接时若 SYN 的序列号是 999，首个数据字节常从 1000 开始。抓包工具可能显示相对序列号，把真实初始序号归零以便阅读；计算时先确认工具显示的是相对值还是线上原值。

路径图：乱序到达的累计确认

箭头表示本例中的处理次序；每个环节的状态都要分别验证，不能由前一环节成功推断后一环节成功。

乱序到达如何确认

发送四段：1000–1299、1300–1599、1600–1899、1900–2199，每段 300 字节。接收方先收到第一段，发 ACK=1300；第三段先于第二段到达时，即便 1600–1899 已暂存，累积确认仍停在 ACK=1300，因为中间缺 1300–1599。第二段到达后，若第三段也还在接收缓冲，ACK 可以一次推进到 1900。第四段随后到达，ACK 变成 2200。

若双方协商了 SACK，接收方还能附上“1600–1899 已收到”的信息，帮助发送方只重传缺口。普通 ACK 与 SACK 的含义不同：前者说明连续前缀，后者补充非连续区块。重复 ACK 可能由丢包或乱序造成，不应看见三次重复 ACK 就直接断言某条链路物理丢包。

滑动窗口允许发多少

接收窗口 rwnd 告诉发送方接收方还能缓存多少未被应用读取的数据；拥塞窗口 cwnd 是发送方对网络可承受在途数据的估计。发送方有效可发送量受到两者较小值约束。若 cwnd=6000 字节、rwnd=4000 字节，当前已有 2500 字节在途，粗略可再发 1500 字节；若 rwnd 随接收应用读取而变化，后续又可增加。实际实现还受 MSS、窗口缩放、重传和数据可用性影响。

在途数据是已经发出但尚未被累计确认的数据，不等于套接字发送缓冲中所有待发送内容。ACK 到达后窗口向前滑动，发送方可以继续发新字节。若接收应用不读数据，rwnd 可能缩到零；发送方暂停正常数据发送并使用零窗口探测等机制等待窗口重新打开。

流量控制与拥塞控制

rwnd 防止快发送方淹没慢接收方，问题发生在接收端缓冲；cwnd 防止发送方过度注入网络，问题发生在路径中的路由器和链路。两者都可能限制吞吐，但修复方法不同。若 rwnd 长期很小，先看接收应用是否及时消费、是否有内存压力；若 cwnd 小且重传、RTT 波动增加，要看网络拥塞或丢包。

单看“带宽 1 Gbps”不能推出单连接吞吐。发送窗口与 RTT 给出窗口受限上限：窗口 64 KiB、RTT 100 毫秒时，理想上限约 655 KiB/s，约 5.24 Mbps，远低于物理带宽。窗口扩大、并发连接或降低 RTT 可能改善吞吐，但还要看丢包与服务器能力。

重传与计时器

若某段丢失，发送方可因重复 ACK 触发快速重传，或等重传超时再发送。超时阈值根据 RTT 估计与抖动调整，不能固定等于一次 RTT。重传数据的序列号与原数据相同，因此抓包出现“同一序列范围再次出现”是线索；也可能是抓包点看到的乱序、设备复制或抓包缺失造成误判。

若 ACK 丢失，后续累计 ACK 可能覆盖前一个 ACK，而无需重传对应数据。TCP 保证最终可靠交付依赖发送端保留未确认数据、接收端去重与有序交付，不能把每个数据段简单理解为必须单独等一个 ACK 才能发下一个。

实战观察点

抓包时按同一连接四元组过滤，记录相对序列号、数据长度、ACK、窗口、SACK 和时间。选一个小流量连接手工计算三个段的下一期待字节，再和工具标注对照。若计算不一致，先检查 SYN 占位、重传或窗口缩放，而非立刻说抓包工具错误。

性能排查时同时记录 rwnd、cwnd、RTT、重传率和应用读写速率。若只看到 ACK 很慢，可能是接收端应用未读、网络排队或延迟 ACK 策略，单一指标无法定位瓶颈。

序号/确认号/窗口的硬规则

序号 Seq单位是字节；SYN 和 FIN 各占 1 个序号ISN 随机（防伪造、防旧连接串扰）
确认号 ACK值为“期望收到的下一个字节序号”，即已连续收到的数据 +1三次握手第二步 ACK = ISN_client + 1

窗口缩放 Window Scale握手时协商移位因子，最大 14（2^14）实际窗口 = Window × 2^scale

用 tcpdump 验证序号与窗口

# 抓包看绝对序号（-S 关闭相对序号偏移）
tcpdump -i any -nn -S 'tcp and port 80'
# 输出形如：
# 10.0.0.1.54321 > 10.0.0.2.80: Flags [S], seq 3735928559, win 64240, options [mss 1460,sackOK,TS val 1 ecr 0,wscale 7]
#   → 窗口 64240 × 2^7 = 64240 × 128 = 8,222,720 字节 ≈ 7.8 MB

# 只抓握手与窗口通告
tcpdump -i any -nn 'tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0'

Wireshark 默认显示相对序号（从 0 开始），排查真实的序号回绕/乱序问题时要关掉（Edit → Preferences → Protocols → TCP → Relative sequence numbers）。

序号回绕与窗口满的排障

  • 32 位序号回绕：4 GB 数据后序号归零。千兆链路约 34 s 就会绕一圈，10 Gbps 只需 3.4 s → 需要 时间戳选项（TSopt）+ PAWS 来区分“新包”和“迟到的旧包”，否则旧包会被误当新数据接收。
  • 窗口缩放必须双方都开：sysctl net.ipv4.tcp_window_scaling（默认 1）。若中间设备改写/剥离 TCP 选项，或老系统不支持，窗口会退化到 65535，长肥管道吞吐立刻掉到几百 Kbps。
  • 零窗口（Zero Window）：对端通告 win=0 说明其接收缓冲已满（应用不读）。表现是发送完全停滞 + 窗口探测包（每隔 5 s 起指数退避，上限 60 s）。
  • SACK：让接收方告诉发送方“哪几段收到了”，避免一个丢包触发整窗重传。检查 sysctl net.ipv4.tcp_sack（默认 1）。
  • 抓包判别口诀：大量 [TCP Retransmission] → 丢包；大量 [TCP ZeroWindow] → 接收端应用慢；大量 [TCP Dup ACK] → 乱序/丢包触发快重传；[TCP Window Full] → 发送端被接收窗限制。
ACK 号为什么是“下一个期望字节”而不是“已收到的最后一个字节”？

累积确认语义：ACK=N 表示“N 之前的所有字节都已收到”。这样单个 ACK 就能覆盖全部历史，且允许 ACK 丢失（后续 ACK 会覆盖前面的信息）。

抓包里 Seq 一直不变但 ACK 在涨，是什么情况？

典型的纯 ACK 包（无数据）：确认收到的同时自己不发送数据，所以自己的 Seq 不变。常见于单向传输（如下载）的接收方。

自检

先收到 1000–1299 和 1600–1899，累计 ACK 应是多少？

ACK=1300。1600–1899 可由 SACK 报告，但连续前缀仍在 1300 处有缺口。
