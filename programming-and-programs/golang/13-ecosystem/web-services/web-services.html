REST vs gRPC

各有所长

REST/JSON 易调试、浏览器友好、生态广；gRPC/Protobuf 强类型、低延迟、流式，适合服务间高频调用。

// REST：人易读、工具多
GET /users/1

// gRPC：强类型、高效
rpc GetUser(GetUserReq) returns (User);
网关

统一出入口

API 网关做路由、鉴权、限流、熔断；Go 写网关（如基于 gin/kratos）性能强，是微服务常见落点。

内部用 gRPC、对外暴露 REST 时，常由网关做协议转换与聚合。
框架定位

按需取舍

Gin 轻量灵活、生态大；go-zero 内置服务治理（限流/熔断/缓存）；选框架看团队与治理需求，而非一味追新。

本仓库已有专页

Gin、go-zero 等框架的深入用法见 13-ecosystem 下的对应页面，本篇只做生态定位。

怎么选

看边界

对外/前端 → REST；内部高频/流式 → gRPC；要治理 → 带中间件的框架；小服务 → 标准库也能扛。

⚠️ 别为「看起来高级」引入 gRPC；REST 在多数业务场景仍是最省心的选择。
