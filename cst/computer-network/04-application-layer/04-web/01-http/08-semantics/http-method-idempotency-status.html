GET、POST、PUT、PATCH：安全、幂等与重试怎样区分

用订单与文档更新案例解释方法语义、条件请求和响应状态，避免“POST 一定不能重试”的误解。

方法语义约束的是意图

HTTP 方法告诉客户端和中间系统请求打算做什么。GET 用于取得资源，按语义应是安全的，即客户端发起它不意图改变服务器状态；PUT 通常表示用请求表示替换目标资源的状态；PATCH 表示部分修改；POST 的语义更宽，常用于提交处理或创建子资源。所谓“安全”不等于服务器完全不记录日志或计数，但不应把 GET 设计成扣费、删数据等有业务副作用的操作。

幂等指相同请求重复执行后，对目标资源的预期效果与执行一次一致；它不等于每次响应字节完全相同。PUT 同一完整表示重复提交通常幂等，DELETE 重复删除的最终资源状态也相同，但第二次可能返回不同状态码。POST 和 PATCH 不能仅凭方法名判断具体业务是否幂等，必须看接口契约。

一个订单创建算例

客户端向 `/orders` POST 创建订单，服务端提交成功但响应丢失。客户端只看见超时，不知道订单是否已创建。若直接换一个新请求再 POST，可能产生两张订单。可让客户端提供稳定的业务幂等键，服务端在事务中把键与首次结果关联；超时后用同一键重试或查询，返回同一订单。这样做是业务设计带来的幂等效果，并非 POST 天然变为 HTTP 语义上的幂等方法。

幂等键的作用域、过期时间和参数一致性要明确。同一键配不同订单内容应拒绝或给出可解释冲突，不能悄悄返回旧单；只把键存在单进程内存中，重启或多副本下可能再次创建。数据库唯一约束与状态查询通常是可靠实现的一部分。

PUT 与 PATCH 的差别

假设文档资源 `/docs/7` 当前标题 A、正文 B。PUT 请求若表示完整替换，客户端应提交完整的新表示；漏掉的字段可能按 API 契约清空或取默认值。PATCH 可只提交“标题改为 C”，但是否幂等取决于补丁动作：设置标题为 C 重复执行通常可保持同一结果；“阅读次数加 1”重复执行会累加。不能笼统说 PATCH 一定不幂等，也不能把 PUT 当作任何字段的局部更新。

并发更新还需要条件机制。两个客户端都读取版本 v1，再分别写入，后写可能覆盖先写。服务端可用 ETag 与 `If-Match` 做乐观并发控制；版本不符时返回 412 Precondition Failed，让客户端重新读取并解决冲突。幂等解决“重试是否重复生效”，条件更新解决“并发写是否覆盖”，二者不是同一问题。

常见状态码如何配合

创建成功常用 201 Created，并可给 Location 指向新资源；无正文成功可用 204 No Content；请求语法或参数不符可以用 400 一类错误，认证未建立常用 401，已识别身份但无权限通常用 403，资源不存在为 404，状态冲突可用 409，前置条件不满足可用 412。429 表示受限流影响，503 表示服务暂不可用，是否可重试还要看方法、幂等策略与响应指示。

不要把所有业务失败都返回 200 并在 JSON 里写 error；这会误导缓存、监控和调用方重试策略。但也不能只凭状态码自动无限重试：一个非幂等 POST 的 503 可能发生在提交结果未知时，必须有查询或幂等键。

浏览器和缓存的影响

GET 通常更容易被浏览器或中间缓存复用，所以把有副作用的操作伪装成 GET 还可能被预取、爬虫或代理无意触发。POST 的响应也不是绝对无法缓存，但缓存条件与语义更严格。GET 的 URL 可能出现在历史、日志和 Referer 中，敏感令牌不应随意放在查询串。方法、缓存与安全边界要一起设计。

HEAD 只请求与 GET 相应的元数据，不返回正文，常用于检查资源信息；OPTIONS 可协商支持的方法或参与 CORS 预检。CORS 预检的 OPTIONS 请求不是业务 POST 被“执行了两遍”，要分清协议交互与应用操作次数。

接口验收

给每个写接口列出方法、路径、请求体、成功码、错误码、重复请求行为、并发冲突行为和超时后的查询方式。用“服务端已提交但响应丢失”注入实验，检查客户端是否会重复下单或扣费；用两个客户端持旧版本同时更新，检查是否有条件写保护。对于 GET，测试预取或重复请求不会改变业务状态。

记录请求 ID 和业务幂等键的脱敏形式，便于跨层追踪；不要把完整支付凭据写入日志。调用方与服务端共同约定重试上限和截止时间，才能把 HTTP 方法语义落到真正安全的行为上。

方法的安全性与幂等性

方法Safe（无副作用）Idempotent（幂等）请求体说明
GET是是无（有也不保证被转发）可缓存、可书签
HEAD是是无只要响应头，用于探测/取元信息
OPTIONS是是无CORS 预检；查询支持的方法
TRACE是是无回显请求，通常应禁用（XST 攻击）
PUT否是有整体替换：PUT /users/1 传完整对象
DELETE否是通常无删两次和删一次结果相同
POST否否有创建子资源、执行动作；重复提交会创建多份
PATCH否否（取决于补丁语义）有局部修改；{"op":"set"} 幂等，{"op":"inc"} 不幂等

幂等是重试的前提：只有幂等请求才能在超时后安全重试。非幂等（POST/PATCH）重试必须带幂等键（客户端生成唯一 ID，如 Idempotency-Key: uuid），服务端据此去重。

幂等与 OPTIONS

# 幂等键的标准用法（Stripe 等 API 的做法）
curl -X POST https://api.example.com/orders \
  -H 'Idempotency-Key: 7d1f2a3c-...' \
  -H 'Content-Type: application/json' \
  -d '{"sku":"A1","qty":1}'
# 服务端：先查该 key 是否处理过 → 有则直接返回上次结果，否则执行并记录

# 看服务端支持哪些方法
curl -X OPTIONS -i https://api.example.com/users
# Allow: GET, POST, HEAD, OPTIONS

# CORS 预检
curl -X OPTIONS -i https://api.example.com/users \
  -H 'Origin: https://a.com' -H 'Access-Control-Request-Method: PUT'

状态码速查与易错点

码含义关键点
200成功最通用
201已创建应带 Location 指向新资源
204无内容响应体必须为空，不能与 200 混用
206部分内容断点续传，需 Content-Range
301永久重定向浏览器会永久缓存（难回滚！）；POST 常被改为 GET
302临时重定向历史上会把 POST 改成 GET
307临时重定向保持原方法与请求体
308永久重定向保持原方法与请求体
400请求错误客户端参数问题
401未认证缺/无效凭证，应带 WWW-Authenticate
403禁止访问认证了但没权限（与 401 区别）
404不存在也可用于“不想告诉你它存在”
409冲突状态冲突（如余额不足、版本冲突）
429请求过多应带 Retry-After（秒或日期）
500服务器内部错误兜底
502Bad Gateway网关收到上游无效响应：上游崩了/返回非 HTTP
503不可用过载或维护，应带 Retry-After
504Gateway Timeout上游响应超时（不是客户端超时，是代理等上游超时）
  • 301 的陷阱：浏览器会永久记住 301，之后不再请求原地址。做错一次 301 会让用户长期打到错误地址，几乎无法回滚 → 临时调整一律用 302/307。
  • 502 vs 504：502 是“上游给了个无效响应或连不上”（进程崩、端口没监听）；504 是“连上了但迟迟不回”（上游慢）。这是网关排障最直接的分水岭。
  • 401 vs 403：401 = 你是谁（未认证）；403 = 我知道你是谁，但你不许（无权限）。写反会导致客户端不触发重新登录。
  • 429 一定要带 Retry-After，客户端据此退避；否则客户端只能瞎猜，容易形成重试风暴。
  • 别用 200 包一切：业务错误码放 body、HTTP 状态仍 200 的做法，会让网关/监控/重试逻辑全部失效（无法按状态区分成功失败）。
POST 超时后能不能重试？

不能盲目重试——可能已经创建成功了，只是响应丢了。正确做法是带 Idempotency-Key，服务端保证同 key 只执行一次。或者先 GET 查询是否已经创建（read-before-write）。

为什么重定向后我的 POST 变成了 GET？

301/302 在历史上的浏览器实现中会把 POST 降级为 GET（规范未定义但事实标准）。要保留方法必须用 307/308。

自检

PATCH 请求一定不是幂等的吗？

不一定。“把标题设为 C”可幂等，“计数器加一”不幂等；要看具体补丁语义。
