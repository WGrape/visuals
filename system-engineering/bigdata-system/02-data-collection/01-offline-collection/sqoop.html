先建立直觉：两座仓库之间的货运队

你有两座仓库：关系数据库（MySQL/Oracle，存放业务数据）和 Hadoop（HDFS/Hive，存放历史数据做分析）。需要在它们之间批量搬运货物。

Sqoop 就是这支货运队：import 把数据库的表搬到 Hadoop，export 把 Hadoop 的结果搬回数据库。

工作原理

常用命令

全量导入

# 说明：--num-mappers 并发度（不是越大越好！）
#        --split-by 按哪个字段切分
#        --delete-target-dir 覆盖写，保证幂等
sqoop import \
  --connect jdbc:mysql://slave:3306/db \
  --username ro_user --password *** \
  --table orders \
  --target-dir /warehouse/ods/orders \
  --fields-terminated-by '\001' \
  --num-mappers 4 \
  --split-by id \
  --as-parquetfile \
  --delete-target-dir

增量导入

# 方式一：append（按自增 ID，只适合只插入的表）
sqoop import ... --incremental append --check-column id --last-value 100000

# 方式二：lastmodified（按时间戳，能处理更新）
sqoop import ... --incremental lastmodified   --check-column updated_at --last-value '2026-10-19 00:00:00'   --merge-key id                 # 按主键合并新旧数据

导出（Hadoop → 数据库）

sqoop export   --connect jdbc:mysql://host:3306/db   --table result_table   --export-dir /warehouse/ads/result   --update-key id --update-mode allowinsert   # 有则更新，无则插入

三个关键参数

① --num-mappers（并发度）。不是越大越好！每个 map 都会开一个数据库连接，并发过高会直接压垮源库。通常设 4~8，并务必连接只读从库。
② --split-by（切分字段）。必须是数值型、分布均匀、有索引的列（通常主键）。如果字段分布不均会导致数据倾斜（某些 map 特别慢）；如果是字符串类型或没有索引，切分本身会很慢甚至全表扫描。
③ 增量导入的漏洞。lastmodified 用 updated_at > last-value 筛选，会漏掉那些更新时间早于位点但刚被修改的记录（边界问题），且无法捕获删除。建议：位点前移一段时间做重叠 + 下游 upsert；要求严格时改用 CDC（Canal/Debezium）。

🎯 面试问答

Q：Sqoop 现在还值得用吗？
A：不建议在新项目中使用。Sqoop 已进入 Apache Attic（退役状态），不再有版本更新和社区维护。替代方案：离线批量同步用 DataX（数据源支持广、有限速、配置化）或 Spark 直连 JDBC；实时同步用 CDC（Canal/Debezium/Flink CDC）。如果现有系统已在使用 Sqoop，建议制定迁移计划逐步替换，但不必紧急——它能正常工作，只是不再演进。

Q：--num-mappers 设得越大越快吗？
A：不是。每个 map 都会建立一个独立的数据库连接并执行查询，并发过高会：① 占满源库连接池；② 打满源库 CPU 和 IO；③ 触发数据库的保护性限流甚至拒绝服务。通常设 4~8 即可，且务必连接只读从库而非主库。真正的瓶颈往往是源库读取速度，加大并发只是把压力转移给了数据库，整体吞吐未必提升。

Q：为什么增量导入会漏数据？
A：两个固有缺陷：① 边界问题——updated_at > last-value 这个条件，会漏掉「修改时间恰好落在位点边界」或「上次同步后才完成更新」的记录；② 无法捕获删除——记录被 DELETE 后，按时间戳永远查不到它，下游会一直保留已删除的数据。缓解：位点前移一段时间做重叠同步 + 下游按主键 upsert。根治：改用 CDC 解析 binlog，它能完整捕获增删改。

Q：Sqoop 和 DataX 该怎么选？
A：选 DataX。对比：DataX 支持几十种数据源（Sqoop 主要只做关系库与 Hadoop 之间）、原生限速（Sqoop 几乎无限速，容易压垮源库）、单进程多线程启动快（Sqoop 走 MapReduce，每次都要启动作业）、社区活跃（Sqoop 已退役）。唯一 Sqoop 仍有优势的场景：需要与 MapReduce 深度集成、依赖 Hadoop 集群做超大规模并行抽取——但这现在更多用 Spark 直接读 JDBC 来实现。

Sqoop 导入的关键参数

参数默认值 / 建议说明
--num-mappers默认 4并发度。按主键范围切分，所以表必须有主键或指定 --split-by
--split-by主键无主键表必须显式指定，否则只能用 --num-mappers 1
--fetch-size默认 1000每次从 DB 取的行数，调大（如 10000）可减少往返
--direct关闭用数据库原生工具（mysqldump）导出，快 2~5 倍但只支持部分数据库
--compress关闭开启 --compression-codec snappy，减少 HDFS 占用
--as-parquetfile文本列存，压缩率高，下游查询快
--fields-terminated-by,文本格式的分隔符，注意数据中含分隔符会错乱
--incremental append—增量导入，需配 --check-column 与 --last-value
--incremental lastmodified—按时间戳增量，可捕获更新
--boundary-query自动求 min/max数据倾斜时可自定义切分边界

num-mappers 不是越大越好：每个 mapper 都是一个数据库连接。设 20 就同时开 20 个连接查源库，很容易把生产库拖垮。经验值：4~8，导入大表时才上调，且要在业务低峰执行。

常用命令

# 全量导入（有主键）
sqoop import \
  --connect jdbc:mysql://db:3306/mydb \
  --username root --password xxx \
  --table orders \
  --num-mappers 4 --split-by id \
  --fetch-size 10000 \
  --target-dir /data/orders \
  --as-parquetfile --compress --compression-codec snappy \
  --delete-target-dir

# 无主键表：只能用 1 个 mapper（或指定 split-by 的索引列）
sqoop import ... --table logs --num-mappers 1

# 增量导入（append：只拉新增）
sqoop import ... --table orders \
  --incremental append --check-column id --last-value 1000000
# 导入后会打印新的 last-value，需自己记录（或用 sqoop job 保存）

# 增量导入（lastmodified：捕获修改，注意会重复）
sqoop import ... --table orders \
  --incremental lastmodified --check-column updated_at --last-value '2026-10-01 00:00:00' --merge-key id

# 导出到 MySQL（Hadoop -> DB）
sqoop export --connect jdbc:mysql://db:3306/mydb \
  --table result --export-dir /data/result \
  --num-mappers 4 --batch       # --batch 用 JDBC batch，快很多

# 创建保存 job（自动维护 last-value）
sqoop job --create myjob -- import --connect ... --incremental append ...
sqoop job --exec myjob

Sqoop 排障清单

症状原因处理
报 no primary key 且卡住表无主键且 num-mappers>1指定 --split-by 或降到 --num-mappers 1
导入极慢num-mappers 少 / fetch-size 小 / 没开 direct调 fetch-size 到 10000；MySQL 用 --direct
把生产库拖慢了并发连接太多 / 全表扫描num-mappers 降到 2~4；低峰执行；只读从库
数据倾斜：某个 mapper 特别慢split-by 列分布不均用 --boundary-query 自定义边界；换分布均匀的列
文本格式字段错位数据里含分隔符或换行改 parquet/avro；或用 --escaped-by/--enclosed-by
增量导入漏数据last-value 没更新 / 用 append 却发生了 update用 lastmodified + --merge-key；保存 last-value
Connection reset数据库连接被防火墙或超时断开加 --connect 的 ?autoReconnect=true；检查 wait_timeout
导出重复数据导出失败重试导致部分已写入导出前清空目标表，或用 staging 表 + 原子切换

Sqoop 已逐步被替代：官方已进入 Attic（退役）。新项目常用 DataX（阿里，插件化）、Debezium + Kafka（实时 CDC）、SeaTunnel。Sqoop 仍是存量 Hadoop 集群里最稳的离线同步工具。
