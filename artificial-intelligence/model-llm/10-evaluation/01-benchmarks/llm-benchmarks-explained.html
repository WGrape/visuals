大模型评测

大模型评测与基准：MMLU / GPQA / HumanEval / Arena 该怎么看

"哪个模型更强"几乎是面试和选型必问。本文按能力维度梳理主流基准各自在测什么、分数怎么读、有哪些公认的坑（数据污染、刷榜、提示词敏感性），以及真正落地时该怎么自建评测集。

应用上线时怎样组合自动评审、人工反馈、延迟和成本指标，见LLM 应用评估体系。

先分清两类评测

客观基准 Benchmark
  • 有标准答案，自动打分
  • 可复现、可横向对比
  • 例：MMLU、GSM8K、HumanEval
主观/偏好评测
  • 开放问答，无唯一答案
  • 靠人类偏好或 LLM-as-Judge 打分
  • 例：Chatbot Arena（Elo）、MT-Bench
现实是：客观基准越来越"饱和"（头部模型差距很小甚至满分），所以近年权重逐渐转向 Agentic / 长程任务（SWE-bench 类）和人类偏好榜单。

主流基准速查（按能力维度）

分数怎么读：三个必须警惕的坑

坑一：数据污染（Contamination）

评测题出现在模型的训练数据里 → 分数虚高，测的是"背没背过"而不是"会不会"。

表现：某模型在老基准上异常高、却在同类型新题上明显下滑。对策：关注发布时间晚于模型训练截止的新基准，或用" contamination 检测"（如让模型续写题目后半段看是否逐字复现）。

坑二：刷榜（Overfitting to Benchmark）

针对特定基准做定向优化（甚至用测试集调参），榜单分数上去了但通用能力没提升。

坑三：提示词与格式极度敏感

同一个模型、同一套题，换个提问方式分数能差 十几个点：

  • 0-shot vs 5-shot
  • 是否加 CoT 提示（"请一步步思考"）
  • 选项顺序、选项字母格式（A/B/C 还是 1/2/3）
  • 答案抽取方式：直接生成 vs 比较各选项 logprob——两者结果可能差很多
所以看榜单时一定要看它的评测协议（shot 数、prompt 模板、采样参数、是否 CoT）。不同协议下的分数不可直接横向比较。

为什么近年更看重 Agentic 评测

SWE-bench 这类基准要求模型读懂真实仓库、定位问题、改代码、通过测试，过程长且要反复试错，很难靠"背题"蒙混，因此成为衡量真实生产力的关键指标。

落地必做：自建评测集

公开基准只能帮你"初筛"，决定能不能上线的永远是你自己业务的评测集。建议流程：

1. 攒真实样本
从线上日志、badcase、客服反馈里挑 100~500 条真实 query
2. 定评分标准
能用规则就用规则（字段准确率、是否命中）；主观项写清 rubric，用 LLM-as-Judge 打分
3. 固化与回归
每次换模型/改 prompt 都跑一遍，做成 CI 里的回归测试
用 LLM-as-Judge 时注意：给明确的评分维度与示例、让评判模型输出理由、定期抽样人工复核防止评判漂移，并注意位置偏差（把候选答案顺序随机化）。
不要把评测集混进训练/微调数据，否则就失去了"独立验证"的意义。

面试速记卡

  • 两类评测：客观基准（有标准答案）vs 人类偏好（Arena Elo / LLM-as-Judge）。
  • 维度对应：MMLU 通识、GPQA 高难推理、GSM8K/MATH 数学、HumanEval/SWE-bench 代码、LongBench 长上下文、C-Eval 中文。
  • 三大坑：数据污染、刷榜、提示词/格式敏感（不同协议分数不可比）。
  • 趋势：客观基准趋于饱和，权重转向 Agentic 长程任务和真实人类偏好。
  • 落地：公开基准只做初筛，必须自建贴近业务的评测集并做成回归测试。

选型判据：不要看排行榜分数，要看你的任务最接近哪个基准。做代码助手重点看 SWE-bench/HumanEval；做知识问答重点看 MMLU/TruthfulQA；做对话产品重点看 MT-Bench/IFEval。不同基准的分数不能横向比较。

评测方法论的关键陷阱

陷阱表现规避
数据污染测试题出现在训练数据中用时间上晚于模型的题；或做 n-gram 重叠检测
提示敏感性换个提示词分数差 10 点固定提示模板并公开；测多个模板取均值
少样本示例影响0-shot 与 5-shot 差距大明确标注 shot 数
答案提取差异解析方式不同结果不同用官方解析脚本
随机性同配置多次跑分不同多次运行报均值与方差
小样本方差164 题的 HumanEval 波动大题少的基准别看小数点后的差异

污染检测

# 数据污染检测（n-gram 重叠法）
def contamination_rate(test_item, train_corpus, n=13):
    '''用 13-gram 重叠判断测试题是否泄漏'''
    words = tokenize(test_item)
    if len(words) < n: return False
    grams = [' '.join(words[i:i+n]) for i in range(len(words)-n+1)]
    return any(g in train_corpus for g in grams)

# 判据：
#   13-gram 命中 → 基本可判定泄漏
#   8-gram  命中率 > 10%  → 高度怀疑
# 更实用的是<strong>时间切分</strong>：只用模型发布之后产生的数据评测

# 多次运行求方差（避免被单次随机性误导）
import statistics
scores = [run_eval(seed=s) for s in range(5)]
print(f"{statistics.mean(scores):.1f} ± {statistics.stdev(scores):.1f}")

用 LLM 当裁判的注意事项

偏见类型表现缓解
位置偏见倾向选第一个答案交换顺序各评一次，取平均
长度偏见倾向给长答案高分在评分标准里明确「不看长度」
自我偏好倾向给自己家族模型的答案高分用不同厂商的模型当裁判
评分不稳定同一对答案多次评分不一致多次评分取众数；或让裁判输出理由

裁判流程

# LLM-as-judge 的标准流程
def judge(q, ans_a, ans_b, judge_model):
    # 关键：两次调用，交换 A/B 顺序，检测位置偏见
    s1 = call_judge(q, ans_a, ans_b)     # A 在前
    s2 = call_judge(q, ans_b, ans_a)     # B 在前
    if s1 != s2:
        return "inconsistent"            # 顺序影响了判断 → 结果不可信
    return s1

# 评分标准（rubric）必须明确，例如：
#   1 分：完全错误或无关
#   3 分：部分正确但有明显缺陷
#   5 分：正确且完整
#   <strong>明确说明「不因回答更长而加分」</strong>

# 与人类判断的一致性（ Cohen's kappa ）：
#   > 0.8  优秀，可替代人工
#   0.6~0.8 可用
#   < 0.6  <strong>裁判不可靠，别用</strong>

自检 Q&A

Q：为什么榜单第一的模型我用着不好？

A：三个原因——① 基准与你的任务不匹配：MMLU 高分不代表会写你的业务代码；② 榜单被针对性优化：有些模型在常见基准上做了大量针对性训练（刷榜），泛化未必好；③ 你的使用方式不同：榜单用的是精心设计的提示与采样参数，你实际用的可能完全不同。正确做法是用你自己的真实任务建一个小测试集（100~500 条），这比任何公开榜单都可靠。

Q：自建评测集要注意什么？

A：四条——① 覆盖真实分布：从线上日志抽样，而不是人工想象；② 包含困难样本：如果全是简单题，测不出差距（天花板效应）；③ 可自动判定：尽量设计成有标准答案或可用规则判定的形式，否则评测成本高到无法迭代；④ 定期更新：用户行为会变，评测集半年不更新就开始失真。规模上 100~500 条通常足够区分模型差异。

Q：HumanEval 分数差距 2 个点有意义吗？

A：基本没有。HumanEval 只有 164 题，2 个点的差距约等于 3 道题——这在随机波动范围内。经验判据：题数 × 差距百分比 = 实际差题数；差题数 < 10 时都不能算显著差异。所以小题量基准（HumanEval、TruthfulQA 的 817 题）只看大档次的差距；要精细比较需上万题的基准（MMLU、MATH）或多次运行看方差。

Q：开源模型自称“接近 GPT-4”该怎么看？

A：看它比的是哪个基准、什么提示、几 shot。常见做法是挑对自己有利的基准与设置：用 5-shot 比对方的 0-shot、用 MMLU 比 MT-Bench、用HumanEval 比 SWE-bench。核实方法：看它有没有公开完整的评测配置（提示模板、采样参数、解析脚本）。没有公开细节的对比结果，可信度很低。另外要区分能力接近与体验接近——指令遵循、格式稳定性、拒答合理性这些不在基准分数里，却极大影响实际体验。
