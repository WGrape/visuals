01 · 从问题出发

为什么会需要这个模式？

暗色按钮配亮色弹窗会造成视觉混乱；每个控件各自选主题容易混搭。

设置页允许切换暗色与亮色。若每个组件独立判断 theme，按钮切到了暗色而弹窗忘记切换，界面就会出现混搭。组件种类越多，同步规则越难检查。

😵 直接写会怎样

button = theme == "dark" ? DarkButton() : LightButton()
dialog = theme == "dark" ? DarkDialog() : LightDialog()
// 这里漏掉 theme 判断，就会出现 DarkButton + LightDialog

💡 关键转折

抽象工厂声明一组创建方法；具体工厂生产同一个产品族。

把“选择一族产品”的决定前移到一个工厂对象。既然拿的是 DarkFactory，它生产的按钮、弹窗自然同属暗色系列。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

interface ThemeFactory {
  createButton(): Button
  createDialog(): Dialog
}
class DarkFactory implements ThemeFactory {
  createButton() { return new DarkButton() }
  createDialog() { return new DarkDialog() }
}
render(factory.createButton(), factory.createDialog())

读代码时抓住三件事

  1. ThemeFactory 定义的是一组创建方法，不是单个 new。
  2. DarkFactory 把每个产品都绑定到同一系列。
  3. 客户端接收工厂实例后不再出现 theme == dark 的分支。

换个业务场景，还能认出来吗？

跨平台 UI 可选 WindowsFactory 与 MacFactory，同时生产菜单、按钮和弹窗。关键约束是整套组件要兼容，不能让某个控件绕开工厂单独选平台。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

有多个产品系列，每个系列内的多种产品必须配套

三个具体场景

  • 暗色/亮色主题同时生成按钮和弹窗
  • Windows/macOS 控件族成套切换
  • 不同数据库方言配套生成连接与命令对象

不适合或要小心

新增产品族容易；新增产品种类要修改所有工厂。工厂方法只决定一种产品，抽象工厂管理一组相关产品。

产品种类经常新增时，每个工厂都要增加方法，维护成本较高

最容易混淆的相邻模式

模式真正的区别
工厂方法一般让一个创建者子类决定一种产品；抽象工厂管理多个相关产品。
建造者按步骤组装一个复杂对象；抽象工厂一次提供多个彼此配套的对象。

区分时问自己：本次创建的是一个对象，还是互相兼容的一族对象？

落地前检查

  • 列出产品族与产品种类，确认真的存在两个维度。
  • 测试同一工厂产出的组件可一起工作。
  • 新增一种控件要修改每个具体工厂，先评估这个成本。
06 · 自己说一遍

两道检验理解的小题

为什么不分别创建 DarkButton 和 LightDialog？

单独构造不能保证产品族一致；同一工厂能统一约束。

新增一种“滑块控件”为什么比新增一种“主题”更费事？

ThemeFactory 要增加 createSlider，每个现有具体工厂也要提供对应 Slider 实现。

第一层 · 本质与识别信号

一句话本质：提供一个创建「一整套相关对象」的接口，且保证这套对象是互相匹配的。关键词是「一族」和「成套」——这是它与工厂方法的唯一分水岭。

识别信号说明
有几个产品，但必须成套使用，混用会出错最核心的信号（如 Mac 按钮 + Windows 滚动条 = 视觉灾难）
产品族会整体切换（主题、平台、云厂商、数据库方言）切换时希望只改一处
代码里到处是 if (platform == MAC) { new MacButton() } else ...分支散落 = 该抽工厂了
需要保证「这一批对象来自同一个来源」如同一套 SDK 版本的 client + parser + serializer
  • 产品族（family）：一组功能相关、设计上要配套的对象。如「Mac 族」= MacButton + MacDialog + MacScrollBar。
  • 产品等级（level）：同一功能的不同实现。如 Button 有三个等级实现（Mac/Win/Linux）。
  • 抽象工厂 = 一个工厂接口，每个方法对应一个产品等级；一个具体工厂对应一个产品族。

最常见的真实场景：多云适配（AWS 的 S3+SQS+SNS vs 阿里云的 OSS+MNS）、数据库方言（MySQL 的 Dialect + 类型映射 + 分页语法）、UI 主题。

第二层 · 骨架代码与量化对比

Go 实现

// —— 经典形态：一族产品，成套切换 ——
type Button interface{ Render() string }
type Dialog interface{ Show() string }

type Factory interface {
    CreateButton() Button
    CreateDialog() Dialog
}

// Mac 族：保证两个组件都是 Mac 风格
type MacFactory struct{}
func (MacFactory) CreateButton() Button { return MacButton{} }
func (MacFactory) CreateDialog() Dialog { return MacDialog{} }

// Win 族
type WinFactory struct{}
func (WinFactory) CreateButton() Button { return WinButton{} }
func (WinFactory) CreateDialog() Dialog { return WinDialog{} }

// 客户端：只依赖 Factory 接口，切换整套 UI 只改一行
func BuildUI(f Factory) string {
    return f.CreateButton().Render() + f.CreateDialog().Show()
}

// —— Go 的简化版：函数式「工厂的工厂」——
type Kit struct {
    NewButton func() Button
    NewDialog func() Dialog
}

var MacKit = Kit{
    NewButton: func() Button { return MacButton{} },
    NewDialog: func() Dialog { return MacDialog{} },
}

// —— 选型：根据环境决定整套 ——
func NewKit() Kit {
    switch runtime.GOOS {
    case "darwin": return MacKit
    default:       return WinKit
    }
}
维度工厂方法抽象工厂
创建几个产品1 种一族（多个）
扩展「新产品等级」（如加个 ScrollBar）—要改接口 + 改所有具体工厂（难）
扩展「新产品族」（如加个 Linux 族）新增一个 Creator（易）新增一个具体工厂（易）
保证成套不保证保证
类的数量每产品 +1每族 +1，且接口每加一个方法所有族都要改
实际使用频率高中低

记住这张表最重要的两行：加「族」容易，加「产品等级」难。这是抽象工厂的固有代价——接口是族的共同契约，加一个方法就要所有族跟着实现。

第三层 · 常见误用与排查清单

  • 把「可以独立选择的产品」硬做成族：如果 Button 用 Mac 的、Dialog 用 Win 的完全没问题，那就不需要抽象工厂——用两个独立的工厂方法即可。这是最常见的误用。
  • 族数量爆炸：3 个产品等级 × 4 个族 = 12 个具体类 + 3 个接口 + 4 个工厂。这种规模下要考虑配置化或参数化工厂（用配置表驱动）而不是硬编码类。
  • 新增产品等级时的改动面没评估：加一个 CreateScrollBar() 要改接口 + 所有具体工厂 + 可能还有调用方。如果产品等级经常变，抽象工厂是错误选择。
  • 工厂接口泄漏具体类型：如 CreateButton() *MacButton——这就失去了抽象的意义。返回值必须是接口。
  • 族之间有共享逻辑却各写一遍：用组合（把公共部分做成基类/嵌入结构体），而不是复制。
  • 运行时才决定族，却写死在编译期：应该把工厂作为参数注入，而不是在函数内部 NewMacFactory()。
  • 测试困难：族内的对象互相依赖，mock 要 mock 一整套。解法：为每个产品等级单独定义接口，测试时可以只替换需要mock 的那个（工厂返回 Kit 结构体比返回接口更容易部分替换）。

第四层 · 原理与取舍

抽象工厂的核心价值是一致性约束：把「这套东西必须配套」这条业务规则，从「靠人记住」变成「由类型系统保证」。这是它无法被简单工厂替代的地方。

  • 为什么「保证成套」这么重要：如果让调用方分别 NewButton() 和 NewDialog()，就没人阻止他混用。混用在编译期合法、运行期才暴露问题（视觉错乱、协议不匹配、版本不兼容）。抽象工厂通过「只能拿到一个 Factory，而一个 Factory 只产一族」把这个问题消灭在编译期。
  • 代价是接口的刚性：族接口一旦发布，加方法就是 breaking change。这是「保证成套」的必然代价——契约越严格，演进越困难。
  • 现代替代方案：① 依赖注入容器（按 profile/env 装配整套 bean，效果等同且更灵活）；② 配置驱动（用配置表描述「这套用哪些组件」，比硬编码类更易扩展）；③ 策略 + 工厂方法组合（各产品独立选择，靠约定而非类型保证一致性）。
  • 判断该不该用的最终标准：混用会不会出错？会 → 抽象工厂有价值；不会 → 用工厂方法，别自找复杂。
场景用抽象工厂？替代方案
UI 主题（按钮+对话框+滚动条）是（混用视觉错乱）—
多云 SDK（存储+队列+通知）是（跨云混用会不通）—
数据库方言（类型映射+分页+函数）是（方言混用 SQL 报错）—
日志器 + 指标上报否（可以独立选）两个工厂方法
缓存 + 数据库否（互不约束）独立注入
序列化器 + 压缩器边缘（若需配套则用）配置驱动更灵活
抽象工厂和「建造者」有什么区别？

区别在关注点：抽象工厂关注「选哪一套」（横向的族选择，一次性返回一族产品的工厂对象）；建造者关注「怎么一步步搭」（纵向的构造过程，分多步设置参数最后 Build()）。举例：抽象工厂是「给我 Mac 套件」，建造者是「给我一个 Button，宽度 100、红色、圆角，最后 Build」。两者经常组合使用——抽象工厂决定用哪套零件，建造者负责把复杂对象拼出来。判断方法：如果创建时的差异体现在「选哪套」（离散的选择），用抽象工厂；如果体现在「配置多少个参数」（连续的组合），用建造者。

为什么抽象工厂在实际项目里用得不多？

因为「必须成套且混用会出错」这个前提其实不常见。大多数系统里，日志器、缓存、数据库连接是可以独立选择实现的，没有「必须配套」的约束——这时用抽象工厂就是自找麻烦（多了一堆类和接口，收益为零）。它真正高频的场景就那么几类：跨平台 UI、多云/多厂商适配、数据库方言、主题/皮肤系统。另外，依赖注入框架普及后，很多原本用抽象工厂解决的「成套装配」问题被 DI 容器的 profile/qualifier 机制接管了——效果一样但代码量少得多。所以现代项目里看到抽象工厂的频率确实在下降。

产品等级经常增加怎么办？

这是抽象工厂的结构性弱点，有三种应对：① 改用参数化工厂——工厂方法签名改成 Create(kind string) Product，新增等级只加一个 case（牺牲了部分类型安全）；② 用注册式 + 工厂方法组合——每个产品等级一个独立的工厂方法，一致性靠约定或运行时校验而非类型保证；③ 重新审视是否真的需要「族」——很多时候「族」是因为设计时的过度归纳，实际各产品可以独立演进。如果产品等级真的频繁增加，强烈说明一开始就不该用抽象工厂，参数化或注册式才是正解。
