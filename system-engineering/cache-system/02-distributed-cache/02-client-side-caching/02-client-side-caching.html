客户端缓存

浏览器与 SDK 侧的缓存如何减少回源：Cache-Control、ETag 与 304

强缓存协商缓存304SWR

一句话：客户端（浏览器/SDK）缓存能直接省掉回源请求。分清“强缓存”和“协商缓存”两条路，是做对前端与 API 缓存的前提。

强缓存：不询问，直接用

Cache-Control: max-age=3600 告诉客户端“这一小时内别来问我”。immutable 进一步表示内容永不变（如带 hash 的静态资源），连条件请求都免了。强缓存命中时，浏览器甚至不发请求，速度最快。

协商缓存：问一句，没变就 304

过期后客户端带 If-None-Match: <ETag> 或 If-Modified-Since 再问一次。服务端比对：没变返回 304 Not Modified（无 body，省带宽）；变了返回 200 + 新内容。ETag 优先级高于 Last-Modified。

机制请求头响应
强缓存无（直接命中）无请求 / 200 (from cache)
协商-ETagIf-None-Match304 / 200+body
协商-Last-ModifiedIf-Modified-Since304 / 200+body

stale-while-revalidate

Cache-Control: max-age=60, stale-while-revalidate=300 表示：60 秒内强缓存；之后 300 秒内先用旧值返回，同时后台静默刷新。用户零等待，又能逐步更新——非常适合非强一致的读多场景。

概念与判定

  • 强 vs 协商：强缓存不发起请求；协商缓存发请求但可能只回 304。
  • 何时用强缓存：内容带版本号/hash 的静态资源（JS/CSS/图片）直接长 max-age+immutable。

参数·命令·量化

  • Cache-Control: public, max-age=3600, stale-while-revalidate=300。
  • ETag 通常用内容哈希；Last-Modified 精度到秒，秒级内变更会漏判。
  • 状态码：200(新) / 304(未变) / 200(from cache)(强命中)。

排障与边界

  • 改了却不更新：强缓存期间浏览器不请求；用内容 hash 文件名或缩短 max-age 解决。
  • 304 仍慢：协商缓存每次都走网络 RTT；高频小资源应改强缓存。

原理与取舍

维度客户端缓存服务端/CDN 缓存
