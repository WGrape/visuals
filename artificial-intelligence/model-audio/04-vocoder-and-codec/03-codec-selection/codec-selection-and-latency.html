音频编解码选型：在码率、延迟、算力与音质之间做取舍

「换个更好的 codec」是语音系统里最常见的优化冲动，也是最容易被误用的一个。这一篇把通信 codec（Opus/AAC/MP3）和神经 codec放在同一张表里，按码率段、延迟预算、CPU 成本和兼容性四项做对比，并给出按场景直选的结论。

先分清楚两类 codec 在解决什么问题

通信 codec（Opus / AAC / MP3）
目标：在给定码率下让人耳听不出差别。靠心理声学模型做频域掩蔽、丢掉被掩盖的能量。

输出是比特流，不是模型可用的表示。
神经 codec（EnCodec / DAC / SoundStream）
目标：把音频变成离散 token 序列，同时尽量保真。

输出是 token，可直接被语言模型建模；压缩只是副产品。
最常见的错误：用「音质」单指标去比这两类。神经 codec 在低码率的可懂度上可以更好，但在 CPU、标准化、抗丢包上远不如 Opus。如果你的链路只是「把 A 的声音传给 B」，选 Opus。

延迟预算：把「卡顿」拆成四个可度量的数

实时语音里用户感受到的延迟，是四项相加的结果。优化前必须先测量各自占比，否则很容易优化错地方：

采集缓冲+编码算法延迟+网络 + 抖动缓冲+解码 + 播放缓冲
  • 采集缓冲：麦克风一次给多少样本，通常 10–20 ms 一帧。
  • 编码算法延迟：codec 自身的前瞻，Opus 可配到 2.5 ms，AAC 常接近 100 ms。
  • 网络 + 抖动缓冲：实时链路里这一项往往是最大头，弱网下抖动缓冲常设 50–200 ms。
  • 解码 + 播放缓冲：为防止播放欠载预留的缓冲，通常再 20–60 ms。
典型误判：为了「降延迟」把 codec 从 AAC 换成 Opus（省 ~90 ms），但抖动缓冲还开着 200 ms——用户几乎感觉不到差别。先测占比，再动手。

码率不是越低越好：三个拐点

  • 拐点 ①（可懂度平台）：约 6–10 kbps。再降码率，能听清但明显发闷、齿音丢失。语音识别在这段仍可工作。
  • 拐点 ②（语音透明）：约 20–32 kbps。多数人已听不出与原始的差异，再往上收益很小。
  • 拐点 ③（收益递减）：音乐/复杂内容需要更高码率，但超过某点后人耳分辨不出，只是白烧带宽。
数字是量级参考不是规格：不同 codec 在同一码率下差异很大，且「语音」与「音乐」的拐点不同。做任何带宽决策前用自己的内容做一轮主观测。

落地检查清单

  1. 先确定这是传输问题还是建模问题——只传声音用 Opus；要让模型读写音频才用神经 codec。
  2. 确认因果性：实时链路必须选 streaming/causal 版本，否则有固定前瞻延迟。
  3. 对齐采样率：codec 采样率、模型采样率、播放采样率三者必须一致，否则音色失真。
  4. 测量而非估算延迟：分别测采集/编码/网络抖动/解码四段，找出真正的大头。
  5. 弱网要有兜底：Opus 开 FEC 与 PLC；神经 codec 需要自己设计丢包隐藏策略。
  6. 别忘算力账：神经 codec 的编码+解码在服务端是常驻开销，按并发量折算 GPU 成本。
一句话收尾：传输选 Opus，建模选神经 codec；延迟问题先测抖动缓冲，音质问题先查采样率。

延迟的构成：总延迟 = 采集缓冲 + 编码算法延迟 + 网络传输 + 抖动缓冲 + 解码 + 播放缓冲。实时通信里抖动缓冲（jitter buffer）常常是大头，通常 20~80ms，网络差时会自适应加大到 200ms+。这也解释了为什么「编解码只占 20ms，实际延迟却有 150ms」。

选型与验证命令

# ffmpeg 查看/转换编码
ffprobe -v error -select_streams a:0 \
  -show_entries stream=codec_name,sample_rate,bit_rate,channels -of default=nw=1 in.mp4

# 转成 Opus（实时通信）
ffmpeg -i in.mp4 -c:a libopus -b:a 32k -application voip out.opus
# -application: voip(低延迟，优化语音) / audio(音乐) / lowdelay(最低延迟)

# 转成 AAC（流媒体）
ffmpeg -i in.mp4 -c:a aac -b:a 128k -ar 44100 out.m4a

# Opus 的关键参数
#   --framesize 10      帧长(ms)：2.5/5/10/20/40/60。越小延迟越低、码率越高
#   --application voip  优化人声
#   --complexity 10     编码复杂度 0~10，越高越好越耗 CPU
#   --packet-loss 20    预期丢包率，据此启用 FEC
# WebRTC 里配置 Opus 的推荐参数
const constraints = {
  audio: {
    channelCount: 1,
    sampleRate: 48000,
    // Opus 特有参数通过 SDP 协商
  }
};
// 关键 SDP 参数：
//   maxplaybackrate=48000
//   stereo=0                  单声道（语音足够，省一半码率）
//   sprop-maxcapturerate=48000
//   usedtx=1                  静音检测（DTX），静音时不发包，省 50%+ 带宽
//   useinbandfec=1            带内 FEC，抗丢包
//   cbr=0                     语音用 VBR 更省

# 抗丢包的三招（VoIP 必备）
# 1) FEC（前向纠错）：多发冗余包，能抗 10~20% 丢包，代价码率 +20~50%
# 2) PLC（丢包补偿）：解码端用算法「猜」丢失的帧，能掩盖 <60ms 的丢包
# 3) 重传（NACK）：延迟允许时用；RTT 大时不如 FEC
# 选择：RTT < 50ms 用 NACK；RTT 大或丢包高用 FEC

Opus 是实时通信的默认答案：它的延迟（5~20ms）远低于 MP3（100ms+）和 AAC（20~50ms），且在 6~40 kbps 就能达到可懂的语音质量。WebRTC 强制要求支持 Opus，这是标准选择。
