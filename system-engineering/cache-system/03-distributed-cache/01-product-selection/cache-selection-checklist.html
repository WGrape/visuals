一、五问定方案

Q1：数据总量多大？单机内存装得下吗？
A：几十 GB 以内、单机能装下 → 单实例 + 主从即可，不必上集群。上百 GB 或需要线性扩展 → 必须分片/集群。这个判断直接决定架构复杂度上不上一个台阶。
Q2：value 的结构是什么？只用字符串够吗？
A：只存序列化后的对象（JSON/Protobuf）→ 纯 KV 产品足够。需要按字段读写、需要排行榜、需要计数、需要队列语义 → 必须有 Hash/ZSet/List/Stream 等结构，选 Redis 系。
Q3：缓存丢了可以接受吗？
A：能接受（缓存只是加速，丢了回源即可）→ 不需要持久化，反而要关掉持久化避免额外开销与写放大。不能接受（例如用它存会话、分布式锁、限流计数）→ 必须开持久化 + 高可用，且要考虑它已经不是"纯缓存"了。
Q4：能容忍多久的陈旧数据？
A：这个答案直接变成 TTL。容忍 5 分钟就设 5 分钟，别随手填 30 分钟。容忍度为 0 的强一致场景，缓存可能根本不该出现在架构里（见「收益与代价」）。
Q5：谁来运维？
A：有专职运维、需要定制与深度调优 → 自建。没有 → 云托管。别高估团队的运维意愿，缓存集群的故障往往发生在半夜。

二、把直觉变成可比较的打分表

对每个候选方案按下面维度打分（1–5），加权求和。重点是把"感觉 Redis 更好"变成"Redis 在结构丰富度上 5 分、Memcached 2 分，但我们只用 get/set，这一项权重设为 1"。

维度建议权重打分要点
数据结构匹配度高需要的结构是否原生支持，还是要客户端拼
容量与成本高内存占用、可否用磁盘型降本、扩容单价
性能（吞吐 / 延迟）中按实测，不要看宣传数字
高可用能力中高故障转移是否自动、RTO/RPO 多少
运维成本中高自建还是托管、监控告警是否现成
生态与迁移成本中客户端库成熟度、是否用了私有特性
团队熟悉度中出问题时能不能快速定位，这一项常被低估

⚠️ 权重里「团队熟悉度」不要设成 0。凌晨三点缓存集群出问题，团队熟悉的产品和不熟悉的产品，故障恢复时间可能差一个数量级。

三、五种选型反模式

  • 先选产品再定需求——"我们用 Redis"然后才想缓存什么。正确顺序是先量化和定义需求（收益与代价那一篇），再选工具。
  • 为了用上某个酷特性而选型——为了用 Stream 做消息队列而选 Redis，结果消息队列该有的可靠性全要自己补。
  • 把缓存当存储用——把唯一数据源放在缓存里，还不开持久化。缓存的定位是"可重建"，违背这一点迟早丢数据。
  • 忽略客户端库质量——服务端选得很好，客户端库连接池有 bug、超时设置不合理，线上一样炸。
  • 只测功能不测容量——上线前没压过"缓存全空"和"缓存全挂"两种极端状态，等到真发生才发现回源量扛不住。

四、选完之后必做的六件事

① 定 key 规范
业务前缀 + 版本 + 标识，例如 order:v2:{orderId}。带版本号才能在迁移时批量失效。详见 热 key 与大 key。
② 定 TTL 并写进文档
每个 key 的过期时间都要有依据（业务容忍度），不能是默认值。见 TTL / TTI。
③ 定淘汰策略并预留内存水位
内存上限要有余量，淘汰策略要按访问分布选（LRU 适合有明显热点的，LFU 适合长期稳定的）。见 LRU / LFU。
④ 定读写模式与失效路径
写库之后是删缓存还是更新缓存？后台管理、定时任务、订正脚本的写入口是否都覆盖了？见 缓存读写模式。
⑤ 定降级方案
缓存不可用时怎么办。必须有熔断/限流，否则缓存宕机反而压垮数据库。见 缓存雪崩。
⑥ 上监控
命中率、回源量、内存水位、慢查询、大 key。见 监控与预热。

Redis vs Memcached：硬性数字对比

维度RedisMemcached
线程模型单线程命令执行（6.0+ IO 多线程）原生多线程
单实例 QPS约 10 万（简单 GET/SET）约 20 – 50 万（多核）
数据结构String/Hash/List/Set/ZSet/Bitmap/HyperLogLog/Stream/Geo只有 String
单 value 上限512 MB1 MB（默认，可调到 128 MB 但不推荐）
持久化RDB + AOF无
集群原生 Cluster（16384 槽）客户端分片（无官方集群）
内存分配jemalloc（碎片较多）Slab（无碎片，但浪费）
适用场景绝大多数场景超大规模纯 KV、多核压榨

结论：默认选 Redis——数据结构丰富、生态成熟、集群原生。只有当你的场景是纯粹的 KV + 超大吞吐 + 多核机器（如超大规模 session 缓存）时，Memcached 的多线程优势才值得放弃 Redis 的一切。

Redis 性能自测与体检

# Redis 性能自测（拿自己机器的数据说话）
redis-benchmark -h 127.0.0.1 -p 6379 -c 50 -n 100000 -t get,set -P 16 -q
#   SET: 112359.55 requests per second
#   GET: 118764.84 requests per second
# 关键参数：-c 并发数  -n 总请求数  -P pipeline 条数
# 注意：不开 pipeline 时吞吐会掉到 1/5 ~ 1/10（每条一个 RTT）

# 开启 IO 多线程（Redis 6.0+，只加速网络读写，命令仍单线程）
io-threads 4            # 建议 = 物理核数的一半~全部，别超过 8
io-threads-do-reads yes # 读也走多线程

# 内存效率体检
redis-cli INFO memory | grep -E "used_memory_human|mem_fragmentation_ratio"
#   mem_fragmentation_ratio > 1.5  -> 碎片严重，考虑重启或换 jemalloc 版本
#   mem_fragmentation_ratio < 1.0  -> 用了 swap！性能会暴跌，立刻排查

# 找大 key（性能杀手）
redis-cli --bigkeys --memkeys      # 扫全库，找出最大的 key
redis-cli MEMORY USAGE mykey       # 单个 key 占多少字节

容量规划：从 QPS 到内存到机器数

步骤公式 / 经验值示例
① 估算 key 数量按业务实体数 × 缓存覆盖率1000 万用户 × 30% = 300 万 key
② 单 key 平均大小含 key 名 + value + 约 50 – 100 B 开销约 500 B
③ 总内存① × ② × 1.3（碎片余量）300 万 × 500 B × 1.3 ≈ 2 GB
④ 单实例上限不超过 10 GB（fork/RDB/迁移都会变慢）2 GB 一实例即可
⑤ 分片数总内存 / 单实例上限，向上取1 – 2 分片
⑥ QPS 校验单分片 10 万 QPS，按峰值 3 倍冗余峰值 5 万 → 安全

单实例不超过 10 GB 的理由：① RDB 的 fork——数据量越大 fork 的页表拷贝越久，可能导致数百毫秒的停顿；② 主从全量同步要传整个 RDB；③ 集群迁移槽时耗时更长。所以宁可多分片，也不要堆大实例。

内存开销实测：Redis 存一个 key=user:10086 → value=32字节，实际占用约 100 – 120 字节（robj + sds + dictEntry + 指针）。短 key 场景下元数据开销可以占到 50% 以上，所以 key 名不要太长，且尽量用 Hash 的 ziplist 编码把多个字段压在一起。

深入自检

什么时候不该用 Redis？

四种情况：① 数据量超过内存（几十 GB 且访问均匀，命中率会很低，不如直接优化 DB）；② 需要复杂查询（多条件过滤、聚合——那是搜索/OLAP 的活，用 ES 或 ClickHouse）；③ 强一致存储（Redis 主从异步复制，故障切换会丢数据，别当唯一数据源）；④ 大 value 高频读写（> 100 KB 的 value，网络与序列化开销会主导，且阻塞单线程）。

Redis 单线程为什么还这么快？

四个原因：① 纯内存访问（100 ns 级）；② 单线程无锁无上下文切换——多线程的锁竞争和缓存一致性开销在内存操作场景下是纯亏损；③ IO 多路复用（epoll）单线程处理上万连接；④ 高效数据结构（SDS、跳表、压缩列表、哈希表渐进式 rehash）。注意：瓶颈永远是网络 RTT 而不是 CPU，所以 pipeline 和批量命令的收益最大。

云 Redis 还是自建？

中小团队优先云 Redis：省去运维（主从、备份、扩缩容、监控），成本按量计费往往比自建人力便宜。自建只在两种情况下划算：① 规模极大（几百 GB 以上，云的溢价明显）；② 有特殊定制需求（改源码、特殊数据结构）。无论哪种，都要做主从切换演练——没演练过的 HA 等于没有 HA。

热 key 和大 key 怎么发现和处理？

发现：redis-cli --hotkeys（需 maxmemory-policy 是 LFU）、--bigkeys、或在客户端做本地计数采样（最准）。处理热 key：本地缓存 + 多副本拆分（hot:1~hot:10 随机读）。处理大 key：拆分（Hash 按字段分片、List 拆多个）、或压缩 value。大 key 的危害是删除/迁移时会阻塞单线程（Redis 4.0+ 用 UNLINK 异步删除来规避）。
