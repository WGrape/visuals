状态防火墙与五元组：放行请求为何回包仍可能被丢

用办公室访问外网的连接跟踪表解释入站、回程、非对称路由和最小权限规则。

静态规则与连接状态

防火墙可以按源 IP、目的 IP、源端口、目的端口和协议等条件匹配流量，这组信息常称五元组。无状态 ACL 主要逐包检查规则；状态防火墙还跟踪已允许连接的状态，让合法返回包按对应连接表项通过。办公室电脑主动连接网站 443 时，出口防火墙允许出站 SYN 并建立状态；网站回来的 SYN-ACK 即使目的端口是客户端临时端口，也可依据状态通过，不需粗暴开放所有入站临时端口。

状态不是无限可信或永久存在。连接跟踪表会超时，设备重启会丢状态，表项容量也有上限。对于 UDP，防火墙没有 TCP 握手可观察，常根据数据报方向和超时构建近似会话状态。规则书写要说明方向、接口、协议与回程策略。

一次 TCP 连接如何通过

客户端 10.0.0.8:53000 向 198.51.100.20:443 发 SYN；防火墙确认该源网段可访问目标端口后建立状态，记录出站五元组及反向匹配信息。网站回 SYN-ACK 到 10.0.0.8:53000，防火墙匹配既有状态并放行；后续 ACK 与应用数据继续沿状态流转。若客户端从未发起该连接，外部主机直接打入 53000，默认拒绝规则应挡住。

如果中间还有 NAT，防火墙看到的地址和端口可能与客户端、服务器端不同。排障必须注明抓包在 NAT 前还是后；用内侧五元组去查外侧状态表可能找不到。多个安全设备串联时，每个设备都要有相应路径和状态。

逐步推演

客户端发起

出站 SYN 按规则放行，F1 建立连接状态。

服务端回应

SYN-ACK 按反向五元组回到网络。

状态匹配

若回 F1，匹配已建立状态并放行。

异常回程

若回 F2 且无状态，可能被默认拒绝。

非对称路由的陷阱

企业有两台状态防火墙 F1 和 F2。去程 SYN 通过 F1，F1 建立状态；回程 SYN-ACK 却因路由选择经过 F2，F2 没看到初始 SYN，可能把回包当作未建立连接而丢弃。此时服务器已回复、客户端仍超时，单查 F1 的允许规则很难解释。解决方案可能是调整去回程路由、让高可用设备同步状态或根据架构采用明确的非对称流量处理，不能简单关掉状态检查。

状态同步也有延迟和故障边界。设备切换瞬间既有连接可能断开，特别是长连接和 UDP 会话。验收要测新连接与已建立连接分别能否在切换后继续，而不只测一次 ping。

规则顺序与最小权限

防火墙规则通常有优先级或顺序，较早命中的规则可能决定结果。先写“允许所有内网到任何位置”，后写“禁止访问管理网段”若被前者覆盖，后者形同虚设。应按来源、目的、端口与协议定义最小业务范围，并在末尾使用清晰的默认拒绝策略。变更前模拟允许流和应拒绝流，核对命中计数和日志。

“目的端口 443”仅表示该流量使用 TCP/UDP 端口 443，不保证传的就是合规 HTTPS；恶意程序也可借用同一端口。高层内容检查需要额外的应用层网关或代理，并有 TLS 终止和隐私边界。网络 ACL 是必要基础，但不是应用鉴权替代品。

故障表现与观测

连接超时时，在客户端、F1、F2 和服务器侧各抓同一五元组及时间窗：客户端有没有发 SYN、哪个设备接收、服务器是否回 SYN-ACK、回包经过哪台设备。若防火墙有拒绝日志，记录规则 ID、接口和连接状态；若没有拒绝日志，也可能是路由或更前一跳丢包。ICMP 能通不证明 TCP 443 可通，TCP 443 通也不证明 HTTP 业务正常。

状态表满时，新连接可能失败而已有连接继续服务；超时过短时，空闲长连接可能在恢复发送时被丢。看连接表占用、建连失败、状态老化和设备 CPU，比只看总带宽更能定位这类问题。

变更验收与安全复盘

新增服务放行时先列出客户网段、服务地址、协议和端口、双向流量是否经同一设备，再写最小规则。验收必须同时测试合法访问、应拒绝的源、服务端回程和设备故障切换。对临时规则记录到期时间与负责人，避免故障排查时留下长期“any-any”放行。

复盘事故时区分“规则未允许”“已有规则却未命中”“回程绕过状态设备”“应用主动拒绝”四种原因。它们对应不同修复动作，不能都归结为“防火墙开个端口”。

五元组与连接状态

状态含义典型报文
NEW新连接的第一个包TCP SYN（或 UDP 首包）
ESTABLISHED已有双向流量的连接连接建立后的数据包
RELATED与已有连接相关的新连接FTP 数据连接、ICMP 错误
INVALID无法识别/不合法乱序包、异常标志组合
UNTRACKED被 NOTRACK 跳过raw 表指定

有状态防火墙的核心：只需放行 NEW（首包），后续双向流量由 ESTABLISHED 自动放行。这比无状态防火墙（要手工配正反两个方向）既安全又简单。

有状态防火墙配置

# 经典有状态规则集
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
iptables -A INPUT -m conntrack --ctstate INVALID -j DROP
iptables -A INPUT -i lo -j ACCEPT
iptables -A INPUT -p tcp --dport 22 -m conntrack --ctstate NEW -j ACCEPT
iptables -A INPUT -p tcp --dport 443 -m conntrack --ctstate NEW -j ACCEPT
iptables -P INPUT DROP          # 默认拒绝（白名单模型）

# 查看连接跟踪状态
conntrack -L
conntrack -L --state ESTABLISHED | wc -l
cat /proc/net/nf_conntrack | head

# 按五元组精确放行
iptables -A INPUT -s 10.0.0.5 -d 10.0.0.1 -p tcp --dport 3306 -j ACCEPT

# 限速防扫描（同一 IP 新建连接速率）
iptables -A INPUT -p tcp --dport 22 -m conntrack --ctstate NEW \
  -m recent --set --name ssh
iptables -A INPUT -p tcp --dport 22 -m conntrack --ctstate NEW \
  -m recent --update --seconds 60 --hitcount 4 --name ssh -j DROP

# nftables 等价写法
nft add rule inet filter input ct state established,related accept
nft add rule inet filter input ct state invalid drop

常见坑与排障

  • 规则顺序至关重要：iptables 按链中顺序自上而下匹配，命中即停止。-A 追加在末尾，若前面有 ACCEPT ALL 就永远轮不到。先放通 ESTABLISHED，再放具体服务，最后默认拒绝。
  • 改规则别把自己锁在外面：远程改 SSH 相关规则时，先确认已有 ESTABLISHED 放行，或用 iptables-apply（改后 10 s 内不确认就自动回滚）。
  • INVALID 丢包要谨慎：某些合法但不常见的报文（如乱序/重传）会被判为 INVALID。生产上可以先只计数不丢弃，确认无影响再 DROP。
  • UDP 的“连接”是虚拟的：UDP 无状态，conntrack 靠“首包 + 双向流量”模拟连接，超时较短（30 s 单向 / 180 s 双向）。高频短 UDP（如 DNS）会产生大量表项。
  • RELATED 依赖 ALG/helper：FTP 主动模式的数据连接需要 nf_conntrack_ftp 模块才能识别为 RELATED。现代做法是改用被动模式 FTP 或 SFTP，不依赖 ALG。
  • 排障顺序：① iptables -L -nv 看规则命中计数（pkts/bytes 为 0 说明没匹配到）；② conntrack -L 看连接是否建立；③ 抓包确认包是否到达；④ 检查默认策略（-P）与规则顺序。
  • 性能注意：规则是线性匹配，几千条规则会显著拖慢。用 ipset（哈希集合）替代大量同类规则，把 O(n) 变 O(1)。
为什么放行了自己的端口还是不通？

检查三处：① 默认策略是 DROP 但没有放行 ESTABLISHED（回包被拦）；② 规则顺序（前面有更宽的规则拦截或后面的规则没轮到）；③ -A INPUT 只管入站，若本机转发还要 FORWARD 链和 ip_forward=1。

有状态防火墙能防 DDoS 吗？

能防一部分（如伪造源的连接耗尽攻击，因为 NEW 包要建 conntrack），但对大流量拥塞型攻击无能为力——流量已经把带宽打满了，防火墙在后面也无济于事。那需要上游清洗/Anycast。

自检

出站流量已被 F1 放行，回包经 F2 返回，为什么仍可能连接超时？

F2 可能没有看到建连请求，也没有对应状态表项，于是将 SYN-ACK 视为未建立连接而丢弃。
