缓存架构

判断何时需要缓存、将缓存放在哪里，以及如何约束数据新鲜度和故障影响。

先判断是否需要缓存

缓存是数据的派生副本。引入它之前，先确认读请求是否真的受后端延迟或容量限制，并写下可接受的数据滞后时间。若瓶颈在慢查询、索引或接口调用，优先处理原始瓶颈。

设计问题需要确认的约束
读负载热点是否集中，命中率能否足以降低源站压力？
数据新鲜度业务能接受多长时间的旧值？哪些操作必须直接读取权威数据？
故障行为缓存不可用时，数据库能否承受回源流量？是否需要限流或降级？
写入成本数据变化后，谁负责失效、重试和监控？

选择缓存所在层

客户端与 CDN

适合可公开复用、允许按版本或有效期更新的内容；重点是发布后的刷新与回源策略。

应用本地缓存

读取延迟低，但每个实例各有副本；要评估实例间失效传播和内存占用。

共享缓存

多个实例共用数据，便于统一失效；要计入网络访问、集群可用性与热点 key 的代价。

多层组合会提高命中率，也会增加失效路径。只有在单层方案无法满足延迟或容量目标时再叠加层次。

明确一致性与降级边界

确定数据库等权威数据源、缓存失效的触发者和失败重试机制。TTL 可限制旧值存活时间，但不能单独保证业务要求的强一致；对资金、库存最终确认等读写，应按业务规则读取或更新权威数据。缓存失效时还要限制回源量，避免把缓存故障放大为数据库故障。

具体读写时序与双写一致性见缓存读写模式和双写一致性；穿透、击穿与雪崩的处理见缓存异常总览；多层部署见多级缓存架构。

缓存架构：先分清「缓存在挡什么」

缓存不是「加个 Redis 就完事」。按它在链路中的位置与目的，可分为四类，每一类的失效策略与一致性要求都不同。

本地缓存进程内（Caffeine/Guava），纳秒级，但每实例一份，容量小、不一致
分布式缓存Redis/Memcached，毫秒级，共享一份，容量大，需网络
多级缓存本地 → 分布式 → DB，逐级回源，兼顾速度与容量
写缓冲先写缓存再异步落库，用于削峰（如库存扣减、计数）
多级缓存链路与 Cache Aside 读写策略

三种经典写策略

策略写路径一致性 / 风险
Cache Aside（旁路）写 DB → 删缓存；读未命中则读 DB 回填最常用。并发下仍有极小概率脏读（读时缓存刚好过期、回填前被另一写删）；删失败会长期脏，需重试
Write Through（穿透写）写缓存 → 缓存同步写 DB → 返回缓存与 DB 强一致；写延迟高，且很多数据写了不一定被读，浪费
Write Back（回写）只写缓存并标记脏 → 异步批量落 DB写性能最好；缓存宕机丢数据，必须配合持久化与可靠队列，适合计数、库存等可容忍短暂丢失的场景

删缓存失败怎么办？三种兜底：① 重试队列（把删除失败写入 MQ 重投）；② 订阅 binlog（ canal / Debezium ）由消费端删除，与主流程解耦——这是最彻底的方案；③ 给缓存设较短 TTL，让脏数据自动过期（兜底但不能作为主要手段）。

三个经典问题与对策

缓存穿透：查一个根本不存在的 key

每次都绕过缓存打到 DB，恶意用随机 id 刷就能拖垮数据库。

  • 缓存空值：DB 查不到也写个空标记（短 TTL，如 60s）
  • 布隆过滤器：前置一层，判断 key 一定不存在则直接返回
  • 参数校验：id ≤ 0、格式非法的请求直接在网关拦掉

缓存击穿：一个热点 key 过期

该 key 被高并发访问，过期瞬间所有请求同时回源 DB。

  • 互斥重建：用分布式锁，只让一个线程回源，其余等待或返回旧值
  • 逻辑过期：缓存永不过期，value 里带过期时间，命中后判断需刷新则异步重建
  • 热点 key 永不过期：由后台任务主动更新

缓存雪崩：大量 key 同时过期

同一时刻大片缓存失效，流量全部涌向 DB。

  • TTL 加随机抖动：基础 TTL + 随机 0~300s，打散过期时间
  • 多级缓存：本地缓存兜住一部分，减小 Redis 失效的冲击
  • 熔断降级：DB 压力过大时返回兜底数据或排队页

三者区别一句话记：穿透是「查不存在的」，击穿是「单个热点过期」，雪崩是「大批同时过期」。

缓存容量与淘汰治理

  • 内存上限要留余量。Redis maxmemory 建议设为实例可用内存的 60%~75%，给 fork（RDB/AOF 重写时的 copy-on-write）、客户端输出缓冲、碎片留出空间，否则会 OOM 或被系统杀掉。
  • 淘汰策略按需选。纯缓存用 allkeys-lru；有永不淘汰的重要 key 用 volatile-lru；希望保留高频热点的用 allkeys-lfu。注意：设了过期时间的 key 才受 volatile-* 影响。
  • key 要有业务前缀与版本位。如 order:v2:{id}，便于批量扫描、灰度切换与整体失效。
  • 禁止大 key 与热 key 同时存在。大 key（>10KB 或元素数万）在删除、迁移、序列化时会卡住单线程；热 key 打在一片上无法用扩容解决，需要本地缓存或多副本（key 加随机后缀分散）。
  • 命中率不是唯一指标。还要看「回源 QPS」绝对值——命中率 99% 但回源 5000 QPS，DB 照样扛不住。

深入自检

先删缓存还是先更新数据库？

标准答案是「先更新 DB，再删缓存」。反过来（先删缓存再更新 DB）会有一个明显的时间窗：删完缓存、DB 还没更新完时，一个读请求进来会读到旧值并回填进缓存，之后 DB 更新完成，缓存里就永久是旧值了。先更新 DB 再删缓存虽然理论上也有极小概率脏读（缓存刚好失效 + 并发读在删除前回填），但那个窗口要求读的回填动作发生在删除之后且 DB 更新之前，概率极低，且可用延迟双删进一步收敛。

延迟双删有必要吗？

作为兜底可以做：更新 DB → 删缓存 → sleep 一小段时间（如 500ms）→ 再删一次。第一次删除处理大部分情况，第二次删除清理并发读回填的脏数据。但它引入了额外延迟，且 sleep 时间不好定。如果有 binlog 订阅删除（canal），就不必用延迟双删——那才是更彻底的解耦方案。

本地缓存和 Redis 的一致性问题怎么解决？

本地缓存天然不一致，因为每个实例独立。三种办法：① 设很短 TTL（秒级），容忍短暂不一致；② 变更时通过 Redis Pub/Sub 或 MQ 广播失效消息，各实例收到后清除本地条目；③ 只缓存极少变更的数据（字典、配置）。实践中通常组合使用：广播失效 + 短 TTL 双保险。

缓存预热怎么做才安全？

不要一次性全量灌入——会瞬间打满 Redis 内存和网卡，并可能把在线热数据挤出去。正确做法：分批 + 限流导入，控制写入 QPS；只预热真正的热点（按历史访问 TopN 统计）；预热期间保持回源逻辑可用；最后核对 key 数量与内存水位是否在预期区间。
