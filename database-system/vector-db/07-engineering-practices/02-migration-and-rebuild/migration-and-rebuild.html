①六类重建触发与各自代价

向量库的「重建」不是可选运维动作，而是几类变更的必然结果。先分清是哪一类，才知道要付出多大代价。

触发原因要做什么代价能否避免
改索引参数（M、efConstruction、lists、m）重建索引小时级参数应尽量一次调好
改量化方案重建索引小时级量化可动态开关（部分产品）
换 embedding 模型重算全部向量 + 重建索引天级 + API 费用选型时慎选，别中途换
改维度或距离度量新建集合 + 全量重灌天级不可原地改
换引擎（迁移）导出 + 重灌 + 切流量天级——
数据大量删除后REINDEX / compaction小时级分区表可减轻
最贵的一类是换 embedding 模型：它不只是重建索引，而是要把所有原始文本重新送进模型算一遍。1000 万 chunk 的重算费用与耗时都必须提前估算，不能等到「想换个更好的模型」时才发现要停机两天。

②embedding 漂移：最隐蔽的静默故障

这是向量库最隐蔽、也最致命的一类故障：库里同时存在两个模型生成的向量。

向量空间是由模型定义的。A 模型生成的向量和 B 模型生成的向量虽然维度可能相同，但语义坐标完全不同 —— 混在一起检索时，距离值毫无意义，召回会断崖式下降，而且不报错、不告警，只是「结果变差了」。

场景后果如何避免
灰度迁移时新旧数据并存部分 query 只能命中一半数据按集合/分区隔离，不要混在同一索引
批量补数据用了新模型老数据静默失配向量表记录 model_version 字段
维度碰巧相同（如都是 1536）最难发现，不会报维度错显式存模型标识，不靠维度区分
换了供应商但接口兼容数值分布不同切换前用同一批文本对比两模型向量距离
# 每个点都记下模型版本，这是唯一可靠的防线
{
  "id": "doc-1#3",
  "vector": [...],
  "payload": {
    "text": "...",
    "embedding_model": "text-embedding-3-small",
    "model_version": "2024-02",
    "dim": 1536,
    "indexed_at": "2026-10-23T12:00:00Z"
  }
}

# 检索时可按版本过滤，防止混查
filter = {"model_version": "2024-02"}

③三种迁移策略与蓝绿流程

三种迁移策略，按风险与停机时间排列：

策略停机风险适用
原地重建有（小时~天）低内部系统、可约维护窗口
蓝绿 + 别名切换接近零中生产系统首选
双写 + 影子读零中（复杂度高）无法停机、需长时间对比验证
# 蓝绿迁移的完整流程

# 1) 建新集合/索引（新参数或新模型）
# 2) 灌历史数据（分批，注意限流避免影响线上）
# 3) 生产流量同时写入新旧两套（双写）
# 4) 影子读：把一小部分真实 query 同时打到新旧，对比结果
#    - 计算 recall 差异（以旧库结果为近似基准）
#    - 抽样人工看 top-10 相关性
# 5) 新库达标后，别名原子切换
# 6) 观察一段时间（建议 ≥ 1 周）再停双写、删旧库

# 别名切换（原子）
POST /collections/aliases
{ "actions": [
    { "delete_alias": { "alias_name": "docs" } },
    { "create_alias": { "collection_name": "docs_v2", "alias_name": "docs" } }
] }

④重算成本与时间的估算公式

重算向量的成本必须提前算，公式很简单：

总 tokens = chunk 数 × 平均 chunk token 数
费用     = 总 tokens / 1e6 × 每百万 tokens 单价

例：1000 万 chunk × 400 tokens = 40 亿 tokens
  按 $0.02/1M  → 约 $80
  按 $0.13/1M  → 约 $520

耗时：
  假设 embedding 服务可提供 500 QPS（批量）
  1000 万 / 500 ≈ 20000 秒 ≈ 5.6 小时（理想情况）
  实际要按限流、失败重试、批大小打折，乘 2–3 倍
时间估算最常见的错误是按单条请求算。单条 embedding 请求约 100–300 ms，1000 万条串行要几百小时。必须用 batch 接口（一次几十到上百条），否则永远跑不完。

⑤启动前的八条检查

重建前逐条确认，缺一条就别启动：

  • 数据源完整可用（原始文本还在，不是只有向量）
  • embedding 模型版本已记录，且新旧结果做过抽样对比
  • 重算脚本支持断点续跑（中途失败不能从头再来）
  • 写入限流已配置，避免迁移流量打垮线上
  • 新索引的召回已用 ground truth 验证达标
  • 别名/切换机制已就绪（不是改配置重启）
  • 回退方案已就绪：旧索引在切换后至少保留一周
  • 监控已覆盖新索引（延迟、召回、错误率）

信号正常异常时先查

⑦速记卡

六类重建触发

参数/量化/换模型/换维度/换引擎/大量删除。

最贵的一类

换 embedding 模型，要重算全部向量。

最隐蔽的故障

混用两个模型的向量，不报错只掉召回。

唯一防线

每个点记录 model_version 并按其过滤。

首选策略

蓝绿 + 别名原子切换，接近零停机。

重算成本

tokens 总量 × 单价；1000 万 chunk 约 $80–500。

时间陷阱

必须用 batch 接口，单条串行永远跑不完。

切换后四看

p99、召回、错误率、内存占用。

重建的成本不在「建索引」，而在「重算向量」与「验证召回」。前者花时间与钱，后者花人。
