Memcached 与 Redis：纯 KV 缓存怎么选？

先确定缓存是否可丢、客户端是否能回源、是否只做 get/set，再比较多线程、数据模型与故障恢复。

先确定缓存的失败语义

Memcached 是可丢失的内存缓存：重启、过期或淘汰都可能让 key 消失。应用必须能从权威数据源回填；如果缓存全空会压垮数据库，还要限制并发回源并预热热点数据。需要唯一权威存储的业务不应把它作为终点。

在什么条件下选择哪一个

业务要求Memcached 的取舍Redis 的取舍
只有短期、可重建的纯 KV服务端简单，多线程并行处理；数据模型和序列化交给客户端。也能胜任；如果已部署 Redis，通常无须另建缓存栈。
频繁修改对象字段、维护榜单或集合整值取出并回写，增加网络往返与并发覆盖风险。Hash、Set、ZSet 等服务端操作更贴近需求。
节点重启后需要恢复数据无持久化，必须由数据库回填，且要设计冷启动保护。可评估 RDB/AOF，但仍要明确允许的数据丢失窗口。
扩容与故障转移客户端分片；扩缩容影响 key 路由，节点故障无服务端副本。可评估复制、哨兵或 Cluster，同时承担相应运维成本。
选型先测量：吞吐瓶颈未必在命令执行。先用实际 value 大小、并发数和命中率压测，再比较客户端、网络、内存与服务端的代价；不能仅凭“多线程比单线程快”下结论。

落地前的四个问题

  1. 缓存未命中时由谁回源？节点全部重启时数据库能承受多少并发？
  2. value 大小集中在哪些区间？单个 slab class 会不会先于总内存触发淘汰？
  3. 多语言客户端使用的哈希函数、虚拟节点与节点顺序是否一致？
  4. 需求是不是已经包含持久化、服务端数据结构或故障自动切换？若是，纯 KV 缓存可能不是合适边界。
