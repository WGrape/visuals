一句话总结：OceanBase 用 LSM-Tree 把随机写变成顺序写（快），代价是读要合并多层数据——靠"转储"收敛增量、靠"每日合并"做彻底整理。

01为什么用 LSM-Tree

传统 B+ 树随机写要定位到页并就地更新，磁盘随机 IO 昂贵。LSM-Tree 把写入先放进内存的 MemTable，满了就顺序刷盘成 SSTable，把大量随机写变成少量顺序写，写入吞吐高。

02写入路径与转储

  • 写先进入 MemTable（内存），并写日志保证持久化。
  • MemTable 满了被冻结，刷盘成一层 SSTable（这一步叫转储 / dump）。
  • 转储会累积多层增量；层数越多，读时要合并的层次越多、越慢。
写快（顺序），读要合并多层

03每日合并（Major Compaction）

每日合并把所有增量 SSTable 与基线合并成一份新的基线：回收被覆盖的旧版本、清理过期数据、释放空间。它通常在业务低峰

执行，是 OB 控制读放大和空间放大的核心机制。

04合并的代价

🧮 CPU / IO

合并要重排并重写大量数据，消耗计算和磁盘 IO。

⏳ 时长

大表合并耗时久，期间读写仍可进行但可能受资源争抢。

📦 空间

合并过程中新旧基线短暂共存，需要额外空间余量。

05调优手段

手段作用
合并时间窗把每日合并放在业务低峰，避免与高峰争抢

06与查询的关系

读 OB 时要合并"基线 + 增量层"得到最新值。如果转储层堆积太多，读路径要合并的层次变多，查询变慢；每日合并把增量收敛回基线，恢复读性能。所以转储频率、增量层数、每日合并节奏共同决定读延迟。

07常见疑问

每日合并能跳过吗？
不建议长期跳过。跳过会让增量层持续堆积，读放大上升、空间无法回收，最终查询变慢。合并可以错峰、可以轮转，但不应长期不合并。
合并时还能正常读写吗？
能。合并是后台重写数据，期间业务读写仍可进行，但会占用 CPU/IO，所以放在低峰并控制并行度，避免拖慢在线查询。
转储和每日合并有什么区别？
转储是 MemTable 满了刷成增量 SSTable（频繁、轻量、局部）；每日合并是把所有增量与基线彻底合并成新基线（低频、重量、全局整理），解决读放大和空间回收。

为什么 LSM 写快读慢这件事值得容忍？

分析型/高写入场景下，写入吞吐往往是瓶颈，LSM 把随机写变成顺序写，写入能力大幅领先 B+ 树。读放大问题则通过后台 compaction（转储 + 每日合并）持续收敛，并且 OB 还有行缓存、块缓存等手段缓解。用可控的读成本换巨大的写吞吐，是这类引擎的常见取舍。

深度补充：OceanBase 转储与合并的量化边界

第一层 · 概念与判定 OceanBase 用 LSM-Tree：写入先落内存 MemTable，写满后“转储”成磁盘 mini SSTable；多层累积到阈值触发“每日合并”（major compaction）把增量合并成基线数据。判定信号：观察 __all_virtual_partition_sstable 的层数与合并时间戳。

动作触发 / 量级影响
Minor 转储MemTable 达 memstore_limit（默认 50%）小 IO、不阻塞读写
Major 合并默认每天 02:00 或层数阈值大 IO、读放大下降
渐进合并分多轮完成避免一次性巨量 IO
租户 memstore默认占内存 50%超阈值写被限流

第三层 · 排障与边界

  • 合并期间 IO 飙升，必须放到低峰并开渐进合并，否则影响在线读写。
  • memstore 占比过高会触发写入限流（freeze + dump），表现为写入变慢。
  • 合并失败会残留中间状态，需看 OBServer 日志的 compaction 报错。
  • 副本数高时合并要在每个副本重放，注意总 IO 放大。
第四层 · 原理与取舍

LSM 用“顺序写加后台整理”换写入吞吐，代价是读要查多层、合并有 IO 与延迟尖刺。OceanBase 把合并收敛到每日一次、并用渐进合并摊薄，核心权衡是“写放大与读放大、合并 IO 与在线性能”。相比 HBase 的持续 compaction，OB 的“每天合并”让读路径更稳定，但要求预留合并窗口的 IO 余量。

实例与速查：OceanBase 合并运维

-- 查看各租户 memstore 占用与合并状态
SELECT tenant_id, active_memstore_used, total_memstore_used
FROM oceanbase.GV$OB_MEMSTORE_INFO;

-- 手动触发某租户 major 合并（低峰期）
ALTER SYSTEM MAJOR FREEZE TENANT = 'my_tenant';

-- 看合并进度
SELECT * FROM oceanbase.DBA_OB_TABLET_REPLICAS
WHERE STATUS != 'NORMAL';
  • 合并尽量排在日常低峰，并确认开启渐进合并避免 IO 尖刺。
  • memstore 达阈值会触发 freeze + 转储，写被限流，需提前加内存或扩容。
  • 观察 __all_virtual_partition_sstable 的 major_snapshot 时间戳确认合并完成。
FAQ：转储和合并有什么区别？

转储（minor）是 MemTable 写满落盘成 mini SSTable，频繁、小 IO、不合并基线；合并（major）是把增量数据合并进基线，默认每天一次、IO 大但让读路径层数收敛。关系是“转储是日常小修，合并是每日大整”。

常见误区与延伸

  • 误区一：合并越频繁越好。合并是重 IO 操作，频繁合并会持续抢占在线读写带宽，应集中在低峰并渐进。
  • 误区二：memstore 占比越大写越快。占比过高会触发冻结与限流，写入反而变慢，需平衡。
  • 延伸：OceanBase 的多副本 + Paxos 让合并在多数派完成即可，少数副本延迟补齐，这是“可用性优先”的设计。
  • 延伸：对比 TiDB 的 Region 分裂/合并、HBase 的持续 compaction，三者的“整理时机”哲学不同，选型要看业务读写画像。

一句话总结：LSM 系数据库用后台整理换写入吞吐，代价是读放大与合并 IO，调参核心是给合并留足 IO 余量。

决策速记

  • 合并时机：默认每日低峰，大表开渐进合并摊薄 IO。
  • 观察指标：memstore 占比与 major 合并时间戳，超阈值会限流。
  • 故障处理：合并失败看 OBServer 日志，残状态需手动核对。
  • 容量规划：给合并留 IO 余量，副本多时总 IO 要翻倍算。

一句话：LSM 系用后台整理换写入吞吐，调参核心是给合并留足 IO 余量。

横向对比与追问

  • 与 TiDB 比：OB 把合并收敛到每日一次并渐进，TiDB 是 Region 持续分裂/调度，整理哲学不同。
  • 与 HBase 比：HBase 持续 minor/major compaction，OB 的每日合并让读路径更稳定。
  • 追问：为什么 LSM 都要后台整理？因为顺序写换吞吐，代价是读放大，必须定期合并收敛层数。
  • 追问：OceanBase 的多副本 Paxos 与 TiDB 的 Raft 各解决什么？都是多数派，OB 强调“多数派完成即可”。

小结：LSM 系数据库的对比主线是“写入模型、整理时机、副本协议”三件事。
