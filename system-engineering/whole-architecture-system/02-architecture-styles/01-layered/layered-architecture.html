分层架构

最经典、最基础的架构风格：把系统按职责切成横向层，层与层之间单向依赖。

像餐厅的前台、厨房、仓库：请求按职责逐层处理，每层只认识约定的下一层。

什么时候适用？

判断信号：应用职责能按表示、业务、数据访问划清，且主要是进程内调用。

  • 常规企业应用把 HTTP、用例和数据库职责分开
  • 团队需要清楚的模块边界与单向依赖规则
  • 从混杂的控制器中抽出稳定业务逻辑

和相近方案怎么区分？

相近方案选择边界
整洁架构都强调边界；整洁架构进一步要求依赖方向指向业务核心，数据库只是外层细节。
微服务跨进程拆分部署；分层架构可完全在一个进程内实现。

最小伪代码

function placeOrder(request):
  dto = web.parse(request)
  order = application.place(dto)
  // application 调用 repository.save(order)
  return web.respond(order)

边界：分层不是每层都必须转发空壳方法；跨层调用规则应明确，避免业务逻辑泄漏到控制器。

四层经典模型 Layered

表现层 → 业务层 → 持久层 → 数据层，调用自上而下、禁止逆向越层

核心约束是单向依赖：上层可以调用下层，下层永远不知道上层的存在（依赖倒置可让下层依赖抽象接口）。这样每层可独立替换与测试。

优点与代价

  • 优点：结构清晰、易于理解、每层可单独测试与替换（如换数据库不动业务层）。
  • 代价：层一旦变多，容易退化为『贫血模型 + 透传层』；跨层改动要改多处；性能上多层封装有开销。

常见变体

  • 经典三层：表现 / 业务 / 数据。
  • DDD 四层：接口层 / 应用层 / 领域层 / 基础设施层。
  • 严格分层：只能依赖相邻下层；松散分层：可跨层依赖。

面试高频问答

Q：为什么禁止表现层直接访问数据库？
A：破坏分层会让业务规则散落到各处、无法复用也无法单测；强制经业务层可保证事务、权限、校验集中可控。
Q：分层架构和微服务冲突吗？
A：不冲突。分层是『一个进程内的纵向切分』，微服务是『跨进程的横向切分』；一个微服务内部通常仍用分层组织代码。
