01僵尸进程：退出了，但还没被回收

第一层

概念与判定

子进程退出时，内核要保留它的退出状态（exit code、资源用量）供父进程读取，直到父进程调用 wait/waitpid。这段「已死但未回收」的状态就是僵尸（Zombie, Z）。

判据僵尸进程正常进程
ps 状态ZR/S/D
是否占 CPU/内存几乎不占（只剩 task_struct）占
能否 killkill -9 无效（已经死了）能
怎么清除父进程 wait，或父进程退出—
僵尸不能被杀，只能被回收。若父进程一直不 wait，僵尸会持续占用 PID 和内核 task_struct，最终耗尽 PID（fork: Cannot allocate memory / Resource temporarily unavailable）。

02三种回收方式

第二层

参数·命令·量化

  1. 同步 wait：父进程调用 waitpid(pid, &status, 0)，阻塞直到子进程退出。
  2. 异步 SIGCHLD：安装 handler，收到 SIGCHLD 时循环 waitpid(-1, ..., WNOHANG) 回收所有已退出的子进程。
  3. 忽略 SIGCHLD：signal(SIGCHLD, SIG_IGN) 或 sigaction 设 SA_NOCLDWAIT，内核自动回收，不产生僵尸。
// 正确的 SIGCHLD 回收：必须循环，因为多个子进程可能同时退出
void on_chld(int sig) {
    int saved = errno;
    while (waitpid(-1, NULL, WNOHANG) > 0) { }
    errno = saved;
}

// 或更省事（不需要子进程退出状态时）
signal(SIGCHLD, SIG_IGN);
只 waitpid 一次是错的：标准信号不排队，多个子进程同时退出时只触发一次 SIGCHLD。handler 里必须 while 循环到没有可回收的子进程为止。

03孤儿进程：父进程先死了

子进程还活着，父进程先退出 → 子进程成为孤儿，被 init（PID 1）或 systemd --user 收养。这通常是好事：收养者会自动 wait，不会产生僵尸。

收养者
PID 1（systemd / init），或设置了 PR_SET_CHILD_SUBREAPER 的祖先进程
影响
孤儿本身继续正常运行，只是 ppid 变成 1
排查
ps -eo pid,ppid,stat,comm 看 ppid=1 的进程
容器里的 PID 1 很关键：若容器的 1 号进程不处理 SIGCHLD，它产生的僵尸会堆积。所以容器常配 tini 或 --init 作为最小的 init。

04守护进程：脱离终端的 double-fork

守护进程（daemon）要在后台长期运行、脱离控制终端。标准做法是 double-fork：

pid_t pid = fork();
if (pid > 0) exit(0);          // 1) 父退出，子成孤儿被 init 收养
setsid();                       // 2) 脱离控制终端，成为新会话首进程

pid = fork();
if (pid > 0) exit(0);          // 3) 第二次 fork：确保不是会话首进程，无法再获得终端

chdir("/");                     // 4) 避免占用挂载点
umask(0);
// 5) 重定向 stdin/stdout/stderr 到 /dev/null 或日志
int fd = open("/dev/null", O_RDWR);
dup2(fd, 0); dup2(fd, 1); dup2(fd, 2);
步骤目的
第一次 fork + 父退出子进程成为孤儿，脱离原终端
setsid()新建会话，成为无控制终端的会话首进程
第二次 fork确保最终进程不是会话首进程，永远无法重新打开终端
chdir("/")避免守护进程阻止某个目录被卸载
重定向 fd避免向已关闭的终端写导致 SIGPIPE/错误

05排障与边界

第三层

排障与边界

  • 大量 Z 进程：ps -eo stat,ppid,pid,comm | awk '$1 ~ /Z/' 找僵尸，再看它们的父进程为何不 wait。
  • 父进程也不能 kill？若是 D 状态（不可中断睡眠，多在等 IO），kill -9 也无效，需等 IO 完成或重启。
  • PID 耗尽：cat /proc/sys/kernel/pid_max，僵尸堆积会耗尽；ps -e | wc -l 看当前进程数。
  • systemd 服务产生僵尸：服务若 Type=forking 但未正确 daemonize，systemd 可能跟踪错 PID。

06速记卡

僵尸 = 未回收

waitpid / SIGCHLD 循环 wait / SIG_IGN。

SIGCHLD 要循环

孤儿是好事

被 init 收养，自动 wait。

double-fork

两次 fork + setsid，彻底脱离终端。

容器 init

tini / --init 处理 PID 1 的僵尸回收。

容器与 systemd 里的回收职责

僵尸进程的本质是父进程没调用 wait。在传统主机上父进程是 shell 或 systemd，到了容器里父进程往往就是你的应用 —— 如果它是 PID 1 又没写信号处理，僵尸就没人收。

场景谁是回收者风险解法
物理机 / 虚拟机init（systemd，PID 1）低孤儿被 init 收养并回收
Docker 单进程容器容器内的 PID 1（你的应用）高：应用不处理 SIGCHLD 就留僵尸docker run --init（注入 tini）
Docker 多进程容器取决于启动脚本中用 tini/dumb-init 或 shell 里 exec 启动主进程
Kubernetes Pod每个容器各自的 PID 1中容器退出后 Pod 重建，僵尸随容器消失；长期运行的容器要加 init
K8s 共享 PID 空间pause 容器（PID 1）中shareProcessNamespace: true 后由 pause 回收
systemd 服务systemd 或子进程收割器低KillMode=control-group（默认）确保全组清理

定位与处理命令

# 看僵尸：STAT 列出现 Z 就是僵尸，看 PPID 找它爹
ps -eo pid,ppid,stat,comm | awk '$3 ~ /Z/'
ps -eo pid,ppid,stat,wchan:20,comm --sort=-pid | head -30
pstree -p <ppid>            # 看父进程是谁，判断该杀谁

# 僵尸杀不掉是正常的：kill -9 僵尸无效，要杀它的父进程（或让父进程 wait）
kill -TERM <ppid>           # 先优雅退出，让父进程有机会回收子进程
kill -9 <ppid>              # 实在不行才杀父进程；父进程死后子进程被 init 收养并回收

# 内核层面确认
cat /proc/<pid>/status | grep -E 'State|PPid'
cat /proc/<pid>/stat | awk '{print $3}'    # 第 3 字段为 Z 表示僵尸

容器场景

# Docker / K8s
docker run --init myimage                      # 注入 tini 作为 PID 1，负责回收僵尸
docker top <cid>                               # 容器内的进程视图
docker exec <cid> ps -eo pid,ppid,stat,comm | awk '$3 ~ /Z/'

kubectl exec <pod> -- ps -eo pid,ppid,stat,comm
kubectl get pod <pod> -o jsonpath='{.spec.shareProcessNamespace}'
kubectl top pod <pod>                          # 僵尸不占 CPU/内存，但占 PID 槽位

systemd 配置要点

# systemd：服务单元里与回收相关的关键项
[Service]
ExecStart=/usr/bin/myapp
KillMode=control-group      # 默认：停止时清理整个 cgroup，避免残留子进程
Restart=on-failure
RestartSec=5s
Delegate=yes                # 允许服务自己管 cgroup（用 systemd 做资源管理时要开）
TasksMax=1000               # 限制进程/线程总数，防止 fork 炸弹拖垮整机

# 查看服务的子进程树与是否被正确清理
systemctl status myapp
systemd-cgls /system.slice/myapp.service
systemctl kill -s TERM myapp

容器内 ps 看到的 PID 是容器命名空间内的编号；在宿主机上要用 docker top 或 ps -ef --forest 才能对上真实 PID。僵尸不占内存也不占 CPU，唯一的危害是占 PID —— 数量到几万时会耗尽 pid_max 导致无法 fork。

代码层面怎么正确回收

写长期运行的进程时，子进程的回收必须在代码里显式处理。三种语言各有一个标准做法。

Go：必须 Wait

// Go：os/exec 启动的子进程必须 Wait，否则退出后变僵尸
cmd := exec.Command("/bin/sh", "-c", "do-something")
if err := cmd.Start(); err != nil { return err }
// ... 做别的事
if err := cmd.Wait(); err != nil {   // Wait 内部调用 wait4，回收子进程
    log.Printf("cmd failed: %v", err)
}

// 大量子进程场景：用 channel 收集，避免 Wait 串行阻塞
var wg sync.WaitGroup
for _, job := range jobs {
    wg.Add(1)
    go func(j Job) {
        defer wg.Done()
        c := exec.Command(j.Bin, j.Args...)
        _ = c.Run()          // Run = Start + Wait，内部已回收
    }(job)
}
wg.Wait()

C：SIGCHLD 与子收割者

// C：忽略 SIGCHLD 让内核自动回收（最简单，但拿不到退出状态）
signal(SIGCHLD, SIG_IGN);

// C：需要退出状态时的标准写法——非阻塞 waitpid 循环
void reap(int sig) {
    int saved_errno = errno;
    while (waitpid(-1, NULL, WNOHANG) > 0) {   // WNOHANG：没有子进程退出就立即返回
        /* 继续回收，直到没有可回收的 */
    }
    errno = saved_errno;
}
struct sigaction sa = {0};
sa.sa_handler = reap;
sigemptyset(&sa.sa_mask);
sa.sa_flags = SA_RESTART | SA_NOCLDSTOP;       // SA_RESTART 避免打断系统调用
sigaction(SIGCHLD, &sa, NULL);

// 想成为「子收割者」（像 init 一样收养孤儿）
prctl(PR_SET_CHILD_SUBREAPER, 1);   // Linux 3.4+

Python 与容器修复

# Python：subprocess 的常见僵尸来源
import subprocess
p = subprocess.Popen(['sleep', '1'])
p.wait()          # 必须 wait；poll() 只检查不回收，配 wait() 使用

# concurrent.futures / multiprocessing 忘记 join 也会留僵尸
from concurrent.futures import ProcessPoolExecutor
with ProcessPoolExecutor(max_workers=4) as ex:    # with 退出时会自动 join
    list(ex.map(work, items))

# 容器里当 PID 1 又不处理 SIGCHLD 时，最小修复：用 tini 包一层
# Dockerfile: ENTRYPOINT ["/usr/bin/tini", "--", "/app/myapp"]

排查与预防逐条核对：

  • 僵尸杀不掉是正常的：kill -9 对 Z 状态无效，必须杀父进程或让父进程 wait。
  • 容器的 PID 1 要负责回收：docker run --init 或 Dockerfile 里用 tini。
  • 长期进程要处理 SIGCHLD，用 waitpid(-1, NULL, WNOHANG) 循环一次收干净。
  • Go 的 exec.Command 忘了 Wait() 是最常见的僵尸来源，用 Run() 更不容易漏。
  • shell 脚本里用 exec 启动主进程，让应用直接当 PID 1，而不是被 shell 包一层。
  • 孤儿进程不危险：父进程死后被 init（或 subreaper）收养，退出时会被正常回收。
  • 守护进程要 double-fork + setsid：脱离控制终端，避免终端关闭时收到 SIGHUP 被杀。
  • 僵尸数量监控：对 ps 里 STAT=Z 的条目数设告警，持续增长说明代码里有 wait 漏了。
  • pid_max 是硬上限（默认通常 32768 或 4194304），僵尸堆积到上限会导致无法 fork 任何新进程。
  • systemd 服务用 KillMode=control-group，否则停止服务时子进程可能残留。
