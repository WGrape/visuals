URL 的路径、查询与百分号编码：看起来一样的地址为何到不同资源

拆开 scheme、authority、path、query、fragment，解释编码、路由归一化和签名风险。

URL 不是一整串“文件名”

以 `https://shop.example.test:443/items/红色?sort=price#reviews` 为例，scheme 是 https，authority 含主机名和可选端口，path 定位 `/items/红色`，query 提供 `sort=price`，fragment `#reviews` 是客户端定位页面内部位置的标识。浏览器发 HTTP 请求时，通常不会把 fragment 送给服务器；服务器只看到路径和查询等请求目标。若后端日志里没有 `#reviews`，不是代理“丢参数”，而是它本来通常不在 HTTP 请求中。

URL 主机名影响 DNS 解析、TLS SNI 和 HTTP Host/`:authority`，但三者可因代理、测试或重定向配置而不同。排障时应分别记录浏览器输入的 URL、解析到的 IP、TLS 验证的名称和应用路由看到的 Host，不能只凭一个地址栏字符串推断后端行为。

百分号编码按字节工作

空格可编码成 `%20`，中文字符通常先转 UTF-8 字节再逐字节百分号编码；例如“中”的 UTF-8 三个字节为 E4 B8 AD，编码为 `%E4%B8%AD`。`%` 后跟两位十六进制表示一个字节，不是“一个中文字符对应一个百分号”。客户端库常自动编码路径参数，手工重复编码可能把 `%2F` 变成 `%252F`，服务器只解码一次后得到文字 `%2F` 而不是斜杠。

查询串中 `+` 是否表示空格，取决于使用 `application/x-www-form-urlencoded` 等表单编码规则；一般 URI 语法里不能一概把 `+` 当空格。排查“a+b 被改成 a b”时要看客户端编码库和服务端解析器，不能简单怪 HTTP 传输丢字节。

保留字符与路由边界

斜杠 `/` 通常分隔路径段，问号 `?` 开始查询，井号 `#` 开始 fragment。若业务 ID 自身含斜杠，编码成 `%2F` 后，代理、框架可能在路由前或后解码，甚至拒绝编码斜杠；不同层次不一致会让请求落到错误路由或触发访问控制漏洞。应设计不含保留分隔符的稳定 ID，或明确整条代理链的解码规则。

路径里的 `.`、`..` 可能被浏览器、代理或服务器规范化。若防火墙在解码前检查路径，而应用在解码后处理 `..`，两者看到的资源不同。安全策略需要在统一的规范形式上判断，并拒绝歧义编码，不应只加一条字符串包含检查。

查询参数的真实语义

查询参数常用于筛选、排序和分页，但并不意味着可以放任何敏感数据。URL 会进入浏览器历史、代理日志、监控和可能的 Referer；访问令牌、密码和个人信息不应随意放在查询串。参数顺序、重复键、大小写和空值如何解释由应用契约决定：`tag=a&tag=b` 可能代表列表，也可能后者覆盖前者。签名算法必须与服务端使用同一规范化和排序规则。

GET 请求体在实践中兼容性有限，不能把大量复杂查询塞进 body 后期望所有代理和缓存都正确理解。对于需要复杂查询的 API，可设计明确的 POST 查询接口，但要写清缓存和幂等语义。

一次签名失败的例子

客户端对原始字符串 `/files/a%2Fb?x=1` 计算签名，代理先解码 `%2F` 再转发为 `/files/a/b?x=1`，服务端按转发后的路径验签，结果不匹配。若服务端为了“修复”而同时接受两种写法，可能出现同一签名指向两个资源的安全风险。应约定在哪一步做百分号编码、路径归一化及签名，必要时由最外层代理保留规范化后的请求目标。

双重编码也可能绕过简单过滤，如 `%252e%252e` 解一次后仍是 `%2e%2e`，再解一次变成 `..`。安全边界应限定解码次数并拒绝歧义路径，避免不同组件各做一次解码。

验证与自测

用普通 ASCII、中文、空格、加号、百分号、斜杠和重复查询键分别构造请求，记录浏览器地址栏、代理收到的 request-target、应用框架解析值。再测重定向后 Location 的编码是否仍正确。若出现 404，先确认真实路径和 Host；若签名失败，对比参与签名的原始字节而不是打印后看似相同的 Unicode 字符。

此处的关键是“哪一层解释了哪些字节”。DNS 不理解 path，TLS 不理解 query，HTTP 服务器不接收 fragment；把层次分清，许多看似神秘的 URL 故障就可定位。

最关键的一条：空格在 URL 路径/查询串里是 %20，在 application/x-www-form-urlencoded 请求体里是 +。两者不能混用——把 + 写进 URL 查询串，服务端会解成字面加号；把 %20 写进表单体，有些实现会解成空格，有些不会。

编码实操

# 正确编码（各语言）
python3 -c "import urllib.parse;print(urllib.parse.quote('a b/中+&'))"
#   a%20b/%E4%B8%AD%2B%26
python3 -c "import urllib.parse;print(urllib.parse.urlencode({'q':'a b','t':'中'}))"
#   q=a+b&t=%E4%B8%AD          ← 注意表单体里空格变成 +

# JavaScript
encodeURIComponent('a b/中+&')     // "a%20b%2F%E4%B8%AD%2B%26"
encodeURI('https://a.com/a b')     // "https://a.com/a%20b"（不编码 :/?&=#）

# Go
url.QueryEscape("a b/中")           // "a+b%2F%E4%B8%AD"
url.PathEscape("a b/中")            // "a%20b%2F%E4%B8%AD"

# curl 自动编码
curl -G 'https://api.example.com/s' --data-urlencode 'q=a b&c' -v

常见坑与排障

  • 双重编码：已编码的 %20 再编码一次变成 %2520。典型发生在“前端编码 + 网关再编码一次”。表现是服务端解出来带 % 字面量。
  • 路径里的 %2F 被服务端拒绝：很多 Web 服务器（Nginx、Tomcat）默认禁止解码后的 / 出现在路径里（安全考虑），会返回 400/404。需要显式开启（Nginx merge_slashes off；Tomcat ALLOW_ENCODED_SLASH）。
  • fragment 不发给服务器：# 之后的内容只存在于浏览器，抓包看不到，服务端也拿不到。想传数据必须用 query 或 body。
  • URL 长度限制：浏览器 2 KB – 8 KB 不等，服务器（Nginx 默认 large_client_header_buffers 4 8k）也有限。大参数必须放 body。
  • 中文乱码的本质：编码端与解码端字符集不一致。现代统一用 UTF-8，但老系统（GBK）仍会踩坑——表现为 %E4%B8%AD 被按 GBK 解成三个汉字。
  • 查询串顺序：协议不保证顺序，签名/缓存 key 前必须做规范化排序，否则签名校验失败或缓存命中率暴跌。
为什么我在 URL 里写了 + 号，服务端收到的是空格？

服务端把查询串按 application/x-www-form-urlencoded 规则解码了（+ → 空格）。要传字面加号必须写 %2B。

encodeURI 和 encodeURIComponent 该用哪个？

编码整条 URL 用 encodeURI（保留 :/?#&= 等分隔符）；编码某个参数值用 encodeURIComponent（连 / & 都编码）。拼 URL 时逐个参数用后者，几乎不会错。

自检

URL 中的 #reviews 会作为 HTTP 请求目标发给服务器吗？

通常不会。fragment 由客户端使用，不随普通 HTTP 请求发送。
