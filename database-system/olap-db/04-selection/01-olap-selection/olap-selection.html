一句话总结：OLAP 选型不必背参数表，只需回答三个问题： ① 要实时还是要吞吐？② 单表扫描还是多表关联？③ 查询并发高不高？ 三个答案一组合，候选范围基本就定了。

01三个关键判断维度

⏱️ 时效：实时 vs 离线

秒级/分钟级（运营看板、实时监控）→ 需要流式写入 + 实时可见，选 ClickHouse / Doris / StarRocks / Druid。

小时级/天级（T+1 报表、离线挖掘）→ Hive / Spark SQL 批处理即可，成本最低。

🔗 模型：单表 vs 多表

宽表/单表为主（日志、埋点、用户行为）→ ClickHouse 的强项，把维表打平进去。

需频繁多表 JOIN（标准数仓星型模型、BI 语义层）→ Doris / StarRocks，CBO 优化器成熟。

👥 并发：高 QPS vs 低 QPS

少量分析师大查询（QPS < 100）→ ClickHouse 完全够用，把 CPU 吃满换最快响应。

对外服务、成百上千 QPS → Doris / StarRocks，或 ClickHouse + 物化视图/预聚合层。

此外还有两个次要维度：是否需要 UPDATE（要 → Doris Unique Key）、 团队运维能力（ClickHouse 调优门槛更高，Doris 更"开箱即用"）。

04常见反模式

❌ 报表直接查业务主库

典型事故：一个 SELECT COUNT(*) FROM orders 把 buffer pool 冲垮， 拖慢整条交易链路。必须走从库 → OLAP 的分层。

❌ 用 ClickHouse 当业务库

它没有事务、UPDATE 是异步的、并发扛不住。需要强一致与高频更新的场景请回到 MySQL/PG。

❌ 维度过多还硬上 Cube

Kylin 的 Cube 随维度指数膨胀。维度 > 10 或基数很高时， 预聚合的收益远小于构建与存储成本。

❌ 一个大宽表塞所有业务

宽表化有边界。字段过多会导致每次查询都要读很多列， 反而失去列存优势。应按分析主题拆成多张宽表。

05面试高频问答

Q：MySQL 从库也扛不住了，下一步怎么演进？
A：按阶段推进：① 先把慢查询优化 + 加索引；② 读写分离，报表走从库； ③ 引入 OLAP 引擎，用 CDC（Canal/Debezium）把数据实时同步过去； ④ 数据量再大就上分层数仓（ODS/DWD/DWS/ADS）。 不要跳步直接上大数据栈，运维成本会失控。
Q：ClickHouse 和 Doris 到底选哪个？
A：看三个信号——多表 JOIN 多、要把结果直接给 BI 工具、需要 upsert， 三者占其一就倾向 Doris/StarRocks；纯日志明细、几万亿行单表扫、团队有调优能力，选 ClickHouse。 不确定时先用 Doris 起步，它的"默认体验"更宽容。
Q：为什么列存分析引擎都不能高并发？
A：因为每个查询都倾向吃满 CPU 与磁盘带宽来换最快的单查询延迟， 这与"高并发共享资源"的设计目标天然冲突。 要高并发就得靠预聚合 / 物化视图把单次查询的数据量降下来，或加缓存层。
