Serverless 无服务器架构

把服务器运维彻底交给云厂商，只写函数/托管服务，按真实调用付费。

Serverless 两层含义 FaaS + BaaS

从下到上：开发者只关心『函数逻辑』与『事件绑定』

Serverless = FaaS（函数即服务，如 AWS Lambda）＋ BaaS（后端即服务，如托管数据库）。开发者不再管『机器』，只管『触发→函数→结果』。

适合的与不适合的

面试高频问答

Q：Serverless 是不是真的没有服务器？
A：有，只是『你不用管』。运维、扩缩容、容灾由云厂商负责，你按调用次数/时长付费，闲时不花钱。
Q：冷启动是什么，怎么缓解？
A：函数长时间无调用后首次拉起需初始化运行时，带来额外延迟。可预留实例(Provisioned)、减小包体积、用轻量运行时、保持温调用缓解。

Serverless：不是没有服务器，是你不用管服务器

Serverless 的准确含义是「服务器管理责任转移给了云厂商」——服务器当然还在，但容量规划、机器运维、扩缩容、打补丁都由平台负责，开发者只提交代码或容器镜像。

责任边界演进与 Serverless 的三种形态

FaaS 的核心特征

事件驱动函数不常驻，由事件触发：HTTP 请求、对象上传、消息、定时、数据库变更
按需计费按调用次数 + 执行时长（GB-秒）计费；不运行不收费
极致弹性从 0 到数千并发自动伸缩，无需任何配置
无状态函数实例可能随时被销毁，不能依赖本地内存与磁盘
维度传统服务FaaS 函数
运行方式进程常驻，等待请求事件到达才创建实例，处理完可能销毁
伸缩单位实例（机器/容器）单个请求（并发实例数）
计费按实例运行时间（即使空闲也收费）按实际调用次数与执行时长
冷启动无（常驻）有（首次调用需创建实例，毫秒~秒级）
状态可保存内存状态无状态，状态必须外置
超时限制无（自己控制）有硬上限（通常 15 分钟以内）
适用长连接、重计算、稳定流量短任务、突发流量、事件处理

什么时候该用 Serverless

非常适合

  • 突发或不规律流量：定时任务、批处理、Webhook、活动页——空闲时不花钱
  • 事件驱动的处理：图片/视频转码、文件处理、数据清洗、消息消费
  • 轻量 API 与 BFF：几个接口的小服务，不值得为它维护一套容器与服务
  • 胶水与自动化：云资源编排、告警响应、运维脚本
  • 初创与验证期：没有运维人力，先把东西跑起来

不太适合

  • 长耗时任务：超过平台超时上限（训练、大批量处理）→ 改用批处理服务
  • 长连接：WebSocket、SSE 在 FaaS 上受限或成本高
  • 高频稳定流量：一直满负荷跑时，Serverless 单价高于常驻实例
  • 超低延迟要求：冷启动不可控，P99 会抖
  • 依赖特定运行环境：大镜像、特定系统库、GPU 常驻

成本拐点大致判断：如果一个服务每天运行时间占比低于 30%~40%，Serverless 通常更省；如果 7×24 满负荷，常驻实例更划算。可用「月度调用次数 × 平均时长 × 单价」与「一台常驻实例月费」直接对比。

冷启动：Serverless 的核心痛点

冷启动是指「首次请求需要创建执行环境」所花的时间，通常包含：

① 调度资源平台分配计算资源：几十到几百毫秒
② 下载代码/镜像包越大越慢，这是最大变量（1MB vs 100MB 差别巨大）
③ 初始化运行时启动 JVM/Node/Python 解释器：几十毫秒到几秒（JVM 最慢）
④ 应用初始化框架启动、依赖注入、建立连接池：通常是最耗时的一段
⑤ 执行函数真正的业务代码

优化手段：

  • 减小包体积：只打包必要依赖，剔除 devDependencies，避免打进整个框架。
  • 延迟初始化：把耗时的初始化（连接池、大对象）放到函数内惰性加载，或放在热路径之外。
  • 复用全局资源：把数据库连接、HTTP 客户端声明在函数外（实例级），同一实例被复用时不会重复创建。
  • 预留实例 / 预热：云厂商提供的「预置并发」或定时 ping 保持实例存活（有成本）。
  • 选轻量运行时：Node/Python 冷启快于 Java；若用 Java 可考虑 GraalVM 原生镜像或 SnapStart。

深入自检

Serverless 真的更便宜吗？

取决于负载形态。Serverless 的计费模型是「按实际使用」，所以负载越低、越不规律，越划算——一个每天只被调用几百次的任务，Serverless 月费可能几块钱，而常驻实例要几十上百元。但如果服务 7×24 高负载运行，Serverless 的单位计算价格通常高于自己租实例，此时反而更贵。另外还要算上隐性成本：冷启动优化的人力、可观测性与调试的复杂度、以及潜在的厂商锁定。判断方法：估算「月度总执行 GB-秒」× 单价，与同等性能的常驻实例月费对比，再加上运维人力成本一起衡量。很多团队最终采用混合模式：稳定核心用常驻服务，突发与边缘任务用 Serverless。

函数是无状态的，那共享数据怎么办？

全部外置。具体：① 业务数据放托管数据库（注意连接池问题——每个函数实例可能各建一个连接，高并发下会打满数据库连接数，需要用 RDS Proxy 之类的连接代理，或限制函数的最大并发）；② 会话与缓存放 Redis；③ 文件放对象存储；④ 跨请求的中间结果放消息队列或数据库，不要指望 /tmp（虽然单次调用内可用，但空间有限且不保证跨调用保留）。另外要注意「实例复用」——平台常重用同一实例处理后续请求，所以函数外的全局变量会在多次调用间保留，这既是性能优化点（连接池复用），也是陷阱（可能残留脏状态）。

Serverless 怎么处理超时和重试？

三个要点：① 设合理的函数超时——宁短勿长，超时会被强制终止，不如早点失败并由调用方重试；② 函数必须幂等——平台在失败时可能自动重试（尤其是事件源触发，如消息队列、对象存储事件），非幂等的函数会造成重复处理，需用业务唯一键去重；③ 长任务拆分——超过函数超时上限的任务，应改成「任务编排」模式：用 Step Functions / 工作流服务把大任务拆成多个短步骤，或改用专门的批处理服务。对于消息触发的场景，还要配置死信队列（重试多次仍失败的消息进入 DLQ），否则会无限重试。

Serverless 的厂商锁定风险有多大？

确实存在，且比容器更严重。锁定来自：函数的编程模型（入口签名、上下文对象）、触发器与事件源的对接方式、配套的 BaaS（托管数据库、认证、队列）、以及 IAM 权限模型。缓解手段：① 把业务逻辑与平台适配层分离——核心逻辑写成纯函数，平台相关的入口代码尽量薄；② 用开源框架（Serverless Framework、Knative）或容器化函数形态，保留迁移可能；③ 优先使用标准化的 BaaS（如兼容 S3 的对象存储、兼容 MySQL 的数据库）而非厂商独有产品；④ 评估迁移成本——如果函数很简单且无状态，重写成本其实不高，真正的锁定往往来自深度使用了厂商的托管数据服务。
