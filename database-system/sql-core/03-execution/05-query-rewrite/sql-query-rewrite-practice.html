调 SQL 不是猜，是先看 EXPLAIN，再对症下药。这里给一套可复用的读计划方法和常见反模式→改写对照。

01先会读 EXPLAIN

重点看三列：type（访问类型，const>ref>range>index>ALL，ALL 是全表扫描要警惕）、rows（估算扫描行数）、Extra（Using filesort / Using temporary / Using where 都是信号）。

EXPLAIN SELECT * FROM orders WHERE user_id=42 AND status='paid' ORDER BY created_at;
-- 关注：
-- type: 若是 ALL，又没有 Using index，说明没用上索引
-- key:  实际用到的索引（NULL = 没用）
-- rows: 估算行数，越大越慢
-- Extra: Using filesort(额外排序) / Using temporary(用临时表) 都要优化
-- MySQL 8 可用 EXPLAIN ANALYZE 看真实耗时与行数

02常见改写套路

  • 避免 SELECT *：只取需要的列，才可能走覆盖索引（Extra 出现 Using index）。
  • 函数包列会让索引失效：WHERE DATE(created_at)='2026-10-01' → WHERE created_at>='2026-10-01' AND created_at<'2026-10-02'。
  • 大 IN 改成 JOIN 小表，或拆成多批；IN 列表过长优化器会放弃索引。
  • OR 跨不同列常导致全表扫：(a=1 OR b=2) → UNION ALL 两个索引查询。
  • 深分页 LIMIT 100000,20 极慢：改用游标 WHERE id>last_id ORDER BY id LIMIT 20。
要点：索引失效第一元凶：对列做运算/函数、隐式类型转换、前模糊 '%abc'、or 条件组合不当。

03索引提示与覆盖

优化器选错索引时用提示纠正；优先构造覆盖索引避免回表。

-- 强制走某索引（慎用，版本升级后可能失效）
SELECT * FROM orders USE INDEX(idx_user) WHERE user_id=42;
-- 覆盖索引：索引本身含查询所需全部列，无需回表
-- CREATE INDEX idx_cover ON orders(user_id, status, created_at);
-- 这样 (user_id,status) 过滤 + created_at 排序都可在此索引完成
