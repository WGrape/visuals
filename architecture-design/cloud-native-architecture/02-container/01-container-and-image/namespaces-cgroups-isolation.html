容器隔离：Namespaces、cgroups 与安全边界

沿一个容器进程的视角理解“看见什么”“能用多少”和“能做什么”。

容器首先是宿主机上的进程

容器并不自带一个完整内核。运行时在宿主机创建进程，给它设置一组 Linux namespaces，使其看到不同的进程编号、挂载点、网络接口或主机名；再用 cgroups 限制和统计 CPU、内存等资源。镜像提供文件系统内容，namespace 提供视图隔离，cgroup 提供资源边界，三者解决的是不同问题。进程在容器里看到自己为 PID 1，不代表宿主机上它真的是 PID 1。

常见 namespace 包括 PID、mount、network、user、UTS 和 IPC。网络 namespace 可以有自己的接口、路由和端口空间；mount namespace 可看到不同挂载树；user namespace 可将容器内 UID 映射到宿主机不同 UID。隔离是否生效要看实际运行参数，使用 host network 或共享 PID namespace 时，相应边界会变弱。

逐步推演

创建进程

容器运行时在宿主机创建真实进程，配置文件系统和运行环境。

设置视图

用 PID、mount、network 等 namespace 改变进程看到的资源。

设置额度

用 cgroup 统计并限制 CPU、内存等资源。

收紧权限

再用用户身份、capabilities 和 seccomp 限制可执行操作。

一次资源限制如何表现

假设容器设置 1 GiB 内存上限，应用进程不断分配内存。cgroup 会统计相关进程的用量，到达限制时可能触发内存回收或 OOM 处理；容器中的进程被杀死，并不等于整台机器没有空闲内存。排查时要同时看容器 memory.current、上限、OOM 计数和宿主机整体内存。CPU 限额则可能使进程被节流，表现为尾延迟上升，却不一定是代码执行量变多。

机制回答的问题典型误判
PID namespace进程能看见哪些 PID容器内 PID 1 等于宿主机 PID 1
Mount namespace看到哪些挂载点镜像只读就没有任何可写路径
Cgroup资源能用多少限制内存等于预留内存
Capabilities / seccomp允许哪些特权操作与系统调用容器默认就完全安全

隔离不是完整安全承诺

共享内核意味着内核漏洞、过宽的 capabilities、特权容器和可写宿主机挂载都可能扩大影响。容器内以 root 运行也不等于拥有宿主机全部 root 权限，但如果加上特权模式或危险挂载，边界会明显改变。可逐项减小权限：使用非 root 用户、只读根文件系统、删除不需要的 capabilities、限制系统调用、避免挂载宿主机敏感路径，并保持内核与运行时更新。

安全配置还要与功能验证一起做。例如应用需要绑定低端口、创建网络设备或使用特定系统调用，应明确它需要哪项能力；不能为了让程序运行直接赋予 privileged。rootless 容器能降低某些宿主机权限风险，但网络、存储和性能行为可能不同，需按工作负载测试。

从现象定位到机制

  1. 容器看不到宿主机某进程：检查 PID namespace，而不是认定进程不存在。
  2. 容器被 OOM 杀死而宿主机尚有内存：检查 cgroup 限额、页缓存统计和应用峰值。
  3. 服务只能在容器内访问：核对 network namespace、监听地址、端口映射与防火墙。
  4. 容器执行系统调用被拒绝：检查 seccomp、capabilities 和权限，而不是只修改镜像层。

练习：容器内命令显示进程号 1，宿主机显示为 42617；应用随后在 1 GiB 限额处被 OOM 杀死。分别指出是哪两种机制解释这些现象，并说出你会查看的两类证据。

资源限制与调度请求不能混淆

在编排平台里，资源 request 常影响调度器把工作负载放到哪里，limit 则约束运行时可用上限；二者语义不同。CPU limit 过低可能产生 cgroup throttling，让应用在低平均 CPU 下仍有高尾延迟。内存 limit 过低会带来 OOM；只调高 limit 而不理解内存泄漏，则可能让节点更快耗尽。排查时应同时观察节点剩余资源、容器 cgroup 计数和应用内存曲线。

命名空间隔离也不是网络可达性的完整解释。容器有独立网络视图，但从宿主机到容器通常还经过虚拟网卡、路由、端口映射或 CNI；服务监听 127.0.0.1 与监听容器接口地址的行为不同。诊断“端口明明在监听却访问不到”时，应从容器内监听地址、容器网络接口、宿主机映射和外部防火墙逐层验证。

namespace 实操

# 查看进程属于哪些 namespace（每条 [402653xxxx] 就是一个 ns）
ls -l /proc/$$/ns
# lrwxrwxrwx 1 root root 0 cgroup -> 'cgroup:[4026531835]'
# lrwxrwxrwx 1 root root 0 ipc    -> 'ipc:[4026531839]'
# lrwxrwxrwx 1 root root 0 mnt    -> 'mnt:[4026531840]'
# lrwxrwxrwx 1 root root 0 net    -> 'net:[4026531957]'
# lrwxrwxrwx 1 root root 0 pid    -> 'pid:[4026531836]'
# lrwxrwxrwx 1 root root 0 user   -> 'user:[4026531837]'
# lrwxrwxrwx 1 root root 0 uts    -> 'uts:[4026531838]'

# 两个进程如果在同一个 namespace，inode 号相同 -> 可以看到对方
# 这就是容器隔离的本质：让进程看不到/摸不到外面的资源

# 手动创建 namespace（理解原理的最佳方式）
unshare --mount --uts --ipc --net --pid --fork --user --map-root-user bash
# 进入后：
hostname container-demo          # 改主机名不影响宿主机（uts ns）
echo $$                          # PID 是 1（pid ns）
ip addr                          # 只有 lo（net ns）
mount -t tmpfs tmpfs /mnt        # 挂载不影响宿主机（mnt ns）

# 进入已存在容器的 namespace（排查神器）
nsenter -t <pid> -n ip addr      # 进入网络 ns 看 IP
nsenter -t <pid> -m -u -i -n -p bash   # 全进入

docker exec 的本质就是 nsenter——找到容器 init 进程的 PID，然后 setns() 加入它的各个 namespace。理解这一点，能让你在没有 docker 命令时也能排查容器网络问题（nsenter -t PID -n + tcpdump）。

cgroup：限制资源用量

子系统限制什么关键文件 / 参数
cpuCPU 时间份额cpu.cfs_quota_us / cpu.cfs_period_us
cpuset能用哪几个核cpuset.cpus
memory内存上限memory.max（v2）
blkio / io磁盘 IO 带宽io.max（v2）
pids进程数上限pids.max（防 fork 炸弹）
net_cls / net_prio网络带宽与优先级配合 tc 使用
devices能访问哪些设备devices.allow

CPU 限制怎么算：cpu.cfs_period_us 默认 100000 μs（100 ms），cpu.cfs_quota_us 设为 50000 表示每 100 ms 只能用 50 ms = 0.5 核；设为 200000 就是 2 核。公式：核数 = quota / period。

cgroup 实操

# 手动用 cgroup v2 限制内存（理解原理）
mkdir -p /sys/fs/cgroup/demo
echo "100M" > /sys/fs/cgroup/demo/memory.max       # 限制 100MB
echo "50000" > /sys/fs/cgroup/demo/cpu.max          # 格式: "quota period" -> 0.5 核
echo $$ > /sys/fs/cgroup/demo/cgroup.procs          # 把当前 shell 加进去

# Docker 等价命令
docker run -d \
  --memory=1g \                    # 硬限制 1GB（超过会被 OOM kill）
  --memory-reservation=750m \      # 软限制，内存紧张时才生效
  --cpus=1.5 \                     # 最多 1.5 核
  --cpu-shares=512 \               # 相对权重（默认 1024，只在竞争时生效）
  --cpuset-cpus="0-3" \            # 绑定核 0-3
  --pids-limit=100 \               # 最多 100 个进程
  --blkio-weight=500 \
  myapp

# ⚠️ 关键提醒：JVM 在容器里的内存问题
#   Java 8u191 之前，JVM 不认识 cgroup 限制，会按<b>宿主机内存</b>算堆大小
#   -> 容器限 1GB，JVM 却申请了 4GB 堆 -> 被 OOM kill
#   解决：
#     -XX:+UseContainerSupport           （8u191+ 默认开启）
#     -XX:MaxRAMPercentage=75.0          # 用容器内存的 75% 作为堆
#   Java 11+ 默认就支持容器，但建议显式设 MaxRAMPercentage

# 看容器实际被限制了多少（在容器内执行）
cat /sys/fs/cgroup/memory.max
cat /sys/fs/cgroup/cpu.max

容器内看内存的两个陷阱：① free 命令在容器里显示的是宿主机的内存（它读 /proc/meminfo，没被隔离）——要看限制请读 /sys/fs/cgroup/memory.max；② 超过 memory 限制时，进程会被 OOM kill，表现为容器退出码 137（128 + SIGKILL 9），这是最常见的容器“无故重启”原因。

容器 vs 虚拟机：隔离强度对比

维度容器虚拟机
隔离级别内核共享，靠 namespace 隔离视图硬件级，独立内核
启动时间毫秒 – 秒秒 – 分钟
内存开销几乎为零（就是进程）每个 VM 几百 MB 起
密度高（单机可跑几百个）低（几十个）
安全性较弱（内核漏洞影响全部）强
性能接近原生有虚拟化开销（约 5 – 15%）

关键区别：容器共享宿主机内核——所以 namespace 隔离的是“视图”（看不到），而不是“资源”（内核仍是同一个）。这意味着内核漏洞可以穿透所有容器，这也是为什么公有云的多租户场景要用 Kata Containers / gVisor（给容器套一层轻量 VM 或用户态内核）来加强隔离。

容器安全加固

# 容器逃逸的风险点（安全检查清单）
# ① 特权模式：几乎等于宿主机 root
docker run --privileged ...        # ❌ 生产环境绝对禁止

# ② 挂载 docker.sock：能控制宿主机上的所有容器
docker run -v /var/run/docker.sock:/var/run/docker.sock ...  # ❌ 极度危险

# ③ 挂载宿主机根目录
docker run -v /:/host ...          # ❌ 可读写宿主机任意文件

# ④ 危险的 capability
docker run --cap-add=SYS_ADMIN ... # ❌ 接近特权
docker run --cap-add=SYS_PTRACE ...# ❌ 可 ptrace 其他进程

# ✅ 安全加固的正确做法
docker run \
  --user 1000:1000 \                  # 不用 root 运行
  --read-only \                       # 根文件系统只读
  --cap-drop=ALL \                    # 去掉所有 capability
  --cap-add=NET_BIND_SERVICE \        # 只加需要的（绑定 80 端口）
  --security-opt=no-new-privileges \  # 禁止提权（setuid 无效）
  --security-opt=seccomp=default.json \
  --tmpfs /tmp:rw,size=100m \         # 可写目录用 tmpfs
  myapp

# 检查容器是否安全
docker inspect <id> | jq '.[] | {Privileged, CapAdd, Binds}'

深入自检

容器里的 root 和宿主机的 root 是同一个吗？

取决于有没有开 user namespace。默认情况下不是——容器内的 root（uid 0）在没有 user ns 时就是宿主机的 uid 0，只是被 capability 限制了能力（不能完全为所欲为）。开启 user ns 后（--userns-remap 或 rootless 模式），容器内的 uid 0 会被映射到宿主机的普通用户（如 uid 100000），此时即使逃逸出来也只是个普通用户，安全性大幅提升。生产建议：开启 userns-remap 或直接用 rootless 容器。

为什么容器里的进程在宿主机上能看到？

因为 pid namespace 是嵌套的——宿主机（父 ns）能看到所有子 ns 的进程，而容器（子 ns）看不到父 ns 的。所以你在宿主机 ps aux 能看到容器进程（PID 是宿主机的真实 PID），而容器内 ps 只看到自己的（PID 从 1 开始）。这个单向可见性正是隔离的实现方式。实用技巧：在宿主机找到容器进程的真实 PID，就能用 nsenter -t PID -n 进入它的网络命名空间排查。

cgroup v1 和 v2 有什么区别？

核心区别：① v1 是多个独立层级（memory、cpu 各挂各的），一个进程可以属于多个层级，导致资源管理混乱；v2 是统一层级（一棵树），所有控制器在一起，语义清晰；② v2 支持压力感知（PSI）——能直接看“CPU/内存有多紧张”，这对调度和自愈很有用；③ v2 的文件名更规范（memory.max 而非 memory.limit_in_bytes）。Kubernetes 1.25+ 已默认使用 cgroup v2，新系统（systemd 250+）也已切换。迁移时主要注意监控脚本的路径变化。

容器网络是怎么实现的？

三层：① network namespace——每个容器有独立的网络栈（自己的网卡、路由表、iptables）；② veth pair——一对虚拟网卡，一端在容器 ns（eth0），一端在宿主机 ns（挂到网桥上），像一根“虚拟网线”；③ 网桥 + NAT——宿主机上的 docker0（或 CNI 插件的 cni0）把各容器的 veth 连起来，再通过 iptables NAT 访问外网。跨主机通信则有 VXLAN 隧道（Flannel）、BGP 路由（Calico）等方案。排查命令：ip netns list、brctl show、nsenter -t PID -n tcpdump。

自检

镜像层、namespace 和 cgroup 能互相替代吗？

不能。镜像提供文件内容，namespace 控制视图，cgroup 管理资源用量。

为什么 privileged 容器会显著扩大风险？

它允许更多特权操作并削弱默认隔离，容易让应用触达宿主机资源。
