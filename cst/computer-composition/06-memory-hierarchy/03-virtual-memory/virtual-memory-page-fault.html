虚拟内存：分页、TLB 与缺页异常

从地址翻译讲到多级页表、快表、缺页类型与页面置换

一、为什么要有虚拟内存

如果程序直接使用物理地址，会遇到三个死结：多个程序地址冲突、程序能看到别人的内存、内存小于程序体积就跑不起来。虚拟内存给每个进程一个独立、连续、从 0 开始的地址空间，由 MMU 负责翻译成物理地址，一举解决隔离、保护与「内存不够」的问题。

隔离
每个进程有自己的页表
A 进程的地址 0x1000 与 B 的完全无关
保护
页表项带权限位
只读页写入会触发段错误
超量使用
只把用到的页放进内存
程序体积可以远大于物理内存
共享
不同页表可映射到同一物理页
共享库、进程间通信都靠它

二、页表与多级页表

页（Page）通常 4KB，物理内存按同样大小切成页框（Frame）。页表记录「虚拟页号 → 物理页框号 + 权限位」。如果单级页表，32 位地址空间 4GB / 4KB = 100 万页，每页表项 4B，一张页表就是 4MB，每个进程都来一份，内存直接被吃光 —— 所以有了多级页表。

32 位地址（两级页表，页大小 4KB = 2^12） | 页目录索引 10 bit | 页表索引 10 bit | 页内偏移 12 bit | 查找过程： 1) CR3 寄存器 -> 页目录基址 2) 用高 10 bit 找到页目录项 -> 得到页表基址 3) 用中间 10 bit 找到页表项 -> 得到物理页框号 4) 物理页框号 << 12 | 页内偏移 = 最终物理地址 页表项常见标志位： P present，1=在内存中，0=不在（访问即缺页） R/W 读写权限（0=只读） U/S 用户/内核态权限 D dirty，被修改过（换出时要写回） A accessed，被访问过（页面置换算法用）

多级页表为什么省内存

因为没用到的中间层可以不分配。一个只用了几 MB 的小进程，只需要少数几张下级页表，而不是把整张 4MB 的扁平页表都建出来。

三、TLB：给翻译加缓存

多级页表意味着一次地址翻译要多次访问内存（每级一次），这慢得无法接受。TLB（Translation Lookaside Buffer）是 MMU 里的一个高速缓存，把「虚拟页号 → 物理页框号」的翻译结果记下来，命中就直接拿到物理地址。

情况需要几次内存访问耗时量级发生频率
TLB 命中1 次（直接访问数据）~1 ns绝大多数
TLB 未命中多级页表次数 + 1（数据）比命中慢数倍到十几倍少量
缺页（页不在内存）还要加一次磁盘 I/O毫秒级，慢百万倍越少越好

为什么 TLB 很小

它做在 MMU 里，用昂贵的相联存储器，容量通常只有几百到几千项。

大页 Huge Page

把页从 4KB 提到 2MB / 1GB，同样 TLB 容量覆盖的内存翻数百倍，对数据库、JVM 这类大内存程序收益明显。

TLB 刷新的代价

进程切换时若换页表就要刷 TLB（现代 CPU 用 ASID/PCID 打标签避免全刷）。

为什么要注意局部性

随机跨大范围访问会疯狂 TLB miss；顺序访问则几乎全命中。

四、缺页异常：三种类型

类型触发场景内核做什么代价
次要缺页 Minor页已在内存，只是页表没建（如首次访问共享库）建映射即可低（几十微秒）
主要缺页 Major页不在内存，在磁盘/文件上发起 I/O 读入，可能还要换出别的页高（毫秒级）
非法访问访问未映射地址或权限不足发 SIGSEGV，进程被杀进程终止

段错误（Segmentation fault）的本质

就是一次非法缺页：地址不在任何合法的 VMA 区间里，或权限不匹配（写只读页、用户态访问内核页）。内核无法修复，只能给进程发 SIGSEGV。

五、页面置换：内存不够时换谁

主要缺页时若物理内存已满，必须挑一页换出。挑谁决定了后续缺页率。

算法思路优点缺点
FIFO换最早进来的实现简单可能换掉热点页（Belady 异常）
LRU换最久没用的接近最优，命中率高严格实现代价高，需硬件支持
Clock / 二次机会环形扫描 + 访问位近似 LRU，开销低精度不如真 LRU
LFU换用得最少的适合稳定访问模式需要老化，否则早期热点赖着不走
OPT（理论）换未来最晚用到的缺页率最低无法实现，只作基准

工作集

进程在一段时间内实际访问的页集合。工作集装得进内存就不怎么缺页。

抖动 Thrashing

工作集大于可用内存 → 不停换入换出 → CPU 都在做 I/O，吞吐崩塌。解决：加内存、减少并发进程数、改善局部性。

交换区 Swap

换出的页存放处。用 SSD 能显著降低主要缺页代价，但仍比内存慢两个数量级。

写时复制 COW

fork 后父子共享只读页，任一方写入才复制 —— 一次 次要缺页 完成复制。

六、工程上的启示

写代码时值得记住的四条

  1. 顺序访问优于随机访问：数组遍历比链表跳指针 TLB 命中率高得多，这往往是数倍差距。
  2. 控制工作集大小：数据结构别无限膨胀，热数据尽量紧凑，冷数据及时释放。
  3. 大内存程序考虑大页：数据库、JVM、AI 推理这类常驻大内存场景，Huge Page 能明显减少 TLB miss。
  4. 谨慎使用 swap：swap 能避免 OOM，但一旦开始频繁换页，服务延迟会不可预测地恶化。
# 观察缺页与 TLB 相关指标 $ ps -o majflt,minflt,cmd -p <pid> # 主要/次要缺页次数 $ sar -B 1 # pgfault/s（缺页）、pgscank/s（换页扫描） $ vmstat 1 # si/so：换入换出，持续非 0 说明在抖动 $ grep -i huge /proc/meminfo # 大页使用情况 $ perf stat -e dTLB-load-misses -p <pid> # TLB 未命中（需 PMU 支持）

七、深入自检

虚拟内存等于「物理内存 + 磁盘」吗？

不等。虚拟内存是一套地址抽象机制，磁盘只是「页面后备存储」的一种。即使物理内存充足、从不使用 swap，虚拟内存机制依然在工作（隔离、保护、共享都靠它）。

为什么 64 位系统用四级甚至五级页表？

因为地址空间巨大（2^48 ~ 2^57），单级页表不可能建得出来，必须分层。代价是 TLB miss 时查找级数变多，所以 64 位下 TLB 与大页更重要。

malloc 之后内存就分配好了吗？

没有。malloc 只扩展了虚拟地址区间（VMA），真正分配物理页是在首次写入触发缺页时（惰性分配）。这也是为什么刚 malloc 的大块内存 RSS 不涨。

为什么有时候内存没满却发生 OOM？

常见原因：① overcommit 策略允许超额申请，真正用到时不够了；② cgroup 限制了容器内存上限；③ 内存碎片导致无法分配连续大块（内核侧）。

缺页异常处理完为什么要「重新执行」那条指令？

因为缺页是在指令执行中途被中断的，这条指令还没完成。内核调入页面、填好页表后返回，CPU 从同一条指令重新开始，这次就能成功翻译地址。

缺页的成本量化与 TLB 命中率

虚拟内存的性能问题几乎全在两个数字上：TLB 命中率和缺页率。理解它们的量级，才知道该优化什么。

事件典型耗时相对参考
TLB 命中 + L1 命中~1 ns1×
TLB 命中 + L2/L3 命中~4~40 ns4~40×
TLB 未命中（需查页表）额外 5~100 ns（多一次内存访问）额外 5~100×
minor fault（页已在内存，只建映射）~1~10 μs1000×
major fault（要读磁盘）1~10 ms（SSD）/10~20 ms（HDD）100 万倍

排查与调优命令

# 看进程的缺页统计（累计值，间隔取样求差）
ps -o pid,minflt,majflt,comm -p 12345
#   minflt: 次缺页（页面已在内存，建映射即可）  -> 通常不用管
#   majflt: 主缺页（真的要读磁盘）              -> 高就有问题

# 实时监控主缺页速率
pidstat -r -p 12345 1      # 看 majflt/s
sar -B 1                   # 系统级 pgpgin/pgpgout (KB/s)、fault/s

# 看 TLB 效率（需要 perf 权限）
perf stat -e dTLB-loads,dTLB-load-misses,iTLB-load-misses -p 12345 sleep 10
#   命中率 = 1 - dTLB-load-misses / dTLB-loads
#   < 95% 就该考虑大页或调整内存访问模式

# 大页（Huge Pages）配置：把 4KB 页换成 2MB，TLB 覆盖提升 512 倍
cat /sys/kernel/mm/transparent_hugepage/enabled       # THP 状态
echo always > /sys/kernel/mm/transparent_hugepage/enabled
grep HugePages /proc/meminfo
# 显式大页（数据库常用，需预留）
sysctl vm.nr_hugepages=1024          # 预留 1024 * 2MB = 2GB

# 交换倾向（0~100，越小越不倾向 swap）
sysctl vm.swappiness                  # 默认 60；数据库建议 1~10
  • minor fault 高是正常的：进程启动、malloc 首次触碰、写时复制（fork 后）都会大量触发 minor fault，不用优化。真正要盯的是 majflt/s。
  • 大页是 TLB 问题的标准解：4KB → 2MB 让同样数量的 TLB 表项覆盖 512 倍内存。数据库、DPDK、大模型推理都建议开。注意 THP 有 defer+madvise 模式，只给显式申请的程序用，避免整机内存碎片。
  • major fault 不一定是内存不足：mmap 读文件、加载共享库、第一次执行代码路径都会触发。关键是看持续速率而不是累计值。
  • swap 是性能悬崖不是渐变：一旦开始 swap，延迟可能涨 100~1000 倍。数据库机器建议直接关 swap 或把 swappiness 设成 1。
  • 内存访问模式影响 TLB：随机访问大数组、链表遍历最容易 TLB miss；顺序访问、数据紧凑（结构体数组而非数组结构体）命中率高。
major fault 高但内存还很空闲，为什么？

三种常见原因：① mmap 读文件——用 mmap 映射大文件后顺序读，本质是靠缺页把文件一页页读进来，这是设计如此，不是故障（可以用 MAP_POPULATE 预读或 madvise(MADV_SEQUENTIAL) 优化）；② 程序刚启动——加载共享库、代码页、首次触碰堆内存，启动期几万次 major fault 很正常；③ page cache 被回收——内存虽然看起来空闲，但如果大部分被 page cache 占了，且文件页被回收，重读时还是缺页。判据是持续速率：稳定运行一段时间后 majflt/s 仍高（比如 >100/s），才是真问题。

什么时候该开大页？

三个信号：① perf 显示 dTLB miss 率 >5%；② 内存占用大且访问相对随机（如数据库的 Buffer Pool、大模型的 KV Cache）；③ 单次内存遍历量超过 TLB 覆盖范围（典型 TLB 有 512~1536 项 4KB 页 ≈ 2~6 MB，超过就得换页表项）。收益最大的是数据库（MySQL/PostgreSQL 的共享内存、Oracle SGA）和高性能网络（DPDK）。注意代价：大页会让内存分配粒度变粗，小内存场景下开 THP 反而浪费内存并引入碎片整理开销——所以 THP 有 madvise 模式，只给主动申请的程序用。

缺页异常到底「异常」在哪里？

名字容易误导。缺页不是「错误」，而是虚拟内存机制的核心工作方式——CPU 访问一个还没建立物理映射的虚拟地址，就触发缺页，由内核的缺页处理程序补齐映射，然后重新执行刚才那条指令，程序完全无感知。除了「真的出错」（访问空指针、越界 → SIGSEGV），绝大多数缺页是正常且必要的。理解这一点，就明白为什么说「按需调页」是虚拟内存能实现「进程隔离 + 内存超售 + 写时复制 + mmap」的基础。
