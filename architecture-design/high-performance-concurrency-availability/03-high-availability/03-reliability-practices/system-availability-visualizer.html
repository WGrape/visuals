理解"几个9"的含义 — 从年度停机时间到实际场景，直观感受每一个"9"的重量

可用性等级一览 （从 90% 到 99.9999%）

📐 核心公式与概念

可用性 = MTBF / (MTBF + MTTF)
可用性 = 总运行时间 - 故障时间 / 总运行时间
  • MTBF（Mean Time Between Failures）：平均故障间隔时间，两次故障之间的平均运行时长
  • MTTF（Mean Time To Failure）：平均修复时间，从故障发生到恢复服务的平均时长
  • SLA（Service Level Agreement）：服务等级协议，服务商与客户间承诺的可用性保障
  • SLO（Service Level Objective）：服务等级目标，内部设定的可用性目标值
  • SLI（Service Level Indicator）：服务等级指标，衡量服务质量的量化指标（如请求成功率）

可用性是算出来的，不是喊出来的

「五个 9」不是一个口号，而是一串可以计算的工程约束：可用性 = MTBF / (MTBF + MTTR)。要提高它，要么让故障更少（提高 MTBF），要么让恢复更快（降低 MTTR）——后者往往更容易、更便宜，也因此更重要。

落地清单

① 先定 SLO 再建体系

  • SLI 要可度量（如「成功响应占比」「P99 < 200ms」）。
  • SLO 要留余量（对外 SLA 应低于内部 SLO）。
  • 错误预算用完后冻结变更，倒逼稳定性投入。
  • SLO 应按用户旅程定义，而不是按机器指标。

② 消除单点

  • 逐层排查：DNS、LB、网关、应用、缓存、DB、MQ。
  • 每个组件至少 N+1，关键组件跨可用区。
  • 有状态组件要有主从/多副本与自动切换。
  • 定期做「杀实例」演练验证。

③ 降低 MTTR

  • 监控要能「发现异常」，不只是「指标好看」。
  • 告警分级：能自动处理的自动处理，才轮到人。
  • Runbook：每个告警对应明确的排查步骤。
  • 发布要能一键回滚，且回滚要被演练过。

④ 数据可靠性

  • 备份要能恢复（定期演练恢复，而不只是备份）。
  • 明确 RPO（能丢多少数据）与 RTO（多久恢复）。
  • 多地多副本，防止地域性故障。
  • 防止误删：软删除、回收站、权限最小化。

深入自检

99.99% 到底有多难？

它意味着一年只允许约 52 分钟不可用，平均到每月 4.4 分钟。这意味着：任何一次人工介入的故障都可能吃掉整月预算，所以必须做到自动发现、自动切换、快速回滚，并且依赖也要达标——串联系统的总可用性是各组件之积，五个依赖各 99.99% 也只有 99.95%。

为什么冗余能提升可用性？

因为并联系统的不可用概率是各组件不可用概率之积：两个独立的 99% 实例并联，同时故障的概率是 0.01×0.01 = 0.0001，即可用性 99.99%。前提是「独立故障」——如果它们共享电源、交换机、数据库或同一个 bug，冗余就失效了（共因故障）。

SLA、SLO、SLI 有什么区别？

SLI 是指标（如成功率 99.95%）；SLO 是内部目标（如月度成功率 ≥ 99.9%）；SLA 是对外承诺（未达标要赔偿）。通常 SLA 比 SLO 宽松，留出缓冲。这套层级让团队在「还有余量」时敢于快速迭代，在「预算将尽」时转向稳定性工作。

错误预算（Error Budget）怎么用？

把 SLO 的未达标额度当作预算：100% - SLO = 允许的失败额度。在这个额度内可以正常发布；一旦预算耗尽，就冻结非必要变更，把精力转向稳定性。它把「稳定 vs 速度」的争论变成数据驱动的规则。

熔断和降级有什么区别？

熔断是「对故障依赖的快速失败」：当下游错误率超过阈值，短时间内直接拒绝调用，避免资源被拖死，并周期性半开探测恢复。降级是「业务层面的取舍」：关闭或简化非核心功能（如关闭推荐、返回缓存数据），保证核心链路可用。两者常配合使用。

如何验证灾备方案真的有效？

唯一可靠的方式是定期演练：真实执行一次切换/恢复，记录 RTO 与 RPO 并与目标对比。演练要包含「最坏情况」（主机房不可用、数据损坏），而不只是单实例故障。演练结果要进复盘并更新 Runbook——没演练过的灾备等于没有灾备。
