MySQL 优化器详解（二）

完整工作过程：一条 SQL 从解析树出发，经过逻辑改写、物理优化、计划改进，最终变成一棵执行计划树交给执行器的全流水线

① 总览：七阶段流水线 ② 解析 Parsing ③ 预处理 / 解析 ④ 逻辑优化（等价改写） ⑤ 物理优化（CBO） ⑥ 计划改进 ⑦ 计划生成与执行 ⑧ 可观测工具 ⑨ 端到端走查
①总览：七阶段流水线

前文讲过优化器「基于代价选最优计划」。这一篇把它的内部流水线摊开。一条 SQL 进入优化器后，大体经过下面几个阶段（不同版本/查询细节略有差异，但骨架一致）：

②阶段 1：解析 Parsing（词法 + 语法）

解析器（Parser）把字符串 SQL 切词、按 MySQL 语法规则构建一棵解析树（Parse Tree）。它只验证「这句话 MySQL 认不认得」，不读任何用户数据、也不判断执行效率。

  • 词法分析：把 SELECT、FROM、users、= 等拆成 token。
  • 语法分析：依据语法规则确认结构合法，生成解析树。

我们日常遇到的 ERROR 1064 (42000) 语法错误、Unknown column（列名拼错，部分在解析阶段就能发现）就在这里抛出。解析阶段不做表/列是否存在的最终判定——那是下一步预处理的工作。

易错点
解析树只是「语法骨架」，里面还没有把 t1.id 真正绑定到某张表的某一列，也没有展开视图。这些都在下一阶段补全。
③阶段 2：预处理 / 名称解析（Resolve）

预处理（也叫 Resolver）在解析树基础上做语义绑定，把它变成一棵「语义清楚」的查询树（Query Block）：

  • 检查表、列是否真的存在，权限是否够；
  • 把 SELECT a FROM t 里的 a 绑定到 t 的真实列；
  • 展开视图：把对视图的引用替换成视图定义的底层表查询；
  • 处理派生表（FROM (SELECT ...) ）、合并 * 成具体列列表；
  • 初步识别 Const Table 雏形：带主键 / 唯一索引等值条件的表，最多命中一行。

到这一步结束，优化器拿到的是一棵「每个节点都知道自己在说哪张表、哪一列」的查询树，可以放心地做等价变换了。

④阶段 3：逻辑优化（等价改写，不改变语义）

这是优化器的「变形金刚」阶段：在不改变查询结果的前提下，把查询重写成等价的、更容易被高效执行的形式。所有变换只动「逻辑结构」，不关心底层存储。这一步的输出仍是逻辑计划，但已经「更好优化」了。

等价变换作用
子查询扁平化 / 上拉把 IN (SELECT ...) 等子查询转成 JOIN 或半连接（semi-join），避免逐行嵌套执行
视图合并把视图拆解为基础表查询，让优化器能跨视图做索引选择
外连接转内连接若 WHERE 已过滤掉 NULL 侧，LEFT JOIN 可安全转成 INNER JOIN，扩大优化空间
谓词下推（Predicate Pushdown）把过滤条件尽可能提前到离数据最近的地方，减少后续 JOIN / 计算的数据量（见下方交互）
等值推导 / 常量传播由 a.id = b.id AND b.id = 5 推导出 a.id = 5，多一条可用索引路径
常量折叠 / 冗余消除WHERE 1=1 AND status='x' 化简、WHERE col = col 这类恒真/恒假判定
可观测（已核实）
这些改写都记录在 optimizer_trace 里：SET optimizer_trace="enabled=on"; 跑完 SQL 后查 information_schema.OPTIMIZER_TRACE，steps.transformations_to_nested_joins、steps.condition_processing 等字段能看到改写痕迹。

⑤阶段 4：物理优化（CBO 核心，算代价挑路）

逻辑计划「怎么写」定了，但「怎么执行」还没定。物理优化基于代价模型，为查询里的每个表、每种 JOIN 组合估算代价并选最优。这是优化器最重的一块，包含四件事：

4.1 初始分析 + Const Table 检测

先对每个表估算「可能的访问行数」与代价，并识别出 Const Table：带主键 / 唯一索引等值条件的表，最多一行。优化器会在优化期就真的去取这一行，其列值在后续优化中直接当常量用，让估算更准；若取不到行，甚至能提前判定整条查询 0 行、直接短路。

4.2 访问路径选择（Access Path）

对每张表，在「全表扫描」与「各索引访问」之间选最便宜的：

访问方式含义典型 type
全表扫描顺序读所有行ALL
ref非唯一索引等值查找ref
range索引范围扫描（BETWEEN / IN / >）range
index / cover纯索引扫描 / 覆盖索引（不用回表）index
index merge多个索引结果做交/并index_merge

4.3 JOIN 顺序与算法选择

  • JOIN 顺序：用贪心搜索（best_extension_by_limited_search）+ 剪枝（optimizer_prune_level=1）枚举顺序，优先让「小表 / 强过滤表」先做，减少后续被 JOIN 的行数。
  • JOIN 算法：
    • 嵌套循环 NLJ：外表逐行，拿连接键去内表（有索引时很快）；
    • 批量主键访问 BKA：把外键批量送进内表索引，减少随机 IO；
    • 哈希连接 Hash Join：MySQL 8.0.18+ 引入，把内表建哈希表，适合大表无索引场景。

4.4 代价估算

对每个候选计划，用统计信息估「会扫多少行、读多少页」，代入代价模型算出总代价，选最小者。这一步就是上一篇讲的「统计信息 × 代价模型」的落地。

为什么有时会选错
代价估算依赖统计信息。若统计过期（长时间没 ANALYZE TABLE）、或数据严重倾斜又没建直方图，估计行数会偏差，进而「全表扫描比索引便宜」的误判——表现为「有索引却不走」。用 FORCE INDEX 或优化器提示（hint）可临时纠偏。
⑥阶段 5：计划改进（排序 / 分组 / 聚合）

选出基础 JOIN 计划后，优化器再做一轮针对「排序、分组、聚合」的改进，目标是尽量少用临时表和文件排序（filesort）：

  • ORDER BY 优化：若 JOIN 顺序 + 索引本身已按 ORDER BY 字段有序（test_if_skip_sort_order），则直接免排序；
  • GROUP BY 优化：能用索引「松索引扫描（loose index scan）」跳过组内重复行最好；否则考虑流式聚合或建临时表；
  • DISTINCT：尽量借索引天然去重，或退化成 GROUP BY；
  • 决定是否需要临时表、用内存还是磁盘临时表（磁盘临时表代价高很多，见上一篇代价常数）。
⑦阶段 6：执行计划生成与执行

优化结束，输出是一棵执行计划树（AccessPath）——描述「先扫哪张表、走哪个索引、怎么 JOIN、在哪排序」。MySQL 8.0.18+ 用 Volcano（火山）迭代器模型把它变成真正可执行的结构：

执行器按火山模型驱动这棵树：从根迭代器开始，递归向下要数据，Init → 反复 Read → Cleanup。每一层迭代器向子层要一行、处理后再向上吐一行，直到 Limit 截断或取完。所有「读页、取行、锁、buffer pool」的脏活，都在最底层的扫描迭代器里交给存储引擎。

一句话串起两篇
优化器产出的 AccessPath 树，就是执行器手里的「作战地图」；执行器带着这张地图去存储引擎「调兵」。优化器算得越准，执行器跑得越省。
⑧可观测工具：看清优化器到底选了啥

EXPLAIN

在 SELECT 前加 EXPLAIN，看选中的执行计划：type（访问方式）、key（用了哪个索引）、rows（估计扫描行数）、Extra（是否用了覆盖索引 / filesort / 临时表）。

8.0 支持 FORMAT=TREE（树状，直观显示 JOIN 嵌套）与 FORMAT=JSON（含 cost_info 详细代价）。

optimizer_trace

SET optimizer_trace="enabled=on"; 然后执行目标 SQL，再查 information_schema.OPTIMIZER_TRACE。

能看全优化器内部：考虑了哪些 JOIN 顺序、每个访问路径的代价、为什么选了某个索引、做了哪些逻辑改写。是「优化器选错」时定位根因的终极工具。

-- 看计划
EXPLAIN FORMAT=TREE
SELECT * FROM A JOIN B ON A.id=B.aid WHERE A.status='paid';

-- 看优化器内心戏
SET optimizer_trace="enabled=on";
SELECT ... ;  -- 你的目标 SQL
SELECT * FROM information_schema.OPTIMIZER_TRACE;
⑨端到端走查：一条 SQL 的一生
SELECT o.id, c.name
FROM orders o JOIN customers c ON o.cid = c.id
WHERE o.status = 'paid' AND c.region = 'cn'
ORDER BY o.created_at DESC
LIMIT 20;
阶段这条 SQL 身上发生的事
② 解析确认语法合法，生成解析树。
③ 预处理绑定 o→orders、c→customers，展开列，确认 o.cid=c.id 合法。
④ 逻辑优化把 o.status='paid'、c.region='cn' 这两类过滤条件下推到各自表的扫描之前；无子查询/视图可合并。
⑤ 物理优化估算：orders 用 idx_status 比全表扫便宜 → 选 ref/range；customers 用主键 c.id 做 NLJ 内表查找；决定先扫 orders（小结果集）再 JOIN customers。算出各组合代价取最小。
⑥ 计划改进ORDER BY o.created_at：若 idx_status 不含 created_at，需 filesort；优化器评估「索引顺序是否满足」决定要不要额外排序；LIMIT 20 让排序只需保留前 20。
⑦ 生成/执行产出 AccessPath 树（IndexScan(orders) → NLJ → customers → Sort → Limit），执行器由 Limit 向下驱动，最终吐回 20 行。
