Hash / Range / List 怎么选，以及如何让事务尽可能落在单分片

一句话总结：分片键决定了数据物理上"和谁做邻居"。选得好，关联数据共置、事务单分片完成；选得差，热点集中、查询全分片扫描、事务被迫跨分片 2PC。

01为什么分片键是最重要的决定

即使数据库自动分片，数据落在哪个分片仍由分片键决定。它直接绑定三件事：

  • 事务代价：跨分片的事务要走 2PC，延迟和失败率都高；单分片事务便宜得多。
  • 查询范围：按分片键的查询只需访问一个分片；否则要广播到所有分片再汇总。
  • 热点分布：分片键的取值分布决定负载是否均匀。

02三种分区策略

策略做法优点缺点
Hash对分片键取哈希映射到分片数据高度均匀，写入不热点范围查询要扫所有分片
Range按分片键的区间切分范围查询只访问少数分片，有序顺序写入易集中到最后一个分片（热点）
List按枚举值分组适合地理/租户等离散归类枚举值分布不均会倾斜
顺序主键在 Range 分片下会集中到同一分片

03让事务尽量落在单分片

核心思路是共置（co-location）：把会在同一事务里一起修改的数据，用同一个分片键放进同一个分片。例如订单和订单明细都用 order_id 作为分片键，它们就在同一分片，转账/扣减可以单分片提交，无需 2PC。

  • 选择业务上"天然聚集"的键：用户 ID、订单 ID、租户 ID。
  • 避免用"全局随机"或"时间戳"这种让关联数据离散的键。

04热点识别与打散

🔥 顺序主键热点

自增 ID / 时间戳做 Range 分片时，最新区间被集中写入。可对分片键做哈希，或加随机前缀打散，读时再合并。

👀 先观测再处理

用分区/Region 粒度的读写监控找到热点，再针对性打散或调度，不要一上来就改结构。

⚖️ 均匀 vs 局部性

Hash 最均匀但破坏范围查询；打散前缀牺牲了"顺序读连续"，要按查询模式权衡。

05反模式

反模式后果
用随机数/UUID 当分片键写入均匀，但任何范围查询都退化成全分片扫描
高基数字段做 List 分区枚举爆炸或分布不均，管理困难且易倾斜
分片键事后想改等于重新分布全部数据，是重型操作

06选择清单

  • ① 这条分片键下，最高频的事务能否落在单分片？
  • ② 最高频的查询能否按分片键定位，而非广播？
  • ③ 键值分布是否均匀，会不会出现写入热点？
  • ④ 未来扩容/再平衡时，能否增量迁移而不全量重分布？

07常见疑问

分片键选错了能改吗？
非常难。改分片键等于按新键重新分布整张表的数据，是重型在线操作，往往要双写+回填。所以分片键应在设计早期慎重确定。
跨分片查询怎么办？
数据库会把查询下发到所有相关分片并行执行再汇总；代价是网络与汇总开销。设计上应让高频查询都能用分片键定位到少数分片。
为什么顺序主键在 Range 分片下会热？
新写入的总是最大键值，落在"最新区间"那一分片，所有写压力集中一处；而 Hash 分片把键值打散，写入天然均匀。

实操要点

场景推荐分片键原因
电商订单order_id / user_id下单与改状态单分片；user_id 还能让"我的订单"精准定位
多租户 SaaStenant_id租户数据共置，便于隔离与按租户扩缩
时序/日志hash(timestamp) 或时间+前缀打散避免纯时间 Range 写入热点
强范围扫描Range 且接受热点治理成本范围查询友好，但需配套打散/调度
为什么"单分片事务"是性能命根子？

跨分片事务要走两阶段提交，涉及多个节点的网络往返、锁等待与协调者，延迟与失败率都显著上升。把关联数据用同一分片键共置，能让绝大多数事务在单分片内通过本地事务完成，既快又不易冲突。这是分库分表和 NewSQL 都反复强调的设计要点。

深度补充：分片键与分区策略量化

第一层 · 概念与判定 分片键决定数据落到哪个分片，是分布式库的“第一性决策”。判定：选高基数的业务主键或经哈希打散，避免热点与倾斜。

策略优点缺点适用
哈希分片均匀、无热点范围查询跨片通用 KV / OLTP
范围分片范围查询本地易热点（尾部）时间序数据
列表 / 目录可控路由需人工规划多租户隔离
一致性哈希扩缩容少迁移实现复杂缓存 / 动态集群

第三层 · 排障与边界

  • 分片键选错导致单分片过热、其他空闲，只能重分片（代价大）。
  • 用自增 ID 做哈希键仍可能倾斜（低位随机性差），可加 salt。
  • 范围分片的时间键会压在“最新分片”，需按天/小时再拆。
  • 跨分片事务与 JOIN 成本陡增，设计时就该避免按分片键 JOIN。
第四层 · 原理与取舍

分片用“水平切分”换写扩展与单分片可控性，代价是跨分片查询、事务与一致性难度上升。哈希换均匀但牺牲范围局部性，范围换局部性但引入热点。权衡是“均衡性 vs 查询模式”：先按访问模式定键，再决定是否需要二级路由或可线性扩缩的一致性哈希。分片键几乎不可改，选型要一次想清楚。

实例与速查：分片键选型

-- 哈希分片（均匀，适合通用 KV / OLTP）
CREATE TABLE o (id BIGINT, ...)  -- 主键做哈希，数据均匀落片

-- 范围分片（时间序数据，注意尾部热点）
PARTITION BY RANGE (to_days(created)) ( ... )  -- 按天/月再拆

-- 一致性哈希常用于缓存/动态集群，扩缩容只需迁移 1/N 数据
  • 分片键选高基数、访问均匀的列；避免用自增 ID 直接哈希（低位随机性差）。
  • 范围分片的时间键会压在“最新分片”，需按更小粒度再拆。
  • 跨分片 JOIN/事务成本陡增，设计时就该避免按分片键 JOIN。
FAQ：分片键选错了能改吗？

非常难。改动往往意味着全量重分片（导出、按新键重建、再导入），在线系统要做到双写过渡。所以分片键是分布式库的“第一性决策”，选型时就要想清访问模式与扩展性，宁可前期多想、不可后期返工。

常见误区与延伸

  • 误区一：分片键随便选。分片键几乎不可改，选错只能全量重分片，是分布式库的“第一性决策”。li>
  • 误区二：哈希分片一定均匀。自增 ID 直接哈希低位随机性差，可能倾斜，可加 salt 或换复合键。
  • 延伸：范围分片适合时间序数据，但要按更小粒度（天/小时）再拆，避免“最新分片”热点。
  • 延伸：一致性哈希在节点变动时只迁移 1/N 数据，适合缓存与动态集群，但实现与虚节点管理更复杂。

一句话总结：分片键决定数据分布与访问局部性，先按访问模式定键再决定哈希/范围/列表，跨分片 JOIN 与事务要从设计上规避。

决策速记

  • 定键优先：分片键几乎不可改，先想清访问模式。
  • 均匀性：哈希换均匀但牺牲范围局部性，选错可加盐。
  • 局部性：范围换范围查询本地但引尾部热点，需再拆。
  • 避跨片：设计时就规避按分片键 JOIN 与跨片事务。

横向对比与追问

  • 与 OceanBase 比：OB 的分区更强调每日合并下的分区策略，TiDB 强调 Region 自动分裂。
  • 与 Redis Cluster 比：Redis 用哈希槽固定 16384 个，分片键映射到槽，迁移按槽。
  • 追问：为什么一致性哈希在缓存常见、在 OLTP 少？因为缓存可重建、允许迁移少，OLTP 要强一致更难。
  • 追问：复合分片键怎么选？优先选高频等值查询的列，避免跨片的范围扫描。

小结：分片策略要和访问模式强绑定，选错几乎不可改。

分片键选型清单

  • 选高基数列：分片键基数太低会退化为少数大分片；优先选 user_id、order_id 这类分布均匀且高频过滤的列。
  • 避免热点：自增 ID 作分片键会造成尾分片写入热点，改用哈希分片或对时间取模打散。
  • 分区配合：按时间做 RANGE 分区便于 TTL 清理，按实体做 HASH 分片保证同实体同节点，二者正交叠加。
