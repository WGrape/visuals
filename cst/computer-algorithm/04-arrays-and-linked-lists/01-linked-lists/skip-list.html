🔍 多层索引

跳表在底层链表之上建立了多层索引。顶层节点可以快速跳过大量元素，就像在图书馆的分类目录中快速定位。

🎲 随机化

新节点随机决定提升到哪一层（抛硬币决定）。平均每 2 个节点有 1 个在 L1，每 4 个有 1 个在 L2，以此类推。

⚡ O(log n) 查找

从顶层开始，向右找到比目标大的最近节点，然后下降到下一层。重复直到最底层，平均只需 log n 步。

🔄 动态平衡

不像红黑树需要旋转维护平衡，跳表通过概率分布自然保持平衡。插入和删除只需局部修改指针。

跳表：给链表建「地铁快线」

有序链表查找要 O(n)，因为只能一步一步走。跳表的想法很朴素：在链表之上再建若干层「稀疏索引」，高层跳过大量节点，低层保证精确。就像地铁有快车（只停大站）和站站停——先坐快线到附近，再换慢线精确到达。层数由随机决定，因此它是概率平衡，而非严格平衡。

随机层数抛硬币决定：Redis 用 p=1/4，最大层数 32
查找从最高层向右走，太大就下降一层
复杂度期望 O(log n)，最坏 O(n)（概率极低）
空间期望 O(n)，约每个节点 1/(1-p) 个指针
优势实现简单、范围查询天然支持、易做并发版本
多层链表：上层快进、下层精确定位

Redis 为什么选跳表：ZSet 需要「按分数排序 + 范围查询 + 增删」，跳表三点都满足，且实现比红黑树简单得多，还便于做并发与内存紧凑优化。元素少且短时 Redis 会用 ziplist/listpack 代替，进一步省内存。

跳表的关键设计

① 层数怎么随机

  • 初始层 1，反复以概率 p「晋升」，直到失败或达上限。
  • p 越小，上层越稀疏、索引越省内存，但查找变慢。
  • 常见选择：p=1/2（经典）或 p=1/4（Redis，更省内存）。
  • 最大层数要设上限（Redis 32），避免极端情况与内存浪费。

② 插入怎么做

  • 先按查找路径记录每层「最后一个小于新值」的节点（update 数组）。
  • 随机生成新节点层数 k。
  • 从 0 到 k-1 层，像链表插入一样接进去。
  • 若 k 超过当前最大层，更新头节点与最大层。
  • Redis 还会记录 span（跨度），用于 O(log n) 计算排名 rank。

③ 删除与更新

  • 同样先记录 update 数组，再逐层断开链接。
  • 若删除的是最高层节点，要下调最大层。
  • 更新分数：Redis 采用「先删后插」，但会判断位置是否变化以避免不必要操作。
  • 注意内存回收（引用计数/GC）。

④ 工程细节与踩坑

  • 随机性要用好的随机源，避免可预测的退化。
  • 并发版本需考虑：Java ConcurrentSkipListMap 用 CAS + 标记节点实现无锁。
  • 内存开销：每个节点多个指针，节点多时内存不小（Redis 用 ziplist 兜底小集合）。
  • 范围查询是跳表强项：定位起点后沿第 0 层顺序扫，非常高效。

深入自检

跳表的复杂度是「期望」还是「最坏」？

是期望 O(log n)。因为层数由随机决定，理论上存在所有节点都在同一层的极端情况（概率极小），此时退化为 O(n)。实际使用中，随机层数让结构以极高概率保持平衡，效果与平衡树相当。若业务要求最坏情况保证，应选红黑树。

为什么 Redis 用 p=1/4 而不是 1/2？

p=1/2 时平均每个节点要存 2 个指针，p=1/4 时约 1.33 个，内存更省；代价是查找层数略多、比较次数增加。Redis 作者实测后认为 p=1/4 在内存与性能之间更均衡。这是典型的「用少量 CPU 换内存」的取舍。

跳表能替代 B+ 树做数据库索引吗？

内存里可以（RocksDB 的 MemTable 就是跳表），但磁盘上不适合：B+ 树一个节点对应一页、可存几百个键，树高只有 3-4 层；跳表节点的指针指向随机位置，无法利用磁盘的顺序预读与页对齐，IO 次数会显著更多。LevelDB/RocksDB 的做法正是「内存用跳表 + 磁盘用 SSTable」。

跳表怎么支持按排名查询（ZRANK）？

Redis 在每个 forward 指针上额外记录 span（该层跨越的节点数）。查找目标节点时，把经过的 span 累加起来，就得到它的排名，无需遍历。同理反向也可以算逆序排名。这是用少量额外字段换取 O(log n) 的排名查询。

跳表和平衡树到底选哪个？

如果需要严格最坏情况保证、或已有成熟实现，选红黑树；如果看重实现简单、范围查询方便、想做无锁并发，选跳表。对多数业务而言，直接用语言标准库的有序容器即可，两者差距在常数因子级别。

skiplist 的内存开销大吗？

比数组大，比红黑树略大或相当。每个节点除了数据还要存若干 forward 指针（平均 1/(1-p) 个）。Redis 的应对是：元素数量少且成员短时用 ziplist/listpack 紧凑存储，超过阈值才转成跳表，这是典型的「小数据用紧凑结构、大数据用高效结构」的分层策略。
