后端三步

后端要解决的三个问题

指令选择

把 IR 操作映射到指令集

同一个 IR 操作在不同架构上可能有多种实现，需要选择「代价最小」的一种。

; IR: %2 = mul i32 %0, 2
; x86 可选实现：
imul eax, 2      ; 通用乘法指令（慢）
shl  eax, 1       ; 左移 1 位（快，等价乘 2）
add  eax, eax     ; 自加（也快）
常用算法：树覆盖 / 树模式匹配（把 IR 树用机器指令「树模式」覆盖，选代价最小覆盖），或 DAG 覆盖。选择依据是各指令的代价（延迟、吞吐、代码大小）。
核心难点

寄存器分配：变量多、寄存器少

x86-64 只有约 16 个通用寄存器，而函数里的值可能成百上千。分配器要决定：哪些值放寄存器、哪些溢出（spill）到栈。

核心概念：活跃区间与干扰图

  • 活跃区间（live range）：一个值从定义到最后一次使用之间的区间。
  • 干扰（interference）：两个值的活跃区间重叠 → 它们不能共用同一个寄存器。
  • 干扰图：节点是值，边表示「不能共用寄存器」；分配等价于给图着色，颜色数 = 可用寄存器数。
图着色是 NP 完全问题，实践用启发式（Chaitin / Briggs 算法）：反复移除度数小于 k 的节点并压栈，若成功则回溯着色；若存在无法着色的节点，则选择代价最低的值做 spill（溢出到栈），重写代码后重新尝试。

指令调度

重排指令以填满流水线

现代 CPU 是流水线和乱序执行的，指令顺序直接影响等待时间。

约束说明
数据依赖后一条要用前一条的结果 → 不能提前（真依赖 RAW）
反依赖 / 输出依赖可通过寄存器重命名缓解
内存依赖两个访存可能指向同一地址，需保守处理（别名分析）
实践意义：写高性能代码时，减少长依赖链、增加指令级并行（ILP），能让调度器有更多发挥空间；这也是循环展开、软件流水线等优化的原理。
面试问答

高频问题

Q1：后端主要做哪几件事？
指令选择（IR 操作 → 机器指令）、寄存器分配（值 → 寄存器或栈）、指令调度（重排以减少流水线停顿），最后输出汇编或目标文件。
Q2：寄存器分配为什么用图着色？
把每个待分配的值看成节点，两个活跃区间重叠的值之间连边（不能共用寄存器）。给图着色、颜色数不超过可用寄存器数，即得到合法分配。图着色是 NP 完全问题，实践中用启发式算法。
Q3：什么是 spill？
当可用寄存器不足以容纳所有同时活跃的值时，把部分值放到栈上（溢出），每次访问需要额外的 load/store。溢出过多会显著降低性能。
Q4：指令调度能随意重排指令吗？
不能。必须保持数据依赖（真依赖）、控制依赖与内存访问语义。反依赖和输出依赖可通过寄存器重命名缓解；内存依赖受别名分析精度限制，通常保守处理。
Q5：乘 2 为什么常被编译成移位？
左移 1 位在数值上等价于乘以 2，而移位指令比乘法指令延迟更低、吞吐更高。指令选择阶段会按代价模型选择更便宜的实现（强度削弱）。

指令选择：把中间表示翻译成机器指令

同一段中间表示往往有多种翻译方式，比如一个乘法可以翻译成乘法指令，也可以翻译成移位加法的组合。指令选择就是在正确性相同的前提下选更快或更短的那一种。

方法思路优点缺点
宏展开为每种中间操作写一段固定的指令模板实现简单、生成快质量一般，看不到跨模板的优化
树覆盖把中间表示看成树，用最少的指令模板覆盖它质量较好，可考虑相邻操作需要动态规划，实现复杂
窥孔优化生成后在小窗口内做局部替换能修掉明显的浪费只能看到局部
代价模型选择给每种方案算代价，选代价最低的与目标机器特性贴合代价模型需要仔细调校
// 同一句源码，不同的翻译结果 x * 4 -> 乘法指令 // 通用，但可能较慢 -> 左移两位 // 等价且更快 x * 3 -> 乘法指令 -> x + (x 左移一位) // 有时更划算 取数组第 i 个元素 -> 乘法算偏移 + 加法 // 通用 -> 利用寻址模式 // 一条指令完成 // 指令选择的本质： // 在一棵表达式树上，找一组能覆盖全部节点的指令模板， // 使得总代价最小。 // 代价可以是： // 指令条数、执行周期、代码体积、功耗 // 优化级别不同，看重的东西也不同

寄存器分配：变量多、寄存器少

中间表示里可以有无穷多个虚拟寄存器，但物理寄存器只有十几个。分配要回答：谁占用物理寄存器，谁溢出到内存。

寄存器分配：活跃区间 → 干扰图 → 图着色 → 溢出

图着色分配

质量最好：它全局考虑所有变量的冲突关系，优先保留热变量在寄存器里。代价是复杂度较高、编译较慢。适合对运行速度要求高的场景。

线性扫描分配

按区间顺序一遍扫描，维护当前活跃集合，满了就溢出。速度快、适合即时编译这种对编译时间敏感的场景，代价是分配到寄存器的比例略低。

// 活跃区间的直观例子 a = 1 // a 在这里出生 b = 2 // b 在这里出生 c = a + b // 之后不再用 a、b，它们的区间到此结束 d = c * 2 // c 的区间到此结束 return d // 区间示意： // a: [1, 3) // b: [2, 3) // c: [3, 4) // d: [4, 5) // a 与 b 重叠，不能共用寄存器 // a 与 c 不重叠，可以共用同一个寄存器 // 溢出的代价： // 每次访问都要多一次内存读写 // 在循环里的热变量被溢出，性能损失尤其明显 // 所以分配器会优先保留： // 循环内使用次数多的变量 // 区间较短、能腾出位置的变量则优先牺牲

指令调度：把等待时间填满

现代 CPU 是流水线的，一条指令从取到完成要多个阶段。如果下一条指令依赖上一条的结果，就只能等着。调度要做的就是把不相关的指令插进等待的空隙。

调度目标做法风险
隐藏延迟把长延迟指令提前发出，中间插入别的活需要足够的无关指令
减少停顿避免连续依赖链受寄存器压力限制
提高并行让多条执行单元同时工作需要硬件支持多发射
减少溢出调度会改变活跃区间，可能增加寄存器压力两者需要权衡
数据相关后一条依赖前一条的结果，必须等
结构相关两条指令抢同一个执行单元
控制相关分支未确定，后面的指令不敢动
重排的前提不改变单线程语义
与寄存器分配冲突调度拉长活跃区间，可能引发更多溢出
常见做法先分配再调度，或两者迭代几轮
基本块内调度范围小、安全、常见
跨块调度收益大但实现复杂

深入自检：代码生成的六个问题

为什么中间表示要分多层？

因为不同优化适合在不同抽象层次做：高层适合做与机器无关的重构，低层适合做与指令集相关的选择。分层让每一层的任务更专注，也便于支持多种目标平台。

寄存器分配失败会怎样？

会溢出：把某些变量放到栈上，每次访问多一次内存读写。这是正确性优先的兜底，程序仍然能跑，只是变慢。好的分配器会让溢出尽量少、且尽量发生在冷路径上。

为什么有时看汇编和源码对不上？

因为优化器做了重排、合并、消除。被判定为无用的计算会被删掉，循环可能被展开或向量化，所以按源码逐行对应汇编往往对不上，这也是调试优化后代码困难的原因。

指令选择会考虑功耗吗？

会。在移动端与嵌入式场景，代价模型里会加入功耗因素，宁愿多一条指令也要少访问一次内存，因为内存访问远比计算耗电。

即时编译和静态编译在代码生成上有什么不同？

即时编译对编译时间极度敏感，会选更快的算法（比如线性扫描分配）、更保守的优化程度；静态编译可以慢慢来，用更彻底的分析换取更好的代码质量。

为什么同一个程序在不同机器上性能不同？

因为代码生成是按目标机器的特性做的：可用寄存器数量、支持的指令集、流水线深度、缓存大小都不一样。所以针对具体平台编译，往往比用通用配置编译更快。
