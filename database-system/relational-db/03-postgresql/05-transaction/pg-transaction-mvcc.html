① 事务与 ACID 在 PG 中的落地

原子性 A

事务 ID + clog（提交日志）标记；回滚时无需 undo，因为旧版本本来就在

一致性 C

约束、触发器、外键、唯一索引在事务内检查

隔离性 I

MVCC：每行多个版本 + 快照（Snapshot）判断可见性

持久性 D

WAL 先落盘 + 检查点，崩溃后重放

注意一个与其他数据库的重要差异：PG 没有 undo 表空间。回滚时不需要「反向操作」，因为旧版本一直留在堆表里，只是不被新快照看见——代价就是需要 VACUUM。

② MVCC 的核心：xmin / xmax / 快照

可见性判断简化为两条规则（配合 clog 中事务的提交状态）：

  • 插入可见：xmin 对应的事务已提交，且 xmin 在快照中「可见」（即事务在本快照开始前已提交）；
  • 删除/更新不可见：xmax = 0（未删），或 xmax 对应事务未提交 / 在本快照之后才开始。

③ 四种隔离级别与三种异常

隔离级别脏读不可重复读幻读写偏斜
Read Uncommitted❌ 不可能（PG 视为 Read Committed）可能可能可能
Read Committed（默认）不可能可能可能可能
Repeatable Read不可能不可能不可能（PG 的快照隔离更强）可能
Serializable不可能不可能不可能不可能（SSI）

脏读

读到别人未提交的数据。PG 在任何级别都不会发生

不可重复读

同一事务内两次读同一行，值变了（别人已提交的 UPDATE）

幻读

同一事务内两次范围查询，多了/少了行（别人已提交的 INSERT）

写偏斜 write skew

两个事务各自读同一组数据、写不同的行，合起来破坏了约束（如两名医生同时下班导致无人值班）

PG 的一个亮点：它的 Repeatable Read 实际是快照隔离（SI），已经能防止幻读（比 SQL 标准要求更强）；而 Serializable 采用 SSI（可串行化快照隔离），通过跟踪读写依赖图检测「危险结构」，在不加全表锁的前提下防止写偏斜——性能远好于传统的两阶段锁（S2PL）。

⑤ 长事务的危害与排查

长事务（尤其 idle in transaction）是 PG 的头号隐形杀手：

  • 阻止 VACUUM 回收死元组 → 表与索引膨胀；
  • 阻止 freeze → 事务 ID 年龄增长，接近回卷风险；
  • 持有锁 → 阻塞 DDL 与其它 DML；
  • 延长 WAL 保留（复制槽场景）→ 磁盘压力。
-- 找出长事务
SELECT pid, state, xact_start, now() - xact_start AS dur,
       wait_event_type, wait_event, left(query, 80) AS q
FROM pg_stat_activity
WHERE xact_start IS NOT NULL AND now() - xact_start > interval '60 seconds'
ORDER BY xact_start;

-- 常见根因：应用开启了事务却忘了提交（ORM 的自动事务、异常分支未提交）
-- 防护参数
SET idle_in_transaction_session_timeout = '60s';   -- 自动断开空闲长事务
SET statement_timeout = '30s';                     -- 单条语句超时
SET lock_timeout = '3s';                           -- 等锁超时

⑥ 常见问法

Q：PostgreSQL 的 MVCC 是怎么实现的？

A：每行有隐藏字段 xmin（插入该版本的事务 ID）、xmax（删除/更新该版本的事务 ID）、ctid（物理位置）。UPDATE 等于「插入新版本 + 给旧版本打 xmax」，旧版本留在堆表中。事务读取时根据自己的快照（Snapshot：记录当时活跃事务集合）判断每个版本是否可见：xmin 已提交且早于快照 → 可见；xmax 未提交或晚于快照 → 未被删除。旧版本由 VACUUM 回收。核心特点：没有 undo 表空间，读者不加锁。

Q：PG 的 Repeatable Read 为什么能防幻读？

A：因为 PG 的 Repeatable Read 实际实现的是快照隔离（Snapshot Isolation）：事务在第一条语句执行时取得一个快照，之后所有读都基于该快照，因此别人后续插入并提交的新行不在快照中，不会出现幻读。这比 SQL 标准对 RR 的要求更强（标准只要求防不可重复读）。但快照隔离防不了写偏斜——那是 Serializable（SSI）的职责。

Q：什么是写偏斜？Serializable 如何解决？

A：写偏斜（write skew）：两个并发事务读取同一组数据，然后各自修改不同的行，单独看都合法，合起来却破坏了全局约束（例：医院要求至少一名医生值班，两名医生同时读到「还有 2 人」后同时请假）。PG 的 Serializable 用 SSI（可串行化快照隔离）解决：跟踪事务间的读写依赖（rw-conflict），在依赖图中检测「危险环」结构，发现就把其中一个事务中止（40001）。代价：需要重试逻辑，且 Serializable 下 SELECT 也可能产生 SIReadLock 开销。

Q：Read Committed 下有什么并发陷阱？

A：最典型的是「读-判断-写」竞态：两个事务都读到库存 = 1，都判断「够」，都扣减，结果库存变 -1。解法三选一：① 原子 UPDATE：UPDATE s SET qty=qty-1 WHERE id=1 AND qty>0;（检查影响行数）——最推荐，无需显式加锁；② SELECT ... FOR UPDATE 先锁后改；③ 提高隔离级别到 Repeatable Read 并处理重试。记住：Read Committed 下每条语句都取新快照，所以两次读之间数据可能已变。

Q：长事务到底有什么危害？

A：四点：① 阻止 VACUUM 回收死元组——只要事务的快照比死元组更老，这些死元组就不能回收，导致表膨胀；② 阻止 freeze，使 age(relfrozenxid) 增长，逼近事务 ID 回卷风险；③ 持有锁，让 DDL 排队并连锁阻塞后续所有查询；④ 在流复制场景下保留 WAL 与旧版本。防护：设 idle_in_transaction_session_timeout、监控 pg_stat_activity.xact_start、ORM 中避免「开了事务不提交」的异常分支。

Q：PG 与 MySQL 的 MVCC 主要差别是什么？

A：旧版本存放位置不同：PG 把旧版本留在堆表内，靠 VACUUM 回收，因此表会膨胀，调优重点是 autovacuum 与 bloat；InnoDB 把旧版本放入 undo 表空间并用 purge 线程清理，聚簇索引里是原地更新，因此表膨胀较轻，调优重点是 undo 与 history list length。另一个差别：PG 是堆表（索引存 ctid 指针，UPDATE 改 ctid 时索引可能也要更新，除非 HOT），InnoDB 是聚簇索引（主键索引即数据）。共同点：都不能有长事务。
