✅ 数据质量：让数据可信可依赖

数据质量不只是「不报错」，而是准确性、完整性、一致性、及时性等多个维度的综合达标。

先建立直觉：体检报告的各项指标

判断一个人健康不健康，不能只看「有没有发烧」。要看血压、血糖、血常规、肝功能等一整套指标，任何一项异常都说明有问题。

数据质量也一样。它不是一个布尔值，而是一组可度量的维度。一份数据可能「格式完全正确」却「内容严重错误」——比如所有订单金额都是 0。

为什么数据质量如此重要？因为下游所有决策都建立在数据之上：报表、风控、推荐、结算。脏数据会导致错误的业务决策，而且往往很难追溯——等到发现报表数字不对时，基于它做的决策已经执行了。

六个核心维度

维度问的问题典型问题示例
准确性 Accuracy数据是否反映真实情况？订单金额算错、用户性别填反
完整性 Completeness该有的都有吗？必填字段为空、某天数据整体缺失
一致性 Consistency不同地方对得上吗？同一指标在两张报表数值不同
及时性 Timeliness数据按时产出了吗？日报延迟 6 小时才跑完
唯一性 Uniqueness有没有重复？同一订单被写入两次
有效性 Validity格式和范围合法吗？手机号 11 位但含字母、年龄 200

质量问题的层次：从字段到链路

发现得越晚，修复成本越高。字段级问题在入仓时就能拦住；而链路级问题可能要等到周报出来、业务方质疑时才被发现，此时下游已经基于错误数据跑了几十个任务，回溯重跑的成本极高。

怎么落地质量管控

① 在链路上分层设卡

位置手段拦住什么
入仓前字段校验、格式检查、非空约束L1、部分 L2
入仓后行数/空值率/分布监控、主键唯一性检查L2、L3
任务后产出校验（断言）、SLA 监控L3、L4
消费前报表口径校验、与上游对账L4

② 两种校验方式

-- 方式一：SQL 断言（简单场景）
SELECT COUNT(*) AS bad_rows FROM orders
WHERE amount < 0 OR user_id IS NULL;
-- 结果 > 0 即告警

-- 方式二：声明式规则（如 Great Expectations）
expect_column_values_to_not_be_null("user_id")
expect_column_values_to_be_between("amount", 0, 1000000)
expect_table_row_count_to_be_between(10000, 1000000)
规则的三种来源：① 业务常识（金额不能为负）；② 历史统计（行数/分布的历史区间，超出即异常）；③ 跨表一致性（订单表总额 = 支付表总额）。第三类最有价值也最容易漏。

③ 关键实践

  • 把质量检查做成任务的一部分：校验失败则任务失败或阻断下游，而不是只打个日志。
  • 区分「阻断」和「告警」：严重问题（主键重复）阻断；轻微波动（行数 ±10%）告警。
  • 用趋势而非绝对值：行数绝对值每天都在变，但「相比昨日 +300%」一定是异常。
  • 建立质量看板：让各表的质量分可视化，形成倒逼机制。
一句话总结：数据质量不是一次性的清洗工作，而是一套持续运行的校验与告警机制。目标是让问题在进入下游之前被发现。

🎯 面试问答

Q：数据质量和数据清洗是一回事吗？
A：不是。数据清洗是一次性的修复动作（把已有的脏数据改对）；数据质量是一套持续的机制（定义标准、持续校验、及时告警、追踪改进）。清洗治标，质量体系治本。现实中两者都需要：先用清洗处理历史欠账，再用质量机制防止新增问题。

Q：应该先治理哪张表？
A：按「影响面 × 问题严重度」排序，优先治理被下游引用最多、且直接支撑核心决策的表。实操方法：① 用血缘关系找出被引用最多的「枢纽表」；② 看质量看板找出问题最多的表；③ 两者取交集优先处理。不要一开始就试图治理全部表——那是做不完的，要先把 20% 的关键表管住。

Q：怎么判断「多少算异常」？
A：三种方法：① 业务规则（硬约束，如金额 ≥ 0、手机号 11 位）——确定性的；② 历史区间（取过去 N 天的统计值，超出均值 ±3σ 或百分位区间即告警）——最常用；③ 同比环比（相比昨日/上周同一天波动超阈值）——适合有周期性的指标。建议组合使用：硬规则拦确定性错误，统计规则兜底未知问题。

Q：质量问题应该由谁负责？
A：最好是数据生产者负责（谁产出谁负责），而不是让下游数据团队兜底。这需要明确的归属机制：每张表标注 owner，质量告警直接通知 owner，并纳入考核。常见失败模式：数据团队自己搞质量治理，但问题根源在上游业务系统的埋点或写入逻辑——改不动源头，就只能一直打补丁。

数据质量的六个维度与量化

维度定义检查方式 / 阈值
完整性该有的数据有没有非空率 > 99%；行数波动 < 20%
准确性值是否正确与权威源比对一致率 > 99.5%
一致性跨系统是否一致对账差异率 < 0.1%
及时性数据是否按时到达延迟 < SLA（如 5 分钟）
唯一性是否有重复主键重复率 = 0
有效性是否符合格式/范围枚举值合法率 100%
监控手段做法说明
行数波动与过去 7 天同小时比偏离 > 3σ 告警
空值率按列统计 NULL 比例突增告警
唯一性COUNT(*) vs COUNT(DISTINCT pk)不等即有重复
分布漂移（PSI）与基线分布的差异PSI < 0.1 稳定；> 0.25 显著漂移
时效性max(updated_at) 与 now 的差超过阈值告警
枚举分布各类别占比变化新值出现/某类消失要告警

PSI（群体稳定性指数）是最有用的分布漂移指标：PSI = Σ (实际占比 - 预期占比) × ln(实际/预期)。判据：< 0.1 稳定，0.1~0.25 需关注，> 0.25 显著漂移。它比单纯比较均值敏感得多——均值一样但分布完全变了的情况它也能发现。

检查代码

-- 1) 唯一性检查（最重要）
SELECT COUNT(*) AS total, COUNT(DISTINCT order_id) AS distinct_ids
FROM orders WHERE dt = '2026-10-22';
-- 两者不等 = 有重复，必须查源头

-- 2) 空值率按列统计
SELECT
  COUNT(*) AS total,
  SUM(CASE WHEN user_id IS NULL THEN 1 ELSE 0 END) * 1.0 / COUNT(*) AS null_user_rate,
  SUM(CASE WHEN amount IS NULL THEN 1 ELSE 0 END) * 1.0 / COUNT(*) AS null_amount_rate
FROM orders WHERE dt = '2026-10-22';

-- 3) 行数波动（与历史比）
WITH daily AS (
    SELECT dt, COUNT(*) AS cnt FROM orders GROUP BY dt
)
SELECT dt, cnt,
       AVG(cnt) OVER (ORDER BY dt ROWS BETWEEN 7 PRECEDING AND 1 PRECEDING) AS avg7,
       cnt * 1.0 / NULLIF(AVG(cnt) OVER (ORDER BY dt ROWS BETWEEN 7 PRECEDING AND 1 PRECEDING), 0) AS ratio
FROM daily ORDER BY dt DESC LIMIT 7;
-- ratio 在 0.8~1.2 之外要告警
# 4) PSI 计算（分布漂移）
import numpy as np

def psi(expected, actual, bins=10):
    """expected: 基线分布样本；actual: 当前样本"""
    # 用基线的分位数分桶（保证桶一致）
    edges = np.percentile(expected, np.linspace(0, 100, bins + 1))
    edges[0], edges[-1] = -np.inf, np.inf
    e_cnt, _ = np.histogram(expected, bins=edges)
    a_cnt, _ = np.histogram(actual, bins=edges)
    e_pct = np.clip(e_cnt / len(expected), 1e-6, None)   # 防除零
    a_pct = np.clip(a_cnt / len(actual),   1e-6, None)
    return np.sum((a_pct - e_pct) * np.log(a_pct / e_pct))

# 判据：<0.1 稳定；0.1~0.25 关注；>0.25 显著漂移
# 实践：对每个重要数值列每天算一次 PSI，超过 0.25 就告警

# 5) 数据质量规则的配置化（推荐做法）
rules = [
    {"name": "非空", "type": "not_null", "column": "user_id", "threshold": 0.99},
    {"name": "唯一", "type": "unique",    "column": "order_id"},
    {"name": "范围", "type": "range",     "column": "amount", "min": 0, "max": 1e7},
    {"name": "枚举", "type": "enum",      "column": "status", "values": ["paid","unpaid","closed"]},
    {"name": "行数", "type": "row_count", "min_ratio": 0.8, "max_ratio": 1.2},
]

症状原因处理
某天数据突然变多/变少上游重跑或漏跑看行数波动；加分区级的质量门，异常不落库
指标与业务方对不上口径不一致 / 数据源不同建立统一的指标定义（语义层）；定期交叉对账
有重复数据上游重跑没幂等写入用 UPSERT；按主键去重；加唯一约束

枚举值出现新值上游加了新状态监控枚举分布；新值要及时纳入口径
数据延迟上游任务积压 / 资源不足监控 SLA 达成率；设基线告警
质量规则太多跑不动每个规则都全表扫用采样；或一次扫描算多个指标（如用 APPROX_COUNT_DISTINCT）

质量门（quality gate）要放在数据落库前：发现问题数据就阻断而不是让它流入下游——脏数据一旦扩散，清洗成本是阻断的 10 倍以上，而且下游已经基于错误数据做出了决策，损失无法挽回。
