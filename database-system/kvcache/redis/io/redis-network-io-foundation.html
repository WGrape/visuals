Redis 网络 IO 的地基

从 socket() 到 epoll_wait()，把 Redis 脚下那一层讲透：Socket 系统调用、文件描述符、C10K、select/poll/epoll、水平与边缘触发。

🧱 先定位：Redis 的网络 IO 站在哪一层

谈「Redis 网络 IO 怎么做的」之前，先确认它脚下有几层。Redis 自己只写最上面两层，下面四层都是操作系统给的。

本篇的边界：姊妹篇《Redis 网络 IO 设计原理》讲上面两层（单线程为什么快、6.0 多线程），《Redis ae 事件循环》与《ae 源码精讲》讲 ae 库本身。本篇讲下面四层——Socket 系统调用、文件描述符、C10K、select/poll/epoll、ET/LT，以及 Redis 是怎么坐在这套地基上的。

🔌 最基础的 Socket 模型：六个系统调用

客户端和服务端要通信，双方各创建一个 Socket——相当于各开一个「口子」，读写数据都走它。可以先把它想象成一根网线，一头插客户端，一头插服务端。

创建 Socket 时要指定网络层用 IPv4 还是 IPv6、传输层用 TCP 还是 UDP。我们只看基于 TCP 的服务端流程。

1
socket()　创建 Socket

指定 IPv4 + TCP，内核返回一个文件描述符。此时还没有地址，也没有连接。

2
bind()　绑定 IP 和端口

绑定端口：内核收到 TCP 报文后，靠 TCP 头里的端口号找到对应应用程序。绑定 IP：机器可能有多块网卡，绑定哪块就只收那块网卡上的包。

3
listen()　进入监听

对应 TCP 状态机的 listen 状态。想知道某个网络程序起没起，用 netstat 看它的端口有没有被监听即可。

4
accept()　取出已建立的连接

从内核的全连接队列里取出一个已完成三次握手的 Socket 返回给应用。没有连接时会阻塞等待。

5
read() / write()　收发数据

用 accept 返回的那个 fd 读写。读写 Socket 的感觉和读写文件几乎一样——因为在 Linux 里 Socket 本来就是以「文件」形式存在的。

6
（客户端侧）connect()

客户端创建 Socket 后调用 connect，参数指明服务端 IP 与端口，随后开始三次握手。

为什么强调「两个 Socket」：后面讲 epoll 时你会发现，Redis 把监听 fd 注册成「可读时去 accept」，把已连接 fd 注册成「可读时去读命令」。这两件事的处理函数完全不同，根源就在这里。

🧬 文件描述符背后：内核里到底有什么

基于「Linux 一切皆文件」的理念，Socket 在内核里也是以文件形式存在的，也有对应的文件描述符（fd）。顺着 fd 往下追，能看到一条完整的链。

为什么全用一个 sk_buff：协议栈是分层的，如果每层都用自己的结构体，层间传递就要反复拷贝数据，CPU 效率会大幅下降。统一用一个结构体 + 移动 data 指针，就做到了零拷贝地穿过各层。

📈 C10K：为什么「一个连接一个线程」不行

上面最基础的 Socket 流程是同步阻塞的：服务端还没处理完一个客户端的 IO、或读写阻塞住时，别的客户端连不上来。只能一对一通信，太浪费了。

单机理论上能连多少个客户端？

TCP 连接由四元组唯一确定：本机 IP、本机端口、对端 IP、对端端口。服务端通常固定监听一个端口，所以本机 IP 和端口是固定的，变化的只有对端 IP 和端口：

最大 TCP 连接数 = 客户端 IP 数 × 客户端端口数 = 232 × 216 = 248（理论值）

理论值很丰满，现实受两个硬约束：文件描述符Socket 也是文件，就占一个 fd，Linux 单进程默认上限常为 1024，可用 ulimit 调大；系统内存每个 TCP 连接在内核里都有数据结构，都要占内存。

三种并发模型，代价各在哪

多进程模型

主进程负责监听，accept 返回后用 fork() 创建子进程，子进程继承父进程的 fd，直接用已连接 Socket 通信。

代价：进程上下文切换要换虚拟内存、栈、全局变量、内核堆栈、寄存器，「包袱」很重；子进程退出若不 wait/waitpid 回收会变成僵尸进程，慢慢耗尽资源。撑 100 个还行，1 万个扛不住。

多线程模型

用 pthread_create() 建线程，把已连接 Socket 的 fd 传进去。同进程内的线程共享 fd 列表、地址空间、全局数据，切换时只需换私有数据，开销比进程小得多。

代价：频繁创建销毁线程仍有开销，所以用线程池；线程池的全局队列要加锁。1 万个线程仍然太多。

I/O 多路复用

一个进程维护多个 Socket。虽然任一时刻只处理一个请求，但每个请求的事件耗时压到 1 毫秒以内，一秒就能处理上千个请求——多个请求复用了同一个进程，类似 CPU 并发多进程，也叫时分多路复用。

这才是 C10K 的正解。

🔍 I/O 多路复用：select / poll / epoll

思路一致：把要监视的连接（fd）交给内核，内核告诉你哪些有事件了，你再处理。差别全在「怎么交、怎么查、怎么回」。

机制数据结构fd 数量限制每次调用要做什么复杂度
select固定长度 BitsMap（fd_set）受 FD_SETSIZE 限制，默认 1024集合拷入内核 → 内核线性遍历 → 集合拷回用户态 → 用户态再遍历一遍O(n)
poll动态数组，链表组织突破 1024，仍受系统 fd 上限约束与 select 本质相同，只是不再用 BitsMapO(n)
epoll内核红黑树 + 就绪链表上限即进程可打开的最大 fd 数epoll_ctl 维护红黑树；内核回调把就绪 fd 挂进就绪链表；epoll_wait 只取就绪的获取就绪接近 O(1)

epoll 的三个调用

int s = socket(AF_INET, SOCK_STREAM, 0);
bind(s, ...);
listen(s, ...);

int epfd = epoll_create(...);          // 创建 epoll 实例
epoll_ctl(epfd, EPOLL_CTL_ADD, s, ...); // 把要监听的 socket 加进去

while (1) {
    int n = epoll_wait(epfd, events, ...);  // 等待就绪事件
    for (每个就绪的 socket) {
        // 处理
    }
}
epoll 赢在哪两点：① 内核用红黑树持有全部待检测的 socket，增删改 O(log n)，不必每次把整个集合传进内核，省掉大量拷贝与内存分配；② 事件驱动——socket 有事件时由回调挂进就绪链表，epoll_wait 只返回真正就绪的那些，不需要轮询扫描全集合。
辟谣：epoll_wait 没有用共享内存。网上不少文章说「用户态和内核态指向同一个就绪链表，所以零拷贝」——这是错的。看过内核源码就知道，epoll_wait 的实现里调用了 __put_user，这个函数正是把数据从内核拷到用户空间。它省的是「遍历」和「整集合来回拷贝」，不是就绪事件的那次拷贝。

⚡ 水平触发 vs 边缘触发

epoll 支持两种事件触发模式。用快递箱很好理解：

水平触发 LT（默认）

快递放进快递箱，只要你没取走，它就不停地给你发短信提醒，直到你取出为止。

对应到 IO：只要内核缓冲区里还有数据可读，就一直把这个可读事件报给你。没读完会反复唤醒你，所以你不必一次读完。

边缘触发 ET

快递放进快递箱，它只发一次短信；你一直不去取，也不会有第二条。

对应到 IO：只在状态变化的那一刻通知一次。如果你没把缓冲区读完，剩余数据就再也没有新通知了——所以必须循环读写直到返回 EAGAIN / EWOULDBLOCK。

为什么 ET 必须配非阻塞 IO：ET 要求你循环读写直到系统告诉你「没了」。如果 fd 是阻塞的，最后一次 read/write 会直接卡在那里，整个事件循环停摆。所以 ET 模式下 fd 必须设成非阻塞。
一般 ET 效率更高，因为能减少 epoll_wait 的系统调用次数；但 LT 更不容易写错。select/poll 只有 LT，epoll 默认 LT，可按场景切成 ET。
另一个容易忽略的点：多路复用说「可读」，未必真的读得到。Linux 手册对 select 有明确说明：数据到达后可能因校验和错误被丢弃，也可能出现被虚假报告为就绪的情况。若用阻塞 IO，接下来的 read 就会真的阻塞住。因此使用 I/O 多路复用时，最好一律搭配非阻塞 IO。

🚀 Redis 怎么坐在这套地基上

Redis 的选择非常克制：非阻塞 Socket + I/O 多路复用 + 单线程事件循环（Reactor）。

ae：一层薄薄的跨平台封装

不同操作系统提供不同的多路复用机制，Redis 在编译期按性能从高到低挑第一个可用的：

#ifdef HAVE_EVPORT
#include "ae_evport.c"   // Solaris event ports
#else
#ifdef HAVE_EPOLL
#include "ae_epoll.c"    // Linux epoll  ← 最常用
#else
#ifdef HAVE_KQUEUE
#include "ae_kqueue.c"   // macOS / BSD kqueue
#else
#include "ae_select.c"   // 兜底：O(n)，且 fd 上限 1024
#endif
#endif
#endif

四种实现对外暴露同一套 API（aeApiCreate / aeApiAddEvent / aeApiDelEvent / aeApiPoll / aeApiName），上层完全不用关心底下是 epoll 还是 kqueue。这就是工厂模式的好处。

一次命令的完整链路

单线程为什么还这么快：瓶颈不在 CPU——数据全在内存里，操作极快；真正耗时的是网络读写与系统调用。用一个线程 + epoll 把「等」的时间全部交给内核，自己只做「处理就绪事件」这一件事，就避开了多线程的锁竞争与上下文切换。

🧵 Redis 6.0 多线程 IO：到底改了什么

网络硬件越来越快，瓶颈逐渐转移到网络 IO 的读写上。6.0 的改动很克制：只把「读写 socket + 协议解析」分给一组 IO 线程，命令执行仍然严格单线程。

1
主线程接收事件、建立连接

取出这批就绪的 socket，放进一个全局队列。

2
IO 线程并行读 + 解析

按轮询（Round-Robin）把待读 socket 分给 IO 线程，并行完成网络读与协议解析。主线程在此期间阻塞等待。

3
主线程串行执行命令

队列全部处理完后，主线程依次执行这些命令，把结果写进内存缓冲区。这一步永远单线程。

4
IO 线程并行写回

再次把写回网卡的活分给 IO 线程，并行发回各客户端；主线程清空队列，接收下一批。

两个配置项，别只配一个

io-threads 默认 1，即关闭多线程 IO。设为 N 表示启用 N-1 个 IO 线程（主线程本身也算一个）。

io-threads-do-reads 默认 no：也就是说默认只并行写回，读取仍由主线程做。想要读写都并行，必须把它设为 yes——很多人只配了 io-threads 就以为全开了。

官方建议与适用条件

只在机器至少 4 核时才考虑开启，且至少留一个备用核：4 核建议设 2 或 3，8 核建议 6，线程数不要超过核数，超过 8 基本没有意义。

低 QPS 场景开启反而可能因线程间数据传递的开销而变慢。生产环境改动前先压测对比。

一句话：多线程 IO 只分担「搬数据」的体力活，碰数据的永远只有主线程一个人。所以 Lua 脚本、事务、SETNX 依然是绝对原子的，业务层不需要因为 6.0 多线程而加任何锁。

🚫 六个常见误区

误区事实
epoll_wait 用共享内存，零拷贝错。内核实现里用了 __put_user 把就绪事件拷到用户空间。省掉的是「遍历全集合」和「整集合来回拷贝」。
Redis 6.0 多线程 = 命令并行执行错。命令执行始终单线程；多线程只负责 socket 的读写与协议解析。
多路复用报「可读」就一定能读到数据不一定。数据可能因校验和错误被丢弃，也可能被虚假报告为就绪，因此必须配非阻塞 IO。
监听 Socket 和已连接 Socket 是同一个不是。监听 fd 全程只有一个、只负责 accept；每个客户端对应一个独立的已连接 fd。
ET 一定比 LT 好ET 系统调用更少、效率更高，但必须一次把数据读完，且必须配非阻塞，写错就会漏事件。LT 更不容易出错。
epoll 比 select 快是因为「不用拷贝」不准确。epoll 的优势主要来自红黑树（避免重复传入全集合）和就绪链表（避免遍历全集合），拷贝次数确实少了，但就绪数据仍要拷一次。

📌 速记

🔌

Socket 六步

socket → bind → listen → accept → read/write；客户端另有 connect 触发三次握手。

🧬

fd 是一条链

fd → file → inode → socket → 收发队列里的 sk_buff；sk_buff 靠移动 data 指针穿过各层，不拷贝。

📈

C10K

理论上限 2 的 48 次方；现实卡在 fd 数与内存。多线程/进程都扛不住 1 万，正解是多路复用。

🔍

epoll 赢在哪

红黑树持有全集（免重复传入）+ 就绪链表只报就绪（免遍历）。select/poll 是两次遍历 + 两次拷贝。

⚡

ET / LT

LT 一直提醒到你读完；ET 只提醒一次，必须循环读到 EAGAIN，且必须配非阻塞。

🚀

Redis 的落点

非阻塞 + 多路复用 + 单线程 Reactor；ae 在编译期从 evport / epoll / kqueue / select 中挑一个。

一句话串起来：内核用 epoll 帮 Redis 盯着成千上万个 fd，Redis 用一个线程把就绪的 fd 取出来依次处理；等的时间全交给内核，自己的时间全花在内存操作上——这就是 Redis 网络 IO 的全部秘密。
