flag 包定义命令行参数，os/flag 支持 -port=8080 与 -port 8080；可用 flag.StringVar 绑定到变量。

var port string
flag.StringVar(&port, "port", "8080", "listen port")
flag.Parse()

典型优先级：flag > env > 文件 > 默认值；启动时校验必填项，缺失早失败（fail fast）。

配置的四个来源与优先级

配置管理的本质是回答一个问题：同一个值在多个地方出现时，谁说了算。约定好优先级，环境差异就不会变成事故。

配置来源的优先级金字塔
默认值保证最小可运行，减少必填项。
配置文件可版本化，适合基线值。
环境变量容器环境的标准注入方式。
配置中心支持热更新，但要有降级。

结构化配置的落地写法

type Config struct { Server struct { Port int `yaml:"port" env:"PORT"` ReadTimeout time.Duration `yaml:"readTimeout"` WriteTimeout time.Duration `yaml:"writeTimeout"` } `yaml:"server"` DB struct { DSN string `yaml:"dsn" env:"DB_DSN"` MaxOpenConns int `yaml:"maxOpenConns"` } `yaml:"db"` LogLevel string `yaml:"logLevel" env:"LOG_LEVEL"` } func Load(path string) (*Config, error) { c := defaultConfig() // ① 默认值 if path != "" { b, err := os.ReadFile(path) if err != nil { return nil, err } if err := yaml.Unmarshal(b, c); err != nil { return nil, err // ② 配置文件 } } applyEnv(c) // ③ 环境变量覆盖 if err := validate(c); err != nil { return nil, err // 启动即校验，别等到用时才发现 } return c, nil } // 启动即失败（fail fast）比运行中才发现配置缺失安全得多
集中在一个结构避免散落各处的 os.Getenv
启动时校验缺关键配置直接退出并说明
打印生效配置脱敏后打一条日志，便于排查
敏感值不落配置文件密钥走环境变量或密钥服务
时间用字符串如 5s / 1m，可读性好
区分环境用 env 字段而非多套目录

多环境与密钥管理

方式做法适用风险
环境变量APP_ENV=prod 区分环境容器、K8s 标配值多了难管理
多配置文件app.dev.yaml / app.prod.yaml本地与简单部署容易漏同步
配置中心远端下发 + 监听变更大规模、需要热更新强依赖，要能降级
密钥服务Vault / KMS / 云厂商密钥管理数据库密码、API Key引入运维复杂度
K8s Secret挂载为环境变量或文件已上 K8s 的场景注意 base64 不等于加密

密钥三条铁律：不进代码仓库；不进日志（打印配置时脱敏）；不随镜像分发（镜像可以被任何人拉取）。

// 打印配置前先脱敏 func (c *Config) String() string { cp := *c if cp.DB.DSN != "" { cp.DB.DSN = maskDSN(cp.DB.DSN) // 只保留主机与库名 } b, _ := json.Marshal(cp) return string(b) }

深入自检

配置该不该支持热更新？

分两类：影响行为的参数（限流阈值、开关）适合热更新；影响资源初始化的参数（端口、连接池大小、DSN）通常应重启生效。强行热更新后者会导致状态不一致。

为什么建议配置集中在启动阶段加载？

散落的 os.Getenv 让「当前到底用的是什么值」无法回答，也让测试难以构造场景。集中加载 + 显式校验 + 打印生效值，能在启动阶段就暴露问题。

环境变量那么多，怎么组织？

统一前缀（如 APP_）、统一命名（大写下划线）、映射到同一个配置结构。超过二十个时考虑改用配置文件，把环境变量只用于少量环境相关的覆盖。

配置文件要不要进仓库？

模板与默认值应当进仓库（便于新人上手与环境复现），但含密钥的实配文件绝不进。生产密钥通过环境变量或密钥服务注入。

本地、预发、生产差异很大怎么办？

先把差异项列出来，逐项判断是「环境差异」还是「配置错误」。真正的环境差异（地址、账号）用变量注入；把相同项统一到默认值里。差异项越少越安全。

Go 配置管理的做法对比

方式优点缺点 / 适用
flag 包标准库、零依赖只支持命令行；配置项多了难维护
环境变量12-Factor 推荐；容器友好无类型、无校验；os.Getenv 到处散落
配置文件（yaml/toml/json）层次清晰、可版本化需要热加载机制
viper支持多种源 + 自动绑定 + 热加载依赖较重；有并发读的安全问题
代码即配置类型安全、可测试改配置要重新编译
12-Factor 要点做法说明
环境差异用环境变量os.Getenv("DB_HOST")不要为每个环境建不同配置文件
配置集中启动时一次性读入结构体不要到处 os.Getenv
敏感信息从 secrets 注入（Vault/K8s Secret）绝不写进代码或镜像
默认值代码里给合理默认环境变量只覆盖差异项
启动校验必填项缺失直接 panic快速失败比运行中出错好

推荐做法：配置文件提供结构 + 环境变量覆盖敏感/环境相关项。启动时解析到一个结构体并校验，之后全程传结构体（或指针），不要在业务代码里散落 os.Getenv。

代码模板

// 配置结构体 + 校验（推荐模式）
type Config struct {
    Env      string `env:"ENV" envDefault:"dev"`
    Port     int    `env:"PORT" envDefault:"8080"`
    DBHost   string `env:"DB_HOST,required"`
    DBPort   int    `env:"DB_PORT" envDefault:"3306"`
    DBUser   string `env:"DB_USER,required"`
    DBPass   string `env:"DB_PASS,required"`      // 敏感项只从环境变量来
    LogLevel string `env:"LOG_LEVEL" envDefault:"info"`
    Timeout  time.Duration `env:"TIMEOUT" envDefault:"5s"`
}

func Load() (*Config, error) {
    var c Config
    if err := env.Parse(&c); err != nil {   // github.com/caarlos0/env
        return nil, err
    }
    if err := c.validate(); err != nil {
        return nil, err
    }
    return &c, nil
}

func (c *Config) validate() error {
    switch c.Env {
    case "dev", "test", "prod":
    default:
        return fmt.Errorf("invalid ENV: %s", c.Env)
    }
    if c.Port <= 0 || c.Port > 65535 {
        return fmt.Errorf("invalid PORT: %d", c.Port)
    }
    return nil
}
// 关键：必填项缺失时直接退出（fast fail），而不是运行时 nil panic
// 配置文件 + 环境变量覆盖（viper 模式）
viper.SetConfigName("config")
viper.SetConfigType("yaml")
viper.AddConfigPath("./etc")
viper.AddConfigPath("/etc/myapp")
viper.AutomaticEnv()                     // 环境变量优先
viper.SetEnvKeyReplacer(strings.NewReplacer(".", "_"))  // db.host -> DB_HOST

viper.SetDefault("server.port", 8080)
viper.SetDefault("server.timeout", "5s")

if err := viper.ReadInConfig(); err != nil {
    if _, ok := err.(viper.ConfigFileNotFoundError); !ok {
        return err        // 文件存在但解析失败 -> 报错
    }
    // 文件不存在 -> 全用默认值和环境变量，允许
}

var c Config
if err := viper.Unmarshal(&c); err != nil { return err }

// 热加载（注意并发安全）
viper.WatchConfig()
viper.OnConfigChange(func(e fsnotify.Event) {
    log.Printf("config changed: %s", e.Name)
    // 注意：viper.Get 不是并发安全的，热加载时要加锁或用 atomic.Value 替换整个配置
})

排障清单

症状原因处理
容器里读不到配置配置文件没挂载 / 工作目录不对用绝对路径；或用环境变量；检查 ConfigMap 挂载
环境变量设了但没生效名字拼错 / 没开启 AutomaticEnv打印实际读到的值；注意 . 与 _ 的替换
配置改了没生效没有热加载，或热加载有并发问题重启；热加载要用 atomic 替换整个配置对象
敏感信息泄露进镜像写在配置文件里被打包只从环境变量/Secret 读；.dockerignore 排除配置
不同环境行为不一致每个环境一份配置文件，容易漂移一份配置 + 环境变量覆盖（12-Factor）
启动后才发现配置错了没做启动校验启动即校验并 fail fast；加 /debug/config 端点（脱敏）
viper 并发 panicviper.Get 不是并发安全的热加载时加锁；或只在启动时读一次

最容易犯的错：把 DB_PASSWORD 这类敏感项写进 yaml 并提交到 Git。正确做法：yaml 里只放结构和默认值，敏感项全部通过环境变量注入，并在 .gitignore 里排除本地配置文件。
