第 07 章 · 树

层次关系与搜索不变量

树让一个节点成为多个分支的入口；搜索性能取决于高度，而不只是节点数。

核心速览

根 Root唯一没有父节点的入口
深度 / 高度深度＝根到该点的边数；高度＝根到最深叶的边数
n−1 条边含 n 个节点的非空树恰好 n−1 条边，且无环
子树任一节点加上它的后代仍是树——递归结构的来源

先建立直觉：为什么需要树

数组查找第 k 个元素是 O(1)，但在中间插入要搬移后面的所有元素，代价 O(n)。链表插入是 O(1)（已知位置时），但查找第 k 个要 O(n) 逐个走。

树想同时拿到两头：它用「父子」这种层次关系把数据组织起来，让查找、插入、删除都只需要从根往下走一条路径。只要这条路径足够短（即树足够「矮胖」），三种操作就都是高效的。

关键洞察：树上的操作代价几乎总是 O(h)，h 是高度，不是节点数 n。所以「让树变矮」是所有平衡树算法的唯一目标——这解释了红黑树、AVL 树、B+ 树为什么都要拼命维持平衡。

二叉搜索树：靠「不变量」而非「位置」查找

普通二叉树只是「形状」，没有任何查找价值。二叉搜索树（BST）多了一条不变量：

对任意节点 x：左子树所有键 < x.key < 右子树所有键，且左右子树自身也满足这条性质。

有了这条不变量，查找就变成了「每比较一次就排除掉一半」：查 5 时当前节点是 4，那么 5 只可能在右子树，左子树整棵可以无视。这就是 BST 把比较次数从 n 降到 h 的原理。

不变量的威力：它让「局部信息」足以做出「全局判断」。你只需要看当前节点的值，就能安全地把一半的子树排除掉——不需要遍历、不需要额外索引。这个思想在二分查找、堆、并查集里反复出现。

中序遍历为什么得到有序序列

中序是「左 → 根 → 右」。由 BST 不变量，左子树都更小、右子树都更大，所以访问顺序天然就是键的升序。这条性质是 BST 与排序算法的桥梁——对 BST 中序遍历即得排序结果，这也是「树形排序」的基础。

插入与删除：不变量怎么维护

插入很简单：从根开始比较，小则往左、大则往右，直到走到空位——把新节点挂在那个空位上，不变量自动保持（因为它落在了正确的位置）。

删除麻烦一些，分三种情况：

被删节点的孩子数做法为什么不破坏不变量
0 个（叶子）直接摘掉没有子树需要安置
1 个用该孩子顶替它的位置孩子本来就在正确的一侧
2 个找中序后继（右子树最小节点）或中序前驱来顶替，再递归删除那个后继后继是右子树中最小的，恰好大于左子树全部、小于右子树剩余部分
删除有两个孩子的节点时，用「中序后继」顶替是标准做法。直观理解：你要在原位置放一个新值，它必须比左子树都大、比右子树（除自己外）都小——全树中满足这个条件的只有中序前驱和中序后继两个候选。

四种遍历与它们的用途

遍历访问顺序典型用途
前序根 → 左 → 右复制一棵树、序列化（先知道根才能重建）
中序左 → 根 → 右BST 得到有序序列；表达式树得到中缀表达式
后序左 → 右 → 根先算子树再算根（求树的高度、释放内存、表达式求值）
层序按层从上到下、每层从左到右按层输出、求最小深度、BFS 类问题（用队列）
记忆技巧：「前 / 中 / 后」指的是根节点被访问的时机——前序先访问根，中序在中间访问根，后序最后访问根。左右子树的相对顺序始终是先左后右。

递归写法极简（以中序为例），迭代写法则要显式维护栈：

# 递归：三行搞定
def inorder(node):
    if not node: return
    inorder(node.left); visit(node); inorder(node.right)

# 迭代：显式栈模拟「走到最左 → 弹出 → 转向右」
def inorder_iter(root):
    stack, cur = [], root
    while stack or cur:
        while cur:            # 一直往左走到底
            stack.append(cur); cur = cur.left
        cur = stack.pop()     # 最左的（或已处理完左子树的）节点
        visit(cur)
        cur = cur.right       # 转向右子树

完全二叉树：用数组存树

完全二叉树按层从左到右紧密填充，没有「空洞」。这个规整的形状带来一个巨大好处：可以用数组存储，不需要指针。

节点下标从 0 起：下标 i 的左孩子是 2i+1，右孩子是 2i+2，父节点是 (i−1)//2。

这省掉了每个节点的左右指针（16 字节），内存更紧凑、缓存更友好——堆（优先队列）就建立在这个表示之上。反过来，如果树形状不规则（比如退化的链），数组表示会浪费大量空间，所以必须用指针。

🎯 面试问答

Q：树的高度和深度有什么区别？

A：深度是从上往下量的：根的深度为 0，一个节点的深度是「根到它的边数」。高度是从下往上量的：叶子高度为 0，一个节点的高度是「它到最深叶子的边数」，树的高度就是根的高度。两者方向相反，复杂度分析里说的 h 指的是高度。

Q：为什么 BST 会退化成链表？怎么避免？

A：因为 BST 的形状完全由插入顺序决定。按 1,2,3,4,5 递增插入时，每个新节点都比之前的都大，于是全部挂在右子树上，树长成一条链，高度变成 n，查找从 O(log n) 退化成 O(n)。避免办法是「平衡」：红黑树、AVL 树通过旋转在每次插入删除后重新调整形状，强制把高度维持在 O(log n)。红黑树牺牲一点严格性换取更少的旋转次数，是工程上更常用的选择。

Q：删除有两个孩子的节点，为什么要用中序后继？

A：因为顶替者必须满足：比整个左子树都大，且比右子树中剩下的都小。全树里满足这个条件的只有两个候选——中序前驱（左子树最大）和中序后继（右子树最小）。用后继顶替后，后继本身最多只有一个右孩子（否则它就不是最小的），于是递归地退化成「删除至多一个孩子的节点」这一简单情况。

Q：中序遍历 BST 为什么一定得到有序序列？

A：中序是「左 → 根 → 右」。由 BST 不变量，左子树所有键都小于根，右子树所有键都大于根，且这一性质递归地成立于每一棵子树。所以按「左、根、右」的顺序列出，就恰好是键的升序。反过来说这也提供了一个判定工具：中序遍历是否有序，是检验一棵树是否满足 BST 不变量的常用方法。

Q：完全二叉树为什么能用数组存？下标关系怎么记？

A：因为完全二叉树按层紧密填充、没有空洞，按层序编号后节点与下标一一对应，不需要指针就能算出父子关系。下标从 0 起：左孩子 2i+1，右孩子 2i+2，父节点 (i−1)//2。这省掉了指针开销并提升了缓存局部性，是堆（优先队列）的实现基础。形状不规则的树若用数组存，会出现大量空洞和空间浪费，所以必须用指针。

Q：什么时候该用树，什么时候该用哈希表？

A：看是否需要「顺序」。只需要按 key 精确查找/插入/删除 → 哈希表，均摊 O(1) 更快。如果需要范围查询（查区间 [a,b] 内的所有键）、前驱/后继、有序遍历、排名 → 必须用平衡搜索树，哈希表做不到（它把键打散了，顺序信息丢失）。这也是数据库索引选择 B+ 树而不是哈希表的原因。

第一层 · 概念与判定：树的分类与识别

一句话判据：树 = 无环连通图，且有 n-1 条边。判断一棵「树」的性质，先看它属于下面哪一类。

四种遍历

# 四种遍历一次记清（递归版最直观）
def preorder(root):    # 根 -> 左 -> 右（先序：用于复制树、序列化）
    if not root: return []
    return [root.val] + preorder(root.left) + preorder(root.right)

def inorder(root):     # 左 -> 根 -> 右（中序：BST 得到有序序列）
    if not root: return []
    return inorder(root.left) + [root.val] + inorder(root.right)

def postorder(root):   # 左 -> 右 -> 根（后序：用于释放、算高度）
    if not root: return []
    return postorder(root.left) + postorder(root.right) + [root.val]

def levelorder(root):  # 层序：BFS，用队列
    from collections import deque
    q, res = deque([root]), []
    while q:
        n = q.popleft()
        if n:
            res.append(n.val)
            q.append(n.left); q.append(n.right)
    return res

# 树高（后序的典型应用）
def height(root):
    return 0 if not root else 1 + max(height(root.left), height(root.right))

量化参考：四种遍历都是 O(n) 时间、O(h) 空间（h 为树高，递归栈）。平衡树 h=log n，退化链表 h=n——后者会爆栈。

第三层 · 排障与边界：递归与判定的坑

坑后果正确做法
递归没判空 rootAttributeError / 空指针函数开头 if not root: return
混淆深度与高度结果差 1明确根的深度算 0 还是 1，全程统一
BST 判定只比较父子放过「右子树里存在更小值」的伪 BST要带上上下界递归，或用中序遍历验证有序
以为树高是 O(log n)递归爆栈或复杂度误判只有平衡树才是 O(log n)；普通二叉树最坏 O(n)
序列化时没记录空节点反序列化结构错乱空节点要写占位符（如 #）
  • 排查顺序：先确认空指针处理 → 再确认深度/高度约定 → 再确认树是否平衡 → 最后验证遍历序列长度等于节点数。
  • 边界一：递归深度 = 树高，Python 默认递归上限约 1000，退化成链表的树会直接爆栈——必要时改迭代。
  • 边界二：判断两棵树相同，必须结构和值都相同；判断镜像要用「左对右」递归。
  • 边界三：二叉树的最近公共祖先（LCA）在 BST 上可以利用有序性 O(h)；普通二叉树要后序回溯或 Tarjan。

BST 判定

# 正确的 BST 判定：带上界与下界
def is_bst(root, lo=float('-inf'), hi=float('inf')):
    if not root: return True
    if not (lo < root.val < hi): return False
    return is_bst(root.left, lo, root.val) and is_bst(root.right, root.val, hi)

# 等价写法：中序遍历结果应严格递增
def is_bst2(root):
    vals = inorder(root)
    return all(vals[i] < vals[i+1] for i in range(len(vals)-1))

第四层 · 原理与取舍：为什么要有「平衡」树

BST 的查找复杂度等于树高。插入顺序决定树形：随机插入得到 O(log n)，有序插入会退化成链表 O(n)。平衡树通过「插入/删除后旋转」强制维持高度约束，把最坏情况也压回 O(log n)。

结构查找插入删除平衡策略用在哪
BST（无平衡）O(h)O(h)O(h)无教学
AVLO(log n)O(log n)O(log n)严格平衡（左右高差≤1），旋转多查多改少
红黑树O(log n)O(log n)O(log n)宽松平衡（最长路径≤2倍最短）工程默认（C++ map、Java TreeMap）
Treap / SkipListO(log n) 期望O(log n) 期望O(log n) 期望随机化平衡Redis zset（跳表）
为什么工程都用红黑树而不是 AVL？

AVL 平衡更严格，查询略快，但插入/删除时要更多次旋转。实际工作负载多为「插入删除与查询混合」，红黑树的旋转次数更少，综合性能更好——C++ 的 std::map、Java 的 TreeMap 都选了红黑树。

什么时候用数组表示树（堆式）？

当树是完全二叉树时（堆、线段树）。用数组下标 i 的孩子是 2i+1/2i+2，省掉指针开销、缓存友好。普通二叉树因为形状稀疏，用数组会浪费大量空间。

树的遍历为什么几乎都用递归？

因为树的定义本身就是递归的（左子树、右子树都是树），递归代码最短最直观。代价是栈空间 O(h)；只有在树极深时才需要改写成显式栈的迭代版本。
