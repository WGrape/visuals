先建立直觉：下班打卡与错峰放学

一栋楼里所有人同时下班，电梯会挤爆；学校同时放学，校门口会堵死。错峰是最朴素也最有效的削峰手段——把同一时刻的动作分散到一个时间窗口里，总量不变，瞬时压力骤降。

缓存过期也是一样：10 万个 key 在同一秒失效和10 万个 key 分散在 300 秒内失效，数据库承受的总查询量完全相同，但瞬时 QPS 相差 300 倍。

三种常见写法

① 简单随机（最常用）

// 基准 300 秒 + 0~300 秒随机
ttl := 300 + rand.Intn(300)
redis.SetEX(key, ttl, val)

② 按业务维度错开

如果不同类别的数据本身就应该有不同的存活时间，可以按业务前缀设定不同基准，再叠加抖动。

base := map[string]int{
    " hot:":  600,   // 热点：长一些
    "cold:" :  120,   // 冷数据：短一些
}
ttl := base[prefix] + rand.Intn(base[prefix]/2)

③ 预热时错峰写入

大促前预热几百万 key 时，不要在一个循环里瞬间写完——不仅 TTL 要抖动，写入时刻本身也要分散，否则虽然过期时间不同，但写入瞬间就把数据库打满了。

for i, k := range keys {
    loadIntoCache(k)
    if i%1000 == 0 { time.Sleep(100 * time.Millisecond) }  // 分批，给 DB 喘息
}

范围怎么定：两个约束

约束说明影响
窗口要足够宽抖动范围应不小于「数据库重建这些数据的总耗时」太窄 → 削峰不明显
上限要可控最长 TTL 不能超过业务能容忍的数据陈旧上限太宽 → 数据太旧
经验值：基准 TTL 的 0.5~1 倍作为随机增量（即实际 TTL 在 1x ~ 2x 基准之间），在削峰效果和数据新鲜度之间比较平衡。

怎样验证真的生效了

  • 看 Redis 的 evicted / expired keys 监控曲线：应该是平缓的，而不是周期性的尖刺。
  • 看数据库的 QPS 曲线：不应出现与 TTL 周期吻合的规律尖峰。
  • 看缓存命中率：错开后命中率应平滑，而非断崖式下跌。
常见误判：加了随机 TTL 但仍然雪崩——多半是因为写入时刻集中（比如整点跑批全量刷新），此时过期虽然分散了，但刷新本身把数据库打满了。要同时检查写入和过期两个时刻。

它解决不了什么

随机 TTL 只对「批量 key 同时过期」有效。以下情况它无能为力，需要别的手段：

  • Redis 整体宕机 → 靠集群高可用 + 多级缓存。
  • 单个热点 key 过期（击穿）→ 靠互斥锁 / 逻辑过期。
  • 查询不存在的 key（穿透）→ 靠布隆过滤器 / 空值缓存。

🎯 面试问答

Q：随机 TTL 会不会让缓存命中率下降？
A：不会明显下降，反而更平稳。命中率主要取决于 TTL 的平均长度，而随机化只是把过期时刻在窗口内重新分布，平均值基本不变（甚至略长）。你得到的是：总命中率相当，但不再有断崖式下跌的瞬间。这正是目的。

Q：所有 key 都应该加随机 TTL 吗？
A：绝大多数是的，成本极低收益很高。但有两种例外：① 必须精确控制失效时刻的数据（如对账快照）；② 本身就用逻辑过期或永不过期策略的热点 key。除此之外，加抖动几乎没有副作用，应该作为默认实践。

Q：抖动范围设多大，有公式吗？
A：没有通用公式，但有两个约束可以推导：下限——窗口要宽到能把峰值压到数据库承载力以下，即 总数 / 窗口秒数 < 数据库安全 QPS；上限——最长 TTL 不超过业务容忍的陈旧时间。取两者交集即可。例如 10 万个 key、数据库安全 500 QPS，窗口至少 200 秒。

Q：为什么我加了随机 TTL，数据库还是有周期性尖峰？
A：大概率尖峰不是来自过期，而是来自写入/刷新。比如整点跑批全量重建缓存，虽然过期分散了，但刷新时刻集中，把所有 key 同时查了一遍库。排查方法：对比尖峰周期与 TTL 周期——若吻合是过期问题，若不吻合（比如恰好在整点）就是刷新问题，需要把刷新也错峰。
