导入系统：绝对导入、相对导入与循环依赖

import 远不止「把代码搬进来」。搜索路径怎么定、绝对/相对导入怎么选、模块为何只加载一次、循环依赖为何会炸——这一篇把 import 的后半程讲透。

搜索路径

import 时解释器去哪找模块？

按 sys.path 列表顺序找：① 当前脚本所在目录 ② PYTHONPATH 环境变量 ③ 标准库 ④ 第三方 site-packages。找到第一个匹配就停。

import sys
print(sys.path)     # 第 0 项通常是入口脚本所在目录

# 临时追加搜索路径（不推荐常用，仅应急）
sys.path.append("/tmp/mylib")
⚠️ 不要用脚本名和库重名（比如自己写个 email.py），否则会把标准库 email 遮掉，import 行为诡异。也别依赖「当前工作目录」，它随启动位置变。
包与 __init__.py 的角色详见__init__.py 详解；本篇聚焦「导入动作本身」。
绝对 vs 相对

包内部该用哪种导入？

绝对导入从项目根写全路径（from pkg.sub import x），清晰、可重构；相对导入用点号（from .sub import x），随包移动不用改，但只能在包内用、不能当脚本直接跑。

# mypkg/
#   __init__.py
#   a.py  →  from mypkg.b import f   # 绝对（推荐）
#   b.py  →  from .c import g         # 相对（同包内）
#         →  from . import a          # 相对，导入同包 a

# 相对层级：. 同级  .. 上一级  ... 上两级
from ..sibling import helper   # 上级包的 sibling 模块
Python 3 统一推荐绝对导入，可读性最好；相对导入只在「包内部深度耦合、希望移动整包不改代码」时选用。注意相对导入的模块不能直接 python b.py 运行，会报 Attempted relative import in non-package。
只加载一次

模块被缓存进 sys.modules

同一进程内，一个模块无论被 import 多少次，只会执行一次；后续 import 直接从 sys.modules 字典取已加载的模块对象。这既是性能优化，也是「模块级单例」的来源。

# a.py
print("a 被加载")      # 只在第一次 import 时打印

# 主程序
import a
import a              # 不再打印，直接命中缓存
import sys
print("a" in sys.modules)  # True

利用这点做「配置单例」「连接池」很方便——在模块顶层建一次，全项目共享。但副作用（import 时自动连数据库、建文件）要小心，因为它只在首次 import 触发，难以控制时机。

循环依赖

互相 import，谁先跑谁崩

a.py import b，b.py 又 import a：执行到一半模块还没建完，访问到未定义的名字就报错。最稳的修复是「延迟导入」或重构分层。

# 错误示范：a.py 顶层就 from b import B
# b.py 顶层又 from a import A  →  ImportError

# 修复法 1：把 import 移进函数（用到了才导入）
def do():
    from b import B    # 延迟到运行时

# 修复法 2：抽出公共依赖到第三个模块 c，
# a、b 都只 import c，打破环
⚠️ 循环依赖往往是「模块职责没切清」的信号。优先重构：把共享的东西下沉到一个中立模块，而不是靠延迟导入打补丁。
动态导入

运行时按字符串加载模块

插件系统、按需加载时才需要动态导入。优先用标准 importlib.import_module，别再用过时的 __import__。

import importlib
mod = importlib.import_module("json")   # 等价于 import json
print(mod.dumps({"a": 1}))

# 插件模式：扫描目录逐个加载
for name in ["plugin_a", "plugin_b"]:
    p = importlib.import_module(name)
    p.register()

动态导入返回的还是同一个模块对象（同样走 sys.modules 缓存）。配合__main__ 守卫：把「可被导入」和「可被直接运行」分开，模块既能当库又能当脚本。

模块搜索顺序与关键机制

import 的完整查找顺序：① sys.modules 缓存（已导入的直接返回）→ ② 内置模块（sys.builtin_module_names）→ ③ 按 sys.path 顺序查找 .py/.so/包目录 → ④ 找到后编译/加载并执行模块代码 → ⑤ 写入 sys.modules。

阶段做什么耗时（首次）
查找遍历 sys.path 找文件几十 μs
编译.py → 字节码（.pyc 缓存到 __pycache__）ms 级（大模块几十 ms）
执行执行模块顶层代码（所有副作用在这里发生）取决于模块内容
缓存写入 sys.modules—
重复导入直接从 sys.modules 返回< 1 μs

import 排查命令

# 看模块搜索路径
python3 -c "import sys; print('\n'.join(sys.path))"
python3 -m site                     # 详细的 site-packages 与路径配置

# 看某个模块从哪来
python3 -c "import numpy; print(numpy.__file__)"
python3 -c "import json; print(json.__file__)"

# 测量导入耗时（找出启动慢的元凶）
python3 -X importtime -c "import requests" 2>&1 | sort -k2 -n | tail -20
# 输出：import time: 列，能看到每个模块的累计/自身耗时

# 看已加载模块与内置模块
python3 -c "import sys; print(len(sys.modules)); print(sys.builtin_module_names)"

# 手动加载与重载
import importlib
mod = importlib.import_module("os.path")
importlib.reload(mod)          # 修改了源码后重载（只在开发时用）

# 清缓存看冷启动差异
find . -name __pycache__ -type d -exec rm -rf {} +

循环导入、包结构与坑

  • 循环导入（circular import）：A 导入 B，B 又导入 A。Python 能处理部分情况（部分初始化的模块对象），但常表现为 ImportError: cannot import name X from partially initialized module。解法：① 把共享的东西抽到第三个模块；② 在函数内部延迟导入（def f(): import B）；③ 用 import module 而不是 from module import name。
  • sys.path[0] 是脚本所在目录（不是当前工作目录），这是很多“明明在同目录却 import 不到”的原因。运行方式不同（python a.py vs python -m pkg.a）会让 sys.path[0] 不同。
  • 相对导入只能在包内用：from . import x 依赖 __package__，直接运行一个模块文件（python x.py）时会报 attempted relative import with no known parent package。
  • __init__.py 的作用：标记目录为包（Python 3.3+ 有命名空间包，不再强制），且导入包时会执行它。所以重型初始化放这里会拖慢所有 import。
  • 导入的副作用：模块顶层代码在导入时执行（连接数据库、读配置、起线程）。这是“为什么 import 一下就卡住”的原因。原则：模块顶层只做定义，副作用放 main 或显式初始化函数。
  • 启动优化：① 用 python -X importtime 找慢模块；② 延迟导入（函数内 import）；③ 避免 from x import *（导入所有名字，慢且污染命名空间）；④ 冷启动敏感场景（如 Lambda、CLI）尤其要注意。
  • 排障顺序：① sys.path 对不对；② sys.modules 里有没有（重复/部分初始化）；③ 是不是循环导入（看 traceback 的 partially initialized）；④ 用 -X importtime 定位慢模块。
为什么改了源码但没生效？

三种可能：① 跑的是 __pycache__ 里的旧 .pyc（Python 会按 mtime 校验，通常会自动失效，但某些文件系统或手动改 mtime 会出问题）→ 删 __pycache__；② 模块已被导入，sys.modules 有缓存 → 用 importlib.reload；③ 装的包在 site-packages，而你改的是另一份源码 → 用 pip install -e . 开发模式安装。

from x import y 和 import x 有什么区别？

import x 只把模块对象绑定到名字 x；from x import y 会执行整个模块，然后把 y 单独绑定。后者更方便但：① 对循环导入更敏感；② 无法感知 y 后续被重新赋值；③ 命名空间污染。大型项目建议 import x + x.y 使用。

一次 import foo 实际走完 5 步。搞清楚顺序，90% 的「明明有这个文件却 import 不到」都能自己定位。

循环依赖：报错形态与 6 种解法

循环导入的本质是模块顶层代码在导入期就要用到对方的属性，而对方还没执行完。报错有固定形态，看到就能认。

两种报错形态

# 典型报错（Python 3.7+ 信息已经很直白）
ImportError: cannot import name 'User' from partially initialized module 'models'
    (most likely due to a circular import) (/app/models.py)

# 另一种形态：先导入的一方拿到的是「半成品」模块
AttributeError: partially initialized module 'a' has no attribute 'b'
    (most likely due to a circular import)
解法做法代价 / 适用
① 延迟导入把 import 挪进函数体内部最省事；但每次调用会查 sys.modules（有缓存，开销极小）
② 提取第三模块公共部分抽到 common.py，两边都 import 它最干净，首选；需要动结构
③ 依赖倒置上层定义接口/协议，下层实现，运行时注入解耦彻底；代码量增加
④ 局部 import + TYPE_CHECKINGif TYPE_CHECKING: from x import Y，注解写字符串只解决类型注解，运行时还得真导入
⑤ 把导入放到底部模块末尾再 import臭名昭著的 hack，可读性差
⑥ 合并模块两个模块本来就拆错了适合小模块

两种最常用写法

# ④ 的标准写法：注解用字符串 / from __future__ import annotations
from __future__ import annotations          # 3.7+ 所有注解都变字符串，不求值
from typing import TYPE_CHECKING

if TYPE_CHECKING:                            # 只有类型检查器会执行，运行时跳过
    from .user import User

class Order:
    def __init__(self, owner: "User") -> None: ...   # 引号可省（有 future 导入时）

# ② 延迟导入
def send_email():
    from .mailer import Mailer               # 调用时才导入
    return Mailer().send()
  • 自检方法：python -X importtime app.py 2>&1 | sort -k2 -n，按累计耗时排序列出导入链，既找循环也找慢导入。
  • 包内相对导入：from . import x 只能在包里用，直接跑 python mod.py 会报 ImportError: attempted relative import with no known parent package。
  • __init__.py 里写业务代码 = 导入 pkg 就执行，最容易制造循环，应保持为空或只做 __all__ 声明。
