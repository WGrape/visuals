🏛️ 外观

给复杂子系统一个容易使用的入口。

一句话记住影院“一键观影”会关灯、开投影、切音源。
问题从哪来图解协作动手试一试伪代码选型与边界
01 · 从问题出发

为什么会需要这个模式？

下单要验证库存、计价、支付、记录订单；调用方重复编排容易漏步骤。

结账要预留库存、计价、收款、创建订单。三个入口各自复制这段调用顺序时，某个入口可能先扣款再校验库存；一旦失败，恢复逻辑也各不相同。

😵 直接写会怎样

function mobileCheckout(cart): inventory.reserve(); payment.charge(); orders.create()
function webCheckout(cart): payment.charge(); inventory.reserve(); orders.create()
// 相同业务流程出现两个不同顺序

💡 关键转折

Facade 提供高层操作，内部协调子系统；底层能力仍可独立使用。

提供 CheckoutFacade.checkout(cart) 作为常用高层入口，让复杂的子系统协作顺序集中在一个地方。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

class CheckoutFacade {
  checkout(cart) {
    inventory.reserve(cart.items)
    receipt = null
    try {
      amount = pricing.total(cart)
      receipt = payment.charge(amount)
      return orders.create(cart, receipt)
    } catch (error) {
      if (receipt != null) payment.refund(receipt)
      inventory.release(cart.items)
      throw error  // 补偿失败还需重试与人工恢复
    }
  }
}

读代码时抓住三件事

  1. 外观公开高层用例 checkout，而非转发每个底层方法。
  2. 外观内部控制调用顺序，并处理常见失败路径。
  3. 子系统仍可独立变化；特殊场景仍可直接使用其接口。

换个业务场景，还能认出来吗？

媒体播放器的 playMovie() 可以开投影、调音量、切输入源、关灯。对外只是一键播放，对内仍由不同设备承担各自职责。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

多个子系统的常用操作需要一个清楚的高层入口

三个具体场景

  • 结账编排库存、计价和支付
  • 影音系统一键观影
  • 部署工具一键执行构建、上传与发布

不适合或要小心

真实结账仍需处理失败补偿与幂等。外观简化入口，却不会自动解决事务。

外观不会自动提供事务或补偿；避免成长为万能业务类

最容易混淆的相邻模式

模式真正的区别
适配器翻译一个不兼容接口；外观简化多个子系统的使用方式。
中介者协调一组对象之间持续的双向交互；外观通常是客户端进入子系统的单向高层入口。

区分时问自己：是在简化多系统的入口，还是翻译一个接口？

落地前检查

  • 明确外观承担的业务事务边界。
  • 不要把所有系统功能塞进一个万能 Facade。
  • 测试子系统失败时的补偿、超时和重复调用。
06 · 自己说一遍

两道检验理解的小题

外观是否必须禁止访问子系统？

不必；它提供常用高层流程，特殊需求仍可调用合适的底层接口。

外观模式能自动保证分布式结账的原子性吗？

不能。它只组织调用；跨服务失败仍需事务、补偿和幂等设计。

第二层 · 多大的复杂度才值得加一层外观

判据阈值说明
调用方要串起的子系统调用数≥ 3低于 3 个直接给个函数就够
跨越的模块/包数≥ 2同一包内不需要外观
调用方数量≥ 2只有一个调用方时外观就是多余间接层
每次调用都要重复的样板代码≥ 5 行如：开事务 → 校验 → 落库 → 提交 → 记日志
子系统是否还会换实现是外观是隔离点，换实现不影响调用方
// 外观：把「下单」这件事的 5 个步骤收进一个方法，调用方只看见 Place
type OrderFacade struct {
	stock   StockService
	pay     PayService
	ship    ShipService
	notify  NotifyService
	tx      TxManager
}

func (f OrderFacade) Place(ctx context.Context, u User, items []Item) (OrderID, error) {
	var id OrderID
	err := f.tx.Do(ctx, func(tx context.Context) error { // 1. 事务边界由外观统一
		if err := f.stock.Lock(tx, items); err != nil {   // 2. 锁库存
			return err
		}
		amt, err := f.pay.Charge(tx, u, items)            // 3. 扣款
		if err != nil {
			return err // 统一回滚，调用方不用记着补偿
		}
		id, err = f.ship.Create(tx, u.Addr, items)        // 4. 建配送单
		if err != nil {
			return err
		}
		return f.notify.Send(tx, u, ‘下单成功’, amt)      // 5. 通知
	})
	return id, err
}
// 调用方：一行。子系统怎么变都与它无关
// id, err := facade.Place(ctx, user, items)
模式为了让谁简单关键区别
外观 Facade让调用方简单提供新接口，子系统不知道外观存在
适配器 Adapter让两个接口能对接不改语义，只转换接口形状
代理 Proxy控制对单个对象的访问接口不变，加的是行为（缓存/鉴权）
中介者 Mediator让多个对象之间解耦对象之间不再互相引用，都找中介者

第三层 · 外观最容易变成负担的五个信号

  • 外观变成上帝对象：一个 Facade 里塞了 30 个方法 → 按业务能力拆成几个小外观（OrderFacade / PayFacade）。
  • 外观里写业务规则：出现 if vip { discount = 0.8 } → 那是领域逻辑，应该留在领域服务，外观只做编排。
  • 返回子系统的类型：Place() (*ship.Order, error) → 泄漏了内部；外观应返回自己的 DTO。
  • 错误被吞掉：外观把所有错误统一成 errors.New(‘失败’) → 调用方无法区分「库存不足」和「支付超时」。
  • 测试只能端到端：外观持有具体结构体而非接口 → 依赖写成接口，测试才能替换子系统。

一句话自检：外观里只应有编排、事务边界、统一错误处理；出现计算、判断、格式化就是放错地方了。

第四层 · 外观与分层架构的边界

外观和一个普通 util 函数有什么区别？

util 是无状态的工具（格式化、加解密），不持有依赖，也不编排多个系统；外观持有子系统引用并定义流程。判断信号：需要注入依赖、需要事务边界，就是外观而不是 util。

API Gateway 是外观吗？

是外观在架构层的形态：它把内部多个服务的调用收成一个端点，并统一处理鉴权、限流、日志。区别在于 Gateway 是独立进程、跨网络，外观通常是进程内的一个对象。

什么时候应该拆掉外观？

当外观的方法开始出现大量可选参数（Place(ctx, u, items, withCoupon, skipNotify)）时，说明调用方的需求已经分化，应该按场景提供多个明确的方法，而不是一个包打天下。

核心速览

一句话给一个复杂子系统套一个简单入口，调用方只见一个方法
解决什么子系统类多、调用顺序有讲究，调用方每次都要学一遍
和适配器区别外观是简化（新接口更简单）；适配器是转换（接口不匹配）
和中介者区别外观是单向封装；中介者是双向协调多个对象之间的交互
外观模式：调用方 -> 外观 -> 子系统，复杂度被挡在外观后面

一、它长什么样

// 不用外观：调用方要自己编排 5 步，还得知道顺序 cfg := loadConfig() conn := newDB(cfg) tx, _ := conn.Begin() checkInventory(tx, sku) deductStock(tx, sku, n) tx.Commit() notify(sku) // 用外观：一行搞定，顺序和细节被封在里面 orderService.PlaceOrder(ctx, sku, n) // 外观内部 func (s *OrderService) PlaceOrder(ctx context.Context, sku string, n int) error { // 内部仍然是那 5 步，但只有这里知道顺序 }
外观不是「上帝类」

外观的职责是编排，不是把所有逻辑都搬进来。如果外观类开始出现业务判断、状态管理、复杂分支，说明它已经越界了，应该把逻辑下沉到子系统。

二、三个容易混淆的结构型模式

模式意图接口变化典型例子
外观 Facade简化复杂子系统的使用提供一个更简单的新接口下单服务封装库存/支付/通知
适配器 Adapter让不兼容的接口能一起工作把一个接口转成另一个把第三方 SDK 转成自家接口
代理 Proxy控制对对象的访问接口不变，增加控制懒加载、权限校验、RPC 桩
中介者 Mediator减少对象间互相引用对象之间改为通过中介者通信UI 组件联动、聊天室

一句话区分：外观是简化、适配器是转换、代理是控制、中介者是协调。四个都引入了「中间一层」，但目的完全不同。

三、什么时候该引入外观

子系统调用超过 3 步且顺序不能错
多个调用方重复同样的编排复制粘贴就是信号
子系统要被替换外观隔离变化，调用方不受影响
分层架构的层间入口上层只依赖下层的 Service 外观
第三方 SDK 太啰嗦包一层让调用方少写样板代码

场景隐藏了什么收益

五、深入自检

外观会不会变成万能类（God Object）？

会，这是最常见的退化。判断标准：如果外观里有大量业务规则、或者修改业务要改外观，就说明它承担了不该承担的职责。此时应该拆分外观或下沉逻辑。

外观和「服务层」是一回事吗？

思想完全一致。三层架构里的 Service 层本质上就是外观：它把 DAO、缓存、消息、外部调用编排起来，对 Controller 暴露简单接口。

需要为外观写接口吗？

如果希望可替换、可 mock，就写。Go 里常见做法是定义接口 + 一个默认实现，这样测试时可以换成假的。但不要为所有外观都强行抽象，简单场景直接用结构体。

外观能降低耦合吗？

降低的是调用方对子系统的耦合——调用方只依赖外观。但外观自己对子系统的耦合仍然存在。如果子系统接口变了，外观也要改，只是影响范围被限制在一处。

和门面 API / BFF 有关系吗？

BFF（Backend For Frontend）就是外观模式在架构层面的应用：为某个前端定制一个聚合接口，隐藏后端多个微服务的调用细节。

记住一句简化入口，隐藏编排
职责边界只编排，不做业务判断
区分口诀外观简化 / 适配转换 / 代理控制
架构对应Service 层、BFF
