向量检索是什么

从“找一样的”到“找像的”：稠密/稀疏向量、最近邻本质、为什么数据库做不了语义检索，以及完整链路。

一句话定义

向量检索（Vector Search / Similarity Search）：把文字、图片、音频等内容编码成一串浮点数（向量 / embedding），然后通过"计算向量之间的距离/相似度"来找回语义上最接近的内容，而不是靠关键词精确匹配。

它解决的核心问题是："和这条内容意思最像的东西是什么？"——传统数据库只会回答"等于/包含某个字符串"，答不了"意思相近"。

稠密向量 vs 稀疏向量

做向量检索前先要分清两种向量，它们是不同的技术路线：

维度稠密向量（Dense）稀疏向量（Sparse）
来源神经网络模型（BGE / OpenAI / BERT）编码词频统计 / 词项权重（BM25、SPLADE）
维度固定 384 / 768 / 1536 维，每维都有值词汇表大小（几万~几十万），绝大多数是 0
可解释性低，每个维度无明确含义高，每个非零维度对应一个词项
擅长语义相似、同义改写、跨语言精确关键词、专有名词、罕见词
典型用法语义搜索、RAG 召回关键词检索；或做"混合检索"的另一路

检索的本质：最近邻问题

把每条内容变成向量后，检索就退化成一个数学问题：给定查询向量 q，在 N 个候选向量里，找距离 q 最近的 k 个。这就是 k 近邻（k-NN）。

目标：argmin_{x in 候选集} distance(q, x) ，取 top-k

"距离"越小 = 越相似。常见距离/相似度见本系列《相似度度量》一篇。理论上 k-NN 可以暴力扫描所有候选求距离，但当 N 达到百万、亿级，且向量维度高达 768/1536 时，暴力扫描慢到不可接受——这正是后面 ANN（近似最近邻）要解决的。

为什么传统数据库 / LIKE 不行

  • SQL 只能做精确/范围匹配：WHERE title LIKE '%苹果%' 找的是包含"苹果"两字的行，找不到"iPhone""水果公司"这种语义相关但不含该词的内容。
  • B+ 树索引对高维向量失效：B+ 树擅长一维有序数据；向量是几百维，"最近"无法用任何一维排序来表达，多维空间没有天然的全序。
  • 语义鸿沟：传统检索靠人类写好的关键词，模型检索靠向量空间里的几何邻近，"意思接近"在关键词体系里没有对应操作。
一句话：传统数据库擅长"找一样的"，向量检索擅长"找像的"。两者互补，不是替代。

向量检索的典型流程

图 2：向量检索五步——编码 → 建索引 → 检索 → （可选）重排

① 把原始内容用 Embedding 模型编码成向量；② 离线把所有向量建好索引（一次性成本）；③ 查询时把 query 也编码，用索引快速找 top-k；④ 通常再接一个 Cross-Encoder 重排提升精度。RAG 就是这套流程 + 把召回文本喂给 LLM。

应用场景

  • 语义搜索 / RAG 召回：知识库问答最典型，按意思找相关段落。
  • 推荐系统：用户向量 × 物品向量，找最像的 item。
  • 去重 / 聚类：相似文档合并、训练数据清洗。
  • 以图搜图 / 多模态：图片、音频编码后同样进向量空间。
  • 异常检测：离所有正常样本都远的向量即为异常。
记住：任何"找相似"的需求，本质上都是向量检索。它是大模型时代检索系统的底座。

一次检索的完整链路

同一个模型把问题也变成向量④ 近邻搜索在索引里找距离最近的前 k 个⑤ 后处理过滤、去重、重排，再交给大模型
检索链路：注意第③步必须用与入库相同的模型，否则空间不一致

度量公式含义对什么敏感适用
余弦相似度只看方向，不看长度向量长度不敏感文本语义（最常见）
内积 Dot方向 + 长度长度敏感已归一化的向量、推荐召回

从暴力到近似

方式做法时间复杂度优点缺点
暴力 Flat和每一条都比一遍O(N·d)100% 召回，结果精确数据量大时不可用
IVF 倒排先聚类，只搜最近的几个簇O(nprobe·N/C)简单、内存省边界点易漏，需调 nprobe
HNSW 图建多层近邻图，贪心跳转O(logN)速度快、召回高内存大、构建慢
PQ 量化把向量压缩成码本大幅省内存内存降一个量级有损，召回下降

调参的本质：三个旋钮

① 召回率 Recall找到的 k 个里，有多少是真正的最近邻。提高召回通常要付出延迟代价。
② 延迟 Latency单次查询耗时。加大搜索范围会变慢，减小会漏。
③ 内存占用索引大小。量化能省内存但损失精度，图索引快但吃内存。

典型参数怎么调

# HNSW 类索引 efConstruction = 200 # 建索引时看多少候选：越大图越准，构建越慢 M = 16 # 每个节点连多少边：越大召回越高，内存越大 efSearch = 64 # 查询时看多少候选：<b>最常调的就是它</b> # efSearch 必须 >= k，通常取 k 的 2~10 倍 # IVF 类索引 nlist = 1024 # 聚成多少簇，一般取 sqrt(N) 附近 nprobe = 16 # 查几个簇：越大召回越高越慢 # 经验：先用 Flat 在小样本上算出「标准答案」， # 再调 ANN 参数看召回率能追到多少（如 95%、99%）

深入自检

向量检索能完全替代关键词检索吗？

不能。向量擅长语义相近，但对精确匹配很弱：型号、人名、错误码、序列号这类「必须一字不差」的查询，关键词/BM25 更可靠。生产上通常是混合检索（向量 + 关键词）再融合。

为什么换了 Embedding 模型就必须重建索引？

因为不同模型产出的向量处在不同的向量空间，距离没有可比性。旧索引与新查询向量混用，结果会毫无意义。

k 取多少合适？

取决于下游：给大模型做 RAG 通常先取 20~50 再重排到 3~5 条；纯推荐召回可以取几百。关键是宁可多召回再精排，因为重排比少召回便宜。

为什么 ANN 检索的「召回率」很难到 100%？

因为近似算法本质是在用少量比较换取速度，必然有漏网。可以调参逼近（如 99%+），但代价是延迟上升。工程上通常接受 95%~99% 的召回。

维度越高越好吗？

不是。高维度能承载更多信息，但会带来维度灾难（距离区分度下降）以及更大的存储与计算开销。很多模型提供 768/1024/1536 等档位，实际用最短满足需求的维度往往性价比最高。
