🍃 MongoDB 概览

文档模型、BSON、灵活 schema 与它适合的场景边界

一句话定位

MongoDB 是一个面向文档（document-oriented）的分布式数据库：数据以「文档」为单位存储，文档长得像 JSON，实际落盘是 BSON。它不像关系库那样要求先定义好表结构，同一个集合里的两条文档可以有完全不同的字段。这种自由度让它在字段多变、迭代快、读多写少的业务里非常顺手，但也意味着「约束」这件事被推给了应用层。

数据单位Document（文档）≈ 一条记录，BSON 存储，最大 16MB
组织方式Database → Collection（集合）→ Document；集合≈表，但不强制 schema
查询语言MQL（MongoDB Query Language）+ 聚合管道 Aggregation Pipeline
事务支持4.0 起多文档事务（副本集），4.2 起分片集群事务

架构长什么样

三条必须记住的设计哲学

① 数据怎么用，就怎么存

关系库先画 ER 图再拆表；MongoDB 反过来——先看查询长什么样。一起被读出来的数据，就应该放在一起（嵌入）。

  • 一次查询能拿全 → 嵌入（embed）
  • 独立访问、体积大、增长无上限 → 引用（reference）

② 灵活 ≠ 随便

没有 schema 不等于不要 schema。生产上用 JSON Schema 校验器（$jsonSchema）锁住关键字段，避免脏数据悄悄混进来。

③ 事务是可选武器，不是默认姿势

单文档写本身就是原子的（atomic），能用一个文档解决就别开事务。跨文档事务代价高，别当关系库用。

④ _id 就是聚簇索引

WiredTiger 按 _id 建索引，物理顺序≈_id 顺序。用随机 _id 会让写入散落各处；有序 _id（ObjectId）写入更友好。

上手：最常用的几条语句

// 插入一条文档
db.users.insertOne({
  name: "Alice", age: 30,
  tags: ["vip", "beta"],
  addr: { city: "Hangzhou", zip: "310000" }
});

// 查询 + 投影（只返回 name/age，_id 不返回）
db.users.find({ age: { $gte: 18 } }, { name: 1, age: 1, _id: 0 });

// 更新：原子地自增
db.users.updateOne({ name: "Alice" }, { $inc: { loginCount: 1 } });

// 数组追加
db.users.updateOne({ name: "Alice" }, { $push: { tags: "new" } });

// 聚合：按城市分组统计平均年龄
db.users.aggregate([
  { $match: { age: { $gte: 18 } } },
  { $group: { _id: "$addr.city", avgAge: { $avg: "$age" }, cnt: { $sum: 1 } } },
  { $sort: { cnt: -1 } },
  { $limit: 10 }
]);

什么时候该用 / 不该用

维度适合不适合
数据结构字段经常变、半结构化、嵌套深严格固定、强约束、需大量外键
查询形态按主键/索引的点查、单集合聚合复杂多表 JOIN、即席分析型 OLAP
一致性单文档原子、最终一致可接受跨行强事务、金融级对账
数据量水平分片扩展到 TB~PB单机小数据量（用关系库更省事）
⚠️ 常见误用：把 MongoDB 当「不用建表的 MySQL」，大量跨集合 $lookup 拼数据。一旦查询需要频繁 join，说明数据模型设计反了——应该回到「按查询形态嵌入」重新建模。

版本里程碑

  • 3.x：WiredTiger 成为默认存储引擎，文档级锁取代库级锁
  • 4.0：多文档 ACID 事务（副本集）
  • 4.2：分片集群事务、通配符索引、字段级加密
  • 4.4：Hedged Reads、可恢复的 shard 迁移
  • 5.0：时序集合（Time Series Collection）、版本化 API
  • 6.0：可查询加密（Queryable Encryption）、时序分片
  • 7.0：分片元数据一致性改进、复合 hashed 索引

    • 🎯 常见问法与答题要点

    Q：MongoDB 的文档最大能多大？超了怎么办？

    A：单文档上限 16MB。超过会写失败。解决思路有三条：①把数组拆成独立集合并用引用；②用 GridFS 存大文件（把文件切成 255KB 的 chunk）；③重新审视模型——一条 16MB 的文档通常说明你把「一对多」错误地全塞进了一侧。

    Q：MongoDB 支持 JOIN 吗？和 SQL 的 JOIN 有什么区别？

    A：支持，用 $lookup。但语义更像「每个主文档发一次子查询」，代价远高于 SQL 的优化器 JOIN，而且被 lookup 的集合不能有分片键限制。MongoDB 官方建议：能用嵌入就用嵌入，只在「多方数据独立访问 / 体量大 / 增长无上限」时才用引用 + $lookup。

    Q：WiredTiger 是什么？为什么它重要？

    A：它是 MongoDB 3.2 起的默认存储引擎，取代了 MMAPv1。带来三个关键改变：文档级并发控制（不再整个库加锁）、MVCC 快照读（读写不互相阻塞）、压缩（snappy/zlib/zstd，通常能省 50%~80% 空间）。它还负责每 60 秒做一次 checkpoint，配合 journal 保证崩溃恢复。

    Q：ObjectId 里藏着哪些信息？有什么用？

    A：12 字节 = 4 字节时间戳（秒）+ 5 字节随机值 + 3 字节自增计数器。因为前 4 字节是时间，所以 ObjectId 大致按创建时间递增，一方面让 WiredTiger 的 B-tree 写入更集中，另一方面可直接用 ObjectId("...").getTimestamp() 反推创建时间，省一个 createdAt 字段。

    Q：为什么说 MongoDB 单文档写是原子的？

    A：WiredTiger 对单个文档的修改在存储引擎层就是一次原子的 MVCC 更新，不存在「写了一半」的中间态可见。这让很多原本需要事务的场景可以直接用文档解决——比如把库存、购物车、计数器放在同一文档内用 $inc 更新就天然安全。
