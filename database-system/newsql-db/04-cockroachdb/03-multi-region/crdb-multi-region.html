①先定生存目标，再定表布局

多区域部署的核心问题是：当整个区域挂掉时，你要的是「数据不丢」还是「服务不停」。 这个选择决定了副本怎么放，也决定了写入延迟。

生存目标含义代价
Zone（机房级）存活容忍单个可用区故障副本跨机房，写延迟 = 同城往返
Region（地域级）存活容忍整个城市/地域故障副本跨城，写延迟 = 跨城往返（几十毫秒级）
这是无法绕开的物理约束。「跨地域强一致」意味着每次写入都要等跨城的多数派确认， 写入延迟不可能低于跨城 RTT。想低延迟就只能放松一致性（异步复制）或放松生存目标。 先接受这个权衡，再谈优化。

②三种表类型的取舍

REGIONAL BY TABLE（默认）

数据整体放在一个主区域，其他区域访问要跨区。 写入最快、本地读快、跨区读慢。适合「绝大多数请求来自同一区域」的业务。

REGIONAL BY ROW

按行的区域列自动决定该行放在哪个区域。 本地读写都快，跨行事务慢。适合「用户数据与其所在地区强绑定」的场景（数据合规、本地化）。

GLOBAL

所有区域都有完整可读副本，本地读极快，但写入需要全区域一致，写最慢。 适合读多写少的参考数据（配置、字典、价格表）。

-- 按行分区：用 region 列决定行的归属
ALTER TABLE users SET LOCALITY REGIONAL BY ROW;

-- 全局表：读多写少的字典表
ALTER TABLE configs SET LOCALITY GLOBAL;

-- 读历史数据用 follower reads，避免跨区访问 leaseholder
SELECT * FROM orders AS OF SYSTEM TIME INTERVAL '10s';
各版本语法与可用表类型有差异（例如 GLOBAL 表的引入时间、 REGIONAL BY ROW 对主键的要求）。请以所用版本的官方文档为准，不要凭记忆写 DDL。

③延迟从哪里来

副本放得越远，写入越慢——这是物理规律，不是配置问题
优化顺序： ① 确认副本位置是否符合你真正需要的生存目标（很多时候副本放得比需要更远，白白付延迟）； ② 让计算靠近数据（应用部署到主区域，或用 REGIONAL BY ROW）； ③ 读多写少的场景用 GLOBAL 表 + Follower Reads； ④ 批量写入合并事务，摊掉每事务的固定 RTT。

④上线前要确认的事

  1. 时钟偏差监控：节点时钟漂移会直接影响 HLC 的正确性边界，必须有告警。
  2. 副本放置可视化：能随时回答「这张表的副本现在在哪几个区域」。
  3. 故障演练：真的拔掉一个 zone / region，验证生存目标是否达成、恢复耗时多久。
  4. 应用层重试：跨区部署下冲突概率更高，重试逻辑必须完整（见「数据分布」篇）。
  5. 跨区流量成本：云厂商的跨地域流量是收费的，副本同步会持续产生费用。
Q：能不能既跨地域容灾又低延迟写入？
A：不能同时满足。要么接受跨城写入延迟（同步复制 + 强一致）， 要么用异步复制换低延迟（主区写、备区异步追，故障时可能丢少量数据）。 这是一致性、可用性、延迟三者取二的经典权衡，没有银弹。
Q：多区域下自增主键还能用吗？
A：能用但不推荐——它同时带来写热点（尾部 Range）和跨区协调开销。 建议用随机/哈希前缀的 UUID 类主键，把写入打散。

一、三种表类型怎么选

类型数据放置读写适合
REGIONAL BY ROW按行的 region 列自动把该行放到对应地域本地读极快本地写快用户数据按地域归属（最常用）
REGIONAL BY TABLE整张表固定在某个地域该地域极快，其他地域慢该地域快只在单一地域使用的数据
GLOBAL所有地域都有完整副本所有地域都能本地读慢（要跨地域共识）小的、读多写少的参考数据
最实用的判断法

问两个问题：① 这一行数据主要由哪个地域的用户写？② 主要由哪个地域的用户读？如果答案一致且能按某个列（如 region、tenant_id）区分，就用 REGIONAL BY ROW；如果全地域都要低延迟读但很少写，用 GLOBAL。

二、关键 SQL

-- 1) 给集群和节点打地域标签 ALTER DATABASE app SET PRIMARY REGION "us-east-1"; ALTER DATABASE app ADD REGION "eu-west-1"; ALTER DATABASE app ADD REGION "ap-southeast-1"; -- 2) 按行分区：以 region 列为依据自动摆放 ALTER TABLE users SET LOCALITY REGIONAL BY ROW; -- 要求表里有 crdb_region 列（可自动生成，也可指定已有列） ALTER TABLE users SET LOCALITY REGIONAL BY ROW AS "region"; -- 3) 全地域低延迟读 ALTER TABLE products SET LOCALITY GLOBAL; -- 4) 查看数据实际分布 SHOW RANGES FROM TABLE users; SELECT * FROM crdb_internal.ranges WHERE table_name = 'users';

三、延迟是怎么降下来的

操作普通部署（leader 可能在对岸）多地域优化后
本地读可能跨洲 100~200ms1~5ms（读本地副本）
本地写跨洲共识 100~200ms本地多数派 5~20ms
跨地域写同上仍受跨洲共识限制，100ms+
GLOBAL 表读跨洲本地读，但可能是 stale read
GLOBAL 表写跨洲更慢（要所有地域参与）

注意 GLOBAL 表的读有一个重要细节：它默认走陈旧读（stale read），读取的是本地副本的最新状态，可能落后于全局最新值。需要强一致时要显式指定读取方式，代价是延迟。

四、生存目标与容灾

REGION 级存活能容忍整个地域失效，副本要分布在 3+ 地域
ZONE 级存活只容忍单可用区失效，副本在同一地域多区
放置策略用 ALTER ... CONFIGURE ZONE 指定副本数量与约束
权衡越高的存活目标 = 越多的跨地域共识 = 越高的写延迟

五、深入自检

为什么写延迟降不下来？

因为写入必须达成共识，共识需要多数派确认。副本跨 3 个地域时，最快也要等两个地域响应，物理距离决定的光速延迟无法绕过。多地域优化主要优化的是读和本地写入方。

REGIONAL BY ROW 的分区键能改吗？

可以，但改分区键意味着数据要重新摆放，代价很大。因此建表时就要想清楚：通常用 tenant_id 或 region，而不是用户 ID（因为同一租户的数据要在一起）。

跨地域事务怎么处理？

尽量避免。如果确实需要，CRDB 会协调多个 range 的 leader，延迟是各参与地域中最慢的那个。设计上应尽量让事务局限在单个地域内。

GLOBAL 表和缓存有什么区别？

GLOBAL 表仍是数据库的一部分，写入后自动同步、可参与 SQL 查询与事务；缓存需要自己维护失效逻辑。代价是 GLOBAL 表的写入很慢，只适合配置、字典这类数据。

怎么验证多地域真的生效了？

用 EXPLAIN 看执行计划里是否有跨地域的网络开销；用 SHOW RANGES 看副本与 leader 是否落在预期地域；再用各地域的客户端实测读延迟对比。
