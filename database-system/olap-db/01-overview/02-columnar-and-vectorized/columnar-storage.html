列式存储与向量化执行

压缩编码、SIMD、批量处理——OLAP 引擎"快一个数量级"的三块基石

① 为什么快 ② 压缩编码 ③ 向量化执行 ④ SIMD ⑤ 延迟物化 ⑥ 常见疑问
一句话总结：列存解决「读得少」，压缩解决「读得快」，向量化解决「算得快」。 三者叠加，才让 ClickHouse / Doris 这类引擎能在单机上秒级扫描几十亿行。

01三层加速，各解决一个问题

🎯 列存：读得少

只读取查询真正用到的列。20 列的宽表只查 3 列， 磁盘 IO 直接降到 1/6 左右，且是连续 IO 而非随机 IO。

🗜️ 压缩：传得快

同列数据同质性强，压缩比常达 5～10 倍。 更关键的是很多聚合可以在压缩态直接做，连解压都省了。

⚡ 向量化：算得快

一次处理一批（Block）而非一行，消除逐行函数调用与分支开销， 提高 CPU cache 命中，并能启用 SIMD 单指令多数据。

图 1：逐行解释执行 vs 批量向量化——开销相差可达 10 倍以上

02主流列存压缩编码

列存把同字段值放一起，才让下面这些编码有了用武之地。选型通常靠自动探测：引擎先采样几万行试各种编码，选压缩比最高的那个。

编码原理最适数据典型压缩比
字典编码
Dictionary		 把去重后的值建成字典，原列存成整数下标 低基数字符串：城市、状态、品类、日志级别 10～100×
RLE 游程
Run-Length		 连续相同值存成「值 + 重复次数」 已排序的列、稀疏的枚举列 极高（看重复度）
Delta 差分 存相邻值的差而非原值 单调递增时间戳、自增 ID 5～20×
位图 Bitmap 每个取值一个 bitmap，标记哪些行命中 极低基数 + 过滤条件（WHERE city='BJ'） 随基数变化
LZ4 / ZSTD 通用块压缩，压在编码之后 兜底通用场景 2～4×
图 2：字典编码同时省空间、加速过滤与聚合
压缩态直接计算：很多引擎（如 ClickHouse）能在字典编码上直接做 GROUP BY city—— 只在整数下标上分组，最后才回字典还原字符串。RLE 上做 COUNT/SUM 也只需「值 × 次数」，不用展开。

03向量化执行模型

经典的做法是 Volcano / Iterator 模型：每个算子实现 next()，父算子递归调用子算子取一行。 它灵活但每行都要走一次虚函数、一次类型判断，解释开销常常超过真正计算的开销。

向量化模型改成：每个算子一次处理一整块（Block / Batch，典型 8192 行）， 块内数据是按列组织的连续数组。

// 逐行：每行 1 次函数调用 + 类型分支
for (row = 0; row < N; row++) {
    val = get_value(row);        // 虚函数
    if (val > threshold) sum += val;   // 每次都分支判断
}

// 向量化：一批一次调用，循环体极简
for (i = 0; i < block_size; i++) {
    sum += values[i];            // 连续内存，无分支
}

为什么快这么多

  • 摊销解释开销：一次调用处理 8192 行，虚函数调用成本除以 8192。
  • CPU Cache 友好：同列数据在内存连续，预取命中率高；逐行模型每行要跳到不同列的偏移。
  • 分支预测友好：循环体内没有 if，CPU 流水线不会被打断。
  • 编译期特化：块的类型在进入循环前已确定，可对 Int32/Float64 分别生成专用代码。
  • 可向量化：编译器更容易自动向量化，或直接手写 SIMD intrinsic。

04SIMD：一条指令算多个数据

SIMD（Single Instruction Multiple Data，单指令多数据）是 CPU 提供的并行能力： 一个 256 位寄存器能同时装 8 个 int32 或 4 个 int64，一条加法指令同时完成 8 次加法。

图 3：SIMD 用更宽的寄存器把 4～8 个数据的同一运算合并成一条指令

现代引擎大量使用 SIMD：过滤（生成掩码）、聚合求和、字符串比较、哈希计算都有 SIMD 实现。 这也是 ClickHouse 名字的由来之一——快到"点击即出结果"。

SIMD 的前提是数据连续。如果数据是按行存放（a0 b0 c0 a1 b1 c1…）， 就没有连续的同列数组可喂给 SIMD 寄存器。这从硬件层面再次说明了为什么分析场景必须列存。

05延迟物化 Late Materialization

列存里一行数据分散在多个列文件中。查询 SELECT name FROM t WHERE amount > 100 有两种执行顺序：

策略做法代价
提前物化
Early		 先把所有条件列 + 输出列拼成完整行，再过滤 拼了大量最终会被过滤掉的行
延迟物化
Late ✅		 只扫描 amount 列，得到命中的行号集合，再用行号去 name 列取少量值 只读取真正需要的那些行的其余列

选择性越高（命中的行越少），延迟物化省下的 IO 越多。这是列存引擎优化器的标准武器。

06常见疑问

Q：列存这么好，为什么 OLTP 数据库不用？
A：列存的写入是致命短板——插入一行要拆成 N 次写（每列一次）， 而 OLTP 的 INSERT/UPDATE 需要一次 IO 落整行。 另外点查单行时，列存要去 N 个列文件各取一点，反而比行存慢。 列存本质是用写入性能换读取性能，这个交易只在分析场景划算。
Q：压缩不会拖慢查询吗？
A：看似要"先解压再算"，实际上磁盘 IO 的节省远大于解压的 CPU 开销—— 而分析的瓶颈通常在 IO。更进一步，字典/RLE 编码支持压缩态直接计算，连解压都省了。
Q：Parquet/ORC 也是列存，和 ClickHouse 的列存一样吗？
A：编码思想相通（都支持字典、RLE、Delta），但定位不同： Parquet/ORC 是文件格式，面向 HDFS/对象存储的离线批处理，不可变、append-only； ClickHouse/Doris 的存储引擎面向在线查询，有主键索引、分区、后台合并（LSM 风格），支持持续写入与实时查询。
