语音翻译与同声传译

级联 / 语音到文本 / 语音到语音三条路线的取舍、同传「等上下文还是先输出」的核心矛盾与增量修正方案，以及术语表、数字校验、说话人分离等实践要点。

三种实现方式

① 级联三段
ASR → 机器翻译 → TTS。

优点：每段可独立优化、中间有文本可编辑审核、可用现成组件拼。
缺点：延迟累加，错误逐级放大。
② 语音到文本翻译
语音直接翻译成另一种语言的文本，再 TTS。

优点：省掉一次转写，减少错误累积，延迟更低。
缺点：中间文本不可控，纠错困难。
③ 语音到语音
直接输出目标语言的语音。

优点：延迟最低，可保留原说话人的音色与情绪。
缺点：完全没有中间文本，无法校对、无法审计。
选择的关键不是"哪个更先进"，而是你的场景能不能接受没有中间文本。 会议字幕、涉外客服需要留痕 → 必须保留文本；同声传译耳机追求实时 → 可以走端到端。

同传的核心矛盾：延迟 vs 质量

翻译需要上下文才能消歧——例如一个代词指代谁、一个动词的时态， 往往要等后面的词出现才能确定。于是产生了同传最本质的取舍。

工程上的解法是「增量输出 + 允许回改」： 先输出一个高置信度的翻译，后续上下文到来时如果发现前面译错了， 再输出一个修正（字幕场景可以刷新，语音场景可以补一句"更正一下"）。 这比"等整句说完再翻译"体验好得多。

实践要点

  • 术语表是刚需：垂直领域（医疗、法律、产品名称）的专有名词必须能强制指定译法， 否则模型会自由发挥。这在任何生产级翻译系统里都是第一优先级。
  • 数字与单位要专门校验：数量级错误（千 vs 百万）、日期格式（日/月顺序）、货币单位， 是翻译事故的高发区，且往往不会报错。
  • 标点与分段影响听感：同传场景下过长的句子会让听众疲劳， 需要在输出侧做句子切分（与「文本归一化」那篇的问题同源）。
  • 说话人分离：多人会议要先做 diarization 区分谁在说，否则翻译会把两个人的话混在一起。
  • 语言检测与代码混用：中英夹杂是很常见的输入，模型要能处理而不是强行归一。

与实时语音对话的关系

语音翻译可以看作实时语音对话的一个特例：把中间的 LLM 换成翻译模型。 所以「实时语音对话」那篇讲的流式流水线、端点检测、打断机制、AEC 回声消除在这里全部适用。

额外的复杂度在于"两种语言混在同一条音频流里"。 用户说中文、系统播英文，此时 VAD 与 AEC 要能区分「用户的人声」和「系统播放的英文语音」—— 这比单语言场景的回声消除更难，需要更强的参考信号对齐与说话人区分能力。

两条路线的本质差异

语音翻译（Speech Translation, ST）有两种做法：级联（先 ASR 成源语文本，再机器翻译）和端到端（语音直接到译文）。级联的优点是模块可独立优化、能输出双语字幕、可复用成熟组件；缺点是 ASR 的错误会原封不动传给翻译。端到端避免了误差传播，但需要稀缺的「语音-译文」平行语料。

实务建议：绝大多数业务先用级联（ASR + 强翻译/LLM），因为可调试、可加热词、可出双语字幕；只有当级联的错误传播成为瓶颈、且你能拿到足量语音-译文语料时，才考虑端到端。

提升质量的实操手段

① 在 ASR 端就把错误掐掉

  • 热词/术语表：人名、地名、产品名优先正确识别。
  • VAD 参数：避免吞字头字尾，宁可多切一点。
  • 领域语言模型 rescoring：显著提升专有名词。
  • 标点与断句：直接影响翻译的句法正确。

② 在翻译端做领域控制

  • 术语表/词典约束：关键术语必须按指定译法。
  • 提供上下文：前文、说话人、场景能消解大量歧义。
  • 固定风格与语气：口语/书面、正式/随意要明确。
  • 要求保留数字、单位、专有名词原文。

③ 流式与延迟

  • 同传场景要边听边译，需权衡「等更长的上下文」与「更低延迟」。
  • 常见策略：短句即时输出，遇到歧义词稍等。
  • 允许「修订式输出」：先出初译，后续可局部修正。

④ 评测怎么做

  • BLEU 是基础，但要注意分词与大小写统一。
  • 关键术语准确率单独统计，比 BLEU 更能反映业务体验。
  • 人工评测要按「忠实度 + 流畅度」两个维度分别打分。
  • 按场景分层：安静/噪声、独白/对话、口音。

深入自检

端到端一定比级联好吗？

不一定。端到端避免了误差传播，但受限于训练数据规模与质量，在多数语言对上仍不及「强 ASR + 强 MT」级联的效果。尤其在低资源语言对上，级联可以分别利用大量语音数据与大量文本平行数据，优势明显。

为什么语音-译文语料这么稀缺？

因为它需要「同一段语音」配「另一种语言的译文」，且要时间对齐。人工翻译成本高，而用 ASR+MT 自动构造又会把级联的错误带进去。常见做法是数据增强（语音合成、伪标签）与多任务预训练（ASR/MT 辅助任务）。

LLM 时代语音翻译有什么新做法？

常见是「ASR → LLM 翻译」的两段式：ASR 出错时 LLM 有一定容错与上下文纠错能力，且改 prompt 就能控风格、加术语。更进一步的方案是把语音编码器直接接入 LLM（语音大模型），实现理解语音的端到端，但成本与工程复杂度更高。

同声传译的延迟怎么压？

核心是「增量翻译」：不等整句结束，按语义块输出。工程上要结合 ASR 的流式输出、句末检测、以及允许后续修订的展示方式。延迟越低，因缺少上下文导致的误译越多，需要按场景取平衡。

翻译结果不错但用户仍不满意，可能是什么原因？

常见三类：① 术语不统一（同一产品名译法多变）；② 语气与场景不符（口语被译成书面语）；③ 缺失上下文导致的代词/指代错误。这三类都不是 BLEU 能反映的，需要业务侧的规则与人工反馈闭环。

怎么保证数字和专有名词不出错？

三层防御：① ASR 端加热词；② 翻译 prompt 明确要求保留数字与专有名词原文；③ 后处理做一致性校验（数字是否前后一致、术语表是否被遵守）。关键字段要有断言与告警。
