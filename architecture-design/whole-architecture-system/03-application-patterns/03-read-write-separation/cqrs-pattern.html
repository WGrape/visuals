什么时候适用？

判断信号：写入规则与读取视图的模型需求差异明显，值得分别设计。

  • 写订单重规则、查订单列表重聚合
  • 读流量远高于写流量且要独立扩展
  • 需要多个专用查询投影

和相近方案怎么区分？

相近方案选择边界
数据库读写分离读写分离可只是主从副本路由；CQRS 把命令模型与查询模型的职责分开。
事件溯源事件溯源用事件记录事实历史；CQRS 不要求以事件作为权威存储。

最小伪代码

function createOrder(cmd):
  transaction:
    order = Order.create(cmd.items)
    writeStore.save(order)
    outbox.insert(OrderCreated(order.id))
// 提交后发布器投递 outbox，消费者幂等更新读模型
on OrderCreated(event):
  readStore.upsert(project(event.orderId))

边界：异步投影有延迟；需要定义读己之写体验、重建投影和重复事件处理。简单 CRUD 未必需要 CQRS。

CQRS 读写分家 Command Query Responsibility Segregation

写请求与读请求走独立路径；读侧可由写侧异步更新，也可共用存储

传统 CRUD 用同一模型既读又写，复杂查询会把写模型撑得很难看。CQRS 把『改数据(Command)』和『查数据(Query)』拆开：写侧聚焦领域规则，读侧直接投喂前端要的扁平 DTO（可由写侧事件异步同步）。

何时值得用

  • 读写负载差异巨大（读多写少）。
  • 查询模型远比写入模型复杂（多表 join、聚合）。
  • 需要与事件溯源配合。

代价

  • 最终一致性：读模型滞后于写。
  • 两套模型、两套存储，复杂度翻倍。
  • 小系统用了是过度设计。

面试高频问答

Q：CQRS 一定要配合事件总线吗？
A：不一定。简单场景可让写侧直接更新读库（同步）；但 CQRS 真正的威力在配合事件/消息做异步投影，实现读写物理隔离。
Q：CQRS 和读写分离(主从)一样吗？
A：不一样。读写分离是『同一数据的副本分担读压力』；CQRS 是『读模型和写模型结构都不同』，读侧可能是为查询量身定制的视图。

CQRS：把「读」和「写」当成两个系统

CQRS（Command Query Responsibility Segregation，命令查询职责分离）的核心主张很简单：写操作和读操作用不同的模型。传统 CRUD 用一个模型既承载写入校验又承载各种查询，结果两边互相迁就——写入要保证一致性所以模型复杂，查询要灵活所以又要加各种冗余字段，最后谁都不好用。

CRUD 单一模型 vs CQRS 读写分离模型

Command 与 Query 的区别

维度Command（命令）Query（查询）
语义改变系统状态（有副作用）只返回数据（无副作用）
命名动词短语：CreateOrder、CancelOrder、ChangeAddress名词短语：OrderById、OrdersByCustomer
返回值通常只返回成功/失败或 ID返回 DTO / 视图模型，可任意裁剪组合
模型形态充血领域模型，含业务规则与不变量校验扁平的读模型（宽表/DTO），为展示而生
一致性要求强一致，通常在同一事务内完成可容忍最终一致（读到稍旧的数据）
存储规范化（3NF），重写入正确性反范式（宽表/冗余），重查询效率
校验重点业务规则：状态是否允许流转、余额是否充足几乎无校验，只有分页与权限

关键认知：同一个「订单」概念，在写侧是一个含状态机与规则的对象，在读侧可能是一条包含用户昵称、商品名、地址快照的扁平记录。它们长得完全不同，这恰恰是 CQRS 想要的效果——各自为各自的目的优化。

同步机制：读模型从哪来

① 同库同步（最简单）

写操作完成后在同一个事务/同一个请求里更新读表。

  • 无延迟、强一致；实现最简单
  • 只是「模型分离」，没有「存储分离」——严格说这是最轻量级的 CQRS
  • 适合：读写都在同一库，只是想让查询更快更简单

② 事务性发件箱 + 消息（最常用）

写操作在同一事务里插入「领域事件」到 outbox 表，后台投递到 MQ，消费者更新读模型。

  • 保证「写成功则事件一定不丢」
  • 读模型最终一致（通常毫秒~秒级）
  • 适合：绝大多数需要真正分离存储的场景

③ CDC 监听 binlog（零侵入）

用 canal / Debezium 捕获数据库变更，直接同步到 ES、ClickHouse、缓存。

  • 业务代码零改动，不改写入逻辑
  • 只能拿到「数据变了」而非「发生了什么业务事件」，语义弱一些
  • 适合：构建搜索索引、数据仓库、异构查询

④ 事件溯源配合（最彻底）

写侧只存事件序列，读侧通过订阅事件流构建任意数量的投影（Projection）。

  • 可以重放历史重建读模型，修 bug 后能重算
  • 复杂度最高，通常搭配 Event Sourcing 一起上
  • 适合：金融账本、审计要求高的场景

什么时候该用 CQRS

适合读写负载差异极大（写少读多且查询复杂）
适合查询形态多样：列表、搜索、报表、聚合，一次建模难以兼顾
适合读写双方都需要独立伸缩与优化
适合团队协作需要清晰的读写职责边界
不适合简单 CRUD，读写模型本来就一样
不适合要求读写强一致（如下单后立即查必须看到最新）
不适合团队缺乏消息中间件与最终一致的运维经验

最常见的实用形态：不做完整的事件溯源，只做「写库 + 读库（或 ES）分离」——写侧保持简单的事务型模型，读侧构建一个面向查询的宽表或索引。这个形态投入产出比最高，是 CQRS 在业界最普遍的样子。

代价与坑

  • 最终一致是硬约束。写完立刻查可能读不到。UI 上要处理：写成功后前端本地合并结果、或显示「处理中」、或用乐观更新。不能假装没有这个延迟。
  • 同步链路要可靠。消息丢了读模型就永久错误。必须有：事务性发件箱、消费幂等、失败重试 + 死信、以及定期对账（比对写库与读库，发现不一致自动修复）。
  • 复杂度显著上升。多一套模型、多一条同步链路、多一份运维。小系统引入 CQRS 往往是净负担。
  • 不要为了 CQRS 而 CQRS。如果只是「查询慢」，先考虑加索引、加缓存、读写分离；这些都试过还不行，再考虑 CQRS。
  • 读模型要能重建。如果读模型只能靠增量事件构建，一旦初始数据有误就只能手工修。应保留「全量重建」能力（从写库重新生成读库），这在修数据 bug 时是救命的。

深入自检

CQRS 就是读写分离（主从复制）吗？

不是，层次不同。主从复制是存储层的技术：同一份数据复制到多台机器，读写打到不同节点，模型完全一样，解决的是读容量与负载问题。CQRS 是模型层的架构决策：读写使用不同的数据结构甚至不同的存储引擎（写用 MySQL 规范化表，读用 Elasticsearch 宽表），解决的是「同一个模型无法同时服务好读写两侧」的问题。两者可以叠加使用：CQRS 的写库自己也可以做主从复制。

CQRS 一定要配 Event Sourcing 吗？

不需要，这是最常见的误解。CQRS 只要求读写模型分离，事件溯源只是实现同步的一种（较复杂）方式。实践中大量 CQRS 系统用的是「写库 + outbox + MQ + 读库」或「CDC 同步到 ES」，完全不涉及事件溯源。只有当业务确实需要完整审计轨迹、时间旅行、或要靠重放修复读模型时，才值得引入 Event Sourcing——它带来的复杂度比 CQRS 本身高得多。

写后立即读的问题怎么处理？

四种常见手段：① 前端乐观更新——写成功后前端直接用返回的数据更新界面，不发查询；② 版本校验——写操作返回版本号，读时带上，读端发现版本过旧则等待或回源写库；③ 临时回源——写后短时间内的查询走写库（类似读写分离的写后读主）；④ 产品层面接受——显示「处理中，请稍后刷新」，把延迟变成可见的状态而非错误。选择取决于业务容忍度：社交点赞可以接受延迟，支付结果必须立即准确。

读模型出错怎么修复？

关键是保留「重建」能力。三层保障：① 幂等消费——同步逻辑可重复执行，重放事件不会造成重复计算；② 全量重建工具——能从写库全量扫描重新生成读库，当增量链路长期出错或数据已污染时使用；③ 定期比对——定时任务抽样或全量比对写库与读库的关键字段，不一致时告警并自动触发重建。没有第②条的 CQRS 系统在生产上是危险的，因为一旦读模型损坏且历史事件已过期，就没有任何办法恢复。
