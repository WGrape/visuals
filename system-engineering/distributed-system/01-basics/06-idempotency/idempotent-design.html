幂等设计

重试、重投、重复提交都是常态：让一次和多次的结果完全相同

一句话
同一个请求执行一次和执行多次，结果完全相同
为什么必须有
网络重试、消息重投、用户重复提交都是常态，不是异常
核心手段
唯一 ID + 去重表、状态机、乐观锁（版本号/CAS）、Token 预领取
不能忘的
幂等键要有过期策略，否则存储无限膨胀

一、四类典型重复场景

场景重复来源后果幂等手段
用户重复提交双击、刷新、返回再提交重复下单提交前领取 Token，服务端校验并删除
网络超时重试客户端/网关重试重复扣款请求带唯一 ID + 去重表
消息重复投递MQ at-least-once重复加积分消费端按消息 ID 去重
上游回调重放第三方回调多次重复发货业务单号 + 状态机判定

二、四种实现方案

方案怎么做优点适用
唯一 ID + 去重表请求带 business_id，插入去重表（唯一索引），冲突则说明处理过通用、可靠下单、支付、通知
数据库唯一约束用业务唯一键建唯一索引，靠数据库报错拦截最省心，无需额外表有天然唯一键的场景
乐观锁 / 版本号UPDATE ... SET status=?, version=version+1 WHERE id=? AND version=?天然防并发覆盖状态流转、余额变更
状态机只在特定前置状态下才执行，执行后变更状态最贴合业务语义订单、工单、退款
分布式锁同一业务单号加锁，串行执行简单直接并发量不高时兜底

三、去重表的正确写法

CREATE TABLE idempotent_record ( biz_id VARCHAR(64) NOT NULL, biz_type VARCHAR(32) NOT NULL, result VARCHAR(2048), status TINYINT NOT NULL, -- 0 处理中 / 1 成功 / 2 失败 expire_at DATETIME NOT NULL, PRIMARY KEY (biz_type, biz_id) -- 唯一索引是幂等的根基 ) ENGINE=InnoDB; -- 处理流程（伪代码） -- 1) 先 INSERT，靠唯一索引抢占 INSERT INTO idempotent_record (...) VALUES (...) ON DUPLICATE KEY UPDATE biz_id = biz_id; if affectedRows == 0 { // 已存在：查询上次结果 r := SELECT status, result FROM ... WHERE biz_type=? AND biz_id=? if r.status == 1 { return r.result } // 已完成，直接返回 if r.status == 0 { return "处理中，请稍后" } // 还在处理，别重复做 } -- 2) 执行业务（必须和状态更新在同一个事务里） -- 3) 更新 result 与 status = 1 -- 4) 定期清理 expire_at 过期的数据

三个必避的坑

① 先查后插有并发窗口——必须用唯一索引的 INSERT 抢占，而不是 SELECT 判断后 INSERT；② 业务与去重表要同库同事务，跨库无法保证原子，会出现「业务成功但去重记录没写」；③ 处理中要返回「处理中」而不是报错，否则上游重试会进入更混乱的状态。

四、消息消费的幂等

MQ 一般是 at-least-once，重复投递是必然事件。消费端必须自己兜住：

用 messageId 去重

每个消息有唯一 ID，消费前先查去重表

用业务单号去重

更稳：业务单号天然唯一，即使消息 ID 变化也能挡住

消费失败要区分

业务失败和重复消费是两回事，别混在一起重试

去重表要设 TTL

否则表会无限膨胀，通常保留 7~30 天即可

五、深入自检

查询类接口需要幂等吗？天然幂等。GET 不改变状态，执行多少次都一样。需要关注的是写操作：POST/PUT/DELETE 里 POST 最危险，因为它语义上就是「新建」。
PUT 天然幂等，DELETE 呢？PUT 是「整体替换」，重复执行结果相同，天然幂等；DELETE 删除同一个资源，重复执行结果也相同（第二次返回不存在），语义上幂等。但要注意「DELETE 返回 404 还是 200」这类细节要一致。
重试会放大流量吗？会，而且可能引发雪崩：下游慢 -> 上游超时 -> 上游重试 -> 下游压力翻倍。因此重试必须有退避（backoff）+ 抖动（jitter）+ 次数上限三件套。
去重表用 Redis 还是 MySQL？并发极高、允许少量丢失用 Redis（SETNX + 过期）；要求绝对可靠用 MySQL（唯一索引 + 事务）。金融类业务一般用 MySQL。
幂等键由谁生成？最好由调用方生成并在重试时保持不变，这样服务端才能识别「这是同一次请求」。如果服务端生成，重试时会拿到新键，幂等就失效了。

记住一句

重复是常态，幂等是必需品

最通用

唯一 ID + 去重表（唯一索引抢占）

必须配套

与业务同事务 + 设置过期

重试三件套

退避 / 抖动 / 次数上限

五种幂等方案的对照

方案实现要点并发安全代价适用
数据库唯一键业务唯一键上加 UNIQUE，插入冲突即重复强（数据库保证）一次索引写创建类操作（下单、发券）
幂等表 / Token先领 token，消费时原子删除（Redis Lua）强（依赖 Lua 原子性）一次 Redis 往返跨系统、无法加唯一键时
乐观锁 versionUPDATE ... WHERE version = ?强（CAS）需要版本号字段更新类操作
状态机约束WHERE status = 'INIT' 才推进强（条件更新）业务状态设计成本有明确状态流转的场景
分布式锁SETNX + 过期时间，锁业务键中等（有过期与误删风险）一次加锁，且有死锁/超时问题兜底手段，不首选

不要「先查再写」：SELECT 判断不存在再 INSERT 存在竞态窗口。幂等必须由存储的约束（唯一键、CAS、原子脚本）保证，而不是由应用逻辑的先后判断保证。

幂等键的设计规则

设计点推荐做法反例
键的构成业务主体 + 业务类型 + 请求指纹只用一个全局流水号，无法区分重试与新请求
请求指纹对关键业务参数做稳定哈希（排序后拼接）直接用原始 JSON（字段顺序变化就失效）
有效期覆盖业务最长重试周期（常见 7~30 天）永不清理，表无限膨胀
存储与业务写入同一事务落库，避免不一致先写 Redis 再写库，两次写不一致
失败语义同键不同参数要拒绝（哈希冲突要能发现）只看键不看参数，参数变了仍返回旧结果

SQL

-- 方案 1：唯一键保证创建幂等（MySQL）
CREATE TABLE orders (
  id           BIGINT PRIMARY KEY AUTO_INCREMENT,
  biz_key      VARCHAR(64) NOT NULL,      -- 业务幂等键
  user_id      BIGINT NOT NULL,
  amount       BIGINT NOT NULL,
  created_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_biz_key (biz_key)         -- 关键约束
) ENGINE=InnoDB;

-- 重复插入返回 1062（Duplicate entry），应用据此返回上一次的结果
INSERT INTO orders (biz_key, user_id, amount) VALUES ('u1:order:fp8a2c', 1, 9900);
-- ERROR 1062 (23000): Duplicate entry 'u1:order:fp8a2c' for key 'uk_biz_key'

-- 方案 3：乐观锁（CAS）
UPDATE orders SET status = 'PAID', version = version + 1
 WHERE id = 100 AND version = 3;          -- affected rows = 0 表示被并发改过

重试与幂等的配合参数

参数常用取值说明
重试次数3~5 次再多通常是系统性故障，应快速失败并告警
退避策略指数退避 + 抖动（如 100ms × 2ⁿ ± 20%）避免重试风暴同时打垮服务
超时按 P99 延迟设定，逐层收敛上游超时必须大于下游，否则重试无意义
幂等数据保留7~30 天需大于最大重试时长 + 人工重放窗口
重试分类仅对可重试错误重试（超时、5xx、限流）4xx 业务错误重试只会浪费资源

退避

# 带抖动的指数退避（避免重试风暴）
import random, time

def retry(fn, times=4, base=0.1):
    for i in range(times):
        try:
            return fn()
        except RetryableError as e:
            if i == times - 1:
                raise
            sleep = base * (2 ** i) * (0.8 + 0.4 * random.random())   # ±20% 抖动
            time.sleep(sleep)
# 4 次重试的等待上限约 0.1+0.2+0.4+0.8 = 1.5s（含抖动约 1.2~1.8s）

排障清单

症状原因处理
重复下单/重复扣款先查后写存在竞态改用唯一键或原子脚本

深入自检

只做「先查后写」为什么不够？

因为查询与写入之间存在时间窗口：两个并发请求可能都查到「不存在」然后都执行写入。幂等必须由存储层约束（唯一索引冲突、CAS 条件更新、原子脚本）来保证，应用层判断只能减少无用写入，不能保证正确性。

幂等键应该包含哪些信息？

业务主体（用户/账户）+ 业务类型 + 请求指纹（关键业务参数排序后的稳定哈希）。太少会把不同请求判成重复；太多（如带时间戳、随机数）会让重试判成新请求。

唯一键冲突返回什么？怎么处理？

MySQL 返回错误码 1062（Duplicate entry）。应用应捕获该错误，回查已有记录并返回其结果（而不是报 500），这样调用方重试得到与首次一致的响应——这才是幂等的完整闭环。

乐观锁和分布式锁怎么选？

能用乐观锁（version/CAS）就别用分布式锁：乐观锁无额外组件、无死锁、无过期误判，代价是冲突时需要重试。分布式锁适合需要互斥访问外部资源（如只允许一个任务执行）的场景，且必须设置过期时间并用 Lua 保证释放的原子性（防止误删别人的锁）。

幂等数据保留多久合适？

要覆盖「最大重试时长 + 人工重放窗口」，常见 7~30 天。太短会导致延迟重试/人工补偿时判不出重复；太长则存储成本与索引膨胀。对账系统通常会保留更久，可走归档表。
