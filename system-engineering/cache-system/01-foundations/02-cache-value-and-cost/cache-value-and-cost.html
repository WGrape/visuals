缓存的收益、代价与适用边界

缓存不是「加了就快」的银弹。这一篇先把收益公式、四类代价和六种「不该加缓存」的场景摆出来，再决定要不要往系统里引入这个有状态的中间件。

为什么快 收益怎么算 代价清单 何时不该加 上线自检 面试要点

📐 一、缓存为什么能提速：差的是数量级，不是百分比

缓存的全部价值来自一件事：把慢路径替换成快路径的次数足够多。 后面所有权衡——命中率、一致性、内存成本——都是从这一条推出来的。先看真实的延迟量级（数值随硬件/环境变化，重点看指数）：

访问路径典型耗时相对量级
CPU L1 缓存命中≈ 1 ns1×
内存随机读≈ 100 ns10²×
SSD 随机读≈ 100 µs10⁵×
同机房网络 RTT≈ 0.5 ms5×10⁵×
跨城网络 RTT≈ 30 ms3×10⁷×
数据库带索引点查1–5 ms10⁶×–5×10⁶×
数据库聚合 / 多表 JOIN10–500 ms10⁷×–5×10⁸×
调用第三方 HTTP 接口50–500 ms10⁸×
⚠️
关键结论：缓存真正救命的是"贵查询"。 如果原查询本身就是带索引的主键点查（1 ms），换成同机房 Redis（0.5 ms RTT）只省一半， 却引入了全套一致性、失效、雪崩问题——这笔账经常是不划算的。 反过来，一个 200 ms 的聚合查询或一次外部 API 调用，缓存命中后降到 1 ms，收益是 200 倍。

用阿姆达尔定律的视角看：系统响应中"可被缓存加速"的部分占比为 p，缓存把这部分加速 s 倍， 整体加速比上限是 1 / ((1-p) + p/s)。如果慢的那部分根本没被缓存覆盖（p 很小），加缓存毫无效果。 这也是"加了缓存接口还是慢"的头号原因：慢的是序列化、是下游调用、是锁竞争，唯独不是数据库。

🧮 二、收益怎么算：命中率 × 延迟差 × 回源量

缓存不是"有"或"没有"，而是一个连续变量：命中率 h。有效延迟由它线性决定：

📘
T有效 = h × T命中 + (1-h) × (T未命中 + T回填)
其中 T未命中 是回源查库的时间，T回填 是写回缓存的时间（通常可忽略，但在大 value / 跨机房写入时不能忽略）。

算一笔具体的账。假设未命中时回源耗时 20 ms，命中时 1 ms，回填忽略不计，目标是把接口 P99 压到 5 ms 以内：

① 列不等式
h × 1 + (1-h) × 20 ≤ 5
② 求解
20 − 19h ≤ 5 → h ≥ 15/19 ≈ 78.9%
③ 判断可行性
也就是说命中率必须稳定在 79% 以上才达标。如果业务是"用户查自己的订单"，key 基数大、访问分散，命中率可能长期只有 40%——这个缓存方案从账上就该否决。

第二个必须算的是回源绝对量：QPS × (1-h)。10 万 QPS、命中率 95%，意味着每秒仍有 5000 次请求打到数据库。 如果数据库单实例只能扛 3000 QPS，那 95% 命中率依然会压垮它——这就是"命中率看着挺高，库还是被打爆"的原因。 命中率是比例，回源量是绝对值，两个都要看。

💸 三、代价清单：你换来的速度要拿什么付

代价具体表现典型后果
一致性缓存与数据源之间存在时间窗口，窗口内读到旧值用户改完资料刷新还是旧的；库存超卖
内存成本内存单价远高于磁盘；命中率要求越高，需要装的数据越多为了把命中率从 90% 提到 99%，内存可能要翻几倍
系统复杂度多一个分布式组件：序列化、key 设计、过期、淘汰、预热、监控代码里到处是"先查缓存再查库"的分支
新的故障模式缓存宕机、集群扩缩容导致命中率跳水、大 key 阻塞、热 key 打爆单分片缓存本来是保护数据库的，出问题时反而成了压垮数据库的放大器
可观测性负担命中率、回源量、内存、慢查询、key 分布都要看没有指标等于闭眼开车，出问题只能靠猜
🚨
最危险的代价是最后一条"放大器效应"。 正常时缓存挡住 95% 流量，数据库按 5% 的容量配置；缓存一旦全挂，100% 流量瞬间灌进来—— 数据库不是"变慢"，是直接不可用。所以缓存层必须有熔断/降级预案（见「缓存雪崩」一章）， 让缓存在不可用时退化成"直接查库但限流"，而不是"无限回源"。

🚫 四、六种「不该加缓存」的场景

① 原查询已经足够快
主键点查 + 覆盖索引，1–2 ms。换成缓存省不到 1 ms，却引入一致性问题。
② 写多读少
每次写都要失效缓存，命中率极低，反而多了"写库 + 删缓存"两次开销。典型如流水表、审计日志。
③ 强一致要求，无法容忍任何陈旧
余额、库存扣减、分布式锁这类场景，缓存的"最终一致"语义会直接造成资损。
④ key 基数极大且访问均匀
如"按用户 ID 缓存用户最近浏览"，用户量大且每人访问分散，缓存装不下全部，命中率长期几十个点。
⑤ 查询结果频繁变化
如实时排行榜秒级刷新、股票行情，缓存的有效期比回填成本还短。
⑥ 数据量小且完全静态
配置表、字典表共几千行——直接放应用进程内的本地缓存（甚至常量）就够了，不需要分布式缓存这一层。
✅
判断口诀："贵、静、热、可容忍陈旧"四条全占才值得上分布式缓存。 贵＝回源成本高；静＝变更不频繁；热＝同一批 key 被反复访问；可容忍陈旧＝短暂读到旧值不造成资损。 缺任何一条，先考虑本地缓存、SQL 优化、或者直接不加。

✅ 五、上线自检清单

检查项合格标准
回源成本量化过能说出未命中时的耗时数字，且它显著大于命中耗时
目标命中率可估算按 key 基数与访问分布估算过，不是拍脑袋定 90%
回源绝对量校验过QPS × (1-h) 在数据库容量之内，且留有 2 倍以上余量
过期时间有依据业务能容忍的最长陈旧时间，不是随手写 30 分钟
失效路径覆盖了所有写入口包括后台管理、定时任务、数据订正脚本，不只是主接口
缓存不可用时降级方案熔断/限流或直接查库，不会无限回源打爆数据库
命中率与回源量有监控告警命中率突降能第一时间发现
大 key 与热 key 排查过单 key 不过大、热点 key 有分散或本地缓存兜底

🎤 六、面试怎么答

Q：你们为什么要用缓存？
不要只答"提高性能"。正确答法是给数字："订单详情接口原来要 JOIN 四张表，P99 180 ms，数据库 CPU 已经 70%。 改成缓存聚合结果后 P99 降到 8 ms，数据库 CPU 降到 20%。命中率稳定在 96%，回源量 400 QPS，在库容量之内。"

Q：加了缓存之后有什么问题？
按代价清单答四类：一致性（有窗口）、内存成本、系统复杂度、新故障模式（缓存宕机反而压垮数据库）。 能补一句"我们做了熔断降级，缓存不可用时直接查库但限流"是加分项。

Q：什么情况下你不会用缓存？
答第二、三节的内容：原查询已经够快、写多读少、强一致、key 基数极大、数据频繁变、数据量小且静态。 能说出"缓存是拿一致性和复杂度换速度，不是免费的"说明真的想清楚了。
