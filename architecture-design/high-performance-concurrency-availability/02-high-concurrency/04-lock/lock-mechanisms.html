各种锁的开销与适用

锁类型机制无竞争开销适用场景
互斥锁 mutex抢不到就阻塞（陷入内核 futex 等待）约 20 ns（用户态原子操作）通用首选，临界区较长时
自旋锁 spinlock抢不到就循环重试（占着 CPU）约 10 ns临界区极短（几十条指令）且多核
读写锁 RWLock读共享、写独占比 mutex 略高读远多于写（如配置缓存）
乐观锁 / CAS先算，提交时检查版本最低（纯原子操作）冲突概率低时
无锁（lock-free）CAS 循环实现的数据结构低但实现复杂极致性能场景（如 Disruptor）
偏向锁 / 轻量级锁JVM 的锁升级优化最低（几乎为零）单线程反复进入同一同步块

关键数字：无竞争的 mutex 加锁/解锁约 20 ns；一旦发生竞争，需要陷入内核 + 上下文切换，开销跳到 1–10 μs（慢 50–500 倍）。所以锁优化的核心不是“换更快的锁”，而是减少竞争：缩小临界区、降低锁粒度、分片、或者干脆去掉共享。

锁优化代码

// Go 的 sync.Mutex 实现要点（理解开销来源）
// 1) 先做一次 CAS 快速路径（无竞争时约 20ns，纯用户态）
// 2) 失败后自旋若干次（期望锁很快释放，避免上下文切换）
// 3) 仍失败则通过 runtime_Semacquire 挂起（进入内核，开销 μs 级）
// 4) 饥饿模式：等待超过 1ms 的 goroutine 会进入饥饿模式，
//    直接把锁交给等待最久的那个（防止新来的 goroutine 一直抢到）

// 降低竞争的四种实用手段：
// ① 缩小临界区：只锁真正共享的部分
mu.Lock()
counter++
mu.Unlock()          // 不要在锁内做 IO、RPC、耗时计算

// ② 分片（sharding）：把一把锁拆成 N 把
const shards = 64
type ShardedMap struct {
    mus [shards]sync.Mutex
    m   [shards]map[string]int
}
func (s *ShardedMap) Set(k string, v int) {
    i := hash(k) % shards
    s.mus[i].Lock(); defer s.mus[i].Unlock()
    s.m[i][k] = v
}

// ③ 用原子操作替代简单计数
atomic.AddInt64(&counter, 1)     // 约 5-10ns，无锁

死锁、排查与选型

死锁的四个必要条件（破坏任意一个即可避免）：① 互斥（资源独占）② 持有并等待 ③ 不可抢占 ④ 循环等待。工程上最有效的是破坏第 ④ 条——给所有锁编号，按顺序获取。

排查手段命令/工具说明
Go 死锁/竞争go run -racerace detector 能发现数据竞争
Go 协程栈curl :/debug/pprof/goroutine?debug=2看哪些 goroutine 卡在锁上
Java 线程栈jstack <pid>找 BLOCKED 状态与 waiting to lock
Java 死锁检测jstack 会自动报告输出里明确写 Found one Java-level deadlock
Linux 锁竞争perf lock、perf sched看锁等待与调度延迟
MySQL 死锁SHOW ENGINE INNODB STATUSLATEST DETECTED DEADLOCK 段
  • 按场景选型：临界区有 IO/耗时操作 → mutex（自旋是浪费 CPU）；临界区只有几条指令且 CPU 核数够 → 自旋更快；读占 95% 以上 → 读写锁；只是简单计数 → 原子操作（不要上锁）；需要尝试获取 → TryLock（带超时，避免无限等待）。
  • 锁粒度不是越细越好：拆得太细会增加锁的数量与获取次数，总开销可能反而上升，且更容易出错。合理做法是按数据的实际访问模式划分（如按用户 ID、按商品 ID 分片），而不是机械地每个字段一把锁。
  • 读写锁的写饥饿：读锁持续被获取时，写锁可能永远拿不到。Go 的 RWMutex 有写优先机制（新来的读者会被阻塞），Java 的 StampedLock 提供乐观读。
  • 别忘了锁的公平性：非公平锁吞吐高但可能饿死某些线程；公平锁保证顺序但吞吐低（多一次排队）。Go 的 Mutex 通过饥饿模式在两者间自适应。
  • 排障顺序：① 确认是锁竞争还是真的慢（看 CPU 是否空闲但吞吐上不去）；② 抓栈看阻塞在哪把锁；③ 看临界区里有没有 IO/RPC；④ 用 race detector 确认有没有数据竞争；⑤ 用 pprof/火焰图定位热点锁。
为什么加了锁反而更慢了？

三种可能：① 临界区太大（锁内做了 IO/RPC/耗时计算），串行化比例过高；② 锁粒度太粗，本可并行的操作被串行；③ 竞争太激烈，大量时间花在上下文切换上（20 ns → 几 μs）。用 pprof 看 sync.Mutex 的 contention 时间就能确认。

能不用锁吗？

能的路径：① 无共享（每线程/协程独立数据，最后合并）；② 不可变对象（只读就不需锁）；③ 原子操作（简单计数/标志位）；④ 消息传递（Go 的 channel、Actor 模型）；⑤ 无锁数据结构（CAS 循环）。“不共享”永远比“共享后加锁”快。

Redlock 的争议点：它依赖「时钟基本同步」。若发生 GC STW 或时钟跳变导致锁在业务逻辑未跑完时过期，就出现两个客户端同时持锁。Martin Kleppmann 与 antirez 的著名争论结论是：对正确性要求极高的场景用 etcd/ZooKeeper 的 fencing token（单调递增序号，资源侧拒绝旧 token），而不是纯靠超时。

锁问题排障清单

  • 先确认是不是锁：show processlist 里大量 Sending data/updating + 同一行 → 是锁等待，不是慢查询。
  • 没走索引 = 锁全表：FOR UPDATE 的 WHERE 条件必须命中索引，否则退化为表锁（用 EXPLAIN 确认 type=ref/range）。
  • 缩短事务：把 RPC、发消息、写日志挪到事务外。事务里一次远程调用 = 锁时间从 5ms 变 200ms，吞吐掉 40 倍。
  • 固定加锁顺序：多表/多行更新约定统一顺序（如按 id 升序），这是消除死锁最有效的手段。
  • Redis 锁必须有过期时间，且过期时间要大于业务最大执行时间的 2~3 倍，或者用 watchdog 续期（Redisson 的 lockWatchdogTimeout 默认 30s，每 10s 续一次）。
  • Go 的坑：sync.Mutex 不可重入，同一 goroutine 二次 Lock 直接死锁；也不能复制已使用的 Mutex（要用 go vet 拦）。
  • 乐观锁替代：高并发低冲突场景用版本号 UPDATE ... SET stock=stock-1, ver=ver+1 WHERE id=? AND ver=?，用影响行数判断是否抢到，冲突再重试。
悲观锁和乐观锁怎么选？

看冲突概率 × 冲突代价。冲突概率 >20% 或临界区很重（涉及 IO）→ 悲观锁；冲突少、临界区只是算一下 → 乐观锁（CAS/版本号）。库存秒杀这种高冲突场景，实际做法往往是把锁前移到 Redis 预扣减，DB 层用乐观锁做最终一致。

为什么 RR 下间隙锁这么容易死锁？

间隙锁锁的是「不存在的记录区间」，两个事务分别在不同区间插入后又要插入对方的区间，就会互相等待。典型是 INSERT ... ON DUPLICATE KEY UPDATE 和 SELECT FOR UPDATE 混用。解法：改成 RC + binlog_format=ROW（RC 下没有间隙锁），或把并发插入改成单线程队列。

分布式锁过期了但业务还没跑完怎么办？

这是分布式锁的核心难题，没有完美解。三种务实做法：① 续期（watchdog，线程活着就一直续）；② fencing token（资源侧校验，拒绝过期请求）；③ 把业务做成幂等 + 可重入，即使重复执行也没副作用。生产上①②③通常一起上。
