301、302、307、308 与 401、429、502：重定向和错误如何安全处理

沿一次登录跳转与接口重试，区分方法是否保留、谁产生错误和何时可重试。

重定向会发起新请求

服务器返回 3xx 与 Location，客户端根据状态码和策略再访问新地址；这不是原请求在网络里自动改变目的地。301 和 308 表示永久移动，302 和 307 表示临时移动。307、308 明确保留原请求方法与正文；303 通常引导客户端改用 GET 取结果。301、302 在历史浏览器行为中，POST 可能被改成 GET，因此需要保留写方法时不应把它们当作可靠的“原样重放”指令。

重定向链会增加 DNS、建连和 TLS 成本，还可能产生循环。客户端要限制跳转次数，并在跨源跳转时谨慎处理 Authorization、Cookie 等凭据。公开站点从 HTTP 跳 HTTPS 常见，但敏感信息不应先通过明文 URL 或请求正文发给不可信入口再期待重定向补救。

一个 POST 的危险例子

客户端 POST `/orders` 创建订单，服务器已创建并回 302 到 `/orders/7`；浏览器可能随后用 GET 查看订单，这是典型“POST/Redirect/GET”体验。若回 307 到另一创建接口，客户端会保留 POST 与正文，目标接口可能再次创建。设计时应明确跳转目标只是结果页面，还是同一写操作的新入口，并配合业务幂等键处理响应丢失和重试。

永久重定向可能被客户端或缓存记住，后续不再请求旧地址；把还在测试的新域名用 301/308 永久发布，回滚难度可能变大。变更前先测试缓存行为、证书、目标路由和旧客户端兼容性。

逐步推演

初次请求

客户端发 POST 或 GET 到原始 URL。

收到 3xx

读取 Location，按状态码决定新方法。

遇到错误

区分认证、限流与网关上游失败。

安全恢复

在总预算内重试，写请求先查幂等结果。

401、403、404 的边界

401 表示请求需要有效认证，通常应配合适当的认证挑战信息；403 表示服务器理解请求但拒绝授权；404 表示目标资源未找到，也可在某些安全策略下避免暴露资源存在。三者不是“用户没登录、已登录、文件不存在”这三个简单固定映射，具体仍由认证方案和业务策略定义。

客户端遇到 401 可以尝试刷新或重新获取凭据，但不能无限循环刷新；403 通常不应靠同一凭据立刻重试；404 是否可重试取决于资源是否可能稍后出现。日志里应记录内部拒绝原因，但对外响应避免泄漏敏感资源位置。

429、503 与 Retry-After

429 常表示请求频率或额度限制，503 表示服务暂不可用；服务端可用 Retry-After 告诉客户端建议等待多久。但该头不替代客户端自己的总截止时间和最大重试次数。大量客户端同时在同一秒恢复请求会形成第二波洪峰，重试应加入随机抖动并控制预算。按租户或用户限流时，响应应能让调用方知道是临时流控还是账户额度耗尽。

一个非幂等写请求收到 503 或在响应前断线，不能仅凭状态猜服务端是否已提交；可能是代理返回 503，也可能后端刚提交后连接断了。客户端需要稳定幂等键或查询最终结果。GET 通常更容易安全重试，但若业务把副作用错误地放在 GET 中，也会出问题。

502、504 从哪一层来

502 Bad Gateway 常由代理或网关在与上游通信失败、收到无效响应时生成；504 Gateway Timeout 常表示网关等待上游超时。它们说明网关视角出了问题，不一定是应用主动返回的状态。要看代理日志中的上游地址、连接失败、读超时和请求 ID，再与后端日志对齐。若网关在后端提交后才超时，客户端看到 504 仍可能有实际业务结果。

浏览器看到一个 502 页面，可能是 CDN、负载均衡或反向代理任何一层生成的。观察响应头和入口日志确定是哪一层，不能直接把责任归到最终服务进程。

一次可执行的验收

用 POST 请求测试 301、302、303、307、308，记录跳转后的方法、正文、目标 Host 和凭据是否保留。对 429/503 检查 Retry-After、退避和最大次数；对 502/504 注入上游连接失败、上游慢响应与“提交成功但响应丢失”。每种情形明确客户端展示、是否重试、如何查询最终状态。

HTTP 状态码是跨层契约。正确使用它可以帮助缓存、代理、监控和调用方决策；滥用 200 包裹所有错误或无条件重试所有 5xx，都会让故障更难定位。

3xx 重定向对照表

状态码语义是否保持方法是否可缓存典型用途
301永久移动否（POST 常被改 GET）会（浏览器永久记忆）域名迁移（谨慎！）
302临时移动否（同上）否临时跳转（历史默认）
303See Other强制改为 GET否POST 后跳转结果页（标准做法）
307临时重定向是否需要保留 POST 体的临时跳转
308永久重定向是会需要保留 POST 体的永久迁移
304未修改——协商缓存命中，无响应体

重定向排查

# 跟随重定向并看链路
curl -IL https://example.com
curl -L --max-redirs 5 -o /dev/null -w '跳转次数=%{num_redirects} 最终=%{url_effective} 最终码=%{http_code}\n' https://example.com/

# 只看跳转目标，不跟随
curl -s -o /dev/null -w '%{redirect_url}\n' https://example.com/

# 不跟随（看到第一个 301/302）
curl -i -s https://example.com/ | head -5

# 浏览器缓存了 301 导致改不回来时：清浏览器缓存 / 用 curl 验证服务端真实返回

重定向次数上限：浏览器通常 20 次后报 ERR_TOO_MANY_REDIRECTS；curl 默认 50 次（--max-redirs 可调）。循环跳转最常见的成因是“HTTP→HTTPS 跳转”与“负载均衡卸载 TLS 后又把请求跳回 HTTPS”互相打架。

重试策略与退避

错误是否重试策略
连接超时 / 连接被拒可重试（多半还没执行）立即重试 1 次，再退避
503 / 502 / 504可重试按 Retry-After 或指数退避
429可重试必须遵循 Retry-After，否则加剧过载
500谨慎只对幂等操作重试，且限制次数
400 / 401 / 403 / 404 / 422绝不重试请求本身有问题，重试无意义
非幂等 POST不盲目重试必须带 Idempotency-Key

标准退避公式：delay = min(cap, base × 2^attempt) × (0.5 + random()/2)，常用 base=100ms、cap=30s、attempt 上限 3–5 次。抖动（jitter）不可省略——没有抖动，故障恢复瞬间所有客户端会同时重试，形成第二次洪峰。

  • 重试预算：总重试次数 ≤ 请求量的 10%（Google SRE 建议）。重试放大是雪崩的加速器：后端慢 → 客户端重试 → 负载翻倍 → 更慢。
  • 超时必须层层递减：网关超时 > 服务超时 > 下游调用超时。否则下游还没放弃，上游已经重试，白白浪费资源。
  • 熔断优于重试：连续失败达到阈值（如 50% 错误率 / 20 个请求）后直接快速失败一段时间，让下游喘口气。
  • 区分读写：读请求可激进重试；写请求必须先确认幂等（唯一键、幂等表、INSERT ... ON DUPLICATE KEY）。
  • 记录重试链路：每次重试带 X-Attempt 与同一个 X-Request-Id，便于在日志里看出“一笔业务被重试了几次”。
为什么服务恢复后反而更慢甚至又崩了？

重试风暴 + 缓存冷启动 + 排队请求积压。解决：抖动退避、熔断、以及预热（恢复时逐步放量）。

Retry-After 有两种写法？

可以是秒数（Retry-After: 120）或 HTTP 日期（Retry-After: Wed, 21 Oct 2026 07:28:00 GMT）。客户端两种都要支持。

自检

POST 收到 307 后跳转，客户端应保留方法和正文吗？

是。307 的语义要求跳转请求保留原方法和正文；写操作需考虑重复执行风险。
