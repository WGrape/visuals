并发模型对比：线程、回调、协程、Actor 与 CSP

五种主流并发模型，本质上是在回答同一个问题：多个同时进行的执行流，怎么组织、怎么通信、怎么共享状态。

五张对照表

模型执行单元通信方式共享状态典型代表
线程 + 锁OS 线程共享内存 + 锁/条件变量直接共享，靠锁保护Java、C++、pthread
回调 / 事件循环事件处理器事件队列单线程内共享，天然无需锁Node.js、浏览器、libuv
协程用户态协程共享内存或通道共享（单线程内无需锁）Go goroutine、Python asyncio
ActorActor 对象异步消息不共享，每个 Actor 私有状态Erlang、Akka
CSP进程/协程通道（channel）通过通道传递，不共享内存Go channel、Rust mpsc

线程 + 锁：最直觉也最容易出错

优点：代码写法和顺序执行一样，共享数据直接读写。缺点：正确性完全依赖程序员正确地加锁——忘锁、死锁、锁粒度过大导致性能退化、优先级反转，这些问题都难以测试且难以复现。

适用场景：并发量不大（几百以内）、临界区清晰、团队对并发有经验。高并发服务直接用裸线程模型会很快遇到调度和内存瓶颈。

回调与事件循环：单线程内的并发

所有事件处理器在同一个线程上串行执行，天然不存在数据竞争——因为根本没有真正的并行。这是它最大的优势，也解释了很多动态语言选择它的原因。

代价是：一个处理器如果执行太久会卡住所有其他事件；复杂流程被拆成一串回调后难以阅读和维护（回调地狱）；错误传播和异常处理变得反直觉。async/await 本质上就是在这个模型上加了语法糖，让代码重新看起来像顺序执行。

协程：把调度权拿回用户态

协程在事件循环之上提供了「可挂起的函数」，既保留了单线程无锁的简洁，又能用接近同步的写法表达异步流程。它和线程模型的关键差别是切换成本与数量级，和回调模型的关键差别是可读性。

需要注意：协程解决的是并发（concurrency，同时处理多件事），不等于并行（parallelism，同时做多件事）。要利用多核，仍然要在多个 OS 线程上跑协程。

Actor 与 CSP：不共享，只传消息

Actor 模型CSP 模型
核心抽象有身份的 Actor，有私有状态和邮箱无身份的进程/协程 + 通道
通信向 Actor 的地址发消息向通道发送/接收
耦合发送方需要知道接收方是谁发送方和接收方通过通道解耦
缓冲邮箱通常无界（可能堆积）通道可有界（自带背压）
强项天然分布、容错、监督树组合性强，适合流水线与扇入扇出

两者的共同点是「不要通过共享内存来通信，而要通过通信来共享内存」。状态不共享，就不需要锁，也就消除了一整类并发 bug。代价是思维方式的转变，以及消息传递本身的开销与调试难度。

怎么选

IO 密集还是 CPU 密集

IO 密集且并发量大 → 协程或事件循环；CPU 密集 → 线程/进程池，考虑真并行。

有多少可变共享状态

共享状态复杂、团队经验一般 → 优先考虑消息传递（Actor/CSP）或少共享的设计。

语言和库的成熟度往往决定一切

Go 用 goroutine + channel 是顺水推舟；Node 用事件循环；Java 现在有虚拟线程。逆着生态走会付出额外代价。

出问题能不能查

再优雅的模型，如果团队没有对应的调试工具和经验，出故障时都会变成灾难。

边界与误区

没有任何一种模型能消除并发的固有复杂度——它们只是把复杂度挪到了不同的地方。线程模型把复杂度放在「加锁是否正确」；回调模型放在「流程被拆散」；消息传递模型放在「消息顺序、丢失与背压」。选模型本质是选择你团队更能驾驭哪种复杂度。

三种并发模型的量化对比

模型调度者切换开销并发上限多核利用

选择的决策依据

场景特征推荐模型理由
CPU 密集多进程（Python）/ 多线程（其他）绕过 GIL；线程数 ≈ 核数
IO 密集、连接多协程 / 事件驱动切换成本极低，能撑高并发
需要强隔离多进程一个崩溃不影响其他
共享大量状态多线程共享内存，无需序列化
混合多进程 × 协程多核 + 高并发，Nginx/Go 都是这个思路

最关键的一条判据：看等待时间占比。如果任务大部分时间在等 IO（网络、磁盘），协程是最优解；如果一直在算，协程毫无收益，甚至因为调度开销略慢——此时应该用进程池/线程池，数量约等于核数。

并发数估算

# 粗略估算：并发数 ≈ 吞吐 × 单任务耗时（Little's Law）
#   L = λ × W
#   L = 并发数,  λ = 到达率(请求/秒),  W = 单个请求耗时(秒)
#
# 例：QPS 10000，单请求耗时 50 ms（0.05 s）
#   L = 10000 × 0.05 = <strong>500 个并发</strong>
#   若单请求耗时降到 5 ms → 只需 50 个并发
#
# 这个公式的价值：<strong>优化延迟等价于降低并发需求</strong>
# 有时候优化单次耗时，比提升并发能力更划算

协程的两个陷阱

陷阱表现规避
协程内阻塞调用整个线程/循环被卡住，所有协程一起停阻塞操作必须走线程池或异步版本
协程泄漏启动后无人等待，永远不会结束必须有超时或取消机制
回调地狱层层嵌套，错误处理分散用 async/await 或 Promise

陷阱与规避

# 陷阱 1：协程里调了同步阻塞函数（最常见也最致命）
async def bad():
    time.sleep(1)                 # ✗ 阻塞整个事件循环！所有协程都停 1 秒

async def good():
    await asyncio.sleep(1)        # ✓ 让出控制权，其他协程继续跑

async def also_good():
    # 确实没有异步版本时，丢到线程池
    loop = asyncio.get_running_loop()
    await loop.run_in_executor(None, blocking_io_call)

# 陷阱 2：协程泄漏
async def leak():
    asyncio.create_task(worker())     # ✗ 没人 await，异常会被吞掉

async def fixed():
    task = asyncio.create_task(worker())
    try:
        await asyncio.wait_for(task, timeout=30)   # ✓ 有超时
    except asyncio.TimeoutError:
        task.cancel()                              # 取消并清理

自检 Q&A

Q：协程一定比线程快吗？

A：不是。协程的优势在切换成本与内存占用，不在执行速度。单次切换协程约 0.1 μs、线程约 1~2 μs，差 10 倍——但这个差距只有在切换极其频繁（每秒百万次）时才体现。若你的程序每秒只切换几千次，协程与线程的实际性能几乎一样。协程真正不可替代的场景是需要同时维持海量执行体（十万以上连接）。

Q：Go 的 goroutine 和 Python 的 asyncio 有什么区别？

A：调度方式不同。Go 是抢占式 + 多线程调度：运行时可以在任意时刻挂起 goroutine，并自动分配到多个 OS 线程上，天然利用多核。Python asyncio 是协作式 + 单线程：协程只在 await 处让出，且所有协程跑在一个线程里，一个核都吃不满。所以 Go 用 goroutine 就能处理 CPU+IO 混合任务；Python 的 CPU 密集部分必须另开进程。

Q：线程池大小怎么定？

A：CPU 密集 = 核数（或核数+1）；IO 密集 = 核数 × (1 + 等待时间/计算时间)。例：8 核，任务 90% 时间在等 IO → 8 × (1 + 9) = 80。但这是理论值，实际要通过压测找拐点——线程过多会因上下文切换与内存占用反而变慢。另外注意线程池不是越大越好，超过某个点吞吐会下降。

Q：为什么有了协程还需要进程？

A：两个原因——① 多核：协程本身跑在单线程上，要利用多核必须开多个 OS 线程或进程；② 隔离性：协程共享同一进程的内存，一个协程的段错误或内存泄漏会拖垮整个进程。所以生产架构常是多进程 × 每进程内多协程（Nginx、Go 服务、Python 的 gunicorn+gevent 都是这个结构），既利用多核又保证高并发。

自检

「不共享内存就没并发问题了」这句话对吗？

不完全对。它消除的是数据竞争（data race）这一类问题，但分布式意义上的问题仍然存在：消息顺序、重复投递、丢失、超时重试、死锁（互相等待对方的消息）。这些问题在 Actor 和 CSP 系统里同样常见。
