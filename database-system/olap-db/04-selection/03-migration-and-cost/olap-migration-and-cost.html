01四条最常见的迁移来源

从哪来迁移动机主要难点
MySQL / PostgreSQL分析查询拖垮线上库 schema 需要重新建模；增量同步的延迟与一致性
Elasticsearch聚合能力弱、存储成本高查询语义不同（DSL → SQL）；嵌套结构扁平化
Hive / Spark 离线查询太慢，想要交互式分区与文件格式要重做；UDF 需要替换
自建 ClickHouse / Doris换引擎或上云托管SQL 方言差异；物化视图与索引要重建
先想清楚"为什么迁"：如果是为了降本，重点在存储与压缩；如果是为了提速，重点在数据模型与索引；如果是为了实时，重点在导入链路。三个目标的最优解不同。

02迁移路径：双写、灰度与回滚

① 全量回溯 + 增量追平。先把历史数据灌进去，再启动增量同步追平，最后在一个时间点切流。
② 双写双跑。新旧两套同时写入，查询也同时发两边，比对结果。这是唯一能在切换前发现语义差异的方法。
③ 灰度切读。先切 1% 的只读流量，观察延迟与错误率，逐步放大。永远保留快速切回的能力。
④ 观察一个完整周期。至少覆盖一次月结/大促/周报高峰，因为长尾问题常在负载峰值才暴露。
⑤ 下线旧链路。确认无流量后再停双写，避免"旧库还在写但没人知道"。
不要做"一次性大切换"。分析系统的错误往往不报错、只是结果不对，等到业务发现时已经影响决策很久了。双跑比对是必须的，不是可选的。

03数据模型改造：迁移中最容易低估的部分

从行存/文档型迁到列存分析引擎，最痛苦的不是搬数据，而是重新建模。三处最常出问题：

问题为什么怎么做
宽表 vs 星型行存里习惯范式化，分析引擎偏好宽表或星型按查询频率决定冗余程度，高频维度下沉到事实表
分区键选择选错会导致全表扫描或分区数爆炸按最常用的时间过滤字段分区，按高频 JOIN/过滤字段分桶
高基数字段用户 ID 这类字段做维度会导致聚合极慢考虑预聚合，或用近似去重（HLL）替代精确 COUNT DISTINCT
不要把 OLTP 的表结构原样搬过来。原样迁移是最省事的做法，也几乎必然导致性能不达标。建模改造才是迁移收益的主要来源。

04怎么验证迁移后结果一致

① 行数与汇总值比对。先比对总量、求和、去重计数，这一步能抓住 80% 的导入问题。
② 分维度下钻比对。按日期、按主要维度分组比对，暴露分区与编码问题。
③ 抽样明细比对。随机抽若干主键，逐字段比对，暴露类型转换与时区问题。
④ 慢查询比对。把旧系统的 Top 慢查询拿过来跑，确认延迟真的改善了。
特别关注四类差异：时区（UTC vs 本地）、浮点精度、NULL 与空串、去重语义。这四项不报错，但会让数字悄悄对不上。

05成本怎么估：存储、计算与人力

成本项怎么估容易漏掉的
存储原始量 × 压缩比（列存常见 3–10 倍，视数据与编码而定）副本倍数、索引与物化视图的额外占用、临时空间
计算按峰值并发 × 单查询资源占用估算导入与 compaction 也吃资源，常与查询争抢
数据同步全量回溯 + 常驻增量链路的资源同步任务的失败重试与监控成本
人力建模改造 + 查询改写 + 双跑验证这一项常被完全忽略，实际往往超过硬件成本
压缩比的具体倍数取决于数据特征与编码方式，差异很大——请用你自己的数据实际导入一次来测，不要按经验值做预算。
Q：迁移一定能降本吗？
A：不一定。如果查询形态没变、建模没改，只是换个引擎，降本幅度通常有限。真正的降本来自：压缩更优、预聚合减少扫描、冷热分层、以及下线旧系统。

06上线前风险清单

Q：最该担心什么？
A：结果不一致但不报错。这是分析系统独有的风险，必须靠双跑比对来防。
Q：实时导入需要特别准备什么？
A：导入的幂等与乱序处理。上游重发、延迟到达都会造成重复或丢数，需要主键去重与时间窗口兜底。
Q：权限怎么做？
A：迁移期两套系统并存，权限容易漏配。提前梳理角色与行级/列级权限需求，不要上线后补。
Q：要不要保留旧系统？
A：至少保留一个可回滚窗口（通常 2–4 周）。分析系统的正确性验证需要时间，过早下线会失去退路。
Q：什么时候该放弃迁移？
A：如果查询形态高度固定且量小，现有系统已经够用，迁移的收益可能覆盖不了建模改造与双跑验证的成本。不是所有分析场景都需要列存引擎。
一句话收尾：迁移的成败不在引擎选型，在建模改造与结果验证。这两项做扎实，换哪个引擎都不会太差。

最核心的经验：SQL 方言改造是最大的隐性成本，很多人以为“都是 SQL，改改就行”，实际上窗口函数、日期函数、JSON 处理、NULL 语义、隐式类型转换的差异会吃掉大量时间。

方言扫描与自动转换

# 迁移前的 SQL 兼容性扫描（自己写个简单的检查脚本）
import re, glob

DIALECT_RISKS = {
    r"\bcollect_set\s*\(":     "Hive 特有，ClickHouse 需改成 groupUniqArray",
    r"\bexplode\s*\(":         "需改成 arrayJoin 或 lateral view",
    r"\bget_json_object\s*\(": "需改成 JSONExtractString / get_json_string",
    r"\bdate_add\s*\([^,]+,":  "参数格式可能不同（天数 vs INTERVAL）",
    r"\bnvl\s*\(":             "改成 ifNull / coalesce",
    r"\bapprox_distinct\s*\(": "改成 uniq / approx_count_distinct",
    r"\bconcat_ws\s*\(":       "参数顺序或 NULL 行为可能不同",
}

for f in glob.glob("sql/**/*.sql", recursive=True):
    text = open(f).read()
    for pat, msg in DIALECT_RISKS.items():
        if re.search(pat, text):
            print(f"{f}: {msg}")

数据校验

# 迁移后的数据校验（必须做的三件事）
# ① 行数校验（最简单但最能发现问题）
SELECT count(*) FROM src.table;
SELECT count(*) FROM dst.table;
-- 不一致就要查：NULL 处理、去重逻辑、过滤条件

# ② 汇总值校验（比行数更能发现内容错误）
SELECT sum(amount), count(distinct user_id), avg(score)
FROM src.table WHERE dt = '2026-01-01';
-- 两边对比，浮点数注意精度（用 round 到小数点后 6 位再比）

# ③ 抽样明细比对（发现"总数对但内容错"的情况）
SELECT * FROM src.table WHERE dt='2026-01-01' ORDER BY id LIMIT 1000;
SELECT * FROM dst.table WHERE dt='2026-01-01' ORDER BY id LIMIT 1000;
-- 用 md5(concat_ws('|', *)) 做整行校验更高效

# 自动化校验脚本思路
def verify(src_sql, dst_sql, tolerance=1e-6):
    s = query_source(src_sql)
    d = query_target(dst_sql)
    if abs(s - d) > tolerance:
        raise ValueError(f"不一致: src={s} dst={d}")
    print(f"✓ 一致: {s}")

# 关键：按分区逐天校验，而不是全表一次比（出错好定位）

最容易出问题的三类差异：① NULL vs 空字符串——不同系统默认值不同，导致 count 和 sum 对不上；② 字符集与排序——中文排序、大小写敏感；③ 时区——源库存 UTC、目标库按本地时区解析，日期边界就会错一天。迁移前先把这三项对齐。

成本模型：算清楚 TCO

成本项计算方式示例（10 TB 数据、20 台机器）
存储成本数据量 × 单价 × 副本数10 TB × 3 副本 = 30 TB；云盘约 0.3 元/GB/月 → 约 9000 元/月
计算成本机器数 × 单价 × 时长20 台 16C64G，云上约 2 元/小时/台 → 约 2.9 万/月
对象存储（冷数据）0.1 元/GB/月100 TB 冷数据 → 约 1 万/月
运维人力0.5 – 2 人按 3 万/人月 → 1.5 – 6 万/月

省钱最有效的三招：① 冷热分离——热数据（近 30 天）放 SSD，冷数据放对象存储（成本差 3 – 10 倍），这是最大的省钱点；② 降采样 / 预聚合——原始数据保留 7 天，之后只保留聚合结果，存储量可降 90%+；③ 压缩——列存压缩率 3 – 10 倍，选对编码（字典、RLE、ZSTD）能再省一半。

隐性成本提醒：运维人力常常超过硬件成本。一个需要专人调优的 OLAP 库，一年的人力成本（30 – 70 万）可能比机器成本高得多。所以选型时“好不好运维”和“快不快”同样重要。

深入自检

能不能不停机迁移？

可以，标准四步：① 双写——应用同时往新旧两套写（新库先只写不读）；② 回填历史——把历史数据批量迁移到新库；③ 双读比对——读仍走旧库，但异步在新库跑同样的查询并比对结果，观察 1 – 2 周（这一步最关键，能发现 SQL 语义差异）；④ 灰度切读——按 1% → 10% → 50% → 100% 逐步切到新库，每步观察 1 – 2 天。全程保留回滚能力。关键是第 ③ 步：没有比对就切换，等于盲赌。

迁移后发现性能更差怎么办？

先定位是哪类查询变慢：① 全表扫描类变慢——检查是否用了列存应有的能力（分区裁剪、稀疏索引、PREWHERE）；② JOIN 变慢——检查 JOIN 顺序、是否走广播还是 shuffle、内存够不够；③ 高并发点查变慢——OLAP 库本来就不擅长点查，这类查询应该拆到 KV/OLTP 而不是硬塞进 OLAP；④ 写入变慢——检查是不是小批量频繁写入（应改成攒批）。常见根因：直接把 OLTP 的表结构和查询搬过来，没有按列存重新设计。列存需要：合理的 ORDER BY、分区、适度反范式化。

要不要保留旧系统？

建议至少并行 1 – 3 个月，然后：① 确认所有查询都迁移完毕（用查询日志核对，而不是凭记忆）；② 确认结果一致性（抽样比对历史报表）；③ 保留旧系统的只读副本（成本很低）作为兜底，直到新系统稳定运行一个完整业务周期（如走完一次月结、一次大促）。完全下线前，务必导出一份数据备份——很多公司下线半年后发现某个年报需要从旧库取数。

小团队该不该上 OLAP 专用库？

看数据量：< 100 GB 且查询不复杂 → 不要上。PostgreSQL（配列存扩展）或 DuckDB（嵌入式、零运维）就能处理，运维成本接近于零。上 OLAP 库的门槛：① 数据量 > 几百 GB；② 查询涉及大范围扫描聚合；③ 有专人能运维调优。现实中最常见的错误是“数据量才 20 GB 就上了 ClickHouse”——性能确实快了，但引入了运维负担、SQL 改造成本、团队学习成本，总体是亏的。
