实时语音对话的体验几乎完全由延迟决定。人会容忍回答不聪明，但很难容忍「问完要等一秒」。延迟是加出来的，所以优化必须一项一项砍，而不是笼统地换模型。

01端到端延迟的四项分解

环节常见耗时（量级）优化手段
VAD 端点检测几十 ~ 200 ms缩短尾部静音判定，用更激进的阈值
ASR 识别60 ~ 200 ms流式识别、减小 chunk、就近部署
LLM 生成200 ~ 500 ms流式首 token、用小模型、裁剪提示
TTS 合成80 ~ 150 ms流式合成、首包优先、就近部署
网络往返10 ~ 100 ms就近接入、长连接复用、协议选型
  • 人对停顿的敏感阈值约 500~800 毫秒，超过就开始觉得对话不自然
  • 总延迟 = 说话结束 → VAD 判定 → ASR → LLM 首 token → TTS 首包 → 出声
  • 优化顺序按占比从大到小：LLM 通常最大，网络最容易被忽略
  • 流式是唯一能显著降低感受延迟的手段：边生成边念，把串行变成流水
要点：一个常被忽略的收益点：让模型边生成边合成。等全部生成完再合成，用户要多等一整句的时间，这是最浪费的一项。
宁可偶尔误判（用户没说话就停了），也不要漏判（用户说话了还在念）

02VAD 的三个关键参数

参数作用调大调小
起始判定阈值多大能量算开始说话更不容易误触发更灵敏，容易把噪声当说话
尾部静音时长静音多久算说完了不容易打断长停顿更快结束，但会切断自然停顿
最小语音段时长短于此不算说话过滤咳嗽等噪声可能漏掉「嗯」「好」等短回应
# 常见取舍（量级参考，具体要按场景调）
VAD_CONFIG = {
    'start_threshold': 0.5,      # 起始判定：0.3~0.7
    'end_silence_ms': 400,       # 尾部静音：300~800 ms，是延迟与容错的分界
    'min_speech_ms': 200,        # 最小语音段：小于它会漏掉短回应
    'max_speech_ms': 30000,      # 超时保护，防止用户一直说
}

# 端点判定的两条策略
# 保守：等 700ms 静音才结束 -> 不容易切断说话，但明显更慢
# 激进：等 300ms 静音就结束 -> 更快，但用户思考时会抢话
要点：尾部静音时长是唯一同时影响延迟与误判的参数。300 ms 更快但会抢话，700 ms 不抢话但明显更慢，常见取值落在 400~600 ms。

03打断处理的三步与取舍

  1. 检测到用户开始说话 → 立刻停止 TTS 播放，不要等说完
  2. 清空已经生成但还没播出的音频，否则停了之后会继续冒出声音
  3. 把新输入送进 LLM，同时决定是否要丢弃上一轮未完成的生成
策略做法代价
全丢检测到打断就放弃上一轮生成响应快，但用户可能只是附和
保留上下文保留已生成内容，只停止播放更自然，但延迟表现不变
区分插入语「嗯」「好的」这类不打断需要额外分类，实现复杂
要点：取舍建议：宁可误判也不要漏判。用户说话了系统还在念，是非常糟糕的体验；反过来用户只是清嗓子导致打断，代价小得多。

04排障顺序与常见坑

  1. 先分段打点：VAD / ASR / LLM / TTS 各自单独计时，不要只看总延迟
  2. 确认流式是否真的生效：如果 TTS 等整句生成完才开始，延迟会凭空多几百毫秒
  3. 检查网络：跨地域往返几十毫秒起，就近接入往往比换模型更有效
  4. 回声问题单独排查：设备外放被自己录进去会导致 ASR 识别混乱
症状原因处理
整体慢但分段都不慢串行了，没有流水线改成流式，边生成边合成
用户说话被抢断尾部静音太短调到 500~700 ms
用户说完了没反应尾部静音太长调到 300~400 ms
系统自己念自己录回声消除没做开 AEC 或改耳机
打断后还继续出声只停了生成没清播放队列清空已生成未播出的音频
要点：最后一条经验：先测再优化。把四段的耗时打点输出成日志，优化才有方向，否则很容易改了半天没改到瓶颈上。
