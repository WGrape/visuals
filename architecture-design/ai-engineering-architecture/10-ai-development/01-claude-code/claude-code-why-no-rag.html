Claude Code · 检索策略

Claude Code 为什么不先给代码库做 RAG？

它用 Grep / Glob / Read 在代码库里反复试探，而不是先建一套向量索引。这不是偷懒，而是对「代码」这个特殊语料的工程权衡。

00先说清楚：Claude Code 实际在怎么做检索

很多人默认「AI 读代码库 = 把代码向量化 → 存向量库 → 查询时召回」。但 Claude Code 走的完全是另一条路：

Claude Code 的 Agentic 检索循环
没有向量库，没有预建索引。Grep 读的是磁盘上此刻的真实内容。

关键观察：Claude Code 的工具箱里压根没有「向量检索」这一项。它的检索原语是 Grep（正则匹配）、Glob（文件名模式）、Read（读文件）——全是精确、确定性、零前置成本的操作。

而外面套的是一层会推理、会迭代的 Agent：搜一个词 → 看结果 → 判断要不要换个词 → 顺着函数名找调用方 → 反复几轮直到拼出全貌。

01Claude Code 的本地工作区检索

打开仓库后，它先从当前工作区的文件名、代码符号和项目说明寻找线索，再按搜索结果读取相关文件。编辑或切换分支后，下一次读取直接面对当前文件内容；无需等待预建检索索引同步。

这个页面关注产品工作流：Grep / Glob 缩小范围，Read 核对完整上下文，Agent 根据结果继续搜。索引成本、语义召回与精确匹配的通用选型，请看代码检索：grep 与 RAG 何时适用。

02项目说明和记忆如何辅助查找

CLAUDE.md 与自动记忆可以提供项目结构、约定和过去的经验，帮助 Agent 决定先查哪里；具体实现仍要以当前代码为准：

Claude Code 的三类项目线索
三类信息共同缩小查找范围；最终仍需读取当前代码核实。

各自的边界

  • Grep / Read：读取当前工作区，验证函数、配置和调用关系。
  • CLAUDE.md：保存团队约定、常用命令和项目入口；内容随代码维护，可能需要人工更新。
  • Auto Memory：记录跨会话经验，适合提供检索线索；涉及实现细节时仍要回到代码核实。

项目说明和记忆是导航线索，当前文件是事实来源。先用线索定位，再读取和验证，避免把过时笔记当成代码现状。

03一次检索如何收敛

从问题到当前代码

Claude Code 先用项目说明和记忆形成搜索线索，再用 Glob / Grep 定位文件和符号，随后用 Read 查看上下文；结果不足时换词、追调用方或检查配置，最后根据读到的当前代码回答或修改。

这种工作流适合交互式、持续变动的本地仓库。若需要大规模语义检索或高并发查询，应按需求评估额外的代码索引；参见检索策略课程。

结论先行：不是不做检索，而是不做「预先建索引的检索」

代码助手不先给整个仓库建向量库，核心原因不是技术做不到，而是性价比与新鲜度都不划算：代码库变化极快，索引建好就可能过期；而代码本身高度结构化，用符号、路径、字符串直接查，往往比向量相似度更准。

新鲜度代码每次提交都在变，预建索引需要持续重建与同步
精确性代码靠符号与引用关系定位，关键词与结构信息更可靠
规模中大型仓库全量嵌入成本高，而实际需要看的通常只有一小片
可解释grep 命中的文件行可以直接核对，向量召回难以解释
增量性改动只在局部，按需读相关文件即可，不需要全局视图
按需检索的收敛过程：每一轮都只是「再多看一点」，而不是先吞下整个仓库

两种路线的正面对比

把「预建索引的 RAG」和「按需探索的检索」放在一起看，差异不在准确度一项，而在维护成本、可解释性与冷启动延迟三项上。

对比项预建索引式 RAG按需探索式检索
首次可用时间需要先全量嵌入，仓库越大越慢立即可用，无需准备
新鲜度依赖重建，代码一改就可能过期每次都读当前磁盘上的真实内容
定位方式语义相似度召回，可能召回不相关片段路径、符号、字符串、引用关系
可解释性难以解释为何召回某段命中位置明确，可直接核对
成本存储与嵌入计算随仓库线性增长只花在真正读过的文件上
擅长跨大范围、语义模糊的自然语言查找精确定位、局部修改、结构化代码
短板索引维护与过期问题若初始关键词不对，可能需要多轮探索

更准确的说法：这不是「RAG vs 不 RAG」的对立，而是「什么时候值得为检索付出预处理成本」的权衡。对聊天知识库值得，对频繁变动的代码库往往不值得。

代码检索的三板斧与各自的适用面

结构化定位

按文件路径、目录约定、模块边界来缩小范围。代码仓库本身就是一棵有意义的信息树，目录名与文件名往往已经说明了职责，这是最便宜也最有效的第一层过滤。

符号与引用查找

找函数定义、找调用点、找类型引用。这一层依赖语言的索引能力，准确度远高于语义相似度，因为它用的是代码真实的引用关系而不是文字相似。

全文关键词搜索

用字符串、错误信息、配置项名直接搜。看似原始，但在代码场景下极其有效：报错信息、常量名、接口路径都是高区分度的锚点。

先看目录结构目录名往往已经回答了「代码在哪一层」
用错误信息搜报错文本是最强的定位锚点
找定义再找引用先定位定义，再顺着引用看影响面
只读相关片段不要一次性读整个大文件
改完立刻验证编译与测试是最可靠的反馈
关键词不对就换换个术语再搜，别死磕
跨语言边界小心生成代码、反射调用搜不到，要单独考虑

什么时候仍然值得做 RAG

前面的结论有明确前提：代码库小到中等、且频繁变动。前提一变，结论也要变。

仓库非常大时怎么办？

当仓库大到「连目录结构都摸不清」时，预建索引的收益会上升：可以先用语义检索把候选范围从几十万文件缩到几十个，再用精确手段定位。这时 RAG 的定位应该是「粗筛器」，而不是最终答案来源。

需要跨仓库检索时呢？

跨仓库、跨服务找「类似实现」是语义检索的强项，因为这类需求本身就是模糊的：你不知道它叫什么，只知道大概在做什么。这时预建索引是划算的。

历史代码与非代码产物呢？

设计文档、需求说明、事故复盘、提交历史这类非结构化、不参与编译的文本，恰恰是 RAG 最擅长的场景，因为它们没有符号可以查。

有没有折中方案？

有：只对「不常变动且难定位」的部分建索引，比如文档、历史提交说明、第三方依赖源码；对业务代码本身保持按需读取。这样既拿到语义检索的好处，又避开过期问题。

一句话总结：把精确手段用在精确的地方，把模糊手段用在模糊的地方。代码是精确的，所以优先用精确手段；只有当问题本身模糊、或规模大到精确手段无从下手时，才值得为检索付出预处理的代价。
