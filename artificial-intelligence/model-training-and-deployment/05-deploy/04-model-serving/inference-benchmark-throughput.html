推理服务有三个互相打架的指标：吞吐、延迟、并发。batch/量化/KV Cache 是调吞吐的三把钥匙，但每把都拿延迟或显存做交换。

01三个关键指标

指标含义谁关心
TTFT首 token 延迟用户体感
TPOT每 token 间隔生成流畅度
TPS / QPS单位时间 token / 请求数容量规划
并发数同时处理的请求数压测设定
要点：用户体感看 TTFT + TPOT；老板算账看总 TPS。两者经常冲突。

02吞吐—延迟权衡

  • 增大 batch / 并发 → GPU 利用率上升 → 吞吐上升。
  • 但单请求要排队，TTFT / TPOT 变高。
  • 小 batch 延迟低，但 GPU 算力和显存带宽喂不饱。
要点：经验公式：吞吐 ≈ 并发数 / 平均延迟。在线服务设 max_batch 上限保延迟；离线批量尽量开大 batch。

03KV Cache 是显存主耗

  • 自回归每生成一个 token，都要读前面所有 token 的 K/V。
  • KV Cache 显存 ≈ 序列长 × 层数 × 隐藏维 × 2(K,V) × 精度字节。
  • 长上下文是显存和带宽的主要消耗点。
要点：PagedAttention 把 KV 按页管理，减少碎片；显存不够时优先降 max_seq_len 或启量化。

04量化换吞吐

手段换来了什么代价
权重 INT8/FP8降显存 + 降带宽 → 同卡吞吐↑精度有损需评测
激活量化进一步降带宽实现更复杂
更短 max_seq_len省 KV Cache 显存截断长上下文
要点：量化主要省「带宽瓶颈」场景的延迟；若瓶颈在算力(FLOPs)，量化收益有限。

05常见疑问

问：为什么长上下文突然变慢？

KV Cache 随序列长度线性增长，显存/带宽压力陡增，可能触发换页或被迫降 batch。

问：batch 越大越慢吗？

不一定。小 batch 是 GPU 喂不饱(吞吐低)；大 batch 吞吐高但单请求延迟高。按「保延迟上限」去设最大 batch 即可。

第一层 · 概念与判定

推理基准关注两个维度：吞吐（throughput，如 req/s、tokens/s）与延迟（latency，p50/p99），二者常此消彼长。

  • 提高吞吐常用手段：增大 batch size、提高并发、用 TensorRT/编译优化。
  • 延迟敏感场景（在线）优先 p99，离线批处理优先吞吐。
  • 判定：GPU 利用率低 → 吞吐没喂满；p99 高 → 排队或预处理瓶颈。

第二层 · 参数·命令·量化

第三层 · 排障与边界

  • 显存不足 OOM：batch 太大或序列过长；降 batch / 开梯度无关推理 / 用 KV-cache 量化。
  • 排队延迟高：并发超过服务容量；加实例或限流，避免雪崩。
  • 预处理瓶颈：CPU 解码/归一化拖后腿，GPU 在等数据；用独立预处理线程/批解码。
  • 动态 shape 抖动：变长输入频繁触发重新编译/ padding；固定或分桶 shape。

第四层 · 原理与取舍

增大 batch 能把矩阵乘的并行度吃满（提吞吐、降单位成本），但显存与排队延迟随之上升，故 p99 变差。瓶颈分两类：compute-bound（算力满）与 memory-bound（带宽满），后者靠算子融合/量化更见效。warmup 是因为首次调用含图编译/内核启动开销，不剔除会污染基准。

为什么吞吐高但 p99 也高？

大 batch 拉高吞吐的同时，单请求要等整批凑齐与算完，尾延迟上升；在线场景需权衡 batch。

GPU util 低说明什么？

数据喂不饱或 kernel 太小；增大 batch/并发或优化数据管线来提升利用率。
