整洁架构 / 洋葱架构

什么时候适用？

判断信号：业务规则要长期独立于 Web 框架、数据库和外部服务。

  • 核心定价规则要在不同接口复用
  • 更换数据库时不改业务用例
  • 单元测试不启动外部基础设施

和相近方案怎么区分？

相近方案选择边界
六边形架构两者都让核心隔离外部；六边形以端口和适配器描述边界，整洁架构更强调同心层级和依赖规则。
传统分层分层可能让业务层依赖具体数据层；整洁架构要求依赖箭头指向内部。

最小伪代码

interface OrderRepository { save(order) }
class PlaceOrder {
  constructor(repo: OrderRepository) { this.repo = repo }
  run(items) {
    order = Order.create(items)  // 领域规则
    this.repo.save(order)
    return order.id
  }
}

边界：内层不导入具体数据库或 Web 框架；接口应由内层需求定义，而非为每个类机械造接口。

依赖规则 Dependency Rule

源码依赖只能由外指向内，内圈不引用任何外圈

整洁架构（Robert Martin）与洋葱架构（Jeffrey Palermo）几乎同构：最内是实体(企业规则)，往外是用例(应用规则)、接口适配器、最外是框架与驱动。铁律：依赖只能向内，内层绝不 import 外层。

四圈职责

  • 实体：最通用、最不易变的企业业务规则。
  • 用例：特定应用的业务流程（一个用例一个交互）。
  • 接口适配器：把数据在『用例格式』与『框架格式』间转换。
  • 框架与驱动：最易变的东西（Web 框架、数据库驱动）。

面试高频问答

Q：为什么内圈不能依赖外圈？
A：为了让最珍贵的业务规则不被易变的框架/数据库绑死。DB 换了、Web 框架换了，只要适配器跟上，核心一行不用动。这是『稳定依赖原则』的体现。
Q：整洁架构和分层架构冲突吗？
A：不冲突，是互补。分层讲『纵向切职责』，整洁架构讲『依赖方向』；实际项目常把整洁架构的圈再按分层细化。

Clean Architecture：四层同心圆与一条铁律

Robert C. Martin（Uncle Bob）提出的 Clean Architecture 用一个同心圆表达架构：越靠内越抽象、越稳定、越与业务相关；越靠外越具体、越易变、越与技术相关。整套架构只有一条不可违反的规则——依赖规则：源码依赖只能由外向内，内层绝不知道外层的存在。

Clean Architecture 四层同心圆与唯一铁律：依赖向内

四层各自是什么

层内容变化频率能否被外层替换
Entities（实体）企业范围内最通用、最稳定的业务规则与数据；可以是带方法的对象，也可以是一组数据结构与函数最低——几乎不变不依赖任何东西，谁都替换不了它
Use Cases（用例）应用专属的业务规则，编排 Entities 完成具体用例（如「下单」「退款」）低——随业务需求变换 UI、换数据库都不应影响它
Interface Adapters（适配器）把数据从「用例与实体最方便的形式」转换成「外部最方便的形式」；Controller、Presenter、Gateway中——随外部技术变换框架需重写这一层
Frameworks & Drivers（框架与驱动）Web 框架、数据库、消息中间件、UI、硬件；只是细节，是「插件」最高本身就是可替换的插件

判断一层的归属：问「如果我要换掉它，会影响哪一层？」换数据库只影响最外两层 → 说明业务层隔离得好；换 Web 框架要改用例代码 → 说明分层失败。

跨越边界：如何让内层调用外层又不违反依赖规则

这是 Clean Architecture 最精妙的地方。用例需要调用数据库（外层），但依赖规则禁止内层知道外层。解法是依赖倒置（DIP）：

依赖倒置：调用方向向外，源码依赖方向向内

另两种跨边界方式：① 依赖注入——外层在创建用例时把实现传进去，内层只持有接口；② Presenter 反转——用例不直接返回数据给 UI，而是调用一个 ViewModel 接口（定义在内层），由外层的 Presenter 实现它并决定怎么展示。

Clean Architecture 带来的四个特性

① 框架无关（Independent of Frameworks）

核心业务不依赖框架的存在。框架是工具，不是架构。

  • 好处：换框架不是重写，而是替换最外层
  • 检验：核心代码里有没有 import org.springframework.*

② 可测试（Testable）

业务规则可以脱离 UI、数据库、Web 服务器测试。

  • 这是最直接的收益：单测秒级、稳定、无需容器
  • 也是判断架构是否干净的最快指标——如果测业务必须起数据库，架构就有问题

③ UI 无关（Independent of UI）

换界面（Web → 移动端 → CLI）不影响业务规则。

  • 用例接收输入、产出输出数据，不关心谁调用它
  • 同一用例可同时服务页面、API、定时任务

④ 数据库无关（Independent of Database）

业务规则不绑定某种存储。

  • 可以先用内存实现开发，后期再接真实数据库
  • 换 Oracle → MySQL → MongoDB 只影响适配器

还有一个常被忽略的：可延迟决策——因为数据库、框架被隔离在外层，项目早期可以先用最简实现跑起来，等技术选型明确后再替换，而不用在需求不清时就做不可逆的技术绑定。

实践中的取舍与批评

  • 不是所有项目都需要全套。简单 CRUD 系统照搬四层会产出大量样板代码（DTO、接口、转换器），维护成本反超收益。Uncle Bob 本人也说「架构是为未来变化留出的选项，不要为不会发生的变化付钱」。
  • 「用例类爆炸」问题。每个用例一个类（CreateOrderUseCase、CancelOrderUseCase …），小系统会显得繁琐。可接受的做法是按相关性聚合，不必机械一比一。
  • 对象转换开销。每层有自己的数据表示（Entity / DomainModel / DTO / ViewModel），转换代码量与性能开销都真实存在，要用工具（MapStruct）与「只在边界转换」来限制。
  • 团队认知成本。新人常问「为什么要写这个接口」，需要配套文档与代码评审，否则会逐渐退化成「有接口但依赖照样向下」的假架构。
  • 用工具守护架构。推荐用 ArchUnit（Java）、import-linter（Python）等写架构测试，在 CI 里强制「domain 包不得依赖 infrastructure 包」，防止随时间腐化。

深入自检

Clean Architecture 和六边形架构该选哪个？

它们是同一原则的不同表达，不必二选一，理解其一即可。差别：六边形只有「内外两圈 + 端口适配器」，术语更少、更容易向团队解释；Clean Architecture 分四层、术语更细，明确了 Use Case 与 Entity 的区分，对复杂业务的表述力更强。实践建议：用六边形的「端口适配器」词汇来做模块划分与命名（好沟通），用 Clean 的「依赖向内 + 用例层」来约束层次（好落地）。工程上更多见到的是两者融合的产物。

Entities 和数据库实体是同一个东西吗？

不是，这是初学者最常混淆的点。Clean Architecture 里的 Entity 是「企业业务规则」的载体，是最抽象最稳定的一层，它不关心自己怎么被存储。数据库实体（JPA @Entity / PO）是持久化细节，属于最外层。所以一个项目里通常同时存在：领域 Entity（含业务方法）、持久化 PO（含 ORM 注解）、传输 DTO（含序列化注解）。把三者合一（在领域对象上加 @Entity 和 @JsonProperty）是最常见的架构腐化起点。

如何判断一个系统是否真的做到了 Clean？

三个快速检验：① 编译期检查——在核心模块（domain/application）目录下 grep 框架与数据库的 import，应该是零；② 测试检查——核心业务测试能否在不启动 Spring/Web/数据库的情况下跑完（应该能，且是秒级）；③ 变更检查——试着换掉一个外部依赖（如把 MySQL 换成内存实现），看需要改动多少个文件（理想情况只改适配器包）。三条里有两条不过，说明分层只是形式上存在。

这套架构适合什么规模的项目？

业务复杂度越高、预期维护时间越长、外部依赖越多变，收益越大。反之，简单的管理后台、数据展示类应用、原型验证、生命周期预计不超过一两年的项目，照搬全套会明显拖慢开发且收益有限。折中做法：即使不做完整四层，也坚持两条底线——① 业务逻辑不写在 Controller 里；② 业务层不直接依赖具体 ORM/框架 API。这两条成本极低但能避免大部分架构腐化。
