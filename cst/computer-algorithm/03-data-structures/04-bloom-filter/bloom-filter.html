第 03 章 · 数据结构概览

一定不存在，还是可能存在

布隆过滤器用位数组加多个哈希回答「一定不存在 / 可能存在」，给出误判率公式与参数选择，并说明为何不能删除。

它回答的是「一定不存在 / 可能存在」

布隆过滤器用一个位数组 + k 个哈希函数表示一个集合：插入时把 k 个位置置 1，查询时若 k 个位置全为 1 就说“可能存在”，只要有一位是 0 就断定“一定不存在”。它用极小的空间和可控的误判率，换掉了一张完整的集合表。

为什么只会有假阳性

  • 无假阴性：插入过的元素，它对应的 k 位一定都被置过 1，之后不会被清 0，所以查询必然全 1。
  • 有假阳性：没插入过的元素，它的 k 个位置可能被其他元素的插入“顺带”置 1，于是被误判为存在。
  • 所以布隆过滤器是单向的结论：说“不存在”就一定不存在（可放心拦截），说“存在”还需要回源确认一次。

它不适合任何要求 100% 准确的场景（权限校验、去重后必须精确计数）。它的价值在于挡掉绝大部分无谓的回源。

误判率与参数怎么定

设位数组长度 m、元素数 n、哈希函数个数 k，则某一位在插入 n 个元素后仍为 0 的概率约 e−kn/m，于是误判率：

p ≈ (1 − e^(−k·n/m))^k

在给定 m/n 时最优的 k = (m/n)·ln2，此时 p 最小。反过来，若希望 n 个元素下误判率不超过 p：

m = − n·ln p / (ln 2)^2        k = (m/n)·ln 2
n = 100 万，目标误判率 1%：m ≈ 9.6 × 10^6 位 ≈ 1.2 MB，取 k = 7。同样规模用 HashSet 存字符串，往往是几十 MB 起步。

经验法则：每位约 9.6 比特对应 1% 误判率；想降到 0.1%，每位大约要 14.4 比特。空间与误判率是指数关系，降一位数量级的误判率只多约 50% 空间。

典型用法

场景怎么挡收益
缓存穿透查询前先问布隆：不存在就直接返回，不再查库挡掉针对不存在 key 的攻击流量
爬虫 URL 去重抓之前判重，已抓过的直接跳过用极小内存记住亿级 URL
数据库/存储前置过滤LSM 树每个 SSTable 配一个布隆避免为不存在的 key 读盘
推荐/广告去重过滤已曝光内容允许极少量误判，换取内存

不能删除，以及替代方案

位数组不支持删除——把某一位清 0 可能影响其他元素。要支持删除就得换结构：

  • Counting Bloom Filter：把每个 bit 换成小计数器（通常 4 位），插入加一、删除减一。空间涨 4 倍左右，且计数器有溢出风险。
  • Cuckoo Filter：存指纹而不是位，支持删除，空间效率在误判率较低时优于布隆。
  • 定期重建：很多系统干脆不管删除，按天/按量重建一个新过滤器，滚动替换。

还有一个常被忽略的点：布隆过滤器不存元素本身，所以无法枚举、无法回表取原值，它只是一个“前置的门禁”。

第二层 · 参数·命令·量化：误判率公式与容量规划

布隆过滤器只有两个设计参数：位数组长度 m 和 哈希函数个数 k。它们决定误判率。

量公式说明
误判率 pp ≈ (1 − e^(−kn/m))^kn 为已插入元素数
最优 kk = (m/n) · ln2 ≈ 0.693 · m/n使误判率最小
最优 mm = −n·ln p / (ln2)²给定目标误判率反推容量
每元素位数m/n10 位/元素 → 误判率约 1%
每元素位数 m/n最优 k误判率内存（100 万元素）
107≈ 1%约 1.2 MB
1611≈ 0.1%约 2 MB
2014≈ 0.01%约 2.4 MB
86≈ 2%约 1 MB

容量规划计算

import math

def optimal_k(m, n):
    return max(1, round((m / n) * math.log(2)))

def optimal_m(n, p):
    return math.ceil(-n * math.log(p) / (math.log(2) ** 2))

def fp_rate(m, n, k):
    return (1 - math.exp(-k * n / m)) ** k

# 规划：100 万元素，目标误判率 1%
n, p = 1_000_000, 0.01
m = optimal_m(n, p)          # 约 9585058 bit ≈ 1.14 MB
k = optimal_k(m, n)          # 约 7
print(f"m={m} bit ({m/8/1024/1024:.2f} MB), k={k}, 实际误判率={fp_rate(m,n,k):.4%}")

# 使用示例（pybloom / redisbloom）
# Redis: BF.RESERVE myfilter 0.01 1000000
#        BF.ADD myfilter item ; BF.EXISTS myfilter item

量化结论：每个元素约 10 bit 就能把误判率压到 1%。对比哈希表（每元素数十字节），布隆过滤器省 1～2 个数量级的内存——这就是它用于缓存穿透防护、爬虫去重的原因。

第三层 · 排障与边界：布隆过滤器的四个坑

坑后果正确做法
以为可以删除标准 BF 不支持删除（多位共享）用 Counting Bloom Filter（计数器代替位），或定期重建
以为「存在」就是真的存在有误判（可能假阳性）BF 说「不存在」一定不存在；说「存在」要去后端确认
容量超了还在加误判率急剧上升按预估量 预留 2～3 倍，或分片 / 定期重建
哈希函数质量差实际误判率高于理论值用 murmur3 / xxhash；工程上常用「双哈希」模拟 k 个
用 BF 做精确去重数据会丢BF 只适合「快速排除绝不存在」，精确场景用 set
  • 排查顺序：先确认是否真的需要删除 → 再看实际插入量是否超过规划 → 再核对 k 是否取最优 → 最后实测误判率。
  • 边界一：布隆过滤器只可能假阳性，不可能假阴性——这是它最重要的性质。
  • 边界二：误判率随插入量超线性恶化：插入量翻倍，误判率远不止翻倍。务必预留容量。
  • 边界三：分布式场景下 BF 通常是本地的，多个实例的 BF 状态不同步；要全局一致就放 Redis（RedisBloom）。

误判率实测

# 实测误判率（与理论值对照）
import random, string
def rand_str(): return ''.join(random.choices(string.ascii_letters, k=12))

inserted = [rand_str() for _ in range(10000)]
# 用集合模拟「已插入」，用一个简单的 BF 实现测试...
fp = sum(1 for x in (rand_str() for _ in range(100000)) if x in inserted)
print("实测误判率:", fp / 100000)
为什么布隆过滤器不能删除元素？

因为多个元素共享位：某个 bit 被置 1 可能来自多个元素，清零它会影响其他元素的判断。解决办法是 Counting Bloom Filter——把 bit 换成小计数器，删除时减 1，代价是空间放大数倍。

缓存穿透用它怎么防？

把「所有合法键」预先灌进 BF。查询时先问 BF：说不存在就直接返回（一定不存在，不用打数据库）；说存在才去查缓存/DB。这样恶意请求随机键时，绝大多数被 BF 挡在第一层。

什么时候不该用布隆过滤器？

① 需要删除；② 需要零误判（资金、权限类）；③ 需要取出元素本身（BF 只存指纹不存数据）。这三类场景改用哈希表或数据库。

说“不存在”就能放心拦截，说“存在”还要回源确认——这就是布隆过滤器的全部契约。

一个「绝不说假阴性」的概率容器

布隆过滤器只有一个位数组和几个哈希函数，却能回答一个很有用的问题：这个元素「可能存在」还是「一定不存在」?

布隆过滤器的三种回答：一定不在 / 可能在 / 以及它的假阳性来源

两个公式和一组直觉数字

给定：n = 预计元素数，p = 可接受的假阳率 位数组长度： m = - n · ln p / (ln 2)² 最优哈希函数个数： k = (m / n) · ln 2 反过来算假阳率： p ≈ (1 - e^(-k·n/m))^k
每个元素分到的位数 m/n对应的假阳率直观
约 4.8 bit约 10 百分号很粗糙，只适合粗略过滤
约 9.6 bit约 1 百分号工程上最常见的区间
约 14.4 bit约 0.1 百分号要求较严格时用
约 19.2 bit约 0.01 百分号已经接近存哈希表的一半空间

记住这条性价比曲线就行：位宽每增加约 4.8 bit，误判率降一个数量级。想要再降一个数量级，就要再付出同样的空间。布隆过滤器的收益随空间线性，在空间二分之前就没有吸引力了。

哈希函数个数 k 不必是最优：k 偏大位被填满得快、假阳率上升但某些查询可能更快；k 偏小则相反。工程上取公式结果向下取整再加减 1 都不会显著变差，重要的是别差得太多。

最典型的应用：挡住缓存穿透

假设有人专门拿不存在的 ID 疯狂请求。每次都会穿过缓存打到数据库 —— 缓存命中率为 0，数据库直接被打满。

请求到来 ↓ 布隆过滤器：这个 key 是否存在？ ├─ 否 → 直接返回空。一次都不打数据库 ← 挡住的正是恶意随机 key └─ 可能 → 查缓存 ├─ 命中 → 返回 └─ 未命中 → 查数据库（这里才可能遇到真实的空值） └─ 数据库若确实没有，把「空值」也写进缓存并设较短 TTL 三层防护：① 布隆（挡随机 key） ② 空值缓存（挡重复同一 key） ③ 互斥回填（挡并发同 key）

注意两条实践要点：

  • 要有预热与重建机制。布隆过滤器在进程启动时是空的，直接上线会把所有请求都判为「不存在」。通常需要在启动时从数据库批量灌一遍。
  • 它是不可变小 watermarks。新增元素要同步 add 进去，删除元素（比如商品下架）在普通布隆里无法反映 —— 这时它只会多放行一些，不会错杀，可接受。

它被大规模用在存储引擎里：LevelDB / RocksDB 的每层 SSTable 都带一个布隆过滤器，读一个 key 时可以跳过绝大多数确定不含该 key 的文件，这是 LSM 树读放大能得到控制的关键一环。

几个常见错觉：

  • 「布隆过滤器能提速查询」 —— 它不存储数据，只用来避免不必要的查询。真正的提速来自「少做了」那些查询。
  • 「误判率是可配置的常数」 —— 它随插入数量增长而恶化。容量按实际增长估计，超出预设 n 之后假阳率会明显上升。
  • 「可以拿它做去重计数」 —— 它连元素本身都不存，更谈不上计数。做基数估算应该用 HyperLogLog 之类的结构。

深入自检

为什么不能从布隆过滤器里删除元素？

因为多个元素会共享同一个二进制位。当你把某位清零时，可能同时破坏了别元素的「存在标记」，从而把本来存在的元素误判成不存在 —— 这就违反了它最基本的性质（绝不能有假阴性）。想支持删除必须把位改成计数器（计数布隆），或用布谷鸟过滤器这类替没法方案。

位数组大小和哈希函数个数怎么先估？

先用业务量估 resham n（宁可估大，超了再扩成本高），再按目标假阳率算 m，最后用公式算 k。值得注意的是：这三个量是相互约束的，m 一旦定死，想更低假阳率只能控制在 n 或重构。多数实现会提供「按假阳率初始化」的接口，把这部分算封装掉。

和单纯「缓存空值」比有什么额外好处？

空值缓存只能挡住已经来过的同一批 key；布隆过滤器挡得下来从来没出现过的随机 key。攻击者可以用无限多个新 ID 打你，但吃掉的内存是固定且可控的那份位数组。这是它在反穿透场景不可替代的原因。

多个哈希函数要选不同的算法吗？

不必。常见做法是用两个高质量哈希 h1、h2，然后构造 gi = h1 + i·h2（double hashing）序列。这样理论上独立性足够，但只需要实现两套哈希。要求不高时甚至可以用同一哈希并加不同种子 —— 关键是让各位的置位尽量均匀且互相独立categor。
