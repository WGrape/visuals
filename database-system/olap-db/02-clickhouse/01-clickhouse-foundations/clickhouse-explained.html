一句话总结：ClickHouse 是一台为「大宽表 + 明细扫描 + 聚合」而生的列式 OLAP 引擎。 它快的核心不是某个银弹，而是四个设计叠加：列式存储、极其稀疏的主键索引、 后台异步合并的 LSM 式写入，以及贯穿全链路的向量化执行。

01它是什么，不是什么

✅ ClickHouse 擅长❌ ClickHouse 不擅长
几十亿～千亿行的明细表聚合（GROUP BY、SUM、COUNT）高并发点查（QPS 高的 KV 查询）
宽表 scan + 过滤，秒级返回单行 UPDATE / DELETE（弱支持，异步 mutation）
日志、埋点、时序、用户行为分析事务（无 ACID 事务）
实时写入 + 实时查询（追加为主）复杂多表 JOIN / 子查询（较弱，需改写）
高压缩比（10× 常见），省存储强一致、低延迟的主数据存储
定位提醒：ClickHouse 是分析引擎不是主数据库。它通常位于数据链路的下游—— 业务数据从 MySQL / 消息队列经 CDC 或 Flink 同步进来，供看板和 adhoc 查询使用。 不要拿它当业务库用。

02整体架构

图 1：ClickHouse 分层——Server 无状态可扩展，存储引擎是性能核心

几个关键概念

📦 Part

每次批量 INSERT 生成一个不可变的 Part 目录。Part 内数据按主键有序。 后台线程不断把小 Part 合并成大 Part。这是典型的 LSM 风格写入——写入只做顺序追加，代价转给后台合并。

🗂️ Partition

PARTITION BY toYYYYMM(date) 按月分区。 查询带分区条件时直接剪枝掉整个目录，是最有效的一级过滤。

🔑 Primary Key（排序键）

ClickHouse 的主键不是唯一约束，而是排序键——决定数据在 Part 内的物理顺序。 这是它最容易被误解的地方，详见「稀疏索引」一节。

🔄 Merge

后台合并同分区的 Part：去重（ReplacingMergeTree）、预聚合（AggregatingMergeTree）、 或单纯排序合并。合并是异步且幂等的。

03MergeTree 引擎家族

MergeTree 是基础引擎，加前缀/后缀衍生出适配不同语义的变体：

引擎额外行为典型用途
MergeTree基础：排序 + 分区 + 后台合并日志、事实明细表
ReplacingMergeTree合并时按排序键保留最后一行（去重）CDC 同步的 upsert 语义
AggregatingMergeTree合并时把多行预聚合成一行状态物化视图增量聚合

CollapsingMergeTree用 sign 列（+1/-1）抵消旧值需要精确更新的场景
ReplicatedMergeTree基于 ZooKeeper / Keeper 的多副本复制生产高可用必备
Distributed本身不存数据，是分片路由视图集群分布式表

04稀疏索引：最容易被误解的设计

MySQL 的 B+ 树索引能精确定位到每一行；ClickHouse 的主键索引是稀疏的—— 它只记录「每 index_granularity 行（默认 8192）的第一行的主键值」。

图 3：稀疏索引用极小的内存代价，把扫描范围缩小到 granule 级

由此推出的建表原则

  1. 主键 = 最常用的过滤/排序维度，按「基数从低到高」排列。 低基数列放前面，后续列的索引效果会被削弱。
  2. 分区键选时间（toYYYYMM 或 toDate），让按时间范围的查询直接剪掉整个目录。
  3. 不要建太多索引——主键只有一个，靠 ORDER BY 决定；额外的用 跳数索引（Data Skipping Index） 如 minmax、set、bloom_filter。
  4. 主键列尽量短，因为它决定了内存里 mark 的大小。

05查询执行：向量化流水线

ClickHouse 不用火山模型，而是推送式（push-based）向量化 pipeline： 数据以 Block（默认 8192 行，按列组织的连续内存）为单位在算子间流动。

图 4：向量化流水线——Block 在算子间批量流动，全程列式内存布局

此外还有两个关键优化：

  • PREWHERE：先只读过滤列的少量数据确定行号，再读其余列——延迟物化的教科书实现。
  • 多线程并行：Part 之间并行、Part 内按 granule 并行，把多核全部吃满。

06优势与常见坑

✅ 优势

· 扫描性能极强，压缩比高
· 写入吞吐高（顺序追加）
· SQL 兼容度不错，学习成本低
· 单机即可撑起 TB 级分析
· 生态成熟（物化视图、MySQL/HTTP 接口）

⚠️ 常见坑

· 不能高并发点查——每次查询都倾向吃满 CPU
· UPDATE/DELETE 是异步 mutation，不是实时生效
· JOIN 能力弱，大表 JOIN 容易 OOM，建议宽表化
· 没有事务，一致性靠上游保证
· 写入要批量（几千行一批），小批量写入会产生大量 Part 拖垮合并

Q：为什么我 INSERT 单行很慢，还报 "Too many parts"？
A：ClickHouse 每次 INSERT 都会生成一个 Part，单行插入意味着海量小 Part， 后台合并跟不上就会触发 Too many parts 报错。 正确做法是客户端攒批（建议 ≥ 1000 行/批，或每秒不超过 1 次写入）， 或用 Buffer 引擎 / Kafka 引擎在服务端缓冲。
Q：ClickHouse 的主键能保证唯一吗？
A：不能。它只是排序键，没有唯一约束。 要去重需要用 ReplacingMergeTree + ORDER BY， 但去重发生在后台合并时，所以查询时要用 FINAL 或 argMax() 才能保证结果正确——这也是一个常见陷阱。
