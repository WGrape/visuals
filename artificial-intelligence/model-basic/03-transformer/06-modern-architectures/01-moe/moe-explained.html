Transformer 架构

MoE 混合专家：为什么大模型参数暴涨却不爆算力

稠密模型每层全算；MoE 用「多个小专家 + 路由」替代，参数很多但每次只激活一小部分（稀疏激活）。Mixtral、DeepSeek 都靠它堆参数。本文讲清结构、路由与负载均衡。

一句话回答

MoE（Mixture of Experts）把每个前馈层换成 N 个并行小专家 + 一个路由。前向时路由只挑 top-k 个专家算，于是总参数很大，但单次推理激活的参数很少——用「参数多」换「表达强」，用「稀疏激活」保住「算力省」。

稠密 vs 稀疏激活

稠密模型
每层 FFN 对全部 token 全算。参数量 = 推理算力，想变强只能整体变大，算力线性涨。
稀疏 MoE
每层有 N 个专家，路由只激活 top-k（常 k=1 或 2）。参数量是 N 倍，激活算力只约 k/N。
激活参数量 ≈ 总参数 × (k / N)
关键收益：在相同推理算力下，MoE 的总参数量可以大几倍，从而容量更大、知识更多。

结构：专家 + 路由

把 Transformer 里的 FFN 层替换成 MoE 层：

  • 专家（Experts）：N 个结构相同但参数独立的 FFN（如 8 个）。
  • 路由（Router / Gating）：一个小线性层，对当前 token 输出 N 个分数，取 top-k 决定交给哪几个专家。

路由（Gating）怎么算

对 token 的隐藏状态 x，router 算 N 个 logits，softmax 后取 top-k：

weights = softmax(W_g · x)  →  选 top-k 个专家，权重归一化

输出 = Σ_{选中专家 e} weight_e · Expert_e(x)。

训练技巧 Noisy Top-k：训练时在 router logits 加一点噪声，防止路由过早锁定、让专家能被更公平地探索。

负载均衡：MoE 的头号难题

如果不约束，路由会偷懒——所有 token 都塞给一两个"明星专家"，其余专家饿死（专家坍缩），容量优势丧失。

解法两类：

  • 辅助损失（auxiliary loss）：鼓励各专家被选中频率均衡（如重要性均衡损失 + 负载均衡损失）。
  • 专家容量（expert capacity）：每个专家每批最多接 cap 个 token，超了的 token 走残差（被"丢弃"）。
负载不均是训练不稳和效果差的主因，工程上要精心调辅助损失权重和容量上限。

代表模型

Mixtral 8×7B
8 专家选 2，激活约 13B，效果对标 70B 稠密。
DeepSeek-V2/V3
细粒度 MoE + 共享专家，极致参数效率。
Qwen / 大模型
多代 MoE 版本，训推均用。

训练与推理的坑

维度说明
显存总参数全要驻留显存（哪怕不都激活），显存占用大。
通信专家常分片到多卡，路由带来频繁的 all-to-all 通信。
负载不均衡导致部分专家/设备成为瓶颈，批处理效率低。
微调路由对数据敏感，小数据微调易过拟合到少数专家。

总结

  • MoE = 参数多、激活少的稀疏结构，用容量换算力效率。
  • 路由 top-k + 归一化权重决定每个 token 走哪几个专家。
  • 负载均衡（辅助损失 + 专家容量）是成败关键。
  • 代表：Mixtral、DeepSeek、Qwen-MoE；代价是显存/通信/微调更复杂。

用「稀疏」换「容量」

标准的 Transformer 每个 token 都要过全部参数，这叫稠密（Dense）模型。想要更强的能力就加参数，但推理成本同时线性上涨。

混合专家（Mixture of Experts, MoE）换了个思路：把前馈层复制成很多份（专家），每个 token 只交给其中少数几个处理。参数总量变大了，但每个 token 实际激活的参数不变，于是实现了「容量大、推理快」。

MoE 的核心分流：路由选人 + 稀疏激活

三个必须说清的机制

① 路由怎么选

一个很小的线性层：把 token 的隐向量映射成每个专家的分数，取 Top-K（K=1 或 2 最常见）。分数通常先 softmax，最后把被选中专家的输出按权重加权求和，融合回主通路。

K 的选择很关键：K=1 最省但表达能力弱、训练不稳；K=2 是工程上的甜点，很多开源模型采用；K 再大就逐渐退化成 Dense。

② 负载均衡

如果放任路由器自由发展，会出现「塌缩」：少数几个专家被反复选中、其余永远闲置，等于白养了一堆参数。

主流做法是在损失里加一项辅助损失（auxiliary loss），惩罚「各专家被分配到的 token 比例偏离均匀」的情况，系数通常很小。此外还有专家容量（capacity factor）：给每个专家设一个处理上限，超出的 token 会被溢出到别处或直接跳过。

③ 专家并行

专家太多，一张卡装不下，就要把专家分散到多张 GPU/机器上。这时每个 token 需要先被送到它的专家所在设备（All-to-All 通信），算完再送回来。

这一步是 MoE 训练与推理的主要瓶颈：通信量随并行度上升，网络带宽往往比算力更早成为限制。工程上有专门的 kernel 融合与通信重叠来压这块开销。

近年常见的两个改进：共享专家（把 1~2 个专家设为所有 token 都过，专门承载通用知识，其余专家负责细分领域；这样路由专家可以更专注，减少重复学习）；细粒度专家（把专家切得更小、数量更多，组合空间更大，同等激活参数下表达力更强）。

MoE 与 Dense 的取舍

维度MoEDense
同等效果的推理成本通常更低（只激活一部分参数）更高
显存占用要装下全部专家，压力大相对可控
训练稳定性更敏感，需要负载均衡与精细的超参更稳，调参友好
微调与部署复杂度路由偏好和专家特化可能被破坏，需额外注意常规做法即可
批量推理的吞吐路由不均衡时会出现部分专家排队负载天然均匀
适合场景追求参数规模与推理成本比的服务显存受限、微调频繁、研究性实验

一句大白话概括：MoE 用「显存」换「算力」，并且把账单从「按参数付费」变成了「按 token 付费」。所以你会发现很多大参数的开源模型，实际跑起来的速度接近小得多的 Dense 模型 —— 这不是魔法，是稀疏激活。

深入自检

8×7B 是不是等于 8 个 7B 模型？

不是。这个记号表示该模型有 8 个专家、每个专家约 7B 参数量级，但注意力层、嵌入层等是共享的，且每次只用到其中 2 个专家。所以总磁盘/pyn显存远小于 8×7B，推理时激活的参数更接近 12~14B 量级。

为什么不干脆每个 token 用全部专家，权重不同？

那就是带权重的加权平均，等价于某种形式的门控融合，参数决定性和 sparse routing 相比仍有本质区别：只有当部分专家完全不参与计算时，才能省下真正的 FLOPs。软加权虽然理论上更平滑，但拿不到稀疏带来的算力收益，同时训练也更容易塌缩。

专家真的学到了「领域」吗？

部分学到了，但不要期待它是人类可读的「数学专家 / Python 专家」。实证观察到的特化更多出现在表层模式上：token 的形态、句法位置、语言种类、代码片段等。把它理解成「按输入特征做条件计算」比「按学科分工」更准确。

MoE 在微调时有什么坑？

主要有三个：① 小批次微调时路由样本不足，某些专家几乎不被访问，导致分布漂移；② 辅助损失权重没调好会在微调阶段重新坍塌；③ 专家并行下的 checkpoint 合并容易出错，保存/加载要特别小心。稳妥做法是微调时冻结或弱约束路由层、用更大的 batch、并在验证集上检查各专家的负载曲线。
