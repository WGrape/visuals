ClickHouse ReplacingMergeTree 去重：为什么刚写完还能查到两版

用同一订单的两条版本记录，解释排序键、后台合并、FINAL 与查询正确性的取舍。

先看同一订单的两次状态

订单 42 初始状态为“待支付”，版本号 1；一分钟后状态变为“已支付”，版本号 2。分析库把两条变化都写入 ReplacingMergeTree。此引擎在合并数据 Part 时，可依据 ORDER BY 定义的排序键识别相同逻辑行，并保留选定版本。若 ORDER BY 包含会变化的状态或时间戳，两条记录的排序键就不同，合并也无法把它们认成同一行。通常应把稳定的业务标识放在去重键语义中，并仔细设计 ORDER BY 与查询过滤。

ReplacingMergeTree 的后台合并是异步发生的。刚插入两条版本后，直接 SELECT count() 可能仍看到 2；“插入成功”并不代表旧版立即消失。即使后来合并，分区边界、Part 分布和查询方式也会影响读到的记录。必须先确定报表需要的是事件历史、当前状态，还是可容忍延迟的近似当前状态。

手推一次查询差异

假设两条数据的稳定排序键都是 order_id=42，version 分别为 1、2，金额都为 100，但状态不同。尚未合并的普通查询会返回两行；`count()` 得 2，`sum(amount)` 得 200。如果业务只想统计当前订单金额，显然不能把这两行直接求和。使用 `FINAL` 可在查询时应用相应去重语义，得到最新状态的一行；但查询时处理更多数据，可能显著增加 CPU 与延迟。具体行为要按表定义、版本列、分区和当前版本验证。

不写版本列时保留哪条记录可能受合并顺序影响，不能把“最后插入的一条”当作可靠业务版本。用单调业务版本号或更新序号表达新旧，并处理重复投递与乱序到达。若两个版本号相同但内容不同，需要定义冲突规则，不然合并结果无法稳定代表业务真相。

分区与删除的边界

同一逻辑订单的不同版本若被写入不同分区，常规后台合并通常只在分区内部工作，旧版可能不会按预期自动消失。常见错误是按可变的更新时间分区，导致同一订单跨月；即使查询加 FINAL，也要理解跨分区处理的实际设置与成本。分区设计应与生命周期、查询裁剪和去重范围一起决定。

删除也可用版本化墓碑表达，但最终是否返回已删除记录、何时物理清理，取决于引擎参数与查询写法。不能把逻辑删除立刻等同于释放磁盘。若要审计完整变更历史，保留所有事件的明细表与当前状态表可能比一张表兼任两种语义更清晰。

操作可能结果适用条件
普通 SELECT/SUM合并前可见多版接受暂时重复或查事件
FINAL 查询按引擎语义查询时去重需测扫描和并发成本
后台合并逐步减少旧版不能承诺实时完成
按版本构建当前层查询目标清晰维护版本与冲突规则

什么时候用查询时去重

报表必须读到当前准确状态时，可在查询中使用 FINAL，或构建按订单 ID 选最大版本的查询/物化状态。后者需注意聚合状态的正确合并与重复事件处理。大表全量 FINAL 有成本，先评估分区过滤、查询范围与并发。若是每日离线报表，可能接受等待合并后再计算，但等待并不是严格的正确性保证；后台合并何时完成受负载影响。

若指标本身是事件数，例如“支付状态变更次数”，就不该把旧版删除后再统计。建模时先给每个指标标明“事件”还是“实体当前快照”。把两种粒度混在一起，SQL 再复杂也补不回丢失的语义。

写入与查询验收步骤

建一张 ORDER BY order_id、带 version 的示意表，插入同一 order_id 的两条不同状态。立即查普通 SELECT、带 FINAL 的 SELECT，以及按 version 求最新的查询，对比行数与金额。再插入一次重复的 version=2 事件，检查重复投递是否产生多计。把更新时间跨分区的例子单独测试，确认实际分区策略不会让旧记录永久残留。

生产观测包含活跃 Part 数、后台合并队列、查询扫描行数、FINAL 查询延迟与磁盘占用。过多小 Part 会拖慢合并与查询；盲目执行昂贵的强制合并来追求“立刻去重”，可能影响整个集群。应按业务准确性需求选择查询时去重或独立当前状态层。

三句必须说清的边界

ReplacingMergeTree 的“Replacing”描述合并时的替换行为，不是事务式 UPDATE；ORDER BY 键定义哪些行会被视为同一逻辑行，不等于普通数据库的唯一约束；版本列帮助挑出新旧，不会自动修复错误分区或相同版本冲突。把这三句写到设计评审里，比只说“它支持去重”更能防止线上错账。

练习：订单 42 的待支付版与已支付版分别落在不同月份分区，报表按月统计当前订单金额。请说明直接 SUM、加 FINAL、重新设计分区或建当前状态表各自需要检查什么。

MergeTree 引擎家族对照

引擎合并时做什么去重/折叠粒度适用
MergeTree只合并排序，不处理重复无日志、明细（重复可接受）
ReplacingMergeTree(ver)保留 ORDER BY 键相同的一组中 ver 最大的行ORDER BY 键需要去重的明细表
SummingMergeTree把数值列求和ORDER BY 键只关心累加值的指标表
AggregatingMergeTree按 AggregateFunction 状态合并ORDER BY 键预聚合指标
CollapsingMergeTree(sign)按 sign 成对抵消（1/-1）ORDER BY 键可取消的状态更新
VersionedCollapsingMergeTree带版本的抵消，乱序也能正确折叠ORDER BY + version乱序更新场景

共同前提：合并是后台异步的，只在同一个 partition 内、同一个 part 合并时才发生。因此「插入后立刻查」可能仍看到重复行——这不是 bug，是使用方式问题。

建表与观测

-- 建表：ORDER BY 决定去重粒度（必须包含业务唯一键）
CREATE TABLE events
(
    id          UInt64,
    user_id     UInt64,
    amount      Decimal(18,2),
    version     UInt64 DEFAULT 0,      -- 版本号，保留最大的一条
    updated_at  DateTime
)
ENGINE = ReplacingMergeTree(version)
PARTITION BY toYYYYMM(updated_at)
ORDER BY (id);                         -- 去重键 = id

-- 观测 parts 状态
SELECT partition, name, active, rows, bytes_on_disk,
       formatReadableSize(bytes_on_disk) AS size
  FROM system.parts
 WHERE table = 'events' AND database = 'default'
 ORDER BY modification_time DESC LIMIT 10;

-- 正在进行的合并
SELECT table, elapsed, progress, num_parts, total_size_bytes_compressed
  FROM system.merges;

-- 强制合并（仅在维护窗口使用）
OPTIMIZE TABLE events FINAL;

查询时拿到“确定去重”结果的三种写法

写法语义代价适用
SELECT ... FINAL读取时做合并去重额外合并开销，大表明显正确性优先、量不大
argMax(col, ver) GROUP BY key显式取 ver 最大的行一次聚合，可控大表首选
预聚合表 / 物化视图写入时就折叠存储与写入逻辑成本固定查询模式

查询写法

-- 写法 1：FINAL（简单但可能有额外开销）
SELECT count() FROM events FINAL WHERE user_id = 42;

-- 写法 2：argMax 显式取最新版本（推荐，可控制）
SELECT id,
       argMax(amount, version)     AS amount,
       argMax(updated_at, version) AS updated_at
  FROM events
 WHERE user_id = 42
 GROUP BY id;

-- 写法 3：只关心最新 N 条时的过滤技巧
SELECT * FROM events
 WHERE (id, version) IN (
     SELECT id, max(version) FROM events GROUP BY id
 );

深入自检

为什么插入后立刻查询还会看到重复？

因为 ReplacingMergeTree 的去重发生在后台 part 合并时，而合并由系统调度、时机不确定，且只在同分区内发生。所以写入后到合并完成之间，重复行是可见的。要拿到确定的去重结果，需在查询侧用 FINAL 或 argMax。

ReplacingMergeTree 的去重粒度由什么决定？

由 ORDER BY（排序键）决定：只有 ORDER BY 键完全相同的一组行才会被折叠成一行。所以建表时必须把业务唯一键放进 ORDER BY，否则去重不会按你预期生效。

version 参数有什么用？

指定用哪一列作为版本号，合并时保留该列最大的那一行。没有它时保留哪一行是不确定的（通常是最后写入的，但不保证）。需要保留最新状态的表必须显式指定 version。

FINAL 和 argMax 怎么选？

FINAL 写起来简单，但会让 ClickHouse 在读取时额外执行合并逻辑，大表上开销明显；argMax 是一次显式聚合，能利用索引与并行，且语义清晰可控，生产中更推荐。固定查询模式还可以用物化视图在写入时预折叠，代价最低。

频繁出现 TOO_MANY_PARTS 说明什么？

说明写入批次太小太碎：每批数据都会生成一个 part，parts 数超过 parts_to_delay_insert（默认 150）就开始反压，超过 parts_to_throw_insert（默认 300）就拒绝写入。根治办法是客户端攒批（每批 ≥ 1 万行或 ≥ 10 MB），调大阈值只是缓解。

自检

ReplacingMergeTree 中插入 v2 后，普通 SUM(amount) 能立刻保证只算 v2 吗？

不能。后台合并异步，普通查询可能同时读到 v1 和 v2；需要按准确性要求设计查询时去重。
