什么时候适用？

判断信号：应用能控制缓存与数据库两端，并接受写后短暂旧值窗口。

  • 商品资料大量读取，编辑相对少：未命中时从数据库加载，并设置合理 TTL。
  • 订单摘要读取频繁：更新数据库后删除对应缓存键，下次读取重新构建。
  • 已有数据库访问层的服务逐步加缓存：只为被测量证明是热点的查询加回填。

和相近模式怎么区分？

相近方案选择边界
Read-Through缓存代理负责加载数据库；Cache-Aside 的应用必须写未命中、回填和失效逻辑。
Write-ThroughWrite-Through 的缓存层同步完成写库；Cache-Aside 的应用先提交数据库，再删旧缓存。

核心伪代码

function read(key):
  cached = cache.get(key)
  if cached != MISS: return cached
  value = db.get(key)
  cache.set(key, value, ttl)
  return value

function write(key, value):
  db.update(key, value)   // 先提交权威数据
  cache.delete(key)      // 再使旧缓存失效

需要更严格新鲜度时，可用版本号、条件回填或串行化关键路径；延迟双删只缓解特定时序，不提供强一致保证。

读时序

先查缓存；命中返回；未命中查 DB，写入缓存后返回。注意设置 TTL 兜底。

写时序

先更新数据库，再删除缓存（而非更新缓存）。下次读自动回填新值，避免并发写导致脏数据。

并发不一致窗口

“读未命中 → 查到旧 DB → 准备写缓存”期间，若发生写库+删缓存，旧值可能被回填进缓存。缓解靠延迟双删与较短 TTL。

🎯 面试问答

Q：为什么写时删缓存而非更新？
A：避免并发写导致缓存与 DB 不一致，删更稳妥。
Q：读未命中会引入脏数据吗？
A：在并发窗可能，靠延迟双删与短 TTL 缓解。
Q：Cache-Aside 最终一致吗？
A：是，依赖删除+回填最终收敛。
