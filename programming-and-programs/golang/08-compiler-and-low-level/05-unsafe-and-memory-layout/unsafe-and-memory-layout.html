unsafe 是「逃生舱」

它提供编译器级别的底层能力，但破坏类型安全、可能随版本/平台失效。只在性能极致或系统编程时才用。

字段顺序影响大小

Sizeof 返回类型占用字节；Alignof 返回对齐边界；Offsetof 返回字段相对结构体起始的字节偏移。

type T struct { a bool; b int64; c int8 }
unsafe.Sizeof(T{})   // 24（含对齐 padding）
unsafe.Offsetof(T{}.b) // 8（a 后填充到 8 对齐）
unsafe.Alignof(int64(0)) // 8
unsafe.Pointer

万能指针桥

unsafe.Pointer 可转为任意类型指针，也能与 uintptr 互转，从而在不同指针类型间「桥接」。它是 unsafe 的核心。

x := int64(10)
p := unsafe.Pointer(&x)
pi := (*int32)(p)   // 把 int64 地址当 int32 看（危险！）
转换规则（必须守）

否则未定义行为

规则：*T -> unsafe.Pointer -> *T2 合法；但 uintptr 只是整数，一旦参与运算（如 +Offset）就可能失效，因为它的指针语义不被 GC 保护。

现代 Go 用 unsafe.Slice / unsafe.String 等新 API 取代手写 uintptr 运算，更安全。
示例：深度相等

通用比较

利用反射 + unsafe 可实现一个「深度相等」函数：逐字节比较，绕过 Go 原生 == 只能比较可比较类型的限制。

// 思路：用 Sizeof 取得大小，把两个值按字节比较
func deepEqual(a, b unsafe.Pointer, n uintptr) bool {
    return *(*[1<<30]byte)(a)[:n] == *(*[1<<30]byte)(b)[:n]
}
忠告

能避则避

unsafe 代码不可移植、不安全、难维护；Go 版本升级可能破坏。优先用标准库；仅在序列化/系统编程等确有必要处使用，并加充分测试。

⚠️ unsafe.Pointer 与 uintptr 混用时，GC 不保证 uintptr 指向的对象存活，极易出现悬空指针。

结构体在内存里长什么样

Go 结构体的字段按声明顺序排列，但每个字段要满足对齐要求，编译器会在字段之间插入填充字节。字段顺序不同，占用大小可能完全不同。

同样的字段，不同顺序，24 字节 vs 16 字节
对齐每种类型有自然对齐值，地址必须是它的倍数。
填充为满足对齐而插入的空白字节。
重排大字段在前、同尺寸归堆，可减少填充。
尾部填充结构体尾部也可能补字节，使数组元素对齐。
import "unsafe" type A struct { b bool; n int64; m int32 } type B struct { n int64; m int32; b bool } unsafe.Sizeof(A{}) // 24 unsafe.Sizeof(B{}) // 16 unsafe.Alignof(A{}) // 8 unsafe.Offsetof(A{}.n) // 8（前面有填充）

string 不可变内容只读，可安全并发读、可安全共享
slice 共享底层数组截取后仍指向同一块，append 可能覆盖
append 可能扩容扩容后指向新数组，与原 slice 脱钩
大 slice 截断要小心保留小切片会拖住整个大数组不释放

经典泄漏：从一个很大的 slice 里截出一小段长期持有，底层大数组会被整块留住。需要独立副本时显式 copy 到新 slice。

unsafe.Pointer 的四条合法用法

用法写法风险
类型转换*T1 ↔ unsafe.Pointer ↔ *T2布局必须兼容，否则读到乱码
转 uintptr 做运算uintptr(p) + offset不能把结果存起来再用
与 syscall 交互传指针给系统调用调用期间对象必须保持存活
零拷贝转换[]byte ↔ string 互转得到的 string 不可再被修改
// ❌ 错误：把 uintptr 存起来再转回指针 u := uintptr(unsafe.Pointer(p)) // 此时 GC 可能已经移动或回收了 p 指向的对象 q := (*T)(unsafe.Pointer(u)) // 未定义行为 // ✅ 正确：转换在同一个表达式内完成 q := (*T)(unsafe.Pointer(uintptr(unsafe.Pointer(p)) + offset)) // ✅ 需要长期持有偏移位置时，配合 runtime.KeepAlive p := unsafe.Pointer(&s.Data) syscall.Syscall(..., uintptr(p), ...) runtime.KeepAlive(&s) // 保证 s 在调用期间不被回收

为什么 uintptr 不能存？uintptr 只是一个整数，GC 不把它当引用。对象失去引用就可能被回收或移动，那个整数就变成了野指针。必须在同一个表达式内完成「转 uintptr → 运算 → 转回指针」。

深入自检

用了 unsafe 是不是就失去 Go 的安全保证了？

是的，很大程度上。unsafe 让编译器不再保证内存安全与类型安全，可能出现越界、悬垂指针、与 GC 交互出错。它适合标准库与极少数性能关键处，业务代码应当慎用并集中封装。

[]byte 和 string 零拷贝转换安全吗？

转换本身只是重新解释头部，不拷贝数据，性能很好。但风险在于：得到的 string 若底层是 []byte，理论上可变；而 Go 假定 string 不可变。常见做法是用在只读场景，或用 unsafe.String / unsafe.Slice 这类更明确的 API，并且绝不修改底层数据。

结构体字段顺序真的值得优化吗？

只有当该结构体被大量创建时才值得。一个省 8 字节的结构体，在一百万个实例下省 8MB，并减少缓存未命中。对一个只创建几次的配置结构体做重排，只会损害可读性。

为什么 unsafe.Sizeof 和我想的不一样？

因为对齐填充。每个字段要放在其对齐值的整数倍地址上，编译器会插入 padding。用 unsafe.Offsetof 逐字段打印，就能看清填充分布。

atomic 操作对对齐有要求吗？

有。在 32 位平台上做 64 位原子操作，要求变量地址 8 字节对齐。最稳妥的做法是把 64 位字段放在结构体第一个字段，或使用标准库提供的原子类型（如 atomic.Int64），由标准库保证对齐。
