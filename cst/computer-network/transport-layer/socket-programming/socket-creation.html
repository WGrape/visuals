①Socket 文件是啥？——先分清两件不同的事

Linux 讲「一切皆文件」，Socket 也被抽象成了文件：你拿到的只是一个 int fd，可以用 read() / write() / close() 操作它，跟操作普通文件长得一模一样。但「Socket 文件」这个词其实对应两种完全不同的东西，混在一起就会晕。

网络 Socket（AF_INET / AF_INET6）

只活在内核内存里，磁盘上没有这个文件。它确实有一个 inode（挂在内核内部的 sockfs 伪文件系统上），但没有路径名，ls 永远看不到它。平时说「socket 是一个文件」，指的是「它能被当成文件来读写」这个使用方式，而不是磁盘上真有文件。

Unix Domain Socket（AF_UNIX）

磁盘上真的有一个文件。比如 Docker 的 /var/run/docker.sock、MySQL 的 /var/run/mysqld/mysqld.sock。ls -l 能看到，文件类型是 s（socket）。这才是字面意义上名副其实的「Socket 文件」——它是 bind() 时绑定到一个路径而创建的，只能同一台机器内的进程通信。

形象记忆：把 socket 想成「一条电话线路」，fd 只是你手里的「听筒编号」，内核里的 struct socket 才是线路本身。你要传数据只能拿到听筒编号（fd），线路的实体、状态、缓冲区全在内核。

②Socket 有哪些属性？

属性分三层看，层次清楚了就不会乱：用户态能看到的（少得可怜，就一个 fd 编号 + 几个开关）、socket 层属性（协议无关）、协议层属性（TCP/UDP 私有细节）。

面试最高频的其实是「四元组」：一条 TCP 连接由 （本机 IP，本机端口，对端 IP，对端端口） 四元组唯一确定。服务端 IP 和端口是固定的（它在一个端口上 listen），所以变化的只有「对端 IP × 对端端口」——这就是「服务端单机最大连接数 ≈ 2³² × 2¹⁶」这个理论值的推导来源。现实里远达不到，卡在两个瓶颈上：
  • 文件描述符上限——每个连接占一个 fd，Linux 单进程默认 1024（ulimit -n 可调）。
  • 系统内存——每个连接在内核都有 struct sock+缓冲区，占内存。C10K 问题问的就是「单机同时处理 1 万请求」。

③内核数据结构：从 int fd 一路挖到 struct tcp_sock

用户态那个 int，只是内核一条长链的入口。理解这条链，才能理解后面 fork / 线程为什么行为不同。

每层各自负责什么

1
struct file —— 「一切皆文件」的接入口
它的 f_op 指向 socket_file_ops，所以你调 read()/write() 时，VFS 会把请求转发到 socket 的读写函数。这一层让 socket「长得像文件」。
2
struct socket —— 协议无关的门面
记录「这是 TCP 还是 UDP、是 IPv4 还是 IPv6、处于什么状态」，持有 ops（指向协议实现）和 sk（指向下面那层）。还有一个等待队列 wq——你 accept() 或 read() 阻塞时，当前进程就睡在这个队列上。
3
struct sock —— 协议通用状态
收发缓冲区、socket 状态、归属信息、各种选项开关。它是 TCP/UDP 都能复用的「公共部分」。
4
struct tcp_sock —— TCP 私有细节
拥塞窗口、RTT 估计、发送/接收序号、重传队列……一条 TCP 连接在内核里的内存开销大头就在这，也是它能扛多少连接的关键。
关键结论（后面全靠它）：socket() 只是造出了「一个还没地址、没连接的空套接字」。它此时不能收发数据，必须经过 bind()/connect() 才有地址，经过 listen()+accept()（或 connect()）才有连接。connect() 和 accept() 的作用就是给这个空壳填上四元组。

④建立连接的完整流程：每一行代码内核做了什么

先把「一对一」的骨架走通，进程/线程方案只是在这个骨架上加了一层「谁去处理这条连接」。

服务端侧

1
socket(AF_INET, SOCK_STREAM, 0) —— 挖一条空线路
内核分配 struct socket + 一个 inode（挂 sockfs，无路径）+ 一个 struct sock（TCP 版）；在进程 fd 表里占一个坑，返回 int fd。此时没有 IP、没有端口、没有连接。
2
bind(fd, 0.0.0.0:8080) —— 给线路挂牌
绑端口：内核收到 TCP 报文后，靠报文里的端口号找到你的进程，再把数据交给你。绑 IP：一台机器可能有多个网卡、多个 IP，绑了哪个网卡，内核才把落到那个网卡上的包给你。绑 0.0.0.0 表示「所有网卡都收」。
3
listen(fd, backlog) —— 进入迎客状态
socket 状态变为 TCP_LISTEN，内核开始为它维护两个队列：半连接队列（收到 SYN、已回 SYN+ACK，等最后 ACK，状态 SYN_RECV）和全连接队列（三次握手完成，状态 ESTABLISHED，等应用 accept() 取走）。用 netstat/ss 就能查到这个端口在监听了。
4
accept(fd) —— 从队列里接走一位客人
全连接队列非空 → 取出一条已完成握手的连接；队列为空 → 阻塞睡眠（挂在该 socket 的等待队列 wq 上）。返回的是一个全新的 fd，对应内核里新建的 struct socket + struct file，它的 struct sock 带着对端地址、状态是 ESTABLISHED。

客户端侧

1
socket(...) —— 同样挖一条空线路
完全相同，得到一个无地址无连接的空套接字。
2
connect(fd, 服务端IP:端口) —— 发起连接
内核发出 SYN，进入 SYN_SENT，然后三次握手开始：SYN → SYN+ACK → ACK。握手完成后本端 socket 填上四元组，状态 ESTABLISHED。客户端一般不用 bind——不 bind 时内核会自动选一个本机 IP 和临时端口（ephemeral port）。
必须刻进脑子的一个区分：监听 Socket 和已连接 Socket 是两个不同的对象。
监听 Socket（listen fd）只干一件事——迎客，它永远不传数据；accept() 返回的已连接 Socket（conn fd）才是真正传数据的那个。一个服务端只有一个监听 socket，但每来一个客户端就会多一个已连接 socket。后面讲 fork / 线程时，「谁关哪个」就靠这个区分。

⑤进程方案 · 一个客户端 + 一个服务端

既然只有一个客户端，其实服务端不需要 fork，进程自己 accept 完自己处理就行。但我们要用「fork 版本」来讲，因为 fork() 复制 fd 表这个机制，是理解后面多客户端方案的地基。 
// server_fork_1v1.c —— 一对一，accept 后 fork，子进程服务客户
int listenfd = socket(AF_INET, SOCK_STREAM, 0);
bind(listenfd, ...);          // 绑 IP + 端口
listen(listenfd, 128);       // 进入 LISTEN，内核建两个队列

int connfd = accept(listenfd, &cli, &len);   // 从全连接队列取走一条，返回新 fd

pid_t pid = fork();          // 关键：复制父进程的 fd 表
if (pid == 0) {               // 返回值 0 → 这是子进程
    close(listenfd);           // 子进程用不到监听 socket，先关掉
    handle(connfd);            // 子进程用 connfd 和客户端通信
    close(connfd);
    exit(0);                 // 退出，等父进程回收
} else if (pid > 0) {        // 返回值 > 0 → 这是父进程（拿到子进程 PID）
    close(connfd);             // 父进程不处理这条连接，关掉自己这份
    waitpid(pid, NULL, 0);     // 回收子进程，避免僵尸
}

fork() 到底复制了什么？—— 复制的是 fd 表，不是 socket

这是最容易被忽略、但最关键的一点：

✅ fork 复制了

父进程的整张 fd 表副本。子进程的 fd 4 和父进程的 fd 4，指向同一个内核里的 struct file（也就是同一个 socket）。同时这个 struct file 的引用计数 +1（变成 2）。

❌ fork 没有复制

没有新建第二个 socket，也没有重建连接。父子俩面对的是同一条已建立的 TCP 连接，谁都能对它 read/write。

为什么父子必须各关一个 fd？

父进程 close(connfd)：不是为了断开连接（子进程还持有一份，连接不会断），而是减少引用计数。引用计数从 2 减到 1。如果父进程不关，它会一直攥着这个 fd 不放——fd 泄漏，而且客户端断开后连接资源也释放不干净。
子进程 close(listenfd)：子进程根本用不到监听 socket。如果不关，子进程存活期间一直占着它，监听 socket 的引用计数永远归不了零——服务想重启时就会报「端口已被占用」。
一句话：fork 之后，父子各自关掉「自己不需要的那一半」。

怎么区分父进程和子进程

fork() 返回值身份该干什么
0子进程close(listenfd) → 用 connfd 服务客户
> 0（子进程 PID）父进程close(connfd) → 回到 accept 等下一个；waitpid 回收
-1失败错误处理（进程数/内存超限）
一对一场景下，其实直接在主进程里处理更简单（省掉 fork 的开销和回收麻烦）。fork 的真正价值在下一节——当客户端变多、需要并发处理时。

⑥进程方案 · 多个客户端 + 一个服务端（每连接一进程）

最传统的并发模型：为每个客户端分配一个进程。父进程只负责 accept()「拉客」，每接进来一位，就 fork() 出子进程接待。父进程立刻回到 accept() 等下一个——所以它能同时接待很多客户端。
职责分离（图 4 的精髓）：父进程只关心监听 Socket，不碰已连接 Socket；子进程只关心已连接 Socket，不碰监听 Socket。各自 close 掉对方那份，让引用计数正确归零。

完整代码：加上僵尸进程回收

// server_fork_multi.c —— 一进程一连接
void reap(int sig) {           // SIGCHLD 处理函数：批量非阻塞回收
    while (waitpid(-1, NULL, WNOHANG) > 0) { }
}

int main(void) {
    signal(SIGCHLD, reap);       // 关键！子进程退出时通知父进程来收尸

    int listenfd = socket(AF_INET, SOCK_STREAM, 0);
    int on = 1;
    setsockopt(listenfd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof(on));
    bind(listenfd, ...);
    listen(listenfd, 128);

    for (;;) {
        int connfd = accept(listenfd, &cli, &len);   // 父进程只在循环里拉客
        if (connfd < 0) continue;

        pid_t pid = fork();
        if (pid == 0) {
            close(listenfd);                  // 子进程：先关监听 socket
            handle(connfd);                   // 处理业务（可能长时间阻塞）
            close(connfd);
            exit(0);
        }
        close(connfd);                       // 父进程：立刻关掉自己那份，回到 accept
    }
}

僵尸进程：不回收会耗尽资源

为什么会有僵尸？子进程退出后，它占的内存、fd 都释放了，但内核还保留一小块信息（退出状态、PID 等），等父进程来 wait 读取。父进程一直不读，这个「空壳」就一直在——这就是僵尸进程（Zombie）。僵尸本身不占多少内存，但占着 PID，数量一多就耗尽 PID 表 / 内核内存。
回收方式写法特点
wait()wait(&st)阻塞等任意一个子进程退出，收到一个就返回
waitpid()waitpid(pid, &st, 0)指定 PID 等待；加 WNOHANG 则不阻塞、没子进程退出就立刻返回
SIGCHLD + 循环 waitpid上面的 reap()生产推荐：子进程退出时内核发信号，父进程批量收，既不阻塞也不漏
signal(SIGCHLD, SIG_IGN)一行搞定显式告诉内核「我不关心」，内核自动回收。简单但要清楚它的副作用（拿不到退出状态）

局限：100 个还行，1 万个必挂

多进程模型在应对 100 个客户端时还能撑，但客户端涨到一万就不行了：
  • 每个进程都要占独立资源——地址空间、页表、栈、内核 task_struct，一万个进程光这些就很吓人。
  • 上下文切换代价很重——切换进程不只换用户态的虚拟内存、栈、全局变量，还要换内核态的内核栈、寄存器等内容。切换一次的开销远大于线程。
  • fork 本身有成本——虽然写时复制（COW）不用真的复制全部内存，但复制页表、复制 fd 表仍然要花时间。
  • 受 fd 上限约束——每个连接一个 fd，默认 ulimit -n = 1024，撑死 1024 个连接（还要减去标准输入输出等）。
所以进程方案的定位是：简单可靠、隔离性好（一个客户崩了不影响别人），适合中小规模。

⑦线程方案 · 一个客户端 + 一个服务端

把上一节的 fork() 换成 pthread_create()，思路完全一样，但有一个决定性的差异——线程共享同一张 fd 表。这个差异彻底改变了 close 的语义。 
// server_thread_1v1.c —— 一对一，accept 后开线程
void *worker(void *arg) {
    int connfd = *(int *)arg;      // 已连接 Socket（在主线程里是同一个编号）
    handle(connfd);
    close(connfd);                // ⚠️ 这个 close 是"真关"，见下方说明
    return NULL;
}

int listenfd = socket(AF_INET, SOCK_STREAM, 0);
bind(listenfd, ...); listen(listenfd, 128);

int connfd = accept(listenfd, &cli, &len);

pthread_t tid;
pthread_create(&tid, NULL, worker, &connfd);   // 开一个线程去处理
pthread_detach(tid);        // 让线程退出后自动回收，避免"线程版僵尸"
continue;                    // 主线程回去 accept 下一个
线程方案最关键的一句话：pthread_create() 默认带 CLONE_FILES 标志 → 新线程和主线程共享同一张 fd 表，不是复制一份。
这意味着：线程里看到的所有 fd 编号，就是主线程看到的那些 fd 编号，没有"我这份 / 你那份"的区别。

于是 close 的语义完全变了

进程方案（fork）线程方案（pthread）
fd 表复制一份副本，父子各一张共享同一张（CLONE_FILES）
同一个 socket 的引用父 fd 4 + 子 fd 4 两份引用只有一份引用，大家看的都是它
close(fd) 的效果只减引用计数，连接不会断（对方还持有）直接关闭，全进程所有线程都会受影响
能不能「子关 listenfd」图省事✅ 可以，只影响子进程❌ 绝对不行！会把监听 socket 关掉，整个服务当场毙命
close 的责任归属父子各关自己不需要的必须约定清楚谁负责关，不能多人重复关
这是线程方案最容易踩的坑：照抄进程方案的代码，在线程里写上 close(listenfd)，结果监听 socket 被真的关掉了——后续所有客户端都连不上，服务等于挂了。线程里不需要关监听 socket，因为它本来就是"大家共用的"，也没有多出来的引用需要清理。

线程的优势与代价

✅ 更轻

创建/销毁线程比进程快得多；上下文切换不用换地址空间（不换页表），切换成本明显更低。

✅ 通信方便

共享地址空间，数据直接就能互相看见，不用像进程那样上管道/共享内存。

❌ 隔离差

一个线程段错误（如野指针）会拖垮整个进程——所有连接一起断。进程方案则只影响单个子进程。

❌ 要加锁

共享数据有竞态，得用互斥锁保护；锁用不好就死锁或性能反降。

⑧线程方案 · 多个客户端 + 一个服务端

最直接的写法：每来一个连接就开一个线程（one thread per connection），主线程只负责 accept()。再进一步是线程池——预先开好固定数量的线程，用任务队列分发连接。两者本质都是「一个连接由一个线程独占处理」。

写法一：一连接一线程（+ detach）

// server_thread_multi.c —— 每连接一个线程
void *worker(void *arg) {
    int connfd = *(int *)arg;
    free(arg);                    // 堆上的 connfd 副本，用完释放
    handle(connfd);
    close(connfd);               // 谁处理谁关闭，约定清楚就不会重复关
    return NULL;
}

while (1) {
    int connfd = accept(listenfd, &cli, &len);
    if (connfd < 0) continue;

    int *p = malloc(sizeof(int));   // ⚠️ 必须 malloc！见下方说明
    *p = connfd;

    pthread_t tid;
    pthread_create(&tid, NULL, worker, p);
    pthread_detach(tid);          // 线程退出后自动回收资源
    // 注意：这里不 close(connfd)，交给 worker 线程关
}
两个必须注意的坑：
  1. 传参数要用 malloc 或数组：如果写成 pthread_create(&tid, NULL, worker, &connfd)，把 connfd 的地址传进去，那主线程下一次 accept() 会覆盖掉这个变量。更糟的是多个线程拿到同一个地址，导致好几个线程处理同一条连接、另一条连接没人管。所以每个连接要一份独立的内存。
  2. pthread_detach 不能忘：线程默认是「joinable」的，退出后要有人 pthread_join 才释放资源；没人 join 就变成线程版的僵尸，一直占着栈和线程控制块。detach 或 join，二选一必须做。

写法二：线程池（固定线程数 + 任务队列）

一连接一线程的问题：客户端一多就开一堆线程，线程创建本身有开销，而且并发数不可控（瞬间涌入 1 万个连接 = 1 万个线程 = 崩）。线程池解决这个：预先开固定 N 个线程，把「待处理的连接」放进队列，谁空谁取。

// 线程池骨架：固定线程数，用条件变量 + 队列分发
int   queue[1024];            // 待处理连接队列（环形或链表）
int   head, tail;
pthread_mutex_t mtx = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  cv  = PTHREAD_COND_INITIALIZER;

void *worker(void *arg) {
    for (;;) {
        pthread_mutex_lock(&mtx);
        while (head == tail)                       // 队列空就睡在条件变量上
            pthread_cond_wait(&cv, &mtx);
        int connfd = queue[head++ % 1024];        // 取一个连接
        pthread_mutex_unlock(&mtx);

        handle(connfd);                            // 在锁外处理，避免阻塞别人
        close(connfd);
    }
}

// 启动时开 N 个线程，之后主线程只负责把 connfd 塞进队列
void dispatch(int connfd) {
    pthread_mutex_lock(&mtx);
    queue[tail++ % 1024] = connfd;
    pthread_cond_signal(&cv);                    // 唤醒一个睡着的线程
    pthread_mutex_unlock(&mtx);
}
线程池的好处：线程数可控（并发上限 = 线程数，防止被打爆）、省掉频繁创建销毁、复用线程栈。代价：队列满了要决定策略（阻塞？丢弃？拒绝？）——这就是「有界队列 + 拒绝策略」的经典问题。

线程能开到多少？

  • 线程栈是主要限制：Linux 默认每线程栈 8MB 虚拟空间，开 1000 个线程光栈就占 8GB 虚拟地址（实际物理内存按需分配，但虚拟空间和页表开销仍在）。可用 ulimit -s 或 pthread_attr_setstacksize 调小（比如 256KB），能把上限提高很多。
  • 上下文切换：线程虽比进程轻，但线程数一多，内核在它们之间调度的开销也会累积，吞吐反而下降。
  • 实际经验：一连接一线程/进程通常能撑到几百 ~ 几千。再往上（万级 C10K）就该换 IO 多路复用（epoll）了——用少量线程 + 事件驱动处理海量连接，这是「进程/线程方案」之后的下一个台阶。

Q：进程方案和线程方案，选哪个？
「一个客户崩了不能影响别人」→ 进程；「连接多、要省资源」→ 线程（+ 线程池）。现实中多数是组合：多进程 + 每进程多线程 + 每进程 epoll，既利用多核，又控制单进程崩溃的影响面（Nginx 就是「多 worker 进程 + 每进程事件驱动」的典型）。
Q：为什么进程方案要「父关 connfd、子关 listenfd」，线程方案却不能这么干？
因为 fork 复制了 fd 表，同一个 socket 有两份引用，父子各关一份正好把引用计数清零，谁也不影响谁。而线程共享一张 fd 表，只有一份引用——线程关掉 listenfd 就是真的关掉了，所有线程都会遭殃。
Q：为什么 accept 返回的 fd 和监听 fd 不是同一个？
因为它们是内核里两个不同的 struct socket。监听 socket 状态是 LISTEN、没有对端地址，只负责在队列里接客；accept() 从全连接队列取出一条已完成握手的连接，会为它新建 struct socket + struct file + fd，状态 ESTABLISHED、带完整四元组。职责单一，隔离清晰。

⑩一句话速记

① Socket 文件：网络 socket 只是「能被当文件读写」的内核对象（有 inode、没路径、磁盘上看不见）；只有 Unix Domain Socket 才有真正的磁盘文件（.sock，类型 s）。
② 属性：用户态只有 fd；内核里是「地址族 / 类型 / 本地地址 / 对端地址 / 状态 / 缓冲区 / 选项 / 引用计数」的集合，其中四元组唯一确定一条连接。
③ 数据结构：fd → files_struct → struct file → struct socket → struct sock → struct tcp_sock，五层一路挖下去。
④ 创建：socket() 造空壳 → bind() 给地址 → listen() 变 LISTEN + 建两个队列 → accept() 取出已连接 socket（新 fd）；客户端 connect() 触发三次握手。
⑤ 四种方案的分水岭只有一个：fd 表是「复制」还是「共享」。fork 复制 → 父子各关一半、互不干扰；pthread 共享 → close 影响全进程、绝不能关监听 socket。

本文基于 Linux 内核 socket 实现（struct socket / struct sock / sockfs）与 POSIX socket 编程接口整理；不同内核版本与发行版的默认参数（如 fd 上限、线程栈大小）可能有差异，请以实际系统为准。
