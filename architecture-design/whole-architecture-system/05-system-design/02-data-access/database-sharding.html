整体架构系统 · 设计原则

分库分表 / 数据分片

单库扛不住时，把数据按规则拆到多个库/表，水平扩展容量与性能。

分片拓扑 Sharding

一次请求按分片键定位目标分片；跨片查询可能扇出到多个分片

当数据库实例的容量或吞吐经测量不足时，可按分片键把数据分到多张表或多个实例。路由层负责定位目标分片，业务仍需处理热点、跨片查询、事务与扩容迁移。表分区和跨实例分片的边界见分区与分片机制对比。

分片键选择

  • 选高频查询维度，让大部分请求落单分片。
  • 避免数据倾斜（某 key 过热）。
  • 避免跨分片 join / 分布式事务——能避免就设计掉。

代价

  • 跨分片查询/聚合变复杂（需汇总多个分片）。
  • 扩容需数据再平衡（一致性哈希可减迁移量）。
  • 分布式事务更难。

面试高频问答

Q：分库分表和读写分离能一起用吗？
A：能，且常叠加：先按业务/分片键分库分表解决容量，再对每个分片做主从读写分离解决读压力。两者解决不同维度问题。
Q：一致性哈希在分片里的价值？
A：扩容加节点时，一致性哈希只需迁移邻近部分数据而非全量重分布，大幅降低再平衡成本与抖动。

分库分表：什么时候才该做

分库分表是「最后的手段」，不是首选。它带来分布式事务、跨片查询、扩容迁移、运维复杂度四座大山。正确的顺序永远是：先优化索引与 SQL → 加缓存 → 读写分离 → 归档历史数据 → 最后才考虑分片。

垂直拆分按业务把一张宽表拆成多张表 / 把不同业务拆到不同库，先做这个
水平分表同库内把一张大表按规则拆成 N 张结构相同的表，解决单表数据量过大
水平分库把数据分散到多个数据库实例，解决单机 CPU / 内存 / 连接 / IO 瓶颈
分片键决定一行数据落在哪个片的字段，选错就是灾难且极难更改
水平分库 + 分表：先按分片键路由到库，再在库内路由到表

分片键怎么选（最重要的一步）

分片键决定了三件事：数据是否均匀、查询是否能单片命中、未来扩容是否好做。判断标准是「最高频的查询是否都带这个字段」——如果 80% 的查询都带 user_id，就用 user_id。

候选分片键优点风险
user_id（最常见）同一用户的数据在一片，查「我的订单」单片命中，天然避免跨片大客户会造成数据倾斜（热点用户）
order_id / 业务主键分布最均匀，写入无热点按用户查要跨所有片，必须建立映射表或基因法
tenant_id（SaaS）租户级隔离，单租户查询单片，便于独立扩容与计费大租户倾斜；跨租户统计困难
时间（按月分表）冷热分离清晰，归档就是删表，历史查询范围明确写入永远打在最新一片，形成写热点；跨月查询要 UNION
地理 / 区域就近访问延迟低，符合数据合规要求用户迁移区域后数据要搬迁；跨区域查询慢

缓解倾斜的两个技巧：① 基因法——把 user_id 的若干位「遗传」进 order_id（order_id = 序列 + user_id % N），这样用 order_id 分片的同时，同用户的订单仍落在同一片；② 大客户独立分片——给头部客户单独一片甚至单独库，其余走通用规则。

分片算法对比

取模 hash(key) % N

最直观，分布均匀。致命伤是扩容要重分布：N 从 3 变 4，绝大部分数据都要搬家。

  • 适合：规模稳定、可接受停机迁移的场景
  • 缓解：初期就按 2 的倍数或较大 N 预留（如 16 库 × 64 表），扩容时只做整库搬迁

一致性哈希

把 key 和节点都映射到 0~2^32 的环上，扩容只影响环上相邻的一小段数据（约 1/N）。

  • 适合：节点频繁增减的缓存集群
  • 数据库很少直接用，因为跨片查询与事务本身就够复杂了

范围分片

按 key 区间划分，如 user_id 1~1000万 一片。扩容只需新增区间，无需搬迁旧数据。

  • 优点：扩容友好、范围查询单片命中
  • 缺点：单调递增的 key（如自增 id、时间戳）会让写集中到最新片

查表路由（配置中心）

用一张路由表显式记录 key → 分片 的映射，灵活度最高。

  • 优点：可手工调整倾斜、支持任意策略组合
  • 缺点：多一次查询（可缓存）；路由表本身要高可用

分片之后绕不开的四个问题

  • 跨片查询。不带分片键的查询要广播到所有片再归并，分页尤其痛（LIMIT 100000,20 会让每片都取 100020 行）。解法：建立异构索引（把数据同步到 ES / 宽表），或用「禁止此类查询」的产品约束。
  • 跨片排序分页。必须在内存中归并排序，深分页用「上一页最大值 + 游标」替代 offset。
  • 分布式事务。优先用「最终一致 + 补偿」（本地消息表 / 事务消息 / Saga），强一致才用 XA 或 TCC，且要接受吞吐下降。设计上应尽量让同一事务只落一片。
  • 全局唯一 ID。自增 id 在多片下会冲突，改用雪花算法（时间戳 + 机器位 + 序列）、号段模式（Leaf-segment）或数据库发号器。
// 雪花算法 64 位结构 0 | 000...000(41bit 毫秒时间戳) | 00000(5bit 数据中心) | 00000(5bit 机器) | 000000000000(12bit 序列) // 单机每毫秒可产生 2^12 = 4096 个 ID；注意时钟回拨问题，需缓存上次时间戳并在回拨时等待或报错

扩容不停机：双写迁移法

从 N 片扩到 M 片不能靠「停机导数据」。标准做法是双写 + 影子迁移，分五步：

① 上线双写新数据同时写旧分片与新分片，读仍走旧
② 全量搬迁后台任务按分片键把历史数据导入新分片
③ 增量追平用 binlog 或按更新时间补跑搬迁期间的增量
④ 灰度校验随机抽取记录比对新旧两套数据，统计不一致率
⑤ 切读下线读逐步切到新分片，观察稳定后关闭双写与旧分片

为什么必须双写：只做「全量搬迁 + 追增量」会有一个窗口期，期间写入可能落在已被搬走的数据上，双写保证新旧两套在任何时刻都包含最新数据，切换时无需停写。

深入自检

单表多少行才该分表？

没有魔法数字，取决于行宽与访问模式。经验值：InnoDB 单表 B+ 树层数控制在 3~4 层时性能最佳，行宽 200B 左右的表，2000 万~5000 万行是常见拐点。更准确的判断看三个信号：① 索引无法全部载入 buffer pool，磁盘随机 IO 明显上升；② DDL（加字段、加索引）耗时不可接受；③ 备份恢复时间过长。如果查询都命中索引且 IO 不是瓶颈，1 亿行不分表也未必有问题。

分库和分表哪个先做？

先垂直拆分（按业务分库），再水平分表，最后水平分库。垂直拆分风险最低、收益最快，能把不同业务的故障和容量压力隔离开。水平分库成本最高（引入分布式事务和跨库查询），只有当单机 CPU/连接/IO 真的扛不住时才做。很多场景下「分表不分库」就已经够用——同一实例内跨表查询还能 JOIN。

为什么分片后自增主键不能用？

每个分片的表各自维护自增计数器，db_0 和 db_1 都会产生 id=1 的记录，合并时主键冲突。另外自增 id 会暴露业务量、且无法在写入前预知，不适合做分库分表的关联键。改用全局 ID 生成器，并让 ID 本身携带分片信息（基因法），可以大幅简化后续查询。

跨片 JOIN 一定不能做吗？

能做，但要分类处理：小表（字典、配置）做「广播表」——每片都存一份全量，JOIN 时本地完成；同分片键的两张大表做「绑定表」——用相同规则分片，同键值必然在同一片，可本地 JOIN；真正的跨片 JOIN 要在中间件做笛卡尔积归并，数据量一大就爆炸，应通过宽表冗余或异构索引（ES）规避。
