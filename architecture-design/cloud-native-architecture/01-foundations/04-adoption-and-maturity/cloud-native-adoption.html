01落地路径与成熟度评估

  1. 容器化：应用与依赖打包成镜像，统一交付物。
  2. CI/CD：建立自动化构建、测试、镜像推送流水线。
  3. 编排上 K8s：用声明式 YAML 描述部署，获得自愈与弹性。
  4. 可观测性：指标、日志、链路三件套，让故障可定位。
  5. 服务治理：按需引入服务网格，处理流量、安全与熔断。
  6. 进阶：Serverless、GitOps、多集群、混沌工程。
Q：我们该上云原生吗？
A：看三个信号——① 发布频率需要提升到每周以上； ② 流量波动大、需要自动弹性； ③ 团队规模扩大、需要独立部署与解耦。
反过来说，如果应用是稳定的单体、流量平稳、团队很小，盲目微服务化 + 上 K8s 只会显著增加复杂度与运维负担。 云原生是手段不是目的。

02常见疑问

Q：用了 Kubernetes 就是云原生了吗？
A：不是。K8s 只是编排工具。如果应用仍是单体、手工改 YAML、没有自动伸缩、 没有可观测性、发布靠人肉，那只是"用 K8s 跑了传统应用"。 真正的标志是自动化闭环：声明期望状态 → 系统自动调谐 → 异常自动自愈 → 指标驱动伸缩。
Q：云原生和"上云"的成本对比如何？
A：云原生前期投入明显更高（需要重构、建流水线、建可观测体系、培养运维能力）， 但规模化后边际成本更低：资源利用率提升、发布效率提升、故障恢复自动化。 小团队/稳定业务往往不划算，规模化的多服务系统收益显著。
Q：十二要素（12-Factor）在云原生里的位置？
A：它是云原生应用的设计方法论（无状态进程、配置外置、日志当事件流、端口绑定等）， 早于 K8s 出现，但思想完全兼容并被 K8s 落地。详见本学科《十二要素》一篇。
