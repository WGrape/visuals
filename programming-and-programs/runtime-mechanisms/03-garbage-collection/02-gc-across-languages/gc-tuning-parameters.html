02Go：两个环境变量就够

\n
参数默认含义建议
GOGC100堆相对上次 GC 后存活量增长 100% 触发内存紧调到 50；CPU 紧调到 200~400
GOMEMLIMIT无上限软内存上限，到了会加强回收设成容器 limit 的 80%~90%
GODEBUG=gctrace=1关闭每次 GC 打一行日志临时排查开，别常开
GOGC=off—关闭自动 GC（配合 memory limit）只在短期批处理任务用
# 容器里最实用的一条：设软上限，让运行时自己压着用\nGOMEMLIMIT=800MiB GOGC=100 ./app\n\n# 看 GC 到底发生了什么（每行末尾是暂停与堆变化）\nGODEBUG=gctrace=1 ./app 2>&1 | head\n# 输出示例：gc 3 @0.043s 4%: 0.015+2.0+0.003 ms clock, ...\n#   4%       → GC 占用的 CPU 比例\n#   heap 变化 → 看回收是否有效（回收后堆没降 = 有泄漏）\n\n# 更推荐：直接看 runtime/metrics 或 pprof\ncurl -s localhost:6060/debug/pprof/heap > heap.out\ngo tool pprof -http=:0 heap.out\n\n# 程序内读取关键指标（写进监控）\nimport \'runtime/metrics\'\n// /gc/cycles/total:gc-cycles   GC 次数\n// /gc/pauses:seconds           暂停时间分布\n// /memory/classes/heap/objects:bytes  堆内对象
要点：Go GC 的目标不是「回收最干净」，而是「在可控 CPU 开销内把堆压在目标之下」。所以有了 GOMEMLIMIT，很多场景根本不需要再动 GOGC。

\n
运行时参数常见值说明
JVM-Xms / -Xmx设成相同值避免运行时扩缩容抖动
JVM-XX:MaxGCPauseMillis100~200G1 的暂停目标，是目标不是保证

# JVM：看 GC 日志与暂停分布（JDK 9+ 统一日志）\njava -Xms2g -Xmx2g -XX:+UseG1GC -XX:MaxGCPauseMillis=200 \\\n     -Xlog:gc*:file=gc.log:time,uptime:filecount=5,filesize=20m -jar app.jar\n# 判读：看 GC 总耗时占运行时长的比例，> 5% 就该看堆使用曲线了\n\n# Python：看分代计数与回收统计\nimport gc\nprint(gc.get_count())      # 各代待检查对象数\nprint(gc.get_stats())      # 各代回收次数\ngc.set_threshold(1000, 15, 15)   # 调大 → 扫描更少、内存更高\n\n# 启动后冻结，把常驻对象移出扫描范围（能明显减少 GC 工作量）\ngc.freeze()\n\n# 找循环引用导致的泄漏\ngc.set_debug(gc.DEBUG_LEAK)
    \n
  • JVM 的堆曲线要看「GC 后的低点」：低点持续抬高就是泄漏，与 Go 的判读方式一致。

  • Python 的内存不降多数不是 GC 问题： pymalloc 的 arena 不还给系统，看 RSS 容易被误导，要看对象数。

  • 三种语言共同点：调参能改善抖动，但解决不了「对象真的还在被引用」。泄漏只有改代码能修。

04排障顺序与判断阈值

\n
    \n
  1. 先看堆曲线形状：锯齿（正常）／单调上升（泄漏）／高位平台（缓存太大）。
    2. \n
  2. 再看GC CPU 占比：Go 看 gctrace 的百分比，JVM 看 GC 日志；超过 10% 说明分配太猛。
    3. \n
  3. 然后看暂停分位：P99 暂停超过业务超时的一半，就要为它让路（调阈值或换 GC）。
    4. \n
  4. 最后才动参数：先设上限保命，再按上面两项指标决定调哪个旋钮。
    5. \n
  5. 改完必须对比压测：同一压力下看吞吐、P99 延迟、RSS 三项，缺一不可。
    6. \n
问：为什么调大 GOGC 后内存涨了但延迟没改善？

说明瓶颈不在 GC 次数，而在单次暂停或分配速率本身。这时应该查分配热点（pprof 的 alloc_space），减少分配，而不是继续调 GC。

问：GOMEMLIMIT 设了为什么还是被 OOM kill？

因为它是软限制，只约束 Go 堆；栈、mmap、C 侧内存、内核页缓存都不算在内。容器 limit 与 GOMEMLIMIT 之间要留 10%~25% 余量。

问：什么时候应该减少分配而不是调 GC？

几乎总是。调 GC 是「让回收更勤/更懒」，减少分配才是从源头减负：复用对象、避免接口装箱、预分配 slice 容量、用 sync.Pool 缓存大对象。
