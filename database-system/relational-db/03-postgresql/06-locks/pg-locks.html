锁机制

表级锁、行级锁（无间隙锁）、advisory lock，以及死锁处理。

① 锁的三个层次② 表级锁模式与冲突矩阵③ 行级锁与死锁④ 咨询锁（Advisory Lock）⑤ 排查阻塞的实战 SQL⑥ 常见问法

① 锁的三个层次

表级锁

由 LOCK TABLE、DDL、VACUUM FULL、某些 DML 触发；8 种模式，冲突关系见下表

行级锁

由 SELECT FOR UPDATE/SHARE、UPDATE/DELETE 触发；不阻塞读（MVCC），只阻塞互相冲突的写

咨询锁 Advisory Lock

应用自定义的锁，与表无关；用于分布式任务互斥、防并发重复执行

页级 / 内存锁

LWLock、spinlock 等内部锁，一般不直接暴露给 DBA，可通过等待事件观察

关键认知：PostgreSQL 的读不阻塞写、写不阻塞读——因为 MVCC 让读者看快照。真正会互相阻塞的是写与写（同一行的 UPDATE/DELETE）以及 DDL 与一切（强排他锁）。

② 表级锁模式与冲突矩阵

生产事故高发点：一条 ALTER TABLE ... ADD COLUMN（尤其带默认值或 SET NOT NULL）会拿 ACCESS EXCLUSIVE 锁。若此时有一个跑了 10 分钟的长查询持有 ACCESS SHARE 锁，DDL 会排队等待，而后续所有新查询都会排在 DDL 后面——瞬间造成全表不可用。对策：给 DDL 加 lock_timeout 与 statement_timeout，并先查是否有长事务。
-- 上线 DDL 的稳妥写法
SET lock_timeout = '3s';       -- 拿不到锁就放弃，避免阻塞雪崩
ALTER TABLE orders ADD COLUMN note text;   -- PG 11+ 无默认值是瞬时的

③ 行级锁与死锁

锁类型触发语句冲突对象
FOR UPDATESELECT ... FOR UPDATE、UPDATE、DELETE其他 FOR UPDATE / FOR NO KEY UPDATE / FOR SHARE
FOR NO KEY UPDATEUPDATE（不改主键/唯一键列时）FOR UPDATE、FOR SHARE
FOR SHARESELECT ... FOR SHAREFOR UPDATE、FOR NO KEY UPDATE
FOR KEY SHARESELECT ... FOR KEY SHARE、外键检查仅 FOR UPDATE

死锁：两个事务互相等待对方持有的锁。PostgreSQL 默认在 deadlock_timeout（默认 1s）后检测死锁并回滚其中一个事务（报 40P01）。

-- 经典死锁：两个事务以相反顺序更新两行
-- T1: UPDATE a SET ... WHERE id=1;  UPDATE a SET ... WHERE id=2;
-- T2: UPDATE a SET ... WHERE id=2;  UPDATE a SET ... WHERE id=1;
-- 对策：所有业务按「同一顺序」访问资源（如按 id 升序排序后更新）

-- 用 SELECT FOR UPDATE 显式排序，避免死锁
BEGIN;
SELECT id FROM orders WHERE id IN (3,1,2) ORDER BY id FOR UPDATE;
UPDATE orders SET status='paid' WHERE id IN (3,1,2);
COMMIT;
排查阻塞的常用 SQL：SELECT pid, wait_event_type, wait_event, state, query FROM pg_stat_activity WHERE wait_event_type='Lock'; 再结合 pg_locks 找 granted=false 的 pid 与持锁者，用 pg_cancel_backend() 或 pg_terminate_backend() 处理。

④ 咨询锁（Advisory Lock）

咨询锁是应用自己定义语义的锁：锁什么、什么时候加锁完全由代码决定，数据库只提供「互斥」能力。常用于：防止定时任务并发执行、防止重复消费、跨会话串行化某个业务键。

-- 会话级（需显式释放或会话结束）
SELECT pg_advisory_lock(12345);       -- 阻塞等待
SELECT pg_try_advisory_lock(12345);   -- 拿不到立刻返回 false
SELECT pg_advisory_unlock(12345);

-- 事务级（事务结束自动释放，推荐！）
BEGIN;
SELECT pg_advisory_xact_lock(hashtext('order:1001'));
-- 在这里做需要互斥的业务逻辑
COMMIT;

-- 常用模式：防止任务重复执行
SELECT pg_try_advisory_lock(999) AS got;   -- 返回 false 说明已有实例在跑
选型建议：优先用事务级（pg_advisory_xact_lock），避免忘记解锁；锁键用 hashtext('业务键') 或双 int 版本 pg_advisory_xact_lock(int, int)（可表达「类型 + ID」）。注意它与行锁不同：不会阻止别人直接改数据，只约束「同样遵守该约定的代码」。

⑤ 排查阻塞的实战 SQL

-- 1. 谁在等锁
SELECT pid, wait_event_type, wait_event, state,
       now() - query_start AS dur, query
FROM pg_stat_activity
WHERE wait_event_type = 'Lock'
ORDER BY dur DESC;

-- 2. 找持锁者（blocking pid）
SELECT blocked.pid AS blocked_pid, blocked.query AS blocked_sql,
       blocking.pid AS blocking_pid, blocking.query AS blocking_sql,
       now() - blocking.query_start AS blocking_dur
FROM pg_stat_activity blocked
JOIN pg_locks bl ON bl.pid = blocked.pid AND NOT bl.granted
JOIN pg_locks kl ON kl.locktype = bl.locktype AND kl.database IS NOT DISTINCT FROM bl.database
                AND kl.relation IS NOT DISTINCT FROM bl.relation
                AND kl.page IS NOT DISTINCT FROM bl.page
                AND kl.tuple IS NOT DISTINCT FROM bl.tuple
                AND kl.virtualxid IS NOT DISTINCT FROM bl.virtualxid
                AND kl.transactionid IS NOT DISTINCT FROM bl.transactionid
                AND kl.classid IS NOT DISTINCT FROM bl.classid
                AND kl.objid IS NOT DISTINCT FROM bl.objid
                AND kl.objsubid IS NOT DISTINCT FROM bl.objsubid
                AND kl.pid != bl.pid AND kl.granted
JOIN pg_stat_activity blocking ON blocking.pid = kl.pid;

-- 3. 处理（先 cancel 再 terminate）
SELECT pg_cancel_backend(<blocking_pid>);      -- 温和：取消当前查询
SELECT pg_terminate_backend(<blocking_pid>);   -- 强制：断开连接

⑥ 常见问法

Q：PostgreSQL 的读写会互相阻塞吗？

A：不会。MVCC 让读者读取事务开始时的快照，写者创建新版本，两者互不阻塞（这也意味着读不需要加锁）。会互相阻塞的是：① 写与写（同一行的 UPDATE/DELETE/FOR UPDATE）；② DDL 与一切（ACCESS EXCLUSIVE 连 SELECT 都阻塞）；③ 显式加锁的 SELECT FOR UPDATE/SHARE 与冲突的写。这是 PG 与 MySQL InnoDB 类似的优点，也是它高并发读表现好的原因。

Q：一条 ALTER TABLE 为什么会导致整表不可用？

A：因为 ALTER TABLE（多数形式）需要 ACCESS EXCLUSIVE 锁，它与包括 SELECT 在内的所有锁冲突。若当时有一个长查询持有 ACCESS SHARE，DDL 会排在锁队列里等待；而 PG 的锁队列是公平队列，后续所有新来的 SELECT 都会排在这个等待中的 DDL 之后——于是整表访问被「卡死」，直到长查询结束。对策：① 给 DDL 设 lock_timeout；② 上线前检查长事务；③ 尽量使用 CREATE INDEX CONCURRENTLY、ADD COLUMN（无默认值）等在线操作；④ 大表结构变更用 gh-ost/pg_repack 类工具。

Q：SELECT FOR UPDATE 和 FOR SHARE 有什么区别？

A：FOR UPDATE：最强，阻塞其它事务对该行的 UPDATE/DELETE 以及 FOR UPDATE/FOR SHARE，用于「我要改这行」；FOR SHARE：允许别人也加 FOR SHARE（共享读锁），但阻塞别人的 UPDATE/DELETE，用于「我要保证这行在我事务期间不被改，但允许别人也读锁它」。还有更弱的 FOR NO KEY UPDATE 与 FOR KEY SHARE，用于精细控制（如外键检查只需保护主键不被删）。实践：库存扣减用 FOR UPDATE；「读-判断-写」的防并发场景也用 FOR UPDATE 或直接用原子 UPDATE ... WHERE 条件更好。

Q：死锁是怎么产生的？数据库怎么处理？

A：两个或多个事务循环等待对方持有的锁（如 T1 锁 A 等 B、T2 锁 B 等 A）。PostgreSQL 在 deadlock_timeout（默认 1s）后会主动检测等待图，发现环就回滚其中一个事务（报 SQLSTATE 40P01），让另一个继续。防范：① 所有业务按固定顺序访问资源（如按 id 排序后再更新）；② 缩短事务、尽快提交；③ 降低隔离级别或拆大事务；④ 捕获 40P01 错误并重试。注意：死锁检测有开销，死锁频繁通常说明应用层顺序有问题。

Q：咨询锁适合什么场景？有什么坑？

A：适合：① 防止定时任务并发执行；② 对「业务键」做跨会话互斥（如同一订单的并发处理串行化）；③ 替代分布式锁（在单库范围内）。坑：① 它不阻止不遵守约定的代码改数据——只是约定式互斥；② 会话级锁必须显式释放（否则连接复用时会一直持有），推荐用事务级 pg_advisory_xact_lock；③ 锁键是 int/bigint，字符串要先哈希，有极小碰撞概率；④ 连接被池复用时注意锁的生命周期。

Q：怎么快速定位「谁阻塞了谁」？

A：标准三步：① pg_stat_activity 过滤 wait_event_type='Lock' 找到被阻塞者；② 用 pg_locks 自连接，找 granted=false 的等待项对应的 granted=true 持锁者 pid；③ 用 pg_cancel_backend()（温和取消查询）或 pg_terminate_backend()（断开连接）处理。日常建议把这段排查 SQL 做成运维脚本或视图，并配置长事务告警（如 xact_start 超过 60s）。

诊断命令

-- 1) 查看当前锁等待（最常用的一条）
SELECT blocked.pid AS blocked_pid, blocked.usename,
       blocking.pid AS blocking_pid, blocking.usename AS blocking_user,
       blocked.query AS blocked_query,
       blocking.query AS blocking_query,
       blocking.state,
       now() - blocked.query_start AS blocked_duration
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking
  ON blocking.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE cardinality(pg_blocking_pids(blocked.pid)) > 0
ORDER BY blocked_duration DESC;
-- 关键函数：pg_blocking_pids(pid) 返回阻塞该 pid 的进程列表
-- 2) 查看锁详情
SELECT l.pid, l.locktype, l.mode, l.granted,
       l.relation::regclass AS table_name,
       a.query, a.state, now() - a.query_start AS duration
FROM pg_locks l
JOIN pg_stat_activity a ON l.pid = a.pid
WHERE NOT l.granted            -- granted=false 表示正在等待
ORDER BY duration DESC;

-- 3) 查看长事务（锁的万恶之源）
SELECT pid, usename, state,
       now() - xact_start AS xact_age,
       now() - query_start AS query_age,
       query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
  AND now() - xact_start > interval '1 min'
ORDER BY xact_age DESC;
-- 长事务会阻止 VACUUM 清理，导致表膨胀

-- 4) 终止阻塞者
SELECT pg_cancel_backend(<pid>);      -- 温和：取消当前查询
SELECT pg_terminate_backend(<pid>);   -- 强杀：断开连接

-- 5) 安全的 DDL 模式（必做）
SET lock_timeout = '3s';              -- 拿不到锁就失败，不一直等
ALTER TABLE t ADD COLUMN c int;       -- 失败也无所谓，重试即可
-- 不要不加 lock_timeout 直接跑 DDL，否则会堵住整张表的所有查询

排障清单

症状原因处理
DDL 卡住导致全表不可用DDL 等待长事务，后面所有查询排队DDL 前必设 lock_timeout；先杀掉长事务
SELECT 也被阻塞ACCESS EXCLUSIVE 锁（如 VACUUM FULL）避免 VACUUM FULL；用 pg_repack
死锁报 40P01两个事务互相等待固定加锁顺序；缩短事务；设 deadlock_timeout
表膨胀（bloat）长事务阻止 VACUUM设 idle_in_transaction_session_timeout；定期 VACUUM
自增序列不连续序列不回滚（正常行为）这是设计如此，不是 bug
分区表锁不够用max_locks_per_transaction 太小调大；或减少单次操作的分区数
CREATE INDEX 阻塞写入默认 SHARE 锁阻塞写用 CREATE INDEX CONCURRENTLY（不阻塞写，但更慢且失败会留无效索引）

DDL 的黄金规则：任何 DDL 前先 SET lock_timeout = '3s';。这样拿不到锁会快速失败而不是排队，避免「一个 ALTER TABLE 堵死整张表」的线上事故。
