OceanBase 配置参数与故障排查

把机制参数与故障证据放在运维语境中校验。

OceanBase

第二层 · OceanBase 的关键机制与参数

机制 / 参数说明运维含义
分区（Partition）数据按分区分布，是调度单位分区键决定负载均衡与热点
三副本 + Paxos多数派确认才提交可容忍单副本故障，写入需多数派
LSM-Tree 存储内存 MemTable + 磁盘 SSTable写友好，读可能需要合并多层
转储（minor freeze）内存增量落盘，释放内存频繁转储说明写入压力大
合并（major freeze）增量与基线合并，整理数据合并期间 IO 上升，要错峰
memstore 比例内存分配给写入缓冲的比例写满会触发转储甚至写入失败
租户（Tenant）资源隔离单位按租户限 CPU/内存，多业务共享集群
-- 1) 看集群与节点状态
SELECT * FROM __all_server WHERE status = 'active';
SELECT zone, svr_ip, svr_port, status FROM __all_server;

-- 2) 看租户与资源
SELECT tenant_id, tenant_name, primary_zone FROM __all_tenant;
SELECT * FROM __all_virtual_tenant_resource;

-- 3) 看分区分布是否均衡（热点排查第一现场）
SELECT tenant_id, table_id, partition_id, svr_ip, role, row_count
FROM __all_virtual_partition_info
ORDER BY row_count DESC LIMIT 20;

-- 4) 看合并与转储状态
SELECT * FROM __all_virtual_freeze_info ORDER BY frozen_scn DESC LIMIT 10;
SELECT * FROM __all_virtual_merge_info LIMIT 10;

-- 5) 看慢查询（排查性能问题）
SELECT tenant_id, svr_ip, query_sql, elapsed_time, rows_processed
FROM __all_virtual_sql_audit
ORDER BY elapsed_time DESC LIMIT 20;

写入延迟怎么估：三副本多数派确认意味着一次写入要等两个副本落盘，跨机房部署时耗时约等于一轮跨机房 RTT。想降低延迟就要把主副本放在业务所在机房（通过 primary_zone 配置），而不是让业务跨机房写。

第三层 · 六个高频问题与排查顺序

  • 写入报内存不足：memstore 被打满 → 检查是否有大事务、转储是否被阻塞，必要时调大租户内存或拆分写入批次。
  • 合并期间性能抖动：major freeze 消耗大量 IO；设置合并窗口（业务低峰）并控制并发度。
  • 分区热点：分区键选了单调值（如时间戳）导致写入集中；改用哈希分区或复合分区键。
  • 跨机房延迟高：主副本不在业务侧机房；用 primary_zone 把主副本调度过去。
  • 只读查询很慢：LSM-Tree 多层未合并，读放大明显；看合并状态与 SSTable 层数。
  • 排查顺序：节点与副本状态 → 分区分布 → 内存与转储 → 合并状态 → 慢查询。

OceanBase 的一个实用优势：租户级资源隔离让多业务可以共用一套集群，代价是资源规划要提前做，事后调整需要迁移租户。
