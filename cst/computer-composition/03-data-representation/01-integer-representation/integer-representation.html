整数表示：补码、符号扩展与「溢出」的两种含义

同一串二进制，按无符号解释是 4294967295，按补码解释是 -1。CPU 只给位和标志，含义由类型决定。搞不清补码与两个溢出标志，就会在边界值、比较和移位上反复踩坑。

一句话定位：补码让减法复用加法器

n 位补码把最高位的权重设为 −2^(n−1)，其余位仍是正权。这样 0 只有一种表示，加减法可以统一成加法：A − B = A + (~B + 1)，硬件只需一个取反器和一个进位输入。

n 位无符号0 ~ 2n−1
n 位补码−2n−1 ~ 2n−1−1（负数比正数多一个）
−1 的表示全 1（8 位 0xFF，32 位 0xFFFFFFFF）
最小值0x80…0，取负仍是它自己（溢出）
补码是一个环：加 1 一直走，越过 +7 就绕到 −8

三种编码对照（4 位）

位模式原码反码补码移码（偏置 8）
0000+0+00−8
0001+1+11−7
0111+7+77−1
1000−0−7−8+0
1001−1−6−7+1
1111−7−0−1+7

原码有两个零、减法要判符号；反码的负零仍是坑；补码把零统一、把减法变加法，所以成为整数的事实标准。移码（偏置表示）把大小顺序映射成无符号顺序，用于浮点指数比较。

符号扩展、截断与溢出

// 符号扩展：高位补符号位，值不变
int8_t  a = -1;        // 0xFF
int32_t b = a;         // 0xFFFFFFFF  ✓ 符号扩展
uint32_t c = (uint8_t)a;  // 0x000000FF  ✓ 零扩展

// 截断：直接丢高位，值可能改变
int32_t x = 300;       // 0x0000012C
int8_t  y = (int8_t)x; // 0x2C = 44   ← 不是 300

// 溢出判定（n 位补码）：同号相加，结果异号
// 8 位：127 + 1 = -128   → OF=1, CF=0
// 无符号：255 + 1 = 0    → CF=1, OF=0
标志含义什么时候置 1谁用它
CF（进位/借位）无符号溢出最高位向外进位（减法x86取反）无符号比较、多精度加减
OF（溢出）有符号溢出同号相加得异号有符号比较、异常
ZF结果为零所有结果位为 0je / bne
SF结果为负结果最高位为 1有符号比较（配合 OF）

C / C++ 里五个真实会咬人的点

  1. 有符号溢出是 UB：int 溢出后编译器可以假设「不会发生」，从而删掉检查。要环绕语义就用无符号或 -fwrapv。
  2. -INT_MIN 仍是 INT_MIN：取负溢出，绝对值函数对它返回负数。
  3. 无符号与有符号比较：if (v.size() > -1) 永远为真，因为 -1 被转成巨大的无符号数。
  4. 右移负数：C 标准是实现定义（算术右移还是逻辑右移），跨平台别依赖。
  5. 移位位数 ≥ 位宽是 UB：x << 32 在 32 位 int 上未定义，不是 0。
查边界值的习惯

任何涉及长度、索引、计数的比较，先问一句「这个变量是有符号还是无符号」。绝大多数 size() >= 0 类型的 bug 都死在这里。

原理与取舍：为什么不用「符号位 + 绝对值」

原码直观，但硬件要额外处理「同号相加、异号相减」和「两个零」，还要为减法单独做一条通路。补码把这三种情况统一成加法，代价是数值范围不对称（负数多一个），以及「取负最小值会溢出」这个怪点。用一点点数学上的不优雅，换来了整整一套算术逻辑的简化。

为什么 8 位补码范围是 −128~127，不是 −127~127？

因为 1000 0000 在原码里是「负零」，补码把这个位模式征用为 −128。这样 256 个位模式刚好覆盖 256 个值，一个不多一个不少。

CPU 怎么知道该按有符号还是无符号解释？

不知道，也不需要知道。加减法电路对两种解释完全相同，区别只在「看哪个标志」和「乘法是否符号扩展」。

为什么浮点用移码表示指数？

移码把大小顺序映射成无符号顺序，比较两个浮点数的指数时可以直接按无符号整数比，硬件更简单。

第一层 · 概念与判定：为什么要补码

计算机用固定位数存整数。无符号数直接二进制；有符号数主流用补码（two's complement）。补码的最大好处是：加减法统一成一套电路，不需要给减法单独设计，且 0 只有一种表示。

表示法0 的表示能表示的负数现状
原码两种（+0/-0）少一个已基本不用
反码两种少一个历史
补码唯一多一个现代通用

一句话判定：看到「int32 取值范围不对称」「为什么负数比正数多 1」，答案都在补码上。

补码计算与符号互转

# 补码求法（以 8 位 -5 为例）
# 5 的二进制: 0000 0101
# 取反:       1111 1010
# 加 1:       1111 1011  => 这就是 -5 的补码
# 验证: -5 + 5 = 1111 1011 + 0000 0101 = 1 0000 0000，溢出位丢弃 = 0  ✓

# Python：有符号 <-> 无符号互转（32 位）
def to_unsigned(x, bits=32):
    return x & ((1 << bits) - 1)
def to_signed(x, bits=32):
    return x - (1 << bits) if x >= (1 << (bits-1)) else x

print(to_unsigned(-1))        # 4294967295
print(to_signed(4294967295))  # -1

# C：printf 看溢出
# int8_t a = 127; a++;  // 变成 -128（溢出环绕）

数量级：int32 上限约 21.4 亿，所以「用 int 存自增 ID/毫秒时间戳」会在约 24 天（毫秒时间戳）或 68 年（秒时间戳）后溢出——时间戳必须用 int64。

第三层 · 排障与边界：高频坑

整数表示的翻车清单：

  • 有符号溢出：int8 加 1 从 127 变 -128，是未定义行为（C/C++），不是取模
  • 无符号混用：unsigned 减到负数变成巨大正数，循环 `for(i=n; i>=0; i--)` 对 unsigned 死循环
  • 符号扩展错：char 转 int 时，有符号 char 负数要符号扩展，错误转型会得错值
  • 位宽跨语言不一致：C 的 long 在 64 位 Linux 是 64 位、在 Windows 是 32 位，结构体跨平台错乱
  • 移位越界：对 32 位数移 ≥32 位或负数位是未定义行为
  • 时间戳用 int32：毫秒时间戳 2038 年后溢出（类 Y2K 的 2038 问题）

排查顺序：① 复现后打印十六进制而非十进制，溢出/符号问题一眼可见；② 检查涉及的类型强转；③ 确认所有时间/ID 字段是 64 位。

第四层 · 原理与取舍

为什么负数比正数多表示一个？

n 位补码共 2^n 种状态。0 只占一种，剩下 2^n-1 个要分给正负。对称分的话正数少一个，于是约定最负的数（如 -128）没有对应的正 128，它自己孤零零占一个状态。所以范围是 -2^(n-1) ~ 2^(n-1)-1。

为什么补码让加减统一？

补码把「减法 a-b」变成「加法 a + (-b) 的补码」，而 -b 的补码恰好是「取反加一」。更妙的是，最高位的进位自然丢弃后结果仍正确，所以 ALU 只需一个加法器就能同时处理加减，硬件极简。

为什么浮点数不在这套表示里？

浮点要表达极大范围和小数，采用 IEEE 754 的「符号+阶码+尾数」科学计数法，不是补码体系，且运算有舍入误差。整数位的补码规则完全不适用于浮点，所以 float 比较要用误差容限而非 ==。
