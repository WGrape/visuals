Feed 流系统设计

推还是拉：用写成本换读成本，工业答案是推拉结合

一句话
核心矛盾是「读的时候要快」还是「写的时候要省」
推模式 写扩散
发一条就写到所有粉丝的收件箱，读极快、写很贵
拉模式 读扩散
读的时候才去聚合关注者的内容，写极省、读很慢
现实方案
大 V 用拉、普通用户用推 —— 推拉结合

一、推拉对比

维度推模式（写扩散）拉模式（读扩散）
写入成本O(粉丝数)，大 V 发一条要写百万次O(1)，只写一份
读取成本O(1)，直接读自己的收件箱O(关注数)，要聚合所有人
延迟粉丝几乎立刻可见读到才算，冷启动慢
存储粉丝数 × 内容数，总量巨大只有一份内容
适合粉丝数少、读多写少粉丝数极多、关注关系稀疏
典型代表早期微博、朋友圈Twitter 早期、RSS

为什么朋友圈是推模式

微信好友上限约 5000，且关系是双向的。写扩散的成本有上界且可控，换来的是「打开朋友圈一定是毫秒级」。这就是典型的用可控的写成本换极致的读体验。

二、推拉结合：工业界的标准答案

纯粹的推或拉都撑不住真实流量，主流做法是按粉丝量级分流：

发内容时： if 作者粉丝数 < 阈值(如 1 万): 推模式：异步任务把内容写入每个粉丝的收件箱 else: 拉模式：只写作者发件箱，粉丝读取时再实时拉取 读 feed 时： 1) 从自己的收件箱取「普通用户」的内容 2) 从关注的大 V 发件箱实时拉取 3) 两部分按时间/权重归并排序后返回 // 这个「阈值」不是随便定的： // 粉丝数 × 发布频率 = 写扩散 QPS，必须能被异步队列消化

三、存储选型

用途选型原因
收件箱（推模式）Redis ZSet（score = 时间戳）需要按时间有序、只保留最近 N 条、读写都极快
发件箱（拉模式）Redis ZSet 或 MySQL 分库分表按作者维度查，天然可分片
正文内容MySQL / HBase / 对象存储容量大、需要持久化、可只存一份
关注关系MySQL + 缓存，或图数据库需要双向查询与快速判断

关键技巧：收件箱只存 ID，不存正文。正文只存一份，读的时候再批量拉取，这样存储量从「内容 × 粉丝数」降到「ID × 粉丝数」，通常能省一到两个数量级。

四、必须解决的四个问题

收件箱无限增长

只保留最近 N 条（如 1000），更早的走拉模式或历史库

僵尸粉丝

按活跃度分级，长期不活跃的用户不做实时写扩散

热点内容

缓存热点作者的发件箱，避免每次都聚合

已读与去重

客户端记录已读位点，服务端按时间游标返回

最容易低估的问题：取消关注

用户取消关注后，收件箱里已经推过的内容要不要删？如果删，要遍历该用户收件箱找出属于该作者的内容，成本高；如果不删，用户会看到已取关的人的内容，体验很差。常见折中：读取时按当前关注列表过滤，写时不处理，靠读侧兜底。

五、深入自检

为什么不让客户端轮询而是长连接？Feed 流对实时性要求高，轮询会带来大量无效请求（大部分时候没有新内容）。长连接/推送能把「有没有新内容」的判断放到服务端，省掉绝大部分空轮询。
大 V 发一条要写百万次，真的扛得住吗？扛不住，所以才要推拉结合。另外写扩散一定是异步的：发内容接口只写发件箱并投递任务，由后台队列慢慢扩散，允许粉丝有几秒延迟。
ZSet 的 score 用时间戳会冲突吗？同毫秒发布的会冲突。工程上会把时间戳左移再拼上内容 ID 的低位，或者直接用「毫秒时间戳 + 自增序号」构造唯一有序的 score。
排序只按时间吗？早期是按时间倒序，现在是权重排序：综合时间衰减、互动率、作者亲密度、内容类型等打分。一旦引入权重，就很难在写入时确定顺序，通常要在读取时重排。
历史 feed 怎么查？收件箱只保留最近 N 条是出于成本考虑，历史内容要靠「作者的发件箱 + 关注列表」重新聚合，或者直接走离线数仓的宽表。

记住一句

推拉之争 = 用写成本换读成本

工业答案

小号推、大号拉、读时归并

省钱关键

收件箱只存 ID，不存正文

易漏点

取消关注后的历史内容处理

六、容量估算：算一遍才知道撑不撑得住

量假设结果
DAU1 亿-
人均每日发0.1 条日新增 1000 万条
人均每日刷20 次，每次 50 条日读取 1000 亿条
读写比10000 : 1典型的读多写少，值得为读做优化
写扩散峰值1000 万条 × 平均 200 粉丝日写入 20 亿次，约 2.3 万 QPS

从这个估算能读出什么

写扩散 2.3 万 QPS 完全可以由异步队列消化，所以普通用户走推模式是可行的；但如果有 1000 万粉丝的大 V，一条内容就是 1000 万次写，必须走拉模式。这就是为什么推拉结合的阈值通常设在「几万粉」这个量级。

七、一个可落地的最小架构

  1. 写入侧：发内容接口只写内容库 + 作者发件箱，返回成功；投递一条扩散消息到 MQ。
  2. 扩散 worker：消费消息，查粉丝列表，按活跃度分批写入收件箱（Redis ZSet）。
  3. 读取侧：先读收件箱取 ID 列表，再批量拉取正文，与大 V 发件箱内容归并排序。
  4. 兜底：收件箱为空或不足时，走拉模式实时聚合，保证新用户也有内容。
  5. 清理：收件箱按 ZSet 大小裁剪，只保留最近 1000 条。

推拉模型的选择与量化

Feed 流的核心矛盾是写扩散（推）和读扩散（拉）的取舍。判断依据是一个可计算的量：粉丝数 vs 发帖频率。

维度推（写扩散 / Fanout on Write）拉（读扩散 / Fanout on Read）
做法发帖时写入每个粉丝的收件箱读时实时聚合关注的人的帖子
写成本O(粉丝数) 一次写 N 份O(1)
读成本O(1) 直接读自己的收件箱O(关注数) 要聚合 N 个人的帖子
延迟读极快（已准备好）读较慢（要实时算）
存储高（大 V 发帖占巨大空间）低（只存一份）
适用粉丝少、发帖多（普通用户）粉丝多、发帖少（大 V）
量化判据计算结论
写扩散代价粉丝数 × 日发帖数大 V：1000 万粉 × 1 帖 = 1000 万次写
读扩散代价日活 × 平均关注数 × 读次数用户：100 关注 × 10 次/天
临界点粉丝数 > 约 几千~几万 就该改用拉业界常用 推拉结合
方案做法代表说明
纯推全量写扩散早期微博（有问题）大 V 发帖会写爆
纯拉全量读扩散朋友圈早期关注多时读很慢
推拉结合普通用户推、大 V 拉，读时合并微博、Twitter 现行方案工业标准答案
智能分流按活跃度：活跃粉丝推、不活跃拉优化版进一步降低写量

实现示例

# ---------- 推拉结合的实现（Redis）----------
# 1. 普通用户发帖 -> 写扩散到粉丝的收件箱
def post(user_id, post_id):
    redis.lpush(f"inbox:{user_id}", post_id)         # 自己的
    followers = get_followers(user_id)               # 从关注服务拿
    if len(followers) < FANOUT_THRESHOLD:            # 如 10000
        pipe = redis.pipeline()
        for f in followers:
            pipe.lpush(f"inbox:{f}", post_id)
            pipe.ltrim(f"inbox:{f}", 0, 999)         # 只留最新 1000 条
        pipe.execute()                                # 批量，一次网络往返
    # 大 V 不推，只写入自己的 outbox

# 2. 读 Feed -> 合并「推来的」+「大V的」
def get_feed(user_id):
    pushed = redis.lrange(f"inbox:{user_id}", 0, 99)      # 推的部分
    big_vs  = get_followed_big_vs(user_id)                # 关注的大V列表
    pulled  = []
    for v in big_vs:
        pulled += redis.lrange(f"outbox:{v}", 0, 9)       # 拉的部分
    merged = merge_sort_by_time(pushed + pulled)[:100]    # 按时间归并
    return hydrate(merged)                                # 批量查正文

# ---------- 关键优化 ----------
# 1. 异步 fanout：发帖接口只写 outbox，fanout 丢 MQ 异步做
#    -> 用户发帖瞬间返回，不需要等 1000 万次写完
# 2. 收件箱裁剪：ltrim 只留 1000 条（没人会翻到那么久之前）
# 3. 离线用户不推：只给最近 7 天活跃的用户 fanout
# 4. 正文不进收件箱：收件箱只存 post_id，读时批量查（避免正文重复存储）
# 5. 多级缓存：Feed 列表 -> 帖子正文 -> 用户信息，分别缓存
  • 答案是推拉结合：普通用户（粉丝 <阈值）走推，大 V 走拉，读的时候合并两份再按时间排序。这是微博、Twitter 的实际做法。
  • 阈值通常设在几千到几万：具体值取决于你的写能力和容忍的延迟。微博公开分享过大约是几万级别。
  • fanout 必须异步：同步写 1000 万份会导致发帖接口超时。做法是写自己的 outbox 后立刻返回，把 fanout 丢进消息队列异步做。
  • 收件箱只存 ID，不存正文：正文重复存 N 份太浪费。读的时候批量查一次（hydrate）。
  • 收件箱要裁剪：LTRIM 到 1000 条左右。用户几乎不会翻更久之前的 Feed。
  • 离线用户不推：只给最近活跃的用户 fanout，能大幅降低写量（很多粉丝是僵尸号）。
  • 计数要单独处理：点赞数、评论数是高写字段，不要存在 Feed 正文里，用 Redis 计数 + 异步落库。
推模型和拉模型怎么选？

不要二选一，标准答案是推拉结合，判据是粉丝数是否超过阈值。推理过程：假设一个用户有 N 个粉丝、每天发 M 条帖子。用推：每次发帖写 N 份，日写量 = N×M。普通用户 N=200、M=2 → 400 次/天，完全没问题；大 V N=1000 万、M=1 → 1000 万次写/条，一条帖子要写几分钟，且占用巨量存储，这就是「大 V 发帖导致微博瘫痪」的原因。用拉：读的时候聚合关注的所有人的帖子，成本 = 关注数。普通用户关注 200 人，每次读要聚合 200 个人的帖子列表再归并排序，读延迟高且放大读 QPS。所以：粉丝少的用推（写便宜、读飞快），粉丝多的用拉（写一份、读时合并）。阈值通常几千到几万，超过阈值的大 V 走拉。读的时候把「推来的收件箱」和「大 V 的 outbox」合并排序即可。

大 V 发帖导致雪崩怎么破？

四道防线：① 异步 fanout——发帖接口只写自己的 outbox 就返回，把「写给粉丝」这件事丢进 MQ 由 worker 慢慢做。这样即使要写 1000 万份，用户感知到的发帖延迟也是毫秒级；② 分流 + 限流——MQ 消费端控制速率，避免瞬间打爆 Redis/存储；可以给不同大 V 分配不同的处理优先级；③ 只推活跃用户——1000 万粉丝里可能只有 100 万是周活的，只给活跃用户 fanout，写量直接降 90%；④ 对超大 V 直接走拉——超过阈值的大 V 根本不 fanout，读者拉取时实时合并。另外还有个细节：收件箱要设上限（如 1000 条），否则长期累积会让存储爆炸，而且老 Feed 也没人看。实践中这四招通常叠加使用。

Feed 的排序要按时间还是按权重？

看产品定位，两种都有：时间序（ chronological）——严格按发布时间倒序，优点是可预期、不会漏、用户有掌控感，适合「关注的人不多、不想错过」的场景（如朋友圈、Twitter 的关注流）。实现简单，收件箱是有序列表，直接读即可；权重序（ranked/algorithmic）——按相关性、互动率、时效性等打分排序，优点是提升 engagement（点赞、停留时长），适合内容过载的场景（如微博首页、抖音推荐流、Facebook）。实现复杂：需要离线算好分数、建倒排 + 排序索引，读时做 top-K 归并，成本远高于时间序。折中方案（也是主流）：推模式用时间序（收件箱天然有序），拉模式/推荐流用权重序；或者默认权重序但提供「切换到最新」的选项。另外要注意：权重序无法做「未读数」的语义（因为顺序会变），设计上要区分。
