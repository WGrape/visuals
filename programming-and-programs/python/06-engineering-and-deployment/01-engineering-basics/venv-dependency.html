虚拟环境与依赖管理

「在我机器上能跑」的根源，几乎都是依赖没隔离。venv 给每个项目一个独立 Python 环境，requirements.txt / poetry 锁定版本——这是工程化交付的第一道关。

为什么隔离

全局装包 = 给所有项目埋雷

系统 Python 装一堆包，A 项目要 requests==2.28、B 项目要 requests==2.31，全局只有一个位置，必然冲突。虚拟环境让每个项目有自己独立的 site-packages。

🌍
全局环境
所有项目共享，版本互相踩
📦
venv 环境
每项目独立，互不干扰，可删除重建
⚠️ 别用系统 Python（尤其 macOS 自带的）直接 pip install。既可能破坏系统工具，又无法多版本并存。永远先建 venv。
venv 用法

建环境、激活、装包三步走

Python 3.3+ 内置 venv 模块，无需第三方工具。激活后，python / pip 都指向环境内的解释器。

# 1. 在项目根建环境（目录名常叫 .venv）
python -m venv .venv

# 2. 激活（bash/zsh）
source .venv/bin/activate
# Windows: .venv\Scripts\activate

# 3. 在环境内装包（此时 pip 装进 .venv）
pip install fastapi uvicorn

# 退出环境
deactivate
激活的本质是改 PATH 把 .venv/bin 放最前。CI / Docker 里通常不用「激活」，而是直接调用 .venv/bin/python 或 python -m pip 保证指向明确。
requirements

用 requirements.txt 锁定依赖

pip freeze > requirements.txt 把当前环境所有包及精确版本导出；别人 pip install -r requirements.txt 就能复现一模一样的环境。

# 导出（含传递依赖与精确版本）
pip freeze > requirements.txt

# 别人复现
pip install -r requirements.txt

# requirements.txt 示例
fastapi==0.111.0
uvicorn[standard]==0.30.1
pydantic==2.7.1
⚠️ pip freeze 会导出全部传递依赖，文件冗长但可复现。更精细的做法：只写「直接依赖」并区分 -r base.txt 与 dev 依赖；或换成下面介绍的 poetry。

依赖装好后，框架怎么跑、Worker 怎么配，见本分区Gunicorn Worker 类、FastAPI 部署、Pydantic 三篇。

进阶工具

poetry / pip-tools：更好的依赖体验

原生 requirements 不解决「版本冲突解析」和「lock 文件」。poetry 提供 pyproject.toml + 锁文件 + 虚拟环境一体化；pip-tools 用 requirements.in 编译出锁定版。

工具特点适用
venv + pip零依赖、最通用简单项目、教学
pip-toolsrequirements.in 编译锁定想保留 pip 工作流
poetrypyproject + lock + 建环境 + 打包发布正式库/应用
pipenvPipfile + 自动 venv偏旧，逐渐被 poetry 取代
# poetry 工作流
poetry init            # 生成 pyproject.toml
poetry add fastapi     # 装包并写依赖 + 更新 lock
poetry install         # 按 lock 重建环境
poetry shell           # 进入环境
团队项目强烈建议用 poetry 或 pip-tools 生成 lock 文件：保证「开发、测试、生产」三套环境依赖完全一致，避免「CI 能过本地挂」。

核心速览

一句话用虚拟环境隔离每个项目的依赖，用锁文件保证每次装到的版本完全一致
为什么必须隔离系统 Python 只有一个 site-packages，两个项目要求同一包的不同版本就会打架
标准组合venv 建环境 + requirements.txt / lock 文件 + pip 安装
核心原则锁住直接依赖与传递依赖的全部版本，否则「我这能跑」永远是谎言
虚拟环境四步：建环境 -> 激活 -> 装包 -> 锁版本

一、venv 做了什么

# 创建 python -m venv .venv # 激活（激活只是改 PATH，不是魔法） source .venv/bin/activate # Linux/macOS .venv\\Scripts\\activate # Windows # 激活前后对比 which python # 激活前：/usr/bin/python3 # 激活后：/path/to/project/.venv/bin/python # 目录里有什么 .venv/ bin/ python、pip、激活脚本 lib/python3.x/site-packages/ 这个项目专属的包 pyvenv.cfg 记录了基础解释器位置 # 退出 deactivate # 关键：venv 不复制解释器，只是软链/引用 + 独立的 site-packages # 所以创建很快、体积很小
为什么用 python -m venv 而不是直接 venv

python -m venv 明确指定了用哪个解释器来创建环境，避免了系统里装了多个 Python 时建错版本的环境。这是一条几乎零成本的保险。

二、依赖文件怎么组织

文件内容特点
requirements.txt直接依赖（可带版本约束）手工维护，简单但可能不精确
requirements.lock / freeze 产物所有包的精确版本（含传递依赖）可复现，是部署应该用的
pyproject.toml项目元数据 + 依赖声明（现代标准）PEP 621，被 Poetry/PDM/uv 等使用
poetry.lock / uv.lock工具生成的锁文件带哈希，防篡改，可完全复现
constraints.txt只约束版本，不触发安装用于统一多个项目的版本基线
# requirements.in（只写直接依赖，宽松约束） requests>=2.28 flask~=3.0 # ~= 表示允许 3.x 的补丁更新，不含 4.0 # 生成精确锁文件 pip install pip-tools pip-compile requirements.in -o requirements.txt # 产出：requests==2.31.0、urllib3==2.1.0、certifi==2023.11.17 ... # 部署时严格按锁文件装 pip install --require-hashes -r requirements.txt # 常用命令 pip freeze # 导出当前环境所有精确版本 pip list --outdated # 看哪些能升级 pip show requests # 看某个包的信息与依赖 pipdeptree # 看依赖树，排查冲突神器

五、深入自检

venv 和 virtualenv 有什么区别？

venv 是 Python 3.3+ 标准库自带的，功能够用且无需安装；virtualenv 是第三方，支持更老的 Python、创建更快、可指定任意解释器版本。新项目直接用 venv。

为什么容器里还要用 venv？

其实可以不用——容器本身就是隔离的。但用 venv 仍有好处：避免污染系统 site-packages、方便多阶段构建时只拷贝环境、与本地开发保持一致。

pip install 时版本冲突怎么办？

先看 pipdeptree 找出是谁要求的冲突版本，然后：① 放宽自己的约束；② 升级冲突的上游包；③ 用 constraints 统一；④ 实在不行才考虑拆分环境。

--require-hashes 有什么用？

要求每个包都带哈希值，pip 会校验下载内容是否被篡改。这是供应链安全的基本防线，配合锁文件使用。

锁文件要多久更新一次？

建议：安全补丁随时更新，常规升级按月或按季度做一次，并跑完整回归。不要让它冻结超过半年——差距越大，升级越痛苦。

创建命令python -m venv .venv
必加 gitignore.venv/、__pycache__/
锁全量只锁直接依赖是不够的

第一层 · 概念与判定：venv / virtualenv / conda / poetry 怎么选

一句话判据：venv 解决「隔离」，poetry / pip-tools 解决「锁定」，两者是不同层的事，别混着比。

工具解决的问题是否锁版本什么时候用
venv（标准库）环境隔离❌默认首选，Python 3.3+ 自带
virtualenv环境隔离（更快、支持老版本）❌需要兼容 Python 2 或要更快时
conda隔离 + 非 Python 依赖（CUDA、MKL）部分科学计算 / 需要二进制依赖
pip-tools从宽松约束生成精确锁✅想继续用 pip 但要可复现
poetry隔离 + 依赖解析 + 锁 + 打包发布✅新项目、要一条龙
  • 信号一：只是想「这个项目别污染全局」→ venv 足够。
  • 信号二：要「别人装出来的版本跟我一模一样」→ 必须有 lock 文件（poetry.lock 或 requirements.txt 带 ==）。
  • 信号三：依赖里有非 Python 的二进制（CUDA / GDAL）→ conda 更省事。

关键区分：隔离 ≠ 锁定。venv 只保证「装到别处」，不保证版本可复现；可复现必须靠 pin 住版本。

第二层 · 参数·命令·量化：三步走与锁定写法

venv / poetry / pip-tools 命令

# 1) 建环境 + 激活 + 装包（三步走）
python3 -m venv .venv              # 建
source .venv/bin/activate          # 激活（Windows 用 .venv\Scripts\activate）
pip install requests==2.31.0       # 装

# 2) 导出精确版本（可复现的关键）
pip freeze > requirements.txt      # 会把所有间接依赖也 pin 住

# 3) 别人复现环境
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# 退出 / 删除
deactivate
rm -rf .venv                       # venv 无副作用，删目录即可

# poetry 常用
poetry init          # 生成 pyproject.toml
poetry add requests  # 装并写入 pyproject
poetry lock          # 生成 poetry.lock
poetry install       # 按 lock 安装（CI 用 --no-dev 或 --only main）

# pip-tools 常用
pip-compile requirements.in   # 从宽松输入生成锁好的 requirements.txt
pip-sync                      # 让环境严格等于 lock（会删多余包）
文件写法含义用在哪
requirements.inrequests>=2.28只写直接依赖 + 宽松范围人维护，pip-tools 输入
requirements.txtrequests==2.31.0全部依赖 pin 到精确版本部署 / CI 安装
pyproject.toml[tool.poetry.dependencies]声明依赖与元信息人维护
poetry.lock自动生成完整依赖树 + hash提交进仓库，保证可复现

量化提醒：一个典型 Web 项目 pip freeze 会输出 40～120 行，其中绝大多数是间接依赖——所以不要手写 requirements.txt，一定用工具生成。

第三层 · 排障与边界：必踩的坑

现象原因怎么查 / 怎么办
装了包装不到 / 装到全局去了没激活 venv，或用了 sudo pipwhich python 看路径是否在 .venv 下
pip 装的是系统 python 的包激活后 python 仍指向系统用 python -m pip 而不是裸 pip
两份 requirements 装出不同结果没 pin 版本，间接依赖漂移全部 ==；或用 lock 文件
依赖冲突解不出来版本约束互相矛盾pipdeptree 看冲突树；poetry 会明确报冲突原因
venv 挪目录后失效venv 里写死了绝对路径不要移动 venv，重建更快
pip install 巨慢走国外源配 pip config set global.index-url 用镜像
  • 排查顺序：先 which python && which pip 确认在环境内 → 再 pip list 看装了什么 → 再 pipdeptree 看依赖树。
  • 边界一：venv 不能创建不同 Python 版本的环境——要 3.9 和 3.12 并存得用 pyenv/conda。
  • 边界二：pip freeze 会把当前环境所有包都导出，包括你临时装来试的——导出前先确认环境干净。
  • 边界三：把 .venv 提交进 git 是常见错误，.gitignore 里必须排除；要提交的是 requirements.txt / poetry.lock。

第四层 · 原理与取舍：venv 到底做了什么

venv 的本质非常朴素：它只是建了一个目录，里面放一份 python 解释器软链 + 独立的 site-packages，再靠改 PATH 让 python 优先找到这里。它不做任何沙箱、不隔离 CPU/内存，也不改变 Python 版本。

方案隔离粒度可复现性代价
全局安装无差一个项目升级包，另一个项目崩
venvsite-packages 目录级需自己 pin每个项目一份，磁盘占用大
poetry / pip-tools目录级 + 依赖解析强（lock 文件）多一层工具与配置
condaPython 版本 + 非 Python 库中体积大、与 pip 混用易冲突
容器（Docker）操作系统级最强构建与启动开销
requirements.txt 和 poetry.lock 能互相转换吗？

结构上不能无损转换：requirements.txt 是扁平列表，poetry.lock 带依赖树和 hash。实践中可以用 poetry export -f requirements.txt --without-hashes 单向导出给不支持 poetry 的环境用。

为什么不干脆全用 Docker？

Docker 隔离最彻底，但本地开发时每次改依赖都要重建镜像，反馈慢。常见做法是本地用 venv + lock 快速迭代，交付/部署用 Docker 固化。

什么时候 venv 不够用？

需要切换 Python 解释器版本（3.8 ↔ 3.12）、或依赖需要系统级二进制库（CUDA、OpenSSL 特定版本）时，venv 解决不了——前者用 pyenv，后者用 conda 或容器。
