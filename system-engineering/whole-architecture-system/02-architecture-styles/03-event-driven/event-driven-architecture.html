什么时候适用？

判断信号：事实发生后多个下游可独立响应，业务允许异步与最终一致。

  • 订单支付后积分与通知各自消费
  • 库存变化触发搜索索引更新
  • 设备遥测驱动多个实时分析服务

和相近方案怎么区分？

相近方案选择边界
观察者模式观察者通常是进程内回调；跨服务事件需要持久化、重试和幂等。
同步 RPCRPC 调用方等待结果；事件驱动的下游可异步处理，但要接受延迟与乱序。

最小伪代码

transaction:
  order.markPaid()
  outbox.insert(OrderPaid(order.id))
// 提交后由发布器把 outbox 送入总线
on OrderPaid(event):
  if not processed(event.id): grantPoints(event.orderId)

边界：事件是已发生事实；可靠投递需要 outbox/重试等机制，消费者要能处理重复与乱序。

事件流模型 EDA

一个事件可被多个消费者独立订阅；生产者不直接调用消费者

核心角色：事件（『发生了什么』的事实，如 OrderCreated）、生产者（发出事件）、经纪人/总线（Kafka、RabbitMQ）、消费者（各自订阅关心的事件）。

两种典型模式

  • 事件通知：只通知『发生了什么』，消费者自己去拉详情（耦合低、需回查）。
  • 事件携带状态(Event Carried)：事件里带上完整数据（自治、但可能冗余）。
  • 事件溯源 Event Sourcing：状态由一连串事件重放得到，而非直接存当前值。

面试高频问答

Q：事件驱动和事件溯源是一回事吗？
A：不是。事件驱动是『通信风格』（用事件解耦服务）；事件溯源是『存储风格』（用事件序列表达状态）。事件溯源是事件驱动的一种进阶用法。
Q：如何保证事件不丢、不重复消费？
A：不丢靠消息队列持久化+确认机制；不重复靠消费者幂等（用事件ID/业务唯一键去重）。顺序性靠分区键绑定。
