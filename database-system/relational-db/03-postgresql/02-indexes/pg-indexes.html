PostgreSQL 索引类型

B-tree 之外的 GIN / GiST / BRIN / Hash / 表达式 / 部分索引——按数据特征选型。

默认 B-treeGIN 倒排GiST 通用搜索BRIN 块范围特殊索引选型对照

① B-tree（常规等值与范围查询的默认选择）

CREATE INDEX 不加类型时就是 B-tree，支持等值、范围、排序、前缀查询，可用于 UNIQUE 和主键。适合大多数字段。

SQLite 也有通用索引、表达式索引与部分索引，但其 ROWID 主键和索引维护方式另有特点；参见SQLite 索引。本页重点是 PostgreSQL 特有的 GIN、GiST、BRIN 等索引类型。

CREATE INDEX idx_orders_user ON orders(user_id);
CREATE UNIQUE INDEX idx_email ON users(email);

② GIN — 倒排索引

GIN（Generalized Inverted Index）为 包含多个元素的复合值 设计：jsonb、数组、tsvector 全文检索。它把每个元素映射到包含它的行，像书的倒排索引。

CREATE INDEX idx_tags ON articles USING gin(tags);        -- 数组
CREATE INDEX idx_doc ON docs USING gin(to_tsvector('english', body));  -- 英文全文
代价：GIN 写入较慢（需更新多个倒排条目），适合读多写少 / 静态文档。

③ GiST — 通用搜索树

GiST（Generalized Search Tree）为 不规则 / 多维 / 近似 数据建模：几何类型、范围类型、相似搜索（k-NN）。PostGIS 的几何索引就是基于 GiST。

CREATE INDEX idx_geo ON shops USING gist(location);      -- 空间
CREATE INDEX idx_range ON reservations USING gist(period); -- 时间段重叠

④ BRIN — 块范围索引

BRIN（Block Range INdex）只记录 连续数据块范围内的最值，体积极小，专为 按物理顺序插入的大表（如时序日志、按时间排序的表）设计。不能精确定位单行，但能快速跳过不相关块。

CREATE INDEX idx_ts ON events USING brin(created_at);  -- 百亿行也只几 MB

⑤ 表达式 / 部分 / 覆盖索引

  • 表达式索引：对函数结果建索引，lower(email)、date(created_at)。
  • 部分索引：只为满足条件的行建索引，WHERE status='active'，省空间提效。
  • 覆盖索引：INCLUDE 列，使索引满足查询无需回表。
CREATE INDEX idx_lower ON users(lower(name));
CREATE INDEX idx_active ON orders(user_id) WHERE status='active';
CREATE INDEX idx_cov ON orders(user_id) INCLUDE (total);

PostgreSQL 的索引不是只有一种

很多人的数据库经验是从 MySQL 或某种单一索引起步的，容易默认「索引 = B 树」。PostgreSQL 的一大特色是索引类型丰富，每种针对一类数据形态。

类型适合什么典型场景
B-tree排序与范围（默认）数值、时间、文本前缀、绝大多数常规列
Hash纯等值比较早年限制较多，现在可用，但多数场景 B-tree 也不差
GIN倒排：一个值对应很多行数组包含、jsonb 键值、全文检索
GiST任意自定义的「距离/重叠」语义几何图形、范围类型、全文部分场景
SP-GiST空间可划分的非平衡结构前缀、四叉树类分布不均的数据
BRIN超大表、按物理顺序相关的列时序日志按时间范围查 —— 体积极小

一句话总结它们的取舍：B-tree 是通用答案；GIN 为「多值列」而生；GiST 处理「邻近/重叠」类谓词；BRIN 用极小的体积换取粗粒度过滤，适合天然有序的大表。

三个 PostgreSQL 特色的索引能力

① 部分索引 Partial Index

只对满足条件的行建索引：

CREATE INDEX idx_orders_pending ON orders (created_at) WHERE status = 'pending';

如果 九成以上的订单都已完成、只有少量待处理，这个索引会非常小而且非常快 —— 代价是它只能服务于同样带该条件的查询。

② 表达式索引

对计算结果建索引，而不是对原列：

CREATE INDEX idx_users_lower_email ON users (lower(email)); -- 之后这条查询才能用上索引： SELECT * FROM users WHERE lower(email) = 'a@b.com';

关键点：查询里必须写完全一样的表达式，否则索引不生效。这是最容易踩的坑。

③ 覆盖索引 / INCLUDE

把查询需要的额外列附带在索引里，实现 index-only scan：

CREATE INDEX idx_orders_cover ON orders (customer_id) INCLUDE (total, created_at); -- 下面这条查询不必回表： SELECT total, created_at FROM orders WHERE customer_id = 42;

好处是完全不回表；代价是索引变大，且 INCLUDE 列不参与排序与查找。

建索引也要讲究：CONCURRENTLY 与维护

普通的 CREATE INDEX 会锁表阻塞写入。在生产库上给一张大表加索引，可能造成几分钟不可写。

安全做法（不阻塞写入）： CREATE INDEX CONCURRENTLY idx_big ON big_table (col); 代价与注意： · 需要扫两遍表，总耗时更长 · 不能放在一个事务块里执行 · 如果中途失败，会留下 INVALID 状态的索引 —— 要 DROP 掉重来 · 增加了 CPU 与 IO 负担，最好挑低峰

定期维护同样重要：

VACUUM回收被更新/删除产生的死元组空间。不是可选项，autovacuum 通常够用但要盯着。
ANALYZE更新统计信息。优化器依赖它估算行数，信息过期会导致选错计划。
REINDEX重建膨胀的索引。pg 的索引会随着频繁更新出现膨胀（bloat）。
监控未使用索引长期零命中的索引白白占用空间并拖慢写入，应定期清理。

一个 PG 特有的重要机制：由于 MVCC 的实现方式，PostgreSQL 的更新是「插入新版本 + 标记旧版本」，所以频繁更新的表会产生大量死元组。没有及时 vacuum，表和索引都会膨胀 —— 这既是空间问题，也会让查询变慢。

怎么判断索引有没有生效

EXPLAIN (ANALYZE, BUFFERS) SELECT ... 重点看这几件事： · Index Scan / Index Only Scan → 说明用上了索引 · Seq Scan → 全表扫描，要想想为什么 · rows=... 的估算值与实际值差多少 → 差得远说明统计信息过期（ANALYZE） · Buffers: shared read vs hit → 读了多少数据块、多少来自缓存 · Index Only Scan 的 Heap Fetches → 是否真的没回表 估算行数严重不准是最常见的「索引失效」原因： 优化器以为只命中 10 行实际是 10 万行 → 选错了计划

几条判据：

  1. 低选择性的列单独建索引通常没用（性别、布尔值）。
  2. 列被函数或隐式转换包裹时索引失效（用表达式索引解决）。
  3. 复合索引遵循最左前缀，列序很重要：把等值条件列放在前面，范围/排序列放在后面。
  4. 小表没必要建索引 —— 优化器会正确地选择顺序扫描。

深入自检

GIN 和 GiST 到底怎么选？

看数据的组织方式。GIN 是倒排结构：一个键指向很多行，适合「某个值出现在哪些行」这类包含关系（数组、jsonb、全文），查询快但更新代价高。GiST 是通用搜索树：适合范围重叠、邻近距离这类谓词（几何、范围类型），更新比 GIN 便宜。查多更推荐 GIN，写多且用邻近语义则看 GiST。

BRIN 为什么能这么小？

因为它不记录每一行，而是记录每个物理区块的取值范围（最小值/最大值）。查询时用这个范围粗筛，跳过大量明显不含目标的区块。它的有效性完全依赖「数据的物理顺序与索引列相关」 —— 时序数据天然满足这一点。反过来，如果数据被打乱插入，BRIN 就几乎失去作用。

为什么 index-only scan 有时候还要回表？

因为 PostgreSQL 需要确认这一行对当前事务是否可见，这个信息不在索引里而在堆表（堆元组的可见性信息）。当表刚刚被 vacuum 且 visibility map 已标记该页全可见时，才能真正跳过回表。所以想让 index-only scan 充分发挥，良好的 vacuum 策略是前提。

autovacuum 不是自动的吗，为什么还要操心？

它是自动的，但默认参数是保守的。对频繁更新或删除的大表，默认阈值可能跟不上死元组产生速度，导致表持续膨胀。常见动作包括：针对热点表单独调低触发阈值、增加 worker 数量、以及避免长时间运行的事务 —— 因为长事务会阻碍死元组的回收。
