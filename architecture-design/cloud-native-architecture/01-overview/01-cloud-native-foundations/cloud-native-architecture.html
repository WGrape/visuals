云原生架构：定义、原则与核心技术栈

为云环境而生的一套方法论：容器化、微服务、不可变基础设施、声明式 API。

云原生四要素 CNCF

CNCF 技术雷达的核心构成

云原生不是某一项技术，而是『把应用设计成天然适合在云上弹性运行』的方法论。关键特征：容器打包、动态编排（K8s）、微服务拆分、通过声明式配置描述『期望状态』而非操作过程。

与微服务的区别

  • 微服务是架构风格（怎么拆）；云原生是落地体系（怎么在云上跑好微服务）。
  • 云原生包含微服务，但还涵盖容器、编排、可观测性、DevOps 等全栈能力。

12-Factor 是云原生的前身

详见同章『12-Factor 应用』一节：一份把应用做成『云友好』的经典清单（基准代码、依赖、配置、后端服务等）。

面试高频问答

Q：为什么云原生强调『不可变基础设施』？
A：服务器一旦部署就不再手动改，任何变更都通过重新构建镜像+重新发布完成。好处是可复现、可回滚、避免『雪花服务器』（每台都偷偷不一样）导致的诡异故障。
Q：Service Mesh 解决了什么？
A：把服务间通信（重试、熔断、加密、追踪）从业务代码下沉到独立 Sidecar 代理，让业务只关心逻辑；是微服务治理的进一步解耦。

云原生：不是「上云」，是「为云而生」

把单机应用搬到云主机上，那叫「云托管」（Cloud Hosting），不叫云原生。云原生的关键是应用的构建与运行方式要充分利用云的特性——弹性、分布式、按需、自动化。

CNCF 定义在公有云、私有云、混合云等动态环境中，构建和运行可弹性扩展的应用
四项技术支柱容器 · 服务网格 · 微服务 · 不可变基础设施 + 声明式 API
核心目标快速迭代、弹性伸缩、故障自愈、资源高效利用
判断标准能否分钟级扩容？能否自动恢复？能否一天发布多次？
云原生四层能力栈：基础设施 → 运行时 → 编排 → 应用

云托管 vs 云原生：具体差别在哪

维度传统云托管云原生
部署单位整机（虚拟机），手工装环境容器镜像，不可变，一次构建到处运行
扩缩容提前买机器，扩容需小时级按指标自动伸缩，分钟甚至秒级
故障恢复人工发现、人工重启健康检查 + 自动重启 + 自动漂移
发布停机发布或半夜发布，回滚困难滚动/蓝绿/金丝雀，秒级回滚，一天多次
配置散落在机器上的配置文件配置中心 / ConfigMap，集中管理与动态刷新
资源利用按峰值常备，平时浪费按需分配 + 混部，利用率大幅提升
状态应用在本地磁盘存状态无状态化，状态外置到数据库/对象存储
运维方式SSH 上机器改配置（宠物模式）声明式描述期望状态，系统自动收敛（牲畜模式）

一句话区分：云托管是「把原来的运维方式搬到云上」；云原生是「改变运维方式本身」——从命令式（我做了一步步操作）转向声明式（我要什么结果）。

四项技术支柱

① 容器（Container）

把应用及其所有依赖打包成一个标准镜像，保证「在我机器上能跑」不再是个问题。

  • 轻量（共享内核，秒级启动）vs 虚拟机（独占内核，分钟级）
  • 不可变：运行中不改容器，改了就重新构建镜像

② 微服务（Microservices）

按业务能力拆分，独立开发、独立部署、独立伸缩。

  • 是云原生的应用组织方式——不拆微服务也能容器化，但无法获得独立伸缩与快速交付的收益

③ 服务网格（Service Mesh）

把服务间通信的治理能力（mTLS、重试、熔断、限流、追踪）下沉到基础设施，以 Sidecar 形式部署，业务代码零感知。

  • 代表：Istio、Linkerd
  • 代价：复杂度与资源开销，小系统未必需要

④ 不可变基础设施 + 声明式 API

服务器不再被手工修改，而是「坏了就换新的」；你只声明期望状态（我要 3 个副本），系统负责达成并维持。

  • Kubernetes 是这一思想的代表实现
  • 好处：可重现、可版本化（Infrastructure as Code）、减少配置漂移

落地云原生的前提清单

云原生不是买一套 K8s 就完事。下面这些是真正的门槛，缺项会导致上云后反而更痛苦：

① 应用无状态化会话外置到 Redis、文件外置到对象存储、定时任务独立部署
② 配置外置配置进 ConfigMap/配置中心，镜像不含环境相关配置
③ 优雅启停实现 readiness/liveness 探针与 SIGTERM 优雅关闭
④ 可观测性结构化日志输出到 stdout、暴露 Prometheus 指标、接入链路追踪
⑤ CI/CD 流水线镜像构建、扫描、推送、部署全自动，可回滚
⑥ 资源管理为容器设 requests/limits，否则会被 OOMKill 或挤占他人资源
⑦ 团队能力需要懂声明式配置、容器网络、存储卷、调度策略的人

常见反模式：把容器当虚拟机用（SSH 进去改配置）、在容器里跑多个进程、不设资源限制、日志写本地文件、把有状态应用（数据库）随便塞进 K8s 而不做可靠存储与备份方案。

收益与代价

  • 收益：交付速度（一天多次发布）、资源利用率（混部与弹性可省 30%~50%）、可用性（自动自愈与滚动发布）、可移植性（跨云厂商）。
  • 代价：技术栈复杂度陡增（K8s、Service Mesh、Operator、Helm 等）、学习曲线陡、调试更间接（多一层抽象）、小规模时运维成本可能超过收益。
  • 务实建议：小团队与小系统可以先只用「容器 + 托管 K8s + CI/CD」，暂不上 Service Mesh 与自建 Operator；先享受标准化与自动部署的收益，再逐步演进。

深入自检

不上 Kubernetes 就不算云原生吗？

不一定。Kubernetes 是云原生的事实标准编排层，但云原生的本质是方法论：容器化、微服务、声明式、弹性、可观测、自动化交付。用云厂商的 Serverless 产品（如函数计算、容器服务）也能达成这些目标，且不直接管理 K8s。反过来，用了 K8s 但应用仍有状态、手工改配置、发布靠人肉，那也不算云原生——只是把旧应用放进了新容器。判断标准是行为而不是工具：能否自动扩容？能否自动恢复？能否一键回滚？能否按需付费？

容器和虚拟机到底有什么区别？

核心区别在隔离层次：虚拟机通过 Hypervisor 虚拟出完整硬件，每个 VM 跑自己的操作系统内核，隔离性强、开销大（GB 级内存、分钟级启动）；容器共享宿主机内核，只用 Namespace 做视图隔离、Cgroup 做资源限制，因此轻量（MB 级、秒级启动）、密度高。代价是隔离性弱于 VM（同一内核，内核漏洞影响面大），所以有安全强隔离需求时会用安全容器（Kata Containers、gVisor）或干脆用 VM。一句话：VM 隔离操作系统，容器隔离进程视图。

为什么强调「不可变基础设施」？

因为它消灭了「配置漂移」这个运维噩梦。传统方式下，服务器运行久了会累积各种手工改动，两台本应相同的机器可能已经完全不同，谁也说不清它们差在哪——这就是为什么重装往往比排查更快。不可变基础设施规定：运行中的实例永不被修改，要变更就构建新镜像、起新实例、销毁旧的。好处是环境完全可重现、回滚就是切回上一个镜像版本、扩容出来的新实例与老实例必然一致。代价是构建与发布链路必须自动化，否则改个小配置也要走完整流程会很痛苦。

小团队值得上云原生吗？

要看规模与目标。3~5 人、单个应用、流量平稳的团队，直接上 K8s 往往是净负担——学习成本和运维开销会超过收益，用云厂商的托管服务（PaaS）或直接 Serverless 更划算。但如果：业务有明显波峰波谷需要弹性、需要一天多次发布、有多个服务需要统一管理、或预期会快速增长，那么尽早容器化 + 用托管 K8s 是值得的。推荐路径：先容器化（收益立刻可见）→ CI/CD 自动化 → 托管 K8s → 按需引入服务网格与 Operator。每一步都能独立产生价值，不必一次到位。
