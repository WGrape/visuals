01用 perf 测 CPI 与瓶颈类型

经验阈值：CPI < 0.5 通常计算密集；CPI > 1 多半在等内存或分支。CPI 高看 cache-miss，分支多折看 branch-miss。

# 统计一段程序的硬件计数器
perf stat -e cycles,instructions,cache-misses,branch-misses ./app
# 关注：
#   CPI = cycles / instructions  （>1 多说明停顿多）
#   cache-misses 高 -> 内存受限
#   branch-misses 高 -> 分支预测差

02套 Amdahl 算加速上限

要点：Amdahl 的教训：优化前先用 perf 找到「串行热点」在哪。把 1% 的串行改成并行毫无意义，把 90% 的热点并行化才是正路。
def speedup(p, n):
    # p: 可并行比例(0~1), n: 处理器数
    return 1 / ((1-p) + p/n)
print(speedup(0.9, 8))    # 约 4.7x
print(speedup(0.9, 100))  # 约 9.2x，收益已很小
# 串行部分 10% 时，无论堆多少核，上限 10x

03画 Roofline 看卡点

Roofline 用「算术强度 = FLOPs / 字节」做横轴，纵轴是可达性能（FLOPs/s）。应用点落在「带宽斜坡」还是「算力天花板」决定该优化什么。

你的点落在含义该怎么做
斜坡区（左）被内存带宽限制减少访存、提升缓存命中、用向量化
天花板（右）被算力限制减少冗余计算、用更快指令/更多核
二者之间部分重叠先算算术强度再定方向
  • 工具：Intel VTune、pcm-memory（测内存带宽）、likwid（测 FLOPs 与强度）。
  • 先量算术强度 = 总 FLOPs / 总访存字节，再对照机器的峰值带宽与峰值算力。

04常用工具清单

  • perf：Linux 通用，计数器丰富。
  • VTune / pcm：Intel 平台细到顶层的 Top-down 分析。
  • likwid：轻量，适合批量测 FLOPs 与带宽。
  • nvvp / Nsight：GPU 侧对应工具。
问：CPI 很低但程序还是很慢，为什么？

CPI 低只说明「每条指令停顿少」，不代表「干的活有用」。可能是指令总数太大（算法低效）、或 true 受限于内存带宽（看 cache-miss 与算术强度），这时要看 Roofline 而非 CPI。

第一层 · 概念与判定：先看哪个指标

性能指标分三类：延迟（单次耗时分布）、吞吐（单位时间处理量）、利用率（资源占用）。先问业务痛点是「慢」还是「撑不住」，再选指标，别一上来只看平均。

业务痛点主看指标
用户觉得卡延迟 p95/p99
担心顶不住峰值吞吐/QPS + 利用率
成本高想缩容利用率峰值
偶发卡顿难复现尾部延迟分布

性能观测命令与分位

# 常见观测命令
top -H -p $PID              # 看线程级 CPU
iostat -x 1                 # 磁盘 util/await
perf stat -p $PID -a        # 指令数/缓存命中
# 分位延迟别只看 avg：用直方图或 p99
# 例：QPS=1000, p99=200ms -> 平均在途请求 ≈ 1000*0.2 = 200（Little 定律）

数量级：人类可感知的卡顿约 >100ms；p99 延迟常是 avg 的 3–10 倍；CPU 利用率 70% 以上排队效应开始明显。

第三层 · 排障与边界：四个坑

  • 只看平均值：avg 掩盖长尾，1% 的请求 10 秒超时在 avg 上毫无痕迹——必须看 p99/p999
  • 协调忽略（coordinated omission）：压测工具在响应回来前不发下一个，测出的「延迟」不含排队等待，严重低估真实尾延迟
  • 指标错配：用吞吐量当延迟、用 CPU 当瓶颈——先定位受限资源（CPU/IO/锁/带宽）再谈优化
  • 采样率太低：p99 需要足够样本，每秒几个请求的采样窗口拉太长，尾延迟被平滑掉

第四层 · 原理与取舍

为什么 p99 比平均值更能代表用户体验？

因为用户记住的是最差的那几次，而不是平均。平均延迟 20ms 可能藏着 1% 的请求 2 秒超时，这 1% 就是投诉来源。分位（p95/p99/p999）刻画分布尾部，正是 SLO/可用性承诺的对象；avg 把头和尾一平均，把问题抹平了。

Little 定律 L=λW 在调优里有啥用？

它说系统内平均在途请求数 = 到达率 × 平均驻留时间。给定 QPS 和延迟就能反推并发压力，或反过来：想降在途数要么降到达率（限流）要么降驻留时间（优化）。它是容量规划的地基——不用拆系统内部，仅凭三个宏观量就能判断「是不是快撑爆了」。

coordinated omission 为什么会让压测结论失真？

因为传统压测是「等上一个回包才发下一个」，系统一旦变慢，发压也跟着变慢，于是慢的那段没被充分施加压力，测出来的延迟不含真实排队等待。正确做法是用「开环」压测（按固定速率发，不等回包），才能暴露高负载下的尾延迟。很多性能报告因此过于乐观。
