PostgreSQL 整体架构

进程模型、共享内存与连接管理——理解 PG 与 MySQL 线程模型的根本差异。

① 进程模型：一连接一进程

PostgreSQL 采用 多进程（Process-per-connection） 架构：一个 postmaster 主进程负责监听端口、派生和管理后端进程；每个客户端连接由一个独立的 postgres 后端进程服务。这与 MySQL（InnoDB）的 多线程 模型（一连接一线程，共享同一进程地址空间）是根本区别。

为什么重要：进程间内存隔离，单个连接崩溃（段错误）通常不会拖垮整个实例；但每个连接约占用 5~15MB 私有内存，高并发下连接数成本高，因此 PG 强烈依赖 PgBouncer 这类连接池。

③ 共享内存区域

所有后端进程通过一块 共享内存（Shared Memory） 交换数据，主要包含：

  • Shared Buffers：数据页缓存（默认 128MB，建议设为物理内存 25%），相当于 MySQL 的 Buffer Pool。
  • WAL Buffers：预写日志缓冲区，提交前先写这里再刷盘。
  • 锁表 / 进程表：全局锁与连接状态。
  • 行列可见性信息：MVCC 需要的事务状态（clog）。

④ 连接模型与权衡

维度PostgreSQL（进程）MySQL（线程）
连接开销高（每连接独立进程 + 内存）低（线程轻量）
隔离性强（地址空间隔离）弱（共享地址空间，一处崩全崩）
连接池需求强依赖（PgBouncer）可选
并发上限受进程数限制（数百~数千）线程可更多
实践：生产环境务必在应用与 PG 之间部署 PgBouncer 并采用 transaction 或 pool 模式，把成千上万的应用连接收敛成几十个后端连接。
