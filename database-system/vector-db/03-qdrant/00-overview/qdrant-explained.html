Qdrant 向量数据库原理

Rust 编写的向量搜索引擎：HNSW 索引、量化压缩与强大的结构化过滤

① 定位 ② 架构与数据模型 ③ 索引与量化 ④ 过滤检索 ⑤ 上手示例 ⑥ 与 Milvus 对比
一句话总结：Qdrant 是用 Rust 编写的开源向量数据库， 最大特色是把向量检索与结构化过滤（payload filter）深度结合—— 它能在带过滤条件的场景下依然保持高性能，这是很多向量库做不到的。 同时提供标量量化（压缩向量、省内存）与简洁的 REST/gRPC API，部署轻量。

01定位与特点

🦀 Rust 实现

内存安全、无 GC 停顿，单机性能与资源占用表现优秀。 编译后是单个二进制，部署极简（Docker 一条命令）。

🎯 过滤能力最强

原生支持任意 payload 字段的过滤与组合， 并针对"带过滤的 ANN"做了专门优化（可用 payload 索引预筛）。

💾 量化省内存

支持标量量化（int8）把向量压到 1/4， 大库场景下内存成本大幅下降，精度损失可控。

🔌 API 友好

REST + gRPC 双接口，官方多语言客户端齐全， 本地模式（in-memory / on-disk）便于开发与测试。

适合：RAG 应用、推荐、语义搜索，尤其是需要带业务条件过滤的检索场景。

03索引机制与量化

HNSW 索引

Qdrant 默认使用 HNSW（分层可导航小世界图）作为向量索引。 它构建多层图结构，检索时从最上层"粗图"快速定位区域，再逐层下钻到最底层精搜。

  • m：每个节点连接的邻居数（越大图越密、越准，内存越大）。
  • ef_construct：建索引时的候选队列大小（越大索引质量越高、构建越慢）。
  • ef（ef_search）：检索时的候选队列大小（越大越准、越慢）——运行时可调，是精度/延迟的主要旋钮。

标量量化 Scalar Quantization

图 2：标量量化用 1/4 内存换取极小的精度损失
Qdrant 的量化用法要点：开启量化后， 检索过程先用量化向量粗排，再对 Top-K 候选用原始向量重打分（rescore / oversampling）。 这样既省内存又保住了最终精度——不要只量化不重打分。

存储策略

策略说明适用
In Memory向量全放内存数据量小、追求极致延迟
Memmap用 mmap 映射到磁盘，靠 OS page cache数据大于内存但可接受部分抖动
On-disk（量化）量化后的向量存盘，原始向量可选保留超大规模、成本敏感

04带过滤的检索（核心优势）

真实业务几乎不会"纯向量检索"——总要加条件，比如 「找相似商品，但只要上架的、价格 < 500 的、且属于某品类」。

图 3：过滤 + ANN 的协同流程
# 带过滤的检索（Python 客户端）
from qdrant_client import QdrantClient
from qdrant_client.models import Filter, FieldCondition, Range

client = QdrantClient(host="localhost", port=6333)

hits = client.search(
    collection_name="products",
    query_vector=query_emb,
    query_filter=Filter(
        must=[                                    # AND
            FieldCondition(key="in_stock", match={"value": True}),
            FieldCondition(key="price",   range=Range(lt=500)),
        ],
        should=[                                  # OR
            FieldCondition(key="category", match={"value": "phone"}),
            FieldCondition(key="category", match={"value": "tablet"}),
        ]
    ),
    limit=10,
    search_params={"hnsw_ef": 128},   # 运行时调 ef：越大越准越慢
)

05上手示例

# 启动（Docker 一行）
docker run -p 6333:6333 -v ./qdrant_storage:/qdrant/storage qdrant/qdrant

# 建集合
client.create_collection(
    collection_name="docs",
    vectors_config={"size": 768, "distance": "Cosine"},
    quantization_config=ScalarQuantization(      # 可选：开启标量量化
        scalar=ScalarQuantizationConfig(type="int8", quantile=0.99, always_ram=True)
    ),
)

# 写入
client.upsert(
    collection_name="docs",
    points=[
        PointStruct(id=1, vector=emb1, payload={"title": "...", "year": 2026}),
        PointStruct(id=2, vector=emb2, payload={"title": "...", "year": 2025}),
    ],
)

# 给过滤字段建 payload 索引（重要！）
client.create_payload_index("docs", field_name="year", field_schema="integer")
实践提醒：忘了建 payload 索引是 Qdrant 最常见的性能问题—— 没有索引时过滤会退化成逐条比对 payload，QPS 断崖式下降。 凡是要用于过滤的字段，务必提前建索引。

06Qdrant vs Milvus

维度QdrantMilvus
语言RustGo + C++
部署复杂度极简（单二进制 / 单容器）较重（etcd、MinIO 等多组件）
扩展性支持分片与副本，集群能力逐步增强为超大规模设计，组件拆分彻底
过滤能力很强，payload 索引类型丰富支持属性过滤，语义略有差异
量化标量量化成熟IVF_PQ / SQ 等多种量化
适用规模百万～千万级，中小团队首选千万～百亿级，大规模生产
上手成本低较高
选型直觉：项目规模中等、希望快速落地 + 过滤条件复杂 → Qdrant； 数据量达到亿级、需要完善的分片/多租户/运维体系 → Milvus。 两者都开源，Qdrant 的本地模式（无需服务端）也非常适合原型开发。
