命令不是背出来的，是「按对象」组织的

Redis 有 200+ 条命令，但结构非常清晰：前缀字母就对应数据结构——SET/GET 是 String，HSET/HGET 是 Hash，LPUSH/RPOP 是 List，SADD 是 Set，ZADD 是 ZSet，XADD 是 Stream。没有前缀的就是通用命令（键管理、事务、服务端）。按这条线索记，命令表就不再是零散清单。

高频踩坑与最佳实践

① 危险命令必须治理

  • KEYS *：全库遍历，O(N) 阻塞，生产禁用。
  • FLUSHALL / FLUSHDB：清空数据，用 rename-command 改名或 ACL 禁掉。
  • 大 LRANGE 0 -1 / HGETALL / SMEMBERS：大 Key 会拖垮实例。
  • MONITOR：吞吐极高时直接把实例打满，只短时调试用。

② 过期与删除

  • EXPIRE 只对键整体生效，Hash 字段不能单独过期。
  • 惰性删除 + 定期删除：过期键不一定立刻释放内存，可能短暂超 maxmemory。
  • 大量键同时过期会造成「过期风暴」，加随机抖动错峰。
  • UNLINK 替代 DEL 删除大键，后台异步回收。

③ Pipeline 与事务

  • Pipeline 只省网络往返，不保证原子。
  • MULTI/EXEC 保证原子，但不支持回滚（语法错全不执行，运行错继续执行）。
  • 需要「读-判断-写」原子时用 Lua 或 SET NX 这类单命令原语。
  • 批量要分片：一次 Pipeline 别塞几万条，按 100-500 切。

④ 观察与排障

  • SLOWLOG GET 找慢命令，重点看 O(N) 类。
  • INFO commandstats 看各命令调用次数与耗时占比。
  • --bigkeys / --memkeys 扫大 Key。
  • CLIENT LIST 找异常连接与阻塞来源。

深入自检

为什么要禁用 KEYS 命令？

KEYS 会遍历整个键空间并一次性返回，时间复杂度 O(N) 且结果一次性组装。Redis 是单线程处理命令，百万级键的实例上执行 KEYS 会造成数百毫秒到数秒的阻塞，所有其他请求全部排队。替代方案是 SCAN：游标分批、每次 O(1)，不会阻塞。

SET key val EX 60 和 SET + EXPIRE 有什么区别？

前者是原子的，一条命令完成写入与过期设置；后者是两条命令，如果第一条成功、第二条因网络或崩溃未执行，这个键就变成了永不过期的「僵尸键」。分布式锁场景尤其致命——必须用 SET 的 NX/PX 参数一次完成。

Pipeline 和事务（MULTI）应该选哪个？

目标不同：Pipeline 解决「网络往返太多」，不保证原子；MULTI/EXEC 解决「一批命令要连续执行不被打断」，保证原子但仍是逐个执行。只追求吞吐用 Pipeline；需要原子性用 MULTI，需要「读判断+写」的原子复合逻辑用 Lua 脚本。

什么时候该用 Hash，什么时候用 String 存对象？

对象字段经常单独读写/更新（如只改用户昵称）→ Hash，省带宽且部分更新；对象整体读写、字段稳定且很小 → 序列化成 String 更简单，且能整体设置过期时间。注意 Hash 字段不能单独设过期，且字段很多时要用 HSCAN 而不是 HGETALL。

SCAN 为什么会漏键或重复？

SCAN 采用游标增量遍历，遍历期间如果发生扩容/缩容（rehash），某些键可能被重复返回，极少数情况可能漏掉。这是设计上的权衡：用「可能重复、可能少漏」换取不阻塞。业务侧要幂等处理（去重），且 SCAN 不保证完整快照。

分布式锁用 SETNX 有什么隐患？

经典隐患有三个：① SETNX 与 EXPIRE 非原子，可能留下永不过期的锁；② 业务执行超时导致锁过期，误删别人的锁；③ 释放锁时没校验持有者。正确做法：SET key random_value NX PX timeout；释放时用 Lua 脚本比对 value 再删除；超长业务要配锁续期（看门狗）。单实例锁在故障切换下不绝对安全，强一致场景用 Redlock 或其他协调服务。
