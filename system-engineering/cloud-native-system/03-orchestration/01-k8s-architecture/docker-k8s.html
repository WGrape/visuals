📚 核心概念 & 关键机制

🔌 Service 如何找到 Pod？— Label Selector 机制

这是最容易困惑的地方，Service 不是通过 IP 找 Pod 的，而是通过 Label Selector（标签选择器）！

  • Pod 上有标签（Labels）：例如 app=web version=v1
  • Service 定义 Selector：selector: app=web
  • K8S 自动匹配：所有带 app=web 标签的 Pod 都会被该 Service 发现
  • 动态更新：新创建的 Pod 如果标签匹配，会自动加入 Service 的负载均衡池

👉 类比：Service 是个"招聘负责人"，Label 是"技能标签"，有对应技能的 Pod 都会被"录用"（加入负载均衡）。

📦 Pod 与 Container 的关系

Pod 是 K8S 的调度单元，Container 是 Docker 的运行实例。

  • 每个 Pod 有一个 Pause 容器：负责持有网络命名空间（Network Namespace），提供共享网络
  • 用户容器共享网络：同一 Pod 内的所有容器共享同一个 IP 和端口空间，localhost 可以直接通信
  • 共享存储：通过 Volume 挂载，同一 Pod 内容器可以访问同一份数据

⚙️ Ingress Controller vs Ingress — 别搞混了！

  • Ingress = 路由规则的"配置文件"（类似 nginx.conf），是 K8S 的 API 对象
  • Ingress Controller = 实际执行路由的"服务器"（类似 NGINX 进程），它本身是一个 Pod
  • 类比：Ingress 是"菜谱"，Ingress Controller 是"厨师"

🔍 核心机制深解：Service 如何通过 Label Selector 找到 Pod

📋 完整工作流

  1. Pod 被打标签：创建 Pod 时，在 metadata.labels 中定义标签，如 app: web
  2. Service 定义 Selector：在 spec.selector 中写明要匹配的标签
  3. K8S 自动建立关联：K8S 的控制器会持续监听，所有标签匹配的 Pod 自动加入该 Service 的 Endpoints 列表
  4. 负载均衡：Service 收到请求后，根据 Endpoints 列表将请求转发到某个 Pod
  5. 动态更新：当有新 Pod 创建（标签匹配）或旧 Pod 删除时，Endpoints 列表会自动更新

📝 实际 YAML 示例

# Pod 的定义（注意 metadata.labels）
apiVersion: v1
kind: Pod
metadata:
  labels:
    app: web        # ← 这个标签会被 Service 匹配
    version: v1
spec:
  containers:
  - name: nginx
    image: nginx:1.25

---
# Service 的定义（注意 spec.selector）
apiVersion: v1
kind: Service
metadata:
  name: service-a
spec:
  selector:
    app: web      # ← 匹配所有带 "app: web" 标签的 Pod
  ports:
  - port: 80
    targetPort: 8080
  type: ClusterIP

K8S 会自动发现所有 labels: app=web 的 Pod，并将它们加入 Service A 的负载均衡池。

🏗️ 完整层级关系（从下到上）

① 基础设施层 物理机 / 虚拟机（Node）— K8S 的工作节点
② 容器运行时层 Docker / containerd — 负责拉取镜像和运行容器
③ Pod 层 K8S 最小调度单元 — 包含一个或多个共享网络的容器
④ Deployment 层 管理 Pod 副本数量 — 负责滚动更新、回滚、自愈
⑤ Service 层 稳定访问入口 + 负载均衡 — 通过 Label Selector 发现 Pod
⑥ Ingress Controller 层 实际处理外部流量的反向代理（NGINX）— 本身是一个 Pod
⑦ Ingress 层 HTTP 路由规则定义（K8S 资源对象）— 被 Controller 读取

注意：③→④→⑤ 可类比为：容器 → 管理容器的副本集 → 暴露服务的入口

Docker 与 K8s 的分工

一句话：Docker 解决「一个应用怎么打包和跑起来」，K8s 解决「一千个容器怎么调度、怎么自愈、怎么伸缩」。K8s 并不依赖 Docker（1.20 后已弃用 dockershim，改用 containerd + CRI）。

Docker 实践

# Dockerfile 最佳实践（多阶段 + 瘦身 + 非 root）
FROM golang:1.22 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download                       # 依赖单独一层，充分利用缓存
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o /app ./cmd/server

FROM gcr.io/distroless/static-debian12    # 运行镜像只有几 MB
COPY --from=build /app /app
USER 10001                                # 非 root
ENTRYPOINT ["/app"]

# 构建与运行
docker build -t app:v1 .
docker run -d --name app -p 8080:8080 --memory=512m --cpus=1 app:v1
docker logs -f app
docker exec -it app sh                    # distroless 没有 shell！调试要用 busybox 版
docker stats                              # 看实时资源

# 镜像瘦身对比
#   golang:1.22 基础        ~800 MB
#   alpine                  ~5 MB（但 musl，CGO 有问题）
#   distroless/static       ~2 MB
#   加 -ldflags "-s -w"     再减 30%

K8s 命令

# 部署一个服务（最小可用）
kubectl create deployment app --image=app:v1 --replicas=3
kubectl expose deployment app --port=80 --target-port=8080
kubectl scale deployment app --replicas=10
kubectl set image deployment/app app=app:v2          # 滚动更新
kubectl rollout status deployment/app
kubectl rollout undo deployment/app                  # 回滚（秒级）

# 排障三板斧
kubectl get pods -A                       # 看状态
kubectl describe pod <pod>                # <b>看 Events，90% 的原因在这里</b>
kubectl logs <pod> [-c container] [--previous]   # 看日志（--previous 看崩溃前的）

# 常见状态与原因
#   Pending       -> 资源不够 / 没有可调度节点（describe 看 Events）
#   ImagePullBackOff -> 镜像拉取失败（名字/标签/私有仓库鉴权）
#   CrashLoopBackOff -> 容器启动即退出（看 logs --previous）
#   OOMKilled     -> 内存超限（调 resources.limits.memory）
#   Running 但不可用 -> readinessProbe 失败

# 资源限制（必须配）
resources:
  requests: { cpu: "100m", memory: "128Mi" }   # 调度依据
  limits:   { cpu: "500m", memory: "512Mi" }   # 硬上限（内存超了会被 OOMKill）
Docker 被 K8s 弃用了吗？

准确说法是 K8s 弃用了 dockershim（1.20 弃用、1.24 移除），不再直接支持 Docker 作为运行时。但Docker 构建的镜像仍然完全可用——因为大家用的都是 OCI 标准镜像，K8s 通过 CRI 接口调 containerd/CRI-O 来运行，而 containerd 本来就是 Docker 的底层组件。所以对开发者来说：本地继续用 Docker 构建，集群里用 containerd 运行，没有任何影响。

Pod 和容器是什么关系？

Pod 是 K8s 的最小调度单位，可以包含 1 个或多个容器。同一个 Pod 里的容器共享网络命名空间（同一个 IP、可以用 localhost 互访）和共享 volume。多容器 Pod 的典型用法是 sidecar 模式：主容器跑业务，sidecar 跑日志采集/服务网格代理/配置同步。注意：Pod 是短暂的，重建后 IP 会变——所以访问服务要走 Service 而不是直接连 Pod IP。

requests 和 limits 该设多少？

requests 是调度依据（K8s 保证节点上所有 requests 之和不超过节点容量），limits 是硬上限。实践：① 都用压测得出，CPU 按 P99 用量的 1.2 倍，内存按峰值 ×1.3；② CPU limit 可以不设（CPU 是可压缩资源，超了只是变慢不会挂），但要设 requests 保证调度；③ 内存 limit 必须设（不设会在节点内存紧张时把整个节点搞挂），且要给 JVM 类应用留足（容器内存 limit 要大于 -Xmx 的 1.3 倍，否则会被 OOMKill）。
