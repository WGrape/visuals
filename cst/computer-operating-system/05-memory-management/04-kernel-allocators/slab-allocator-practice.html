Slab 分配器：观测、调参与泄漏排查

从 /proc/slabinfo 到内核参数，把 Slab 理论落到可操作的观测与调优。

理论页把 Slab 的 object/buffer/page 三层结构讲清楚了。本页聚焦可操作部分：怎么看 slab 占了多少、怎么调每 slab 的批量与回收、以及 dentry/inode 缓存暴涨时如何快速止血。

01观测：slabtop 与 /proc/slabinfo

最常用的是 slabtop（实时排序）和 /proc/slabinfo（持久可读）。要看某个 cache 的细节，直接读 sysfs。

  • slabtop -s c # 按 cache 大小排序，立刻看到谁是内存大户
  • cat /proc/slabinfo | awk '$3*$4 > 1048576' # 单 cache 占用 >1MB 的
  • ls /sys/kernel/slab/ # 每个 slab cache 一个目录
  • cat /sys/kernel/slab/kmalloc-2k/object_size # 单个对象大小
# 看 dentry / inode 这两个最容易暴涨的 cache
grep -E '^(dentry|inode_cache)' /proc/slabinfo
# 输出示例（各列含义见下）：
# name <active_objs> <num_objs> <objsize> <objperslab> <pagesperslab> ...
# dentry  51234  52000   192   21    1 : tunables ...
# 关键：active_objs 接近 num_objs 且还在涨 => 对象被持续持有
要点：slabtop 的 OBJ 列和 /proc/slabinfo 的 active_objs 不等，是因为 slab 以整页批量分配，存在已分配但未使用的余量；真正判断泄漏看 active_objs 的增长趋势而非绝对值。

02调参：min_partial / cpu_partial / reclaim

每个 slab cache 在 sysfs 下都有 tunables，影响每 CPU 缓存批量和部分满 slab 的保留数量。

参数作用调大/调小的后果
cpu_partial每 CPU 部分满 slab 的对象上限调大=减少锁竞争但费内存
min_partial每 CPU 最少保留的部分满 slab 数调大=分配更快但更碎
order单 slab 占用页数的 2 的对数调大=减少内部碎片但更易分配失败
reclaim_account是否计入内存回收开启=压力下更易回收
# 临时调大某 cache 的 cpu_partial（重启失效，需内核开启 CONFIG_SLUB）
echo 120 > /sys/kernel/slab/kmalloc-2k/cpu_partial
# 永久生效需改启动参数或写 udev 规则；生产环境先观测再定
要点：SLUB（主流默认）下这些 tunables 大多直接写在 sysfs；老 SLAB 分配器才有 /proc/slabinfo 里的 tunables 列。调参前务必确认分配器类型：dmesg | grep -i slab。

03排查：slab 内存泄漏与 dentry 暴涨

典型症状是 free 显示可用内存不少，但 slab 持续上涨、业务 OOM。按下面顺序定位。

  • 先确认是哪种 cache 在涨：watch -n1 'grep -E "dentry|inode|buffer_head" /proc/slabinfo'
  • 若是 dentry/inode，多半是遍历大量小文件 + 未限制导致；可临时 drop：echo 2 > /proc/sys/vm/drop_caches（只清 dentry/inode，不丢数据）
  • 若是业务对象 cache，查对应内核模块/驱动是否有 kmalloc 未 kfree
  • 长期方案：限制容器 memory 或调大 vfs_cache_pressure（默认 100，调大=更积极回收 dentry/inode）
# vfs_cache_pressure：控制回收 dentry/inode 的积极性
# 默认 100；设为 200 表示比回收 page cache 更积极地回收目录项
sysctl -w vm.vfs_cache_pressure=200
# 写入 /etc/sysctl.conf 持久化
echo 'vm.vfs_cache_pressure=200' >> /etc/sysctl.conf
要点：drop_caches 的 1/2/3：1=pagecache，2=dentries+inodes，3=全清。生产只清 2 最安全；清 1/3 可能瞬间打满磁盘读（重新读回 page cache）。

04对比：buddy / slab / kmalloc

三者是分层关系：buddy 管页框，slab 在页上切对象，kmalloc 是 slab 对任意尺寸的封装。

机制管理单位适用场景
buddy页框(4KB 起，2 的幂)物理页分配，大块内存
slab固定大小对象内核对象（task_struct、inode 等）
kmalloc任意小对象驱动/内核里临时小内存
vmalloc虚拟连续、物理未必连续大块、不要求物理连续
问：为什么不用 kmalloc 直接管所有内存？

kmalloc 底层仍是 slab；slab 的价值是把同尺寸对象聚成一池，避免伙伴系统按页分配带来的内部碎片和初始化开销。
