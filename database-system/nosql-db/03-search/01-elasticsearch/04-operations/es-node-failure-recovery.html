副本为什么不能和主分片在同一台机器？

从「反亲和规则」到「节点宕机全流程恢复」，一步到位讲透

一、铁律：副本和主分片绝不共处一节点

Elasticsearch 有一条硬约束，叫 Shard Allocation Awareness（分片分配感知）

⚠️

错误配置 ES 会拒绝

如果把 P0 和 P0 的副本 R0 放在同一台 Node-1 上，该节点宕机时，数据和备份一起丢失——副本形同虚设。

✅

正确配置（ES 默认行为）

P0 在 Node-1，R0 在 Node-2。Node-1 宕机 → R0 在 Node-2 上毫发无损 → 立即提升为主分片，数据零丢失。

核心原因一句话：「不要把鸡蛋放在同一个篮子里」。如果主分片和它的副本在同一台物理机上，这台机器挂了，这个分片的所有数据就彻底没了。副本存在的意义就是「跨节点冗余」。

三、节点宕机后，ES 的 9 步完整恢复流程

从一个节点心跳丢失，到集群恢复 GREEN，中间发生了什么？

T+0s
① 心跳丢失 — Node-1 不再响应
Master 节点每隔 1 秒 ping 所有节点。连续 3 次无响应（默认 30s 超时），Master 判定 Node-1 已宕机。
T+30s
② Master 确认宕机 — 集群状态变为 RED
Master 发现 P0 的主分片在宕机节点上，该分片不可用 → 集群状态 RED（部分数据不可读写）。
T+30.1s
③ Master 检查副本 — 发现 R0 存活且数据最新
Master 查询集群元数据，发现 P0 的副本 R0 在 Node-2 上，且数据与主分片完全同步（in-sync replica）。
T+30.2s
④ 副本提升 — R0 立刻被提升为新主分片 P0'
Master 下发指令：将 Node-2 上的 R0 标记为新的主分片。此操作几乎瞬间完成，是内存中的元数据变更。
T+30.3s
⑤ 集群状态降级 — RED → YELLOW
新主分片 P0' 已就绪，数据可读写。但由于副本数量不足（少了一个 R0），集群变为 YELLOW。
T+30.4s
⑥ 协调节点更新路由表
所有节点更新内部路由表：P0 的新位置是 Node-2。后续写入和读取请求自动路由到新主分片。
T+30.5s
⑦ Master 发起副本重建
Master 选择 Node-3（健康节点，与 P0' 不在同一机器），下发指令：从 P0' 拷贝数据，创建新的 R0。
T+31s ~ T+?s
⑧ 数据拷贝 — 从新主分片全量同步到新副本
Node-3 从 Node-2 的 P0' 通过网络拷贝 Segments 文件。耗时取决于分片大小（可能秒级到小时级）。
T+?s
⑨ 副本就绪 — 集群恢复 GREEN
新 R0 在 Node-3 上创建完成，副本数恢复 → 集群 GREEN。整个过程对客户端透明。

四、几个你可能会追问的问题

Q1：如果 Master 节点自己宕机了怎么办？

其他 Master-eligible 节点会发起选举，选出新 Master。这个过程叫 Zen Discovery（ES7+ 用新的协调层）。 新 Master 上来第一件事就是读取集群元数据，然后接管故障恢复流程。所以即使 Master 挂了，恢复也不会中断。

Q2：如果在副本提升完成之前，又有新数据写入怎么办？

写入会失败并返回错误，因为目标主分片不可用。客户端需要重试。一旦副本提升完成（通常毫秒级），路由表更新后写入即可正常进行。
这就是为什么推荐设置 wait_for_active_shards=all —— 确保写入时所有副本都确认。

Q3：那副本设置几个合适？

至少 1 个副本（生产环境底线）。允许容忍 1 个节点宕机不丢数据。
如果集群很大（比如 10+ 节点），可设 2 个副本，容忍 2 个节点同时宕机。
代价：每增加 1 个副本，存储翻倍，写入延迟增加（需要等更多 ACK）。

Q4：acker 的分片分配感知怎么配置？

可以通过 cluster.routing.allocation.awareness.attributes 配置机架感知，确保分片不但在不同节点、更在不同机架/可用区。

ES 节点故障恢复的关键参数

参数默认值说明
discovery.zen.minimum_master_nodes（7.x 前）(master数/2)+1防脑裂。7.x 起由投票配置自动管理，不需要手动设
index.number_of_replicas1副本数。设为 1 时数据有 2 份，可容忍 1 节点故障
cluster.routing.allocation.node_concurrent_recoveries2单节点并发恢复的分片数，调大恢复快但影响查询
indices.recovery.max_bytes_per_sec40mb恢复带宽限速。恢复慢就调大（如 200mb）
cluster.routing.allocation.disk.watermark.low/high/flood85% / 90% / 95%超过 high 会把分片迁走；超过 flood 索引被只读
index.unassigned.node_left.delayed_timeout1m节点失联后等多久才开始重分配（避免短暂抖动触发大规模搬迁）
gateway.expected_nodes / recover_after_time—集群重启时等到 N 个节点才恢复，防恢复不完整
action.destructive_requires_namefalse设 true 可禁止 _all 的误删

分片恢复的三个阶段：① INIT 选目标节点；② INDEX 从其他副本拷贝 Lucene 文件（若主分片损坏）或本地加载；③ TRANSLOG 重放未刷盘的操作；④ FINALIZE 刷新并变为主分片。恢复期间该分片可查但较慢，整个集群健康度是 yellow。

排查与恢复命令

# 1) 看集群健康与分片状态
curl -s 'localhost:9200/_cluster/health?pretty'
# status: green(全分配) / yellow(主分片齐,副本缺) / red(有主分片缺失，该索引部分数据不可查)
# active_primary_shards、active_shards、unassigned_shards、relocating_shards

# 2) 定位未分配的分片及原因（最关键的一条命令）
curl -s 'localhost:9200/_cluster/allocation/explain?pretty'
# 返回 "deciders" 字段会明确写原因：
#   - the node is above the high watermark cluster setting        -> 磁盘满
#   - the shard cannot be allocated to the same node on which ... -> 副本不能与主分片同节点
#   - too many shards ...                                          -> 分片数超上限

# 3) 看恢复进度
curl -s 'localhost:9200/_cat/recovery?v&active_only=true'
# 字段：index shard time type stage files files_percent bytes bytes_percent
# type: peer(从副本拷) / snapshot(从快照) / empty_store(新建空分片)
# 4) 恢复动作
# 磁盘水位导致的无法分配：先清理磁盘或扩容，再触发重试
curl -XPOST 'localhost:9200/_cluster/reroute?retry_failed=true'

# 临时放宽水位（紧急）
curl -XPUT 'localhost:9200/_cluster/settings' -H 'Content-Type: application/json' -d '{
  "transient": { "cluster.routing.allocation.disk.watermark.low": "90%",
                 "cluster.routing.allocation.disk.watermark.high": "95%",
                 "indices.recovery.max_bytes_per_sec": "200mb" }
}'

# 分片数超限时提高上限
curl -XPUT 'localhost:9200/_cluster/settings' -H 'Content-Type: application/json' -d '{
  "persistent": { "cluster.max_shards_per_node": 3000 }
}'

# 确认某索引只读了（flood 水位触发）后解锁
curl -XPUT 'localhost:9200/<index>/_settings' -H 'Content-Type: application/json' -d '{
  "index.blocks.read_only_allow_delete": null }'

故障场景处理清单

场景现象处理步骤
单数据节点宕机yellow，unassigned = 该节点上的副本数等 delayed_timeout（1m）后自动重分配；节点 30 分钟内回来可直接复用本地分片
多节点宕机导致 redactive_primary_shards 减少，部分数据不可查先恢复含主分片的节点；实在恢复不了用快照恢复，接受最近一次快照后的数据丢失
脑裂（两个 master）两个集群各自写入，数据分叉7.x 的投票机制已基本避免；6.x 及以前必须正确设 minimum_master_nodes=(n/2)+1
磁盘写满flood watermark 触发，索引变只读清磁盘（删旧索引 / 扩容），再手动清除 read_only_allow_delete
恢复太慢bytes_percent 长时间不动调大 max_bytes_per_sec 与 node_concurrent_recoveries；注意会挤占查询资源
JVM 频繁 OOM节点反复掉出集群堆不超过 31GB（压缩指针阈值），且不超过物理内存 50%；加大 indices.fielddata.cache.size
分片数过多master 变慢、恢复极慢单节点分片数控制在 < 1000，单分片大小 20~50GB；用 rollover + ILM 管理时序索引
