投机解码（Speculative Decoding）

为什么 decode 是带宽瓶颈、draft-verify-accept 的完整流程与接受准则、决定收益的三个变量、以及高 batch 与创意写作等不适用场景。

要解决的问题：decode 是带宽瓶颈

Decode 每步只生成一个 token，却要把整个模型权重从 HBM 读一遍。 这意味着：batch=1 时，算一次矩阵乘只服务 1 个 token，权重的搬运成本被严重摊薄。

加大 batch
一次权重加载服务 N 个请求 → 吞吐上去，但单请求延迟也上去，且受显存限制
投机解码
一次权重加载验证 K 个候选 token → 在不加大 batch 的前提下提吞吐
投机解码不改变输出分布（在正确的接受准则下），这是它相对"换个更小的模型"最大的优势—— 你加速的还是原来那个模型的采样结果。

流程：小模型起草，大模型验证

为什么能加速：Draft 模型小、每 token 便宜； Target 模型虽然每步要算 γ+1 个位置，但权重只加载一次，而 decode 的成本几乎全在权重加载上。 于是"γ 次串行前向"变成"1 次并行前向 + γ 次便宜的 draft"。

收益由三个数决定

变量含义影响
接受率 α候选 token 被接受的比例最关键。α 高 → 每轮产出多
草稿长度 γ每轮生成几个候选γ 太大会让拒绝位置靠前、白算增多；通常 3~8，需实测
成本比 cdraft 单步耗时 / target 单步耗时draft 越便宜越好，但要和 α 权衡——太小的模型 α 会掉
加速比不是线性的。α 从 0.5 提到 0.7 带来的收益，远大于 γ 从 5 加到 10。 所以工程重点在提高接受率：让 draft 模型的分布尽量贴近 target， 以及让 draft 更容易"猜中"——比如利用任务的高可预测性（代码补全、格式化输出、模板化回答的 α 天然更高）。
独立小模型
同系列小号（如 7B 给 70B 起草）。零训练成本，α 取决于分布相似度
自起草（EAGLE / Medusa）
用 target 自身的隐藏层/额外头预测候选，α 明显更高，但需训练适配层
检索式草稿
从历史输出或 n-gram 表取候选，对模板化、重复性内容有效

什么时候不该用

  • 高 batch 场景：decode 已经是算力瓶颈而非带宽瓶颈时，加大 batch 的收益更高，投机解码反而增加复杂度。
  • 草稿模型也要占显存：显存吃紧时放不下第二个模型，可用自起草方案缓解。
  • 输出高度随机时：温度高、创意写作类任务接受率低，收益有限甚至变慢。
  • prefill 主导的长输入短输出：瓶颈在 prefill，投机解码只优化 decode，帮不上忙。
部署提示：主流推理框架（vLLM、TensorRT-LLM、SGLang 等）已内置投机解码实现， 但各版本支持的 draft 方案、是否支持批量场景下的投机、与 prefix caching / chunked prefill 能否叠加都不相同。 启用前请查阅你所用版本的官方文档，并用真实请求压测确认收益——这是最容易"开了反而变慢"的优化项。
