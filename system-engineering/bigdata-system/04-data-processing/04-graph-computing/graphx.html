图计算 vs 图数据库

先建立直觉：通讯录和它的关系网

传统表格存的是「每个人是什么」：姓名、年龄、城市。要查「张三的朋友的朋友」，你得反复 JOIN，写起来痛苦，跑起来更慢。

图结构存的是「谁和谁有关」：人是顶点，关系是边。「朋友的朋友」就是沿着边走两步——直观且高效。

什么时候该用图？当你的查询主要是「多跳关系」时——二度/三度人脉、资金链路追溯、设备关联分析、路径规划。这些用 SQL 递归 JOIN 会非常低效，而图计算天然就是为遍历设计的。

Pregel 迭代模型：像波浪一样传播

大规模图计算的主流模型是 Pregel（GraphX、Giraph 都基于它）：以顶点为中心，迭代地收发消息。

为什么用这种模型？图算法（如 PageRank、最短路径）本质上都是「沿着边反复传播信息直到稳定」。Pregel 把这个过程抽象成「顶点级收发消息」，天然可并行——每个顶点独立计算，只在超步边界同步。

🎯 面试问答

Q：什么场景应该用图而不是表？
A：当查询以多跳关系为主时。比如「二度人脉」「资金从 A 经过几道手到了 B」「这台设备关联了哪些账号」。用 SQL 做这些需要递归 JOIN，复杂度随跳数指数增长，性能极差；而图结构下就是「沿边走几步」，自然且高效。反之，如果只是简单的聚合统计（按地区求和、按时间分组），关系型表更合适，不要为了「酷」而用图。

Q：Pregel 的超步是什么意思？
A：「超步（superstep）」是一次全局同步的迭代轮次。在每一轮里，所有顶点并行地做三件事：接收上一轮邻居发来的消息 → 更新自己的状态 → 向邻居发送新消息。所有顶点都做完才进入下一轮（这就是「同步」）。当没有顶点再发消息或达到最大轮次时，计算收敛结束。好处：模型简单、易于并行；代价：每轮都要等最慢的顶点（木桶效应）。

Q：GraphX 和 Neo4j 怎么选？
A：看用途：GraphX（及同类图计算引擎）做离线全图分析——跑 PageRank、社区发现这类需要遍历全图的批量算法，数据量可达十亿边，耗时分钟到小时。Neo4j（及其他图数据库）做在线交互式查询——从某个点出发做几跳遍历，要求毫秒到秒级响应。两者常配合使用：图计算离线算出结果（如社群标签），写回图数据库供在线查询。

Q：图计算的性能瓶颈通常在哪？
A：主要在三处：① 数据倾斜——少数超级节点（如大 V、热门账号）有海量边，导致个别分区任务极慢，是整个作业的瓶颈；常用边分割或度数裁剪缓解。② 迭代轮次过多——每轮都有全局同步开销，可通过更好的初始值和收敛条件减少轮次。③ 内存压力——图结构常驻内存，超大图需要分布式或外存方案。实际调优时优先查度数分布，倾斜往往是最主要的问题。

抽象含义底层表示

切分策略决定通信量，这是图计算性能的第一变量：

策略切分依据适用图通信特征
RandomVertexCut边按两端点 hash 分配幂律图（社交网络），默认高度数点被切开，通信分散

Pregel 迭代模型与聚合

Pregel API 三要素

// PageRank：用 Pregel 迭代直到收敛
val pagerank = graph.pregel(0.0, maxIterations = 20)(
  // vprog：收到消息后的顶点更新
  (id, rank, msgSum) => 0.15 + 0.85 * msgSum,
  // sendMsg：沿边发送消息
  triplet => Iterator((triplet.dstId, triplet.srcAttr / triplet.srcAttr)),
  // mergeMsg：合并多个消息
  (a, b) => a + b
)
  • 顶点程序（vprog）：每个活跃顶点独立执行，可读写自身属性。
  • 消息发送（sendMsg）：只在活跃顶点的邻边上触发，不活跃的顶点不参与，这是加速收敛的关键。
  • 消息合并（mergeMsg）：同一目标的多条消息先合并，直接减少网络传输量。

Pregel 是同步迭代模型：每轮是“全体发消息 → 全体收消息 → 下一轮”。收敛判据是没有顶点再收到消息，而不是跑满 maxIterations。

自检 Q&A

Q：分区数怎么定？

A：经验值是总核数的 3~4 倍。太少无法并行；太多则单个分区太小、调度开销占比升高，且切分更碎导致顶点副本增多、通信量上升。

Q：为什么我的图计算卡在某一轮不动？

A：典型是数据倾斜——少数超级节点（如大 V、热门商品）度数极高，对应分区的 task 处理量是其他的几十倍。处理办法：改用 EdgePartition2D 打散、或对高度数顶点做特殊剪枝（截断其邻边）。

Q：GraphX 和 GraphFrames 怎么选？

A：GraphX 是 RDD 底层 API，表达能力强但写起来啰嗦；GraphFrames 基于 DataFrame，支持模式匹配查询（motif finding），能直接用 SQL 风格表达图模式，开发效率高很多。新项目优先 GraphFrames，需要精细控制迭代过程时才下沉到 GraphX。
