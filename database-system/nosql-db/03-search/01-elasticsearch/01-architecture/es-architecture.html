节点角色：不是每台机器都干一样的活

一个 ES 集群里的节点可以承担不同角色，理解分工是规划集群的第一步。

角色职责规划要点
候选主节点 Master-eligible参与选主、维护集群状态通常 3 个，数量必须为奇数以避免平票
数据节点 Data持有分片，执行读写与聚合磁盘、内存、IO 的主战场，按数据量与热度扩容
摄取节点 Ingest写入前做预处理（管道）CPU 密集的转换可以从数据节点剥离
协调节点 Coordinating只转发与汇总请求大规模集群里独立出来能降低数据节点负担
机器学习节点 ML跑异常检测等任务专用任务，按需单独配置

选主为什么强调奇数：候选主节点需要形成多数派（quorum）才能选出主节点并做出集群状态变更。偶数个节点在分裂时容易出现两边都是半数的情况 —— 两边都无法形成多数，集群不可用。这也是防止脑裂的基本手段。

分片：横向扩展的最小单位

别的节点上 否则单机故障会同时丢主副本，失去容灾意义 加节点后会自动 rebalance
主分片与副本必须跨节点分布

三条必须记住的规则：

  • 主分片数创建后不可更改。因为文档路由公式是 hash(_id) % 主分片数，一旦改变，所有已有文档的定位就全乱了。需要变更只能重建索引（reindex）。
  • 副本数可以随时调整。它只是多拷贝几份，不影响路由 —— 提高读吞吐与容灾能力的首选手段。
  • 主负责写，副本与主都可以承担读。副本越多，读能力越强，但写入需要同步给更多副本，成本上升。

一次写入的可靠性设计

PUT /my-index/_doc/1 → 协调节点根据 _id 算出目标分片 P1 ① 请求转发到 P1 所在节点 ② P1 本地写入（buffer + translog） ③ P1 并行把这份写操作转发给它的所有副本 R1 ④ 等待一定数量的副本确认成功 ← 由 wait_for_active_shards 控制： 1 只要主成功就返回（最快，容灾最弱） quorum 大多数副本（含主）确认（常用默认思路） all 所有副本都确认（最安全，最慢） ⑤ 返回客户端"写成功" 注意：第 ④ 步保证的是「副本收到了」，不代表副本已经 fsync 落盘。 真正的持久性仍依赖各节点自己的 translog 策略。

并发控制：ES 用乐观锁而不是加锁。每次写操作带一个序号 _seq_no 与 _primary_term，如果请求里指定了一个过期的 if_seq_no，说明这期间文档已经被别人改过了，服务端直接返回冲突（HTTP 409）由业务决定重试策略。这与很多数据库的版本号机制是同一个思路。

六个高频踩坑

问题现象对策
分片数过多内存暴涨、查询变慢、恢复时间长单分片控制在合适大小；用索引生命周期管理滚动 rollover
分片数过少无法利用多节点并行预留合理的并行度；必要时重建索引
字段爆炸 mapping explosionmapping 暴涨、集群状态膨胀限制字段数量、用扁平结构、dynamic 设为 strict
热点分片某节点 CPU/IO 明显高于其它检查路由键是否倾斜；改用更均匀的 key
深度分页from/size 很大时 OOM 或超时改用 search_after 或 scroll（批量导出）

关于分片大小的一条经验：常见的建议区间是单个分片在 20~50GB 量级。它不是硬性规定，但它同时兼顾了三件事：并行度（分片够多）、恢复速度（单分片不太大，重分配与恢复快）、查询开销（段不太多）。规划时先估算总数据量再反推分片数。

深入自检

为什么主分片数不能改？

因为文档定位完全依赖它：目标分片 = hash(_id) % 主分片数。改成另一个数字后，同一个 _id 会被算到完全不同的分片上，历史数据就再也找不着了。ES 唯一的支持方式是重建索引：新建目标索引（想要的分片数），把老索引的数据滚动迁移过去，最后用别名切换流量。

脑裂是怎么发生的，怎么防？

网络分区把集群劈成两半，若两边都认为自己能选主并各自对外提供服务，就会出现两份互相冲突的数据。防范核心是多数派原则：候选主节点数为奇数（如 3 或 5），集群变更必须获得半数以上候选节点同意。只有获得多数派的那一边能继续工作，另一边自动停止服务，避免双写。

副本除了容灾还有什么用？

两个重要作用：① 提升读吞吐 —— 读请求可以分摊到主或任一副本；② 提升查询并行度 —— 协调节点可以在多个副本间择优。代价是写入要同步更多份、存储成本翻倍。所以副本数本质上是用存储与写放大换读能力与容灾的一次取舍。

集群健康的 yellow 状态要紧吗？

要看场景。yellow 表示主分片齐全但副本未全部分配，数据没丢、读写可用，但容灾能力下降（再坏一个节点就可能真的丢数据）。常见触发原因是副本数大于可用节点数。生产环境应当尽量恢复到 green；临时性的 yellow 也要明白「此刻正处在容灾能力降级中」。

ES 的核心概念与数值

概念默认值 / 建议说明
分片（Shard）7.x 起默认 1 主分片主分片数建索引后不可改；只能 reindex
分片大小20~50 GB（日志可到 100GB）太大恢复慢、迁移慢；太小开销大
副本数1可随时改；1 表示数据有 2 份
Lucene 段（Segment）不可变，定期 mergesegment 数越多查询越慢
refresh_interval1s近实时搜索的关键；写入量大可调到 30s
translog 刷盘async（5s）改成 request 更安全但慢 5~10 倍
index_buffer_size堆的 10%写缓冲；满了会触发 refresh
JVM 堆不超过 31GB超过后压缩指针失效，对象膨胀约 20~40%
堆与内存堆 ≤ 物理内存 50%另一半留给 OS 的 page cache（Lucene 依赖它）
fielddatatext 字段默认关闭聚合 text 字段会爆内存；用 keyword

为什么堆不能超过 31GB：JVM 在堆 < 32GB 时可以用压缩指针（4 字节而非 8 字节表示对象引用），一旦超过，所有引用都变成 8 字节，实际可用空间反而下降。所以 ES 节点的标准配置是 31GB 堆 + 64GB 物理内存，剩下 33GB 给 OS 做文件缓存——Lucene 的段文件严重依赖 page cache，全给堆反而更慢。

写入与查询链路

# 写入链路（近实时的原理）
# 1) 请求到协调节点 -> 按 routing 转发到主分片所在节点
# 2) 写 translog（顺序写，防宕机丢失）+ 写内存 buffer
# 3) refresh（默认 1s）：buffer -> 新 segment（可被搜索，但还没 fsync）
# 4) 每隔一段时间 flush：segment fsync 落盘，清空 translog
# 关键：能被搜索 ≠ 已落盘。宕机时靠 translog 重放

# 查询链路（scatter-gather）
# 1) 协调节点广播到所有相关分片（每个分片本地查）
# 2) 各分片返回 top N 的 doc id + score
# 3) 协调节点归并排序，取全局 top N
# 4) 若需取原文，再发一次 fetch 请求（两阶段：query then fetch）

# 关键参数：size + from 的深分页陷阱
# from=10000&size=10 -> 每个分片要算 10010 条，协调节点合并 (分片数 × 10010) 条
# 默认 index.max_result_window = 10000，超过会报错
# 深分页正确做法：
#   1) search_after（用上一页的排序值做游标）
#   2) scroll（快照，适合全量导出，不适合实时）
#   3) PIT（point in time，7.10+，推荐）
# 常用运维命令
# 集群健康
curl 'localhost:9200/_cluster/health?pretty'
# green/yellow/red + unassigned_shards

# 分片分配情况
curl 'localhost:9200/_cat/shards?v&s=index,shard'
# 看每个分片在哪个节点、是 p(主) 还是 r(副)、状态 STARTED/RELOCATING/UNASSIGNED

# 索引与段信息
curl 'localhost:9200/_cat/indices?v&s=docs.count:desc'
curl 'localhost:9200/_cat/segments?v'          # 段数过多的索引要 force merge
curl 'localhost:9200/<index>/_stats?pretty'

# 节点资源
curl 'localhost:9200/_cat/nodes?v&h=heap.percent,ram.percent,cpu,load,master,name'
curl 'localhost:9200/_nodes/stats/jvm?pretty'  # GC 次数与耗时

# 慢查询日志定位
curl -XPUT 'localhost:9200/<index>/_settings' -H 'Content-Type: application/json' -d '{
  "index.search.slowlog.threshold.query.warn": "5s",
  "index.search.slowlog.threshold.fetch.warn": "1s",
  "index.indexing.slowlog.threshold.index.warn": "5s"
}'

分片数是最难改的决定：主分片数建索引时就固定了，改只能 reindex（重建索引，代价很大）。所以建索引时要按未来 1~2 年的数据量规划，单分片 20~50GB。日志类按时间滚动的索引（每天/每月）则好办，因为每个新索引可以有不同的分片数。
