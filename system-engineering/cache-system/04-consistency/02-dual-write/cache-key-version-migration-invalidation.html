缓存键版本迁移：改了数据结构，怎样避免新旧应用互相读错

用商品卡片从 v1 到 v2 的上线过程讲命名空间、双读、回填、失效和回滚。

先分开两种“版本”

商品缓存原来存 `product:v1:42`，值只有价格和标题；新版要增加库存展示与币种。若新旧应用都读写同一个 key，旧版可能把新版字段丢掉，新版也可能把旧值误当完整数据。给缓存 key 加 schema 命名空间如 `product:v2:42`，可以隔离不同序列化格式；但这只解决“结构兼容”，不自动解决商品 42 的数据新鲜度。商品价格从 100 改为 90 时，v1 和 v2 都可能同时过期或陈旧，仍需按更新流程失效。

另一种数据修订号如数据库 row_version=18，用于识别同一商品哪一版内容更新。把 schema 版本和数据修订号混成一个字段，会让迁移和日常更新的职责不清。先写清值格式、键格式、修订来源和可容忍陈旧时间。

图解：商品缓存 v1→v2 迁移

沿箭头逐步核对输入、变换和输出；下面的推演可以逐步切换。

一次从 v1 到 v2 的上线

旧实例只读写 v1；先发布可读 v1 和 v2、但只写 v1 的兼容版，验证新解析器；再逐步让新版实例读写 v2。v2 首次未命中时从数据库构造新格式，而不是盲目把 v1 字节复制过去。观察 v2 命中率、数据库回源量和字段完整性后，扩大新版本比例。等所有旧实例退出且回滚窗口结束，再停止维护 v1，随后按 TTL 或受控清理让旧键消失。

具体顺序取决于应用是否允许双读和双写。若 v2 缺失就回退读 v1，应明确旧值能否安全转换；若不能，不应为了命中率返回结构不完整数据。发布时还要核对所有消费者，包括定时任务、后台管理和异步消息处理器，避免隐藏的旧代码继续写 v1。

逐步推演

隔离格式

v1 与 v2 使用不同命名空间。

灰度新读

v2 miss 从权威数据库构建，不盲拷 v1 字节。

双重失效

更新商品时覆盖仍活跃的两套读路径。

退出旧版

过回滚窗口后渐进清理旧键与监控。

更新和失效仍要覆盖两套键

后台把商品 42 的价格改为 90，数据库事务成功后需要使 v1、v2 中相关缓存不再被错误使用。迁移期间可同时失效两套键，或让旧实例停写并逐步退出；若只删 v2，旧实例仍从 v1 返回 100。缓存旁路模式中的并发读写竞态仍存在：读线程从数据库读到旧值、更新线程删键后，读线程又把旧值写回。版本检查、延迟再删或短 TTL 等策略可降低风险，最终选择要看一致性要求。

若用 `product:42:rev18` 这类数据版本键，读取者必须先知道当前修订号；版本指针本身又需要可靠更新。不能因为键名含 `rev18` 就宣称强一致。每个旧修订键也要设置 TTL 或有清理计划，否则频繁更新会让缓存占用无限增长。

对象版本解决什么没有解决什么
schema 命名空间 v1/v2新旧序列化格式隔离商品内容是否最新
数据修订号 rev18识别内容修订先后当前修订号的可靠发现
TTL为旧键设置最终回收界限更新后立即一致
灰度比例控制新键冷启动回源并发读写竞态

缓存雪崩与回源预算

上线时几百万个 v2 键都是冷的，如果所有流量瞬间切换，新版每次都打数据库，可能把后端压垮。可以灰度新读路径、按热点集合预热、限制每秒回源并为热点 miss 合并并发构建。预热也需基于数据库当前版本，并设置随机化 TTL，避免所有预热键同时到期。观测除命中率外还要看回源 QPS、数据库 P99、缓存写入量和旧键内存占用。

不要为追求 100% 命中率把过期旧值无限续命。若商品价格用于支付，结算环节应再次从权威数据确认价格与库存；展示层可容忍短暂陈旧，交易正确性不能完全委托给缓存。

回滚时的选择

新版上线后若发现 v2 格式有 bug，旧代码回滚可能仍可读取 v1；但若迁移过程中已经停写 v1，回滚后 v1 可能陈旧。回滚方案可选择“旧版从数据库重新构建 v1”或“在迁移窗口双重失效、必要时双写”，并明确数据库查询容量。不能只看应用镜像可回滚，忽略缓存状态与消息消费者版本。

回滚演练应在 v2 已经运行一段时间、v1 键已有部分过期的状态下做，检查价格更新是否准确、回源是否可承受以及旧解析器是否遇到新格式。安全清理旧键时优先使用有范围的扫描和渐进删除，避免一次性阻塞或误删相似前缀。

验收一条完整时间线

建立商品 42，v1 价格 100；发布兼容版和 v2 版，确认两格式独立；把数据库价格改为 90，检查两种应用都不会长期读出 100；让 v2 首次冷启动，观察回源峰值；再回滚一部分实例，检查旧路径仍能正确构建。最后按清理策略统计旧键数量与占用，不把临时迁移负担变成永久内存泄漏。

监控最好按 schema 版本分别记录命中、反序列化失败、值缺字段、回源和写入；若只看总命中率，新旧版本问题会互相掩盖。版本迁移的成功标准是结构兼容、数据新鲜度与容量三者都在约定范围。

自检

把 key 从 product:v1:42 改成 product:v2:42，能自动保证新价格不会读到旧值吗？

不能。schema 命名空间只隔离格式；价格更新仍需覆盖所有活跃读路径的失效和回填策略。
