// 循环里这样写会很慢

    s += w  // 反复分配拷贝
}

高效拼接：Builder

复用缓冲区，避免反复分配

strings.Builder 内部维护一个 []byte，WriteString 追加不分配新内存，最后 String() 一次性产出。

var b strings.Builder
for _, w := range words {
    b.WriteString(w)
}
s := b.String()   // 一次成型，性能远好于 +

深入自检

为什么循环里用 += 拼接字符串很慢？

string 不可变，每次 += 都要分配一块新内存并把旧内容整体拷过去。拼接 n 次的总拷贝量是 O(n²)。用 strings.Builder 预分配后，追加是均摊 O(1)，总复杂度降为 O(n)。

len(s) 和字符数不一致怎么办？

len 返回字节数。UTF-8 下一个汉字占 3 字节，所以含中文时二者不同。求字符数用 utf8.RuneCountInString，或转成 []rune 后取长度（后者有拷贝开销）。

按字节切片会不会出问题？

会。s[0:2] 如果正好切在一个多字节字符中间，会得到非法 UTF-8，输出时出现乱码或替换字符。需要按字符截取时应先转 []rune 或用 range 定位边界。

string 转 []byte 有开销吗？

有，会发生一次内存拷贝（因为 string 不可变，必须复制才能让你改）。在高频路径上可以通过 bytes 包的操作、或复用 buffer 来减少转换次数。

字符串比较大小写不敏感怎么做？

用 strings.EqualFold，它按 Unicode 规则比较且不分配内存；比 ToLower 后再 == 更高效也更正确（能处理某些特殊字符的大小写映射）。

字符串本质：不可变的字节序列

长度与遍历

// runtime 里的定义
type stringStruct struct {
    str unsafe.Pointer    // 指向字节数据的指针
    len int               // 字节长度（不是字符数！）
}
// 结论：string 是 <b>16 字节</b>的头部（ptr + len），且<b>不可变</b>

s := "hello"
// len(s) 是<b>字节数</b>，不是字符数
len("hello")      // 5
len("你好")        // <b>6</b>（UTF-8 下每个汉字 3 字节）
len("👋")          // 4（emoji 是 4 字节的 rune）

// 正确数字符数
utf8.RuneCountInString("你好")   // 2
len([]rune("你好"))              // 2（但有额外分配）

// 遍历：range 会自动解码 UTF-8
for i, r := range "你好" {
    fmt.Println(i, string(r))    // i 是<b>字节下标</b>：0 和 3
}
// 按下标取到的是 byte 不是 rune
s := "你好"
fmt.Println(s[0])                // 228（UTF-8 第一个字节）

替换strings.Replace(..., -1)O(n)每次都分配

转 []byte[]byte(s)O(n) 拷贝热路径要避免来回转换

拼接性能

// 性能对比（循环拼接 10000 次）
// 错误：O(n^2)，每次都分配新字符串并拷贝
s := ""
for i := 0; i < 10000; i++ { s += "x" }        // 约 50ms，分配 10000 次

// 正确：strings.Builder
var b strings.Builder
b.Grow(10000)                                   // 预分配，避免扩容
for i := 0; i < 10000; i++ { b.WriteString("x") }
s := b.String()                                 // 约 0.1ms，分配 1 次
//   实测差距可达 <b>100~1000 倍</b>

// 零拷贝转换（谨慎使用！转换后绝不能修改）
func unsafeStr2Bytes(s string) []byte {
    return *(*[]byte)(unsafe.Pointer(&struct{
        string
        Cap int
    }{s, len(s)}))
}
//   风险：得到的 []byte 不可写，写了会 panic 或破坏常量
//   只在只读且确定生命周期短的热路径用

为什么 Go 的字符串设计成不可变？

三个好处：① 可以安全地共享——子串、map key、并发读都不用拷贝也不用加锁；② 可以放在只读段——字符串常量在程序生命周期内不会被改，多个 goroutine 共享零成本；③ 简化 GC——不需要处理「字符串被修改导致其他引用者看到变化」的情况。代价是需要修改时必须新建（所以有了 Builder）。这和 Java/Python 的选择一致，与 C++ 的 std::string（可变）相反。

什么时候该用 []byte 而不是 string？

判断标准是要不要修改/频繁追加。string 适合「存储、传递、比较、作为 key」；[]byte 适合「逐步构建、原地修改、IO 读写、加密/压缩这类按字节操作的场景」。IO 接口（io.Reader/Writer）都是 []byte，所以在网络/文件处理栈里用 []byte 能省掉转换；在业务逻辑和 map key 场景用 string 更方便安全。

strings.Clone 什么时候需要？

当你从一个大字符串里取了一小段子串，且这个子串要长期存活时。因为子串共享底层字节数组，只要子串还活着，整个大字符串就无法被 GC——这是很隐蔽的内存泄漏（比如解析一个大 JSON 后只保留一个字段）。strings.Clone(s) 会拷贝一份独立的，切断引用。Go 1.18+ 才有，之前用 string([]byte(s))。
