🔄 MySQL MVCC 原理详解

Multi-Version Concurrency Control 多版本并发控制

核心概念

📌 隐藏列

InnoDB 为每行记录添加了两个隐藏列：DB_TRX_ID（事务ID）和 DB_ROLL_PTR（回滚指针），用于实现多版本。

📜 Undo Log

记录数据修改前的值，形成版本链。每次修改都会生成一条 undo 记录，通过回滚指针串联起来。

👁️ Read View

读事务开始时创建的快照，记录当前活跃事务ID列表，用于判断数据版本的可见性。

🎯 可见性判断

根据 Read View 判断：数据的事务ID是否对当前事务可见，决定读取哪个版本的数据。

InnoDB 行记录结构

每一行数据背后，都隐藏着 MVCC 的关键信息：

id 主键
name 用户名
age 年龄
trx_id 事务ID
roll_ptr 回滚指针

💡 工作原理

DB_TRX_ID：记录最近一次修改该行的事务ID
DB_ROLL_PTR：指向 undo log 记录的指针，形成版本链的链表头

可见性判断算法

🎯 核心规则

当事务读取一行数据时，通过 Read View 判断该行数据的某个版本是否可见：

IF (trx_id == creator_trx_id) THEN

// 自己修改的，可以看见

ELSE IF (trx_id < min_trx_id) THEN

// 提交过且比快照还早，可以看见

ELSE IF (trx_id > max_trx_id) THEN

// 快照创建后才开始的，看不见

ELSE IF (trx_id in m_ids) THEN

// 活跃事务修改的，看不见

隔离级别与 MVCC

🔒 READ COMMITTED

  • 每次读取都生成新的 Read View
  • 可避免脏读和不可重复读
  • 同一事务中两次读取可能不同
  • PostgreSQL 的默认级别

🔐 REPEATABLE READ

  • 事务开始时创建 Read View
  • 整个事务期间复用同一个快照
  • InnoDB 默认隔离级别
  • 解决脏读、不可重复读、幻读

📖 READ UNCOMMITTED

  • 不使用 MVCC
  • 读取最新版本（可能有脏数据）
  • 可能脏读，实际很少用

🏛️ SERIALIZABLE

  • MVCC + 锁机制
  • 读取时会加锁
  • 最强隔离，性能最差
  • 并发度最低

核心要点总结

✅ MVCC 优势

• 读不阻塞写，写不阻塞读
• 大幅提升并发性能
• 快照读避免幻读问题
• 减少锁争用

⚠️ 注意事项

• 需要定期清理旧版本（purge）
• 极端情况下可能产生长事务
• RR 级别下仍有幻读可能（需 gap lock）
• 只适用于快照读

🔍 适用场景

• 高并发读多写少
• 需要一致性快照
• 长事务处理
• 报表查询

MVCC 想解决的就一件事

最朴素的并发控制是「读的时候加锁，写的时候加锁」。但它带来一个糟糕的体验：一个长查询会把所有写堵死，一个写操作会让所有读等待。

MVCC（多版本并发控制）的思路换了个方向：每一行保留多个历史版本。读操作去看「在它开始的那一刻，这行是什么样子」，不必关心此刻是否有人正在改。于是 读不阻塞写，写也不阻塞读。

第一个自己有权限看到的版本就是它的答案。 写事务则完全不同：它必须读最新版本并加锁（否则会丢更新）
undo 版本链 + ReadView = 每个事务看见自己的那一版

InnoDB 实现 MVCC 的三件套

组件作用说明
DB_TRX_ID每行隐藏的事务 id 列记录这一版是谁改出来的
DB_ROLL_PTR指向 undo log 里上一个版本的指针靠它把历史版本串成一条链
ReadView读事务启动时拍下的活跃事务快照包含哪些事务「还没提交」，据此判断可见性

可见性判断规则（简化）：沿着版本链从头走到尾，对每个版本的 DB_TRX_ID 做判断：

设：当前 ReadView 里 m_ids 拍快照那一刻还活跃（未提交）的事务 id 集合 min_trx_id m_ids 里最小的 id max_trx_id 系统下一个将被分配的 id 对某个版本的 trx_id： ① trx_id < min_trx_id → 早就提交了 → <b>可见</b> ② trx_id >= max_trx_id → 是在我之后才开启的事务 → <b>不可见</b> ③ trx_id 在 m_ids 里 → 快照时它还活着，尚未提交 → <b>不可见</b> ④ 其余情况 → 快照时它已提交 → <b>可见</b> 不可见就顺着 DB_ROLL_PTR 往前一个版本，重复判断。

如果没有任何一个版本对我可见，这一行就等于「不存在」 —— 这正是快照读能看到一致性视图的原因。

RC 与 RR 的差别就在这里

两个隔离级别的实现几乎完全一样，差别只有一句话：ReadView 什么时候生成。

隔离级别ReadView 生成时机效果
读已提交 RC每条语句执行前都重新生成一次能读到别的事务在这一瞬间之前提交的改动 → 同一事务里两次读可能不一致（不可重复读）
可重复读 RR只在事务中第一次快照读时生成，之后一直用这份整个事务看到的是同一个快照 → 可重复读
同一个场景，RC 与 RR 的差别只在于要不要刷新快照

这个差别带来了一个常被误解的点：RR 的「可重复读」针对的是快照读。如果你在同一事务里用了当前读（SELECT ... FOR UPDATE、UPDATE、DELETE），它们读的是最新版本并加锁 —— 此时 InnoDB 靠的是间隙锁 / next-key lock来防止幻读，而不是 MVCC。

为什么长事务很危险

  • undo 无法回收。只要有事务可能还需要回溯到某个历史版本，那条 undo 链就必须留着 —— 一个跑了几个小时的事务能让 undo 表空间持续膨胀。
  • 版本链变长。同一行被改得越多，快照读时要往前回溯的步数越多，查询越来越慢。
  • 锁持有时间长。事务里持有的锁要等它结束才释放，直接拉高锁等待与死锁概率。
  • 回滚代价高。长事务失败回滚时要撤销大量改动，耗时可能是运行时长的数倍。

实操建议：把事务写得尽量短 —— 不要在一个事务里做网络调用、文件 IO、人工确认。监控长时间未提交的事务，并给关键业务设置超时。

深入自检

purge 线程负责什么？

负责回收那些已经没有任何 ReadView 需要它们的历史版本与 undo 日志。判断标准是：系统中最早还在活跃的事务都不再可能回溯到某个版本，这个版本就可以删了。这也解释了为什么长事务会阻塞 purge —— 它像一根钉子，把它之前的所有历史都钉住不让清理。

MVCC 解决了幻读吗？

分情况：快照读（普通 SELECT）在 RR 下因为一直用同一份 ReadView，看不到新插入的行，所以不会出现幻读；但当前读看得见最新数据，就必须靠间隙锁来防止别的事务在查询区间里插入新行。很多「我明明设了 RR 怎么还有幻读」的困惑，根源在于没分清这两种读。

为什么我的 UPDATE 看不到别人刚提交的数据？

恰恰相反 —— UPDATE 走的是当前读，它一定会读到最新的已提交版本并加锁。如果你觉得「没看到」，那多半是业务逻辑的问题，而不是 MVCC 的问题。写操作永远基于最新状态正是为了避免丢失更新。

RR 下要不要担心「读到过期数据」？

要看业务。如果需要严格「读最新提交的数据」，应当显式使用当前读（SELECT ... FOR UPDATE 或在读已提交模式下执行），而不是依赖快照读。金融、库存、余额这类场景尤其要注意：先读快照再更新，可能基于一个过期的判断做出错误的写入，必要时应使用悲观锁或乐观版本号来兜底。
