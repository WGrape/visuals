Qdrant 向量数据库原理

Rust 编写的向量搜索引擎：HNSW 索引、量化压缩与强大的结构化过滤

① 定位 ② 架构与数据模型 ③ 索引与量化 ④ 过滤检索 ⑤ 上手示例 ⑥ 与 Milvus 对比 ⑦ 概念与判定 ⑧ 参数与命令 ⑨ 排障与边界 ⑩ 原理与取舍
一句话总结：Qdrant 是用 Rust 编写的开源向量数据库， 最大特色是把向量检索与结构化过滤（payload filter）深度结合—— 它能在带过滤条件的场景下依然保持高性能，这是很多向量库做不到的。 同时提供标量量化（压缩向量、省内存）与简洁的 REST/gRPC API，部署轻量。

01定位与特点

🦀 Rust 实现

内存安全、无 GC 停顿，单机性能与资源占用表现优秀。 编译后是单个二进制，部署极简（Docker 一条命令）。

🎯 过滤能力最强

原生支持任意 payload 字段的过滤与组合， 并针对"带过滤的 ANN"做了专门优化（可用 payload 索引预筛）。

💾 量化省内存

支持标量量化（int8）把向量压到 1/4， 大库场景下内存成本大幅下降，精度损失可控。

🔌 API 友好

REST + gRPC 双接口，官方多语言客户端齐全， 本地模式（in-memory / on-disk）便于开发与测试。

适合：RAG 应用、推荐、语义搜索，尤其是需要带业务条件过滤的检索场景。

03索引机制与量化

HNSW 索引

Qdrant 默认使用 HNSW（分层可导航小世界图）作为向量索引。 它构建多层图结构，检索时从最上层"粗图"快速定位区域，再逐层下钻到最底层精搜。

  • m：每个节点连接的邻居数（越大图越密、越准，内存越大）。
  • ef_construct：建索引时的候选队列大小（越大索引质量越高、构建越慢）。
  • ef（ef_search）：检索时的候选队列大小（越大越准、越慢）——运行时可调，是精度/延迟的主要旋钮。

标量量化 Scalar Quantization

图 2：标量量化用 1/4 内存换取极小的精度损失
Qdrant 的量化用法要点：开启量化后， 检索过程先用量化向量粗排，再对 Top-K 候选用原始向量重打分（rescore / oversampling）。 这样既省内存又保住了最终精度——不要只量化不重打分。

存储策略

策略说明适用
In Memory向量全放内存数据量小、追求极致延迟
Memmap用 mmap 映射到磁盘，靠 OS page cache数据大于内存但可接受部分抖动
On-disk（量化）量化后的向量存盘，原始向量可选保留超大规模、成本敏感

04带过滤的检索（核心优势）

真实业务几乎不会"纯向量检索"——总要加条件，比如 「找相似商品，但只要上架的、价格 < 500 的、且属于某品类」。

图 3：过滤 + ANN 的协同流程
# 带过滤的检索（Python 客户端）
from qdrant_client import QdrantClient
from qdrant_client.models import Filter, FieldCondition, Range

client = QdrantClient(host="localhost", port=6333)

hits = client.search(
    collection_name="products",
    query_vector=query_emb,
    query_filter=Filter(
        must=[                                    # AND
            FieldCondition(key="in_stock", match={"value": True}),
            FieldCondition(key="price",   range=Range(lt=500)),
        ],
        should=[                                  # OR
            FieldCondition(key="category", match={"value": "phone"}),
            FieldCondition(key="category", match={"value": "tablet"}),
        ]
    ),
    limit=10,
    search_params={"hnsw_ef": 128},   # 运行时调 ef：越大越准越慢
)

05上手示例

# 启动（Docker 一行）
docker run -p 6333:6333 -v ./qdrant_storage:/qdrant/storage qdrant/qdrant

# 建集合
client.create_collection(
    collection_name="docs",
    vectors_config={"size": 768, "distance": "Cosine"},
    quantization_config=ScalarQuantization(      # 可选：开启标量量化
        scalar=ScalarQuantizationConfig(type="int8", quantile=0.99, always_ram=True)
    ),
)

# 写入
client.upsert(
    collection_name="docs",
    points=[
        PointStruct(id=1, vector=emb1, payload={"title": "...", "year": 2026}),
        PointStruct(id=2, vector=emb2, payload={"title": "...", "year": 2025}),
    ],
)

# 给过滤字段建 payload 索引（重要！）
client.create_payload_index("docs", field_name="year", field_schema="integer")
实践提醒：忘了建 payload 索引是 Qdrant 最常见的性能问题—— 没有索引时过滤会退化成逐条比对 payload，QPS 断崖式下降。 凡是要用于过滤的字段，务必提前建索引。

06Qdrant vs Milvus

维度QdrantMilvus
语言RustGo + C++
部署复杂度极简（单二进制 / 单容器）较重（etcd、MinIO 等多组件）
扩展性支持分片与副本，集群能力逐步增强为超大规模设计，组件拆分彻底
过滤能力很强，payload 索引类型丰富支持属性过滤，语义略有差异
量化标量量化成熟IVF_PQ / SQ 等多种量化
适用规模百万～千万级，中小团队首选千万～百亿级，大规模生产
上手成本低较高
选型直觉：项目规模中等、希望快速落地 + 过滤条件复杂 → Qdrant； 数据量达到亿级、需要完善的分片/多租户/运维体系 → Milvus。 两者都开源，Qdrant 的本地模式（无需服务端）也非常适合原型开发。

⑦第一层 · 概念与判定：什么场景该选 Qdrant

Qdrant 的定位非常清晰：用「一个进程」把向量检索做到位，不引入分布式复杂度。选它的判据因此也很清晰 —— 你是否愿意用「单机上限」换「极低运维成本」。

场景选 Qdrant 的理由不选的理由
向量 100 万 – 3000 万单机 + 量化可覆盖，延迟个位数毫秒—
团队没有专职 SRE单二进制，无 etcd/对象存储/MQ 依赖—
需要复杂的 payload 过滤filterable HNSW，过滤与向量检索深度整合—
需要 Rust/嵌入式生态可作库使用，也可独立部署—
向量 > 1 亿—分片能力弱于 Milvus 存算分离
需要 DISKANN 类磁盘索引—Qdrant 以内存 HNSW 为主
已有 Postgres 且规模不大—pgvector 省一整套系统
一句话判定：「向量规模在千万级、想少运维、要强过滤」—— 选 Qdrant。「已经亿级、需要按角色弹性」—— 选存算分离的 Milvus。

⑧第二层 · 参数 · 命令 · 量化：最小可用配置

Qdrant 的配置全部走 HTTP API，没有 schema 迁移概念。下面是最小可用的一套（含量化与 payload 索引，这是生产必须的两项）。

# 1) 起服务：单条命令，无外部依赖
docker run -p 6333:6333 -p 6334:6334 \
  -v $(pwd)/qdrant_storage:/qdrant/storage qdrant/qdrant

# 2) 建集合：量化码常驻内存 + 原向量落盘
PUT /collections/docs
{
  "vectors": { "size": 768, "distance": "Cosine", "on_disk": true },
  "quantization_config": {
    "scalar": { "type": "int8", "quantile": 0.99, "always_ram": true }
  }
}

# 3) 过滤字段建 payload 索引（不建就是全段扫描）
PUT /collections/docs/index?wait=true
{ "field_name": "tenant_id", "field_schema": "keyword" }

# 4) 写入
PUT /collections/docs/points?wait=true
{ "points": [{ "id": 1, "vector": [...], "payload": {"tenant_id": "t1"} }] }

# 5) 查询：量化必须开 rescore
POST /collections/docs/points/search
{
  "vector": [...], "limit": 10,
  "filter": { "must": [{ "key": "tenant_id", "match": { "value": "t1" } }] },
  "params": { "quantization": { "rescore": true, "oversampling": 2.0 } }
}
配置项默认值说明影响
hnsw_config.m16图邻居数，建集合时可设内存与召回
hnsw_config.ef_construct100构建时的搜索宽度建索引时间
indexing_threshold_kb20000超过 20 MB 未索引数据才建 HNSW导入后多久变快
on_disk_payloadtrue（较新版本）payload 是否落盘返回字段延迟
quantization.scalar.quantile0.99裁掉 1% 极端值抗离群维度
oversampling2.0粗筛后放大倍数召回与延迟
压测前必须等索引建完：GET /collections/docs 里的 indexed_vectors_count 追上 points_count，否则你测到的是暴力扫描的性能，会得出完全错误的结论。

⑨第三层 · 排障与边界：高频坑与失效模式

Qdrant 的故障几乎都能归到三类：异步优化的时序、少建了某个索引、容器化没做持久化。

现象根因正确做法
导入后查询要几秒优化器还没建 HNSW，数据在未索引缓冲被暴力扫等 indexed_vectors_count 追平后再测
过滤查询极慢过滤字段没建 payload 索引对要过滤的字段建索引，别给全字段建
开了量化内存没降原向量仍全量在内存（on_disk 没开）vectors.on_disk: true + 量化码 always_ram: true
量化后召回掉了没开 rescore，或 oversampling 太小开 rescore，oversampling 从 2 起调
删除后内存/磁盘不降标记删除，vacuum 异步触发调低 deleted_threshold，耐心等
容器重启数据全没存储目录没挂载到持久卷必须 -v host:/qdrant/storage，这是第一坑
备份跟着一起丢了快照默认只落容器内 /qdrant/snapshots定时把快照拉到 S3/OSS 并做恢复演练
刚写入的点搜不到读写分离/副本异步，最终一致写后读别依赖向量库；用返回的主键回表
边界：Qdrant 不是关系库 —— 没有 JOIN、没有跨集合事务、payload 不支持复杂聚合分析。它的职责边界就是「按向量 + 条件取候选点」，拿到 id 之后的一切仍归业务库。

⑩第四层 · 原理与取舍：为什么敢做成单进程

Milvus 用五个角色 + 三个外部依赖换扩展性，Qdrant 走的是完全相反的路：把段（segment）模型、WAL、优化器全部收进一个进程，用 Rust 把单机性能榨到极致。这个选择能成立，前提是它对「单机能扛多大」有明确判断 —— 靠量化与磁盘化把千万级压进一台机器。

它的核心机制是「段 + 异步优化器」：新数据先进入带 WAL 保护的未索引缓冲，读写都不阻塞；当某个段的未索引数据超过阈值（默认 20 MB），后台优化器才为它构建 HNSW。这个设计带来两个直接后果 —— 写入极快，但数据「什么时候变快」不由你控制。理解这一点，就能理解它所有的时序类「异常」。

设计选择收益代价
单进程、零外部依赖部署与运维成本极低；故障面小扩展能力上限低于存算分离架构
段 + 异步优化器写入不被建索引阻塞；吞吐高导入后一段时间内查询慢（未索引段被暴力扫）
filterable HNSW过滤与向量检索在同一张图上协同，选择率不极端时表现稳定实现复杂；极端选择率下仍需特殊处理
三层存储各自可落盘能按预算精细控制内存与延迟的交换配置项多，配错会「省了内存但慢了十倍」
最终一致读多副本读吞吐高、实现简单写后读不可靠，需要在业务层兜住
一句话收束：Qdrant 的取舍是「用单机极限换零运维复杂度」。它在千万级区间几乎无可替代；超过这个区间，才轮到存算分离架构发挥价值。
