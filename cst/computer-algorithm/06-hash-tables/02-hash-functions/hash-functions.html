哈希函数与碰撞处理

非加密哈希怎么选、碰撞怎么解决，以及生日攻击为何能打穿哈希表

哈希表好用，前提是哈希函数选对、碰撞处理得当。这一页讲清非加密哈希怎么挑、碰撞怎么解决，以及为什么生日攻击能打穿一个没防护的哈希表。

一、哈希函数家族

⚡

非加密（快）

MurmurHash、xxHash、FNV、CityHash：为速度与分布均匀而生，无安全保证，适合哈希表键、分片、去重、校验。

🔒

加密（慢但抗撞）

SHA-1/2/3、MD5、BLAKE：抗碰撞、抗预映象，但慢几个数量级，只在该用密码学保证时才用。

🧭

带局部性

一致性哈希用的哈希要"邻近输入映射邻近"，与无序分布相反，别混用。

二、碰撞怎么解决

方案做法优点代价
链式（拉链）同桶挂链表/红黑树实现简单、删除易指针开销、缓存不友好
开放寻址线性/二次/双重探测找空位缓存友好、无额外分配删除需墓碑、易聚集
Cuckoo两个桶、踢出重放查询 O(1) 确定可能重构、写放大
Robin Hood开放寻址 + 均衡探测距离方差小、最坏更稳实现略复杂
负载因子（已用桶/总桶）超过 ~0.7 时碰撞概率陡增，多数实现会触发扩容 rehash——扩容本身是要付的"重建税"。

概念与判定

  • 选非加密还是加密：只要目标是"均匀分桶/快速校验"就用非加密；只有需要"抗人为伪造碰撞"才上加密哈希。
  • 碰撞不可避免：鸽巢原理决定键空间远大于桶数，必须设计碰撞处理而非幻想零碰撞。

参数·命令·量化

  • 负载因子建议阈值 0.7；Java HashMap 默认 0.75 触发扩容。
  • 生日悖论：在 n 个桶里放 k 个键，碰撞概率约 1 - e^(-k^2/2n)，k≈1.18√n 时过半。
  • 非加密哈希吞吐：Murmur/xxHash 可达每秒数 GB，SHA-256 慢 1~2 个数量级。

排障与边界

  • 碰撞 DoS：攻击者构造大量同桶键打满链表，使查询退化为 O(n)；防御=随机化哈希种子（SipHash/带盐）。
  • 扩容抖动：rehash 一次性重建会卡顿，大表应分批或增量 rehash。

原理与取舍

  • 链式 vs 开放寻址：开放寻址缓存更优但删除难；链式删除易但指针开销大、对 GC 不友好。
  • 加密哈希进哈希表：纯属浪费算力，除非你要的是安全属性。
