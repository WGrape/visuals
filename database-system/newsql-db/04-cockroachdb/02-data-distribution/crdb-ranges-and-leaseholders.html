CockroachDB 数据分布

①Range：数据分布的最小单位

CockroachDB 把整张表（以及所有索引）按主键顺序切成一段段连续的键值区间，每段叫一个 Range， 默认达到阈值就分裂，变小了会合并。每个 Range 是一个独立的 Raft 组，有自己的副本集合。

Range 是调度、分裂、副本放置的共同单位
与 TiDB 的 Region 概念几乎一一对应（都是按主键有序切段 + Raft 组 + 自动分裂调度）， 但术语不同：CockroachDB 叫 Range + Leaseholder，TiDB 叫 Region + Leader。 具体阈值与默认副本数请以所用版本文档为准，不要照抄旧资料里的数字。

②Leaseholder：读写走谁

每个 Range 的 Raft 组里有一个 Leaseholder（租约持有者），它不同于 Raft Leader 但通常重合：

  • 所有读写请求都先打到 Leaseholder，由它负责一致性读与写入提案。
  • 写仍需走 Raft 达成多数派提交；读在租约有效期内可直接本地返回，省掉一轮 Raft 往返。
  • 租约会过期与迁移。节点挂掉后要等租约超时才能把 lease 转走，这决定了故障恢复时间。
  • Leaseholder 分布不均会造成读热点，需要通过负载均衡或打散主键缓解。
Follower Reads：允许从非 Leaseholder 的副本读取略旧的数据 （例如 AS OF SYSTEM TIME 指定一个过去的时间戳）。 代价是牺牲实时性，收益是不用跨区访问 Leaseholder——在多区域部署下能把读延迟从跨洲降到本地。 适合报表、对账、历史查询这类容忍几十秒~分钟级延迟的场景。

③一致性、时钟与事务重试

混合逻辑时钟（HLC）

CockroachDB 用 HLC 而非 TrueTime：物理时钟 + 逻辑计数器， 节点间时钟偏差超过阈值会触发告警。它不能消除时钟偏差的影响， 只是把偏差限制在可观测范围内。

Serializable 是默认隔离

默认提供最强的可串行化隔离，而不是常见的「读已提交」。 好处是没有幻读与写偏斜，代价是写冲突更常见、必须处理重试。

40001 重试错误

事务因冲突被中止时返回特定错误码，应用层必须重试整个事务。 这是使用 NewSQL 最容易踩的坑：把重试逻辑漏掉，就会随机报错。

幂等是前提

重试意味着同一事务可能被执行多次（或部分执行后回滚）。 写入必须是幂等的，或依赖事务原子性保证「要么全成要么全不成」。

-- 客户端侧重试伪代码（各语言驱动有现成封装）
for attempt := 0; attempt < maxRetry; attempt++ {
    err := txn(ctx, func(tx *Tx) error {
        // 整段业务逻辑必须放在闭包里，重试时会整体重跑
        ...
    })
    if err == nil { return nil }
    if isRetryable(err) { continue }   // 40001 类错误
    return err
}
不要把重试放在事务内部，也不要只重试单条语句。 可串行化下被中止的是整个事务，重试单条语句会产生部分写入。 标准做法是「整个业务闭包 + 指数退避重试 + 幂等键」三件套。

关键概念：Range 是按 key 范围切分的连续片段，每个 Range 是一个独立的 Raft Group（有自己的 leader、日志、leaseholder）。这与“按 key 哈希分片”不同——范围分片保留了 key 的顺序，所以范围扫描只碰少数几个 Range（哈希分片则要扫全部分片）。

Range 观测与操作

-- 查看 Range 分布（CRDB 的必备排障 SQL）
SHOW RANGES FROM TABLE orders;
--   start_key  end_key  range_id  range_size_mb  lease_holder  replicas  voting_replicas
--   NULL       /1000    42        245            3              {1,3,5}   {1,3,5}
--   /1000      /2000    43        312            7              {2,7,9}   {2,7,9}
--   -> lease_holder 所在节点负责该 Range 的读和协调写

-- 查看集群各节点的 Range 数与容量
SELECT node_id, range_count,
       round(used_capacity/1024^3,1) AS used_gb,
       round(available_capacity/1024^3,1) AS avail_gb
FROM crdb_internal.kv_store_status;

-- 找出最大的 Range（可能需要手动分裂）
SELECT range_id, round(range_size/1024^2) AS mb,
       start_key, end_key, lease_holder
FROM crdb_internal.ranges
ORDER BY range_size DESC LIMIT 10;

-- 手动分裂（热点 Range 手动打散）
ALTER TABLE orders SPLIT AT VALUES (1000), (2000), (3000);

-- 手动转移 leaseholder（负载均衡）
ALTER TABLE orders RELOCATE LEASE TO 5;
ALTER TABLE orders RELOCATE TO 5, 6, 7;    -- 搬副本

热点 Range 是最常见的性能问题：如果主键是单调递增的（自增 ID 或时间戳前缀），所有写入都会打到最后一个 Range——单点瓶颈，无法分散。解法：① 用随机前缀或 UUID 作为主键；② 用 ALTER ... SPLIT AT 预分裂；③ CRDB 18.0+ 支持哈希分片索引（USING HASH）。

Leaseholder：读写的关键角色

角色职责数量与 Raft Leader 的关系
Raft Leader接收写请求、驱动 Raft 日志复制每个 Range 1 个—
Leaseholder服务读请求、协调写、维护时间戳缓存每个 Range 1 个通常与 Raft Leader 是同一节点（会跟随转移）

为什么要区分 Leaseholder 和 Raft Leader：因为读操作不需要走 Raft 日志（那样太慢）。Leaseholder 持有一个租约（lease）——在租约期内它保证自己是最新的（能读到所有已提交的数据），所以可以直接本地读，不需要与其他副本通信。这就是 CRDB 能提供可串行化隔离级别但读延迟仍然很低的原因。

Leaseholder 操作

-- 查看 leaseholder 分布是否均衡
SELECT lease_holder, count(*) AS ranges
FROM crdb_internal.ranges
GROUP BY lease_holder ORDER BY ranges DESC;
--   如果某个节点的 range 数明显多于其他 -> 该节点读压力大
--   CRDB 会自动做 lease 再平衡，但有时需要手动触发

-- 查看租约转移历史（排查抖动）
SELECT * FROM crdb_internal.lease_history LIMIT 20;

-- 强制转移某个热点 Range 的 lease
ALTER TABLE orders RELOCATE LEASE TO 3;

-- 关键配置：lease 相关的系统设置
SHOW CLUSTER SETTING kv.lease.transfer_timeout;      -- 租约转移超时
SET CLUSTER SETTING kv.range_split.by_load_enabled = true;    -- 按负载分裂（关键！）
SET CLUSTER SETTING kv.range_split.load_based_threshold = 1000; -- QPS 阈值

-- 按负载分裂（Load-based Splitting）是 CRDB 的特色：
#   当某个 Range 的 QPS 超过阈值，<b>即使没到大小上限也会分裂</b>
#   这能自动打散热点（传统按大小分裂做不到这点）

Load-based Splitting 是 CRDB 解决热点 Range 的关键特性：传统分片只按大小分裂，一个被高频访问的小 Range 永远不会分裂。CRDB 会监控每个 Range 的 QPS，超过阈值（默认约 1000 QPS）就分裂，从而把热点分散到多个 Range、多个节点。

深入自检

Range 和 TiDB 的 Region 有什么区别？

概念几乎一样（都是按 key 范围分片 + Raft 多副本），主要差别在默认值和调度：① 默认大小——CRDB Range 默认 512 MiB 分裂、TiDB Region 默认 96 MiB 分裂（TiDB 的更小，调度更灵活但元数据更多）；② 调度器——TiDB 有独立的 PD（Placement Driver）集群做全局调度，CRDB 的调度是内置在集群里的（每个节点参与）；③ 读服务——CRDB 用 Leaseholder，TiDB 用 Leader + Follower Read（可配置从副本读，牺牲强一致换延迟）；④ 分裂策略——CRDB 支持按负载分裂，TiDB 主要按大小（也有按 key 数量）。

跨地域部署怎么配置？

CRDB 的特色能力是副本放置策略（用 SQL 声明数据放哪）：① ALTER TABLE ... CONFIGURE ZONE 设置 num_replicas、constraints、lease_preferences；② 典型配置：3 副本分别放在 3 个地域，并把 lease_preferences 设为用户所在地域——这样读请求本地就能完成（本地性延迟），写入仍需跨地域共识；③ 更激进的做法是用 REGIONAL BY ROW 表——每一行根据某个字段（如 region 列）自动放到对应地域，实现真正的数据主权（data domiciling）和本地读写。代价：跨地域写入延迟 = RTT（北京↻欧洲约 200 ms），所以要把写入和读的 lease 放在同一侧。

Range 太多会有什么问题？

三个问题：① Raft 开销——每个 Range 一个 Raft Group，都要维持心跳（默认约每秒数次）和选举定时器，Range 数上万时心跳流量就会占用可观的网络和 CPU；② 元数据压力——Range 的描述信息存在 meta ranges 里，Range 越多，查找路由的深度和缓存压力越大；③ 调度开销——再平衡算法要跟踪所有 Range 的负载。经验上限：单个节点几万个 Range 是合理的，超过 10 万就要关注。控制方法：调大 range_max_bytes、清理无用数据（让小 Range 自动合并）。

怎么排查某个查询慢？

四步：① EXPLAIN——看是否走了索引、有没有 full scan、是否有 跨节点的分布式扫描；② 看是否是热点 Range——crdb_internal.ranges 看 range 大小和 QPS，或用 DB Console 的 Hot Ranges 页面；③ 看是否跨地域——如果 leaseholder 在另一个地域，每次读都要跨地域 RTT（几十到上百 ms）；④ 看事务重试——CRDB 是可串行化隔离，冲突时会返回 40001 错误要求客户端重试，如果应用没处理重试逻辑，会表现为“随机失败”或“很慢”。第 ④ 点是 CRDB 特有的、最容易踩的坑。
