一致性哈希与会话粘性：扩容为什么会让缓存大量失效

用三台后端加到四台的算例比较取模与哈希环，并解释粘性不是共享状态。

先分清目标是什么

负载均衡可能追求请求均匀分配，也可能希望同一用户、缓存键或对象持续落到同一后端。简单轮询容易均匀，但不保持亲和；对后端数量取模如 hash(key)%N 能稳定选择，但 N 改变时大量 key 的结果会变化。一致性哈希把键与节点映射到一个环上，让新增或删除节点时主要影响环上相邻的一部分键，常用于分布式缓存或亲和路由。

一致性哈希不保证绝对均匀，也不自动处理节点容量差异。实际系统常用虚拟节点或权重让每台机器占多个环位置，降低数据偏斜。选什么 key 很关键：按用户 ID 可以让用户粘在同一节点，按连接五元组可能在用户重连后变化，按 Cookie 需要防伪与过期策略。

取模在扩容时发生什么

假设三台节点 A、B、C，按 hash(user)%3 选后端。扩容为四台后变成 hash(user)%4，即使 A、B、C 都没坏，很多用户的余数不同，原来在 A 的用户可能跑到 B 或新 D。若会话只在各后端内存，用户会突然掉登录状态；若缓存按 key 分散，命中率短时间下降，后端数据库压力上升。具体迁移比例依哈希分布和节点数，不能用单个小样本当作固定百分比。

可以用 0 到 11 这 12 个均匀哈希值手算：分别对 3 和 4 取模，只有 0、1、2 的结果相同，其余 9 个值都会换目标，迁移比例为 75%。这个数字依赖“余数直接对应固定节点”及均匀分布，只是本例；它说明扩容时取模会扰动许多既有键。若后端只是无状态 API，重分布可能没那么严重，均匀流量反而更重要。别在没有亲和需求时复杂化算法。

哈希环的移动范围

把 A、B、C 放在环上，键顺时针找到第一个节点。新增 D 时，通常只有原先落在 D 前驱到 D 之间的键改投 D；其他键保持原节点。虚拟节点把每台机器放多个位置，使负载在统计上更平滑。节点故障时它负责的键会落到后继节点，后继必须有容量接住，否则“路由可达”仍会因过载失败。

真正的缓存系统还要搬迁数据或允许冷缓存回源。一致性哈希只告诉新请求去哪，不会把旧缓存内容自动复制过去；扩容期间要限制回源洪峰，并观察后端数据库压力。

粘性会话的代价

把用户会话只存在某后端内存，再依靠负载均衡粘性让用户每次回到该后端，是一种兼容方案。节点故障或部署重启后，这份状态仍可能丢失；如果一个“超级用户”产生极高请求量，粘性还会形成热点。更稳健的方式是把会话放共享存储，或用可验证令牌并设计撤销机制，后端尽量无状态。此时亲和可作为性能优化，而不是正确性的唯一前提。

长连接尤其要注意：四层负载均衡选一次后，一条 HTTP/2 或 WebSocket 连接可能承载大量请求。即使按新请求哈希均匀，已有热连接不会自动迁移。扩容时要结合连接排空和新连接分配策略。

权重与健康状态

不同节点规格可能不一样，可用加权虚拟节点或其他算法分配更多键到大机器。节点摘除时，环上键重映射；恢复时也会再次变化。健康检查抖动若让节点频繁上下线，键会反复迁移，缓存命中率和会话稳定性持续受损。要设置恢复阈值与排空窗口，避免一时探测失败引发全局抖动。

对请求路由和数据分片不能盲目共用同一环：请求层可快速调整，数据层迁移可能需要校验与副本协议。写入去哪个分片会影响一致性，算法升级必须有版本兼容和迁移计划。

验收与观测

用一百万个代表性用户或缓存键模拟三节点到四节点，统计每节点键数、迁移键数、最大/最小负载比；再模拟单节点故障和恢复。线上灰度时观察缓存命中率、回源 QPS、登录失效、节点 CPU、连接数和 P99 延迟。若新节点加入后少量热门 key 集中落在它上面，虚拟节点数量多也未必消除热点，需要按访问频率而非仅按键数量检查。

一致性哈希解决“节点数量变化时尽量少改路由”，不解决会话数据持久、写入幂等或后端容量。只有把三个问题分开，扩容才不会以用户掉线为代价。

一致性哈希的关键数字

项目数值/做法说明
哈希环空间2^32（常用）节点与 key 都映射到环上
虚拟节点数100 – 200 个/物理节点解决分布不均；太少仍会倾斜
节点变化时重映射比例约 K/N（K=key 数，N=节点数）普通哈希是 ~100%，一致性哈希只动 1/N
负载均衡度（100 vnodes）偏差约 5–10%虚拟节点越多越均匀，但内存与时间开销上升
典型实现Ketama、Jump Consistent Hash、Rendezvous（HRW）Jump 无需虚拟节点、分布极均匀

为什么需要虚拟节点：物理节点少时（如 3 台），它们在环上的位置是随机的，很可能把环分成很不均匀的三段（比如 10% / 30% / 60%）。每个物理节点拆成 100–200 个虚拟节点后，大数定律让分布趋于均匀。

普通取模 hash(key) % N约 (N−1)/N ≈ 100%均匀O(1)
一致性哈希 + 虚拟节点约 1/N较好（5–10% 偏差）O(N × vnodes)

一致性哈希实现与验证

# Jump Consistent Hash（Google，2014）—— 无需虚拟节点，代码极短
def jump(key, num_buckets):
    import random
    random.seed(key)
    b, j = -1, 0
    while j < num_buckets:
        b = j
        r = random.random()
        j = int((b + 1) / r)
    return b

方式做法优点缺点

会话复制/集中存储Session 放 Redis最彻底，任意后端都能服务Redis 成为依赖；增加一次网络往返
  • 首选方案是“消灭会话粘性”：把 session 外置到 Redis（或改用 JWT 无状态 token），这样任何请求都能打到任意后端——扩容、故障切换、灰度都变得简单。粘性会话是最后手段。
  • 缓存场景必须用一致性哈希：普通取模在扩缩容时会让 几乎全部 缓存 key 失效，瞬间击穿到数据库（缓存雪崩）。一致性哈希只失效 1/N。
  • 但一致性哈希不能解决热点：某个 key 被访问 100 万次（如爆款商品），无论哈希怎么算都只落在一台机器上 → 该机器被打爆。热点要靠本地缓存 + 副本 + 限流解决。
  • 按 IP 哈希的坑：移动端/NAT 出口会让大量用户共享同一个出口 IP → 严重倾斜；且用户 IP 变化会导致会话丢失。优先用 cookie 或用户 ID 做 key。
  • 健康检查与哈希的配合：节点摘除时，一致性哈希只影响该节点的 key（1/N）；如果还要保证“尽量不迁移”，可以用 有界负载的一致性哈希或 Rendezvous hashing。
  • 验证方法：用真实 key 分布跑一遍，统计各节点负载的标准差/最大最小比。偏差 > 20% 就要增加虚拟节点或换算法。
一致性哈希能彻底避免缓存失效吗？

不能，只能把失效比例从 ~100% 降到 ~1/N。要进一步降低可以用双层哈希或预热；但更实际的思路是让后端能承受短暂击穿（熔断 + 限流 + 数据库保护）。

虚拟节点越多越好吗？

不是。100–200 个通常够了；再往上收益递减，但内存和查找开销线性上升（1000 个 vnode × 1000 节点 = 100 万条环上条目）。Jump Consistent Hash 能完全避开这个问题，是更现代的选择。

自检

一致性哈希让用户落到新节点后，旧会话数据会自动出现吗？

不会。算法只改变路由，旧节点内存状态不会自动搬迁，仍需共享存储或明确迁移。
