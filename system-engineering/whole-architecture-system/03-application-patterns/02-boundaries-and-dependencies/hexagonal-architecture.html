和相近方案怎么区分？

相近方案选择边界
整洁架构都保护业务核心；六边形用输入/输出端口明确交互点，整洁架构强调层级依赖。
GoF 适配器端口适配器可使用 Adapter 模式；六边形描述整个应用边界。

最小伪代码

interface PlaceOrderPort { place(items) }
interface OrderStore { save(order) }
class PlaceOrder implements PlaceOrderPort {
  constructor(store: OrderStore) { this.store = store }
  place(items) { this.store.save(Order.create(items)) }
}

边界：端口代表业务需要的能力；别把数据库客户端接口原样搬进核心。

端口与适配器 Ports & Adapters

领域在中心，外层是适配器；依赖方向永远指向中心

核心思想：领域逻辑不依赖任何框架。它只定义『端口』（需要什么能力、提供什么能力），外层用『适配器』把具体技术（MySQL、REST、Kafka）接到端口上。业务可脱离数据库/Web 单独测试。

为何又叫『端口适配器』

因为图形象征是把系统画成六边形，每条边是一个端口，外接一个适配器。本质是『依赖倒置』的彻底贯彻。

面试高频问答

Q：六边形架构和整洁架构有什么关系？
A：它们是同一思想（依赖朝向领域核心）的不同表达。六边形强调『端口/适配器』，整洁架构强调『同心圆依赖规则』，本质都要求领域不依赖基础设施。
Q：适配器会不会越写越多？
A：会，但这是优点：每个外部技术只是一个适配器，替换技术（如 MySQL 换 Postgres）只改适配器，核心不动。

六边形架构：让核心不被外部绑架

六边形架构（Hexagonal Architecture，也叫端口与适配器 Ports and Adapters）由 Alistair Cockburn 提出。它要解决的核心问题是：业务逻辑不应该依赖任何外部设施——不依赖 Web 框架、不依赖数据库、不依赖消息队列、不依赖任何第三方 SDK。

做法是把系统分成「内」「外」两圈：内部是领域核心，外部是各种适配器，两者之间通过端口（接口）连接，依赖方向永远从外指向内。

六边形架构：领域核心居中，端口隔离，适配器可插拔

端口与适配器：一对概念讲透

概念是什么方向举例
端口 Port一个接口（抽象类），声明「我需要什么能力」或「我提供什么能力」是边界，不是实现OrderRepository 接口、PaymentGateway 接口
入站端口 Primary Port外部如何驱动核心（核心提供的能力）外 → 内CreateOrderUseCase 接口
出站端口 Secondary Port核心需要外部提供什么（核心依赖的能力）内 → 外（接口定义在内部）OrderRepository、NotificationSender
入站适配器把外部输入翻译为核心调用外 → 内REST Controller、MQ 消费者、定时任务、CLI
出站适配器实现核心要求的外部能力内 → 外JpaOrderRepository、RedisCache、AliPayGateway

最关键的一点：出站端口的接口定义在领域层，实现在基础设施层。这就是依赖倒置——核心说「我需要一个能存订单的东西」，但不关心它是 MySQL、MongoDB 还是内存 Map。于是换数据库时领域代码一行不用改。

和传统分层的本质区别

传统分层（依赖向下）

Controller → Service → Dao → Database。每一层依赖下一层的具体实现。

  • 问题：Service 里 import 了 JdbcTemplate，就绑死在 JDBC 上
  • 单元测试必须起数据库或用大量 mock
  • 换框架、换存储、换协议都会波及业务代码

六边形（依赖向内）

所有依赖箭头指向领域核心，核心不 import 任何外部东西。

  • 领域层只有接口，实现在外部注入
  • 测试时用内存实现替换真实适配器，秒级、稳定
  • 外部技术变化被适配器挡住，核心零改动

「六边形」是比喻不是形状

六条边只是示意「可以有多个端口」，不代表必须正好六个。

  • 实际可以有任意多个入站/出站端口
  • 名字也叫 Onion（洋葱）和 Clean Architecture，思想一致：依赖向内、核心独立

落地：目录结构怎么放

order-service/ ├── domain/ ← 领域核心（零外部依赖，纯 Java/Kotlin） │ ├── model/ Order、OrderItem、Money（充血模型，含业务规则） │ ├── service/ OrderDomainService（跨聚合的领域逻辑） │ └── port/ ── 出站端口（接口） │ ├── OrderRepository.java │ └── PaymentGateway.java ├── application/ ← 用例编排层 │ ├── usecase/ CreateOrderUseCase（入站端口 + 实现） │ └── dto/ Command / Query 对象 └── adapter/ ← 适配器（全部外部依赖集中在此） ├── inbound/ OrderController、OrderMqConsumer、OrderJob └── outbound/ JpaOrderRepository、AliPayGateway、RedisCache // 铁律：domain/ 下不允许出现 import org.springframework.* / javax.persistence.*

什么时候值得用

  • 值得：业务逻辑复杂（规则多、状态流转多）、生命周期长（要维护多年）、需要高测试覆盖率、外部依赖多变（可能换数据库/换框架/多入口）。
  • 不值得：简单 CRUD 后台、生命周期短的原型、团队对依赖倒置与领域建模不熟悉（会变成为了分层而分层）。
  • 代价要清楚：类数量增加（每个端口一个接口 + 一个实现）、对象转换增多（DO ↔ Domain ↔ DTO）、初期开发变慢。这个成本换来的是长期可维护性与可测试性。
  • 常见反模式：把端口接口和实现放在同一个包里、让领域对象继承 JPA 实体（等于把数据库注解写进核心）、为了「纯粹」把所有逻辑塞进领域对象导致臃肿（该用领域服务时就用）。

深入自检

六边形架构和 Clean Architecture 有什么区别？

思想几乎一致：核心独立、依赖向内、边界用接口隔离。差别主要在术语与层次划分的细致度。六边形强调「端口与适配器」，只有内（领域）外（适配器）两圈，术语最少；Clean Architecture（Robert C. Martin）画了四层同心圆：Entities → Use Cases → Interface Adapters → Frameworks & Drivers，术语更细、规则（依赖规则）表述更形式化；DDD 分层（Interface/Application/Domain/Infrastructure）则是工程落地视角。实践上可以认为它们是同一原则的不同表达，选一套术语贯彻到底即可，不要混着用。

Repository 接口该放在领域层还是应用层？

放在领域层。理由是：Repository 表达的是「领域对象的持久化契约」，它的方法名应该用领域语言（findByOrderNo、save），而不是数据语言（selectByColumn、insert）。领域服务和用例都可能需要它，放领域层才能被两者共享。实现（JpaOrderRepository）放在适配器层，用 JPA/MyBatis 等具体技术实现，并负责 DO 与 Domain 对象之间的转换。这样领域层不会因为换 ORM 而变动。

这么分层会不会导致大量无谓的对象转换？

确实会，这真实成本。缓解办法：① 明确每一种对象的用途，不要为转换而转换——如果 Domain 和 DO 字段几乎一致且无业务行为，可以考虑合并（简单 CRUD 场景）；② 用 MapStruct 之类的工具自动生成转换代码，减少手写；③ 只在边界处转换——跨层时转，层内部不转；④ 判断是否值得：业务规则越多、越复杂，转换成本越能被收益覆盖；纯 CRUD 则不值得。架构决策永远是权衡，不是照搬。

如何在已有系统上渐进式改造？

不要推倒重写。推荐「绞杀者模式」：① 新功能严格按六边形写，作为示范；② 在现有 Service 层之上引入端口接口，把最深层的外部依赖（如支付网关、短信）先抽成端口，收益最直接；③ 逐步把散落在 Controller 和 SQL 里的业务规则搬进领域对象；④ 每次改动配套补单元测试，因为可测试性是这套架构的核心收益；⑤ 用 ArchUnit 之类的工具加架构守护测试，防止依赖方向被后续开发破坏。
