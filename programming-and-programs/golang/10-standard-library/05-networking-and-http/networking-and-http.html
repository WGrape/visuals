服务端

func(w, r)

http.HandlerFunc 把普通函数适配成 Handler；http.ListenAndServe 启动；路由用 mux.HandleFunc 注册。

func hello(w http.ResponseWriter, r *http.Request) {
    fmt.Fprintln(w, "hello")
}
mux := http.NewServeMux()
mux.HandleFunc("/hello", hello)
http.ListenAndServe(":8080", mux)
客户端

http.Get 与 Do

简单请求用 http.Get；要控制超时/Header/Body 就用 http.Client + http.NewRequest，并务必关闭 resp.Body。

resp, err := http.Get("https://example.com")
if err != nil { /* ... */ }
defer resp.Body.Close()
body, _ := io.ReadAll(resp.Body)
中间件

包装 Handler

中间件是 func(http.Handler) http.Handler，用来做日志、鉴权、恢复；多个中间件层层包裹，形成责任链。

func logMW(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        log.Println(r.URL.Path)
        next.ServeHTTP(w, r)
    })
}
超时与取消

别让请求挂死

服务端给 Handler 设超时，客户端给 Client.Timeout 设上限；用 r.Context() 在取消时及时退出下游调用。

⚠️ 不设超时的 HTTP 服务，遇到慢下游会耗尽连接与 goroutine，最终雪崩。

net/http 的两副面孔：服务端与客户端

同一个包既做服务端也做客户端，但两者的关注点完全不同：服务端要防慢连接、控超时；客户端要复用连接、控并发。

服务端按连接起 goroutine，客户端靠 Transport 复用连接
Server 超时Read / Write / Idle / ReadHeader 四个都要设。
Client 复用Client 与 Transport 都要复用，不要每次新建。
Body 必须关不关 Body 连接就不会回到池里，池会耗尽。
优雅退出用 Shutdown 而不是 Close，等请求处理完。

服务端：必须配置的超时与优雅退出

srv := &http.Server{ Addr: ":8080", Handler: mux, ReadHeaderTimeout: 5 * time.Second, // 防慢头部攻击 ReadTimeout: 15 * time.Second, // 读完整请求 WriteTimeout: 30 * time.Second, // 写响应 IdleTimeout: 60 * time.Second, // keep-alive 空闲 } go func() { if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) { log.Fatal(err) } }() // 优雅退出：先停止接收新连接，再等存量请求 quit := make(chan os.Signal, 1) signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM) <-quit ctx, cancel := context.WithTimeout(context.Background(), 20*time.Second) defer cancel() if err := srv.Shutdown(ctx); err != nil { srv.Close() // 兜底强制关闭 }

为什么只设 WriteTimeout 不够：慢客户端可以慢慢发请求头，占住连接不释放。ReadHeaderTimeout 专门防这一类「慢速攻击」，是公网服务必备项。

客户端：连接池与三个必做动作

动作做法不做会怎样
关闭 Bodydefer resp.Body.Close() 且读完连接不归还，池耗尽后请求排队
复用 Client包级变量保存一个实例每次新建 Transport，连接无法复用、句柄暴涨
设置 TimeoutClient.Timeout 或用 context下游卡住会把上游拖垮
限制重定向CheckRedirect 设上限遇到循环重定向会一直跳
读完整 Body需要复用连接时必须读完剩余数据未读会导致连接被丢弃
// 一个可复用的客户端（包级变量） var client = &http.Client{ Timeout: 10 * time.Second, Transport: &http.Transport{ MaxIdleConns: 200, MaxIdleConnsPerHost: 50, // 关键：默认只有 2 MaxConnsPerHost: 200, IdleConnTimeout: 90 * time.Second, DialContext: (&net.Dialer{ Timeout: 3 * time.Second, KeepAlive: 30 * time.Second, }).DialContext, }, } // 正确使用姿势 resp, err := client.Get(url) if err != nil { return err } defer resp.Body.Close() body, err := io.ReadAll(io.LimitReader(resp.Body, 1<<20)) // 限大小

MaxIdleConnsPerHost 默认是 2，这是高并发下最常见的隐形瓶颈：对同一个域名，超过 2 个的空闲连接会被直接关闭，导致反复建连。

路由与中间件

Go 1.22+ ServeMux支持 GET /path/{id} 模式与方法匹配
中间件即包装func(http.Handler) http.Handler
顺序很重要恢复 panic 的中间件要最外层
context 传值请求级数据放 ctx，不要全局变量
Handler 里别做重活耗时任务丢给后台并立即返回

// Go 1.22+ 的增强路由 mux := http.NewServeMux() mux.HandleFunc("GET /users/{id}", getUser) mux.HandleFunc("POST /users", createUser) mux.Handle("/static/", http.StripPrefix("/static/", http.FileServer(http.Dir("static")))) func getUser(w http.ResponseWriter, r *http.Request) { id := r.PathValue("id") // ... } // 中间件链 func chain(h http.Handler, mw ...func(http.Handler) http.Handler) http.Handler { for i := len(mw) - 1; i >= 0; i-- { h = mw[i](h) } return h } handler := chain(mux, recoverMW, loggingMW, authMW)

深入自检

为什么我的服务在压测下连接数暴涨？

通常是客户端没关 resp.Body 或没读完，连接无法归还连接池，Transport 只能不断新建。检查所有发起请求的地方是否都 defer Close，以及是否需要读完 Body。

默认 Transport 能直接用吗？

DefaultTransport 已经有合理的默认值，但它没有 Timeout，且 MaxIdleConnsPerHost 只有 2。生产环境应显式构造 Transport 并设置超时与每主机连接数。

优雅退出为什么要用 Shutdown 而不是 Close？

Close 会立即关闭所有连接，正在处理的请求会被中断；Shutdown 先停止接收新连接，再等待存量请求完成（或超时）。对无损发布来说这是必须的。

Handler 里 panic 了会怎样？

net/http 会 recover 掉单个连接的 panic，不至于让整个进程崩溃，但该请求会中断并返回空响应。仍建议加一层 recover 中间件记录日志并返回 500。

HTTP/2 需要额外配置吗？

使用 TLS 时标准库通常会自动协商 HTTP/2，无需额外代码。明文 HTTP/2（h2c）需要显式配置。注意 HTTP/2 下连接复用更充分，连接池参数的意义会变化。

Go 网络编程的关键默认值（很多是坑）

项目默认值问题 / 建议
http.Client.Timeout0 = 永不超时必须显式设置，否则请求会永远挂住
Transport.MaxIdleConnsPerHost2默认值太小！高并发下必须调到 50~200
Transport.MaxIdleConns100全局上限，也要调大
Transport.IdleConnTimeout90s要小于服务端的 keepalive 超时
http.Server.ReadTimeout0设 5~10s，防慢客户端攻击
http.Server.WriteTimeout0设 10~30s
http.Server.IdleTimeout0设 60~120s
http.DefaultClient无超时生产禁用，必须自建 client
TCP KeepAlive15s（net.Dialer）探测间隔
SetReadDeadline无长连接要设，否则读会一直阻塞

最重要的三条：① Client.Timeout 默认是 0（永不超时），线上必设；② MaxIdleConnsPerHost 默认只有 2，是并发瓶颈；③ 必须读完并关闭 Response.Body，否则连接不会归还连接池，最终耗尽。

正确用法代码

// 1) 生产用的 HTTP Client（复用！不要每次 new）
var client = &http.Client{
    Timeout: 10 * time.Second,
    Transport: &http.Transport{
        MaxIdleConns:        1000,
        MaxIdleConnsPerHost: 100,                    // 默认是 2，必须调
        MaxConnsPerHost:     200,
        IdleConnTimeout:     90 * time.Second,
        ForceAttemptHTTP2:   true,
    },
}

func get(url string) ([]byte, error) {
    resp, err := client.Get(url)
    if err != nil { return nil, err }
    defer resp.Body.Close()
    if resp.StatusCode != 200 {
        io.Copy(io.Discard, resp.Body)     // 关键：即使不要 body 也要读完才能复用连接
        return nil, fmt.Errorf("status %d", resp.StatusCode)
    }
    return io.ReadAll(resp.Body)
}

// 2) 服务端超时（防慢客户端）
srv := &http.Server{
    Addr:         ":8080",
    Handler:      mux,
    ReadTimeout:  5 * time.Second,       // 读请求头+body
    WriteTimeout: 30 * time.Second,      // 写响应
    IdleTimeout:  120 * time.Second,     // keepalive 空闲
    ReadHeaderTimeout: 2 * time.Second,  // 只读请求头，防 Slowloris 攻击
}
log.Fatal(srv.ListenAndServe())
// 3) 用 context 控制超时（比 Client.Timeout 更灵活）
ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
defer cancel()
req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)
resp, err := client.Do(req)
// ctx 超时会自动取消请求并关闭连接

// 4) TCP 层的超时控制
conn, err := net.DialTimeout("tcp", addr, 3*time.Second)
if err != nil { return err }
conn.SetDeadline(time.Now().Add(30 * time.Second))    // 整体截止
conn.SetReadDeadline(time.Now().Add(10 * time.Second))
conn.SetWriteDeadline(time.Now().Add(10 * time.Second))

// 5) 优雅退出（K8s 滚动更新不丢请求）
srv := &http.Server{Addr: ":8080", Handler: mux}
go func() { srv.ListenAndServe() }()
<-sigterm
ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
defer cancel()
srv.Shutdown(ctx)      // 停止接收新请求，等待进行中的请求完成

排障清单

症状原因处理
请求永久挂住Client.Timeout=0显式设 Timeout 或用 context
并发上不去MaxIdleConnsPerHost=2调到 50~200；按 QPS × RT 估算
连接耗尽 / too many open files没读 body 就 close，连接没归还先 io.Copy(io.Discard, body) 再 Close
connection reset by peer复用了服务端已关闭的连接IdleConnTimeout < 服务端 keepalive；加重试
服务端被慢客户端拖死没设 ReadTimeout/ReadHeaderTimeout设 5s / 2s；前面加 Nginx 缓冲
滚动更新时 502没做优雅退出用 srv.Shutdown(ctx)；配 K8s 的 preStop
DNS 解析慢每次请求都解析用自定义 Dialer.Resolver 加缓存；或复用连接
TLS 握手慢没复用会话用同一个 Transport（自动复用 session ticket）

连接池大小的算法：连接数 = QPS × 平均 RT。QPS 1000、RT 100ms → 需要 100 个并发连接。默认 2 远远不够。
