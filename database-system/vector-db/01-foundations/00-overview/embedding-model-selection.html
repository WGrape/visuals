Embedding 模型选型

选 Embedding 模型不是「越大越好」，而是看语言覆盖、维度、上下文长度、能否私有化部署，以及和下游重排 / RAG 的配合。本文给一张可落地的选型决策表与高频坑。

01为什么单独讲选型

文本经 Embedding 变成向量，向量就是检索质量的天花板。选错模型会直接拖垮整条 RAG 链路：维度不匹配无法比对、语言覆盖不够召回崩、上下文太短把长文档语义截断。

同一个 query 和 doc 必须由同一模型编码到同一向量空间，否则相似度毫无意义——这是所有向量检索的前提。

02看哪些指标

语言覆盖

中文优先 bge / m3e；多语言选 bge-m3、Voyage-Multilingual、Cohere。

维度

常见 256 / 512 / 768 / 1024 / 1536 / 3072；维度↑ 精度↑，但存储与检索成本也↑。

上下文长度

短文本 512 够；长文档需 8192+，否则被截断丢失语义。

开源 vs 商用

必须私有化部署 → 选开源（bge / e5 / gte）；想省心 → OpenAI / Cohere / Voyage。

成本与延迟

商用按 token 计费，量大要算账；自部署吃 GPU 显存与吞吐。

指令式 Embedding

instruction-tuned（bge-m3、gte-Qwen）可按任务描述调向量，RAG 效果通常更好。

04选型决策树

① 必须私有化部署？

是 → bge-m3 / bge-large-zh / e5 / gte；否 → 进入 ②

② 多语言？

是 → bge-m3 / Voyage-Multilingual / Cohere；否 → ③

③ 主要中文？

是 → bge-large-zh / gte-large-zh / m3e；否 → OpenAI / Cohere

④ 长文档(>2k)？

是 → bge-m3(8192) / Voyage(32k)；否 → 任意 512 模型

类比：选 Embedding 模型像选「翻译官」——不同翻译官把同一句话翻成不同语言的笔记，彼此的笔记不能直接比；要比较，就固定用同一个翻译官。

05维度与成本

单条向量大小 = 维度 × 4 字节（float32）。768 维 ≈ 3 KB/条；1000 万条就是约 30 GB 纯向量，加上索引还要更多。维度直接决定内存与检索延迟。

Matryoshka 表示学习

OpenAI 3 系、bge 支持把 1536 维截断到 256 维几乎不损精度 → 省存储省检索。

量化

float32 → int8 省 4 倍内存，召回略降，常见于生产降本。

06常见坑

归一化不一致

是否 cosine 归一化要一致；内积(ip)与 cosine 结果方向不同。

缺前缀

e5 必须加 query:/passage:，不加效果骤降。

维度不对齐

query 和 doc 维度必须相同，否则无法计算。

切块不一致

编码时的切块策略要与入库一致，否则语义偏移。

相似度方向

cosine 越大越相似；某些库返回 distance 越小越相似。

只看榜单

上线前必用真实 query 集测 recall@K，而非论文分数。

最重要的一条：同一个库里所有向量必须用同一个模型、同一个版本生成。中途换模型等于换了一个向量空间，必须全量重建索引——这是选型时要一次想清楚的原因。

成本、存储与精度的量化

量化估算

存储估算（float32，1 个维度 4 字节）：

  原始向量大小 = 向量条数 × 维度 × 4 字节
  例：1000 万条 × 768 维 × 4B = 30.7 GB（还不算索引结构开销）

  HNSW 索引的额外开销：通常再增加 30%~100%（存图结构 + 多层）
  => 1000 万条 768 维，实际常按 40~60 GB 规划内存

降本三招：
  1) 降维      768 -> 384，存储直接减半
  2) 量化      float32 -> int8（标量量化），再减到约 1/4，召回率损失通常 <2%
               乘积量化（PQ）可再压，但召回损失更明显
  3) Matryoshka 表示学习（MRL）：模型支持「截断前 N 维仍可用」
     -> 一套向量按需截断，兼顾精度与成本

检索精度与速度的取舍（HNSW 参数）：
  M          每个节点的邻居数，越大图越密 -> 召回高、内存大、构建慢（常用 16~32）
  ef_construction  构建时的候选队列，越大质量越好、构建越慢（常用 200~500）
  ef_search        查询时的候选队列，越大召回越高、查询越慢（常用 64~256）
  => 调优顺序：先固定 M，再调 ef_search 到召回率达标
  • 分块（chunking）比模型选择更影响效果：块太大语义混杂，太小丢失上下文。常见 256~512 token，重叠 10%~20%，按语义边界（段落/标题）切优于按字数硬切。
  • 混合检索：稠密向量（语义）+ BM25（关键词）融合，在实体名、型号、错误码这类「精确匹配」需求上明显优于纯向量。
  • 重排序（rerank）：先用向量粗召回 top 50~100，再用 cross-encoder 精排，精度提升通常很显著，代价是一次额外的模型推理。
  • 评测：至少要有自己的一组 query-doc 对，看 recall@k（k 常取 10/50）而不是只看单条效果。

评测

# 评测最小闭环：召回率 + 延迟 + 成本，三个都要量
def evaluate(queries, gold, retrieve, k=10):
    hit = latency = 0
    for q, expect in zip(queries, gold):
        t0 = time.time()
        got = [d.id for d in retrieve(q, k)]
        latency += time.time() - t0
        hit += 1 if expect in got else 0
    return {
        "recall@%d" % k: hit / len(queries),
        "avg_latency_ms": latency / len(queries) * 1000,
    }

# 上线前必测的三个场景：
#   1) 短关键词查询（如 "401 错误"）—— 检验混合检索是否必要
#   2) 长句/口语化查询（如 "我登录老是失败怎么回事"）—— 检验语义能力
#   3) 跨语言查询（中文问、英文文档）—— 检验多语言模型是否必要
维度是不是越高越好？

不是。维度高通常带来小幅精度提升，但存储、内存、检索耗时都线性上升。先用 768 做基线，再对比降维后的召回损失，很多场景 384 就够了。

要不要用商业 API 的 embedding？

省运维、质量稳定，但有网络延迟、按量计费、数据出域三个问题。数据敏感或 QPS 很高时自建更合适。

换模型了怎么办？

必须全量重建。可行做法是双写过渡：新数据用新模型写入新索引，后台慢慢重建历史数据，切换时对两套索引做一致性抽查。
