元数据描述「数据是什么」，血缘描述「数据从哪来到哪去」——两者共同构成数据治理的基础设施。

先建立直觉：药品说明书 + 食材溯源码

  • 元数据像药品说明书：成分（字段）、用途（业务含义）、保质期（更新频率）、生产厂家（owner）。
  • 血缘像食材溯源码：这盘菜用了哪些原料、原料来自哪个农场、经过了哪些加工环节。

没有说明书，你不知道这瓶药怎么吃；没有溯源码，食材出问题时你不知道该召回哪一批。

元数据的三类

类型描述对象举例
技术元数据数据的物理特征字段名、类型、分区、存储格式、行数、文件大小
业务元数据数据的业务含义字段中文名、业务口径、计算逻辑、所属主题域
操作元数据数据的运行状况任务执行时间、产出行数、负责人、SLA、质量分
业务元数据最容易缺失，也最有价值。技术元数据可以自动采集（从 Hive Metastore 等）；但「这个字段到底什么意思」「GMV 含不含退款」这类业务口径必须靠人维护。而恰恰是它缺失，导致了最多的沟通成本和口径分歧。

血缘：表与表之间的依赖图

血缘解决的两个核心问题

① 影响分析（向下游看）

「我要改 dwd_order_detail 的字段类型，会影响谁？」——顺着血缘向下遍历，找出所有下游表与报表，逐一通知与评估。

没有血缘的后果：改了上游表结构，下游几十个任务悄悄报错或直接产出错误结果，往往几天后才被发现。这是数据开发最常见的事故类型之一。

② 溯源分析（向上游看）

「老板看板上这个 GMV 数字不对，它是怎么算出来的？」——顺着血缘向上追溯，逐层查看每一层的计算逻辑，定位问题出在哪一环。

血缘怎么采集

方式做法精度成本
SQL 解析解析任务的 SQL，提取 input/output 表高（可到字段级）中（需解析器）
运行时采集从执行引擎（Spark/Flink）的 hook 获取高中
人工登记在元数据平台手动维护取决于人高且易过时
字段级血缘比表级血缘有价值得多。表级只能告诉你「A 表变了会影响 B 表」；字段级能精确到「A 表的 amount 字段影响 B 表的 total 字段」。当一张宽表有 200 个字段时，这个精度差异决定了影响分析是否可用。

落地建议

  1. 先建表级血缘（成本低、见效快），再逐步做到字段级；
  2. 血缘要自动采集，不要靠人工维护（必然过时）；
  3. 把血缘嵌入开发流程：改表结构时自动提示影响面；
  4. 结合质量告警：上游表出问题时，自动通知所有下游 owner。

🎯 面试问答

Q：元数据和血缘有什么区别？
A：元数据是「数据的说明书」——描述单张表/单个字段是什么（类型、含义、owner、更新频率）；血缘是「数据的族谱」——描述表与表之间的来源和去向关系。一个描述实体，一个描述关系。两者互补：血缘告诉你「数据从哪来」，元数据告诉你「沿途每一站到底是什么」。

Q：为什么人工维护的元数据总是不准？
A：因为数据每天都在变，而人不会同步更新：新增了表、改了字段、换了 owner，登记信息却停留在几个月前。所以元数据采集必须自动化——技术元数据从 Metastore 自动同步，血缘从 SQL 或执行引擎自动解析。只有业务口径这类无法自动推断的信息才人工维护，且要配合流程强制（如建表时必须填写）。

Q：表级血缘够用吗？
A：能解决大部分问题，但在大宽表场景下精度不足。如果一张 200 字段的宽表改了 1 个字段，表级血缘会告诉你「下游 30 张表受影响」，但其中可能只有 2 张真正用了那个字段——告警会被淹没，影响分析失去意义。字段级血缘能精确到字段，是大型数据平台的必备能力，但采集成本也更高（需要 SQL 解析器支持列级解析）。

Q：没有血缘平台，小团队怎么办？
A：用轻量方式补位：① 强制命名规范（dwd_/dws_/ads_ 前缀体现分层），从表名就能看出大致层级；② 把 SQL 统一放在 Git 里管理，用 grep 搜表名就能找到上下游；③ 关键表在文档里手工维护一份上下游清单；④ 用开源的 DataHub / Apache Atlas / OpenMetadata 自建，成本不高。关键是先有「可追溯」的意识，工具可以逐步补。
