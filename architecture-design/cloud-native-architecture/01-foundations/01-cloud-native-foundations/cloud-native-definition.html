01什么是云原生

CNCF（Cloud Native Computing Foundation）给出的官方定义是：

云原生技术有利于各组织在公有云、私有云和混合云等新型动态环境中， 构建和运行可弹性扩展的应用。代表技术包括容器、服务网格、微服务、不可变基础设施和声明式 API。

这些技术能够构建容错性好、易于管理、便于观察的松耦合系统； 结合可靠的自动化手段，工程师可以频繁且可预测地对系统做出重大变更。

关键在"设计思想"，不在"部署位置"

维度传统上云（Cloud Hosting）云原生（Cloud Native）
迁移方式把原有应用直接搬到云主机按需要改造交付、观测与扩缩容机制；不要求一律拆成微服务
对故障的假设主要依靠人工发现与恢复用健康检查、冗余和自动恢复缩短中断
扩容方式提前配置容量，人工部署按负载和容量策略弹性扩缩容
基础设施管理手工配置、脚本声明式 + 基础设施即代码（IaC）
发布方式依赖手工步骤，回退成本较高按风险选择小批量发布、自动检查与回滚
状态管理状态常与单机绑定明确持久化和故障恢复边界；有状态服务同样可以云原生运行
常见误解：买了云服务器 ≠ 云原生；用了 Kubernetes ≠ 云原生。 单体应用也可以使用容器、自动化交付、健康检查和可观测性；关键在于是否利用动态平台的弹性与自动化能力。

02与相邻概念的区别

概念关注点与云原生的关系
云计算（IaaS/PaaS/SaaS） 资源的供给方式 云原生运行其上；云提供弹性资源，云原生提供利用这些资源的方法论
云架构 云上系统的拓扑设计（网络、CDN、负载均衡、高可用） 偏基础设施与流量架构，见《云架构系统》学科；云原生偏应用形态与交付方式
分布式系统 多节点协同的一般性原理（共识、CAP、事务） 其中的一致性、故障处理与通信原理可用于云原生系统；通用机制见《分布式系统》学科
微服务 一种架构拆分风格 是云原生定义列举的代表性架构方式，但微服务可以在非容器环境实现，也不是所有云原生应用的前提
DevOps 研发与运维协作的方法论 与云原生常结合，强调协作、自动化交付和反馈闭环；CNCF 定义没有把它列为固定“支柱”
本学科的知识边界：本学科（云原生）关注应用如何为云而生； 基础设施与流量架构（云网络、CDN、负载均衡）属于《云架构系统》； 通用分布式原理属于《分布式系统》。同名主题只在一处展开，避免重复。
