Flink 作业运行架构

以流为基石：真正的流计算、状态管理与精确一次语义

一、Flink 定位：批是流的特例

Apache Flink 是一个分布式、流处理优先（stream-first）的计算引擎。它的核心世界观是：一切皆流。数据分为无界流（Unbounded Stream，无终点的实时数据）与有界流（Bounded Stream，有起点终点的离线数据 = 批）。Flink 把批处理直接当作"有界流"来处理，因此用同一套运行时与 API 统一了流与批。

与 Spark Streaming 的本质区别：Spark Streaming（旧 DStream / 微批）把流切成一小段一小段的微批（micro-batch）来近似实时，本质仍是批；而 Flink 是真正意义上的逐条事件（event-by-event）流式处理，事件一来就处理，延迟可低至毫秒级，且天然支持事件时间与乱序。
🌊

真流（True Streaming）

逐条处理、持续计算，无需等待一个批次攒满。适合实时风控、监控告警、实时大屏等对延迟敏感的场景。

🔁

流批一体

有界流=批、无界流=实时，共用 DataStream 运行时。同一份 SQL 既可跑离线也可跑实时，避免维护两套代码。

⏱️

事件时间优先

以数据自带的时间戳（Event Time）而非到达时间（Processing Time）为基准，配合 Watermark 正确处理乱序与迟到，结果更贴近真实业务。

二、核心概念卡片

🔧

DataStream API

Flink 最核心的流处理编程接口。通过 env.addSource() 接入数据，用 map/filter/keyBy/window 等算子构建处理拓扑，最后 addSink() 写出。底层抽象是不断流动的 DataStream。

⛓️

算子链 Operator Chain

满足"一对一转发 + 并行度相同 + 允许 chain"条件的相邻算子，会被链化成同一个线程内的算子链，省去序列化/网络/线程切换开销，类似 Spark 的 Stage 内流水线。

🧮

任务槽 Task Slot

TaskManager 的资源切片（通常 = 核数）。一个 Slot 内可串行运行同一任务的多个子任务（operator chain）。并行度决定 SubTask 总数，Slot 数决定并发上限。

💾

状态 State 与 Checkpoint

State 是算子的中间记忆（如窗口聚合值、去重集合）。Checkpoint 是分布式一致性快照，周期性把各算子状态持久化，用于故障恢复，是实现精确一次的基础。

🕰️

时间语义

事件时间（Event Time）数据产生时间；处理时间（Processing Time）算子处理时刻；摄入时间（Ingestion Time）进入 Flink 源的时间。事件时间最准但需 Watermark 配合。

三、执行架构：JobManager 与 TaskManager

Flink 采用经典的主从（Master-Worker）架构：JobManager 负责协调与资源，TaskManager 负责执行具体子任务。

七、批流一体与生态

📝

Table API / SQL

声明式统一接口，同一 SQL 既可批（有界流）也可流（无界流）执行，Flink planner 自动选择执行路径，是批流一体的关键层。

🔌

CDC 连接器

通过 Flink CDC 直接捕获 MySQL/PostgreSQL/Oracle 的 binlog 变更，无需额外中间件即可构建实时数仓与同步链路。

📨

Kafka / HDFS 连接

Kafka 是 Flink 最常见的 Source 与 Sink（也是精确一次 2PC 的典型搭档）；结果常写出到 HDFS/对象存储做离线归档。

🚀

部署形态

支持 Standalone、Flink on YARN、Native Kubernetes（K8s Operator 拉起 JobManager/TaskManager），可与现有资源调度体系无缝集成。

八、面试问答

Q1：Flink 的精确一次（Exactly-Once）是怎么实现的？
三层协同：①Source 端可重放（如 Kafka offset 可重置），保证故障后能重读；②内部通过 Chandy-Lamport 的 barrier 对齐 + 状态快照，保证状态只恢复一次；③Sink 端用 TwoPhaseCommitSinkFunction 两阶段提交，等所有算子 Checkpoint 成功才真正提交外部事务。三者结合实现"端到端精确一次"，注意是结果精确一次而非内部不重放。
Q2：Flink 与 Spark Streaming 怎么选？
看延迟与语义诉求：需要毫秒级真流、复杂事件时间/乱序处理、强精确一次选 Flink（如实时风控、CEP）。若业务是分钟级准实时、团队已用 Spark 生态、以 SQL/批为主，Structured Streaming 的微批更省心、与离线代码复用度高。本质是"真流逐条" vs "微批近似"的路线差异。
Q3：Flink 的状态存在哪里？Heap 与 RocksDB 怎么选？
Heap 状态后端把状态放 JVM 堆，读写快但受 GC 与内存上限约束，状态不能太大；RocksDB 状态后端把状态放本地磁盘 + 内存块缓存，支持超大状态、增量 Checkpoint，但序列化/反序列化有额外开销。经验法则：状态超 GB 级或需增量快照用 RocksDB，小状态追求极致性能用 Heap。
Q4：反压（Backpressure）是什么？Flink 怎么处理？
反压指下游处理慢（如外部 Sink 阻塞）导致上游数据堆积、被迫降速的现象。Flink 基于信用（credit）的网路流控：接收端按自身 buffer 余量给发送端"信用额度"，收满即停发，反压沿 DAG 反向传播到 Source，无需全局协调即可自然限流，避免 OOM 且对正常算子影响最小。
