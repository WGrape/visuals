📋 完整请求链路说明

① 客户端发起 HTTPS 请求到 api.test-example.com
② DNS 解析 CNAME 到云厂商 ELB，智能调度到最近节点
③ 云防火墙 + DDoS 高防 + WAF 进行流量清洗和攻击防护
④ 四层 SLB: 基于 IP/Port 快速转发 | 七层 SLB: 基于 URL/Header 智能路由
⑤ K8s Ingress 根据路径规则 (/api/*) 路由到对应 Service
⑥ API Pod 处理业务逻辑，读写 MySQL 主从数据库
⑦ 热点数据写入 Redis 缓存，加速查询响应
⑧ 耗时任务异步投递到消息队列，由 Worker Pod 处理

🔐 四层 vs 七层 负载均衡对比

四层 L4 基于 IP + 端口转发，速度快，开销小，不解析内容，适合 TCP/UDP 长连接
七层 L7 基于 HTTP/HTTPS 协议，能看懂 URL/Header/Cookie，适合精细路由、SSL终结、限流

一图看懂：请求从上到下的七层

把一次「打开 App 首页」拆开看，它并不是「客户端连数据库」这么简单，而是穿过七层设施。每一层都在解决上一层的某个痛点：越靠外越关注接入与防护，越靠内越关注状态与一致性。理解分层的最好办法是追问：如果把这一层删掉，会出什么事？

一次请求的七层穿透：越往外层越「便宜且可丢弃」，越往内层越「昂贵且要一致」
分层的本质把「不同失效代价」的东西分开：接入层可以随便扩容丢弃，存储层不行
越外层越早拒绝能在 CDN 挡掉的流量，绝不放进网关；能在网关限掉的，绝不放进数据库
每层都要有超时上游超时必须小于下游超时之和，否则重试风暴会打穿全链路
无状态才好扩③④⑤ 尽量无状态，状态都下沉到 ⑥⑦，扩容才能靠加机器解决

各层怎么选：职责、组件与选型要点

同一层往往有多个可选组件，选型的判断标准不是「谁更强」，而是你的瓶颈在哪：连接数是瓶颈就加四层，路由规则复杂就换七层，读多写少就加缓存。

层常见组件核心职责选型要点
① 用户端App / Web / 小程序重试策略、本地缓存、离线兜底重试必须带退避与抖动，否则雪上加霜
② 接入DNS、CDN、WAF就近接入、静态加速、清洗攻击动静分离：静态走 CDN，动态回源
③ 四层LVS、NLB、F5高并发连接分发性能极高但看不懂 URL，无法做路径路由
④ 七层Nginx、APISIX、Envoy路由、鉴权、限流、灰度、可观测规则灵活但有解析开销，单机能扛的并发低于四层
⑤ 应用Spring Boot / Go 服务业务逻辑与编排横向扩容的前提是真正的无状态
⑥ 缓存Redis、Caffeine扛读、降延迟、削峰必须设计好击穿、穿透、雪崩三件事
⑦ 存储MySQL、ES、Kafka持久化、检索、异步解耦写路径尽量短，能异步的就异步

一句话记忆：四层看「谁来的」（IP+端口），七层看「要什么」（URL+Header+Body）。所以灰度发布、A/B、按用户分流这类需求只能放在七层。

时间都花在哪：200ms 的请求是怎么被吃掉的

优化性能的第一步不是「换更快的机器」，而是先量清楚时间的去向。下面是一笔典型的账，你会发现真正做业务计算的时间往往不到两成。

DNS 解析约 20~80ms，可被本地缓存与预解析降到接近 0
建连 + TLSTCP 三次握手 + TLS 握手，约 1~2 个 RTT
网关转发鉴权、限流、日志，约 1~5ms
业务计算服务内 CPU 时间，通常是大头中最小的一块
下游调用串行 RPC 与 DB 查询，往往占掉一半以上
网络往返跨机房调用一次 RTT 就可能几毫秒

最容易的优化：减少往返

把三次串行 RPC 改成并发调用，省掉的是两个 RTT；把跨机房调用改成本地缓存，省掉的是整段网络。这类优化几乎不改业务代码，收益却最大。

最容易的误判：只看平均

平均值会被大量快请求拉低。一次 200ms 的平均背后，可能是九成请求 50ms、一成请求 1.5s。用户投诉的永远是那一成，所以要盯 P99 而不是平均。

深入自检：把架构讲透的六个问题

为什么需要四层和七层两层负载均衡？

因为它们的性价比不同。四层只做转发，单机可扛百万级并发，成本极低，适合放在最前面承接全部流量；七层能读懂 HTTP，可以做路径路由、鉴权、限流、灰度，但每台能扛的并发少一个量级。先四层后七层，就是用便宜的机器扛量、用贵的机器做精细化控制。

DNS 为什么不直接返回一个固定 IP？

因为一个域名背后需要按需把用户导到不同机房：就近接入、机房级容灾、灰度切流都依赖 DNS 给出不同结果。代价是 DNS 有缓存，切换生效慢，所以重要场景会配合短 TTL 与 HTTPDNS。

CDN 命中不了怎么办？

这叫回源：CDN 边缘节点没有缓存或缓存过期，就回你的源站取数据再缓存起来。回源率过高说明缓存策略有问题（缓存时间太短、URL 带了随机参数、没区分动静），会被动放大源站压力。

网关挂了是不是全站不可用？

如果只有一组网关，是的。所以网关本身要多层部署 + 四层负载均衡 + 健康检查自动摘除；更稳的做法是旁路化：把鉴权、限流做成网关插件的同时，服务自身也有兜底限流，不把命交给单一组件。

服务无状态到底指什么？

指不在服务进程内存里存放「换个实例就丢失且不可重建」的数据：会话、定时任务状态、本地文件。这些东西要挪到 Redis、数据库、对象存储里，否则扩容和重启都会出问题。

为什么下游一定要配超时和熔断？

因为没有超时的调用会把上游的连接池慢慢耗光，一个慢的下游能拖垮整条链路。熔断则是在下游已经明显不健康时快速失败，给下游留出恢复时间，而不是被重试持续捶打。

线上排查清单：从现象反推是哪一层

全部用户打不开先看 DNS 与接入层，再看四层是否有存活节点
部分区域慢CDN 节点或运营商链路问题，看按地域的延迟分布
5xx 突增网关后端的健康实例数、服务发布、下游超时
延迟高但 CPU 低多半是排队或下游慢，看线程池与连接池占用
数据库 CPU 打满缓存击穿或慢查询，看命中率与慢日志

只有新版本异常灰度流量比例、配置下发、序列化兼容
偶发超时GC 停顿、网络抖动、连接池耗尽、热点分片

分层架构与每层的量化职责

一个完整的后端架构可以拆成 8 层。每层的价值是把某一类问题收敛到一处解决，避免每个服务重复处理。

层组件解决什么关键指标
接入层DNS、CDN、WAF、DDoS 防护就近访问、抗攻击、卸载静态流量CDN 命中率 >95%
网关层Nginx / APISIX / Kong / Envoy路由、限流、鉴权、TLS 卸载、灰度P99 网关耗时 <20ms
应用层微服务（Go/Java）业务逻辑P99 <100ms，无状态
服务治理注册中心、配置中心、熔断限流服务发现、动态配置、故障隔离熔断触发次数
异步层Kafka / RocketMQ削峰、解耦、最终一致积压条数、消费延迟
缓存层本地缓存 + Redis 集群降低读压力命中率 >95%，P99 <2ms
数据层MySQL（主从/分库分表）+ 搜索引擎 + 对象存储持久化与检索慢查询数、主从延迟
可观测日志、指标、链路追踪出问题能定位覆盖率、告警准确率

延迟预算分解

# 延迟预算（总 200ms 的一次典型请求）
#   DNS 解析        5~50 ms   （有缓存则 ~0）
#   TCP + TLS       1~2 RTT   （同机房 1ms，跨地域 30~100ms）
#   CDN 边缘        1~5 ms    （命中时）
#   网关            5~20 ms
#   应用逻辑        10~50 ms
#   缓存读取        1~3 ms    （Redis 同机房）
#   或 DB 查询      5~30 ms   （走索引）
#   RPC 调用        5~20 ms   （每个下游服务）
#   序列化返回      1~5 ms
#
# 关键洞察：<b>网络往返（RTT）是大头</b>
#   同机房 RTT ~0.5ms，同城 ~2ms，跨城 ~30ms，跨国 ~200ms
#   所以架构设计第一原则是：<b>减少跨地域调用</b>，其次才是优化代码

架构演进的通用路径：单体 → 按业务拆分服务 → 引入缓存/MQ/分库分表 → 容器化与治理。绝大多数系统在「单体 + 缓存 + 读写分离」阶段就能撑到日活百万，不要过早微服务化——微服务带来的分布式复杂度（一致性、排查、部署）往往超过它解决的团队协同问题。

每一层的常见故障与防护

故障影响防护手段
单实例宕机部分请求失败多实例 + 负载均衡 + 健康检查（摘除 <5s）
下游服务变慢线程池打满，级联雪崩超时 + 熔断 + 隔离舱（bulkhead）
下游全挂功能不可用降级（返回兜底/缓存/默认值）
流量突增全部超时限流（网关层 + 应用层）+ 排队/削峰
DB 慢查询整体变慢慢查询监控 + 超时 + 读写分离 + 缓存
缓存集体失效DB 被打垮TTL 抖动 + 多级缓存 + 熔断
MQ 积压数据延迟监控积压 + 消费者扩容 + 死信队列
机房故障整体不可用多可用区 / 异地多活（成本最高，按需）

冗余与健康检查

# 容量与冗余的经验数字
#   单机水位：CPU < 60%，内存 < 70%，连接数 < 上限的 70%
#   冗余：N+1（能扛 1 台故障），核心服务 N+2
#   扩容触发线：CPU 或 QPS 连续 5 分钟 > 70%
#   线程池：核心服务单独池，避免一个慢接口拖垮全局
#   超时：下游超时的累加 < 上游超时（否则重试无意义）
#     例：A -> B -> C，A 超时 500ms，则 B 应 <= 300ms，C 应 <= 200ms

# 健康检查（K8s）
livenessProbe:                 # 活不活着，失败就重启
  httpGet: { path: /healthz, port: 8080 }
  initialDelaySeconds: 10
  periodSeconds: 10
readinessProbe:                # 能不能接流量，失败就摘除
  httpGet: { path: /ready, port: 8080 }
  periodSeconds: 5
#   /healthz 只查进程存活；/ready 要查依赖（DB/Redis）是否可用
#   注意：/ready 查依赖太严格会导致依赖抖动时全部摘除
什么时候该拆微服务？

三个信号满足两条：① 团队规模——超过 2~3 个团队在同一个代码库上冲突（Conway 定律）；② 独立伸缩需求——某块业务（如视频转码）的资源需求与主体完全不同；③ 独立发布需求——某块业务要每天发多次，主体每季度才发一次。如果三条都不满足，单体 + 模块化是更优解（部署简单、排查容易、无分布式事务）。

为什么说「不要过早优化架构」？

因为分布式系统的复杂度是阶跃式的：引入服务拆分就要处理服务发现、链路追踪、分布式事务、幂等、最终一致、跨服务排障。这些问题每一个都能吃掉几个人月。而「单体 + 缓存 + 读写分离 + 异步化」这套组合，实测能撑到日活百万、QPS 万级。所以正确的做法是：先做到单体瓶颈，再按上面三个信号逐块拆分。

怎么评估一个架构合不合理？

看四个问题：① 单点——任一组件挂掉会怎样，有没有冗余；② 容量——能不能水平扩展，有没有状态阻碍扩容；③ 故障隔离——一个模块挂掉会不会拖垮全局（有没有熔断/隔离）；④ 可观测——出问题时多久能定位（有没有指标/日志/链路）。这四条比「用了多少中间件」重要得多。
