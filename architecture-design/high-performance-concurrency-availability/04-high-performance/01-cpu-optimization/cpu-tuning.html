CPU 优化实战

把热点函数的 CPU 占用压下来：算法、并发与缓存友好。

优化顺序：先大后小

二八法则

80% 的 CPU 往往消耗在 20% 的代码上。先用剖析工具找到那 20%，再谈微优化，否则容易在无关紧要的地方过度工程。

常见杠杆依次递减：算法与数据结构 → 并发/并行 → 减少无效计算 → 缓存友好 → 编译器/语言层微调。

并发与并行的取舍

无锁/批处理

CPU 密集型优先用多进程（每进程独立 GIL）或语言原生线程；I/O 密集用异步。避免用多线程去扛纯计算——GIL 会把它打回单核。

典型手段：把不变的计算提到循环外、用查表代替重复计算、合并多次小分配、开启编译器的 -O2/-O3 与 PGO（基于剖学的优化）。

问题 1
如何系统性降低 CPU 占用？

先剖析定位最大热点；优先换更优的算法/数据结构；再考虑并发并行摊薄；最后才是循环级微优化与编译器开关。每一刀都用前后火焰图对比验证。

问题 2
多进程还是多线程更适合 CPU 密集？

多进程。Python 受 GIL 限制，多线程无法并行执行字节码；Java/Go 等原生线程可并行，但要警惕锁竞争。跨进程注意序列化与通信开销。

问题 3
什么是伪共享（false sharing）？

多个 CPU 核心各自修改同一缓存行里不同变量时，缓存行在核心间反复失效同步，导致本应并行的写变成串行。对策是对齐到缓存行或加填充隔离。

问题 4
编译器优化能指望多少？

能白捡一部分，但无法替代算法层面的改进。开启 -O2 通常稳；PGO 在热路径明显的服务上可再快几个百分点。

通用原则：先量化（profile），再优化；每次只改一处；改完必须验证。凭直觉优化往往改了不痛不痒的地方。

实践要点

① 算法与数据结构

  • 复杂度是第一位：O(n²) 在数据量上来后无药可救。
  • 哈希表/索引替代线性查找。
  • 避免循环内重复计算与重复分配。
  • 用批量接口替代逐条调用。

② 减少重复工作

  • 缓存计算结果（注意失效策略）。
  • 预计算与物化。
  • 复用缓冲区与对象（注意并发安全）。
  • 提前校验，避免无效请求走完整流程。

③ 并发与亲和

  • 线程数匹配核数（CPU 密集）或更高（IO 密集）。
  • 减少锁粒度与共享，避免伪共享。
  • NUMA 架构：绑核 + 本地内存分配。
  • 注意容器 CPU limit 与 CFS 配额导致的节流（throttling）。

④ 系统层

  • 关闭省电模式（performance governor）降低抖动。
  • 注意 CPU 节流：容器 cpu.max、cfs_quota。
  • 隔离中断与业务核（isolcpus）。
  • 关注超线程带来的 30% 左右性能而非 100%。
  • 云服务器注意 CPU 积分与基线性能。

深入自检

CPU 使用率高就一定要优化吗？

不一定。CPU 高说明资源被充分利用，这本身是好事（说明没在空等）。需要优化的是「无效的 CPU 消耗」：重复计算、低效算法、不必要的序列化、过多的系统调用。判断标准是看「单位业务量消耗的 CPU」是否合理，而不是使用率数字本身。

为什么 sy 高也是问题？

因为内核态时间不产出业务价值：上下文切换、系统调用、锁竞争、内存管理都在消耗 CPU，还会导致缓存与 TLB 失效。典型场景：线程过多导致频繁切换、小包网络 I/O 导致大量系统调用、mmap 缺页风暴。降 sy 的常见手段是批量化与减少线程。

容器里 CPU 明明没跑满，为什么延迟高？

很可能是 CFS 配额节流（throttling）：容器设置了 CPU limit 后，内核按周期（通常 100ms）分配配额，配额用完后该周期内的进程被强制挂起，表现为周期性延迟尖刺。观测：cgroup 的 cpu.stat 里 throttled_time。对策：放宽 limit、提高配额周期、或减少突发 CPU 使用。

火焰图怎么看？

横轴是样本数（越宽表示占用 CPU 越多，注意不是时间顺序），纵轴是调用栈深度。看「宽而平」的顶层函数就是热点。要点：找最宽的平顶（自身耗时）、看是否有意外的调用（如正则、序列化）、对比优化前后。采样要覆盖典型负载与足够时长。

超线程（HT）的核怎么算？

一个物理核的两个逻辑核共享执行单元与缓存，通常只能带来 20-40% 的额外吞吐，而不是翻倍。容量规划时不要按逻辑核数线性外推；压测才是可靠依据。另外要注意调度器可能把两个繁忙线程放到同一物理核上，导致性能波动。

如何系统性地做 CPU 优化？

五步：① 建立基线（当前 CPU 消耗与 QPS 的比值）；② profile 找热点（火焰图、perf）；③ 按收益排序，每次只改一处；④ 复测验证（CPU 下降、QPS 提升、延迟不恶化）；⑤ 固化回归（把性能基线纳入 CI 或定期压测）。切忌并行改多个点，那样无法归因也无法回滚。
