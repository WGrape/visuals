🎯 核心概念：什么是 CPU 密集 / I/O 密集

计算机程序运行时，主要消耗两种资源：CPU（处理器）和 I/O（输入输出）。根据瓶颈在哪，程序被分为两类：

🔴 CPU 密集型（CPU-Bound）

程序的运行瓶颈在 CPU 运算速度上。CPU 一直在忙、一直在算，几乎没有空闲。

特征：

  • 相关核心或容器配额可能持续接近饱和
  • 增加计算能力时吞吐或延迟有改善空间
  • 执行时间 ≈ CPU 计算时间
  • 仍需排除锁竞争、内存带宽等其他瓶颈

💡 类比：一个数学家在做心算，脑子是瓶颈，笔和纸不是。

🔵 I/O 密集型（I/O-Bound）

程序的运行瓶颈在 I/O 设备的速度上。CPU 大部分时间在等待，实际计算很少。

特征：

  • 请求耗时主要发生在等待外部资源期间
  • 大量时间花在等待网络/磁盘/数据库
  • 执行时间 ≈ 等待 I/O 的时间
  • 优先测量外部延迟、并发量与连接池饱和度

💡 类比：一个厨师在等外卖小哥送食材，等待是瓶颈，厨艺不是。

💡 快速判断技巧 问自己一个简单的问题："换了更快的 CPU，程序会明显变快吗？"
如果答案是「会」→ CPU 密集型；如果答案是「不会，瓶颈在读硬盘/等网络」→ I/O 密集型。

⚡ 为什么区分它们如此重要？

因为瓶颈位置不同，增加计算并行度与重叠 I/O 等待的收益也不同。混合负载需要分阶段测量，盲目加线程可能让争用更严重。

🔴 CPU 密集型 — 怎样决定并行度？

先测计算阶段的 CPU 利用率、任务耗时和队列等待，再增加工作进程或计算线程。可从可用核心数附近开始压测，但最佳并行度还受内存带宽、锁竞争、NUMA、容器配额和任务大小影响。

先找可并行的工作

独立任务可以分给多个执行单元；有共享状态或串行阶段时，加线程的收益会递减。

再测吞吐与尾延迟

逐步增加工作单元，观察吞吐、P95/P99、上下文切换和内存占用；超过某一点后继续增加可能只会增加争用。

最后选语言运行模型

Python、Go 等语言的调度和并行限制不同；通用容量决策留在本课，具体实现见下方语言专题。

Python 的 GIL、进程池与线程池选型见Python 并发模型；Go 的 goroutine 调度与任务组织见Go goroutine 课程。

🔵 I/O 密集型 — 应该怎么处理？

核心原则：不要让 CPU 闲着等 I/O，让等待时间「重叠」起来

💡 I/O 等待时 CPU 是空闲的 这是关键洞察：当一个线程在等磁盘/网络时，操作系统可以立即切换 CPU 去运行另一个线程。这意味着 I/O 密集型任务天然适合高并发——线程数可以远大于 CPU 核心数。

为什么等待型任务可以提高并发？

关键原理：

  • 网络与磁盘等待可以与其他任务的计算重叠，但协议解析和系统调用仍消耗 CPU
  • 异步任务在等待 I/O 时挂起；线程池则由操作系统调度其他可运行线程
  • 协程切换通常不需要为每个任务创建操作系统线程，但运行时调度和内存仍有成本
  • 可承载的任务数受连接池、文件描述符、内存、远端限额和超时影响

结论：I/O 并发量可以高于 CPU 核心数，但必须受连接、内存、远端限额与排队预算约束。

实现时的边界

I/O 并发量应受连接池、文件描述符、远端限额、队列长度和内存约束。异步不意味着无限并发；请给请求设置超时、取消和并发上限。具体 Python asyncio 与 Go goroutine 代码分别放在Python 异步模式和Go goroutine专题。

🎯 一句话总结 + 速查表

🔴 CPU 密集型

  • 瓶颈在 CPU 计算速度
  • 从可用核心数附近开始测并行度
  • 关注串行段、锁竞争、内存带宽与上下文切换
  • 语言运行时会影响线程或进程的选择
  • 适合的数据并行任务可评估 SIMD / GPU

🔵 I/O 密集型

  • 瓶颈在 I/O 设备速度（网络/磁盘）
  • 线程数 可以 >> CPU 核心数
  • 等待时 CPU 可切换到其他线程
  • 评估异步任务或受控线程池的资源成本
  • Python: asyncio；JS: 天然异步
  • Go: goroutine；Java 21+: Virtual Thread
🔥 记住这一句话就够了： CPU 密集看计算并行度与争用； I/O 密集看等待能否重叠及资源上限。两者都要以吞吐、尾延迟和资源占用实测。
