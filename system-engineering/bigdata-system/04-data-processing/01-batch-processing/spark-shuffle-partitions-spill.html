Spark Shuffle 分区与 Spill：为什么 200 个任务里只有最后一个很慢

用 200 GB 聚合任务计算每分区数据量，区分分区太少、数据倾斜和执行器内存不足。

先看一次 200 GB 的聚合

Spark 对 200 GB 明细按用户 ID 聚合，Shuffle 把相同键路由到同一个下游分区。若分区数只有 20，粗略平均每分区 10 GB；若是 200，平均约 1 GB；若是 2000，平均约 100 MB。真实分布不均、压缩比不同，实际任务内存需求不能只用总字节除以分区数，但这个估算可以先判断任务粒度是否明显失衡。分区数过少，单个 Reduce 任务要处理大量数据，容易 Spill 到磁盘、GC 变长甚至失败；分区数过多，会产生大量短任务和元数据开销。

Shuffle 包括上游写中间数据、下游按分区拉取、排序或聚合以及可能的磁盘 Spill。网络传输不是唯一成本。只有理解具体算子是在 Map 侧先聚合、在 Reduce 侧做排序，还是进行 JOIN，才能正确解释瓶颈。多给执行器内存未必解决数据倾斜，也可能掩盖分区设计问题。

为什么最后一个任务拖住全作业

假设 199 个 Reduce 任务各用 30 秒，最后一个任务处理 50 GB 热点用户，需要 10 分钟。作业阶段完成时间由最慢任务决定，平均任务时间很漂亮也没用。需要在 Spark UI 看任务输入字节、Shuffle read、Spill、GC 时间、调度等待和失败重试。若最后任务输入远大于其他任务，这是键分布倾斜；若所有任务都读约 1 GB 但都 Spill 严重，是普遍内存或分区大小问题；若输入和 Spill 都正常却等很久，则看资源队列、远端拉取和上游慢节点。

倾斜治理要先确认热点键来源。空值被统一填成一个默认用户 ID，可能让所有缺失键落到同一分区；少数超级用户也可能天然有大量记录。对热点做随机加盐可分散第一阶段聚合，但最后仍需按原键合并局部结果，且只适合可分解聚合。JOIN 的加盐还需考虑另一侧数据复制，不能直接照搬聚合公式。

分区数、并行度与 AQE

`spark.sql.shuffle.partitions` 常用于设置 SQL Shuffle 的初始分区数，但它不是所有作业的唯一并行度旋钮。Adaptive Query Execution 可以根据运行时统计合并过小分区、处理部分倾斜 JOIN 等，具体功能和条件依 Spark 版本及配置。合理做法是先看执行计划与数据规模，设一个不过小的初始粒度，再从 UI 检查 AQE 实际生成的分区大小和任务数量。

增加分区数能降低一般分区平均大小，但同一个热点键默认仍被哈希到同一分区；因此“把 200 改成 2000”未必能解决单个超级键。相反，若 2000 个任务每个只处理几 KB，调度与网络连接成本可能吞掉收益。观察数据分布分位数比只看平均值更可靠。

Spill 是线索，不是单独结论

Spark 在内存不足以容纳当前排序、聚合或哈希结构时，会把部分中间数据写磁盘。适量 Spill 可能是算法的正常保护，持续巨量 Spill 通常意味着内存压力、任务输入太大或算子策略不匹配。要同时看 Spill bytes、GC、执行器磁盘 IO、任务失败和峰值堆外内存。若所有节点都在 Spill，先考虑缩小单任务输入、优化聚合与投影、提高可用内存；若只有一个任务 Spill，先查倾斜。

缓存无关中间表或盲目提高 executor memory 会增加资源占用，可能使并发作业更慢。对于 JOIN，还应检查是否可以广播足够小的一侧、是否有过滤条件提前下推，以及两侧键类型是否一致。类型转换或表达式可能阻碍正常的连接策略。

一个可复现诊断流程

固定输入数据与 Spark 版本，记录作业计划。先运行 20 分区，再运行 200 分区，比较每任务 Shuffle read 中位数、P95、最大值与 Spill。若 200 分区下多数任务变快，最大值仍极高，抽样统计热点键频率并在 Spark UI 定位长尾任务。若所有任务的处理数据相近，增加分区或优化内存更有依据。最后在同一机器资源配额下比较总耗时、成本与输出行数，避免性能优化改变聚合结果。

练习：200 GB 数据分成 200 个 Shuffle 分区，理论均值约 1 GB，但最大任务读 45 GB，其余任务不到 1 GB。你会先加内存还是先查键频率？说明理由，并给出一个可验证的实验。

不能只看总耗时

若写出阶段缓慢，可能是目标表分区过细、产生大量小文件，与上游 Shuffle 倾斜不同。跨阶段要分别看扫描、Shuffle、聚合、写出耗时。最终产物的文件数、大小和逻辑行数也要一起验收；作业从十分钟降到五分钟，却写出十万小文件，会把成本转移给后续查询。

自检

200 个分区中只有一个读 45 GB，把分区数改为 2000 就一定能消除长尾吗？

不一定。同一热点键仍可能哈希到同一分区；应先查键频率并选择适合的拆分策略。
