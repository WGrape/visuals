Go 的 timer/after 基于四叉堆管理；runtime 的 sysmon 后台线程负责网络轮询兜底、抢占、回收长时间阻塞的 M。对应左书 6.3 与 6.7。

Timer 与 Ticker

基于 channel 通知

time.After 返回只读 channel，到期发送；Ticker 周期性发送。底层都挂在 runtime 的定时器系统上。

select {
case <-time.After(2 * time.Second):
    fmt.Println("timeout")
case v := <-ch:
    fmt.Println("got", v)
}
时间堆管理

高效取最近到期

所有 timer 按「绝对到期时间」放在四叉堆里；netpoller 等待时按最近到期时间设超时，到点唤醒并触发到期 timer。

大量 time.After 若不被消费会泄漏（timer 持有引用直到触发）。长生命周期里优先用 time.NewTimer 并显式 Stop。
sysmon 系统监控

后台兜底线程

sysmon 不与任何 G 绑定，定期运行：触发网络轮询兜底、回收陷入系统调用的 M、对运行过久的 G 发起抢占、打印死锁等。

// runtime 伪循环
go func() {
  for {
    usleep()
    checkNetpoll()      // 兜底轮询
    preemptLongRunning()// 抢占长 G
    retakeSyscall()     // 回收阻塞 M
  }
}()
使用要点

避免泄漏

定时器用完要 Stop；Ticker 用完要 Stop 且 drain channel；sysmon 无需关心，但理解它有助于解释「为啥有时 goroutine 被强占」。

⚠️ time.After 在 select 中每次调用都新建 timer，长循环里请用 NewTimer 复用，否则产生大量短命 timer。

Go 定时器是怎么组织的

成千上万个定时器如果每次都排序扫描，成本不可接受。Go 用四叉小顶堆按触发时间组织定时器，并把堆分摊到各个 P 上以降低锁竞争。

四叉小顶堆：插入删除 O(log N)，取最近到期 O(1)
小顶堆按到期时间排序，堆顶即下一个要触发的定时器。
按 P 分片定时器分摊到各 P，减少全局锁竞争。
四叉每层 4 个子节点，缓存局部性优于二叉。
到期处理到期后唤醒等待的 goroutine 或发送 channel。

Sleep / After / Ticker 的差异与陷阱

API语义要不要手动释放典型坑
time.Sleep(d)挂起当前 goroutine d 时长不需要阻塞 goroutine，循环中滥用会拖慢退出
time.After(d)返回 channel，d 后收到一个值一次性，用完即弃放进 for-select 循环会每次新建定时器
time.NewTimer(d)可复用的 Timer，支持 Stop/Reset需要 StopReset 前必须排空已有值
time.NewTicker(d)周期性触发，直到 Stop必须 Stop忘记 Stop 会永久泄漏
time.AfterFunc(d, f)到期后在新 goroutine 执行 f需要 Stop闭包捕获大对象会延长生命周期
context.WithTimeout带取消语义的超时需要 cancel忘记 cancel 会泄漏上下文与子 goroutine
// 反例：每轮循环都新建一个 Timer，堆积到超时才回收 for { select { case v := <-ch: handle(v) case <-time.After(time.Second): // 每轮一个新定时器 return } } // 正例：复用一个 Ticker，并在退出时 Stop ticker := time.NewTicker(time.Second) defer ticker.Stop() for { select { case v := <-ch: handle(v) case <-ticker.C: return } } // Timer.Reset 的正确姿势：先 Stop 并排空 if !t.Stop() { select { case <-t.C: default: } } t.Reset(d)

sysmon：运行时自带的后台巡检线程

sysmon 是一个不绑定 P 的特殊线程，周期性地做几件「没人主动做就会出问题」的事。

抢占长时间占用 P 的 goroutine（超过约 10ms）会被标记并抢占
网络轮询在没有 M 轮询 netpoller 时接管，避免事件饿死
强制 GC距上次 GC 超过约 2 分钟则触发一次，防止长期不回收
归还内存清扫后把长时间空闲的内存页逐步还给操作系统
调度兜底发现可运行 G 长时间没被调度时，尝试唤醒或新建 M
不参与 GCsysmon 自身不持有 P，也不被 GC 扫描栈

对使用者意味着什么：Go 在 1.14 之后引入了异步抢占，纯计算型的死循环不再能把整个 P 卡死。但这不意味着可以写无退出条件的循环——它只是让调度更公平。

深入自检

time.After 在循环里到底有什么问题？

每次调用都创建一个新定时器。在高频循环里，这些定时器到期之前不会被回收，会同时堆积成千上万个，占用内存并拖慢定时器堆的操作。改成循环外创建 Ticker 并 defer Stop 即可。

Go 1.23 之后 time.After 还需要担心吗？

Go 1.23 对定时器做了改进，未被引用的定时器可以更早被回收，channel 也改为非缓冲。这确实缓解了旧问题，但在循环里创建一次性定时器仍是浪费——用 Ticker 表达「周期性」语义也更清晰。

Timer.Reset 为什么容易出错？

因为 Stop 返回 false 时，channel 里可能还有一个已发送但未被接收的值。若不排空就 Reset，下一次 select 会立刻读到这个旧值，导致逻辑误判。正确做法是先 Stop，再用非阻塞 select 排空，最后 Reset。

sysmon 会让我的程序变慢吗？

基本不会。它是一个轻量后台线程，按周期休眠与巡检，只在发现异常（长时间占用、需要 GC、内存长期空闲）时才做实际工作。它带来的好处（公平调度、及时回收）远大于开销。

为什么有时候定时器不准时？

定时器保证的是「不早于」而非「恰好在」。到期后 goroutine 需要重新排队等待 P 执行，如果当时 CPU 饱和或 GOMAXPROCS 太小，实际触发会延后。对时间精度敏感的场景不要依赖 Go 定时器做硬实时控制。

Timer / Ticker 的正确用法与经典泄漏

Timer 用法

// ❌ 经典泄漏：for-select 里用 time.After
for {
    select {
    case v := <-ch:
        handle(v)
    case <-time.After(time.Second):   // 每次循环都新建一个 Timer
        timeout()                      // 旧 Timer 要到期才会被回收 -> 高频循环下大量堆积
    }
}

// ✅ 正确：复用一个 Timer，用完 Reset
timer := time.NewTimer(time.Second)
defer timer.Stop()
for {
    timer.Reset(time.Second)           // Go 1.23+ 无需先 drain
    select {
    case v := <-ch:
        handle(v)
        if !timer.Stop() {             // Go 1.22 及以前：Stop 后必须排空 channel
            <-timer.C                  // 否则 Reset 时可能有残留事件
        }
    case <-timer.C:
        timeout()
    }
}

// Ticker 一定要 Stop，否则泄漏
ticker := time.NewTicker(time.Second)
defer ticker.Stop()

// 只要“一段时间之后”，不要 Timer
select {
case <-time.After(3 * time.Second):
case <-ctx.Done():          // 配合 context 取消
}
API用途坑
time.NewTimer(d)一次性定时器，可 Stop/Reset不 Stop 也不会立即泄漏（到期自动回收），但重复创建仍会堆积
time.After(d)语法糖，等于 NewTimer + 取 C循环里用是经典泄漏点
time.NewTicker(d)周期触发必须 Stop，否则永久泄漏
time.Tick(d)语法糖无法 Stop，只在确定常驻的场景用
timer.Reset(d)重置Go 1.23 前需先 Stop 并排空 C，否则可能收到旧事件
time.Sleep(d)阻塞当前 goroutine不可取消；要可取消请用 Timer + context

精度：Go 定时器不保证精确，实际触发时间 = 目标时间 + 调度延迟。通常误差在毫秒级，但在 GC STW、调度拥塞或系统负载高时会显著变大。不要用定时器做硬实时控制，也不要假设 "100ms 后一定执行"。

底层实现与 sysmon

版本实现性能特征
Go ≤ 1.22全局最小四叉堆，由单个 timer goroutine / netpoller 驱动增删 O(log n)；大量定时器时锁竞争明显
Go 1.23+每个 P 各自维护 timer 堆，与 netpoller 深度整合并发创建/删除定时器大幅降低锁竞争，海量定时器场景提升明显
  • sysmon（系统监控线程）：runtime 里的后台线程，不绑定 P，负责抢占长时间运行的 goroutine、触发 netpoll、回收空闲 M/P。
  • 它的检查间隔是动态的：从 20μs 起，逐步退避到 10ms。所以「抢占慢 goroutine」不是瞬时的。
  • 异步抢占（Go 1.14+）：解决「无函数调用的死循环无法被抢占」的问题。在此之前，一个不含函数调用的 for 循环可以让整个 P 卡死。
  • GC 相关：sysmon 还负责在长时间没有 GC 时触发强制 GC（两分钟阈值）。

怎么判断定时器泄漏了？

看 goroutine 数量是否随时间单调增长且不回落。pprof 的 goroutine profile 里如果看到大量停在 time.Sleep / select 的 goroutine，基本就是 Timer/Ticker 没 Stop。

为什么 Timer Stop 返回 false？

表示定时器已经到期或被停止过一次。Go 1.22 及以前，此时 channel 里可能还有未取出的事件，必须先 drain 再 Reset，否则下次会立刻收到一个虚假事件。

定时器和 Sleep 怎么选？

需要取消 / 需要和其他 channel 竞争 → Timer；单纯阻塞等待 → Sleep；周期任务 → Ticker（记得 Stop）。
