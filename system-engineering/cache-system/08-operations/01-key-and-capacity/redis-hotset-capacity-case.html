先建立直觉：给仓库定面积

要租多大的仓库？你得知道：要放多少件货（key 数量）、每件多大（单条大小）、以后还会增加多少（增长趋势）。拍脑袋定面积，要么浪费钱，要么装不下。

Redis 容量规划同理，而且装不下的代价更严重——内存满了会触发淘汰，命中率下降，甚至写失败。

容量估算三步

① 确定要缓存什么（热点集合）

不是所有数据都该进缓存。用 访问频次 × 数据量 筛选：

数据类型是否缓存理由
高频访问的热门商品✅ 是收益最大
低频访问的长尾商品❌ 否缓存了也没人读，白占内存
几乎不变的配置/字典✅ 是（长 TTL）命中率极高
频繁变化的状态⚠️ 谨慎一致性成本高
超大对象（几百 KB 以上）❌ 否（或拆分）单个就阻塞网络与线程
识别方法：分析访问日志统计 top N 热点；或开 redis-cli --hotkeys（需 LFU 策略）；或在客户端埋点上报。不要凭直觉猜热点——实际热点往往和想象不同。

② 计算单条大小

# 实测单个 key 的内存占用
MEMORY USAGE user:10086
# 批量评估：抽样若干 key 求平均
redis-cli --bigkeys    # 顺便找出大 key
别忘了 Redis 自身的开销。实际占用 = key 字符串 + value 序列化后大小 + 结构体/字典/过期表等元数据开销（通常每条几十到上百字节）。所以实测永远比理论计算准——用 MEMORY USAGE 抽样。

③ 推算总量与增长

总内存 ≈ 热点 key 数量 × 平均单条大小 × (1 + 冗余系数)

例：
  热点商品           100 万条
  平均单条实测        约 800 字节（含 Redis 元数据）
  小计               ≈ 800 MB
  副本（主从）        × 2  → 1.6 GB
  碎片与冗余          × 1.3 → 约 2.1 GB
  未来 6 个月增长     × 1.5 → 约 3.2 GB
  ⇒ 建议按 4 GB 规划（再留安全水位）

安全水位与告警

为什么不能用到 100%？① 内存接近上限会频繁触发淘汰，命中率下降、延迟上升；② 主从同步、RDB fork、AOF 重写都需要额外的临时内存，满了会失败；③ 突发流量可能瞬间写满，来不及反应。建议常态水位控制在 70% 以下。

常见的容量失控原因

原因现象处理
无 TTL 的 key 堆积内存只增不减给所有 key 设 TTL；扫描无 TTL 的 key
大 key少数 key 占大头--bigkeys 找出并拆分
过期数据未回收已过期但仍占内存检查惰性删除是否被触发
内存碎片used_memory_rss 远大于 used_memory关注 mem_fragmentation_ratio，必要时重启整理
业务增长未预估缓慢逼近上限监控日增量，提前规划

规划清单

  1. 用访问日志识别真正的热点集合，而不是全量缓存；
  2. 用 MEMORY USAGE 实测单条大小（别用理论值）；
  3. 套公式算总量，乘上副本、碎片、增长三个系数；
  4. 设置 maxmemory 与合适的淘汰策略（通常 allkeys-lru）；
  5. 配置水位告警（70% / 85% / 90% 三级）；
  6. 监控日增量，每月回顾一次容量规划。

🎯 面试问答

Q：估算容量时最容易忽略什么？
A：最容易忽略三件事：① Redis 自身元数据开销——每条 key 除了 value 还有结构体、字典、过期表等开销，通常几十到上百字节，小 value 场景占比很高；② 内存碎片——used_memory_rss 往往明显大于 used_memory；③ 主从副本——每个从节点都要一份完整内存。所以实测（MEMORY USAGE 抽样）永远比理论计算可靠，并记得乘上冗余系数。

Q：内存使用率到多少需要扩容？
A：70% 就该开始评估，85% 必须立即处理。原因是：内存接近上限会频繁触发淘汰，导致命中率下降、延迟上升；而且主从全量同步、RDB fork、AOF 重写都需要额外临时内存，满了会直接失败。建议常态水位控制在 70% 以下，给突发流量和运维操作留足余量。

Q：maxmemory 应该设成多少？
A：设为实例可用内存的 70%~80%，而不是 100%。必须给 Redis 之外的开销留出空间：RDB fork 时的 copy-on-write、AOF 缓冲区、主从同步缓冲区、客户端输出缓冲区等，这些都可能额外占用可观内存。如果设为 100%，这些场景很容易导致 OOM 被系统 kill。同时要配套设置 maxmemory-policy（通常 allkeys-lru）。

Q：内存一直涨但不淘汰，怎么回事？
A：先查三件事：① 有没有 key 没设 TTL——用脚本扫描 TTL = -1 的 key，这是最常见原因；② 有没有大 key——redis-cli --bigkeys 查；③ 过期数据是否真的被回收——看 expired_keys 指标是否在增长，如果数据明明过期但这个计数不涨，说明惰性删除没被触发（这些 key 过期后再没人访问）。另外检查 mem_fragmentation_ratio，碎片过高也会表现为「内存降不下来」。
