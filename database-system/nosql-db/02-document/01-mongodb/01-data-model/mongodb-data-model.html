🧱 MongoDB 数据模型设计

嵌入 vs 引用、一对多、多对多、分桶与反范式化的取舍

核心命题：一次查询想拿什么，就怎么放

关系建模的出发点是「消除冗余」（范式化）；文档建模的出发点是减少查询往返（反范式化）。因为 MongoDB 单文档写入是原子的、单文档读取是一次 IO，所以把相关数据放进同一个文档往往又快又安全。代价是冗余——同一份数据在多个文档里各存一份。

嵌入 Embed子文档/数组直接放进父文档，一次读全
引用 Reference只存 _id，需要时再查（或 $lookup）
分桶 Bucket把时间序列按时间窗聚成一条文档
反范式 Denormalize把常读字段复制一份，避免二次查询

决策树：嵌入还是引用？

四种经典关系怎么建

① 一对一（1 : 1）

优先嵌入。除非子对象很大且很少访问，才拆成两个集合。

// 嵌入：用户 + 身份证信息（总是带着读）
{
  _id: ObjectId("..."),
  name: "Alice",
  idCard: { no: "3301...", issueDate: ISODate("2020-01-01") }
}

② 一对少（1 : Few，且数量有界）

嵌入数组。典型：一篇文章的地址、一个订单的若干商品行。

{
  _id: "order_1001",
  user: "u_9",
  items: [                       // 商品行嵌入，几十条以内
    { sku: "A1", qty: 2, price: 39.9 },
    { sku: "B7", qty: 1, price: 128 }
  ],
  total: 207.8,
  status: "paid"
}

③ 一对多（1 : Many，无上限）

在「多」的一侧存「一」的 _id（子引用）。典型：用户与订单、作者与文章。

// posts 集合：每条帖子记作者 id
{ _id: "p_1", authorId: "u_9", title: "..." }
// 查某作者最近 10 篇（authorId 建索引）
db.posts.find({ authorId: "u_9" }).sort({ createdAt: -1 }).limit(10)

④ 多对多（N : N）

双向数组互存 id，或只在一侧存（取决于哪边查询多）。典型：学生 ↔ 课程。

// 学生侧存课程 id（查询高频侧）
{ _id: "s_1", name: "Bob", courseIds: ["c_1","c_3"] }
// 课程侧存学生 id（若也要反查）
{ _id: "c_1", title: "DB", studentIds: ["s_1","s_2"] }
// 两边都要改 → 用事务，或只存一侧 + 反查索引
⚠️ 数组互存要注意数组无界增长：一门课 10 万学生，studentIds 就撑爆 16MB。这种「超级节点」要反过来用「多侧存 id」的单向引用。

分桶模式：对付时间序列

物联网/监控场景每秒产生一条数据，如果一条文档存一个点，索引会爆炸。分桶把一个时间窗内的 N 个点合并进一个文档。

// 一个传感器、一小时一个桶、桶内 3600 秒采样
{
  sensorId: "s_01",
  bucketStart: ISODate("2026-01-01T10:00:00Z"),
  samples: [ { t: 0, v: 21.3 }, { t: 1, v: 21.5 }, ... ],
  count: 3600,
  sum: 76543.2, avg: 21.26, max: 25.1, min: 18.9   // 预聚合
}

效果：文档数从 3600 降到 1，索引条目同步减少；预聚合字段让「求小时均值」直接读现成值。MongoDB 5.0 的时序集合就是把这个模式内置了。

反范式化的代价与补救

反范式做法换来什么代价
把商品名/价格复制进订单行查订单不 join 商品表商品改名后历史订单仍显示旧名（通常这正是想要的）
把作者昵称复制进文章列表页一次查出改昵称要批量刷文章
预聚合计数（评论数、点赞数）列表页免 count写入时要用 $inc 同步维护
嵌入最新 N 条子记录详情页免二次查写入要同时维护两侧
💡 经验法则：读 : 写 > 10 : 1 就大胆反范式化；读写比例接近 1:1 时，冗余维护成本会超过收益，改用引用。

用 JSON Schema 锁住关键字段

db.createCollection("users", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["name", "email"],
      properties: {
        name:  { bsonType: "string", minLength: 1 },
        email: { bsonType: "string", pattern: "^.+@.+$" },
        age:   { bsonType: "int", minimum: 0, maximum: 150 }
      }
    }
  },
  validationLevel: "strict",     // strict | moderate
  validationAction: "error"      // error | warn
});

建模检查清单

  • ✓ 列出所有高频查询（按频次排序），逐条确认能在 1 次查询内完成
  • ✓ 每个嵌入数组都要问：它会不会无限增长？
  • ✓ 预估单文档大小，远离 16MB 上限
  • ✓ 为每个查询模式配一个能命中它的索引（见索引篇）
  • ✓ 字段命名统一（camelCase），避免 userName 与 user_name 混用
  • ✓ 反范式字段明确记录「谁负责维护」，最好在写入路径里用 $inc/$set 一起改

🎯 常见问法与答题要点

Q：嵌入和引用的判断标准到底是什么？

A：三个问题按顺序问：①子数据会不会脱离父文档单独被查？会→引用。②数组会不会无限增长？会→引用或分桶。③两者是否总是一起更新、一起读？是→嵌入。经典例子：订单的收货地址（嵌入）、用户的订单列表（引用）、文章的评论（嵌最新 10 条 + 引用全集）。

Q：为什么 MongoDB 不推荐无限增长的数组？

A：三条硬伤：①16MB 文档上限；②数组变大后，push 需要重写整个文档（WiredTiger 是整体重写），写放大严重；③数组上的多键索引条目数 = 数组长度，索引会跟着膨胀，维护成本线性上升。

Q：多对多关系怎么存最稳？

A：看哪边查询多。通常只在查询高频的一侧存 id 数组，另一侧靠该字段的索引反查（给数组字段建索引后，{courseIds: "c_1"} 能走索引）。只有两侧都要极高频反查时才双向冗余，然后用事务或异步任务保证一致。

Q：分桶模式怎么选桶大小？

A：权衡「桶太大读多余数据」和「桶太小索引爆炸」。经验值：让每个桶文档控制在 几十 KB 以内、样本数几百到几千。常见是按「每小时一桶」或「每 1000 条一桶」。如果查询大多是按时间范围扫描，桶大一点更省；如果大多是点查某个时刻，桶小一点更准。

Q：反范式化后数据不一致怎么办？

A：三种策略：①写入路径同步维护（同一个事务/update 里 $set 冗余字段），最常用；②异步对账（定时任务扫描修正），适合容忍短暂不一致；③干脆不冗余，接受二次查询。千万别「想起来才更新」。

Q：MongoDB 有外键约束吗？

A：没有。引用完整性完全靠应用层保证。删除主文档时，引用它的子文档会变成悬空引用。生产上要么在应用层做级联删除（放事务里），要么设计时避免强依赖（软删除 + 定期清理）。
