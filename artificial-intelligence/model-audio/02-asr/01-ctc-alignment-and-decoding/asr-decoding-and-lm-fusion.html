声学模型只输出「每一帧像什么音」，要变成一句通顺的话，还需要解码与语言模型。融合位置决定了准确率与延迟的平衡，也是实际落地时最需要调的部分。

01解码要解决什么：从帧概率到句子

  • 声学模型逐帧输出概率，帧数远多于字符数 —— 中间存在对齐问题
  • CTC 的做法：允许输出空白与重复，最后折叠成文本，天然处理对齐
  • 注意力解码的做法：解码时自己去找该看哪一帧，不需要预先对齐
  • 束搜索（beam search）是在这两者之上做近似最优路径搜索
方式怎么处理对齐能否流式特点
CTC用空白符与折叠隐式对齐适合结构简单、流式友好，但独立性假设较强
Attention（AED）解码时软对齐不太适合准确率好，但要等整段说完
RNN-T联合网络逐步输出适合流式与准确率兼顾，实现最复杂
CTC + Attention 混合两者加权可配置训练更稳，推理可切换
要点：选型的第一问是「要不要流式」。要实时上屏就必须用 CTC 或 RNN-T；能等说完再出结果时，AED 类通常更准。

02三种语言模型融合方式

方式融合时机延迟准确率实现成本
浅融合 Shallow Fusion解码每一步就加 LM 分低中低，最常用
二次打分 Rescoring先出 N-best 再重排中较高中，需保留 N-best
联合训练 Joint训练阶段就融合低高高，要重新训练
  • 浅融合是默认起点：不改训练流程，加一个 LM 就能提升准确率
  • 二次打分适合离线转写这种不强求实时的场景，可以把大模型放在后面慢慢排
  • 联合训练效果最好，但需要重新训练，且 LM 更新时要重来一遍
  • 热词（hotword）通常做成上下文偏置：在解码时给指定词加分，不改模型
要点：浅融合的融合权重是与解码器耦合的，换 LM 后必须重新调，否则会出现「识别结果很通顺但不是用户说的」这种情况。

03三个必调参数与默认值量级

参数常见取值调大的效果调大的代价
beam_size（束宽）5 ~ 20准确率提升计算量线性增长，边际收益递减
lm_weight（LM 权重）0.2 ~ 0.6更通顺、专名更好容易把错的音纠正成通顺的错句
热词偏置权重3 ~ 10热词识别率明显提升非热词被误纠成热词
CTC blank 阈值与 beam 配合影响结束判断过于灵敏会提前截断
# 典型解码配置（以常见的 CTC 前缀束搜索为例）
decoder = CtcPrefixBeamSearch(
    beam_size=10,        # 束宽：5 够快，20 提升有限但明显变慢
    lm_weight=0.35,      # 语言模型权重，调大更顺但更容易事后圆场
    hotword_weight=6.0,  # 热词偏置，针对人名地名等专名
)

# 热词列表：单独维护，不要写进模型
hotwords = ['张三', '产品名A', '地名B']

# 流式场景要控制 chunk：太小影响准确率，太大增加延迟
# 常见取舍：chunk 0.4~1.0 秒，首字延迟与准确率的分界线
CHUNK_MS = 640
要点：调参顺序建议：先定束宽，再调 LM 权重，最后加热词。反过来调会互相干扰，因为热词偏置会掩盖 LM 权重的问题。

04排障顺序与常见坑

  1. 先判断是声学问题还是语言问题：把声学模型输出不接 LM 直接解码，如果这时就错，问题在声学侧
  2. 识别结果「很通顺但和原话不一致」→ LM 权重过大，调小
  3. 专名、人名总是识别成同音常用词 → 加热词偏置，或加领域 LM
  4. 流式场景延迟高 → 先看 chunk 大小，再看束宽，最后才考虑换模型
症状原因处理
结果通顺但内容错LM 权重过大调小 lm_weight
专名识别差缺领域 LM 或热词加上下文偏置
流式延迟高chunk 太大或束宽过大减小 chunk 到 0.4~0.6 秒
尾部丢字结束判断过早调整结束静音时长
数字识别差文本的 LN（逆归一化）缺失在后处理里把 一二三 转回 123
要点：容易被忽略的一步：识别出来还要做逆归一化（ITN），把「二零二六年」转回「2026 年」。只做 ASR 不做 ITN，下游拿到的是没法直接用的文本。

第一层 · 概念与判定：解码在干什么

ASR 模型输出的是每帧对各个 token 的概率（声学得分），解码就是把这些概率搜出最可能的中文序列。由于同音字极多，仅靠声学模型会大量混淆（「常识」vs「常时」），必须引入语言模型（LM）提供语言通顺度打分来消歧。

解码类型特点何时用
贪心解码每帧取最大概率基线、不实用
Beam Search保留 top-k 候选最常用
CTC 前缀束搜处理 blank 与重复CTC 模型必用
WFST 解码声学+LM 编译成图传统 Kaldi 方案

一句话判定：只要追求准确率，就要在解码阶段把 LM 融合进去，纯声学 beam 是不够的。

第二层 · 参数·命令·量化：融合方式与权重

融合方式做法参数取舍
Shallow Fusionbeam 阶段声学+LM 概率相加lm_weight 0.1~0.3简单，最常用
Deep FusionLM 隐状态拼进解码网络需联合训练效果好但复杂
Cold Fusion预训练 LM 仅推理提供特征LM 冻结省算力
无 LM只用声学——流式低延迟场景

Shallow Fusion 解码核心代码

# PyTorch 用 torchaudio 做带 LM shallow fusion 的解码（示意）
# 声学得分 logp_acoustic 来自 encoder+decoder
# 语言得分 logp_lm 来自 n-gram 或神经 LM
lm_weight = 0.2
for cand in beam:
    score = cand.acoustic_score + lm_weight * cand.lm_score
    # 加长度惩罚，避免极短候选占优
    score /= len(cand.tokens) ** 0.2
beam = sorted(beam, key=lambda c: score, reverse=True)[:beam_size]

# 关键超参
beam_size   = 10      # 太小漏解，太大慢
lm_weight   = 0.2     # 太大变「念稿」，太小同音混淆
temperature = 1.0     # 流式常调低以加速

数量级：beam_size 从 5 提到 20，WER 通常还能降 0.3~0.8 个点但延迟近似线性上升；lm_weight 超过 0.4 后往往「念稿感」明显、口语词被压掉。

第三层 · 排障与边界：高频坑

融合翻车清单：

  • LM 过强：lm_weight 太大，常见口语（「那个」「然后」）被压掉，听感像念稿、像播音
  • OOV 惩罚：LM 词表没覆盖的领域词，会被强行换成常见词，专有名词必错
  • beam 太小：同音候选被早早砍掉，长句尾部错误骤增
  • 流式/离线不一致：流式用 chunk 解码、LM 只能看已出词，离线能看全句，二者 WER 差几个点
  • 标点缺失：解码出纯文本无标点，下游要另接标点模型（ITN 阶段）
  • 热词不生效：只改 bias 不改 LM，热词在 beam 里分数仍不够

诊断顺序：① 先看 WER 的 Sub/Del/Ins 分布，Ins 多说明 LM 在乱补词；② 抽错误样本，区分是声学混淆还是 LM 选错；③ 调 lm_weight 做扫描，找 WER 最低点而不是拍脑袋。

第四层 · 原理与取舍

既然端到端模型很强，为什么还要外部 LM？

端到端（如 Conformer/Whisper）已隐含语言知识，但领域适配慢、长尾词弱。外部 LM 能零训练地注入最新领域语料、热词、专有名词表，成本远低于重新微调大模型。所以工业界仍普遍保留 LM 融合作为低成本适配手段。

神经 LM 一定比 n-gram 好吗？

长上下文更准，但推理慢、易过平滑、流式难用。n-gram 快、可控、易做折扣与裁剪，流式场景反而更稳。常见折中：用 n-gram 做 shallow fusion 保速度，神经 LM 只在离线转写时用。

为什么流式场景常常关掉 LM？

流式要低延迟，LM 每出一个 token 就要查一次、还要看历史，会显著增加首字延迟（FA）和尾字延迟（FL）。所以流式常只用轻量声学 beam，把语言通顺度交给后处理或离线二次解码。
