WAL 预写日志

Write-Ahead Logging 原理、checkpoint，以及它如何支撑崩溃恢复与复制。

① WAL 是什么：先记账，再落盘② LSN、段文件与目录结构③ Checkpoint：把「账」并入「库」④ 归档、PITR 与备份体系⑤ 逻辑复制与复制槽⑥ 常见问法

① WAL 是什么：先记账，再落盘

WAL（Write-Ahead Log，预写日志）的核心规则只有一条：修改数据页之前，必须先把描述这次修改的日志记录持久化。这样即使崩溃，也能用日志把数据库恢复到一致状态。

为什么这样能提速？数据页的修改是随机写（散落在文件各处），而 WAL 是顺序追加写。把「每次提交都要随机刷页」换成「顺序写日志 + 后台批量刷页」，吞吐提升一个数量级。

② LSN、段文件与目录结构

LSN（Log Sequence Number）是 WAL 中的字节偏移量，单调递增，用来标识「日志写到哪了」。WAL 文件存放在 pg_wal（10 之前叫 pg_xlog）目录，每个段文件默认 16MB，文件名是 24 位十六进制（时间线 + 逻辑编号）。

-- 当前 WAL 写入位置与 LSN 差
SELECT pg_current_wal_lsn(), pg_walfile_name(pg_current_wal_lsn());

-- 主从复制延迟（字节）
SELECT pg_current_wal_lsn() - pg_last_wal_replay_lsn() AS lag_bytes;

-- 查看 WAL 相关配置
SELECT name, setting, unit FROM pg_settings
WHERE name IN ('wal_level','wal_segment_size','min_wal_size','max_wal_size',
               'wal_keep_size','wal_compression','checkpoint_timeout','max_wal_senders');
参数作用常见取值
wal_level日志记录的详细程度replica（支持流复制）／logical（支持逻辑复制）
max_wal_size自动检查点触发的软上限1GB~8GB，视写入量
checkpoint_timeout检查点最大间隔5min（高写入可 15~30min）
wal_compression压缩 WAL 记录高写入时开 on 可显著省空间
wal_keep_size为备库保留的最小 WAL配合复制槽使用
synchronous_commit提交是否等待 WAL 落盘on（安全）／off（快，丢少量）

③ Checkpoint：把「账」并入「库」

检查点是这样一个时刻：所有脏页都已刷盘，且 WAL 中记录了一个 checkpoint 记录。此后崩溃恢复只需从该点重放 WAL，而不必从头开始。

触发条件

checkpoint_timeout 到期、WAL 量超过 max_wal_size、手动 CHECKPOINT、创建基础备份、干净关闭

代价

检查点会引发大量脏页刷盘，造成 IO 尖峰与延迟抖动——这就是「checkpoint 抖动」

调优

调大 checkpoint_timeout、调大 max_wal_size、调小 checkpoint_completion_target 的反面（设为 0.9 让刷页更平滑）

full_page_writes

检查点后首次修改某页时整页写入 WAL，防止部分写（torn page）；代价是 WAL 变大

高写入库的典型坑：频繁检查点 + full_page_writes 会让 WAL 量成倍放大（可能达到实际数据变更的 3~5 倍）。表现为磁盘很快写满、复制延迟增大。对策：拉长检查点间隔、开启 wal_compression、使用支持原子写的存储/文件系统时可考虑关闭 full_page_writes（需谨慎）。

④ 归档、PITR 与备份体系

WAL 段文件会被循环复用；若要做时间点恢复（PITR），必须把 WAL 归档到别处。

# postgresql.conf
wal_level = replica
archive_mode = on
archive_command = 'test ! -f /archive/%f && cp %p /archive/%f'
# %p = 源文件路径，%f = 文件名

# 基础备份
pg_basebackup -D /backup/base -Ft -z -P

# 恢复：准备 recovery.signal + 目标时间
restore_command = 'cp /archive/%f %p'
recovery_target_time = '2026-10-20 14:30:00'
方案RPO特点
pg_dump 逻辑备份备份点可跨版本、可单表恢复；大库慢
pg_basebackup + WAL 归档秒级PITR 的标配；需归档存储
流复制备库近 0（同步模式）高可用首选；不能防误删（会同步）
延迟备库—recovery_min_apply_delay，用于救回误操作
关键提醒：归档命令失败会无限重试并让 pg_wal 堆积，最终磁盘写满导致数据库宕机。务必监控 pg_wal 目录大小与 pg_stat_archiver 的 failed_count。

⑤ 逻辑复制与复制槽

PostgreSQL 10+ 内置逻辑复制：以「表」为单位、按行级变更同步，可跨大版本、可只同步部分表，常用于升级迁移、数据分发、数仓同步。

-- 发布端
CREATE PUBLICATION pub_orders FOR TABLE orders, order_items;

-- 订阅端
CREATE SUBSCRIPTION sub_orders
  CONNECTION 'host=10.0.0.1 dbname=prod user=rep'
  PUBLICATION pub_orders;
复制槽（Replication Slot）是双刃剑：它保证主库不会删除备库还没消费的 WAL，避免备库掉线后需要重建；但如果备库永久下线而未删除槽，WAL 会无限堆积并撑爆磁盘。务必监控：SELECT slot_name, active, restart_lsn, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained FROM pg_replication_slots;

⑥ 常见问法

Q：WAL 为什么能保证崩溃后不丢数据？

A：因为提交时只有 WAL 落盘就返回成功，而 WAL 完整描述了这次修改。崩溃重启后 PostgreSQL 进入恢复流程：从最近的 checkpoint 开始重放（REDO）WAL，把已提交事务的修改补回数据页；未提交事务的修改则根据 clog 判断为无效（其数据页修改可能已落盘，但不会被认为可见）。核心法则「日志先于数据」（WAL 规则）确保了重放一定完备。

Q：synchronous_commit 各档位有什么区别？

A：on（默认）：提交等待本地 WAL fsync 完成，保证本机崩溃不丢；remote_apply：还要等备库应用完，最安全但最慢；remote_write：等备库写入（不必 fsync）；local：只等本地写入（不必 fsync，掉电可能丢）；off：不等 fsync，异步提交，最多丢几百毫秒数据但吞吐明显提升。选择原则：金融类用 on/remote_apply，日志类、可重放数据可用 off。

Q：WAL 突然暴涨，怎么排查？

A：按顺序查：① SELECT * FROM pg_stat_archiver; 看归档是否失败（失败会一直保留 WAL）；② SELECT * FROM pg_replication_slots; 看是否有非活跃槽长期保留大量 WAL；③ 检查是否有大批量写入/大事务（批量 UPDATE 会产生海量 WAL）；④ 检查 checkpoint_timeout 是否过小 + full_page_writes 造成的整页写入放大；⑤ 检查 wal_level 是否为 logical（记录量更大）。最常见的原因是「归档卡住」和「孤儿复制槽」。

Q：full_page_writes 为什么要存在？

A：因为页写入不是原子的：8KB 的页在断电时可能只写了一半（torn page），此时页内数据既非旧也非新，仅靠增量 WAL 无法修复。PG 的做法是在每个检查点之后首次修改某页时，把整页内容写入 WAL，恢复时直接用整页覆盖，从而免疫部分写。代价是检查点后的一段时间 WAL 量显著增大——这也是为什么要避免过于频繁的检查点。

Q：逻辑复制和物理流复制怎么选？

A：物理流复制：字节级同步整个实例，备库只读、版本必须一致、不能选表——适合高可用与读扩展；逻辑复制：按表订阅行级变更，可跨版本、可过滤、可双向——适合升级迁移、数据分发、异构同步、数仓接入，但不复制 DDL、不复制序列值、大事务延迟更高。常见组合是物理复制做 HA + 逻辑复制做数据分发。

Q：PITR 能恢复到任意时刻吗？有哪些限制？

A：能恢复到基础备份之后、最新可用 WAL 之前的任意时间点（recovery_target_time）或指定事务（recovery_target_xid）。限制：① 恢复是整实例级的，不能只恢复一张表（单表误删只能恢复到临时实例再导出）；② 必须有完整的基础备份 + 连续的 WAL 归档，中间断档则只能恢复到断档前；③ 恢复后时间线（timeline）会分叉，需要重新做基础备份。

第一层 · WAL 是什么、为什么必须有

WAL（Write-Ahead Log，预写日志）的规则只有一句话：修改数据页之前，必须先把描述这次修改的日志写到磁盘。这样崩溃重启时，重放日志就能把没来得及落盘的数据页补回来——即「ARIES 算法」的核心。

问题没有 WAL有 WAL
写入 1 行要写多少磁盘整页（8KB）随机写一条小记录顺序追加 + 后台批量刷页
崩溃后未刷盘的修改丢失（内存中的脏页没了）重放 WAL 恢复
随机写 vs 顺序写随机（页在哪写哪）顺序追加（磁盘顺序写比随机写快 1~2 个数量级）
fsync 频率每次提交要刷整页每次提交只刷一条 WAL 记录
  • 顺序写是 WAL 性能的根本来源：机械盘上随机写 ~100 IOPS，顺序写可到 ~100MB/s。把随机改成顺序，是数据库能扛住高写入的根本。
  • 提交时只保证 WAL 落盘，数据页可以慢慢刷。这就是「提交很快」的原因，也是「崩溃恢复需要时间」的原因。
  • WAL 不只用于崩溃恢复：物理流复制（主从）、逻辑复制（逻辑解码）、在线备份（pg_basebackup）、时间点恢复 PITR 全部建立在 WAL 之上。

运维命令

# —— 观察当前 WAL 位置与堆积 ——
SELECT pg_current_wal_lsn(), pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), '0/0'));
SELECT pg_current_wal_insert_lsn(), pg_current_wal_flush_lsn();   -- insert 与 flush 的差就是未落盘量

# 复制延迟（主库上执行，单位为字节）
SELECT client_addr, state, sent_lsn, write_lsn, flush_lsn, replay_lsn,
       pg_size_pretty(pg_wal_lsn_diff(sent_lsn, replay_lsn)) AS lag_bytes
FROM pg_stat_replication;

# 复制槽（最关键：不消费的槽会让 WAL 无限堆积）
SELECT slot_name, active, restart_lsn, confirmed_flush_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots ORDER BY retained DESC;

# —— WAL 目录体积 ——
du -sh $PGDATA/pg_wal        # 正常应接近 max_wal_size；远大于说明有槽/从库卡住

# —— 查看 WAL 内容（排查与学习利器）——
pg_waldump -p $PGDATA/pg_wal -s 0/1A2B3C4D -e 0/1A2B4FFF | head -40
#   rmgr: Heap     len: 54 ... desc: INSERT+INIT ...    <- 能看到每条记录的类型
pg_waldump -p $PGDATA/pg_wal -r Heap --stats=record     # 按记录类型统计

# —— 手动操作 ——
CHECKPOINT;                                        # 手动触发检查点
SELECT pg_switch_wal();                            # 切换 WAL 段（归档前常用）
SELECT pg_drop_replication_slot('slot_name');      # 删除不再使用的复制槽！

WAL 文件名是 24 位十六进制（如 000000010000000000000001）= 时间线(8) + 逻辑段号(16)。pg_waldump 直接读文件不需要启动数据库，排查崩溃原因时非常有用。

第三层 · 排障清单

  • pg_wal 目录暴涨、磁盘告警 → 90% 是复制槽不消费。执行上面的 pg_replication_slots 查询，看哪个槽 active = false 且 retained 巨大。处理：修好消费者，或确认无用后 pg_drop_replication_slot。这是 PG 最经典的磁盘事故。
  • 日志出现 checkpoints are occurring too frequently → max_wal_size 太小，checkpoint 被 WAL 量而非时间触发。调大 max_wal_size（如 4~8GB），并确认 checkpoint_completion_target ≥ 0.9。
  • 写入延迟周期性尖刺 → 大概率是 checkpoint 集中刷脏页。调大 checkpoint_timeout + max_wal_size，并下调 shared_buffers（大 shared_buffers 意味着 checkpoint 时要刷的脏页更多）。
  • 从库延迟持续增大 → 先看是发送慢（网络/主库 IO）还是回放慢（从库有长查询阻塞回放，或单线程回放跟不上）。PG 16 起支持并行回放。
  • 主库删除了从库还需要的 WAL（requested WAL segment ... has already been removed） → 从库掉队太久。解法三选一：设 wal_keep_size 留更多、开 复制槽（最稳妥，但要监控）、或配置 restore_command 让从库从归档拉。
  • wal_level 从 replica 改成 minimal 后复制全断 → 改 wal_level 需要重启，且 minimal 下不保留复制所需信息。改回来重启即可。
  • 归档卡住（archive_command 失败） → .ready 文件堆积在 pg_wal/archive_status/。WAL 段在归档成功前不会被回收，会撑爆磁盘。检查归档目标是否可达/权限/磁盘满。

第四层 · 原理与取舍

三个必须理解的机制：checkpoint 决定了恢复要多长时间，full_page_writes 决定了崩溃后页是否可信，WAL 段回收决定了磁盘会不会被撑爆。

  • Checkpoint：把内存中所有脏页刷到磁盘，并在 WAL 里记一条 checkpoint 记录。恢复时只需要从最后一个 checkpoint 开始重放，之前的 WAL 就可以删了。所以它同时决定了「恢复时间」和「WAL 保留量」——调大 checkpoint 间隔 = 恢复变慢但写入更平滑。这就是取舍。
  • full_page_writes（部分写问题）：数据页是 8KB，而磁盘原子写通常是 4KB（或 512B）。断电时可能出现页写了一半——前 4KB 是新的、后 4KB 是旧的，这个页彻底损坏，而 WAL 里的「增量」记录无法修复它。解法：checkpoint 之后第一次修改某页时，把整页写进 WAL（full page image）。恢复时先用整页覆盖，再应用增量。代价是 checkpoint 刚结束时 WAL 量会突然增大（这就是 checkpoint 后写放大的原因）。除非你的文件系统/存储能保证 8KB 原子写（如 ZFS、某些企业存储），否则绝对不要关。
  • WAL 段回收：WAL 以 16MB 的段文件循环使用。一段能被回收，必须同时满足：① 已被 checkpoint 覆盖（崩溃恢复不需要）；② 没有任何复制槽/从库的 restart_lsn 指向它；③ 若开了归档，归档已成功。三个条件任何一个不满足，WAL 就一直堆着——这就是磁盘爆掉的根因。
  • 逻辑解码：wal_level = logical 时 WAL 里会额外记录足够的信息，让 PG 能把物理变更翻译成行级事件（INSERT/UPDATE/DELETE 的前后镜像），供 Debezium 等 CDC 工具消费。代价是 WAL 体积增大（约 +20~50%）。
选择恢复时间写入平滑度WAL 占用
checkpoint 频繁（默认 5min / 1GB）短（几十秒）有明显周期性 IO 尖刺小
checkpoint 稀疏（30min / 16GB）长（几分钟~十几分钟）平滑大
开 wal_compression略长（要解压）更平滑（写盘量小）小 30~50%
关 full_page_writes—写放大消失大幅减小｜但有数据损坏风险
WAL 能不能只保留几天用于 PITR？

能，这就是时间点恢复（PITR）：一次基础备份（pg_basebackup）+ 连续的 WAL 归档 = 可以恢复到归档覆盖范围内的任意时刻。做法是设 archive_mode = on 和 archive_command（如拷贝到对象存储），恢复时用 recovery_target_time 指定目标时刻。关键点：基础备份必须周期性重做（否则要重放的 WAL 越来越长），常见策略是「每周一次全备 + WAL 连续归档，保留 7~30 天」。这是应对误删/逻辑错误的唯一手段——流复制不行，因为主库上的 DELETE 会立刻同步到从库。

为什么 checkpoint 后写入量会突然变大？

就是 full_page_writes 的效应。checkpoint 之后，每个第一次被修改的页都要把整页（8KB）写进 WAL，而不是只写几十字节的增量。所以 checkpoint 刚结束时 WAL 生成速率可能是平时的几倍到十几倍，持续到「热页都写过一次整页」为止。这也解释了一个反直觉的现象：把 checkpoint 调得太频繁，WAL 总量反而会爆炸——因为每次 checkpoint 都重置了 full page 的状态。所以调 checkpoint 要看「WAL 生成速率」而不只是「磁盘占用」。

同步复制（synchronous_commit）应该怎么配？

synchronous_commit 有五档：off（不等 WAL 落盘，最多丢几百毫秒）、local（等本地落盘）、remote_write（等从库收到写内存）、on（默认，等从库落盘）、remote_apply（等从库回放完）。严格的同步复制（on/remote_apply）能保证 RPO=0，但每次提交都要等一轮网络往返，吞吐可能掉一个数量级，且从库挂掉会让主库写阻塞。实践建议：普通业务用默认 on 配异步从库（RPO 是「网络延迟量级」）；真正要求零丢失的关键库用 synchronous_commit = on + 至少两个同步从库（用 synchronous_standby_names = ANY 1 (s1, s2)，这样挂一个不会整体阻塞）。
