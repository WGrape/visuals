路由表最长前缀匹配：数据包究竟走哪一跳

手算重叠路由、默认路由与回程路径，解释“能发出却收不到”的常见原因。

路由选择先看目的 IP

主机或路由器转发 IP 包时，先查目的 IP 是否命中某条路由前缀。多条都命中时，通常选择前缀最长、范围最具体的一条，而不是随意选择先写的那条。例如目标 10.2.3.9 同时匹配 10.0.0.0/8、10.2.0.0/16 和 10.2.3.0/24，应先使用 /24 的下一跳。0.0.0.0/0 是 IPv4 默认路由，只有没有更具体选择时才接住流量。

同一前缀长度的多条候选可能还要比较路由来源优先级、度量值或等价多路径配置；不同操作系统和路由协议细节不同。最长前缀规则说的是转发表匹配范围，不等于所有路由协议都以同一种方式学习或度量路径。排障时要看实际生效的转发表，而不只看配置文件。

路径图：10.2.3.9 的路由选择

箭头表示本例中的处理次序；每个环节的状态都要分别验证，不能由前一环节成功推断后一环节成功。

手算一张表

路由表有 10.0.0.0/8→网关 A，10.2.0.0/16→网关 B，10.2.3.0/24→网关 C，0.0.0.0/0→网关 D。目的 10.2.3.9 命中前三条，选 C；10.2.8.9 命中 /8 与 /16，选 B；10.9.1.1 只命中 /8，选 A；8.8.8.8 选 D。用二进制写出前缀可以检验边界：10.2.3.255 属于 /24，而 10.2.4.0 不属于。

如果 /24 下一跳 C 已失效，系统是否自动改走 /16 B，取决于 /24 路由是否被撤销。仅仅链路后端不可用而路由表仍保留 /24，可能持续把流量送进黑洞。链路探测、动态路由收敛与健康检查的配置决定故障时能否回退。

逐步推演

匹配前缀

用目的 IP 找出所有覆盖它的前缀。

选择最具体

先比较前缀长度，10.2.3.9 选 /24。

寻找下一跳

核对出口接口、网关与邻居 MAC。

验证回程

从对端再查到源地址的路由与策略。

转发还要解析下一跳

选中下一跳之后，路由器需要确定从哪个接口发出，并在以太网链路上找到下一跳 MAC。直连网段可直接解析目的主机；非直连网段解析的是网关。ARP 或 IPv6 邻居发现失败时，路由表看上去完全正确，包仍可能出不去。每转发一跳，IP TTL 或 IPv6 Hop Limit 递减，达到零时丢弃并可能返回 ICMP 差错。

路由表中“经网关 G”并不保证 G 自己有到最终目标的路由。沿途每台路由器都独立查表，因此 traceroute 才能逐跳观察路径。还要考虑防火墙、NAT 和策略路由可能改变实际路径，仅凭一次普通查表不能说明全部转发决策。

为什么回程同样重要

A 发往 B 的包可能经路由器 R1 顺利到达 B，但 B 的返回路由指向 R2；若 R2 不知道 A 的前缀或被防火墙拦截，A 会表现为“请求超时”。检查时分别从 A 与 B 看去程、回程路由，并对照防火墙状态表。状态防火墙若要求双向流量经过同一设备，非对称路径也可能被丢弃。

源地址选择也影响回程。多网卡主机可能从接口 X 发包，却选择接口 Y 的 IP 作为源地址；远端回复走向 Y 所在网络。排障时记录真实报文的源与目的 IP，不能只根据应用绑定的主机名猜测。

静态路由与动态路由

静态路由适合简单、稳定且变更少的拓扑；动态协议用于在多路径网络中传播可达前缀和收敛故障。OSPF 等域内协议与 BGP 等域间协议解决的范围和策略不同，但最终仍需把选定路径安装到转发表。路由学习成功并不意味着转发一定成功，还要检查下一跳可达、接口、ACL 与设备容量。

最长前缀匹配还关系到安全。更具体路由可以覆盖聚合路由，让某个地址段走不同路径；错误宣告或配置可能造成流量劫持与黑洞。变更前后应比对受影响前缀的去程和回程，而非只检查一条目的地址。

验证命令与实验

在主机上可查路由表和针对某个目的地址的实际路由选择；在路由器上查看生效前缀、下一跳、邻居表与接口计数器。测试时选 /24 内、/24 外但 /16 内、/16 外但 /8 内、所有具体前缀外四个地址，逐个核对手算结果。若 traceroute 停在某跳，该跳之后可能丢包，也可能只是 ICMP 响应被限制，需要结合端口测试和抓包。

一个完整结论要包含“哪条前缀命中、哪个下一跳、该下一跳是否可达、回程是否存在”。少任何一项，都可能把应用超时误判成 DNS 或服务器问题。

路由选择的三条规则

路由器转发时按以下顺序决策：① 最长前缀匹配 → ② 管理距离（AD）→ ③ 度量值（Metric）。注意顺序：先比前缀长度，不同协议之间比 AD，同一协议内比 Metric。

举例：同时存在 10.0.0.0/8 via A（静态，AD=1） 和 10.1.0.0/16 via B（OSPF，AD=110）。去往 10.1.2.3 时，/16 更长，所以走 B —— 即使 AD 更差。这就是最长前缀优先。

路由表操作

# 查看路由表
ip route show
# default via 192.168.1.1 dev eth0 proto dhcp src 192.168.1.100 metric 100
# 10.0.0.0/8 via 10.1.1.1 dev eth1
# 192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.100

# 查某个目的地址命中哪条路由（排障利器）
ip route get 8.8.8.8
ip route get 10.1.2.3 from 192.168.1.100

# 添加/删除静态路由
ip route add 10.2.0.0/16 via 10.1.1.1 dev eth1
ip route add default via 192.168.1.1 metric 100
ip route del 10.2.0.0/16

# 策略路由（按源地址选路由表）
ip rule add from 10.0.0.0/24 table 100
ip route add default via 10.0.0.1 table 100

# 看内核路由缓存/查找统计（老内核有 route -C）
ip -s route show cache   # 新内核已移除缓存

默认路由与黑洞排查

  • 默认路由 0.0.0.0/0 的前缀长度是 0，永远最后匹配（兜底）。没有默认路由 = 只能访问直连和明细网段。
  • 多默认路由的 metric：多条 default 时按 metric 小的优先（等价路由会做 ECMP 负载）。Linux 上 DHCP 给的 default metric 常是 100，手工加的若 metric 更大会“配了但不生效”。
  • 策略路由（Policy Routing）：Linux 默认查 local → main → default 三张表，规则见 ip rule。多出口、VPN 分流要靠 ip rule + 自定义表实现（如按源地址或 fwmark）。
  • 常见故障 1：配了明细路由但走不通 → 检查回程路由。单向通（能去不能回）是最容易被忽略的问题：对端也要有回本端的路由。
  • 常见故障 2：VPN 连上后所有流量都走 VPN → 检查是否推了 0.0.0.0/0 路由（redirect-gateway）。要分流就用 ip rule 排除内网网段。
  • 常见故障 3：ip route get 显示走的是非预期接口 → 看 metric 和路由表优先级。
  • 黑洞与 null0：聚合路由常配一条指向 null0 的汇总路由（丢弃），配合明细路由使用；防止环路和匹配到默认路由后兜圈子。
为什么有两条能匹配的路由，走的却不是我认为的那条？

按优先级排查：① 前缀更长的赢；② 前缀相同比 AD（直连 0 > 静态 1 > eBGP 20 > OSPF 110 > iBGP 200）；③ 同一来源比 metric。Linux 上还要看 ip rule 的策略路由顺序。

ping 通但服务不通，可能是路由问题吗？

可能。若存在非对称路由（去程走 A、回程走 B），且 B 路径上有状态防火墙/NAT 没看到去程的 SYN，回包会被丢弃。用 traceroute 双向测，或在两端同时抓包对比。

自检

一条更具体的 /24 路由指向坏网关，是否一定自动回退到可用的 /16？

不一定。若 /24 仍在生效转发表中，最长前缀匹配可能持续选择坏网关；要看故障检测是否撤销该路由。
