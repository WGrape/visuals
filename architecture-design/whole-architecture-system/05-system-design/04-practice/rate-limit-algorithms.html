限流算法详解

漏桶、令牌桶、滑动窗口——三种算法的本质区别不是「谁更高级」，而是「它们对突发流量各自放不放行」。一图看懂，不再背概念。

限流要解决什么

限流是系统的「保险丝前的第一道闸门」：当请求量超过系统处理能力时，主动拒绝超额部分，保护后端不被压垮。三种经典算法回答的是同一个问题——「这一刻，该不该放行这个请求？」，但判断策略不同。

① 漏桶算法 Leaky Bucket

把请求想象成倒进桶里的水，桶底有个固定大小的洞，水以恒定速率漏出（被处理）。桶满则溢出（拒绝）。核心特征：流出速率恒定，平滑无突发。

图：漏桶强制「匀速流出」，再大的突发洪峰也被削成平稳流。
  • 优点：输出绝对平滑，保护后端最稳，适合「下游处理速率必须恒定」的场景（如调用第三方按量计费接口）。
  • 缺点：即使系统空闲、桶是空的，突发流量也要排队匀速流出，无法利用突发余量。

② 令牌桶算法 Token Bucket

桶里不放请求，而是按固定速率生成令牌。每个请求要拿走一个令牌才被放行；桶空则拒绝。关键点：令牌攒着不消费，所以允许一定程度的突发。

图：令牌桶允许「攒够令牌后一次性放行一波」，兼顾平滑与突发。
  • 优点：长期速率受限，但支持短时突发（桶里有攒下的令牌就能一次放行多个），最贴合真实业务。
  • 缺点：突发过猛时仍可能被打满（令牌瞬间耗尽），需合理设桶容量。
  • 实战：Guava RateLimiter、Nginx limit_req、Sentinel 默认都基于令牌桶思路。

③ 滑动窗口 / 计数器 Sliding Window

把时间切成小格（如 1 秒 = 10 个 100ms 格），只统计「过去 N 秒」内的请求数。相比固定窗口，它消除了「窗口临界点的双倍突发」问题。核心是用更小的粒度逼近真实速率。

对比固定窗口滑动窗口
统计方式每个时间窗累计计数，窗结束清零统计「当前时刻往前 N 秒」的滚动计数
临界突发窗边界可能出现 2 倍限额的突发平滑，几乎无临界翻倍
实现成本极低（一个计数器）较高（需维护时间槽或环形数组）

三选一：怎么挑

🛡️ 保护脆弱下游

下游速率必须恒定（第三方按量接口）→ 漏桶，宁肯排队也不冲垮它。

⚡ 通用 API 限流

既要限速又不想误伤正常突发 → 令牌桶，几乎是所有限流组件默认选择。

📊 精确速率统计

对「单位时间请求数」敏感、要杜绝临界翻倍 → 滑动窗口。

🔧 极简场景

粗粒度防护、实现要快 → 固定窗口计数器，配合短窗口降低风险。

💡 类比：漏桶像「水龙头接满就溢出的水杯」，水必须匀速漏；令牌桶像「游乐园发入场手环」，每隔一会儿发一个，手环攒着，人来了没手环就进不去——但攒够手环时一群人能一起进。
⚠️ 避坑：限流一定要区分拒绝策略——是「直接 429 拒绝」还是「放入队列排队（相当于漏桶的桶）」？前者简单但用户体验差，后者更平滑但要防队列无限增长。

🎯 面试问答

Q：令牌桶和漏桶最根本的区别？
A：漏桶限制的是「流出速率」（恒定），令牌桶限制的是「平均流入速率」但允许「突发流入」。一句话：漏桶怕你突发太猛被削平，令牌桶允许你攒一波再放。
Q：固定窗口为什么会在临界点出现双倍流量？
A：假设限额 100/秒，第 0.9 秒来了 100 个，第 1.1 秒（新窗口）又来 100 个——这 200 个请求落在「相邻两窗各 100」，但时间上只隔 0.2 秒，系统实际 0.2 秒内承受了 200。滑动窗口用「滚动统计」消除了这个漏洞。
Q：分布式系统里限流状态怎么共享？
A：单机限流易实现但各节点独立、总限额难控。多节点常用「集中式计数器」（Redis + Lua 原子增减）或「网关层统一限流」；也可接受「单节点限额 × 节点数 ≈ 集群限额」的近似方案以降复杂度。

四种限流算法的取舍与实现

限流算法的选择取决于两件事：要不要允许突发和边界要不要精确。这两点决定了该用哪个。

算法数据结构是否允许突发边界精度空间
固定窗口计数一个计数器 + 时间戳边界可能双倍突发差（临界突刺问题）O(1)
滑动窗口计数多个小格子（或 Redis ZSet）平滑，无双倍突发取决于格子粒度O(格子数)
漏桶（Leaky Bucket）队列 + 恒定出水速率不允许突发（出水恒定）输出完全平滑O(队列)
令牌桶（Token Bucket）令牌数 + 上次补充时间允许突发（攒的令牌可一次用完）突发量 = 桶容量O(1)
维度漏桶令牌桶
出水方式恒定速率（无论进来多猛）有令牌就能过，可以突发
对突发的态度削峰填谷，排队等待允许，用完为止
实现队列 + 定时器/惰性计算令牌计数 + 时间差补充
适用需要严格平滑下游（如写数据库）大多数 API 限流（允许短时突发）
代表Nginx limit_reqGuava RateLimiter、Sentinel
部署位置方案特点
单机限流Guava RateLimiter / Resilience4j最快，无网络开销；但只能限本机（N 台机器实际是 N×阈值）
分布式限流Redis + Lua 脚本集群总量精确；有网络开销（~1ms）
网关限流Nginx / Kong / APISIX / Envoy入口统一限，最省事
自适应Sentinel 系统自适应（按 Load/CPU）不设固定阈值，看机器实际水位

实现代码

# ---------- 令牌桶（Go 标准库 golang.org/x/time/rate）----------
import "golang.org/x/time/rate"
lim := rate.NewLimiter(rate.Limit(100), 200)   # 100 QPS，桶容量 200
#                       ^每秒补充 100 个       ^最多攒 200（允许 2 秒突发）
if !lim.Allow() { return errors.New("rate limited") }
#   非阻塞判断；还可以用 Wait(ctx) 阻塞等待，或 Reserve() 预约

# ---------- Redis 分布式限流（Lua 保证原子性）----------
# 令牌桶 Lua 脚本
local key = KEYS[1]
local rate = tonumber(ARGV[1])      # 每秒补充
local capacity = tonumber(ARGV[2])  # 桶容量
local now = tonumber(ARGV[3])
local tokens_key = key .. ':tokens'
local ts_key = key .. ':ts'
local last_tokens = tonumber(redis.call('get', tokens_key) or capacity)
local last_ts = tonumber(redis.call('get', ts_key) or now)
local delta = math.max(0, now - last_ts) / 1000
local tokens = math.min(capacity, last_tokens + delta * rate)
if tokens < 1 then
    return 0                         # 拒绝
end
redis.call('set', tokens_key, tokens - 1)
redis.call('set', ts_key, now)
return 1                             # 通过

# ---------- 滑动窗口（Redis ZSet 实现，精确但有空间开销）----------
#   ZADD key <timestamp> <uuid>
#   ZREMRANGEBYSCORE key 0 <now-60000>      # 删掉 1 分钟前的
#   ZCARD key                                # 当前窗口内请求数
#   用 Lua 包起来保证原子性

# ---------- Nginx 限流（网关层，最省事）----------
# http 块中：
limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;
# server/location 中：
limit_req zone=api burst=20 nodelay;
#   burst=20：允许突发 20 个
#   nodelay：突发的不排队，直接放行（否则会匀速处理）
  • 固定窗口的临界突刺是真实存在的：在窗口切换的瞬间，前 1 秒和后 1 秒各来阈值数量的请求，2 秒内实际通过 2 倍。对严格场景不可接受。
  • 令牌桶是最常用的选择：O(1) 空间、允许突发（符合大多数 API 的真实需求）、实现简单。Guava RateLimiter 和 Go 的 x/time/rate 都是它。
  • 漏桶适合保护下游：当你需要「无论上游多猛，下游收到的速率恒定」时（如保护数据库），漏桶比令牌桶合适。
  • 单机限流的 N 倍问题：10 台机器每台限 100 QPS，实际集群可能是 1000 QPS。要精确控制总量必须用 Redis 分布式限流。
  • Redis 限流必须用 Lua 保证原子性：分开的 GET + SET 在并发下会失效。
  • 被限流的请求要给 Retry-After：HTTP 429 响应带上 Retry-After 头，让客户端知道多久后重试。
  • 限流要分级：按用户/租户/IP/接口分别限，避免一个租户把整个服务的配额吃光。
令牌桶和漏桶到底选哪个？

核心问题是要不要允许突发。令牌桶：桶里攒着令牌，攒够了多少就能一次性用掉——一个限 100 QPS、桶容量 200 的令牌桶，如果之前 2 秒没人访问，第 3 秒可以瞬间放行 200 个请求。这符合大多数 API 的真实场景（用户不会匀速访问，短时间密集请求是正常的）。漏桶：无论进来多猛，出水速率恒定——100 QPS 的漏桶，哪怕突然来 1000 个请求，也是每秒匀速放行 100 个，其余排队或丢弃。这适合保护下游（如保护数据库不被突发流量打垮），因为下游收到的始终是平滑的速率。判断准则：限流的目的是「保护自己的服务不被打爆」→ 令牌桶（允许合理突发，用户体验好）；目的是「保护下游系统」→ 漏桶（恒定出水，绝对平滑）。工程上令牌桶用得更多，因为它空间 O(1)、实现简单、且更符合用户预期。另外 Go 的 x/time/rate 和 Guava 的 RateLimiter 都是令牌桶。

固定窗口的临界突刺问题有多严重？

最坏情况是通过量翻倍。举例：限流 100 QPS，用 1 秒固定窗口。如果在第 1 秒的最后 100ms 来了 100 个请求（窗口内计数到 100，全部通过），然后在第 2 秒的最前 100ms 又来了 100 个请求（新窗口重新计数，也全部通过）——那么200 毫秒内实际通过了 200 个请求，瞬时速率是阈值的 10 倍。这在保护下游的场景下是致命的（你以为限了 100，下游实际收到了瞬时 1000 的速率）。解法三种：① 滑动窗口——把 1 秒切成 10 个 100ms 的格子，统计最近 10 个格子的总和，精度由格子粒度决定（格子越细越精确，但内存开销越大）；② 滑动日志（Redis ZSet 存每个请求的时间戳）——完全精确，但每个请求存一条记录，内存开销大，只适合低 QPS 场景；③ 令牌桶/漏桶——天然没有这个问题，因为它们是按速率补充而不是按窗口计数。实践建议：精确性要求高的用滑动窗口（取 10~60 个格子通常够）；要求简单且允许小误差的用令牌桶。

分布式限流怎么做才准确？

核心是原子性——计数和判断必须在一次 Redis 操作里完成，否则并发下会失效（比如两个请求同时读到计数 99，都认为没超限，都放行，实际变成 101）。必须用 Lua 脚本（Redis 保证 Lua 脚本整体原子执行）。三种实现：① 令牌桶 Lua（上面的示例）——存 tokens 和 ts 两个 key，每次计算时间差补充令牌，空间 O(1)，最推荐；② INCR + EXPIRE——最简单的固定窗口，但要注意 INCR 和 EXPIRE 不是原子的（INCR 成功但 EXPIRE 失败会导致永久限流），也要用 Lua 包起来；③ ZSet 滑动日志——精确但每条请求存一个 member，只适合低 QPS。几个实践要点：① Redis 挂了怎么办——通常降级为放行（可用性优先），或降级为单机限流；② 网络开销——每次限流判断一次 Redis 往返（约 0.5~1ms），高频接口要评估是否可接受；③ 批量/预取——可以一次取 10 个令牌，减少 90% 的 Redis 调用；④ 集群维度——如果用 Redis Cluster，同一个 key 必须落在同一个 slot（Lua 脚本涉及多个 key 时要保证它们在同一个 hash slot）。

一、四算法对比

算法怎么算能突发吗空间边界问题
固定窗口计数每分钟一个计数器，到点清零能，且可能双倍突发O(1)窗口交界处可放行 2 倍配额
滑动窗口计数把窗口分格，统计最近 N 格之和基本不能O(格数)格子越多越精确，内存越大
滑动窗口日志记录每个请求时间戳不能O(请求数)最精确但内存不可控
漏桶请求入桶，桶以恒定速率漏出不能，强制匀速O(1)突发请求排队或被丢弃
令牌桶按速率生成令牌，请求取令牌能，攒多少就能突多少O(1)突发量 = 桶容量
固定窗口的双倍突发问题

配额 100/分钟。00:59 打满 100 次，01:00 计数器清零，01:00~01:01 又能打 100 次。于是一秒钟内通过了 200 次请求。这就是固定窗口最大的缺陷，滑动窗口和令牌桶都是为了解决它而出现的。

二、令牌桶：最常用的一版实现

type TokenBucket struct { capacity float64 // 桶容量 = 允许的突发量 rate float64 // 每秒生成多少令牌 tokens float64 last time.Time } func (b *TokenBucket) Allow(now time.Time) bool { // 1) 先按流逝时间补令牌（懒计算，不需要定时器） elapsed := now.Sub(b.last).Seconds() b.tokens = min(b.capacity, b.tokens+elapsed*b.rate) b.last = now // 2) 有令牌就放行并扣掉 if b.tokens >= 1 { b.tokens-- return true } return false } // 参数直觉：rate=100/s, capacity=200 // -> 平均 100 QPS，允许瞬间冲到 200

三、分布式限流：Redis + Lua

单机限流只能保护单实例。集群限流必须有一个共享的计数点，Redis + Lua 是最常见的方案：

-- KEYS[1]=限流 key, ARGV[1]=rate/s, ARGV[2]=capacity local key = KEYS[1] local rate, cap = tonumber(ARGV[1]), tonumber(ARGV[2]) local now = redis.call('TIME') local now_ms = now[1] * 1000 + math.floor(now[2] / 1000) local data = redis.call('HMGET', key, 'tokens', 'ts') local tokens = tonumber(data[1]) or cap local ts = tonumber(data[2]) or now_ms -- 补令牌 tokens = math.min(cap, tokens + (now_ms - ts) / 1000 * rate) local allowed = 0 if tokens >= 1 then tokens = tokens - 1 allowed = 1 end redis.call('HMSET', key, 'tokens', tokens, 'ts', now_ms) redis.call('PEXPIRE', key, math.ceil(cap / rate * 1000) + 1000) return allowed -- 关键：读-算-写必须在同一个 Lua 里原子完成， -- 否则并发下会超发

四、限流 vs 熔断 vs 降级

限流熔断降级
触发条件流量超过阈值下游错误率/慢调用超阈值系统压力过大或依赖不可用

五、深入自检

限流阈值怎么定？

先压测得到单机容量，再乘以实例数打折扣（0.6~0.8），最后按业务优先级分配配额。凭感觉拍一个数是最常见的错误做法。

被限流的请求应该怎么处理？

三种：直接拒绝（返回 429 + Retry-After）、排队等待（适合异步任务）、降级返回兜底数据。同步用户请求通常是直接拒绝 + 客户端退避重试。

为什么要给不同的调用方分别限流？

否则一个调用方把配额打满，其他调用方全部被饿死。按 API Key / 用户 / 租户维度限流是必备能力。

网关限流和应用限流都要做吗？

要。网关挡住绝大部分外部洪峰；应用自己做一层是防止内网其他服务或网关被绕过时的兜底，也是保护自己的最后一道闸门。

漏桶和令牌桶到底选哪个？

需要严格匀速输出（如保护下游 DB 不被冲击）选漏桶；希望允许合理突发（如用户批量操作）选令牌桶。绝大多数业务限流用令牌桶更贴合直觉。
