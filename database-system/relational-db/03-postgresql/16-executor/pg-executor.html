① 火山模型（Volcano / Iterator）

PG 的执行器采用经典的火山模型：每个计划节点实现统一的迭代器接口，父节点通过 next() 向子节点拉取一行，逐层向上，直到顶层。

简化伪代码：
ExecProcNode(node):
    return node->ExecProcNode(node)      # 多态调用

# 例如 NestLoop 的 next()：
#   1. 从左子节点取一行（outer tuple）
#   2. 用该行的连接键去右子节点取匹配行（inner tuple）
#   3. 返回组合后的结果行；右子节点耗尽则回到步骤 1

优点

实现简单、通用性强、内存占用小（不需要物化中间结果）、天然支持 LIMIT 提前终止

缺点

每行都要多次函数调用（虚函数调用开销）、无法充分利用 CPU 流水与 SIMD

缓解

表达式 JIT 编译（PG 11+）：把 WHERE/聚合中的表达式编译成本地代码，复杂分析查询可提速 10%~30%

趋势

PG 正在推进向量化执行与列存（如 pg_analytics、ParadeDB 等生态项目）

EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT o.status, count(*) FROM orders o
WHERE o.created_at >= '2026-10-01' GROUP BY o.status;

-- 典型输出
-- HashAggregate  (actual time=.. rows=5 loops=1)
--   Group Key: o.status
--   Batches: 1  Memory Usage: 24kB
--   ->  Seq Scan on orders o (actual rows=120000 loops=1)
--        Filter: (created_at >= '2026-10-01'::date)
--        Rows Removed by Filter: 880000    ← 过滤掉了 88 万行
Rows Removed by Filter 是重要信号：它显示扫描了但被过滤掉的行数。若该值远大于返回行数，说明扫描范围过大——应考虑加索引或加更精确的条件来减少扫描量。

③ JIT 编译

-- 相关参数
SHOW jit;                       -- on（PG 11+ 默认开启，但只在代价够高时触发）
SHOW jit_above_cost;            -- 100000：代价超过此值才考虑 JIT
SHOW jit_inline_above_cost;     -- 500000
SHOW jit_optimize_above_cost;   -- 500000
SHOW jit_provider;              -- llvmjit

-- 观察是否用了 JIT
EXPLAIN (ANALYZE) SELECT ...;
-- 计划后出现：JIT: Functions: 12, Options: Inlining true, Optimization true...

什么场景有用

复杂分析型查询：大量表达式计算、聚合、多列 WHERE——可提速 10%~30%

什么场景有害

短小 OLTP 查询：编译开销（毫秒级）可能超过省下的时间

调优

OLAP 库调低 jit_above_cost；OLTP 库可直接 SET jit = off

依赖

需要安装 LLVM 与 postgresql-llvmjit 包，某些发行版默认未装

④ 并行执行与内存

并行查询由 leader + worker 组成：Gather 节点负责汇总。每个 worker 是独立进程，独占一份 work_mem。

-- 计划中的并行
-- Gather  (cost=.. rows=..) (actual time=.. rows=..)
--   Workers Planned: 2
--   Workers Launched: 2
--   ->  Parallel Seq Scan on big_table
--        Filter: (...)
--        Rows Removed by Filter: ...
内存核算：并行查询的总内存 ≈ worker 数 × work_mem × 排序/哈希节点数。因此调大并行度必须同步评估内存，否则容易 OOM 或大量落盘。OLTP 高并发场景建议把 max_parallel_workers_per_gather 调到 0~2，把资源让给并发请求。

⑤ 常见问法

Q：什么是火山模型？有什么优缺点？

A：火山模型（Volcano/Iterator Model）中，每个执行节点实现统一接口，父节点通过 next() 逐行向子节点拉取数据。优点：实现简单通用、内存占用小（不需物化中间结果）、天然支持 LIMIT 提前终止（取够就停）、易于组合各种算子；缺点：每行都要经过多次虚函数调用，函数调用与解释执行的开销大，无法充分利用 CPU 流水与 SIMD。缓解：PG 11+ 引入表达式 JIT 编译，把 WHERE/聚合中的表达式编译成本地机器码，复杂分析查询可提速 10%~30%。

Q：EXPLAIN 里 loops 很大说明什么？

A：loops 表示该节点被父节点重复执行的次数，典型出现在 Nested Loop 的内侧节点：外表每返回一行，内表就要重新扫描一次。判断方法：节点的实际总耗时 = actual time × loops。若 loops 达到几千上万，即使单次很快，总代价也很可观。对策：① 给内表的连接键建索引（把内表扫描变成索引查找）；② 让优化器改用 Hash Join（调大 work_mem 或补统计信息使其估算正确）；③ 减少外表返回的行数（先过滤）。

Q：JIT 对查询有帮助吗？什么时候该关？

A：有帮助的场景：复杂分析型查询——涉及大量表达式计算、聚合、多列 WHERE 条件，JIT 把表达式编译成本地代码，通常可提速 10%~30%。该关的场景：短小 OLTP 查询（毫秒级），因为 JIT 编译本身有毫秒级开销，可能超过省下的时间；此外若未安装 LLVM 支持，JIT 不可用。调优：OLAP 库调低 jit_above_cost 让更多查询受益；OLTP 库直接 SET jit = off。

Q：并行查询是怎么执行的？内存怎么估？

A：由 leader 进程 + 若干 worker 进程协作：计划中出现 Gather / Gather Merge 节点，worker 并行扫描/聚合，结果汇总到 leader。每个 worker 是独立进程，各自独占一份 work_mem。内存估算：总内存 ≈ worker 数 × work_mem × 排序/哈希节点数，因此提高并行度必须同步评估内存，否则会 OOM 或大量落盘。调优：OLAP 场景调大 max_parallel_workers_per_gather（4~8）；OLTP 高并发场景调到 0~2，把资源让给并发请求。

Q：Rows Removed by Filter 很大说明什么？

A：它表示扫描到但被 WHERE 条件过滤掉的行数。若远大于最终返回行数（如扫 100 万行只返回 1000 行），说明扫描范围过大、过滤效率低下。对策：① 建更精准的索引，让过滤条件下推到索引层；② 增加更精确的查询条件；③ 若是部分索引的适用场景（如只查 status='pending'），可建部分索引大幅缩小扫描量；④ 考虑分区表，让查询只扫相关分区；⑤ 若过滤列与物理顺序相关，BRIN 索引也能显著减少扫描。

Q：执行器和优化器是怎么配合的？

A：分工：优化器（Planner）只负责选择计划——枚举路径、估算代价、输出一棵计划树（由 Scan/Join/Aggregate/Sort 等节点组成）；执行器（Executor）负责按计划取数——以火山模型从根节点递归调用 next()，各节点按需向下拉取。关键点：执行器不做优化决策，它忠实执行优化器选出的计划。因此「执行慢」的根因通常在计划（扫描方式、JOIN 顺序、是否落盘），而不是执行器本身——排查时应先看 EXPLAIN (ANALYZE) 找出代价最高的节点。
