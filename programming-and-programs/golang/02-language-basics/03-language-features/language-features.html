LIFO 栈、参数即时求值

defer 把调用压栈，函数 return 前按「后进先出」执行；但 defer 后面的参数在注册时就求值，不是执行时。

func f() {
    defer fmt.Println("1")
    defer fmt.Println("2") // 先注册，后执行
    fmt.Println("run")
}
// 输出: run  2  1

defer func(x int) { fmt.Println(x) }(i) // i 在 defer 时定格
经典用途：关闭文件/解锁/记录耗时。配合匿名函数可读取并修改具名返回值（命名返回 + defer 修改 = 实现 retry/包装返回值）。
new 与 make 的区别

一个返指针，一个造容器

new(T) 分配零值内存并返回 *T；make 只为 slice/map/chan 这三种「引用类型」分配底层结构并返回初始化好的 T（不是指针）。

p := new(int)        // *int，指向 0
var q *int = new(int)

s := make([]int, 0, 8)  // 切片，len0 cap8
m := make(map[string]int) // 空映射可用
c := make(chan int, 3)   // 缓冲通道
⚠️ 用 new(map[string]int) 得到的是 *map，且底层仍为 nil，无法直接写入；映射必须用 make 或字面量初始化。
零值语义

声明即可用

所有变量声明后都有零值（数值0、bool false、string ""、指针/nil接口/切片/映射/通道为 nil）。这点和 C 的未初始化完全不同。

var s []int          // nil 切片，可直接 range（不崩溃）
var m map[string]int // nil 映射，读取返回零值但写入会 panic
if m == nil { m = make(map[string]int) } // 用前需 make
运算符与短声明

Go 的一些习惯

Go 没有 ++i 只有 i++（且是语句不是表达式）；支持多赋值 a, b = b, a；指针用 & 取地址、* 解引用。

i++            // 合法，且是语句
// ++i          // 非法

a, b = b, a    // 并行交换，不用临时变量

p := &x        // 取地址
*p = 10        // 解引用赋值

defer 的完整行为：三句话讲清

defer 看起来简单，但三个细节决定了你能否用对：注册时参数就求值、执行时后进先出、能修改命名返回值。

// 1) 参数在注册时求值，而不是执行时 func f() { i := 0 defer fmt.Println(i) // 此刻就把 0 拷贝进来了 i = 100 // 输出：0 } // 想延迟求值，用闭包，闭包捕获的是变量本身 func g() { i := 0 defer func() { fmt.Println(i) }() i = 100 // 输出：100 } // 2) 多个 defer 后进先出 func h() { defer fmt.Println("first") defer fmt.Println("second") // 输出顺序：second, first } // 3) defer 可以修改命名返回值 func k() (err error) { defer func() { if err != nil { err = fmt.Errorf("wrap: %%w", err) // 改的是返回出去的那个 err } }() return doSomething() }
注册即求值defer 后的函数参数在这一行就确定了
后进先出多个 defer 按栈顺序执行，适合成对的资源释放
可改命名返回值匿名返回值改不了，命名返回值可以
在 return 之后执行返回值先被赋值，然后才跑 defer

new 与 make：一个返回指针，一个造容器

两者的分工非常清晰：new 只分配零值内存并返回指针，make 负责初始化容器结构。它们都不能互相替代。

对比new(T)make(T, args)
适用类型任意类型仅 slice、map、channel
返回值指针类型与 T 同类型，不是指针
内存内容全部置为零值完成内部结构初始化，立即可用
典型用法p := new(int)，等价于取地址m := make(map[string]int)
可否省略多数情况用取地址更直观不能省略，声明后直接用会 panic 或阻塞
// new：分配零值，返回指针 p := new(int) // 指向一个值为 0 的 int *p = 10 // 等价写法，更常用： x := 0 p = &x // make：初始化容器，返回容器本身 s := make([]int, 0, 10) // len=0, cap=10，预留容量 m := make(map[string]int) // 空映射，可以直接写入 ch := make(chan int, 1) // 带缓冲的通道 // 声明但不 make 会怎样？ var m2 map[string]int m2["a"] = 1 // panic: 向 nil map 写入 var ch2 chan int ch2 <- 1 // 永久阻塞，nil channel 上发送会一直等 // 但 nil slice 可以直接 append，这是唯一的例外 var s2 []int s2 = append(s2, 1) // 没问题

零值可用：Go 的设计哲学

为什么强调零值可用

因为 Go 保证每个变量声明后都有一个合法的零值，这让很多类型不需要构造函数就能直接用：互斥锁的零值就是未加锁状态、字节缓冲的零值就是空缓冲、nil 切片可以直接 append。

零值可用的边界

它不意味着所有类型都不需要初始化。map 的零值是 nil，写入会 panic；channel 的零值是 nil，发送会永久阻塞。判断标准是看这个类型的零值是否构成一个可用的空状态。

数值零值 0可直接参与运算
字符串零值空串可直接拼接与比较
nil 切片可直接 append、取长度、range
nil map可读不可写，写入 panic
nil channel发送接收都会阻塞
互斥锁零值未加锁，可直接使用
指针零值 nil解引用会 panic
接口零值 nil类型与值都为 nil 才是 nil

深入自检：语言特性的六个坑

defer 放在循环里会怎样？

会累积到函数返回时才统一执行。如果在循环里 defer 文件关闭，循环中会一直持有文件句柄，可能耗尽资源。正确做法是把循环体抽成独立函数，让 defer 在每次迭代结束时生效；或者在迭代内显式调用关闭。

defer 的性能开销大吗？

现代 Go 中 defer 的开销已经很小，开放编码优化让多数场景接近直接调用，但仍比直接调用略高。在极热的循环里可以考虑去掉，一般业务代码完全不必为此牺牲可读性。

recover 能捕获所有 panic 吗？

不能。它必须在 defer 中调用才有效，直接调用无效；且只能恢复当前 goroutine 的 panic。子 goroutine 里的 panic 无法被父 goroutine 的 recover 捕获，会直接导致整个进程退出。所以启动 goroutine 时通常要在最外层加保护。

nil 接口与持有 nil 指针的接口一样吗？

不一样。接口值由动态类型与动态值两部分组成，只有两者都为 nil 时接口才等于 nil。把一个 nil 指针赋给接口后，接口的类型部分非空，所以它与 nil 比较的结果是 false，这是经典的坑。

为什么 Go 没有三元运算符？

语言设计者认为它容易被滥用、降低可读性，所以坚持用完整的 if-else 表达条件。这是刻意的设计取舍，习惯后反而觉得代码更清楚。

短变量声明有什么限制？

它只能在函数内使用，且至少要声明一个新变量，否则要用等号。还要注意作用域遮蔽：在内层用短声明声明同名变量会遮蔽外层变量，在 if 或 for 里尤其常见，容易引发不易察觉的 bug。

defer 的语义、性能与三个坑

defer 三坑

// 坑 1：参数在 defer 时就求值（不是执行时）
func f() {
    i := 0
    defer fmt.Println(i)   // 立刻把 0 拷贝进去
    i++
    return                 // 输出 0，不是 1
}

// 坑 2：defer 在循环里会堆积到函数结束才执行
for _, f := range files {
    fh, _ := os.Open(f)
    defer fh.Close()       // ❌ 循环 1 万次 = 1 万个 fd 撑到函数结束
}
// ✅ 用匿名函数包一层，或者干脆显式 Close
for _, f := range files {
    func(name string) {
        fh, _ := os.Open(name)
        defer fh.Close()
        // ...
    }(f)
}

// 坑 3：defer 与命名返回值
func g() (r int) {
    defer func() { r = 10 }()   // 能修改返回值（因为是命名返回值）
    return 1                     // 最终返回 10
}
func h() int {
    var r int
    defer func() { r = 10 }()   // 改不到返回值
    return 1                     // 返回 1
}
项事实
执行顺序LIFO（后注册先执行）
参数求值时机注册时立即求值，返回值在执行时才确定
性能（Go ≤ 1.12）堆上分配 defer 记录，约 50~100 ns 级别
性能（Go 1.13+）引入开放编码 defer（open-coded），函数内无循环的 defer 直接内联展开，开销降到 约 1~10 ns
性能（Go 1.14+）进一步优化，绝大多数场景 defer 开销已可忽略
结论不要为了性能避免使用 defer；要避免的是「循环里的 defer」和「热路径上百万次的 defer」

defer 的正确心智模型：它是「注册一个保证会执行的收尾动作」，用途是让资源释放紧邻资源获取，避免提前 return 时漏掉清理。不要用它做业务逻辑（比如依赖它的执行时机）。

nil map 和空 map 有什么区别？

空 map（make(...)）可以写入；nil map 写入 panic。读、len、range 在两者上都正常。判断是否存在 key 用 v, ok := m[k]，不能靠 v == nil（key 存在但值为零值时也成立）。

new 和 &T{} 用哪个？

&T{} 更灵活（可以顺便赋初值），new(T) 只做零值分配。实际代码里几乎都用前者。

defer 会不会影响性能？

Go 1.13 之后的开放编码 defer 已经把绝大多数场景的开销压到几乎可忽略。真正要避开的是循环体内 defer（资源堆积）。
