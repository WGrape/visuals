一致性哈希

当数据要分散到 N 台机器上，怎么决定"哪条数据去哪台"？一致性哈希用一条哈希环把"加机器/减机器只搬少量数据"变成了现实。

为什么需要 核心原理 哈希环图解 虚拟节点 三种方案对比 面试要点

⚠️ 一、为什么需要一致性哈希

最朴素的办法是"取模分片"：节点 = hash(key) % N。它简单，但有个致命问题——节点数 N 一变，几乎所有数据都要重新映射。

💥
取模法的灾难：3 台机器扩到 4 台，hash(key) % 3 变成 hash(key) % 4。理论上有 ≈ 75% 的数据会落到不同的节点上，引发大规模数据迁移，缓存系统瞬间击穿、数据库被打爆。节点频繁上下线的分布式环境根本扛不住。
一致性哈希要解决的核心矛盾：既要把数据均匀分散到多节点，又要让节点增减时，只影响极小一部分数据，而不是全量重分布。

🧩 二、核心原理：把"地址空间"排成一个环

一致性哈希把哈希值空间（如 0 ~ 2³²-1）首尾相连，想象成一个顺时针的环。节点和数据都通过同一个哈希函数映射到环上。

构建哈希环
取一个哈希函数（如 MD5、SHA，或 MurmurHash），把结果对 2³² 取模，得到一个 [0, 2³²) 的整数区间，首尾相接成环。
节点上环
对每个节点（用 IP、名字等）做哈希，得到它在环上的位置。例如 Node-A、Node-B、Node-C 各占环上一段。
数据上环
对数据 key 同样做哈希，得到环上某点。沿环顺时针走，遇到的第一个节点就是它归属的节点。
增减节点只动相邻数据
新增节点只"抢走"环上它到前一个节点之间的数据；删除节点只把它的数据顺时针交给下一个节点。其余节点的数据纹丝不动。

⭕ 三、哈希环图解

下图中，3 个节点把环分成 3 段；数据 K1~K5 顺时针找最近节点。注意：顺时针是约定方向。

K1 顺时针最近的节点是 A；K2/K3 落到 B；K4 落到 C；K5 顺时针越过顶部回到 A。当新增节点 D 插在 A 与 C 之间（环左下方），只有原本属于 A 的一部分数据改投 D，B、C 完全不受影响。

🎭 四、虚拟节点：解决"数据倾斜"

裸的一致性哈希有个问题：节点少时，它们在环上的分布可能极不均匀——某台机器"占了一大半环"，数据严重倾斜。解决方法是虚拟节点（vnode）。

⚖️
虚拟节点做法：每台物理节点复制成多个"虚拟节点"（如 Node-A#1, Node-A#2 ... Node-A#100），统统打散到环上。数据先落到虚拟节点，再映射回真实节点。虚拟节点越多，数据分布越均匀（实践中常用 100~200 个）。
无虚拟节点
3 个真实节点 → 环上 3 点，倾斜明显；某节点宕机，其负载全压给顺时针下一台，雪崩。
有虚拟节点
每台 100 个 vnode → 环上 300 点，均匀分布；单节点宕机，它的 vnode 平均分散给其余所有节点，影响被摊薄。

📊 五、三种分片寻址方案对比

方案节点增减的数据迁移量数据均匀度典型应用
取模 hash % N几乎全量（≈ (N-1)/N）均匀固定分片、不可扩缩场景
一致性哈希（无 vnode）仅相邻段（小）易倾斜早期 Memcached 客户端

💡
一句话记忆：一致性哈希 = 哈希环 + 顺时针归属 + 虚拟节点。它用"局部重映射"换来了"弹性扩缩容"。

🎯 六、面试高频追问

一致性哈希为什么能减少数据迁移？
因为只有"新节点到前一个节点之间"的弧段数据会改变归属，其余弧段映射不变。迁移量从 O(N) 降到 O(1/N)。
为什么需要虚拟节点？
真实节点少时环上分布不均、易倾斜；且单节点故障会把全部压力给下一台。虚拟节点把负载打散、摊薄，提升均匀度与容错。
Redis Cluster 用一致性哈希吗？
不用。Redis Cluster 用 16384 个固定 slot，key 经 CRC16 映射到 slot，slot 再分配给节点。它同样能在扩缩容时局部迁移，但寻址和迁移单位都与哈希环不同。
和"范围分片"怎么选？
哈希分片（一致性哈希）利于均匀分布与扩缩容，但范围查询弱；范围分片（按时间/ID 区间）利于区间扫描，但易热点。按访问模式选型。

为什么普通取模不行：一次扩容要搬多少数据

方案加一台节点（N→N+1）数据迁移量命中率
hash(key) % N所有 key 的余数全变≈ (N−1)/N ≈ 全部接近 0%
一致性哈希只影响该节点到前驱之间的一段1/(N+1)N/(N+1)

举例：3 台扩到 4 台。取模法要迁移 约 75% 的数据（缓存几乎全失效，DB 会被打穿）；一致性哈希只迁移 1/4 = 25%，且这 25% 只从 3 个旧节点流向 1 个新节点。

虚拟节点：解决数据倾斜的关键

不加虚拟节点时，物理节点在环上分布不均匀，可能某个节点扛了 40% 的数据。解法是让每个物理节点在环上占 K 个虚拟位置（virtual node）。

虚拟节点数 K/物理节点数据分布标准差内存开销评价
1（无虚拟节点）很大，可能 >30% 偏差无不可用
100约 3 – 5%10 万条（1000 节点 × 100）轻量场景够用
150 – 200约 1 – 2%约 20 万条业界常用
1000+<1%100 万条以上收益递减，查找变慢

K 的经验值 150 – 200（Amazon Dynamo 论文用的是变体，实践中 100–200 最常见）。再往上加对标标准差的改善已经很小，但环上查找的红黑树/跳表变大，反而拖慢路由。

最小实现与均衡度验证

# Python: 一致性哈希最小实现（可直接跑）
import hashlib, bisect

class ConsistentHash:
    def __init__(self, nodes, vnodes=150):
        self.vnodes = vnodes
        self.ring = []            # 环上位置，有序
        self.map = {}             # 位置 -> 物理节点
        for n in nodes: self.add_node(n)

    def _hash(self, s):
        return int(hashlib.md5(s.encode()).hexdigest(), 16)   # 2^128 空间

    def add_node(self, node):
        for i in range(self.vnodes):
            h = self._hash(f"{node}#{i}")
            bisect.insort(self.ring, h)
            self.map[h] = node

    def remove_node(self, node):
        for i in range(self.vnodes):
            h = self._hash(f"{node}#{i}")
            self.ring.remove(h); del self.map[h]

    def get_node(self, key):
        h = self._hash(key)
        i = bisect.bisect(self.ring, h) % len(self.ring)      # 顺时针第一个
        return self.map[self.ring[i]]

ch = ConsistentHash(["10.0.0.1", "10.0.0.2", "10.0.0.3"])
print(ch.get_node("user:10086"))

# 验证均衡度：10 万个 key 的分布
from collections import Counter
c = Counter(ch.get_node(f"k{i}") for i in range(100000))
print(c)   # 每个节点约 33000，偏差 < 2%

加权一致性哈希：机器配置不同怎么办

真实集群里机器配置不一样（有的 32 核有的 8 核）。做法是按权重分配虚拟节点数：K_i = K_base × weight_i。

节点权重（按内存）虚拟节点数（K_base=150）预期承载比例
node-A（32 GB）230040%
node-B（16 GB）115020%
node-C（16 GB）115020%
node-D（8 GB）0.57510%
node-E（8 GB）0.57510%

注意：扩容时如果只加虚拟节点数而不迁移数据，已存在的 key 分布不会自动变均匀——权重调整后要重新平衡（rebalance），把多出来的 key 迁到新节点。

Redis Cluster 用的是哈希槽，不是一致性哈希

对比项Redis Cluster一致性哈希
分片单位16384 个哈希槽（slot）虚拟节点
计算方式CRC16(key) % 16384hash(key) 找环上后继
扩容把部分 slot 整体迁走迁移环上一段区间
元数据每个节点都知道 slot→node 映射客户端或路由层持有环
重定向MOVED（永久）/ ASK（迁移中）客户端自行计算

为什么是 16384：Redis 官方说明是集群节点数最多 1000 个左右，16384 个槽足够均匀分配；同时槽位用 bitmap 表示只需 16384/8 = 2048 字节 = 2 KB，在心跳报文里传输可以接受（若用 65536 槽则需 8 KB，心跳太重）。

深入自检

哈希环的查找复杂度是多少？

环上的虚拟节点位置存在有序结构（红黑树 / 跳表 / 排序数组 + 二分）里，查找是 O(log M)，M = 虚拟节点总数（= 物理节点数 × K）。1000 节点 × 150 = 15 万个位置，log₂ ≈ 17 次比较，完全可接受。用排序数组 + bisect 最简单，代价是插入是 O(M)——但节点变更很罕见，无所谓。

一致性哈希能彻底解决数据倾斜吗？

不能彻底，只能压低。虚拟节点让标准差降到 1 – 2%，但如果某些 key 本身是超级热点（比如一个 key 占 30% 的流量），哈希帮不上忙——那是热点问题不是分布问题，需要本地缓存、多副本、key 拆分来解。

扩容时正在迁移的数据怎么读？

这是最关键的实现细节。标准做法是双写 + 重定向：迁移期间源节点仍持有数据，若已迁走则返回重定向（Redis 的 ASK），客户端带 ASKING 去新节点读。迁移完成后源节点返回 MOVED（永久），客户端更新本地路由表。一致性哈希方案里则是迁移区间内的 key 在新旧节点都能读到（新节点回填）。

什么时候不该用一致性哈希？

① 需要范围查询时——哈希把顺序打散了，改用按 key 范围分片（如 HBase Region、TiDB Region）；② 数据量很小且节点稳定时——直接取模更简单；③ 需要严格控制数据分布时——哈希是概率均匀的，做不到精确。
