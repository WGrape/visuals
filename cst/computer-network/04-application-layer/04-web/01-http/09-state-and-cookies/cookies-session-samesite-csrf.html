Cookie、Session、SameSite 与 CSRF：登录状态怎么传

沿登录、跨站请求和登出三段流程理解浏览器自动带 Cookie 的便利与风险。

HTTP 请求本身没有登录记忆

服务器收到两次 HTTP 请求时，不会仅凭 TCP 连接就知道它们属于同一用户。常见方案是在登录成功后给浏览器一个 Cookie，里面存不透明的会话 ID；浏览器在符合域名、路径和安全属性的后续请求中自动带上 Cookie。服务器用会话 ID 查找服务端状态，得到用户身份和过期时间。Cookie 是携带机制，Session 是服务器或应用定义的状态；也有把签名令牌直接存入 Cookie 的方案，不能混为一谈。

会话 ID 应足够随机且难猜，并通过 TLS 传输。服务器不能把“浏览器发来了某个 Cookie”直接当作授权充分条件，还应验证会话签名或服务端记录、过期、用户权限与撤销状态。Cookie 内容可被用户修改，所以业务金额和权限级别不应作为未经验证的明文事实直接信任。

Set-Cookie 属性各管一件事

`Secure` 限制 Cookie 只在安全传输中发送；`HttpOnly` 阻止页面 JavaScript 直接读取它，降低某些脚本窃取风险；`SameSite` 控制跨站请求时是否附带 Cookie。`Domain` 和 `Path` 决定发送范围，过宽会扩大可接收 Cookie 的主机或路径。`Max-Age` 或 `Expires` 管理浏览器保存期限，不等于服务端会话一定仍有效。

HttpOnly 并不能让网站免于 XSS：恶意脚本虽然读不到 Cookie，仍可能在同源页面发起带 Cookie 的请求。Secure 也不等于防 CSRF。属性要组合使用，并由服务端执行真正的操作授权。

逐步推演

登录

服务器创建会话并通过 Set-Cookie 发送 ID。

正常请求

浏览器按域、路径和属性自动附带 Cookie。

跨站诱导

攻击页面尝试让浏览器带 Cookie 提交写请求。

服务端校验

验证会话、CSRF token、来源与业务授权。

CSRF 从哪里来

用户已登录银行站点，浏览器保存银行 Cookie。随后用户打开攻击者页面，页面诱导浏览器向银行发起转账请求；若浏览器自动附带 Cookie，而银行只看 Cookie 不看请求来源与防伪令牌，就可能把请求当成用户主动操作。攻击者通常读不到跨站响应，也仍可能造成写入副作用，这就是 CSRF 的关键。GET 不应承担转账这类写操作，否则链接或图片加载就可能触发。

SameSite=Lax 能限制某些跨站场景，但对具体顶级导航、方法和浏览器实现要按规范测试；Strict 更严格，也可能影响正常跨站跳转后的体验；None 用于需要跨站发送 Cookie 的场景，通常要求 Secure。不能把 SameSite 当作唯一防线，尤其业务确实需要跨站嵌入或存在同站子域风险时。

防护怎么组合

对修改状态的请求验证 CSRF token，令牌与用户会话绑定并在服务端校验；同时检查 Origin 或 Referer 等来源信号，在适当条件下拒绝跨站提交。对高风险动作还可要求重新认证或额外确认。不要只依赖自定义请求头，因为代理和跨域配置可能变化；也不要把 CSRF token 放在可被攻击页面轻易读取的位置。

CSRF 与 XSS 不能互相替代：如果攻击者已能在本域执行脚本，很多基于页面可读 token 的 CSRF 防护也可能被绕过。因此还需输出转义、CSP、依赖治理和最小权限。网络层 TLS 防窃听是基础，却不解决浏览器是否应自动替用户提交请求的问题。

登录与登出的生命周期

登录成功后服务器创建会话、设置 Cookie，后续请求校验会话；登出时应撤销服务端会话并让浏览器过期 Cookie。只在浏览器删除 Cookie 而服务端仍接受旧会话，已泄漏的 ID 可能继续可用；只撤销服务端会话而浏览器保留旧 Cookie，用户可能反复发送失效标识。会话续期、设备管理和强制下线应有明确策略。

多节点应用需要会话共享或可验证令牌的统一撤销方案，不能把会话只放在某台进程内而没有粘性路由或共享存储。高并发时 Session 存储的延迟和故障也会影响所有登录请求。

动手检查

在浏览器开发者工具里观察登录响应的 Set-Cookie，以及后续同站和跨站请求是否携带它；核对 Secure、HttpOnly、SameSite、Domain、Path 与过期时间。用两个不同用户、两个浏览器配置测试会话隔离。登出后重放旧会话请求，应被拒绝；修改权限后也要按业务要求及时生效。

CSRF 测试应在合法登录状态下，从不同站点发起修改请求，验证没有 token 或来源不符会被拒绝。不要仅以“攻击页面读不到响应”作为安全通过标准，关键是服务器有没有执行副作用。

自检

设置 HttpOnly 后，CSRF 就自动被阻止了吗？

不会。HttpOnly 主要阻止 JavaScript 直接读取 Cookie；浏览器仍可能自动在请求中携带它。
