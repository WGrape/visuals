业务系统 / 设备与连接

设备影子与业务状态协作

设备可能离线、消息可能重复或乱序；业务系统不能把“命令已发出”等同于“设备已执行”。

三种状态一条指令异常处理设计清单

01 / 期望状态、上报状态与业务状态不能混用

状态谁维护示例：远程开锁
期望状态（desired）服务端设备影子或控制平面授权用户希望门锁打开；记录目标版本与命令编号
上报状态（reported）设备实际观测，经消息上报门锁传感器报告“已打开”，附设备序号和采集时间
业务状态订单、工单或授权服务工单已批准、执行中、成功或失败；不能直接复制设备在线状态

“在线”不表示设备已执行，“已发送”也不表示门锁打开。设备影子保存最近可见的期望/上报状态，但必须标注时间与版本，不能把旧上报当成当前事实。

02 / 从业务命令到设备确认

  1. 校验业务确认工单、用户权限和设备归属，生成唯一命令 ID 与有效期；业务状态变为“待执行”。
  2. 可靠投递记录待发送命令，再经 Broker 下发。消息送达确认只是传输层信号，不是设备执行结果。
  3. 设备执行设备按命令 ID 去重，检查版本及有效期，执行后返回结果并上报实际状态。
  4. 状态收敛服务端匹配命令 ID，验证上报版本与结果，再更新工单；超时进入“待核实”，不能擅自标为成功。

MQTT 的 QoS 解决传输层投递语义，不能替代业务幂等或执行确认；协议基础见 MQTT 原理。

03 / 离线、乱序和重复时怎么办

离线

待执行命令设过期时间；设备重连后先同步最新期望状态，不能无条件重放所有旧命令。

乱序

用每台设备的单调版本或序列号判断新旧；晚到的“已锁”不能覆盖更新的“已开”报告。

重复

按命令 ID 在设备和服务端两端去重；ACK 丢失触发重试时，也不能执行两次有副作用的动作。

涉及支付或人身安全的动作不能仅凭“最后一次设备上报”认定完成，应结合传感器证据、人工确认或补偿流程；设备影子不是强一致数据库。

04 / 上线前检查

  • 定义工单/订单状态机，以及设备状态与业务状态的转换条件和负责方。
  • 记录命令 ID、版本、设备时间与服务端接收时间；明确离线过期与重试上限。
  • 测试断线重连、重复 ACK、乱序上报和命令执行成功但回执丢失。
  • 监控期望与上报长期不一致的设备，设置人工排障入口。

一句话：通信链路交付消息，状态协作证明业务动作是否真的完成；两者应分开设计。
