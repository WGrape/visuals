🌳 组合

让单个对象和一组对象用同一种方式被处理。

一句话记住文件和文件夹都能“求大小”；文件夹把子项大小相加。

01 · 从问题出发

为什么会需要这个模式？

报价单有商品和嵌套套餐；调用方为每层分别写递归分支很难维护。

购物车里可以放商品，也可以放包含商品的套餐。若计算总价时先判断“这是商品还是套餐”，再手写每层递归，新增一种容器会让调用点重新分支。

😵 直接写会怎样

function total(node):
  if node.type == "item": return node.price
  if node.type == "bundle":
    return sum(total(x) for x in node.children)

💡 关键转折

叶子和容器实现同一接口；容器递归委托给孩子。

把“求价格”定义为 Component 契约。叶子返回自己的值，容器把同一操作委托给孩子；递归自然发生。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

interface Component { totalPrice() }
class Item implements Component {
  totalPrice() { return this.price }
}
class Bundle implements Component {
  totalPrice() {
    return sum(child.totalPrice() for child in this.children)
  }
}
cart.totalPrice()

读代码时抓住三件事

  1. Component 定义所有节点共有的操作。
  2. Item 和 Bundle 都实现 totalPrice。
  3. Bundle 的 children 声明为 Component 列表，所以可装叶子也可装容器。

换个业务场景，还能认出来吗？

文件系统的 File.size 返回文件大小，Directory.size 累加子文件/子目录；权限系统的单权限和权限组也可形成树。别把只适用于目录的 add/remove 硬加给文件。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

业务天然呈树形，叶子和容器要执行同一操作

三个具体场景

  • 商品与嵌套套餐统一求价
  • 文件与文件夹统一求大小
  • 组织节点与部门统一统计人数

不适合或要小心

add/remove 不必强塞进叶子接口。要防止构造循环引用，否则递归可能无限进行。

避免循环引用；不要把容器专有的 add/remove 强塞给叶子

最容易混淆的相邻模式

模式真正的区别
装饰器也是递归包装，但通常一层包一个对象以叠加职责；组合容器可持有多个孩子，表达树的部分-整体关系。
迭代器负责遍历集合；组合定义集合的树结构与统一操作。

区分时问自己：一个容器会持有多个子节点，还是一层只包装一个对象？

落地前检查

  • 阻止循环引用，避免无限递归。
  • 明确空容器返回什么。
  • 子项变更后若缓存总价，需处理缓存失效。
06 · 自己说一遍

两道检验理解的小题

嵌套三层套餐为何仍能求总价？

每层只依赖 Component.totalPrice()；叶子返回价格，容器递归求和。

叶子需要实现 add(child) 吗？

不一定。只把真正共同的操作放入 Component；容器专有操作可留在 Bundle。

核心速览

一句话把对象组织成树，让「单个对象」和「组合对象」对调用方完全一致
核心树枝（Composite）和树叶（Leaf）实现同一个接口，树枝的方法内部递归调用孩子
直观例子文件系统：文件和目录都能被 ls、被统计大小、被删除
代价接口会变胖——叶子必须实现自己根本不支持的方法
组合模式：调用方眼里没有「树」，只有「组件」

一、最小实现

type Node interface { Size() int64 Print(indent string) } type File struct{ name string; size int64 } func (f *File) Size() int64 { return f.size } func (f *File) Print(ind string) { fmt.Println(ind + f.name) } type Dir struct{ name string; children []Node } func (d *Dir) Size() int64 { var s int64 for _, c := range d.children { s += c.Size() } // 递归是关键 return s } func (d *Dir) Print(ind string) { fmt.Println(ind + d.name + "/") for _, c := range d.children { c.Print(ind + " ") } } // 调用方完全不需要区分文件还是目录 root.Print("") // 打印整棵树 fmt.Println(root.Size())
递归就是组合模式的灵魂

树枝的操作 = 对自身处理 + 对所有孩子递归调用同一操作。一旦你写出这种递归，树形结构带来的复杂度就被彻底隐藏了。

二、透明式 vs 安全式

方式接口里放什么优点缺点
透明式Add/Remove/GetChild 都声明在 Component 里调用方完全不用类型判断叶子要实现无意义的方法，只能返回错误或 panic
安全式只在 Composite 里声明 Add/Remove叶子接口干净，编译期就能挡住误用调用方必须做类型断言，失去了透明性

《设计模式》原书推荐透明式，但工程实践里安全式更常见，因为「对一个文件调用 Add」应该在设计上就不可能，而不是到了运行期才报错。Go 里还常用第三种做法：接口只放共有行为，组合相关的操作放在具体类型上，调用方只在需要时断言。

三、和它长得很像的几个模式

模式结构目的区别
组合树让部分与整体一致对待重点是结构递归
装饰器链给对象逐层加职责只有一个真实对象，其余是包装
责任链链沿链传递请求直到被处理请求在链上传递，不是递归遍历
访问者任意结构给结构加新操作而不改类常与组合搭配，用来遍历树并做不同操作

五、深入自检

叶子必须实现 Add 吗？

取决于你选透明式还是安全式。透明式要求实现（通常返回错误）；安全式不要求。更推荐安全式，让类型系统替你挡住误用。

组合模式和「树」是绑定的吗？

是的。组合模式本质是「用树表达部分-整体关系并让接口统一」。如果结构不是树（比如是图、有环、有共享节点），递归就会出问题，需要额外的访问标记。

性能上要注意什么？

每次操作都递归遍历整棵子树，深度大时有栈风险、节点多时是 O(n)。常见优化：在节点上缓存 Size 这类聚合结果，并在子节点变更时失效缓存。

和访问者模式怎么配合？

组合负责「结构」，访问者负责「在结构上做不同操作」。当你需要给同一棵树支持「统计大小」「导出 JSON」「权限校验」等多种操作时，用访问者避免把逻辑都塞进节点类。

Go 里没有继承，组合模式怎么写？

用接口 + 组合（embedding）。定义一个接口，叶子和容器各自实现；容器内部持有 []接口 而不是具体类型。这比继承更简洁，也天然支持安全式。

记住一句叶子与树枝同接口，调用方只见树不见类型
灵魂树枝操作 = 自身 + 递归孩子
推荐写法安全式：Add 只在容器上
