协程原理：挂起、恢复与栈的归属

协程是用户态的可挂起函数。理解它的关键是搞清楚一件事：函数挂起时，那些还没执行完的状态存在哪。

协程与线程的本质区别

维度线程协程
调度者操作系统内核用户态运行时/调度器
切换成本需要陷入内核、保存完整上下文用户态跳转，成本低一到两个数量级
切换时机抢占式，任意指令处都可能被切走协作式，只在显式挂起点让出
默认栈大小通常 MB 级，创建时就占用通常 KB 级起步，可增长
数量级几百到几千几万到百万
并行能力多核真并行单线程内并发，需多线程才能并行

协程不是「更轻的线程」这么简单——更准确的说法是：协程把调度权从内核拿回到用户态，代价是失去了抢占能力，一个协程如果不主动让出就会阻塞整个线程。

挂起时状态存在哪：三种实现

每个协程有自己的栈

挂起时栈原封不动地保留，恢复时把栈指针换回去即可。优点：可以在任意嵌套深度挂起，代码写法接近同步。代价：每个协程要预留栈空间，数量大时内存可观。Go 的 goroutine、Lua 的 coroutine 属此类。

编译成状态机

编译器把 async 函数改写成状态机对象，局部变量成为对象字段，挂起点变成状态编号。优点：极省内存（只有一个小对象）。代价：只能在本函数内挂起，调用另一个挂起函数必须 await 传递上去。Rust / Python / JS 的 async 属此类。

不是没有状态，是没有独立调用栈

无栈协程挂起时，它的调用者栈帧必须一路返回到事件循环。这就是为什么 async 函数里不能随便在深层调用栈中挂起——必须显式 await 一路往上传递。

async 会「传染」

无栈协程里，调用 async 函数的函数也必须变成 async，直到某个能 await 的入口。这就是常说的 function coloring 问题。有栈协程没有这个问题。

调度：谁决定下一个跑谁

协程自己不管调度，运行时需要一个调度器把就绪的协程分配到工作线程上执行。常见模型是 M:N 调度：M 个协程跑在 N 个 OS 线程上。

事件调度器做什么
协程发起 IO 并挂起把它从运行队列移除，注册 IO 完成回调
IO 就绪把对应协程放回就绪队列
协程阻塞式系统调用可能阻塞整个工作线程 → 需要把其他协程挪走或补充线程
协程执行计算很久不让出抢占式调度器会在安全点强制切换；协作式则会被卡住

协程不是万能的

场景协程表现原因
大量高并发 IO（网络请求、RPC）非常适合大部分时间在等 IO，切换成本低，数量可以很大
CPU 密集计算无收益，甚至更差没有 IO 可等，切换只增加开销；真并行要靠多核
阻塞式系统调用 / 同步库会拖垮整个线程协作式调度下不主动让出就会卡住其他协程
需要真并行要和线程/进程配合协程解决并发（concurrency），不直接解决并行（parallelism）

最后一条最关键：协程让你「同时处理很多件事」，但不让你「同时做很多件事」。想利用多核，仍然需要多线程或进程，协程只是让每个线程上的等待时间被充分利用。

常见故障模式

症状可能原因处理
并发上不去，CPU 也不忙混入了阻塞式调用（同步 IO、阻塞锁）换成异步库，或把阻塞调用丢到专门的线程池
协程数量暴涨导致 OOM无上限地创建协程，或协程泄漏（永远等不到唤醒）限制并发数、给等待加超时、检查是否有未取消的等待
单个慢请求拖慢整体协程内长时间计算不让出主动让出点，或把 CPU 密集部分移到独立线程池
panic/exception 丢失协程里的异常没被捕获且无人等待结果确保每个协程都有错误处理路径，不要「发射后不管」
取消不生效子协程没接收取消信号取消必须沿调用链传递，IO 也要支持取消

边界与误区

「协程开销极小所以可以随便开」是危险的。协程便宜是相对线程而言，每个协程仍有栈和状态开销，而且泄漏的协程会一直占着它所引用的所有对象。实践中仍要用信号量/工作池限制并发规模，并给所有等待加超时。

协程的实现机制：挂起点与状态保存

协程的本质是可以被挂起和恢复的函数。关键问题是：挂起时如何保存执行状态？

类型状态保存在哪是否能跨函数挂起代表
有栈协程独立的栈空间能（任意深度调用中挂起）Go goroutine、Lua
无栈协程状态机/闭包对象只能在顶层 await 处挂起Python async、C++20、Rust

状态机本质

# Python 的协程在编译后变成了什么？
import dis

async def fetch():
    await asyncio.sleep(1)
    return 42

# 查看字节码会发现：协程对象带有 SEND / ASYNC_GEN 等指令
# 本质：编译器把 async 函数重写成一个<strong>状态机</strong>，
#       每个 await 是一个状态，局部变量存在协程对象的帧里

# 等价的手动状态机（示意）：
class FetchCoroutine:
    def __init__(self): self.state = 0
    def send(self, value):
        if self.state == 0:
            self.state = 1
            return asyncio.sleep(1)      # 返回「要等待的东西」
        if self.state == 1:
            self.state = 2
            return 42                    # 完成
        raise StopIteration

无栈协程的「传染性」：因为只能在顶层 await 挂起，所以调用链上每一层都必须是 async——这就是 async def 会「传染」的原因。有栈协程（Go）没这个问题，普通函数里也能被挂起。

事件循环：协程的调度者

事件循环伪代码

# 事件循环的核心伪代码
while True:
    # 1) 执行所有就绪的协程任务
    for task in ready_queue:
        result = task.step()        # 推进到下一个 await
        if result is IO:
            io_waiting[result.fd] = task    # 挂起，等 IO
        elif result is DONE:
            finished.append(task)

    # 2) 用 epoll/select 等待 IO 就绪（<strong>这里会阻塞</strong>，但只阻塞一次）
    ready_fds = epoll_wait(timeout=next_timer_deadline)
    for fd in ready_fds:
        ready_queue.append(io_waiting.pop(fd))

    # 3) 处理到期的定时器
    for t in expired_timers:
        ready_queue.append(t.task)
关键点说明
单线程所有协程在一个线程里跑，不存在数据竞争
一次阻塞epoll_wait 是唯一的阻塞点，不会因单个 IO 卡住
协作式协程必须主动 await 才让出，否则一直占用
回调转成同步写法await 让异步代码看起来像同步，错误处理也变简单

为什么单线程事件循环没有数据竞争：因为协程之间只在 await 处切换，而 await 是你显式写出来的。在没有 await 的代码段里，不会有其他协程插入执行——所以那段代码天然是原子的。这是 async 编程比多线程容易得多的根本原因。

性能数字与实际收益

操作耗时对比
函数调用约 10 ns基准
协程切换约 100~200 ns比函数调用贵 10~20 倍
线程切换约 1~2 μs比协程贵 10 倍
进程切换约 5~10 μs比协程贵 50 倍

结论：协程切换虽比函数调用贵，但远低于线程切换，且内存占用低两个数量级。所以它适合IO 密集 + 高并发。但要清醒：await 不是免费的——在极热的内层循环里，异步函数调用的开销会累积，所以不要把每个小函数都改成 async。

性能边界

# 实测：什么时候协程反而更慢
#   场景：纯计算，无 IO
#   同步版：  直接调用 100 万次     → 约 0.05 s
#   异步版：  await 100 万次        → 约 0.5 s（<strong>慢 10 倍</strong>）
#
# 原因：每次 await 都要经过事件循环调度、创建/推进协程状态
#       而纯计算没有任何等待时间可以「让给」别人
#
# 判据：
#   有真实 IO 等待      → async 收益巨大
#   纯 CPU 计算         → async 只有开销，应走多进程

自检 Q&A

Q：async def 定义后不 await 会怎样？

A：什么都不会执行，而且会收到 RuntimeWarning: coroutine was never awaited。调用 async def 函数只是创建协程对象，不执行函数体——必须 await、asyncio.run() 或 create_task() 才会真正运行。这是新手最常见的困惑，也是「代码没报错但也没执行」的经典原因。

Q：create_task 和直接 await 有什么区别？

A：await 是串行，create_task 是并发。await a(); await b() 会等 a 完成再做 b，总耗时 = a + b；t1=create_task(a()); t2=create_task(b()); await t1; await t2 让两者并发，总耗时 = max(a, b)。这是 asyncio 最重要的性能技巧——把独立的等待操作用 create_task 或 gather 并发起来。

Q：为什么我的 asyncio 程序和多线程一样慢？

A：大概率是某个地方阻塞了事件循环。常见来源——① 用了同步的 IO 库（requests 而不是 aiohttp）；② 混入了 CPU 密集计算（应丢到 run_in_executor）；③ 用了 time.sleep() 而非 asyncio.sleep()。诊断方法：加一行监控，看事件循环的最大延迟（loop.slow_callback_duration，默认 100 ms 会告警），超过说明有阻塞。

Q：Go 的 goroutine 也算协程吗，为什么写法这么不同？

A：算，但它是有栈协程 + 抢占式调度。Go 的 go f() 不需要在调用链上标记 async，因为每个 goroutine 有独立可增长的栈，可以在任意位置被运行时挂起。Python 的无栈协程只能在显式的 await 处让出，所以必须层层标记。代价对比：Go 的运行时更复杂（要管理栈增长与抢占），但写起来自然；Python 的实现简单，但要遵守「async 传染」的约束。

自检

为什么在协程里调用了阻塞式 IO 会拖垮整个服务？

协程是协作式调度，只有主动让出（await / yield / 发起异步 IO）时调度器才能切换。阻塞式 IO 会一直占住底层 OS 线程不让出，而该线程上可能还挂着成百上千个就绪的协程，它们全部得不到执行。
