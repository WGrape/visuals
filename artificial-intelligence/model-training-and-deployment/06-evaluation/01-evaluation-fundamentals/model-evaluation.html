模型评估
每个阶段训完，怎么知道"好不好"

数据清洗、分词、预训练、SFT、对齐……每一站结束都要验收。评估不只是"看个准确率"——它横跨能力、安全、对齐、效率多个维度，而且不同阶段用的尺子完全不同。这一页把整章的"评估"收口讲清。

第 1 步 · 为什么

评估不是"训完看一眼"

训练的目标函数（如交叉熵）和"模型到底好不好用"之间，隔着一道鸿沟。损失低 ≠ 回答好。评估要回答的是：能力够不够、安不安全、符不符合人类偏好、成本扛不扛得住。

防翻车
灾难性遗忘、对齐税（变乖但变笨）、奖励黑客，都靠评估提前发现。
做取舍
SFT 数据配比、RL 奖励设计、量化精度，都需要评估来比较"哪版更好"。
一个经典误区：只在训练集分布内看指标，模型可能只是"背过了"。评估必须用held-out（留出）数据 + 多维度的真实任务。

不同阶段，用不同的尺子

整章旅程每走一站，验收指标都不一样。下面这张表是"训练→评估"的对照地图：

第 3 步 · 四个维度

评估要看的四个维度

① 能力 Capability
知识、推理、代码、长文本。看基准分，也看留出任务的真实表现。
② 安全 Safety
有害内容、偏见、越狱鲁棒性。红队测试 + 毒性评测集。
③ 对齐 Alignment
是否有用、诚实、无害，合不合人类偏好（MT-Bench / 胜率）。
④ 效率 Efficiency
延迟、吞吐、显存、成本（部署阶段重点，见 推理指标与成本）。
四维度常互相打架：对齐太狠会掉能力（"对齐税"）；量化太狠会掉精度。评估的价值就是把这些权衡摆到台面上，帮你在批次/精度/数据上做决策。
第 4 步 · 怎么做

评估的方法论

  • 自动评测：客观题（选择题、可验证答案）跑脚本算分；开放题用 LLM 当裁判（LLM-as-Judge）给偏好分（MT-Bench 思路）。快、可复现，但裁判模型本身有偏好偏差。
  • 人工评测：抽样人工打分，质量最高但慢且贵，常用于对齐阶段的金标准与裁判校准。
  • 留出集 held-out：绝不拿训练数据当考题，防止"背过"式虚高。
  • 排行榜 Leaderboard：LMSYS Chatbot Arena、OpenCompass 等提供横向可比分数，但需注意基准是否已被"刷分"污染。
  • 红队 Red Teaming：主动构造攻击 / 越狱，测安全边界。
常见坑：基准过拟合（为刷分调模型，换批数据就崩）、长度偏好（裁判偏爱更长的回答，模型学会"写废话"）、只看平均分掩盖了某些关键能力塌方。应对：多维 + 人工抽检 + 留出。
收尾 · 一句话带走

所以，模型评估是什么

模型评估 = 在每个训练阶段结束后，用"该阶段专属的尺子"验收能力/安全/对齐/效率。 预训练看 PPL、SFT 看指令基准、对齐看 MT-Bench、推理看 AIME/GSM8K、 部署看延迟与成本。它横跨四个维度且常互相权衡， 一句话：训练造出"会不会"，评估回答"好不好、安不安全、值不值"——缺一不可。

相关阅读：训练基础 · 后训练全景 · RL 强化学习后训练 · 推理指标与成本

各阶段评估什么：指标与阈值

评估不是只在最后做一次，而是每个阶段都有验收点。把「什么时候测、用什么测、多少分算过」写成表，才能做到可回退。

阶段评估什么常用指标典型阈值 / 判据
预训练后（基座）通用语言能力、知识PPL、MMLU、C-Eval、GSM8K、HumanEval同类规模对比，不设绝对线
SFT 后指令跟随、格式人工盲评胜率、MT-Bench、IFEval（指令遵循率）IFEval >70%；胜率 >50%
对齐后（DPO/RLHF）有用性 + 安全性胜率（vs SFT）、有害内容率、拒绝率胜率 >60%；过拒率 <10%
能力专项数学/代码/长文本GSM8K、MATH、HumanEval、大海捞针热力图按业务定
上线前端到端业务效果业务指标（转化、满意度、人工介入率）A/B 测试，看长期留存
上线后漂移与退化线上采样评分、用户反馈率设定告警线

指标计算

# 分类/生成类指标怎么算（别只看accuracy）
from sklearn.metrics import accuracy_score, f1_score, roc_auc_score

# 分类
accuracy_score(y, p)               # 类别不平衡时不可靠
f1_score(y, p, average='macro')    # 各类别等权，更公平
roc_auc_score(y, prob)             # 排序质量，与阈值无关

# 生成类（LLM 主流三档）
#   ① 精确匹配 EM：完全答对才算对（最严格，适合有唯一答案的题）
#   ② 包含匹配：答案出现在生成里（宽松，易被「啰嗦」刷分）
#   ③ <b>模型裁判 LLM-as-Judge</b>：让强模型按 rubric 打分（1~5 分或 A/B 胜负）
#      注意：要给<b>评分标准</b>（rubric）+ 打乱顺序 + 多次采样取平均
#      GPT-4 做裁判与人类的一致率约 80%，够用但有偏差（偏好更长、更靠前的答案）

# 困惑度 PPL（语言模型的基础指标）
import math
ppl = math.exp(sum(-logprobs) / n_tokens)
#   注意：PPL 只在<b>同 tokenizer、同数据集</b>之间可比，跨模型无意义

最重要的一条：离线指标涨 ≠ 线上效果好。因为离线测的是「拟合历史数据的能力」，而线上是闭环系统（模型改变用户行为 → 用户行为变成新样本）。所以任何模型上线都必须过 A/B 测试，且要看长期指标（7 日/30 日留存），而不只是当天的点击率。

评测集设计与常见陷阱

陷阱表现解法
数据泄露测试集出现在训练数据里，分数虚高用 held-out 集；做 n-gram 重叠检测；用时间切分
过拟合评测集MT-Bench 分数涨，人觉得变差保留一份从不看的最终测试集；定期换新题
只看平均分长尾 case 全挂但平均好看按难度/类别分组统计；看 P10 而非均值
只看单轮多轮对话能力没测到加多轮评测集
裁判偏差LLM 裁判偏好长答案、偏好先出现的随机化顺序 + 双向评测（A/B 和 B/A 各测一次）
样本太少500 题上差 2 个点，可能是噪声做显著性检验；样本量至少几百到上千

评测集与显著性

# 评测集构建清单（可直接套）
#   1) 来源：真实用户 query 采样（最重要）+ 人工构造的边界 case
#   2) 分层：按业务场景分层（如咨询/下单/投诉各 100 条）
#   3) 难度：简单/中等/困难 各占一定比例，困难 case 单独看
#   4) 参考答案：每题配 rubric（评分标准），而不是只有一个「标准答案」
#   5) 规模：统计上要能区分 2~3 个点的差异 -> 通常 >= 300 条
#   6) 版本：每次改评测集要留版本，否则历史分数不可比
#   7) 保密：最终测试集不能进入训练/调优的反馈循环

# 显著性检验（别凭感觉说「提升了」）
from scipy.stats import bootstrap
# 或简单点：对每条样本算「新模型赢/平/输」，做二项检验
#   1000 条样本，胜 520 平 180 输 300：
#   净胜率 = (520-300)/1000 = 22%  -> 显著（样本够大）
#   100 条样本，胜 55 输 45：净胜 10% -> 不显著（p 值远大于 0.05）
为什么 LLM 评测这么难？

三个原因：① 答案不唯一——「写一首关于春天的诗」没有标准答案，无法用精确匹配；② 维度多——有用性、安全性、事实性、流畅度、指令遵循，这些维度可能互相冲突（更安全就更保守）；③ 分布漂移——评测集很快被「训练进去」或不再代表真实分布。所以现在的共识是多指标 + 人工抽检 + 线上 A/B 三管齐下，任何单一指标都不可信。

过拒绝（over-refusal）是什么，怎么测？

模型把正常请求也当成有害请求拒绝掉（如「如何制作炸弹」该拒，但「如何制作蛋糕」也拒就是过拒）。测法：构造一批看似敏感但实际无害的 query（如「kill a process」「how to kill time」），统计被拒比例。健康值 <10%。过拒是安全对齐做过了头的典型症状，会严重伤害体验——这也是为什么对齐时要同时看「有害内容率」和「过拒率」两条曲线。

小样本（几十条）能不能评估？

能做定性判断（明显变好/变坏），不能做定量结论（提升 3% 不可信）。经验：① <100 条只能看有没有明显退步（回归测试）；② 300~1000 条能区分 5 个点以上的差异；③ 要区分 1~2 个点需要数千条 + 显著性检验。所以小样本评测的正确用法是做红线测试（确保不退化），而不是用来排名。

阶段必看指标合格判据只看它会漏掉什么
预训练loss 曲线、困惑度平滑下降且无突刺下游能力
继续预训练领域困惑度、原能力保留领域降、通用不退化灾难性遗忘

# 1) 困惑度（perplexity）：语言模型的基础体检指标
import math
def perplexity(total_nll, total_tokens):
    # total_nll: 所有 token 的负对数似然之和
    return math.exp(total_nll / total_tokens)
# 判读：同 tokenizer、同数据集下才能横向比较；
#   换了 tokenizer 或数据集，困惑度数值没有可比性

评估样本量怎么定：想检测出 5 个百分点的差异，通常需要数百到上千条样本；样本太少（几十条）时，看到的差异大概率是噪声。这就是为什么「改一点就涨 3 分」往往不可信。

第三层 · 六个高频问题

  • 测试集污染：评估数据出现在训练集里，分数虚高；用未公开数据或留出集复核，并做去重检查。
  • 只报平均分：生成任务方差大，必须同时报标准差或置信区间，否则差异不可判断。
  • 只看自动指标：BLEU/ROUGE 与人工感受相关性有限；关键场景必须有人评环节。
  • 忽略长度偏置：模型靠写更长来赢，胜率虚高；评估时要做长度对照。
  • 评估集长期不变：模型会隐式过拟合到评估集；定期更换或补充新样本。
  • 不看失败案例：平均分掩盖了长尾；每次评估都要抽样看 20~50 条失败案例并归类。

一条实用规则：每次改动只改一个变量，评估至少跑两次。同时改多个超参又只跑一次，得到的结论基本没有参考价值。

第四层 · 为什么评估这么难

为什么不能只用一个分数衡量模型？

因为「好」是多维的：正确性、安全性、有用性、简洁性彼此可能冲突。单一分数会诱导模型在某个维度上刷分（例如靠写长取胜）。

自动评估和人工评估怎么配合？

自动评估用于高频回归（每次改动都跑，快速发现退化）；人工评估用于关键节点（版本发布前、重大改动后），样本不必多但要有代表性。

评估集应该多大？

取决于要检测的差异大小：差异越大需要的样本越少。作为起点，分类类 500~1000 条、生成类 200~500 条，并始终报方差。
