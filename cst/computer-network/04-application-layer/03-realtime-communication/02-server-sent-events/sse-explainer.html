此处用 HTTP/1.1 chunked 展示增量传输；HTTP/2 则使用 DATA 帧

📋 SSE 事件格式

event: message data: {"time": "14:30:25", "price": 156.78} id: 1001 event: message data: {"time": "14:30:30", "price": 157.12} id: 1002 event: close data: 连接关闭

每条消息以 data: 开头，以 \n\n 结尾。
可以指定 event: 类型（如 message、close、error），id: 用于断线重连。

🔀 第三阶段：连接复用与效率优化

SSE 在一条保持打开的 HTTP 响应上持续发送事件。HTTP/1.1 与 HTTP/2 对并行请求的承载方式不同，SSE 的事件格式不依赖其中一种。

SSE 协议细节与字段

SSE 就是一个永不关闭的 HTTP 响应：Content-Type: text/event-stream，然后按固定格式一行行往下写。协议简单到可以手写。

协议格式

# 最小可用的 SSE 响应
HTTP/1.1 200 OK
Content-Type: text/event-stream; charset=utf-8
Cache-Control: no-cache
Connection: keep-alive
X-Accel-Buffering: no          # 关键：禁止 nginx 缓冲

# 帧格式（每个字段一行，以空行结束一个事件）
id: 12345\n
event: message\n              # 可选，自定义事件名，默认 message
data: {"text":"hello"}\n      # 可多行，会自动用 \n 拼接
retry: 3000\n                 # 可选，重连间隔（毫秒），客户端会遵守
\n                            # 空行 = 一个事件结束

# 心跳注释行（防代理超时断连，必须每隔 15~30s 发一次）
: keep-alive\n\n

# 多行 data 会被客户端合并成 "line1\nline2"
data: line1\n
data: line2\n
\n
字段作用客户端行为
data消息体（可多行）多行用 \n 拼接后触发事件
event事件名需要 addEventListener(event) 才能收到
id事件序号断线重连时自动带上 Last-Event-ID 请求头
retry重连间隔（ms）覆盖浏览器默认（Chrome 约 3s）
: 注释心跳浏览器忽略，仅保持连接

Go 服务端实现

// 服务端（Go 标准库，无任何依赖）
func sse(w http.ResponseWriter, r *http.Request) {
    w.Header().Set("Content-Type", "text/event-stream")
    w.Header().Set("Cache-Control", "no-cache")
    w.Header().Set("X-Accel-Buffering", "no")
    flusher, _ := w.(http.Flusher)

    lastID := r.Header.Get("Last-Event-ID")   // 断线重连：从这之后补发
    id := parseOr(lastID, 0)

    ticker := time.NewTicker(15 * time.Second)  // 心跳
    defer ticker.Stop()
    for {
        select {
        case <-r.Context().Done():
            return                              // 客户端断开，退出
        case msg := <-broker:
            id++
            fmt.Fprintf(w, "id: %d\nevent: msg\ndata: %s\n\n", id, msg)
            flusher.Flush()                     // 必须 flush！
        case <-ticker.C:
            fmt.Fprint(w, ": ping\n\n")         // 心跳注释
            flusher.Flush()
        }
    }
}

两个最常踩的坑：① 忘记 Flush()——响应被缓冲在 Go/框架里，客户端一条都收不到，这是「SSE 不工作」的第一原因；② nginx 缓冲——默认会攒够 4KB 或 60s 才下发，必须加 X-Accel-Buffering: no 或 nginx 里配 proxy_buffering off; proxy_read_timeout 3600s;。

两种客户端写法

// 客户端：原生 EventSource（自动重连，最省事）
const es = new EventSource('/api/stream');
es.addEventListener('msg', e => console.log(e.lastEventId, JSON.parse(e.data)));
es.onerror = e => console.log('state:', es.readyState);  // 0连接中 1打开 2关闭
// 关闭：es.close()

// 客户端：fetch + ReadableStream（需要 POST / 自定义 header 时用这个）
const res = await fetch('/api/stream', { method: 'POST', body: JSON.stringify(q) });
const reader = res.body.getReader();
const dec = new TextDecoder();
let buf = '';
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  buf += dec.decode(value, { stream: true });
  const parts = buf.split('\n\n');          // 按空行切分事件
  buf = parts.pop();
  for (const p of parts) {
    const data = p.split('\n').filter(l => l.startsWith('data:'))
                  .map(l => l.slice(5).trim()).join('\n');
    if (data) handle(data);
  }
}
  • HTTP/1.1 的 6 连接限制：同一域名浏览器最多 6 个并发连接。开一个 SSE 就占掉 1 个，页面若有多个 SSE 会互相阻塞。上 HTTP/2 就解决了（多路复用，单连接承载多流）——这也是 SSE 在现代部署中的标准前提。
  • EventSource 不能发 POST / 自定义头：需要携带复杂请求参数时改用 fetch + ReadableStream 自己解析（如上代码），代价是要自己处理重连。
  • 服务端要感知断开：Go 用 r.Context().Done()，Node 用 res.on('close')。否则客户端关了页面，goroutine/连接还在跑，几小时就攒出资源泄漏。
  • 背压：客户端读得慢、服务端一直写，会撑爆缓冲区。生产实现要做丢弃策略（如只保留最新 N 条）或暂停生成。
LLM 流式输出为什么普遍用 SSE 而不是 WebSocket？

因为场景是纯粹的单向推送：客户端发一次请求，服务端持续吐 token。SSE 的三个优势正中需求：① 基于 HTTP，鉴权/Cookie/限流/日志全复用现有网关；② 浏览器原生自动重连 + Last-Event-ID 续传；③ 实现极简（几十行）。WebSocket 的双向能力在这里完全用不上，反而多了握手、心跳、重连三件事要自己写。

SSE 断线后会丢数据吗？

用原生 EventSource 不会丢（前提是服务端实现了 id + Last-Event-ID）：浏览器重连时会自动带上最后收到的事件 ID，服务端据此补发。这是 SSE 相对裸 WebSocket 的隐藏优势。若用 fetch 自定义实现，就得自己维护这个 ID 并在重连时传给服务端。

什么时候必须用 WebSocket？

三个条件满足任一：① 客户端要高频向服务端推（聊天输入、协同编辑的光标位置、游戏操作）；② 要传二进制（音视频帧、protobuf）；③ 需要极低且稳定的往返延迟（WebSocket 帧头只有 2~14 字节，比 HTTP 每次都带完整头省得多）。除此之外优先考虑 SSE。
