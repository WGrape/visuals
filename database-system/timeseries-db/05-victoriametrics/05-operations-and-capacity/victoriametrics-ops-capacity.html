VictoriaMetrics 迁移、容量与排障

用真实时间线规模计算内存磁盘，并规划迁移验证与回滚。

VictoriaMetrics

05落地要点

  1. Prometheus 侧保留期可以设短（比如几小时到一两天），本地只做热数据，历史全在 VictoriaMetrics。但要注意本地保留太短时，远端故障期间的数据就真的没了。
  2. 监控 remote_write 本身：队列堆积、写入失败率、落后程度。远端写入是异步的，静默丢数是这类架构最常见的坑。
  3. 降采样：长期数据用降采样保留，原始精度只留近期。这是控制成本最有效的手段。
  4. 基数治理照样要做：换存储不会让高基数变便宜，只是让同样的基数更便宜。user_id 当 label 在任何时序库里都是错的。
  5. 先小范围灰度：把一部分 job 的 remote_write 指向 VictoriaMetrics，对比两边查询结果一致后再全量切。
版本与协议相关提示：组件名称、支持的写入协议、MetricsQL 函数集合、降采样配置方式都随版本演进。请以你使用版本的官方文档为准。

关键参数与默认值的量化对照

下列参数是单机版/集群版最常用的落地开关，默认值决定是否踩坑：

参数默认值作用与调优要点
-retentionPeriod1（月）保留期，支持 d/w/y。只能延长不能缩短：设小了不会立刻删旧数据
-memory.allowedPercent60允许占用主机/容器内存的百分比，容器里按 limit 计算
-search.maxUniqueTimeseries300000单条查询可扫描的序列数上限，超限直接报错而非慢查询
-search.maxPointsPerSeries30000单序列返回点数上限，长区间查询需先降采样
-search.maxQueryDuration30s查询超时，被中断的查询仍计费 CPU
-search.maxQueueDuration10s并发打满时排队上限，超过直接拒绝
-maxLabelsPerTimeseries30单条序列 label 数上限，高基数 label 会被丢弃
-dedup.minScrapeInterval0（关闭）设为 scrape_interval 可去掉重复抓取的样本
-insert.maxQueueDuration60s写入队列缓冲时长，调大可扛短暂尖峰但吃内存

集群版同名参数要分别加到 vminsert/vmselect/vmstorage 上，只有 vmstorage 侧的 -retentionPeriod 决定数据生命周期。

部署、迁移与验证的可执行命令

部署与迁移

# 单机版：立即能跑的最小部署（数据落 ./vm-data）
docker run -d --name vm -p 8428:8428 \
  -v $(pwd)/vm-data:/victoria-metrics-data \
  victoriametrics/victoria-metrics:v1.102.0 \
  -retentionPeriod=12 -memory.allowedPercent=70 \
  -search.maxUniqueTimeseries=1000000

# Prometheus 侧把样本转发过去
remote_write:
  - url: http://vm:8428/api/v1/write
    queue_config:
      max_samples_per_send: 10000      # 单请求样本数
      max_shards: 30                   # 并发分片
      capacity: 100000                 # 队列容量（内存缓冲）
      min_backoff: 30ms
      max_backoff: 100ms

# 从 Prometheus 本地存储迁历史数据（限速避免打爆写入）
./vmctl prometheus --prom-snapshot=/path/to/snap \
  --vm-addr=http://vm:8428 --vm-concurrency=4 --vm-batch-size=500000

验证与运维

# 看写入健康度：活跃序列数、每秒写入点数
curl -s http://vm:8428/api/v1/status/tsdb | python3 -m json.tool

# 查询是否触碰上限（返回 422 且带 limits 字样即为超限）
curl -s 'http://vm:8428/api/v1/query_range?query=up&start=-1h&end=now&step=60'

# 按 label 删除序列（先 dryRun=1 确认影响面）
curl -s 'http://vm:8428/api/v1/admin/tsdb/delete_series?match[]={job="old"}&dryRun=1'

# 打快照并备份（快照是硬链接，几乎不占额外空间）
curl -s http://vm:8428/snapshot/create > snap.json
curl -s 'http://vm:8428/api/v1/export?match[]={__name__=~".+"}' -o backup.jsonl

容量估算：从序列数推内存和磁盘

容量可以按下面两条公式粗算，误差通常在一个数量级内：

项目估算公式示例
内存活跃序列数 × 0.5~1 KB + 查询峰值缓存100 万活跃序列约 0.5~1 GB 常驻，复杂聚合查询另加缓存
磁盘样本点总数 × 1~2 字节（压缩后）100 万序列 × 30s 采样 = 2.88 亿点/天 ≈ 0.4~0.6 GB/天
点速率活跃序列数 ÷ 采样间隔100 万序列 / 15s ≈ 6.7 万点/秒
查询代价扫描序列数 × 时间跨度点数30 万序列 × 1 天(2880 点) = 8.6 亿点，必须降采样
  • 先压测再定规格：用真实 remote_write 灌 24 小时，读 /api/v1/status/tsdb 的序列数与磁盘。
  • 保留期与磁盘线性相关：保留期从 1 个月延长到 12 个月，磁盘需求约 ×12。
  • 降采样是查询侧的救星：集群版可对超过 -downsampling.period 的数据做聚合，历史查询扫的点数下降 1~2 个数量级。

排障清单：症状 → 原因 → 动作

症状最可能的原因处理动作
写入返回 429 / 队列满并发或批太小，队列积压调大 max_shards 与 capacity；或 -insert.maxQueueDuration 放宽
查询报 too many timeserieslabel 基数过高或未加范围限定加 job/instance 过滤；或提高 -search.maxUniqueTimeseries
改小保留期后磁盘没降保留期收缩只影响新写入确认 -retentionPeriod 生效；需要立刻回收才删序列
容器被 OOM killlimit 小于 -memory.allowedPercent 推算值把 limit 提到估算内存的 1.5 倍，或调低该百分比
Grafana 面板变慢长区间原始点扫描用 rate() 聚合 + 降采样；避免 step 小于采集间隔
数据出现重复/跳变多副本 Prometheus 同时写设 -dedup.minScrapeInterval = 抓取间隔

深入自检

把 -retentionPeriod 从 12 改成 1，磁盘会立刻释放吗？

不会。保留期收缩只对新写入生效，已有数据仍按旧策略保留。要立刻回收空间必须显式删除序列，或重建实例并导入需要保留的数据。

单机版什么时候必须换集群版？

三个信号：活跃序列数超过单机内存能承载的量级、写入点速率持续打满单机 CPU、或需要写入与查询分别扩容/多租户隔离。只因为“想做HA”不必上集群版——单机版可用双写 + 双读实现高可用。

为什么 remote_write 已经通了，Grafana 查不到数据？

先确认查询走的是 VM 的 /api/v1/query（PromQL 兼容）。常见坑是数据源填了 Prometheus 端口、查询时间范围超出保留期、或 -search.maxPointsPerSeries 截断返回。

VictoriaMetrics 的 MetricsQL 相对 PromQL 多了什么实用能力？

典型包括 rollup_* / decrease_over_time 等窗口聚合、负 offset 与更宽松的时间语法、keep_metric_names 保留指标名。写法与 PromQL 不完全等价，迁移前应对关键告警规则逐条验证。

如何验证迁移后数据没丢？

对比两端的活跃序列数与关键指标在重叠时间窗的采样点数：在原 Prometheus 与新 VM 上跑同一条 count_over_time，差异应在 1% 以内（抓取抖动导致）。
