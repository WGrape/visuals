01scrape 配置与抓取

Prometheus 主动 pull 各 target 的 /metrics，配置在 prometheus.yml 的 scrape_configs。

global:
  scrape_interval: 15s
  evaluation_interval: 15s

scrape_configs:
  - job_name: 'node'
    static_configs:
      - targets: ['10.0.0.1:9100', '10.0.0.2:9100']
  - job_name: 'api'
    kubernetes_sd_configs:        # 用服务发现，免手动列 IP
      - role: pod
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        regex: "true"
        action: keep
要点：拉模型下 target 要暴露 /metrics；target 挂了 Prometheus 自己发现，不用 target 反向注册——这也是它比 push 模型易运维的原因。

02relabel_configs 实战

relabel 在抓取前改写/过滤 target 的 label 和地址，是 Prometheus 配置最灵活也最难的部分。

action作用
keep只保留匹配 regex 的 target
drop丢弃匹配 regex 的 target
replace用 regex 提取并改写 label 值
labelmap把匹配到的源 label 映射成新 label
hashmod按 hash 分片，配合分片抓取
# 只抓 annotation 标了 scrape=true 的 pod，并把 pod 名写进 instance
relabel_configs:
  - source_labels: [__meta_kubernetes_pod_name]
    target_label: pod
    action: replace
  - source_labels: [__address__]
    target_label: __address__
    replacement: '$1:8080'   # 改写抓取端口

03常用 PromQL

PromQL 是查询语言，下面几句覆盖 80% 的监控需求。

# 过去 5 分钟 QPS
sum(rate(http_requests_total[5m]))

# P99 延迟（histogram 必须 _bucket 有 le 标签）
histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket[5m])) by (le))

# 节点内存使用率
1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes

# 错误率
sum(rate(http_requests_total{code=~"5.."}[5m])) / sum(rate(http_requests_total[5m]))

# up 为 0 的实例（挂了）
up == 0
要点：rate() 必须作用在 counter 上且区间不小于 scrape 间隔两倍；histogram_quantile 的 by (le) 不能漏，否则跨实例聚合无意义。

04Recording Rule 与告警

高频聚合预计算成新时间序列，仪表盘和告警直接引用，降低查询压力。

groups:
- name: example
  rules:
  - record: job:http_instances:sum
    expr: sum(http_requests_total) by (job)
  - alert: InstanceDown
    expr: up == 0
    for: 1m
    labels: {severity: page}
    annotations:
      summary: "{{ $labels.instance }} 已 down 1 分钟
问：rate 和 irate 区别？

rate 算区间平均速率，平滑抗抖动；irate 只看区间最后两个点，更灵敏但更跳。看趋势用 rate，看瞬时尖刺用 irate。
