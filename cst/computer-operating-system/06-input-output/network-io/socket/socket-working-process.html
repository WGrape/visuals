①先给结论：整个过程里一共出现「几个 Socket」

一次 TCP 通信，从头到尾在两个进程里共出现这些 Socket：

🖥 服务端：1 个监听 Socket

socket() → bind() → listen() 得到，全程只有这一个，fd 不变（如 fd=3）。它不传业务数据，只负责「接客」。

🔗 服务端：N 个已连接 Socket

每 accept() 一次就新建一个（fd=4、5、6…），每个死死绑定一个客户端。N = 当前已接受的连接数。

💻 客户端：1 个 Socket

socket() → connect()，就这一个。客户端不需要 listen，也不需要 accept。

所以「一次连接」的完整构成是：客户端 1 个 Socket ＋ 服务端 1 个已连接 Socket（由那个唯一的监听 Socket 产出）。
监听 Socket 从头到尾只有那一个，它自己不下场聊天——队列在流动、已连接 Socket 在不断新生。
想搞清楚「为什么一个 Socket 只能服务一个客户端、监听 Socket 又服务谁」，见同目录 《一个 Socket 到底服务几个客户端》。

②全景时序图：一次完整通信发生了什么

③服务端开局三步：socket() → bind() → listen()

int lfd = socket(AF_INET, SOCK_STREAM, 0);          // ① 造一个 socket，拿到 fd=3
bind(lfd, (struct sockaddr *)&addr, sizeof addr);  // ② 绑上 IP:端口（门牌号）
listen(lfd, 511);                              // ③ 进入 LISTEN，挂起两条队列
int cfd = accept(lfd, NULL, NULL);              // ④ 从全连接队列取出 → 新 fd=4
1
socket()：造一个「空壳」
内核建立 struct socket + struct sock，分配一个 sockfs inode，返回 fd。此时没有地址、不能收连接，谈不上服务谁。
2
bind()：绑上 IP:端口
给 socket 一个「门牌号」，客户端才知道往哪连。仍然没有开始监听。
3
listen(backlog)：进入被动监听，挂两条队列
状态变 LISTEN。内核为它准备好半连接队列和全连接队列。从此它只做一件事：接连接请求。注意 listen() 不阻塞——它只是把 socket 置为监听态就返回。
4
accept()：阻塞等待，取出一个已完成连接
全连接队列为空时阻塞（非阻塞下返回 EAGAIN）。有货就取出来，并新建一个已连接 Socket。
「怎么监听」的答案就是这三步：先 socket() 造对象，再 bind() 给它地址，最后 listen() 把它切换成监听态并挂上队列。真正的「等待」发生在 accept()（或 epoll 等监听 fd 可读）。

④核心：监听 Socket 挂着的两条队列

这是「监听」最容易被忽略的部分——listen() 之后，内核给这个 socket 挂了两条独立队列，握手过程就是连接在这两条队列之间搬家：

对比项半连接队列（SYN queue）全连接队列（accept queue）
装的是什么半开连接：SYN_RCVD，已回 SYN+ACK、等 ACK已建连：ESTABLISHED，握手完成、等 accept()
长度由谁定net.ipv4.tcp_max_syn_backlog；默认 256，内存 ≥128MB 的机器自动提到 1024（低内存降到 128）listen(backlog) 的值，但会被 net.core.somaxconn 静默截断
somaxconn 默认值自 Linux 5.4 起为 4096；更早的内核是 128（这也解释了为什么很多人设了 backlog=1024 却只生效 128）
满了会怎样新 SYN 被丢弃（客户端表现为连接超时）。开启 tcp_syncookies（默认 1）后该上限被绕过默认行为由 tcp_abort_on_overflow 决定：为 0 时内核忽略 ACK、重传 SYN+ACK；为 1 时直接回 RST
怎么观察netstat -s | grep dropped（SYN 丢弃计数）ss -lnt：Recv-Q = 当前队列长度，Send-Q = 队列上限
一个高频误解：很多人以为 backlog 是「半连接 + 全连接的总数」。在 Linux 上不是——backlog 只控制全连接队列（已完成握手、等 accept 的那些），半连接队列由 tcp_max_syn_backlog 单独管。

⑤怎么确认「连接建立好了」？——三次握手 + 队列搬家

「连接建立好」在两端不是同一时刻发生的，这是理解后续「什么时候可写」的关键：

1
服务端收到 SYN → 半连接队列 +1
内核为这条连接建一个 request_sock 放进半连接队列，状态 SYN_RCVD，回 SYN+ACK。此时连接还没建好。
2
客户端收到 SYN+ACK → 发出 ACK，客户端这边先 ESTABLISHED
客户端发出最后一个 ACK 的瞬间，它就认为连接建立好了，connect() 返回。此刻服务端还没确认。
3
服务端收到 ACK → 从半连接队列移到全连接队列
状态变 ESTABLISHED。服务端这边到此才算建好。连接现在躺在全连接队列里等应用来拿。
4
应用 accept() → 拿到 fd，应用视角「连接可用」
这是第三个时间点：内核建好 ≠ 应用拿到。如果应用不 accept，连接会一直堆在全连接队列里（客户端却已经以为连上了、可以发数据）。
所以「确认建立连接」有三个不同时刻：客户端发出 ACK 时（客户端视角已建好）→ 服务端收到 ACK 入全连接队列（服务端内核视角建好）→ 应用 accept() 拿到 fd（应用视角可用）。
这也是为什么全连接队列满会造成诡异现象：客户端 connect() 早已成功、数据也发了，服务端应用却迟迟拿不到连接。

⑥accept() 干了什么：产出一个全新的 Socket

accept() 最容易误解的一点：它返回的不是那个监听 Socket，而是一个全新的内核对象。

监听 Socket（fd=3）

accept 前后完全不变：还是那个 fd、还是那个 struct sock、状态还是 LISTEN。它继续等下一个连接。

已连接 Socket（fd=4）

accept 时新建：新的 struct socket + 新的 struct sock + 新的 sockfs inode。四元组在此时钉死，绑定那一个客户端。

推论：服务端进程里始终有两套 fd——一个不变的监听 fd + 一堆不断增减的已连接 fd。收发数据走的是后者。close() 监听 fd 只会停止接受新连接，不会影响已经 accept 出来的连接（它们是独立 fd，各自有引用计数）。

⑦什么时候可读、什么时候可写？

接上文 《Socket 是怎么被创建出来的》 里那套「可读 / 可写 / 异常」的判定，这里把它放到时间轴上看：

阶段监听 Socket（fd=3）已连接 Socket（fd=4）客户端 Socket
listen() 之后不读写数据。全连接队列为空 → 不可读还不存在还不存在
握手完成、未 accept全连接队列非空 → 可读（含义：有新连接可 accept）还不存在可写（connect 已返回）
accept() 之后队列被取空 → 恢复不可读可写（发送缓冲有空间）可写
对端发来数据—接收缓冲非空 → 可读—
应用 read() 取走—缓冲空 → 恢复不可读（LT 下）—
发送缓冲被塞满—不可写（write 阻塞 / EAGAIN）同理
对端 close()—可读 且 read() 返回 0—
实战大坑：别在 epoll 里一直监听「可写」。发送缓冲区绝大多数时候都有空间，所以 EPOLLOUT 几乎永远就绪——如果一直注册它，epoll_wait 会立刻反复返回，CPU 空转到 100%。正确做法是：默认只关心可读；只有在确实有数据要发、且 write 返回 EAGAIN 时，才临时挂上 EPOLLOUT，发完立刻摘掉。
监听 Socket 的「可读」和普通 Socket 的「可读」含义完全不同：前者是「有人来敲门（有连接待 accept）」，后者是「有数据来了」。详见 《Socket 是怎么被创建出来的》 第 ③ 节。

⑨关闭：四次挥手与 TIME_WAIT

1
主动方 close() → 发 FIN，进入 FIN_WAIT_1
「我这边没数据要发了」，但还能收。
2
被动方回 ACK，进入 CLOSE_WAIT
被动方此刻进入 CLOSE_WAIT，它的 read() 会返回 0 —— 应用层据此知道对端关了，然后自己也要 close()。
3
被动方也 close() → 发 FIN，进入 LAST_ACK
等到自己的 FIN 被确认。
4
主动方回 ACK → 进入 TIME_WAIT（2×MSL）→ CLOSED
TIME_WAIT 出现在主动关闭的那一方。停留 2×MSL 是为了让最后的 ACK 能到达、并让旧连接的残留报文在网络中消散。
两个实用结论：① 服务端出现大量 CLOSE_WAIT，几乎一定是应用忘了 close()（对端已关，自己没关）；
② 服务端出现大量 TIME_WAIT，说明是它在主动关闭——对短连接服务，让客户端主动关闭可以把 TIME_WAIT 推给客户端。

⑩常见误区与速记

误区 1：「listen() 会阻塞等待连接」

❌ listen() 只是把 socket 切成监听态并挂上队列，立刻返回。真正阻塞等待的是 accept()（或 epoll 等待监听 fd 可读）。

误区 2：「backlog = 半连接 + 全连接的总数」

❌ Linux 上 backlog 只控制全连接队列，且会被 net.core.somaxconn 静默截断（Linux 5.4+ 默认 4096，更早内核 128）。半连接队列由 tcp_max_syn_backlog 单独管。

误区 3：「accept() 返回的就是那个监听 Socket」

❌ 完全是两个对象。监听 Socket 的 fd 不变；accept() 返回的是新建的 fd + 新建的 struct sock + 新建的 inode。

误区 4：「connect() 成功 = 服务端应用已经拿到连接」

❌ 客户端发出最后一个 ACK 时 connect() 就返回了。服务端这边连接可能还堆在全连接队列里没被 accept。两端「建好」的时刻不同。

误区 5：「epoll 里一直监听可写事件更高效」

❌ 发送缓冲基本总有空间，EPOLLOUT 几乎永远就绪 → epoll_wait 立刻反复返回 → CPU 空转。只在 write 返回 EAGAIN 时才临时关注可写，发完即摘。

环节一句话
socket()造对象，拿 fd，还没有地址
bind()给它门牌号 IP:端口
listen()切监听态 + 挂两条队列，不阻塞
半连接队列装 SYN_RCVD，等最后的 ACK
全连接队列装 ESTABLISHED，等 accept（长度 = min(backlog, somaxconn)）
accept()取出一个 → 新建一个已连接 Socket
可读有数据来了 / 对端关闭 /（监听 socket）有连接待 accept
可写发送缓冲有空闲空间（几乎总成立，别一直监听）
close()四次挥手，TIME_WAIT 留在主动关闭方
最终速记：「一个监听挂两队列，握手搬家到全连接；accept 取货造新 fd，读写只看缓冲区。」
