WebSocket 背压、断线重连与消息顺序：聊天消息为什么会重复

用聊天室故障时间线设计发送队列、序号、确认和重连恢复，避免只靠“长连接在线”。

长连接不等于无限吞吐

WebSocket 在建立后提供双向消息帧，但链路和客户端消费能力仍有限。服务器每秒向某浏览器推送 1000 条消息，浏览器只能处理 200 条时，待发送数据会在服务端、内核或客户端逐渐积压。连接仍显示 OPEN，并不表示用户及时看到了消息。背压是生产者根据消费者和缓冲状态减速、限队列或舍弃低优先级信息的机制。

浏览器 WebSocket API 可观察待发送字节量等指标，但它不能直接证明对端应用已处理。服务端也要给每个连接设置队列上限、发送超时和慢消费者策略；否则一个慢客户端可能占用大量内存拖垮整个聊天室。

一次慢客户端时间线

客户端 C 在弱网下接收消息，服务端队列从 100 条涨到 10 万条。若服务端无限缓存，内存持续增长；若直接丢弃消息而不给客户端提示，用户会以为聊天记录完整。可按业务选择：关键聊天消息持久化并允许按序号补拉，在线提示或输入状态可以丢弃最新/旧消息，队列超过阈值时主动断开并要求客户端重连恢复。不同消息类型不能共用同一“永远不丢”策略。

压测应同时跑大量正常用户与少量极慢用户，看服务端内存、单连接队列、广播耗时和正常用户尾延迟。只有单连接功能测试无法暴露背压问题。

补齐缺口并切回实时流。

TCP 顺序不等于业务恰好一次

单条 WebSocket 连接底层通常基于可靠有序传输，帧在这条连接内按顺序到达。然而断线后客户端不知最后一条发送的消息是否已经被服务端处理；重连重发可能产生重复。若服务器向客户端推送消息时响应丢失，客户端也可能在补拉与实时推送之间重复看到同一条。需要消息 ID、会话或频道序号和幂等去重，而不是只相信“TCP 可靠”。

跨多个服务器实例或多个频道时，产生顺序还受后端队列与存储影响。业务要明确保证的是单会话顺序、单频道顺序还是全局顺序；全局严格顺序成本很高且常不必要。消息显示时按服务端确认的序号排序，并处理临时本地气泡与最终确认的合并。

重连恢复协议

客户端记录最后连续处理的服务端序号 N。重连后带上 N，请求从 N+1 补拉；服务器把缺口补齐后再切入实时推送，或用统一有序流解决补拉与实时竞态。若服务器只保留最近一小时消息，客户端离线过久应收到“历史已过期，请全量同步”而不是假装没有缺口。客户端发送写消息也要带稳定消息 ID，服务端重复收到同一 ID 返回首次结果。

重连应使用指数退避与随机抖动。若网关重启使一百万客户端同时断线，所有客户端每秒固定重试会形成重连风暴。刷新认证凭据与重新订阅频道也要在重连流程里明确，不能沿用已过期令牌。

心跳和中间代理

WebSocket 协议有 Ping/Pong 控制帧，服务端可用它检测传输层活性；浏览器脚本是否能直接发送协议 Ping 取决于 API 能力，业务层可另设计心跳。心跳收到回应不等于客户端 UI 已消费完消息，背压仍需观察队列。代理、负载均衡和 NAT 都可能在空闲时关闭连接，心跳间隔要兼顾它们的超时、电量与服务负担。

一些代理不支持或错误处理 WebSocket Upgrade、空闲超时太短或未转发认证头，表现为握手成功后很快断线。排查要记录代理层关闭码和时间，而不是只看浏览器 onclose。

安全与隔离

服务端握手时验证用户凭据和允许的 Origin，建立连接后也要在订阅频道和每条高影响消息上校验权限。用户权限被撤销或令牌过期时，长连接不能无限继续接收旧授权频道的数据。广播层必须按租户和频道隔离，错误订阅不能靠前端不显示来掩盖。消息大小、频率和总队列需要限额，防止恶意客户端发巨帧或不读数据耗尽资源。

如果聊天内容需要端到端加密，普通 WSS 只保护客户端到服务端这一段，服务端仍可读取应用正文。两者的信任模型不同，应按产品要求明确。

验收清单

模拟断线发生在“客户端发出但未获确认”“服务端推送但客户端未持久化”“补拉中又收到新消息”三个时点，检查无重复展示和无静默丢失。再让慢客户端持续不读，确认队列上限生效且正常客户端不受显著拖累。记录连接数、每连接缓冲、消息端到端延迟、重连率和缺口补拉成功率。

长连接的核心问题不只是握手能否成功，而是长期运行中的慢消费者、未知结果和恢复边界。

背压与缓冲的确切指标

概念位置关键值处理
bufferedAmount浏览器 WebSocket 对象已排队但未发出的字节数超过阈值就暂停生产
bufferedAmountLowThreshold浏览器默认 0（必须手动设！）设 64 KB 并监听 onbufferedamountlow
服务端发送队列应用进程SO_SNDBUF 满则 write 阻塞用异步写 + 队列水位告警
内核发送缓冲OSss -tm 看 w 字段长期满说明对端读得慢

背压的本质：生产快于消费时，数据会在某处堆积。WebSocket 是 TCP，不会丢消息，只会越堆越多直到内存爆掉或延迟变得不可接受。所以必须在应用层显式处理，而不是指望 TCP。

背压处理代码

// 浏览器侧标准背压处理
const ws = new WebSocket(url);
const HIGH = 1024 * 1024;   // 1 MB 高水位
const LOW  = 64 * 1024;     // 64 KB 低水位
ws.bufferedAmountLowThreshold = LOW;
let paused = false;

function send(data) {
  if (ws.bufferedAmount > HIGH) { paused = true; queue.push(data); return; }
  ws.send(data);
}
ws.onbufferedamountlow = () => {
  paused = false;
  while (queue.length && ws.bufferedAmount < LOW) ws.send(queue.shift());
};

// 服务端（Node ws 库）也有对应属性
if (ws.bufferedAmount > HIGH) { /* 暂停生产 */ }
ws.on('drain', () => { /* 继续 */ });

bufferedAmountLowThreshold 默认是 0，也就是说 onbufferedamountlow 默认几乎不触发——这是最常见的背压实现 bug。

重连、有序与幂等

  • 重连退避：指数退避 + 抖动，如 min(30s, 1s × 2^n) × (0.5 + random/2)。服务端大面积重启时，不做抖动会有同步重连风暴。
  • 消息序号：每条消息带单调递增 seq；重连后客户端上报“最后收到的 seq”，服务端从断点补发（或全量快照）。不要假设“WebSocket 不断就不需要序号”。
  • 顺序保证的边界：WebSocket 在单条 TCP 连接内保证有序，但重连后是新连接，旧连接残留的消息与新消息的相对顺序无法保证。业务上要么容忍乱序（用状态版本号覆盖），要么重连后先拉全量快照再接增量。
  • 幂等：重连后重发的写请求必须带 idempotency key（客户端生成的唯一 ID），服务端去重。否则“消息发没发成功不知道 → 重发”会造成重复下单。
  • 心跳：WebSocket 有协议级 Ping/Pong 控制帧，但浏览器 JS 无法主动发 Ping。常见做法是应用层定时发 {type:'ping'} 消息，30 s 一次，2 次超时判定断线。
  • 服务端超时：Nginx proxy_read_timeout 默认 60 s，比心跳过短会被代理切断 → 调到大于心跳间隔（如 3600 s）。
WebSocket 说是有序可靠，为什么还要自己做序号和补发？

协议的有序性只在一条连接内成立。一旦断线重连，中间那些“发出去但不知道对端收没收到”的消息就丢失了，业务层无从判断。序号 + 补发/快照解决的是“连接切换时的语义连续性”。

怎么判断是网络断了还是对端卡了？

心跳超时说明端到端不可达（可能任一端问题）；若 Ping 有回但业务消息不回，多为服务端应用阻塞。可再加一个“业务健康检查”接口区分。

自检

一条 WebSocket 连接上的 TCP 有序，重连后就天然恰好一次吗？

不是。断线时发送与确认结果可能未知，重连补发会重复；需要消息 ID、序号与去重。
