Rerank 重排序

ANN 召回快但粗，常常「答案排在第 80 名」。Rerank 用交叉编码器对召回候选精排，把真正相关的顶上来。本文讲清双塔 vs 交叉编码器、融合方式、流水线、何时用、常见坑。

01召回与精排的分工

召回 Recall

从亿级里快取 Top-100~1000 候选，要求低延迟、可建索引，但只看「表面相似」，会漏相关、混不相关。

精排 Rank

对这 100 条用更强模型重排 Top-10，精度优先、不计较速度。

没有 rerank 时，Top-K 直接喂给 LLM，经常漏掉真正答案（在 100 名外或排第 30）。rerank 是 RAG 精度的关键放大器。

03两种融合方式

无模型融合

RRF（Reciprocal Rank Fusion）或加权 score 融合（向量分 + BM25 分），零额外推理，先混合后取 Top-N。

有模型融合

learned reranker（cross-encoder）对融合后的候选逐条打分重排。

混合检索标准组合：先 RRF 融合 → 再 rerank，是 RAG 高精度的常见配方。

04典型流水线

召回阶段宁多勿漏（召回率优先）；rerank 阶段在 CPU/GPU 上跑 cross-encoder，把真正相关的顶到前 10。

05什么时候需要 rerank

该用

答案常在召回候选但排不到前 10；多语言/长文档/语义微妙；recall@10 不达标；问答准确率要求高。

可不用

简单关键词/短文本场景；候选本就很少；对延迟与成本极度敏感的原型期。

06常见 reranker

bge-reranker-v2-m3

开源、多语言、强，常被私有化部署，社区首选。

Cohere Rerank

商用 API，易用、效果好，按调用计费。

Jina Reranker

开源/商用双形态，多语言支持好。

自训练

用业务标注对 fine-tune cross-encoder，贴合自有语料。

07坑与成本

延迟翻倍

rerank 100 条可能比召回还慢，设上限（只 rerank 前 50~100）。

成本

商用 API 按次计费，量大要算账。

召回池太小

先召回够多再 rerank；池子太小 rerank 也无米之炊。

多样性下降

rerank 只优化相关度，可能结果扎堆，必要时加多样性重排。

rerank 不能替代召回。召回漏了，rerank 再强也救不回。

Rerank 的收益、成本与选型

Rerank 是 RAG 里性价比最高的准确率提升手段——它不做检索，只是把粗排结果重新精排。但代价是延迟和成本。

代码示例

# ---------- RRF 融合（零成本，先试这个）----------
def reciprocal_rank_fusion(rank_lists, k=60):
    # rank_lists: [[doc_id,...], [doc_id,...]]  多路召回结果
    scores = {}
    for lst in rank_lists:
        for rank, doc_id in enumerate(lst):
            scores[doc_id] = scores.get(doc_id, 0) + 1.0 / (k + rank + 1)
    return sorted(scores.items(), key=lambda x: -x[1])
#   k=60 是原始论文的默认值，一般不用调
#   优势：不需要归一化分数（向量分数和 BM25 分数不可比，RRF 只看排名）

# ---------- Cross-encoder Rerank ----------
from sentence_transformers import CrossEncoder
model = CrossEncoder('BAAI/bge-reranker-v2-m3')      # 中文推荐
pairs  = [(query, doc) for doc in candidates]        # 候选 50 条
scores = model.predict(pairs)                        # 每条 0~1（越相关越高）
top = [c for _, c in sorted(zip(scores, candidates), reverse=True)][:5]

# 典型延迟（单条 A10G）：bge-reranker-base ~15ms，large ~45ms
#   50 条候选 × 15ms = 750ms（串行，难以并行化）

# ---------- 工程优化手段 ----------
# 1. 先用向量分数截断：只 rerank top-50，不是 top-200
# 2. 批量推理（batch=16~32），比逐条快 3~5 倍
# 3. 缓存高频 query 的 rerank 结果
# 4. 异步：先返回向量召回结果，rerank 到位后再更新（streaming 场景）
# 5. 分层：便宜模型 rerank top-200 -> 50，贵模型 rerank 50 -> 5
  • 先做 RRF，再考虑 Rerank：RRF 把「向量召回 + BM25 关键词召回」的结果按排名融合，零成本、零延迟，通常能提 5~10% 的召回质量。这是投入产出比最高的一步。
  • Rerank 的候选数是最关键的调参项：从 200 降到 50，延迟降 4 倍、准确率通常只掉 1~2%。先用 50，测出来不够再加。
  • 中文必须用中文 rerank 模型：bge-reranker-v2-m3、Cohere rerank-multilingual 这类。拿英文模型 rerank 中文，效果可能还不如不 rerank。
  • cross-encoder 无法预编码是根本限制：query 和 doc 必须拼在一起过模型，所以每条候选都要单独算一次。这就是为什么它比向量检索慢 100 倍。
  • ColBERT 是折中方案：doc 端可以预编码成多向量，query 端在线算 MaxSim，延迟比 cross-encoder 低 5~10 倍，准确率接近。
  • 评估要测端到端：不要只看 rerank 模型本身的指标，要看最终 RAG 回答的准确率。有时候 rerank 提升的召回质量，被后续的 prompt 组装吃掉了。
Rerank 到底值不值得上？

看三个信号：① 你的召回质量是不是瓶颈——先测 recall@50（正确答案在前 50 条里的比例）。如果已经 95%+，rerank 最多帮你把它排到前面，提升有限；如果只有 60~70%，说明好答案根本没被召回，rerank 救不了，该去优化召回（换 embedding、加关键词、改 chunk）；② 你能接受多少延迟——交互式问答的总预算通常 1~3 秒，rerank 50 条要 0.5~1 秒，占掉一大半。如果延迟敏感，只 rerank top-20；③ QPS 和预算——cross-encoder 是按候选条数计费的（不是按 query 数），1000 QPS × 50 条 = 每秒 5 万次推理，成本会失控。这时考虑 ColBERT（doc 可预编码）或干脆用 RRF。我的建议顺序：先 RRF（免费）→ 测提升 → 不够再上 rerank（候选从 20 起步）→ 还不够再考虑换 embedding 或改 chunk 策略。

为什么 cross-encoder 比向量检索准那么多？

根本差异是信息交互的时机。向量检索（bi-encoder）把 query 和 doc 分别编码成两个向量，然后算余弦相似度——两个向量在编码时从未见过对方，交互只发生在最后一步的点积上，信息严重损失。cross-encoder 把 [CLS] query [SEP] doc [CLS] 拼成一个序列送进 Transformer，让 query 的每个 token 和 doc 的每个 token 在自注意力里充分交互，模型能捕捉到「这个词和那个词其实在说同一件事」这类细粒度匹配。代价是：doc 无法预编码（因为它必须和 query 拼在一起），每个候选都要单独前向传播一次——所以延迟高 100 倍。这就是为什么工业界用「召回用 bi-encoder（快、可预编码）+ 精排用 cross-encoder（准、慢）」的两阶段架构，用少量候选换取两者的优点。

RRF 的 k=60 需要调吗？

基本不需要。k 的作用是控制排名靠前的结果的优势程度——k 越小，第一名相比第二名的优势越明显（1/61 vs 1/62 差别小，而 k=1 时是 1/2 vs 1/3，差距就大了）。原始论文用 60，社区实践也基本都是 60，在大多数数据集上 k 从 10 到 100 的效果差异很小。真正影响效果的是参与融合的召回路数：① 两路（向量 + BM25）融合通常比单路提 5~15%；② 三路以上边际收益递减；③ 如果某一路质量很差，融合反而会拖累整体——所以要先单独评估每一路的 recall@K，把明显差的去掉。另外 RRF 有个常被忽略的优点：它只用排名不用分数，所以不用做分数归一化——向量相似度（0~1）和 BM25 分数（可能 0~30）量纲完全不同，直接加权求和很难调，而 RRF 完美绕开了这个问题。

为什么检索之后还要排序

召回阶段为了快，做了很多妥协：向量被压缩了、搜索是近似的、距离只比较单个向量、无法同时看查询和文档。这些妥协让它能毫秒级返回几十上百条候选，但同时也意味着「它给出的顺序并不完全可信」。

召回要快而全，重排要准而精

三种常见的重排手段

手段怎么做精度成本
Cross-Encoder把 query 与候选拼成一个输入，让模型直接输出相关度分数最好（能同时看到两边，充分交互）每条候选都要一次前向，很贵
双塔/向量距离各自编码后算距离最弱（两边互不看见）最便宜，就是召回阶段用的
LLM 重排把候选列表交给大模型打分或排序好，且能理解复杂指令最贵、延迟最高，适合小候选集
融合分数 RRF把多路召回的排名做加权融合中等（不需要模型）几乎为零

为什么交叉编码更准：双塔模型在编码时看不到对方，只能各自压缩成一个向量，压缩过程中必然丢失交互信息；而 Cross-Encoder 让两者在模型内部逐层做注意力交互，能捕捉到「这个词在这一句里的特殊含义」这类细微差别。

为了控制成本，Cross-Encoder 的经典用法： 召回 → top 100（约 10~30ms） ↓ Cross-Encoder 对 100 条打分（约 50~200ms，看模型与批大小） ↓ 取 top 5 送进 prompt（约 1000~3000 tokens） batch 越大，重排的单条摊销成本越低； 但候选数每翻一倍，延迟近似翻倍 —— 这就是要拿实际数据二选一的点。

RRF：不用模型的融合手段

如果你同时跑了关键词检索（BM25）和向量检索，两路的分数不在同一个量纲（一个可能是 0~20 的 BM25 分数，一个是 0~1 的余弦）。直接加权相加毫无意义。

倒数排名融合（Reciprocal Rank Fusion, RRF）绕开了分数，只使用排名：

RRF 公式 score(d) = Σ_over_lists 1 / (k + rank_i(d)) k 通常取 60（用于抑制头部权重，避免第一名独占鳌头） 例：某文档在向量检索里排第 3，在关键词检索里排第 1 score = 1/(60+3) + 1/(60+1) = 0.0159 + 0.0164 = 0.0323 另一篇只在向量里排第 1： score = 1/(60+1) = 0.0164 → 同时被两路认可的文档胜出

它的优点非常实用：不需要调权重的冰敷 bugafu、不需要归一化、两路结果的质量差异不会导致某一路被埋掉。做混合检索时，RRF 是默认值。

什么时候加，怎么测

值得加的信号

  • 召回的前几条经常「看起来相关但其实答不上问题」。
  • 正确答案出现在 top-20 但总不在 top-5（召回率不差，排序差）。
  • 送入大模型的上下文预算紧张，必须只挑最有用的那几条。
  • 查询里有比较隐含的语义关系（否定、因果、细微差别）。

怎么判断有没有用

  • 用一批人工标注的 query–文档对，测 nDCG@10 与 Recall@k。
  • 关注端到端效果（最终回答质量），而不是只看检索排序变好。
  • 测延迟与成本，看 p95 是否还能接受。
  • 若 RPC 只在边际上改善，优先去改切分与 Embedding，收益通常更大。

一条经验顺序：RAG 效果差时，归因优先级通常是 切分质量 > embedding 模型 > 查询改写 > 混合召回 > 重排。重排是一项「锦上添花」的优化 —— 它无法拯救一个从一开始就召回不出来的系统。

深入自检

有了重排，是不是召回就可以随便一点？

不是。重排只能对已经进入候选集的文档重新排序，它无法召回漏掉的文档。如果正确答案压根不在 top-100 里，再强的重排器也看不见它。所以评估时分两步看：Recall@100（召回有没有漏）与 nDCG@5（排序好不好），两者分别优化。

重排的延迟能不能接受？

通常能，因为它只处理几十到一两百条。但它给端到端增加的延迟是实打实的，常用优化有三：① 只对 top-N 做重排并调小 N；② 批处理并行打分；③ 换个更小的专用重排模型（很多重排模型比通用大模型小一到两个数量级）。先把延迟曲线测出来再决定 N。

MMR 是什么，和重排什么关系？

MMR（最大边际相关性）解决的是冗余问题：召回来的 top-20 里可能有一半是几乎重复的段落，占满了 prompt 却没提供新信息。它会在「与查询相关」与「与已选结果不重复」之间取平衡。它常与重排配合：先按相关性排序，再用 MMR 去重挑多样性的结果。

自己训练重排器值得吗？

绝大多数团队不值得。现成的开源/云端重排模型已经很强，而自训需要大量高质量的标注 query–文档对，成本远高于收益。真正值得投入的往往是构造一批自己的评测集，用它来判断该选哪个现成模型、该把 top-k 设成几 —— 这个投入产出比高得多。
