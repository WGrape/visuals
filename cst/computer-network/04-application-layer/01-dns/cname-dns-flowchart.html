DNS：把「好记的名字」翻译成「IP」

DNS 是互联网的电话簿。它的设计有三个关键点：分层命名（根 → 顶级域 → 二级域 → 子域）、分布式权威（每层只负责自己那一段）、缓存（靠 TTL 大幅降低查询量）。CNAME 则是这套系统里的「别名」，它会让解析链路多绕一圈。

CNAME 的代价：每多一层 CNAME 就多一次完整解析（可能增加几十到上百毫秒），所以链式 CNAME（a→b→c）要避免。CDN 场景常见「用户域名 CNAME 到 CDN 域名」，一层即可。

实践与排障

① 修改记录后多久生效

  • 取决于 TTL：最长需等原 TTL 过期。
  • 正确姿势：先调小 TTL（如改 60 秒），等待旧 TTL 过期后再改记录。
  • 各地运营商缓存行为不同，可能有额外延迟。
  • 验证：dig/nslookup 指定不同 DNS 服务器对比。

② CNAME 使用限制

  • 同一名字有了 CNAME 就不能再有 A、MX 等其他记录（CNAME 是「这个名字的全部答案」）。
  • 根域名（example.com）不能用 CNAME，因为会与 SOA/NS 冲突。
  • 需要根域名指向 CDN 时用 ALIAS/ANAME（厂商扩展）或直接用 A 记录。
  • MX 不能指向 CNAME（规范要求指向真实名字）。

③ 常见排查命令

  • dig +trace example.com：看完整解析链路。
  • dig @8.8.8.8 example.com：指定 DNS 服务器查询。
  • nslookup -type=CNAME www.a.com：查特定记录类型。
  • systemd-resolve --flush-caches / ipconfig /flushdns：清本地缓存。

④ DNS 的其他角色

  • 负载均衡：一个名字返回多个 IP（DNS 轮询），或按来源返回不同 IP（智能解析/GSLB）。
  • 故障切换：健康检查失败时把记录指向备用 IP。
  • 服务发现：Kubernetes 用 DNS 解析 Service 名。
  • 安全：DNSSEC 防篡改；DoH/DoT 加密查询防监听。

深入自检

为什么改了 DNS 记录，有的人立刻生效、有的人要等很久？

因为缓存分布在不同层级且各自按 TTL 过期：本地 OS 缓存、路由器、运营商递归 DNS、公共 DNS 都可能持有旧记录。谁的缓存先过期谁先看到新值。所以规范流程是提前把 TTL 调小，并预留一个旧 TTL 周期的等待时间。

CNAME 和 URL 重定向有什么区别？

层级完全不同：CNAME 是 DNS 层的「名字别名」，客户端无感知，浏览器地址栏不变；重定向（301/302）是 HTTP 层的响应，浏览器收到后会重新发起请求，地址栏会变。想「换域名但保留旧名字」用 CNAME 或 HTTP 重定向取决于是否要改变地址栏与是否跨协议。

根域名为什么不能用 CNAME？

因为根域（apex）必须有 SOA 与 NS 记录来标识这个区的开始与权威服务器，而 CNAME 的语义是「这个名字的全部答案都是另一个名字」，会与这些必需记录冲突，违反 DNS 规范。替代方案是使用厂商提供的 ALIAS/ANAME/FLAT 记录，或直接配置 A/AAAA。

DNS 轮询能算负载均衡吗？

能实现最简单的流量分摊，但很粗糙：不考虑后端健康（故障仍会被返回）、不考虑负载与地域、且客户端与中间 DNS 的缓存会让分配严重不均。生产通常用「DNS 指向负载均衡器/CDN」，由 LB 做真正的健康检查和智能调度，DNS 只负责第一跳。

DNSSEC 解决了什么问题？

解决 DNS 应答被伪造/篡改的问题（如缓存投毒）：通过逐级数字签名，让解析器能验证「这个答案确实来自权威且未被修改」。它只保证完整性与来源真实性，不加密内容；要防监听需要 DoH（HTTPS）或 DoT（TLS）。

一个名字返回多个 IP 时，客户端会怎么选？

通常由客户端（或 stub 解析器）选择，常见策略是取第一个、随机或按 Happy Eyeballs（IPv6/IPv4 双栈并行尝试、谁快用谁）。返回值顺序会被 DNS 服务器轮换以实现粗粒度分摊。真正的健康与负载调度应交给 L4/L7 负载均衡。
