1构建的瓶颈在重复

大型仓库里 90% 的构建工作是重复的：同一份源码被反复编译。加速的核心是缓存（命中就跳过）与远程执行（把任务发到集群）。这层优化不改变构建图，只改变"谁算、算过没"。

本文聚焦缓存与远程执行：ccache、远程构建、Bazel remote execution、可重现构建。

2缓存与远程执行对比

手段机制收益
本地缓存(ccache)按预处理后哈希存目标文件单机重复编译免重算
远程缓存共享内容寻址缓存团队/CI 互相命中
远程执行动作发到 worker 池横向扩展、利用空闲机
可重现固定环境/时间戳缓存可跨机器安全复用

3ccache 与 Bazel 远程

# 本地缓存：把 gcc 包一层
export CC="ccache gcc"
ccache -M 10G                 # 设缓存上限
ccache -s                     # 看命中率

# Bazel 远程执行/缓存（示意）
bazel build //pkg:all \
  --remote_cache=grpc://cache.example.com \
  --remote_executor=grpc://exec.example.com \
  --jobs=200

缓存键通常基于"输入内容哈希 + 工具链哈希 + 命令行"，任一变化即未命中。

4远程执行流程

图：action 先查远程缓存，未命中再远程执行

第一层 · 概念与判定

判定是否值得引入：

  • CI 频繁全量重建、缓存命中率低 → 上远程缓存；
  • 单机编译打满、构建时长瓶颈在算力 → 远程执行；
  • 需要审计/复现产物 → 可重现构建；
  • 小项目本地 ccache 足矣。

第二层 · 参数·命令·量化

关键参数：

项建议
缓存上限ccache -M 给足（如 10–50G）
远程 jobs按 worker 数设 --jobs
缓存键含工具链版本，避免错版本命中
bazel clean --expunge   # 清本地缓存排错

第三层 · 排障与边界

排障：

  • 命中率低：检查是否把时间戳/绝对路径打进输入；
  • 缓存污染：工具链变更未进键，导致错产物，规范键；
  • 远程执行环境差：worker 与本地环境不一致，用容器化沙箱；
  • 不可重现：嵌入了日期/用户名/随机，需固定。

第四层 · 原理与取舍

原理取舍：

  • 缓存用"内容寻址"换速度，但键设计错就成错误源；
  • 远程执行用"网络+协调"换横向扩展，引入一致性与安全成本；
  • 可重现牺牲一点便利性换取可验证与可共享；
  • 结论：缓存与远程执行是规模化的必经之路，前提是输入可哈希、环境可复现。
