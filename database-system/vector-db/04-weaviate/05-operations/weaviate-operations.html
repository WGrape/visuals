①监控与可观测性

Weaviate 的可观测性走得比另两家更「云原生」：内置 /v1/meta、Prometheus 指标、以及较完善的日志分级。

关注项位置说明
Prometheus 指标/metrics（需开 monitoring）请求数、延迟、索引大小
节点/分片状态/v1/nodes各节点对象数、shard 状态
Schema 与统计/v1/schema、/v1/objects/_stats类定义与对象计数
LSM 与段状态日志 + 指标段压缩、flush 情况
Weaviate 的 GraphQL 查询慢，很多时候不是向量检索慢，而是返回字段太多（GraphQL 会把所有请求字段真实取回）。排查时先看查询里 _additional 和字段列表有没有要多了。

②备份模块与恢复

Weaviate 的备份是模块化的，需要显式启用 backup 模块：

# docker 里启用 filesystem 备份模块
ENABLE_MODULES=backup-filesystem
BACKUP_FILESYSTEM_PATH=/var/lib/weaviate/backups

# 触发备份
POST /v1/backups/filesystem
{ "id": "backup_20261023" }

# 查状态
GET /v1/backups/filesystem/backup_20261023

# 恢复
POST /v1/backups/filesystem/backup_20261023/restore
和 Qdrant 一样，filesystem 备份落在本地。生产上应配 backup-s3 / backup-gcs 直接写到对象存储，并定期做恢复演练。

⑤速记卡

监控

/metrics + /v1/nodes；GraphQL 慢先查返回字段。

备份

需显式启用 backup 模块；filesystem 落本地，生产用 S3/GCS。

第一误判

小数据集调 ef 没反应 = 走了 flatSearchCutoff 暴力扫。

第一慢因

自动向量化同步调外部 API，拖慢写入。

内存

冷 tenant 置 INACTIVE；注意 vectorCacheMaxObjects。

混合检索

调 alpha（默认 0.75 偏向量）与 fusionType。

重建

新建 Class + 应用切名，无法原地改维度。

运维负担

运维命令手册：健康检查 / 备份 / 恢复

向量库的运维和三件事有关：能不能读写（健康）、数据能不能回来（备份）、慢在哪（指标）。下面是可直接复制的命令。

Weaviate 备份/恢复 API

# 1) 健康与就绪：k8s 探针用的就是这两个端点
curl -s http://localhost:8080/v1/.well-known/live   | jq .   # 存活
curl -s http://localhost:8080/v1/.well-known/ready  | jq .   # 就绪（未就绪则不接受读写）
curl -s http://localhost:8080/v1/meta | jq .                  # 版本与模块信息

# 2) 备份：先在服务端启用 filesystem 模块并配置路径，再触发
# 环境变量：BACKUP_FILESYSTEM_PATH=/var/lib/weaviate/backups
curl -X POST 'http://localhost:8080/v1/backups/filesystem/my-backup-1' \
     -H 'Content-Type: application/json' \
     -d '{"include": ["Article", "Product"]}'

# 3) 查备份状态（备份是异步的，必须轮询）
curl -s 'http://localhost:8080/v1/backups/filesystem/my-backup-1' | jq .
# status: STARTED / TRANSFERRING / TRANSFERRED / SUCCESS / FAILED

# 4) 恢复（同样异步）
curl -X POST 'http://localhost:8080/v1/backups/filesystem/my-backup-1/restore' \
     -H 'Content-Type: application/json' \
     -d '{"include": ["Article"]}'

Compose 配置与容器内检查

# Docker Compose 最小运维配置：数据目录与备份目录必须挂卷
services:
  weaviate:
    image: semitechnologies/weaviate:1.27.0
    ports:
      - "8080:8080"
      - "2112:2112"      # Prometheus 指标端口
    environment:
      PERSISTENCE_DATA_PATH: /var/lib/weaviate
      BACKUP_FILESYSTEM_PATH: /var/lib/weaviate/backups
      QUERY_DEFAULTS_LIMIT: 25
      AUTHENTICATION_ANONYMOUS_ACCESS_ENABLED: 'true'
      CLUSTER_HOSTNAME: node1
    volumes:
      - ./data:/var/lib/weaviate
      - ./backups:/var/lib/weaviate/backups

# 容器内的日常检查
docker exec -it weaviate sh -c 'du -sh /var/lib/weaviate && ls /var/lib/weaviate/backups'
docker logs --tail 200 weaviate | grep -iE 'error|warn|compaction'

指标与 k8s 检查

# 指标：Prometheus 端口默认是 2112，先看有哪些指标再挑关键的
curl -s localhost:2112/metrics | grep -iE 'object|vector|query|backup' | head -40

# k8s 上的例行检查
kubectl get pods -l app=weaviate -o wide

kubectl exec weaviate-0 -- du -sh /var/lib/weaviate
kubectl logs weaviate-0 --previous                 # 崩溃前的日志（最关键）

备份不是导出：Weaviate 的备份是服务端快照，恢复时要求类结构一致；跨版本恢复前必须先在测试环境验证一次，不要等到故障时才发现不兼容。

容量估算与运维清单

向量库的容量几乎可以线性估算：内存 ≈ 向量数 × 维度 × 4 字节 × (1 + 索引开销系数)。HNSW 的图结构本身不存向量，但要存邻居链接，开销系数通常在 1.2 ~ 1.6 之间。

向量数维度原始向量含 HNSW 索引（×1.4）备注
100 万768≈2.9 GB≈4.1 GB常见 BERT 类嵌入规模
1000 万768≈29 GB≈41 GB需要多节点分片
1000 万1536≈57 GB≈80 GBOpenAI 类嵌入，容量翻倍
1 亿768≈287 GB≈400 GB必须分片 + 考虑量化（PQ/SQ）

算完内存还要算磁盘：磁盘通常是内存的 1.2 ~ 2 倍（含 WAL、备份、原始对象与删除墓碑）。如果内存吃不下，优先上量化（SQ/PQ 可把内存降到 1/4 ~ 1/8），而不是先加机器。

调优项常见取值往大调往小调
HNSW efConstruction128 ~ 512（默认多为 128）召回更高、构建更慢、图更大构建快、内存小、召回降
HNSW maxConnections(M)16 ~ 64（默认多为 32）召回高、内存与构建时间上升内存小、召回降
查询 ef多为动态（随 limit 变化）召回高、延迟高延迟低、召回降
批量导入 batch几百 ~ 几千条/批吞吐高、内存峰值高内存稳、吞吐低
量化（SQ / PQ）PQ 常按维度分段精度高、压缩少内存降到 1/4~1/8、召回降

运维逐条核对（不同版本参数名可能有出入，请以所用版本的文档为准）：

  • 备份必须定期演练恢复：只备份不演练，等于没有备份。至少每季度做一次全量恢复验证。
  • 备份目录与数据目录分开：同盘备份在磁盘损坏时一起丢。
  • 先算内存再上线：向量数 × 维度 × 4B × 1.4，算出来超单机内存就必须提前分片。
  • 导入期间不要同时做大规模查询压测：compaction 与导入争抢 IO，P99 会显著劣化。
  • 删除是软删除：会产生墓碑，需要等待后台压缩回收，磁盘不会立刻下降。
  • ef 与召回直接相关：调召回前先确认是不是 ef 太小，不要盲目扩容。
  • 监控要覆盖备份状态：备份失败通常不体现在读写指标上，必须单独轮询。
  • 版本升级前先在测试集群导入一份真实数据：向量索引格式可能随版本变化。
  • 限流要放在网关：单个大 ef + 大 limit 的查询就能打满一个节点的 CPU。
Weaviate 的问题有一半是「你以为它在做 A，其实它在做 B」：以为走 HNSW 其实在暴力扫，以为只改了标量其实重新向量化了。
