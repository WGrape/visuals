云平台架构 / 发布与部署

云负载均衡切流与回退

云上发布的关键不只是替换进程，而是让负载均衡、跨可用区实例与后端连接在切流期间保持可用。

拓扑与切流摘流与连接故障时回退验收清单

01 / 先确认负载均衡能把流量送到哪里

假设订单 API 横跨两个可用区：每个 AZ 各有旧版实例，准备新版时先在两个 AZ 都启动新副本。只有在新版通过业务就绪检查后，才把它们加入目标组；不能先把整个 AZ 切走再补容量。

  1. 准备目标组确认旧版和新版实例所在 AZ、最小健康实例数与剩余容量；数据库及私网路由必须已就绪。
  2. 引入新版新实例先通过应用就绪检查，再按请求权重或稳定用户分组接入少量流量。
  3. 逐步扩流分别观察两个 AZ 的请求分配、错误率、p95 延迟与业务成功率，确认负载没有挤到单个 AZ。
  4. 保留退路旧版实例暂不释放；停止扩流时先把权重切回，再处理仍在旧连接上的请求。

权重分流、DNS 解析和实例比例不是同一个控制面：DNS 缓存可能延迟生效；某些负载均衡只按连接分配，少量长连接也可能承载大量请求。先验证实际平台的分流语义。

02 / 摘流不等于立即杀进程

就绪与健康

就绪决定是否接新请求，存活决定进程是否需重启。新版未加载配置或下游连接未建立时，应不接流量。

连接排空

停止接新连接后，等待正在执行的 HTTP 请求结束；WebSocket、SSE 与后台任务要另定超时和迁移策略。

会话与任务

粘性会话、本地文件及队列消费者不会随入口权重自动迁移；状态外置、幂等消费和优雅退出需提前验证。

若故障发生在一个 AZ，负载均衡摘流后剩余 AZ 必须有承载能力；自动扩容冷启动期间，连接池和托管数据库的上限仍可能先被打满。

03 / 失败时回退哪个控制面？

异常立即动作还要核对
新版错误率上升停止扩流，权重指回仍健康的旧版目标组旧版容量、未结束连接、业务请求幂等
单 AZ 失效负载均衡摘除失效 AZ 后端另一 AZ 容量、数据库切换和区域间网络成本
数据库模式不兼容暂停发布并评估前向修复；不要直接恢复旧快照旧版是否还能读取新版写入的数据，扩展/回填/收缩是否分阶段

“回滚流量”和“回滚数据”是两种操作。切回旧目标组不会抹掉新版已写入的业务数据；数据库变更必须在上线前验证双版本兼容。

04 / 云平台发布前的验收

  • 记录负载均衡目标组、各 AZ 健康实例数、切流权重及旧版保留时长。
  • 按版本和 AZ 拆分观测 5xx、p95、下单成功率；提前设定暂停和切回阈值。
  • 演练长连接排空、应用实例异常及单 AZ 不可用，而不是只测正常发布。
  • 确认 IaC 变更没有误删目标组或扩大公网入口，数据库模式变更可兼容旧版。

滚动、蓝绿、金丝雀的通用策略与容器发布控制，请继续阅读 云原生发布策略；这页聚焦云平台的负载均衡与可用区边界。

一句话：云上安全发布 = 有容量的多 AZ 后端 + 可观测的入口切流 + 能承受旧版回退的数据模型。
