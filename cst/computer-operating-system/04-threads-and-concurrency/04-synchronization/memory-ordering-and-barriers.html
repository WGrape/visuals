01可见性与有序性

第一层

概念与判定

同步不只管「互斥」，还管可见性与有序性。CPU 有 store buffer、编译器和 CPU 都会重排指令——「代码写的顺序」不等于「其他线程看到的顺序」。

图：data 与 ready 的经典重排陷阱。没有屏障，消费者可能先看到 ready 再读到旧 data。
内存序保证典型用途
relaxed只保证原子性，不保证顺序计数器、统计
acquire之后的读不能上移加锁后读共享数据
release之前的写不能下移解锁前发布数据
seq_cst全局单一顺序（最强）默认，最安全也最慢

x86 是 TSO（强内存模型）：读读、读写、写写不乱序，只有「写后读」可能重排。所以 x86 上 acquire/release 几乎零成本（编译屏障即可），而 ARM 是弱内存模型，需要真正的屏障指令。

03排障与边界

第三层

排障与边界

  • 双重检查锁定的坑：if (inst == NULL) { lock(); if (inst == NULL) inst = new X(); }——inst 必须原子且用 acquire/release，否则可能看到「已分配但未构造完」的对象。
  • volatile 不等于原子：C/C++ 的 volatile 只阻止编译器优化，不提供跨核可见性/原子性。Java 的 volatile 才有内存语义。
  • 只在 x86 测过：x86 的强内存模型会掩盖缺屏障的 bug，代码到 ARM（手机/服务器）就崩。必须按语言内存模型写，而非按 x86 行为写。
  • 原子操作也有开销：lock 前缀会锁 cache line，高竞争下比 mutex 还慢。

04原理与取舍

第四层

原理与取舍

内存序是把「正确性证明」交给类型系统：release 与 acquire 配对，建立 happens-before 关系，编译器与 CPU 都必须遵守。这比手写屏障更不容易出错。

强度性能正确性风险
relaxed最高高（需自行推理）
acquire/release高低（配对使用）
seq_cst最低最低（默认首选）

深入 Q&A

Q：为什么 x86 上 release 几乎免费？
A：因为 x86 硬件已经保证写写有序，编译器只需不重排即可，无需 sfence。

Q：Go 的 sync/atomic 有内存序吗？
A：有。Go 1.19+ 提供 atomic.LoadAcquire/StoreRelease 等显式内存序 API，之前只能靠 sync.Mutex 或 atomic 的隐式语义。
