什么时候适用？

判断信号：多个后端服务需要统一外部入口、路由和公共入口治理。

  • 移动端统一访问订单与用户服务
  • 统一入口鉴权和限流
  • 按路径或版本把请求转发给不同服务

和相近方案怎么区分？

相近方案选择边界
反向代理网关常基于反向代理，但还承载 API 级鉴权、路由和治理语义。
BFFBFF 按具体前端需求聚合接口；通用网关通常是跨客户端的公共入口。

最小伪代码

function gateway(request):
  identity = verifyToken(request.token)
  enforceRateLimit(identity)
  target = routes.match(request.path)
  return forward(target, request, timeout=2s)

边界：网关不应承载复杂领域规则；后端服务仍需保护自己的安全边界。

何时采用 API 网关

当多个客户端需要访问多个服务，并且鉴权、路由或流量策略需要统一治理时，可以在服务前设置 API 网关。它承担入口决策，领域规则仍由后端服务负责。

  • 放置位置：外部负载均衡之后、内部服务之前；服务间调用是否经网关，要按实际流量路径决定。
  • 边界取舍：反向代理侧重通用转发，API 网关管理 API 级规则；内部服务通信可由服务网格等机制治理。
  • 代价：统一入口也会集中故障风险，需无状态部署、横向扩展和清晰的超时预算。

API 网关：所有流量的唯一入口

微服务化以后，客户端如果直接连各个服务，会遇到一堆问题：要记住几十个服务地址、每个服务都要重复做鉴权、协议不统一（有的 gRPC 有的 HTTP）、跨域与限流各自实现。API 网关把这些横切关注点集中到一处，让后端服务只关心业务。

路由把 /api/order/** 转发到订单服务，支持路径重写与版本路由
鉴权校验 token / 签名，把用户身份透传给下游（不再各服务重复校验）
限流熔断按 IP、用户、API 维度限流；下游不健康时快速失败
协议转换对外 REST/JSON，对内 gRPC；或聚合多个接口为一个 BFF 接口
API 网关在架构中的位置：统一入口 + 横切能力下沉

网关 vs 反向代理 vs 负载均衡

组件工作层核心职责典型产品
负载均衡 L4传输层（TCP）按连接把流量分给后端，不解析内容LVS、云 SLB/CLB（四层）
反向代理 L7应用层（HTTP）解析 HTTP，做转发、TLS 终止、缓存、压缩Nginx、Envoy
API 网关应用层 + 业务语义在 L7 之上叠加鉴权、限流、灰度、API 治理、协议转换Kong、APISIX、Spring Cloud Gateway
Service Mesh 边车应用层（进程旁）服务间调用的治理：mTLS、重试、熔断、可观测Istio/Envoy、Linkerd

趋势：南北向流量（外部进入）走 API 网关，东西向流量（服务间）走 Service Mesh。两者边界在收敛，Envoy 就是同时被用作网关和边车的典型。

网关里最该做的五件事

① 认证与鉴权下沉

网关校验 JWT / OAuth2 token，校验通过后把 userId、tenantId 放进请求头透传给下游。下游信任该头——但这要求网关是唯一入口且内网可信。

  • 必须剥离外部传入的同名头，防止伪造
  • 内网建议再加 mTLS，防内部越权

② 限流（多维度）

按 客户端 IP / 用户 / AppKey / 接口 分别计数。算法常用令牌桶（允许突发）或漏桶（强制匀速）。

  • 单机限流不准 → 用 Redis + Lua 做集群维度
  • 超限时返回 429 + Retry-After

③ 熔断与降级

下游错误率或 RT 超阈值时，网关直接返回兜底响应，不再转发。避免线程池被拖死。

  • 半开状态试探恢复，不能一直熔断
  • 区分「读接口可降级」与「写接口不可随意降级」

④ 灰度与流量染色

按 header、cookie、用户分桶把流量导到不同版本，实现金丝雀发布与 A/B。

  • 染色标记要沿调用链透传（Trace 里带 tag）
  • 灰度比例要能一键回滚

⑤ 可观测三件套：访问日志（谁、什么时候、调了什么、耗时多少）、指标（QPS、错误率、P99）、链路追踪（TraceId 贯穿全链路）。没有这三样，线上问题几乎无法定位。

网关不该做的事

  • 不要放业务逻辑。网关里写业务判断会让它变成新的「大泥球」，且难以测试和发布。业务聚合应放在 BFF（Backend For Frontend）层。
  • 不要让所有内部调用都过网关。内网服务间调用过网关会多一跳、增加延迟、并让网关成为性能瓶颈。应走 RPC 直连 + 服务发现。
  • 不要做重量级报文转换。大 body 的 JSON↔XML 转换会吃掉大量 CPU，网关应该尽量「透传」。
  • 不要忽略超时设置。网关的 connect/read timeout 必须小于客户端超时，否则下游慢时网关先堆积，形成级联雪崩。
  • 不要忘了自身高可用。网关是全站单点，必须多实例 + 负载均衡 + 健康检查，且配置变更要能灰度（一次改错全站不可用）。

深入自检

有了 Service Mesh 还需要 API 网关吗？

需要，两者职责不同。Mesh 治理的是「服务到服务」的东西向流量，通常由基础设施团队统一管控，客户端无感知；网关面对的是「外部客户端进来」的南北向流量，需要做面向用户的认证、配额、开放平台计费、API 版本管理等业务化治理。简单系统可以只用网关；复杂系统两者并存，边界是「流量是否来自组织外部」。

网关做鉴权，下游服务还用再校验吗？

要看信任模型。如果网关是唯一入口、内网可信、且网关会剥离伪造的身份头，下游可以只做粗粒度校验。但更稳妥的做法是「纵深防御」：网关做认证（你是谁），下游做授权（你能不能操作这个资源）——因为越权判断（如用户 A 访问订单 B）只有持有数据的服务才能准确判断。零信任架构下还应加 mTLS 与服务级鉴权。

网关限流为什么要用 Redis 而不是本地计数？

本地计数器的上限是「单机配额」。若限流目标是「某用户每分钟 100 次」，而这个用户的请求被分散到 10 个网关实例，每个实例各允许 100 次，实际放过了 1000 次。集群维度限流需要共享计数：Redis + Lua 脚本保证原子性，或用专门的限流服务。代价是每次请求多一次 Redis 访问（约 0.5~1ms），可以做本地预扣 + 定期同步来降低开销。

网关超时应该怎么设？

遵循「逐层收敛」原则：客户端超时 > 网关超时 > 网关到下游的超时 > 下游内部调用超时，每层留 20%~30% 余量。同时区分连接超时（短，如 1~3s，快速发现不可用）与读超时（按接口 P99 的 1.5~2 倍设定）。还要设连接池上限与排队超时——否则下游慢时请求在网关排队，很快打满内存。
