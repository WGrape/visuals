存储层：Segment 与索引

分区被切成 Segment

一个分区不是单个大文件，而是拆成多个 segment（默认 1GB 或 7 天滚动）。

  • 好处：清理旧数据时直接删文件，无需重写
  • 每个 segment 配 .index（offset→物理位置）与 .timeindex（时间戳→offset）

稀疏索引 + 二分查找

Kafka 不为每条消息建索引，而是每隔若干字节建一条（index.interval.bytes 默认 4KB）。

  • 查找：先二分定位索引项 → 顺序扫描到目标 offset
  • 权衡：索引小（可全放内存），查找是「二分 + 少量顺序扫描」

保留策略 vs 消费进度

Kafka 删数据只看 retention（retention.ms / retention.bytes），不看有没有被消费。

  • 这是与传统 MQ 最大的区别，也是可重放的基础
  • 风险：消费严重滞后可能读到已被清理的数据 → 必须监控 lag

日志压缩（compact）

开启 cleanup.policy=compact 后，同 key 只保留最新值。

  • 适合：状态快照、物化视图、变更日志（CDC）
  • 不适合：需要完整事件序列的场景

消费者组与 Rebalance

Rebalance 是消费者组内重新分配分区的过程，期间整个组停止消费，是 Kafka 运维中最常见的抖动来源。

触发原因 1消费者加入或退出（正常扩缩容、发布重启）
触发原因 2消费者心跳超时或 poll 间隔超时（处理太慢被判死）
触发原因 3订阅的 Topic 分区数发生变化
减少抖动增大 session.timeout.ms 与 max.poll.interval.ms；减小 max.poll.records 使单批处理更快
更优方案用 CooperativeSticky 增量协作式分配（Kafka 2.4+），避免全局暂停
静态成员设 group.instance.id 使重启不触发 Rebalance（Static Membership）
# 典型的「处理太慢导致 Rebalance 循环」问题 max.poll.records = 500 # 一次拉 500 条 业务处理 500 条耗时 8 分钟 max.poll.interval.ms = 300000 # 5 分钟没调用 poll 就被踢出组 → 被踢出 → Rebalance → 重新拉取同样 500 条 → 又被踢出 ... # 修法（三选一或组合）： max.poll.records = 50 # 减少单批数量 max.poll.interval.ms = 900000 # 放宽超时（需评估故障发现速度） 改为「poll 线程 + 业务线程池」分离，poll 线程及时返回

深入自检

Kafka 还需要 ZooKeeper 吗？

取决于版本。2.8 之前 Kafka 强依赖 ZooKeeper 存元数据（Broker 列表、Topic 配置、ISR、控制器选举）。2.8 起引入 KRaft 模式（Kafka Raft Metadata），用内置的 Raft 协议管理元数据，不再需要外部 ZooKeeper；3.x 起 KRaft 已可用于生产，4.0 完全移除 ZooKeeper 支持。KRaft 的好处：减少一个外部依赖、元数据变更更快（控制器直接推送而非经由 ZK watch）、支持更多分区（ZK 模式下万级分区就有压力）。新建集群应直接用 KRaft；存量集群按版本规划迁移。

offset 应该自动提交还是手动提交？

生产环境推荐手动提交。自动提交（enable.auto.commit=true）是「按固定间隔提交已拉取的最大 offset」，与业务是否处理完无关，会造成两类问题：① 提交后业务处理失败 → 消息丢失（因为位点已前进）；② 业务处理成功但尚未到提交间隔就宕机 → 重复消费。手动提交能精确控制：业务处理成功后才 commitSync（同步，可靠但慢）或 commitAsync（异步，快但需处理失败）。实践中常用「异步提交 + 关闭前同步提交」的组合，并按分区粒度提交以保证顺序正确性。

Kafka 的分区副本是怎么保证不丢数据的？

靠 ISR（In-Sync Replicas）机制。每个分区有一个 Leader 和若干 Follower，Follower 持续从 Leader 拉取日志。与 Leader 差距在 replica.lag.time.max.ms（默认 30s）内的副本留在 ISR 中。生产者设 acks=all 时，Leader 要等 ISR 中所有副本都写入才返回成功，因此只要 ISR 中还有副本存活，已确认的消息就不会丢。再配合 min.insync.replicas=2，可保证 ISR 少于 2 个时写入直接失败（避免只写一份就认为成功）。ISR 全部失效时，若 unclean.leader.election=false，则该分区不可写——宁可不可用也不丢数据，这是典型的 CP 选择。

怎么排查 Kafka 消费慢的问题？

按顺序排查四个层面：① 看 lag 是持续增大还是波动——持续增大说明消费能力不足，波动说明有周期性抖动（如 Rebalance）；② 看消费者数是否已达分区数上限——已达上限则加消费者无效，必须加分区；③ 看单条处理耗时——如果是业务逻辑慢（如每条都查数据库），考虑批量化或加缓存；④ 看是否有 Rebalance 循环——检查 max.poll.interval.ms 与实际处理耗时的关系。常用命令：kafka-consumer-groups.sh --describe 查看 LAG 列，配合监控看 records-lag-max 与 rebalance-total 指标。
