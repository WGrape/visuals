常见误区

误导性图表

先建立直觉：图表是翻译器

原始数据是一堆数字，人脑不擅长直接从中看出规律。图表的作用是把数字翻译成视觉信号——长短、高低、颜色深浅，这些是人眼能在零点几秒内感知的。

但翻译会失真。选错图表类型，等于翻译错了——读者会得出错误结论，而且毫无察觉。

怎么选图表：按目的而非喜好

你想表达什么合适的图表为什么
比较大小柱状图 / 条形图人眼对长度差异最敏感
看趋势变化折线图斜率直观反映变化速度
看占比构成饼图（少分类）/ 堆叠柱状图饼图只适合 3~5 个分类且总和有意义
看分布直方图 / 箱线图能看出集中趋势与异常值
看两个变量关系散点图一眼看出相关性
看地理分布地图（choropleth）地域差异一目了然
看进度达成仪表盘 / 进度条目标与实际的差距
饼图是最常被滥用的图表。人眼不擅长比较角度和面积，尤其当分类超过 5 个、或各扇区大小接近时，几乎无法判断谁大谁小。改用条形图按大小排序，可读性会好得多。饼图只适合「展示 2~3 个分类、且强调某部分占比」的简单场景。

指标体系：先定义，再展示

做看板前必须先想清楚指标。指标 = 维度 + 度量 + 口径：

  • 维度：从哪些角度看（时间、地区、渠道、用户类型）；
  • 度量：看什么数值（GMV、订单数、转化率）；
  • 口径：最关键也最容易含糊——GMV 含不含退款？活跃用户怎么定义？
口径不一致是 BI 项目最常见的失败原因。同一个「日活」，A 报表算的是「打开 App」，B 报表算的是「产生任意行为」，两个数字对不上，会议开半天都在争论谁对。解决：把指标定义沉淀到元数据，全公司唯一，看板上可直接查看口径说明。

看板设计：金字塔结构

设计原则：上层只放结论（好不好），下层提供归因路径（为什么）。好的看板应该让人在 5 秒内知道「情况如何」，并在 1 分钟内能下钻到原因。

四个常见误区

误区问题正确做法
Y 轴不从 0 开始微小差异被视觉放大成巨大差距柱状图 Y 轴必须从 0 开始（折线图可视情况放宽）
双 Y 轴两条线的「交叉点」是人为的，取决于缩放尽量拆成两个图，或改用双指标组合图并明确标注
用颜色表达数值人眼无法准确比较颜色深浅用长度/位置表达数值，颜色仅用于区分类别
图表过于花哨3D 效果、阴影、渐变干扰阅读数据墨水比原则：去掉一切不承载信息的装饰

🎯 面试问答

Q：为什么业务方总说看板「不好用」？
A：通常是三个原因：① 指标口径不清——数字和别的报表对不上，不敢用；② 只有汇总没有下钻——看到「转化率下降」却无法查是哪些渠道/人群导致的；③ 更新不及时——数据是昨天的，无法支撑今天的决策。解决顺序：先统一口径（最关键），再补下钻能力，最后优化时效性。

Q：饼图到底该不该用？
A：少用。人眼不擅长比较角度和面积。当分类超过 3~5 个、或各扇区大小接近时，几乎无法判断谁大谁小。替代方案：用条形图按大小排序——长度比较是人眼最擅长的。饼图只适合「2~3 个分类、要强调某一部分占比、且总和有明确意义」的简单场景。

Q：Y 轴一定要从 0 开始吗？
A：柱状图必须——因为柱状图的长度编码了数值，不从 0 开始会严重夸大差异（10 和 11 看起来像差 10 倍）。折线图可以放宽——折线关注的是趋势和变化率而非绝对高度，截断 Y 轴反而能更清楚地展示波动，但要明确标注轴的范围，避免误导。

Q：指标太多，看板怎么组织？
A：用金字塔分层：顶层 3~5 个北极星指标（一屏说清「好不好」），中层按维度拆解（时间/地区/渠道，回答「哪里有问题」），底层可下钻的明细（回答「为什么」）。不要把所有指标平铺在一屏——那等于没有重点。另外每个看板要有明确的受众和目标，给高管和给运营的看板不应该长一样。

BI 分层架构与选型

一套 BI 从下到上是：数据源 → 数仓分层 → 语义层（指标定义）→ 查询引擎 → 可视化 → 分发。绝大多数 BI 项目的问题不在可视化，而在第 3 层的指标口径不统一。

层做什么常见选型关键考量
数据源业务库、埋点、日志MySQL / Kafka / 对象存储接入方式是 CDC 还是定时抽
数仓分层ODS → DWD → DWS → ADSHive / Spark / Iceberg分层是否清晰、复用率
语义 / 指标层统一口径：GMV、DAU 怎么算自研 / dbt / MetricFlow / 数据中台最关键也最容易被跳过
查询引擎即席查询要快ClickHouse / Doris / Presto / StarRocksP95 响应 < 3s
可视化图表与看板Superset / Metabase / Tableau / 帆软自助程度、权限
分发订阅、预警、嵌入业务系统邮件/企微/iframe

分层与命名规范

# 分层规范（业界通用的 ODS/DWD/DWS/ADS）
#   ODS  原始数据层      与源系统 1:1，只做清洗不做业务加工，保留历史
#   DWD  明细数据层      维度退化、脱敏、统一枚举，最细粒度的业务事实
#   DWS  汇总数据层      按主题预聚合（如「用户日活表」），供上层复用
#   ADS  应用数据层      面向具体报表/接口的最终结果，可冗余
#
# 命名规范（省掉大量沟通成本）：
#   表：   {层}_{主题域}_{业务过程}_{粒度}_{周期}
#   例：   dws_trade_order_user_1d      (交易域-订单-用户粒度-日)
#          ads_trade_gmv_1d
#   字段： 金额统一 amt_、数量 cnt_、时间统一 _at / _date

# 指标定义模板（写进指标平台，避免各说各话）
#   指标名：日均活跃用户 DAU
#   业务口径：当日有有效访问行为的去重用户数
#   技术口径：COUNT(DISTINCT user_id) FROM dwd_log WHERE dt=? AND event IN (...)
#   维度：渠道、平台、版本、地区
#   负责人 / 变更记录

BI 项目最常见的失败模式：跳过语义层，让每个报表自己写 SQL 算指标。结果就是「财务的 GMV 和运营的 GMV 差 8%」，然后花几周对账。正确做法是先把 Top 20 个核心指标的口径写死在指标层，报表只做展示。

自助 BI 为什么常常失败？

三个原因：① 数据模型不适合自助——直接把 ODS 明细表开放给业务，业务看不懂也不会用；② 指标口径没统一——自助算出来的数和中台对不上，信任崩塌；③ 没有权限与成本控制——一个新手写了个全表扫描拖垮整个集群。正确路径是：先做好 DWS 宽表 + 指标层，再开放自助，同时配好资源队列和查询超时。

实时看板该怎么做？

分档：① 秒级（大屏监控）——走流式链路 Flink → Redis/ClickHouse，成本高，只给核心指标；② 分钟级——微批（1~5 分钟）写入 OLAP，性价比最高，绝大多数「实时」需求其实分钟级就够；③ T+1——离线跑批，适合复盘类。判断标准：决策动作的频率——如果人几分钟才看一次，做秒级就是浪费。

看板越做越慢怎么办？

按这个顺序查：① 是不是直连明细表了（应走 ADS 预聚合）；② 图表数是否过多（合并或减少，或用标签页延迟加载）；③ 时间范围是否过大（加默认值和上限）；④ 查询引擎是否需要物化视图/rollup 预聚合（ClickHouse 的 MaterializedView、Doris 的 Rollup）；⑤ 加结果缓存。这五步通常能解决 90% 的慢看板问题。
