云平台架构 / 发布与部署

云上交付流水线

从一次代码提交，到一份可追溯的制品在测试和生产环境晋级；不要在生产机器上临时拼装新版本。

流水线 环境与配置 发布闸门 示例路径

01 / 代码如何变成云上的一个版本

交付的核心不是“自动运行一段脚本”，而是确保同一份已验证制品沿环境推进，每次发布都能回答：谁批准、部署了什么、何时生效。

  1. 提交与验证静态检查、单测、依赖扫描和必要的集成测试在构建阶段阻止明显错误。
  2. 构建制品构建一次镜像或程序包，记录提交、版本及内容摘要，推送到有访问控制的制品仓库。
  3. 测试环境按摘要部署同一制品，注入环境配置，运行接口与数据库兼容性检查。
  4. 生产晋级经过审批/变更窗口，把同一摘要部署到生产，而不是重新构建一个“差不多”的版本。

镜像标签可以移动，内容摘要不会；部署记录应保存摘要、配置版本和关联变更单。这样回滚才有可定位的目标。

02 / 分开制品、配置、秘密和云资源

制品

包含应用代码与运行依赖，不为每个环境改一份二进制；制品仓库与生产账户实行最小权限。

配置与秘密

数据库地址、限流阈值等配置按环境管理；密码、令牌存秘密管理服务，避免写进代码、镜像或部署日志。

基础设施

VPC、负载均衡和实例组有独立变更周期；资源变更先预览影响，再与应用版本协调发布。

环境隔离也包括账号/项目、网络和数据：测试环境不能随手指向生产数据库；生产部署身份只拿到发布所需权限，不应拥有整个云账号的管理权。

03 / 发布闸门在什么时候拦住错误？

关口必须通过的信号失败时怎么处理
合入前构建、单测与安全检查拒绝合入，不生成生产候选版本
测试环境端到端流程、接口兼容、迁移预演修复后重新验证，而非绕过环境直接发版
上线前审批、生产容量与回滚目标已确认暂停晋级，先补齐监控与运行手册
上线后错误率、延迟与业务指标观察窗口停止扩流并回退应用版本

“部署成功”只意味着系统执行了变更，不能替代用户视角的验收；健康探针正常时，订单失败率依旧可能上升。

04 / 订单 API 的一次真实晋级

开发提交新的订单字段 → 构建制品 v2（摘要固定） → 在预发布环境验证旧客户端仍可下单 → 准备兼容旧版本的数据库扩展 → 生产先部署小比例实例 → 比较 5xx、p95 延迟和下单成功率 → 再逐步放量。

如果新增字段需要不可逆迁移，先停止发布并改成“扩展 → 回填 → 切换读写 → 收缩”多阶段变更，不能把回滚寄托在数据库快照上。更通用的流水线和 GitOps 概念见 云原生 CI/CD 与 GitOps。

一句话：先确定交付物是什么、能否复现，再讨论怎样放量。
