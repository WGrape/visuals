Redis 是如何"找到"过期 Key 的？

被动（惰性）检查 + 主动（定期）自适应抽样扫描，一条不漏地说清楚

① 先说结论：Redis 不维护"过期列表"

Redis 没有一张"已过期 Key 清单"，也不会给每个 Key 挂定时器。 所谓"找到过期 Key"，靠的是两条并行的发现路径：
  • 被动 惰性删除（Lazy / Passive）：你访问到它时才顺手查一下、过期就删。
  • 主动 定期删除（Periodic / Active）：后台定时随机抽一批 Key 检查，过期就删。
你的判断完全正确：确实就是"被动 + 主动"两种。下面先把"Key 到底存在哪、过期时间记在哪"讲清楚，否则后面两条路都没法理解。

每个 Redis 数据库（redisDb）其实有两张表

怎么判断一个 Key 过期了？ 看它在 expires 表里有没有记录，再拿当前 Unix 时间戳和那条记录比较：当前时间 > expires[key] 就过期。没在 expires 表里的 Key 就是"永不过期"。所以"找过期 Key"本质就是查这张 expires 表。
为什么不用定时器（定时删除）？ 给每个带 TTL 的 Key 挂一个定时器，过期瞬间触发删除——内存最友好，但几百万 Key 就要维护几百万个定时器，CPU 直接被打爆。Redis 事实上放弃了这种方案，只保留惰性 + 定期两条路。

② 被动路径：惰性删除（你访问到才查）

这是最直觉的一条路。任何读写命令在执行前，都会先调用 expireIfNeeded() 问一句"这个 Key 过期没？"。没过期就正常执行；过期了就当场删除，再告诉客户端"没有这个 Key"。

// db.c / expireIfNeeded() 简化逻辑（已核实，勿改） int expireIfNeeded(redisDb *db, robj *key) { if (!keyIsExpired(db, key)) return 0; // expires 里没记录 或 未过期 if (server.masterhost != NULL) return 1; // 从节点不主动删，等主节点 DEL 同步 notifyKeyspaceEvent(NOTIFY_EXPIRED, "expired", key, db->id); return dbDelete(db, key); // 删：dict + expires 一起摘掉 }

✅ 优点

对 CPU 极友好——只有"被访问"的 Key 才付检查成本，不空转、不扫全库。

❌ 代价

一个 Key 如果永远没人访问，就算早过期了也会一直占着内存——这就是"被动路径兜不住"的内存泄漏风险，所以需要下面的主动路径补位。

主从细节（易考点）： 从节点本身不执行删除，它只是被动等主节点发来的 DEL 命令来同步删除。Redis 3.2 之后从节点在读取时也会顺手过滤掉过期 Key（返回空），但"删除动作"仍只发生在主节点，保证主从一致。

③ 主动路径：定期删除（后台"随机抽一批"扫描）

这是你问题里的重点——"主动扫描，怎么扫的？"。答案先给出来：不遍历全库，而是自适应随机抽样。

核心算法（activeExpireCycle，expire.c）： 后台每隔一小段时间，从 expires 表里随机抽 20 个 Key 检查；把过期的删掉；如果这 20 个里过期比例 > 25%（即 > 5 个），就再抽 20 个继续扫，直到比例降到 25% 以下或时间预算用完。

为什么是"抽样"而不是"扫全库"？

如果真去遍历全部几千万个 Key 找过期，一次就要卡好几秒甚至几分钟，主线程直接阻塞、请求全超时。随机抽样每次只看 20 个，成本固定且极小；再加上它每秒跑约 10 次，正常情况每秒就能清掉约 200 个过期 Key，足够把长期不被访问的过期 Key 慢慢清干净，同时几乎不占 CPU。

两个关键设计，决定了它"聪明又温柔"

🔁 current_db 指针（轮询）

有个静态变量记住"上次扫到第几个 db"。下次从那里接着扫，扫完所有 db 再回到 0。这样 16 个库被均匀轮询，不会出现"某个 db 一直没被扫到、过期 Key 堆积"。

⏱ 时间预算 + 自适应循环

每轮有 CPU 时间上限（slow 模式约 25ms）。过期比例低就很快收工；一旦某批抽样里过期 > 25%，说明"过期潮"来了，它就自动加力多扫几轮，把内存水位压下去——平时几乎不占 CPU，忙时才多干活。

SLOW 模式 vs FAST 模式（双档自适应）

主动扫描其实有两个档位，配合起来既省 CPU 又能救急：

维度SLOW 模式（默认巡逻）FAST 模式（救急补漏）
触发入口时间事件 serverCron事件循环 beforeSleep()（进入 epoll_wait 前）
执行频率每秒约 10 次（hz 默认 10，每 100ms 一次）最高每秒约 1000 次（每 ~1ms 一次）
单次时长上限约 25ms（= 1000000×25÷100÷hz 微秒）仅 1ms（硬上限，极短）
触发条件定时触发，无条件仅当上次 SLOW 因超时被中断，或预估过期占比 > 10% 时才跑（距上次 < 2ms 会跳过）
目的日常巡逻，控制内存整体水位在新请求到来前顺手清掉过期 Key，避免请求时触发惰性删除造成延迟毛刺

⑤ 两条路怎么配合？还有第三道防线

分工一句话： 惰性删除是"最后一道关"（保证你读到的一定干净）；定期删除是"日常保洁"（把没人访问的过期 Key 慢慢扫掉，控内存水位）；两者都兜不住、内存真写满了，就交给内存淘汰策略（可能删掉还没过期的 Key）来救急——但那是另一回事，详见《过期删除 vs 内存淘汰的区别》一文。

⑥ 怎么知道它在干活？监控与调优

# INFO stats 里看这几个字段 expired_keys # 累计被「过期逻辑」删掉的 Key 总数（惰性+定期都算） expired_stale_perc # 预估「已过期但还没删」的 Key 占带 TTL Key 的比例（FAST 模式触发依据） expired_time_cap_reached_count # 定期删除「撞到时间预算上限」的次数；持续增长说明过期潮压力大

⚙️ 调 hz 提高清理频率

hz 10（默认）→ 调到 hz 50~100 会让 SLOW 扫描更频繁，过期 Key 清得更快，但更费 CPU。不建议随便破百。

🌊 警惕"过期风暴"

大量 Key 在同一秒集中过期（如都用 EXPIREAT 同一时刻），会让抽样里过期比例瞬间 > 25%，定期删除被迫循环加力，造成延迟毛刺。给 TTL 加随机抖动（如 3600 + rand(0,300)）即可化解。

⑦ 速查总结

  1. 不维护过期列表、不挂定时器：过期信息只存在每个 db 的 expires 表（key → 绝对过期时间戳）。
  2. 被动（惰性）：命令执行前 expireIfNeeded() 查 expires 表，过期就删、返回 nil。CPU 友好，但没人访问就清不掉。
  3. 主动（定期）：后台自适应随机抽样——每轮从 expires 抽 20 个，删过期的；抽样过期 > 25% 就继续循环；用 current_db 轮询各库、有 CPU 时间预算（slow≈25ms）。
  4. 双档：SLOW（serverCron，10×/s，25ms）日常巡逻；FAST（beforeSleep，~1ms）救急补漏。
  5. 三道防线：惰性把关 → 定期巡逻 → 内存淘汰救急。
