从一端到另一端的全景

把 Kafka 看成一条可重放、可并行、持久化的日志流水线，比把它当成「消息队列」更容易理解它的设计。

顺序追加的文件，配一个稀疏索引（偏移量 → 物理位置） 查找时先用二分定位到 segment，再用索引定位到大致位置，最后顺序扫一小段 读多走操作系统的页缓存 + 零拷贝（sendfile），数据不必在内核与用户态之间来回复制 这就是 Kafka 即使数据全在磁盘上，吞吐依然极高的原因：它把顺序 IO 与零拷贝用到了极致

生产端：四个决定成败的动作

动作含义要点
分区决定消息进哪个 Partition有 key 就按 key 哈希（保证同 key 有序）；无 key 轮询
批量攒够一批再发batch.size 与 linger.ms 共同控制「攒多少、等多久」
压缩整批压缩后发送批越大压缩率越高；代价是 CPU
确认何时算写成功acks=0 最快但可能丢；1 只等 leader；all 等所有 ISR —— 可靠性要求高就用 all

幂等与事务：开启幂等后，生产者带上编号与序列号，服务端能识别并丢弃因重试产生的重复消息；事务则进一步保证「发到多个分区」这组动作要么都可见要么都不可见。它们解决的都是「网络不确定导致的重试」问题。

典型的高可靠生产者配置思路 acks = all # 等 ISR 全部确认 enable.idempotence = true # 幂等：防重试重复 max.in.flight = 5 # 配合幂等，可保持并发又不乱序 retries = 大一些 # 网络抖动时自动重试 compression.type = lz4/snappy # 批压缩，省带宽 linger.ms = 5~20 # 多攒一点，提高吞吐 代价：可靠性与吞吐都提升的同时，延迟会上升。 配置永远是在「延迟 / 吞吐 / 可靠性」三角里选点。

服务端：副本、ISR 与高水位

每个 Partition 有多个副本，其中一个当 leader 负责读写，其余作为 follower 拉取同步。

ISR「跟得上」的副本集合 —— 落后太多会被临时踢出。
LEO每个副本自己写到的最新位置（log end offset）。
HW 高水位所有 ISR 都已同步到的位置。消费者只能看到 HW 之前的消息。
acks=all 的对象是 ISR 而不是全部副本 —— ISR 为空时写入会失败。

这个机制解释了两个常见现象：① follower 落后被踢出 ISR 后，写入只需等剩下的副本，延迟下降但冗余度也下降；② 消息只有在被所有 ISR 同步（越过 HW）后才对消费端可见，这就是「已提交」的含义。

保留策略：Kafka 的消息不会因为被消费而删除 —— 它按时间或大小保留（如保留 7 天），到期整体删除旧 segment。另一种是 log compaction：按 key 只保留最新值，适合「状态快照」类场景（如保存每个用户的最新资料）。

消费端：组、再均衡与提交

  1. 消费组：同一组内的消费者分摊分区（一个分区同时只能被组内一个消费者消费）；不同组相互独立，各自都能读到全量 —— 这就是「广播」与「负载均衡」两种模式的实现方式。
  2. 再均衡（rebalance）：成员变化或分区数变化时重新分配。期间整个组会短暂停顿，是消费抖动的常见来源。
  3. offset 提交：决定「处理到哪了」。自动提交方便但可能丢或重复；处理完再手动提交才能得到可靠的语义。
  4. 至少一次：先处理再提交 → 处理成功但提交失败时会重复消费（业务必须幂等）。
  5. 至多一次：先提交再处理 → 可能丢。很少用。
消费端幂等的常见做法 ① 用业务唯一键（订单号）做去重表 / 唯一索引 ② 用 (topic, partition, offset) 记录已处理位置，与业务操作放在同一个事务里 ③ 让下游操作本身幂等（如 UPSERT、SETNX、状态机流转） 重点：Kafka 只保证「分区内有序」， 跨分区的全局顺序需要自己设计（通常是按业务 key 分区）。

深入自检

Kafka 为什么这么快？

五件事叠加：① 顺序写磁盘（比随机写快一两个数量级）；② 页缓存（热数据实际在内存，绕开了 JVM 堆）；③ 零拷贝（sendfile 让数据不经过用户态复制）；④ 批量与压缩（把小消息攒成大块，摊薄每次请求的固定开销）；⑤ 分区并行（天然横向扩展）。它几乎没有做什么「聪明的算法」，靠的是把顺序 IO 与批量用到极致。

消息堆积了怎么办？

先判断是生产太快还是消费太慢。消费慢最常见：① 加消费者实例（但分区数是上限，消费者不能多于分区数）；② 提高单条处理效率（批量写下游、并行处理）；③ 必要时增加分区数（注意会改变 key 的分区映射）。另外要确认是不是某条消息反复失败卡住了整个分区 —— 死信队列是必备的兜底。

消息会丢吗？

三个环节都可能：① 生产端 acks=0/1 且没有重试；② 服务端 ISR 全挂或 acks=1 时 leader 刚写完就宕机；③ 消费端先提交 offset 再处理，处理失败就再也读不到。要避免丢失，需要三端一起配置：acks=all + 幂等 + 处理完再提交 offset，并且接受吞吐与延迟的代价。

分区数怎么定？

没有万能公式，但有几个约束：① 分区是并行度上限（消费者数不能超过它）；② 分区越多，文件句柄、内存、再均衡时间都上升；③ 分区数变会改变 key→分区的映射，影响顺序性。常见做法是先按目标吞吐估算（单分区通常能到几千到上万条每秒），留出 1.5~2 倍余量，并提前规划好而不是频繁调整。
