超时预算：DNS、连接、TLS、读写与总截止时间怎么配

用 800 毫秒 API 请求拆解各阶段等待，避免“每层都设 800 毫秒”放大故障。

“请求超时”必须问超在哪一段

一次 HTTPS API 调用可能经历 DNS 解析、TCP 建连、TLS 握手、请求体写出、服务器排队与处理、响应首字节、正文持续读取。客户端库可能分别提供 DNS、connect、TLS handshake、write、read idle 或 total timeout，名字和覆盖范围依实现不同。总截止时间约束从请求开始到最终完成的全部时间；单阶段超时只限制其中某段。日志若只写“timeout”，无法知道是网络路径、证书、服务端慢还是客户端读取阻塞。

例如客户端把 connect timeout 设 200 毫秒、read timeout 设 500 毫秒，却没有总截止时间。如果服务器每 400 毫秒送一小字节，某些“读超时”定义会不断重置，整个请求可能持续很久。业务需要的是明确的总预算，再给阶段设置合理上限。

一条 800 毫秒预算

用户接口目标是 800 毫秒。DNS 和连接可能占 100 毫秒，TLS 占 80 毫秒，请求发送与代理排队占 70 毫秒，服务端处理占 400 毫秒，响应传输及余量 150 毫秒。这里不是固定配额表，而是说明各阶段相加必须落在总截止时间内。若 DNS 已耗 300 毫秒，后端不能仍假装自己拥有完整 800 毫秒。调用链应传递剩余时间或绝对 deadline。

阶段阈值要由真实分布和业务目标确定。DNS 冷缓存、跨地域 RTT、证书验证、请求体大小都会改变正常耗时；设得过短会误杀健康请求，设得过长会拖住资源。先测 P50/P95/P99，再决定预算和降级行为。

逐步推演

分阶段计时

DNS、connect、TLS、write、first byte、read 各留证据。

传递 Deadline

后端拿到剩余时间，不重新获得完整预算。

控制重试

每次尝试与退避都从同一总预算扣。

处理未知结果

写操作超时后按幂等键查询状态。

嵌套调用如何放大等待

网关调订单服务，订单服务调库存，再调支付。若每层各设置 800 毫秒，最坏情况下三段串行就可能超过用户可接受时间。上游超时后，下游可能仍在处理并占用线程、数据库连接和支付额度。正确做法是把剩余总 deadline 传到下游，并给每步留日志与回包余量；接近截止时间时可直接拒绝新的昂贵调用。

取消信号是减少浪费的建议，不保证撤销已提交的操作。支付已扣款但网关 504，客户端看到的是结果未知，不是交易失败；应有幂等键和状态查询。对只读请求可在剩余预算内尝试重试，对写请求要按业务语义处理。

重试从同一个预算里扣

如果一次调用最多 800 毫秒，第一次尝试耗 500 毫秒，剩 300 毫秒；再等 200 毫秒退避，仅剩 100 毫秒给第二次尝试。重试配置若只写“最多三次”，而每次重新获得 800 毫秒，总等待可能超出数秒并放大下游负载。重试应有最大次数、总截止时间、退避和随机抖动，并避免上游、网关、SDK 同时对同一请求各重试三次。

服务器返回 429/503 和 Retry-After 时，客户端还要判断建议等待是否超过用户当前预算；超过就应尽早返回或转异步处理，而不是固执等待。若服务端确实可能长时间处理，可设计作业 ID 和查询接口。

不同超时现象的证据

DNS 超时看解析器和响应码；connect 超时看 SYN 是否得到 SYN-ACK 与回程路由；TLS 超时看握手阶段和证书；write 超时可能是客户端发送缓冲、网络窗口或服务器不读；首字节慢可能是代理排队、应用或数据库；正文读得慢可能是服务端流式生成、网络拥塞或接收应用慢。抓包和分阶段 trace 能定位哪一段在等待。

如果每次恰好在固定 60 秒失败，优先找哪层代理或客户端配置了 60 秒空闲/总超时。若只在大响应失败，要看读超时是否是“每次读等待”还是“整个下载期限”，并检查 PMTU、窗口与代理缓冲。

服务端与代理协同

代理可能先于后端超时并返回 504，但后端仍继续处理。应让后端知道客户端 deadline，必要时取消无意义的计算。连接池获取连接、线程池排队和数据库查询也要计入服务端预算；如果只给数据库设置 500 毫秒，却让请求在连接池排队两秒，用户仍会超时。监控应记录 queue time、upstream connect time、first byte time、total time 和取消原因。

链路上不同代理的 timeout 若顺序颠倒，可能产生难理解的错误：内层 60 秒、外层 30 秒，外层先返回，内层继续浪费 30 秒。应按系统拓扑安排各层限制，并保留少量回包余量。

故障演练与验收

分别注入 DNS 不响应、目标端口无回包、TLS 服务卡住、后端处理超时、慢速流式正文和“提交成功但响应丢失”。每次记录哪个阶段触发、最终状态码、下游是否取消、业务是否有副作用。用同一请求 ID 串联客户端、代理和服务端时间线。

最后验证总等待不超过用户目标，并在超时时给出可行动的结果：可安全重试、处理中可查询、或明确失败。没有总预算和业务状态查询的“超时”只是把未知结果推给用户。

各阶段超时建议值

阶段建议值说明过长后果
DNS 解析2 – 5 s通常几十 ms，5 s 已足够宽裕用户白屏等待
TCP 建连（connect）1 – 5 s要短：连不上说明端口不通/被拦，重试比等待有效占用连接槽位
TLS 握手5 – 10 s含证书下载与 OCSP，比 TCP 长一些同上
首字节（TTFB / read）按 P99 × 2–3业务相关，慢接口可 30 s慢请求堆积吃光资源
整体 deadline各阶段之和 × 1.2留一点余量—

典型 HTTP 客户端超时配置（以 Go 为例）：

Go 超时配置

client := &http.Client{
    Timeout: 30 * time.Second,          // 整体 deadline，兜底
    Transport: &http.Transport{
        DialContext: (&net.Dialer{
            Timeout:   2 * time.Second,  // TCP 建连
            KeepAlive: 30 * time.Second,
        }).DialContext,
        TLSHandshakeTimeout:   5 * time.Second,   // TLS 握手
        ResponseHeaderTimeout: 10 * time.Second,  // 等响应头（TTFB）
        ExpectContinueTimeout: 1 * time.Second,
        IdleConnTimeout:       90 * time.Second,  // 空闲连接保持
        MaxIdleConns:          100,
        MaxIdleConnsPerHost:   10,
    },
}
// 注意：Timeout 是整体的，Transport 里的是分阶段的
// 分阶段超时必须 < 整体超时，否则分阶段配置形同虚设

超时级联与常见错误

  • 超时必须层层递减：网关 > 服务 > 下游。例如网关 30 s、服务 20 s、下游调用 10 s。若反过来（下游 30 s、网关 10 s），网关超时重试时下游还在忙 → 白做 + 放大负载。
  • 最容易漏的是“整体超时”：很多客户端只配了各阶段超时，没有整体 deadline，结果 DNS 2 s + connect 5 s + TLS 10 s + read 30 s 叠加起来可能 47 s 才失败。整体超时必须设。
  • 连接超时要短，读超时要长：连不上（1–2 s）说明目标不可达，快速失败重试更有效；读超时（按 P99）要给足，因为服务端确实在处理。
  • 空闲超时要小于中间设备：IdleConnTimeout 应小于 LB/NAT 的空闲超时（常见 60–350 s），否则连接池里会有“已死但客户端以为可用”的连接。建议 90 s 或直接靠 TCP keepalive。
  • 重试要有预算：总重试不超过请求量的 10%，且退避加抖动。否则超时重试会放大故障。
  • 排障：用 curl -w 分解看卡在哪个阶段；服务端看处理时间是否与客户端感知一致（不一致说明是网络/排队，不是处理慢）。
设置了超时为什么还会卡很久？

检查是否有多层重试：客户端超时 5 s × 重试 3 次 = 15 s，若外层网关再重试 2 次就是 30 s。要计算总的端到端时间：单次超时 × 重试次数 × 层级数。

连接超时设 1 秒会不会太短？

同机房/同地域通常 1–2 ms 就建连，1 s 非常宽裕。跨地域/公网可放宽到 3–5 s。关键是要设——不设就是无限等待（Go 默认是无限）。

自检

每层串行调用都设 800 毫秒超时，能保证用户请求 800 毫秒内完成吗？

不能。各层等待可能相加，还可能有排队和重试；应传递统一总截止时间。
