TCP Keepalive、HTTP Keep-Alive 与应用心跳不是一回事

从长连接空闲后断线的时间线解释三种机制各自检测或复用什么。

同一个 keepalive 名字指向不同层

HTTP Keep-Alive 通常指复用一条 TCP 连接发送多个 HTTP 请求，减少重复握手；TCP keepalive 是操作系统对空闲 TCP 连接发探测段，判断对端是否仍可达；应用心跳是业务协议定期交换有语义的消息，如 WebSocket Ping/Pong 或自定义心跳。三者解决的问题不同，不能因为已开启 HTTP 持久连接就认定故障会及时被发现。

长连接处于 ESTABLISHED 只说明本机内核尚未收到关闭或复位信息，不保证远端进程仍在工作。若 Wi-Fi 消失、NAT 映射过期或中间链路断开，而双方都没有新数据，连接状态可能长时间保持“看似正常”。检测需要主动通信与合理超时。

TCP keepalive 的行为

操作系统可在连接空闲一段时间后发探测，若多次没有回应，向应用报告连接失效。默认空闲等待时间在很多系统上较长，通常不适合作为秒级业务故障检测；配置项涉及开始探测前空闲时长、探测间隔和失败次数。具体平台默认值和可调范围不同，要在目标系统验证。

TCP keepalive 证明 TCP 对端栈有回应，并不证明应用线程能及时处理请求。一个服务进程卡在死锁中，内核可能仍按规则回应某些 TCP 探测；业务层心跳若由应用逻辑处理，能覆盖更高层的健康问题。但应用心跳过频又会增加空口唤醒、NAT 状态和服务器负担。

HTTP Keep-Alive 的边界

浏览器或客户端把多个请求放在同一条 TCP 连接上，空闲一段时间后服务器或代理可能主动关闭。客户端准备复用时若发现连接已被对端关闭，应重新建连；如果关闭与新请求同时发生，还会出现竞态，重试是否安全取决于请求方法与业务幂等性。连接池应有空闲超时、最大寿命和失败后重建策略，而不是把一条连接永久保存。

HTTP/2 可以在单连接上多路复用流，HTTP/3 则在 QUIC 连接上多路复用；“复用”不等于“永不断线”。中间负载均衡器、代理和 NAT 的空闲超时可能比客户端配置更短，导致客户端以为可用、实际路径已丢状态。

应用心跳如何设计

即时消息服务可每隔一段时间发心跳并要求应用层回应；服务端据此更新“在线”状态。心跳消息需带请求标识或时间，避免旧回应被误认为当前回应。超时阈值要考虑移动网络切换、后台省电、短时丢包和服务高峰；一个心跳没回来就立刻宣告离线，可能造成频繁假阳性。

WebSocket Ping/Pong 是协议层控制帧，浏览器 JavaScript API 对控制帧的直接控制能力受环境限制，若业务需要“用户在线并可处理消息”，可能还要业务层确认。心跳检测到失联后，重连应使用退避与随机抖动，避免大规模客户端同时冲击服务器。

NAT 映射与保活成本

NAT 或状态防火墙根据最近流量维护连接映射，空闲时间过长可能删除。适度保活可以维持映射，但具体超时并无全球统一值；不同运营商和设备可能差别很大。心跳包是否经过目标 NAT 以及是 TCP 还是 UDP，也影响效果。不要为了“永不掉线”把全网客户端都设成每秒一次心跳，可能造成服务器与移动设备电量压力。

如果业务允许几十秒感知离线，应先写清离线检测 SLO，再依据端到端测试设间隔。若必须秒级故障切换，可能需要更主动的请求超时与健康检查，而不是依赖操作系统默认 TCP keepalive。

一次故障实验

客户端与服务器建立连接，随后断开客户端 Wi-Fi 但不正常发送 FIN。分别观察 HTTP 连接池何时发现不可用、TCP keepalive 在当前配置下何时报告错误、业务心跳何时判定离线。再模拟服务器进程卡住但内核仍在，比较 TCP 层探测与业务心跳的差异。每个实验记录“检测时间”和“误报率”，并确认重连不会重复提交业务写请求。

排障时先问“哪一层的保活”：复用请求、探测 TCP 可达，还是证明业务处理能力。名字相似不能当作配置相同。

自检

打开 HTTP Keep-Alive 后，是否意味着 TCP 会每秒主动探测故障？

不是。HTTP Keep-Alive 指请求复用；TCP keepalive 是独立的内核探测机制，应用心跳又是另一层。
