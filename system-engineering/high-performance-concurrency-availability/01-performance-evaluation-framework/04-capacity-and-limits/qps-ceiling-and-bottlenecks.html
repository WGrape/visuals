为什么并发增加，QPS 也会到顶？

Little 定律描述已发生的平均关系；它没说系统的 CPU、IO、网络和上游资源可以无限供给。容量规划先分清「送来多少、收下多少、完成多少」。

四条速率不要只叫“QPS”

到达 / offered

上游尝试发送的速率

包括重试；可能在客户端连接池、网络或本地队列等待。

准入 / admitted

进入选定服务边界的速率

未被网关/应用拒绝的那一部分；边界要写清。

完成 / completed

离开该边界的请求速率

可能同时包含成功、错误与拒绝，统计时须声明计入口径。

成功 / successful

满足业务成功条件的速率

大量 429/5xx 时，完成 QPS 高也未必有用。

若一段时间内准入持续大于完成且没有拒绝/丢弃，系统内未完成请求会增长；此时不能用准入 QPS 代替完成 QPS，再拿业务 RT 强行算出稳定容量。

两个约束：槽位与处理能力

同时容纳多少？

并发位 C 限制业务层同时占用的请求数；每个处理中的请求占用资源和时间。若持续填满且平均业务占位 W 不变，对应的完成速率约 C/W。

每秒实际能完成多少？

CPU 算力、IO/网络带宽、数据库、源站、账号速率限制等可能先于并发位达到可持续瓶颈；排队后 W 往往随负载变化。

λ稳定可行 ≤ min(外部准入速率, 资源可持续处理能力, C / W业务)

这是在给定请求混合、实测容量、稳态与匹配边界的 W 下的规划上界，不是一个随意代数字就能得到「实际 QPS」的恒等式。若 W 随负载变，需在目标负载重新测量。对单个调用方还要考虑客户端同时发送能力与按 Key 的 RPM 等其它闸门。

纯假设的 4,000 + 1,000 演算

设想一套与 Jina Reader 无关的理想化模拟系统：最多 4,000 个业务层并发位，另有最多 1,000 次/秒的资源可持续处理能力。只为说明「上界取小」；假设排队前 W 在各行给定、持续有足够请求、实际不会因负载变化。

业务段平均 W槽位估算 C/W另一资源上界可行的完成速率上界对应平均业务 in-flight
3 秒约 1,333 次/秒1,000 次/秒1,000 次/秒约 3,000 个
5 秒800 次/秒1,000 次/秒800 次/秒约 4,000 个

这两行不是压测结果。在真实系统中，慢下来的原因可能恰好是共享资源争用，W 不会保持固定；并发槽可能占满而完成率不升反降。不能据此断言「服务端未占满 4,000 就必定返回 429」或「处理快就无上限」。

为什么“队列越长，4000 ÷ 客户端 RT 越小”算错了？

若固定 4,000 是业务层处理中的 L，但客户端 RT 包含网关前排队，就把不同边界混到一个等式里。正确做法有两种：业务吞吐用平均业务处理中数 ÷ 平均业务占位时间；全链路吞吐用平均全链路未完成数（含等待）÷ 平均全链路 RT。两者在稳态无额外损失、同一请求群体下描述同一完成率。

排队导致 W 增大时，业务段并发数若保持不变、业务占位时间也没变，则业务完成速率未必下降；反而全链路在途量会随等待增加。若 CPU 争用又令业务占位时间上升，才可能进一步压低业务段吞吐。用分层例子验证 →

该如何找可持续工作点

  1. 选定同一请求组合和成功标准，定义压测的到达、准入、完成和成功速率；明确源站、账户限额与测试环境。
  2. 逐级增压，不仅看完成/成功 QPS，还看 P50、P95/P99、队列长度、资源利用率、429/5xx、超时与重试；设置停止条件，避免把上游打崩。
  3. 吞吐停止随负载增长而增长且尾延迟明显变差时，先排查最先饱和的资源或限额；继续加客户端连接、线程或协程通常无法提高成功吞吐。
  4. 保留余量与熔断/限流，考虑流量突刺与故障；容量是特定请求负载与 SLO 下的可持续成功吞吐，而不是短时完成峰值。
