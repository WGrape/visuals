压缩选型与在线改造：冷热分层、效果度量与不停服换编码

怎么按层选算法、怎么建立度量基线、怎么安全地在生产上完成编码改造

OLAP压缩选型在线变更冷热分层回滚
① 分层 ② 度量 ③ 在线改造 ④ 检查清单 ⑤ 疑问
一句话总结：压缩不是「选一个算法」就结束了，而是按列的生命周期选：热数据选解压快的，冷数据选压缩率高的，归档数据可以分层。这一篇讲三件事：怎么分层选、怎么度量效果、怎么在不影响在线查询的前提下完成改造。

01按数据冷热分层选算法

层级访问特征推荐算法理由
热层（近几天，高频查）每次查询都要读LZ4 或 ZSTD 低 level解压快，查询延迟优先
温层（近几月，偶尔查）读少，但仍要能查ZSTD 默认 level压缩率与速度的平衡点
冷层 / 归档几乎不查，或只做合规保留ZSTD 高 level，或更激进的组合磁盘成本优先，慢一点无所谓
要点：分层通常靠 TTL + 存储策略（热盘 SSD / 冷盘 HDD / 对象存储）自动完成，不同层可以配不同的压缩参数。具体写法以产品文档为准。

02怎么度量：别只看「压缩率」

指标怎么算为什么看它
压缩比未压缩字节 / 压缩后字节省了多少空间
压缩吞吐MB/s（写入时）会不会拖慢导入
解压吞吐MB/s（查询时）直接影响查询速度，最容易被忽略
查询 P95 延迟改编码前后的对比最终裁判——空间省了但变慢就是亏
CPU 占用导入与查询时的 CPU压缩是会抢 CPU 的，别把 CPU 打满
-- 思路：改造前先记录基线，改造后在同一查询集上对比
-- 1) 基线：记录目标表当前的空间与典型查询耗时
SELECT formatReadableSize(sum(bytes_on_disk)) FROM system.parts
WHERE table='events' AND active;

-- 2) 挑 3~5 条典型查询，各跑 3 次取中位数（避免缓存造成误判）
SELECT province, count() FROM events WHERE ts >= now() - INTERVAL 7 DAY GROUP BY province;
-- 记录耗时 T0

-- 3) 改编码（触发该列重写）
ALTER TABLE events MODIFY COLUMN ts CODEC(DoubleDelta, ZSTD);

-- 4) 再跑同一批查询，记录 T1；同时看新空间占用
-- 5) 判断：空间收益是否值得 T1-T0 的延迟变化
要点：没有基线就改参数是运维大忌。至少记录空间、查询耗时、CPU三项，一次只改一个变量。

03在线改造：如何在不停服的情况下换编码

  1. 先在小表/单分区验证：确认收益再推广，别直接在主表上赌。
  2. 一次只改一列：多列同时改，出了问题不知道是哪一列造成的。
  3. 避开业务高峰：改编码会重写该列数据，伴随较重的 IO 与临时磁盘占用。
  4. 确认磁盘余量：重写期间需要额外的空间，磁盘满了会导致失败甚至影响写入。
  5. 观察副本/分片状态：改造过程中关注副本同步延迟，别让只读副本落后太多。
  6. 保留回滚路径：确认旧的参数组合还能改回去，并记录原始建表语句。
动作影响范围是否阻塞查询注意
改列编码（MODIFY CODEC）该列一般不阻塞读写，但有 IO 压力会有临时空间占用
改排序键（ORDER BY）整表重写不阻塞，但耗时最长代价最大，务必先验证
改分区键整表重写同上通常与排序键一起评估
新建表 + 双写迁移可控不阻塞最稳但工作量最大

04上线前检查清单

  • ☐ 已记录改造前的空间、查询耗时、CPU 三项基线
  • ☐ 已在小表或单分区验证过收益
  • ☐ 已确认磁盘余量足够覆盖重写期间的额外占用
  • ☐ 已选定低峰窗口，并通知到相关方
  • ☐ 一次只改一个变量（一列 或 一个参数）
  • ☐ 已准备回滚方案与原始建表语句
  • ☐ 改造后有对比数据与结论记录
要点：这张清单同样适用于「改分区键」「改排序键」「改副本策略」等任何存储侧的在线变更。

05常见疑问

问：能不能全局把 ZSTD level 调到最高省空间？

不建议。level 越高，压缩时的 CPU 与耗时增长很快，而压缩率收益递减。高 level 只适合冷数据归档层，热层用它会拖慢导入。

问：改编码会锁表吗？

多数产品不会阻塞读写，但会消耗大量 IO 与临时磁盘，间接导致查询变慢。所以在低峰做、并且先确认磁盘余量，比担心「锁不锁」更重要。

问：压缩省下来的空间值不值这个改造成本？

算一笔账：省下的磁盘成本（元/月） vs 改造的人力 + 风险 + 可能的查询变慢。只有当磁盘是明确瓶颈、或数据规模还在快速增长时，这笔账才划算。

问：我应该先改编码还是先改排序键？

先改排序键。排序键决定了相邻值是否重复，是压缩率的量级因素；编码是在此基础上的优化。排序键错了，怎么调编码都救不回来。

编码与压缩的默认值对照

「编码」决定同列数据怎么排列（字典/RLE/差分/位打包），「压缩」决定排好之后用什么算法压。两者都要选，且编码的收益通常比压缩大一个数量级。

系统默认压缩常用编码改压缩的代价典型压缩率
ClickHouseLZ4（MergeTree 默认）LowCardinality、Delta、DoubleDelta、Gorilla、T64、ZSTD 组合ALTER ... MODIFY CODEC，新数据立即生效，旧 part 需 OPTIMIZE 或后台合并LZ4 约 3~5×，ZSTD(3) 约 5~8×，加编码 10×+
ParquetSNAPPY（Spark 写入默认）字典编码（默认开启）、RLE_DICTIONARY、DELTA_BINARY_PACKED、PLAIN整文件重写，不能原地改SNAPPY 约 3×，ZSTD 约 4~6×
ORCZLIB（Hive 默认）字典、RLE、位打包整文件重写ZLIB 约 4~6×
Doris/StarRocksLZ4（默认）字典、Bitmap、RLE、DeltaALTER TABLE ... MODIFY COLUMN约 5~10×
TimescaleDB列存压缩（内部算法）字典 + Delta + 简单 8B 打包chunk 级压缩/解压官方口径 >90%（10×+）

ClickHouse：量化现状 + 改编码

-- ClickHouse：先看现状，再决定改哪个列
SELECT table, name,
       formatReadableSize(sum(data_compressed_bytes))   AS compressed,
       formatReadableSize(sum(data_uncompressed_bytes)) AS uncompressed,
       round(sum(data_uncompressed_bytes) / sum(data_compressed_bytes), 2) AS ratio,
       compression_codec
FROM system.columns
WHERE database = 'default'
GROUP BY table, name, compression_codec
ORDER BY sum(data_uncompressed_bytes) DESC
LIMIT 20;

-- 改编码：字符串低基数列改 LowCardinality，时间列改 DoubleDelta，浮点改 Gorilla
ALTER TABLE events MODIFY COLUMN status   LowCardinality(String);
ALTER TABLE events MODIFY COLUMN ts       DateTime CODEC(DoubleDelta, ZSTD(3));
ALTER TABLE events MODIFY COLUMN value    Float64  CODEC(Gorilla, ZSTD(1));

-- 只对新增 part 生效；存量 part 触发一次合并即可重写
OPTIMIZE TABLE events FINAL;

Parquet：读列级压缩明细

# Parquet：不改数据也能看出列级压缩情况
python3 - <<'PY'
import pyarrow.parquet as pq
f = pq.ParquetFile('events.parquet')
print('rows:', f.metadata.num_rows, 'row_groups:', f.metadata.num_row_groups)
for i in range(f.metadata.num_row_groups):
    rg = f.metadata.row_group(i)
    for j in range(rg.num_columns):
        c = rg.column(j)
        print(f'{c.path_in_schema:24s} enc={c.encodings} comp={c.compression} '
              f'{c.total_uncompressed_size/1e6:8.1f}MB -> {c.total_compressed_size/1e6:6.1f}MB '
              f'({c.total_uncompressed_size/max(c.total_compressed_size,1):.1f}x)')
PY

# 换压缩重写出一份新文件（zstd 级别越高越慢，收益递减）
python3 -c "import pyarrow.parquet as pq, pyarrow as pa; \
pq.write_table(pq.read_table('events.parquet'), 'events_zstd.parquet', compression='zstd', compression_level=5)"

ZSTD 级别从 1 提到 19，压缩率通常只再提升 10%~20%，但压缩耗时可能翻 5~10 倍。OLAP 场景推荐 ZSTD(1)~ZSTD(3)：解压速度几乎不变，而解压是查询时每次都要付的成本。

在线换编码：不停服的迁移步骤与检查清单

换编码/压缩本质是在改存储格式，能做到不停服的前提是：新旧格式可以共存。ClickHouse / Parquet / Iceberg 都满足这点（按 part / 文件粒度区分格式），所以可以滚动替换。

步骤命令/动作是否阻塞查询回滚方式
1. 量化现状查 system.columns 的压缩比与 codec否—
2. 小范围验证新建一张测试表插入 1% 数据对比否删除测试表
3. 改列定义ALTER TABLE ... MODIFY COLUMN否（DDL 短暂锁）MODIFY 回原 codec
4. 存量重写OPTIMIZE TABLE ... FINAL 或等后台合并是（合并消耗 IO/CPU），建议限流停止 OPTIMIZE，旧 part 仍可读
5. 验证收益重新查压缩比 + 抽样查询延迟否—
6. 观察 24h看 CPU、IO、查询 P99、合并队列长度否出问题整体回退 codec

限流与验证

-- 合并前先限流，避免把线上 IO 打满（ClickHouse 20.8+）
SET max_bytes_to_merge_at_max_space_in_pool = '10G';
SET background_pool_size = 4;   -- 默认 16，压低可给查询让路

-- 观察合并队列，backlog 持续增长说明重写跟不上写入
SELECT database, table,
       count() AS merging_parts,
       sum(bytes_on_disk) AS bytes,
       formatReadableSize(sum(bytes_on_disk)) AS readable
FROM system.merges
GROUP BY database, table
ORDER BY bytes DESC;

-- 抽样对比查询延迟（改前改后各跑一次，看 read_bytes 是否下降）
SELECT count(), sum(value)
FROM events
WHERE ts >= now() - INTERVAL 7 DAY
SETTINGS send_logs_level = 'trace';   -- 日志里看 Selected parts / Read bytes

换压缩前逐条确认：

  • 先量再改：记录改前的压缩比、查询 P99、写入吞吐三个基线，否则无法判断有没有变好。
  • 低基数字符串（基数 < 1 万）优先上 LowCardinality / 字典编码，收益往往比换压缩算法大 3 倍以上。
  • 时间列用 Delta / DoubleDelta，单调递增的浮点（如累计值）用 Gorilla。
  • 压缩级别别贪高：ZSTD ≥ 10 之后压缩率收益很小，但 CPU 成本陡增。
  • 存量重写必须限流：合并是 CPU + IO 双密集，不限流会直接抬高线上查询延迟。
  • 换完要验证查询侧：压缩比变好但解压变慢是常见陷阱，看 P99 而不只看平均值。
  • Parquet/ORC 是文件级格式，改压缩=重写文件，提前算好磁盘峰值（新旧两份同时存在）。
  • 列顺序也会影响压缩：把低基数列放前面能让字典编码命中更多连续页。
