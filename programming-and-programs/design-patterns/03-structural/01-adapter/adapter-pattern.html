适配器模式：对接不兼容接口

保持现有客户端契约，用一个薄层翻译外部能力。

学完能解释什么

  • 找出目标接口与既有接口不兼容的地方
  • 用组合实现对象适配器而不改动被适配类
  • 判断何时适配器会掩盖真正的领域模型问题

逐步看机制

客户端依赖稳定契约

业务只知道 send(message)，不应散落外部 SDK 的方法名、字段和异常格式。

什么时候真的需要适配

你的代码已经依赖 send(message)，某个第三方 SDK 只提供 publish({body})。让所有调用点都认识 SDK 会把变化扩散到业务层；适配器把“外部语言”限制在一个边界内。它解决的是接口兼容，不是随意包装每个类。

最小实现：组合而非侵入修改

class NotificationAdapter {
  constructor(externalClient) {
    this.client = externalClient;
  }
  async send(message) {
    if (!message || !message.text) throw new Error('empty message');
    return this.client.publish({ body: message.text });
  }
}

// 客户端只调用 notifier.send({ text: 'ready' })。

对象适配器持有被适配对象；类适配器依赖继承且受语言多继承限制。生产实现还应处理超时、返回值和错误翻译，但不能悄悄吞掉失败。

与相邻模式怎么区分

模式主要目的
Adapter让不兼容接口变得可用
Decorator保持接口，叠加职责
Facade给复杂子系统提供更简单的入口

如果字段映射涉及大量复杂业务规则，先检查领域边界是否放错；一层不断变厚的适配器通常是设计信号，而不是继续叠包装的理由。

自检

适配器一定要继承第三方类吗？

不一定。对象适配器通过组合持有外部对象，更容易替换、测试，也避免修改第三方实现。
