TTS 文本规范化与发音消歧

同一串字符可能有不同读法。先决定“读什么”，再交给声学模型决定“怎么说”。

核心机制

文本规范化把日期、数字、单位、缩写等书写形式转成适合朗读的词序列。它要利用上下文：12:30 可读作“十二点半”，而编号 12-30 往往应逐段读。

发音消歧随后处理多音字、人名、外来词和断句。语义上下文、词典和显式标注都可能参与；词典覆盖不到新词时，还需要可回退的规则或模型。

用一个例子看过程

输入：2026/10/15 09:05，银行行长到场。
目标：二〇二六年十月十五日九点零五分，银行行长到场。

识别片段

先识别日期和时间的边界，避免把斜线和冒号当普通字符朗读。

按语境展开

把日期、时间转成目标语言的可读词序列；不要对所有数字套同一条读法。

消歧并检查

根据“银行行长”的词法与语境确定多音字读法，再检查专名与停顿。

观察、原因与处理

观察原因或含义处理与验证

文本前端的四道关口

  1. 片段识别：先把日期、金额、数字加单位、网址和专名识别成完整片段。例如“3.5kg”应整体识别，不能让小数点与单位各自进入逐字朗读规则。
  2. 按类型展开：“2026/10/15”适合按日期读，“订单号 00128”要保留前导零，“¥1,250.00”还要处理货币单位与小数位。相同数字在时间、金额、版本号和电话号码中不能共用一条读法。
  3. 发音消歧：多音字、外来词和人名需要词边界、句子语义或词典支持。词典无法穷尽新词，系统应有可解释的回退策略。
  4. 分句与韵律提示：长文本按语义边界拆分，向声学模型提供停顿和语气线索；错误切分会改变句意。

前端输出可以理解为“朗读脚本”，包含可读词序列和必要的发音、停顿信息；具体模型也可能把部分步骤联合训练，但排错时仍要分清输入解释与声音生成。

从一次错误读法定位原因

假设用户输入“请在 08:30 前拨打 400-123-4567，订单号 A007”。先记录原文，再保存规范化后的词序列：时间应按时刻处理，电话号码通常逐段逐位读，订单号要保留字母与前导零。如果前端输出已经丢掉“00”，改声码器不会恢复它；若词序列正确但停顿生硬，检查分句和韵律；若文字与韵律都对却有爆音或音色漂移，再排查声学表示、音频拼接与播放器。

建立回归集时按日期、货币、分数、单位、型号、地址、缩写、中英混读和专名分桶。每条样本保存期望读法、地区语言、允许变体与真实音频。自动文本比对能发现规则回退，但仍需抽听，因为文字相同也可能在重音或停顿上出错。

边界与误区

SSML 可以给出某些显式读法，但接口支持的标签不同；前端输出也不等于最终音质。排错时先查看规范化文本，再检查声学和波形阶段。

规则系统与模型系统怎样协作

确定性的格式，例如 ISO 日期、货币符号和常见单位，可以用明确规则解析，再让模型处理缺少上下文的多音字与韵律。这种分工便于复现错误：相同输入和地区设置应得到相同的结构化片段。规则与模型冲突时要有优先级，例如用户显式给出的音素标注通常应覆盖自动猜测，但非法标注也要回退或报错。上线新规则时，先在测试集上比较改变了哪些旧样本，而不只检查新样本是否正确。

一段文本还可能同时含中英文和缩写。“AI v2.1 于 10:05 发布”需要先确定 AI 是读字母、单词还是产品名，v2.1 是版本号而非小数测量值。仅以字符形状判断往往不够，要把语料领域、产品词典和语音播报场景一起纳入。对无法确定的输入，可以要求上游提供显式标注，而不是假装模型总能猜中。

如何让读法可复现

同一段播报在不同地区可能有不同日期顺序、货币名称和数字习惯。输入契约应显式包含语言与地区，而不是依赖服务端默认值；词典、规范化规则和模型版本也应随请求或日志记录。否则一次线上读法问题很难在本地复现。规则升级时抽取受影响的输入类别，逐条对比旧版与新版的规范化结果，再抽听音频。对于专有产品名，词典还要约定大小写、字母逐读与单词连读的优先级。若上游可以提供结构化字段，优先传入“日期”“金额”“订单号”等类型信息，减少从裸文本猜测的歧义。

为什么需要 TN（Text Normalization）：TTS 模型直接在文本上训练，见到 199 不知道该读「一九九」还是「一百九十九」。如果训练集里数字很少，模型会随机发挥。TN 把非标准词（NSW）转成可读形式，是 TTS 流水线的第一道关卡，它的错误会直接变成语音里的错误，且无法在后续环节修复。

实现方法

# 方法 1：规则 + 正则（可控、可解释，工业界主流）
import re

def normalize_number(m):
    s = m.group()
    n = int(s)
    if len(s) <= 4: return num2zh(n)          # 1234 -> 一千二百三十四
    if re.match(r'^1[3-9]\d{9}$', s):          # 手机号
        return ' '.join(digit2zh(d) for d in s)  # 逐位读
    if len(s) >= 8: return ' '.join(digit2zh(d) for d in s)  # 长号码也逐位
    return num2zh(n)

def normalize_currency(m):
    s = m.group()
    if s.startswith('¥') or s.startswith('￥'):
        return num2zh(float(s[1:])) + '元'
    if s.startswith('$'):
        return num2zh(float(s[1:])) + '美元'
    return s

PATTERNS = [
    (r'\d{4}-\d{2}-\d{2}', normalize_date),
    (r'\d{1,2}:\d{2}',      normalize_time),
    (r'[¥￥$]\d+(\.\d+)?',  normalize_currency),
    (r'\d+(\.\d+)?%',      normalize_percent),
    (r'\d+(\.\d+)?',       normalize_number),   # 数字放最后（最通用）
]

def text_normalize(text):
    for pat, fn in PATTERNS:
        text = re.sub(pat, fn, text)
    return text

# 常见错误
# ✗ 数字规则放在日期前面 -> 日期被拆散
# ✗ 没处理小数点后的 0 -> 3.10 读成「三点一」而不是「三点一零」

排障清单

症状原因处理
数字读错规则顺序错或没匹配到检查正则顺序；数字规则放最后
日期被拆成三个数字数字规则优先级高于日期特殊模式先匹配，通用数字最后
长数字读法不对该逐位读还是按数量级读没分清手机号/身份证/编号逐位；金额/统计按数量级
英文缩写读错没有缩略语词表维护常见缩写词表；未知缩写按字母读
多音字读错TTS 前端还有多音字消歧环节TN 只管数字等 NSW；多音字由专门的模块处理
小数读法不对小数点后的零被省略小数部分要逐位读：3.10 → 三点一零
不同语言混排处理错没做语言识别先分句按语言，再分别 TN

TN 的两个工程原则：① 规则要可测试——每条规则都要有对应的测试用例，改动时跑一遍；② 歧义交给上下文——同一串数字在不同上下文读法不同，这靠规则顺序和上下文判断解决，别指望一个正则搞定所有情况。

自检

“3.5kg”读法错误，应先改声码器吗？

先检查文本前端是否把数字与单位展开成预期词序列；声码器只负责把声学表示变成声音。
