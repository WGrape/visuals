    一条主线：每一版都在解决上一版的某个痛

    HTTP 的版本演化看似复杂，但如果抓住「每一代到底在修什么问题」，脉络会非常清楚。

    三个版本的演化目标与两层队头阻塞的区别
    版本核心改动解决了什么遗留问题
    HTTP/0.9只有 GET，返回纯 HTML能传网页没有头、没有状态码、不能传多媒体
    HTTP/1.0引入请求/响应头、状态码、多种方法能描述内容类型、缓存、错误每个请求都要新建 TCP 连接
    HTTP/1.1持久连接、管线化、Host 头、分块传输复用连接、支持虚拟主机管线化仍有应用层队头阻塞
    HTTP/2二进制分帧、多路复用、HPACK 头压缩、流优先级一条连接并发多个流TCP 层丢包仍会卡住所有流
    HTTP/3QUIC 基于 UDP、内置 TLS 1.3、连接迁移彻底摆脱传输层队头阻塞、0-RTTUDP 在部分网络受限制、CPU 开销更高

    HTTP/2 到底改了什么

    ① 二进制分帧

    原来的 HTTP 是纯文本逐行解析，机器处理既慢又容易出错。HTTP/2 把所有报文拆成固定结构的帧（HEADERS 帧、DATA 帧…），每个帧带上所属的流 ID。

    这一步是后面所有能力的基础：有了帧和流 ID，才谈得上多路复用。

    ② 多路复用

    同一条 TCP 连接上可以同时跑许多条流，帧可以交错发送，接收端按流 ID 重新组装。

    这直接干掉了 HTTP/1.1 时代「浏览器对同一域名只能开 6~8 条连接」带来的各种黑科技（域名分片、雪碧图、内联小资源）。

    ③ 头部压缩 HPACK

    每次请求都带一堆几乎相同的头（User-Agent、Cookie、Accept…），浪费严重。HPACK 用静态表 + 动态表 + 霍夫曼编码，把重复头部压到只剩索引。

    这也是为什么 HTTP/2 要求头的大小要有上限，并促使大家减少携带巨大 Cookie。

    ④ 服务端推送（后被弱化）

    允许服务端不等请求就主动推资源。想法很好，但实践中缓存命中判断困难、容易推重复，主流浏览器已不再积极支持。

    这是一个值得记住的工程教训：协议设计得很美不等于能落地。

    HTTP/3 的关键取舍

    把传输从 TCP 换成 UDP 之上的 QUIC，换来四个实际收益：

    独立的流每条流的丢包只在自己这条流里等重传，其它流照常推进。
    连接迁移QUIC 用 Connection ID 标识连接而非四元组，手机从 Wi-Fi 切到蜂窝时连接不断。
    握手更快传输握手与 TLS 握手合并，常见情况下 1-RTT 就能开始传数据，复用会话甚至可以 0-RTT。
    加密成为默认QUIC 几乎所有头部字段都加密，中间设备进行协议级的窥探与干预被大幅限制。

    代价也很清楚：

    • CPU 开销更高。TCP 有几十年的内核优化与网卡卸载（offload）支持，QUIC 多在用户态实现，加解密与重传逻辑都要自己来。
    • UDP 可能被限制。部分企业网络、老旧运营商设备会限速甚至丢弃 UDP，导致不得不回退到 HTTP/2。
    • 运维观测习惯要变。以往靠 TCP 端口、序列号做排障的工具失效，需要新的抓包与指标体系。

    现实建议：服务端同时提供 HTTP/2 与 HTTP/3，由客户端协商（通过 Alt-Svc 头或 HTTPS DNS 记录发现）。绝不要把「只支持 HTTP/3」作为唯一选项。

    深入自检

    HTTP/2 完全解决了队头阻塞吗？

    只解决了应用层的那一层：不同请求不再互相排队。但传输层的队头阻塞依然存在 —— TCP 要求按序交付，任何一个包丢失，连接上所有流的数据都要等它被重传回来。所以在高丢包网络（移动、弱网、跨境）上，HTTP/2 有时甚至不如多条 HTTP/1.1 连接并行。这正是 HTTP/3 存在的理由。

    为什么 QUIC 要建在 UDP 上而不是直接改 TCP？

    因为 TCP 的实现已经分布在无数操作系统内核、中间件、NAT 与防火墙里。任何新的 TCP 选项都可能被中间盒子当作非法包丢弃（这被称为协议僵化）。UDP 只提供最小的数据报能力，把拥塞控制、重传、流控全放到应用层实现，才能真正做到按需演进。

    HTTP/1.1 的管线化怎么就没普及？

    它要求服务端严格按请求顺序返回响应，一旦第一个请求慢（比如大 SQL 查询），后面所有响应全被堵住，这就是典型的应用层队头阻塞。实现复杂、效果有限，浏览器基本都默认关闭。直到 HTTP/2 引入帧与流，才真正解决了这个并发问题。

    我该给自己的服务开 HTTP/2 吗？

    通常值得，成本很低（多数反向代理与 CDN 一条配置即可），收益集中在高并发多资源场景下减少连接数与握手开销。但要注意：① 必须 HTTPS（浏览器只在加密连接上协商 HTTP/2）；② 大文件下载场景收益不明显；③ 如果你的服务严重依赖队上升建议同时ping проведении观测首字节时间，判断是不是真的变好了。
