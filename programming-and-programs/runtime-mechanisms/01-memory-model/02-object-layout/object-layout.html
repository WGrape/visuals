是什么

对象在内存里怎么摆

一个对象（结构体实例）在内存中通常是一块连续区域：各字段按声明顺序排布，中间可能插入填充字节（padding）以满足对齐要求。对象大小 = 各字段大小 + 填充。

规则

对齐：为什么要「凑整」

⚙️
硬件要求
CPU 按字长访问内存；未对齐访问在部分架构上会直接报错（如 ARM 早期），在 x86 上虽可用但更慢
📦
单次访存
对齐的数据可一次总线周期读完；跨两个字的未对齐数据需要两次访存再拼接
🧮
对齐值
通常等于该类型的大小（int64 按 8 对齐，int32 按 4 对齐），上限常为一个字长
📐
整体对齐
结构体整体大小需是其最大字段对齐值的整数倍，数组连续存放时才不会错位
演算

手算一个对象多大

// Go 示例
type Bad struct {
    a bool    // 1 字节，对齐 1
    b int64   // 8 字节，对齐 8
    c int32   // 4 字节，对齐 4
}
// 布局：a(1) + pad(7) + b(8) + c(4) + pad(4) = 24 字节

type Good struct {
    b int64   // 8
    c int32   // 4
    a bool    // 1
}
// 布局：b(8) + c(4) + a(1) + pad(3) = 16 字节

// 同样的字段，换个顺序省了 1/3 内存
什么时候值得优化：对象数量巨大（百万级缓存条目、大数组）时，省下的内存直接转化为更低的 GC 压力与更好的缓存命中率。少量对象则不必纠结。
进阶

缓存行与伪共享

CPU 缓存以缓存行（Cache Line，通常 64 字节）为单位加载。若两个无关的变量恰好落在同一缓存行，且被不同 CPU 核频繁写入，就会互相使对方的缓存失效——这叫伪共享（False Sharing），是并发程序里隐蔽的性能杀手。

😵
表现
加了多线程反而更慢；两个线程写不同的变量，却出现大量缓存一致性流量
💊
解法
按缓存行填充（padding）把变量隔开到不同缓存行；或让每个核写自己的计数、最后汇总（Go 的 pprof 中常见此模式）
面试问答

高频问题

Q1：为什么要内存对齐？
CPU 按字长访问内存，对齐的数据可一次访存取完；未对齐数据可能跨越两个字，需要两次访存再拼接，在部分架构上甚至会触发异常。对齐是牺牲少量空间换取访问效率。
Q2：结构体字段顺序会影响大小吗？
会。字段间为满足对齐会插入填充字节。把对齐值大的字段放前面（从大到小声明），能减少填充，显著降低对象体积。
Q3：什么是伪共享？
两个被不同 CPU 核频繁写入的变量落在同一缓存行，导致缓存行在核间反复失效与同步，性能急剧下降。解决办法是按缓存行填充隔离变量，或让各核写独立副本最后汇总。
Q4：结构体整体大小为什么要按最大对齐值补齐？
因为数组元素连续存放。若整体大小不是最大对齐值的整数倍，第二个元素开始就会错位，破坏每个字段的对齐。
Q5：优化对象布局真的有用吗？
在对象数量巨大时很有用（百万级缓存、大数组）：省内存、降低 GC 压力、提升缓存命中率。对象数量少时收益有限，可读性优先。
