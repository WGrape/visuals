架构设计怎么做：从需求到 ADR

把「功能需求 / 质量需求 / 约束」分开、先用约束筛方案、再用优先级比取舍、最后用 ADR 固化决策——一套能落地的架构设计流程，以及四种验证手段。

INPUT · 输入

一、先把需求分成三类

📥 功能需求 / 质量需求 / 约束
类型内容例子对架构的影响
功能需求系统要做什么支持下单、退款、查询订单决定模块与数据模型
质量需求做到什么程度下单 P99 < 200 ms、可用性 99.9%决定技术手段与冗余级别
约束不能违背的前提必须用现有 MySQL、团队 5 人、三个月上线直接否决部分方案
约束最容易被忽略，却最有杀伤力。一个技术上完美的方案，如果团队没有运维能力、或者采购周期超过上线时间，就是不可行的。把约束在第一轮就列出来，能省掉大量无效设计。
LIMIT · 约束优先

二、约束为什么比质量属性更硬

🔒 四类常见约束
  • 技术约束：已有的技术栈、必须复用的中间件、不允许引入的新组件。
  • 组织约束：团队规模与能力、跨团队协作成本、运维人力。
  • 时间与成本约束：上线时间窗口、预算上限、硬件采购周期。
  • 合规约束：数据不能出境、必须留存审计日志、个人隐私处理要求。
质量属性可以商量，约束通常不能。"P99 200 ms"可以谈成 300 ms；"数据不能出这个机房"没有商量余地。设计流程上应该先用约束筛掉不可行方案，再在剩余方案里比质量属性。
FLOW · 工作流

三、一次架构设计的六个步骤

🔧 从需求到方案
  1. 收集输入 — 功能需求、质量需求、约束，全部写下来并标注来源。
  2. 确定优先级 — 质量属性排序，明确"冲突时谁让路"。
  3. 识别关键需求 — 找出真正决定架构的那 2–3 条（通常是最高并发量、最大数据量、最严格的时效）。
  4. 提出候选方案 — 至少 2–3 个，而不是一上来就细化唯一方案。
  5. 对照评估 — 用关键需求与约束逐条打分，明确每个方案牺牲了什么。
  6. 记录决策 — 写下选了哪个、为什么、放弃了什么、什么条件下要重新评估。
"至少三个候选方案"是防止过早收敛的有效手段。只有一个方案时，讨论会退化成"这个细节怎么实现"；有多个方案时，讨论才会上升到"我们到底要什么"。
ADR · 决策记录

四、用 ADR 把决策固化下来

📝 一份 ADR 该有什么
字段内容为什么重要
标题与编号简短的决策名 + 自增编号便于引用与追溯
状态提议 / 已接受 / 已废弃 / 被取代避免读到过时文档
背景当时的约束与问题半年后没人记得当时的上下文
决策选了什么结果本身
备选方案考虑过但没选的防止重复讨论同一件事
后果带来的好处与代价让代价是已知的，而不是意外
重新评估条件什么情况下要推翻它给未来的人一个触发器
ADR 最大的价值在"备选方案"和"重新评估条件"两栏。前者避免团队反复讨论已经否决过的方案，后者让架构能被安全地推翻——而不是把三年前的决定当成永久真理。
CHECK · 验证

五、设计完怎么验证

🧪 四种验证手段
  • 场景走查：拿真实的业务场景（下单、退款、大促）在架构图上跑一遍，看有没有走不通的地方。
  • 关键路径压测：只压最核心的一两条链路，验证吞吐与延迟是否达标，而不是等上线后才发现。
  • 原型验证：对最不确定的技术点（比如某个中间件的写入能力）做最小原型实测。
  • 故障演练：主动把某个依赖打挂，看系统是按设计降级还是整体崩掉。
没有验证过的架构只是假设。场景走查成本最低、发现的问题最多，应该在设计评审前就做一遍；压测与故障演练成本高，但只在最核心链路上做，投入产出比很高。

设计的产出不是图，而是一组可以追溯的决策

很多人把架构设计等同于画部署图，但图的保质期很短，真正有长期价值的是决策本身以及它背后的理由。判断一次设计是否合格，就看事后有人问「当初为什么这么定」时，你能不能拿出当时的依据。

架构设计的六步：每一步都要留下可追溯的产物，而不是只留下一张图
功能需求系统要做什么。可以通过加功能补齐，通常有回旋余地
质量属性做到什么程度：性能、可用、安全、可扩展。靠结构调整，改起来贵
约束不可协商的边界：合规、预算、工期、既有系统。违反就直接失败
决策记录把「选了什么、为什么、放弃了什么」写下来，是团队记忆的载体

质量属性之间必然冲突：先想清楚放弃什么

架构设计的难点从来不是「把性能做到最好」，而是在互相拉扯的目标之间做出取舍。任何声称所有属性都最优的设计，通常只是还没想清楚。

想要的目标会牺牲什么典型表现常见缓解手段
更强的性能一致性与成本引入缓存与异步后，读到旧数据设定可接受的陈旧窗口，关键路径走同步
更高的可用成本与一致性多副本多机房，数据同步有延迟区分关键与非关键数据，分级保障
更强的安全易用性与延迟多因素认证、全链路加密、审计按数据敏感度分级，不做一刀切
更好的可扩展复杂度与交付速度拆分服务后调试与排障变难先按领域粗粒度拆分，避免过度拆分
更低的成本冗余与响应速度资源压到刚好，突发就抖为非关键部分留出可降级的余量
更快的交付长期可维护性先硬编码上线，后面再还债明确记录技术债与偿还时间点

约束为什么最硬

质量属性可以讨价还价，约束不行。预算超了项目就停，合规不通过就不能上线。所以设计的第一步永远是把约束列全，它们会直接淘汰一大部分候选方案。

取舍要写成记录

取舍留在脑子里，半年后连自己都会忘记当时的前提。写成记录的好处是：当前提变化（比如流量翻十倍）时，你能立刻判断这条决策是否还成立。

ADR 该写什么：一份能用的模板

决策记录（ADR）不需要长篇大论，但必须包含四件事：背景、决定、理由、后果。缺了「后果」，后人就无法判断它现在还适不适用。

# ADR-014 订单查询走读写分离 ## 背景 订单列表页 QPS 峰值约 8000，单次查询扫描行数多，主库 CPU 长期高于七成。 业务上允许列表页数据有约 1 秒的陈旧。 ## 决定 订单列表查询走只读副本；下单与支付后的立即查询仍走主库。 ## 理由 - 读多写少，读压力占九成以上，分离收益最大 - 业务可接受约 1 秒陈旧，风险可控 - 相比引入缓存，改动更小，不需要处理缓存一致性 ## 后果（必须写） - 正：主库 CPU 降到约三成，列表页 P99 明显下降 - 负：副本延迟升高时用户可能看不到刚下的单，需要前端提示 - 负：需要监控副本延迟并在超阈值时自动切回主库 - 触发重评的条件：写峰值提升三倍，或副本延迟长期超过 2 秒 ## 备选方案（为什么没选） - 加缓存：一致性处理成本高，当前收益不如读写分离直接 - 分库分表：改造量大，当前数据量还不构成瓶颈

最后一条「触发重评的条件」是最容易被忽略、也最有价值的部分：它把一条静态决策变成了可自动失效的判断规则。

新手最容易犯的六个设计错误

一上来就选技术先定约束与质量属性，再谈框架
把所有属性都列为必须没有取舍就没有设计，必须排优先级
只画正常路径超时、重试、部分失败才是架构的主战场
忽略团队能力设计超出团队维护能力，落地必然走样
决策不写理由半年后无人知道前提，改动全靠猜
设计完不验证没有验证标准的架构只是愿望
过度设计为两年后的假想流量付出今天的复杂度
复制大厂方案规模与约束不同，照搬往往水土不服
需求没定清楚时能开始设计吗？

可以，但要先把「不确定的部分」显式标出来，并围绕它设计可替换的边界。比如数据结构尚未确定，就把存取抽象成接口，等需求明确后只改实现。怕的不是需求变，而是需求变了以后改动面失控。

怎么判断一个设计是过度设计？

问一句：如果未来半年流量只涨一倍，这个复杂度还值得吗？如果答案是不值得，就说明你在为假想的未来买单。更稳妥的做法是保留扩展点，但先不实现扩展。

架构评审应该关注什么？

不是关注图漂不漂亮，而是关注三件事：约束是否被满足、质量属性的取舍是否明确、失败路径是否被覆盖。评审的价值在于挑出「没想到的场景」，而不是挑格式问题。

什么时候该重新做架构设计？

当触发条件变化时：量级上一个数量级、业务模式改变、原有约束消失或新增。这也是为什么决策记录要写「触发重评的条件」——它让重新设计变成主动行为，而不是被事故逼着做。
