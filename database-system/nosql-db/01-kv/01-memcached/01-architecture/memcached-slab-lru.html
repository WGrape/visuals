先建立直觉：停车场按车型分区

停车场按车型划了若干区域：小型车位、中型车位、大型车位。一辆车只能停在不小于它的区域。

好处：不会产生「大车位停小车后剩下零碎空间没法用」的碎片问题。代价：中型车停进大型车位会浪费空间；而且小型车位满了，即使大型车位全空，小车也进不去。

Memcached 的 Slab 机制完全同理。

Slab 结构

增长因子（growth factor）

chunk 尺寸按增长因子递增：96B → 120B → 152B → …（默认约 1.25）。

因子效果
较小（如 1.1）尺寸梯度密 → 内存浪费少，但 slab class 数量多、管理开销大
较大（如 2.0）class 少 → 管理简单，但浪费严重（100B 的值可能进 192B 的 chunk）
调优思路：如果你的 value 大小分布集中（比如都是 1KB 左右），可以把增长因子调小，让 chunk 尺寸贴近实际值，减少浪费。如果 value 大小差异很大，则用默认或稍大值。

淘汰：按 class 独立的 LRU

这是 Memcached 最容易被误解的地方。LRU 不是全局的，而是每个 slab class 各有一条 LRU 链。当某个 class 的所有 chunk 都被占满时，新写入会在该 class 内淘汰最久未用的 item——即使其他 class 还有大量空闲内存。

实际后果：如果你的数据大小分布很不均匀，可能出现「总内存只用了 50%，但已经开始淘汰」的怪现象——因为某一档的 slab 被打满了。

监控与调优

指标含义健康信号
evictions因内存不足被淘汰的次数持续 > 0 说明容量不足，应扩容或优化
get_hits / get_misses命中/未命中次数命中率 = hits/(hits+misses)，应 > 90%
bytes / limit_maxbytes已用/总内存接近上限会频繁淘汰
curr_items当前 item 数结合命中率看增长趋势
# 查看运行状态
echo -e "stats\nquit" | nc 127.0.0.1 11211

# 重点关注
STAT evictions 12345        # 淘汰次数
STAT get_hits 9876543
STAT get_misses 123456
STAT bytes 3221225472
STAT limit_maxbytes 4294967296
调优清单：① 让 value 大小分布尽量集中，避免某个 class 被打满；② 按实际 value 大小调整增长因子；③ 监控 evictions，持续增长就扩容；④ 给不需要长期保留的数据设较短 TTL。

🎯 面试问答

Q：为什么总内存没满却开始淘汰数据？
A：因为 LRU 是按 slab class 分别做的，不是全局的。每个 class 只能使用分配给自己的那部分内存。如果某一档大小的数据（比如都是 1KB 左右）把对应 class 的 chunk 占满，就会在该 class 内淘汰，即使其他 class 还有大量空闲。解决办法：让 value 大小分布尽量集中、调整增长因子让 chunk 尺寸更贴合、或直接扩容。

Q：growth factor 该怎么调？
A：看你的 value 大小分布。分布集中（如都在 1KB 附近）→ 调小因子（如 1.05~1.1），让 chunk 尺寸贴近实际值，减少浪费。分布分散（几十 B 到几 MB 都有）→ 用默认或稍大值，避免 class 过多。判断依据：观察 stats slabs 里各 class 的 chunk_size 与实际 item 大小，看浪费比例。

Q：Memcached 的 LRU 和 Redis 的有什么不同？
A：两点：① 粒度——Memcached 是按 slab class 分段 LRU（局部），Redis 是全局近似 LRU（随机采样若干 key 淘汰最久未用的，更接近全局最优）。② 精度——Memcached 是精确 LRU（链表维护），Redis 是近似 LRU（采样，可调精度）。因此 Redis 的内存利用率通常更高，不会出现「某档满了但全局还有空间」的问题。

Q：怎么判断 Memcached 容量够不够？
A：核心看 evictions（淘汰次数）和 命中率。evictions 持续增长说明容量不足——数据在不断被挤出，会直接拉低命中率。命中率 < 90% 也要警惕。注意：由于 slab 的局部淘汰特性，即使 bytes 远小于 limit_maxbytes，也可能出现淘汰——所以要同时看 evictions 和命中率，不能只看内存使用率。
