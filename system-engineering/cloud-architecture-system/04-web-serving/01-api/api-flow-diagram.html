    一次 API 请求的完整旅程

    用户在 App 上点一下「下单」，到看到「下单成功」，中间经过了十几道工序。理解这条链路，才能在出问题时快速定位是哪一环慢了或错了。

    一次 API 请求的完整链路：从客户端到数据库再返回

    链路中各环节的关键设计

    环节关键设计常见坑
    客户端超时设置、重试策略（只对幂等）、连接池复用、本地缓存无超时导致一直等待；重试风暴放大流量
    DNS / 连接DNS 预解析与缓存、连接复用（keep-alive）、HTTP/2 多路复用每次请求重新建连，TLS 握手开销大
    网关鉴权、参数校验、限流、路由、日志、灰度网关超时大于客户端超时 → 客户端已放弃，网关还在等
    业务服务无状态、线程池/连接池隔离、熔断降级、幂等共享线程池被一个慢依赖拖满，所有接口一起超时
    缓存Cache Aside、防穿透/击穿/雪崩、TTL 抖动热点 key 过期瞬间全部回源，打垮数据库
    数据库索引、慢查询治理、连接池、事务尽量短大事务持锁时间长；连接池耗尽导致整个服务不可用
    下游调用超时、熔断、有限重试、兜底降级无熔断 → 下游慢 → 上游线程池打满 → 雪崩

    超时预算：必须逐层收敛

    这是链路设计中最容易被忽视、也最容易引发事故的一条。原则是下游的超时必须小于上游的超时，否则上游已经放弃，下游还在傻等，资源被白白占用，最终堆积成雪崩。

    用户可感知总超时：3s ├─ 客户端超时 3000ms ├─ 网关超时 2500ms （< 客户端） │ ├─ 连接超时 500ms （短，快速发现不可用） │ └─ 读超时 2000ms （按业务 P99 的 1.5~2 倍） ├─ 业务服务超时 2000ms │ ├─ 查缓存 50ms │ ├─ 查数据库 500ms │ └─ 调下游服务 800ms │ └─ 下游内部 600ms （< 800ms） 规则：每一层留 20%~30% 余量给序列化、日志、重试等开销 重试要计入预算：若重试 1 次，单次超时应为预算的一半 反例（错误示范）： 客户端超时 3s，网关超时 30s，服务超时 60s → 用户 3s 后放弃并重试，服务端还在处理第一批 → 请求不断堆积，线程池耗尽，全站雪崩

    同步链路 vs 异步链路：怎么切分

    同步（用户等待）

    必须立即得到结果才能继续的操作：

    • 登录鉴权——不知道结果无法进入
    • 库存校验与锁定——不知道结果无法下单
    • 支付——不知道结果无法告知用户
    • 核心数据的读取与写入

    异步（后台处理）

    失败了可以稍后重试、且不影响用户当前操作的：

    • 发短信/推送/邮件通知
    • 加积分、发优惠券、更新等级
    • 同步数据仓库、更新搜索索引
    • 生成报表、图片处理、视频转码
    • 记录审计日志、埋点上报

    切分的收益

    • 降低延迟：用户不用等通知发完才看到成功
    • 提高成功率：通知服务挂了不影响下单成功
    • 削峰：突发流量先入队，消费者匀速处理
    • 解耦：加一个新的下游不需要改主流程

    异步化的代价

    • 最终一致：用户可能看到「下单成功但积分未到」
    • 需要幂等：消息可能重复投递
    • 需要监控积压：队列堆积要及时告警
    • 需要兜底：失败要有重试与死信队列

    API 设计规范要点

    • 资源化 URL。GET /orders/{id} 而不是 GET /getOrder?id=；用名词复数、层级表达关系（/users/{id}/orders）。
    • 用对 HTTP 方法。GET 查询（幂等、可缓存）、POST 创建、PUT 整体更新（幂等）、PATCH 部分更新、DELETE 删除（幂等）。
    • 语义化状态码。200 成功、201 已创建、204 无内容、400 请求参数错、401 未认证、403 无权限、404 不存在、409 冲突（如重复下单）、429 限流、500 服务端错。不要把错误全塞进 200 里再用 body 里的 code 区分。
    • 版本化。URL 前缀（/v1/orders）或 Header 版本；破坏性变更必须升版本，不能就地改。
    • 统一的错误结构。包含 code、message、traceId；traceId 让用户报错时能提供定位依据，极大提升排障效率。
    • 分页与过滤规范。游标分页优于 offset（深分页性能问题）；返回 total 与 hasMore；排序字段白名单。
    • 幂等键。写操作支持客户端传 Idempotency-Key，服务端去重，配合客户端重试使用。

    深入自检

    接口很慢，怎么定位是哪一环？

    按「自顶向下 + 逐段计时」的方法：① 先看客户端感知的总耗时，再用浏览器 DevTools 或抓包拆出 DNS、TCP、TLS、首字节（TTFB）、内容下载各占多少——如果 TTFB 就很高，问题在服务端；如果 TTFB 低但下载慢，是响应体太大或网络差；② 服务端用链路追踪（TraceId）看每个 span 的耗时，一眼就能看出是网关、业务服务、缓存还是数据库慢；③ 数据库慢就查慢查询日志与执行计划（EXPLAIN），看是否走索引、扫描行数、是否临时表与文件排序；④ 注意「看似服务慢其实是连接池等待」——很多慢请求的时间其实花在等连接而非等 SQL。工具上，APM（SkyWalking / Prometheus + Grafana）能常态提供这些数据，不要等到出问题才临时加日志。

    为什么要强调「连接池」？它出问题时表现是什么？

    连接池（数据库、Redis、HTTP 客户端）是非常常见的隐形瓶颈。出问题时典型表现：请求耗时突然变长，但数据库和 CPU 都很空闲——因为时间都花在等待获取连接上。常见原因：① 池太小，并发高时排队；② 有慢查询或慢调用长期占用连接不释放；③ 连接泄漏（未在 finally 中归还）；④ 事务跨度太长，在事务里做 RPC 调用或耗时计算，连接被长时间占用。排查与处理：监控池的活跃数、等待数、等待时间；设置合理的最大连接数与获取连接的超时（不要无限等）；用 APM 定位持有时长最长的调用；把事务范围缩到最小，绝不在事务里做网络调用。另外注意：每个服务实例 × 池大小 × 实例数不能超过数据库的最大连接数。

    重试为什么经常帮倒忙？

    因为重试会放大流量，且常在下游已经过载时触发。典型场景：下游成功率降到 50%，上游对每个失败重试 2 次，下游收到的请求变成 3 倍，成功率进一步下降，形成正反馈直到崩溃——这就是重试风暴。防御手段：① 重试预算——重试请求占总请求的比例设上限（如 10%），超了就不再重试；② 只在熔断未打开时重试；③ 指数退避 + 抖动——避免所有客户端同时重试（会形成尖峰）；④ 只重试可重试的错误——连接超时、503 可以重试，400 参数错误、403 无权限、业务失败不该重试；⑤ 只对幂等操作重试——否则会造成重复下单、重复扣款。最根本的是：下游已经明确过载时，正确的做法是快速失败（熔断降级）而不是重试。

    RESTful 一定要严格遵守吗？

    不必教条。REST 的价值在于一致性、可预测性与利用 HTTP 既有语义（缓存、状态码、幂等），这些收益在面向资源的 CRUD 接口上最明显。但现实中有很多不适合纯 REST 的场景：批量操作、复杂搜索（请求体比 URL 更合适）、非 CRUD 的动作（如「取消订单」「审批通过」用 POST /orders/{id}/cancel 更自然）、RPC 风格的内部调用。务实做法：对外开放的、面向资源的 API 尽量遵循 REST；复杂动作可以用「资源 + 动作」的折中形式；内部服务间调用不必强求 REST（gRPC 往往更高效）。最重要的是团队内部一致——最糟的是同一个系统里三种风格混用。另外无论什么风格，版本化、统一错误结构、幂等支持这三条都应该坚持。
