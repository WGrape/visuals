①三种 key 模型决定能表达什么

Doris / StarRocks 建表时必须选一种 key 模型，它决定了主键相同的两行怎么处理。 这是与 MySQL 最大的思维差异：这里的表更像「按 key 组织的物化结果」，不是逐行记录。

模型重复 key 的处理适用注意
Duplicate（明细）都保留日志、流水、需要保留每条原始记录最贴近传统表，存储最大
Aggregate（聚合）按指标列的聚合函数合并（SUM / REPLACE / MAX / MIN 等）本来就是统计结果的宽表查询时自动聚合，但导入阶段就已合并，原始明细不可恢复
Unique（主键）保留最新一条（按导入顺序）需要 Upsert 语义的维表、状态表本质是 REPLACE 聚合的特化；写入有去重开销
-- Aggregate 模型：key 列 + 带聚合类型的指标列
CREATE TABLE daily_sales (
  dt        DATE,
  shop_id   BIGINT,
  amount    DECIMAL(18,2) SUM,        -- 同 key 的行累加
  order_cnt BIGINT        SUM,
  status    VARCHAR(20)   REPLACE     -- 同 key 的行取最后一次
) AGGREGATE KEY(dt, shop_id)
DISTRIBUTED BY HASH(shop_id) BUCKETS 8;

-- Unique 模型：按主键保留最新
CREATE TABLE user_dim (
  user_id  BIGINT,
  name     VARCHAR(50),
  city     VARCHAR(50)
) UNIQUE KEY(user_id)
DISTRIBUTED BY HASH(user_id) BUCKETS 8;
选错的代价很高：建表后 key 模型不能改，只能新建表再导数据。 判断口径：需要原始明细 → Duplicate；查询永远是聚合结果 → Aggregate；需要更新覆盖 → Unique。 拿不准时先用 Duplicate，存储比返工便宜。

②分区与分桶

分区（Partition）

通常按时间做范围分区。作用：① 查询按时间裁剪直接跳过整个分区； ② 历史数据可整体删除/替换；③ 冷热分层存储的基础。

分桶（Bucket / Tablet）

分区内再按哈希分桶，决定数据在各节点间的分布与并行度。 桶数太少 → 并行度不够；太多 → 元数据膨胀、小文件多。

分桶列怎么选

选高基数且常用于 JOIN / 聚合分组的列（如 user_id、shop_id）。 直接决定能否用上 Colocate Join 与本地聚合。

桶数的经验值

通常按「单桶压缩后几百 MB ~ 1GB 量级」估，且不超过集群磁盘数的若干倍。 具体建议请以所用版本官方文档为准——不同版本对 tablet 数量的容忍度不同。

最容易犯的错：分桶列基数太低。用 status（只有几个取值）做分桶列， 数据会严重倾斜到少数几个桶里，查询并行度退化成 1，还造成热点。 另一个常见错是分桶列与 JOIN 键不一致，导致每次 JOIN 都要跨节点重分布数据。

③物化视图与 Rollup：预聚合的正确用法

物化视图把「按某组维度预聚合的结果」物理存下来，查询时自动命中，不必重扫明细。 关键限制是聚合必须与物化视图的定义匹配，否则不会命中。

查询物化视图定义能否命中
SELECT dt, SUM(amount) GROUP BY dtGROUP BY dt✓
SELECT dt, shop_id, SUM(amount) GROUP BY dt, shop_idGROUP BY dt✗ 维度更细，无法从粗结果还原
SELECT dt, SUM(amount) GROUP BY dtGROUP BY dt, shop_id✓ 可从细结果再聚合（上卷，多数实现支持）
SELECT dt, COUNT(DISTINCT uid)SUM(amount) GROUP BY dt✗ 聚合函数不匹配
设计原则：物化视图按「最细的常用维度」建，让更粗的查询能上卷复用。 不要为每种查询组合各建一个——每多一个物化视图，就多一份写入放大和存储。 一般先按实际的慢查询 Top N 建 2~5 个，再看效果。
COUNT(DISTINCT) 是预聚合的难点。去重视图无法直接上卷 （两个分组的基数不能相加）。解决方案通常是用位图（bitmap）类型存中间状态， 查询时再求并集计数。具体支持的函数与类型请以所用版本文档为准。

④建表自检清单

  1. key 模型：需要明细吗？需要更新吗？选错不可改。
  2. 分区键：查询是否总带时间条件？没有时间过滤的查询会扫全部分区。
  3. 分桶列：基数够高吗？与高频 JOIN / GROUP BY 的列一致吗？
  4. 字段类型：能用定长/小类型就不要用大类型；字符串维度考虑用低基数优化。 改列类型的代价与 MySQL 一样大。
  5. 索引：列存的点查依赖稀疏索引 + zonemap/min-max 跳过， 等值高频维度放前面。详见本学科「数据跳过」章节。
  6. 导入方式：实时流（Routine Load）还是批量（Broker Load / INSERT INTO SELECT）？见下一篇。
Q：Doris 和 StarRocks 差别大吗？
A：同源（StarRocks 从 Doris 分叉），核心概念、key 模型、SQL 语法高度相似， 本页讲的模型与建表思路两边通用。差异在执行引擎细节、优化器能力、生态集成与版本节奏上， 且在持续变化。选型请以当前版本的官方能力与 POC 实测为准。
Q：Unique 模型能当 OLTP 库用吗？
A：不能。它是批量导入 + 覆盖合并的语义，不是逐行事务。 单行高频更新、需要事务隔离、需要低延迟点查 → 那是 OLTP 库的职责。 把 OLAP 当 OLTP 用是常见的架构错配。
