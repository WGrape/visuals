分支预测：95% 准确率为什么还是性能杀手

每 5~6 条指令就有一个分支，而流水线必须提前取指。猜错一次要清空 15~20 级前端。这一篇讲清 2 位计数器、TAGE、BTB 的原理，以及「准确率」和「性能损失」为什么不是一回事。

一句话定位：预测是为了「不停取指」

取指单元遇到分支时必须决定下一条取哪：顺序取下一条，还是跳到目标地址。等分支结果算出来再取，流水线就停了十几个周期，所以必须猜——猜对继续跑，猜错清空重来。

误预测代价约等于流水线深度（15~20 周期）
分支密度平均每 5~6 条指令 1 个分支
现代准确率95%~99%（大核）
关键结构方向预测器 + BTB + 返回地址栈
2 位饱和计数器：需要连续两次反向才翻转预测

把损失算成 CPI

CPI 增加 = 分支频率 × 误预测率 × 惩罚周期
误预测率分支频率 1/5分支频率 1/3含义
1%0.030.05几乎可忽略
5%0.150.25相当于慢了 15%~25%
10%0.300.50性能腰斩
20%0.601.00比不流水还慢
准确率不是线性指标

从 95% 提到 99%，误预测次数减少 5 倍，性能提升可能只有几个百分点——但某些分支密集的代码（解析器、状态机、虚函数调用）里，这 4 个百分点就是 20% 的差距。

预测器家族：从 2 位计数器到 TAGE

类型原理优点缺点
静态预测编译期决定（后向分支预测跳、前向预测不跳）零硬件成本准确率 70% 左右
1 位计数器记住上次结果简单循环边界必错两次
2 位饱和计数器连续两次反向才翻转循环只错一次对不规则分支无效
局部历史用该分支自己的历史做索引适合规律分支表容量压力大
全局历史（gshare）用最近 N 个分支的结果做索引能捕捉相关性历史混叠
Tournament两个预测器 + 选择器取长补短面积翻倍
TAGE多张不同历史长度的表投票现代主流，准确率最高实现复杂、训练慢

除了「跳不跳」，还要预测「跳去哪」：BTB（分支目标缓冲）缓存目标地址；函数返回用 RAS（返回地址栈）预测，因为同一个 return 指令的目标每次都不同。

代码层面：怎么让分支更好预测

// 难预测：数据驱动的分支
if (unlikely_condition) { ... }

// 好预测：循环边界（规律）
for (int i = 0; i < n; i++) { ... }

// 间接跳转是重灾区：虚函数、switch、函数指针表
switch (op) { case ADD: ... case MUL: ... }   // 目标多，BTB 压力大

// 无分支化：用算术或条件传送替分支
sum += cond ? x : 0;      // 可能编译成 cmov
mask = -(int)cond;        // 位掩码技巧

注意：无分支化不一定更快。cmov 会强制两条路径的数据都算出来，如果其中一条是昂贵的 load，反而更慢。要按「分支可预测性 + 两条路径的代价」判断。

排障：分支相关的问题定位

现象根因验证
同一段代码不同数据差 3 倍数据相关分支不可预测perf stat 看 branch-misses
虚函数调用密集处慢间接跳转 BTB 命中率低perf 看 iTLB/branch 事件
大 switch 性能悬崖跳转表 vs 比较链的选择看编译产物是否有 jump table
加了 if 反而更快帮助编译器生成更规整的布局对比汇编的跳转结构
Spectre 修补后变慢推测执行被限制（lfence/retpoline）属安全与性能的显式权衡

原理与取舍：为什么不能做到 100%

分支结果取决于运行时数据，而数据到达的时间晚于取指。理论上可以做到「预测所有可预测的模式」，但不可预测的分支（随机数据、哈希比较、解析器状态）没有规律可循。于是工程上转向两个方向：减少分支（谓词执行、向量化）和隐藏惩罚（更早解析分支、更小的冲刷范围）。

为什么循环边界用 2 位计数器只错一次？

进入循环时预测「跳」，最后一次退出时预测错 1 次并翻转到「不跳」；下次进入循环又会错 1 次。2 位计数器让「只错最后一次」成为可能，1 位则会错两次。

TAGE 是什么缩写？

TAgged GEometric history length——用几何级数长度的多段历史分别索引多张预测表，再由最长匹配的历史表给出预测，兼顾短规律与长规律。

分支预测和 Spectre 有什么关系？

Spectre 利用「预测执行会真的去读内存」这一点，通过缓存时序侧信道泄漏数据。修补手段（序列化、retpoline）本质是限制推测，代价是性能。

第一层 · 概念与判定：预测器在看什么

流水线越深，分支判断不出来就越要清空重来。分支预测器的任务就是在条件还没算出来时，先猜一条路走下去。猜对了零成本，猜错了要回滚。

预测类型依据典型准确率适用
静态预测编译期猜测（如「向后跳视为循环」）低（约 60–70%）无历史信息时的兜底
动态·局部这条分支自己的历史约 85–93%规律明显的循环
动态·全局（TAGE 类）其他分支的历史 + 本分支历史95–99%现代 CPU 主流
间接跳转预测历史目标地址高（用于虚函数调用）switch、函数指针、vtable

一句话判定：如果你的分支有规律（如循环、按状态机的分支），预测器几乎全对；如果是依赖随机数据的分支（如逐字符比较、随机 key 的 if），预测器会频繁失败。

第二层 · 参数·命令·量化：失败一次代价多少

量化维度典型数值说明
现代 CPU 流水线深度14 – 20 级越深，清空代价越大
分支预测失败惩罚15 – 20 个周期清空流水线 + 重新取指
预测器历史表项数数 K 到数十 K表越大越准，但面积/功耗也大
典型分支占比每 5 – 10 条指令有一条分支分支很密集，累积影响大
预测准确率 95% 时每 20 条指令浪费约 1 次惩罚约损失 5–10% 性能
预测准确率降到 80%性能可能掉 20–30%所以随机分支很伤

用 perf 量化分支预测失败

# 用 perf 直接量出分支预测失败率
perf stat -e branches,branch-misses ./your_program

# 输出示例解读：
#   branches          1,234,567,890
#   branch-misses        12,345,678   #  1.00% of all branches
# 经验阈值：branch-misses 超过 1% 就值得优化，超过 5% 通常是热点

# 定位到底是哪段代码在狂 miss
perf record -e branch-misses ./your_program
perf report

# C/C++ 里给编译器明确提示（把大概率分支标出来）
if (__builtin_expect(ptr != NULL, 1)) { /* 热路径 */ }

# 或者用 Linux 内核的宏
if (likely(ptr != NULL)) { ... }
if (unlikely(error_occurred)) { ... }

优化收益直觉：把 1% 的 miss rate 降到 0.5%，在 10 亿条分支的循环里能省下约 750 万个周期（约 2.5 ms）。

第三层 · 排障与边界

高频坑清单：

  • ① 误以为分支很便宜：现代 CPU 上预测失败的代价相当于执行十几条指令
  • ② 在热循环里放不可预测的分支：如逐字符比较字符串、按随机输入判断
  • ③ 滥用 likely/unlikely：标错了反而会让编译器把冷路径排进热区，适得其反
  • ④ 以为消除了分支但没消除：三元运算符、短路求值、&& 仍是分支
  • ⑤ 忘记间接跳转：虚函数调用、函数指针的 miss 代价比条件分支更高
  • ⑥ 用查表代替了分支，但表太大：跳转表能消除分支，但会带来 cache miss

排查顺序：先用 perf 确认 miss rate 真的高 → 用 perf report 定位到具体函数 → 再针对性改（消除分支或用查表）→ 改完必须复测。

第四层 · 原理与取舍

为什么要把 if 改成无分支（branchless）写法？

因为预测失败是概率事件，而 branchless 是确定的。比如 if (x > 0) sum += x; 在 x 随机正负时会频繁 miss，改成 sum += x & -(x > 0); 这类位运算就没有分支。但要注意取舍：branchless 在规律数据时反而更慢，因为它总要算两边，而可预测的分支几乎零成本。所以只在随机分支上用。

现代 CPU 预测器已经 99% 准了，还要管吗？

大多数情况不用管 —— 正常业务代码的预测准确率已经很高，优化它收益极小，不如去优化 cache 和算法。只有在极热的循环里（如解析器、编解码、数值计算、数据库内核），那 1% 的 miss 被放大到数十亿次才有意义。先 profile 再优化，别猜。

编译器能自动帮我消除分支吗？

能，但有限。编译器会做 if-conversion（把简单 if 转成条件传送 CMOV），但只对两条分支体都很短的情况有效；如果分支体里有函数调用、循环，它就不会转。此外 likely/unlikely 提示编译器优化布局，但它不影响预测器——预测器是硬件的，运行时自己学。
