编程范式：过程式、面向对象与函数式

三种看待问题的方式。它们不是互斥的阵营，而是同一个工具箱里的不同工具。

是什么

范式是「组织代码的思维方式」

编程范式不是语法特性，而是看待和分解问题的方式：程序是由「一步步指令」构成，还是由「相互作用的对象」构成，还是由「函数的组合」构成。

📋
过程式 / 指令式
按步骤修改状态：变量、循环、条件
🧱
面向对象 OOP
把数据与行为封装成对象，靠消息传递协作
🔗
函数式 FP
把计算看成函数组合，强调不可变与无副作用
现代语言多是「多范式」：Go 偏过程式但支持一等函数与接口；Python/JS 都能写 OOP 也能写 FP；Scala/Rust 更是显式融合。范式是工具箱，不是阵营。

函数式要点

函数式最值得借鉴的三件事

🧊
不可变
数据创建后不再修改，避免共享可变状态带来的并发问题
🧪
纯函数
相同输入必得相同输出、无副作用 → 易测试、易推理、易缓存
🔗
声明式与组合
用 map/filter/reduce 表达「要什么」而非「怎么做」，代码更短更清晰
// 指令式：描述「怎么做」，引入中间变量与可变状态
let result = [];
for (let i = 0; i < users.length; i++) {
    if (users[i].active) result.push(users[i].name);
}

// 声明式：表达「要什么」，无中间状态
const result = users.filter(u => u.active).map(u => u.name);
实践

实际项目里怎么选

  • 业务实体建模 → 面向对象直观（订单、用户、库存各有状态与行为）。
  • 数据转换与流水线 → 函数式的 map/filter/reduce 更清晰、更少 bug。
  • 底层与性能敏感路径 → 过程式最可控。
  • 并发密集 → 优先不可变数据、减少共享状态（Go 的「用通信共享内存」也是同一思路）。
不要为了范式而范式。强行把简单逻辑写成纯函数链，或为了「面向对象」给每个数据结构都配一层类，都会让代码更难读。范式服务于可读性与可维护性。
面试问答

高频问题

Q1：面向对象和面向过程的区别？
面向过程按步骤组织代码，关注「怎么做」，数据与操作分离；面向对象把数据与行为封装成对象，通过对象协作完成功能，更利于建模复杂业务与隔离变化。
Q2：什么是纯函数？有什么好处？
相同输入必定产生相同输出、且不产生可观察副作用的函数。好处是易测试、易推理、可缓存、可安全并发执行。
Q3：为什么函数式更适合并发？
因为它强调不可变数据与无副作用，消除了共享可变状态，从根上减少了数据竞争，因此不需要大量加锁也能安全并发。
Q4：不可变数据有什么代价？
每次「修改」都要创建新副本，可能带来额外的内存分配与 GC 压力。实践中常用结构共享（持久数据结构）或只在必要处使用不可变。
Q5：声明式和命令式有什么区别？
命令式描述执行步骤（怎么做），声明式描述目标结果（要什么）。声明式通常更简洁、更少中间状态错误，如 SQL、map/filter/reduce。

三种范式的核心差异：看状态放在哪

区分范式最有用的切入点是问一句：数据和对数据的操作是怎么组织的？状态放在哪里？答案不同，范式就不同。

范式组织方式状态在哪核心手段
过程式以步骤为中心，把问题拆成一串操作在变量与数据结构里，被函数读写顺序、分支、循环、函数拆分
面向对象以对象为中心，数据与行为绑定在一起封装在对象内部，只允许通过方法访问封装、继承、多态
函数式以计算为中心，把变换组合起来尽量不保留可变状态，变换产生新值纯函数、不可变、高阶函数、组合
三种范式的分野：状态由谁持有、由谁修改

同一个问题的三种写法

用一个具体任务来看差异最容易理解：把一组订单里已完成的挑出来，求金额总和。

// 过程式：一步步做，用循环与临时变量 func SumDone(orders []Order) int { total := 0 for i := 0; i < len(orders); i++ { if orders[i].Done { total += orders[i].Amount } } return total } // 面向对象：对象自己知道怎么回答 func (o *Order) IsDone() bool { return o.Done } type OrderList struct{ items []Order } func (l *OrderList) SumDone() int { total := 0 for _, o := range l.items { if o.IsDone() { total += o.Amount } } return total } // 函数式味道：把筛选和求和拆成可组合的变换 func SumDone2(orders []Order) int { return Sum(Map(Filter(orders, IsDone), Amount)) } // 三种写法都能用，选择依据是： // - 逻辑简单、追求直白 -> 过程式 // - 有清晰的对象边界与行为 -> 面向对象风格 // - 变换链条清晰、想复用每一步 -> 拆成小函数组合

不要为了范式而范式

把一个简单循环硬拆成链式变换，往往只是让代码更难读、更难调试。判断标准始终是：哪种写法让下一个读代码的人最快理解。

最值得借鉴的是函数式的三点

一是减少可变状态，能不改的变量就不改；二是把小函数组合起来，而不是写一个大函数；三是让函数更纯，同样的输入总是同样的输出，测试与并发都会简单很多。

Go 里的范式取舍

没有类与继承用组合与嵌入代替
接口是隐式实现天然支持面向行为编程
方法只是语法糖本质仍是函数，接收者是第一个参数
一等函数函数可作为参数与返回值
闭包捕获变量，但要注意循环变量的坑
不可变靠约定语言不强制，需要自己克制
泛型补齐抽象适合容器与通用算法
并发改变取舍共享可变状态在并发下代价很高
Go 是面向对象语言吗？

它有类型、方法、接口与封装，但没有类与继承。更准确的说法是：它支持面向对象的部分思想，尤其是封装与多态，同时刻意放弃了继承，用组合与接口来代替。这也是它代码风格偏平实的原因。

为什么不鼓励继承？

因为深层继承链会带来紧耦合与脆弱基类问题：改一个父类可能影响所有子类。Go 用组合加接口替代：复用靠嵌入，抽象靠接口，关系更扁平也更容易理解。

函数式能用到什么程度？

可以写纯函数、用高阶函数、用闭包，但没有模式匹配、没有内置的不可变数据结构、标准库也没有通用的链式操作。所以实践中通常是借鉴其思想，而不是照搬其他语言的写法。

什么时候该引入泛型？

当你发现同一段逻辑因为类型不同而重复写了多遍，且这段逻辑与具体类型无关时，比如容器与通用算法。不要用泛型做为灵活而灵活的抽象，接口往往更简单。

范式会互相冲突吗？

在同一份代码里混用是常态，冲突主要来自风格不统一。建议一个模块内部保持一致的风格：要么以对象方法为主，要么以纯函数变换为主，混搭会让读者不断切换心智模型。

一句话总结：范式不是非此即彼的选择题，而是描述代码组织方式的语言。真正决定代码质量的是边界是否清晰、状态是否可控，而不是用了哪一种范式。

三范式对照：能拿走用的取舍表

维度过程式面向对象函数式
核心抽象步骤与状态对象与消息纯函数与组合
状态管理可变、常共享封装进对象默认不可变
并发友好度差（靠锁）中（需刻意设计）好（无共享可变状态）
复用手段函数 / 模块继承、组合、多态高阶函数、组合子
典型失败全局状态难追踪、改一处崩一片继承爆炸、贫血模型、过度设计学习曲线陡、调试栈难读、有性能开销
最适用脚本、性能敏感的热路径复杂业务领域模型、需要多态扩展数据管道、并发、编译器、规则引擎

几个硬事实：Go 没有继承只有组合与接口；Java 是单继承 + 多接口；Haskell 默认惰性求值；Rust 用所有权系统在编译期排除数据竞争。不可变数据结构的持久化实现靠结构共享，单次「修改」是 O(log n) 而不是 O(n) 拷贝。

怎么选：场景 → 范式

场景推荐理由
一次性脚本、数据清洗过程式 + 少量函数式直来直去，别为抽象付费
业务域模型复杂、规则多变面向对象（组合优先）多态能把 if-else 换成扩展点
高并发服务函数式风格（不可变消息 + 纯处理函数）无共享就没有锁，也就没有数据竞争
ETL / 流式计算函数式（map/filter/reduce）组合性强，易并行
性能热路径（内层循环）过程式 + 可变局部变量避免分配与间接调用开销
UI / 状态机函数式 + 单向数据流状态变更可追溯、可回放

同一需求的三种写法

# 同一个需求：计算订单实付金额（满减 + 会员折扣 + 运费）
orders = [{"amount": 260, "vip": True}, {"amount": 80, "vip": False}]

# --- 过程式：一步步改状态 ---
total = 0
for o in orders:
    a = o["amount"]
    if a >= 200:
        a -= 30
    if o["vip"]:
        a *= 0.95
    if a < 99:
        a += 12
    total += a
print(total)

# --- 面向对象：把规则变成可扩展的策略对象 ---
class Rule:
    def apply(self, a, o): return a
class FullReduction(Rule):
    def apply(self, a, o): return a - 30 if a >= 200 else a
class VipDiscount(Rule):
    def apply(self, a, o): return a * 0.95 if o["vip"] else a
class Shipping(Rule):
    def apply(self, a, o): return a + 12 if a < 99 else a

def calc(o, rules):
    a = o["amount"]
    for r in rules:          # 新增规则 = 新增一个类，不改这里（开闭原则）
        a = r.apply(a, o)
    return a
rules = [FullReduction(), VipDiscount(), Shipping()]
print(sum(calc(o, rules) for o in orders))

# --- 函数式：规则是纯函数，用组合串起来 ---
def pipe(*fns):
    def g(a, o):
        for f in fns:
            a = f(a, o)
        return a
    return g
pricing = pipe(lambda a, o: a - 30 if a >= 200 else a,
               lambda a, o: a * 0.95 if o["vip"] else a,
               lambda a, o: a + 12 if a < 99 else a)
print(sum(pricing(o["amount"], o) for o in orders))

看完这三版的关键体会：过程式最短，面向对象最易扩展，函数式最易组合和测试。选哪个不取决于信仰，取决于这个需求将来更可能「变长」还是「变多」。

自检

Go 算不算面向对象语言？

不算典型 OO：没有类和继承，只有结构体 + 接口 + 组合。但它的接口是隐式实现的，实际上把「面向接口编程」做得比 Java 更轻。

函数式一定更慢吗？

不一定。不可变与高阶函数确实可能带来额外分配，但换个角度：无共享可变状态让并行变安全，省下的锁竞争往往远超分配开销。真正慢的通常是不经思考的链式中间集合（每次 map 都新建列表）。

什么时候继承是合理的？

三条同时满足：真的是稳定的 is-a 关系、层级不超过 2 层、子类不会需要「部分否决」父类行为。否则一律用组合。

实际项目里怎么混？

主流做法是外层面向对象组织、内层函数式实现：用对象划分模块边界和依赖注入，方法内部用纯函数处理数据。这也是大多数现代语言的实际写法。
