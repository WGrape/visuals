Worker Pool

用缓冲 channel 当信号量

启动固定数量的 worker，任务通过 channel 分发，既限制并发又避免无节制创建 goroutine。

sem := make(chan struct{}, 10)  // 最多 10 并发
for _, job := range jobs {
    sem <- struct{}{}
    go func(j Job) {
        defer func() { <-sem }()
        process(j)
    }(job)
}
Pipeline

阶段间用 channel 串联

每个阶段是「接收-处理-发送」的 goroutine，用 channel 连接；上游慢下游不慌，天然背压。

func stage(in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for v := range in { out <- v*v }
    }()
    return out
}
Fan-in / Fan-out

分叉并行，汇聚结果

Fan-out：多个 worker 消费同一输入提速；Fan-in：把多个 channel 合并成一个。二者常配合处理批量任务。

合并多个 channel 可用一个 select 循环，或把每个源用 goroutine 转发到统一输出再 close。
取消传播

用 context 统一撤收

长链任务把 ctx 一路传下去，父取消时所有子 goroutine 收到信号，及时退出、释放资源。详见 Context 篇。

ctx, cancel := context.WithCancel(parent)
defer cancel()
for i := 0; i < n; i++ {
    go worker(ctx, i)
}
// 某处 cancel() -> 所有 worker 的 <-ctx.Done() 解除阻塞

扇入扇出与流水线

扇入（合并）

把多个 goroutine 的结果汇总到一个 channel。

func merge(cs ...<-chan int) <-chan int { var wg sync.WaitGroup out := make(chan int) for _, c := range cs { wg.Add(1) go func(c <-chan int) { defer wg.Done() for v := range c { out <- v } }(c) } go func() { wg.Wait() close(out) // 全部结束才关闭 }() return out }

关键：等所有输入都结束（WaitGroup）之后再关闭输出。

流水线

每阶段一个 goroutine，用 channel 串联，天然并行。

// 阶段：生成 → 平方 → 输出 a := gen(1, 2, 3) b := square(a) for v := range b { fmt.Println(v) } func square(in <-chan int) <-chan int { out := make(chan int) go func() { defer close(out) for v := range in { out <- v * v } }() return out }

每个阶段都要保证「入参关闭 → 自己关闭出参」，否则会泄漏。

单飞 singleflight

同一 key 的并发请求只真正执行一次。

var g singleflight.Group v, err, shared := g.Do(key, func() (any, error) { return loadFromDB(key) // 只有一个请求真正执行 }) // shared=true 表示结果是与其他调用共享的 // 典型用途：防缓存击穿 // 热 key 失效时，成百上千个请求只会打一次数据库

这是防缓存击穿最直接的手段。

context：并发的生命周期管理

深入自检

goroutine 泄漏通常是怎么发生的？

三类最常见：从无人发送的 channel 接收；向无人接收的 channel 发送；循环里没有 ctx.Done 或关闭信号的退出分支。表现为 goroutine 数只增不减，可用 pprof 的 goroutine profile 直接定位堆积在哪个调用栈。

工作池的 worker 数怎么定？

区分任务类型：CPU 密集型接近 CPU 核数（再多只会增加调度开销）；I/O 密集型可以远大于核数，具体取决于下游承受能力，通常通过压测找到吞吐拐点。无论哪种都应有上限。

errgroup 和 WaitGroup 有什么区别？

WaitGroup 只等待完成，不处理错误与取消；errgroup 会收集第一个错误，并可通过 WithContext 在出错时取消其余 goroutine，还支持 SetLimit 限制并发数。需要「有一个失败就整体失败」时用 errgroup。

context.WithValue 该用吗？

可以，但要克制。它适合传请求级的横切数据（trace id、用户身份），不适合当函数参数袋。传值会降低代码可读性并让依赖隐式化，能用显式参数传的就用显式参数。

限流应该放在哪一层？

多层都要有不同目的的限流：入口层防突发流量，客户端层防打垮下游依赖，资源层保护自身（连接池、goroutine 数）。只在一处限流，往往挡不住最需要保护的那一个环节。

Worker Pool

// Worker Pool：控制并发的经典写法
func workerPool(jobs <-chan Job, results chan<- Result, n int) {
    var wg sync.WaitGroup
    for i := 0; i < n; i++ {              // 启动 n 个 worker
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := range jobs {         // <strong>channel 关闭时自动退出</strong>
                results <- process(j)
            }
        }()
    }
    wg.Wait()                             // 等所有 worker 结束
    close(results)                        // <strong>只有发送方才 close</strong>
}

// 使用
jobs := make(chan Job, 100)
results := make(chan Result, 100)
go workerPool(jobs, results, 8)           // 8 个并发
for _, j := range allJobs { jobs <- j }
close(jobs)                               // 关 jobs → worker 退出 → results 被关
for r := range results { handle(r) }

channel 的黄金规则：只由发送方关闭 channel。接收方关闭会导致「send on closed channel」 panic。多个发送方时用额外的 done channel 或 sync.WaitGroup 协调。

并发数怎么定

任务类型并发数依据典型值
CPU 密集CPU 核数runtime.NumCPU()
IO 密集（网络）下游承受能力10~1000，看对方限流
磁盘 IO磁盘并发能力机械盘 ≈ 1~4；SSD 可更高
混合分开控制不同阶段不同池

不要无脑开 goroutine：一万个 goroutine 同时打数据库，会把连接池打满、把数据库连接打爆。正确做法是用信号量或 Worker Pool 显式限制，上限参考下游的承受能力（如连接池大小的 80%）。

信号量限流

// 用带缓冲 channel 做信号量（最简洁的限流）
sem := make(chan struct{}, 20)      // 最多 20 个并发

for _, task := range tasks {
    sem <- struct{}{}               // 获取（满了会阻塞）
    go func(t Task) {
        defer func() { <-sem }()    // <strong>释放（务必 defer）</strong>
        do(t)
    }(task)                          // <strong>注意传参，避免闭包捕获陷阱</strong>
}
// 等全部完成：再获取 20 次（能全拿到说明都释放了）
for i := 0; i < cap(sem); i++ { sem <- struct{}{} }

// Go 1.18+ 也可用官方的 semaphore.Weighted（支持动态权重）
import "golang.org/x/sync/semaphore"
s := semaphore.NewWeighted(20)
s.Acquire(ctx, 1)
defer s.Release(1)

Singleflight：解决缓存击穿

场景：热点 key 过期，1 万个并发请求同时未命中，全部打到数据库。

Singleflight

import "golang.org/x/sync/singleflight"

var g singleflight.Group

func Get(key string) (any, error) {
    // <strong>相同 key 的并发调用只会执行一次 do 函数</strong>
    v, err, shared := g.Do(key, func() (any, error) {
        return dbQuery(key)          // 只有一个请求真正查库
    })
    // shared=true 表示结果被多个调用共享
    return v, err
}

// 效果：1 万个并发 → 只查 1 次库，其余 9999 个等待并共享结果

// 变体：
g.DoChan(key, fn)     返回 channel（可配合 select 做超时）
g.Forget(key)         手动清除（让下次 Do 重新执行）

// 注意：
#   1) 若 fn 阻塞，所有等待者都会阻塞 → <strong>要设超时</strong>
#   2) 一个失败，所有等待者都失败（不会重试）
#   3) 适合「重建代价高 + 并发集中」的场景，普通 key 不需要
方案做法适用
Singleflight合并相同 key 的请求缓存击穿首选
互斥锁抢锁重建，其余返回旧值逻辑过期方案
后台刷新过期前异步更新体验最好

自检 Q&A

Q：goroutine 泄漏怎么发现？

A：用 runtime.NumGoroutine() 监控，或 pprof 的 goroutine profile。典型泄漏模式：① 向无人接收的 channel 发送（永久阻塞）；② 从永不关闭的 channel 接收（永久等待）；③ select 里没有 default 也没有退出条件。规避手段：所有 goroutine 都要有明确的退出路径——用 context.WithCancel 或 done channel 控制，并在启动就想清楚「它什么时候结束」。压测时看 goroutine 数是否随请求线性增长，是则泄漏。

Q：channel 该用带缓冲还是无缓冲？

A：看是否需要解耦生产与消费速度。无缓冲（同步）：发送方会阻塞直到接收方就绪，起到同步与背压作用，适合需要严格交接的场景。带缓冲：允许短暂的速度差异，提升吞吐，但缓冲满了仍然阻塞——它只是把背压延后，不能消除。经验：若能估算峰值差，设一个小缓冲（如 worker 数的 1~2 倍）；不能估算就用无缓冲，让背压自然传递。

Q：select 多个 case 同时就绪会怎样？

A：随机选一个。Go 刻意做了随机化，避免某个 case 长期被饿死（如果按固定顺序选，高频率的 case 会永远抢占）。所以不要依赖 select 的 case 顺序。另外要注意：如果 select 里有 default，它是非阻塞的——没有任何 case 就绪时立即执行 default，这在轮询场景有用，但会造成 busy loop（应配合 sleep 或去掉 default）。

Q：errgroup 和 WaitGroup 怎么选？

A：优先 errgroup。它比 WaitGroup 多两个关键能力：① 错误传播（任一任务出错，能拿到第一个错误）；② 取消传播（用 WithContext 时，一个任务失败会自动取消 context，其他任务收到信号后退出）。WaitGroup 只能等，没法知道是否出错、也没法提前终止。唯一的注意点：errgroup 里的任务必须响应 context 取消，否则取消信号无效——这也是写好 Go 并发的通用要求。
