大模型选型

大模型选型指南：能力、成本、延迟、合规怎么权衡

"用哪个模型"不是一个分数题，而是一道多维约束下的决策题。本文给出一套可复用的选型框架：先看硬约束（合规、数据不出域）划范围，再看能力门槛，最后用成本和延迟做收敛，并给出分级路由这类实战打法。

第一刀：闭源 API vs 开源自部署

闭源 API（云端大模型）开源自部署
能力上限通常最强，且持续升级，不用自己运维头部开源已很接近，但顶尖能力仍有差距
成本结构通常按 token 或请求计费，也可能有最低消费与专有容量费用；适合先验证需求或承接波动流量需核算 GPU、运维与利用率；稳定高负载时可能降低单位成本
数据合规核对供应商的数据留存、处理区域、私网接入与合同约束可控制部署域与日志，但仍需落实权限、审计和数据治理
可控性不可改权重、不能微调（或受限），版本可能静默变更可微调、可量化、可定制、版本锁定
运维仍需管理配额、版本变化、故障回退与调用监控还需管理推理服务、扩缩容和 GPU 监控（vLLM / TGI 等）
适合快速验证、通用场景、流量不稳、无合规压力规模化稳定流量、强合规、需领域微调、要压成本
现实中大量团队是混合：通用/复杂任务走闭源，高频简单任务走自建小模型。

成本与延迟：怎么算

成本

单次成本 ≈ 输入 token × 输入单价 + 输出 token × 输出单价
  • 输出 token 通常比输入贵数倍，所以"让模型少废话"是直接的降本手段。
  • 缓存命中能大幅降低重复前缀的成本（Prompt Caching）——把稳定的 system prompt / 长文档放前缀。
  • 自部署要算单卡吞吐 × 显卡时租金，再折算成每千 token 成本，与 API 对比。

延迟

首 token 延迟 TTFT
决定"多久开始出字"，受 prompt 长度、排队、网络影响
生成速度TPOT / tokens-per-second
决定"出字快不快"，受模型大小、量化、batch 影响
规律：更小的模型与量化通常能节省显存或计算，但可能影响任务质量；增大 batch 往往改善吞吐，却可能拉长单个请求的等待时间。选型要同时实测质量、TTFT、吞吐和单位成本。

实战打法：分级路由（Model Routing）

不要试图用一个模型解决所有请求。常见做法：

  1. 先分类：用规则或小模型判断请求复杂度（简单问答 / 抽取 / 复杂推理 / 代码）
  2. 再分流：简单任务 → 小模型（快且便宜）；复杂任务 → 强模型
  3. 兜底重试：小模型结果置信度低或校验失败时，自动升级到强模型重跑
  4. 持续回收：统计各档位的成功率与成本，动态调整阈值
这套打法通常能在几乎不掉点的前提下把成本砍掉大半，是生产环境最常见的优化手段。
注意路由本身也有成本和错误率：路由错了会把复杂题送给小模型。务必为"降级"保留出口（用户反馈 / 校验失败即升级）。

面试速记卡

  • 第一刀：合规/数据不出域是硬约束，直接决定闭源还是自部署。
  • 闭源 vs 开源：闭源能力强、零固定成本、数据出网；开源可控、可微调、量大更省、要运维。
  • 验证：公开榜单只做初筛，必须用自建评测集；重点看 badcase 与格式遵循。
  • 成本：输出 token 更贵；Prompt Caching 降重复前缀成本。
  • 延迟：TTFT（首字）与 TPOT（出字速度）分开设指标。
  • 高级打法：分级路由 + 失败升级，显著降本且基本不掉点。

# 三维打分脚本：效果 / 延迟 / 成本
python - <<'PY'
import time, statistics, json

def evaluate(model, cases, price_in, price_out):
    acc, lats, tin, tout = 0, [], 0, 0
    for q, gold in cases:
        t0 = time.perf_counter()
        pred, usage = call(model, q)          # 你的调用封装
        lats.append((time.perf_counter() - t0) * 1000)
        acc += (pred.strip() == gold)
        tin += usage["prompt_tokens"]; tout += usage["completion_tokens"]
    acc /= len(cases)
    cost = tin / 1e6 * price_in + tout / 1e6 * price_out
    return {
        "model": model,
        "acc": round(acc, 3),
        "p50_ms": round(statistics.median(lats)),
        "p95_ms": round(sorted(lats)[int(len(lats) * 0.95)]),
        "cost": round(cost, 4),
        "tokens": {"in": tin, "out": tout},
    }

for m, pi, po in [("A", 3.0, 15.0), ("B", 0.3, 1.5), ("C", 0.0, 0.0)]:
    print(json.dumps(evaluate(m, CASES, pi, po), ensure_ascii=False))

# 路由与降级：按任务难度分流，控制成本
#   简单任务 -> 小模型；困难任务 -> 大模型；失败 -> 重试上一档
def route(task):
    tier = classify_difficulty(task)          # 规则或小模型打分
    for model in TIERS[tier:]:                # 从当前档往大档退
        try:
            out = call(model, task)
            if validate(out):                 # 结构化校验/自检
                return out
        except Exception:
            continue
    raise RuntimeError("all tiers failed")

深入自检

选型时最该避免的做法是什么？

只看公开榜单。榜单与你的任务分布、提示风格、输出格式要求都不同，排名往往不能直接迁移。正确做法是用自有评测集（至少 200~500 条覆盖典型与边界样本）做盲评，同时记录延迟与成本，三维一起比较。

成本和效果冲突时怎么决策？

先定效果底线（关键任务不可退让），再在达标者中选成本最低的；若都不达标，考虑任务拆分——让小模型做简单部分（分类、抽取、改写），大模型只处理少数困难样本，通常能以 1/5~1/10 的成本拿到 90% 以上的效果。

为什么不直接看绝对价格？

因为模型定价、上下文单价、输入输出差价变动频繁，且不同厂商计量口径不同。用「相对倍数 + 实际 token 消耗量」更稳定：先测出你的任务每千次调用消耗多少 token，再乘以单价，得到的才是真实月成本。

如何评估延迟是否可接受？

分开看 TTFT（首字延迟，决定“卡不卡”）与 TPOT（每 token 时间，决定“流得快不快”），并看 P95 而不是均值。交互式场景的体感门槛大致是 TTFT < 1 秒、TPOT < 30 ms；批量任务则更关注总吞吐与配额。

换模型时要做什么回归？

三件事：① 在同一个评测集上重跑，比较分项指标（不要只看总分）；② 检查结构化输出的合法率（JSON 解析成功率、字段完整率）；③ 检查失败与重试率的变化。提示词往往需要按新模型重新调整，尤其是格式约束与 few-shot 示例。
