1. 物理内存碎片是什么

内核分配高阶页框时，通常需要一段连续物理页。即使总空闲页数足够，若空闲页散落在多个不相邻位置，也可能无法满足请求。这是物理页层面的外部碎片；按固定大小或 2 的幂次分配时，实际用量小于拿到的块大小，则会产生内部碎片。

假设每格代表一个物理页： [已用][空闲][已用][空闲][已用][空闲][空闲][已用] 空闲共 4 页，却只有一段连续 2 页；申请连续 4 页会失败或触发规整。

普通用户进程的连续虚拟地址不一定要求连续物理页；透明大页、部分 DMA 或其他高阶页框分配才更直接受物理碎片影响。具体失败路径还取决于可回收页、内存区域和分配标志，不能仅凭总空闲量断言一定触发 OOM。

2. 伙伴系统：分裂与合并

Linux 以伙伴系统管理物理页框。空闲块按 order 分类，order 为 n 的块有 2n 个连续页；没有合适块时可以分裂更大块，释放时只有同阶且空闲的伙伴才能合并。它能快速管理页框，但相邻页若被占用，分散的小块就无法凭合并得到大块。

分配 4 页：查 order 2 → 若无空闲块，分裂 order 3 的 8 页块。 释放 4 页：检查相邻的同阶伙伴 → 两者都空闲才合成 8 页块。 若伙伴仍在使用，空闲总量增加也无法合成连续 8 页。
关键取舍：伙伴系统通过分裂与合并减少碎片，但 3 页需求通常会占用 4 页块，形成内部浪费；长期混合不同生命周期的页仍会形成外部碎片。

3. 内核对象缓存与内部碎片

内核需要频繁分配 inode、dentry 等对象。Slab/SLUB 等对象缓存按对象类型或大小管理槽位，复用已分配的页，降低小对象分配成本。它处理的是内核对象，与伙伴系统管理物理页框的层级不同。

伙伴系统提供物理页 → 对象缓存把页划成槽位 → 相同大小的内核对象复用槽位。 对象释放后槽位可重用；只有满足回收条件的空页才能交还页框分配器。

固定槽位减少对象间的外部碎片，却可能留下槽位内部浪费和未完全释放的对象页。它不能直接保证高阶页框分配成功。

4. 页面迁移与内存规整

当需要连续物理页时，Linux 可尝试把可移动页迁移到其他空闲页，调整页表映射，从而聚合出较大的连续空闲区域。内核也按页的可迁移性组织页块，减少不可移动页把区域切碎的机会。

规整前： [可移动][空闲][不可移动][可移动][空闲][空闲] 迁移可移动页后：部分空闲页得以相邻；不可移动页仍可能阻断连续空间。

规整有复制、页表更新和延迟成本，也不能移动所有页。透明大页等场景可能触发后台或直接规整；是否值得开启相关策略，应按业务延迟和高阶分配需求判断。

碎片有两种，别混为一谈

内存没法用满，浪费的部分叫碎片。但浪费发生的位置不同，成因与解法完全不同。

碎片的两个层次：块间的空隙 vs 块内的空置

三种放置策略：谁更容易产生外部碎片

策略做法优点缺点
首次适应 First Fit从头找到第一个够大的空闲块快，倾向保留大块在后部容易在前端积累小碎片
最佳适应 Best Fit找大小最接近需求的块剩下最小的碎片倾向制造大量极小的、永远用不上的碎片
最坏适应 Worst Fit挑最大的那个块来切剩下的碎块较大仍有用途很快就把大块消耗殆尽
下次适应 Next Fit从上次的位置继续找分布更均匀实现略复杂，介于两者之间

实践结论并不直观：理论与模拟显示首次适应通常表现良好，而且因为它不需要遍历全部块，速度也最快。最佳适应听起来最聪明，实际上会留下大量无法再利用的针尖式碎片。

整理（紧凑）：最直接也最麻烦的办法

既然问题是「不连续」，那就把已占用的块全部往一边搬，让空闲集中到另一边。这在理论上完美，但在实践中有三个硬伤：

  1. 指针全部失效。对象地址变了，所有指向它的指针、引用、内部偏移量都要修正。C/C++ 这类能露出裸指针的语言，运行时几乎无法安全完成这件事。
  2. 移动需要停机。搬运期间不能让别的线程访问这些对象，通常需要「停止整个世界」。
  3. 本身要耗时。紧凑通常依赖发起请求时才顺手做（如 slab 的 compaction），搬运数据量大的时候会明显卡顿。

现代操作系统其实用「虚拟内存」绕过了这件事：

虚拟内存用「映射」消灭了物理连续性要求

于是矛盾发生了转移：外部碎片基本消失了，剩下的主要是内部碎片（最后一页用不满的平均浪费是半个页，4KB 页就是大约 2KB）。

现代内存分配器怎么做事

① 伙伴系统 Buddy

物理页按 2 的幂管理：请求 3 页就给 4 页，请求 9 页就给 16 页。释放时若「伙伴」也空闲就合并成更大块。

优点：合并判断极其简单（看相邻块是否同阶）。缺点：内部碎片平均接近 25 百分号，最坏接近一半。

② Slab / SLUB

在伙伴系统之上再套一层「对象缓存」：为每种常见大小维护若干个 slab，里面预先切好等大对象，用完 physical memory 归还。

好处有二：消除该尺寸的内部碎片，且对象不必反复构造初始化（缓存热的）。Linux 内核大量使用它。

③ GC 里的三种策略

标记-清除：不移动，会产生碎片；标记-整理：移动压实解决碎片，但要修正引用；复制回收：把活对象复制到另一半空间，顺手完成整理。

这就是为什么带 GC 的语言可以做压实而 C/C++ 不能 —— 语言层面能定位并修改所有引用。

④ 实践建议

应用层最容易犯的错是反复申请释放不同大小的块。稳定做法是：用对象池/内存池、尽量按固定大小批量分配、避免大量短生命周期对象。

排查时用 pprof / jemalloc profile 看地址空间的空闲分布，而不是只看 RSS。

深入自检

有了虚拟内存，是不是就没有碎片问题了？

物理层面的外部碎片基本消解了，但问题转移到了两个地方：① 进程虚拟地址空间里仍然会出现碎片（尤其是长期运行、频繁 mmap 的服务），这就是为什么 64 位程序比 32 位不容易「地址空间耗尽」；② 页/块内部的浪费依然存在，这是无法消除的，只能靠更细的粒度或专用缓存来降低。

为什么整理 compaction 不能随便用？

因为它要移动对象的地址。任何持有这个对象地址的地方都必须同步更新 —— 包括其它语言写的扩展、DMA 缓冲区、甚至是你自己 log 出来的指针值。语言运行时若不能可靠地找到并修改所有引用，压实就是不安全的操作。这也是为什么「停止世界」式的整理阶段往往会带来明显卡顿。

伙伴系统为什么非要按 2 的幂？

为了让「相邻块能否合并」的判断变成一次简单的位运算：两个同阶且地址相邻的块互为伙伴，合并条件极易验证。代价是分配粒度粗，导致平均约四分之一的内部碎片。现实中伙伴系统负责大块，小块交给 slab/slub 之类的二级分配器处理。

我自己写代码要注意什么？

三条：① 尽量复用对象（池化），尤其是高并发路径上的临时对象；② 避免混着大量不同尺寸的长短命分配，那是最容易制造碎片的模式；③ 长期运行的服务要监控 RSS 与实际使用量的差值，差值持续变大往往就是碎片或泄漏在积累 —— 两者要用不同的指标分开观测，不要只盯一个数字。
