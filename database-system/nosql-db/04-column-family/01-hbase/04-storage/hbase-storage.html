💾 HBase 存储结构

HFile 格式、WAL、MemStore 刷写、Compaction 与 BloomFilter

写入的两条路径

一次 put 会同时写两个地方：WAL（顺序追加到 HDFS，用于崩溃恢复） 和 MemStore（内存中的有序结构）。只有两者都成功才返回客户端。HFile 不是写入时产生的，而是 MemStore 攒够后 flush 出来的。

HFile 内部结构

HFile 是不可变（immutable）的有序文件，按 (rowkey, 列族, 限定符, 时间戳) 排序。它分成若干层，从尾到头读：

块作用何时加载
Data Block真正的 KeyValue 数据，默认 64KB 一块按需读入 BlockCache
Meta Block元数据（BloomFilter 等）打开文件时
File Info文件级信息（平均 key 长度、压缩算法等）打开文件时
Data Block Index每个 Data Block 的起始 key → 偏移量常驻内存（打开即载入）
Trailer指向其他各块的指针，定长首先读（在文件末尾）
💡 查找一个 key 的过程：读 Trailer → 找到 Index（在内存）→ 二分定位到可能包含该 key 的 Data Block → 读该 block（可能命中 BlockCache）→ 在 block 内顺序扫描。BloomFilter 在这一步之前先做「这个文件一定没有这个 key」的判断，省掉整次 IO。

BloomFilter：读放大的克星

LSM 结构下一次读可能要查 MemStore + 多个 HFile。BloomFilter 用极小的内存（每个 HFile 一份）回答一个保守问题：「这个文件里肯定没有这个 rowkey 吗？」——如果答「肯定没有」就直接跳过整个文件。

ROW（默认）按 rowkey 过滤，get 场景收益最大
ROWCOL按 rowkey+列族+限定符 过滤，精确到列
NONE关闭；纯 scan 场景可关掉省内存
代价每个 HFile 多占几 KB~几十 KB 内存
⚠️ BloomFilter 有假阳性（说可能有、实际没有），但不会假阴性。所以它只会带来「多读一个文件」的浪费，不会漏数据。

Compaction：两种

类型触发范围特点
MinorStore 内 HFile 数 ≥ 3挑选部分相邻小文件合并轻量、频繁；不删除墓碑与过期版本
Major默认 7 天一次，或手动Store 内全部文件合并成一个重量级（大量 IO）；真正物理删除墓碑与超期数据

为什么要 Compaction

  • 减少文件数 → 减少读时要查的文件数量（降低读放大）
  • 回收空间：真正删掉被覆盖的旧版本与 delete 墓碑
  • 提升本地性：合并后的新文件重新分布到本机 DataNode

Compaction 的副作用

  • 写放大：同一份数据被反复读写合并
  • 占用 IO/网络，可能影响在线读写 → 要限速
  • Major Compaction 期间磁盘 IO 峰值明显

Region Split：自动分片

  • Region 内某个 Store 的总大小超过阈值（默认 hbase.hregion.max.filesize = 10GB）
  • RegionServer 找到该 Region 的中间 rowkey（split point）
  • 在该点把 Region 切成两个子 Region（原 Region 下线）
  • 子 Region 先在同一 RS 上，随后 HMaster 做负载均衡把它们搬走
  • 引用文件机制让子 Region 先「引用」父 HFile，避免立刻拷贝数据
    • ⚠️ 频繁 split 会产生大量小 Region 与小文件，触发更多 compaction。生产上强烈建议建表时预分区（pre-splitting），并按数据增长速率调大 max.filesize（如 20~50GB）。

    关键参数速查

    参数默认含义
    hbase.hstore.flush.size128MB单个 MemStore 超过就 flush
    hbase.regionserver.global.memstore.size0.4RS 上所有 MemStore 占堆上限，超了强制 flush 并可能阻塞写

    🎯 常见问法与答题要点

    Q：一次 put 会立刻写磁盘吗？

    A：不会写 HFile，但会写 WAL（顺序追加到 HDFS）。路径是：put → 追加 WAL → 写入内存 MemStore → 返回成功。HFile 要等 MemStore 攒到 128MB 才 flush 生成。所以「写入快」的本质是：只做了一次顺序 WAL + 一次内存写，没有随机磁盘 IO。

    Q：HFile 为什么设计成不可变的？

    A：不可变带来三个好处：①无锁并发读——文件不会变，多个读不用加锁；②缓存安全——BlockCache 里的 block 永远不会失效；③顺序写 + 多副本简单——HDFS 只支持追加，不可变文件天然契合。代价是更新只能「写新版本」，删除只能「写墓碑」，最终靠 compaction 合并整理。

    Q：读放大是什么？怎么缓解？

    A：LSM 下一次 get 可能要查：MemStore + BlockCache + 磁盘上多个 HFile。HFile 越多读越慢，这就是读放大。缓解手段：①BloomFilter 跳过肯定不含该 key 的文件；②Compaction 减少文件数量；③BlockCache 缓存热 block；④控制 flush 频率避免产生过多小文件。

    Q：Minor 和 Major Compaction 的本质区别？

    A：Minor 只挑选部分相邻的小文件合并，轻量高频，不做物理删除（墓碑和旧版本仍在）。Major 把 Store 内所有文件合并成一个，会真正丢弃超过 VERSIONS 的版本、超过 TTL 的数据和 delete 墓碑。所以「删了数据磁盘没变小」往往是在等 major compaction。

    Q：写入突然被阻塞（blocked）是怎么回事？

    A：典型是触发了 blockingStoreFiles（默认 16）：某个 Store 的 HFile 数量达到上限，HBase 会阻塞该 Store 的写入，等 compaction 把文件数降下来。原因通常是写入太快而 compaction 跟不上。对策：调大 blockingStoreFiles、调大 compaction 线程数、检查是否关闭了自动 compaction、优化 rowkey 减少小文件。

    Q：BloomFilter 该选 ROW 还是 ROWCOL？

    A：默认 ROW 就够，它按 rowkey 过滤，对 get 场景收益最大。如果查询经常指定到具体列（且列非常多），ROWCOL 更精确，但 BloomFilter 体积也更大（每条 cell 都要算）。纯 scan（全表扫描）场景 BloomFilter 没用，可以关掉省内存。

    Q：为什么建议建表时预分区？

    A：不预分区的表一开始只有 1 个 Region，所有写入打在单台 RegionServer 上形成热点，而且随着数据量增长会不断自动 split，产生大量小 Region 和随之而来的 compaction。预分区在建表时就按规划的 rowkey 范围切好 N 个 Region（配合散列 rowkey），从第一天起就是分布式的。
