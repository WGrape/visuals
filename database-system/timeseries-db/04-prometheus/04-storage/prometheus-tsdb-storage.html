01写路径：从抓取到落盘

写路径：样本先进内存 Head 并追加 WAL；每 2 小时把 Head 落成一个不可变 Block；后台再把这些 Block 合并成更大的 Block。
  1. 抓取 → Head Block：样本先进内存中的 head block，同时建立倒排索引（label → 时间线列表）。
  2. 追加 WAL：同一份样本追加写入预写日志，用于崩溃恢复。这是写放大的来源之一，也是为什么 Prometheus 的磁盘 IO 模式是「顺序小写 + 周期性大块」。
  3. 每 2 小时切块：head 中的数据达到时间跨度阈值后，被压缩成一个不可变的 block 目录（包含 chunks、index、meta.json、tombstones）。2 小时是常见的默认块跨度，属于实现细节，不同版本可能调整。
  4. 后台 Compaction：把多个相邻小 block 合并成更大的 block，同时清理被删除的数据和超过保留期的数据。
为什么是「不可变 block + 合并」而不是原地更新？因为时序数据的删除永远是「整段时间一起删」（保留期到期），而不是「删某一条」。按时间分块后，删一个 block 就是删一个目录，代价极低；如果原地更新，就要做代价高昂的随机删除和空间回收。

02内存去哪了：基数才是内存杀手

不要按「存了多少数据点」估算 Prometheus 内存，要按「有多少条活跃时间线」估算。每条活跃时间线在 head block 里都要维护索引条目和最近样本，成本是每条线固定开销 × 活跃线数，与样本总量关系不大。这就是为什么加一个高基数 label 会让内存暴涨。
因素对内存的影响控制手段
活跃时间线数主导因素，近似线性控制 label 基数；用 sample_limit 类的配置限制单个目标的样本数
head block 覆盖的时间跨度跨度越长，内存中数据越多由块跨度（2h）决定，通常不该改
抓取间隔间隔越短，同样跨度内样本越多非核心指标拉长到 30s/60s
WAL 与 checkpoint崩溃恢复需要保留的日志量由实现自动管理，关注磁盘水位即可

03读路径：为什么长周期查询会拖垮实例

  • 查询按时间范围裁剪 block：只加载时间区间有交集的 block，未命中的直接跳过。这是分块带来的最大好处。
  • 近期数据走 head（内存），历史数据走 block（mmap 读盘）。跨 head + 多个 block 的查询需要合并结果，代价随覆盖的 block 数增长。
  • block 经过 compaction 合并后数量减少，长周期查询会变快——这就是 compaction 除了省空间之外的第二个价值。
  • 但加载的 chunk 数和解压的样本数才是主要成本：查 30 天 × 1000 条时间线 = 需要解压海量样本，比查 1 小时贵几个数量级。
实践结论：仪表盘默认时间范围要短（1h/6h），长周期分析交给 recording rule 预聚合后的指标，或者直接查远端存储。不要让 Grafana 变量允许用户随意把范围拉到 30 天。

04保留期与长期存储

方案做法优点代价
调大本地保留期启动时配置 --storage.tsdb.retention.time零组件、查询最快单机容量与内存受限；长周期查询变慢；单点故障丢历史
remote_write 到远端Prometheus 边写本地边转发样本本地保持轻量，历史集中存；可跨集群聚合多一个组件；要处理队列堆积与丢数监控
降采样（recording rule）把细粒度指标预聚合成 5m/1h 粒度长期保存存储量下降一两个数量级丢掉原始细节；规则要维护
联邦（federation）上层 Prometheus 拉取下层的聚合结果层级清晰，适合多集群只能拉聚合后指标，不能拉原始序列
remote_write 必须监控它自己。远端存储挂掉或网络拥塞时，Prometheus 会把样本堆在内存队列里，堆满后开始丢数据。一定要对 prometheus_remote_storage_* 系列指标（队列长度、失败率、落后程度）设告警，否则远端静默丢数你可能很久都不知道。具体指标名以你版本的文档为准。

05磁盘与运维要点

  1. 磁盘容量 ≈ 每秒样本数 × 每样本字节 × 保留秒数。先估算 rate(prometheus_tsdb_head_samples_appended_total) 再乘保留期，别拍脑袋。
  2. 用 SSD。虽然 WAL 是顺序写，但查询时要随机读大量 chunk，机械盘会成为瓶颈。
  3. 不要放在会被外部清理的目录。有人把数据目录挂到临时卷上，重启就没了。
  4. Prometheus 自身要被监控：至少关注目标存活（up）、抓取耗时、TSDB 的 WAL 回放与 compaction 耗时、head 里的 series 数。
  5. 本地存储不是 HA 的。两台 Prometheus 抓同样的目标是常见做法（各自独立存储），但它们的查询结果可能因为抓取时刻不同而略有差异——做 HA 时要注意这个「双写不一致」。
默认值与路径相关提示：块跨度（2h）、默认保留期、数据目录位置、compaction 并发等参数的具体默认值随版本变化。请以你部署版本的官方文档为准。

每样本 1.7 字节是怎么来的：Prometheus 用的是 delta-of-delta 编码+ XOR 压缩。时间戳用 delta-of-delta（大多数样本间隔固定，delta 的 delta 是 0，一个比特就能表示）；值用 XOR（相邻值接近，XOR 后高位全 0）。两者结合让每个样本平均只占 1.7 字节——而原始存储需要 16 字节（8 字节时间戳 + 8 字节 float64），压缩比约 9 倍。

配置与命令

# 启动参数
prometheus \
  --storage.tsdb.path=/data/prometheus \
  --storage.tsdb.retention.time=15d \        # 保留期（默认 15 天）
  --storage.tsdb.retention.size=500GB \      # 或按大小限制
  --storage.tsdb.max-block-duration=2h \     # block 时长
  --storage.tsdb.wal-compression \           # 开启 WAL 压缩（省 30~50%，2.11+）
  --config.file=prometheus.yml

# 注意：retention 修改需要重启；且 <b>不能同时设 time 和 size 的严格限制</b>
# 实际行为：先到哪个限制就用哪个

# 查看存储使用情况
du -sh /data/prometheus/*
ls /data/prometheus/01HXXXX/          # 每个 block 一个目录
#   chunks/  存实际数据
#   index    倒排索引（label -> series）
#   meta.json block 元信息（时间范围、series 数）
#   tombstones 删除标记

# 查询 TSDB 状态
curl 'localhost:9090/api/v1/status/tsdb' | jq
# 返回：headStats（numSeries, chunkCount, minTime, maxTime）
#       seriesCountByMetricName / labelValueCountByLabelName（找基数大的）
# 基数爆炸排查（Prometheus 最常见的运维问题）
# 1) 找出 series 数最多的指标
topk(10, count by (__name__)({__name__=~".+"}))

# 2) 找出基数最大的 label
topk(10, count(count by (instance)({__name__=~".+"})))

# 3) 查看总 series 数
prometheus_tsdb_head_series        # Head block 里的 series 数
prometheus_tsdb_head_samples_appended_total

# 4) 单个指标占多少 series
prometheus_tsdb_symbol_table_size_bytes
# 或用 API
curl 'localhost:9090/api/v1/label/__name__/values' | jq 'length'

# 限制基数（Prometheus 2.x 的配置）
# scrape_configs 里：
#   metric_relabel_configs:
#   - source_labels: [url]
#     action: drop                  # 直接丢弃高基数指标
#   - source_labels: [user_id]
#     action: labeldrop             # 删掉高基数 label
