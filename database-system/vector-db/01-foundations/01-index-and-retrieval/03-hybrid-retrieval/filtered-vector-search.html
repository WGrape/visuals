过滤向量检索

真实查询几乎都带业务约束：「查语义最像、且属于 A 部门、近 7 天、状态=有效」。本文讲清 pre-filter / post-filter、空结果陷阱、过滤下的 ANN 机制与兜底策略。

01为什么需要过滤

纯向量检索只管「语义像不像」，但业务常要求「语义像 AND 满足条件」。

例：客服知识库只召回「当前生效」的文档；商品推荐只召回「该用户可见」的 SKU；监控告警只查「近 7 天」的指标。

02pre-filter vs post-filter

pre-filter（先过滤再搜）post-filter（先搜再过滤）
含义只在对满足条件的子集做 ANN先 ANN 取 Top-K 再筛条件
优点结果一定满足条件检索快、不限制候选池
缺点子集太小/空 → 召回失败Top-K 被滤光 → 返回 <K 甚至 0
适用过滤选择率高、条件硬条件软、希望尽量有结果

03空结果陷阱

post-filter 取 Top-K=10，结果 10 条都不满足「部门=A」→ 返回 0 条，用户以为「没答案」。

更隐蔽的是返回 3 条（10 条里只有 3 条满足），用户以为「就这么多」，其实还有相关内容没被召回。

生产环境必须监控「过滤后返回数 / K」的比例。长期偏低说明索引或过滤设计有问题，而不是「数据少」。

04过滤下的 ANN 机制

Qdrant

payload 字段建索引（match / range），HNSW 检索时逐层用 payload 过滤候选；选择率极低时退化为近暴力扫描。

Milvus

bool_expr 过滤，配合标量索引；过滤与向量检索并行后再合并。

选择率（满足过滤的比例）直接决定召回与延迟：选择率 0.1% 比 50% 慢很多，因为极少数点散布在各层图里。

05查询改写与兜底

放宽条件

严格过滤无果 → 自动放宽时间窗/部门一档做降级召回。

双路融合

向量 + 标量双路召回，最后融合，避免单路被滤光。

退到关键词

向量检索无果 → 退到 BM25 / 关键词匹配。

分层 fallback

先 strict 过滤，结果为空自动放宽一档重试。

06实践建议

建标量索引

高频过滤字段务必建标量索引（等值和范围）。

控制选择率

避免「稀有条件」做 post-filter，否则必空结果。

监控空结果率

告警「返回数/K」长期低于阈值。

建模原则

过滤字段设计成独立标量，而非塞进文本让向量去学。

类比：过滤像「在图书馆先按楼层/类别筛选书架，再在里面找最像的书」——先选书架（pre）还是先抱一大堆书再一本本翻（post），效率和结果天差地别。

过滤向量检索：三种策略的代价

带过滤条件的向量检索难点在于：ANN 索引是按向量距离组织的，不是按属性组织的。过滤条件会把索引的近邻结构打乱，导致召回率暴跌。

策略做法优点致命问题
Pre-filter（先过滤后检索）先用属性过滤出候选集，再暴力/索引检索结果精确，不漏过滤后候选可能极多 → 退化成暴力搜索，慢
Post-filter（先检索后过滤）先 ANN 检索 top-K×N，再按属性过滤快，索引效率高可能召回不足——符合条件的都在 K×N 之外
Hybrid / 过滤感知索引索引内部按属性分区（如 IVF + 每个聚类带属性倒排）两者兼顾实现复杂，索引膨胀
过滤选择性推荐策略原因
高选择性（命中 <1%）Pre-filter 或 分区索引候选少，暴力也快；Post-filter 必然召回不足
中等（1%~20%）分区 / 过滤感知索引两种极端策略都不好
低选择性（>50%）Post-filter大部分都符合，过滤影响小
产品过滤实现注意
Milvus分区 + 表达式过滤，支持 pre/post 自动选择高选择性场景建议用 partition key 物理分区
Pineconemetadata filtering（单阶段过滤感知）注意 metadata 大小限制
Qdrantpayload index + 过滤感知 HNSW给过滤字段建 payload 索引，否则全扫
Weaviate过滤与向量检索融合（filtered HNSW）—
pgvector可建 B-tree + HNSW，由优化器选择过滤选择性差时可能选错计划，需调参

代码示例

# Milvus：分区（物理隔离，最高效的过滤）
#   按 tenant_id 或 category 分区，查询时只扫一个分区
client.create_partition("docs", "tenant_a")
results = client.search(
    collection_name="docs",
    data=[query_vec],
    partition_names=["tenant_a"],     # 物理分区：直接跳过其他分区
    limit=10)

# Milvus：表达式过滤（逻辑过滤）
results = client.search(
    collection_name="docs",
    data=[query_vec],
    filter='category == "tech" and year >= 2024',
    limit=10)
#   注意：Milvus 会根据过滤选择性自动选 pre/post，
#   但极端场景建议显式用 partition。

# Qdrant：payload 索引（关键！不给过滤字段建索引就是全表扫）
client.create_payload_index("docs", field_name="category",
                            field_schema=models.KeywordSchemaType.KEYWORD)
client.search("docs", query_vector=vec,
              query_filter=models.Filter(must=[
                  models.FieldCondition(key="category",
                      match=models.MatchValue(value="tech"))]),
              limit=10)

# 评估过滤检索质量：必须测「过滤条件下的召回率」
#   recall@K = |ANN结果 ∩ 真实TopK| / K
#   在有过滤和无过滤两种场景下都要测！
#   常见坑：无过滤 recall@10 = 0.99，加上过滤掉到 0.6
  • 一定要测「带过滤的召回率」：只在无过滤场景测 recall 是最大的测试盲区。加上过滤后掉到 0.6 是家常便饭。
  • 高选择性过滤用物理分区：如多租户按 tenant 分区，查询时直接跳过其他分区，比表达式过滤快一个量级。
  • 给过滤字段建索引：Qdrant 的 payload index、Milvus 的标量索引，没建索引的过滤等于全表扫描。
  • Post-filter 的 top-K 要放大：如果过滤条件命中 10%，要取 top-K×10 才能保证够 K 条。但放大倍数越大越慢，且极端情况下仍不够。
  • 数值范围过滤比等值过滤更难：price > 100 这类无法用倒排精确命中，通常要扫描或建范围索引。
  • 混合检索（向量 + 关键词）是另一个维度：这里说的过滤是结构化属性（类别、时间、租户），不是 BM25 关键词。两者可以叠加。
为什么加了过滤条件后检索结果变少了（甚至空）？

典型的 Post-filter 召回陷阱。流程是「先用 ANN 找 top-100 个最近邻，再在这 100 个里按条件过滤」——如果你的过滤条件只命中全库的 1%（比如某个冷门类别），那么 top-100 里平均只有 1 条符合条件，甚至一条都没有。而真实符合条件的向量可能在第 5000 名，ANN 根本没捞到它。解法三种：① 改用 Pre-filter——先按条件把候选集缩小（1% 的话候选就很少了），再在候选集里检索，此时哪怕暴力算也不贵；② 用物理分区——把类别/租户做成独立分区，查询时只进一个分区，这是最彻底也最快的方案；③ 用过滤感知索引（Qdrant 的 payload-index HNSW、Milvus 的分区）——索引内部就按属性组织了，图遍历时只走符合条件的节点。工程上的判断标准是选择性：命中率低于 5% 就必须用 Pre-filter 或分区，Post-filter 不可接受。

多租户场景怎么做过滤最合理？

优先级：① 物理分区（partition / collection per tenant）——如果租户数不多（几十到几百）且数据量都较大，直接一个租户一个分区/集合，查询时指定分区，性能最好、隔离最彻底；② partition key（Milvus 的 partition key 功能）——租户多时让系统自动按 key 分到不同分区，你查询时带上 tenant_id 即可，兼顾了隔离和运维成本；③ 表达式过滤——租户极多（上万）且每个数据量小（几百条）时才用，因为分区本身有元数据开销，太多分区反而拖慢。关键权衡是「分区数 vs 每分区数据量」：分区太多（>几千）会让索引碎片化、内存开销大；分区内数据太少（<1000 条）则 HNSW 的图结构质量下降、召回变差。另外别忘了安全性——物理分区天然防跨租户泄漏，表达式过滤则依赖每次查询都正确带上条件，出错成本高得多。

过滤和向量检索的执行顺序能手动控制吗？

看产品。Milvus 会基于过滤的选择性自动选择策略（有迭代式过滤：先小范围 ANN、不够就扩大范围重来），你也可以显式用 partition_names 强制走分区；Qdrant 是过滤感知的 HNSW——遍历图时直接跳过不满足 payload 条件的节点，前提是你给该字段建了 payload index；Weaviate 类似，把过滤融进了 HNSW 遍历；pgvector 则由查询优化器决定（是先走 HNSW 索引还是先走 B-tree），有时会选错，需要靠 SET enable_seqscan 或调整 hnsw.ef_search 来引导。实践建议：先用产品默认策略，然后测「带过滤的召回率」；如果不达标，再按上面的顺序（分区 → 建字段索引 → 换产品）逐级优化。

真实查询从来不是「纯向量」

教科书里的 ANN 检索是「在全库里找最近的 k 个点」。但真实业务永远带着条件：

  • 只在这一个租户的文档里搜
  • 只要最近三个月的内容
  • 排除已下线的商品
  • 限定某个权限范围内可见的数据

于是问题变成了：既要元数据条件命中，又要向量距离最近。这就是所谓的过滤检索（filtered search），也是工业界最常踩坑的地方。

先筛再搜 vs 先搜再筛：各自的失效场景正好相反

决定的关键是「选择性」

所谓选择性（selectivity），就是过滤条件命中了多大比例的数据。它是选择策略的第一依据。

选择性例子命中比例推荐做法
低（条件宽松）status = published九成以上Post-filter 基本够用，只有少量候选被筛掉
中某个分类、某个时间段百分之几到几十两种都勉强，重点调到能够 visiting oversampling 的程度
高（条件很窄）tenant_id = X 且 doc_id in [...]千分之一以下必须用分区/分片预先隔离，别指望动态过滤

最常见也最要命的场景是「多租户」：每个查询只在一个租户的数据里搜，条件是 tenant_id = ?。这个条件选择性极高（一个租户可能只占总量的百分之几甚至更少）。如果还把它当作普通过滤字段，无论 pre 还是 post 都会很难受：

  • 用 pre-filter：图索引里绝大多数邻接点不属于这个租户，搜索会在图上「四处碰壁」，很快退化成扫描。
  • 用 post-filter：ANN 找到的最近邻大多是别的租户的，白找一堆再丢掉。

正解是把隔离上移一层：按租户做分区/namespace/collection，让每次检索的「数据世界」从一开始就是对的。这不是偷懒，而是把「必选条件」变成「选址条件」。

一个更稳的中间路线：一边搜一边筛

既然两种极端都有问题，工程上出现的常见折中是：在搜索过程中增量地做过滤检查。

循环式 filtered ANN（思路示意） budget = k * 10 // 过采样：多取一些候选 visited, results = [], [] while visited < budget and 还没收敛: 在图/倒排上继续走一小步，拿到一小批候选 用 metadata 条件检查这批候选 合格的放进 results if len(results) >= k and 这一轮已足够稳定: break 最后在 results 里取距离最近的 k 条 要点： ① 搜索过程中持续计数「已经找到多少合格候选」 ② 因为知道可能会被过滤掉一部分，就主动多走一些路（过采样） ③ 这样既保持了索引的可行走性，又不会像纯 post-filter 那样回来不够 k

过采样因子（oversampling）怎么定：粗略地可以按预计命中比例的倒数来给。如果条件大约只命中 10 percent，那就多取约 10 倍的候选。但它是有上限的 —— 当选择性太低（千分之一）时，靠过采样已经毫无经济性可言，仍然应该走分区。

工程落地清单

  1. 把「必带的强过滤条件」做成分区键，而不是运行时过滤字段。多租户、业务线、数据类型都适用。
  2. 给常用过滤字段建立额外的 metadata 索引（各向量库叫法不同：payload index / attribute index / scalar index）。没有它，pre-filter 就是全表扫。
  3. 明确写入 queries 时先估算命中比例。可以在写入侧维护简单的统计，帮助运行时做出选择。
  4. 始终做「兜底」：当过滤后结果不足 k 时，是放宽 ANN 精度继续找，还是接受更少的结果，要有明确策略而不是默默返回几条。
  5. 把「带过滤」和「不带过滤」的延迟分别压测。很多团队只测了裸向量查询，上线后真实查询带着过滤，性能差十倍才发现。

深入自检

为什么 pre-filter 会让 HNSW 图失效？

HNSW 依赖图的可达性：从一个入口点沿边走到更近的节点。预过滤后，大量节点被排除，许多边指向的节点不可用，图的连通性被破坏 —— 你原本能顺着走到优质近邻的路径断了，算法只能在剩下的残缺结构里乱转，效率骤降。实践中往往会退化成「把候选集全量 linearly 扫一遍」。

post-filter 返回不足 k，能不能简单地再取一批？

可以，但要小心成本失控。常见做法是把第一批搜索的搜索范围（ef）扩大，或者回到上一层多取一些候选再筛。更好的办法是在搜索过程中就计入过滤（即前面提到的循环式/单阶段方案），避免「先找到一堆再全部丢掉」这种明显的浪费。

时间范围过滤特别常见，有特别的处理吗？

有。时间往往是连续且递减访问的：最近的查询得多，历史数据访问少。常见做法是按时间段分片（例如按月/按周一个分区），查询时只命中涉及的那几个分片；再叠加上「冷热分离」 —— 热数据放内存与高性能存储，冷的压缩归档。这样既天然完成了过滤，也顺便优化了成本。

关系数据库里的部分索引能不能用在这里？

可以，而且是很多场景的性价比之选。如果数据量在千万级以内、延迟要求在几十毫秒级，带向量扩展的关系库 + 针对高选择性条件建立的部分索引往往就够了。它的好处是过滤与业务查询可以在同一个事务、同一套 SQL 里完成，运维复杂度低得多 —— 缺点是规模继续增长时可扩展性不如专用向量库。
