🎯 一句话本质

mmap = 在你的虚拟地址空间里「圈一块地」，并把这块地和某个东西绑定起来。
绑定的可以是磁盘上的文件（文件映射），也可以是纯内存（匿名映射）。
绑定之后，你访问这块地就像访问普通数组一样——用指针读写，不用 read/write。

🏠 生活类比：给房间贴一张「投影地图」

mmap 就是「贴」这个动作：把外部对象贴进地址空间，之后用指针直接读写

为什么叫「内存映射」？

映射的意思是：建立虚拟地址区间 ↔ 某个后端对象的对应关系。建立之后：

  • 读 ptr[0] → 内核自动把对应内容搬进物理内存 → 你拿到数据
  • 改 ptr[0] → 视 flags 决定是写回文件还是仅本进程可见
  • 不用了 munmap → 拆掉这块地
所以 mmap 不是「分配内存」的唯一含义——它本质是建立映射关系。只是当后端是「空地」时，看起来就像在分配内存，这就是为什么你在内存分配话题里总看到它。

🧱 mmap 到底做了什么？

最关键的一点：mmap 是「预约」，不是「入住」。

mmap 是预约，缺页中断才是入住

内核里的三个结构

结构作用
vm_area_struct（VMA）一段连续的虚拟地址区间，记录起止、权限（rwx）、是文件映射还是匿名、后端文件+偏移
页表项 PTE初始为空；缺页后填入「虚拟页 → 物理页帧」的映射
address_space / page cache文件映射的后端：磁盘内容在内存里的缓存页
所以「mmap 分配了内存」这句话只对了一半：它分配的是虚拟地址区间（一段门牌号），物理内存要等你真正去读写时才一页一页兑现。

munmap：拆掉这块地

munmap(addr, length);   // 解除映射，释放这段虚拟地址空间与对应物理页

这也是为什么 free() 大块内存能立刻把内存还给操作系统——因为大块是 mmap 来的，free 直接 munmap；而小块在堆里，只能留在分配器手里慢慢复用。

🧪 动手：mmap 一块，然后访问它

点「mmap 一块」创建映射（虚线 = 只预约），再点「访问」触发缺页把它变成真实物理页（实线绿色）。

进程虚拟地址空间中的映射区
映射块：0 ｜ 已兑现物理页：0 页
提示：mmap 返回后物理页是 0 —— 这就是「预约 vs 入住」。
匿名映射（最像「分配内存」） 
void *p = mmap(NULL, 4096*4,
    PROT_READ|PROT_WRITE,
    MAP_PRIVATE|MAP_ANONYMOUS,
    -1, 0);       // fd = -1，无文件
p[0] = 1;         // 此时才分配物理页
munmap(p, 4096*4);
文件映射（把文件贴进来） 
int fd = open("data.bin", O_RDONLY);
void *p = mmap(NULL, len,
    PROT_READ, MAP_PRIVATE,
    fd, 0);
printf("%c", ((char*)p)[0]);  // 直接用指针读！
munmap(p, len);
匿名映射的本质：后端不是文件，而是「一堆零页」。内核在你写入时会分配一个清零的物理页，所以匿名 mmap 拿到的内存一定是全 0（这也是 calloc 大块时敢不 memset 的原因）。

📂 两种 mmap：文件映射 vs 匿名映射

同一个 mmap，后端不同 → 用途完全不同
类型flags后端典型用途
私有文件映射MAP_PRIVATE文件 page cache加载 so、读大文件、只读数据共享
共享文件映射MAP_SHARED文件 page cache多进程共享、修改要落盘（需 msync）
私有匿名映射MAP_PRIVATE|MAP_ANONYMOUS零页malloc 大块、线程栈、大缓冲
共享匿名映射MAP_SHARED|MAP_ANONYMOUS共享物理页进程间共享内存

💰 为什么讲内存分配总提到 mmap？

因为 malloc 有一条「大块走 mmap」的分界线。拖动滑块看看不同大小的分配走哪条路。

1 KB （glibc 默认阈值 M_MMAP_THRESHOLD = 128 KB）
这就是「内存分配里总看到 mmap」的原因：大块内存就是它给的
为什么大块要单独 mmap？
  • 避免在大堆里留下巨大空洞（外部碎片）
  • 释放时能整块归还给操作系统，而不是卡在堆顶
  • 独立 VMA，权限/生命周期清楚
为什么小块不 mmap？
  • 每次 mmap 都要建 VMA、至少占 1 页（4KB），17 字节也要给 4096
  • munmap 有 syscall 与 TLB 刷新开销
  • 小块高频分配，走堆内空闲链表快得多

除了 malloc，还有谁在用 mmap？

场景怎么用 mmap
加载动态库（.so）把库文件的 text/data 段映射进进程，多进程共享同一份物理页，省内存
创建线程pthread_create 用 mmap 给新线程分配栈空间
进程间共享内存MAP_SHARED 映射同一文件或匿名共享区
读写大文件替代 read/write，减少一次数据拷贝（下一节）
Java / Go 的堆运行时向 OS 要内存，底层就是 mmap（Go 的 sysAlloc）
显存 / 设备内存把设备寄存器或显存映射进用户空间直接访问

⚡ mmap 读文件 vs read()：差在哪

这是 mmap 最经典的优势场景。点按钮看两条路径的数据搬运次数。

mmap 省掉的是「内核缓冲区 → 用户缓冲区」这一次 CPU 拷贝
mmap 适合的场景
  • 大文件、多次重复访问同一批页
  • 随机访问（按需只把碰到的页读进来）
  • 多进程共享同一份只读数据（如动态库）
mmap 不一定更快的情况
  • 小文件、顺序只读一次：缺页中断 + TLB 刷新可能比一次 read 更贵
  • 每次缺页都有内核开销，可用 MAP_POPULATE 预读
  • 32 位进程地址空间紧张，映射大文件容易放不下
// 用 mmap 读文件
int fd = open("big.bin", O_RDONLY);
struct stat st; fstat(fd, &st);
char *p = mmap(NULL, st.st_size, PROT_READ, MAP_PRIVATE, fd, 0);
// 之后就像操作内存一样操作文件内容
printf("%c\n", p[1000]);
munmap(p, st.st_size);

🛠️ 函数签名与参数

#include <sys/mman.h>

void *mmap(void *addr,        // 建议起始地址，通常填 NULL 让内核选
           size_t length,     // 映射长度（会向上取整到页大小 4KB 的倍数）
           int prot,          // 权限：PROT_READ / PROT_WRITE / PROT_EXEC / PROT_NONE
           int flags,         // 见下表
           int fd,            // 文件描述符；匿名映射填 -1
           off_t offset);     // 文件内偏移，必须是页大小的整数倍

int munmap(void *addr, size_t length);
int msync(void *addr, size_t len, int flags);   // 把修改刷回文件
int mprotect(void *addr, size_t len, int prot); // 改权限
flags含义
MAP_PRIVATE私有：写入触发写时复制（COW），只本进程可见，不写回文件
MAP_SHARED共享：写入对其他进程可见，文件映射会写回磁盘
MAP_ANONYMOUS匿名：不关联文件（fd 填 -1），内容初始为 0
MAP_FIXED必须映射到指定地址（危险，可能覆盖已有映射）
MAP_POPULATE立刻预读页表，避免后续缺页抖动（用空间换时间）
MAP_HUGETLB使用大页（2MB/1GB），减少 TLB miss
MAP_NORESERVE不预留 swap 空间

⚠️ 常见坑

坑说明
SIGBUS 崩溃映射了文件，但文件被别的进程截断了，再去访问超出范围的页 → 直接 SIGBUS（不是段错误）
offset 必须页对齐offset 必须是 4096 的整数倍，否则 EINVAL
length 会向上取整映射 1 字节也占一页，别用它分配大量小对象
MAP_SHARED 改了不落盘？内核延迟写回，要确保持久化得调 msync()（类似 fsync）
忘记 munmap地址空间泄漏；64 位下不炸，但 VMA 数量有上限（max_map_count）
映射长度超过文件访问超出文件末尾的页（最后一页之内一般安全，跨页则 SIGBUS）

✅ 一句话带走

mmap 不是「分配内存」，而是「建立映射」——在你的虚拟地址空间里圈一块地，把文件或空地贴上去。
mmap 返回时只是预约（建 VMA），真正分配物理内存要等你首次访问触发缺页。
内存分配里总看到它，是因为 malloc 超过 128KB 就走 mmap，这样 free 能立刻把内存还给操作系统。
