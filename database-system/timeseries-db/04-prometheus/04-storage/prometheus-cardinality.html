01基数到底怎么算

\n
# 一个 metric 的序列数 = 所有 label 取值数的乘积\n#   series = |label1| * |label2| * ... * |labelN|\n\n# 例：http_requests_total{method, status, route, user_id}\n#   method  : GET/POST/PUT/DELETE/PATCH      → 5\n#   status  : 200/301/400/404/500/502/503    → 7\n#   route   : /api/a, /api/b, ...            → 20\n#   user_id : 每个用户一个值                 → 100000\n#   series  = 5 * 7 * 20 * 100000 = 70,000,000   ← 爆炸\n\n# 去掉 user_id 之后：5 * 7 * 20 = 700   ← 正常\n# 结论：基数由「取值数最多」的那个 label 主导，\n#   其他 label 只有几个取值，乘上去影响很小
label 类型典型取值数能不能做 label
method / status / 状态码5 ~ 20可以
service / instance / job几十 ~ 几百可以
route（模板化路径）几十 ~ 几百可以（必须模板化）
URL 原始路径（含 id）无限绝对不行
user_id / order_id十万 ~ 亿绝对不行
trace_id / request_id无限绝对不行
错误 message 全文无限绝对不行
要点：判断标准一句话：取值集合是否会随时间无上限增长。会增长的就不能做 label，只能进日志或追踪系统。
\n
label 取值数是相乘的：一个高基数 label 就能放大几千倍

02多少算多：数量级与资源占用

\n
活跃序列数状态典型内存说明
< 10 万健康几百 MB ~ 1 GB单实例轻松
10 万 ~ 100 万要关注数 GB需要规划与治理
100 万 ~ 1000 万高负载十 GB 级要考虑拆分或远程存储
> 1000 万通常已出问题数十 GB 级先查是不是有高基数 label
# 一个粗略的内存估算（head block，仅作量级参考）\n#   每条活跃序列大致几 KB 级开销（索引 + 最新样本 + chunk 元数据）\n#   100 万条活跃序列 → 数 GB 内存，且随 chunk 保留期增加\n# 所以「内存爆了」的第一反应应该是：查序列数，而不是加机器
    \n
  • 抓取间隔不改变基数：它改变的是样本数量（磁盘），不是序列数（内存）。
    • \n
  • histogram 的 bucket 也算基数：一个 histogram 有 N 个 bucket 就是 N 条序列（外加 _sum/_count）。bucket 越多，序列数越多。
    • \n
  • target 频繁上下线也会涨序列：每次 instance 变化都产生新序列；K8s 环境下 Pod 名变动要特别小心。
    • \n
  • 保留期不影响内存：只影响磁盘；内存主要由「活跃序列数」决定。
    • \n

03排查：三条命令定位元凶

\n
# 1) 哪个 metric 的序列最多（Top 10）\ntopk(10, count by (__name__)({__name__=~\'.+\'}))\n\n# 2) 哪个 label 的取值最多（把 __name__ 换成上一步查出来的 metric）\ntopk(10, count by (route)(http_requests_total))\n\n# 3) 总序列数与增长趋势\nprometheus_tsdb_head_series           # 当前 head block 的序列数\nprometheus_tsdb_head_series_created_total  # 累计创建过的序列数\n#   判读：created_total 远大于 head_series → 有大量序列被反复创建（ churn ）\n\n# 4) 抓取与存储健康\nprometheus_target_interval_length_seconds\nprometheus_tsdb_head_chunks\nprometheus_tsdb_head_chunks_created_total\n\n# 5) 离线分析（推荐，能看到最占地方的 label）\npromtool tsdb analyze /path/to/data\n# 输出里会直接列出：最多的序列、最多的 label 对、churn 比例
现象第一怀疑确认命令处理
内存持续涨序列数在涨head_series查 topk 找元凶 label

04五种降基数手段

\n
    \n
  1. 删掉高基数 label：把 user_id / URL 原路径这类字段从 label 里移除，需要下钻分析的放日志。
    2. \n
  2. 路径模板化：/user/123 → /user/{id}，这是服务端最常见的修复点。
    3. \n
  3. 用记录规则预聚合：record: svc:requests:rate5m 把细粒度聚合掉，只留需要的维度。
    4. \n
  4. 减少 histogram bucket：默认 bucket 数量不少，按实际 SLO 精简到 5~8 个。
    5. \n
  5. 按职责拆分实例：不同团队/环境分开部署，避免一个实例的基数被无关指标拖垮。
    6. \n
问：能不能先加内存顶过去？

能顶一时，但基数通常是乘法增长：加一次 label 就可能翻几十倍。在加机器之前，先用 topk 找到那个取值最多的 label，往往删一个字段就解决。

问：为什么 label 不能存用户 ID，日志就可以？

因为 Prometheus 的索引是「序列 → 样本」，每个 label 组合都是一条独立序列，要常驻内存；日志是按行存的，写进去就落盘，成本模型完全不同。

问：降基数和降采样是一回事吗？

不是。降基数是减少序列条数（省内存），降采样是减少样本密度（省磁盘）。内存爆了要降基数，磁盘爆了才考虑降采样。
