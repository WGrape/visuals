1总体流程一览

用户拍照上传作文 → 服务端拿到图片 → OCR 拿到"行级坐标 + 文字" → 切句/分句 → 候选句送 LLM 评语 + 打分 → 把"亮点句"的原始坐标在原图上画绿线、写序号、写"优" → 前端展示右栏评分卡。整个过程 1.5 ~ 4 秒完成端到端体验。

① 用户上传图片→ ② 鉴权 + 落 OSS→ ③ OCR + 版面分析→ ④ 行/句切分→ ⑤ 候选句召回→ ⑥ LLM 评语+打分→ ⑦ 分数合成→ ⑧ 坐标回写图→ ⑨ 推送 + 展示

2系统架构与分工

5 个角色、4 个核心服务、1 个异步管道。客户端只负责拍+展示；服务端负责 OCR、AI 评语、坐标回写与持久化。

为什么用消息队列而不是同步链路？

OCR（~500ms）+ LLM（~1.5~3s）+ 标注（~200ms）三者串行同步在网络抖或 LLM 慢时会卡到 5~6 秒，HTTP 容易超时。改为「BFF 接收 → 入 Kafka → 各 Worker 订阅 → 完成后写库 + 推 SSE/WebSocket」后，客户端体验稳定在 2~3 秒，且后端可以独立扩缩容。

3图片上传与切图策略

「谁切图、切几段、怎么切」是这份方案最容易被反复追问的细节。一次说清。

3.1 客户端预处理（必做）

  • EXIF 旋转矫正：手机拍照方向可能 0/90/180/270，canvas 旋转归位。
  • 长边压缩到 2048px：原图 4MB、4032×3024 → 压缩到 150~300KB、2048 长边。OCR 实际只需要这个精度，再大反而拖慢。
  • JPEG 质量 85：折中清晰度与体积，OCR 准确率几乎不受影响。

3.2 谁切图：客户端粗切 + 服务端精切（推荐）

「切图」在本方案有两层含义：

  • 客户端粗切 不做像素切分，仅做"整图压缩 + 分块上传"（HTTP/2 多流或 multipart 并发）—— 这是网络层面的切，目的是断点续传和并行提速。
  • 服务端精切 OCR 服务拿到完整图后，由"版面分析"模型自动识别"这是一张作文纸"并切出"文字行 / 段落 / 格子"—— 这是语义层面的切，目的是拿到每行/每段的精确坐标。
为什么不让客户端按像素切？

客户端不知道"哪些字属于一句话"，按固定高度切成几条横带会让句子跨带、坐标错位；用户拍的歪一点、斜一点就更乱。把"理解版面"的事交给专门训练的版面模型才是稳的。

4OCR + 版面分析：识别文字 + 拿到坐标

这一步是整套方案最依赖模型的一步，也是出错最容易肉眼难发现的一步。

📐 版面分析（Layout Analysis）

模型：PaddleOCR-PP-Structure / 阿里云"通用文字识别-表格/文档" / 腾讯云"通用票据/教育场景 OCR"。
输出：「这是一张作文纸」「有 N 行手写文字」「每行的 [x, y, w, h] 包围盒」。

🔤 文字识别（Text Recognition）

模型：PaddleOCR-PP-OCRv4 / 云 API。
输入：每行的图像子块。
输出：每个字的字符 + 位置（[x, y, w, h]，相对原图坐标）。

4.1 标准 OCR 输出结构

// OCR 服务输出（写入 DB ocr_result 表）
{
  "task_id": "t_abc123",
  "image_size": { "w": 2048, "h": 1536 },
  "lines": [
    {
      "line_id": 1,
      "bbox": [ 40, 42, 1015, 24 ],  // [x1, y1, x2, y2] 相对原图
      "char_boxes": [
        { "char": "梦", "bbox": [40, 42, 48, 66] },
        { "char": "想", "bbox": [92, 42, 48, 66] },
        ...
      ],
      "text": "在无限的宇宙间，万物皆有其源"
    },
    ...
  ]
}

关键：bbox 全部相对原图坐标，前端用 viewBox 缩放即可任意倍率展示，不会因 CSS 缩放丢失精度。

4.2 核心风险：手写体识别错误

手写体错误是 AI 作文批改的第一杀手

学生的字千奇百怪：「的/得/地」混用、连笔、行倾斜、字与字粘连——OCR 直接吃掉 30% 效果。三个对策：

  1. 专用手写模型：必须用"中文手写体"专用模型（PaddleOCR 手写、阿里云"教育-手写体"），不能用通用印刷体模型。
  2. 置信度过滤：每个字带 conf，conf < 0.6 的字标红 / 允许用户点击改字，再让 LLM 改写。
  3. 行级别二次校对：把整行文本送给一个轻量 LLM（GPT-4o-mini / Qwen2.5-7B）做"基于上下文的纠错"，专治 OCR 把"梦想"识别成"木相"这类同音字错误。

5行/段切分与"格子"还原

OCR 给了「行」，我们还需要「句子」。中英文分句逻辑不同，必须显式处理。

5.1 行 → 段

OCR 输出按「物理行」组织，但作文中段首会缩进 2 字、段间会空行。规则：

  • 行首字符是"开头标点（如「，"）→ 接上行
  • 行末是「，」/「；」/「——」 → 接下行
  • 行间 y 距离 > 普通行距 × 2.5 → 视为空行/段分隔
  • 行首 2 个 char 距离与正文不一致 → 视为段首缩进

5.2 段 → 句（中文分句器）

用 jieba + 自定义正则。句末标点集：。！？；…"」』；引号内不切；省略号"……"不切。

import jieba

def split_sentences(text: str) -> list[str]:
    # 1) 保护引号
    text = protect_quotes(text)
    # 2) 按强标点切
    raw = re.split(r'([。！？；…"」』])', text)
    # 3) 拼回标点
    sents = [raw[i] + raw[i+1] for i in range(0, len(raw)-1, 2)]
    return [s for s in sents if s.strip()]

5.3 句 → 字符坐标回填

对每句，按字符在原行中的 char_boxes 拼出整句的 [x1, y1, x2, y2]，作为后续「划线」和"亮点标记"的精确锚点。

6句子抽取与亮点候选

全篇通常 400~800 字，不可能把整篇丢给 LLM 选"亮点句"——既贵又慢。工程上要做"候选召回"。

① 长度过滤

丢掉 < 8 字、> 60 字的句子（太短是短语、过长常是 OCR 粘连）。

② 修辞启发式

匹配「像/似/如同/仿佛/是/犹如/宛如」「引用书名号《》」等强信号，作为亮点的高召回候选。

③ Embedding 排序

对候选句算 embedding，与「优美/亮点/好句」的正例句向量算相似度，Top-N 进 LLM。

// 候选召回（示例：每篇 25~40 句 → 筛到 6~8 句送 LLM）
const candidates = sentences.filter(s =>
  s.length >= 8 && s.length <= 60                    // 长度
  && /[，。！？]/.test(s)                         // 完整句子
  && (/像|似|如同|仿佛|犹如|宛如|好比/.test(s)
     || /《[^》]+》/.test(s)
     || /——|因而|于是/.test(s))                 // 修辞信号
).slice(0, 8);

7LLM 评语与打分（核心 AI 环节）

把"全文字数 + 候选句 + 评分维度定义"塞进 Prompt，让 LLM 用 JSON 结构化输出 一把吐出总评 + 维度分数 + 亮点引用。

7.1 Prompt（截选）

// messages → LLM
{
  "system": "你是一位资深语文老师，请按以下 JSON 格式批改作文。不要输出 JSON 之外的任何内容。",
  "user": `
【评分维度】（每项 A/B+/B/C+/C/D 之一）
  1. 中心突出：是否围绕主题

  3. 语言流畅：表达是否通顺、有文采
  4. 思想健康：价值观是否正面
  5. 结构严谨：层次、过渡、首尾呼应
  6. 书写规范：字迹工整、标点正确

【输出 JSON Schema】

7.2 关键技术点

  • JSON Mode / Tool Use：用 response_format=json_object 或 tools=[{"name": "submit_review"}] 强约束输出，避免 LLM 输出散文。
  • Few-shot：在 system 里塞 1~2 个示范 JSON 模板，提升格式稳定性。
  • 模型选择：默认 gpt-4o-mini / qwen2.5-72b（中文好 + 便宜）；高峰/重点用户切 claude-3.5-sonnet / gpt-4o。
  • Temperature 0.3：批改需要稳定，不要太多"灵感"。
  • 超时与重试：单次超时 8s，失败 1 次重试，再失败走降级（用模板评语 + 仅 OCR 文本 + 用户自助评分）。
  • Prompt 缓存：system 部分长期不变，开 prompt cache 省 60% 成本。
如何确保 LLM 选出的 sid 一定在候选里？

LLM 偶尔会"幻觉"出一个不在候选里的 sid。工程上：解析后必须 assert sid ∈ candidates.sids，不在则丢弃该 highlight 并 prompt 一次修正（让 LLM 重新输出）。这步校验比想象的更重要。

8分数合成与等级

LLM 给的是字母等级（A/B+/B/C+/C/D），要映射成 0~100 的分数 + 最终"优/良/中/差"四级。

等级AB+BC+CD
百分制90~10082~8975~8168~7460~67< 60
# 分数合成：六个维度加权，权重可按学段配置（初中/高中不同）
def final_score(scores, weight='junior_high'):
    w = { 'center': 0.20, 'material': 0.15, 'language': 0.25,
          'thought': 0.10, 'structure': 0.15, 'writing': 0.15 }[weight]
    pct = { 'A': 95, 'B+': 85, 'B': 78, 'C+': 71, 'C': 63, 'D': 50 }
    raw = sum(pct[v] * w[k] for k, v in scores.items())
    grade = '优' if raw >= 85 else '良' if raw >= 75 else '中' if raw >= 60 else '差'
    return round(raw, 1), grade

9坐标回写：在原图上划线 / 写序号 / 写"优"

这是用户最直观看到的一步。两条路线：前端 SVG 实时叠加 vs 后端预合成图片，建议两者都做——前端负责可交互，后端负责可分享。

9.1 路线 A：前端 SVG 实时叠加（默认）

前端拿到 image_url + highlight_boxes[] + grade 后，用一个 <svg viewBox="0 0 W H"> 覆盖在 <img> 上：

<!-- 关键：viewBox 用原图分辨率，CSS 任意缩放 -->
<div class="essay-canvas">
  <img src="https://cdn/.../orig.jpg" />
  <svg viewBox="0 0 2048 1536" class="overlay">
    <for-each highlight>
      <line x1={x1} y1={y2+4} x2={x2} y2={y2+4}
            stroke="#22c55e" stroke-width=5 />
      <circle cx={x1-12} cy={y1-8} r=12 fill="#22c55e" />
      <text x={x1-12} y={y1-4} text-anchor="middle" fill="#fff">{idx}</text>
    </for>
    <image href={`seal-${grade}.png`} x={1900} y={40} width={100} />
  </svg>
</div>

优点：可点击（点绿色序号弹句评）、可缩放、零图片资源。
缺点：截图分享时要把 SVG 一起 html2canvas 进去。

9.2 路线 B：后端预合成图片（用于分享/收藏）

用 Pillow 在服务端把"原图 + 划线 + 序号 + 优"一次性合成为一张 PNG/JPEG，存 OSS。前端 html2canvas 兜底，但更稳。

from PIL import Image, ImageDraw, ImageFont

def annotate(orig_path, highlights, grade, out_path):
    img = Image.open(orig_path).convert('RGB')
    draw = ImageDraw.Draw(img)
    for i, hb in enumerate(highlights, start=1):
        x1, y1, x2, y2 = hb['bbox']
        draw.line([(x1, y2+4), (x2, y2+4)], fill=(34,197,94), width=5)
        draw.ellipse([(x1-22, y1-22), (x1-2, y1-2)], fill=(34,197,94))
        draw.text((x1-17, y1-19), str(i), fill='white', font=font_small)
    # 右上角贴预制"优"印章
    seal = Image.open(f'asset/seal-{grade}.png').convert('RGBA')
    img.paste(seal, (img.width - 140, 40), seal)
    img.save(out_path, 'JPEG', quality=88)
坐标转换的不变式

无论走 A 还是 B，所有坐标必须基于「原图分辨率」（如 2048×1536）这一不变基准。SVG 用 viewBox、Pillow 用像素、DOM 用百分比——三者都能映射回原图坐标，这是「缩放不糊 / 跨端一致」的根本保障。

🛡️ 失败与重试

OCR 失败 → 重试 2 次 → 标记 partial result；LLM 失败 → 重试 1 次（换 prompt）→ 走降级（用模板总评 + 跳过划线）。

⏱️ SLA 监控

每阶段埋点上报耗时：OCR P95 < 800ms、LLM P95 < 3s、端到端 P95 < 4s。超阈值自动切备用模型/降级。

为什么把 OCR 结果也存 ES？

老师/家长后续要"按关键字找作文"、"按学生查历史"，ES 既能做全文检索也能按 sid 反查坐标。MySQL 是权威源，ES 是查询副本，通过 Binlog 同步。

14关键风险与对策

🔴 OCR 错字导致评语失真

对策：① 用中文手写专用模型；② 置信度低于阈值字符标红允许用户改；③ 整行二次 LLM 纠错；④ 把 OCR 文本 + 候选亮点句给 LLM 时附上"原文可能有错字，结合上下文理解"提示。

🔴 LLM 输出 sid 不在候选中

对策：解析后断言 sid ∈ 候选集合；不通过则丢弃并 prompt 一次让 LLM 重选；两次失败则改用基于 embedding 相似度最高的 N 个候选。

🟠 划线坐标与渲染端不一致

对策：所有坐标统一以"原图分辨率"为基准，SVG viewBox、Pillow 像素、CSS 百分比三种坐标显式转换；提供 render_visual_check 单测（合成图后抽样 5 篇人眼对比）。

🟠 学生上传非作文 / 试卷

对策：① LLM 评语里要求先判断"是否为作文"，不是则只返回提示；② BFF 调用前用轻量分类器（图像分类 + 文本长度阈值）先过滤；③ 错误码 1003 引导重传。

🟠 LLM 成本失控

对策：① 系统 Prompt + 维度定义走 prompt cache（降 ~60%）；② 默认 mini 模型，按学段/用户等级升级；③ 每用户每日限 N 次；④ 入参压缩：候选句不超过 8 条、全文不超 1200 字（超长自动截取）。

🟢 隐私 / 未成年人数据

对策：① 端到端 HTTPS + OSS 私有 bucket + CDN 鉴权签名；② 评语与图分离存储，定期清理已注销用户数据；③ 内容过滤（敏感词、政治安全）前置；④ 不收集非必要字段；⑤ 完整审计日志可追溯。
