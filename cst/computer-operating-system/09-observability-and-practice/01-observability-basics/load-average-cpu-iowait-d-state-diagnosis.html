CPU 不高而 load average 很高：运行队列、D 状态与 iowait 怎样判断

用 8 核机器 load=12、CPU=30% 的现场，沿任务状态、磁盘延迟和容器限额定位瓶颈。

load average 不是 CPU 百分比

Linux 的 load average 通常统计一段时间内可运行任务与不可中断睡眠任务的平均数量，并给出约 1、5、15 分钟的指数平滑值。可运行任务可能正在 CPU 上执行，也可能排队等 CPU；不可中断睡眠常见于等待某些内核 I/O 等路径。CPU 使用率则描述 CPU 时间花在 user、system、idle、iowait 等状态上的比例。两个指标口径不同：8 核机器 load=12、CPU 使用率只有 30%，不能直接断言“CPU 还有 70% 空闲所以没有瓶颈”，也不能直接断言“12/8=150% CPU 使用率”。

先核对观察范围和时间窗。load 是平滑后的整机信号，CPU 百分比可能来自某一秒、某个进程或某个容器；把不同窗口、不同作用域的数放在一起会制造假矛盾。

8 核 load=12 的三种可能

若 8 个核心持续 100% 忙，运行队列还有 4 个任务等 CPU，load 接近 12 的确可能表示 CPU 饱和。若 CPU 总使用率仅 30%，但有很多任务停在 D 状态等慢磁盘或远程文件系统，load 也可能升高，CPU 却大部分时间没有运行应用代码。若宿主机 8 核空闲、容器只有 1 核 CPU 配额，容器内进程可能因 cgroup 节流而排队，容器业务慢但宿主总 CPU 不高。三种情况修复方向完全不同。

具体 load 值还受进程数量、短任务突发、采样间隔和系统实现影响。1 分钟值刚上升而 15 分钟值仍低，表示问题可能新发生；三个值都高，更像持续负载。不能只凭一张截图定因。

iowait 到底代表什么

CPU iowait 是某些统计口径下 CPU 空闲且系统有等待 I/O 的时间比例，不等于“磁盘利用率”，也不等于“应用请求等待磁盘的百分比”。多核系统里某个线程等 I/O，其他线程仍可把 CPU 跑满；iowait 可能很低，但该线程的尾延迟很高。反过来 iowait 高提示要查 I/O 路径，却不能单独说明是哪个设备、哪个进程或哪段远程存储慢。

排障需看设备读写延迟、队列、吞吐和错误，同时看进程的等待状态与调用栈。系统可能在文件系统、块设备、网络存储或内存回收路径停住；只看 iostat 一个平均延迟也可能掩盖尾部故障。

先拆整机再到线程

记录故障窗口里的业务延迟与错误率，再看整机 CPU user/system/idle/iowait、每核分布、load 趋势、运行队列和 D 状态任务数。若 CPU user/system 高，定位热点进程和线程，采样 on-CPU 调用栈；若业务慢但 CPU 低，找阻塞线程、I/O 延迟、锁等待、网络超时或容器节流。`top`、`pidstat`、`vmstat`、`iostat` 等工具提供不同视角，具体字段含义依平台和版本，使用时要核对单位与采样窗口。

对 D 状态线程，可从进程状态、内核调用栈及其打开的文件或挂载点找等待对象。不要因为看见 D 就直接重启数据库：若底层磁盘持续慢，重启只会扩大恢复时间。先定位设备和共享依赖，再决定动作。

容器里的限额陷阱

Kubernetes Pod 设了 CPU limit，例如 1 核，但宿主机有 8 核。应用在高峰需要短时 2 核，cgroup 会对超出额度的运行时间节流；业务 P99 升高、容器限额计数增长，宿主整体 CPU 仍可能很低。此时盲目增加线程数可能让争用更严重。要结合容器 CPU 使用、节流次数/时间、请求并发与线程运行队列分析，并区分 requests 决定调度预留、limits 决定硬限额的角色。

不同 cgroup 版本和监控代理对节流指标的采集口径会变化，不能只看一个“throttled 事件数”绝对值。应在相同负载下调整限额或优化 CPU 工作量，观察业务延迟是否改善。

一个故障时间线

10:00 用户反馈 API 延迟从 80 毫秒升到 2 秒，8 核主机 load 从 2 升到 12，CPU 总使用率从 25% 到 30%。若同时发现 D 状态任务数从 0 升到 10、存储设备 P99 读延迟从 5 毫秒升到 800 毫秒，而 on-CPU 火焰图没有新热点，优先怀疑 I/O 路径；接着核对挂载点、设备错误、存储服务健康和受影响进程。若 D 状态不多，却有容器 CPU 节流明显上升，就走限额方向。一个证据链必须包含业务症状、等待主体和资源异常的同一时间窗口。

将故障期与正常期同样长度的样本对照，比“现在 top 看起来正常”可靠。问题恢复后，平滑的 15 分钟 load 仍可能高一阵，不表示故障仍在发生。

修复后的验收

若确认存储延迟导致等待，修复设备或减少随机 I/O 后，在相同流量下应看到 D 状态与存储尾延迟下降，业务 P99 恢复；若是 CPU 节流，调整限额或减少计算后应看到节流与请求尾延迟同步改善。保留变更前后请求量、缓存命中和依赖状态，避免把流量自然下降误认为修复有效。对偶发事件可加上进程状态、设备延迟和容器节流的联合告警，但不应只凭 load 单指标自动重启。

自检

8 核机器 load average=12、CPU 使用率 30%，是否能直接把 load 当成 150% CPU 使用率？

不能。load 还可能计入不可中断等待任务；应核对时间窗、任务状态、I/O 延迟和容器限额。
