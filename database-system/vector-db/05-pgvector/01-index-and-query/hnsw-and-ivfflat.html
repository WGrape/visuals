①HNSW 参数与 ef_search 默认值陷阱

pgvector 的调参空间比专用库小，但默认值比专用库更危险 —— 尤其是 IVFFlat 的 probes 默认只有 1，等于只查一个桶。

CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE docs (
  id        bigserial PRIMARY KEY,
  tenant_id int,
  content   text,
  emb       vector(1536)
);

-- HNSW：默认 m=16, ef_construction=64
CREATE INDEX docs_emb_hnsw ON docs
  USING hnsw (emb vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);

-- 查询时控制搜索宽度（默认 40）
SET hnsw.ef_search = 100;

SELECT id, content, 1 - (emb <=> $1) AS score
FROM docs
WHERE tenant_id = 42
ORDER BY emb <=> $1
LIMIT 10;
参数默认上限调大代价
m（建索引）16100召回↑、图内存↑索引变大，构建更慢
ef_construction（建索引）641000图质量↑构建时间显著增加
hnsw.ef_search（查询）40（无硬上限）召回↑延迟线性上升
hnsw.ef_search 默认 40 只在你要 LIMIT 较小时够用。要取 top-100 却把 ef_search 留在 40，返回结果会少于 100 条 —— 这是 pgvector 最常见的「结果数不对」原因。经验规则：ef_search ≥ LIMIT。

②IVFFlat：lists 公式与 probes=1 的坑

IVFFlat 的建索引快得多，但两个默认值组合起来会造成「召回惨不忍睹」的假象。

-- lists 的选择（官方建议）
--   rows <= 1M  : lists = rows / 1000
--   rows >  1M  : lists = sqrt(rows)
CREATE INDEX docs_emb_ivf ON docs
  USING ivfflat (emb vector_cosine_ops)
  WITH (lists = 1000);

-- 关键：probes 默认是 1！
SET ivfflat.probes = 20;

SELECT id FROM docs ORDER BY emb <=> $1 LIMIT 10;
数据量lists 建议probes 起手说明
10 万10010官方公式 rows/1000
100 万100020–32官方公式 rows/1000
1000 万316232–64官方公式 sqrt(rows)
probes=1 是 pgvector 最坑的默认值。100 万条数据、lists=1000 时，只探 1 个桶意味着只扫描 0.1% 的数据，召回可能只有 60%。网上大量「pgvector 召回很差」的帖子根因都是这一行没设。

另一个硬性前提：IVFFlat 必须在表里有数据之后再建索引。空表上建 IVFFlat 会得到无意义的聚类中心，后续写入的数据分布与中心严重不匹配。HNSW 没有这个限制。

③建索引的内存与时间预算

这是 pgvector 最容易被低估的一环。HNSW 构建是内存密集 + CPU 密集的操作，默认配置下建 500 万条的 HNSW 可能跑十几个小时甚至 OOM。

-- 建索引期间临时提高内存与并行度（会话级）
SET maintenance_work_mem = '8GB';          -- 默认通常只有 64MB~1GB
SET max_parallel_maintenance_workers = 4;  -- 默认 2

CREATE INDEX CONCURRENTLY docs_emb_hnsw
  USING hnsw (emb vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);
因素影响建议
maintenance_work_mem决定能否一次性建完图；不够会落盘，慢数倍设为预估索引大小的 1–1.5 倍
max_parallel_maintenance_workers并行构建线程数按 CPU 核数给 2–8
ef_construction构建时间近似线性先在 1/10 数据上调好再全量建
CONCURRENTLY不阻塞写入，但更慢且不能与并行构建同时用维护窗口内还是用普通建索引更快
实践建议：先用 10% 的数据建一次索引，量出时间与内存，再线性外推决定全量要不要放维护窗口。直接对全量试，很可能跑到一半 OOM 然后回滚，白等几小时。

④WHERE 过滤导致的召回塌陷

pgvector 的过滤是标准 SQL WHERE，看起来天生优雅，实际存在一个隐蔽的性能陷阱。

HNSW 索引扫描是「沿着图走，边走边判断条件」。如果条件很严（比如只匹配 0.1% 的行），图会走到没有邻居可走也凑不满 K 条，结果数不足甚至为空 —— 这被称为过滤后的召回塌陷。

版本行为对策
< 0.8.0严格 post-filter，结果可能少于 K放宽条件重查，或先过滤再向量排序（放弃索引）
≥ 0.8.0（iterative scan）自动扩大搜索范围直到凑够 KSET hnsw.iterative_scan = relaxed_order;
-- 0.8.0+：让索引扫描在过滤后继续扩展
SET hnsw.iterative_scan = relaxed_order;   -- 或 strict_order
SET hnsw.max_scan_tuples = 40000;          -- 默认 20000，扫描上限

SELECT id FROM docs
WHERE tenant_id = 42 AND created_at > now() - interval '30 days'
ORDER BY emb <=> $1
LIMIT 10;
strict_order 保证按精确距离顺序返回但更慢；relaxed_order 更快但可能略微乱序。多数 RAG 场景用 relaxed 即可（后面还有 rerank 兜底）。

⑤正确写法与常见误写对照

pgvector 的完整查询写法与常见误写对照：

-- ✅ 正确：走 HNSW 索引
SELECT id, 1 - (emb <=> $1) AS sim
FROM docs ORDER BY emb <=> $1 LIMIT 10;

-- ❌ 误写 1：运算后再排序，索引失效
SELECT id FROM docs ORDER BY 1 - (emb <=> $1) DESC LIMIT 10;

-- ❌ 误写 2：内积忘了取负
SELECT id FROM docs ORDER BY (emb <#> $1) LIMIT 10;
--   正确应为 ORDER BY emb <#> $1（<#> 已返回负内积，直接升序即最大内积）

-- ✅ 降维 + 半精度（3072 维场景）
ALTER TABLE docs ADD COLUMN emb_h halfvec(3072);
UPDATE docs SET emb_h = emb::halfvec;
CREATE INDEX ON docs USING hnsw (emb_h halfvec_cosine_ops);

-- ✅ 二值量化检索
CREATE INDEX ON docs USING hnsw ((binary_quantize(emb)::bit(1536)) bit_hamming_ops);
SELECT id FROM docs
ORDER BY binary_quantize(emb)::bit(1536) <~> binary_quantize($1)::bit(1536)
LIMIT 40;

⑥速记卡

ef_search 默认 40

取 top-100 会少返回；规则是 ef_search ≥ LIMIT。

probes 默认 1

pgvector 最坑默认值，召回可能只有 60%。必须显式设。

IVFFlat 前置条件

必须先有数据再建索引，空表建了等于没建。

建索引内存

maintenance_work_mem 不够会落盘，慢数倍。

小规模先试

用 10% 数据量时间，线性外推再决定全量。

过滤塌陷

< 0.8.0 结果可能不足 K；0.8+ 用 iterative_scan。

3072 维

改用 halfvec(3072) 或表达式索引。

排序写法

ORDER BY emb <=> $1，不要在外层做运算。

pgvector 的两个默认值（ef_search=40、probes=1）足以让一次正常的测试得出「pgvector 不可用」的错误结论。先改默认值，再下判断。
