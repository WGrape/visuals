先建立直觉：自来水管网系统

要把很多口井的水汇集到水厂，你需要：进水口（接水）→ 管道/蓄水池（暂存）→ 出水口（送到水厂）。

Flume 就是这样的管网：Source 接数据，Channel 暂存，Sink 送到目的地。而且管网可以多级串联——各楼层的支管汇到总管，再送到水厂。

核心概念：Agent 三段式

Channel 选型：可靠性与性能的权衡

Channel可靠性性能适用
Memory Channel低（进程挂了数据全丢）高允许少量丢失的场景（如普通日志）
File Channel高（落盘持久化）中不能丢数据（如金融、交易日志）
Kafka Channel高（且可多消费者）高推荐，兼具可靠与性能
Memory Channel 是最常见的丢数据原因。它把数据放在内存队列里，Agent 进程崩溃或重启时队列中的事件全部丢失。生产环境对重要数据务必用 File 或 Kafka Channel。

Source 选型

Source做法问题
exec执行 tail -F 等命令读数据不记录位点，重启后重复或丢失
spooldir监听目录中的新文件文件必须不可变（写完才能被采集）
taildir监听文件追加，记录位点✅ 推荐，支持断点续传
exec source 的坑：它只是执行一条 shell 命令，不记录读到哪里了。Agent 重启后会从文件开头（或重新 tail）开始，导致重复采集或漏采。生产上应使用 taildir source——它把读取位点持久化到磁盘，重启后精确续传。

典型配置

# 定义 Agent 的组件
a1.sources = r1
a1.channels = c1
a1.sinks = k1

# Source：taildir 监听日志文件，记录位点
a1.sources.r1.type = TAILDIR
a1.sources.r1.filegroups = f1
a1.sources.r1.filegroups.f1 = /var/log/app/*.log
a1.sources.r1.positionFile = /var/flume/taildir_position.json

# Channel：File Channel 保证不丢
a1.channels.c1.type = file
a1.channels.c1.checkpointDir = /var/flume/checkpoint
a1.channels.c1.dataDirs = /var/flume/data

# Sink：写 HDFS，按时间分目录
a1.sinks.k1.type = hdfs
a1.sinks.k1.hdfs.path = /logs/app/%Y-%m-%d/%H
a1.sinks.k1.hdfs.rollInterval = 600      # 10 分钟滚动生成新文件
a1.sinks.k1.hdfs.rollSize = 134217728    # 或 128MB 滚动
a1.sinks.k1.hdfs.fileType = DataStream

# 绑定
a1.sources.r1.channels = c1
a1.sinks.k1.channel = c1
HDFS Sink 的小文件问题：rollInterval（按时间滚动）如果设得太短（如默认 30 秒），会产生海量小文件，拖垮 NameNode 和下游计算。建议：优先用 rollSize（按 128MB 滚动）而不是按时间，并适当调大 rollInterval。

多级串联

Flume 支持 Agent 首尾相接：采集 Agent → 汇聚 Agent → HDFS。好处是把「分散采集」和「集中写入」解耦——采集端轻量，汇聚端负责批量写入 HDFS 减少小文件。

Flume vs Filebeat

维度FlumeFilebeat
语言/资源Java（JVM，较重）Go（约 10MB 内存）
位点记录taildir source 支持原生注册表，成熟可靠
背压靠 Channel 容量原生背压感知
生态Hadoop 生态集成好Elastic 生态集成好
现状逐渐淡出更主流
选型建议：新项目优先考虑 Filebeat（更轻、位点管理更成熟、背压机制更好）。Flume 仍有价值的场景：已深度使用 Hadoop 生态、需要直接写 HDFS/HBase、或已有大量 Flume 配置沉淀。更现代的架构是 Filebeat/Flume → Kafka → 下游消费者，用 Kafka 统一缓冲。

🎯 面试问答

Q：Flume 会丢数据吗？
A：取决于 Channel 和 Source 的选型。用 Memory Channel 时，Agent 进程崩溃会丢失内存队列中的所有数据——这是最常见的丢数据原因。用 File Channel 或 Kafka Channel 则能持久化，保证不丢（但性能略低）。另外用 exec source 也有风险：它不记录读取位点，重启后会重复或漏采。生产建议组合：taildir source + File/Kafka channel。

Q：exec source 和 taildir source 有什么区别？
A：核心区别是是否记录位点。exec 只是执行一条 shell 命令（如 tail -F），不持久化读到哪一行，Agent 重启后会从头或重新 tail，导致重复采集或漏采。taildir 会把每个文件的读取偏移量写入 positionFile，重启后精确从断点继续。生产环境必须用 taildir（Flume 1.7+ 支持）。

Q：为什么 HDFS 上产生了很多小文件？
A：通常是 HDFS Sink 的滚动策略配置不当。rollInterval 默认 30 秒——意味着即使只写了几 KB，每 30 秒也会生成一个新文件。在日志量小时会产生海量小文件，拖垮 NameNode 内存、让下游计算产生海量任务。解决：调大 rollInterval（如 600 秒）、优先用 rollSize（按 128MB 滚动）、设置 rollCount = 0(不按条数滚动)，并定期做小文件合并。

Q：现在还应该用 Flume 吗？
A：看场景。新项目建议优先考虑 Filebeat：它更轻（Go 编写，约 10MB 内存 vs Flume 的 JVM）、位点管理更成熟、有原生背压感知、社区活跃。Flume 仍适合的场景：已深度绑定 Hadoop 生态、需要直接写入 HDFS/HBase/Hive、或团队已有大量 Flume 配置。更通用的现代架构是：Filebeat/Flume → Kafka → 下游消费者，用 Kafka 做统一缓冲层，采集端和处理端各自独立演进。
