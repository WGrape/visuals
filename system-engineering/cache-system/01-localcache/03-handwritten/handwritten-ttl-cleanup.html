Redis 的做法

先建立直觉：冰箱里的过期食品

冰箱里塞满食物，每样都贴了保质期。怎么清理？

  • 策略一（惰性）：你要吃的时候才拿出来看日期，过期就扔。问题：那些你永远不吃的，会一直在冰箱里烂着。
  • 策略二（定期）：每周六固定翻一遍冰箱，过期的全扔。问题：翻冰箱很累，而且可能周一就过期的东西要等到周六才扔。
  • 策略三（定时提醒）：每样食物上贴个「到期闹钟」，到点响一声你就扔。问题：食物多的时候，闹钟太多。

现实中三种会混着用，缓存系统也一样。

策略一：惰性删除（Lazy / Passive）

做法：不主动做任何事，只在 Get 时检查是否过期，过期就删除并返回未命中。

func (c *cache) Get(k string) (any, bool) {
    it, ok := c.data[k]
    if !ok { return nil, false }
    if time.Now().After(it.expireAt) {
        delete(c.data, k)        // 访问时才发现过期
        return nil, false
    }
    return it.val, true
}
优点缺点
✅ 零额外 CPU 开销，只在访问时判断一次❌ 不访问的过期数据永不释放 → 内存泄漏
✅ 实现最简单❌ 内存占用可能长期虚高
典型故障：一个服务写入大量带 TTL 的数据后就不再访问，Redis/本地缓存的内存一直降不下来，看起来像「TTL 没生效」。实际是惰性删除还没被触发——数据过期了但没人碰它。

策略二：定期删除（Active / Periodic）

做法：后台任务定时扫描一部分数据，删除其中过期的。

优点缺点
✅ 能回收不被访问的过期数据❌ 有 CPU 扫描开销
✅ 可通过采样控制成本❌ 清理不及时（要等下一轮扫到）
Redis 的特别约束：Redis 处理命令是单线程的，定期删除的扫描不能太久，否则会阻塞所有请求。所以 Redis 严格限制每轮的数量和执行时长。这也是为什么它用随机采样而不是全量扫描——用概率覆盖换取可控的开销。

策略三：定时删除 / 时间轮（Timer Wheel）

做法：为每个 key 注册一个定时器，到期立即删除。高效的实现是时间轮：把时间轴分成若干格，相同过期时刻的 key 挂在同一个格子里，指针走到哪格就清理哪格。

优点缺点
✅ 及时，过期即删除，内存最干净❌ 每个 key 一个定时器，内存开销大
✅ 时间轮可做 O(1) 调度❌ 大量 key 同时过期会产生清理尖峰
为什么不普遍采用？缓存里 key 数量动辄百万级，为每个 key 维护定时器太贵。只有在 key 数量可控、要求精确及时删除的场景（如连接超时管理）才划算。

三种策略对比

策略CPU 开销内存回收及时性实现复杂度
惰性删除极低（仅访问时判断）差（不访问就不回收）极低
定期删除中（可控）中（有延迟）中
定时删除低（事件驱动）好（即期即删）高（需定时器/时间轮）
Redis 的答案：惰性 + 定期。访问时惰性检查（保证读到的一定是有效数据），后台定期采样（保证冷数据能被回收）。不用定时删除，因为百万级 key 的定时器太贵。这是「用一点点不及时换巨大的内存/CPU 节省」的典型权衡。

实践建议

  • 自己写缓存：惰性检查必做（保证正确性），定期清理选做（防止内存泄漏）。
  • 定期清理要限量 + 限时：每次只处理一小批，超时就等下一轮。
  • 监控「过期但未回收」的内存占比，它是判断清理是否跟得上写入的指标。
  • 如果内存持续增长不降，先怀疑惰性删除没被触发，再怀疑清理频率太低。

🎯 面试问答

Q：Redis 到底用的是哪种过期策略？
A：惰性删除 + 定期删除两者结合。访问 key 时先检查过期（惰性，保证读不到脏数据）；同时后台每秒运行 10 次定期任务，每次随机抽取 20 个 key 删除其中过期的，如果这批中过期比例超过 25% 就立即再抽一批（说明过期数据多，需要加大清理力度）。不用定时删除，因为百万级 key 每个都挂定时器太耗内存。

Q：为什么我设了 TTL，内存还是一直涨？
A：最常见原因是只依赖惰性删除：数据过期了，但因为没人再访问它，删除动作从未被触发，它一直占着内存。这在「写入后不再读取」或「一次性数据」场景特别明显。排查：看 Redis 的 expired_keys 指标是否在增长——如果数据明明过期了但这个值不涨，说明清理没跟上。

Q：定期删除会阻塞请求吗？
A：设计不当会。Redis 是单线程处理命令的，如果定期扫描一次性遍历几百万 key，会长时间阻塞所有请求。所以 Redis 严格限制：每次只随机采样 20 个，且有执行时间上限，超时立刻停止等下一轮。自己实现时也要遵守这个原则——分批、限量、限时。

Q：时间轮适合什么场景？
A：适合需要精确定时、且任务数量可控的场景，比如网络连接超时管理（几十万连接，每个都有超时时间）、延时消息、定时任务调度。它不适合缓存过期，因为缓存 key 数量太大（百万甚至千万级），为每个 key 维护定时器或链表节点的内存开销不可接受，而且大量 key 同时过期会导致清理尖峰。
