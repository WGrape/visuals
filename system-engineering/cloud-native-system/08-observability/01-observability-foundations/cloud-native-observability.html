一句话总结：监控回答"已知的问题是否发生"（靠预设的仪表盘与告警）； 可观测性回答"没预想到的故障为什么发生"（靠系统输出的丰富信号去自由探索）。 在微服务 + 弹性伸缩的环境下，故障模式无法穷举，因此可观测性是云原生的必备支撑能力， 而非可选项。

01监控 vs 可观测性

维度监控 Monitoring可观测性 Observability
核心问题"是否出问题了？""为什么出问题？"
前提预先知道可能出什么故障承认故障模式无法穷举
手段预设仪表盘 + 阈值告警高基数、高维度的原始数据 + 自由探索
典型输出CPU 85% 告警"哪个租户、哪个版本、哪条链路变慢了"
适用系统单体、稳定拓扑微服务、动态拓扑、频繁发布
输出足够丰富的信号， 使人在故障发生时能临时提出问题并得到答案，这才是可观测性。

02三支柱

趋势与告警 局限：聚合后丢失细节 无法回答"是哪个用户" Prometheus / Grafana Counter / Gauge / Histogram 📝 Logs 日志 离散的事件记录 高成本 · 数据量大 擅长：细节与上下文 局限：难以聚合统计 无法看出整体趋势 Loki / Elasticsearch 结构化 JSON 优于纯文本 🔗 Traces 链路 单次请求的全路径 采样存储 · 中等成本 擅长：定位瓶颈服务 局限：采样会漏掉偶发 需与指标配合 Jaeger / Tempo TraceId / SpanId 串联 三者互补：指标发现问题 → 链路定位服务 → 日志查明原因

排障的典型路径

  1. Metrics 发现异常：Grafana 上看到某服务 P99 延迟突增、错误率上升。
  2. Traces 定位环节：按时间段和服务筛出慢请求，看 span 树发现卡在数据库调用。
  3. Logs 查明根因：用该请求的 TraceId 检索日志，看到具体 SQL 与报错堆栈。
关键前提：三者必须能互相跳转。 日志里带 trace_id、指标与链路共享同一套标签（service / version / instance）， 才能做到"从告警一键下钻到根因"。这是可观测性建设中最容易被忽视、却最影响效率的一点。

04该采集什么信号

四大黄金信号（Google SRE）

信号含义常用指标
Latency 延迟处理请求耗时P50 / P95 / P99（必须看分位数，平均值会掩盖长尾）
Traffic 流量系统承载的请求量QPS / RPS、并发连接数
Errors 错误失败请求占比错误率 = 5xx 数 / 总请求数
Saturation 饱和度资源有多"满"CPU、内存、磁盘 IO、队列长度、连接池占用

USE 与 RED（两个常用方法论）

🔧 USE（面向资源）

Utilization 使用率 · Saturation 饱和度 · Errors 错误。
用于排查基础设施（CPU、磁盘、网络）瓶颈。

🌐 RED（面向服务）

Rate 请求速率 · Errors 错误率 · Duration 耗时。
用于衡量微服务的用户体验，是四大黄金信号的简化版。

两个常见错误：
① 只看平均值——平均延迟 50ms 可能掩盖了 5% 请求的 5 秒超时， 必须看 P95/P99 分位数；
② 基数爆炸——把 user_id、request_id 这类无限取值塞进指标标签， 会让时序数量爆炸拖垮存储（详见《时序数据库》的高基数陷阱）。 高基数信息应放日志与链路，而非指标标签。

05从指标到 SLO 与告警

三个概念层层递进：

概念定义示例
SLI（指标）衡量服务质量的量化指标成功请求数 / 总请求数
SLO（目标）对 SLI 设定的目标值30 天内可用性 ≥ 99.9%
SLA（协议）对外承诺及违约后果未达 99.9% 则赔付

错误预算 Error Budget

SLO 99.9% 意味着每月允许 0.1% 的失败额度（约 43 分钟）。 这笔"预算"可以被有意消耗在发布新功能上—— 预算充足就加快发布，预算耗尽就冻结变更、专注稳定性。 这把"稳定性 vs 迭代速度"的争论变成了可量化的决策。

# Prometheus 多窗口告警（比单阈值更稳：兼顾快速发现与避免抖动误报）
# 1) 快窗口：2 分钟内错误率 > 2% → 紧急告警
(
  sum(rate(http_requests_total{status=~"5.."}[2m]))
  / sum(rate(http_requests_total[2m]))
) > 0.02

# 2) 慢窗口：1 小时内错误率 > 1% → 消耗错误预算，需介入
(
  sum(rate(http_requests_total{status=~"5.."}[1h]))
  / sum(rate(http_requests_total[1h]))
) > 0.01
告警设计原则：① 只告警影响用户的症状（而非"CPU 高"这种原因）； ② 每条告警必须可执行（有明确处理动作），否则应降级为看板指标； ③ 减少告警疲劳——告警太多等于没有告警。

06常见疑问

Q：有了服务网格还需要自己埋点吗？
A：网格能提供东西向流量的黄金指标与链路（黑盒视角，无需改代码）， 但看不到服务内部——比如某个函数慢、缓存命中率低、业务逻辑分支错误。 因此推荐组合：网格负责网络层信号（零成本），关键业务路径用 OpenTelemetry 显式埋点（白盒视角）。
Q：为什么要用分位数而不是平均延迟？
A：平均值会被大多数快请求拉低，掩盖少数慢请求的糟糕体验。 而用户体验恰恰由最慢的那部分决定（且慢请求常来自重要客户或复杂操作）。 实践：P99 用于告警，P50 用于容量规划，两者都要看。
Q：日志、指标、链路的存储空间怎么控制？
A：三类策略不同——
① 指标：聚合后体积极小，可存数月至数年；
② 日志：量最大，用分级 + 采样 + 保留期（如错误日志存 30 天、调试日志存 3 天）；
③ 链路：必须采样（如 1%~10%）， 并对异常/慢请求做尾部采样（保证有价值的那部分被保留）。
