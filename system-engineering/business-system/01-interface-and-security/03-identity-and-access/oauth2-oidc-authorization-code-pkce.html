OAuth2 与 OIDC：授权码、PKCE 和令牌校验

用第三方登录与订单 API 的同一条请求链，分清“用户是谁”和“客户端获准做什么”。

先分清两个协议的职责

OAuth2 是委托授权框架：资源所有者允许客户端在限定范围内访问资源服务器。OIDC 在 OAuth2 之上定义登录身份层，客户端请求 openid scope 后获取 ID Token、UserInfo 等标准身份声明。OAuth2 的 Access Token 给资源服务器用；OIDC 的 ID Token 给客户端确认登录身份用。二者不是“一个新版本和一个旧版本”，也不能把 Access Token 当登录凭证直接解析后信任。

角色在“通过身份平台登录订单系统”中信任边界
用户 / 资源所有者在身份平台完成登录与授权不把账户密码交给订单系统
客户端订单系统的 Web 后端或前端应用持有自身会话；不能替资源服务器推断权限
授权服务器 / OIDC Provider验证用户并签发授权码、令牌受信任的 issuer；通过发现文档获取端点与密钥
资源服务器实际提供订单 API 的服务按受众、范围及业务归属验证请求

图解：授权码 + PKCE 的后端登录链

图中箭头是教学简化：实际浏览器经过重定向拿到 code，后端用受保护的令牌端点交换；授权服务器不会把客户端密钥交给浏览器。用会话把授权请求与回调绑定，不能只靠 URL 里的用户 ID 识别请求。

逐步推演：每一步在防什么

请求前绑定会话

客户端生成每次请求独立的 state、nonce 和高熵 code_verifier，只发送由 verifier 派生的 S256 code_challenge。预先登记精确回调地址，服务端保存 state/verifier/nonce 与当前登录会话的绑定。

回调不是完成登录

授权服务器重定向携带 code 和 state。先检查 state 匹配、一次性消费，确认回调地址与本次请求对应；错误或缺失就停止。state 关联授权响应，nonce 在后续验证 ID Token 时关联身份声明，两者用途不同。

授权码不能脱离验证器使用

后端在令牌端点提交 code、精确的 redirect URI 和原始 verifier，机密客户端按注册方式认证自身。授权服务器验证 challenge 后才发令牌。PKCE 限制“截获 code 即可兑换”的风险；浏览器型公开客户端更不能依赖静态 client secret。

资源端再做独立判定

客户端验证 ID Token 后建立自己的登录会话；调用订单 API 时携带发给该 API 的 Access Token。资源服务器独立验证令牌、scope 与对象归属，不把“已登录”当“能看任何订单”。

第一层 · 概念与判定

字段 / 凭证谁验证常见误判
state客户端将回调值与本次会话中的随机值比对以为同一用户 ID 就能防回调串线
nonceOIDC 客户端将 ID Token 声明与请求值比对以为它可代替 state
ID Token客户端验证身份声明，建立登录会话拿它作 API 授权令牌
Access Token资源服务器按其格式校验或向授权服务器查询假设所有 Access Token 都是可自行解析的 JWT
scope资源服务器核对被委托的能力有 orders.read 就能读其他用户订单

第二层 · 校验参数与示例

OIDC 客户端应使用可信 issuer 的发现文档和公钥集合，验证 ID Token 的签名算法白名单、签名、iss、aud、时间声明，以及本次请求所需的 nonce；必要时检查多受众场景的 azp。不要直接信任令牌头提供的任意密钥地址，也不要因为能 Base64 解码就认为令牌有效。资源服务器按 Access Token 实际契约验证签名或使用 introspection，核对自己的 aud、有效期与 scope；不能用客户端 ID Token 的校验逻辑替代。

// 伪代码：把登录身份验证与 API 授权分开
callback := validateStateAndRedeemCode(code, state, storedVerifier)
id := validateIdToken(callback.idToken, trustedIssuer, clientId, storedNonce)
session := createLocalSession(id.subject)

request := validateAccessToken(bearerToken, trustedIssuer, ordersApiAudience)
requireScope(request, "orders.read")
requireOrderOwnership(request.subject, requestedOrderId)

此处的 scope 是示意值；真实字段、轮换策略、时钟容差和客户端认证方式以所选身份平台的协议契约为准。

第三层 · 故障与边界

  • 回调报 state 不匹配：检查多标签页、会话 Cookie 的 SameSite、代理回调域、一次性值是否提前被消费；不能直接跳过校验。
  • 令牌签名通过但 API 返回 401：常见是 issuer、audience、过期或时钟偏差不符；检查拿的是 ID Token 还是为该 API 签发的 Access Token。
  • 登录成功却访问被拒（403）：检查 scope/角色以及订单归属；重新登录不应自动绕过授权策略。
  • 刷新令牌泄露：刷新令牌应受服务端安全存储或合适的浏览器边界保护，支持轮换/撤销；退出本地会话不等于所有已发 Access Token 立即失效，需按契约设计短寿命与撤销机制。

第四层 · 原理与取舍

既然 PKCE 已经存在，还需要 state 吗？

需要把回调正确关联到当前用户的授权请求。PKCE 将 code 绑定到持有 verifier 的客户端实例；state 提供客户端侧的请求-响应关联与跨站请求防护。两者目标不同，不应互换。

ID Token 和 Access Token 都是 JWT，能通用吗？

不能。即使都采用 JWT 封装，受众与用途也不同；资源服务器不能因为 ID Token 签名有效，就接受发给登录客户端的令牌访问订单 API。

Scope 写着 orders.read 为什么仍要查归属？

Scope 只表示获准调用一类操作，不能证明请求的具体订单属于该用户或租户。对象级授权应在资源服务器读取数据前完成。

自检

浏览器回调带着正确 code，但 state 不一致，能先兑换看看吗？

不能。应停止流程、记录安全事件，并让用户重新发起授权；兑换成功不能补回失去的请求关联。
