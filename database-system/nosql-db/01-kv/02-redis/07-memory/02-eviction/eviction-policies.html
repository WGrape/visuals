八种策略 = 两条轴的笛卡尔积

记策略不要死背八个名字，记住两条轴即可：淘汰范围（allkeys 全部键 / volatile 仅带过期时间的键）和挑选算法（random 随机 / lru 最近最少用 / lfu 最不经常用 / ttl 剩余寿命最短）。两者组合出六种，再加一个 noeviction（不淘汰、直接报错），共八种。

noeviction默认策略；内存满时写命令返回错误，读仍可用
allkeys-lru全体键中淘汰最久未访问的，最通用的缓存策略
volatile-lru只在设了 TTL 的键里淘汰 LRU，保护持久数据
allkeys-lfu淘汰访问频次最低的，适合有稳定热点的场景
volatile-lfu带 TTL 的键中淘汰 LFU
allkeys-random随机淘汰，成本最低但命中率差
volatile-random带 TTL 的键中随机淘汰
volatile-ttl优先淘汰剩余寿命最短的，适合「越旧越没用」的数据

LRU / LFU 是怎么实现的

① 为什么是「近似 LRU」

  • 精确 LRU 需要维护全局链表，每次访问都要移动节点，内存与性能开销大。
  • Redis 做法：每个对象在 lru 字段里记一个 24 位的「时钟」，淘汰时随机采样 N 个键，挑 idle 最大的淘汰。
  • maxmemory-samples 默认 5，调到 10 精度接近精确 LRU，代价是 CPU。
  • Redis 3.0 后有淘汰池（pool）机制，候选会被缓存复用，精度进一步提升。

② LFU 的计数器设计

  • LFU 用同一个 24 位字段拆成两部分：16 位分钟级时间 + 8 位频次计数器。
  • 频次用概率递增（对数增长）：不是每次访问 +1，而是越热越难涨，防止计数器很快饱和。
  • 支持衰减：lfu-decay-time（默认 1 分钟）让久未访问的键频次下降，避免旧热点永久霸占。
  • 新建键有初始频次，避免刚写入就被立刻淘汰。

③ 配置与调优

  • maxmemory 必须显式设置，否则 64 位系统默认不限制（用满机器内存）。
  • 设置值通常取物理内存的 60-75%，要给 RDB fork、复制缓冲区、碎片留空间。
  • maxmemory-samples：5→10 可提升命中率，CPU 敏感场景保持默认。
  • lfu-log-factor 10 / lfu-decay-time 1 是默认，热点切换慢时可调大 decay。

④ 主从与集群的影响

  • 淘汰只在主节点发生，主节点淘汰后通过 DEL 传播给从节点。
  • 从节点默认不淘汰（有自己的 maxmemory 时会按策略删，但会与主不一致）。
  • 集群模式下每个分片独立淘汰，可能出现「某分片先满」的热倾斜。
  • 监控要按实例/分片分别看 used_memory 与 evicted_keys。

深入自检

volatile-lru 和 allkeys-lru 到底差在哪？

差在「哪些键有资格被淘汰」。allkeys-lru 把所有键都当缓存，可能淘汰掉你希望永久保存的数据；volatile-lru 只在设置了过期时间的键里淘汰，因此你只要不给持久数据设 TTL，它就绝对安全。代价是：如果所有带 TTL 的键都被淘汰完仍不够，Redis 无法继续淘汰，写命令会像 noeviction 一样报错。

为什么 LFU 的频次要用概率递增？

因为计数器只有 8 位（最大 255）。如果每次访问都 +1，一个稍热的键几分钟内就会打到 255 并永久饱和，之后无法区分「访问 1 万次」和「访问 10 万次」。概率递增让增长越来越难（近似对数），使计数器在很长的时间尺度上仍有区分度。

LRU 信息会被哪些操作污染？

最典型的是全量扫描类操作：一次 SCAN、一次大范围 LRANGE、一次批量导出，会把大量冷数据的访问时间刷新，让它们看起来「刚被访问过」，从而挤掉真正的热点。这也是为什么生产要避免全量遍历，或用单独实例做离线分析。

淘汰会导致数据丢失吗？

会，这正是它的设计目的——把 Redis 当缓存用时，被淘汰的键等同于「缓存未命中」，业务应能从后端数据源回填。如果你把 Redis 当唯一存储（不能丢），就必须用 noeviction 并做好容量规划，否则满内存后写失败；也不能依赖 volatile-* 策略，因为无 TTL 键可淘汰时同样会写失败。

为什么设置了 maxmemory 还是会 OOM？

常见原因：① 淘汰赶不上写入速度（瞬时大写入）；② 复制缓冲区、客户端输出缓冲区占用不计入淘汰范围的部分；③ 内存碎片率很高；④ 从节点内存不足。要做的是：给 maxmemory 留足余量、监控 mem_fragmentation_ratio、限制客户端缓冲区、关注 evicted_keys 增长速率。

如何判断淘汰策略选得对不对？

看两个指标：命中率（keyspace_hits / (hits+misses)）与 evicted_keys 增速。若命中率长期低于预期且 evicted_keys 持续增长，说明内存偏小或策略不匹配。做法：先用 INFO stats 取当前基线，再切换策略（CONFIG SET 可在线生效）观察 24 小时，对比命中率变化。
