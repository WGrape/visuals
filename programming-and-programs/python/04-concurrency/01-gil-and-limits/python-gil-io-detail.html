⭐ 核心原理：Python 的 I/O 函数（如 socket.read、file.read） 底层调用 C 库，Python 解释器知道"这个操作会阻塞"，于是主动释放 GIL

T3 → T4：Thread-B 等待 I/O 响应，Thread-A 获得 GIL
Thread-B 进入 I/O 等待状态，不消耗 CPU：
# Thread-B 的状态变化 Thread-B.state = "BLOCKED" # 被 OS 标记为阻塞 Thread-B.gil = null # 不持有 GIL # Thread-A 检测到 GIL 可用 Thread-A.state = "RUNNING" # 被 OS 调度 Thread-A.gil = acquired # 重新获取 GIL，继续执行
这就是多线程的价值！Thread-B 在等待网络响应时，完全不占用 CPU， Thread-A 可以充分利用这段时间执行自己的任务

# 操作系统通知：I/O 完成！ Thread-B.state = "READY" # 变为就绪状态 # 等待 OS 下一次调度，获取 GIL 后继续执行

T5 → T6：Thread-A 和 Thread-B 继续交替执行
循环往复，两个线程通过 OS 调度 + GIL 机制实现"伪并发"
💡 关键结论
I/O 操作时 GIL 释放的本质：

1. Python 的 I/O 函数（socket、file、requests 等） 底层调用 C 库，Python 解释器能识别"这是一个需要等待的操作"

2. 识别后，Python 会主动释放 GIL，而不是让线程空等

3. 其他线程检测到 GIL 可用 + 被 OS 调度后，就能获取 GIL 继续执行

4. 结果：多个线程在 I/O 等待期间可以交替执行，充分利用 CPU 资源

这就是为什么多线程对 I/O 密集型任务有帮助： 等待的时候不占 CPU，别人就可以用！

GIL 是什么，为什么存在

全局解释器锁是解释器里的一把大锁：同一时刻只允许一个线程执行字节码。它不是语言规范，而是当前主流实现的一个工程取舍。

保护什么保护解释器内部状态，尤其是引用计数不被并发破坏
带来什么好处单线程性能更好、C 扩展写起来简单、对象模型不必处处加锁
带来什么代价多线程无法利用多核做并行计算
存在多久了自早期版本就有，围绕它的移除尝试一直在进行
锁的让出与获取：多线程是交错执行，不是同时执行

什么时候会释放这把锁

这是判断「多线程有没有用」的关键：只要线程在等待外部事件时把锁让出去，并发就有效；如果它一直在算，锁就不会让。

场景是否释放锁结论
网络读写、文件读写阻塞前释放多线程对 IO 密集有效
睡眠等待释放多线程有效
纯计算循环不主动释放，靠切换间隔多线程无法加速
数值计算库的重活可在 C 层主动释放能真正利用多核
等待锁或条件变量释放多线程有效
调用不释放锁的 C 扩展不释放会阻塞其他线程
import sys, time, threading # 切换间隔：解释器每隔这么久就考虑让出锁 sys.getswitchinterval() # 默认通常是 0.005 秒 sys.setswitchinterval(0.001) # 调小：切换更频繁，单线程更慢 # 场景一：IO 密集，多线程有效 def fetch(i): time.sleep(0.5) # 睡眠时释放锁 return i # 场景二：CPU 密集，多线程无效，要用多进程 def cpu(n): s = 0 for i in range(n): s += i * i # 一直在算，不会主动让锁 return s # 选型结论： # IO 密集 -> 多线程 或 异步 IO # CPU 密集 -> 多进程，或者用能在底层释放锁的计算库 # 混合场景 -> 进程池 + 每个进程内线程池

三种并发模型的取舍

多线程：简单但有上限

写法最接近同步代码，共享数据方便，但受锁限制，只能加速 IO 部分。适合中小规模的并发任务，需要注意共享数据的加锁。

多进程：能上多核但成本高

每个进程有独立的解释器与锁，可以真正并行。代价是内存占用更高、进程间通信要走序列化，而且启动比线程慢。

IO 密集多线程或异步，都能有效并发
CPU 密集多进程，或底层释放锁的计算库
高并发连接异步 IO 更有优势
共享状态多多线程更简单，但要加锁
需要真正并行只能靠多进程
进程间通信走序列化，注意开销
进程启动成本比线程高得多
调试难度多进程排障比多线程更麻烦

深入自检：GIL 的六个常见问题

多线程一定比单线程快吗？

不一定。如果任务是纯计算，多线程反而更慢：加锁、切换、调度都有开销，却拿不到更多算力。只有当任务中有等待（网络、磁盘、睡眠）时，多线程才能把等待时间利用起来。

异步 IO 能绕开锁吗？

严格说不是绕开，而是避开了它的影响：异步模型是单线程内切换任务，根本不需要多个线程同时执行字节码。所以它对高并发 IO 场景非常有效，但同样无法加速计算。

为什么计算库能多核？

因为它们在底层用 C 实现，执行重活时会主动释放锁，算完再取回来。所以矩阵运算这类任务即使只用单线程写，也可能跑满多个核。

移除锁的尝试进展如何？

一直是社区的重要议题，难点在于既要移除锁，又不能牺牲单线程性能、不能破坏现有 C 扩展的兼容性。近期版本已经在推进可选的免锁构建模式。

多进程一定更好吗？

不是。进程更重、通信更贵、调试更难。只有在确实需要并行计算时才值得。很多服务先用多线程加异步 IO 就够了，遇到计算瓶颈再针对性改造。

怎么判断我的程序卡在哪？

先看是等待还是计算：采样看线程栈，如果大部分时间停在网络或文件调用上，是 IO 密集；如果一直在自己的循环里，是 CPU 密集。判断清楚再选并发模型，否则容易南辕北辙。

GIL 的机制与实测数据

项目数值说明
GIL 切换间隔5ms（默认）sys.getswitchinterval()；可调
持有 GIL 的最大时长一个线程最多跑 5ms 就让出CPU 密集时表现为「时间片轮转」
释放 GIL 的操作IO、sleep、部分 C 扩展文件/socket 读写、time.sleep、numpy 计算
不释放的操作纯 Python 计算循环、字符串处理等
线程切换开销约 1~5 µs含内核态切换
进程切换开销约 10~50 µs比线程贵一个量级
进程间通信开销更高（需序列化）pickle/共享内存
多线程 CPU 密集加速比≈1 或 <1没有加速，反而因切换变慢

GIL 存在的根本原因：CPython 的内存管理不是线程安全的（引用计数如果能被多线程同时修改就会出错）。GIL 是一个大锁，保证同一时刻只有一个线程执行 Python 字节码，从而让引用计数等操作无需加锁。代价是丧失了多核并行能力。

Python 3.13 起有实验性的 free-threading（无 GIL）版本，但生态兼容性还在推进中，短期内生产环境仍以有 GIL 版本为主。

import sys, time, threading, os
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

print("switch interval:", sys.getswitchinterval())     # 5ms

def cpu_bound(n=30_000_000):
    s = 0
    for i in range(n): s += i
    return s

def io_bound():
    time.sleep(0.5)          # sleep 会释放 GIL
    return 1

# 实验 1：CPU 密集，多线程 vs 多进程
t0 = time.time()
[cpu_bound(10_000_000) for _ in range(4)]
print(f"串行:        {time.time()-t0:.2f}s")

t0 = time.time()
with ThreadPoolExecutor(4) as ex: list(ex.map(cpu_bound, [10_000_000]*4))
print(f"4 线程:      {time.time()-t0:.2f}s")     # 基本不快甚至更慢

t0 = time.time()
with ProcessPoolExecutor(4) as ex: list(ex.map(cpu_bound, [10_000_000]*4))
print(f"4 进程:      {time.time()-t0:.2f}s")     # 接近 4 倍（核数够的话）

# 实验 2：IO 密集，多线程有效
t0 = time.time()
with ThreadPoolExecutor(50) as ex: list(ex.map(io_bound, range(50)))
print(f"50 线程 IO:  {time.time()-t0:.2f}s")     # 约 0.5s（并发生效）

一句话总结：IO 密集用线程/协程，CPU 密集用进程。GIL 只在执行 Python 字节码时才持有，IO 和 C 扩展计算会释放它，所以 IO 密集场景多线程是有效的。
