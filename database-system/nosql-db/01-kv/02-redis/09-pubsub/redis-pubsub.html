📡 Redis 发布订阅（Pub/Sub）

一对多的实时消息广播：发布者只管发，订阅者各听各的

Pub/Sub 是 Redis 内置的消息发布/订阅机制：发布者把消息发到某个频道（channel），所有订阅了该频道的客户端会立刻收到，发和收完全解耦。它适合「一对多广播、允许丢消息、要极简」的场景。

💡 类比：广播电台。电台（发布者）按频率（频道）播出，任何打开这个频率的人（订阅者）都能听到；电台不管谁在听、也不重播——你没赶上就听不到了。这就是 Pub/Sub 的「发后不理、不持久化」本质。

🛠 核心命令

命令作用例子
SUBSCRIBE channel [channel...]订阅一个或多个频道（阻塞等待消息）SUBSCRIBE news.sport
PUBLISH channel message向频道发消息，返回收到消息的订阅者数PUBLISH news.sport "goal!"
PSUBSCRIBE pattern按通配符订阅一类频道PSUBSCRIBE news.*
UNSUBSCRIBE [channel]取消订阅（不带参数=全部）UNSUBSCRIBE news.sport
PUBSUB CHANNELS查看当前活跃的频道PUBSUB CHANNELS
一个 PUBLISH 会把消息同时推给所有在线订阅者（fan-out 扇出）。返回的整数是「收到消息的订阅者个数」，若返回 0 表示当时没有人在听——消息直接丢弃，不会留存。

⚡ 典型场景

🔔

实时通知

订单状态变更推给前端/后台监听者

📊

轻量事件总线

服务间解耦广播，触发缓存失效、刷新统计

🎮

聊天室 / 弹幕

房间消息广播给所有在线成员

🔁

改一处配置，所有节点秒级收到并生效

⚠️ 三大坑（必看）

① 不持久化、会丢消息。消息只在「发布的瞬间」推给当时在线的订阅者。订阅者掉线期间、或根本没人订阅时发的消息，全部丢失。Redis 不会为 Pub/Sub 存任何历史。
② 没有 ACK、没有重投。Pub/Sub 是「发后不理」的纯推送，订阅者处理失败也不会重发，也不保证顺序以外的任何可靠性。
③ 慢消费者会拖垮连接。消息由 Redis 直接推给订阅者；若某订阅者处理慢、TCP 发送缓冲区积压，Redis 会阻塞在该连接上，进而影响同一实例上其他客户端。生产环境务必让订阅者消费够快。

一句话选型：要「即时广播、能丢无所谓」用 Pub/Sub；要「不丢、能重放、多消费者分工」用 Stream。别用 Pub/Sub 当可靠 MQ。

🎯 面试问答

Q：Pub/Sub 能当消息队列用吗？
A：只能做「不可靠广播」。它没有持久化、没有 ACK、没有消费组，消息会因订阅者不在线而丢失，不适合对可靠性有要求的队列场景（用 Stream 或专业 MQ）。
Q：发布时返回 0 是什么含义？
A：当时没有任何订阅者在线，消息直接被丢弃（不报错、不存储）。
Q：PSUBSCRIBE 和 SUBSCRIBE 区别？
A：前者按通配符（如 news.*）订阅一类频道，后者订阅精确频道名。一个消息若同时匹配精确订阅和模式订阅，订阅者可能收到两次。
Q：Pub/Sub 消息会进 RDB/AOF 吗？
A：不会。Pub/Sub 消息是纯内存瞬时广播，不经过任何持久化路径。

Pub/Sub 的可靠性边界与替代方案

Redis Pub/Sub 最大的特点也是最大的坑：它不持久化。消息发出去，如果当时没有订阅者，就永久丢失。理解这一点，才知道该不该用它。

维度Pub/SubStream (Redis 5.0+)专业 MQ (Kafka)
持久化无，纯内存广播有，写 AOF/RDB有，落磁盘
消费确认 ACK无有（pending 列表）有
断线补偿无，断线期间消息丢失有（按 ID 续读）有（offset 回放）
消费者组无（每个订阅者都收全量）有（组内分摊）有
堆积能力无（写了就发）有（受 maxlen 限制）强（TB 级）
延迟<1 ms~1 ms5~50 ms
适用实时广播、在线状态、缓存失效通知要可靠的轻量消息队列大数据量、严格不丢
场景推荐原因
在线用户状态广播Pub/Sub丢一条无所谓，下一条就覆盖
本地缓存失效通知Pub/Sub丢了最多是缓存晚一点失效
订单/支付事件Stream 或 Kafka绝对不能丢
跨服务异步任务Stream + 消费者组需要 ACK 和重试
聊天室消息（要历史）Stream需要回溯历史消息
聊天室消息（不要历史）Pub/Sub实时即可

命令速查

# Pub/Sub 基本操作
SUBSCRIBE channel:orders          # 订阅
PUBLISH channel:orders "hello"    # 发布（返回收到消息的订阅者数量）
PSUBSCRIBE channel:*              # 模式订阅（按 glob 匹配）
UNSUBSCRIBE channel:orders
PUBSUB CHANNELS [pattern]         # 列出活跃频道
PUBSUB NUMSUB channel:orders      # 该频道订阅者数（关键监控项！）
PUBSUB NUMPAT                     # 模式订阅总数

# 坑：SUBSCRIBE 之后该连接不能执行其他命令（除 SUBSCRIBE/UNSUBSCRIBE/
# PING/QUIT 等），需要另开一个连接做普通命令。

# ---------- 需要可靠时改用 Stream ----------
XADD mystream '*' field1 val1                     # 追加（* = 自动生成 ID）
XADD mystream MAXLEN ~ 10000 '*' f1 v1            # 限制长度（~ 表示近似裁剪）
XGROUP CREATE mystream mygroup $ MKSTREAM         # 创建消费者组
XREADGROUP GROUP mygroup c1 COUNT 10 BLOCK 5000 STREAMS mystream >
#                                                    ^ ">" 表示只取新消息
XACK mystream mygroup <id>                        # 处理完必须 ACK！
XPENDING mystream mygroup                         # 查看未 ACK 的消息
XCLAIM mystream mygroup c2 3600000 <id>           # 超时未 ACK 转给别的消费者（>1h）

# 监控关键：XPENDING 的 pending 数量持续增长 = 消费者处理不过来
  • 订阅者数为 0 时消息直接丢弃：这是 Pub/Sub 最反直觉的地方。PUBLISH 的返回值就是收到消息的订阅者数量，返回 0 意味着消息永远消失了。建议在生产代码里检查这个返回值。
  • 客户端断线重连后看不到断线期间的消息：所以 Pub/Sub 不能用于「必须送达」的场景。要补偿就用 Stream。
  • 订阅连接不能再做别的：进入订阅模式后该连接只能执行订阅相关命令，普通 GET/SET 会报错。需要两个连接：一个订阅，一个做业务。
  • 模式订阅（PSUBSCRIBE）开销大：每次发布都要遍历所有模式做匹配，频道多、模式多时会明显消耗 CPU。慎用 *。
  • 消息不堆积但有慢消费者问题：Redis 6.0 之前，如果某个订阅者读取慢，Redis 的输出缓冲区会持续增长，可能触发 client-output-buffer-limit 把该客户端踢掉。可以调大 pubsub 的缓冲区限制（默认 32MB 硬限制）。
  • 集群模式下 Pub/Sub 会广播到所有节点：发布一条消息会传遍整个集群，频道多、消息频繁时网络开销可观。
Pub/Sub 和 Stream 到底选哪个？

一句话判断：能不能接受丢消息。能接受（在线状态广播、缓存失效通知、实时推送的「最新值」类场景）→ Pub/Sub，简单、延迟最低（亚毫秒）；不能接受（订单、支付、任务队列）→ Stream 或专业 MQ。中间的灰色地带是「允许少量丢失但要能追历史」——用 Stream，配 MAXLEN ~ N 限制内存。还有一个常被忽略的因素：消费者组。Pub/Sub 是广播（每个订阅者都收到全量），如果你要的是「多个 worker 分摊处理」，必须用 Stream 的消费者组，Pub/Sub 做不到。

Stream 的 pending 持续增长怎么排查？

说明消费者消费了但没 ACK，或者消费得比生产慢。排查步骤：① XPENDING mystream mygroup 看 pending 总数和每个消费者的分摊；② 如果集中在某一个消费者，通常是该消费者卡住或挂了 —— 用 XCLAIM 把超时（如 >1 小时）的消息转移给其他消费者；③ 如果所有消费者都涨，说明消费速度跟不上生产 —— 要么加消费者（但注意 Stream 的消费者组里，一个 group 内的消息是按「均匀分配」而不是按能力的），要么优化处理逻辑，要么用 MAXLEN 做取舍。④ 别忘了检查代码里是不是漏了 XACK——这是最常见的原因，消息处理完了但没确认，会一直留在 pending 里。

Redis 挂了消息会丢吗？

分三种情况：① Pub/Sub——必丢，它本来就不落盘，连 AOF 都不写；② Stream + AOF 每秒刷盘（默认 appendfsync everysec）——最多丢 1 秒的消息；③ Stream + appendfsync always——基本不丢，但写入性能大幅下降（每次都 fsync）。另外注意主从切换：Redis 的复制是异步的，主库挂了从库可能没收到最新的写入，这部分数据会丢。所以对可靠性要求高的场景，要么用 Kafka/RocketMQ 这类有 ISR 机制的专业 MQ，要么接受「最多丢 1 秒」并做好业务层的对账补偿。

四个必须知道的坑

① 离线即丢失订阅者断开期间发布的消息不会重发，重连也拿不到。要可靠就用 Stream。
② 无 ACK 无重试Redis 只负责「尽力推一次」，客户端处理失败没有补救机制。
③ 消费慢会积压内存Redis 为每个订阅者维护输出缓冲区，慢消费者会被强制断开（client-output-buffer-limit）。
④ Cluster 下会广播PUBLISH 会在整个集群内广播一次，频道量大时网络开销可观。

深入自检

PUB/SUB 和 Stream 最本质的区别是什么？

PUB/SUB 是扇出广播，消息发出去就结束，服务端不保存；Stream 是可持久的日志，消息有 ID、可以重复读、可以分组消费。前者是「通知」，后者是「队列」。

为什么订阅了却收不到消息？

按顺序排查：① 频道名是否完全一致（大小写敏感）；② 是否用了 PSUBSCRIBE 但发布的是精确频道（反之亦然）；③ 客户端是否还在订阅态（执行命令会退出）；④ Cluster 下是否连错分片（PUB/SUB 会自动广播，但客户端连接需正常）。

订阅连接为什么会被服务端断开？

因为输出缓冲区超过 client-output-buffer-limit pubsub（默认 32MB 硬限制 / 8MB 60 秒软限制）。这通常意味着消费速度跟不上发布速度，需要优化消费逻辑而不是一味调大限制。

如何用 PUB/SUB 做「可靠一点」的广播？

常见做法是PUB/SUB 只发通知，真正的数据回源查：订阅端收到「某键已变更」后去读 Redis 或数据库拿最新值。这样即使通知丢了，最多是延迟，不会导致数据错误。

Redis 7 的 Sharded Pub/Sub 解决了什么？

Cluster 模式下普通 PUBLISH 会广播到所有节点，SSUBSCRIBE/SPUBLISH 把频道绑定到单个分片的哈希槽，减少集群内的广播风暴，代价是频道必须落在同一槽。
