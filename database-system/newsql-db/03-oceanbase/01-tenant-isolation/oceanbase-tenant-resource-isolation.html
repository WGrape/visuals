OceanBase 租户资源隔离与容量治理

从共享集群中的两个业务租户出发，理解资源单元、容量边界和“隔离”应怎样验收。

租户为何是设计起点 OceanBase 在一个集群中可承载多个租户，租户各有数据库对象、账户和资源配置。对业务来说，租户是管理、权限与资源治理的重要边界；但“多租户”不等于每个租户都有独占物理机器。若两个租户共用磁盘或网络，某些噪声仍可能通过共享基础设施传播。架构设计先写清哪些资源可共享、哪些服务等级必须隔离，再决定资源配置。

例如交易租户要求低延迟，分析租户夜间跑大查询。若只给两者同样的 CPU 配额，分析扫描仍可能挤占存储带宽和缓存。需要同时看 CPU、内存、I/O、网络、磁盘容量与副本布局。权限隔离也要独立验证，不能因为性能配额设置正确就假设账户绝不会跨租户访问。

资源单元和分布 资源单元配置描述租户在节点上可使用的 CPU、内存等资源，资源池决定单元如何分配到节点与可用区。业务容量估算不能只看总集群空闲量：某个可用区的节点若不足，目标副本可能无法满足放置约束；某个节点虽有 CPU 空闲，却可能内存或磁盘先到边界。规划副本数、故障域和未来增长时，应按最弱故障域计算冗余。

假设三可用区各有节点，交易租户要求任一可用区故障后仍能提供服务。除了日常容量，还应留出故障后剩余区域承载流量和副本恢复的空间。把所有资源用满来追求高利用率，会让故障切换和扩容同时失去缓冲。

逐步推演

定义边界

列出租户在权限、性能和恢复方面的独立要求。

规划资源

按节点、可用区与故障后的容量分配资源单元。

注入干扰

用分析扫描压测交易租户的尾延迟。

验收与调整

根据共享瓶颈调整配额、放置或集群划分。

一个邻居噪声实验 先让交易租户以固定 QPS 运行短事务，记录 P50、P95、P99、锁等待和事务冲突。然后让分析租户执行大范围扫描与排序，观察交易延迟变化，同时看节点 CPU、内存、磁盘队列和网络。若 P99 明显上升，不能只凭“租户 CPU 未超配”宣布隔离成功；应定位共享路径。可分别限制分析租户并发、调整资源单元或将其放到不同节点，比较效果。

实验要在读写混合负载下做，不能只跑纯读。扫描可能冲掉缓存，批量写入可能影响后台合并或日志复制。恢复到正常负载后还要观察延迟是否回落，判断是否有积压任务。隔离验收应给出可重复的压测配置与最大允许干扰幅度。

扩容与缩容的步骤 扩容前确认节点健康、可用区布局和资源池上限，再增加容量或调整租户配额。调整后看副本迁移、负载重新均衡、事务延迟和后台任务；短时间内指标可能波动，不能把迁移阶段当作稳态性能。缩容更危险：要先证明剩余节点可容纳副本和故障余量，防止缩容后在下一次节点故障时无处恢复。

容量规划应把业务峰值、季节增长、备份与维护窗口列入预算。CPU 使用率低也可能因内存保留、日志盘或热点分区而无法加租户。租户规格变更要有回滚计划和影响时间窗，并通知依赖方在变更期间观察响应时间。

权限与备份边界 租户内用户权限应按最小可用范围分配，备份任务、审计日志和密钥管理也要按租户明确归属。共享集群管理员可能拥有跨租户的基础设施权限，因此还需审计管理面操作。测试时用另一个租户账户尝试访问表名相同的对象，确认隔离在数据库权限和应用连接配置两层都有效。

恢复演练要验证能否只恢复目标租户或目标库，以及恢复时资源从哪里来。备份成功不等于恢复可用；要记录恢复点、恢复耗时、数据校验和连接切换步骤。若某租户数据增长过快，也不能让备份流量挤占另一个租户的业务高峰。

运维指标与决策 为每个租户建立事务延迟、吞吐、错误、锁等待、资源配额、实际使用、存储增长和后台任务的视图，并能关联到物理节点。若只展示集群平均值，低流量关键租户可能被高流量租户掩盖。为重要租户设置最低可用容量和干扰阈值，定期做邻居噪声演练。

租户是否继续共用集群应由实测业务服务等级决定。如果共享路径始终无法满足关键交易延迟，可以分集群部署；如果容量与隔离表现稳定，共享集群可降低运维成本。选择要有成本、风险和可回退路径，而不是仅凭“多租户”三个字。

一个容量决策的算例

假设交易租户平时需要 12 个 CPU 单位、故障时预计增长到 18 个；分析租户高峰需要 10 个。若剩余两个可用区在单区故障后合计只能提供 24 个单位，就算日常合计 22 个看似能放下，故障时也可能缺 4 个。规划时要用故障后的放置约束重新计算，而不是把全集群所有空闲资源简单相加。再观察日志盘、内存和网络是否也满足故障场景，找出最早触顶的资源。

给租户扩配后，应用连接池和并发上限未必自动同步调整。若数据库容量变大、应用却仍排队，业务延迟不会改善；若应用一下释放过多并发，又可能把新容量立即打满。数据库与应用的变更应联合压测并分阶段放量。

租户、资源单元与资源池

概念含义层级关系
Unit（资源单元）最小的资源配额单位：CPU + 内存 + 日志盘 + IOPS最底层
资源池（Resource Pool）由若干 Unit 组成，分布在多个 Zone（OBServer）上池 = Unit × Zone 数
租户（Tenant）逻辑数据库实例，绑定一个或多个资源池一个租户可跨多个 Zone
Zone可用区 / 故障域，通常对应一个机房或机架副本分布单位

算一下资源：创建一个 3 Zone 的租户，每个 Unit 规格为 4C8G，则该租户在每个 Zone 上占 4C8G，总共占用 12C24G（3 个 Zone × 4C8G）。很多人误以为总共只占 4C8G，导致资源超卖。

OceanBase 租户操作

-- 创建资源单元规格
CREATE RESOURCE UNIT my_unit
  MAX_CPU 4, MIN_CPU 4,
  MEMORY_SIZE '8G',
  LOG_DISK_SIZE '20G',
  MAX_IOPS 10000, MIN_IOPS 5000, IOPS_WEIGHT 10;

-- 创建资源池（3 个 Zone 各放一个 Unit）
CREATE RESOURCE POOL my_pool
  UNIT 'my_unit', UNIT_NUM 1,
  ZONE_LIST ('zone1','zone2','zone3');

-- 创建租户（MySQL 兼容模式）
CREATE TENANT IF NOT EXISTS my_tenant
  RESOURCE_POOL_LIST ('my_pool'),
  PRIMARY_ZONE 'RANDOM',
  CHARSET 'utf8mb4',
  OB_COMPATIBILITY_MODE 'mysql'
  SET ob_tcp_invited_nodes = '%';

-- 查看资源使用
SELECT * FROM oceanbase.__all_unit_config;
SELECT * FROM oceanbase.__all_resource_pool;
SELECT * FROM oceanbase.GV$OB_UNITS;
SELECT tenant_id, svr_ip, max_cpu, min_cpu, memory_size
  FROM oceanbase.__all_unit;

-- 在线调整（扩容）
ALTER RESOURCE UNIT my_unit MAX_CPU 8, MEMORY_SIZE '16G';
-- 增加 Unit 数量（水平扩展）
ALTER RESOURCE POOL my_pool UNIT_NUM 2;

隔离机制与运维要点

资源维度隔离手段说明
CPUcgroup（控制组）+ OB 内部调度MIN_CPU 是保证配额，MAX_CPU 是上限；空闲时可超用
内存严格限制（超过即报错）内存是硬限制，与 CPU 不同，不能超用
磁盘LOG_DISK_SIZE 独立配额日志盘满会导致写入失败，需监控
IOPSMIN/MAX_IOPS + IOPS_WEIGHT按权重分配，避免单租户打满磁盘
连接数/并发租户级变量（max_connections 等）防止单租户耗尽连接
大查询大查询队列与限流避免大查询拖垮整个租户
  • 内存是硬限制，CPU 是弹性限制：这是 OceanBase 与很多系统的关键差异。MEMORY_SIZE 超了会直接报 OB_TENANT_OUT_OF_MEM；而 CPU 在集群空闲时可以超过 MIN_CPU 用到 MAX_CPU。
  • Unit 数量 = 该 Zone 内的副本数：UNIT_NUM = 1 表示每个 Zone 一份资源；调大 UNIT_NUM 可以在 Zone 内做水平分片（多副本并行服务），但会成倍增加资源占用。
  • PRIMARY_ZONE 决定读写在哪里：设为 RANDOM 让主副本分散在各 Zone（负载均衡）；设为单一 Zone 则所有主副本集中（减少跨机房写入，但容灾能力下降）。
  • 多租户不等于强隔离：CPU/IOPS 是弹性共享的，一个租户跑大查询仍会挤占其它租户。真正需要强隔离时用独立集群或给关键租户设 MIN 配额。
  • 排障顺序：① 看 GV$OB_UNITS 各租户配额与实际使用；② 看是否内存打满（硬限制，最常见报错）；③ 看日志盘是否满；④ 看是否有大查询占满 CPU；⑤ 用 GV$OB_SQL_AUDIT 找慢 SQL。
  • 容量规划：总资源 = Σ(Unit × Zone 数)，规划时务必按三副本计算，且预留 30% 给合并（major compaction）等后台任务。
为什么我建了 4C8G 的租户，集群却少了 12C24G？

因为资源池分布在 3 个 Zone，每个 Zone 各占一份 Unit（4C8G × 3 = 12C24G）。这是多副本容灾的必然代价。若只有一个 Zone 或 UNIT_NUM=1 且单 Zone，才只占一份。

租户内存不够可以临时超用吗？

不可以。OceanBase 的内存是硬配额，超了直接报错。要扩容必须 ALTER RESOURCE UNIT 调整 MEMORY_SIZE（在线生效），或者清理数据/降低 memtable 占用。

自检

两个租户 CPU 配额独立，就能保证交易延迟互不影响吗？

不能。磁盘、网络、缓存和后台任务仍可能共享；应通过邻居噪声实验验证尾延迟。

练习：选一个真实业务样本，写出输入、预期结果、一次失败时的证据，以及可以复现实验的验收标准。
