RoPE 实战：base、配对方式与长上下文外推

RoPE 用一个旋转矩阵把位置信息编码进 q/k，让注意力点积只依赖相对距离。公式很短，但 base 取多少、配对方式怎么排、外推时改哪个参数，每一步都能让模型从「长文正常」变成「长文全错」。

一句话定位：按频率旋转，点积自带相对位置

q̃_m = R(mθ) q,　k̃_n = R(nθ) k　⟹　⟨q̃_m, k̃_n⟩ = f(m − n)

每个维度对用一个固定频率 θ 旋转，位置 m 的向量转 m·θ。两个不同位置的向量做点积时，绝对角度被抵消，只剩角度差 (m−n)·θ——这就是「相对位置」的来源。

是否需要参数不需要，纯运算（所以权重表里看不到它）
作用对象只作用 q 和 k，不作用 v
默认 base10000（早期）/ 500000（LLaMA-3）/ 1000000（部分长文模型）
实现位置注意力内部，q/k 投影之后、QKᵀ 之前
按频率旋转，长波长负责远距离、短波长负责局部顺序

最长波长 < 训练长度时，位置信息在高频段就「绕圈」了，远距离无法区分。判断一个模型能不能直接吃长文，先看 2π·base^((d-2)/d) 与目标长度的比值，而不是看宣传页。

三种外推方案：改位置、改 base、改频率

配对方式：相邻配对 vs 前后半配对

同一个旋转公式有两种维度排列：把 (0,1)、(2,3) 当一对（相邻，原论文实现），或把 (0,64)、(1,65) 当一对（前后半，HuggingFace 的 rotate_half）。数学等价，但要求权重按对应顺序训练。

# 前后半配对（HF 实现，主流模型权重都按这个训练） def rotate_half(x): x1, x2 = x[..., :x.shape[-1]//2], x[..., x.shape[-1]//2:] return torch.cat([-x2, x1], dim=-1) def apply_rope(q, k, cos, sin): return q*cos + rotate_half(q)*sin, k*cos + rotate_half(k)*sin
混用等于换了一个模型

用相邻配对的实现去加载按前后半训练的权重，模型还能跑、loss 也像正常，但长文与位置敏感任务会明显退化。这种错误不会报错，只会「悄悄变笨」。

原理与取舍：为什么旋转比加法好

绝对位置编码（可学习向量或正弦）需要模型自己学会「位置 A 与位置 B 的关系」，而且训练长度之外没有定义；RoPE 把相对性直接写进点积结构，模型只需学「差多少」，外推时只要调整频率分布就有机会泛化到更长。这也是它取代绝对位置编码成为主流的原因。

RoPE 为什么不作用在 v 上？

v 承载的是「内容」，位置信息已经通过 q·k 的打分进入权重；给 v 加位置反而污染内容表示。

MLA 为什么和 RoPE 冲突？

MLA 把 K 压缩成低秩 latent，而 RoPE 需要在完整 K 上做逐维旋转，两者维度不对齐。DeepSeek 的做法是解耦出一小段专门带 RoPE 的维度（64 维）单独处理。

能不能用位置编码长度直接判断能否吃长文？

不能只看 max_position_embeddings，它是训练配置；真正的有效长度要看 rope_theta、训练数据长度和是否做了长文续训。

第一层 · 概念与判定：RoPE 解决什么问题

一句话：RoPE（旋转位置编码）把绝对位置编码成「旋转」，使得注意力分数只依赖相对位置差——这样模型天然具备相对位置感知，且便于外推到更长上下文。

编码方式怎么表示位置相对位置能力外推能力
正弦位置编码（原始 Transformer）加到 token embedding 上弱（需学习）差
可学习绝对位置（BERT/GPT-2）查表得到位置向量弱不能外推（受训练长度限制）
RoPE对 Q/K 做旋转强（数学上保证）可外推（配合缩放策略）
ALiBi给注意力分数加线性偏置强好，但不主流
  • 信号一：模型要支持超过训练长度的上下文 → 必须用 RoPE 这类可外推的编码。
  • 信号二：LLaMA / Qwen / Mistral / DeepSeek 都用 RoPE。
  • 信号三：看到「上下文从 4k 扩到 128k」的方案 → 本质是 RoPE 的缩放改造。

核心直觉：RoPE 不改向量模长，只改方向。位置 m 的 query 旋转 θ·m，位置 n 的 key 旋转 θ·n，两者点积只与 (m−n) 有关——这就是相对位置的来源。

RoPE 实现与外推

import torch

def build_rope_cache(dim, max_len, base=10000.0, device='cpu'):
    # theta_i = base^(-2i/dim)，i = 0, 2, 4, ...
    inv_freq = 1.0 / (base ** (torch.arange(0, dim, 2, device=device).float() / dim))
    t = torch.arange(max_len, device=device).float()
    freqs = torch.outer(t, inv_freq)              # (max_len, dim/2)
    emb = torch.cat([freqs, freqs], dim=-1)       # (max_len, dim)
    return torch.cos(emb), torch.sin(emb)

def apply_rope(x, cos, sin):
    # x: (batch, n_head, seq, head_dim)  -> 旋转后
    def rotate_half(v):
        d = v.shape[-1] // 2
        return torch.cat([-v[..., d:], v[..., :d]], dim=-1)
    return x * cos + rotate_half(x) * sin

# 外推：把 base 调大（NTK-aware 的核心）
cos, sin = build_rope_cache(128, 32768, base=500000.0)   # 支持更长上下文

# HuggingFace 里通过 config 指定
# {"rope_theta": 10000.0, "rope_scaling": {"type": "yarn", "factor": 4.0}}

量化参考：LLaMA-1/2 训练长度 2048 / 4096、base=10000；LLaMA-3 把 base 提到 500000，配合训练长度 8192，可支持到 128k 上下文——这主要靠的就是 RoPE 参数与缩放策略的调整。

第三层 · 排障与边界：长上下文的坑

现象原因怎么查 / 怎么办
超过训练长度后效果骤降位置编码未做外推处理改用 PI / NTK / YaRN；或换长上下文模型
长文本「中间丢失」注意力稀释 + 训练分布问题属于模型能力边界；可用检索替代超长上下文
微调后长上下文能力下降微调数据太短，破坏了外推微调时混入长样本
不同框架实现不一致RoPE 的共轭/交错排布差异核对实现；HF 有统一实现
cache 长度算错KV cache 与位置编码错位确认 position_ids 正确递增
  • 排查顺序：先确认当前上下文长度是否超过模型训练长度 → 再看 config 里 rope_scaling 配没配 → 最后确认框架实现一致。
  • 边界一：RoPE 的外推不是免费的——超过训练长度仍会退化，只是退化得比绝对位置编码慢。真要长上下文通常还需微调。
  • 边界二：base 越大，低频分量越多，理论上支持越长，但位置分辨率会下降（近距离区分度变差），需要权衡。
  • 边界三：多模态 / 打包训练时 position_ids 要按样本重新编号，否则跨样本的位置会串。

RoPE 相对性自检

# 自检：验证 RoPE 的相对位置性质
# 对任意位置偏移 k，(q_m · k_n) 应只依赖 (m - n)
import torch
def rope_rotate(v, m, base=10000.0):
    d = v.shape[-1]
    inv = 1.0 / (base ** (torch.arange(0, d, 2).float() / d))
    ang = m * inv
    cos, sin = torch.cos(ang).repeat(2), torch.sin(ang).repeat(2)
    def rh(x):
        h = x.shape[-1] // 2
        return torch.cat([-x[h:], x[:h]])
    return v * cos + rh(v) * sin

q = torch.randn(64); k = torch.randn(64)
s1 = (rope_rotate(q, 5) * rope_rotate(k, 2)).sum()   # m-n = 3
s2 = (rope_rotate(q, 8) * rope_rotate(k, 5)).sum()   # m-n = 3
print(torch.allclose(s1, s2, atol=1e-5))             # True：只与相对位置有关

方法做法优点代价

为什么改 base 就等于「支持更长」？

因为 base 决定旋转角频率 θ_i = base^(-2i/d)。base 越大，频率越低、周期越长，同样的维度就能编码更长的位置而不「绕圈」混淆。直观理解：base 就是位置编码的「尺子长度」。

RoPE 和 ALiBi 怎么选？

主流大模型（LLaMA/Qwen/Mistral/DeepSeek）都用 RoPE，生态和工具链更成熟。ALiBi 在极长外推上有优势但采用率低。实际选型时跟随主流即可，除非你有明确的外推需求。

128k 上下文真的都能用满吗？

要谨慎。很多模型虽然宣称支持 128k，但在中后段的召回能力会明显下降（即「中间丢失」现象）。工程上更稳妥的做法是用检索（RAG）把相关内容放到靠前位置，而不是把 128k 全塞进去指望模型自己找。
