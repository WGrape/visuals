ulimit 命令详解

逐项讲清 ulimit -a 输出的 9 个限制，并正面回答你最关心的问题：stack size 限制的是整个进程，还是每一个线程？

一句话结论（先给答案）： ulimit 是 shell 内建命令，用来给「当前 shell 及其之后启动的子进程」设置资源使用上限。你贴的输出里 -s: stack size 8176 这个 stack size 限制的是「每一个线程」的栈，不是整个进程的栈总和——主线程有自己一个栈，每新建一个线程又各有一个栈，每个都被这个值卡住。1000 个线程就是约 1000 × 8MB 的栈空间。

1. ulimit 是什么

ulimit 是 Bash / Zsh 的内建命令（不是独立程序，which ulimit 查不到），它背后调用的是系统调用 getrlimit() / setrlimit()，用来读写一组叫 resource limit（资源限制）的内核参数。

三个关键性质

  • 作用于「进程」级别：每个限制都是针对单个进程的（或该进程内的每个线程，见第 4 节）。
  • 继承，不传染：在 shell 里执行 ulimit -s 4096 后，这个 shell 以及它之后 fork/exec 出来的所有子进程都会带上新限制；但不会影响已经存在的进程，也不会影响别的终端窗口。
  • 软限制 / 硬限制：每个资源都有 soft 和 hard 两道闸。普通进程可以把 soft 往上调到 hard 为止；要改 hard 只能由 root 操作。
# 默认显示的是「软限制」；加 -H 看硬限制，加 -S 看软限制
ulimit -s          # 看栈软限制（KB）
ulimit -Hs         # 看栈硬限制
ulimit -a          # 列出全部软限制
ulimit -aH         # 列出全部硬限制

2. 它怎么生效（软 / 硬限制）

每个资源限制其实是「软 + 硬」两道闸：

类型含义谁能改
软限制 (soft)实际生效的上限。进程可以把它调到不超过硬限制的任何值。任何进程（含你自己）
硬限制 (hard)软限制的天花板。软限制永远 ≤ 硬限制。只有 root 能往上调
直觉：软限制像「你自己定的闹钟」，硬限制像「公司规定的最晚下班时间」。你能把闹钟从 18:00 调到 21:00，但不能超过 22:00（硬限制），除非你是老板（root）。

  • -n 256 → 高并发服务（每连接一个 fd）很容易「too many open files」，这是 macOS 开发最常踩的限。

4. 核心问题：stack size 限制的是整个进程，还是每一个线程？

直接回答：是每个线程，不是整个进程。
-s 设置的是 RLIMIT_STACK。它的语义是：「进程中每一个线程（包括主线程）的栈，最大不能超过这个值」。它不是「所有线程的栈加起来」的上限。

把「进程」和「线程」分开想就清楚了：

  • 一个进程里，代码段、堆、全局变量是所有人共享的——这些用 -d(数据段)、-v(地址空间) 来限制，是「整个进程一份」。
  • 但栈是每个线程私有的——每个线程跑自己的函数调用链，如果共用一个栈，函数调用会互相踩。所以每个线程必须有自己独立的栈。
  • 于是 RLIMIT_STACK 只能按「每线程」来卡：主线程一个栈被它限制，新开的线程又各有一个栈、也被它限制。
每线程-s stack size 整个进程-d 数据段 · -v 地址空间 每线程(隐含)-u 进程/线程总数
一句话记牢：「栈」天然是线程私有的，所以凡是限制栈的，都只能是每个线程一份。被打翻的是「单个线程的栈」，不是「全公司的栈总和」。

6. 每线程栈的代价：为什么这条限制很关键

既然每个线程各占一份栈，那 -s 的大小直接决定了「一个进程最多能开多少个线程」：

估算公式

最大线程数 ≈ (可用虚拟地址空间 − 代码/数据/堆开销) ÷ 每线程栈大小

你的 -v 是 unlimited（虚拟地址空间几乎不卡），所以线程数主要被 -s 和 -u（2666）夹着。但注意：即使虚拟空间充足，每线程 8MB 也会让栈的「虚拟地址预留」快速膨胀——尤其在 32 位或地址空间紧张的环境。

100 线程
栈空间总预留 ≈ 800 MB
实战含义：
  • 写高并发服务（线程池、Go 的 CGO 线程、Java 默认 1MB 栈、Redis 的 io-threads）时，-s 越大，能开的线程越少。
  • 想开海量线程？调小 ulimit -s（比如 1024 = 1MB）能显著提上限，但递归过深或大局部数组会更容易栈溢出——这是权衡。
  • glibc 在 pthread_create 时，会按 RLIMIT_STACK 预留（reserve）虚拟地址——哪怕你没用满，那块地址也先占着。

7. 其它几个容易误解的项

-d 数据段 vs -v 地址空间（别混）

  • -d 只管「堆 + BSS」这一块，不含栈、不含 mmap。
  • -v 管「整个进程能用的虚拟内存总和」——堆、栈、mmap、动态库全算进去。通常 unlimited，一旦被设小，哪怕逻辑上内存够也会分配失败。

-u 进程数，其实「含线程」

-u 限制的是该用户的总进程数。在 Linux 上线程也是轻量级进程（LWP），会被算进去；macOS 上同样受 max user processes 约束。所以「开太多线程」也会撞 -u。它和 -s 是「线程数」这道闸的两个不同角度：-s 管每个线程吃多少栈，-u 管总共能有几个。

-c core 文件 = 0 的坑

很多线上「程序崩了却找不到原因」，就是因为 -c 0 不落 core。调试前先 ulimit -c unlimited，崩溃后就能用 lldb / gdb 打开 core 文件定位。

-f 文件大小

限制「单进程能写出的文件最大尺寸」。曾经有人导数据，文件写到 2GB 突然写不进——就是 -f 被设了上限。unlimited 就没这问题。

8. 怎么改、怎么持久化

临时改（只对当前 shell 及子进程生效）

ulimit -s 4096        # 栈限制改成 4MB/线程（软限制，不超过硬限制即可）
ulimit -n 1024        # 文件描述符改成 1024
ulimit -c unlimited    # 允许生成 core dump

看某个正在跑的进程的实际限制

# Linux / macOS 都能用
cat /proc/<pid>/limits        # Linux：逐项列出软/硬限制
prlimit --pid <pid>          # Linux：更直观
launchctl limit             # macOS：看当前 launchd 设的各类限制
持久化要分系统（你这是 macOS，别照抄 Linux 教程）：
  • Linux：改 /etc/security/limits.conf（配合 PAM），或 systemd 的 LimitNOFILE= 等服务单元指令。
  • macOS：没有 limits.conf。要用 launchctl limit <资源> <软> <硬> 设置，或写进 ~/Library/LaunchAgents/ 的 plist（如 LimitStack、LimitNumberOfFiles）让它随登录生效。
注意：ulimit 写在 .bashrc / .zshrc 里只对「交互式 shell 起的程序」有效，对由 launchd / systemd 直接拉起的服务不生效——服务要各自在它们的启动配置里设。

回到你的问题，收个尾：
ulimit -s 8176 表示「每个线程的栈最多约 8MB」。主线程占一份、每新建一个线程又各占一份，它们互不共享、各自被 8MB 卡住。所以不是「整个进程只有 8MB 栈」，而是「每个线程都有最多 8MB 的栈」——线程越多，栈占的虚拟空间越大，这也是高并发场景要权衡栈大小的根本原因。
