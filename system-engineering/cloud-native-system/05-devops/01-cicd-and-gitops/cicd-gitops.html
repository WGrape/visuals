一句话总结：DevOps 是云原生的交付支柱，目标是让变更变得频繁、可预测且安全。 CI 负责"每次提交都验证可集成"，CD 负责"把验证过的产物自动送达环境"； GitOps 则更进一步——用 Git 仓库作为系统期望状态的唯一事实源，由控制器自动把集群调谐到该状态。

01DevOps 是什么

DevOps 不是职位也不是工具，而是打破开发（Dev）与运维（Ops）割裂的一套实践与文化：

🤝 协作文化

开发对服务的全生命周期负责（you build it, you run it）， 运维能力以平台形式提供给开发自助使用。

⚙️ 自动化优先

构建、测试、部署、扩容、回滚全部自动化。 能被流水线做的事，就不该由人手工执行。

📊 度量与反馈

用 DORA 四指标衡量：部署频率、变更前置时间、 变更失败率、平均恢复时间（MTTR）。

🔁 小步快跑

把大变更拆小，每次变更风险低、易回滚。 降低单次变更的风险，比提高发布审批的严格度更有效。

02CI 与 CD 的分界

术语全称做什么关键实践
CIContinuous Integration
持续集成		 开发每次提交都自动触发构建 + 测试，尽早发现集成问题 主干开发、频繁提交、每次提交跑自动化测试、失败即修复
CD（交付）Continuous Delivery
持续交付		 保证代码随时可发布，但最终上线由人确认 部署流程自动化、环境一致、随时可产出可发布产物
CD（部署）Continuous Deployment
持续部署		 通过测试后自动上线，无需人工确认 需要强测试覆盖 + 灰度 + 自动回滚兜底
面试常问："持续交付"与"持续部署"的区别。 交付 = 随时可发（人来按按钮）；部署 = 自动发（没人按按钮）。 两者都要求流水线自动化，差别只在最后一步是否需要人工审批。

03云原生流水线的典型构成

# GitHub Actions 示例：构建镜像 → 推送 → 部署到 K8s
name: build-and-deploy
on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # ① 单元测试（CI 的核心）
      - run: npm test

      # ② 构建容器镜像（产物不可变，用 commit sha 打标签）
      - run: docker build -t registry/app:${{ github.sha }} .

      # ③ 镜像扫描（安全左移）
      - run: trivy image registry/app:${{ github.sha }}

      # ④ 推送到镜像仓库
      - run: docker push registry/app:${{ github.sha }}

      # ⑤ 更新部署清单（GitOps 模式下是改 Git 而非直接 kubectl apply）
      - run: |
          sed -i "s|image: .*|image: registry/app:${{ github.sha }}|" k8s/deploy.yaml
          git commit -am "bump image" && git push

🔒 不可变产物

镜像用 commit sha 打标签，永不覆盖。 各环境部署同一个产物，避免"测试过了但生产镜像不同"。

🧪 测试分层

单元测试（快，每次提交）→ 集成测试 → 端到端测试（慢，发布前）。 金字塔结构，越往上越少越慢。

🛡️ 安全左移

在流水线早期做依赖扫描、镜像扫描、SAST， 而不是等上线后再发现。

🔑 密钥管理

密钥不进 Git，用 K8s Secret / Vault / 云厂商 KMS； GitOps 场景下用 Sealed Secrets 或 SOPS 加密后入库。

04GitOps：以 Git 为唯一事实源

GitOps 是为云原生（尤其 K8s）量身定制的持续交付模式，四条核心原则：

  1. 声明式描述整个系统：所有环境配置都是 Git 里的 YAML/Helm/Kustomize 清单。
  2. Git 是唯一事实源：系统期望状态完全由 Git 内容决定，集群里的实际状态只是它的投影。
  3. 通过 Pull Request 变更：所有变更走评审、走 CI 校验，有完整审计记录。
  4. 软件代理自动调谐：控制器持续比对 Git 与集群，发现偏差就自动收敛（也支持自动回滚）。

05发布策略

策略做法优点代价
重建（Recreate）先停旧版本再起新版本实现最简单、无版本共存有停机时间
滚动（Rolling）逐个替换实例无停机、资源不翻倍回滚较慢；新旧短暂共存
蓝绿（Blue-Green）部署一套完整新版本，验证后切流量秒级切换与回滚需双倍资源
金丝雀（Canary）先放少量真实流量到新版本，按指标逐步放大风险最低，指标驱动实现最复杂，需流量治理
A/B 测试按用户属性分流对比可做业务效果对比偏产品实验而非发布
选型建议：无状态小服务用滚动即可； 核心大版本用蓝绿保证可秒退； 高频且风险敏感的服务上金丝雀（配合 Prometheus 指标自动判定是否继续放量—— 这叫 Progressive Delivery，可用 Argo Rollouts / Flagger 实现）。

06常见疑问

Q：GitOps 和传统 CI/CD 是替代关系吗？
A：不是，通常组合使用。典型分工是—— CI（Jenkins/GitLab CI/GitHub Actions）负责拉代码、跑测试、构建镜像、推送仓库； GitOps 工具（ArgoCD/Flux）负责监听镜像标签变更、更新清单、把集群调谐到期望状态。 流水线不直接操作集群，这是 GitOps 的关键边界。
Q：GitOps 里密钥怎么处理？
A：密钥不能明文进 Git。常见方案有三种：
① Sealed Secrets：用集群公钥加密后密文可安全入库，只有集群能解；
② SOPS：用 KMS/GPG 加密清单文件；
③ External Secrets Operator：Git 里只存引用，实际值从 Vault/云 KMS 拉取。
第三种最符合"密钥不入库"的最佳实践。
Q：为什么强调"不可变镜像 + 用 sha 打标签"？
A：如果用 :latest 这类可变标签， "测试环境验证通过的镜像"和"生产实际拉取的镜像"可能不是同一个， 且出事后无法精确追溯与回滚。用 commit sha 打标签能保证各环境产物完全一致、可精确回滚。
