数据分片与分区

当单库单表撑不住时，要把数据水平拆到多台机器。怎么拆、按什么拆、拆完怎么再平衡，决定了系统的扩展天花板。

什么是分片 四种分片策略 分片键怎么选 热点与倾斜 再平衡 面试要点

🧩 一、什么是分片（Sharding / Partition）

把一张大表按某种规则切成多份，每份叫一个分片（shard / partition），分布到不同节点。每个节点只负责一部分数据，整体突破单机容量与性能上限。

💡
垂直拆分 vs 水平拆分：垂直拆分是按"列/业务"分库（用户库、订单库）；水平拆分（即分片）是按"行"把同一张表的数据分散到多机。面试里说的"分库分表"通常指水平分片。
分片的核心目标：① 突破单机存储上限；② 突破单机算力上限（查询/写入并行）；③ 故障隔离（一个分片挂不影响全局）。

🗺️ 二、四种分片策略

策略规则优点缺点适用
范围分片按 key 区间切（如 user_id 0–1kw）范围查询快、易扩展易热点（最新区间最忙）时序/日志、按时间
哈希分片hash(key) % N分布均匀、无热点范围查询需扫多分片通用 KV、用户数据
列表/枚举按枚举值定向（地区/租户）业务语义清晰易不均、需人工规划多租户、地域隔离
地理分片按地理位置就近降低延迟跨区查询复杂全球化部署
🔗
与一致性哈希的关系：哈希分片的"节点增减"痛点，正是一致性哈希要解决的。生产上常用"固定槽位（如 Redis 16384 slot）"替代裸取模。

🔑 三、分片键（Shard Key）怎么选

分片键选错，再好的策略也救不回来。它决定数据分布、查询路由和扩展能力。

高基数（取值多）
基数太低（如"性别"只有 2 个值）会导致分片极少、无法打散。优先选 user_id、order_id 这类高基数字段。
查询高频携带
大部分查询都应带上分片键，否则要"广播"到所有分片再聚合，丧失分片意义。
避免单调递增
用自增 ID 做范围分片会产生"永远写最后一单片"的热点；可用雪花 ID（见分布式ID）或哈希打散。
尽量不变
分片键一旦写入不宜变更，否则要跨分片迁移整行数据。

🔥 四、热点与数据倾斜

即使选了哈希，也可能因"某 key 被疯狂访问"（如爆款商品、大 V 用户）造成单分片热点。

⚠️
常见解法：① 热点 key 加随机后缀（写时分散、读时聚合）；② 本地缓存 + 限流；③ 对超热 key 单独复制多副本做读负载均衡；④ 提前做数据预判与预分片。

⚖️ 五、再平衡（Rebalancing）

集群扩缩容、节点上下线时，要把分片重新分布到新拓扑上，这个过程叫再平衡。目标是：迁移量最小、不停服、不丢数据。

再平衡三原则
① 尽量均匀：各节点承载相近分片数；② 最小化迁移：借助一致性哈希/槽位，只动必要分片；③ 自动化且可回滚：多数系统（Kafka/Cassandra）由控制器自动调度，迁移按"先复制再切换"保证安全。

🎯 六、面试高频追问

分库分表后，跨分片查询/事务怎么办？
聚合查询靠中间件（如 ShardingSphere）并行查各分片再汇总；跨分片事务用分布式事务（TCC/Saga/消息最终一致）兜底，尽量避免。
分片数和节点数一定要相等吗？
不一定。常见做法是"分片数 > 节点数"，一个节点承载多个分片，扩节点时只需把部分分片搬过去，调度更灵活（Kafka 的 partition 即如此）。
分片键和唯一 ID 的关系？
全局唯一且最好带分片信息的 ID 能简化路由。例如把分片号编入 ID 高位，或通过 ID 反查分片，避免额外查路由表。

延伸阅读：一致性哈希 · 数据复制 · 分布式ID生成

第一层 · 概念与判定

分片（Sharding）把数据按分片键水平切到多节点，突破单库容量与连接上限；与「分区（单实例内切表）」不同，分片跨实例。

  • 水平分片：按行切，结构相同；垂直分片：按列/业务切，结构不同。
  • 路由方式决定「给定一个 key 怎么找到它所在的节点」。
  • 判定：单表 > 千万行或单实例写入/连接成瓶颈 → 考虑水平分片。

第二层 · 参数·命令·量化

三种路由策略对比：

策略定位方式扩容代价
哈希取模hash(key) % NN 变化需全量重分布
范围分片key 落在 [a,b)易热点，但扩容友好
一致性哈希环上顺时针找节点节点增减只迁移相邻数据

第三层 · 排障与边界

  • 热点分片：某 key 或范围被集中访问；换高基数的分片键或对该 key 做二级打散（salted）。
  • 跨分片 JOIN / 分布式事务：单分片事务简单，跨片需用 2PC/Saga，代价陡增；尽量让查询命中单分片。
  • 扩容再平衡：取模分片扩 N 几乎全量迁移；一致性哈希或按目录（shard map）路由可局部迁移。
  • 全局唯一 ID：自增主键跨片冲突；改用 Snowflake/号段/UUID。

第四层 · 原理与取舍

哈希分片写分布最均匀但扩容迁移量大；范围分片扩容易、易做区间扫描但易热点；一致性哈希在节点增减时只迁移少量数据，并用虚拟节点抹平倾斜。本质是「写入均匀性 / 扩容迁移量 / 查询局部性」三角权衡。

分片键怎么选才不踩坑？

选查询最频繁带的、基数高、分布均匀的字段（如 user_id）；避免低基数或单调递增（时间戳）导致热点。

跨分片聚合怎么办？

把聚合下推到各分片并行算，再在中间件层合并；或预计算宽表/汇总表，避免运行时跨片。

核心速览

分片是什么把一张大表按规则拆到多个库/表每台机器只承担一部分数据与流量
和分区的区别分区在本机，分片跨机器分区解决单表太大，分片解决单机不够
最关键决策分片键怎么选决定了路由、扩容与跨片查询的难度
最大代价跨片操作变难跨片 JOIN、事务、排序都要在应用层做

垂直拆与水平拆

先垂直按业务拆，再水平按数据分片，最后给每个分片加副本

分片键怎么选

候选分片键优点缺点适合
用户 ID同一用户数据集中，查询基本单库大客户会造成热点SaaS、C 端业务（最常用）
订单 ID / 业务主键分布均匀按用户查要跨片订单、日志类
时间天然冷热分离，归档方便写入集中在最新分片时序、流水、日志
地域就近访问，符合合规分布可能不均多地部署业务
一致性哈希扩容只迁移少量数据范围查询困难缓存、KV 存储

三种路由方式

① 范围路由按 ID 区间（如 1-1000万 → 分片1）。范围查询友好，但容易热点。
② 哈希路由hash(key) % N，分布最均匀，但扩容需要大量迁移（可用一致性哈希缓解）。
③ 查表路由维护一张「键 → 分片」的映射表，最灵活，可随时调整，代价是多一次查询。

扩容：为什么要预分片

方案 A：直接翻倍（2 -> 4 片） hash(id) % 2 -> hash(id) % 4 数据迁移量约 50%，且迁移期间一致性难保证 方案 B：一致性哈希 把节点和数据都映射到哈希环，扩容时只迁移相邻区间的数据 迁移量约 1/N，但范围查询与热点倾斜需要额外处理 方案 C：预分片（推荐） 一开始就逻辑上分 1024 片，物理上只开 8 台 扩容 = 把逻辑片从旧机器搬到新机器，<b>路由规则不变</b> 代价：前期设计复杂，但长期最省心

深入自检

什么时候才该分片？

优先级应该是：索引与 SQL 优化 → 缓存 → 读写分离 → 垂直拆分 → 最后才是水平分片。分片会显著提升系统复杂度，单机扛得住就别分。

分片键选错了能改吗？

能，但很痛。通常做法是双写迁移：同时按新旧两个键写两份，回填历史数据，校验一致后切读，最后下线旧键。周期长、风险高，所以选型阶段要多花时间。

如何处理热点用户？

几种办法：① 对热点用户单独一个分片或单独库；② 在分片键上加盐（如 user_id + 后缀）打散，代价是按 user_id 查要合并多片；③ 热点数据走缓存，减少直接打库。

分库还是分表？

分表解决单表数据量过大（索引深度、DDL 慢），仍在同一个实例，不解决 IO/CPU 瓶颈；分库把压力分散到不同机器，解决连接数、IO、CPU 瓶颈。通常先分表，压力真的大了再分库。

分片后怎么做全局统计？

两条路：① 各片并行算再汇总（适合可并行的聚合）；② 建独立的分析链路，把数据同步到数仓/OLAP（ClickHouse、Doris）里做统计，这是更推荐的做法，避免统计查询影响在线库。
