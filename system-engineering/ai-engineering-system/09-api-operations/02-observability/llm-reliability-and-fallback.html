LLM 稳定性：失败、重试与降级

把「内容被安全策略拦截」当网络错误去重试，只会烧钱并放大延迟。这一篇先盘清八种失败模式与各自的正确处理，再给出重试预算、四层降级路径与熔断隔离的落地方式。

1. 先把失败模式盘清楚

LLM 调用的失败比普通 HTTP 调用多出好几种，且处理方式完全不同—— 把「内容被安全策略拦截」当成网络错误去重试，只会浪费额度并放大延迟。

失败模式表现可否重试正确处理
超时超过 deadline 无响应可以（有预算）受控重试 + 降级到更快模型
限流 429Provider 返回限流可以（按 Retry-After）退避重试，重试预算耗尽后降级
服务端 5xxProvider 故障可以跨可用区/跨 Provider 重试
上下文超长输入超过窗口不可提前截断或摘要，压缩后重发
内容违规被安全策略拦截不可直接返回预设话术，记录审计
输出截断达到 max_tokens不可（原样重试无效）提高上限，或要求更简短输出
格式错误JSON 解析失败可（一次）带错误反馈重试一次，仍失败则降级为文本
可重试与不可重试必须分开。 超时/5xx/限流可以重试；参数非法、内容违规、上下文超长属于确定性失败，重试一万次结果一样， 只会白白烧钱并延迟报错。

2. 超时与重试预算

LLM 请求耗时跨度极大（几百毫秒到几十秒），超时设置不能照搬普通接口。 同时，重试必须有预算——无预算重试是雪崩放大器。

  1. 按场景分层设置 — 交互式对话 TTFT 目标 1–2 s；离线批处理可以放宽到分钟级，追求吞吐。
  2. 设置 deadline 而非固定超时 — 用剩余时间预算传递到下游，避免在已超时的请求上继续消耗。
  3. 重试预算封顶 — 重试请求占比设上限，超了就直接降级，防止重试风暴。
  4. 记录重试原因 — 按错误类型统计重试率，429 占比突增说明容量规划有问题，不是重试配置的问题。

重试策略三要素：指数退避 + 抖动（避免同步重试风暴）、重试预算 （例如重试量不超过总请求量的 10%）、只在可重试错误上重试。 三者缺一，重试就从保护机制变成故障放大器。

流式接口要单独处理超时。 流式响应已经开始返回内容后再超时，已经生成的部分通常仍然计费。 所以需要区分"首字超时"（整体放弃）和"流式中断"（已产出内容仍可用，降级返回）。

3. 模型路由与降级

降级的本质是用质量换可用性。设计时要提前定义清楚： 什么条件下切、切到什么、切了之后质量损失可接受吗。

降级层级触发条件降级动作
同模型换规格延迟超阈值切到同系列更快/更短的规格
跨模型降级主模型不可用或配额耗尽切到备用小模型，提示词同步简化
能力降级所有模型不可用返回缓存结果 / 规则兜底 / 转为人工
功能降级整体容量不足关闭非核心功能，保住核心链路（brownout）
降级也要可观测。 给每次响应打上"是否降级、降级原因、降级前后模型"三个标签， 否则当质量投诉出现时，你无法判断是模型问题还是降级导致的。

4. 熔断与隔离

熔断解决的是「下游已经不行了，别再打了」。在 LLM 场景还要额外做租户隔离—— 一个租户把额度打满，不能影响其他所有租户。

  1. 熔断触发 — 连续失败率或 429 率超过阈值，持续 N 秒后打开熔断器。
  2. 半开探测 — 熔断后按间隔放少量请求探测，成功则关闭，失败则继续熔断。
  3. 隔离舱 — 按 Provider / 模型 / 租户划分独立的连接池与信号量，避免一处故障拖垮全部。
  4. 优雅返回 — 熔断期间返回明确的可理解响应（含预计恢复提示），而不是空白或超时。

租户隔离的三个层次：配额隔离（每租户独立配额）、 队列隔离（防止单租户占满排队位）、并发隔离（限制单租户同时在途请求数）。 只做配额不做并发隔离，仍可能出现单租户用大量长请求堵死队列。

5. 落地清单

  • 失败模式已分类，可重试与不可重试分开处理
  • 超时按场景分层，流式与非流式分别处理
  • 重试有预算上限、有退避抖动、有原因统计
  • 降级路径已定义并经过演练（含「所有模型不可用」的最后一档）
  • 每次响应带「是否降级 / 原因 / 前后模型」标签
  • 熔断器有半开探测，且不会永久卡死
  • 租户级配额、队列、并发三重隔离已生效

稳定性的分水岭在于：是否把「LLM 不可用」当成一种正常的系统状态来设计，而不是当成永远不会发生的意外。

失败类型与可重试性判断

不是所有失败都该重试。判断标准是：重试有没有可能成功以及重试会不会造成副作用。

失败HTTP / 表现可重试？策略
限流429 + Retry-After 头是遵守 Retry-After；无则指数退避
服务端错误500 / 502 / 503 / 504是退避重试，最多 2~3 次
超时客户端超时谨慎可重试但要设幂等键；否则可能产生重复
上下文超长400 context_length_exceeded否（重试必失败）截断/压缩上下文后再试
参数错误400 invalid_request否修参数，重试无意义
鉴权失败401 / 403否刷新凭据，重试无意义
内容过滤400 content_filter否（重试必失败且浪费钱）改 prompt 或走降级
输出截断finish_reason=length是（续写）用 continuation 再请求一次
格式不合法JSON 解析失败是（受限）带错误信息重试 1 次（自我修复）

重试实现

import random, time

RETRYABLE = {429, 500, 502, 503, 504}

def call_with_retry(fn, max_retries=3, base=0.5, cap=8.0):
    last = None
    for i in range(max_retries + 1):
        try:
            return fn()
        except LLMError as e:
            last = e
            if e.status not in RETRYABLE or i == max_retries:
                raise
            # 指数退避 + 全抖动（full jitter，避免重试风暴）
            delay = min(cap, base * 2 ** i)
            delay = random.uniform(0, delay)     # 关键：加抖动
            time.sleep(delay)
    raise last

# 超时预算（一个可套的分配）
#   总预算 30s：
#     第 1 次  10s
#     第 2 次  10s + 退避 1s
#     第 3 次  10s + 退避 2s
#   注意：重试会<b>放大</b>延迟，别让重试把总耗时拖到用户不可接受

两个必做项：① 全抖动（full jitter）——不抖动会让所有客户端在同一刻重试，形成重试风暴把下游彻底打垮；② 重试预算——重试次数 × 单次超时要小于用户可接受的等待时间，否则「提高了成功率但用户早跑了」。常见配置：最多 2 次重试、单次超时 10~30s。

降级策略与可观测指标

降级层级触发条件降级到什么
同模型重试偶发 5xx / 超时换个区域/接入点重试
模型降级主模型连续失败或限流切到更小的模型（如 GPT-4 → GPT-4o-mini），质量降但可用
参数降级延迟过高降 max_tokens、关掉 stream、减 n
能力降级模型完全不可用走规则/模板/缓存答案；或返回「稍后再试」
缓存兜底任何失败且有过历史答案返回语义缓存里的最近一次结果（带过期标记）

降级链与指标

# 多模型 Fallback 链（伪代码）
CHAIN = [
    ("gpt-4o",   {"timeout": 20, "retries": 1}),
    ("gpt-4o-mini", {"timeout": 10, "retries": 1}),
    ("local-qwen",  {"timeout": 15, "retries": 0}),
]

def robust_call(prompt):
    for name, cfg in CHAIN:
        try:
            return call(name, prompt, **cfg)      # 每个模型内部自带重试
        except LLMError as e:
            metrics.inc("llm.fallback", tags={"from": name, "reason": e.kind})
            continue
    return cached_or_degraded(prompt)             # 最后兜底

# 必须埋的指标
#   llm.request.count            (tag: model, status)
#   llm.latency.histogram        (分 TTFT 和总耗时两个)
#   llm.tokens.prompt/completion
#   llm.error.rate               (按 error type 分)
#   llm.retry.count  / llm.fallback.count   <- 最关键：反映实际不稳
#   llm.cost.cumulative
  • 熔断：连续失败 N 次（如 10 次）就熔断该模型 30~60 秒，直接走降级，不再浪费时间等超时。这是降级链能生效的前提——否则每次都要等满超时。
  • 幂等键：给每个请求生成 request_id 传给服务端（部分厂商支持），这样重试不会产生重复扣费或重复副作用。
  • 超时要分两段：连接超时（2~5s）和读取超时（20~60s）。流式响应尤其要注意——首个 token 之前用短超时（如 10s），首 token 之后可以放宽（因为已经在稳定输出了）。
  • 记录原始请求：把完整 request/response（脱敏后）落日志，否则线上出问题完全无法复现。这是 LLM 应用排障最重要的一条基础设施。
重试次数设多少合适？

通常 2 次重试（共 3 次尝试）。再多收益递减：如果 3 次都失败，说明是持续性问题（服务真的挂了/真的限流了），再试只会拖长用户等待。更聪明的做法是重试预算：把重试次数换成「总时间预算」，在时间预算内重试，超了就降级。

流式响应中途断了怎么办？

分两种：① 还没收到首 token——当普通失败处理，可重试（成本低）；② 已经收到部分内容——重试会重复生成（浪费钱且用户看到重复）。实践做法：保留已收到的部分，用 continuation 提示模型接着写，或直接把已有内容返回给用户并标记为「可能不完整」。所以流式请求要单独记「已产出 token 数」这个指标。

怎么判断是模型问题还是我们的问题？

看三个指标：① 错误类型分布——429 是我们的配额/速率问题，5xx 是厂商问题，400 是我们参数问题；② 错误是否集中——集中在某个时间段多为厂商故障，集中在某个接口多为我们的代码；③ 对比基线——用固定的健康检查请求（每 5 分钟一次简单 prompt）做基准，把「我们的波动」和「厂商的波动」分开。
