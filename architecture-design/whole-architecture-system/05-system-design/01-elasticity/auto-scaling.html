弹性伸缩

按负载自动增减资源，闲时省钱、峰时顶得住。

伸缩类型 Auto Scaling

云的核心卖点之一就是『按需』

水平伸缩：增减实例数（主流，无状态前提）；垂直伸缩：给实例升配（有上限、需重启）。触发基于指标（CPU、QPS、队列长度、自定义），通常由 HPA/KEDA 之类控制器执行。

伸缩的前提

  • 无状态：实例可随时增删（见 12-Factor）。
  • 快速启动：镜像小、初始化快，才能跟得上流量。
  • 缩容保护：优雅退出、 draining 连接，避免误杀在途请求。

注意

  • 伸缩有冷却期，突发流量可能来不及，需预留缓冲容量。
  • 震荡(频繁伸缩)要用稳定窗口抑制。

面试高频问答

Q：水平伸缩和垂直伸缩怎么选？
A：优先水平：无上限、高可用、契合云。垂直仅适合无法拆分的单体或数据库，且受单机规格封顶。
Q：为什么弹性伸缩要求无状态？
A：因为缩容会随机杀掉实例，若实例内存里存了会话/状态就会丢；状态外移到共享存储(数据库/Redis)后，任何实例都能接手。

弹性伸缩：让容量跟着负载走

弹性伸缩解决的是「峰值按最大容量备、平时又浪费」的矛盾。它的核心是一个闭环：采集指标 → 判断是否越界 → 触发扩缩 → 等待冷却 → 再采集。理解这个闭环，就理解了所有弹性系统的设计。

弹性伸缩闭环：采集 → 判定 → 执行 → 冷却

两种伸缩方向

维度垂直伸缩 Scale Up水平伸缩 Scale Out
做法换更大的机器（加 CPU、内存）加更多实例（机器数 ×N）
上限有物理上限，单机规格封顶理论无上限，受限于数据库、许可、网络
停机通常需要重启 / 迁移，有中断无中断，滚动替换即可
应用改造无需改造要求应用无状态（会话外置、文件外置）
成本模型单机成本超线性增长（高端机溢价）线性，且可用竞价实例大幅降本
适用数据库主节点、有状态服务、短期救急Web/API 服务、无状态计算、批处理 Worker

水平伸缩的前提是「无状态」。必须先做三件事：会话外置到 Redis、本地文件外置到对象存储、定时任务加分布式锁或独立部署。否则扩出来的实例会各自为政，出现登录态丢失、文件找不到、定时任务重复执行。

伸缩策略：反应式 vs 预测式 vs 定时

反应式（指标触发，最常用）

设定阈值与持续时长，越界即触发。云厂商的 Target Tracking 就是典型。

  • 关键参数：阈值、连续次数、步长、冷却时间
  • CPU 是通用但不精确的信号；更贴近业务的是 QPS per 实例、队列积压长度、RT P99
  • 注意：扩容后指标回落需要时间，冷却期太短会「扩过头」

预测式（提前扩容）

基于历史周期性规律（每天 9 点、每周一、大促）提前扩容。

  • 解决「扩容滞后」——新实例启动 + 预热可能要几分钟，指标触发时已经晚了
  • 适合规律明显的业务；突发流量仍要靠反应式兜底

定时 / 事件驱动

已知时间点直接调整容量，最简单也最可靠。

  • 大促前 1 小时手动或脚本扩容到 N 台，结束后缩回
  • 与 CI/CD、发布系统联动：发布期间临时扩容，发布完缩回

扩容的隐藏时间成本

很多人以为「触发扩容 = 立刻有容量」，实际上从触发到新实例真正能接流量，可能要 3~10 分钟。这段时间就是结构性风险窗口，必须靠「提前量」或「预留缓冲」来覆盖。

① 调度 & 拉起云厂商分配宿主机、启动 VM/容器：30s ~ 3min
② 镜像拉取容器镜像越大越慢，1GB 镜像冷启动可达数分钟
③ 应用启动JVM/框架初始化、配置加载：30s ~ 2min
④ 预热JIT 编译、连接池建立、本地缓存填充：1 ~ 5min
⑤ 注册生效注册中心 + 负载均衡 + 健康检查通过：10s ~ 1min

降低启动耗时的手段：精简镜像（减小体积、分层复用）、常驻预热池（保持一批已就绪实例待命）、就绪探针必须真实（不能只检查端口通）、以及预留 20%~30% 的空闲缓冲——永远不要跑在 100% 水位上。

常见故障模式

  • 扩缩抖动（Thrashing）。在阈值附近反复扩容缩容。对策：扩缩使用不同阈值（滞回区间），并设足够长的冷却与缩容冷却时间。
  • 扩容了但还是扛不住。瓶颈不在应用层而在下游：数据库连接池被打满、Redis 单分片热点、消息队列消费能力不足。扩容前先画全链路，确认瓶颈位置。
  • 缩容导致请求失败。直接杀实例会中断进行中的请求。必须先从负载均衡摘除 → 等待优雅关闭（graceful shutdown，处理完存量请求）→ 再销毁。
  • 有状态服务被误扩缩。带本地状态、持有分布式锁、运行定时任务的实例不能随意增减。要么改造为无状态，要么排除出伸缩组。
  • 成本失控。只设了扩容没设上限。必须配置实例数上下限（min/max），并对预算做告警。

深入自检

为什么缩容要比扩容保守得多？

缩容的代价是非对称的。扩容多了只是多花点钱，业务无感；缩容多了会直接导致容量不足、请求失败，影响用户体验甚至造成资损。而且扩容有滞后性（新实例启动慢），一旦缩过头再想扩回来，中间那段窗口就是真实故障。所以实践上：扩容用较短的持续时长（1 分钟内）+ 较大步长，缩容用较长的持续时长（10 分钟以上）+ 最小步长（一次一台）。

用 CPU 做伸缩指标有什么问题？

CPU 是间接指标，未必反映真实压力：IO 密集型服务 CPU 很低但已饱和；JVM 应用 GC 时 CPU 高但可能是回收而非负载；异步服务可能 CPU 不高但队列已经堆积。更好的指标是「饱和度」类的直接信号：请求排队时长、队列积压长度、单实例 QPS vs 压测容量、RT P99。最稳妥是多指标组合，任一触发即扩容，全部满足才缩容。

数据库能自动伸缩吗？

比无状态服务难得多。垂直伸缩（升规格）通常要主从切换，有短暂中断；水平伸缩（加只读副本）只解决读，不解决写。常见做法：读副本做自动伸缩（因为只读节点无状态、可随时增删），写节点靠预留规格 + 人工评估扩容。真正需要写扩展时，应该考虑分库分表或分布式数据库，而不是指望自动伸缩。

优雅关闭具体要做哪些事？

按顺序：① 从注册中心/负载均衡摘除自己，不再接新流量；② 等待存量请求处理完（设超时上限，如 30s）；③ 关闭入口端口但仍保持已有连接；④ 释放资源——提交或回滚事务、归还连接池、上报未完成的指标与日志、释放分布式锁；⑤ 通知编排系统可以销毁。Kubernetes 的 preStop hook + terminationGracePeriodSeconds 就是干这个的。
