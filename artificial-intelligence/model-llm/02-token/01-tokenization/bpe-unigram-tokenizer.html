BPE 与 Unigram：Tokenizer 如何构造词表

从一份小语料推演子词词表的形成，理解词表大小、未知词处理与模型成本之间的关系。

为什么不直接按字或按词切分

按完整词建词表会遇到新词、专名和拼写变化，词表也会快速膨胀；按单字或字节虽然覆盖稳定，但常见词需要更多 token，序列更长。子词方法在两者之间选择：高频片段合成较大单位，低频片段退回较小单位。模型看到的是 token ID 序列，不是原文字符本身；相同文字在不同 tokenizer 下可能产生不同长度和不同边界。

分词流程通常还包括 Unicode 规范化、预分词、特殊符号处理和字节编码。训练词表时使用的规范化规则必须与推理时一致。若训练时把大小写合并、上线时却保留大小写，实际 token 分布会改变。特殊 token 如句首、消息边界和工具分隔符有独立语义，不能当作普通文本片段随意拼接。

逐步推演

建立最小单位

先确定字符、字节或预分词片段，确保输入覆盖与规范化规则一致。

统计并合并

在玩具语料中统计相邻片段频次，BPE 按频次选择合并并更新序列。

控制词表规模

比较合并后平均序列长度与嵌入矩阵大小，避免只优化单一语言。

上线验证

用真实语料测 token 长度、往返解码和特殊 token 边界。

用玩具语料理解 BPE 合并

假设初始单位是字符，语料里“low”出现很多次，“lower”出现较少。BPE 统计相邻单位对的频次，选最高频的一对合并成新单位，然后重新统计并重复，直到达到预定词表大小。若先合并 l+o 为 lo，再合并 lo+w 为 low，之后单词 lower 可被切成 low 与 er。这里的顺序只是演示，真实合并次序由整个训练语料的频次决定。

词表太小，常见短语也被切成多个 token，输入输出变长；词表太大，嵌入矩阵和输出层更大，稀有 token 的训练样本可能不足。词表大小是覆盖率、序列长度、模型参数与多语言公平性的取舍。对中文、代码、表情和混合脚本，不能用英文词长经验估算 token 数；应直接运行目标模型的 tokenizer。

路线构造思想典型边界
字/字节最小单位直接编码覆盖稳定，序列可能较长
BPE反复合并高频相邻片段合并顺序依训练语料
Unigram从候选子词中删减，寻找较优分段依概率模型和目标函数
完整词每个词单独入表新词与词表膨胀问题突出

Unigram 与 BPE 的不同问题

Unigram 通常先准备较大的候选子词集合，再估计子词概率，删除对语料似然贡献较小的候选，直到达到目标词表规模。分词时可寻找概率较高的片段组合。BPE 的核心是按合并规则逐步形成词表，两者都能得到子词单位，却不保证同一句话切出相同边界。也不能只凭某个例子断定哪一种始终更省 token；语言分布、预处理和词表预算都会改变结果。

未知词处理依具体实现而异。字节级设计可把任意 UTF-8 文本退回字节表示，避免传统意义上的未知 token；其他设计需要字符覆盖或未知符号。编码和解码还必须验证往返：对正常用户输入、换行、组合字符和 emoji，编码再解码是否得到预期文本。可逆性、规范化和特殊 token 转义是接口契约的一部分。

工程验收与常见误判

  1. 固定 tokenizer 版本和词表文件，测中文、英文、代码、日志、表格和混合输入的 token 长度分布。
  2. 比较新增业务术语前后 token 切分；只追求少几个 token，可能破坏旧文本兼容性或导致模型嵌入不匹配。
  3. 验证特殊 token 不会被用户文本意外构造为控制边界；对外展示 token 数量时使用实际编码结果。
  4. 修改 tokenizer 通常涉及模型嵌入层与训练分布，不能仅替换线上分词文件就期待模型保持行为。

练习：两个接口都宣称支持“128K 上下文”，同一文档在模型 A 中是 80K token，在模型 B 中是 110K token。解释为什么字符数相同而余量不同，并说明应如何为检索分块设置安全余量。

词表更新与兼容性

Tokenizer 是模型训练产物的一部分。同一个 token ID 在新旧词表中若代表不同片段，模型嵌入矩阵中对应行的含义就会错位；即使旧 ID 保留，新增 token 的嵌入也需要训练。生产系统应将 tokenizer 文件、特殊 token 映射和模型权重按同一版本发布，并在缓存键中包含版本。缓存旧 token ID 序列再喂给新模型，可能产生不可解释的输出。

评估词表时不要只报英文语料的平均 token 数。对于中文、阿拉伯文、代码和 emoji，应分别看 P50/P95 的切分长度与异常长片段。对检索应用尤其重要：文档分块按字符数切，模型实际按 token 数截断，可能恰好丢掉引文末尾的限定条件。较稳妥的做法是用目标 tokenizer 计算 chunk 上限，并留出系统提示、工具描述和模型回复的空间。

BPE vs Unigram vs WordPiece：机制差别

算法训练方式合并/选择准则特点

BPE 核心实现

# 从零实现 BPE（核心逻辑，理解原理）
from collections import Counter

def train_bpe(corpus, vocab_size=1000):
    # ① 初始化：按字符切分，词尾加 </w> 标记
    vocab = Counter()
    for word, freq in corpus.items():
        vocab[tuple(word) + ('</w>',)] += freq

    merges = []
    while count_tokens(vocab) < vocab_size:
        # ② 统计所有相邻对的频次
        pairs = Counter()
        for token, freq in vocab.items():
            for i in range(len(token) - 1):
                pairs[(token[i], token[i+1])] += freq
        if not pairs: break
        # ③ 合并频次最高的一对
        best = max(pairs, key=pairs.get)
        merges.append(best)
        # ④ 应用合并到整个词表
        vocab = apply_merge(vocab, best)
    return merges

# 关键细节：合并次数 = 目标词表大小 - 初始字符数
#   例：初始 256 个字节 + 50000 次合并 = 50256 个 token
#   GPT-2 是 50257，多出的是特殊 token

# 编码（推理时）：按 merges 的先后顺序依次应用
def encode(word, merges):
    token = tuple(word) + ('</w>',)
    for a, b in merges:
        token = merge_pair(token, a, b)
    return token

# Unigram 的关键差别：保留概率，可做多种切分采样
#   例："unhappiness" 可切为 ["un","happi","ness"] 或 ["un","happy","ness"]
#   Unigram 按概率采样其中一种 -> 天然的数据增强（BPE 的切分是确定的）

为什么中文更费 token：主流词表基于英文语料训练，对中文覆盖差，很多汉字被拆成多个 UTF-8 字节级 token（一个汉字 3 字节，可能占 2 – 3 个 token）。这也是国内模型（Qwen、DeepSeek、GLM）专门扩充中文词表的原因——Qwen2 的 151936 词表中中文占比高，同样中文文本的 token 数比 Llama 少 20 – 40%。

深入自检

为什么要分词而不是用字符或整词？

三个权衡：① 整词——词表爆炸（百万级）、无法处理未登录词、形态变化（run/running/ran）要分别学；② 字符——词表小（几百），但序列长度暴涨（一个 10 字母的词要 10 个 token），注意力 O(N²) 承受不起，且语义单元太碎难学；③ 子词（BPE）——取中间：常见词整词一个 token、罕见词拆子词、新词可组合。这就是所有现代 LLM 都用子词分词的原因。

词表越大越好吗？

不是单调的。收益：token 数减少；代价：① embedding 层参数变大（128k × 4096 ≈ 5 亿参数，占小模型很大比重）；② 低频 token 学不好；③ 输出层 softmax 变慢（要对 128k 个 logits 归一化）。甜点区在 3 万 – 15 万之间，取决于模型规模和语料语言分布。

Unigram 相比 BPE 有什么实际优势？

两个：① 可做切分采样——Unigram 保留概率模型，训练时按概率随机采样不同切分，相当于免费的数据增强，提升鲁棒性（BPE 的切分是确定的，做不到）；② 可给出切分概率便于置信度分析。代价是实现更复杂、训练更慢。追求简单选 BPE，追求效果选 Unigram。

怎么处理多语言分词？

三种思路：① 统一大词表——多语言语料混合训练 BPE（如 mT5，词表 25 万），简单但每种语言的压缩率都被稀释；② 语言专属词表 + 路由——复杂但高效；③ 字节级模型（ByT5、Megabyte）——完全不需要分词器，天然支持所有语言且无 OOV，代价是序列长度增加 3 – 5 倍。目前主流还是 ①，字节级是研究热点但尚未大规模落地。

自检

BPE 每次合并最高频字符对，能保证所有新词都是一个 token 吗？

不能。合并受训练语料和词表预算限制；罕见新词可能继续被拆成多个子词或字节。

为什么升级 tokenizer 不只是一个文本预处理改动？

token ID 与切分分布会改变，模型嵌入和训练时学到的序列模式都与旧词表相关。
