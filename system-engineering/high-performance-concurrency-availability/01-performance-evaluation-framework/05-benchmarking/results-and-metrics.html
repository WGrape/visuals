压测结果怎么看：别只盯 Requests/sec

报告必须同时回答“发了多少、完成多少、成功多少、等了多久、卡在什么资源”；先统一观测边界与窗口，才谈比较。

第一组：请求量与有效吞吐

指标定义如何防止误判
尝试/到达速率客户端发起数或网关收到数 ÷ 窗口秒数来源、重试与限流前后口径可能不同
完成 QPS / RPS在观察边界结束的请求数 ÷ 秒可能包含 429、5xx 等错误响应
成功 QPS满足预先约定的 HTTP 与业务条件的完成数 ÷ 秒不能把工具显示的 Requests/sec 直接叫成功 QPS
错误与超时分别统计 HTTP 非成功、业务失败、网络/连接错误、超时、取消失败样本是否计入延迟分布，要单独说明

例如总计发起 1,000 次，完成 980 次，其中 950 次业务成功、20 次客户端超时：成功率分母取 1,000 次尝试还是 980 次完成会得到不同结果。写明分母与重试规则，勿用完成率代替成功率。

第二组：延迟分布与排队

  • 端到端 RT：客户端计时的响应时间；按相同窗口给平均值与 P50/P95/P99，并说明超时和错误如何处理。平均值很低也可能有严重尾延迟。
  • 分段耗时：连接/DNS/TLS（若需要）、网关等待、业务执行、数据库/缓存/外部依赖等待。不能将不同边界的时间与在途量混用。
  • 并发与积压：客户端未完成数、连接数、网关排队数、业务 active 数各自统计平均与峰值；持续增长的队列意味着该档可能未稳定。

同口径稳态下，平均在途量约等于完成速率 × 同边界平均耗时；不能用 P99 或连接数代替平均耗时与请求数。详见Little 定律及P 指标。

第三组：机器、进程与依赖

同时观察压测端和目标端的 CPU 利用/限额与节流、内存/GC、网络带宽与丢包、磁盘 IO、文件描述符、监听/连接池排队、数据库慢查询与锁、缓存命中、下游限额。QPS 平台不一定是服务端 CPU 满：也可能是负载机发不动、上游限流或数据库池排队。

示意：如何判定一档是否合格

以下数字纯属教学示意，非真实压测数据。要求成功率 ≥ 99%、客户端 P99 ≤ 300ms 且队列稳定。低档每秒成功 80 次、P99 为 140ms、队列不增长；下一档每秒成功 105 次、P99 为 260ms、队列不增长；再上调时完成速率约 110 次/秒但成功率下降、P99 为 900ms、队列持续增长。第三档不合格，不能把“110 次/秒”宣布为可持续容量。第二档也需足够长的观察窗口和多次复验才能确认。

报告中把每档的负载配置、实测请求总数、各类错误、P99、资源曲线与原始记录放在一起。仅凭单次 ab/wrk 文本输出无法解释全部原因；容量评估流程提供结论边界。
