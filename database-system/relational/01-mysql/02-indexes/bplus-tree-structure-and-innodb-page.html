B+ 树：从数据结构到 InnoDB 的一页 16KB

一个节点 = 一页 = 16KB。把这句话想通，索引的一切行为就都能解释了。

很多讲解只告诉你「B+ 树矮胖、叶子有链表、范围查询快」，但真正的困惑往往在落地层： 树上的一个节点到底对应磁盘里的什么东西？一行数据是怎么被塞进一页里的？ 为什么主键用自增就能少很多页分裂？三层的树凭什么能撑住两千万行？ 这一篇从数据结构讲到存储页，把整条链路一次说清楚。

1. 先问为什么：磁盘 IO 才是成本

假设内存里有一千万条有序记录，二分查找只要约 24 次比较，看起来很完美。 但数据库的数据在磁盘上，而磁盘的读写单位不是「一条记录」，是 一个块 / 一页（InnoDB 默认 16KB）。一次随机 IO 大约 0.1~1ms 量级， 比一次内存比较贵了五个数量级。

所以数据库索引的设计目标不是「比较次数最少」，而是：

让一次查询走过的「页」尽量少 —— 也就是让树尽量矮、每个节点尽量宽。

为什么不用这几种结构

fanoutN，fanout 上千 1000 万行 → 3 层，且根页常驻内存 每个节点 = 一页 16KB，一次 IO 读进上千个 key 范围查询沿叶子链表单向扫，不再来回跳

同样的数据量，二叉结构瘦高、B+ 树矮胖；层数直接等于最坏 IO 次数

结构问题
有序数组查询快（二分），但插入要搬移，落盘就是整页重写，写放大严重
二叉搜索树 / 红黑树树高 log₂N，节点只存一个 key，1000 万行约 24 次随机 IO；且范围查询要反复回到父节点
哈希表等值 O(1)，但天然无序，做不了范围查询与排序，也不支持最左前缀
B 树每个节点都存数据，节点能放的 key 数量变少 → 扇出变小、树变高
B+ 树非叶节点只存 key + 指针（不存数据）→ 扇出极大 → 树极矮；数据全在叶子且叶子相连 → 范围扫描顺滑

2. B+ 树的三条硬规则

把 B+ 树拆开看，它其实只有三条规则，其余性质都是推论：

① 多路平衡，不是二叉

一个节点里可以放成百上千个 key：k1 | k2 | k3 … 每个 key 的左右两侧各挂一个子节点指针。所有叶子都在同一层，树永远平衡。

② 非叶节点只当路标

非叶节点只存 key + 子节点页号，绝不存真实数据。这让一页能塞下上千个 key，扇出大、树就矮。

③ 数据全在叶子，叶子互相连

所有真实数据都在叶子节点上；叶子之间用双向链表串起来，于是范围查询就是「定位起点 + 顺着链表扫」。

推论：因为非叶节点只是路标，同一个 key 会同时出现在非叶和叶子上（非叶里的是「副本」，用于导航）。 这不是冗余错误，而是刻意设计——它换来的是极高的扇出。

4. 等值查询：树高就是 IO 次数

执行 WHERE id = 31 时，InnoDB 做的事只有一件：从根页开始，一层一层往下跳，直到叶子页。 每下降一层最多读一页，所以：

最坏 IO 次数 = 树的高度（层数） 典型值：3 层 → 最多 3 次页访问；而根页几乎常驻 Buffer Pool → 实际常常只有 1~2 次磁盘 IO

5. 范围查询：叶子链表的价值

执行 WHERE id BETWEEN 12 AND 40 时，流程变成两段：

  1. 先做一次等值定位：沿树一路向下找到 id = 12 所在的叶子页（3 次 IO）；
  2. 再顺着叶子链表横向扫：从这一页开始一路往后读，直到遇到 > 40 的记录为止。

这就是 B+ 树相对 B 树最大的优势——B 树的数据散落在所有层，范围查询必须在树里来回中序遍历，父节点反复进出内存； 而 B+ 树的数据全在叶子、叶子还连成链表，第二段完全变成顺序 IO。

B+ 树把范围查询拆成「一次定位 + 一段顺序扫描」，这是它取代 B 树的关键原因

6. 插入与页分裂

插入新行时，先按 key 找到目标叶子页；只要页里还有剩余空间，就直接写进去。 真正的麻烦是目标页满了：

页分裂是索引写入最贵的操作之一：要申请新页、搬移约一半记录、在父页插入目录项，还要写 redo log； 父页也满时会连锁向上分裂，最坏情况一路分裂到根 —— 树就是这么长高的。 删除则相反：当页内记录数低于合并阈值（默认 50%）时，会尝试与相邻页合并，让树变矮。

为什么推荐自增主键

  • 自增主键：新行永远追加到最右边的叶子页，页写满就新开一页，几乎不触发中间页的分裂，页利用率高、碎片少。
  • 随机主键（如 UUID）：新行可能落到任意一页，频繁触发页分裂与随机 IO，写性能明显下降，索引还会变得"虚胖"。

7. 落地：InnoDB 的一页 16KB

到这里才是关键：B+ 树里的"节点"，在 InnoDB 里就是一个数据页（Page），默认 16KB。 页是 InnoDB 磁盘与内存之间最小的读写单位 —— 你只想读一行，InnoDB 也会把那一行所在的 16KB 整页读进 Buffer Pool。

一页 = 16KB：头部管元信息与链表，中间放行记录，尾部目录用于页内快速定位

8. 页内怎么找：槽 + 二分

页被读进内存后，要在一页的几百条记录里找某一行，InnoDB 不从头扫链表，而是走两步：

  1. 在页目录（Page Directory）上二分：槽是有序的，二分定位到「目标 key 落在哪两个槽之间」；
  2. 在槽内顺着链表线性走几步：一个槽只覆盖 4~8 条记录，最多再走几步就命中。

所以一次点查询的完整路径是：树间纵向定位（3 层）→ 页内二分定位（log₂槽数）→ 槽内几步。 真正花钱的只有前面的「页」访问次数。

Buffer Pool 的意义：页被读过一次就缓存在内存里，下次再访问不产生磁盘 IO。 B+ 树的根页和高层目录页访问极其频繁，基本永远命中缓存， 所以真实业务里一次主键点查询常常只有 0~1 次物理 IO。

9. 聚簇索引与二级索引

InnoDB 里「表」本身就是一棵按主键组织的 B+ 树；其他的索引是另一棵 B+ 树，只是叶子上放的东西不一样：

聚簇索引的叶子存整行，二级索引的叶子存主键值——后者需要再走一次主键树（回表）

10. 算一算：3 层树能装多少行

把上面所有数字串起来，就能自己估算容量。默认 16KB 页、BIGINT 主键（8B）+ 页号指针（6B）：

非叶页扇出 ≈ (16KB − 页头开销) ÷ (8B + 6B) ≈ 16384 ÷ 14 ≈ 1170 个指针/页 叶子页行数 ≈ (16KB − 页头开销) ÷ 单行大小 总容量(高度 h) ≈ 扇出h−1 × 叶子页行数
按默认值算：扇出约 1170，每个叶子页约 15 行（1KB/行）。 2 层 ≈ 1.7 万行，3 层 ≈ 2000 万行，4 层 ≈ 230 亿行。 这就是「千万级表的主键查询依然只要 3 次 IO」的由来 —— 也是常说「单表两千万要开始考虑拆分」的粗略依据。

11. 工程要点与面试速记

用自增/趋势递增主键

避免随机写入导致的频繁页分裂与索引碎片；同时让范围扫描更接近顺序 IO。

主键尽量短

二级索引的叶子都存主键值，主键越长，所有二级索引都跟着变大、变高。

能覆盖就别回表

把高频查询需要的列纳入联合索引，看到 Using index 就省掉了回表的随机 IO。

最左前缀原则

联合索引 (a,b,c) 相当于按 a → b → c 排序的字典序，跳过 a 就用不上这棵树的有序性。

区分度高、选择性好的列建索引

性别、状态这类低区分度列单独建索引收益很低，优化器会直接放弃走全表。

页分裂与合并有代价

批量导入时按主键排序插入、合理设置合并阈值，能显著降低碎片与写放大。

为什么不用红黑树树高 log₂N，千万行要二十多次随机 IO；B+ 树只要 3 层
为什么不用哈希索引等值快但完全无序，做不了范围查询、排序与最左前缀
一次主键点查询几次 IO最多等于树高（通常 3）；根页常驻缓存，实际常 0~1 次物理 IO
什么是回表二级索引叶子只存主键，拿到主键后需再走一遍主键 B+ 树取整行
什么是覆盖索引查询所需列都在索引里，无需回表；EXPLAIN 显示 Using index
