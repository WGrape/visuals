发布策略：滚动、蓝绿、灰度与回滚

六种发布方式对比、K8s 配置示例，以及最容易翻车的数据库变更

一、六种常见发布方式一览

发布方式的本质是在 停机成本、资源成本、回滚速度、风险控制粒度 之间做取舍。没有最优解，只有最适合当前业务形态的那一档。

重建 Recreate
先停旧版再起新版
必然有 downtime
适用：内部系统、可停服窗口
滚动 Rolling
逐批替换实例
无停机、零额外资源
适用：大多数无状态服务的默认选择
蓝绿 Blue-Green
两套环境整切
秒级回滚、需双倍资源
适用：关键服务、要求快速回退
灰度 / 金丝雀
先放小流量验证
风险最小、需流量治理能力
适用：面向 C 端的核心链路

零用户影响、需回放能力

二、滚动发布：默认但不万能

滚动发布按批次替换实例，靠就绪探针保证新实例可用后才继续下一批。它的软肋是：新老版本同时在线提供服务，接口与数据结构必须双向兼容。

apiVersion: apps/v1 kind: Deployment spec: strategy: type: RollingUpdate rollingUpdate: maxSurge: 1 # 最多比期望副本多起 1 个（决定发布速度） maxUnavailable: 0 # 发布过程中不允许可用副本低于期望（保证容量不降） minReadySeconds: 15 # 新 Pod Ready 后观察 15s 再算成功，避免「刚起就挂」 template: spec: readinessProbe: # 关键：就绪探针决定这一批是否算成功 httpGet: { path: /healthz, port: 8080 } initialDelaySeconds: 5 periodSeconds: 3

滚动发布的两个坑

  • 就绪探针写得太宽松：Pod 一启动就 Ready，结果预热没完成就被打流量，发布期间错误率飙升。应配合 minReadySeconds 与预热逻辑。
  • 新老版本不兼容：v2 改了接口字段或消息格式，v1 实例还在消费 —— 必须保证双向兼容一个发布周期。

三、蓝绿与灰度：差别在「切换粒度」

维度蓝绿灰度（金丝雀）
流量切换0 或 100%，一步到位1% → 5% → 20% → 50% → 100%
资源占用发布期间需两套全量环境只需少量额外实例
问题影响面切错就是全量受影响最多影响当前灰度比例的用户
验证充分性切换前只能靠预验证能用真实流量验证
依赖能力路由可切（网关/Service）流量染色 + 按比例路由 + 指标对比
适合变更风险低但要極速回滚变更风险高、需要真实验证

灰度的关键不是「放流量」，而是「能对比」

灰度必须有新老版本的指标对比（错误率、P99、业务转化率）与自动回滚阈值。只放流量不对比，灰度就只是慢一点的蓝绿。

四、数据库变更：发布里最容易翻车的一环

应用可以秒级回滚，数据库不行。所以 DB 变更必须与发布解耦，遵循「扩展-迁移-收缩」三步法。

  1. 扩展（Expand）：只做加法 —— 加新列、加新表、加新索引，旧代码不受影响，可独立发布。
  2. 迁移（Migrate）：双写（新旧列都写）+ 回填历史数据 + 校验一致性。此时新旧代码都能工作。
  3. 收缩（Contract）：确认旧代码已全部下线后，再删旧列、删旧表。这一步往往要推迟几个版本。
操作是否安全原因与替代方案
加可空列安全不停机；注意超大表加列仍可能锁表（看版本与算法）
加索引基本安全优先 ALGORITHM=INPLACE, LOCK=NONE；大表用在线 DDL 工具
删列 / 改列名危险旧代码还在读写 → 先双写，确认无引用后再删
改列类型 / 缩窄长度危险可能锁表、可能截断数据 → 新增列 + 双写迁移
加非空约束（无默认值）危险存量数据不满足会失败 → 先回填再慢慢加约束
大批量 UPDATE / DELETE危险长事务 + 锁 + 主从延迟 → 分批、限流、带 sleep

永远先问：这次发布能不能回滚？

如果发布包含不可逆的数据库变更，那么「回滚」就只能靠向前修复。这类发布必须在低峰期做、必须有数据备份、必须有验证脚本。

五、回滚：别等出事才想起它

回滚要有「预案」

提前写清：回滚命令是什么、谁执行、需要几分钟、数据怎么处理。

回滚要演练

每个季度至少真跑一次回滚流程，否则预案大概率是过期的。

镜像用 digest 而非 tag

:latest 无法保证回滚到的是同一个镜像，用 digest 才可靠。

配置也要版本化

只回滚代码不回滚配置，等于没回滚。配置与代码一起打版本。

保留旧版本实例

蓝绿发布后旧环境别立刻销毁，留出观察窗口（如 30 分钟到几小时）。

指标驱动自动回滚

灰度阶段错误率/P99 超阈值自动回滚，别依赖人盯盘。

六、深入自检

小团队该选哪种发布方式？

无状态服务用滚动（K8s 默认，几乎零成本）；关键服务再叠一层特性开关，这样即使不切流量也能秒关功能。蓝绿成本高，等到有明确回滚诉求再上。

灰度按什么维度分流最合理？

常见有四种：按百分比（最简单）、按用户 ID 哈希（保证同一用户稳定命中）、按地域/机房（先小机房验证）、按内部员工（先内部试用）。核心业务建议用用户哈希，避免同一用户在新老版本间跳变导致体验不一致。

为什么灰度期间错误率没涨，但业务指标掉了？

因为技术指标（错误率、延迟）只反映「没报错」，不反映「结果对不对」。灰度的对照组一定要带上业务指标：转化率、下单成功率、GMV。

数据库变更和应用发布谁先谁后？

遵循「先扩后收」：加列/加表先于应用发布；删列/改结构晚于应用下线。这样任意时刻都存在一个可工作的组合，回滚才安全。

特性开关会不会让代码变脏？

会，所以要定期清理：开关上线时同步登记「预计下线时间」，超过期限自动告警。把开关当成临时债务而不是永久架构。

一句话原则

发布前唯一的终极问题是：如果这一版有问题，我怎么在 5 分钟内回到上一版？答不上来，就先别发。

四种发布策略的对比与选择

发布策略本质是在发布速度、风险、资源成本三者间取舍。没有最好的，只有最适合当前场景的。

策略做法回滚速度额外资源适用场景
重建（Recreate）先停旧版本，再启新版本慢（要重新部署）无开发环境、可接受停机的内部系统
滚动（Rolling）逐批替换实例中（逐批回滚）少量（多几个实例）默认选择，大多数无状态服务
蓝绿（Blue-Green）起一整套新版本，切流量秒级（切回路由）2 倍（短暂）要求秒级回滚、有状态但可双写
金丝雀/灰度（Canary）先放 5%~10% 流量试快（调权重回 0）少量高频发布 + 要控制爆炸半径
影子（Shadow）新版本接收流量副本但不返回无风险1 倍（镜像流量）验证正确性/性能，不影响用户

数据库迁移难难最难（两版共用一库）

K8s 配置

# ---------- Kubernetes 滚动更新（默认策略）----------
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%         # 可以超出期望副本的比例（额外起多少）
      maxUnavailable: 0     # 发布期间允许不可用的比例（0=零停机）
  minReadySeconds: 10       # 新 Pod Ready 后再观察 10 秒才算成功
  progressDeadlineSeconds: 600

# 操作
kubectl set image deploy/app app=app:v2
kubectl rollout status deploy/app             # 看进度
kubectl rollout undo deploy/app               # 一键回滚
kubectl rollout undo deploy/app --to-revision=3
kubectl rollout history deploy/app
kubectl rollout pause/resume deploy/app       # 暂停/继续（金丝雀手动控制）

# ---------- 蓝绿：靠 Service selector 切换 ----------
kubectl apply -f app-v2.yaml                 # 先部署 v2（label version=v2）
kubectl patch svc app -p '{"spec":{"selector":{"version":"v2"}}}'
#   回滚：把 selector 改回 v1，秒级

# ---------- 金丝雀：靠副本数比例（简易版）----------
#   v1: 9 副本 + v2: 1 副本 -> 约 10% 流量（因为 Service 轮询）
kubectl scale deploy/app-v1 --replicas=9
kubectl scale deploy/app-v2 --replicas=1
#   正式方案用 Istio / Nginx Ingress 的权重分流，或 Argo Rollouts

# ---------- Argo Rollouts（金丝雀自动化）----------
spec:
  strategy:
    canary:
      steps:
      - setWeight: 5
      - pause: {duration: 5m}      # 观察 5 分钟
      - setWeight: 20
      - pause: {duration: 10m}
      - setWeight: 50
      - pause: {duration: 10m}
      analysis:                    # 自动分析：指标不达标就回滚
        templates:
        - templateName: error-rate
        args:
        - name: service
          value: app
  • 滚动更新期间新旧版本共存是最大的隐患：如果你的 API 不向后兼容、或者数据库 schema 变了，滚动期间一定出问题。数据库迁移必须独立且向后兼容（先加列 → 部署新代码 → 再删旧列，即 expand-contract 模式）。
  • maxUnavailable: 0 + maxSurge 25% 是零停机的标准配置：先起新的，起来了再杀旧的。
  • minReadySeconds 和 readinessProbe 很重要：没有它们，K8s 会在 Pod 刚启动（还没预热完）就认为成功，把流量打过去，导致大量 5xx。建议设 10~30 秒。
  • 金丝雀的关键不是分流，是「观察指标 + 自动决策」：只看人工观察等于没做。要有明确的指标（错误率、P99 延迟）和自动回滚阈值。
  • 蓝绿最贵的是资源：整套 2 倍资源。如果实例很多（几百个），可以只在发布期间临时扩容，发布完缩回去。
  • 有状态服务（数据库、带本地缓存的服务）发布要特别小心：滚动更新会导致缓存全冷、连接迁移。这类服务通常要配合优雅下线（preStop + 等待连接排空）。
  • 回滚不等于安全：如果发布包含了数据库迁移，回滚代码但数据库已经是新结构，可能直接崩。所以迁移要设计成可双向兼容。
蓝绿和金丝雀怎么选？

看你要解决的核心风险是什么。蓝绿解决的是「回滚要快」——它准备好一整套新版本，验证通过后一次性切换，出问题切回去只要改个路由（秒级）。适合：回滚成本极高的场景、需要发布前完整验证的场景。代价是 2 倍资源和「切换即全量的风险」——如果新版本有 bug，切换瞬间就是 100% 用户受影响。金丝雀解决的是「爆炸半径」——先给 5% 用户，观察指标正常再逐步放量，最坏情况只影响 5%。适合：高频发布、用户量大、无法承受全量故障的场景。代价是流程更复杂（需要流量治理能力 + 指标分析 + 自动决策），且发布周期更长。实践建议：大多数团队用「滚动更新 + readinessProbe + 一键回滚」就够了；当发布频率高到每天多次、或者用户量大到 5% 故障都不可接受时，才上金丝雀；蓝绿适合那些「发布窗口很窄、必须秒级回滚」的遗留系统或金融类系统。

滚动更新时新旧版本共存怎么处理兼容性？

这是滚动更新最容易踩的坑，核心原则是让两个版本能同时正确工作：① API 向后兼容——新版本不要删除或改变旧版本依赖的字段，只增不改；需要改语义时，分两次发布（第一次新旧都支持，第二次才删）；② 数据库用 expand-contract 模式——第一步：加新列/新表（旧代码忽略它）；第二步：部署新代码同时写新旧两处（双写）；第三步：迁移历史数据；第四步：部署只读新列的代码；第五步：删除旧列。每一步都可以独立回滚；③ 不要在一次发布里同时改代码和删字段；④ 消息队列的消息格式同理——消费者要能处理新旧两种格式。判断标准很简单：如果新版本部署到一半时出问题需要回滚，旧版本能不能继续正常工作？如果不能，这个发布就必须拆分。

金丝雀的观察指标应该看什么？

三类指标缺一不可：① 错误类——HTTP 5xx 错误率、业务错误码、panic/exception 数量。这是最优先的判据，金丝雀版本的错误率显著高于基线就回滚（注意是相对比较，不是绝对值，因为全量时也可能有少量错误）；② 性能类——P99/P95 延迟、超时率。新版本如果有性能退化，在 5% 流量下可能看不出全量时的问题，所以要对比同等流量下的延迟分布；③ 业务类——转化率、下单成功率这类。有些 bug 不报错但业务结果错了，只有业务指标能发现。观察时长要覆盖一个完整业务周期——如果你的服务有明显的日内波动（如白天高峰、夜间低谷），在低谷期观察 10 分钟说明不了高峰期的表现。实践配置：每个灰度阶段至少 5~10 分钟，且要跨越一个完整的请求波峰；判据用相对比较（金丝雀 vs 基线）而不是绝对阈值。
