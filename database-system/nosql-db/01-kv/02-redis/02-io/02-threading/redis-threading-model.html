🧵 Redis 线程模型

「Redis 是单线程的」这句话对了一半：命令执行确实单线程，但 Redis 6.0 之后网络 I/O 和后台任务早已多线程。

纯内存 + 高效数据结构 + 无锁

先纠正一个常见误解

「Redis 是单线程的」只对一半。准确说法是：「Redis 的命令执行（读写数据）始终是单线程的」。而从 Redis 6.0 开始，网络 I/O（读 socket、解析协议、写回响应）已经可以多线程；更早的 4.0 就已经有后台线程处理惰性删除和 fsync。
版本单线程的部分多线程的部分
≤ 3.x网络 I/O + 命令执行基本没有（仅 bio 线程做 fsync/close）
4.0命令执行新增 lazyfree 线程（异步删除大 key）
6.0命令执行新增 I/O 多线程（io-threads）
7.x命令执行I/O 多线程 + 更多后台任务卸载

整体架构：主线程 + I/O 线程 + 后台线程

I/O 多线程：到底并行了什么

Redis 6.0 的多线程只并行了「搬运」，没有并行「干活」：

  1. 读阶段：多个 I/O 线程并行从 socket 读数据、解析 RESP 协议，把命令放进队列。
  2. 执行阶段：主线程一个人串行执行队列里的所有命令（这一步仍是单线程）。
  3. 写阶段：多个 I/O 线程并行把响应写回 socket。
一句话记忆：多线程「收发快递」，单线程「处理包裹」。因为真正的耗时往往在 read()/write() 系统调用和协议解析上，把这些挪走之后，主线程可以更专注地跑命令。

配置

# redis.conf —— I/O 多线程默认关闭
io-threads 4           # 工作线程数（含主线程）；设为 1 = 关闭
io-threads-do-reads yes # 是否让 I/O 线程也负责「读 + 解析」

# 经验值（官方建议）：
#   8 核机器        → io-threads 4~6
#   开启后性能提升    → 通常 1 倍左右（不是 N 倍）
#   超过 8 个线程    → 收益递减，反而增加调度开销
注意 io-threads 的语义：它设置的是总线程数（含主线程）。设成 4 意味着「主线程 + 3 个 I/O 线程」。设成 1 就是关闭多线程，这也是默认值。

后台线程（bio）：4.0 就有了

后台任务对应配置 / 命令为什么需要卸载
惰性释放 lazyfreeUNLINK key、FLUSHALL ASYNC、lazyfree-lazy-eviction yes删除一个百万元素的 ZSet 要逐个 free，在主线程做会造成明显卡顿
AOF fsyncappendfsync everysecfsync 可能阻塞数百毫秒，交给后台线程避免影响主线程
关闭文件描述符内部自动某些情况下 close() 会触发刷盘而阻塞
# 主键删除用 DEL（同步，大 key 会卡主线程）
DEL big-hash

# 改用 UNLINK（异步，主线程只做「摘链表」，真正的 free 交给后台线程）
UNLINK big-hash

# 同理，清空库也用 ASYNC 版本
FLUSHALL ASYNC
FLUSHDB ASYNC

为什么单线程还能这么快

  • ✅ 纯内存操作：数据都在内存，没有磁盘 I/O 这个最大的瓶颈。
  • ✅ 高效数据结构：SDS、跳表、哈希表、listpack 都针对场景精心优化。
  • ✅ 没有锁竞争：单线程执行命令，天然不需要加锁，省掉锁获取/释放和死锁检测。
  • ✅ 没有线程切换：不用在 CPU 核心之间来回调度，缓存局部性更好。
  • ✅ I/O 多路复用：epoll/kqueue 一个线程管理成千上万个连接。
真正的瓶颈排序（实际生产中最常见的）：① 网络往返（RTT）→ 用 Pipeline / MGET 批量解决；② 大 key / 复杂度过高的命令；③ 内存与 fork；④ 最后才轮到 CPU。所以「单线程不够用」在绝大多数场景并不是首要矛盾。

单线程带来的三个「副作用」

  1. 命令天然原子：INCR、LPUSH 等不需要额外加锁，也不会有并发写冲突。
  2. 一个慢命令会拖垮所有人：KEYS *、对百万元素做 HGETALL、复杂度 O(N) 的 SORT，会让后续所有客户端一起等。
  3. 无法利用多核：单实例最多吃满一个核。横向扩展靠多实例 / 集群 / 分片，而不是靠加大线程数。
生产禁止使用：KEYS *（用 SCAN 代替）、对未知大小容器直接用 HGETALL/SMEMBERS/LRANGE 0 -1（先 HLEN/SCARD/LLEN 看大小）。这类命令是 Redis 卡顿的头号原因。

怎么判断 Redis 是被什么卡住的

# 1. 查看慢日志（默认记录执行超过 10ms 的命令）
SLOWLOG GET 10
SLOWLOG LEN

# 2. 实时观察命令延迟分布
LATENCY DOCTOR
LATENCY LATEST

# 3. 查看瞬时 OPS 与连接数
INFO stats
INFO clients

# 4. 找出大 key
redis-cli --bigkeys
redis-cli --memkeys

🎯 面试问答

Q：「Redis 是单线程的」这句话准确吗？
A：不准确，只对了一半。准确说法是「命令执行（读写数据）始终单线程」。而：① Redis 6.0 起网络 I/O 已支持多线程（io-threads），并行做 socket 读写和 RESP 解析；② 4.0 起就有后台线程处理惰性删除（lazyfree）、AOF fsync、关闭文件描述符。所以更精确的表述是「Redis 的数据操作是单线程的，但整体进程不是单线程的」。
Q：Redis 6.0 的多线程到底并行了什么？
A：只并行了「搬运」，没有并行「干活」。具体分三段：多个 I/O 线程并行读 socket 并解析协议 → 放进队列 → 主线程串行执行所有命令 → 多个 I/O 线程并行写回响应。关键点：I/O 线程从不执行任何命令、不触碰数据库。这样既享受了并行 I/O 的吞吐提升，又保留了单线程执行命令带来的无锁、原子性优势。
Q：io-threads 应该怎么配？
A：该参数表示的是总线程数（含主线程），设成 1 表示关闭（默认值）。官方经验：8 核机器设 4~6，通常能带来约 1 倍的吞吐提升，不是 N 倍。超过 8 个收益递减甚至变差。要真正启用读并行还需 io-threads-do-reads yes（只开写并行的话效果有限）。CPU 通常不是 Redis 的瓶颈，所以这个配置不是必选项，先排查大 key 和 Pipeline 更划算。
Q：为什么 Redis 坚持让命令执行保持单线程？
A：三个原因：① 瓶颈不在 CPU——Redis 的瓶颈通常是内存访问和网络 RTT，多线程执行带来的收益有限；② 省掉锁开销——单线程执行命令天然无数据竞争，不需要加锁/解锁，也没有死锁风险，代码大幅简化；③ 命令原子性——每个命令的执行不可被打断，INCR 之类的操作天然线程安全。多线程执行会引入锁、可见性、调试复杂度，收益却不成正比，所以官方选择了「I/O 多线程 + 执行单线程」这种折中。
Q：单线程模型有什么坑？
A：最大的坑是一个慢命令会阻塞所有客户端。因为命令串行执行，一次 KEYS * 或对百万元素集合做 HGETALL，会让后续请求全部排队等待。生产上应：① 禁用 KEYS，改用 SCAN；② 对未知大小的容器先查长度（HLEN/SCARD/LLEN）再决定是否全量取；③ 删除大 key 用 UNLINK 而非 DEL；④ 开启慢日志 SLOWLOG GET 定期巡检。另外单实例只能用满一个核，要利用多核得靠多实例或集群分片。
