数据写入流程
1
原始文档输入 ES层
客户端发送 JSON 文档到 ES REST API (9200端口)
输入数据结构
{ "title": "Elasticsearch实战", "author": "张三", "content": "分布式搜索引擎详解", "views": 12345 }
↓
2
路由计算 ES层
根据 _uid 计算目标分片
路由公式
shard_num = hash(_uid) % primary_shards
↓
3
Memory Buffer 内存
文档写入内存缓冲区，同时写入 Translog (保证持久性)
内存状态
[ Doc 1: {title: "A", content: "foo"}, Doc 2: {title: "B", content: "bar"}, Doc 3: {title: "C", content: "baz"} ]
↓ refresh (1秒)
4
Segment (内存) 内存 Lucene
缓冲区数据生成新的 Segment，建立倒排索引
索引结构
倒排索引已创建，可被搜索
↓ flush (或达到阈值)
5
Segment Files 磁盘 Lucene
Segment 刷到磁盘，Translog 清理
磁盘文件结构
index/ _0.tim (倒排表 - Term Dictionary) _0.tip (词典索引) _0.doc (正排表 - Doc IDs) _0.fnm (字段定义) _0.nvd (评分因子) translog/ translog.ckp
↓ 后台合并
6
Segment Merge 磁盘 Lucene
后台线程合并小 Segment 为大 Segment，减少文件数量

📍 写入流程总结

  • Document → 路由计算 → Memory Buffer → Segment(内存) → Segment(磁盘) → Merge
  • Translog 贯穿全程，保证故障可恢复
  • Refresh 默认 1 秒，实现近实时搜索

数据查询流程
1
Query 输入 ES层
客户端发送搜索请求到 ES REST API
查询示例
GET /my_index/_search { "query": { "match": { "content": "搜索" } } }
↓
2
Query Parsing & Routing ES层
解析查询条件，计算目标分片 (可能分散在多个节点)
↓
3
IndexSearcher 内存 Lucene
创建搜索器，并行遍历所有 Segment
↓ Query Phase
4
Query Phase (查询阶段) Lucene
遍历倒排索引，找到匹配文档，计算评分
倒排表查询过程
1. 在 .tim 中定位 Term "搜索" 2. 读取倒排列表 (Postings) 3. 计算 BM25/TF-IDF 评分 4. 取每个 Segment 的 Top N 5. 归并排序取全局 Top 10
↓ Fetch Phase
5
Fetch Phase (获取阶段) Lucene
根据 DocId 从 .doc 文件加载原始文档
正排表读取
DocId 3 → 从 .doc 加载原始 JSON DocId 7 → 从 .doc 加载原始 JSON DocId 15 → 从 .doc 加载原始 JSON
↓
6
组装结果返回 ES层
聚合各分片结果，返回给客户端

📍 查询流程总结

  • Query → 解析/路由 → IndexSearcher → Query Phase → Fetch Phase → 返回
  • Query Phase: 遍历倒排索引，找到匹配文档
  • Fetch Phase: 根据 DocId 拉取原始文档
  • 写入用正排建倒排，查询从倒排找正排

核心速览

一句话文档写入先进内存 buffer，refresh 成 segment 才能被搜到，flush 后才真正落盘
三个动作refresh（可搜）、flush（持久化）、merge（合并 segment）
为什么近实时refresh 默认 1 秒，所以叫近实时而非实时
不可变segment 一旦生成就不改，删除只是标记，更新是「删+加」
ES 写入四步：buffer -> refresh 可搜 -> flush 落盘 -> merge 优化

一、三个动作的分工

动作触发做什么代价不做的后果
refresh默认 1s，或手动调用把内存 buffer 里的文档生成新的 Lucene segment频繁 refresh 产生大量小 segment文档搜不到
flushtranslog 达阈值或定时把内存中的 segment 写盘，并清空 translog一次 fsync，较慢宕机丢失数据
merge后台自动把多个小 segment 合并成大 segment，清理已删文档占用 IO 与 CPUsegment 太多，查询变慢

二、为什么 segment 不可变

不可变带来三个巨大好处，代价是更新删除都很别扭：

无需加锁并发读不需要任何同步
缓存友好倒排索引、Filter 缓存可以长期驻留
可以压缩一次性写入后可做高效压缩

代价：删除只在 .del 文件里标记，查询时过滤掉；更新 = 标记删除旧文档 + 索引新版本。真正的空间回收发生在 merge 时。这也是为什么频繁更新的索引会膨胀。

三、写入链路上的关键参数

参数默认调大调小
refresh_interval1s写入吞吐更高，实时性变差更实时，但 segment 暴增
translog.durabilityrequest异步更安全？不——改成 async 会提升吞吐但可能丢 5s 数据-
translog.flush_threshold_size512MBflush 更少，恢复更慢flush 更频繁，IO 压力大
number_of_replicas1读能力更强、更安全写入更快（副本同步开销小）
批量写入的两个必做项

① 用 _bulk 而不是一条条 POST，单批 5~15MB、几千条为宜，过大反而会拖慢；② 大批量导入时临时把 refresh_interval 设为 -1、replicas 设为 0，导完再改回来并手动 refresh —— 这是导入提速最直接的一招。

# 批量导入提速三板斧 PUT /my_index/_settings { "index": { "refresh_interval": "-1", "number_of_replicas": 0 } } # ... 用 _bulk 导入 ... POST /_bulk { "index": { "_index": "my_index", "_id": "1" } } { "title": "文档一", "content": "..." } { "index": { "_index": "my_index", "_id": "2" } } { "title": "文档二", "content": "..." } # 导入完成后恢复 PUT /my_index/_settings { "index": { "refresh_interval": "1s", "number_of_replicas": 1 } } POST /my_index/_refresh

四、translog 到底防什么

文档进了 buffer 但还没 flush 时，进程挂了数据就没了。translog 就是这段窗口的保险：每次写入都追加一条日志，重启后重放 translog 即可恢复。

durability行为吞吐风险
request（默认）每次写请求都 fsync translog较低几乎不丢
async每 5 秒 fsync 一次高可能丢最近 5 秒

五、深入自检

为什么写入后立刻搜不到？

因为 refresh 还没发生。默认 1 秒一次，所以最长要等 1 秒。需要立刻可见就在写请求里带 refresh=wait_for，代价是这次请求会等到 refresh 完成。

segment 太多会怎样？

每个 segment 都要占文件句柄与内存，且查询要遍历所有 segment 再归并结果。几百个 segment 时查询性能会明显下降。解决：调大 refresh_interval、或手动 _forcemerge（谨慎，开销大）。

为什么不建议频繁 forcemerge？

merge 是 IO 与 CPU 密集型操作，会把整机的 IO 打满，影响线上查询。只在不再写入的索引（如按天归档的历史索引）上做，且放在低峰期。

删除了文档为什么磁盘没变小？

因为只是打了删除标记，空间要等 merge 时才回收。想立刻回收可以对只读索引做 forcemerge，或干脆删除整个索引。

replica 会影响写入性能吗？

会。写入必须等所有副本（默认 wait_for_active_shards=1 只等主分片，但副本同步仍会消耗网络与 IO）。导入期间把副本设为 0 是标准提速手段。

实时性要求很高怎么办？

三条路：① 写时带 refresh=wait_for；② 用 GET API 按 ID 取（走 translog，实时）；③ 降低 refresh_interval。但高频 refresh 会让 segment 暴涨，通常更推荐前两种。

记住一句refresh 管可搜，flush 管不丢
默认 1 秒所以叫近实时
导入提速关 refresh + 关副本 + _bulk
不可变代价删除是标记，更新是删+加
