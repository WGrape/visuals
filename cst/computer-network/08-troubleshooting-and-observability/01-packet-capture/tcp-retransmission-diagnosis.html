TCP 重传抓包诊断：丢包、乱序与超时

用序列号、ACK、SACK 和抓包位置判断“重传”真正说明了什么。

抓到重传，不等于立刻找到丢包点

TCP 发送的是字节流，每个报文段的序列号标识起始字节位置，ACK 表示接收方期望的下一个字节。如果发送方迟迟没有得到某段数据已被确认的证据，可能通过重复 ACK 或重传超时再次发送。但单端抓包看到“重传”并不能直接断定原始包在网络中丢了：ACK 可能丢失，包可能乱序，抓包程序也可能漏包。需要把发送端、接收端和中间链路的位置一起考虑。

例如发送方发出 seq=1000、长度=1000 的段，接收方若完整收到，下一期望字节是 2000，回 ACK=2000。若该段未到，后续更高序列的数据先到，接收方会继续表明从 1000 开始仍有缺口；启用 SACK 时还可说明后续哪些字节块已经收到。重传的 seq 与长度应和原始数据范围对照，而不是只看抓包工具自动标注的“TCP Retransmission”。

逐步推演

定位连接

用五元组和时间范围锁定问题请求，记录抓包位置。

对齐序列

按 seq、len 和 ACK 重建发送与确认的字节范围。

区分路径

把重复 ACK、SACK、RTO 与两端抓包对应起来。

关联应用

检查慢请求是否真正由重传造成，还是发生在服务端排队。

逐段读取一次异常

假设抓包里依次看到 seq=1000 len=1000、seq=2000 len=1000、重复 ACK=1000、随后重传 seq=1000。先核对接收方是否真的看到了第一段：如果接收端也没有，而后段已到，可能是数据段在路径中丢失；如果接收端已回 ACK=2000，但发送端没看到，则可能是 ACK 路径问题；如果两端看到的顺序不同，可能是网络乱序。时间间隔也有价值：很快重传常由重复 ACK 等信号触发，等待较久后重传可能是 RTO。

证据可能解释还要验证
重复 ACK接收方仍在等待缺口是否伴随乱序和 SACK
SACK 块部分后续数据已到缺失范围与重传范围
较长等待后重传可能是超时路径RTT、RTO 与 ACK 轨迹
单端缺少原始包也可能是抓包漏包对照另一端与接口丢包计数

抓包位置与网卡卸载的影响

在发送端网卡前抓包，可能看到尚未被硬件切成最终线上包的大段数据；接收端又可能因 GRO/LRO 合并而显示不同长度。抓包中“一个大 TCP 包”未必就是线上的真实以太网帧。分析 MSS、分段和重传时要记录 TSO/GSO/GRO 等卸载状态，必要时在交换机镜像口或另一端抓包比对。

时间戳也要小心。两台主机时钟未校准，不能简单用两份抓包的绝对时间相减得到单向延迟。可以先用同一 TCP 连接的序列号和 ACK 配对，再校正时钟偏差。若应用报告超时，但 TCP 没有明显重传，瓶颈可能在服务端排队、线程池、TLS 或应用逻辑，不应把所有慢请求归因于网络。

可重复的排障流程

  1. 固定五元组、抓包位置与时间范围，保留原始 pcap 和接口丢包计数。
  2. 按序列号重建字节范围，记录首次发送、重复发送、ACK、SACK 与时间间隔。
  3. 对照发送端和接收端：确定原始数据是否到达、ACK 是否返回以及是否乱序。
  4. 把网络证据与应用超时、队列时长和重试日志关联，判断真正的用户影响。

练习：发送端见到重传，接收端抓包却显示原始数据已经到达并发出 ACK。至少列出两种可能原因，并说明需要哪一份证据才能区分 ACK 丢失和发送端抓包误判。

别把窗口受限误判成丢包

发送方暂时不发数据，可能因为拥塞窗口收缩，也可能因为接收窗口为零、应用本身没有更多数据，或服务端处理慢。抓包时要看发送窗口、接收窗口广告、ACK 节奏和应用日志。零窗口通常表示接收方来不及从 TCP 缓冲读取数据；这与链路丢包需要不同处理。快速重传之后拥塞控制还可能降低发送速率，使用户看到一段更长的吞吐下降。

单个抓包文件也可能不完整：过滤表达式漏掉反向 ACK、抓包进程丢包、NAT 或负载均衡改变连接五元组，都可能导致分析者错误拼接时间线。准备抓包时尽量保留双向流量并记录抓包丢包统计。若无法双端同时抓包，就把结论表述为“某端观察到什么、仍缺少什么证据”，不要把推测写成已证实的链路故障。

应用重试的干扰

HTTP 客户端超时后可能新建另一条 TCP 连接重试同一业务请求。抓包若只按目标端口统计，会把两条连接混成一条“重复发送”。先按五元组和连接建立时间分开，再用请求 ID 关联日志，区分 TCP 层重传与应用层重试。

自检

ACK=2000 对 seq=1000、len=1000 表示什么？

接收方累计确认到 1999，下一步期待从 2000 开始的字节。

为什么单端抓包不能直接证明网络丢包？

ACK 丢失、乱序、抓包漏包和网卡卸载都可能改变所见轨迹。
