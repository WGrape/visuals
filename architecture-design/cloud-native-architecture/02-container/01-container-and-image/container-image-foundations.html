容器与镜像：隔离的是进程，不是内核

看清 OCI 镜像、分层文件系统和 Linux 资源边界。

学完能解释什么

  • 区分镜像、容器和运行时三个对象
  • 解释 namespaces、cgroups 与分层文件系统各自解决的问题
  • 知道镜像可复用不等于镜像天然可信

逐步看机制

固化文件与启动约定

镜像由清单、配置和只读文件层组成；同一层可复用。镜像本身不是正在运行的进程。

三个术语，一条链路

镜像是可分发的应用文件系统与元数据；容器是以这些文件启动、处于隔离视图中的进程集合；运行时负责创建隔离与启动进程。OCI 的镜像与运行时规范让构建、分发和运行有共同约定，但不会替应用解决配置、权限或状态管理。

隔离能力各有边界

机制提供什么没有提供什么
namespacesPID、挂载、网络等资源的独立视图不自动限制 CPU/内存消耗
cgroups对 CPU、内存、进程数等记账与限额不提供独立文件系统或不同内核
分层文件系统镜像只读层复用、容器可写层不适合作为独立可靠的数据备份

与虚拟机相比，容器共享宿主内核。因此容器逃逸、内核漏洞和过度权限是真实风险；镜像扫描、非 root 运行、最小权限与持续更新缺一不可。

理解一次镜像变更

改动上层文件不会修改已发布的底层只读层，而是产生新层/新镜像；容器运行时通过写时复制呈现统一文件系统。版本标记（tag）可以重新指向不同内容，生产部署应尽量固定不可变摘要。应用需要持久数据时明确挂载卷或使用外部数据服务；“重启同一个容器没丢数据”不能证明删除/重建后还能恢复。

自检

镜像更新后，已经运行的容器会自动换成新镜像吗？

不会。运行中的进程仍基于创建它时的文件系统与配置；需要显式重新创建或滚动发布。

容器镜像：一次构建，到处运行

容器镜像是打包了应用及其全部依赖的只读模板。它解决的是那个古老的问题：「在我机器上是好的」——因为镜像里连操作系统用户态都打包了，运行环境完全一致。

镜像分层结构与容器/虚拟机对比

镜像 vs 容器：一对易混概念

概念是什么类比生命周期
镜像 Image只读的模板，包含应用与依赖的分层文件面向对象里的「类」 / 安装光盘构建一次，可被分发与复用
容器 Container镜像的运行实例，在镜像层之上加一个可写层面向对象里的「对象」 / 装好的系统可创建、启动、停止、删除
仓库 Registry存放和分发镜像的地方代码仓库（GitHub）Docker Hub、Harbor、各大云厂商镜像服务
标签 Tag镜像的版本标识Git 的 tag不要用 latest 作为生产版本

关键认知：镜像是不可变的。容器运行期间的修改都写在可写层，容器删除后这些修改全部消失。要变更就必须重新构建镜像——这正是「不可变基础设施」的实践基础。

Dockerfile 常用指令

指令作用要点
FROM指定基础镜像尽量选精简基础镜像（alpine / slim / distroless）以减小体积与攻击面
COPY / ADD复制文件进镜像优先 COPY；ADD 会自动解压 tar 并支持 URL，行为不够直观
RUN在构建期执行命令（装依赖、编译）多个命令用 && 合并成一层，减少层数
ENV设置环境变量构建期与运行期都生效；密钥不要用 ENV（会留在镜像里）
WORKDIR设置工作目录用绝对路径，避免 cd 命令
EXPOSE声明监听端口只是文档性质，实际映射靠 docker run -p
USER指定运行用户生产镜像应切换到非 root 用户，降低风险
CMD / ENTRYPOINT指定容器启动命令ENTRYPOINT 定可执行文件，CMD 定默认参数；二者配合最灵活
HEALTHCHECK定义健康检查让编排系统能判断容器是否真的可用
# 一个典型的多阶段构建示例（Java） FROM maven:3.9-eclipse-temurin-21 AS builder WORKDIR /build COPY pom.xml . RUN mvn -B dependency:go-offline # 依赖层先构建，利用缓存 COPY src ./src RUN mvn -B package -DskipTests FROM eclipse-temurin:21-jre-alpine # 运行镜像只含 JRE RUN adduser -D app && mkdir /app && chown app /app WORKDIR /app USER app # 非 root 运行 COPY --from=builder /build/target/app.jar ./app.jar EXPOSE 8080 HEALTHCHECK --interval=15s CMD wget -qO- http://localhost:8080/health || exit 1 ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "app.jar"] # 效果：构建依赖（Maven、JDK、源码）不进入最终镜像，体积可从 800MB 降到 150MB

镜像瘦身与安全：六个实践

① 多阶段构建

构建工具链（编译器、Maven、npm 缓存）不该进生产镜像。用多阶段构建只把产物复制出来。

  • 体积常能减少 60%~90%
  • 同时减少攻击面（镜像里没有 gcc、没有 shell 更好）

② 选精简基础镜像

  • alpine：约 5MB，但用 musl libc，某些软件有兼容问题
  • slim：Debian 精简版，兼容性好
  • distroless：只有运行时，连 shell 都没有，最安全也最难调试

③ 利用构建缓存

Docker 按层缓存，某层变了它之后的所有层都要重build。

  • 把变化少的放前面：先 COPY 依赖清单再装依赖，最后 COPY 源码
  • 用 .dockerignore 排除 node_modules、.git、日志等

④ 不要打进密钥

ENV / COPY 进镜像的密钥会永久留在层里，即使后续删除也能被还原。

  • 用运行时注入（环境变量 / Secret 挂载 / 密钥管理服务）
  • 构建期需要密钥时用 BuildKit 的 secret mount

⑤ 非 root 运行

默认 root 运行意味着容器逃逸后就是宿主机 root。

  • Dockerfile 里加 USER app
  • K8s 里配 securityContext.runAsNonRoot

⑥ 镜像扫描与签名

  • CI 里集成 Trivy / Grype 扫描 CVE
  • 用 cosign 做镜像签名，生产只允许运行已签名镜像
  • 基础镜像要定期更新，不能一次构建用三年

常见误区

  • 把容器当虚拟机用。在容器里跑 SSH、跑多个进程、手工修改配置——这些都违背不可变原则，会导致扩容出来的实例与老实例不一致。
  • 用 latest 标签上生产。latest 是可变的，两次拉取可能得到不同镜像，回滚时会拉到错误的版本。必须打不可变版本标签（如 v1.2.3 或 git sha）。
  • 镜像里写死配置。数据库地址写进镜像，换环境就要重新构建。配置应运行时注入。
  • 数据写在容器层。容器删除数据就没了，且容器层读写性能较差。需要持久化必须用 volume 挂载。
  • 镜像过大。1GB 的镜像在冷启动、分发、扩容时都是灾难——拉取时间直接决定了弹性伸缩的速度。目标应控制在 100~300MB 以内。
  • 忽略 .dockerignore。把 node_modules、.git、本地日志都 COPY 进去，既增大体积又可能泄露敏感信息。

深入自检

镜像的分层是怎么实现的？为什么能节省空间？

靠联合文件系统（UnionFS / overlayfs）。镜像由多个只读层叠加而成，容器启动时在上面加一个可写层。读取文件时从上往下查找，找到即用；修改文件时用写时复制（copy-on-write）——把文件复制到可写层再改，原只读层不变。节省空间的原因：多个镜像如果共享同一个基础层（比如都用同一个 node:20 基础镜像），该层在磁盘上只存一份、内存中也只加载一份；推送到仓库时，未变化的层不需要重复上传；拉取镜像时本地已有的层会直接复用。这也是为什么 Dockerfile 的指令顺序很重要——把稳定的层放前面，改代码时只有最后几层需要重建和重新传输。

为什么容器比虚拟机启动快这么多？

因为要初始化的东西少得多。虚拟机需要先由 Hypervisor 虚拟硬件，然后完整启动一个操作系统内核：BIOS/UEFI 自检、内核加载、设备驱动初始化、系统服务启动（systemd），这一套下来通常几十秒到几分钟。容器只是调用宿主机内核创建 Namespace（隔离进程视图、网络、挂载点等）和 Cgroup（限制资源），然后直接执行镜像里指定的启动命令——本质上就是启动一个进程，所以是毫秒到秒级。代价是隔离性：所有容器共享同一内核，内核漏洞和部分资源（如 /proc、某些系统调用）的隔离不如 VM 彻底，所以高安全场景会用安全容器（Kata、gVisor）补足。

容器的可写层能存数据吗？

技术上能，但强烈不建议。三个问题：① 易失——容器删除或重建，可写层数据立即消失，而容器是随时可能因为调度、自愈、发布被重建的；② 性能差——写时复制机制使得容器层的写 IO 性能明显低于直接写宿主目录或卷；③ 不可共享——容器被调度到其他节点后，数据不会跟着走。正确做法：需要持久化的数据用 volume（bind mount 或 named volume）挂载，在 K8s 里就是 PV/PVC；需要跨节点共享的用分布式存储或对象存储；临时数据可以用 tmpfs（内存盘），但同样不持久。

如何排查容器里的问题？容器里没有 shell 怎么办？

这正是不含 shell 的精简镜像（如 distroless）的调试难点。几种手段：① 优先用外部可观测性——日志输出到 stdout（平台收集）、暴露 metrics 端点、接入链路追踪，这样根本不需要进容器；② 用 docker exec 或 kubectl exec 进入有 shell 的调试镜像；③ K8s 用 kubectl debug 挂载一个临时调试容器（ephemeral container）到目标 Pod 的命名空间，共享进程与网络命名空间来排查；④ 用 nsenter 从宿主机直接进入容器的命名空间；⑤ 对于 JVM 类应用，可用 jcmd/jstack 通过共享的 /proc 从宿主机侧执行。实践建议：生产镜像保持精简（安全），调试靠外部可观测性 + 临时调试容器。
