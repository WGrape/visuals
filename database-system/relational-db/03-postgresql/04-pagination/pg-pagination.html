深分页与游标分页

LIMIT/OFFSET 的陷阱，以及 keyset（游标）分页为什么更快更稳。

OFFSET 的问题keyset 游标服务端游标对比

① LIMIT/OFFSET 的深翻页陷阱

OFFSET 100000 时，数据库仍要 先读出并跳过前 10 万行 才能返回第 10 万行之后的数据——越翻越慢。并且在并发写入时，OFFSET 还会导致 重复或漏读（插入使行整体平移）。

SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 100000;  -- 慢且可能漂移

② keyset（游标 / Seek）分页

改为 记住上一页最后一行的值，用索引条件定位：

SELECT * FROM orders
WHERE id < :last_id          -- 上一页最后一条的 id
ORDER BY id DESC LIMIT 20;

这个条件走 B-tree 索引 直接定位，不扫描跳过前面的行；且插入不影响结果集（基于有序键，稳定）。

要点：keyset 必须基于 唯一且有序 的列（如 id 或 (created_at, id) 复合），否则边界行会重复。

③ 服务端游标

对真正需要“翻很多页”的场景，可用 DECLARE CURSOR 在服务端维持游标，分批 FETCH。代价是占用连接与事务，需配合连接池谨慎使用。

BEGIN; DECLARE c CURSOR FOR SELECT * FROM orders ORDER BY id;
FETCH 20 FROM c;  -- 翻页
CLOSE c; COMMIT;

④ 方案对比

方案深翻性能数据稳定性适用
OFFSET差（随深度恶化）差（并发漂移）浅翻、后台
keyset优（O(log n)）好无限滚动、API
服务端游标优好大批量导出
