结构体里塞了 padding，sizeof 比成员之和还大。对齐是为了让 CPU 一次总线取数，cache line 对齐还能避免伪共享。

01为什么对齐

  • CPU 按字长（4/8 字节）读写内存，一次取一个对齐单元。
  • 未对齐访问可能跨两次总线，甚至在某些架构触发硬件异常。
  • x86 容忍未对齐但变慢；ARM/MIPS 等 RISC 架构可能直接异常。

02偏移与 sizeof 计算

// 在 8 字节对齐环境下
struct S {
    char a;     // 偏移 0, 占 1
    // padding 7 字节
    int  b;     // 偏移 8, 占 4
    short c;    // 偏移 12, 占 2
    // padding 2 字节(对齐到 8 的倍数)
};
// sizeof(S) = 16，而非 1+4+2 = 7
要点：规则：每个成员偏移 = 上一个偏移 + 大小，再向上取整到该成员的对齐系数；结构体整体大小再向上取整到最大成员对齐系数。

03#pragma pack

#pragma pack(1)   // 取消填充，紧凑但访问变慢
struct P { char a; int b; short c; };  // sizeof = 7
#pragma pack()    // 恢复默认
要点：网络协议、文件格式常用 1 字节对齐省空间；但跨平台直接 memcpy 结构体要小心对齐差异导致布局不一致。

04cache line 与伪共享

  • cache line 通常 64 字节，CPU 以 line 为单位缓存。
  • 两个线程改同一 cache line 的不同字段，会互相使对方缓存失效，叫伪共享(false sharing)。
  • 高频并发计数器常补足 padding 到 64 字节，隔离到独立 cache line。
要点：伪共享不易察觉但能让多核程序性能腰斩；用 perf 看 cache-miss 或用填充隔离是常用解。

05常见疑问

问：为什么 sizeof 比成员和还大？

编译器插入了 padding 填充字节以满足对齐，让每个成员落在自己的对齐边界上。

问：什么时候要主动 pack？

需要把结构体原样写到 wire/磁盘、且对端按固定布局解析时；普通内存对象不建议。

第一层 · 概念与判定

内存对齐指数据存放的起始地址是其类型大小的整数倍。CPU 按字/缓存行粒度访存，未对齐的访问在某些架构直接触发硬件异常，或在 x86 上付出多次访存+拼接的代价。

  • 对齐好处：单次访存可取全、利于缓存行、满足 SIMD 与原子操作要求。
  • 代价在结构体：编译器插入 padding 补齐，sizeof 往往大于字段和。
  • 判定：性能莫名掉、原子操作崩溃、跨语言结构体大小对不上 → 查对齐。

第三层 · 排障与边界

  • 伪共享（false sharing）：两个 CPU 各改同一缓存行的不同变量，互相 invalidate；用 64B padding 或 alignas(64) 隔开。
  • 结构体瘦身误删 padding：重排字段把小类型放一起可减 padding，但别为省字节牺牲热路径对齐。
  • 跨缓存行原子操作：lock-free 操作要求变量不跨缓存行，否则 CAS 在某些平台不保证。
  • 序列化对齐错位：把结构体 memcpy 到网络/磁盘，对方对齐规则不同会读错。

第四层 · 原理与取舍

对齐让 CPU 一次总线事务取完整数据；未对齐可能跨越两个缓存行，需要两次读+移位拼接，甚至在某些 RISC 架构直接 fault。SIMD 指令（如 AVX）通常要求 32/64 字节对齐，否则降级或异常。padding 是以空间换访存效率的通用取舍。

为什么 x86 不对齐也能跑但慢？

x86 硬件会拆成多次访存并拼接，正确性无损但多花周期；RISC（ARM/MIPS）则常直接抛异常。

怎么减少结构体 padding？

按字段大小从大到小排列，让小字段填充已有空隙，从而减小 sizeof 与缓存占用。
