🔙 CDN 回源：边缘没有时的那一次远行

回源是 CDN 中唯一打到源站的请求，控制回源量就是控制源站成本与稳定性。

先建立直觉：便利店缺货时的调货

你去楼下便利店买东西，店里有就直接拿（边缘命中，几毫秒）；店里没有，店员就得从中心仓库调货（回源）——你要等，店员也要额外跑一趟。

如果这家店经常缺货，中心仓就会被频繁打扰，成本上升、还可能爆仓。所以便利店要尽量让热门商品不断货（提高命中率 / 预热）。

回源的本质：CDN 里唯一会打到源站的那部分请求。所有 CDN 优化的核心目标之一就是把回源量压到最低。

什么时候会回源

触发场景说明能否避免
首次访问这个资源从没被缓存过可用预热提前铺货
缓存过期TTL 到期设更长 TTL / 用 hash 文件名
主动刷新你触发了 purge必然（这是有意为之）
参数变化URL 带随机参数，被当作新 key去掉随机参数，或配置忽略参数
配置了不缓存no-store / private检查响应头
「参数变化」是最隐蔽的回源杀手。很多前端为了绕缓存会给 URL 加 ?t=时间戳 或 ?random=xxx，CDN 会把它当成一个全新的 key，每次都回源，命中率归零。正确做法：需要更新时用内容 hash 作为文件名，而不是加随机查询串；或在 CDN 控制台配置「忽略指定查询参数」。

分层回源：不要所有边缘都直连源站

好处：① 源站面对的连接数从「边缘节点数」降到「区域节点数」；② 区域节点缓存命中后，边缘等待时间也更短；③ 源站短暂抖动时，区域缓存还能兜住一部分。

回源合并（回源保护）

热点资源刚过期的瞬间，可能有几百个边缘节点同时发现失效、同时回源 —— 这就是 CDN 版的缓存击穿。

后果：源站瞬间承受一波尖峰，可能直接打挂。解决：开启回源合并（也叫回源保护 / Collapsed Forwarding），让同一个资源的并发回源只放行第一个，其余等待并复用结果。这和我们在 Redis 里用互斥锁解决击穿是完全相同的思路。

降低回源率的实用清单

  1. 文件名带内容 hash（app.3f2a1b.js），配合超长 TTL（如一年）——最有效；
  2. 去掉 URL 里的随机/时间戳参数，或在 CDN 配置忽略；
  3. 区分静态与动态：静态走 CDN 长缓存，HTML 与接口 no-cache；
  4. 预热：大促、发版前主动把新资源推送到边缘；
  5. 开启分层回源与回源合并；
  6. 监控回源率与回源带宽，异常时排查是否有新引入的随机参数。

🎯 面试问答

Q：回源率多少算正常？
A：静态资源类业务，字节命中率 95% 以上比较健康；低于 90% 就该排查。但要注意区分请求命中率和字节命中率——视频等大文件即使请求命中率一般，字节命中率也可能很高（因为大文件命中了就占绝大部分流量）。关注字节命中率更能反映源站带宽压力。

Q：为什么我设了很长的 max-age，命中率还是上不去？
A：常见原因是 URL 不唯一：① URL 带了随机参数或时间戳；② 同一个资源有多个不同 URL（如带/不带 www、http/https）；③ 资源本身是长尾的（访问一次就不再访问）。排查方法：看 CDN 的「热门 URL 排行」和「回源 TOP URL」，如果发现大量几乎相同但参数不同的请求，就是参数问题。

Q：回源合并是什么原理？
A：和 Redis 用互斥锁解决击穿完全同构：当多个边缘节点对同一个资源同时回源时，只允许第一个请求真正上行到源站，其余请求挂起等待，拿到结果后一起返回。这样源站对这个资源只会被打一次，而不是几百次。代价是等待的那一批请求延迟略高，但远好于把源站打挂。

Q：源站挂了，CDN 还能继续服务吗？
A：部分可以。已经缓存在边缘且未过期的资源仍能正常返回，用户无感知；但未缓存或已过期的资源会回源失败。所以 CDN 客观上提供了一定的容灾能力，这也是它的隐藏收益之一。更进一步可以配置备用源站（多源回源），主源失败自动切备源。

回源机制与关键数字

回源是 CDN 中唯一会打到源站的动作，也是成本和风险的集中点。核心指标是回源率——它直接决定源站带宽和稳定性。

回源率计算

# 回源率（最重要的一个指标）
#   回源率 = 回源流量 / CDN 总流量 = 回源请求数 / 边缘总请求数
#
# 健康值参考：
#   静态小文件（图片/JS/CSS）   回源率 < 5%     （命中率 > 95%）
#   视频点播                    回源率 < 10%
#   动态/个性化内容              回源率 可能 50%+  <-- 这类不该放 CDN
#
# 源站带宽估算：
#   源站带宽 = CDN 总带宽 x 回源率
#   例：CDN 峰值 10 Gbps，回源率 3%  -> 源站只需 300 Mbps
回源类型说明适用
首次回源边缘节点没有缓存，第一次取不可避免，靠预热减少
过期回源缓存 TTL 到期后重新取靠合理 TTL 控制频率
回源校验（304）带 If-None-Match / If-Modified-Since 问源站源站返回 304，只传头不传体，省 90%+ 带宽
强制回源带 Cache-Control: no-cache 或刷新发布后更新内容
Range 回源只取文件的一部分（分片）大文件必备，避免为了 1MB 拉 1GB
回源合并多个相同请求合并成一次回源热点内容，防止惊群

回源诊断命令

# 用 curl 判断有没有命中 CDN 缓存
curl -I https://cdn.example.com/a.jpg
#   看这几个响应头：
#   X-Cache: HIT / MISS / EXPIRED      <- 各家字段名不同
#   Age: 3600                          <- 在 CDN 里已缓存多少秒；>0 说明命中
#   Via: ...cache...                   <- 经过的代理
#   X-Served-By: cache-nrt-xxx         <- 具体是哪个边缘节点
#   CF-Cache-Status: HIT               <- Cloudflare 的字段

# 对比两次请求，Age 递增说明命中
curl -sI https://cdn.example.com/a.jpg | grep -i '^age'

# 验证回源校验（304）：带上一次响应的 ETag
ETAG=$(curl -sI https://cdn.example.com/a.jpg | grep -i etag | tr -d '\r' | cut -d' ' -f2)
curl -I -H "If-None-Match: $ETAG" https://cdn.example.com/a.jpg
#   -> HTTP/1.1 304 Not Modified  （无响应体，省带宽）

# 源站侧看回源来源（确认是 CDN 节点而不是真实用户）
grep 'cdn-node' /var/log/nginx/access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head

回源优化与故障排查

手段效果注意
合理设置 TTL回源率直接下降静态资源带版本号可设 1 年（max-age=31536000, immutable）
预热消除首次回源的慢请求大促前必做；预热要分批限速，否则打爆源站
Range 分片回源大文件回源流量降 50%+源站必须支持 Range，返回 206
回源合并热点内容的惊群降为 1 次回源需 CDN 支持，或源站做单飞
回源超时与重试避免源站慢拖垮边缘超时建议 5~15s；重试要限制次数（1~2 次）
多级回源（边缘→区域→中心）进一步降低源站压力层级越多，一致性越难保证
故障现象原因处理
回源率突然飙升① 大量新内容/新 URL；② 缓存规则被误改；③ URL 带了随机参数检查是否有时间戳/UUID 参数；配置忽略参数缓存
源站被回源打爆缓存 TTL 太短 / 没预热 / 热点集中延长 TTL + 回源合并 + 预热
回源 502/504源站超时或拒绝；回源 HOST 配错查源站负载；确认回源 HOST 与源站虚拟主机匹配
回源 403源站防盗链把 CDN 节点拦了把 CDN 回源 IP 段加入白名单；或回源带合法 Referer
内容更新了但 CDN 还是旧的TTL 未到期用刷新（按 URL）或改 URL 版本号（更推荐）
HTTPS 回源失败证书/协议不匹配确认源站证书有效、SNI 正确、协议版本一致
  • 最有效的两条实践：① 静态资源文件名带内容哈希（app.a1b2c3.js），然后 TTL 设一年 + immutable——这样永远不用刷新，发布即生效；② 刷新优于改 TTL：真要更新就主动调刷新 API，别把 TTL 设成几分钟去换取「准实时」，那会让源站压力暴涨。
  • 刷新有配额：各家 CDN 每天的刷新 URL 数都有上限（常见几百到几万条/天），大批量更新要走目录刷新或直接改版本号。
  • 回源 HOST 是最容易配错的一项：它决定源站用哪个虚拟主机响应。配错会返回源站默认站点的内容或 404，且现象诡异（部分 URL 正常、部分不正常）。
回源率多少算健康？

静态资源 <5%（命中率 >95%）是及格线，做得好能到 1~2%。如果超过 10%，说明缓存策略有问题——八成是 URL 带了变化参数（时间戳、随机数、用户 ID）或 TTL 设得太短。动态内容（个性化 API）本来就不该走缓存，别用回源率衡量。

304 回源和普通回源差多少？

差一个数量级。普通回源要传完整响应体（比如 2MB 图片），304 只传几百字节的响应头。对源站来说带宽省 99%+，但对请求数没有帮助（还是要打一次源站），所以源站的 QPS 压力不变。想同时省请求数，得靠延长 TTL。

CDN 刷新和预热有什么区别？

刷新是「把边缘的旧内容删掉」，下次请求会回源取新的（会产生回源流量）；预热是「主动把内容推到边缘节点」，让首次访问就命中（不产生用户触发的回源）。正确顺序是：先刷新、再预热，尤其大促前。只预热不刷新会预热到旧内容。
