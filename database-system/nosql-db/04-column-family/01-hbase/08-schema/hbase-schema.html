📐 HBase 模式设计

列族划分、表属性、高表 vs 宽表、版本与 TTL 的实战取舍

模式设计的四个决策点

① RowKey唯一索引，决定查询与分布（见 RowKey 篇）
② 列族划分物理隔离单位，2~3 个为宜
③ 高表 vs 宽表一行多列 还是 多行少列
④ 表/列族属性VERSIONS、TTL、压缩、BloomFilter、块大小

列族怎么划分

划分依据只有一条：把访问模式相同、大小与增长速率相近的列放在一起。因为列族是物理隔离的，scan 指定列族可以完全不读其他列族的文件。

场景划分方式理由
用户画像base（基本信息）+ behavior（行为序列）base 小而常读，behavior 大且只批量扫
订单info（订单头）+ items（商品行）查订单头时不必读庞大的商品行
时序单列族 v，限定符 = 时间戳偏移数据同质，无需拆分
消息meta（元数据）+ body（正文）列表页只读 meta
⚠️ 列族数量上限建议 2~3 个。原因：①每个列族有独立 MemStore，列族多 → MemStore 摊薄 → 各自触发 flush → 小文件爆炸；②flush 是 Region 级触发所有 Store，列族多则该次 flush 产生的文件多；③compaction 压力成倍上升。

高表 vs 宽表

维度宽表高表
原子性整行原子（一行内所有列）只有单行原子，跨行无事务
查询灵活性差（列不能做范围条件）好（维度进 rowkey 可范围扫）
分片能力差（一行不可再分）好（按 rowkey 自然分布）
单行大小可能很大（受 Region 大小限制）小且均匀
适用场景维度有限、需要整体读、要原子维度多、数据量大、要范围查（推荐）
💡 实践倾向：优先高表。因为「一行不可再分」意味着单行数据只能在一台机器上，无法被 Region 分片利用；而高表让每个 RowKey 独立分布，天然均衡。

表与列族属性

create 'user',
  { NAME => 'base',                 -- 列族名
    VERSIONS => 1,                  -- 保留版本数
    TTL => 31536000,                -- 过期秒数（365 天）
    COMPRESSION => 'SNAPPY',        -- 压缩：NONE/GZ/LZO/SNAPPY/ZSTD/BROTLI
    BLOOMFILTER => 'ROW',           -- ROW / ROWCOL / NONE
    BLOCKSIZE => 65536,             -- data block 大小（默认 64KB）
    BLOCKCACHE => true,             -- 是否进读缓存
    IN_MEMORY => false,             -- 是否常驻（元数据表可用）
    DATA_BLOCK_ENCODING => 'FAST_DIFF',  -- 块内编码，省空间
    MIN_VERSIONS => 0,
    KEEP_DELETED_CELLS => false },
  { NAME => 'stat', VERSIONS => 3, TTL => 86400, COMPRESSION => 'SNAPPY' },
  { NUMREGIONS => 16, SPLITALGO => 'HexStringSplit' }   -- 预分区

-- 修改属性（需先 disable）
disable 'user'
alter 'user', { NAME => 'base', VERSIONS => 3 }
enable 'user'

属性选择指南

属性建议说明
COMPRESSIONSNAPPY（默认推荐）压缩比 ~2-4x，CPU 开销低；ZSTD 压缩比更高但更耗 CPU；GZ 压缩比最高最慢
DATA_BLOCK_ENCODINGFAST_DIFF块内前缀编码，rowkey 相似时省很多空间；几乎无 CPU 代价
BLOOMFILTERROWget 场景收益大；ROWCOL 更精确但体积大；纯 scan 可关
BLOCKSIZE64KB（默认）读多写少可小一点（32KB）；全表扫描多可大一点（128KB）
VERSIONS1（默认）保留 N 个版本 ≈ 存储放大 N 倍，谨慎加大
TTL按需设置过期数据在 major compaction 时清理
BLOCKCACHEtrue随机读多要开；纯批量扫描的列族可关
IN_MEMORYfalsetrue 会让该列族的 block 优先常驻缓存，只给极小的元数据列族用

建表检查清单

  • ✓ RowKey 已按「散列前缀 + 主维度 + 次维度」设计，能覆盖最高频查询
  • ✓ 预分区已规划（NUMREGIONS / SPLITS），Region 数 ≈ 总量 ÷ 单 Region 目标大小
  • ✓ 列族 ≤ 3 个，按访问模式与增长速率划分
  • ✓ 开启 SNAPPY 压缩 + FAST_DIFF 编码
  • ✓ BloomFilter 设为 ROW
  • ✓ VERSIONS 明确设置（不要留默认后误以为能查历史）
  • ✓ 时序/日志类设置了 TTL
  • ✓ 预估单 Region 大小，调好 max.filesize 避免频繁 split

改名与迁移的注意点

⚠️ 列族名一旦确定很难改（要 disable → alter → enable，且大表耗时很长）。列族名建议用短名（如 b、s），因为每个 cell 都会存列族名。生产上见过用 basic_info 这种长名白白浪费大量存储的案例。

🎯 常见问法与答题要点

Q：列族名用长名有什么影响？

A：列族名和列限定符都会完整存进每个 cell。用 basic_info（10 字节）而不是 b（1 字节），在几十亿 cell 的表上就是几十 GB 的差距，还要算上 MemStore/BlockCache 的内存占用。所以列族名、限定符名都要尽量短，这是 HBase 廉价却常被忽略的优化。

Q：高表和宽表怎么选？

A：优先高表。宽表（一行几百万列）的问题是：一行数据不可再分，永远只能在一台 RegionServer 上，无法被 Region 分片利用，且单 region 过大。高表把维度编进 rowkey（如 user_001_20260101），每个 key 独立分布、可范围扫描、可被 split。宽表的唯一优势是整行原子——如果需要一次性原子读写某实体的全部属性，才考虑宽表。

Q：VERSIONS 设成 3 会怎样？

A：同一个 cell 会保留最近 3 个时间戳版本，存储放大约 3 倍（每个版本都是完整的 cell，含 rowkey + 列 + ts + 值），compaction 与 scan 开销同比例上升。只有确实需要历史版本（审计、时序回溯）时才设 >1，并建议配合 TTL 限制总量。默认是 1。

Q：压缩算法选 SNAPPY 还是 ZSTD？

A：SNAPPY 是安全默认：压缩比 2~4x，CPU 开销很低，几乎不影响吞吐。ZSTD（HBase 2.x+）压缩比更高（能再省 20~40% 空间），但压缩时 CPU 消耗更大，适合冷数据、读多写少的表。GZ 压缩比最高但最慢，一般不用。另外别忘了开 DATA_BLOCK_ENCODING=FAST_DIFF——它做的是块内前缀编码，几乎零 CPU 成本却能再省不少空间，和压缩可以叠加使用。

Q：TTL 设了数据会立刻消失吗？

A：不会。查询时立刻不可见（读路径会跳过超过 TTL 的 cell），但物理删除要等 major compaction。所以设了 TTL 后磁盘空间不会马上下降，这是正常的。如果空间长期不降，检查 major compaction 有没有正常跑（默认 7 天一次）。

Q：为什么 alter 改列族属性要先 disable 表？

A：因为列族属性是物理存储格式的一部分（压缩算法、块大小、编码方式），改变它意味着新旧 HFile 格式不一致。HBase 要求先 disable 让所有 Region 下线并完成 flush，alter 后再 enable，这样新写入的文件统一用新格式；旧文件在下一次 compaction 时被转成新格式。大表 disable/enable 耗时很长，所以属性要一开始就规划好。

Q：一张表该建多少个 Region？

A：用公式估算：Region 数 ≈ 预计总数据量 ÷ 单 Region 目标大小（默认单 Region 上限 10GB，生产常调到 20~50GB）。例：预计 2TB、目标 20GB/Region → 100 个 Region。再结合集群节点数取整（10 节点 → 每节点 10 个）。同时要保证 Region 数 ≥ 写入并发度需求。别过度切分——空 Region 也是负担。
