FaaS 适用场景与成本模型

Serverless 不等于更便宜。它把成本从「为闲置资源付费」换成「为调用次数和运行时长付费」，哪个划算取决于负载曲线。

成本模型换了个方向

长驻服务的成本是「实例数 × 时间」，无论有没有请求都在花钱；FaaS 的成本主要是「调用次数 × 单次时长 × 单价」，空闲时不花钱。这个差异导致存在一个成本交叉点：负载低于它 FaaS 更省，高于它长驻更省。

负载特征长驻服务FaaS
极低且不规律（一天几次）长期闲置，浪费严重明显更省
有明显波峰波谷按峰值常备，谷时闲置通常更省（自动扩缩）
持续高负载（接近满负荷）资源利用率高，单位成本低通常更贵（单价含托管溢价）
稳定中等负载成本可预测可能接近或略贵，需实测

算一次成本交叉点

不要只看一项

FaaS 通常按调用次数 + 运行时长（GB·秒）计费，还可能有请求数、出网流量、预置并发、日志存储等。只算其中一项会显著低估。

用真实流量曲线

平均 QPS 意义有限。拿到按小时的调用量分布，才能判断峰谷差有多大——峰谷差是 FaaS 收益的主要来源。

统一口径

长驻：常备实例数 × 时长 × 单价。FaaS：调用次数 × 平均时长 × 单价 + 附加项。两者都要加上运维人力成本的差异。

冷启动、连接数、超时

FaaS 的突发扩容会冲击下游数据库连接；长驻服务的运维、扩缩容、故障恢复也是人力成本。把这些折算进来再比。

什么样的负载适合 FaaS

适合原因不适合原因
事件驱动的异步处理天然按事件触发，无需常驻长连接服务（WebSocket）连接要一直保持，按次计费不合适
定时任务与批处理执行完就结束低延迟强要求的在线接口冷启动会落到尾延迟上
流量剧烈波动的入口自动扩缩，不用为峰值常备持续高吞吐的核心链路单价溢价在满负荷时放大
文件/图片处理、转码CPU 密集但短暂需要大量内存常驻缓存的服务每次调用都要重建缓存
胶水层与集成逻辑轻量、变更频繁有复杂状态机或长事务的流程执行时长与状态管理受限

被低估的约束

除了成本，还有几项约束常被忽略，往往比钱更致命：

约束表现应对
执行时长上限单次调用有最长时限长任务拆分成编排流程，或改用容器/批处理服务
无本地状态实例随时回收，内存不可靠状态外置到存储/缓存；不要依赖全局变量缓存
下游连接风暴每次扩容都新建数据库连接设置并发上限，使用连接池或代理，评估数据库容量
冷启动尾延迟新实例初始化落到用户等待精简依赖、预置并发、或把敏感入口改回长驻
供应商锁定事件格式与运行时绑定平台核心业务逻辑与平台适配层分离

混合架构往往是最优解

实际系统很少全 Serverless 或全长驻。常见且有效的划分：对延迟敏感的入口保持长驻服务，把异步处理、定时任务、流量突发的边缘功能放到 FaaS，中间用消息队列或事件总线连接。

这样既保住了核心链路的延迟稳定性，又让波动部分享受弹性扩缩的成本优势。判断依据很简单：这段逻辑的负载曲线是平稳的还是剧烈波动的？对尾延迟的容忍度有多高？

边界与误区

「Serverless 就是不用管服务器」是营销说法而非事实。你仍然要管：函数粒度划分、并发配额、依赖包体积、冷启动、下游容量、可观测、成本控制。它转移的是服务器运维这部分工作，不是全部运维工作。

成本怎么算（公式 + 例子）

成本公式

FaaS 成本 = 请求数 × 请求单价
          + 执行时间(GB-s) × GB-s 单价
          + （冷启动时间是否计费，各平台不同）

GB-s = 内存规格(GB) × 执行时长(s) × 调用次数

例子：每月 1000 万次调用，平均 200ms，内存 512MB(0.5GB)
  GB-s = 0.5 × 0.2 × 10,000,000 = 1,000,000 GB-s

再算冷启动占比（这是 FaaS 最大的隐藏成本）：
  若冷启动率 1%、冷启动耗时 800ms、业务耗时 200ms
  -> 冷启动带来的额外时间 = 1e6 × 0.01 × 0.8s = 8,000 s
  -> 折算 GB-s = 0.5 × 8000 = 4,000 GB-s（占总 GB-s 的 0.4%）
杠杆动作效果
降内存规格1024MB → 512MBGB-s 直接减半（但 CPU 通常按内存比例分配，可能变慢，要先测）
降执行时长减少冷启动、复用连接、精简依赖时长和内存是乘法关系，两头都能省
降冷启动预留实例 / 预热 / 精简包体对延迟敏感场景是首要优化项
批量化把 N 条消息攒批再处理请求数从 N 降到 N/batch，请求计费大幅下降
合并到常驻服务稳定高负载部分迁回容器FaaS 在高且稳定的负载下通常比常驻容器贵

FaaS 经济的分水岭：负载低且有明显波峰波谷时 FaaS 便宜（不为闲置付费）；负载高且平稳时，常驻容器的单位算力成本更低。粗略的经验：当某服务的 CPU 利用率长期 > 30%~50%，就该认真算一下迁回容器是否更省。

冷启动的构成与优化

阶段耗时量级优化手段
调度 / 拉起运行时几十 ~ 几百 ms预留实例（Provisioned Concurrency）
下载并解压代码包与包体大小正相关精简依赖：只打包真正用到的模块；包体从 50MB 降到 5MB 效果立竿见影
运行时初始化语言差异大Java/C# 最重（JVM/CLR 启动），Go/Rust/Python 较轻
业务初始化可控，往往是最大头连接/客户端提到全局作用域复用，别在 handler 里每次新建

FaaS 适合什么场景？

事件驱动、流量尖峰明显、低频任务：图片/视频处理、 webhook、定时任务、数据清洗、CRON。不适合：长连接、超长任务、极低延迟稳态服务、有复杂本地状态的服务。

为什么我的 FaaS 账单比容器还贵？

多半是负载太稳太高（FaaS 单位算力溢价）+ 冷启动占比高 + 每次调用都新建连接导致时长虚高。先用 GB-s 拆解，看是次数多还是单次久。

自检

为什么高流量下 FaaS 可能比长驻贵很多？

FaaS 单价里包含了托管、自动扩缩、按次计费的溢价。负载低时你省掉了闲置成本，溢价被抵消；负载持续高时几乎没有闲置可省，溢价就完全体现在账单上。此外频繁冷启动还会额外增加时长计费。

成本模型的根本差异：按什么计费

常驻服务按「时间」付费，函数按「执行次数与时长」付费。这个差异决定了它们的成本曲线形状完全不同：常驻服务是水平线，函数是过原点的斜线，两条线必然存在一个交叉点。

对比项常驻服务函数 FaaS
计费依据实例数 × 运行时长调用次数 × 单次时长 × 规格
空闲成本空跑也要付钱没人调用就是零成本
成本曲线近似水平线，与流量无关近似过原点斜线，与流量成正比
低流量时明显浪费非常划算
高流量时摊薄后更便宜可能超过常驻成本
额外成本运维人力、容量规划冷启动、网关调用、可观测开销
# 成本交叉点怎么算（统一口径后再比） # 常驻：按实例小时计费 server_cost = instances * price_per_instance_hour * hours # 例：2 台 * 0.4 元/小时 * 730 小时/月 ≈ 584 元/月（不含空闲浪费） # 函数：按调用次数 + 执行时长（GB-s）计费 faas_cost = requests * price_per_request \ + requests * avg_duration_s * memory_gb * price_per_gb_s # 例：1000 万次/月，平均 200ms，512MB(0.5GB) # 请求费：1000万 * 0.0000013 ≈ 13 元 # 时长费：1000万 * 0.2s * 0.5GB * 0.000035 ≈ 35 元 # 合计约 48 元/月 # 交叉点：令两者相等，反解请求量 # 当请求量低于交叉点，函数更便宜；高于交叉点，常驻更便宜 # 别忘了这几项隐性成本： # - 冷启动：低频调用时冷启动占比高，实际时长大于平均时长 # - 连接数：每次调用新建数据库连接会拖慢并增加开销 # - 网关与日志：API 网关调用费与日志存储费常常被漏算 # - 运维人力：常驻服务需要人管容量，这部分也是钱

四类负载的适配度

判断一个任务适不适合函数化，核心看两个特征：流量是否波动、单次执行是否短小无状态。

负载类型适配度原因建议
突发且稀疏的任务非常适合空闲时不花钱，突发时自动扩优先用函数
事件驱动的胶水逻辑非常适合短小、无状态、天然由事件触发优先用函数
定时任务与批处理片段较适合运行时间短，按次计费划算注意单次时长上限
稳定高流量的核心接口不太适合成本高于常驻，且冷启动影响体验用常驻服务
长耗时任务不适合超过平台单次时长上限用容器或专用任务队列
强状态与长连接不适合实例随时回收，状态无处安放用常驻服务或有状态服务

被低估的约束一：冷启动

冷启动包括拉镜像、初始化运行时、建立连接等，对低频函数可能占到实际耗时的大部分。缓解手段：精简依赖包体积、把连接建立放到初始化阶段复用、对延迟敏感的接口配置预热或预留实例。

被低估的约束二：并发与连接

函数可能瞬间扩出成百上千个实例，每个实例都会去连数据库，很容易把连接数打满。必须配连接池代理或限制最大并发，否则扩缩容反而会压垮下游。

混合架构往往是最优解

现实中最常见的结论不是「全上函数」或「全不用」，而是按流量特征分层：稳定主干用常驻，波动与长尾用函数。

核心链路稳定高流量 → 常驻服务，成本与延迟都更优
边缘逻辑低频、胶水类 → 函数，省运维
突发任务批处理、回调 → 函数，天然弹性
定时任务周期性作业 → 函数，按次计费
长任务超时的重活 → 容器或专用队列
统一入口用网关把两者收敛到同一域名下
函数一定比常驻便宜吗？

不一定。低流量时函数便宜很多，但流量持续走高后，按次计费会超过常驻实例的固定成本。判断方法是算出交叉点，再看你的实际请求量落在哪一侧。

为什么算出来的成本和账单差很多？

常见漏算项：网关调用费、日志与指标存储费、冷启动期间也计时长、以及为压缩冷启动而配置的预留实例费用。算成本时要把这些一并计入，否则结论偏乐观。

函数能替代容器吗？

不能互相替代，而是互补。函数适合短小、事件驱动、流量波动的任务；容器适合长驻、有状态、需要精细控制运行时的服务。很多团队把两者放在同一个平台上统一管理，而不是二选一。

什么时候应该把函数迁回常驻？

当它的调用量持续稳定且足够高、成本已经超过常驻，或者它对冷启动延迟非常敏感、预留实例成本抵消了弹性收益时。这是正常的架构演进，不是失败。

一句话总结：FaaS 的价值不在「更便宜」，而在「把容量规划这件事外包出去」。你要付的是弹性溢价，换来的是不必为峰值常备资源、也不必为闲置付费。
