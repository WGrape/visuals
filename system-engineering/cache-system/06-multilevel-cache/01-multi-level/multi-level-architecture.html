🏗️ 多级缓存：把每一层放在它该在的位置

本地缓存挡住热点、分布式缓存提供共享、数据库兜底——三层各司其职，兼顾速度、容量与一致性。

L1 本地

纳秒~微秒，挡住热点

🌐

L2 Redis

毫秒，共享与中心化

🗄️

L3 数据库

最终数据源

🔗

CDN

最外层，静态资源

先建立直觉：家门口便利店 → 区域超市 → 总仓库

  • 家门口便利店（本地缓存）：最快，走路就到，但货品少，且每家店各自进货。
  • 区域超市（Redis）：稍远，货品全，大家共享同一份库存。
  • 总仓库（数据库）：最远最慢，但什么都有，是最终真相。

绝大多数需求在便利店就解决了；便利店没有才去超市；超市也没有才调仓库。

完整架构

反向回填上层 用户请求 CDN 静态资源 （最外层） L1 本地缓存 Caffeine 纳秒~微秒 L2 Redis 分布式共享 毫秒级 数据库 最终真相 兜底 反向回填：查到数据后逐级写回上层（DB → Redis → 本地） 每加一层，速度更快但一致性更弱 —— 多级缓存的全部设计都是在这两者之间取舍

每一层的定位

层级速度容量是否共享能否主动失效
CDN最快（就近）大全网共享可（刷新，但有延迟）
L1 本地缓存极快（进程内）小各实例独立难（需广播）
L2 Redis快（网络往返）大✅ 共享✅ 可以
L3 数据库慢最大共享—
核心矛盾：越快的层越难保持一致。本地缓存最快，但它分散在每个进程里，无法被中心化地主动失效——这是多级缓存最本质的难题（详见「L1 失效」）。

读路径与写路径

读（逐层查找 + 反向回填）

func Get(id int64) (*User, error) {
    if u, ok := localCache.Get(id); ok { return u, nil }     // ① L1
    if u, ok := redis.Get(key(id)); ok {                      // ② L2
        localCache.Set(id, u)                                 //    回填 L1
        return u, nil
    }
    u, err := db.Query(id)                                    // ③ L3
    if err != nil { return nil, err }
    if u != nil {
        redis.SetEX(key(id), ttl, u)                          // 回填 L2
        localCache.Set(id, u)                                 // 回填 L1
    }
    return u, nil
}

写（自上而下失效）

func Update(u *User) error {
    if err := db.Update(u); err != nil { return err }   // ① 先更新数据库
    redis.Del(key(u.ID))                                 // ② 删除 Redis（中心化，可主动失效）
    mq.Publish("cache-invalidate", u.ID)                 // ③ 广播各实例删除本地缓存
    return nil
}
两条铁律：
• 读：自外向内查找，命中即返回，然后自内向外回填。
• 写：先更新数据库，然后自内向外（先中心后本地）失效——因为中心化的层能可靠删除，本地层要靠广播。

代价与风险

代价说明缓解
一致性变弱层级越多，副本越多，不一致窗口越大本地缓存短 TTL + 广播失效
排查变难数据不对时要逐层确认响应加调试头标明来源；提供强制穿透参数
内存成本本地缓存占用应用堆内存严格控制容量，只放最热数据
复杂度代码与运维都更复杂只在确实需要时引入
不要为了「架构完整」而堆层数。每一层都带来一致性风险和运维负担。判断标准：只有当某一层能明确解决一个已观测到的问题（如热点把 Redis 单分片打满）时才加它。

🎯 面试问答

Q：一定要上多级缓存吗？
A：不一定。大多数业务 L2（Redis）+ DB 两层就够了。引入 L1 本地缓存的典型理由是：① 存在极端热点，把 Redis 单分片打满；② 对延迟要求极苛刻，连 Redis 的网络往返都嫌慢；③ 想降低 Redis 的读压力与成本。如果这些都不成立，加本地缓存只会带来一致性问题，得不偿失。

Q：数据更新时，各级缓存的失效顺序是什么？
A：先更新数据库，再自内向外失效：① UPDATE DB；② DEL Redis（中心化，能可靠删除）；③ 广播通知各实例删除本地缓存。顺序很重要——必须先更新数据库再删缓存（否则并发读可能把旧值写回缓存）；而 Redis 要在本地缓存之前处理，因为本地缓存分散在各进程，只能靠异步广播，可靠性最低，放在最后。

Q：本地缓存和 Redis 的数据不一致时怎么办？
A：这是必然会发生的，目标是缩短窗口而非消除。手段：① 本地缓存设很短 TTL（1~10 秒）作为兜底；② 变更时广播失效加速收敛；③ 只把能容忍陈旧的数据放本地缓存（如商品描述），库存余额这类强一致数据不放；④ 提供强制刷新入口供运营/客服手动纠正。

Q：多级缓存的命中率应该怎么统计？
A：分层统计，不要只看总体。至少要分别知道：L1 命中率、L2 命中率、以及整体回源到 DB 的比例。这样出问题时才能定位：L1 命中率暴跌说明本地缓存配置或广播失效有问题；L2 命中率暴跌可能是容量不足或雪崩；回源率上升说明整体缓存效果变差。没有分层监控，多级缓存会变成黑盒。

第一层 · 每一层解决什么问题

多级缓存不是「多堆几层」，而是每一层对抗一种不同的瓶颈。CDN 抗网络距离，本地缓存抗进程内访问开销，分布式缓存抗数据库回源。层次错了，加了也没用。

层级典型延迟容量解决什么代表
浏览器/客户端缓存0ms（不发包）几十 MB完全不发请求HTTP Cache、localStorage
CDN / 边缘5~30msTB 级网络距离（跨省跨国的 RTT）CloudFront、阿里云 CDN
接入层缓存1~5msGB 级重复请求、热点Nginx proxy_cache、OpenResty
应用本地缓存50~200nsMB~GB进程内访问开销、极致延迟Caffeine、Go 的 map/sync.Map
分布式缓存0.2~1msGB~TB数据库回源、共享状态Redis、Memcached
数据库自身缓存—GB磁盘 IOInnoDB Buffer Pool、PG shared_buffers
  • 数量级要记牢：本地缓存 ~100ns，Redis ~0.5ms，数据库 ~5ms，跨省网络 ~30ms。每跨一层差 10~100 倍，这就是分层的意义。
  • 不是所有系统都需要全部层级：一个内部管理系统可能只需要「本地缓存 + 数据库」；一个面向全国用户的读多写少系统才需要 CDN。
  • 层数越多，一致性越难：n 层缓存意味着一次更新要失效 n 处，任何一处漏掉就是脏数据。每加一层都要问：收益是否值得这份复杂度？

第二层 · 配置、容量与命中率

层关键参数经验值说明
CDN缓存 TTL静态 30 天 / 动态 0~60s静态资源用文件名带 hash + 长 TTL，配合「永不缓存 HTML 入口」

配置与估算

# —— Nginx 接入层缓存（最常被忽略的一层）——
proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=mycache:100m
                 max_size=10g inactive=60m use_temp_path=off;

location /api/ {
    proxy_cache mycache;
    proxy_cache_valid 200 302 60s;       # 200/302 缓存 60 秒
    proxy_cache_valid 404 10s;           # 404 只缓存 10 秒
    proxy_cache_lock on;                 # 【关键】同一 key 并发只放行一个回源
    proxy_cache_lock_timeout 5s;
    proxy_cache_use_stale error timeout updating http_500 http_502 http_503;
    #   ^ 后端出错时【返回陈旧缓存】，比返回错误好得多（stale-if-error）
    proxy_cache_background_update on;    # 后台异步更新，不阻塞用户
    add_header X-Cache-Status $upstream_cache_status;   # HIT/MISS/BYPASS
    proxy_pass http://backend;
}

# —— 命中率与容量速算 ——
# 命中率 ≈ 1 - (热数据集大小 / 缓存容量)^k   （k 与访问分布有关，Zipf 分布下较快收敛）
# 经验：缓存容量达到热数据集的 1.2 倍，命中率通常在 85~95%
#       再翻倍到 2.4 倍，命中率可能只涨 2~3%（收益递减，见 Zipf 长尾）

# —— 本地缓存容量估算 ——
#   单机可用内存 4GB，JVM 堆 2GB，本地缓存最多给 512MB
#   若单条 1KB -> 最多 50 万条；若单条 10KB -> 5 万条
#   按 80% 装载 -> 实际设 maximumSize = 40 万 / 4 万

最容易漏的两个开关：proxy_cache_lock（防击穿）和 proxy_cache_use_stale（后端故障时用陈旧数据兜底）。这两个不开，缓存层在故障时反而会放大问题。

第三层 · 排障清单

  • 加了缓存但延迟没降 → 先用 X-Cache-Status 或监控确认到底命中了没有。很多「加了缓存没效果」其实是命中率只有 20%。
  • 本地缓存导致各实例数据不一致 → 这是本地缓存的固有代价。缓解：① 短 TTL（1~5 分钟）；② 失效广播（用 Redis Pub/Sub 或 MQ 通知各实例清缓存）；③ 版本号机制（缓存 key 带版本号，更新时递增版本号）。
  • 缓存击穿（热点 key 过期瞬间大量回源） → 三级防护：① proxy_cache_lock（接入层只放行一个）；② 逻辑过期 + 互斥重建（应用层只让一个线程回源）；③ 永不过期 + 后台刷新（Caffeine 的 refreshAfterWrite）。
  • 缓存穿透（查不存在的 key） → 布隆过滤器前置，或缓存空值（短 TTL，如 60s）。注意空值也要设 TTL，否则存了永远不存在的 key 会占满缓存。
  • 缓存雪崩（大量 key 同时过期） → TTL 加随机抖动（如 TTL + random(0, 300s)），避免同一时刻集体失效。
  • CDN 缓存了不该缓存的内容（用户信息串号） → 最危险的问题。原因：CDN 按 URL 缓存，若响应内容随用户变化（如带个人信息），就会被串给用户。解法：① 个性化内容绝对不要走 CDN（Cache-Control: private）；② 若必须缓存，把用户维度放进 URL 或 Vary 头；③ 分清「静态资源走 CDN」和「API 走 CDN」的边界。
  • 多级缓存的一致性问题 → 更新时从上到下逐级失效，且要容忍部分失败（某一层失效失败要有补偿：短 TTL 兜底 + 告警）。
  • 内存占用超预期 → 本地缓存最容易失控。必须设容量上限（maximumSize）而不是只设 TTL——只设 TTL 时，短时间内大量写入仍会撑爆内存。

第四层 · 原理与取舍

多级缓存的核心矛盾是：越靠近用户的层越快但越难保持一致，越靠近数据的层越一致但越慢。所有设计都是在这条轴上找平衡点。

设计选择延迟一致性复杂度适用
只用分布式缓存0.5ms好（单一数据源）低大多数系统的正确起点
本地 + 分布式0.1~0.5ms中（有短暂不一致）中（要处理失效传播）高并发读热点
再加接入层1~5ms中中高读多写少、可容忍秒级陈旧
再加 CDN5~30ms差（分钟级）高静态资源、全国/全球用户
全栈覆盖—最难最高大型 C 端读系统
  • 每加一层的收益是递减的：假设各层命中率 80%，三层叠加后回源率 = 0.2³ = 0.8%，看似极好。但要注意命中率的分布：如果热点集中，第一层就能拦掉 95%，后面几层的边际价值很低；如果访问均匀（长尾），每层都只能拦 50%，多层才有意义。
  • 一致性成本随层数指数级增长：n 层缓存，一次更新要失效 n 处，且要保证顺序（从上层到下层还是反过来都有坑）。实践建议：层数 ≤ 3（本地 + 分布式 + 数据库自身），除非有明确的地理分布需求才加 CDN。
  • 「陈旧但可用」优于「新鲜但错误」：这是 stale-while-revalidate 和 proxy_cache_use_stale 的设计哲学。后端故障时返回 60 秒前的缓存，用户体验远好于返回 500。这个取舍在多数业务里都是划算的。
  • 缓存粒度决定一切：缓存整页（快但难失效）、缓存片段（平衡）、缓存数据对象（灵活但要组装）。很多缓存方案失败的根源是粒度选错——比如缓存了整页却频繁需要局部更新。
本地缓存值不值得加？大多数场景是不是 Redis 就够了？

大多数场景 Redis 就够了，不要一上来就加本地缓存。判断标准很简单：算一下 Redis 的延迟在你的接口总耗时里占多少。如果接口总耗时 50ms，Redis 占 0.5ms（1%），加本地缓存最多省 0.5ms——收益微乎其微，却引入了「各实例数据不一致」这个新问题。真正需要本地缓存的是两种场景：① 极致延迟要求（接口总耗时要求在 1~5ms 内，Redis 的 0.5ms 就是 10%+）；② 极热的小数据集（如配置信息、字典表，几 KB 但每秒被访问几万次——这时 Redis 的 QPS 和网络开销反而是瓶颈）。另外别忘了本地缓存还有一个隐藏收益：Redis 故障时的兜底——本地有缓存时 Redis 挂了不至于立刻全站击穿。

多级缓存的更新顺序应该从上到下还是从下到上？

先更新数据库，再删除缓存（Cache-Aside 的标准做法），且删除顺序是「从下层到上层」（先删分布式，再广播失效本地）。为什么是删除而不是更新？因为「更新缓存」在并发下会有写覆盖问题：两个请求 A、B 并发更新，可能 A 写库 → B 写库 → B 更新缓存 → A 更新缓存，最终缓存里是 A 的旧值。删除则没有这个问题（下次读自然会从库里加载最新值）。为什么从下到上？因为如果先失效本地、后删 Redis，中间窗口内本地缓存可能读到 Redis 的旧值并重新填充——把旧数据又缓存了一遍。所以顺序是：写库 → 删 Redis → 广播失效本地缓存。还要注意：删除失败要有补偿（重试 + 短 TTL 兜底），否则会长时间不一致。

CDN 缓存 API 响应有什么坑？

三个必须知道的坑：① 个性化内容被串号——CDN 按 URL 缓存，如果两个用户请求同一个 URL，第一个用户的响应会被返回给第二个。这是严重的安全事故。防护：个性化响应必须带 Cache-Control: private 或明确 Vary: Cookie/Authorization；② 缓存时间不可控——CDN 节点众多，刷新（purge）需要时间（几十秒到几分钟），且各节点可能不一致。所以不要依赖 CDN 的即时失效，重要变更要走 URL 版本号；③ 回源风暴——一个热点 URL 在 CDN 过期瞬间，全国几十个边缘节点会同时回源。要开启回源合并/分层回源（CDN 厂商一般都有这个功能）。总结：静态资源（带 hash 的 js/css/图片）放心用 CDN 并设长 TTL；动态 API 要极其谨慎，能不用就不用。
