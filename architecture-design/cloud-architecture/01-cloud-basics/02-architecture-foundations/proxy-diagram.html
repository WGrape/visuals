正向代理 vs 反向代理：一句话分清

区分的关键是「代理的是谁」：

正向代理代理客户端——服务端不知道真实客户端是谁（VPN、公司上网代理）
反向代理代理服务端——客户端不知道真实服务端是谁（Nginx、CDN、网关）
正向代理目的隐藏客户端、突破访问限制、缓存提速、访问控制
反向代理目的负载均衡、隐藏后端、TLS 终止、缓存、压缩、安全过滤
正向代理代理客户端，反向代理代理服务端

反向代理在架构中的位置与作用

作用说明价值
负载均衡把请求按策略分发到多个后端提升容量与可用性，后端可水平扩展
TLS 终止在代理层完成 HTTPS 解密，后端走 HTTP后端免于管理证书与加解密开销；但内网要可信
静态资源与缓存直接返回静态文件，或缓存后端响应大幅降低后端压力与延迟
压缩与安全Gzip/Brotli 压缩；WAF、限流、IP 黑名单、防爬统一安全策略，后端专注业务
路径路由按 URL 前缀把请求分发到不同服务单入口聚合多服务（微服务网关的基础）
隐藏后端拓扑后端 IP 与端口不对外暴露减少攻击面，后端变更对客户端透明
灰度与 A/B按规则把部分流量导向新版本支撑金丝雀发布

注意：反向代理本身是单点，必须做高可用（主备 + VIP、或云厂商的托管负载均衡），否则它一挂全站不可达。

相关概念辨析

代理 vs 网关 vs 负载均衡

  • 负载均衡器：主要做流量分发，L4（按连接）或 L7（按内容）
  • 反向代理：在 L7 上代理服务端，可做缓存、改写、TLS 终止
  • API 网关：在反向代理之上叠加业务语义（鉴权、限流、计费、协议转换）
  • 边界是模糊的：Nginx 既是反向代理也是负载均衡；Kong/APISIX 既是代理也是网关

四层 vs 七层

  • L4（传输层）：只看 IP 和端口，不解析内容；性能极高，支持任意 TCP 协议
  • L7（应用层）：解析 HTTP，可按 URL/Header/Cookie 路由；能做缓存与改写，但 CPU 开销更大
  • 选择：需要按内容路由或做 HTTP 特性 → L7；追求极致性能或代理非 HTTP 协议（数据库、MQ）→ L4

透明代理

客户端无需任何配置，流量被网络设备（网关、iptables）透明地重定向到代理。

  • 常用于企业上网审计、K8s 的 Service 转发
  • 对客户端完全无感知

代理带来的可观测性问题

经过代理后，后端看到的源 IP 是代理的，客户端看到的是代理的响应。

  • 必须传递真实 IP：X-Forwarded-For / X-Real-IP
  • 协议也要传递：X-Forwarded-Proto（判断原始是 http 还是 https）
  • 安全：这些头可被伪造，只有信任的代理传来的才可采信

Nginx 配置要点

upstream backend { least_conn; # 负载策略：轮询/权重/ip_hash/least_conn server 10.0.1.5:8080 weight=3 max_fails=3 fail_timeout=30s; server 10.0.1.6:8080 weight=1; server 10.0.1.7:8080 backup; # 备用节点 keepalive 64; # 与后端保持长连接，减少握手开销 } server { listen 443 ssl http2; server_name api.example.com; ssl_certificate /etc/nginx/cert.pem; ssl_certificate_key /etc/nginx/key.pem; location /api/ { proxy_pass http://backend; proxy_set_header Host $host; proxy_set_header X-Real-IP $remote_addr; proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; proxy_set_header X-Forwarded-Proto $scheme; proxy_connect_timeout 3s; # 连接超时要短，快速发现不可用 proxy_read_timeout 30s; # 读超时按业务 P99 设定 proxy_next_upstream error timeout http_502; proxy_next_upstream_tries 2; # 失败重试次数要克制 } location /static/ { alias /var/www/static/; expires 30d; # 静态资源长缓存 } } # 关键提醒： # 1) proxy_connect_timeout 必须小于客户端超时，否则会堆积 # 2) 重试只对幂等请求开启，POST 重试可能造成重复下单 # 3) keepalive 到后端能显著降低延迟与 TIME_WAIT 数量

深入自检

为什么后端拿到的客户端 IP 是代理的？怎么解决？

因为 TCP 连接是代理与后端建立的，后端看到的源地址自然是代理的 IP。解决靠 HTTP 头传递：代理在转发时把真实客户端 IP 放进 X-Forwarded-For（XFF）或 X-Real-IP，后端从这些头里读取。实践注意三点：① XFF 是追加链——经过多层代理时形如「真实IP, 代理1IP, 代理2IP」，取最左边一个（但要能识别伪造）；② 只在信任的代理边界采信这些头，直接暴露在公网的后端不能信——攻击者可伪造 XFF 绕过 IP 限制；③ 需要同时传 X-Forwarded-Proto，否则后端生成的链接会用 http 而非 https。云负载均衡、CDN、Nginx 都需要正确配置这些头。

正向代理能缓存吗？反向代理能翻墙吗？

前者能，后者通常不能（或者说不是它的用途）。正向代理可以缓存——早期公司上网代理缓存常用网页，减少外网带宽；它也能做访问控制（禁止访问某些站点）。反向代理不能用于翻墙，因为它的部署位置在服务端一侧，客户端必须能直接访问到它——而翻墙的需求恰恰是客户端访问不到目标。翻墙用的是正向代理（或 VPN 这类隧道技术）。简单记：正向代理帮客户端「出去」，反向代理帮服务端「接住」。

TLS 终止在代理层安全吗？

取决于内网是否可信。TLS 终止后，代理到后端是明文 HTTP，如果内网被入侵，流量可被窃听。三种方案：① 信任内网——云 VPC / 专有网络内终止，这是最常见也最省事的方案；② 重新加密——代理解密做路由与过滤后，再用 TLS 转发到后端（TLS 桥接），开销大但更安全；③ 端到端加密——代理只做透传不解密（SNI 路由 / 四层转发），安全性最高但无法做基于内容的路由与缓存。零信任架构下推荐方案②或③。另外注意证书私钥要妥善保管，代理层集中了所有证书，是高风险资产。

代理导致的请求延迟变高怎么排查？

按链路逐段测量：① 客户端到代理（含 DNS、TCP 握手、TLS 握手）；② 代理内部处理（路由匹配、过滤、重写、日志）；③ 代理到后端（连接建立、请求转发、等待响应）。常见瓶颈：代理未开启到后端的 keepalive（每次请求都重新握手，延迟增加几十毫秒并产生大量 TIME_WAIT）；代理 CPU 打满（TLS 握手、gzip 压缩、正则匹配都很耗 CPU）；缓冲区配置不当导致响应被多次拷贝；日志同步写入阻塞。工具上可以用 Nginx 的 $upstream_response_time 与 $request_time 两个变量——两者差值就是代理自身的开销，差值大说明瓶颈在代理。
