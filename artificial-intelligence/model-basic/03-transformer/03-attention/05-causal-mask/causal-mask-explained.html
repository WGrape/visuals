因果掩码：为什么模型不能偷看后面的词

掩码是自回归生成的前提，也是训练与推理行为差异最大的地方。它还会和 padding、packing、滑动窗口纠缠在一起——做错任何一处，表现都是「loss 异常低但评测崩」。

一句话定位：把上三角的分数压成 -inf

一个 (seq, seq) 的分数矩阵里，位置 i 对位置 j 的分数若 j > i 就应该被禁止。做法是加一个上三角为 -inf 的掩码，softmax 之后这些位置的权重变成 0。

训练一次前向并行算所有位置，靠掩码阻断未来信息
推理每步只有 1 个 query，历史全在 KV Cache 里，天然只能看过去
数值写法-1e9（bf16 安全）或 -inf（fp32 下可用，需注意 nan）
省算力causal 只需算下三角，理论省 50%
两张掩码视角：训练时是矩阵下三角，推理时退化成一行全可见

正确写法与三个数值陷阱

# 训练：加性掩码（-inf 加在 softmax 之前） mask = torch.full((s, s), float('-inf')).triu(1) # 上三角（不含对角）为 -inf attn = softmax(q @ k.transpose(-1, -2) / sqrt(d) + mask, dim=-1) # bf16 下更稳的写法：用一个大负数，而不是 -inf mask = torch.full((s, s), -1e9, dtype=torch.bfloat16).triu(1) # 与 padding 掩码合并（padding 位置也不该被看见） mask = causal_mask | pad_mask[:, None, None, :] # bool 版，True 表示屏蔽
陷阱现象原因
用 0 乘代替 -inf权重和不为 1、梯度异常softmax 前的 0 分不是「禁止」，是「普通分数」
bf16 用 -inf偶发 nan-inf 参与后续加减会出现 inf-inf
掩码方向写反loss 正常但生成崩triu / tril 记混，模型能看到未来
只做 causal 不做 paddingbatch 内短句被 padding 污染pad 位置也被注意力读到

和 padding / packing / 窗口的三处纠缠

场景掩码要做什么不做会怎样
batch 内变长（左 padding）padding 位置屏蔽；且位置 id 要从 0 开始重编生成错位、续写接不上
batch 内变长（右 padding）padding 屏蔽即可pad token 被当作上下文，短句质量下降
多文档 packing 训练causal + 文档块对角掩码跨文档串味，loss 异常低，评测明显掉点
滑动窗口（Mistral）causal 再叠窗口外屏蔽显存估算偏大，长文行为与预期不符
前缀共享 / prompt cache缓存段全可见，新段只对新段做 causal位置错位或注意力漏读缓存
packing 不设文档掩码是「隐形掉点」第一名

把多条短样本拼成一条长序列能提升 GPU 利用率，但如果不做块对角掩码，模型会跨文档看内容：训练 loss 会反常地低（信息泄漏），下游评测却明显变差，非常难查。

注意：decode 阶段每步只有 1 个 query，causal 没有可省的（它天然只看历史），省的是 prefill。所以长 prompt 的 TTFT 才是掩码优化的主要受益者。

排障清单：掩码相关的五个症状

  1. loss 异常低但评测差：掩码没生效（方向反了或 dtype 不匹配被广播掉），模型看到了未来。
  2. 生成时重复开头几个字：通常不是掩码，而是 prompt cache 的位置编码没偏移，去查位置 id。
  3. batch 里只有长句正常：padding 掩码缺失，短句被 pad 影响。
  4. 多卡结果不一致：掩码按局部 seq 生成（每卡各自的 shard），需要在全局 seq 上构造。
  5. 长文检索突然变差：滑动窗口把远处内容挡了，或 rope_scaling 与掩码窗口不匹配。

原理与取舍：为什么必须因果

自回归语言模型的训练目标是「给定前 i-1 个 token 预测第 i 个」，如果允许看到未来，模型会直接抄答案，loss 趋近 0 而毫无泛化。因果掩码把「一次并行前向」变成 seq 个合法的预测任务，这是 Transformer 能高效训练生成模型的核心技巧（teacher forcing）。

为什么推理时不需要显式掩码？

decode 每步只有 1 个新 query，历史 K/V 全在 cache 里，本来就不存在「未来」。所以推理路径上通常直接跳过掩码构造，省一次 (1, seq) 的加法。

双向注意力（BERT）为什么不需要？

它的任务是填空/分类，输入本来就已经完整，不存在泄漏问题。代价是不能直接用来做生成。

掩码矩阵会不会很占显存？

bool 版 8K² 是 64MB，fp16 加性掩码是 128MB。工程上通常用 bool + kernel 内判断，或按块生成，避免整块驻留。
