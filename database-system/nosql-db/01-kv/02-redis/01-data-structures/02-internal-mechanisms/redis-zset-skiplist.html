⛷️ Redis ZSet 与跳表（Skip List）

有序集合为什么不用红黑树而用跳表？跳表的「抛硬币」分层如何做到 O(log N) 查找，插入删除又为什么更省心。

找到起点后顺底层链表直扫

先建立直觉：跳表就是「地铁 + 步行」

假设你在一本 1000 页的书里找第 612 页。有两种翻法：

  • 一页一页翻：最坏翻 612 次——这就是单链表，O(N)。
  • 先翻目录（章）→ 再翻小节 → 再逐页找：这就是跳表。目录是「高层索引」，跳过大量无关页，最终定位到具体页。

跳表做的事一模一样：在有序链表之上额外搭几层稀疏的「快进指针」，高层一次跨过很多节点，低层逐步逼近，最终精确命中。

结构长什么样

三条要点：

  1. L0（底层）是完整的有序链表，包含所有节点。这是数据的「真相层」。
  2. 上层是下层的稀疏子集——每个节点有若干层指针，层数越高节点越少。
  3. 每个节点还有向下的指针（图中虚线），查找时从高层降到低层。

查找：向右走、走不动就往下走

查找 38 的过程（对照上图）：

  1. 从 L3 的头节点出发，右边是 17（<38，可以走）→ 走到 17；再右边是 +∞（太大，不能走）→ 降到 L2。
  2. L2：右边是 55（>38，不能走）→ 降到 L1。
  3. L1：右边正好是 38 → 命中，结束。
这个「向右走、走不动就往下走」的循环就是跳表查找的全部。因为每降一层，候选区间就缩小一半左右，所以总步数约等于层数 = O(log N)。

层数怎么定？抛硬币

跳表不靠「重新平衡」来维持结构，而是在建节点时用随机决定层数：

// Redis 的实现：p = 0.25（1/4 概率继续加一层）
int zslRandomLevel(void) {
    int level = 1;
    // 每层有 25% 的概率再往上加一层
    while ((random() & 0xFFFF) < (ZSKIPLIST_P * 0xFFFF))
        level += 1;
    return (level < ZSKIPLIST_MAXLEVEL) ? level : ZSKIPLIST_MAXLEVEL;
}
参数Redis 取值含义
晋升概率 p0.25每上一层概率降为 1/4，所以高层非常稀疏
最大层数32ZSKIPLIST_MAXLEVEL，足够支撑 2^32 量级元素
期望层数≈ 1.331/(1-p) = 4/3，平均每个节点只有 1.33 层指针
为什么 p 取 1/4 而不是 1/2？更小的 p 让高层更稀疏，节省内存（平均指针数从 2 降到 1.33）。代价是查找时每层跨越的步数变多，但渐进复杂度同为 O(log N)。Redis 更在意内存，所以选了 1/4。

为什么 Redis 选跳表而不是红黑树

维度跳表红黑树
查找O(log N)O(log N)
范围查询（ZRANGEBYSCORE）✅ 找到起点后沿 L0 直扫，天然有序需要中序遍历，回溯父节点，更麻烦
插入/删除✅ 只改相邻节点的指针，局部操作可能触发旋转 + 变色，牵连子树
实现与调试✅ 代码短、逻辑直观case 分支多（LL/LR/RR/RL 等），易错
内存平均 1.33 个指针/节点（略多）每节点固定左右子 + 颜色位
Redis 作者 antirez 的原话大意是：跳表更容易实现和调试，且范围查询是 ZSet 的核心操作（排行榜、延迟队列都依赖 ZRANGEBYSCORE），跳表在这件事上天然占优；内存稍多的代价完全可以接受。

ZSet 的双结构：跳表 + 哈希表

ZSet 在内存里同时维护两个结构：

  • dict（哈希表）：member → score，让 ZSCORE key member 是 O(1)。
  • zskiplist（跳表）：按 score 排序（score 相同按 member 字典序），支撑 ZRANGE / ZRANK / ZRANGEBYSCORE。

两者共享同一份 member 和 score 的内存（指针引用），所以不是「存两份数据」，只是多了一层索引开销。这也是为什么 ZSet 的内存占用比单纯的 Hash 高。

listpack 是线性存储，查找是 O(N)。Redis 用它纯粹是为了在小集合场景下省内存（省掉指针和哈希表的开销）。一旦元素变多就自动升级，无需人工干预。

🎯 面试问答

Q：跳表是怎么做到 O(log N) 的？
A：靠多层稀疏索引：底层 L0 是完整有序链表，上面每一层都是下一层的稀疏子集（Redis 用 p=0.25 的抛硬币决定每个节点升到几层）。查找时从最高层出发，能往右走就往右走，走不动就降一层。因为每降一层候选区间大致减半，总步数约等于层数，即 O(log N)。它不是靠「严格平衡」，而是靠概率上的平衡——结构上没红黑树那么规整，但期望性能一样好。
Q：为什么 Redis 的 ZSet 用跳表而不用红黑树？
A：三个实际原因：① 范围查询更自然——ZSet 的核心命令 ZRANGE/ZRANGEBYSCORE 是排行榜和延迟队列的基础，跳表找到起点后直接沿底层链表扫即可，红黑树要中序遍历并回溯父节点；② 插入删除更简单——跳表只改相邻节点指针，红黑树可能触发旋转和变色，牵连整棵子树，代码复杂易错；③ 实现易调试。代价是内存略多（平均 1.33 个指针/节点），Redis 认为这个代价可以接受。
Q：ZSet 为什么同时用跳表和哈希表？
A：两者解决不同的查询维度：跳表按 score 排序，支撑 ZRANGE、ZRANK、ZRANGEBYSCORE 这类「按分数/名次」的操作；哈希表做 member → score 映射，让 ZSCORE 和 ZADD 的去重判断是 O(1)。两者共享同一份 member/score 字符串内存（只是指针引用），所以不会真的把数据存两遍，额外开销只是哈希表的索引结构。
Q：跳表的层数上限为什么是 32？
A：ZSKIPLIST_MAXLEVEL = 32，配合 p = 0.25，理论上可支撑 (1/0.25)^32 = 2^64 量级的元素，远超实际 Redis 实例能存的数量。所以这个上限在实践中永远碰不到，只是防止随机数极端情况下层数无限增长的兜底。
Q：小 ZSet 和大 ZSet 的存储有区别吗？
A：有。元素数 ≤ zset-max-listpack-entries（默认 128）且每个 member 长度 ≤ zset-max-listpack-value（默认 64 字节）时，用紧凑连续的 listpack 存储，省掉所有指针开销，查找是 O(N) 但集合小所以无所谓。任一条件超限就自动升级为 skiplist + dict，无需人工干预，也不会反向降级。
