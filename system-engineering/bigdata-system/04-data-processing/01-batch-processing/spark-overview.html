Spark 计算引擎总览

基于内存的分布式计算：RDD、DAG 与 Spark 生态全家桶

一、Spark 是什么：为什么它比 MapReduce 快

Apache Spark 是一个基于内存的统一分析引擎（Unified Analytics Engine），设计目标是用一个统一的编程模型覆盖批处理、SQL 查询、流处理、机器学习和图计算。它诞生于 2010 年前后（UC Berkeley AMPLab），核心论文《Resilient Distributed Datasets》奠定了其分布式内存计算的基石。

在 Spark 之前，Hadoop MapReduce 是主流计算引擎，但其每一步中间结果都要落盘到 HDFS（磁盘 I/O + 网络复制三副本），迭代计算（如机器学习、图算法）尤其缓慢。Spark 的关键洞察是：大多数计算的中间结果可以驻留内存，只有当内存不足或需要容错时才落盘。

⚡

内存计算

中间结果缓存在内存而非 HDFS，迭代算法速度可提升 10~100 倍。RDD 默认存内存，OOM 时自动降级到磁盘。

🧩

DAG 执行计划

把整条计算逻辑建模为有向无环图（DAG），在宽依赖处切分为多个 Stage，同一个 Stage 内的算子流水线（pipeline）连续执行，避免 MapReduce 那种强制"一堆 Map 全跑完才能 Reduce"的代价。

🔁

减少不必要的 Stage

窄依赖算子（map、filter、flatMap）被 fusion 进同一 task 连续跑；只有遇到 shuffle 类的宽依赖（groupByKey、reduceByKey）才落地一次磁盘，Stage 数量远少于 MapReduce 的"每个算子一对 Map/Reduce"。

🌐

统一 API

同一套 Scala/Java/Python/R API 表达批、流、SQL、ML。开发者无需为不同场景切换引擎，学习成本和代码迁移成本都大幅下降。

二、核心概念：RDD、DAG、宽窄依赖与运行角色

理解 Spark 要先抓住四个核心概念，它们是后面所有架构与调优讨论的基础。

📦

RDD（弹性分布式数据集）

RDD 是 Spark 最基础的抽象：只读、分区的数据集合。弹性（Resilient）指分区可丢失后通过血缘重算；分布式指数据被切分为多个 Partition 分散在集群上。三大特性：①分区列表（Partition）；②计算每个分区的函数；③依赖（Dependencies，血缘）；④可选的首选位置（ locality 优化）；⑤可选分区器（Hash/Range）。

🕸️

DAG（有向无环图）

用户写出的 transformation 不会立即执行，而是被记录成一张 DAG。Driver 上的 DAGScheduler 根据依赖关系把 DAG 切分成 Stage，再把 Stage 提交为 TaskSet 交给 TaskScheduler 分配到 Executor 执行。这种"惰性求值（Lazy Evaluation）"让优化器有机会合并、剪枝算子。

✂️

宽依赖 vs 窄依赖

窄依赖：子 RDD 的每个分区只依赖父 RDD 的少量（通常一个）分区（map、filter、union），可流水线执行、无需落盘。宽依赖：子分区依赖父的多个分区（groupByKey、join 非同区），必须触发 Shuffle——这是 Stage 的物理边界，也是性能主要瓶颈来源。

🎛️

Driver 与 Executor

Driver 跑用户 main()、构建 DAG、调度任务、维护运行时状态。Executor 是 Worker 节点上的进程，负责执行 task、把数据缓存在 BlockManager，并通过心跳向 Driver 汇报。Executor 一旦启动通常常驻直到应用结束。

五、Spark 生态全家桶

Spark 不止一个计算核心，而是一整套以 Spark Core 为底座的组件库，覆盖从批处理到图计算的主流场景。

⚙️

Spark Core

提供 RDD API、任务调度、内存管理、容错与存储（BlockManager）。它是所有上层组件的运行时底座，定义了任务分发、shuffle、cache/persist 等基础机制。

🗃️

Spark SQL

提供 DataFrame / Dataset 结构化 API，内置 Catalyst 优化器（逻辑计划→物理计划，谓词下推、列裁剪）与 Tungsten 二进制执行引擎（堆外内存、代码生成），让 SQL 与结构化处理接近手写代码的性能。

🌊

Structured Streaming

以"微批 + 表"模型把流看成无限追加的表，提供端到端精确一次（exactly-once）语义。编程接口与 Spark SQL 高度一致，降低流批统一门槛。

🤖

MLlib

分布式机器学习库，提供分类、回归、聚类、协同过滤、特征工程与 Pipeline API。基于 RDD/DataFrame 并行训练，适合大规模特征与模型。

🕸️

GraphX

图计算 API（基于 Pregel 的顶点中心计算）。本组件在本站有独立专页，此处不展开。

六、与 Hadoop 的关系：Spark 取代的是谁

关键澄清：Spark 不是存储系统，它本身不提供 HDFS 那样的分布式文件系统。Spark 通常读取 HDFS / 对象存储（S3、OSS）上的数据，并把调度跑在 YARN 或 Kubernetes 之上。一句话——Spark 取代的是 MapReduce 这个计算引擎，而不是 Hadoop 整个生态。

在实际生产部署中，最常见的形态是"HDFS 存 + YARN 调度 + Spark 算"三层协作：YARN 负责资源隔离与分配，HDFS 负责数据持久化与三副本容错，Spark 负责在上面高效完成计算。两者是互补而非替代关系。

维度MapReduce（旧）Spark（新）
中间结果强制落盘 HDFS默认驻留内存
执行模型Map→Reduce 固定两阶段按依赖自由切分 Stage
迭代性能差（每轮重写磁盘）优（内存缓存）
生态覆盖仅批处理批/流/SQL/ML/图

七、面试问答

Q1：宽依赖和窄依赖的区别？Stage 为什么要按宽依赖切分？
窄依赖子分区只依赖父的一个或少数分区（map、filter），可流水线在一个 task 内连续执行，无需网络。宽依赖（groupByKey、reduceByKey、跨区 join）需要把父的多个分区数据按 key 重新分发，即 Shuffle，必须落盘并跨节点传输，因此成为 Stage 的物理边界。切 Stage 的意义是：同一个 Stage 内的算子能融合（fusion）成一条流水线，减少任务调度与落盘次数。
Q2：Spark 为什么比 MapReduce 快？
三点：①中间结果存内存而非每步落 HDFS，省去大量磁盘 I/O 与三副本复制；②DAG 执行计划允许把多个窄依赖算子融合进一个 Stage 流水线执行，而 MapReduce 强制每步都是一次完整 Map+Reduce 作业；③Catalyst/Tungsten（在 SQL 场景）做计划优化与二进制执行。注意：当数据远大于内存时，Spark 也会落盘，此时速度优势会收窄。
Q3：RDD 的"血缘（Lineage）"如何实现容错？
RDD 不保存完整数据，而是保存"如何从父 RDD 计算得来"的依赖链（一组算子函数）。某个分区丢失时，Driver 根据血缘找到其上游依赖，重新计算该分区即可，无需回滚整个作业。这是"重新计算（recompute）"而非"复制"的容错思路，代价是重算长血缘可能较慢——此时用 checkpoint 把中间结果物化到可靠存储来打断长血缘。
Q4：cache/persist 与 checkpoint 有什么区别？
cache/persist 把 RDD 缓存在内存或磁盘，仍保留血缘，用于加速重复使用的同一血缘数据，Executor 挂掉会失效并触发重算；checkpoint 把 RDD 物化到可靠存储（HDFS）并切断血缘，用于打断超长血缘、提升容错与避免重复重算，但写代价更高。实践中常先 persist 再 checkpoint 以兼顾性能与安全。

Spark 核心概念与执行模型

概念含义关键特性
RDD弹性分布式数据集不可变、分区、可重算（血统）
DataFrame/Dataset带 schema 的结构化抽象Catalyst 优化器，比 RDD 快
Job一个 action 触发一个 job—
Stage按 shuffle 边界切分窄依赖可流水线，宽依赖切分
Task一个分区上的一个计算并行度 = 分区数
血统（Lineage）记录变换过程用于恢复容错无需复制数据

为什么 DataFrame 比 RDD 快：RDD 只记录函数闭包，优化器看不见数据语义，无法优化；DataFrame 有 schema + Catalyst 优化器，能做谓词下推、列裁剪、常量折叠、代码生成（Tungsten）。同样逻辑，DataFrame 常比 RDD 快 2~10 倍，且内存占用更低。所以新代码一律用 DataFrame API，不要用 RDD。

# 处理 2：广播 join（小表直接广播，避免 shuffle）

自检 Q&A

Q：Executor 数量与并行度怎么配？

A：并行度 = 分区数，不是 executor 数。Executor 提供的是执行槽位（cores），若分区数远小于总核数，核会闲置。经验：分区数 ≈ 总核数 × 2~4。单 executor 的 cores 建议 2~5——超过 5 时，单个 JVM 内的多线程会争抢 HDFS 连接与 GC 资源，吞吐反而下降。

Q：为什么我的 Spark 作业 90% 的时间花在 GC 上？

A：典型原因是数据都堆在 JVM 堆里（用了 RDD 或缓存了大量对象）。三种解法——① 改用 DataFrame（Tungsten 用堆外内存 + 二进制格式，对象开销极小）；② 减少 cache/persist，或改用 MEMORY_AND_DISK_SER（序列化后存，体积小但读取要反序列化）；③ 调大 executor 内存或改用 G1GC。最根本的是 ①。

Q：shuffle.partitions=200 什么时候要改？

A：几乎总是要改。200 是通用默认值，但——数据量小时（几百 MB）200 个分区会产生大量小文件，应调小到 20~50；数据量大时（TB 级）200 个分区意味着单分区几 GB，会 OOM 或极慢，应调大到 1000~5000。判据是单分区目标 128 MB：分区数 = 总数据量 / 128 MB。开 AQE 后可以让引擎自动合并小分区，容错性更好。

Q：Spark 比 Hive 快在哪？

A：核心是内存计算 + DAG 调度。Hive 把每个 MR 作业的中间结果落盘，多个作业串联时 IO 开销巨大；Spark 把整个 DAG 放在内存里，中间结果能复用就不落盘，只在 shuffle 时写盘。此外 Spark 有线程级的任务调度（MR 是进程级，启动开销大）与 Catalyst 优化。典型提速 3~10 倍，但数据量远超内存时优势会缩小（都要落盘）。
