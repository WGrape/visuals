模块边界与包结构：单体的“内功”

单体能不能活得好，七分看内部结构。划清子域、用包强制分层、守住依赖方向、避开反模式——这是把单体写“不烂“的关键。

划分子域两种包组织依赖规则反模式

🗺️ 一、先划子域，再划模块

不要按“技术名词“分模块，要按“业务能力 / 子域“分。订单、库存、用户，比 controller/service/dao 更能反映业务。

划分依据例子评价
业务能力（推荐）order / inventory / user贴近业务，便于未来拆分
技术层（次选）web / service / dao简单，但业务变大后层内仍耦合

📦 二、包怎么组织

按层切（横向）
技术视角
web / service / dao
加功能要改多个包
按特性切（纵向）
业务视角
order/… 内含其各层
加功能多在一个包内完成

推荐以业务模块为顶层包，模块内部再分层：order/web、order/domain、order/infra。这样每个模块自洽，最利于演进。

⬆️ 三、依赖方向纪律

  • 单向、无环：模块 A 依赖 B，B 就不能回头依赖 A。
  • 公开 API 而非实现：模块只暴露接口/门面，藏起内部细节。
  • 用工具守住：ArchUnit、模块可见性、编译检查，把约定变成硬约束。

🕳️ 四、三大反模式

❌
  • 双向依赖：A 调 B，B 又调 A，边界名存实亡。
  • 共享内核滥用：一个"common"包被所有人依赖，最终变成谁都离不开的泥潭。
  • 循环依赖：A→B→C→A，改任何一处都可能牵一发动全身。
