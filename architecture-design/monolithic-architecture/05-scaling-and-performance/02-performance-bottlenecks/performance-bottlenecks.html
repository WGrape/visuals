单体架构的性能瓶颈与定位

单体的性能问题集中在少数几类：CPU、内存、IO、锁、连接池、数据库。先有方法论（测量→定位→验证），再动手，避免瞎优化。

瓶颈来源定位方法论数据库这一关常见坑

🎯 一、瓶颈通常在哪

CPU
计算密集
序列化、加解密、算法
单核打满拖慢全部
内存 / GC
堆压力
大对象、缓存无界
GC 停顿导致毛刺
IO / 锁
阻塞
慢查询、同步阻塞
锁竞争、线程池满
连接池
隐性瓶颈
DB/HTTP 连接耗尽
请求排队、超时

🔬 二、定位方法论

测量 → 定位 → 验证，闭环进行，拒绝“感觉哪慢就改哪”。
压测
构造负载
→
Profiling
CPU/内存火焰图
→
APM
链路追踪
→
优化
针对性改+再测
  • 火焰图看 CPU 到底耗在哪段代码。
  • APM / 链路追踪看一次请求慢在哪个环节。
  • 慢查询日志定位数据库这一关。

🗄️ 三、数据库这一关最贵

  • 多数单体性能问题，根因是数据库：慢 SQL、缺索引、N+1 查询。
  • 先加索引、改 SQL、批处理，往往比加机器更划算。
  • 读多写少时，缓存 + 读写分离立竿见影。

🕳️ 四、常见坑

❌
  • 过早优化：没测量就改，可能改错地方。
  • 无界缓存：缓存把内存吃光，反而引发 GC 风暴。
  • 连接池过小：并发一上来就排队超时，像是“应用慢“实为连接不够。
