🧊 Redis 过期删除 vs 内存淘汰

一句话：过期删除管"该死的"（key 到点了就清掉），内存淘汰管"腾地方的"（内存满了挑一个扔掉）。两者根本不是一回事——下面用图和交互讲透。

1先打个比方：冰箱里的食物

最形象的理解，不需要记术语。

🟦 过期删除 = 保质期到了就扔

你给每样食物贴了保质期。到期那天，不管冰箱空不空，该扔就扔。 目标只有一个：把"已经坏了/该丢了"的东西清出去。冰箱很空也照扔——因为它只关心"到没到期"。

🟧 内存淘汰 = 塞满了必须腾地方

冰箱塞满了，你还要往里放新菜。此时 Redis 会挑一样东西扔掉来腾位子—— 被扔的可能还很新鲜、根本没过期。目标只有一个：腾出空间让新数据能写进来。

记住这句就够了：过期删除是"到点清理"，内存淘汰是"满员舍弃"。 一个看时间，一个看空间。

2它们根本不是一回事

从定义上就把边界划清，后面才不会混。

🟦 过期删除策略（Expiration）

你用 EXPIRE 给 key 设了 TTL。当 TTL 走到 0，Redis 要把这个 key 删掉。 它回答的是："已过期的 key，怎么把它清掉？"

核心关注：这个 key 过期了没有？过期了就删。 完全不关心内存满不满、新数据要不要写。

🟧 内存淘汰策略（Eviction / maxmemory-policy）

你设了 maxmemory。当内存用到上限，又有写命令要进来，Redis 必须腾地方。 它回答的是："内存满了，挑哪个 key 扔掉？"

核心关注：从现有 key 里选一个牺牲品。 完全不关心这个 key 过没过期、TTL 还剩多少。

⚠️ 最关键的认知：内存淘汰会删掉"还没过期"的 key，而过期删除只删"已经过期"的 key。 一个是"宁可错杀新鲜的也要腾空间"，一个是"只清理该死的"。所以就算你给所有 key 都设了 TTL， 内存一旦写满，Redis 照样会扔掉 TTL 还很长的 key。

3一张图看清两条链路

左边是过期删除的生命线，右边是内存淘汰的生命线——触发条件、判断、结果全不一样。

⚠️ 注意右链第一格的触发条件：只有"写命令 + 内存已满"才会触发淘汰。 单纯的读命令（GET）不会触发内存淘汰；内存没满时写命令也不会触发。 而过期删除是"到点就处理"，跟有没有新写入、内存满不满都没关系。

6它们是"配合"的，不是"二选一"

真实运行里，两者是前后两道防线。

🟦 第一道防线（过期删除）：key 到点就被清，不需要等内存满。绝大多数"该死"的 key 在这一关就被处理掉，根本到不了淘汰。
🟧 第二道防线（内存淘汰）：只有当第一道没拦住、内存真的写满了，才为了腾地方扔 key——而且扔的可能是还很新鲜的 key。

7关键澄清：volatile-* 不是"只删过期键"

这是 90% 的人会理解错的地方。

⚠️ volatile-lru / volatile-lfu / volatile-random 里的 "volatile" 意思是 "只从『设了 TTL 的 key』里选候选"，不是"只删已过期的 key"。

它挑出来的牺牲品，可能 TTL 还剩很久——比如 volatile-lru 会从带 TTL 的 key 里挑"最久没用"的那个，哪怕它还剩 50 分钟才过期，照样被扔。
🟧 那"优先删快过期的"是哪个？是 volatile-ttl：它同样只在带 TTL 的 key 里选，但按剩余寿命排序， 剩余 TTL 最短的先被扔——这是唯一一个"偏向删快过期 key"的淘汰策略，但它依然不要求 key 已经过期。
🟦 反过来，过期删除永远只删已过期的 key，不存在"挑一个没过期的清掉"这回事。

8常见误区 & 一句口诀

❌ 误区1：给所有 key 都设了 TTL，就不需要关心内存淘汰了。
✅ 错。内存写满时，淘汰照样会扔掉 TTL 还很长、甚至根本没用到的 key。TTL 只是"过期删除"的依据，不是"不被淘汰"的保护伞。
❌ 误区2：内存淘汰会先删那些已过期的 key。
✅ 不一定。除 volatile-ttl 外，其他策略按 LRU/LFU/随机选，跟"过没过期"无关。已过期的 key 多半早被惰性/定期删掉了，淘汰时根本遇不到几个。
❌ 误区3：读命令（GET）也会触发内存淘汰。
✅ 不会。淘汰只在"会增加内存的写命令 + 内存已满"时触发。GET 不增内存，自然不触发。
📜 一句口诀：「过期看时间，到点就清；淘汰看空间，满员就扔； 过期只删该死的，淘汰敢扔鲜活的；二者各管一道，配合才稳。」
