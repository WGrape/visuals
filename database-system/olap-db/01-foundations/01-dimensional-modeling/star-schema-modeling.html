OLAP 星型模型：先定义事实表粒度

报表是否会重复计数，首先取决于每一行事实到底代表什么。

核心机制

事实表记录交易、事件或周期快照。建模第一步是写清粒度，例如“一行对应一笔订单明细”，再决定外键维度和可加总指标。

维度表解释谁、何时、何地和商品属性。若直接把一对多明细连接到事实表，金额会被复制；应先聚合到相同粒度，或设计桥接与去重规则。

用一个例子看过程

fact_order_line：每行是一笔订单中的一个商品行
维度：date、customer、product
指标：quantity、line_amount

声明粒度

明确一行代表订单、订单明细还是每日商品快照，不能混用。

核对键关系

确认维度键在所选版本上唯一；缓慢变化维度需明确生效时间。

验证汇总

比较事实表直接求和与维度连接后的求和，排查乘法放大。

观察、原因与处理

观察原因或含义处理与验证
金额翻倍连接到一对多维度或明细核对连接键和粒度
退货难算正负流水或状态含义不清约定业务事件和指标口径
历史属性变化维度被原地覆盖选择适合的历史维度策略

粒度声明比表名更重要

“订单事实表”可能一行代表订单、一行代表订单商品明细，或一行代表每天每商品的快照。粒度不同，主键、可加总金额与连接关系都不同。若事实粒度是订单明细，每行的 line_amount 可以跨商品、地区和日期求和；把订单级 total_amount 重复写在每条明细上，按商品连接后会放大订单金额。建模前应把“一行代表什么”写成可验证的话，并给出唯一键。

维度表描述客户、商品和日期等上下文。历史属性变化要定策略：原地覆盖会让旧事实按新属性解释；保存历史版本则需要按生效时间找到当时的维度行。两种方式都可能合理，取决于报表要“按当前组织架构回看”还是“按当时组织架构统计”。

哪些指标能跨维度相加

指标能否直接相加建议保存
商品行销售额通常可以，注意退货符号金额与币种
库存余额可跨商品，不宜跨时间累加快照值与快照时间
客单价不可平均各分组比率销售额与订单数
去重用户数跨分组相加可能重复原始 ID 或合适的可合并摘要

一对多连接尤其容易改变粒度。一个订单有两条商品行，订单总金额 150；把订单表与商品行连接后再 SUM(order_total)，可能得到 300。应在正确粒度上聚合，或改用明细行金额，并对照源系统控制总数验证。

建模验收清单

  1. 写出事实表唯一键、一行的业务含义以及事件时间。
  2. 检查每个维度连接在指定版本上是否一对一，是否存在孤儿键。
  3. 分别验证明细总额、退货处理和维度连接后的总额。
  4. 为缓慢变化维度明确历史查询口径；为比率保留分子与分母。

练习：订单 A 有两条商品行，分别 100 与 50。比较“订单级金额连接商品后求和”和“商品行金额求和”两个查询的结果，并解释差异来自哪个粒度转换。

边界与误区

“客单价”这类比率不可简单跨分组求平均；应保留分子和分母再计算。模型正确性先于列存、索引和向量化调优。

事实类型决定查询方式

交易事实记录一次事件，例如支付或退货，适合按时间累加；周期快照记录某时刻的状态，例如每日库存，通常不能跨日期直接求和；累积快照把一个流程的多个里程碑时间放在同一行，例如下单、支付、发货、签收，适合计算流程耗时。三者都可放在星型模型中，但“数值是否可加总”“记录何时更新”完全不同。若把库存快照误当交易流水，季度库存总量会随着天数虚增。

建模验收不能只看单条 SQL。应挑选几笔从下单到退货的真实业务案例，核对事实行数量、维度版本和金额符号，再与源交易系统按日对账。对晚到的维度或事实，明确补齐和重算窗口。这样的数据质量约束应在表契约中写清，而不是等报表不一致后再猜。

晚到事实与维度如何处理

商品维度记录可能晚于订单事实到达。若维度键暂时找不到，直接丢弃事实会造成金额缺口；永久使用“未知商品”又会让后续报表一直不准。可以先以未知成员承接事实，并在维度到达后回填，或者把事实暂存等待，但要规定等待上限与补算流程。缓慢变化维度也有类似问题：事实晚到时，应按事件发生时间选择当时有效的维度版本，而不是默认绑定当前最新版本。每次补算都应重新核对日总额、行数和维度缺失率。

进一步验证

一个有用的验收样本是“同一客户改名后又退货”。按历史属性统计时，原订单可能归到旧客户版本，退货事实则按业务规则归到原交易或当前客户。若没有明确的事件时间和维度版本规则，两张报表都看似合理，却无法互相对账。

补充判断

在维度连接前后比较事实表的行数和总金额是一种快速哨兵检查。金额不变但行数变多，可能存在正负抵消的重复；因此行数、唯一键数与金额都要核对，不能只看一个总和。

星型模型的组成与代价

概念说明例子
事实表存度量值（可聚合的数值）订单金额、数量、时长
维度表存描述属性（用于过滤分组）时间、商品、用户、地区
星型模型1 个事实表 + N 个维度表直接相连维度不规范化（有冗余）
雪花模型维度表再拆成子维度规范化，省空间但 join 多
退化维度维度属性直接放事实表如订单号（无其他属性）
缓慢变化维（SCD）维度属性随时间变化Type 1/2/3 三种处理方式
SCD 类型做法适用
Type 1直接覆盖，不保留历史修正错误；不关心历史
Type 2加新行（加有效期间 + 版本号）最常用；保留完整历史
Type 3加「旧值」列只需保留上一次的值
Type 2 的关键列valid_from / valid_to / is_current查询时加时间条件

星型 vs 雪花的选择：星型的维度表是反规范化的（有冗余），换来的是join 少一层。列存 OLAP 里冗余的代价很小（压缩率高），而 join 的代价很大，所以 OLAP 几乎都选星型。这和 OLTP 的 3NF 设计思路完全相反。

建模实操

-- 事实表：只放外键 + 度量（尽量窄）
CREATE TABLE fact_order (
    dt          DATE,              -- 时间维度外键
    product_id  INT,
    user_id     BIGINT,
    region_id   SMALLINT,
    -- 度量（可聚合）
    amount      DECIMAL(18,2),
    qty         INT,
    -- 退化维度
    order_no    VARCHAR(32)
)
PARTITION BY dt
DISTRIBUTED BY HASH(user_id) BUCKETS 32;

-- 维度表：宽、行数少、可冗余
CREATE TABLE dim_product (
    product_id  INT,
    name        VARCHAR(200),
    category_l1 VARCHAR(50),      -- 冗余层级，避免再 join
    category_l2 VARCHAR(50),
    brand       VARCHAR(50),
    price       DECIMAL(10,2)
)
DISTRIBUTED BY HASH(product_id) BUCKETS 4;

-- 典型查询（星型 join）
SELECT p.category_l1, SUM(f.amount) AS gmv
FROM fact_order f
JOIN dim_product p ON f.product_id = p.product_id
JOIN dim_date d    ON f.dt = d.dt
WHERE d.year = 2026 AND d.month = 10
GROUP BY p.category_l1
ORDER BY gmv DESC;
-- SCD Type 2 的实现（保留历史）
CREATE TABLE dim_user (
    user_key    BIGINT,            -- 代理键（surrogate key），自增
    user_id     BIGINT,            -- 业务键（自然键）
    city        VARCHAR(50),
    level       VARCHAR(20),
    valid_from  DATE,
    valid_to    DATE,              -- 9999-12-31 表示当前
    is_current  TINYINT
);

-- 查询「当时的维度值」（事实表记的是 user_key 不是 user_id）
SELECT SUM(f.amount)
FROM fact_order f JOIN dim_user u ON f.user_key = u.user_key
WHERE u.city = '北京';
-- 这样能正确反映下单时用户所在的城市

-- 更新维度（Type 2）：关旧行 + 开新行
UPDATE dim_user SET valid_to = '2026-10-21', is_current = 0
WHERE user_id = 123 AND is_current = 1;
INSERT INTO dim_user VALUES (NEW_KEY, 123, '上海', 'gold', '2026-10-22', '9999-12-31', 1);

排障清单

症状原因处理
指标对不上（重复计数）join 到不唯一的维度表join 前保证维度键唯一；SCD Type2 要用代理键
用了 SCD Type2 后数字翻倍同一 user_id 有多行历史事实表必须存 user_key（代理键）而不是 user_id
维度表 join 慢维度表太大 / 没 broadcast小维度用 broadcast join；大维度要分桶对齐
事实表太宽把描述属性放进了事实表描述属性放维度表；事实表只留外键+度量
时间维度没建每次用函数算年月建 dim_date 表（预生成 10 年的日期属性）
层次查询慢雪花模型 join 太多反规范化成星型；或冗余层级列
维度更新后历史数据变了用了 Type 1（覆盖）需要历史用 Type 2

事实表 grain（粒度）必须先定清楚：一行代表什么？「一个订单」还是「一个订单的一个商品」？粒度决定了所有度量能否相加，这是维度建模最重要的一步。粒度不清晰的模型，后期所有指标都会出问题。

自检

订单金额连接订单明细后变成两倍，先检查什么？

先检查事实行粒度与连接基数，确认同一订单金额是否被每条明细重复带出。
