GROUP BY 与聚合函数

分组、过滤、去重与执行原理——SQL 统计的必修课

① 聚合函数 ② 分组机制 ③ HAVING vs WHERE ④ COUNT 的坑 ⑤ 执行原理 ⑥ 常见疑问
一句话总结：GROUP BY 把行按分组键归并成组， 聚合函数在每组内算出一个值，最终每组输出一行。 WHERE 在分组前过滤行，HAVING 在分组后过滤组——这是两者唯一的本质区别。

01常用聚合函数

函数作用NULL 处理说明
COUNT(*)统计行数计入 NULL 行统计总行数最快的方式
COUNT(col)统计该列非 NULL 的行数跳过 NULL与 COUNT(*) 结果常不同
COUNT(DISTINCT col)去重后计数跳过 NULL代价较高，需排序/哈希
SUM(col)求和跳过 NULL全 NULL 时返回 NULL 而非 0
AVG(col)平均值跳过 NULL等价于 SUM/COUNT，分母不含 NULL
MAX/MIN(col)最大/最小跳过 NULL字符串按字典序比较
GROUP_CONCAT(col)组内字符串拼接跳过 NULLMySQL 专用；PG 用 STRING_AGG
所有聚合函数（除 COUNT(*)）都忽略 NULL。 这带来两个常见意外：① SUM 结果比预期小（NULL 被当 0 跳过而不是报错）； ② AVG(col) 的分母是非 NULL 行数，不是总行数—— 想把 NULL 当 0 算平均值要写 AVG(COALESCE(col, 0))。

02分组机制与 SELECT 列规则

图 1：分组 → 组内聚合 → 每组一行

SELECT 里能写什么列？

这是 ONLY_FULL_GROUP_BY 模式下最常见的报错来源。规则很简单—— SELECT 列表中的每一列，必须是：

  1. 出现在 GROUP BY 里的列（分组键），或
  2. 被聚合函数包裹的列（如 SUM(salary)），或
  3. 函数依赖于分组键的列（如按主键分组时，该表的其它列）——MySQL 5.7+ 能识别这种依赖。
-- ❌ 错误：name 既不在 GROUP BY 里，也没被聚合
SELECT dept, name, AVG(salary) FROM employees GROUP BY dept;
-- MySQL 5.7+ 报 ONLY_FULL_GROUP_BY 错误；MySQL 5.6 会"随便取一个 name"（危险！）

-- ✅ 正确写法 1：把 name 也放进分组键
SELECT dept, name, AVG(salary) FROM employees GROUP BY dept, name;

-- ✅ 正确写法 2：用聚合函数处理（如拼接姓名）
SELECT dept, GROUP_CONCAT(name), AVG(salary) FROM employees GROUP BY dept;

-- ✅ 正确写法 3：用 ANY_VALUE() 明确表示"随便取一个"
SELECT dept, ANY_VALUE(name), AVG(salary) FROM employees GROUP BY dept;
为什么 MySQL 5.7 要默认开启 ONLY_FULL_GROUP_BY？ 老版本允许"随便取一行"的行为会静默返回不确定的结果—— 开发环境看起来对，生产环境数据一变结果就错。开启严格模式是逼你把 SQL 写清楚。 不要通过关闭这个模式来"解决"报错。

03WHERE 与 HAVING 的区别

维度WHEREHAVING
执行时机分组前分组后
作用对象过滤原始行过滤分组结果
能用聚合函数吗❌ 不能✅ 可以
能用列别名吗❌ 不能（MySQL）✅ 可以（MySQL）
性能优先用，先过滤能大幅减少分组数据量分组后才过滤，代价更高
-- 需求：找出 2026 年订单总额超过 10 万的用户
SELECT user_id, SUM(amount) AS total
FROM orders
WHERE created_at >= '2026-01-01'      -- ① 先用 WHERE 过滤行（减少数据量）
GROUP BY user_id                       -- ② 按用户分组
HAVING SUM(amount) > 100000            -- ③ 再过滤"组"
ORDER BY total DESC;

-- 能用 WHERE 的绝不用 HAVING：
-- ❌ 慢：先对所有行分组，再剔除
SELECT user_id, SUM(amount) FROM orders
GROUP BY user_id HAVING user_id > 1000;
-- ✅ 快：先过滤掉大部分行，再分组
SELECT user_id, SUM(amount) FROM orders
WHERE user_id > 1000 GROUP BY user_id;

04COUNT 的四个经典陷阱

1️⃣ COUNT(*) vs COUNT(col)

COUNT(*) 数行，包含全 NULL 行； COUNT(col) 数该列非 NULL 的值。 列允许 NULL 时两者结果不同。

2️⃣ COUNT(1) 等于 COUNT(*) 吗

在 MySQL 中完全等价，优化器会把 COUNT(1) COUNT(0) 都优化成 COUNT(*)。 不要相信"COUNT(1) 更快"的过时说法。

3️⃣ COUNT(DISTINCT) 很慢

需要去重（排序或建哈希表），大数据量时代价高。 可用近似算法或预聚合表替代精确计数。

4️⃣ 大表 COUNT(*) 很慢

InnoDB 因为 MVCC 无法维护一个全局行数，必须扫描。 会挑最小的二级索引来扫。需要精确值可用计数表； 估算用 SHOW TABLE STATUS 的 rows。

InnoDB 的 COUNT(*) 优化

InnoDB 不能像 MyISAM 那样存一个常数行数（因为 MVCC 下"有多少行"取决于事务快照）， 必须真的去数。但它会选择一个最小的二级索引来扫描， 因为二级索引的叶子节点只存 (索引列, 主键)，比聚簇索引小得多。

优化手段：① 建一个小的二级索引专门给 COUNT 用； ② 维护一张计数表（用触发器或业务层更新）； ③ 用近似值（SHOW TABLE STATUS、EXPLAIN 的 rows）； ④ 放到缓存/统计系统里。

05GROUP BY 的执行原理

MySQL 实现分组主要有三种方式，用 EXPLAIN 的 Extra 列可以看到：

方式Extra 显示说明性能
松散索引扫描Using index for group-by 直接利用索引的有序性，只扫描必要的组最快（但条件苛刻）
紧凑索引扫描Using index（无临时表） 顺序扫描整个索引，靠索引有序性分组快
临时表Using temporary 建内存/磁盘临时表来分组慢，需优化
图 2：给 GROUP BY 的列建索引，是优化分组最直接有效的手段

优化建议

  1. 给 GROUP BY 的列建索引——让数据库免去临时表和排序。
  2. 先用 WHERE 缩小数据集再分组，减少参与分组的行数。
  3. 避免 GROUP BY 后跟 ORDER BY 不同列——会触发二次排序。 如果 ORDER BY 的列就是 GROUP BY 的列，可加 ORDER BY NULL 禁止默认排序。
  4. 调大 tmp_table_size 让临时表留在内存，避免落盘。
  5. MySQL 5.7+ 默认 GROUP BY 会隐式按分组列排序， 5.7 之后不再隐式排序（遵循 SQL 标准），必要时显式写 ORDER BY。

06常见疑问

Q：DISTINCT 和 GROUP BY 有什么区别？
A：去重结果常常相同，但语义与执行不同：
· SELECT DISTINCT dept FROM t = SELECT dept FROM t GROUP BY dept（都去重）；
· 但 GROUP BY 可以配合聚合函数，DISTINCT 只能去重；
· MySQL 优化器对两者的处理经常生成相同的执行计划，性能差异可忽略。 建议：需要聚合用 GROUP BY，纯去重两者皆可，DISTINCT 语义更清晰。
Q：想统计"每个分组的前几条"，GROUP BY 能做到吗？
A：不能优雅地做到。GROUP BY 每组只输出一行，要取前 N 条得靠 窗口函数（ROW_NUMBER / RANK）或变量模拟。 详见《窗口函数》一篇中「分组 Top-N」的标准写法——这是窗口函数最经典的应用场景。
Q：多列 GROUP BY 和 GROUPING SETS 是什么？
A：GROUP BY a, b 按 a、b 的组合分组。 而 GROUPING SETS（以及 ROLLUP、CUBE） 能一次查询生成多个分组维度的小计与合计， 比如同时给出「按部门」「按城市」「总计」三档结果。
MySQL 支持 ROLLUP（WITH ROLLUP），但 GROUPING SETS/CUBE 支持不完整（PostgreSQL、Oracle 完整支持）。做报表时非常有用。
