SQL JOIN 原理与算法

七种 JOIN 语义 × 三种物理算法——从写对到跑快

INNER/LEFT/RIGHTNested LoopHash JoinMerge Join驱动表
① JOIN 语义 ② 三种物理算法 ③ 代价与选择 ④ 优化实践 ⑤ 常见陷阱
一句话总结：JOIN 要分两层看——逻辑层是你写 INNER/LEFT/OUTER 表达的语义； 物理层是数据库实际用的算法（Nested Loop / Hash / Merge）。 SQL 写对了只保证结果正确，性能取决于优化器选了哪种算法、谁当驱动表。

最容易踩的坑：LEFT JOIN 的 WHERE 条件位置。
LEFT JOIN b ON ... AND b.status=1 → 条件在 ON 里，左表行保留，右表不满足则填 NULL。
LEFT JOIN b ON ... WHERE b.status=1 → 条件在 WHERE 里，NULL 行被过滤掉， 效果退化成 INNER JOIN！这是面试与生产最常见的错误。

02三种物理 JOIN 算法

① Nested Loop Join（嵌套循环）

图 2：嵌套循环——最简单但最慢，靠索引救命

BNL（Block Nested Loop）：MySQL 的优化——把驱动表的一批行（join_buffer）一次性拿去和被驱动表比对， 减少被驱动表的扫描次数。join_buffer_size 太小会导致被驱动表被反复扫描。

② Hash Join（哈希连接）

较小的表当 build 侧 ② Probe：大表逐行探测 hash(key) → 找桶 → 比对 O(1) 定位，只需扫一遍 复杂度 ≈ O(M + N)，远优于嵌套循环的 O(M×N) ⚠️ 限制：只能做等值连接（=），非等值（>、LIKE）无法哈希 内存不够时会落盘分片（Grace Hash Join），性能下降但仍可用
图 3：Hash Join——MySQL 8.0.18+ 才支持，是目前的主力算法

③ Merge Join（排序归并）

两边都按 JOIN KEY 排序，然后像归并排序的合并步骤一样双指针推进。 复杂度 O(M log M + N log N)。如果两边本来就有序（有索引），则退化为 O(M+N)，极快。

MySQL 对 Merge Join 支持有限（主要靠索引扫描模拟），PostgreSQL、Oracle 用得多。

优化器的决策逻辑：① 先看 JOIN 类型是否等值 → 非等值只能用嵌套循环； ② 估算两张表的行数与选择性，选结果行数少的当驱动表； ③ 如果驱动表小、被驱动表有索引 → Nested Loop + Index Lookup； ④ 如果都是大表且是等值连接 → Hash Join。

驱动表选择：小表驱动大表

Nested Loop 下，驱动表行数越少，被驱动表被扫描的次数越少。

04优化实践

  1. 被驱动表的 JOIN 列必须有索引。这是 Nested Loop 性能的生命线。 用 EXPLAIN 看，如果出现 Using join buffer (Block Nested Loop)， 说明没走索引，通常是灾难。
  2. 用小表驱动大表。STRAIGHT_JOIN 可强制指定驱动表顺序 （仅当你确信优化器选错时用）。
  3. 避免 JOIN 时做函数/类型转换。 ON a.id = CAST(b.id AS ...) 会导致索引失效， 必须保证 JOIN 列类型一致。
  4. 只 SELECT 需要的列。减少回表与网络传输， 配合覆盖索引可做到 Using index。
  5. 大表 JOIN 前先过滤。把过滤条件下推到各自表内， 缩小参与 JOIN 的数据量。
  6. 多表 JOIN 控制在 3～4 张以内。超过后优化器的搜索空间爆炸， 容易选到糟糕计划；应考虑拆分查询或冗余字段。
-- 用 EXPLAIN 观察 JOIN 执行情况
EXPLAIN SELECT u.name, o.amount
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.created_at > '2026-01-01';

-- 关键看这几列：
--   type:  eq_ref / ref  → 走了索引（好）
--          ALL           → 全表扫描（危险）
--          index         → 全索引扫描
--   key:   实际使用的索引
--   rows:  预估扫描行数（越小越好）
--   Extra: Using index       → 覆盖索引（好）
--          Using join buffer → BNL，没走索引（需优化）
--          Using where       → 额外过滤

05常见陷阱

Q：LEFT JOIN 加了 WHERE 条件后，左表的行数变少了？
A：你把右表的过滤条件写在了 WHERE 里。LEFT JOIN 产生的 「右表全 NULL」的行会被 WHERE b.status=1 过滤掉， 语义退化成 INNER JOIN。
解决：把右表条件移到 ON 子句里： LEFT JOIN b ON b.a_id = a.id AND b.status = 1。
Q：JOIN 后结果行数比左表还多？
A：右表的 JOIN KEY 不唯一，一对多导致结果放大。 比如左表 100 行，右表每个 key 平均 5 行 → 结果 500 行。
解决：① 确认右表的 JOIN 键是否应该是唯一的（加唯一索引约束）； ② 或先对右表做聚合去重再 JOIN：JOIN (SELECT a_id, MAX(x) FROM b GROUP BY a_id) t； ③ 如果只想判断"是否存在"，改用 EXISTS（SEMI JOIN 不放大）。
Q：IN 和 EXISTS 该用哪个？
A：现代优化器（MySQL 5.6+）会把两者优化成同样的 SEMI JOIN 执行计划， 性能差异已基本消失，按可读性选即可。
但有两条经验仍适用：① NOT IN 遇到子查询含 NULL 时 结果永远为空（经典陷阱），应改用 NOT EXISTS； ② 子查询结果集很大时，JOIN 通常比 IN 更可控。
Q：COUNT(*) 在 JOIN 后为什么不准？
A：JOIN 放大了行数。COUNT(*) 统计的是结果集行数而非左表行数。 要统计左表行数，用 COUNT(DISTINCT a.id) 或先聚合再 JOIN。
