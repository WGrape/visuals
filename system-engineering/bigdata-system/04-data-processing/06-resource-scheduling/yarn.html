YARN 资源调度

把「资源管理」从计算框架里拆出来：RM / NM / AM 与 Container

为什么需要 YARN

在 Hadoop 1.x 时代，MapReduce 的 JobTracker 既要接收作业、又要负责把 CPU 和内存分配给任务——资源管理与作业调度耦合在同一个单点进程里。集群规模一大，JobTracker 就成了 bottleneck：调度慢、容错差、还只能跑 MapReduce，Spark/Flink 想用这套集群根本没门。

YARN（Yet Another Resource Negotiator）的解法很优雅：把「资源调度」从计算框架里彻底拆出来，变成集群共用的基础设施。这样 MapReduce、Spark、Flink 都只是「跑在 YARN 上的一种应用」，它们共享同一个资源池，按需申请，互不干扰。类比：YARN 像公司的「公共资源部」，谁要用多少工位（CPU）和设备（内存）都向它报备，而不是每个团队各盖一栋楼。

关键认知：YARN 只管「把资源给谁、给多少」；至于任务怎么算、数据怎么处理，是上层计算框架（AM）的事。职责分离，各司其职。

四大角色

🧭

ResourceManager（RM）

全局唯一的资源调度大脑，运行在主节点。它维护整个集群的资源视图（有多少可用 CPU/内存），接收各应用的资源请求，按调度策略把 Container 分配给 ApplicationMaster。它不关心任务逻辑，只管「资源账本」。

🖥️

NodeManager（NM）

每个工作节点上跑一个的「管家」。负责向 RM 汇报本机资源（默认每 3 秒一次心跳）、管理本节点上的 Container 生命周期（启动、监控、销毁），并监控容器资源使用是否超量。它是资源隔离的真正执行者。

📋

ApplicationMaster（AM）

「每个应用一个」，由 RM 在某节点的 NM 上启动。它是该应用的「项目经理」：向 RM 申请运行任务所需的 Container，拿到资源后与 NM 协作启动任务，并跟踪任务进度、处理失败重试。MapReduce 有 MR 的 AM，Spark 有 Spark 的 AM。

📦

Container

资源封装的最小单位，是 YARN 的「资源账单」：明确指定若干 vCore（虚拟 CPU 核）和 Memory（如 2G 内存）。任务只能在分配给它的 Container 内运行，超出限额会被 NM 杀掉。它是物理资源在逻辑上的切片。

三种调度器对比

YARN 通过可插拔的调度器决定「谁来用资源、用多少」。三种主流策略定位不同：

调度器队列模型抢占适用场景
FIFO Scheduler单队列，先到先做无简单测试、单用户小集群，资源大作业会阻塞后续
Capacity Scheduler多队列，各队列有容量下限/上限支持（可配）多租户生产集群，按部门划分队列保证最低资源
Fair Scheduler多队列，动态公平共享支持追求资源利用率与公平性，空闲资源被按需借走
默认通常开启 Capacity Scheduler。核心取舍在于：是优先「保证每个队列的最低资源」（Capacity），还是优先「所有作业动态公平瓜分空闲资源」（Fair）。

与 MapReduce / Spark 的关系

YARN 是底座，上层计算框架只是它的「租客」：

  • MapReduce on YARN：MapReduce 的 AM 向 RM 申请 Container，在容器内跑 Map/Reduce Task。MR 已退化为 YARN 上的一个应用。
  • Spark on YARN（client 模式）：Driver 跑在提交作业的客户端机器上，Executor 由 AM 向 YARN 申请 Container 启动。适合交互式调试，Driver 退出任务即结束。
  • Spark on YARN（cluster 模式）：Driver 也跑在 YARN 集群的 Container 里，客户端提交后即可断开。适合生产长作业。
一句话区分：client 模式 Driver 在本地、看得见日志；cluster 模式 Driver 在集群内、客户端可安全退出。生产多用 cluster。

面试问答

Q：Container 到底是什么？
A：Container 是 YARN 中资源分配的最小单位，是对物理资源（vCore CPU + Memory）的逻辑封装。RM 把一个 Container（如 2 vCore、4G 内存）分配给某个应用的 AM，任务只能在该 Container 限定的资源内运行；超标会被 NodeManager 杀掉。注意它和 Docker 容器不是一回事，YARN 的 Container 是资源账单而非隔离沙箱（虽也可配合 cgroups 做隔离）。
Q：ApplicationMaster 挂了会怎样？
A：AM 由 RM 负责监控，一旦心跳超时，RM 会重新调度一个新的 AM 在别的节点上重启（默认重试次数可配，如 2 次）。应用状态由 AM 自己负责恢复（如 MapReduce 会重新申请资源重跑未完成的任务）。所以 AM 故障不会让整个应用彻底失败，但会带来一定恢复开销。
Q：YARN 和 Kubernetes（K8s）的定位差异？
A：YARN 专为「大数据批/流计算」设计，深度理解 vCore/内存、与 HDFS 亲和（数据本地性），调度粒度偏重资源；K8s 是通用容器编排平台，擅长微服务、弹性伸缩与多云部署。当下趋势是 Spark/Flink 既可 on YARN 也可 on K8s，新集群更多转向 K8s，但存量 Hadoop 生态集群仍以 YARN 为资源层。

YARN 架构与三个核心组件

组件职责数量故障影响
ResourceManager全局资源调度与分配1（可 HA）整个集群不可用
NodeManager单节点资源管理与容器启停每节点 1 个仅该节点任务失败
ApplicationMaster每个应用一个，向 RM 申请资源每应用 1 个该应用失败
Container资源抽象（内存+CPU 核）动态单个任务重试

YARN 的设计突破：把资源管理与作业调度分离。RM 只管“给谁多少资源”，AM 管“用这些资源跑什么、失败怎么重试”。所以同一个集群能同时跑 MapReduce、Spark、Flink——这是 Hadoop 1.x 做不到的（那时 JobTracker 什么都管）。

关键资源配置

参数默认值含义与调优
yarn.nodemanager.resource.memory-mb8192 MB节点可分配给容器的总内存，应设为物理内存的 80%
yarn.nodemanager.resource.cpu-vcores8节点可用虚拟核数，常设为物理核的 1~2 倍
yarn.scheduler.minimum-allocation-mb1024 MB单个容器的最小内存
yarn.scheduler.maximum-allocation-mb8192 MB单容器上限，必须 ≥ 你申请的量
yarn.nodemanager.vmem-pmem-ratio2.1虚拟内存/物理内存比例，超限杀容器
mapreduce.map.memory.mb1024 MB单个 map 任务内存

资源申请

# 提交作业时指定资源（Spark on YARN 为例）
spark-submit \
  --master yarn \
  --deploy-mode cluster \
  --driver-memory 2g \
  --executor-memory 4g \
  --executor-cores 2 \
  --num-executors 20 \
  --conf spark.executor.memoryOverhead=1g \   # 堆外内存，默认 max(384m, 0.1×堆内)
  --conf spark.dynamicAllocation.enabled=true \
  app.jar

# 经验：总内存 = (executor-memory + memoryOverhead) × num-executors
#       必须 < 队列可用容量，否则一直 ACCEPTED 不运行

最常见的失败：容器被 kill 且日志显示 Container killed by YARN for exceeding memory limits。原因往往是堆外内存没算进去——JVM 堆外（直接缓冲、线程栈、元空间）也要占容器额度。解法是调大 memoryOverhead，或检查是否有 native 库在分配堆外内存。

三种调度器对比

调度器机制优点缺点
FIFO先进先出最简单大作业会饿死小作业
Capacity队列 + 容量保证多租户，生产常用配置复杂
Fair公平分享，动态平衡小作业响应快大作业可能被压制

队列配置

<!-- capacity-scheduler.xml 核心配置示例 -->
<property>
  <name>yarn.scheduler.capacity.root.queues</name>
  <value>prod,dev</value>
</property>
<property>
  <name>yarn.scheduler.capacity.root.prod.capacity</name>
  <value>70</value>          <!-- 保证 70% 容量 -->
</property>
<property>
  <name>yarn.scheduler.capacity.root.prod.maximum-capacity</name>
  <value>90</value>          <!-- 空闲时可借用至 90% -->
</property>
<property>
  <name>yarn.scheduler.capacity.root.dev.capacity</name>
  <value>30</value>
</property>
<!-- 关键：capacity 是“保证下限”，maximum-capacity 是"借用上限" -->

队列设计的判据：按业务线或优先级划分，而不是按个人。capacity 保证各队列的下限（防止被饿死），maximum-capacity 允许空闲时借用（提高利用率）。两者配合才能既不饿死又能压满集群。

自检 Q&A

Q：作业一直 ACCEPTED 不变成 RUNNING 怎么办？

A：三种原因——① 资源不够：队列容量已满，等前面的作业释放（最常见）；② 单容器申请量超过上限：maximum-allocation-mb 小于你申请的量，永远分配不到；③ AM 启动失败：看 yarn applicationattempt -list 与 AM 日志。诊断第一步是 yarn application -status 看 Diagnostics 字段，它通常会直接说明卡在哪。

Q：Executor 数量到底设多少？

A：按总资源 / 单 executor 资源算，并留余量。例：集群可用 100 核 400 GB，单 executor 配 4 核 16 GB → 理论 25 个，实际配 20 个留 20% 余量。另外要考虑并行度与分区数的关系：executor 数 × core 数 = 并行 task 数，若数据分区数远小于这个值，多的核会闲置——所以分区数（如 Spark 的 spark.sql.shuffle.partitions，默认 200）也要一起调。

Q：为什么容器总被 kill？

A：先分清是物理内存还是虚拟内存超限。日志里 beyond physical memory limits → 真实内存超了，需加大 executor-memory 或 memoryOverhead；beyond virtual memory limits → 通常是 JVM 预留了远超实际使用的虚拟地址空间（尤其 64 位 + 大量线程时），可以调大 vmem-pmem-ratio 或直接关闭虚拟内存检查（yarn.nodemanager.vmem-check-enabled=false）。

Q：YARN 和 Kubernetes 在大数据场景怎么选？

A：看技术栈。已有 Hadoop 生态（HDFS、Hive、Spark）且以批处理为主 → YARN 集成最成熟，迁移成本高不值得。新建平台、需要与在线服务混部或统一运维 → Kubernetes 更合适（Spark on K8s 已成熟，Flink on K8s 是官方推荐）。关键差异：YARN 的资源粒度与队列模型更适合批处理的多租户，K8s 的声明式与生态更适合统一基础设施。两者不是替代关系，很多公司在长期共存。
