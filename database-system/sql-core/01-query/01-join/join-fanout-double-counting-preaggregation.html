SQL JOIN 扇出：订单明细和支付尝试一连接，金额为什么翻倍

用两条明细乘两次支付尝试的四行结果，解释多对多膨胀与预聚合修复。

两个一对多关系会相乘

订单 1 有两条明细，金额分别 30 和 70；它还产生过两次支付尝试，一次失败、一次成功。单独把 orders 连 order_lines 得两行；单独连 payment_attempts 也得两行。如果在同一查询里把两张子表都按 order_id 连到订单，订单 1 会得到 2×2=4 行：每条明细分别配上两次尝试。此时 SUM(line.amount)=30+30+70+70=200，而真实订单明细合计只有 100。这叫 JOIN 扇出，根因是连接基数，不是 SUM 函数算错。

只有先弄清每张表的粒度与主键，才能预判输出行数。orders 是一单一行，order_lines 是一单多行，payment_attempts 也是一单多行。查询目标若是一单一行，就不能直接把两个多行集合同时展开后再随意聚合。

图解：两个一对多 JOIN 的乘法

沿箭头逐步核对输入、变换和输出；下面的推演可以逐步切换。

把四行明确写出来

连接后的行分别是 (line30, 支付失败)、(line30, 支付成功)、(line70, 支付失败)、(line70, 支付成功)。SELECT 看前十行时可能只注意到“每个字段都对”，却漏掉整张结果集已经重复。若用 COUNT(*) 当订单数，会得到 4；COUNT(DISTINCT order_id) 可以把订单数改回 1，但 SUM(line.amount) 仍是 200。`SUM(DISTINCT line.amount)` 也不是通用修复：若两条合法明细金额都为 30，它会错误地只计一次 30。

对多个一对多表，扇出可能继续相乘。例如再连三条优惠券核销记录，订单 1 可能变成 2×2×3=12 行。输出行数暴涨不仅影响正确性，也会让排序、聚合和网络传输变慢。

逐步推演

列出粒度

订单一行、明细两行、尝试两行。

直接连接

订单 1 膨胀成 2×2=4 行，金额算成 200。

各自预聚合

明细和支付分别压成每单一行。

核最终金额

订单 1 回到 100，并保留未支付订单。

先聚合到订单粒度再连接

正确的一种方式是先从 order_lines 按 order_id 聚合出 line_total=100、line_count=2，得到每单一行；再从 payment_attempts 按 order_id 计算需要的支付状态或成功金额，同样每单一行；最后把两个一单一行的结果连接到 orders。此时主查询仍是一单一行，金额不会相乘。预聚合可以用 CTE、子查询或物化汇总表，关键是写清每个中间结果的唯一键和粒度。

若只需判断“是否存在成功支付”，用 EXISTS 通常比连接整张尝试表更贴近语义；它不把每次尝试变成一行输出。若需要最新一次尝试的详情，先按明确时间和稳定 tie-breaker 排名，每单取一行，再连接；不要用 `MAX(status)` 猜哪个状态最新。

连接阶段订单 1 行数金额观察
orders1尚未展开明细
连 order_lines230+70=100
再连两次 payment_attempts430+30+70+70=200（错误）
两侧先预聚合再连1line_total=100（正确）

LEFT JOIN 与过滤位置

报表还要显示未支付订单时，可以 LEFT JOIN 预聚合支付结果。但若在最外层 WHERE 写 `payment_status='SUCCESS'`，没有匹配支付记录的订单会被过滤掉，结果常等同于内连接。要判断是否保留未支付行，先明确业务问题；把条件放在支付子查询里、JOIN ON 里或 WHERE 里，含义可能不同。条件位置调整不是纯性能优化，还会改变结果集合。

退款、部分支付和多币种会使“成功金额”更复杂。应区分支付尝试、实际渠道交易、退款流水和最终净额，不能因为一个订单有成功尝试就忽略后续退款。

用执行计划定位扇出

EXPLAIN 或实际执行统计中观察各连接节点的估计行数与实际行数。若 orders 1000 行、明细平均 4 行、尝试平均 3 行，直接双连接可能生成约 12000 行；若优化器误估成 1000 行，可能选错连接顺序或内存预算。慢查询排查时同时看真实结果行数、各表键是否有索引、统计信息是否新鲜。索引可以让查找更快，却不会自动修正把金额乘大的语义错误。

数据质量也要核对：如果 payment_attempts 的 order_id 本身有异常重复或一条尝试被重复入库，先解决业务去重，再讨论 SQL 聚合。

怎样设计验收数据

建立订单 1：两条金额 30、70 的明细、两次支付尝试；订单 2：一条金额 50 的明细、一次成功尝试；订单 3：一条金额 20 的明细、没有支付尝试。期望订单明细总额依次为 100、50、20。分别用原始双 JOIN 和预聚合写法查询，观察订单 1 的 4 行扇出、订单 3 在 LEFT JOIN 下是否保留，以及最终汇总是否为 170。再把订单 1 两条明细都改为 30，证明 SUM(DISTINCT amount) 会低估。

真实报表应把每个 CTE 的“主键/粒度”和期望行数写成注释或测试断言。只有确保中间结果粒度正确，后面的 GROUP BY 才有可信含义。

JOIN 扇出与重复计数的判据

场景是否扇出说明
1:1（主键对主键）不扇出行数不变，安全
N:1（订单→用户）不扇出每条订单最多匹配 1 个用户，安全
1:N（用户→订单）扇出一个用户有多条订单，行数放大
N:M（订单→商品→促销）扇出且可能双重两个 1:N 串联，倍数是乘积
维度表有多条匹配扇出维度表不唯一是最常见的坑

扇出的量化：假设订单 100 万行，用户表 10 万行；订单 JOIN 用户（N:1）→ 结果仍是 100 万行（前提：用户表的 join key 唯一）。但如果用户表有重复（比如 ETL 重复导入导致一个 user_id 有 3 条），结果就变成 300 万行，SUM(amount) 直接翻 3 倍。这就是「金额对不上」最常见的根因。

检测与修复

-- 检测 1：join 后行数是否异常增加
SELECT
  (SELECT COUNT(*) FROM orders) AS n_orders,
  (SELECT COUNT(*) FROM (
      SELECT o.id FROM orders o JOIN users u ON o.user_id = u.id) t) AS n_joined;
-- n_joined > n_orders 说明用户表有重复的 user_id

-- 检测 2：直接看维度表 join key 是否唯一
SELECT user_id, COUNT(*) AS c
FROM users GROUP BY user_id HAVING COUNT(*) > 1
ORDER BY c DESC LIMIT 10;
-- 有结果 = 维度表不唯一，join 必然扇出

-- 检测 3：对比 join 前后的聚合值
SELECT
  (SELECT SUM(amount) FROM orders)                                     AS direct_sum,
  (SELECT SUM(o.amount) FROM orders o JOIN users u ON o.user_id=u.id)  AS joined_sum;
-- 两者不等 = 重复计数，必须修
-- 修复 1：先聚合再 join（最推荐，从根本上消除扇出）
WITH u AS (
    SELECT user_id, MAX(city) AS city          -- 或用 ROW_NUMBER 取一条
    FROM users GROUP BY user_id                -- 关键：保证每个 user_id 只有一行
)
SELECT u.city, SUM(o.amount)
FROM orders o JOIN u ON o.user_id = u.user_id
GROUP BY u.city;
-- 这样 join 前维度表已经唯一，不可能扇出

-- 修复 2：用窗口函数去重取一条
WITH u AS (
    SELECT * FROM (
        SELECT *, ROW_NUMBER() OVER (PARTITION BY user_id
                                     ORDER BY updated_at DESC) AS rn
        FROM users
    ) t WHERE rn = 1
)
SELECT ... FROM orders o JOIN u ON o.user_id = u.user_id;

-- 修复 3：用子查询代替 join（标量子查询天然不扇出）
SELECT o.id, o.amount,
       (SELECT city FROM users u WHERE u.user_id = o.user_id LIMIT 1) AS city
FROM orders o;
-- LIMIT 1 兜底防重复（但性能可能差，数据量大时用方案 1）

排查清单

症状原因处理
SUM 结果比预期大维度表 join key 不唯一先聚合维度表再 join；加唯一性校验
COUNT(DISTINCT) 与 COUNT 差很多存在扇出明确该用哪个；通常 COUNT(DISTINCT id) 才是对的
两个 1:N 串联后数字暴涨扇出相乘（N:M）分别聚合到同一粒度后再合并，不要直接串 join
LEFT JOIN 后 NULL 增多右表无匹配（正常）用 COALESCE；但要区分「无匹配」和「匹配到 NULL 值」
预聚合表与明细对不上聚合口径/时间粒度不一致统一口径；建立对账任务定期校验
加了 DISTINCT 就对了但很慢用 DISTINCT 掩盖了扇出不要靠 DISTINCT 掩盖，要修 join 逻辑；DISTINCT 只是遮住了症状
同一指标两个报表数值不同join 路径不同统一到一张事实表或统一的聚合层（语义层）

黄金规则：做聚合时，先保证每个维度表的 join key 唯一，再 join。用 GROUP BY 或 ROW_NUMBER 把维度表收敛到唯一粒度，就能从根本上杜绝重复计数。靠 DISTINCT 善后是治标不治本，还拖慢查询。

自检

COUNT(DISTINCT order_id) 算回一单，是否也让 SUM(line.amount) 自动回到 100？

不会。订单数的去重不影响已被复制的明细金额；应先按订单粒度聚合明细，再连接支付结果。

第一层 · 概念与判定：什么是扇出、怎么识别

一句话：JOIN 键不唯一时，行数会被放大，导致 SUM/COUNT 重复计算。这就是「扇出（fan-out）」引发的双计问题。

术语含义后果
扇出左表 1 行匹配右表 N 行 → 变 N 行行数放大 N 倍
双计放大后对左表字段 SUM，被加了 N 次金额/数量虚高
笛卡尔积两边都不唯一，行数 = n × m灾难级，可能打爆内存
  • 信号一：JOIN 后的 COUNT(*) 明显大于左表 COUNT(*) → 扇出了。
  • 信号二：SUM(金额) 与单独查左表的 SUM 对不上 → 双计了。
  • 信号三：看起来「结果虚高但每条都对」→ 典型的扇出双计特征。

扇出复现与三种解法

-- 复现：订单 1 行，订单项 3 行，直接 JOIN 求和 -> 订单金额被算 3 次
SELECT o.id, SUM(o.amount)      -- 错：amount 被重复加
FROM orders o JOIN items i ON i.order_id = o.id
GROUP BY o.id;

-- 验证扇出：对比 JOIN 前后行数
SELECT COUNT(*) FROM orders;                              -- 基准
SELECT COUNT(*) FROM orders o JOIN items i ON i.order_id = o.id;   -- 若更大则扇出

-- 解法一（推荐）：先聚合到唯一粒度，再 JOIN
SELECT o.id, o.amount, COALESCE(t.item_cnt, 0) AS item_cnt
FROM orders o
LEFT JOIN (SELECT order_id, COUNT(*) AS item_cnt FROM items GROUP BY order_id) t
       ON t.order_id = o.id;                              -- 子查询已聚合到 1 行/订单

-- 解法二：用 COUNT(DISTINCT) 修正计数（只能救计数，救不了 SUM）
SELECT COUNT(DISTINCT o.id) FROM orders o JOIN items i ON i.order_id = o.id;

-- 解法三：确认维度表唯一后再 JOIN（外键约束保证）
-- 维度表（users/products）通常唯一，事实表（orders/items）不唯一
-- 原则：事实表 JOIN 事实表 必须先在某一侧聚合

核心原则：事实表 JOIN 事实表，必须先把一侧聚合到唯一粒度。维度表 JOIN 事实表通常是安全的（维度表主键唯一）。

第四层 · 原理与取舍：三种解法的取舍

解法做法能修 COUNT能修 SUM代价
先聚合再 JOIN子查询把一侧聚合到唯一键✅✅SQL 变长，但最正确
COUNT(DISTINCT)去重计数✅❌救不了 SUM；大数据慢
SUM/COUNT(1/N)按扇出倍数折算⚠️ 不稳⚠️ 不稳倍数不固定时失效，不推荐
改用 EXISTS只判存在不取行✅✅不能取右表字段
为什么 COUNT(DISTINCT) 救不了 SUM？

因为 SUM 加的是值。订单金额 100 被复制 3 次，SUM 得 300；DISTINCT 只能对「哪些 id 出现过」去重，无法知道「100 应该只加一次」。所以 SUM 的双计只能靠「先聚合再 JOIN」或「不在放大后的结果上求和」解决。

怎么快速判断我的 JOIN 有没有扇出？

对比行数：分别跑 SELECT COUNT(*) FROM 左表 和 JOIN 后的 COUNT(*)。若后者更大，就是扇出。更精确的做法是 COUNT(DISTINCT 左表主键) 与 COUNT(*) 对比，两者不等即存在放大。

有没有办法从设计上避免？

有：① 建星型模型——事实表只 JOIN 维度表，事实表之间不直接 JOIN；② 用外键约束保证 JOIN 键唯一；③ 在数据仓库里建汇总层（DWS），预先聚合到常用粒度，下游直接查汇总表。
