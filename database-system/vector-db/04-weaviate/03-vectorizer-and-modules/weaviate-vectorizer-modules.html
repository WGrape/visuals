①五类模块与各自的职责

Weaviate 把「文本 → 向量」这件事内置成了模块（module）：在 Schema 里声明用哪个 vectorizer，写入对象时自动调模型生成向量，你不需要碰 embedding API。

模块类别代表模块作用
text2vec-*openai / cohere / huggingface / transformers / voyage / jinaai文本 → 向量
multi2vec-*clip / bind / colpali图文 / 多模态 → 同一向量空间
reranker-*cohere / transformers / jinaai / voyager检索后重排
generative-*openai / cohere / anthropic / ollama检索后直接生成答案（RAG 内置）
qna-*openai抽取式问答
generative-* 是 Weaviate 的特色：一次 GraphQL 查询可以「检索 + 拼 prompt + 调 LLM + 返回答案」，省掉自己写 RAG 编排。代价是把编排逻辑锁进了数据库层，后续换链路会比较重。

②自动向量化 vs 自带向量

两条路：让 Weaviate 生成，或者自己生成（vectorizer: none）：

方式配置优点缺点
自动向量化"vectorizer": "text2vec-openai"省事；批量写入自动处理写入路径绑模型；调外部 API 影响写入延迟与成本
自带向量"vectorizer": "none"完全掌控模型与版本；可离线批算自己负责一致性；漏传向量会直接报错
# 自动向量化
{
  "class": "Doc",
  "vectorizer": "text2vec-openai",
  "moduleConfig": {
    "text2vec-openai": { "model": "text-embedding-3-small", "dimensions": 512 }
  },
  "properties": [{ "name": "content", "dataType": ["text"] }]
}

# 自带向量
{
  "class": "Doc",
  "vectorizer": "none",
  "properties": [{ "name": "content", "dataType": ["text"] }]
}
# 写入时必须带 vector
{ "class": "Doc", "properties": {...}, "vector": [0.1, 0.2, ...] }

③写入路径上的向量化：吞吐与成本陷阱

自动向量化发生在写入路径上同步调用外部 API，这直接决定了批量导入的吞吐上限和失败模式。

现象原因对策
批量导入卡住/极慢逐条同步调 embedding API，受 RPS 与延迟限制开客户端 batching（autocut/batch 参数）；或改为自带向量离线批算
导入部分失败外部 API 限流 / 超时降低并发、加重试；批量接口按批返回成功失败
写入延迟随数据量上升向量化 + HNSW 插入叠加分批导入，观察 HNSW 构建进度
成本意外高每次写入都调一次 embedding（含更新）更新非向量字段也会触发重新向量化，需显式跳过
第 4 条是最容易漏的：只改了一个标量属性，也可能触发整条对象重新向量化，既浪费钱又拖慢写入。批量更新标量字段时务必确认向量化是否被触发。

④Named vectors：多向量独立索引

Named vectors 是 Weaviate 相对成熟的能力：一个对象可以有多组向量，每组独立索引，查询时指定用哪组。

{
  "class": "Doc",
  "vectorizer": "none",
  "properties": [{ "name": "title", "dataType": ["text"] },
                 { "name": "body",  "dataType": ["text"] }],
  "vectorConfig": {
    "title_vec": { "vectorizer": { "text2vec-openai": {} }, "vectorIndexType": "hnsw" },
    "body_vec":  { "vectorizer": { "text2vec-openai": {} }, "vectorIndexType": "hnsw" }
  }
}

实用场景：标题向量权重高、正文向量覆盖全，检索时两路各取 top-K 再融合，比把标题和正文拼在一起做一条向量效果更好 —— 拼接会稀释标题信号。

⑤换模型的五步迁移

更换 vectorizer（换模型 / 换维度 / 换供应商）在 Weaviate 里是一次数据迁移，不是配置变更：

  1. 新建 Class（如 DocV2），声明新 vectorizer；维度不同必须新 Class，不能原地改。
  2. 导出原对象（只导 properties，不导 vector），重新导入到新 Class，由新 vectorizer 生成向量。
  3. 对比检索质量：同一批 query 在新旧 Class 上各跑一次，对比 recall 与人工观感。
  4. 切流量：应用层切换 Class 名，或维护一个配置项做灰度。
  5. 清理旧 Class：确认稳定后再删，别急着删（回退要重新灌一遍）。
向量维度和距离度量在多数向量库里建库即定，不可原地修改。所以「换 embedding 模型」永远等价于「重建一整套数据」，这件事必须提前规划成本和窗口。

⑥速记卡

模块体系

text2vec / multi2vec / reranker / generative / qna 五类可插拔。

两种模式

自动向量化（省事）vs vectorizer: none（掌控）。

写入即向量化

同步调外部 API，批量导入吞吐受其限制。

最大的坑

改标量字段可能触发重新向量化，白花钱。

generative 模块

检索 + 生成一体，但把 RAG 编排锁进数据库层。

Named vectors

多向量独立索引，标题/正文分开比拼接更好。

换模型 = 迁移

维度不同必须新建 Class 并重灌全量数据。

规划前提

维度和度量建库即定，重建成本要提前算。

自动向量化把「省事」换成了「耦合」。用得爽的前提是明确知道它在写入路径上做了什么，尤其是那个「改标量也重新向量化」的隐藏成本。
