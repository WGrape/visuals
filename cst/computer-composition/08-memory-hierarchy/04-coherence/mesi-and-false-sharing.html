缓存一致性 MESI：多核为什么能共享内存，以及伪共享为什么这么贵

每个核都有自己的 L1/L2，同一块内存会有多份副本。MESI 用四个状态 + 广播失效，让这些副本「看起来只有一份」。而一旦两个线程写同一缓存行的不同变量，这套协议就会把性能拖垮。

一句话定位：用状态机维护「多份副本的一份假象」

MESI 给每行数据标四种状态：Modified（脏且独占）、Exclusive（干净且独占）、Shared（多份干净副本）、Invalid（作废）。写之前必须保证「只有我有有效副本」，读之前必须拿到最新值。

M本核改过、内存是旧值，其他核都没有
E只有本核有，且与内存一致
S多核共享，都是干净副本
I本副本无效，要读就重新取
四态与关键转换：写共享行要先广播作废

状态转换表（本核视角）

当前态本核读本核写其他核读其他核写
M命中，保持 M命中，保持 M回写/转发后变 S回写后变 I
E命中，保持 E原地升级 M（无需总线事务）变 S变 I
S命中，保持 S广播 invalidate，升级 M保持 S变 I
I发 read，得到 S 或 E发 RFO，得到 M——
E 态的价值

E 态让「独占且干净」的行可以直接升级为 M，不需要任何总线事务。这就是为什么单线程写自己刚读的数据几乎零成本——硬件通过 read-exclusive 提前拿到了独占权。

伪共享：算一笔真实的账

struct { long a; long b; } s;   // a 与 b 在同一 64B 缓存行

// 线程 1 反复写 s.a，线程 2 反复写 s.b
// 每次写都要：广播 invalidate → 等 ack → 从对方缓存搬整行
// 结果：两个线程比单线程还慢 5~10 倍

// 修法：把两个变量放到不同缓存行
struct { long a; char pad[56]; } s1;
struct { long b; char pad[56]; } s2;
场景每次写的代价相对性能
单线程写本地变量L1 命中，1~4 周期基准 1×
两个线程写不同缓存行各自命中，偶尔共享总线0.9~1.0×
两个线程写同一缓存行（伪共享）每次都要作废+搬运（约 100~300 周期）0.1~0.2×
两个线程读同一行（无写）S 态共享，几乎无开销1.0×

判定方法：perf c2c 能直接指出「哪两个变量、哪两个核在争同一行」。没有这个工具时，看「扩展性」——加线程反而变慢，且 CPU 利用率不高，基本可以怀疑伪共享。

store buffer 与「内存重排」

为了不让写操作阻塞流水线，CPU 把写先放进 store buffer，稍后才真正写入缓存。于是别的核可能先看到「你后面的写」而看不到「你前面的写」——这就是内存重排的硬件根源。x86 用 TSO（只允许 store-load 重排），ARM/RISC-V 用更弱的模型（允许更多重排）。

// 经典 litmus test：两个线程各写各的，可能同时读到 0
// 线程1: x = 1; r1 = y;
// 线程2: y = 1; r2 = x;
// 弱内存序下 r1 == r2 == 0 是可能的

所以需要内存屏障（mfence / dmb）或原子操作来约束。这也是为什么 Java 的 volatile、Go 的 atomic、C++ 的 memory_order 必须存在——它们不是在「加锁」，而是在告诉编译器与 CPU「这里不许重排」。

排障：一致性问题的典型表现

现象根因处理
加线程后性能反降伪共享perf c2c，padding 到 64B
标志位改了对方看不到缺内存屏障/原子操作用 atomic store/load 或 volatile
偶发死循环等待编译器把读提到循环外用 volatile 或 atomic
数据竞争难复现弱内存序 + 缓存时序TSan 检测，或用顺序一致原子变量定位
NUMA 机器扩展性差跨节点访问 + 一致性流量绑核、本地分配

原理与取舍：为什么不让所有核共享一个 L1

共享缓存延迟高、带宽争抢严重；私有缓存快，但要维护一致性。MESI 的取舍是：读共享（S 态多副本，省带宽）、写独占（M 态单副本，保正确）。代价是每次跨核写都要一次「作废 + 搬运」，这也解释了为什么多线程程序的扩展性常常卡在「共享写」上，而不是「计算量」上。

MESI 和 MOESI 差什么？

MOESI 多一个 O（Owned）态：脏数据可以被多个核共享，由一个核负责应答读请求。它减少了「脏行被读」时的回写次数，AMD 用它。

为什么写完要等 ack？

必须确认其他核的副本都作废了，否则可能出现「两个核同时认为自己是唯一有效副本」。这个等待正是伪共享昂贵的直接原因。

原子操作和锁是什么关系？

锁是用原子操作实现的（如 CAS）。原子操作由缓存一致性协议在硬件层保证（lock 前缀 → 独占行），所以无竞争的原子操作只需约 20 周期，有竞争时会退化成总线锁或反复重试。

实测：把伪共享的代价跑出来

伪共享（false sharing）指两个核各写一个不同变量，但这两个变量落在同一条 cache line 上，于是一致性协议把它们当成同一个地址反复抢。改法只有一种：把两个变量隔开到不同 cache line。

Go：伪共享对比基准

// Go：不加 padding vs 加 padding，用 go test -bench 直接看差距
package main

import (
    "sync"
    "sync/atomic"
    "testing"
)

// 无 padding：两个计数器的数组元素相邻，很可能落在同一条 cache line
type Shared struct{ a, b [8]int64 }

func BenchmarkFalseSharing(b *testing.B) {
    var s Shared
    var wg sync.WaitGroup
    for i := 0; i < b.N; i++ {
        wg.Add(2)
        go func() { for j := 0; j < 1000; j++ { atomic.AddInt64(&s.a[0], 1) }; wg.Done() }()
        go func() { for j := 0; j < 1000; j++ { atomic.AddInt64(&s.b[0], 1) }; wg.Done() }()
        wg.Wait()
    }
}

// 加 padding：每个计数器独占一条 cache line（x86 为 64 字节 = 8 个 int64）
type Padded struct {
    a    int64
    _pad [7]int64   // 64 - 8 = 56 字节填充
    b    int64
}
// 实测在同一台双核机器上，Padded 版本通常快 2~5 倍

C++ / Java 的隔离写法

// C++：用 alignas 强制每个计数器独占 cache line
#include <atomic>
#include <thread>
struct alignas(64) Counter { std::atomic<int64_t> v{0}; };
Counter c0, c1;   // 两个对象地址相差 64 字节，必然不同行

// Java：@Contended（JDK 8 需 -XX:-RestrictContended，JDK 9+ 在 jdk.internal.vm.annotation）
@sun.misc.Contended
static final class Counter { volatile long v; }

perf c2c：定位争抢热点

# 用 perf c2c 直接看哪些 cache line 在被多个核争抢（最权威的伪共享定位手段）
perf c2c record -F 60000 -- ./app
perf c2c report --stdio
# 输出里 HITM（Hit Modified）高的行就是争抢热点：
#   HITM 表示本核读到了别的核改过的行，代价最高
#   关注 "Shared Object" 与代码行，改 padding 后 HITM 应显著下降
平台cache line 大小注意
x86 / x86-64（Intel、AMD）64 字节最通用，padding 到 64 即可
Apple Silicon（L2 层级）128 字节只按 64 对齐仍可能有伪共享，关键计数器按 128 对齐
ARM Cortex-A 系列64 字节与 x86 一致
IBM POWER128 字节同 Apple，需要更大 padding

Go 1.19 之前没有官方的 cache line padding 类型，常用 [7]int64 手写；写并发计数器的通用做法是按核分片（shard）+ padding，最后再汇总，这比用原子累加同一个变量快一个数量级。

协议变体与工程清单

MESI 是教学模型，真实处理器在它基础上打了补丁，目的是减少一次不必要的总线事务或内存回写。

协议新增状态解决什么谁在用
MESI—基础四态：Modified / Exclusive / Shared / Invalid教学模型
MESIFF（Forward）多个核共享时指定唯一一个负责响应，避免所有共享者一起回数据Intel（多核/多路）
MOESIO（Owned）允许脏数据在核间直接共享而不必先写回内存AMD、ARM 部分实现
MSI / MEI—简化版，牺牲性能换面积嵌入式小核

store buffer 是所有「明明写了却看不到」问题的根源：写操作先进入 core 私有的 store buffer，对别的核暂时不可见。要让它可见，必须走内存屏障或带 lock 的指令。

手段x86 指令代价量级适用场景
编译器屏障无（仅阻止编译期重排）0单核内与信号处理交互
写屏障（store-store）sfence（x86 上通常不需要）约 10~20 周期确保之前的写先被看到
全屏障mfence 或 lock 前缀指令约 20~50 周期需要强顺序的场景
原子操作（seq_cst）lock xadd 等约 20~30 周期（无争抢时）C++ std::atomic 默认语义
获取/释放语义通常是普通 mov（x86 TSO 天然满足）几乎 0能放宽就放宽，性能最好

排查与规避逐条核对：

  • 先确认是不是伪共享：用 perf c2c 看 HITM，不要凭直觉加 padding。
  • 计数器、标志位按核分片并 padding 到 64（Apple/POWER 用 128），最后汇总。
  • 只读数据尽量共享（停在 Shared 态），读写混合的数据才是伪共享重灾区。
  • 不要在锁里放无关变量：锁对象和被保护数据相邻也会造成伪共享。
  • 需要立刻可见的写要配屏障：只写不 fence 时，别的核可能读到旧值。
  • x86 是 TSO 模型：只有 store-load 会被重排，load-load / store-store 不会，别到处加 mfence。
  • 原子变量默认 seq_cst，能用 acquire/release 就改，通常能省掉一次 fence。
  • 数组分片比原子累加快：8 个分片比 1 个 atomic 快几倍，代价是读的时候要汇总。
  • 验证要用 contention 场景测：单核跑不出伪共享，必须多核同时写。
