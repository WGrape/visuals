边界：拆分前先确认团队、部署节奏和扩展瓶颈。小系统优先保持清晰模块边界。

核心区别 Monolith vs Microservices

单体关注『一个应用内怎么分模块』，微服务关注『多个应用间怎么协作』

微服务不是『把单体拆小』这么简单——它把『模块边界』升级成了『进程边界 + 网络边界 + 团队边界』，代价是引入了分布式系统的所有复杂度（网络、一致性、可观测性）。

微服务的隐性成本 Hidden cost

  • 网络开销：一次本地函数调用变成一次 RPC，延迟与失败率上升。
  • 分布式事务：跨服务一致性要靠 Saga、TCC、消息最终一致。

面试高频问答

Q：如何向面试官解释『为什么不用微服务』？
A：先说业务规模与团队规模：在域模型简单、团队小、迭代快的早期，单体的强一致和零分布式复杂度是优势；微服务带来的网络、一致性与运维成本在小规模下是净负担。强调『架构服务于当前阶段，而非追潮流』。
Q：服务拆多细合适？
A：以『领域边界 + 团队边界』为准，一个服务对应一个可独立部署、可独立演进的限界上下文；拆太细会陷入分布式调用地狱，一般一个团队维护 2~5 个服务较合理。
Q：单体就一定会变成『大泥球』吗？
A：不会。单体内部用清晰的模块边界（如 DDD 分层、包依赖约束）也能长期保持健康；『大泥球』源于缺乏边界意识，而非单体本身。

什么时候该拆：三个信号与三个反信号

微服务不是「更先进的架构」，而是一种用复杂度换组织效率的手段。判断该不该拆，不看潮流，看下面这些具体信号。

该拆的信号具体表现不该拆的反信号具体表现
团队规模变大多个团队改同一份代码，发布互相阻塞团队很小三五个人，沟通成本本来就很低
发布频率冲突A 模块要每天发，B 模块要每月发发布节奏一致整体一起发即可，无需隔离
负载特征分化某模块需要独立扩容，其他不需要负载均匀整体扩容更简单也更便宜
故障隔离需求一个模块崩溃不应拖垮全站规模尚小没有足够流量验证隔离的价值
技术栈确实需要差异某部分需要特殊语言或运行时纯粹为了技术尝鲜引入多栈只会增加维护成本
最重要的一条拆分的驱动力应来自组织与发布节奏，而不是「看起来更先进」
先粗后细先按业务领域拆成几个大块，跑顺了再细分
可回滚拆分要能逐步推进，每一步都可独立回滚
数据先想清楚服务边界本质是数据所有权边界，这比代码拆分更难也更重要

微服务的六项隐性成本

拆分带来的成本不在代码里，而在日常运维与排障的每一处细节。这些成本往往在半年后才逐渐显现，但那时已经很难回头。

分布式调试一次请求跨多个服务，定位问题要看多份日志
网络不可靠本地调用变成远程调用，必须处理超时、重试、幂等
数据一致性跨服务事务无法用数据库事务解决，要引入补偿
部署与编排服务数量成倍增长，需要完整的发布与编排体系
可观测要求没有链路追踪几乎无法排障，这是硬门槛
团队认知负担每个人需要理解的边界与契约显著增加
测试成本集成测试环境变复杂，端到端验证更慢
资源开销每个服务都有固定开销，服务越多浪费越多

最容易被低估的一项

是「本地调用变成远程调用」这件事本身。原本一个函数调用要么成功要么抛异常，现在多了三种结果：成功、失败、超时（不知道成功还是失败）。超时带来的不确定性，是幂等、重试、对账等一系列复杂度的根源。

最容易被忽略的一项

是数据所有权。如果拆了服务但仍然共用一个数据库、直接互相查表，那只是把单体变成了「分布式单体」：既付出了分布式的代价，又没有获得独立部署与演进的好处。

怎么拆：绞杀者模式的推进顺序

最稳妥的迁移不是推倒重来，而是让新服务逐步绞杀旧系统：新功能走新服务，旧功能按优先级逐步迁出，中间用一层路由把流量分开。

绞杀者模式：每一步都可回滚，任何时刻系统都是可用的
# 绞杀者模式的路由层（伪代码） def handle(request): feature = request.path if feature in MIGRATED_FEATURES: # 已迁移的功能走新服务 return new_service.handle(request) return legacy.handle(request) # 其余仍走旧系统 # 推进原则： # 1) 一次只迁一个功能，迁完观察一段时间 # 2) 灰度开关控制，随时可以切回旧路径 # 3) 数据迁移先双写，再校验，最后切读 # 4) 旧模块确认零流量后才删除，不要提前删 # 数据迁移的三步： # 双写期：新旧库都写，以旧库为准 # 校验期：对比两边差异，修正不一致 # 切读期：读新库，保留旧库一段时间做兜底

深入自检：关于拆分的六个高频问题

单体就一定不好吗？

不是。对于团队小、业务尚在探索期的系统，单体的优势非常明显：开发快、调试简单、部署省事、没有分布式一致性问题。很多成功产品早期都是单体，问题往往出在「单体内部已经一团乱」而不是单体本身。

模块化单体是不是折中方案？

是的，而且常被低估。在单体内部强制模块边界（清晰的包结构、禁止跨模块直接访问内部实现），既获得了隔离与可维护性的大部分好处，又暂时不必付出分布式代价。当某个模块确实需要独立部署时，再拆出去也更容易。

服务拆多细合适？

以「能否被一个团队独立理解和维护」为界，而不是以「功能多小」为界。一个服务如果需要跨三个团队协调才能改，说明边界划错了；如果小到只有一两个接口且没有独立数据，拆分收益就小于成本。

共享数据库为什么是反模式？

因为它让两个服务的实现细节互相耦合：一方改表结构就要通知另一方，独立部署就成了一句空话。正确做法是每个服务拥有自己的数据，需要对方数据时通过接口获取，或者用事件同步一份只读副本。

跨服务事务怎么处理？

不要试图模拟分布式事务，成本高且脆弱。更常用的做法是：把长事务拆成一系列本地事务，用补偿动作处理失败（Saga）；或者通过消息队列保证最终一致，并设计好幂等与对账。

什么时候该考虑合回去？

当两个服务总是同时修改、同时发布、彼此频繁调用，且它们之间没有真正的独立演进需求时，边界就划错了。合并回去是正当的优化，不必因为已经拆了就硬撑。
