Kubernetes 三种探针：服务还没准备好，为什么被反复重启

用启动要 45 秒的应用解释 startup、readiness、liveness 的判定顺序、故障动作与滚动发布。

三个探针分别回答三个问题

startupProbe 问“容器是否已经完成启动阶段”；readinessProbe 问“当前是否适合接收新流量”；livenessProbe 问“容器是否陷入需要重启才能恢复的状态”。这三个问题可能有不同答案：数据库连接池还在预热时应用已启动但不应接流量；运行一段时间后下游短暂不可用，应用自身仍活着，可能只需暂时不接新请求，而非重启容器。把同一个 `/health` 端点复制给所有探针，容易让一次依赖抖动触发大规模重启。

探针可以用 HTTP、TCP、exec 等方式，具体支持依 Kubernetes 版本和配置。TCP 端口能接受连接只证明监听栈通了，不证明路由、数据加载或权限准备完成。健康端点应快速、有界并表达清晰语义。

45 秒启动案例

应用加载索引和预热连接池需要 45 秒。若 liveness 在第 5 秒就开始检查、连续几次失败便重启，容器可能总在第 45 秒之前被杀，反复进入 CrashLoopBackOff。可以设置 startupProbe 给启动阶段足够窗口，例如周期 5 秒、允许 12 次失败，名义上约覆盖 60 秒，具体检查起点、耗时和阈值仍要按配置验证。startupProbe 未成功期间，liveness 和 readiness 的常规检查会被推迟；启动成功后，再由 readiness 判断能否接流量，由 liveness 判断是否需要重启。

另一种做法是配置很长的 liveness 初始延迟，但它对异常慢启动与运行期故障不够灵活。startupProbe 明确把“正在启动”从“运行中失活”分开，指标和排障也更清楚。

readiness 失败发生什么

Pod 运行后遇到临时依赖问题，readiness 失败通常使它被标记为 NotReady，Service 的端点选择会逐步停止把新流量送来；容器本身不因 readiness 失败而重启。端点变化在控制面与数据面传播需要时间，已有连接和在途请求不会瞬间消失。因此应用仍要处理取消、超时和优雅退场。若 readiness 检查把所有可选下游都设为必需，一个共享依赖短抖动可能让所有副本同时 NotReady，服务反而完全没端点；要按业务能否真正服务核心请求设计。

滚动发布时，新 Pod 未 Ready 通常不计作可用副本，部署进度可能停住。此时先看 readiness 事件、日志和依赖状态，不应通过直接移除探针让尚未准备好的应用接流量。

探针回答的问题失败时典型动作
startup启动阶段是否完成继续等待；超阈值时重启
readiness现在能否接新流量标记 NotReady，逐步移出端点
liveness是否需重启恢复连续失败达到阈值后重启
业务监控用户请求是否真的成功告警、回滚或治理依赖

liveness 失败的代价

liveness 连续失败达到阈值时，kubelet 会重启相应容器。若进程死锁、事件循环永久阻塞且无内部恢复机制，重启可能有效；若只是数据库慢、网络故障或远端限流，重启所有副本通常无助于修复下游，还会丢失连接、缓存和请求状态，制造新的冷启动峰值。liveness 端点不宜做昂贵全链路查询，否则健康检查本身在高负载下超时，反过来扩大故障。

CrashLoopBackOff 是容器反复退出或重启后的退避现象，不只由探针造成；启动命令错误、配置缺失、内存 OOM 等也可能触发。看容器上次退出原因和事件，不能见到这个状态就一律调大探针阈值。

参数不是越短越好

`periodSeconds` 决定检查频率，`timeoutSeconds` 给单次探针响应上限，`failureThreshold` 决定连续失败门槛；`successThreshold` 对 readiness 的恢复也有作用，具体字段允许范围按 API 校验。阈值太敏感会因短时调度或网络抖动误判，太迟钝则让坏副本长时间接请求。要按服务启动分布、正常延迟、恢复时间和最小副本数设定。生产数据应观察 P95/P99 启动耗时，而非只看开发机最快一次。

若应用只在第一次启动时长，startup 窗口可覆盖冷启动，同时 liveness 运行期仍保持合理敏感度。变更探针参数后应实际模拟慢启动和死锁，两类情况都要通过。

发布与终止的时间线

新 Pod 调度、拉镜像、启动容器、startup 成功、readiness 成功后才适合承接 Service 新流量。删除旧 Pod 时，状态会转为终止，端点更新和应用 SIGTERM/预停止钩子并行发生；旧进程应停止接新请求、等待必要的在途请求结束，并在宽限期内退出。readiness 不是流量瞬时开关，客户端连接和负载均衡缓存也有传播延迟。部署策略的 maxUnavailable、maxSurge 和最小副本数决定滚动时的容量余量。

若新版本错误地把 readiness 永远设为失败，部署可能停滞；若把 readiness 过早设成功，用户会遇到“Pod 已 Ready 但首批请求很慢”。发布验收需同时看探针状态与真实业务成功率。

排查清单

记录 Pod 事件、探针失败日志、上次退出原因、容器启动时间和 readiness 变化时间。对慢启动，比较 startup 允许窗口与实际初始化最长耗时；对运行期短暂不就绪，核查是否错误触发 liveness；对只有某节点失败，检查节点网络和资源压力。最后用受控实验模拟 45 秒冷启动、短时数据库故障和进程死锁：期望分别是“等启动”“暂不接流量但不乱重启”“重启坏容器”。三条路径对应不同探针，不能只以 Pod 最终 Running 为验收。

三类探针的参数与语义

探针作用失败后果
startupProbe容器是否已启动完成失败则不执行其他探针；超过失败阈值则重启
readinessProbe是否可接收流量失败则从 Service 的 endpoints 摘除（不重启）
livenessProbe是否还活着失败则重启容器
参数默认值说明
initialDelaySeconds0容器启动后多久开始探测
periodSeconds10探测间隔
timeoutSeconds1单次探测超时
successThreshold1连续成功几次算成功（liveness 必须为 1）
failureThreshold3连续失败几次算失败
terminationGracePeriodSeconds30优雅退出等待时长

最重要的原则：livenessProbe 绝对不要检查依赖（DB、下游服务）。如果 liveness 检查 DB，DB 抖动会导致所有 Pod 被判定不健康并重启，故障被放大甚至引发雪崩。依赖检查只能放在 readiness 里。

startupProbe 解决的是慢启动问题：Java 应用启动可能要 60 秒，如果只用 liveness（failureThreshold=3 × periodSeconds=10 = 30 秒），会在启动完成前就被杀掉。startupProbe 允许设置单独的、更宽松的阈值。

配置模板

apiVersion: v1
kind: Pod
spec:
  containers:
  - name: app
    image: myapp:1.0
    ports: [{containerPort: 8080}]

    # 1) 启动探针：给慢启动的应用足够时间
    startupProbe:
      httpGet: {path: /healthz, port: 8080}
      periodSeconds: 5
      failureThreshold: 30          # 30 × 5s = 最多等 150 秒启动
    # 启动成功后，kubelet 才切换到 liveness/readiness

    # 2) 存活探针：只检查进程是否活着，<b>不查依赖</b>
    livenessProbe:
      httpGet: {path: /healthz, port: 8080}
      initialDelaySeconds: 0        # 有 startupProbe 时可以设 0
      periodSeconds: 10
      timeoutSeconds: 1
      failureThreshold: 3           # 连续 3 次失败 -> 重启

    # 3) 就绪探针：检查依赖，决定是否摘流量
    readinessProbe:
      httpGet: {path: /readyz, port: 8080}
      periodSeconds: 5
      timeoutSeconds: 2
      failureThreshold: 2           # 连续 2 次失败 -> 从 endpoints 摘除
      successThreshold: 1           # 1 次成功即重新加入

    # 4) 生命周期钩子：优雅退出
    lifecycle:
      preStop:
        exec:
          command: ["/bin/sh", "-c", "sleep 5"]   # 等 endpoint 传播完成
  terminationGracePeriodSeconds: 45   # 必须 > preStop sleep + 应用退出时间
# 应用侧的探针实现（Go）
mux.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
    // liveness：只判断进程是否存活，不加任何依赖检查
    w.WriteHeader(200)
    w.Write([]byte("ok"))
})

mux.HandleFunc("/readyz", func(w http.ResponseWriter, r *http.Request) {
    // readiness：检查关键依赖
    ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)
    defer cancel()
    if err := db.PingContext(ctx); err != nil {
        http.Error(w, "db unavailable", 503)
        return
    }
    w.WriteHeader(200)
    w.Write([]byte("ready"))
})

排障清单

症状原因处理
Pod 反复重启（CrashLoopBackOff）liveness 太严格或启动慢加 startupProbe；调大 initialDelaySeconds/failureThreshold
滚动更新时 502Pod 被摘除前 endpoint 还没传播加 preStop sleep 5s；terminationGracePeriodSeconds 设够
依赖抖动导致全部重启liveness 检查了依赖依赖检查只在 readiness；liveness 只查进程
服务起来了但没流量readiness 一直失败看 kubectl describe 的探针失败原因；检查 /readyz 实现
探针本身消耗资源探测太频繁或检查太重readiness 的 periodSeconds 别小于 5；/readyz 要快（<100ms）
重启后数据丢失容器被强杀应用要处理 SIGTERM 做优雅退出；用 preStop 钩子
启动探针通过了但应用还没真就绪startupProbe 检查点太早startupProbe 也用 readiness 的端点；或增加检查项

preStop sleep 是必须的：kubelet 发送 SIGTERM 和 「从 endpoints 摘除」是并行发生的，摘除需要几秒才能传播到所有 kube-proxy。不加 sleep，Pod 已经开始关闭却还在接收流量，导致 502。这是滚动更新 502 的头号原因。

自检

下游数据库短暂变慢导致 readiness 失败，Kubernetes 会因此立即重启容器吗？

不会。readiness 主要影响是否接收新流量；是否重启由 liveness、进程退出等机制决定。
