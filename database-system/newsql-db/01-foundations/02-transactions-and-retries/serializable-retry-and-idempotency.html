分布式 SQL 可串行化重试：冲突、未知提交与幂等键

用两笔抢同一张优惠券的交易，区分事务冲突重试与网络超时后的结果确认。

先把两种失败分开

两位用户同时抢一张只剩 1 张的优惠券。事务 T1、T2 都先读到库存 1，再尝试把库存改成 0 并写入领取记录。若数据库承诺可串行化结果，不能让两笔都按“读到 1”成功提交；它必须让某笔等待、检测写冲突，或在提交时拒绝一笔并要求重试。被明确拒绝且回滚的事务可以从头重新读取；重新读取后它会看到库存 0，正常返回“已抢完”。这是并发控制中的事务重试。

另一种情况是客户端已发出 COMMIT，数据库可能成功写入提交决定，但响应在网络上丢失。客户端收到超时，无法单凭超时判断事务是否回滚。此时直接以新请求再次领取，可能重复插入或重复扣款。未知提交要先依据稳定业务键查询结果，再按数据库与业务约束决定是否重发。把“明确的序列化失败”和“提交结果未知”都当作同一种异常，会造成账务错误。

沿箭头逐步核对输入、变换和输出；下面的推演可以逐步切换。

手推一次冲突

起始库存 1，T1 和 T2 的读时间重叠。T1 写库存 0、写领取记录 A；T2 也企图写库存 0、写领取记录 B。如果二者都提交，最终库存虽然是 0，领取记录却有两条，数量不变量被破坏。数据库的可串行化机制应使结果等价于某个串行顺序：先 T1 后 T2，或先 T2 后 T1；后者重新读时只能看到 0。应用应把“读取库存、校验、扣减、插入领取记录”置于同一个受保护事务里。

有些数据库允许乐观并发：读时不加长锁，提交时验证冲突。另一些场景会通过行锁、时间戳或条件更新来控制。具体冲突码、自动重试策略和最大重试范围由产品及驱动决定，不能把某个厂商的错误码当成通用 SQL 规范。应用应区分可重试错误、约束冲突、业务拒绝和未知结果，并记录每类次数。

提交冲突

幂等键把“重发”绑定到同一业务意图

给每次领取生成唯一请求键 request_id，在受事务保护的表上对它建立唯一约束。第一次请求若已成功，后续带同一个键再来，应读取并返回第一次结果；第一次未成功则可继续执行。这一键必须代表同一业务意图，不能每次 HTTP 重试都生成新键。对支付、转账等操作，还要把请求参数摘要与键一起存储，防止同一键被误用于不同金额。

唯一键解决“同一请求重复执行”问题，但不自动保证所有业务不变量。库存检查仍需在正确隔离或原子条件更新下完成；仅在入口缓存中记住 request_id，进程重启就丢失，也不能抵御并发副本。若外部短信或支付 API 放在可重试事务闭包内，事务被重放时副作用可能执行两次。应让事务内只提交数据库状态，外部效果经持久化事件和幂等消费者处理。

现象可判定状态下一步
序列化失败并明确回滚未提交从头重试且有限退避
唯一键命中已有同一业务意图核对参数并返回原结果
COMMIT 应答丢失未知用 request_id 查状态
库存不足业务拒绝返回已抢完，不盲重试

重试边界和退避

显式序列化失败后，从事务最开始重试，不要只重放最后一条 UPDATE：先前 SELECT 的值已经可能失效。重试次数要有限，加入随机退避避免大量客户端在热点键上同步再次相撞。若每秒 1000 个请求都争同一行，重试只会放大冲突与排队；需要队列化、库存分片或更合适的业务限流。无条件无限重试可能让用户端一直等待，也会推高数据库负载。

事务提交后才应给用户“成功”结果；如果响应前连接断开，客户端用 request_id 查询已落库结果。查询暂时无记录并不总等于先前事务已失败：还要考虑未完成事务、异步可见性与查询副本延迟。可设计服务端查询状态接口，返回进行中、成功、失败，并对超时状态做最终核对。

可观测性与演练

记录 request_id、事务尝试次数、冲突原因、最终提交 ID、涉及分片数及外部效果 ID。业务监控分别统计冲突重试率、未知提交率、重复键命中率与库存负数等不变量。若只统计 HTTP 200，可能掩盖两次扣款后只返回一次成功。压测应故意让多个请求同时抢最后一张券，再在 COMMIT 响应前注入断线，核对领取记录恰好一条。

跨分片事务还可能因更多网络往返而扩大冲突窗口。优先按业务键布局相关数据，减少不必要的跨分片写入；但数据亲和不能替代事务与幂等设计。真正的验收标准是，在超时、重试和节点故障组合下，库存与领取记录仍满足“库存 + 已领取数量 = 初始数量”等约束。

容易混淆的结论

“可串行化”描述已提交事务的并发结果，不表示每笔都必然一次成功；应用通常仍要处理事务冲突。“幂等”描述重复提交同一业务请求的外部效果，不等于数据库自动识别两个不同 request_id 是同一意图。“超时”描述客户端没有及时收到答案，不等于服务端未执行。把这三句话放在同一张故障时间线上，才能写出正确重试流程。

各库的报错码与重试信号

数据库冲突/重试错误含义

CockroachDB40001（RETRY_SERIALIZABLE）可安全重试

TiDB（悲观事务）1213 Deadlock / 锁等待超时死锁需重试
MySQL/InnoDB1213 死锁、1205 锁等待超时需重试

重试铁律：只有明确标识为可重试的错误码才重试，且重试的整个事务必须重新执行（不能只重发最后一条语句），同时事务要幂等（否则重试会产生副作用）。

重试代码模板

重试模板

import time, random

RETRYABLE = {"40001", "9007", "1213", "1205", "RETRY_SERIALIZABLE", "SERIALIZATION_FAILURE"}

def run_txn(fn, max_retries=5):
    """fn 必须是完整事务闭包：重试时整体重跑，而不是补发最后一条语句。"""
    for attempt in range(max_retries):
        try:
            with db.transaction() as tx:
                result = fn(tx)          # 整个事务逻辑
            return result
        except DBError as e:
            if e.sqlstate not in RETRYABLE and e.code not in RETRYABLE:
                raise                     # 非可重试错误直接抛
            if attempt == max_retries - 1:
                raise
            # 指数退避 + 抖动，避免重试风暴
            time.sleep(min(0.05 * (2 ** attempt), 1.0) * (0.8 + 0.4 * random.random()))

# 5 次重试的等待上限约 0.05+0.1+0.2+0.4+0.8 = 1.55s（含抖动）

深入自检

Snapshot Isolation 为什么不能防止写偏斜？

因为 SI 下两个事务可以基于同一个快照各自读取、再写不同的对象，写写不冲突所以都能提交，但合起来破坏了一个跨对象的约束（例如两个医生同时请假导致无人值班）。Serializable（SSI 或 2PL）会检测这种读写依赖环并中止其中一个。

哪些错误可以安全重试？

明确标识为序列化失败/死锁/锁等待超时的错误（PostgreSQL 与 CRDB 的 40001、TiDB 的 9007、MySQL 的 1213 与 1205）。语法错误、约束违反、权限错误都不能靠重试解决。判断依据是错误码，而不是错误文本。

重试时为什么要重跑整个事务？

因为冲突意味着该事务读到的版本已失效，只补发最后一条语句会让前面的读与后面的写不一致，产生错误结果。正确做法是回滚后从头重跑整个事务逻辑，并配合幂等设计保证重复执行无副作用。

幂等和重试是什么关系？

幂等是重试安全的前提：若事务包含非幂等操作（如插入无唯一键的记录、发送外部消息），重试会产生重复副作用。因此重试必须与唯一键/条件更新/事务消息（Outbox）配合，让「执行 N 次」与「执行 1 次」结果相同。

如何降低序列化冲突的发生率？

四类：① 缩短事务（不在事务内做远程调用与大查询）；② 统一加锁顺序（避免死锁）；③ 拆分热点（单行计数器拆多行）；④ 合理选择隔离级别与显式锁（RC + FOR UPDATE 往往比全局 SERIALIZABLE 更可控）。同时保留退避重试作为兜底。

自检

客户端在 COMMIT 后超时，能否直接认定事务已经回滚并用新请求键再扣一次？

不能。提交决定可能已经持久化但应答丢失；先用原请求键查询并确认结果。
