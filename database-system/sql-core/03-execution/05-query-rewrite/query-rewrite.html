①改写的三条主线

SQL 是声明式语言：你只说要什么，不说怎么拿。这带来一个问题—— 同一语义有多种写法，优化器不一定能把「坏写法」都救回来。改写的目的就是把查询变回 优化器能看懂、能估算、能用索引的形态。

① 减少数据量

更早地过滤、更精确地投影（别 SELECT *）、 只查需要的分区。这是收益最高的一条——参与运算的行越少，后面所有算子都变快。

② 让谓词可 Sargable

裸列单独一侧、避免函数包裹、消除隐式转换、拆 OR 为 UNION ALL。 详见「过滤条件与索引可用性」。

③ 减少随机 IO 与排序

覆盖索引消回表、索引顺序对齐 ORDER BY/GROUP BY、延迟关联只回表少量行。

②六种高频改写手法

1. 延迟关联（Deferred Join）

深翻页时先只在索引上找出主键，再回表取完整行，把回表行数从 OFFSET+N 降到 N。

-- ❌ 先回表 100020 行再丢弃
SELECT * FROM orders WHERE status='paid' ORDER BY created_at DESC LIMIT 20 OFFSET 100000;

-- ✓ 覆盖索引里先定位 20 个 id
SELECT o.* FROM orders o
JOIN (SELECT id FROM orders WHERE status='paid'
      ORDER BY created_at DESC LIMIT 20 OFFSET 100000) t ON t.id = o.id;

2. OR 拆 UNION ALL

-- ❌ 跨列 OR，两个索引都用不上
SELECT * FROM t WHERE a = 1 OR b = 2;
-- ✓ 各走各的索引（注意补互斥条件或用主键去重）
SELECT * FROM t WHERE a = 1
UNION ALL
SELECT * FROM t WHERE b = 2 AND a <> 1;

3. 相关子查询 → JOIN / 窗口函数

-- ❌ orders 每行跑一次
SELECT o.id, (SELECT MAX(created_at) FROM logs l WHERE l.order_id=o.id) FROM orders o;
-- ✓ 先聚合再关联
SELECT o.id, l.last_at FROM orders o
LEFT JOIN (SELECT order_id, MAX(created_at) last_at FROM logs GROUP BY order_id) l
       ON l.order_id = o.id;

4. 分页：OFFSET → 键集

-- ❌ 越翻越慢
SELECT * FROM t ORDER BY id LIMIT 20 OFFSET 100000;
-- ✓ 记住上一页的游标位置
SELECT * FROM t WHERE id > ?last_id ORDER BY id LIMIT 20;

5. COUNT 优化：大表精确计数走汇总表

-- 维护计数表，写入侧 +1/-1，读取侧 O(1)
UPDATE daily_stat SET cnt = cnt + 1 WHERE dt = CURDATE() AND biz = 'order';
SELECT cnt FROM daily_stat WHERE dt = ? AND biz = 'order';

6. 批量代替循环

-- ❌ 应用层循环 1000 次单条插入（1000 次网络往返 + 1000 次事务）
-- ✓ 一次多行插入 / 批量接口
INSERT INTO t (a,b) VALUES (1,2),(3,4),(5,6), ...;
-- 更新多条不同值：用 CASE 或 JOIN 临时表，不要 1000 条 UPDATE

③反向清单：这些改写往往没用

流传的说法实际情况
COUNT(1) 比 COUNT(*) 快无差别，优化器等价处理
SELECT * 一定慢影响在网络传输与覆盖索引上。列不多、都要用时无差别； 但会让覆盖索引失效、表结构变更时结果不稳，仍建议显式列
子查询一定比 JOIN 慢现代优化器会去关联化，多数情况计划相同
IN 比 EXISTS 慢同上，看计划而非写法
大写关键字更快无依据，纯风格问题
ORDER BY 用主键更快取决于能否用索引避开排序，与「主键」本身无关
加索引总能变快索引有写放大与空间成本，且优化器可能因选择率放弃它
改写的唯一验证标准是执行计划 + 实际耗时，不是写法好不好看。 每次改写前后都测一遍，并且用真实数据分布的数据量测—— 在 1000 行的测试库上跑出来的结论，到 1000 万行的生产上经常反过来。

④一套可重复的调优流程

  1. 拿到慢 SQL 与实际参数（参数不同可能走完全不同的计划，这就是参数嗅探问题）。
  2. 跑 EXPLAIN ANALYZE，记录每个算子的预估/实际行数与耗时。
  3. 找最大耗时算子，先解决它——优化要抓主要矛盾，不要一上来就调参数。
  4. 判断属于哪一类问题：扫描方式 / JOIN 顺序 / 排序落盘 / 估算失真 / 回表过多。
  5. 按前面章节的手法改写或补索引，一次只改一处。
  6. 复测，确认实际耗时下降且没有引入新问题（如写放大、锁范围变大）。
  7. 回归验证边界：空结果、极大结果、并发下的表现。
Q：什么时候该放弃优化 SQL，改架构？
A：当单条 SQL 已经是最优计划，但数据量本身决定了它必然慢—— 比如亿级表上按多个维度自由组合聚合。这时方向是：预聚合（汇总表/物化视图）、 列存（ClickHouse/Doris 类）、读写分离、或把这类查询迁到分析型系统。 认清「这是 OLAP 需求」比继续调 OLTP 库的 SQL 更有效。
