推理服务指标与成本

TTFT / TPOT / E2E / 吞吐四个指标的区别、并发拐点为什么决定了 SLO、按 token 拆的成本公式，以及四层观测清单。

四个必须区分的指标

TTFT 首 token 延迟
用户发完到看到第一个字。由 prefill + 排队 决定
TPOT 每 token 间隔
决定"出字快慢"。由 decode 效率 决定
E2E 延迟
TTFT + TPOT × 输出长度。用户真正感知的 waiting time
吞吐
tokens/s（总）或 req/s。服务端成本的核心指标
只报"平均延迟"一定会误判。长输出请求的 E2E 天然更长， 平均值会把短请求的好表现和长请求的坏表现混在一起。 按输入/输出长度分桶统计，并关注 P95/P99 而非均值。

吞吐与延迟的取舍曲线

拐点之后再加并发，吞吐几乎不涨而延迟陡升——因为瓶颈从"GPU 算不过来"变成"请求排队等不到"。 生产上应当把并发限制在拐点左侧，超出部分用排队或拒绝，而不是硬塞进去。

成本模型

单次请求成本 ≈ GPU 时薪 ÷ 该 GPU 一小时能处理的请求数

更可控的拆法：
  成本/1K tokens = (GPU 时薪 / 3600) ÷ (吞吐 tokens/s) × 1000

例：时薪 ¥20 的卡，实测吞吐 2000 tokens/s
  每 1K tokens 成本 ≈ (20/3600) ÷ 2000 × 1000 ≈ ¥0.0028
  一条 500 输入 + 1500 输出的请求 ≈ ¥0.0056
提高吞吐
连续批处理、量化、投机解码、更好的算子
减少 token
缩短 prompt、限制输出长度、缓存命中复用、路由到小模型
提高利用率
削峰填谷、错峰批处理、按负载自动扩缩容
容易被忽略的一项：空闲成本。按请求计费的 serverless 推理在低负载时便宜， 高负载时贵；自建常驻实例则相反——只要有卡在跑就在花钱，哪怕 QPS 是 0。 选型前先看你的流量曲线是否平稳。

上线前的观测清单

层要看到什么
请求层QPS、排队时长、拒绝率、按输入/输出长度分桶的 P50/P95/P99
引擎层运行中请求数、等待队列长度、KV Cache 使用率、prefix cache 命中率
GPU 层利用率、显存占用、是否出现 OOM 与显存碎片告警

链路追踪要带上模型参数。同样一条慢请求， 可能是 prompt 长、输出长、温度高、走了 fallback 大模型、或是命中了未缓存的前缀。 没有这些标签，事后根本无法归因。

四个指标，别只盯吞吐

大模型推理的性能不是一个数，而是四个互相制约的指标：TTFT（首 token 时延）、TPOT（每 token 时延）、总延迟、吞吐。批处理能抬高吞吐，但会拖长 TTFT；缩短 TTFT 常要牺牲并发。做容量规划时必须先明确业务对哪一个最敏感。

TTFT首 token 时延，由排队 + Prefill 主导，决定「多久开始出字」
TPOT / ITL每个输出 token 的间隔，决定「出字流畅度」
E2E 延迟≈ TTFT + TPOT × 输出长度
吞吐单位时间处理的 token 数，分输入吞吐与输出吞吐
并发同时处理的请求数，是吞吐与延迟的杠杆
Goodput满足 SLO 的有效吞吐，比裸吞吐更有意义
Prefill 决定 TTFT，Decode 决定 TPOT，两者优化手段不同

成本公式直觉：成本 ≈ （输入 token × 单价_in + 输出 token × 单价_out）× 调用量。输出 token 通常比输入贵数倍，所以「让模型说短一点」往往是最直接的成本优化。

成本治理的实操清单

① 先把账算清楚

  • 按接口/业务线统计：调用量、平均输入输出 token、GPU 时长。
  • 算出「单次调用成本」与「单位业务价值成本」，否则优化无从下手。
  • 区分在线推理与离线批处理：后者可用闲置算力，成本低很多。

② 模型分级路由

  • 简单任务走小模型，复杂任务才走大模型（分类器或规则做路由）。
  • 典型收益：60-80% 请求由小模型承接，总成本降一半以上。
  • 必须做质量兜底：小模型置信度低时升级到大模型。

③ 缓存与复用

  • 精确缓存：相同请求直接命中。
  • 语义缓存：相似问题复用答案（需谨慎，避免答非所问）。
  • Prefix caching：长系统提示词只算一次。
  • 多轮对话复用历史 KV。

④ Prompt 与输出控制

  • 精简系统提示：只保留必要指令与示例。
  • RAG 只送必要片段，别整篇塞。
  • 明确要求简洁输出，必要时限制 max_tokens。
  • 结构化输出比自然语言的废话更省 token。

⑤ 部署层优化

  • 连续批处理 + PagedAttention（vLLM 类框架默认）。
  • 量化：FP8/INT8 在多数场景损失很小。
  • 投机解码：对 TPOT 敏感场景收益明显。
  • 自动扩缩容与错峰：离线任务放低峰。

⑥ 观测与治理

  • 监控 P50/P95/P99 而非均值。
  • 按业务线做成本看板与配额，超限告警。
  • 灰度对比：优化前后同时跑，看质量指标是否下滑。
  • 定期复盘：模型换代与价格变动会重塑最优方案。

深入自检

吞吐高就代表体验好吗？

不一定。吞吐是系统视角的效率，用户感受到的是 TTFT 与 TPOT。若为了堆吞吐把 batch 做得很大，TTFT 会显著变长，用户会觉得「点了半天没反应」。所以更合理的指标是 Goodput：在满足延迟 SLO 前提下的吞吐。

TTFT 和 TPOT 哪个更重要？

取决于场景。对话与实时助手更看重 TTFT（尽快开始出字）；长文生成、批量转写更看重 TPOT 与总吞吐。流式展示的产品尤其要压 TTFT，因为用户对「空白等待」最敏感。

为什么加了批处理延迟反而变高？

因为批处理要等待凑够一批，这段等待直接加到 TTFT 上；同时大 batch 的单步解码更慢，TPOT 也会上升。解决方法是连续批处理（请求可随时加入/离开，不必等整批结束），而不是静态批处理。

KV Cache 为什么会成为瓶颈？

KV Cache 随「并发数 × 上下文长度」线性增长，长对话场景下很快吃满显存，导致能承载的并发骤降。这也是 PagedAttention、KV 量化、KV 卸载等技术出现的原因。容量规划时必须按最长上下文估算，而不是平均值。

如何估算一套部署的成本？

按「目标 QPS × 平均输出 token 数」反推所需 GPU 数：先实测单卡在不同并发下的输出 token/s（Goodput），再用峰值 QPS 除以它得到卡数，最后加 30-50% 余量。别忘了把排队导致的 SLO 违约算进去，别只用平均吞吐估。

量化会不会影响效果？怎么评估？

FP8 通常几乎无损；INT8 在多数任务上损失 1-2 个点，但极端任务（数学、长文推理）可能更明显。评估方法：用业务验证集（而非通用基准）对比量化前后，重点看关键任务的准确率与格式稳定性，并关注尾部分布的退化。
