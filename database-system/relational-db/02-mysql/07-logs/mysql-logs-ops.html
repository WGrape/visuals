MySQL 三日志运维：redo / undo / binlog 怎么看怎么调

从观测命令到关键参数，把崩溃恢复与复制可靠性落到可执行的操作上。

MySQLredobinlogundo运维
Redo Binlog Undo 对照 恢复
MySQL 的可靠性靠 redo / undo / binlog 三件套。理解它们各自干嘛、怎么观测和调参，才能既不出事又能跑得快。

01Redo Log：崩溃恢复的主心骨

InnoDB 把修改先写 redo（物理日志），再异步刷数据页。redo 是环形的，写满会触发 checkpoint 把脏页刷盘。redo 太小会频繁刷盘拖慢写入。

-- 查看 redo 配置与 checkpoint 进度
SHOW VARIABLES LIKE 'innodb_log_file_size';     -- 单文件大小，总 = size * files
SHOW VARIABLES LIKE 'innodb_log_files_in_group';
SHOW ENGINE INNODB STATUS\G                      -- 看 LOG 段：Log sequence / Log flushed / Last checkpoint
-- 经验值：redo 总大小设到能容纳约 1 小时峰值写入；不够则 checkpoint 追不上

-- 调大需在停服下改（5.7 需先改 my.cnf 再重启；8.0 支持 ALTER 在线扩容）
-- innodb_log_file_size = 1G

02Binlog：主从复制与时间点恢复

binlog 是逻辑日志，用于复制和 PITR。格式选 ROW 最安全（记录行变更），STATEMENT 有不确定性风险。sync_binlog=1 才保证每事务刷盘。

SHOW VARIABLES LIKE 'binlog_format';     -- 推荐 ROW
SHOW VARIABLES LIKE 'sync_binlog';      -- 1=每事务刷盘；0=交给 OS
SHOW VARIABLES LIKE 'expire_logs_days'; -- 保留天数，到期自动 purge

-- 看当前 binlog 位点与文件
SHOW BINARY LOG STATUS;                 -- 8.4+（旧版 SHOW MASTER STATUS）
SHOW BINLOG EVENTS IN 'mysql-bin.000012' LIMIT 10;
-- 手动清理（谨慎）：PURGE BINARY LOGS BEFORE '2026-10-01 00:00:00';

03Undo Log：回滚与 MVCC

undo 记录「修改前的值」，支撑回滚和快照读。长事务会阻止 undo 复用，导致 undo 表空间膨胀。MySQL 8.0 可在线 truncate。

-- 查 undo 占用
SELECT tablespace_name, file_size/1024/1024 AS mb
FROM information_schema.files
WHERE file_type='UNDO LOG';
-- 8.0 开启自动 truncate
SET GLOBAL innodb_undo_log_truncate=ON;
SET GLOBAL innodb_max_undo_log_size=1073741824;   -- 超过 1G 触发截断

04三日志对照

日志类型作用调优要点
redo物理(页修改)崩溃恢复、保证持久log_file_size 够大
undo逻辑(前像)回滚、MVCC 快照防长事务、可 truncate
binlog逻辑(行/语句)复制、PITRformat=ROW, sync=1

05崩溃恢复与排障

  • 正常重启 InnoDB 自动 redo 前滚 + undo 回滚，无需人工介入。
  • 起不来的极端情况才用 innodb_force_recovery=1..6（只读救数据），事后立即导出重建，绝不该长期运行。
  • 主从不一致：先查 binlog 位点是否连续、是否有非确定性函数。
要点：redo 保你「库能起来且数据不丢」，binlog 保你「能从从库/备份点恢复」。两者 sync 都设 1 是最稳但最慢，按业务容忍度下调。

第一层 · 概念与判定：五种日志各管什么

MySQL 核心日志：错误日志（启停/报错）、慢查询日志（定位慢 SQL）、binlog（主从/恢复/审计）、redo（崩溃恢复）、undo（回滚）。排查先选对日志。

要干什么看哪个日志
实例起不来/报错error log最直接
哪条 SQL 慢slow query log配阈值
主从不一致/误删恢复binlog按位点/时间
崩溃后数据丢失否redo / undo自动

第二层 · 参数·命令·量化：关键开关

参数建议值作用

MySQL 慢日志与 binlog 运维

-- 在线开启慢日志，不必重启
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 0.5;          -- 秒
SET GLOBAL log_queries_not_using_indexes = ON;

-- 看慢日志内容
mysqldumpslow -s t /var/log/mysql/slow.log | head
pt-query-digest /var/log/mysql/slow.log     # Percona 更细

-- binlog 按时间恢复示例
mysqlbinlog --start-datetime='2026-01-01 00:00:00' \
            --stop-datetime='2026-01-01 01:00:00' \
            mysql-bin.000123 | mysql -u root -p

数量级：long_query_time 设 0.5s 通常合适；全表扫日志开 ON 后量很大，只适合临时排查，长期开会拖慢且占盘；binlog 保留 7–14 天兼顾恢复与容量。

第三层 · 排障与边界：四个坑

  • 慢日志压根没开：默认 OFF，线上「慢」却无任何记录——先确认 slow_query_log=ON 再谈优化
  • binlog 爆盘：expire_logs_days 没设或设太大，磁盘写满实例挂——定时清理 + 监控剩余空间
  • long_query_time 设太大：设 10s 只抓极慢，大量 1–2s 的「温水煮青蛙」SQL 全漏掉
  • log_queries_not_using_indexes 长期开：全表扫日志海量，既拖性能又淹没有用信息——排查完即关

第四层 · 原理与取舍

binlog 和 redo log 到底有什么区别？

binlog 是服务层、逻辑级的追加日志，记录「做了什么改动」，用于主从复制和点位恢复，所有引擎共用；redo log 是InnoDB 层、物理级的循环日志，记录「页怎么改」，用于崩溃后把已提交事务刷回磁盘（WAL）。两者职责不同：redo 保持久性、binlog 保复制与恢复。两阶段提交正是为了让他俩一致。

为什么慢查询日志是定位慢 SQL 的首选？

因为它直接给出执行时间、锁等待、扫描行数、是否用索引，比自己猜执行计划快得多，且能配合 mysqldumpslow/pt-query-digest 聚合出『最该优化的 Top N』。配合 log_queries_not_using_indexes 还能抓出全表扫的隐性慢 SQL。是性能排查的入口。

为什么 binlog_format 推荐 ROW 而不是 STATEMENT？

STATEMENT 记录 SQL 文本，遇到 now()/uuid()/触发器 主从可能不一致；ROW 记录每行实际变更，主从绝对安全、还能做行级恢复，代价是日志量更大（尤其大批量更新）。在数据一致性优先的今天，ROW 是默认且推荐的选择。
