超标量与乱序执行：IPC 是怎么从 1 走到 4 的

流水线让一条指令一个周期「流出」，但它仍受依赖链限制：下一条要用上一条的结果，就得等。超标量一次发射多条，乱序执行让后面的指令先跑——两者叠加，才有了现代 CPU 的 3~5 IPC。

一句话定位：宽度 × 乱序 = IPC

超标量（superscalar）解决「一个周期发几条」；乱序（out-of-order）解决「发的顺序能不能变」。前者要复制执行单元，后者要一整套记分牌/重命名/ROB 来保证「执行乱序、结果有序」。

发射宽度4~8 条/周期（Apple M 系 8 宽，x86 大核 6 宽）
ROB 深度x86 大核 300~600 项，决定能「看多远」
乱序窗口ROB 满则前端停顿，这是最常见的瓶颈
IPC 上限受宽度、依赖链、缓存、分支共同限制
三段式：按序前端 → 乱序后端 → 按序提交

三种依赖，只有一种是真的

依赖类型例子能否并行解决手段
RAW（真依赖）a = b + 1; c = a * 2不能，必须等只能靠提高并行度或改算法
WAR（反依赖）a = b + 1; b = c * 2可以（用不同物理寄存器）寄存器重命名
WAW（输出依赖）a = b + 1; a = c * 2可以（保留最后一次写）寄存器重命名
内存依赖store [p]; load [q]若地址可能别名则不能存储缓冲 + 内存消歧

寄存器重命名是乱序执行的地基：体系结构上只有 16/32 个寄存器，物理上可以有 200+ 个。重命名把「同一个寄存器名」映射到不同物理寄存器，WAR/WAW 立刻消失，只剩真依赖。

IPC 的天花板在哪

限制因素典型数值影响
发射宽度4~8IPC 不可能超过它
依赖链长度由算法决定链式求和 IPC ≈ 1/L（L 为加法延迟）
分支误预测率5% 左右每次误预测清空前端 15~20 周期
L1 缺失率1%~5%每次 miss 停顿 10~40 周期
ROB 容量300~600窗口外的指令无法提前执行
乱序不是免费午餐

为了「看得更远」，CPU 要维护重命名表、ROB、保留站、load/store 队列，这些都是大块 SRAM 与比较电路，功耗占比可达核心的 20%~30%。这也是为什么移动端更偏向「窄而深」的顺序核心（能效优先）。

代码层面能做什么

排障：为什么 IPC 上不去

现象最可能原因验证
IPC < 1 且 cache miss 高内存墙perf stat 看 LLC-miss、stalls
IPC 波动大分支误预测（数据相关分支）看 branch-misses 占比
单线程快、多线程不涨共享缓存/带宽打满对比单核与多核的带宽曲线
加了 SIMD 反而慢降频或数据未对齐看频率与 alignment
循环向量化失败别名假设（编译器不敢并行）加 restrict 或 -fno-alias

原理与取舍：为什么移动端不追大乱序

乱序窗口每扩大一倍，IPC 提升不到 10%，但面积与功耗接近翻倍。手机的热预算只有几瓦，于是走「宽而浅 + 大小核」路线：大核短时间冲刺，小核顺序执行保能效。服务器则相反，功耗不是首要约束，用大 ROB、深流水换单线程性能。

乱序执行会不会破坏程序语义？

不会。它保证「按程序顺序提交」，异常、中断、内存可见性都在提交点按序处理，所以外部观察到的行为与顺序执行一致（除了 Spectre 这类侧信道）。

超标量和多发射是一回事吗？

基本同义：一个周期发射多条指令。配套还需要多端口寄存器堆、多个执行单元、足够宽的取指与译码。

SMT（超线程）和乱序什么关系？

SMT 让两个线程共享一个物理核的乱序资源，靠「一个线程等内存时另一个线程填坑」提高利用率。它不增加执行单元，只提高占用率。

怎么量：用 perf 把 IPC 和瓶颈量出来

乱序执行的一切优化都要先用数据确认瓶颈在哪。Linux 下 perf 是唯一不需要改代码就能拿到IPC、分支预测失败率、访存停顿的手段，几条命令就能定位到「前端 / 后端 / 访存 / 分支」中的哪一类。

perf：从 IPC 到瓶颈分类

# 最核心的一条：拿到 IPC（每周期指令数）
perf stat -e instructions,cycles,cache-misses,branch-misses ./app
# 输出里的 insn per cycle 就是 IPC：
#   < 1.0  流水线在挨饿，多半是访存或分支
#   1.0~2.0 普通乱序核的常见区间
#   > 3.0  说明代码对流水线很友好（循环展开充分、命中缓存）

# Top-down 分析（Intel 机器）：直接给出四大类瓶颈占比
perf stat --topdown -a -- taskset -c 0 ./app
#   Frontend Bound 高 -> 取指/译码跟不上（指令太多、分支太多）
#   Backend Bound   高 -> 执行单元或访存跟不上（依赖链、缓存未命中）
#   Bad Speculation 高 -> 分支预测失败
#   Retiring        高 -> 真正干活的，越高越好（理想 70%+）

# 精确到函数与代码行
perf record -F 99 -g --call-graph dwarf -e cycles:pp ./app
perf report --sort=overhead,symbol -g folded

# 只看某一段循环（需要代码里埋 marker，或用 perf_event_open）
指标怎么看健康区间不健康时的第一动作
IPC（instructions/cycle）perf stat 的 insn per cycle1.0 ~ 2.5低于 1 先看 cache-misses 与 branch-misses
branch-miss 率branch-misses / branches< 1%超过 2% 用查表或 CMOV 去掉不可预测分支
cache-miss 率cache-misses / cache-references< 5%改数据布局（SoA / 结构体拆分）或加 prefetch
Retiring 占比perf stat --topdown> 50%低于 30% 说明大量周期花在等待与投机失败
LLC miss 率perf stat -e LLC-load-misses越低越好超过 L2 命中就掉到内存，延迟从 ~14 周期涨到 ~200+ 周期

乱序窗口的容量决定了「能提前看多远」，这是硬件给的上限。不同微架构差异很大，下面只给量级：

结构典型容量（量级）决定了什么代码能影响的程度
发射宽度4 ~ 8 条/周期单周期最多能并行几条指令低（靠编译器调度）
ROB（重排序缓冲）200 ~ 600 项能提前执行多少条指令中（缩短依赖链让它装得更多）
物理寄存器堆180 ~ 400 个重命名能消除多少假依赖低
LSQ（访存队列）几十项允许多少个未完成的访存中（减少不必要的 load/store）
分支预测器 / BTB数千 ~ 数万项循环中能预测多准高（减少分支数量、让分支有规律）
store buffer数十项写能否提前完成中（减少写、避免 store-forwarding 停顿）

这些数字随微架构逐年变化，不要背具体值；只要知道量级，剩下的用 perf 在自己机器上量。

代码层面能做什么 + 排障清单

乱序执行能自动隐藏的是独立的慢操作；它隐藏不了依赖链和预测失败。所以所有优化归根到底是两件事：砍依赖、砍分支、砍访存。

四种典型改法

// 1) 累加拆成 4 路：把一条依赖链拆成 4 条，让乱序核有活可干
//    单路每周期只能做 1 次加（延迟 4 周期则 IPC 上限 0.25），4 路理论 4 倍
double s0=0, s1=0, s2=0, s3=0;
for (size_t i = 0; i + 3 < n; i += 4) {
    s0 += a[i+0];  s1 += a[i+1];  s2 += a[i+2];  s3 += a[i+3];
}
double sum = (s0 + s1) + (s2 + s3);   // 注意：改变了浮点加法顺序，误差略有变化

// 2) 用 xor 清零打断「假依赖」：编译器会把 xor eax,eax 识别为与旧值无关
__asm__ volatile("xor %eax, %eax");   // 或写 int x = 0; 让编译器自己选断点

// 3) 结构体按 64 字节对齐，避免跨 cache line
struct alignas(64) Counter { int64_t v; };

// 4) 数据布局从 AoS 改 SoA：只遍历一个字段时缓存命中率显著提升
写法的代价典型周期量级说明
L1 命中约 4~5 周期最理想，编译器会尽量让热数据留在这
L2 命中约 12~14 周期仍可接受
L3 命中约 40~50 周期开始明显拖慢
主存访问约 200~300 周期等于几十条指令白跑，乱序窗口会被迅速填满
分支预测失败约 15~20 周期还要清空流水线，代价远高于普通指令
store-to-load 转发停顿约 10~15 周期刚写又读同一地址时触发，尽量避免
错误共享（false sharing）每次写数百周期两个核反复抢同一 cache line

IPC 上不去时按这个顺序排查：

  • 先量再改：跑 perf stat 拿 IPC 与 miss 率，没有基线的一切优化都是猜。
  • IPC < 1：十有八九是访存或分支，先查 cache-misses 与 branch-misses，别急着改逻辑。
  • 长依赖链（如串行累加、指针追逐）是乱序的死穴，优先拆链而不是微调指令。
  • 不可预测分支改成查表或 CMOV，收益通常比循环展开大。
  • 循环展开 4~8 次即可，再往上收益递减，还会挤爆指令缓存。
  • 减少 store：写比读贵，且容易触发 store-forwarding 停顿与伪共享。
  • 热数据按 64 字节对齐并按核分片，避免跨行与伪共享。
  • perf report 看的是采样热点，热点函数里占比最高的往往是等待指令，不是计算指令。
  • 改完必须重测：编译器可能已经做了你想做的事，手工优化反而打乱它的调度。
