①参数地图：建索引参数 vs 查询参数

Milvus 的索引参数分两类：建索引参数在建索引时确定、改了要重建；查询参数每次 search 可以临时覆盖、不动索引。搞清楚哪些能在线调，才不会为了调一个 ef 去重建索引。

口诀：建索引参数决定“索引长什么样”，查询参数决定“扫多深”。线上做召回/延迟权衡时，优先调查询参数。

②IVF 家族：nlist 与 nprobe

nlist：把空间切成多少个桶

官方经验公式 nlist = 4 × sqrt(N)，注意 N 是单个 Segment 内的实体数，不是全表行数。段被切成很多小段时，按整表算出来的 nlist 会严重偏大。

# 单段约 100 万条 → nlist ≈ 4 × 1000 = 4000
index_params.add_index(field_name="embedding", index_type="IVF_FLAT",
                       metric_type="COSINE", params={"nlist": 4096})

nprobe：每次扫多少个桶

nprobe 是召回与延迟的主旋钮：值越大扫得越多、召回越高、越慢。经验起点 nprobe = 16 或 32，上限不超过 nlist。

正确做法：先定召回目标（如 95%），再从 nprobe=1 起二分/线性扫描，找到达标的最小 nprobe，而不是拍脑袋取个值。

③HNSW：M / efConstruction / ef

M（建）

每个节点的邻居数，常见 8–64，默认 16 左右。M 越大图越密、召回越高，内存与建索引时间随之上升。

efConstruction（建）

建图时的候选队列长度，常见 200–500。越大图质量越好、建得越慢。它不影响查询速度，只影响索引质量。

ef（查）

查询时的候选队列长度，必须 ≥ top_k。这是 HNSW 的召回/延迟旋钮，等价于 IVF 的 nprobe。

index_params.add_index(field_name="embedding", index_type="HNSW",
                       metric_type="COSINE",
                       params={"M": 16, "efConstruction": 200})
# 查询时在线调 ef，不必重建索引
res = client.search(collection_name="docs", data=[query_vec], limit=10,
                    search_params={"metric_type": "COSINE",
                                   "params": {"ef": 128}})

内存估算

HNSW 的内存 ≈ (dim × 4 + M × 2 × 4) × N 字节（每层图边 + 原始向量），另加元数据与 ID 开销。以 1000 万条 768 维、M=16 为例：约 (3072 + 128) × 1e7 ≈ 32 GB，比原始向量大约多 4%。注意实际还要叠加标量字段与缓存。

HNSW 没有“省内存”的版本时非常吃内存，且数据必须常驻 QueryNode。内存不够就换 HNSW_SQ/HNSW_PQ，或改用 IVF 系列。

④量化参数：m 与 nbits

PQ 把 dim 维切成 m 段、每段用一个码本索引表示，每段用 nbits 位存码本编号。因此 m 必须能被 dim 整除。

  • 压缩比 ≈ (m × nbits / 8) / (dim × 4)。例：dim=768、m=96、nbits=8 → 96 字节 / 3072 字节 ≈ 1/32。
  • m 越大分段越细 → 压缩比越低、召回越高；nbits 越大码本越精细 → 内存越大、召回越高。
  • SCANN 的 reorder_k 会保留原始向量对候选做精排，用少量内存换回明显召回。
量化带来的是有损压缩。若业务对 top-1 的准确性极其敏感（如精确查重），不要上 PQ；若只是 RAG 召回后还有 rerank/LLM 兜底，PQ 的损失通常可接受。

⑤怎么测召回：以 FLAT 为 ground truth

  1. 同一批数据建两个 Collection：A 用 FLAT（作为标准答案）、B 用待评估索引。
  2. 准备一批真实查询向量（≥ 200 条，最好来自线上分布，不要用随机向量）。
  3. 两边都用 limit=K 检索，逐条比对 ID 集合： 
    recall@K = |top_K(ann) ∩ top_K(flat)| / K
    再对所有查询取平均。
  4. 固定召回目标（如 0.95），从小到大扫 ef/nprobe，记录每个点的 P99 延迟，画出上文的拐点曲线。
  5. 取“刚好达标”的参数上线，并留出 20% 余量应对数据增长。
两个高频错误：① 用随机向量做查询集——分布和真实 Embedding 完全不同，测出来的召回没有意义；② 只测一次冷查询——忽略了缓存预热，结果不可复现。

⑥段结构与索引：为什么小段会拖垮检索

Milvus 对每个 Segment 独立建索引，一次查询要在所有相关段上各搜一遍再归并：

  • 段太小 → 每段索引建得没意义（比如 1000 条数据也建 HNSW），且查询要遍历很多段，固定开销被放大。
  • 段太大 → 建索引耗时长、单次 compaction 压力大，且 growing 段转 sealed 的延迟变高。
  • 目标：让 sealed 段落在“索引收益最大”的区间（常见为百 MB 量级），靠 compaction 把碎段合并上去。
如果你发现“数据量没涨多少，但查询变慢了”，第一嫌疑就是小段数量暴涨。查看 Segment 数量与平均大小，必要时手动触发 compaction 并调整批次大小。
