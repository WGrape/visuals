tsvector / tsquery、GIN 索引、权重与排名，以及中文分词。

① 全文检索的核心概念

PG 内置全文检索（FTS），无需额外组件即可做中文/英文的关键词搜索。核心是两件事：把文本变成 tsvector（词向量）、把查询变成 tsquery（查询表达式），再用 @@ 匹配。

-- to_tsvector：文本 → 词向量（分词 + 归一化 + 去停用词）
SELECT to_tsvector('english', 'The quick brown foxes are jumping');
-- 'brown':3 'fox':4 'jump':6 'quick':2   ← 复数归一、停用词去除、带位置

-- to_tsquery：查询 → 表达式
SELECT to_tsquery('english', 'quick & fox');    -- AND
SELECT to_tsquery('english', 'quick | fox');    -- OR
SELECT to_tsquery('english', 'quick & !fox');   -- NOT
SELECT phraseto_tsquery('english', 'quick brown');  -- 短语（相邻）

-- 匹配
SELECT * FROM docs
WHERE to_tsvector('english', body) @@ to_tsquery('english', 'quick & fox');

document

原始文本（通常多列拼接）

tsvector

词位（lexeme）+ 位置的有序集合，存进索引的对象

tsquery

查询表达式，支持 &（与）、|（或）、!（非）、<->（相邻）

配置 config

决定分词器与词典：english、simple、中文需 zhparser 等

② 建索引与查询

关键：预先把 tsvector 存成生成列，再对列建 GIN 索引——避免每次查询都重新分词。

-- 推荐做法：生成列 + GIN 索引
ALTER TABLE docs
  ADD COLUMN search_vec tsvector
  GENERATED ALWAYS AS (
    setweight(to_tsvector('english', coalesce(title, '')), 'A') ||
    setweight(to_tsvector('english', coalesce(body, '')),  'B')
  ) STORED;

CREATE INDEX idx_docs_search ON docs USING gin (search_vec);

-- 查询（必须与原表达式一致才能命中索引）
SELECT id, title,
       ts_rank(search_vec, q) AS rank
FROM docs, to_tsquery('english', 'postgres & index') q
WHERE search_vec @@ q
ORDER BY rank DESC LIMIT 20;
索引类型特点适用
GIN倒排索引，查询快，更新较慢，体积较大默认选择（读多写少）
GiST签名索引，更新快，有假阳性需回表过滤，体积小写入频繁的场景
RUM（扩展）支持短语与排序加速，最灵活需要高性能排序的场景
setweight 的作用：给不同字段设置权重（A > B > C > D），让 ts_rank 在排序时标题命中比正文命中更靠前——这对搜索体验影响很大。

③ 中文全文检索

PG 内置配置不支持中文分词（simple 会按标点/空格切，中文整句成一个词）。常用方案：

方案做法特点
zhparser + pg_jieba基于 SCWS/jieba 的中文解析器扩展需编译安装扩展，效果较好
simple 配置 + 二元切分把中文切成两字词（bigram）无需扩展，索引大、召回粗糙
pg_trgm三元组匹配，支持 LIKE '%x%' 走索引适合模糊包含而非真正分词
外部搜索引擎Elasticsearch / OpenSearch功能最全：分词、高亮、聚合、相关性调优
-- pg_trgm 方案（无需中文分词器，适合「子串包含」）
CREATE EXTENSION pg_trgm;
CREATE INDEX idx_name_trgm ON users USING gin (name gin_trgm_ops);
SELECT * FROM users WHERE name ILIKE '%张三%';    -- 走索引

-- 相似度排序
SELECT name, similarity(name, '张三') AS s
FROM users WHERE name % '张三' ORDER BY s DESC LIMIT 10;
选型建议：① 中文搜索是核心功能（电商、内容平台）→ 用 Elasticsearch/OpenSearch；② 只是站内简单搜索且数据量不大 → PG 内置 FTS + zhparser 足够；③ 只是模糊匹配姓名/编号 → pg_trgm 最省事。引入 ES 的代价是数据同步与运维复杂度，不要为了「搜索」过早引入。

④ 排序与高亮

-- ts_rank / ts_rank_cd（后者考虑词距，更贴近相关性）
SELECT id, title,
       ts_rank_cd(search_vec, q, 32 /* rank_cd 的 normalization */) AS rank
FROM docs, to_tsquery('english', 'postgres & index') q
WHERE search_vec @@ q
ORDER BY rank DESC;

-- 高亮（ts_headline）
SELECT ts_headline('english', body, q,
         'StartSel=<mark>, StopSel=</mark>, MaxFragments=2, MinWords=10, MaxWords=30') AS snippet
FROM docs, to_tsquery('english', 'postgres & index') q
WHERE search_vec @@ q;

ts_rank

按词频与权重打分，简单快速

ts_rank_cd

加入词距（cover density），相邻词命中得分更高

normalization 参数

0（忽略长度）/ 1（按文档长度对数归一）/ 2（按词频归一）/ 32（按唯一词数归一）

ts_headline

生成高亮摘要，可指定片段数与标记

⑤ 常见问法

Q：PG 的全文检索够用吗？什么时候该引入 Elasticsearch？

A：够用的场景：站内搜索、后台管理检索、数据量在百万级以内、只做关键词匹配与简单排序——PG 内置 FTS（英文/其他拉丁语系）开箱可用，省去一套系统与同步成本。该引入 ES/OpenSearch 的场景：① 中文搜索是核心功能（需要成熟分词、同义词、拼音、纠错）；② 需要复杂相关性调优、聚合分析、高亮、suggest；③ 数据量与 QPS 很大，需要独立扩展；④ 搜索与业务数据解耦、多源汇聚。代价：数据同步链路（CDC/双写）、一致性延迟、运维成本——不要为了「看起来专业」而过早引入。

Q：为什么我的全文检索查询没走索引？

A：最常见原因：查询中的 tsvector 表达式与索引中的表达式不一致。例如索引建在 to_tsvector('english', title || ' ' || body)，而查询写的是 to_tsvector('english', body) @@ ...，两者不同就无法使用索引。标准解法：① 把 tsvector 建成 GENERATED ALWAYS AS ... STORED 生成列，查询时直接引用该列（WHERE search_vec @@ q）；② 或者建表达式索引并保证查询表达式字面一致。另外确认：配置名要一致（'english' vs 'simple'），否则也无法命中。

Q：GIN 和 GiST 索引在全文检索上怎么选？

A：GIN（推荐默认）：真正的倒排索引，查询快、无假阳性，但更新较慢（插入时维护 posting list）、索引体积较大、构建较慢；适合读多写少的搜索场景，可用 fastupdate 与 gin_pending_list_limit 缓解更新开销。GiST：基于签名（有损压缩），体积小、更新快，但查询时有假阳性需要回表过滤，因此查询较慢；适合写入频繁、对查询延迟要求不高的场景。权衡口诀：查得快用 GIN，写得快用 GiST。

Q：中文全文检索在 PG 里怎么做？

A：PG 内置配置不分词中文（simple 会把整句当一个词）。三种做法：① 安装 zhparser / pg_jieba 扩展——提供中文解析器，效果较好，但需要编译安装与维护；② 二元切分（bigram）——把「数据库优化」切成「数据、据库、库优、优化」，无需扩展但索引膨胀明显、召回较糙；③ pg_trgm——三元组匹配，适合子串包含/模糊匹配（如搜姓名、编号），对真正的分词搜索效果一般。若中文搜索是核心能力，通常直接用 Elasticsearch/OpenSearch 更省事。

Q：ts_rank 和 ts_rank_cd 有什么区别？排序怎么调？

A：ts_rank：基于词频与权重（A/B/C/D）打分，简单快速；ts_rank_cd：加入 cover density（词距）——查询词在文档中越邻近，得分越高，通常更贴近真实相关性。调优手段：① 用 setweight 给标题/摘要更高权重（对搜索体验影响最大）；② 第三个参数 normalization 控制是否按文档长度归一（长文档天然词频高，不归一会被长文垄断，常用 1 或 32）；③ 结合实际点击/业务信号做二次排序（如 ORDER BY rank * 0.7 + popularity * 0.3）。

Q：全文检索的索引更新会影响写入性能吗？

A：会。GIN 索引插入较慢，因为每插入一行都要更新多个词的 posting list。缓解方式：① 开启 fastupdate=on（默认）——新条目先写入待处理列表，批量合并，显著提升写入吞吐（代价是查询时要扫描待处理列表，略微变慢）；② 调大 gin_pending_list_limit（默认 4MB）让批量合并更少发生；③ 定期 VACUUM 触发合并；④ 写入极频繁且查询要求不高时改用 GiST。实践：默认开启 fastupdate 即可，只有在写入 QPS 极高时才需要进一步调参。

实操 SQL

-- 1) 建表时用生成列自动维护 tsvector（PG 12+）
CREATE TABLE docs (
    id     BIGSERIAL PRIMARY KEY,
    title  TEXT,
    body   TEXT,
    ts_vec TSVECTOR GENERATED ALWAYS AS (
        setweight(to_tsvector('simple', coalesce(title,'')), 'A') ||
        setweight(to_tsvector('simple', coalesce(body,'')),  'B')
    ) STORED
);
-- setweight: A > B > C > D，标题权重更高

-- 2) GIN 索引
CREATE INDEX idx_docs_ts ON docs USING GIN (ts_vec);

-- 3) 查询与排序
SELECT id, title,
       ts_rank(ts_vec, query) AS rank,
       ts_headline('simple', body, query,
                   'StartSel=<mark>, StopSel=</mark>, MaxFragments=3') AS snippet
FROM docs, plainto_tsquery('simple', '分布式 事务') query
WHERE ts_vec @@ query
ORDER BY rank DESC
LIMIT 20;

-- 4) 短语查询（要求词相邻）
SELECT * FROM docs
WHERE ts_vec @@ phraseto_tsquery('simple', '分布式事务');

-- 5) 前缀匹配（搜索框自动补全）
SELECT * FROM docs
WHERE ts_vec @@ to_tsquery('simple', 'distrib:*');
-- 6) 用 pg_bigm 处理中文（无需词典，二元切分）
CREATE EXTENSION pg_bigm;
CREATE INDEX idx_docs_bigm ON docs USING GIN (body gin_bigm_ops);
-- 用 LIKE 查询也能走索引（这是 pg_bigm 最大的价值）
SELECT * FROM docs WHERE body LIKE '%分布式事务%';
-- 限制：查询词太短（< 2 字）效果差

-- 7) 查看索引大小与效果
SELECT pg_size_pretty(pg_relation_size('idx_docs_ts'));
EXPLAIN ANALYZE SELECT * FROM docs WHERE ts_vec @@ plainto_tsquery('simple','test');
-- 确认用了 Bitmap Index Scan on idx_docs_ts，而不是 Seq Scan

-- 8) 大规模时的调优
ALTER INDEX idx_docs_ts SET (fastupdate = off);   -- 写多读少时关掉，查询更快
-- 或定期手动合并 pending list
SELECT gin_clean_pending_list('idx_docs_ts');
