sort 包：三种用法从简到繁

Go 的排序是不稳定的（sort.Sort / sort.Slice），相等元素的相对顺序不保证。需要保持原有顺序时用对应的 Stable 版本。

// ① 基本类型：sort.Ints / sort.Strings / sort.Float64s nums := []int{3, 1, 2} sort.Ints(nums) sort.Sort(sort.Reverse(sort.IntSlice(nums))) // 降序 // ② 任意切片 + 比较函数（最常用） users := []User{{Name: "b", Age: 30}, {Name: "a", Age: 20}} sort.Slice(users, func(i, j int) bool { return users[i].Age < users[j].Age }) // ③ 稳定排序：相等元素保持原顺序 sort.SliceStable(users, func(i, j int) bool { return users[i].Age < users[j].Age }) // ④ 已排序数据上的二分查找 i := sort.Search(len(nums), func(i int) bool { return nums[i] >= 7 }) // i == len(nums) 表示没找到
sort.Slice最常用，传 less 函数即可。
Stable 版本需要保持相等元素原顺序时用。
Reverse包一层即可降序，不用写反向 less。
sort.Search在有序数据上二分，返回插入位置。

性能与选择：什么时候用哪个

场景推荐复杂度说明
小切片（< 12 元素）sort.SliceO(n log n)内部对小区间用插入排序，实际很快
需要稳定性sort.SliceStableO(n log n)额外内存，稍慢
只找是否存在map 或 sort.SearchO(1) / O(log n)一次性查找用 map 更快
TopK堆或一次遍历O(n log k)全排序再取前 K 是浪费
几乎有序的数据sort.Slice接近 O(n)pdqsort 对此有优化
并发大数据分片排序后归并可并行标准库不提供并行排序

Go 1.19 起 sort 使用 pdqsort（pattern-defeating quicksort），在很多实际分布下明显快于旧实现，并且对「已排序」「逆序」「大量重复」三类坏输入有针对性优化。

slices 与 maps：Go 1.21 起的泛型工具包

数据处理的常见陷阱

排序不稳定

用 sort.Slice 排多关键字时，第二关键字会被打乱。

// ❌ 两次排序：第二次会打乱第一次的结果 sort.Slice(u, func(i, j int) bool { return u[i].Age < u[j].Age }) sort.Slice(u, func(i, j int) bool { return u[i].Name < u[j].Name }) // ✅ 一次比较里写全所有关键字 sort.Slice(u, func(i, j int) bool { if u[i].Name != u[j].Name { return u[i].Name < u[j].Name } return u[i].Age < u[j].Age })

闭包捕获比较值

比较函数里访问外部切片要小心下标与并发。

  • 排序过程中切片会被原地重排
  • 不要在 less 里修改切片
  • 并发排序同一切片需要加锁

隐式 O(n²)

  • 在循环里对切片做删除（每次搬移）
  • 用 slice 做去重查找而非 map
  • 字符串拼接用 + 而非 Builder
  • 先估算数据量级，再选数据结构

深入自检

sort.Slice 和 sort.SliceStable 该怎么选？

只有在「相等元素的原始顺序有意义」时才需要 Stable，比如先按时间排好再按类别排。多数场景用 sort.Slice 更快。如果拿不准，就用 Stable 换取可预期的结果。

为什么排序结果和我预想的不一样？

常见原因是用了不稳定排序做多关键字排序，或者 less 函数不是严格的「小于」关系（比如用了 <=）。less 必须是严格弱序，否则结果未定义。

TopK 真的需要全排序吗？

不需要。全排序是 O(n log n)，而维护一个大小为 K 的堆是 O(n log k)，K 远小于 n 时快得多。也可以直接用一次遍历维护前 K 个。

slices 包能完全替代 sort 吗？

对基本类型与简单结构体基本可以，而且更类型安全。但 sort 包仍在一些场景更灵活（如自定义 sort.Interface 的类型），两者会长期共存。

怎么判断排序是不是性能瓶颈？

先用 pprof 看 CPU 占比。若排序确实占大头，再看：能不能减少排序次数、能不能只排需要的部分、数据是否可以预先有序、比较函数是否过重（比如里面做了字符串格式化或 map 查找）。

sort 包：三个 API 与选择

API签名适用稳定性
sort.Ints / Float64s / Strings针对基本类型切片最常见场景，最快不保证
sort.Slice(x, less)任意切片 + 比较函数通用不保证（pdqsort 是不稳定的）
sort.SliceStable同上需要保持相等元素的原有顺序保证稳定，但更慢且额外内存
sort.Search(n, f)在已排序序列上二分查找—
sort.Sort(data Interface)实现 Len/Less/Swap老代码 / 自定义数据结构—

常用写法

// 基本用法
sort.Ints(a)                                    // 升序
sort.Sort(sort.Reverse(sort.IntSlice(a)))       // 降序（包一层 Reverse）
sort.Slice(users, func(i, j int) bool {
    return users[i].Age < users[j].Age
})
// 多字段排序：先按 Age 升序，相同则按 Name 降序
sort.Slice(users, func(i, j int) bool {
    if users[i].Age != users[j].Age {
        return users[i].Age < users[j].Age
    }
    return users[i].Name > users[j].Name
})

// 二分查找（切片必须已排序！）
i := sort.Search(len(a), func(i int) bool { return a[i] >= target })
if i < len(a) && a[i] == target { /* 找到了 */ }

// Go 1.21+ 有泛型版，无需写比较函数的类型断言
slices.Sort(a)
slices.SortFunc(users, func(x, y User) int { return cmp.Compare(x.Age, y.Age) })
idx := slices.BinarySearch(a, target)

// 只取前 K 个（K 远小于 N 时用堆更划算）
h := &minHeap{}
for _, v := range data {         // 维护大小 K 的堆，O(n log k)
    if h.Len() < k { heap.Push(h, v) } else if v > h.Top() { heap.Pop(h); heap.Push(h, v) }
}

性能事实：Go 1.19 起 sort.Slice 底层换成 pdqsort（pattern-defeating quicksort），相比旧快排在有大量重复元素或已部分有序的输入上快很多，并且对「恶意输入导致退化为 O(n²)」有防护。平均与最坏复杂度：平均 O(n log n)。

性能与坑

场景复杂度建议
全量排序O(n log n)直接用 sort
只取 Top-K（K << N）堆是 O(n log k)比全排序 O(n log n) 省得多
已排序序列上查找O(log n)sort.Search / slices.BinarySearch
多次查找O(log n) 每次先排序一次（O(n log n)）再二分，比每次线性扫划算
几乎有序的数据插入排序 O(n·d)小规模（n < 12）pdqsort 内部会退化成插入排序
  • sort.Search 的前提是已排序：在未排序切片上用会得到无意义的结果，而且不报错。
  • sort.Slice 不稳定：相等元素的相对顺序可能被打乱。分页+排序场景务必用 SliceStable，否则翻页时会出现重复/漏行。
  • 比较函数必须满足严格弱序：less(i,i) 必须为 false，且不能有 a<b 与 b<a 同时成立的情况，否则结果未定义（可能 panic 或死循环）。
  • 比较函数里的昂贵操作：比较会被调用 O(n log n) 次，里面做字符串转换/正则会严重拖慢，应预先计算好排序键（这就是「装饰-排序-去装饰」模式）。
  • 大结构体排序：sort 会频繁交换元素。排指针切片（[]*T）比排值切片（[]T）快得多。

优化写法

// 装饰-排序-去装饰（把昂贵的排序键预先算出来）
type item struct{ v string; key []byte }   // key 是预先算好的排序依据
items := make([]item, len(data))
for i, d := range data {
    items[i] = item{v: d, key: expensiveNormalize(d)}   // 只算 n 次
}
sort.Slice(items, func(i, j int) bool {
    return bytes.Compare(items[i].key, items[j].key) < 0   // 比较很便宜
})

sort.Slice 和 sort.SliceStable 差多少？

SliceStable 需要额外的内存与移动，通常慢 20%~50%（视数据规模）。不需要稳定性时用 slice.Sort 即可。

什么时候稳定性重要？

当「相等元素的原始顺序有业务含义」时——最典型就是分页：先按时间排序再按分数排序，不稳定的排序会让每页顺序漂移。

1.21 的 slices 包要不要迁？

新代码推荐用：类型安全、无需 sort.Interface 样板、有 BinarySearch 等便利函数。老代码不急着改，行为一致。
