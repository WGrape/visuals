①LIKE：唯一标准化的匹配方式

LIKE 是 SQL 标准里唯一的字符串模式匹配。两个通配符：% 匹配任意长度（含零）， _ 匹配恰好一个字符。

模式含义能走 B+Tree 索引？
'abc%'以 abc 开头✓ 可转范围扫描
'%abc'以 abc 结尾✗
'%abc%'包含 abc✗
'a_c'a 开头 c 结尾共 3 字符△ 前缀部分可用
B+Tree 只能按「有序前缀」定位，前导通配符破坏了有序性
转义问题：要匹配字面量的 % 或 _ 必须用 ESCAPE 子句，如 LIKE '100\%%' ESCAPE '\'。 更根本的建议是：用户输入直接拼进 LIKE 就是注入风险，参数化查询是底线。

②大小写敏感与排序规则

LIKE 是否区分大小写，不取决于 LIKE，而取决于列的排序规则（collation）。 以 _ci 结尾（case insensitive）的不区分，_bin / _cs 区分。

数据库默认行为显式控制
MySQL（utf8mb4_general_ci / 0900_ai_ci）不区分用 _bin 排序规则或 LIKE BINARY
PostgreSQL区分（LIKE）ILIKE 不区分；citext 扩展
SQL Server取决于排序规则列定义或 COLLATE 子句
Oracle区分UPPER(col) LIKE UPPER(?)（会失索引，需函数索引）
大小写不敏感查询 + 索引：用 UPPER(col) = ? 会让索引失效， 正确做法是建函数索引 / 表达式索引（CREATE INDEX ON t (UPPER(col))）， 或干脆把列设成不区分大小写的排序规则。

③正则表达式

各库都提供正则匹配，但函数名与语法不统一，且都不走普通索引。

数据库语法说明
MySQL 8col REGEXP 'pattern' / REGEXP_LIKE(col, pat)ICU 正则，8.0 起支持
PostgreSQLcol ~ 'pat'（区分）/ ~*（不区分）POSIX 正则
OracleREGEXP_LIKE(col, 'pat')还有 REGEXP_SUBSTR/REPLACE
SQLite需加载扩展默认无内置
正则在数据库里是性能杀手：逐行回溯匹配、无法用索引、无法估算选择率。 数据量超过万行且需要在线响应时，应把这类匹配放到应用侧或搜索引擎。 数据库里的正则更适合数据清洗、一次性校验、小表过滤。

④什么时候该上全文检索

需求LIKE全文索引外部搜索引擎
前缀匹配 abc%✓ 最佳可以但没必要过重
任意位置子串✓（全表扫）△ 取决于分词器✓ n-gram 可支持
中文分词搜索✗ 语义不对△ MySQL 需 ngram 解析器✓ ES 最成熟
相关性打分排序✗△ 基础 BM25/TF-IDF✓ 可调
高亮、同义词、拼音、纠错✗✗✓ 唯一选择
选型口径：能收敛成前缀匹配就留在 LIKE； 需要「按词搜索 + 排序」用数据库全文索引（MySQL FULLTEXT、PG tsvector）； 需要中文分词、高亮、同义词、拼音、纠错、多字段权重 → 直接上 Elasticsearch / OpenSearch， 用 binlog 或双写保持同步。不要让数据库承担搜索引擎的职责。
Q：中文用 MySQL FULLTEXT 为什么搜不出？
A：默认解析器按空格/标点切词，中文整段会被当成一个词。需要配置 ngram 解析器并设置 token 大小（通常 2）， 且建索引时就要指定——改解析器必须重建索引。中文搜索体验要求高时仍建议改用 ES。
Q：LIKE '%x%' 一定要全表扫吗？
A：B+Tree 下必然如此。替代方案：① 反转列 + 前缀索引处理后缀查询；② 数据量大就用倒排索引； ③ 若只是固定的几个关键词，可以加一个生成列（generated column）标记录后再索引。

写法走索引?原因

后缀匹配优化

-- 反例：后缀/包含匹配在大表上是灾难
SELECT * FROM users WHERE email LIKE '%@gmail.com';
-- 1000 万行全表扫描，秒级到分钟级

-- 解法 1：冗余一个反转列（专门优化后缀匹配）
ALTER TABLE users ADD COLUMN email_rev VARCHAR(255);
UPDATE users SET email_rev = REVERSE(email);
CREATE INDEX idx_rev ON users(email_rev);
SELECT * FROM users WHERE email_rev LIKE REVERSE('%@gmail.com');
--   REVERSE('%@gmail.com') = 'moc.liamg@%'  → <strong>变成前缀匹配，走索引</strong>

-- 解法 2：生成列（MySQL 5.7+/PG 都支持，自动维护）
ALTER TABLE users ADD COLUMN domain VARCHAR(100)
  GENERATED ALWAYS AS (SUBSTRING_INDEX(email, '@', -1)) STORED;
CREATE INDEX idx_domain ON users(domain);
SELECT * FROM users WHERE domain = 'gmail.com';   -- 等值匹配，最快

NULL 与转义的坑

场景结果说明
x LIKE '%' 且 x 为 NULLNULL（不匹配）NULL 不参与 LIKE 匹配
x NOT LIKE 'a%' 且 x 为 NULLNULL（不返回）三值逻辑，需 OR x IS NULL
模式里含 %/_ 字面量需转义用 ESCAPE 子句
大小写取决于排序规则utf8mb4_general_ci 不区分

转义与排序

-- 转义特殊字符（搜索字面量 % 或 _）
SELECT * FROM t WHERE name LIKE '%100\%%' ESCAPE '\';
--   匹配包含 "100%" 的字符串
--   注意：ESCAPE 子句必须写，否则 \% 行为未定义

-- PostgreSQL 的写法不同
SELECT * FROM t WHERE name LIKE '%100#%%' ESCAPE '#';

-- 大小写敏感控制（MySQL）
SELECT * FROM t WHERE name LIKE 'abc%' COLLATE utf8mb4_bin;   -- 敏感
SELECT * FROM t WHERE name LIKE 'abc%' COLLATE utf8mb4_general_ci;  -- 不敏感

-- 陷阱：<strong>排序规则决定是否走索引</strong>
--   若列的 collation 与查询指定的不同，索引可能失效

正则与全文检索的选择

需求方案理由
简单的前缀/包含LIKE最简单，前缀能走索引
复杂模式（手机号、邮箱格式校验）REGEXPLIKE 表达不了
中文/英文分词搜索全文索引LIKE 与正则都不分词
高亮、相关性排序全文索引LIKE 无相关性概念
模糊搜索 + 相关性ES / Lucene数据库全文索引能力有限

为什么中文搜索不能用 LIKE：LIKE 是子串匹配，不分词。搜「数据库」能匹配「数据库系统」，但搜「数据 库」（带空格）或「据库」就匹配不到——因为它不理解词的边界。中文全文索引需要专门的分词器（MySQL 的 ngram parser、PG 的 zhparser、或直接用 ES）。

中文全文索引

-- MySQL 中文全文索引（ngram 分词器）
CREATE TABLE articles (
  id INT PRIMARY KEY,
  title VARCHAR(200),
  body TEXT,
  FULLTEXT (title, body) WITH PARSER ngram      -- <strong>关键：ngram</strong>
) ENGINE=InnoDB;

-- ngram_token_size 默认 2（二字分词），需重启生效
--   SHOW VARIABLES LIKE 'ngram_token_size';

SELECT *, MATCH(title, body) AGAINST('分布式系统' IN NATURAL LANGUAGE MODE) AS score
FROM articles
WHERE MATCH(title, body) AGAINST('分布式系统' IN NATURAL LANGUAGE MODE)
ORDER BY score DESC;

-- 限制：
#   1) 默认忽略长度 < ngram_token_size 的词（如单字「书」搜不到）
#   2) 有停用词表，常见词被忽略
#   3) InnoDB 全文索引仅支持 CHAR/VARCHAR/TEXT
#   4) 分区表不支持全文索引

自检 Q&A

Q：LIKE '%x%' 一定全表扫描吗？

A：通常是的，但有两个例外——① 如果查询只需要索引列（覆盖索引），优化器可能扫索引而不扫表（索引通常比表小得多，IO 更少）；② MySQL 8.0 的倒排索引或某些数据库的 GIN/trigram 索引（PostgreSQL 的 pg_trgm 扩展）能加速包含匹配。所以真有高频的包含搜索需求，PostgreSQL 的 pg_trgm 或专门的搜索引擎是正解，而不是硬扛 LIKE。

Q：为什么我加了索引，LIKE 还是慢？

A：按可能性——① 模式以 % 开头（前面说的，无法用 B+ 树）；② 返回行数太多：即使走索引，命中 50% 的行时优化器会判断全表更快；③ 索引列上做了函数变换（如 LOWER(name) LIKE ...），导致索引失效；④ 排序规则不匹配。诊断用 EXPLAIN 看 type 是 range（走索引）还是 ALL（全扫）。

Q：RLIKE 和 REGEXP 有区别吗？

A：MySQL 里完全等价，RLIKE 是 REGEXP 的同义词。真正的区别在正则方言：MySQL 8.0 前用 Henry Spencer 正则（不支持 \d、\w 等 PCRE 简写），8.0+ 改用 ICU（支持 \d）。PostgreSQL 用 POSIX 正则，~ 操作符区分大小写、~* 不区分。跨库迁移时正则语法必须重写，这是常见的迁移坑。

Q：全文索引和 LIKE 该什么时候切换？

A：三个信号——① 需要分词（中文、英文单词边界）；② 需要相关性排序（不只是「匹配/不匹配」，还要「有多匹配」）；③ 数据量与查询量让 LIKE 的全表扫描扛不住（大表上 LIKE 是 O(n)）。若只是简单的前缀搜索（如「输入 abc 自动补全」），LIKE + 索引完全够用，不要过早引入全文索引——它有额外的维护成本与限制。
