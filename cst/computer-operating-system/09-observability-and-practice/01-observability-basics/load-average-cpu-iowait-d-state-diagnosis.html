CPU 不高而 load average 很高：运行队列、D 状态与 iowait 怎样判断

用 8 核机器 load=12、CPU=30% 的现场，沿任务状态、磁盘延迟和容器限额定位瓶颈。

load average 不是 CPU 百分比

Linux 的 load average 通常统计一段时间内可运行任务与不可中断睡眠任务的平均数量，并给出约 1、5、15 分钟的指数平滑值。可运行任务可能正在 CPU 上执行，也可能排队等 CPU；不可中断睡眠常见于等待某些内核 I/O 等路径。CPU 使用率则描述 CPU 时间花在 user、system、idle、iowait 等状态上的比例。两个指标口径不同：8 核机器 load=12、CPU 使用率只有 30%，不能直接断言“CPU 还有 70% 空闲所以没有瓶颈”，也不能直接断言“12/8=150% CPU 使用率”。

先核对观察范围和时间窗。load 是平滑后的整机信号，CPU 百分比可能来自某一秒、某个进程或某个容器；把不同窗口、不同作用域的数放在一起会制造假矛盾。

图解：高 load、低 CPU 的判断路线

沿箭头逐步核对输入、变换和输出；下面的推演可以逐步切换。

8 核 load=12 的三种可能

若 8 个核心持续 100% 忙，运行队列还有 4 个任务等 CPU，load 接近 12 的确可能表示 CPU 饱和。若 CPU 总使用率仅 30%，但有很多任务停在 D 状态等慢磁盘或远程文件系统，load 也可能升高，CPU 却大部分时间没有运行应用代码。若宿主机 8 核空闲、容器只有 1 核 CPU 配额，容器内进程可能因 cgroup 节流而排队，容器业务慢但宿主总 CPU 不高。三种情况修复方向完全不同。

具体 load 值还受进程数量、短任务突发、采样间隔和系统实现影响。1 分钟值刚上升而 15 分钟值仍低，表示问题可能新发生；三个值都高，更像持续负载。不能只凭一张截图定因。

逐步推演

记录症状

8 核机器 load=12、CPU 30%，业务 P99 变慢。

看可运行队列、D 状态与每核 CPU。

验证等待源

比较磁盘尾延迟、线程栈或 cgroup 节流。

复验业务

相同流量下看 P99、队列和等待是否同时恢复。

iowait 到底代表什么

CPU iowait 是某些统计口径下 CPU 空闲且系统有等待 I/O 的时间比例，不等于“磁盘利用率”，也不等于“应用请求等待磁盘的百分比”。多核系统里某个线程等 I/O，其他线程仍可把 CPU 跑满；iowait 可能很低，但该线程的尾延迟很高。反过来 iowait 高提示要查 I/O 路径，却不能单独说明是哪个设备、哪个进程或哪段远程存储慢。

排障需看设备读写延迟、队列、吞吐和错误，同时看进程的等待状态与调用栈。系统可能在文件系统、块设备、网络存储或内存回收路径停住；只看 iostat 一个平均延迟也可能掩盖尾部故障。

信号能说明什么不能单独说明什么
load averageR/D 类任务的平滑数量CPU 使用百分比
CPU user/systemCPU 实际执行任务的时间请求是否在等 I/O
iowait某些口径下空闲 CPU 有 I/O 等待具体设备或线程的延迟
D 状态线程处于不可中断等待必然是哪一个磁盘故障

先拆整机再到线程

记录故障窗口里的业务延迟与错误率，再看整机 CPU user/system/idle/iowait、每核分布、load 趋势、运行队列和 D 状态任务数。若 CPU user/system 高，定位热点进程和线程，采样 on-CPU 调用栈；若业务慢但 CPU 低，找阻塞线程、I/O 延迟、锁等待、网络超时或容器节流。`top`、`pidstat`、`vmstat`、`iostat` 等工具提供不同视角，具体字段含义依平台和版本，使用时要核对单位与采样窗口。

对 D 状态线程，可从进程状态、内核调用栈及其打开的文件或挂载点找等待对象。不要因为看见 D 就直接重启数据库：若底层磁盘持续慢，重启只会扩大恢复时间。先定位设备和共享依赖，再决定动作。

容器里的限额陷阱

Kubernetes Pod 设了 CPU limit，例如 1 核，但宿主机有 8 核。应用在高峰需要短时 2 核，cgroup 会对超出额度的运行时间节流；业务 P99 升高、容器限额计数增长，宿主整体 CPU 仍可能很低。此时盲目增加线程数可能让争用更严重。要结合容器 CPU 使用、节流次数/时间、请求并发与线程运行队列分析，并区分 requests 决定调度预留、limits 决定硬限额的角色。

不同 cgroup 版本和监控代理对节流指标的采集口径会变化，不能只看一个“throttled 事件数”绝对值。应在相同负载下调整限额或优化 CPU 工作量，观察业务延迟是否改善。

一个故障时间线

10:00 用户反馈 API 延迟从 80 毫秒升到 2 秒，8 核主机 load 从 2 升到 12，CPU 总使用率从 25% 到 30%。若同时发现 D 状态任务数从 0 升到 10、存储设备 P99 读延迟从 5 毫秒升到 800 毫秒，而 on-CPU 火焰图没有新热点，优先怀疑 I/O 路径；接着核对挂载点、设备错误、存储服务健康和受影响进程。若 D 状态不多，却有容器 CPU 节流明显上升，就走限额方向。一个证据链必须包含业务症状、等待主体和资源异常的同一时间窗口。

将故障期与正常期同样长度的样本对照，比“现在 top 看起来正常”可靠。问题恢复后，平滑的 15 分钟 load 仍可能高一阵，不表示故障仍在发生。

修复后的验收

若确认存储延迟导致等待，修复设备或减少随机 I/O 后，在相同流量下应看到 D 状态与存储尾延迟下降，业务 P99 恢复；若是 CPU 节流，调整限额或减少计算后应看到节流与请求尾延迟同步改善。保留变更前后请求量、缓存命中和依赖状态，避免把流量自然下降误认为修复有效。对偶发事件可加上进程状态、设备延迟和容器节流的联合告警，但不应只凭 load 单指标自动重启。

第一层 · 概念与判定：三个指标各在说什么

指标统计的是什么容易误解的点
load average可运行态 + 不可中断睡眠态的进程数均值包含等 IO 的进程，不等于 CPU 使用率
CPU iowaitCPU 空闲且有未完成 IO的时间占比高 iowait 只是「闲着等 IO」，不代表磁盘满了
D 状态（uninterruptible sleep）进程在等内核 IO 完成，无法被信号打断kill 杀不掉，只能等 IO 完成或重启
CPU 使用率非空闲时间的占比（含 sys/usr/等）与 load 无必然关系

判定口诀：load 高 + CPU 使用率高 = 真的在算（计算瓶颈）；load 高 + CPU 使用率低 + iowait 高 = 在等 IO（IO 瓶颈）；load 高 + CPU 低 + iowait 低 = 有大量 D 状态进程（可能在等锁或存储异常）。

定位 load 与 IO 问题的完整命令链

# ① 先看 load 的三个值，判断是在涨还是在落
cat /proc/loadavg
# 输出：0.35 0.42 0.38 2/1437 123456
#       |    |    |    |      └─ 最后 PID
#       |    |    |    └─ 可运行数/总进程数
#       └─ 1 / 5 / 15 分钟均值

# ② 看 CPU 各部分占比，重点关注 wa（iowait）与 st（steal）
top -bn1 | head -5
# 或更直观
vmstat 1 5
# 关键列：r（运行队列）= load 的来源；b（阻塞）= D 状态进程数
#          wa = iowait；us/sy/id 分别用户态/内核态/空闲

# ③ 找磁盘问题：util 接近 100% 说明设备已饱和
iostat -x 1 3
# 关键列：%util（设备利用率）、await（平均等待 ms）、svctm（服务时间）
#         rkB/s + wkB/s（吞吐）、aqu-sz（平均队列长度）

# ④ 找出到底哪些进程在 D 状态
ps -eo stat,pid,comm,wchan:30,cmd | awk '$1 ~ /D/'

# ⑤ 看进程卡在内核哪个函数（wchan 字段）
cat /proc/<PID>/wchan; echo
cat /proc/<PID>/stack   # 需要 root，能直接看到调用栈

数量级直觉：4 核机器上 load = 4 表示刚好跑满；load = 8 表示有一半请求在排队。所以 load 一定要除以核数才有意义。

第三层 · 排障与边界

高频坑清单：

  • ① 拿 load 绝对值判断：64 核机器 load=30 很正常，2 核机器 load=10 已经爆了
  • ② 以为 iowait 高就是 CPU 忙：恰恰相反，iowait 高说明 CPU 闲着在等 IO
  • ③ 用 kill -9 杀 D 状态进程：杀不掉，它会一直等到 IO 返回
  • ④ 忽略 steal（st）：虚拟机上 st 高说明被宿主机抢了 CPU，不是你的问题
  • ⑤ 只看 1 分钟 load：瞬时尖峰会被 15 分钟均值平滑掉，要看趋势
  • ⑥ 把 nice 进程算漏：load 包含所有可运行进程，不区分优先级

标准排查顺序（记住这个链条）：

  • ① uptime 看 load 趋势（是在涨还是在落）
  • ② vmstat 1 看 r 与 b：r 高是 CPU 竞争，b 高是 IO 阻塞
  • ③ top 看 CPU 分布：us 高是应用，sy 高是内核，wa 高是 IO
  • ④ iostat -x 看磁盘：%util 接近 100% 且 await 远超 svctm 就是饱和
  • ⑤ ps 找 D 状态进程，再用 /proc/PID/stack 定位卡在哪
  • ⑥ 如果是网络存储（NFS/Ceph），还要查网络而不只是本地磁盘

第四层 · 原理与取舍

为什么 D 状态进程杀不掉？

因为 D 状态（TASK_UNINTERRUPTIBLE）的设计目的就是保证内核 IO 路径不被打断。如果允许信号打断正在写磁盘的进程，可能导致数据结构处于半更新状态、数据损坏。所以内核让进程必须等 IO 完成，任何信号都先挂起。这也是为什么存储故障时会出现大量 D 状态进程堆积 —— 它们不是卡死，是在等一个永远不会返回的 IO。

iowait 高但磁盘 util 不高，是怎么回事？

常见两种情况：① 网络存储（NFS、iSCSI、Ceph）—— 本地 iostat 看不到远端设备的繁忙，iowait 却会正常统计；② 单个慢设备拖累 —— 系统有一个设备 %util 100%，其他设备空闲，平均下来 util 不高但进程在等。所以要逐设备看，别只看汇总。

load 高但所有 CPU 指标都正常，还可能是什么？

最容易被忽略的是锁竞争和内存压力：① 大量线程阻塞在互斥锁上 —— 它们不在运行队列，但 load 统计的是可运行+不可中断，实际的等待可能来自 futex；② 内存不足导致频繁回收 —— 进程看似在跑，实际在等页回收；③ 容器 CPU 配额（cfs quota）被限流 —— CPU 看着不高，实际被 throttle，表现为 load 升高与延迟上升。这三种只用 top 看不出来，需要 perf 和 cgroup 指标。

自检

8 核机器 load average=12、CPU 使用率 30%，是否能直接把 load 当成 150% CPU 使用率？

不能。load 还可能计入不可中断等待任务；应核对时间窗、任务状态、I/O 延迟和容器限额。
