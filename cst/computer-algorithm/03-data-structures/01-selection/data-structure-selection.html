第 03 章 · 数据结构概览

先问清读写、顺序与访问方式

选型不是背复杂度表，而是按「读写比例、是否需要有序、访问方式」三个问题定位结构，再核对操作代价与常数。

先问三个问题，再挑结构

选型不是背复杂度表，而是先回答三件事：

  1. 读写比例：是读多写少（配置表、字典），还是写多读少（日志缓冲），还是读写参半（排行榜）。
  2. 要不要有序：需要按 key 排序遍历、取第 k 大、查前驱后继吗？不需要的话，哈希往往比平衡树快一个常数。
  3. 访问方式：按下标随机访问（数组）、顺序扫描（链表）、按 key 精确查（哈希/树）、只关心最大最小（堆）、还是按前缀/区间（Trie、线段树）。

这三个问题决定了 80% 的选型结果。剩下的 20% 才是常数因子、缓存局部性和工程约束。

四种最常见的误用

  • 用数组维护频繁中间插入：插入本身是 O(1) 次移动，但每次移动是 memmove 级别的 O(n)，累计就是 O(n²)。
  • 用链表做随机访问：写起来是“第 i 个节点”，跑起来是 O(n) 次指针跳转，且每次跳转都可能 cache miss。
  • 指望哈希表有序：哈希表不维护任何顺序，要有序就用树，或者把 key 单独抽出来排序。
  • 用堆当有序容器：堆只保证堆顶是极值，遍历出来不是有序序列，取第 k 大要弹 k 次。
把它们记成一句话：哈希换顺序，堆换全序，树保顺序，链表换随机访问——每一次“换”都是有代价的取舍。

复杂度之外还要看什么

  1. 缓存局部性：连续内存（数组、扁平线段树）比指针结构（链表、树）快得多，n 不大时数组线性扫描经常赢过 O(log n) 的树。
  2. 常数与实现复杂度：红黑树常数大、代码长；跳表期望同阶但更好写，也更利于并发。
  3. 内存开销：每个链表节点多两个指针，Trie 每个节点一份子节点表，数据量上亿时内存比时间更早成为瓶颈。
  4. 并发与持久化：无锁跳表、LSM 树这类选择往往由工程约束决定，而不是复杂度表。

第三层 · 排障与边界：选型的五类错误

错误选型后果正确做法

BST 有序插入退化成链表 O(n)平衡树 / 跳表

  • 排查顺序：先列出「最高频的三个操作」→ 再看它们各自要求的复杂度 → 再对照决策表 → 最后确认语言内置容器是否满足。
  • 边界一：数组的优势不止 O(1) 访问，还有缓存局部性——同样 O(n) 遍历，数组比链表快几倍。
  • 边界二：哈希的 O(1) 是均摊的，扩容时要重哈希，单次插入可能退化到 O(n)。
  • 边界三：不要为了「更高级」而选复杂结构——数组 + 排序 + 二分 能解决的场景非常多，且常数最小。

数组和链表到底怎么选？

看访问模式：随机访问多 → 数组（O(1) 下标 + 缓存友好）；已知位置的插入删除多 → 链表（O(1) 改指针）。但实践中数组胜率更高，因为缓存效应显著，而且「先找到位置」本身往往就要 O(n)。

什么时候该自己实现数据结构？

几乎不用。标准库覆盖了 95% 场景且经过极致优化。例外：需要特殊操作（并查集、Trie、线段树、带索引堆）时标准库没有，才自己写。

哈希表一定比平衡树快吗？

单次操作是（O(1) vs O(log n)），但哈希表不支持有序遍历、范围查询、前驱后继。需要这些就必须用平衡树——这不是性能取舍，是能力取舍。

选数据结构的三个问题

面对一个问题，与其凭感觉「用某某吧」，不如先回答三个具体问题，答案通常会自动浮出来：

要不要按键查找？需要 → 哈希/树/跳表；不需要 → 看下面两个问题。
要不要顺序/区间/最值？需要 → 有序容器（平衡树/跳表/堆/线段树）。
会不会动态增删？会 → 链式或动态扩展结构；静态 → 数组、前缀和、稀疏表往往更快。
规模与 write 比例？决定是优先考虑实现复杂度还是常数因子与缓存局部性。

还有一个容易被漏掉的第四要素 —— 数据的访问模式：是随机访问多还是顺序遍历多？读写比例如何？这些决定了「理论复杂度相同的两个结构」在实际硬件上会有数倍差距。

这张表的使用顺序是自上而下：越靠上的需求越基础，被满足之后再看次一级的需求。很多「选错结构」的故事，都是因为跳过了上面的条目直接冲着某个听起来更高级的结构去。

一条常被低估的准则：内存布局

理论上同为 O(n) 的遍历，数组往往比链表快好几倍。原因不在算法，而在硬件：CPU 会预取相邻的内存到缓存行里。数组连着走，几乎每次访问都命中缓存；链表每个节点散落在堆里，一次访问一次缓存缺失。

同样的渐进复杂度，缓存局部性带来数倍差距

由此得到一条很实用的偏好：在 n 不大（几千以内）且主要是遍历的场景，优先选连续内存。这就是为什么很多高性能库内部用数组实现队列、甚至用「结构体数组（SoA）」而不是「数组结构体（AoS）」。

把选择过程写成一个 checklist

① 先问操作形态：按 key 查？按序In enumeration？只要最值？要范围聚合？ ② 再问动态性：只增？可删？可改？位置是否变动？ ③ 估算规模：n < 1000 时，常数与实现难度 通常比复杂度阶更关键 ④ 估算读写比：读多写少 → 预处理型结构（前缀和、稀疏表） 读写均衡 → 平衡/分块型结构 ⑤ 最后才是 apoptotic 的具体实现： 有没有现成可靠的库实现？ 手写会不会带来 bug 风险？ 能不能先用最简单的方式把功能做出来，再按性能数据分析优化

最后一个不该被忽略的原则：先做对，再做快。绝大多数实际项目的性能瓶颈不在数据结构的选择，而在重复计算、无谓的拷贝、以及不必要的网络往返。用性能剖析数据驱动优化，而不是用直觉。

深入自检

哈希表和平衡树到底怎么选？

绝大多数情况下选哈希表：查找期望 O(1)、代码简单、实现成熟。只有当你需要顺序时才选平衡树 —— 范围查询、排序遍序、找前驱后继、按rank取第 k 个。此外哈希表要留意装填因子与扩容时的抖动，对延迟极其敏感的场景要为 rehash 买单。

什么时候该选用看起来「更差」的结构？

当实现复杂度与可维护性进入考量时。比如一个 n=200 的列表用线性查找完全够用，却上了红黑树，结果引入了 bugs 与额外依赖。工程师的价值往往体现在「选了足够简单、足够快的结构」而不是「用了最先进的结构」。

数组的 O(n) 插入真的那么糟吗？

未必。现代 CPU 用高度优化的指令批量移动连续内存，几千个元素的 memcpy / memmove 通常比几十次随机指针跳转还快。只有在 n 很大（十万以上）且插入频繁时，才需要认真考虑链表或分块结构。

能不能给个简单的经验优先级？

可以：① 默认动态数组；② 需要按键查找就加哈希表；③ 需要顺序就用排序容器或堆；④ 动态区间才上树状数组/线段树；⑤ 只在确有把握收益时才考虑跳表、并查集、字典树这类专用结构。这条链路覆盖了绝大多数日常需求。
