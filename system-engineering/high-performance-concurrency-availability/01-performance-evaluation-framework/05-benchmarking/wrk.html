wrk：多线程、事件驱动的 HTTP 压测工具

wrk 用少量负载端线程配合事件通知管理多条连接；它的 -c 表示连接数，不是 ab 的并发请求数，更不是服务端业务处理位数。

工作方式：线程、连接、请求分开看

wrk 将连接分配给多个负载端线程，由事件驱动的 IO 循环发出请求并接收响应。-t 是压测机线程数，-c 是要保持的总连接数，-d 是持续时间。单条连接上的请求次数可以很多；连接数不等于整轮请求总量，也不保证服务端同一时刻处理了同样数量的请求。普通 wrk 用连接上的响应推动后续请求，并非精确的恒定到达率发生器。

为了可靠测量，要同时看压测机 CPU、端口、文件描述符、网络和目标监听队列；wrk 可能先触及客户端瓶颈。具体安装及默认值以官方 README与本机 wrk --help 为准。

命令：本机低负载教学示例

# 2 个负载端线程、10 条连接、持续 15 秒，附延迟分布
wrk -t2 -c10 -d15s --latency http://127.0.0.1:8100/ping

# 添加请求头，并设置请求超时
wrk -t2 -c10 -d15s --timeout 2s -H 'Accept: application/json' http://127.0.0.1:8100/ping

# 运行单独准备的 Lua 脚本（下一节为 request.lua 内容）
wrk -t2 -c10 -d15s -s request.lua http://127.0.0.1:8100/

命令只供已授权的本机示例服务阅读与复现；目录中并未提供或执行 request.lua。

重要参数速查

参数含义注意
-t N / --threads N压测机使用的线程数多开线程不保证更多有效吞吐；别当成服务端线程
-c N / --connections N总连接数与 ab 的请求并发定义不同；核对本机端口/FD 与服务端连接限制
-d 时长 / --duration 时长测试持续时间，如 15s、2m总请求数是运行结果而非此参数直接指定
--latency输出详细延迟统计与百分位结合错误和超时一起看，勿只挑成功样本
--timeout 时长响应超时阈值，如 2s与业务 SLO 的时间边界分开定义
-H '名称: 值' / --header加入请求头需与真实请求的缓存/认证语义一致
-s 文件 / --script 文件载入 LuaJIT 脚本，定制请求或处理结果每请求执行脚本逻辑可能限制压测端性能

Lua：让请求符合业务语义

例如本机示例接口支持以下路径时，可将这段内容保存为 request.lua，再使用上一节命令；静态设置可减少每请求动态计算的开销。

wrk.method = "GET"
wrk.path = "/ping?kind=demo"
wrk.headers["Accept"] = "application/json"

wrk 还提供 request()、response(status, headers, body) 等钩子，可构造动态请求或校验响应；启用逐请求处理会影响发生器上限，脚本的业务校验结果也应单独统计。详见 官方脚本接口。

输出怎么读

  • Latency 一行给平均值、标准差及最大值；--latency 增加百分位分布。Req/Sec 的线程统计与最终 Requests/sec 的总体速率不是同一个展示层次。
  • requests in ... 和 Requests/sec 反映工具完成量和平均速率，Transfer/sec 是传输速率；不能直接等同业务成功吞吐。
  • Socket errors: connect, read, write, timeout（有错误时）分别反映连接、读取、写入和超时问题；配合状态码与响应体核验业务成功条件。工具未内建你业务的成功规则。

结果要与端到端指标与服务端监控交叉验证，不要用连接数倒推 QPS 或硬件容量。
