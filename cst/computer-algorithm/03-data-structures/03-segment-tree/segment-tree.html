第 03 章 · 数据结构概览

把区间拆成对数个节点

线段树用二叉树覆盖区间，把区间聚合查询与区间更新同时压到 O(log n)，区间更新依赖懒标记下推。

它要解决的是「区间查询 + 修改」的矛盾

前缀和能做到 O(1) 区间求和，但一旦有点更新，整个前缀和数组就得重算；直接遍历区间求和是 O(n)，更新倒是 O(1)。线段树把两件事都压到 O(log n)：区间查询 O(log n)，单点/区间更新也是 O(log n)。

10 万个数的数组，每秒几万次「把第 i 个改掉」和「求 [l, r] 的和」。前缀和撑不住更新，暴力遍历撑不住查询——这就是线段树的典型入场时机。

结构：一棵覆盖区间的二叉树

  • 每个节点负责一段连续区间，存这段的聚合值（和、最小值、最大值、最大子段和……）。
  • 常用数组存树：根节点下标 1，节点 p 的左右孩子是 2p 和 2p+1，空间开 4n 一定够。
  • 聚合操作必须满足结合律：父 = 左 ⊕ 右。加法、min、max、异或都行；平均数直接存会出错（要同时存和与个数）。

三个操作与复杂度

def build(p, l, r):                  # O(n)
    if l == r: tree[p] = a[l]; return
    m = (l + r) // 2
    build(p * 2, l, m); build(p * 2 + 1, m + 1, r)
    tree[p] = tree[p * 2] + tree[p * 2 + 1]

def query(p, l, r, ql, qr):          # O(log n)
    if ql <= l and r <= qr: return tree[p]   # 整段命中
    m = (l + r) // 2; s = 0
    if ql <= m: s += query(p * 2, l, m, ql, qr)
    if qr > m:  s += query(p * 2 + 1, m + 1, r, ql, qr)
    return s
为什么是 O(log n)？查询区间被拆成若干「完全覆盖」的节点，每层最多贡献 2 个节点，树高 O(log n)，所以节点数 O(log n)。

区间更新必须配懒标记

把 [l, r] 每个数都加 5，如果逐个叶子更新再往上回溯，一次就是 O(n)。懒标记（lazy tag）的做法是：命中整段时只更新该节点的聚合值并打上标记，等到真正需要下钻时再把标记下推给子节点。

  1. 更新命中整段：tree[p] += 5 * 区间长度，lazy[p] += 5。
  2. 后续查询/更新要进入子树前：把 lazy[p] 下推，更新两个孩子的聚合值与标记，清空自己的标记。
  3. 复杂度仍为 O(log n)。

懒标记的正确性依赖「标记可叠加」：加法标记可以直接累加，赋值标记要注意覆盖顺序（赋值会覆盖之前的加法），实际实现里通常按「先赋值后加法」的优先级维护两个标记。

结构区间查询单点更新区间更新支持的操作代码量
前缀和O(1)O(n)O(n)仅可差分运算（和、异或）极小
树状数组（BIT）O(log n)O(log n)需差分技巧满足结合律 + 可差分小

能用树状数组就别上线段树（常数小、代码短）；需要 min/max/最大子段和这类不可差分的操作，或者要区间赋值，才必须上线段树。

区间查询 + 修改同时存在，且操作满足结合律时，线段树是最稳的选择。

它解决的是「区间」的问题

给你一个数组。反复问两类问题：a[l..r] 的和（或最大值）是多少？以及中间还会修改某些位置的值。如果什么都不改，前缀和 O(1) 完事；一旦有修改，前缀和就要 O(n) 重算。线段树就是为「查询 + 修改」都保持 O(log n) 而生的。

线段树：每个节点管一段区间，查询时被拆成少数几个完整块
建树O(n)，通常用数组下标 2i / 2i+1 表示左右孩子。
单点更新O(log n)，改叶子后向上重算受影响的祖先。
区间查询O(log n)，把目标区间拆成若干完整节点再合并。
区间修改O(log n)，需要懒标记，否则会退化成 O(n)。

为什么区间修改必须用懒标记

如果要把 [2, 7] 每个元素都加 3，最直接的写法是递归到每个叶子逐个改 —— 一共 O(n) 次。线段树的性能保证会当场失效。

懒标记的思路是「先记账，后补做」：如果当前节点区间被修改范围完全覆盖，就只更新这个节点的值，并在它身上打一个「我的子孙都还没加上这个 3」的标记。之后只有当必须往下走时，才把这个标记下推给孩子。

伪代码：带懒标记的区间加 func update(o, l, r, ql, qr, add): if ql <= l and r <= qr: # 完全覆盖 → 就地更新并打标记 tree[o] += add * (r - l + 1) lazy[o] += add return push_down(o, l, r) # 下推旧标记 mid = (l + r) / 2 if ql <= mid: update(o*2, l, mid, ql, qr, add) if qr > mid: update(o*2+1, mid+1, r, ql, qr, add) tree[o] = tree[o*2] + tree[o*2+1] # 向上合并 func push_down(o, l, r): if lazy[o] != 0: mid = (l + r) / 2 把 lazy[o] 应用到左右孩子的值与标记上 lazy[o] = 0

三条实现纪律：① 任何往下递归之前必须先 push_down；② push 完成后当前节点的标记要清零；③ 子节点信息汇总回来后记得更新父节点。懒标记的 bug 几乎都出在这三条中的某一条。

和它的几个「近亲」怎么选

结构能力复杂度什么时候用它
前缀和数组静态区间和，不能改查询 O(1)，更新 O(n)数据完全不变时最快
线段树任意「可合并」信息（和/最大/最小/最大公因数…）查询更新均 O(log n)通用答案，支持区间修改
树状数组 BIT差分可逆的运算（和、异或、计数）O(log n)，常数极小、代码短只要前缀和/计数，不需要最大值时首选
稀疏表 Sparse Table静态区间最值、gcd（不可修改）预处理 O(n log n)，查询 O(1)数据不变、查询极多
平衡树 / 有序集合动态增删 + 顺序信息O(log n)序列本身会变长变短

一条经验法则：能用树状数组解决就先用它（代码量只有线段树的三分之一，常数也小），遇到 BIT 不支持的操作（比如区间最大值、复合信息）再升级成线段树。

工程写法：递归 vs 迭代

递归实现（常见写法）

直观、好写、官方教科书代码通常使用递归。缺点：函数调用开销与栈深（虽然只有 log n ≈ 20 层，很安全）。

数组大小开 4n 是最省事的做法：足以容纳任意长度 n 的满二叉树形态。

迭代实现（自底向上）

把树写成「底层一排叶子、上面逐层合并」的形态，两个下标指针往上/往下走，不需要递归，常数更小。

思路：把区间 [l, r] 转成 [l+n, r+n] 的连续段，然后 while l <= r 处理两侧，父节点自然覆盖更大的段。

// 维护「区间最大值 + 单点更新」的极简递归版（Go 风格） type Seg []int func (t Seg) pushUp(o int) { t[o] = max(t[o<<1], t[o<<1|1]) } func (t Seg) build(a []int, o, l, r int) { if l == r { t[o] = a[l] return } m := (l + r) >> 1 t.build(a, o<<1, l, m) t.build(a, o<<1|1, m+1, r) t.pushUp(o) } func (t Seg) query(o, l, r, ql, qr int) int { if ql <= l && r <= qr { return t[o] } m, ans := (l+r)>>1, -(1 << 60) if ql <= m { ans = max(ans, t.query(o<<1, l, m, ql, qr)) } if qr > m { ans = max(ans, t.query(o<<1|1, m+1, r, ql, qr)) } return ans }

深入自检

为什么查询一个区间最多只会命中 O(log n) 个节点？

因为树每层最多有两个节点是「被部分覆盖、必须继续往下走」的，其余被访问的节点都是整段被完全覆盖的直接返回。树高是 log n，所以最多访问约 2·log n 个完整节点加上这条路径本身，总的来说仍是 O(log n)。

线段树的空间为什么习惯开 4n？

n 个叶子对应一棵深度为 ⌈log n⌉ 的树，节点数上界略小于 4n 而大于 2n（取决于 n 是否为 2 的幂）。开 4n 是最稳妥的整数取值，多一点内存换不来多少风险，很多时候也可以直接开 2 的幂容量的底层数组来避开这个估算。

懒标记的常见 bug 有哪些？

最常见的三类：① 递归下去前忘了下推旧标记，导致子节点读到过期数据；② 下推之后没把当前节点的标记清零，后续重复下推；③ 标记的含义是「增量」还是「覆盖」混淆 —— 若操作包含赋值（覆盖），标记必须记录「覆盖值」，并且叠加顺序不能搞反（先来的先失效）。

什么时候应该不用线段树？

三种情况：① 数据完全静态，稀疏表或前缀和更省事；② 只需要前缀和/计数，树状数组代码量更小；③ 数据会动态增删导致位置频繁变动，此时更合适的是平衡树。线段树是通用解，但通用往往意味着常数偏大，能用专用结构时不要用通用的。
