SQLite 动态类型

① 五类存储类型（Storage Classes）

SQLite 采用动态类型：列声明的类型只是「亲和性（Type Affinity）」建议，实际存储的是值的存储类型。这是它与其他数据库最大的不同。

存储类说明举例
NULL空值NULL
INTEGER有符号整数，按大小用 1/2/3/4/6/8 字节变长存储42
REAL8 字节 IEEE 浮点3.14
TEXT字符串，支持 UTF-8/UTF-16'hello'
BLOB二进制，原样保存x'1A2B'

关键差异

没有 DATE/TIME/BOOLEAN 类型：日期通常存 TEXT（ISO8601）或 INTEGER（Unix 时间戳），布尔存 0/1

没有 DECIMAL

金额建议存整数分，避免浮点误差；或存 TEXT

动态类型的坑

CREATE TABLE t(x INT) 里也能插入字符串——因为 INT 只是亲和性

例外

INTEGER PRIMARY KEY 列必须是整数（它是 ROWID 的别名）

CREATE TABLE demo(a INT, b TEXT, c REAL, d);
INSERT INTO demo VALUES (1, 'x', 2.5, NULL);
INSERT INTO demo VALUES ('字符串也能进INT列', 123, '文本也能进REAL列', x'00FF');

-- 查看实际存储类型
SELECT a, typeof(a), b, typeof(b), c, typeof(c) FROM demo;
-- typeof() 返回 NULL/INTEGER/REAL/TEXT/BLOB

② 类型亲和性（Type Affinity）规则

声明类型会按规则映射到五种亲和性之一：INTEGER / TEXT / BLOB / REAL / NUMERIC。规则按声明字符串按顺序匹配：

亲和性匹配规则（按顺序）常见声明
INTEGER含 "INT"INT, INTEGER, BIGINT
TEXT含 "CHAR"、"CLOB"、"TEXT"VARCHAR(255), TEXT, CLOB
BLOB含 "BLOB" 或未声明类型BLOB, (空)
REAL含 "REAL"、"FLOA"、"DOUB"REAL, DOUBLE, FLOAT
NUMERIC其余（含 "NUM"、日期等）NUMERIC, DECIMAL, BOOLEAN, DATE
-- 亲和性的实际效果：尽量把值转成该亲和类型，转不了就原样存
CREATE TABLE t(x NUMERIC);
INSERT INTO t VALUES ('123');     -- 转成 INTEGER 123
INSERT INTO t VALUES ('3.14');    -- 转成 REAL 3.14
INSERT INTO t VALUES ('abc');     -- 转不了，存为 TEXT 'abc'
SELECT x, typeof(x) FROM t;
-- 123|integer
-- 3.14|real
-- abc|text

-- 比较时的规则：不同存储类有固定大小顺序
-- NULL < INTEGER/REAL < TEXT < BLOB
实际陷阱：WHERE varchar_col = 123 不会匹配 '123'——因为整数与文本属于不同存储类，比较时不相等（不像 MySQL 会做隐式类型转换）。务必保证传入参数的类型与存储类型一致，这是 SQLite 最常见的「查不到数据」原因。

③ 日期、时间与布尔

-- 三种常见存法
-- ① TEXT（ISO-8601，推荐：可读、可排序、支持 SQLite 日期函数）
INSERT INTO events(created_at) VALUES ('2026-10-20 14:30:00');

-- ② INTEGER（Unix 秒；空间最省，比较最快）
INSERT INTO events(created_at) VALUES (strftime('%s','now'));

-- ③ REAL（Julian day，较少用）

-- 日期函数
SELECT date('now');                          -- 2026-10-20
SELECT datetime('now', '+1 day');
SELECT strftime('%Y-%m-%d %H:%M', 'now');
SELECT julianday('now') - julianday('2026-01-01');   -- 相差天数

-- 布尔：存 0/1
CREATE TABLE users(id INTEGER PRIMARY KEY, active INTEGER NOT NULL DEFAULT 1);
推荐做法：① 日期用 TEXT 存 ISO-8601（UTC）——可直接字符串比较排序，且 date()/strftime() 能直接用；② 金额用 INTEGER 存最小单位（分）；③ 布尔用 INTEGER 0/1 并加 CHECK (x IN (0,1)) 约束。

④ 约束与严格表

-- 常用约束
CREATE TABLE users (
  id      INTEGER PRIMARY KEY,            -- 等于 ROWID
  email   TEXT NOT NULL UNIQUE,
  age     INTEGER CHECK (age >= 0 AND age < 150),
  status  TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active','banned')),
  created TEXT NOT NULL DEFAULT (datetime('now'))
);

-- 外键（默认关闭！必须显式开启）
PRAGMA foreign_keys = ON;
CREATE TABLE orders (
  id      INTEGER PRIMARY KEY,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE
);

-- STRICT 表（SQLite 3.37+）：拒绝类型不符的插入
CREATE TABLE t (a INTEGER, b TEXT) STRICT;
INSERT INTO t VALUES ('abc', 'x');   -- 报错：cannot store TEXT value in INTEGER column

PRIMARY KEY

INTEGER PRIMARY KEY 是 ROWID 别名（最快）；其他类型主键会额外建唯一索引

NOT NULL

必须有值（NULL 也算一个存储类）

CHECK

自定义条件，用于枚举/范围约束

外键默认关闭

每次连接都要 PRAGMA foreign_keys = ON;——这是历史兼容行为，非常容易踩坑

STRICT 表

3.37+ 支持，强制类型检查，新项目建议开启

DEFAULT

支持字面量与括号表达式（如 (datetime('now'))）

⑤ 常见问法

Q：SQLite 为什么被称为『动态类型』？跟其他数据库有什么不同？

A：因为类型属于「值」而不属于「列」——列声明的类型只是亲和性（affinity）建议，SQLite 会尽量把插入的值转换成该亲和类型，转不了就原样存。因此 CREATE TABLE t(x INT) 里也能插入 'abc'，typeof(x) 会返回 text。对比：MySQL/PostgreSQL 是静态类型，类型不符会报错。例外：INTEGER PRIMARY KEY 列必须是整数（因为它是 ROWID 的别名）。新项目可用 STRICT 表（3.37+）获得静态类型检查。

Q：为什么 WHERE id = '123' 查不到数据？

A：因为 SQLite 不做隐式类型转换：列中存的是 INTEGER 123，而你传入的是 TEXT '123'，不同存储类的值比较时不相等（存储类的比较顺序是 NULL < INTEGER/REAL < TEXT < BLOB，跨类即不等）。这与 MySQL 的行为相反（MySQL 会隐式转换后匹配），因此从 MySQL 迁移过来时极易踩坑。解决：保证应用层传入的参数类型与列中实际存储的类型一致；或用 CAST 显式转换；或用 STRICT 表 + 严格的参数绑定。

Q：SQLite 怎么存日期和金额？

A：日期三种方案：① TEXT 存 ISO-8601 字符串（推荐）——可读、字典序即时间序、date()/strftime() 等函数直接可用；② INTEGER 存 Unix 时间戳——最省空间、比较最快，但不可读；③ REAL 存 Julian day（少用）。金额：用 INTEGER 存最小货币单位（分），绝对不要用 REAL（浮点误差）；若必须保留小数位可用 TEXT 或配合应用层处理。布尔：用 INTEGER 0/1，可加 CHECK (x IN (0,1))。

Q：INTEGER PRIMARY KEY 有什么特殊之处？

A：它是 ROWID 的别名：表本身就是按它组织的 B-tree，因此不需要额外索引、定位最快，并且它必须是 64 位整数。对比：若声明成 TEXT PRIMARY KEY 或 INT PRIMARY KEY DESC，就不是 ROWID 别名，SQLite 会额外创建一个唯一索引来维护主键，占用更多空间且稍慢。另外：SQLite 的表默认都有隐式 ROWID（可用 WITHOUT ROWID 声明去掉，适合纯键值表或多列主键的场景，可省一层间接查找）。

Q：外键约束为什么没生效？

A：因为 SQLite 默认关闭外键检查（为了向后兼容），每个连接都必须显式执行 PRAGMA foreign_keys = ON;，而且必须在事务之外执行（在事务内无效）。常见表现：插入了不存在的外键值、删除父行时子行没有级联删除，且不报错。其他要点：① 该 PRAGMA 不是持久化的，每次新建连接都要执行（连接池要注意）；② ON DELETE CASCADE 只在开启后才生效；③ 可用 PRAGMA foreign_key_check; 检查现有数据的违反情况。

Q：STRICT 表是什么？该用吗？

A：STRICT 是 SQLite 3.37（2021-11）引入的表选项：开启后拒绝不符合列声明类型的值（只能存 NULL/INTEGER/REAL/TEXT/BLOB 且必须与亲和性兼容），并提供静态类型检查；此外还要求 PRIMARY KEY 列隐含 NOT NULL、禁止部分历史遗留的宽松语法。建议：新项目开启 STRICT——它保留了 SQLite 的轻量与灵活，同时避免了动态类型带来的隐蔽 bug（如「字符串存进了 INT 列导致查不到」）。注意：已有表不能 ALTER 成 STRICT，需要重建表迁移。

SQLite 的类型亲和性（type affinity）

声明类型亲和性存储行为
含 INTINTEGER能转成整数就存整数
含 CHAR/CLOB/TEXTTEXT转成文本
含 BLOB 或无类型BLOB原样存，不转换
含 REAL/FLOA/DOUBREAL转成浮点数
含 NUMERIC/DECIMAL/BOOL/DATENUMERIC优先整数，其次浮点，否则文本

这是 SQLite 最反直觉的地方：它是动态类型，声明的类型只是「亲和性建议」，实际可以存任何类型。你可以在 INTEGER 列里存字符串，SQLite 不会报错。规则：值的类型跟着值走，不跟着列走。

存储类说明大小
NULL空值0 字节
INTEGER有符号整数1/2/3/4/6/8 字节（按需，不是固定 8 字节）
REALIEEE 754 浮点8 字节
TEXTUTF-8/UTF-16 字符串按内容长度
BLOB原始字节按内容长度

INTEGER 是变长的：存 1 只占 1 字节，存 2³¹ 以上才占 8 字节。这是 SQLite 数据库文件小的原因之一。

常见坑与正确写法

-- 坑 1：布尔值实际存成 0/1
CREATE TABLE t (flag BOOLEAN);       -- BOOLEAN 的亲和性是 NUMERIC
INSERT INTO t VALUES ('true');       -- 存成文本 'true'（转不成数字）
INSERT INTO t VALUES (1);            -- 存成整数 1
SELECT * FROM t WHERE flag = 1;      -- 只匹配到第二行！
-- 正确：统一用 0/1，或显式 CHECK 约束
CREATE TABLE t (flag INTEGER NOT NULL CHECK (flag IN (0, 1)));

-- 坑 2：日期没有原生类型
-- SQLite 没有 DATE 类型，三种常见存法：
--   a) TEXT: '2026-10-22 10:30:00'（推荐，可读性好，可用字符串比较）
--   b) INTEGER: Unix 时间戳（秒或毫秒）
--   c) REAL: Julian day
-- 用 TEXT 时要保证格式统一（ISO8601），否则字符串比较会错
SELECT * FROM t WHERE created_at >= '2026-10-01' AND created_at < '2026-11-01';
-- 函数：date(), datetime('now'), strftime('%Y-%m-%d', 'now')

-- 坑 3：主键 INTEGER 才是 rowid 别名
CREATE TABLE a (id INTEGER PRIMARY KEY, ...);    -- ✅ id 就是 rowid，自增
CREATE TABLE b (id INT PRIMARY KEY, ...);        -- ⚠️ INT 也行（含 INT 即 INTEGER 亲和）
CREATE TABLE c (id VARCHAR(20) PRIMARY KEY, ...); -- ❌ 不是 rowid，是普通唯一索引
-- AUTOINCREMENT 只在 INTEGER PRIMARY KEY 上允许，且保证单调不复用
-- 不用 AUTOINCREMENT 时，删了最大值后可能复用该 id
-- 坑 4：类型比较规则（比较前会应用亲和性）
SELECT 1 = '1';              -- 0（false）！INTEGER 与 TEXT 永不相等
SELECT '1' = '1';            -- 1
-- 列有 INTEGER 亲和性时，比较前会把 '1' 转成 1
CREATE TABLE t (v INTEGER);
INSERT INTO t VALUES ('1');
SELECT * FROM t WHERE v = 1;      -- 能查到（'1' 被转成 1 存储）
SELECT * FROM t WHERE v = '1';    -- 也能查到（比较时 '1' 应用 INTEGER 亲和性转成 1）

-- 用 typeof() 看实际存储类型（调试利器）
SELECT v, typeof(v) FROM t;
--   integer

-- 坑 5：浮点精度
SELECT 0.1 + 0.2 = 0.3;      -- 0（false），IEEE754 的固有问题
-- 金额一定要用 INTEGER 存「分」，不要用 REAL
CREATE TABLE orders (amount_cents INTEGER NOT NULL);

-- 坑 6：没有真正的 ALTER COLUMN
-- SQLite 只能：改表名、加列、部分场景下改列
ALTER TABLE t ADD COLUMN new_col TEXT;
-- 改列类型/删列需要重建表（建新表 -> 拷数据 -> 删旧表 -> 改名）

排障清单

症状原因处理
插入字符串后查不出来列是 INTEGER 亲和，被转成了数字用 typeof() 看实际类型；统一存入的类型
自增 ID 出现重复没用 AUTOINCREMENT，删除后复用加 AUTOINCREMENT；或用 UUID

最实用的调试命令：SELECT col, typeof(col) FROM t LIMIT 10;当你对数据存成了什么有疑问时，这个能立刻给出答案。
