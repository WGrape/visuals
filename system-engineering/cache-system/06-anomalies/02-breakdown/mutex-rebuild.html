🔒 互斥重建：让一千个请求只查一次库

用一把分布式锁把并发重建收敛成单次重建，是解决击穿最直接的手段。

先建立直觉：一张「正在补货」的牌子

超市货架空了。如果每个顾客发现没货都跑去仓库喊一次，仓库会被吵死。合理的做法是：第一个发现没货的人去仓库取货，同时在货架上挂一块牌子「正在补货，请稍等」。后面的人看到牌子就在旁边等一会儿，货补上了直接拿。

互斥重建就是这块牌子：分布式锁。持锁线程去查库补货，其他线程等待后重读缓存。

完整流程与关键分支

正确实现（含所有保护）

func GetById(id int64) (*User, error) {
    key := fmt.Sprintf("user:%d", id)
    lockKey := key + ":lock"

    if v, ok := redis.Get(key); ok {
        return decode(v), nil          // 1. 命中直接返回
    }

    // 2. 未命中，尝试抢锁（NX + 过期时间，一条命令保证原子）
    got, err := redis.SetNX(lockKey, "1", 5*time.Second)
    if err == nil && got {
        defer redis.Del(lockKey)       // 3. 铁律：finally 释放

        u, err := db.QueryUser(id)     // 4. 只有持锁者查库
        if err != nil { return nil, err }
        if u == nil {
            redis.SetEX(key, 60, NULL_MARK)   // 空值也缓存，防穿透
            return nil, nil
        }
        redis.SetEX(key, 300, encode(u))
        return u, nil
    }

    // 5. 未抢到锁：退避 + 抖动后重试，超限降级
    for i := 0; i < 3; i++ {
        time.Sleep(time.Duration(20<<i)*time.Millisecond + jitter())
        if v, ok := redis.Get(key); ok { return decode(v), nil }
    }
    return fallback(id)                // 兜底：默认值 / 旧快照 / 报错
}

四个必须注意的坑

坑后果正确做法
锁没有 TTL重建线程崩溃 → 锁永不释放 → 该 key 永久不可用SETNX 必须同时设过期时间（用单条原子命令，不要先 SETNX 再 EXPIRE）
未用 finally 释放查库抛异常时锁残留，要等 TTL 才恢复释放逻辑放 defer / finally
锁 TTL < 重建耗时锁提前过期，第二个线程又进来查库 → 保护失效TTL 要显著大于最坏重建耗时；或加看门狗自动续期
重试风暴大量线程同时 sleep 后同时重试，形成第二次尖峰指数退避 + 随机抖动 + 最大重试上限 + 超限降级
还有一个隐蔽问题：误删别人的锁。如果线程 A 卡顿导致锁自动过期，线程 B 拿到锁，此时 A 恢复并执行 DEL，就把 B 的锁删了。正确做法：锁的 value 存一个唯一标识（如 UUID），释放时先比对再删（用 Lua 脚本保证原子）。

什么时候不该用互斥锁

  • 超高频热点（几十万 QPS 单 key）：等待线程太多，反而拖垮响应时间 → 改用逻辑过期或本地缓存。
  • 重建极慢（几秒）：等待时间不可接受 → 改为异步刷新 + 返回旧值。
  • 可接受陈旧数据：没必要让请求阻塞，逻辑过期更划算。
一句话：互斥锁用「让请求等一下」换「数据库只查一次」。当「等一下」的代价超过「多查几次」的代价时，就该换方案了。

🎯 面试问答

Q：为什么 SETNX 和 EXPIRE 不能分两条命令写？
A：因为不是原子的。如果 SETNX 成功后进程立刻崩溃，过期时间还没设上，这把锁就永久存在了，该 key 再也无法重建。必须用单条原子命令（Redis 的 SET key val NX EX 30），或用 Lua 脚本把两步合并。

Q：释放锁为什么要比对 value？
A：防止删掉别人的锁。场景：线程 A 持锁后卡顿（GC 停顿），锁超时自动释放；线程 B 拿到锁开始重建；此时 A 恢复，执行 DEL——把 B 的锁删掉了，线程 C 又能进来，保护形同虚设。解法：锁 value 存 UUID，释放时用 Lua 脚本「值相等才删」，保证原子。

Q：重试次数超限后应该返回什么？
A：取决于业务容忍度，优先级：① 返回本地缓存的旧值（如果有）；② 返回兜底默认值（如空列表、默认配置）；③ 返回明确的错误/稍后重试。不要无限等待——那会把线程耗尽，把「缓存问题」放大成「服务整体不可用」。

Q：互斥锁和逻辑过期能一起用吗？
A：可以，而且是很好的组合：逻辑过期保证请求永不阻塞（始终返回数据，哪怕旧），互斥锁保证同时只有一个线程去重建（避免重复查库）。即「读永远成功 + 重建只有一次」，这是生产上对付顶级热点的常见搭配。

缓存重建防击穿的方案对比

方案原理代价 / 风险
互斥锁（mutex rebuild）只有一个线程回源，其他等或返回空等待线程会阻塞；锁本身可能成瓶颈
逻辑过期（提前刷新）value 里存过期时间，过期后先返回旧值再异步刷新实现稍复杂；有短暂不一致
永不过期 + 异步更新缓存不设 TTL，靠后台任务刷新需要独立的刷新机制
单飞（singleflight）同 key 并发只放行一个回源Go 有现成实现；只解决并发不解决首次
布隆过滤器拦截不存在的 key解决穿透不是击穿；有误判率约 1%
空值缓存查不到也缓存（短 TTL）防穿透；TTL 一般 60~300s
多级缓存本地 + Redis 分层本地层能扛住大量重复请求

互斥锁的标准实现（Redis SET NX）：

import time, uuid

def get_with_mutex(key, loader, ttl=600, lock_ttl=3, wait=0.05, max_wait=50):
    """互斥重建：只有一个线程回源，其余短暂等待后读缓存"""
    v = cache.get(key)
    if v is not None:
        return v
    lock_key = f"lock:{key}"
    token = str(uuid.uuid4())
    # SET key token NX EX lock_ttl  —— 原子抢锁
    got = redis.set(lock_key, token, nx=True, ex=lock_ttl)
    if got:
        try:
            v = loader()                       # 回源查 DB
            cache.set(key, v if v is not None else "", ex=ttl)
            return v
        finally:
            # 必须用 Lua 保证「判断 value 相等才删」，不能先 get 再 del
            redis.eval(
                "if redis.call('get',KEYS[1])==ARGV[1] then "
                "return redis.call('del',KEYS[1]) else return 0 end",
                1, lock_key, token)
    else:
        # 没抢到锁：短暂轮询等缓存就绪
        for _ in range(max_wait):
            time.sleep(wait)
            v = cache.get(key)
            if v is not None:
                return v
        return None        # 或返回兜底默认值/降级

互斥重建的坑与排障

症状原因处理
等待线程全部超时回源很慢 + 等待次数不够限制等待总时长（如 500ms）；超时返回兜底值而不是一直等
锁没被释放导致永久不可用回源 panic 没走 finally；或进程被 kill锁必须带过期时间（lock_ttl）；业务代码用 try/finally
误删了别人的锁先 GET 再 DEL 不是原子操作必须带唯一 token + Lua 比较删除，这是 Redlock 的基本要求
锁过期了但回源还没完成lock_ttl 小于回源耗时lock_ttl 要 > 回源 p99 耗时；或开看门狗自动续期（Redisson 有）
热点 key 重建时大量阻塞单 key 并发极高配合逻辑过期：不等锁，直接返回旧值并异步刷新
DB 压力没降下来不同 key 的并发（不是同 key）互斥锁只对同一个 key 有效；整体压力大要限流+扩容
锁本身成瓶颈所有 key 抢同一把锁锁的粒度是 per-key，不要全局一把

互斥锁 vs 逻辑过期怎么选：互斥锁保证一致性但要等待；逻辑过期不用等但会短暂返回旧值。能接受旧值就优先用逻辑过期，体验更好；强一致（余额、库存）才用互斥锁。
