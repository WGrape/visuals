什么时候适用？

判断信号：客户端可能因超时或消息重投重复执行同一业务操作。

  • 付款请求带幂等键避免重复扣款
  • 消息消费重复投递时只记一次积分
  • 创建订单接口因网络超时重试

和相近方案怎么区分？

相近方案选择边界
重试重试提高瞬时失败后的成功率；幂等保证重复尝试不会重复产生副作用。
去重去重是常见实现手段；完整幂等还包括相同结果返回与处理中状态恢复。

最小伪代码

function charge(request):
  key = request.idempotencyKey
  created, record = store.insertIfAbsent(key, status=PROCESSING)
  if not created:
    if record.alreadyDone: return record.savedResult
    return RetryLater
  result = payment.charge(request)
  store.complete(key, result)
  return result

边界：键要绑定请求语义和有效期；占位、业务副作用、结果保存之间仍需事务或恢复方案。

为什么必须幂等 Idempotency

重试/消息重投/双击都会让同一操作到达多次

在分布式环境下，超时重试、消息重投、用户双击都会让同一个语义的请求到达多次。若『扣款』被重复执行，灾难就来了。幂等保证：无论执行 1 次还是 N 次，业务效果相同。

常见实现手段

  • 唯一幂等键：请求带 clientId+seq，服务端用唯一索引去重。
  • 状态机：已支付则忽略重复支付。
  • 乐观锁/版本号：update ... where version=N。
  • Token 机制：先取令牌，提交即消费，重复提交无令牌被拒。

面试高频问答

Q：GET 天然幂等，POST 不幂等，怎么处理？
A：REST 语义上 GET/PUT/DELETE 应幂等，POST 不幂等。对必须安全的写操作，用『幂等键 + 去重表』把非幂等接口变成幂等，或改用 PUT（带资源标识）。
Q：幂等键存多久？
A：至少要覆盖『请求可能重复到达』的窗口（通常几小时到一天），并定期清理；同时配合业务状态机，即使键过期也能靠状态兜底。

幂等：分布式系统里的「防重复」底线

幂等的严格定义是：同一操作执行任意多次，对系统状态的影响与执行一次相同。注意是「对状态的影响」——返回值可以不同（第二次可以返回「已处理」而非「处理中」），但副作用不能重复。

为什么必须有它？因为在分布式系统里，重复请求是常态而不是异常：网络超时后客户端重试、消息队列的重投、上游的补偿重发、用户双击按钮……只要接口不幂等，重复扣款、重复下单、重复发券就一定会发生。

天然幂等GET 查询、DELETE 删除、SET（赋值而非累加）——重复执行结果相同
非幂等CREATE 创建、INCREMENT 累加、扣款、发券——每次执行都会产生新副作用
幂等令牌客户端生成的唯一 ID，服务端用它识别「这是同一笔请求」
去重表服务端用唯一索引把幂等键固化下来，靠数据库约束兜底
幂等键流转：客户端生成 → 服务端去重 → 业务只执行一次

五种实现方案对比

方案做法适用场景注意点
唯一索引（最常用）建去重表或用业务表的唯一键，INSERT 冲突即判定重复下单、支付、发券等所有「创建类」操作冲突后要能返回首次结果；去重记录与业务操作必须在同一事务
状态机（业务幂等）给实体加状态字段，只有处于前一状态才允许流转订单状态、退款状态、任务状态用 UPDATE ... WHERE status = 期望值 的乐观方式，靠影响行数判断
乐观锁 version表加 version 字段，更新时带 WHERE version = 旧值余额扣减、库存扣减等更新类影响行数为 0 表示被并发修改，需重试或报错；不适合高频热点行
分布式锁以幂等键为锁名加锁，拿到锁才执行临界区很短且无法用数据库约束表达的场景锁必须有超时与续约；Redis 锁在主从切换下不安全，关键场景用 Redlock 或数据库锁
Token 机制（防重复提交）进入页面时服务端下发 token，提交时带上并一次性核销表单重复提交、支付确认页token 核销要原子（Redis DEL 返回值判断）；核销失败说明已提交过

优先顺序：唯一索引 / 状态机 > 乐观锁 > Token > 分布式锁。原因是前两者把并发正确性交给数据库的约束（最可靠、无额外组件），而分布式锁引入了新依赖且有多种失效边界（锁超时、GC 停顿、时钟漂移）。

消息消费的幂等（最容易出事的地方）

几乎所有消息队列都提供「至少一次」投递（at-least-once），这意味着重复投递必然发生：消费者处理完但还没提交位点就宕机、或提交失败、或 Rebalance 导致消息被重新分配。所以消费端幂等不是可选项，是必选项。

① 用消息 ID 去重以 msgId 或业务唯一键建唯一索引，重复消息 INSERT 冲突直接跳过
② 消费前查状态先查业务实体是否已处理（如订单是否已支付），是则直接 ACK
③ 消费记录表单独的 consume_log 表记录已处理的 msgId，与业务操作同事务
④ 处理与 ACK 顺序先处理业务再 ACK；若先 ACK 后处理，宕机会丢消息
⑤ 重试要有上限超过最大重试次数进入死信队列，人工介入，不能无限循环

经典错误：在消费逻辑里写「先 SELECT 判断已存在则跳过，否则 INSERT」。在高并发或消息重投时，两个线程可能同时 SELECT 到「不存在」然后都 INSERT。正确做法是直接 INSERT 让唯一索引去拦截，或用 INSERT ... ON DUPLICATE KEY UPDATE / INSERT IGNORE，把判断交给数据库。

-- 幂等消费：一条 SQL 搞定插入与去重 INSERT INTO consume_log (msg_id, biz_key, status) VALUES ('msg-001', 'order-888', 'DONE') ON DUPLICATE KEY UPDATE msg_id = msg_id; -- 冲突时不做任何变更 -- 判断 ROW_COUNT()： -- 1 → 首次处理，继续执行业务逻辑 -- 0 → 重复消息，直接 ACK 返回

四类典型重复场景

用户重复提交双击 / 刷新 / 返回再提交 → 重复下单
网络超时重试客户端 / 网关重试 → 重复扣款
消息重复投递MQ at-least-once → 重复加积分
上游回调重放第三方回调多次 → 重复发货

四类来源各异，但兜底手段一致：用唯一标识 + 存储约束把重复挡在业务副作用之外。

落地代码示例：去重表 / Token / 重试

方案落到代码上，关键是把判断交给存储约束（唯一索引、Lua 原子脚本），而不是应用层「先查后写」。下面三段是工程里最常见的最小可用实现。

问题推荐实现选型要点
创建类去重去重表 + 唯一索引（INSERT 抢占）与业务同事务；冲突返回首次结果
防重复提交Token 预领取 + Lua 原子核销Redis SETNX / Lua；比对 value 防误删
写操作重试退避 + 抖动 + 上限避免重试风暴打垮下游

去重表建表（MySQL）

CREATE TABLE idempotent_record ( biz_id VARCHAR(64) NOT NULL, biz_type VARCHAR(32) NOT NULL, result VARCHAR(2048), status TINYINT NOT NULL, -- 0 处理中 / 1 成功 / 2 失败 expire_at DATETIME NOT NULL, PRIMARY KEY (biz_type, biz_id) -- 唯一索引是幂等的根基 ) ENGINE=InnoDB;

Token 原子核销（Lua）

-- KEYS[1]=token key, ARGV[1]=期望业务指纹 if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) -- 命中：删除并返回 1 else return 0 -- 未命中或指纹不符：拒绝 end

带抖动的指数退避（Python）

import random, time def retry(fn, times=4, base=0.1): for i in range(times): try: return fn() except RetryableError: if i == times - 1: raise sleep = base * (2 ** i) * (0.8 + 0.4 * random.random()) # ±20% 抖动 time.sleep(sleep) # 4 次重试等待约 1.2~1.8s（含抖动）

Redis 还是 MySQL？ 并发极高、允许少量丢失用 Redis（SETNX + 过期）；要求绝对可靠用 MySQL（唯一索引 + 事务）。金融类业务一般用 MySQL。幂等记录务必设 TTL（7~30 天）并定期归档，否则表无限膨胀。

幂等设计的常见误区

把幂等做成「先查后写」

这是最高频的错误。检查和写入之间有天然的并发窗口。

  • 必须用原子操作：唯一索引、CAS、带条件的 UPDATE
  • 「查一下再决定」在多实例下必然漏

去重键选错粒度

  • 太粗：用「用户 ID」去重 → 用户第二笔正常订单被误拦
  • 太细：每次请求生成新 UUID → 完全起不到去重作用
  • 正确：键应等于「业务上一次真实意图」，如「订单 ID + 操作类型」

忽略返回结果的一致性

幂等不等于「第二次返回空」。客户端重试时期望拿到与第一次语义相同的结果。

  • 应缓存首次执行结果并返回
  • 否则客户端可能把「已处理」误判为「失败」继续补偿

去重数据不清理

  • 幂等记录会无限增长，成为新的大表
  • 按业务保留周期（如 7~30 天）定期归档删除
  • 保留期要大于最大可能的重复到达间隔

深入自检

GET 请求一定幂等吗？

从 HTTP 语义规范上 GET、PUT、DELETE 是幂等的，POST 不是。但工程上要看实现：一个 GET 接口如果内部做了「查询并写入浏览记录 + 计数 +1」，那它就不幂等。反之，一个 POST 接口如果带了幂等键并在服务端去重，它对外表现为幂等。所以幂等是接口的契约，不是由 HTTP 方法自动保证的——设计接口时要显式声明并保证。

扣款这种操作怎么做到幂等？

关键是不要写「UPDATE account SET balance = balance - 100」这种相对操作，而要基于状态机或流水：① 为每笔扣款生成唯一流水号（业务幂等键），扣款表以流水号建唯一索引；② 扣款前先插入流水（状态=处理中），冲突则说明已处理过；③ 执行 UPDATE 时带条件（如 WHERE balance >= 100）并用乐观锁 version；④ 流水与余额变更在同一事务；⑤ 最终结果记录在流水上，重复请求直接返回该结果。核心是把「相对操作」转化为「基于唯一标识的绝对状态流转」。

分布式锁做幂等有什么坑？

三个典型问题：① 锁超时——业务执行时间超过锁的 TTL，锁被别人拿到，两个请求同时进入临界区；② 误释放——线程 A 的锁过期后被 B 获得，A 结束时 DEL 掉了 B 的锁（需 value 存唯一标识，用 Lua 比对再删）；③ Redis 主从切换——主节点写入锁后未同步就宕机，从节点提升为主，锁丢失。所以对资金类场景，优先用数据库唯一约束而非分布式锁；必须加锁时用 Redlock 或带 fencing token 的方案。

幂等键过期时间设多久？

原则是「大于最大可能的重复到达间隔，小于业务允许的存储成本」。考虑几个来源：客户端重试窗口（通常分钟级）、消息队列最大重试时长（可能小时级）、人工补偿与对账周期（可能天级）。实践上：纯防网络重试留 24 小时足够；涉及资金对账的关键流水建议永久保留（或至少保留到对账完成 + 一个争议期）。不要用「几秒钟」——那防不住队列积压导致的延迟重投。
