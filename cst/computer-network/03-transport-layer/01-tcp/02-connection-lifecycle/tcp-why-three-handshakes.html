📋 总结：三次握手缺一不可

  • 防止历史连接：第三次握手让客户端确认服务器是否真的愿意建立新连接
  • 同步序列号：双方交换 ISN，确保后续数据传输有序
  • 验证双向通信：至少需要三次验证（发送→接收→确认）
  • 效率最优：四次可以但浪费，合并 SYN+ACK 为最优方案
  • 防止资源浪费：避免建立无用的虚假连接

握手真正在做的事：互相确认初始序号

TCP 要可靠，就必须给每个字节编号，并且双方都要知道对方的起始编号。三次握手本质上就是在交换并确认两个方向的初始序列号（ISN）。

发送方知道自己的序号送达；反过来对方的序号是否被正确收到，需要对方的 ACK 来证明。 两次握手只确认了「客户端→服务端」这一个方向，服务端的初始序号没有被客户端确认， 于是无法判断服务端发出的数据是否被正确接住 —— 可靠性保证不完整。
三次握手 = 两个方向的序号各确认一次

为什么不是两次，也不是四次

两次为什么不行

表面原因：无法让服务端确认自己的 ISN 已被客户端收到，可能导致服务端稀里糊涂地开始发数据。

更致命的是历史重复连接问题：一个因网络延迟迟到的旧 SYN 到达服务端，两次握手会让服务端误以为这是新连接并直接建立，分配资源、开始传输，而客户端根本没打算通信 —— 资源白白浪费。有了第三次确认，客户端有机会用 RST 把这个误会掐掉。

四次为什么不必

理论上「SYN → ACK，再 SYN → ACK」四次最清楚，但第 2、3 步完全可以合并成一个报文：SYN 和 ACK 是两个标志位，能同时置位。

于是三次就成了「既保证两个方向都被确认、又不多花一次往返」的最小方案。

一句话版本：三次握手＝「我在」「我在 + 我听到你了」「我听到你了」。最后一句不可省，因为它是在告诉对方你的话我也听清楚了。

和 TLS 的叠加：HTTPS 时代，用户真正等到能发数据，往往是「TCP 三次握手 + TLS 握手」串行加起来。这也是为什么 TLS 1.3 大幅裁减往返次数、QUIC 把两者合并 —— 优化目标一直是减少往返。

为什么四次挥手，以及 TIME_WAIT 在等什么

四次挥手：两个方向分别关闭，中间出现半关闭状态

TIME_WAIT 等那 2·MSL 是为了两件事：

  1. 让最后的 ACK 有机会被送达。万一这个 ACK 丢了，对方会重发 FIN，此时你还在，可以再回一次 ACK。如果早就关掉了，对方会收到 RST 而不是 ACK，认为出错。
  2. 让旧连接的残包在网络里消散。如果不等待，马上用相同的四元组建新连接（这在短连接服务里非常常见），上一个连接的迟到数据包可能被新连接误收 —— 数据错乱。

由此得到一个常见问题：压测或爬虫场景服务端出现大量 TIME_WAIT，是因为它主动关闭了连接。让服务端保持长连接、或调整成由客户端主动关闭，通常能显著缓解。

深入自检

三次握手里能不能携带数据？

第三次可以（客户端已确认双方序号、状态到达 ESTABLISHED），前两次理论上某些实现也支持携带少量数据（TCP Fast Open）。常见实现里 第三次 ACK 报文通常会顺带捎上第一个请求的数据，省下一次往返。前两次一般不带数据，因为连接尚未完全建立、服务端还要分配资源。

SYN Flood 具体是怎么把服务打挂的？

攻击者发送大量 SYN 但不回第三次 ACK，服务端为每个 SYN 分配了连接资源并放进半连接队列等待确认。队列被灌满后，正常用户的 SYN 也会被丢弃，表现为连接超时。防御手段包括 SYN Cookie（不预分配资源）、缩短重传超时、在负载均衡/防火墙侧限速。

为什么握手要交换 MSS 与窗口缩放因子，而不是之后慢慢试探？

因为这些参数必须在传数据之前就达成一致，否则第一批发出去的报文就可能不合适。TCP 把这些关键参数放在握手报文的选项字段里协商，正是为了让连接一开始就在正确的配置下工作，避免过渡期的低效或出错。

四次挥手能不能合并成三次？

可以，当被动关闭方也没有数据要继续发时，它的 ACK 与 FIN 可以合并成一个报文，看起来就是三次。延迟确认机制进一步提高了这种合并的概率。所以「四次挥手」说的是一般情况，实际抓包常常看到三次。
