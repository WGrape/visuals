①单进程内的职责划分

Qdrant 用 Rust 写成，单二进制、无外部依赖：不需要 etcd、不需要对象存储、不需要消息队列，./qdrant 起来就能用。这个设计选择决定了它的取舍 —— 部署极简、单机性能好，但水平扩展能力不如存算分离的 Milvus。

要理解它的行为（为什么刚导入数据时查询慢、为什么内存曲线有台阶），关键是把「集合 → 段（Segment）→ 优化器」这条链看清楚。

②优化器与四个触发阈值

Qdrant 的写入是「先落 WAL，再进内存段」，优化器在后台异步做三件事。这三件事都有触发阈值，理解阈值才知道什么时候该等、什么时候该调。

优化器做什么关键阈值你感知到的现象
Indexing把缓冲里的点建成 HNSWindexing_threshold_kb 默认 20000（约 20 MB）导入后一段时间内查询很慢，之后突然变快
Flusher把段刷到磁盘flush_interval_sec 默认 5重启后数据不丢（WAL + flush 配合）
Vacuum清理被删除的点deleted_threshold 默认 0.2、vacuum_min_vector_number 默认 1000删除后磁盘/内存不马上降，过一阵才降
Compaction合并小段max_optimization_threads段数量过多时合并，期间 IO 升高
导入大量数据后不要立刻压测。等优化器把 HNSW 建完（观察 /collections/{name} 的 indexed_vectors_count 追上 points_count），否则你测到的是暴力扫描的性能。
# 观察索引进度
GET /collections/docs
# → result.points_count          已写入总数
# → result.indexed_vectors_count 已建索引数
# 两者相等 = 优化器已完成

# 想立刻建索引：调低阈值
PATCH /collections/docs
{ "optimizers_config": { "indexing_threshold_kb": 1000 } }

③三层存储：向量 / payload / 索引各自放哪

这是 Qdrant 最有辨识度的设计：数据分三层，每层可以独立决定「在内存还是磁盘」。存储决策直接决定内存账单和延迟表现。

层内容开关默认代价
向量本体float32 / 量化码 / HNSW 图vectors.on_disk、quantization_config.*.always_ram内存放盘 → 省内存，延迟升到个位数~数十 ms
Payload（标量字段）随点存储的属性on_disk_payloadtrue（较新版本默认落盘）落盘 → 省内存，但返回 payload 时读盘
Payload 索引用于过滤的倒排/数值索引create_payload_index按需创建不建索引 → 过滤退化为全段扫描
HNSW 图邻接表hnsw_config.on_disk内存图落盘 → 内存大降但延迟明显上升
Qdrant 的经典省内存组合：量化码常驻内存（always_ram）+ 原向量与 HNSW 图放盘。查询先用内存里的量化码粗筛，再从盘上取少量原向量精排 —— 用很小的延迟代价换 4–10 倍内存。

④与 Milvus 的架构范式对比

选型时常被问到「Qdrant 和 Milvus 差在哪」，答案主要在架构范式而不是功能清单。

维度QdrantMilvus
实现语言RustGo + C++（核心索引）
外部依赖无（单二进制）etcd + 对象存储/本地盘 + 消息队列（分布式模式）
架构范式单进程内含全部职责，分布式靠 Raft 协调存算分离，各角色独立扩展
扩展方式加节点 + 增加副本/分片按角色横向扩（QueryNode / DataNode / IndexNode）
过滤能力过滤与向量检索深度整合，filterable HNSW标量索引 + 位图，过滤在段级生效
量化scalar / binary / product 三种，配置灵活量化绑定索引类型（IVF_SQ8/IVF_PQ 等）
适合中小规模、想少运维、Rust 生态、边缘部署大规模、需要按角色弹性、已有 K8s 体系
一个实用的判断：数据量在千万级以内、团队不想维护一套分布式系统，Qdrant 的运维成本明显更低；数据往亿级走、需要独立扩查询层，Milvus 的存算分离才体现出价值。

⑤生产配置清单

Qdrant 的启动参数几乎都通过配置文件或环境变量控制，生产上值得改的就这几项：

# config/production.yaml
storage:
  storage_path: /qdrant/storage
  snapshots_path: /qdrant/snapshots
  optimizers:
    indexing_threshold_kb: 20000   # 调小 → 更快建索引，但频繁小段
    deleted_threshold: 0.2         # 删除比例超过 20% 触发 vacuum
    vacuum_min_vector_number: 1000
  # 关掉遥测（内网环境）
telemetry_disabled: true

service:
  max_request_size_mb: 32
  grpc_timeout_sec: 60

# 集群模式
cluster:
  enabled: true
  p2p:
    port: 6335
  consensus:
    tick_period_ms: 100

⑥速记卡

单二进制

无 etcd / 无对象存储 / 无 MQ，./qdrant 即可跑。

三层存储

向量 / payload / payload 索引，各自可独立决定内存或磁盘。

段模型

新写入进未索引缓冲，超阈值才建 HNSW —— 解释导入后查询慢。

优化器四件

indexing / flusher / vacuum / compaction，各有阈值。

压测前提

等 indexed_vectors_count 追平 points_count。

省内存套路

量化码常驻内存 + 原向量与图放盘。

vs Milvus

单进程自洽 vs 存算分离；千万级内 Qdrant 运维更省。

端口

REST 6333 / gRPC 6334 / 集群 p2p 6335。

Qdrant 的很多「异常」其实是优化器在工作：导入后慢、删除后不降、段越积越多，都是阈值触发的正常行为。
