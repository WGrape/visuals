栈内存管理

Go 的 goroutine 使用可增长的连续栈：初始很小，需要时复制扩容、不够时再缩。理解栈分配、逃逸分析与栈伸缩，有助于写出省 GC 的代码。对应左书 7.3。

不够就搬

当栈满，runtime 分配一块更大的新栈，把旧栈内容整体复制过去，更新所有指针——对 G 自身透明。

栈缩容

GC 时回收多余

栈在 GC 周期若发现只用了一小部分，会缩回更小的尺寸，避免长期占用。收缩同样复制内容。

因为可伸缩，Go 鼓励「多开 goroutine、局部变量随便用」；不必像 C 那样纠结栈大小。
逃逸分析

决定变量去哪

编译器分析变量生命周期：若可能逃出函数（如返回指针、被并发引用），就分配到堆；否则留在栈。栈对象随函数返回自动回收，零 GC 成本。

// 逃逸：返回局部变量指针 -> 分配堆
func f() *int { x := 1; return &x }

// 不逃逸：留在栈
func g() int { x := 1; return x }  // x 在栈

// go build -gcflags="-m" 查看逃逸结论
实践建议

减少堆分配

让临时对象留在栈、复用 buffer（sync.Pool）、避免不必要的指针传递，能显著降低 GC 压力。

⚠️ 逃逸分析是编译期启发式，并非百分百；用 -gcflags=-m 验证关键路径，别凭直觉。

goroutine 的栈：从 2KB 开始按需伸缩

操作系统线程栈通常是固定的几 MB，所以「万级线程」不现实。Go 的 goroutine 栈则从 2KB 起步，按需自动增长与收缩，这才是能轻松跑几十万 goroutine 的前提之一。

连续栈的翻倍增长与拷贝
2KB 起步新 goroutine 的初始栈很小，因此创建成本极低。
翻倍增长不够时申请两倍新栈并整体拷贝，均摊成本低。
也会收缩GC 时若栈使用率过低会缩小到一半，回收内存。
1GB 上限64 位下单个栈的上限，超出就是栈溢出。

实践意义：热路径上把变量留在栈上，能同时省掉分配与 GC 两份开销。但这不意味着要刻意扭曲代码——先测量，再优化。

栈相关的三类问题

栈溢出

表现为 goroutine stack exceeds 1000000000-byte limit 后 panic。

  • 最常见原因：无限递归或递归深度未被约束
  • 也可能是结构体极大值传递导致栈暴增
  • 修复：加递归深度上限、改成迭代、大结构体改传指针

栈增长抖动

深调用链恰好卡在边界时，每次调用都触发拷贝。

  • 典型场景：递归解析深层嵌套 JSON
  • 表现为 P99 抖动，但平均耗时正常
  • 缓解：降低单次递归深度、改迭代、给 worker 预热

栈与闭包

闭包捕获变量会让变量逃逸，间接增加堆压力。

  • 循环中启动 goroutine 捕获循环变量是经典陷阱
  • Go 1.22 起循环变量语义已调整，但仍建议显式传参
  • 大对象被闭包长期持有会拖长生命周期

深入自检

为什么 goroutine 能开几十万个，线程不行？

两个层面：内存上，goroutine 栈从 2KB 起且按需伸缩，十万量级也只占几百 MB；而系统线程栈通常固定 MB 级。调度上，goroutine 由 Go 运行时在用户态调度，不经过内核态切换。

栈增长时要拷贝，指针不会失效吗？

会失效，所以运行时在拷贝时会修正栈中的指针指向。能被修正的前提是运行时清楚地知道栈上哪些位置是指针——这依赖编译期生成的栈映射信息。这也是 unsafe 操作受限的原因之一。

栈会无限增长吗？

不会。64 位下默认上限约 1GB，超过会触发栈溢出 panic 而不是无限增长。这个上限可以通过 runtime/debug 的 SetMaxStack 调整，但一般不建议动。

逃逸分析说没逃逸，为什么 pprof 里还有分配？

可能你看的是不同的变量或不同的调用点；也可能是 interface 装箱、闭包、channel 传递导致另一处逃逸。用 -gcflags='-m -m' 逐层看，配合 pprof 的 alloc_space 精确定位到行。

大数组应该放栈还是堆？

一般放堆：几十 KB 以上的数组放栈会迅速逼近栈上限并可能触发拷贝抖动，用 slice 或指针传递更稳妥。判据仍是实测——但默认倾向是把大对象放到堆上并复用。
