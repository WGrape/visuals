01 · 从问题出发

为什么会需要这个模式？

过滤条件支持 AND、OR、字段比较；到处拼字符串会让语义和优先级混乱。

产品允许用户配置筛选规则“年龄大于等于 18 且已激活”。若直接用字符串拼接或 eval，优先级、错误提示和安全边界都难控制。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

interface Expr { interpret(ctx): Boolean }
class And implements Expr {
  constructor(left, right) {
    this.left = left; this.right = right
  }
  interpret(ctx) {
    return this.left.interpret(ctx) && this.right.interpret(ctx)
  }
}
rule = And(GreaterEqual("age", 18), Field("active"))
allowed = rule.interpret(user)

读代码时抓住三件事

  1. 每种语法节点都实现 interpret(ctx)。
  2. And 递归组合子节点结果，可使用短路求值。
  3. 叶子节点负责读取字段并进行类型安全比较。

换个业务场景，还能认出来吗？

权限规则或告警规则若只有少量稳定语法，可用解释器表示。若语言包含大量运算符、作用域和错误恢复，应使用成熟解析器而不是手写越来越多的节点。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

小型稳定规则语言需要解析并组合求值

三个具体场景

  • 用户筛选表达式 AND/OR
  • 简单权限规则与条件告警
  • 计算器的基础表达式树

不适合或要小心

不要把任意用户输入直接 eval。复杂语言的词法、语法、错误处理通常交给成熟解析器。

复杂语言、错误恢复或不可信脚本输入应交给成熟解析器

最容易混淆的相邻模式

模式真正的区别
策略多个算法可替换，通常一次选择一个算法；解释器按语法规则组合许多表达式节点。
组合解释器的语法树可用组合模式建结构，但解释器强调给这些节点定义语义。

落地前检查

  • 绝不对不可信输入直接 eval。
  • 明确定义括号、优先级和类型错误。
  • 为解析错误提供位置与原因，而非静默判假。
06 · 自己说一遍

两道检验理解的小题

它只组合两个 Expr；字段读取由叶子节点负责。

新增 OR 语法只需新增一个节点类吗？

// 40 行可运行的递归下降解释器：支持 + - * / 与括号、优先级正确
type Lexer struct {
	s   string
	pos int
}

func (l *Lexer) next() byte {
	for l.pos < len(l.s) && l.s[l.pos] == ' ' {
		l.pos++ // 跳空白
	}
	if l.pos >= len(l.s) {
		return 0
	}
	c := l.s[l.pos]
	l.pos++
	return c
}

// expr := term { ('+'|'-') term }
func (l *Lexer) expr() int {
	v := l.term()
	for {
		c := l.next()
		if c == '+' {
			v += l.term()
		} else if c == '-' {
			v -= l.term()
		} else {
			l.pos-- // 回退一个字符，交给上层处理
			return v
		}
	}
}

// term := factor { ('*'|'/') factor }   -- 分层即优先级
func (l *Lexer) term() int {
	v := l.factor()
	for {
		c := l.next()
		if c == '*' {
			v *= l.factor()
		} else if c == '/' {
			v /= l.factor()
		} else {
			l.pos--
			return v
		}
	}
}

// factor := number | '(' expr ')'
func (l *Lexer) factor() int {
	c := l.next()
	if c == '(' {
		v := l.expr()
		l.next() // 吃掉 ')'
		return v
	}
	l.pos--
	start := l.pos
	for l.pos < len(l.s) && l.s[l.pos] >= '0' && l.s[l.pos] <= '9' {
		l.pos++
	}
	n, _ := strconv.Atoi(l.s[start:l.pos])
	return n
}

为什么优先级是这样保证的：expr → term → factor 三层嵌套，越靠下的函数调用优先级越高（先被算完）。想加一个优先级，就在中间插一层，不要在一个函数里写分支判断。

第三层 · 解释器模式的六个坑

  • 左递归导致无限递归：expr := expr + term 直接按文法写会栈溢出；必须改写成循环（见上）。
  • 嵌套过深爆栈：用户输入 ((((...)))) 几千层就打穿 goroutine 栈；加深度上限并在超限时返回错误。
  • 错误没有位置信息：只报 syntax error 等于没报；token 要带行/列，报错时给出附近片段。
  • 词法与语法混在一起：一边读字符一边归约，加一个运算符就要改三处；务必先 tokenize 再 parse。
  • 用 eval 执行用户输入：这是注入漏洞，不是解释器模式；解释器是自己定义语义，绝不要把输入交给宿主语言的 eval。
  • 性能没量级概念：递归下降解析是 O(n)，通常在百万行/秒量级；慢一般慢在反复分配 AST 节点，用对象池或边解析边求值缓解。

判断该不该自己写：规则能写在一页纸内就手写，超过一页纸就上生成器。手写解释器的成本随规则数超线性增长。

第四层 · 它和编译、规则引擎的边界在哪

解释器和编译器到底差在哪？

解释器直接对 AST 求值，每次执行都重新遍历；编译器把 AST 先变成字节码/机器码，一次编译多次执行。同一个表达式要跑上万次（比如告警规则对海量数据求值），就该编译或向量化，而不是反复解释。

为什么很多人说这个模式‘用得少’？

因为通用语言（SQL 条件、JSON 查询、正则）已经覆盖了大多数‘需要解释’的场景；只有当业务有自己的领域语法（风控规则、定价公式、筛选表达式）时才值得自己写。

解释器模式带来什么真实代价？

每加一条语法规则就要加一个类/函数，类数量随规则数线性增长；并且调试链路变长（词法 → 语法 → AST → 求值），所以必须分阶段可测试，每段能单独打印中间结果。

一、它长什么样

解释器模式最直观的例子是「四则运算表达式」。文法可以写成三条产生式：

expr := term (('+' | '-') term)* term := factor (('*' | '/') factor)* factor := NUMBER | '(' expr ')' // 表达式 "1 + 2 * (3 - 1)" 建成 AST 后： // '+' // / \ // 1 '*' // / \ // 2 '-' // / \ // 3 1

每条产生式对应一个节点类，节点接口只有一个方法 interpret(ctx)：

type Expr interface{ Eval(ctx Context) int } type Number struct{ v int } func (n Number) Eval(Context) int { return n.v } type Add struct{ l, r Expr } func (a Add) Eval(c Context) int { return a.l.Eval(c) + a.r.Eval(c) } type Mul struct{ l, r Expr } func (m Mul) Eval(c Context) int { return m.l.Eval(c) * m.r.Eval(c) }

二、和它容易混淆的三种做法

做法适用和解释器的区别
解释器模式文法极简、规则稳定、要频繁求值每个语法规则一个类，加规则=加类
解析器 + 求值器（推荐）表达式、JSON、SQL where 这类解析器只负责建 AST，求值逻辑独立，类不会爆炸
嵌入脚本引擎（Lua / JS / CEL）规则需要运行时热更新不改代码就能换规则，最灵活
策略模式 + 配置根本不是语言，只是参数组合没有文法也就没有解释器，别硬套
什么时候不要用它

当你发现「加一条规则要同时改三个类」或者「节点类已经超过 15 个」，说明该换解析器了。《设计模式》原书也明确写了：解释器模式适用于简单的、效率不是关键的文法。

四、深入自检

为什么不直接 eval 字符串？

因为 eval 等价于把解释器交给了攻击者：任意代码执行、无法限流、无法审计、报错不可控。解释器模式的价值恰恰是把可执行范围限定在你定义的文法内。

AST 是解释器模式的一部分吗？

严格说不是。解释器模式的经典写法是把「解析」也塞进类里；工程上更常见的做法是解析与求值分离：先用递归下降/Pratt 解析器产出 AST，再单独遍历 AST 求值。这样加语法只动解析器，加语义只动求值器。

性能差在哪？

每个节点一次虚函数调用，深层表达式是递归调用链；再加上大量小对象分配。优化手段通常是：常量折叠、编译成字节码或闭包树、缓存已编译的表达式对象。

和访问者模式什么关系？

解释器负责「定义文法与求值」，访问者负责「在不改节点类的前提下给节点加新操作」。想给 AST 同时支持「求值」「打印」「类型检查」三种操作，就用访问者。
