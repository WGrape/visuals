OTA升级概述

Over-The-Air 空中下载技术详解

📱

什么是OTA？

OTA（Over-The-Air）即空中下载技术，是通过移动通信网络（2G/3G/4G/5G/WiFi）远程为设备推送软件更新的技术。无需连接电脑或人工干预，设备自动完成升级。

移动端 IoT设备 车载系统
🔄

OTA vs 传统升级

传统方式需要用户手动下载安装包、连接电脑或SD卡刷机。OTA实现远程静默升级，用户无感知，极大降低维护成本。

传统：用户介入 OTA：自动完成
🛡️

安全性要求

OTA升级涉及固件篡改风险，必须采用签名验证机制。设备端校验包签名，服务端使用私钥签名，设备使用公钥验签。

签名算法：AES-256 + RSA-2048

类型 描述 包大小 下载时间 适用场景
整包升级 完整下载新版本APK/固件 大（50MB-500MB） 较长 首次安装、大版本迭代

Step 1: 版本检测

客户端向服务端发送当前版本号，服务端返回最新版本信息及下载URL。常见策略：

  • 主动检测：启动时/定时检测
  • 被动检测：服务端推送检测指令
  • 智能检测：WiFi环境自动检测

Step 2: 下载策略选择

根据网络状况和升级类型选择下载策略：

// 下载策略伪代码
if (wifiConnected && fileSize < 100MB) {
    downloadNow();  // WiFi下立即下载
} else if (cellular) {
    promptUser();   // 蜂窝网络下询问用户
} else {
    scheduleDownload(); // 预约下载
}

Step 3: 断点续传下载

使用HTTP Range请求支持断点续传，网络中断后可从上次位置继续。这是最核心的可靠性保障。

Range: bytes=500-999 / Range: bytes=500-

Step 4-5: 完整性校验

下载完成后进行双重验证：

  • MD5/SHA256校验：验证包完整性，防止传输损坏
  • RSA签名验签：验证包来源可信，防止篡改攻击

Step 6-7: 安装执行

Android使用PackageManager/Intent安装APK；iOS通过MobileCoreServices安装；IoT设备写入对应Flash分区。

Android: Intent.ACTION_VIEW iOS: UIApplication.openURL

Step 8: 回滚机制

升级失败时自动回滚到上一稳定版本。常见策略：

  • A/B双分区：同时保留两个系统版本
  • Recovery模式：独立的恢复系统
  • Bootloader锁：验证启动镜像完整性

HTTP Range 请求头

客户端告诉服务器需要文件的哪个字节范围，支持单段和多段请求。

Range: bytes=0-99        // 前100字节
Range: bytes=500-        // 从500字节到末尾
Range: bytes=0-99, 200-299 // 多段请求
📭

HTTP Content-Range 响应头

服务器返回实际提供的字节范围和文件总大小。

Content-Range: bytes 0-99/1000
// 当前: 0-99，总大小: 1000字节

Content-Length: 100
// 本次响应体长度

Accept-Ranges: bytes
// 服务器声明支持断点续传
🔢

多线程分片下载

将文件分成多个片段，多线程并行下载，充分利用带宽提升速度。

// 4线程分片下载
Thread1: Range: bytes=0-249999
Thread2: Range: bytes=250000-499999
Thread3: Range: bytes=500000-749999
Thread4: Range: bytes=750000-999999

💡 关键点

206 Partial Content：服务器返回206表示支持断点续传，返回200表示从头开始。客户端需要检查响应状态码来判断。

🔒 TCP保证可靠传输的机制

🤝

三次握手建立连接

TCP通过三次握手建立可靠连接，确保双方都准备好数据传输。

Client → Server: SYN (seq=x)
Server → Client: SYN+ACK (seq=y, ack=x+1)
Client → Server: ACK (ack=y+1)

// 连接建立完成，开始传输
📮

确认应答 (ACK)

每个数据包都需要对方确认（ACK），超时未确认会触发重传。

// 累计确认机制
发送: Packet #1 #2 #3
收到: ACK #3  // 表示#3及之前都收到
🔄

超时重传

发送数据后启动定时器，超时未收到ACK则重新发送。

// RTT (Round Trip Time) 动态调整
RTO = RTT + 4 × RTTD
// RTO: 重传超时时间
📊

滑动窗口

流量控制机制，接收方告知发送方可发送的数据量，避免拥塞。

// 窗口大小动态调整
拥塞窗口(cwnd) × 接收窗口(rwnd)
🚦

拥塞控制

慢启动 → 拥塞避免 → 快速重传 → 快速恢复

慢启动 拥塞避免 快速重传 快速恢复

🔐 HTTP vs HTTPS 在OTA中的区别

特性 HTTP HTTPS
加密 ❌ 明文传输 ✅ TLS 1.3 加密
身份认证 ❌ 无 ✅ 证书验证服务端身份
数据完整性 ⚠️ 需额外校验 ✅ MAC校验
防篡改 ❌ 可被中间人修改 ✅ 加密签名防篡改
OTA推荐 ⚠️ 仅内网环境 ✅ 必须使用

⚠️ 安全警告

OTA升级必须使用HTTPS！未加密的HTTP传输可能被中间人攻击，注入恶意固件。建议启用Certificate Pinning（证书锁定）防止DNS劫持。

断点续传与校验：可复制的实现

OTA 的三件事：下载要能续传、刷写要能回滚、结果要能上报。任何一环缺失都会变砖或留下僵尸设备。

续传与校验命令

# 1) HTTP Range 续传（服务端必须支持 Accept-Ranges）
curl -I https://ota.example.com/fw/v2.1.0.bin | grep -i 'accept-ranges\|content-length'
#   看到 accept-ranges: bytes 才支持续传

# 断点续传下载：-C - 表示自动从已下载部分继续
curl -C - -o fw.bin https://ota.example.com/fw/v2.1.0.bin

# 手动指定起点（设备端实现时就是这个逻辑）
curl -H 'Range: bytes=1048576-' -o part.bin https://ota.example.com/fw/v2.1.0.bin
#   服务端应返回 206 Partial Content，而不是 200

# 2) 校验：下载完必须验证，且用强校验
sha256sum fw.bin                       # 与发布时记录的摘要比对
# 设备端还要验证签名（防止伪装固件）
openssl dgst -sha256 -verify pubkey.pem -signature fw.bin.sig fw.bin
机制作用典型取值不做会怎样
Range 请求断点续传分块 1~16 MB弱网环境每次失败都从头下，成功率骤降
ETag / Last-Modified判断固件是否变化内容哈希或 mtime拉取到一半源变了，拼出错误固件
SHA-256 校验完整性32 字节摘要位翻转导致的坏固件被刷入
签名验证来源可信RSA-2048 / ECDSA恶意固件刷入，等于设备被接管
A/B 双分区失败可回滚两份固件分区刷写中断即变砖
版本号单调检查防降级攻击单调递增版本号被回滚到有漏洞的旧版本

设备端流程

# 设备端典型流程（伪代码，体现关键顺序）
1. 上报当前版本 -> 服务端返回 {url, version, size, sha256, signature, min_version}
2. 校验 version > current && version >= min_version      # 防降级
3. 分块下载（Range），每块写入临时分区，记录已下载偏移到非易失存储
4. 下载中断 -> 重启后从记录偏移继续（续传）
5. 下载完成 -> 校验 sha256 -> 校验签名
6. 校验通过 -> 写入备用分区(B) -> 标记待激活
7. 重启 -> bootloader 尝试启动 B 分区
8. 启动成功 -> 上报成功，标记 B 为有效
   启动失败(连续 N 次) -> bootloader 自动回退到 A 分区
失败场景处理策略关键点
下载中断（网络）记录偏移，续传偏移要持久化，掉电不能丢
下载中断（掉电）重启后检查临时文件与偏移未完成的固件不能标记为可刷写
校验失败删除重下，累计次数上限后上报错误不能重试无限次
刷写中断（掉电）bootloader 检测到 B 不完整 -> 回退 A靠 A/B 分区保证
新固件启动失败看门狗 / 启动计数回退 A失败计数要持久化
磁盘空间不足下载前先检查可用空间 ≥ size × 1.2预留临时文件空间
版本回退攻击校验版本号单调性 + 签名版本号校验要在签名保护范围内

最容易踩的坑：把「下载完成」当成「升级完成」。真正的成功标志是新固件启动成功并上报。因此临时状态（已下载、待激活、启动中）必须持久化，否则掉电后设备无法确定自己处于哪一步。

灰度、监控与清单

灰度策略做法适用风险
按设备 ID 哈希分批先 1% → 10% → 50% → 100%大规模设备回滚要能按批次暂停
按区域/型号分批先灰度一个城市/型号硬件差异大覆盖不全
按时间段只在凌晨低峰推影响用户体验的升级进度慢
强制升级窗口到期后强制安全补丁要留「用户可拒绝一次」的口子

监控指标必须包含：成功率、失败原因分布、平均耗时、当前各版本占比、卡在中途的设备数。其中「卡在中途」是最危险的——它意味着设备处于不确定状态。

上线前逐条核对：

  • 服务端必须支持 Range 请求（返回 206），否则续传无从谈起。
  • 下载偏移要持久化，掉电后能接着下。
  • 必须先校验再刷写：SHA-256 验完整，签名验来源，两者都要。
  • 必须支持版本回滚保护：禁止降级到有漏洞的旧版本。
  • 优先用 A/B 分区，这是唯一能在刷写失败时保证不变砖的方案。
  • 下载前检查磁盘空间（≥ 固件大小 × 1.2），并预留临时文件。
  • 状态机要持久化：下载中/待激活/启动中都要能恢复。
  • 必须有灰度与暂停开关：出问题时一键停推。
  • 失败重试要有上限与退避，避免全网设备同时重试打爆服务器。
  • 升级窗口要避开业务高峰，并考虑设备所在时区。
  • 监控要能定位到单设备：只知道成功率无法排查具体故障。
  • 必须做断电测试：在下载中、校验中、刷写中分别断电，验证都能恢复。
