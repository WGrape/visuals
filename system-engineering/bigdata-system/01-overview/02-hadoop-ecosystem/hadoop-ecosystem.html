Hadoop 生态全景

不是数据库：分布式存储 + 资源调度 + 第一代计算引擎的工具集合

核心结论：三个支柱

Hadoop 不是一款软件，而是一套围绕「在廉价机器集群上处理海量数据」这一目标的工具集合。它的内核由三个相互独立的角色构成，理解它们各自负责什么，是看懂整个生态的前提。

🗄️

HDFS（存文件）

分布式文件系统，是整套生态的「硬盘」。它把一个大文件切成若干 128MB 的块（Block），每个块默认保存 3 份副本（Replication=3）分散在不同机架，提供高容错与高吞吐的流式顺序读。它本身不提供随机修改、索引或查询能力。

🧭

YARN（管 CPU/内存）

资源调度器，是整套生态的「操作系统资源管理层」。它把集群的 CPU、内存抽象成统一的资源池，让上层的计算框架（MapReduce / Spark / Flink）按队列申请使用，避免各自为政地抢占机器。详见本站资源调度专页。

⚙️

MapReduce（算数据）

第一代分布式计算引擎，是生态的「老一代 CPU」。它把计算表达为 Map（映射）与 Reduce（归约）两个阶段，自动把任务分发到数据所在的节点上并行执行。如今更多被 Spark 取代，但其「分而治之」思想仍在（见后续计算模型专页）。

一句话类比：HDFS 像一块被切成小块、还自动做了三份备份的超大硬盘；YARN 像集群里的「资源调度员」，谁要用多少 CPU 和内存都向它申请；MapReduce 像一份写死了「先分组、再汇总」的固定计算脚本。

Hadoop 不是数据库

初学者最大的误区是以为「Hadoop = 一个能查询的大数据库」。这是错的。HDFS 只管把文件可靠地存到一堆机器上，它不知道文件里是日志还是图片，也没有表、列、SQL、索引这些概念。所谓「数据库能力」是上层组件在 HDFS 之上「自己叠出来」的。

  • HDFS：只存文件，没有查询、没有索引、没有事务。你不能直接写一条 SELECT 去问它。
  • HBase：把 HDFS 当成自己的「底层磁盘」，在它之上实现了按行键（RowKey）随机读写的 NoSQL 数据库，提供毫秒级点查。
  • Hive：不是数据库，而是数据仓库工具。它把 SQL 解析、翻译成一个个计算任务（早年是 MapReduce，后来可翻译成 Spark），真正的数据仍然是 HDFS 上的文件。
组件本质定位底层存储能否随机查询典型接口
Hadoop(HDFS)分布式文件系统自身即存储否，只有文件读写put/get/流式读
HBaseNoSQL 数据库（列族）运行在 HDFS 之上是，按 RowKey 点查Java API / Shell
Hive数据仓库 / SQL 翻译层HDFS 上的文件离线 SQL 扫描HiveQL（类 SQL）
注意：Hive 元数据（表结构）存在独立的 Metastore（通常用 MySQL）里，实际数据文件躺在 HDFS 上。所以「删了 Hive 表」默认只删元数据，文件还在。

生态组件分类

围绕 HDFS 与 YARN 这两块底座，社区长出了一大批组件。按职责可粗略分成三类：

💾

存储 / 表格式类

HBase（实时 NoSQL）、Hive（离线数仓表）、Hudi / Iceberg（支持 upsert、时间旅行的表格式，解决数据更新难题）。它们最终都把数据落在 HDFS 上，解决「怎么组织、怎么查」的问题。

🚀

计算引擎类

MapReduce（第一代批处理）、Spark（内存迭代、批流一体）、Flink（低延迟流处理）。它们向 YARN 申请资源，读取 HDFS 上的数据做计算，是「干活的」。

🤝

协调 / 支撑类

Zookeeper（分布式协调：选主、配置管理、分布式锁）。它不属于大数据计算本身，却是 HBase、Kafka、甚至 YARN HA 的「地基」。本站分布式系统学科有 Zookeeper 专页，这里不重复展开。

分层架构图

把上面的关系画成一张分层图：最上面是业务应用，中间是各种「叠在底座上的能力」，底座永远是 HDFS（存）与 YARN（管资源）。

从 1.x 到 2.x 的演进

Hadoop 1.x 里，MapReduce 既当「计算引擎」又当「资源调度器」：一个叫 JobTracker 的进程同时负责接受作业、分配资源、监控任务，所有压力集中在单点，集群一大就撑不住。Hadoop 2.x 把「资源管理」单独拆出来，成了 YARN，MapReduce 退化为仅仅一个跑在 YARN 上的应用。点下方按钮切换两种架构对比。

面试问答

Q：为什么说 Hadoop 不是数据库？
A：Hadoop 内核中的 HDFS 只提供分布式文件存储，没有表、列、索引、SQL 查询与事务能力；所谓数据库能力是 HBase（在 HDFS 上做随机读写）和 Hive（把 SQL 翻译成计算任务）等上层组件「叠」出来的。所以 Hadoop 本身更准确叫「分布式存储 + 资源调度 + 计算框架的集合」，而非一个数据库。
Q：HBase 和 Hive 的区别是什么？
A：定位不同。HBase 是 NoSQL 数据库，面向低延迟的按 RowKey 随机读写，适合在线查询；Hive 是数据仓库工具，面向离线批量分析的 SQL 表达，把查询翻译成 MapReduce/Spark 任务扫描 HDFS 文件。一个偏「实时点查」，一个偏「离线分析」，底层都依赖 HDFS。
Q：现在还有必要学 Hadoop 吗？
A：有必要，但要分清学什么。MapReduce 已不是主流计算引擎（被 Spark/Flink 取代），但 HDFS 作为海量数据的存储底座、YARN 作为资源调度范式，仍是大量企业集群的现实基础；Hive、HBase、Spark on YARN 等生态组件都围绕它构建。理解 Hadoop 的存储底座与资源调度思想，是看懂整个大数据生态的钥匙。

一句话理解 HDFS 的设计取舍：默认块 128MB、顺序写、多副本、不支持随机修改。这一切都是为了高吞吐的顺序扫描，代价是不能低延迟随机更新——所以 HBase 才需要 LSM 树来补上点查与更新能力。

常用命令与选型

命令

# HDFS
hdfs dfs -ls /user/data
hdfs dfs -put local.txt /user/data/
hdfs dfs -get /user/data/f.txt ./
hdfs dfs -du -h /user/data                # 看占用（注意副本数会乘上去）
hdfs fsck /user/data -files -blocks       # 检查块健康与副本数
hdfs dfsadmin -report                     # 集群容量报告
hdfs dfs -setrep -w 2 /user/data          # 改副本数

# YARN
yarn application -list
yarn application -kill <appId>
yarn logs -applicationId <appId>          # 看作业日志（排障第一步）

# Hive
hive -e "SHOW PARTITIONS t PARTITION(dt='2026-01-01')"
hive -e "ANALYZE TABLE t PARTITION(dt) COMPUTE STATISTICS"   # 统计信息影响执行计划

# 小文件问题诊断（HDFS 最常见的病）
hdfs dfs -count /user/data                # 文件数 vs 目录数
# 大量远小于 128MB 的文件会拖垮 NameNode（元数据常驻内存）
#   解法：写入端合并（Spark coalesce / 按批 flush）、离线 compaction、或用 Hudi/Iceberg

为什么小文件是 HDFS 的病？

每个文件的元数据（约 150 字节）常驻 NameNode 内存，千万级小文件会撑爆 NameNode；同时每个小文件都要起一个 map task，作业效率极低。

Hive 和 Spark SQL 是什么关系？

Hive 最初是「SQL → MapReduce」的翻译器 + Metastore；Spark SQL 可以直接读 Hive Metastore，只借用它的元数据而用自己的执行引擎——这是当下的常见用法。

副本数 3 是不是浪费？

3 副本 = 3 倍存储成本，换来的是单机架故障下的数据安全与本地性。成本敏感场景可用纠删码（EC，HDFS 3.x 支持），存储降到约 1.5 倍，代价是修复时的计算与网络开销。
