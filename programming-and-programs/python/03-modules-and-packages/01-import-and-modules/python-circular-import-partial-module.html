Python 循环导入：为什么明明定义了函数却报 partially initialized

沿 a.py 与 b.py 的导入顺序画出 sys.modules 状态，给出拆依赖和推迟导入的选择。

报错的关键是执行顺序

有两个模块：a.py 顶部先执行 `from b import helper`，稍后才定义 `def run()`；b.py 顶部又执行 `from a import run`。程序从 import a 开始时，Python 创建 a 模块对象并登记到 sys.modules，然后执行 a 的顶层代码。a 还没走到 `def run()` 就转去加载 b；b 再从 a 取 run，此时 sys.modules 里虽有 a 对象，run 属性却尚未定义，于是出现“partially initialized module”相关错误。文件里确实有 run，不代表它在当前执行时刻已经创建。

Python 这么做是为了避免每次循环导入都无限递归创建新模块。首次导入通常会执行模块顶层代码，后续同名导入利用缓存；但缓存中的对象可能仍处在初始化途中。理解这条时间线，比看到错误就随机移动 import 行更可靠。

图解：循环导入时的部分初始化模块

沿箭头逐步核对输入、变换和输出；下面的推演可以逐步切换。

手推 a 与 b 的状态

第一步，import a，把 a 放入 sys.modules，状态可理解为“执行中”。第二步，a 请求 b，创建并登记 b。第三步，b 请求 a，拿到同一个尚未执行完毕的 a。第四步，b 立刻访问 a.run；由于 a 的定义语句还没执行，访问失败。若把 a 的 run 定义移到导入 b 之前，这个特定例子可能能运行，但双向依赖仍存在，未来添加顶层逻辑后容易再次出错。

`import a` 与 `from a import run` 的取值时点也不同：前者得到模块对象，可稍后通过属性访问；后者在导入语句处就要取出具体属性。不过只改语法未必治本，调用若发生在模块初始化期间仍可能失败。要先画依赖图，标记哪些顶层语句触发了跨模块访问。

逐步推演

import a

创建 a 并登记到 sys.modules。

a 导入 b

b 创建并开始执行顶层代码。

b 访问 a.run

a 尚未执行 def run，属性不存在。

拆依赖

共用定义移到 common 或注入回调。

推荐先拆双向依赖

若 a 是业务服务、b 是工具函数，却让 b 反过来导入 a，多半是职责边界混乱。把双方共用的协议、数据类或纯函数抽到第三个模块 common，使依赖变成 a→common、b→common，而不是 a↔b。若 b 只需要回调，可以把回调函数或接口对象从 a 注入 b，避免 b 在导入时知道 a 的具体实现。

类型注解也可能造成循环导入。只为类型检查需要的导入可放到 TYPE_CHECKING 分支，运行时用前向引用或推迟求值的方式；具体写法要与 Python 版本和注解使用场景匹配。某些运行时框架会读取注解并解析名字，不能假设 TYPE_CHECKING 下的名字在运行时总能找到。

处理办法适合场景边界
抽 common共享协议或纯函数优先消除依赖环
回调注入低层不应依赖高层明确所有权
局部导入罕见路径或可选依赖可能只延后结构问题
TYPE_CHECKING纯类型依赖运行时解析注解仍需核对

局部导入何时合适

把 `from b import helper` 放进真正调用 helper 的函数里，可推迟到两个模块初始化完成后再执行，常可解除启动期循环。这适合可选依赖、罕见路径或为了避免重型库启动成本的场景。但若依赖关系本质上仍是双向，局部导入只是隐藏结构问题；测试和重构可能再次踩到。不要把所有 import 都塞进函数里作为统一修复。

也要检查同名遮蔽：项目文件叫 `json.py`、`typing.py` 或与依赖包同名，可能意外导入自己，报错样子像循环导入。观察 traceback 中实际加载的文件路径，确认模块解析到了预期包。直接运行包内文件与用 `python -m package.module` 启动也可能影响包上下文与绝对/相对导入，应采用一致的启动入口。

重现与定位流程

最小化成两个文件，打印模块顶层语句的执行顺序和 `list(sys.modules)` 中相关名字；不要打印敏感配置或整个模块字典。沿 traceback 找到第一次从 a 进入 b，再找 b 回到 a 的语句，记录此时 a 已定义哪些属性。检查是否有顶层函数调用、装饰器执行、类体求值或单例初始化间接触发另一模块；这些都是导入期间运行的代码。

修复后从全新 Python 进程运行测试，避免交互式环境已缓存模块造成假成功。分别从项目正式入口、测试入口和命令行模块方式启动，核对解析路径与导入图。若通过改变导入顺序才能偶然通过，依赖环仍值得进一步拆除。

常考结论

模块导入是“创建模块对象、放入缓存、执行顶层语句”的过程；函数定义也是执行到定义语句时才绑定名字。`sys.modules` 有某模块，不表示该模块所有属性都已存在。循环导入错误大多由顶层立即取对方尚未绑定的名字触发。解决它通常是重新划清依赖方向，必要时才用局部导入或类型检查专用导入。

自检

sys.modules 中已经有 a，为什么 b 执行 `from a import run` 仍可能失败？

因为 a 的顶层代码尚未执行到 `def run`，缓存中的模块对象还没有这个属性。
