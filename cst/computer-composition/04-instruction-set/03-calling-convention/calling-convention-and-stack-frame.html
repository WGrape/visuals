调用约定与栈帧：函数调用在机器层发生了什么

「函数调用」不是语言特性，而是一套 ABI 约定：参数放哪、返回值放哪、谁负责保存寄存器、栈怎么对齐。搞不清这套约定，就解释不了栈溢出、可变参数崩溃、跨语言调用错位和尾调用优化。

一句话定位：ABI 是编译器之间的合同

调用方（caller）和被调用方（callee）由不同代码、甚至不同编译器生成，必须事先约定参数与返回值的传递位置、寄存器的保存责任、栈的对齐要求。这套约定就是 calling convention，属于 ABI 的一部分。

整数参数rdi, rsi, rdx, rcx, r8, r9（x86-64 SysV）
浮点参数xmm0~xmm7
返回值rax（整数）/ xmm0（浮点）
栈对齐调用前 rsp 必须 16 字节对齐
栈帧布局：call 压返回地址，被调用者再保存 rbp 与寄存器

寄存器谁负责保存

类别寄存器保存责任含义
参数/返回值rdi…r9, rax, xmm0-7调用者假设会被改不用保存
易失（caller-saved）rax, rcx, rdx, rsi, rdi, r8-r11调用者保存callee 可随意用
非易失（callee-saved）rbx, rbp, r12-r15被调用者保存callee 用了必须恢复
栈指针rsp双方维护callee 返回前必须复原
方向标志DF约定为 0字符串指令依赖它
栈对齐不是建议，是硬要求

SysV ABI 规定 call 时 rsp 必须 16 字节对齐。编译器会在 prologue 里 sub rsp, 8 之类的调整来满足它；手写汇编或 JIT 忘了这条，一旦被调用函数用了对齐的 SSE 指令（如 movaps）就会直接段错误。

一个函数的完整生命周期

// C: long f(int a, int b, int c, int d, int e, int f2, int g, int h)
// 前 6 个进寄存器，g/h 走栈

f:
    push  rbp              # 保存旧帧指针（callee-saved）
    mov   rbp, rsp         # 建立新帧
    sub   rsp, 32          # 分配局部空间（保持 16B 对齐）
    mov   [rbp-4], edi     # 参数落栈（如果需要取地址）
    ...
    mov   eax, ...         # 返回值放 rax
    leave                  # mov rsp,rbp; pop rbp
    ret                    # 弹出返回地址并跳转
优化做了什么触发条件
叶子函数省略帧指针不 push rbp，直接用 rsp 寻址不开 -fno-omit-frame-pointer 时默认
尾调用优化复用当前栈帧，call 换成 jmpreturn f(x) 且无后续操作
内联直接展开函数体小函数、hot path
寄存器传参避免压栈参数 ≤ 6 个整数

跨语言/可变参数的两个坑

可变参数函数（printf 类）需要知道「用了几个向量寄存器」，x86-64 用 al 传递这个信息；不设置 al 就可能读到脏的 xmm 寄存器。跨语言调用（C ↔ Go/Rust/Java）则要严格对齐 ABI，包括栈对齐、布尔类型宽度、结构体传值规则——这些细节各语言并不完全一致。

# 手写可变参数调用的正确姿势（x86-64）
mov  eax, 0        # 0 个向量寄存器被使用
call printf

# 常见错误：没设 al，printf 读 xmm0 时拿到脏数据

现象根因怎么查

原理与取舍：为什么不全用寄存器传参

寄存器快，但数量有限且要被 callee 复用。约定「前 N 个走寄存器、其余走栈」是在「调用开销」与「寄存器压力」之间取平衡。x86-64 选 6 个整数寄存器，ARM64 选 8 个——寄存器多的架构可以少压栈，这也是 ARM 在函数调用密集场景略占优的原因之一。

为什么返回地址要压栈而不是放固定寄存器？

因为函数会嵌套调用，返回地址必须按调用顺序保存（后进先出），栈天然满足。放固定寄存器的话，嵌套调用会覆盖。

尾调用优化为什么能省栈？

因为 return f(x) 之后当前帧再无用途，可以直接复用（jmp 而不是 call）。递归写成尾递归 + 开启优化，就不会栈溢出。

结构体传值时到底传什么？

小结构体（≤16 字节）可能被拆进寄存器，大结构体按「隐式指针」传递（调用者分配空间、传地址）。这条规则各 ABI 不同，是跨语言调用最容易错的地方。
