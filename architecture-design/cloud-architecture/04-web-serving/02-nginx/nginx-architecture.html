关键设计说明

🌐 事件驱动模型

NGINX 不使用线程处理每个连接，而是通过 epoll (Linux) / kqueue (BSD/macOS) 等系统调用实现异步 I/O 多路复用。一个 Worker 进程可同时处理数千个连接，内存开销极低。

⚡ 零拷贝 (Zero Copy)

使用 sendfile() 系统调用直接在内核空间将文件数据从磁盘发送到网卡，避免用户态缓冲区的数据拷贝，大幅提升静态文件传输性能。

🔄 热重载机制

Master 进程收到 SIGHUP 后重新读取配置，fork 新 Worker 进程并逐步接管旧连接，旧 Worker 在处理完存量请求后自动退出，实现零停机配置更新。

🧩 模块化设计

NGINX 的核心只负责事件调度和基础框架，所有功能（代理、缓存、压缩、SSL、限流等）都以模块形式挂载。HTTP 处理链由 11 个 Phase 按序执行，各 Phase 可注册多个 handler。

🧠 内存池管理

每个请求创建独立内存池，所有内存从池中分配，请求结束时整体释放。消除了内存碎片和内存泄漏问题，分配开销近似于栈分配。

📊 Slab 分配器

共享内存使用 slab 分配器管理，将内存页按固定大小（8B/16B/32B/...）划分为 slab，避免小块内存的碎片问题。用于共享数据如 limit_req 计数器、SSL session 等。

进程模型与连接处理

进程数量职责特点
Master1 个读取配置、管理 worker、平滑重启以 root 运行
Worker= CPU 核数（默认）实际处理请求以普通用户运行，相互独立
Cache Manager1 个缓存索引管理—
Cache Loader1 个启动时加载缓存—

为什么 worker 数设为 CPU 核数：每个 worker 是单线程事件循环，一个 worker 只能占一个核。多于核数会造成上下文切换浪费；少于核数则浪费 CPU。多核机器上的标准做法是 worker_processes auto;。

进程与连接配置

# nginx.conf 核心配置
worker_processes auto;                  # 自动 = CPU 核数
worker_cpu_affinity auto;               # 绑定 CPU，减少缓存失效（可选）
worker_rlimit_nofile 65535;             # <strong>必须调</strong>，默认 1024 太小

events {
    use epoll;                          # Linux 必用 epoll
    worker_connections 65535;           # 单 worker 最大连接数
    multi_accept on;                    # 一次 accept 多个连接
}

http {
    # 理论最大连接数 = worker_processes × worker_connections
    # 但作为反向代理时，一个客户端连接会占用<strong>两个</strong>连接（上下游各一）
    #   实际并发 ≈ worker_processes × worker_connections / 2
    # 例：8 核 × 65535 / 2 ≈ 26 万（理论值，实际受内存限制）
}

# 系统侧必须同步
#   ulimit -n 65535
#   /etc/security/limits.conf：* soft nofile 65535

最常见的故障：worker_connections are not enough 或 accept 失败。原因是 worker_rlimit_nofile 与系统 ulimit 没调。两者都要改，且 nginx 的 worker_connections 不能超过 worker_rlimit_nofile。

事件驱动模型：为什么能支撑高并发

Nginx 用 epoll + 非阻塞 IO + 事件循环，一个 worker 单线程处理数万连接。

模型连接数 vs 线程数C10K 表现代表
每连接一线程1:1崩溃（内存与切换开销）早期 Apache prefork
线程池N:M有限（池大小封顶）Apache worker
事件驱动N:1轻松支撑Nginx / Node / Redis
  • epoll 的优势：select/poll 每次都要把 fd 集合从用户态拷到内核态并线性扫描（O(n)）；epoll 用红黑树管理 fd、就绪链表返回结果，只返回活跃连接（O(1) 摊销）。
  • 代价：一个 worker 内不能有阻塞操作。任何阻塞（如同步磁盘 IO）会卡住该 worker 上所有连接。

与 Apache 的对比结论：Nginx 在高并发静态资源与反向代理场景优势明显（内存占用低一个数量级）；但动态内容处理需要交给后端（FastCGI/uWSGI 或 upstream）。所以典型架构是 Nginx 做反向代理与静态资源，应用服务器在后。

反向代理与超时配置

指令默认值说明
proxy_connect_timeout60s与上游建立连接的超时，内网可降到 5s
proxy_send_timeout60s发送请求给上游的超时
proxy_read_timeout60s等待上游响应的超时，最常调
proxy_bufferingon缓冲上游响应；流式响应要关掉
keepalive无upstream 里的长连接数，必配
proxy_next_upstreamerror timeout失败时转发到下一台

反向代理配置

upstream backend {
    server 10.0.0.1:8080 max_fails=3 fail_timeout=30s;
    server 10.0.0.2:8080 max_fails=3 fail_timeout=30s;
    keepalive 64;                    # <strong>必须配</strong>，否则每次请求都新建连接
    keepalive_requests 1000;         # 单连接最多复用次数
    keepalive_timeout 60s;
}

server {
    location /api/ {
        proxy_pass http://backend;   # 注意：带 / 会剥离路径前缀，不带则保留
        proxy_http_version 1.1;      # keepalive 需要 HTTP/1.1
        proxy_set_header Connection "";   # 清除 close，启用长连接

        proxy_connect_timeout 5s;
        proxy_read_timeout 30s;      # 按后端 P99 设定
        proxy_send_timeout 30s;

        proxy_next_upstream error timeout http_502;
        proxy_next_upstream_tries 2;
    }
}

流式响应（SSE、大模型流式输出）必须关 proxy_buffering：开启时 Nginx 会攒够缓冲区再发给客户端，导致流式输出变成一次性返回。同时要设 proxy_read_timeout 足够长，否则长连接会被中途断开。

自检 Q&A

Q：proxy_pass 带不带斜杠有什么区别？

A：这是最经典的配置陷阱。proxy_pass http://backend;（不带路径）会把完整 URI 转发；proxy_pass http://backend/;（带路径）会把 location 匹配的部分替换掉。例如 location 是 /api/，请求 /api/user：不带斜杠转发 /api/user，带斜杠转发 /user。混用会导致后端 404，排查时直接看后端收到的 path。

Q：502 和 504 分别说明什么？

A：502 Bad Gateway = 连不上或上游直接拒绝（上游进程挂了、端口不通、连接被拒）；504 Gateway Timeout = 上游超时未响应（上游处理太慢，超过 proxy_read_timeout）。排查方向完全不同：502 查上游是否存活与网络连通性；504 查上游处理耗时与超时配置。看 error_log 里的具体信息：connect() failed 是 502，upstream timed out 是 504。

Q：Nginx 的负载均衡策略有哪些？

A：四种——① 轮询（默认，平均分配）；② weight（按权重，用于机器性能不同）；③ ip_hash（按客户端 IP，实现会话保持，但扩容时会大量重映射）；④ least_conn（发给连接数最少的，长连接场景优于轮询）。商业版还有 least_time。若需要真正的会话保持，更推荐把会话外置到 Redis，而不是依赖 ip_hash。

Q：reload 会导致请求中断吗？

A：不会。Nginx 的热重载是：master 收到 HUP 信号 → 启动新 worker → 新 worker 接新连接，老 worker 处理完存量请求后退出。所以 nginx -s reload 是安全的。但要注意：老 worker 若卡在长连接（如 WebSocket）上不会立即退出，需要 worker_shutdown_timeout 强制（默认无限制，可能残留进程）。
