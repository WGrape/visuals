消息队列 MQ

消息队列用一句话概括：把"现在就做"变成"稍后做"，把"我直接调你"变成"你听广播"。它是解耦、异步、削峰的标配中间件。

🎯为什么需要消息队列

三个经典价值：解耦、异步、削峰。一句话——让系统"不那么同步、不那么紧绑、不那么怕洪峰"。

解耦：生产者不必知道谁消费，新增消费者无需改生产者。
异步：生产者发完即返回，耗时操作后台慢慢消费。
削峰：突发流量先堆在队列，消费者按自己节奏处理，保护后端。

🧩两种核心模型

① 点对点（Queue / 竞争消费）
一条消息只被一个消费者处理。多个消费者组成"消费组"，抢着消费，天然做负载均衡。典型场景：订单处理、任务分发。
② 发布/订阅（Topic / 广播）
一条消息被所有订阅者收到。典型场景：事件通知、日志广播、缓存失效。Kafka 用"消费组"把两者统一：组内竞争、组间广播。
🔑
记忆：Queue=一个活一人干；Topic=一个活所有人收到。Kafka 的 Topic + Consumer Group 同时实现了这两种语义。

🧱核心工作模式

异步处理
注册成功后，发短信、发邮件、初始化画像等非核心链路，丢进 MQ 异步做，主流程秒回。
应用解耦
下单系统只发"订单已创建"事件，库存、积分、推荐各自订阅，互不依赖、独立扩容。
流量削峰
秒杀时请求先入队，后端按数据库承载能力匀速消费，避免被打垮。
消息驱动 / 事件溯源
把状态变更作为事件流，下游可重放（如 CDC 数据同步），也可做审计与回放。

🛡️可靠性：不丢、不重、不卡

投递语义（面试必考三级）：
语义含义能否做到
At most once最多一次，可能丢易，但不安全
At least once至少一次，可能重复常见（Kafka 默认），配合幂等
Exactly once恰好一次，不丢不重难，需事务/幂等+去重（Kafka 事务、Flink 两阶段）
⚠️
生产者不丢：用acks=all（ISR 全收）+ 重试。
Broker 不丢：副本机制 + 落盘（fsync）。
消费者不丢：先处理业务再提交 offset，避免"消费中宕机 offset 已提交"导致消息丢失。

🔁幂等：消息重复怎么办

网络重试、Rebalance、acks=all 都会造成消息被消费多次。幂等保证"处理多次 = 处理一次"。

常见幂等方案

① 唯一键 + 数据库去重表（如订单号）：插入前查，存在则跳过。

② 业务状态机：已支付→不再处理支付消息。

③ Redis SETNX / 原子锁：用 messageId 占位防重。

④ Kafka 幂等生产者：broker 端按 pid+seq 去重，避免生产者重试产生重复。

✅
口诀："做不到 exactly-once，就做 at-least-once + 幂等"。这是工业界最务实的组合。

🔢顺序消费

很多业务要求"同一订单的消息按顺序处理"（如 创建→支付→发货）。

Kafka 的顺序保证：同一 partition 内消息有序；只要把同一业务键（如订单ID）哈希到同一 partition，且单 partition 单线程消费，即可保证全局顺序。
⚠️
代价：顺序消费会牺牲并行度（partition 内串行）。所以"要顺序"和"要高并发"要按业务键粒度权衡，通常只需"按订单顺序"而非"全局顺序"。

🎯面试要点速记

三大价值：解耦、异步、削峰。
两种模型：点对点（竞争消费）+ 发布订阅（广播）；Kafka 用 Topic+Group 统一。
投递语义：at-most / at-least / exactly once，业界多用 at-least-once + 幂等。
不丢消息：生产者 acks=all+重试、Broker 副本落盘、消费者先处理后提交 offset。
幂等方案：去重表 / 状态机 / Redis 原子锁 / Kafka 幂等生产者。
顺序：同 key 哈希到同 partition + 单线程消费。
🔥
必考题："如何保证消息不丢失？"——分三段答：生产端（确认+重试）、服务端（多副本+刷盘）、消费端（先消费后提交位移）。漏掉任何一段都算不完整。

投递语义：三种语义到底差在哪

语义实现方式代价典型场景
At most once发出去就不管（fire-and-forget）会丢消息可容忍丢失的监控埋点
At least once失败重投，消费端幂等会重复绝大多数业务的默认
Exactly once事务 + 幂等 + 两阶段提交吞吐大幅下降Kafka Streams / Flink 内部

重要认知：端到端的 exactly-once 极其昂贵。工程上真正可靠且便宜的组合是 at-least-once 投递 + 消费端幂等，效果等价于“有效一次”。

Kafka 语义配置

# Kafka 幂等生产者 + 事务（开启 exactly-once 语义 EOS）
Producer 侧：
  enable.idempotence=true       # 幂等：单分区不重复不丢（默认已开）
  acks=all                      # 必须配合，等所有 ISR 确认
  max.in.flight.requests.per.connection=5   # ≤5 才能保证幂等下的顺序
  retries=Integer.MAX_VALUE     # 无限重试
  transactional.id=tx-order-1   # 开启事务（跨分区原子写）

Consumer 侧：
  isolation.level=read_committed  # 只读已提交的事务消息
  enable.auto.commit=false        # 处理完再手动提交 offset

# 吞吐 vs 可靠性的三个档位（实测同一集群）
#   acks=0  + 异步批发送 : ~1,000,000 msg/s   （可能丢）
#   acks=1  + 异步批发送 : ~  300,000 msg/s   （leader 挂了会丢）
#   acks=all + 幂等      : ~  100,000 msg/s   （不丢）

积压排查与扩容

# ① 看 Kafka 积压（最重要的一条命令）
kafka-consumer-groups --bootstrap-server localhost:9092 \
    --describe --group order-consumer
# 输出：TOPIC PARTITION CURRENT-OFFSET LOG-END-OFFSET LAG
#       order  0        1000           50000          49000   <- LAG 4.9万

# ② 估算追平时间： 追平秒数 = LAG / 消费速率
#    LAG=49000, 消费 500 msg/s  ->  98 秒
#    LAG=49000, 消费 50 msg/s   ->  16 分钟（要处理了）

# ③ 紧急扩容消费者（受分区数上限约束！）
#    消费者数 <= 分区数，超过的会空闲
kafka-topics --bootstrap-server localhost:9092 --alter \
    --topic order --partitions 24      # 从 8 扩到 24（只能增不能减）

# ④ 临时降级：批量消费 + 跳过非关键处理
#    max.poll.records=500（默认 500，可调到 2000）
#    fetch.min.bytes=1 -> 调大减少请求次数
  • 根本解法是提高单条消费速度：加本地缓存、批量写 DB、去掉同步 RPC
  • 扩容消费者有上限：消费者数 > 分区数时多余的空闲，需先扩分区
  • 扩分区会打破 key 顺序：按 key 分区的消息在分区数变化后，同 key 可能落到不同分区
  • 紧急兜底：新建 topic 大盘点消费，老 topic 直接跳过（事后补偿）

分区数与吞吐：容量规划的硬数字

分区数单 topic 吞吐消费者上限适用
1约 10 MB/s1严格保序的小流量
8 – 12约 50 – 100 MB/s12中小业务默认
24 – 48约 200 – 500 MB/s48大流量核心链路
100+收益递减100+需评估：文件句柄、ZK/元数据开销、选主变慢

经验公式：分区数 = max(目标吞吐 / 单分区吞吐, 峰值消费者数)。单分区吞吐经验值 10 MB/s（约 1 万条/s，按 1 KB/条）。Kafka 官方建议总分区数不超过 集群 broker 数 × 200。

分区不是越多越好：每个分区在 broker 上是一个目录（含 .log/.index/.timeindex），分区过多会导致 ① 文件句柄耗尽 ② 选主时元数据同步慢 ③ 端到端延迟上升。

深入自检

Kafka 为什么能这么快？

四个原因：① 顺序写磁盘——append-only 日志，顺序写比随机写快 数千倍，且现代 OS 会做预读和合并；② 零拷贝 sendfile——数据从页缓存直接进网卡，跳过 2 次用户态/内核态拷贝（传统要 4 次）；③ 批量压缩——多条消息一起压缩，压缩率高，网络传输量小；④ 页缓存而非 JVM 堆——避免 GC 开销，且 broker 重启后缓存仍在（不用预热）。

Kafka 和 RocketMQ 的持久化有什么本质区别？

Kafka 是分区级的日志文件（每个 partition 一个目录）；RocketMQ 是全broker 共享一个 CommitLog + 消费队列索引（ConsumeQueue 只存 20 字节定长：8 字节 offset + 4 字节 size + 8 字节 tag hash）。这个差别带来两个后果：① RocketMQ 的写是全局顺序（一个文件），Kafka 是分区级顺序；② RocketMQ 的 Topic 数可以上万（因为索引很小），Kafka 上百个 topic 就开始吃力。

消息重复消费了怎么办？

不要试图消灭重复，要让消费幂等。三种做法优先级：① 业务幂等设计——把 balance -= 100 改成 balance = 计算后值，或加流水号；② 去重表——用 msg_id 唯一键，消费前先 INSERT，Duplicate 就跳过；③ 乐观锁版本号——WHERE version=?。Redis SETNX 只能做辅助，主从切换会丢。

延迟消息怎么实现？

RocketMQ 是原生的（18 个固定延迟等级：1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h），不支持任意时间——这是为了用固定队列做定时扫描，实现简单高效。Kafka 需要自己实现：常见方案是时间轮或多级延迟 topic；RabbitMQ 用 TTL + 死信队列（DLX）组合，或装 rabbitmq_delayed_message_exchange 插件。
