QPS 到底能扛多少？一套可复现的评估方法

一个峰值数字不等于可持续容量。目标是找出：在约定请求组成和成功率、P99、资源余量都达标时，系统能长期完成多少有效工作。

先限定测试对象与权限

仅在明确授权的自有或隔离环境中评估；第三方 API 的公开文档限额不是压测许可。本课只介绍观察与判断方法，不发起负载、不提供对外站点的压测脚本。提前定义保护阈值、持续时间和可回滚方案，避免波及真实用户及共享依赖。

第一步：冻结口径与工作负载

  1. 明确评估对象：单机/集群、具体接口或业务事务、缓存冷热比例、请求体与响应体大小、依赖版本和环境配置；混合负载按真实流量比例构造。
  2. 区分客户端尝试发送、网关已准入、服务已完成、业务成功的速率。QPS 的分子和统计窗口写清楚；把重试的每次发送计入尝试次数。
  3. 定义服务目标，例如成功率 ≥ 99%、端到端 P99 ≤ 300ms，并注明窗口和失败/超时是否纳入延迟样本。只筛成功请求算 P99 会掩盖慢失败。

第二步：按负载模型施加渐进压力

闭环模型

固定虚拟用户或固定在途并发，上一请求完成后再发送。适合模拟等待结果才继续的客户端；系统变慢时发送速率也会下降，可能掩盖真实到达压力。

开环模型

按预设到达速率提交，尽量与上一请求是否完成无关。更易观察高于处理能力时的等待与拒绝，但负载生成器自身也必须有界、可停。

每一档有预热、稳定观察窗口和恢复间隔；先校验压测端不会成为瓶颈，再小步提高负载。突然把客户端并发数直接调到供应商声明的服务并发上限，不是容量评估。

第三步：同时记录四类证据

有效产出

完成/成功 QPS、业务 TPS、失败与拒绝（429/5xx）数；吞吐量口径必须与开始时一致。

用户体验

客户端端到端 RT 的 P50/P95/P99，超时和取消单列；再拆分网关等待、业务处理与依赖等待。

在途与积压

客户端待发、连接池等待、网关队列、业务 active 的平均/高水位。统计边界须与延迟对应。

资源与依赖

CPU、IO、网络、内存、工作池和数据库连接占用；源站限速与外部服务错误也可能先成为限制。

理解 并发测量边界 和 分位数，再解读这些指标的变化。

第四步：把“上限”定义为满足 SLO 的可持续工作点

可持续有效 QPS ≠ 最大发送 QPS ≠ 短时最大完成 QPS

例如仅作示意：低档尝试 50 次/秒时成功 50 次/秒、P99=120ms；下一档尝试 100 次/秒时成功约 99 次/秒、P99=240ms；再升至 150 次/秒，成功率下降、P99 达 1,600ms，队列持续增长。若目标是成功率 ≥ 99%、P99 ≤ 300ms，则第三档显然不合格；第二档是否可作为长期工作点，还要看观察窗口够长、依赖稳定、资源余量足够。不要把本示例当作真实系统压测结果。

若到达持续大于完成，未完成量会积累或被拒绝。Little 定律不能替代容量测试；C/W 也只有在特定稳定条件下才是规划上界。

停止、复盘与复验

  1. 任一档触发预设的错误率、尾延迟、持续积压或资源阈值就停止增压；不要靠压垮服务来寻找“极限”。
  2. 定位最先失守的是发送端、网络、账号限额、网关、应用 CPU/IO、数据库还是其它依赖。记录配置、版本、数据量与原始指标窗口。
  3. 优化后在同样口径、同样请求混合下复验；为生产规划保留故障和流量突刺余量，不以测试环境峰值直接承诺 SLA。

跨域案例：Reader 文档中的并发描述与 RPM 限额只能用于理解约束层次，不能作为未经授权的上游压测目标。
