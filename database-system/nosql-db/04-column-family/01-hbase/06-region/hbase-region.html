🧩 HBase Region 与分片

Region 是什么、如何分裂与合并、预分区、热点与负载均衡

Region 是什么

Region 是 HBase 最小的负载均衡与分布式单位：一张表按 rowkey 的字典序范围被横向切成多个 Region，每个 Region 负责一段连续的 rowkey 区间，在任一时刻只由一台 RegionServer 服务。

Region = 行区间[startKey, endKey)，全局有序、互不重叠
Store = 列族一个 Region 内含多个 Store，每个 Store 对应一个列族
RegionServer一台机器承载几十~几百个 Region
分裂阈值默认单 Region 达 10GB 自动 split

Region 的一生

  • 诞生：create 表时按预分区规则（或默认 1 个）创建 Region，由 HMaster 分配到某台 RS
  • 服务：承接该 rowkey 区间的所有读写
  • 分裂 Split：任一 Store 大小超 max.filesize（默认 10GB）→ 找中点 rowkey → 切成两个子 Region
  • 迁移 Move：HMaster 负载均衡器（默认每 5 分钟）按 RS 的 Region 数把子 Region 搬匀
  • 合并 Merge：删除大量数据后可手动 merge 相邻小 Region（HBase 2.x 支持）
  • 下线：disable/drop 表，或 RS 宕机后被重新分配

    • Split 的细节

    • 触发单位是 Region 内单个 Store（列族），但分裂是整个 Region 一起切。
    • 找 split point：选该 Region 中最大的 Store，取它的中间 rowkey（尽量让两边数据量均衡）。
    • 子 Region 不立刻拷贝数据，而是创建 reference 文件指向父 HFile 的一半；等下一次 compaction 时才真正裂开成独立文件。
    • Split 期间父 Region 短暂下线（毫秒~秒级），客户端会重试。
    • Split 后本地性下降：子 Region 可能被搬到别的机器，compaction 后逐渐恢复。

    预分区（Pre-splitting）

    新表默认只有 1 个 Region —— 所有写入打在一台机器上，直到 10GB 才分裂。这段时间是纯粹的热点。预分区在建表时就把 Region 切好。

    // 方式一：手动指定 split key
create 't', 'cf', SPLITS => ['10', '20', '30', '40', '50', '60', '70', '80', '90']

// 方式二：按十六进制自动切（配合 hash 前缀 rowkey）
create 't', 'cf', { NUMREGIONS => 16, SPLITALGO => 'HexStringSplit' }

// 方式三：均匀字节切分（DecimalStringSplit / UniformSplit）
create 't', 'cf', { NUMREGIONS => 10, SPLITALGO => 'UniformSplit' }

// 方式四：从文件读 split key
create 't', 'cf', SPLITS_FILE => '/tmp/splits.txt'
    💡 预分区数量估算：Region 数 ≈ 预计总数据量 ÷ 单 Region 目标大小。例如预计 1TB、希望每个 Region 10GB → 约 100 个 Region，再按集群节点数取整（如 10 节点 → 每节点 10 个）。

    Region 数量：健康的区间

    单 RS 的 Region 数评价说明
    < 10偏少资源没摊开，扩容收益低
    20 ~ 200健康官方推荐区间
    200 ~ 500偏多MemStore 摊薄、flush 频繁，需要调参
    > 1000病态小文件爆炸、compaction 风暴、Master 负担重

    Region 过多的根源通常是：max.filesize 太小 + 没预分区导致反复 split + 列族过多。对策：调大 max.filesize（20~50GB）、建表预分区、减少列族、必要时手动 merge 小 Region。

    热点（Hotspotting）

    Region 分布不均不叫热点，写入集中在一个 Region 才叫热点。典型成因：

    ① 单调递增 rowkey

    如 timestamp、自增 ID 做 rowkey。新数据永远落在最后一个 Region，那台机器被打爆，其他机器闲着。

    解：加 hash 前缀（MD5(key).substring(0,2) + key）或反转（reverse(timestamp)）。

    ② 业务天然倾斜

    如按 userId 做 rowkey，某几个大客户的写入量是普通用户的千倍。

    解：给大客户单独加盐（userId + random(0~N)）打散到多个 Region。

    // 三种打散热点的 rowkey 方案
// A. 加盐 Salting：前缀随机
rowkey = (userId.hashCode() % 16) + "_" + userId + "_" + ts

// B. Hash 前缀：均匀但丢失有序性（scan 会散到所有 Region）
rowkey = MD5(userId).substring(0, 4) + "_" + userId

// C. 反转：保序变「倒序」，适合时间戳
rowkey = reverse(String.valueOf(Long.MAX_VALUE - timestamp))

    负载均衡

    • HMaster 的 SimpleLoadBalancer 默认每 5 分钟（hbase.balancer.period）运行一次。
    • 依据：让各 RS 承载的 Region 数量尽量相等（默认按数量，不是按数据量）。
    • 可开关：balance_switch true/false（滚动重启集群时要先关掉）。
    • 高级：StochasticLoadBalancer（默认实际使用）综合 Region 数、读写请求数、本地性、MemStore 大小做代价函数计算。
    • 多租户隔离用 RSGroup：把 RS 分组，表绑定到指定组。

    🎯 常见问法与答题要点

    Q：Region 和 Store 什么关系？

    A：Region 是按 rowkey 范围的水平切分；Store 是 Region 内按列族的垂直切分。所以：一张表 → N 个 Region → 每个 Region 内含 M 个 Store（M = 列族数）→ 每个 Store = 1 个 MemStore + 若干个 HFile。分裂是 Region 级别的（整个 Region 一起切），但触发条件是 Region 内某个 Store 的大小超阈值。

    Q：为什么不建议用自增 ID 或时间戳直接当 rowkey？

    A：因为 rowkey 字典序全局有序，单调递增的 key 会让所有新写入都落在最后一个 Region，那台 RegionServer 被打爆而其他机器空闲，完全丧失分布式的意义——这就是经典热点。解决方案：加 hash/salt 前缀打散、反转时间戳、或把业务维度提前（如 userId + ts 而非 ts + userId）。

    Q：Region 越多越好吗？

    A：不是，有个甜蜜点（单台 RS 20~200 个）。太少则资源摊不开；太多则：①MemStore 被摊薄，每个都很小却各自触发 flush，产生海量小文件；②compaction 次数剧增；③HMaster 维护与 ZK 压力增大；④一次 RS 宕机要恢复的 Region 太多，恢复变慢。

    Q：预分区该切多少个 Region？

    A：公式：Region 数 ≈ 预计总数据量 ÷ 单 Region 目标大小，再对节点数取整。例：预计 2TB、希望单 Region 20GB → 100 个 Region；若集群 10 台 → 每台 10 个。另外要考虑写入并发度：Region 太少会成为写入瓶颈。注意别过度——切太多会产生一堆空 Region。

    Q：Split 会影响线上读写吗？

    A：会有秒级抖动。Split 期间父 Region 会短暂下线（先把 Region 标记为 splitting、关闭、创建两个子 Region 再上线），这期间对该区间的请求会失败并被客户端重试。另外 split 后子 Region 可能被搬到别的机器，数据本地性变差，读要走网络，直到后续 compaction 才恢复。所以生产上要避免频繁 split——预分区 + 调大 max.filesize。

    Q：Region 分裂后数据是怎么分的？会立刻拷贝吗？

    A：不会立刻拷贝。子 Region 先创建 reference 文件，它记录了「父 HFile 的某一半范围」，读取时通过 reference 去读父文件。真正的物理拆分发生在下一次 compaction 时。这样设计避免了 split 时的大规模数据拷贝，让它变成近乎瞬时的元数据操作。

    Q：怎么判断集群有没有 Region 热点？

    A：看三个地方：①HBase Master UI / status 'detailed' 看各 RS 的 Region 数是否均衡；②各 RS 的 请求数（readRequestsCount / writeRequestsCount）——Region 数均衡但请求数差很多，说明有热点；③监控各 RS 的 CPU/IO。请求数差异大时，去查写入最集中的那批 rowkey 前缀，基本就是 rowkey 设计问题。

    Q：能不能手动移动或合并 Region？

    A：能。移动：move 'ENCODED_REGION_NAME', 'SERVER_NAME' 或 balancer 触发均衡。合并（HBase 2.x+）：merge_region 'r1','r2'（需先 offline）。合并主要用于大量删除数据后清理碎片小 Region。注意手动操作前建议先 balance_switch false 关掉自动均衡，避免打架。
