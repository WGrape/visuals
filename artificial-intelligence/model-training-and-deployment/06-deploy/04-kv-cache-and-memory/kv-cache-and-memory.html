KV Cache 与推理显存

把显存账算清楚：KV Cache 的精确估算公式、MHA/GQA/MQA 的差异、前缀共享与分页管理如何消灭碎片，以及容量不够时按收益排序的三个杠杆。

KV Cache 到底占多少显存

Decode 阶段每生成一个 token，都要把历史上所有 token 的 Key / Value 重新参与注意力计算。 缓存下来就不用重算，代价是显存随 batch × 序列长度 × 层数 × KV 头数 × head_dim 线性增长。

# 每个 token 的 KV 显存（bytes）
per_token = 2(K 和 V) × n_layers × n_kv_heads × head_dim × dtype_size

# 例：32 层、GQA 8 个 KV 头、head_dim=128、fp16(2 bytes)
per_token = 2 × 32 × 8 × 128 × 2 = 131072 bytes ≈ 128 KB / token

# 一条 8K 上下文的请求：8192 × 128KB ≈ 1 GB
# 并发 32 条：≈ 32 GB —— 已经超过一张 A100 80G 的一半
这是大模型服务显存墙的根源：并发数和上下文长度不能同时要。 很多"OOM"事故不是模型太大，而是KV Cache 吃掉了剩下的显存。
MHA
每个 Q 头配一个 K 头一个 V 头，KV 最大
GQA
一组 Q 头共享一个 KV 头，压缩 4~8 倍，质量几乎不掉
MQA
所有 Q 头共享 1 个 KV 头，压缩最大，长文质量略降

四条压缩路线

前缀共享（Prefix Caching / Automatic Prefix Cache）在两类场景收益最大： ① 所有请求共享一段很长的 system prompt；② 多轮对话的历史部分不变，只追加新一轮。 命中时该段 prefill 直接跳过，TTFT 明显下降。

碎片：为什么"还剩 30% 显存"却分配失败

朴素做法是为每条请求预留一块最大长度的连续显存（比如 max_seq_len=8192 全预留）。 实际用多少不确定，于是产生两类浪费：

内部碎片
请求只用了 800 token，却占着 8192 的坑，剩下的谁也用不了
外部碎片
不同请求反复申请释放后，空闲显存被切成小块，凑不出一整段连续的

容量估算：一问就能算出要几张卡

显存总需求 ≈ 模型权重 + KV Cache + 激活值 + 框架开销

1) 权重：    参数量 × dtype 字节
             7B × fp16(2B) = 14 GB
             7B × int4(0.5B) ≈ 3.5 GB

2) KV Cache：并发数 × 平均上下文 × per_token
             32 × 4096 × 128KB ≈ 16 GB

3) 激活与框架：经验值 1~3 GB（与 batch、实现相关）

7B + fp16 + 32 并发 4K 上下文 ≈ 14 + 16 + 2 ≈ 32 GB  → 单卡 A100 40G 够，L4 24G 不够
调容量时的三个杠杆（按收益排序）： ① 降 KV 单 token 成本——开 fp8 KV、用 GQA 模型； ② 降并发或上下文——限流、截断历史、开启前缀共享； ③ 降权重——量化（见本学科「模型量化」章节）。 先量出来到底是哪一项占大头，再动对应的杠杆。
上面的公式是量级估算，不是精确值。不同框架的实现（是否用 PagedAttention、 是否共享前缀、激活是否重算）会差出 20%~40%。上线前用真实流量压测，以实测为准。
