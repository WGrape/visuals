视频检索：从自然语言找到正确片段

视频切段、跨模态向量、近邻召回和时间重排组成完整链路。

学完能解释什么

  • 区分视频级检索与片段级时间定位
  • 解释文本/视频嵌入对齐及向量索引的作用
  • 用 Recall@K 与时间定位指标评估检索质量

逐步看机制

建立有时间边界的候选段

按镜头或固定时长分段，记录起止时间；过长会稀释短事件，过短会丢失上下文。

检索“哪段”比找“哪部”更难

查询“人关上红色的门”时，视频级向量也许找到含有门的长视频，但用户需要事件发生的几秒。切段粒度决定覆盖与上下文：短窗口易漏掉动作因果，长窗口则让相关片段在平均特征中变弱。候选必须带来源、起止时间和采样策略，才能把命中结果定位回原视频。

召回、排序和定位是三个任务

双编码器把文本和视频片段分别映射到向量，适合大规模召回；近似最近邻 ANN 可降查询成本，但不是“更准确”的保证。交叉编码或更细粒度的帧—词匹配可重排前 K 个候选，计算更贵。若查询需要“先拿钥匙再开门”，必须保留事件顺序；只平均所有帧的静态图像向量可能找错时段。

评估不只看一个相似度

Recall@K 衡量正确视频或片段是否出现在前 K 个结果；片段级结果还要按时间区间 IoU 或相关性标注评价是否定位准确。建立硬负例：同一个人“开门”和“关门”、同一场景不同时间，才能测试模型学到动作而非背景。

日志和索引需处理视频删除、版权和敏感人脸；片段嵌入也可能泄露内容信息，不能把它当匿名数据。

自检

为什么视频级 Recall@1 高仍不足以证明片段检索可用？

它只说明找对视频，不保证找对视频中的时间位置；还需要片段级标注和时间定位评估。

怎么把视频变成一个向量

① 抽帧

视频不能直接整段输入。做法：均匀采样若干帧（8~32 帧），或用关键帧抽取（镜头切换处）。采样策略直接影响效果——均匀采样可能漏掉关键瞬间。

② 帧级编码

用预训练图像编码器（通常是 CLIP 的视觉塔）把每帧编码成向量，得到一组帧向量。

③ 时序聚合

把帧向量聚合成一个视频向量。方法从简到繁：平均池化（简单但丢时序）、时序注意力（学权重）、Transformer 聚合（建模帧间关系）、分段聚合（先段内后段间）。

④ 对齐训练

用对比学习（类似 CLIP）训练：让「视频向量」与「对应文本向量」距离近，与不相关文本距离远。这是整个系统效果的关键。

视频级 vs 片段级（时刻定位）

粒度输出技术要点应用
视频级返回相关视频列表整段编码成一个向量，标准向量检索视频库搜索、推荐
片段级 / 时刻定位返回视频 + 起止时间需编码多粒度片段或做时序回归「找出他说话的那 10 秒」、精彩片段剪辑
帧级精确到帧逐帧向量 + 序列匹配以图搜帧、版权取证

工程要点

库规模百万级视频 × 每段多向量 → 亿级向量，必须上 ANN 索引
多向量策略一个视频存多个片段向量，召回更准但库更大
混合检索向量 + 关键词（标题/ASR 字幕/标签）混合，召回更好
过滤按时间、来源、权限过滤，注意 HNSW + 过滤的性能问题
更新新增视频要增量入库；换模型必须全量重建

深入自检

视频检索和图像检索有什么不同？

多了一个时间维度，带来三个额外问题：①视频不是一个向量——一段视频包含若干帧甚至若干镜头，怎么聚合成一个（或一组）向量是关键设计；②查询粒度——用户可能想找整段视频，也可能只想找视频里的某几秒，后者需要片段级索引与时刻定位；③数据量——视频的向量条目远多于图片（若按片段存，一个视频可能产生几十条向量），对向量库规模和检索性能要求高。

为什么视频检索大多基于 CLIP？

因为 CLIP 已经把图像和文本对齐到了同一个语义空间，这为跨模态检索提供了现成的起点。视频检索的做法通常是「复用 CLIP 的视觉塔做帧编码 + 文本塔做查询编码」，只需要额外学习时序聚合和视频-文本对齐即可，训练成本远低于从零学一个视频-文本双塔。这就是为什么 CLIP4Clip、VideoCLIP 这类方法能在较小数据上取得不错效果。当然，专门的视频-文本预训练模型（如 InternVideo）效果会更好。

把视频编码成一个向量，还是多个向量？

看需求与成本。单向量：整段聚合成一个向量，库小、检索快，但长视频里只有一小段相关时容易被稀释，且无法定位到具体时间段。多向量：按镜头/时间窗切成多个片段各存一个向量，召回更准、还能返回具体时间段，代价是库规模放大几十倍和检索时要做聚合。折中做法：两级检索——先用视频级向量快速筛出候选视频，再在候选内做片段级精排定位时间。

用户搜「穿红衣服的人摔倒」，为什么常常搜不准？

这类查询包含多个语义要素（主体、属性、动作）且有组合关系，是视频检索的典型难点。原因：①向量是整体的——一个向量要把「红衣」「人」「摔倒」三个概念压在一起，容易顾此失彼；②属性与动作难对齐——模型可能匹配到「摔倒」却忽略颜色；③训练数据的描述往往简单，模型没学好复杂组合。改进方向：用更强的多模态大模型做编码、做属性解耦（分别编码后在检索时组合）、用混合检索补上文本侧的属性词、以及加 Rerank 做精细匹配。

检索结果里时间定位不准怎么办？

片段级检索（时刻定位）的边界往往不够准，常见改进：①多尺度片段——同时索引 2 秒、5 秒、10 秒的窗口，检索后取交集或投票；②先召回后精修——先找到大致区间，再在该区间附近用更小步长滑动窗口精确定位；③边界回归——在检索模型上加一个边界回归头，直接预测起止时间；④后处理平滑——对相邻片段的分数做平滑，避免边界抖动。

视频检索系统怎么评估？

核心指标是 Recall@K（前 K 个结果里有没有包含正确视频）和 Median Rank（正确结果的中位排名）；片段级检索还要看 t IoU（预测时间段与真实时间段的交并比）以及 R@K, IoU=m 这类联合指标（既要求召回又要求定位准）。工程上还要测查询延迟 P99、入库吞吐和库容量。评估集要按查询类型（简单名词 / 复杂描述 / 动作 / 属性组合）分开统计，否则总体数字会掩盖短板。

检索范式对照

范式代表模型核心机制代价
双塔（Dual Encoder）CLIP 类、VideoCLIP视频/文本独立编码后算相似度可预计算，检索快，交互弱
单塔/交叉编码CLIP4Clip（部分）帧与文本一起进模型精度高，无法预计算，只适合重排
多模态 LLMVideo-LLaVA 类视频转 token 进 LLM理解强，推理贵
帧聚合均值池化/时序 Transformer多帧特征聚合成单一向量折中方案，最常用

工业界标准架构：双塔召回 + 交叉编码重排。双塔把全库视频预先编码成向量建索引（可服务百万级），交叉编码器只对召回的 top-100 做精细打分。直接对全库跑交叉编码是不可行的——复杂度是 O(库大小)。

编码与检索

# 视频检索的典型流水线（伪代码）
import torch

def encode_video(path, model, preprocess, num_frames=16):
    frames = sample_uniform(path, num_frames)   # 均匀抽 16 帧
    x = torch.stack([preprocess(f) for f in frames]).cuda()  # [T, C, H, W]
    with torch.no_grad(), torch.autocast("cuda"):
        feats = model.encode_image(x)            # [T, D]
        feats = feats / feats.norm(dim=-1, keepdim=True)
    return feats.mean(0)                         # 均值池化 → [D]

def encode_text(q, model):
    t = model.encode_text(tokenize([q]).cuda())
    return t / t.norm(dim=-1, keepdim=True)

评估指标与常见失效

指标含义说明
R@K前 K 个结果含正确项的比例K 常取 1/5/10，最常用
Median Rank正确结果排名中位数越小越好，理想为 1
mAP多正样本场景的平均精度一个查询对应多段相关视频时用
nDCG考虑相关性等级有分级标注时用

常见失效模式：

  • 只匹配静态画面：模型靠单帧就能答对，说明没学到时序信息。检测方法——把视频帧随机打乱再测，若指标几乎不掉，说明时序建模形同虚设。
  • 长视频稀释：固定抽 16 帧时，10 分钟视频每帧间隔 37 秒，关键动作大概率被跳过。长视频应先做镜头分割，再按镜头检索。
  • 文本侧过拟合评测集：在 MSR-VTT 上高分的模型换到自建业务集可能崩，因描述风格差异大。务必在自己的查询分布上复测。

自检 Q&A

Q：视频检索该抽多少帧？

A：取决于视频时长与动作密度。经验：短视频（< 30 秒）抽 8~12 帧足够；长视频必须先切镜头再在每个镜头内抽 4~8 帧。盲目加大帧数收益递减——从 16 帧到 32 帧通常只涨 1~2 个点 R@1，但计算翻倍。

Q：为什么文本检索视频比视频检索文本难？

A：因为查询和候选的粒度不对称。文本查询往往只描述片段（“一个人打开车门”），而候选是整个视频。解决办法是视频也切片——把长视频切成片段分别编码，检索粒度从“整段视频”变成“片段”，R@1 通常能提升 10 个点以上。

Q：双塔模型的相似度分数能直接当置信度用吗？

A：不能跨查询比较。CLIP 类模型的相似度绝对值没有校准——不同查询的分数分布差异很大（“红色汽车”和“一个关于友谊的故事”天然不在同一量纲）。要做阈值判定，需要在自己的数据上标定，或用相对排序（top1 与 top2 的差值）作为置信信号。

Q：如何支持“找所有出现某人的片段”这类查询？

A：纯语义检索做不了——需要实体级索引。做法是在入库时并行抽取结构化标签（人脸 ID、OCR 文本、ASR 字幕、物体类别），检索时走混合检索：结构化条件先过滤出候选（如 “person_id = X”），再在候选集内做语义排序。这与向量库的 payload 过滤是同一套思路。
