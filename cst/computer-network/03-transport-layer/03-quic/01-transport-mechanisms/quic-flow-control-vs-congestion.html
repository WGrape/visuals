QUIC 流量控制与拥塞控制：多个流如何共享一条连接

用两个下载流解释流级额度、连接级额度、拥塞窗口和丢包后的不同限制。

三种限制作用于不同范围

QUIC 可在一条连接中并行运行多个流。流级流量控制限制某一流最多能让接收端暂存多少未消费数据；连接级流量控制限制全部流的总体接收缓冲；拥塞控制约束整条连接向网络注入的在途数据。前两者保护接收方资源，后者保护路径和其他流量。若只看到“流发不动”，必须找出究竟是谁的额度耗尽。

假设流 A 是大型图片、流 B 是小型 HTML 片段。A 的应用消费慢，流级额度耗尽时 A 暂停；B 只要还有自身和连接级额度，仍可继续交付。若连接级额度被所有流占满，B 也可能受影响；若拥塞窗口因丢包缩小，所有流共享的发包预算都会变少。独立流避免 TCP 字节流层的队头阻塞，却不承诺彼此完全没有资源竞争。

一次数值算例

接收方给连接级额度 100 KiB，流 A 额度 80 KiB，流 B 额度 40 KiB。若 A 已收到 80 KiB 而应用未读取，A 的流级额度用完；B 已收到 10 KiB，连接合计 90 KiB，还可在 B 上接收约 10 KiB，尽管 B 自己额度尚余 30 KiB。若应用先读取 A 的 60 KiB，接收方可通过更新流和连接额度让发送方继续发。数字仅用于说明上限配合，真实协议通告的是随消费推进的绝对偏移。

如果此时拥塞窗口只允许 20 KiB 在途，而已有 18 KiB 未确认，发送方即使获得新的接收额度，也只能再注入约 2 KiB，直到确认到来。流控更新与 ACK 是不同信号；把接收额度变大却没有吞吐提升，可能是路径拥塞而非接收方问题。

逐步推演

流 A 消费慢

A 的流级额度先用完。

连接还剩空间

B 继续交付，直到连接级额度用完。

接收端读取

MAX_STREAM_DATA/MAX_DATA 更新可发送偏移。

网络丢包

拥塞窗口下降，两个流共享发包预算。

丢包发生在哪里

QUIC 数据放在加密包中，包丢失后可在新包中重新发送相应流数据或控制信息。流 A 的某个偏移区间缺失，A 在该缺口之后的数据暂不能按序交给应用，但流 B 已完整收到的数据可独立交付。包丢失还会让连接的拥塞控制更新在途预算，因此 B 的后续传输速度仍可能下降。

HTTP/3 也要遵守自己的请求和响应语义。某个 HTML 请求依赖另一资源的结果时，应用层仍可能等待；传输层消除一个阻塞原因，不等于页面渲染依赖完全消失。抓包时由于 QUIC 加密，通常需端点日志与协议统计才能看到流和窗口细节。

MAX_DATA 与 MAX_STREAM_DATA

QUIC 用类似 MAX_DATA 的帧更新连接级可接收数据量，用 MAX_STREAM_DATA 更新单个流的额度。发送方不能越过接收方通告的最大偏移。若接收应用处理慢，额度不前进，发送方会被流控阻塞；继续盲目增加发送缓存不会解决接收应用的瓶颈。接收方通告较大额度可减少频繁更新，却也会占用更多缓冲空间。

每个流还涉及创建数量等限制，不只是字节额度。若客户端想并行开太多流，可能碰到并发流数上限；服务端可依据内存和业务容量配置。分析时分别看连接级字节、流级字节、允许流数和拥塞状态。

与 TCP 的比较

TCP 基于单个有序字节流，一处丢失会暂时阻塞后续字节交付给上层，即使 HTTP/2 已把它们分成不同逻辑流。QUIC 在传输层识别独立流，因此只让有缺口的流等待按序交付。另一方面，TCP 与 QUIC 都需要拥塞控制和接收端流量控制，也都受链路带宽与 RTT 限制。QUIC 不是“没有窗口”的 UDP 应用。

同一 QUIC 连接共享一套拥塞控制，某些场景下把大型下载与低延迟请求放在同一连接，仍需注意调度公平性。不同实现可有不同优先级策略，业务应在实际网络条件下测响应延迟。

排障和验收

记录连接 RTT、丢包、拥塞窗口或发送速率、连接级阻塞时间、各流级阻塞时间、接收应用读取速率。若 A 停滞但 B 正常，先查 A 的流级额度与应用消费；若 A、B 同时停，查连接级额度与拥塞状态；若切换网络后停，查路径验证与迁移。用受控的慢消费者和丢包实验分别复现，验证两种根因的指标差异。

性能评估别只看总吞吐。对交互流关注 P95/P99 完成时间，对大流关注持续速率，并记录在不同接收缓冲设置和丢包率下的变化。

流控 vs 拥塞控制：一句话分清

维度流控 Flow Control拥塞控制 Congestion Control
保护对象接收方不被发送方淹没网络不被大家一起压垮
由谁通告接收方通过 MAX_DATA / MAX_STREAM_DATA 帧告知额度发送方自己根据丢包/RTT 估算 cwnd
粒度QUIC 是双层：连接级 + 每条流级连接级（整条 QUIC 连接一个 cwnd）
触顶后果发送方停发，报 STREAM_DATA_BLOCKED / DATA_BLOCKEDcwnd 减小，发送速率下降
对应 TCP 概念rwnd（接收窗口）cwnd（拥塞窗口）
能否关掉可调大额度，不能关可换算法（CUBIC/BBR），不能关

两者同时起作用：实际可发送量 = min(流控额度剩余, cwnd)。很多“QUIC 很慢”的锅其实在流控额度没及时调大，而不是拥塞控制。

QUIC 帧方向作用对应 TCP
MAX_DATA接收 → 发送提高连接级总发送额度窗口通告 win
MAX_STREAM_DATA接收 → 发送提高单条流的发送额度无（TCP 只有连接级）
DATA_BLOCKED发送 → 接收告知“我被连接级额度卡住了”无
STREAM_DATA_BLOCKED发送 → 接收告知“我被流级额度卡住了”无
MAX_STREAMS接收 → 发送允许对端开多少条流无

curl --http3-only -o /dev/null -w "h3 http=%{http_version} t=%{time_total}s speed=%{speed_download}B/s\n" https://example.com/big
curl --http2     -o /dev/null -w "h2 http=%{http_version} t=%{time_total}s speed=%{speed_download}B/s\n" https://example.com/big

# Nginx 侧相关配置
# http3_max_field_size 4k;        # 头部字段上限
# http3_stream_buffer_size 64k;   # 单流缓冲（影响流控额度消费速度）
# quic_retry on;                  # 抗放大攻击的地址验证
  • 最常见的 QUIC 性能坑：接收方应用层读得慢 → 流控额度长期不抬高 → 发送方被 STREAM_DATA_BLOCKED 卡死。表现是吞吐上不去但抓包看不到丢包。
  • 多流不等于更快：所有流共享同一条连接的 cwnd，开 100 条流只是公平分配这一个 cwnd，并不会凭空增加带宽。
  • 小额度 + 高 RTT = 停等：如果流控额度小于 BDP（带宽×RTT），发送方会“发一点就停”，吞吐严重受限。跨洋链路务必把初始额度调到 BDP 的 2 倍以上。
  • 与 HTTP/2 的对比：HTTP/2 的多路复用在 TCP 上会因丢包全连接阻塞；HTTP/3 每条流独立，弱网（1% 丢包）下 h3 通常显著优于 h2。
  • 排障抓手：抓包看有没有大量 STREAM_DATA_BLOCKED / DATA_BLOCKED（流控问题）；有大量 ACK 触发的重传（拥塞问题）。
为什么 QUIC 要分连接级和流级两层流控？

防止某一条流吃光整条连接的接收缓冲，导致其它流饿死（这是 HTTP/2 + TCP 的痛点之一）。两层额度让接收方能精确控制每条流的资源占用。

把流控额度调到无限大行不行？

技术上可以设很大值，但那等于放弃对接收方内存的保护——发送方可以瞬间塞满接收缓冲造成 OOM。正确做法是按实际消费速度动态抬高额度。

自检

流 A 被流级流量控制阻塞，流 B 一定也被阻塞吗？

不一定。若 B 自身和连接级额度仍有余量，且拥塞窗口允许，它可以继续传输。
