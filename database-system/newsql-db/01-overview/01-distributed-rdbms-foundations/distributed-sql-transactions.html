分布式 SQL 事务：协调、复制与提交

一条 SQL 跨多个分片时，原子提交和副本持久化解决的是两类不同问题。

核心机制

跨分片事务需要让所有参与分片对同一提交结果达成一致。常见实现有预写/准备阶段、提交记录和故障恢复逻辑；具体协议因产品而异。

副本共识负责一个分片内部的有序复制与故障切换。它不能单独保证多个分片的事务原子性；协调提交也不能替代每个分片的持久化。

用一个例子看过程

转账：A 所在分片扣 100；B 所在分片加 100。
目标：两项都提交，或两项都不对外生效。

读取并锁定

确认事务读取的版本和写入冲突，避免并发交易覆盖或重复扣款。

协调提交

参与分片完成必要的准备和持久化后，形成可恢复的提交决定。

故障恢复

协调者或节点重启后，依据持久记录继续提交或清理，而不是猜测结果。

观察、原因与处理

观察原因或含义处理与验证
跨分片变慢网络往返与锁等待增加观察事务涉及的分片数和冲突
提交结果未知客户端在应答前断线用幂等键或事务状态查询确认
副本可用但交易卡住分片间协调仍在等待检查协调状态与参与者日志

副本确认与事务提交各管什么

副本协议维护一个分片内的日志顺序和持久化；跨分片事务保证 A、B 等多个参与者对外呈现一个共同结果。转账时，A 分片可能已把“扣 100”的写入意图复制给多数副本，但在全局提交决定生效前，其他事务不能只看到扣款而看不到 B 的入账。实际系统会组合 MVCC、锁、意图记录、事务记录或时间戳，产品细节并不相同。

协调者宕机后，参与者应依据持久记录继续推进或恢复，不能凭内存状态猜结果。若客户端在提交响应前断线，交易可能已提交、也可能尚未提交；“超时”不是“回滚”的同义词。业务层应使用幂等键和状态查询，确保重试不会重复扣款。

一笔转账的故障时间线

阶段需要确认的状态故障时表现
读取和写入意图快照版本、冲突与锁并发交易等待或重试
参与者准备各分片有可恢复记录跨分片延迟增加
形成提交决定共同提交状态与时间戳断线后客户端结果未知
清理与恢复残余意图、锁和重试状态故障恢复后局部请求卡住

压测不能只看成功率，还要记录涉及分片数、提交 P95/P99、冲突重试率和未知结果比例。故障演练覆盖参与者重启、协调者重启、网络分区与客户端断线，并检查“总余额不变”等业务不变量。

性能取舍与练习

单分片事务通常少走协调路径。若订单、余额与库存经常按同一业务键更新，可评估数据亲和布局，减少跨分片比例；同时注意热点分片和容量倾斜。不要为了减少一次网络往返，把必须原子更新的两项改成无保护的独立写入。

练习：转账请求超时后，请写出“已提交但应答丢失”和“未提交”两种可能状态，并设计使用同一个业务幂等键的重试流程。只根据超时提示直接再发一次扣款是危险的。

边界与误区

不同产品对隔离级别、时间戳分配、并行提交和重试的语义不同；不要把某一产品的 2PC 路径当作全部 NewSQL 的统一实现。

隔离级别与应用重试

原子提交解决“两项要么都生效”，隔离级别处理“并发事务彼此能看到什么”。两个转账同时读取余额 100、都打算扣 80，即便每笔交易内部都原子提交，若没有合适的冲突检测或序列化约束，也可能破坏余额不为负的业务不变量。实现可能让其中一笔等待、失败或自动重试；应用必须知道重试会不会重放外部副作用，例如发送短信或调用支付网关。

长事务持有锁或旧版本更久，可能加大冲突、阻塞清理与放大存储。把用户交互或慢外部 API 放在数据库事务中尤其危险。可把事务缩小到必要读写，并在外部效果上使用业务幂等键与补偿流程。数据亲和布局可减少跨分片，但不能取代正确的并发控制。

阅读具体 NewSQL 产品文档时应逐项核对：默认隔离级别、客户端重试契约、事务超时、跨地域提交路径、只读事务语义以及故障后的未决事务恢复方式。“支持分布式事务”本身不足以回答这些问题。

如何追踪一次未决交易

给每笔业务请求分配稳定的幂等键和追踪 ID，日志记录事务开始、涉及的分片、提交尝试、最终决定及客户端应答。若客户端超时，先按键查询已提交结果；没有结果时再按产品支持的语义安全重试。服务端也要避免把数据库自动重试与外部副作用混在同一个不可分辨的闭包中：事务重放一次，发送短信或调用支付接口可能执行两次。故障演练可故意在提交前、提交后应答前断开连接，核对最终余额和外部效果各只发生一次。

进一步验证

还要验证唯一约束和外键等数据库约束在跨分片场景下的实际支持范围。业务若依赖“同一幂等键只存在一条订单”，应把键设计成可被数据库可靠约束或用明确的冲突处理流程。没有持久约束，应用进程重启后仅靠内存去重无法防止重复交易。

自检

Raft 已复制 A 分片的扣款，是否意味着转账事务已提交？

不意味着。B 分片和跨分片提交决定仍须满足该数据库的事务协议。
