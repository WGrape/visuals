01GOMAXPROCS 与容器陷阱

GOMAXPROCS 决定并行执行的 OS 线程上限（P 的数量）。在容器里若没设 GOMAXPROCS，Go 会按宿主物理核数初始化，可能远超容器 CPU quota，导致大量时间片争抢与 throttling。用 uber 的 automaxprocs 自动对齐。

# 启动前设（容器里强烈建议）
export GOMAXPROCS=4
go run main.go

# Go 1.25+ 已内置自动按 cgroup 限额设 GOMAXPROCS；老版本引入：
import _ "go.uber.org/automaxprocs"   # 自动设成 cgroup CPU quota

# 运行时也能改
runtime.GOMAXPROCS(4)

02怎么观测调度

  • GODEBUG=schedtrace=1000：每 1 秒打印调度器摘要（gomaxprocs、idle、runqueue 长度）。
  • GODEBUG=schedtrace=1000,scheddetail=1：再展开每个 P 的本地队列。
  • runtime.NumGoroutine()：实时 goroutine 数，暴涨常意味泄漏。
  • pprof：goroutine / threadcreate profile 看阻塞点。
GODEBUG=schedtrace=1000 ./app
# 输出示例：
# SCHED 1000ms: gomaxprocs=4 idleprocs=1 threads=8 spinningthreads=1 \
#   idlethreads=3 runqueue=3 [2 0 1 0]  <- 方括号内是各 P 的本地运行队列长度
# runqueue 长期很大 => 生产者远快于消费者，需限流或加 worker

03常见阻塞与排查

syscall 会占用一个 M（P 被解开去找别的 M），大量阻塞 syscall 会耗尽线程；GC STW 与 mark 阶段也会暂停所有 G。用 go tool trace 看时间线最准。

# 生成 trace（运行时开启）
import "runtime/trace"
f, _ := os.Create("trace.out")
trace.Start(f); defer trace.Stop()
// 复现负载后退出，用浏览器打开看 G/M 阻塞、GC、syscall 时间线
go tool trace trace.out

# 常见信号
# - Syscall 占比高 => 减少阻塞系统调用，或挪到专用 worker
# - GC 频繁/STW 长 => 降分配、调 GOGC、看 heap profile

第一层 · 概念与判定：GMP 是什么，何时看调度

G（goroutine）、M（内核线程）、P（处理器上下文，持有可运行 G 的本地队列）。关注调度通常因为协程暴涨、P 不够用、或 syscall 把 M 占死。

现象怀疑点
goroutine 数只涨不跌泄漏 / 没 cancel
CPU 用不满GOMAXPROCS 偏小或被限
syscall 卡顿传染M 被阻塞、P 被 handoff
延迟毛刺GC 抢占 / 偷 G

Go 调度观测：GOMAXPROCS 与 schedtrace

# 查看/限制并行度
GOMAXPROCS=4 ./app                 # 只用到 4 个 P
go env -w GOMAXPROCS=...           # 一般不设，让 runtime 定

# 周期性打印调度器状态（每 1000ms）
GODEBUG=schedtrace=1000 ./app
# 输出示例: sched: gomaxprocs=8 idleprocs=2 threads=12 spinningthreads=1 ...

# 代码里看协程数
n := runtime.NumGoroutine()
runtime.GOMAXPROCS(0)              // 读当前值

数量级：每 P 本地可运行队列约 256 个 G，超出才进全局队列；sysmon 每约 20us 醒来一次做抢占扫描，长循环（>10ms）会被强制让出。

第三层 · 排障与边界：五个坑

  • 容器里 GOMAXPROCS 读错：默认按宿主可见核数，容器 cgroup 只给 2 核却开 64 个 P，线程争抢、上下文切换暴涨——用 automaxprocs 或显式设
  • syscall 阻塞整条 M：阻塞式系统调用会把 M 占住，runtime 只能新开 M 顶上，M 数飙升
  • goroutine 泄漏：channel 没人收 / context 没 cancel，NumGoroutine 单调上升直到 OOM
  • 全局队列争用：本地队列打满后全挤全局队列，成了锁热点
  • 误以为加 P 就快：P 超过物理核只是增加切换，真瓶颈在 IO 或锁时加 P 无效

第四层 · 原理与取舍

为什么容器里 GOMAXPROCS 常常要手动对齐 cgroup？

因为 Go 默认用 runtime.NumCPU() 看宿主机的核数，而容器靠 cgroup 限额（比如 2 核）。宿主 64 核时 Go 会开 64 个 P，但容器只拿到 2 核的调度时间，于是大量 P 互相抢、上下文切换和调度开销反而拖慢。让 GOMAXPROCS 等于 cgroup 限额（automaxprocs 自动读）才能跑满又不内耗。

sysmon 和 work-stealing 分别解决什么？

sysmon 是 runtime 的后台监控 M：周期性扫描，对运行过久的 G 做异步抢占（避免一个死循环饿死全 P）、触发 GC、把陷入 syscall 的 P 重新 handoff 出去；work-stealing 则是负载均衡：某 P 本地队列空了，就从别的 P 或全局队列『偷』一半 G 来跑，避免有的 P 忙死有的闲死。

为什么 Go 能在用户态轻松调度百万 goroutine？

因为调度单位是 G，切换在用户态（G-M-P 模型），不进内核、不换页表；G 初始栈仅 2KB 且动态增长，百万 G 内存也才约 2GB。对比 OS 线程 8MB 栈 + 内核调度，开几千就到内存/切换上限。代价是碰到阻塞 syscall 时 M 被占，需要 runtime 额外开 M 兜底。
