网络轮询器（Netpoller）

Go 用 netpoller（基于 epoll/kqueue/iocp）把网络 IO 变成非阻塞，并与 GMP 调度协作：goroutine 在 IO 等待时让出线程，就绪后再被唤醒。

概述

让海量连接变廉价

传统「一连接一线程」在十万连接下内存与上下文切换爆炸。Go 用事件驱动 + 轻量 G，单机支撑海量连接。

事件驱动模型

底层是 epoll

netpoller 封装了各平台的 IO 多路复用（Linux epoll、macOS kqueue、Windows iocp），只用一个系统线程监听大量 fd。

// 伪流程
for { evs := epoll.Wait()
  for ev in evs {
    g := findG(ev.fd)
    injectG(g)  // 把对应 G 放回可运行队列
  }
}
G 在 IO 等待时让出

不占操作系统线程

当 goroutine 做网络读写而被阻塞，runtime 把它从 M 上摘下（park），M 转去跑别的 G；此时 OS 线程并不被这次 IO 占用。

这正是 Go 高并发的基石：少量 OS 线程靠 netpoller 调度海量 G，既非「一连接一线程」，也非「全异步回调地狱」。
就绪后唤醒

IO 完成再继续

netpoller 收到可读/可写事件，找到等待该 fd 的 G，把它重新入队，由调度器择机执行，从阻塞点继续。

与 channel 阻塞的区别

channel/锁阻塞由 runtime 直接调度；网络 IO 阻塞经由 netpoller 事件唤醒，二者都让 G 让出 M，但唤醒来源不同。

对比传统模型

为何更省

一连接一线程：内存随连接线性涨；回调模型：逻辑碎片化。Go 模型：连接数 ↑ 只增 G（很小），阻塞成本低。

⚠️ 但 netpoller 只覆盖网络/定时器类 IO；磁盘文件 IO 在某些平台仍会占用线程（runtime 用专门线程池兜底）。

为什么 Go 能「一个连接一个 goroutine」

传统的线程池模型里，一个连接占用一个线程，连接多了线程就爆了。Go 的做法是：把阻塞式写法编译成非阻塞实现——你写的是同步代码，底下由 netpoller 在 I/O 未就绪时把 goroutine 挂起，就绪后再唤醒。

netpoller：写的是同步，跑的是异步
非阻塞 fd网络 fd 默认设为非阻塞，读不到就返回 EAGAIN。
gopark / goready未就绪时挂起 goroutine，就绪后重新入队执行。
M 不阻塞挂起后工作线程立刻去跑别的 goroutine。
与 GMP 协作网络 I/O 不占用额外线程，靠调度器复用。

哪些 I/O 走 netpoller，哪些不走

场景是否走 netpoller说明
网络 socket是标准库 net 包统一接入，自动非阻塞
管道、终端（可设置非阻塞）部分能被设为非阻塞的可接入
本地文件读写否文件 I/O 不支持非阻塞语义，会占用一个 M
cgo 调用否会占用 M，且不计入 GOMAXPROCS 限制
syscall 阻塞否占用 M，可能导致运行时新建线程
time.Sleep否走定时器，不占 M

这解释了两个常见现象：一是磁盘 I/O 密集的服务会看到线程数上涨（因为文件读写不复用 M）；二是 cgo 调用多的服务线程数远大于 GOMAXPROCS。这些都属于正常行为，不是泄漏。

超时与死锁：netpoller 相关的典型坑

忘记设超时

没有超时，连接会一直挂着，goroutine 永不退出。

// 反例：任何超时都没有 conn, _ := net.Dial("tcp", addr) conn.Read(buf) // 对端不发包就永久挂起 // 正例：Deadline + 上层 context conn.SetDeadline(time.Now().Add(3 * time.Second)) conn.SetReadDeadline(time.Now().Add(3 * time.Second)) conn.SetWriteDeadline(time.Now().Add(3 * time.Second))

goroutine 泄漏

每个连接一个 goroutine 的模型下，泄漏会随连接数线性堆积。

  • 读写循环必须有退出条件（ctx.Done）
  • 关闭连接时确保两侧都被唤醒
  • 用 runtime.NumGoroutine 做基线监控

阻塞在 cgo

cgo 调用会占住 M，堆积时线程数暴涨。

  • 给 cgo 调用设超时或改异步
  • 监控线程数（不是 goroutine 数）发现异常
  • 必要时限制并发 cgo 调用数

深入自检

既然是异步的，为什么我的代码写起来像阻塞的？

这正是设计目标：netpoller 把异步复杂度藏在运行时里，业务侧保持同步写法。代价是你需要理解「挂起」这件事——例如忘记设超时，goroutine 就会永远停在那里。

netpoller 会用掉额外的线程吗？

通常不需要专门的轮询线程。轮询由 sysmon 后台线程或暂时空闲的 M 承担，就绪事件通过 goready 把 goroutine 放回运行队列。因此网络 I/O 密集时线程数仍然接近 GOMAXPROCS。

为什么文件 I/O 不能像网络一样复用？

文件描述符在语义上总是「就绪」的，非阻塞标志对普通文件无效。因此文件读写会真正占用一个 M；大量并发文件操作时运行时会新建线程，这是预期行为。

连接数到几万会不会有问题？

单纯的连接数通常不是瓶颈，每个 goroutine 只占 2KB 起。真正容易出问题的是：每个连接都配套若干 goroutine、缓冲区、定时器，导致内存与调度开销成倍放大。要关注的是总资源而非连接数本身。

怎么确认服务有没有 goroutine 泄漏？

三步：持续采集 runtime.NumGoroutine 看趋势是否只增不回；用 pprof 的 goroutine profile 看堆积在哪个调用栈；检查该栈是否缺少 ctx 退出分支或超时设置。

netpoller 让「同步写法」获得「异步性能」：你写的是 conn.Read(buf) 这种阻塞式代码，但 Go 运行时在底层做了三件事：① 把 fd 注册到 epoll；② 把 goroutine 挂起（不占 OS 线程）；③ epoll 就绪时唤醒对应的 goroutine。这就是 Go 能轻松支撑数十万连接的根本原因。

验证代码

// Go 的同步写法，底层是异步的
func handle(conn net.Conn) {
    buf := make([]byte, 1024)
    n, err := conn.Read(buf)      // 看起来阻塞，实际不占 OS 线程
    if err != nil { return }
    conn.Write(buf[:n])
}

// 起 10 万个连接，OS 线程数远小于 10 万
for i := 0; i < 100000; i++ {
    c, _ := net.Dial("tcp", addr)
    go handle(c)                   // 每个连接一个 goroutine，几 KB 栈
}
// 用 ps -o nlwp <pid> 看线程数，通常只有几十个
// 手动用 epoll（理解 netpoller 的原理）
import "golang.org/x/sys/unix"

epfd, _ := unix.EpollCreate1(unix.EPOLL_CLOEXEC)
unix.EpollCtl(epfd, unix.EPOLL_CTL_ADD, fd,
    &unix.EpollEvent{Events: unix.EPOLLIN | unix.EPOLLET, Fd: int32(fd)})
// EPOLLET = 边缘触发：只在状态变化时通知一次

events := make([]unix.EpollEvent, 128)
for {
    n, err := unix.EpollWait(epfd, events, -1)   // -1 = 无限等待
    if err != nil && err == unix.EINTR { continue }
    for i := 0; i < n; i++ {
        fd := int(events[i].Fd)
        if events[i].Events&unix.EPOLLIN != 0 {
            // 边缘触发必须<b>循环读到 EAGAIN</b>！
            for {
                n, err := unix.Read(fd, buf)
                if n > 0 { handleData(buf[:n]); continue }
                if err == unix.EAGAIN { break }    // 读完了
                // 其他错误：关闭连接
                unix.Close(fd); break
            }
        }
    }
}
// ET 模式下如果只读一次就返回，剩余数据不会再触发事件 -> 数据「卡住」

Go 与 Node.js 的区别：两者都是事件驱动，但 Node 是显式回调（回调地狱），Go 是同步写法 + 运行时调度。Go 的 goroutine 让异步代码看起来像同步代码，可读性和错误处理都好得多，这是 Go 在网络服务领域的核心优势。
