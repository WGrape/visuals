优化级别

-O0 到 -O3 分别做了什么

级别含义调试性典型用途
-O0不优化，直接翻译最好，变量与源码一一对应开发调试
-O1基础优化，不含耗时分析较好追求编译速度
-O2启用绝大多数优化变量可能被消除/重排生产默认
-O3再加激进优化（激进内联、循环展开）差计算密集场景
-Os优化体积而非速度—嵌入式、分发体积敏感
为什么开了 -O2 断点会「跳」？优化会重排、内联、消除变量，源码行与机器指令不再一一对应；调试时变量可能显示为 optimized out。所以调试构建用 -O0 -g。
优化范围

三种优化范围

🔍
局部优化 Peephole
只在基本块内，看相邻几条指令；如常量折叠、强度削弱
🌐
全局优化
跨基本块、整个函数内做数据流与控制流分析
🔗
过程间优化 IPO
跨函数甚至跨模块（LTO），如跨模块内联、全程序分析
LTO（Link Time Optimization）把优化推迟到链接期，此时能看到全部模块，可做跨文件内联与死代码消除。代价是链接变慢、内存占用高。

边界

优化不能跨越的边界

所有优化的前提是语义保持：不能改变程序的「可观察行为」。以下几类会限制优化：

🧵
并发与内存模型
多线程下不能随意重排读写；需遵循语言的内存模型与屏障语义
⚡
volatile / 原子
声明为 volatile 或原子操作的访问不能被消除或重排
🎭
别名分析限制
无法确定两个指针是否指向同一内存时，只能保守处理
🐛
未定义行为 UB
编译器可假设 UB 不发生，据此做激进优化——这是很多「诡异 bug」的根源
UB 的杀伤力：C/C++ 里有符号整数溢出是未定义行为。编译器可假设它永不发生，从而删掉相关的溢出检查分支——结果就是「明明写了判断却不生效」。这类问题只在开启优化后出现。
面试问答

高频问题

Q1：-O2 和 -O3 有什么区别？为什么生产不一定用 -O3？
-O3 在 -O2 基础上增加更激进的内联与循环展开等。-O3 可能显著增大代码体积，反而降低指令缓存命中率；对分支密集、内存访问密集的程序收益有限甚至变慢。所以生产多用 -O2，计算密集场景才评估 -O3。
Q2：为什么开启优化后调试变得困难？
优化会重排指令、内联函数、消除变量，源码行与机器指令不再一一对应，变量可能已被优化掉（optimized out）。调试应使用 -O0 -g 构建。
Q3：什么是 LTO？
链接期优化。把优化推迟到链接阶段，此时可见全部模块，可做跨文件内联、全程序死代码消除等过程间优化。代价是链接更慢、占用更多内存。
Q4：内联一定能提升性能吗？
不一定。内联消除调用开销并为后续优化打开空间，但会导致代码膨胀、指令缓存压力增大；过度内联反而变慢。编译器会基于成本模型（调用频率、函数体积）决定是否内联。
Q5：什么是未定义行为，它和优化有什么关系？
标准未规定结果的行为（如有符号整数溢出、数组越界、空指针解引用）。编译器可假定 UB 不发生并据此优化，导致程序在开启优化后表现出与预期完全不符的行为。

一、最值得记住的八种优化

优化做了什么收益来自例子
常量折叠编译期算出常量表达式省掉运行期计算2*3 -> 6
常量传播把已知常量代入后续使用让更多折叠成为可能x=3; y=x+1 -> y=4
公共子表达式消除重复计算只算一次省掉重复运算a*b 出现两次只算一次
死代码删除删掉不影响输出的代码减小体积、省时间不可达分支
函数内联把函数体展开到调用点省调用开销 + 开启后续优化小函数被展开
循环不变式外提把循环内不变的计算挪到外面N 次变 1 次数组地址计算提前
强度削弱用便宜操作替换昂贵操作乘法变加法、除法变移位i*4 -> i<<2
循环展开一次迭代处理多个元素减少分支、提高指令并行每次处理 4 个元素
为什么 -O2 是默认档

-O2 包含了几乎全部「安全且收益稳定」的优化，编译时间可控，且不引入 O3 常见的体积膨胀与浮点语义变化。O3 会做更激进的循环变换与向量化，对数值敏感的程序可能得到不同但同样合法的结果。

二、寄存器分配：优化里最关键的一步

IR 里变量数量无限，物理寄存器只有十几个。寄存器分配要解决「谁进寄存器、谁溢出到内存」：

// 核心概念：活跃区间（live range） // 变量从「定义」到「最后一次使用」之间都是活跃的 // 图着色分配五步： // 1) 构建干扰图：活跃区间重叠的两个变量之间连边 // 2) 计算 spill 代价：在循环里的变量代价高 // 3) 简化：反复移除度数 < K 的节点并压栈 // 4) 着色：按逆序弹栈，给每个节点挑一个邻居没用的颜色 // 5) 溢出：简化失败就选代价最低的变量 spill 到栈，重来 // 结果：绝大多数变量留在寄存器，少数高频循环变量必须保住

三、优化不能做什么（别名分析是天花板）

编译器最大的障碍是别名：两个指针可能指向同一块内存时，它不敢重排、不敢缓存到寄存器：

void f(int *a, int *b) { *a = 1; *b = 2; // 编译器能合并成一次写吗？不能 —— 除非证明 a != b // 这就是 C 的 restrict、Fortran 的明确无别名假设的价值 } // Go / Rust 的好处：语言层面提供了更多保证 // - Go 的 slice 有明确边界与逃逸分析 // - Rust 的 &mut 排他借用从类型系统层面排除别名

四、PGO 与 LTO：工程上收益最大的两个开关

手段做法典型收益代价
LTO 链接时优化在链接阶段仍能看见所有模块的 IR跨模块内联、死代码跨文件删除，常 5%~15%链接变慢、内存占用高
PGO profile 引导先跑一次采集热点，再按热点重新编译分支布局与内联更准，常 10%~20%需要真实负载，构建流程复杂化
BOLT 后链接优化对二进制按 profile 重排代码布局减少 i-cache miss，5%~10%依赖 perf 数据

五、深入自检

为什么开 -O2 后断点打不上、变量看不到？

因为变量被放进寄存器、语句被重排、函数被内联，源码与机器码不再一一对应。调试就用 -O0，或者加 -fno-inline -fno-omit-frame-pointer 换取部分可调试性。

优化会不会改变我的浮点结果？

会。浮点不满足结合律，重排求和顺序、向量化都会改变舍入路径。需要严格可复现时用 -ffp-contract=off 或关闭 fast-math；做数值比较务必用误差范围而不是相等。

为什么有时候 O3 比 O2 还慢？

循环展开与激进内联会让代码体积膨胀，指令缓存命中率下降；更大的基本块也可能让调度器找不到最优解。这就是「优化不是越强越好」的直接证据。

volatile 和 atomic 会不会阻止优化？

会，而且是故意的。volatile 禁止把变量缓存到寄存器（每次都真实读）；atomic 在此之上还约束了指令重排与多核可见性。滥用它们会显著拖慢程序。

Go 编译器做了哪些优化？

逃逸分析决定栈上还是堆上、函数内联（有预算限制）、边界检查消除、死代码删除、以及 SSA 阶段的公共子表达式消除与寄存器分配。用 go build -gcflags=-m 可以看内联与逃逸决策。
