一句话总结：GROUP BY 会把多行压成一行； 窗口函数则在保留每一行的前提下，为每行算出一个"基于一组相关行"的值。 它的核心价值就是「既要看明细，又要看这行所处的位置/上下文」—— 排名、累计、同比环比、分组 Top-N 全靠它。

01GROUP BY 做不到的事

需求：「列出每个员工，以及他所在部门的平均工资，用于和自己的工资对比」。

02语法骨架

函数名(参数) OVER (
    [PARTITION BY 分组列]        -- 按什么分组（类似 GROUP BY，但不压缩行）
    [ORDER BY 排序列]            -- 组内按什么顺序（决定累计/排名的顺序）
    [ROWS | RANGE 窗口帧]        -- 限定计算范围（如前 2 行到当前行）
)

📦 PARTITION BY

把数据切成若干"窗口"，函数在各自窗口内独立计算。 省略就是全表一个窗口。

📏 ORDER BY

定义窗口内的行顺序。对排名类和累计类函数必不可少； 对纯聚合（如部门均值）可以省略。

🖼️ 窗口帧（Frame）

进一步限定"当前行相关的行范围"， 如 ROWS BETWEEN 2 PRECEDING AND CURRENT ROW（移动平均）。

🎯 执行时机

窗口函数在 WHERE/GROUP BY/HAVING 之后、 ORDER BY/LIMIT 之前计算。

重要限制：窗口函数不能写在 WHERE 里。 因为它算出来的值在 WHERE 阶段还不存在。 要过滤窗口函数的结果，必须包一层子查询或 CTE： SELECT * FROM (SELECT ..., ROW_NUMBER() OVER(...) rn FROM t) x WHERE x.rn <= 3。

03三大排名函数（面试必考）

这是最容易混淆的一组，区别只在并列时的处理：

图 2：三大排名函数的差异只在并列处理
-- 经典题：每个部门工资最高的 3 个人（分组 Top-N）
SELECT * FROM (
  SELECT
    name, dept, salary,
    ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) AS rn
  FROM employees
) t
WHERE rn <= 3;

-- 如果希望并列的人都能选上（可能超过 3 个），改用 RANK 或 DENSE_RANK
-- 注意：ROW_NUMBER 会把并列的人随机取一个，结果不稳定！
--       需要稳定结果时，ORDER BY 里加一个唯一列：ORDER BY salary DESC, id
面试陷阱：用 ROW_NUMBER() OVER (ORDER BY salary DESC) 时， 如果 salary 有重复，每次执行返回的排名可能不同（谁在前不确定）。 要结果稳定，必须在 ORDER BY 里补一个唯一列（如主键 id）。

04LAG / LEAD：取前后行的值

用来做环比、同比、相邻差——没有窗口函数时要自关联，极其痛苦。

图 3：LAG/LEAD 让"和上一行比较"变成一行 SQL
-- 计算每月环比增长
SELECT
  month,
  revenue,
  LAG(revenue) OVER (ORDER BY month)            AS prev_revenue,
  revenue - LAG(revenue) OVER (ORDER BY month)  AS mom_diff,
  ROUND(100.0 * (revenue - LAG(revenue) OVER (ORDER BY month))
        / LAG(revenue) OVER (ORDER BY month), 2) AS mom_pct
FROM monthly_sales
ORDER BY month;

-- 也可用 default 参数避免 NULL：LAG(revenue, 1, 0)
-- FIRST_VALUE / LAST_VALUE：取窗口内第一行/最后一行
SELECT
  month, revenue,
  FIRST_VALUE(revenue) OVER (ORDER BY month) AS first_month_rev
FROM monthly_sales;

05聚合窗口：累计与移动平均

把 SUM/AVG/COUNT/MAX/MIN 配上 OVER，就得到累计类指标：

SELECT
  month,
  revenue,
  -- 累计求和（Running Total）：默认帧是 首行 ~ 当前行
  SUM(revenue) OVER (ORDER BY month) AS running_total,

  -- 全表总和（不写 ORDER BY，帧就是整个分区）
  SUM(revenue) OVER () AS grand_total,

  -- 每行占总和的比例（经典用法！）
  ROUND(100.0 * revenue / SUM(revenue) OVER (), 2) AS pct_of_total,

  -- 3 个月移动平均（当前行 + 前 2 行）
  AVG(revenue) OVER (ORDER BY month
                     ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS ma3
FROM monthly_sales
ORDER BY month;
最关键的一条规则：聚合窗口函数写了 ORDER BY 就默认带帧 （RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW，即累计到当前行）； 不写 ORDER BY 则帧是整个分区（每行结果都相同）。 理解这一点，"为什么我的 SUM 是累计的而不是总数"这个问题就迎刃而解。

06窗口帧 ROWS vs RANGE

写法含义典型用途
ROWS BETWEEN n PRECEDING AND CURRENT ROW按物理行数算前 n 行n 日移动平均
ROWS BETWEEN CURRENT ROW AND n FOLLOWING当前行 + 后 n 行预测/前瞻
ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW首行到当前行累计求和（默认）
RANGE BETWEEN INTERVAL '7' DAY PRECEDING AND CURRENT ROW按值区间（如 7 天内）时间窗口聚合
ROWS 与 RANGE 的关键差异：
· ROWS 数的是行——"前 2 行"就是字面意义的前 2 行，不论值是否相同。
· RANGE 看的是值——"前 7 天"按排序列的实际值计算； 且相同值的行会被归为一组（并列行的计算结果相同）。
做移动平均一般用 ROWS（结果更符合直觉）； RANGE 在处理重复值时要特别小心。

07常见疑问

Q：窗口函数能用在 UPDATE / DELETE 里吗？
A：不能直接用。窗口函数只能出现在 SELECT 和 ORDER BY 中。 常见替代是用 CTE + JOIN： WITH ranked AS (SELECT id, ROW_NUMBER() OVER(...) rn FROM t) UPDATE t JOIN ranked ... WHERE rn > 1 —— 这也是"删除重复记录保留一条"的标准写法。
Q：窗口函数的性能如何？
A：通常需要一次排序（按 PARTITION BY + ORDER BY 的列）， 数据量大时可能是瓶颈。优化关键：给 PARTITION BY + ORDER BY 的列建联合索引， 让数据库直接用索引顺序而免去排序。 另外，多个窗口函数若使用相同的窗口定义，数据库只需排一次序—— 尽量复用同一个 OVER 子句。
Q：MySQL 从哪个版本开始支持？
A：MySQL 8.0（2018 年）才引入窗口函数，5.7 及更早版本不支持。 这是 5.7 → 8.0 升级最重要的理由之一。 8.0 支持 ROW_NUMBER、RANK、DENSE_RANK、LAG、LEAD、FIRST_VALUE、LAST_VALUE、 NTH_VALUE、NTILE，以及所有聚合函数作为窗口函数。
PostgreSQL、SQL Server、Oracle 支持得更早也更完整。

第三层 · 排障与边界：窗口函数的坑

坑后果正确做法
ROWS 与 RANGE 搞混有重复值时结果不同要「前 N 行」用 ROWS；要「值范围内」用 RANGE
窗口函数不能写在 WHERE 里语法错误包一层子查询，在外层过滤
ORDER BY 有重复值时累计和抖动同组行的累计值不同ORDER BY 加上唯一列（如主键）保证确定性
以为窗口函数会去重行数不变窗口函数不改变行数，要聚合用 GROUP BY
嵌套窗口函数不允许用子查询分层
LAG/LEAD 越界返回 NULL用第三个参数给默认值 LAG(x, 1, 0)

常见坑的写法

-- ROWS vs RANGE 的关键区别（有重复值时）
-- ROWS: 按物理行数算（前 1 行）
SUM(v) OVER (ORDER BY d ROWS BETWEEN 1 PRECEDING AND CURRENT ROW)
-- RANGE: 按值范围算（值 >= 当前值-1 的所有行，含重复值）
SUM(v) OVER (ORDER BY d RANGE BETWEEN 1 PRECEDING AND CURRENT ROW)

-- 正确：给 ORDER BY 加唯一列，让结果确定
ROW_NUMBER() OVER (ORDER BY score DESC, id)   -- 加 id 打破平局

-- 窗口函数结果要在外层过滤（不能写进 WHERE）
SELECT * FROM (
  SELECT id, ROW_NUMBER() OVER (PARTITION BY uid ORDER BY ts DESC) rn
  FROM logins
) t WHERE rn = 1;                              -- 每用户最新一次登录

-- LAG/LEAD 的默认值
LAG(amount, 1, 0) OVER (ORDER BY ts)           -- 越界时返回 0 而不是 NULL
  • 排查顺序：先确认 ROWS/RANGE → 再确认 ORDER BY 是否唯一 → 再看有没有把窗口函数写进 WHERE → 最后检查行数是否符合预期。
  • 边界一：窗口函数在 GROUP BY 之后、ORDER BY 之前执行，所以它看到的是分组后的结果。
  • 边界二：RANK() 会跳号（1,1,3），DENSE_RANK() 不跳号（1,1,2），ROW_NUMBER() 不并列（1,2,3）——三者语义不同。
  • 边界三：NTILE(n) 在不能整除时，前面的组会多分到行。

支持度：MySQL 8.0+、PostgreSQL 8.4+、SQL Server 2012+、Oracle 8i+。MySQL 5.7 及更早版本没有窗口函数，只能用变量或自连接模拟。

第四层 · 原理与取舍：窗口函数 vs 自连接 vs 聚合

窗口函数的价值：一次扫描就能同时看到「当前行」和「同组的其它行」，而不用自连接。

方案扫描次数可读性性能适用

先 GROUP BY 再 JOIN 回去2 次中中只需聚合值时

为什么 ROWS 和 RANGE 在没重复值时结果一样？

因为「前 N 行」和「值在前 N 的范围内」在没有并列值时指向同一批行。一旦 ORDER BY 的列有重复，RANGE 会把所有值相同的行都算进窗口，ROWS 只算物理上的 N 行——这就是差异的来源。

窗口函数会走索引吗？

PARTITION BY + ORDER BY 的列如果有复合索引，数据库可以省掉排序步骤，直接从有序索引读取。所以「(uid, ts)」这类复合索引对 PARTITION BY uid ORDER BY ts 的查询帮助很大。

和 GROUP BY 的本质区别是什么？

GROUP BY 会压缩行数（每组一行）；窗口函数保持原行数，只是给每行附加一个计算值。所以「既要明细又要汇总」的场景必须用窗口函数，GROUP BY 做不到。
