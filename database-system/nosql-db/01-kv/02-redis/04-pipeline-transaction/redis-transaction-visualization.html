🎯 核心区别详解

1. 原子性 (Atomicity)

🔴 Redis
"要么全部执行，要么全部不执行"仅适用于命令入队阶段。一旦 EXEC，命令会全部执行，即使中间出错也不会回滚。
🔵 MySQL
真正的原子性。任何步骤失败都会触发回滚，数据库状态回到事务开始前。

2. 错误处理

🔴 Redis
语法错误（入队时）→ 拒绝执行；运行时错误（如类型错误）→ 继续执行后续命令。
🔵 MySQL
任何错误都会终止事务，可选择回滚或提交。约束违反会立即报错。

3. 隔离级别

🔴 Redis
单线程模型天然提供串行化隔离级别，无脏读、不可重复读、幻读问题。
🔵 MySQL
支持 4 种隔离级别，通过 MVCC 和锁机制实现，需根据场景选择。

4. 使用场景

🔴 Redis
批量操作、乐观锁（WATCH）、简单原子操作。不适合复杂业务事务。
🔵 MySQL
金融交易、订单处理、库存扣减等需要强一致性的业务场景。

💡 实现原理说明

MULTI：将客户端标记为事务状态，后续命令不会立即执行，而是放入事务队列。

命令队列：Redis 使用一个数组（multiState.commands）存储事务中的所有命令。

EXEC：遍历命令队列，依次执行每个命令。执行期间不会被其他客户端命令打断。

WATCH：实现乐观锁，监控键的变化。如果键被其他客户端修改，EXEC 会返回 nil 表示执行失败。

📝 代码示例对比

# Redis 事务示例 - 转账操作
# 使用 WATCH 实现乐观锁

WATCH account:a account:b      # 监控两个账户

balance_a = GET account:a      # 获取余额
if balance_a >= 100:
    MULTI                      # 开启事务
    DECRBY account:a 100      # 扣款
    INCRBY account:b 100      # 加款
    result = EXEC              # 执行事务
    
    if result == nil:          # 监控的键被修改
        # 事务失败，需要重试
        retry_transaction()
else:
    UNWATCH                    # 取消监控

# 注意：如果 EXEC 前键被修改，EXEC 返回 nil
# 需要客户端实现重试逻辑
-- MySQL 事务示例 - 转账操作
-- 使用悲观锁 (SELECT FOR UPDATE)

START TRANSACTION;           -- 开启事务

-- 查询并锁定账户
SELECT balance FROM accounts 
WHERE account_id = 'a' 
FOR UPDATE;                  -- 行级排他锁

SELECT balance FROM accounts 
WHERE account_id = 'b' 
FOR UPDATE;

-- 执行转账
UPDATE accounts 
SET balance = balance - 100 
WHERE account_id = 'a' AND balance >= 100;

UPDATE accounts 
SET balance = balance + 100 
WHERE account_id = 'b';

COMMIT;                      -- 提交事务
-- 或 ROLLBACK; 回滚事务

-- 任何错误都会自动回滚
-- 锁机制保证并发安全

Pipeline 与事务的量化收益

核心差异：Pipeline 是批量发送省网络往返；事务是保证一组命令的原子执行。两者正交，可同时使用。

方式RTT 次数（N 条命令）原子性耗时示例（N=100，RTT=0.5ms）
逐条发送N无50 ms
Pipeline1无约 1 ms（快 50 倍）
MULTI/EXECN+2有约 51 ms
Pipeline + 事务1有约 1 ms

Pipeline 用法

# Pipeline 示例（Python redis-py）
pipe = r.pipeline()
for i in range(1000):
    pipe.set(f"k:{i}", i)
pipe.execute()          # 一次网络往返，1000 条命令

# 关键参数：批次大小
#   太小 → 省不了 RTT；太大 → 单次响应太大，阻塞 Redis
#   <strong>建议每批 100~1000 条</strong>，或控制单批响应 < 10 MB

# 注意：pipeline 默认<strong>开启事务</strong>（redis-py 的 pipeline(transaction=True)）
# 若只需批量不需要原子性，用 transaction=False 可略微减少开销

Pipeline 不保证原子性：它只是把多条命令打包发送，Redis 仍逐条执行，期间可能插入其他客户端的命令。需要原子性必须配合 MULTI/EXEC 或 Lua 脚本。

命令作用说明

事务与乐观锁

# 乐观锁实现“检查再设置”（CAS）
WATCH balance          # 1) 监视
val = GET balance      # 2) 读取
MULTI                  # 3) 开启事务
SET balance val - 100  # 4) 基于读到值计算
EXEC                   # 5) 执行；若 balance 被其他客户端改过，返回 nil

# 客户端必须处理 EXEC 返回 nil 的情况 → 重试
# 典型重试上限 3~5 次，超过则放弃或改用 Lua 脚本

# Lua 脚本：把“检查+设置”变成服务端原子操作，无需重试
# EVAL "if redis.call('get',KEYS[1]) >= ARGV[1] then
#         return redis.call('decrby',KEYS[1],ARGV[1])
#       else return -1 end" 1 balance 100

Redis 事务的两个重要限制：

  • 没有回滚：语法错误（入队时就发现）会整体不执行；但运行时错误（如对字符串执行 INCR）只会让该条失败，其余命令照常执行。这与关系型数据库的事务语义完全不同，是最容易误解的地方。
  • 事务内的读看不到事务内的写：MULTI 后的命令只入队，GET 返回的是入队前的状态，无法基于前面的写结果做判断。要做“读-判断-写”必须用 Lua 脚本。

Lua 限流器

# 限流器（令牌桶）——经典 Lua 用例
# KEYS[1]=桶的key  ARGV[1]=容量  ARGV[2]=每秒补充  ARGV[3]=当前时间戳
local cap = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or cap
local ts = tonumber(b[2]) or now
tokens = math.min(cap, tokens + (now - ts) * rate)   # 按时间补充
if tokens < 1 then return 0 end                       # 令牌不足
redis.call('HMSET', KEYS[1], 'tokens', tokens - 1, 'ts', now)
return 1

# 执行：EVAL script 1 rate:user:1 10 5 1699999999
# 复用：先 SCRIPT LOAD 得到 sha，之后 EVALSHA sha ...

# 三条硬规则：
#   1) 脚本必须<strong>短小</strong>——执行期间 Redis 单线程被独占，慢脚本会阻塞全部请求
#   2) <strong>禁止长时间循环</strong>（如 KEYS * 后遍历），会触发 busy script 错误
#   3) key 必须通过 KEYS[] 传入，不能硬编码（集群模式下会路由错误）

自检 Q&A

Q：Pipeline 到底能快多少？

A：取决于 RTT 与命令执行时间的比例。同机房 RTT 约 0.2~0.5 ms，单条命令执行约 10~50 μs——所以每条命令的 RTT 开销是执行时间的 10~50 倍。批量 100 条能省掉 99 次往返，收益接近 10~50 倍。但如果命令本身很慢（如大 key 操作），Pipeline 的收益就有限，瓶颈在执行而不在网络。

Q：为什么 Redis 事务不支持回滚？

A：这是设计取舍。Redis 作者认为：事务失败只可能是编程错误（如类型用错），这类错误应在开发期发现，而不是靠运行时回滚掩盖。保持简单让 Redis 实现极轻——不需要 undo log、不需要 MVCC。这个设计在生产很少造成问题，因为正确使用下运行时错误几乎不会发生。但你必须知道这一点，别把它当关系型事务用。

Q：Lua 脚本执行太久会怎样？

A：Redis 会判定为 busy script。默认超过 5 秒（lua-time-limit）后，Redis 不再自动终止脚本（因为脚本可能有副作用），但会开始接受 SCRIPT KILL 和 SHUTDOWN NOSAVE 命令，其他命令全部阻塞。所以必须写短脚本。若已卡住，用 SCRIPT KILL（未执行写操作时可用）；若已写入，只能 SHUTDOWN NOSAVE——这是运维噩梦，务必避免。

Q：集群模式下事务还能用吗？

A：有限制。事务与 Lua 脚本要求所有涉及的 key 在同一个 hash slot，否则报 CROSSSLOT Keys in request don't hash to the same slot。处理办法是用 hash tag：把相关的 key 写成 {user1}:balance、{user1}:orders，Redis 只对 {} 内的部分计算 slot，从而保证它们落在同一槽位。这是集群下使用多 key 操作的标准做法。
