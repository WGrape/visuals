OLAP 基准测试与负载画像

选型失败的典型原因是拿引擎能力对比表当决策依据——能力表只能排除不能选择，因为决定体验的是负载落在哪个区域。先把数据新鲜度、查询形态、并发量、数据规模、查询灵活性五个维度量化，候选通常就从五六个收敛到一两个；再用 SSB / TPC-H / TPC-DS 做初筛和回归，最终必须用业务自有查询集决策。测试必须跑真实规模数据、每类查询跑多次取中位数与 P99、冷热分开测、并发要测、导入要与查询同时进行、记录全部配置，否则结果无法复现。厂商公布的 benchmark 不是造假，但通常在最优配置、单一查询、无并发下取得，与真实场景差得很远。
🚚

OLAP 迁移路径与成本估算

从 MySQL / ES / Hive / 旧 OLAP 迁来各有不同难点，但成败关键都不在引擎选型，而在建模改造与结果验证。全量回溯加增量追平后必须双写双跑，因为分析系统的错误往往不报错只是结果不对，等到业务发现时已影响决策很久；灰度切读要覆盖一个完整业务周期，长尾问题常在峰值才暴露。建模改造是最容易低估的部分——把 OLTP 表结构原样搬过来几乎必然导致性能不达标。验证要分层做：行数汇总比对能抓住八成导入问题，再分维度下钻、抽样明细、最后比对旧系统 Top 慢查询。成本除存储与计算外，别忘了副本倍数、导入 compaction 争抢资源，以及常被完全忽略的人力成本。
