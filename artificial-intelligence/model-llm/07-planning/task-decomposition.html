任务分解 Task Decomposition

把「做一份竞品分析报告」这种大目标，拆成模型一次就能可靠完成的小步骤——这是几乎所有 LLM 规划能力的地基。难的不是拆，而是拆到什么粒度。

① 为什么复杂任务必须先分解

让模型一口气完成一个多步骤任务，常见的失败不是「做得慢」，而是做漏、做错、且自己不知道：

  • 中间步骤被跳过。任务越复杂，模型越倾向于直接跳到结论，把中间该做的调研、验证省掉。
  • 上下文被稀释。长任务的所有要求挤在一个提示里，越靠后的要求越容易被忽略。
  • 错误无法定位。一次性产出，错了也不知道是哪一步错的，只能整体重来。
  • 没法并行、没法复用。不分步骤就无法判断哪些能同时做、哪些结果可以复用。
分解的本质价值：把「一个大而不可靠的生成」换成「多个小而可靠的生成」——每步都在模型的舒适区内，而且每步都可以单独检查。

② 核心两难：拆太粗 vs 拆太细

🪨

拆太粗：做不动

单步仍然太复杂，模型还是一步跳到结论，分解等于没分。表现：每个子任务依然含糊，执行结果经常缺斤少两。

🧱

拆太细：代价高

子任务暴涨 → 调用次数和成本上升；每多一步就多一次出错机会；还要额外维护步骤间传递的状态，上下文更容易乱。

判断粒度的实用标准：一个子任务应该小到模型一次调用能可靠完成、大到不需要额外通信开销。经验上，每个子任务对应「一次工具调用」或「一个可独立验证的产物」是比较好用的尺度。

③ 四种常见拆法

➡️

1. 按执行顺序拆

最直觉：先做什么、再做什么。适合流程固定的任务（如「取数 → 清洗 → 统计 → 出图」）。缺点：忽略依赖，无法并行。

🎯

2. 按子目标拆

先把目标拆成几个独立可验证的成果（如「价格对比」「功能对比」「结论建议」），每个成果再各自展开。优点：天然可验证。

🧩

3. 按模块 / 角色拆

按职责域划分（数据、文案、审核），甚至交给不同的 agent 角色。适合：多智能体协作；代价：需要额外的通信与结果整合。

🪜

4. Least-to-Most：由易到难

先解决最简单的子问题，把它的答案作为下一步的输入，逐步逼近原问题。好处：每步都有前面的成果兜底，比一次性硬啃难题稳得多。

④ 计划应该是 DAG，不是一条直线

图 1：把计划表达为有向无环图（DAG），而不是线性步骤列表。
工程要点：DAG 让两件事变得可能——并行执行没有依赖关系的分支，以及用拓扑排序确定安全执行顺序。另外，显式依赖能在执行前就发现「循环依赖」「缺少某个工具」这类问题。

⑤ ADaPT：别急着拆，做不动再拆

固定粒度分解有个尴尬：简单任务被过度拆开（白花成本还更容易错），复杂任务又拆得不够。ADaPT（Prasad et al., 2024，NAACL）给出的思路是按需分解（as-needed decomposition）：

  • 先尝试直接执行整个任务；
  • 只有当直接执行失败时，才把这个任务递归地分解得更细，再重试；
  • 简单任务因此不会被无谓地拆开，复杂任务则会自动被拆到足够细。
该论文报告：相比固定分解的做法，按需分解在 ALFWorld 上成功率提升 28%，在 TextCraft 上提升 33%。
可以借鉴的通用原则：分解应该是由失败驱动的，而不是提前定死的。先试简单的，做不动再细化——这比一上来就生成一棵庞大的计划树更省、也更稳。

⑦ 分解的常见失败模式

🕳️

子目标遗漏

分解时漏掉了任务的某个必要部分（如只对比了价格，忘了功能）。缓解：分解后加一步「完整性检查」，或用 checklist 约束输出。

🔀

依赖关系搞错

把有依赖的两步当成独立、或反过来制造了循环依赖。缓解：显式输出依赖边，执行前做一次拓扑排序验证。

📦

中间结果丢失

前一步的产物没被正确传给后一步，后一步只能靠「猜」补上——这正是幻觉的温床。缓解：结构化地保存每步产物，显式注入后续提示。

📏

粒度一刀切

不论任务难易都按同一粒度拆，简单任务被过度拆、复杂任务拆不透。缓解：按需分解（ADaPT 思路）。
