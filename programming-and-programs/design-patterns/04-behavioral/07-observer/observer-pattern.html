📣 观察者

一个对象变化，已订阅的对象自动得到通知。

一句话记住订阅天气播报的人，在天气变化后各自收到更新。
问题从哪来图解协作动手试一试伪代码选型与边界
01 · 从问题出发

为什么会需要这个模式？

订单支付后，页面、审计和通知都要响应；订单若直接调用每个模块，会与所有下游耦合。

订单状态变成已支付时，页面要刷新、审计要记录、通知模块要发消息。如果订单对象直接持有这三个具体模块，每增加一个响应者都要改订单代码。反过来，永久保存回调也可能导致重复执行和内存引用。

😵 直接写会怎样

function markPaid(order):
  order.status = PAID
  page.refresh(order)
  audit.record(order)
  sms.send(order.user)
  // 又加一个订阅者，就要修改这里

💡 关键转折

主题对象维护订阅集合，状态变化后通知订阅者；订阅者可独立加入或退出。

发布者只维护订阅集合并发出“已发生的变化”；观察者自己订阅、处理和在生命周期结束时取消。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

class Subject {
  listeners = Set()
  subscribe(fn) {
    listeners.add(fn)
    return () => listeners.delete(fn)
  }
  emit(event) {
    for fn in copy(listeners): fn(event)
  }
}
stop = orderEvents.subscribe(onOrderPaid)
orderEvents.emit(OrderPaid(orderId))
stop()

读代码时抓住三件事

  1. subscribe 返回取消订阅函数，方便明确释放。
  2. emit 遍历快照，可避免通知期间修改集合破坏当前迭代。
  3. 同步回调的耗时和异常传播是发布者必须考虑的语义。

换个业务场景，还能认出来吗？

浏览器的事件监听、GUI 数据绑定都常见观察者。跨服务订单事件若要求持久化、重试和至少一次投递，则需要消息系统、outbox 和消费者幂等，不能只靠内存回调。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

一个对象变化后，多个订阅者需要各自响应

三个具体场景

  • 订单支付后刷新页面并记审计
  • GUI 模型变化通知视图
  • 浏览器 DOM 事件通知多个监听器

不适合或要小心

同步回调会影响发布者的耗时和错误传播；跨服务可靠投递要用持久化消息与幂等消费。

同步回调会拖慢发布者；跨进程可靠交付需要消息队列等机制

最容易混淆的相邻模式

模式真正的区别
中介者集中决定多个对象如何协作；观察者是发布状态变化，让订阅者各自响应。
消息队列提供跨进程传输、持久化和重试等能力；进程内观察者不自动提供这些保证。

区分时问自己：发布者只广播事实，还是由中心协调者决定下一步？

落地前检查

  • 明确回调同步还是异步、失败后是否继续。
  • 测试重复订阅和取消订阅。
  • 业务事务未提交前不要发布“已完成”事件。
06 · 自己说一遍

两道检验理解的小题

为什么订阅函数最好返回取消订阅句柄？

组件卸载或任务结束时可移除回调，避免重复处理和长期持有对象。

如果观察者处理很慢，会影响发布者吗？

同步回调会占用同一调用链并拖慢发布者；需异步化时要重新定义投递和失败语义。

核心速览

一句话一个对象状态变化时，自动通知所有登记过的依赖者
别名发布-订阅（Pub/Sub）的近亲，但观察者是直接引用，Pub/Sub 多一层中介
解决什么解耦「谁变了」和「谁要跟着变」
必须注意通知顺序、循环通知、观察者泄漏（忘记注销）
观察者模式的完整生命周期：注册 -> 变更 -> 通知 -> 注销

一、两种通知方式

方式做法优点缺点
推模型 pushnotify 时把变化的数据一起传过去观察者不用回头查，简单数据格式固定，加字段要改接口
拉模型 pull只通知「我变了」，观察者自己来取观察者按需取，扩展性好观察者要知道怎么取，耦合略高

工程上更常见的是推一个事件对象：既包含变更类型也包含关键字段，观察者按需读取。这样既避免了接口频繁变动，也不需要观察者回头查主题。

二、Go 里的写法

type Event struct{ Type string; Payload any } type Subject struct { mu sync.RWMutex subs map[uint64]func(Event) // 用 id 便于注销 next uint64 } func (s *Subject) Subscribe(fn func(Event)) (unsubscribe func()) { s.mu.Lock() id := s.next; s.next++ s.subs[id] = fn s.mu.Unlock() return func() { // 返回取消函数，调用方 defer 即可 s.mu.Lock(); delete(s.subs, id); s.mu.Unlock() } } func (s *Subject) Notify(e Event) { s.mu.RLock() fns := make([]func(Event), 0, len(s.subs)) for _, f := range s.subs { fns = append(fns, f) } // 拷贝一份再通知 s.mu.RUnlock() for _, f := range fns { f(e) } // 不在持锁状态下回调，避免死锁 }
三个必避的坑

① 持锁回调：观察者在回调里又去订阅/注销，会死锁或破坏遍历 —— 先拷出快照再通知；② 忘记注销：观察者生命周期比主题长时，会造成内存泄漏和「通知到已销毁对象」；③ 循环通知：A 通知 B、B 又改了 A，需要加版本号或抑制标志。

三、观察者 vs 发布订阅

观察者模式发布订阅 Pub/Sub
耦合主题直接持有观察者引用通过消息队列/事件总线中转
知道对方吗知道（同步调用）不知道（解耦更彻底）
同步性通常同步通常异步、可持久化
跨进程否是（Redis Pub/Sub、Kafka）
适用进程内组件联动跨服务事件驱动

五、深入自检

观察者里的异常会不会影响主题？

同步模型下会——一个观察者 panic，后面的观察者就收不到通知了。生产代码里要么逐个 recover，要么把通知放到独立的 goroutine / 队列中异步执行。

通知顺序能保证吗？

取决于实现。用 map 存储时顺序是不确定的；如果对顺序有要求，必须用切片保存并按注册顺序遍历，或显式提供优先级。

观察者执行慢会拖垮主题吗？

同步通知会。任何慢观察者都会阻塞主题线程。解决办法：异步通知 + 每个观察者独立超时，或者干脆换成消息队列。

和监听器（Listener）、回调（Callback）什么关系？

是同一思想的不同名字与粒度。回调是单个函数；监听器通常是一对事件的多个回调；观察者是面向对象语境下的完整表述。Go/JS 里常用回调实现，效果等价。

什么时候不该用观察者？

当通知链条长到无法追踪，或者业务逻辑依赖通知顺序时。这时的典型症状是「改一处代码，不知道会触发什么」。事件太多就改成显式的编排（Orchestration）。

记住一句状态一变，自动通知登记者
必做三件事快照通知 / 提供注销 / 防止循环
同步 vs 异步进程内同步，跨服务用 MQ
和 Pub/Sub 区别是否经过中介、能否跨进程
