什么是架构：决策、质量属性与权衡

架构不是那张方框加箭头的图，而是「为什么这么画」的一系列决策。这一篇讲清架构的决策本质、六类质量属性、三对经典权衡、三个层次与四个常见误解。

DECISION · 决策视角

一、架构的本质是一组决策

🎯 不只是"画出来的图"

很多人把架构等同于那张方框加箭头的图。但图只是决策的结果，架构本身是为什么这么画的那一系列选择：数据放哪、服务怎么拆、调用是同步还是异步、一致性要做到什么程度、失败时怎么办。图会过时，决策与理由不会。

一个可操作的判断标准：如果团队说不出"我们为什么选 A 不选 B"，那这个系统还没有架构——只有一堆碰巧能跑起来的代码。
📐 决策的代价差异
决策类型例子改变成本
易改函数命名、内部实现、日志格式分钟–小时
中等模块边界、接口定义、依赖方向天–周
难改服务拆分方式、数据存储选型、通信协议周–月
几乎不可改数据模型范式、是否分布式、一致性模型需要重写
架构师的价值在于把有限的精力放在"难改"和"几乎不可改"的决策上。在易改的地方纠结是浪费，在几乎不可改的地方拍脑袋是灾难。
QUALITY · 质量属性

二、质量属性：架构要满足的"非功能需求"

⚖️ 六类质量属性
质量属性问的是什么典型手段
性能多快？吞吐多少？缓存、异步、批处理、索引、就近访问
可用性能用多久？故障恢复多快？冗余、故障转移、熔断降级、灰度
可扩展性加机器能加多少吞吐？无状态化、分片、水平拆分
可维护性改起来多痛？模块边界清晰、依赖单向、测试覆盖
安全性谁能做什么？数据会不会漏？认证授权、最小权限、加密、审计
成本要花多少钱？资源利用率、弹性伸缩、架构简化
质量属性必须写成可验证的指标。"系统要高性能"不是需求，"下单接口 P99 < 200 ms，支持 5000 QPS"才是。无法衡量的质量属性等于没有需求，也就无法判断架构是否达标。
TRADE-OFF · 权衡

三、为什么不存在"最优架构"

🔀 三对经典冲突
  • 一致性 vs 可用性：分布式下网络分区时二者不可兼得。要么牺牲可用性保一致，要么接受短暂不一致保可用。
  • 延迟 vs 吞吐：批处理能大幅提高吞吐，但单个请求的延迟会变长。实时链路和离线链路通常要分开设计。
  • 灵活性 vs 性能：高度抽象、可配置的系统往往有额外开销；极致优化的系统通常牺牲了通用性。
架构设计本质上是在约束条件下做取舍，并把取舍讲清楚。所谓"这个架构不好"，通常不是设计错了，而是它优化的目標和你的目标不一致。
🧭 取舍要有优先级

质量属性之间会冲突，所以必须排序。一个电商大促系统可能把"可用性 > 一致性 > 成本"；一个对账系统则可能是"一致性 > 一切"。没有优先级，遇到冲突时就会各执一词、反复返工。

LEVEL · 层次

四、架构的三个层次

层次关注什么产出物谁负责
企业级架构多个系统如何组合、数据在哪流转、复用什么能力系统地图、领域划分、集成规范架构委员会 / 首席架构师
应用级架构单个系统的模块划分、技术选型、与外部的依赖服务拆分、接口契约、部署拓扑应用架构师 / 技术负责人
模块级架构具体模块内部的类、函数、数据结构组织包结构、接口定义、关键类图开发工程师
常见错误：用模块级的思维做应用级的决策。比如纠结"这个字段用 int 还是 bigint"（模块级），却对"要不要拆成两个服务"（应用级）拍脑袋。层次感决定了你把注意力放在哪。
MYTH · 误解

五、四个常见误解

🚫 需要澄清的认知
  • "微服务更先进"：微服务解决的是组织协作与独立部署问题，代价是分布式复杂度。团队规模不大时，单体往往更快更稳。
  • "架构是架构师一个人的事"：决策由架构师主导，但约束来自业务、成本、团队能力。闭门造车的架构落地时必然变形。
  • "架构定完就不用改了"：业务规模变化 10 倍时，原有取舍大概率失效。架构需要随业务演进，关键是保留演进的余地。
  • "用了某某框架就有了架构"：框架解决的是如何实现，不解决要不要这么做。框架选错可以换，方向错了代价极大。

架构的多视角定义

视角 / 方法关注什么产出物
4+1 视图逻辑、进程、开发、物理 + 场景五类视图 + 用例串起来
C4 模型Context / Container / Component / Code 四层缩放分层图 + 文字说明
模块视角职责划分与依赖方向模块图、包结构
运行时视角进程、线程、通信与数据流转时序图、部署图
质量属性视角性能、可用性、安全、可修改性如何实现质量属性场景与权衡记录

一句话定义：架构是对系统「元素、关系以及它们与环境的关系」的顶层设计，核心目的是满足质量属性（非功能需求）而非功能本身。功能靠代码，性能/可用/扩展/安全靠架构。

质量属性必须量化才有意义

属性量化方式常见指标
可用性一年允许的停机分钟数99.9% = 8.76 h/年；99.99% = 52.6 min/年；99.999% = 5.26 min/年
性能延迟分位数与吞吐P95 < 200 ms、P99 < 500 ms、QPS ≥ 5000
可扩展性扩容后的线性度资源 ×2 时吞吐 ≥ 1.7×
可修改性改一个典型需求的成本需求到上线 ≤ 2 人日
安全性攻击面与响应速度高危漏洞修复 ≤ 24 h、全链路加密
可观测性故障定位时间 MTTDMTTD < 5 min、MTTR < 30 min

可用性数字对照：99.9%（三个 9）年停机约 8.8 小时；99.99%（四个 9）约 53 分钟；99.999%（五个 9）约 5.3 分钟。每多一个 9，成本通常上一个数量级。

架构决策记录（ADR）模板

ADR

# ADR 0007: 订单服务引入消息队列异步化

## 状态
已接受（2026-03-11）

## 背景
下单峰值 3000 QPS，同步调用库存与优惠券导致 P99 达 1.8s，超时率 3%。

## 决策
引入 Kafka：下单写库后发消息，库存与优惠券异步消费。

## 权衡（关键）
- 收益：P99 降到 350ms；峰值可削峰，下游故障不影响下单。
- 代价：引入最终一致，需要处理重复消费（幂等）与延迟可见（约 200ms~2s）。
- 放弃的方案：同步并行调用（P99 仍 900ms）、直接扩容数据库（成本高 5 倍）。

## 验证方式
压测 5000 QPS 下 P99 &lt; 500ms；消费积压 &lt; 1000 条；对账差异率 &lt; 0.01%。
ADR 要素为什么必要缺失后果
背景 + 约束说明为什么在这个时点做决定后人无法判断决策是否仍成立
备选方案证明做过比较无法评估是否还有更优解
权衡与代价架构决策几乎都是取舍只看到收益，代价被隐藏
验证方式让决策可证伪无法判断决策是否达成目标

深入自检

架构和功能需求的区别是什么？

功能需求回答「系统做什么」，靠代码实现；架构回答「系统怎么组织才能满足质量属性」——性能、可用性、可扩展性、安全性、可修改性。同一个功能可以有很多种结构，架构就是在这些结构中做取舍。

为什么质量属性必须写成可量化的场景？

因为「高性能」「高可用」无法验证也无法验收。写成场景（如「1000 并发下 P95 < 200 ms」「年停机 < 53 分钟」）才能做压测、定方案、验收，也才能在冲突时做权衡。

架构决策为什么一定要记录权衡？

因为架构选择几乎都是取舍：引入缓存换来延迟但带来一致性问题，异步化换来吞吐但带来最终一致。只写收益不写代价，后人会在不知情的情况下踩坑，或在条件变化后误以为该决策仍然成立。

4+1 视图和 C4 该用哪个？

C4 更适合日常沟通（四层缩放，Context 给业务、Container 给架构、Component 给开发）；4+1 更适合完整描述复杂系统（额外覆盖进程与物理部署视角）。实际中常以 C4 为主，涉及并发与部署时补运行时/部署视图。

怎么判断一个系统是过度设计？

看抽象是否对应「已发生的变动」：如果为了将来可能的第二种数据库、第三种消息源提前加了一层接口，而这些变动从未发生，就是过度设计。判据是——这层抽象当前是否为至少两个实现服务？若只有一个实现且无明确第二个，就该等变化来了再抽。
