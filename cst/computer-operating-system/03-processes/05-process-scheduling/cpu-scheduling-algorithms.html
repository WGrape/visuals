01调度要解决什么

第一层

概念与判定

调度器在「就绪队列」里挑一个任务上 CPU。目标是互相冲突的几件事：

指标定义谁在乎
周转时间完成时间 − 到达时间批处理
响应时间首次上 CPU 的时间 − 到达时间交互式/桌面
吞吐量单位时间完成的任务数服务器
公平性各任务获得的 CPU 份额多租户
可预测性延迟抖动实时系统
先分清任务类型：CPU 密集（一直算）和 IO 密集（算一下等很久）。好的调度让 IO 密集任务尽快回到 IO，把 CPU 让给 CPU 密集任务。

算法规则优点致命缺点
FCFS先来先服务简单、无饥饿护航效应：长任务堵住短任务

RR固定时间片轮转响应快、公平时间片难调；切换开销

MLFQ多级队列 + 动态反馈兼顾响应与吞吐实现复杂、参数多

03MLFQ：用反馈自动分级

MLFQ（多级反馈队列）不需要预知运行时间，而是观察行为：

  1. 设多个优先级队列，高优先级时间片短（如 8ms），低优先级时间片长（如 64ms）。
  2. 新任务进最高优先级队列。
  3. 用完整个时间片还没结束 → 降到下一级（说明是 CPU 密集）。
  4. 在时间片内主动让出（IO/睡眠）→ 留在原级（说明是 IO 密集，值得优待）。
  5. 定期把所有任务提升回最高级（防饥饿）。
这就是「让 IO 密集任务保持高优先级」的自动化版本：交互式进程频繁睡眠，自然留在高层，响应快；后台计算任务不断耗尽时间片，自然沉到底层。

04Linux 的调度类与 CFS 速览

Linux 用调度类分层，优先级从高到低：

调度类策略用途
stop—内核内部停机（最高）
dlSCHED_DEADLINE截止时间调度（EDF）
rtSCHED_FIFO/SCHED_RR实时任务，抢占普通任务
fairSCHED_NORMAL（CFS/EEVDF）普通进程
idleSCHED_IDLE只在 CPU 空闲时跑

每个调度类内部再选任务；高类有可运行任务时，低类完全得不到 CPU。这就是为什么一个死循环的 SCHED_FIFO 线程能把整机卡死。

普通进程的 nice 值范围 -20 ~ +19，只影响 fair 类内部的相对权重，无法让它跑赢实时任务。

05实时调度：SCHED_FIFO / RR / DEADLINE

策略抢占规则适用
SCHED_FIFO同优先级不抢占，直到阻塞或让出短小确定的实时线程
SCHED_RR同优先级时间片轮转多个同优先级实时线程
SCHED_DEADLINE按 runtime/deadline/period 做 EDF周期性硬实时任务
# 把 pid 1234 设为 FIFO 优先级 50
chrt -f -p 50 1234

# 查看调度策略与优先级
chrt -p 1234
ps -eo pid,cls,rtprio,ni,comm
实时任务必须可预测地阻塞。一个 FIFO 死循环会饿死所有普通任务，甚至让内核线程（如 ksoftirqd）无法运行。生产上用 cgroup 限制实时带宽（cpu.rt_runtime_us）兜底。

06排障与边界

第三层

排障与边界

  • 优先级反转：低优先级任务持锁，高优先级任务等锁，中优先级任务却抢占了低优先级 → 高优先级被无限期拖延。解法：优先级继承（PTHREAD_PRIO_INHERIT）或优先级天花板。
  • CPU 亲和性：任务被绑在单核（taskset），多核机器上仍可能只用一个核。
  • cgroup CPU 限额：容器 cpu.max 设太小，进程表现为「CPU 不满但很慢」，看 cpu.stat 的 throttled 计数。
  • 调度延迟：不是所有「慢」都是 CPU 不够，可能是等锁、等 IO、或 runqueue 排队。看 /proc//schedstat。

07原理与取舍

第四层

原理与取舍

所有通用调度器都在做同一件事：用「历史行为」预测「未来需求」。SJF 需要预知运行时间（不可得），MLFQ 用「是否耗尽时间片」间接推断，CFS 用「已获得的虚拟运行时间」衡量公平。

取舍选择 A选择 B
响应 vs 吞吐小时间片（响应快）大时间片（切换少）
公平 vs 效率严格轮转让 IO 密集优先
通用 vs 实时CFS 公平FIFO/DEADLINE 确定

深入 Q&A

Q：为什么 Linux 不给普通进程「绝对优先级」？
A：绝对优先级会导致饥饿。nice 只调权重，配合 vruntime 保证每个任务最终都能跑，避免「低优先级永远得不到 CPU」。

Q：多核上调度器还要做什么？
A：负载均衡——把任务从忙核迁移到闲核，同时考虑缓存亲和性（尽量不迁移，迁移代价是缓存失效）。
