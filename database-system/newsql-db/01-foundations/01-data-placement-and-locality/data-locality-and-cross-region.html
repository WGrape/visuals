分布式数据库的数据位置与跨地域延迟

读写是否跨地域，取决于副本位置、一致性要求和事务访问的分片。

核心机制

副本靠近用户可缩短某些读取的网络距离，但强一致读写常需联系当前主副本或满足法定多数。把副本放在远端不自动使所有请求本地完成。

跨地域事务还可能访问多个分片，并增加提交确认、冲突等待及故障切换成本。应先区分读多写少、同地域交易与跨地域交易。

用一个例子看过程

用户在上海；订单主副本在上海；库存主副本在新加坡。
创建订单并扣库存是一笔跨地域、跨分片事务。

画访问路径

标出客户端、分片主副本、其他副本与查询协调节点的位置。

明确一致性

区分强一致读、事务写和允许过期的副本读，各自记录延迟。

调整布局

按交易亲和性放置数据；再用故障演练验证可用性和数据约束。

观察、原因与处理

观察原因或含义处理与验证
本地读仍慢需要远端主副本或一致性确认核对读语义和实际副本路径
写入长尾高跨地域确认与冲突等待分解网络、排队与提交耗时
切换后吞吐骤降新主位置或容量不同测试故障后的流量路径和容量

按请求类型画真实网络路径

近端副本可能让允许陈旧的读取就近完成；强一致读取则可能需要当前主副本、读屏障或其他确认。写入通常要经过主副本并等待复制协议要求的确认。事务若又访问远端分片，跨分片协调和锁等待也进入关键路径。因此“用户附近有副本”只能说明布局，不能推出全部读写都在本地完成。

设三副本位于上海、上海和新加坡。正常时，多数确认可能由同城两个副本完成；若故障后只剩上海与新加坡，确认可能需要跨地域往返。若三副本分布在不同大洲，多数确认通常更远。这只是路径推演，具体产品的租约、读策略和提交协议仍须实测。

四项布局约束

约束要问的问题验证方式
交易亲和性常一起写的数据是否跨分片按事务统计涉及的分片和地域
数据驻留数据能否离开指定地域核对副本、备份与日志位置
故障域能容忍几处机房或地域故障实际故障演练
读取新鲜度允许多旧的副本结果读后写一致性测试

决策前画正常和故障两张拓扑图，并按真实客户端地域占比测量。记录主副本迁移、热点分片、跨地域流量费用以及故障后的剩余容量。迁移数据位置还会产生全量搬迁与切换期额外负担。

练习：为什么读快了，写仍慢

把只读副本放到用户城市后，报表查询变快，结算写入仍很慢。请标出订单、库存和支付分片的主副本位置，检查是否存在跨地域事务，再分解复制等待与协调耗时。继续增加只读副本不一定缩短强一致写的提交路径。

边界与误区

副本读的陈旧程度、数据驻留规则和故障容忍要求必须一并评估。强一致性、低跨洲延迟和任意位置写入不能靠一个配置同时免费获得。

用两个场景检查布局是否合理

场景一：内容浏览主要在上海，允许数秒陈旧的浏览数据在上海副本读取，而少量编辑请求发送到主副本所在地。这种布局可能改善读延迟，但业务必须容忍刚编辑后短时间读到旧值，或者对同一用户使用读后写一致性策略。场景二：结算要同时更新订单和库存，两个主分片分处上海与新加坡。即使浏览查询已变快，结算仍跨地域协调。需要评估交易亲和性、主副本位置与一致性约束。

故障时常常是另一套性能画像。某地域退出后，剩余副本可能满足法定多数却容量不足，或多数确认距离明显增加。因此容量规划不能只按正常流量的平均延迟计算；要测一次地域故障后的 P95/P99、排队时间和写入错误率。数据复制越分散，容灾可能越好，但传播成本、费用与故障后路径也更复杂。

为迁移计划设回滚点：在移动主副本或调整数据区域前，确认备份、同步进度、流量切换顺序以及数据驻留要求。迁移期的双倍网络或存储成本应进入预算。最终以用户关键操作的端到端延迟与错误率判断效果，不用“本地副本数量”当作成功指标。

延迟预算的一个估算

若一次跨地域往返约 80 毫秒，事务路径中串行出现两次远端往返，单是网络下界就可能接近 160 毫秒，还未算排队、磁盘和冲突。这个估算不能代替实测，却能帮助发现“要求跨洲强一致写 P99 小于 20 毫秒”一类不合理目标。接着用追踪拆分客户端到协调节点、协调到参与分片、复制确认和应用处理时间。若产品支持近端读，也要注明陈旧程度与读后写语义。把延迟、故障域和数据驻留要求放在同一张决策表，才能解释为何选择某种副本布局。

进一步验证

还应按业务时间段分开测试：白天读流量高，夜间批处理写入高，最优副本位置可能不同。若读服务允许陈旧数据，要给出最大可接受滞后和实测滞后分布；“最终一致”四个字不足以支撑支付或库存决策。布局方案应附上故障切换后的容量与延迟数据。

补充判断

复盘一次跨地域慢请求时，最好同时保留客户端、协调节点和分片节点的时间戳，并校准时钟。只在客户端看到 300 毫秒，无法判断延迟来自网络、排队还是锁等待；分段追踪可以把布局问题与容量问题分开。

数据局部性与跨地域的代价

项目延迟说明
L1 缓存~1 nsCPU 内
L2/L3 缓存4~40 ns—
内存访问~100 ns比 L1 慢 100 倍
SSD 随机读~100 µs比内存慢 1000 倍
同机房网络0.2~1 ms—
同城跨 AZ1~3 ms物理距离 10~100km
跨省（北京-上海）20~30 ms—
跨国（中美）150~250 ms光速限制：地球半周约 67ms（单向）
优化手段做法效果
数据本地性把计算调度到数据所在节点Spark/Hadoop 的核心思想
单元化按用户分片，读写收敛在单元内跨地域多活的基础
读本地副本就近读取（follower read）延迟从 30ms 降到 1ms
缓存热数据放本地消除跨地域调用
异步复制跨地域只做异步同步写入不等待远程确认

跨地域事务为什么慢：一个 2PC 事务需要 4 次跨地域往返。北京↔上海 30ms RTT 下就是 120ms 的纯网络开销。如果这个事务还要读 3 次数据，就是 7 次往返 = 210ms。结论：跨地域部署必须让事务收敛在单地域内，这也是单元化架构的根本出发点。

实操配置

// TiDB：Placement Rules 控制数据放置
// 让某个表的 leader 固定在特定区域（ follower read 就近读）
ALTER TABLE orders ALTER PARTITION p_beijing
  ALTER PLACEMENT POLICY ROLE=leader REPLICAS=1;

CREATE PLACEMENT POLICY beijing_policy
  PRIMARY_REGION="bj" FOLLOWERS=2;
ALTER TABLE orders PLACEMENT POLICY=beijing_policy;

// 就近读（follower read）
SET tidb_replica_read = 'closest-replicas';   // 读最近的副本
// 或 'leader'（默认，强一致）/ 'follower'（任意 follower）

// 查看 Region 分布
SHOW TABLE orders REGIONS;
// 看每个 Region 的 leader 在哪台机器上，判断分布是否均衡
-- CockroachDB：区域配置（多地域的标准做法）
-- 1) 给节点打区域标签
-- cockroach start --locality=region=us-east-1,zone=us-east-1a

-- 2) 设置数据库的主区域
ALTER DATABASE app SET PRIMARY REGION "us-east-1";
ALTER DATABASE app ADD REGION "us-west-1";

-- 3) 表级的数据归位（GLOBAL / REGIONAL / REGIONAL BY ROW）
ALTER TABLE users SET LOCALITY REGIONAL BY ROW;
-- 效果：每行数据根据 crdb_region 列的值，自动放在对应区域
--      该区域的用户读写都在本地，延迟从 60ms 降到 2ms

ALTER TABLE config SET LOCALITY GLOBAL;
-- GLOBAL 表：所有区域都有完整副本，读本地（快），写需要跨地域共识（慢）
-- 适合「读多写极少」的字典表

-- 4) 查看数据的实际位置
SHOW RANGES FROM TABLE users;
SELECT crdb_region, count(*) FROM users GROUP BY 1;

症状原因处理

读到了旧数据读了异步复制的副本需要强一致就读 leader；或接受秒级延迟
某个地域特别慢Region 分布不均检查数据分布；调整 placement
切换主地域后很慢数据没跟着迁移执行数据归位；注意迁移本身要时间

最实用的原则：让数据靠近访问它的人，而不是让人靠近数据。跨地域多活的正确做法不是「所有数据 everywhere」，而是「按用户分片，各自的数据在自己区域」——这就是单元化。

自检

在用户附近加只读副本，能保证强一致写也变快吗？

不能。写入仍受主副本、复制确认和跨分片协调路径约束。
