动机

原则是为了对抗「变化」

软件唯一不变的就是变化。设计原则的本质目标是：让修改的成本尽可能低——改动一处不会连锁影响一片，新增功能不必推翻既有结构。

模块之间依赖越少、越抽象越好
🎯

实现可替换，行为仍正确
原则不是教条。它们描述的是「长期来看更容易维护的方向」，而不是每条都必须机械照做。过度套用原则同样会让代码变得复杂难读。

SOLID 之外的高频原则

DRY
不要重复知识。但不要为了 DRY 强行抽象——三次重复再考虑抽象往往更合适
😌
KISS
保持简单。能用直白写法就别套复杂模式，可读性本身是最高价值
🚫
YAGNI
不要为「将来可能要」的需求提前设计。先满足当前需求，等真的需要再扩展
🤝
迪米特法则 LoD
只与直接的朋友交谈——减少 a.b.c.d() 这种链式穿透，降低耦合
DRY 的滥用：两段代码长得像但语义不同，强行合并会产生一个谁都改不动的「万能函数」。判断标准是它们是否因同一个原因而变化，而不是长得像不像。
落地

什么时候该坚持、什么时候该妥协

  • 先写简单版本，等第二个、第三个相似需求出现时再做抽象——抽象需要样本。
  • 变化概率高的地方值得遵循原则（接口、插件点、外部依赖）；稳定的内部实现不必过度设计。
  • 用测试来检验设计：如果一个类难以下手写单测，通常说明耦合过重、职责太多。
  • 代码评审时看「改动的扩散范围」：改一个需求要动 10 个文件，往往是抽象边界划错了。

面试问答

高频问题

Q1：SOLID 分别指什么？
单一职责（一个类只有一个变化原因）、开闭原则（对扩展开放对修改关闭）、里氏替换（子类可替换父类）、接口隔离（不依赖用不到的方法）、依赖倒置（依赖抽象而非实现）。
Q2：依赖倒置为什么重要？
它让高层模块不依赖具体实现，替换实现时不必改高层代码，并且方便用 mock 做单元测试。这是可测试性与可扩展性的关键。
Q3：DRY 要一直遵守吗？
不。两段代码相似但变化原因不同时，强行合并会造成错误的抽象。判断依据是「是否因同一原因而变化」，通常等到第三次重复再抽象更稳妥。
Q4：什么情况下不应过度设计？
遵循 YAGNI：不要为臆想中的未来需求提前加抽象层。稳定的内部逻辑直接写清楚即可；把设计精力留给真正易变、需要扩展的点。
Q5：怎么判断一个类职责过多？
看它是否有多个「变化原因」（如既管业务规则又管数据库又管日志）；看是否难以命名；看单测是否难写。三者占其一就该考虑拆分。

SOLID 五原则：每条都要能说出“违反了会怎样”

原则一句话违反的典型症状代码信号
S 单一职责一个类只有一个改变的理由改个日志格式要动业务类类超过 300 行、方法超过 50 行
O 开闭原则扩展开放、修改封闭加一种类型就要改 switch满屏 if/else 判断类型
L 里氏替换子类必须能替换父类子类方法抛 NotImplementedError重写后行为变窄（前置条件更严）
I 接口隔离不要强迫实现不需要的方法实现类里一堆空方法接口方法 > 10 个
D 依赖倒置依赖抽象而非具体换个数据库要改一堆代码高层模块里 new 低层类

最实用的是 S 和 D：S 决定了你的类会不会变成“上帝类”；D 决定了你的代码能不能测试和替换（也是依赖注入的理论基础）。O 最容易被过度使用——不是所有地方都需要预留扩展点，“三次法则”：同一类变化出现第三次时才抽象。

其他重要原则（比 SOLID 更常用）

原则英文含义实践
DRYDon't Repeat Yourself不要重复三次法则：重复 3 次才抽象，2 次可忍
KISSKeep It Simple, Stupid保持简单能写 10 行就别写 100 行
YAGNIYou Aren't Gonna Need It别做用不到的功能不要预留“以后可能用”的扩展点
迪米特法则Law of Demeter只和直接朋友说话禁止 a.getB().getC().do()
组合优于继承Composition over Inheritance用组合代替继承继承超过 2 层就该警惕
关注点分离Separation of Concerns分层分模块Web 三层：Controller/Service/Repo

几个原则冲突时怎么选：YAGNI > DRY。不要为了消除两处相似代码就急着抽象——如果它们变化原因不同，抽象后反而会互相牵制（这是“错误的抽象比重复更糟”的经典教训）。等第三次出现、看清共性再动手。

重构示例

# 坏味道：过长参数 + switch 惊悚现身
def create_order(user_id, sku_id, qty, addr, coupon, pay_type, ...):  # 9 个参数！
    if pay_type == "alipay":  ...
    elif pay_type == "wechat": ...
    elif pay_type == "card": ...   # 每次新增支付方式都要改这里（违反 O）

# 重构后：参数对象 + 策略
@dataclass
class OrderRequest:                    # ① 参数对象（解决过长参数）
    user_id: int; sku_id: int; qty: int
    addr: str; coupon: str | None = None

class PaymentStrategy(Protocol):       # ② 策略接口（解决 switch）
    def pay(self, amount: int) -> str: ...

class Alipay: 
    def pay(self, amount): ...
class WechatPay:
    def pay(self, amount): ...

def create_order(req: OrderRequest, pay: PaymentStrategy) -> Order:
    # 新增支付方式 = 新增一个类，这里一行不变（符合 O）
    ...

# 用字典代替 if/elif 链（Python 里更轻量的做法）
PAYMENTS = {"alipay": Alipay(), "wechat": WechatPay(), "card": CardPay()}
def create_order(req, pay_type):
    return PAYMENTS[pay_type].pay(req.amount)

深入自检

单一职责的“职责”到底怎么界定？

用“变化的原因”来界定，而不是用功能数量。判断方法：问自己“这个类会因为几种不同的原因被修改？”——如果一个 OrderService 会因为“业务规则变了”和“日志格式变了”两种原因被改，它就有两个职责，应该把日志拆出去。量化参考：单一职责的类通常 < 300 行，方法 < 50 行，依赖 < 5 个。

依赖倒置具体怎么做？

三步：① 定义抽象接口（如 UserRepository）；② 高层模块只依赖接口（Service 里注入 UserRepository，不知道是 MySQL 还是 Redis）；③ 具体实现在入口处注入（main() 里 new MySQLUserRepo() 传进去）。收益有两个：可测试（单测时传 Mock）、可替换（换数据库不改业务代码）。Python/Go 这类语言用鸭子类型/接口天然支持，不需要像 Java 那样显式声明。

什么时候应该违反设计原则？

三种合理情况：① 性能关键路径——抽象带来的间接调用和数据拷贝可能有成本，热路径上有理由写得“直白”；② 一次性脚本/原型——不会长期维护的代码不必过度设计；③ 团队能力与工期——过度设计的复杂度和 bugs 也是成本。原则是指导不是教条，核心目标是降低长期维护成本，如果某个“原则”反而让成本升高，那就不要它。

怎么让团队真的遵守这些原则？

靠工具而非自觉：① Lint 规则——限制函数行数（如 pylint max-args=5）、检测圈复杂度（> 10 告警）；② Code Review checklist——把“参数超过 4 个”“函数超过 50 行”写成可勾选项；③ 依赖检查——用工具禁止循环依赖和跨层调用（如 ArchUnit、import-linter）；④ 重构纳入迭代——每迭代留 10 – 20% 时间还技术债，否则原则永远停留在 PPT 上。
