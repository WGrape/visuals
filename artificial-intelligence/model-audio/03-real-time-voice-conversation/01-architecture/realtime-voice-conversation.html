端到端实时语音对话

级联与端到端两条路线的差别、一次交互的延迟构成与三个真正有效的压缩手段、端点检测为什么只能做到「错了也能恢复」、全双工与回声消除的工程要点。

两种架构：级联 vs 端到端

级联（ASR → LLM → TTS）
  • 三段各自独立，可单独替换与调优
  • 中间产物是文本，可观测、可插入业务逻辑、可过滤
  • 代价：延迟 = 三段之和，且端点检测错了会整体错位
端到端（语音进语音出）
  • 模型直接处理语音并输出语音，保留语气、情绪、非语言信息
  • 延迟更低，支持自然的打断与重叠
  • 代价：中间没有可靠文本，难调试、难加业务规则、难以审计
现实里多数产品是混合：端到端模型负责自然交互与快速响应， 同时在旁路用 ASR 产出文本做记录、审核与业务触发。不要让"有没有文本"成为事后才发现的需求盲区。

延迟预算：把每一段的时间摊开

最重要的一条：把流水线做成流式的，而不是三段串行。 串行模式下任何一段慢都会全额累加；流式重叠后，用户感知的延迟主要取决于「检测到用户说完了」到「第一句合成完成」这一段。

端点检测：什么时候认为"说完了"

这是实时语音最难也最影响体验的一环。判早了会打断用户，判晚了会让人觉得迟钝。

信号作用局限
静音时长最简单：静音超过阈值就判定结束思考停顿、环境噪声、句末气音都会误判
语义完整性结合文本判断是否像一句完整的话依赖 ASR 结果，短句（"嗯""好"）难判断
韵律与能量句末音高下降、能量衰减疑问句上升语调会误判为未结束
多模态结合摄像头/上下文判断是否在说话成本高，多数场景不可得
工程上的现实做法：给一个自适应阈值 + 兜底超时。 先用较短的静音阈值快速响应（牺牲一点误判率），同时在检测到疑似结束时再等一个很短的窗口确认； 超过绝对超时就强制结束。不要追求完美判断，追求"错了也能优雅恢复"——这就是打断机制存在的理由。

全双工与回声消除

半双工
对讲机模式：说的时候不能听。实现简单，体验生硬。
全双工
可同时说和听，允许打断与重叠。需要 AEC 与更复杂的状态机。
AEC 回声消除
设备播放的声音会被麦克风重新采集，形成回声让模型"听到自己"。 没有 AEC 的实时语音一定会出现自激或误识别。
  • 参考信号必须对齐：AEC 需要把"正在播放的音频"作为参考送给算法，延迟对不齐就消不干净。
  • 播放中断要及时：用户打断时要立刻停止播放并清空缓冲，否则残留音频继续被采集，形成假打断。
  • 状态机要显式：聆听 / 思考 / 播放 / 被打断 四个状态的迁移条件必须写清楚， 否则会出现"模型说自己也听自己"的死循环。

上线清单

  1. 分环境测延迟：安静环境只是理想值，必须在噪声、远场、弱网下测 P95。
  2. 定义可接受的打断行为：用户打断后是丢弃回答、还是记住并稍后补全？
  3. ASR 纠错与兜底：识别失败时是让用户重复、还是走文本输入？
  4. 内容安全：语音链路的两端（输入转写、输出合成）都要过审核，端到端模型的内部表达可能不经过文本层。
  5. 降级路径：模型服务超时、网络抖动时退到什么形态？
  6. 成本计量：按音频时长计费的模型，长会话与静音也在计费——是否需要静音裁剪？
最容易被忽略的一项：静音也在花钱。 按分钟计费的语音服务，如果用户开着麦克风但长时间不说话， 级联方案可以用 VAD 跳过静音段，端到端方案则要看服务是否支持。上线前确认计费口径。

核心速览

一句话把 ASR → LLM → TTS 串成一条低延迟流水线，并支持随时被打断
延迟预算端到端 500~800ms 才有「对话感」，超过 1.5s 就明显卡顿
核心技术VAD 断句、流式 ASR、流式 LLM 输出、首包优先 TTS
最难的部分打断：用户一开口就要立刻停掉正在播放的语音
实时语音对话全链路：每一环都必须流式，否则延迟叠加到不可接受

一、延迟预算怎么拆

环节预算优化手段
音频采集与上传20~60ms小分片上传（20~40ms 一包）、就近接入
VAD 判定说话结束100~300ms语义端点检测，别只看静音时长
ASR 识别150~300ms流式模型、热词、流式标点
LLM 首 token200~500ms小模型 / 投机解码 / 预填充缓存
TTS 首包音频150~300ms流式声码器、一收到句号就合成
网络往返50~150ms边缘节点、长连接复用
为什么「首包延迟」比「总延迟」更重要

用户感知的是「我说完之后多久听到第一个字」。只要第一个字来得快，后面的内容边播边生成，体验就是流畅的。因此所有优化都要围绕缩短首包：LLM 还没写完就先把第一句送去 TTS，这就是「句级流式」。

二、打断（Barge-in）怎么做

这是实时语音对话最难也最能决定体验的一环。用户插话时，系统必须在 200ms 内停住：

本地 VAD 优先客户端先做一轮 VAD，一检测到人声立刻停止播放并上报
服务端 VAD 确认避免把回声当成用户说话（需要回声消除 AEC）
立即取消生成向上游发送 cancel，LLM/TTS 立即中断并释放资源
丢弃已排队音频播放队列要能被一键清空，否则会继续播完旧内容
保留上下文被打断的那一轮要记录，用户接着说时语义要连贯
// 典型的会话状态机 type TurnState int const ( Idle TurnState = iota // 等待用户说话 Listening // 正在收音（VAD 已触发开始） Thinking // ASR + LLM 处理中 Speaking // 正在播放 TTS 音频 ) // 打断事件只在一个状态下有意义 func (s *Session) onUserSpeechDetected() { switch s.state { case Speaking: s.player.Stop() // 1) 立刻停播放 s.tts.Cancel() // 2) 取消还在合成的音频 s.llm.Cancel() // 3) 取消还在生成的文本 s.state = Listening case Thinking: s.llm.Cancel() s.state = Listening case Idle: s.state = Listening } }

三、回声消除为什么绕不开

如果用扬声器播放，麦克风会把 AI 的声音再录进去，造成：① 误触发打断；② ASR 把 AI 的话识别成用户的话。解决办法按优先级：

手段做法适用
硬件方案用耳机，物理隔绝体验最好，但场景受限
AEC 回声消除用播放信号作为参考，从录音中减去必须做，WebRTC 自带成熟实现
播放期间降灵敏度正在播放时提高 VAD 触发阈值简单兜底，但会漏掉真打断
服务端二次确认客户端报打断后服务端用文本上下文判断降低误判率

四、和纯文本对话的架构差异

维度文本对话实时语音对话
传输一问一答，短连接或 SSE长连接双向流（WebSocket / WebRTC）
状态基本无状态有会话状态机，需要管打断与上下文
延迟敏感首 token 延迟即可首包音频延迟，且全程流式
错误处理重试即可音频流中断要做平滑恢复，不能重头再来
资源占用请求结束即释放长连接期间持续占用，并发成本更高

五、深入自检

为什么不能等 ASR 出完整结果再给 LLM？

因为一句话平均 2~4 秒，等说完再处理，光 ASR 就吃掉大半延迟预算。流式 ASR 能边说边出字，虽然中间结果可能被修正，但只要 VAD 判定结束后做一次终稿确认即可。

LLM 输出一半被打断，那半句要保留吗？

建议保留到上下文里（标注为未说完），因为用户打断往往是在接话。但如果用户明显是换话题（比如「算了，问个别的问题」），就应该丢弃。判断依据是打断后新输入的语义相关性。

TTS 为什么不能等 LLM 全部生成完？

LLM 生成一段回复可能要 1~3 秒，等完再合成首包延迟就爆了。正确做法是按标点/语义切句，收到第一句立刻送 TTS，后续句子流式追加。

延迟抖动比平均延迟更影响体验吗？

是。音频是连续播放的，一次 500ms 的抖动就会造成明显卡顿。因此要做播放缓冲（200~400ms），用少量固定延迟换取平滑播放。

WebRTC 和 WebSocket 怎么选？

需要回声消除、抗抖动、弱网自适应就用 WebRTC（浏览器端成熟）；服务端到服务端、或者客户端已自带音频处理，用 WebSocket 更简单可控。

延迟预算端到端 500~800ms
最难一环打断要在 200ms 内生效
必备前置回声消除 AEC
