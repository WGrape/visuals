动态数组扩容的均摊分析：某次复制 8 个元素，为什么 append 仍是 O(1)

沿容量 1→2→4→8→16 的九次追加，手数复制次数、总成本与最坏单次成本。

先区分三种提问

动态数组末尾追加一个元素，若当前容量还有空位，只需把元素写入末尾，通常是常数时间；若已满，必须申请更大的连续空间、复制旧元素，再写入新值，这一次可能花 O(n)。因此“每次 append 最坏 O(1)”是错的。正确的常见结论是：按几何比例扩容的一长串 append，平均到每次的摊销成本为 O(1)。均摊说的是任意长操作序列的总成本上界，不是保证某次请求永远没有延迟尖峰。

这里默认数组元素复制成本相近、容量按 2 倍增长且内存分配成功。不同语言可能使用其他增长因子，也可能有对象构造、写屏障或内存搬迁等额外开销。分析先说明模型，再谈实际实现。

图解：九次追加的扩容账本

沿箭头逐步核对输入、变换和输出；下面的推演可以逐步切换。

九次追加手算

初始容量为 1，连续插入第 1 个元素无需搬运。插入第 2 个时容量从 1 扩到 2，复制 1 个；第 3 个时扩到 4，复制 2 个；第 5 个时扩到 8，复制 4 个；第 9 个时扩到 16，复制 8 个。九次追加共写入新元素 9 次，旧元素被搬运 1+2+4+8=15 次，在这个简化模型里总移动或写入次数为 24。第 9 次单独就需要复制 8 个旧元素，明显不是常数成本。

若只看第 2、第 3、第 5、第 9 次，会觉得越来越慢；但这些昂贵扩容越来越稀疏。容量翻倍后，下一次扩容前通常有与旧容量同量级的便宜追加可分摊成本。

逐步推演

容量为 1

第 1 次追加直接写入。

逐次翻倍

第 2、3、5、9 次分别复制 1、2、4、8 个旧元素。

合计九次

复制 15 次，新元素写入 9 次，共 24。

推广 n 次

几何级数复制总量 O(n)，均摊每次 O(1)。

为什么总复制数是线性的

插入 n 个元素时，发生的复制规模近似 1、2、4、8……，直到小于 n 的某个幂。几何级数的总和小于 2n；再加上 n 次新元素写入，总操作数小于约 3n 的量级。常数会因起始容量与计费方式不同而变，但总成本仍 O(n)。用总成本除以 n，得到每次追加摊销 O(1)。这个证明不是说每个元素只复制一次：最早的元素可能在每次扩容都被复制，但整个序列的复制工作仍受几何级数约束。

如果每次只增加固定容量 1，插入第 n 个元素可能复制 n−1 个，总复制约 1+2+…+(n−1)=O(n²)，均摊 O(n)。增长策略决定结论，不能把动态数组的 O(1) 均摊直接套到任意扩容方式。

记账法的直觉

可以给每次便宜的追加多收一点“虚拟费用”，把暂时没用到的额度存起来，等未来扩容时支付复制旧元素的费用。比如每次操作收取固定常数单位，而实际当次只写入一个元素，剩余余额累积在已有元素或数组上。两倍扩容意味着在下次复制前已经经历了足够多次追加，存款足以支付一次大搬运。严格证明要保证任何前缀操作序列的余额不为负；只说“平均一下”却不写总和，不足以证明。

势能法把这份存款写成状态函数。不同教材会选不同势能，例如与已占容量和空位数有关；无论选哪种，摊销成本等于实际成本加势能变化，整段求和时中间变化抵消。手算题用几何级数最直观，想推广到复杂数据结构时记账或势能更方便。

删除和缩容不能随意对称

若一满就扩容、一降到容量一半就立刻缩容，在容量边界附近反复插入、删除，可能每步都触发大量复制。例如容量 8、元素数在 4 与 5 之间摆动，若阈值设计不当，会频繁缩到 4 又扩到 8。常见策略是给扩容和缩容之间留滞回区间，例如满时扩、降到四分之一左右才缩，避免抖动。具体阈值还要权衡内存浪费与延迟。

垃圾回收语言中，缩容是否真的把底层数组还给系统也取决于引用和运行时。只看逻辑长度下降不能断定内存已释放。

均摊复杂度不能替代尾延迟

在线请求若恰好撞上第 9 次扩容，用户仍会感受到复制 8 个元素的延迟；数据量变成几百万时，这个尖峰可能更明显。实时场景可提前预留容量、分块存储或把大规模搬迁移到后台，但这些方案有内存或实现复杂度代价。需要用 P95/P99 延迟与内存占用验收，而不能仅引用 O(1) 均摊。

数组元素若是复杂对象，复制可能涉及构造、析构或引用计数，也要用真实基准测试。渐进复杂度描述输入规模增长的结构，不直接等于某语言某机器的毫秒数。

把追加次数扩到 17，容量会从 16 扩到 32，再复制 16 个旧元素；累计复制 1+2+4+8+16=31。比较 n=9 与 n=17 的总复制数，二者都低于 2n。再把扩容规则改为每次只加 1，列出前 5 次复制数 0、1、2、3、4，观察总和开始呈二次增长。最后找出“单次最坏”“序列总成本”“均摊每次”三种答案，避免考试中把它们混写。

第一层 · 概念与判定：什么是「均摊」

一句话：单次操作的最坏代价可能很高，但把 n 次操作的总代价加起来除以 n，平均值很低——这个平均值就是均摊复杂度。

概念含义举例
最坏单次某一次操作的最高代价动态数组扩容那一次是 O(n)
均摊n 次操作总代价 / nappend 均摊 O(1)
期望（平均）对随机输入的平均快排平均 O(n log n)
  • 信号一：某操作「偶尔很贵、通常很便宜」，且贵的那次之后会有一段便宜期 → 适合均摊分析。
  • 信号二：动态数组 append、并查集的 find（路径压缩）、单调栈的弹出，都是典型的均摊 O(1)。
  • 信号三：如果每次操作都可能同样贵 → 均摊帮不上忙。

关键区分：均摊 ≠ 平均（期望）。均摊是确定性的（对任意输入序列都成立）；期望依赖于输入的随机性假设。

第二层 · 参数·命令·量化：三种分析方法

方法思路优点适合
聚合分析直接算 n 次操作的总代价，再除以 n最直观动态数组 append
记账法给便宜操作「多收」一点，存起来付给贵操作形象易懂栈的 multipop
势能法定义势能函数 Φ，摊还代价 = 实际 + ΔΦ最通用、严格并查集、伸展树

动态数组的聚合分析（容量满时翻倍扩容）：

三种均摊分析方法

# 聚合分析：n 次 append 的总代价
# 扩容发生在 size = 1, 2, 4, 8, ..., 2^k 时，各搬移 1, 2, 4, ..., 2^k 个元素
# 总搬移 = 1 + 2 + 4 + ... + 2^k = 2^(k+1) - 1 < 2n
# 加上 n 次「写入自身」的 O(1)，总代价 = n + 2n = 3n
# => 均摊 3n / n = O(1)

# 记账法：每次 append 收 3 个单位
#   1 个单位：写入当前元素
#   2 个单位：存起来（1 个给自己将来被搬，1 个给别人被搬）
# 扩容时搬移的开销由之前存的钱支付 -> 永不透支

# 势能法：定义 Φ = 2 * size - capacity
#   append 不扩容：实际 1，ΔΦ = 2        -> 摊还 3
#   append 扩容  ：实际 1 + size，ΔΦ = 2 - size -> 摊还 3
#   两种情况摊还代价都是 O(1)

import sys
lst = []
for i in range(10):
    cap = sys.getsizeof(lst)                 # 粗略观察容量变化
    lst.append(i)
    print(i, len(lst), cap)
参数常见取值影响
扩容倍数2 倍（最常用）均摊 O(1)；倍数越小扩容越频繁
Python list 增长模式约 1.125 倍 + 预分配内存更省，仍均摊 O(1)
Go slice 增长小 slice 翻倍，大 slice 约 1.25 倍同上
初始容量可指定（如 make([]int, 0, n)）预分配可完全消除扩容

量化结论：动态数组 append n 次，总元素搬移次数 < 2n，总代价 < 3n，所以均摊 O(1)。扩容倍数必须大于 1 的常数倍（不能是「每次只加 1 个容量」，那会退化成 O(n)）。

第三层 · 排障与边界：均摊分析的坑

坑后果正确做法
扩容倍数写成 cap+1均摊退化成 O(n)必须是几何增长（乘以常数倍）
把均摊当成最坏用在实时系统偶发卡顿（扩容那一次）实时场景要预分配容量
混淆均摊与期望分析错误均摊是确定性的，不依赖随机输入
shrink 时立即缩容扩容-缩容震荡，反复 O(n)用滞后：只在 size < capacity/4 时才缩一半
以为 append 一定 O(1)单次最坏是 O(n)明确「均摊 O(1)」与「最坏 O(n)」的区别
  • 排查顺序：先确认扩容是几何增长 → 再算总搬移次数是否 < 2n → 最后确认缩容有滞后。
  • 边界一：均摊 O(1) 不排除某一次操作是 O(n)。对延迟敏感的系统（实时、高频交易）必须预分配。
  • 边界二：缩容如果和扩容用同一个阈值（满了就扩、不满就缩），会在临界点反复搬移——必须加滞后区间。
  • 边界三：PHP / Python 等语言的数组是「哈希表 + 有序」混合结构，实际开销比纯动态数组复杂。

预分配消除扩容

# 预分配：完全消除扩容开销（已知规模时强烈推荐）
n = 1_000_000
# Python
lst = [0] * n                    # 一次性分配
# Go
s := make([]int, 0, n)           # 预分配容量
# C++
std::vector<int> v; v.reserve(n);
扩容倍数取多少最好？

2 倍最常用，因为它让「搬移总量 < 2n」这个上界很干净，且内存浪费不超过 2 倍。倍数越大扩容越少但内存浪费越多——工程上常见的折中是 1.5～2 倍（Go 在大 slice 上用约 1.25 倍，Python 约 1.125 倍，都是为了省内存）。

为什么缩容要用 1/4 而不是 1/2？

为了滞后（hysteresis）：如果 size 降到 capacity/2 就缩到一半，那么紧接着一次 append 又会触发扩容，形成震荡。用 1/4 阈值 + 缩到 1/2，扩容与缩容之间就有了一个缓冲带，避免频繁搬移。

并查集的 find 为什么是均摊 O(1)？

严格说是 O(α(n))（反阿克曼函数，实践中 ≤ 5）。它同时用了「路径压缩」和「按秩合并」两个优化，需要用势能法证明——这也是势能法最著名的应用案例。

自检

第 9 次 append 复制 8 个元素，还能说这一次操作最坏 O(1) 吗？

不能。该次最坏 O(n)；对一长串按倍数扩容的追加，才有每次摊销 O(1)。
