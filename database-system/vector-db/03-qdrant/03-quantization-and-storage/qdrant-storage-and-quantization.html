①三种量化与黄金配置组合

Qdrant 的量化支持三种粒度，选择依据不是「哪个压得狠」，而是你的维度、内存缺口和延迟预算。

类型配置键压缩比（payload）默认关重排时的召回适用
标量 int8scalar: {type: int8}4×很高（几乎无感）默认首选
二值binary: {}32×低，必须重排维度 ≥ 1024 的高维 embedding
乘积product: {compression: x16}16× 起中，需重排内存极度紧张
PUT /collections/docs
{
  "vectors": {
    "size": 1024,
    "distance": "Cosine",
    "on_disk": true              # 原向量放盘
  },
  "quantization_config": {
    "scalar": {
      "type": "int8",
      "quantile": 0.99,          # 裁掉 1% 极端值
      "always_ram": true         # 量化码常驻内存
    }
  },
  "optimizers_config": { "indexing_threshold_kb": 20000 }
}
on_disk: true + always_ram: true 是这套配置的核心组合：原向量在磁盘上占空间，量化码在内存里做粗筛。粗筛拿到的候选再回磁盘取原向量精排。

②内存估算公式与四个规模实例

内存到底要多少？可以用这条式子做一版估算（单位：字节/条）：

总量 ≈ N × [ 向量本体 + 图邻接表 + payload 均值 + 索引开销 ]

向量本体：
  FP32        = dim × 4
  int8 量化码 = dim × 1
  BQ 量化码   = dim / 8
图邻接表（HNSW，M 默认 16）：
  ≈ M × 2 × 4 = 128 B
payload：
  按字段类型累加（int 8B、float 8B、小字符串 ~ 几十 B）
规模配置向量本体图payload 估合计
100 万 × 768dFP32 全内存3.07 GB0.13 GB0.2 GB≈ 3.4 GB
100 万 × 768dint8 常驻 + 原向量落盘0.77 GB0.13 GB0.2 GB≈ 1.1 GB
1000 万 × 768dint8 常驻 + 原向量落盘7.7 GB1.3 GB2 GB≈ 11 GB
1000 万 × 1536dBQ 常驻 + 原向量落盘1.9 GB1.3 GB2 GB≈ 5.2 GB
第二条到第三条的对比值得注意：从 100 万涨到 1000 万，内存涨了 10 倍，但图开销成了不可忽视的大头（1.3 GB）。如果还想压，只能降 M 或者换 IVF 体系 —— 这时候「量化已经没得压了」是正常的。

③payload 落盘与索引该建在哪些字段

Qdrant 的 payload 默认落盘（on_disk_payload 在较新版本默认 true），这意味着每个返回结果的 payload 都要读盘。这个开关的取舍很实际：

场景建议理由
结果只需 id + scorewith_payload: false免掉全部读盘开销，最快
结果要返回小 payload默认落盘即可OS page cache 会缓存热点，代价可接受
payload 大（长文本、base64）务必落盘进内存会直接吃光 RAM
过滤字段频繁必须建 payload 索引否则过滤退化为全段扫描
# 建 payload 索引（过滤前必做）
PUT /collections/docs/index?wait=true
{
  "field_name": "tenant_id",
  "field_schema": "keyword"      # keyword 适合精确匹配
}
# 数值范围过滤用 integer / float
# 全文检索用 text（会建倒排 + 分词）
只在 要过滤的字段上建索引。payload 索引本身要占内存和写入时间，给 20 个字段全建索引会让写入吞吐掉一个量级。

④快照备份：唯一的备份机制及其陷阱

快照（snapshot）是 Qdrant 唯一的备份机制，也是最容易在生产上翻车的一环 —— 它落盘在本地，不会自动上传云存储。

# 创建快照
POST /collections/docs/snapshots
# → result.name: docs-2026-10-23-12-00-00.snapshot

# 下载（务必拉到外部存储！）
GET /collections/docs/snapshots/docs-2026-10-23-12-00-00.snapshot

# 恢复
PUT /collections/docs/snapshots/recover
{ "location": "file:///qdrant/snapshots/docs-2026-10-23-12-00-00.snapshot" }

# 全量（整个存储）快照
POST /snapshots
默认快照保存在容器内 /qdrant/snapshots。容器重建 = 备份一起没。必须配一个定时任务把快照拉到 S3/OSS，并定期做恢复演练 —— 没演练过的备份等于没有备份。

⑤正文为什么不该进向量库

长文本字段（原文 chunk）是向量库最隐蔽的内存杀手：

内容单条大小100 万条占用建议
id + 短标签~50 B50 MB可进内存
标题 + 100 字摘要~400 B400 MB落盘
完整 chunk 正文（1000 字）~3 KB3 GB不要存向量库
整篇文档 / base64 附件数十 KB 起数十 GB存对象存储，库里只留 key
向量库里只该存「需要在过滤或排序里用到的标量」+「指回原始数据的主键」。正文放对象存储或业务库，检索拿到 id 后再回表 —— 这条纪律能省掉后面 80% 的内存麻烦。

⑥速记卡

三种量化

scalar 4× / binary 32× / product 16×+。默认选 scalar。

黄金组合

on_disk: true + always_ram: true：原向量落盘、量化码常驻。

图开销

M=16 约 128 B/条，千万级时是 GB 级大头。

payload 默认落盘

返回 payload 要读盘，用 with_payload: false 可免。

过滤必建索引

只给真要过滤的字段建，全建会拖垮写入。

快照要外传

默认只落本地盘，容器重建即丢失。

正文别进库

1000 字 chunk × 100 万 = 3 GB，存对象存储。

量化后必须重排

rescore: true + oversampling 2–3。

内存估算的纪律：先算向量本体，再加图，再加 payload，最后乘副本数。四步都算完，才不会出现「按向量大小买了机器结果 OOM」。
