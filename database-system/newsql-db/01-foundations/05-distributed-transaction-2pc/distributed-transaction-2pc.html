一句话总结：跨分片写要么全部成功、要么全部回滚——2PC 用"先投票、再决定"的两步协议保证原子性；但它让协调者成为关键，也带来阻塞与延迟代价。

01为什么需要原子提交

一条 SQL 涉及多个分片时，没有原子提交，就可能"分片 A 成功、分片 B 失败"，留下半成品。分布式事务要的是跨分片的 all-or-nothing：要么所有分片都提交，要么都不提交。

022PC 的两阶段

🗳️ 阶段一：Prepare

协调者问每个参与者"能否提交"。参与者锁资源、写 undo/redo 日志，准备好后投 yes；若任一环节失败则投 no。

✅ 阶段二：Commit / Rollback

协调者若收到全部 yes，发 commit；只要有一个 no，发 rollback。参与者按指令最终落定。

03阻塞问题：协调者是单点

如果协调者在阶段二发令前宕机，参与者已经 prepare（持锁）却不知道该提交还是回滚，只能阻塞等待直到协调者恢复。这期间相关资源被锁住，是 2PC 最被诟病的地方。各类优化（如 3PC、Percolator）都在设法弱化这个阻塞窗口。

04Percolator：去掉独立协调者

TiDB 用的 Percolator 模型不依赖一个独立的协调者进程，而是从参与者里选一个作为 Primary：

  • 每行数据有三个隐藏列：write（提交记录/版本）、lock（锁）、data（真实值）。
  • 提交时先提交 Primary 的状态；Secondary 的提交与否由"是否看到 Primary 已提交"来裁决。
  • 若中间崩溃，恢复时看 Primary 的状态：已提交则把 Secondary 补齐，未提交则回滚。
  • 配合多版本和乐观锁，读不阻塞写、写不阻塞读。

05未知提交（Uncertain Commit）

两阶段提交中，如果客户端在"协调者已决定但还没确认"时网络中断，客户端不知道事务最终是提交还是回滚。这个中间态必须由协议在恢复后裁决，而业务侧要能容忍重试——这正是幂等设计在分布式事务里特别重要的原因（见幂等设计）。

06开销

🌐 网络往返

至少多一轮 prepare + 一轮 commit 的网络交互，延迟明显上升。

🔒 锁持有

prepare 后持锁到 commit，冲突事务要排队或重试。

🔁 冲突重试

高并发写同分片时写写冲突频繁，重试成本计入延迟。

07常见疑问

2PC 为什么会在协调者故障时阻塞？
因为参与者已经 prepare（资源上锁、日志就绪）但没收到最终指令，既不能单方面提交（可能别的参与者投了 no）也不能单方面回滚（可能已该提交），只能等协调者恢复裁决。
Percolator 怎么去掉协调者单点？
它把"协调者状态"外化成 Primary 行上的提交标记，任何参与者/恢复线程都能通过读 Primary 来裁决 Secondary，避免了独立协调者进程宕机导致的全局阻塞。
业务侧怎么处理"未知提交"？
用幂等键重试。因为最终状态只会有"已提交"或"未提交"之一，重试同一条请求要么拿到首次结果、要么首次执行，客户端不会重复产生副作用。

为什么尽量让事务落在单分片？

单分片事务用本地事务即可，无 prepare/commit 的跨节点往返、无协调者阻塞窗口、无未知提交难题。跨分片 2PC 的延迟通常高一个数量级，且冲突重试成本更高。所以分片键设计的核心目标之一就是让高频事务单分片化。

深度补充：2PC 的参数与边界

第一层 · 概念与判定 两阶段提交（2PC）用协调者让多个参与者要么全提交要么全回滚，是分布式事务的基线协议。判定：需要跨库强一致、且能接受其阻塞代价时使用。

阶段动作阻塞点
Prepare各参与者写 undo/redo 并锁资源参与者投票前持有锁
Commit协调者发 commit，参与者落盘协调者单点
超时默认进入不确定/回滚资源长时间锁定

第三层 · 排障与边界

  • 协调者宕机在 Prepare 后、Commit 前，参与者锁长期不释放（阻塞）。
  • 网络分区导致部分提交、部分未决，需日志+对账补偿（3PC 也只能缓解）。
  • Prepare 阶段持锁，长事务会拖垮并发，需控制事务粒度。
  • 误把 2PC 当万能：高冲突场景应改最终一致 + 补偿（Saga/TCC）。
第四层 · 原理与取舍

2PC 用“先统一表决、再统一提交”换跨参与者原子性，代价是协调者单点与同步阻塞——任何一环失败都可能让资源锁住直到恢复。它提供强一致但牺牲可用性与延迟（CAP 偏向 C 与 P 之间反复横跳）。生产常用“2PC + 事务日志 + 超时兜底 + 补偿对账”组合，或用 TCC/Saga 把大事务拆成可补偿的小步，换更高可用。

实例与速查：2PC 兜底

-- 参与者在 Prepare 阶段写 undo/redo 日志并锁资源
-- 协调者超时未收到全部 YES，则发起全局回滚
-- 生产实践：2PC + 事务日志 + 超时兜底 + 补偿对账

-- 高冲突场景改用 Saga/TCC 把大事务拆成可补偿的小步：
--   TCC: Try(预留) -> Confirm(提交) / Cancel(释放)
  • 协调者单点且同步阻塞，Prepare 后宕机会让资源长时间锁定。
  • 网络分区可能造成部分提交/未决，需日志 + 定时对账补偿。
  • 长事务持锁会拖垮并发，控制事务粒度。
FAQ：2PC 能保证绝对不丢数据吗？

不能保证“不阻塞”。2PC 能保证“原子提交或不提交”，但在协调者崩溃且恢复前，处于不确定状态的参与者必须持有锁等待，这是它的固有缺陷（阻塞）。3PC 用超时和预询问缓解但引入更多复杂度，实践中常配日志与人工/自动补偿来兜底。

常见误区与延伸

  • 误区一：2PC 不会丢数据。2PC 保证原子提交，但协调者崩溃后处于不确定状态的参与者会长时间持锁（阻塞）。
  • 误区二：网络分区能自动恢复。分区可能造成部分提交/未决，必须靠日志与定时对账补偿。
  • 延伸：3PC 用预询问与超时减少阻塞，但引入更多往返与不一致窗口，实践中少用。
  • 延伸：TCC/Saga 把大事务拆成可补偿的小步，牺牲强一致换高可用，适合长流程业务。

一句话总结：2PC 用协调者与两阶段换跨参与者原子性，代价是阻塞与单点，生产需配事务日志、超时兜底与补偿对账。

决策速记

  • 强一致用 2PC：跨库原子提交，接受其阻塞代价。
  • 防阻塞：配事务日志、超时兜底与补偿对账。
  • 高冲突改用 Saga/TCC：把大事务拆成可补偿小步。
  • 别迷信：2PC 保证原子但协调者崩溃会持锁，需对账。

一句话：2PC 用两阶段换原子性，代价是阻塞单点，生产需补偿兜底。

横向对比与追问

  • 与 Saga 比：2PC 强一致但阻塞，Saga 用补偿换可用但需业务写回滚逻辑。
  • 与 TCC 比：TCC 把操作拆 Try/Confirm/Cancel，比 Saga 更显式但侵入更强。
  • 追问：为什么银行核心仍用 2PC？因为要强一致，宁可阻塞也不接受部分提交。
  • 追问：Raft/Paxos 与 2PC 什么关系？前者做副本一致性，后者做跨参与者事务，常配合使用。

小结：分布式事务是“一致性 vs 可用性”的取舍，2PC 偏 C，Saga/TCC 偏 A。

2PC 故障决策

  • 协调者在第一阶段后崩溃：参与者已写日志但未提交，恢复后收不到决策进入不确定态，需靠日志或对账兜底。
  • 参与者超时未收到 commit：默认应继续等待或询问其他参与者，不能自行回滚，否则可能与其他提交产生不一致。
  • 应对：引入超时 + 协调者持久化决策日志 + 崩溃恢复后重放；必要时升级 3PC 或 TCC 降低阻塞窗口。
