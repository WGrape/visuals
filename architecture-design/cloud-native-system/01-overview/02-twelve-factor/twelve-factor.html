12-Factor 应用

一份让 SaaS 应用『天生云友好』的经典方法论清单。

12 要素概览 Twelve-Factor

Adam Wiggins 提出，已成为云原生工程共识

核心精神：配置与代码分离、无状态可丢弃的进程、把后端(数据库/缓存)当附加资源、日志当事件流。这些原则让应用能随云弹性伸缩、随处部署。

最关键的几条

  • 配置存环境变量：同一份构建物在不同环境靠配置切换，而非改代码。
  • 进程无状态：任何实例可随时被杀/重建，状态外移到后端服务。
  • 日志是流：打到 stdout，由平台收集，应用不自管日志文件。
  • 环境等价：开发/测试/生产尽量一致，减少『我机器上能跑』。

面试高频问答

Q：12-Factor 现在还适用吗？
A：适用，且是云原生的思想前身。容器化把它进一步固化（镜像=构建物、环境变量=配置、stdout=日志流），本质一致。
Q：为什么强调『进程无状态』？
A：因为只有无状态，平台才能随时起新实例应对流量、杀掉异常实例而不丢数据；状态必须外移到数据库/缓存等后端服务。

12-Factor：云上应用的十二条军规

12-Factor 由 Heroku 的工程师在 2011 年提出，是构建 SaaS / 云原生应用的经验总结。它不是架构模式，而是一组工程约束——遵守它们，应用就能自然地做到可移植、可伸缩、易交付。

12-Factor 十二条按关注点分组

十二条逐条解读（上）

#原则要求违反的典型症状
Ⅰ基准代码一份代码库对应一个应用，多次部署各自独立；部署环境差异靠配置而非分支为每个客户维护一个分支，改个 bug 要合十几次
Ⅱ依赖显式声明所有依赖（package.json / pom.xml / requirements.txt），并在运行时隔离依赖系统全局安装的库，换个机器就跑不起来
Ⅲ配置配置（数据库连接串、密钥、特性开关）存于环境变量或配置中心，绝不进代码库把生产数据库密码提交到 Git
Ⅳ后端服务数据库、缓存、消息队列都视为「附加资源」，通过 URL/配置接入，可随意替换代码里硬编码了 MySQL 地址，换 Redis 要改代码
Ⅴ构建/发布/运行严格分离：构建（代码→产物）、发布（产物+配置→版本）、运行（启动进程）；发布版本不可变在线上直接改代码热更新，出问题无法复现与回滚
Ⅵ进程应用进程无状态且无共享；任何需要持久化的数据放后端服务会话存在本地内存，扩容后用户反复掉登录

十二条逐条解读（下）

#原则要求违反的典型症状
Ⅶ端口绑定应用自包含 Web 服务器，通过端口对外提供服务，不依赖外部容器注入必须部署到特定 Tomcat 才能运行，无法独立启动
Ⅷ并发通过增加进程实例横向扩展，而不是让单个进程变强（进程是一等公民）靠加内存和 CPU 纵向扩容，遇到单机上限就无解
Ⅸ易处理启动快速（秒级），可随时被杀；收到 SIGTERM 时优雅关闭（处理完存量请求）启动要 5 分钟，发布与扩容都极慢；强杀导致请求中断
Ⅹ环境等价开发、预发、生产尽可能一致（依赖、配置结构、人员介入方式）「在我机器上是好的」，上线就出问题
Ⅺ日志把日志当作事件流，输出到 stdout，由运行环境负责收集与路由日志写本地文件，容器一销毁日志就没了
Ⅻ管理进程数据迁移、一次性脚本等管理任务，与常驻进程使用同样的代码与配置运行迁移脚本单独放一台机器上手工跑，版本与线上不一致

最常被违反的三条：Ⅲ 配置（硬编码密钥）、Ⅵ 无状态（会话放本地）、Ⅺ 日志（写本地文件）。这三条恰好也是容器化路上最先踩的坑。

为什么这些原则在云上特别重要

因为它们直接决定能否自动扩缩

进程无状态（Ⅵ）+ 端口绑定（Ⅶ）+ 并发扩展（Ⅷ）三条是弹性的前提。

  • 有状态 → 新实例没有数据，扩了也白扩
  • 不绑端口 → 编排系统无法健康检查与接入流量

因为它们决定发布能否自动化

构建/发布/运行分离（Ⅴ）+ 易处理（Ⅸ）是滚动发布与快速回滚的基础。

  • 发布产物不可变 → 回滚就是切回上一版本
  • 启动快 + 优雅终止 → 滚动替换不中断服务

因为它们决定环境是否可信

显式依赖（Ⅱ）+ 环境等价（Ⅹ）消灭「环境不一致」这类最难排查的问题。

  • 依赖锁版本 → 构建可重现
  • 环境一致 → 预发验证过的行为在生产同样成立

因为它们决定可观测性

日志作为事件流（Ⅺ）让日志收集与容器生命周期解耦。

  • 写 stdout → 平台统一收集、检索、告警
  • 写本地文件 → 容器销毁即丢失，多实例无法聚合

12-Factor 之外：后来的补充

12-Factor 提出于 2011 年，随着云原生发展，社区补充了一些新条目（常称为 15-Factor）：

⑬ API 优先先设计并契约化 API，再实现；便于多方并行开发与集成
⑭ 遥测（Telemetry）除日志外，还要暴露指标、健康检查、链路追踪，构成完整可观测性
⑮ 认证与授权把身份贯穿到架构中，服务间调用也要认证（对应零信任趋势）

另外要注意 12-Factor 的适用边界：它面向的是「无状态的在线 Web/SaaS 应用」。有状态服务（数据库、消息队列）本身就不符合「无状态进程」原则，它们作为后端服务（Ⅳ）被引用即可，不需要自己遵守全部条目。

深入自检

配置为什么不能放进代码库？

四个具体原因：① 安全——数据库密码、API 密钥一旦进 Git，即使后续删除也仍存在于历史记录中，且任何有读权限的人都能拿到，是高频泄露源；② 环境差异——同一份代码要部署到开发、测试、生产，配置必须不同，写死在代码里就只能靠分支区分，又违反了「一份基准代码」原则；③ 变更成本——改个数据库地址要走一次完整的代码提交、评审、构建、发布流程，紧急情况下无法快速调整；④ 不可重现——镜像里带着生产配置，就无法安全地分发到测试环境。正确做法是代码读环境变量（或配置中心），部署时由运行环境注入，密钥类走专门的密钥管理服务。

「无状态」是不是说应用不能有任何数据？

不是。无状态指的是进程的内存和本地磁盘不保存需要跨请求延续的数据。应用当然要处理数据，但这些数据应该放在后端服务里：用户会话放 Redis、文件放对象存储、业务数据放数据库、定时任务状态放数据库并用分布式锁协调。允许的例外是「可重建的本地缓存」——丢了会变慢但不会出错，这是性能优化而非状态存储。检验方法：随机杀掉任何一个实例，用户是否完全无感？如果会掉登录、丢上传文件、任务重复执行，说明还有状态没外置。

日志写 stdout 有什么实际问题？

好处是平台可以统一处理：收集（Fluent Bit / Filebeat）、检索（ES / Loki）、告警、归档、采样，应用完全不用关心。需要注意的实际问题：① 必须是结构化日志（JSON），否则检索与聚合很痛苦；② 一行日志不要过长（有些收集器有单行长度限制，超长会被截断）；③ 不要把多行堆栈拆成多行输出，或确保收集器配置能识别多行合并；④ 注意日志量——高并发下全量 DEBUG 日志会吃掉大量 CPU 与存储，应分级并支持动态调整；⑤ 敏感信息（密码、身份证号）必须脱敏。

12-Factor 在今天还完全适用吗？

大部分仍然适用，尤其是容器与 K8s 环境下——里面的很多原则（无状态、端口绑定、日志流、快速启停）几乎就是 K8s 的硬性要求。但也有需要修正的地方：① Ⅲ 配置用环境变量在微服务数量多时管理成本高，业界多用配置中心（Nacos、Apollo）替代；② Ⅷ 并发强调进程模型，而今天多以容器副本为单位扩展，进程与容器是两层；③ 现代实践补充了遥测、API 优先、认证授权等条目（15-Factor）。总体看，12-Factor 作为一份 checklist 依然非常有价值，但不必教条——理解每条背后的目的比机械遵守更重要。
