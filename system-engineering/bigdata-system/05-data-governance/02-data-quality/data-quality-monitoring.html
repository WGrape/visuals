数据质量监控怎么落地

五个质量维度的规则模板、三层卡点位置与处置流程、让告警真正生效的运营要点

数据质量数据治理卡点监控
① 五个维度 ② 卡点位置 ③ 运营要点 ④ 疑问
数据质量不是「加一堆规则」，而是「在正确的位置设卡点 + 有明确的处置流程」。规则太多而没人处理，等于没有质量体系。

01五个质量维度与对应规则

维度在问什么典型规则怎么量化
完整性数据有没有缺行数非空、关键字段非 NULL、分区齐全空值率、分区缺失数
准确性值对不对金额非负、枚举值在范围内、金额与明细对得上异常值比例、对账差异额
一致性多处是否对得上主外键完整、跨表汇总一致、同一指标不同口径一致不一致记录数
及时性数据到没到分区按时产出、延迟低于 SLA产出延迟分钟数
唯一性有没有重复主键唯一、去重后行数不下降重复行数 / 重复率
-- 五类规则的 SQL 模板（可直接改表名复用）
-- 1) 完整性：关键字段空值率
SELECT dt,
       COUNT(*) AS total,
       SUM(CASE WHEN user_id IS NULL THEN 1 ELSE 0 END) AS null_uid,
       ROUND(SUM(CASE WHEN user_id IS NULL THEN 1 ELSE 0 END) * 1.0 / COUNT(*), 4) AS null_rate
FROM dwd_orders WHERE dt = '${bizdate}'
GROUP BY dt
HAVING null_rate > 0.001;      -- 超过 0.1% 即视为异常

-- 2) 准确性：金额非负 + 上下界
SELECT COUNT(*) FROM dwd_orders
WHERE dt = '${bizdate}' AND (amount < 0 OR amount > 1000000);

-- 3) 一致性：明细与汇总对账
SELECT (SELECT SUM(amount) FROM dwd_orders WHERE dt='${bizdate}') AS detail_sum,
       (SELECT gmv FROM ads_daily_summary WHERE dt='${bizdate}')   AS summary_gmv;
--   两者差值超过阈值（如 0.01 元或 0.01%）就要告警

-- 4) 唯一性：主键重复
SELECT order_id, COUNT(*) AS c FROM dwd_orders
WHERE dt='${bizdate}' GROUP BY order_id HAVING c > 1;

-- 5) 及时性：分区是否产出
SELECT CASE WHEN COUNT(*) = 0 THEN 'MISSING' ELSE 'OK' END
FROM dwd_orders WHERE dt='${bizdate}';
要点：规则要分阻断级（失败就停任务，如主键重复）和告警级（记录并通知，如空值率略升）。全部设成阻断会导致任务频繁失败，全部设成告警则没人处理。

02卡点位置与处置流程

位置校验什么失败怎么办为什么在这
入湖（ODS）格式、字段类型、行数量级、主键唯一阻断 + 通知上游脏数据挡在外面，避免污染全链路
加工层（DWD/DWS）业务规则、对账、枚举值阻断下游 + 保留现场防止错误被放大到所有下游
出仓（ADS/应用）与源系统对账、口径一致阻断 + 降级用昨日数据直接影响报表与决策
持续监控趋势类指标（行数波动、空值率趋势）告警 + 工单捕捉偶发与渐变问题

#   今日行数 / 近 7 日中位数，落在 [0.7, 1.3] 之外则告警
#   —— 绝对值阈值在大促、节假日必然误报
要点：最容易被忽略的是及时性：数据「算错」容易被发现，「没算出来」却常常没人察觉，直到业务方来问。每个关键表都要有产出时间监控与 SLA 告警。

03让规则真正生效的运营要点

  • 规则必须有责任人：每条规则绑定到具体的人/团队，否则告警无人认领。
  • 告警要能直接定位：消息里带上表名、分区、失败规则、样本数据、负责人。
  • 用波动检测代替绝对阈值：行数、空值率这类指标用「与历史同期比较」更准。
  • 定期清理失效规则：业务变化后规则会失真，误报多了大家就会屏蔽告警。
  • 质量结果要可视化：按表/按域展示质量分与趋势，让问题可追踪。
  • 先覆盖关键表：不要一次性给所有表加规则，先做影响最大的 Top 20 张表。
  • 要有降级方案：出仓卡点失败时是「用昨日数据」还是「不发」，必须提前定好。
# 质量告警的落地形态（调度任务里的伪代码）
def run_with_quality_check(dt):
    run_task(dt)                      # 先跑数据
    results = run_rules(dt)           # 再跑规则
    blocking = [r for r in results if r.level == 'block']
    warning  = [r for r in results if r.level == 'warn']

    if blocking:
        mark_partition_invalid(dt)    # 标记分区不可用，下游不会读到脏数据
        notify(owner, blocking)       # 通知责任人
        raise TaskFailed(blocking)    # 阻断调度

    if warning:
        notify(owner, warning)        # 只通知，不阻断
        save_quality_record(dt, results)

    save_quality_record(dt, results)  # 无论结果如何都留痕，供趋势分析

04常见疑问

问：规则要写多少条才够？

先写「能挡住已知事故」的那些。把历史上出过的问题列出来，每条对应一条规则，这比凭空设计几十条规则有效得多。之后再按新增事故逐步补充。

问：告警太多没人看怎么办？

三个动作：① 分级（阻断/告警/提示）；② 收敛（同一张表多个规则失败合并成一条告警）；③ 定期复盘误报，把长期误报的规则删掉或调阈值。告警的信噪比比数量更重要。

问：用什么工具？

轻量方案：SQL 规则 + 调度系统（Airflow 的 SQL check / Dataform 的 assertions），够用且零依赖。专业方案：Great Expectations / Soda / Deequ（规则管理更规范），或与数据目录工具集成（如 DataHub 的质量模块）。

问：数据质量该由谁负责？

谁产出谁负责。平台方提供规则框架与卡点能力，规则内容必须由懂业务的数据开发定义，否则规则会脱离业务实际（要么漏掉真问题，要么天天误报）。

质量分、告警分级与故障处置

质量规则按阻断 / 告警 / 提示三级管理，并绑定责任人与处置动作

质量要能被度量才谈得上治理。最简单的做法是把每张表的规则结果汇总成一个质量分，按域展示趋势，让问题可追踪、可对比。

评分维度权重建议怎么算说明
完整性30%1 - 关键字段空值率关键字段由业务方指定
准确性25%1 - 异常值比例金额范围、枚举合法性等
一致性20%对账一致记录 / 总记录与主数据源或汇总表比对
及时性15%按时产出天数 / 总天数按 SLA 判定是否按时
唯一性10%1 - 重复率主键重复比例

质量分落库与看板

-- 质量分汇总表（把规则结果落库，供看板查询）
CREATE TABLE dq_daily_score (
    dt        STRING,
    db_name   STRING,
    table_name STRING,
    owner     STRING,
    integrity  DOUBLE,   -- 完整性得分 0~1
    accuracy   DOUBLE,
    consistency DOUBLE,
    timeliness  DOUBLE,
    uniqueness  DOUBLE,
    score      DOUBLE,   -- 加权总分
    failed_rules STRING  -- 失败规则列表（JSON）
);

-- 看板查询：按域看质量趋势与责任团队
SELECT table_name, owner,
       ROUND(AVG(score), 3) AS avg_score_7d,
       MIN(score)           AS worst
FROM dq_daily_score
WHERE dt BETWEEN '${start}' AND '${end}'
GROUP BY table_name, owner
HAVING avg_score_7d < 0.95
ORDER BY avg_score_7d
LIMIT 20;
故障典型原因处置顺序
分区没产出上游延迟、调度失败、资源不足① 查调度日志 → ② 查上游依赖 → ③ 补跑 → ④ 通知下游延迟
行数暴涨/暴跌上游重复导入、过滤条件变化、业务异常① 对比历史中位数 → ② 查上游变更 → ③ 判断是否真异常
空值率突升上游字段改名、采集端改版① 定位哪几个字段 → ② 查上游发布记录 → ③ 回滚或补数
对账不一致口径变化、时区、去重逻辑不同① 确认口径文档 → ② 找出差异样本 → ③ 修正口径或修数据
主键重复重跑未清理、上游重复推送① 阻断下游 → ② 定位重复来源 → ③ 去重后重跑

落地逐条核对：

  • 规则绑定责任人，无人认领的规则等于不存在。
  • 分级管理：阻断 / 告警 / 提示，不要一刀切。
  • 质量分落库，按趋势看而不是只看当天是否通过。
  • 及时性单独监控：数据没产出比算错更常见也更隐蔽。
  • 用波动检测代替绝对阈值，避免大促/节假日误报。
  • 定期清理失效规则，误报多了大家会屏蔽告警。
  • 出仓卡点要有降级方案：用昨日数据还是停发，提前定好。
  • 先覆盖 Top 20 张关键表，不要一次性铺开。
  • 故障处置要有 runbook，把每类问题的排查顺序写下来。
