时序库存储布局：WAL、内存块、Block 与 compaction

写入路径的每个环节、Block 内部结构、chunk 大小的权衡，以及重启/删除/保留策略的底层行为

时序数据库存储WALBlockcompaction
① 写入路径 ② Block 结构 ③ Chunk ④ 运维 ⑤ 疑问
一句话总结：时序库的写入路径是「先写 WAL 保证不丢，再写内存块保证查询可见」，内存块攒够时间后整块落盘变成只读 Block，后台再把小 Block 合并成大 Block。理解这条链路，才能解释「为什么重启要等 WAL 回放」「为什么删除是标记而非立刻生效」「为什么旧数据不能改」这些行为。

01写入路径：WAL + 内存块

写入先落 WAL 再写内存块，攒够后整块落盘，后台再合并
  1. 样本到达：一条样本 = 序列标识 + 时间戳 + 值。
  2. 追加 WAL：先顺序写预写日志（只追加，很快），保证进程崩溃后能恢复。
  3. 写入内存块（Head）：写进当前活跃的 Head Block，此后查询就能看到它。
  4. 攒够后落盘：Head 达到时间跨度或大小阈值后，把这段数据压缩后写成只读 Block。
  5. 后台合并：多个小 Block 被合并成更大的 Block，减少文件数与索引开销。
  6. 到期整块删除：保留策略到期时，整个 Block 一起删——所以删除极快。
要点：「整块删除」是时序库保留策略能做得极其高效的原因：它不需要逐行 DELETE，直接删目录。代价是保留粒度必须是块/时间，不能精确到某条序列。

02Block 里装了什么

组成部分内容作用
chunks压缩后的样本数据块真正的数据，按序列分组压缩
index序列 → chunk 的映射 + 倒排索引按标签快速定位到序列，再定位到它的数据块
meta时间范围、序列数、统计信息查询前先按时间范围过滤掉整个 Block
tombstones删除标记（软删除）真正的数据要等 compaction 时才物理清除

查询时如何利用 Block：先用 meta 的时间范围过滤掉不相关的 Block（这一步几乎不花代价），再用 index 按标签找到目标序列，最后只解压命中的 chunks。这就是为什么时序库查询一个月的数据也可能很快——大部分 Block 在第一层就被跳过了。

03Chunk：压缩与查询的基本单位

设计选择块大一点块小一点
压缩率好（参考窗口长）差
查询放大差（要解压更多无关数据）好
内存占用head 内存更高head 内存低
文件数/元数据少多
要点：块大小是压缩率与查询放大之间的经典权衡。时序库通常取「固定跨度的时间」或「固定样本数上限，先到者为准」——具体阈值以产品文档为准，不要凭印象调。

04运维相关：重启、删除与容量

行为底层发生了什么运维含义
进程重启回放 WAL 重建内存中的 HeadWAL 越大，重启越慢。WAL 长时间没被截断通常说明落盘有问题
删除数据先写 tombstone 标记，compaction 时才真删删除后磁盘不会立刻释放，要等合并
修改历史数据基本不支持Block 是只读的，历史数据只能整块重写
保留策略到期整块删除目录极快，但要接受块粒度的时间边界
磁盘写满通常触发写保护（停止写入）监控磁盘水位，别等写满才处理

05常见疑问

问：为什么重启要很久？

因为要回放 WAL 把内存中的 Head Block 重建出来。WAL 积压越大回放越久。正常情况下 WAL 会在 Head 落盘后被截断，如果 WAL 一直很大，说明落盘环节出了问题。

问：为什么删了数据磁盘没释放？

删除是软删除（tombstone），物理清除发生在后续的 compaction。想立刻释放需要触发合并，但合并本身有 IO 代价，通常在低峰自动做。

问：为什么历史数据不能改？

Block 落盘后是只读且压缩过的，改一个点就要重写并重新压缩整个块。这是时序库的设计取舍：牺牲可修改性，换取极高的写入吞吐与压缩率。需要修正历史数据的场景，通常是删掉重导。

问：保留策略设多久合适？

取决于「多旧的数据还要被查」。常见做法是细粒度短期 + 降采样长期：比如 15 秒精度留 15 天，5 分钟精度留 1 年。这样既能查历史趋势，又不占太多空间。

容量算账：从采样率到磁盘

时序库的容量可以手算，误差通常在 ±20% 以内。核心公式只有一条：字节数 ≈ 点数 × 每样本字节 + 索引开销。每样本字节取决于编码：Gorilla 类（XOR + varint）在缓慢变化的浮点指标上约 1.3~1.7 字节，整型计数器可低到 0.6 字节，而随机噪声序列会退化到接近 8 字节（等于不压缩）。

采样间隔每天点数/测点每样本 1.7B 时每天30 天
1s86,400≈147 KB147 KB≈4.3 MB
10s8,640≈14.7 KB14.7 KB≈430 KB
1min1,440≈2.4 KB2.4 KB≈72 KB
5min288≈0.49 KB0.49 KB≈14 KB

算一个真实规模：10,000 个测点 × 1s 采样 × 保留 30 天 = 10,000 × 86,400 × 30 = 2.59×10¹⁰ 个点；按 1.7 字节算约 44 GB，再加上倒排索引（通常占 5%~15%）和 WAL 预留，规划 55~60 GB 比较稳妥。如果把采样降到 10s，同一份数据只剩 4.4 GB —— 这就是「降采样是最便宜的优化」的原因。

用现网数据反推压缩率（比拍脑袋准）

# Prometheus：直接读 TSDB 状态，拿到实际样本数与 chunk 数
curl -s localhost:9090/api/v1/status/tsdb | jq '.data.headStats'
# 返回 numSeries / numChunks 后可反推：每序列平均 chunk 数 > 2 说明内存块在被频繁滚动

# 反推每样本字节：用磁盘占用除以样本数
du -sb /prometheus/data | awk '{print $1}'   # 实际字节
# 每样本字节 = 实际字节 / (numSeries * 每天点数 * 保留天数)

算出来每样本 > 3 字节，通常说明序列基数（cardinality）过高或值抖动剧烈，先查 topk(10, count by (__name__)({__name__=~'.+'})) 这类基数问题，再考虑调采样间隔。

块参数的三个典型改动

# Prometheus：把保留期从 15d 提到 30d，并限制单 block 的样本上限，避免 OOM
prometheus --storage.tsdb.retention.time=30d            --storage.tsdb.max-samples-per-chunk=120            --storage.tsdb.wal-segment-size=128MB

# TimescaleDB：把 chunk 改成 1 天并开启压缩策略
SELECT set_chunk_time_interval('metrics', INTERVAL '1 day');
SELECT add_compression_policy('metrics', INTERVAL '7 days');
SELECT compress_chunk(i) FROM show_chunks('metrics', older_than => INTERVAL '7 days') i;

# InfluxDB：查看各 shard 的实际磁盘占用，判断块粒度是否合适
influx -execute 'SHOW SHARD GROUPS'
influx_inspect report -detailed /var/lib/influxdb/data

上线前逐条核对：

  • 保留期 × 采样率 × 测点数 先算一遍再采购磁盘，时序库的增长是线性的，不是阶梯的。
  • 单个 block/chunk 不要跨天：Prometheus 固定 2h，TimescaleDB 默认 7d，太大会让删除旧数据变成整块重写。
  • 磁盘留 30% 余量：压缩（compaction）时需要同时存在新旧两份块文件。
  • WAL 单独盘放，容量按 2h 写入量 × 4 估算（Prometheus 默认段 128MB，崩溃恢复至少保留 1 个段）。
  • 删除数据用 API/TTL，不要 rm -rf 数据目录——索引和块是配对的，手工删会留下悬空索引。
  • 测点数 > 100 万或单序列 > 1 亿点时，先做降采样（1s→1min 聚合留存），比换硬件便宜一个数量级。
  • 压缩率突然变差（每样本字节数变多），第一嫌疑是标签基数爆炸，不是编码算法。
  • 冷数据导出：Prometheus 用 promtool tsdb dump，TimescaleDB 用 COPY (...) TO PROGRAM 'gzip'。
