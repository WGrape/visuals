先建立直觉：公司的试用期 + 转正制度

把缓存想象成一家公司，容量有限（只能有 100 名正式员工）：

  • Window 区（约 1%）：相当于试用期。新人先进这里，先干着，积累业绩。
  • TinyLFU 准入：转正答辩。新人要和「表现最差的正式员工」比业绩（访问频次），赢了才能转正。
  • Main 区（约 99%）：正式员工区，内部再分 probation / protected 两段（SLRU），表现好的升到 protected。

这样设计同时解决了两个经典难题：新人不被直接淘汰（有试用期），混子进不来（要 PK 业绩）。

为什么需要这三段

组件解决什么问题不这么做会怎样
Window（LRU）新数据饥饿（LFU 的盲区）新数据频次为 1，一进来就被淘汰，永远热不起来
TinyLFU 准入批量扫描污染（LRU 的盲区）一次全表扫描把所有热数据挤出去
Main（SLRU）主区内部的淘汰顺序只有频次、没有时间维度，无法适应热度变化
定期减半计数饱和所有计数涨到接近，频次失去区分度

频次怎么算：Count-Min Sketch

TinyLFU 需要知道每个 key 的访问频次，但为百万级 key 各存一个计数器太贵。它用 Count-Min Sketch：一个 d × w 的计数矩阵，用 d 个哈希函数定位，更新时各格 +1，查询时取最小值。

为什么取最小值？哈希冲突只会让别人也往你的格子加数，所以格子值 ≥ 真实值，取最小最接近真值，且绝不低估。内存占用与 key 数量无关，只与 d×w 有关——这就是「极小内存估算海量 key 频次」的原理。
饱和问题：访问量持续增长会让所有格子都变大，区分度消失。Caffeine 的做法是定期把所有计数减半（右移一位）。这同时起到老化作用——久未访问的数据迅速趋近 0。

为什么命中率比 LRU 高

负载LRUW-TinyLFU
稳定热点好好
一次性批量扫描差（热数据被挤掉）好（扫描数据频次低，准入被拒）
热点随时间的迁移好好（SLRU 降级机制 + 计数减半）
大量新内容好好（Window 区保护）
核心思想：不要只用「时间」（LRU）或只用「频次」（LFU）做决策，而是用频次决定「能不能进」，用时间决定「进来之后谁先走」。两者分工，各补对方的短板。

实践提示

  • Caffeine 的这些机制对使用者完全透明，你只需 Caffeine.newBuilder()...build()。
  • 可以调 initialCapacity 减少扩容开销，但不需要调 Window/Main 比例——默认值已足够好。
  • 想看效果就开 recordStats()，对比不同配置下的命中率。

🎯 面试问答

Q：Window 区为什么只要 1%？
A：因为它只是「新数据的缓冲带」，目的是让新数据在正式比频次之前有机会积累几次访问，不被「频次为 1」直接淘汰。这个目标不需要很大空间——1% 已足以容纳短期新数据。给太大反而浪费，因为 Window 是纯 LRU，没有频次保护，抗污染能力弱。

Q：TinyLFU 准入具体怎么 PK？
A：当 Window 区满了需要淘汰一个候选者 C，同时 Main 区也要腾位置时：比较 C 的频次和 Main 区「受害者 V」的频次。若 C 频次更高，则 C 进入 Main、V 被淘汰；否则 C 直接丢弃，V 保留。关键点：这个比较用的是估算频次（Count-Min Sketch），不是精确值，但对「谁更热」的判断足够可靠。

Q：Main 区为什么还要分 probation 和 protected？
A：为了让已经被证明是热点的数据得到更强保护。新进 Main 的先在 probation（试用期），再次被访问才晋升到 protected。淘汰时优先从 probation 取，protected 只有在其自身满了时才降级回 probation。好处：既保护了真正的热点，又因为「可能被降级」保留了对热度变化的适应能力——这是纯 LFU 做不到的。

Q：计数减半会丢失频次信息吗？
A：会损失精度，但这是有意为之。减半后，高频数据的相对大小关系基本保持（1000 和 10 变成 500 和 5，仍然差 50 倍），而低频数据迅速趋近 0——这正是我们想要的老化效果。同时它避免了计数饱和（所有值都涨到上限而失去区分度）。用一点精度换「抗饱和 + 自动老化」，非常划算。

第一层 · W-TinyLFU 解决什么问题

传统 LRU 的两大短板：① 一次全表扫描会把热数据全部挤出去（缓存污染）；② 只看最近访问时间，无法判断「谁才是真正的热点」。W-TinyLFU 用频率信息做准入控制，并用一小段 Window LRU 吸收突发流量。

组件作用占比
Window LRU接纳新条目，吸收突发访问约 1%
TinyLFU频率草图，判断谁更热不占缓存空间
SLRU Protected被证明是热点的长期保留约 80% 的 Main 区
SLRU Probation候补区，等待证明自己约 20% 的 Main 区

第二层 · 内部参数与可观测数字

参数取值 / 默认值含义
Window 区占比约 1%新条目先进这里，命中后晋升
Protected 占比Main 区的 80%多次命中后进入，不易被淘汰

淘汰决策的核心逻辑：Window 区满了要往 Main 区挤，Probation 区也要淘汰一个，两者用 TinyLFU 估计的频率比大小，频率低的那个走。这就是「准入控制」—— 一次性的突发访问进不来，因为它的频率估计很低。

Caffeine 基本用法与统计

import com.github.benmanes.caffeine.cache.Cache;
import com.github.benmanes.caffeine.cache.Caffeine;
import java.time.Duration;

// 基本用法：按容量 + 写入后过期
Cache<String, Data> cache = Caffeine.newBuilder()
        .maximumSize(10_000)                    // 触发 W-TinyLFU 淘汰的容量上限
        .expireAfterWrite(Duration.ofMinutes(10))
        .recordStats()                          // 关键：打开统计才能观测命中率
        .build();

// 推荐的读取方式：get(key, loader) 是原子的，避免缓存击穿
Data v = cache.get(key, k -> loadFromDb(k));

// 观测
System.out.println(cache.stats().hitRate());    // 命中率
System.out.println(cache.stats().evictionCount());

几种容量与过期策略的组合

Caffeine.newBuilder()
    // 1) 基于容量：触发 W-TinyLFU
    .maximumSize(10_000)
    // 2) 基于权重：不同条目占不同成本（如大对象）
    .maximumWeight(100_000)
    .weigher((String k, Data v) -> v.sizeInKB())
    // 3) 写入后过期 / 访问后过期
    .expireAfterWrite(Duration.ofMinutes(10))
    .expireAfterAccess(Duration.ofMinutes(5))
    // 4) 定时刷新：命中后异步刷新，不阻塞读
    .refreshAfterWrite(Duration.ofMinutes(1))
    // 5) 异步加载 + 线程池
    .executor(Runnable::run)
    .buildAsync((k, e) -> loadFromDb(k));

第三层 · 调不出来时怎么查

  • 命中率低但容量很大：多半是访问模式本身就是一次性的（如扫描全表），加大容量没用，要先改访问模式或加布隆过滤。
  • 命中率突然掉：检查是否有定时任务批量拉取数据造成缓存污染，这类流量正是 TinyLFU 想挡的 —— 把它与在线流量分开缓存。
  • 频率老化没生效：老热点会把位置占死，确认版本支持 aging（Reset），并观察样本数阈值是否被触发。
  • 淘汰数远大于预期：可能是 maximumWeight 配了但 weigher 返回值过大，实际条目数远小于预期。
  • 统计全是 0：忘了 .recordStats()，Caffeine 默认不记录统计。
  • 内存没降下来：缓存的是引用，条目被淘汰后如果外部仍持有引用就不会释放；另检查是否用了 softValues。

关键指标：hitRate() 与 evictionCount()。命中率低于 80% 通常说明缓存策略或访问模式有问题，而不是容量问题。

第四层 · 原理与取舍

为什么用频率而不是只用时间：LRU 假设「最近用过的还会再用」，这在扫描类负载下完全失效。频率信息能识别出「谁被反复访问」，但频率也有滞后性 —— 所以 W-TinyLFU 用 Window 区让新条目有机会先证明自己。

策略抗突发扫描开销适用
LRU差最低访问局部性强的场景
LFU好需维护频率，需老化稳定热点
TinyLFU很好Sketch，空间极小通用，Caffeine 默认
W-TinyLFU最好比 TinyLFU 多一个 Window有突发流量的通用场景
ARC / LIRS好较复杂需要自适应时
为什么频率统计用 Count-Min Sketch 而不是精确计数？

因为精确计数需要为每个 key 维护计数器，空间随 key 数量线性增长，在千万级 key 下不可接受。Count-Min Sketch 用几个哈希数组把空间压成常数级，代价是只会高估不会低估（冲突累加），而淘汰场景只需要比较相对大小，高估是可以接受的。

为什么要给频率做 aging（重置）？

因为早期热点会一直占着最高的计数值，导致新热点永远比不过它。做法是当总样本数达到阈值时把所有计数器减半 —— 相当于让历史衰减，保持对近期趋势的敏感。

Window 区为什么要设成 1% 这么小？

它的作用只是吸收突发流量：新条目先在这里待一会儿，如果真有热度就会被访问并晋升。如果设大，就退化成普通 LRU，失去抗扫描能力；设太小又会让真正的新热点来不及证明自己。
