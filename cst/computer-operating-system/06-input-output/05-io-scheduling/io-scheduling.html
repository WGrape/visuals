I/O 调度

块层如何合并排序请求——mq-deadline / none / kyber / bfq 与 HDD vs SSD 取舍

概念参数与命令排障原理速记

01调度器与磁盘差异

第一层

概念与判定

应用产生的 I/O 请求是随机、乱序、并发的。直接丢给磁盘效率很低（尤其 HDD 寻道极慢）。I/O 调度器位于文件系统/块层之间，对请求做合并、排序、重排，再下发给设备。

图：请求经调度器合并排序后派发到设备。
调度器适用核心思想
mq-deadlineHDD / 通用按截止时间保证请求不饿死，多队列
none（noop）SSD/NVMe基本不排序，设备自己并行，少一层开销
kyber低延迟 SSD根据目标延迟动态限制队列深度
bfq桌面/交互按「扇区数」公平分配带宽，照顾交互响应
机械盘 vs 固态盘彻底不同：HDD 寻道毫秒级，排序（电梯算法）收益巨大；SSD 随机访问无寻道，乱序并行反而更快，过多排序反而徒增延迟——所以 NVMe 上常用 none。

02查看与切换调度器

第二层

参数·命令·量化

查看与切换调度器

# 看某块盘当前调度器（中括号为当前）
cat /sys/block/nvme0n1/queue/scheduler
# 例如: [none] mq-deadline kyber bfq

# 临时切换
echo mq-deadline > /sys/block/sda/queue/scheduler

# 关键队列参数
cat /sys/block/sda/queue/nr_requests        # 队列深度
cat /sys/block/sda/queue/rotational         # 1=机械盘 0=固态
cat /sys/block/sda/queue/read_ahead_kb       # 预读

# 观察实际 IO 行为
iostat -x 1        # await/svctm/%util
fio --rw=randread --bs=4k --iodepth=32 ...   # 压测不同调度器
参数含义
nr_requests队列能积压的请求数，太大增延迟、太小降吞吐
rotational是否机械盘，决定默认调度器选择
read_ahead_kb顺序读预取量
容器里看到的调度器可能是假的：很多云盘是网络/虚拟块设备，宿主机那层才是真调度。容器内调 /sys/block 常常无效或不生效。

03排障与边界

第三层

排障与边界

  • %util 100% 但吞吐不高：HDD 在疯狂寻道，或队列深度太小。换 mq-deadline / 增大 nr_requests。
  • NVMe 上用 mq-deadline 反而慢：SSD 不需要排序，none 更合适。
  • 写放大与饥饿：纯写狂占带宽，读被饿死——mq-deadline 的截止时间机制就是解这个。
  • 数据库场景：随机小 IO 多，过低队列深度会限制 IOPS；但过高又增尾延迟（p99）。要按 SLA 调。
  • 多队列（blk-mq）：现代内核默认多队列，单队列锁竞争已成历史，调度器也得是多队列版。

04原理与取舍

第四层

原理与取舍

调度器本质是「吞吐 vs 延迟 vs 公平」的权衡：HDD 侧重空间局部性（排序减寻道），SSD 侧重延迟与公平（不挡路），桌面侧重交互体验（bfq）。没有万能调度器。

目标选谁代价
HDD 吞吐mq-deadline读可能被写延迟
SSD 低延迟none / kyber少排序、少公平保障
桌面交互bfq吞吐略降
云盘随宿主机容器内调参无效

深入 Q&A

Q：为什么 SSD 不排序反而快？
A：SSD 内部是并行闪存颗粒，没有机械寻道，任意逻辑块访问延迟相近。排序徒增一层合并/等待，反而让请求晚发、尾延迟升高。

Q：电梯算法（elevator）现在还有吗？
A：老的单队列 cfq/deadline 已淘汰，mq-deadline 是其多队列继承者，仍保留「按方向扫、截止时间兜底」的电梯思想。
