把“好不好”写进 CI

临时跑一次评测只能回答“这一刻好不好”；把评估写成可版本化、可重复、可进 CI 的代码，才能回答“每次改动有没有悄悄变坏”。这一页讲清评测集版本化、回归门禁、评估流水线组成与 CI 集成。

第 1 步 · 为什么

把评估写成代码，而不是一次性的 notebook

临时跑一次评测只能回答"这一刻好不好"；把评估写成可版本化、可重复、可进 CI 的代码，才能回答"每次改动有没有悄悄变坏"。

可复现
同一份评测集 + 同一份脚本，任何人跑结果一致。
可回归
每次改模型/数据都自动跑，设门禁挡住退化。
评估代码和你训练代码一样重要：它是模型的单元测试。没有它的团队，每次发版都是"开盲盒"。
第 2 步 · 版本化

评测集与回归门禁

评测集必须像代码一样版本化，否则历史分数不可比；并用"回归门禁"拦住明显退化。

  • 评测集版本号：每次改题留版本，旧分新分才可对比。
  • 红线测试：一小批"绝不该错"的样本，只要挂就阻断发布（哪怕平均分好看）。
  • 回归门禁：新模型相对基线，主指标跌幅超过阈值（如 >2pp）即告警/阻断。
  • 保密集：最终测试集不进训练/调优反馈循环，防隐式过拟合。
别用"平均分涨了就发版"：平均分掩盖长尾崩盘。门禁要看分层 + 红线 + 方差，而不是单一均值。

第 4 步 · CI

把评估塞进 CI/CD

评估脚本接入 CI：每次 PR 自动跑红线测试与小样本回归，门禁不过不允许合并/发布。

  • 红线测试（快）：几十到几百条，秒级跑完，任何退化立刻拦。
  • 完整评测（慢，异步）：上千条 + 裁判，PR 合并后跑，结果进看板。
  • 产物留存：每次评估存分数、失败样本、裁判原始输出，便于回溯。
  • 看板与告警：分数趋势图 + 护栏指标告警，退化一眼可见。
成熟团队的标志：模型改动和代码改动走同一套 PR → CI → 评估门禁 → 发布 流程，没有人"手动发一版试试"。
收尾 · 一句话

所以评估框架是什么

评估框架 = 把"模型好不好"变成可版本化、可重复、可进 CI 的自动化流水线。 核心是评测集版本化 + 红线门禁 + 分层回归 + 看板告警， 让每次模型/数据改动都能被自动验收。一句话：没有评估代码的团队，每次发版都是开盲盒。

第一层 · 概念与判定：哪些评估该进 CI

评估类型跑的频率门禁角色
红线测试（几十~几百条）每次 PR阻断：挂了不准合并
小样本回归（数百条）每次 PR告警：掉分超阈值提示
完整评测（上千条+裁判）合并后/定时记录：进看板趋势
线上 A/B发布前决策：要不要全量

第二层 · 参数·命令·量化：门禁阈值怎么定

# 回归门禁的伪代码逻辑
  baseline = load_score("model_v1", eval_set="v3")     # 基线分数（固定评测集版本）
  current  = run_eval("model_v2", eval_set="v3")
  drop = baseline["main"] - current["main"]

  # 红线：任何一条红线样本失败 -> 阻断
  if current["redline_fail"] > 0:
      block("红线样本失败")

  # 主指标跌幅超过 MDE 且显著 -> 阻断
  if drop > MDE and significant(current, baseline):
      block(f"主指标下跌 {drop:.1f}pp 且显著")

  # 护栏：有害率/延迟越线 -> 阻断
  if current["harmful_rate"] > GUARD["harmful_rate"]:
      block("护栏越线")

MDE（最小可检测效应）由样本量决定：样本少就别设太严的阈值，否则噪声也会触发阻断。经验：小样本门禁只拦明显退化。

第三层 · 排障与边界：评估代码六个坑

  • 评测集不版本化：改了题历史分不可比 → 评测集带版本号。
  • 只报均值：平均分掩盖长尾 → 分层 + 报方差。
  • 红线样本太少：几条红线拦不住系统退化 → 红线要覆盖关键能力。
  • 门禁过严：噪声也阻断，团队开始"跳过评估" → 阈值按样本量定。
  • 裁判结果不留存：无法回溯"为什么那版变差" → 存原始输出。
  • 评估与训练同源：评测集泄漏进训练 → 保密集不进反馈循环。

第四层 · 原理与取舍：为什么评估值得当"一等公民"

评估代码和训练代码，哪个更该被重视？

很多团队重训练轻评估，结果"训练很热闹、上线全靠蒙"。评估代码是模型的单元测试，它决定了你能否相信每一次改动。把它当一等公民（版本化、进 CI、有人维护），长期收益远大于多训几个 epoch。

小团队没资源做完整评估怎么办？

先做红线测试 + 人工抽检：几十到几百条关键样本，每次改动都跑，确保不退化；完整评测和线上 A/B 等流量起来再补。评估的起步门槛很低，关键是"先有、再全"。

为什么失败样本比平均分更有价值？

平均分告诉你"整体还行"，失败样本告诉你"哪里会翻车"。每次评估都抽样看 20~50 条失败案例并归类，是定位模型短板最高效的手段——这也是为什么评估代码要留存原始输出。

第一层 · 概念与判定 “evals as code”把评测写成可版本化、可重跑的测试用例集合，而非一次性脚本。判定：当评估需要 reproducible、可 diff、可进 CI 时使用 pytest + 评测库。

工具 / 形态用途关键点
pytest + 断言确定性用例可进 CI
RAGAS / DeepEvalRAG/LLM 指标忠实度、相关性
PromptFoo红蓝对比多模型 diff
自托管评测集私有数据回归防退化

第三层 · 排障与边界

  • 评测集与训练/调优集泄漏，分数虚高，必须隔离。
  • LLM 当裁判本身有偏差，需人工校准与金标准对照。
  • 只盯单一总分，掩盖某子能力退化，要拆维度。
  • 评测成本随用例数线性增长，需抽样与并行。
第四层 · 原理与取舍

evals as code 用“工程化测试”换可复现与可回归，代价是要维护数据集与指标管线。相比一次性 notebook，它让每次模型/提示变更都能看到“哪些能力退步了”。权衡是“维护成本 vs 可靠性”：关键能力必须进 CI 红线，长尾能力用抽样评测控制成本。评测集即产品规格的另一种表达。

FAQ：评测要覆盖多少用例才够？

没有固定数字，原则是“能稳定区分版本好坏”。关键能力用例进 CI 红线（几十到几百条即可），长尾能力用随机抽样控制成本。更重要的不是数量而是覆盖度：每个已知失败模式都要有对应用例，否则退化无人知晓。

常见误区与延伸

  • 误区一：评测集越大越好。关键是覆盖度而非数量，每个已知失败模式都要有对应用例。
  • 误区二：一次评测定终身。模型与提示会迭代，评测集要随产品演进持续维护。
  • 延伸：把评测集与训练/调优集隔离，否则分数虚高，退化无人知晓。
  • 延伸：LLM 当裁判要先人工金标准校准，只可信作回归哨兵，关键结论仍人工复核。

一句话总结：evals as code 用工程化测试换可复现与可回归，关键能力进 CI 红线、长尾用抽样，评测集即产品规格的另一表达。

横向对比与追问

  • 与人工评测比：evals as code 可重跑、可 diff、可进 CI，代价是维护数据集。
  • 与一次性 notebook 比：后者结果无法回归，模型一升级就丢对照基线。
  • 追问：为什么评测集也要版本化？因为它就是“产品应该长什么样”的规格表达。
  • 追问：离线指标高就能上线吗？不能，离线偏离真实分布，必须线上 A/B 验证。

小结：把评测当代码工程化，是用可复现性换对退化的早期感知。

evals as code 落地清单

  • 把评估写成可版本化、可重跑的代码：固定数据集、固定 prompt 模板、固定评分函数，避免手测一次带来的不可复现。
  • 评分分层：先自动指标（exact match、F1、代码编译通过率），再 LLM-as-judge，最后小样本人工抽检，三者互为校验。
  • 回归门禁：每次模型或 prompt 变更都跑同一 eval 套件，用 diff 报告量化变好还是变差，再决定是否合入。
