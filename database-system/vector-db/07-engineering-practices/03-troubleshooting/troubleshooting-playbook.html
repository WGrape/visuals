①四层排查法：数据 → 索引 → 参数 → 资源

向量检索的故障有一个共同特点：大多数不报错，只是结果变差。所以排查不能靠错误日志，而要靠一套固定的分层检查法。

排查顺序反过来（先怀疑引擎、先去调参）是最大的浪费。先把「数据对不对」验证掉，因为它最容易被忽略、又最常是根因。

按现象查表，每行都给验证手段而不只是猜测：

现象最可能原因验证 / 处理
召回突然下降混入不同模型版本的向量；或有数据没灌进来查 model_version 分布；比对点数量与源数据
刚写入就搜不到一致性窗口（异步 flush / 副本落后）等可见或显式 flush；写后读不要依赖向量库

③五个最容易把排查带偏的现象

这五个现象最容易把排查带偏，值得单独记：

现象直觉判断真实原因
「换个更大的 ef 就好了」参数不够可能是数据层问题 —— 调参只是在掩盖
「内存够用啊，还没打满」资源没问题HNSW 索引可能已被换出到 swap，延迟在偷偷变差
「QPS 没问题」性能达标p99 可能已经翻倍；均值掩盖长尾
「召回 0.98，很好」质量达标ground truth 可能是用 ANN 生成的，这个数字不可信
「用了量化但没变化」量化没生效或没影响要么没生效，要么原向量仍在内存里全量保留

④跨产品通用检查动作

跨产品通用的一组检查动作，可以按序执行：

# 1) 数据量对不对
#    Qdrant
GET /collections/docs            # points_count / indexed_vectors_count
#    Milvus
collection.num_entities
#    pgvector
SELECT count(*) FROM docs;
#    ES
GET /docs/_count

# 2) 索引状态
#    pgvector：确认真的用上了索引
EXPLAIN (ANALYZE, BUFFERS) SELECT id FROM docs ORDER BY emb <=> $1 LIMIT 10;

# 3) 参数是否被显式设置（很多产品默认值极小）
SHOW hnsw.ef_search;             -- pgvector 默认 40
SHOW ivfflat.probes;             -- pgvector 默认 1，必改

# 4) 资源与长尾
#    看 p50 / p95 / p99 三个数，不要只看均值
#    看进程 RSS 与是否 swap

⑤排障记录该包含什么

排障最缺的不是能力，而是记录。一份好的排障记录应包含：

  • 现象：具体到数字（召回从 0.95 掉到 0.72、p99 从 30ms 涨到 400ms），不是「变慢了」
  • 时间线：什么时候开始、之前做过什么变更（这是最有价值的一条）
  • 范围：全量还是部分租户/部分 query、单机还是全集群
  • 已排除项：查过什么、结论是什么（避免下一个人重复劳动）
  • 根因与验证：改了什么之后恢复的，怎么确认是这一项
  • 防复发：加了什么监控、什么检查、什么默认值变更

⑥速记卡

最大特点

向量故障多数不报错，只是结果变差。

四层顺序

数据 → 索引 → 参数 → 资源，不要跳层。

经验分布

数据层占一半，参数层三成，「引擎不行」不到一成。

最高频根因

索引没建完就测/上线；混用两个模型版本的向量。

必改默认值

pgvector probes=1、ef_search=40。

必查组合

返回数少于 K = ef < K 或过滤太严。

易误判

「内存没打满」不代表没问题，索引可能在 swap 里。

记录纪律

现象带数字、时间线带变更、已排除项要写。

排障的效率差别不在经验多少，而在顺序对不对。先验证数据、再验索引、然后参数、最后资源，能省掉大半无效尝试。
