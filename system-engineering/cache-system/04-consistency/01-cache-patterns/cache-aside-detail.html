📖 Cache-Aside：最常用也最稳妥的缓存模式

应用自己管理缓存——读时先查缓存、miss 再查库并回填；写时先更新库再删除缓存。

命中返回，miss 回源回填

极苛刻但存在

先建立直觉：自己做笔记的学生

Cache-Aside（旁路缓存）的意思是：缓存不自动和数据库同步，全靠应用代码自己维护。

  • 读：先看笔记（缓存），有就直接用；没有就翻书（数据库），并把答案抄到笔记上。
  • 写：改书（数据库），然后把笔记上对应的那条划掉（删除缓存），下次要用再重新抄。

它之所以叫「旁路」，是因为缓存不在主链路上——数据库才是权威，缓存只是旁边的加速器。

标准流程

代码实现

// 读
func Get(id int64) (*User, error) {
    key := fmt.Sprintf("user:%d", id)
    if v, err := redis.Get(key); err == nil {
        return decode(v), nil            // ① 命中直接返回
    }
    u, err := db.Query(id)               // ② miss：查库
    if err != nil { return nil, err }
    if u == nil {
        redis.SetEX(key, 60, NULL_MARK)  // 空值也缓存，防穿透
        return nil, nil
    }
    redis.SetEX(key, ttlWithJitter(300), encode(u))  // ③ 回填（TTL 带抖动防雪崩）
    return u, nil
}

// 写
func Update(u *User) error {
    if err := db.Update(u); err != nil { return err }  // ① 先更新数据库
    if err := redis.Del(key); err != nil {
        mq.Publish("retry-del", key)                    // ② 删除失败要重试
    }
    return nil
}

为什么「先更新数据库，再删除缓存」

四种组合中它风险最小。要产生脏数据需要两个极苛刻的条件同时成立：

  1. 此刻缓存恰好已经失效（否则读请求直接命中缓存，不会查库）；
  2. 读请求的「查库 → 写缓存」完整落在写请求「更新数据库」之前（毫秒级窗口）。

相比之下，「先删缓存再更新库」只需一次普通并发读就会出错（读请求把旧值写回缓存，之后一直错）。

「先更新缓存再更新数据库」最差：一旦数据库更新失败，缓存里就是数据库中不存在的值，且没有任何机制自动修正（要等 TTL 过期）。而「先更库后删」最坏只是多读一会儿旧值。

Cache-Aside vs 其他模式

模式谁负责写缓存优点缺点
Cache-Aside应用简单、可控、缓存故障不影响主流程首次必 miss；代码侵入
Read/Write Through缓存层应用不关心缓存需缓存层支持写库
Write Behind缓存层异步写性能极高有数据丢失风险
为什么 Cache-Aside 最流行？因为它最简单且最稳健：业务逻辑清晰，缓存挂了系统仍能（慢速）工作，不需要缓存层具备写数据库的能力。绝大多数互联网公司用的就是它。

三个必配的保护

  1. TTL 带随机抖动——防止批量 key 同时过期引发雪崩；
  2. 空值缓存——防止查询不存在的数据造成穿透；
  3. 删除失败重试——删除失败时入队重试，或用 binlog 订阅兜底。

🎯 面试问答

Q：Cache-Aside 首次请求一定会 miss 吗？
A：会，这是它的固有特点——数据只有在被查询过一次后才会进缓存。对普通业务无妨（一次 miss 而已），但对大促、冷启动场景，大量请求同时 miss 会直接压垮数据库。解决办法就是缓存预热：提前把热点数据加载进缓存。这也是为什么 Cache-Aside 常常要配合预热一起使用。

Q：为什么写操作是删除缓存而不是更新缓存？
A：两个理由：① 幂等性——删除一次和删除多次效果一样，不存在「两个线程先后写缓存导致顺序颠倒、旧值覆盖新值」的问题；而更新缓存则会，需要额外加锁或版本号。② 懒加载——删掉后如果没人读，就省了一次无谓的写；尤其当缓存的值需要复杂计算或多表聚合时，这个节省很可观。例外：写后立即被大量读取且值很稳定时，主动更新更划算。

Q：缓存服务挂了，Cache-Aside 还能工作吗？
A：能，这是它的一大优势。因为缓存是「旁路」的——读路径上缓存 miss 就直接查库，写路径上删缓存失败也不影响数据库更新。所以 Redis 宕机时系统会变慢但不会不可用（当然要给数据库加限流/熔断保护，否则流量全压过去会把库打挂）。相比之下 Write-Through/Write-Behind 模式下缓存是主链路的一部分，挂了影响更大。

Q：Read/Write Through 和 Cache-Aside 有什么区别？
A：核心区别是谁负责同步：Cache-Aside 由应用代码显式读写缓存和数据库；Read/Write Through 则由缓存层自己负责——应用只跟缓存打交道，缓存 miss 时由缓存去查库，写时也由缓存同步写库。后者对应用更透明，但要求缓存组件支持这些逻辑（如某些 ORM 二级缓存、支持 Write-Through 的存储引擎），通用性不如 Cache-Aside。

Cache Aside 的标准实现

也叫 Lazy Loading——缓存不由写方主动填充，而是读时未命中才回填。

标准实现

# 读路径
def get(key):
    v = cache.get(key)
    if v is not None:
        return v                    # 命中
    v = db.query(key)               # 未命中：查库
    if v is not None:
        cache.setex(key, TTL, v)    # 回填（<strong>只对存在的key缓存</strong>）
    return v

# 写路径（关键顺序）
def update(key, new_val):
    db.update(key, new_val)         # 1) <strong>先更新数据库</strong>
    cache.delete(key)               # 2) <strong>再删除缓存</strong>

# ⚠️ 顺序不能反：先删缓存再更新库会留下长期脏数据
#   删缓存 → (此时读请求进来，读到旧值并回填) → 更新库
#   结果：缓存里是旧值，库里是新值，且会一直脏到 TTL 结束
路径步骤关键点
读命中直接返回最快路径
读未命中查库 → 回填只对存在的数据回填
写更新库 → 删缓存顺序固定
删失败重试/异步补偿必须有兜底

为什么「只对存在的数据回填」：若查询结果为空也缓存，会占用内存且需要在数据创建时精确失效，容易出错。防穿透更好的是缓存空值用短 TTL（60~300 秒）或布隆过滤器，而不是永久缓存空值。

为什么是“删除”而不是“更新”缓存

对比项删除缓存更新缓存
写操作开销一次 delete要计算并序列化完整缓存值
冷数据写无浪费写了没人读，纯浪费
并发写顺序安全可能留脏数据
复杂缓存值无需关心要重算（如聚合结果）

并发写导致脏数据的时序：线程 A 更新库为 v1、线程 B 更新库为 v2，若两者都“更新缓存”，但写缓存的顺序与写库的顺序不一致（A 的缓存更新晚于 B），最终缓存是 v1 而库是 v2。删除则没有这个问题——无论谁先删，下次读都会拿到库里的最新值。

例外：若缓存值计算代价极高且更新极频繁、读取也频繁，更新缓存可能更划算。但这属于特例，默认一律删除。

三个必配的防护

风险现象防护
删缓存失败脏数据存活到 TTL重试 + MQ 异步补偿
并发脏读读慢于写时回填旧值延迟双删（延迟 500ms 再删一次）
热点 key 击穿过期瞬间大量请求打库互斥锁/单飞重建
主从延迟回填时读到从库旧值回填强制读主库

完整实现

# 完整实现（含双删 + 失败补偿 + 单飞）
def update(key, new_val):
    cache.delete(key)                       # 1) 写前删
    db.update(key, new_val)                 # 2) 更新库
    mq.send_delayed(lambda: cache.delete(key), delay_ms=500)  # 3) 延迟双删

def get_safe(key, ttl=3600):
    v = cache.get(key)
    if v is not None:
        return v
    # 单飞：只有一个线程去查库
    if cache.setnx(f"lock:{key}", 1, ex=5):
        try:
            v = db.query(key)               # 强制走主库
            if v is not None:
                cache.setex(key, ttl, v)
            return v
        finally:
            cache.delete(f"lock:{key}")
    time.sleep(0.05)
    return cache.get(key)                   # 等一会再读，或返回空

TTL 也要加抖动：一批 key 若在同一时刻写入、TTL 相同，会同时过期造成雪崩。做法是 ttl = base × (1 ± 20%)。

自检 Q&A

Q：Cache Aside 适合什么场景？

A：读多写少，且能接受最终一致。典型如商品详情、用户信息、配置数据——读是写的几十上百倍，缓存命中率高，收益明显。不适合的场景：① 写极频繁（每次写都要删缓存，缓存形同虚设）；② 要求强一致（库存、余额——应直读库或用分布式锁）；③ 数据量小且查询快（缓存收益覆盖不了复杂度）。

Q：缓存该设多长 TTL？

A：按“能容忍多久的陈旧”来定，而不是拍脑袋。三个参考——① 强实时（库存、价格）：秒级或不缓存；② 一般业务数据（商品、文章）：5~30 分钟；③ 极少变更（配置、字典）：小时级 + 主动失效。另外必须加抖动防雪崩，并且 TTL 是最后防线而不是主要手段——主要手段应该是写操作时主动删除。

Q：删缓存失败会怎样，怎么兜底？

A：后果是缓存一直脏到 TTL 过期，可能几分钟到几小时。兜底三层——① 同步重试 2~3 次（指数退避）；② 仍失败则发到消息队列异步重试（保证最终成功，这是关键）；③ 监控删除失败率，超过阈值告警。很多系统漏掉 ②，导致偶发的网络抖动造成的脏数据长期存在。另外订阅 binlog（Canal）由数据变更驱动删除是更彻底的方案——它不依赖应用侧的删除动作成功。

Q：Cache Aside 需要加锁吗？

A：普通场景不需要，热点 key 需要。不加锁时，缓存过期的瞬间会有多个线程同时查库（都是未命中），若该 key 是热点，数据库会瞬间承受大量并发。加锁（或单飞 singleflight）能保证只有一个线程回源，其余等待或直接返回空。判据是峰值 QPS × 重建耗时：若远大于 1，说明并发回源严重，需要加锁。普通 key 并发极低，加锁反而增加复杂度。
