一图看懂三种方案

RDB：给内存拍一张照片

思路很朴素：在某一瞬间把内存里的数据整个 dump 成二进制文件。

触发方式

方式命令 / 配置是否阻塞
自动save 900 1（900 秒内至少 1 次改动）否（fork 子进程）
手动-同步SAVE是，阻塞主线程（生产禁用）
手动-异步BGSAVE否（fork 子进程）
主从复制全量复制时主库自动 BGSAVE否
关闭前SHUTDOWN 且没开 AOF—

核心机制：fork + 写时复制（COW）

  1. 主进程调用 fork() 创建子进程。此时父子共享同一份物理内存（页表复制，内存不复制）。
  2. 子进程只读地遍历这份内存，把数据写进临时 RDB 文件。
  3. 主进程继续服务客户端。如果它修改了某页内存，操作系统会把该页复制一份（写时复制），子进程看到的仍是 fork 那一刻的旧值。
  4. 子进程写完 → 用临时文件原子替换旧的 dump.rdb。
fork 的两个风险：① fork() 本身会阻塞主线程（复制页表），内存越大越慢，几十 GB 的实例可能阻塞数百毫秒；② COW 期间如果写入量很大，会额外复制大量内存页，极端情况下内存峰值接近两倍。所以生产要留足内存余量，并关注 latest_fork_usec。

AOF：把每条写命令记下来

AOF 记的不是数据，而是命令。恢复时把命令重新执行一遍（重放）。

*3
$3
SET
$5
mykey
$5
hello

写回策略（关键配置）

appendfsync行为最多丢多少性能
always每条命令都 fsync 到磁盘几乎不丢（只丢最后一条）最慢
everysec后台线程每秒 fsync 一次最多丢 1 秒推荐
no交给操作系统决定何时刷盘可能丢很多（通常 30 秒）最快
默认且推荐 everysec。它在「最多丢 1 秒」和「性能接近 no」之间取得了最好的平衡，是绝大多数生产环境的选择。

AOF 重写（rewrite）：给日志瘦身

问题：反复 INCR counter 一万次，AOF 里就有一万条命令，但最终状态只是一个数字。文件会无限膨胀。

解法：BGREWRITEAOF——不读旧 AOF，而是直接读当前内存数据，用最少的命令生成一份等价的新 AOF。

# 手动触发
BGREWRITEAOF

# 自动触发（默认）
auto-aof-rewrite-percentage 100   # 比上次重写后体积增长 100% 时触发
auto-aof-rewrite-min-size 64mb    # 且文件至少 64MB
重写为什么是安全的？重写期间的新命令会同时写入「旧 AOF 缓冲区」和「重写缓冲区」，重写完成后把缓冲区里的增量命令追加到新文件，最后原子重命名。整个过程不会丢数据。

混合持久化（Redis 4.0+）

思路：AOF 重写时，先把当前数据以 RDB 二进制格式写进 AOF 文件的开头，之后的增量命令仍以 AOF 格式追加。

# 开启（Redis 7 起默认开启）
aof-use-rdb-preamble yes
结果文件长这样： 
[REDIS 二进制 RDB 内容]  ← 加载极快，覆盖绝大部分数据
*3
$3
SET
...   ← 之后的新命令，量很小
这样同时拿到两边的好处：恢复时先快速加载 RDB 部分（比逐条重放 AOF 快一个数量级），再补上少量增量命令，数据丢失窗口仍然是 AOF 的秒级。这是生产的推荐配置。

选型速查

场景建议
纯缓存，丢了从 DB 重建即可RDB 就够，甚至可以只保留 RDB
不允许丢数据（如做计数、做队列）AOF everysec + 混合持久化
既要备份又要低丢失RDB + AOF 同时开（Redis 会优先用 AOF 恢复）
完全不在乎持久化两者都关，性能最高
两个都开时，恢复用谁？优先用 AOF，因为它的数据更完整。只有当 AOF 关闭时才会用 RDB。另外要注意：开启 AOF 后，SHUTDOWN 或重启前务必确认 AOF 已刷盘，否则可能丢掉最后 1 秒。

生产常用配置片段

# RDB
save 900 1          # 15 分钟内有 1 次写
save 300 10         # 5 分钟内有 10 次写
save 60 10000       # 1 分钟内有 1 万次写
dbfilename dump.rdb
dir /var/lib/redis
stop-writes-on-bgsave-error yes   # 快照失败时拒绝写入（避免「以为存了其实没存」）

# AOF
appendonly yes
appendfilename "appendonly.aof"
appendfsync everysec
aof-use-rdb-preamble yes          # 混合持久化
no-appendfsync-on-rewrite no      # 重写时是否暂停 fsync（否=更安全）

运维巡检命令

INFO persistence        # rdb_last_bgsave_status / aof_last_bgrewrite_status
INFO stats              # latest_fork_usec（fork 耗时，毫秒级要警惕）
redis-check-aof --fix appendonly.aof   # AOF 文件损坏修复
redis-check-rdb dump.rdb               # RDB 文件校验

🎯 面试问答

Q：RDB 和 AOF 的核心区别是什么？
A：RDB 存的是「数据快照」——某一时刻内存数据的二进制副本；AOF 存的是「写命令日志」——把每条写命令追加到文件，恢复时重放。由此带来三点差异：① 文件大小：RDB 紧凑，AOF 大（但有 rewrite 压缩）；② 恢复速度：RDB 直接加载快，AOF 要逐条重放慢；③ 数据安全性：RDB 会丢失上次快照之后的所有写入（分钟级），AOF 在 everysec 下最多丢 1 秒。
Q：AOF 的 appendfsync 三档该怎么选？
A：always（每条命令都刷盘）几乎不丢数据但性能最差；no（交给操作系统）性能最好但可能丢几十秒；everysec（每秒刷一次）是默认和推荐值——最多丢 1 秒，性能损失很小。绝大多数业务选 everysec 即可。确实有「一条都不能丢」的强需求时，更应该考虑的是主从复制 + 多副本，而不是把单机的 fsync 拉满。
Q：混合持久化是怎么做到又快又全的？
A：开启 aof-use-rdb-preamble yes 后，AOF 重写时不再生成纯命令日志，而是把当前内存数据以 RDB 二进制格式写在 AOF 文件开头，之后的增量命令仍用 AOF 格式追加。恢复时先加载 RDB 部分（一次性的二进制加载，比逐条重放快一个数量级），再补放少量增量命令。这样既拿到了 RDB 的恢复速度，又保留了 AOF 的秒级丢失窗口。Redis 7 起已默认开启。
Q：为什么 BGSAVE 会让 Redis 卡顿？
A：两个原因：① fork 本身阻塞——fork() 需要复制进程页表，内存越大耗时越长，几十 GB 的实例可能阻塞几百毫秒，期间主线程不能处理请求；② COW 内存压力——fork 后主进程每修改一个内存页，操作系统就要复制该页，写入量大时内存占用可能接近翻倍，甚至触发 swap 或 OOM。生产上要留足内存余量、避免超大实例，并监控 INFO stats 里的 latest_fork_usec。
Q：AOF 文件越来越大怎么办？
A：靠 AOF 重写（BGREWRITEAOF）。它不读旧 AOF 文件，而是直接读当前内存数据，用最少的命令重新生成一份等价的新 AOF（比如被 INCR 一万次的计数器，重写后只是一条 SET counter 10000）。默认自动触发条件是「体积比上次重写后增长 100% 且至少 64MB」。重写期间的新命令会同时写入旧缓冲区和重写缓冲区，最后原子替换，不会丢数据。
Q：RDB 和 AOF 都开，重启时用哪个恢复？
A：优先用 AOF，因为它数据更完整（丢失窗口更小）。只有当 AOF 关闭时才会加载 RDB。这也是为什么生产上「两者都开」是常见配置：RDB 用于备份、快速主从全量同步，AOF 用于日常崩溃恢复。另外如果 AOF 文件损坏，可以用 redis-check-aof --fix 修复，但会丢弃损坏点之后的命令，所以定期备份 RDB 仍然必要。
