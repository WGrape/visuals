大模型选型

大模型选型指南：能力、成本、延迟、合规怎么权衡

"用哪个模型"不是一个分数题，而是一道多维约束下的决策题。本文给出一套可复用的选型框架：先看硬约束（合规、数据不出域）划范围，再看能力门槛，最后用成本和延迟做收敛，并给出分级路由这类实战打法。

第一刀：闭源 API vs 开源自部署

闭源 API（云端大模型）开源自部署
能力上限通常最强，且持续升级，不用自己运维头部开源已很接近，但顶尖能力仍有差距
成本结构按 token 付费，零固定成本，适合起步与波动流量固定 GPU 成本，量大后边际成本更低
数据合规数据要出网，敏感行业受限数据不出域，可控可审计
可控性不可改权重、不能微调（或受限），版本可能静默变更可微调、可量化、可定制、版本锁定
运维无需要推理服务、扩缩容、监控（vLLM / TGI 等）
适合快速验证、通用场景、流量不稳、无合规压力规模化稳定流量、强合规、需领域微调、要压成本
现实中大量团队是混合：通用/复杂任务走闭源，高频简单任务走自建小模型。

成本与延迟：怎么算

成本

单次成本 ≈ 输入 token × 输入单价 + 输出 token × 输出单价
  • 输出 token 通常比输入贵数倍，所以"让模型少废话"是直接的降本手段。
  • 缓存命中能大幅降低重复前缀的成本（Prompt Caching）——把稳定的 system prompt / 长文档放前缀。
  • 自部署要算单卡吞吐 × 显卡时租金，再折算成每千 token 成本，与 API 对比。

延迟

首 token 延迟 TTFT
决定"多久开始出字"，受 prompt 长度、排队、网络影响
生成速度TPOT / tokens-per-second
决定"出字快不快"，受模型大小、量化、batch 影响
规律：模型越小、量化越狠、batch 越大 → 越快越便宜，但能力下降。选型就是在这条曲线上找你的可接受点。

实战打法：分级路由（Model Routing）

不要试图用一个模型解决所有请求。常见做法：

  1. 先分类：用规则或小模型判断请求复杂度（简单问答 / 抽取 / 复杂推理 / 代码）
  2. 再分流：简单任务 → 小模型（快且便宜）；复杂任务 → 强模型
  3. 兜底重试：小模型结果置信度低或校验失败时，自动升级到强模型重跑
  4. 持续回收：统计各档位的成功率与成本，动态调整阈值
这套打法通常能在几乎不掉点的前提下把成本砍掉大半，是生产环境最常见的优化手段。
注意路由本身也有成本和错误率：路由错了会把复杂题送给小模型。务必为"降级"保留出口（用户反馈 / 校验失败即升级）。

面试速记卡

  • 第一刀：合规/数据不出域是硬约束，直接决定闭源还是自部署。
  • 闭源 vs 开源：闭源能力强、零固定成本、数据出网；开源可控、可微调、量大更省、要运维。
  • 验证：公开榜单只做初筛，必须用自建评测集；重点看 badcase 与格式遵循。
  • 成本：输出 token 更贵；Prompt Caching 降重复前缀成本。
  • 延迟：TTFT（首字）与 TPOT（出字速度）分开设指标。
  • 高级打法：分级路由 + 失败升级，显著降本且基本不掉点。
