①读执行计划的通用方法

各库的 EXPLAIN 输出格式不同，但读法相通。掌握这套方法，换数据库也能上手。

  1. 从最内层/最缩进的算子往外读，数据是从叶子流向上层的；缩进最深的那一步最先执行。
  2. 关注每个算子的三件事：访问方式（全扫/索引/范围）、预估行数、实际行数。
  3. 预估 vs 实际差一个数量级 = 统计信息失真或谓词估算失败，这是绝大多数慢查询的根因。
  4. 顺着行数放大/收缩的方向找瓶颈：哪一层输出行数突然暴涨（笛卡尔积、JOIN 放大）， 或哪一层从 100 万骤降到 10 行但扫了 100 万（过滤太晚）。
  5. 看附加信息：Using filesort、Using temporary、 Using index（覆盖索引，好事）、Using where、Using join buffer。
最重要的一条：只看预估行数容易被误导， 一定要拿到实际行数——MySQL 8.0.18+ 用 EXPLAIN ANALYZE， PostgreSQL 用 EXPLAIN (ANALYZE, BUFFERS)，SQL Server 看实际执行计划。 它会真的执行一遍 SQL，不要在生产的写语句上直接跑。

③行数估算为什么会错

优化器是基于代价的：它先估算每个算子的输出行数与代价，再选总代价最小的计划。 估算错了，计划就会选错。常见失真来源：

统计信息过期

大批量导入/删除后没更新统计信息。MySQL InnoDB 的采样页数、 PostgreSQL 的 default_statistics_target 都会影响精度。 解法：ANALYZE TABLE / ANALYZE。

列间相关性

优化器默认假设各列独立。city='杭州' AND age<18 若实际强相关，估算会严重偏离。解法：多列统计/扩展统计（PG CREATE STATISTICS）。

数据倾斜

平均值掩盖了热点值。status='done' 占 90% 而 'init' 占 1%， 用同一个选择率估算必然出错。解法：直方图（MySQL 8 自动、PG ALTER TABLE SET STATISTICS）。

无法估算的表达式

函数包裹、LIKE '%x%'、跨表条件、OR 组合， 优化器只能用默认选择率（往往是个拍脑袋的常数）。解法：改写成可估算的形式。

实际行数 / 预估行数 是最有价值的单个指标。 比值 > 10 或 < 0.1 时，别急着改 SQL 加索引——先解决估算问题， 否则优化器换了数据分布还会选错。

④拿到计划后的行动顺序

  1. 确认扫描方式：大表是否走了全扫？谓词是否可 Sargable？（见「过滤条件与索引可用性」）
  2. 看 JOIN 顺序与驱动表：小表是否作为驱动表？被驱动表的关联列有没有索引？
  3. 检查覆盖：能否通过加宽索引让 Using index 生效，消掉回表？
  4. 消掉排序：ORDER BY / GROUP BY 能否与索引顺序对齐？
  5. 处理估算失真：更新统计信息、补直方图、改写法让谓词可估算。
  6. 最后是改写业务 SQL：拆 OR、改 EXISTS、加汇总表、换分页方式。
Q：加了索引优化器不用怎么办？
A：先确认不是估算问题（更新统计信息后重试）。若确认索引更优而优化器仍选全扫， 再考虑 hint（FORCE INDEX / STRAIGHT_JOIN）—— 但 hint 是把决策写死，数据分布变化后会变成负担，作为最后手段并留下注释说明原因。
Q：EXPLAIN 和 EXPLAIN ANALYZE 差在哪？
A：前者只做优化、不执行，输出的是预估；后者真的执行，输出实际行数与耗时。 前者安全可随时跑，后者会在写语句上产生副作用，只能在只读语句或测试环境用。
