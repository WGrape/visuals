🔍 MongoDB 索引

ESR 法则、复合索引顺序、覆盖查询、索引类型与执行计划解读

为什么需要索引

没有索引时 MongoDB 做 COLLSCAN（全集合扫描）：把每个文档都取出来比对。1000 万文档查一个人要扫 1000 万次。建索引后走 IXSCAN：在有序的 B-tree 里按二分定位，复杂度从 O(N) 降到 O(log N)。

默认索引每个集合自动有 _id 唯一索引
数据结构B-tree（WiredTiger），有序、支持范围与排序
单集合上限64 个索引
复合键上限32 个字段

ESR 法则：复合索引字段怎么排

这是 MongoDB 官方给的金规则。复合索引 {a:1, b:1, c:1} 的字段顺序按三类排：

  • E — Equality（等值）：先用等值匹配的字段，如 {status: "paid"}
  • S — Sort（排序）：再放排序字段，如 .sort({createdAt: -1})
  • R — Range（范围）：最后放范围条件，如 {age: {$gte: 18}}
    • 💡 索引前缀规则：{a:1,b:1,c:1} 能被 {a}、{a,b}、{a,b,c} 的查询用上，但不能被只用 {b} 或 {b,c} 的查询用上。建索引时把最通用的字段放最前。

    索引类型速查

    类型创建方式用途
    单字段{age: 1}最常用；排序方向对单字段无所谓（可反向扫）
    复合{a:1, b:-1}多条件 + 排序；方向在复合里有意义
    多键 Multikey数组字段自动变多键数组每个元素一条索引条目；多字段数组索引有限制
    唯一 Unique{email:1},{unique:true}约束不重复；缺失字段按 null 处理
    稀疏 Sparse{sparse:true}只为「存在该字段」的文档建条目，省空间
    部分 Partial{partialFilterExpression:{...}}只索引满足条件的子集，比稀疏更灵活
    TTL{createdAt:1},{expireAfterSeconds:3600}自动过期删除；后台线程每 60s 跑一次
    文本 Text{title:"text"}全文检索；一个集合最多 1 个 text 索引
    地理 2dsphere{loc:"2dsphere"}附近的人、地理围栏
    Hashed{_id:"hashed"}分片键用，保证均匀分布（只支持等值）
    通配符 Wildcard{"$**":1}字段不固定时一把梭，4.2+
    隐藏 Hidden{hidden:true}先隐藏观察性能，确认无用再删

    覆盖查询：连文档都不用读

    如果查询的条件字段和返回字段都在索引里，MongoDB 直接从索引拿数据，完全不回表（不读文档）。执行计划里表现为 totalDocsExamined: 0。

    // 建复合索引
db.users.createIndex({ status: 1, city: 1, age: 1 });

// 覆盖查询：条件+投影全在索引里
db.users.find(
  { status: "active", city: "HZ" },
  { _id: 0, status: 1, city: 1, age: 1 }
).explain("executionStats");
// → totalKeysExamined: 1200, totalDocsExamined: 0   ✅ 完美

// 只要把 _id 放回来就要回表（除非 _id 也在索引里）
db.users.find({ status: "active" }, { age: 1 });  // 默认带 _id → 回表

    读执行计划：三个数字决定好坏

    db.users.find({ age: { $gte: 18 } }).explain("executionStats")
    字段含义好 / 坏
    stage访问方式IXSCAN 好；COLLSCAN 坏；SORT 出现在 fetch 前说明内存排序
    totalKeysExamined扫了多少索引条目越接近返回数越好
    totalDocsExamined回表读了多少文档0 最好（覆盖查询）
    nReturned最终返回条数理想比例：examined / returned ≈ 1
    executionTimeMillis耗时结合数据量看
    ⚠️ 黄金指标：keysExamined ÷ nReturned。这个比值是 1000 说明你扫了 1000 条才找到 1 条，索引不够精准，需要加字段或调整顺序。

    索引的代价

    • 写放大：每次 insert/update/delete 都要同步维护所有相关索引。索引越多写越慢。
    • 空间：索引可能比数据还大，且必须常驻内存才有效（WiredTiger 靠 cache 缓存索引）。
    • 选错索引：MongoDB 会并行试多个候选计划，胜出的缓存下来；索引太多会让选计划本身变慢。
    • 建索引阻塞：前台建索引会锁集合；生产环境用 background:true（4.2+ 默认后台化）。

    慢查询排查套路

  • 开 Profiler：db.setProfilingLevel(1, { slowms: 100 })
  • 查 db.system.profile.find().sort({ts:-1}).limit(10)
  • 对慢语句跑 .explain("executionStats")，看 stage 与三个数字
  • COLLSCAN → 补索引；IXSCAN 但 examined 大 → 调字段顺序或加字段
  • 有 SORT 阶段 → 让索引顺序匹配 sort（ESR 的 S）
  • 检查无用索引：db.users.aggregate([{$indexStats:{}}])，命中次数为 0 的考虑隐藏后删除

    • 建索引的正确姿势

    // 生产环境后台建，避免长时间锁
db.orders.createIndex({ status: 1, createdAt: -1 }, { background: true });

// 先隐藏观察再删（4.4+）
db.orders.hideIndex("status_1_createdAt_-1");
db.orders.unhideIndex("status_1_createdAt_-1");

// 部分索引：只给活跃订单建，省 90% 空间
db.orders.createIndex(
  { createdAt: -1 },
  { partialFilterExpression: { status: { $eq: "active" } } }
);

    🎯 常见问法与答题要点

    Q：复合索引 {a:1,b:1} 能被 {b:1} 的查询用上吗？

    A：不能。复合索引遵循最左前缀原则：只有从第一个字段开始的连续前缀才有效。{a:1,b:1,c:1} 支持 a / a+b / a+b+c，不支持 b / c / b+c。所以要按「最通用、最常单独查」的字段排前面。

    Q：ESR 法则里为什么 Range 要放最后？

    A：因为一旦遇到范围条件，索引在该字段之后就无法再用于精确定位和排序了——范围匹配出来的是一个区间，区间内后续字段无序。所以把 range 放最后，能最大化前面字段的定位能力。举例：{status:1, age:1, city:1} 遇到 age:{$gte:18} 后 city 就不能用于定位了。

    Q：索引方向（1 还是 -1）重要吗？

    A：单字段索引不重要，B-tree 可以正着扫也可以倒着扫。但复合索引重要：{a:1,b:-1} 和 {a:1,b:1} 对 sort({a:1,b:-1}) 的支持不同。必须让索引方向要么与 sort 完全一致，要么完全相反（{a:-1,b:1} 也支持 {a:1,b:-1}）。

    Q：多键索引（数组字段）有什么坑？

    A：①数组每个元素产生一条索引条目，数组长 1000 就是 1000 条；②复合索引里最多只能有一个数组字段（否则条目数会笛卡尔积爆炸）；③等值匹配数组是「任一无素匹配即命中」，语义上要注意；④大数组会让索引体积远超数据。

    Q：怎么知道索引有没有被用上？

    A：两条命令：语句级用 .explain("executionStats") 看 stage 是不是 IXSCAN；索引级用 db.coll.aggregate([{$indexStats:{}}]) 看 accesses.ops 计数。长期为 0 的索引就是纯负担，先 hide 观察一周再 drop。

    Q：TTL 索引是实时的吗？

    A：不是。后台线程每 60 秒跑一次，所以过期数据最多延迟 1 分钟被删。另外 TTL 要求字段是 Date 类型或含 Date 的数组；单字段索引才支持 TTL，复合索引不支持。

    Q：索引越多越好吗？

    A：恰恰相反。每个索引都会让写入变慢（要同步维护）、占用内存（索引必须热在 cache 里才有用）、拖慢查询计划选择。经验值：单集合索引控制在 5~10 个以内，且每个索引都要对应一个明确的真实查询。
