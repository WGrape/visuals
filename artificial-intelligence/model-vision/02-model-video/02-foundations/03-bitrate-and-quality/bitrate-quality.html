视频码率与质量：带宽预算怎么分配

在清晰度、压缩失真、时延和模型任务效果之间做可测量的取舍。

学完能解释什么

  • 分清分辨率、帧率和码率三个不同变量
  • 理解固定/可变码率与质量目标模式的边界
  • 同时用视频质量指标和下游任务结果做验证

逐步看机制

先明确任务和传输预算

视频会议更在意实时与错误恢复，离线电影更重视质量；AI 检测可能比主观画质更怕小目标失真。

码率不是帧率

帧率是每秒采样画面数量，分辨率是每帧空间采样密度，码率是每秒编码数据量。提升帧率会增加运动采样，但在固定码率下每帧可用比特可能变少；提升分辨率也不会从模糊源恢复细节。比较编码方案须固定源内容、codec、编码速度/延迟配置与采样约定。

选择 CBR、VBR 还是质量目标

CBR 适合传输容量明确且缓冲有限的链路，但复杂运动段可能被迫牺牲画质；VBR 随复杂度变化分配码率，平均码率好控制但瞬时峰值可能更高；CRF 等质量目标模式更强调相对稳定的编码质量，输出体积事先不保证。自适应流媒体还会提供多档码率，让播放器根据网络与缓冲选择版本。

“画质好”要明确比较口径

PSNR 测像素误差，对内容与时间严格对齐的参考视频有用；SSIM 测局部结构；VMAF 是训练得到的感知质量指标。它们各有局限，不能代替真实用户场景。给视频模型喂重压缩画面时，按运动幅度、快速字幕、暗场和小物体分组评价下游任务；平均质量分数高不一定意味着 OCR 或检测稳定。

实时系统还需测编码/解码延迟、码率突发和缓冲回压，避免用离线画质收益换来不可接受的端到端时延。

自检

固定码率下提高视频分辨率，画质一定提高吗？

不一定。更多像素会竞争同一比特预算，单像素保真可能下降，源本身也未必包含更多细节。

核心速览

码率 Bitrate每秒的数据量，如 4 Mbps；决定画质与体积的上限
分辨率画面像素数，如 1920×1080
帧率 FPS每秒帧数，24/25/30/60
三者关系体积 ≈ 码率 × 时长；画质 ≈ 码率 ÷ (分辨率 × 帧率)
关键认知分辨率高不等于清晰——码率不足的高分辨率反而比低分辨率更糊

码率、分辨率、画质的关系

画质 ≈ 每像素码率 = 总码率 ÷ (宽 × 高 × fps) —— 分辨率翻倍，码率要翻约 4 倍才能维持同等画质 这就是为什么"4K 但只有 2M 码率"的视频，看起来还不如"720p 2M 码率"清晰
图：码率固定时，分辨率越高每像素预算越少，画质反而下降

画质评估方法

客观指标

PSNR / SSIM：与原始未压缩视频逐像素比较，简单但与主观感受相关性一般。VMAF（Netflix 开源）：结合多种特征并用机器学习拟合主观评分，与主观感受相关性最好，是目前业界主流。

主观评价

最终标准。常用 MOS（平均意见分）：找若干评测者按 1~5 分打分取平均。做_codec 对比或码率阶梯测试时不可或缺。

无参考评估

线上无法拿到原始视频时，只能做无参考质量评估（检测块效应、模糊、噪声）。精度有限，但可大规模监控。

码率阶梯测试

把同一素材压成多个码率，画「码率-VMAF 曲线」，找到边际收益骤减的拐点——那就是性价比最优的码率。

省码率的手段

换高效编码H.264 → H.265 省 40%，→ AV1 再省 20%
内容自适应CRF 模式让复杂场景多给码率，简单场景少给
Per-Title 编码按每个视频的复杂度单独定码率，而非一刀切
分辨率自适应 ABR按用户带宽/设备动态切换码率档位（HLS/DASH）
预处理降噪先去噪再编码，能显著省码率（噪声极耗码率）

深入自检

码率越高画质一定越好吗？

在同一编码器和分辨率下，码率越高画质越好，但边际收益递减：从 1M 到 2M 提升明显，从 8M 到 16M 几乎看不出差别。更重要的是跨分辨率比较没有意义——4K@4M 的画质通常不如 1080p@4M，因为 4K 的像素数是 1080p 的 4 倍，每像素分到的码率只有 1/4，量化更粗糙，反而出现块状伪影和细节丢失。所以正确的做法是：先按目标画质确定每像素码率，再乘以分辨率得出总码率。

VMAF 是什么？为什么比 PSNR 好用？

VMAF（Video Multi-method Assessment Fusion）是 Netflix 开源的画质评估指标。它不只看像素误差，而是融合多种特征（细节损失、运动、亮度等），并用机器学习拟合人类主观评分。相比之下，PSNR/SSIM 只看像素级差异，与人的主观感受相关性较差（PSNR 高的视频可能因为过度平滑看起来更糊）。VMAF 得分范围 0~100，一般认为 93+ 是「几乎无感知差异」，80 左右是「可接受」，低于 60 明显劣化。它是目前做码率优化和编码器对比的业界标准。

为什么我的视频在本地很清楚，上传后就糊了？

因为平台会重新转码。你上传的原始视频会被平台压成多个码率档位（供不同带宽用户播放），而平台为了节省存储和带宽，通常使用较低的码率。更糟的是，如果你的原始视频本身已经是压缩过的，平台再压一次就是二次压缩，代际损失叠加。对策：①上传时尽量提供高码率的原始素材（平台给的上传码率上限内尽量高）；②用平台推荐的编码参数（H.264 + 合适 profile）；③避免上传已经被压过很多次的版本；④画面不要有过多噪点和快速运动（这些最耗码率）。

做自适应码率（ABR）要注意什么？

ABR（HLS/DASH）把视频切成多个码率档位，客户端按带宽动态切换。要点：①档位设计——通常 5~7 档，相邻档位码率比约 1.5~2 倍，覆盖从 240p 低码到 1080p；②关键帧对齐——所有档位必须在相同时间点有 I 帧，否则切换时会黑屏或卡顿；③分片时长——常用 2~6 秒，太短则请求多、太长则切换不灵敏；④起播优化——首片用低码率快速起播，再逐步升档；⑤缓冲策略——客户端要留足够缓冲避免频繁抖动切换。

怎么在不明显降质的前提下把视频体积压小？

按顺序尝试：①换更高效的编码器——H.264→H.265 通常省 40%，这是最大杠杆；②用 CRF 而非固定码率——让编码器按内容复杂度分配，避免浪费；③做 Per-Title 优化——动画、静态课件这类简单内容可以用很低的码率，动作大片则需要高码率，不要一刀切；④降噪预处理——噪点极其耗码率，先轻度降噪能省不少；⑤适当降分辨率——如果目标是在手机上看，1080p 降到 720p 可能比保持 1080p 低码率效果更好；⑥降低帧率——30fps 降到 24fps 对多数内容影响不大但对运动画面明显。最后用 VMAF 验证质量是否可接受。

码率与质量的关系是对数而非线性：从 1Mbps 加到 2Mbps 质量提升明显，从 8Mbps 加到 9Mbps 几乎看不出差别。超过某点后继续加码率是纯浪费带宽，这个点就是「视觉无损点」，1080p H.264 大约在 6~8 Mbps。

编码命令与参数

# CRF 恒定质量模式（推荐，单遍；CRF 每 +6 约减一半码率）
ffmpeg -i in.mp4 -c:v libx264 -crf 23 -preset medium -c:a aac -b:a 128k out.mp4
#   CRF: 18 = 视觉无损, 23 = 默认, 28 = 明显压缩；范围 0(无损)~51
#   preset: ultrafast/superfast/veryfast/faster/fast/medium/slow/slower/veryslow
#           slow 比 medium 省 5~10% 码率但慢 3 倍；veryslow 省 10~15%，慢 10 倍

# 限制码率（有带宽上限时）用两遍 ABR
ffmpeg -i in.mp4 -c:v libx264 -b:v 5M -pass 1 -f null /dev/null
ffmpeg -i in.mp4 -c:v libx264 -b:v 5M -pass 2 -c:a aac -b:a 128k out.mp4

# H.265 同质量省约 40~50% 码率
ffmpeg -i in.mp4 -c:v libx265 -crf 28 -preset medium out.mp4   # crf28(265) ≈ crf23(264)

# 关键帧间隔（影响 seek 与直播首帧）
ffmpeg -i in.mp4 -g 60 -keyint_min 60 -sc_threshold 0 out.mp4  # 30fps 时 2 秒一个关键帧

# 查看实际码率与帧信息
ffprobe -v error -select_streams v:0 -show_entries stream=bit_rate,width,height,r_frame_rate,codec_name -of default=nw=1 in.mp4
# 批量评估：VMAF 对比不同码率的质量
ffmpeg -i out.mp4 -i in.mp4 -lavfi libvmaf=log_path=vmaf.json -f null -
# VMAF > 93 接近无损感知；80~93 良好；< 70 明显劣化

# 直播场景的 ABR 阶梯（HLS/DASH）
# 1080p 5Mbps / 720p 3Mbps / 540p 1.5Mbps / 360p 0.8Mbps
# 切片 2~6 秒：太短请求多，太长卡顿恢复慢

分辨率也不是越高越好：码率固定时，1080p 糊成一片还不如 720p 清晰。经验判据：每像素比特数（bpp）低于 0.06 时画质会明显崩，1080p@30fps 需要至少 1920×1080×30×0.06 ≈ 3.7 Mbps。
