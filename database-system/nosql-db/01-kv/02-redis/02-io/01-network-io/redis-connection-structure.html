⑥ 连接相关重要配置参数（服务端）
maxclients
最大并发连接数，默认 10000。超出后新连接返回 "ERR max number of clients reached"
tcp-backlog
TCP 握手队列长度（默认511），高并发下需同步提高 somaxconn 内核参数
timeout
连接空闲超时（秒），0=永不超时；生产建议设 300，防止僵尸连接积累
tcp-keepalive
TCP KeepAlive 探测间隔（秒，默认300）。操作系统层面检测死连接
client-query-buffer-limit
单客户端接收缓冲上限（默认1GB），超出强制断开，防止单连接耗尽内存
client-output-buffer-limit
输出缓冲限制，分三类：normal / slave / pubsub。Pub/Sub 慢消费者超限会被强制断开

连接参数与排障

# 输出缓冲区三类限制（这是最常被撑爆的地方）
client-output-buffer-limit normal 0 0 0              # 普通客户端：不限（危险！大 key 会撑爆）
client-output-buffer-limit slave   256mb 64mb 60     # 主从：硬256MB / 软64MB持续60s
client-output-buffer-limit pubsub  32mb  8mb  60     # 订阅：硬32MB / 软8MB持续60s

# 含义：软限制 64MB 且持续 60 秒 -> 断开；或硬限制 256MB -> 立即断开
# 典型故障：订阅者消费慢 -> pubsub 缓冲区涨到 32MB -> 被踢 -> 消息丢失

最经典的坑：一个 KEYS * 或返回百万元素的 LRANGE，输出缓冲区会瞬间涨到几百 MB——Redis 是单线程的，这个大响应会阻塞所有其他客户端。所以生产必须禁用 KEYS（用 SCAN），且限制返回条数。

连接池配置

# Go: go-redis 连接池配置
rdb := redis.NewClient(&redis.Options{
    Addr:         "localhost:6379",
    PoolSize:     30,                  // 最大连接数（默认 10 * CPU 核数）
    MinIdleConns: 10,                  // 最小空闲连接，避免每次新建
    MaxConnAge:   30 * time.Minute,     // 连接存活上限，防止长连接老化
    PoolTimeout:  3 * time.Second,      // 连接池满了等待多久（必须设！）
    IdleTimeout:  5 * time.Minute,      // 空闲多久回收
    DialTimeout:  5 * time.Second,
    ReadTimeout:  3 * time.Second,      // 必须设，防止慢查询拖死
    WriteTimeout: 3 * time.Second,
})

# 关键：PoolTimeout 不设的话，连接池耗尽时请求会无限等待
#       表现为"服务卡死"，实际上是所有 goroutine 都在等 Redis 连接

# Java: Lettuce 连接池
#   lettuce.pool.max-active=30  max-idle=10  min-idle=5  max-wait=3s

连接池不是越大越好：Redis 是单线程处理命令，连接数超过一定值后上下文切换和内存反而成为负担。经验上限：单实例总连接数 < 1 万，且单客户端池 < 100。真正的吞吐瓶颈是网络 RTT，提升手段是 pipeline / MGET / Lua 脚本而不是加连接。

pipeline 与批量命令：吞吐提升的关键

手段原理提升倍数注意
Pipeline多条命令打包一次 RTT5 – 10×不宜超过 1 万条/批，会阻塞
MGET/MSET单命令多个 key接近 pipeline只适用于同类型
Lua 脚本服务端原子执行多命令省 RTT + 原子性脚本要短，别跑长循环
事务 MULTI打包但不省 RTT（只是保证顺序）0（不提速）常被误用为提速手段

pipeline 与 Lua

# 实测：pipeline 的收益（同机房 RTT 0.2ms）
redis-benchmark -t set -n 100000 -q          # 无 pipeline：约 6-10 万 QPS
redis-benchmark -t set -n 100000 -P 16 -q    # pipeline 16：约 50-100 万 QPS

# Go: pipeline 正确用法
pipe := rdb.Pipeline()
for i := 0; i < 1000; i++ {
    pipe.Set(ctx, fmt.Sprintf("k%d", i), i, 0)
}
_, err := pipe.Exec(ctx)     // 一次 RTT 完成 1000 条

# 分批控制（避免一次塞太多导致阻塞）
const batch = 500
for i := 0; i < len(keys); i += batch {
    end := min(i+batch, len(keys))
    pipe := rdb.Pipeline()
    for _, k := range keys[i:end] { pipe.Set(ctx, k, val, 0) }
    pipe.Exec(ctx)
}

# Lua 脚本：原子地做"读-判断-写"（避免并发竞态）
const script = `
local cur = redis.call('GET', KEYS[1])
if cur and tonumber(cur) > tonumber(ARGV[1]) then
    return 0
end
redis.call('SET', KEYS[1], ARGV[1], 'EX', 60)
return 1
`
rdb.Eval(ctx, script, []string{"maxid"}, newID)

MULTI/EXEC 不提升性能——它只是把命令排队，每条仍要一次 RTT。很多人误以为事务能加速，实际上只有 pipeline 能省 RTT。（Jedis 等客户端的“事务 + pipeline”合并模式才会既原子又快速。）

深入自检

为什么 Redis 单线程还能支撑 10 万 QPS？

因为瓶颈不在 CPU。纯内存操作约 100 ns，而网络 RTT 是 0.2 ms = 20 万 ns——也就是说 99.95% 的时间花在网络 IO 上，CPU 大部分时候是空闲的。单线程 + IO 多路复用（epoll）足以把网络 IO 跑满。多线程的收益极小，却要付出锁竞争、缓存一致性、复杂度的代价。（Redis 6.0 的多线程只用来做网络读写和协议解析，命令执行仍是单线程。）

连接数突然暴涨怎么排查？

四步：① INFO clients 确认规模；② CLIENT LIST 按 addr 聚合，看是哪个应用实例；③ 看 cmd= 字段——如果大量停在 blpop/brpop，说明是阻塞订阅没设超时；④ 检查客户端是否每次请求新建连接（没用连接池）。最常见的两个原因：连接池配置错误和应用重启后旧连接没释放（设 timeout 可自愈）。

慢查询怎么定位？

三步：① 用 SLOWLOG GET 10 看最近慢命令（默认记录 > 10 ms 的，不含网络 IO 时间）；② CONFIG SET slowlog-log-slower-than 5000 调阈值；③ 用 LATENCY DOCTOR 看延迟诊断。最常见的三类慢查询：KEYS *（全库扫描）、大 key 的一次性读取（百万元素的 LRANGE/HGETALL）、时间复杂度误用（对大集合做 SUNION、ZRANGE 大范围）。

客户端缓存（client-side caching）值得用吗？

值得，尤其对热点 key。Redis 6.0+ 的 CLIENT TRACKING 让服务端在 key 被修改时主动推送失效通知，客户端维护本地缓存，可以把热点读的延迟从 0.2 ms 降到 微秒级，并大幅降低 Redis 压力。代价：① 客户端库要支持（Lettuce/Jedis 支持，go-redis 部分支持）；② 需要额外的连接接收失效消息；③ 一致性是失效通知驱动，网络问题会导致短暂不一致。适合读多写少的配置类、字典类数据。
