什么时候适用？

判断信号：数据可被拆成输入输出契约清楚的顺序处理阶段。

  • 日志解析、校验、脱敏、写出流水线

和相近方案怎么区分？

相近方案选择边界
责任链责任链的某环可终止或处理请求；管道过滤器重在每段转换数据并交给下一段。
工作流编排工作流可能有分支、等待和回退；线性管道更适合连续转换。

最小伪代码

records = readLines(source)
parsed = map(parseLine, records)
valid = filter(isValid, parsed)
write(sink, map(normalize, valid))

边界：每段应有明确输入输出契约；有状态过滤器和错误处理需要额外约定。

管道-过滤器 Pipe & Filter

每个过滤器只做一件事，可任意重组顺序

每个过滤器是无状态、独立的处理单元（如压缩、加密、日志、校验），管道负责把前者的输出接成后者的输入。Unix 的 `cat | grep | sort` 就是经典范例。

适用与优势

  • 高复用：过滤器可像乐高一样重组。
  • 并行友好：相邻过滤器可流水线并行。
  • 可演进：增删环节不影响其他。
  • 常用于编译器前端、ETL、多媒体处理。

面试高频问答

Q：管道-过滤器和职责链有什么区别？
A：管道-过滤器是『数据流经一串变换、产出新数据』；职责链是『请求在链上传递、由某节点处理或不处理』。前者变换数据，后者传递/拦截请求。
Q：过滤器为什么要求无状态？
A：无状态才能保证任意排序与并行都不影响结果，也便于水平扩展与故障重试。

管道-过滤器：像流水线一样处理数据流

管道-过滤器（Pipe-Filter）是一种数据流架构：把处理过程拆成若干个独立的过滤器（Filter），每个过滤器只做一件事，它们之间用管道（Pipe）连接，上一个的输出就是下一个的输入。典型例子是 Unix 命令行：cat log | grep ERROR | sort | uniq -c——每个命令都是过滤器，竖线就是管道。

管道-过滤器结构：Source → Filter 链 → Sink

过滤器 vs 管道：各自职责

角色职责典型实现设计要点
数据源 Source产生初始数据流文件读取、Socket 接收、MQ 消费、数据库游标负责分批与限速，别一次性把全量数据灌进管道
过滤器 Filter读输入 → 处理 → 写输出解析器、校验器、转换器、聚合器、编码器无状态最好；若必须有状态（如聚合窗口），要明确边界
管道 Pipe连接过滤器，传输数据内存队列、流（Stream）、Unix pipe、Kafka topic决定背压行为：有界队列会阻塞上游，无界队列会 OOM
数据汇 Sink消费最终结果写文件、发 HTTP、入库、发消息负责最终的一致性保证（批量提交、幂等）

过滤器的四种类型：生产者（只有输出）、转换器（输入输出都有，做变换）、测试器（按条件放行或丢弃，如过滤器 / 分流器）、消费者（只有输入）。真实系统大多是转换器 + 测试器的组合。

背压：管道架构的生命线

为什么必须有背压

如果上游快、下游慢，而无界队列在中间堆积，最终必然 OOM。背压（Backpressure）就是让消费速度反过来约束生产速度的机制。

  • 没有背压的异步系统，在高负载下一定会崩
  • 这是 Reactive Streams / Flow / Akka Streams 的核心命题

三种背压策略

  • 阻塞：队列满时上游线程阻塞等待（最简单，线程会占住）
  • 丢弃：新数据丢弃（采样场景可接受；要计数并告警）
  • 限速：下游主动向上游请求 N 条（request(n)，最灵活，响应式流标准做法）

有界队列的容量怎么定

  • 太小：上游频繁阻塞，吞吐上不去
  • 太大：内存占用高，且故障时积压数据全丢
  • 经验：按「单条大小 × 目标缓冲时长 × 峰值速率」估算，并设监控

并行化

  • 多个过滤器可以并行执行（不同数据在链上不同位置，像流水线）
  • 同一过滤器也可多实例并行（无状态前提下）
  • 瓶颈在最慢的那个过滤器——优化要盯住它，而不是平均分配资源

适用边界与坑

  • 适合：数据可以流式处理、处理步骤相对独立、需要灵活组合与复用、批处理与流式计算场景。
  • 不适合：需要交互式反馈（用户等结果再决定下一步）、需要全局事务（任一步失败整体回滚）、步骤之间需要大量共享状态。
  • 坑 1：过度拆分。每个过滤器都有数据传递与可能的序列化开销，拆得过细会让性能与调试都变差。
  • 坑 2：错误处理不明确。某个过滤器抛异常后怎么办？必须预先约定：跳过该条并记日志、整批失败、还是进入死信队列。不同数据能容忍的错误策略不同，建议可配置。
  • 坑 3：隐式状态。过滤器里偷偷用了全局变量或线程上下文，会导致并行时出错。要保持「输入决定输出」的纯粹性。
  • 坑 4：观测缺失。数据经过 N 个过滤器后少了多少、错了多少、各阶段耗时多少，必须在每个过滤器出口埋点，否则线上出问题无法定位是哪一环。

深入自检

管道-过滤器和责任链模式是一回事吗？

形似而神不同。责任链（Chain of Responsibility）是行为型设计模式，链上每个处理器决定「自己处理还是交给下一个」，通常只有一个处理器最终处理，目标是解耦请求与处理者，数据是一个对象在各处理器间传递并可能被修改。管道-过滤器是架构风格，每个过滤器都会处理流经的每一份数据，目标是数据变换，强调流式、可并行、可组合。Servlet Filter 链其实更接近责任链（有 chain.doFilter 决定是否继续），而 Netty Pipeline 与编译器流水线才是典型的管道-过滤器。

为什么流式处理比批量读进来处理更好？

三个原因：① 内存——流式只需常驻一小份缓冲，批量要把全量数据载入内存，数据量一大就 OOM；② 延迟——流式第一条数据可以在最后一条还没到达时就已经处理完成（流水线并行），批量必须等全部就绪；③ 组合性——流式组件可以任意拼接，批量处理往往是整块逻辑难以复用。代价是流式编程心智负担更高，且单条处理的开销（函数调用、上下文切换）相对更大，所以实践中常做「微批处理」折中——每积累 1000 条或 100ms 处理一次。

过滤器之间应该用内存队列还是消息中间件？

取决于是否需要「跨进程」与「持久化」。同一进程内用内存队列（Disruptor、BlockingQueue）延迟最低，但进程崩溃数据全丢、也无法跨机器扩展。跨进程用 Kafka/Pulsar 等消息中间件：可持久化、可重放、可跨机器扩缩容，代价是毫秒级延迟与运维成本。判断标准：数据量是否超过单机处理能力？是否需要重放或审计？是否允许进程崩溃丢数据？三个都是否 → 用内存队列；任一为是 → 上消息中间件。

如何测试管道-过滤器架构？

优势恰恰在这里：因为过滤器无状态且接口统一，可以逐个单独测试——给定输入断言输出，无需启动整条链路。三个层次：① 单元测试每个过滤器（输入 → 输出）；② 集成测试整条链路（喂入样本数据，校验最终输出与统计指标）；③ 故障注入测试（某个过滤器抛错、变慢、返回空，验证整条链的容错与背压行为）。这是该架构相对单体处理逻辑最大的工程优势之一。
