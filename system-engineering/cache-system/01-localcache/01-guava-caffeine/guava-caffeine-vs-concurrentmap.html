🆚 为什么不能直接用 ConcurrentHashMap 当缓存

ConcurrentHashMap 只是个并发容器，缺少容量控制、过期清理与淘汰策略——这三件事才是「缓存」的本质。

先建立直觉：柜子和会自己整理的柜子

ConcurrentHashMap 是一个并发安全的柜子：多人同时存取不会乱。但它只管存取——东西放进去就一直在那儿。

缓存需要的是一个会自己整理的柜子：满了要腾位置、过期要清理、还要知道该先扔哪一个。这些 CHM 全都不提供。

缺的三件事

能力ConcurrentHashMap本地缓存（Caffeine/Guava）
并发安全✅ 有（分段/CAS）✅ 有
容量上限❌ 没有，put 多少装多少✅ maximumSize / maximumWeight
过期清理❌ 没有，数据永不失效✅ expireAfterWrite / expireAfterAccess
淘汰策略❌ 没有✅ LRU / W-TinyLFU
自动加载❌ 需自己写（且有击穿风险）✅ get(key, loader)，自带加载保护
命中率统计❌ 无✅ recordStats()
移除回调❌ 无✅ removalListener
用 CHM 当缓存最直接的后果是内存泄漏。因为它没有容量上限也没有过期机制，只要不断 put，内存就会一直涨，直到 OOM。这在长期运行的服务里是必然发生的，不是「可能」。

如果非要自己撸，至少要补什么

还有一个隐性问题：击穿。用 CHM 手写「miss → 查库 → put」时，高并发下所有线程都会同时查库。而 Caffeine 的 get(key, loader) 保证同一 key 只有一个线程回源。这个保护自己实现起来并不容易。

什么时候真的可以用 CHM

  • ✅ 数据量极小且固定：如启动后加载的几百条字典/配置，不再变化，总量可控。
  • ✅ 作为更大缓存实现的底层存储：比如你自己写分段缓存，每段用 CHM 存。
  • ❌ 作为通用缓存：任何「数据会持续增长」或「需要失效」的场景都不行。
一句话：CHM 解决的是并发存取，缓存解决的是有界 + 会过期 + 能淘汰。两者不是替代关系，而是「你在 CHM 之上还要补很多东西才是缓存」。

🎯 面试问答

Q：用 ConcurrentHashMap 存少量配置可以吗？
A：可以，这是它少数合适的场景之一：数据量小、固定、不再变化、不需要过期（如启动加载的字典表、枚举映射）。因为总量可控，不存在内存泄漏问题，也无需淘汰。但即使这样，也建议明确注释「这是常量映射，不是缓存」，避免后人误当成缓存往里塞动态数据。

Q：自己加个定时清理不就行了？
A：可以，但你要自己解决一串问题：清理时读写要不要加锁（会不会阻塞）？清理频率和扫描量怎么定（会不会影响主线程）？只清理不淘汰的话，写入速度超过清理速度时怎么办？命中率怎么监控？这些都能做，但加起来就是重新实现一遍 Caffeine。直接用成熟库通常更划算，且经过大量生产验证。

Q：Caffeine 底层用的是什么数据结构？
A：它内部使用分段（stripe）的哈希表，设计理念类似 ConcurrentHashMap，但在其上叠加了：基于环形缓冲区的异步事件处理（读写操作记入 buffer，由后台线程批量应用，从而让读路径几乎无锁）、Count-Min Sketch 频次统计、以及 Window/Main 两段 LRU 结构。这也是它能在高并发下保持高吞吐的原因。

Q：缓存的 value 很大时需要注意什么？
A：两点：① 用权重限容而非条目数——maximumWeight + weigher，否则少量大对象就能撑爆内存；② 考虑只缓存必要字段，不要把整个大对象塞进去。另外 Caffeine 的 expireAfterAccess 与 refreshAfterWrite 对大对象要谨慎，频繁刷新会带来可观的序列化/网络开销。

Caffeine 关键参数与默认值速查

参数默认值含义与调参建议
initialCapacity16初始哈希表容量。已知条目数时设为 size/0.75 可减少扩容
maximumSize无上限按条目数驱逐。必须显式设置，否则进程缓存会无限增长直到 OOM
maximumWeight无上限配合 weigher 按权重驱逐（如按 value 字节数）
expireAfterWrite不过期写入后固定过期。适合弱一致的配置/字典数据
expireAfterAccess不过期读后刷新过期。适合热点会话，但会引入读放大
refreshAfterWrite不自动刷新过期后异步刷新，旧值继续返回（不会阻塞请求）
softValues/weakKeysfalse交给 GC 回收。一般不推荐，GC 压力不可控
recordStats()关闭开启后有约 1%~3% 的额外开销，生产建议开，QPS 极高时评估

为什么 Caffeine 替换 Guava Cache：命中率上 Caffeine 的 Window-TinyLFU 在 Zipf 分布下比 Guava 的 LRU 高 5%~20%；并发上 Caffeine 读操作多数无锁（Guava 用分段锁），16 线程读场景下吞吐约为 Guava 的 2~4 倍。

迁移成本很低：Caffeine 的 Cache/LoadingCache 接口与 Guava 几乎一致，官方还提供 caffeine-guava 的 GuavaAdapters 做双向适配，可灰度替换。

可直接落地的构建代码

// Caffeine：size + 写过期 + 异步刷新 + 统计
Cache<String, User> cache = Caffeine.newBuilder()
    .initialCapacity(1024)                 // 预估 1024/0.75 ≈ 1365 条
    .maximumSize(10_000)                   // 硬上限，防 OOM
    .expireAfterWrite(Duration.ofMinutes(10))
    .refreshAfterWrite(Duration.ofMinutes(1))  // 到期后异步刷新，旧值仍可读
    .recordStats()                         // 开 hitRate / evictionCount
    .removalListener((k, v, cause) -> {    // WAS_REPLACED / EXPIRED / SIZE / EXPLICIT
        if (cause == RemovalCause.SIZE) metrics.inc("cache.evict.size");
    })
    .build();

// 命中率观测（生产必接）
CacheStats s = cache.stats();
// s.hitRate() 目标 > 0.9；s.evictionCount() 突增 = 容量不够或突发流量
// s.averageLoadPenalty() 单位纳秒，> 10ms 说明 loader 慢，会拖垮调用方
// 权重驱逐：按 value 实际大小限制，而不是条数
Cache<String, byte[]> blob = Caffeine.newBuilder()
    .maximumWeight(256 * 1024 * 1024)      // 256 MiB
    .weigher((String k, byte[] v) -> v.length)   // 返回 0 会导致永不驱逐！
    .build();

// Guava -> Caffeine 适配器（灰度迁移用）
com.github.benmanes.caffeine.guava.CaffeinatedGuava.build(
    Caffeine.newBuilder().maximumSize(10_000), CaffeineGuava.asGuavaCache());

深入自检

maximumSize 和 expireAfterWrite 同时设置，谁先生效？

两者都是驱逐条件，任一满足即驱逐。Caffeine 内部按 O(1) 的时间轮 + LRU 队列维护，过期条目不会立刻物理删除，而是在写操作或定期维护中被清理。

refreshAfterWrite 和 expireAfterWrite 设成一样会怎样？

refresh 永远不会触发——因为条目先被 expire 判定过期并同步重新加载了。正确做法是 refresh < expire，例如 refresh 1 分钟、expire 10 分钟。

为什么 weigher 返回 0 很危险？

权重为 0 的条目不计入 maximumWeight，可以无限堆积。同理 weigher 返回值必须 > 0，且要保证同 key 的权重稳定，否则内部计数会错乱。

本地缓存要不要做预热？

要，尤其是冷启动瞬时流量大的场景。做法：启动时 getAll 批量加载热 key，或用 Cache.putAll 直接灌入。不预热时冷启动命中率为 0，会把 DB 打穿。

recordStats 的开销值得开吗？

值得。开销约 1%~3%，换来 hitRate/evictionCount/loadPenalty 三个关键指标。没有命中率就无法判断容量是否合理，只能靠猜。QPS 十万级以上的极热路径可单独关掉。
