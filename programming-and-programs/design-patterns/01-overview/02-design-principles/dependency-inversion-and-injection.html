04 · 把原则写进代码

最小伪代码

interface PaymentPort { charge(amount): Receipt }
class CheckoutService {
  constructor(payment: PaymentPort) { this.payment = payment }
  pay(order) {
    order.ensurePayable()
    return this.payment.charge(order.total)
  }
}
class StripeAdapter implements PaymentPort {
  charge(amount) { return mapReceipt(stripe.charge(toCents(amount))) }
}

从代码中带走三件事

  1. DIP 是依赖方向：业务不依赖具体 SDK。
  2. DI 是传入依赖的做法，不要求引入容器框架。
  3. 端口由业务需要定义，别照搬第三方 SDK 的全部方法。
05 · 原则不是教条

对应哪些模式？什么时候收手？

  • 适配器：把外部接口翻译成业务契约
  • 工厂方法：创建具体实现但消费端只见接口
  • 代理：保持接口并控制访问

不是每个类都需要接口。只有真实的替换边界、外部依赖或测试隔离需求，才值得引入抽象。

依赖注入和依赖倒置是一回事吗？

不是。依赖倒置规定高层依赖抽象；依赖注入是把依赖从外部传入的一种实现手段。

依赖倒置：把箭头反过来

传统分层里，高层依赖低层实现（Service → MySQLStore）。依赖倒置要求：高层不依赖低层，二者都依赖抽象。于是更换底层实现不再影响上层。

依赖倒置把「高层依赖低层」变成「双方依赖抽象」
倒置依赖方向从「向下」变成「都指向抽象」。
抽象归高层接口由使用方定义，不是提供方。
可替换换实现不动上层代码。
可测试测试时注入 mock 即可。

依赖倒置 vs 依赖注入

概念是什么解决什么
依赖倒置（DIP）设计原则：依赖抽象而非实现降低耦合、提高可替换性
控制反转（IoC）把流程控制权交给框架或容器让通用流程复用，业务只填细节
依赖注入（DI）实现方式：由外部传入依赖把「怎么拿到依赖」从类里移除
// Go 里最常见的 DI：构造函数传接口 type Store interface { Get(ctx context.Context, id int64) (*Order, error) Save(ctx context.Context, o *Order) error } type OrderService struct { store Store // 依赖抽象 log *slog.Logger } func NewOrderService(s Store, l *slog.Logger) *OrderService { return &OrderService{store: s, log: l} } // 装配在 main 里完成 store := mysql.NewStore(dsn) svc := NewOrderService(store, logger) // 测试时注入内存实现 svc := NewOrderService(&memStore{}, testLogger)

不需要 DI 框架：Go 里「构造函数传依赖」就是依赖注入，编译期可见、无反射、无魔法。只有当装配逻辑极其复杂时才考虑编译期生成工具（如 wire）。

三种注入方式与各自的适用

构造函数注入

  • 最推荐：依赖在构造时确定，之后不可变
  • 对象始终处于完整状态
  • 依赖一目了然
func NewService(s Store, c Cache) *Service { if s == nil { panic("store required") } return &Service{store: s, cache: c} }

字段 / setter 注入

  • 适合可选依赖或循环装配
  • 缺点：对象可能处于不完整状态
  • Go 里常用于测试时替换某个字段
s := &Service{} s.Logger = testLogger // 可选覆盖 // 生产代码谨慎使用： // 调用方可能忘记设置而拿到零值

方法参数注入

  • 依赖只在这一次调用中需要
  • 最灵活，也最显式
  • 适合请求级依赖（ctx、logger、tx）
func (s *Service) Create(ctx context.Context, o *Order) error // ctx 携带 trace id、超时、取消 // 事务作为参数或放在 ctx 里传递

反模式与注意事项

Service Locator全局容器取依赖，隐藏了真实依赖，难测试
全局单例隐式依赖 + 共享状态，测试互相污染
init 里建连接启动即失败不好处理，测试也难
过度注入什么都传接口，反而看不出真正的变化点
接口过宽注入了大接口但只用一两个方法
循环依赖Go 编译期报错，靠接口倒置或下沉解决
// ❌ Service Locator：依赖被隐藏 func Create(o *Order) error { db := locator.Get("db").(*sql.DB) // 依赖藏在这里 ... } // ✅ 显式注入：看签名就知道需要什么 func (s *Service) Create(ctx context.Context, o *Order) error { return s.store.Save(ctx, o) } // ❌ 全局单例：并发测试会互相干扰 var defaultStore Store // ✅ 由调用方持有实例 type Service struct{ store Store }

判断标准：看类型定义（struct 字段与构造函数）能否回答「它需要什么」。如果需要读代码才能知道，就说明依赖被隐藏了。

深入自检

依赖倒置和依赖注入是一回事吗？

不是。倒置是设计原则（依赖抽象而非实现），注入是实现手段（由外部提供依赖）。你可以注入具体类型（满足注入但不满足倒置），也可以倒置但不注入（较少见）。两者常一起使用，但概念不同。

为什么不建议用 DI 框架？

Go 的构造函数注入已经足够清晰，且是编译期可见的静态代码。框架的反射与容器会带来启动开销、隐式行为与调试困难。只有在依赖关系庞大到手工装配难以维护时，才考虑编译期生成工具。

全局单例有什么问题？

它让依赖变成隐式的：读代码看不出谁依赖了它，测试也难以替换。更糟的是共享状态会让并发测试互相干扰。若确实需要全局对象，至少提供可替换的入口并明确文档说明。

接口应该由谁定义？

由使用方定义。这样接口天然只包含使用方真正需要的方法，也不会被多个调用方的需求拉扯膨胀。提供方只需实现接口，不必预先猜测调用方需要什么。

注入太多依赖怎么办？

通常说明这个类承担了过多职责，应当拆分。也可能是可选依赖过多——可以用函数式选项把它们变成可选。若确实需要很多协作对象，考虑引入一个「门面」把一组相关依赖打包。
