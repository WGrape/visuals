🕸️ Neo4j 概览

属性图模型、无索引邻接，以及图数据库真正擅长的那类问题

一句话定位

Neo4j 是目前最主流的原生图数据库：数据以「节点 + 关系」的形式存储，关系是一等公民（不是外键、不是 JOIN 表）。它的核心卖点是 index-free adjacency（无索引邻接）——从某个节点出发走关系，代价与图的局部连接数有关，而与全图规模无关。

🌰 打个比方：关系库查「朋友的朋友」像在电话簿里一页页翻找；Neo4j 像每个人口袋里直接揣着朋友的电话号码——你问 A，A 直接把他朋友的联系方式递给你，走多少层都一样快。
数据模型属性图：节点(Node) + 关系(Relationship) + 标签(Label) + 属性(Property)
查询语言Cypher —— 用 ASCII 艺术描述图模式，声明式
核心优势多跳关系遍历，深度增加时性能不会指数衰减
事务完整 ACID（单实例/因果集群），写入即落盘

属性图模型的四件套

有向、有类型、可带属性 ③ Label / Property 分类标签与键值对 ④ 关系两端直接存了对方的物理指针 → 遍历不需要查索引

无索引邻接：为什么它快

关系型数据库Neo4j
关系怎么存外键列 + JOIN 表，靠索引查找关系记录里直接存两端节点的物理指针
查 2 跳朋友2 次 JOIN，每次索引查找 O(log N)顺指针走 2 步，O(局部度数)
查 5 跳朋友5 次 JOIN，代价随深度指数级放大顺指针走 5 步，代价随深度线性增长
数据量大 10 倍明显变慢基本不变（只与局部连接有关）
💡 这就是图数据库的核心价值：查询代价与「你要探索的局部」成正比，而与「数据库总共有多少数据」无关。

该用 / 不该用

✅ 强烈适合

  • 社交网络：好友推荐、N 度人脉、影响力传播
  • 风控反欺诈：团伙识别、环路检测、资金链路追踪
  • 知识图谱：实体关系、语义推理、问答
  • 推荐系统：基于关系的协同过滤、路径挖掘
  • IT 运维/依赖分析：故障影响面、根因定位
  • 权限与组织架构：层级继承、可达性判断

❌ 不适合

  • 大批量同构数据更新（如全表 UPDATE）
  • 重度聚合统计（OLAP）—— 图数据库不做列式扫描
  • 简单 KV 点查（用 Redis/KV 库更合适）
  • 超大规模属性存储（大文本、BLOB）
  • 关系很浅、只有 1 跳（关系库 JOIN 完全够用）
⚠️ 判断标准很简单：如果你的核心查询需要「沿着关系走多跳」，图数据库才有意义。只查 1 跳的话，关系库 + 索引更快也更省心。

上手三分钟

// 1. 创建节点（CREATE）
CREATE (a:Person {name:'Alice', age:30})
CREATE (b:Person {name:'Bob', age:28})
CREATE (c:Company {name:'Acme'})

// 2. 创建关系
MATCH (a:Person {name:'Alice'}), (b:Person {name:'Bob'})
CREATE (a)-[:KNOWS {since:2020}]->(b)

// 3. 查询：Alice 的朋友
MATCH (a:Person {name:'Alice'})-[:KNOWS]->(f)
RETURN f.name

// 4. 二度人脉（朋友的朋友，排除自己）
MATCH (a:Person {name:'Alice'})-[:KNOWS*2]->(fof)
WHERE fof <> a
RETURN DISTINCT fof.name

// 5. 最短路径
MATCH p = shortestPath(
  (a:Person {name:'Alice'})-[*..5]-(b:Person {name:'David'}))
RETURN p

因果集群（Causal Cluster）Core Server（写，Raft 共识）+ Read Replica（读扩展）高可用 + 读扩展
💡 因果一致性：Neo4j 集群保证「如果你读了某个结果，之后再读一定能看到导致它的那些写」——通过书签（bookmark）机制传递，适合大多数业务，不像强一致那样牺牲性能。

🎯 常见问法与答题要点

Q：图数据库和关系库最本质的区别是什么？

A：关系是一等公民 vs 靠外键推导。关系库里「A 认识 B」是一条存在关联表或外键列里的记录，查多跳要反复 JOIN + 索引查找，代价随深度指数增长。Neo4j 里关系是一条独立存储的记录，两端直接存着对方节点的物理指针（无索引邻接），遍历就是顺指针走，代价只与局部连接数有关，与全图大小无关。

Q：什么是 index-free adjacency？

A：「无索引邻接」。指节点在存储层就直接持有相邻关系的物理指针，从一个节点走到它的邻居是一次 O(1) 的指针跳转，不需要查任何索引。这带来一个关键性质：查询代价 = f(你要探索的局部)，而不是 f(全库数据量)。所以库从 100 万节点涨到 1 亿节点，同样的「查某人 3 度人脉」耗时几乎不变。

Q：Neo4j 支持事务吗？

A：支持完整 ACID。写入要么全成功要么全回滚，读不会看到未提交的中间态。集群模式下默认是因果一致性（通过 bookmark 保证「读你所写」和因果序），而不是全局强一致——这是在性能与一致性之间的务实选择。

Q：什么时候不该用图数据库？

A：三条判断：①只查一跳——关系库加索引更快更简单；②重度聚合分析（全表 SUM/GROUP BY）——图数据库不做列式扫描，比 OLAP 引擎慢得多；③数据高度同构且关系简单——用关系库或文档库即可。另外 Neo4j 不适合存大文本/BLOB，大属性会拖慢遍历。

Q：Neo4j 的写入性能怎么样？

A：单次写入比关系库慢一些（要维护节点记录、关系记录、双向指针与索引），但完全够用——单实例通常每秒几万条简单写入。批量导入一定要用 neo4j-admin import（离线批量导入，比逐条 CREATE 快几十倍）或 LOAD CSV 配合 CALL {} IN TRANSACTIONS 分批提交。

Q：图数据库能做聚合统计吗？

A：能做，但不是它的强项。Cypher 支持 count/sum/avg/collect 等聚合，但它逐记录遍历而不是列式批量扫描，所以全库级统计（如「统计所有用户的平均年龄」）远慢于 OLAP 引擎。实践做法：关系遍历用 Neo4j，批量统计导出到 Spark/数仓。

Q：Neo4j 集群是怎么保证一致的？

A：Enterprise 的因果集群：Core Server 之间用 Raft 共识协议复制写操作（保证多数派确认），Read Replica 异步追赶提供读扩展。一致性模型是因果一致——客户端写完后拿到一个 bookmark，下次读带上它，集群保证这次读一定能看到那次写的结果。
