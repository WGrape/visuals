微服务拆分：粒度、边界与分布式单体

拆分的难点不在「拆多小」，而在「边界画在哪」。画错了，微服务只会把函数调用变成网络调用，代价更高、问题更多。

为什么拆分粒度是个伪问题

很多人问「一个微服务应该多少行代码」，这个问题没有答案。真正决定拆分质量的是边界是否落在变化频率不同的地方：如果两个模块总是一起改、一起发布、一起扩容，把它们拆开就只会凭空增加网络跳转、分布式事务和排障难度。

领域驱动设计给出的答案是限界上下文（Bounded Context）：同一个词在不同上下文里含义不同，就是天然的边界。电商系统里的「商品」，在商品上下文里是名称/价格/库存，在订单上下文里是订单行的一个快照，在物流上下文里是重量/体积。强行统一成一个模型，会让每个改动都牵扯所有方。

六个拆分信号

信号含义典型处理
变更频率不同有的模块天天改，有的半年不动一次分开部署，避免高频改动反复触发全量回归与发布
扩容曲线不同有的吃 CPU，有的吃内存或 IO分开部署，各自按自己的瓶颈扩容
可用性要求不同支付不能挂，报表挂一会儿无所谓分开部署，隔离故障域与资源竞争
数据所有权不同两块数据各有各的主人和一致性要求分开存储，禁止跨服务直接读对方库
合规/安全边界不同某块数据受更严格的审计或地域约束独立部署与存储，便于隔离审计
团队结构不同康威定律：系统结构会复制组织结构按团队职责划分，减少跨团队协调成本

用一次拆分推演看代价

列出候选边界

把「订单」和「库存」分开看似合理：订单关心状态流转，库存关心数量扣减，变更频率和一致性要求都不一样。

谁拥有哪份数据

订单表归订单服务，库存数量归库存服务。订单里只存下单时的商品快照，不存实时库存——实时库存是库存服务的私有数据。

原来是本地事务，现在怎么办

下单要扣库存，跨了两个服务。本地事务失效，必须改成 Saga（下单 → 扣库存 → 失败则补偿取消订单）或 TCC。这一步的复杂度是拆分最大的隐性成本。

拆开到底解决了什么

如果答案是「订单和库存现在可以独立发布和扩容」，那拆分成立；如果答案是「好像也没什么区别」，那就不该拆。

分布式单体：最常见的失败形态

分布式单体（Distributed Monolith）指服务在部署上拆开了，但在逻辑上仍然紧耦合：改一个功能要同时改五个服务、五服务必须按序发布、任何一个挂掉整体不可用。它同时具备单体和微服务的所有缺点。

症状根因修正方向
改一个功能要同步发布多个服务边界画错了，把强耦合的东西拆开了重新审视边界，把总是同变的部分合回去
服务之间互相查对方的数据库没有守住数据所有权改为 API 调用或事件通知，数据库是私有实现
发布窗口必须全体到场接口没有版本兼容能力建立契约测试与向后兼容的演进规则
一个服务挂了全站不可用缺熔断降级，强依赖没做弱化处理区分强弱依赖，弱依赖可降级

先单体、后拆分的实践路径

对大多数团队，从结构良好的单体开始是更稳的选择。在单体内部按模块划清边界（清晰的包结构、模块间只通过接口通信），等到某个边界确实出现了不同的变更频率或扩容需求，再把它拆出去。

这样做的好处是：边界的位置在实践中被验证过，而不是在设计阶段靠猜。等到真的要拆时，模块间的接口已经存在，拆分只是把进程内调用换成网络调用。反过来「先拆后想」的团队，往往在半年后开始痛苦地合并服务。

边界与误区

拆分不是目标而是手段。如果单体运行良好、团队规模不大、发布频率够用，保持单体完全合理。微服务的收益来自规模：足够多的团队、足够高的发布频率、足够明确的独立扩容需求。达不到这个规模，微服务带来的运维成本会超过收益。

拆分的依据与常见错误

核心依据：按业务能力拆，而不是按技术分层拆。

错误拆法问题正确做法
按技术层拆（controller/service/dao 各自成服务）一次业务请求跨多个服务，毫无收益按业务能力拆
按数据表的 CRUD 拆服务无业务语义，只是分布式 DAO围绕业务实体与用例
拆得太细（纳米服务）网络调用开销 > 业务收益，调试地狱先粗后细，按痛点拆
共享数据库服务间通过库耦合，等于没拆每个服务独立数据源

判断边界是否合理的三个信号：① 两个功能是否总是同时变更（是 → 不该拆开）；② 是否需要不同的伸缩策略或 SLA（是 → 该拆开）；③ 拆开后是否需要跨服务的分布式事务（是 → 边界可能划错了）。

粒度：量化参考

规模指标过细合理过粗
单个服务代码量< 1 千行5 千~5 万行> 20 万行
团队规模/服务1 人管 5 个1 个服务 2 人可维护10 人挤 1 个
单服务接口数< 5 个10~50 个> 200 个
调用链深度> 8 跳3~5 跳1 跳（单体）
单服务数据表< 2 张5~20 张> 50 张

调用链深度是最容易被忽略的指标：一次请求跨 8 个服务，假设单跳可用性 99.9%，整体可用性就是 0.999^8 ≈ 99.2%——已经明显劣化。而且 P99 延迟会累加。所以拆分时有意识地控制链路深度，比单纯追求服务数量小更重要。

拆分后的数据归属与事务

场景方案一致性复杂度
同服务内多表本地事务强一致低
跨服务，可接受延迟Saga（补偿）/ 事件驱动最终一致中
跨服务，必须同步成功TCC / 2PC强一致高，慎用
仅通知，无需回滚Outbox + 消息队列最终一致低，推荐

Outbox 实现

-- Outbox 模式：把“改数据”与“发消息”变成一个本地事务
BEGIN;
  UPDATE orders SET status = 'PAID' WHERE id = 123;
  INSERT INTO outbox (aggregate_id, event_type, payload)
  VALUES (123, 'OrderPaid', '{"order_id":123,"amount":99.0}');
COMMIT;
-- 独立的投递进程轮询 outbox，发到 MQ 后标记已发送
-- 关键价值：<strong>不会出现“库改了但消息没发”或"消息发了但库没改"</strong>

-- 消费侧必须幂等：用 event_id 去重
INSERT INTO processed_events (event_id) VALUES ('evt_abc');
-- 若唯一键冲突 → 已处理过，直接跳过

为什么 Outbox 优于「先写库再发 MQ」：后者两步不是原子的，任何一步失败都会不一致，而且失败后无法自动补偿（消息发出去就收不回）。Outbox 把消息先当数据落库，再由投递进程保证“至少一次”发出，把分布式事务问题降级为本地事务 + 幂等消费，复杂度低一个数量级。

自检 Q&A

Q：单体什么时候该拆？

A：看痛点而不是看规模。四个明确信号——① 团队协作冲突：多个团队改同一份代码，发布互相阻塞；② 伸缩需求分化：某个模块需要独立扩容（如支付峰值是其他的 10 倍）；③ 可用性要求不同：某个模块挂了不能影响主流程；④ 技术栈需求不同：某模块需要特殊语言或存储。没有这些痛点就拆，只会把函数调用变成网络调用，纯亏。

Q：拆完后服务间循环依赖怎么办？

A：循环依赖说明边界划错了，不要试图用技术手段绕过。三种重构——① 提取公共能力成第三个服务；② 改成事件驱动：A 不直接调 B，而是发事件，B 订阅后自行处理（把同步依赖变成异步通知）；③ 合并：如果两个服务耦合如此紧密，很可能本来就该是一个。其中 ② 最常用，也最能降低耦合。

Q：如何避免“分布式单体”？

A：分布式单体指物理上拆了、逻辑上仍强耦合——每次变更要同时改多个服务并同步发布，比单体还糟。三个检查点——① 是否共享数据库（是 → 一定是分布式单体）；② 是否频繁跨服务同步调用（是 → 边界有问题）；③ 是否必须同时发布（是 → 说明拆错了）。根治办法是重新划边界，让每个服务能独立开发、独立部署、独立伸缩。

Q：服务间调用用同步还是异步？

A：判据是调用方是否需要立即知道结果。需要（如扣款前校验余额）→ 同步；不需要（如发通知、更新推荐）→ 异步。异步的好处是削峰 + 解耦 + 可用性隔离（下游挂了不影响主流程）。实践中的常见错误是把所有调用都做成同步，导致可用性是各服务可用性的乘积——把非关键路径改成异步，能显著提升整体可用性。

自检

为什么「按数据表拆服务」经常是错的？

数据表只是模型的存储形式，不代表业务边界。按表拆会得到一堆只做 CRUD 的贫血服务，业务逻辑散落在调用方，任何一次业务改动都要协调多个服务。正确的顺序是先识别业务边界，再决定数据归谁。
