①为什么索引类型这么多：一个不可能三角

向量检索要在内存占用、召回率、查询延迟三者之间取舍，没有一种索引能同时做到最优。Milvus 把各种 ANN 实现封装成可切换的 index_type，让你按业务阶段选：小数据量暴力就够，千万级上图索引，十亿级靠量化 + 磁盘。

三角形的三个顶点分别是召回率、内存效率、低延迟；每种索引落在这个平面的不同位置。

②向量索引全景

索引路线内存开销适用规模核心参数
FLAT暴力扫描原始向量大小百万级以内 / 需要 100% 召回的基线无
IVF_FLAT倒排 + 原始向量≈ 原始大小千万级，内存够nlist / nprobe
IVF_SQ8倒排 + 标量量化≈ 原始的 1/4千万级，内存吃紧nlist / nprobe
IVF_PQ倒排 + 乘积量化可压到 1/10 以下亿级nlist/nprobe/m/nbits
HNSW分层可导航小世界图原始 + 图边（较贵）千万级，要求低延迟高召回M/efConstruction/ef
HNSW_SQ / HNSW_PQ / HNSW_PRQ图 + 量化显著低于 HNSW图索引但内存受限同 HNSW + 量化参数
SCANN倒排 + 各向异性量化低亿级，追求吞吐nlist/nprobe/reorder_k
DISKANN基于磁盘的 Vamana 图极低（数据在 SSD）十亿级，内存远小于数据图参数 + 缓存大小
AUTOINDEX系统代选按数据量自动不想调参时的默认选择无
GPU_CAGRA / GPU_IVF_*GPU 图 / 倒排显存高 QPS、可接受 GPU 成本同对应 CPU 索引
索引是 Segment 级的：Milvus 对每个 Segment 单独建索引，而不是对整张表建一个索引。所以 Segment 越小越碎，索引越建越不划算——这也是compaction 重要的原因。

③三条技术路线在做什么

IVF 靠“少看”，HNSW 靠“少跳”，量化靠“少存”。理解这一句，就理解了索引选型的全部逻辑：数据量大到扫不动就分桶，分桶还不够就压向量，延迟敏感就用图。

④度量方式：别选错相似度

metric_type含义方向什么时候用
L2欧氏距离越小越近向量未经归一化、关心绝对距离
IP内积越大越近已归一化的向量；稀疏向量（BM25）只能用 IP
COSINE余弦相似度越大越近文本 Embedding 的默认选择，等价于归一化后的 IP
HAMMING / JACCARD位向量距离 / 相似系数HAMMING 越小越近、JACCARD 越大越近BINARY_VECTOR 指纹去重
最常见的错：用 COSINE 训练/生成的向量却用 L2 检索，或反过来；以及把 score 的方向搞反做排序。L2 越小越好，IP/COSINE 越大越好——做阈值截断时务必区分。

⑤标量索引：过滤性能的另一半

向量检索的耗时常常不在向量上，而在标量过滤。Milvus 为每个标量字段单独建索引，过滤时先算出一个 bitset（命中掩码），再传给 ANN 过程做过滤。

INVERTED

倒排索引，2.x 的主力。等值、in、范围、前缀匹配都支持，字符串/数值/JSON path 都能用。默认首选。

BITMAP

低基数字段（性别、状态、是否删除）的位图，压缩率高、按位运算快。

STL_SORT

排序索引，适合数值型范围查询（时间区间、价格区间）。

Trie

前缀树，适合字符串前缀匹配；新版本多由 INVERTED 取代。

标量索引不会自动创建。只建了向量索引而忘了给过滤字段建索引，是“明明只筛 1% 数据却很慢”的头号原因。

⑥内存 / 召回 / 延迟横向对比

以 1000 万条 768 维 float32 向量为例，原始向量约 30 GB：

索引内存量级典型召回典型延迟一句话
FLAT~30 GB100%高（随规模线性）基线，用来测其他索引的召回
IVF_FLAT~30 GB95%–99%中内存没省，靠分桶换速度
IVF_SQ8~8 GB90%–98%中性价比高的省内存方案
IVF_PQ~2–3 GB80%–95%中极省内存，召回损失明显
HNSW~36–45 GB97%–99%+低性能最好、也最吃内存
HNSW_PQ~10–15 GB90%–97%低要图的延迟又要省内存的折中
DISKANN~数 GB 内存 + SSD90%–98%中高十亿级唯一现实选项

表中数量级为经验估算，实际取决于维度、参数与版本；请以自己数据集的压测为准。

⑦选型决策树

数据量 < 100 万，或要求 100% 召回？
        └─ 是 → FLAT（先跑通，别过早优化）
百万 ~ 千万，内存充足、延迟敏感？
        └─ 是 → HNSW（M=16~32，ef 按召回目标调）
千万 ~ 亿级，内存是瓶颈？
        ├─ 能接受召回损失 → IVF_PQ / SCANN / HNSW_PQ
        └─ 召回要求高     → IVF_SQ8 / HNSW_SQ
亿级 ~ 十亿级，数据远大于内存？
        └─ DISKANN（SSD 承载主体，内存只放图与缓存）
有 GPU 且 QPS 要求极高？
        └─ GPU_CAGRA / GPU_IVF_PQ
不想调参 / 原型阶段？
        └─ AUTOINDEX
选定索引后真正的功夫在调参：见索引参数调优。通用原理见向量索引图解。
本页数值（上限、默认值）随版本演进，给出的是 Milvus 2.x 常见取值，落地前请用你部署版本的官方文档核对。
Milvus 的索引体系 = 路线（暴力 / 倒排 / 图） × 量化（无 / SQ8 / PQ / PRQ） × 介质（内存 / 磁盘 / GPU）。选型时先按数据量和内存定路线，再按召回目标定量化和参数，最后用压测闭环。
