词法分析（scanner）

字符流切成 token

扫描器跳过空白注释，把关键字、标识符、运算符、字面量识别成 token 流，供解析器消费。

// 源码: x := 1 + 2
// token 流: IDENT(x) DEFINE(:=) INT(1) ADD(+) INT(2)
语法分析（parser）

token 组成 AST

解析器按语法规则把 token 流构造成抽象语法树（AST），表达式、语句、声明都成了树节点。

// x := 1 + 2 的 AST 片段
AssignStmt {
  Name: Ident("x")
  Value: BinaryExpr {
    Op: ADD
    L: BasicLit(1)  R: BasicLit(2)
  }
}
类型检查

语义校验 + 类型推导

遍历 AST 检查类型是否匹配、标识符是否声明、隐式转换（如无类型常量）如何处理，并把推导出的类型写回 AST 节点。

Go 是强类型，类型检查能在编译期拦下大量错误；同时它还处理「无类型常量」的延迟定型（如 1 在浮点上下文变 float）。
前端的产出

交给中端后端

经过类型检查的 AST 被转换成更规整的中间表示（SSA 前身），进入中端优化与后端机器码生成（见下一篇）。

调试入口

go 编译中间产物可用 go build -gcflags=-S 看汇编，或用 go/parser、go/types 自己写静态分析工具。

从源码到机器码：编译器的六个阶段

go build 背后是一条完整的编译流水线。理解它，才能看懂「为什么这个变量逃逸了」「为什么这个函数没被内联」这类问题。

编译流水线：前三步解析，中端优化，后端落地
AST抽象语法树，语法层面的结构。
SSA静态单赋值形式，优化的主要载体。
中端与 CPU 架构无关，优化规则最多。
后端架构特化、寄存器分配、出机器码。

三个最值得关心的优化

函数内联

把小函数体直接展开，省掉调用开销，并为后续优化创造条件。

# 看内联决策（含被拒绝的原因） go build -gcflags='-m -m' ./... 2>&1 | grep inline # can inline foo → 可内联 # cannot inline bar: function too complex → 太复杂 # 含 for/range/select/recover 等通常不支持内联

内联常常是连锁反应：内联后常量可折叠、分支可消除、变量不再逃逸，收益远不止省一次调用。

逃逸分析

判断变量能否留在栈上，直接决定 GC 压力。

go build -gcflags='-m -m' ./... 2>&1 | grep escape # moved to heap: x → 逃逸 # x does not escape → 留在栈上

常见逃逸原因：返回指针、闭包外泄、装箱为 interface、大小在运行时才确定。

边界检查消除

编译器能证明下标安全时，会去掉运行时越界检查。

// 编译器能证明 i 在范围内 → 去掉检查 s := make([]int, 10) for i := range s { s[i] = i // 无额外比较指令 } // 无法证明 → 每次访问都要判断 func get(s []int, i int) int { return s[i] }

可用 -gcflags=-d=ssa/check_bce/debug=1 查看哪些检查被保留。

怎么观察编译产物

-gcflags=-m打印优化决策：内联、逃逸
-gcflags=-S打印汇编（含源码行号对照）
-gcflags=-N -l关闭优化与内联，便于调试
GOSSAFUNC导出 SSA 各阶段的 HTML 图
go tool objdump反汇编已编译的二进制
go build -a忽略缓存强制重编，用于对照
# 最常用：看某个函数到底生成了什么 go build -gcflags='-S' ./... 2>&1 | grep -A 30 '"".add' # 生成 SSA 可视化（会在当前目录产出 ssa.html） GOSSAFUNC=add go build ./... open ssa.html

深入自检

中端优化和后端优化有什么区别？

中端与 CPU 架构无关，规则通用（内联、逃逸、死代码消除、常量折叠），是绝大多数优化的所在地；后端负责把 SSA 降级为具体指令、分配寄存器、处理调用约定。同一份中端结果可以喂给 amd64、arm64 等多个后端。

为什么改了一行代码性能掉了很多？

常见原因是意外阻断了内联或造成逃逸。例如把参数改成 interface{} 导致装箱逃逸、在函数里加了 defer 或 recover 使函数无法内联、把固定长度改成动态长度导致切片逃逸到堆。用 -gcflags='-m -m' 对比改动前后的输出最直观。

编译慢是不是优化开太多？

不完全是。Go 编译慢的主要来源常是依赖解析与包编译的串行部分，以及重复构建大型依赖。可用 go build 的缓存、并行度与依赖裁剪来改善，而不是盲目关闭优化。

GOSSAFUNC 的图看不懂怎么办？

不必逐块看懂。看三个点就够：起始阶段有多少块、优化后块数是否减少、关键的值是否被常量折叠或消除。块数显著减少通常意味着优化生效。

编译期能做的事，为什么还要运行时检查？

因为很多信息只有运行时才知道：切片真实长度、接口的实际类型、并发下的数据竞争。编译器的目标是「能证明就消除，不能证明就保留检查」，这也是 Go 安全性的来源。

编译器调试命令

# 看内联决策（最有用的编译器调试手段）
go build -gcflags="-m" ./... 2>&1 | grep -v 'can not inline' | head -30
# 输出示例：
#   ./main.go:10:6: can inline add with cost 4 as: func(int, int) int { return a + b }
#   ./main.go:15:20: inlining call to add
#   ./main.go:20:15: leaking param: x          ← 逃逸到堆
#   ./main.go:20:15: moved to heap: buf        ← 分配到堆

# 看生成的汇编（验证优化效果）
go tool compile -S main.go | head -40
go build -gcflags="-S" ./...
# 关键：看到大量 CALL 且没有内联标记 → 内联没生效

# 看 SSA 的每个 pass（进阶，看优化过程）
GOSSAFUNC=add go build ./...
# 会生成 ssa.html，用浏览器打开可看到每一步 SSA 的变化

# 看编译计划与依赖
go build -x ./...              # 打印所有执行的命令
go list -deps ./... | wc -l    # 依赖包数量

# 编译耗时分析
go build -a -x ./... 2>&1 | ts -i    # 需要 moreutils 的 ts

逃逸分析与性能实践

  • 逃逸的五大诱因：① 返回局部变量的指针；② 变量被闭包捕获且闭包逃逸；③ 赋给 interface（装箱，如 fmt.Println(x)）；④ 切片/map 动态扩容；⑤ 对象太大（超过栈容量，常见阈值约 64 KB）。
  • 栈分配 vs 堆分配的成本差：栈分配就是移动一下栈指针（1 条指令），函数返回自动回收；堆分配要走内存分配器（几十 ns）+ 后续 GC（标记、清扫、可能的移动）。热路径上每秒百万次分配会显著拖慢程序。
  • 优化手段：① 传值而不是传指针（小结构体）；② 复用对象（sync.Pool、预分配 slice 容量）；③ 避免不必要的接口装箱；④ 用 strings.Builder 代替字符串拼接。
  • 但不要过度优化：逃逸分析只是启发式，且 Go 的分配器很快。先 profile 再优化——用 go test -benchmem 看 allocs/op，只优化真正的热点。
  • 边界检查消除（BCE）：编译器能证明下标安全时会去掉 bounds check。写法上给编译器提示（如先判断 if i < len(s) 再多次访问 s[i]）能显著提速。用 -gcflags="-d=ssa/check_bce/debug=1" 看哪些检查没被消除。
  • 编译速度：Go 以编译快著称（设计目标之一），百万行项目全量编译通常 10–60 s。主要开销在依赖分析与链接，源码编译本身很快。这也是 Go 开发体验好的重要原因。
怎么知道我的变量逃逸到堆了？

go build -gcflags="-m" ./...，看输出里的 moved to heap 和 leaking param。这是最直接的方法。另外 go test -benchmem 的 allocs/op 也能间接反映——如果某个操作本不该分配却显示有分配，多半是逃逸了。

内联一定好吗？

通常是（省掉函数调用开销、让更多优化成为可能），但会让二进制变大（代码膨胀），可能降低指令缓存命中率。Go 用 80 的 cost budget 平衡这个取舍。极端情况可以 -gcflags="-l" 关闭内联对比测试。
