一句话总结：列存能压到行存的几分之一，靠的不是某一个神奇算法，而是同列数据类型一致、值域相近、按列选编码这三件事叠加。实际存储链路通常是「类型编码 → 通用压缩」两级：编码负责把值变短变规整（还能直接在编码数据上做谓词下推），通用压缩负责最后的字节级去重。

01为什么列存天生好压

🧱 同列同类型

一列里全是同一种类型，不需要为每行存类型信息，也不必做跨类型的通用编码。

🔁 重复度高

维度列（省份、状态、品类）基数很低，几十万行里可能只有几十个不同值。

📈 相邻值相近

时间戳、自增 ID、按时间写入的指标，相邻行的差值很小——差分后就是小整数。

🎯 可以按列选算法

行存只能整块压；列存每一列可以单独挑最合适的编码，这是最大的自由度。

要点：压缩率不是目标本身。压缩要兼顾解压速度——分析查询每次都要把数据读出来解压，压得太狠反而拖慢查询。

02两级链路：编码 + 通用压缩

同一列数据经过「编码 → 位打包 → 通用压缩」逐级变小
层级做什么代表算法能否在压缩态上直接查询
编码（Encoding）按数据类型与分布重新表示值RLE、字典、Delta、位打包、Gorilla多数可以（这是它比通用压缩更值钱的地方）
通用压缩（Compression）字节流的通用冗余消除LZ4、ZSTD、Snappy、Gzip不能，必须先解压

顺序很重要：先编码再通用压缩。编码后的数据更规整（小整数、长游程），通用压缩才能拿到更高的压缩率；反过来做基本没效果。

要点：判断一个列该用什么编码，先问三个问题：基数高不高？相邻值差得远不远？值域能不能用少量 bit 表示？

03六种常见编码与适用数据

编码原理最适合的数据典型压缩效果不适用
RLE（游程）把连续重复值存成「值 + 次数」低基数列、已按该列排序的列排序好的低基数列可达数十倍高基数且无序（游程长度≈1，反而膨胀）
字典编码值 → 整数 id，另存字典表低基数字符串（状态、省份、品类）长字符串替换成 1~2 字节，非常显著高基数列（字典本身会膨胀，退化为近似无压缩）
Delta（差分）存相邻值的差，再配合位打包单调递增的时间戳、自增 ID时间戳从 8 字节降到 1~2 字节很常见随机无序的大整数（差值仍然很大）
DoubleDelta差分的差分等间隔的时间序列（每 10 秒一个点）等间隔序列可压到接近常数采集间隔抖动的数据
位打包（Bit-packing）按实际位宽而非类型宽度存值域小的整数（如 0~100 的状态码）INT64 存 0~15 可省掉 75%~90%值域接近类型上限
Gorilla / XOR相邻浮点做异或，只存变化位浮点型的监控指标（缓慢变化）监控类时序压缩比可达 10 倍量级剧烈跳变的浮点
-- ClickHouse：在建表时按列指定编码链（先编码，后通用压缩）
CREATE TABLE events (
  ts        DateTime CODEC(DoubleDelta, ZSTD),      -- 等间隔时间戳：二次差分再 ZSTD
  uid       UInt64   CODEC(Delta, ZSTD),            -- 递增 ID：差分再 ZSTD
  status    LowCardinality(String),                 -- 低基数字符串：字典化（自动）
  province  LowCardinality(String) CODEC(ZSTD),
  amount    Decimal(18,2) CODEC(ZSTD),
  raw_json  String   CODEC(LZ4)                     -- 高基数列：只做快速通用压缩
) ENGINE = MergeTree
ORDER BY (province, ts);                            -- 排序键直接影响 RLE 效果

-- 查看各列实际压缩后大小（这是调编码的依据，不要凭感觉）
SELECT
  column,
  formatReadableSize(sum(data_compressed_bytes))   AS compressed,
  formatReadableSize(sum(data_uncompressed_bytes)) AS uncompressed,
  round(sum(data_uncompressed_bytes) / sum(data_compressed_bytes), 2) AS ratio
FROM system.columns_data   -- 实际系统表名以版本文档为准
GROUP BY column ORDER BY compressed DESC;
要点：ORDER BY 的第一列如果是低基数列，RLE 的游程会非常长，压缩率能拉开数量级差距。这是「排序键设计」和「压缩」之间最重要的联系。

04压缩与查询性能的取舍

选择优点代价什么时候选
LZ4解压极快，CPU 开销小压缩率中等默认首选，热数据、查询频繁的表
ZSTD压缩率高，可分级（level 越高越慢越小）解压稍慢，压缩时 CPU 更高冷数据、归档、磁盘成本敏感的表
更高压缩 level再省一点空间压缩耗时明显上升，写入变慢只有确认磁盘是瓶颈时才调
不压缩最快空间占用大极热的小表、或已由上层缓存挡住的场景
  • 解压是有成本的：一次全表聚合要把几亿行的列读出来解压，压缩算法慢会直接拖长查询。
  • 压缩率影响 IO：分析型查询多数是 IO 瓶颈，压得小 → 读得少 → 反而更快。这就是「压缩能提速」的来源。
  • 平衡点通常是 LZ4 或 ZSTD 的低 level：空间省不少，解压还够快。
  • 编码几乎总是白赚：它既省空间，又能让谓词在编码态上直接跳过整块数据。

05排障：压缩率突然变差的原因

  • 换了排序键：原本按低基数列排序形成的长游程被打散，RLE 效果骤降——这是最常见的「压缩率退化」原因。
  • 低基数判断错了：以为基数低、实际有几百万不同值，字典编码退化成「字典比数据还大」。
  • 类型用大了：用 UInt64 存 0~100 的状态码，没有位打包就白白浪费 7 个字节。
  • 数据分布变了：业务上线新枚举值、ID 换成 UUID，都会让原有编码失效，需要重新评估。
  • 写入批次太小：小批次写入产生的块更小，压缩的「参考窗口」变小，压缩率天然差一些。
  • JSON/长文本进了列存：这类高熵数据和列存压缩不兼容，应考虑存成对象存储 + 外表，或只保留需要的字段。
-- 排查路线：先看每列实际压缩比，再决定改编码还是改排序键
-- 1) 找出「压缩率最差且占空间最大」的列（优先治理这两项都高的）
SELECT name, type,
       formatReadableSize(sum(data_compressed_bytes)) AS comp,
       round(sum(data_uncompressed_bytes)/greatest(sum(data_compressed_bytes),1), 2) AS ratio
FROM system.columns
WHERE table = 'events'
GROUP BY name, type
ORDER BY sum(data_compressed_bytes) DESC
LIMIT 20;

-- 2) 确认基数：高基数列不该用字典/LowCardinality
SELECT uniqExact(status)   AS status_card FROM events;   -- 几千以内适合字典
SELECT uniqExact(raw_json) AS json_card   FROM events;   -- 极高的别做字典

-- 3) 改编码需要重写数据（ALTER ... MODIFY COLUMN ... CODEC 会触发该列重写）
ALTER TABLE events MODIFY COLUMN amount CODEC(Delta, ZSTD);

06常见疑问

问：压缩率是不是越高越好？

不是。压缩率要与解压速度一起看。分析查询每次都要解压，如果为了多省 20% 空间让查询慢 30%，对交互式分析是亏的。热数据优先选快的算法。

问：为什么我按文档配了编码，压缩率还是不行？

多半是排序键的问题。RLE 类编码完全依赖「相同值挨在一起」，如果排序键的第一个字段是高基数列，相同值根本不会相邻。先看排序键，再调编码。

问：字典编码的「低基数」到底多低算低？

经验上几千到几万个不同值以内效果明显；到几十万就要实测——判断标准是字典表本身的大小能不能被「重复节省的空间」覆盖。用上面那条 uniqExact 实测最准。

问：能不能对已有的大表改编码？

能，但会触发该列的数据重写，代价是一次较大的 IO 与磁盘临时空间。建议在低峰做，并先在一个分区或一张小表上验证收益。
