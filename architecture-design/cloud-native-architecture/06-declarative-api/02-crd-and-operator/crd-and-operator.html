CRD 与 Operator：把运维知识写进控制器

Kubernetes 的内置资源不够用时，用 CRD 定义自己的资源，再用控制器让声明变成现实——这就是 Operator 模式。

两个概念的分工

概念是什么解决什么
CRD（CustomResourceDefinition）一种扩展机制，让你定义新的资源类型让集群认识「Database」「Backup」这类领域对象
Controller（控制器）一段持续运行的调和逻辑让 CRD 里声明的期望状态变成实际状态
OperatorCRD + 控制器 + 领域运维知识把「怎么正确运维一个 MySQL 集群」编码成自动化

CRD 只是数据结构，控制器才是行为。只创建 CRD 而不写控制器，资源能被存进集群但什么都不会发生。这是初学者最常见的误解。

调和循环：控制器到底在做什么

监听资源变化

控制器 watch 自己关心的资源类型，变化事件进入工作队列。

期望状态 vs 实际状态

读出资源里声明的期望状态（spec），再查询真实世界的实际状态（哪些 Pod 在跑、数据是否同步）。

消除差异

如果实际状态偏离期望，执行操作把它拉回来：创建缺失的 Pod、触发备份、调整配置。

持续循环，永不终止

调和不是一次性的。即使此刻一致，下一秒也可能因为节点故障而偏离，所以控制器必须持续运行。

调和必须是幂等的：同一个输入重复执行多次，结果应该一致。这是控制器设计的核心约束——事件可能重复投递、操作可能部分失败，控制器随时可能在任意一步被打断重来。

声明式 API 的价值在哪

命令式是「做这个动作」，声明式是「我要这个结果」。声明式的优势在 Kubernetes 这类环境里被放大：

场景命令式的麻烦声明式的处理
节点宕机导致 Pod 丢失需要有人或脚本发现并重新执行创建命令控制器发现实际状态偏离，自动补齐
并发操作多个操作互相覆盖，需要加锁都只是修改期望状态，控制器统一调和
恢复与迁移要记录做过哪些步骤只要期望状态还在，控制器就能重建
审计与回滚动作历史难以追溯期望状态本身就是声明，可版本化、可对比

Operator 适合封装什么

Operator 的价值在于把有状态的、需要领域知识的运维动作自动化。判断标准：如果这件事需要「懂这个软件的人」才能做对，它就适合写成 Operator。

适合不适合
主从切换与故障恢复纯无状态的部署编排（Deployment 就够了）
备份与时间点恢复一次性任务（用 Job）
版本升级与数据迁移简单的配置分发（用 ConfigMap）
扩缩容时的数据重平衡只需要定时触发的操作（用 CronJob）

写一个 Operator 的成本不低：要处理状态机、失败重试、并发安全、版本升级。先用内置资源能不能满足需求，再考虑 CRD。过度使用 CRD 会让集群里堆满只有作者能理解的资源类型。

常见陷阱

陷阱表现规避
控制器不幂等重复执行导致重复创建资源所有写操作前先查是否存在，用确定性名称
在调和里做长时间阻塞操作阻塞整个控制器，其他资源得不到处理长操作拆分到多次调和，用状态字段记录进度
忽略 spec 之外的字段别人手动改了实际资源，控制器不纠正调和时对比完整状态，不只是检查存在性
没有处理删除资源删了，外部资源泄漏使用 finalizer 在删除前清理外部资源
状态字段乱用把不该持久化的信息写进 statusstatus 只存观测结果，不存期望状态

边界与误区

Operator 不是「更自动化的 Helm」。如果只是把一组 YAML 打包安装，Helm / Kustomize 更合适。Operator 的独特价值是运行时的持续调和——它不只是安装，而是长期确保状态正确。如果不需要运行时调和，就不该写 Operator。

CRD 与 Operator 的关系

概念是什么作用
CRD自定义资源定义，扩展 K8s API让你能 kubectl get foos
CRCRD 的实例一条具体的自定义资源
Controller监听资源变化、调谐实际状态让实际状态趋近期望状态
OperatorCRD + Controller + 领域知识把运维专家的脑子写成代码

核心是“调谐循环”（Reconcile Loop）：不是“执行一次”，而是不断比较期望状态与实际状态，有差异就修正。这个幂等的循环是 K8s 声明式 API 的灵魂——重复执行不会出错，中断后能自动续上。

调谐循环

# 调谐函数的标准骨架（controller-runtime）
func (r *FooReconciler) Reconcile(ctx context.Context,
        req ctrl.Request) (ctrl.Result, error) {
    // 1) 读取期望状态（CR）
    var foo myv1.Foo
    if err := r.Get(ctx, req.NamespacedName, &foo); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)  // 已删除则忽略
    }

    // 2) 检查实际状态
    var deploy appsv1.Deployment
    err := r.Get(ctx, types.NamespacedName{
        Name: foo.Name, Namespace: foo.Namespace}, &deploy)

    // 3) 有差异就修正（<strong>保证幂等</strong>）
    if apierrors.IsNotFound(err) {
        return ctrl.Result{}, r.createDeployment(ctx, &foo)
    }
    // 4) 需要重试时返回 RequeueAfter，而不是自己 sleep
    if foo.Spec.Replicas != *deploy.Spec.Replicas {
        deploy.Spec.Replicas = &foo.Spec.Replicas
        return ctrl.Result{}, r.Update(ctx, &deploy)
    }
    return ctrl.Result{}, nil        // 已一致，什么都不做
}

调谐函数必须幂等且不阻塞：① 不能假设“只执行一次”，任何一步都可能被重放；② 不要在 Reconcile 里做长耗时操作，需要等待就返回 RequeueAfter 让框架稍后重新入队。

CRD 定义要点

CRD 定义

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: foos.example.com
spec:
  group: example.com
  names:
    kind: Foo
    listKind: FooList
    plural: foos
    singular: foo
  scope: Namespaced              # 或 Cluster（集群级）
  versions:
  - name: v1
    served: true                 # 该版本是否提供 API
    storage: true                # <strong>只能有一个版本为 storage</strong>
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            properties:
              replicas:
                type: integer
                minimum: 1        # <strong>一定要写校验</strong>，否则错值也能存
                maximum: 100
                default: 3
          status:                 # 子资源，存实际状态
            type: object
    subresources:
      status: {}                 # 开启后 status 与 spec 分开更新
    additionalPrinterColumns:    # kubectl get 时显示的列
    - name: Replicas
      type: integer
      jsonPath: .spec.replicas
要点说明常见错误
必须写 schema 校验否则任何值都能存进去不写校验，错数据要等到 controller 才报错
status 子资源分离期望与实际状态不开启时更新 status 会覆盖 spec
storage 版本唯一只有一个版本负责持久化多个 storage 版本会被拒绝
版本转换多版本时用 conversion webhook只改 storage 版本会让老客户端读到错数据

并发控制与性能相关配置

配置项默认值说明
MaxConcurrentReconciles1单个 controller 的并发调谐数，高吞吐可调到 5~10
SyncPeriod10 小时全量重新同步周期，兜底防漏事件
RateLimiter指数退避 5ms~1000s失败重试的限速，防止雪崩
Cache开启controller 读资源走本地缓存，不直接打 API Server

为什么 SyncPeriod 要设 10 小时：事件驱动可能丢事件（网络抖动、进程重启），定期全量对账是兜底。设为 0 会关闭全量同步——不推荐，但特大集群为了减轻 API Server 压力可以调长到 24 小时。

  • 必须给 controller 配 RBAC：默认 ServiceAccount 无任何权限，忘记配会一直报 forbidden。
  • 用 OwnerReference 建立级联关系：让 CR 删除时其创建的 Deployment/Service 自动被 GC 回收。
  • 避免 controller 之间互相触发死循环：A 改 B、B 改 A，会无限调谐。用 generation 变化判断而非任意更新。

自检 Q&A

Q：Operator 和 Helm Chart 有什么区别？

A：Helm 是“安装时”的模板渲染，Operator 是“运行期间”的持续管理。Helm 装完就结束了，之后应用的扩缩容、故障恢复、版本升级都要人来做；Operator 把这些运维动作写进调谐循环，持续运行。判据：只需要部署一次且之后不用管 → Helm；需要持续运维（备份、故障转移、滚动升级）→ Operator。两者也常结合：用 Helm 部署 Operator，再由 Operator 管理应用。

Q：CRD 删不掉怎么办？

A：通常是被 finalizer 卡住。CR 上有 finalizer 时，删除请求只会设置 deletionTimestamp，等 controller 完成清理并移除 finalizer 后才真正删除。若 controller 已卸载或出 bug，finalizer 永远不会被移除 → 资源卡在 Terminating。处理办法：kubectl patch foo xxx -p '{"metadata":{"finalizers":[]}}' --type=merge 手工移除。这是生产环境最常见的 CRD 问题，所以写 controller 时务必保证清理逻辑健壮，且 finalizer 的移除要在清理成功后执行。

Q：调谐函数里该不该直接更新 status？

A：要更新，但要用正确的方式。开启 status 子资源后，必须用 r.Status().Update() 而不是 r.Update()——后者会连带覆盖 spec，可能把用户刚提交的新期望值冲掉。另外 status 应记录可观测的实际状态（Ready/Progressing/Failed + 原因 + 观察到的 generation），让用户 kubectl get 就能看到进展，这是 K8s 的约定。

Q：Operator 挂了会怎样？

A：已运行的业务不受影响，但失去自动运维能力。这是声明式架构的重要优点——Operator 管理的 Pod/Service 是真实存在的资源，Operator 挂掉只是“没人再调谐了”，业务继续跑。风险在于：此期间的变更不会被自动修正（如节点故障后不会自动重建），且可能因缺失 finalizer 处理导致资源卡在删除中。所以 Operator 自身也要做高可用（多副本 + leader election，controller-runtime 默认支持）。

自检

为什么要强调控制器必须幂等？

调和循环会被反复触发，而且可能在任何一步失败重试。如果控制器逻辑依赖「这是第一次执行」，重复执行就会产生重复资源或错误状态。幂等性让控制器可以从任意中断点安全恢复。
