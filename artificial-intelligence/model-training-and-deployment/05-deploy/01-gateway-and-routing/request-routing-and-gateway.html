Serving · 入口层

请求入口与路由

所有流量都要先经过这里：鉴权、限流、协议转换，然后被挑一个后端副本送进去。在普通 Web 服务里这一步简单到可以轮询；在 LLM 服务里，它决定了你的首字延迟是 300 毫秒还是 3 秒，也决定了缓存能不能命中。这一页讲的就是「选谁」这件事。

01入口层到底在做什么

网关（API Gateway / 边缘节点）不是「转发器」，它至少承担四类职责，前两类是通用能力，后两类是 LLM 场景特有的：

通用身份与配额

API Key / JWT 校验、租户识别、QPS 与 token 配额、账单归集。没有这一步，一个用户就能把整个集群打满。

通用协议与格式

把 HTTP 请求转成流式 SSE 或 WebSocket；统一 OpenAI 兼容格式；请求/响应改写（补 system prompt、脱敏、裁剪超长输入）。

LLM 专属路由决策

选哪个副本、哪个模型、哪个池子。这是本页的重点，也是最容易被做成「轮询就完事」的地方。

LLM 专属流式治理

生成中不能重试（重试会重复计费与重复输出）；要处理客户端断开、超时、背压，以及「已经开始输出后就不能切后端」的约束。

最容易被忽略的一条：LLM 请求的成本后验性。普通请求进来时就知道工作量；LLM 请求进来时你不知道它会生成 20 个 token 还是 2000 个。所以配额与限流不能只看 QPS，还要看并发中请求数 + 在飞 token 数，否则一条长请求能顶掉几十条短请求的资源。

02入口链路全景

03L4 与 L7 的分工

职责要分清，否则会绕远路：

层次看什么在 LLM 链路里的位置典型问题
L4（传输层）IP / 端口 / TCP 连接最外层，多机房与可用区入口连接级均衡，看不见请求内容，无法做模型路由
L7（应用层）HTTP 路径 / Header / Body网关或业务侧，做模型、租户、长度路由解析成本高；流式响应要注意缓冲，别把 SSE 攒成整包再发
通用负载均衡的算法与健康检查（加权轮询、最小连接、一致性哈希、探活与摘流）属于基础设施通识，这里不重复写，请见 L4/L7 负载均衡与健康检查 与 SLB 负载均衡架构。本页只讲 LLM 场景里不一样的那部分。

一个必须点明的前提差异：从 LLM 的视角看，后端副本之间是不等价的。它们不只是「同样的代码跑在不同机器上」，而是各自持有不同的 KV Cache、不同的显存余量、不同的批处理进度。所以传统 LB 的「平均分配」在这里往往是负优化。

04为什么不能轮询

假设两个副本，轮询会把流量对半劈开。但真实情况常是：

  • 副本 A 刚接了 3 条 30k 上下文的请求，KV Cache 占了 85%，再进来就要抢占（preemption）甚至拒绝；
  • 副本 B 空闲，KV 只用了 20%。

轮询的结果是：一半请求被送到快撑爆的 A，排队、抢占、TTFT 暴涨；而 B 在空转。集群整体利用率看着不错，用户体感却很差。

正确的做法是按负载信号加权，而不是按连接数平均。这一点和第 9 节要讲的「负载信号选什么」是同一件事的两面。

05前缀亲和路由：本页最值钱的一招

回忆一下推理的两个阶段：prefill 把整段 prompt 算一遍得到 KV Cache，decode 再逐个生成。而真实流量里，请求的前缀往往高度重复——同一段 system prompt、同一套 few-shot 示例、同一份 RAG 上下文、同一个用户的对话历史。

如果同一个前缀的请求恰好落到同一个副本，那段 KV 已经在显存里了，整段 prefill 可以跳过；落到别的副本，就要从头再算一遍。

实践要点：

  • 哈希的对象是「前缀 token 序列」，不是整段 prompt。因为 KV 是按前缀累积的，只要开头一致就能复用。
  • 要设「亲和上限」。纯亲和会把公共前缀的请求全压到一个副本上；通常做法是「亲和优先 + 超过阈值就退化为按负载选」。
  • 前提是副本开了 prefix caching。vLLM 用 --enable-prefix-caching；不开启的话亲和零收益。
  • 收益上界就是公共前缀的长度占比。如果每个请求前缀都不同（比如完全自由输入），别指望它。

06会话粘性：多轮对话别乱跳

多轮对话是天然的强前缀：第 3 轮请求的前缀 = 前 2 轮全部内容。如果第 3 轮被路由到另一个副本，前两轮的 KV 就白算了，而且还得把历史重新塞进去 prefill。

所以多轮场景通常按 session_id 做会话粘性（sticky session），让同一会话尽量落同一副本。三个注意点：

  1. 粘性不是永久的。副本挂掉、缩容、发布都会打断，所以客户端要能接受「重算一次」。
  2. 粘性会放大不均衡。热门会话会把某个副本压满，需要超时降级为普通路由。
  3. 长会话最终会超出上下文窗口，那时候前缀必然变化（滚动窗口/摘要压缩），亲和的收益也随之重置。
一个实用组合：session_id 一致性哈希 + 前缀哈希兜底 + 队列深度阈值。前两者管命中率，第三者管不均衡。

07模型分级路由：最大的成本杠杆

不是所有请求都值得用最大的模型。前缀「帮我改写这句话」和「设计一个分布式事务方案」的难度差了几个数量级，但用同一个模型处理时，成本完全一样。

典型收益：让 60~80% 的简单请求走小模型，整体成本能降一半以上。

分级方式怎么判断优点风险
规则路由按接口、业务线、功能标签可控、可解释、零额外成本粒度粗，同一接口内难度差异大
长度/关键词启发prompt 长度、是否含代码块、是否需要工具实现便宜误判率高
分类器路由小分类模型判断难度/意图效果好，可训练多一跳延迟与维护成本
级联（cascade）小模型先答，置信度低再升级质量可控失败时付两次钱、两次延迟
必须做质量兜底。分级路由的失败模式不是「报错」，而是「悄悄变差」——用户拿到一个看起来合理但更浅的答案。所以要有：小模型置信度低时自动升级、按业务线监控质量指标、以及一个随时可用的「强制走大模型」开关。成本与质量的完整治理清单见 推理指标与成本。

08按长度与能力分池

这是最容易被忽略、踩坑后最痛的一条：一条超长请求可以拖垮一整批。

  • 显存维度：128k 上下文的 KV Cache 可能是 8k 的 16 倍。它进池的那一刻，会挤掉几十条短请求的容量。
  • 时间维度：prefill 是算力密集的，一条 128k 的 prefill 会让同一批里所有请求的 TTFT 一起变长（除非用了 chunked prefill）。
  • 公平性维度：延迟敏感的小请求被一条离线大任务拖住，用户体验断崖式下跌。

所以常见做法是按 prompt 长度 分池（如 <8k / 8k~32k / >32k），或者按优先级分池（在线交互 / 后台批量），各自独立扩容、独立 SLO。物理隔离比在同一个队列里做优先级调度更可靠。

09负载信号选什么

信号可用性说明
CPU 利用率不可用GPU 服务的瓶颈几乎从不在 CPU；用它做均衡等于随机
GPU 利用率一般「高」可能是健康的高（批跑满了），也可能是病态的高（全在重算前缀）
队列深度 / 等待请求数首选直接反映「还有多少人在等」，与 TTFT 强相关
KV Cache 占用率首选决定还能不能接新请求；>85% 就该停止派长请求给它
在飞请求的剩余 token 预估进阶能预判「这个副本还要忙多久」，比瞬间指标更稳
近期 TTFT 分位数进阶结果导向，能自动反映你没建模到的瓶颈

工程上常见的组合是：队列深度优先 → KV 占用做硬闸门 → 前缀亲和做加权 → 记录失败时熔断降权。指标本身的定义见 推理指标与成本。

10保护：限流、排队、超时、降级

入口层是唯一还能「优雅拒绝」的地方。过了这一层，请求已经占着 GPU 显存，再想拒绝就只能靠中断生成。

限流

按租户/接口限 QPS；更要按 并发中请求数 与 在飞 token 数 限，因为单请求工作量差异巨大。

排队 vs 拒绝

队列有界。满了就快速失败（带 Retry-After），别让请求在队列里等到超时——那样既花了时间又拿不到结果。

超时策略

分成 TTFT 超时 与 总时长超时。首字超时通常设几百毫秒到数秒；总时长要覆盖最长合理输出。

降级

依次：走小模型 → 命中缓存直接返回 → 缩短最大输出长度 → 降低检索条数 → 返回兜底文案。要预先定义顺序。

流式生成的三个特殊约束：① 已经开始输出就不能重试，否则用户会看到重复内容、上报也会重复计费；② 客户端断开要立刻取消后端生成，否则 GPU 会为没人看的 token 白烧钱；③ 重试必须幂等（固定 request_id，避免同一请求被服务两次）。
# 伪配置：入口层的保护顺序
route:
  guards:
    - auth             # 鉴权失败直接 401，不占任何资源
    - quota            # 超配额 429 + Retry-After
    - inflight_limit   # 并发中请求数超限 → 排队或快速失败
    - ttft_timeout     # 首字超时（如 3s）→ 取消后端生成
    - total_timeout    # 总时长（如 120s）
  degrade_order:
    - small_model_first
    - cache_only
    - reduce_max_tokens
    - fixed_fallback_text

11灰度与多版本路由

模型上线比 Web 服务灰度更难，因为输出不可二进制比较。可行的做法：

  • 按流量比例切（1% → 5% → 50% → 100%），但要让同一用户固定落同一版本，否则体验抖动。
  • 影子流量（shadow）：把生产请求复制一份给新模型，只记结果不返回，用来做离线对比。注意这会双倍消耗 GPU，仅适合小比例。
  • 保留回滚开关：路由层要有「一键回旧版本」，且旧副本要预热常驻——临时拉起旧版本可能要好几分钟，那时候故障已经扩大了。
  • 按租户/内测白名单先放量，比纯随机流量更容易收集有效反馈。

13速记卡

问题一句话答案
入口层做几件事？鉴权配额、协议转换、路由决策、流式治理
为什么不能轮询？副本不等价：显存余量、KV 占用、缓存内容都不同
路由最值钱的一招？前缀亲和：相同前缀落同一副本，跳过整段 prefill
亲和的风险？公共前缀会把负载压向少数副本，要设亲和上限
最大的成本杠杆？模型分级路由：60~80% 简单请求走小模型，成本降一半以上
什么请求最该隔离？超长上下文与离线批量任务，一条就能拖垮一整批
负载信号看什么？队列深度 + KV 占用率，不看 CPU
流式生成的特殊约束？输出开始后不可重试；断开要取消后端；重试要幂等
