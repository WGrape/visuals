调解码参数的正确姿势是「只动一个、其余保持默认」。大多数人调不好，是因为同时改了温度、top_p、top_k、重复惩罚，最后不知道是哪个起了作用。

01每个参数单独在干什么

参数作用点变大意味着默认值（常见）
temperature除以 logits 后再 softmax，改变分布陡峭程度分布变平 → 低概率词也有机会，输出更发散1.0（很多 API 默认）
top_p（核采样）按累积概率动态截断候选集候选变多 → 多样性上升1.0（即不截断）
top_k只保留概率最高的 k 个（固定数量）候选变多 → 多样性上升通常不启用（0 或 50）
repetition_penalty对已出现的 token 降权更强地避免复读，但可能损伤连贯性1.0（不惩罚）
frequency / presence penalty按出现次数惩罚 / 只要出现过就惩罚前者抑制高频词，后者鼓励换话题0
max_tokens生成长度上限不控制质量，只控制成本与截断风险由服务端决定
# 温度的实际效果（同一句 prompt，直觉对比）
temperature = 0.0   # 贪心解码：每次取概率最高的词，结果确定但可能单调
temperature = 0.3   # 轻微随机：适合事实问答、代码、抽取
temperature = 0.7   # 常见默认：适合对话、摘要
temperature = 1.0   # 明显发散：适合头脑风暴、创意写作
temperature > 1.5   # 容易胡言乱语，几乎不用于生产

# 关键性质：temperature=0 时，top_p / top_k 都不再起作用
# 因为分布已经退化成「只有一个候选」
要点：temperature 与 top_p 是串联生效的：先按温度改变分布形状，再在变形后的分布上做截断。所以「高温 + 低 top_p」和「低温 + 高 top_p」会得到完全不同的效果，不能只看单个参数。

02按场景直接抄的参数组合

场景temperaturetop_p其他理由

# OpenAI 风格 API 的推荐写法（只动必要的参数）
resp = client.chat.completions.create(
    model='gpt-4o-mini',
    messages=messages,
    temperature=0.2,        # 确定性任务
    top_p=1.0,              # 不额外截断（避免与温度叠加导致不可预期）
    max_tokens=800,
    stop=['\n\n---'],       # 明确停止条件，比靠模型自觉更稳
    seed=42,                # 需要复现时固定 seed（尽力而为，不保证完全一致）
)

# 需要多样性时：不要只调温度，而是采样多次再选
resps = client.chat.completions.create(
    model='gpt-4o-mini', messages=messages, n=5, temperature=0.9)
best = max(resps.choices, key=lambda c: score(c.message.content))
要点：一条实用经验：需要「多样性」时，采样多次再挑选，比把温度调高更有效。高温只是让每次输出更随机，而 n>1 + 挑选是在多个完整方案里选最好的。

03五个常见错误

  • 同时调 temperature 和 top_p：两者叠加后效果难以预测，出问题时无法归因。官方建议二选一。
  • 想要确定性却只把温度调到 0.1：仍有随机性。真正确定要设 0，并配合结构化输出约束。
  • 用 repetition_penalty 掩盖提示词问题：复读往往是因为上下文太短或示例太少，惩罚参数只是把症状压下去。
  • 把 max_tokens 当成「回答长度」：它是上限，模型可能提前停止（遇到 stop 或 EOS）。要控制长度应在提示词里说明。
  • 以为 seed 能保证完全复现：浮点非确定性、批处理调度都会让结果有细微差异，seed 只能做到「基本稳定」。
# 排查「输出不稳定」的标准流程
1. 先把 temperature 设为 0，看结果是否稳定
   - 不稳定 → 问题不在解码，而在提示词/上下文/工具返回
   - 稳定   → 确实是解码随机性，再逐步调高温度
2. 固定 seed 与 max_tokens，排除长度截断导致的差异
3. 用 20~50 条样本跑一遍，统计「结果一致率」而不是只看单条

04常见疑问

问：top_p 和 top_k 该用哪个？

优先用 top_p。因为它是自适应的：分布很陡时自然只留几个候选，很平时自动放开。top_k 是固定数量，在分布很陡时会保留一堆概率极低的词（引入噪声），在分布很平时又可能截掉有价值的长尾。

问：为什么我把温度调到 0，两次结果还是不一样？

三个原因：① 服务端批处理导致的浮点非确定性（同样的输入在不同 batch 下结果可能有微小差异）；② 模型或权重更新；③ 采样仍在 tie-break 时随机（概率相同的词之间）。要做到严格可复现，需要固定 seed + 固定版本 + 关闭批处理，实际很少有服务能保证。

问：重复惩罚设多少合适？

通常 1.05 ~ 1.2。超过 1.3 会明显损伤语句通顺度，出现用词怪异。如果必须设到 1.3 以上才能避免复读，说明问题在提示词或训练，应该从根上解决。

问：beam search 什么时候用？

在翻译、摘要这类有明确最优解且输出较短的任务上有效。但它会让输出趋于「安全平淡」，开放式生成反而变差，而且推理成本翻倍。现代对话场景基本不用 beam search。

参数叠加效果与跨服务差异

解码参数是串联生效：先改分布形状，再截掉长尾，最后才采样

同一个参数在不同服务上的默认值和实现可能不同，切换模型时一定要重新验证，不能假设「参数名一样，行为就一样」。

差异点常见情况影响应对
temperature 默认值多数服务默认 1.0，部分为 0.7换服务后输出风格突变显式传参，不依赖默认
top_p 是否生效部分服务 top_p 与 temperature 可同时设叠加后效果难预测二选一，另一个保持默认
temperature 上限多数上限 2.0，少数 1.0超过会被截断或报错检查服务端限制
penalty 量纲OpenAI 是 -2~2 的加成，其他多为 1~2 的乘数同数值效果完全不同按文档确认量纲
seed 支持部分服务支持且尽力而为不完全可复现不要用于强一致场景
stop 序列多数支持字符串或数组不设时可能输出多余内容显式设置停止条件

换模型前的参数探测

# 迁移模型时的参数核对清单（改模型前后各跑一次对比）
def probe(client, model):
    outs = []
    for t in (0.0, 0.3, 0.7, 1.0):
        r = client.chat.completions.create(
            model=model,
            messages=[{'role': 'user', 'content': '用一句话解释什么是幂等'}],
            temperature=t, top_p=1.0, max_tokens=200, seed=7)
        outs.append((t, r.choices[0].message.content))
    return outs

# 对比维度：
#   1. 温度为 0 时两次结果是否一致（判断是否真确定性）
#   2. 温度升高后输出是否明显变发散（判断量纲是否一致）
#   3. 是否出现截断（判断 max_tokens 与 stop 的行为）

调参排查逐条核对：

  • 一次只改一个参数，其余保持默认，否则无法归因。
  • 需要确定性就设 temperature=0，不要设 0.01 这种「看起来很小」的值。
  • temperature 与 top_p 二选一，同时调会让效果不可控。
  • 换模型/换服务必须重新验证参数，默认值与量纲可能不同。
  • 输出不稳定先查提示词：把温度设为 0 后仍不稳定，说明问题不在解码。
  • 需要多样性用 n>1 采样再挑选，比单纯调高温度更有效。
  • 重复惩罚不超过 1.2，再高会损伤语句通顺度。
  • 用 20~50 条样本统计一致率，不要凭单条输出下结论。
