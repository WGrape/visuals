虚拟化：一台机器如何运行多套系统

从 Hypervisor、硬件辅助到内存与设备虚拟化。

学完能解释什么

  • 说清宿主机、虚拟机与 Hypervisor 的边界
  • 理解 CPU、内存和 IO 为什么需要不同的虚拟化机制
  • 区分虚拟机与容器共享内核的模型

逐步看机制

为每个 Guest 提供看似独占的机器

虚拟机拥有自己的内核、虚拟 CPU、虚拟内存和虚拟设备；物理资源由宿主机与 Hypervisor 分配。

虚拟化的基本契约

Hypervisor（虚拟机监控器）把物理机器抽象成多台可隔离的虚拟机器。Guest 可安装自己的操作系统；宿主机或 Hypervisor 持有物理 CPU、内存和设备的最终控制权。所谓“隔离”依赖特权级、地址转换和设备访问控制，不能只靠进程名称或文件夹划分。

三条资源路径

资源Guest 看到实际由谁约束
CPU一个或多个 vCPUHypervisor 把 vCPU 调度到物理核；特权指令触发 VM exit 或硬件辅助处理
内存连续的 Guest 物理内存二级地址转换 EPT/NPT 限定实际物理页，并维护映射与 TLB
设备虚拟磁盘、网卡设备模拟、virtio 队列或受控的设备直通

VM exit 有成本，但不能笼统说“虚拟机每条指令都被软件模拟”：普通指令大多直接在物理 CPU 上运行。

容器为什么不是轻量虚拟机

容器通常以 namespaces 隔离资源视图、以 cgroups 约束用量，与宿主机共享内核；虚拟机运行独立 Guest 内核。容器启动更快、镜像更轻，但隔离与可运行的内核类型不同。需要不同内核或更强的内核边界时优先评估 VM；需要快速交付进程环境时再评估容器。

排查时分清“Guest 中看见的负载”和宿主机的资源争用：vCPU 被超额分配会出现等待，即使 Guest 里的应用没有修改也可能变慢。

自检

VM 中的普通加法指令必须先被 Hypervisor 模拟吗？

通常不需要；普通指令直接执行。特权操作、地址映射和设备访问才需要受控处理。

虚拟化的本质：把「一份硬件」变成「多个看起来独占的副本」

虚拟化的核心难题是特权指令：Guest OS 以为自己在直接操作硬件，但它运行在非特权态，执行敏感指令必须被 Hypervisor 捕获并模拟（陷入-模拟）。现代 CPU 提供硬件辅助（VT-x / AMD-V），让这个过程又快又完整。

核心技术细节

① CPU 虚拟化

  • 经典做法：敏感指令陷入 Hypervisor，由它模拟执行（trap-and-emulate）。
  • 硬件辅助：VT-x 引入根/非根模式，Guest 直接在 CPU 上跑，只有真正敏感的操作才退出（VM-Exit）。
  • 开销来源：VM-Exit 次数（IO 密集时很多）。
  • 调优：减少 exits、启用 APICv、合理绑定 vCPU 与 NUMA。

② 内存虚拟化

  • Guest 有「虚拟物理地址」，还要再转成真实物理地址，两层转换。
  • 早期用影子页表（软件维护，开销大）；现代用 EPT/NPT（硬件二级页表）。
  • 优化：大页（HugePage）减少 TLB 未命中；KSM 合并相同页（有 CPU 代价）。
  • balloon 与内存超卖：要小心 OOM 与抖动。

③ I/O 虚拟化

  • 全模拟（如模拟 e1000 网卡）：兼容最好，性能最差。
  • 半虚拟化 virtio：Guest 知道自己在虚拟环境，用高效队列（vring）通信。
  • 设备直通（PCI passthrough / SR-IOV）：接近原生性能，但失去迁移能力。
  • vhost-net / vhost-user：把数据面挪到内核或用户态，减少切换。

④ 容器隔离的机制

  • Namespace：隔离视图（pid/mnt/net/uts/ipc/user）。
  • Cgroup：限制资源（cpu/memory/io/pids）。
  • Capabilities、seccomp、AppArmor/SELinux：限制权限。
  • 注意：容器共享宿主内核，内核漏洞可逃逸 —— 这就是安全容器存在的理由。

深入自检

Type 1 和 Type 2 虚拟化有什么区别？

Type 1（裸金属）直接运行在硬件上，如 KVM、Xen、ESXi，性能与隔离更好，用于数据中心；Type 2 运行在宿主操作系统之上，如 VirtualBox、VMware Workstation，便于桌面使用但多一层开销。注意 KVM 虽常被视为 Type 1，但它以内核模块形式存在，是一种「宿主型 + 裸金属特性」的混合实现。

容器和虚拟机哪个更安全？

虚拟机更强：它有独立内核，Guest 逃逸需要先突破 Hypervisor，难度高。容器共享宿主内核，内核漏洞、配置不当（如特权容器、挂载 docker.sock）都可能导致逃逸。运行不可信代码应选 VM 或安全容器（Kata/Firecracker/gVisor）。

为什么云函数（Serverless）偏爱微 VM？

因为它们要同时满足：多租户强隔离（不可信代码）、极快启动（冷启动要毫秒级）、高密度（成本）。Firecracker 这类微 VM 裁掉了大量设备与功能，只保留最小内核路径，在保留 VM 级隔离的同时把启动压到百毫秒级、内存开销降到几 MB。

虚拟机的性能损失主要在哪？

主要是三处：VM-Exit（特权操作与中断处理）、内存虚拟化（两级页表与 TLB 压力）、I/O 路径（模拟设备或额外的 virtio 队列拷贝）。计算密集型任务损失很小（1-3%）；I/O 密集与系统调用密集的任务损失可能很大，需要 virtio、vhost、SR-IOV 等手段优化。

超卖（overcommit）有什么风险？

CPU 超卖通常安全（大多数 VM 不是满载），但内存超卖很危险：当所有 VM 同时要用内存时，宿主会开始 swap 甚至 OOM Kill，表现为整体雪崩。所以生产环境内存超卖要谨慎，并配合监控、气球驱动（balloon）与 QoS 分级。

容器里看到的时间、PID、CPU 是真的吗？

部分是「视图」：PID、挂载点、网络、主机名都是 Namespace 隔离出来的独立视图；但 CPU 时间、内存统计若没做 cgroup 感知，应用可能读到宿主的值（如旧的 JVM/Go runtime 会误判可用 CPU 数）。现代运行时与 /sys/fs/cgroup 感知已大幅改善，但部署时仍要注意设置 CPU/内存 limit 与 JVM 参数。
