先记住这条主线

Redis 对外是 5 种数据类型，但每种类型在内部会根据数据大小自动切换不同的底层编码。这个设计的目的只有一个：小数据用紧凑结构省内存，大数据用高效结构保性能，而且切换全自动，对用户透明。

编码只升不降。一旦因为数据量变大而升级成 hashtable/skiplist，即使之后把元素删光也不会退回 listpack。所以「先灌一批大数据再删掉」的 key 会一直占着大结构的内存。

String 的三种编码

  • int：值是整数（且在 long 范围内）时，直接把数字存在指针位，连字符串对象都不分配。
  • embstr：≤ 44 字节的短字符串。SDS 头和字符数据一次分配、连续内存，只需一次 malloc/free，缓存友好。
  • raw：更长的字符串。SDS 头和字符数据分两次分配。
SDS（Simple Dynamic String）是 Redis 自己实现的字符串，相比 C 原生字符串多了三个关键能力：O(1) 获取长度（存了 len）、二进制安全（可以存任意字节，包括 \0）、杜绝缓冲区溢出（自动扩容）。

List 为什么是 Quicklist

历史上有过两种结构，各有硬伤：

  • ziplist（连续内存）：省内存，但插入要搬移内存，元素多了代价爆炸。
  • linkedlist（双向链表）：插入快，但每个元素要存前后指针（16 字节），元素多时指针开销惊人，且内存不连续。

Quicklist 是两者的折中：外层是双向链表，链表的每个节点内部是一个 listpack。

选型决策：什么场景用哪个

基数统计（UV）HyperLogLog12KB 固定内存，误差 0.81%

一条实用经验：不要把所有数据都塞进一个大 String（JSON 序列化）。如果经常只改其中一个字段，用 Hash 更划算——可以只读写单个 field，且小 Hash 用 listpack 编码，内存可能比 JSON 字符串还小。
性能红线：① 避免 KEYS *（用 SCAN）；② 不要在未知大小的容器上直接 HGETALL/SMEMBERS/LRANGE 0 -1（先看 HLEN/SCARD/LLEN）；③ 大 key 用 UNLINK 删除，不用 DEL。

🎯 面试问答

Q：Redis 有哪几种基础数据类型？
A：五种：String（字符串/整数/浮点，最大 512MB）、Hash（field-value 映射）、List（有序可重复）、Set（无序去重，支持交并差）、ZSet（去重且每个元素带 score 排序）。此外还有基于它们实现的高级类型：Bitmap（String）、HyperLogLog（String）、GEO（ZSet）、Stream（独立类型）。
Q：同一个 Redis 类型为什么会有不同底层编码？
A：因为小数据和大数据的优化目标不同。小数据用紧凑连续结构（listpack / intset / embstr）——省掉指针开销，内存可能省好几倍，虽然操作是 O(N) 但 N 很小无所谓；大数据用高效索引结构（hashtable / skiplist / raw）——保证 O(1) 或 O(log N)。切换由 Redis 根据阈值自动完成，对用户完全透明，用 OBJECT ENCODING key 可以查看当前编码。
Q：List 的底层是什么？为什么不用纯链表？
A：Redis 3.2 起是 Quicklist：外层双向链表，每个链表节点内部是一个紧凑的 listpack。纯链表每个元素要存前后两个指针（16 字节开销），元素多了内存浪费严重；纯 ziplist 虽然省内存但插入要搬移整块内存。Quicklist 折中：节点内连续存储省内存，节点间靠指针连接保证插入效率，只需拆/合单个节点。
Q：ZSet 底层是什么？
A：大数据量时是 跳表（skiplist）+ 哈希表（dict）双结构：跳表按 score 排序，支撑 ZRANGE / ZRANK / ZRANGEBYSCORE；哈希表做 member → score 映射，让 ZSCORE 是 O(1)。两者共享同一份 member/score 内存（只是指针引用），不会真的存两份。小 ZSet（≤128 个元素且 member ≤64 字节）则用 listpack 紧凑存储。
Q：什么时候用 Hash 而不是 String 存 JSON？
A：经常只读写对象的部分字段时，用 Hash 更划算：可以 HGET/HSET 单个 field，不必「取整个 JSON → 反序列化 → 改一个字段 → 序列化 → 写回」；而且小 Hash 用 listpack 编码，内存往往比序列化后的 JSON 字符串还小。反之，如果每次都是整体读写、字段很少变动、或者需要嵌套结构，用 String 存 JSON 更简单直接。
Q：Redis 字符串为什么不用 C 原生字符串？
A：因为 Redis 自研的 SDS 解决了 C 字符串的三个硬伤：① O(1) 获取长度（SDS 头部存了 len，C 字符串要 strlen 遍历）；② 二进制安全（可以存任意字节包括 \0，C 字符串遇到 \0 就截断）；③ 杜绝缓冲区溢出（SDS 修改时自动检查并扩容）。此外 SDS 还有空间预分配和惰性释放，减少内存重分配次数。
