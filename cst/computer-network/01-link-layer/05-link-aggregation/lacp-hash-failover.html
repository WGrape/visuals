LACP 链路聚合：两根 1G 网线能让单个下载达到 2G 吗

沿交换机与服务器的两条物理链路解释聚合协商、流量哈希和故障切换。

聚合的是链路集合

服务器有两块 1 Gbps 网卡，分别接交换机两个端口。若配置 LACP，双方可协商把它们组成一个逻辑聚合接口，向上层表现为一条链路，用于提高多流总容量和链路冗余。聚合不是把一条普通 TCP 连接的每个包随机分摊到两根线；常见实现会按源/目的 MAC、IP、端口等字段计算哈希，使同一流落在同一成员口，以减少包乱序。

因此两条 1G 成员链路通常可让多条合适分布的流合计接近 2G，但一条流可能仍被单成员的 1G 速率限制。实际值还受协议开销、哈希碰撞、网卡、CPU 和交换机容量影响。不能仅看聚合接口显示“2G”就向用户承诺单连接一定 2G。

LACP 如何协商成员

LACP 通过控制报文让两端确认哪些物理口属于同一聚合组，检查端口参数和对端系统信息。成员口需要在速率、双工、VLAN 允许列表等方面满足设备要求；有些设备会把不合格成员置于非转发或独立状态。静态聚合不依赖 LACP 协商，配置错误时更容易形成单向或环路风险，生产环境应按设备设计选择并验证。

如果服务器只配置了聚合，而交换机把两个端口当独立普通端口，可能出现 MAC 地址漂移、流量黑洞甚至二层环路。排障先看两端聚合状态、活动成员数、伙伴系统 ID 和每个物理口计数，而不是只看操作系统逻辑接口 UP。

逐步推演

协商成员

服务器和交换机用 LACP 确认两个物理口可加入。

选择出口

对连接字段做哈希，把一条流固定到成员口。

聚合多流

多条流可分布到两口，提高总吞吐。

成员故障

坏口退出，流量重映射到剩余成员。

一次流量分配算例

有四条长连接，每条需要 600 Mbps。若哈希正好把两条放链路 A、两条放链路 B，每根线需求 1.2 Gbps，实际会被 1G 限制，合计也达不到 2.4G；若四条都哈希到 A，B 可能空闲而 A 拥塞。聚合总带宽是“足够多分布良好的流”下的潜在容量，不能确保任意流组合均衡。可以查看每成员实际字节数验证哈希效果。

换哈希字段可能改善某种业务，例如大量客户端连同一服务器端口时加入源端口更有区分度。但不同设备支持的字段和方向不同；一端发送哈希与另一端发送哈希可独立决定，不能只改服务器一侧就期待两个方向都均衡。

失效时发生什么

链路 A 物理断开后，LACP 或接口状态应把它从活动成员移除，原本映射到 A 的流量重新分配到 B。B 只有 1G 容量，若原来总流量接近 2G，切换成功仍会发生拥塞和延迟上升。冗余保证有路径，不保证故障后容量不降。业务验收要同时测连通性与故障后的峰值负载。

成员口恢复时，哈希映射可能再次变化，部分流短时间乱序或丢包。应用重试、TCP 重传和队列抖动应纳入切换时延统计。若上联交换机本身故障，两根线都接它时仍一起中断；跨设备聚合需要交换机支持相应多机箱技术，并按特定拓扑配置。

与 STP 的关系

LACP 把多个物理端口作为一个逻辑连接交给上层网络，STP 则在更大二层拓扑中防止环路。它们可同时存在，但 LACP 不能代替整个网络的 STP，STP 也不会自动把两条独立链路的带宽相加。若把一端聚合、一端不聚合，STP 观察到的拓扑可能与预期不同。设计时画清逻辑链路和物理成员，不要只画两根线。

VLAN Trunk 可以承载在聚合接口上，需保证成员配置一致。某 VLAN 只在一根成员口允许，会产生哈希相关的间歇性故障：某些流通、某些流不通。排查要按成员口检查 VLAN 和错误计数。

验收方法

先在两端核对聚合组、活动成员、协议状态和 VLAN 配置；用多条并发流测试总吞吐，再用单条流验证其上限。分别断开 A 和 B，检查持续连通、恢复时间与故障后延迟。若总吞吐低，查看每根线利用率和哈希字段；若单流低于 1G，再查网卡、CPU、磁盘与对端限速。

运行中修改聚合算法或成员口会改变现有连接分布，应先在非高峰演练并有回滚配置。对关键业务，记录故障后只有一根线时的实际可用容量，而非只在正常双链路状态报漂亮数字。

链路聚合模式与哈希策略

模式（Linux bonding）是否需要交换机配合说明
802.3ad（LACP，mode 4）需要交换机开 LACP推荐：动态协商，能检测链路故障
balance-xor（mode 2）需要静态聚合按哈希选链路，不检测链路状态
active-backup（mode 1）不需要主备，只有一条活跃，故障切换
balance-rr（mode 0）需要轮询发包，可能乱序，很少用
balance-tlb / alb（mode 5/6）不需要按负载/ARP 自适应，出向负载均衡
哈希策略（xmit_hash_policy）依据效果
layer2源/目的 MAC同一对设备只有一条链路（最差）
layer2+3MAC + IP同一对 IP 只有一条链路
layer3+4（默认推荐）IP + 端口不同连接可分摊到不同链路，最常用
encap2+3 / encap3+4隧道内层VXLAN/GRE 环境用（否则所有隧道流量走同一条）

关键认知：LACP 是按流（flow）哈希的，单条 TCP 连接永远只走一条物理链路。所以 2×10 G 的聚合，单个大文件传输最多只能跑 10 G；只有多条并发连接才能跑满 20 G。这是“聚合了但速度没变”的头号原因。

LACP 配置与验证

# 创建 LACP 绑定
ip link add bond0 type bond mode 802.3ad xmit_hash_policy layer3+4
ip link set eth0 master bond0
ip link set eth1 master bond0
ip link set bond0 up

# 查看状态（关键文件）
cat /proc/net/bonding/bond0
# 看：Bonding Mode、MII Status、各 Slave 的 MII Status 与 Aggregator ID
#     Aggregator ID 一致 = 同一个 LACP 聚合组（不一致说明协商失败）

# LACP 速率（fast=1s / slow=30s）
cat /sys/class/net/bond0/bonding/lacp_rate

# 交换机侧（Cisco）
# interface Port-channel1
#   ...
# interface Gi0/1
#   channel-group 1 mode active      # active=主动发 LACP，passive=被动

# 看流量分布（验证是否均衡）
cat /proc/net/dev | grep -E 'eth0|eth1|bond0'

故障切换与常见坑

  • LACP 速率：slow（默认，30 s 发一次 LACPDU） vs fast（1 s）。要快速检测链路故障用 fast，两端必须一致。
  • Aggregator ID 不一致 = 协商失败：常见原因是两端模式不匹配（一端 active 一端没开 LACP）、或成员口配置不一致（速率/双工/VLAN/trunk 放行不同）。交换机通常要求成员口配置完全相同才会聚合。
  • 哈希不均：如果流量集中在少数几个 IP:端口（如一条大流量数据库连接），layer3+4 也可能全压在一条链路上。解决：换哈希策略、增加流的数量、或改用更高带宽单链路。
  • 虚拟化/隧道场景：VXLAN/GRE 把所有内层流封装成同样的外层五元组 → 标准哈希全走一条链路。必须用 encap3+4 按内层哈希，或在叠加层做负载均衡。
  • 排障顺序：① cat /proc/net/bonding/bond0 看各 slave 是否 up 且 Aggregator ID 一致；② 看交换机侧 Port-channel 是否形成；③ 看两端速率/双工/VLAN 配置；④ 用多流压测验证是否真的分摊（iperf3 -P 8）。
  • 验证均衡的正确方法：用 多条并发流（iperf3 -P 8）而不是单条。单流测试永远只能跑满一条物理链路。
两条 1 G 聚合了，为什么传文件还是 1 G？

单条 TCP 连接被哈希到固定一条物理链路。这是 LACP 的设计（保证同一流的包不乱序）。要用多线程/多连接传输（如 iperf3 -P 4、BT 下载、多条 scp）才能跑满聚合带宽。

链路断了会丢包吗？

LACP 检测到链路 down 后会把流量切到剩余链路，通常 几十到几百毫秒内完成（fast 模式更快）。期间的包会丢，TCP 会重传。用 lacp_rate fast + 交换机配合能缩短到几十毫秒。

自检

两根 1G 网线聚合后，单条 TCP 下载一定达到 2G 吗？

不一定。常见哈希让一条流固定走一个成员口，单流往往仍受该口 1G 上限限制。
