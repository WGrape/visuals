日常高性能服务几乎都建立在 IO 多路复用（select/poll/epoll/kqueue） 或 异步 IO 之上。

Reactor 与 Proactor

事件驱动两兄弟

Reactor：事件就绪后由应用自己读（如 epoll + 非阻塞读写）；Proactor：内核完成 IO 后回调（如 Windows IOCP、Linux io_uring）。前者生态成熟，后者延迟更低。

epoll 为什么高效

select/poll 每次都要把全量 fd 拷进内核并线性扫描；epoll 用内核红黑树管理 fd，只返回「就绪」的集合，复杂度从 O(n) 降到 O(就绪数)。

问题 1
阻塞和非阻塞到底差在哪？

阻塞调用会一直挂起线程直到数据就绪；非阻塞立刻返回，没数据就报错，需要你之后轮询或等事件通知。非阻塞让一个线程能照看成百上千个连接。

问题 2
同步 IO 和异步 IO 怎么区分？

同步 IO 在数据就绪后，读/写动作仍由你的线程完成；异步 IO 连读写的拷贝都交给内核，做完再通知你。所以 epoll 属于同步（你亲自 read），io_uring 更接近异步。

问题 3
epoll 为什么比 select 快？

select 每次调用都要把全部 fd 从用户态拷进内核并线性遍历；epoll 在内核维护就绪队列，只把「真有事件」的 fd 给你，省去了重复拷贝和全量扫描。

问题 4
Reactor 和 Proactor 怎么选？

Linux 上 Reactor（epoll + 非阻塞）生态最成熟、最常用；追求极致低延迟且内核支持时，可用 io_uring 风格的 Proactor。业务层通常无感知，由框架封装。

I/O 模型的本质是「谁等、怎么等」

网络编程的性能差异，根源在 I/O 模型。四个概念要先分清：阻塞/非阻塞说的是「等待时线程是否被挂起」，同步/异步说的是「结果由谁通知」。它们是两个维度，常被混为一谈。

为什么 epoll 快：它不需要每次把所有 fd 从用户态拷到内核态，也不需要在返回后遍历全部 fd 找就绪的——内核直接给出就绪列表。所以连接数很大但活跃连接少的场景（典型如长连接推送），epoll 优势巨大。

工程落地要点

① LT 与 ET 怎么选

  • LT（水平触发，默认）：没处理完会持续通知，安全但可能重复唤醒。
  • ET（边缘触发）：只通知一次，性能更好，但必须一次读/写到 EAGAIN。
  • ET 必须配非阻塞 fd，否则一次读不完就再也收不到通知。
  • 一般建议：先 LT 保证正确，性能不够再改 ET。

② 事件循环不能被阻塞

  • 业务处理（复杂计算、数据库调用）要丢到线程池。
  • 否则一个慢请求会卡住上万连接。
  • Netty 的 boss/worker + 业务线程池就是典型分层。
  • 注意超时任务与背压，别让线程池队列无限堆积。

③ 惊群与负载均衡

  • 多进程/线程同时 epoll_wait 同一 fd 会惊群。
  • 解决：SO_REUSEPORT（内核分担）、或单 accept + 分发。
  • Nginx 的 accept_mutex 也是为此。
  • 多核利用：每核一个事件循环（thread-per-core）。

④ 常见调优参数

  • 文件描述符上限：ulimit -n 与 /proc/sys/fs/file-max。
  • TCP 参数：somaxconn、tcp_tw_reuse、backlog。
  • 缓冲区：SO_RCVBUF/SO_SNDBUF 与自动调优。
  • 关闭 Nagle（TCP_NODELAY）降低小包延迟。
  • 开启 keepalive 检测死连接。

深入自检

阻塞 I/O 和非阻塞 I/O 的核心区别是什么？

在于「数据没就绪时调用是否立即返回」。阻塞 I/O 会把线程挂起，直到数据准备好并拷贝完成才返回；非阻塞 I/O 立刻返回一个错误码（EAGAIN），调用方需要之后再来问。真正的 I/O 操作（内核拷数据到用户空间）在两者里都是同步完成的，这点常被误解。

同步 I/O 和异步 I/O 怎么区分？

看「结果是谁通知的」：同步 I/O 由调用方自己等待并读取结果（哪怕是非阻塞轮询）；异步 I/O 是内核完成整个操作（包括拷贝）后主动通知调用方。POSIX 的定义正是以此划分，所以 epoll 属于同步 I/O（它只通知「就绪」，还得自己 read）。

为什么 select 有 1024 的限制？

因为它用固定大小的位图（fd_set）表示描述符集合，FD_SETSIZE 通常编译为 1024。poll 改用数组因此没有硬上限，但每次仍要遍历全部元素，连接数大时性能差。这也是 epoll 出现的主要动因。

ET 模式下为什么会漏读数据？

因为 ET 只在「状态发生变化」时通知一次。如果这次通知后你只读了一部分数据就返回，剩下的数据不会触发新的通知，就会滞留在缓冲区里。正确做法是配合非阻塞 fd，循环 read 直到返回 EAGAIN，确保把缓冲区读空。

一个线程真的能撑上万连接吗？

能，前提是每个连接大部分时间是空闲的（典型的长连接/推送场景），活跃连接占比低。epoll 的开销与「就绪事件数」成正比而非连接总数，所以 C10K、C100K 都可实现。但若每个连接都在持续传大量数据，瓶颈会变成带宽与数据拷贝，单线程就不够了。

io_uring 相比 epoll 强在哪？

它把系统调用本身也异步化了：通过用户态与内核共享的环形队列提交请求、收割完成，避免了每次操作的系统调用开销，也支持真正的异步读写（数据拷贝由内核完成）。在高 IOPS 场景（存储、高速网络）收益显著，代价是编程模型更复杂、对内核版本有要求。
