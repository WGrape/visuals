读懂 EXPLAIN：基数估计、连接顺序与实际行数

把执行计划中的“估计 rows”与真实执行结果对照，找到慢查询为什么选错路径。

SQL 语义相同，物理计划可能不同

一条 JOIN 查询可以先过滤再连接，也可以先构建哈希表、走索引嵌套循环或排序合并。优化器根据表行数、列分布、索引与代价模型估计不同计划的成本，选择看起来较便宜的一条。EXPLAIN 展示的是计划，不是 SQL 书写顺序的逐字执行。不同数据库的计划节点名称、统计信息和 ANALYZE 语法不同，应先确定当前产品版本。

基数估计指某节点预计输出多少行。假设 orders 有一百万行，条件 status='paid' 预计选出 1%，即一万行；若实际有 80 万行，后续 JOIN 的构建侧、扫描次数和内存需求都会偏离计划。一次错误估计可能沿计划树放大，不要只盯最慢的末端节点，而要找最早出现巨大估计偏差的地方。

逐步推演

读取计划

区分计划节点、估计行数、实际行数与循环次数。

找最早偏差

从树底部向上找首个巨大估计误差。

验证原因

检查统计、数据倾斜、列相关性与参数分布。

比较改动

在代表性数据上测 SQL、索引或统计更新的总成本。

一次估计偏差的推演

查询按地区筛客户，再连接订单。优化器估计地区只有 100 个客户，于是对每位客户走订单索引；实际有 50 万客户，索引随机访问变成海量 I/O。若先扫描订单并做哈希连接，在该实际数据分布下可能更合适。这里不是说哈希连接永远更快，而是说明计划依赖数据分布。需要用实际执行计划记录每节点估计行数、真实行数、循环次数与耗时，才能定位假设在哪一步失效。

观察可能原因进一步检查
估计 100，实际 50 万统计过期或数据倾斜列分布与统计更新时间
每次索引访问很快，总体却慢循环次数过大实际 loops 与随机 I/O
Hash 节点溢写磁盘实际基数超过内存预算内存、批次与临时文件
过滤未下推表达式或语义限制节点位置与谓词形式

统计信息与相关性

单列直方图可描述某列常见值和分布，但多个条件之间可能有关联。若“地区=华东”与“状态=已支付”高度相关，简单把两个选择率相乘会低估结果行数。数据库可能提供扩展统计、多列统计或采样机制，能力依产品而异。更新统计之前先核对过滤值、NULL 比例、时间分区和最新导入的数据是否被纳入。

参数化查询还可能因参数值不同呈现不同基数：一个热门客户有百万订单，普通客户只有十笔。复用同一计划可能对一类参数很好、另一类很差。分析时保留真实参数的分布与隐私处理后的样本，避免只用测试环境的小数据判断线上计划。

安全的调优顺序

  1. 用实际执行计划记录估计 rows、实际 rows、loops、时间与 I/O，找最早偏差节点。
  2. 核对 SQL 谓词是否可使用索引、统计是否过期、过滤列是否高度相关。
  3. 在代表性数据上测试统计刷新、索引或查询改写，每次只变一个因素。
  4. 比较总耗时、尾延迟、内存与写入维护成本，避免只让单条查询变快。

练习：某节点估计 10 行、实际 10 万行，后续嵌套循环执行 10 万次。你会先加大内存、强制 JOIN 顺序，还是先检查数据分布与统计？请说明证据链。

计划变化不等于问题已经解决

刷新统计后优化器可能选出另一计划，但如果数据继续快速变化，计划可能再次退化。必要时建立定期统计维护、数据分布异常告警和代表性查询回归。强制索引或固定计划可以作为短期止损，但可能让其他参数值变慢；应记录适用范围和撤销条件。线上比较需要观察真实参数、并发和缓存状态，不能只在空闲测试库执行一次 EXPLAIN 就下结论。

估计偏差会如何传播

连接两个表时，优化器先估计每侧过滤后的行数，再估计连接后行数。若左表实际比预期多一万倍，嵌套循环的内侧访问可能同样放大一万倍；若哈希表实际过大，又会溢写临时文件。慢查询不一定是某个节点“自身算法坏”，而可能是上游错误基数把它放进了不合适的位置。查看实际计划时，既看 rows，也看 loops：一次 2 毫秒的索引访问执行 10 万次，总耗时仍很大。统计刷新后先验证估计是否改善，再检查整体计划与并发负载，避免只看到估计值变准却忽略新计划的内存成本。

WHERE 列上存在大量 NULL、少数超热门值或高度相关的多列条件时，平均选择率尤其容易失真。把这些值作为测试参数单独执行实际计划，比只用一个随机参数更能暴露计划不稳定性。

执行计划与基数估计的关键字段

字段含义怎么读
type（MySQL）访问方式system < const < eq_ref < ref < range < index < ALL；出现 ALL 要警惕
rows预估扫描行数与 filtered 相乘才是上游要处理的行数
filtered过滤后剩余百分比rows × filtered% = 传给上层的行数
Extra补充信息Using filesort/Using temporary 是性能红灯
actual rows（PG）实际行数（EXPLAIN ANALYZE）与 estimate 差 10 倍以上说明统计信息有问题
cost（PG）优化器估算代价相对值，看比例；startup_cost..total_cost
key_len实际用到的索引字节数判断是否用了复合索引的全部列
loops（PG）该节点执行次数嵌套循环的内层要乘上 loops

基数估计为什么会错：优化器默认假设列之间独立、值均匀分布。现实里这两条经常不成立：比如「城市=北京」和「年龄<25」高度相关，独立假设会把选择率算成 0.1 × 0.2 = 0.02，实际可能是 0.15，低估 7 倍 → 优化器选了嵌套循环而不是哈希连接 → 慢几十倍。

诊断命令

-- MySQL：看实际与预估的差距
EXPLAIN FORMAT=JSON SELECT * FROM orders WHERE dt >= '2026-10-01' AND status = 1;
-- 关注 examined_rows vs rows_examined_per_scan

-- MySQL 8.0.18+ 的 EXPLAIN ANALYZE（会真执行！）
EXPLAIN ANALYZE SELECT * FROM orders WHERE dt >= '2026-10-01';
-- 输出每个节点的 actual time 和 actual rows，能直接对比预估

-- PostgreSQL：EXPLAIN ANALYZE（最详细）
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT * FROM orders WHERE dt >= '2026-10-01';
-- 关键看：
--   Seq Scan ... rows=10000 (actual=500)  <- 预估 10000，实际 500，差 20 倍！
--   Buffers: shared hit=100 read=5000     <- hit 高说明缓存命中好

-- 更新统计信息
ANALYZE orders;                        -- PG
ANALYZE TABLE orders;                  -- MySQL
-- 提高统计精度（PG）
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 500;   -- 默认 100，最大 10000
ANALYZE orders;
-- 发现估计偏差后的处理手段（PG）
-- 1) 扩展统计：告诉优化器列之间有相关性
CREATE STATISTICS st_orders (dependencies, ndistinct) ON city, age FROM users;
ANALYZE users;

-- 2) 多列统计（MySQL 8.0+ 没有直接的，但可以建复合索引让优化器用 index dive）
-- MySQL 的 eq_range_index_dive_limit（默认 200）
--   IN 列表长度 <= 200 时走 index dive（精确），超过则用统计估算（可能不准）

-- 3) 强制指定（最后手段）
SELECT /*+ USE_INDEX(orders, idx_dt) */ * FROM orders WHERE dt >= '...';  -- MySQL 8.0 hint
SET enable_nestloop = off;    -- PG：临时关闭嵌套循环（会话级）
-- hint 是双刃剑：数据分布变化后会失效，谨慎使用

排障清单

症状原因处理
预估与实际差 10 倍以上统计信息过期或精度不够ANALYZE；调 STATISTICS 目标；开自动 analyze
明明有索引却全表扫预估返回行数太多（> 表 20~30%）确认条件是否真的返回那么多；加更精确的条件；或强制索引
复合索引只用到一部分不满足最左前缀 / 中间有范围查询范围条件放最后；按「等值列 → 排序列 → 范围列」建索引
Using filesort排序无法用索引建包含排序列的复合索引；或减少排序数据量
Using temporaryGROUP BY / DISTINCT 需要临时表加索引让分组有序；调 tmp_table_size
join 顺序不合理基数估计错导致选错顺序ANALYZE；或用显式 join 顺序（PG 的 join_collapse_limit）
EXPLAIN 快但执行慢EXPLAIN 不执行，只是计划用 EXPLAIN ANALYZE（注意会真跑，别在生产跑 DML）

判断统计信息是否健康的标准：预估行数与实际行数的比值在 0.1~10 之间算正常。超出这个范围，优化器选错计划的概率就会大幅上升。

自检

EXPLAIN 里写的 rows 一定是实际扫描行数吗？

不一定。许多计划中的 rows 是优化器估计；需使用产品支持的实际执行计划比较真实行数。

为什么两列选择率不能总是直接相乘？

两列可能相关，独立性假设会高估或低估结果基数。
