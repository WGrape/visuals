🎯 核心区别总结

连接模式

短连接：请求-响应后立即关闭
长连接：多次请求-响应复用同一连接
WebSocket：握手后持久连接，任意时刻双向通信

通信方向

短/长连接：半双工，只能 Client 发起请求
WebSocket：全双工，双方平等，可主动发送

实时性

短/长连接：轮询或 SSE 实现伪实时
WebSocket：原生支持真正的实时通信

协议开销

HTTP：每次请求需完整 Header
WebSocket：首帧握手后，帧 Header 仅 2-14 字节

适用场景

RESTful API 表单提交 页面加载 低频数据获取 实时聊天 在线游戏 股票行情 协作编辑 IoT 设备状态 实时通知

WebSocket 不是「另一个协议」那么简单

WebSocket 的巧妙之处在于借用 HTTP 完成握手：先发一个带 Upgrade: websocket 的普通 HTTP 请求，服务端回 101 Switching Protocols，之后这条 TCP 连接就切换成 WebSocket 帧格式。这样既能穿过已有的 80/443 端口与代理，又摆脱了 HTTP 的请求-响应模式与头部开销。

关键取舍：WebSocket 换来低延迟与双向能力，代价是服务端要维护海量长连接状态——内存、心跳、重连、水平扩展（需要会话共享或粘性路由）都是新的复杂度。

工程落地要点

① 心跳与断线重连

  • 必须实现 Ping/Pong 或应用层心跳：中间设备（NAT、LB）会静默断开空闲连接。
  • 客户端要有重连与指数退避（避免服务端恢复瞬间被冲垮）。
  • 区分「可重试」与「不可重试」的关闭码（如 1000 正常、1008 策略拒绝）。
  • 重连后要做状态补偿（补拉离线期间的消息）。

② 水平扩展

  • 长连接绑定在某台机器上 → 需要粘性会话（sticky）或连接层与业务层分离。
  • 跨实例广播：用 Redis Pub/Sub、Kafka 或专门的消息总线。
  • 优雅下线：先停止接新连接、发关闭帧、等待排空，再退出。
  • 监控：连接数、消息速率、帧大小分布、重连频率。

③ 背压与限流

  • 慢客户端会堆积发送缓冲 → 需要限制单连接的待发队列长度。
  • 对大消息分片与大小上限做限制，防止单条消息拖垮服务。
  • 按用户/连接限流，防止单连接刷爆。
  • 注意消息顺序与幂等（重连重发可能导致重复）。

④ 什么时候不该用 WebSocket

  • 只是偶尔拉一次数据 → 普通 HTTP 更简单可靠。
  • 只需要服务端单向推 → SSE 更省事。
  • 需要请求级别的缓存、CDN、可观测性 → HTTP 生态更成熟。
  • 无状态、可水平扩展优先的架构 → 长连接会带来额外负担。

深入自检

WebSocket 握手为什么要用 HTTP？

为了兼容现有的网络基础设施：复用 80/443 端口、穿过企业代理与防火墙、携带 Cookie 做鉴权、让已有的负载均衡与 TLS 终止设备无需改造。这样新协议可以在旧世界里平滑部署，这是它成功的关键设计。

为什么客户端到服务端的帧必须加掩码？

主要是为了防止「缓存投毒」类攻击：如果攻击者能通过浏览器构造特定的帧内容（可被预测的中间设备看到），可能让中间代理把它当成 HTTP 请求缓存下来。强制客户端加随机掩码，使线上字节不可预测，从而消除这类风险。

WebSocket 连接断了怎么检测？

TCP 断开发现很慢（可能几分钟），所以要有应用层机制：WebSocket 协议本身提供 Ping/Pong 帧，应用层也可以定期发心跳消息并期待回应。通常做法是「空闲 N 秒发 Ping，M 秒无 Pong 就判定断开并重连」，同时结合 TCP keepalive 与服务端超时配置。

WebSocket 和 gRPC 流式怎么选？

浏览器前端通信选 WebSocket（生态成熟、浏览器原生支持）；内部服务间通信选 gRPC 流（有 schema、代码生成、拦截器、可观测性）。浏览器不能直接调 gRPC，需要 grpc-web 做桥接，此时不如直接用 WebSocket 或 HTTP/2 流。

多实例部署时 WebSocket 有哪些坑？

三个典型坑：① 连接粘性——负载均衡要按连接保持（或按用户 ID 路由），否则重连会落到别的实例；② 跨实例广播——A 实例上的消息要发给连在 B 实例的用户，需要消息总线；③ 发布与扩容——重启会断开连接，要有优雅下线、重连风暴防护（退避 + 抖动）。

WebSocket 会被 HTTP/3 取代吗？

短期内不会，但会有替代方案出现。基于 QUIC 的 WebTransport 提供了双向、多流、不可靠数据报等能力，在弱网与游戏场景更有优势。不过 WebSocket 生态极其成熟，未来大概率是长期共存：WebSocket 继续服务通用实时场景，WebTransport 在特定场景补充。
