Apache Pulsar 深度解析

Pulsar 的最大卖点是存算分离：无状态 Broker 只管服务与路由，消息持久化交给 Apache BookKeeper（Bookie）存储集群；再叠加分层存储（S3）与多租户。这让它在「海量主题、弹性扩容、无限留存」上比 Kafka 更从容。

1架构：Broker（无状态）+ BookKeeper + ZooKeeper

Kafka 的 Broker 既管计算又管存储；Pulsar 把存储拆给 BookKeeper，Broker 可以随意扩缩。

Broker 把消息写入 BookKeeper；数据老化后卸载到对象存储
  • Broker：无状态，负责协议、路由、消费分发；扩缩容无需迁移数据。
  • BookKeeper / Bookie：低延迟的日志存储，以 Ledger（段）为单位，多副本写入保证持久化。
  • ZooKeeper：存元数据与 broker/bookie 协调（新版也在去 ZK）。
  • 分层存储：老数据从 BookKeeper 卸载到 S3/OSS，实现「无限留存 + 低成本」。

2Topic、分区与 Ledger

Pulsar 的 Topic 可分区；每个分区的消息按 Ledger（段）追加到 BookKeeper。段写满或滚动后关闭、开新段——这种「段」模型让数据迁移、分层存储、扩容都非常自然。

分段是关键因为消息以可关闭的 Ledger 段存储，老段可以直接整体卸载到对象存储，新段继续在 BookKeeper；扩容时新段落到新 Bookie，无需 reshuffle 全量数据。

3四种订阅模式

模式语义典型用途
Exclusive单个消费者独占严格顺序
Shared多消费者轮询（无序）水平扩展消费
Failover主消费者+备，主挂切换高可用顺序

第二层 · Pulsar 的关键概念与参数

概念 / 参数默认 / 常见值说明
订阅类型Exclusive / Failover / Shared / Key_Shared决定消息怎么分发给消费者
bundle 数量默认 4topic 的负载分片单位，影响分裂与迁移
ackTimeout默认不启用（0）需要显式设，超时后消息会被重新投递
message TTL默认 0（不淘汰）未确认消息的存活时间
retention默认 0（不保留）已确认消息保留多久，设了才能回放
backlog quota默认无限制建议设上限，避免磁盘被未消费消息撑爆
分区 topic按吞吐设分区数决定最大并行度
存储层BookKeeper消息存在 BookKeeper 上，broker 无状态
# 1) 看 topic 统计：堆积的元凶基本都在这
pulsar-admin topics stats persistent://public/default/my-topic
#   关键字段：msgBacklog（未消费条数）、backlogSize、storageSize

# 2) 看订阅与未确认消息
pulsar-admin topics subscriptions persistent://public/default/my-topic
pulsar-admin topics stats my-topic | grep -A5 unackedMessages

# 3) 手动处理堆积：跳过、清 backlog、重置游标
pulsar-admin topics skip --count 1000 -s my-sub persistent://public/default/my-topic
pulsar-admin topics clear-backlog -s my-sub persistent://public/default/my-topic
pulsar-admin topics reset-cursor -s my-sub -t 2026-10-25T10:00:00Z persistent://public/default/my-topic

# 4) BookKeeper 侧（存储是否健康）
pulsar-admin bookies list
pulsar-admin broker-stats

# 5) 客户端必配：ack 超时 + 死信（不要留默认）
Consumer<byte[]> c = client.newConsumer()
    .topic('persistent://public/default/my-topic')
    .subscriptionName('my-sub')
    .subscriptionType(SubscriptionType.Shared)
    .ackTimeout(60, TimeUnit.SECONDS)      // 默认不启用，一定要显式设
    .deadLetterPolicy(DeadLetterPolicy.builder()
        .maxRedeliverCount(3)
        .deadLetterTopic('persistent://public/default/my-dlq')
        .build())
    .subscribe();

Shared 与 Key_Shared 的区别：Shared 把消息轮转发给所有消费者（不保证顺序）；Key_Shared 按 key 哈希分发，同一个 key 只给一个消费者，从而在并行消费的同时保住 key 内的顺序。

第三层 · Pulsar 的六个高频坑

  • ackTimeout 没设：消费者处理到一半挂了，消息永远不被重新投递，表现为「消息卡住不消费」。
  • 没设 maxRedeliverCount：一条坏消息无限重投，把整个分区堵死；必须配死信队列。
  • 未消费消息撑爆磁盘：retention 与 backlog quota 默认都很宽松；生产环境必须设上限并监控。
  • bundle 数太少：热点 topic 无法分裂迁移，负载集中在单个 broker；创建时按预期吞吐设 bundle 数。
  • 以为 broker 无状态就不用管磁盘：broker 无状态但 BookKeeper 有状态，磁盘与副本数都要规划。
  • 用 Shared 却期待顺序：Shared 不保证顺序；要顺序就用 Key_Shared 或 Exclusive/Failover。

排查顺序：topics stats 看 backlog → subscriptions 看未确认 → 看是不是某条消息在反复重投 → 再看 BookKeeper 磁盘。

第四层 · 存算分离带来什么

Pulsar 和 Kafka 架构上最大的差别是什么？

Pulsar 把服务层（broker）与存储层（BookKeeper）分开：broker 无状态，扩容只需加 broker，数据不用搬迁；Kafka 的分区与存储绑定在 broker 上，扩容要搬数据。

存算分离的代价是什么？

多一跳网络与一层系统复杂度：写入路径变长、运维要同时懂 broker 与 BookKeeper、延迟通常略高于同一部署下的 Kafka。

什么时候更适合选 Pulsar？

需要多租户、大规模 topic、读写分离、快速扩缩容的场景；如果只有几个高吞吐 topic、团队已熟悉 Kafka 生态，Kafka 往往更省心。
