渐进发布与安全回退

发布不是把新版本复制到机器上，而是控制新旧版本共同运行期间的流量、容量和数据兼容。

策略取舍 扩流机制 回退边界 决策流程

01 / 三种常见发布策略，风险落点不同

策略如何切换资源代价适合场景与限制
滚动更新分批替换实例，旧版逐渐退场需要临时余量但一般不翻倍默认选项；新旧版要能短时间共存，容量不足时会拖慢发布
蓝绿发布准备两套环境，验证绿色环境后把入口切到它短期维持两套环境流量切换清晰；数据库通常共享，不能假设切回蓝色就能恢复旧数据
金丝雀发布先给少量真实流量到新版，逐步扩大比例需同时维持两版及分流能力便于比较真实指标；按实例数量扩容不等于精确按请求量分流

云负载均衡或网关负责入口分流，应用部署系统负责实例替换；两边的控制面不一定一致。先确认平台支持的是权重分流、按用户稳定分组还是仅按实例分配，再选择策略。

02 / 一次可中止的金丝雀放量

  1. 准备确认旧版仍可运行、新版健康检查通过，预留额外容量和可执行的回退入口。
  2. 小流量例如先给新版 5% 流量；观察时间应覆盖调用链延迟和关键业务路径。
  3. 对比按版本分组看 5xx、p95 延迟、下单成功率，而不只看实例存活。
  4. 推进或停止指标稳定再增加权重；越过预设阈值就停止扩流并把入口指回旧版。

长连接、粘性会话、消息消费者与定时任务不一定受 HTTP 入口权重控制。切流前需要处理连接排空（drain）、未完成请求和重复消费/幂等，避免“一切换就丢单”。

03 / 回滚应用 ≠ 回滚数据

应用与流量

保留旧版制品与旧实例的短暂容量；通过权重切回或恢复旧制品，但要考虑启动、缓存预热及连接排空时间。

数据库

先增加兼容字段，再双读/双写或回填，确认旧版仍能工作后再切换；删除字段放到后续独立发布。不要把生产数据恢复到旧快照当作常规回滚。

外围依赖

消息格式、外部 API 和配置开关也要保持版本兼容；一旦新数据已写出，旧版必须能读或有明确的前向修复方案。

如果新版本修改了不可逆的数据含义，最安全的办法可能是停止放量、修复前进，而不是强行回滚；发布评审要提前写下这个边界。

04 / 发布前写好一张操作卡

  • 确定制品摘要、负责人、发布窗口、变更与旧版兼容性。
  • 预设每阶段流量比例、至少观察多久、由谁判断继续。
  • 定义“停止”阈值：错误率、延迟、业务成功率和下游饱和度，按版本区分。
  • 确认回退操作与预计耗时，演练数据库版本兼容、连接排空和告警通知。

更偏容器编排的发布控制见 云原生发布策略；这里重点是云平台的负载均衡、故障域与数据边界。

一句话：发布速度由可观测和可回退能力决定，不由“一键部署”按钮决定。
