寄存器分配手算：三个活跃值争两个寄存器时谁该溢出

用一个基本块分析活跃区间、干扰图、图着色与 spill/reload 的实际代价。

虚拟寄存器不等于机器寄存器

编译器中间表示可以给每个临时值一个独立名字，仿佛有无限多寄存器；真实 CPU 的通用寄存器数量有限，还要遵守指令集和调用约定。寄存器分配要把同时需要的值放到不同物理寄存器，放不下的值暂存到栈等内存位置，称为 spill。分配错误可能让一个值覆盖另一个值，造成难以复现的计算错误；分配保守则会增加内存读写、拖慢程序。

“变量出现得多”不等于“总是需要寄存器”。关键是活跃性：从某点开始到未来最后一次使用之间，某个值必须保持可用。编译器通常在控制流图上做向后数据流分析，求每个基本块的 live-in、live-out，再细化到指令位置。

三个值同时活跃的算例

假设一段代码先读 a、b，计算 c=a+b，接着算 d=a×b，最后用 c+d。计算 c 之后、计算 d 之前，a 和 b 仍要给乘法用，c 要留给最后加法用，三个值同时活跃。若目标机器在这段代码里只允许使用两个可分配寄存器，a、b、c 不可能同时各占一个。它们构成三角形干扰关系，需要把其中至少一个值临时放到内存，或通过合法重排/重算改变活跃区间。

例如把 c 写入栈槽，保留 a、b 在两个寄存器中计算 d，然后再取回 c 与 d 相加。具体指令可能还需要为乘法目标和加法目标腾寄存器，编译器会进一步安排 move、spill 与 reload；本例只说明“两个位置容不下三个同时活跃值”的硬约束。

干扰图与着色

把每个虚拟值看作图顶点，若两个值在某个位置同时活跃且不能共用物理寄存器，就连一条干扰边。为图用 K 种颜色着色，相当于把值放进 K 个寄存器；a、b、c 两两干扰形成三角形，K=2 时无法无冲突着色。图着色分配器会选某个值 spill，重新计算活跃性与干扰关系，再分配；线性扫描分配器则按活跃区间排序，在区间冲突时选择保留或溢出，编译速度通常更可控。

干扰图并非越多边越“安全”：错误地漏边会产生错误代码，过度加边会造成不必要的 spill。边的建立需考虑指令对源/目标寄存器的约束和两个值能否在同一时刻复用位置。

选哪个值 spill

只比较“谁最早结束”不总最优。若 c 只在最后用一次，把它存栈再读一次可能代价不高；若 a 在热循环中每轮被使用十次，spill a 会产生大量 load/store。可按使用频率、循环深度、重算成本、栈访问代价与寄存器约束估计 spill 成本。常量或简单地址有时重算比存取更便宜，但必须确认重算无副作用并保持语言语义。

一段代码中的最佳选择还会受后续调用影响：某些寄存器会被函数调用破坏，调用前后仍活跃的值可能需要放到被调用方保存的寄存器或临时保存。调用约定是平台 ABI 的一部分，不可把任何寄存器随意分配给所有值。

拷贝合并与 φ 降低

编译器常有“把 x 复制到 y”的指令；若 x 和 y 的活跃区间不冲突，分配到同一个寄存器可消除这次拷贝。过于激进地合并也可能让干扰图难以着色，最终多出 spill，得不偿失。SSA 形式中的 φ 节点在降低时会转成控制流边上的拷贝，这些拷贝也参与寄存器分配和消除。应按真实前驱边执行，不可让不同分支的值互相覆盖。

若机器指令只能在特定寄存器做乘除法，或一次指令有固定输出寄存器，还要预着色和插入移动指令。纯抽象的 K 色模型不能表达全部 ISA 约束，但提供理解分配冲突的第一步。

为什么重排可能减少压力

本例若不需要保持原指令顺序，并且运算无副作用，可以先计算 d=a×b，此后 a、b 不再使用，再计算 c=a+b 就晚了：a、b 的值已可能被覆盖，所以要在改写前确认值仍可得。更实际的做法可能是保留 a/b 到最后，或重算便宜的表达式；有时改变计算顺序、及时消费中间值能缩短同时活跃的区间。重排必须尊重数据依赖、溢出/异常语义与内存副作用，不能只为了减少寄存器就改变程序结果。

寄存器压力还会影响指令调度：为了隐藏流水线延迟提前计算，可能拉长中间值活跃时间，产生更多 spill。后端需要在并行性与寄存器成本间平衡。

看汇编时怎样验收

先画每条指令前后的活跃集合，确认三角形冲突确实存在；再数目标机器真正可用的寄存器，不把栈指针或 ABI 保留寄存器算进去。检查生成汇编是否有对应 spill store 与 reload load，重新运行多种输入核对结果。性能测试对比内存访问次数、循环热度和指令数，而不仅是汇编文件大小。一个多余 spill 在冷路径可能无足轻重，在十亿次迭代的热循环里却会显著影响性能。

判定规则：若活跃区间冲突图能用 k 种颜色着色（k = 可用寄存器数），就无需溢出；无法着色时选择代价最低的区间做 spill。

活跃区间与溢出的代价

概念定义量化影响
活跃变量（live）在某点之后还会被读取的变量同时活跃数 > 寄存器数就必须溢出
活跃区间从定义到最后一次使用的范围区间越长冲突概率越高
spill（溢出）把寄存器值写入内存槽多出 1 次 store
fill（回填）从内存槽读回寄存器多出 1 次 load
代价对比寄存器访问 ≈ 0 周期；L1 命中约 4 周期；内存约 200+ 周期一次 spill+fill 约等于几十条指令的时间

代码写法如何影响分配结果

示例

// 1) 同时活跃的变量越多，越容易溢出
int f(int a, int b, int c, int d) {
    int t1 = a * b, t2 = c * d, t3 = a + c, t4 = b - d;   // 4 个同时活跃
    return t1 + t2 + t3 + t4;
}

// 2) 缩短活跃区间：尽早使用、缩小作用域
int g(int a, int b, int c, int d) {
    int s = a * b;            // 用掉就不再活跃
    s += c * d;
    s += a + c;
    s += b - d;
    return s;
}

// 3) 循环里的不变量外提（减少循环内的活跃压力）
for (int i = 0; i < n; i++) {
    sum += arr[i] * scale;    // scale 若在循环内计算，会反复占用寄存器
}
写法对分配的影响建议
引入大量中间变量活跃区间变多变长复用变量、缩小作用域
register 关键字现代编译器基本忽略不要用，靠 -O2 即可
取地址 &x变量必须落在内存，无法常驻寄存器热路径避免对频繁使用的局部变量取地址
大函数（上百个局部变量）冲突图稠密，溢出多拆分函数
-O0 编译每个变量都放栈，几乎不分配寄存器性能对比必须用 -O2/-O3

排障清单

症状原因处理
汇编里大量 rsp/rbp 相对访问寄存器溢出到栈减少同时活跃变量；拆分函数
-O0 下性能很差未启用优化，所有变量走栈用 -O2/-O3 对比
热循环性能不达预期循环内活跃变量超过寄存器数循环展开适度、变量复用、外提不变量
函数调用开销大参数多于传参寄存器（x86-64 为 6 个整数参数）参数过多时改用结构体指针
内联后反而变慢内联增加了寄存器压力用 __attribute__((noinline)) 或调整内联阈值
不同编译器结果差异大分配算法与启发式不同以实测为准，不要假设某种写法一定更快

深入自检

寄存器不够时会发生什么？

发生溢出（spill）：把某些活跃值写入栈上的槽位，用到时再 load 回来。选择哪些值溢出由代价模型决定（通常选使用频率低、区间长的）。spill/fill 会引入额外的内存访问，是热路径性能下降的常见原因。

图着色和线性扫描有什么区别？

图着色构建冲突图（边表示两个区间重叠）再尝试 k 着色，质量高但复杂度高，适合离线编译；线性扫描按区间起点顺序遍历并维护活跃列表，超限时溢出，速度快，适合 JIT 与 LLVM 默认流程。

为什么 -O0 生成的代码会频繁读写栈？

因为 -O0 的目标是调试友好：每个变量都在内存里有唯一位置，方便调试器随时查看，且不做寄存器分配与优化。因此 -O0 的性能数据没有参考价值，必须看 -O2 及以上。

怎么判断一段热代码是否被溢出拖累？

看生成的汇编：若热循环里出现大量 mov %reg, -8(%rbp) / mov -8(%rbp), %reg 这类存取，就是溢出信号。进一步可用 llc -debug-only=regalloc 统计 spilling 次数，再配合 perf 看是否停顿在访存。

把变量声明得更靠近使用点有意义吗？

对源码可读性有意义；对编译器而言，真正决定寄存器压力的是活跃区间（定义到最后一次使用），而不是声明位置（现代编译器用 SSA，声明位置几乎不影响）。真正有效的是减少同时活跃的值、复用变量、拆分函数。

自检

a、b、c 在同一点两两同时活跃，目标只有两个可用寄存器，能让三者全留寄存器吗？

不能。三角形干扰图至少需要三种颜色；必须改变活跃结构或让至少一个值溢出到其他位置。
