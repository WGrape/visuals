CQRS 模式

命令与查询职责分离：写模型和读模型走两套完全不同的路径。

CQRS 读写分家 Command Query Responsibility Segregation

写侧与读侧模型、存储、接口完全分开

传统 CRUD 用同一模型既读又写，复杂查询会把写模型撑得很难看。<b>CQRS</b> 把『改数据(Command)』和『查数据(Query)』拆开：写侧聚焦领域规则，读侧直接投喂前端要的扁平 DTO（可由写侧事件异步同步）。

何时值得用

  • 读写负载差异巨大（读多写少）。
  • 查询模型远比写入模型复杂（多表 join、聚合）。
  • 需要与事件溯源配合。

代价

  • 最终一致性：读模型滞后于写。
  • 两套模型、两套存储，复杂度翻倍。
  • 小系统用了是过度设计。

面试高频问答

Q：CQRS 一定要配合事件总线吗？
A：不一定。简单场景可让写侧直接更新读库（同步）；但 CQRS 真正的威力在配合事件/消息做异步投影，实现读写物理隔离。
Q：CQRS 和读写分离(主从)一样吗？
A：不一样。读写分离是『同一数据的副本分担读压力』；CQRS 是『读模型和写模型结构都不同』，读侧可能是为查询量身定制的视图。
