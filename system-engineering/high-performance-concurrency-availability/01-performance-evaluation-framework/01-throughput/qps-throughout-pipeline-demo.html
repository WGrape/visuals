💡 吞吐量 = TPS × 平均响应大小

吞吐量（Throughput）：单位时间内系统输出的数据总量。
可以理解为"水管出水量"——不管进来多少水，只管出去多少。

举例：每秒完成 5 个请求，每个返回 100KB 数据 → 吞吐量 = 500 KB/s

把一次请求拆成流水线来看

一个请求从进入到返回，要经过接入层、应用逻辑、缓存、数据库、下游服务等多环。整条链路的 QPS 上限由最弱的那一环决定；而端到端延迟是各环耗时之和。性能优化的第一步永远是分段打点，找出最慢的一环。

木桶效应整体吞吐 = 各环节上限的最小值
串行累加总延迟 = 各环节耗时之和

提升吞吐的六类手段

① 减少工作量

  • 加缓存：避免重复计算与重复查询。
  • 裁剪字段：只查需要的列，减少序列化与传输。
  • 提前返回：非法请求尽早拒绝，别走完整流程。

② 合并与批量

  • 批量查询替代 N 次单查（注意 IN 的条数上限）。
  • Pipeline / MGET 减少网络往返。
  • 合并写：批量提交、异步刷盘。

③ 并行与异步

  • 无依赖的下游调用并行发起。
  • 非关键路径（日志、通知、埋点）丢消息队列异步化。
  • 注意并行会增加并发压力，别把下游打垮。

④ 缩短关键路径

  • 把强依赖降级为弱依赖（失败也能返回）。
  • 预计算与物化：提前算好结果。
  • 就近访问：本地缓存、单元化部署。

⑤ 削峰填谷

  • 消息队列缓冲突发流量。
  • 限流与排队：保护系统在容量内运行。
  • 错峰调度：批量任务放低峰。

⑥ 扩容与分片

  • 无状态服务水平扩容最直接。
  • 有状态服务按 key 分片。
  • 注意扩容后依赖（DB 连接数）也要跟上。

深入自检

为什么数据库连接池经常成为隐藏瓶颈？

因为池大小固定，而每个请求可能占用连接若干毫秒。当并发超过「池大小 ÷ 单请求占用时长 × 请求耗时」时，请求会排队等连接，表现为接口延迟飙升但数据库本身很闲。典型公式：池大小 ≈ 并发数 × 单请求 DB 次数 × (DB 耗时 / 请求总耗时)，需要实测调整。

为什么资源利用率不能跑满？

根据排队论，当利用率 ρ 接近 1 时，排队长度与等待时间呈 1/(1-ρ) 式暴涨。实际经验是：CPU/服务利用率超过 70-80% 后，P99 延迟会明显恶化。所以容量规划要留余量，把系统稳态控制在拐点以下。

并行调用一定更快吗？

不一定，但通常能缩短「多个无依赖调用」的总耗时（从求和变取最大）。代价是并发压力上升，可能把下游或连接池打满。要配合：并发上限、超时控制、以及确认这些调用确实无依赖。另外并行会掩盖依赖关系，改动时要小心引入正确性 bug。

缓存命中率提升了，为什么整体延迟没降？

可能的原因：① 缓存不是瓶颈，真正的耗时在别处（下游、序列化）；② 缓存调用本身有固定开销（网络往返），命中与未命中的差距没想象中大；③ 命中率提升的是低频路径。要先看 Trace 确认耗时分布，再优化。

如何判断该加机器还是该优化代码？

先看瓶颈性质：如果是「整体容量不足且单请求成本已合理」（CPU 均匀打满、无明显热点），加机器最直接；如果存在明显热点（某个函数占 40% CPU、某条 SQL 占 80% 耗时），优化代码收益更大且省成本。实践中先做低成本的优化（索引、缓存、批量），再扩容。

重试会怎样放大问题？

重试会成倍增加下游压力：下游变慢 → 上游超时 → 重试 → 下游压力更大 → 更慢，形成雪崩。防护手段：限制重试次数、指数退避 + 抖动、只在幂等操作上重试、重试也要受熔断与限流约束、以及用「重试预算」（总重试量不超过正常流量的一定比例）。
