🚦 状态

把不同状态下的行为分给不同状态对象。

一句话记住地铁闸机在“锁定”和“已解锁”时，对推门动作反应不同。

01 · 从问题出发

为什么会需要这个模式？

订单的待支付、已支付、已取消对 cancel/pay 有不同规则；巨型 if/else 难以维护。

订单有待支付、已支付、已取消。pay 和 cancel 在每个状态下的行为不同；若状态数和操作数都增长，一个巨型 switch 会变成难以检查的状态转移矩阵。

😵 直接写会怎样

function pay(order):
  if order.status == PENDING: charge(); order.status = PAID
  else if order.status == PAID: return AlreadyPaid
  else if order.status == CANCELLED: return Invalid
// cancel、refund 等函数再重复判断 status

💡 关键转折

Context 持有当前 State；每个状态决定可执行动作和下一状态。

让订单把操作委托给当前 State。每个状态对象定义此时可做什么、何时迁移到哪个状态。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

interface OrderState { pay(order); cancel(order) }
class Pending implements OrderState {
  pay(order) { charge(order); order.state = new Paid() }
  cancel(order) { order.state = new Cancelled() }
}
class Paid implements OrderState {
  pay(order) { return AlreadyPaid }
  cancel(order) { return RefundRequired }
}

读代码时抓住三件事

  1. Context 对外保持稳定操作接口，并持有当前 State。
  2. 具体状态实现此时的行为与合法转移。
  3. 外部副作用失败时不能提前切换状态，要明确定义事务顺序。

换个业务场景，还能认出来吗？

网络连接可处于 Disconnected、Connecting、Connected；send() 在三个状态下分别拒绝、排队或真正发送。状态模式让这些行为在各状态类中明确。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

同一对象在不同生命周期状态下对同一操作有不同反应

三个具体场景

  • 订单待支付/已支付/已取消
  • 网络连接断开/连接中/已连接
  • 地铁闸机锁定/解锁

不适合或要小心

不要只为两个简单布尔分支引入一堆类。状态迁移应明确定义非法操作及副作用失败时的处理。

简单的两分支不必造状态类；迁移和副作用失败须定义清楚

最容易混淆的相邻模式

模式真正的区别
策略算法通常由调用方按需求选择；状态通常由对象自身生命周期迁移。
责任链请求沿处理器链传递；状态模式只把操作委托给当前状态。

区分时问自己：行为是随内部状态迁移，还是由外部主动选择算法？

落地前检查

  • 列出状态×操作矩阵，定义每个格子的行为。
  • 测试非法转移和重复操作。
  • 副作用与状态写入之间要处理失败、并发和幂等。
06 · 自己说一遍

两道检验理解的小题

已支付订单再次 pay() 会走 Pending.pay() 吗？

不会；订单委托给当前 Paid 状态，按 Paid 的规则响应。

支付失败时是否应该先把订单设成 Paid？

不应该；应先确认支付成功或定义可靠的中间态，再完成状态迁移，避免状态与外部事实不一致。

第一层 · 本质与识别信号

一句话本质：把「状态」变成对象，让对象在不同状态下有不同的行为。它消灭的是代码里成片的 if (state == X) / switch (state)。

识别信号说明
一个方法里有 switch (state) 且每个 case 行为都不同最典型的信号
状态有明确的转换规则（哪些转换合法、哪些非法）状态机场景
同样的 if (state) 在多个方法里重复出现该把状态抽成对象了
新增一个状态要改很多处 if违反开闭原则
  • 核心结构：一个 State 接口（每个动作一个方法）+ 每个状态一个实现类 + 上下文对象持有一个 State。行为委托给当前状态对象。
  • 与策略模式的关系：结构上完全一样（都是「持有接口 + 委托」）。区别在意图：策略是「调用方主动选一个算法」（外部驱动、一次性的）；状态是「状态自己会转换到下一个状态」（内部驱动、会变的）。
  • 判断口诀：状态之间会互相转换 → 状态模式；只是选一个算法且不切换 → 策略模式。

第二层 · 骨架代码与转换表

Go 实现

// —— 订单状态机（状态模式的经典场景）——
type State interface {
    Pay(o *Order) error
    Ship(o *Order) error
    Cancel(o *Order) error
    Name() string
}

type Order struct {
    state State
    // ... 其他字段
}

// 关键：行为完全委托给当前状态；状态自己负责转换
func (o *Order) Pay() error    { return o.state.Pay(o) }
func (o *Order) Ship() error   { return o.state.Ship(o) }
func (o *Order) Cancel() error { return o.state.Cancel(o) }

func (o *Order) transition(s State) { o.state = s }

// —— 各状态实现：非法操作直接返回错误，不用写 if ——
type Pending struct{}
func (Pending) Name() string { return "pending" }
func (Pending) Pay(o *Order) error    { o.transition(Paid{}); return nil }
func (Pending) Ship(o *Order) error   { return errors.New("未支付不能发货") }
func (Pending) Cancel(o *Order) error { o.transition(Canceled{}); return nil }

type Paid struct{}
func (Paid) Name() string { return "paid" }
func (Paid) Pay(o *Order) error    { return errors.New("已支付，请勿重复支付") }
func (Paid) Ship(o *Order) error   { o.transition(Shipped{}); return nil }
func (Paid) Cancel(o *Order) error { o.transition(Refunding{}); return nil }  // 需退款

type Shipped struct{}
func (Shipped) Name() string { return "shipped" }
func (Shipped) Pay(o *Order) error    { return errors.New("已发货") }
func (Shipped) Ship(o *Order) error   { return errors.New("已发货，请勿重复") }
func (Shipped) Cancel(o *Order) error { return errors.New("已发货，请走退货流程") }

// —— 对比：不用状态模式的写法 ——
func (o *Order) Cancel_bad() error {
    switch o.status {                      // 每个方法都要写一遍 switch
    case "pending":  o.status = "canceled"; return nil
    case "paid":     o.status = "refunding"; return nil
    case "shipped":  return errors.New("已发货")
    default:         return errors.New("未知状态")
    }
}   // 新增一个状态 -> Pay/Ship/Cancel 三个方法都要改
当前状态Pay()Ship()Cancel()
待支付→ 已支付✗ 未支付不能发货→ 已取消
已支付✗ 重复支付→ 已发货→ 退款中
已发货✗✗ 重复发货✗ 走退货流程
退款中✗✗→ 已取消
已取消✗✗✗ 终态

把转换表画出来再写代码——状态模式最大的价值就是让这张表在代码里显式可见（每个状态类一个文件，一眼看完全部转换），而不是散落在 switch 里。

第三层 · 常见误用与排查清单

  • 状态只有 2~3 个且行为差异很小：直接 if 更清晰。状态模式的收益随状态数和动作数乘积增长——3 个状态 2 个动作 = 6 个分支，用 switch 完全够；5 个状态 4 个动作 = 20 个分支，就该上状态模式了。
  • 状态对象持有可变数据导致串味：状态对象通常应该是无状态单例（可以共享一个实例）。如果状态里存了业务数据，多个上下文共用会互相污染。需要带数据时，让上下文持有数据，状态只负责行为。
  • 转换逻辑散落在两处：一半在状态类里转换，一半在上下文里改状态。这是最容易出现的不一致 bug。约定：所有转换都在状态类里做，上下文只提供 transition()。
  • 忘记处理非法转换：每个状态都要为所有动作提供实现（哪怕是返回错误）。用接口强制实现所有方法，编译器会提醒你。
  • 状态爆炸：状态数超过 10 个时，类数量失控。此时考虑表驱动状态机（用 map[state]map[event]state 描述转换）+ 统一的执行器，比几十个类更好维护。
  • 持久化时的状态反序列化：数据库存的是字符串，要有一个 stateFromString() 映射。漏了某个状态会 panic，务必用 default 兜底。
  • 并发下状态转换的竞态：两个请求同时触发转换（如同时支付和取消）。要加锁或用数据库乐观锁（WHERE status = 'pending'），否则会出现状态错乱。

第四层 · 原理与取舍

状态模式的本质是用多态替代条件分支——把「根据状态选择行为」这个运行期判断，变成编译期就确定的方法分派。

维度switch/if 写法状态模式
新增一个状态改所有方法里的 switch新增一个类（0 处改动）
新增一个动作加一个方法 + 写 switch改接口 + 改所有状态类
非法转换的处理靠 default 分支，容易漏每个状态显式实现，编译器强制
转换规则可读性散落在各方法集中在状态类中，一目了然
类的数量1N（状态数）
调试跳转直接看 switch要跳到对应状态类
  • 注意这张表的第二行：状态模式让「加状态」变容易，却让「加动作」变难（要改接口 + 所有状态类）。这和抽象工厂的特性是对称的。选模式前先想清楚：你的系统会更频繁地加状态，还是加动作？
  • 如果两者都频繁变：用表驱动状态机（转换表 + 动作表都是数据），变更时只改数据不改代码。很多工作流引擎就是这么做的。
  • 性能：状态模式把一次整数比较（switch）换成一次接口方法调用（无法内联）。在每次调用只做几纳秒的极热路径上有可测量开销；在业务状态机（订单、连接、播放器）里完全无关紧要——这类操作一秒最多几千次。
状态模式和策略模式真的只是意图不同吗？

结构上是的—— UML 图几乎一模一样（都是「上下文持有抽象 + 委托」），代码也几乎一样。真正的区别有三点：① 谁驱动转换——策略由调用方设置（ctx.SetStrategy(new(A))），选完就用；状态由状态自己转换（Pay() → setState(Paid{})），上下文通常不知道下一个状态是什么。② 状态之间是否互相知晓——状态类会引用其他状态类（转换目标），策略类之间互不知晓。③ 生命周期——策略通常在构造时选定、之后不变；状态在运行时不断变化。所以判断很简单：会不会自己变？会 → 状态；不会 → 策略。另外实践中还有个标志：状态模式的状态类往往有 Name() 用于持久化和日志，策略类通常没有。

什么时候不该用状态模式？

三种情况：① 状态少且简单（2~3 个状态、每状态行为差异小）——直接写 if 更短更清楚，模式带来的类数量是纯负担；② 状态转换不频繁变化但动作频繁增加——因为加动作要改接口和所有状态类，反而比 switch 更痛苦，此时用表驱动或 map[state]handler 更好；③ 状态逻辑需要集中一处配置（如给运营同学配置转换规则）——代码化的状态类不如数据表+通用执行器灵活。判断标准：当「加状态」是主要变化方向时，状态模式才真正划算。如果变化主要来自别处，它只是一个好看但碍事的壳。

状态机怎么保证并发安全？

三个层次：① 内存态（单进程内的状态对象）用锁保护 transition，或直接让状态对象无状态（这样切换只是替换指针，仍需原子性——用 atomic.Value 或在锁内做）；② 持久态（数据库里的 status 字段）用乐观锁：UPDATE orders SET status='paid' WHERE id=? AND status='pending'，检查 rows_affected——这是最实用也最常见的做法，不依赖应用层锁；③ 分布式：把状态转换做成幂等（带状态版本号或幂等键），配合消息队列的重试。核心原则：状态转换必须是「校验当前状态 + 写入新状态」的原子操作，先读后写的两段式一定会有竞态（两个请求都读到 pending，都认为自己可以转换）。
