⚡ Reactor 模式详解

处理高并发 I/O 的核心设计模式 — Nginx / Redis / Node.js 背后的同一套思想

先从问题出发：高并发 I/O 的困境

传统的「一请求一线程」模型：每来一个客户端连接就 fork/create 一个线程去服务它。 线程在等待 I/O（读网络、读磁盘）时会阻塞，什么也干不了。 当并发连接数达到 10 万+ 时，内存和调度开销就会把系统压垮—— 这就是著名的 C10K 问题。


解法的核心思路：不让线程等 I/O，让 I/O 好了之后来通知线程。 Reactor 模式就是这一思路的标准实现。

Reactor 模式的一句话定义

Reactor 模式是一种基于事件驱动的并发 I/O 设计模式。 它使用一个（或少数几个）线程， 通过操作系统提供的 I/O 多路复用（select / poll / epoll / kqueue） 机制，同时监听大量文件描述符（socket）上的 I/O 事件； 一旦某个描述符就绪，就把对应事件分发给预先注册的 Handler 来处理。


关键词：事件循环（Event Loop）、 事件分发（Dispatch）、 非阻塞 I/O、 Handler 回调。

Reactor 模式的四个核心组件
🔄 Reactor（反应堆）

也叫 Event Loop / Dispatcher。
职责：不断调用 epoll_wait 等待事件， 把就绪事件路由给对应的 Handler。 它是整个模式的调度核心。

📡 Handle（句柄）

就是文件描述符 fd， 代表一个 I/O 资源：监听 socket、连接 socket、管道、定时器 fd 等。 事件都附着在 Handle 上发生。

🔌 Event Demultiplexer（事件多路分解器）

操作系统提供的多路复用接口：
select / poll / epoll / kqueue。
负责阻塞等待，直到至少一个 Handle 就绪再返回。

📋 Event Handler（事件处理器）

应用层注册的回调函数。 不同事件类型（可读、可写、连接、关闭） 对应不同 Handler。Handler 应快速执行， 不做耗时阻塞操作。

🚪 Acceptor（接受器）

特殊的 Handler，专门处理新连接到来事件。 调用 accept() 拿到新 socket fd， 为其创建 Connection Handler 并注册到 Reactor。

📦 Concrete Handler（具体业务处理器）

处理已建立连接上的读写业务逻辑： 读数据 → 解码 → 执行业务 → 编码 → 写回响应。 可以把耗时部分扔给线程池。

关键设计原则

1. Handler 必须非阻塞 —— 若 Handler 内调用了阻塞操作（DB 查询、文件读写）， Reactor 线程会被卡住，所有其他连接都饿死。解法：把耗时任务扔进线程池。


2. 注册/注销是动态的 —— Acceptor 建立连接后把 (fd, Handler) 对插入 Reactor 的事件注册表；连接关闭时从表中移除，Reactor 不再监听该 fd。


3. 同一 fd 的读写都由同一 Handler 负责 —— 避免多线程竞争同一连接的状态，连接状态机天然线程安全。

三种经典变体
① 单 Reactor 单线程

✓ 无锁，实现简单
✗ CPU 单核，Handler 阻塞即全挂
适合：单核 CPU、业务极轻、延迟要求不高

② 单 Reactor 多线程

✓ 可利用多核 CPU
✗ Reactor 仍单线程，高并发下 accept 成瓶颈
适合：中等并发、业务有 CPU 计算

③ 主从 Reactor 多线程（Netty 模型）

✓ Main Reactor 专职 accept，Sub Reactor 并行处理 I/O，吞吐量最高
✓ 可完整利用多核，是现代高性能服务器首选
✗ 实现最复杂，需处理线程间任务分发
代表：Netty、Nginx（多 worker 进程版）

单 Reactor 单线程 — 核心伪代码（Python 风格）
# ── 1. 注册表 ──────────────────────────────────────────
handlers = {}   # fd → handler_func

def register(fd, event_type, handler):
    epoll.ctl(EPOLL_CTL_ADD, fd, event_type)
    handlers[fd] = handler

def unregister(fd):
    epoll.ctl(EPOLL_CTL_DEL, fd)
    del handlers[fd]

# ── 2. Acceptor ────────────────────────────────────────
def on_accept(listen_fd):
    conn_fd = accept(listen_fd)          # 拿到新连接 fd
    set_nonblocking(conn_fd)
    register(conn_fd, EPOLLIN, on_read)  # 注册读事件

# ── 3. Handler ─────────────────────────────────────────
def on_read(conn_fd):
    data = recv(conn_fd, 4096)
    if not data:
        unregister(conn_fd)
        close(conn_fd)
        return
    response = process(data)             # 业务逻辑（必须快！）
    send(conn_fd, response)

# ── 4. Reactor 主循环 ──────────────────────────────────
listen_fd = create_tcp_server("0.0.0.0", 8080)
set_nonblocking(listen_fd)
register(listen_fd, EPOLLIN, on_accept)

while True:
    events = epoll.wait(timeout=-1)    # 阻塞直到有事件
    for fd, event in events:
        handler = handlers.get(fd)
        if handler:
            handler(fd)                  # dispatch！

from concurrent.futures import ThreadPoolExecutor
pool = ThreadPoolExecutor(max_workers=16)

def on_read(conn_fd):

    # ↓ 耗时业务交给线程池，Reactor 立刻返回继续监听

def handle_business(conn_fd, data):

Reactor 模式核心价值总结

① 解耦事件检测与事件处理 —— Reactor 只管"谁就绪"，Handler 只管"怎么处理"，职责清晰。


② 用少量线程撬动海量并发 —— 线程不在 I/O 上等待，CPU 利用率高，内存占用低。


③ 可扩展 —— 新 I/O 类型只需实现新 Handler 并注册，不改动 Reactor 核心逻辑，符合开闭原则。


④ 注意边界 —— Reactor 不是银弹：Handler 中不能有阻塞操作；CPU 密集型任务仍需线程池； 单 Reactor 在极高 QPS 下 accept 仍可能成瓶颈（升级为主从 Reactor）。

四种 IO 模型：一次说清

模型等待数据数据拷贝线程状态典型
阻塞 IO阻塞阻塞全程阻塞read() 默认
非阻塞 IO立即返回（需轮询）阻塞用户态忙等O_NONBLOCK
IO 多路复用阻塞在 select/epoll阻塞一次等多个 fdselect/poll/epoll
异步 IO立即返回内核完成后通知完全不阻塞io_uring / IOCP

关键区别：IO 多路复用和异步 IO常被混淆——前者的数据拷贝阶段仍然阻塞（线程要自己调用 read 把数据从内核拷到用户态）；后者是内核拷完再通知你，线程从头到尾不阻塞。所以严格说，Linux 上的 epoll 属于同步 IO（POSIX 定义：真正的异步 IO 是拷贝也不阻塞）。

POSIX 的定义：同步 IO = 在 IO 操作完成前，进程被阻塞；异步 IO = 请求后立即返回，完成时通知。按这个标准，阻塞、非阻塞、IO 多路复用都属于同步 IO，只有 aio/io_uring（Linux）和 IOCP（Windows）是异步。

epoll 用法

// epoll 的标准用法（三步）
int epfd = epoll_create1(0);

// ① 注册关注的 fd 和事件
struct epoll_event ev;
ev.events  = EPOLLIN | EPOLLET;     // ET = 边缘触发
ev.data.fd = sockfd;
epoll_ctl(epfd, EPOLL_CTL_ADD, sockfd, &ev);

// ② 等待事件就绪（返回的是"就绪的"fd，不用全扫）
struct epoll_event events[MAX_EVENTS];   // 通常 1024 或更大
while (1) {
    int n = epoll_wait(epfd, events, MAX_EVENTS, -1);   // -1 = 永久阻塞
    for (int i = 0; i < n; i++) {
        if (events[i].data.fd == listenfd) {
            // 新连接
            int conn = accept(listenfd, ...);
            setnonblocking(conn);              // 必须设为非阻塞！
            ev.events = EPOLLIN | EPOLLET;
            ev.data.fd = conn;
            epoll_ctl(epfd, EPOLL_CTL_ADD, conn, &ev);
        } else {
            handle_io(events[i].data.fd);      // 读写
        }
    }
}

// ③ ET 模式必须循环读到 EAGAIN
while ((n = read(fd, buf, sizeof(buf))) > 0) { ... }
if (n < 0 && errno == EAGAIN) {
    // 数据读完了，等下次事件
}

ET 与 LT 的区别：LT（水平触发）——只要缓冲区还有数据，每次 epoll_wait 都会通知（可只读一部分，安全但效率略低）；ET（边缘触发）——只在状态变化时通知一次，必须一次性读完/写完（循环到 EAGAIN），否则会丢数据。ET 性能更好但更容易写错；Netty 用的是 LT + 自己优化，Redis 用的是 LT。

Reactor 的三种线程模型

模型结构优点缺点代表
单 Reactor 单线程一个线程做所有事（accept + IO + 业务）无锁、简单无法用多核，业务阻塞会卡死全部Redis
单 Reactor 多线程Reactor 线程管 IO，业务丢线程池利用多核Reactor 仍是瓶颈（高并发下）早期 Netty
主从 Reactor 多线程mainReactor 管 accept，subReactor 多个管 IO充分利用多核实现复杂Netty / Nginx / Memcached

为什么 Redis 用单线程还这么快：因为它的业务逻辑极快（内存操作约 100 ns），瓶颈完全在网络 IO，单线程 + epoll 足以跑满。而且单线程带来两大好处：无锁竞争、命令原子性。反例：如果业务处理要 10 ms（如复杂计算、调外部接口），单线程模型的吞吐就只有 100 QPS——这时必须上多线程模型。

深入自检

C10K 问题是怎么被解决的？

核心矛盾：一个连接一个线程的模型下，1 万个连接要 1 万个线程，光线程栈就要 8 MB × 10000 = 80 GB，且上下文切换开销巨大。解决思路是一个线程管理多个连接——这就是 IO 多路复用：用一个 epoll_wait 同时监听上万个 fd，只有真正就绪的才处理。内存降到 几 KB/连接，切换开销几乎为零。配套的另外两点：① 非阻塞 IO（避免一个慢连接卡住线程）；② 事件驱动的编程模型（回调/状态机）。现代还加上了 io_uring（真正的异步 IO，进一步减少系统调用）。

Reactor 和 Proactor 有什么区别？

Reactor：就绪通知——epoll 告诉你“这个 fd 可以读了”，然后你自己调 read 去读（同步 IO）；Proactor：完成通知——你提交一个读请求（含缓冲区），内核读完拷好再通知你（异步 IO）。所以：Linux 的 epoll 是 Reactor，Windows 的 IOCP 是 Proactor，Linux 的 io_uring 也支持 Proactor 模式。性能上 Proactor 更优（省一次系统调用、可批量提交），但 Reactor 更简单且可移植。Java 的 AsynchronousChannel 在 Linux 上其实是用线程池模拟的 Proactor（底层仍是 epoll）。

为什么 epoll 用红黑树 + 就绪链表？

两个数据结构解决两个不同的问题：① 红黑树存所有注册的 fd——支持 O(log n) 的增删改查（epoll_ctl），避免每次调用都拷贝全量 fd；② 就绪链表存本次就绪的 fd——epoll_wait 只需把链表内容拷给用户（O(就绪数) 而非 O(总 fd 数)），这就是它比 select/poll 快的关键（后两者要 O(n) 全扫）。回调机制：fd 就绪时，内核的中断处理会调用 epoll 注册的回调，把该 fd 挂进就绪链表——所以 epoll_wait 只是“取走成品”。

写 Reactor 服务器最容易犯的错是什么？

四个高频错误：① ET 模式没循环读完——只 read 一次，剩余数据要等下次事件，可能永远等不到（死锁）；② 没设非阻塞——ET 模式下阻塞 read 会卡死整个 loop；③ 业务耗时操作放在 IO 线程——一个慢请求阻塞所有连接，正确做法是丢线程池；④ 写事件没及时注销——缓冲区为空时如果还监听 EPOLLOUT（LT 模式），会持续触发导致 CPU 100%（忙循环）。第 ④ 点尤其隐蔽：正确做法是只在真正有数据要写时才注册 EPOLLOUT，写完立即注销。
