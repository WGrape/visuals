内存结构与关键参数

shared_buffers / work_mem / maintenance_work_mem / effective_cache_size 该怎么配。

① 内存全景图② shared_buffers：为什么官方建议 25%③ work_mem：最危险的旋钮④ maintenance_work_mem 与维护操作⑤ 常见问法

① 内存全景图

shared_buffers

全局共享的数据页缓存，所有后端进程共用

wal_buffers

WAL 写盘前的缓冲，通常很小（几 MB）

work_mem

每操作的排序/哈希内存，最容易配错

maintenance_work_mem

VACUUM、CREATE INDEX 等维护操作的内存

temp_buffers

临时表专用，会话本地

effective_cache_size

不分配内存，只是给优化器的提示值

autovacuum_work_mem

autovacuum worker 专用（默认 -1，用 maintenance_work_mem）

OS 页缓存

PG 之外的一层缓存，与 shared_buffers 形成双缓存

② shared_buffers：为什么官方建议 25%

与 MySQL 的 Buffer Pool 不同，PG 同时依赖 OS 页缓存：数据文件既可能在 shared_buffers 中，也可能在 OS 缓存中，形成两级缓存。

设得太小设得太大
命中率低，频繁磁盘读挤压 OS 缓存，总体命中率反而下降
写操作更快落盘（脏页少）检查点时要刷的脏页更多，IO 尖峰更猛
—启动更慢（需要预热/初始化大块内存）
-- 观察缓存命中率（应 > 99%）
SELECT datname,
       round(blks_hit * 100.0 / GREATEST(blks_hit + blks_read, 1), 2) AS hit_pct,
       blks_hit, blks_read
FROM pg_stat_database WHERE datname = current_database();

-- 观察各表的缓冲使用
SELECT c.relname, count(*) AS buffers
FROM pg_buffercache b JOIN pg_class c ON c.relfilenode = b.relfilenode
GROUP BY 1 ORDER BY 2 DESC LIMIT 10;   -- 需 CREATE EXTENSION pg_buffercache
调优方法：先看命中率，若已达 99%+ 就不必再加（加了收益甚微，反而增加检查点压力）。若明显偏低，再结合内存总量逐步上调，每次 25% → 40% 观察效果。不要照搬 MySQL 的「内存 70%」经验。

③ work_mem：最危险的旋钮

核心事实：work_mem 是「每个排序 / 哈希操作」的上限，不是每连接或每查询的上限。一个查询可能含多个排序节点，并行查询还会乘以 worker 数。
-- 危险估算示例
-- work_mem = 256MB，并发 100，每查询平均 3 个排序/哈希节点
-- → 理论峰值 = 256MB × 3 × 100 = 76.8 GB  （远超物理内存！）

-- 正确做法：全局保守 + 会话级放开
-- postgresql.conf
work_mem = 16MB

-- 报表/批处理会话
SET work_mem = '256MB';
-- 或只对某条语句：SET LOCAL work_mem = '256MB'; （事务内生效）

当内存不够时会写临时文件，可通过以下方式观察：

-- 开启临时文件日志（超过 log_temp_files 就记录）
log_temp_files = 0        -- 记录所有临时文件
-- 日志中出现：temporary file: path "base/pgsql_tmp/xxx", size 12345678

-- 查看当前临时文件使用
SELECT * FROM pg_stat_database WHERE temp_files > 0;

④ maintenance_work_mem 与维护操作

用于 VACUUM、CREATE INDEX、ALTER TABLE ADD PRIMARY KEY、REINDEX。默认 64MB，对大表往往偏小。

-- 临时调大以加速建索引（会话级，不影响其他连接）
SET maintenance_work_mem = '2GB';
CREATE INDEX CONCURRENTLY idx_big ON big_table (col);

-- autovacuum 专用
autovacuum_work_mem = -1        -- 默认 -1：使用 maintenance_work_mem
                                -- 设为具体值可为 autovacuum 单独限制
建索引的加速技巧：① 调大 maintenance_work_mem（通常能到 1~4GB）；② 调大 max_parallel_maintenance_workers（PG 11+ 支持并行建 B-tree 索引）；③ 事后再把参数调回。注意：CREATE INDEX CONCURRENTLY 不能并行，且失败会留下 INVALID 索引，需检查并 DROP 后重建。

⑤ 常见问法

Q：PG 的内存参数该怎么整体规划？

A：推荐顺序：① shared_buffers = 内存的 25%（留出空间给 OS 缓存）；② effective_cache_size = 50%~75%（只是提示值，不占内存）；③ work_mem 保守起步（8~32MB），用 log_temp_files 观察是否需要针对会话调大；④ maintenance_work_mem 可设较大（512MB~数 GB），仅在维护操作时使用；⑤ 最后按「worker 数 × work_mem + shared_buffers」核算峰值，避免 OOM。核心原则：共享内存给足，会话内存保守按需放开。

Q：为什么 PG 不把内存都给 shared_buffers？

A：因为 PG 依赖操作系统的页缓存，两者构成双缓存：数据可能在 OS 缓存里而不在 shared_buffers 里，反之亦然。若把 shared_buffers 设得过大，会挤压 OS 缓存，整体命中率反而下降；同时检查点需要刷的脏页更多，造成更猛的 IO 尖峰。这与 MySQL InnoDB 的 Buffer Pool（自己管理、几乎独占）策略不同，因此不能照搬「内存 70% 给缓存」的 MySQL 经验。

Q：怎么判断 work_mem 是否够用？

A：三个信号：① EXPLAIN (ANALYZE) 中排序/哈希节点出现 external merge Disk: xxx kB 或 Hash Join 出现 Batches: N（N>1）——说明已落盘；② 日志中出现 temporary file（需设 log_temp_files = 0）；③ pg_stat_database.temp_files / temp_bytes 持续增长。处理：不要盲目全局调大，而是对产生临时文件的具体会话单独 SET work_mem。

Q：effective_cache_size 会影响性能吗？

A：会，但不通过分配内存——它只作为优化器的提示，用于估算「索引扫描的页是否大概率在缓存中」，从而影响索引扫描 vs 全表扫描的选择。设得太小，优化器会高估索引的 IO 代价而错误地选择全表扫描；设得过大则可能过度偏好索引。建议设为 OS 可用缓存的估计值（内存的 50%~75%），它零成本，设错只影响计划选择。

Q：出现 OOM 或内存暴涨，怎么排查？

A：按顺序：① 检查 work_mem × 排序节点数 × 并发数 × 并行 worker 的理论峰值；② 用 EXPLAIN (ANALYZE, BUFFERS) 看是否有大量临时文件；③ 查询 pg_stat_activity 找长时间运行的大查询；④ 检查连接数（每个后端进程自身也有内存开销，几千连接会吃掉几 GB）；⑤ 检查 shared_buffers 与 max_connections 的组合是否过大；⑥ 临时表与游标（temp_buffers）。防护：用连接池限制后端连接数、给关键会话设 statement_timeout、必要时用 cgroup 限制实例总内存。
