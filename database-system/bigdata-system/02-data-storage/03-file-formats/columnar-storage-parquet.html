列式存储与 Parquet：为什么只查 3 列就能快 10 倍

一张 100 列的表，你只查其中 3 列。行式存储要把 100 列全读出来再丢掉 97 列；列式存储只把那 3 列读出来。这不是"优化"，而是两种根本不同的字节排布方式带来的必然结果。本文从磁盘上的字节怎么摆开始，一路讲到 Parquet 的三层结构、编码压缩、统计信息裁剪，以及嵌套数据的 Dremel 模型。

1先给结论

列式存储快，靠的不是"某种神奇压缩"，而是四个可叠加的独立收益：

① IO 裁剪

只读取查询真正用到的列。100 列里查 3 列，磁盘 IO 直接降到约 3%。

② 压缩比高

同一列数据类型一致、值域相近，字典编码 / RLE / 差分编码都能吃得下，体积常降到 1/5 ~ 1/10。

③ 向量化执行

同列连续存放，可以一次把 1024 个值加载进 CPU 向量寄存器批量算，而不是一个一个判断类型。

④ 统计裁剪

每个数据块带 min/max 统计，WHERE age > 30 可以直接整块跳过，连读都不读。

一句话记忆行式 = "一条记录的所有字段挨着放"，适合整行读写（OLTP，点查一条订单）；列式 = "一列的所有值挨着放"，适合少列大批（OLAP，扫一亿行算个汇总）。

2行式 vs 列式：磁盘上的字节到底怎么摆

这是理解一切的起点。假设有 4 行、5 列的用户表：

行式：一条记录的字段紧挨着；列式：一列的值紧挨着

关键推论磁盘的最小读取单位是块（HDFS block 通常 128MB，SSD page 4KB）。你不可能"只读一行里的 age 那个字段"——行式下 age 被夹在 name 和 city 中间，必须把周围的字节一并读进来。这就是列式省 IO 的物理根源。

3Parquet 的三层结构：Row Group → Column Chunk → Page

Parquet 不是"简单地按列存"，它是一个精心分层的容器。三层结构是它既能裁剪、又能并行、还能支持嵌套的关键。

Parquet 三层结构：读取时先读 Footer（很小），再决定跳到哪些 Row Group 的哪些 Column Chunk

三层的分工

层级是什么典型大小它解决了什么
Row Group
行组		数据水平切分后的一个分片，含该分片所有列默认 128MB
（parquet.block.size）		并行 + 粗粒度裁剪。不同 Row Group 交给不同 Task 并行扫；每个 Row Group 带 min/max，能整组跳过
Column Chunk
列块		一个 Row Group 内某一列的全部数据不定（取决于列宽）列裁剪。只打开查询涉及的列块，其余列的字节完全不读
Page
页		列块内部的更小切分，是压缩 / 编码的最小单位默认 1MB
（page.size）		细粒度裁剪 + 解压粒度。Page Index 记录每页 min/max，可跳过单个页；解压时只解一页而非整列
为什么 Row Group 不能太小也不能太大？太小 → 文件里 Row Group 数量爆炸，Footer 元数据变大、顺序读变差、压缩字典重复；太大 → 并行度不够（一个 Row Group 只能被一个 Task 扫），且裁剪粒度变粗。128MB 与 HDFS block 对齐是经验最优。

四种核心编码

📖 字典编码 Dictionary

把列里的去重值建成字典，原数据只存整数下标。city 只有 "BJ/SH/GZ" 三个值时，字符串变 0/1/2，体积骤降。字典过大时自动退回 PLAIN。

🔁 游程编码 RLE

连续重复值存成「值 + 重复次数」。status 列连续 5 万个 "OK" → 存为 (OK, 50000)。常与字典编码配合（RLE_DICTIONARY）。

📦 位打包 Bit-packing

值域小就少用几位。0~15 只需 4 bit，一个字节塞两个值，比 int32 省 8 倍。

📉 差分编码 Delta

递增数值（时间戳、自增 ID）只存相邻差值。1,2,3…1000000 → 1,1,1… 差分后几乎全是 1，再叠 RLE 压到极致。

通用压缩算法怎么选

算法压缩比解压速度是否可切分适用场景
Snappy中（~2-3x）最快否（但 Parquet 按 Page 切，所以不影响并行）默认选择，CPU 与体积平衡最好
Gzip高（~4-6x）慢否冷数据归档、存储成本优先
ZSTD高（接近 Gzip）快（接近 Snappy）否新项目首选，综合最优，支持压缩级别 1-22
LZO中快需额外建索引老集群兼容，新项目少用
none1x——已加密 / 已压缩数据（如 JPEG、protobuf），再压纯浪费 CPU
为什么列存的压缩比天然更高？压缩算法的本质是"消除重复模式"。city 这一列翻来覆去只有几十个城市名，模式极密集；而行式存储里 city 后面紧跟 salary、再紧跟时间戳，模式被彻底打乱。这就是"同列同构"带来的红利——它和压缩算法本身无关，是排布方式的红利。

5统计信息裁剪：连读都不读

列式存储最"暴力"的一招：靠元数据直接判定某些数据块不可能命中，于是跳过整块 IO。

-- 查询：找 60 岁以上的北京用户
SELECT name FROM users WHERE city = 'BJ' AND age > 60;

Footer 里存着每个 Row Group、每个 Column Chunk 的 min/max。执行过程：

读 Footer
几十 KB
→
Row Group 裁剪
age.max < 60 → 整组跳过
→
Page 裁剪
用 Page Index 再细跳
→
只读 city+name
其余 98 列不碰
裁剪失效的典型情况① 数据未排序：如果 age 随机分布，几乎每个 Row Group 的 min/max 都横跨 18~70，一个也跳不掉。② 谓词取反 / 函数包裹：WHERE upper(city)='BJ' 无法直接用 min/max 判定。③ 高基数列且分布均匀。
→ 对策：写数据时按常用的过滤列 SORT BY / 分区，让 min/max 范围变窄，裁剪率立刻上去（这就是 Z-Order 与聚簇优化的动机）。

6嵌套数据：Parquet 怎么存 List 和 Struct

列式存储最反直觉的难题：JSON 那样的嵌套结构，怎么"按列"存？Parquet 用的是 Google Dremel 论文的 Repetition Level / Definition Level 方案。

// 一行数据（一个用户有多个订单）
{
  "id": 1,
  "orders": [           // repeated group，可重复
    {"item": "A", "price": 10},
    {"item": "B", "price": 20}
  ]
}

存成列时需要两个额外的小整数列，才能无损还原层次：

概念全称回答的问题取值范围
RRepetition Level
重复级别		"这个值是在哪一级发生了重复？"（0 = 新的一条记录）0 ~ 嵌套深度
DDefinition Level
定义级别		"这个值在 optional/repeated 路径上，定义到第几层？"（小于最大层数 = 该值是 NULL / 空）0 ~ 该字段最大层数
直觉理解把嵌套结构拍平成一张大表后，光看 item 这一列你无法知道"A 和 B 属于同一个用户，还是两个不同用户"。R 就是用来标记"从这里开始换了新记录 / 新的一层重复"；D 用来标记"这个位置原本有值，还是因为父级缺失导致的 NULL"。两个整数列非常小（RLE 后几乎可忽略），却让列存完整支持嵌套。

8什么时候不该用列式存储

❌ 点查单条记录

WHERE id = 123 取整行。列存要把 N 个列块各读一小段再拼起来，比行存一次顺序读慢得多。这是 OLTP 数据库（MySQL / Postgres）坚持行存的原因。

❌ 频繁整行写入 / 更新

列存下一个 INSERT 要往 N 个列块各追加一点，写放大严重。这也是为什么湖仓要靠批量追加 + 表格式事务而不是行级 UPDATE。

❌ 查询几乎总是全列

每次都 SELECT *，列裁剪的收益归零，只剩压缩收益，还要承担组装行的开销。

❌ 小文件堆积

列存的元数据（Footer、字典）有固定开销。几 KB 的小 Parquet 文件，Footer 可能比数据还大，且无法有效裁剪。必须做小文件合并（Compaction）。

9常见误区

"列式存储 = 压缩算法更强？"
错。用的是完全相同的通用算法（Snappy / ZSTD）。差别在于喂给算法的数据：列式把同类型、同值域的值聚在一起，模式密集；行式把异类字段混在一起，模式被打散。红利来自排布，不来自算法。
"Parquet 具有事务能力，能 UPDATE 单行？"
错。Parquet 是不可变文件格式，写完就不能改。所谓"湖仓支持 UPDATE / DELETE"是上层的表格式（Iceberg / Hudi / Delta）通过"重写数据文件 + 元数据原子切换"实现的，不是 Parquet 文件本身变了。
"Row Group 越小，裁剪越精准，性能越好？"
不见得。Row Group 太小会导致：Footer 元数据膨胀、每个 Row Group 各建一遍压缩字典（重复浪费）、顺序读退化成大量小随机读、并行 Task 数暴涨带来调度开销。默认 128MB 是平衡值，一般不要动。
"只要转成 Parquet 就一定快？"
不一定。如果数据没有排序、且查询的过滤列分散在各 Row Group 全值域，min/max 裁剪完全失效；同时若查询老是全列，列裁剪也失效。此时收益只剩压缩。分区 + 排序 + 合理 Row Group 大小才是让 Parquet 真正飞起来的三件套。
