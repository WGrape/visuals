⏳ TTL vs TTI：两种过期时间的区别

TTL 从写入开始倒计时，TTI 从最后一次访问开始倒计时——选哪个决定了缓存的更新频率与内存占用。

先建立直觉：两种保质期的算法

  • TTL（Time To Live）：食品生产日期 + 固定保质期。不管你有没有看过它，到点就过期。
  • TTI（Time To Idle）：从最后一次被打开开始计时。一直有人开就一直不过期；没人碰了才开始倒计时。

一个是「从出生算」，一个是「从最后一次互动算」。

时间线对比

关键差异：TTL 下，访问不会延长生命周期（t6 必过期）；TTI 下，每次访问都重置计时器，持续被访问的热数据永远不会过期。

各自的适用场景

TTL 适合

  • ✅ 要求数据不能太旧：即使一直被访问，也要定期回源拿最新（如价格、库存、配置）。
  • ✅ 希望内存占用可预测：所有数据最多存活 TTL，容量有上界。
  • ✅ 缓存与源数据可能不一致：TTL 是最终一致性的兜底保障。
TTL 是默认首选。因为它提供了「数据最多陈旧多久」的确定性保证，这在工程上非常宝贵——你可以明确地说「最坏情况用户看到 5 分钟前的数据」。

TTI 适合

  • ✅ 数据几乎不变：如字典表、配置、静态内容，没必要定期强制刷新。
  • ✅ 希望冷数据尽快释放：没人访问就快速清理，节省内存。
  • ✅ 会话类数据：用户活跃就保持，用户走了就自动清理（如 Session 缓存）。
TTI 的风险：一个持续被高频访问的 key 永远不会过期，如果源数据变了，缓存会长期停留在旧值。所以纯 TTI 不适合「数据会变且要求新鲜」的场景。

组合使用

两者可以同时设置，取先到期者生效：

// Caffeine：同时设置，任一满足即过期
Caffeine.newBuilder()
    .expireAfterWrite(30, TimeUnit.MINUTES)   // TTL：最多存活 30 分钟（保证新鲜度）
    .expireAfterAccess(5, TimeUnit.MINUTES)   // TTI：5 分钟没人访问就清理（省内存）
    .build();
这是实践中最好的组合：TTL 作为新鲜度上限（保证数据不会太旧），TTI 作为内存回收加速（冷数据不必等满 TTL 才释放）。两者互补，既保证正确性又提高内存利用率。
Redis 没有原生 TTI。Redis 的 EXPIRE 是 TTL 语义（访问不续期）。想实现 TTI 效果，需要在每次访问时手动执行 EXPIRE 重置过期时间（多一次命令开销），或者用 OBJECT IDLETIME 配合定期清理。

🎯 面试问答

Q：TTL 和 TTI 能同时设置吗？
A：能，而且推荐这么做。规则是任一条件满足即过期。典型组合：TTL 设一个较长的上限（如 30 分钟，保证数据不会太旧），TTI 设一个较短的值（如 5 分钟，让冷数据尽快释放）。Caffeine 通过 expireAfterWrite + expireAfterAccess 支持，两者可叠加。

Q：为什么 Redis 的 EXPIRE 不是 TTI？
A：因为 Redis 的过期时间是在写入时设定的，读取操作不会重置它（这是有意设计——读路径要保持极致简单和高效）。所以 Redis 只有 TTL 语义。要实现 TTI：① 每次 GET 后手动再 EXPIRE（多一次往返，但可控）；② 或改用 OBJECT IDLETIME 查询空闲时间，由后台任务清理。注意：Redis 在某些淘汰策略下，访问会更新 LRU/LFU 的元数据，但那是淘汰用的，不影响过期时间。

Q：热数据用 TTI 会不会永远不更新？
A：会，这正是 TTI 的主要风险。一个每秒被访问几千次的 key，其空闲时间永远为 0，永远不会因 TTI 过期——如果源数据变了，缓存会长期停留在旧值。所以不要单独用 TTI 缓存会变化的数据。要么加一个 TTL 上限兜底，要么在数据变更时主动删除缓存。

Q：TTL 设多久合适？
A：取决于业务能容忍的陈旧程度：
• 配置、字典：几分钟到几小时（变更少）；
• 商品描述、文章内容：几分钟到几十分钟；
• 价格、库存、状态：秒级到分钟级，且最好配合主动失效；
• 会话、token：与登录有效期一致。
原则：TTL 是「最坏情况下的数据陈旧窗口」，先问业务能容忍多久，再反推 TTL；同时务必加随机抖动防雪崩。

两种过期策略对比

策略含义优点缺点典型实现
TTL Time To Live从写入起固定时长后过期简单、可预测、实现成本低可能刚被访问就过期（热点数据也失效）Redis EXPIRE、SET ... EX
TTI Time To Idle最后一次访问后闲置时长才过期热点数据永不过期，冷数据自动清理需要维护访问时间，成本略高Caffeine expireAfterAccess、Ehcache timeToIdle

两种策略的实现

# Redis：只有 TTL（没有原生 TTI）
SET key value EX 3600              # 3600 秒后过期
EXPIRE key 3600
TTL key                            # 查看剩余秒数，-1=永不过期，-2=已不存在
PERSIST key                        # 移除过期时间
SET key value EX 3600 NX           # 只有不存在时才设置（分布式锁基础）

# 模拟 TTI（每次访问续期——注意这会放大写QPS）
GET key; EXPIRE key 3600           # 每次读都续期
#   代价：读请求变成读写两次，QPS 翻倍。热点 key 上要谨慎

# Caffeine（Java）：TTL 与 TTI 都有
Caffeine.newBuilder()
    .expireAfterWrite(10, TimeUnit.MINUTES)    // TTL
    .expireAfterAccess(5, TimeUnit.MINUTES)    // TTI
    .maximumSize(10_000)
    .build();
#   注意：两个一起配时，<b>取更严格的那个</b>

# Ehcache 3
CacheConfigurationBuilder.newCacheConfigurationBuilder(
    Long.class, String.class,
    ResourcePoolsBuilder.heap(1000))
  .withExpiry(ExpiryPolicyBuilder.timeToIdleExpiration(Duration.ofMinutes(5)))
  .build();

Redis 的过期实现是惰性删除 + 定期抽样：访问时发现过期才删（惰性），同时每 100ms 随机抽 20 个 key 检查（定期）。这意味着已过期的 key 可能仍占内存。官方建议过期 key 的比例不要长期过高，否则定期删除会变慢。另外 Redis 主库的过期删除会同步到从库，从库不主动删过期 key（3.2 之前从库会返回已过期数据）。

TTL 设置实践与雪崩防护

数据类型建议 TTL理由
热点基础数据（配置、字典）较长（1~24h）或永不过期 + 主动刷新访问频繁，重建代价大
用户会话与服务端 session 一致（30min~7d）一致性要求
业务对象（商品、订单）5~30 min兼顾一致性与命中率
榜单 / 聚合结果1~10 min可接受一定延迟
防刷 / 限流计数等于窗口长度（1s~1h）精确控制窗口
分布式锁业务最大耗时的 2~3 倍太短会提前释放，太长故障恢复慢

TTL 抖动与多级错开

# 防雪崩：TTL 加随机抖动（必须做）
ttl = base_ttl + random.randint(0, int(base_ttl * 0.3))
#   例：base=3600 -> 实际 3600~4680 秒
#   不加抖动：一批 key 同时写入 -> 同时过期 -> 瞬间全部回源 -> 打垮 DB

# 多级缓存的 TTL 错开（本级要比下级短或加长，别相同）
#   本地缓存 60s  <  分布式缓存 300s  <  DB
#   这样本地失效时先打到分布式缓存，而不是直接打到 DB

# 热点 key 永不过期 + 异步刷新（逻辑过期）
#   缓存里存 {value, expire_at}
#   读时发现 expire_at 已过 -> 返回旧值 + 触发异步刷新（单飞）
#   好处：永远有值返回，不会击穿
#   代价：短暂的数据不一致

# 监控命中率（TTL 是否合理的最直接指标）
redis-cli info stats | grep -E 'keyspace_(hits|misses)'
#   命中率 = hits/(hits+misses)，< 90% 就该查 TTL 和容量
TTL 设长一点不是命中率更高吗，为什么还要设短？

因为代价是数据陈旧。TTL 的本质是「你愿意容忍多久的不一致」。判断方法：问业务「这个数据晚 5 分钟更新，用户能接受吗？」——价格/库存这类敏感数据可能只能容忍秒级；文章分类、城市列表可以容忍小时级。不是越长越好，是取业务可接受的上限。另外 TTL 过长会让缓存成为事实上的数据源，一旦需要修正就很难清理。

缓存雪崩、穿透、击穿分别怎么防？

① 雪崩（大批 key 同时失效）→ TTL 加随机抖动 + 多级缓存 + 熔断降级；② 穿透（查根本不存在的 key）→ 布隆过滤器或缓存空值（短 TTL 如 60s）；③ 击穿（单个热点 key 失效瞬间）→ 互斥重建（单飞）或逻辑过期（永不过期 + 异步刷新）。三者机制不同，要分别处理。

TTI 有什么坑？

① 写放大——每次读都要更新过期时间，读 QPS 高的 key 会产生同等量级的写；② 内存不可控——只要有访问就不过期，理论上内存可能一直涨（必须同时配 maximumSize 兜底）；③ 语义反直觉——一个长期不更新的数据因为一直被读而永不过期，即使源已经改了。所以 TTI 通常要和 TTL 一起配，或者只用于「有访问就说明还需要」的场景。
