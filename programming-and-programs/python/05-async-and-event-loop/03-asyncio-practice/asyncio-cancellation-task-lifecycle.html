asyncio 取消与任务生命周期：超时后资源真的释放了吗

沿下载任务的超时、取消传播和 finally 清理，理解 TaskGroup、屏蔽取消与后台任务引用。

取消是协作式请求

Python 的 asyncio Task 并发执行协程。调用 task.cancel() 会请求在任务下一次可中断的 await 处注入 CancelledError；它不等于立即杀死线程，也不保证外部操作已经撤销。任务如果长时间执行纯 CPU 循环、没有 await，事件循环得不到控制权，取消和其他任务都可能延迟。下载任务若已向远端发出请求，取消本地等待也不会自动回滚远端已完成的写入。

任务生命周期包含创建、调度、等待、完成、失败和取消。创建任务后若没有明确所有者，程序退出时可能留下未观察的异常或未完成的连接。结构化并发鼓励在一个作用域里创建并等待子任务，让父任务退出前知道子任务的结局。Python 3.11 起的 TaskGroup 提供这类生命周期边界，但仍需要正确清理资源和设计外部副作用。

一次超时的时间线

假设调用方给下载设置 2 秒超时。2 秒到达时，超时作用域取消当前等待的任务；下载协程在下一次 await 处收到 CancelledError，执行 finally 关闭响应流与临时文件，然后取消才真正完成。如果 finally 中还要 await 某个清理操作，退出耗时可能超过 2 秒。因此超时是启动取消流程的期限，通常不是函数返回的硬实时上界。

若协程捕获 CancelledError 后悄悄忽略并继续无限循环，上层等待可能卡住，TaskGroup 与 timeout 的控制语义也被破坏。需要做必要清理时，通常在 finally 中执行后继续传播取消；若确有理由抑制取消，应明确恢复任务状态并承担后续生命周期责任。不要用宽泛异常处理把失败和取消混为一谈。

TaskGroup 遇到一个子任务失败

一组并行下载有三个子任务。一个任务抛出普通异常时，TaskGroup 会取消尚未完成的兄弟任务，等待它们完成清理，然后把异常组交给调用方处理。这样父级不必手工追踪每个创建的 Task。但如果兄弟任务吞掉取消，整个作用域可能久久不能退出。若某项业务允许部分成功，需要在子任务内部转换可预期的业务失败为结果值，或明确选择其他并发编排，而不是误以为 TaskGroup 会自动“忽略一项错误”。

与之相比，gather 的异常处理和其他 awaitable 的生命周期规则有不同细节，不能只凭“都是并发”替换。编排前先写清：一个失败后其他是否继续、结果顺序是否要保留、谁负责取消、是否要收集所有错误。正确性由这些业务语义决定。

shield 与不可取消区

`asyncio.shield()` 可以保护内部 awaitable 不因外层取消而被直接取消，但外层等待者仍会收到取消；内部工作可能继续运行。若没有保存内部 Task 的引用并安排最终等待或记录异常，就可能留下脱离父级管理的后台任务。shield 适用于极少数必须完成的提交或清理步骤，不能把整个请求都包起来以“解决超时”。

外部副作用更需要幂等性。假设上传文件已经提交到远端，客户端超时后再次发起上传，可能创建两份对象。使用稳定操作 ID 或可查询的提交状态，才可以安全重试。取消解决本地任务调度，不能代替业务幂等协议。

资源清理的实操检查

网络响应、数据库连接、临时文件与信号量应放在 async with 或 try/finally 作用域中。若在获取信号量后遇到取消，必须确保 release 发生；async with 可减少遗漏。清理代码自身也可能失败，需要记录原始取消与清理异常，避免只留下“连接关闭失败”而丢失超时上下文。对长时间清理可设置独立预算，但不能在半写入状态下草率宣布成功。

测试时用可控的慢服务让任务刚好停在“获取连接后、收到响应前”和“远端已提交、响应未返回”两个位置，触发取消并检查连接池容量、临时文件数和远端对象数。只测普通成功路径无法发现资源泄漏。

把责任写成表

调用方负责给任务设时间预算、等待其终态并处理未知的外部结果；子协程负责在取消传播时释放本地资源；外部服务依赖业务 ID 处理重复请求；监控负责记录超时、实际退出耗时和残留任务数。若请求已结束，但后台 Task 仍持续执行且无人持有引用，资源消耗与异常会变成难排查的幽灵负载。

自检

调用 task.cancel() 之后，可以立即认定远端写入已撤销、连接也已关闭吗？

不能。取消要等协程运行到可中断点并完成清理，远端副作用还需要单独确认。
