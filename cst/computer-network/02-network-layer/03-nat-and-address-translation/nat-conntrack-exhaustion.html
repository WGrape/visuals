NAT 连接跟踪表耗尽：有带宽却突然无法新建连接

用出口网关百万短连接解释映射表、源端口、超时、重试放大和排障指标。

NAT 不只改一个地址

家庭网关或企业出口做 NAPT 时，需要记住内部源地址端口、外部目标、转换后的公网地址端口及协议等状态，才能把回复送回正确内部主机。每条活跃映射要占用表项和一定内存，设备还要按协议和空闲时间回收。公网链路带宽很空，也可能因状态表满、可用出口端口不足或设备 CPU 过载而不能建立新连接。因此“带宽够”不是出口容量的充分条件。

同一个公网 IP 到同一个远端目标的可用源端口组合有限；增加内部客户端数量不会凭空增加出口端口。不同远端目标、NAT 实现和多公网 IP 会影响实际容量，不能只用 65535 直接当整台网关的最大连接数。系统还要保留系统端口和处理冲突。

一次短连接风暴

公司 5000 个客户端每秒各发数个短 HTTP 请求，却未复用连接。出口 NAT 每秒新建大量映射，旧映射在连接关闭后可能仍保留一段时间以处理迟到报文；遇到远端超时，客户端再重试，瞬时新建速率更高。状态表接近上限后，新连接的 SYN 或 UDP 数据报可能被丢弃，用户看到“有的网站打不开，已打开的页面还能继续”。旧连接继续工作、新连接失败，是状态资源耗尽的重要线索。

若应用把每次 DNS 查询、HTTP 请求都开新连接，先改善连接复用、合理超时与重试，再考虑换更大的网关。只扩充状态表而保持无上限重试，可能把问题推迟到内存或后端服务。

逐步推演

建立映射

内部连接占用网关状态和出口端口。

短连接突发

新建速率高于回收速率，表项累积。

耗尽表现

旧连接可能继续，新连接开始超时。

治理容量

连接复用、退避和出口资源共同调整。

TCP 与 UDP 状态时间不同

TCP 有 SYN、ESTABLISHED、FIN/RST 等可观察状态，网关可据此管理映射；UDP 没有握手，设备通常按最近流量和较短空闲超时维持近似状态。视频通话或 QUIC 长连接若在中间设备上长期静默，映射可能被清除，下一次从外部来的包到不了内部客户端。为了维持映射发送的保活包又会消耗移动设备电量和设备状态容量，需要平衡。

有些流的应用层关闭与设备状态清除并非同时发生，故障时不要只凭服务器上的 TCP 状态推断网关表项。抓包位置在 NAT 前后也会看到不同四元组，必须用时间与映射日志关联。

端口耗尽与表项耗尽不完全相同

状态表内存满意味着整个设备可记录的新映射不足；出口端口不足可能只影响某个公网地址到某类目的组合；CPU 达到瓶颈则可能让映射创建很慢甚至丢包。排障要分别看 active conntrack count、上限、插入失败、哈希碰撞或查找压力、每公网 IP 的端口利用、CPU 和丢包。不能见到一项计数高就自动调大同一个内核参数。

客户端自身也可能耗尽临时源端口，导致请求根本没出主机；服务器 accept 队列满也会让新连接失败。三者症状相似，抓包从客户端、NAT、服务器逐段看 SYN 是否到达，可缩小范围。

重试如何形成正反馈

出口丢掉新连接后，客户端超时重试；如果每层代理和 SDK 都按固定间隔重试三次，原本 1 万 QPS 可能在故障中被放大成数倍新连接。新请求和重试竞争更少的状态容量，故障恶化。需要在客户端设置总截止时间、指数退避和随机抖动，在网关限额与应用侧连接池处同时控制，而不是无限放大出口设备。

重试写请求还可能重复业务副作用，NAT 故障并不会改变幂等规则。用户看到超时，要查询业务结果而不是盲目重新支付。

缓解与容量规划

先减少不必要连接：HTTP 持久连接、连接池、批量请求、适度空闲时间和健康的 DNS 缓存。再依据连接建立速率、平均存活时间和峰值并发估算状态需求，可用 Little 定律从到达率与平均持续时间估算平均活跃量，并加突发与故障余量。增加公网出口 IP、横向分担 NAT 网关或提高状态容量前，还要确认回程对称、日志和监控能正确追踪映射。

调短状态超时会更快回收，却可能误伤长时间空闲的正常连接；调长超时保护长连接，却占用更多表项。按 TCP/UDP 和业务类型做测试，不能一个数字覆盖所有流量。

验收实验

用固定请求数和连接复用率对照压测，记录新建连接每秒、状态表使用率、插入失败、端口占用、客户端超时与服务端收到的 SYN 数。模拟某些客户端无退避重试，再启用退避与连接池，比较峰值。最后断开一台 NAT 节点，验证剩余节点是否有足够状态容量和回程路径。

定位结论要说清是客户端端口不足、NAT 表项不足、出口端口不足还是服务器队列满。只有明确瓶颈资源，扩容才不会花钱却不改善用户体验。

自检

出口带宽利用率很低，能排除 NAT 网关容量问题吗？

不能。连接跟踪表、出口端口或 CPU 可能先触顶，导致新连接失败。
