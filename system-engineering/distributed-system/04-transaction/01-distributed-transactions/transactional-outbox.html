Transactional Outbox：跨数据库与消息的可靠发布

让业务写入和待发事件进入同一数据库事务，再用可重试发布处理消息系统故障。

双写为什么容易留下半成品

订单服务既要写数据库订单，又要向消息队列发布“订单已创建”。若先提交数据库、再发消息，发消息前进程崩溃会留下订单但没有事件；若先发消息、再提交数据库，数据库提交失败会留下没有订单的事件。把两次调用放进一个普通 try 块也不能形成跨系统原子性。Transactional Outbox 把订单行和待发布的 outbox 行放在同一个数据库事务里提交，让“有订单就有待发事件”成为本地事务保证。

Outbox 不直接保证消息只送一次。后台发布器扫描或订阅 outbox，成功发送后标记已发布；若发送成功却在标记前崩溃，重启后会再次发送。通常应接受至少一次投递，并让消费者用事件 ID 做幂等处理。若消费者更新自己的数据库，幂等记录与业务写入最好也在同一个本地事务中。

逐步推演

本地提交

一个事务写业务记录和 outbox 事件，确保二者共同存在或共同回滚。

异步发布

发布器扫描或订阅待发事件，发送给消息系统。

幂等消费

消费者按稳定 event_id 去重，并与本地业务更新一起提交。

监控恢复

观察积压、最老事件年龄、重复投递和按业务键的顺序。

订单创建的完整时间线

一次请求生成稳定 order_id 与 event_id。在数据库事务里插入订单和 outbox 事件，提交后立刻向用户返回订单创建成功。发布器随后读取未发布事件，按指定主题发送；消息系统确认后，再记录发送状态。用户请求无需等待消息系统在线，但下游看到事件会有可监测的延迟。若业务要求“下游同步完成才算成功”，Outbox 并不满足该需求，需要另选协调或同步协议。

故障点留下的状态恢复方式
本地事务提交前订单与 outbox 都没有客户端按幂等键重试
提交后、发送前订单和待发事件都存在发布器稍后继续发送
发送后、标记前事件可能被重复发送消费者按 event_id 幂等
消费中途失败消息重新投递消费事务与去重记录一起提交

顺序、积压与清理仍要设计

同一个订单先“创建”后“取消”，若由多个发布器并发处理，消息可能乱序到达。可按 aggregate_id 分区、记录单调版本号，消费者拒绝旧版本，或按业务键顺序发布。全局顺序通常代价很高，也未必必要；应明确需要的是“同一订单内有序”还是“所有订单全局有序”。

发布器可以轮询 outbox，也可以利用数据库变更日志 CDC。轮询实现直接，却要控制扫描索引、批量大小与锁争用；CDC 降低轮询压力，但增加日志订阅与重放运维。两种方式都要监控待发条数、最老事件年龄、重复投递率和失败重试。删除旧 outbox 行前，先确认已被可靠发布并满足审计保留要求。

验收清单与适用边界

  1. 业务行和 outbox 行在同一数据库事务中写入，事件包含稳定 ID、业务键、类型、版本与时间。
  2. 消费者允许重复投递，幂等窗口覆盖消息重试和故障恢复周期。
  3. 发布积压达到门槛时报警，记录从业务提交到下游生效的端到端延迟。
  4. 演练发送成功但标记失败、发布器重启、消费者事务失败与消息乱序。

练习：订单事件发出后发布器崩溃，重启又发送同一个 event_id。消费者怎样保证库存只扣一次？如果两个事件属于同一订单，如何识别旧版本并避免状态倒退？

表结构与消费者去重的最小设计

Outbox 表至少应能表示 event_id、aggregate_id、aggregate_version、event_type、payload、created_at 和发布状态；发布状态可用于重试，但不能当作消费者已经生效的证明。消费者可以建立以 event_id 为唯一键的 inbox 或处理记录，在同一个本地事务中先尝试插入去重键、再更新业务状态。重复消息碰到唯一约束后直接确认处理完成，避免再次扣库存。

事件 payload 应包含足够的业务标识与版本，但不宜无节制复制敏感数据。Schema 演进时，旧消费者可能还在运行；新增字段尽量保持向后兼容，删除字段要等待消费者升级。订单创建和取消的顺序可由 aggregate_version 检查：如果取消版本 2 先到，消费者可以暂缓、重试或依业务策略处理，不能盲目用较旧的创建事件覆盖较新状态。

Outbox 适合最终一致的跨服务传播，并不保证下游在用户响应前已经完成。若业务必须在同一请求里确认多个系统全部成功，需要明确同步协调、超时和补偿策略。把 Outbox 的“可靠发布”误称为“全链路实时原子提交”，会导致接口契约与真实行为不符。

自检

Outbox 是否实现了跨数据库和消息队列的严格一次提交？

没有。它把业务写入和待发记录做成本地原子事务，发布阶段仍可能至少一次投递。

为什么发布器发送成功后仍可能再次发送？

发送确认与本地“已发送”标记之间可能崩溃，恢复后会重试未标记事件。
