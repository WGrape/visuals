①FAISS 提供了什么、没提供什么

FAISS、ScaNN、hnswlib 这些是索引算法库，不是数据库。它们只解决「给定一批向量和一个查询，怎么快速找到最近邻」，其余的一切（存储、增删、并发、持久化、过滤、服务化）都在库外。

你需要的能力FAISS 提供了吗要自己做
建索引 + 检索✅ 最核心能力，性能极强——
写入新向量⚠️ 部分索引支持 add并发写入、事务、一致性
删除向量⚠️ 需 remove_ids，很多索引不支持或不高效墓碑管理、定期重建
持久化⚠️ write_index 手动落盘版本管理、崩溃恢复
元数据存储❌ 完全不提供另外维护 id → 业务数据的映射
过滤条件⚠️ 仅支持 id 级 IDSelector按业务字段过滤要自己先筛 id
服务化 / 多副本❌自己包 HTTP/gRPC、做副本与负载均衡
把 FAISS 直接放上生产是最常见的架构误用之一。它没有崩溃恢复、没有并发写安全、没有元数据存储。如果一定要用，正确姿势是「FAISS 只做检索，数据以业务库为准，索引可随时重建」—— 也就是把 FAISS 当成可以丢弃的缓存。
import faiss, numpy as np

d, n = 768, 1_000_000
xb = np.random.random((n, d)).astype('float32')
faiss.normalize_L2(xb)                    # 余弦相似度必须先归一化

# HNSW：查询快，内存高
index = faiss.IndexHNSWFlat(d, 32)        # 32 = M
index.hnsw.efConstruction = 200
index.add(xb)

# IVF + PQ：内存省，需要训练
quantizer = faiss.IndexFlatIP(d)
index = faiss.IndexIVFPQ(quantizer, d, 4096, 96, 8)   # nlist, m, nbits
index.train(xb)
index.add(xb)

# 查询
faiss.normalize_L2(xq)
index.nprobe = 32
D, I = index.search(xq, 10)

# 持久化（手动！）
faiss.write_index(index, "index.faiss")
FAISS 的价值在于单机性能极限与 GPU 支持。研究、离线批处理、或把检索嵌进自己的 Python 服务时它非常合适；当成有状态的线上服务则不合适。

②Elasticsearch：已有 ES 的零新增方案

Elasticsearch / OpenSearch 走的是另一条路：先有搜索引擎，再往里加向量能力。如果你的系统已经在用 ES 做全文检索，加向量几乎是零新增系统的选择。

维度ES / OpenSearch说明
字段类型dense_vector支持 float / int8 / int4 / 二值量化索引
索引类型hnsw / int8_hnsw / int4_hnsw / bbq_hnsw / flat选索引类型即选量化档位
默认参数m=16、ef_construction=100num_candidates 控制搜索宽度
过滤原生 filter context，与向量检索组合这是它的强项：过滤器生态极成熟
混合检索BM25 + kNN，可自己加权或 RRF 融合也支持 RRF 原生（较新版本）
运维如果已在用，增量成本极低否则是一个不小的系统
# 搜索：num_candidates 决定「先捞多少候选再精排」
POST /docs/_search
{
  "knn": {
    "field": "emb",
    "query_vector": [...],
    "k": 10,
    "num_candidates": 200
  },
  "query": {
    "bool": { "filter": [{ "term": { "tenant_id": 42 } }] }
  }
}
num_candidates 是 ES 向量检索的召回旋钮，默认值往往偏小。过滤条件越严越要调大，否则会出现和 pgvector 一样的「结果不足 K 条」。

③Chroma / LanceDB / sqlite-vec

嵌入式方案适合「开发体验优先、数据量不大」的场景：

方案形态特点上限
Chroma进程内 / 轻量服务开发体验最好，Python 友好，自带持久化百万级
LanceDB嵌入式（Lance 列存）磁盘优先、支持版本化、无需服务千万级（磁盘）
sqlite-vecSQLite 扩展零依赖、单文件、可随应用分发十万级
DuckDB VSSDuckDB 扩展分析场景，与 SQL 一起用百万级
嵌入式方案的共同优势是把「一个数据库」变成「一个文件或一个库」，桌面应用、CLI 工具、单机分析、原型验证都非常合适；不适合多副本高可用的线上服务。

④两个问题定性与一张对照表

两个问题就能定性：

问题选算法库 / 嵌入式选服务化向量库
数据是否需要被多个服务并发读写？否是
索引丢失后能否从源数据重建？能（索引当缓存）不能（索引就是数据）
需要过滤 + 元数据联合查询？简单过滤即可复杂过滤

⑤速记卡

FAISS 是库

只做「建索引 + 检索」，其余全在库外。

FAISS 的正确用法

把它当可丢弃的缓存，数据以业务库为准。

FAISS 强项

单机性能极限、GPU、离线批处理。

ES 强项

过滤器生态 + BM25 混合，已在用则增量成本极低。

num_candidates

ES 的召回旋钮，过滤越严越要调大。

嵌入式四选

Chroma（体验）/ LanceDB（磁盘）/ sqlite-vec（零依赖）/ DuckDB。

定性两问

是否多服务并发读写？索引能否重建？

分界

< 1000 万且单进程可考虑库；其余上服务。

「库」和「库服务」的差别不在功能多少，而在谁负责状态。库把状态交给你，服务把状态接过去 —— 后者才是线上系统的常态。
