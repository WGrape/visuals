映射（Map）与哈希表

Go 的 map 底层是哈希表。这篇讲创建、增删查、nil 映射、随机遍历序、并发不安全，以及它为什么不能做键的某些类型。

概述

map 是引用类型的哈希表

map[K]V 把键哈希后分散到桶里，查找接近 O(1)。键必须可比较（不能用 slice/map/func 作键）。

基本用法

创建、读取、删除、判断存在

必须用 make 或字面量初始化；读取不存在的键返回零值，配合 comma-ok 可区分「零值」与「不存在」。

m := make(map[string]int)
m["a"] = 1
v := m["a"]            // 1
v, ok := m["x"]       // 0, false（不存在）
delete(m, "a")        // 删除键

// 字面量
m2 := map[string]int{"x": 1, "y": 2}
nil 映射的读写

读可以，写会 panic

声明未初始化的 map 是 nil，读取返回零值不报错，但写入直接 panic——这是高频新手错误。

var m map[string]int   // nil
_ = m["k"]              // 返回 0，不 panic
// m["k"] = 1          // panic: assignment to entry in nil map

if m == nil { m = make(map[string]int) }
m["k"] = 1             // 安全
遍历顺序随机

故意打乱，防依赖顺序

每次 for range 遍历 map 的顺序都是随机的（运行时会打散），这是有意为之，避免程序依赖某种顺序。

for k, v := range m {
    fmt.Println(k, v)
}
// 需要有序：先收集 key 排序再访问
底层实现简述

哈希 + 桶 + 增量扩容

map 由若干「桶」组成，每个桶存 8 个键值对；冲突时溢出桶链式扩展。负载过高时触发增量式扩容（搬迁分摊到后续操作）。

键类型需要实现可比较（==）。想用 struct 作键，其所有字段必须可比较（不能含 slice/map）。
并发安全

map 不是并发安全的

多个 goroutine 同时读写 map 会触发 fatal error（并发检测）。需要并发请用 sync.Map 或自己加 sync.RWMutex。

⚠️ 只在读多写少、且键集合稳定时考虑 sync.Map；否则用普通 map + RWMutex 更直观、性能也可控。

map 的内部结构

Go 的 map 是哈希表，采用桶 + 溢出链处理冲突，并在扩容时渐进迁移，避免一次性搬迁造成的卡顿。

hmap 的桶结构与两种扩容
桶 8 槽每个桶存 8 个键值对，满了挂溢出桶。
tophash存哈希高位，先快速筛选再比 key。
渐进迁移扩容时每次操作顺带搬一点，不集中卡顿。
遍历无序顺序不保证，甚至每次运行都不同。

m := make(map[string]int) // 必须初始化 m2 := map[string]int{"a": 1} // 字面量 // 正确判断存在性 if v, ok := m["a"]; ok { // 存在，v 是值 } // 预分配容量，减少扩容 m := make(map[string]int, 10000) // 删除 delete(m, "a") // 遍历（顺序随机） for k, v := range m { ... } // ❌ 编译错误：不能取 map 元素的地址 // p := &m["a"] // 并发安全的写法 var mu sync.RWMutex mu.RLock(); v := m[k]; mu.RUnlock() mu.Lock(); m[k] = v; mu.Unlock()

为什么不能取地址：map 扩容时元素会被搬到新的桶，之前拿到的地址会失效。为了保证安全，Go 直接禁止对 map 元素取地址。

sync.Map 什么时候值得用

适用场景

  • 读多写少，且 key 集合稳定（如缓存配置）
  • 多个 goroutine 读写互不相交的 key
  • 写入后长期只读取的场景
var m sync.Map m.Store("a", 1) v, ok := m.Load("a") m.LoadOrStore("b", 2) m.Delete("a") m.Range(func(k, v any) bool { return true }) // 注意：它是 any 类型，失去编译期类型检查

不适用场景

  • 写多读少（内部双 map 结构反而更慢）
  • 需要类型安全与 range 语义
  • 需要 len 等常规操作（要自己数）

大多数情况下「普通 map + RWMutex」更简单、更快、更安全。

性能要点

  • make 时给容量提示，避免频繁扩容
  • key 尽量用简单类型，哈希更快
  • 避免在热路径反复建 map
  • 大量删除后重建以释放内存

深入自检

为什么 map 遍历顺序是随机的？

Go 有意在遍历时随机选择起始桶与起始槽位，防止开发者依赖遍历顺序写出隐含 bug。如果你需要稳定顺序，必须自己取出 key 排序后再遍历。

map 是并发安全的吗？

不是。并发读写会触发运行时的并发检测并直接 panic（fatal error: concurrent map read and map write）。需要同步时用 RWMutex，或在某些场景下用 sync.Map。

delete 之后内存会释放吗？

槽位会被标记为空可供复用，但桶数组本身不会缩小。删除大量元素后如果希望释放内存，最有效的办法是新建一个 map 并把需要的元素拷过去，让旧的被 GC 回收。

make(map[string]int, 10000) 的容量是硬性限制吗？

不是，它只是容量提示（hint），用于一开始分配足够的桶以减少扩容。超出后 map 仍会继续增长，只是会经历扩容。

为什么 map 的 key 必须可比较？

哈希冲突时需要用 == 判断 key 是否相同。slice、map、function 不可比较，因此不能作为 key；数组与结构体若所有字段都可比较，则可以作 key。
