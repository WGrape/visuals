ClickHouse MergeTree 引擎详解

Part 目录、granule、mark 文件与后台合并——ClickHouse 性能的地基

MergeTreePartgranulemark后台合并
① 磁盘结构 ② granule 与 mark ③ 合并机制 ④ 引擎变体 ⑤ 运维要点
一句话总结：MergeTree 的本质是「写入 = 追加一个有序的不可变小目录（Part）， 后台不断把小 Part 合并成大 Part」。理解了 Part 与 granule，就理解了 ClickHouse 为什么快、以及它所有的限制。

01Part 在磁盘上长什么样

每次 INSERT 都生成一个 Part 目录，命名类似 202401_1_5_2（分区_最小块_最大块_合并层级）。 目录内部每一列一个文件：

图 1：Part 目录按列切分文件，这是「只读需要的列」的物理基础
关键洞察：.bin 是压缩后的列数据，.mrk2 是「第 n 个 granule 在 bin 里的压缩块偏移 + 解压后行偏移」。 查询时先用 primary.idx 定位 granule 范围，再用 .mrk2 直接 seek 到对应位置—— 不需要解压整个文件。

02granule：最小的不可分割读取单位

granule（粒度）是 ClickHouse 里最小的读取单位，默认 index_granularity = 8192 行。 稀疏索引里的一条记录叫一个 mark，指向一个 granule 的起点。

图 2：granule 是读取的最小粒度——这就是 ClickHouse 不适合点查的原因
为什么不能点查：哪怕只找 1 行，ClickHouse 也至少读 1 个 granule（8192 行）。 单个查询不算慢，但高并发下每个查询都吃掉 8192 行的解码成本，CPU 迅速打满。 这就是官方建议「QPS 控制在 100 以内」的原因——它是吞吐型引擎，不是并发型引擎。

03后台合并机制

同分区的 Part 会被后台线程持续合并。合并是归并排序（Part 内已有序）， 产出更大的有序 Part，旧的 Part 标记 inactive 后异步删除。

合并的三条触发规则

  • Part 数量超阈值：分区内 Part 数过多时优先合并小 Part。
  • Part 总大小超阈值：避免单个分区里堆积过多数据。
  • TTL 到期：按 TTL 规则删除或迁移过期数据。
图 3：合并本质是 Part 间的归并排序，产出全局有序的大 Part

合并的代价

⚠️ 写放大

同一份数据可能被反复读写合并多次。写入速率很高时，合并线程可能跟不上，产生 Too many parts。

⚠️ 去重不实时

ReplacingMergeTree 的去重只在合并时发生，未合并前会读到重复行。必须用 FINAL 或 argMax 兜底。

✅ 幂等安全

合并是幂等的，中断后可重做。查询用 Part 快照，合并过程不阻塞读写。

04引擎变体怎么选

引擎合并时的特殊行为注意点
MergeTree无，仅排序合并基础款，日志明细首选
ReplacingMergeTree同排序键保留版本最大 / 最后写入的行去重异步；查询需 FINAL 或 argMax()
AggregatingMergeTree把多行聚合函数状态合并需配合 AggregateFunction 类型 + 物化视图
SummingMergeTree数值列直接 SUM，非数值列取一行比 Aggregating 简单但只支持求和
CollapsingMergeTree按 sign 列（+1/-1）抵消写入顺序敏感，乱序会导致结果错误
VersionedCollapsingMergeTreesign + version，可容忍乱序解决了 Collapsing 的乱序问题
ReplicatedMergeTree多副本通过 Keeper 同步生产必备；与上面任意变体可叠加
实践建议：多数场景用 ReplicatedReplacingMergeTree + 业务侧保证幂等写入， 查询用 argMax(col, version) 取最新值，比依赖 FINAL 的性能更可控。 纯追加的日志流用基础 MergeTree 即可，最简单也最快。

05运维要点

建表示例

CREATE TABLE events (
    event_date  Date,
    user_id     UInt64,
    event_type  LowCardinality(String),   -- 低基数用 LowCardinality，字典编码
    amount      Decimal(18, 2),
    created_at  DateTime
) ENGINE = ReplicatedReplacingMergeTree(created_at)
PARTITION BY toYYYYMM(event_date)          -- 按月分区，便于 TTL 与剪枝
ORDER BY (event_type, user_id, created_at) -- 主键=排序键，低基数在前
TTL event_date + INTERVAL 90 DAY           -- 自动过期
SETTINGS index_granularity = 8192;

-- 看一张表有多少 part、多大、多久没合并（Too many parts 的第一现场）
SELECT partition, name, rows, bytes_on_disk / 1024 / 1024 AS mb,
       modification_time, active
FROM system.parts
WHERE table = 'events' AND database = 'default'
ORDER BY modification_time DESC
LIMIT 20;

-- 正在进行的合并与进度
SELECT database, table, elapsed, progress, num_parts, total_size_bytes_compressed / 1024 / 1024 AS mb
FROM system.merges;

-- 每个分区的 part 数（> 100 就该警惕）
SELECT partition, count() AS parts, sum(rows) AS rows
FROM system.parts
WHERE table = 'events' AND active
GROUP BY partition
ORDER BY parts DESC;

-- 紧急止血：暂停合并（注意：只是临时手段，不解决根因）
SYSTEM STOP MERGES;   -- 恢复： SYSTEM START MERGES;

-- 强制合并（慎用：会吃掉大量 IO 与 CPU，别在业务高峰跑）
OPTIMIZE TABLE events FINAL;

-- 异步 mutation：删数据不会立刻生效，要查进度
ALTER TABLE events DELETE WHERE dt < '2026-01-01' SETTINGS mutations_sync = 0;
SELECT mutation_id, command, is_done, parts_to_do
FROM system.mutations WHERE table = 'events' AND NOT is_done;

第三层 · MergeTree 的六个高频故障与处理

  • Too many parts (300)：根因是单次写入行数太少（几百行就 commit）。处理：客户端攒批到 1 万~10 万行或 10~50 MB 再写，而不是调大阈值。
  • 写入成功但查不到：数据落在未合并的 part 里且查询走了 FINAL 之外的去重假设；ReplacingMergeTree 要去重必须用 FINAL 或 argMax 聚合，别指望后台合并。
  • 磁盘只增不减：删除是异步 mutation，且旧 part 要等合并才回收；查 system.mutations，必要时 SYSTEM STOP MERGES 排查后被卡住的 mutation。
  • OPTIMIZE FINAL 之后空间反而涨：合并期间新旧 part 同时存在，峰值需要约 2 倍空间；确保磁盘余量 > 最大分区的 2 倍。
  • COUNT 很快、带条件很慢：没命中主键前缀。稀疏索引只在 ORDER BY 前缀上有用，条件字段要放进主键前几列或加跳数索引。
  • TTL 没生效：TTL 依赖合并触发，part 不合并就不删；用分区直接 DROP PARTITION 更干脆，或设 ttl_only_drop_parts。

排查顺序固定为：system.parts 看 part 数与大小 → system.merges 看是否卡住 → system.mutations 看删改是否完成 → 最后才考虑 OPTIMIZE。

第四层 · 为什么是稀疏索引而不是 B+ 树

为什么不能像 MySQL 一样每行建索引？

分析型表单表动辄数十亿行，行级索引的体积会超过数据本身，且索引维护会拖垮批量写入。稀疏索引每 8192 行才记一条，索引体积约为数据的千分之一，代价是只能定位到 granule，再在 granule 内扫描。

granule 为什么要设为 8192？

它是‘索引体积’与‘扫描浪费’的折中：调小索引变大、点查更准；调大索引变小、但每次多扫无关行。8192 是按典型压缩块与内存页量级取的经验值，除非有实测依据否则不要动。

主键和 ORDER BY 为什么必须一致（或主键是前缀）？

数据按 ORDER BY 物理排序，稀疏索引记录的是每个 granule 的 ORDER BY 首值；如果主键不是排序键前缀，索引记录的值就无法用于定位范围，索引形同虚设。
