什么时候适用？

判断信号：多个业务流程需要复用有明确契约的企业服务。

  • 订单与售后流程共用客户服务
  • 跨系统复用库存或身份能力
  • 大型组织治理长期稳定的服务契约

和相近方案怎么区分？

相近方案选择边界
微服务微服务更强调独立部署与自治数据边界；SOA 更强调企业级服务复用与集成治理。
模块化单体进程内模块协作成本低；SOA 的跨服务调用带来网络失败与契约治理。

最小伪代码

customer = customerService.get(customerId)
if not customer.active: return Rejected
stock = inventoryService.reserve(items)
try:
  return orderService.create(customer, stock)
catch error:
  inventoryService.release(stock)
  throw error

边界：服务化会增加网络调用和治理成本。共享契约不能变成所有服务直接共享数据库。

SOA 的核心思想 Service-Oriented

服务通过总线解耦，总线承担路由/转换/编排

SOA 把『功能』提升为一等公民：每个服务自治、可复用、对外暴露标准契约（如 SOAP/WSDL）。ESB 负责协议转换、消息路由、服务编排，是集中式的中枢。

SOA vs 微服务

微服务可看作 SOA 思想在『去中心化、轻量化』方向上的演进

适用场景

  • 大型企业内部多系统互联互通（ERP/CRM 对接）。
  • 需要统一治理、审计、协议转换的合规场景。
  • 遗留系统封装暴露为服务。

面试高频问答

Q：ESB 是银弹吗？
A：不是。ESB 容易变成中心化瓶颈与『上帝组件』，逻辑全堆在总线里反而难维护；微服务因此提倡『智能端点、哑管道』，把逻辑下沉到服务。
Q：SOA 和微服务的本质区别是什么？
A：治理哲学不同：SOA 强调集中治理与复用，微服务强调去中心化与独立交付。技术细节（容器、REST）只是表象。

SOA 是微服务的「前辈」，ESB 是它的标志

SOA（面向服务的架构）主张把系统拆成可复用的服务，通过企业服务总线（ESB）集成。它与微服务共享「服务化」思想，但强调集中式治理与智能管道；微服务则倾向「去中心化治理 + 哑管道（dumb pipe）」。理解这个差别，就理解了两代服务化架构的演进。

服务可复用的业务能力单元，有明确契约
ESB企业服务总线：路由、转换、编排、协议适配
契约服务接口定义（WSDL、Schema），强调先契约后实现
治理集中式：统一注册、统一规范、统一管理
复用SOA 的核心目标之一是服务复用
编排ESB 或 BPM 负责把多个服务编排成流程
对比项SOA微服务
拆分粒度较粗，偏企业级服务较细，围绕业务能力/领域
集成方式ESB（智能管道，含路由转换编排）轻量协议（HTTP/gRPC）+ API 网关（哑管道）
治理方式集中式：统一注册、统一规范去中心化：各团队自治、各自技术栈
数据管理常共享数据库/企业级数据模型每个服务独立数据库（Database per Service）

失败原因ESB 成为瓶颈与单点、治理过重分布式复杂度、运维要求高

从 SOA 到微服务的演进逻辑

① ESB 为什么成了瓶颈

  • 所有集成逻辑集中在 ESB：路由、转换、编排、适配。
  • ESB 成为性能瓶颈与单点故障。
  • 改一个服务要动 ESB 配置，发布耦合。
  • ESB 团队成为瓶颈，业务等待。

② 微服务的应对

  • 哑管道：管道只负责传输，智能放在服务两端。
  • 去中心化治理：各团队自选技术栈与发布节奏。
  • 服务自治：独立数据库、独立部署。
  • 代价：分布式复杂度转移到服务自身（熔断、链路、一致性）。

③ SOA 留下来的遗产

  • 服务契约先行的思想（现在的 API First、OpenAPI）。
  • 服务注册与发现（现在的服务注册中心）。
  • 服务复用与治理的意识。
  • 编排 vs 编舞（Orchestration vs Choreography）的讨论。

④ 现在还该不该上 ESB

  • 一般不建议新建重量级 ESB。
  • 但「集成平台」的需求仍在：多协议适配、老系统集成。
  • 现代替代：API 网关 + 消息队列 + iPaaS 集成平台。
  • 关键是把「编排逻辑」从中间件移回服务，避免中心化瓶颈。

深入自检

SOA 和微服务最大的区别是什么？

核心是「集成与治理的方式」：SOA 用集中式 ESB 承载路由、转换、编排等智能逻辑，强调企业级复用与统一治理；微服务把这些智能放回服务自身，用轻量的 HTTP/gRPC 与消息通信，强调服务自治、独立部署与团队自治。粒度上微服务通常也更细。

为什么微服务强调「可复制优于复用」？

因为跨服务的代码复用会造成耦合：共享库一改，所有服务都要跟着升级发布，反而失去了独立部署的优势。微服务更倾向于容忍适度的重复（DRY 的边界是「服务内」），用「复制 + 各自演进」换取自治。共享的是契约（API），不是代码。

什么是编排（Orchestration）和编舞（Choreography）？

编排是「有一个中心协调者」指挥各服务按流程执行（如 ESB/BPM 或 Saga 协调器），优点是流程清晰、易监控；缺点是中心化、耦合。编舞是「各服务订阅事件自行响应」，优点是解耦、易扩展；缺点是流程散落、难追踪、难调试。现代微服务常按场景混用。

ESB 完全没有价值了吗？

不是。在「需要集成大量异构老系统」的场景（银行、电信、制造业），协议转换、报文映射、可靠投递这些能力仍有价值，只是现在更多由 API 网关、集成平台（iPaaS）、消息队列分别承担，而不是塞进一个中心化的 ESB。原则是：不要让集成中间件承载业务流程。

服务粒度怎么定才合适？

微服务没有统一标准，常用判断依据：① 是否能独立部署与扩缩；② 是否有独立的数据与团队；③ 改动频率是否相近（变化原因单一）；④ 拆开后的分布式成本是否值得。经验上先从「较粗」开始，随着边界清晰再拆——过早拆得太细会付出巨大的分布式代价。

从单体迁移到服务化该怎么走？

推荐渐进式：① 先模块化单体（清晰的模块边界与接口）；② 按「绞杀者模式」逐步剥离，新功能走新服务，老功能逐步迁移；③ 优先剥离变化频繁或资源特性不同的部分；④ 配套建设：服务发现、配置中心、链路追踪、发布与监控。切忌一次性重写——那是高风险的赌博。
