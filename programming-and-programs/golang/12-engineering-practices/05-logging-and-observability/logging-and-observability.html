实践

日志不是调试

日志服务于运行期可观测，不是开发期打印；避免打敏感字段，注意采样与成本。

⚠️ 别用 fmt.Println 做生产日志，既无级别也无结构，难以统一采集。

日志分几级，各自记什么

日志级别不是「重要程度」，而是「谁需要看、什么时候看」。定错级别，要么噪音淹没信号，要么出事时没有记录。

级别记什么面向谁量级
DEBUG排查所需的细节（参数、中间结果）开发排查大，默认关闭
INFO正常运行的关键节点（启动、关键动作）运维与研发中
WARN可自愈的异常（重试成功、降级生效）需要关注小
ERROR需要人介入的问题（依赖失败、数据异常）告警对象很小
FATAL无法继续运行，立即退出立即响应极少
ERROR 要可行动无法行动的错误不该是 ERROR。
WARN 是预警已经自愈但值得留意。
DEBUG 默认关需要时按环境或请求动态打开。
一条一事件不要把多个事件塞进一条日志。

最常见的错误：把「预期的业务失败」（如用户余额不足、参数错误）记成 ERROR。它是正常业务分支，应当用 WARN 或直接不记，只体现在指标里。否则错误日志会被稀释到毫无价值。

结构化日志与上下文传递

// 从请求入口就建立带上下文的 logger func middleware(next http.Handler) http.Handler { return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) { traceID := r.Header.Get("X-Trace-Id") if traceID == "" { traceID = newID() } logger := slog.Default().With( "trace_id", traceID, "path", r.URL.Path, "method", r.Method, ) ctx := context.WithValue(r.Context(), loggerKey{}, logger) next.ServeHTTP(w, r.WithContext(ctx)) }) } // 业务代码里取出来，自动带上全部上下文 logger := FromContext(ctx) logger.Info("order created", "order_id", id, "amount", amt) // 输出 // {"level":"INFO","msg":"order created", // "trace_id":"a1b2","path":"/api/orders", // "method":"POST","order_id":123,"amount":99.9}
trace_id 贯穿一次请求的所有日志可串起来
字段固定命名便于检索与聚合，别随意换名
敏感信息脱敏手机号、身份证、令牌要掩码
错误带上原因err 字段保留原始错误
耗时单独字段duration_ms 便于做分位统计
别用 fmt 拼接无法检索就无法分析

慢日志与错误上报

// 慢请求日志：只对超过阈值的请求记录详情 func SlowLog(next http.Handler, threshold time.Duration) http.Handler { return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) { start := time.Now() rw := &statusRecorder{ResponseWriter: w, status: 200} next.ServeHTTP(rw, r) d := time.Since(start) logger := FromContext(r.Context()) if d > threshold { logger.Warn("slow request", "duration_ms", d.Milliseconds(), "status", rw.status, "query", r.URL.RawQuery, ) } if rw.status >= 500 { logger.Error("server error", "status", rw.status) } }) }

日志采样

高频成功日志要采样，否则存储成本与写入开销都会失控。

  • 成功请求按比例采样（如 1%）
  • 错误与慢请求全量记录
  • 采样比例写进日志字段，便于还原真实量级

错误上报

日志之外还要有主动的错误收集。

  • panic 必须 recover 并上报
  • 上报要带堆栈与上下文
  • 同类错误要聚合，避免刷屏

日志滚动

应用一般只管输出到 stdout，由采集端负责落盘与轮转。

  • 容器化场景下直接写标准输出
  • 避免在应用里做文件切分
  • 注意 stdout 阻塞会拖慢服务

深入自检

日志应该记在出错的地方还是上层？

原则：要么记要么返回，不要既记又往上抛，否则一条错误在调用链上被记三四次。通常在「决定如何处理」的那一层记录，下层只负责包装错误并返回。

为什么结构化日志比文本日志好？

文本日志只能人肉 grep，结构化日志能被日志系统索引、聚合与告警。比如「按 trace_id 查一次请求的所有日志」「按 user_id 统计错误分布」，文本日志基本做不到。

日志会影响性能吗？

会。同步写磁盘、大量格式化、高频打点都可能成为瓶颈。做法：异步或缓冲输出、热路径降低级别、采样、避免在大循环里打点。

错误日志为什么会被稀释？

因为把预期内的业务失败也记成了 ERROR。正确做法是按「是否需要人介入」来定级别：参数校验失败是 INFO/WARN，依赖不可用才是 ERROR。

怎么判断日志够不够用？

做一次复盘演练：给定一个用户报障的 trace_id，能否在几分钟内还原这次请求的完整路径、参数与失败原因。做不到就说明缺关键字段或链路没串起来。

日志：级别、结构化与成本

级别用在哪线上策略
DEBUG排查期的详细信息默认关闭，支持按请求/按租户动态开启
INFO关键状态变更、启动/关闭、外部调用结果保留，但控制量
WARN可恢复的异常、降级、重试要能聚合告警
ERROR请求失败、依赖不可用必须带上下文与错误链
FATAL无法继续运行谨慎使用，避免一个请求的问题杀掉进程

Go 日志写法

// ✅ 结构化日志：字段化，可被检索与聚合
logx.WithContext(ctx).Infow("order created",
    logx.Field("order_id", id),
    logx.Field("uid", uid),
    logx.Field("amount", amount),
    logx.Field("cost_ms", cost.Milliseconds()),
)

// ❌ 字符串拼接：无法聚合，只能靠正则
log.Printf("order %d created by %d, amount %d", id, uid, amount)

// 采样：高频 INFO 日志按比例采样，避免打爆磁盘
if rand.Float64() < 0.01 {      // 1% 采样
    logx.WithContext(ctx).Infow("cache hit", logx.Field("key", key))
}

// 错误日志要带「链」而不是只带一句话
if err != nil {
    logx.WithContext(ctx).Errorw("create order failed",
        logx.Field("order_id", id),
        logx.Field("err", err.Error()),
    )
    return fmt.Errorf("create order %d: %w", id, err)   // %w 保留错误链
}

日志的三个硬成本：① 磁盘与存储费用（结构化日志比纯文本大 2~5 倍）；② 写入时的 CPU 与锁竞争（同步写尤其明显）；③ 采集/传输带宽。所以高频路径不要打 INFO，错误日志要防「风暴」（同一错误短时间内重复打印要合并计数）。

可观测三件套：指标、日志、链路

支柱回答什么典型工具关键实践
Metrics「有多快 / 有多少 / 有多满」Prometheus + Grafana用 RED（Rate/Error/Duration）看服务，用 USE（Utilization/Saturation/Errors）看资源
Logs「具体发生了什么」Loki / ELK结构化 + 关联 trace id
Traces「一次请求在哪里慢」OpenTelemetry + Jaeger跨服务透传 context，采样率按流量调

Prometheus 要点

# Prometheus 的四种指标类型（选错类型是最常见的坑）
Counter     累计值，只增（请求总数、错误总数）—— 用 rate() 求速率
Gauge       可增可减（当前连接数、队列长度）
Histogram   分桶统计（耗时分布）—— 可算分位数，但桶边界要提前定
Summary     客户端算分位数 —— 不能跨实例聚合，聚合场景别用

# 最常用的几条 PromQL
rate(http_requests_total[5m])                       # QPS
sum(rate(http_requests_total{code=~"5.."}[5m]))
  / sum(rate(http_requests_total[5m]))              # 错误率
histogram_quantile(0.95,
  sum(rate(http_request_duration_seconds_bucket[5m])) by (le))   # P95 延迟

# 坑：rate() 的区间要 >= 4 倍抓取间隔（15s 抓取 -> 至少 [1m]）
  • 黄金四指标：延迟（Latency）、流量（Traffic）、错误（Errors）、饱和度（Saturation）。告警优先级：错误 > 饱和度 > 延迟 > 流量——流量本身不该告警。
  • 指标基数爆炸：把 user_id、url 路径原始值当 label 会让时间序列数暴涨，Prometheus 内存吃不消。高基数维度只放日志和链路里。
  • 链路采样：全量采样成本高，常用「头采样 1% + 错误/慢请求全采」的组合策略。
  • 告警要有可操作性：没有对应处理手册的告警等于噪音，应该删掉。
日志和指标的分工？

指标回答「系统整体怎么样」，用于趋势和告警；日志回答「这一次具体发生了什么」，用于定位。能从指标算出来的东西（如 QPS）不要用日志统计。

为什么 P95 要算分位数而不是平均值？

平均值会被大量快请求拉平，掩盖长尾。P95/P99 才反映真实用户感知，而且分位数不会被「大多数请求很快」所掩盖。

trace id 怎么贯穿全链路？

入口生成（或从上游 header 取），放进 ctx，跨服务通过 HTTP header / gRPC metadata 透传，每个服务的日志都带上它。OpenTelemetry 已经把这些标准化了。
