01 · 从问题出发

为什么会需要这个模式？

导出流程固定，但 PDF 与 CSV 的创建细节不同；每加一种格式就修改流程，分支会不断增长。

假设导出器已有 PDF、CSV 两种格式。下个月要接入 HTML，业务流程其实仍是“准备数据→导出→返回文件”。如果流程直接 new 具体导出器，每次加格式都要进入流程函数改条件，还可能忘记异常处理或日志。

😵 直接写会怎样

function exportReport(format, data):
  if format == "pdf": exporter = PdfExporter()
  else if format == "csv": exporter = CsvExporter()
  // 新增格式时继续改这里
  return exporter.export(data)

💡 关键转折

父类定义使用产品的流程和创建入口；子类只负责决定创建哪种具体产品。

将“哪个类被创建”的选择从通用流程里抽出去。每个具体创建者覆盖 createExporter，run 仍只面向 Exporter。

04 · 从图到代码

最小伪代码：把变化留在正确的位置

interface Exporter { export(data) }
abstract class ExportCreator {
  abstract createExporter(): Exporter
  run(data) { return this.createExporter().export(data) }
}
class PdfCreator extends ExportCreator {
  createExporter() { return new PdfExporter() }
}

读代码时抓住三件事

  1. Exporter 是产品契约：run 只调用它承诺的方法。
  2. createExporter 是变化点：由子类决定产品类型。
  3. run 是不变骨架：日志、错误处理和返回方式可统一放这里。

换个业务场景，还能认出来吗？

UI 框架中的 DialogCreator 可以统一执行 show() 流程，WindowsDialogCreator 和 WebDialogCreator 分别创建原生或网页对话框。识别关键：创建者子类决定一种产品，后续流程只看产品接口。

05 · 用对边界

什么时候用，什么时候收手？

判断信号

产品类型会增加，但创建后使用产品的流程稳定

三个具体场景

  • 报表导出扩展 PDF、CSV、HTML
  • 跨平台按钮创建后都执行 show
  • 插件为同一处理流程提供不同解析器

不适合或要小心

只有一个固定产品时直接构造更简单。与简单工厂相比，扩展点在创建者子类，而非一个不断变大的 switch。

产品固定且创建简单时，直接构造更清楚

最容易混淆的相邻模式

模式真正的区别
简单工厂通常在同一个函数用参数和 switch 选择具体类；新增产品会修改这个选择函数。
抽象工厂同时生产一整组相关产品；这里每次只通过一个工厂方法得到一种产品。

区分时问自己：变化的是一种产品的创建者，还是一整套相关产品？

落地前检查

  • 确认产品确实有稳定的共同接口。
  • 给新创建者做契约测试：所有产品都能执行 export(data)。
  • 如果只有固定一种产品，不要为消除一个 new 引入继承层次。
06 · 自己说一遍

两道检验理解的小题

新增 HTML 格式要修改 run(data) 吗？

不用；增加 HtmlCreator 和 HtmlExporter 即可。

如果要给每种格式增加统一的审计日志，应该放在哪？

放在创建者基类的 run 流程中；不要复制到每个 PdfCreator/CsvCreator。
