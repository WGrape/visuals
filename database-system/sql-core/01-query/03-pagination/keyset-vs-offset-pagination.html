深分页与游标分页：OFFSET 100000 为什么越来越慢

用按时间倒序的订单列表，推算跳过行成本，并解释并发插入后的重复与漏读。

两种分页回答同一个界面需求

订单列表每页 20 条，按创建时间倒序显示。常见写法是 `ORDER BY created_at DESC LIMIT 20 OFFSET 100000`：数据库要先定位有序结果的前 100020 条，再丢掉前 100000 条，才把最后 20 条交给页面。即使有合适索引，深处的 OFFSET 往往仍需要沿索引跳过大量条目；若还要回表读取宽列或排序未走索引，成本更高。不能只看到返回 20 行就推断数据库只处理了 20 行。

游标分页也称 keyset pagination：上一页最后一条是 `(created_at=10:00:00, id=900)`，下一页直接查询排序键小于该元组的行，按同一顺序取 20 条。索引可从游标附近继续扫描，成本更接近一页大小，但前提是排序键与谓词能一起利用索引。

图解：五条订单的两次翻页

沿箭头逐步核对输入、变换和输出；下面的推演可以逐步切换。

为什么要加唯一的第二排序键

很多订单在同一秒创建，若只按 created_at 排序，数据库可以任意排列同时间行。上一页最后一条时间为 10:00:00，下页只写 `created_at < 10:00:00`，会漏掉同一秒还没显示的订单；写 `<=` 又会重复上一页的若干订单。可用 `(created_at DESC, id DESC)` 建立稳定全序，下一页谓词是“时间更早，或时间相同且 id 更小”。某些数据库支持元组比较 `(created_at,id) < (?,?)`，但方言和 NULL 排序规则要核对。

若 ID 并非单调创建，也不影响它作为同时间的稳定 tie-breaker，只要唯一且排序固定。若 sort key 可以更新，某条记录可能在翻页期间移动位置，仍可能出现重复或遗漏；关键导出任务需要固定快照或记录高水位线。

并发插入怎样影响 OFFSET

第一页读取前 20 条后，有新订单插入排序最前面。第二页用 OFFSET 20，会先跳过“新订单 + 原第一页前 19 条”，于是原第一页第 20 条可能再次出现在第二页。这是位置偏移随数据变化的结果。游标根据上一页最后的排序键继续找更旧记录，新插在最前面的订单通常不会扰乱后续页，但它也不会在当前翻页会话里被看到；要刷新列表才能看到新记录。

游标分页并不自动提供完整一致快照。并发删除、排序键更新、权限变化仍会改变后续可见集合。如果要求“导出开始时的所有订单恰好一次”，需数据库快照、稳定水位或业务版本规则，并明确长事务的资源成本。

索引如何配合

对于 `WHERE tenant_id=? ORDER BY created_at DESC,id DESC`，可考虑以 tenant_id 开头、后接排序列的复合索引。游标谓词和排序方向要与索引能力相配；混合升降序、表达式排序、NULLS FIRST/LAST 在不同数据库中的优化不同。用 EXPLAIN 或实际执行统计比较扫描行数、排序节点、回表次数和延迟，而不是只凭 SQL 形式判断。

若需要精确跳到“第 5001 页”，游标方案没有天然的随机页码定位；可以保存里程碑游标、按时间区间跳转，或接受 OFFSET 的代价。产品界面通常更适合“下一页/加载更多”，而财务报表可能需要明确页码与稳定快照。两者可按用例分别选择。

三条查询的手算

假设排序后 id 依次为 105、104、103、102、101，页大小 2。第一页返回 105、104；此时新插入 106，序列变为 106、105、104、103、102、101。OFFSET 2 的第二页得到 104、103，重复 104。以第一页末尾 104 为游标，第二页查 id<104，得到 103、102。若 104 被删除，游标仍可按其记录的排序键继续，因为不需要再次找到 104 这行。

实际列表按 created_at、id 排序时，游标应同时携带两个值，而不是只携带 id。为防篡改或跨租户复用，可在应用层把排序字段、租户与过滤条件编码进受保护的游标，解码时验证它仍适用于当前查询。

常见误区

“加 LIMIT 20 就只扫描 20 行”忽略了 OFFSET；“按时间排序天然稳定”忽略了并列时间；“游标一定完全无重复漏读”忽略了更新和删除；“加一个索引就能解决所有深分页”忽略了扫描和回表。优化前用代表性数据量测试第 1 页、第 100 页和最深页，记录实际扫描行数及 P95。练习：上例新插入 id 106 后，分别列出 OFFSET 第二页和游标第二页，并解释为什么不同。
