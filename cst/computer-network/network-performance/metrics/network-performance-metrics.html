①一张图看懂：四个基础指标各在衡量什么

网络性能通常用四个指标衡量：带宽（链路最快能跑多快）、延迟（一个包要多久到）、吞吐量（实际每秒传了多少）、PPS（每秒能处理多少个包）。 它们的关系可以类比成一条运货公路：带宽是路有多宽、延迟是路有多长加堵不堵、吞吐量是实际每小时过去了多少货、PPS 是收费站每小时能放行多少辆车。

带宽 Bandwidth

链路的最大传输速率，单位 b/s（比特/秒）。它是物理/协议上限，不是实测值。

延迟 Latency

数据从发出到收到响应所需的时间。不同场景含义不同：TCP 建连耗时、一个包往返耗时（RTT）等。

吞吐量 Throughput

单位时间内成功传输的数据量，单位 b/s 或 B/s。受带宽限制，也受延迟、窗口、丢包影响。

PPS

Packet Per Second，以包为单位的传输速率，衡量系统对包的转发能力。小包场景下它才是瓶颈。

②带宽 vs 吞吐量：100M 宽带为什么只有 12.5MB/s

第一坑：b 和 B 差 8 倍。b/s 是比特每秒（网络设备口径），B/s 是字节每秒（我们习惯的下入口径）。 1 B = 8 b，所以 100 Mbps ÷ 8 = 12.5 MB/s —— 这就是运营商的「100M」到你手里只剩 12.5MB/s 的原因，不是被偷了带宽，是单位不同。

PPS 也会成为独立瓶颈。很多设备标称「10Gbps」，但那是指大包（1500 字节）下的带宽；如果流量全是 64 字节小包， 受限于每秒能处理多少包（PPS），实际带宽可能只有标称的十分之一。所以压测时一定要区分「大包带宽」和「小包 PPS」。
怎么判断瓶颈是不是 PPS？看包大小：若 吞吐(Mbps) ≈ PPS × 包长(bit) 且 PPS 已经打满设备标称值，说明被 PPS 限死， 此时加大带宽没用，要减少包数量（合包、加大 MSS）或换更强的转发设备。

③延迟拆解：一个包在路上花掉的四段时间

端到端时延不是一个整体，而是四段相加（Kurose & Ross 的经典模型）： 总时延 = 发送时延 + 传播时延 + 处理时延 + 排队时延。 前两个有公式能算，后两个取决于设备状态和网络拥塞，只能实测。
两个公式要分清：
发送时延 d_trans = 数据长度 L (bit) ÷ 发送速率 R (bit/s) —— 只和包大小、带宽有关，和距离无关。
传播时延 d_prop = 距离 D (m) ÷ 传播速率 s (m/s) —— 只和距离、介质有关，和包大小无关。
介质传播速率参考值说明
自由空间（无线电）≈ 3.0×10⁸ m/s即光速
光纤≈ 2.0×10⁸ m/s约 2/3 光速（信号在介质中走的是曲折路径）
铜线（双绞线/同轴）≈ 2.3×10⁸ m/s不同资料 2.3～2.6×10⁸ 不等

为什么要关心「哪一段占主导」？因为它决定你该优化什么：
  • 大文件传输慢 → 多半是发送时延主导（包多、带宽小）→ 加带宽最有效
  • 跨地域访问慢 → 多半是传播时延主导（距离远，物理极限）→ 只能靠 CDN / 就近接入，加带宽没用
  • 高峰期卡顿 → 多半是排队时延主导（拥塞）→ 优化调度、限流、扩容
RTT（往返时间）才是应用最常感知的量：它约等于一来一回的传播时延 + 途经设备的处理/排队时延， 用 ping 就能直接得到。北京↔上海光纤约 1300km，单程传播时延 ≈ 6.5ms，所以 RTT 下限约 13ms —— 这是物理决定的，优化软件改变不了。

④时延带宽积 BDP：管道再粗，也会被“距离”拖住

时延带宽积 BDP = 带宽 × RTT，物理意义是「这条链路上同时最多能装多少数据（在途字节数）」，也叫「以比特为单位的链路长度」。 它是滑动窗口和缓冲区大小的下限：窗口小于 BDP，链路就跑不满。
窗口受限吞吐 = 窗口大小 ÷ RTT（窗口单位是字节，RTT 是秒，结果乘 8 得 b/s）。
TCP 头部窗口字段只有 16 位，不开启窗口缩放时上限 64KB（65535 字节）。所以： 64KB ÷ 100ms ≈ 5.2 Mbps —— 哪怕你接的是 1Gbps 的线路，单条连接也只能跑到 5Mbps 左右。

⑤丢包率与重传率：TCP 吞吐的隐形杀手

TCP 把「丢包」当成「网络拥塞」的信号：一丢包就把拥塞窗口砍半、进入慢启动。 于是丢包率对吞吐的影响不是线性的，而是「随丢包率的平方根成反比」——这就是 Mathis 公式给出的结论。
Mathis 公式（丢包受限吞吐上限）：
吞吐 ≈ (MSS ÷ RTT) × (1.22 ÷ √p)  其中 MSS 为段数据长度（以太网常用 1460 字节），p 为丢包率（0～1）。
1.22 这一常数来自对 TCP Reno 拥塞避免阶段的分析（Mathis 等，1997）。
注意：上图的绝对数值取决于 MSS 与 RTT，不要当常量背。记住的是规律： 丢包率翻 4 倍，吞吐大约减半；反过来，把丢包从 2% 降到 0.1%，吞吐可提升一个数量级。 一个 0.1% 的坏光纤接头，就足以让跨洋备份任务从 1Gbps 掉到几 Mbps。

丢包率和重传率要一起看。丢包率是「发出去没到的比例」，重传率是「重传的包占比」。 如果重传率明显高于丢包率，说明有大量「其实到了却被判定丢掉」的伪重传（乱序、超时设置过短），白白浪费带宽； 如果重传率 ≈ 丢包率，则是真实链路丢包，该去查线路/中间设备。

⑥另外四个常用指标：可用性 / 并发连接数 / 丢包率 / 重传率

网络可用性

表示网络能否正常通信。常以「几个 9」衡量：99.9% 意味着一年可中断约 8.76 小时，99.99% 约 52.6 分钟，99.999% 约 5.26 分钟。

并发连接数

同时保持的 TCP 连接数量。服务端受限于端口资源、文件描述符、内存与半连接队列；这是「能同时服务多少人」的直接体现。

丢包率

所丢失数据包数量占所发送数据组的比率。是延迟与吞吐恶化的源头，也是链路质量最直观的信号。

重传率

重传包占发送包的比例。TCP 层每次重传都要等一个 RTT 左右，重传率高会同时抬高延迟、压低吞吐。

可用性不是「通/不通」这么简单。严格来说它要定义清楚：是「能 ping 通」还是「业务可用」？ 常见做法是按请求成功率 × 时间算，并区分「完全不可用」与「部分降级」（比如成功率从 99.9% 掉到 95% 就该告警了）。

⑧指标不是孤立的：一条典型的恶化因果链

线上「网络变慢」往往不是单一指标异常，而是一条链。看懂因果，才知道该先按住哪一个。
诊断顺序建议：先看利用率（是不是真的跑满了）→ 再看丢包/重传（是不是链路有问题）→ 再看延迟构成（是带宽、距离还是排队）→ 最后看主机侧（网卡丢包、CPU 软中断）。 很多人一上来就怀疑「带宽不够」，但真实原因常常是丢包或对端应用慢。

⑩面试与实战速查

Q1：带宽和吞吐量有什么区别？
带宽是链路理论最大传输速率（恒定属性，单位 b/s）；吞吐量是实际成功传输的数据量（随时间波动）。 吞吐量 ≤ 带宽。两者常被混用，但一个是「上限」、一个是「实测」。
Q2：为什么 100M 宽带下载只有 12.5MB/s？
因为 b（比特）和 B（字节）差 8 倍。100 Mbps ÷ 8 = 12.5 MB/s。运营商标的是比特，下载工具显示的是字节。
Q3：网络时延由哪几部分组成？各自和什么有关？
总时延 = 发送时延 + 传播时延 + 处理时延 + 排队时延。
发送时延 = 包长 ÷ 带宽（与距离无关）；传播时延 = 距离 ÷ 传播速率（与包大小无关，光纤约 2×10⁸ m/s）； 处理时延看设备性能（μs 级）；排队时延看拥塞程度（可能暴涨）。
Q4：为什么跨地域访问慢，加带宽没用？
因为瓶颈是传播时延（物理距离决定，北京↔上海单程约 6.5ms，跨洋上百 ms），加带宽只提升「每秒能塞多少」，不改变「多久到」。 正确做法是 CDN、就近接入、边缘计算——把内容搬到离用户近的地方。
Q5：什么是时延带宽积（BDP）？有什么用？
BDP = 带宽 × RTT，表示链路上「在途」的最大数据量。它决定了滑动窗口与缓冲区的最小值：窗口小于 BDP，链路就跑不满。 高带宽长距离链路（LFN）必须开窗口缩放并把缓冲区调到 ≥ 1 个 BDP。
Q6：为什么 0.1% 的丢包就能让 1G 链路掉到几 Mbps？
TCP 把丢包当拥塞信号，一丢包就砍半窗口。Mathis 公式 吞吐 ≈ (MSS/RTT) × 1.22/√p 表明吞吐与丢包率的平方根成反比， 所以微小丢包会被急剧放大。跨洋链路上一个坏接头就能造成这种效果。
Q7：PPS 和带宽，什么情况下 PPS 先成为瓶颈？
小包场景。设备标称带宽通常是 1500 字节大包下的值；当流量全是几十字节的小包时，受每秒包处理能力限制， 实际带宽可能只有标称的零头。判断方法：看 吞吐 ≈ PPS × 包长 是否成立且 PPS 已打满。
Q8：只看平均延迟够不够？
不够。平均值会掩盖长尾：99 个请求 10ms、1 个 3s，平均只有 40ms，但用户体验由最慢的那些决定。 所以要看 P95 / P99 分位数，实时场景还要看抖动 Jitter（延迟波动）。
Q9：服务端「网络慢」，怎么判断是不是真的网络问题？
按顺序排查：① ip -s link 看网卡 dropped 是否增长（主机侧）；② ss -ti 看 cwnd/RWND—— 若 RWND 很小或出现零窗口，瓶颈在对端应用而不是网络；③ 看带宽利用率是否真的接近打满； ④ 抓包看是否有大量重传/RST。很多「网络慢」最后都指向应用层。
Q10：可用性「几个 9」分别对应多少停机时间？
99.9% ≈ 8.76 小时/年；99.99% ≈ 52.6 分钟/年；99.999% ≈ 5.26 分钟/年。 注意先定义清楚口径（是能 ping 通，还是业务请求成功率达标）。

✓一句话速记

带宽是上限、吞吐是实测（差 8 倍是 b 与 B）；延迟拆四段——发送看包长与带宽、传播看距离与介质、处理看设备、排队看拥塞； 管道粗不等于跑得快，窗口要 ≥ 时延带宽积 BDP；丢包对吞吐是「平方根级」打击（Mathis 公式），0.1% 就足以毁掉一条长肥管道； 看指标别只看平均值，要看 P95/P99 与抖动；而且别急着怪网络——网卡丢包、CPU 软中断、对端零窗口都可能是真凶。
