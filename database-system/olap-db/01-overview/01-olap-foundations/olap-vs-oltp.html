一句话总结：OLTP 是「一行一行的增删改」，OLAP 是「一列一列的聚合」。 前者优化点写延迟，后者优化批量扫描吞吐。两者对数据布局的要求天然冲突， 所以现代架构一定会把它们拆开——用 CDC 把 OLTP 的数据同步到 OLAP 引擎再算。

01两种不同的 workload

同一个业务，两类查询的访问模式完全不同。理解这张表，后面所有设计取舍都顺理成章。

维度OLTP（在线事务处理）OLAP（在线分析处理）
典型场景下单、支付、扣库存日报、留存、漏斗、大盘看板
读写比读写均衡，单行操作几乎只读，批量导入
单次涉及行数几条～几百条百万～百亿条
涉及列数整行（SELECT *）少数几列（SELECT SUM(amount)）
延迟要求毫秒级，要求稳定 P99秒～分钟级可接受
数据时效当前最新状态历史全量 + 追加
代表产品MySQL、PostgreSQL、OracleClickHouse、Doris、StarRocks
图 1：OLTP 用索引精确定位一行；OLAP 扫描整列做聚合——访问模式的根本差异
Q：为什么大表上跑 SELECT COUNT(*) 或全量报表会把 MySQL 拖垮？
A：这类查询会把几千万行的整行长数据（含你根本不 SELECT 的字段）从磁盘读入内存， 还要占用大量 buffer pool，把业务热点页挤出去。同一份数据在行存引擎里， OLAP 读到的无用字节比有用字节多几十倍。所以规则很简单——分析查询不要跑在主库上。

02行存 vs 列存：布局决定性能

这是 OLAP 引擎最核心的一个设计决定。同样的数据，两种排布方式的 IO 量天差地别。

图 2：列存把同字段的值物理上连续存放，分析查询的无效 IO 大幅下降

量化看差距

假设一张 20 列的表共 1 亿行，查询只用到其中 3 列：

方案需要读取的数据量相对代价
行存全表扫描20 列 × 1 亿行1×
行存 + 覆盖索引3 列 × 1 亿行（但索引本身有维护成本）≈0.2×
列存3 列 × 1 亿行，且压缩后通常再小 5～10 倍≈0.02×

这就是为什么 ClickHouse 能在单机上秒级扫描几十亿行——省掉的 IO 不是一个数量级的差别。

03压缩与向量化执行

列存还带来两个额外红利，这是它比"行存 + 覆盖索引"更优的关键。

🗜️ 极高压缩比

同列数据类型一致、值域相似，极易压缩。常用手段：字典编码（city 只有几十个值 → 存成整数）、 RLE 游程编码（排序列连续相同值 → 存「值 + 重复次数」）、Delta 编码（时间戳存差值）、位图。

压缩不只是省磁盘——它直接减少磁盘 IO 和内存带宽，这才是分析查询的瓶颈所在。

⚡ 向量化执行

行存引擎通常「一次处理一行」的火山模型，函数调用开销巨大。 列存可以一次处理一批（一个 Block，通常 8192 行）： 循环内没有分支判断、数据类型已知、函数单行执行，CPU cache 命中率极高，还能吃到 SIMD 指令。

这是 ClickHouse 得名的原因（Click + House = 点击即出结果的数仓）。

关键直觉：分析型查询的瓶颈几乎从不在 CPU 计算，而在「把数据从磁盘搬进 CPU」的路上。 列存 + 压缩 + 向量化，三件事都是在砍这条搬运链路上的开销。

04MPP：把一台机器扩展到多台

单节点列存再快也有上限。MPP（Massively Parallel Processing，大规模并行处理）的思路是： 数据分片存、查询并行算。

图 3：MPP 架构——每个 Worker 只扫自己本地的数据分片，结果再汇总

MPP 的两类 JOIN 策略

策略做法适用场景
广播 JOIN把小表全量发到所有 Worker，本地 JOIN事实表 ⋈ 维表（维表很小）
Shuffle JOIN两边都按 JOIN KEY 哈希重分布，相同 key 落同一节点大表 ⋈ 大表
Colocate JOIN预先按相同 key 分 shard，本地 JOIN 不需网络Doris/StarRocks 的分桶表

面试常问的优化点：大表 JOIN 时务必让数据先按 key 分布好，把 shuffle 的网络开销降到零。

05OLAP 侧的数据模型

ROLAP（关系型）里最常见的两种建模方式：

⭐ 星型模型 Star Schema

一个事实表（订单、点击流）+ 多个维表（用户、商品、时间）。 维表只连一层，JOIN 简单直观，绝大多数场景首选。

❄️ 雪花模型 Snowflake

维表再往下规范化拆分（商品 → 品类 → 大类）。 省存储但 JOIN 层级变多。列存时代存储不值钱，通常倾向反规范化回星型。

📦 宽表 Denormalized

把维表字段全部打平到一张大宽表里，查询时零 JOIN。 ClickHouse / Doris 常见做法，用写入期的冗余换查询期的极速。

🧊 Cube 预聚合

按维度组合预先算好所有聚合结果（Kylin 为代表）。 查询不用扫明细，直接查 cube。代价是维度爆炸与数据膨胀。

实践趋势：宽表 + 物化视图正在取代传统 Cube。OLAP 引擎本身够快， 与其维护昂贵的预聚合，不如让引擎实时算，运维复杂度低得多。

Q：能不能一个数据库同时扛 OLTP 和 OLAP？
A：HTAP（混合事务分析处理）正是这个目标，TiDB、PolarDB 都在做，常见做法是 用两套引擎 + 日志实时同步（行存主副本 + 列存只读副本）而不是一套引擎硬扛。 实践中资源隔离是关键——否则一个大查询就能把交易链路拖慢。
