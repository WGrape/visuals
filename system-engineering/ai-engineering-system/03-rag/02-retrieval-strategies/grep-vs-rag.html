代码检索：何时用 grep，何时用 RAG？

按查询类型、仓库规模、更新频率和延迟要求选择检索方式

代码检索的核心需求

代码 ≠ 自然语言文档。代码有它特殊的检索属性：

已知符号
精确匹配
功能意图

关键洞察：查找已知函数名、变量名和类名时，精确匹配通常是第一步；若只知道“哪里处理登录失败”这类意图，语义检索或多轮关键词搜索也可能有用。
精确检索示例

grep -rn "getUserById" --include="*.ts"
grep -rn "import.*AuthService" --include="*.ts"
grep -rn "shell/" --include="*.md" --include="*.json" --include="*.js" | grep -v ".git"

grep 只做一件事：字符串匹配。但配合 LLM 的推理能力，效果出奇地好。

仅靠向量检索时要处理的三个问题
缺陷一：向量化会丢失精确符号
embedding 可能把不同符号映射到相近向量；已知符号和调用关系仍需关键词或结构化检索核对。
缺陷二：索引构建成本高且过期快
代码变更后要维护索引新鲜度，构建与更新成本取决于仓库规模、切分方式和增量更新能力；直接搜索当前文件无需预建索引。
缺陷三：检索粒度难以控制
代码按行、函数或文件切分，各有上下文取舍；召回后仍需读取完整定义及调用方。关键词搜索通常能直接给出文件和行号。

grep 方案

  • 零构建成本，随用随搜
  • 延迟取决于仓库大小与搜索范围
  • 符号匹配确定，但同名结果仍需核对
  • 天然支持正则表达式
  • 文件变化实时可见
  • 返回行号，可精确读取上下文
  • 不依赖任何额外基础设施

RAG 方案

  • 需要检索索引和更新机制
  • 建索引有前置成本
  • 可能返回语义相近但错误的结果
  • chunk 切分策略复杂
  • 索引实时性难保证
  • 可保留文件和位置元数据，仍需核对源码
  • 依赖 embedding 模型质量

工程哲学总结

已知名称或调用点时，先用关键词和结构化检索定位；自然语言意图较模糊、仓库较大且索引可保持新鲜时，可补充语义召回。两种方式可以组合，最终都要读取当前源码验证。

选型回答：三个判断维度

面试官问这题，真正想考察的是你对"工具与问题匹配"的判断力，而不是 RAG 知识本身。

第一层：代码的本质决定检索策略

已知函数名、类名或变量名时优先精确搜索；只有功能描述而不知道符号时，语义检索可以帮助找候选。

第二层：工程成本与实时性

比较仓库变化频率、增量索引能力、查询并发与延迟目标。直接搜索读取当前文件；索引检索要付出构建和同步成本。

第三层：LLM 已经替代了 RAG 的"语义桥"角色

LLM 可推断关键词并迭代搜索，也可结合语义召回与调用图。无论哪种方案，回答或修改代码前都要打开当前文件核实。

延伸：大型代码库的 Code RAG 方案；Claude Code 的本地检索工作流。

先量化：两种检索的真实开销对比

维度grep / ripgrep向量检索 (RAG)
建立索引0（每次实时扫）需预先 embedding，变更即失效
单次查询耗时0.1 – 3 s（千万行仓库）20 – 200 ms（不含生成）
准确率（精确匹配）100%（字面一致必然命中）语义近但可能漏掉精确项
召回（同义/模糊）差：换个词就搜不到好：语义相近能召回
成本仅 CPUembedding 费用 + 向量库常驻内存
代码变更敏感度无，天然实时索引滞后，需增量重建
可解释性有：能看到文件行号弱：只给相似度分数

核心结论：代码是精确符号系统——函数名、类型、错误字符串都是字面量，grep 的精确匹配恰好是最优解；而 RAG 的模糊语义在代码场景反而会引入噪声。这就是 Claude Code、Cursor 等工具把 Glob + Grep 作为主力检索手段、而非全仓库 embedding 的原因。

ripgrep 为什么比 grep 快一个数量级

  • 并行遍历：多线程递归目录（grep -r 是单线程）
  • 尊重 .gitignore：默认跳过 node_modules、.git 等，扫描量直接少 90%
  • SIMD 加速：用 memchr 向量化指令找首个候选字节
  • 自动跳过二进制：不用手动 --binary-files=without-match
  • 内存映射 + 顺序读：大文件处理更高效

ripgrep 实战命令

# 实测对比（Linux 内核源码，约 7 万文件 / 1.1 GB）
time grep -r "tcp_retransmit_skb" .          # 约 8 - 15 s
time rg "tcp_retransmit_skb"                 # 约 0.3 - 0.8 s   -> 快 10-20 倍

# 只搜特定类型（关键！能再快一个数量级）
rg -t go "func HandleOrder"                  # 只看 .go
rg -g '*.{ts,tsx}' "useEffect"               # glob 过滤
rg --files -g '*.py' | wc -l                 # 先摸清候选规模

# 只看定义 / 只要文件名（AI 助手最常见的两步）
rg -n "^func " -t go            # 列出所有函数定义（带行号）
rg -l "TODO|FIXME"              # 只要文件名，不输出内容（省 token！）

# 上下文控制：AI 场景下别把整个文件塞进上下文
rg -C 3 "func HandleOrder"      # 前后各 3 行
rg -A 10 -B 2 "panic"           # 后 10 行前 2 行

# 统计与聚合（判断改动范围）
rg -c "HandleOrder"             # 每个文件命中次数
rg --stats "pattern"            # 看扫了多少字节/文件

AI 编程助手的关键技巧：先用 rg -l 拿文件列表，再用 rg -n 精确定位行号，最后只读取相关行区间。比把整个文件塞进上下文省 10 – 100 倍 token。

那 RAG 在代码场景就没用了吗？——两阶段混合才是正解

不是没用，而是用错了位置。正确的分工是：

阶段手段候选规模目的
① 粗筛（召回）grep / 符号索引全仓库 → 50 – 200 个文件零成本、精确、实时
② 精排（排序）embedding 相似度 / 重排模型200 → 5 – 10 个片段理解语义相关性
③ 读取（构造上下文）按行区间精确读取5 – 10 片段控制 token 预算

这个结构叫 retrieve-then-rerank。它的价值在于：粗筛用便宜且精确的字面检索兜住召回，精排用昂贵但聪明的模型提升准确性。反过来（纯向量召回）会漏，正过来（纯 grep）会排不准。

混合检索实现

# 混合检索的伪实现
def hybrid_search(query: str, repo: str, k: int = 10):
    # ① 关键词粗筛：字面精确 + 语义扩展词
    kws   = extract_keywords(query)            # "重试" -> ["retry", "retries", "Retry-After"]
    files = ripgrep_files(repo, kws)           # 全仓库 -> 约 100 个候选文件

    # ② 语义精排：只对候选打分（成本降 1000 倍）
    chunks = chunk_by_function(files)          # 按函数/类切块，100-200 行一块
    scores = rerank_model.score(query, chunks) # cross-encoder 精排

    # ③ 取 top-k 并控制预算
    return top_k(scores, k=k, max_tokens=8000)

# 为什么按函数切块而不是按固定长度切？
#   - 代码有天然边界（函数/类），固定长度会把半个函数切开
#   - 调用方看到半个函数无法理解语义
#   - 经验值：函数块 100-200 行，overlap 0（代码不需要 overlap）

成本账：为什么全仓库 embedding 不划算

项目规模代码行数token 估算一次性 embedding 成本索引重建频率
小项目10 万行约 400 万约 $0.02（每次 commit
中型100 万行约 4000 万约 $0.2 – $1每次 commit
大型 monorepo1000 万行约 4 亿约 $2 – $20持续

算账逻辑：代码 1 行 ≈ 4 token。monorepo 每天几百次 commit，索引永远处于“正在重建”的状态，新鲜度无法保证——这是比钱更要命的问题。而 grep 的“索引”就是文件系统本身，永远是最新的。

  • grep 的隐性优势：无需运维向量库、无需 GPU、无冷启动、离线可用
  • 向量检索的不可替代场景：自然语言提问（“哪里处理了支付失败？”）、跨仓库、缺乏明确符号名
  • 折中方案：只对文档、注释、测试用例做 embedding（语义密度高），代码本体用 grep

深入自检

grep 找不到同义词怎么办？比如搜“取消”找不到 cancel？

这是 grep 的真实短板，有四种解法：① 查询扩展——用一次 LLM 调用把中文查询转成多个英文候选词（取消 → cancel / abort / revoke / terminate），再逐个 grep；② 正则：rg 'cancel|abort|revoke'；③ 符号索引（LSP / ctags）——按语义符号查找定义与引用，比文本更准；④ 兜底用 grep 到文件名后再读目录结构推测。实践中 ①②③ 组合已能覆盖绝大多数情况。

为什么 AI 助手不全量读代码而是要搜？

因为上下文窗口是硬约束。即使 200k token 的窗口，一个中型仓库的全部代码也远超这个量级（100 万行 ≈ 400 万 token，是窗口的 20 倍）。而且塞得越多，注意力越分散——无关代码会稀释模型对关键部分的关注，导致回答质量下降。所以“精准检索 + 少量上下文”不仅省钱，还更准。

RAG 在代码场景下什么时候明显更好？

三种情况：① 自然语言意图查询（“这个项目怎么做鉴权的？”）——没有可 grep 的符号名；② 跨仓库 / 跨服务理解业务流程；③ 大规模重构影响面分析，需要理解语义关联而非字面。除此之外（定位符号、找定义、查调用点、搜错误字符串）grep 全面占优。

能不能用 AST 索引替代文本 grep？

能，而且更准——这是 LSP（Language Server Protocol） 的做法：解析出 AST 后按符号精确查找定义/引用/实现，不受注释和字符串干扰。代价是需要为每种语言维护解析器、且要增量重建索引。所以现实中的层次是：LSP 符号索引（最准，需维护） > grep（次准，零成本） > 向量检索（模糊，兜底）。Claude Code 等工具会同时用 grep 和 LSP 能力互补。
