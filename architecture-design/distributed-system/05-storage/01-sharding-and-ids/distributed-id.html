分布式 ID 生成

分库分表后，数据库自增 ID 不再全局唯一。需要一个全局唯一、趋势递增、高吞吐、低延迟的 ID 方案——这就是分布式 ID 生成要解决的问题。

核心需求 常见方案 雪花算法 时钟回拨 号段模式 面试要点

📋 一、好的分布式 ID 要满足什么

全局唯一
跨机器、跨时间不冲突。
趋势递增
利于 B+ 树索引、避免页分裂。
高性能
本地生成、不依赖网络。
高可用
生成器本身不能成为单点。
可排序
ID 隐含时间，便于排查。

🧰 二、常见方案对比

方案唯一性递增依赖缺点
UUID极高❌ 无序无长、无序、索引碎片
数据库自增（步长）依赖 DB✅DB性能瓶颈、扩容难
Redis INCR依赖 Redis✅Redis需持久化防丢失
号段（Leaf-segment）中心分配✅DB/缓存需做好号段缓存
雪花算法机器+时间✅ 趋势时钟时钟回拨问题

❄️ 三、雪花算法（Snowflake）— 面试重点

Twitter 提出的 64 位 Long 型 ID，把一个 ID 拆成"时间戳 + 机器号 + 序列号"三段，本地即可生成，无网络依赖。

生成逻辑：ID = (当前毫秒 - 纪元) << 22 | 机器ID << 12 | 同一毫秒内自增序列号。同一毫秒内序列号用满则"等下一毫秒"。
✅
优点：纯本地计算、QPS 极高（单机能到百万级/秒）、ID 含时间可排序、不依赖中心服务。

⏰ 四、时钟回拨问题（面试必问）

雪花算法依赖"时间单调递增"。如果机器时钟因为 NTP 校准等原因往回拨，可能生成和"过去"重复的 ID。

⚠️
常见应对：① 检测到回拨 < 阈值（如 5ms），短暂等待/自旋到时间追平；② 回拨较大时，借用"备用机器位"或扩展序列号区间补偿；③ 用 ZooKeeper/etcd 记录上次时间，回拨则拒绝并报警；④ 美团 Leaf、百度 UidGenerator 等改进版用"缓存时钟/历史时间"规避。

📦 五、号段模式（Leaf-segment）

另一种思路：由一个中心服务一次性"批发"一段 ID 区间（号段）给应用，应用在内存里自增发号，发完再取下一段。

DB 存当前最大号 max_id
每次取号段 [max_id+1, max_id+step]，原子更新 max_id。
应用本地自增发号
号段内纯内存自增，性能高；号段用尽前异步预取下一段，避免卡顿。
优点
对时钟不敏感、DB 压力小（几百次/天级更新）。缺点：号段耗尽瞬间若 DB 慢会短暂阻塞。

🎯 六、面试高频追问

为什么不用 UUID？
UUID 128 位太长、完全无序，作为 InnoDB 主键会导致 B+ 树频繁页分裂、索引碎片严重、查询变慢。趋势递增的 ID 对索引更友好。
雪花 ID 如何保证不重复？
时间戳保证"不同毫秒大概率不同"；同一毫秒内靠机器 ID 隔离 + 序列号自增，三者组合全局唯一。关键是机器 ID 不冲突（靠配置中心/启动注册分配）。
分片键能和 ID 结合吗？
可以。把分片号编入 ID 高位（如机器 ID 段映射到分片），取 ID 即可定位分片，省去路由表（见数据分片）。

好 ID 的五个要求

单机时代用数据库自增就够了。一旦分库分表、多机房、多实例，「生成全局唯一的 ID」就变成一道必须专门设计的题。

全局唯一最底线：任何两台机器同时生成也不能撞。
趋势递增这一点常被忽略 —— 它决定了做主键时索引是否友好。
高可用发号服务挂了，整个下单链路就断了。
高性能每次生成一个 ID 都走一次 RPC 会成为瓶颈。
不泄露信息连续自增的订单号会暴露业务量，也可能被遍历。

其中第二点最关键：如果 ID 完全随机（如 UUID v4），把它当主键会让 B+ 树频繁页分裂、写入变成随机 IO；如果是趋势递增，插入几乎总是追加在最右侧 —— 这个差别能让写入吞吐差出好几倍。

四种主流方案

方案原理优点缺点
数据库自增单点自增列简单、严格递增单点瓶颈、暴露业务量、扩展性差
UUID / ULID本地生成，无需协调零协调、零依赖UUID v4 无序（索引不友好）；长度大
号段（Segment）服务一次取一段号在本地发几乎零延迟、数据库压力极小号段用完需再取；重启会浪费一段；全局不完全递增
Snowflake时间戳 + 机器号 + 序列号趋势递增、本地生成、高性能强依赖时钟；需要分配机器号
Snowflake 的经典 64 位布局 0 | 000...000 41位 | 00000 00000 10位 | 000000000000 12位 ↑ ↑ ↑ ↑ 符号位 毫秒时间戳 机器/数据中心 id 毫秒内序号 含义： · 41 位毫秒时间戳 ≈ 可用 69 年（相对某个起始时间） · 10 位机器号 = 最多约 1024 台机器 · 12 位序号 = 每毫秒每台机器可生成 4096 个 单机的理论上限：4096 × 1000 ≈ 每秒四百万个 —— 对绝大多数业务绰绰有余

为什么它够用又好用：时间戳在高位，因此整体趋势递增；其余位由机器号与序号填充，保证不冲突。生成过程完全没有网络调用，纯内存计算，极快。

时钟回拨：雪花算法唯一的硬伤

因为它靠「时间戳递增」保证趋势递增，一旦机器时钟往回跳，就可能生成重复 ID。触发原因包括：人工改时间、NTP 大幅度校准、虚拟机迁移或休眠恢复。

时钟回拨会直接导致 ID 重复

四种常见应对：

① 拒绝回拨就抛错，让上层重试或告警。最简单，但会影响可用性。
② 短暂等待回拨幅度很小（几十毫秒）时，sleep 到追上原时间再继续。
③ 换机器号检测到回拨就换一个 worker id，避开冲突。需要额外的分配机制。
④ 预留位 / 扩展时钟用「上次时间戳」兜底继续递增，接受 ID 暂时不再反映真实时间。

工程上最常见的组合：小幅回拨（如 100ms 内）等待，超过阈值直接报错并告警。同时把「时钟偏移」纳入监控 —— 这是运维雪花类服务必看的指标。

选型建议

场景推荐理由
订单号、流水号（要趋势递增）号段 或 雪花递增对索引与分库友好；号段实现更简单
内部对象 id（不需要递增）UUID v7 / ULID时间前缀让它也可排序，同时零协调
小规模系统，已有数据库号段模式复用现有 DB，实现成本低
多机房、需要严格性能雪花（含机器号规划）本地生成，无网络依赖
对外暴露的业务编号另建映射不要直接暴露内部 id，避免被遍历与推测业务量

一条经常被忽略的实践：把「发号」做成独立的基础服务而不是散落在各业务代码里 —— 这样时钟监控、机器号分配、号段回收、故障降级才有统一的地方处理。很多团队一开始图省事各写各的，最后出现 ID 冲突时才追悔莫及。

深入自检

UUID 真的完全不能当主键吗？

不是不能，而是要清楚代价：完全随机导致 B+ 树频繁页分裂、写入变成随机 IO、索引碎片多、占用空间也更大（36 字符）。如果数据量不大、写不频繁，问题不明显；一旦到千万级且写入频繁，差别会很明显。折中办法是用 时间有序的 UUID v7 / ULID，兼顾零协调与近似递增。

号段模式重启为什么会浪费 ID？

因为服务一次取了「1000~2000」这段，只在本地发出去 300 个就重启了，剩下的 700 个不会归还 —— 下次重新取一段。所以号段模式下 ID 会出现跳号，且跳的量与重启频率、号段大小有关。业务上通常可以接受（ID 只需唯一），但不要用 ID 的连续性做任何业务假设。

机器号怎么分配？

常见做法有三种：① 配置文件里写死（简单，但扩容要改配置）；② 启动时向注册中心/ZooKeeper/etcd 申请一个未被占用的号并续约；③ 用数据库自增或号段分配。无论哪种都要保证同一时刻不重复 —— 这是雪花算法唯一需要外部协调的地方。

ID 需要带业务含义吗（如时间、地区码）？

一般不建议把它塞进主键。业务含义会随时间变化（比如新增地区、业务线调整），而主键应该是稳定的。更常见的做法是主键保持纯技术 ID，业务属性放在单独的字段或一张映射表上；如果确实需要可读的业务编号，就单独生成，两者并存。
