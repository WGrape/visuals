🔗 硬链接 vs 软链接

硬链接（Hard Link）：两个目录项指向同一个 inode。删除任意一个，文件仍在（引用计数 > 0）。不能跨文件系统，不能链接目录。


软链接（Symbolic Link）：独立的 inode，文件内容是目标路径字符串。可以跨文件系统、可以链接目录。源文件删除后，软链接失效（悬空链接）。

# 硬链接 ln file.txt hardlink.txt ls -li # 同一 inode 号 # 软链接 ln -s /etc/hosts mylink readlink mylink # → /etc/hosts

VFS：一切皆文件的实现机制

VFS（虚拟文件系统）是 Linux 的“万能适配器”：上层（open/read/write）只面对统一接口，下层对接 ext4、XFS、NFS、overlayfs、procfs 等几十种具体文件系统。

VFS 四大对象含义对应磁盘/内存结构
super_block一个已挂载的文件系统文件系统元信息（块大小、inode 总数）
inode一个文件的元数据权限、大小、时间戳、数据块指针
dentry一个目录项（路径到 inode 的映射）纯内存缓存（加速路径查找）
file一个进程打开的文件文件描述符 + 当前读写位置

VFS 对象实操

# VFS 对象怎么看
# ① inode：文件的身份证
stat file.txt
#   File: file.txt
#   Size: 4096      Blocks: 8      IO Block: 4096   regular file
#   Device: 802h/2050d   Inode: 131074      Links: 1
#   Access: (0644/-rw-r--r--)  Uid: ( 1000/  user)   Gid: ( 1000/  user)
#   ...
ls -i file.txt            # 只看 inode 号

# ② dentry 缓存（路径查找加速器）
cat /proc/sys/fs/dentry-state
#   年龄最大的dentry数  未使用的dentry数  可回收的dentry数 ...

# ③ 打开的文件
lsof -p <pid>             # 该进程打开了哪些文件
ls -l /proc/<pid>/fd      # 文件描述符（含 socket、管道）
cat /proc/sys/fs/file-nr  # 已分配/空闲/上限 的文件描述符数

# ④ 硬链接与软链接的本质区别
ln  file.txt hard.txt     # 硬链接：新的 dentry 指向<b>同一个 inode</b>
ln -s file.txt soft.txt   # 软链接：新的 inode，内容是<b>目标路径字符串</b>
ls -li                    # 看 inode 号：硬链接相同，软链接不同
# 硬链接的限制：不能跨文件系统、不能链接目录（防环）
# 删除文件 = 删除 dentry + inode 链接数 -1；链接数为 0 且无进程打开时才真正删数据

性能：页缓存与 IO 栈

层次作用延迟观测命令
应用缓冲stdio 的用户态缓冲——
页缓存 Page Cache内核缓存的文件内容约 100 ns（命中）free 的 buff/cache
块层 + 调度器合并、排序 IO 请求—cat /sys/block/sda/queue/scheduler
设备驱动操作硬件SSD 约 100 μs；机械盘约 10 msiostat -x 1

页缓存是 Linux IO 性能的核心：读过的文件会缓存在内存，下次访问不碰磁盘（延迟从 100 μs 降到 100 ns，快 1000 倍）。这也是为什么 Linux 的“空闲内存少”通常不是问题——空闲内存会被自动用作页缓存，需要时再回收。判断内存是否真的不够，要看 available 而不是 free。

页缓存与 IO 观测

# 内存：别被 buff/cache 吓到
free -h
#               total   used    free   shared  buff/cache   available
# Mem:           15Gi   3.2Gi   1.5Gi   200Mi       11Gi        11Gi
#                                        ^^^^^^^^^^  ^^^^^^^^^
#                                        被用作缓存   真正可用（含可回收缓存）
# -> 看 available（11G），不要看 free（1.5G）！

# 手动释放缓存（仅测试用，生产不要随便清）
echo 3 > /proc/sys/vm/drop_caches      # 清页缓存+目录项+inode
# 清完性能会明显下降（要重新预热），所以生产慎用

# 磁盘 IO 观测（最重要的三条命令）
iostat -x 1
#   r/s   w/s    每秒读写次数（IOPS）
#   rkB/s wkB/s  每秒读写字节

深入自检

为什么删除了大文件，磁盘空间没释放？

最常见的原因：文件被某个进程打开着。rm 只是删除了目录项（dentry），只要有进程持有该文件的 fd，inode 和数据块就不会被回收。典型场景：删了一个正在被写入的大日志文件，df 显示空间没释放，但 ls 已经看不到文件了。排查：lsof | grep deleted（能看到被删但仍被占用的文件）；解决：重启对应进程，或用 > file 截断（而不是 rm，这样不需要重启）。另一个原因：文件系统预留空间（ext4 默认预留 5% 给 root），用 tune2fs -m 1 /dev/sda1 可调到 1%。

ext4 和 XFS 怎么选？

经验规则：① 通用场景、根目录、小到中等文件 → ext4（最成熟、工具完善、出问题好救）；② 大文件（> 1 GB）、高并发写入、需要超大容量 → XFS（XFS 的分配器对并发写更友好，且支持在线扩容不能在线缩容）；③ 需要快照/压缩/校验和 → Btrfs 或 ZFS。注意：XFS 只能扩容不能缩容，ext4 可以缩容。另外，数据库场景现在推荐直接用裸盘或 XFS，避免文件系统层的额外开销（如 PostgreSQL/MySQL 在 XFS 上表现更好）。

什么是“一切皆文件”？真的都是文件吗？

是设计哲学而非字面意思。Linux 把很多资源都抽象成文件描述符：普通文件、目录、设备（/dev/sda）、管道、socket、/proc 里的内核信息、甚至 /dev/null、/dev/random。好处是统一接口——open/read/write/close 一套搞定，还能用 select/epoll 统一做 IO 多路复用（这也是 Redis、Nginx 能统一处理文件和网络的原因）。但严格说不是全部：信号、定时器、某些 ioctl 不走文件接口。更准确的说法是“一切皆文件描述符”。

磁盘 IO 慢怎么系统性地排查？

四步定位法：① 看整体——iostat -x 1，看 %util（是否打满）和 await（单次 IO 耗时）；② 找进程——iotop -o 找出 IO 大户，判断是正常业务还是异常（如日志狂刷）；③ 看 IO 模式——随机还是顺序（blktrace 或看 r/s 与 rkB/s 的比值：每 IO 字节数小 = 随机）；④ 针对性优化——随机 IO 多 → 加内存（页缓存）或换 SSD；顺序 IO 慢 → 检查是否直写（O_DIRECT）、条带大小、RAID 配置；写多 → 检查是否开了 atime、是否 fsync 过于频繁。最常见的三个元凶：没用页缓存、随机写太多、fsync 太频繁。

第一层 · 分层与核心对象

Linux 文件系统的关键设计是 VFS（虚拟文件系统）抽象层：上层（open/read/write）统一，下层（ext4、XFS、btrfs、NFS）各自实现。理解四个核心对象就能理解全部。

对象是什么何时创建存在哪
superblock一个已挂载文件系统的元数据mount 时内存 + 磁盘（多份备份）
inode文件的元数据（不含文件名）文件创建时磁盘 inode 表
dentry目录项（文件名 → inode 的映射）路径查找时内存缓存（dcache）
file进程打开的文件实例（含读写位置）open() 时内存（进程 fd 表）
  • inode 存什么：权限、所有者、大小、时间戳、数据块指针、链接数。不存文件名——文件名存在目录的 dentry 里。这就解释了为什么硬链接可以多个名字指向同一 inode，而移动文件（同分区）只需改 dentry 不动数据（所以很快）。
  • 目录是什么：目录也是一个文件，内容是「文件名 → inode 号」的列表。所以「读一个目录下的文件名」本质上是读这个文件的内容。
  • VFS 的价值：让 cp、ls 这些工具不用关心底层是 ext4 还是 NFS。这是 Linux 能同时支持十几种文件系统的原因。
  • 一切皆文件：普通文件、目录、设备、socket、管道在 VFS 层都是「文件」，只是 file_operations 的实现不同。

命令

# —— 排查「磁盘满了但 du 看不到」——
df -h                     # 显示 100% 满
du -sh /                  # 但加起来远小于总量
# 原因：文件被删除但仍被进程持有（fd 未关闭）-> 空间未释放
lsof | grep deleted       # 【关键】找 deleted 但仍被打开的文件
# 解决：重启对应进程，或 > /proc/<pid>/fd/<fd> 截断

# —— 排查 inode 耗尽 ——
df -i                     # IUse% 100% 但空间还有
# 原因：海量小文件（如日志碎片、session 文件、邮件）
find / -xdev -type f | cut -d/ -f2 | sort | uniq -c | sort -rn | head
# 解决：删除小文件；重建文件系统时调小 inode_ratio（只能重建！）

# —— 看一个文件实际占用多少块 ——
stat -f .                 # 文件系统信息：块大小、总块数
stat bigfile              # Blocks 字段是【512B 扇区数】
#   实际占用 = Blocks * 512 字节（注意稀疏文件会小于逻辑大小）
du -h --apparent-size bigfile   # 逻辑大小（ls 显示的）
du -h bigfile                   # 实际占盘大小（稀疏文件会小很多）

# —— 稀疏文件（数据库/虚拟机镜像常用）——
truncate -s 10G sparse.img      # 创建 10G 的逻辑大小，实际占 0 字节
ls -lh sparse.img               # 显示 10G
du -h sparse.img                # 显示 0
#   这就是「ls 和 du 不一致」的常见原因

# —— 挂载选项优化（/etc/fstab）——
#   defaults,noatime,nodiratime       # 不更新 atime，减少写
#   barrier=1 / nobarrier             # 有电池保护的 RAID 可关 barrier 提速
#   data=ordered（ext4 默认）          # 日志模式：ordered 平衡安全与性能
#   discard（SSD TRIM）                # 或用定时 fstrim，别用实时 discard

# —— 碎片与整理 ——
filefrag -v bigfile             # 看文件有多少个 extent（越少越连续）
e4defrag /path                  # ext4 在线整理（效果有限）

两个高频事故：① 删了日志但 df 还是满（进程仍持有 fd）；② inode 耗尽（小文件太多）。排查命令分别是 lsof | grep deleted 和 df -i。

第三层 · 排障清单

  • 删了文件空间没释放 → 进程仍持有文件描述符。用 lsof | grep deleted 定位，重启进程或用 > /proc/<pid>/fd/<n> 截断。正确清理日志的做法是 truncate 而不是 rm。
  • inode 用完 → df -i 显示 100%。海量小文件导致（如 /var/spool、session 目录、Node 的 node_modules）。inode 数量在格式化时就固定了，无法在线调整——只能删文件或重建文件系统。
  • 文件系统只读（Read-only file system） → 通常是检测到错误后内核主动保护（或磁盘故障）。看 dmesg 里的 ext4/XFS 报错，需要 fsck（要卸载后做）。
  • 写入很慢 → 按顺序排查：① iostat -x 看 %util 是否接近 100%、await 是否很高；② 日志模式（data=journal 最安全但最慢，ordered 平衡，writeback 最快但可能元数据不一致）；③ 是否开了 barrier（有 BBU 的 RAID 可关）；④ 是否同步写（fsync 太频繁）。
  • ls 和 du 大小不一致 → 稀疏文件（du 显示实际占用，ls 显示逻辑大小），或者块大小导致的取整浪费（1 字节的文件也占 4KB）。
  • 硬链接和软链接混淆：硬链接共享 inode（不能跨文件系统、不能指向目录），删除原文件后数据仍在；软链接是独立文件（存路径），原文件删除后变成断链。
  • 跨文件系统移动很慢 → mv 在同一分区内只改 dentry（瞬间完成）；跨分区要真实复制数据。所以大文件跨分区移动很慢是正常的。
  • SSD 上的 TRIM → 删除文件后 SSD 不知道块可回收，写入性能会下降。用定时 fstrim（systemctl enable fstrim.timer）而不要用 mount 的 discard（实时 discard 会影响性能）。
  • 文件名大小写 / 编码问题 → Linux 文件名区分大小写且是字节序列（非 UTF-8 也能存）。跨系统拷贝可能出现乱码。

第四层 · 原理与取舍

三个核心机制决定了文件系统的行为：inode 与文件名的分离、页缓存（Page Cache）、日志（Journaling）。

  • inode 与文件名分离的三个后果：① 硬链接——多个名字指向同一 inode（inode 里有个「链接计数」，减到 0 才真正删除数据）；② 同分区移动瞬间完成——只需改 dentry，不动数据；③ 删除是异步的——rm 只是减少链接数并删除 dentry，只要还有进程打开这个文件，数据就还在（这就是「删了空间不释放」的原理）。
  • 页缓存（Page Cache）：Linux 会用空闲内存缓存文件数据。所以「内存快满了」常常不是问题——free 里的 buff/cache 是可回收的。读文件时先查页缓存（命中就不用碰磁盘），写文件时先写页缓存（延迟写，由内核异步刷盘）。这就是为什么顺序读第二次会快几十倍，也是为什么断电可能丢数据（要靠 fsync 强制落盘）。
  • 日志（Journaling）解决什么问题：文件系统的一次操作可能要改多处元数据（如删除文件要改 inode、位图、目录项）。中途断电会导致不一致（如 inode 标为已删但位图没更新）。日志的做法：先把要做的修改写进日志区，提交后再应用到实际位置。崩溃后重放/回滚日志即可。代价是写放大（数据要写两次）。
  • ext4 的三种 data 模式：journal（数据+元数据都记日志，最安全最慢）、ordered（默认，只记元数据，但保证数据先于元数据落盘）、writeback（只记元数据，无顺序保证，最快但可能残留旧数据）。生产用默认 ordered 即可。

为什么删了大文件磁盘空间还是没释放？

因为 Linux 的文件删除是「解除链接」而不是「立即擦除」。具体来说：rm 做的事是删除目录项（dentry）并把 inode 的链接计数减 1。只有当链接计数归零、且没有任何进程打开这个文件时，数据块才会被真正释放。如果有进程（如一个还在跑的服务）之前 open 了这个文件并且没关闭，那么内核会保持 inode 和数据块存活，磁盘空间就不释放。这是设计使然——进程正在读写的文件不应该被凭空抽走。排查用 lsof | grep deleted，会显示 (deleted) 标记。解决：重启该进程，或者用 > /proc/<pid>/fd/<fd号> 把文件截断为 0（这样不用重启也能立刻释放）。正确的日志清理姿势是用 truncate -s 0 或 > logfile 而不是 rm——这样进程的 fd 还有效，继续往里写也没问题。

Page Cache 占了很多内存，是不是内存泄漏？

不是，这是 Linux 的正常运行机制。Linux 的设计哲学是「空闲内存就是浪费的内存」——内核会把空闲内存用来缓存文件数据（Page Cache），当应用程序需要内存时，这些缓存会自动回收。所以看到 free 里 free 很小但 buff/cache 很大，是完全正常的。判断内存是否真的紧张，要看：① available 列（这是估算的可用内存，包含了可回收的缓存）；② 有没有发生 swap（si/so 非零说明真的不够了）；③ 有没有 OOM Kill（dmesg | grep -i oom）。只有当这三者都异常时才是真的内存问题。顺便说，这也是为什么顺序读第二次会快几十倍——第一次读进了 Page Cache，第二次直接从内存拿。反过来，如果你确实想释放缓存（比如做性能测试），可以 echo 3 > /proc/sys/vm/drop_caches，但这只是测试手段，生产环境不需要也不应该做。

ext4 和 XFS 怎么选？

大多数场景 ext4 是安全默认，但有几个明确的切换信号：选 XFS 的情况：① 单文件很大或总量很大（TB 级、大文件存储/媒体库）——XFS 用 B+ 树管理分配，大文件和大目录性能明显更好；② 高并发写入（XFS 的分配组设计让并发写入可以并行）；③ 不想被 inode 数量限制——XFS 的 inode 是动态分配的，ext4 的 inode 在格式化时固定（小文件多了会用光，且无法在线调整）。选 ext4 的情况：① 通用服务器/根分区——ext4 更成熟、工具链更全、fsck 更快；② 可能需要缩小分区（XFS 不支持缩小，只能备份-重建-恢复）；③ 小文件很多且数量可预估（提前算好 inode 数）。补充一点：ext4 的 inode 耗尽是个真实的运维事故，如果建文件系统时预期会有海量小文件，要么选 XFS，要么在 mkfs.ext4 时用 -i 调小 inode_ratio。
