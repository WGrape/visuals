🗂️ .ibd 文件是什么？

.ibd（InnoDB Data File）是 MySQL InnoDB 引擎 特有的表空间文件。

  • 每个表一个 .ibd 文件（默认开启 innodb_file_per_table）
  • 存储表的数据和索引
  • 文件大小随数据量动态增长
  • 路径：datadir/database/table.ibd

🏗️ 文件内部结构

  • 表空间（Tablespace）：最高层，有唯一 Space ID
  • 段（Segment）：分叶子段、非叶子段、Undo段
  • 区（Extent）：64个连续页面 = 1MB
  • 页面（Page）：最小IO单位 = 16KB

📄 页面（Page）类型

  • FIL_PAGE_INDEX (17855)：B+树节点页
  • FIL_PAGE_INODE (17817)：段索引节点
  • FIL_PAGE_SDI (17882)：序列化字典信息
  • FIL_PAGE_LOB_DATA：大对象数据页
  • FIL_PAGE_TYPE_ALLOCATED (0)：未分配空闲页
  • FIL_PAGE_UNDO_LOG：Undo 日志页

⚙️ 相关 MySQL 参数

  • innodb_page_size：页面大小，默认 16KB
  • innodb_file_per_table：每表独立 .ibd
  • innodb_buffer_pool_size：Buffer Pool 大小

页面详情

核心速览

页 Page = 16KBInnoDB 的最小 IO 单位，一切结构的基石
区 Extent = 1MB连续 64 个页，保证顺序 IO
段 Segment逻辑对象（叶子段/非叶段/回滚段），由若干区组成
表空间 Tablespace一个 .ibd 文件 = 一个独立表空间（innodb_file_per_table=ON）

四层嵌套关系

InnoDB 的存储结构是严格的四层嵌套，理解它是看懂 .ibd 文件的第一步：

层级大小是什么为什么这么设计
Page 页16 KB最小的磁盘管理单位，一次 IO 读一个页16KB 是机械盘顺序 IO 与内存利用率的平衡点；太小 IO 次数多，太大浪费内存与带宽
Extent 区1 MB（64 个连续页）分配单位，一次申请一整块保证页物理连续，让 B+Tree 的范围扫描变成顺序 IO，避免随机 IO
Segment 段可变逻辑对象：叶子节点段、非叶子节点段、回滚段把 B+Tree 的叶子层和非叶层分开管理，各自独立申请区
Tablespace 表空间可变一个 .ibd 文件（独立表空间模式）每张表一个文件，便于单表迁移、删除即释放空间
💡 一句话记忆：页管 IO、区管连续、段管逻辑、表空间管文件。

页的 7 大组成部分

不管是哪种页，前 38 字节的 File Header 和后 8 字节的 File Trailer 都是通用的；中间部分随页类型而不同。

部分大小作用
File Header38 B页的元信息：Checksum、页号、上一页/下一页指针、LSN、页类型。上下页指针让同层页串成双向链表
Page Header56 B页内状态：记录数、Free Space 偏移、槽位数、最后插入位置等
Infimum + Supremum26 B两个伪记录，分别是页内最小和最大记录，作为行链表的头尾哨兵
User Records变长真正存的行记录，按主键顺序串成单向链表
Free Space变长尚未使用的空间，插入时从这里分配
Page Directory变长槽位（Slot）数组，每 4~8 条记录一个槽，记录组内最大记录的偏移——用于页内二分查找
File Trailer8 BChecksum + Old LSN，用于检测「页是否写了一半」（部分写失效）
⚠️ 关键理解：页内记录是链表 + 目录的组合。链表保证插入时不移动数据，目录（Page Directory）提供 O(log n) 的定位能力——先二分定位到槽（一组 4~8 条），再在组内顺着链表走几步。这就是「逻辑有序、物理可不连续」的实现。

页类型用途

行格式：记录是怎么存在页里的

InnoDB 支持 4 种行格式（ROW_FORMAT），8.0 默认 DYNAMIC：

行格式特点适用
REDUNDANT最老格式，字段长度偏移表，浪费空间仅兼容老版本
COMPACT5.0 引入，变长字段长度列表倒序存放，省空间兼容场景
DYNAMIC（默认）溢出列只存 20 字节指针，真实数据放溢出页推荐，长文本/JSON 友好
COMPRESSED在 DYNAMIC 基础上对页做 zlib 压缩归档、冷数据（CPU 换空间）

一条 COMPACT/DYNAMIC 记录的物理布局（从左到右）：

| 变长字段长度列表 | NULL 标志位 | 记录头信息(5B) | 主键列 | DB_TRX_ID | DB_ROLL_PTR | 其他列 |
                                     ↑                    ↑           ↑
                                  真实数据              事务ID    回滚指针(MVCC)
💡 行里藏着 MVCC 的两把钥匙：DB_TRX_ID（最后修改该行的事务 ID）与 DB_ROLL_PTR（指向 undo log 里上一个版本的指针）。它们加上 ReadView 就构成了 InnoDB 的一致性非锁定读。

B+Tree 与页的关系

非叶子页（内节点）

只存键值 + 子页页号（约 1200 个目录项/页），不存行数据。所以三层 B+Tree 能索引 1200 × 1200 × 十几行 ≈ 两千万行，树高通常只有 3~4 层。

叶子页

存完整行数据（聚簇索引）或「索引列 + 主键值」（二级索引）。同层叶子页之间用双向链表串起来，所以范围扫描是顺序 IO，非常快。

聚簇索引（Clustered）二级索引（Secondary）
叶子存什么整行数据索引列 + 主键值
数量每表仅 1 个可多个
查完整行直接拿到需要回表（用主键再查一次聚簇索引）
建索引代价主键即数据本身额外一棵 B+Tree，占空间、拖慢写入

空间分配：碎片是怎么产生的

  • 段按需申请区：新建段先申请 32 个碎片页（Fragment Page）省空间，用满了才开始整区（1MB）分配。
  • 删除不释放给 OS：删掉的行只是标记删除（delete-mark），空间留在页内等待复用；OPTIMIZE TABLE 才真正整理并释放。
  • 页分裂：页满了（15/16 填充因子）插入时分裂成两页，产生约 50% 的空闲空间——这是碎片的主要来源。
  • 区不能被两个段共用：即使区里只用了几页，整区也属于某个段，这是空间浪费的另一来源。
-- 看表的碎片与大小
SELECT table_name,
       ROUND(data_length/1024/1024, 1)   AS data_mb,
       ROUND(index_length/1024/1024, 1)  AS idx_mb,
       ROUND(data_free/1024/1024, 1)     AS free_mb,      -- 碎片
       table_rows
FROM information_schema.tables
WHERE table_schema='db_name' AND table_name='t1';

-- 整理碎片（会重建表，8.0 通常是 INPLACE，但仍要留空间与锁窗口）
OPTIMIZE TABLE t1;

文件相关的运维要点

独立表空间 vs 共享

  • innodb_file_per_table=ON（8.0 默认）：每表一个 .ibd
  • DROP TABLE 直接删文件释放空间
  • 可单表迁移（ALTER TABLE ... DISCARD/IMPORT TABLESPACE）

页大小能不能改

  • 默认 16KB，由 innodb_page_size 决定（4/8/16/32/64）
  • 实例级参数，初始化后不可改，改了要重新初始化
  • SSD + 点查多的场景有人试 8KB；扫描多的用 32KB

双写缓冲（Doublewrite）

  • 解决部分写失效：16KB 页只写了 4KB 就断电
  • 先写 doublewrite buffer（连续区），再写真实位置
  • 崩溃恢复时用副本修复坏页

页损坏怎么办

  • File Trailer 的 Checksum 检测出坏页
  • innodb_force_recovery 逐级尝试启动并导出
  • 真正的防线永远是备份

🎯 常见问法与答题要点

Q：InnoDB 为什么要分「页—区—段」三层？

A：各解决一个问题。页（16KB）是 IO 单位，匹配磁盘与内存的读写粒度；区（1MB = 64 连续页）是分配单位，保证同一批页物理连续，让 B+Tree 的范围扫描变成顺序 IO；段是逻辑单位，把 B+Tree 的叶子层、非叶层分开管理，各自独立申请区。没有区这一层，页就会随机散落，范围查询会退化成随机 IO。

Q：页内记录是怎么组织的？查找复杂度是多少？

A：两层结构——记录按主键顺序串成单向链表（插入不移动数据），同时每 4~8 条记录建一个 Page Directory 槽位。查找时先在槽位数组上二分定位到某一组（O(log n)），再在组内顺着链表走几步（O(1) 常数）。所以页内查找不是全扫，而是近似 O(log n)。这也是「逻辑有序、物理可不连续」能高效工作的关键。

Q：File Trailer 有什么用？

A：检测部分写失效（partial page write）。16KB 的页写到一半（比如只写了 4KB）断电，页就损坏了，而 redo log 也无法修复（因为 redo 是基于完整页做的物理修改）。File Trailer 存了 Checksum 和 Old LSN，与 File Header 比对不一致就说明页坏了。真正的修复靠双写缓冲（doublewrite buffer）里保留的完整副本。

Q：行格式 DYNAMIC 和 COMPACT 有什么区别？

A：主要区别在溢出列的处理。COMPACT 会把溢出列的前 768 字节存在本页、剩下的放溢出页；DYNAMIC 则只存 20 字节的指针，全部数据放溢出页。好处是本页能放更多行、B+Tree 更矮、点查更快，尤其适合含 TEXT/JSON 大字段的表。MySQL 8.0 默认就是 DYNAMIC。

Q：一条行记录里哪些字段是隐藏的？

A：至少三个：DB_ROW_ID（无主键时的隐式行 ID）、DB_TRX_ID（最后修改该行的事务 ID）、DB_ROLL_PTR（指向 undo log 中上一个版本的回滚指针）。后两者是 MVCC 的物理基础——配合 ReadView 判断某版本对当前事务是否可见，可见性判断沿着 DB_ROLL_PTR 串成的版本链回溯。

Q：B+Tree 三层能存多少行？

A：估算：非叶页 16KB，每个目录项约「键值 8B + 页号 6B」≈ 14B，一页约 1100~1200 个目录项；叶子页每行按 200B 算约 80 行。三层（根 + 中层 + 叶子）= 1200 × 1200 × 80 ≈ 1.1 亿行；即使每行 1KB 也有约 1200×1200×15 ≈ 2000 万行。所以实际业务里 B+Tree 高度通常只有 3~4 层，一次点查只需 3~4 次 IO（且非叶页几乎全在缓冲池里，实际磁盘 IO 往往只有 0~1 次）。

Q：为什么删了很多数据，.ibd 文件没变小？

A：因为 InnoDB 不把空间还给操作系统。DELETE 只是给行打 delete-mark，空间留在页内等待复用；页空了也不会把所在的区还给文件。要真释放需要 OPTIMIZE TABLE（8.0 通常是 INPLACE 重建，但仍需要额外的磁盘空间和短暂的锁）。如果是要归档清理，推荐用分区表 + DROP PARTITION，那是真正直接删文件的操作。

Q：页大小能调整吗？什么时候值得调？

A：innodb_page_size 是实例级参数且初始化后不可更改，要改必须重新初始化实例，成本极高。默认 16KB 适合绝大多数场景。理论上：SSD + 大量随机点查可以考虑 8KB（减少单次 IO 的无效读取）；大量顺序扫描可以考虑 32KB（减少 IO 次数）。但实践中收益通常不明显而风险很高，不建议为了调优去改它。
