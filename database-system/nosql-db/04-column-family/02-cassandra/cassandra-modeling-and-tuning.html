01建模第一原则：按查询设计分区键

Cassandra 不是关系库，不能先建表再随便查。分区键决定了数据落在哪个节点，必须按最高频的查询来设计。

CREATE TABLE orders_by_user (
  user_id   bigint,
  order_id  timeuuid,
  amount    decimal,
  PRIMARY KEY ((user_id), order_id)
) WITH CLUSTERING ORDER BY (order_id DESC);
-- 按 user_id 分区，order_id 聚簇排序，查某用户订单很快
  • 避免热分区：单一超级分区（如 user_id=0）会压垮一个节点 → 加桶 (user_id, bucket) 打散。
  • 分区键基数要够大，否则大量数据挤进少数分区。
  • 别用分区键做范围扫描，那是聚簇列的事。

02一致性级别调优

级别延迟一致性适用
ONE最低可能读旧对一致性不敏感的高吞吐读
QUORUM中多数派，强默认推荐，读写都 QUORUM
ALL最高全副本要求强但易超时，少用
LOCAL_QUORUM低（不跨 DC）多数派本地多数据中心首选

读写可以分别设不同级别（写 QUORUM、读 ONE 提高读吞吐），但要清楚代价。

03常用运维命令

nodetool status            # 看集群节点/状态/负载
nodetool cfstats ks.table  # 表级统计
nodetool repair -pr ks      # 反熵修复（定期跑，否则副本漂移）
nodetool compact ks table   # 手动 compaction
nodetool flush              # 内存表刷盘
要点：REPAIR 不跑的后果：节点失效后副本数据不一致且无法自动收敛。这是 Cassandra 运维的头号责任。

04常见反模式

  • 宽行无限增长（一个分区塞几百万行）→ 读写都慢、易超分区大小限制。
  • 滥用 Secondary Index：本质是隐藏的全集群扫描，热点明显。
  • 把 Cassandra 当关系库用（大量 join、聚合）→ 性能崩溃，应在写入时反范式化。
问：什么时候不该用 Cassandra？

需要复杂事务、跨行 ACID、或强一致读的场景；以及团队没有运维分布式存储经验时，先用托管方案更稳。

第一层 · 概念与判定：建模第一原则

Cassandra 是按查询建模的宽列库，不是按实体建模的关系库。先写查询，再反推表结构；一张表服务一类查询，宁可冗余也不要 JOIN。

关系库思路Cassandra 思路
三张表 + JOIN每张高频查询一张宽表
任意维度过滤分区键决定能高效查的维度
范式化去重故意冗余，换写入放大换读性能

第二层 · 参数·命令·量化：一致性级别与读写

场景一致性级别含义
用户读写强一致QUORUM（读写都）R+W>副本数，不丢不旧
埋点/日志ONE / ANY能写就写，丢点无妨
读多写少看最新LOCAL_ONE 读 + QUORUM 写读快、写稳
跨 DCLOCAL_QUORUM不出 DC，降延迟

Cassandra 建表 + 一致性 + 运维命令

-- 建表：分区键 + 聚簇键，控制单行大小
CREATE TABLE events (
  device_id text,
  day date,
  ts timeuuid,
  payload text,
  PRIMARY KEY ((device_id, day), ts)
) WITH CLUSTERING ORDER BY (ts DESC);

-- 一致性级别按需设
CONSISTENCY QUORUM;
SELECT * FROM events WHERE device_id='d1' AND day='2026-10-28';

-- 运维：看是否出现热点/大分区
nodetool cfstats keyspace.events
nodetool toppartitions keyspace events 10
nodetool tpstats   # 看读写队列堆积

数量级：单分区建议 < 100MB（硬上限约 2GB 但会拖慢修复）；副本数 RF=3 时 QUORUM = 2；读放大随聚簇列增多而增大。

第三层 · 排障与边界：四个反模式

  • 用递增时间戳/自增 id 做分区键：所有写打到最新分区，热点炸——改用哈希/随机前缀打散
  • 大分区：一个设备一年的数据塞一个分区，compaction 与读取都崩——按时间再分桶
  • 无界宽行：不停 append 不出 TTL，分区无限涨——设 default_time_to_live 或定期归档
  • 二级索引滥用：高基数列上建索引等于全集群扫描——改成本地索引用低基数列或物化视图
  • 读前先读修复：开了 read_repair 高比例，读延迟被修复拖垮——降低 repair_chance

第四层 · 原理与取舍

为什么 Cassandra 不适合 JOIN 和聚合？

因为它把数据按分区键散列到各节点，JOIN 意味着跨节点拉数据，网络开销让性能崩溃。它的设计前提是查询模式已知且简单：一次主键（分区键+聚簇键）定位一行或一段。所以建模时就把 JOIN 摊平进表，用写入冗余换读取的单次命中——这是宽列库的代价交换。

一致性级别 QUORUM 和 ALL 怎么选？

QUORUM 是可用性与一致性的平衡点：R+W>RF 保证读到最新写入，且允许一个副本挂掉仍可用。ALL 要等全部副本，强一致但一个慢副本就拖垮延迟、一个挂就写不进。除非金融级强一致且副本极稳，否则生产用 QUORUM，个别关键读再升 ALL。

为什么写能这么快，读却容易慢？

写走 LSM：先写内存 memtable 再批量刷 SSTable，几乎顺序写，所以快；但读要合并 memtable + 多层 SSTable（可能还有墓碑），分区越大、版本越多越慢。所以调优核心是控制分区大小 + 合理 compaction 策略（STCS/LCS/TWCS），让读只扫少量文件。
