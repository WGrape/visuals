一句话总结：云原生不是"把应用搬到云上"，而是让应用从设计之初就为云而生—— 假设基础设施会随时故障、随时扩容，因此把弹性、自愈、可观测、自动化全部内建进架构。 CNCF 将其归纳为四大支柱：容器、微服务、DevOps、声明式 API。

01什么是云原生

CNCF（Cloud Native Computing Foundation）给出的官方定义是：

云原生技术有利于各组织在公有云、私有云和混合云等新型动态环境中， 构建和运行可弹性扩展的应用。代表技术包括容器、服务网格、微服务、不可变基础设施和声明式 API。

这些技术能够构建容错性好、易于管理、便于观察的松耦合系统； 结合可靠的自动化手段，工程师可以频繁且可预测地对系统做出重大变更。

关键在"设计思想"，不在"部署位置"

维度传统上云（Cloud Hosting）云原生（Cloud Native）
迁移方式把物理机应用原样搬到云主机重构为容器化、微服务化
对故障的假设假设服务器稳定，靠人工救火假设随时故障，靠编排自动自愈
扩容方式提前买机器，人工部署按指标自动弹性伸缩
基础设施管理手工配置、脚本声明式 + 基础设施即代码（IaC）
发布频率按月/季度，风险高每天多次，灰度 + 自动回滚
状态管理有状态、粘滞会话无状态、状态外置
常见误解：买了云服务器 ≠ 云原生；用了 Kubernetes ≠ 云原生。 如果应用仍是单体、手动部署、靠人肉运维，那只是"在云上跑的传统应用"。 判断标准是——它是否利用了云的弹性与自动化能力。

02四大支柱

图 1：四大支柱由 Kubernetes 编排层粘合，可观测性等能力作支撑

📦 容器

解决"环境一致性与交付标准化"。把应用及依赖打包成不可变镜像， 开发、测试、生产完全一致；进程级隔离让资源可控、调度轻量。

🔀 微服务

解决"规模化协作与独立演进"。拆成可独立开发、部署、伸缩的小服务， 故障隔离在单个服务内，团队可并行演进。

🔄 DevOps

解决"交付速度与质量"。用 CI/CD 流水线把构建、测试、发布自动化， 小步快跑 + 灰度 + 自动回滚，让高频发布变得安全。

📜 声明式 API

解决"系统自愈与自动化"。只描述"期望状态"， 由控制循环持续调谐实际状态向期望收敛——这是 K8s 自愈能力的根本来源。

03CNCF 生态全景

CNCF 托管的项目分三个成熟度等级：Sandbox（沙箱）→ Incubating（孵化）→ Graduated（毕业）。 毕业项目意味着具备生产级成熟度与健康的社区治理。

类别毕业项目代表作用
编排与调度Kubernetes容器编排的事实标准
容器运行时containerd行业标准的容器运行时
监控告警Prometheus时序监控与告警（详见《时序数据库》）
服务网格Linkerd（Istio 为孵化）服务间通信的流量、安全与可观测
分布式追踪Jaeger请求链路追踪
日志Fluentd / Fluent Bit日志采集与转发
远程调用gRPC高性能 RPC 框架
服务发现/配置CoreDNS、etcd集群 DNS 与分布式键值存储
无服务器Knative（孵化）基于 K8s 的 Serverless 框架
制品与供应链Harbor、Notary（孵化）镜像仓库与签名

04与相邻概念的区别

概念关注点与云原生的关系
云计算（IaaS/PaaS/SaaS） 资源的供给方式 云原生运行其上；云提供弹性资源，云原生提供利用这些资源的方法论
云架构 云上系统的拓扑设计（网络、CDN、负载均衡、高可用） 偏基础设施与流量架构，见《云架构系统》学科；云原生偏应用形态与交付方式
分布式系统 多节点协同的一般性原理（共识、CAP、事务） 是云原生的理论基础，见《分布式系统》学科；云原生是其工程化落地形态
微服务 一种架构拆分风格 是云原生的支柱之一，但微服务可以在非容器环境实现，不等于云原生
DevOps 研发与运维协作的方法论 是云原生的支柱之一，强调自动化交付闭环
本学科的知识边界：本学科（云原生）关注应用如何为云而生； 基础设施与流量架构（云网络、CDN、负载均衡）属于《云架构系统》； 通用分布式原理属于《分布式系统》。同名主题只在一处展开，避免重复。

05落地路径与成熟度评估

  1. 容器化：应用与依赖打包成镜像，统一交付物。
  2. CI/CD：建立自动化构建、测试、镜像推送流水线。
  3. 编排上 K8s：用声明式 YAML 描述部署，获得自愈与弹性。
  4. 可观测性：指标、日志、链路三件套，让故障可定位。
  5. 服务治理：按需引入服务网格，处理流量、安全与熔断。
  6. 进阶：Serverless、GitOps、多集群、混沌工程。
Q：我们该上云原生吗？
A：看三个信号——① 发布频率需要提升到每周以上； ② 流量波动大、需要自动弹性； ③ 团队规模扩大、需要独立部署与解耦。
反过来说，如果应用是稳定的单体、流量平稳、团队很小，盲目微服务化 + 上 K8s 只会显著增加复杂度与运维负担。 云原生是手段不是目的。

06常见疑问

Q：用了 Kubernetes 就是云原生了吗？
A：不是。K8s 只是编排工具。如果应用仍是单体、手工改 YAML、没有自动伸缩、 没有可观测性、发布靠人肉，那只是"用 K8s 跑了传统应用"。 真正的标志是自动化闭环：声明期望状态 → 系统自动调谐 → 异常自动自愈 → 指标驱动伸缩。
Q：云原生和"上云"的成本对比如何？
A：云原生前期投入明显更高（需要重构、建流水线、建可观测体系、培养运维能力）， 但规模化后边际成本更低：资源利用率提升、发布效率提升、故障恢复自动化。 小团队/稳定业务往往不划算，规模化的多服务系统收益显著。
Q：十二要素（12-Factor）在云原生里的位置？
A：它是云原生应用的设计方法论（无状态进程、配置外置、日志当事件流、端口绑定等）， 早于 K8s 出现，但思想完全兼容并被 K8s 落地。详见本学科《十二要素》一篇。
