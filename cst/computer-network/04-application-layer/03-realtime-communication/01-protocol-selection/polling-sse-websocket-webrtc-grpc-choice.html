轮询、长轮询、SSE、WebSocket、WebRTC 与 gRPC 怎么选

按通信方向、延迟、断线恢复和部署环境为通知、聊天、音视频分别选协议。

先写出消息从谁到谁

如果浏览器偶尔查询订单状态，普通 HTTP 轮询每几秒 GET 一次最简单，代价是空请求和状态更新延迟；长轮询让服务器暂时挂起请求，等有变化或超时后回答，客户端再发下一次；SSE 在一个 HTTP 响应里持续向浏览器推送文本事件；WebSocket 建立后能双向发送消息帧；WebRTC 侧重实时音视频和点对点数据通道；gRPC 常用于服务间 RPC 与流式调用。名字相近并不代表它们服务同一场景。

选型先列四项：客户端是浏览器还是服务进程、需要单向还是双向、允许的更新延迟、丢线后能否补历史。只说“要实时”不足以选协议：订单状态允许两秒延迟，游戏操作要求几十毫秒，视频通话还要处理抖动与编解码。

一张业务决策表的口头版

低频状态查询：普通轮询通常足够，监控易做且失败易重试；高频单向通知：SSE 可复用 HTTP 语义，浏览器有 EventSource 及事件 ID 机制；大量双向聊天：WebSocket 更直接，但需要处理心跳、慢消费者和重连；音视频通话：WebRTC 提供媒体路径、拥塞与 NAT 穿越能力，不能靠普通 WebSocket 一路推视频帧就自动获得同样体验；服务间强类型流式调用：gRPC 可复用 HTTP/2 流和 Deadline。

这些不是排他规则。WebRTC 建连往往需要 WebSocket 或 HTTP 做信令；SSE 单向推送同时可用普通 POST 发送用户指令；WebSocket 聊天仍可能用 HTTP 拉历史记录。系统可以组合协议，但要让每条链路职责清晰。

逐步推演

明确方向

谁主动发送、是否需要双向和二进制。

确定语义

通知可补状态，聊天需去重，媒体可丢过期帧。

选择通道

低频轮询、单向 SSE、双向 WS、媒体 WebRTC。

验证恢复

在弱网、代理、重启与大量连接下测试。

轮询与长轮询的成本

每五秒轮询一次，一万个在线用户平均每秒约 2000 个查询，即使绝大多数没有变化，仍占网关和后端资源。可加条件请求或更长间隔减成本，但更新会更慢。长轮询减少空响应频率，却占有等待连接和服务端挂起请求的资源；代理与负载均衡的读超时必须长于预期等待，服务端要在超时后给客户端明确重连行为。

客户端重试要有随机抖动，避免服务恢复时大量用户同时请求。无论轮询还是长轮询，返回内容都应有版本或游标，防止相邻请求重叠造成状态倒退。

SSE 与 WebSocket 的恢复差异

SSE 是服务端到浏览器的事件流，事件可携带 id，浏览器重连时可发送 Last-Event-ID；但服务器必须保存相应历史并实现补发，协议字段本身不会凭空找回丢失事件。WebSocket 双向更灵活，却要自行设计消息 ID、序号、确认与补拉。两者都需要考虑长连接在代理上的空闲超时、认证过期、广播扇出和慢消费者。

SSE 基于文本事件格式，适合通知和 AI 文本流；若要高频二进制双向消息，WebSocket 更合适。大量连接的扩容关键常是服务端状态和广播架构，不是升级一个协议就能自动解决。

WebRTC 与服务间 RPC 的边界

WebRTC 媒体可尝试 P2P，也可能经 TURN 中继；它要处理采样、编解码、抖动缓冲、拥塞和传输安全。WebSocket 只给双向消息通道，音视频的这些能力需另做。gRPC 则更适合受控服务间调用，浏览器直连支持取决于环境和代理，常需要 gRPC-Web 或网关适配；不能假定普通浏览器 `fetch` 可直接使用全部 gRPC/HTTP2 功能。

网络防火墙可能阻断 UDP，导致 WebRTC 走中继或失败；企业代理也可能限制 WebSocket Upgrade。选型要以目标环境实测，而不是只在本机浏览器开发环境成功。

延迟之外还要看语义

订单通知必须不漏，可以在数据库保存状态，用推送只做“有变化了”的提示，客户端再按游标拉权威数据；聊天消息需要确认和去重；视频帧过期后通常宁愿丢弃也不无限重传。协议提供的可靠性与应用需要的业务保证不完全相同。若服务端写操作在超时前已提交，任何协议都需要幂等键或结果查询。

对单向通知，SSE 和长轮询都可做；若业务要求客户端持续高频上行，SSE 不适合独立承担。把通信方向画在架构图上，比先争论“哪个协议先进”更有效。

选型验收

对候选方案在目标浏览器、移动弱网、企业代理和大量并发下测更新 P95/P99、重连时间、缺消息率、服务端每连接内存和带宽。模拟代理关闭、认证过期、服务器重启和客户端后台省电。最后写明协议组合：例如“HTTP 提交命令，SSE 通知版本，断线后 GET 补状态”；用户体验由完整链路决定。

自检

选了 SSE 并设置事件 ID，就一定不会漏任何历史消息吗？

不会。服务器仍需持久化事件并按 Last-Event-ID 实现补发；否则 ID 只是标识。
