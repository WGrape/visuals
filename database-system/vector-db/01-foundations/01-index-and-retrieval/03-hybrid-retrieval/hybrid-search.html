为什么单靠向量检索不够

稠密向量（Embedding）擅长语义相似： synonym、改写、跨语言都能召回。但它有几个硬伤：

① 精确匹配差用户搜 "Redis 7.2 release notes"，向量可能召回一堆 Redis 教程，却漏掉标题里精准含该串的文档
② 稀有词/专有名词弱型号、人名、错误码、SKU（如 "iPhone 15 Pro Max"）在训练语料里少见，向量表示不准
③ 数字与符号不敏感"error 1045" 和 "error 1046" 向量可能几乎一样

而 BM25 关键词检索恰恰相反：精确匹配强、专有名词准，但不懂同义词与语义。两者互补——这就是混合检索（Hybrid Search）的出发点。

一句话：向量负责「意思对」，关键词负责「字面准」，Rerank 负责「排得对」。

标准三段式架构

RRF 倒数排名融合（最推荐）

RRF（Reciprocal Rank Fusion）是目前最主流、也最省事的融合方式。它完全不看分数，只看排名：

RRF_score(d) = Σ 1 / (k + rank_i(d))　　k 通常取 60

其中 rank_i(d) 是文档 d 在第 i 路检索结果里的排名（从 1 开始）。文档在某路排第 1 → 得 1/61；排第 10 → 得 1/70；没被这路召回 → 得 0。

优点说明
无需归一化BM25 分数是 0~几十的无界值，余弦是 -1~1，量纲完全不同——RRF 只用排名，天然免疫
无需调参k=60 是论文给出的默认值，绝大多数场景直接用就行
鲁棒某一路结果质量差也不会毁掉整体
def rrf(rank_lists, k=60, top_k=10):
    # rank_lists: [[doc1, doc2, ...], [doc3, doc1, ...]]
    scores = {}
    for lst in rank_lists:
        for rank, doc in enumerate(lst, start=1):
            scores[doc] = scores.get(doc, 0) + 1.0 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)[:top_k]
注意：RRF 只用排名意味着丢失了分数差异信息——「第 1 名比第 2 名强很多」和「两者几乎并列」在 RRF 眼里差别很小。如果你的两路分数都可比且可靠，加权融合可能更优（见下节）。

加权融合（分数归一化后）

如果想利用分数的绝对差异，用加权融合：

score = α · norm(s_dense) + (1-α) · norm(s_sparse)

关键是必须先归一化，否则量纲不同会一边倒。两种常用归一化：

方法公式特点
Min-Max(s - min) / (max - min)压到 [0,1]；对离群值敏感，一批里有个超高分会把其他都压扁
分数归一（推荐）s / max(该批分数)简单稳定，但批次间不可比
α 怎么定？经验起点 α = 0.5 左右。若业务偏语义（客服问答、知识库）→ α 调高（0.6~0.7）；若偏精确匹配（代码搜索、商品 SKU、法条）→ α 调低（0.3~0.4）。最好用标注数据扫一遍 α，画 NDCG 曲线选最优。

稀疏向量：把 BM25 也变成向量

现代向量库（Qdrant、Milvus 2.4+、Weaviate、Elasticsearch）支持稀疏向量（Sparse Vector）：把 BM25 / SPLADE 的词权重表示成「词项 id → 权重」的高维稀疏向量，和稠密向量存在同一个库里、用同一套接口检索。

BM25 稀疏向量词频/逆文档频率算权重，词表大小即维度（几万~几十万维，绝大多数为 0）
SPLADE / 学习型稀疏用神经网络预测词权重，还能扩展出原文本没有的相关词（term expansion）
优势统一存储与检索路径、支持同一套过滤、融合更简单

为什么还要 Rerank

Rerank（重排序）用 Cross-Encoder 对「查询 + 候选文档」拼在一起做一次完整注意力计算，输出精确相关分。它比双塔 Embedding 准得多，但慢得多——所以只用在候选集的精排上。

双塔 Bi-Encoder（粗排）交叉编码 Cross-Encoder（精排）
怎么算query 和 doc 各自编码成向量，再算相似度query 和 doc 拼在一起过一遍模型
能否离线预计算 doc能（这是它快的关键）不能，每次都要现算
速度毫秒级 / 百万条几十毫秒 / 每条
精度中高（能捕捉细粒度交互）
经典组合：混合检索召回 Top-100 → Rerank 精排取 Top-10。Rerank 通常能把 NDCG@10 提升 10~30 个百分点，是 RAG 效果提升性价比最高的一步。

落地检查清单

  • 两路检索（稠密 + BM25）各召回 50~200 条候选，别太少
  • 融合优先用 RRF（k=60），零调参、鲁棒
  • 若分数可比且想利用分数差异，再用加权融合 + 扫 α
  • 融合后接 Rerank，最终取 Top-K
  • 用标注集评估 Recall@K 与 NDCG@10，别只看延迟
  • 监控「两路结果重合度」——重合极低说明某一路有问题
  • Rerank 有额外延迟预算（几十~一百毫秒），提前和 SLA 对齐

    • 🎯 常见问法与答题要点

    Q：为什么有了向量检索还要关键词检索？

    A：因为两者短板互补。向量（稠密）擅长语义相似——同义词、改写、跨语言都能召回，但精确匹配弱：搜「Redis 7.2 release notes」可能召回一堆 Redis 教程却漏掉标题精准匹配的文档；对型号、人名、错误码这类稀有专有名词也表示不准（「error 1045」和「error 1046」向量可能几乎一样）。BM25 关键词检索恰恰相反——字面匹配极准但不懂语义。混合起来召回质量明显优于任何单一路。

    Q：RRF 是什么？为什么推荐它？

    A：RRF（Reciprocal Rank Fusion，倒数排名融合）：score(d) = Σ 1/(k + rank_i(d))，k 通常取 60。推荐它的核心原因是只用排名、不用分数——BM25 分数是 0~几十的无界值、余弦是 -1~1，量纲完全不可比，直接加权会一边倒；而 RRF 天生免疫这个问题，且 k=60 是论文默认值，零调参就能用，鲁棒性也好。代价是丢失了分数差异信息。

    Q：加权融合和 RRF 怎么选？

    A：默认选 RRF（零调参、鲁棒）。只有当你确认两路分数都可靠且可比、并且想利用「第 1 名比第 2 名强很多」这种强度差异时，才用加权融合：先把两路分数归一化（推荐 s/max 或 min-max），再 score = α·norm(dense) + (1-α)·norm(sparse)，α 用标注数据扫一遍选最优（语义型业务 0.6~0.7，精确匹配型 0.3~0.4）。

    Q：Rerank 为什么能显著提升效果？

    A：因为粗排用的是双塔 Bi-Encoder：query 和 doc 各自独立编码成向量再算相似度——doc 向量可以离线预计算（这是快的原因），但 query 和 doc 之间没有细粒度交互，精度有限。Rerank 用 Cross-Encoder 把 query 和 doc 拼在一起过一遍完整模型，能捕捉词级交互，精度高得多。代价是不能预计算、每条要几十毫秒，所以只对几十~几百条候选跑。实践上 Rerank 常能把 NDCG@10 提升 10~30 个百分点。

    Q：混合检索的延迟会翻倍吗？

    A：不会翻倍，但要留预算。两路检索是并行的，所以粗排延迟 ≈ max(向量检索, BM25) 而不是两者之和（通常几十毫秒）。真正额外增加的是 Rerank：对 100 条候选跑 Cross-Encoder 通常要几十到一百多毫秒。总延迟通常仍在 100~200ms 量级，对 RAG 应用完全可接受。可以用「候选数」和「Rerank 模型大小」来调延迟/精度权衡。

    Q：稀疏向量（SPLADE）比 BM25 好在哪？

    A：BM25 只能匹配原文出现过的词。SPLADE 这类学习型稀疏表示用神经网络预测词权重，还能扩展出原文没有但语义相关的词（term expansion）——比如原文写「笔记本」，SPLADE 可能同时给「laptop」「电脑」分配权重。所以它既有关键词检索的精确性和可解释性，又带一点语义泛化能力，效果通常优于 BM25，代价是需要跑模型（比 BM25 慢、需要 GPU 编码）。

    Q：怎么评估混合检索的效果？

    A：两步：①准备标注集——人工标注若干 query 的相关文档（哪怕 100 条也好）；②算指标——粗排阶段看 Recall@K（Top-100 里有没有包含正确文档，决定天花板），最终看 NDCG@10 / MRR（排序质量）。然后做消融：单向量 / 单 BM25 / 混合 / 混合+Rerank 四组对比，能清楚看到每一步的贡献。别只看延迟和 QPS。
