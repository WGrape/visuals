🔀 ARC 与 TinyLFU：两条改进 LRU 的路线

ARC 用「幽灵队列 + 自适应调参」融合 LRU 与 LFU，TinyLFU 用「频次准入」在入口把关——思路不同，目标一致。

先建立直觉：两种改进思路

LRU 的毛病是容易被批量扫描污染，LFU 的毛病是历史包袱和新数据饥饿。改进路线有两条：

  • ARC 的思路：我两个都用，而且让系统自己决定该更相信哪个——像混合动力汽车，自动切换油电比例。
  • TinyLFU 的思路：我不纠结淘汰谁，我在门口把关——用频次判断「你配不配进来」，冷数据直接挡在门外。

ARC：自适应混合

维护两个真实队列加两个幽灵队列：

队列内容占缓存
T1只访问过一次的数据（偏 LRU）是
T2访问过两次以上（偏 LFU）是
B1从 T1 淘汰的 key（只记 key）否
B2从 T2 淘汰的 key（只记 key）否

参数 p 控制 T1 的大小（T2 = C − p）。调节依据是「幽灵命中」：

  • 访问到 B1 中的 key → 说明新数据淘汰太快 → 增大 p（给 T1 更多空间，更偏 LRU）；
  • 访问到 B2 中的 key → 说明热数据淘汰太快 → 减小 p（给 T2 更多空间，更偏 LFU）。
精髓：ARC 不预测未来，而是从过去的错误中学习——「刚淘汰的东西又被需要」就是「上次淘汰错了」的直接证据，据此调整比例。而且完全不需要人工调参。

TinyLFU：频次准入

核心是一个极小的频次估算器（Count-Min Sketch）加一条规则：新数据要进来，必须和「被淘汰候选者」比频次，谁高谁留下。

  • 一次性扫描进来的冷数据频次是 1 → PK 不过缓存里的热数据 → 被挡在门外，根本污染不了缓存；
  • Count-Min Sketch 让频次统计只占极小内存（与 key 数量无关）。
纯 TinyLFU 的短板：新数据频次天然低，可能永远进不来（新数据饥饿）。所以 Caffeine 用的是 W-TinyLFU——前面加一个小的 Window 区（LRU）接纳新数据，让它们先积累热度再参与准入 PK。

为什么「准入端」更有效？因为一旦冷数据进来了，它就已经污染了缓存、挤走了热数据，事后才发现再淘汰也来不及（命中率已经损失）。在入口挡住，热数据从头到尾没受影响——这是 W-TinyLFU 命中率通常更高的原因。

怎么选

  • 应用层 Java 本地缓存 → 直接用 Caffeine（W-TinyLFU），无需自己选。
  • 存储/文件系统层、负载多变且无法调参 → ARC（ZFS 的经典选择）。
  • 简单场景 → 纯 LRU 足够，不必引入复杂度。

🎯 面试问答

Q：ARC 和 TinyLFU 哪个更好？
A：没有绝对答案，但在应用层缓存中 W-TinyLFU 更常见且通常命中率更高（Caffeine 的广泛采用就是证明）。原因是它在准入端就把冷数据挡住，热数据从头到尾不受影响；而 ARC 是在淘汰端决策，冷数据已经进来过、已经造成了命中率损失。ARC 的优势在于完全自适应、无需任何假设，适合负载多变且不便调参的底层存储场景。

Q：幽灵队列和 Count-Min Sketch 哪个更省内存？
A：Count-Min Sketch 省得多。它是一个固定大小的 d × w 计数矩阵，占用只与精度要求有关（通常几 KB 到几十 KB），与 key 数量完全无关。而 ARC 的幽灵队列要记录最多 C 个 key（C 是缓存容量），百万级缓存就是百万条记录，虽然只存 key 不存 value，开销仍明显高于 Sketch。

Q：为什么 W-TinyLFU 前面要加 Window 区？
A：为了解决新数据饥饿。纯 TinyLFU 用频次做准入，而新数据频次天然是 1，几乎不可能 PK 过缓存里已经积累高频次的老数据——结果就是新数据永远进不来。Window 区是一个小的 LRU 缓冲区，让新数据先在这里待着并积累访问频次，等有了一定热度再参与 Main 区的准入竞争。这是 W（Window）前缀的由来，也是 W-TinyLFU 优于纯 TinyLFU 的关键。

Q：这些算法需要我手动实现吗？
A：基本不需要。Java 直接用 Caffeine（内置 W-TinyLFU）；Redis 提供 allkeys-lru 和 allkeys-lfu 可选；Go 的 ristretto 也采用了类似 TinyLFU 的准入策略。自己实现的价值在于理解「时间 vs 频次」「准入 vs 淘汰」这组权衡，生产环境直接用成熟库更稳妥——这些算法的边界情况很多，实现错了反而比 LRU 更差。

第一层 · 三个算法解决什么问题

LRU 有两个公认的弱点：① 一次全表扫描会把热数据全部冲掉（扫描污染）；② 只看「最近用没用」，不看「用了多少次」。ARC 解决第一个，LFU 系解决第二个，W-TinyLFU 两个都解决。

算法核心思路解决 LRU 的什么弱点代表实现
LRU只按最近访问时间淘汰—（基线）LinkedHashMap、Redis 近似 LRU
LFU只按访问频率淘汰② 频率盲（但带来新问题：历史热点赖着不走）—（纯 LFU 很少用）
ARC两个 LRU 列表（T1 最近一次 / T2 至少两次）+ 自适应调大小① 扫描污染PostgreSQL、ZFS
LIRS按重用距离（IRD）分层①（比 ARC 更彻底）Apache Traffic Server、MySQL InnoDB（改进版）
TinyLFU用 Count-Min Sketch 以极小内存估频率②（用概率数据结构解决 LFU 内存问题）Caffeine、Ristretto
W-TinyLFULRU 窗口 + TinyLFU 主区，带 SLRU 分段① + ②Caffeine（Java 事实标准）
  • 为什么纯 LFU 不能用：① 要为每个 key 维护计数器，内存开销大；② 历史热点永不淘汰（一个昨天访问一万次的 key，今天没用了还赖在缓存里）；③ 新数据冷启动困难（频率低，刚进就被淘汰）。
  • TinyLFU 的关键突破：用 Count-Min Sketch（一个二维计数数组 + 多个哈希）把频率统计的内存压到每个 key 不到 1 字节，牺牲一点精度换来了可行性。
  • 为什么需要「老化」：TinyLFU 会周期性把所有计数减半（或重置），让历史热点自然衰减——这就解决了纯 LFU 的第②个问题。

Java/Caffeine

// —— Caffeine（W-TinyLFU）典型配置 ——
Cache<String, User> cache = Caffeine.newBuilder()
    .maximumSize(100_000)                    // 条目上限
    .initialCapacity(50_000)                 // 预分配，避免 rehash
    .expireAfterWrite(Duration.ofMinutes(10))   // 写入后 10 分钟过期
    .refreshAfterWrite(Duration.ofMinutes(1))   // 1 分钟后【异步刷新】
    .recordStats()                           // 开启统计（有轻微开销）
    .build(key -> loadFromDB(key));          // 自动加载

// —— 命中率怎么看 ——
CacheStats s = cache.stats();
System.out.printf("hitRate=%.3f evictions=%d loadTime=%dms%n",
    s.hitRate(), s.evictionCount(), s.averageLoadPenalty()/1_000_000);
// 关键指标：hitRate（命中率）、evictionCount（淘汰数）、averageLoadPenalty（平均加载耗时）

// —— 容量估算：Count-Min Sketch 占多少内存 ——
// Caffeine 的频率 sketch 约为 maximumSize * 1 字节（内部用 4bit 计数器 × 若干哈希）
// 例：maximumSize = 100 万 -> sketch 约 1 MB 左右（对比 HashMap 存 100 万计数器要几十 MB）

// —— 常见坑：maximumWeight 必须配 weigher ——
Cache<String, byte[]> c = Caffeine.newBuilder()
    .maximumWeight(1L << 30)                 // 1GB 总权重
    .weigher((String k, byte[] v) -> v.length)  // 不配 weigher 会抛异常
    .build();

选 refreshAfterWrite 还是 expireAfterWrite：前者不阻塞（过期后仍返回旧值，后台刷新），适合能容忍短暂陈旧的数据；后者过期就必须等待加载，适合一致性要求高的。两者可以同时设，refresh 更早触发。

第三层 · 排障与调参清单

  • 命中率上不去（<80%） → 按顺序排查：① 容量是否太小（evictionCount 是否持续很高）；② key 设计是否合理（是否把高基数维度（如用户 ID、时间戳）放进了 key，导致根本无法复用）；③ 是否有周期性全量扫描污染（此时 LRU 会崩，ARC/W-TinyLFU 应该没事）。
  • ARC 效果不明显 → ARC 只在存在扫描型负载时才优于 LRU。如果访问模式本身就符合局部性（正常业务），ARC 和 LRU 命中率差距通常 <2%。不要期待 ARC 是银弹。
  • Caffeine 命中率低于 Guava → 常见原因是 maximumSize 设太小导致窗口区（1%）频繁淘汰，或启用了 expireAfterAccess 与 W-TinyLFU 的频率统计冲突。先去掉过期策略单独测命中率。
  • 频率统计占内存超预期 → maximumSize 设得过大（如 1000 万）时，sketch 本身也要几十 MB。合理做法是按实际热数据集大小设（热数据通常远小于总数据量）。
  • 缓存抖动（命中率周期性下跌） → 周期性任务（报表、批处理）把缓存冲掉。解法：① 用 W-TinyLFU（对扫描免疫）；② 把批处理走独立缓存实例；③ 批处理时旁路缓存。
  • 淘汰数持续增长但命中率没提升 → 说明新增的容量没带来复用，即数据集本身缺乏局部性。继续加内存是浪费，应该重新设计 key 或缓存粒度。
  • 统计信息开销 → recordStats() 有约 5~10% 的额外开销。生产环境可以只在灰度/采样时开启。

第四层 · 原理与取舍

理解这三个算法，只需要搞清三件事：ARC 的自适应双列表、Count-Min Sketch 怎么用 1 字节估频率、W-TinyLFU 为什么要加一个 LRU 窗口。

  • ARC 的自适应机制：维护两个列表——T1（只访问过一次）和 T2（访问过≥2 次），以及两个影子列表 B1/B2（记录被淘汰的 key 的元数据，不存值）。当 B1 命中（说明刚淘汰的「一次访问型」key 又被访问了），就调大 T1 的目标比例；B2 命中则调大 T2。影子列表是 ARC 的精髓——它让算法能「感知到自己淘汰错了」，从而自适应地在「抗扫描」和「保局部性」之间找平衡。代价是要额外存影子元数据（约为缓存容量的 100%）。
  • Count-Min Sketch 为什么省内存：它是一个 d × w 的计数矩阵（如 4 行 × 容量数），每个 key 用 d 个哈希映射到每行的一个位置，访问时对应位置 +1；查询频率时取 d 个位置的最小值（因为哈希冲突只会让计数偏大，取最小最接近真值）。每个 key 不占独立空间，整个 sketch 是固定大小（约 O(容量) 而非 O(key 数)），摊到每个 key 不到 1 字节。误差是有界的（只会高估，不会低估），这对淘汰决策完全够用。
  • 为什么要「老化」：定期把所有计数右移一位（减半）。这让历史热点自然衰减，避免纯 LFU 的「赖着不走」问题。Caffeine 的实现是在 sketch 增长到阈值时触发 reset（除以 2）。
  • W-TinyLFU 为什么要加 LRU 窗口：因为 TinyLFU 对新条目不友好——新 key 频率为 1，进主区会立刻被淘汰，导致「突发的新热点」（如刚发布的热点新闻）根本进不了缓存。解法：前面加一个占 1% 的 LRU 窗口区，新条目先在这里「观察」，被访问到一定次数后晋升到主区；主区内部再用 SLRU（分段 LRU，80% 保护段 + 20% 试用段）进一步分层。这就是 W-TinyLFU 的 W（Window）。

为什么 Caffeine 能全面超过 Guava Cache？

三个层面的改进：① 淘汰算法——Caffeine 用 W-TinyLFU，Guava 是分段 LRU。官方基准测试在多种真实 trace（数据库、搜索、分析）下，Caffeine 命中率显著更高，尤其在有扫描型负载的场景。② 并发实现——Guava 用分段锁（类似 ConcurrentHashMap 的分段），Caffeine 借鉴了 Java 8 ConcurrentHashMap 的无锁读 + 写时细粒度锁 + 环形缓冲区异步处理，读写吞吐高得多，且读完全无锁。③ 淘汰的异步化——淘汰任务在后台线程完成，不阻塞put 操作。所以换 Caffeine 通常能同时拿到「更高命中率」和「更高吞吐」。这也是为什么 Caffeine 现在是 Spring Boot 默认的缓存实现。

命中率到底多少算健康？

没有统一标准，但有几个经验阈值：>95% 优秀（说明热数据集完全装下了）；80~95% 正常（多数业务系统在这个区间）；60~80% 偏低，值得优化（先查 key 设计和容量）；<60% 说明缓存基本没起作用，要重新审视是否该缓存、缓存粒度是否太细。更重要的是看趋势和构成：如果命中率 90% 但 averageLoadPenalty 高达 100ms，说明每次 miss 代价极大，此时提升 1% 命中率的价值远大于命中率 70% 但 miss 只要 1ms 的场景。缓存的价值 = 命中率 × miss 代价，别只看命中率。

本地缓存和分布式缓存怎么选？

看四个因素：① 一致性要求——要求强一致（如库存、余额）必须用分布式缓存（或干脆不缓存）；能容忍秒级不一致（如用户资料、配置、字典）可以用本地缓存。② 数据量——热数据在单机内存能装下（几 GB 内）适合本地；TB 级必须分布式。③ 延迟要求——本地缓存是纳秒级（无网络），分布式是亚毫秒级。极致延迟用本地。④ 命中率与网络放大——本地缓存每加一台机器，回源量就翻倍；分布式缓存全局只有一份 miss。最常见的架构是两层：本地 Caffeine（纳秒级、抗热点）+ Redis（共享、一致），本地 miss 才走 Redis，配合 Pub/Sub 或短 TTL 做失效传播。这也是记忆里「多级缓存」章节讲的架构。
