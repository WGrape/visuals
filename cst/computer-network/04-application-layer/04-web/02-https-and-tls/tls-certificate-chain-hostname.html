TLS 证书链与主机名校验：锁标志从哪里来

沿浏览器验证证书的顺序解释信任根、中间证书、SAN、有效期和常见故障。

加密与身份验证是两件事

TLS 握手会协商密钥并加密后续流量，但客户端还必须确认“对方确实是我想访问的站点”。服务器提供证书和相关链信息，客户端验证签名链是否能连到本地信任的根证书、证书是否在有效期内、主机名是否匹配以及用途是否适合服务端认证。只有双方把加密与身份校验都做对，浏览器锁标志才有意义。

证书中的公钥不是直接拿来加密整个网页；现代 TLS 通常通过密钥交换建立会话密钥，再用对称加密保护数据。证书主要把站点身份与公钥绑定。把“有 HTTPS”解释为内容一定真实也不准确：恶意网站也可申请自己域名的合法证书，TLS 证明的是当前连接的域名身份，不证明网页业务内容可靠。

链是怎样搭起来的

假设服务器证书由中间 CA I 签发，I 又由根 CA R 签发。浏览器或操作系统预装并信任 R，服务器通常发送自己的证书和必要的中间证书，让客户端能逐级验证签名。根证书通常不需要服务器重复发送。若服务器漏配 I，部分客户端可能因本地刚好缓存了 I 而可用，另一些客户端却报“不完整证书链”。

证书链验证不是只看证书文件数量，还要检查各级签发关系、用途、约束与有效期。根信任来自客户端自身的信任库，而不是服务器说“请相信这个根”。企业代理若在终端安装了自己的根证书，可能对内部流量进行 TLS 检查；诊断时应明确这是受管设备的信任策略变化。

SAN 与主机名

浏览器访问 `api.example.test`，证书需要在 Subject Alternative Name 中包含该 DNS 名称或有效通配匹配。证书只覆盖 `www.example.test` 时，访问 api 子域会失败，即使两者指向同一个 IP。一个 IP 上可服务多个域名，客户端通过 TLS ClientHello 中的 SNI 等信息帮助服务器选择相应证书，之后仍要对访问的主机名做校验。

通配证书 `*.example.test` 常覆盖一层子域，例如 `api.example.test`，却不能按想当然覆盖 `a.b.example.test` 或裸域 `example.test`。具体匹配遵守客户端规则。排查证书错误时要记录访问 URL 的主机名、实际握手拿到的证书 SAN、SNI 值，而非只看证书文件在磁盘上存在。

有效期与时间问题

证书有 Not Before 和 Not After 时间。若客户端时钟严重偏差，合法证书也可能被判为尚未生效或已过期。证书更新时，负载均衡器、反向代理和各地域节点可能尚未全部加载新证书；从一个节点验证成功，不代表所有接入点已完成切换。监测应覆盖各域名和代表性节点，并在到期前留出更新与回滚时间。

服务器证书、私钥和中间证书要相互对应。把新证书配上旧私钥会导致握手失败；只上传新证书但未重载服务也可能继续展示旧证书。私钥应按最小权限保存，不能为了方便排查把内容贴进公开日志或页面。

撤销与信任边界

证书可能在到期前被撤销，例如私钥泄漏。OCSP、CRL 等机制提供撤销状态信息，但客户端是否阻断连接、是否使用 stapling、离线时如何处理取决于实现与策略。不能把“证书仍在有效期内”当作绝对安全证明。对于高价值系统，还需监控证书签发记录和异常替换。

证书正确也不代表端到端都加密：若 TLS 在 CDN 或负载均衡终止，后端链路可能重新建立 TLS，也可能是其他保护方式。系统图要标出每段连接的终止点、证书和信任域，才说得清数据在哪些节点可见。

一次故障排查

用户报告“浏览器提示证书不安全”。先确认访问的准确域名与时间，再看实际握手证书的 SAN、签发者、有效期和完整链。若只有某地域报错，检查该地域入口或 CDN 节点是否加载旧证书；若只有老系统报错，检查其信任库和中间链。若通过代理访问才报错，记录代理证书和终端信任配置。

修复后应分别从浏览器和命令行按相同主机名验证 TLS，并确认 HTTP 请求实际到达预期应用。不要通过关闭证书校验来“解决”生产故障，那只是移除了身份验证。

关键规则：服务器应发送 leaf + 中间证书（不要发根证书，发了也没用还浪费 1–2 KB）。缺中间证书是最常见的部署错误——部分浏览器（尤其 Firefox、Android、Java）不会自动补全，会直接报错，而 Chrome 会通过 AIA 补全从而“看起来正常”。

证书排查命令

# 查看对端证书链
openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null 2>/dev/null

# 只看关键字段
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName

# 验证链（CAfile 为系统信任库）
openssl verify -CAfile /etc/ssl/cert.pem leaf.pem
openssl verify -untrusted intermediate.pem -CAfile /etc/ssl/cert.pem leaf.pem

# 本地证书文件解析
openssl x509 -in cert.pem -noout -text | head -40

# 测试指定 SNI（多域名同 IP 时必须带 -servername）
openssl s_client -connect 1.2.3.4:443 -servername a.example.com

# 检查 OCSP Stapling
openssl s_client -connect example.com:443 -status </dev/null 2>/dev/null | grep -A5 'OCSP Response'

SAN、通配符与运维要点

  • CN 已被废弃：现代浏览器只认 SAN（subjectAltName），即使 CN 写了正确域名，没有 SAN 也会报 hostname mismatch。签发证书必须填 SAN。
  • 通配符只匹配一层：*.example.com 匹配 a.example.com，但不匹配 a.b.example.com，也不匹配 example.com（裸域）本身。
  • 证书数量限制：一张证书可含多个 SAN（常见上限约 100 个域名）；链长度一般 ≤ 4 层（太长会被拒）。
  • SNI 是必须的：同一 IP 托管多个 HTTPS 站点靠 TLS 握手时的 SNI 字段区分。老客户端（Android 2.x、Java 6、Python 2.7 默认）不支持 SNI，会拿到默认证书导致校验失败。
  • 过期监控：证书有效期已缩短到 90 天（CA/B 论坛决议，2026 年推进到 47 天），必须自动化续期（ACME / cert-manager）+ 到期告警（建议提前 30 天）。
  • HSTS：Strict-Transport-Security: max-age=31536000; includeSubDomains; preload，强制走 HTTPS 防降级；上 preload 前要确认全站（含子域）都能 HTTPS，否则等于自我 DDOS。
  • 排障顺序：① openssl s_client -showcerts 看链是否完整；② 看 SAN 是否含访问的域名；③ 看是否过期；④ 看系统信任库是否含对应根（Java 用 keytool -list -keystore $JAVA_HOME/lib/security/cacerts）。
浏览器能访问，但程序/移动端报证书错误，为什么？

典型的中间证书缺失：Chrome 会通过证书的 AIA 扩展自动下载中间证书，而 Java/Android/curl 等不会。抓 -showcerts 看服务端是否真的发了完整链，然后补上中间证书。

curl 报 unable to get local issuer certificate 怎么修？

要么服务端补齐中间证书（根本解决），要么客户端用 --cacert 指定包含该中间/根证书的 CA 文件。不建议用 -k（跳过校验，等于放弃安全）。

自检

证书由公开 CA 签发，但 SAN 没有访问的域名，浏览器应接受吗？

不应接受。签名链可信还不够，访问主机名必须匹配证书允许的身份。
