asyncio 取消与任务生命周期：超时后资源真的释放了吗

沿下载任务的超时、取消传播和 finally 清理，理解 TaskGroup、屏蔽取消与后台任务引用。

取消是协作式请求

Python 的 asyncio Task 并发执行协程。调用 task.cancel() 会请求在任务下一次可中断的 await 处注入 CancelledError；它不等于立即杀死线程，也不保证外部操作已经撤销。任务如果长时间执行纯 CPU 循环、没有 await，事件循环得不到控制权，取消和其他任务都可能延迟。下载任务若已向远端发出请求，取消本地等待也不会自动回滚远端已完成的写入。

任务生命周期包含创建、调度、等待、完成、失败和取消。创建任务后若没有明确所有者，程序退出时可能留下未观察的异常或未完成的连接。结构化并发鼓励在一个作用域里创建并等待子任务，让父任务退出前知道子任务的结局。Python 3.11 起的 TaskGroup 提供这类生命周期边界，但仍需要正确清理资源和设计外部副作用。

一次超时的时间线

假设调用方给下载设置 2 秒超时。2 秒到达时，超时作用域取消当前等待的任务；下载协程在下一次 await 处收到 CancelledError，执行 finally 关闭响应流与临时文件，然后取消才真正完成。如果 finally 中还要 await 某个清理操作，退出耗时可能超过 2 秒。因此超时是启动取消流程的期限，通常不是函数返回的硬实时上界。

若协程捕获 CancelledError 后悄悄忽略并继续无限循环，上层等待可能卡住，TaskGroup 与 timeout 的控制语义也被破坏。需要做必要清理时，通常在 finally 中执行后继续传播取消；若确有理由抑制取消，应明确恢复任务状态并承担后续生命周期责任。不要用宽泛异常处理把失败和取消混为一谈。

TaskGroup 遇到一个子任务失败

一组并行下载有三个子任务。一个任务抛出普通异常时，TaskGroup 会取消尚未完成的兄弟任务，等待它们完成清理，然后把异常组交给调用方处理。这样父级不必手工追踪每个创建的 Task。但如果兄弟任务吞掉取消，整个作用域可能久久不能退出。若某项业务允许部分成功，需要在子任务内部转换可预期的业务失败为结果值，或明确选择其他并发编排，而不是误以为 TaskGroup 会自动“忽略一项错误”。

与之相比，gather 的异常处理和其他 awaitable 的生命周期规则有不同细节，不能只凭“都是并发”替换。编排前先写清：一个失败后其他是否继续、结果顺序是否要保留、谁负责取消、是否要收集所有错误。正确性由这些业务语义决定。

机制能保证什么仍需注意

shield 与不可取消区

`asyncio.shield()` 可以保护内部 awaitable 不因外层取消而被直接取消，但外层等待者仍会收到取消；内部工作可能继续运行。若没有保存内部 Task 的引用并安排最终等待或记录异常，就可能留下脱离父级管理的后台任务。shield 适用于极少数必须完成的提交或清理步骤，不能把整个请求都包起来以“解决超时”。

外部副作用更需要幂等性。假设上传文件已经提交到远端，客户端超时后再次发起上传，可能创建两份对象。使用稳定操作 ID 或可查询的提交状态，才可以安全重试。取消解决本地任务调度，不能代替业务幂等协议。

资源清理的实操检查

网络响应、数据库连接、临时文件与信号量应放在 async with 或 try/finally 作用域中。若在获取信号量后遇到取消，必须确保 release 发生；async with 可减少遗漏。清理代码自身也可能失败，需要记录原始取消与清理异常，避免只留下“连接关闭失败”而丢失超时上下文。对长时间清理可设置独立预算，但不能在半写入状态下草率宣布成功。

测试时用可控的慢服务让任务刚好停在“获取连接后、收到响应前”和“远端已提交、响应未返回”两个位置，触发取消并检查连接池容量、临时文件数和远端对象数。只测普通成功路径无法发现资源泄漏。

把责任写成表

调用方负责给任务设时间预算、等待其终态并处理未知的外部结果；子协程负责在取消传播时释放本地资源；外部服务依赖业务 ID 处理重复请求；监控负责记录超时、实际退出耗时和残留任务数。若请求已结束，但后台 Task 仍持续执行且无人持有引用，资源消耗与异常会变成难排查的幽灵负载。

取消机制

import asyncio

async def worker(n):
    print(f"start {n}")
    await asyncio.sleep(10)
    return n * 2

async def main():
    t = asyncio.create_task(worker(1))
    await asyncio.sleep(0)          # 让出一次，让 task 开始执行

    print(t.done())                 # False（还在 sleep）
    t.cancel()                      # 请求取消
    try:
        await t
    except asyncio.CancelledError:
        print("task cancelled")     # <strong>必须捕获，否则异常向上传播</strong>

    print(t.cancelled())            # True

asyncio.run(main())

# 关键：cancel() 只是「请求」，
#   它会在协程<strong>下一个 await 点</strong>抛出 CancelledError
#   如果协程里没有 await，取消不会生效！

取消的正确写法与三个坑

坑表现正确做法
吞掉 CancelledErrorexcept Exception 捕获了它单独捕获 CancelledError 并重新抛出
取消后不清理资源泄漏（连接未关）用 try/finally 或 async with
屏蔽取消asyncio.shield() 用错只用于保护关键段，不是全部

正确写法

async def worker():
    try:
        await asyncio.sleep(100)
    except asyncio.CancelledError:
        # ✗ 错误：except Exception 会吞掉取消
        # ✓ 正确：捕获后做清理，然后<strong>重新抛出</strong>
        await cleanup()
        raise                        # 必须重新抛出！
    finally:
        await release_resource()     # 无论取消与否都执行

# 屏蔽取消（慎用）：保护一小段不可中断的操作
async def critical():
    await asyncio.shield(save_to_db())   # 外层取消时，save_to_db 仍会跑完
# 注意：shield 只保护内层任务不被取消传播，
#       外层的 await 仍会抛 CancelledError

# 超时控制（最常用的取消场景）
try:
    await asyncio.wait_for(slow_op(), timeout=5)
except asyncio.TimeoutError:
    print("超时")                    # wait_for 内部就是 cancel

最容易踩的一条：except Exception 在 Python 里能捕获 CancelledError（因为 CancelledError 继承自 BaseException 而非 Exception…实际上 Python 3.8+ 起 CancelledError 继承自 BaseException，所以 except Exception 不会捕获它）。但 except BaseException 和裸 except: 会吞掉取消——务必避免。

API版本特点

TaskGroup

# 3.11+ 推荐：TaskGroup（结构化并发）
async def main():
    async with asyncio.TaskGroup() as tg:
        t1 = tg.create_task(fetch(1))
        t2 = tg.create_task(fetch(2))
    # 退出 with 块时，<strong>自动等待所有任务完成</strong>
    print(t1.result(), t2.result())

# TaskGroup 的关键优势：
#   1) 任一任务失败 → 自动取消其他所有任务（不会留孤儿任务）
#   2) 退出时保证全部完成，不会漏等
#   3) 异常用 ExceptionGroup 聚合

# 对比 gather 的老问题：
#   await asyncio.gather(a(), b())
#   若 a 抛异常，b 仍在后台跑 → <strong>孤儿任务 + 异常难定位</strong>

结构化并发的核心保证：任务的生命周期被限制在一个明确的作用域内。离开作用域时，要么全部成功完成，要么全部被取消——不会留下「跑了一半没人管的任务」。这是 3.11 引入 TaskGroup 的主要动机，也是现代并发编程的共识（Kotlin、Swift、Rust 都采用）。

自检 Q&A

Q：task.cancel() 之后为什么任务还在跑？

A：两个原因——① 协程里没有 await 点：取消只在 await 处生效，纯计算的代码段无法被中断（这是协作式调度的固有限制）；② 吞掉了 CancelledError：如果代码用 except BaseException: pass 或裸 except 捕获后不重新抛出，取消就被「吃」了，任务会继续。诊断：看协程里是否有密集循环且没有 await，必要时在循环中插入 await asyncio.sleep(0) 作为让出点。

Q：asyncio.run() 报「Event loop is closed」怎么办？

A：通常是因为有任务没被等待就退出了。asyncio.run() 在结束时关闭事件循环，若还有后台任务在跑，它们会报错。解法：① 用 TaskGroup 或显式 await 所有任务；② 退出前统一取消：for t in asyncio.all_tasks(): t.cancel()；③ 检查是否用了 create_task 却没保存引用（任务可能被 GC）。

Q：取消时怎么保证资源被释放？

A：用 try/finally 或 async with，不要用裸的 try/except。因为取消是通过抛异常实现的，finally 一定会执行。但要注意：finally 里不要再写可能挂起的 await——取消后再次 await 可能立即又抛 CancelledError。Python 3.8+ 提供了 asyncio.shield() 保护关键的清理操作，或把清理设计成同步的、幂等的。

Q：gather 和 TaskGroup 该用哪个？

A：3.11+ 优先 TaskGroup。原因是它提供结构化并发保证：一个任务失败会自动取消其余任务，避免孤儿任务与资源泄漏；异常用 ExceptionGroup 聚合，能一次看到所有失败。gather 的问题是：默认第一个异常会立即抛出，但其他任务继续在后台运行，容易导致「程序退出了但任务还在跑」的诡异现象。只有当你确实需要「即使有失败也等所有任务跑完并收集异常」时，才用 gather(..., return_exceptions=True)。

调用 task.cancel() 之后，可以立即认定远端写入已撤销、连接也已关闭吗？

不能。取消要等协程运行到可中断点并完成清理，远端副作用还需要单独确认。
