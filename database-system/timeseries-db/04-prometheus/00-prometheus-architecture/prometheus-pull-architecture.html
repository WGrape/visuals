Prometheus 拉取模型与数据流架构

沿服务发现、目标抓取、本地 TSDB 与规则评估理解拉模型的设计边界。

Prometheus

01为什么是拉取（Pull）而不是推送（Push）

这是 Prometheus 与大多数监控系统最根本的分歧。推送模型里，每个被监控程序自己知道监控服务器在哪、要往哪发；拉取模型里，被监控方只需要把指标挂在一个 HTTP 端点上，由 Prometheus 决定抓谁、多久抓一次。

拉取的好处
  • 被监控服务不需要知道监控系统的地址，配置集中在监控侧
  • Prometheus 自己能判断目标是否活着：up 指标天然就是存活探测
  • 抓取失败、超时、目标下线都有明确的指标可查，不会出现「数据没了但没人知道」
  • 本地开发和调试可以直接 curl localhost:8080/metrics 看原始数据
拉取的代价
  • 需要服务发现机制告诉 Prometheus 抓谁（K8s、Consul、文件或自定义 SD）
  • 被监控方必须能被 Prometheus 网络可达，跨网段/VPC 场景要额外打通
  • 批处理任务可能执行完就退出了，抓不到——这时才需要 Pushgateway
Pushgateway 是特例不是常规。它适合「跑完就退出、无法被拉取」的短任务（定时备份脚本、CI 任务）。常驻服务用它会带来两个问题：指标变成单点瓶颈，而且任务挂掉后 Pushgateway 仍会继续返回上一次的旧值，形成「僵尸指标」。用它时务必配合 push_time_seconds 判断新鲜度。

02整体架构与数据流向

Prometheus 主动去目标上「拉」指标；告警判定在 Server 内完成，通知交给 Alertmanager；长期存储走 remote_write。
  • Retrieval（抓取）：按 scrape_interval 周期性地从服务发现给出的目标列表拉取 /metrics，写入本地 TSDB。常见间隔是 15s 或 30s。间隔越短，数据越细，但存储与查询压力线性增长。
  • TSDB（本地存储）：自研的时序存储引擎，按时间分块，配合 WAL 保证崩溃不丢数据。
  • HTTP Server / PromQL：对外提供查询接口，Grafana 就是它的主要消费者。
  • Rules（规则求值）：周期性执行 recording rule（预计算）与 alerting rule（告警判定）。
  • Alertmanager：独立组件。Prometheus 只判断「条件是否满足」并推送告警，去重、分组、抑制、静默、路由到具体通知渠道都由 Alertmanager 负责。
分工要点：Prometheus 负责「指标对不对」，Alertmanager 负责「通知怎么发」。把静默、分组规则写进 Prometheus 是错误的——它根本不管这些。

03拉模型带来的三个必然推论

推论原因实际影响
指标是「采样」而非「事件」只在抓取时刻读一次值，两次抓取之间的变化不可见短于抓取间隔的尖峰会被完全漏掉。想抓瞬时尖峰必须缩短间隔或改用直方图/日志
时间戳由抓取方决定Prometheus 记录的是「我抓到它的时刻」，不是「指标产生的时刻」乱序和迟到数据在本地存储里基本不存在，但通过 remote_write 写入外部系统时仍可能遇到
目标必须无状态地暴露全量指标每次抓取都是一次完整的当前状态快照不要在 /metrics 里做增量或「只返回上次之后的变化」

04Prometheus 擅长什么、不擅长什么

擅长
  • 基础设施与服务的数值型指标：QPS、延迟、错误率、资源水位
  • 多维标签下的聚合分析：按实例、按接口、按地域下钻
  • 实时告警（秒级到分钟级）
  • 云原生场景，尤其是 Kubernetes 生态
不擅长
  • 100% 精确的计费/审计数据：采样 + 可能的抓取失败，不是账本
  • 高基数维度：把 user_id、trace_id 当 label 会瞬间撑爆内存
  • 原始事件/日志：应该交给日志系统或链路追踪
  • 超长周期存储：本地 TSDB 面向近期数据，长期留存通常走远端存储或降采样
「Prometheus 只能存 15 天」是误解。本地保留期只是默认值，可以改配置延长；真正的问题是单机容量与查询性能随数据量下降，所以长期留存一般用 remote_write 写入 VictoriaMetrics、Thanos、Mimir 这类远端方案，而不是硬调大本地保留期。
