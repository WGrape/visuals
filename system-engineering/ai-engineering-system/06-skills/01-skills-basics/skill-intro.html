大模型的能力模块：Skill

Skill = 可被重复调用的一组能力，让 Agent 拥有 "会做的事"

1 为什么需要 Skill？

解决普通对话的三大问题：每次重新描述、输出不稳定、无法重复使用

普通对话

  • 每次重新描述需求
  • 输出格式不稳定
  • 无法沉淀与复用
  • 经验无法积累
→

使用 Skill

  • 能力可复用，无需重复描述
  • 输出更稳定、可控
  • 高效可沉淀，积累资产
  • Agent 开始有"会做的事"

🚀 提升效率

一次封装，多次复用。将高频任务固化为 Skill，节省大量重复投入。

🎯 保证输出一致

固定的 Prompt + 流程保证每次调用输出格式稳定，便于下游使用。

🧠 沉淀知识

把经验转化为能力资产，让 Agent 持续进化，越来越"能干"。

3 Skill 和 Tool 有什么区别？

Tool 是单个工具，Skill 是完成任务的方法

🔧 Tool（工具）

单一能力，执行原子操作

🔍 搜索 🌤 天气 🧮 计算 📅 日历

每个 Tool 只做一件事，是最小的执行单元。调用即返回结果，不包含流程控制。

Skill 到底解决什么问题

提示词解决「怎么说」，工具解决「能动手」，而 Skill 解决的是「把某类任务的完整做法固化下来，并且按需加载」。它是一份可复用的能力包：既有指令，也可以带脚本、模板和参考资料。

渐进式加载：先只挂目录，命中后再翻正文，是把大量能力塞进有限上下文的关键
为什么不是提示词提示词每次都要用户重说，且无法携带脚本与参考资料
为什么不是工具工具只提供动作，不规定什么时候用、按什么步骤用
核心价值一一致性：同一类任务每次都按同一套规范产出
核心价值二省上下文：不命中就不占额度，命中才加载

和 Prompt / Tool / MCP / Subagent 怎么区分

这几个概念经常被混用，区分的关键是问两句话：它规定流程吗？它需要外部连接吗？

概念本质是否规定流程典型用法
Prompt（提示词）一段给模型的指令文本可以，但靠用户每次手写临时、一次性的表达
Tool（工具）一个可被模型调用的动作不规定查天气、跑命令、写文件
MCP工具与资源的标准接入协议不规定把外部系统接进模型生态
Skill指令 + 脚本 + 资源的打包能力规定，这是它的核心按规范完成某一类完整任务
Subagent带独立上下文的子执行体由调用方给定长任务隔离、并行探索

组合关系：Skill 内部可以调用 Tool，Tool 可以由 MCP 提供；复杂 Skill 还可以派发 Subagent 去并行收集信息。它们是不同层次的东西，不是互斥选项。

一个 Skill 的目录结构与加载顺序

结构设计的唯一目的就是让「不需要的东西永远不被读进来」。所以入口文件要短，细节都下沉到可按需读取的附属文件里。

my-skill/ SKILL.md # 入口：名字、说明、主流程（务必短） reference/ api-spec.md # 细节规范，按需读取 faq.md # 常见问题的既有结论 templates/ report.md # 输出模板，保证格式稳定 scripts/ validate.py # 确定性的校验逻辑，交给脚本而不是让模型心算 # SKILL.md 顶部用少量元信息描述自己 --- name: my-skill description: 当用户需要做 X 类任务时使用；不适合 Y 场景 --- # 正文只写：适用场景、步骤、检查点、反例 # 能脚本化的判断一律写进 scripts，别让模型靠推理硬算

入口文件为什么要短

因为它一旦被激活就会整体进入上下文。把细节拆到附属文件后，只有真正需要的那一份才会被读进来，其余部分永远不占额度。

什么时候该写成脚本

凡是确定性逻辑——格式校验、字段比对、计数、排序、正则匹配——都应该交给脚本。让模型做确定性计算既慢又不可靠，而脚本每次结果一致。

写好一个 Skill 的七个要点

说明要写清边界既写什么时候用，也写什么时候不要用
主流程要可执行写成编号步骤，而不是原则性描述
反例比正例重要把常见错误做法明确写出来
输出要有模板模板是保持一致性的最省力手段
确定性逻辑脚本化校验、计数、排序交给代码
参考资料按需拆入口保持短，细节下沉
留检查点每步结束时自检，比最后统一检查更有效
版本与回归改动后用同一批评测任务验证不倒退
Skill 和「把提示存成文件」有什么区别？

区别在于加载机制与携带物。普通提示文件要么全量塞进上下文，要么靠人手动粘贴；Skill 先只注册名字与说明，命中后才加载正文，并能在需要时读取附带的脚本、模板与参考资料。这让「同时挂载几十种能力」成为可能。

为什么 Skill 的说明里要写「什么时候不要用」？

因为只写适用场景时，模型倾向于过度触发，把不该用这套流程的任务也套进去。明确写出不适用场景，能显著降低误触发，这一点比堆正面描述更有效。

Skill 里的脚本失败了怎么办？

把失败信息结构化返回给模型，让它据此调整参数重试或换路径，而不是让脚本静默失败。同时脚本应该自带清晰的错误说明——错误信息本身就是给模型看的提示。

多个 Skill 都能命中怎么办？

靠说明的边界区分。如果仍频繁冲突，说明这两个 Skill 的划分本身有问题，应该重新按「任务类型」而不是按「技术领域」来切分，边界才会清晰。

Skill 的结构与加载机制

Skill 本质是打包好的领域知识 + 工作流 + 可执行脚本，按需加载进上下文，让通用模型瞬间具备某领域的专业能力。

组成内容加载时机占 token
元数据（frontmatter）name + description常驻（系统提示里）每个几十~上百 token
正文 SKILL.md工作流、规范、示例触发时才加载1k~5k token
脚本 scripts/可执行代码不进上下文，直接执行0（只把输出带回来）
参考资料 references/详细文档、API 手册按需读取（grep 或整篇）按需
模板 assets/要产出的文件骨架按需拷贝按需

结构与 frontmatter

# 目录结构（Claude Code / WorkBuddy 通用约定）
my-skill/
├── SKILL.md              # 必需：主文档
├── scripts/              # 可选：可执行脚本
│   └── validate.py
├── references/           # 可选：详细参考
│   └── api-reference.md
└── assets/               # 可选：模板
    └── report-template.html

# SKILL.md 的 frontmatter（只有 name 和 description 会被常驻读取）
---
name: pdf-extract
description: 从 PDF 提取文本与表格、填写表单、合并拆分文档。
             当用户提到 PDF、pdf、表单填写、文档抽取时使用。
---

# 正文（触发后才加载）
## 工作流
1. 用 scripts/extract.py 提取文本
2. ...

# 关键：description 决定「会不会被触发」，要写清楚
#   ✅ "当用户要求 X 或提到 Y 时使用"    <- 包含触发词
#   ❌ 描述太抽象，如「这个技能很强大」    <- 不会被触发

核心设计是渐进式披露（progressive disclosure）：常驻的只有 name + description（几十 token），正文等真正用到了才读进来，脚本干脆不进上下文只把执行结果带回来。这样装 20 个 skill 也只占几百 token。写 skill 时最重要的决策就是什么该放正文、什么该放 scripts/references。

Skill vs 其他扩展方式

方式解决什么适合不适合
Prompt / 系统提示一次性指令简单、临时复用、需要多文件的复杂流程
Skill可复用的领域知识与工作流有固定步骤 + 领域知识 + 可能要跑脚本只需要一两句指令
Tool / Function Calling执行动作（查库、调 API）需要外部系统交互纯知识/规范
MCP Server跨应用复用的工具服务工具要被多个客户端复用只在一个应用里用
RAG外部知识检索知识量大且变化固定流程与规范
Subagent独立上下文的子任务任务会污染主上下文（如大量搜索）简单步骤
  • 判断口诀：要让模型知道怎么做 → Skill；要让模型能做某个动作 → Tool/MCP；要让模型知道某个事实 → RAG。
  • 脚本优于说明：能用脚本确定性完成的事（格式转换、校验、统计），就别让模型一步步照着文字做——更快、更准、不占 token。
  • 正文要短：SKILL.md 控制在 500 行以内，细节放 references/。正文太长会挤占工作上下文。
  • 给示例：一两个完整的输入→输出示例，比十段说明有效。
Skill 和 Prompt 模板有什么区别？

三点：① 触发方式——Skill 由模型根据 description 自动判断要不要用，Prompt 要人工/代码显式选择；② 可携带资源——Skill 能带脚本、参考文档、模板，Prompt 只是一段文本；③ 渐进加载——Skill 的正文按需加载，Prompt 模板一旦注入就常驻占 token。所以当你的指令超过几百字、要复用、或需要配套文件时，就该做成 Skill。

为什么我的 Skill 从来不被触发？

九成是 description 写得不好。它要包含用户可能说出的原话关键词（中英文都要，如「PDF、pdf、表单、extract」），并明确「什么时候用」。写得抽象（「处理文档」）既不会触发，也可能误触发。检查方法：直接问模型「你现在有哪些 skill」或给它一个应该触发的请求，看有没有加载。

Skill 里应该放多少内容？

遵循三层：① SKILL.md 放主干流程（看完就能做对 80% 的事），控制在几百行；② references/ 放细节与边界情况，正文里写明「遇到 X 情况时读 references/Y.md」；③ scripts/ 放确定性操作。这样既保证能力完整，又不让上下文被无关内容撑爆。
