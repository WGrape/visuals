存储结构：堆表、页与 TOAST

① 堆表与 relfilenode：表就是一堆文件② 页（Page）与元组（Tuple）③ TOAST：大字段的行外存储④ FSM 与 VM：怎么快速找到空位⑤ 表膨胀（Bloat）与治理⑥ 常见问法

① 堆表与 relfilenode：表就是一堆文件

PostgreSQL 里每张表是一个堆（Heap）——一个无序的行集合，写入顺序决定物理顺序。表的数据文件以 relfilenode 命名（可在 pg_class 中查到），单个文件超过 1GB 自动分段（relfilenode.1、relfilenode.2…）。索引是独立的文件，与表数据分开存放。

-- 查看表对应的物理文件
SELECT relname, relfilenode, relpages, reltuples
FROM pg_class WHERE relname = 'orders';

-- 查看数据目录路径
SHOW data_directory;
-- 定位文件：SELECT pg_relation_filepath('orders');
注意：TRUNCATE、VACUUM FULL、CLUSTER 会重建表并改变 relfilenode；而普通的 DELETE/UPDATE 不会。这就是为什么复制工具要小心处理 DDL。

表空间的本质

表空间只是一个目录别名：把不同的表放到不同的磁盘上，用于 IO 隔离或容量管理（如把历史归档表放到廉价盘）。它不是 MySQL 那种「一个库一个目录」的逻辑隔离。

② 页（Page）与元组（Tuple）

数据文件按 8KB 页（默认 block_size，编译期确定）组织。每个页内含若干元组（行版本），以及页头、行指针数组（ItemId）和空闲空间。

元组头里的 MVCC 字段

字段含义作用
xmin插入该行版本的事务 ID决定该版本对谁可见
xmax删除/更新该版本的事务 ID（0 表示未删）决定该版本是否已被作废
ctid(块号, 行指针偏移)行的物理地址；UPDATE 后指向新版本
infomask标志位（已提交/已回滚/已冻结…）避免频繁查 clog
关键理解：UPDATE = INSERT + 旧版本标记删除。旧版本仍留在页里直到 VACUUM 回收，所以频繁 UPDATE 的表会「膨胀」。

③ TOAST：大字段的行外存储

一行必须能放进一页（约 8KB 减去头部）。当某行的可变长列（text、jsonb、bytea）超过约 2KB（TOAST_TUPLE_THRESHOLD）时，PostgreSQL 会先压缩，仍放不下就切块存到附属 TOAST 表，主表只留一个指针。

PLAIN

不压缩、不行外存储（用于定长类型）

EXTENDED

默认：先压缩，再行外存储

EXTERNAL

只行外存储、不压缩（适合已压缩的图片）

MAIN

先压缩，压缩后仍太大才行外存储

-- 查看带 TOAST 的表
SELECT relname FROM pg_class WHERE reltoastrelid != 0;

-- 修改列的存储策略
ALTER TABLE articles ALTER COLUMN body SET STORAGE EXTERNAL;

-- TOAST 表的大小
SELECT pg_size_pretty(pg_total_relation_size('articles'));
性能提示：SELECT 时若不访问 TOAST 列，就不会读 TOAST 表——所以避免 SELECT * 对宽表意义重大。另外 LIKE '%x%' 这类操作必须解压 TOAST，代价很高。

④ FSM 与 VM：怎么快速找到空位

FSM 空闲空间映射

记录每个页的空闲空间量，插入时快速定位可容纳的页，避免逐页扫描

VM 可见性映射

标记「页内所有元组对所有事务可见」，让 VACUUM 跳过这些页，也支持 index-only scan

index-only scan

若 VM 标记页为全可见，且查询列都在索引里，可完全不回表

VACUUM 与 VM

VACUUM 清理死元组后设置 VM 位；之后的 UPDATE/INSERT 会清除该位

这也是为什么及时 VACUUM 能显著提升 index-only scan 命中率——很多人只把 VACUUM 当「回收空间」，忽略了它在可见性地图上的作用。

⑤ 表膨胀（Bloat）与治理

MVCC 下 UPDATE/DELETE 产生的旧版本不会立即释放，而是等待 VACUUM 标记为可复用。若长时间不清理，或存在长事务阻止回收，文件会不断膨胀——这就是 bloat。

-- 安装扩展后查看膨胀
CREATE EXTENSION pgstattuple;
SELECT * FROM pgstattuple('orders');
-- dead_tuple_percent 高说明膨胀严重

-- 常用估算查询（基于统计信息）
SELECT relname,
       n_live_tup, n_dead_tup,
       round(n_dead_tup * 100.0 / GREATEST(n_live_tup + n_dead_tup, 1), 2) AS dead_pct,
       last_autovacuum
FROM pg_stat_user_tables
WHERE n_dead_tup > 1000
ORDER BY n_dead_tup DESC LIMIT 20;
治理手段做法代价
常规 VACUUM标记死元组空间可复用，不还给操作系统低，可在线
VACUUM FULL重写整表，真正收缩文件ACCESS EXCLUSIVE 锁，需双倍空间
pg_repack在线重建表，锁时间极短需额外扩展，需磁盘
分区表按时间分区，旧分区直接 DETACH/DROP改造成本
填充因子 fillfactor页内预留空间，减少跨页更新牺牲一点空间换 UPDATE 性能
最常见的膨胀原因：① 存在长时间未提交的事务（它之后的死元组都不能回收）；② 未提交的复制槽 / 逻辑复制持有旧版本；③ autovacuum 参数过保守跟不上写入速度；④ 孤儿预备事务（prepared transaction）。排查顺序：pg_stat_activity → pg_replication_slots → pg_prepared_xacts。

⑥ 常见问法

Q：PostgreSQL 的 UPDATE 和 MySQL InnoDB 的 UPDATE 有什么不同？

A：PostgreSQL 的 UPDATE 是「插入新版本 + 旧版本留在原处」，旧版本需要 VACUUM 回收，因此频繁更新会膨胀；InnoDB 也是类似的 MVCC，但把旧版本放到 undo 表空间，由 purge 线程清理，主键索引里是「原地更新 + 回滚段」，因此聚簇表本身的膨胀较轻，代价是 undo 表空间可能暴涨。结论：PG 要重点盯 autovacuum，MySQL 要重点盯 history list length。

Q：为什么表删了一半数据，文件大小没变？

A：因为 DELETE 只是把行标记为死元组（设置 xmax），空间仍被占用、只是可复用；只有 VACUUM FULL / CLUSTER / pg_repack / TRUNCATE 这类重写表的操作才会把空间还给操作系统。治理建议：普通 VACUUM 让空间可复用（对后续写入有利），真正要收缩文件则用 pg_repack 在线重建，避免 VACUUM FULL 的长时间排他锁。

Q：ctid 能不能当主键用？

A：不能。ctid 是物理地址 (块号, 偏移)，VACUUM FULL、CLUSTER、UPDATE 都会改变它，而且表重写后全部失效。它只适合在单条语句内做临时技巧，例如快速去重：DELETE FROM t a USING t b WHERE a.ctid < b.ctid AND a.id = b.id;（同一语句内 ctid 稳定）。

Q：fillfactor 该怎么设？

A：默认堆表是 100（页填满）、B-tree 索引是 90。频繁 UPDATE 的表建议设 70~90，让页内留出空间容纳新版本，从而减少跨页迁移、降低索引更新代价（PG 的 HOT 更新还能在页内复用索引指针，避免索引膨胀）。设置方式：ALTER TABLE t SET (fillfactor = 80);——注意只对之后写入的新页生效，已有页需 VACUUM FULL / pg_repack 重写。

Q：一行最大能多大？一张表最大能多大？

A：单行：受页大小限制，但通过 TOAST 可以把大字段放到行外，因此实际可存约 1GB 级别的单个字段值（TOAST 最大约 1GB）。单表：默认受文件系统限制，理论上限 32TB；超过 1GB 会分裂成多个段文件。单个字段：text/jsonb/bytea 经 TOAST 后上限约 1GB。实践建议：单个 JSON 文档最好不要超过几 MB，否则 TOAST 的读写与解压开销会很可观。
