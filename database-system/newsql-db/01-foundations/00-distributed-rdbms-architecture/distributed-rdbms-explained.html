一句话总结：当单机 MySQL 扛不住时，传统做法是「分库分表 + 中间件」—— 路由和跨片事务常需中间件与应用共同处理。NewSQL（原生分布式关系型数据库）把部分分片路由、复制和事务协调交给数据库， 但应用仍需检查 SQL 兼容性、数据分布与热点、跨节点操作代价，以及失败后的重试语义。

01单机数据库的三个天花板

💾 容量天花板

单实例容量增加后，备份、DDL 和故障恢复可能超出业务窗口；拐点由硬件、表结构、运维方案与恢复目标决定。

⚡ 写入天花板

主库写入会受 CPU、锁竞争、日志刷盘、索引维护等因素限制。增加只读副本通常不能提高单主写入能力。

🧮 连接与 CPU

复杂查询与高并发事务可能争用 CPU、内存和连接资源；连接池与实际负载决定瓶颈出现的位置。

于是有了两条路线：中间件分库分表（ShardingSphere、MyCat）与原生分布式数据库（TiDB、OceanBase、CockroachDB）。

03路线二：原生分布式（NewSQL）

NewSQL 的目标是在分布式部署中继续提供 SQL 接口和事务能力，把分片路由、复制与故障恢复更多地交给数据库处理。 各产品的 SQL 兼容范围、隔离级别与跨节点事务代价不同，迁移应用前仍需逐项验证。

图 2：以 TiDB 为例说明 SQL 层、PD 与 TiKV Region；其他产品的组件划分不同
关键差异：存储层自己知道数据在哪、如何复制、如何迁移。 TiDB 等系统可自动调度数据副本；加节点后仍要监控迁移负载、热点和容量。OceanBase 等产品的分区与再均衡策略需按产品配置评估。

04常见机制与产品能力

① 自动分片（Range / Hash）

数据库把数据分布到多个可管理单元：TiDB 的 Region 按键范围组织并可自动分裂，OceanBase 的 Partition 遵循表分区方案； 二者不是同一个概念，也没有统一的默认大小。范围分布利于部分范围访问，但分布键和热点仍需设计。

② 多副本一致（Raft / Paxos）

副本数量与复制协议依产品配置：TiDB 的 TiKV 使用 Raft，OceanBase 使用 Paxos 系共识机制。 多数派确认可以保护已提交写入，但故障范围、异地部署和切换配置会影响实际 RPO/RTO； 不能把“零丢失、秒级恢复”当作所有部署的保证。

③ 分布式事务（2PC + 乐观/悲观锁）

TiDB 使用基于 Percolator 的提交协议处理跨 Region 事务；其他产品的事务协议与时间戳机制不同，不能统一概括为同一种 2PC 或 TSO。 MVCC 与时间戳机制可支持分布式一致性快照，但隔离级别、读取新鲜度、冲突处理和重试方式应按产品及配置核对。

图 3：抽象 2PC 流程；具体锁、日志和故障恢复机制依数据库实现而异

④ 部分产品提供 HTAP 能力

部分 NewSQL 产品还提供事务与分析混合负载能力，但这不是所有产品的共同特征。 例如 TiDB 可让 TiKV 服务事务、TiFlash 列存副本服务分析；副本复制与查询新鲜度仍有边界。

TiDB 的做法

TiKV（行存）服务事务，TiFlash（列存）作为 Raft Learner 异步复制， 优化器按代价自动选择走行存还是列存。

OceanBase 的做法

部分版本支持行列混合存储与分析查询能力；列存是否启用、查询新鲜度和隔离方式需按版本、表配置与执行计划核对。

重要提醒：NewSQL 不是万能的。它用网络开销换扩展性与高可用。 分布式系统可能增加跨节点通信与事务协调成本；单分片点查的实际延迟仍取决于部署、缓存和负载。 数据量与可用性要求还不需要分布式能力时，应先评估单机或主从方案，再决定是否承担额外运维成本。

06常见疑问

Q：什么时候该考虑从单机 MySQL 迁移到 TiDB？
A：先确认瓶颈：单实例容量、写吞吐或恢复窗口是否已不能满足目标，以及现有分库分表的跨片查询与扩容成本。 再用真实 SQL、事务、数据分布和故障场景验证 TiDB 的兼容性与收益；只凭行数不能决定迁移。
Q：NewSQL 的分片键还需要设计吗？
A：仍需设计。以 TiDB 为例，Region 按键范围自动分裂，但递增写入键可能持续落在相邻 Region，形成写热点。 应按表的主键与聚簇索引设置检查实际写入分布；AUTO_RANDOM 或适用时的 SHARD_ROW_ID_BITS 可用于打散写入， 同时要权衡范围查询、索引大小和迁移兼容性。其他 NewSQL 产品的分布规则需要分别核对。
Q：既然有分布式事务，跨分片 JOIN 就能随便用了吗？
A：不能无条件使用。跨节点 JOIN 可能需要网络数据交换，数据量较大时成本可能显著高于本地 JOIN。 应检查执行计划与数据分布，减少高频跨节点数据交换；是否能通过共置、分区或索引改善，取决于具体产品和查询形态。

选型的关键不是「谁更强」，而是三个硬约束：① 单库数据量是否真的超过单机上限（一般 > 2~5TB 且有明显增长）；② 写 QPS 是否超过单机能力；③ 是否能接受改分片键与业务 SQL。三个都是否定的话，先别上分布式——单机 + 读写分离 + 归档往往够用很久。

上手前必知的量化事实

项典型值 / 事实
单机 MySQL 舒适区数据量 < 2TB、写 QPS < 3000~5000（视硬件与索引而定）
分片键选择必须选高基数、查询高频、分布均匀的列；选错等于把压力还压在一片上
跨片查询代价N 片的全表扫描 = N 次并行的片内扫描 + 汇总，没有分片键条件的查询会打满所有片
分布式事务延迟2PC / Percolator 至少多一轮网络 RTT，跨地域时延迟会显著放大

热点按时间/租户分片容易出现「最新一片是热点」，需加哈希后缀打散

SQL 注意事项

-- 分库分表下最典型的“不能写”的 SQL（ShardingSphere 场景）
SELECT * FROM orders WHERE user_id = ?;                 -- ✅ 带分片键，路由到单片
SELECT * FROM orders WHERE order_no = ?;                -- ⚠ 非分片键，全片扫描（需要建映射表或基因法）
SELECT a.*, b.* FROM orders a JOIN users b ON ...;      -- ⚠ 跨片 JOIN，尽量改成“先查再拼”或冗余字段
SELECT COUNT(*) FROM orders;                            -- ⚠ 全片聚合，考虑维护计数表
SELECT * FROM orders ORDER BY create_time LIMIT 10;     -- ⚠ 跨片排序，需在中间层归并

-- NewSQL（TiDB 为例）看执行计划时重点关注
EXPLAIN ANALYZE SELECT ...;   -- 看是否出现全表扫（TableFullScan）与估算行数偏差
SHOW TABLE regions;           -- 看数据分布是否倾斜
SELECT * FROM information_schema.tiflash_replica;   -- 列存副本是否就绪
什么时候真的需要分布式？

数据量或写吞吐单机撑不住，且已做过索引优化、归档、读写分离。分布式库带来的复杂度是数量级的，别为了「技术先进」上车。

分片键怎么选？

先列 top 10 高频查询，找一个能覆盖最多的列；再看分布是否均匀（用 COUNT(*) GROUP BY 验）；最后确认它没有单调递增导致的写热点。

能不改代码迁移吗？

共享存储路线（Aurora/PolarDB）几乎可以；NewSQL 兼容性较好但需验证 SQL 与事务语义；分库分表通常要改 SQL 与分片设计。
